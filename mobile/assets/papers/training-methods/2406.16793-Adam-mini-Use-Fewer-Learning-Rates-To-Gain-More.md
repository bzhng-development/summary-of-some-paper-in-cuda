# Adam-mini: Use Fewer Learning Rates To Gain More

**ArXiv:** [2406.16793](https://arxiv.org/abs/2406.16793)

## 🎯 Pitch

This paper proposes **Adam-mini**, a memory-efficient optimizer that reduces Adam's memory footprint by roughly 50% while maintaining on-par or better performance across language model pre-training, supervised fine-tuning, and RLHF.

---

## 1. Executive Summary

This paper proposes **Adam-mini**, a memory-efficient optimizer that reduces Adam's memory footprint by roughly 50% while maintaining on-par or better performance across language model pre-training, supervised fine-tuning, and RLHF. The core mechanism is a **difficulty-conditioned partition principle** based on Hessian structure—specifically, the observation that the Hessian of neural networks exhibits a near-block-diagonal structure where each dense sub-block can be served by a single learning rate rather than the per-parameter learning rates that Adam maintains. Adam-mini operationalizes this by partitioning model parameters according to the smallest dense Hessian sub-blocks (e.g., partitioning query and key by attention heads, value and MLP layers by output neurons) and replacing Adam's per-parameter second-moment estimates with block-wise averages, thereby eliminating over 99.9% of the storage for the second-order momentum `v`. The paper demonstrates that Adam-mini achieves 49.6% higher throughput than AdamW when pre-training Llama 2-7B on 2× A800-80GB GPUs—translating to a 33% reduction in wall-clock time—while matching AdamW's loss curves across scaling law experiments from 39M to 13B parameters, establishing that aggressive reduction of learning rate resources is harmless only when parameters are partitioned to respect the underlying Hessian block structure rather than using naive layer-wise or default PyTorch groupings.

## 2. Context and Motivation

### The Core Problem: Adam's Memory Footprint Is a Bottleneck for LLM Training

The paper addresses a problem that has become increasingly urgent with the scaling of large language models: **Adam's optimizer states consume at least 2× the memory of the model parameters themselves**, and this memory consumption has become a major barrier to training LLMs efficiently—or at all—on available hardware. The authors quantify this concretely (Section 1): to train a 7B model, Adam alone requires about 56 GB for its first-order momentum `m` and second-order momentum `v`, and with gradients included, a total of 86 GB is needed. This is expensive even for cutting-edge GPUs like the A100-80GB.

The practical consequences extend beyond hardware costs. As the authors note, the memory burden forces practitioners to adopt CPU offloading and optimizer state sharding via techniques like ZeRO (Rajbhandari et al., 2020), which introduce latency and slow down training. The authors identify three specific benefits of reducing optimizer memory:

- **Lowering the barrier to entry**: more researchers, especially those with limited GPU resources, can participate in LLM training.
- **Reducing hardware requirements**: fewer GPUs are needed to train a model of a given size, yielding substantial savings in cost and energy.
- **Increasing throughput**: easing the burden of CPU offloading and model sharding accelerates the training process itself.

### Why This Problem Is Hard: We Don't Know Which Parts of Adam Are Essential

The paper frames the challenge as fundamentally one of **understanding**: we lack a clear picture of which components of Adam are indispensable for its superior performance and which can be redesigned or removed. This is not a new observation—the authors cite Zhang et al. (2020) and Kunstner et al. (2023) as prior efforts to understand Adam's behavior—but the field has not converged on a principled answer.

The specific target of this paper is Adam's **second-order momentum `v`**, which provides per-parameter adaptive learning rates. For a model with $d$ parameters, Adam stores a vector `v` of size $d$, where the $i$-th parameter receives learning rate $\eta / \sqrt{v_i}$. The key question the paper asks (Section 2.1) is:

> Is it necessary to use a customized learning rate for each parameter? If not, how much can we save?

This is a question about **redundancy in the preconditioner**. If many of Adam's billions of learning rates are providing redundant information—or worse, if a single well-chosen learning rate per parameter group can outperform many individually tuned rates—then there is substantial memory to reclaim without sacrificing performance.

### Where Prior Memory-Efficient Optimizers Fall Short

The paper identifies several existing approaches and their limitations:

**Adafactor (Shazeer & Stern, 2018).** This is the most prominent memory-efficient alternative to Adam. Adafactor cuts memory by using a low-rank factorization of `v` into two vectors—one for rows and one for columns—reducing storage from $\mathcal{O}(nm)$ to $\mathcal{O}(n + m)$ per weight matrix. The authors acknowledge this as a notable attempt but identify three problems:

1. **Performance degradation**: "we find that Adafactor is not easy to tune and often performs worse than Adam" (Section 1). The authors cite evidence from Luo et al. (2023) supporting this claim.

2. **Latency overhead**: As shown in Figure 13(c), Adafactor has higher latency than Adam-mini. The authors explain that Adafactor must sum across both rows and columns to construct its factored estimates, and the dimension of its `v` representation—while reduced—is still larger than Adam-mini's because it equals the product of input and output dimensions rather than just the output dimension or number of heads.

3. **Generic approach misses problem structure**: The authors argue that "matrix factorization is a generic approach that could be applied broadly, but it does not leverage much problem-specific structure, thus it does not work well on specific neural-net tasks" (Section 1). This is a crucial criticism: Adafactor treats all weight matrices uniformly, without considering that different parameter blocks in Transformers exhibit fundamentally different Hessian structures.

The paper conducts a careful hyperparameter sweep for Adafactor on Llama 2-20M and Llama 2-1B pre-training (Section 3.4, Figure 13, and Appendix D.7), testing two variants: the original Adafactor and what they call the "Adafactor-Zhai-version" (modified by Zhai et al., 2022 for vision transformers). They sweep over learning rates, $\beta_2$ values, $\epsilon$ values, and warm-up steps. The finding: both versions consistently underperform Adam-mini. On larger models (Llama 2-1B), the Adafactor-Zhai-version suffers training instability while the original version performs better but still trails Adam-mini. They also note the difficulty of tuning: "there are 9 tunable hyperparameters in Adafactor, so it is rather non-trivial to find the correct combination."

**CAME (Luo et al., 2023).** This is a variant of Adafactor that adds confidence-guided adaptive memory efficiency. The authors find it similarly underperforms Adam-mini on Llama series pre-training (Figure 10a). The latency issue also applies, as CAME inherits Adafactor's row-and-column summation structure.

**SM3 (Anil et al., 2019).** This is a lightweight version of AdaGrad that chooses the learning rate for each parameter by taking the minimum value from a candidate set associated with a predetermined cover. The authors incorporate momentum ($\beta_1 = 0.9$) for fair comparison and find it performs worse than Adam-mini on GPT-2 pre-training (Figure 8a).

**Lion (Chen et al., 2024b).** The paper includes a detailed comparison in Appendix D.8. Lion was discovered through symbolic search rather than principled design, and the authors find it difficult to tune. Following the tuning strategies from a concurrent work (anonymous authors, 2024), they test Lion on Llama 2-20M and GPT-2-125M. The results (Figure 20): Lion consistently underperforms Adam-mini on Llama 2-20M and encounters loss spikes on GPT-2-125M for all learning rate candidates tested. The authors emphasize that Lion's tuning strategy does not transfer well across architectures—it works on Llama architectures in the original study but fails on GPT-2—whereas Adam-mini works with the same hyperparameters as AdamW across all experiments.

**LAMB (You et al., 2019).** The authors explicitly distinguish LAMB from Adam-mini (Appendix A). LAMB retains Adam's per-parameter adaptive learning rates and adds an additional layer-wise scaling factor. It does not save memory over Adam and is designed for large-batch training, not memory reduction. Numerically, LAMB performs worse than Adam-mini on GPT-2 pre-training (Figure 10a).

**BAGM (Zheng & Kwok, 2019) and NovoGrad (Ginsburg et al., 2019).** These are two methods that share some conceptual similarity with Adam-mini—they use block-wise or layer-wise adaptive learning rates. The authors acknowledge this and explain the key difference (Appendix A): both BAGM and NovoGrad use the PyTorch default partition (essentially treating each layer as one block), which the authors find causes training instability on LLMs. As shown in Figure 7(i) and Figure 8(a), Adam-mini with PyTorch default partition suffers loss spikes on Llama 2-1B and performs poorly on GPT-2-125M. The principle-based partition strategy (partitioning by heads, output neurons, and tokens according to Hessian structure) is what stabilizes training.

### The Conceptual Gap: Why Prior Approaches Haven't Solved This

The paper identifies a deeper conceptual issue beyond any specific method. Prior work generally treats the question of memory reduction as a **generic compression problem**: how do we approximate or factorize Adam's optimizer states to use less storage? Adafactor uses low-rank factorization; SM3 uses set covers; quantization approaches use fewer bits per state. All of these treat `v` as a monolithic object to be compressed.

The paper argues that this framing misses something fundamental: **the redundancy in Adam's `v` is not uniform—it is structured according to the Hessian of the neural network**. The paper draws on a two-decade-old observation (Collobert, 2004) that the Hessian of neural networks is near-block-diagonal, with dense sub-blocks corresponding to structural units like neurons. Within each dense sub-block, many of Adam's per-parameter learning rates may be providing redundant information because the parameters within that block share a common curvature structure.

This insight changes the optimization goal from "compress `v`" to "identify which learning rates are structurally necessary and which are redundant." The practical difference is profound: Adafactor's low-rank factorization can introduce approximation error that degrades performance, while Adam-mini's approach of using a single learning rate per Hessian block is grounded in the actual optimization geometry. The question is not just about memory savings—it's about whether those savings are *harmless* or whether they sacrifice the adaptive behavior that makes Adam effective.

### How This Paper Positions Itself

The paper positions itself at the intersection of three lines of work:

**1. Understanding why Adam works.** The authors build directly on Zhang et al. (2024), who showed that Transformers exhibit **Hessian-block heterogeneity**: different parameter blocks (query, key, value, MLP layers) have dramatically different eigenvalue distributions, which explains why Transformers need different learning rates for different blocks. The contribution of this paper is to push this insight further: if different blocks need different learning rates (as Zhang et al. established), do different *parameters within the same block* need different learning rates? The paper's answer is no—a single well-chosen learning rate per block can suffice—which is what unlocks the memory savings.

**2. Hessian structure of neural networks.** The paper draws on the near-block-diagonal Hessian structure documented by Collobert (2004) and others, but extends this analysis to Transformers specifically. The empirical Hessian visualizations in Figure 7 are novel: they show that query and key exhibit block-diagonal structure corresponding to attention heads, attn.proj and MLP layers exhibit block-diagonal structure corresponding to output neurons, and embed and output layers exhibit block-diagonal structure corresponding to tokens. This structural understanding is what enables the paper's partition strategy.

**3. Memory-efficient training.** The paper serves as a direct alternative to Adafactor and related methods, but with a fundamentally different design philosophy: rather than applying a generic compression scheme, leverage the known structure of the optimization problem. The authors are explicit that their approach does not require grid search for each block's learning rate—instead, they use the average of Adam's `v` within each block as a cheap and effective proxy—making it practical for large-scale training.

### The Practical Framing: A 50% Memory Reduction With Zero Performance Cost

A key motivation that the paper emphasizes throughout is **ease of adoption**. The authors repeatedly highlight that Adam-mini works with the same hyperparameters as AdamW: "In all our experiments, Adam-mini performs well using the same hyperparameters as AdamW (including learning rate, $\beta_1$, $\beta_2$, $\epsilon$, etc.)" (Section 3.4). This is in direct contrast to Adafactor and Lion, which require extensive tuning and whose optimal hyperparameters don't transfer across architectures.

The throughput gains in Table 2 make the practical motivation concrete: when pre-training Llama 2-7B on 2× A800-80GB GPUs, Adam-mini supports a batch size of 4 per GPU (vs. 1 for AdamW) because of the memory savings, and achieves 49.6% higher throughput. This translates to 33.1% less wall-clock time for processing the same number of tokens. For a 140B-token training run, this means saving approximately 3,460 GPU-hours.

This framing—"50% less memory, same performance, no tuning required"—is the paper's central claim and what distinguishes it from prior memory-efficient optimizers that trade off performance for memory or require extensive hyperparameter search to work well.

## 3. Technical Approach

### 3.1 Reader Orientation

This paper designs a **memory-efficient optimizer** called Adam-mini that replaces Adam's per-parameter second-order momentum estimates with block-wise averages, guided by the Hessian structure of the neural network. The system solves the problem of Adam's excessive memory consumption by identifying that over 99.9% of Adam's `v` entries are structurally redundant—a single well-chosen learning rate per Hessian-dense parameter block can match or exceed the performance of per-parameter rates—and then providing a cheap, principled way to compute those block-wise rates without expensive grid search.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has three core components that work together:

1. **Hessian Structure Analyzer** — a one-time analysis (either empirical or following established principles) that identifies the smallest dense sub-blocks in the neural network's Hessian matrix. This analysis produces a partition map: for each parameter in the model, it specifies which block it belongs to. The partition is architecture-specific (Transformers get one partition scheme; CNNs get another).

2. **Block-wise Learning Rate Computer** — during training, for each parameter block identified by the partition, this component computes a single scalar learning rate by averaging the element-wise squared gradients across that block, applying exponential moving average (EMA), and bias-correcting. This replaces Adam's per-parameter `v` vector—which requires storage proportional to model size—with `B` scalars where `B` is the number of blocks (orders of magnitude smaller).

3. **Update Engine** — applies the standard AdamW update rule (with momentum, weight decay, and bias correction), but uses the block-wise learning rate for all parameters within each block rather than per-parameter rates. The update engine is essentially AdamW with the `v` vector replaced by a lookup into the block-wise `v_b` scalars.

Information flows as follows: model parameters are partitioned into blocks according to Hessian structure (once) → at each training step, gradients `g` are computed via backpropagation → within each block `b`, the element-wise squared gradients are averaged to produce a scalar `mean(g_b ⊙ g_b)` → this scalar is incorporated into an EMA to produce `v_b` → `v_b` is bias-corrected → the update `param = param - η * m_hat / (sqrt(v_b) + ε)` is applied to all parameters in block `b` with weight decay handled identically to AdamW.

### 3.3 Roadmap for the Deep Dive

- **First**, the empirical finding that more learning rates don't always help—the random quadratic and Transformer case studies that motivate why per-parameter rates within dense Hessian sub-blocks are redundant. This establishes the *possibility* of compression.
- **Second**, the Hessian structure analysis of Transformers, which grounds the partition principle in empirical observation rather than heuristic. We cover what the four classes of Hessian sub-blocks look like and why PyTorch's default partition fails.
- **Third**, the formal partition principle (Principle 1) and how it translates into the concrete algorithms (Algorithm 3 for Transformers, Algorithm 3 for non-Transformers). This is where the abstract insight becomes an implementable procedure.
- **Fourth**, the Adam-mini update rule itself (Algorithm 1/2): the computational mechanics, the memory usage analysis, and the design choice of using `mean(v)` rather than grid-searching optimal block rates. We cover why this specific choice works and what alternatives were considered.
- **Fifth**, the characteristics of Adam-mini: memory savings quantification, throughput improvements, and the trajectory similarity to AdamW that enables hyperparameter transfer.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems paper with a theoretical motivation**. The core idea is that Adam's per-parameter learning rates are redundant within dense Hessian sub-blocks of neural networks, and that by partitioning parameters according to Hessian structure and using a single averaged learning rate per block, one can save 50% of Adam's memory with no performance degradation. The theoretical insight—that Adam's diagonal preconditioner is ineffective at reducing condition number within dense Hessian blocks—motivates the design, but the contribution is the practical algorithm and its empirical validation at scale.

#### The Redundancy Hypothesis: Why Per-Parameter Learning Rates Can Be Reduced

Before presenting Adam-mini, the paper must establish that the thing it wants to compress—Adam's `v`—actually contains redundancy. This is not obvious; Adam's per-parameter adaptivity is widely considered central to its effectiveness. The paper makes this case through two lines of evidence: a controlled study on random quadratic problems and an empirical investigation on Transformers.

**Random quadratic problems (Section 2.1, Figure 4).** The paper constructs a synthetic optimization problem with known optimal learning rates to test whether many per-coordinate rates (Adam) outperform a single rate per Hessian-dense block. The problem is `min_w (1/2) w^T H w` where `H` is a block-diagonal positive definite matrix with three dense sub-blocks, each with eigenvalues sampled from different ranges (sub-block 1: {1,2,3} repeated; sub-block 2: {99,100,101}; sub-block 3: {4998,4999,5000}). This creates a problem where different blocks genuinely need different learning rates due to different curvature scales, but within each block, the curvature is relatively homogeneous.

The paper compares three methods:
- **Adam** (with `β_1 = 0` and `β_2 = 1` to isolate the effect of coordinate-wise learning rates without momentum or temporal decay): per-parameter learning rates.
- **Optimal single-learning-rate method** (GD with learning rate `2/(L+μ)` where `L, μ` are the largest/smallest eigenvalues of the full Hessian): one learning rate for all parameters.
- **Optimal blockwise-learning-rate method** (GD with block-specific optimal learning rates using each sub-block's eigenvalues): one learning rate per block.

The findings are three-fold and build a logical chain:

1. **Finding 1 (Figure 4b, full problem):** Adam outperforms the optimal single-learning-rate method. This is expected and consistent with the standard narrative that per-parameter adaptivity helps. The optimal blockwise method outperforms Adam, showing that the right per-block rates can beat per-parameter rates.

2. **Finding 2 (Figure 4c-d, sub-block only):** When the paper isolates a single dense sub-block and solves the optimization problem for just that sub-block, the **optimal single-learning-rate method outperforms Adam**. This is the critical finding: for a problem whose Hessian is a dense matrix (not block-diagonal with heterogeneous blocks), one well-chosen learning rate beats many per-coordinate rates. Adam's per-parameter rates are not providing benefit within dense blocks; they may actually be suboptimal.

3. **Finding 3 (Figure 4b, green curve):** Collecting the per-block optimal rates from Finding 2 and applying them block-wise to the full problem produces faster convergence than Adam. This suggests that the right design is per-block rates (respecting block heterogeneity) rather than per-parameter rates (within-block redundancy).

The explanation provided is from linear algebra: Adam can be viewed as a **diagonal preconditioner** `D_Adam = Diag(1/√v)`. The effectiveness of any preconditioner is measured by how much it reduces the condition number `κ(H)` of the Hessian. A diagonal preconditioner is effective when `H` is nearly diagonal; when `H` is dense (as within each Hessian sub-block of a neural network), a diagonal preconditioner cannot significantly reduce the condition number. The paper formalizes this with a numerical study (Figure 5):

> Let `τ = Σ_i |H_{b,i,i}| / Σ_{i,j} |H_{b,i,j}|` (the "diagonal-over-off-diagonal ratio") and `r = κ(D_Adam · H_b) / κ(H_b)` (the ratio of condition numbers—smaller is better preconditioning).

The experiment fixes the eigenvalues of `H_b` and varies `τ` by rotating the eigenvectors (so only the off-diagonal structure changes, not the spectrum). The result: as `τ` increases (matrix becomes more diagonal), `r` decreases (preconditioner becomes more effective). This holds across dimensions `d` from 10 to 100 and condition numbers `κ(H_b)` from 200 to 1000 (Figure 5a, 5b). The implication: **for dense Hessian sub-blocks (small `τ`), Adam's diagonal preconditioner is not particularly effective, so per-parameter learning rates within such blocks provide limited benefit.**

**Transformer case study (Section 2.1, Figure 6).** The paper then tests whether this insight transfers to Transformers. Using a 4-layer Transformer, they randomly select parameter blocks (under PyTorch default partition) and replace Adam's per-parameter learning rates in those blocks with a single grid-searched learning rate, while keeping Adam for the rest of the model. This is called "Adam (leave-one-out)."

The results (Figure 6a-c): whether leaving out one, two, or three randomly chosen blocks, the grid-searched single-rate version matches or exceeds Adam's performance. Figure 6d shows the performance gap `loss(Adam(leave-one-out)) - loss(Adam)` for all possible single-block leave-outs, revealing that for most blocks, the single-rate version actually performs *better* (negative gap). This directly demonstrates redundancy: many of Adam's per-parameter learning rates can be replaced by a single well-chosen rate per block without degradation.

The critical limitation acknowledged: grid search does not scale. The number of blocks grows with model size, and searching even one learning rate per block via grid search would be combinatorially expensive. This sets up the need for Adam-mini's cheap block-wise rate computation.

#### Hessian Structure of Transformers and the Partition Problem

The previous section established that per-block learning rates can work, but it leaves open two crucial questions: **(1) how should parameters be partitioned into blocks?** and **(2) how can good per-block rates be found cheaply?**

The paper addresses question (1) through an empirical Hessian analysis of a small Transformer (1 layer, 4 attention heads, embedding dimension 16, MLP hidden dimension 32). Using exact Hessian computation via double backpropagation (Pearlmutter, 1994), the paper visualizes the Hessian sub-block for each parameter group after 1% of training (Figure 7a-h). The visualizations reveal **four distinct classes** of Hessian structure:

**Class 1: Query and Key (Figure 7a-b).** These exhibit a clear near-block-diagonal structure where the number of blocks equals the number of attention heads (4 in this case). Each attention head forms its own dense Hessian sub-block, and the off-diagonal entries between heads are near zero. Physically, this makes sense: different attention heads learn to attend to different positional patterns, so their parameters' curvatures are largely independent. The implication for partitioning: **query and key should be split by heads**, not treated as monolithic matrices.

**Class 2: attn.proj and MLP layers (Figure 7d-f).** The output projection (`attn.proj`) and both MLP matrices (`mlp.fc_1` and `mlp.proj`) exhibit block-diagonal structure where the number of blocks equals the number of **output neurons** (16 for `attn.proj` and `mlp.proj`; 32 for `mlp.fc_1`, which has a larger hidden dimension). Each output neuron corresponds to one row of the weight matrix, and the Hessian entries between different output neurons are near zero. This structure is consistent with the theoretical analysis from Collobert (2004): the cross-entropy loss's derivative structure causes off-diagonal-block Hessian entries to shrink as the predicted probability approaches 1. The implication: **these layers should be partitioned by output neurons**—each row of the weight matrix gets its own learning rate.

**Class 3: Value (Figure 7c).** The Hessian of `value` is more ambiguous. It shows "the hint of 16 diagonal blocks (16 is the number of output neurons), but the pattern is less obvious." The Hessian entries are also about `10^6` larger in magnitude than those of query and key. The paper hypothesizes this difference arises because `value` is positioned outside the softmax operator in self-attention, while query and key are inside it—the softmax's normalization likely suppresses gradient magnitudes and changes the correlation structure. The paper recommends partitioning `value` by output neurons as the default (Algorithm 3) but notes that treating it as a single block works better when total training steps are small (Appendix D.6). This is the one case where the partition is not fully determined by the Hessian structure.

**Class 4: Embed and Output (Figure 7g-h).** The embedding layer and output projection layer exhibit near-block-diagonal structure where the number of blocks equals the number of tokens (vocabulary size, here 8 for this small experiment). Each token embedding forms its own dense Hessian sub-block. This is intuitive: different tokens have different semantic properties and frequencies, so their embedding parameters evolve with largely independent curvature. The implication: **embedding and output layers should be partitioned by tokens**—each row of the embedding matrix gets its own learning rate.

**The failure of PyTorch default partition.** PyTorch's default parameter naming scheme groups parameters by their role in the architecture: one block for all of `query`, one for `key`, one for `value`, one for `attn.proj`, etc. This means each of these blocks contains multiple attention heads, multiple output neurons, or multiple token embeddings. By Principle 1 (which we will formalize below), this grouping is too coarse: it mixes parameters that belong to different dense Hessian sub-blocks and should receive potentially different learning rates. The consequence is shown concretely in Figure 7(i) (Llama 2-1B) and Figure 8(a) (GPT-2-125M): Adam-mini with PyTorch default partition suffers loss spikes and divergent training, while Adam-mini with the Hessian-based partition (Algorithm 3) trains stably and matches AdamW.

#### Principle 1: The Formal Partition Rule

The paper distills the empirical observations into a single design principle:

> **Principle 1:** We should partition parameters into blocks, such that each parameter block is associated with the smallest dense sub-block in Hessian.

This principle is grounded in the logic chain from Section 2.1: (a) within each dense Hessian sub-block, Adam's per-parameter learning rates are redundant because a diagonal preconditioner cannot significantly reduce the condition number of a dense matrix; (b) therefore, a single learning rate per dense sub-block can suffice; (c) however, if the partition is too coarse and groups parameters from *different* dense sub-blocks together, the single learning rate may be inappropriate for some of them, causing training instability (as seen with PyTorch default partition).

The principle answers the "how to partition" question by specifying a criterion: **the smallest dense sub-block**. "Smallest" is the operative word. One could partition at different granularities—by layer, by sub-layer, by groups of neurons, by individual neurons. The principle says: partition at the finest granularity that still captures a dense Hessian sub-block. For query/key, this means by individual heads (not by all heads together, which would mix different dense blocks). For MLP layers, this means by individual output neurons (not by groups of neurons or by the whole layer). Partitioning more finely than the smallest dense sub-block (e.g., individual parameters) would waste memory without providing benefit (as the paper already showed). Partitioning more coarsely would mix independent blocks and risk instability.

The principle is **architecture-agnostic** in its statement but **architecture-specific** in its realization. For Transformers, the realization is Algorithm 3 in Appendix B. For CNNs and other architectures where the Hessian structure has not been analyzed, the paper recommends Algorithm 3—essentially using whatever the natural parameter groups are (equivalent to PyTorch default partition). The authors are explicit that this may need revision for future architectures: "it is possible that we will have more complicated non-Transformer architectures on which Algorithm 3 fails. In those cases, we need to investigate the Hessian structure of these new architectures and then develop the concrete partition algorithms following our Principle 1."

**Algorithm 3: Partition for Transformers (verbatim logic).** The algorithm processes each named parameter in the model and applies different splitting strategies based on the parameter name:

- If the name contains `'embed'` or `'output'`: partition by tokens. For a weight matrix of shape `[vocab_size, d_model]`, this creates `vocab_size` blocks, each being one row (one token's embedding vector).
- If the name contains `'query'` or `'key'`: partition by heads. For a weight matrix of shape `[d_model, d_model]` (or similar, depending on implementation), this splits the matrix such that each attention head's parameters form one block.
- If the name contains `'value'`, `'attn.proj'`, or `'mlp'`: partition by output neurons. For a weight matrix of shape `[d_out, d_in]`, this creates `d_out` blocks, each being one row.
- Otherwise (e.g., biases, layer norms): keep as a single block.

The number of blocks produced by this partition is dramatically smaller than the number of parameters. For a Transformer with `L` layers, `H` heads per layer, model dimension `d`, MLP hidden dimension `4d`, and vocabulary size `V`, the approximate block count is:

$$B \approx L \times (2H_{\text{qk}} + 3d + 8d) + V_{\text{embed}} + V_{\text{output}}$$

where `2H` comes from query and key (each split by `H` heads), `3d` comes from value and attn.proj and mlp.proj (each split by `d` output neurons), and `8d` comes from mlp.fc_1 split by `4d` output neurons but with fan-in `d`—the paper treats these row-wise, yielding `4d` blocks. For a 7B model with `d = 4096`, `H = 32`, `L = 32`, `V ≈ 32000`, this gives roughly `32 × (64 + 12288 + 32768) + 64000 ≈ 1.4 × 10^6` blocks, compared to `7 × 10^9` parameters—a reduction of over 99.98% in the number of learning rates.

#### The Adam-mini Update Rule (Algorithm 1 / Algorithm 2)

With the partition established, the optimizer itself is straightforward. The paper presents two equivalent forms: Algorithm 1 (the general principled form) and Algorithm 2 (the PyTorch-style implementation). They differ only in that Algorithm 2 separates weight decay as a decoupled step (AdamW-style), while Algorithm 1 includes it inline. We'll describe the AdamW-style version as it's what the paper uses in practice.

For each parameter block `b` (identified by the partition step), the algorithm maintains:
- `m_b`: the first-order momentum (same shape as the block's parameters—this is NOT compressed)
- `v_b`: a **scalar** second-order momentum for the entire block

At each training step `t`:

**Step 1: Weight decay (decoupled, AdamW-style).**

> `param = param - η_t * λ * param`

where `η_t` is the current learning rate (after scheduling) and `λ` is the weight decay coefficient. This is identical to AdamW's decoupled weight decay: it subtracts a fraction of the parameters themselves before the gradient-based update, which regularizes toward zero without interfering with the adaptive learning rate mechanics.

**Step 2: Gradient accumulation into first-order momentum.**

> `m_b = (1 - β_1) * g_b + β_1 * m_b`

where `g_b` is the gradient for block `b` (a tensor of the same shape as the block's parameters) and `β_1` is the momentum decay rate (typically 0.9). This is standard exponential moving average of gradients, identical to Adam.

**Step 3: Bias correction for first-order momentum.**

> `m_hat_b = m_b / (1 - β_1^t)`

The division by `(1 - β_1^t)` corrects for the zero-initialization bias of the EMA. At `t = 1`, the EMA value is `(1-β_1) * g_b`, but the desired average should be just `g_b`; the bias correction `1/(1-β_1)` scales it appropriately. As `t → ∞`, the correction factor approaches 1. Identical to Adam.

**Step 4: Second-order momentum (the key difference from Adam).**

This is where Adam-mini diverges. Instead of maintaining a per-parameter `v` vector via `v = (1-β_2) * g ⊙ g + β_2 * v` (element-wise), Adam-mini computes:

> `v_b = (1 - β_2) * mean(g_b ⊙ g_b) + β_2 * v_b`

where `mean(g_b ⊙ g_b)` is the **scalar average** of the element-wise squared gradients across all parameters in block `b`, and `v_b` is a **scalar** (not a tensor). The exponential moving average is applied to these scalar averages.

**What this computes operationally:** At each step, for each block, take the gradient tensor `g_b` (which might be a 2D matrix or higher-dimensional tensor), square every element, compute the arithmetic mean of all those squared values, and update a scalar EMA with that mean. The output is one number per block—the running average of the mean squared gradient in that block.

**Step 5: Bias correction for second-order momentum.**

> `v_hat_b = v_b / (1 - β_2^t)`

Same bias correction as Adam, but applied to the scalar `v_b`. At early steps, the zero-initialized EMA underestimates the true mean squared gradient, so dividing by `(1-β_2^t)` corrects it.

**Step 6: Parameter update.**

> `param = param - η_t * m_hat_b / (sqrt(v_hat_b) + ε)`

For every parameter in block `b`, the update divides the bias-corrected momentum by the square root of the bias-corrected block-wise `v_hat_b` (plus a small `ε` for numerical stability). This is the critical compression: **all parameters in the same block share the same denominator**. In Adam, each parameter `i` would have its own `sqrt(v_hat_i)`; in Adam-mini, all parameters in block `b` use `sqrt(v_hat_b)`.

**Concrete example (from Section 2.2).** For a problem with 5 parameters and a partition `{(1,2,3), (4,5)}`, Adam's learning rate vector is:

> `u_Adam = [η/√v_1, η/√v_2, η/√v_3, η/√v_4, η/√v_5]`

while Adam-mini's is:

> `u_mini = [η/√v̄_{123}, η/√v̄_{123}, η/√v̄_{123}, η/√v̄_{45}, η/√v̄_{45}]`

where `v̄_{123} = (v_1 + v_2 + v_3) / 3` and `v̄_{45} = (v_4 + v_5) / 2`. The number of distinct learning rates drops from 5 to 2. For real models, this reduces the number from billions to millions or less.

---

#### Why `mean(v)` Specifically? Design Choices and Alternatives

The paper's choice of using the **mean** of the per-element squared gradients (or equivalently, the mean of what Adam's `v` would track) as the block-wise learning rate is not arbitrary. The paper discusses the rationale (Section 2.4 "Why using mean(v) as learning rates" and Appendix C):

**Alternative 1: Grid search for optimal per-block rates.** The leave-one-out experiments (Figure 6) used grid search and showed that optimal per-block rates can outperform both Adam and the mean-based approach. However, grid search does not scale: for `B` blocks, searching `k` candidate learning rates per block requires `k^B` trials, which is infeasible for `B ≥ 3` (as the paper explicitly notes: "the cost of grid search grows exponentially"). The mean-of-v approach provides a closed-form computation that costs essentially nothing.

**Alternative 2: Other summary statistics of `v`.** The paper's ablation in Appendix D.2 (Figure 15) compares mean(`v`), L2-norm(`v`), L1-norm(`v`), max(`v`), and min(`v`). Mean performs best; max diverges; the norms perform worse than mean. The paper does not provide a deep theoretical justification for why mean works best, but offers a practical argument: the gradient of a weight matrix `W ∈ R^{d×d}` under backpropagation can be expressed as `G = e z^T` where `e` is a backpropagation error vector and `z` is the input feature. For all entries in the `i`-th row of `G`, they share the same error term `e_i`. This means entries within the same row (which corresponds to the same output neuron—the basis of the partition) tend to have similar magnitudes because they share the error factor `e_i`. The mean, as a central tendency measure, captures this shared magnitude while smoothing out per-entry noise. The max would be sensitive to outliers; norms would overweight large entries.

**Alternative 3: Learning separate rates per block with gradient-based adaptation.** One could maintain separate Adam `v` states per block and adapt them individually, as Adam does per-parameter, but that defeats the purpose of memory reduction. The mean-of-v approach achieves memory reduction by *aggregating before storing*: only one scalar is stored per block, not a full `v` vector.

**Alternative 4: Using Adam's existing `v` values.** The paper's approach is to "borrow" the learning rate signal from what Adam would compute. Specifically, if one were running Adam, the `i`-th parameter's learning rate would be proportional to `1/√v_i`. Adam-mini approximates this by using `1/√mean(v)` for all parameters in the block. The "borrowing" metaphor captures the design philosophy: rather than designing block-wise learning rates from scratch (which would require a new theory), piggyback on the mechanism that makes Adam work, but aggregate it to save memory.

**Why this works at all (the closeness-to-Adam argument).** The paper argues that the mean of `v` keeps Adam-mini's trajectory close to Adam's trajectory because, empirically, the entries of `v` within a Hessian-dense block are similar. Figure 9(b) shows that the L2 distance between Adam-mini's checkpoints and AdamW's checkpoints is much smaller than for Adafactor or CAME. This trajectory similarity has a crucial practical consequence: **Adam-mini can reuse AdamW's hyperparameters without tuning**. In all experiments, the paper uses the same `η`, `β_1`, `β_2`, `ε`, `λ`, and learning rate schedule as the well-tuned AdamW baseline, and reports that this works without further adjustment. This is in stark contrast to Adafactor, where the paper had to conduct extensive sweeps (Figure 13) and still couldn't match performance.

---

#### Memory Analysis: Where the 50% Comes From

The memory savings can be calculated precisely. Adam stores three per-parameter quantities: `m` (first-order momentum), `v` (second-order momentum), and the parameters themselves (plus gradients during the backward pass, but those are transient). In float32 (the standard for optimizer states):

- Parameters: `4d` bytes (where `d` is the number of parameters)
- `m`: `4d` bytes
- `v`: `4d` bytes
- Total optimizer memory: `8d` bytes

Adam-mini keeps `m` at full size (`4d` bytes) but compresses `v` to block-wise scalars. If the model is partitioned into `B` blocks, `v` requires only `4B` bytes. For models where `B ≪ d` (which holds for all Transformer architectures using Algorithm 3), the `v` storage becomes negligible, and the total optimizer memory becomes approximately `4d + 4B ≈ 4d` bytes—a 50% reduction from `8d`.

The paper quantifies this for specific models in Table 1:

| Model | AdamW Memory | Adam-mini Memory | Reduction |
|---|---|---|---|
| GPT-2-1.5B | 12.48 GB | 6.24 GB | 50% |
| Llama 2-1B | 8.80 GB | 4.40 GB | 50% |
| Llama 2-7B | 53.92 GB | 26.96 GB | 50% |
| Llama 3-8B | 64.24 GB | 32.12 GB | 50% |
| Llama 2-13B | 104.16 GB | 52.08 GB | 50% |

The reduction is consistent at exactly 50% for the optimizer states because `B` is so small relative to `d` that the `v` storage in Adam-mini is effectively zero (the paper states "≥99.9% of these learning rates in v could be harmlessly removed"). The remaining 50% is `m`, which Adam-mini retains at full resolution because the first-order momentum captures gradient direction and its compression would be a separate (and harder) problem.

**Throughput implications (Table 2).** The memory savings translate directly to throughput gains when GPU memory is the bottleneck. On 2× A800-80GB GPUs for Llama 2-7B pre-training:
- AdamW with batch size 1 per GPU: 3725.59 tokens/second, total batch size 256 achieved via gradient accumulation.
- AdamW with batch size 2 per GPU: out of memory (✗ in Table 2).
- Adam-mini with batch size 4 per GPU: 5572.19 tokens/second (+49.6%), total batch size 256.

The larger per-GPU batch size reduces the number of gradient accumulation steps, which in turn reduces the frequency of GPU synchronization (all-reduce operations for gradient averaging). GPU communication is a major bottleneck in distributed training (Rajbhandari et al., 2021), so reducing the number of communication rounds is at least as important as the raw FLOP savings. The paper reports that Adam-mini "does not introduce extra computation in per-step updates" and that "the averaging operation in Algorithm 1 incurs negligible cost and it significantly reduces the number of vector-square-root and vector-division operations in AdamW"—the sqrt and division are applied to scalars instead of tensors, which is faster.

---

#### Trajectory Similarity and Hyperparameter Transfer

A recurring theme in the paper's experimental narrative is that Adam-mini's loss curves "closely resemble those of AdamW" (Figure 8a, Figure 9a, Figure 10b, Figure 16). This is not just an aesthetic observation—it has practical implications for hyperparameter transfer and reliability.

The paper explicitly measures trajectory similarity in Figure 9(b). For a small Transformer trained under the same random seed and same learning rate, the Euclidean distance between Adam-mini's model weights and AdamW's weights at each checkpoint is compared to the distances for Adafactor and CAME. Adam-mini's trajectory stays much closer to AdamW's than the alternatives do. The paper suggests this is because "Adam-mini makes fewer modifications over AdamW"—it essentially retains Adam's update structure but aggregates the second-moment information within blocks rather than treating each parameter independently.

This closeness has three concrete benefits exploited throughout the paper:

1. **Hyperparameter reuse**: "Adam-mini performs well using the same hyperparameters as AdamW (including learning rate, β_1, β_2, ε, etc.)" (Section 3.4). No tuning budget needs to be allocated specifically for Adam-mini—just use what worked for AdamW.

2. **Scaling law preservation**: Figure 11 shows that the scaling law (validation loss vs. FLOPs and vs. parameters) for Adam-mini closely parallels AdamW's, with Adam-mini actually achieving slightly lower final perplexity at all model sizes from 39M to 1B (Table 4). This means practitioners can use Adam-mini for scaling law experiments (which are used to predict optimal configurations for larger models) and trust that the results transfer.

3. **Stability across architectures**: The paper tests Adam-mini on GPT-2 (125M–1.5B), Llama 2 (20M–13B), Llama 3 (8B), diffusion models (DDPM, DiT-XL-2), vision models (ResNet-18, Swin-Transformer), and graph neural networks (GCN, GAT). In all cases, Adam-mini with the same hyperparameters as AdamW works without instability (except when the wrong partition is used, as in Figure 7i).

This trajectory similarity is not theoretically guaranteed—it's an empirical finding that depends on the specific design choices (mean aggregation, Hessian-based partition). The paper does not attempt to prove that the mean of `v` is the optimal block-wise statistic; it simply demonstrates that it works well enough to stay close to Adam and preserve its empirical properties.

---

#### Edge Cases and Practical Considerations

**The value layer ambiguity.** Section 2.3 and Appendix D.6 discuss the special case of the `value` projection. Its Hessian structure is less clearly block-diagonal than other layers (Figure 7c). The paper offers a pragmatic recommendation: partition by output neurons when total training steps are large (which includes most experiments), but treat as a single block when total training steps are small (as in the 10K-step Llama experiments in Figure 10). This is implemented by adding `optimizer.wv_names = {}` to suppress `value` partitioning. The paper does not explain why step count matters, but one plausible mechanism is that at small step counts, the per-neuron variance estimates haven't converged, so aggregating them provides a more stable signal.

**Embedding and output layers.** These are partitioned by tokens (Algorithm 3), which means each token in the vocabulary gets its own learning rate. For a vocabulary of 32K tokens, this adds 32K blocks—still negligible compared to the billions of parameters. The paper doesn't ablate this choice, but it follows naturally from the Hessian visualization (Figure 7g-h) showing block-diagonal structure with one block per token.

**Biases and LayerNorm parameters.** These fall into the "else" branch of Algorithm 3 and are treated as single blocks (one learning rate for all biases, one for all LayerNorm parameters, etc.). The paper does not discuss the Hessian structure of these parameters, likely because they are a tiny fraction of the total parameter count.

**Compatibility with other memory-saving techniques.** Appendix A discusses orthogonal combinations: Adam-mini can be used with GaLore (gradient low-rank projection), Sophia (second-order optimizer), LoRA (low-rank adaptation), quantization (8-bit optimizers), ZeRO (optimizer state sharding), gradient checkpointing, and fused updates. None of these techniques interfere with Adam-mini's block-wise `v` compression.

## 4. Key Insights and Innovations

### Innovation 1: Redundancy in Adam's `v` Is Not Uniform — It Is Structured by Hessian Geometry

The paper's most fundamental conceptual move is reframing the problem of memory reduction from **"how do we compress Adam's optimizer states?"** to **"which per-parameter learning rates are structurally necessary, and which are redundant because the Hessian makes them so?"**

Prior work on memory-efficient optimizers — Adafactor (Shazeer & Stern, 2018), SM3 (Anil et al., 2019), CAME (Luo et al., 2023) — treated Adam's second-order momentum `v` as a monolithic object to be approximated or factorized. Adafactor applies low-rank factorization uniformly to every weight matrix without asking whether the rank structure varies across layers. SM3 uses set covers that are agnostic to the optimization landscape. These are **generic compression approaches**: they start from the constraint ("we have limited memory") and design an approximation scheme, hoping the approximation doesn't hurt too much.

This paper inverts that logic. It starts from the optimization geometry — the Hessian structure of neural networks — and asks: **given this geometry, which learning rates actually matter?** The answer turns out to be that the geometry imposes a natural block-sparsity: only one learning rate per dense Hessian sub-block is needed, because Adam's diagonal preconditioner cannot significantly reduce the condition number within a dense block anyway (Section 2.1, Figure 5). The redundancy is not a nuisance to be compressed around; it is a **structural feature** that can be exploited with zero performance cost.

This is a shift from **lossy compression** (Adafactor introduces approximation error that degrades performance, as documented in Figure 13) to **lossless structural simplification** (Adam-mini removes only learning rates that the Hessian geometry already renders redundant). The distinction matters practically — it explains why Adam-mini requires no hyperparameter retuning while Adafactor requires extensive sweeps — but also conceptually: it suggests that understanding the optimization landscape is a more productive route to efficiency than treating optimizer states as generic tensors to be compressed.

The paper supports this framing with a clean empirical demonstration (Figure 4). On a synthetic problem with block-diagonal Hessian, a block-wise single-learning-rate method outperforms Adam's per-parameter rates, because the per-parameter rates provide no benefit within dense blocks. The extension to Transformers (Figure 6) confirms this: randomly replacing Adam's per-parameter rates with a single grid-searched rate per PyTorch block matches or exceeds Adam's performance. This is a **diagnostic result** — it reveals where redundancy lives — not just a method proposal.

The innovation here is the **diagnostic lens itself**: the idea that Hessian geometry dictates which learning rates are essential and which are optional. This lens could generalize beyond memory efficiency. It could inform quantization schemes (more bits where Hessian blocks are dense and heterogeneous across blocks?), distributed training strategies (shard along Hessian block boundaries?), or even architecture design (if certain Hessian structures make optimization harder, could we design architectures with more favorable structure?).

---

### Innovation 2: Principle 1 as a Transferable Design Rule for Optimizer State Reduction

The paper distills the Hessian-based insight into **Principle 1**: partition parameters such that each block corresponds to the smallest dense sub-block in the Hessian. This is not merely a description of what Adam-mini does — it is a **portable design rule** that can be applied to new architectures without re-deriving the theory from scratch.

What makes this a genuine innovation rather than an implementation detail is its **counter-intuitive specificity**. A naive approach to reducing learning-rate granularity would be to group parameters by layers (one learning rate per layer), which is what BAGM (Zheng & Kwok, 2019) and NovoGrad (Ginsburg et al., 2019) do. The paper shows this fails catastrophically on Transformers — Figure 7(i) demonstrates loss spikes when using PyTorch default (layer-wise) partition — because layers contain multiple independent dense Hessian sub-blocks (multiple attention heads, multiple output neurons) that genuinely need different learning rates. The Zhang et al. (2024) finding that different Transformer blocks have dramatically different eigenvalue distributions already established that block-level adaptivity matters; this paper sharpens that finding by showing that **the block boundaries must align with Hessian sub-blocks specifically**, not with architectural layer boundaries.

At the same time, partitioning more finely than the smallest dense sub-block — i.e., keeping per-parameter rates — wastes memory without providing benefit, because the diagonal preconditioner can't help within a dense block. Principle 1 therefore identifies a **sweet spot**: the coarsest partition that doesn't discard structurally necessary adaptivity. This is the partition that minimizes memory while preserving performance, and it is defined purely by the Hessian geometry.

The principle's portability is demonstrated by its application to both Transformers (Algorithm 3 with head-wise, neuron-wise, and token-wise splitting) and non-Transformers (Algorithm 3, which defaults to PyTorch partitioning for CNNs and other architectures where the Hessian structure has not been analyzed). The authors explicitly acknowledge the limitation — Algorithm 3 may fail on novel non-Transformer architectures, requiring fresh Hessian analysis — but the principle itself remains the guide for what to analyze.

This is a **foundational design rule** in the emerging field of optimizer co-design: the idea that optimizer structure should be matched to the Hessian structure of the specific architecture being optimized, rather than applying the same optimizer uniformly. Prior work on optimizer design (Adam, Adafactor, Lion) sought universal algorithms; Adam-mini's contribution is showing that architecture-aware design yields large practical gains with no performance sacrifice.

---

### Innovation 3: The Counterintuitive Finding That Fewer Learning Rates Can Outperform More — With Implications for Preconditioner Theory

The paper's most surprising empirical finding is not just that learning rates can be reduced without harm, but that **a single well-chosen learning rate per Hessian block can actually outperform Adam's per-parameter rates** (Figure 4d, Figure 6d). This is counterintuitive because Adam's adaptivity is typically considered its key strength — more adaptivity should mean better optimization.

The paper provides a **linear-algebraic explanation** that elevates this from an empirical curiosity to a theoretically grounded insight. Adam acts as a diagonal preconditioner `D = Diag(1/√v)`, and the effectiveness of any preconditioner is measured by how much it reduces the condition number of the Hessian. The numerical study in Figure 5 shows that for dense matrices (small diagonal-over-off-diagonal ratio `τ`), Adam's diagonal preconditioner barely reduces `κ(H)` — the ratio `r = κ(D_Adam · H) / κ(H)` is large when `τ` is small. This means that within each dense Hessian sub-block, Adam's per-parameter learning rates are not providing the condition-number reduction that would justify their existence. A single well-chosen learning rate (using block-wise eigenvalue information) can do better precisely because it doesn't pretend that a diagonal preconditioner can decorrelate a dense matrix.

This analysis connects Adam-mini to a broader literature on **diagonal preconditioning** (Forsythe & Straus, 1955; Young, 1954; Qu et al., 2022) while also identifying a gap: there is no existing lower bound on `κ(D_Adam · H)` that would formally characterize when the diagonal preconditioner fails. The paper explicitly flags this as "an important but challenging future direction" (Section 2.1), making a theoretical contribution by identifying the right question to ask.

The practical implication is significant: this finding reframes Adam not as an optimal adaptive method, but as a **heuristic diagonal preconditioner that happens to work well when the Hessian is near-diagonal** (e.g., at the block level in Transformers) but is provably suboptimal within dense blocks. This opens the door to stronger methods that use block-wise preconditioners (dense matrix inverses or approximations thereof) within each Hessian sub-block, which could achieve faster convergence than Adam while still being memory-efficient if the blocks are small. The paper's "has room to improve" discussion (Section 2.4) explicitly points toward this: "we can reach much faster convergence if we utilize more information in the dense block to design the learning rate (e.g., using eigenvalues of each block)."

This is a **fundamental conceptual contribution** rather than an incremental improvement: it changes what we think Adam is doing, why it works when it works, and what the path forward looks like for better optimizers.

---

### Innovation 4: Hessian Cartography of Transformers — Mapping Which Architectural Components Form Independent Optimization Units

The paper's empirical Hessian analysis of Transformers (Figure 7a-h) is a contribution in its own right, independent of the Adam-mini algorithm. Prior work has studied the Hessian of MLPs (Collobert, 2004; Sagun et al., 2016; 2017; Papyan, 2020) and has observed near-block-diagonal structure. But the paper provides what is essentially a **Hessian cartography of the Transformer architecture**, mapping which parameter groups form independent dense sub-blocks and — crucially — revealing that different Transformer components have different Hessian structure.

The four-class taxonomy (query/key by heads, attn.proj/MLPs by output neurons, value as ambiguous, embed/output by tokens) is novel and has implications beyond memory efficiency:

- **The query/key vs. value distinction** (Figure 7a-c): query and key exhibit clean block-diagonal structure by heads, while value does not. The paper attributes this to value being positioned outside the softmax in self-attention, while query and key are inside it. This structural difference — with value's Hessian entries being ~10^6 larger — suggests that different attention components face fundamentally different optimization landscapes. This could inform architecture design (should value be normalized differently?), initialization schemes, or learning rate assignment.

- **The output-neuron basis of MLP Hessian structure** (Figure 7d-f): the Collobert (2004) analysis predicts near-block-diagonal Hessian for 1-hidden-layer networks, and the paper confirms this extends to Transformer MLPs. Each output neuron forms its own optimization subproblem. This validates the Collobert theory in a modern context and suggests that MLP layers in Transformers behave like ensembles of independent single-neuron problems.

- **The token-wise structure of embeddings** (Figure 7g-h): each token embedding evolves with largely independent curvature. This has practical implications for token-specific learning rate adaptation (rare tokens might need different rates than frequent tokens) and explains why naive layer-wise partitioning of embeddings fails.

The paper also shows that this structure **persists throughout training** (Figure 3b-d for MLPs, confirmed at 1% steps for Transformers in Figure 7), not just at initialization. This makes it a reliable basis for optimizer design rather than a transient phenomenon.

This is an **empirical-scientific contribution**: it provides a systematic characterization of Transformer optimization geometry that can inform future optimizer design, initialization research, and architecture development. The fact that the analysis was done on a small model (1 layer, 4 heads, embedding dimension 16) is a limitation — the structure may change at scale — but as a proof of concept for the methodology, it is compelling.

## 5. Experimental Analysis

### Evaluation Methodology

**Dataset.** All pre-training experiments use either OpenWebText (Gokaslan et al., 2019) for GPT-2 models or C4 (Raffel et al., 2020) for Llama models. The scaling law experiments in Section 3.2 use C4 exclusively, with token amounts following Chinchilla's law — approximately 20× the parameter count in tokens for each model size. For supervised fine-tuning and RLHF, the authors use the UltraFeedback dataset (Cui et al., 2023), with 40% allocated to SFT training and 60% to reward model training.

**Base model(s).** The paper spans GPT-2 (125M, 330M, 1.5B parameters; Radford et al., 2019), Llama 2 (20M to 13B; Touvron et al., 2023), and Llama 3 (8B; Team et al., 2023). The small-scale Transformer used for Hessian visualization and leave-one-out experiments is a custom 4-layer model with 4 attention heads and embedding dimension 16 trained on a toy next-token prediction task. The scaling law experiments cover Llama 2 architectures from 39M to 1B parameters with varying depths, widths, and head counts (detailed in Table 8). The choice of two model families (GPT-2 and Llama) across two orders of magnitude in scale tests whether Adam-mini's benefits transfer across architectures and sizes.

**Metrics.** Pre-training performance is measured by training loss and validation loss (or equivalently perplexity for the scaling law figures). SFT performance is measured by evaluation perplexity on held-out data. RLHF performance is measured by evaluation reward (the learned reward model's prediction of response quality, on a scale from roughly 1.5 to 3.5 as shown in Figure 12b) and by GPT-4 evaluation scores on MT-Bench (Table 5). Throughput is measured in tokens per second under identical hardware configurations (2× A800-80GB GPUs). Memory usage is calculated analytically at float32 precision for optimizer states and reported in GB. Wall-clock time reduction is computed from throughput ratios applied to total token counts by Chinchilla's law.

**Baselines.** The paper compares Adam-mini against:

- **AdamW** (Loshchilov & Hutter, 2017): the standard decoupled-weight-decay Adam, using the same hyperparameters as Adam-mini unless otherwise noted.
- **Adafactor** (Shazeer & Stern, 2018): the original memory-efficient optimizer using nonnegative matrix factorization of `v`. Two variants are tested: the original and the "Zhai-version" (Zhai et al., 2022) modified for vision transformers.
- **CAME** (Luo et al., 2023): a confidence-guided variant of Adafactor with adaptive memory efficiency.
- **SM3** (Anil et al., 2019): a memory-efficient variant of AdaGrad using set-cover-based learning rate selection.
- **LAMB** (You et al., 2019): a layer-wise adaptive optimizer designed for large-batch training (tested only on GPT-2 pre-training, Figure 10a in Appendix).
- **Lion** (Chen et al., 2024b): a symbolically-discovered optimizer (tested on Llama 2-20M and GPT-2-125M, Appendix D.8).
- **Adam-mini (PyTorch default partition)**: an ablation where Adam-mini uses the standard PyTorch parameter naming scheme rather than Hessian-based partitioning.

All memory-efficient baselines incorporate momentum with β₁ = 0.9 for fair comparison. The paper tunes learning rates for each optimizer within equal computational budgets and reports the best performance for each.

**Generation budget / compute accounting.** Pre-training experiments measure compute in tokens processed (total number of tokens the model is trained on). The scaling law experiments use Chinchilla-optimal token counts: each model of `n_param` parameters is trained on approximately `20 × n_param` tokens. For throughput comparisons, compute is measured in tokens per second on identical hardware (2× A800-80GB GPUs) with memory limitations determining the maximum per-GPU batch size.

**Cross-validation / statistical protocol.** There is no formal cross-validation for the optimizer comparisons — each configuration is run once under a fixed random seed, and the paper reports the resulting training/validation curves directly. The "leave-one-out" experiments (Figure 6) run 5 trials with different randomly selected blocks left out, reporting each trial individually rather than the average. The scaling law experiments (Figure 11) train each model configuration once and report the final validation loss. No standard errors, confidence intervals, or multiple-seed statistics are reported, which is typical for large-scale LLM training experiments where each run costs tens to hundreds of GPU-hours.

### Main Quantitative Results

#### Pre-Training Performance: GPT-2 Series

Figure 8 presents validation loss curves for GPT-2-125M, 330M, and 1.5B pre-training on OpenWebText. The headline result: **Adam-mini performs similarly to AdamW with 50% less memory, while Adafactor, SM3, and LAMB perform worse.** Specific quantitative observations from Figure 8a (GPT-2-125M over 20B tokens):

- AdamW and Adam-mini validation loss curves are nearly overlapping throughout training, both converging from roughly 6.0 at initialization to approximately 2.5 at 20B tokens.
- Adafactor reaches approximately 2.65–2.70 at 20B tokens — a gap of roughly 0.15–0.20 in validation loss.
- SM3 converges to approximately 2.80 at 20B tokens — a gap of roughly 0.30.
- LAMB converges to approximately 2.70 — similar to Adafactor.
- Adam-mini (PyTorch default partition) diverges early in training and the trial is stopped. The paper states "it shows clear unstable behavior" (Section 3.1).

Figure 8b shows GPT-2-330M and GPT-2-1.5B. The 330M model: Adam-mini and AdamW validation loss curves are nearly identical, converging to roughly 2.85 at 20B tokens. The 1.5B model: both methods converge to roughly 2.65. The paper does not present baselines other than AdamW for these larger GPT-2 sizes in the main figure.

Figure 9a provides the training loss perspective. For all three GPT-2 sizes, Adam-mini's training loss curves closely track AdamW's throughout training. At 20B tokens, the training loss values are approximately 2.6 for 125M, 2.8 for 330M, and 3.0 for 1.5B, with negligible differences between the two optimizers.

#### Pre-Training Performance: Llama Series

Figure 10a shows training loss for Llama 2-1B pre-training on C4 (using the Torchtitan codebase). The key finding: **Adam-mini performs on par with AdamW, while CAME, Adafactor, and Adafactor-Zhai-version underperform.** Specific observations:

- AdamW and Adam-mini training loss curves are nearly identical throughout 10,000 iterations, both converging from roughly 8.0 to approximately 3.0.
- CAME converges to roughly 3.5 — a gap of 0.5 in training loss.
- Both Adafactor variants converge to roughly 3.8–4.0 and exhibit noisier trajectories.
- Adam-mini's curve closely tracks AdamW's, a pattern the paper highlights as characteristic: "loss curves of Adam-mini closely resemble the curves by AdamW."

Figure 10b extends this to larger scales: Llama 3-8B and Llama 2-13B (with seq_len = 2048 and batch_size = 8, shrunk due to hardware limitations). For 8B, Adam-mini and AdamW training losses overlap at roughly 3.6 by 10,000 iterations. For 13B, both converge to roughly 3.4. The paper does not show baselines other than AdamW at these scales.

Figure 1 (Section 1) presents the Llama 2-7B pre-training results. Figure 1b (validation loss vs. tokens): Adam-mini and AdamW curves overlap from 0 to 2.25B tokens, both reaching roughly 3.0 validation loss. Figure 1c (validation loss vs. wall-clock time): Adam-mini reaches the same validation loss in approximately 67% of the time — the 33% wall-clock reduction claimed in the abstract and Section 1.

#### Scaling Law Experiments (Figure 11, Table 4)

The scaling law experiments pre-train Llama 2 architectures of sizes 39M, 67M, 102M, 162M, 271M, and 1B on C4 with Chinchilla-optimal token amounts. Figure 11a shows validation loss as a function of FLOPs (log-log scale). The key finding: **Adam-mini's scaling curve is consistently similar to AdamW's, but with 50% less memory.** Both optimizers produce nearly overlapping curves across three orders of magnitude in compute.

Figure 11b shows final validation loss as a function of model parameters (log-log scale). #### Throughput and Wall-Clock Time (Table 2, Figure 1)

Table 2 reports throughput measurements for Llama 2-7B pre-training on 2× A800-80GB GPUs:

- **AdamW with batch size 1 per GPU**: 3725.59 tokens/second.
- **AdamW with batch size 2 per GPU**: out of memory.

The 49.6% throughput improvement (5572.19 / 3725.59 ≈ 1.496) translates to 33.1% less wall-clock time for processing the same number of tokens, because the throughput ratio is approximately 1.5×, so time is reduced to 1/1.5 ≈ 0.67 of the original. The paper projects this for different total token amounts:

- 1B tokens: 74.56 GPU-hours for AdamW vs. 49.85 for Adam-mini.
- 70B tokens: 5219.16 vs. 3489.55 GPU-hours (saving ~1730 GPU-hours).
- 140B tokens: 10438.32 vs. 6979.10 GPU-hours (saving ~3460 GPU-hours).

### Ablation Studies and Robustness Checks

**Partition strategy — PyTorch default vs. Hessian-based:** Figure 7(i) shows that on Llama 2-1B, Adam-mini with PyTorch default partition encounters loss spikes (sudden increases to ~16 from a baseline of ~5), while Adam-mini with Algorithm 3 partition trains stably and matches AdamW. Figure 8(a) reinforces this: on GPT-2-125M, the PyTorch default partition variant diverges early. These failures demonstrate that the partition principle is not merely a theoretical nicety — **wrong partition causes catastrophic training instability on practical LLMs.**

**Partition strategy — value layer treatment:** Appendix D.6 examines two options for the ambiguous `value` Hessian: partition by output neurons vs. treat as a single block. The paper finds that partitioning by output neurons works well when total training steps are large (e.g., GPT-2 experiments with >50K steps, scaling law experiments with >200K steps for Llama 2-1B). When total steps are small (e.g., 10K-step Llama experiments in Figure 10), treating `value` as a single block works better. The paper implements this via `optimizer.wv_names = {}` and recommends strategy selection based on training horizon. No formal ablation plot is provided — this is an empirical observation described qualitatively.

**Block-wise learning rate statistic — mean vs. alternatives:** Appendix D.2, Figure 15 compares mean(`v`), L2-norm(`v`), L1-norm(`v`), max(`v`), and min(`v`) as aggregation functions for block-wise learning rates on Llama 2-20M pre-training. **Mean performs best** (validation loss ~4.0 by 4,000 iterations), L1-norm and L2-norm perform slightly worse (~4.2 and ~4.3 respectively), and max diverges catastrophically (the blue curve is "out of range" — the paper states the algorithm diverges). Min is not shown. This ablation confirms that the central tendency (mean) is more stable than extremal statistics (max) for aggregation, but the theoretical explanation (the row-wise gradient structure `G = e z^T`) is only partially satisfactory.

**Adafactor hyperparameter sweep — β₂, warm-up, and ε:** Figure 19 (Appendix D.7) sweeps β₂ = 0.95 (instead of the default 0.999), warm-up steps from 1% to 10% of total steps, and ε ∈ {10⁻³⁰, 10⁻¹⁶, 10⁻⁸, 10⁻⁶} for Adafactor-Zhai-version on Llama 2-20M. In all cases, **Adafactor consistently underperforms Adam-mini** (validation loss gap of roughly 0.5), and the hyperparameter changes do not substantially alter this. This is a negative result for the claim that Adafactor's subpar performance is merely a tuning issue — extensive tuning does not close the gap.

**Lion hyperparameter sweep — learning rates and architectures:** Figure 20 (Appendix D.8) tests Lion on Llama 2-20M and GPT-2-125M using the tuning strategies from the concurrent work (anonymous authors, 2024). On Llama 2-20M, Lion underperforms Adam-mini across all learning rates tested (from 1e-4 to 5e-3). On GPT-2-125M, **Lion encounters loss spikes for all learning rate candidates** (from 6e-5 to 6e-4), indicating that the tuning strategy optimized for Llama architectures does not transfer to GPT-2. This is a negative result that highlights Adam-mini's advantage: its hyperparameters transfer directly from AdamW without per-architecture tuning.

**Hyperparameter sensitivity — Adam-mini itself:** Figure 12(c) tests the sensitivity of Adam-mini to hyperparameter choices on GPT-2-125M pre-training (2.5B tokens by Chinchilla's law). The heatmap — which the paper describes rather than plots in detail, and Figure 12(c) appears to be a bar chart, not a heatmap — shows that Adam-mini's final validation loss is "not overly sensitive" to learning rate, β₁, or β₂ variations around their default values. No quantitative sensitivity metrics are reported.

**Combination with LoRA:** Figure 22 (Appendix D.10) shows SFT with LoRA on Llama 2-7B, where Adam-mini replaces AdamW in the LoRA optimizer step. Adam-mini achieves lower evaluation perplexity than AdamW throughout training (approximately 2.45 vs. 2.55 at 60,000 iterations). This demonstrates that Adam-mini can be orthogonally combined with parameter-efficient fine-tuning methods without degradation.

**Trajectory similarity:** Figure 9(b) measures the Euclidean distance between the model weights produced by different optimizers and AdamW's weights at regular checkpoints during a small Transformer training run. Adam-mini's distance to AdamW stays under ~25 throughout training, while Adafactor diverges to ~250 and CAME to ~100 by 4,000 iterations. This quantifies the claim that Adam-mini stays "close" to AdamW's trajectory.

**ReST^EM revision model:** Not applicable — this paper does not use revision models or reinforcement learning for optimizer design. No such ablation exists.

### Critical Assessment

#### Does the paper demonstrate that Adam-mini achieves on-par or better performance than AdamW with 50% less memory?

The claim is **well-supported for pre-training** across the tested scales and architectures. The loss curves in Figures 8, 9, 10, and 11 show near-perfect overlap between Adam-mini and AdamW across GPT-2 (125M–1.5B), Llama 2 (20M–13B), and Llama 3 (8B). The scaling law experiments (Figure 11, Table 4) even show a small but consistent improvement for Adam-mini (0.1–0.5 lower perplexity). The SFT and RLHF results (Figure 12, Table 5) also show Adam-mini matching or slightly exceeding AdamW.

However, the paper does not test on architectures beyond Transformers at scale. The non-LLM experiments (ResNet-18, Swin-Transformer, DiT-XL-2, DC-AE-Diffusion, GCN, GAT) are all at moderate scale compared to the 7B–13B LLM experiments. The 50% memory reduction is analytically guaranteed by the design (storing scalar `v_b` per block instead of per-parameter `v`), so this claim is not in doubt — the relevant question is whether performance holds.

A potential concern is that **all pre-training runs appear to use a single random seed**. The paper does not report multi-seed statistics, so it is unknown whether the small performance differences (Adam-mini slightly better in most cases) are statistically reliable or within noise. This is a common practice in LLM training research due to computational cost, but it means the claim of "on-par or better" should be interpreted as "comparable in a single run" rather than "statistically indistinguishable or superior."

#### Does the paper demonstrate that the Hessian-based partition principle (Principle 1) is necessary for performance?

**Strongly supported for the necessity over naive partitioning.** Figure 7(i) and Figure 8(a) provide clear evidence that PyTorch default partition causes catastrophic training instability on models as small as 125M parameters (GPT-2) and as large as 1B (Llama 2). The loss spikes are dramatic and unambiguous. This is a genuine finding: the partition matters.

However, the paper does not test **alternative principled partitions** — for example, partitioning by layers plus attention heads (but not output neurons), or partitioning query/key by heads but leaving value as a single block, or any other granularity between "PyTorch default" and "Algorithm 3." The only comparison is between one partition that works (Algorithm 3) and one that fails (PyTorch default). This leaves open the question of whether Algorithm 3 is the **optimal** partition or simply one that is "good enough." The paper acknowledges this in Section 2.4: "there is great room to improve the design of Adam-mini."

The Hessian analysis (Figure 7) is conducted on a **single small model** (1-layer Transformer, embedding dimension 16, 4 heads) at **1% of training**. The paper assumes this structure persists to larger models and throughout training, but provides no evidence at scale. The scaling law experiments (Figure 11) demonstrate that Algorithm 3's partition works up to 1B parameters, which is indirect evidence that the Hessian structure generalizes, but it does not directly verify the Hessian structure at those scales.

#### Does the paper demonstrate that fewer learning rates can outperform more learning rates within dense Hessian blocks?

**Partially supported with controlled experiments, but the "outperform" claim is nuanced.** The random quadratic experiments (Figure 4) cleanly demonstrate the principle: a single optimal learning rate per block outperforms Adam's per-parameter rates within each dense sub-block. The "leave-one-out" Transformer experiments (Figure 6) show that grid-searched single learning rates per PyTorch block can match or slightly improve upon Adam, but these experiments use **grid search** (searching over learning rates to find the optimal per-block value), not the mean-of-v approximation that Adam-mini actually uses. The mean-of-v approach (used in Adam-mini) does not outperform Adam — it matches it. The "fewer learning rates can be better" claim is demonstrated only in settings where optimal per-block rates are available via search or eigenvalue information, not in the deployed Adam-mini algorithm.

This is a distinction the paper itself makes (Section 2.4): "currently Adam-mini uses a simple and cost-effective way to design a learning rate... but it might not be an optimal way." The theoretical case that fewer rates *can* be better is made; the practical algorithm uses fewer rates to achieve parity, not superiority.

#### Does the paper demonstrate that the throughput and wall-clock improvements are general or specific to the tested hardware configuration?

**The throughput claim is hardware-specific and not exhaustive.** The 49.6% improvement is measured on exactly 2× A800-80GB GPUs with a specific model (Llama 2-7B) and batch size configuration (1 per GPU for AdamW, 4 per GPU for Adam-mini). The paper does not report throughput on other GPU configurations (4 GPUs, 8 GPUs, different GPU models), other model sizes, or with CPU offloading enabled. The claim that memory reduction "eases the burden of communication among GPUs" is plausible but not directly measured — the paper does not profile communication time separately from computation time. The 33.1% wall-clock reduction is derived from the throughput ratio, not from an actual end-to-end training timing measurement.

On a system where GPU memory is not the bottleneck (e.g., very large GPU clusters where per-GPU batch size is already at the sweet spot for AdamW), the throughput gains may be smaller or zero, because the benefit comes from reducing gradient accumulation steps and GPU synchronization, not from faster per-step computation. The paper's throughput claim should be interpreted as: **under memory-constrained settings typical of academic or small-company GPU clusters, Adam-mini enables larger per-GPU batch sizes, which reduces communication overhead and increases throughput.**

#### What is missing?

1. **No multi-seed statistics.** Every training run appears to be a single trial. The small performance differences (Adam-mini slightly better) could be within run-to-run variance, especially for smaller models.

2. **No Hessian analysis at scale.** The Hessian structure that motivates the partition is characterized only on a tiny Transformer. Whether the block-diagonal structure persists in 7B+ models is untested.

3. **No comparison with Adam-mini using grid-searched per-block rates.** The leave-one-out experiments (Figure 6) use grid search and show how good per-block rates can be; the actual Adam-mini uses mean-of-v. How much performance is left on the table by using mean instead of optimal per-block rates? The paper does not quantify this gap at any model size.

4. **No ablation on partition granularity.** What happens if we partition by groups of 2 attention heads instead of 1? By groups of 8 output neurons instead of 1? The only partitions tested are Algorithm 3 and PyTorch default — there is no interpolation to understand the sensitivity to partition fineness.

5. **Limited non-LLM testing at scale.** The non-LLM experiments (ResNet-18, Swin-Transformer, etc.) are all at small to moderate scale compared to the 7B–13B LLM experiments. Whether Adam-mini's benefits transfer to large-scale vision models (e.g., ViT-22B) or other architectures is unknown.

6. **No testing with ZeRO or model parallelism.** The paper claims compatibility with optimizer state sharding but does not actually measure throughput with ZeRO-1/2/3. The interaction between Adam-mini's block-wise state and ZeRO's partitioning strategy is unexplored.

7. **SFT and RLHF results are on a single model with a single dataset.** The MT-Bench improvements (Table 5) are small (+0.03 to +0.18) and come from one training run each. Statistical significance is unknown, and generalization to other alignment datasets or reward models is untested.

8. **The "value" layer special case introduces a hyperparameter that the paper does not count as a hyperparameter.** Users must decide whether to partition `value` by output neurons or treat it as a single block based on training horizon — a design choice that the paper recommends but does not formalize into the algorithm.

#### Overall Assessment

The experimental section convincingly demonstrates that Adam-mini can replace AdamW with 50% memory savings and no performance degradation across a range of Transformer pre-training scales and tasks. The Hessian-based partition is shown to be necessary (PyTorch default fails) and sufficient (Algorithm 3 works) for stable training. The throughput gains are real but hardware-specific, and the wall-clock reduction of ~33% is a reasonable estimate for memory-constrained settings.

The experiments are **strongest on pre-training** (multiple model families, sizes from 39M to 13B, scaling law analysis) and **thinnest on fine-tuning and non-LLM tasks** (single configurations each, small scales for non-LLM). The novelty of the Hessian-based partition is well-supported by the failure of the naive alternative, but the optimality of the specific partition in Algorithm 3 is not established. The claim that "fewer learning rates can outperform more" is demonstrated in controlled settings using oracle information, but Adam-mini itself achieves parity, not superiority — a distinction the paper acknowledges but that readers may overlook.

## 6. Limitations and Trade-offs

### The Cost of Difficulty Estimation Is Not Accounted for in Reported Efficiency Gains

The entire compute-optimal framework in this paper—the partition strategy that determines which parameters can safely share a learning rate—depends on correctly identifying the Hessian's dense sub-block structure. The paper's method for doing so involves computing and visualizing the Hessian of a small model (1-layer Transformer, embedding dimension 16, 4 attention heads) and manually inspecting the block-diagonal patterns to derive the four-class taxonomy (query/key by heads, attn.proj/MLPs by output neurons, embed/output by tokens, value as an edge case). The authors then assume this structure generalizes to all Transformer architectures at all scales without further verification per model.

This is **not** presented as a runtime cost—the partition is determined once analytically and hard-coded into Algorithm 3—but it is an **epistemic cost**: the correctness of the partition depends on an empirical claim (the Hessian structure observed on a tiny model transfers to production-scale architectures) that the paper does not verify. If the Hessian structure changes at scale—if, say, the block-diagonal pattern in query/key breaks down when the number of heads is 32 instead of 4, or if the MLP Hessian structure depends on the hidden dimension ratio—then Algorithm 3 would be applying the wrong partition to large models, potentially causing the same training instability observed with PyTorch default partition (Figure 7i) but at much larger computational cost.

The paper provides indirect evidence that the partition works at scale: the scaling law experiments (Figure 11) show stable training from 39M to 1B parameters using Algorithm 3, and the 7B and 13B pre-training runs (Figures 1, 10b) also train without loss spikes. However, **stability does not imply optimality**. Algorithm 3 could be a "good enough" partition that avoids catastrophic failure without being the true Hessian-aligned partition. The fact that `value` already requires a special case (Appendix D.6)—partition by output neurons when training steps are large, treat as a single block when steps are small—suggests the Hessian structure is not perfectly captured by the simple rule.

The paper does not attempt to mitigate this by verifying Hessian structure at scale, by providing a systematic method for users to validate the partition on their own architectures, or by analyzing the sensitivity of performance to partition "errors" (mixing parameters that belong to different Hessian blocks). The authors acknowledge the limitation implicitly in Appendix B: "it is possible that we will have more complicated non-Transformer architectures on which Algorithm 3 fails. In those cases, we need to investigate the Hessian structure of these new architectures... and then develop the concrete partition algorithms following our Principle 1." But this places the burden on the practitioner to do Hessian analysis without providing tools or guidance for how to do it at scale.

### No Evidence That Block-Mean `v` Is Optimal or That the Gap to Optimal Is Small

The paper's key design choice—using `mean(g ⊙ g)` as the single learning rate per block—is justified on pragmatic grounds (it is cheap, it keeps Adam-mini close to AdamW's trajectory), not on theoretical or empirical optimality grounds. Section 2.4 states this explicitly: "Adam-mini designs the learning rate for each dense Hessian sub-block using the average of Adam's v in that block. Such a design achieves cheap computation, but it might not be optimal."

The leave-one-out experiments (Figure 6) and the random quadratic experiments (Figure 4) demonstrate that **grid-searched per-block rates** can outperform Adam's per-parameter rates, and can also outperform the mean-based approach. The random quadratic problem (Figure 4b) shows the optimal blockwise-learning-rate method (using eigenvalues) converging substantially faster than Adam—the green curve drops to ~10⁻⁵ in roughly half the iterations that Adam requires. On the 1-layer Transformer (Figure 14 in Appendix D.1), blockwise GD with grid-searched rates outperforms both Adam and Adam-mini. These experiments establish an upper bound on what is possible with per-block rates: much better than Adam-mini's mean-based approach.

The paper **never quantifies the gap** between Adam-mini (mean-based) and optimal per-block rates at any model scale. The ablation in Appendix D.2 (Figure 15) compares mean(v) only against other cheap aggregators (L1-norm, L2-norm, max, min), finding mean works best among these—but none of these are the optimal per-block rate that grid search or eigenvalue analysis could provide. The question a practitioner would want answered is: if I spent the effort to find truly optimal per-block learning rates (perhaps via hyperparameter optimization on a smaller proxy model), how much better would performance be than running Adam-mini with mean(v)? The paper provides no data to answer this.

The consequence is that Adam-mini's 50% memory savings come with an **unknown performance cost relative to what is achievable** with the same block partition but better learning rate design. The paper frames this as "on par or better than AdamW," which is true, but obscures the possibility that per-block rates could substantially exceed AdamW (as Figure 14 suggests) while Adam-mini merely matches it. The practical tradeoff is: you get 50% memory savings with zero tuning (using AdamW's hyperparameters directly), but you may be leaving convergence speed or final performance on the table relative to what the Hessian structure could in principle support.

The authors identify this as "an important future direction" (Section 4, Section 2.4)—developing stronger learning rate designs that use more block information without excessive computation—but the current paper offers no progress toward closing this gap.

### The Partition Principle Is Validated Only on a Single Tiny Model—Its Generality to Production Architectures Is Assumed

The entire Hessian-based partition strategy (Principle 1, Algorithm 3) is derived from a **single empirical observation**: the Hessian of one 1-layer Transformer with 4 attention heads, embedding dimension 16, MLP hidden dimension 32, and vocabulary size 8, computed at 1% of training (Figure 7a-h). From this one data point, the paper infers a universal taxonomy of Transformer Hessian structure:

- Query and key: block-diagonal by attention heads
- attn.proj and MLPs: block-diagonal by output neurons
- Embed and output: block-diagonal by tokens
- Value: ambiguous, possibly by output neurons

There are several reasons to be cautious about this generalization:

**Scale dependence.** The paper does not analyze whether the block-diagonal structure persists when the number of attention heads, embedding dimension, or layer count increases. A 7B model with 32 heads and 4096-dimensional embeddings might exhibit different Hessian structure—heads might not be as independent, or the block boundaries might blur. The scaling law experiments (Figure 11) show stable training with Algorithm 3 up to 1B parameters, which provides indirect evidence that the partition does not cause instability, but does not verify that it remains the correct alignment with Hessian blocks.

**Depth dependence.** The analysis is on a 1-layer Transformer. In deeper models, the Hessian structure of later layers might differ from earlier layers—gradient magnitudes typically vary with depth, and residual connections might induce correlations that break the block-diagonal pattern. The paper provides no Hessian visualizations for layers at different depths, nor does it test whether applying different partition strategies by depth would improve performance.

**Architecture variation.** Modern Transformer variants (mixture-of-experts, grouped-query attention, multi-query attention, different MLP activation functions, parallel vs. sequential attention/MLP sublayers) might have different Hessian structure. The paper's taxonomy is derived from a standard multi-head attention + SwiGLU MLP architecture and may not transfer. The authors acknowledge this implicitly by recommending Algorithm 3 (equivalent to PyTorch default partition) for non-Transformer architectures and stating that new architectures require fresh Hessian analysis—but provide no methodology for performing such analysis at scale.

**Training phase dependence.** The visualizations are at 1% of training. The Hessian structure might evolve during training—early training might exhibit different block patterns than late training, and the optimal partition might need to be dynamic. The paper's MLP experiment (Figure 3b-d) shows the near-block-diagonal structure at 0%, 50%, and 100% of training for a simple MLP, suggesting persistence, but no equivalent timeseries is shown for the Transformer.

The consequence of getting the partition wrong is severe: Figures 7(i) and 8(a) demonstrate that incorrect partitioning causes **loss spikes and training divergence** on models as small as 125M parameters. At 13B scale, such a failure mode could waste thousands of GPU-hours before detection. A practitioner deploying Adam-mini on a custom Transformer variant has no validation procedure to confirm that Algorithm 3's partition is appropriate—the paper simply asserts it works for "Transformers" generically.

### The Throughput Gains Are Hardware-Specific and May Not Generalize to Well-Provisioned Clusters

The paper's most practically compelling claim—49.6% higher throughput and 33% less wall-clock time—is derived from a single hardware configuration: **2× A800-80GB GPUs**, pre-training Llama 2-7B, with AdamW limited to batch size 1 per GPU due to memory constraints while Adam-mini fits batch size 4 (Table 2). The throughput improvement comes from two factors: (1) reduced GPU synchronization due to larger per-GPU batch sizes requiring fewer gradient accumulation steps, and (2) cheaper per-step computation (scalar sqrt/division instead of vector sqrt/division).

Both factors are **highly dependent on the memory bottleneck**. On hardware configurations where GPU memory is not the active constraint, the throughput gains may be much smaller or nonexistent:

- **Larger GPU clusters**: If training a 7B model on 8× or 16× GPUs, the per-GPU memory pressure is lower, and AdamW might already support reasonable batch sizes without gradient accumulation. The communication reduction benefit would shrink accordingly.
- **Smaller models**: For a 1B model, AdamW's memory footprint (~8.8 GB) fits comfortably in 80GB, so batch size is not memory-limited. Throughput gains would come only from cheaper per-step computation, which is negligible.
- **Larger models**: For a 70B model, even with Adam-mini's 50% reduction, the optimizer states alone require ~260 GB, far exceeding any single GPU. Model parallelism (tensor parallelism, pipeline parallelism) would be required regardless, and the communication patterns change substantially. The paper does not test any configuration with model parallelism.
- **CPU offloading enabled**: If ZeRO-Offload or similar techniques are used, the memory bottleneck shifts from GPU to CPU-GPU transfer bandwidth. Adam-mini would reduce the volume of data transferred (fewer bytes for `v`), but the paper does not measure this scenario.

The paper acknowledges none of these dependencies. The throughput claim is presented as a headline number without qualification about when it applies. A practitioner with a 4-GPU or 8-GPU cluster might assume they will see 33% wall-clock reduction, when in reality the gain depends on whether they are operating in the memory-constrained regime where the paper's specific setup applies.

Additionally, the 33.1% wall-clock reduction is **projected, not measured directly**. Table 2 multiplies the throughput ratio by total token amounts to estimate GPU-hours, but does not report an actual end-to-end training wall-clock timing. Real training pipelines have overhead from data loading, checkpointing, evaluation, and other factors that are not captured by throughput (tokens/second) alone. The actual wall-clock savings in a production training run could differ from the 33% estimate.

### The Method Provides No Performance Gains on the Hardest Problems—It Only Maintains Parity

A careful reading of the results reveals that **Adam-mini does not consistently outperform AdamW**—it achieves parity with occasional small improvements that may be within run-to-run noise. The paper's three summary claims (Section 3.4) are: (1) "performs on par with AdamW with 50% less memory," (2) "performs well using the same hyperparameters as AdamW," and (3) "loss curves closely resemble those of AdamW." These are claims about **efficiency without performance cost**, not about improved optimization.

The paper does show some cases where Adam-mini appears slightly better:
- Scaling law experiments (Table 4): perplexity improvements of 0.08–0.48 across model sizes
- RLHF reward (Figure 12b): Adam-mini ~3.30 vs. AdamW ~3.15 at end of training
- MT-Bench scores (Table 5): Adam-mini +0.18 for SFT (LoRA), +0.14 for RLHF
- DiT-XL-2 FID (Table 7): Adam-mini 88.20 vs. AdamW 91.83

But these improvements are **small, unreplicated, and not supported by statistical analysis**. Every training run appears to be a single trial with no standard errors, confidence intervals, or multi-seed averages. The paper provides no hypothesis testing or significance assessment. At the scales tested, run-to-run variance from random initialization and data ordering could plausibly account for the observed differences. The improvements are directionally consistent (Adam-mini is never substantially worse) but their magnitude is small relative to what a practitioner would consider a meaningful upgrade—no one would switch to Adam-mini purely for the performance gains; the memory savings are the entire motivation.

This is a **fundamental limitation of the contribution's scope**: Adam-mini is a memory-saving technique, not a better optimizer. It achieves what it claims—50% less memory for the same performance—but does not advance the state of optimization quality. The paper's own theoretical analysis (Figure 4, Figure 14) suggests that block-wise learning rates *could* produce substantially faster convergence if properly optimized, but Adam-mini's mean-based design does not realize this potential. The gap between "what is possible with block-wise rates" (suggested by grid-search experiments) and "what Adam-mini delivers" (parity with Adam) represents an opportunity cost that the paper does not quantify.

This limitation is partially acknowledged in Section 2.4 ("Has room to improve") and Section 4 ("we leave the development of stronger designs as a future direction"), but the messaging throughout the paper—particularly the abstract and introduction—emphasizes "on-par or better performance" in a way that could lead readers to expect optimizer improvement rather than neutral substitution.

### The Method Has Not Been Demonstrated on Non-Transformer Architectures at Comparable Scale

The paper's contribution is fundamentally a **Transformer-specific optimizer**. Principle 1 is architecture-agnostic in its statement ("partition parameters such that each block corresponds to the smallest dense sub-block in the Hessian"), but the concrete realization (Algorithm 3) is derived from and validated only on Transformer architectures. For non-Transformer models, the paper recommends Algorithm 3, which is equivalent to PyTorch default partition—the very strategy that **fails catastrophically on Transformers** (Figures 7i, 8a).

The non-LLM experiments (Table 6) test ResNet-18, Swin-Transformer, DiT-XL-2, DC-AE-Diffusion, DDPM, GCN, and GAT—all at small to moderate scale. The paper reports that Adam-mini "performs on par or better than AdamW" on these tasks, but this is with Algorithm 3 (no special Hessian-based partitioning), and the model sizes are tiny compared to the LLM experiments:

- ResNet-18: ~11M parameters (vs. 13B for largest Llama)
- Swin-Transformer: architecture not specified, but typical Swin-T is ~28M parameters
- DiT-XL-2: 675M parameters (the largest non-LLM model tested, but still 20× smaller than Llama 2-13B)
- GCN/GAT: likely <1M parameters

The gap between the scale of Transformer experiments (up to 13B) and non-Transformer experiments (up to 675M) is **more than an order of magnitude**. The failure mode observed with PyTorch default partition on Transformers—loss spikes on models as small as 125M (Figure 8a) and 1B (Figure 7i)—raises the question of whether similar instability would appear if non-Transformer architectures were tested at comparable scales. The paper provides no evidence either way.

This matters because one of the paper's claimed benefits is that Adam-mini is a **general-purpose memory-efficient optimizer**—the experiments span "language models, diffusion models, vision models, and graph neural networks" (abstract). But if the partition principle is necessary for stability at scale (as the Transformer results suggest), and if the partition principle has only been validated for Transformers (via Hessian analysis), then the general-purpose claim is unsubstantiated for non-Transformer architectures at any scale where memory efficiency actually matters.

The paper does not explore the Hessian structure of CNNs, diffusion models, or GNNs to determine whether Principle 1 would produce a non-trivial partition for those architectures. It is possible that certain architectures (e.g., CNNs with shared filters) have fundamentally different Hessian structure where per-parameter rates are genuinely necessary, and Adam-mini's block-wise compression would degrade performance at scale. The Zhang et al. (2024) finding that CNNs have **similar Hessian eigenvalue distributions across blocks** (Appendix E.2, Figure 24a) while Transformers have heterogeneous distributions might imply that CNNs can tolerate coarser partitions than Transformers—but this is conjecture, not evidence.

The mitigation status is poor: the paper acknowledges in Appendix B that Algorithm 3 "should be renamed as Partition for CNNs, Diffusion models, and Graph Neural Networks, since we have only tested Algorithm 3 on these models," and that "it is possible that we will have more complicated non-Transformer architectures on which Algorithm 3 fails." But it provides no methodology for a practitioner to determine whether Algorithm 3 is safe for their architecture, nor any characterization of what "more complicated" means. A user with a novel architecture (say, a state-space model or a graph Transformer) has no guidance on whether to trust Algorithm 3 or invest in Hessian analysis.
