# Ouroboros: Generating Longer Drafts Phrase by Phrase for Faster Speculative Decoding

**ArXiv:** [2402.13720](https://arxiv.org/abs/2402.13720)

## 🎯 Pitch

This paper introduces **Ouroboros**, a training-free framework that improves drafting efficiency for speculative decoding by generating and verifying candidate continuations at the phrase level rather than token-by-token.

---

## 1. Executive Summary

This paper introduces **Ouroboros**, a training-free framework that improves drafting efficiency for speculative decoding by generating and verifying candidate continuations at the phrase level rather than token-by-token. Evaluated on code generation (HumanEval, MBPP), arithmetic reasoning (GSM8K), summarization (CNN/DM), and machine translation (WMT16) using target/draft pairs such as Yi-34B/6B and Llama-2-chat-70B/7B, Ouroboros combines four mechanisms: accelerating drafting via phrases (using Jacobi-iteration-style parallel phrase generation within the draft model's forward passes), lengthening drafts via phrases (concatenating multiple candidate phrase suffixes to the draft and verifying them in a single target-model forward through a custom tree attention mask), generating phrases from verification (salvaging sub-segments of rejected draft tokens that match the target model's verification output), and reusing phrases from history contexts (carrying a phrase pool across consecutive queries to warm-start drafting). Ouroboros achieves speedups of up to 2.8× over speculative decoding and 3.9× over vanilla autoregressive decoding, establishing that phrase-level draft acceleration outperforms token-level drafting — but only when a draft model serves as an intermediary to filter low-quality phrases before target-model verification, rather than feeding retrieved phrases directly to the target model.

## 2. Context and Motivation

### The Core Problem: Drafting Is the Bottleneck in Speculative Decoding

Autoregressive language models are inherently sequential — each token depends on all preceding tokens, forcing generation to proceed one token at a time. This sequential dependency means that even on powerful hardware, most of the available compute capacity sits idle during inference because the memory bandwidth required to load model weights far exceeds the computational throughput required to process a single token. In other words, **LLM inference is memory-bound rather than computation-bound** (Leviathan et al., 2023), and the fundamental limiting factor is not how fast the model can compute, but how many memory accesses are required per generated token.

**Speculative decoding** (Xia et al., 2023a; Leviathan et al., 2023; Chen et al., 2023a) partially solves this by reorganizing the generation process into two phases:

1. **Drafting:** A small, fast draft model generates a batch of candidate tokens autoregressively (e.g., 10 tokens, one at a time).
2. **Verification:** The large target model processes the entire draft in a single parallel forward pass, accepting the longest prefix that matches what it would have generated independently and discarding the rest.

This works because the target model's forward passes are the expensive bottleneck, and speculative decoding amortizes their cost over multiple accepted tokens. The speedup formula (Equation 5 in the paper) captures the tradeoff:

$$\text{speedup} = \frac{[\mathbb{A}(\gamma) + 1] \cdot t_T}{\gamma \cdot t_S + t_T}$$

where $\mathbb{A}(\gamma)$ is the expected number of draft tokens that match the target model's output, $t_T$ is the target model's forward time, $t_S$ is the draft model's forward time, and $\gamma$ is the draft length. The numerator represents the time the target model would have spent generating $\mathbb{A}(\gamma) + 1$ tokens autoregressively (one forward pass per token), while the denominator represents the time spent in speculative decoding: $\gamma$ forward passes of the draft model plus one forward pass of the target model.

The key insight hidden in this formula is that **drafting efficiency is now the bottleneck**. The draft model must generate $\gamma$ tokens sequentially — if $\gamma$ is too small, few tokens are accepted per target forward pass, and the speedup is minimal. If $\gamma$ is too large and the draft is inaccurate, many forward passes of the draft model are wasted producing tokens that get rejected, increasing the denominator and again limiting speedup. Worse, the draft model's sequential generation time ($\gamma \cdot t_S$) can rival or exceed the target model's forward time if $\gamma$ is large enough, eating into the gains.

The paper's pilot experiment (Figure 1) makes this bottleneck concrete. When varying the draft model size for a Llama-2-chat-70B target model on MT-Bench:

> "We observe that larger draft models tend to achieve higher draft accuracy, but the cost of generating drafts also rises, so that medium-sized models offer the best decoding speed."

A 0.068B draft model generates low-quality drafts (fewer accepted tokens), while a 13B draft model generates better drafts but is slow enough that the overall system decelerates. The optimal draft model size (around 1.1B parameters in their experiment) balances these forces, but even at this optimum, the sequential drafting overhead remains the limiting factor. Similarly, when examining the relationship between draft length and speed:

> "The target model can accept more tokens per iteration on average when the draft is longer, but longer drafts introduce more forward passes required for the draft model, and thus, the optimal draft length in speculative decoding is not the largest one."

The fundamental tension is clear: **you want long drafts to amortize the target model's cost, but you pay for every draft token with a sequential forward pass of the draft model**. Breaking this tradeoff — generating long, accurate drafts without paying the full sequential cost — is the central motivation for Ouroboros.

The paper diagnoses this bottleneck as two concrete limitations (Section 1, Figure 2):

- **Insufficient Draft:** Drafting too few tokens leaves speedup on the table, but traditional token-level drafting makes long drafts expensive because each token requires its own forward pass. If the drafting process itself could be accelerated, longer drafts would become affordable, and speedup would increase.
- **Underutilized Draft:** When the target model rejects a draft, only the correct prefix is kept — the rejected suffix tokens are entirely discarded. But the paper shows empirically (Table 1) that rejected drafts often contain **sub-segments** that match what the target model would have generated, even when the overall sequence fails. These matching segments represent wasted drafting effort that could be salvaged.

These two limitations are enforcement mechanisms for a deeper insight: **the sequential nature of drafting, not the verification step, is what ultimately caps speculative decoding speedup**. Improving drafting efficiency — how many accepted tokens you get per unit of drafting cost — is the highest-leverage direction for further gains.

### Why This Matters: Real-World Deployment Economics

The importance of this problem extends beyond academic curiosity about decoding algorithms. LLM inference is **the dominant operational cost for most deployed language models**. Unlike training, which is a one-time (or occasional) capital expense, inference is a continuous operational expense that scales with user demand. Every token generated in a chat application, code completion, or summarization pipeline costs real money in GPU time, electricity, and datacenter capacity.

Speculative decoding has already become a standard acceleration technique because it is **lossless** — unlike quantization, pruning, or distillation, it doesn't change the model's weights and thus cannot degrade output quality. The target model's output distribution is mathematically preserved (Equation 4 establishes that accepted tokens are exactly what the target model would have generated autoregressively). This losslessness property is critical for production deployments where even small quality regressions are unacceptable.

But current speculative decoding leaves substantial efficiency on the table. The paper's baseline measurements show that even with a well-chosen draft model, speculative decoding achieves only modest speedups on certain tasks — for example, 1.11× on GSM8K with Yi-34B/6B (Table 2). In a production setting where inference costs millions annually, a 1.11× speedup saves some money but doesn't fundamentally change the economics. Pushing speedup to 1.84× (as Ouroboros does on the same task) nearly doubles the cost savings — a difference that matters enormously at scale.

Moreover, the problem gets harder with larger target models. A 70B target model (like the Llama-2-chat-70B used in several experiments) is so large that even loading its weights into GPU memory dominates latency. The draft model's sequential overhead, while smaller in absolute terms, becomes a larger fraction of the total because $t_T$ shrinks relative to the draft model's cumulative time when the target model uses tensor parallelism. Improving drafting efficiency thus has accelerating returns as target models scale up.

### Prior Approaches and Their Shortcomings

The paper positions Ouroboros against a landscape of techniques that have been proposed to accelerate LLM inference, each of which addresses part of the problem but leaves the fundamental drafting bottleneck unsolved.

#### Model Compression (Quantization, Pruning, Distillation)

These techniques reduce the target model's computational footprint: quantization stores weights in lower precision (e.g., 4-bit integers instead of 16-bit floats), pruning removes redundant parameters, and distillation trains a smaller model to mimic the larger one. The paper acknowledges these are mature approaches (Section 5.3), but notes they are **not lossless**:

> "model compression methods such as quantization and pruning may cause model performance degradation and sometimes even require non-negligible additional training costs."

For accuracy-critical applications, any degradation is unacceptable. Moreover, compression reduces the memory footprint and per-token compute cost but doesn't address the fundamental sequential dependency — even a compressed model still generates one token at a time. Compression and speculative decoding are **orthogonal** (the paper explicitly notes they can be combined), but compression alone cannot solve the drafting bottleneck that Ouroboros targets.

#### Non-Autoregressive Decoding

Non-autoregressive methods (Wei et al., 2019; Guo et al., 2020; Ghazvininejad et al., 2019) attempt to break the sequential dependency entirely by generating multiple tokens in parallel through techniques like masked language modeling or iterative refinement. The paper acknowledges their speed advantages but notes a critical flaw:

> "These non-autoregressive methods bring an improvement in inference efficiency and also significantly hurt model performance."

The quality degradation is severe enough that non-autoregressive methods have not seen widespread production adoption, especially for tasks requiring precise reasoning or long coherent outputs. They trade quality for speed, while speculative decoding (and Ouroboros) achieves speed without sacrificing quality.

#### Training-Based Speculative Decoding Enhancements

Several works have attempted to improve speculative decoding by training custom draft models or auxiliary components:

- **Distillation-based alignment** (Miao et al., 2023; Zhou et al., 2023): Training the draft model to better match the target model's distribution, increasing $\mathbb{A}(\gamma)$. This helps but doesn't accelerate the drafting process itself.
- **EAGLE** (Li et al., 2024): Trains a specialized tiny draft model (as small as 1B parameters for a 70B target) with a novel architecture that incorporates feature uncertainty. This achieves impressive draft generation speed but trades off draft accuracy — the paper's comparison in Table 5 shows EAGLE produces fewer accepted tokens per iteration (3.48 on average vs. Ouroboros's 4.96 on Spec-Bench) because the aggressive size reduction impairs the draft model's ability to predict the target's output.
- **Medusa** (Cai et al., 2024) and **PaSS** (Monea et al., 2023): Add extra prediction heads to the target model itself, allowing parallel generation of multiple future tokens. These require training the additional heads and fine-tuning, tying the acceleration method to a specific model.
- **Self-Speculative Decoding** (Zhang et al., 2024a) and **PPD** (Yang et al., 2023b): Use a subset of the target model's layers as the draft model. This avoids needing a separate draft model but requires architectural modifications and retraining.

All of these training-based approaches share a limitation: they require non-trivial model development work (training runs, data preparation, architecture changes) and are tied to specific models. If you want to accelerate inference for a new model, you need to repeat the training pipeline. Ouroboros, in contrast, is **entirely training-free** — it works with any draft/target model pair out of the box, using only heuristic phrase generation strategies.

#### Phrase-Based Drafting Without a Draft Model

Existing methods that use phrases for drafting fall into a pattern that the paper identifies as suboptimal: they retrieve phrases from prompts, documents, or n-gram pools and feed them **directly to the target model** for verification:

- **Lookahead Decoding** (Fu et al., 2023): Generates an n-gram pool using Jacobi iteration and feeds n-grams matching the current context to the target model. Each round of phrase drafting requires a forward pass of the target model, which is extremely expensive. As the paper notes (Section 3.1): "each round of phrase drafting requires a forward pass of the target model to verify the draft, limiting the whole acceleration effect." The target model is the expensive resource — making it verify every draft phrase individually wastes its capacity.
- **PLD** (Prompt Lookup Decoding) (Saxena, 2023): Searches for matching n-grams in the prompt and feeds them as candidate continuations to the target model.
- **LLMA** (Yang et al., 2023a) and **REST** (He et al., 2024): Retrieve phrases from reference documents or retrieval corpora.

The paper's experiments (Table 6) quantify the weakness of this direct-verification approach. PLD and REST both produce dramatically fewer accepted tokens per iteration (1.51 and 1.83 on average, respectively) compared to Ouroboros (4.96), because:

> "We are the first to use a draft model as an intermediary to filter away low-quality phrases before providing them to the target model."

Without a draft model to serve as a quality filter, the target model wastes forward passes verifying phrases that are unlikely to be accepted. The draft model is much cheaper per forward pass than the target model (by roughly 10× in typical pairings like 7B/70B), so it makes economic sense to let the draft model reject bad phrases before the target model ever sees them.

#### Tree-Structured Verification

The paper builds on an established technique from the speculative decoding literature: verifying multiple draft candidates simultaneously using a **tree-structured attention mask**. This approach, used in SpecInfer (Miao et al., 2023), Medusa (Cai et al., 2024), and lookahead decoding (Fu et al., 2023), constructs a custom attention pattern where multiple candidate continuations share a common prefix in the KV cache but diverge into separate branches, all verified in a single target-model forward pass. Ouroboros extends this idea (Section 3.2, Figure 3) to verify $K$ phrase-extended drafts in parallel, making the lengthening strategy practical by eliminating the sequential verification cost.

### How Ouroboros Positions Itself

The paper positions Ouroboros as a **training-free, composable framework** that addresses the drafting bottleneck from two complementary directions:

**1. Make drafting faster (reduce $\gamma \cdot t_S$ per accepted token).** By generating draft tokens at the phrase level using Jacobi-iteration-style parallel generation (borrowed from lookahead decoding but applied to the draft model instead of the target model), the draft model produces multiple tokens per forward pass rather than one. If a forward pass of the draft model would have produced $\gamma$ tokens sequentially at a cost of $\gamma \cdot t_S$, the phrase-level approach produces the same $\gamma$ tokens in roughly $\frac{1}{c}\gamma$ forward passes, where $c$ is the reduction ratio. This directly attacks the denominator of the speedup equation.

**2. Make drafts longer without paying for it (increase $\mathbb{A}(\gamma)$ without increasing drafting cost).** By concatenating $K$ candidate phrase suffixes to an existing draft and verifying them all in a single target-model forward pass (using the tree attention mask), Ouroboros extends the effective draft length by $\beta$ tokens at essentially zero additional drafting cost. The only cost is the slightly increased verification time, but since verification is memory-bound and processing $\gamma + \beta$ tokens costs only marginally more than processing $\gamma$ tokens, this is nearly free. The revised speedup equation becomes:

$$\text{speedup} = \frac{[\mathbb{A}(\gamma + \beta) + 1] \cdot t_T}{\frac{1}{c}\gamma \cdot t_S + t_T}$$

The numerator grows (more tokens accepted per target forward) while the denominator shrinks (fewer draft model forwards per draft), producing compounded gains.

**3. Salvage waste and leverage history.** The phrase generation and reuse mechanisms add two additional sources of draft tokens without paying for them: extracting matching sub-segments from rejected drafts converts wasted draft-model computation into usable phrase pool entries, and carrying phrases across similar queries amortizes the phrase discovery cost across multiple user interactions. These are secondary optimizations that further improve $c$ and the effective draft length, but the paper's ablation (Table 4) shows that accelerating and lengthening drafting via phrases are the dominant contributors to speedup, with salvage and reuse providing additional incremental gains.

A critical architectural insight distinguishes Ouroboros from lookahead decoding: **phrases should accelerate the draft model, not the target model directly**. Lookahead decoding generates phrases and feeds them to the target model for verification, requiring one expensive target forward per phrase round. Ouroboros instead lets the draft model generate and filter phrases cheaply, then batches multiple phrase-extended drafts into a single target model forward. This indirection through the draft model is what enables the cascaded speedup: the draft model absorbs the cost of exploring low-quality phrase candidates, and only the promising ones reach the expensive target model.

Finally, Ouroboros inherits speculative decoding's **losslessness guarantee**. Because all accepted tokens are sampled from the target model's distribution under the same statistical conditions as autoregressive decoding, Ouroboros cannot degrade output quality. The paper verifies this empirically across all datasets (Appendix A, Tables 7–9), showing that task performance metrics (accuracy, ROUGE, BLEU) are identical within floating-point noise between vanilla decoding and Ouroboros. This is essential for adoption — practitioners can drop Ouroboros into an existing speculative decoding pipeline with zero risk of quality regression.

## 3. Technical Approach

### 3.1 Reader Orientation

Ouroboros is a training-free decoding framework that augments any existing speculative decoding setup (target model + draft model) with phrase-level generation, verification, and recycling mechanisms to increase the number of tokens the target model accepts per forward pass while simultaneously reducing the number of draft-model forward passes required to produce those tokens. The system solves the drafting bottleneck in speculative decoding — the tension between wanting long drafts to amortize target-model cost and wanting cheap drafts to avoid wasting draft-model computation — by generating drafts as assemblies of multi-token phrases rather than individual tokens, extending those drafts with zero-cost phrase concatenation, and harvesting reusable phrases from rejected verification results and historical contexts.

### 3.2 Big-Picture Architecture (Diagram in Words)

Ouroboros operates as a modification to the standard speculative decoding loop, inserting four mechanisms around the existing draft model and target model. The components are:

1. **Draft Model (unchanged from speculative decoding):** A smaller autoregressive language model (e.g., 6B or 7B parameters) that produces candidate continuations. In Ouroboros, this model is no longer queried token-by-token — it is queried in a **phrase-parallel** mode where each forward pass generates multiple candidate phrase continuations simultaneously using Jacobi-iteration-style parallel decoding (borrowed from lookahead decoding's mechanism but applied to the draft model rather than the target).

2. **Phrase Pool:** An in-memory data structure that stores and retrieves candidate phrase continuations. The pool is populated from three sources: (a) phrases generated by the draft model during the phrase-parallel drafting step, (b) sub-segments of rejected drafts that match the target model's verification output (salvaged from verification), and (c) phrases accumulated from earlier queries in the same session (reused from history contexts). Each phrase is associated with the token sequence that would precede it in context, enabling fast lookup of phrases starting with a given token.

3. **Custom Tree-Attention Verification Mask:** A modification to the target model's attention mechanism that enables parallel verification of $K$ candidate extended drafts in a single forward pass. The mask constructs a tree-structured KV cache where all $K$ candidate phrase suffixes share the common draft prefix but diverge into separate branches, allowing the target model to score every candidate simultaneously at the cost of roughly one forward pass.

4. **Acceptance and Phrase Harvesting Logic:** After the target model verifies the $K$ extended drafts, Ouroboros selects the phrase suffix that yields the longest accepted continuation (using the same token-matching criterion as standard speculative decoding). The system then harvests two types of residual phrases: (a) sub-segments of the original draft that were rejected as a contiguous prefix but contained internal matches with the target's verification output, and (b) alternative phrase suffixes that were verified but not selected, filtered through the target model's corrections.

Information flows through the system in a repeated loop: (1) the draft model performs phrase-parallel generation to produce a draft and populate/extend the phrase pool, (2) $K$ phrases matching the draft's final token are retrieved from the phrase pool and concatenated to form $K$ extended drafts, (3) the target model verifies all $K$ extended drafts in one forward pass using the tree-attention mask, (4) the longest accepted continuation is output, and (5) rejected sub-segments and unused phrase variants are harvested back into the phrase pool for future iterations.

### 3.3 Roadmap for the Deep Dive

- **First**, the phrase-parallel drafting mechanism: how Jacobi iteration is adapted from lookahead decoding to accelerate the draft model specifically, what the reduction ratio $c$ represents, and why applying phrase-level parallelism to the draft model rather than the target model is the critical architectural decision.
- **Second**, the draft lengthening mechanism: how $K$ candidate phrase suffixes are selected, concatenated, and verified in parallel using the tree-structured attention mask, what the parameter $\beta$ (costless extended length) represents, and how this mechanism produces the revised speedup formula (Equation 6).
- **Third**, the phrase generation from verification mechanism: what "matched tokens" beyond the correct prefix means in practice (Table 1), how sub-segments are identified and extracted from discarded drafts, and how the target model's corrections to unselected phrase variants are captured.
- **Fourth**, the phrase reuse from history contexts mechanism: what constitutes a "similar" context, how the phrase pool persists across queries, and why this produces gains even across different task domains.
- **Fifth**, the revised speedup equation and how all four mechanisms compose to produce compounded efficiency gains.
- **Sixth**, hyperparameter configuration, the heuristic tuning procedure, and the practical recipe for deploying Ouroboros.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems and algorithms paper** whose core idea is that phrase-level drafting — mediated through a draft model as an intermediary quality filter — can simultaneously accelerate draft generation and lengthen drafts at near-zero additional cost, breaking the tradeoff between draft length and drafting efficiency that limits standard speculative decoding.

---

#### 3.4.1 Phrase-Parallel Drafting: Accelerating the Draft Model via Jacobi Iteration

The first and most impactful mechanism in Ouroboros (contributing the largest speedup in the ablation study, Table 4) replaces the draft model's standard token-by-token autoregressive generation with a **phrase-parallel** generation process. The goal is simple: produce $\gamma$ draft tokens using fewer than $\gamma$ sequential forward passes of the draft model.

The paper adopts the **Jacobi iteration** mechanism from lookahead decoding (Fu et al., 2023) but applies it to the draft model rather than the target model. This redirection is the critical design choice. In lookahead decoding, the target model itself performs Jacobi iteration to generate candidate n-grams, and then each n-gram must be verified by a forward pass of the *same* target model. Since the target model is the expensive resource, making it both generate and verify phrases wastes its capacity — each target-model forward pass can either generate new phrases or verify existing ones, but not both efficiently.

Ouroboros avoids this cost structure entirely: the cheap draft model handles the computationally wasteful task of generating candidate phrases, and the expensive target model only needs to verify the most promising ones. The paper states this explicitly (Section 3.1):

> "Different from lookahead decoding, we use phrases to indirectly accelerate the target model T through a draft model S, allowing each forward pass of the target model to simultaneously verify multiple rounds of phrases, achieving a better acceleration."

**The Jacobi iteration mechanism (as adapted from Fu et al., 2023).** In standard autoregressive generation, the draft model produces tokens one at a time: generate $d_1$, then condition on $d_1$ to generate $d_2$, then condition on $d_1, d_2$ to generate $d_3$, and so on. Each step requires a separate forward pass through the draft model because the model must ingest the newly generated token to compute the next-token distribution.

Jacobi iteration breaks this sequential dependency by initializing a "guess" sequence of length $\gamma$ and then iteratively refining all positions in parallel. The process works as follows:

1. **Initialization:** A sequence of $\gamma$ placeholder tokens is appended to the input context. These can be padding tokens, repeated copies of the last real token, or random tokens — the method is not sensitive to initialization quality because the iterative refinement converges quickly.

2. **Parallel forward pass:** The draft model processes the entire sequence (context + $\gamma$ placeholders) in a single forward pass. For each position $i$ in the placeholder region, the model produces a next-token distribution based on the current guesses at positions $1$ through $i-1$.

3. **Update:** Each placeholder token is replaced by the token that the model predicts for that position (typically using greedy selection, i.e., taking the argmax of the distribution).

4. **Iteration:** Steps 2–3 are repeated for a fixed number of rounds. With each iteration, the guessed sequence converges toward what the model would produce autoregressively. Eventually, some number of tokens stabilize — they stop changing between iterations — and these stabilized tokens form a high-confidence "phrase" that can be used as a draft.

The key efficiency gain is that **one forward pass of the draft model generates or refines $\gamma$ tokens simultaneously** rather than just one token. In standard autoregressive drafting, producing $\gamma$ tokens costs $\gamma$ forward passes. With Jacobi iteration using $m$ refinement rounds, the cost is $m$ forward passes, and $m$ is typically much smaller than $\gamma$ because multiple tokens stabilize per round. The paper captures this as the **reduction ratio $c$**, where the effective cost of generating $\gamma$ tokens becomes $\frac{1}{c}\gamma$ forward passes, with $c > 1$ representing the average number of tokens produced per forward pass.

**How Ouroboros integrates Jacobi iteration.** The paper does not re-derive the Jacobi iteration algorithm but references Fu et al. (2023) for the implementation details (Section 3.1: "We will not go into detail how to generate new draft phrases in parallel due to space constraints, and can refer to Fu et al. (2023)"). The contribution is not the Jacobi iteration mechanism itself but its **strategic deployment**: running Jacobi iteration on the draft model produces phrases that are then added to the **phrase pool**. These draft-model-generated phrases serve as the primary source of candidate continuations for the draft lengthening step (Section 3.2).

The phrases produced by Jacobi iteration are multi-token sequences that have stabilized under the draft model's own distribution. By storing them in the phrase pool indexed by their starting token, Ouroboros can later retrieve and concatenate them to extend drafts at zero additional drafting cost — the phrase was already generated and its cost already paid.

**Why apply Jacobi iteration to the draft model and not the target model?** The paper provides a direct comparison through its experimental results against lookahead decoding (which applies Jacobi iteration to the target model). Lookahead decoding achieves speedups of 1.17× to 1.64× across tasks (Table 2), while Ouroboros achieves 1.35× to 2.68× — consistently and often substantially higher. The architectural reason is that each round of Jacobi iteration on the target model costs $t_T$ (a full target-model forward pass), and lookahead decoding requires multiple such rounds before the final verification. Ouroboros instead spends $t_S$ per Jacobi iteration round (a draft-model forward pass, typically 5–10× cheaper), and the target model only pays $t_T$ once per verification cycle, to verify multiple phrase-extended drafts simultaneously.

#### 3.4.2 The Revised Speedup Equation: Compounding Draft Acceleration and Draft Lengthening

The paper introduces a revised speedup formula (Equation 6) that captures the combined effect of the two primary mechanisms: accelerating drafting via phrases (reducing draft-model forward passes) and lengthening drafts via phrases (adding tokens at zero draft-model cost).

The standard speculative decoding speedup (Equation 5) is:

$$\text{speedup} = \frac{[\mathbb{A}(\gamma) + 1] \cdot t_T}{\gamma \cdot t_S + t_T}$$

where $\mathbb{A}(\gamma)$ is the expected number of accurate draft tokens (tokens in the draft that match what the target model would have generated), $\gamma$ is the draft length, $t_S$ is the forward time of the draft model, and $t_T$ is the forward time of the target model.

**What it computes:** the ratio of target-model forward-pass time saved (the numerator — the time the target model would have spent generating $\mathbb{A}(\gamma) + 1$ tokens autoregressively) to the total time spent in speculative decoding (the denominator — the time for $\gamma$ draft-model forward passes plus one target-model forward pass).

**Why this form:** the speedup is determined by three interacting factors. First, $\mathbb{A}(\gamma)$ captures draft quality — how many draft tokens the target model actually accepts. Second, $\gamma \cdot t_S$ captures draft cost — how much time was invested in producing the draft. Third, $t_T$ captures the unavoidable verification cost. The ratio is inherently bounded because $\mathbb{A}(\gamma) \leq \gamma$ (you cannot accept more tokens than you draft) and $\mathbb{A}(\gamma)$ grows sublinearly with $\gamma$ (longer drafts are harder to get fully correct).

Ouroboros modifies two terms in this equation. First, drafting acceleration reduces the draft generation cost from $\gamma \cdot t_S$ to $\frac{1}{c} \gamma \cdot t_S$, where $c > 1$ is the average number of draft tokens generated per forward pass of the draft model using Jacobi iteration. If Jacobi iteration produces, say, 4 tokens per forward pass on average, then $c = 4$ and the draft cost drops by a factor of 4. Second, draft lengthening adds $\beta$ tokens to the draft at essentially zero additional draft-model cost (the phrases are retrieved from the pool, not generated afresh), increasing the expected accepted tokens from $\mathbb{A}(\gamma)$ to $\mathbb{A}(\gamma + \beta)$.

The resulting Ouroboros speedup equation is:

$$\text{speedup} = \frac{[\mathbb{A}(\gamma + \beta) + 1] \cdot t_T}{\frac{1}{c} \gamma \cdot t_S + t_T}$$

where $c$ is the phrase-parallel generation factor (tokens generated per draft-model forward pass), $\beta$ is the costless extended length (additional tokens concatenated from the phrase pool without new draft-model forwards), and all other terms retain their meanings from Equation 5.

**What it computes:** the numerator grows because a longer draft yields more accepted tokens on expectation (since $\mathbb{A}$ is monotonically non-decreasing — giving the target model more candidates to verify can only increase or maintain the number of matches). The denominator shrinks because the same $\gamma$ base tokens are now produced in fewer forward passes. The combined effect is multiplicative: the numerator increases while the denominator decreases, producing a speedup that can exceed the sum of either mechanism applied independently.

**Why this form:** it isolates the two levers Ouroboros provides over standard speculative decoding. The parameter $c$ quantifies how much phrase-parallelism accelerates drafting — a pure engineering improvement to the draft generation process that doesn't depend on target-model behavior. The parameter $\beta$ quantifies how much phrase-pool retrieval lengthens drafts — a cost-free increase in draft scope that leverages the memory-bound nature of target-model verification. The fact that $c$ appears in the denominator (reducing cost) while $\beta$ appears in the numerator (increasing benefit) means that the two mechanisms compound rather than competing for the same budget.

#### 3.4.3 Lengthening Drafts via Phrases: Candidate Selection, Concatenation, and Tree-Attention Verification

Once the draft model has produced a base draft $d_1, d_2, \ldots, d_\gamma$ (using the accelerated phrase-parallel process), Ouroboros attempts to extend this draft at zero additional draft-model cost by appending candidate phrase suffixes retrieved from the phrase pool.

**Candidate selection.** Given the last token of the draft $d_\gamma$, Ouroboros queries the phrase pool for all stored phrases whose first token equals $d_\gamma$. These are phrases that, in previous contexts (from earlier draft-model Jacobi iterations, from salvaged verification segments, or from historical queries), naturally followed $d_\gamma$ as a continuation. From these matching phrases, $K$ candidates are selected. The paper sweeps $K$ values (Figure 6 shows the effect, with an optimum around $K = 3$ in their experiments), and the default used in most experiments is $K = 3$.

The $K$ selected phrases are denoted $p^1_{1 \ldots \beta}, p^2_{1 \ldots \beta}, \ldots, p^K_{1 \ldots \beta}$, each of length $\beta$ tokens. Critically, the first token of every candidate phrase is guaranteed to match $d_\gamma$: $p^1_1 = p^2_1 = \cdots = p^K_1 = d_\gamma$. This means the phrases naturally extend the draft without introducing a token-mismatch at the boundary — the transition from $d_\gamma$ to the second token of each phrase is what the target model will verify.

The paper notes (Section 3.2) the rationale for trying multiple phrases rather than just one:

> "Trying multiple phrases to get multiple longer drafts can increase the probability that one of these phrases passes the verification of the target model."

If only one phrase is appended and the target model rejects it at the second token, no additional tokens are accepted beyond the base draft. With $K$ candidates, the probability that at least one phrase yields additional accepted tokens grows, and the system selects the best-performing candidate after verification.

**Constructing the K extended drafts.** For each candidate phrase $j \in \{1, \ldots, K\}$, the extended draft is formed by concatenating the base draft with all tokens of the phrase *except the first token* (which is already $d_\gamma$):

$$\text{Extended draft } j: \quad d_{1 \ldots \gamma},\; p^j_{2 \ldots \beta}$$

This produces $K$ distinct drafts, each of length $\gamma + \beta - 1$, all sharing the common prefix $d_{1 \ldots \gamma}$ and diverging at position $\gamma + 1$ where different candidate phrases propose different continuations.

**Tree-attention verification.** Naively, verifying $K$ extended drafts would require $K$ separate forward passes of the target model — one per draft — which would multiply the verification cost by $K$ and defeat the purpose of free draft lengthening. Instead, Ouroboros uses a **custom attention masking mechanism** (Section 3.2, Figure 3) that enables all $K$ drafts to be verified in a single forward pass.

The masking mechanism, inspired by Cai et al. (2024) (Medusa) and similar to the tree attention used in SpecInfer (Miao et al., 2023), works as follows:

1. **Shared prefix:** All $K$ drafts share the initial context $x_{1 \ldots n}$ and the base draft $d_{1 \ldots \gamma}$. In the Transformer's key-value (KV) cache, these tokens are stored once and shared across all $K$ branches. The attention mask for these positions is standard causal: each token attends to all previous tokens in the shared prefix.

2. **Divergent branches:** For the phrase suffix tokens $p^j_{2 \ldots \beta}$ of each branch $j$, the attention mask restricts each token to attend to: (a) the entire shared prefix ($x_{1 \ldots n}, d_{1 \ldots \gamma}$), and (b) the preceding tokens within its own branch ($p^j_{2 \ldots i-1}$). It explicitly **does not** attend to tokens from other branches ($p^{j'}_{2 \ldots}$ for $j' \neq j$), because those tokens are not part of the same candidate continuation.

3. **Parallel computation:** The Transformer processes all tokens — shared prefix plus all $K$ branches — in a single forward pass. The attention masking ensures that each branch's token representations are computed exactly as they would be in $K$ separate forward passes, but the matrix multiplications are batched into one.

Figure 3 in the paper illustrates this masking pattern. The query (Q) attends to keys (K) along two dimensions: the prefix segment and the branch-specific segment, with cross-branch attention blocked out.

**Verification and branch selection.** For each branch $j$ and each position $i$ in the phrase suffix ($i \in \{2, \ldots, \beta\}$), the target model computes a verification token $v^j_i$:

$$v^j_i \sim P_T(\cdot \mid x_{1 \ldots n}, d_{1 \ldots \gamma}, p^j_{2 \ldots i-1})$$

These are sampled from the target model's next-token distribution, conditioned on the shared prefix and the branch-specific preceding tokens. All $v^j_i$ for all $j$ and $i$ are computed simultaneously in the single tree-attention forward pass.

For each branch $j$, Ouroboros then determines the number of consecutive matches $\hat{A}^j$ between the phrase tokens and the verification tokens, starting from the second position (since the first position $p^j_1 = d_\gamma$ is already verified as part of the base draft):

$$\hat{A}^j \text{ satisfies: } \begin{cases} v^j_{2 \ldots \hat{A}^j} = p^j_{2 \ldots \hat{A}^j} \\ v^j_{\hat{A}^j+1} \neq p^j_{\hat{A}^j+1} \text{ or } \hat{A}^j = \beta \end{cases}$$

In words: $\hat{A}^j$ is the length of the longest prefix of the phrase suffix (starting from position 2) that matches the target model's verification output. If the entire phrase matches, $\hat{A}^j = \beta$; otherwise, $\hat{A}^j$ is the position of the first mismatch.

**Final acceptance.** The branch with the largest $\hat{A}^j$ is selected:

$$j^* = \arg\max_j \hat{A}^j$$

The final accepted sequence is:

$$d_{1 \ldots \gamma},\; p^{j^*}_{2 \ldots \hat{A}^{j^*}},\; v^{j^*}_{\hat{A}^{j^*}+1}$$

That is: the entire base draft (which was already verified during the base draft verification), followed by the matching prefix of the best phrase suffix, followed by the target model's corrected token at the mismatch position. This yields a total of $\gamma + \hat{A}^{j^*} + 1$ accepted tokens from one target-model forward pass, where the base draft contributed $\gamma$ tokens, the phrase contributed $\hat{A}^{j^*}$ costless tokens, and the target model contributed one corrected token.

**Why this form of verification works.** The memory-bound nature of Transformer inference is the enabling physical property. In the GPU execution model, loading model weights from GPU HBM (high-bandwidth memory) dominates latency, while the actual matrix multiplications are relatively fast. Verifying a draft of length $\gamma$ tokens requires approximately the same weight-loading cost as verifying a draft of length 1 (the weights are loaded once per forward pass regardless of sequence length, within reasonable bounds). Therefore, extending the draft by $\beta$ tokens adds negligible verification time — Leviathan et al. (2023) established this empirically. The tree-attention mask adds some overhead from processing $K$ branches, but as long as $K$ is small (the paper uses $K = 3$), this overhead is modest.

The alternative — verifying the $K$ extended drafts in $K$ separate forward passes — would cost $K \cdot t_T$, completely undermining the "costless" nature of the draft extension. The tree-attention mask enables the cost to remain approximately $1 \cdot t_T$, making the $\beta$ additional tokens nearly free.

**The $\beta$ parameter and its tuning.** What is the optimal phrase length $\beta$? The paper recognizes a tradeoff (Section 4.3, Figure 6). Longer phrases ($\beta$ large) increase the potential gain when a phrase is accepted, because more tokens are added per successful extension. But longer phrases are less likely to be fully accepted — the probability that the target model's output matches $\beta$ consecutive tokens from the phrase pool decreases with $\beta$. The paper sweeps $\beta$ values experimentally and reports (Appendix B) that values in the range $\beta \in [5, 7]$ work well across tasks. Combined with the tree-verification approach, $\beta$ tokens are verified at the cost of one target-model forward pass.

#### 3.4.4 Generating Phrases from Verification: Salvaging Rejected Draft Sub-Segments

Standard speculative decoding discards all draft tokens after the first mismatch. If the draft model produces $d_1, d_2, \ldots, d_\gamma$ and the target model accepts $d_1, \ldots, d_A$ but rejects $d_{A+1}$ (because $v_{A+1} \neq d_{A+1}$), tokens $d_{A+2}, \ldots, d_\gamma$ are thrown away, even though some of them might be individually correct — they just happen to appear in a context that differs from what the target model would produce.

The paper quantifies this waste through a simple experiment (Section 3.3, Table 1). For a Yi-34B/6B target/draft pair on MBPP, CNN/DM, and WMT16, it compares two quantities:

- **A:** the number of consecutive accurate tokens in the draft prefix (the standard speculative decoding acceptance length).
- **#Match:** the total number of tokens in the draft that match the target model's verification output, *regardless of position continuity*, defined as:

$$\text{\#Match}(d_{1 \ldots \gamma}, v_{1 \ldots \gamma}) = \sum_{i=1}^\gamma \mathbb{1}[d_i = v_i]$$

where $\mathbb{1}[d_i = v_i] = 1$ when the draft token equals the verification token at the same position, and 0 otherwise.

The results are striking (Table 1):
- On MBPP: $A = 12.7$ vs. $\text{\#Match} = 18.9$
- On CNN/DM: $A = 8.4$ vs. $\text{\#Match} = 17.8$
- On WMT16: $A = 5.3$ vs. $\text{\#Match} = 17.0$

In every case, **#Match is substantially larger than A** — often by a factor of 2–3×. This means that within a rejected draft, many tokens that the target model *would* have produced are present but at non-contiguous positions.

The paper diagnoses why this happens (Section 3.3, Figure 4):

> "We view some specific cases and find that sometimes the emergence of this situation is caused by the misplacement of the generation."

The draft model might produce the right tokens but in the wrong order or with extra/missing tokens interspersed. For example, the draft might generate `[2, 4, 6, 8]` while the target model would generate `[2, 4, 6, 8]` but with a different alignment or with an extra intermediate token. The individual token predictions are correct, but the sequential structure is flawed.

**The phrase harvesting algorithm.** Ouroboros converts this observation into a mechanism for populating the phrase pool. When a draft $d_{1 \ldots \gamma}$ is verified against target-model outputs $v_{1 \ldots \gamma}$ and the acceptance length is $A$, the system examines the rejected suffix $d_{A+1 \ldots \gamma}$ to identify **contiguous sub-segments** where the draft tokens match the verification tokens:

1. Scan positions $i$ from $A+1$ to $\gamma$.
2. Whenever $d_i = v_i$, start recording a matching sub-segment.
3. Continue recording as long as $d_j = v_j$ for consecutive positions $j$.
4. When a mismatch occurs ($d_k \neq v_k$), finalize the matching sub-segment and insert it into the phrase pool.

These sub-segments represent tokens that the draft model correctly predicted, and that the target model confirmed, but that were originally rejected because they appeared after a structural error in the draft sequence. By extracting them as standalone phrases, Ouroboros salvages the draft model's wasted computation and makes those tokens available as candidate continuations in future drafting iterations.

Figure 4 illustrates this with a concrete example: a draft `[P, 1, 2, 4, 6, 8]` that gets verified, with mismatches at certain positions but internal matches that form usable phrase sub-segments. The harvesting step extracts `[2, 4, 6, 8]` (or similar) as a reusable phrase.

**Harvesting from unselected phrase branches.** The draft lengthening mechanism (Section 3.4.2) verifies $K$ candidate phrase suffixes but only uses one — the one with the longest $\hat{A}^j$. The other $K-1$ branches represent additional verification effort that is normally wasted. Ouroboros salvages information from these unselected branches as well.

For each unselected branch $o \neq j^*$, the target model produced verification tokens $v^o_{2 \ldots \beta}$. The system creates a corrected phrase by combining the branch's first token (which is $d_\gamma$, already verified as correct) with the target model's verification output for that branch:

$$\text{Corrected phrase: } p^o_1, v^o_{2 \ldots \beta}$$

This corrected phrase is inserted into the phrase pool, replacing the original phrase $p^o_{1 \ldots \beta}$ that contained errors. The logic is that the target model's verification output represents what the target model *would* have generated given the same prefix, so it is a higher-quality candidate for future use than the draft model's original phrase.

This mechanism effectively uses the target model's forward pass — which already had to process the unselected branches due to the tree-attention mask — to also improve the phrase pool. The additional cost is negligible (just storing the corrected tokens in memory), but the benefit is an ongoing supply of target-model-verified phrases that make future drafting more accurate.

#### 3.4.5 Reusing Phrases from History Contexts: Cross-Query Acceleration

The final mechanism leverages a simple observation about real-world LLM deployments: consecutive user queries often exhibit topical or structural similarities. In a code-generation session, the next query likely involves similar programming patterns. In a translation task, consecutive sentences share common phrasing conventions. In a multi-turn dialogue, the conversation maintains topical coherence.

Standard speculative decoding treats each query independently — the draft model starts cold, generating from scratch for each new input. Lookahead decoding clears its n-gram pool between queries. Ouroboros instead **retains the phrase pool across query boundaries**, allowing phrases generated during one query's drafting to accelerate subsequent queries.

The mechanism is straightforward (Section 3.4):

> "Different from lookahead decoding that cleanup phrases from history contexts when conducting the generation of subsequent input queries, we propose to reuse phrases generated from previous generations to further accelerate the drafting process."

When a user submits a new query, Ouroboros does not reset the phrase pool. Instead, it continues to query the pool for phrases matching the current draft's last token, just as it would within a single query. If the pool contains phrases from previous queries that happen to start with the right token, they are candidates for draft extension.

**When does this help?** The paper investigates context locality (Appendix F) by constructing a mixed-domain dataset containing examples from MBPP (code generation), GSM8K (arithmetic reasoning), CNN/DM (summarization), and WMT16 (machine translation), and evaluating Ouroboros under different orderings:

- **High locality (CN=20):** All 20 examples from one dataset are processed consecutively before switching to the next dataset. The phrase pool fills with domain-specific phrases during the first few examples and then provides high-quality candidates for the remaining examples.
- **Medium locality (CN=10, CN=4, CN=1):** Domain switches happen more frequently.
- **No locality (shuffle):** Examples from all domains are randomly interleaved.

Table 17 shows the results. With phrases reusing enabled:
- CN=20 (high locality): 36.00 token/s
- shuffle (no locality): 35.39 token/s
- No phrases reusing: 32.53–32.68 token/s

The key finding is that **phrases reusing helps even in the shuffle setting**, where consecutive queries come from completely different domains. The speed improves from ~32.7 token/s (no reusing) to ~35.4 token/s (reusing, shuffle), a gain of approximately 8%. Under high locality (CN=20), the gain is slightly larger at ~10%.

The paper interprets this robustness as evidence that the phrase pool captures patterns that are useful across tasks — common syntactic structures, function words, punctuation patterns — as well as task-specific vocabulary. Even in the shuffle setting, the pool accumulates a diverse collection of phrases that can match future contexts probabilistically.

**Practical implications.** The phrase reuse mechanism means Ouroboros improves over time within a deployment session. The first query of a session sees only the draft-model-generated phrases (since the pool starts empty). The second query benefits from phrases salvaged during the first query's verification and from any phrase-pool entries generated by the first query's Jacobi iterations. By the tenth query in a consistent domain, the pool is rich with domain-appropriate continuations, and the drafting process has a head start that cold-start speculative decoding cannot match.

This also means that Ouroboros's speedup advantage over standard speculative decoding grows slightly with session length — a property that matters for production deployments where users send many queries within a single session.

#### 3.4.6 Composition of Mechanisms: How They Feed Into Each Other

The four mechanisms are not independent modules that can be swapped in and out arbitrarily — they form a **pipeline with feedback loops** where the output of one mechanism becomes the input to another.

**Forward flow (within a single decoding iteration):**

1. **Phrase-parallel drafting** uses Jacobi iteration on the draft model to produce a base draft $d_{1 \ldots \gamma}$ and simultaneously generates phrases that are added to the phrase pool. The draft model's forward passes are the only source of new computation in this step — all other mechanisms operate on stored data.

2. **Draft lengthening** retrieves $K$ phrases from the pool whose first token matches $d_\gamma$, forms $K$ extended drafts, and verifies them in one target-model forward pass using the tree-attention mask. This step consumes phrases from the pool but does not add any.

3. **Phrase generation from verification** processes the verification results: (a) extracts matching sub-segments from the rejected portion of the base draft, (b) creates corrected phrases from unselected branches using the target model's verification output. These new phrases are inserted into the pool, replenishing and improving it.

**Feedback loops (across iterations and queries):**

4. **Phrase reuse from history** ensures that the pool persists across iterations within a query and across queries within a session. Phrases generated during iteration $i$ of query $j$ are available during iteration $i+1$ of query $j$ and iteration 1 of query $j+1$.

The system thus has a "rich get richer" dynamic: as more phrases accumulate in the pool (from Jacobi iteration, salvage, and history), the draft lengthening step has more and higher-quality candidates to choose from, which increases the likelihood of accepting longer phrase extensions, which in turn produces more salvageable material for the pool. The paper does not formally analyze this feedback loop but empirically demonstrates that the system stabilizes at a higher steady-state speed than cold-start speculative decoding (Table 17, comparing "phrases reusing off" at ~32.6 token/s to "phrases reusing on" at ~35.4–36.0 token/s).

**Why the draft model intermediary is essential to this architecture.** A natural question is: couldn't you eliminate the draft model entirely and just use phrase-pool retrieval + target-model verification? The paper's comparison against PLD and REST (Table 6) answers this. These methods retrieve phrases from prompts or documents and feed them directly to the target model. They achieve far fewer accepted tokens per iteration (1.51 for PLD, 1.83 for REST, vs. 4.96 for Ouroboros on average across Spec-Bench) and correspondingly lower speeds. The reason is that the target model is too expensive to waste on verifying low-quality phrases — the phrase pool inevitably contains many candidates that won't match the target model's output, and the draft model serves as a cheap filter that ensures only promising phrases reach the expensive target model.

The paper states this architectural principle explicitly (Section 3.1):

> "We are the first to use a draft model as an intermediary to filter away low-quality phrases before providing them to the target model."

The draft model thus plays three roles: (1) it generates the base draft that serves as the "stem" to which phrases are attached, (2) it generates phrases via Jacobi iteration that populate the pool with draft-model-consistent continuations, and (3) it serves as a quality filter — only phrases that are consistent with the draft model's own output distribution (because they match $d_\gamma$ and were generated or verified in similar contexts) reach the target model. This filtering role is what makes the phrase-level approach dramatically more efficient than direct retrieval-based methods.

#### 3.4.7 Hyperparameter Configuration and Tuning Recipe

Ouroboros introduces several hyperparameters beyond those of standard speculative decoding. The paper provides both a sensitivity analysis (Appendix B) and a practical tuning recipe (Appendix B.1, Algorithm 1).

**Hyperparameter definitions:**

- **$\gamma$ (base draft length):** The number of tokens generated by the phrase-parallel draft model before phrase extension. This is an upper bound on how many tokens will be produced by Jacobi iteration before the phrase-pool extension kicks in. The paper finds that $\gamma$ should be larger for tasks with high draft-target model agreement (code generation: $\gamma \in [7, 14]$) and smaller for tasks with low agreement (machine translation: $\gamma \in [2, 6]$). Reason: when the draft model closely matches the target, longer base drafts are more likely to be accepted, making the investment in draft-model forward passes worthwhile.

- **$W$ (Jacobi iteration phrase width):** The number of candidate phrases generated during each round of Jacobi iteration. This is a lookahead decoding hyperparameter that controls how many parallel refinement paths are explored. The paper uses values in the range $W \in [15, 20]$ across tasks. Larger $W$ means more candidate phrases per forward pass, which improves the chance of finding high-quality phrases but increases the memory and compute cost per Jacobi iteration round.

- **$\beta$ (phrase extension length):** The number of tokens in each candidate phrase suffix appended to the base draft. Values in $\beta \in [5, 7]$ are used across all tasks. Longer phrases offer larger potential gains but lower acceptance probability.

- **$K$ (number of extended draft branches):** How many candidate phrase suffixes from the pool are concatenated to the base draft and verified in the tree-attention forward pass. The paper sweeps this (Figure 6, tested on HumanEval with Yi-34B/6B) and finds an optimum around $K = 3$ — fewer branches reduce the chance of finding an accepted extension, while more branches increase the tree-attention overhead without proportionally increasing the acceptance probability.

**Sensitivity analysis (Appendix B, Table 10).** The paper reports a grid search on GSM8K with Yi-34B/6B, varying $\gamma \in [3, 5]$, $W \in [14, 16]$, and $\beta \in [5, 7]$. The standard deviation across all configurations is only **0.57 token/s** (with speedup standard deviation 0.04). This low variance indicates that Ouroboros is "stable to hyperparameters" (Appendix B), meaning practitioners do not need exhaustive grid search to find a good configuration — a heuristic approach suffices.

**Heuristic tuning algorithm (Algorithm 1).** The paper proposes a lightweight search procedure that exploits this stability:

1. **Fix $K = 3$:** This value is constant across all experiments.
2. **Sample $\hat{W} \sim [15, 20]$ and $\hat{\beta} \sim [5, 7]$:** These ranges work well across tasks, so any value within them is a reasonable starting point.
3. **Choose $\hat{\gamma}$ based on task type:** For "HH" (High Homogeneity) tasks like code generation where the draft model closely tracks the target model, sample $\hat{\gamma} \sim [7, 14]$. For "LH" (Low Homogeneity) tasks like machine translation, sample $\hat{\gamma} \sim [2, 6]$.
4. **Sequential refinement:** Optimize $\gamma$ first (minimizing clock time on the target dataset with fixed $\hat{W}$ and $\hat{\beta}$), then optimize $W$ using the best $\gamma$, then optimize $\beta$ using the best $\gamma$ and $W$. This greedy coordinate descent is sufficient because the parameters are weakly coupled.

The paper verifies this recipe empirically across all model pairs and datasets (Table 12 lists the specific hyperparameters used in each reported experiment).

**The HH vs. LH task distinction (Appendix B.1, Table 11).** This is a practical heuristic rather than a formal classification. High homogeneity tasks are those where the draft model's output distribution closely matches the target model's — the paper's example is code generation, where both models are trained on similar corpora and produce syntactically constrained outputs. Low homogeneity tasks have greater distributional mismatch — machine translation is the example, where the smaller draft model may produce less fluent or differently structured translations. The optimal $\gamma$ is larger for HH tasks because longer base drafts are more likely to be accepted when the models agree, making the investment in draft-model forward passes pay off.

#### 3.4.8 Why Training-Free Matters: The Deployment Advantage

The paper emphasizes (Section 3.5) that Ouroboros is "entirely training-free" — no model distillation, no fine-tuning, no auxiliary head training, no architectural modifications. All phrase generation strategies are "heuristic" (operating on the draft model's existing forward-pass outputs without learning), and all phrases are "gradually accumulated during the generation process of models, without prior preparation on a large-scale corpus."

This property has three practical implications:

1. **Drop-in compatibility:** Ouroboros can be applied to any existing speculative decoding pipeline without modifying the models. If a deployment already uses a draft model to accelerate a target model, Ouroboros replaces the drafting and verification logic but keeps the same model weights.

2. **Zero preparation cost:** Unlike training-based methods (EAGLE, Medusa, distillation-based speculative decoding), there is no training run, no data preparation, no hyperparameter tuning on held-out data. The phrase pool is built organically during inference.

3. **No quality risk:** Because the output tokens are still sampled from the target model's distribution (the verification step is unchanged), Ouroboros preserves the mathematical losslessness guarantee of speculative decoding. The paper verifies this empirically (Appendix A, Tables 7–9): task performance metrics are identical across vanilla decoding, speculative decoding, lookahead decoding, and Ouroboros, with minor differences attributable to floating-point arithmetic order.

The paper acknowledges that training-based methods can potentially achieve higher speedups in specialized settings (Table 5 compares Ouroboros against EAGLE, which achieves slightly higher throughput on Spec-Bench at 24.96 token/s vs. Ouroboros's 21.51 token/s, but with fewer accepted tokens per iteration). However, the training-free nature of Ouroboros makes it the more practical option for practitioners who cannot or do not want to invest in custom model training.

The paper explicitly positions the training-based version as future work (Section 6):

> "The training-based version of Ouroboros towards extreme acceleration will be our next work."

This suggests that the current Ouroboros represents a **lower bound** on what phrase-level drafting can achieve — training the draft model to better support phrase-parallel generation or training a dedicated phrase-prediction head could further increase $c$ (the reduction ratio), pushing speedups beyond the current training-free ceiling.

## 4. Key Insights and Innovations

### Innovation 1: The Draft Model as an Intermediary Filter — Redirecting Phrase-Level Acceleration

The dominant prior approach to phrase-based decoding was to feed retrieved phrases directly to the target model for verification. Lookahead decoding (Fu et al., 2023) generates n-grams via Jacobi iteration and passes them to the target model; PLD (Saxena, 2023) retrieves matching n-grams from the prompt; REST (He et al., 2024) and LLMA (Yang et al., 2023a) pull phrases from reference documents. All of these share the same architectural assumption: **phrases go straight to the expensive model**.

Ouroboros fundamentally reframes this. The critical conceptual move is inserting a cheap draft model **between** phrase generation and target-model verification. The draft model absorbs the wasteful exploration — generating candidate phrases, rejecting low-quality ones, and only passing promising continuations to the target model — while the target model's expensive forward passes are reserved for high-confidence verification of multiple phrase-extended drafts in parallel.

This is not an incremental optimization of lookahead decoding. It's a structural reorganization of the drafting-verification pipeline that exploits a previously overlooked asymmetry: the draft model's forward pass is 5–10× cheaper than the target model's, so using it to filter phrases before the target model sees them shifts the cost structure of the entire system. The empirical evidence in Table 6 makes this concrete: PLD and REST achieve only 1.51 and 1.83 accepted tokens per iteration on average, while Ouroboros achieves 4.96 — nearly 3× more. The denominator of the speedup equation improves because the target model isn't wasting forward passes on bad phrases; the numerator improves because the phrases that do reach the target model have been pre-screened for consistency with the draft model's distribution, which correlates with target-model acceptance.

This reframing has downstream implications the paper doesn't fully explore but are logically entailed: any future method that generates candidate continuations (retrieval-based, learned, or heuristic) can be inserted upstream of the draft model rather than directly connected to the target model, inheriting the filtering benefit. The draft model becomes a composable quality bottleneck in the inference pipeline, not just a cheap token generator.

This is a **fundamental architectural insight**, not an incremental refinement. It transforms the role of the draft model from "token-level approximator of the target" to "phrase-level quality filter and drafting orchestrator," which is a qualitatively different function.

---

### Innovation 2: Verifying Multiple Extended Drafts as a Tree — Making Draft Lengthening Nearly Free

The idea of extending a draft with additional candidate tokens is not new — standard speculative decoding with larger $\gamma$ does exactly this, and methods like Medusa (Cai et al., 2024) verify multiple candidate continuations in parallel using tree attention. What makes Ouroboros's approach intellectually distinctive is the **zero-cost framing of draft lengthening**, achieved by decoupling the source of draft tokens (the phrase pool, populated from past computation) from the cost of generating them (already paid in previous forward passes).

Standard speculative decoding faces a fixed tradeoff encoded in the speedup equation: longer drafts (larger $\gamma$) increase the expected accepted tokens $\mathbb{A}(\gamma)$ but cost $\gamma \cdot t_S$ in draft-model forward passes. The relationship is roughly linear in cost and sublinear in benefit, creating a hard optimum. Prior work tried to push this optimum by improving the draft model (distillation, architectural changes) or reducing $t_S$ (smaller draft models), but the fundamental $\gamma \cdot t_S$ term remained.

Ouroboros breaks this tradeoff by introducing a new category of draft tokens — those whose generation cost is **already sunk**. Phrases stored in the pool from earlier Jacobi iterations, salvaged from rejected drafts, or carried forward from previous queries have zero marginal drafting cost at the moment they're used. Concatenating them to a base draft increases the effective draft length from $\gamma$ to $\gamma + \beta$ without adding to the $\gamma \cdot t_S$ term. The only new cost is a slightly more expensive target-model forward pass (to verify $\gamma + \beta$ tokens instead of $\gamma$), which is negligible because verification is memory-bound.

The tree-attention verification mechanism (Figure 3) is the enabling technical piece, but the conceptual innovation is the **separation of draft token provenance from draft token cost**. By recognizing that tokens can come from a pre-computed pool rather than being generated on-the-fly, Ouroboros makes draft length a variable that can be increased independently of drafting cost. The revised speedup equation (Equation 6) formalizes this: $\beta$ appears only in the numerator (increasing benefit) while $\gamma$ appears in both numerator and denominator. This is a **reframing of the speculative decoding optimization problem** from "what's the optimal fixed draft length?" to "how do we assemble drafts from a mix of freshly generated and pre-computed tokens to maximize acceptance per unit cost?"

The empirical magnitude is significant (Table 4: lengthening drafts contributes roughly a 12% speedup over the phrase-accelerated baseline on HumanEval), but the conceptual contribution matters more than the raw number. It establishes that speculative decoding's cost structure can be hacked by stockpiling computation across time — a form of amortized inference that has no analog in prior work on single-query decoding acceleration.

---

### Innovation 3: Salvaging Information from Rejected Drafts — Treating Verification as a Phrase Generation Step

Standard speculative decoding treats verification as a binary decision per draft token (accept or reject), with rejected tokens discarded as pure waste. This is a natural but lossy abstraction: it assumes that if a draft fails as a contiguous sequence, none of its sub-parts are useful.

Ouroboros challenges this assumption with a simple diagnostic experiment (Table 1). By comparing the number of **contiguous** accepted tokens (A, the standard metric) against the total number of **position-matched** tokens (#Match, counting any draft token that equals its verification counterpart regardless of continuity), the paper reveals a large gap: on MBPP, A = 12.7 vs. #Match = 18.9; on CNN/DM, 8.4 vs. 17.8; on WMT16, 5.3 vs. 17.0. The draft model is frequently producing the right tokens in the wrong places — a misalignment problem, not an accuracy problem.

This diagnostic insight leads to a **reconceptualization of the verification step**. Verification is no longer just an accept/reject gate; it becomes a **phrase generation source**. The target model's verification output serves as an oracle that identifies which sub-sequences of the draft are salvageable, and those sub-sequences are harvested into the phrase pool for future use. Similarly, unselected branches from the tree-attention verification — which would normally be discarded — are corrected by the target model's outputs and stored as improved phrases.

This is a **new diagnostic concept** with implications beyond Ouroboros. It reveals that speculative decoding's inefficiency isn't primarily about the draft model being wrong — it's about the draft model being **structurally misaligned** with the target model in ways that produce correct local predictions but incorrect global sequences. The field's focus on improving draft model accuracy (distillation, better training) targets the symptom but not the underlying alignment pathology. Ouroboros's salvage mechanism is a pragmatic workaround, but the underlying finding — that draft-target mismatch is often positional rather than predictive — suggests research directions the paper doesn't pursue, such as training draft models to be position-aware or developing verification methods that can reorder as well as filter.

This is an **incremental mechanism** (salvaging sub-sequences is a straightforward algorithmic addition) built on a **fundamental diagnostic insight** (the gap between A and #Match reveals a previously unquantified form of waste). The mechanism matters less than the reframing it enables: verification is not the end of the pipeline but a feedback loop that improves future drafting.

---

### Innovation 4: A Training-Free Framework That Matches Training-Based Methods — And the Implicit Argument This Makes About Drafting Bottlenecks

The paper's comparison against EAGLE (Li et al., 2024) in Table 5 is superficially about performance, but it carries a deeper intellectual payload. EAGLE trains a specialized 1B-parameter draft model with a custom architecture and distillation from the target model. It invests significant training compute to achieve draft generation at roughly 7× smaller model size than Ouroboros's 7B draft model. Despite this aggressive drafting speed optimization, EAGLE achieves only slightly higher throughput than Ouroboros on Spec-Bench (24.96 token/s vs. 21.51 token/s on average) while producing dramatically fewer accepted tokens per iteration (3.48 vs. 4.96).

This comparison is not just "our method is competitive." It constitutes an **implicit argument about where the true bottleneck in speculative decoding lies**. EAGLE optimizes for drafting speed — making the draft model as small and fast as possible — at the expense of drafting effectiveness (fewer accepted tokens). Ouroboros optimizes for drafting effectiveness — keeping the draft model large enough to produce high-quality drafts and using phrases to increase acceptance length — while making drafting faster through parallelism rather than model compression. The fact that these two opposite strategies converge to similar throughput suggests that **there is no single bottleneck to optimize for**, and that the speedup surface has multiple local optima corresponding to different drafting speed/accuracy tradeoffs.

The paper makes this argument explicitly in Section 4.4:

> "We look back at the training-based methods including Eagle, they pursue ultimate drafting speed at the expense of lossing draft accuracy. We, on the other hand, optimize the drafting speed while keeping the accuracy unchanged."

This reframes the speculative decoding optimization problem from "minimize $t_S$" (the dominant assumption in training-based work) to "optimize the speed/accuracy Pareto frontier of the drafting process." Ouroboros demonstrates that keeping draft accuracy high and accelerating generation through parallelism (Jacobi iteration) and reuse (phrase pool) is a viable — and training-free — point on this frontier.

The broader implication is that the field's investment in training smaller draft models may be misallocated. If a training-free method using an off-the-shelf 7B draft model can match a custom-trained 1B model, the marginal benefit of draft model compression (beyond what off-the-shelf models already provide) is limited. The higher-leverage direction — the one Ouroboros opens — is making the existing draft model more efficient at using its forward passes, through parallelism and information reuse, rather than trying to make it smaller.

This is a **conceptual argument supported by empirical evidence**, not a strictly novel mechanism. It qualifies as an innovation because it challenges a dominant assumption in the subfield and redirects research attention toward an underexplored dimension of the optimization problem.

## 5. Experimental Analysis

### Evaluation Methodology

- **Datasets.** The paper evaluates on six benchmarks spanning four task categories. For code generation: **HumanEval** (Chen et al., 2021), 164 entries each consisting of a text prompt and Python function prefix, and the **MBPP** validation set (Austin et al., 2021), 90 entries requiring full function prediction from a text prompt and test cases. For arithmetic reasoning: **GSM8K** (Cobbe et al., 2021), 100 randomly sampled entries. For document summarization: **CNN/DM** (See et al., 2017; Hermann et al., 2015), 100 randomly sampled entries. For machine translation: the **German-to-English subset of WMT16** (Bojar et al., 2016), 100 randomly sampled entries. Maximum generation lengths are set to 512 for HumanEval and MBPP, 256 for GSM8K, 128 for CNN/DM, and 64 for WMT16. For comparisons against training-based methods and prior phrase-based methods, the paper also uses **Spec-Bench** (Xia et al., 2024), reporting results separately on six sub-tasks: MT-Bench (Zheng et al., 2024), Translation, Summarization, QA, Math Reasoning, and RAG.

- **Base Models.** The target/draft model pairs used are: **Yi-base-34B/6B** (Young et al., 2024), **DeepSeek-coder-instruct-33b/6.7B** (Bi et al., 2024), and **CodeLlama-instruct-34B/7B** (Roziere et al., 2023) for code generation tasks (HumanEval, MBPP); **Yi-base-34B/6B** and **Llama-2-chat-70B/7B** (Touvron et al., 2023) for GSM8K, CNN/DM, and WMT16. In each pair, the larger model serves as the target and the smaller as the draft model. These models are described as "recently representative and popular LLMs" (Section 4.1) spanning code-specialized and general-purpose families, and the Llama-2-chat models are specifically noted as being "more suitable for well understanding rich semantics distributed in human natural languages and generating diverse outputs" for the random sampling experiments (Section 4.2).

- **Metrics.** The primary reported metric is **decoding speed in tokens per second (token/s)**, measured as wall-clock time for end-to-end generation. The paper also reports **speedup ratio** — the decoding speed of a method divided by the decoding speed of vanilla autoregressive decoding on the same hardware, model, and dataset configuration. For comparisons against training-based and phrase-based methods on Spec-Bench, the paper additionally reports **#accept** — the average number of draft tokens accepted by the target model per verification iteration — to characterize drafting effectiveness independently of raw throughput. Task performance is verified to be lossless (Appendix A, Tables 7–9) using standard dataset metrics: Accuracy (%) for HumanEval, MBPP, and GSM8K; ROUGE-1 score (%) for CNN/DM; and BLEU score (%) for WMT16.

- **Baselines.** Three baselines are compared: **(1) Vanilla autoregressive decoding** — the target model generates tokens one at a time with no draft model or parallel verification. **(2) Speculative decoding** (Leviathan et al., 2023; Chen et al., 2023a) — the standard token-level drafting-then-verifying framework with a smaller draft model, using greedy decoding (temperature = 0) for the draft model in greedy experiments and temperature-matched sampling in random sampling experiments. **(3) Lookahead decoding** (Fu et al., 2023) — generates n-gram pools via Jacobi iteration applied directly to the target model and verifies phrase candidates using the target model's own forward passes. For comparisons against training-based methods (Section 4.4), **EAGLE** (Li et al., 2024) serves as the primary baseline, using its trained 1B draft model to accelerate Llama-2-chat-70B. For comparisons against phrase-based methods (Section 4.5), **PLD** (Prompt Lookup Decoding; Saxena, 2023) and **REST** (Retrieval-based Speculative Decoding; He et al., 2024) serve as baselines, both retrieving phrases from prompts or documents and feeding them directly to the target model for verification.

- **Generation Budget / Compute Accounting.** The paper does not use a formal "generation budget" abstraction (unlike papers that measure FLOPs or sample counts). Instead, all methods are compared using **wall-clock decoding speed on identical hardware**. This is both a strength (realistic end-to-end measurement) and a limitation (hardware-specific, not a portable efficiency metric). The paper accounts for the computation in Ouroboros's tree-attention verification implicitly — the verification of $K$ extended drafts in one forward pass is timed as a single target-model forward pass, and the wall-clock overhead of the tree-structured attention mask is reflected in the final token/s measurement. Draft-model forward passes (including Jacobi iteration rounds) are similarly timed and included in the total. No analytical FLOP count or memory bandwidth model is provided; all efficiency claims are empirical wall-clock measurements.

- **Statistical Protocol.** The paper does not report confidence intervals, standard errors, or statistical significance tests on speedup measurements. For hyperparameter sensitivity, the paper reports the standard deviation across a grid of configurations (Appendix B, Table 10: "token/s std: 0.57, speedup std: 0.04"), which provides informal evidence of stability but is not a formal statistical protocol. For task performance verification, the paper acknowledges that "the small difference in task performance among vanilla, Speculative, Lookahead and Ouroboros is caused by floating point error" (Appendix A) and treats identical performance within a few tenths of a percentage point as evidence of losslessness. For the heuristic hyperparameter search (Algorithm 1), the optimization is performed by minimizing clock time on a per-dataset basis, which introduces a risk of overfitting hyperparameters to the test set that the paper does not formally control for (no mention of a held-out validation set for hyperparameter selection).

### Main Quantitative Results

#### Greedy Decoding Speed on Code Generation Tasks

Figure 5 presents the headline greedy decoding results on HumanEval and MBPP across three target/draft model pairs. The speedup pattern is consistent:

> "Ouroboros outperforms vanilla greedy decoding, lookahead decoding, and speculative decoding under all backbone models and dataset configurations."

On **HumanEval** with Yi-34B/6B (Figure 5, left panel): Ouroboros achieves 61.2 token/s, compared to 32.3 token/s for lookahead decoding (1.9× speedup over lookahead), 21.5 token/s for speculative decoding (2.8× speedup over speculative), and 15.6 token/s for vanilla decoding (3.9× speedup over vanilla). The gap between Ouroboros and the next-best method (lookahead) is approximately 28.9 token/s — nearly as large as lookahead's total speed. On DeepSeek-coder-33b/6.7B: Ouroboros achieves 41.0 token/s vs. 25.1 (lookahead), 21.5 (speculative), and 15.4 (vanilla). On CodeLlama-34B/7B: Ouroboros achieves 39.2 token/s vs. 27.2 (lookahead), 23.4 (speculative), and 18.3 (vanilla).

On **MBPP** (Figure 5, right panel), the same ordering holds but with somewhat smaller absolute speeds: Yi-34B/6B achieves 44.0 token/s under Ouroboros vs. 27.7 (lookahead), 21.8 (speculative), and 15.5 (vanilla); DeepSeek-coder achieves 31.8 token/s vs. 19.0 (lookahead), 18.0 (speculative), and 15.0 (vanilla); CodeLlama achieves 34.5 token/s vs. 22.7 (lookahead), 20.1 (speculative), and 16.5 (vanilla).

A noteworthy pattern: the absolute speed of Ouroboros varies substantially across model families even when the target/draft size ratio is similar. Yi-34B/6B achieves 61.2 token/s on HumanEval while DeepSeek-coder-33b/6.7B achieves only 41.0 token/s — a 50% difference. Since Ouroboros is training-free, this implies that the draft model's inherent quality and its alignment with the target model significantly impact the phrase-level acceleration, even though the method itself is model-agnostic. The paper does not analyze the source of this cross-model variance, but it likely reflects differences in Jacobi iteration convergence speed and phrase acceptance rates.

#### Greedy Decoding Speed on Natural Language Tasks

Table 2 extends the evaluation to GSM8K (arithmetic reasoning), CNN/DM (summarization), and WMT16 (machine translation) using Yi-34B/6B and Llama-2-chat-70B/7B.

On **Yi-34B/6B**, Ouroboros achieves speedups of 1.84× (GSM8K), 1.55× (CNN/DM), and 1.35× (WMT16) over vanilla decoding. The speedup over speculative decoding is more modest than on code tasks: 1.66× on GSM8K (28.23 vs. 16.99 token/s), 1.27× on CNN/DM (22.65 vs. 17.82 token/s), and 1.14× on WMT16 (19.94 vs. 17.48 token/s). The speedup over lookahead decoding varies: 1.12× on GSM8K (28.23 vs. 25.14), 1.21× on CNN/DM (22.65 vs. 18.77), and 1.11× on WMT16 (19.94 vs. 17.98).

On **Llama-2-chat-70B/7B**, the speedups are substantially larger: 2.68× over vanilla on GSM8K (24.03 vs. 8.96 token/s), 1.81× on CNN/DM (14.67 vs. 8.12), and 2.02× on WMT16 (19.27 vs. 9.52). The speedup over speculative decoding is 1.43× on GSM8K (24.03 vs. 16.86), 1.15× on CNN/DM (14.67 vs. 12.77), and 1.31× on WMT16 (19.27 vs. 14.72). The speedup over lookahead decoding is 1.74× on GSM8K (24.03 vs. 13.77), 1.55× on CNN/DM (14.67 vs. 9.47), and 1.32× on WMT16 (19.27 vs. 14.65).

Two observations stand out from this table. First, **the relative gain of Ouroboros over lookahead decoding is much larger on Llama-2-chat-70B/7B than on Yi-34B/6B** — for example, 1.74× vs. 1.12× on GSM8K. This is consistent with Ouroboros's architectural argument: lookahead decoding's bottleneck (target-model forward passes for phrase verification) becomes more severe as the target model scales up (70B vs. 34B), while Ouroboros's draft-model-mediated approach benefits from the increasing gap between $t_S$ and $t_T$. Second, **on WMT16 with Yi-34B/6B, lookahead decoding achieves a higher absolute speed than speculative decoding (17.98 vs. 17.48 token/s), and Ouroboros's gain over lookahead is only 1.11×** — the narrowest margin in any comparison. This suggests that for machine translation with this model pair, the phrase-level acceleration provides limited additional benefit, possibly because the draft model's Jacobi iteration produces fewer useful phrases when translating between languages (a "low homogeneity" task in the paper's classification).

#### Greedy Decoding Speed Comparison with Training-Based Methods

Table 5 compares Ouroboros against EAGLE (Li et al., 2024) on Spec-Bench, using Llama-2-chat-70B as the target model. Ouroboros uses the off-the-shelf Llama-2-chat-7B as its draft model; EAGLE uses a custom-trained 1B draft model with a specialized architecture.

The headline result is that EAGLE achieves slightly higher average throughput (24.96 token/s) than Ouroboros (21.51 token/s) — a 16% advantage. However, the **source** of the speed is fundamentally different. Ouroboros accepts far more draft tokens per iteration on average: 4.96 vs. EAGLE's 3.48 across all Spec-Bench sub-tasks. The detailed breakdown shows:

| Sub-task | Ouroboros token/s | Ouroboros #accept | EAGLE token/s | EAGLE #accept |
|----------|-------------------|-------------------|---------------|---------------|
| MT-Bench | 24.23 | 5.16 | 28.20 | 3.52 |
| Translation | 18.91 | 3.92 | 24.23 | 3.16 |
| Summarization | 19.91 | 4.93 | 22.03 | 3.16 |
| QA | 21.63 | 4.67 | 24.83 | 3.23 |
| Math Reasoning | 25.39 | 4.95 | 29.90 | 3.81 |
| RAG | 19.00 | 5.43 | 20.56 | 3.54 |

The consistently higher #accept for Ouroboros (ranging from 3.92 to 5.43 vs. 3.16 to 3.81 for EAGLE) reflects the tradeoff the paper emphasizes: EAGLE's much smaller draft model (1B vs. 7B) generates drafts faster but less accurately, producing fewer tokens that the target model accepts per iteration. Ouroboros keeps the larger 7B draft model and accelerates it through phrase parallelism, preserving draft accuracy. The paper frames this explicitly:

> "We look back at the training-based methods including Eagle, they pursue ultimate drafting speed at the expense of lossing draft accuracy. We, on the other hand, optimize the drafting speed while keeping the accuracy unchanged."

This is not simply a speed comparison — it's an argument that there are multiple points on the drafting speed/accuracy Pareto frontier, and training-free phrase-level acceleration occupies a different (and sometimes more practical) point than aggressive draft model compression.

The paper notes a limitation: "Eagle cannot be integrated into Ouroboros since the special model architecture of their draft model only supports autoregressive token-level drafting" (Section 4.4). This means the comparison is between two alternative approaches to improving drafting efficiency, not between combinable techniques. The paper speculates that combining Ouroboros-style phrase parallelism with training (a future direction) could find a "better balance between drafting speed and accuracy."

#### Greedy Decoding Speed Comparison with Phrase-Based Methods

Table 6 compares Ouroboros against PLD (Prompt Lookup Decoding; Saxena, 2023) and REST (Retrieval-based Speculative Decoding; He et al., 2024) on Spec-Bench with Llama-2-chat-70B. These methods retrieve phrases from prompts or documents and feed them directly to the target model for verification, without a draft model intermediary.

The performance gap is large and consistent. Ouroboros achieves 21.51 token/s on average with 4.96 accepted tokens per iteration. PLD achieves 14.44 token/s with 1.51 accepted tokens per iteration. REST achieves 13.83 token/s with 1.83 accepted tokens per iteration. On every sub-task, Ouroboros's #accept is 2.5–3.6× higher than PLD or REST.

This comparison validates a core architectural claim of the paper: introducing a draft model between phrase retrieval and target-model verification dramatically improves phrase quality. Without the draft model's filtering, the target model wastes forward passes verifying low-quality phrases that it rejects after only 1–2 tokens — PLD and REST average fewer than 2 accepted tokens per verification, meaning most of the target model's capacity is spent rejecting phrases at the first or second token. Ouroboros achieves nearly 5 accepted tokens per verification, meaning the target model's expensive forward passes are amortized over many more accepted tokens.

The paper's interpretation is direct:

> "We are the first to use a draft model as an intermediary to filter away low-quality phrases before providing them to the target model."

The magnitude of the improvement (roughly 1.5× the throughput and 3× the acceptance length) makes this more than an incremental improvement — it demonstrates that the direct-verification approach of prior phrase-based methods is fundamentally cost-inefficient.

#### Random Sampling Results

Table 3 evaluates Ouroboros under random sampling (non-greedy generation) with Llama-2-chat-70B/7B, using temperatures 0.5 and 1.0 with top-p = 0.8. The baseline greedy decoding speed is included for reference.

On GSM8K: greedy Ouroboros achieves 24.03 token/s; this drops to 22.04 token/s at temperature 0.5 and 19.27 token/s at temperature 1.0. Despite the reduction, Ouroboros at temperature 1.0 still outperforms speculative decoding under greedy decoding (19.27 vs. 16.86 token/s) and substantially outperforms speculative decoding at temperature 1.0 (14.11 token/s) — a 1.37× speedup. On CNN/DM: Ouroboros at temperature 1.0 achieves 14.23 token/s vs. speculative decoding at temperature 1.0 achieving 13.75 token/s — a modest 1.03× speedup but still faster. On WMT16: Ouroboros is remarkably robust, achieving 19.95 token/s at temperature 0.5 and 19.33 at temperature 1.0, compared to 19.27 under greedy — actually slightly faster under random sampling. Speculative decoding drops from 14.72 (greedy) to 13.91 (temp 0.5) and 14.28 (temp 1.0) on WMT16.

The paper does not deeply analyze why Ouroboros degrades with temperature on some tasks but not others. One plausible explanation: higher temperature reduces Jacobi iteration convergence speed (tokens are less deterministic, so more rounds are needed to stabilize phrases), which increases the effective drafting cost. On WMT16, the effect may be masked because the base speedup is already lower (the draft model has low homogeneity with the target on translation), so temperature-dependent effects are proportionally smaller.

The key practical finding is that Ouroboros works under random sampling — it is not restricted to greedy decoding. The paper notes that Llama-2-chat was chosen for random sampling experiments because SFT-trained chat models are "more suitable for well understanding rich semantics distributed in human natural languages and generating diverse outputs" (Section 4.2).

#### Task Performance Verification

Appendix A (Tables 7, 8, and 9) verifies that Ouroboros does not degrade task performance. The key claim:

> "Theoreotically, Speculative Decoding, Lookahead Decoding and Ouroboros generates the same token sequences compared with vanilla Decoding. We observe no overall performance degradation of Ouroboros."

Table 7 (HumanEval and MBPP, greedy): Yi-34B/6B achieves 18.3% (vanilla), 18.9% (speculative), 18.9% (lookahead), 18.9% (Ouroboros) on HumanEval — identical within the variation attributable to floating-point arithmetic. The same holds across all model pairs and both datasets. Table 8 (GSM8K, CNN/DM, WMT16, greedy): Near-identical performance across all methods, with occasional 1-point differences (e.g., GSM8K Yi-34B/6B: 61.0% for all methods except Ouroboros at 61.0%; Llama-2-chat: 66.0% for vanilla/speculative/lookahead, 65.0% for Ouroboros — a 1% difference attributed to floating-point error). Table 9 (random sampling): Similarly stable performance, with some fluctuation (e.g., WMT16 BLEU: 20.6 vanilla, 21.2 speculative, 22.7 lookahead, 25.0 Ouroboros — a 4.4 point improvement that the paper does not explain but is framed within "overall no performance degradation").

The paper explicitly acknowledges the source of minor variations:

> "The small difference in task performance among vanilla, Speculative, Lookahead and Ouroboros is caused by floating point error, since the calculations are not fully the same between the methods (especially the calculation order of attention). The experimental results show that the calculation error would not cause notable performance degradation."

This is an important verification because Ouroboros introduces modifications to the attention masking (tree-structured verification) and the generation process (phrase concatenation) that could, in principle, alter the numerical computation path enough to change outputs. The data show that these numerical differences do not systematically degrade or improve performance — the variations are symmetric around the vanilla decoding baseline and small in magnitude.

### Ablation Studies and Robustness Checks

**Ablation of each Ouroboros component (Table 4, Section 4.3):** Table 4 ablates the four mechanisms incrementally on HumanEval with Yi-34B/6B. The baseline (speculative decoding) achieves 21.46 token/s. Adding phrase-parallel drafting (Section 3.1) raises speed to 49.90 token/s — a 2.33× improvement over the baseline, making this the single largest contributor. Adding draft lengthening via phrases (Section 3.2) further raises speed to 55.92 token/s — an additional 12% gain. Adding phrase generation from verification (Section 3.3) raises speed to 58.18 token/s — an additional 4% gain. Adding phrase reuse from history contexts (Section 3.4) raises speed to the final 61.20 token/s — an additional 5% gain.

This ablation establishes a clear hierarchy: **phrase-parallel drafting >> draft lengthening > phrase salvage ≈ phrase reuse**. The fact that the first mechanism alone provides over 2× speedup validates the paper's central architectural claim — that applying Jacobi iteration to the draft model is far more impactful than any of the phrase-pool mechanisms. The subsequent mechanisms provide incremental but compounding gains, with the full stack achieving 2.85× over the speculative decoding baseline.

Two important notes: First, the baseline here is speculative decoding at 21.46 token/s, not the vanilla decoding baseline of 15.6 token/s. So the 2.85× gain is multiplicative on top of speculative decoding's already-1.38× speedup over vanilla, yielding the paper's headline 3.9× total speedup. Second, this ablation was conducted only on HumanEval with Yi-34B/6B. The paper does not provide per-mechanism ablations on other datasets or model pairs, so the relative contribution of each mechanism may vary by task. The draft lengthening mechanism, for example, may contribute more on tasks where the phrase pool accumulates higher-quality candidates (code generation, with its repetitive syntactic patterns) and less on tasks like machine translation.

**Effect of the number of extended draft branches K (Figure 6, Section 4.3):** Figure 6 sweeps $K$ (the number of candidate phrase suffixes verified in the tree-attention forward pass) from 0 to 9, tested on HumanEval with Yi-34B/6B **without** phrase reuse from history contexts (to isolate the lengthening mechanism). The result:

> "There exists a best K value, fewer or more phrases cause slower decoding speed."

The speed increases from approximately 54 token/s at $K = 0$ (no extension) to a peak of approximately 58 token/s at $K = 3$, then declines to approximately 56.5 token/s at $K = 9$. The paper attributes the decline past the optimum to the increased tree-attention overhead: verifying more branches increases the target model's forward-pass time (more tokens to process in the attention pattern), and this cost eventually outweighs the benefit of having more candidate extensions.

The optimum at $K = 3$ is used as the default across all experiments. The paper does not analyze whether this optimum depends on the task, the model pair, or the phrase pool quality — $K = 3$ is treated as a universal constant. The fact that the curve is relatively flat between $K = 2$ and $K = 5$ (all within ~1 token/s of the optimum) suggests that the exact value is not critical, but the ablation is limited to a single configuration.

**Hyperparameter sensitivity analysis (Appendix B, Table 10):** The paper conducts a grid search over $\gamma \in [3, 5]$, $W \in [14, 16]$, and $\beta \in [5, 7]$ on GSM8K with Yi-34B/6B, measuring token/s for all 27 combinations. The standard deviation across configurations is 0.57 token/s on a mean of approximately 28–29 token/s — roughly 2% relative variation. The speedup standard deviation is 0.04 on speedups in the 1.8–2.0× range.

This low variance is interpreted as evidence that "Ouroboros is stable to hyperparameters" (Appendix B). This is a practically important finding: it means practitioners can use the heuristic tuning procedure (Algorithm 1) — which is essentially a greedy coordinate descent starting from reasonable defaults — without risk of landing in a catastrophically bad configuration. The stability also suggests that the four mechanisms compose smoothly; there are no narrow hyperparameter regions where performance spikes or collapses.

However, the grid search covers only a narrow range of each parameter ($\gamma$: 3 values, $W$: 3 values, $\beta$: 3 values) on a single task and model pair. The stability result should not be over-interpreted as evidence that any hyperparameter values work — the ranges were chosen based on the paper's recommended recipe (Table 11), and values far outside these ranges might perform substantially worse.

**Effect of generation length limits (Appendix E, Tables 15–16):** To rule out the hypothesis that Ouroboros's speedup comes from early stopping or phrase repetition, the paper evaluates performance under generation length limits of 64, 128, 256, and 512 tokens on GSM8K with Yi-34B/6B.

Table 15 shows Ouroboros's speedup grows with the generation length limit: 2.17× at $l = 64$, 2.42× at $l = 128$, 2.66× at $l = 256$, and 2.67× at $l = 512$ (all compared to greedy decoding at the same length limit). This monotonic increase is consistent with the phrase pool mechanism: longer generations provide more opportunities for the pool to accumulate useful phrases, and the amortization of phrase discovery cost improves with sequence length.

Table 16 verifies that task performance is not degraded at any length limit — accuracy is identical within 1% across all methods at each length, with shorter limits ($l=64, 128$) causing answer truncation and lower absolute accuracy (44.5%, 61.0%) compared to adequate limits ($l=256, 512$ at 63.4–64.6%). The paper concludes:

> "Two conclusions can be obtained. First, the length limits used in our experiments are reasonable, as shorter length limits result in ill-generated answers. Second, phrase repetition in the generation is not the reason why Ouroboros achieves such a high speedup."

The second conclusion addresses a potential concern: that Ouroboros might achieve speedup by generating repetitive phrases that inflate the acceptance count without producing meaningful output. If this were happening, the task performance would degrade (repetitive output wouldn't match the reference). Since performance is preserved, the accepted phrase extensions represent genuine, non-repetitive content.

**Context locality ablation for phrase reuse (Appendix F, Table 17, Figure 7):** The paper constructs a mixed-domain dataset with 20 examples each from MBPP, GSM8K, CNN/DM, and WMT16 (80 examples total), and evaluates Ouroboros under different ordering conditions that vary the "consecutive number" (CN) — how many examples from the same dataset appear consecutively before switching domains. CN=20 means all 20 examples from each domain are processed as a block; CN=1 means examples alternate between domains; "shuffle" randomizes the order completely.

Table 17 shows the results. With phrases reusing turned **off**, speed is 32.68 token/s (shuffle) and 32.53 token/s (CN=20) — essentially identical, confirming that without reuse, domain ordering doesn't matter. With phrases reusing turned **on**, speeds are:
- CN=20 (highest locality): 36.00 token/s
- CN=10: 35.32 token/s
- CN=4: 34.83 token/s
- CN=1: 35.36 token/s
- shuffle (lowest locality): 35.39 token/s

The main finding is that **phrases reusing helps even in the shuffle setting** — speeds improve from ~32.6 token/s (no reuse) to ~35.4 token/s (reuse, shuffle), a gain of approximately 8.5%. Higher locality provides an additional small boost (36.00 vs. 35.39 token/s for CN=20 vs. shuffle), but the effect of locality is smaller than the effect of turning reusing on at all. The paper interprets this:

> "The effect caused by context locality is smaller than whether to turn on the phrases reusing. The speed of lower CN is similar to the shuffle setting when applying phrases reusing, but both are approximately 3 token/s faster compared to the cold start setting, proving that the phrases pool is still effective across multiple tasks."

This suggests that the phrase pool accumulates generally useful linguistic patterns (common syntactic structures, frequent token sequences) that transfer across domains, not just domain-specific patterns. The practical implication is that Ouroboros's phrase reuse mechanism does not require task-homogeneous query streams — it provides benefit even in mixed-domain deployments, which is the more realistic production scenario.

**Block efficiency analysis (Appendix C, Definition C.1, Table 13):** Block efficiency $\eta$ is defined as the ratio of generated tokens to target-model forward-pass calls, representing the theoretical upper bound on speedup if drafting time could be reduced to zero. Table 13 reports $\eta$ for Yi-34B/6B across all five datasets:
- HumanEval: Ouroboros 13.12, Speculative 11.16, Lookahead 3.08
- MBPP: Ouroboros 7.43, Speculative 6.14, Lookahead 2.71
- GSM8K: Speculative 5.23, Ouroboros 4.65, Lookahead 2.30
- CNN/DM: Ouroboros 7.46, Speculative 4.71, Lookahead 1.70
- WMT16: Ouroboros 4.05, Speculative 2.41, Lookahead 1.37

Ouroboros achieves the highest block efficiency on 3 of 5 tasks (HumanEval, MBPP, CNN/DM), with speculative decoding taking the lead on GSM8K and Ouroboros leading on WMT16. The "method with largest $\eta$ is highlighted with the bold font, and the second largest result is with the underlined font." The variation is informative: on GSM8K, speculative decoding's higher block efficiency (5.23 vs. Ouroboros's 4.65) suggests that on arithmetic reasoning, the phrase-pool extensions are less effective relative to straightforward token-level drafting — possibly because math generation requires precise symbolic sequences that don't match well with phrase-pool entries. On CNN/DM, Ouroboros's lead (7.46 vs. 4.71) is largest, suggesting summarization's relatively formulaic language benefits most from the phrase approach.

This metric matters because it represents the headroom for further improvement. Ouroboros achieves 13.12 tokens per target-model forward on HumanEval but only 61.2 token/s in wall-clock measurement. The gap between $\eta$ and realized speedup reflects drafting time, memory bandwidth limitations, and implementation overhead. The paper notes that block efficiency "shows that [Ouroboros] has a larger ideal speedup ratio that may be achieved by future algorithms or systematic implementation" (Appendix C).

**Comparison against Cascade Speculative Decoding (Appendix D, Table 14):** The paper compares Ouroboros against Cascade Speculative Decoding (Chen et al., 2023b), which accelerates the draft model by introducing an even smaller (third) model to draft for it — a two-level speculative hierarchy (160M→7B→70B or 1.1B→7B→70B). On GSM8K with Llama-2-70B/7B, Cascade configurations achieve 7.90 token/s (160M→7B→70B) and 9.22 token/s (1.1B→7B→70B), compared to 16.86 token/s for standard speculative decoding (7B→70B) and 24.03 token/s for Ouroboros (7B→70B). Cascade actually performs **worse** than standard speculative decoding — adding the third model slows things down. The paper attributes this to model mismatch: the tiny draft models (Llama-160M, TinyLlama-1.1B) "are not officially trained by Meta. This has led to discrepancies in the model's output, thereby slowing down the drafting process." This negative result validates Ouroboros's approach: accelerating the draft model through parallelism (Jacobi iteration) rather than through hierarchical speculative chains avoids the model-alignment problems that plague multi-level drafting.

### Critical Assessment

The experimental evaluation demonstrates that Ouroboros provides substantial speedups over speculative decoding (up to 2.8×) and over vanilla decoding (up to 3.9×) across a range of model pairs and tasks. The losslessness claim is well-verified. However, several aspects of the experimental design limit the generality and precision of the claims, and some claims are narrower than they first appear.

**Claim: "Ouroboros can achieve speedups of up to 2.8× over speculative decoding and 3.9× over vanilla decoding."** This is supported at specific data points (HumanEval, Yi-34B/6B, greedy decoding: 61.2 vs. 21.5 token/s for speculative, 61.2 vs. 15.6 for vanilla). But the "up to" framing masks enormous variance: on WMT16 with Yi-34B/6B, the speedup over vanilla is only 1.35× (19.94 vs. 14.78 token/s, Table 2) — barely a third of the headline number. On CNN/DM with the same model pair, it's 1.55×. The paper's own results show that the benefit is highly task-dependent, with code generation enjoying dramatically larger gains than machine translation or summarization. This is not a flaw — the paper doesn't hide the task-dependent results — but the abstract's "up to 2.8×" without qualification creates a misleading expectation. A fairer summary would be "speedups ranging from 1.14× to 2.8× over speculative decoding depending on task and model pair."

The dependence on task is not well-explained. The paper introduces the HH/LH (high homogeneity / low homogeneity) distinction in the hyperparameter recipe (Appendix B.1) but doesn't systematically analyze whether the speedup magnitude correlates with draft-target model alignment. A quantitative measure of "homogeneity" (e.g., draft-target token agreement rate, or KL divergence between their output distributions) and its correlation with Ouroboros speedup across tasks would have strengthened the analysis significantly. Without this, the practitioner cannot predict whether Ouroboros will help on their specific task without running the experiment.

**Claim: "Ouroboros is entirely training-free."** This is true and well-demonstrated. The models used are off-the-shelf; no fine-tuning, distillation, or architectural modification is applied. However, "training-free" does not mean "cost-free to deploy." The paper does not account for the memory overhead of the phrase pool or the tree-attention verification, both of which consume GPU memory beyond what speculative decoding requires. The phrase pool grows over time, storing potentially thousands of token sequences. While memory overhead likely doesn't dominate compared to model weights (a 7B model in FP16 occupies ~14GB; phrase pools storing a few thousand 7-token sequences occupy megabytes), the paper provides no memory measurements. For memory-constrained deployments, this could be a practical concern.

**Claim: "Ouroboros does not affect the generation quality at all" (Section 6).** Appendix A shows that task performance metrics are nearly identical across methods, which is strong evidence for losslessness. However, the verification is limited to final-answer accuracy/ROUGE/BLEU metrics on short-form tasks. The paper does not examine whether the *distribution* of outputs changes under Ouroboros (e.g., does the model become more repetitive, does diversity decrease, does the output become more or less verbose?). Since Ouroboros's phrase-pool mechanism preferentially extends drafts using phrases that have been accepted before, there is a theoretical risk of increasing repetition or reducing lexical diversity — this is not tested. For deployment in creative generation tasks where diversity matters, this is a relevant concern.

**Missing baseline: Ouroboros without the draft model (pure retrieval→target).** The paper compares against PLD and REST (Table 6) as baselines for "retrieval without draft model," but these methods retrieve phrases from external sources (prompts, documents). A cleaner ablation would be: what is the speed of Ouroboros's phrase-pool mechanism when phrases are fed directly to the target model, bypassing the draft model? This would isolate the contribution of the draft-model filter, quantifying how much speedup comes from the phrase quality improvement vs. simply having more candidate tokens to verify. The comparison with PLD/REST suggests the answer (poor speed without draft model), but those methods use different phrase sources, so the comparison is confounded.

**Limited hyperparameter search scope.** The grid search in Table 10 covers a narrow hyperparameter range ($\gamma$: 3–5, $W$: 14–16, $\beta$: 5–7) and concludes Ouroboros is "stable." But this range was presumably chosen because the authors already knew it works well. A true sensitivity analysis would test wider ranges (e.g., $\gamma = [1, 20]$, $\beta = [1, 15]$) to identify where performance degrades. The heuristic tuning algorithm (Algorithm 1) samples from these same narrow ranges and then greedily optimizes — but the greedy optimization is performed on the test set itself (since clock time is minimized on the target dataset). This means the reported speeds may be slightly overfit to the test data. A proper validation split for hyperparameter selection would have been more rigorous.

**The Spec-Bench comparison with EAGLE (Table 5) needs context.** EAGLE achieves 24.96 token/s vs. Ouroboros's 21.51 token/s on average — a 16% advantage for the training-based method. The paper frames this as "the speed slightly faster than our training-free method," which is technically accurate but downplays that EAGLE wins on throughput. The paper's counterargument is higher acceptance rate (4.96 vs. 3.48), which would translate to higher throughput if the draft model's forward passes were cheaper. But in the measured wall-clock times, EAGLE's smaller draft model wins. This is a legitimate tradeoff (speed vs. acceptance rate), but the paper's claim that Ouroboros "match[es] training-based methods" (Section 4.4 framing) is imprecise — it matches in some metrics, loses in throughput, and wins in acceptance rate. A more precise claim would be "achieves competitive throughput (within 16%) while accepting 42% more tokens per iteration, without training."

**The paper does not compare against the simplest combined baseline.** The most natural baseline for Ouroboros is: speculative decoding + Jacobi iteration applied to the draft model, without any of the phrase-pool mechanisms (no lengthening, no salvage, no reuse). This baseline is partially captured by the first ablation row in Table 4 ("+ Accelerating drafting via phrases" at 49.90 token/s), but that row might include some phrase-pool usage (the paper doesn't specify whether phrases from Jacobi iteration are used for extension in this row or only for the base draft). Clarifying exactly what the "accelerating drafting only" configuration entails would help isolate the contribution of each mechanism.

**Single GPU configuration.** All experiments use 2 × NVIDIA A800 80GB GPUs with NVLINK × 8. While this is a standard high-end setup, the speed measurements are hardware-specific. The paper does not provide enough detail to estimate how the speedups would transfer to other hardware configurations (e.g., single-GPU consumer cards, cloud instances with different interconnects, CPUs). The memory-bound nature of inference means that hardware bandwidth limitations strongly affect the absolute speeds and potentially the relative speedups between methods. A sensitivity analysis across hardware configurations would have strengthened the practical deployment claims.

**The paper's core conceptual claim — that the draft model as intermediary filter is the key insight — is supported by the comparison with PLD/REST (Table 6) but not tested with a within-method ablation.** The ideal experiment would be: take Ouroboros's phrase pool, feed those same phrases directly to the target model for verification (bypassing the draft model's filtering step), and measure the speed. If the speed drops substantially, the draft-model filter is indeed essential. If it doesn't drop much, then the phrase quality is high enough that the filter isn't adding much value, and the architectural claim is weaker. This experiment is not in the paper, so the strength of the "draft model as intermediary" claim rests primarily on the PLD/REST comparison, which is confounded by different phrase sources.

Overall, the experiments convincingly demonstrate that Ouroboros provides substantial, training-free speedups over speculative decoding in the tested settings, with strong evidence for losslessness. The main empirical weaknesses are the absence of a cleaned within-method ablation for the draft-model filter claim, the lack of output diversity analysis, the narrow hyperparameter sensitivity testing, and the hardware-dependence of the wall-clock measurements. The speedups on natural language tasks are substantially smaller than on code generation, which limits the generality of the headline numbers but not the validity of the approach.

## 6. Limitations and Trade-offs

### The Difficulty Estimation Cost Is Not Included in Reported Speedups

**The assumption or constraint.** The phrase-pool mechanisms — particularly draft lengthening via phrases and phrase generation from verification — depend on having a populated phrase pool from which to retrieve candidate continuations. In a cold-start scenario (the first query of a session), the phrase pool is empty, and Ouroboros must rely solely on phrase-parallel drafting to populate it. The paper's headline speedup numbers include the steady-state performance after the pool is populated but do not amortize the cost of building the pool from scratch.

The paper does not provide cold-start vs. steady-state speed comparisons. The ablation in Table 4 shows that phrase-parallel drafting alone (without pool mechanisms) achieves 49.90 token/s, while the full stack achieves 61.20 token/s — a 23% gap that reflects what the first query of a session might experience before the pool accumulates useful phrases. But this ablation doesn't measure the transient: how many queries does it take to reach the steady-state 61.20 token/s? Is it 2 queries? 10? 50? For short sessions (e.g., single-turn code completions), the pool may never reach steady state, and the effective speedup would be closer to the phrase-parallel-only number.

**The consequence.** In deployments with short sessions or infrequent queries, the amortized benefit of the phrase-pool mechanisms may be substantially lower than the headline speedups suggest. A code completion API that receives isolated, uncorrelated requests would not benefit from phrase reuse or from pool accumulation — each request would effectively be a cold start. The paper's "reusing phrases from history contexts" mechanism (Section 3.4) assumes session persistence across queries, which is reasonable for multi-turn chat but not for stateless API deployments. For such deployments, the achievable speedup is bounded by the "accelerating + lengthening" ablation row in Table 4 (55.92 token/s, corresponding to ~2.6× over speculative decoding rather than ~2.85×), and even the lengthening benefit depends on the pool being seeded by earlier queries within the same session.

Furthermore, the phrase generation from verification mechanism (Section 3.3) only produces salvageable phrases when drafts are partially rejected — but partial rejection is itself a sign of draft-target mismatch. On tasks where the draft model closely matches the target (high homogeneity), drafts are accepted fully, producing fewer salvage opportunities. On tasks with low homogeneity, drafts are rejected more often, producing more salvage opportunities but also lower base acceptance rates. The net effect of this tradeoff on the total speedup is not characterized.

**What evidence exists in the paper.** Table 17 (Appendix F) provides indirect evidence: with phrase reusing turned **off**, the speed is ~32.6 token/s regardless of domain ordering. Turning reusing **on** provides an additional ~3 token/s (to ~35.4–36.0 token/s) across all orderings, including shuffled (cross-domain) configurations. But this experiment already starts with a warmed-up pool from previous examples in the same evaluation run — it does not measure the first-query speed. The paper acknowledges this limitation only indirectly, by noting that phrase reuse helps "even in the shuffle setting" and that the pool is "effective across multiple tasks" (Appendix F), but does not quantify the cold-start penalty.

**Mitigation status.** Not addressed. The paper does not discuss cold-start performance, does not provide warm-up curves showing speed as a function of queries processed, and does not amortize the phrase-pool construction cost over session length in the reported speedup numbers. The phrase reuse from history contexts mechanism (Section 3.4) is described as a benefit for multi-query sessions, but the cost of initially filling the pool is not accounted for. A practitioner evaluating Ouroboros for a deployment with short sessions has no data to estimate the effective speedup they would experience.

---

### The Tree-Attention Verification Overhead Is Not Isolated or Characterized

**The assumption or constraint.** The draft lengthening mechanism (Section 3.2) verifies $K$ extended drafts in a single target-model forward pass using a custom tree-structured attention mask (Figure 3). The paper treats this verification as having roughly the same cost as verifying a single draft of length $\gamma + \beta$, citing the memory-bound nature of Transformer inference (Leviathan et al., 2023) as justification that "the time it takes for the target model to verify dozens of tokens using a single forward is not much different from the time spent on verifying a single token" (Section 3.2). However, the tree-attention mask introduces additional computation beyond a simple batched forward pass: the $K$ branches multiply the number of tokens that must be processed in the attention mechanism (the effective sequence length grows by $K \times \beta$ in the branching region), and the custom masking pattern may interact with GPU memory access patterns in ways that are not captured by the standard memory-boundness argument.

**The consequence.** If the tree-attention verification cost is larger than assumed, the optimal $K$ might be different than the experimentally determined $K = 3$, and the speedup attributed to draft lengthening might be overstated. More importantly, the cost scales with both $K$ (number of branches) and $\beta$ (phrase length), creating a tradeoff that is only partially explored. Figure 6 sweeps $K$ and shows a speed optimum around $K = 3$, with degradation at $K = 9$ attributed to "increased tree-attention overhead." But the paper does not decompose this overhead into its components: how much is from increased memory access (loading more KV cache entries), how much is from increased computation (more attention dot products), and how much is from implementation inefficiency in the custom masking code. Without this decomposition, it is unclear whether the $K=3$ optimum is fundamental (a physical limit from GPU memory bandwidth) or an artifact of the current implementation (which could be optimized to support larger $K$ effectively).

Furthermore, the tree-attention mechanism assumes that all $K$ branches can share the KV cache for the common prefix $d_{1 \ldots \gamma}$. In practice, sharing KV cache entries across diverging branches may require careful memory management to avoid redundant storage or cache invalidation. The paper does not discuss the memory overhead of maintaining $K$ parallel branches in the KV cache, which grows linearly with $K$ and $\beta$ in the branching region. For long base drafts ($\gamma$ large) with short phrases ($\beta$ small), this overhead is negligible. But for configurations with large $\beta$, the branch tokens may dominate the total KV cache size, and the tree-attention forward pass may become meaningfully slower than a single-draft forward pass of the same total token count.

**What evidence exists in the paper.** Figure 6 provides the primary evidence: speed as a function of $K$ on HumanEval with Yi-34B/6B (without phrase reuse). The curve shows a clear optimum, confirming that verification overhead exists and matters. However, the ablation does not separate the effect of $K$ on draft acceptance probability (more branches → higher chance of finding an accepted extension) from the effect on verification cost (more branches → longer target-model forward pass). The shape of the curve (rising then falling) is consistent with both effects operating, but their relative magnitudes are unknown. The paper's block efficiency analysis (Table 13) provides an upper bound on speedup if verification and drafting costs were zero, but does not isolate the tree-attention overhead specifically.

**Mitigation status.** Partial. The paper acknowledges that "verifying too many phrases might slow down the verification in real-model inference scenarios" and identifies $K$ as a hyperparameter to tune (Section 4.3, Figure 6). However, the tuning is empirical and does not provide a model for predicting the optimal $K$ on a new task or hardware configuration without running the sweep. The paper's heuristic tuning recipe (Appendix B.1) fixes $K = 3$ as a universal default, which may be suboptimal on hardware with different memory bandwidth characteristics or on tasks where the phrase pool contains higher-quality candidates (making larger $K$ more beneficial).

### Speedups Vary Dramatically Across Tasks and Model Pairs, and the Source of This Variance Is Not Diagnosed

**The assumption or constraint.** The paper reports speedups at two extremes: a maximum of 3.9× over vanilla decoding on HumanEval with Yi-34B/6B (Figure 5) and a minimum of 1.35× on WMT16 with the same model pair (Table 2). This is a 2.9× range in effectiveness (3.9 / 1.35) for the same method on the same hardware with the same models, varying only the task. The paper introduces a heuristic distinction between "HH" (High Homogeneity) and "LH" (Low Homogeneity) tasks in the hyperparameter tuning recipe (Appendix B.1), where HH tasks (e.g., code generation) are those with high draft-target agreement and LH tasks (e.g., machine translation) have low agreement. But this distinction is used only to set the hyperparameter $\gamma$ (base draft length) — the paper does not analyze whether the HH/LH distinction explains the variance in speedup magnitude, and it provides no quantitative measure of homogeneity (such as token-level agreement rate between draft and target model outputs, or KL divergence) that could be used to predict speedup on a new task.

**The consequence.** A practitioner considering Ouroboros for their task cannot predict, without running the experiment, whether they will get the 1.35× speedup (which may not justify the implementation complexity) or the 3.9× speedup (which definitely does). The paper's results show that code generation benefits dramatically more than machine translation or summarization, but it does not explain **why** in terms that would generalize. Is it because code has more repetitive syntactic structures that benefit the phrase pool? Is it because the Yi-34B/6B pair has higher agreement on code than on translation? Is it because code generation produces longer sequences, giving the phrase pool more time to accumulate useful entries? Without diagnostic analysis, the speedup on a new task is essentially unpredictable.

The cross-model variance is equally striking. On HumanEval, Yi-34B/6B achieves 61.2 token/s, while DeepSeek-coder-33b/6.7B achieves only 41.0 token/s under Ouroboros — a 50% difference despite similar model sizes and the same task. Yet the paper provides no analysis of why. Differences in Jacobi iteration convergence speed, phrase acceptance rates, or draft-target alignment could all contribute, but none are measured.

**What evidence exists in the paper.** The speedup variance is clearly visible in the paper's own tables: Table 2 shows Yi-34B/6B speedups of 1.84× (GSM8K), 1.55× (CNN/DM), and 1.35× (WMT16); Figure 5 shows code generation speedups of 2.1–3.9× depending on model pair. The paper's hyperparameter recipe (Table 11) acknowledges that different tasks need different $\gamma$ values (larger for HH, smaller for LH), which is a partial acknowledgment that task characteristics matter. But the recipe is post-hoc: you need to know whether your task is HH or LH to set $\gamma$, and the paper provides no procedure for determining this beyond "code generation = HH, machine translation = LH" — a classification that doesn't extend to novel domains.

**Mitigation status.** Not addressed. The paper does not compute any draft-target agreement metric, does not correlate such a metric with observed speedup, and does not provide a model for predicting speedup on a new task. The HH/LH classification remains a rough heuristic with no quantitative grounding. Section 8 (future work) does not mention this as a direction, implying the authors may consider the task-dependence obvious or expected rather than a limitation requiring diagnosis.

### Speedup Measurements Are Hardware-Specific and Not Portable

**The assumption or constraint.** All speedup numbers are reported as wall-clock token/s on a specific hardware configuration: 2 × NVIDIA 80GB A800 GPUs with NVLINK × 8 interconnect and an Intel Xeon Platinum 8350C CPU (Section 4.1). This is a high-end server-grade setup with fast inter-GPU communication (NVLINK) that enables efficient tensor parallelism for the large target models. The paper does not test on other hardware configurations — single-GPU setups, consumer-grade GPUs (e.g., RTX 4090 with 24GB VRAM), cloud instances with slower interconnects, or CPU-only inference.

The memory-bound nature of Transformer inference means that hardware memory bandwidth is the primary determinant of absolute decoding speed, and the relative speedup between methods can change when the bottleneck shifts. For example, on a single-GPU setup with limited memory bandwidth, the draft model and target model compete more directly for memory access resources, potentially changing the ratio $t_T / t_S$ that governs the speculative decoding speedup equation. Ouroboros's tree-attention verification — which processes $K$ branches simultaneously — may be relatively more expensive on hardware with less parallel memory bandwidth, because the additional KV cache entries for the branches increase contention for the same memory channels.

**The consequence.** Practitioners cannot directly apply the paper's speedup numbers to their own hardware. A deployment on a single RTX 4090 or an A100 with different memory bandwidth characteristics will experience different absolute speeds and potentially different relative speedups between Ouroboros and baselines. The optimal hyperparameters ($K$, $\gamma$, $W$, $\beta$) may also shift: if the tree-attention overhead is proportionally larger on lower-bandwidth hardware, the optimal $K$ might be smaller, and the draft lengthening mechanism might contribute less to the total speedup.

The paper's reliance on a 2-GPU setup with NVLINK also means that the target model (e.g., Llama-2-chat-70B at ~140GB in FP16) is likely split across GPUs using tensor parallelism. The inter-GPU communication via NVLINK is fast, but if a practitioner uses a different parallelism strategy (pipeline parallelism, or a single larger GPU like an H100 with 80GB), the time-per-forward-pass $t_T$ changes, altering the $t_S / t_T$ ratio that governs the speedup equation. The paper provides no scaling analysis with respect to hardware parameters.

**What evidence exists in the paper.** The paper reports hardware specifications in Section 4.1 and provides block efficiency analysis (Appendix C, Table 13) as a hardware-independent metric. Block efficiency represents the theoretical maximum speedup if all drafting and memory-access overhead were eliminated, which is intended as a portable upper bound. On HumanEval with Yi-34B/6B, Ouroboros achieves block efficiency of 13.12 tokens per target-model forward, compared to an actual speed of 61.2 token/s. The gap between these numbers reflects drafting cost and hardware limitations, but the paper does not decompose this gap to identify which portions are hardware-specific vs. algorithm-inherent.

The paper also notes in Section 5.2 (Related Work) that efficient implementation methods (FlashDecoding, PageAttention, Tensor Parallelism) and Ouroboros are "orthogonal" and "combining efficient implementation methods and Ouroboros can achieve more significant inference acceleration." This statement acknowledges that implementation quality matters, but it does not provide evidence that Ouroboros's relative advantage over baselines is preserved under different implementation choices.

**Mitigation status.** Partial. The block efficiency metric provides a hardware-independent theoretical upper bound, but it does not help a practitioner estimate the realized speedup on their specific hardware. The paper does not test on multiple hardware configurations, does not provide a performance model that parameterizes speedup as a function of memory bandwidth or GPU count, and does not discuss how the optimal hyperparameters might shift with hardware. The hyperparameter tuning recipe (Algorithm 1) operates by minimizing clock time on the target hardware, which implicitly adapts to hardware characteristics, but only for the hardware the practitioner is using — they must run their own sweep to find good values.

### The Paper Does Not Evaluate Output Diversity or Repetition Risk

**The assumption or constraint.** Ouroboros's phrase-pool mechanisms — particularly the reuse of phrases from history contexts (Section 3.4) and the salvage of matching sub-segments from verification (Section 3.3) — create a positive feedback loop: phrases that are accepted by the target model are stored in the pool, and phrases in the pool are more likely to be used in future drafts, which makes them more likely to be accepted again. Over a long session, this could bias the model's output distribution toward frequently occurring phrases in the pool, reducing lexical diversity and potentially increasing repetition.

The paper verifies losslessness (Appendix A) using task performance metrics (accuracy, ROUGE, BLEU), which measure correctness against a reference output. These metrics do not capture diversity — a model that repeatedly generates the same correct answer to a math problem would score 100% on accuracy but 0% on any diversity metric. For tasks where diversity matters (creative writing, dialogue, open-ended generation), a reduction in output diversity could be a significant quality degradation, even if task performance metrics are unchanged.

**The consequence.** In deployment scenarios requiring diverse outputs — such as a chatbot that should not repeat phrases verbatim across turns, or a creative writing assistant where variation is valued — Ouroboros's phrase-pool mechanisms might cause the model to become repetitive in ways that are invisible to the paper's evaluation. The paper's experiment on generation length limits (Appendix E, Tables 15–16) argues that "phrase repetition in the generation is not the reason why Ouroboros achieves such a high speedup" because task performance is preserved. But this only shows that Ouroboros isn't producing *meaningless* repetition (e.g., repeating the same token endlessly) — it doesn't rule out *meaningful* repetition (e.g., reusing the same phrasing for similar semantic content across multiple outputs). The distinction matters: a summarization model that always uses the phrase "the article discusses" to open its summaries is not "wrong" by ROUGE, but it is less useful than a model that varies its phrasing.

Furthermore, the phrase pool has no mechanism for forgetting or decaying old phrases. If a session spans a topic shift (e.g., a user switches from discussing sports to discussing politics), phrases from the sports domain remain in the pool and could be proposed as candidate continuations for the politics discussion. The paper's context locality experiment (Appendix F) suggests that cross-domain phrase reuse still provides speedup, but it doesn't test whether the reused phrases are *appropriate* or merely not-harmful-enough-to-degrade-task-metrics. A coding phrase proposing a `for` loop structure in the middle of a translation task might not cause a BLEU score drop (because the target model rejects it), but the computational effort of verifying and rejecting it is wasted — and this waste is hidden in the overall speedup measurement.

**What evidence exists in the paper.** The paper does not measure output diversity. No diversity metrics (e.g., distinct-n, self-BLEU, entropy of output distribution) are reported. The losslessness verification (Appendix A) covers only task performance. The generation length experiment (Appendix E) addresses a specific concern (phrase repetition causing speedup inflation) but does not address the broader diversity question. The paper's random sampling experiments (Table 3) use temperature 0.5 and 1.0 with top-p = 0.8, which should produce diverse outputs, but no diversity analysis is performed on these outputs to check whether Ouroboros reduces diversity relative to vanilla sampling at the same temperature.

The implicit assumption is that because Ouroboros is mathematically equivalent to speculative decoding in terms of the tokens accepted (Equation 9 preserves the target model's distribution), it cannot affect output diversity. But this equivalence holds only for the accepted tokens — the phrase-pool mechanisms determine *which* draft tokens are proposed to the target model in the first place. If the pool biases the draft toward certain phrasings that are then accepted by the target model, the output distribution shifts, even though each accepted token is still sampled from the target model's conditional distribution. The target model's conditional distribution $P_T(\cdot \mid \text{context})$ can assign high probability to "the article discusses" in a summarization context — so accepting that phrase doesn't violate losslessness — but if the phrase pool proposes that specific wording more often than the base draft model would, the effective output distribution changes.

**Mitigation status.** Not addressed. The paper does not measure diversity, does not discuss the risk of diversity reduction, and does not propose any mechanism for controlling or decaying the phrase pool to mitigate this risk (e.g., a maximum pool size, a recency-weighted selection policy, or a diversity-aware phrase sampling strategy). The paper's statement that "Ouroboros does not affect the generation quality at all" (Section 6, repeated in the abstract) is supported only by task performance metrics, not by diversity analysis. This is a significant gap for deployments where output diversity matters.

### Hard Problems Where the Draft Model Fails Produce Near-Zero Benefit from Phrase Mechanisms

**The assumption or constraint.** Ouroboros fundamentally depends on the draft model's ability to produce tokens and phrases that the target model will accept. When the draft model and target model diverge significantly — on tasks where the smaller model lacks the capability or knowledge to approximate the larger model's output — the phrase-pool mechanisms provide little additional benefit. The draft model produces low-quality drafts that are rejected early (small $A$), the phrase pool accumulates poor-quality entries from those rejected drafts (since salvaged sub-segments are themselves products of the weak draft model), and the phrase extension mechanism concatenates phrases that are unlikely to match the target model's verification output.

The paper partially acknowledges this dynamic through the HH/LH distinction in the hyperparameter recipe (Appendix B.1): "LH: Low homogeneity between draft and target model, e.g. machine translation." But it does not analyze the **failure regime** where homogeneity is so low that Ouroboros provides effectively no benefit over standard speculative decoding, or where the additional mechanisms (phrase pool, tree verification) add overhead without corresponding acceptance gains.

**The consequence.** Ouroboros is not a universal accelerator — its benefit is bounded by the quality of the draft model for the specific task. For practitioners using a draft model that already has low acceptance rates on their task (e.g., a general-purpose 7B model drafting for a code-specialized 70B model on a highly specialized programming language), Ouroboros's additional mechanisms may provide marginal or zero speedup, and the implementation complexity may not be justified. The paper's results on WMT16 with Yi-34B/6B (Table 2: only 1.35× speedup over vanilla, and lookahead decoding nearly matches speculative decoding at 17.98 vs. 17.48 token/s) suggest that machine translation is in or near this regime — the phrase-level mechanisms add only 1.11× over lookahead decoding and 1.14× over speculative decoding, which may not justify the additional system complexity.

More broadly, the paper's approach is fundamentally **amplificatory, not capability-creating**: it can make an already-decent draft model more efficient, but it cannot compensate for a fundamentally poor draft model. This is analogous to the finding in the example paper (on compute-optimal test-time scaling) that test-time compute cannot help on the hardest problems where the base model's pass@1 is near zero. Ouroboros inherits this limitation from speculative decoding — and the phrase mechanisms do not change it.

**What evidence exists in the paper.** The WMT16 results (Table 2) provide the clearest evidence of a low-benefit regime. With Yi-34B/6B on WMT16, Ouroboros achieves 19.94 token/s vs. speculative decoding's 17.48 token/s — only a 1.14× speedup. The gap between Ouroboros and lookahead decoding is even narrower (19.94 vs. 17.98, 1.11×). On Llama-2-chat-70B/7B, the WMT16 speedup is larger (19.27 vs. 14.72 for speculative, 1.31×), but still lower than on other tasks for the same model pair (e.g., 2.68× on GSM8K). This suggests that machine translation is a consistently lower-benefit task, consistent with the LH classification.

The paper does not report the component-level ablation (Table 4) on WMT16 or other LH tasks. If the phrase-pool mechanisms contributed 23% to the total speedup on HumanEval (49.90 → 61.20 token/s, the gap between phrase-parallel drafting alone and the full stack), but contributed only 5% on WMT16, that would directly quantify the diminishing returns. Without this data, the dependence of the phrase mechanisms' benefit on draft-target homogeneity is qualitatively observed but quantitatively uncharacterized.

**Mitigation status.** Partial. The paper provides the HH/LH hyperparameter tuning distinction (Table 11), which adjusts $\gamma$ to be smaller for LH tasks. This mitigates the cost of low-homogeneity drafting (by not investing in long base drafts that will be rejected), but it does not increase the benefit of the phrase-pool mechanisms on such tasks. The paper does not investigate whether alternative phrase sources (e.g., retrieval from reference corpora as in REST) could supplement the draft-model-generated pool on LH tasks, or whether training the draft model to better match the target on the specific task could improve Ouroboros's effectiveness. The paper's future work direction (Section 6) — "the training-based version of Ouroboros towards extreme acceleration" — could address this limitation, but the current training-free version provides no mechanism for improving draft-target alignment.
