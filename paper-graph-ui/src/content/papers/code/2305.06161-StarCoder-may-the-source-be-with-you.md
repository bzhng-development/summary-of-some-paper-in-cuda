# StarCoder: may the source be with you!

**ArXiv:** [2305.06161](https://arxiv.org/abs/2305.06161)

## 🎯 Pitch

This paper introduces **StarCoder** and **StarCoderBase**, a pair of 15.5B-parameter open-access Code LLMs developed by the BigCode community and trained exclusively on permissively licensed source code from The Stack dataset.

---

## 1. Executive Summary

This paper introduces **StarCoder** and **StarCoderBase**, a pair of 15.5B-parameter open-access Code LLMs developed by the BigCode community and trained exclusively on permissively licensed source code from The Stack dataset. The models combine three architectural mechanisms — an 8K-token context length (enabling conditioning on long files and repository-level code), Fill-in-the-Middle training (allowing code infilling conditioned on both prefix and suffix), and Multi-Query Attention (enabling fast large-batch inference) — and are trained on 1 trillion tokens across 80+ programming languages, with StarCoder further fine-tuned on 35B Python tokens. Across the most comprehensive evaluation of Code LLMs to date — spanning HumanEval, MBPP, DS-1000, ODEX, MultiPL-E across 19 languages, and security and infilling benchmarks — StarCoderBase outperforms every open-access multi-language Code LLM and matches or exceeds OpenAI's `code-cushman-001`, while StarCoder achieves 33.6% pass@1 on HumanEval (outperforming the ~12B-parameter `code-cushman-001` at 33.5%) and 52.7% on MBPP. The paper further introduces a **novel attribution tracing tool** that combines Bloom-filter-based membership checking with a BM25 search index, establishing that it is possible to detect and locate model generations copied from the training set — though this tool cannot distinguish generic boilerplate from protected content and requires a minimum context length to trigger a match.

## 2. Context and Motivation

### The Core Problem: Openness, Access, and Governance in Code LLMs Are Fundamentally Broken

The paper tackles a multidimensional crisis in the development of Large Language Models for Code (Code LLMs). The underlying issue is not a single technical gap but rather a confluence of **legal, ethical, scientific, and practical concerns** that collectively undermine the legitimacy and utility of Code LLMs as they are currently developed by major industry players. The BigCode community frames this explicitly in Section 1, listing copyright, privacy, and openness as the three central concerns that motivate the entire project.

**Copyright.** The legal landscape is unsettled and actively adversarial. Code LLMs are trained on vast quantities of publicly available source code — much of it hosted on GitHub under a patchwork of licenses. The question of whether training machine learning models on this data constitutes fair use (in the U.S.) or falls under other copyright exceptions (in the E.U.) has not been resolved by courts, but lawsuits have already been filed: *DOE 1 v. GitHub, Inc.* (2022) directly targets GitHub Copilot, and *Andersen et al. v. Stability AI et al.* (2023) pursues similar claims against Stable Diffusion. The paper cites Henderson et al. (2023)'s argument that LLM developers should provide tools to verify that model outputs do not infringe copyright, and observes that fair use is most likely to be upheld when the model generates "novel content dissimilar to any copyrighted training data." This creates a **direct technological requirement**: models trained on code must be accompanied by mechanisms that help users determine whether generated outputs are novel or memorized from the training corpus. This requirement becomes a major throughline of the paper, culminating in the attribution tracing tools described in Section 9.

**Privacy (PII).** The regulatory environment is equally active. The paper cites Italy's temporary ban of ChatGPT and the ongoing GDPR investigation into OpenAI (BBC, 2023). Under GDPR, organizations processing personal information must have a valid legal basis, must inform individuals how their data is processed, and must provide mechanisms for data access, rectification, and deletion. This creates an existential challenge for LLM developers: public code repositories inevitably contain personal information — names in license headers, emails in commit logs, API keys accidentally committed, usernames in issue discussions. The paper notes that "obtaining explicit consent from data creators is difficult at this scale," which means that developers must either find alternative legal bases (uncertain), or invest seriously in PII detection and redaction *before* training. This requirement motivates nearly the entirety of Section 4, which describes a substantial effort to collect PII annotations, train a dedicated detection model, and redact the training corpus.

**Openness and transparency.** The paper draws a sharp contrast between the prevailing mode of Code LLM development — closed-access models with hidden training data and opaque methodologies — and the principles of open science. It distinguishes between degrees of openness:

- **Closed-access models** (Chowdhery et al., 2022; Hoffmann et al., 2022) are entirely internal to the developing organization. Researchers cannot inspect, audit, or build upon them.
- **API-gated models** (Brown et al., 2020; OpenAI, 2023a) allow some experimentation but hide crucial details about training data and methodology, limiting research into safety (Perez et al., 2022), model internals (Olsson et al., 2022), and model improvement (Togelius and Yannakakis, 2023).
- Existing **open-access models** vary dramatically in their degree of transparency: some release weights but restrict distribution (Touvron et al., 2023; LLaMA's non-commercial license), some release weights but not training data (Nijkamp et al., 2023; Zhang et al., 2022; Fried et al., 2022), and some are permissively licensed but were developed without community input (Raffel et al., 2020; Tay et al., 2022).

The paper positions BigCode as a response to this landscape: a community-driven, open-scientific collaboration explicitly modeled on the BigScience workshop (which produced BLOOM; BigScience Workshop, 2022) and EleutherAI (which released GPT-NeoX, GPT-J, and Pythia along with training data; Black et al., 2022; Wang and Komatsuzaki, 2021; Biderman et al., 2023). The goal is not simply to release *another* open-access model, but to demonstrate that a model can be developed with **full transparency** — published training data, documented filtering and PII redaction pipelines, community governance, and opt-out mechanisms — while remaining competitive with the best closed-access alternatives.

### The Gap: No Open-Access Code LLM Combines Scale, Performance, and Responsible Data Governance

Prior to StarCoder, the landscape of Code LLMs was divided into two camps — **closed-access models with strong performance but zero transparency**, and **open-access models that were either too small, too opaque, or trained on insufficient data**. The paper systematically documents the limitations of earlier open-access Code LLMs:

**PolyCoder (Xu et al., 2022)** and **SantaCoder (Ben Allal et al., 2023)** are notable for releasing both models and training data. However, they are small: 2.7B and 1.1B parameters, respectively, trained on less than 300 GB of code. By contrast, the paper's models are 15.5B parameters and trained on approximately 800 GB of filtered code, representing a **~10× scale increase in both model size and data volume**. This scale gap matters because performance on code generation tasks has consistently been shown to improve with model size and training tokens (Kaplan et al., 2020; Hoffmann et al., 2022), and the paper explicitly aims to test whether responsible data practices can scale to models competitive with industry offerings.

**CodeGen-16B-Multi (Nijkamp et al., 2023)** and **CodeGen-16B-Mono** are open-access models at a scale comparable to StarCoder, but suffer from significant transparency gaps. CodeGen-Mono is fine-tuned on a proprietary Python dataset that is not publicly available, meaning researchers cannot inspect, replicate, or understand *why* the model's Python performance improves. The training data for the base CodeGen model (The Pile, plus additional BigQuery code) is partially available but includes code under restrictive licenses — the paper does not attempt to filter by license, which is precisely the governance gap BigCode aims to close.

**CodeGeeX-13B (Zheng et al., 2023)** is another open-access 13B-parameter model trained on 23 programming languages, but releases only model weights, not the full training dataset. This limits scientific reproducibility and external auditing.

**InCoder (Fried et al., 2022)** introduced Fill-in-the-Middle training and released the model, but the paper is released under a non-commercial license and high-level details about data collection remain limited.

**LLaMA (Touvron et al., 2023)** offers a family of open-access models (7B to 65B) with strong performance, but explicitly restricts use to non-commercial research in its license — a restriction that the StarCoder paper addresses by developing a "more commercially viable" Open Responsible AI Model License (OpenRAIL-M) that permits commercial use while embedding use restrictions in identified critical scenarios (Section 1).

The closed-access frontier is defined by **OpenAI's codex models**: `code-cushman-001` (~12B parameters), which served as the initial GitHub Copilot model (Chen et al., 2021), and `code-davinci-002` (~175B parameters). These models are available only through paid APIs, with no disclosure of training data composition or filtering methodology. Google's **PaLM** (540B; Chowdhery et al., 2022) and DeepMind's **Chinchilla** (Hoffmann et al., 2022) are even more restricted, available only within their respective organizations.

The gap, therefore, is not merely that no open-access model matched `code-cushman-001`'s performance — it's that **no open-access model simultaneously provided (1) competitive performance at a scale exceeding 1B parameters, (2) full transparency of the training data and its curation process, (3) permissive or commercially-viable licensing, (4) deliberately constructed PII redaction and data governance tooling, and (5) attribution mechanisms to support copyright compliance.** StarCoder aims to fill all five dimensions simultaneously.

### Prior Approaches to Data Governance and Their Shortcomings

The paper identifies specific deficiencies in how prior projects handled the governance dimensions of large-scale code data:

**License filtering.** Most prior Code LLMs either ignored license filtering entirely (training on all available code regardless of license) or applied it in a non-transparent way. The Stack (Kocetkov et al., 2022), in contrast, built an explicit license detection pipeline that classifies repositories by license type and restricts the training set to permissively licensed code — but this approach has known limitations, including misclassification of licenses and the challenge of handling code that is duplicated across repositories with different licenses.

**Opt-out mechanisms.** Prior to BigCode's work, no major Code LLM project provided a systematic mechanism for developers to check whether their code was included in the training data or to request its removal. The Stack includes an "Am I in The Stack" tool and an opt-out process (44 people opted out by the time of data processing), but the paper acknowledges (Section 10.2) that opt-out at the repository level is insufficient when code can be duplicated across repositories. This is a fundamental unsolved problem in data governance for web-scale training data.

**PII redaction.** Prior Code LLM projects applied varying levels of PII filtering, but none published a detailed methodology with annotations, model training, and performance evaluation. The closest prior work is Ben Allal et al. (2023), which used regular expressions for PII detection — an approach that the paper demonstrates (Table 8) achieves reasonable performance on emails (96.83% F1) but catastrophically poor precision on keys (3.62%) and modest recall on IP addresses (87.71%). The regex approach fundamentally cannot scale to the diversity of ways PII appears in source code (names in comments, usernames in paths, keys embedded in configuration files), which motivates the paper's substantial investment in a trained NER model.

**Attribution at generation time.** Perhaps the most novel governance gap addressed is **post-generation attribution**: when a Code LLM produces code, how can users determine whether that code was memorized from the training set? The paper identifies this as a direct requirement for copyright compliance (the fair use argument is strengthened when the model generates novel content), but prior work provides no tooling for this purpose at model deployment time. The Bloom-filter membership checker and BM25 search index described in Section 9 are, to the paper's knowledge, the first integrated tools of their kind released alongside a production-scale Code LLM.

### How This Paper Positions Itself: Transparent Development as a Competitive Baseline

The paper's positioning is distinctive: rather than positioning StarCoder as primarily a *technical* advance over prior Code LLMs, it frames the project as a **demonstration that transparent, community-driven, and legally-conscious development practices can produce models that are competitive with the best closed-access alternatives**. The evaluation in Section 6 is the mechanism for this demonstration — by showing that StarCoder matches or outperforms `code-cushman-001` (a model developed by one of the world's best-resourced AI labs with no transparency constraints), the paper makes the case that **"responsible development" is not inherently in tension with "strong performance."**

This positioning is reinforced by several structural choices:

- **Community governance.** The project is "co-stewarded by two industry research labs" (ServiceNow Research and Hugging Face) but comprises "more than 600 members from diverse academic institutes and industry labs." The paper emphasizes that the Legal, Ethics, Governance Working Group held decision-making authority that sometimes overrode research interests (Section 10.1 notes the decision to remove and not release a dataset of identified malicious code, even though it might be useful for security research).

- **Licensing pragmatism.** Rather than adopting a standard open-source license (which might not address AI-specific risks) or a fully permissive license (which would enable unrestricted use), the paper develops a version of the OpenRAIL-M license that is "more commercially viable for companies wishing to use and distribute the model" while still embedding use restrictions — including prohibitions on generating malware, disseminating PII with intent to harm, and other "critical scenarios." This represents a middle path between the fully closed (OpenAI) and the fully unrestricted.

- **Tooling as a signal.** The decision to release attribution tracing tools alongside the model is not just practical — it is **rhetorical**. The paper is arguing that model developers have a responsibility to provide mechanisms for downstream users to assess copyright risk, and that releasing such tools should be a standard part of model releases, not an afterthought. This is a normative claim about what responsible development entails, and the paper demonstrates it by precedent rather than by argument alone.

- **Scale as a credibility condition.** The 15.5B parameter scale matters because it prevents a convenient dismissal: "transparent development is fine for toy models, but real systems need the scale of proprietary data." By reaching a scale where the model is competitive with `code-cushman-001` (~12B parameters, the original Copilot model), the paper preempts this objection. The model is not the largest possible Code LLM (it is far smaller than the 540B PaLM or even the 175B `code-davinci-002`), but it crosses a threshold where the performance is practically useful, making the governance claims meaningful.

In summary, the paper addresses a gap that spans **law** (copyright, GDPR), **science** (reproducibility, auditability), and **practice** (the need for tools that make code generation safe and compliant). It positions StarCoder as a demonstration that these concerns can be addressed systematically without sacrificing performance, and argues — implicitly but forcefully — that the field should treat such practices as the baseline for responsible development, not as optional extras.

## 3. Technical Approach

### 3.1 Reader Orientation

This paper describes the **end-to-end pipeline for building StarCoderBase and StarCoder** — a pair of 15.5B-parameter Code LLMs trained entirely on permissively-licensed GitHub source code — spanning data curation, PII redaction via a custom NER model, architectural design with Fill-in-the-Middle and Multi-Query Attention, and large-scale distributed training on 1 trillion tokens. The core problem this system solves is: **how do you train a Code LLM that is simultaneously competitive with closed-access models like `code-cushman-001` in code generation performance, transparent in every component of its development (data provenance, filtering decisions, PII redaction methodology), and legally compliant enough to be released under a commercially-viable license?** The solution takes the shape of a carefully staged pipeline where each stage (data selection, heuristic filtering, language-specific cleaning, deduplication, PII detection and masking, decontamination against evaluation benchmarks, and finally model training with Fill-in-the-Middle transformations and sentinel-token-based formatting) is documented, evaluated, and — critically — designed to be reproducible by external researchers using the same publicly-available data source.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has **five major stages**, each producing an intermediate artifact consumed by the next:

1. **Data Source Selection (Section 3):** The Stack v1.2 — a 6.4 TB collection of permissively-licensed GitHub repositories — serves as the universe of admissible data. From its 358 programming languages, 86 are selected based on data volume thresholds (≥500 MB) and popularity indices (top 50 on Githut 2.0 or December 2022 TIOBE Index). Additional data types are included: GitHub issues (54 GB), Git commits (sampled to 64 GB), and Jupyter notebooks (converted to scripts and structured text-code pairs). Data formats like JSON, YAML, and CSS are heavily down-sampled (re-weighed to 1–3 GB) to teach the format without memorising data.

2. **Heuristic Filtering Stage (Section 3.1–3.4):** A multi-layer pipeline of language-specific and cross-language filters removes low-quality, auto-generated, or data-heavy files. This includes XML detection, alphanumeric ratio filters (≥25% alphabetic characters), HTML boilerplate removal (visible text must be ≥20% of HTML and ≥100 characters), JSON/YAML size and structure filters, and Git-commit-specific filters (removing empty messages, bot commits, hash-heavy diffs). The outcome is a reduction from ~816 GB (after dedup) to ~799 GB of filtered data.

3. **PII Redaction Stage (Section 4):** A custom Named Entity Recognition (NER) model — StarEncoder fine-tuned on 12,000 manually-annotated files — detects six PII types (names, emails, keys, passwords, IP addresses, usernames) across all programming languages, GitHub issues, Git commits, and Jupyter notebooks. Detected entities are replaced with sentinel tokens (`<NAME>`, `<EMAIL>`, `<KEY>`, `<PASSWORD>`) or synthetic IP addresses. This stage required 800 GPU-hours of inference and is the paper's primary mechanism for GDPR compliance.

4. **Data Formatting and Decontamination (Section 5.1–5.2):** Each data source (code files, GitHub issues, Jupyter notebooks, Git commits) is wrapped in a structured template with sentinel tokens that encode metadata (repository name, filename, stars bucket, issue participants, etc.) and task structure. Code files undergo Fill-in-the-Middle (FIM) transformations at a 50% rate, randomly split between PSM and SPMv2 modes. The entire training set is then decontaminated: files containing docstrings, solutions, or prompts from HumanEval, MBPP, APPS, GSM8K, and DS-1000 are removed (558 Python files removed, the largest number for any language).

5. **Model Training Stage (Section 5.3–5.6):** A 15.5B-parameter decoder-only Transformer with Multi-Query Attention and 8K context length is trained on the formatted data for 250K iterations (1 trillion tokens) using a 3D-parallel setup across 512 A100 GPUs. StarCoder is then produced by fine-tuning StarCoderBase on 35B Python tokens for 2 epochs. The trained model supports both left-to-right completion and Fill-in-the-Middle infilling at inference time.

**Information flow:** The Stack v1.2 → language selection and license filtering → per-language heuristic cleaning → near-deduplication (MinHash + LSH, Jaccard 0.7, 5-grams) → PII detection and masking → template formatting with sentinel tokens → FIM transformation → decontamination → tokenization (BPE, 49,152 vocab) → distributed training → StarCoderBase → Python fine-tuning → StarCoder.

### 3.3 Roadmap for the Deep Dive

- **First, the data selection and language inclusion criteria (Section 3.1):** I explain *which* 86 languages were selected, *why* from 358, and what the decision process reveals about balancing data volume, user demand, and community input. ### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems and engineering paper** whose core technical idea is that combining (a) exhaustive, transparent, and language-specific data curation, (b) a custom-trained PII detection model for privacy compliance, and (c) Fill-in-the-Middle training at scale with Multi-Query Attention produces a Code LLM that is competitive with closed-access models while being fully auditable. The technical contribution is in the **pipeline integration** and **engineering decisions** at each stage — no single component is novel in isolation, but the combination, documentation, and release constitute the advance.

---

#### Language Selection and Data Volume Decisions

The Stack v1.2 contains source code in 358 programming languages identified by file extension (Kocetkov et al., 2022). Not all of these languages contain enough data to contribute meaningfully to training, and some are configuration formats or inactive languages that would waste compute budget. The paper applies **three inclusion criteria** (Section 3.1):

1. **Volume threshold:** Any language with more than 500 MB of data after deduplication is automatically included. This is a purely data-driven criterion that ensures the model has enough examples to learn the syntax and idioms of the language.

2. **Popularity indices:** Languages ranked in the top 50 on either **Githut 2.0** (which measures GitHub activity) or the **December 2022 TIOBE Index** (which measures search engine and developer community engagement) are included even if they fall below the 500 MB threshold. This criterion captures languages that are important to developers but may have less public open-source code (e.g., proprietary languages with smaller open-source footprints, or languages where development happens primarily outside GitHub).

3. **Dialect inclusion:** Dialects of already-selected languages are included to provide syntactic context. The paper gives the example of Racket and Scheme for Lisp.

**Explicit exclusions.** Configuration languages (Nix, Puppet, etc.) and languages "no longer actively supported" (ActionScript) are excluded because they do not represent programming tasks the model is intended to perform. The authors note that "out of the languages present in MultiPL-E, only D and Swift were not included in the training set." For D, language misclassification of files in The Stack resulted in less than 2 MB of data — too little to train on. For Swift, the exclusion is attributed to "human error" — the language was accidentally left off the final list.

The paper makes a deliberate and non-obvious choice: to **follow the natural distribution of data** rather than up-sample or down-sample programming languages. The rationale is explicit (Section 3.6):

> "the largest amount of available data comes from popular programming languages and would, therefore, benefit a larger group of end-users"

This is a consequential decision that trades off performance equity (low-resource languages get less training signal) for practical utility (the model is strongest where the most users are). The paper additionally notes that after deduplication, several high-resource languages (C, C++, C#, Java, JavaScript, Python, PHP) had similar volumes — 44 to 87 GB each — which "further reinforced our belief that we did not need to drastically re-weigh the existing data distribution."

**The JSON, YAML, and CSS exception.** The paper explicitly re-weighs three data formats downward (Section 3.6): JSON and YAML to 1 GB each, CSS to 3 GB. The reasoning is that these formats are primarily data containers rather than executable code — the model should learn their syntax and structure, but "without wasting compute resources on memorizing the data in such files." This is a nuanced position: the model *should* be able to generate valid JSON, but shouldn't memorise specific JSON configuration files from the training set.

#### Heuristic Filtering Pipeline

The filtering pipeline is applied after deduplication but **independently for each programming language**, with language-specific decisions about which filters to enable. This per-language customisation is critical because a single filter applied uniformly would produce unacceptable false-positive rates on languages with different syntactic conventions.

**Visual inspection as filter calibration (Section 3.1, "Visual inspection").** Before applying any automated filters, the community conducted a manual audit: 30,000 files were randomly selected from The Stack for each programming language, categorized by extension, and up to 1,000 files per extension were kept. Eighteen community annotators examined 50–100 files each, answering two questions:

1. Does the file contain "normal code written by humans" (as opposed to text, data, or a single long line of autogenerated code)?
2. Should the default filters (alpha-numeric filter requiring >25% alphabetic characters, long-line filter requiring lines <1,000 characters) be applied to this extension?

The outcome was concrete: 36 extensions were excluded entirely, and the long-line filter was eliminated for 27 extensions. The annotator remarks and decisions are publicly documented in a Google sheet, making this one of the most transparent data curation processes in the LLM literature. This manual inspection is not merely a data quality step — it is a **governance mechanism** that allows community members to directly influence what data enters the training set, fulfilling the project's commitment to open decision-making.

**XML filter.** The paper observed that certain file extensions (given example: `.sld`) contained more than 50% XML files, where the extension was used for data serialisation rather than program source code. The filter checks for the literal string `<?xml version=` within the first 100 characters of the file. If found, the file is removed. The 100-character window makes the filter efficient (no need to parse the entire file) and the specific string is unlikely to appear in non-XML source code, minimising false positives. XSLT is excluded from this filter because XSLT *is* an XML-based language — applying the XML filter to it would remove legitimate source files.

**Alpha filter (Section 3.1, "Alpha filter").** The filter removes files where fewer than 25% of characters are alphabetic (letters). This is designed to catch data files that store numeric tensors, binary-encoded data, or large arrays of numbers — particularly common in MATLAB, where the paper reports "numerous data files that frequently stored large tensors." The 25% threshold is the result of balancing: too low and data files pass through; too high and legitimate code in symbol-heavy languages (Assembly, for instance) gets falsely removed. The calibration process was iterative: the filter was tested on a small subset, and for the 25 extensions with the highest number of detections, annotators manually verified whether the filter was appropriate. Languages where the filter produced false positives (like Assembly, where register names and opcodes are non-alphabetic) had the filter disabled.

**HTML filter.** HTML files present a unique challenge: they contain a mix of code (JavaScript, CSS) and boilerplate (repeated structural tags, navigation elements, links). A naive inclusion risks training the model on website chrome rather than meaningful content. The custom HTML filter addresses this by computing the **ratio of visible text** to total HTML content. Only files where:

- Visible text makes up at least 20% of the HTML code, AND
- The visible text has a minimum length of 100 characters

are retained. "Visible text" means the text that would be rendered in a browser, excluding markup tags. This filter effectively removes link directories, navigation templates, and other low-information HTML files while preserving documentation, tutorials, and embedded code examples.

**JSON and YAML filters.** The filters for these data formats are more aggressive than for programming languages because the goal is format learning, not content memorisation. For YAML, a file is kept only if ALL of the following hold:

- File length between 50 and 5,000 characters (removing both trivial two-line configs and massive data dumps)
- Average line length less than 100 characters
- Maximum line length less than 1,000 characters
- More than 50% alphabetic characters

These thresholds remove "around 20% of the files and 90% of the volume" — the 90% volume reduction with only 20% file count reduction indicates that the removed files are disproportionately large (likely machine-generated data dumps), which is exactly the target. For JSON, the filters are simpler (50–5,000 characters, >50% alphabetic), removing approximately 70% of files and 98% of volume. The higher volume reduction for JSON reflects that JSON files in GitHub repositories are even more likely to be machine-generated data than YAML files.

**GitHub issues filtering (Section 3.3).** The filtering for GitHub issues (natural language conversations from issues and pull requests) follows a four-stage pipeline motivated by the observation that bot-generated content, email replies, and single-user monologues dominate raw issue data:

1. **Email reply removal:** A set of regular expressions (detailed in Appendix A) strips auto-generated text appended when users reply to GitHub issues via email. These regexes match patterns like `From:...Reply to this email directly...view it on GitHub` and `On...notifications@github.com...wrote:`. An additional regex removes date headers (`\d+/\d+/\d+ \d{2}:\d{2} [AP]M.+wrote`) and long underscore separators (`_{20,}`). Issues with remaining message content shorter than 200 characters after email stripping are removed entirely; long comments are truncated to a maximum of 100 lines (retaining the last 20 lines) by removing the middle. This step eliminates 18% of issue volume.

2. **Bot author removal:** A static list of known bot usernames (17 entries including `codecov-io`, `coveralls`, `CLAassistant`) and pattern-based bot detection (username contains `[bot]`, `botmanager`, `bors-`, `jenkins`, `k8s-`, `-test-`, `travis`, or ends with any of 14 suffixes including `-automaton`, `-benchmark`, `-ci`, `-linter`) is used to identify bot comments. All comments from bot authors are removed. This eliminates 17% of total events and empties 14.7% of issues entirely. The paper notes that bot-generated issues tend to be "lengthy and contain numerous logs and links," which makes them both high-volume and low-signal for language modeling.

3. **Conversation quality filtering:** Single-user conversations are treated as low-quality unless they are short. Specifically, a conversation is retained only if it involves 2+ users, OR (it involves a single user AND the total text within comments is less than 7,000 characters [the 96th percentile]). Additionally, single-user issues with more than 10 events are removed because they "tended to be of poor quality or originate from overlooked bots." This removes a further 14% of issues.

4. **Language filtering:** A fasttext language identification model (`lid.176.bin`) filters out non-English issues. This is necessary "to enable accurate redaction of names using a PII detection model" (Section 4.3) — the PII model is trained on English data, and applying it to non-English text would produce unreliable results.

**Git commits filtering (Section 3.4).** The Git commit data was collected from BigQuery and contains single-file commits from repositories matching the same licenses and file extensions as The Stack. The raw dataset is approximately 4 TB. The paper applies seven filters, summarised in Table 4:

1. **Maximum characters:** Code files longer than 100,000 characters are removed.
2. **Small changes subsampling:** Commits with 2 or fewer changed lines are subsampled with 50% probability, reducing the training signal spent on trivial edits.
3. **Long-range refactorings subsampling:** Commits spanning 200 or more changed lines are subsampled with 10% probability. These are likely large refactorings where the diff is mostly code movement rather than semantically meaningful edits.
4. **Empty commit message removal:** Commits with an empty subject line are discarded.
5. **Automatic commit removal:** Commits whose message contains or equals a list of stop words (not specified in the paper) are removed.
6. **Hash message removal:** Commits with a whitespace-separated words-to-characters ratio greater than 20 are removed — this catches diffs consisting primarily of hash values or binary data, where the text consists of long alphanumeric strings with few word breaks.
7. **Data file subsampling:** Data formats (JSON, YAML, XML, HTML) are subsampled with 50% probability to reduce their representation relative to source code.

After filtering, the dataset is sampled to 50% of the remaining files. A key design choice for commit data: to avoid "spending too much compute budget on learning to copy the file content," the full file is used only 20% of the time. For the remaining 80%, a window of 0–32 lines around the first and last changed line is sampled. This forces the model to focus on the *change* itself rather than memorising large unchanged portions of files. The resulting dataset contains 64 GB of commit data.

#### Near-Deduplication

The deduplication pipeline (Section 3.5) is inherited from Ben Allal et al. (2023) and operates on source code files across all programming languages and Jupyter notebooks (but not Git commits, due to time constraints, or GitHub issues, because duplicates are unlikely in conversational text).

**Procedure.** For each file, **MinHashes** are computed on 5-grams of characters. MinHash is a locality-sensitive hashing technique that compresses a set into a fixed-size signature (a vector of hash values) such that the Jaccard similarity between two sets can be estimated from the fraction of matching entries in their MinHash signatures. The choice of 5-grams means the unit of comparison is a 5-character window — the method detects files that share substantial substrings, which is characteristic of copy-pasted code (the most common form of duplication in GitHub repositories).

The MinHash signatures are then grouped into buckets using **Locality Sensitive Hashing (LSH)**. LSH hashes the signatures such that similar signatures are likely to collide into the same bucket with high probability. Within each bucket, pairs of files with estimated **Jaccard similarity ≥ 0.7** are identified, and one copy is removed. The Jaccard similarity between two files A and B is the size of their intersection (shared 5-grams) divided by the size of their union — a value of 0.7 means that 70% of the distinct 5-grams appearing in either file appear in both.

The 0.7 threshold is deliberately set high enough to avoid removing files that share boilerplate (license headers, import statements) but are otherwise distinct — a common challenge in code deduplication. The use of character-level rather than token-level 5-grams means the method is robust to whitespace and formatting differences (which are common when code is copy-pasted and reformatted). The paper does not report the total volume reduction from deduplication, but Tables 1–2 show that the total volume after deduplication is 815.68 GB across all sources, and after filtering this drops to 799.37 GB.

#### Data Weighting and the Natural Distribution Decision

Section 3.6 describes a community discussion about whether to up-sample or down-sample programming languages. The decision to **follow the natural distribution** — sampling data sources proportionally to their volume — rests on three observations:

1. **User alignment:** The largest data volumes come from the most popular languages, so the natural distribution already aligns with user needs.
2. **Post-deduplication equalisation:** After deduplication, several high-resource languages (C, C++, C#, Java, JavaScript, Python, PHP) had similar volumes (44–87 GB), reducing the need for explicit re-weighting.
3. **Data format exceptions:** JSON, YAML, and CSS are re-weighed to 1 GB (YAML), 1 GB (JSON), and 3 GB (CSS) to teach format without data memorisation.

This decision has a specific implication: the model will not perform equally across all 86 languages. Languages with less than 1 GB of training data (over 30 of the 86, visible in Tables 1–2) receive a tiny fraction of the training budget. The paper does not frame this as a limitation but rather as a pragmatic tradeoff, consistent with the overall philosophy of transparency: the data distribution is published, so users can assess for themselves whether the model's language coverage meets their needs.

#### PII Redaction: Annotation Data Collection

Section 4 describes a substantial data collection effort that produced a **12,000-file annotated PII dataset** across 31 programming languages. This dataset is the foundation for training the PII detection model and is a standalone contribution — it is released under gated access for further research.

**Crowd-worker setup.** The annotation was conducted on the Toloka platform with 1,399 crowd-workers from 35 countries (listed in Appendix B, Table B.1). The compensation model is explicitly described:

- Average completion: 206 tasks per worker
- Average earnings: approximately $27
- Average work duration: 3.1 hours
- Target hourly rate: $7.30, calibrated against purchasing power parity

The paper states that eligibility was limited to countries where "$7.30 was equivalent to the highest minimum wage in the US ($16.50) in terms of purchasing power parity." This is a deliberate attempt to pay fair wages while operating within budget constraints — a practical ethical consideration that is rarely documented in ML papers. Out of 1,399 workers, 695 filled out a quality survey, and 519 completed it. The average score on the question "would you like to contribute to another project like this?" was 4.92 out of 5.

**File selection strategy.** The 12,000 files are not a uniform random sample. To increase representation of rare PII types (keys, passwords, IP addresses), 7,100 files were pre-filtered from a larger pool using the `detect-secrets` tool with all default plugins activated, plus regular expressions from Ben Allal et al. (2023) for detecting emails, IPv4 addresses, and IPv6 addresses. The remaining 5,100 files were randomly selected without pre-filtering. This two-part strategy balances two goals: (1) the model must see enough examples of rare PII types to learn to detect them, and (2) the dataset must not be so biased toward pre-filtering heuristics that the model merely learns to replicate the heuristics. The 5,100 unfiltered files serve as a calibration set that prevents this overfitting.

**Annotation task design.** Annotators distinguished between three categories of PII appearance:

- **License header PII:** Names, emails, or usernames that appear in copyright headers or license boilerplate. These are typically provided voluntarily by authors for attribution and "may not require masking" — the model should learn that these are public identifiers, not private data.
- **Placeholder PII:** Names, emails, or usernames used as example values (e.g., `john.doe@example.com`, `username_here`). These are not real secrets and do not need masking.
- **Confidential PII:** Actual personal information (real names, working email addresses, real usernames in API calls or configuration files) that should be masked.

This tripartite distinction matters because blindly masking all detected names would remove valuable training signal from license headers (where names provide authorship context) and from placeholder examples (which teach the model about code documentation patterns). The categories are applied to names, emails, and usernames; keys, passwords, IP addresses, and IDs are not sub-categorised.

**Detected entities and annotation quality.** The annotators identified a total of 22,950 PII entities. Table 5 reports the count per entity type and a manual quality inspection on 300 files:

| PII Type | Count | Recall | Precision |
|---|---|---|---|
| IP_ADDRESS | 2,526 | 85% | 97% |
| KEY | 308 | 91% | 78% |
| PASSWORD | 598 | 91% | 86% |
| ID | 1,702 | 53% | 51% |
| EMAIL | 5,470 | 99% | 97% |
| NAME | 2,477 | 89% | 94% |
| USERNAME | 780 | 74% | 86% |
| AMBIGUOUS | 287 | — | — |

The ID category was excluded from model training due to low precision and recall (both near 50%) — annotators found it "particularly challenging" to distinguish secret IDs from non-secret identifiers like variable names. The sub-categories (EMAIL_EXAMPLE, EMAIL_LICENSE, NAME_EXAMPLE, NAME_LICENSE, USERNAME_EXAMPLE, USERNAME_LICENSE) were mapped back to their parent category for evaluation, but the model was not trained to distinguish them (the paper notes "the model's poor performance in distinguishing them" as the reason).

#### StarEncoder: The Base Encoder Model

The PII detection model is not trained from scratch — it is a fine-tuned version of **StarEncoder**, a 125M-parameter encoder-only model trained by the BigCode team (Section 4.2). StarEncoder is an internal tool model designed to be efficiently fine-tunable for both code- and text-related tasks, analogous to how BERT serves as a base for downstream NLP tasks.

**Architecture.** StarEncoder is a bi-directionally self-attentive Transformer (encoder-only, meaning it can attend to all tokens in the input simultaneously) with the hyperparameters in Table 6:

- Hidden size: 768
- Intermediate size: 3,072
- Maximum position embeddings: 1,024
- Number of attention heads: 12
- Number of hidden layers: 12
- Attention type: standard multi-head (not multi-query)
- Total parameters: approximately 125M

This is a relatively small model by modern standards — the 125M parameter count is comparable to BERT-base — reflecting its role as a task-specific encoder rather than a generative model. The 1,024-token context window is sufficient for the code snippets being analysed for PII.

**Pre-training objectives.** StarEncoder is pre-trained with two objectives inherited from BERT (Devlin et al., 2019):

1. **Masked Language Modeling (MLM):** 15% of tokens in the input are independently masked (replaced with a `[MASK]` token), and the model must predict the original token at each masked position. This teaches the model bidirectional representations of code — it learns to understand tokens in the context of both what comes before and after, which is crucial for PII detection (a name in isolation is ambiguous; a name surrounded by code that looks like a license header vs. a configuration file is contextually identifiable).

2. **Next Sentence Prediction (NSP):** The model receives pairs of code snippets separated by a `[SEP]` token, preceded by a `[CLS]` token. The snippets are either consecutive segments from the same source file (positive example) or from different documents (negative example). A linear classifier on the `[CLS]` representation predicts whether the pair is consecutive. This objective teaches the model document-level coherence, which helps with PII detection by providing context about whether a token appears in a location typical of PII (e.g., at the top of a file in a comment) vs. in executable code.

**Input format.** The input to StarEncoder is structured as `[CLS] Snippet-1 [SEP] Snippet-2`, where the two snippets are selected randomly either from the same source file or from two distinct files. The MLM loss is applied to masked tokens across both snippets; the NSP loss is applied to the `[CLS]` token.

**Training scale.** StarEncoder is trained for 100,000 steps with a global batch size of 4,096 sequences, each up to 1,024 tokens. This means the model observes approximately 400 billion tokens during pre-training, which takes "roughly two days using 64 NVIDIA A100 GPUs." The large batch size (4,096 × 1,024 ≈ 4.2 million tokens per step) provides stable gradient estimates for the relatively small model.

#### PII Detection Model: NER Fine-Tuning

With StarEncoder as the base, the PII detection model is created by adding a **token classification head** — a linear layer that maps each token's hidden representation to a probability distribution over entity classes — and fine-tuning on the annotated PII dataset (Section 4.3).

**Target classes.** The model is trained to classify tokens into six entity types (plus the implicit "no entity" class): names, emails, keys, passwords, IP addresses, and usernames. The ID entity was excluded due to low annotation quality. The sub-categories (license vs. placeholder vs. confidential) are not predicted because the model could not reliably distinguish them — the paper notes "the model's poor performance in distinguishing them" and maps all sub-categories to the parent entity.

**Training data split.** The annotated dataset is split into 7,878 training examples and 4,000 test examples, "ensuring that both splits have a balanced representation of the different PII types." Table 7 shows the entity counts in each split:

| Entity | Train | Test |
|---|---|---|
| EMAIL | 4,721 | 1,742 |
| NAME | 3,847 | 1,298 |
| IP_ADDRESS | 1,941 | 521 |
| USERNAME | 1,320 | 346 |
| PASSWORD | 390 | 148 |
| KEY | 171 | 118 |

The training split is augmented with 400 annotated files from Ben Allal et al. (2023), providing additional examples from a different annotation effort.

**Fine-tuning baseline results.** After fine-tuning, the model achieves F1 scores above 90% on names, emails, and IP addresses (89.19%, 96.01%, 91.61% respectively, from Tables 8–9), and 73.39% on passwords. Performance on keys and usernames is substantially lower: 56.66% on keys and 59.39% on usernames. The paper attributes low key performance to the limited number of labels (only 171 training instances), and low username performance to confusion with "decorators and values in paths — most likely because we annotated usernames inside links for social media platforms," where the syntax of a path (`/@username` or `/user/username`) is ambiguous with non-username path components.

**Pseudo-labeling augmentation.** To improve performance on keys and passwords — the two rarest and most critical PII types — the paper applies a **pseudo-labeling technique** (Lee, 2013). The procedure works as follows:

1. **Initial model ensemble:** Two encoder models are fine-tuned on the 400-file PII dataset from Ben Allal et al. (2023). This small dataset serves as the seed.

2. **Unlabeled data annotation:** The ensemble generates predictions on 18,000 unlabeled files. For each token, the average probability logits from the two models are computed as a confidence score.

3. **Confidence thresholding:** Pseudo-labels are retained only if the average probability exceeds a threshold. The threshold is 0.5 for most entities but raised to 0.6 for names and usernames — the paper does not explain this asymmetry, but it is likely because names and usernames have higher false-positive rates in preliminary testing, so a higher threshold is needed to ensure pseudo-label quality.

4. **Key/password trigger-word filtering:** For keys and passwords specifically, the paper observed "a significant number of false positives" in the pseudo-labeled data. To address this, an additional filter is applied: a pseudo-labeled key or password is retained only if the 100 characters preceding it contain a trigger word such as `key`, `auth`, or `pwd`. This heuristic leverages the fact that real secrets in code are almost always accompanied by a descriptive variable name or comment, while false positives (e.g., random strings that happen to look like keys) lack this context.

5. **Two-stage training:** The model is first trained on the synthetic pseudo-labeled dataset, then fine-tuned on the human-annotated dataset. This order — synthetic first, real second — ensures that the model benefits from the larger quantity of pseudo-labeled data but ultimately respects the higher-quality human annotations.

**Results of pseudo-labeling.** Tables 8 and 9 show the effect:

- **Emails:** F1 improves from 96.01% to 98.15% (precision 94.01% → 97.73%, recall 98.10% → 98.94%)
- **IP addresses:** F1 improves from 91.61% to 91.94% (modest)
- **Keys:** F1 improves from 56.66% to 70.41% — a substantial jump, primarily driven by recall improvement (53.38% → 80.81%) while precision remains similar (60.37% → 62.38%)
- **Passwords:** F1 improves from 73.39% to 81.57% (precision 59.16% → 70.94%, recall remains high)
- **Names:** F1 improves from 89.19% to 91.59%
- **Usernames:** F1 improves only slightly from 59.39% to 61.49% — the paper concludes that "the performance for detecting usernames did not show significant improvement, so we decided to exclude it from the PII redaction process"

The final PII detection model thus targets five entity types (names, emails, keys, passwords, IP addresses) and excludes usernames and IDs.

**Comparison against regular expressions.** Table 8 directly compares the final NER model against the regex-based approach from Ben Allal et al. (2023) on the three entity types that regexes support (emails, IP addresses, keys). The paper notes that the email regex was enhanced to address false positives found during evaluation, boosting its F1 from 81.8% to 96.83% — already very competitive with the NER model. However:

- **Keys:** The regex approach achieves only 3.62% precision and 49.15% recall (F1: 6.74%), compared to the NER model's 60.37% precision and 53.38% recall (F1: 56.66%). The paper explains that the `detect-secrets` tool "generated many false positives, especially in specific programming languages like Go and C-sharp that weren't well represented in the regex evaluation."

This comparison justifies the substantial investment in a trained NER model: for rare, high-stakes PII types like keys, regexes are essentially useless as a standalone detection mechanism, while even a modestly-performing NER model (56.66% F1) is vastly better.

**Post-processing rules.** Before the model is applied to the full 815 GB training dataset, several post-processing rules are added to reduce false positives (Section 4.3, "Post-processing"):

1. **Minimum length for secrets:** Detected secrets with fewer than 4 characters are ignored (e.g., a 2-character string detected as a key is almost certainly a false positive).
2. **Full name requirement:** For name entities, at least one space must be present within the detection — this ensures that only full names (first + last) are masked, not individual words that happen to look like names.
3. **Key validation:** Detected keys with fewer than 9 characters are ignored, and a `gibberish-detector` (an external tool) is used to filter out keys that are "not gibberish" — real API keys and passwords tend to be high-entropy random strings; tokens that look like English words or common variable names are likely false positives.
4. **IP address validation:** The `ipaddress` Python package is used to verify that the detected string is actually a valid IP address. Non-valid or private (non-Internet-facing) addresses are ignored. Additionally, a list of IP addresses from popular DNS servers (same list as in Ben Allal et al., 2023) is used to filter out false positives from DNS configuration files.

**PII replacement strategy.** Detected PII entities are replaced with sentinel tokens: `<NAME>`, `<EMAIL>`, `<KEY>`, and `<PASSWORD>`. For IP addresses, the replacement strategy is different: an IP address is replaced with one of 5 synthetic, private, non-Internet-facing IP addresses (listed in Appendix C), randomly selected. The paper uses 5 IPv4 addresses (e.g., `172.16.31.10`, `192.168.127.12`) and 5 IPv6 addresses (e.g., `fd00:c2b6:b24b:be67:2827:688d:e6a1:6a3b`). Replacing with private IP addresses rather than a generic sentinel token preserves the syntactic structure of IP addresses in code — the model still learns to generate valid IP address syntax, but the specific values are synthetic.

**GitHub issues special handling.** For GitHub issues, a different strategy is used for usernames (which were excluded from the NER model but are critical to mask in conversational text). The paper uses an **anonymization by participant counter** approach: within each issue conversation, the authors are replaced with pseudonyms like `username_0`, `username_1`, etc., where the number is the participant's order of appearance in the conversation. These pseudonyms are prepended to the beginning of each comment to preserve speaker identity. All mentions of these pseudonyms within the messages are also replaced. Critically, only the usernames of active participants are masked — mentions of non-participating users (e.g., `@torvalds` in a discussion about Linux) are not anonymized, preserving valuable training signal about how developers reference external projects and people.

**Compute cost.** Running the PII detection model over the entire training dataset (815 GB of programming languages, plus GitHub issues [names only], Git commits, and Jupyter notebooks) required **800 GPU-hours** on NVIDIA A100 80 GB GPUs. This is a substantial cost — roughly 0.25% of the total training compute (320,256 GPU-hours) — and represents a deliberate investment in privacy that is unnecessary for raw model performance.

#### Data Formatting with Sentinel Tokens

Section 5.1 describes how each data source is formatted into a structured template with sentinel tokens before being fed to the model. These templates serve multiple functions: they separate different data sources with explicit delimiters (preventing the model from confusing code with issue text), they encode metadata that provides context (repository name, stars bucket, filename), and they structure tasks like commit editing and notebook execution.

**Code formatting template:**
```
<reponame>reponame<filename>filename<gh_stars>stars\ncode<|endoftext|>
```

The metadata tokens (`<reponame>`, `<filename>`, `<gh_stars>`) are prepended to the code content. The repository name and filename tell the model which project and file the code belongs to, which the paper argues helps the model learn repository-level conventions. The GitHub stars are bucketed into five categories: 0, 1–10, 10–100, 100–1000, and 1000+. Bucketing prevents the model from overfitting to exact star counts (which would be spurious — a repository's popularity does not determine code quality with precision) while still providing a popularity signal. Crucially, each metadata field is independently **prefixed at random with probability 0.2**. This means that 20% of the time, the repository name is omitted; 20% of the time, the filename is omitted; and 20% of the time, the stars are omitted. The purpose is explicit: "to enable the model to operate without this metadata during inference." If metadata were always present during training, the model might learn to rely on it, making it brittle when users provide code without repository context — which is the common case in IDEs and interactive coding assistants.

**Fill-in-the-Middle (FIM) transformation.** The code content in the template undergoes the FIM transformation (Bavarian et al., 2022). FIM is a data-augmentation technique that teaches the model to generate code conditioned on both a prefix (code before the insertion point) and a suffix (code after the insertion point) — the "fill in the middle" use case where a developer wants to insert code between two existing blocks.

The transformation operates at the **character level** (not token level) on the source code. With a FIM rate of 0.5, 50% of code files are transformed into FIM format; the other 50% are left in standard left-to-right format. This split ensures the model is equally capable of standard completion and infilling.

Two FIM modes are used, each with probability 0.5:

1. **PSM mode (Prefix-Suffix-Middle):** The file is split at a randomly chosen position into a prefix (everything before the split) and a suffix (everything after). The training sequence becomes `<fim_prefix>` + prefix + `<fim_suffix>` + suffix + `<fim_middle>` + middle, where "middle" is the actual code that was removed. During inference, the model receives the prefix and suffix and must generate the middle.

2. **SPMv2 mode (Suffix-Prefix-Middle):** Similar to PSM but the order of prefix and suffix is swapped in the input: `<fim_suffix>` + suffix + `<fim_prefix>` + prefix + `<fim_middle>` + middle. Bavarian et al. (2022) found that including both orderings improves performance, particularly when the suffix provides more contextual constraint than the prefix.

The sentinel tokens used are `<fim_prefix>`, `<fim_middle>`, `<fim_suffix>`, and `<fim_pad>` (for padding sequences to uniform length). During standard left-to-right generation, these tokens are never produced; during infilling, the model is prompted with `<fim_prefix>`...`<fim_suffix>`...`<fim_middle>` and generates the completion.

**GitHub issues formatting template:**
```
<issue_start>Title: title\nusername_0:comment0<issue_comment>username_1:comment1
... <issue_closed (optional)><|endoftext|>
```

Each issue starts with `<issue_start>`, followed by the issue title. Comments are separated by `<issue_comment>` tokens. Each comment is prefixed with the anonymized speaker identifier (e.g., `username_0:`) to preserve turn-taking structure. If the issue was closed, a `<issue_closed>` token is included at the end. The issue title is included in the sequence to provide topic context — the model learns that the first comment usually addresses the issue title.

**Jupyter notebooks — scripts.** Jupyter scripts (produced by Jupytext conversion) are formatted identically to code files, with the same metadata template and FIM transformation. This treats notebook scripts as standard source code, which is appropriate since the conversion strips cell metadata and outputs, leaving only executable code.

**Jupyter notebooks — structured.** For the structured Jupyter dataset, each notebook is decomposed into a chain of text-code-output triplets:
```
<jupyter_start><jupyter_text>text0<jupyter_code>code0
<jupyter_output>output0<jupyter_text>text1<jupyter_code>code1
... <|endoftext|>
```

This format captures the instructional structure of Jupyter notebooks: a text cell (typically Markdown explaining what the next code cell does), followed by a code cell, followed by the output of executing that code cell. The model is trained to predict code given text (instruction following), output given code (acting as a code interpreter), and text given previous code and output (documentation generation). If an output cell is empty, a special sentinel `<empty_output>` is inserted instead of `<jupyter_output>output`. At inference time, the `<empty_output>` token can be suppressed (excluded from the sampling distribution) to force the model to always predict an output, enabling its use as a basic code interpreter.

**Git commits formatting template:**
```
<commit_before>code_before<commit_msg>message<commit_after>code_after<|endoftext|>
```

The `code_before` and `code_after` contain the file content before and after the commit, respectively, and `message` is the commit message. As described in Section 3.4, the full file is used only 20% of the time; otherwise, a window of 0–32 lines around the changed lines is used. This template teaches the model to perform editing tasks: given code before a change and a natural language commit message, generate the code after the change. This is a form of instruction following baked into the pretraining data.

**Summary of sentinel tokens.** All sentinel tokens are listed in Table 10, totalling 17 tokens. These tokens are special — they are added to the tokenizer's vocabulary and have fixed, non-compositional meanings. They serve as structural markup that the model can use to identify which type of content it is generating and to switch between modes (e.g., from code to issue discussion).

#### Training Data Decontamination

Before training, the dataset is decontaminated against the evaluation benchmarks used in Section 6 (HumanEval, MBPP, APPS, GSM8K, DS-1000). The goal is to prevent the model from memorising evaluation examples, which would invalidate benchmark scores as measures of generalisation.

The decontamination procedure (Section 5.2) removes any file that contains:

- Docstrings or solutions from HumanEval and MBPP
- Docstrings from APPS (a competitive programming benchmark)
- Questions from GSM8K (a math word problem benchmark)
- Prompts from DS-1000 (a data science benchmark)

The paper reports that Python has the highest number of removed files (558 files out of approximately 12.8 million), which is expected because HumanEval, MBPP, and DS-1000 are Python benchmarks. The absolute number is small — 558 files out of millions — suggesting that benchmark contamination in The Stack is not widespread, but the precaution is taken to ensure integrity of the evaluation.

#### Tokenizer Design

The tokenizer (Section 5.3) follows the design from Ben Allal et al. (2023) and uses **Byte-Level Byte-Pair Encoding (BPE)** trained with the Hugging Face Tokenizers library. Key specifications:

- **Vocabulary size:** 49,152 tokens, including the 17 sentinel tokens from Table 10. This is larger than the typical 32K–50K used in many LLMs (GPT-2 uses ~50K), providing finer-grained representation of code tokens.
- **Pre-tokenization:** Includes a **digit-splitter** that separates digits from non-digit characters (e.g., `foo123` becomes `foo` + `123`) and the **GPT-2 pre-tokenizer regex splitter**, which splits on whitespace and punctuation using a standard pattern. The digit-splitter is particularly important for code because numeric literals are common and often unique (a specific integer like `2048` may appear rarely, but the digits `2`, `0`, `4`, `8` are common), so splitting them allows the tokenizer to reuse digit tokens across different numbers rather than requiring a unique token for each integer literal.
- **Byte-level:** The tokenizer operates on bytes, meaning it can represent any sequence of bytes, including characters not seen during tokenizer training. This is important for code, which may contain arbitrary binary data, Unicode characters, or unusual symbols in comments or string literals. A character-level tokenizer with a fixed vocabulary would produce `<UNK>` for unseen characters; a byte-level tokenizer can always tokenise any input by falling back to individual bytes.
- **Training data:** The tokenizer is trained on the same data distribution as the model, ensuring that the vocabulary is optimised for the code and text domains the model will encounter.

The BPE algorithm works by starting with a vocabulary of individual bytes and iteratively merging the most frequent adjacent token pairs to form new tokens, up to the target vocabulary size. The result is a vocabulary where common code patterns (e.g., `def `, `import `, `return`) become single tokens, improving both compression (fewer tokens per file) and the model's ability to learn common syntactic patterns.

#### Model Architecture

The model architecture (Section 5.4) is a **15.5B-parameter decoder-only Transformer** with three distinguishing features: Multi-Query Attention, Fill-in-the-Middle training, and an 8K-token context length supported by FlashAttention. The architecture is directly scaled up from SantaCoder (1.1B parameters), with the hyperparameters given in Table 11:

| Hyperparameter | SantaCoder (1.1B) | StarCoder (15.5B) |
|---|---|---|
| Hidden size | 2,048 | 6,144 |
| Intermediate size | 8,192 | 24,576 |
| Max position embeddings | 2,048 | 8,192 |
| Num. attention heads | 16 | 48 |
| Num. hidden layers | 24 | 40 |
| Attention type | Multi-query | Multi-query |

The scale-up from SantaCoder to StarCoder involves: tripling the hidden size (2,048 → 6,144), quadrupling the context length (2,048 → 8,192), tripling the number of attention heads (16 → 48), increasing the number of layers by 1.67× (24 → 40), and tripling the intermediate FFN size (8,192 → 24,576).

**Decoder-only Transformer.** A decoder-only architecture means that each token can only attend to previous tokens in the sequence (causal/autoregressive attention), not to future tokens. This makes it suitable for autoregressive generation: the model produces one token at a time, and each new token conditions on all previously generated tokens. For Fill-in-the-Middle, the attention mask is adjusted so that the prefix can attend to the prefix, the suffix can attend to the prefix and suffix, but the suffix does not attend to the middle (which hasn't been generated yet).

**Multi-Query Attention (MQA).** In standard multi-head attention, each attention head has its own query (Q), key (K), and value (V) projection matrices. With H = 48 heads and hidden size d = 6,144, each head operates on d/H = 128 dimensions. The key and value projections produce H separate K and V tensors per layer. Multi-Query Attention (Shazeer, 2019) modifies this: the query projection still produces H separate query tensors, but the key and value projections produce only a single key and value tensor shared across all heads. Each head computes attention using its own query against the shared key and value. The result is a dramatic reduction in the size of the KV cache during inference: for a sequence of length L, the KV cache stores H × L × (d/H) × 2 = 2 × L × d values for standard attention, but only 2 × L × (d/H) = 2 × L × d/H values for MQA. With H = 48, this is a 48× reduction in KV cache memory, which directly translates to larger possible batch sizes during inference. The paper explicitly calls this out: "fast large-batch inference enabled by multi-query attention."

During training, MQA requires expanding the shared key and value to match the number of heads before calling the attention kernel. The paper states: "To make FlashAttention work with MQA during training, we simply expand the key and value before calling the attention kernel." This expansion is a no-op in terms of the actual computation — it just replicates the shared tensor H times so that the attention kernel sees the expected shapes — but it avoids the need to implement a custom attention kernel that natively supports MQA.

**FlashAttention.** The 8K context length is enabled by FlashAttention (Dao et al., 2022), a memory-efficient exact attention algorithm that avoids materialising the full N×N attention matrix in GPU high-bandwidth memory (HBM). Standard attention computes softmax(QK^T / √d_k) × V, which requires storing the N×N attention weights matrix. For N = 8,192, this matrix contains 67 million entries — at 2 bytes each (FP16), that's 134 MB per attention head per layer, or 134 × 48 × 40 ≈ 257 GB for the full model, far exceeding GPU memory. FlashAttention restructures the computation using tiling (processing the attention matrix in blocks that fit in on-chip SRAM) and recomputation (re-computing attention weights in the backward pass rather than storing them from the forward pass). This reduces the memory footprint from O(N^2) to O(N), making 8K context length feasible on standard GPU hardware.

**Learned absolute positional embeddings.** The model uses learned (not sinusoidal) absolute positional embeddings with a maximum position of 8,192. Each position from 0 to 8,191 has a learned embedding vector that is added to the token embedding before the first Transformer layer. This is standard for decoder-only models and provides the model with information about token order — essential for code, where statement order determines semantics.

---

#### Training Details and Distributed Setup

**StarCoderBase training (Section 5.5).** The base model is trained for 250,000 iterations with a batch size of 4 million tokens per iteration, for a total of 1 trillion tokens seen. The optimizer is Adam (Kingma and Ba, 2015) with:

- β₁ = 0.9 (exponential decay rate for the first moment estimate)
- β₂ = 0.95 (exponential decay rate for the second moment estimate, slightly lower than the default 0.999, which the paper notes was chosen to improve stability in large-batch training)
- ε = 10⁻⁸ (numerical stability constant)
- Weight decay: 0.1 (L2 regularisation applied directly to weights, not gradients — the AdamW variant)

The learning rate schedule is **cosine decay** from 3 × 10⁻⁴ to 3 × 10⁻⁵ after a linear warmup of 2,000 iterations. The warmup period prevents large gradient updates early in training when the optimizer's moment estimates are poorly calibrated. The cosine decay reduces the learning rate smoothly from the peak (3 × 10⁻⁴) to the minimum (3 × 10⁻⁵) following a cosine curve over the remaining 248,000 iterations. The 10× ratio between peak and minimum learning rates is standard in LLM training and reflects the observation that reducing the learning rate by an order of magnitude over the course of training improves final loss.

**StarCoder fine-tuning (Section 5.5).** Starting from the final StarCoderBase checkpoint, the model is fine-tuned on the Python subset of the training data for 2 epochs (35B tokens, 8,500 steps at 4M tokens/step). The optimizer settings are the same except for the learning rate: starting at 5 × 10⁻⁵ and decaying to 5 × 10⁻⁶ after 1,000 steps of linear warmup. The lower learning rate (5 × 10⁻⁵ vs. 3 × 10⁻⁴) reflects that this is a fine-tuning stage starting from a pre-trained model — the weights are already in a good region of the loss landscape, so large updates would risk catastrophic forgetting of non-Python capabilities.

**3D-parallel distributed training (Section 5.6).** The model is trained on 512 NVIDIA A100 80 GB GPUs distributed across 64 nodes (8 GPUs per node). The parallelism strategy is 3D: tensor parallelism, pipeline parallelism, and data parallelism combined.

- **Tensor parallelism** shards individual weight matrices across GPUs. Each linear layer's weight matrix is split column-wise, so each GPU computes a partial output that is then combined (via all-reduce) to form the full output. This reduces the memory per GPU for each layer.
- **Pipeline parallelism** shards the model by layers. Different GPUs own different contiguous groups of layers, and activations are passed between them. The paper uses pipeline parallelism rank 4, meaning the model's 40 layers are split into 4 groups, each assigned to a different GPU (or set of GPUs, if combined with tensor parallelism).
- The combination of tensor and pipeline parallelism requires 16 GPUs (two nodes) for one model replica.

The remaining compute is used for **data parallelism**: 32 replicas of the model are run in parallel, each processing a different micro-batch of data, and gradients are averaged across all replicas. The total parallelism is 32-fold data × 4-way pipeline × (tensor parallelism factor).

**Micro-batch scheduling.** The global batch size is 512 sequences, achieved by using a micro-batch size of 1 sequence per GPU and accumulating gradients for 16 steps before updating weights. A micro-batch size of 1 minimises GPU memory usage (each GPU processes a single sequence at a time), while gradient accumulation over 16 steps simulates a larger effective batch size without memory overhead. The total tokens per step is 512 sequences × 8,192 tokens/sequence = 4,194,304 tokens (approximately the 4M tokens reported).

The paper uses **Megatron-LM's distributed optimizer**, noting it "leads to slightly higher throughput in this configuration." A consequence of this choice is that the gradient reduction step (averaging gradients across data-parallel replicas) happens in FP32 — even though training uses BF16 for most computations — which "leads to 10% lower throughput than FP16, but we used it anyway to avoid training instabilities." BF16 (Brain Floating Point 16) has the same exponent range as FP32 but reduced mantissa precision, making it less prone to overflow/underflow during training than FP16, at the cost of slightly lower throughput.

The paper reports "except for a few restarts, we did not experience significant training instabilities" — a notable statement given the scale (15.5B parameters, 512 GPUs) and the notorious instability of large-scale Transformer training.

#### Carbon Emissions

Section 5.7 reports the carbon footprint using the methodology from Lacoste et al. (2019). For StarCoderBase:

- Total GPU hours: 320,256 (512 GPUs × ~625 hours based on 250K iterations at 4M tokens/step)
- Average power per GPU: 280W
- Total electricity: 320,256 × 280W = 89,671.68 kWh
- Carbon intensity: 0.15495 kgCO₂e/kWh (us-west-2 AWS region)
- PUE (Power Usage Effectiveness): 1.2
- Total emissions: 89,671.68 × 0.15495 × 1.2 = 16.68 tonnes CO₂eq

For StarCoder fine-tuning: an additional 3.5% of training time, resulting in approximately 0.58 tonnes CO₂eq.

This carbon reporting is notable because: (1) it is rare in LLM papers (though becoming more common), and (2) the emissions are relatively modest for a 15.5B-parameter model — 16.68 tonnes CO₂eq is roughly the annual carbon footprint of 1–2 people in developed countries, orders of magnitude less than estimates for models like GPT-3 or PaLM (which can exceed hundreds of tonnes). This low carbon cost is partly due to the clean energy mix of the us-west-2 AWS region and partly due to the relatively modest training budget (1 trillion tokens for a 15.5B model — many similarly-sized models use 1.4–2 trillion tokens).

## 4. Key Insights and Innovations

### Innovation 1: Open-Access Performance Can Match Closed-Access Without Sacrificing Data Governance

The paper's most fundamental intellectual contribution is not a single technical algorithm but a **demonstration that directly challenges a dominant implicit assumption in the field**: that responsible data practices — license filtering, PII redaction, opt-out mechanisms, and full training data transparency — are inherently in tension with achieving competitive model performance. Prior to StarCoder, the landscape of Code LLMs was bifurcated: closed-access models like `code-cushman-001` and `code-davinci-002` achieved strong results through opaque data pipelines with unknown filtering, while open-access models that disclosed their training procedures (SantaCoder at 1.1B, PolyCoder at 2.7B) were substantially smaller and weaker. The unstated assumption was that the performance gap was *caused by* the transparency constraints — that the proprietary data, unfiltered of inconvenient licenses and PII, was what made the difference.

StarCoder refutes this assumption directly. By training exclusively on permissively-licensed code from The Stack — and by applying aggressive heuristic filtering that removed data files, XML dumps, and bot-generated GitHub issues — the paper shows that a model can match `code-cushman-001` (Table 15: StarCoderBase passes it on 10 of 19 MultiPL-E languages) and outperform all prior open-access multi-language models **while** being fully transparent about every data decision. The significance is not that StarCoder is *better* than closed-access models — it's roughly comparable to `code-cushman-001` and substantially behind `code-davinci-002` (Table D.1) — but that it demonstrates **competitive viability under full transparency constraints**. This reframes the burden of proof: closed-access developers can no longer plausibly claim that opacity is necessary for performance; the paper establishes a baseline showing it is not.

This is a **fundamental reframing**, not an incremental performance gain. The field's default assumption was "transparency costs performance"; StarCoder shifts the conversation to "transparency costs performance only if you're unwilling to invest in careful data engineering." The investment is real — 800 GPU-hours for PII detection, community-driven manual inspection of 30,000 files, per-language filter calibration — but it's manageable, and the paper provides a replicable template.

The evidence is anchored in Table 15, where StarCoderBase outperforms CodeGen-16B-Multi (which does not filter by license) across all 19 languages, often by large margins (Julia: 21.09% vs. 0.29%; Racket: 11.77% vs. 0.66%), and in Table 12, where StarCoder (33.6% HumanEval pass@1) essentially ties `code-cushman-001` (33.5%). These are matched or better results achieved *with* the governance constraints the field assumed were prohibitive.

---

### Innovation 2: PII Detection as a Standalone, Evaluated Component of the Training Pipeline — Not an Afterthought

Prior work on Code LLMs handled PII minimally and opaquely: regular expressions for emails and IP addresses, no public evaluation, no reported precision or recall. Ben Allal et al. (2023) used regex-based detection, but the paper's own evaluation (Table 8) reveals that this approach achieves 3.62% precision on keys — essentially useless for one of the most critical PII types. The field treated PII redaction as a box to check, not as a technical problem worthy of rigorous methodology.

This paper makes PII detection a **first-class technical artifact** with its own data collection, model training, evaluation, and failure analysis. The contributions are methodological, not algorithmic — the NER model itself is a standard fine-tuned BERT — but the systematic approach is intellectually distinctive:

- **Annotation at scale with quality measurement.** The paper collected 22,950 entity annotations across 12,000 files in 31 programming languages, then manually inspected 300 files to compute per-type precision and recall (Table 5). The decision to measure and report annotation quality — and to exclude the ID category (53% recall, 51% precision) from model training on that basis — treats the data collection as an engineering problem with measurable error rates, not an oracle.

- **Pseudo-labeling with domain-specific trigger-word filtering.** The observation that pseudo-labeled keys suffer from false positives in code contexts, and that filtering by trigger words (`key`, `auth`, `pwd` within 100 characters) improves precision, is a code-specific insight. It reflects an understanding that PII in source code has contextual regularities (secrets are typically assigned to variables with descriptive names) that differ from PII in natural language text. This boosted key F1 from 56.66% to 70.41% (Table 8).

- **Direct comparison of NER vs. regex.** Table 8 is a rare direct comparison showing that regex-based key detection is essentially non-functional (6.74% F1 vs. 56.66% for NER), providing empirical justification for the 800 GPU-hour investment in PII detection that would otherwise seem excessive. This comparison makes the case that regex-based approaches, still common in industry, are inadequate for production-scale code datasets.

- **Post-processing rules as documented heuristics.** The rules for ignoring short secrets (<4 characters), requiring spaces in names (full names only), validating IP addresses with the `ipaddress` package, and filtering non-gibberish keys are simple but are explicitly documented with their rationale. This transparency allows downstream users to assess whether the redaction pipeline is appropriate for their use case — a sharp contrast to the black-box filtering in closed-access models.

The significance here is **normative as much as technical**: the paper argues through its methodology that PII detection should be a carefully evaluated component of the training pipeline, not a cursory regex pass. By releasing the annotated dataset (under gated access) and the StarEncoder model for fine-tuning, it provides a foundation for future work to improve upon rather than reinvent.

---

### Innovation 3: Fill-in-the-Middle as a General-Purpose Capability Multiplier, Not Just an Infilling Feature

FIM training was introduced by Bavarian et al. (2022) and adopted by InCoder (Fried et al., 2022) and SantaCoder (Ben Allal et al., 2023), but prior work evaluated it primarily on infilling-specific benchmarks: single-line completion, type prediction, and docstring generation. The implicit framing was that FIM adds *a new capability* (infilling) alongside left-to-right generation, but leaves standard code generation performance roughly unchanged.

StarCoder's evaluation suggests a more interesting relationship: **FIM training appears to improve performance on standard left-to-right code generation as well**, not just on infilling tasks. The evidence is circumstantial but suggestive. StarCoder achieves 33.6% pass@1 on HumanEval (standard left-to-right completion task, Table 12), substantially outperforming CodeGen-16B-Mono (29.3%) — a model of comparable size that was fine-tuned on Python but does not use FIM. On DS-1000 in completion mode (Table 13), StarCoder reaches 26.0% overall compared to code-cushman-001's 18.1%, a 44% relative improvement, despite DS-1000 being a left-to-right completion task for both models. And on the ODEX benchmark (Table 14), StarCoder substantially outperforms all baselines on open-domain coding queries, which are standard left-to-right generation tasks.

The paper does not explicitly claim that FIM improves left-to-right generation — it does not run the ablation of training without FIM — but the performance pattern across multiple standard completion benchmarks, compared to non-FIM models of similar scale, points toward this interpretation. If correct, the mechanism would be that FIM training forces the model to learn bidirectional dependencies in code (the middle of a function depends on both the prefix and the suffix, which often includes return type information, imports, and surrounding function definitions), and this richer understanding transfers to left-to-right generation by improving the model's internal representations of code structure. FIM becomes a **data-augmentation technique that improves code understanding generally**, not just a mechanism for supporting infilling at inference time.

This is a **conceptual reframing** rather than a proven claim, and it's one of the paper's most interesting speculative contributions. If future work confirms that FIM training improves left-to-right performance, it would change how researchers think about pretraining objectives for code — FIM wouldn't be an optional feature for models that need infilling, but a standard component of code pretraining, similar to how masked language modeling improved representations in BERT beyond what next-sentence prediction alone achieved.

---

### Innovation 4: The Attribution Tracing Tools as a New Category of Model Release Artifact

The paper introduces a class of tooling that, to our knowledge, has no precedent in the LLM literature: **post-generation attribution tracing integrated into a code editor**. The combination of a Bloom-filter-based membership checker (26 GB, approximately 3% of the training data size) and a BM25 search index over the full training corpus (preprocessed with 3-gram tokenization and Lucene's ASCIIFoldingFilter) creates a two-stage pipeline: the membership checker provides a rapid, approximate signal of whether a generated code snippet overlaps with training data; if a match is flagged, the full search index can locate the specific source file and repository.

This is intellectually distinctive because it addresses a legal and normative requirement (copyright compliance, the fair use argument that models should generate "novel content dissimilar to any copyrighted training data") with a concrete technical artifact that did not exist before. Prior work discussed the *need* for such tools (Henderson et al., 2023 argued that LLM developers should provide mechanisms for copyright compliance) but did not build them. The paper makes the construction of these tools part of the model release itself — the VSCode extension integrates them directly into the developer workflow.

The tool's design reveals a pragmatic understanding of the attribution problem:

- **Two-stage resolution.** The membership checker operates on 50-character strings (minimum resolution), which means it can quickly flag long code segments that are likely copied but won't trigger on short, generic snippets. This is appropriate: copyright concerns attach to substantial similarity, not to individual variable names or boilerplate patterns. The search index provides higher-resolution matching for cases that pass the Bloom filter.

- **No attempt at boilerplate detection.** The paper explicitly acknowledges that "both attribution tools do not attempt to distinguish between generic code (e.g., boilerplate) or protected content." This is a limitation (the tools will flag `import numpy as np` if it appears in the training set), but it reflects an honest assessment of what the technology can currently do. Distinguishing boilerplate from creative expression is a hard legal and technical problem; the tools provide raw evidence and leave interpretation to the user.

- **Public hosting.** The membership checker is hosted at a public URL (`http://stack.dataportraits.org/`), making it accessible without downloading the 26 GB artifact. This design choice reflects the project's commitment to transparency: anyone can check whether a code string appears in the training data, not just model developers.

This is a **normative innovation** — it establishes a new category of artifact that responsible model releases should include — rather than a technical one. The underlying technologies (Bloom filters, BM25) are decades old. The contribution is demonstrating that these tools *can and should* be built as part of the model development process, and releasing them as an integral part of the StarCoder package. Future open-access models that do not include similar attribution tooling will be measured against this precedent.

---

### Innovation 5: The "Natural Distribution" Training Data Principle as a Deliberate Governance Choice

Section 3.6 describes a seemingly mundane decision: train on data proportionally to its volume rather than up-sampling or down-sampling programming languages. This is presented as a community discussion that concluded with following "the natural distribution." But this decision is far from neutral — it is a **governance choice masquerading as a technical default**, and understanding why reveals a distinctive philosophical position.

The alternative — up-sampling low-resource languages to improve their performance — is common in multilingual NLP (e.g., sampling strategies that prevent high-resource languages from dominating training). The paper explicitly considered and rejected this approach. The reasoning is threefold: (1) popular languages have more users, so optimizing for them benefits more people; (2) after deduplication, high-resource languages had similar volumes anyway (44–87 GB), reducing the need for re-weighting; (3) data formats like JSON and YAML *were* down-sampled because their purpose is format learning, not content memorization.

The implicit argument is that **the natural distribution of permissively-licensed open-source code on GitHub is a legitimate and fair basis for allocating model capacity.** If Python has 60 GB of data and R has 0.30 GB (Table 1), then the model will be stronger at Python because more people write permissively-licensed Python code on GitHub — and that's a feature, not a bug. The model reflects the community of developers who chose to share their code under permissive licenses.

This framing has consequences that the paper acknowledges implicitly. Figure 2 (right) shows that low-resource languages like R, Racket, and Julia see limited improvement or even performance declines during training (R's pass@1 drops significantly between the 800B and 1000B checkpoints). The paper's investigation of R's performance variance (Table D.3) reveals that individual problem pass rates fluctuate wildly between checkpoints — HumanEval_0_has_close_elements goes from 197/200 passing at 600B to 5/200 at 1000B — suggesting the model is not stably learning R but rather oscillating in its ability to apply transferred knowledge from other languages. This is a direct consequence of the natural distribution decision: R gets too little data for stable learning, and the model's R performance is brittle.

The contrast with prior work is instructive. CodeGen-16B-Multi (Nijkamp et al., 2023) trained on a curated set of six languages (C, C++, Go, Java, JavaScript, Python) from BigQuery, essentially pre-selecting which languages get capacity. CodeGeeX (Zheng et al., 2023) selected 23 languages from Pile and CodeParrot plus additional Python, Java, and C++ data — a hybrid of selection and up-sampling. StarCoder's approach is different: **include everything above a volume threshold, weight by volume, and be transparent that this produces unequal performance**. It's a political choice about whose code matters, justified by appeal to user counts and data availability rather than researcher discretion.

This innovation is **conceptual**: it reframes data weighting from a purely technical optimization (maximizing average benchmark performance) to a governance decision that should be transparent and defensible. The paper doesn't argue this explicitly — the language in Section 3.6 is technocratic ("the largest amount of available data comes from popular programming languages and would, therefore, benefit a larger group of end-users") — but the implications for fairness, equity, and the politics of language inclusion in Code LLMs are substantial and underexplored.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The primary evaluation is conducted on the HumanEval (Chen et al., 2021) and MBPP (Austin et al., 2021) benchmarks for Python, the MultiPL-E translation of HumanEval into 18 additional languages (Cassano et al., 2023), and the DS-1000 benchmark for data science workflows (Lai et al., 2022). Additional evaluations cover security (Asleep at the Keyboard; Pearce et al., 2022), infilling (type prediction and docstring generation benchmarks from Pradel et al., 2020; Fried et al., 2022; Yee and Guha, 2023; Lu et al., 2021), natural language reasoning (GSM8K, MMLU, CoQA, HELM), and social bias/toxicity (StereoSet, RealToxicityPrompts). The training data is decontaminated against all evaluation benchmarks by removing files containing docstrings, solutions, or prompts (Section 5.2), yielding 558 removed Python files as the largest per-language count.

- **Base model(s).** The paper evaluates StarCoderBase (15.5B parameters, trained on 1T tokens across 80+ languages) and StarCoder (StarCoderBase fine-tuned on 35B Python tokens). Both are decoder-only Transformers with Multi-Query Attention and 8K context length, trained exclusively on permissively-licensed code from The Stack v1.2. The architecture is directly scaled from SantaCoder (1.1B; Ben Allal et al., 2023), representing a ~14× increase in parameter count and a ~10× increase in both training data volume and context length.

- **Metrics.** The primary metric throughout is **pass@k** (Chen et al., 2021): the fraction of benchmark problems solved, where a problem is considered solved if any one of k generated code samples passes all hidden test cases. The paper focuses on **pass@1** (single-attempt solve rate) for most comparisons, generating n = 200 samples per problem for open-access models (temperature 0.2 for pass@1, 0.8 for k > 1) and n = 20 samples for API models. For non-code-generation tasks, metrics vary: BLEU score for docstring generation (smoothed 4-gram; Papineni et al., 2002), exact match for type prediction, F1 score for CoQA, accuracy for MMLU and GSM8K, and StereoSet's ICAT score (combining language modeling and stereotype scores per Equation 1). For the Asleep at the Keyboard security benchmark, the metrics are Valid (percentage of syntactically valid completions) and Insecure (percentage of valid completions containing the target vulnerability).

- **Baselines.** The paper compares against five categories of models, with the key open-access baselines being: **CodeGen-16B-Multi** and **CodeGen-16B-Mono** (Nijkamp et al., 2023) — 16B-parameter models trained on The Pile plus BigQuery code, with Mono fine-tuned on a proprietary Python dataset; **CodeGeeX-13B** (Zheng et al., 2023) — 13B-parameter model trained on 23 languages; **SantaCoder-1.1B** (Ben Allal et al., 2023) — the project's prior 1.1B model; **InCoder-6B** (Fried et al., 2022) — a 6B model with FIM capabilities; and **LLaMA** (7B, 13B, 33B, 65B; Touvron et al., 2023) for natural language tasks. Closed-access baselines include **code-cushman-001** (12B; Chen et al., 2021) and **code-davinci-002** (175B; OpenAI) for code tasks, plus **PaLM** (540B; Chowdhery et al., 2022) and **LaMDA** (137B; Thoppilan et al., 2022) where applicable. The HELM evaluation (Table 27) additionally compares against 13 other models including GPT-NeoX-20B, BLOOM-176B, OPT-175B, and GLM-130B.

- **Generation budget / compute accounting.** For code generation benchmarks, all models are evaluated under a fixed sampling budget per problem: n = 200 samples for open-access models and n = 20 for API models. The paper does not vary inference compute budget as an experimental axis — the focus is on comparing model quality at a fixed per-problem sampling cost. This is a notable difference from the "compute-optimal test-time scaling" style of analysis (the paper does not ask "how does performance change if we give StarCoder more samples?"). For the perplexity evaluation with long contexts (Section 6.4, Table 21), the comparison is between 2K and 8K token window sizes, measuring how additional context reduces perplexity on held-out GPL repositories. Carbon emissions from training are reported separately (Section 5.7) but not factored into evaluation comparisons.

- **Cross-validation / statistical protocol.** No cross-validation or statistical significance testing is reported. The primary benchmarks (HumanEval, MBPP, DS-1000) have fixed test sets (164, 500, and 1,000 problems respectively), and all models are evaluated on the same set of problems. For pass@k estimation, the paper uses the unbiased estimator from Chen et al. (2021): $\text{pass@}k = \mathbb{E}_{\text{Problems}}\left[1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}\right]$, where n is the total number of samples generated and c is the number of correct samples. The paper does not report confidence intervals or standard errors, and the decontamination protocol (removing files containing benchmark content) is the primary mechanism for preventing evaluation leakage rather than statistical safeguards.

### Main Quantitative Results

#### Python Code Generation: HumanEval and MBPP

The headline result is that **StarCoder achieves the highest HumanEval and MBPP pass@1 among all open-access models**, and **matches or exceeds the closed-access code-cushman-001** (Table 12).

On HumanEval (Table 12): StarCoder reaches **33.6%** pass@1, essentially tied with code-cushman-001 (33.5%) and ahead of all other open-access models: CodeGen-Mono-16B (29.3%), CodeGeeX-13B (22.9%), CodeGen-Multi-16B (18.3%), and SantaCoder-1.1B (18.0%). StarCoderBase — without Python-specific fine-tuning — achieves 30.4%, which already exceeds every open-access multi-language model and trails only CodeGen-Mono (a Python specialist) among open models. The larger closed-access code-davinci-002 (175B parameters, approximately 11× larger than StarCoder) reaches 45.9%, establishing the performance ceiling at the time of evaluation.

On MBPP (Table 12): StarCoder reaches **52.7%**, substantially outperforming code-cushman-001 (45.9%) and all open-access models. CodeGen-Mono-16B scores 35.3%, CodeGeeX-13B scores 24.4%, and SantaCoder-1.1B scores 35.0%. The gap between StarCoder and code-cushman-001 on MBPP (52.7% vs. 45.9%, a 14.8% relative advantage) is notably larger than on HumanEval, suggesting that StarCoder's training data and FIM objective may be particularly suited to the shorter, more constrained problems in MBPP compared to the longer-form problems in HumanEval. StarCoderBase at 49.0% already substantially exceeds code-cushman-001, meaning the base model — before any Python-specific fine-tuning — is the stronger model on this benchmark.

A critical context point: HumanEval contains 164 problems and MBPP contains approximately 500 (the exact number varies by evaluation setup). The difference of a few percentage points on HumanEval (33.6% vs. 33.5%) corresponds to a difference of roughly 1 problem, making the "matching" claim statistically fragile. The MBPP advantage is larger in both relative and absolute terms and thus more robust.

#### Python Data Science: DS-1000

On DS-1000 (Table 13), which consists of 1,000 realistic data science problems across seven Python libraries (Matplotlib, NumPy, Pandas, PyTorch, SciPy, Scikit-Learn, TensorFlow), **StarCoder achieves 26.0% overall pass@1 in completion mode, substantially outperforming all other models**. code-cushman-001 reaches 18.1%, CodeGen-16B-Mono reaches 11.7%, and InCoder-6B reaches 7.4%. The advantage is consistent across individual libraries: StarCoder leads on Matplotlib (51.7% vs. 40.7% for code-cushman-001), NumPy (29.7% vs. 21.8%), Pandas (11.4% vs. 7.9%), PyTorch (21.4% vs. 12.4%), SciPy (20.2% vs. 11.3%), Scikit-Learn (29.5% vs. 18.0%), and TensorFlow (24.5% vs. 12.2%). The performance pattern is library-dependent — StarCoder is strongest on Matplotlib (51.7%) and weakest on Pandas (11.4%) — reflecting both the varying difficulty of the library-specific tasks and the representation of each library's patterns in the training data.

In insertion (FIM) mode, StarCoder achieves 25.4% overall, nearly identical to completion mode (26.0%), demonstrating that FIM training does not degrade standard left-to-right performance when the model is evaluated in FIM mode. SantaCoder-1.1B shows a larger gap between completion (5.7%) and insertion (9.3%), suggesting that FIM capability improves with scale — the 15.5B model has learned to use bidirectional context more effectively than the 1.1B model.

The paper highlights an important pattern (Section 6.1.2): "model performance on HumanEval and MBPP benchmarks does not always correlate with performance on the more realistic DS-1000 benchmarks." CodeGen-Mono slightly outperforms code-cushman-001 on HumanEval (29.3% vs. 33.5%) — wait, I misread: CodeGen-Mono is 29.3% and code-cushman-001 is 33.5% on HumanEval, so code-cushman-001 is actually better. The claim should be: CodeGen-Mono performs reasonably on HumanEval and MBPP but drops sharply on DS-1000 (11.7%), while the StarCoder models maintain strong performance across both types of benchmarks. This underscores the value of evaluating on diverse problem distributions rather than relying on a single benchmark.

#### Open-Domain Coding: ODEX

On the ODEX benchmark (Table 14), which tests code generation for both closed-domain (built-in Python functions) and open-domain (external libraries) queries across four natural languages (English, Spanish, Japanese, Russian), **StarCoder and StarCoderBase substantially outperform all baselines on open-domain coding queries**. On the English subset, StarCoderBase achieves 46.5% overall pass@1 (40.7% open-domain, 53.0% closed-domain) compared to the next-best SantaCoder at 37.7%. The performance advantage is concentrated in the open-domain queries: StarCoderBase achieves 40.7% on English open-domain vs. SantaCoder's 30.9%, while the closed-domain gap is smaller (53.0% vs. 45.1%).

A particularly interesting pattern in Table 14 is the **cross-lingual generalization**: StarCoder achieves strong performance on non-English queries despite being trained primarily on English-centric GitHub data. On Russian queries, StarCoder reaches 50.4% overall vs. code-davinci-001's 43.2%. On Japanese queries, StarCoder reaches 44.2% vs. code-cushman-001's 25.7%. The paper notes that "both StarCoder and StarCoderBase models generally exhibit smaller gaps between open- and closed-domain queries than other baseline models," suggesting that the training data diversity (80+ languages, natural language text from issues and notebooks) produces more generalized code generation capabilities rather than narrow memorization of specific library patterns.

#### Multi-Language Evaluation: MultiPL-E Across 19 Languages

Table 15 reports pass@1 on MultiPL-E (the HumanEval problems translated into 18 additional programming languages) for StarCoder, StarCoderBase, CodeGen-16B-Multi, CodeGeeX-13B, and code-cushman-001. The central claim is that **StarCoderBase outperforms every open-access multi-language Code LLM across all 19 languages, and is competitive with code-cushman-001 on most languages** (Section 6.2.1).

The detailed performance landscape (Table 15):

- **Languages where StarCoderBase substantially (>5 percentage points) exceeds code-cushman-001:** Julia (21.09% vs. 1.54%), Racket (11.77% vs. 7.05%), and Lua (26.61% vs. 26.24% — wait, this is 0.37 points, but the paper claims >5% for Julia only). Actually, the paper states that "code-cushman-001 outperforms StarCoderBase by more than 5% on C++, Java, Ruby, and Swift, and StarCoder outperforms code-cushman-001 by more than 5% on Julia." Checking the numbers: StarCoder scores 23.02% on Julia vs. code-cushman-001's 1.54%, a 14× gap — this is the standout result.

- **Languages where code-cushman-001 substantially exceeds StarCoderBase:** C++ (30.59% vs. 30.56% — negligible), Java (31.90% vs. 28.53%, a 3.37 point gap), Ruby (28.63% vs. 17.25%, an 11.38 point gap), and Swift (22.12% vs. 16.74%, a 5.38 point gap). The Ruby gap is particularly large and notable because Ruby is a high-resource language in the training data (6.81 GB, Table 2, more than Go at 23.78 GB — actually Ruby has 6.81 GB, so perhaps the issue is data quality rather than quantity).

- **StarCoder vs. StarCoderBase:** Despite being fine-tuned on Python only, StarCoder slightly outperforms StarCoderBase on several non-Python languages: C++ (31.55% vs. 30.56%), Java (30.22% vs. 28.53%), Julia (23.02% vs. 21.09%), PHP (26.08% vs. 26.75% — StarCoderBase is better here), Python (33.57% vs. 30.35%), and TypeScript (32.29% vs. 32.15%). The paper notes this is surprising: "At this time, we can only speculate on why this is the case, and further investigation of the open training data is likely to help shed light on this finding." Possible explanations include transfer learning from Python (languages with similar syntax benefit), or the additional Python training exposing the model to higher-quality general-purpose code patterns that transfer across languages.

- **Low-resource language performance:** CodeGen-16B-Multi, which reportedly does not include several languages in its training set, achieves non-zero performance on C# (8.24%), Lua (8.50%), PHP (8.37%), and TypeScript (20.07%), demonstrating cross-lingual transfer. TypeScript's high performance is expected because "simple JavaScript functions often type-check with TypeScript by design." Similarly, StarCoder achieves 22.74% on Swift despite Swift being excluded from training (Section 3.1), suggesting transfer from syntactically similar languages.

#### Security Evaluation: Asleep at the Keyboard

Table 16 reports security evaluation on the Asleep at the Keyboard benchmark (40 scenarios across 23 in C and 17 in Python, testing 18 CWEs from MITRE's Common Weakness Enumeration). StarCoderBase achieves **98.70% valid code in insertion mode and 85.50% in completion mode**, with insecure rates of 35.87% and 39.77% respectively among valid completions. Comparatively: InCoder-6B achieves 85.40% valid in insertion mode with 34.31% insecure; CodeGen-16B-Multi achieves 95.50% valid in completion mode with 43.25% insecure; code-cushman-001 achieves 96.40% with 42.32% insecure.

The key finding: **StarCoderBase generates valid code more reliably than alternatives (98.70% in insertion mode) and has the lowest insecure generation rate among models with >95% valid code (35.87% vs. 42.32% for code-cushman-001).** InCoder-6B has a slightly lower insecure rate (34.31% insertion) but much lower validity (85.40%), so the lower insecurity may be an artifact of generating less code overall. The insertion format substantially improves validity for StarCoderBase (85.50% → 98.70%), suggesting that FIM training helps the model understand the security-relevant context (prefix and suffix) more effectively than left-to-right generation.

Table D.2 extends this comparison to code-davinci-002: the 175B model achieves 98.40–98.60% valid but 42.70–42.99% insecure — worse security performance than StarCoderBase (35.87% insecure in insertion mode). This is a notable result: a model trained with transparent data governance and explicit PII redaction generates fewer security vulnerabilities than a much larger closed-access model. The paper wryly observes that "the significantly larger size of code-davinci-002 does not appear to improve its performance at generating secure code."

#### Fill-in-the-Middle Benchmarks

**Single-line infilling (Table 17).** On the single-line FIM benchmark (exact line match on HumanEval solutions translated to Java, JavaScript, and Python), StarCoder achieves **0.73 (Java), 0.74 (JavaScript), and 0.62 (Python)** in line exact match. SantaCoder-1.1B achieves 0.62, 0.60, 0.44; InCoder-6B achieves 0.49, 0.51, 0.31. The ~14× scale increase from SantaCoder yields a 0.11–0.18 absolute improvement, with the largest gain on Python (0.44 → 0.62).

**Python return type prediction (Table 18).** On predicting return type annotations for Python functions from GitHub, StarCoderBase achieves **86.6% F1 overall and 77.4% F1 on non-None types.** SantaCoder achieves 78.5% and 66.9%; InCoder-6B achieves 46.8% and 59.1%. The near-perfect overall F1 (86.6%) is partly driven by trivial None-type predictions (the model can often guess `-> None` correctly for functions that return nothing), but the 77.4% non-None F1 demonstrates genuine type inference capability. However, the paper notes a critical limitation: "as the functions in this evaluation set were taken from GitHub repositories, they may overlap with the training data for SantaCoder and the StarCoder models" — a direct admission that this benchmark may be contaminated, weakening the evidential value of the result.

**TypeScript type prediction (Table 19).** Using the evaluation framework from Yee and Guha (2023), which evaluates on JavaScript packages that have never been translated to TypeScript (reducing contamination risk), StarCoderBase outperforms InCoder-6B on all metrics: 38.3% of packages fully type-check (vs. 23.4%), 78.0% of files have no type errors (vs. 75.1%), and 45.2% of annotations are trivial (e.g., `any`) vs. InCoder's 47.9%. The lower trivial-annotation rate combined with higher type-checking success implies that StarCoderBase generates more precise, non-trivial types that actually type-check.

**Python docstring generation (Table 20).** On the CodeXGLUE code summarization task (generating docstrings for Python functions, evaluated with smoothed BLEU-4), StarCoder achieves **21.99 BLEU**, StarCoderBase achieves 21.38, SantaCoder achieves 19.74, and InCoder-6B achieves 18.27. The paper again cautions about training set overlap — these functions come from public GitHub repositories that may appear in the training data.

#### Performance Trajectory Through Training

Figure 2 tracks StarCoderBase performance (MultiPL-E pass@1) at five checkpoints: 200B, 400B, 600B, 800B, and 1000B (final) tokens. The left panel plots pass@1 against log-dataset-size for each checkpoint, with linear fits (excluding the leftmost point where "we expect the linear dependence to break due to transfer learning"). The goodness of fit increases from R² = 0.399 at 600B to R² = 0.510 at 1000B, suggesting that the relationship between data volume and performance is becoming more linear as training progresses — larger datasets produce more consistent improvements.

The right panel of Figure 2 shows per-language performance curves. **High-resource languages (Python, Java, JavaScript, C++) show consistent improvement throughout training**, with the slopes suggesting further improvement with additional tokens. **Low-resource languages show mixed and sometimes negative trends**: R's pass@1 drops significantly between 800B and 1000B checkpoints. The paper's manual inspection of R's completions (Table D.3) reveals that "the pass rate between different checkpoints varies in what appears to be a completely uncorrelated manner" — individual problems show wild swings (e.g., HumanEval_0_has_close_elements: 197/200 passing at 600B, 5/200 at 1000B). The failures are caused by "minor mistakes, e.g., not taking the absolute value when computing GCD, not converting a string to a character array, or not checking edge cases." This suggests that for low-resource languages, the model is not stably learning the language but rather oscillating — at some checkpoints, transferred knowledge from higher-resource languages correctly solves the problem; at others, minor syntactic errors cause failures.

#### Perplexity with Long Contexts

Table 21 compares StarCoderBase perplexity on held-out GPL repositories when using 2K vs. 8K token windows. Across all 10 languages evaluated (C++, C#, C, Go, Java, JavaScript, PHP, R, Ruby, Rust), **the 8K window consistently produces lower perplexity**. For example: C++ drops from 2.01 to 1.79; JavaScript drops from 1.98 to 1.68; PHP drops from 1.73 to 1.43. The average perplexity reduction across languages is approximately 0.21 (from 1.80 to 1.59), representing an 11.7% relative improvement. This directly demonstrates that StarCoderBase leverages the additional context — it is not merely architecturally capable of 8K context, but genuinely benefits from it when making predictions.

The evaluation is designed to be conservative: perplexity is always measured on the final 1K tokens of each 8K chunk, so both conditions predict the same tokens. The only difference is whether the model can see 1K tokens of previous context (2K condition) or 7K tokens (8K condition). Since the chunks span repository file boundaries, the 8K window likely captures cross-file dependencies (imported modules, parent class definitions) that the 2K window misses.

#### Natural Language and Reasoning Evaluation

**GSM8K math reasoning (Table 22).** StarCoderBase achieves **21.5% with Program-Aided Language models (PAL; generating Python code as reasoning steps) vs. 8.4% with Chain-of-Thought (CoT; generating natural language reasoning).** With majority voting over 100 PAL generations, performance rises to 26.0% (PAL) and 31.2% (PAL+maj1@40 after temperature tuning). CodeGen-Mono-16B achieves 13.1% with PAL and 22.4% with majority voting; CodeGen-Multi-16B achieves 8.6% and 15.2%. StarCoderBase substantially outperforms both CodeGen variants, but trails LLaMA-33B (38.7% PAL, 35.6% CoT) and LLaMA-65B (50.9% CoT). The PAL > CoT pattern is consistent with prior findings (Gao et al., 2022) and reflects that Code LLMs are more reliable when generating executable code than when performing multi-step natural language reasoning.

**MMLU (Table 23).** StarCoderBase achieves **34.2% 5-shot accuracy**, outperforming CodeGen-Multi-16B (27.8%) and GPT-NeoX-20B (32.9%), but trailing LLaMA-7B (35.1%) and LLaMA-13B (46.9%). The model outperforms GPT-NeoX despite being ~25% smaller and trained primarily on code rather than natural language, which the paper partially attributes to the ~20% of training tokens that are natural language (GitHub issues, Markdown, Jupyter text).

**CoQA (Table 24).** StarCoderBase achieves **0.67 F1 zero-shot**, ahead of CodeGen-Multi-16B (0.59) but behind LLaMA-7B (0.71), LLaMA-13B (0.73), and GPT-NeoX-20B (0.73). The conversational format of CoQA (answer a series of interconnected questions about a passage) is far from the model's training distribution (GitHub issue discussions are structurally different from CoQA's passages), making the competitive performance notable even if below LLaMA.

**Social bias: StereoSet (Table 25).** StarCoderBase achieves the **lowest stereotype scores** across all four bias domains (Gender: 58.76%, Profession: 53.24%, Race: 56.48%, Religion: 55.69%) compared to LLaMA-13B (63.40% overall) and CodeGen-Multi-16B (61.29% overall). The ideal stereotype score is 50% (model is equally likely to prefer stereotypical and anti-stereotypical completions). StarCoderBase's ICAT score (which combines language modeling and stereotype scores, where higher is better) is 76.65 overall, vs. 67.55 for CodeGen-Multi-16B and 64.14 for LLaMA-13B. The paper notes that StarCoderBase's language modeling scores (86.18% overall) remain competitive, suggesting that "StarCoderBase's lower stereotype scores are not simply due to worse language modeling."

**Toxicity: RealToxicityPrompts (Table 26).** Using a RoBERTa-based toxicity classifier, 0.42% of StarCoderBase responses are flagged as toxic, compared to 0.74% for LLaMA-13B and 0.21% for CodeGen-Multi-16B. Using an offensive word list, 1.12% of StarCoderBase responses contain potentially offensive tokens, vs. 1.43% for LLaMA-13B and 0.82% for CodeGen-Multi-16B. StarCoderBase sits between the two baselines — less toxic than LLaMA-13B but more toxic than CodeGen-Multi-16B.

**HELM reasoning (Table 27).** StarCoderBase is compared against 13 other models on 8 natural language reasoning tasks from HELM. **StarCoderBase substantially outperforms all other open-access models** (BLOOM-176B, OPT-175B, GPT-NeoX-20B, GLM-130B, UL2-20B, OPT-66B, YaLM-100B, T5-11B) and achieves competitive performance with much larger closed-access models. On bAbI (synthetic reasoning), StarCoderBase achieves 50.4% vs. code-davinci-002's 68.6%; on Dyck (synthetic language tasks), it achieves 85.4% vs. code-davinci-002's 80.5%; on Legal Support, it achieves 53.2% vs. text-davinci-003's 62.2%. The paper speculates that "the mixture of code and natural language in the training data contributes to the model's strong performance on these reasoning tasks."

#### Qualitative Evaluation Insights

Appendix E demonstrates three interaction modes using the pretraining templates:

1. **Jupyter notebook format:** The model can act as a code interpreter by predicting output cells (showing correct predictions for `is_prime(3)` → `True` and list comprehension results).

2. **Git commits format:** The model performs code editing: given `<commit_before>def fibonacci(n):<commit_msg>add type hints to function<commit_after>def`, it generates `def fibonacci(n: int) -> list[int]:`.

3. **GitHub issues format:** The model responds to technical questions in a conversational format, providing plausible debugging advice.

In Section E.3, the paper demonstrates that **prompt engineering with StarCoder's metadata tokens can boost HumanEval performance from 33.6% to 40.8%** — a 7.2 percentage point improvement — simply by prepending `<filename>solutions/solution_1.py\n# Here is the correct implementation of the code exercise` at temperature 0.1. The same prompt hurts CodeGen-16B-Mono (reducing it from 29.3% to 28.10%) and has negligible impact on StarCoderBase, suggesting that the Python fine-tuning made StarCoder more responsive to filename and comment cues about solution quality.

### Ablation Studies and Robustness Checks

The paper is notably **sparse** on formal ablation studies. The evaluation compares StarCoder and StarCoderBase against external baselines but does not systematically isolate the contribution of individual design choices (e.g., training without FIM, without PII redaction, with different data weightings). The following are the closest approximations to robustness checks in the paper:

- **StarCoderBase vs. StarCoder (Table 12, Table 15):** The comparison between the base model and the Python-fine-tuned variant serves as a de facto ablation of Python-specific fine-tuning. On HumanEval, fine-tuning improves performance from 30.4% to 33.6% (+3.2 points). On MBPP, from 49.0% to 52.7% (+3.7 points). On MultiPL-E (Table 15), the effect is mixed: StarCoder slightly outperforms StarCoderBase on most languages (e.g., C++: 31.55% vs. 30.56%; Java: 30.22% vs. 28.53%) but StarCoderBase is better on some (Go: 21.47% vs. 17.61%; Lua: 26.61% vs. 23.89%). This suggests that Python fine-tuning causes modest improvements on Python and does not catastrophically degrade multi-language performance — a robustness check on the transfer learning dynamics.

- **Performance through training (Figure 2):** Tracking performance at 200B-token intervals serves as an ablation of training duration. The key finding is that high-resource languages continue to improve, while low-resource languages show instability. This is evidence that the natural distribution data weighting benefits popular languages at the expense of low-resource ones, and that further training would likely widen this gap.

- **2K vs. 8K context (Table 21):** This is a direct ablation of context length, holding all other variables constant. The consistent perplexity reduction demonstrates that the 8K context window is not merely an architectural capability but a genuine performance improvement.

- **Completion vs. insertion on DS-1000 (Table 13):** For models supporting FIM, comparing completion mode to insertion mode tests whether FIM training improves or degrades standard left-to-right performance. StarCoder achieves 26.0% completion vs. 25.4% insertion — essentially identical — suggesting no degradation. SantaCoder-1.1B shows the opposite pattern (5.7% completion vs. 9.3% insertion), implying that FIM capability improves with scale.

- **NER vs. regex for PII detection (Table 8):** While not a model ablation, this is a direct comparison of the two PII detection approaches, justifying the choice to invest in a trained NER model. The regex approach achieves only 6.74% F1 on keys, making it essentially non-functional for one of the most critical PII types.

- **Pseudo-labeling ablation (Tables 8 and 9):** The comparison of NER trained only on annotated data vs. NER trained with pseudo-labeling pre-training shows consistent improvements across all PII types, with the largest gain on keys (56.66% → 70.41% F1). This validates the pseudo-labeling strategy.

**Missing ablations that would have strengthened the paper:**

- **FIM vs. no-FIM training.** The paper claims implicitly that FIM contributes to performance (through the consistent insertion mode results and the competitive left-to-right performance), but never trains a StarCoder variant without FIM for comparison. This is an understandable omission given the compute cost, but it means the contribution of FIM to standard code generation is speculative.

- **Data weighting ablation.** The natural-distribution weighting is a deliberate choice, but no experiment tests an alternative (e.g., up-sampling low-resource languages). The instability of low-resource language performance suggests this is a consequential decision, but no counterfactual is provided.

- **PII redaction ablation.** The paper does not train a version without PII redaction to test whether the redaction process degrades performance (e.g., by removing useful training signal from names and emails). The performance results are strong, suggesting no major degradation, but this is unverified.

- **Scale ablation.** The comparison to SantaCoder (1.1B, same architecture family) provides a single scale point, but intermediate scales (e.g., 3B, 7B) would reveal whether the architecture scales smoothly or has thresholds where certain capabilities emerge. The paper does not include scaling law analysis analogous to Kaplan et al. (2020) or Hoffmann et al. (2022).

### Critical Assessment

#### Claim 1: StarCoder outperforms every open LLM for code that supports multiple programming languages.

**Supported, with nuance.** Table 15 shows that StarCoderBase outperforms CodeGen-16B-Multi and CodeGeeX-13B (the only open-access multi-language Code LLMs at comparable scale) on all 19 MultiPL-E languages. The margins are often substantial (Julia: 21.09% vs. 0.29% for CodeGen; Racket: 11.77% vs. 0.66%). However, the claim's force is limited by the **small number of open-access multi-language models at this scale**: there are effectively only three (StarCoderBase, StarCoder, CodeGen-Multi-16B, and CodeGeeX-13B). "Every open LLM for code that supports multiple programming languages" inflates the apparent breadth of comparison. The paper does **not** compare against potential multi-language variants of InCoder or SantaCoder scaled up to 15B parameters because those models do not exist. The claim is technically true but the competitive landscape is sparse.

#### Claim 2: StarCoder matches or outperforms the OpenAI code-cushman-001 model.

**Supported, with variance by benchmark and language.** On HumanEval (Table 12), StarCoder (33.6%) essentially ties code-cushman-001 (33.5%). On MBPP (Table 12), StarCoder outperforms by a clear margin (52.7% vs. 45.9%). On DS-1000 (Table 13), StarCoder dominates (26.0% vs. 18.1%). On MultiPL-E (Table 15), the outcome is language-dependent: StarCoderBase outperforms on Julia and is competitive on most languages, but lags significantly on Ruby (17.25% vs. 28.63%) and Swift (16.74% vs. 22.12%). The "matches or outperforms" characterization is valid at the aggregate level but masks substantial per-language variation. A fairer summary: **StarCoder is competitive with code-cushman-001 on Python and multi-language benchmarks, with specific strengths (Julia, MBPP, DS-1000) and specific weaknesses (Ruby, Swift).**

A critical unexamined factor: code-cushman-001 is a model released in 2021 and deprecated at the time of writing — it represents a two-year-old capability baseline from a company that has since released substantially more capable models (code-davinci-002, GPT-3.5, GPT-4). Matching a two-year-old model is a lower bar than the rhetoric of "matches the closed-access frontier" suggests. The comparison to code-davinci-002 (Tables D.1, D.2) shows StarCoder substantially behind on code generation (e.g., 30.56% vs. 48.44% on MultiPL-E C++) but comparable on security (better, in fact: 35.87% insecure in insertion mode vs. 42.70% for code-davinci-002). The paper is transparent about these results but the headline claim focuses on the more favorable comparison.

#### Claim 3: When fine-tuned on Python, StarCoder substantially outperforms existing LLMs that are also fine-tuned on Python.

**Supported on HumanEval and MBPP, but with a critical caveat about training data transparency.** CodeGen-Mono-16B is the primary comparison: StarCoder outperforms it on HumanEval (33.6% vs. 29.3%) and MBPP (52.7% vs. 35.3%). However, the paper explicitly notes that CodeGen-Mono's Python fine-tuning data is **not publicly available** (Section 2, "Salesforce released CodeGen-Mono-16B without disclosing a proprietary Python dataset"). This means that CodeGen-Mono is not a "fair" baseline in the sense of a controlled comparison — we do not know the size, composition, or quality of its fine-tuning data, and it is possible that StarCoder simply used more or better Python data. The paper's commitment to transparency makes this point self-reinforcing (CodeGen-Mono is opaque in a way that makes it impossible to diagnose the performance gap), but it also weakens the causal claim: we cannot attribute the improvement to model or training design rather than data quality.

#### Claim 4: StarCoder takes important steps towards a safe open model release through PII redaction, attribution tools, and licensing.

**Supported, but with acknowledged limitations that the paper itself documents.** The PII detection pipeline is the most rigorously evaluated component: Tables 5, 8, and 9 report precision and recall for each entity type, and the comparison to regex approaches (Table 8) demonstrates genuine improvement. However, the paper acknowledges (Section 10.2) that "StarCoder may still produce PII" and that the annotation dataset has limitations (keys have only 308 training instances; IDs were excluded entirely). The attribution tools (Section 9) are novel and functional but do not distinguish boilerplate from protected content — a limitation the paper explicitly owns ("Both attribution tools do not attempt to distinguish between generic code (e.g., boilerplate) or protected content"). The OpenRAIL-M license is described as "more commercially viable" but specific terms are not evaluated empirically — the paper reports no study of whether the license indeed increases commercial adoption. The "important steps" framing is appropriate: these are **first-generation tools** with measurable but incomplete effectiveness, not solved problems.

#### Claim 5: The 8K context length enabled by FlashAttention provides genuine benefits.

**Supported by perplexity evidence (Table 21) but not by downstream task evaluation.** The perplexity reduction is clear and consistent across languages. However, the paper does **not** evaluate whether this perplexity improvement translates to better performance on downstream tasks — there is no HumanEval or MBPP benchmark experiment comparing 2K vs. 8K context during generation. The paper could have compared StarCoder's performance with truncated context (2K) to full context (8K) on code generation tasks, but this experiment is not reported. The claim that 8K context "enables conditioning on long files and repository-level code" is architecturally true but the practical benefit beyond perplexity is unmeasured.

#### Claim 6: FIM training produces a model that is simultaneously capable of left-to-right generation and infilling without performance trade-offs.

**Supported for left-to-right performance (StarCoder's strong HumanEval and MBPP results), but not through controlled ablation.** The DS-1000 insertion vs. completion comparison (Table 13) shows that FIM mode does not degrade performance — StarCoder's insertion score (25.4%) essentially equals its completion score (26.0%). However, the paper does not train a StarCoder variant without FIM to isolate FIM's contribution to left-to-right performance. The implicit claim that FIM training *improves* left-to-right generation (as suggested by the comparison to non-FIM CodeGen-Mono) cannot be separated from other model differences (architecture, training data, tokenizer). The evidence is circumstantial.

#### Genuine Weaknesses

1. **No formal ablations.** The paper's primary mode of analysis is comparison against external baselines, not controlled variation of the StarCoder architecture or training pipeline. Factors like FIM training, MQA, the 8K context length, the specific PII redaction pipeline, and the data weighting strategy are all bundled together, making it impossible to attribute performance to individual components. This is understandable for a project of this scale (the compute cost of ablations would be prohibitive) but limits the scientific contribution to a system demonstration rather than a controlled experiment.

2. **Small test sets for some benchmarks.** HumanEval has only 164 problems. A 3-percentage-point difference (e.g., StarCoder's 33.6% vs. code-cushman-001's 33.5%) corresponds to a difference of roughly 1 problem — a razor-thin margin. The paper does not report confidence intervals, making it impossible to assess whether the "matching" claim on HumanEval is statistically robust. The MBPP margin (52.7% vs. 45.9%) is larger and more reliable.

3. **Training set contamination risk on auxiliary benchmarks.** The paper explicitly acknowledges that the return type prediction and docstring generation benchmarks (Tables 18, 20) may overlap with training data, weakening their evidentiary value. The decontamination protocol was applied to HumanEval, MBPP, APPS, GSM8K, and DS-1000 but not to these auxiliary benchmarks — an asymmetry that makes those results harder to interpret.

4. **Single evaluation point for context length.** The 2K vs. 8K perplexity comparison (Table 21) is the only experiment quantifying the benefit of long context, and it is a perplexity metric rather than a downstream task metric. The claim that 8K context "enables repository-level code understanding" is not directly tested — there is no experiment where the model must use cross-file context to generate correct code.

5. **No temporal held-out evaluation.** All evaluations use static benchmarks that existed at the time of The Stack v1.2 collection. The paper does not test on code repositories created after the training data cutoff to measure genuine generalization vs. memorization. The decontamination protocol removes exact matches to benchmark content, but does not guard against the model having seen structurally similar problems during training.

6. **The HumanEval prompt engineering result (40.8% with a specific prefix) is not explained.** The 7.2 percentage point improvement from adding `<filename>solutions/solution_1.py\n# Here is the correct implementation of the code exercise` is substantial and model-specific (CodeGen-Mono is hurt by the same prompt). The paper reports this as an observation but does not investigate *why* StarCoder responds so strongly to a filename and comment — is it a spurious correlation in the fine-tuning data? An artifact of the `<filename>` token's association with high-quality solutions? This result raises questions about the robustness of the HumanEval evaluation that are not addressed.

#### Missing Experiments

- **Scaling law analysis.** The comparison to SantaCoder (1.1B) provides two points on the scale curve, but intermediate model sizes (e.g., 3B, 7B) are absent. The paper cannot answer: is the 15.5B scale necessary for the observed capabilities, or would a 7B model achieve similar performance with the same data pipeline?

- **Context length ablations on downstream tasks.** Does 8K context improve code generation accuracy compared to 2K context on tasks requiring cross-file reasoning? The paper demonstrates perplexity improvement but not task-level improvement.

- **FIM ablation.** Train a 1.1B or 3B model with and without FIM to isolate FIM's contribution to left-to-right generation performance.

- **PII redaction ablation.** Train a small model on data with and without PII redaction to measure whether the redaction process degrades code generation performance.

- **Language-specific data scaling.** The natural-distribution weighting is justified but not tested against alternatives. A controlled experiment up-sampling a mid-resource language (e.g., R) and measuring the performance impact would validate or challenge the natural-distribution principle.

- **Temporal generalization.** Evaluate on GitHub repositories created after The Stack v1.2's collection cutoff to measure genuine generalization vs. memorization.

## 6. Limitations and Trade-offs

### 6.1 The PII Redaction Pipeline Remains Incomplete and Leaves Critical Gaps

**The assumption or constraint.** The paper invests substantially in PII detection (Section 4, 800 GPU-hours of inference) but acknowledges multiple categories of residual risk. The paper explicitly states that IDs were excluded from model training "due to low annotation quality" (Section 4.3) with precision and recall both near 50% (Table 5). Usernames were excluded because pseudo-labeling "did not show significant improvement" (Section 4.3), leaving an F1 of only 61.49% (Table 9). Even for the five detected entity types, performance is uneven: keys reach only 70.41% F1 even after pseudo-labeling (Table 8), meaning roughly 30% of API keys and secrets in the training data are not masked. The paper further acknowledges (Section 10.2): "Despite our best efforts to remove PII..., StarCoder may still produce PII."

**The consequence.** A model trained on inadequately-redacted data can memorise and regenerate PII at inference time. For keys (70.41% F1), the 30% of unmasked secrets in the training data become part of the model's learnable distribution — and since keys are high-entropy unique strings, they are particularly susceptible to memorisation. For the excluded categories (IDs, usernames), there is no redaction at all, meaning the model is trained directly on whatever identifiers appeared in the 80+ programming languages of The Stack. The paper's license "restricts use that aims to generate or disseminate PII with the purpose of harming others" (Section 10.2), but this is a legal restriction on users, not a technical prevention mechanism — the model may still generate PII inadvertently, and the license does not protect the individuals whose data was memorised. For GDPR compliance, the paper's approach of redacting some but not all PII categories creates a grey area: the presence of a PII detection pipeline demonstrates good-faith effort, but the known gaps (IDs, usernames, the false-negative rate on keys) mean the model is not provably PII-free.

**What evidence exists in the paper.** Tables 5, 8, and 9 provide per-category precision and recall. The key evidence of incompleteness: IDs were excluded from model training entirely (Table 5 shows 1,702 annotations collected but 53% recall and 51% precision — effectively random). Usernames were excluded from the final redaction pipeline after pseudo-labeling showed no significant improvement (61.49% F1, Table 9). For the remaining categories, the F1 scores range from 70.41% (keys) to 98.15% (emails), all below perfect. The paper does **not** report a systematic study of how frequently StarCoder generates PII at inference time — the risk is characterised qualitatively in Section 10.2 but not measured quantitatively. The GitHub issues section (Section 4.3, "Github issues") applies NER-based redaction only for names, relying on regex for keys, IP addresses, and emails — an approach the paper's own Table 8 shows is catastrophically poor for keys (6.74% F1).

**Mitigation status.** The paper partially addresses the gaps through its pseudo-labeling augmentation (improving key F1 from 56.66% to 70.41%) and through post-processing heuristics (minimum length thresholds, trigger-word filtering, IP address validation). However, these are acknowledged to be incomplete. The paper explicitly calls for "further research and development of PII redaction technology" (Section 10.2) and releases the annotated dataset under gated access to facilitate this. The excluded categories (IDs, usernames) receive no mitigation — they are simply not redacted. For a practitioner deploying StarCoder in a GDPR-regulated environment, the known gaps mean that additional PII filtering on model outputs would be necessary, and the model cannot be assumed safe for applications where training data memorisation could expose private information.

### 6.2 Low-Resource Languages Exhibit Unstable and Potentially Degrading Performance During Training

**The assumption or constraint.** The paper's decision to follow the "natural distribution" of data (Section 3.6) means that languages with small data volumes (<1 GB) receive a tiny fraction of the 1-trillion-token training budget. The paper explicitly observes this consequence: "some of the low-resource languages see limited improvement during training or even have a pass@1 decline" (Section 6.3). The paper further acknowledges that "the dependence of pass@1 on data size (Figure 2, left)...performance improves only for languages with large enough amounts of data (≳1 GB)."

**The consequence.** For low-resource languages, the model's performance is not merely weak — it is **unstable and unpredictable**. Figure 2 (right) shows R's pass@1 declining significantly between the 800B and 1000B checkpoints. The paper's manual investigation (Table D.3) reveals that individual problem pass rates oscillate wildly: HumanEval_0_has_close_elements goes from 197/200 passing at 600B tokens to 5/200 at 1000B. This is not gradual improvement or graceful degradation — it is near-random fluctuation. The paper describes the failures as "minor mistakes, e.g., not taking the absolute value when computing GCD, not converting a string to a character array, or not checking edge cases" (Section 6.3), and notes that "the pass rate between different checkpoints varies in what appears to be a completely uncorrelated manner" (Section 6.3). For a practitioner, this means that **StarCoderBase's performance on low-resource languages is not reliable** — a specific version of the model may solve a problem correctly or fail on a trivial syntactic error, and this is not predictable from training progress. The model is not "learning R" in a stable sense; it is applying transferred knowledge from high-resource languages in a brittle way that can be disrupted by continued training on other data. Furthermore, the paper's decision to release only the final checkpoint (1000B tokens) means users cannot access the potentially better-performing intermediate checkpoints for specific low-resource languages.

**What evidence exists in the paper.** Figure 2 (right panel) directly visualises the performance trajectories. Table D.3 provides per-problem pass counts for R across checkpoints, showing swings of 190+ samples out of 200 between consecutive checkpoints (e.g., HumanEval_0 at 600B: 171/200; at 800B: 197/200; at 1000B: 5/200). The paper's linear fit analysis (Figure 2, left) shows R² values of only 0.399–0.510 for the log-data-size vs. performance relationship, indicating that data volume explains less than half the variance in performance — other factors (transfer learning dynamics, training order effects) dominate for low-resource languages. The paper does **not** evaluate whether the performance instability correlates with specific language features (static vs. dynamic typing, syntax similarity to high-resource languages) or whether certain low-resource languages are more stable than others.

**Mitigation status.** Not addressed. The paper observes the phenomenon but does not propose a solution. The natural-distribution decision is treated as a deliberate governance choice (Section 3.6: "the largest amount of available data comes from popular programming languages and would, therefore, benefit a larger group of end-users"), but the paper does not discuss whether alternative strategies — up-sampling, multi-task learning, temperature-scaled loss weighting — could stabilise low-resource language performance without sacrificing high-resource performance. The paper does not recommend that users avoid low-resource languages, nor does it provide guidance on which languages are "stable enough" for production use. For a practitioner, the takeaway is: if your use case requires reliable code generation in a language with less than ~1 GB of training data, StarCoderBase is likely unsuitable without additional fine-tuning, and even then, the base model's instability may limit transfer learning effectiveness.

### 6.3 The Attribution Tools Cannot Distinguish Generic Code from Protected Content, Limiting Their Practical Utility for Copyright Compliance

**The assumption or constraint.** The Bloom-filter membership checker and BM25 search index (Section 9) are designed to locate training set matches for generated code snippets. The paper explicitly acknowledges a fundamental limitation: "Both attribution tools do not attempt to distinguish between generic code (e.g., boilerplate) or protected content" (Section 10.2). The membership checker operates on 50-character substrings (Section 9.1) and requires "a certain amount of context to trigger a match" (Section 10.2). The BM25 index preprocesses code with lowercase filtering, ASCII folding, and 3-gram tokenization (Section 9.2) — transformations that lose structural information and increase false-positive matches for common code patterns.

**The consequence.** A practitioner attempting to use these tools for copyright compliance faces an interpretability problem: when the tool flags a match, is it because the model copied a creative, copyrighted implementation (a legal concern), or because it generated a standard code pattern that appears in thousands of repositories (not a legal concern)? The paper's motivating framework (Section 1) cites Henderson et al. (2023)'s argument that "fair use [is] most likely when the model generates novel content dissimilar to any copyrighted training data" — but the attribution tools cannot operationalise "dissimilar to copyrighted training data" because they cannot identify which training data is copyrighted (all training data is permissively licensed in theory, but license detection has errors; Section 10.2) nor which generated code is "similar enough" to constitute infringement. The 50-character minimum resolution means that shorter copied snippets (e.g., a 30-character unique algorithm implementation) will not be flagged, creating false negatives. Conversely, a 50-character match on a common pattern (e.g., a standard library import or a widely-used data structure implementation) will be flagged, creating false positives that users must manually triage. The membership checker also "uses hash matching and thus may have false positives" (Section 10.2) due to Bloom filter collisions.

**What evidence exists in the paper.** The paper's description of the tools is primarily architectural (Sections 9.1–9.2) and does not include a systematic evaluation of false-positive and false-negative rates, precision, recall, or user studies of interpretability. The 26 GB size of the membership checker (Section 9.1) is reported, and the BM25 index configuration is described, but no experiment measures how often the tools correctly identify copied code vs. flagging generic patterns, or how often they miss genuinely copied code. The paper does not report a single quantitative result for the attribution tools — no precision, no recall, no latency measurement, no example of a true positive vs. false positive attribution. The limitation is acknowledged in prose (Section 10.2) but not empirically characterised.

**Mitigation status.** Partially addressed through design but not through evaluation. The two-stage architecture (fast Bloom filter + detailed search) is conceptually appropriate for the problem, and the integration into a VSCode extension (Section 9) makes the tools accessible to developers. However, the missing evaluation means users cannot know the tools' reliability. The paper frames them as "a starting point for researchers and developers" and explicitly calls for ongoing research (Section 10.2: "we hope that these tools will support ongoing research on the responsible development of LLMs"). For a practitioner deploying StarCoder in a context where copyright compliance matters, the attribution tools provide a signal, but the interpretation of that signal requires legal expertise and manual review that the tools do not automate or guide.

### 6.4 The Evaluation is Confined to English-Only Benchmarks and a Single Pre-2023 Code Distribution, Leaving Deployment-Relevant Generalisation Unmeasured

**The assumption or constraint.** All code generation benchmarks (HumanEval, MBPP, DS-1000, MultiPL-E, ODEX) are English-language, and the training data cutoff (The Stack v1.2, collected from GitHub prior to 2023) means that the model has not seen code using libraries, APIs, or language features introduced after the data collection window. The paper explicitly acknowledges this in Section 10.2: "We evaluated the performance of StarCoder solely on English-based benchmarks... To make these models more accessible to a wider audience, future research should investigate the performance and limitations of Code LLMs on other natural languages." The ODEX benchmark (Section 6.1.3) includes non-English natural language instructions (Spanish, Japanese, Russian), but these are translations of English coding queries — not coding problems originating in non-English developer communities with different conventions, libraries, and documentation ecosystems.

**The consequence.** A practitioner deploying StarCoder for a non-English developer audience cannot estimate the model's performance from the paper's evaluation. The model may struggle with natural language instructions in languages not well-represented in the training data (GitHub issues were filtered to English only; Section 3.3). More subtly, coding idioms, library preferences, and documentation patterns vary across language communities — a Python data science workflow common in the English-language StackOverflow may be rare in the Japanese Qiita ecosystem, and StarCoder's training data may under-represent the latter. Similarly, for code using post-2022 library versions (e.g., Python 3.12 features, React 19 APIs, Rust 2024 edition), the model has no training signal and may generate outdated or incompatible code. The paper's decontamination against specific benchmarks (Section 5.2) ensures that evaluation numbers are not inflated by memorisation, but it does **not** ensure that the model generalises to temporally or culturally shifted code distributions. The HELM evaluation (Section 7.4, Table 27) tests natural language reasoning but does not test code generation in non-English contexts.

**What evidence exists in the paper.** The ODEX evaluation (Table 14) provides the only cross-lingual code generation results: StarCoder achieves 44.2% on Japanese and 50.4% on Russian open+closed-domain queries, which is competitive with or exceeding English performance (44.7%). This is suggestive of cross-lingual transfer, but ODEX queries are English-origin problems translated into other languages — they test the model's ability to handle translated natural language, not its ability to generate code appropriate for non-English development ecosystems. The paper does **not** evaluate on non-English code generation benchmarks (e.g., Chinese-language coding problems, Russian documentation generation). The temporal limitation is not evaluated at all: there is no experiment measuring performance on libraries or APIs released after The Stack v1.2. The paper reports that 44 people opted out of The Stack (Section 3) and that the dataset was processed at a specific point in time, but does not discuss the staleness implications.

**Mitigation status.** Not addressed. The paper flags the limitation for future work (Section 10.2: "future research should investigate the performance and limitations of Code LLMs on other natural languages") but does not provide a mitigation strategy. The open-access nature of StarCoder means practitioners can fine-tune the model on their target language or library distribution, and the paper's release of training data and tooling supports this. However, the evaluation does not provide baselines for how much fine-tuning data would be needed, or whether the model's existing multi-lingual code capabilities transfer to new libraries and languages.

### 6.5 Key Training and Architecture Decisions Are Not Isolated Through Controlled Ablations, Leaving Their Individual Contributions Uncertain

**The assumption or constraint.** The paper bundles multiple architectural and data decisions — Fill-in-the-Middle training, Multi-Query Attention, 8K context length, the specific PII redaction pipeline, the per-language heuristic filtering, and the natural-distribution data weighting — into a single model release. None of these components is evaluated through a controlled ablation (training a variant without it) at the 15.5B scale, or even at a smaller scale with extrapolation. The paper implicitly claims that these components collectively contribute to StarCoderBase's performance, but cannot attribute gains to individual design choices.

**The consequence.** A practitioner trying to decide whether to adopt specific components of the StarCoder pipeline for their own Code LLM cannot determine which choices are load-bearing. Is the 8K context length contributing meaningfully to code generation performance, or is the perplexity improvement (Table 21) a metric that does not translate to downstream task accuracy? Does FIM training improve left-to-right code generation (as suggested by the comparison to non-FIM CodeGen-Mono, Table 15), or is the gap attributable to differences in training data scale, language coverage, or architecture? Does the PII redaction pipeline degrade performance by removing training signal (names in code, email patterns, key structures), or is the impact negligible? The paper's comparison to SantaCoder (1.1B) provides a single scale point within the same architecture family, but SantaCoder also differs in context length (2K vs. 8K), training data volume (<300 GB vs. ~800 GB), and language coverage — too many variables to isolate any single factor. The nearest approximation to an ablation is the StarCoderBase vs. StarCoder comparison (Tables 12, 15), which isolates Python fine-tuning, but this is a data addition, not a component removal. The FIM contribution is partially tested through the DS-1000 completion vs. insertion comparison (Table 13), which shows that FIM mode does not degrade standard completion performance — but this tests inference mode, not the presence vs. absence of FIM during training.

**What evidence exists in the paper.** The 2K vs. 8K perplexity comparison (Table 21) is the only direct ablation of a single model component, and it measures perplexity (a proxy metric), not downstream task performance. For all other design choices — FIM training, MQA, data weighting, PII redaction — no ablation results exist at any scale. The paper reports performance improvements over SantaCoder (e.g., HumanEval: 18.0% → 30.4% base, 33.6% fine-tuned) but the ~14× scale increase bundles together parameter count, data volume, context length, architecture changes, and data pipeline improvements, making causal attribution impossible. The near-identical performance of StarCoderBase and StarCoder on some non-Python languages (Table 15, e.g., C++: 30.56% vs. 31.55%) suggests that Python fine-tuning has minimal impact on those languages — a weak form of ablation — but this does not isolate any of the base model's design choices.

**Mitigation status.** Not addressed. The paper does not frame the absence of ablations as a limitation, though the scale of the project (320,256 GPU-hours for a single training run) makes comprehensive ablations at the 15.5B scale economically infeasible. A practical mitigation would have been to conduct ablations at a smaller scale (e.g., 1.1B parameters, matching SantaCoder) and extrapolate trends — the paper already has SantaCoder as a baseline, so training a 1.1B variant without FIM, or with 2K context, would have been relatively inexpensive and could have isolated specific components. The paper does not pursue this. For practitioners, the consequence is that the paper functions as a system demonstration rather than a controlled experiment: StarCoderBase works well, but the reader cannot confidently extract which engineering choices to replicate in their own models.

### 6.6 The HumanEval Prompt Sensitivity Result Undermines Confidence in Benchmark Robustness and Reveals Uncharacterised Brittleness

**The assumption or constraint.** Section E.3 reports that prepending `<filename>solutions/solution_1.py\n# Here is the correct implementation of the code exercise` to HumanEval prompts boosts StarCoder's pass@1 from 33.6% to 40.8% — a 7.2 percentage point improvement, larger than the gap between StarCoder and the next-best open-access model (CodeGen-Mono at 29.3%). The same prompt reduces CodeGen-Mono's performance from 29.3% to 28.10% and has "negligible impact" on StarCoderBase. The paper does not investigate the mechanism behind this sensitivity, does not evaluate whether similar prompt perturbations affect other benchmarks, and does not report variance in HumanEval performance across prompts. The finding is presented as a qualitative observation in an appendix (Section E.3), not as a core result.

**The consequence.** This result reveals that **StarCoder's benchmark performance is not stable under prompt perturbations** — seemingly innocuous changes (a filename and a comment) produce effects larger than the differences between models that required 15.5B parameters and 1T training tokens to achieve. This undermines the paper's quantitative claims in at least two ways. First, if HumanEval pass@1 can swing by 7.2 points based on prompt formatting, then the "StarCoder matches code-cushman-001" claim (33.6% vs. 33.5%, a 0.1-point gap) is fragile — a slightly different prompt format could reverse the conclusion. The paper reports HumanEval results at a single temperature (0.2) with a single prompt format (the standard HumanEval prompt), and the appendix reveals that this choice is not neutral. Second, the model-specificity of the effect (StarCoder benefits, CodeGen-Mono is hurt, StarCoderBase is unaffected) suggests that Python fine-tuning introduced a spurious correlation between filename/comment cues and solution quality — the model learned that files named `solutions/solution_1.py` with comments asserting correctness tend to contain correct code, and this metadata cue boosts its generation quality independently of the problem description. This is a form of **prompt overfitting**: the model's apparent capability depends on whether the prompt matches patterns associated with high-quality solutions in the fine-tuning data, not solely on its understanding of the coding task. For practitioners, this means that StarCoder's performance in deployment will depend on prompt formatting choices that the paper neither systematically explores nor provides guidance for.

**What evidence exists in the paper.** The effect is documented in a single paragraph of Section E.3 with a single prompt variant. The paper does not report: (1) whether the effect generalises to MBPP, DS-1000, or MultiPL-E; (2) what component of the prompt (filename, comment, both) drives the improvement; (3) whether different filenames or comments produce different effects; (4) performance variance across seeds or temperatures for the prompted vs. unprompted conditions; (5) whether the effect interacts with problem difficulty (are easy or hard problems more affected?). The finding is described as an observation that occurred during inspection of model outputs ("We inspected StarCoder-generated programs on the HumanEval benchmark and found that there were several cases where the model produces what are effectively empty solutions"), and the prompt prefix was tried as an ad-hoc fix. The paper explicitly notes that "these prefixes are typically model-specific" — acknowledging the lack of generality — but does not explore the implications for benchmark validity.

**Mitigation status.** Not addressed. The paper does not discuss whether the prompt sensitivity compromises the benchmarking methodology, does not propose prompt standardisation protocols, and does not recommend that future evaluations report prompt sensitivity. The result is quarantined in an appendix and not referenced in the main evaluation sections (6.1, 6.2). For a practitioner, the implication is that **the reported benchmark numbers may not reflect out-of-the-box performance without prompt engineering**, and that the model's sensitivity to prompt formatting is uncharacterised — making it difficult to predict real-world performance or to compare StarCoder fairly to other models that may also exhibit prompt sensitivity (but where it is similarly unreported).

## 7. Implications and Future Directions

### How This Work Changes the Landscape

The StarCoder paper is not a methodological or algorithmic breakthrough — it introduces no novel training objective, no new architecture, and no previously unknown technique. Yet it represents a **normative inflection point** in how the field thinks about Code LLM development. The paper's primary contribution is demonstrating that **transparency, responsible data governance, and competitive performance are simultaneously achievable at scale**, and in doing so, it shifts the burden of proof from the open-source community ("can open models compete?") to closed-access developers ("why can't you document your pipeline to this standard?").

This is best understood as a **reframing** rather than a paradigm shift. Prior to StarCoder, the landscape of Code LLMs was implicitly organised around a tradeoff: you could have strong performance (OpenAI's codex models, Google's PaLM), or you could have transparency and community governance (SantaCoder, PolyCoder, EleutherAI's models), but you couldn't have both at the scale where performance becomes practically useful. StarCoder breaks this framing. By matching `code-cushman-001` on HumanEval (33.6% vs. 33.5%, Table 12) and substantially outperforming it on MBPP (52.7% vs. 45.9%) and DS-1000 (26.0% vs. 18.1%, Table 13), while providing complete documentation of every stage of the data pipeline — language-specific filter calibration with community annotator remarks published in a public Google sheet (Section 3.1), a PII detection model with per-type precision and recall (Tables 8–9), carbon accounting (16.68 tonnes CO₂eq, Section 5.7), and an attribution tracing tool integrated into VSCode (Section 9) — the paper sets a new baseline for what a responsible model release looks like. The field can no longer claim that performance requires opacity.

**Reconciling prior contradictions.** The paper resolves a latent tension in the open-source AI community between the BigScience/BLOOM model (which prioritised transparency but stopped at 176B parameters with a multilingual focus, not code) and the EleutherAI model (which released training data and models like GPT-NeoX-20B, but without the same depth of data governance tooling or per-language curation). StarCoder demonstrates that the BigScience-style collaborative governance model — community working groups with decision-making authority, opt-out mechanisms, annotated data collection for PII — can produce models that are not just "good for an open model" but competitive with industry offerings. The paper also directly refutes the implicit claim embedded in projects like CodeGen-Mono (which released a 16B model but withheld the Python fine-tuning dataset; Nijkamp et al., 2023) and CodeGeeX (which released a 13B model without training data; Zheng et al., 2023) that withholding data is necessary or harmless. StarCoder shows, through its competitive performance, that withholding data was not necessary, and through its attribution tools, that transparency provides concrete benefits (copyright compliance support) that closed models cannot offer.

**Which research directions become more attractive.** The paper makes the following research investments more compelling:

- **PII detection as a first-class research area within ML.** Prior to this paper, PII detection in training data was an engineering afterthought — a regex pass that nobody evaluated. The paper's demonstration that a custom-trained NER model can achieve 70.41% F1 on keys (vs. 6.74% for regex, Table 8) but still leaves 30% undetected establishes PII detection as an open research problem with measurable metrics and clear room for improvement. The release of the 12,000-file annotated dataset (under gated access) provides a benchmark for this subfield.

- **Attribution tracing as a standard model release component.** The Bloom filter + BM25 pipeline (Section 9) is a first-generation tool that the paper explicitly acknowledges cannot distinguish boilerplate from protected content. This opens a research direction: how do you build attribution tools that incorporate legal notions of substantial similarity, that handle obfuscated or refactored code, and that scale to trillion-token datasets with acceptable latency? The paper's integration into VSCode demonstrates that these tools must work at interactive speeds, not just in batch post-hoc analysis.

- **Data weighting as a governance decision rather than a purely technical optimisation.** The paper's explicit decision to follow the natural distribution (Section 3.6) and the resulting instability of low-resource language performance (Figure 2, Table D.3) reframes data weighting as a political choice about whose code matters. Future work can now explicitly study the equity implications of data weighting strategies, rather than treating the distribution as a given.

**Which research directions become less attractive.** The paper implicitly argues against several common practices:

- **Releasing model weights without training data or curation documentation.** CodeGen-Mono and CodeGeeX are now positioned as incomplete releases — useful as baselines, but insufficient as scientific artifacts because their training data composition is unknown and their performance gains cannot be attributed or reproduced. The paper's thorough documentation raises the expected standard for what constitutes a complete model release.

- **Treating PII redaction as a solved problem.** The direct comparison of NER vs. regex (Table 8) makes it difficult to justify shipping a Code LLM with only regex-based PII filtering, now that the performance gap is quantified.

- **Evaluating only on HumanEval and MBPP.** The paper's finding that "model performance on HumanEval and MBPP benchmarks does not always correlate with performance on the more realistic DS-1000 benchmarks" (Section 6.1.2) — combined with the prompt sensitivity result in Appendix E.3 showing a 7.2-point swing from a filename and comment — makes single-benchmark evaluation look increasingly fragile. Future Code LLM papers that evaluate only on HumanEval will be compared unfavorably to this paper's comprehensive suite.

### Follow-Up Research This Work Enables

**1. A systematic study of how FIM training affects left-to-right code generation performance, through controlled ablation at the 1–3B scale.**
The paper shows circumstantial evidence that FIM training improves standard left-to-right generation (StarCoder outperforms non-FIM CodeGen-Mono on HumanEval, 33.6% vs. 29.3%, Table 12; DS-1000 completion, 26.0% vs. 11.7%, Table 13), but cannot isolate the FIM contribution from other model differences (architecture, data volume, language coverage, tokenizer). A controlled experiment would train two SantaCoder-scale (1.1B) models on identical data, one with FIM transformations at a 50% rate (matching StarCoder's setting; Section 5.1) and one without, and evaluate on HumanEval, MBPP, DS-1000, and MultiPL-E in left-to-right completion mode only (no FIM inference). If the FIM-trained variant substantially outperforms the non-FIM variant on standard completion tasks, this would establish FIM as a general-purpose pretraining objective for code, not merely a mechanism for enabling infilling — a finding that would change how most Code LLMs are pretrained. The paper's release of SantaCoder's architecture and training methodology (Ben Allal et al., 2023) makes this replication straightforward.

**2. Building a difficulty-aware attribution tool that estimates the "originality" of a generated code snippet relative to its training set matches, incorporating code structure rather than surface-level string matching.**
The existing attribution tools (Section 9) operate on string-level features: 50-character Bloom filter hashes and BM25 over 3-grams. They cannot distinguish between memorisation of a unique 50-character sequence (a potential copyright concern) and generation of a 50-character sequence that happens to appear in many training files (e.g., a standard library import). A follow-up would compute, for each generated snippet flagged by the Bloom filter, the **inverse document frequency (IDF)** of its constituent n-grams in the training corpus — snippets composed of rare n-grams (high IDF) are more likely to be unique creative content; snippets composed of common n-grams (low IDF) are likely boilerplate. This IDF-weighted attribution score would provide a continuous measure of "copying risk" that aligns more closely with the legal concept of substantial similarity than the current binary match/no-match output. The paper's release of the BM25 index (Section 9.2) provides the infrastructure to compute IDF scores without building a new index. The evaluation would measure how often high-IDF matches correspond to human-judged instances of meaningful copying vs. false positives on a manually annotated set of 500–1,000 generated snippets.

**3. Quantifying the memorisation of PII and secrets in StarCoderBase through a systematic red-teaming evaluation that probes for training data extraction.**
The paper documents its PII detection pipeline's performance (Tables 5, 8, 9) but does not evaluate whether StarCoderBase actually memorises and regenerates the PII that evaded redaction. The known gaps — IDs excluded entirely, usernames excluded after low F1 (61.49%), keys at 70.41% F1 leaving ~30% undetected — mean the model was trained on some quantity of real personal data. A follow-up would adapt the training data extraction methodology from Carlini et al. (2021) to code: prompt the model with prefixes of known PII-containing files from The Stack (e.g., the first 200 tokens of a file known to contain an API key), generate completions, and measure how often the model reproduces the exact PII. This experiment would quantify the practical privacy risk of the known detection gaps — does the model actually memorise the 30% of undetected keys, or does their high entropy make them difficult to learn? The paper's release of The Stack v1.2 makes it possible to construct ground-truth PII location data (by running the PII detection pipeline and identifying what it missed in a held-out set) and test extraction rates systematically. A null result (low extraction rates despite known undetected PII) would suggest that high-entropy secrets are naturally protected by their uniqueness; a high extraction result would demonstrate that the PII pipeline's gaps translate to real privacy risk and motivate investment in closing them.

**4. Investigating the mechanism behind StarCoder's prompt sensitivity and designing a benchmark protocol that reports performance variance across prompt formats.**
The HumanEval prompt engineering result (40.8% with a particular filename and comment vs. 33.6% standard, Appendix E.3) reveals that benchmark performance is not stable under prompt perturbations, but the paper does not explore the mechanism or the generality. A follow-up would systematically vary the components of the successful prompt — filename only, comment only, different filenames (`solutions/solution_1.py` vs. `src/main.py` vs. `test.py`), different comments ("correct implementation" vs. "working solution" vs. "this should pass all tests"), and random metadata — and measure the performance impact on HumanEval, MBPP, and DS-1000 for both StarCoder and StarCoderBase. This would determine whether the effect is driven by the `<filename>` token (if any filename boosts performance, it's a metadata attention effect), by the comment semantics (if only correctness-asserting comments help, it's a learned association from the fine-tuning data), or by a specific combination. The finding that StarCoderBase is unaffected while StarCoder is strongly affected suggests the sensitivity was introduced during Python fine-tuning (35B tokens, Section 5.5), which provides a natural ablation: evaluate StarCoder checkpoints during fine-tuning to identify when the prompt sensitivity emerges. This experiment would inform whether future models should be fine-tuned with metadata randomly dropped (as the pretraining data was, with p=0.2; Section 5.1) to reduce prompt brittleness.

**5. Scaling laws for code that jointly model programming language data volume, model size, and downstream task performance across languages.**
The paper provides a natural testbed for code-specific scaling law analysis that goes beyond the standard perplexity-vs-compute formulation (Kaplan et al., 2020; Hoffmann et al., 2022). Figure 2 (left) shows a log-linear relationship between data volume and pass@1 for each training checkpoint, but this is a bivariate fit that doesn't account for model size or cross-lingual transfer effects. A follow-up would train a family of StarCoder-architecture models at sizes ranging from 100M to 15B parameters, with controlled language mixtures (varying the ratio of high-resource to low-resource languages), and measure pass@1 on MultiPL-E for each language as a function of both model parameters and language-specific token count. This would produce **language-specific scaling laws** that predict, for a given programming language and target performance level, the minimum model size and training data volume required. The paper's instability findings (Table D.3: R's pass@1 dropping from 197/200 to 5/200 for a single problem across checkpoints) suggest that below some critical data threshold, scaling laws break down and performance becomes effectively random — identifying that threshold for different language families (statically typed vs. dynamically typed, C-family vs. functional) would provide actionable guidance for data curation. The released training data, model architecture, and evaluation harness (Section 6, "A Code LM Evaluation Harness") provide all the infrastructure needed.

**6. A temporal generalisation benchmark that evaluates StarCoder on GitHub repositories created after The Stack v1.2's collection cutoff, measuring how much of its performance comes from genuine code understanding vs. memorisation of training-time patterns.**
The paper's decontamination protocol (Section 5.2) removes exact matches to benchmark problems from the training data, but this only addresses literal memorisation. If StarCoder's strong performance on HumanEval and MBPP comes substantially from having seen structurally similar problems (different variable names, same algorithmic pattern) during training, its performance should degrade on problems using APIs, libraries, or language features that postdate The Stack v1.2. A follow-up would construct a benchmark of 200 Python problems using only Python 3.11+ features, libraries released after 2023, and APIs documented after the training cutoff, and compare StarCoder's pass@1 on this temporal holdout set to its performance on the standard HumanEval. A large performance drop would indicate that the model's apparent capability is partly pattern-matching against a specific code distribution; a small drop would demonstrate genuine algorithmic reasoning. The comparison to code-cushman-001 (which was trained on unknown data with an unknown cutoff) would be particularly informative — if both models degrade similarly, the limitation is inherent to current Code LLM technology; if StarCoder degrades more (because its training data is narrower and better-documented), the transparency enables a more honest assessment of capability boundaries.

### Practical Applications and Downstream Use Cases

**1. On-device code completion with a verifiable training data provenance trail.**
A software company deploying code completion in an IDE (e.g., a self-hosted alternative to GitHub Copilot) can use StarCoderBase with the VSCode extension's attribution tools (Section 9) to provide developers with real-time information about whether a suggested completion matches code in the training set. The Bloom filter provides a rapid first-pass check (operating on 50-character substrings; Section 9.1), and the BM25 index enables detailed source tracing for flagged completions. This matters specifically for organisations in regulated industries (finance, healthcare, government contracting) where code provenance must be auditable — if a generated function incorporates code from a specific permissively-licensed repository, the developer can verify the license terms before incorporating it. The paper's 98.70% valid code rate in insertion mode on security benchmarks (Table 16, Asleep at the Keyboard) and 35.87% insecure rate (lower than code-cushman-001's 42.32% and code-davinci-002's 42.70% in Table D.2) means the model generates syntactically valid code more reliably than the closed-access alternatives that dominated the market at the time of writing.

**2. Fine-tuning a domain-specific Code LLM on proprietary codebases without starting from an opaque base model.**
An enterprise with a large internal codebase (e.g., a telecommunications company with millions of lines of Java and Python) can fine-tune StarCoderBase on their proprietary code, confident that the base model was trained exclusively on permissively-licensed open-source code — reducing the risk that the fine-tuned model will regurgitate GPL-licensed code into their proprietary codebase. The paper's documentation of every data source (Tables 1–2), every filtering decision (Section 3.1), and every PII redaction step (Section 4) provides the legal and compliance teams with a complete audit trail that no closed-access model can match. The 15.5B parameter scale is large enough that fine-tuning on a few hundred million tokens of domain-specific code is feasible with modest hardware (the paper fine-tuned StarCoder on 35B Python tokens using only 3.5% additional GPU-hours; Section 5.7), and the model's multi-language training (80+ languages, Section 3.1) means it already has exposure to the syntax and idioms of most languages the enterprise is likely to use.

**3. A benchmark-agnostic evaluation harness that reduces the cost of comprehensive Code LLM assessment.**
The paper's "Code LM Evaluation Harness" (Section 6, described as "inspired by the LM Evaluation-Harness" from Gao et al., 2021b) supports HumanEval, MultiPL-E, and DS-1000 with Docker-based execution for safety, and is released as open-source infrastructure. A research lab evaluating a new Code LLM can use this harness to run the same comprehensive suite of evaluations that the paper reports — 19-language MultiPL-E (Table 15), seven-library DS-1000 (Table 13), security benchmarks (Table 16), infilling benchmarks (Tables 17–20), and natural language reasoning (Tables 22–27) — against both their model and the paper's baselines, with standardised prompts, temperatures, and sampling budgets. This directly addresses the paper's finding that "model performance on HumanEval and MBPP benchmarks does not always correlate with performance on the more realistic DS-1000 benchmarks" (Section 6.1.2) by making multi-benchmark evaluation as easy as single-benchmark evaluation. The Docker-based execution ensures that generated code is actually run against test cases rather than evaluated heuristically, matching the paper's rigorous execution-based evaluation methodology.

**4. A baseline for measuring PII leakage in Code LLMs through a standardised red-teaming protocol.**
Security researchers auditing Code LLMs for privacy violations can use the paper's PII detection pipeline (StarEncoder + NER model, Section 4.3) as a standardised measurement tool. The annotated PII dataset (12,000 files, 22,950 entities, released under gated access) provides ground-truth labels for evaluating any PII detection system, and the paper's per-type precision and recall numbers (Tables 8–9) establish a performance baseline. A researcher evaluating a new Code LLM's privacy risk can: (1) run the StarEncoder-based PII detector on the model's training data (if available) to estimate residual PII; (2) generate completions from privacy-sensitive prompts and run the detector on outputs to measure PII regeneration rates; and (3) compare against the paper's reported detection performance to contextualise their findings. The paper's 800 GPU-hour inference cost for PII detection and the 0.25%-of-training-compute ratio provide a calibration point for the resources required to apply this methodology at scale, making it easier for other projects to budget for similar PII auditing.

### When to Prefer This Method

The paper does not articulate an explicit tradeoff between StarCoder and specific named alternatives for particular deployment scenarios — it positions StarCoder as a demonstration that transparent development can produce competitive models, rather than as the optimal choice under a specific set of conditions. The primary comparison is against `code-cushman-001` (Table 12, Table 15), but the paper does not provide decision rules for when a practitioner should choose StarCoder over that model, nor does it compare against fine-tuning approaches, smaller models with more inference compute, or domain-specific Code LLMs. The "When to Prefer" framework would require the paper to have articulated these tradeoffs (e.g., "use StarCoder when you need attribution tracing; use code-cushman-001 when you need lower latency; use CodeGen-Mono when you are Python-only and don't need training data transparency"), but the paper's positioning as a holistic responsible-development demonstration means such a matrix would impose a structure the paper itself does not develop. The closest the paper comes to a comparative recommendation is the implicit argument embedded in its governance choices: prefer StarCoder when you need (1) training data provenance guarantees, (2) PII redaction with documented performance, (3) attribution tracing tools for copyright compliance, or (4) a commercially-viable license with use restrictions — but the paper does not quantify the performance cost (if any) of choosing these governance features over a less-transparent alternative, making a decision matrix speculative rather than grounded in the paper's evidence.
