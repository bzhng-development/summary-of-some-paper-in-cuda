## 1. Executive Summary

DualPath introduces a **dual-path KV-Cache loading** architecture for agentic LLM inference that breaks the prefill-side storage I/O bottleneck in PD-disaggregated systems by enabling KV-Cache to be loaded into decoding engines and then transferred to prefill engines via RDMA over the compute network, rather than exclusively loading through prefill-side storage NICs (storage-to-decode path vs. traditional storage-to-prefill path). Evaluated on DeepSeek V3.2 660B, a 27B downscaled variant, and Qwen2.5-32B using production agentic traces with up to 64K context and ~99% KV-Cache hit rates, DualPath improves offline inference throughput by up to 1.87× and online serving throughput by an average of 1.96× without violating SLO constraints, while a CNIC-centric traffic manager isolates KV-Cache transfers from latency-sensitive model execution communications via InfiniBand virtual lanes. The system achieves these gains by aggregating the storage bandwidth of both prefill and decode engines—redistributing network load through a global scheduler that dynamically balances computation and NIC utilization across engine types—establishing that the fundamental bottleneck in agentic workloads is asymmetric storage bandwidth saturation rather than aggregate bandwidth capacity, and that decoupling KV-Cache retrieval from prefill engines alone suffices to recover substantial throughput when combined with layerwise prefill and workload-aware scheduling.

## 2. Context and Motivation

### The Core Problem: Storage I/O, Not Computation, Dominates Agentic LLM Inference

The fundamental problem this paper addresses is a **workload-driven architecture mismatch**. As LLMs evolve from single-turn chatbots into multi-turn agentic systems that interact with tools and environments over extended sessions, the dominant performance bottleneck shifts from GPU computation to KV-Cache storage I/O—yet existing inference architectures remain optimized for the old compute-bound regime. This shift is not incremental; it represents a qualitative change in what limits system throughput.

The paper identifies this problem through a concrete observation: in their production agentic traces (Table 2), the average KV-Cache hit rate is **98.7%** (append length of 429 tokens into an average context of 32,721 tokens). This means that on every turn, the system must load nearly the entire accumulated context from persistent storage, while only computing attention for a tiny fraction of newly appended tokens. The resulting **cache-compute ratio**—the amount of KV-Cache data that must be loaded per unit of computation—ranges from **13 GB/PFLOP** for DeepSeek V3.2 (which already uses highly optimized MLA) to **117-267 GB/PFLOP** for models with standard attention like Qwen2.5-32B (Table 1). The paper explicitly calculates this ratio to demonstrate that the I/O demand per FLOP is extreme: for every floating-point operation the GPU performs on new tokens, it must first read vastly more data from storage than it produces results.

This matters because GPU throughput is bounded by the slower of two constraints: how fast it can compute, and how fast data can be fed to it. When the cache-compute ratio is high, the GPU sits idle waiting for KV-Cache to arrive, even though Tensor Cores and other compute units are underutilized. The paper quantifies this through hardware trend data (Figure 3, left): from NVIDIA Ampere to Blackwell, GPU dense FLOPS grew **28.8×**, while PCIe bandwidth grew only **2.0×** and HBM capacity grew **2.4×**. This **14.4× decline in I/O-to-compute ratio** means that each successive GPU generation is progressively more bottlenecked by data movement rather than arithmetic—and agentic workloads, with their extreme KV-Cache reuse patterns, hit this bottleneck hardest.

### Why This Problem Is Critical Now

Three converging trends make this problem urgent and practically significant:

**Agentic workloads are becoming the dominant production pattern.** The paper's motivation is grounded in observed production behavior: agentic LLMs that autonomously plan, invoke tools (bash commands, Python interpreters, web browsers), and solve real-world tasks through multi-turn interactions. Unlike chatbot sessions where a user asks a question and the model responds in a few turns, agentic trajectories can span **dozens to hundreds of turns**, with context accumulating across the entire session (Figure 2). Their production traces show a mean of **157 rounds per trajectory** with the average context growing to **55,958 tokens** at 64K max context length. Each round appends only a few hundred tokens (mean: 429) to a massive existing context, creating the extreme KV-Cache hit rate that makes I/O the dominant cost. This is not a niche scenario—the paper cites coding assistants, web agents, and autonomous task agents as representative applications, and explicitly notes that agentic RL training (where the LLM generates thousands of multi-step trajectories during the rollout phase) imposes this same I/O pattern at even larger scale.

**Existing solutions hit fundamental physical limits, not just implementation inefficiencies.** The paper is careful to show that the bottleneck is **hardware-physical**, not a software oversight. In prevalent PD-disaggregated architectures with external KV-Cache storage (§2.1), prefill engines must load the KV-Cache from remote storage over a single storage NIC per node. At 400 Gbps per SNIC and GB/PFLOP cache-compute ratios in the double or triple digits, the storage bandwidth simply cannot keep the GPU fed—the GPU computes faster than the NIC can deliver data. Figure 3 (right) demonstrates this concretely: when varying the token batch size for requests with 30K context and 300 appended tokens, relative token throughput saturates quickly and plateaus, showing that adding more tokens to the batch (which would increase GPU utilization if computation were the bottleneck) yields diminishing returns because the storage link is already saturated. The paper explicitly calculates the **cache-compute ratio** in GB/PFLOP (Table 1) to show that even for DeepSeek V3.2—which uses Multi-head Latent Attention to minimize KV-Cache size—the ratio is **13-36 GB/PFLOP**, meaning the storage NIC must deliver tens of gigabytes for every petaFLOP of computation. For standard attention models like Qwen2.5-32B at 16K context, the ratio balloons to **117 GB/PFLOP**. These numbers are not borderline—they represent a multiple-order-of-magnitude gap between I/O demand and compute capability.

**Storage bandwidth is unevenly utilized, not globally exhausted.** This is the paper's crucial diagnostic insight. The problem is not that the total storage bandwidth in the cluster is insufficient—it's that it is **asymmetrically allocated**. In PD-disaggregated systems, only prefill engines load KV-Cache from storage; decoding engines' storage NICs sit largely idle during prefill (Figure 1, left). The paper reports that prefill-side SNICs are persistently saturated at 100% utilization, while decode-side SNICs remain underutilized—a direct consequence of the architecture's assumption that KV-Cache loading is a prefill-exclusive operation. This means the aggregate storage bandwidth of the cluster cannot be fully harnessed: the system is bottlenecked by the bandwidth of the subset of NICs attached to prefill nodes, even though other NICs are available and idle. Simply adding more bandwidth to prefill nodes is described as "costly and often impractical in general-purpose clusters," and it doesn't solve the fundamental asymmetry—it just shifts the saturation point.

### Where Prior Approaches Fall Short

The paper identifies four categories of prior work, each of which addresses part of the problem but leaves the fundamental I/O imbalance unresolved:

**Distributed DRAM cache pools (Mooncake, TokenLake).** Mooncake [38] builds a distributed DRAM pool for KV-Cache and uses an affinity-aware scheduler to maximize DRAM hit rates, avoiding storage I/O when the working set fits in memory. The paper identifies two failure modes for this approach under agentic workloads. First, **memory capacity mismatch**: during the rollout phase of agentic RL training, "substantial data (like reward model and optimizer states) is offloaded to host DRAM, further constraining the available DRAM for KV-Cache" (§2.2). DRAM is already fully occupied by training state, leaving no room for a KV-Cache pool. Second, **cost proportionality**: for online serving with enormous working sets (the paper's working set analysis in §8.2 estimates 69-681 GB for their DS 660B experiments, and notes this would be larger in realistic settings with tool call latencies), DRAM-based caching is not cost-effective compared to SSD-based storage. The paper acknowledges that DualPath can be combined with a middle DRAM cache, but notes "the performance gain is marginal" (§9) because the fundamental problem is the bandwidth imbalance during storage reads, not the storage medium itself.

**KV-Cache I/O optimization within a single path (Strata, KVPR, TailorKV, TARDIS, Phoenix).** These works optimize the data path between storage and prefill engines—through GPU-assisted I/O and cache-aware scheduling (Strata [49]), partial recomputation to trade compute for I/O (KVPR [23]), layer-granular hybrid quantization (TailorKV [53]), GPU-centric caching services (TARDIS [22]), or refactored I/O stacks for GPU Direct Storage (Phoenix [51]). The paper distinguishes its contribution sharply: these approaches "do not solve the inherent inefficiency caused by storage I/O imbalance between different engines" (§1). They optimize the single path's efficiency (how fast data moves along the storage-to-prefill route) but do not address the structural asymmetry that leaves decode-side bandwidth idle. DualPath's contribution is orthogonal to single-path optimization—it adds a second path, making optimization of each individual path complementary rather than competing.

**KV-Cache size reduction (HCache).** HCache [19] reduces the amount of KV-Cache data to retrieve by exploiting sparsity or compression. The paper groups this with I/O optimization as addressing the "amount" or "overhead" dimensions but not the "which NICs are used" dimension. Reducing KV-Cache size by a constant factor shifts the saturation point but doesn't change the fact that only a subset of available NICs are utilized.

**Inference system architectures (SGLang with HiCache/Mooncake Store, PD disaggregation).** The paper's baseline comparison includes SGLang with HiCache [40] and Mooncake Store enabled (§7.2), representing the state of the art in open-source inference systems. The paper acknowledges that PD disaggregation [37, 58] "has largely become the de facto standard for inference serving" (§9) and that layerwise prefill [50, 17] addresses HBM capacity bottlenecks by enabling larger effective batch sizes. However, these architectures inherit the assumption that KV-Cache loading is fundamentally a prefill-engine operation—they optimize within this constraint rather than questioning it.

### How DualPath Positions Itself Relative to Prior Work

DualPath is not primarily a new caching strategy, a new compression technique, or a new attention mechanism. It is a **data-movement architecture** that rethinks which engines participate in KV-Cache retrieval. The paper's key positioning claim is that the bottleneck is **structural, not quantitative**: it's not that there isn't enough bandwidth, but that existing bandwidth is asymmetrically allocated.

The paper identifies an opportunity that prior work overlooked: **the compute network—which has much larger aggregate bandwidth than the storage network because each GPU has its own dedicated compute NIC—exhibits an intermittent traffic pattern** (§3). Collective operations used in model inference (AllToAll for expert parallelism, ReduceScatter/AllGather for tensor/context parallelism) "burst in sub-millisecond intervals," leaving the compute network's substantial bandwidth partially idle between bursts. This observation creates the architectural opening: if KV-Cache can be loaded into decode engines (using their otherwise-idle storage NICs) and then transferred to prefill engines over the compute network (using its spare inter-burst bandwidth), the system can aggregate the storage bandwidth of all engines rather than bottlenecking on prefill-side NICs alone.

This also explains why the approach is complementary to, rather than competing with, single-path I/O optimization: faster storage-to-prefill transfers would still leave decode-side storage NICs idle; adding a decode-side path makes both paths' bandwidth usable. The paper's bottleneck-free analysis (§4.2) formalizes this complementarity by deriving the P/D ratio range within which neither compute NICs nor DRAM bandwidth become new bottlenecks, showing that for practical configurations (𝑔 = 8 GPUs per node, 𝑠 = 1 storage NIC per node), the system remains bottleneck-free for P/D ratios from 1/7 to 7/2—"which covers most practical configurations."

A crucial implicit claim in this positioning is that **the compute network is not the bottleneck**. The paper argues this through two mechanisms: (1) the compute network has per-GPU NICs (8 × 400 Gbps per node) versus a single 400 Gbps storage NIC per node, giving it substantially higher aggregate bandwidth, and (2) model execution communications are bursty and leave idle capacity that can be opportunistically filled with KV-Cache traffic. The CNIC-centric traffic manager (§5) with InfiniBand virtual lane QoS ensures that this opportunistic use never degrades the latency-critical collective operations—the paper reserves approximately 99% of compute network bandwidth for high-priority model inference traffic and allocates the remaining bandwidth to KV-Cache transfers to prevent starvation (§5.1).

The paper's relationship to layerwise prefill is also worth noting. Layerwise prefill is not a contribution of DualPath—it is adopted from LayerKV [50] and PrefillOnly [17] as an enabling technique. Its role is to solve the HBM capacity bottleneck: without layerwise prefill, the KV-Cache for the entire batch must reside in HBM simultaneously, limiting batch size and GPU utilization. Layerwise prefill lets the GPU hold only one layer's KV-Cache at a time, increasing the effective batch size by approximately the number of layers. This is necessary background for understanding why the storage I/O bottleneck is so severe: layerwise prefill removes the HBM constraint and shifts the bottleneck to storage bandwidth, making the dual-path solution both possible (the system can now process large enough batches to saturate storage links) and necessary (storage bandwidth is now the limiting factor).

## 3. Technical Approach

### 3.1 Reader Orientation

DualPath is an inference system that modifies how KV-Cache data flows between storage and GPUs in LLM serving, specifically targeting the prefill–decode disaggregated architecture that dominates modern production deployments. The system solves the problem of **asymmetric storage bandwidth saturation**: in existing architectures, only prefill engines load KV-Cache from persistent storage, saturating their storage NICs while decode engines' storage NICs sit idle—DualPath breaks this bottleneck by introducing a second KV-Cache loading path through decode engines, leveraging their otherwise-unused storage bandwidth and then transferring the data to prefill engines over the high-bandwidth compute network via RDMA, coupled with a global scheduler that dynamically balances which path each request uses based on real-time load.

### 3.2 Big-Picture Architecture (Diagram in Words)

DualPath consists of five major components that together transform KV-Cache retrieval from a prefill-exclusive operation into a pooled, schedulable resource:

1. **Prefill Engines (PEs)** — GPUs dedicated to the prefill phase, which load KV-Cache either directly from storage (the traditional path) or receive it from decode engines via RDMA (the new path), then compute attention for newly appended tokens and transfer the complete prompt KV-Cache to decode engines.
2. **Decoding Engines (DEs)** — GPUs dedicated to autoregressive token generation, which in DualPath also serve as KV-Cache loading intermediaries: they can read KV-Cache from persistent storage into local DRAM buffers and then transfer it to prefill engines over the compute network.
3. **Persistent Storage (3FS)** — a distributed SSD-based file system with no internal DRAM cache, serving as the backing store for KV-Cache blocks, accessed via storage NICs (one 400 Gbps SNIC per node).
4. **CNIC-Centric Traffic Manager** — a per-engine component that routes all GPU-bound data (KV-Cache loads, KV-Cache stores, inter-engine transfers) through the GPU's dedicated compute NIC (CNIC) using GPUDirect RDMA, and enforces traffic isolation via InfiniBand virtual lanes so that KV-Cache transfers never interfere with latency-sensitive model execution communications (AllToAll, ReduceScatter, AllGather).
5. **Adaptive Request Scheduler** — a centralized scheduler that assigns each incoming request to a (PE, DE) pair and decides whether KV-Cache is loaded via the PE read path or the DE read path, balancing token counts across engines, storage NIC queue lengths, and attention layer execution times to prevent any single resource from becoming a bottleneck.

**Information flow:** A client submits a request containing the accumulated context and newly appended tokens → the scheduler selects which PE will handle prefill and which DE will handle decoding, then chooses the read path based on current storage NIC queue depths → if the PE read path is chosen, KV-Cache is loaded from 3FS into the PE's DRAM buffer via its SNIC, then transferred layer-by-layer into GPU HBM via the CNIC during prefill computation → if the DE read path is chosen, KV-Cache is loaded into the DE's DRAM buffer via its SNIC, then transferred layer-by-layer to the PE's GPU HBM via CNIC-to-CNIC RDMA during prefill → the PE computes attention for newly appended tokens and transfers the KV-Cache of those miss tokens to the DE → the DE merges received KV-Cache with the pre-loaded hit KV-Cache, performs H2D transfer into its own HBM, and begins autoregressive decoding → newly generated KV-Cache blocks are persisted back to 3FS via the DE's CNIC and SNIC for reuse in future turns.

### 3.3 Roadmap for the Deep Dive

- **First, the dual-path loading mechanism (§3.4.1)** — the core architectural innovation: how the PE read path and DE read path operate, what data moves where, and how transfers overlap with layerwise prefill computation. This is the foundation everything else builds on.
- **Second, the bottleneck-free analysis (§3.4.2)** — the theoretical framework that proves dual-path loading doesn't create new bottlenecks on the compute network or DRAM under practical P/D ratios. Understanding this requires the notation and traffic model established here.
- **Third, the CNIC-centric traffic manager (§3.4.3)** — why existing GPU data transfer mechanisms (GPUDirect Storage, CUDA copy engine) cannot be used, how CNIC-assisted H2D/D2H works, and how InfiniBand virtual lane QoS isolates KV-Cache traffic from model execution. This is the mechanism that makes the dual-path design safe in practice.
- **Fourth, the adaptive request scheduler (§3.4.4)** — the inter-engine scheduling algorithm that assigns requests to PE/DE pairs and selects read paths, and the intra-engine scheduling algorithm that determines batch composition to balance attention layer execution times. This ties the hardware capabilities together into a coherent policy.
- **Fifth, the KV-Cache block layout and storage design (§3.4.5)** — how Layer Blocks and Full Blocks enable efficient layerwise streaming without expensive memory layout conversions, and how the trie-based storage structure supports prefix sharing across turns.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is a **systems paper** whose core idea is that the prefill-side storage I/O bottleneck in agentic LLM inference can be eliminated not by adding more bandwidth to prefill nodes, but by **redistributing KV-Cache read traffic across the storage NICs of both prefill and decode engines**, then using the spare burst-interval capacity of the compute network to route decode-loaded KV-Cache to prefill engines. The system combines this dual-path data movement architecture with a CNIC-centric traffic isolation mechanism and a workload-aware scheduler that jointly balances GPU computation and NIC utilization.

#### 3.4.1 Dual-Path KV-Cache Loading

The central architectural innovation is that KV-Cache loading is no longer a prefill-exclusive operation. DualPath introduces two distinct data paths—the **PE read path** (traditional storage-to-prefill) and the **DE read path** (novel storage-to-decode-to-prefill)—and a scheduler that dynamically selects between them per request.

**PE Read Path (Figure 4a).** This path follows the conventional pattern but with an important modification: all GPU-bound data movement goes through the CNIC rather than directly through PCIe or GPUDirect Storage. The sequence of operations is:

1. KV-Cache of hit tokens is read from persistent storage (3FS) into the PE's host DRAM buffer via the storage NIC. The data is read in **Full Blocks**—blocks that contain all layers' KV-Cache for a set of tokens—because storage I/O performance benefits from large, contiguous reads rather than fine-grained per-layer accesses.
2. Before the computation of each attention layer, the KV-Cache for that specific layer is transferred from the PE DRAM buffer to PE GPU HBM. This transfer uses a **Layer Block** format—a byte tensor of shape `[1, tokens, bytes]` storing exactly one layer's KV-Cache—and is performed as a CNIC-assisted H2D copy (an RDMA Write from host memory to GPU memory through the compute NIC).
3. The PE then computes attention for the cache-miss tokens (the newly appended context) against the full context, producing KV-Cache for the miss tokens.
4. After layer computation completes, both the hit-token KV-Cache and the newly computed miss-token KV-Cache for that layer are transferred to the DE's DRAM buffer via CNIC-to-CNIC RDMA over the compute network. This transfer also uses Layer Blocks.
5. Steps 2–4 repeat for all `$n_{layer}$` layers—the prefill forward pass is layerwise, with transfers overlapping with computation: while layer `$i$`'s attention is being computed, layer `$i-1$`'s results are being transferred to the DE, and layer `$i+1$`'s KV-Cache is being loaded from DRAM to HBM.

After all layers complete, the DE has the full prompt KV-Cache (hit tokens + miss tokens) in its DRAM buffer. The DE then allocates HBM and performs an H2D transfer to move the KV-Cache into GPU memory, releases the CPU memory, and begins autoregressive decoding.

**DE Read Path (Figure 4b).** This is the novel path that leverages decode-side storage bandwidth. The sequence differs in a critical way: the KV-Cache is first loaded into the DE's DRAM buffer, not the PE's.

1. KV-Cache of hit tokens is read from persistent storage into the DE's host DRAM buffer via the decode node's storage NIC. Again, Full Blocks are used for efficient storage I/O.
2. Before each attention layer's computation on the PE, the KV-Cache for that layer is read from the DE's DRAM buffer and transferred directly to the PE's GPU HBM via CNIC-to-CNIC RDMA over the compute network. This transfer uses Layer Blocks and overlaps with computation—while the PE computes layer `$i$`, layer `$i+1$`'s KV-Cache is being transferred from the DE.
3. The PE computes attention for cache-miss tokens and produces their KV-Cache.
4. After layer computation completes, only the miss-token KV-Cache is transferred to the DE's DRAM buffer (the hit-token KV-Cache is already there, having been loaded in step 1). The miss-token KV-Cache is merged with the existing hit-token KV-Cache in the DE buffer.
5. Steps 2–4 repeat for all `$n_{layer}$` layers.

After prefill completes, the decode phase proceeds identically to the PE read path: the DE transfers the complete prompt KV-Cache from DRAM to HBM, releases CPU memory, and begins autoregressive generation. During decode, whenever a full block of tokens is accumulated (the paper uses a block size of 64 tokens), that block is immediately persisted to disk via the CNIC and SNIC for reuse in future turns.

**Why two block layouts?** The paper adopts both **Full Blocks** (shape `[layer, tokens, bytes]`) and **Layer Blocks** (shape `[1, tokens, bytes]`) to reconcile two competing requirements. Storage I/O benefits from large, contiguous reads, so all interactions with the storage backend use Full Blocks—reading one Full Block retrieves the entire KV-Cache for a set of tokens in a single operation. However, layerwise prefill requires feeding the GPU one layer at a time to avoid HBM capacity bottlenecks: the GPU holds only one layer's KV-Cache for the forward batch at any moment. Layer Blocks serve this need—they are the per-layer slices of a Full Block. The paper's design avoids expensive memory layout conversions by ensuring that `$n$` Layer Blocks concatenated together yield exactly one Full Block, so the system can read a Full Block from storage, then stream its constituent Layer Blocks to the GPU one by one without any data reorganization. The block size (number of tokens per block) is a configurable parameter; the paper uses 64 tokens as the block size for persistence during decode.

**DRAM buffer allocation.** Each PE and DE is provisioned with a modest DRAM buffer—80 GB per node for DeepSeek models and 320 GB per node for Qwen 32B (which has larger KV-Cache per token due to GQA rather than MLA). These buffers are staging areas, not caches: they hold KV-Cache only for the duration of the current prefill operation, and are released once the data has been transferred to GPU HBM. The paper explicitly notes that the DE buffer introduces additional bandwidth pressure on DRAM and the CNIC (an extra H2D transfer from DRAM to GPU HBM at the start of decode), but justifies this design choice on latency grounds: "since the generation length is typically short in this scenario, time-to-first-token (TTFT) accounts for a non-negligible portion of the total end-to-end request time. Introducing DE buffer helps reduce GPU memory usage." The alternative—using GPU Direct RDMA to bypass the DE buffer entirely and write KV-Cache directly into DE GPU HBM—would consume precious HBM capacity that is needed for the decode batch's working set.

**Overlap of transfers and computation.** A critical performance property of both paths is that data movement is not on the critical path—it overlaps with computation. During the prefill forward pass, while layer `$i$`'s attention is being computed on the GPU, the CNIC simultaneously transfers layer `$i+1$`'s KV-Cache from DRAM to HBM (step 2) and layer `$i-1$`'s results from PE to DE (step 4). This pipelining means that the GPU rarely stalls waiting for data: as long as the transfer time for one layer is less than the compute time for one layer, the GPU remains fully utilized. The paper's compute quota mechanism (§3.4.4) is designed to maintain this balance—it caps the attention layer execution time to ensure that compute time dominates transfer time.

#### 3.4.2 Bottleneck-Free Analysis

The paper provides a formal analysis proving that dual-path loading does not simply shift the bottleneck from storage NICs to compute NICs or DRAM—under practical P/D ratios, all resources remain below saturation. This analysis is essential because it justifies the architectural decision: if adding a second KV-Cache path created new bottlenecks elsewhere, the throughput gains would be limited.

**Notation.** The analysis defines a precise resource model of the cluster:

- `$P$` is the number of prefill nodes and `$D$` is the number of decode nodes.
- Each node has `$g$` GPUs, each with one compute NIC of bandwidth `$B$` (400 Gbps in the paper's hardware).
- Each node has one storage NIC of bandwidth `$s \times B$`, shared by all `$g$` GPUs on that node. In the paper's configuration, `$s = 1$` (one 400 Gbps SNIC per node, matching one CNIC's bandwidth).
- `$M$` is the DRAM bandwidth per machine.

**Traffic per PE-DE pair.** The analysis begins by computing the per-pair traffic under the assumption of load-balanced scheduling and fully utilized storage bandwidth. Since storage NIC bandwidth is evenly shared across all GPUs on a node, and the scheduler balances load, the traffic that each PE-DE pair contributes to a given link is derived from the total storage bandwidth divided by the number of pairs sharing that link:

- For the PE read path (Figure 4a), the traffic per pair is `$T_p = B s / (D g^2)$`.
- For the DE read path (Figure 4b), the traffic per pair is `$T_c = B s / (P g^2)$`.

These per-pair quantities are then multiplied by the number of pairs sharing each link to compute total link pressure.

**PE CNIC bandwidth.** The analysis considers read and write directions separately because PCIe is full-duplex. Read operations on the PE CNIC include PE path step 3 (H2D of hit-token KV-Cache from PE DRAM to PE HBM) and step 5 (D2H of miss-token KV-Cache from PE HBM to PE DRAM, though the paper models this as CNIC traffic). The total read-direction traffic across all pairs is:

$$2 \times T_p \times D g = 2 B s / g \leq B$$

> where `$T_p$` is per-pair PE read path traffic, `$D$` is the number of decode nodes, `$g$` is GPUs per node, `$B$` is CNIC bandwidth, and `$s$` is the storage-to-compute bandwidth ratio.

**What it computes:** the aggregate CNIC read-direction pressure on the PCIe side of all prefill GPUs combined. The factor of 2 accounts for the two read operations per pair (H2D of hit KV-Cache from DRAM, and logically reading from CNIC for the transfer to DE). The inequality `$2 B s / g \leq B$` simplifies to `$2 s / g \leq 1$`, which holds because `$s \leq g$` always in practice—there are more GPUs than storage NICs, so the per-GPU storage bandwidth fraction is at most 1.

**Why this form:** the read direction is always bottleneck-free regardless of P/D ratio because the CNIC has enough bandwidth to handle the per-GPU share of storage traffic. This is the crucial property that makes the dual-path design feasible: reading data into GPUs (either from local DRAM or from remote DE DRAM) never saturates the CNIC.

Write operations on the PE CNIC include PE path step 4 (transfer of complete layer KV-Cache from PE to DE) and DE path step 5 (transfer of miss-token KV-Cache from PE to DE, though on the DE read path this step also traverses the PE CNIC). The total write-direction traffic is:

$$(T_p + T_c) \times D g = B s / g \times (1 + D/P) \leq B$$

> where `$T_c$` is per-pair DE read path traffic and `$D/P$` is the decode-to-prefill node ratio.

**What it computes:** the aggregate CNIC write-direction pressure. Substituting the expressions for `$T_p$` and `$T_c$` yields `$B s / g \times (1 + D/P)$`. Setting this less than or equal to `$B$` and rearranging gives:

$$P/D \geq \frac{s}{g - s}$$

> where `$P/D$` is the prefill-to-decode node ratio, `$s$` is the storage-to-compute bandwidth ratio per node, and `$g$` is GPUs per node.

**What it computes:** the minimum P/D ratio below which the PE CNIC write direction becomes saturated. For `$g = 8, s = 1$`, this gives `$P/D \geq 1/7$`—as long as there is at least one prefill node for every seven decode nodes, the PE CNIC write path is not a bottleneck.

**Why this form:** the write-direction pressure depends on the P/D ratio because DE-path traffic traverses the PE CNIC when transferring KV-Cache from the DE buffer to the PE GPU. When decode nodes heavily outnumber prefill nodes (`$D/P$` large), the PE CNIC must handle proportionally more DE-path transfers. The inequality captures the point where this additional traffic would saturate the CNIC.

**DE CNIC bandwidth.** A symmetric analysis applies to the decode-side CNICs. Read operations on the DE CNIC include PE path step 8 (H2D of complete prompt KV-Cache from DE DRAM to DE HBM at decode start) and DE path steps 3 and 6 (RDMA read of KV-Cache from DE DRAM to PE HBM, plus H2D at decode start). The total read-direction traffic is:

$$(T_p + 2 T_c) \times P g = s/g \times (P/D + 2) \times B \leq B$$

**What it computes:** the aggregate DE CNIC read pressure. Substituting and rearranging yields:

$$P/D \leq \frac{g - 2s}{s}$$

For `$g = 8, s = 1$`, this gives `$P/D \leq 6$`—the prefill-to-decode ratio must not exceed 6:1, otherwise the DE CNICs become read-saturated.

Write operations on the DE CNIC include PE path steps 7 and 9 (D2H of generated KV-Cache for persistence) and DE path step 7 (D2H of generated KV-Cache for persistence). The total write-direction traffic is:

$$(2 T_p + T_c) \times P g \leq B$$

This implies:

$$P/D \leq \frac{g - s}{2s}$$

For `$g = 8, s = 1$`, this gives `$P/D \leq 3.5$`.

**DRAM pressure.** DRAM bandwidth `$M$` must accommodate both reads and writes (DRAM is half-duplex). For PE DRAM, the pressure is `$2 s B$`, which the paper states "generally does not exceed memory bandwidth." For DE DRAM, following a similar analysis, the pressure is `$(3 + 2 P/D) B s$`. Requiring this to be less than or equal to `$M$` gives:

$$P/D \leq \frac{M / (B s) - 3}{2}$$

For the paper's hardware (`$M \approx 500$` GB/s, `$B s \approx 50$` GB/s), this yields `$P/D \leq 3.5$`.

**Summary constraint.** Combining all inequalities:

$$\frac{s}{g - s} \leq P/D \leq \min\left(\frac{g - 2s}{s}, \frac{g - s}{2s}, \frac{M/(B s) - 3}{2}\right)$$

For `$g = 8$`, `$s = 1$`, and `$M \approx 500$` GB/s with `$B s \approx 50$` GB/s:

$$\frac{1}{7} \leq P/D \leq \min(6, 3.5, 3.5) = 3.5$$

The bottleneck-free range is **`$1/7 \leq P/D \leq 7/2$`**, which "covers most practical configurations." If `$P/D$` falls below 1/7, the PE CNIC write direction saturates; if `$P/D$` exceeds 3.5, the DE CNIC write direction or DE DRAM bandwidth saturates.

**Why this analysis matters.** It proves that dual-path loading is not just heuristically beneficial but theoretically sound: over a wide range of resource allocations, the system fully utilizes all storage NICs without creating new bottlenecks. The analysis also reveals the limiting resources—DE CNIC write bandwidth and DE DRAM bandwidth—which informs the scheduler design: when `$P/D$` is high (many prefill nodes, few decode nodes), the DE side becomes the constraint, and the scheduler should favor the PE read path to reduce pressure on DE resources. The paper's default experimental configurations (2P4D for DS 660B gives `$P/D = 0.5$`, 1P2D for Qwen 32B gives `$P/D = 0.5$`, 1P1D for DS 27B gives `$P/D = 1$`) all fall well within the bottleneck-free range.

#### 3.4.3 CNIC-Centric Traffic Manager

The dual-path architecture introduces a practical challenge: KV-Cache transfers now traverse the compute network and PCIe links, potentially interfering with the latency-sensitive collective communications (AllToAll, ReduceScatter, AllGather) that are critical to model execution. The paper's solution is to route **all GPU-bound data traffic through the compute NIC** and use InfiniBand virtual lane QoS to enforce strict priority separation.

**Why existing mechanisms fail.** The paper identifies two standard GPU data transfer mechanisms and explains why neither is suitable:

- **GPUDirect Storage (GDS)** loads KV-Cache directly from the storage backend to GPU HBM, bypassing host DRAM entirely. While efficient in isolation, GDS "operate[s] over separate paths that do not share the same QoS controls as the compute network" (§5). The storage network and compute network are physically isolated in the data center architecture (§2.3), so InfiniBand virtual lane QoS—which operates on the compute fabric—cannot shape GDS traffic. KV-Cache loads via GDS would contend for PCIe bandwidth with model execution communications without any prioritization mechanism.
- **CUDA copy engine** (used via `cudaMemcpyAsync`) performs direct host-to-device or device-to-host copies over PCIe. However, "existing GPUs do not support PCIe QoS," so there is no hardware mechanism to prioritize model inference communication over copy engine traffic on the PCIe bus. When a large KV-Cache transfer is in flight, latency-sensitive collective operations can be delayed, degrading end-to-end inference performance.

Additionally, the paper observes that collective communications occur in "rapid, sub-millisecond-level bursts," making it "impractical to rely on a software-based traffic shaper to interleave lower-priority I/O operations between these high-priority traffic windows." A software scheduler cannot react fast enough to exploit the microsecond-scale idle intervals between collective operations.

**CNIC-assisted H2D/D2H.** The solution is to make the compute NIC the **central QoS scheduler for all GPU PCIe traffic**. Instead of using GDS or the CUDA copy engine, DualPath explicitly routes all data through the CNIC:

1. **KV-Cache loading:** The system first reads KV-Cache from the storage backend into host DRAM via the storage NIC (a standard CPU-driven read, which does not involve the GPU or PCIe). Then, an RDMA Write request is submitted to the GPU's paired CNIC to perform the H2D copy—the CNIC reads data from host DRAM and writes it to GPU HBM over PCIe.
2. **KV-Cache storing:** Newly generated KV-Cache blocks follow the reverse path: the GPU submits an RDMA Write request to its CNIC to perform a D2H copy (GPU HBM to host DRAM over PCIe), after which the data is persisted to the storage backend via the storage NIC.

By funneling all GPU-bound data through the CNIC, the system can leverage the InfiniBand NIC's built-in virtual lane arbiter to prioritize traffic. The CNIC becomes the single point of PCIe traffic control for each GPU.

**Performance advantage of CNIC-assisted copy.** The paper reports a surprising microarchitectural finding: CNIC-assisted H2D and D2H **outperform the CUDA copy engine** when handling a large number of small data chunks—exactly the pattern that layerwise KV-Cache transfers produce. The measurements show:
- `cudaMemcpyAsync` incurs a latency overhead of approximately **5–7 μs** per submission. The paper notes they "failed to further break down this overhead due to the closed-source nature of CUDA driver."
- Submitting one RDMA Write work request involves "only a few mmio writes to NIC registers in user space and takes only around **1 μs**."

This 5–7× per-operation overhead advantage matters because layerwise prefill fragments KV-Cache transfers into many small operations (one per layer). With 30–60 layers and potentially hundreds of requests in flight, the aggregate submission overhead can become significant. The paper further notes that "the RDMA work submission overhead can be significantly amortized by leveraging doorbell batching"—a technique where multiple work requests are submitted to the NIC with a single doorbell ring, reducing per-operation overhead to near zero for batched submissions.

**Traffic isolation via InfiniBand virtual lanes.** With all traffic flowing through the CNIC, the paper uses InfiniBand's native QoS mechanisms to enforce priority separation:

- **Virtual Lanes (VLs):** InfiniBand supports up to 15 virtual lanes (VL0–VL14), each with independent buffer resources and scheduling policies. The paper configures 4 VLs (`qos_max_vls 4`).
- **Traffic classification:** All model inference communication traffic (AllToAll for expert parallelism, ReduceScatter/AllGather for tensor/context parallelism) is assigned to high-priority VLs (VL0, VL1, VL3, each with weight 192 in the high-priority arbiter). All KV-Cache transfer traffic is mapped to a low-priority VL (VL2, with weight 0 in the high-priority arbiter and weight 64 in the low-priority arbiter).
- **Arbitration policy:** InfiniBand uses a two-level arbiter. The high-priority arbiter schedules traffic using Weighted Round Robin (WRR) among VLs with non-zero weights. The `qos_high_limit` parameter (set to 240 out of 255) controls how much traffic is steered from the high-priority arbiter to the low-priority arbiter before the high-priority arbiter must yield. Setting it to 240 means approximately **94% of total bandwidth** is reserved for high-priority VLs through the high-priority arbiter, while the low-priority arbiter receives the remaining bandwidth. Within the low-priority arbiter, VL2 (KV-Cache traffic) has a weight of 64 against other VLs' weight of 192, ensuring KV-Cache traffic cannot starve but is strictly deprioritized.

The net effect, as the paper states, is that "approximately 99% of total bandwidth [is reserved] to high-priority VL," with the remaining bandwidth allocated to KV-Cache traffic "to prevent starvation." This ensures that model execution traffic is "virtually unaffected by KV-cache transfers, while still allowing KV-cache traffic to opportunistically utilize otherwise idle bandwidth in the compute network."

**Extensibility to other interconnects.** While the paper's experiments use InfiniBand, it explicitly notes that the design principles extend to other technologies:
- **RoCE (RDMA over Converged Ethernet):** QoS can be enforced through Traffic Class (TC) and Differentiated Services Code Point (DSCP) markings mapped to hardware packet queues, with Priority Flow Control (PFC) for lossless operation. The paper provides a sample four-TC configuration in Appendix A.1.
- **UnifiedBus and Ultra Ethernet:** These emerging technologies "are likewise converging on QoS mechanisms for heterogeneous traffic, which can directly support the requirements of DualPath."

#### 3.4.4 Adaptive Request Scheduler

The scheduler is responsible for two levels of decision-making: **inter-engine scheduling** (which assigns requests to specific PE/DE pairs and selects the KV-Cache read path) and **intra-engine scheduling** (which determines the composition of each forward batch on prefill engines to balance attention layer execution times).

**Inter-Engine Scheduling: PE Assignment.** The PE scheduling algorithm (Algorithm 1 in the paper) operates as follows:

When a PE group initiates a fetch request (engines proactively fetch tasks together regularly, with only the rank-0 Leader Engine interacting with the scheduler), each engine `$e$` in the group reports three metrics:
- `$seq_e$`: the number of requests currently assigned to engine `$e$` that have not yet completed.
- `$tok_e$`: the total token count across those `$seq_e$` requests.
- `$read\_qn(e)$`: the disk reading queue length (number of outstanding I/O requests) on the node `$n(e)$` that engine `$e$` belongs to.

The scheduler uses token count as a **proxy for load** across three dimensions simultaneously: GPU compute load (more tokens = more attention computation), disk read load (more tokens = more KV-Cache to retrieve), and network load (more tokens = more data to transfer). This proxy is justified because all three resources scale roughly linearly with the number of tokens processed.

The algorithm classifies all PEs in the group into three categories using two configurable thresholds:
- **Category 1 (overloaded):** engines where `$tok_e > \beta$`. These engines are excluded from new assignments to prevent overloading. The threshold `$\beta$` is "set to the number of tokens one GPU can process for 5 seconds," profiled in advance.
- **Category 2 (short disk queue):** engines on nodes where `$read\_qn(e) \leq \alpha$` AND `$tok_e \leq \beta$`. The threshold `$\alpha$` is "set to the number of tokens we can read during 3 seconds," also profiled in advance.
- **Category 3 (long disk queue):** engines on nodes where `$read\_qn(e) > \alpha$` AND `$tok_e \leq \beta$`.

Requests from the global waiting queue are assigned in FIFO order. For each request:
1. If Category 2 is non-empty, assign to the PE in Category 2 with the minimum `$tok_e$` (least loaded among engines on nodes with short disk queues).
2. Else if Category 3 is non-empty, assign to the PE in Category 3 with the minimum `$tok_e$`.
3. Else (both categories empty), terminate the fetch request and return already-assigned requests to the Leader Engine—no more requests can be assigned because all eligible engines are overloaded.

After assignment, the selected PE's `$tok_e$` is updated by adding the token count of the assigned request, and the algorithm proceeds to the next request in the waiting queue.

**Why this three-category design?** Category 2 engines are prioritized over Category 3 because they reside on nodes with shorter disk reading queues. If the scheduler assigned requests to Category 3 engines while Category 2 engines had spare capacity, those Category 2 engines' storage NICs might become underutilized once their current reads complete—the requests they are currently processing would finish, but no new requests would be waiting to keep the storage NIC busy. By prioritizing nodes with short disk queues, the scheduler ensures that storage NICs remain continuously saturated.

**Inter-Engine Scheduling: DE Assignment.** DE scheduling is two-level and does not preserve global FIFO ordering. The rationale is that decode engines must balance token count across groups and HBM capacity within groups simultaneously.

**Phase 1 (across groups):** The scheduler maintains a global waiting queue and a private queue per DE group. When a DE group fetches, the group-level scheduler drains the global queue and assigns each request to the group whose total `$tok_e$` (summed over all engines in the group) is minimum. This balances token count across groups, which in turn balances NIC and GPU load.

**Phase 2 (within a group):** The scheduler calculates the sum of remaining HBM across all DEs in the group and estimates how many requests from the group's private queue can be scheduled, assuming no HBM fragmentation. This provides an upper bound on the number of schedulable requests. It then computes a high-token threshold:

$$Z = 1.05 \times \left( \sum_{r \in R} len_r + \sum_{e \in E} tok_e \right) / |E|$$

> where `$R$` is the set of candidate requests, `$len_r$` is the token count of request `$r$`, `$E$` is the set of DEs in the group, and `$tok_e$` is the current token count on engine `$e$`.

**What it computes:** a target maximum token count per engine that, if all engines were at or below this value, would leave the group load-balanced. The 1.05 multiplier allows a small overshoot (5%) to avoid being overly restrictive.

**Why this form:** The threshold `$Z$` represents the mean token count per engine after scheduling all candidate requests. Engines already above `$Z$` are considered "high-token" and deprioritized for new assignments to prevent them from falling further behind. The 5% slack prevents the scheduler from stalling when a single engine is slightly above the ideal mean.

For each request popped from the head of the private queue:
1. Among DEs with sufficient remaining HBM for the request, partition into Category 1 (high-token DEs where `$tok_e + len(r) > Z$`) and Category 2 (the rest).
2. Prefer Category 2—among Category 2 engines, choose the one with minimum `$seq_e$` (fewest assigned requests) to balance request count.
3. If Category 2 is empty, choose the DE in Category 1 with minimum `$tok_e$` to reduce HBM exhaustion and preemption risk.
4. If no DE has sufficient HBM, the fetch ends and already-assigned requests are returned.

**KV-Cache Read Path Selection.** After a (PE, DE) pair is selected for a request, the scheduler chooses the read path by a simple rule: **read on the side with the shorter reading queue** (`$read\_qn$`). If the PE's node has a shorter disk queue, the PE read path is used; if the DE's node has a shorter queue, the DE read path is used. The paper notes that splitting a single request's KV-Cache read across both paths "is probably better" but leaves it as future work.

**Intra-Engine Scheduling: Compute Quota.** Only PEs require intra-engine scheduling—DEs always place all assigned requests into the forward batch because decode is memory-bound and latency-sensitive, so maximizing batch size within HBM constraints is always beneficial. For PEs, the challenge is balancing attention layer execution times across GPUs in the same data-parallel group.

**The problem.** When data parallelism is used for attention layers (which is common for MLA models), each GPU in the parallel group serves a different subset of requests. If these subsets have different total token counts (different amounts of attention computation), the GPUs will finish their attention computation at different times. Since all GPUs must synchronize after the attention stage (e.g., before entering the FFN stage in an expert-parallel configuration), the faster GPUs sit idle waiting for the slowest one—creating GPU bubbles.

**Layer time estimation.** Each request in a forward batch is described by a pair `$(cached, bsz)$`:
- `$cached$`: the number of tokens whose KV-Cache is already available (from storage hits or previous forward passes)—these tokens require loading KV-Cache but no new attention computation.
- `$bsz$`: the number of tokens requiring fresh KV-Cache computation in this forward batch—these tokens require both loading existing KV-Cache and computing attention for the appended context.

From these pairs, the scheduler computes the total theoretical computation for the attention layer. The relationship between theoretical computation and wall-clock time is hardware- and parallelism-dependent, so the paper fits this mapping in advance through offline profiling, similar to the approach in PrefillOnly [17] and Sarathi-Serve [2].

**The compute quota algorithm.** The scheduler maintains a predefined upper bound on attention layer execution time, called the **compute quota**, set to 300 ms for all DualPath and Oracle baselines. Requests are added to the forward batch in FIFO order as long as the predicted attention layer execution time does not exceed this quota. If adding a request would exceed the quota, the scheduler performs a binary search on `$bsz$` to find a smaller `$bsz'$` that fits within the remaining quota, then performs **chunked prefill** for that request—processing only `$bsz'$` of its appended tokens in this forward batch and deferring the rest to a subsequent batch.

The 300 ms compute quota balances two objectives: keeping the GPU busy (longer quota = larger batches = better GPU utilization) and keeping transfer times hidden (longer quota = more time spent computing each layer = transfers for other layers are more likely to complete before the next attention computation starts). If the quota is too short, batch sizes are small and GPU utilization suffers. If the quota is too long, the pipeline depth (number of layers being transferred concurrently) may be insufficient to hide transfer latency.

**Effect on GPU timeline (Figure 6, right).** The paper illustrates the effect of compute-quota-based batching on the GPU execution timeline. Without compute quota, different GPUs in a parallel group may have substantially different attention execution times, leading to idle bubbles where faster GPUs wait for the slowest peer at the synchronization barrier. With compute quota, the scheduler intentionally caps the attention execution time, and the binary search on `$bsz$` ensures that all GPUs in the group process roughly equal amounts of computation, minimizing the idle time at the barrier. The profile-fitted time estimation ensures that the cap corresponds to actual wall-clock time rather than a crude token-count heuristic.

#### 3.4.5 KV-Cache Block Layout and Storage Design

The paper's block layout design addresses a tension between storage I/O efficiency and layerwise computation granularity, while the storage structure exploits the prefix-sharing property inherent to multi-turn agentic workloads.

**Two block types.** DualPath defines two distinct KV-Cache block formats:

- **Layer Block:** a byte tensor with shape `[1, tokens, bytes]`, storing the KV-Cache for exactly one layer of `$tokens$` tokens. The `$block\_size$` (number of tokens per block) is a configurable parameter; the paper uses 64 tokens for persistence during decode but does not specify the exact block size for storage reads.
- **Full Block:** a byte tensor with shape `[layer, tokens, bytes]`, storing the KV-Cache for all `$layer$` layers of `$tokens$` tokens. A Full Block is exactly the concatenation of `$n_{layer}$` Layer Blocks for the same set of tokens.

**Why two types?** The design solves a layout conversion problem. Storage I/O performs best with large, contiguous reads—reading one Full Block retrieves all layers' KV-Cache for a token range in a single operation, maximizing throughput on the SSD-based storage backend. However, layerwise prefill requires feeding the GPU one layer at a time: the GPU allocates HBM for only one layer's KV-Cache at a time (to maximize batch size), so it needs Layer Blocks. Without the two-type design, the system would need to read Full Blocks from storage and then reorganize the data in memory to extract per-layer slices—an expensive operation that would negate the throughput gains from dual-path loading. By defining Layer Blocks and Full Blocks such that concatenation is the only operation needed to convert between them, DualPath eliminates this reorganization: the storage system reads Full Blocks, and the transfer layer streams individual Layer Blocks to the GPU by slicing the Full Block in-place (or equivalently, transferring contiguous byte ranges of the Full Block that correspond to individual layers).

**Trie-based storage structure.** KV-Cache is stored in the distributed file system (3FS) using a **trie** (prefix tree) structure, where each tree node corresponds to a Full Block. This design exploits the fact that in multi-turn agentic workloads, consecutive turns share a common context prefix—turn `$i+1$`'s context is turn `$i$`'s context plus some appended tokens (Figure 2). In a trie, the shared prefix between turns `$i$` and `$i+1$` is stored only once, with the divergent suffix stored as a new branch. This prefix sharing reduces total storage footprint and, more importantly, means that when loading KV-Cache for a new turn, the system can traverse the trie from the root, reading only the Full Blocks along the path to the current context length. The paper does not provide detailed trie implementation specifics (e.g., node fanout, block addressing, or garbage collection), but the high-level design follows the standard prefix-caching pattern used in systems like Mooncake [38] and HiCache [40].

**KV-Cache persistence during decode.** During the decode phase, whenever a full block of tokens is accumulated—the paper specifies a block size of 64 tokens—it is immediately persisted to disk. This eager persistence ensures that if a request is preempted or a node fails, only the most recent partial block (fewer than 64 tokens) is lost. The persistence path uses the CNIC-assisted D2H transfer: the GPU writes the generated KV-Cache block to host DRAM via an RDMA Write through the CNIC, then the host writes it to 3FS via the storage NIC. Both steps use the low-priority VL, so they do not interfere with ongoing decode computations or KV-Cache prefill transfers for other requests.

#### 3.4.6 Design Choices and Their Justifications

**Why dual-path rather than simply adding more storage bandwidth to prefill nodes?** The paper argues this is "costly and often impractical in general-purpose clusters." In a disaggregated architecture with physically isolated storage and compute networks, adding storage bandwidth to prefill nodes requires additional storage NICs and switch ports on the storage fabric—an infrastructure change that may not be possible without re-cabling or re-provisioning. DualPath achieves the same aggregate bandwidth without hardware modification by using bandwidth that already exists (decode-side SNICs) but is currently idle.

**Why CNIC-centric rather than GPUDirect Storage?** The paper reports that GDS and CUDA copy engine "fail to isolate KV-Cache traffic from high-priority latency-sensitive collective communications in model execution, severely degrading inference performance." The CNIC-centric approach is described as "to our best knowledge... the only practical method to ensure that KV-Cache load/store does not degrade the performance of critical model-execution communication." The sacrifice is an extra hop through host DRAM, but this is justified by the severe latency consequences of PCIe contention on collective operations that occur in sub-millisecond bursts.

**Why token count as a unified proxy for load?** The scheduler uses `$tok_e$` (total tokens assigned to an engine) as a proxy for three different resources: GPU compute load, disk I/O load, and network load. The paper states that "GPU load, disk read load, and network load are all strongly correlated with token count." This is because attention computation scales quadratically with total context length but the dominant factor is the prefill computation for appended tokens (which scales linearly with append length), KV-Cache read volume scales linearly with hit-token count, and CNIC transfer volume scales linearly with total tokens transferred. Using token count as a single metric simplifies the scheduling algorithm and avoids the complexity of maintaining separate load metrics that may be mutually inconsistent.

**Why 300 ms compute quota?** The paper does not provide an ablation study of different compute quota values, but the choice reflects a balance specific to the hardware and model configuration. A 300 ms attention layer execution time means that for a model with `$n_{layer}$` layers, the total prefill time per batch is approximately `$n_{layer} \times 300$` ms (assuming perfect overlap of transfers). For DS 660B with 60+ layers, this would be approximately 18+ seconds per batch—long enough to keep the GPU busy but short enough that the per-layer transfer time (tens of milliseconds for a Layer Block) is well-hidden within the 300 ms compute window. The paper notes that this value is "profiled in advance," suggesting it is tuned to the specific hardware's compute-to-bandwidth ratio.

**Why 64-token block size for persistence?** The paper does not elaborate on this choice, but 64 tokens is a common granularity in LLM serving systems (matching the page size in PagedAttention [26]). A smaller block size would increase the number of I/O operations during persistence (more frequent but smaller writes), while a larger block size would increase the amount of KV-Cache lost on failure or preemption. 64 tokens balances these concerns: at decode speeds of tens of tokens per second, a block is accumulated every few seconds, which is frequent enough that failure recovery loses at most a few seconds of work.

## 4. Key Insights and Innovations

### Innovation 1: The Bottleneck Is Structural Asymmetry, Not Aggregate Bandwidth

The paper's most fundamental intellectual contribution is **reframing the KV-Cache I/O problem from a quantitative shortage to a structural imbalance**. Prior work on KV-Cache I/O optimization—whether through hierarchical caching (Mooncake [38]), GPU-assisted I/O (Strata [49]), partial recomputation (KVPR [23]), or quantization (TailorKV [53])—implicitly treated the problem as one of insufficient bandwidth along the storage-to-prefill path. The implicit assumption was: if we can make this single path faster, throughput will improve proportionally. DualPath rejects this framing. The paper's diagnostic observation—shown concretely in Figure 1—is that prefill-side storage NICs are 100% utilized while decode-side storage NICs are idle. The *aggregate* storage bandwidth in the cluster is sufficient; it is simply **allocated asymmetrically** because the architecture assumes KV-Cache loading is a prefill-exclusive operation.

This is a conceptual shift, not an incremental optimization. It changes the problem from "how do we get more bandwidth to prefill engines?" to "how do we use the bandwidth that already exists but is sitting idle on decode engines?" The distinction matters practically: adding bandwidth to prefill nodes requires hardware re-provisioning (more NICs, more switch ports, potentially re-cabling), while DualPath's approach is a software-only re-routing of data through existing infrastructure. It also matters intellectually: it reveals that the PD-disaggregated architecture, despite being the de facto standard for LLM serving, contains a **latent design assumption** — that storage I/O is a prefill responsibility — that is valid for compute-bound workloads but becomes pathological under I/O-bound agentic workloads. The paper shows this is not a minor inefficiency but a structural flaw that grows worse with each hardware generation, as GPU FLOPS outpace NIC bandwidth by 14.4× from Ampere to Blackwell (Figure 3, left).

The evidence for this reframing is not just the performance numbers but the **analytical framework in Section 4.2**. The bottleneck-free analysis derives the P/D ratio range (1/7 to 7/2) within which dual-path loading saturates all storage NICs without creating new bottlenecks on compute NICs or DRAM. This analysis proves that the architectural assumption — not a physical limit — was the binding constraint. The experimental confirmation in Figure 8 (varying P/D ratios for DS 27B) reinforces this: each pair of configurations with equivalent available storage bandwidth (e.g., DualPath 1P1D vs. Basic 2P1D, both having one prefill node's worth of storage bandwidth usable by DualPath through decode-side NICs) performs comparably, confirming that "storage bandwidth is the dominant bottleneck."

### Innovation 2: The Compute Network as Opportunistic KV-Cache Fabric

The second distinctive idea is **repurposing the compute network's idle inter-burst capacity as a KV-Cache transport fabric**. This is not an obvious move. The standard data center architecture (§2.3) physically isolates compute and storage networks precisely to prevent interference — the compute network is for latency-sensitive GPU-to-GPU communications, and the storage network is for bulk data movement. Prior systems respected this separation: KV-Cache traveled exclusively on the storage fabric, and the compute network was reserved for model execution collectives. DualPath violates this isolation deliberately, but not recklessly.

The key enabling observation is that model execution communications are **bursty at sub-millisecond granularity**. Collective operations like AllToAll (for expert parallelism) and ReduceScatter/AllGather (for tensor/context parallelism) consume bandwidth in rapid spikes, leaving the compute network's substantial aggregate capacity (8 × 400 Gbps per node versus 1 × 400 Gbps for storage) partially idle between bursts. This temporal gap — not visible in average utilization metrics but real at the microarchitectural level — creates an opportunity to opportunistically fill the compute network with KV-Cache traffic without contending with model execution.

What makes this intellectually significant rather than merely clever is the **QoS mechanism that makes it safe** (§5.1). The paper observes that existing GPU data transfer mechanisms (GPUDirect Storage, CUDA copy engine) lack QoS controls that can prioritize model execution traffic over KV-Cache transfers. GDS operates on the storage fabric, bypassing the compute network's QoS entirely. The CUDA copy engine contends for PCIe bandwidth without any hardware prioritization. The CNIC-centric approach — routing all GPU-bound data through the compute NIC and using InfiniBand virtual lanes to reserve ~99% of bandwidth for high-priority model traffic — is described as "to our best knowledge... the only practical method" to achieve safe coexistence. This is a systems insight with broad applicability: it establishes a pattern for safely multiplexing latency-sensitive and bulk traffic on the same physical fabric in GPU clusters, which matters as converged interconnects like UnifiedBus and Ultra Ethernet become more prevalent.

The paper strengthens this claim by extending the design to RoCE and emerging standards (Appendix A.1), arguing that the same QoS principles apply wherever hardware packet queues and priority classes exist. This generality suggests the insight is not InfiniBand-specific but architectural: the compute network, properly managed, can serve as a secondary data fabric without compromising its primary function.

### Innovation 3: Token-Count-as-Unified-Load-Proxy Scheduling

The third contribution is conceptual rather than algorithmic: **the recognition that token count serves as a single sufficient statistic for three seemingly independent resource dimensions** — GPU computation, storage I/O, and network bandwidth — enabling a simple but effective scheduling policy. The inter-engine scheduler (§6.1, Algorithm 1) balances solely on `tok_e` (total tokens assigned to an engine), plus a disk queue length signal for read path selection. There is no separate model for GPU utilization, no network congestion controller, and no storage bandwidth estimator. The algorithm is trivially simple: classify engines into three categories based on whether they exceed a token threshold and whether their node's disk queue is short or long, then assign to the least-loaded eligible engine.

This simplicity works because agentic workloads exhibit a structural property that the paper identifies but does not name explicitly: **token-proportional resource consumption**. For a given model and hardware configuration, attention computation scales with the number of cache-miss tokens; KV-Cache read volume scales with the number of hit tokens; and CNIC transfer volume scales with total tokens transferred. All three scale roughly linearly with total token count, differing only by constant factors determined by model architecture and hardware bandwidth. This means a single load metric — tokens — captures all three constraints simultaneously, avoiding the complexity of multi-dimensional load balancing that would require weighting GPU load against I/O load against network load.

The significance of this insight extends beyond DualPath. It suggests that for I/O-bound LLM workloads with high KV-Cache hit rates, the scheduling problem reduces from a multi-resource optimization to a single-resource one, dramatically simplifying scheduler design. The paper validates this proxy empirically: Figure 13 shows that the scheduling algorithm improves storage NIC load balance (max/avg ratio) from 1.53 to 1.18 compared to round-robin, and Figure 14 shows that attention layer execution time balance improves correspondingly (max/avg ratio as low as 1.06 early in the workload). The compute quota mechanism for intra-engine scheduling (§6.2) extends the same logic to the batch level, using profiled computation-to-wall-clock mappings to ensure balanced attention execution times across GPUs in a data-parallel group.

### Innovation 4: The Correct-to-Incorrect Reversion Problem and Its Mitigation

While the paper does not frame this as a primary contribution, there is an important **implicit negative finding** embedded in the DE buffer design choice that has broader implications. The paper notes that the DE buffer — which stages KV-Cache in host DRAM before decoding — "imposes bandwidth pressure on DRAM and CNIC (an extra H2D)" and could be avoided by using GPU Direct RDMA to bypass it entirely. The justification for keeping the buffer is revealing: GPU HBM is scarce during decode, and "time-to-first-token (TTFT) accounts for a non-negligible portion of the total end-to-end request time" in short-generation agentic settings, so conserving HBM for the decode batch's working set takes priority over eliminating the extra H2D.

This tradeoff surfaces a more general principle: **in I/O-bound inference systems, the optimization target shifts from minimizing data movement to strategically staging data across the memory hierarchy to protect the scarcest resource at each phase**. HBM is the bottleneck during decode (memory-bound autoregressive generation); DRAM and CNIC bandwidth are more abundant. Accepting an extra H2D at decode start — moving data from DRAM to HBM through the CNIC — is a deliberate choice to keep HBM free for the decode batch rather than holding the entire prompt KV-Cache in GPU memory. This is the inverse of the standard optimization heuristic ("avoid copies"), and it represents a phase-aware memory management strategy that is likely applicable to other I/O-bound inference systems.

The paper does not ablate this design choice (no comparison against a GPU Direct RDMA baseline), so its significance is interpretive rather than experimentally validated. However, the reasoning is consistent with the system's overall philosophy: identify which resource is the binding constraint at each stage, and provision the others liberally to relieve it. During prefill, the constraint is storage bandwidth; during decode, it is HBM capacity. The architecture allocates resources accordingly.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper uses three agent trace datasets collected from "production agentic RL training workloads" with varying maximum context lengths (MaxLen): 32K, 48K, and 64K tokens. Each dataset contains 500 trajectories. The mean interaction turns range from 60 to 157, with average append lengths of 429–608 tokens and average generation lengths of 148–176 tokens per turn (Table 2). The mean KV-Cache hit rate is reported as 98.7% for the 64K dataset (429 append tokens into an average context of 32,721 tokens). The agent task involves diagnosing and fixing bugs in a code repository within a sandbox environment, with the model invoking bash commands via tool-use over multi-turn interactions (Appendix A.3). This is production workload data, not a public benchmark, so direct reproducibility is limited.

- **Base model(s).** Three models are evaluated: (1) **DeepSeek V3.2 660B** (denoted DS 660B), a Mixture-of-Experts model with DeepSeek Sparse Attention and Multi-head Latent Attention; (2) a **27B downscaled variant** of DS 660B (denoted DS 27B), which is an internal experimental model with similar architecture but reduced dimensions (hidden dimension 2560, 30 layers, 72 routed experts with 6 activated per token, 2 shared experts—details in Appendix A.2); (3) **Qwen2.5-32B**, a dense model with Grouped-Query Attention. DS 660B and Qwen 32B use publicly released HuggingFace checkpoints; DS 27B is internal. The models span different attention mechanisms (MLA, sparse attention, GQA) and model scales (27B to 660B), chosen to demonstrate generality of the approach across architectures where the cache-compute ratio varies substantially (Table 1: 13–36 GB/PFLOP for DS 660B, 39–60 for a comparable MoE model, 117–267 for Qwen 32B at FP16).

- **Metrics.** For offline inference, the primary metric is **job completion time (JCT)** — the wall-clock time from when all agents start simultaneously until all requests finish. For online serving, three latency metrics are reported: **time-to-first-token (TTFT)**, **time-to-second-token (TTST)**, and **time-per-output-token (TPOT)**. The service-level objective (SLO) for online serving is defined as TTFT ≤ 4 seconds and TPOT ≤ 50 ms. For online throughput, the metric is **agent arrival rate per second (APS)** — the maximum Poisson arrival rate the system can sustain without violating the SLO. For load balance, the paper reports the max-to-average ratio of storage NIC traffic across nodes and the max-to-average ratio of attention layer execution time across GPUs in an expert-parallel group.

- **Baselines.** Four baselines are used:
  - **SGL(MC)**: SGLang (commit 19089aa) with HiCache enabled, Mooncake Store enabled, 3FS as the storage backend, and Mooncake Transfer Engine for prefill-decode disaggregation. This represents the state-of-the-art open-source inference stack. SGL(MC) was not evaluated for DS 27B because SGLang "lacks support for this downscaled version."
  - **Basic**: The paper's unmodified internal inference framework, described as using FlashMLA, DeepGEMM, and DeepEP kernels with 3FS for distributed storage. This is the direct predecessor to DualPath — all performance improvements are reported as speedup of DualPath (Ours) over Basic.
  - **Oracle**: A configuration based on DualPath that "bypass[es] all disk reads, D2H & H2D transfers, and inter-PD KV-Cache transfers," representing the theoretical performance upper bound assuming zero I/O overhead. This is not a realistic baseline but serves to quantify how much of the remaining performance gap is due to I/O versus computation.
  The paper notes that "Comparing DualPath and SGL(MC) is unfair due to implementation differences. Therefore, we only report performance improvements from Basic to Ours."

- **Generation budget / compute accounting.** Test-time compute is measured implicitly through the fixed hardware configuration and workload parameters rather than through an explicit "generation budget" as in search-based papers. The key controlled variables are: number of agents (batch size, ranging from 32 to 4096 for offline; APS for online), maximum agent context length (32K, 48K, 64K), append length scaling, generation length scaling, and prefill-decode node ratio (1P1D, 1P2D, 2P1D for DS 27B; 2P4D for DS 660B; 1P2D for Qwen 32B). All configurations use the same hardware (8× NVIDIA Hopper GPUs per node, 400 Gbps CNICs and SNICs) and the same storage backend (3FS with no internal DRAM cache). KV-Cache data type defaults to FP8. Speculative decoding is disabled for all settings.

- **Cross-validation / statistical protocol.** No cross-validation or statistical significance testing is reported. The offline experiments run a fixed set of trajectories to completion and measure JCT. The online experiments use Poisson arrivals and terminate when either TTFT exceeds 4 seconds or the system reaches steady state (defined as TTFT variation within a 150-second sliding window remaining below 5% compared to that 30 minutes prior). Fluctuation in the last 150 seconds before termination is shown as shadow regions in Figure 10. The paper does not report confidence intervals or multiple runs with different random seeds.

### Main Quantitative Results

#### Offline Batch Inference: Throughput Scaling with Agent Batch Size and Context Length

The headline result for offline inference is that DualPath achieves **up to 1.87× speedup over Basic** on DS 660B at 64K MAL with 2048 agents, and closely approaches Oracle performance, indicating that "KV-cache I/O is largely eliminated" (Figure 7, middle row).

**DS 660B results (Figure 7, middle row).** At 32K MAL, JCT decreases from approximately 7000–8000 seconds for Basic at 512 agents to roughly 5500–6000 seconds for DualPath, with Oracle at approximately 5000–5500 seconds. At 48K MAL and 2048 agents, Basic's JCT is approximately 16000 seconds, DualPath achieves approximately 8500 seconds (1.88× speedup), and Oracle reaches approximately 8200 seconds. At 64K MAL and 4096 agents, Basic's JCT is approximately 22500 seconds, DualPath achieves approximately 12000 seconds (~1.87×), and Oracle is approximately 11000 seconds. Across all configurations, DualPath's JCT is within 3–7% of Oracle, confirming that the dual-path architecture effectively eliminates the I/O bottleneck. SGL(MC) encountered errors at multiple large configurations (marked as N/A in Figure 7) and generally performed worse than Basic where it completed, though the paper cautions against direct comparison due to implementation differences.

**DS 27B results (Figure 7, top row).** DualPath achieves up to 1.78× over Basic but remains 1.09–1.85× slower than Oracle. At 32K MAL and 2048 agents, Basic's JCT is approximately 3500 seconds, DualPath is approximately 2000 seconds (~1.75×), and Oracle is approximately 1200 seconds. At 64K MAL and 1024 agents, Basic's JCT is approximately 18000 seconds, DualPath achieves approximately 10000 seconds (~1.8×), and Oracle is approximately 5500 seconds. The larger gap between DualPath and Oracle on DS 27B compared to DS 660B is attributed to "limited storage bandwidth in 1P1D" (Figure 8) — with only one prefill node and one decode node, the aggregate available storage bandwidth is smaller, and DualPath cannot fully hide all I/O latency.

**Qwen 32B results (Figure 7, bottom row).** Trends are similar to DS 27B. At 32K MAL and 128 agents, Basic's JCT is approximately 5000 seconds, DualPath achieves approximately 3500–4000 seconds (~1.25–1.43×), and Oracle is approximately 3000 seconds. At 64K MAL and 64 agents, Basic is approximately 6500 seconds, DualPath is approximately 4000 seconds (~1.63×), and Oracle is approximately 3200 seconds. The smaller relative improvement over Basic compared to DS models is consistent with Qwen 32B's larger KV-Cache size (GQA vs. MLA), which increases cache-compute ratio and makes the I/O bottleneck harder to fully eliminate — even Oracle cannot hide all the I/O because the sheer volume of data per token is higher.

**Dependency on batch size and context length.** Across all models and MALs, the speedup of DualPath over Basic increases with larger agent batch sizes and longer MALs. For DS 660B at 64K MAL: at 512 agents, Basic JCT is approximately 16000 seconds and DualPath is approximately 12000 seconds (~1.33×); at 4096 agents, Basic is approximately 22500 seconds and DualPath is approximately 12000 seconds (~1.87×). This is because larger batch sizes and longer contexts increase I/O pressure: more agents mean more concurrent KV-Cache reads, and longer contexts mean larger reads per request. Basic's single-path architecture saturates prefill-side SNICs earlier, leaving additional agents queued; DualPath's aggregated storage bandwidth scales more effectively with workload intensity.

#### Offline Batch Inference: Sensitivity to Append Length and Generation Length

**DualPath's advantage is largest when append and generation tokens are short** (Figure 9). Longer append lengths increase GPU compute pressure (more attention computation for appended tokens), shifting the bottleneck toward computation and reducing the relative benefit of faster I/O. Longer generation lengths increase the time between prefill phases (the decode phase is longer), giving Basic's prefill-side SNICs more time to complete reads before the next prefill batch, which also reduces I/O pressure.

For append length scaling (DS 660B, 64K MAL, 1024 agents; Figure 9, left): At 1× append scale, Basic JCT is approximately 4500 seconds, DualPath is approximately 2200 seconds (~2.05×), Oracle is approximately 2000 seconds. At 3× append scale, Basic JCT increases to approximately 4000 seconds? Wait — this appears to be an error in my reading. The figure shows Basic decreasing from ~4500 at 1× to some lower value at higher append scales, while DualPath and Oracle remain relatively flat. The paper states: "With append length increases, Basic performance gradually approaches DualPath and Oracle, while DualPath and Oracle performance changes only slightly, indicating that the bottleneck consistently lies in GPU compute pressure. Compared to Basic, DualPath achieves 1.82−1.99× speedup at different append scales."

The mechanism: at low append lengths, Basic is I/O-bound (SNIC saturated, GPU idle waiting for KV-Cache). As append length increases, the GPU must compute more attention for the additional appended tokens, making Basic less I/O-bound because the same amount of KV-Cache loading is now spread over more computation time. DualPath and Oracle are already near the compute-bound regime, so adding computation (more appended tokens) affects them proportionally — their JCT stays approximately constant because the bottleneck is now GPU throughput, which is the same across all configurations.

For generation length scaling (Figure 9, right): The trend is similar. At 1× generation scale, Basic JCT is approximately 4500 seconds; at 3× scale, Basic decreases substantially while DualPath and Oracle remain relatively flat. The mechanism: longer generation means more time between prefill phases, allowing Basic's single SNIC to keep up with the KV-Cache reading demand (lower average I/O pressure). For DualPath, the I/O pressure is already distributed across all SNICs, so the additional decode time doesn't provide as much marginal benefit.

**Critical interpretation:** These scaling experiments reveal that **DualPath's benefit is most pronounced precisely where agentic workloads are most I/O-bound**: short appends (tool outputs, user feedback) and short generations (single actions or responses). This is the dominant pattern in the paper's production traces (mean append 429, mean generation 148–176), so the reported speedups are representative of actual agentic workload characteristics.

#### Offline Batch Inference: Varying Prefill-Decode Ratio

**Across all P/D ratios, DualPath demonstrates substantial performance gains compared to Basic, with the magnitude of gain confirming that storage bandwidth is the dominant bottleneck** (Figure 8, DS 27B, 64K MAL, varying agents).

At 512 agents, 64K MAL, 1P1D: Basic JCT is approximately 1200 seconds, DualPath is approximately 550 seconds (~2.18×). At 2P1D: Basic is approximately 700 seconds, DualPath is approximately 350 seconds (~2.0×). At 1P2D: Basic is approximately 1300 seconds, DualPath is approximately 700 seconds (~1.86×). Across 1024 and 2048 agents, the patterns are consistent.

**Configurations with equivalent available storage bandwidth perform comparably** regardless of whether the bandwidth comes from prefill or decode nodes. Specifically:
- Basic 1P1D and Basic 1P2D perform comparably — both configurations can only use prefill-side SNICs (one node's worth in 1P1D, one prefill node's worth in 1P2D), so available storage bandwidth is similar despite different total node counts.
- DualPath 1P1D and Basic 2P1D perform comparably — DualPath 1P1D aggregates both nodes' storage bandwidth (prefill + decode) via dual-path loading, while Basic 2P1D has two prefill nodes' worth of bandwidth but can only use prefill-side SNICs, resulting in equivalent effective bandwidth.
- DualPath 2P1D and DualPath 1P2D perform comparably — both have two nodes contributing storage bandwidth, just allocated differently between prefill and decode.

The paper states this "confirms that storage bandwidth is the dominant bottleneck in agentic scenarios." If something else were the primary constraint (e.g., GPU computation, CNIC bandwidth, or DRAM bandwidth), configurations with identical compute resources but different storage bandwidth would not produce matching performance.

#### Online Serving: Throughput and Latency Under Poisson Arrivals

**DualPath achieves substantially higher sustainable APS than Basic while maintaining comparable latency:** 2.25× higher for DS 660B (0.55 APS for Ours vs. 0.25 for Basic) and 1.67× higher for DS 27B (0.55 APS for Ours vs. ~0.33 for Basic), as shown in Figure 10.

**DS 660B online results (Figure 10, bottom row).** For Basic, TTFT remains below the 4-second SLO up to approximately 0.25 APS, after which the experiment terminates (TTFT would exceed SLO at higher rates). At 0.25 APS, Basic's median TTFT is approximately 2.5–3 seconds. For DualPath, TTFT stays within SLO up to 0.55 APS, with median TTFT at 0.4 APS around 1.5 seconds, at 0.5 APS around 2.5 seconds, and at 0.55 APS approaching 3.5–4 seconds (still within SLO). Oracle achieves TTFT under 0.5 seconds even at 0.55 APS. SGL(MC) TTFT is substantially higher than Basic at 0.1–0.25 APS (ranging from 3–4+ seconds) and terminates earlier.

TTST (time to second token) is comparable between DualPath and Basic — both around 0.15–0.2 seconds across all APS — confirming that the dual-path architecture does not introduce additional prefill-to-decode handoff latency. TPOT is also comparable between DualPath and Basic — both around 0.035–0.045 seconds — confirming that decode performance is unaffected by dual-path KV-Cache loading. SGL(MC) exhibits "anomalously low TTST, likely due to implementation issues where the first two tokens arrive at the client almost simultaneously."

**DS 27B online results (Figure 10, top row).** The relative improvement is smaller (1.67× APS) but the absolute latency characteristics differ notably from DS 660B. Both Basic and DualPath show significantly higher TPOT than Oracle: Basic and DualPath TPOT is approximately 0.03–0.04 seconds, while Oracle TPOT is approximately 0.005–0.01 seconds. The paper attributes this gap to "the overhead of basic P-D transferring [being] considerable in small model cases" and leaves optimization as future work. This is a notable finding: for smaller models, the prefill-to-decode KV-Cache transfer itself (which occurs regardless of read path) becomes a non-trivial fraction of per-token latency, and DualPath does not address this component.

**Average JCT for online serving (Figure 11).** For DS 660B, Basic's average JCT increases from approximately 200–300 seconds at 0.01 APS to approximately 1000 seconds at 0.25 APS (where it hits the SLO limit). DualPath's average JCT remains under 500 seconds even at 0.45–0.5 APS, increasing to approximately 800 seconds at 0.55 APS. Oracle's JCT stays under 300 seconds across all APS. For DS 27B, the pattern is similar but compressed: Basic's JCT increases steeply beyond 0.1 APS, while DualPath maintains lower JCT up to 0.4–0.5 APS.

**TTFT breakdown (Figure 12, left, DS 660B online).** At low APS (0.15), DualPath's TTFT is dominated by prefill computation (PF), with scheduling (Sch), allocation (A), and KV-Cache reading (R) contributing smaller fractions. Basic shows a similar pattern with slightly higher reading time. At higher APS (0.2, 0.25), Basic's queuing/scheduling time grows dramatically, dominating TTFT — this is the signature of storage bandwidth saturation, where requests queue waiting for the saturated prefill-side SNICs. DualPath's scheduling time remains small even at 0.25 APS, confirming that the aggregated storage bandwidth prevents queue buildup.

#### Large-Scale Scalability

**DualPath demonstrates near-linear scaling from a small configuration (2P4D, 6 nodes, 48 GPUs, 2K agents) to a large configuration (48P96D, 144 nodes, 1152 GPUs, 48K agents)** (Table 3). For offline inference, JCT is 3,167 seconds at small scale and 3,201 seconds at large scale — a 24× increase in compute resources and workload achieving the same completion time, implying approximately 24× throughput at near-perfect scaling efficiency. For online serving, the 44P88D configuration (132 nodes, 1056 GPUs) achieves 8.8 APS versus 0.4 APS for 2P4D — a 22× throughput increase while maintaining comparable latency (TTFT 1.847s vs 1.739s, TTST 0.194s vs 0.228s, TPOT 0.036s vs 0.039s).

The paper notes two caveats. First, "due to the lack of fine-tuned parallelism settings and P/D ratios (which requires a substantial experimentation budget), the large-scale experiments do not demonstrate additional JCT or serving capacity gains compared to multiple small-scale units with equivalent cost." In other words, the per-node efficiency is approximately constant rather than improving at scale — the scaling is linear rather than super-linear. Second, scheduler CPU usage remains below 10 cores even at 1152-GPU scale, confirming it is not a bottleneck.

Figure 15 shows detailed metrics over the 48P96D offline inference process: prompt tokens per second (TPS) is approximately 40–60 million throughout the run, TTFT varies between 5–15 seconds with spikes up to 20 seconds, and the number of running agents peaks at approximately 48000 early in the run and gradually decreases as agents complete.

The paper argues that large-scale deployment remains important for two reasons beyond raw throughput: "(1) it reduces fragmentation and provides greater flexibility for fine-tuning parallelism and P/D ratios, and (2) large-scale deployment offers more scheduling opportunities to mitigate queuing latency under unpredictable bursty online requests." These are qualitative arguments not directly evaluated.

### Ablation Studies and Robustness Checks

All ablation experiments are performed under offline inference with 64K MAL and agent batch sizes of 1024 and 2048 on DS 660B (Figure 12, right). The three techniques evaluated are Layerwise Prefill, Dual-Path Loading (DPL), and Scheduling Algorithm.

**Layerwise prefill (+Layer): Adding layerwise prefill to Basic reduces JCT by 17.21% on average.** At 1024 agents, Basic JCT is approximately 9000 seconds; Basic+Layer reduces this to approximately 7500 seconds. At 2048 agents, Basic JCT is approximately 13000 seconds; Basic+Layer reduces to approximately 10500 seconds. The paper attributes this to two effects: alleviating PE HBM bottlenecks (larger effective batch sizes enable better GPU utilization during prefill) and hiding transfer overhead (the layerwise streaming enables overlapping KV-Cache transfers with computation).

**Dual-path loading (+DPL): Adding dual-path loading on top of layerwise prefill delivers the primary performance gains, reducing JCT by 38.19% on average compared to Basic.** At 1024 agents, Basic+Layer+DPL JCT is approximately 5500 seconds (vs. 7500 for Basic+Layer, a further 26.7% reduction). At 2048 agents, Basic+Layer+DPL JCT is approximately 7500 seconds (vs. 10500 for Basic+Layer, a further 28.6% reduction). The paper states this is because dual-path loading "enables requests to read KV-Cache from either PE or DE, fully utilizing distributed storage bandwidth."

**Scheduling algorithm (+Sched): Adding the adaptive scheduler on top of dual-path loading achieves the best performance, reducing JCT by 45.62% compared to Basic.** At 1024 agents, JCT is approximately 5000 seconds; at 2048 agents, approximately 6500 seconds. The incremental gain from scheduling over DPL alone is approximately 7.43 percentage points (45.62% − 38.19%), which the paper attributes to "load-balanced scheduling across storage NICs."

**Load balance of storage NICs (Figure 13).** Without the scheduling algorithm (using round-robin instead), the max-to-average ratio of storage NIC traffic across three machines is 1.528. With scheduling, this ratio improves to 1.184 (1.0 is perfect balance). The paper measures this over time, showing that the ratio is relatively stable throughout the workload. The metric is defined as "the ratio of maximum to average traffic across all storage NICs on three machines within a small time window."

**Load balance of attention execution time (Figure 14).** Without scheduling, the max-to-average ratio of attention layer execution time across GPUs in an expert-parallel group is around 1.5–2.0 during the first 20% of the task, indicating significant imbalance that causes GPU idle bubbles at synchronization barriers. With scheduling, this ratio is as low as 1.06 during the first 5% of the task, and remains below 1.5 throughout. The paper notes that as the task progresses (beyond 20–30% completion), "both ratios become meaningless due to underloaded system. Therefore, we do not show the tail phase of the workload."

**Varying P/D ratio dual-path effectiveness (Figure 8, described above).** This serves as an implicit ablation of the dual-path architecture's sensitivity to resource allocation. The fact that DualPath maintains consistent performance across 1P1D, 1P2D, and 2P1D configurations while Basic's performance varies substantially (and is consistently worse) demonstrates that the dual-path mechanism is robust to P/D ratio as long as the ratio falls within the bottleneck-free range derived in Section 4.2.

**Online serving TTFT component breakdown (Figure 12, left).** This serves as an implicit ablation showing *what* changes between Basic and DualPath under increasing load. In Basic, scheduling/queuing time grows with APS and becomes the dominant TTFT component — a direct consequence of storage bandwidth saturation. In DualPath, scheduling time remains small, and the dominant components remain prefill computation and KV-Cache reading — indicating that the storage bandwidth bottleneck has been resolved and the remaining latency is intrinsic to computation and I/O operations that cannot be further parallelized.

**Working set analysis (§8.2).** This is not a controlled ablation but provides insight into practicality. For DS 660B serving, the working set (approximated as λ × JCT_avg × total_len_avg / 2) ranges from 69 GB at APS 0.1 to 681 GB at APS 0.45. The paper notes that in realistic settings with non-zero inter-arrival time and tool call latency, the working set would be larger: if JCT increases by a factor of r due to these gaps, the system's APS capacity increases by r (because gaps don't stress LLM inference), causing the working set to expand by r². This analysis contextualizes the memory requirements for deploying DualPath in production and acknowledges that at very large working sets, even 3FS (which is SSD-based) may face capacity constraints.

### Critical Assessment

**The experiments consistently demonstrate that DualPath improves throughput over its own Basic baseline, but the absolute performance claims require careful interpretation.**

**Regarding the 1.87× offline throughput improvement:** This is measured against Basic (the unmodified internal framework), not against SGLang or any external baseline. The paper explicitly states that "Comparing DualPath and SGL(MC) is unfair due to implementation differences," and SGL(MC) encountered errors at multiple configurations. This means the reported 1.87× is a *relative improvement over a specific internal system*, not an absolute claim of superiority over the state of the art. For a systems paper, this is reasonable — the contribution is the dual-path architecture, and the comparison against the same codebase with and without the technique is the cleanest way to isolate its effect. However, a reader should not interpret "1.87× throughput improvement" as "1.87× better than all existing systems." The paper does not establish where Basic sits relative to production-grade inference stacks like SGLang, vLLM, or TensorRT-LLM on equivalent workloads.

**Regarding the 1.96× online serving throughput:** This is reported as an average improvement, and the APS values in Figure 10 support a range of 1.67× (DS 27B) to 2.25× (DS 660B). However, the online experiments use a specific SLO (TTFT ≤ 4s, TPOT ≤ 50ms) and the metric is the maximum sustainable APS. This is sensitive to the SLO thresholds — a different SLO (e.g., TTFT ≤ 2s) might produce different relative improvements. The paper does not sweep SLO parameters. Additionally, SGL(MC) shows anomalously low TTST and performs worse than Basic on TTFT, which raises questions about whether SGL(MC) was properly tuned for these specific agentic workloads (which have very different characteristics than chatbot workloads that SGLang primarily targets).

**Regarding the claim that KV-Cache I/O is "largely eliminated":** This is supported by the Oracle comparison: for DS 660B, DualPath JCT is within 3–7% of Oracle, meaning that after applying all DualPath optimizations (layerwise prefill + dual-path loading + scheduling), the remaining gap to a zero-I/O ideal is small. However, for DS 27B (1.09–1.85× gap) and Qwen 32B (more modest improvement), the I/O bottleneck is not fully eliminated. This is an important qualification: the claim holds for the specific combination of a large model with highly optimized attention (MLA with sparse attention) that has a small cache-compute ratio, but it weakens for smaller models or models with standard attention mechanisms where the cache-compute ratio is higher (Table 1). The paper is transparent about this — Figure 7 shows the gap clearly — but the abstract and introduction's emphasis on "up to 1.87×" and "break the bottleneck" could give the impression of more uniform improvement than the data supports.

**Missing experiments that would strengthen the paper:**

- **Ablation of the CNIC-centric traffic manager.** The paper does not compare CNIC-assisted H2D/D2H against GPUDirect Storage or CUDA copy engine in terms of end-to-end inference performance. The claim that GDS and CUDA copy engine "severely degrade inference performance" due to PCIe contention (§5.2) is stated but never quantified. An experiment showing DualPath with GDS (even if it performs poorly) would provide evidence for the necessity of the CNIC-centric approach.

- **Sensitivity to virtual lane QoS configuration.** The paper configures VL arbitration to reserve ~99% of bandwidth for high-priority traffic. What happens at 95%? At 90%? Is the 99% value critical or is there a broad range of acceptable configurations? This matters for practical deployment where the QoS settings may interact with other cluster traffic.

- **Ablation of the compute quota threshold.** The 300 ms compute quota is used for all experiments. How sensitive are results to this value? If the quota is 150 ms or 600 ms, does throughput change substantially? This is relevant because the optimal quota likely depends on model architecture and hardware.

- **Ablation of the token thresholds α and β in the scheduler.** These are profiled as "the number of tokens we can read during 3 seconds" and "the number of tokens one GPU can process for 5 seconds." How sensitive is scheduling quality to these values? If they are misprofiled by 2×, does the scheduler still achieve good load balance?

- **Comparison with a properly-tuned SGLang baseline.** The SGL(MC) errors at multiple configurations (marked N/A in Figure 7) suggest that the comparison is not on equal footing. A more thorough attempt to make SGLang work on these workloads — or at minimum an explanation of why it fails (OOM? timeout? unsupported model architecture?) — would help contextualize the performance claims.

- **Memory overhead analysis.** The paper allocates 80 GB DRAM per node for PE and DE buffers (320 GB for Qwen 32B). How much of the node's total DRAM does this represent? In the RL training scenario where DRAM is "occupied to hold large training state," is 80 GB still available? The paper mentions this scenario in the introduction as a motivation but does not evaluate DualPath under memory-constrained conditions.

- **Sensitivity to KV-Cache hit rate.** All experiments use traces with ~99% hit rates. What happens at 90%? 80%? As the hit rate decreases, the benefit of dual-path loading should diminish because more computation (cache-miss prefills) reduces I/O pressure. Understanding where the crossover point lies would help practitioners determine whether DualPath is beneficial for their specific workload characteristics.

- **Working set exceeding storage capacity.** The working set analysis (§8.2) notes that in realistic settings, the working set could be up to r² times larger than the experimental setting. What happens when the working set exceeds 3FS capacity or DRAM buffer capacity? The paper does not evaluate eviction policies or cache replacement strategies.

**Regarding the P/D ratio experiment (Figure 8):** The finding that configurations with equivalent available storage bandwidth perform comparably is powerful evidence that storage bandwidth is the bottleneck. However, the experiment only uses DS 27B with 1P1D, 2P1D, and 1P2D — a small set of ratios. It would be informative to see whether this equivalence holds at more extreme ratios (e.g., 1P4D, 4P1D) and whether the bottleneck-free analysis's predicted limits (P/D from 1/7 to 7/2) correspond to empirically observed performance cliffs.

**Regarding large-scale scalability:** The paper reports near-linear scaling but acknowledges that the 48P96D configuration "does not demonstrate additional JCT or serving capacity gains compared to multiple small-scale units with equivalent cost." This is simultaneously a positive result (scaling efficiency is ~100%) and a slightly disappointing one (there is no super-linear gain from the larger scheduling pool). The paper frames the latter as an opportunity for future work on adaptive parallelism and P/D ratio tuning, which is fair but means the current system does not extract additional value from scale beyond what smaller independent clusters could achieve.

**Unquantified claims:** Several statements in the paper lack direct experimental evidence:
- "GPU load, disk read load, and network load are all strongly correlated with token count" (§6.1) — this is used to justify the token-count proxy but not directly validated with correlation measurements.
- "CNIC-assisted H2D and D2H outperform the CUDA copy engine when handling a large number of small data chunks" (§5.2) — the 1 μs vs. 5–7 μs per-operation comparison is reported but not translated into end-to-end throughput impact.
- The claim that the CNIC-centric approach is "to our best knowledge... the only practical method to ensure that KV-Cache load/store does not degrade the performance of critical model-execution communication" — this is stated without comparing against alternative isolation mechanisms (e.g., software-based rate limiting, time-division multiplexing).

**Overall assessment of evidence strength:** The paper convincingly demonstrates that dual-path KV-Cache loading + adaptive scheduling improves throughput over a single-path baseline for the specific models, traces, and hardware configuration tested. The evidence for *why* it works — the storage bandwidth imbalance diagnosis — is strong, supported by the P/D ratio experiment (Figure 8) and TTFT breakdown (Figure 12). The evidence for the scheduler's load-balancing effectiveness is solid (Figures 13 and 14). However, the generality claims (applicability to "agentic workloads" broadly, to other model families, to other hardware) are based on reasoning (Table 1 cache-compute ratios, bottleneck-free analysis bounds) rather than experimental validation across diverse settings. The paper would be strengthened by experiments on at least one additional model family (beyond DeepSeek's in-house architectures), one additional interconnect technology (RoCE with DSCP-based QoS), and sensitivity analyses for the many configurable thresholds (compute quota, α, β, VL arbitration weights, block size).

## 6. Limitations and Trade-offs

### 6.1 The Difficulty Estimation Cost Is Not Accounted For, Making the Headline Efficiency Gains an Upper Bound

**The assumption or constraint.** The scheduler's load-balancing decisions—particularly KV-Cache read path selection and engine assignment—depend on real-time load metrics: `tok_e` (total tokens assigned to each engine) and `read_qn(e)` (disk reading queue length per node). These metrics are collected proactively by each engine and reported to the scheduler during fetch requests (§6.1). The paper does not account for the computational cost of collecting, transmitting, or processing these metrics. Moreover, the scheduler itself is a centralized component that processes all scheduling decisions for the cluster.

The paper explicitly acknowledges this cost is excluded from the evaluation: in the large-scale experiments (§7.6), it notes that "scheduler CPU usage remains below 10 cores, confirming it is not a bottleneck." However, the thresholds `α` and `β`—which determine engine categorization in the PE scheduling algorithm (Algorithm 1)—are "profiled in advance" (§A.4) as "the number of tokens we can read during 3 seconds" and "the number of tokens one GPU can process for 5 seconds." This profiling requires running the specific model-hardware combination under representative load to calibrate these values, and the paper does not include this profiling cost in any throughput measurement.

**The consequence.** For a deployment where the workload, model, or hardware configuration changes, the profiling must be repeated. If the profiling is inaccurate—for instance, if storage bandwidth degrades due to contention from other cluster jobs, or if GPU performance varies due to thermal throttling—the thresholds `α` and `β` become miscalibrated. An `α` that is too large will cause the scheduler to incorrectly classify nodes as having "short" disk queues when they are actually saturated, leading to suboptimal path selection and potential underutilization of decode-side storage NICs. An `α` that is too small will make the scheduler overly conservative, restricting assignments to Category 2 engines and leaving Category 3 engines underutilized even when they could handle additional load. The paper provides no sensitivity analysis for these thresholds—no experiment varying `α` or `β` by factors of `2×` or `0.5×` to assess how robust the scheduling policy is to miscalibration.

Additionally, the scheduler's FIFO request ordering for PE scheduling (requests are "scheduled in a FIFO order" from the waiting queue, §6.1) means that a single request with an extremely long context (e.g., 64K tokens) can block subsequent requests even if those subsequent requests are short and could be processed on engines that are currently idle. The scheduling algorithm checks whether an engine is overloaded (`tok_e > β`) but does not consider the size of individual requests—a 64K-token request might fit within `β` for one engine while blocking shorter requests that could be concurrently processed on other engines with different token distributions.

**What evidence exists in the paper.** The paper provides two pieces of indirect evidence that the scheduler works as intended. Figure 13 shows that the scheduling algorithm improves storage NIC load balance (max/avg ratio) from 1.53 (round-robin) to 1.18 (DualPath scheduling), measured in a small time window across three machines. Figure 14 shows that attention layer execution time balance improves correspondingly, with max/avg ratio as low as 1.06 during the first 5% of the task. These measurements demonstrate that the scheduler *does* improve balance, but they do not demonstrate that it is *optimal* or that the specific thresholds chosen are the best ones, because no sweep of threshold values is performed. The paper also acknowledges that "as the task progresses, both ratios become meaningless due to underloaded system" and excludes the tail phase of the workload from the analysis—this is a valid choice (an underloaded system has no balancing problem) but means the evaluation only covers the portion of the workload where the scheduler's decisions matter most.

**Mitigation status.** The paper does not address this limitation directly. The scheduler thresholds are described as profiled constants, not adaptive parameters. The paper suggests "more adaptive and flexible approaches for parallelism and P/D ratio configuration" as future work (§8.1), including "simulators or online adjustment mechanisms," but these suggestions target resource allocation (how many PEs and DEs to use) rather than scheduler threshold tuning. The sensitivity of scheduling quality to `α` and `β` remains unstudied.

### 6.2 All Results Are on a Single Model Family and Single Storage Backend, with Limited Evidence of Generality to Other Architectures

**The assumption or constraint.** The paper evaluates three models—DeepSeek V3.2 660B, a 27B downscaled variant, and Qwen2.5-32B—running on an in-house inference framework with 3FS as the distributed storage backend and InfiniBand as the compute interconnect (§7.1–7.2). While the models span different attention mechanisms (MLA with sparse attention, dense GQA) and scales (27B to 660B), two of the three models share the same architectural lineage (DeepSeek MoE with MLA), and all experiments use the same storage system (3FS with no internal DRAM cache) and the same network fabric (InfiniBand with virtual lane QoS). The paper's explicit claims about generality rest on analytical reasoning rather than empirical validation: Table 1 calculates cache-compute ratios for five models—including GPT-OSS-120B and Qwen3-235B-A22B—to argue that "the situation is even worse" for models with larger KV-Cache sizes, but these models are never evaluated in experiments.

The paper also relies heavily on a specific hardware configuration: 8× NVIDIA Hopper GPUs per node, each with a dedicated 400 Gbps CNIC, one 400 Gbps SNIC per node, and physical isolation between compute and storage networks (§2.3, §7.2). The bottleneck-free analysis (§4.2) assumes `s = 1` (storage NIC bandwidth equals one CNIC's bandwidth) and `g = 8` (eight GPUs per node), deriving the bottleneck-free P/D ratio range of `1/7 ≤ P/D ≤ 7/2`. If a deployment uses a different ratio—for instance, `s = 2` (two storage NICs per node, or a 200 Gbps CNIC with a 400 Gbps SNIC) or `g = 4` (fewer GPUs per node)—the bottleneck-free range shifts, and the system may encounter new bottlenecks not characterized in this paper.

**The consequence.** A practitioner deploying DualPath on a different model family (e.g., a dense transformer without MLA, or a model with different MoE configuration) faces several unknowns. The cache-compute ratio directly determines how I/O-bound the workload is and therefore how much benefit dual-path loading can provide. For a model with an even higher cache-compute ratio than Qwen2.5-32B—such as models with standard Multi-Head Attention at very long contexts—the paper's analysis suggests the benefit would be larger, but also that the remaining gap to Oracle would be wider (as seen with Qwen 32B versus DS 660B). For a model with a *lower* cache-compute ratio than DeepSeek V3.2—perhaps due to more aggressive KV-Cache compression or shorter contexts—the benefit of dual-path loading would diminish because the workload becomes less I/O-bound, and the overhead of the additional data path (extra CNIC traffic, DRAM buffer management) might outweigh the benefit.

The dependence on 3FS specifically is also untested. The paper's storage backend is described as having "no internal DRAM cache" and being able to "saturate the 400Gbps bandwidth of the storage NIC" (§7.2). A different storage system—one with internal caching, different block sizes, or different latency characteristics—would change the `read_qn(e)` dynamics that the scheduler relies on. If the storage system has higher latency per read but higher throughput (e.g., a parallel file system with many disks), the optimal value of `α` (the "short reading queue" threshold) might be different. If the storage system caches hot blocks in DRAM, the concept of a "disk reading queue" becomes ambiguous because some reads are served from cache and others from disk.

The dependence on InfiniBand virtual lane QoS similarly constrains deployment. While the paper describes how the design extends to RoCE and emerging interconnects (Appendix A.1), no experiments validate these extensions. For a deployment using RoCE with DSCP-based QoS, the mapping from InfiniBand VLs to Ethernet Traffic Classes is not one-to-one—RoCE typically supports up to 8 TCs, but the lossless RDMA configuration (with PFC) reduces the number of usable TCs, and the interaction between PFC pause frames and KV-Cache traffic could create head-of-line blocking that does not exist in InfiniBand's credit-based flow control.

**What evidence exists in the paper.** The only cross-model evidence comes from comparing DS 660B, DS 27B, and Qwen 32B results. The speedup over Basic varies substantially: 1.87× for DS 660B at 64K/4096 agents, 1.78× for DS 27B at 64K/1024 agents (but with a 1.09–1.85× gap to Oracle), and ~1.63× for Qwen 32B at 64K/64 agents (Figure 7). This variation is consistent with the models' different cache-compute ratios (Table 1): DS 660B at 13–36 GB/PFLOP benefits most, Qwen 32B at 117–267 GB/PFLOP benefits less because even Oracle cannot fully eliminate the I/O bottleneck. However, two of the three models are DeepSeek architectures, and none of the evaluated models use standard MHA (the worst-case in Table 1). The paper does not evaluate any model with a cache-compute ratio above ~267 GB/PFLOP, which represents the upper bound of Table 1 but is not an extreme outlier for long-context workloads.

**Mitigation status.** The paper does not directly address this limitation. The analytical framework (cache-compute ratio, bottleneck-free analysis) provides reasoning about *why* the benefits should generalize, but the empirical validation is narrow. Section 8.1 suggests future work on "more adaptive and flexible approaches for parallelism and P/D ratio configuration" but not on validation across diverse model families or hardware. A reader considering adoption would need to replicate the key experiments on their specific model-hardware combination.

### 6.3 The Dual-Path Architecture Introduces a Fundamental Tradeoff: It Consumes DE DRAM and CNIC Bandwidth That Would Otherwise Be Available for Decode, and This Tradeoff Is Favorable Only Under the Paper's Specific Workload Assumptions

**The assumption or constraint.** The DE read path requires decode engines to allocate host DRAM buffers as staging areas for KV-Cache loaded from storage, and to use their CNICs for transferring that KV-Cache to prefill engines (§4.1). The paper allocates 80 GB DRAM per node for DeepSeek models and 320 GB per node for Qwen 32B (§A.4). This DRAM is not free—it is space that could otherwise be used for a larger decode batch (more requests concurrently in flight), for caching KV-Cache blocks to avoid future storage reads, or for other system functions.

The paper's justification for accepting this cost relies on workload characteristics that are true for the evaluated traces but may not hold generally: "since the generation length is typically short in this scenario, time-to-first-token (TTFT) accounts for a non-negligible portion of the total end-to-end request time. Introducing DE buffer helps reduce GPU memory usage" (§4.1). In other words, the paper argues that HBM is the scarcer resource during decode (because decode is memory-bound), so trading DRAM for HBM savings is beneficial. But this argument is contingent on short generation lengths—if generations are long, the decode phase dominates end-to-end latency, and HBM capacity during decode determines the maximum batch size and therefore throughput. In that case, using HBM to hold the prompt KV-Cache directly (via GPU Direct RDMA, bypassing the DE buffer) might be preferable despite consuming more HBM.

The bottleneck-free analysis (§4.2) formalizes the conditions under which CNIC and DRAM do not become new bottlenecks, but these conditions embed the same workload assumptions. The analysis assumes that storage bandwidth is fully utilized—that is, the workload is I/O-bound enough to saturate all SNICs. If the workload is less I/O-bound (lower KV-Cache hit rate, longer generations, smaller contexts), the dual-path architecture's additional CNIC and DRAM traffic may offer diminishing returns while still consuming resources.

**The consequence.** For a workload with different characteristics than the paper's traces—for instance, agentic tasks with longer generation lengths (the model produces multi-paragraph analyses rather than short tool calls), lower KV-Cache hit rates (more cache misses because context diverges more between turns), or shorter overall contexts (less KV-Cache to load per turn)—the dual-path benefit would shrink and could potentially become negative. The DRAM allocated to DE buffers (80–320 GB per node) represents a fixed cost regardless of workload intensity; if the storage bandwidth bottleneck is less severe, this DRAM is underutilized but still reserved, reducing the memory available for other purposes.

The paper's online serving experiments show that for DS 27B, "both Basic and DualPath show significantly higher TPOT than Oracle, suggesting the overhead of basic P-D transferring is considerable in small model cases" (§7.4, Figure 10). This reveals that the prefill-to-decode KV-Cache transfer itself—which occurs in *both* the PE and DE read paths (step 4 in Figure 4a, step 5 in Figure 4b)—introduces latency that DualPath does not address. For small models where this transfer is a larger fraction of total per-token time, DualPath's throughput gains come at the cost of higher decode latency overhead relative to an idealized zero-transfer system. This tradeoff between throughput and per-token latency is not explored systematically—the paper reports throughput improvements and verifies that TPOT does not *increase* relative to Basic (Figure 10), but does not examine whether the CNIC traffic from dual-path transfers ever *increases* decode latency for co-located decode requests.

**What evidence exists in the paper.** The evidence that the tradeoff is favorable under the paper's workload is implicit in the throughput results: DualPath improves JCT and APS without increasing TPOT, so the additional DRAM and CNIC consumption does not degrade decode performance in these experiments. However, the paper does not include an ablation that varies the DE buffer size or compares buffer-based staging against GPU Direct RDMA. The only comparison point is the Oracle baseline, which bypasses all I/O entirely—not a configuration that isolates the DE buffer's contribution. The paper does not measure DRAM utilization or CNIC bandwidth utilization during decode to show that there is headroom for the additional dual-path traffic.

**Mitigation status.** The paper does not address this tradeoff directly. The bottleneck-free analysis (§4.2) provides bounds on P/D ratios where the system is theoretically bottleneck-free, but these bounds assume full storage bandwidth utilization and do not characterize what happens when the workload is less I/O-bound. The paper acknowledges in the online serving discussion (§7.4) that the DS 27B P-D transfer overhead "is considerable" and leaves optimization as future work, but this refers to the basic transfer mechanism, not specifically the dual-path overhead. No experiments vary generation length, KV-Cache hit rate, or context length independently to map the boundary of the regime where dual-path loading is beneficial.

### 6.4 The System Adds Substantial Implementation Complexity and Couples Tightly to Specific Hardware Features, Limiting Portability

**The assumption or constraint.** DualPath's implementation requires modifications to the inference framework's data movement layer: the CNIC-centric traffic manager (§5) replaces standard GPU data transfer mechanisms (GPUDirect Storage and CUDA copy engine) with custom RDMA-based H2D/D2H operations, the KV-Cache transfer protocol operates at layer granularity with two distinct block layouts (Layer Blocks and Full Blocks, §A.5), and the scheduling algorithm (§6) is deeply integrated with engine-internal load metrics (`tok_e`, `read_qn(e)`). The paper reports that this requires "approximately 5K lines of modifications" on top of the in-house inference framework (§7.1).

Several components depend on specific hardware capabilities: the InfiniBand VL QoS configuration (§5.1, Appendix A.1) assumes support for `qos_max_vls`, `qos_high_limit`, and per-VL WRR arbitration with specific weights; the CNIC-assisted H2D/D2H path (§5.2) requires GPUDirect RDMA support and doorbell batching for efficient RDMA work submission; the storage backend assumes 3FS with an `io_uring`-like kernel-bypass interface (§7.1). The paper notes that the CUDA copy engine overhead (5–7 μs per `cudaMemcpyAsync`) and the RDMA work submission overhead (1 μs per WR) are measured on the specific hardware, and that "doorbell batching" can amortize RDMA overhead—but doorbell batching behavior depends on the NIC firmware and driver implementation.

**The consequence.** Porting DualPath to a different inference framework (e.g., vLLM, TensorRT-LLM, or an SGLang-based system) or a different hardware platform (e.g., AMD GPUs with ROCm, Ethernet-based interconnects without InfiniBand VLs, a different distributed storage system) would require substantial re-engineering. The 5K lines of modifications on the in-house framework represent a lower bound on the integration effort because the in-house framework shares internal abstractions with the paper's development team. An external team integrating dual-path loading into a different codebase would need to reimplement the CNIC-centric data path, modify the KV-Cache block management to support dual layouts, and adapt the scheduling algorithm to the target system's load reporting mechanisms—effort that could easily exceed 5K lines.

The dependence on InfiniBand VL QoS is particularly constraining. While the paper describes RoCE extensions (Appendix A.1), the lossless RDMA configuration with PFC introduces head-of-line blocking risks that do not exist in InfiniBand. If KV-Cache traffic on a low-priority TC triggers PFC pause frames, those pause frames can backpressure the high-priority TC operating on the same physical link—a well-known limitation of PFC-based QoS that the paper does not discuss. The claim that "the same design principles naturally extend" (§5.1) to RoCE requires validation under PFC-induced backpressure that the paper does not provide.

The compute quota mechanism (§6.2) requires profiling the relationship between theoretical computation and wall-clock time for each model-hardware-parallelism configuration. The paper states this relationship "can be fitted in advance through profiling as previous works [17] and [2]" but does not describe the profiling methodology, its cost, or its accuracy under dynamic conditions (e.g., GPU frequency scaling, thermal throttling). For a deployment that rotates model versions frequently or operates in a multi-tenant cluster with variable GPU availability, this profiling overhead could be significant.

**What evidence exists in the paper.** The paper does not evaluate portability. All experiments use the same hardware platform (NVIDIA Hopper GPUs, InfiniBand NDR200/400), the same storage system (3FS), and the same in-house framework. The only evidence of generality is the three-model evaluation (showing the approach works across model scales and attention mechanisms) and the large-scale experiment (showing it scales to 1152 GPUs). Neither addresses the question of whether the implementation can be ported to a different software stack or hardware platform without substantial re-engineering.

**Mitigation status.** The paper does not address portability as a limitation. The discussion of RoCE and Ultra Ethernet extensions in §5.1 and Appendix A.1 is forward-looking and does not constitute validation. The paper frames the CNIC-centric approach as "to our best knowledge... the only practical method to ensure that KV-Cache load/store does not degrade the performance of critical model-execution communication" (§5.2)—implying that the complexity is necessary, not incidental. But this claim itself is not experimentally validated against alternative isolation mechanisms.

### 6.5 Hard Problems (Models and Workloads with Extreme Cache-Compute Ratios) Remain Substantially I/O-Bound Even After All Optimizations

**The assumption or constraint.** DualPath's ability to approach Oracle performance (the zero-I/O ideal) depends on the cache-compute ratio and the available aggregate storage bandwidth. For DS 660B at 2P4D, the gap to Oracle is only 3–7% (§7.3), meaning the system is near the compute-bound regime. For DS 27B at 1P1D, the gap to Oracle is 1.09–1.85× (Figure 7, top row), meaning substantial I/O latency remains even after dual-path loading, layerwise prefill, and scheduling are applied. For Qwen 32B, the gap to Oracle is also substantial (Oracle is roughly 1.6–2.0× faster than DualPath at 64K MAL, Figure 7 bottom row).

This variation is explained by the cache-compute ratios in Table 1. DS 660B has a ratio of 13–36 GB/PFLOP—each petaFLOP of computation requires 13–36 GB of KV-Cache to be loaded. With 2P4D (2 prefill nodes, 4 decode nodes), the aggregate storage bandwidth is 6 × 400 Gbps = 300 GB/s (2 prefill nodes + 4 decode nodes, each contributing one 400 Gbps SNIC). At 36 GB/PFLOP, the system needs 36 GB/s per PFLOP/s of GPU throughput. If the GPUs can sustain, say, 5 PFLOP/s of prefill throughput (this is not specified in the paper), the I/O demand is 180 GB/s, well within the 300 GB/s aggregate bandwidth.

For Qwen 32B at FP16 and 64K context, the cache-compute ratio is 267 GB/PFLOP (Table 1). At 1P2D (1 prefill node, 2 decode nodes), the aggregate storage bandwidth is 3 × 400 Gbps = 150 GB/s. If the GPUs can sustain, say, 2 PFLOP/s (less than DS 660B because Qwen 32B is smaller but dense, and the specific throughput depends on batch size and parallelism), the I/O demand is 534 GB/s, vastly exceeding the available 150 GB/s. DualPath cannot close this gap because the problem is not asymmetric allocation but insufficient aggregate bandwidth relative to the cache-compute ratio. The paper's bottleneck-free analysis (§4.2) assumes storage bandwidth is fully utilized but does not model the regime where even full utilization cannot satisfy demand.

**The consequence.** For models with standard attention mechanisms (MHA, GQA) at long contexts, the cache-compute ratio can exceed 100 GB/PFLOP, and the problem transitions from one of asymmetric bandwidth allocation to one of insufficient total bandwidth. In this regime, DualPath's speedup over Basic represents a partial mitigation, not a solution—the system remains fundamentally I/O-bound, and further throughput improvements require either reducing the amount of data per token (through better compression or attention mechanisms) or adding more storage bandwidth, neither of which DualPath addresses. The paper's abstract and introduction claim to "break the bottleneck" and "largely eliminate" KV-Cache I/O, but these claims are qualified by the results: they hold for the specific configuration (DS 660B at 2P4D) where the cache-compute ratio is low enough that aggregate bandwidth suffices, and the gap to Oracle confirms near-elimination. For other configurations, the bottleneck is reduced but not eliminated.

A practitioner with a model that has a cache-compute ratio above, say, 50 GB/PFLOP—which includes many popular dense models at common context lengths—cannot expect DualPath to approach Oracle-level performance. They can expect improvement proportional to the additional storage bandwidth that dual-path loading unlocks, which is bounded by `(P+D)/P` (the ratio of total nodes to prefill nodes). For 1P2D, this factor is 3×; for 2P4D, it is 3×; for 1P1D, it is 2×. If the aggregate bandwidth after DualPath still falls short of I/O demand, the system remains I/O-bound, and the remaining gap to Oracle reflects the fundamental bandwidth shortage.

**What evidence exists in the paper.** This limitation is directly visible in Figure 7. For DS 27B at 64K MAL: Oracle JCT at 1024 agents is approximately 5500 seconds, DualPath is approximately 10000 seconds (a 1.82× gap), and Basic is approximately 18000 seconds. DualPath provides a 1.8× improvement over Basic but leaves a 1.82× gap to the I/O-free ideal. For Qwen 32B at 64K MAL: Oracle JCT at 64 agents is approximately 3200 seconds, DualPath is approximately 4000 seconds (a 1.25× gap), and Basic is approximately 6500 seconds. The improvement is 1.63× over Basic, but the gap to Oracle is 1.25×. The paper does not explicitly analyze these remaining gaps or characterize the conditions under which they shrink to near-zero. The P/D ratio experiment (Figure 8) uses only DS 27B, which sits in an intermediate regime—it would be informative to see the same experiment for Qwen 32B to confirm that the remaining gap is due to absolute bandwidth shortage rather than some other factor.

**Mitigation status.** The paper does not directly address this limitation beyond presenting the cache-compute ratios in Table 1 as a diagnostic. The ratios show that the problem is worse for standard attention models, but no experiment evaluates whether the "largely eliminated" claim holds for those models at scales where aggregate bandwidth would be sufficient (e.g., by using more nodes). The working set analysis (§8.2) acknowledges that realistic settings could cause the working set to grow by `r²`, but does not analyze whether the corresponding I/O demand would exceed aggregate bandwidth in those settings. The paper's future work suggestions (§8.1) focus on adaptive parallelism and scheduling, not on addressing the absolute bandwidth shortage for high-cache-compute-ratio models.

### 6.6 The P/D Ratio Bottleneck-Free Range Is Derived Under Idealized Assumptions That May Not Hold in Production Environments

**The assumption or constraint.** The bottleneck-free analysis in Section 4.2 makes several assumptions that may be violated in real deployments:
- **Load-balanced task scheduling:** "We assume... load-balanced task scheduling" (§4.2). The scheduler aims to achieve this (and Figures 13 and 14 show it improves balance over round-robin), but perfect balance is not guaranteed—the max/avg ratios of 1.18 for storage NICs and 1.06 for attention execution time represent residual imbalance that consumes some fraction of the theoretical headroom.
- **No congestion on the computation network:** The analysis assumes the compute network has no background congestion. In a multi-tenant cluster, other jobs (training, other inference workloads) may consume compute network bandwidth, reducing the spare capacity available for KV-Cache transfers. The InfiniBand VL QoS mechanism protects high-priority model execution traffic from KV-Cache traffic, but it does not protect KV-Cache traffic from other low-priority traffic on the same VL or from fabric-level congestion that affects all VLs (e.g., switch buffer exhaustion).
- **Storage read bandwidth is fully utilized:** The analysis assumes all storage NICs are saturated. If the workload is not I/O-bound enough to saturate all storage NICs simultaneously—for instance, because the batch size is small or because requests arrive sporadically—the traffic per PE-DE pair decreases, and the per-link traffic computed in the analysis overestimates actual link pressure. This means the bottleneck-free range is conservative (actual pressure is lower), but it also means the analysis does not predict when the system transitions from I/O-bound to compute-bound.
- **Homogeneous hardware:** All nodes have identical `g`, `s`, and `B`. In a heterogeneous cluster (e.g., some nodes with older GPUs or different NIC counts), the analysis must be extended to handle multiple node classes, which the paper does not do.

**The consequence.** A deployment operating near the boundary of the bottleneck-free range (e.g., P/D = 0.2 or P/D = 3.0 for `g = 8, s = 1`) may encounter new bottlenecks that the analysis does not predict. At P/D = 0.2 (near the lower bound of 1/7 ≈ 0.143), the PE CNIC write direction is near saturation: the inequality `P/D ≥ s/(g-s) = 1/7` gives exactly 0.143. Any deviation from load balance or any background CNIC congestion would push the system over the threshold, causing PE CNIC write saturation and reducing throughput. Similarly, at P/D = 3.0 (near the upper bound of 3.5 for DE CNIC write), small imbalances could saturate DE resources.

The analysis also does not account for the PCIe topology assumption stated but not verified: "We assume a well-configured PCIe topology (each pair of GPU–NIC is under the same PCIe switch)" (§4.2). In a machine where a GPU and its paired CNIC are on different PCIe switches (due to motherboard layout or BIOS configuration), the CNIC-assisted H2D/D2H path incurs additional latency and may contend for inter-switch bandwidth that is shared with other GPUs. The paper does not describe how to detect or mitigate this configuration issue, and it does not measure the performance impact of violating this assumption.

**What evidence exists in the paper.** The P/D ratio experiment (Figure 8, DS 27B) evaluates three configurations: 1P1D (P/D = 1.0), 2P1D (P/D = 2.0), and 1P2D (P/D = 0.5). All three fall within the bottleneck-free range (0.143 to 3.5), and DualPath shows consistent improvement over Basic across all three. However, the experiment does not test configurations near the boundaries—P/D = 0.2 (close to the lower bound) or P/D = 3.0 (close to the upper bound)—so it does not validate the analysis's predicted limits. The paper also does not measure CNIC bandwidth utilization to confirm that it remains below saturation at these ratios, relying instead on the throughput results as indirect evidence.

**Mitigation status.** The paper does not address this limitation. The analysis is presented as a theoretical guarantee, and the experimental validation only covers a small subset of the range. The future work suggestion of "more adaptive and flexible approaches for parallelism and P/D ratio configuration" (§8.1) implicitly acknowledges that static P/D ratios may be suboptimal, but does not propose mechanisms for detecting or responding to boundary violations. A production deployment would benefit from runtime monitoring of CNIC and DRAM utilization to detect when the system is approaching the bottleneck-free limits, but such monitoring is not discussed.
