Here are the takeaways from this Ryan Peterman interview (host of The Peterman Post, sharing his personal playbook for shipping code faster to free up time for career growth):

**Resolving Ambiguity Before Code**

Before writing any code, the fastest engineers figure out what to change and where to change it without burning hours reading unfamiliar code. The foundation is **becoming fluent at code search**—learning the tool and its keyboard shortcuts so you can find the right location in minutes rather than hours. Since no single engineer can hold an entire large codebase in their head, you also need to **know who knows what**; ask around or check git blame to identify the right person, then use soft skills to extract the information you need. A third pillar is self-serve data fluency. He cringes when he sees engineers asking data scientists to run simple queries for them. "Delegation can be good but it can also add more waiting and overhead. If you can get answers for yourself you’ll be a lot faster in figuring out what direction to go in."

**Writing Code Faster with Small, Focused Diffs**

One of the most important parts of churning out code fast is writing smaller, encapsulated diffs. "As your code changes get larger, the time to write, test, review, and merge them in goes up exponentially. Not to mention that the chance of catching bugs is much lower." Once you're in the habit, you'll find that proving your code works can actually take longer than writing it. Three testing tactics speed this up. First, **batching test plans**: create large stacks of commits that are all loosely related on the same code path, then run tests covering the entire stack at once—"for a stack of 10 commits, I only paid the cost of testing once while making sure nothing broke." Second, **gating all changes** behind feature flags so users can't access code paths while you work on them, letting you land code as fast as you want without fear of breakage; you verify everything at once by turning on the flag for a small monitored population at the end. Third, **copying existing test plans** from git blame on unfamiliar code paths—if someone documented how they tested their changes, you can reuse that methodology instead of reinventing it.

**Faster Code Reviews as the Real Bottleneck**

After landing an average of five code changes per day to production—over 1,000 commits—the bottleneck shifted from writing and testing code to waiting on code reviews. Two strategies counter this. **Reduce friction for the reviewer**: spoon-feed them by pointing out what to scrutinize and providing relevant context via comments, and hint at how fast a small change will be to review by adding tags like "[easy]" to diff titles. **Get your code approved the first time it's reviewed**, because waiting time doubles if you need even one iteration. Preempt potential feedback, thoroughly test your code before submitting, and discuss any ambiguous parts of your implementation with people in advance so there isn't thrash after you've written it. Underneath all this is the social reality: "Writing software is social." If you're a good collaborator, you build trust so people review your code faster. He also found that writing clear descriptions for each code change was the most effective way to educate reviewers on what he was doing and why, so anyone could understand enough to review it.

**Maintaining Flow State**

Writing code requires deep focus because you need to juggle a lot of context—how deep in the call stack you are, what else references your code—and loading that into working memory takes time. Every interruption forces you to pay that cost again. Tactics he relies on: **noise-canceling headphones** (he initially thought Meta's $350 headphone stipend was pure luxury, then realized it was a big productivity booster); **creating focus blocks** by moving or canceling meetings in favor of async communication, clustering whatever meetings remain so they maximize contiguous deep-work time; **working when fewer people interrupt you**—he was always most productive at night because no one was asking him for anything (morning people can invert this); and **reducing noisy notifications** by turning off unimportant channels and checking pings in batches.

**Optimizing Your Workflow and Using the Gaps**

There are often technical solutions to getting work done faster. He recommends auditing your workflow and identifying what you're waiting on—builds, tests, queries—because slow parts are often opportunities to build tools that help you move faster, with the added benefit of leveraged impact when you share them. No matter how much you optimize, there will always be some waiting, and for those small fragments of time you should find tiny tasks to interleave: cleaning up code, replying to pings, querying data. "You shouldn't just sit there while you're waiting for builds. That time adds up and you can get much more done." Do all this right, and you free up that extra 30% of time to enable the career growth Evan described. He notes one additional factor in his own trajectory beyond efficiency: he worked more hours, enjoying the work enough that he averaged a natural extra 30% of work time. Coupling that with being more efficient let him pursue many parallel growth opportunities.
