# IceCache: Memory-Efficient KV-Cache Management for Long-Sequence LLMs

**ArXiv:** [2604.10539](https://arxiv.org/abs/2604.10539)

## 🎯 Pitch

Grouping semantically similar tokens into the same memory pages—rather than ordering by position—lets IceCache maintain 99% of full KV-cache accuracy on LongBench with only a 256-token budget, even matching a competitor’s 256-token performance using just 64 tokens. This page layout boosts cache-hit rates and transfer efficiency so much that the method stays accurate and fast on generation-heavy tasks where prior offloading methods degrade.

---

## 1. Executive Summary

This paper introduces **IceCache**, a KV-cache management strategy that integrates semantic token clustering with PagedAttention to improve memory efficiency during long-sequence LLM inference. Evaluated on LongBench, GSM8K, and RULER using Llama-3.1-8B-Instruct, Mistral-7B-Instruct-v0.2, Qwen3-32B, and LongChat-7B-v1.5, IceCache organizes semantically related tokens into contiguous memory pages via a hierarchical, dynamically updatable data structure called the **DCI-tree** (clustering key embeddings by similarity rather than original token order) and performs head-specific approximate nearest neighbor search to select only the most relevant pages for sparse attention. With a 256-token budget, IceCache maintains 99% of full KV-cache accuracy on LongBench while using only 25% of the token budget required by competing offloading-based methods — matching PQCache's 256-budget performance with just 64 tokens — establishing that semantically-aware page layout substantially improves retrieval hit rates and memory bandwidth utilization during CPU–GPU transfers, though the approach operates only on problems where a trained verifier or ground-truth signal is available for the base model's output distribution.

## 2. Context and Motivation

### The Core Problem: KV-Cache Memory Grows Linearly with Sequence Length

The fundamental challenge this paper addresses is the **memory footprint of the Key-Value (KV) cache** during long-sequence LLM inference. To understand why this matters, we need to be precise about what the KV-cache is and why it grows.

During autoregressive generation, an LLM processes tokens one at a time. At each step, the model computes attention between the current token's query vector and the key vectors of all previous tokens. Without a cache, the model would recompute the keys and values for every previous token on every decoding step — a quadratic cost in sequence length that makes generation prohibitively slow. The KV-cache solves this by storing each token's computed key and value vectors after their first computation. On subsequent steps, the model simply reads these pre-computed values rather than recomputing them, reducing the per-step cost from $O(n^2)$ to $O(n)$ for a sequence of length $n$.

However, this efficiency gain comes at a steep memory price. Each token's KV-cache entry stores two vectors (key and value) of dimension $d$ for each of $L$ attention layers and $H$ attention heads. The total memory consumption is:

$$M_{\text{KV}} = 2 \times L \times H \times d \times n \times \text{bytes\_per\_element}$$

For a model like Llama-3.1-8B with 32 layers, 8 key-value heads (grouped query attention), and a dimension of 128 per head, each token adds approximately $2 \times 32 \times 8 \times 128 = 65{,}536$ float16 values, or roughly 131 KB of KV-cache per token. At a sequence length of 36,000 tokens — a typical long-context scenario on LongBench — this balloons to approximately **4.7 GB** just for the KV-cache of a single request. For comparison, the model parameters of an 8B-parameter model in float16 occupy roughly 16 GB. The KV-cache can easily become a substantial fraction of total GPU memory, and when serving multiple requests concurrently or running on resource-constrained hardware (edge devices, consumer GPUs, shared cloud instances), it becomes the primary bottleneck.

This is not a theoretical concern. The paper's Figure 1 illustrates the practical tradeoff: existing systems must choose between high accuracy (keeping the full KV-cache on GPU, which consumes ~3.5 GB of CUDA memory and yields ~200 ms time-per-output-token at 36k sequence length) or memory efficiency (offloading to CPU, which reduces GPU memory to ~1 GB but often sacrifices accuracy). The gap between these extremes — achieving high accuracy *and* low memory — is where IceCache operates.

### Why This Problem Is Important

**Real-world deployment constraints.** As LLMs are increasingly deployed for tasks requiring long contexts — document summarization, multi-turn dialogue, codebase understanding, chain-of-thought reasoning, and retrieval-augmented generation — sequence lengths routinely exceed tens or hundreds of thousands of tokens. An NVIDIA A100 40GB (the GPU used in this paper) can comfortably serve a model with full KV-cache at moderate sequence lengths, but at 100k tokens, the KV-cache alone can exceed 13 GB, leaving insufficient room for model parameters and activation memory. On consumer GPUs (8–24 GB) or edge devices, the situation is far more acute. The paper explicitly targets these resource-constrained scenarios where offloading is not a choice but a necessity.

**The growing gap between model capabilities and hardware.** The trend toward longer-context models (Claude's 200k, Gemini's 1M+ token windows) is outpacing GPU memory scaling. Without effective KV-cache management, these capabilities cannot be realized on typical deployment hardware. The problem is compounded in serving systems that must handle many concurrent requests: a single request with a 100k-token context can monopolize GPU memory that could otherwise serve dozens of shorter requests.

**Chain-of-thought and long-generation tasks.** The paper specifically highlights that many existing methods "experience significant performance degradation" in long-generation tasks such as chain-of-thought reasoning, multi-step problem solving, and long-form summarization (Section 1). This is because generation tasks are *sequential*: the model produces new tokens that must be added to the KV-cache, and the cache's composition changes as generation progresses. Methods that make static decisions about which tokens to keep (eviction-based approaches) or that rely on precomputed importance scores from the prompt phase become increasingly stale as the generation diverges from the prompt context. The paper's emphasis on GSM8K CoT reasoning (Section 5.4) and long-generation benchmarks (LongGenBench, Appendix C) reflects this concern: generation-heavy workloads are the hardest case for KV-cache management, and the paper positions itself as solving a problem that prior work largely sidesteps.

### Prior Approaches and Where They Fall Short

The paper categorizes existing KV-cache management into two families (Section 2.1), each with distinct failure modes:

#### Eviction-Based Methods: Fast but Inflexible

Eviction-based methods permanently discard tokens from the GPU cache, keeping only a subset deemed important. The paper cites three representative approaches:

- **H2O** (Zhang et al., 2024b) retains tokens based on their cumulative attention scores — essentially keeping the tokens that have received the highest attention weights historically. The paper notes this is fast because it avoids CPU–GPU transfers entirely, but problematic because attention patterns shift during generation. A token that was important during prompt processing may become irrelevant during decoding, or vice versa — and the eviction decision is irreversible.

- **StreamingLLM** (Xiao et al., 2023) keeps only the first few "sink tokens" (initial tokens that serve as attention sinks) and the most recent window of tokens, discarding everything in between. While remarkably efficient, this approach cannot handle tasks where the model needs to reference information from the middle of a long document — a common pattern in multi-document QA, summarization, and fact-verification tasks.

- **SnapKV** (Li et al., 2024b) selects important key-value pairs by analyzing attention patterns from the end of the prompt, identifying which earlier tokens are likely to be attended to during generation. However, this is a static selection made before generation begins, making it vulnerable to the same staleness problem: generation can shift the model's attention to tokens that were not selected.

The paper's core critique of eviction-based methods is that they "often rely on static selection strategies and fail to adapt to changing contexts" (Section 2.1). The experimental results bear this out: in Table 1, StreamingLLM and SnapKV achieve average LongBench scores of 33.5 and 40.8 on Llama-3.1-8B, respectively — substantially below the full KV-cache score of 49.5. The gap is particularly stark on tasks requiring retrieval from the middle of long documents, where their strategies of keeping only recent or sink tokens fail.

#### Offloading-Based Methods: More Accurate but High-Latency

Offloading-based methods keep the full KV-cache on CPU but dynamically transfer relevant portions to GPU during decoding:

- **MagicPig** (Chen et al., 2024b) uses Locality Sensitive Hashing (LSH) to approximate which keys are most relevant to the current query, sampling a subset for computation. The paper's main criticism (visible in Section 5.3.2, Figure 7) is latency: MagicPig is restricted to running on CPUs with AVX-512 instructions, making it impractical for GPU-centric deployment.

- **OmniKV** (Hao et al., 2025) improves efficiency by reusing important tokens across consecutive layers — essentially, tiering the layers so that expensive retrieval happens at a subset of "anchor" layers and is shared with adjacent layers. However, the paper notes that OmniKV "offloads only a subset of layers while keeping all remaining layers fully resident on the GPU, resulting in substantially higher memory usage than other methods" (Section 5.3). At 36k tokens on an A100 with Llama-3.1-8B, OmniKV uses approximately 3 GB of CUDA memory (Figure 1) — far more than IceCache's ~1.2 GB.

- **PQCache** (Zhang et al., 2024a) applies product quantization to compress the KV-cache, reducing its memory footprint while maintaining the ability to approximately reconstruct key vectors for attention computation. This is the strongest offloading baseline in the paper's experiments (47.3 average LongBench score at budget 256 on Llama-3.1-8B). However, the latency analysis (Figure 7a) shows PQCache takes 13.3 seconds for the time-to-second-token at 36k sequence length — nearly twice IceCache's 7.7 seconds — because decompression and reconstruction add substantial overhead to each retrieval operation.

**The fundamental limitation of existing page-based methods.** The paper identifies a deeper, structural problem with how prior work organizes KV-cache pages. Methods like **Quest** (Tang et al., 2024) and **ArkVale** (Chen et al., 2024a) build on PagedAttention — the virtual memory system that divides the KV-cache into fixed-size pages — and add query-aware page selection. For each decoding step, they estimate each page's importance to the current query and retrieve only the top-k pages.

However, these methods construct pages based on **original token order**. This means tokens that are semantically related to a given query — and that the model needs to attend to simultaneously — are often scattered across many different pages. To retrieve all relevant tokens, the system must load pages that are mostly filled with irrelevant content. The paper's explicit critique (Section 2.2):

> "tokens that are semantically relevant to a given query may be scattered across multiple pages. In contrast, IceCache performs semantic clustering during indexing, grouping similar tokens into the same pages. This organization increases the likelihood that relevant tokens are co-located, improving retrieval hit rates and reducing unnecessary memory transfers."

This is the paper's key insight about *why* prior page-based offloading methods underperform: **the page layout is decoupled from the attention patterns it serves**. Organizing pages by token order is a holdover from how sequences are naturally processed, but it is a poor match for how attention actually retrieves information — by semantic similarity, not by temporal proximity.

**The missing piece: dynamic update during generation.** The paper also identifies a second limitation that cuts across both eviction and offloading methods: they lack effective mechanisms to update the KV-cache data structure as new tokens are generated. Eviction methods make one-time decisions; offloading methods typically precompute importance scores during the prefill phase. But during long-generation tasks like chain-of-thought reasoning, the model's attention patterns evolve as new reasoning steps are produced. Tokens that were irrelevant during the prompt phase may become critical mid-generation, and vice versa. Without a mechanism to dynamically reindex and reevaluate importance as generation progresses, even offloading-based methods experience the "significant performance degradation" in long-generation tasks that the paper highlights (Section 1).

### How IceCache Positions Itself

IceCache's positioning rests on three architectural innovations that directly address the limitations identified above:

**1. Semantic page layout replaces temporal ordering.** Instead of building pages based on token position, IceCache clusters tokens by the similarity of their key embeddings using a hierarchical tree structure (the DCI-tree, built via the Multi-level DCI algorithm). Each leaf node in the tree corresponds to a physical memory page, meaning tokens that are close in embedding space — and thus likely to be attended to together — are stored contiguously. This directly addresses the "scattered relevant tokens" problem: when a query retrieves pages, each page contains a concentrated set of semantically related tokens, maximizing the useful information per byte transferred from CPU to GPU.

**2. Head-specific retrieval replaces uniform page selection.** Quest and ArkVale select the same set of pages for all attention heads, but attention heads in transformers learn different patterns — some focus on syntax, others on long-range dependencies, others on local context (the paper notes this implicitly by referencing work showing that "initial layers of the model exhibit relatively low sparsity" in Section 5.1). IceCache constructs a **separate DCI-tree for each attention head**, allowing the page selection to be tailored to what each head is actually looking for. This is a form of fine-grained, head-level specialization that no prior page-based method provides.

**3. Dynamically updatable indexing enables adaptation during generation.** The DCI-tree is designed for efficient incremental updates. When new tokens are generated and offloaded from the GPU's window to the CPU, they are inserted into the tree based on their key embeddings — not simply appended to the end of a sequential structure. If a node exceeds the maximum page size, new pages are allocated to maintain balance. This means the tree's organization remains semantically meaningful throughout generation, and importance estimates stay current rather than becoming stale. This is what enables IceCache to "effectively mitigate performance degradation in long-generation tasks" (Section 1).

The paper frames these contributions as solving a specific, well-defined problem at the intersection of two existing lines of work: it adopts PagedAttention's efficient memory management abstraction (i.e., fixed-size pages with virtual-to-physical mapping) but replaces the page *layout strategy* with a semantically-driven one; and it adopts the query-aware retrieval paradigm of Quest/ArkVale but replaces coarse-grained, head-uniform selection with fine-grained, head-specific search through a hierarchical index.

The theoretical grounding is worth noting: the paper connects its approach to the well-established observation that attention matrices are sparse — "in each row of A, only a few attention weights have significant (large) values, while the majority of the remaining values are close to zero" (Section 3.1). This sparsity is what makes selective retrieval possible in principle. But prior methods fail to leverage the *structure* of this sparsity — that the important keys for a given query tend to be semantically clustered. IceCache's innovation is building a data structure that aligns with this structure, turning an empirical observation about sparsity patterns into an architectural principle for memory management.

Finally, the paper explicitly positions itself against the accuracy-efficiency tradeoff that characterizes the existing landscape. Figure 1 is the clearest statement of this positioning: Full Attention without offloading has high accuracy but high memory; methods like PQCache and OmniKV reduce memory but add latency or sacrifice accuracy; IceCache occupies the unclaimed region of low memory, low latency, and high accuracy. The paper aims to show that this tradeoff is not inherent to the problem — it's an artifact of suboptimal page organization and selection strategies.

## 3. Technical Approach

### 3.1 Reader Orientation

IceCache is a KV-cache management system that reorganizes how attention key-value pairs are stored in memory pages — grouping tokens by semantic similarity rather than by their original sequence order — so that during decoding only the most relevant pages need to be transferred from CPU to GPU. The core problem it solves is the linear growth of KV-cache memory with sequence length on resource-constrained hardware, and the "shape" of the solution is a hierarchical clustering tree (the DCI-tree) that enables fast, query-aware retrieval of semantically related token groups, combined with a pipelining scheme that hides the latency of CPU-side indexing behind ongoing GPU computation.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components that operate across two phases (prefill and decoding):

1. **Token Categorizer** — classifies all tokens into three groups: sink tokens (beginning of sequence), window tokens (most recent), and middle tokens (everything else). Sink and window tokens always stay on GPU; middle tokens are the candidates for offloading and selective retrieval.

2. **DCI-tree Builder (Indexing)** — for each attention head, transforms the key embeddings of middle tokens, then constructs a hierarchical tree (the DCI-tree) where leaf nodes group semantically similar tokens. Each leaf maps to a physical memory page on the CPU. This is built once during prefill and updated incrementally during decoding when window tokens age out and are offloaded.

3. **Page Selector (Query-Aware Retrieval)** — during decoding, takes the current token's query embedding and uses the Multi-level DCI approximate nearest neighbor algorithm to traverse the DCI-tree, identifying the top-k tokens most relevant to that query. The pages containing those tokens are marked for retrieval.

4. **Bulk Loader / Offloader** — aggregates the selected (non-contiguous) pages into contiguous CPU and GPU buffers, transfers them in a single high-throughput PCIe transaction (bulk backload), and scatters them into the correct GPU KV-cache slots. The reverse process offloads aged-out window pages to CPU.

5. **Pipelining Scheduler** — overlaps GPU prefill computation with CPU-bound KV offloading and DCI-tree indexing across consecutive layers, so that the latency of indexing is mostly hidden.

Information flows as follows: during prefill, tokens enter the model layer by layer → after layer 2, KV embeddings are offloaded to CPU → the DCI-tree builder clusters them into pages → during decoding, each new token's query embedding triggers the page selector → the bulk loader transfers selected pages back to GPU → sparse attention is computed using only those pages → when the window slides, aged-out tokens are inserted into the DCI-tree, keeping the index current.

### 3.3 Roadmap for the Deep Dive

- **First**, the key embedding transformations (Equations 2 and 3), because all subsequent indexing and retrieval operates in this transformed space — understanding the mapping from raw key/query vectors to the similarity space is foundational.
- **Second**, the DCI-tree indexing procedure (Algorithm 2), including random promotion, parent assignment, and the mapping from tree nodes to physical memory pages — since the tree is the central data structure that everything else depends on.
- **Third**, the Multi-level DCI query algorithm (Algorithms 3 and 4) — how page selection actually works during decoding, including the hierarchical search, priority queue, and head-specific retrieval.
- **Fourth**, the bulk loading and pipelining mechanisms (Figures 4 and 5) — the engineering optimizations that make the system fast in practice, including contiguous buffer aggregation and cross-layer overlap.
- **Fifth**, the incremental update procedure during decoding (Algorithm 1, lines 26–37) — how the DCI-tree stays current as generation progresses, which is what enables IceCache to handle long-generation tasks.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems paper** whose core idea is that the memory layout of KV-cache pages should match the semantic structure of attention patterns — clustering tokens by key embedding similarity rather than by sequence position — and that a dynamically updatable hierarchical index can make this layout practical for both retrieval speed and accuracy during long-sequence generation.

#### Key and Query Embedding Transformations

Before any indexing or retrieval can happen, IceCache transforms raw key and query vectors into a space where Euclidean distance serves as a proxy for attention relevance. This is necessary because the M-DCI algorithm (which powers both tree construction and querying) operates on Euclidean distances, but attention relevance is measured by dot-product similarity. The transformation bridges this gap.

The transformation for a key vector `$k_j \in \mathbb{R}^d$` is:

$$T_K(k_j) = \begin{bmatrix} k_j / c \\ \sqrt{1 - \|k_j\|_2^2 / c^2} \end{bmatrix}^\top$$

where `$c \geq \max_{j'} \|k_{j'}\|_2$` is a constant at least as large as the maximum `$\ell_2$` norm across all keys in the dataset, `$k_j$` is the raw key embedding for token `$j$`, and `$\|k_j\|_2$` is its Euclidean norm. The output is a vector in `$\mathbb{R}^{d+1}$` — the original `$d$` dimensions scaled by `$1/c$`, plus one extra dimension encoding residual norm information.

The transformation for a query vector `$q_i \in \mathbb{R}^d$` is:

$$T_Q(q_i) = \begin{bmatrix} q_i / \|q_i\|_2 & 0 \end{bmatrix}^\top$$

where `$q_i$` is the raw query embedding for token `$i$`, and `$\|q_i\|_2$` is its Euclidean norm. The output is a vector in `$\mathbb{R}^{d+1}$` — the `$\ell_2$`-normalized query vector padded with a zero in the extra dimension.

**What these transformations compute, operationally:**

For keys: each key vector is first scaled down by the maximum norm `$c$` across all keys (producing coordinates in `$[-1, 1]$`), then augmented with a residual term `$\sqrt{1 - \|k_j\|_2^2 / c^2}$`. This residual captures how far the key's norm is from the maximum — keys with norm close to `$c$` get a near-zero residual; keys with smaller norms get residuals close to 1. The result is that every transformed key vector `$T_K(k_j)$` has **unit Euclidean norm**, because:

$$\|T_K(k_j)\|_2^2 = \|k_j/c\|_2^2 + (1 - \|k_j\|_2^2/c^2) = 1$$

For queries: each query vector is `$\ell_2$`-normalized to unit length and padded with a zero. This means the query lies entirely in the first `$d$` dimensions of the `$(d+1)$`-dimensional space, with no component in the extra dimension.

**Why this form:**

The key insight is that under these transformations, the Euclidean distance between a transformed query and a transformed key is directly related to their dot-product similarity (which determines attention weight). Consider the squared Euclidean distance:

$$\|T_Q(q_i) - T_K(k_j)\|_2^2 = \|T_Q(q_i)\|_2^2 + \|T_K(k_j)\|_2^2 - 2 \cdot T_Q(q_i)^\top T_K(k_j)$$

Since both transformed vectors have unit norm (`$\|T_Q(q_i)\|_2^2 = 1$` and `$\|T_K(k_j)\|_2^2 = 1$`), this simplifies to:

$$\|T_Q(q_i) - T_K(k_j)\|_2^2 = 2 - 2 \cdot T_Q(q_i)^\top T_K(k_j)$$

And the dot product `$T_Q(q_i)^\top T_K(k_j)$` expands (using the zero-padding of the query) to:

$$T_Q(q_i)^\top T_K(k_j) = \frac{q_i^\top k_j}{\|q_i\|_2 \cdot c}$$

This is proportional to the raw attention score `$q_i^\top k_j$` scaled by constants `$\|q_i\|_2$` and `$c$`. Therefore, **minimizing Euclidean distance in the transformed space is equivalent to maximizing dot-product attention in the original space**. This is critical because M-DCI is a nearest-neighbor algorithm that operates on distances — the transformation makes "nearest neighbors in Euclidean distance" correspond to "largest attention weights," which is exactly what page selection needs to identify.

An alternative approach — using raw key and query vectors with cosine similarity — would not work directly with M-DCI because the algorithm requires a metric space (where the triangle inequality holds). Euclidean distance satisfies this; cosine similarity alone does not. The unit-norm embedding on a hypersphere (which this transformation produces) provides exactly the right structure: Euclidean distance becomes a monotonic function of dot-product similarity on the unit sphere, enabling distance-based search to serve as similarity-based retrieval.

The choice of `$c \geq \max_{j'} \|k_{j'}\|_2$` ensures that the argument to the square root `$\sqrt{1 - \|k_j\|_2^2 / c^2}$` is always non-negative (since `$\|k_j\|_2 / c \leq 1$`), producing a real-valued residual. In practice, `$c$` is set to the empirical maximum norm observed across all keys during indexing.

#### DCI-Tree Indexing: Building the Hierarchical Semantic Clustering

The DCI-tree is the central data structure that organizes key embeddings into a hierarchy where semantically similar tokens are grouped together. It is built independently for each attention head during the prefill phase (for prompt tokens) and updated incrementally during decoding (for newly generated tokens that age out of the GPU window). Algorithm 2 specifies the construction procedure.

**Input and scope:** The indexing function `DCI-INDEXING` takes a set of `$n$` key embeddings `$k_1, \ldots, k_n \in \mathbb{R}^d$` (already transformed via `$T_K$`) and a promotion ratio `$r < 1$`. It outputs a DCI-tree `$T$` — a hierarchical structure with `$L$` levels where each node is a cluster of tokens and leaf nodes map to physical memory pages.

**Step 1: Random level assignment.** For each key `$k_i$`, the algorithm assigns it to a level `$\ell_i$` through a **random promotion process**:

```
ℓ_i ← 1  (start at bottom level)
while Random(0, 1) < r do
    ℓ_i ← ℓ_i + 1  (promote to next higher level)
end while
```

where `Random(0, 1)` draws a uniform random number in `$[0, 1)$`. This produces a geometric distribution over levels: the probability a point is assigned to level `$\ell \geq 1$` is `$r^{\ell-1} \cdot (1 - r)$` (for `$\ell < L$`), with the highest level `$L$` receiving any points that survive `$L-1$` promotions (probability `$r^{L-1}$`). The number of points at level `$\ell$`, denoted `$n_\ell$`, satisfies `$n_\ell \approx r \cdot n_{\ell-1}$` — each higher level has roughly a fraction `$r$` of the points from the level below.

**Why random promotion rather than deterministic assignment?** Random promotion creates a skip-list-like structure where higher levels contain a sparse subset of points that serve as "entry points" for search. When querying, the algorithm starts at the top level (which has very few points), finds the closest ones, then descends to the next level and searches only within the clusters defined by those top-level parents. This hierarchical pruning is what makes search fast: it avoids scanning all points by eliminating large regions of the space early. A deterministic assignment (e.g., based on norm or position) would not guarantee that higher levels are representative of their subtrees — random sampling ensures that, in expectation, every point in a subtree has an equal chance of being represented at higher levels, preserving the ability to route queries to the correct region.

After level assignment, any levels with zero points are removed, and the total number of levels `$L$` is recorded. The tree is initialized with a single root node at the top.

**Step 2: Parent assignment via 1-nearest-neighbor.** For each point `$k_i$` at level `$\ell_i$`, the algorithm finds its **parent** at level `$\ell_i + 1$` — defined as the closest point (in terms of Euclidean distance in the transformed space) among all points assigned to level `$\ell_i + 1$`. This is formulated as a 1-nearest-neighbor query:

$$\{p_i\} \leftarrow \text{QUERY}(k_i, T, \ell_i + 1, 1)$$

where `$p_i$` is the index of the nearest point at level `$\ell_i + 1$`. The QUERY function (Algorithm 4) uses the same M-DCI search procedure that will be used during decoding, applied recursively to build the tree. Point `$k_i$` is then inserted into the tree with `$p_i$` as its parent node index.

**What "parent" means structurally:** All points at level `$\ell$` that share the same parent at level `$\ell+1$` form a **node** (a cluster). The parent point is the "representative" of that cluster at the higher level. This creates a tree where:
- The root is at level `$L$` and contains a small number of points (the most promoted ones).
- Each point at level `$\ell$` is the parent of a cluster of points at level `$\ell-1$`.
- Leaf nodes (at level 1) contain the majority of points, organized into clusters based on their nearest higher-level representative.

**Step 3: Mapping nodes to physical memory pages.** Each node in the DCI-tree — particularly each leaf node — corresponds to a memory page in the KV-cache storage. The paper's Figure 3 illustrates this mapping with a concrete example: Node 0 in the tree maps to Page 0 in physical memory, containing key-value embeddings for tokens `{1, 0, 2}`. The mapping is maintained via a table that records, for each node, the corresponding page ID and the number of tokens stored (the "#filled" column in Figure 3).

**Why this mapping matters:** Because tokens are clustered by key embedding similarity, tokens that end up in the same leaf node are semantically related (their transformed key vectors are close in Euclidean distance). This means they are likely to all be relevant to similar queries — when a query retrieves a page, it gets a concentrated set of relevant tokens rather than a mix of relevant and irrelevant ones that happen to be adjacent in the original sequence. This directly addresses the paper's critique that prior methods "construct pages based on the original token order, which often causes tokens relevant to a given query to be scattered across multiple pages."

**Page size constraint and dynamic allocation:** The paper specifies a fixed page size `$s$` (a hyperparameter). When a node exceeds `$s$` tokens (either during initial indexing or during incremental updates), new pages are dynamically allocated, and the node's tokens are distributed across multiple pages. The mapping table tracks which pages belong to which node. This ensures that the physical memory layout respects the semantic clustering even as clusters grow.

**Computational cost and amortization:** Building the DCI-tree requires running M-DCI queries for every point (to find its parent), which involves distance computations. However, this cost is incurred once during the prefill phase (for prompt tokens) and is amortized over all subsequent decoding steps. The paper's pipelining scheme (Section 4.5, Figure 5) overlaps this indexing with GPU prefill computation to hide its latency.

**Incremental updates during decoding (Algorithm 1, lines 26–37):** When a window page (the oldest page in the GPU's sliding window of recent tokens) is offloaded to CPU, its tokens must be inserted into the DCI-tree to keep the index current. The procedure mirrors the initial indexing:
1. For each token `$k_i$` in the offloaded page, assign a random level `$\ell_i$` using the same promotion process.
2. Find the parent at level `$\ell_i + 1$` using a QUERY.
3. Insert the token into the tree with that parent, and add it to the corresponding memory page.

This dynamic update is what enables IceCache to handle long-generation tasks. In contrast to methods like SnapKV (which makes a one-time token selection during prefill) or StreamingLLM (which permanently discards middle tokens), IceCache's tree remains semantically accurate as the sequence grows — newly generated tokens that become important for later attention are properly indexed and can be retrieved when needed. The paper explicitly claims this is why IceCache "mitigates performance degradation in long-generation tasks."

**Computational complexity note:** The paper does not provide asymptotic complexity analysis for tree construction, but the process can be characterized: for `$n$` points with `$L$` levels and a promotion ratio `$r$`, the expected number of points at the top level is `$n \cdot r^{L-1} \approx O(1)$` (just a few points), and each QUERY operation during construction involves traversing from the top level down, with the search space approximately doubling at each level (since `$n_{\ell-1} \approx n_\ell / r$`). The total work scales roughly as `$O(n \cdot \log_{1/r} n)$` if the tree is balanced — comparable to building a k-d tree or other spatial index.

#### Page Selection: Head-Specific Approximate Nearest Neighbor Search

During decoding, when the model generates a new token with query embedding `$q_i$`, IceCache must decide which KV-cache pages to load from CPU back to GPU for computing attention. This is the page selection step, which uses the M-DCI algorithm to traverse the DCI-tree and identify the `$k$` most relevant tokens — then loads the pages containing those tokens. The detailed procedure is split across Algorithms 3 and 4.

**Algorithm 3 (PAGE-SELECT) — top-level dispatch:**

The function takes the query vector `$q_i$` (transformed via `$T_Q$`), the DCI-tree `$T$` for the current attention head, and the number of critical keys `$k$` (the budget of tokens to retrieve). It:

1. Calls `QUERY(q_i, T, -1, k)` — the `$-1$` signals "search all levels" — which returns the set `$S_k$` of `$k$` key indices that are the approximate nearest neighbors to `$q_i$` (i.e., the keys expected to yield the highest attention weights).
2. Calls `FIND-PAGE-INDEX(S_k)` — a helper that looks up which physical memory pages contain the tokens in `$S_k$`, using the node-to-page mapping table. This produces `$S_\ell$`, the set of page indices to load.
3. Returns `$S_\ell$`.

The critical design choice here: IceCache does not load individual tokens — it loads entire pages. If `$k$` tokens are selected and each page holds up to `$s$` tokens, the number of pages loaded `$p$` and total tokens transferred `$N$` satisfy:

$$N \leq p \cdot s$$

where the inequality reflects that some pages may not be completely full. This means IceCache loads **more tokens than the strict top-k** (all co-located tokens in the selected pages are loaded), but because semantically similar tokens are clustered together, those extra tokens are likely to also be relevant — they are "bonus" tokens that cost little extra bandwidth (since the page is transferred as a unit) and have high probability of being useful. The paper's results (Table 1, achieving near-identical accuracy to ground-truth top-k) suggest this overhead is small and the co-location benefit outweighs the cost of transferring a few extra irrelevant tokens.

**Algorithm 4 (QUERY) — the hierarchical M-DCI search:**

This is the core search algorithm that traverses the DCI-tree from the top level down to the target level (which is level 1 when `$\ell = -1$`, i.e., searching all levels). The key mechanism is **recursive P-DCI (Prioritized DCI) search with a priority queue**.

**Inputs:** the transformed query `$q_i$`, the DCI-tree `$T$` with `$L$` levels, a target level `$\ell$` (or `$-1$` to search all levels), and the number of nearest neighbors `$k$` to return.

**Output:** the `$k$` nodes (leaf-level clusters) containing the keys with the highest inner product with `$q_i$`.

**Step-by-step traversal:**

**Initialization:** Start with the set `$S$` containing only the root node of the tree (the node at level `$L$`). Initialize an empty priority queue `$P$` with capacity `$k$`.

**Top-down search loop:** For each level `$i$` from `$L$` down to the target level `$\ell$` (or down to `$1$` if searching all levels):

1. For each node `$s$` in the current candidate set `$S$`:
   - Call `Prioritized-DCI-Query(q_i, s, k)` — a subroutine that, within the cluster of points belonging to node `$s$` (at level `$i$`), finds the `$k$` points that are closest to `$q_i$` in Euclidean distance. These become the **child candidates** at the next lower level (`$i-1$`). The "prioritized" aspect means the search within the node uses a lower-bound-based ordering to avoid computing distances to all points in the cluster (details below).
   - Add these child candidates to a temporary set `$S'$`.

2. If this is the target level (or if we're searching all levels, which means we process all levels and collect candidates at each), add the candidates `$S'$` to the priority queue `$P$` (maintaining only the top-`$k$` by some score — implicitly, by Euclidean distance to `$q_i$`).

3. Set `$S \leftarrow S'$` for the next iteration.

At the end, return the `$k$` nodes from `$P$` that contain the keys closest to `$q_i$`.

**What Prioritized-DCI-Query does inside each node:**

The paper does not provide pseudocode for this subroutine, but describes it conceptually in Section 3.3 (referencing Li & Malik, 2017). The idea is:

- Each node at level `$i$` contains a set of points (tokens) that share the same parent at level `$i+1$`.
- For each point in the node, we want to estimate its distance to the query `$q_i$` **without computing the full Euclidean distance** (which requires `$O(d)$` operations for each point).
- P-DCI precomputes, for each node, projection vectors (random vectors). The distance between any point and the query can be **lower-bounded** by the distance between their projections onto these random vectors. This lower bound is cheap to compute — just a dot product in the projection space.
- The algorithm maintains a priority queue of points ordered by their lower-bound distance. It pops the point with the smallest lower bound, computes its **true distance** to `$q_i$` (the expensive `$O(d)$` operation), and updates the true nearest-neighbor set. If the next point's lower bound exceeds the distance of the `$k$`-th nearest neighbor found so far, the algorithm terminates — no remaining point can be closer.
- This "prioritized" approach (processing points in order of their lower bounds, stopping early when the bound exceeds the current `$k$`-th distance) is what makes the search efficient: it computes true distances for only a small fraction of points, those that are plausible candidates based on the cheap lower bound.

**Why multi-level search rather than flat P-DCI:**

The hierarchical structure amplifies the efficiency of P-DCI. At the top level, there are very few points (typically `$O(1)$`), so P-DCI is trivially fast. As we descend, the number of points per node grows, but we only search within the nodes that were selected at the previous level — pruning away large regions of the space that are far from the query. Without the hierarchy, P-DCI would need to maintain lower bounds for all `$n$` points, and while it would still avoid computing true distances for most, the overhead of maintaining the priority queue over `$n$` entries would be substantial. The hierarchy reduces this to maintaining smaller queues over clusters, each of size `$O(n/r^h)$` for some height `$h$`.

**Head-specific retrieval:**

The paper emphasizes that "IceCache constructs a separate DCI-tree for each attention head" (Section 4.4). This means the QUERY algorithm runs independently for each head, potentially selecting different pages for different heads. This is a major departure from Quest and ArkVale, which compute a single page importance score (by aggregating across heads) and select the same pages for all heads.

The rationale: different attention heads in transformers learn different patterns — some attend to syntactic structure, some to long-range dependencies, some to local context. A one-size-fits-all page selection necessarily includes tokens irrelevant to some heads and omits tokens critical to others. Head-specific selection tailors the retrieval to what each head actually needs.

**Group-query attention (GQA) handling:** For models using GQA (where multiple query heads share the same key-value head), IceCache computes the **union** of selected pages across all queries in the same group and shares the resulting pages among them. This avoids redundant retrieval while preserving head-level specificity in selection. The paper attributes this design to Yuan et al. (2025) but integrates it into the IceCache framework.

**The page loading decision:** After QUERY returns the `$k$` leaf nodes with the closest keys, FIND-PAGE-INDEX maps those nodes to physical page indices. Critically, the system filters out pages that are **already resident on the GPU** — typically pages from the window and sink regions that were never offloaded, or pages loaded during a previous decoding step that haven't been evicted yet. Only the remaining (non-resident) pages are scheduled for transfer. This avoids redundant PCIe transfers for pages that are still in GPU memory.

**Why `$k$` is a tunable budget:** The parameter `$k$` (the number of critical keys to retrieve) directly controls the accuracy-efficiency tradeoff. The paper tests budgets of 64, 128, and 256 tokens (Table 1), corresponding to page counts that depend on the page size `$s$`. A smaller `$k$` means fewer pages loaded, less PCIe bandwidth consumed, and faster attention computation — but higher risk of missing relevant tokens and degrading accuracy. The paper's key empirical finding is that with semantic clustering, a small `$k$` (e.g., 64 tokens) already achieves high accuracy because the retrieved pages contain concentrated relevant information — unlike sequential-page methods where the same budget would load many irrelevant tokens.

#### Bulk Loading and Pipelining: Making Retrieval Fast in Practice

The page selection algorithm identifies *which* pages to load from CPU to GPU, but the mechanics of actually transferring them significantly impacts end-to-end latency. IceCache introduces two engineering optimizations to minimize this overhead: bulk loading and pipelining.

**The problem with naive page transfer:** In PagedAttention, memory pages are not contiguous in either physical CPU memory or GPU memory — they are allocated from a pool and may be scattered throughout the address space. If IceCache selected, say, 8 pages and attempted to transfer them individually, it would incur 8 separate PCIe transactions. Each PCIe transaction has fixed overhead (DMA setup, address translation, interrupt handling), and small transfers cannot saturate the available bandwidth. The result is high latency per byte transferred.

**Bulk backload (Figure 4):** IceCache aggregates all selected (non-resident) pages into a single contiguous buffer before transfer. The procedure works as follows:

1. **CPU-side aggregation:** After page selection, the CPU copies the KV-cache entries from their scattered locations in CPU memory into a pre-allocated **CPU backload buffer** — a contiguous region of memory sized to hold the maximum expected page load. The entries are packed sequentially.

2. **Single PCIe transfer:** The entire CPU backload buffer is transferred to the GPU in a single, high-throughput PCIe transaction. This is *bulk* transfer — one DMA operation instead of many — which efficiently uses the available PCIe bandwidth (the A100's PCIe 4.0 x16 link can sustain ~25–30 GB/s for large contiguous transfers, but fraction of that for many small scattered transfers).

3. **GPU-side scatter:** Once the data arrives in the GPU backload buffer (a pre-allocated contiguous region in GPU memory), a scatter operation copies each page to its correct slot in the GPU KV-cache table. The KV-cache table is the GPU-side data structure that maps virtual page indices to physical memory locations; the scatter operation writes the transferred data into the appropriate slots.

**Bulk offload (reverse direction):** When a window page is aged out and must be moved from GPU to CPU, a similar but reversed procedure applies. The pages to offload are aggregated into a contiguous GPU buffer, transferred to CPU in a single PCIe transaction, and then scattered into the CPU-side KV-cache storage.

**Why this matters quantitatively:** The paper's latency breakdown (Figure 7c) shows that "Loading" (CPU–GPU communication) accounts for only 0.015 seconds out of a total 0.11 seconds per output token at 36k sequence length — just 14% of the total TPOT. Without bulk loading, this fraction would be much higher because each individual page transfer would incur DMA setup overhead comparable to the actual data transfer time for small pages. Bulk loading reduces the communication overhead to near the theoretical minimum — the data copy time plus a single DMA setup.

**Pipelining (Figure 5):** During the prefill phase, three operations must happen for each layer:
- **Prefill computation on GPU:** computing keys, values, and attention for the input prompt tokens.
- **Offloading (OL):** transferring the computed KVs from GPU to CPU.
- **Indexing:** building the DCI-tree on the CPU once the KVs arrive.

In a naive serial execution (Figure 5a), these run in strict sequence: prefill layer `$L_i$` → offload layer `$L_i$` → index layer `$L_i$` → prefill layer `$L_{i+1}$` → ... This means the GPU sits idle during offloading and indexing (CPU-bound operations), and the CPU sits idle during prefill (GPU-bound operation).

IceCache's pipelining (Figure 5b) overlaps these operations across consecutive layers:

1. While the GPU computes prefill for layer `$L_i$`, the CPU simultaneously processes the **offload of KVs from layer `$L_{i-1}$`** (which completed its prefill one step earlier) and **builds the DCI-tree index for the KVs of layer `$L_{i-1}$`**.

2. This is possible because offloading uses the PCIe bus (which can operate concurrently with GPU compute via CUDA streams and asynchronous memory copies) and indexing is purely CPU-bound.

3. As soon as KVs from layer `$L_i$` arrive in CPU memory (after offload completes), the DCI-tree indexing for layer `$L_i$` begins — running in parallel with the GPU's prefill of layer `$L_{i+1}$` and the offload of layer `$L_{i+1}$`'s KVs.

The result: the latency of CPU-side indexing is **almost entirely hidden** behind the GPU's prefill computation. The only indexing latency that affects the critical path is for the last few layers, where there is no subsequent prefill computation to hide behind. Since indexing cost scales with the number of tokens (roughly `$O(n \log n)$` for tree construction), and prefill computation also scales with `$n$`, the overlap is naturally balanced — both scale similarly, so the hidden work is roughly proportional to the visible work.

**Layer exclusions:** The paper notes that "neither IceCache nor baseline methods are applied to the first two layers of the models" (Section 5.1). This is based on prior work (Tang et al., 2024) showing that "initial layers of the model exhibit relatively low sparsity" — meaning the attention patterns in early layers are more uniform across tokens, making selective retrieval less effective (most pages would be selected anyway). By keeping the first two layers' full KV-cache on GPU, IceCache avoids wasting retrieval effort on layers where sparsity is insufficient to benefit from selection.

**Critical-page reuse (IceCache reuse variant):** The paper also describes a faster variant where DCI-trees are built and queried only at a subset of "anchor layers" (every 3 layers, starting from layer 3), and the selected page indices are reused for the intervening layers. This is analogous to OmniKV's layer reuse strategy and trades some accuracy for reduced indexing and query overhead. Table 5 shows IceCache (reuse) with a 256 budget achieves 47.7 average LongBench score on Llama-3.1-8B — slightly below IceCache's 49.0 but still above all baselines — while reducing the time-to-second-token from 7.7s to 5.9s (Figure 7a). This demonstrates that the DCI-tree overhead is modest enough that even at full per-layer granularity, the latency is competitive; the reuse variant simply offers an additional speed-accuracy tradeoff knob.

**Integration with FlashInfer:** The paper implements IceCache on top of FlashInfer (Ye et al., 2025), a highly optimized attention kernel library. FlashInfer provides efficient sparse attention primitives that can handle non-contiguous KV-cache layouts — essential for IceCache because while pages are contiguous within themselves, the set of selected pages may be scattered in the GPU KV-cache table. FlashInfer's attention kernel takes a mask specifying which tokens to attend to and efficiently computes attention only for those positions, avoiding computation on the discarded tokens.

#### Incremental Tree Updates During Decoding

The dynamic update mechanism — how the DCI-tree stays current as new tokens are generated — is described in Algorithm 1, lines 26–37, and is what distinguishes IceCache from methods that make one-time token selection decisions.

**When updates occur:** The trigger is the offloading of the oldest window page `$P_w$` from GPU to CPU. In PagedAttention, the "window" is the set of most recent tokens that are always kept on GPU for fast access to local context. As new tokens are generated and appended to the window, the oldest window page eventually falls outside the window and is offloaded to CPU. At this point, the tokens in `$P_w$` transition from being always-available-on-GPU to being selectively-retrieved-from-CPU — and therefore must be added to the DCI-tree so they can be retrieved when needed.

**Update procedure for each token `$k_i$` in the offloaded page:**

1. **Random level assignment:** Assign a level `$\ell_i$` using the same geometric distribution promotion process as during initial indexing (Algorithm 2). The promotion ratio `$r$` is the same, ensuring consistency — new tokens enter the tree at levels proportional to the existing distribution.

2. **Parent search:** Call `QUERY(k_i, T, \ell_i, 1)` to find the single nearest neighbor at level `$\ell_i + 1$`, which becomes the parent node `$p_i$` for `$k_i$`.

3. **Insertion:** Insert `$k_i$` into the tree with `$p_i$` as its parent node index. This means `$k_i$` is added to the cluster (node) associated with `$p_i$`. If that node already has a memory page associated with it, `$k_i$`'s KV-cache entry is written to that page. If the page is full (reaches size `$s$`), a new page is dynamically allocated.

**Why random promotion is reused:** The geometric distribution ensures that tokens added during decoding have the same expected level distribution as those added during prefill. This preserves the **probabilistic balancing** of the tree: each higher level has roughly a fraction `$r$` of the points from the level below, regardless of when those points were inserted. If new tokens were always inserted at the bottom level (level 1), the tree would become unbalanced over time — bottom-level nodes would grow while higher levels would remain sparse, degrading the pruning efficiency of the hierarchical search. Random promotion prevents this by occasionally promoting new tokens to higher levels, maintaining the skip-list-like structure.

**Cost of incremental updates:** Each offloaded page triggers an insertion for each of its `$s$` tokens. For each token, the dominant cost is the QUERY to find the parent — which involves traversing the tree from the top down to level `$\ell_i + 1$`, performing P-DCI queries at each level. However, the number of tokens per page is small (typically 16–64), and the update is triggered only occasionally (when a page fully leaves the window). In practice, window sizes are set to be a modest fraction of the total sequence (e.g., a few thousand tokens), so updates are infrequent relative to the number of decoding steps. The paper's latency breakdown (Figure 7c) shows that "Offloading and others" accounts for only 0.015 seconds per token — suggesting the update overhead is minimal.

**Why dynamic updates matter for long-generation tasks:** In chain-of-thought reasoning or long-form generation, the model's attention patterns evolve as it produces new content. A token generated mid-reasoning may become crucial for later steps (e.g., an intermediate calculation result). Methods like SnapKV that select important tokens once (during prefill) and never update their selection will miss these newly-generated critical tokens if they aren't in the window. Methods like StreamingLLM that only keep sink and recent tokens will discard them entirely once they leave the window. IceCache's incremental indexing ensures these tokens are stored in the tree — grouped with semantically similar tokens — and can be retrieved when later queries need them. This is the mechanistic basis for the paper's claim of "mitigating performance degradation in long-generation tasks."

#### Design Choices Summary

**Why semantic clustering over sequential page layout:** Sequential layout (used by Quest, ArkVale, PQCache) scatters semantically related tokens across many pages, requiring more pages (and more PCIe bandwidth) to achieve the same retrieval recall. Clustering concentrates relevance, improving the hit rate per page loaded.

**Why hierarchical M-DCI over flat P-DCI or LSH:** Flat P-DCI would require maintaining a priority queue over all `$n$` tokens; LSH (used by MagicPig) is a sampling-based method with probabilistic recall guarantees. The hierarchy provides efficient pruning with deterministic (not sampling-based) search guided by distance lower bounds, giving more precise control over the top-`$k$` retrieval.

**Why head-specific trees over unified page selection:** Different attention heads attend to different patterns. A one-size-fits-all page selection forces heads to share pages that may be irrelevant to some and miss pages critical to others. Head-specific retrieval tailors the selection — at the cost of building and querying more trees (one per head).

**Why bulk loading over individual page transfer:** PCIe has high per-transaction overhead. Bulk aggregation amortizes this overhead over many pages, approaching the theoretical bandwidth limit of the link. This is purely a systems optimization — it does not affect accuracy, only latency.

**Why the transformation `$T_K, T_Q$` rather than operating in raw embedding space:** The M-DCI search operates on Euclidean distances (a metric space). Raw attention uses dot-product similarity, which is not a metric. The transformation maps the problem to a unit hypersphere where Euclidean distance is a monotonic function of dot-product similarity, enabling distance-based nearest-neighbor search to serve as attention-based retrieval. The specific form (appending a residual dimension to keys, padding queries with zero) ensures all transformed vectors have unit norm, making the distance-similarity relationship exact.

**Why random promotion rather than deterministic level assignment:** Random promotion ensures that higher levels are statistically representative of the points below them, regardless of insertion order. Deterministic assignment (e.g., by norm) could create degenerate trees where certain regions of the embedding space are overrepresented at high levels and others underrepresented, causing queries to miss relevant clusters during hierarchical descent. Randomness provides a probabilistic guarantee of balanced representation.

## 4. Key Insights and Innovations

### Innovation 1: Semantic Page Layout as a First-Class Design Principle for KV-Cache Management

The dominant, largely unquestioned assumption across prior KV-cache management systems — from PagedAttention (Kwon et al., 2023) through Quest (Tang et al., 2024) and ArkVale (Chen et al., 2024a) — is that memory pages should be organized by **token sequence order**. This is a natural default: tokens arrive sequentially during prefill, so storing them contiguously in the order they appear is the path of least resistance. The page table simply maps logical token positions to physical memory, preserving temporal adjacency.

IceCache's foundational conceptual move is to reject this default and replace it with a **semantic layout principle**: memory pages should be organized by the similarity of what the tokens *mean* to the attention mechanism, not by where they appear in the sequence. The paper identifies a specific failure mode that this temporal-default causes: tokens that are semantically relevant to a given query are "scattered across multiple pages" (Section 2.2), forcing retrieval systems to load pages that are mostly filled with irrelevant content. This is not a small inefficiency — it means that under a fixed page budget, prior methods systematically underutilize the available PCIe bandwidth by transferring tokens with low expected relevance, while simultaneously missing relevant tokens that happen to reside in pages not selected.

What makes this a conceptual innovation rather than an engineering tweak is that it reframes the KV-cache management problem from **memory allocation** (how to efficiently pack sequential data into pages) to **information organization** (how to structure storage so that retrieval is maximally informative per byte transferred). The DCI-tree is the mechanism that realizes this principle (detailed in Section 3), but the principle itself is separable from the mechanism: any clustering algorithm that groups tokens by key embedding similarity and maps clusters to pages would instantiate the same idea. The paper's empirical results quantify the benefit: with a 64-token budget, IceCache on Llama-3.1-8B achieves 47.8 average LongBench accuracy, matching PQCache's performance at a 256-token budget (a 4× budget reduction), and with 256 tokens reaches 49.0 — within 0.5 points of the full KV-cache at 49.5 (Table 1). This is direct evidence that the semantic layout principle, independent of the specific retrieval algorithm, is the dominant factor: PQCache also uses query-aware page selection, but its sequential page layout means the same retrieval budget loads fewer useful tokens.

The paper's diagnostic framing — "scattered relevant tokens" as the root cause of retrieval inefficiency — is itself a contribution. Prior work characterized the KV-cache problem primarily in terms of *which* tokens to keep (eviction) or *how* to retrieve them (LSH, product quantization), without questioning whether the *storage organization* might be the bottleneck. IceCache's reframing suggests that storage layout and retrieval strategy are not independent design choices — they must be co-designed so that the structure of storage matches the structure of retrieval access patterns.

This is a **fundamental shift** in how to think about the problem, not an incremental improvement. It changes the design space from "how do we select better pages from a fixed, sequential layout?" to "how do we design the layout to make page selection inherently more effective?" The paper shows that the latter yields gains that the former cannot match, even with sophisticated selection algorithms.

---

### Innovation 2: The DCI-Tree as a Dynamically Updatable Index for Streaming Attention

Prior approaches to KV-cache management make a critical assumption about temporality: the importance of tokens is either determined once (during prefill, as in SnapKV and StreamingLLM) and frozen, or recomputed from scratch at each decoding step (as in Quest and ArkVale) without maintaining a persistent structure that learns from previous retrievals. This creates a fundamental tension: static methods cannot adapt to evolving attention patterns during long-generation tasks, while stateless dynamic methods waste computation re-deriving information that could be preserved across steps.

IceCache introduces a **stateful, incrementally updatable index** — the DCI-tree — that maintains a semantically-organized representation of the entire KV-cache and updates it as new tokens are generated. This is conceptually distinct from both the eviction paradigm (permanently discard tokens) and the stateless retrieval paradigm (recompute importance scores from scratch). The DCI-tree is a **persistent data structure** that accumulates information: when a window page is offloaded to CPU, its tokens are inserted into the tree based on their key embeddings, where they remain available for retrieval by any future query. When a query arrives, the tree is traversed to find relevant pages — but the tree itself persists across queries, so the organizational work done during indexing is amortized over all subsequent decoding steps.

What makes this a genuine innovation is the combination of three properties that no prior KV-cache system simultaneously achieves:

1. **Semantic organization** (tokens grouped by similarity, not sequence position).
2. **Incremental updatability** (new tokens inserted without rebuilding the index).
3. **Query-aware retrieval** (pages selected based on the current query's embedding, not a static importance score).

Each property individually exists in prior work: PagedAttention provides efficient paging but no semantic organization; Quest/ArkVale provide query-aware retrieval but on a static, sequentially-organized page layout; SnapKV provides a form of persistence (fixed token selection) but no updatability. The DCI-tree's distinct contribution is integrating all three into a single data structure that supports the full lifecycle of long-sequence inference: prefill-time construction, decode-time retrieval, and continuous insertion of new tokens without degradation.

The significance of updatability is empirically demonstrated in the paper's results on generation-heavy tasks. On GSM8K chain-of-thought reasoning (Table 3), IceCache achieves 47.4% accuracy with a 10% budget (matching full KV-cache at 48.2%), while ArkVale — which uses query-aware retrieval but without incremental indexing — falls to 30.9% under the same budget. This 16.5 percentage point gap is not explained by retrieval quality alone (ArkVale performs competitively on non-generative LongBench tasks at 42.8 vs. IceCache's 47.8 with budget 64 in Table 1); it reflects the fact that in generation tasks, the model's attention shifts to newly produced tokens, and ArkVale's prefill-time page selection cannot adapt to retrieve them. The DCI-tree's incremental updates directly address this failure mode.

The random promotion mechanism (Section 3, Algorithm 2) is worth highlighting as an elegant design choice that enables updatability without sacrificing tree balance. Rather than requiring periodic rebalancing (which would be expensive and interrupt decoding), the geometric distribution of level assignments ensures that insertions naturally maintain the hierarchical structure regardless of insertion order. This is a form of **probabilistic balancing** — the tree stays approximately balanced in expectation without any explicit rebalancing operations — which is what makes incremental updates computationally cheap enough to run during decoding without introducing noticeable latency (only 0.015 seconds per token in Figure 7c).

This is a **fundamental advance** in how indexing interacts with streaming inference. It establishes that KV-cache management can be framed as an **online indexing problem** — building and maintaining a search structure over a growing dataset — rather than a one-time selection or per-step recomputation problem. This framing opens the door to a rich literature on dynamic spatial indices (skip lists, B-trees, R-trees) that prior KV-cache work had not connected to.

### Innovation 3: Head-Specific Retrieval as a Necessary Condition for High-Fidelity Sparse Attention

The dominant approach in query-aware KV-cache selection — represented by Quest and ArkVale — computes a single page importance score by aggregating across all attention heads, then selects the same set of pages for every head. This is a natural simplification: it reduces the retrieval problem to one decision per layer rather than one per head, cutting the retrieval overhead by a factor of `$H$` (the number of heads). The implicit assumption is that the aggregation does not lose much information — that heads largely agree on which tokens are important.

IceCache challenges this assumption and provides evidence that it is costly. By constructing a separate DCI-tree for each attention head and performing independent page selection, IceCache achieves substantially higher accuracy than ArkVale at the same budget (Table 1: 42.8 vs. 47.8 at budget 64 on Llama-3.1-8B; 33.0 vs. 39.0 on Mistral-7B). Critically, this gap cannot be attributed to the semantic page layout alone, because ArkVale also uses query-aware selection on PagedAttention-organized pages — the head-specific retrieval is an independent source of gain.

The conceptual contribution here is the identification that attention head diversity is not a nuisance to be averaged away but a **signal to be preserved**. Different heads in a transformer learn different attention patterns — some focus on local syntax (attending to immediately adjacent tokens), some on long-range semantic dependencies (attending to tokens with similar meaning regardless of distance), some on specific positional patterns (attending to sentence boundaries or section headers). When Quest or ArkVale aggregates importance scores across heads, a token that is critical to one head (e.g., a long-range referent for a coreference-resolution head) but irrelevant to others will have its importance diluted below the selection threshold. Head-specific retrieval avoids this dilution: each head gets exactly the pages it needs, even if they differ from what other heads need.

The paper's handling of Grouped-Query Attention (GQA) models adds nuance: for GQA, where multiple query heads share a single KV head, IceCache takes the union of selected pages across queries in the same group. This is a principled compromise — it preserves head-level specificity in *selection* (each query head independently identifies its relevant pages) while avoiding redundant transfers for heads that share KV representations. The fact that IceCache still outperforms head-uniform methods on GQA models (Llama-3.1-8B and Mistral-7B both use GQA) demonstrates that the selection diversity matters even when the underlying KV representations are shared.

This is an **incremental but important refinement** of the sparse attention paradigm. Prior work established that attention is sparse (only a few tokens receive significant weight per query). IceCache's head-specific retrieval establishes that this sparsity is **structured differently per head**, and that respecting this structure yields accuracy gains beyond what uniform sparsity patterns can achieve. The implication for future work is clear: KV-cache selection strategies should be evaluated not just on aggregate sparsity but on whether they preserve the heterogeneity of attention patterns across heads.

The layer-exclusion design choice (keeping the first two layers' full KV-cache on GPU; Section 5.1) reinforces this insight from the opposite direction: early layers exhibit low sparsity (attention is more uniform), so head-specific retrieval provides little benefit there. The paper applies neither IceCache nor baseline methods to layers 0–1, implicitly acknowledging that head-specific retrieval is most valuable where attention is sparse and heterogeneous — which is precisely where head-uniform methods lose information by averaging.

### Innovation 4: Computing Retrieval in a Transformed Space Where Distance Encodes Attention Relevance

A subtle but consequential conceptual move in IceCache is operating page selection in a **transformed embedding space** (Equations 2 and 3) where Euclidean distance between transformed key and query vectors is mathematically equivalent to their dot-product attention score. This is not a standard dimensionality reduction or approximation — it is an exact mapping that changes the *computational primitive* for retrieval from inner-product search (which is not a metric) to nearest-neighbor search (which is).

The significance of this move is that it unlocks a vast toolkit of metric-space indexing algorithms — including M-DCI, but also k-d trees, ball trees, HNSW, and locality-sensitive hashing variants — that are designed for Euclidean or metric distances but cannot directly operate on inner-product similarity. Without this transformation, IceCache's hierarchical tree search would need to be redesigned from scratch to support maximum-inner-product search (MIPS), a known harder problem because the inner product does not satisfy the triangle inequality, which is what gives hierarchical pruning its efficiency guarantees.

The conceptual contribution is the recognition that the *shape* of the attention retrieval problem can be changed by a suitable embedding, without loss of information, to fit the shape of existing efficient algorithms. The specific transformation — appending a residual dimension to keys to make them unit-norm, and zero-padding queries — maps all points onto a unit hypersphere where Euclidean distance `$d(a,b)$` relates to inner product `$\langle a, b \rangle$` via `$d(a,b)^2 = 2 - 2\langle a, b \rangle$`. On the sphere, "closer in Euclidean distance" ≡ "larger inner product" ≡ "higher attention weight." This is an exact equivalence, not an approximation — no information is lost in the transformation.

Prior work on approximate attention has explored various transformations: LSH-based methods like Reformer (Kitaev et al., 2020) use random projections to hash similar vectors to the same bucket; product-quantization methods like PQCache compress key vectors into discrete codes for efficient storage and approximate inner-product computation. But these are fundamentally *lossy* — they trade accuracy for speed. IceCache's transformation is *lossless* for the retrieval objective: the nearest neighbors in the transformed space are exactly the keys with the highest attention scores. Any error in IceCache's retrieval comes from the approximate nature of the M-DCI search (which may miss some true nearest neighbors), not from the transformation itself.

This is a **reframing of the problem** rather than a new algorithm. It says: the difficulty of efficient attention is not inherent to the inner-product formulation; it is a mismatch between the problem's geometry (which is metric on the sphere) and the conventional representation (raw unnormalized vectors). By exploiting this geometry — specifically, the fact that on the unit sphere, Euclidean distance and inner product are monotonically related — the problem becomes amenable to the extensive literature on metric nearest-neighbor search. The paper's choice of M-DCI is one instantiation of this principle, but the principle itself is broader.

The empirical payoff is that M-DCI's lower-bound pruning (Prioritized DCI) provides deterministic, distance-based guarantees on retrieval quality — unlike LSH-based sampling (MagicPig), which provides probabilistic recall guarantees. The Passkey Retrieval results (Figure 6) are illuminating here: IceCache maintains 100% retrieval accuracy across all tested budgets (64, 128, 256) and all context lengths (10k–100k words), with no degradation as the passkey insertion position varies. This is the behavior of a system that can deterministically locate tokens by their semantic content, not probabilistically stumble upon them. The transformation makes this deterministic retrieval possible by giving the search algorithm a proper metric structure to exploit.

This innovation sits at the **intersection of fundamental and engineering**: the geometric insight (inner product ≡ Euclidean distance on the sphere) is mathematically elementary, but its application to KV-cache retrieval — and the resulting ability to use metric-space indices without approximation error — is a novel synthesis that the paper is the first to exploit at this scale.

### Innovation 5: PCIe Transfer Patterns as a First-Class Design Constraint, Not an Afterthought

A recurring pattern in systems papers is that algorithmic innovations (semantic clustering, hierarchical search) are designed first, and the communication layer (how data actually moves between CPU and GPU) is optimized post-hoc. IceCache inverts this: the **bulk loading design** (Section 4.5) treats the PCIe transfer characteristics as a constraint that shapes the retrieval strategy, not as an implementation detail to be cleaned up later.

The specific insight is that small, scattered memory transfers over PCIe are catastrophically inefficient — not because the total bytes are large, but because the **per-transaction overhead** (DMA engine setup, address translation, interrupt handling) dominates the actual data movement time for transfers smaller than a certain threshold (typically tens to hundreds of KB). Prior page-based methods implicitly assumed that the cost of loading `$p$` pages is roughly `$p \times$` (cost of loading one page), which is true for the data copy time but false for the total wall-clock time due to fixed per-transaction costs. IceCache's bulk loading — aggregating all selected pages into a single contiguous buffer, performing one PCIe transaction, then scattering on the GPU side — amortizes the fixed overhead over many pages, approaching the theoretical bandwidth limit of the link.

What makes this a conceptual contribution rather than just an optimization is that it **changes the optimal retrieval strategy**. If individual page transfers are expensive, the system is incentivized to select fewer pages with higher per-page relevance (to minimize the number of transactions). But if bulk loading makes transfers cheap, the system is incentivized to select more pages (to maximize recall) as long as they can be aggregated into a single transfer. This shifts the tradeoff space: IceCache can afford to be more aggressive in page selection — loading pages that are "probably relevant" — because the marginal cost of an additional page in a bulk transfer is near-zero (just the data copy time, with no additional DMA setup). This makes the clustering strategy even more valuable: when a page is loaded, the "bonus" co-located tokens come essentially for free in terms of transfer overhead.

The quantitative evidence for this is in the latency breakdown (Figure 7c): CPU–GPU communication accounts for only 0.015 seconds of the 0.11-second total TPOT at 36k sequence length — just 13.6% of the per-token latency. For comparison, the DCI-query (CPU-side search) accounts for 0.05 seconds (45.5%), and the actual decoding computation accounts for 0.04 seconds (36.4%). Without bulk loading, the communication fraction would be substantially higher — potentially dominating the latency and making the entire retrieval-based approach uncompetitive with eviction methods. By making communication cheap, IceCache shifts the bottleneck back to where it can be optimized (faster CPU search) or tolerated (GPU decode), rather than being fundamentally limited by the PCIe bus.

The **pipelining design** (Figure 5) applies the same principle to the prefill phase: rather than treating offloading and indexing as sequential steps that add to the critical path, the system overlaps them with GPU prefill computation. This is a standard technique in high-performance computing, but its application to KV-cache indexing is novel because indexing is typically seen as a prefill-time cost that cannot be hidden. The key enabler is that indexing is CPU-bound (distance computations, tree insertions) while prefill is GPU-bound (matrix multiplications, attention), so they can genuinely run in parallel without competing for the same resource. The result is that the latency of building the DCI-tree — which could be substantial for long sequences (roughly `$O(n \log n)$` distance computations for `$n$` prompt tokens) — is almost entirely hidden.

This is an **incremental but practically decisive** contribution. Many elegant algorithmic ideas for KV-cache management have failed to achieve practical adoption because their latency overheads (in absolute wall-clock time) outweighed their memory savings. IceCache's careful attention to the systems layer — bulk loading, pipelining, buffer management — is what makes the algorithmic contributions (semantic clustering, hierarchical search, head-specific retrieval) viable in practice. The paper's Figure 1, showing IceCache in the Pareto-optimal region of the accuracy-latency-memory tradeoff, is as much a testament to the systems engineering as to the core algorithmic ideas. Without this innovation, IceCache would be another high-accuracy, high-latency method — interesting in principle but not deployable.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper uses three primary benchmarks. **LongBench** (Bai et al., 2023) is the main evaluation suite, comprising 16 sub-tasks across six categories (Single-Document QA, Multi-Document QA, Summarization, Few-shot Learning, Synthetic, Code) with sequence lengths ranging from 1,235 to 18,409 tokens (Table 1). **Passkey Retrieval** (Mohtashami & Jaggi, 2023) tests long-range dependency handling by inserting a random passkey at variable positions within long contexts (10k–100k words, 100 test cases per length). **GSM8K** (Cobbe et al., 2021) evaluates chain-of-thought mathematical reasoning with a 10% KV-cache budget constraint. Additional evaluations use LongGenBench (Wu et al., 2024) for long-form generation tasks (Appendix C) and RULER (Hsieh et al., 2024) for extremely long-context scenarios up to 250k tokens (Section 5.5).

- **Base model(s).** The paper tests four models spanning scales and attention architectures: **Llama-3.1-8B-Instruct** (8B parameters, group-query attention with 8 KV heads) and **Mistral-7B-Instruct-v0.2** (7B, GQA) on an NVIDIA A100 40GB PCIe GPU; **Qwen3-32B** (32B, GQA) on an NVIDIA H100 80GB PCIe GPU; and **LongChat-7B-v1.5** (7B, standard multi-head attention without GQA) also on the A100. The model selection deliberately spans both GQA and standard MHA architectures, and the inclusion of Qwen3-32B tests scalability to larger models. Additionally, **Qwen3-4B-Instruct-2507** is used for the RULER extremely-long-context experiments (Section 5.5) on a single H100.

- **Metrics.** **Accuracy (%):** For LongBench, accuracy is computed per sub-task and averaged across all 16 sub-tasks (each sub-task's metric follows the original benchmark definitions — e.g., F1 for QA tasks, ROUGE-L for summarization). For Passkey Retrieval, accuracy is the fraction of test cases (out of 100) where the model correctly retrieves the passkey. For GSM8K, accuracy is the fraction of problems with correct final answers. **Latency:** Two metrics are reported — Time to the Second Token (TT2T) measures the wall-clock time from the start of decoding to the completion of the second generated token (capturing the page selection and loading overhead for the first decoding step, since the first token uses the full KV-cache), and Time Per Output Token (TPOT) measures the average wall-clock time per generated token across the full decoding sequence. Both are reported in seconds at a 36k input sequence length. **Memory:** CUDA memory footprint is reported in GB (Figure 1), measuring peak GPU memory consumption during inference. **Recall in retrieval:** For Passkey Retrieval, the paper implicitly reports recall of the critical token (the passkey) across varying context lengths and insertion positions.

- **Baselines.** Six state-of-the-art KV-cache optimization methods serve as baselines, spanning both eviction-based and offloading-based approaches:
  - **SnapKV** (SKV; Li et al., 2024b): Eviction-based; selects important KV pairs by analyzing attention patterns from the prompt tail.
  - **StreamingLLM** (SLM; Xiao et al., 2023): Eviction-based; keeps only sink tokens and a recent window.
  - **OmniKV** (OKV; Hao et al., 2025): Offloading-based; reuses important tokens across consecutive layers, requiring only a subset of layers to perform full KV-cache operations. Notably, it uses substantially more GPU memory than other methods because most layers stay fully resident.
  - **MagicPig** (MPG; Chen et al., 2024b): Offloading-based; uses Locality Sensitive Hashing (LSH) to sample relevant keys. The paper notes it is restricted to CPUs with AVX-512.
  - **PQCache** (PQC; Zhang et al., 2024a): Offloading-based; applies product quantization to compress KV-cache and approximate attention. This is the strongest baseline in the LongBench accuracy experiments.
  - **ArkVale** (AKV; Chen et al., 2024a): Offloading-based; uses query-aware page criticality estimation with PagedAttention.

  Two upper-bound references are also included: **Full KV-cache** (FULL), which keeps the entire KV-cache on GPU with no offloading or eviction; and **ground-truth top-k** (TOP-k), which uses oracle knowledge of the actual top-k highest attention weights to select tokens — representing the theoretical ceiling for any sparse attention method at a given budget.

- **Generation budget / compute accounting.** The "budget" for all methods is measured in **number of KV-cache tokens retained or retrieved**. For IceCache, this is the parameter `$k$` — the number of critical keys identified by the M-DCI query (Section 4.4), which controls how many pages are selected and therefore how many total tokens (up to `$p \times s$` where `$p$` is the number of loaded pages and `$s$` is the page size) are used in sparse attention. The paper tests budgets of 64, 128, and 256 tokens (Table 1). For baselines, the budget represents the equivalent constraint on their token retention mechanisms (e.g., top-k pages for Quest/ArkVale, retained tokens for SnapKV/StreamingLLM). For the GSM8K experiments, a relative budget of 10% of the full KV-cache size is applied to all methods (Table 3). Latency comparisons (Figure 7) use a fixed input sequence length of 36k tokens to control for sequence-length effects on decoding speed. The paper does **not** include the cost of DCI-tree construction (during prefill) or incremental updates (during decoding) in the token budget — that cost is measured separately as latency overhead (Figure 7c). All methods use the entire KV-cache to generate the first token, so the TT2T metric captures the overhead of page selection and loading for the first retrieval step (Section 5.3.2).

- **Cross-validation / statistical protocol.** The paper does not report cross-validation or statistical significance testing. The standard protocols for LongBench and GSM8K evaluation are used (fixed test sets). For Passkey Retrieval, 100 test cases are generated per (context length, insertion position) combination, providing a reasonable sample size for this synthetic task. The paper explicitly notes that neither IceCache nor baseline methods are applied to the first two layers of any model (Section 5.1), following prior work (Tang et al., 2024) that found early layers exhibit low sparsity, making selective retrieval less beneficial. All latency measurements are taken on the same hardware setup with 64 CPU threads fixed (Section 5.1). The paper implements all methods within the same HuggingFace Transformers framework (v4.57.1) with FlashInfer (Ye et al., 2025) for attention operations, ensuring hardware-level consistency across baselines.

### Main Quantitative Results

#### Passkey Retrieval: Perfect Long-Range Recall Across All Budgets

IceCache achieves 100% retrieval accuracy on Passkey Retrieval across all tested budget sizes (64, 128, 256), all context lengths (10k–100k words), and all passkey insertion positions (0% to 95% of the context in 5% increments). Figure 6 shows three uniform heatmaps — one per budget — where every cell (context length × insertion position) is at 100% accuracy. This is a particularly stringent test: a passkey inserted at 95% position within a 100k-word context requires the model to attend to a single token buried deep in the sequence, where methods that only keep recent tokens (StreamingLLM) or make static selection decisions (SnapKV) would predictably fail. The uniform 100% result demonstrates that IceCache's head-specific M-DCI search can deterministically locate semantically relevant tokens regardless of their position, length, or the total context length — a property that sampling-based methods (MagicPig's LSH) or static-selection methods cannot guarantee. The paper does not report Passkey Retrieval results for baselines, so direct comparison on this specific metric is not possible, but the contrast with the baselines' LongBench performance (where they underperform, particularly on tasks requiring mid-document retrieval) is suggestive.

#### LongBench: IceCache Matches Full KV-Cache Accuracy While Using a Fraction of the Budget

**Headline results on Llama-3.1-8B-Instruct (Table 1):**

With a 256-token budget, IceCache achieves an average LongBench accuracy of **49.0**, compared to 49.5 for the Full KV-cache and 49.8 for the ground-truth top-k oracle. This is a 0.5-point gap to the full model — meaning IceCache preserves **99.0%** of the original accuracy while operating with a tiny fraction of the KV-cache (256 tokens vs. the full sequence lengths of up to ~18k tokens). Compared to the strongest baseline at the same budget:
- PQCache (256 budget): 47.3 (1.7 points behind IceCache)
- OmniKV (256 budget): 46.3 (2.7 points behind)
- ArkVale (256 budget): 42.8 (6.2 points behind)

The efficiency advantage is even more dramatic at lower budgets. IceCache with a **64-token budget achieves 47.8** — matching PQCache's performance at a 256-token budget (47.3) while using only 25% of the tokens. This is the concrete basis for the paper's claim that IceCache "attains competitive or even superior latency and accuracy while using only 25% of the KV-cache token budget" (Abstract).

**Per-task analysis on Llama-3.1-8B (Table 1, ICE vs. baselines at budget 256):**

IceCache outperforms all baselines on 12 of 16 sub-tasks. The largest margins over PQCache (the strongest baseline) appear on:
- Qasper (Single-Doc QA): 44.7 vs. 43.3 (+1.4)
- HotpotQA (Multi-Doc QA): 55.2 vs. 55.2 (tie, but IceCache leads on other Multi-Doc tasks: 2WikiMQA at 45.9 vs. 45.1, Musique at 30.6 vs. 28.4)
- GovReport (Summarization): 34.6 vs. 27.2 (+7.4 — the largest single-task gap)
- Lcc (Code): 62.5 vs. 59.0 (+3.5)

Notable cases where IceCache does not lead:
- TriviaQA (Few-shot): 92.0 vs. PQCache's 91.1 (both close to FULL's 91.7)
- SAMSum (Few-shot): 43.5 vs. PQCache's 41.2 and SnapKV's 39.0 (IceCache leads but by a smaller margin)
- PRe (Synthetic): 100.0 (perfect, matching ground-truth top-k and MagicPig)
- RB-P (Code): 56.4 vs. SnapKV's 56.2 (essentially tied, with OmniKV at 51.5)

The Multi-Document QA and Summarization categories show the most consistent IceCache advantages, which aligns with the paper's motivation: these tasks require retrieving information from diverse positions within long documents, precisely the scenario where semantic clustering should maximize page-level hit rates compared to sequential page layout.

**Results on Mistral-7B-Instruct-v0.2 (Table 1):**

With a 256-token budget, IceCache achieves **41.7** average accuracy, compared to 42.2 for Full KV-cache and 42.6 for ground-truth top-k. The strongest baseline, MagicPig, reaches 39.1 — a 2.6-point advantage for IceCache. At 64-token budget, IceCache scores **39.0**, already matching MagicPig's 256-budget performance. The pattern mirrors Llama-3.1-8B: IceCache maintains near-oracle accuracy at a fraction of the budget.

Per-task patterns differ somewhat from Llama-3.1-8B. On Mistral-7B, PQCache drops to 37.4 (vs. IceCache's 41.7 at budget 256), a 4.3-point gap — larger than on Llama-3.1-8B. This suggests PQCache's product quantization approach may be more sensitive to model-specific attention patterns, while IceCache's semantic clustering transfers more robustly. Also notable: MagicPig (39.1) is the strongest baseline on Mistral-7B (vs. PQCache being strongest on Llama-3.1-8B), indicating that baseline ranking is model-dependent.

**Results on Qwen3-32B and LongChat-7B-v1.5 (Table 2):**

For Qwen3-32B (a much larger model), IceCache with a 64-token budget achieves **42.2** average accuracy, retaining 97.2% of Full KV-cache performance (43.4). At 256 tokens, it reaches **43.1**, or 99.3% of full performance. This demonstrates that IceCache's benefits scale to 32B-parameter models without degradation — the clustering and retrieval quality does not depend on model scale.

For LongChat-7B-v1.5 (standard multi-head attention, not GQA), IceCache at 64 tokens achieves **33.9** (96.3% of Full's 35.2), rising to **35.0** at 256 tokens (99.4% of Full). This confirms that IceCache works effectively with standard MHA — the head-specific retrieval design does not require GQA and provides benefits regardless of the attention architecture.

The paper does not report baseline comparisons for these two additional models (only Full KV-cache is shown in Table 2), which is a limitation — we cannot assess whether IceCache's advantage over baselines is consistent across model scales and architectures, or whether it primarily holds for the 7–8B scale.

#### Latency Analysis: IceCache Achieves Competitive Speed Without Sacrificing Accuracy

**Time to the Second Token (TT2T) at 36k sequence length on Llama-3.1-8B (Figure 7a):**

- IceCache: **7.7 seconds**
- IceCache (reuse variant): **5.9 seconds**
- OmniKV: 5.8 seconds (fastest among retrieval-based methods)
- ArkVale: 7.4 seconds
- PQCache: 13.3 seconds (slowest among retrieval-based methods)
- SnapKV: 0.55 seconds (eviction-based, much faster but lower accuracy)
- StreamingLLM: 0.13 seconds (fastest overall, lowest accuracy)
- MagicPig: Not reported (restricted to CPUs with AVX-512)

IceCache's 7.7-second TT2T puts it in a competitive middle ground: slower than OmniKV (which achieves its speed by reusing pages across layers and keeping most layers fully resident on GPU — a higher-memory design) but substantially faster than PQCache (13.3s, nearly 2× IceCache's latency). The reuse variant at 5.9 seconds essentially matches OmniKV while achieving higher accuracy (47.7 vs. 46.3 at budget 256 on LongBench; Tables 1 and 5).

The large gap between eviction methods (0.13–0.55s) and retrieval methods (5.8–13.3s) reflects the inherent cost of CPU–GPU communication and CPU-side search that offloading-based methods incur. However, as the paper notes, "their speed often comes at the cost of accuracy": StreamingLLM scores 33.5 on LongBench (Table 1), compared to IceCache's 49.0 — a 15.5-point accuracy gap that makes the speed comparison moot for accuracy-sensitive applications.

**Time Per Output Token (TPOT) at 36k sequence length (Figure 7b):**

- IceCache: **0.11 seconds per token** (with 99.0% accuracy relative to Full KV)
- IceCache (reuse): **0.06 seconds per token** (with 96.4% accuracy relative to Full, from Table 5: 47.7/49.5)
- OmniKV: 0.05 seconds per token (with 93.5% accuracy: 46.3/49.5)
- PQCache: 0.13 seconds per token (with 95.6% accuracy: 47.3/49.5)
- ArkVale: ~0.09 seconds per token (estimated from Figure 7b bar chart)
- SnapKV: 0.03 seconds per token (with 82.4% accuracy: 40.8/49.5)
- StreamingLLM: 0.03 seconds per token (with 67.7% accuracy: 33.5/49.5)

IceCache achieves the **highest accuracy percentage** (99.0%) among all methods while maintaining TPOT (0.11s) well below PQCache (0.13s) — it is both more accurate and faster than the next-best retrieval baseline. The reuse variant (0.06s) trades ~2.6 accuracy points for a ~45% latency reduction, still outperforming OmniKV in accuracy while nearly matching its speed. This establishes IceCache as the Pareto-optimal method in the accuracy-latency space among retrieval-based approaches.

**TPOT latency breakdown for IceCache (Figure 7c):**

At 36k sequence length with a total TPOT of 0.11 seconds:
- **DCI-query (CPU-side search):** 0.05 seconds (45.5% of total)
- **Decoding (GPU computation):** 0.04 seconds (36.4%)
- **Loading (CPU–GPU communication):** 0.015 seconds (13.6%)
- **Offloading and others:** 0.005 seconds (4.5%)

The DCI-query module is the largest single contributor to latency, which makes sense: for each decoding step, every attention head (or every anchor head in GQA) must traverse its DCI-tree using M-DCI search, which involves distance computations and priority queue operations. However, this CPU-bound work runs in parallel across heads and does not block the GPU — the loading and decoding components are what determine the critical path. The fact that loading is only 0.015 seconds validates the bulk loading design: without it, individual small page transfers would multiply this component significantly. The miscellaneous overhead (0.005s for offloading and incremental tree updates) is negligible.

#### GSM8K Chain-of-Thought Reasoning: Preserving Accuracy in Long-Generation Tasks

With Mistral-7B-Instruct-v0.2 and a 10% KV-cache budget (Table 3):

- **IceCache: 47.4%** accuracy
- Full KV-cache: 48.2% (gap of only 0.8 points)
- PQCache: 46.2% (1.2 points behind IceCache)
- SnapKV: 44.7% (2.7 points behind)
- StreamingLLM: 44.4%
- OmniKV: 42.7%
- MagicPig: 43.1%
- ArkVale: **30.9%** (16.5 points behind IceCache)

The GSM8K results reveal a critical pattern that distinguishes IceCache from other methods in generation-heavy scenarios. ArkVale — which achieves 42.8 average LongBench accuracy on Llama-3.1-8B (not dramatically behind IceCache's 47.8 at the same 64-token budget) — collapses to 30.9% on GSM8K. This 16.5-point gap is the largest between any two methods in the table and is the clearest empirical evidence for the paper's claim that static or prefill-time-only token selection fails in long-generation tasks. ArkVale selects important pages based on prompt-phase attention patterns and does not update its selection during generation; in chain-of-thought reasoning, the model continuously produces new reasoning steps that become critical for subsequent attention, and ArkVale cannot retrieve them if they weren't selected during prefill. IceCache's incremental DCI-tree updates (inserting newly generated tokens into the tree as they age out of the window) directly address this failure mode, enabling it to maintain near-full accuracy even as the attention patterns evolve.

PQCache at 46.2% is the strongest baseline, suggesting that its product-quantization-based retrieval provides some robustness to generation-time attention shifts — but still trails IceCache by 1.2 points. The small gap to Full KV-cache (0.8 points) indicates that for this task and budget, IceCache is extracting nearly all the value available from selective retrieval.

#### Scalability to Extremely Long Contexts (RULER, 150k–250k Tokens)

Using Qwen3-4B-Instruct-2507 with a 256-token budget (Table 4), IceCache maintains accuracy comparable to Full KV-cache across all tasks and context lengths:

**Single-NIAH (Needle-in-a-Haystack):**
- 150k, 200k, 250k tokens: IceCache achieves **100.0%** at all lengths (matching Full KV exactly)

**Multi-keys NIAH:**
- 150k: IceCache **98.0%** vs. Full 97.0% (slightly better)
- 200k: IceCache **91.3%** vs. Full 92.0% (0.7-point gap)
- 250k: IceCache **93.0%** vs. Full 91.0% (2.0-point advantage)

**QA:**
- 150k: IceCache **92.0%** vs. Full 93.0% (1.0-point gap)
- 200k: IceCache **95.0%** vs. Full 95.0% (tie)
- 250k: IceCache **91.7%** vs. Full 91.3% (0.4-point advantage)

The IceCache (reuse) variant shows similar results, typically within 1–2 points of vanilla IceCache. The occasional cases where IceCache **exceeds** Full KV-cache accuracy (e.g., Multi-keys NIAH at 250k: 93.0% vs. 91.0%) may reflect noise given the small differences, or could indicate that selective attention — by filtering out distractors — sometimes helps the model focus on the correct information.

Figure 8 demonstrates the latency scaling advantage: as context length grows from 150k to 300k tokens, Full KV-cache's decode latency per token rises sharply (from roughly 150ms to 320ms), while IceCache and IceCache(reuse) grow much more slowly (from roughly 110ms to 140ms for IceCache, and 70ms to 95ms for IceCache(reuse)). This is the direct consequence of fixed-budget retrieval: IceCache always loads the same small number of pages regardless of total context length, so its attention computation cost is roughly constant. Full KV-cache attention cost scales with sequence length (loading all keys and values), causing the steep latency growth visible in the figure.

### Ablation Studies and Robustness Checks

**IceCache (reuse) variant: trading accuracy for speed.** The critical-page-reuse technique — building DCI-trees and performing queries only at every third layer ("anchor layers") starting from layer 3, and reusing the selected page indices for the intervening layers — is evaluated on LongBench with Llama-3.1-8B at a 256-token budget (Table 5). IceCache (reuse) achieves **47.7** average accuracy, compared to vanilla IceCache's 49.0 — a drop of 1.3 points. Per-task, the largest drops appear on GovReport (31.8 vs. 34.6, −2.8), RB-P (53.1 vs. 56.4, −3.3), and HotpotQA (55.1 vs. 55.2, negligible). The latency benefit is substantial: TT2T drops from 7.7s to 5.9s (Figure 7a), and TPOT from 0.11s to 0.06s (Figure 7b) — roughly a 25–45% latency reduction for a 2.6% relative accuracy decrease (47.7/49.0 vs. 49.0/49.5). This establishes a smooth accuracy-latency tradeoff curve where practitioners can choose the operating point based on deployment constraints.

**Model architecture robustness: GQA vs. standard MHA.** The paper tests both GQA models (Llama-3.1-8B, Mistral-7B, Qwen3-32B) and a standard MHA model (LongChat-7B-v1.5). IceCache achieves 99.4% of Full KV-cache accuracy on MHA (35.0 vs. 35.2 at budget 256; Table 2) — essentially identical to its performance on GQA models (99.0% on Llama-3.1-8B, 98.8% on Mistral-7B). This demonstrates that the head-specific retrieval design works equally well regardless of whether heads share KV representations (GQA) or have independent ones (MHA). The paper's GQA handling — computing the union of selected pages across query heads in the same group — does not appear to lose meaningful information compared to full per-head retrieval.

**Model scale robustness: 7B to 32B parameters.** IceCache's accuracy retention relative to Full KV-cache is consistent across model scales: 99.0% for 8B (Llama-3.1), 98.8% for 7B (Mistral), 99.3% for 32B (Qwen3-32B). The Qwen3-32B results (Table 2) are particularly important because larger models typically have higher-dimensional key embeddings (more information per token) and more attention heads (more heterogeneity), which could theoretically make clustering harder (higher-dimensional spaces suffer from the curse of dimensionality) and retrieval more head-specific. The fact that IceCache maintains near-perfect accuracy at 32B scale with a tiny 64–256 token budget suggests the semantic clustering principle is robust to these scaling effects.

**Task diversity: 16 sub-tasks across 6 categories.** The LongBench results (Tables 1 and 2) cover fundamentally different types of long-context understanding: extractive QA (NarrativeQA, Qasper), multi-hop reasoning (HotpotQA, 2WikiMQA, Musique), abstractive summarization (GovReport, QMSum, MultiNews), few-shot in-context learning (TREC, TriviaQA, SAMSum), synthetic retrieval (PassageCount, PassageRetrieval), and code understanding (Lcc, RepoBench-P). IceCache's performance is not uniform across categories — it shows the largest advantages on Multi-Doc QA and Summarization, the smallest on Few-shot Learning — but it consistently outperforms baselines across all categories with the same 256-token budget. This breadth is important because KV-cache management methods can be brittle to task type: a method optimized for extractive retrieval might fail on summarization where attention is more diffuse. IceCache's consistent performance suggests the semantic clustering approach is task-agnostic.

**Budget sensitivity: 64, 128, and 256 tokens.** Both on Llama-3.1-8B and Mistral-7B (Table 1), IceCache's accuracy improves monotonically with budget: 47.8 → 48.6 → 49.0 on Llama-3.1-8B; 39.0 → 40.4 → 41.7 on Mistral-7B. The marginal gain from doubling the budget diminishes: +0.8 from 64→128, +0.4 from 128→256 on Llama-3.1-8B. This is expected: the most critical tokens are captured even at small budgets; additional budget captures progressively less important tokens. The fact that 64 tokens already achieves 96.5% of full accuracy (47.8/49.5) on Llama-3.1-8B indicates that the attention distribution is indeed highly sparse and that IceCache's semantic clustering successfully concentrates the most important tokens in the first few retrieved pages.

**Layer exclusion: first two layers kept full.** The paper excludes the first two layers from all methods (both IceCache and baselines), following prior findings (Tang et al., 2024) that early layers exhibit low attention sparsity. This is not formally ablated — there is no experiment showing what happens if IceCache is applied to all layers. However, the near-perfect accuracy retention (99.0%) despite this exclusion suggests that the early layers' full KV-cache contributes minimally to overall accuracy; applying selective retrieval to them would likely increase latency with negligible accuracy gain. A missing ablation: what happens if *more* layers are kept full (e.g., first 4 or first 6)? This would reduce the benefit of IceCache but might be necessary for tasks with diffuse attention patterns.

**Incremental update mechanism: implicit validation through GSM8K.** The incremental DCI-tree updates during decoding (inserting offloaded window tokens into the tree) are not directly ablated (no "IceCache without updates" experiment). However, the GSM8K results (Table 3) serve as an implicit validation: ArkVale, which uses query-aware page selection but without dynamic updates, collapses to 30.9% on GSM8K while IceCache achieves 47.4% — close to Full KV-cache's 48.2%. The most parsimonious explanation for this 16.5-point gap is IceCache's incremental indexing, since both methods use query-aware retrieval on PagedAttention-organized pages (the only difference being IceCache's semantic layout and dynamic updates). A direct ablation (IceCache with tree frozen after prefill vs. IceCache with updates) would strengthen this causal attribution but is not provided.

**Long-generation tasks (LongGenBench, Appendix C).** IceCache substantially outperforms PQCache on long-form generation: 0.331 average accuracy vs. 0.273 (Table 6), while nearly matching Full KV-cache (0.324 vs. 0.331 — IceCache is actually 0.007 points higher, possibly within noise). The completion rate (fraction of examples where the model produces a valid output) is 95.3% for IceCache vs. 97.6% for Full and 88.7% for PQCache. The fact that IceCache *exceeds* Full KV-cache accuracy on several LongGenBench metrics (Accuracy Once: 0.377 vs. 0.349; Accuracy Periodic: 0.164 vs. 0.135) while having a slightly lower completion rate suggests that selective attention may help the model avoid distraction from irrelevant context during generation — a phenomenon also observed in the RULER results (Table 4, where IceCache sometimes exceeds Full).

**Negative result: the DCI-query dominates TPOT latency.** Figure 7c shows that the CPU-side DCI-query accounts for 45.5% of per-token latency (0.05s out of 0.11s). This is not framed as a negative by the paper, but it is a practical limitation: even with bulk loading and pipelining, the retrieval search itself is the bottleneck. This constrains how much IceCache can improve latency — optimizations to the CPU search (faster M-DCI implementation, SIMD acceleration, multi-threading across heads) would be necessary to reduce TPOT further. The reuse variant partially addresses this by reducing the number of queries (only every third layer), cutting TPOT nearly in half (0.06s), but with an accuracy cost.

### Critical Assessment

#### Claim 1: IceCache maintains 99% of full KV-cache accuracy with a 256-token budget.

**Supported, with important scope limitations.** On LongBench with Llama-3.1-8B-Instruct, IceCache at budget 256 achieves 49.0 vs. Full's 49.5 — indeed 99.0% retention (Table 1). On Mistral-7B-Instruct, it's 41.7 vs. 42.2 (98.8%). On Qwen3-32B, 43.1 vs. 43.4 (99.3%). On LongChat-7B, 35.0 vs. 35.2 (99.4%). These numbers are consistent across models and architectures.

However, the claim's generality is bounded in ways the paper does not fully acknowledge:

- **The 99% figure is an average across 16 diverse sub-tasks.** Individual task retention varies: GovReport (Summarization) sees a 0.6-point drop from Full (34.6 vs. 35.2, ~98.3% retention), while NarrativeQA (Single-Doc QA) actually improves slightly (30.6 vs. 30.2 at budget 256). The average masks task-level variation that could matter for deployment on specific task types.

- **LongBench's maximum sequence length is ~18k tokens** (NarrativeQA at 18,409). The RULER experiments extend to 250k, but only on a 4B model and only for synthetic retrieval tasks (Single-NIAH, Multi-keys NIAH) plus QA. The 99% claim has not been validated on realistic tasks (summarization, multi-hop reasoning) at 100k+ token scales, only on needle-in-a-haystack retrieval which is the easiest case for sparse attention.

- **The claim is measured at budget 256.** At budget 64 on Llama-3.1-8B, retention drops to 96.5% (47.8/49.5) — still impressive, but the paper's headline "99% maintenance" is specific to the 256-budget operating point.

- **The accuracy definition for LongBench averages heterogeneous metrics** (F1, ROUGE-L, exact match) across sub-tasks. A 0.5-point drop in this average could reflect larger drops on specific metrics that are diluted in the average.

#### Claim 2: IceCache attains competitive or superior accuracy while using only 25% of the KV-cache token budget of other offloading methods.

**Supported with qualification.** The specific comparison is IceCache at budget 64 (47.8 average on LongBench, Llama-3.1-8B) vs. PQCache at budget 256 (47.3). This is indeed 25% of the token budget for equivalent accuracy. However:

- **This is a comparison at one specific operating point** (budget 64 vs. 256). At budget 128, IceCache (48.6) substantially exceeds PQCache at 256 (47.3), making the 25% claim somewhat conservative — IceCache might need even less than 25% at this accuracy level. But at higher accuracy targets (e.g., matching PQCache's best possible performance), the ratio would differ.

- **The "token budget" metric is not perfectly comparable across methods.** IceCache loads tokens plus their co-located neighbors (up to `$p \times s$` tokens for `$p$` loaded pages). If the page size `$s$` is 16 and `$k=64$` tokens are targeted, the actual number of loaded tokens could be up to `$p \times 16$` where `$p \leq 64$` (since multiple target tokens can be in the same page). The paper doesn't report the actual number of tokens loaded vs. the budget `$k$`, making direct budget comparisons approximate.

- **PQCache's budget semantics differ:** PQCache uses product quantization to compress the KV-cache and approximate attention with all compressed tokens, not a strict subset. The "budget 256" for PQCache may represent a different computational and memory regime than IceCache's "budget 256."

#### Claim 3: IceCache establishes a new state-of-the-art accuracy-latency tradeoff.

**Supported for the Pareto frontier among retrieval-based methods, but not a universal claim.** Figure 7b shows that IceCache achieves 99.0% accuracy retention at 0.11s TPOT, while the next-best retrieval method (PQCache) achieves 95.6% at 0.13s — IceCache dominates in both dimensions. Among all methods, IceCache is indeed on the Pareto frontier: no other method achieves both higher accuracy and lower latency simultaneously.

However:

- **Eviction-based methods occupy a different Pareto region** (SnapKV at 82.4% accuracy, 0.03s TPOT; StreamingLLM at 67.7%, 0.03s). For latency-critical applications where 80% accuracy is acceptable, these methods dominate IceCache. The paper acknowledges this in the latency analysis ("their speed often comes at the cost of accuracy"), but the state-of-the-art claim should be qualified as "among methods that preserve >95% of full accuracy."

- **MagicPig is excluded from latency comparisons** because it is "restricted to costly AVX-512 CPUs" (Section 5.3.2). This is a legitimate exclusion for GPU-centric deployment, but it means the latency comparison is incomplete — MagicPig might be faster on CPU-only setups, which the paper does not evaluate.

- **The latency measurements are at a single sequence length (36k)** and a single GPU (A100). Relative performance may shift at different sequence lengths (Figure 8 shows Full KV-cache latency grows much faster than IceCache's, so the advantage would widen at longer sequences) or on different hardware (PCIe bandwidth varies across GPU generations and form factors).

#### Claim 4: IceCache effectively mitigates performance degradation in long-generation tasks.

**Strongly supported by the GSM8K results but from a single task.** The key evidence is Table 3: IceCache achieves 47.4% on GSM8K CoT vs. Full's 48.2%, while ArkVale drops to 30.9%. The mechanism — incremental DCI-tree updates — is the only plausible explanation for why IceCache maintains near-full performance while a query-aware retrieval method without updates fails catastrophically.

However:

- **GSM8K is a single benchmark** with a specific type of generation (mathematical chain-of-thought). LongGenBench (Appendix C) provides additional evidence on long-form text generation tasks, where IceCache (0.331) nearly matches Full (0.324) and substantially outperforms PQCache (0.273). But two benchmarks is still limited evidence for the broad class of "long-generation tasks."

- **The causal role of incremental updates is inferred, not directly tested.** An ablation with updates disabled would directly measure the update mechanism's contribution. Without it, alternative explanations (e.g., IceCache's semantic page layout alone might be sufficient if the prefill-phase tree already captures the relevant embedding regions) cannot be ruled out, though they seem less plausible given ArkVale's collapse (ArkVale also does query-aware retrieval, just on sequentially-organized pages).

- **The 10% budget on GSM8K** is a relative budget tied to sequence length, not an absolute token count. This makes it harder to compare across tasks with different generation lengths.

#### Claim 5: IceCache is effective across different model scales and attention architectures.

**Supported but with incomplete baseline comparisons.** IceCache maintains 99.0–99.4% accuracy retention across 7B, 8B, and 32B models with both GQA and MHA (Tables 1 and 2). However:

- **Baseline comparisons are only provided for Llama-3.1-8B and Mistral-7B** (Table 1). For Qwen3-32B and LongChat-7B, only Full KV-cache is shown (Table 2). We cannot assess whether IceCache's advantage over baselines persists at larger scales or on MHA, only that it maintains near-Full accuracy.

- **The model scale range (7B–32B) is relatively narrow.** No experiments on very small models (<1B parameters, where attention patterns might be less sparse) or very large models (70B+, where KV-cache pressure is most acute in practice).

- **All models are from a similar "era"** of LLM development (Llama-3.1, Mistral, Qwen3, LongChat — all roughly 2023–2024 architectures). It's unclear whether the attention sparsity patterns that IceCache exploits are universal across training methodologies and architectural variants (e.g., mixture-of-experts models, models with different positional encodings).

#### What would strengthen the paper:

1. **A direct ablation of incremental DCI-tree updates** (IceCache with frozen prefill tree vs. IceCache with updates) on both LongBench and GSM8K to quantify the update mechanism's contribution independently from the semantic layout.

2. **Baseline comparisons on Qwen3-32B and LongChat-7B** to verify that IceCache's advantages over SnapKV, PQCache, et al. scale to larger models and standard MHA architectures.

3. **Experiments on a 70B+ model** to test whether the semantic clustering principle holds at scales where KV-cache pressure is most severe in deployment.

4. **Sensitivity analysis on the promotion ratio `$r$` and page size `$s$`** — these hyperparameters are mentioned but never varied experimentally, making it unclear how sensitive IceCache's performance is to their settings.

5. **Confidence intervals or multiple runs** for the latency measurements to distinguish genuine differences from measurement noise (the 0.01-second differences between some methods in Figure 7 are small relative to potential system variance).

6. **A "no clustering" ablation** — running IceCache's M-DCI page selection on sequentially-organized pages (i.e., the same retrieval algorithm as IceCache but with Quest/ArkVale's page layout) — to isolate the contribution of semantic clustering from the contribution of M-DCI as a retrieval algorithm. This would cleanly separate the two innovations.

7. **Measurement of actual tokens loaded vs. the budget `$k$`** to quantify how often the semantic clustering causes IceCache to load more tokens than the nominal budget (due to co-location in pages) and whether this overhead grows with sequence length or model scale.

## 6. Limitations and Trade-offs

### 6.1 The DCI-Query Dominates Per-Token Latency, Capping Speed Improvements

**The constraint:** IceCache's per-token decoding latency at 36k sequence length is 0.11 seconds — competitive with retrieval-based baselines but an order of magnitude slower than eviction-based methods (SnapKV at 0.03s, StreamingLLM at 0.03s; Figure 7b). The latency breakdown in Figure 7c reveals that the **DCI-query module alone accounts for 0.05 seconds (45.5% of total TPOT)**, making it the single largest contributor. This is the CPU-side M-DCI search that traverses the DCI-tree for each attention head to identify the top-k relevant keys — an operation that involves distance computations, priority queue maintenance, and tree traversal across multiple hierarchical levels.

**The consequence:** IceCache's latency is fundamentally bounded by the speed of CPU-side approximate nearest neighbor search. Even with bulk loading reducing PCIe transfer overhead to just 0.015 seconds (13.6% of TPOT) and incremental updates contributing a negligible 0.005 seconds, the core retrieval algorithm remains the bottleneck. This means that **further engineering optimizations to data transfer or GPU computation will yield diminishing returns** — the majority of the latency is algorithmic, not infrastructural. For latency-sensitive applications (interactive chat, real-time code completion, live translation), 0.11 seconds per output token is substantially slower than eviction-based alternatives, and even the reuse variant (0.06s per token, trading ~2.6 accuracy points on LongBench as reported in Table 5 vs. Table 1) remains 2× slower than SnapKV. Practitioners choosing between IceCache and an eviction-based method must weigh whether the accuracy gain (99.0% vs. 82.4% accuracy retention on LongBench for Llama-3.1-8B at budget 256) justifies a ~3–4× increase in per-token latency.

**What evidence exists:** Figure 7c directly quantifies the DCI-query's share of latency. Figure 7b provides the absolute TPOT comparisons across methods. Table 1 provides the corresponding accuracy numbers. The paper does not profile the DCI-query further — no breakdown of how time is spent across levels of the tree, across attention heads, or between distance computations and priority queue operations.

**Mitigation status:** The reuse variant (IceCache reuse, Section 5.3.2 and Table 5) partially mitigates this by performing DCI queries only at every third layer, cutting TPOT to 0.06s — a ~45% reduction. However, this comes at an accuracy cost (47.7 vs. 49.0 on LongBench with Llama-3.1-8B at budget 256), and the paper does not explore other mitigation strategies such as SIMD-accelerated distance computations, reduced-precision arithmetic for the lower-bound estimates, multi-threaded parallelism across attention heads within a single query, or early termination heuristics that sacrifice recall guarantees for speed. The paper also does not discuss whether the DCI-query could be offloaded to GPU (which would eliminate PCIe round-trips for the distance computations but require the tree structure to reside in GPU memory, undercutting the memory savings). This limitation is not explicitly acknowledged as a central bottleneck — the paper presents the latency breakdown descriptively rather than framing the DCI-query's dominance as a constraint on further speed improvements.

### 6.2 The Cost of Building and Updating the DCI-Tree Is Not Amortized Over the Token Budget

**The constraint:** IceCache's headline efficiency numbers — 99% accuracy retention with a 256-token budget — measure only the **retrieval budget during decoding** (the number of tokens loaded per step for sparse attention). They do not account for the computational cost of **constructing the DCI-tree during prefill** or **incrementally updating it during decoding** (inserting offloaded window tokens as generation progresses). Constructing the tree for `$n$` prompt tokens requires running M-DCI queries for every token to find its parent (Algorithm 2), which involves distance computations and hierarchical traversals. Incremental updates during decoding (Algorithm 1, lines 26–37) require the same operation for each token in each offloaded window page.

**The consequence:** In a deployment where the prefill phase is rare relative to the number of decoding steps (e.g., a single long document is processed once, then many queries are answered), the tree construction cost is amortized over many decoding steps and is negligible. But in a **short-prompt, high-throughput setting** — where many independent requests each have modest prompt lengths (a few hundred to a few thousand tokens) and generate short responses — the prefill indexing cost could **dominate the total inference time**. Each new request requires building a fresh DCI-tree from scratch, and the paper provides no quantification of this cost relative to the prompt processing time. The pipelining design (Figure 5b) hides indexing latency behind GPU prefill computation, but only when the prefill computation is long enough to mask the indexing — for short prompts, the indexing may extend the critical path.

Additionally, the incremental update cost during decoding (inserting offloaded window tokens into the tree) is not isolated in the latency breakdown. Figure 7c groups "Offloading and others" at 0.005 seconds, which includes both the PCIe transfer of aged-out window pages and the DCI-tree insertions. At longer sequence lengths or with larger window sizes, the frequency of page offloading (and thus tree insertions) increases, potentially raising this component.

**What evidence exists:** The paper does not report prefill-phase latency separately from end-to-end latency. Figure 7a reports Time to the Second Token (TT2T) at 7.7 seconds for IceCache at 36k sequence length, which includes the prefill, the first token generation (using full KV-cache), and the retrieval/loading for the second token — but does not break out how much of that 7.7 seconds is attributable to DCI-tree construction vs. model computation. Section 4.1 notes that "by performing indexing during the prompt or CPU offloading phase, IceCache amortizes the tree construction cost and avoids incurring additional latency during inference" — but this is a design intent, not a measured result. No experiment varies prompt length independently of total sequence length to isolate indexing cost.

**Mitigation status:** The pipelining design partially addresses this by overlapping indexing with prefill (Figure 5b), but the effectiveness of this overlap depends on prompt length and the relative speeds of GPU prefill vs. CPU indexing. The paper does not explore whether the DCI-tree could be cached and reused across requests that share the same prompt (e.g., in a serving system where the same system prompt or document is processed many times), which would completely amortize the indexing cost. The paper also does not investigate whether a lighter-weight indexing scheme (e.g., a shallower tree, or indexing only a subset of layers) could reduce prefill overhead with acceptable accuracy loss. This limitation is implicitly acknowledged in the amortization discussion (Section 4.1) but is not quantitatively characterized.

### 6.3 Semantic Clustering Depends on the Quality of Key Embeddings, Leaving Uncertainty for Model Architectures and Training Paradigms Not Tested

**The constraint:** IceCache's core mechanism — clustering tokens by the similarity of their key embeddings in the transformed space — assumes that **key embeddings encode semantically meaningful similarities** that correspond to attention patterns. This assumption holds for the models tested (Llama-3.1-8B, Mistral-7B, Qwen3-32B, LongChat-7B, and Qwen3-4B), all of which are dense transformer models from a similar era (2023–2024) with standard rotary position embeddings and similar training recipes.

**The consequence:** The paper provides no evidence about what happens when this assumption is violated or attenuated:

- **Models with different positional encodings** (e.g., ALiBi, no positional encoding, or learned absolute positions) might produce key embeddings where position dominates semantics, causing the DCI-tree to cluster tokens by position rather than by content — which would reduce the hit rate benefit since relevant tokens at different positions would be in different clusters regardless of semantic similarity.

- **Mixture-of-Experts (MoE) models** route tokens through different feed-forward experts, which could cause key embeddings from the same semantic cluster to diverge due to different expert pathways — potentially breaking the assumption that similar content produces similar keys.

- **Models fine-tuned for specific tasks** (e.g., instruction-tuned, RLHF-trained) might have key embedding distributions that differ substantially from the base pretrained models tested. A model fine-tuned for mathematical reasoning might have keys that cluster by problem-solving step rather than by surface-level semantic similarity, which could either help or hurt IceCache's retrieval depending on whether the clustering aligns with attention patterns.

- **Very small models** (e.g., <1B parameters) with lower-dimensional key embeddings might not have sufficient representational capacity to encode fine-grained semantic distinctions, making the clusters coarse and less informative for retrieval.

- **Non-transformer architectures** (e.g., state-space models like Mamba, RWKV) that do not use key-value attention at all are entirely outside IceCache's scope, but even within the transformer family, architectural variants like linear attention or sliding-window attention could change the sparsity patterns that IceCache exploits.

**What evidence exists:** The paper tests four model families but all within a narrow architectural band (dense transformers with RoPE, 7B–32B parameters, 2023–2024 vintage). Table 2 shows IceCache works on both GQA and standard MHA, which is a positive signal for architectural robustness, but this is a difference in attention head organization, not in the fundamental nature of key embeddings. The paper provides no sensitivity analysis: there is no experiment varying the key embedding transformation (e.g., what happens if `$c$` is set incorrectly?), no comparison of clustering quality across layers (are later layers' key embeddings more semantically structured than early layers'?), and no measurement of cluster purity or intra-cluster vs. inter-cluster attention weight distributions that would characterize how well the clustering aligns with actual attention patterns.

**Mitigation status:** Not addressed. The paper states in Section 5.1 that the choice of models is meant to "assess scalability and architectural generality" by including both GQA and MHA, but this is a narrow definition of architectural generality. The transformation `$T_K$` (Equation 2) is presented as a fixed mapping with no discussion of its robustness to embedding distribution shifts. A practitioner deploying IceCache on a model outside the tested distribution would need to assume transferability without evidence.

### 6.4 No Ablation Isolates the Contribution of Semantic Page Layout from the Contribution of M-DCI Retrieval

**The constraint:** IceCache makes two simultaneous changes relative to prior page-based methods like Quest and ArkVale: (1) it organizes pages by semantic clustering rather than sequential token order, and (2) it uses the M-DCI algorithm for query-aware retrieval rather than the page-criticality estimation used by those baselines. The experimental results (Table 1) show IceCache substantially outperforming ArkVale (49.0 vs. 42.8 on Llama-3.1-8B at budget 256), but **cannot distinguish how much of the gain is due to better page layout vs. better retrieval**.

**The consequence:** Without a controlled ablation, the paper's central claim — that semantic page layout is the key innovation — rests on inference rather than direct evidence. It is possible, for example, that M-DCI is a dramatically better retrieval algorithm than ArkVale's page-criticality estimation even on sequentially-organized pages, and that the semantic clustering contributes only a small additional benefit. Or, conversely, that semantic clustering alone (with ArkVale's simpler retrieval algorithm) would achieve most of the gain, and M-DCI's sophistication is partially redundant.

This matters for several practical reasons:

- **If M-DCI is the primary driver**, then practitioners should focus on implementing M-DCI-like retrieval regardless of page layout — which would mean IceCache's additional complexity (building and maintaining DCI-trees, head-specific indexing) might not be necessary.
- **If semantic clustering is the primary driver**, then the specific retrieval algorithm matters less, and practitioners could substitute a simpler, faster retrieval mechanism (e.g., coarse-level filtering followed by exact top-k on a small candidate set) while keeping the semantic page layout — potentially reducing the DCI-query latency bottleneck (Limitation 6.1).
- **Implementation complexity:** M-DCI and the DCI-tree require substantial engineering effort (hierarchical index construction, random promotion, priority-queue-based search, incremental updates). If a simpler index (e.g., flat k-means clustering with pages assigned to clusters, followed by brute-force search within selected clusters) achieves comparable accuracy, the implementation cost of IceCache's full design would be hard to justify.

**What evidence exists:** The closest the paper comes to an ablation is comparing IceCache against Quest and ArkVale (Table 1), which share the sequential page layout but differ in retrieval algorithm. ArkVale (42.8 at budget 64 on Llama-3.1-8B) vs. IceCache (47.8) shows the combined gain of both innovations. But there is no "IceCache retrieval on sequential pages" condition or "ArkVale retrieval on clustered pages" condition to factorize the contributions. The paper also does not report retrieval recall (the fraction of true top-k attention keys that are present in the selected pages) for IceCache vs. baselines, which would directly measure the contribution of page layout to retrieval quality independently of downstream task accuracy. The Passkey Retrieval results (Figure 6) show perfect recall but only for IceCache — no baseline comparison.

**Mitigation status:** Not addressed. The paper does not acknowledge this as a missing experiment or suggest it as future work. Section 4.4 (page selection details) describes the semantic clustering benefit qualitatively ("tokens relevant to a given query tend to be concentrated within fewer pages" and "the hit rate of significant keys during decoding increases") but does not quantify hit rate improvement relative to sequential layout.

### 6.5 The 99% Accuracy Claim Is Validated Primarily on Tasks Where Attention Is Highly Sparse and Retrieval-Centric

**The constraint:** IceCache's strongest results — 99.0% accuracy retention on LongBench with a 256-token budget on Llama-3.1-8B — are achieved on a benchmark heavily weighted toward tasks that require retrieving specific information from long documents: Single-Doc QA, Multi-Doc QA, and Summarization together account for 9 of the 16 sub-tasks. These are precisely the tasks where attention sparsity is most pronounced (the model needs to find and focus on a small number of relevant passages) and where semantic clustering should provide the greatest benefit.

**The consequence:** The paper's headline accuracy numbers may not generalize to tasks where **attention is more diffuse** — where the model needs to attend to many tokens across the entire sequence rather than focus on a few highly relevant ones. The table below shows the per-category accuracy gap between IceCache (budget 256) and Full KV-cache on Llama-3.1-8B, computed from Table 1:

| Category | Full KV | IceCache (256) | Gap | % Retention |
|---|---|---|---|---|
| Single-Doc QA (2 tasks) | 42.9 avg | 42.7 avg | −0.2 | 99.5% |
| Multi-Doc QA (3 tasks) | 44.5 avg | 43.9 avg | −0.6 | 98.7% |
| Summarization (3 tasks) | 29.2 avg | 28.6 avg | −0.6 | 97.9% |
| Few-shot Learning (3 tasks) | 69.3 avg | 69.5 avg | +0.2 | 100.3% |
| Synthetic (2 tasks) | 53.9 avg | 53.4 avg | −0.5 | 99.1% |
| Code (2 tasks) | 62.0 avg | 59.5 avg | −2.5 | 96.0% |

The Code category shows the largest absolute drop (−2.5 points), which may reflect that code understanding tasks involve reasoning about program structure where relevant tokens are distributed throughout the code (variable definitions, function calls, imports) rather than clustered in a single passage. If a practitioner deploys IceCache primarily for code-related tasks, they might see meaningfully lower accuracy retention than the 99% average would suggest. Conversely, Few-shot Learning actually improves slightly (+0.2), possibly because selective attention filters out distracting in-context examples.

For tasks like **translation** (where every token in the source maps to tokens in the target and attention is broad), **creative writing** (where the model needs to maintain thematic coherence across the entire generated text), or **dialogue** (where turn-taking information is distributed across the conversation), the attention sparsity assumption may weaken significantly. The paper does not evaluate any of these task types.

**What evidence exists:** The category-level analysis above is computable from Table 1 but not presented by the paper. The inclusion of diverse sub-tasks on LongBench is a strength, but the paper's analysis treats them only in aggregate (the average score) or at the individual sub-task level, without discussing how the effectiveness varies by attention patterns. The RULER experiments (Table 4) add evidence for synthetic retrieval tasks (Single-NIAH, Multi-keys NIAH) but do not test diffuse-attention scenarios. LongGenBench (Appendix C) tests long-form generation, which is closer to diffuse attention, and IceCache nearly matches Full KV there (0.331 vs. 0.324) — but this is a single benchmark with a 256-token budget, and the paper does not analyze attention sparsity on this task.

**Mitigation status:** Not explicitly addressed. The paper's choice of benchmarks is justified by the prevalence of long-context understanding tasks in current LLM deployment, but the limitation to sparsity-assuming tasks is not discussed as a constraint on generalizability. The paper does not suggest a diagnostic for practitioners to determine whether their task's attention patterns are sparse enough to benefit from IceCache.

### 6.6 The Promotion Ratio and Page Size Hyperparameters Are Not Evaluated for Sensitivity

**The constraint:** Two hyperparameters fundamentally shape IceCache's behavior: the **promotion ratio `$r$`** (Section 4.2, Algorithm 2) that controls how many points are promoted to higher levels of the DCI-tree (determining tree depth and search pruning aggressiveness), and the **page size `$s$`** (mentioned in Algorithm 1 and Section 4.1) that determines how many tokens are co-located per page (affecting the tradeoff between retrieval precision — fewer irrelevant tokens per page with small `$s$` — and transfer efficiency — fewer pages to load with large `$s$`). The paper does not report the values used or conduct any sensitivity analysis.

**The consequence:** A practitioner implementing IceCache must choose these hyperparameters without guidance, and poor choices could significantly degrade performance:

- **If `$r$` is too large:** too many points are promoted to high levels, making the tree shallow (few levels) and search less efficient (larger candidate sets at each level, reducing the pruning benefit of the hierarchy). This could increase DCI-query latency without improving recall.
- **If `$r$` is too small:** too few points are promoted, making the tree deep but sparse at higher levels. Queries might miss relevant clusters because the top-level entry points are not representative of the underlying data distribution (random promotion with very small `$r$` produces high variance in which points reach the top).
- **If `$s$` is too small:** pages contain few tokens, so retrieving `$k$` relevant tokens requires loading many pages, increasing the number of PCIe transactions (even with bulk loading, there is overhead from the scatter operation and page table lookups) and potentially loading proportionally fewer "bonus" co-located tokens.
- **If `$s$` is too large:** pages contain many tokens, so loading a page retrieves many irrelevant tokens along with the relevant ones, wasting PCIe bandwidth and GPU memory on tokens that don't contribute to attention.

The lack of guidance is particularly problematic because optimal values likely depend on the model (key embedding dimensionality affects clustering structure), the sequence length (longer sequences may need larger pages to keep the number of nodes manageable), and the task (diffuse attention may benefit from larger pages that capture broader context).

**What evidence exists:** None. The paper describes the promotion mechanism (Algorithm 2: `while Random(0, 1) < r do ℓ_i ← ℓ_i + 1`) and mentions that pages have size `$s$` (Algorithm 1, line 16: "Number of tokens in the last page ≥ s − 1") but never states the actual values used in experiments, never varies them, and never reports how performance (accuracy, latency, memory) changes with different settings. This is a significant omission for a systems paper where hyperparameter sensitivity directly affects deployability.

**Mitigation status:** Not addressed. The paper does not acknowledge hyperparameter sensitivity as a limitation or suggest default values or heuristics for choosing `$r$` and `$s$`. This is a gap that a practitioner would need to fill through trial-and-error on their specific model and task.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

IceCache introduces a **fundamental reframing of KV-cache management from a memory allocation problem to an information organization problem**. This is not an incremental tweak to page selection algorithms — it is a shift in what the field considers the primary design variable. Prior work (PagedAttention, Quest, ArkVale, PQCache) accepted the default that memory pages should be organized by token sequence order, then asked: "given this layout, how do we select the best pages?" IceCache inverts this: "what layout would make page selection inherently most effective, and how do we build it?"

This reframing matters because it changes what future researchers optimize. Before IceCache, the natural research trajectory was toward **better page selection algorithms** — more sophisticated criticality estimators, more accurate importance scores, more clever ways to approximate attention from a fixed sequential storage. After IceCache, the natural trajectory shifts toward **co-designing storage layout and retrieval together** — asking how the structure of memory should mirror the structure of attention. This is a more productive framing because it attacks the root cause of retrieval inefficiency (scattered relevant tokens) rather than mitigating its symptoms (loading irrelevant tokens and hoping the selection algorithm compensates).

The paper's empirical results quantify how much this reframing matters: IceCache with a 64-token budget matches PQCache's performance at a 256-token budget on LongBench with Llama-3.1-8B (47.8 vs. 47.3; Table 1). PQCache already had a sophisticated retrieval mechanism (product quantization with approximate attention), but its sequential page layout meant it needed 4× more tokens to achieve the same accuracy. This 4× gap is not attributable to IceCache having a better retrieval algorithm — it is the direct consequence of semantic page layout vs. sequential page layout. The paper resolves the apparent tension between high-accuracy retrieval methods (which used large page budgets to compensate for scattered relevant tokens) and low-latency eviction methods (which sacrificed accuracy for speed) by showing that **the tradeoff was an artifact of page layout, not a fundamental constraint**.

The paper also establishes a new paradigm for how KV-cache indices interact with streaming inference: the **online indexing framing**. Prior methods treated the KV-cache either as a static pool (select tokens once, as in SnapKV and StreamingLLM) or as a stateless problem (recompute importance from scratch each step, as in Quest and ArkVale). IceCache demonstrates that a persistent, incrementally updatable index — the DCI-tree — can maintain a semantically-organized representation across the entire generation lifecycle, adapting to new tokens as they arrive. This is a conceptual advance beyond KV-cache management: it connects LLM inference to the rich literature on dynamic spatial indices and opens the door to adapting techniques from database systems, computational geometry, and online learning that have not previously been applied to transformer attention.

The GSM8K results (Table 3) provide the clearest evidence of this paradigm shift's practical importance: ArkVale — a sophisticated query-aware retrieval method with static page selection — collapses to 30.9% accuracy on chain-of-thought reasoning, while IceCache achieves 47.4% (vs. Full's 48.2%). The 16.5-point gap is not about retrieval quality in the abstract — it is about whether the retrieval system can **stay current with the model's evolving attention as it generates new reasoning steps**. This establishes dynamic updatability as a first-class requirement for any KV-cache method targeting generation-heavy workloads, effectively deprecating static-selection approaches for those scenarios.

Finally, the paper changes the **evaluation landscape** for KV-cache methods. Prior work often reported accuracy only on retrieval-centric benchmarks or at a single budget. IceCache demonstrates that the interesting scientific question is not "does method X achieve good accuracy?" but rather "**how does accuracy scale with budget, and how does this scaling vary across task types?**" The budget sweep (64, 128, 256 tokens in Table 1), the task-level breakdown across 16 diverse sub-tasks, and the explicit latency-accuracy tradeoff analysis (Figure 7b) collectively establish a higher standard for what constitutes a thorough KV-cache evaluation. Future papers that report only average accuracy at a single budget on a single benchmark will appear incomplete by comparison.

### Follow-Up Research This Work Enables

**1. Isolating the contribution of semantic page layout from the retrieval algorithm via a controlled ablation.** The most important open question in this paper is causal: how much of IceCache's gain over baselines is due to the semantic page layout (clustering tokens by key embedding similarity), and how much is due to the M-DCI retrieval algorithm? The paper compares IceCache against sequential-layout methods (ArkVale, Quest) but never tests M-DCI on sequential pages or a simpler retrieval algorithm on clustered pages. A clean 2×2 factorial experiment — {sequential layout, clustered layout} × {baseline retrieval, M-DCI retrieval} — would decompose the contributions. The prediction that IceCache's results suggest: clustered layout with ArkVale's simpler page-criticality estimator should significantly outperform sequential layout with M-DCI, establishing layout as the dominant factor. This experiment would directly validate (or challenge) the paper's central thesis and guide practitioners on whether the implementation complexity of M-DCI is necessary.

**2. Stress-testing IceCache on tasks with diffuse attention patterns.** IceCache's strongest results are on retrieval-centric tasks (Single-Doc QA, Multi-Doc QA, Summarization) where attention is highly sparse and concentrated on a few relevant passages. A critical gap is performance on tasks where attention is **diffuse** — where the model needs to attend broadly across the entire sequence rather than focus on a few tokens. Specific targets: machine translation (attention maps are typically dense across source-target alignments), long-form creative writing (where thematic coherence requires attending to distant but widely distributed context), and multi-turn dialogue (where turn-taking and conversational history create broad attention patterns). The key measurement would be accuracy retention relative to Full KV-cache as a function of attention entropy (higher entropy = more diffuse attention). If IceCache's retention drops from 99% on sparse-attention tasks to, say, 80% on diffuse-attention tasks, this would establish a boundary condition on when semantic clustering is appropriate and motivate hybrid strategies (e.g., larger page budgets or different clustering criteria for diffuse-attention layers).

**3. Scaling IceCache to 70B+ models to test whether semantic clustering degrades with embedding dimensionality.** The paper demonstrates IceCache on models up to 32B parameters (Qwen3-32B, Table 2), but the most acute KV-cache pressure in deployment occurs at 70B+ scales (Llama-3.1-70B, Mixtral 8×22B, DeepSeek-V2). Larger models have higher-dimensional key embeddings (typically 128 dimensions for 70B+ models vs. 128 for 8B models in Llama-3.1 — the dimensionality doesn't necessarily scale with parameters, but the number of heads does, increasing to 64 or more), which could affect clustering quality. The curse of dimensionality suggests that Euclidean-distance-based clustering becomes less meaningful in very high dimensions, potentially reducing the benefit of semantic page layout. A study on Llama-3.1-70B (or similar) measuring accuracy retention at IceCache's standard budgets (64, 128, 256) on LongBench would reveal whether the 99% retention holds at scale or degrades. If it holds, IceCache becomes a compelling solution for the compute tier where KV-cache memory is most problematic. If it degrades, the investigation would reveal why — is it embedding dimensionality, attention head count, or model-specific attention patterns? — and point toward mitigations (e.g., per-head dimensionality reduction before clustering, or different transformation functions `T_K`).

**4. Replacing the DCI-tree with alternative dynamic indices to reduce the CPU-search latency bottleneck.** Figure 7c reveals that the DCI-query accounts for 45.5% of per-token latency (0.05s out of 0.11s). This is the single largest bottleneck preventing IceCache from approaching eviction-method latencies. The semantic page layout principle is separable from the specific retrieval algorithm — any clustering method that groups similar tokens into pages would preserve the layout benefit. This opens a clear research direction: substitute the DCI-tree with faster dynamic indices and measure the latency-accuracy tradeoff. Candidates include: (a) flat k-means clustering with brute-force search within the top-`m` clusters (sacrificing hierarchical pruning for simpler, potentially GPU-acceleratable search); (b) HNSW (hierarchical navigable small world graphs), which provides logarithmic search complexity with state-of-the-art recall on high-dimensional ANN benchmarks; (c) product-quantization-based inverted file indices that compress key embeddings and enable fast approximate search with low memory overhead. The key metric would be TPOT vs. accuracy retention at a 256-token budget on Llama-3.1-8B, compared to IceCache's 0.11s at 99.0% and IceCache(reuse)'s 0.06s at 96.4% (Figure 7b, Tables 1 and 5). If HNSW, for example, achieves 98.5% retention at 0.05s TPOT, it would make IceCache-style semantic layout practical for latency-sensitive applications.

**5. Extending semantic clustering beyond per-head independence to cross-head sharing and multi-level representations.** IceCache builds separate DCI-trees for each attention head, which is principled (heads learn different patterns) but potentially wasteful — heads often exhibit redundancy, and maintaining hundreds of independent trees (32 layers × 8–64 KV heads) is expensive. A natural extension is to build **shared or partially-shared indices**: cluster heads by the similarity of their attention patterns (using a metric like centered kernel alignment on attention maps from a calibration dataset), build a DCI-tree per cluster rather than per head, and use the cluster's tree for all heads in the cluster. This would reduce indexing overhead and tree storage while preserving much of the head-specificity benefit. A stronger version: build a single multi-representation tree where each node stores not just one key embedding but a **set of projections** capturing different head-specific similarity notions, and queries traverse the tree using their head's specific projection. The experiment would measure accuracy retention as a function of the number of distinct trees (from 1 shared tree to full per-head trees), quantifying the redundancy in head-level attention patterns and establishing the optimal sharing granularity.

**6. Training-time integration: can models learn to produce key embeddings that are optimized for clustered retrieval?** All of IceCache's gains come from post-hoc organization of a pretrained model's key embeddings. A more ambitious direction: modify the **training objective** to encourage key embeddings that are naturally clusterable — e.g., by adding an auxiliary loss that rewards low intra-cluster variance and high inter-cluster separation in the key embedding space, or by incorporating the DCI-tree's page structure as an architectural constraint during training (similar to how sparse mixture-of-experts models route tokens to experts). The research question: can a model trained with a "clustering-friendly" key embedding structure achieve the same downstream accuracy as a standard model while requiring even smaller IceCache budgets? A proof-of-concept experiment would be to fine-tune a pretrained model with a contrastive loss on key embeddings (pulling together keys that receive high mutual attention, pushing apart keys that don't) and then measure IceCache's accuracy retention at a 32-token budget vs. the unmodified model. If the modified model achieves 95% retention at 32 tokens where the standard model achieves 80%, this establishes that **KV-cache efficiency can be a training-time objective**, not just an inference-time optimization — potentially changing how models are pretrained for deployment-constrained environments.

### Practical Applications and Downstream Use Cases

**Long-document processing on consumer GPUs.** A user with an NVIDIA RTX 4070 (12 GB VRAM) running Llama-3.1-8B-Instruct cannot process a 36k-token document with Full KV-cache — the model parameters (~16 GB in float16) plus KV-cache (~4.7 GB) plus activations would exceed available memory. IceCache with a 256-token budget reduces GPU KV-cache memory to the sink + window tokens (a few thousand tokens, ~0.3–0.5 GB) plus the selectively loaded pages (~0.1 GB for 256 tokens at 131 KB/token), bringing total GPU memory well under 12 GB. The accuracy cost is negligible: 99.0% retention on LongBench (Table 1) and perfect passkey retrieval across all context lengths (Figure 6). This enables local, private processing of long legal documents, academic papers, or technical manuals on consumer hardware — a use case currently restricted to cloud-hosted models with expensive high-memory GPUs.

**High-throughput batch inference for document QA at fixed latency budgets.** A document understanding service that answers questions over a corpus of 50k-token reports processes thousands of queries per hour. With Full KV-cache on A100 GPUs, each request's decoding latency grows with the number of concurrent requests (due to KV-cache memory contention), and the per-token latency at 36k tokens is ~200 ms (Figure 1). Switching to IceCache with the reuse variant (IceCache(r)) reduces GPU memory per request from ~3.5 GB to ~1 GB (Figure 1), allowing the system to serve 3–4× more concurrent requests per GPU while maintaining 96.4% accuracy (Table 5). Critically, the per-token latency drops to 0.06 seconds (Figure 7b) — a ~3.3× speedup over Full KV-cache — because the attention computation is now over a small fixed-size page set rather than the full 36k-token sequence. The throughput gain is multiplicative: more concurrent requests plus faster per-request decoding yields roughly an order-of-magnitude increase in queries served per GPU-hour.

**On-device chain-of-thought reasoning assistants.** A mobile coding assistant that performs multi-step reasoning about codebase changes generates long chain-of-thought traces (500–2000 tokens of reasoning per query). With eviction-based KV-cache methods (StreamingLLM, SnapKV), the assistant's reasoning accuracy degrades mid-generation as critical early reasoning steps are discarded — the paper shows eviction methods achieve only 44.4–44.7% on GSM8K CoT vs. Full KV-cache's 48.2% (Table 3). IceCache, with its incremental DCI-tree updates, maintains 47.4% accuracy — within 0.8 points of Full — because newly generated reasoning tokens are properly indexed and retrievable when later steps need them. This enables complex multi-step reasoning on memory-constrained edge devices (phones, laptops) where Full KV-cache is impossible and eviction-based methods would silently produce incorrect reasoning chains.

**Cost-efficient serving of large models at scale.** A cloud provider serving Qwen3-32B (a model whose parameters alone occupy ~64 GB in float16, requiring at minimum an H100 80GB GPU) processes requests with varying context lengths. IceCache with a 256-token budget reduces KV-cache memory by ~95–99% (from potentially tens of GB to a few hundred MB for the selectively loaded pages), enabling the model to run on a single H100 where Full KV-cache would require multiple GPUs or aggressive memory offloading. The accuracy retention is 99.3% (Table 2), meaning end-users perceive no quality degradation. For the provider, the cost savings are direct: serving on 1× H100 instead of 2× or more, with latency that scales sub-linearly with context length (Figure 8: IceCache's decode latency grows ~30% from 150k to 300k tokens vs. Full's ~110% growth). This makes large-model serving economically viable for long-context applications that would otherwise require prohibitive hardware.
