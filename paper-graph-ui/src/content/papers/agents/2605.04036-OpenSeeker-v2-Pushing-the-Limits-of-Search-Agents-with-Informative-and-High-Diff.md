# OpenSeeker-v2: Pushing the Limits of Search Agents with Informative and High-Difficulty Trajectories

**ArXiv:** [2605.04036](https://arxiv.org/abs/2605.04036)

## 🎯 Pitch

A tiny 10.6k dataset of ultra-hard search problems lets a 30B model beat industry giants that used massive multi-stage training. By simply expanding knowledge graphs and filtering out easy questions, SFT alone achieves state-of-the-art on deep-search benchmarks.

---

## 1. Executive Summary

This report introduces **OpenSeeker-v2**, a search agent trained via a simple supervised fine-tuning (SFT) approach that rivals agents built with far heavier multi-stage pipelines. Using a 30B-parameter model evaluated on BrowseComp, BrowseComp-ZH, Humanity's Last Exam, and xbench, the paper demonstrates that three data-synthesis modifications — **scaling graph size for richer exploration** (expanding the knowledge graph from $k$ to $K$ nodes to mandate multi-hop reasoning), **expanding the tool set for broader functionality** (increasing available tools to encourage diverse interaction patterns), and **strict low-step filtering** (discarding trajectories solvable in fewer than $T_{\text{min}}$ tool calls to enforce a minimum difficulty floor) — produce a condensed 10.6k-example dataset that is surprisingly powerful. OpenSeeker-v2 achieves state-of-the-art performance among ~30B ReAct-based agents — 46.0% on BrowseComp, 58.1% on BrowseComp-ZH, 34.6% on Humanity's Last Exam, and 78.0% on xbench — decisively outperforming Tongyi DeepResearch (trained with CPT+SFT+RL, achieving 43.4%, 46.7%, 32.9%, and 75.0% respectively) and RedSearcher (also CPT+SFT+RL), establishing that data quality — specifically, high-difficulty, information-rich trajectories averaging 64.67 tool calls — can substitute for multi-stage industrial training pipelines when the goal is long-horizon search and reasoning.

## 2. Context and Motivation

### The Core Problem: Search Agent Development Is Gated Behind Industrial-Scale Compute

The fundamental tension this paper addresses is straightforward: **frontier search agents are increasingly essential, yet their development has become structurally inaccessible to academic and open-source teams.** A "search agent" here refers to an LLM-based system that can autonomously navigate the web, retrieve information, synthesize evidence across multiple sources, and answer complex questions that require multi-step reasoning — the kind of task epitomized by benchmarks like BrowseComp (Wei et al., 2025) and Humanity's Last Exam (Phan et al., 2025). These capabilities are no longer optional; as the paper states in its opening line:

> "In the era of information explosion, deep search has emerged as a non-negotiable competency for frontier Large Language Model (LLM) agents"

The gap is not that academic teams lack insight into how to build these agents. The gap is that the dominant industrial recipe — which the paper characterizes as "highly resource-intensive" — creates an economic barrier that excludes most research groups. This recipe, as practiced by organizations like Alibaba Tongyi Lab (Team et al., 2025b) and RedNote (Chu et al., 2026), typically involves:

1. **Continual Pre-Training (CPT)** on massive corpora of web interaction data, which requires orchestrating large-scale crawling, rendering, and data processing pipelines.
2. **Supervised Fine-Tuning (SFT)** on curated demonstration trajectories, which itself requires generating high-quality agent behavior at scale.
3. **Reinforcement Learning (RL)** stages that further optimize agent behavior through reward signals, which introduces additional infrastructure for reward modeling, online sampling, and policy optimization.

Each of these stages compounds the compute, data, and engineering requirements. The result, as the paper frames it, is that "the development of these high-performance agents has long remained a 'closed-door game' played almost exclusively by well-funded corporate entities." This is not merely an academic complaint — it has real consequences for the field. When only a handful of industrial labs can build and study frontier search agents, progress is bottlenecked by the research priorities of those labs, and the scientific community loses the ability to independently verify, critique, and improve upon the state of the art.

### Why This Problem Matters: Beyond Academic Access

The inaccessibility of search agent development matters for several reasons that go beyond "fairness" arguments:

**Reproducibility and scientific rigor.** When the dominant approach involves multi-stage pipelines with proprietary data and undisclosed hyperparameters, it becomes impossible for independent researchers to determine *which components* of the pipeline are actually responsible for performance gains. Is CPT essential, or could the same data be absorbed during SFT? Does RL add capabilities that SFT cannot, or does it mainly correct for deficiencies in the SFT data distribution? The industrial reports that exist (Team et al., 2025b; Chu et al., 2026) describe their pipelines in broad strokes but do not provide the controlled ablations needed to answer these questions. This creates a situation where the community must either trust the industrial recipe or invest enormous resources to replicate it — neither of which is scientifically healthy.

**Democratization of deployment.** Search agents are not just research artifacts; they have direct practical applications in information retrieval, research assistance, and decision support. If the only viable path to building competent search agents requires industrial-scale infrastructure, then the deployment of these systems will remain concentrated in the hands of large corporations, with implications for who controls access to sophisticated information-seeking tools.

**The data-centric hypothesis.** The paper's core bet is that **data quality matters more than training pipeline complexity** for search agents. This is a specific, testable hypothesis that challenges the prevailing industrial wisdom. If true, it would redirect research attention away from ever-more-complex multi-stage training recipes and toward the problem of how to *construct* high-quality training data for search agents — a problem that is fundamentally more accessible to academic labs, since it requires creativity and careful methodology rather than raw compute. This reframing has analogs in other areas of AI: the insight that carefully curated demonstration data can outperform massive but noisy datasets has been demonstrated in instruction tuning (Zhou et al., 2023; Gunasekar et al., 2023), but it had not been systematically validated for long-horizon search agents prior to this work.

### Prior Approaches and Where They Fall Short

The paper positions itself against a specific landscape of comparable systems, which is detailed in Table 1. Understanding the limitations of these prior approaches is essential to understanding what OpenSeeker-v2 contributes.

#### The Industrial Heavyweight Approach: Tongyi DeepResearch and RedSearcher

**Tongyi DeepResearch** (Team et al., 2025b) represents the canonical industrial pipeline. Developed by Alibaba's Tongyi Lab, it is a ~30B-parameter ReAct-based search agent trained with CPT + SFT + RL. On the benchmarks that overlap with OpenSeeker-v2's evaluation, it achieves 43.4% on BrowseComp, 46.7% on BrowseComp-ZH, 32.9% on Humanity's Last Exam, and 75.0% on xbench. These are strong numbers — strong enough that the paper treats them as the primary baseline to beat — but they come at a cost that is not publicly quantified. The CPT stage alone likely requires training on hundreds of billions of tokens of web interaction data, which demands infrastructure for large-scale web crawling and rendering. The RL stage adds further complexity: it requires defining a reward function for search agent behavior, which is non-trivial because the quality of a search trajectory depends on both the final answer *and* the efficiency and correctness of the intermediate steps.

The key limitation of this approach — from the perspective of the OpenSeeker-v2 authors — is not that it fails to work, but that it is **structurally unreproducible** by academic teams. The ingredients are individually feasible (CPT, SFT, and RL are well-understood techniques), but the scale and integration required make the full pipeline prohibitive without industrial resources. Moreover, because the components are not cleanly ablated in the Tongyi DeepResearch report, it is impossible to know whether all three stages are necessary or whether some could be eliminated without performance loss.

**RedSearcher** (Chu et al., 2026) follows a similar template: CPT + SFT + RL, targeting a ~30B scale, with a focus on long-horizon search. It achieves 42.1% on BrowseComp, 49.8% on BrowseComp-ZH, and 34.3% on HLE — numbers that are close to Tongyi DeepResearch and, in some cases, slightly ahead. The same structural limitation applies: the training pipeline is resource-intensive and not easily reproducible by external teams. A notable detail from Figure 2: RedSearcher's training data has an average of **36.01 tool calls per trajectory**, compared to OpenSeeker-v1's 46.97 and OpenSeeker-v2's 64.67. This suggests that RedSearcher's data synthesis pipeline produces substantially shorter, less complex trajectories than the OpenSeeker family, which may partially explain why their CPT+SFT+RL pipeline underperforms OpenSeeker-v2's SFT-only approach — the complexity of the training data itself may matter more than the complexity of the training procedure.

#### The Data-Quality Predecessor: OpenSeeker-v1

**OpenSeeker-v1** (Du et al., 2026) is the direct precursor to OpenSeeker-v2, developed by the same academic team. It was the first attempt to build a competent search agent using only SFT, trained on 11.7k examples synthesized from a knowledge graph. On BrowseComp, it achieved 29.5%; on BrowseComp-ZH, 48.4%; on xbench, 74.0%. These numbers were respectable but clearly behind the industrial heavyweights — Tongyi DeepResearch's 43.4% on BrowseComp represented a 13.9 percentage point gap, which is enormous on a benchmark where the state-of-the-art at the time was in the low 50s.

The gap between OpenSeeker-v1 and the industrial baselines was precisely what motivated the current paper. The question became: *why* did OpenSeeker-v1 fall short? The possibilities included: (1) SFT is inherently insufficient and RL is necessary to achieve frontier performance, (2) the training data quantity was too small (11.7k examples vs. the presumably much larger industrial datasets), or (3) the training data *quality* was insufficient — the trajectories weren't difficult or information-rich enough to teach the model robust search skills. This paper's central contribution is providing evidence that the answer is primarily (3), with some role for (2).

OpenSeeker-v1's data synthesis pipeline had specific limitations that OpenSeeker-v2 directly addresses:

- **The knowledge graph expansion was limited to $k$ nodes**, which constrained the topological diversity of synthetic queries. If the subgraph around a seed node is small, the only questions that can be generated are those answerable from a few sources, which biases the dataset toward simpler, shallower reasoning.
- **The tool set was smaller**, which restricted the range of search behaviors the agent could learn. If the agent only has access to, say, a basic web search tool, it never learns to use specialized tools (e.g., for structured data extraction, for cross-referencing, for language-specific search) that might be optimal for certain queries.
- **No explicit difficulty filter was applied**, so the dataset included trajectories that could be solved in very few steps — potentially a large fraction of the data, since simpler queries are easier to synthesize and more commonly appear when expanding from a limited subgraph.

These limitations meant that OpenSeeker-v1's training data, while functional, was not optimized for inducing the specific capability that distinguishes frontier search agents: the ability to sustain long, multi-hop search trajectories where evidence must be aggregated across many sources.

#### Other SFT-Based and RL-Based Attempts

The paper also positions itself against **WebSailor-V2** (Li et al., 2025) and **WebLeaper**, both ~30B-scale agents. WebSailor-V2 exists in both SFT-only (24.4% BrowseComp) and SFT+RL (35.3% BrowseComp) variants — a useful within-study comparison that shows RL providing an 10.9 percentage point boost. This suggests that RL *can* improve performance substantially when the SFT baseline is relatively weak, which makes OpenSeeker-v2's result (46.0% with SFT only) all the more striking: it achieves better performance than WebSailor-V2's RL variant *without using RL at all*. This implies that the RL gains observed in WebSailor-V2 may have been compensating for deficiencies in the SFT data distribution — deficiencies that OpenSeeker-v2's improved data synthesis avoids.

**WebLeaper** shows a similar pattern: SFT-only at 27.7% BrowseComp, improving to 38.8% with RL. Again, the RL boost is substantial (~11 percentage points), but the RL result still falls well short of OpenSeeker-v2's SFT-only result.

These comparisons are important because they establish a clear pattern: prior SFT-only search agents consistently scored in the 24–30% range on BrowseComp, and RL was necessary to push beyond that ceiling. OpenSeeker-v2 breaks this pattern: it reaches 46.0% with SFT alone, exceeding not only all prior SFT-only agents but also the RL-enhanced versions of those agents, and even exceeding the CPT+SFT+RL industrial pipelines. This is a discontinuous improvement that demands explanation — and the paper's explanation is that the data synthesis modifications (scaling graph size, expanding tools, strict low-step filtering) transform the SFT data from "adequate" to "sufficiently difficult and information-rich."

### How OpenSeeker-v2 Positions Itself

The paper's positioning can be understood along three axes:

**Axis 1: Methodological minimalism as a deliberate choice.** Unlike papers that introduce new training algorithms or architectural innovations, OpenSeeker-v2's methodology section (Section 2.1) is strikingly simple: three modifications to the data synthesis pipeline, followed by standard SFT. There is no RL, no CPT, no novel loss function, no architectural modification. This minimalism is strategic — it isolates the *data* as the causal factor. If OpenSeeker-v2 had introduced a new training algorithm alongside data improvements, it would be impossible to attribute the performance gains. By keeping the training method constant (standard SFT, identical to OpenSeeker-v1) and varying only the data synthesis, the paper makes its central claim cleanly testable.

**Axis 2: Data quality over data quantity.** The paper deliberately works with a *smaller* dataset than OpenSeeker-v1 (10.6k vs. 11.7k examples) and achieves dramatically better performance. This is perhaps the most counterintuitive aspect of the result: dropping 1.1k examples while making the remaining ones more difficult and information-rich yields a ~16.5 percentage point improvement on BrowseComp. The message is that the *distribution* of training trajectories matters more than the *count*, and specifically that the presence of easy trajectories may actively harm performance by crowding out learning signals for difficult search behavior. This is consistent with findings in other domains (e.g., the "textbook quality" hypothesis in language model pre-training; Gunasekar et al., 2023), but had not been demonstrated for search agents.

**Axis 3: The academic-to-industrial bridge.** The paper explicitly identifies OpenSeeker-v2 as "the first state-of-the-art search agent within its model scale and paradigm (ReAct) to be developed entirely by a purely academic team using only SFT." This is not just a bragging point — it's a proof of existence. By demonstrating that SOTA-level search agents *can* be built with academic resources, the paper lowers the barrier to entry for the entire field and creates a reproducible baseline that other teams can build on, modify, and improve. The open-sourcing of model weights (via Hugging Face) and code (via GitHub) reinforces this positioning: unlike the industrial baselines, OpenSeeker-v2 is designed to be studied, replicated, and extended.

Importantly, the paper does *not* claim that SFT is universally superior to CPT+SFT+RL. It acknowledges the performance of closed-source proprietary models (Claude-4-Opus, GPT-5-High, OpenAI Deep Research) that achieve even higher scores (48–55% on BrowseComp) using paradigms and scales beyond OpenSeeker-v2's scope. The claim is more specific: *within the ReAct paradigm at ~30B scale*, SFT with high-quality data can match or exceed CPT+SFT+RL. Whether RL or CPT would further improve OpenSeeker-v2 is an open question the paper leaves for future work — the point is that they are not *necessary* to reach the current frontier.

### The Unstated Assumption: Trajectory Difficulty as a Proxy for Learned Capability

Underlying the paper's approach is an important assumption that is worth making explicit: **the difficulty of the training trajectories determines the difficulty of the problems the agent can solve at test time.** This is not trivially true. It's possible that training on very difficult trajectories could lead to the model learning spurious patterns (e.g., always making many tool calls even when few would suffice) or could make the training signal too sparse for effective SFT. The paper's results suggest that, at least for the architectures and data scales studied, these failure modes do not dominate: the model generalizes from high-difficulty training trajectories to high-difficulty test problems without overfitting to trajectory length or tool-call patterns. Figure 2 provides indirect evidence for this: the substantially higher average tool-call count in OpenSeeker-v2's training data (64.67 vs. 36.01 for RedSearcher and 46.97 for OpenSeeker-v1) correlates with better benchmark performance, but the performance gains are on *accuracy*, not on simply producing longer trajectories — the model learns to search effectively, not just to search for a long time.

This assumption connects to a broader question in the LLM agent literature that the paper engages implicitly: **what is the limiting factor for agent performance at a given model scale?** Is it the model's underlying reasoning capability (which might require pre-training scale), the model's instruction-following and tool-use skills (which might require RL to optimize for complex reward signals), or the model's exposure to sufficiently complex demonstrations during training (which requires only better data synthesis)? The paper's results argue for the third answer, at least for the ReAct paradigm at 30B scale. This is a significant empirical finding because it suggests that the capacity for sophisticated search behavior is already latent in models like Qwen3-30B-A3B-Thinking-2507 — it just needs to be elicited through the right training data, not created through additional training stages.

## 3. Technical Approach

### 3.1 Reader Orientation

OpenSeeker-v2 is a **data synthesis and training pipeline** that produces a search agent — an LLM that can autonomously navigate the web, invoke tools, and answer complex multi-hop questions — through a single supervised fine-tuning (SFT) stage rather than the multi-stage industrial pipelines (continual pre-training + SFT + reinforcement learning) that currently dominate the field. The system solves the problem of **inaccessible frontier search agent development** by demonstrating that training data quality — specifically, the difficulty and informational richness of synthetic search trajectories — matters more than training pipeline complexity; the "shape" of the solution is a set of three simple modifications to an existing trajectory synthesis pipeline that, together, produce a condensed 10.6k-example dataset whose difficulty distribution forces the model to learn sustained, long-horizon search behavior during a standard SFT run.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has four major components arranged in a pipeline:

1. **Knowledge Graph Expansion Engine**: Takes a base knowledge graph $\mathcal{G} = (V, E)$ and a seed node $v_{\text{seed}}$, expands outward to a subgraph $\mathcal{G}_{\text{sub}}^{(K)}$ of size $K$ (where $K > k$, the expansion budget used in the predecessor OpenSeeker-v1). This enlarged subgraph provides the raw informational substrate from which complex questions are generated.

2. **Question-Trajectory Synthesizer**: Conditions on the expanded subgraph to generate a synthetic question $q$ that inherently requires evidence aggregation across multiple nodes (because the subgraph is topologically rich), then simulates a ReAct-style trajectory $\tau$ — a sequence of reasoning steps, tool calls (drawn from an expanded tool set $\mathcal{A}$), tool observations, and a final answer — that solves the question. Each trajectory consists of $T$ tool-call steps.

3. **Difficulty Filter**: Examines each synthesized trajectory and discards any where $T < T_{\text{min}}$ (a predefined minimum tool-call threshold). Trajectories that survive this filter are, by construction, impossible to solve through shallow keyword matching or single-source lookup — they enforce a minimum horizon of search and reasoning.

4. **Standard SFT Trainer**: Takes the filtered dataset $\mathcal{D}_{\text{v2}}$ (10.6k examples of $(q, \tau)$ pairs) and performs standard next-token prediction fine-tuning on a base LLM (Qwen3-30B-A3B-Thinking-2507), producing the final OpenSeeker-v2 agent. There is no RL stage, no continual pre-training, and no architectural modification.

Information flows linearly: base knowledge graph → expanded subgraph → synthetic question + ReAct trajectory → difficulty filter → SFT training → deployable agent. The key insight is that the difficulty filter and the graph/tool expansions are not post-hoc optimizations but *integral design choices* that shape the distribution of the training data to be fundamentally different from the distribution that would arise from naive synthesis.

### 3.3 Roadmap for the Deep Dive

- **First**, the knowledge graph expansion mechanism (scaling from $k$ to $K$), since it is the upstream modification that determines the complexity of the questions that can be generated and why naive expansion would produce disproportionately simple queries.
- **Second**, the expanded tool set, because tool diversity and graph richness interact: a richer graph enables more complex questions, but the agent can only learn to solve them if it has the tools to navigate that complexity.
- **Third**, the strict low-step filtering rule, which is the linchpin that enforces the minimum difficulty floor and is the most counterintuitive design choice (since it *reduces* dataset size).
- **Fourth**, the ReAct trajectory structure and SFT training procedure, since these are the "consumer" of the synthesized data and define what the agent actually learns.
- **Fifth**, the synthesis pipeline end-to-end, walking through a concrete example to show how the components interact and what makes the resulting trajectories "informative and high-difficulty."

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily an **empirical systems paper** whose core idea is that three data synthesis modifications — scaling graph size, expanding tools, strict low-step filtering — can transform an SFT-only training pipeline from producing mediocre search agents (OpenSeeker-v1 at 29.5% BrowseComp) to producing state-of-the-art ones (OpenSeeker-v2 at 46.0% BrowseComp) that surpass industrial CPT+SFT+RL pipelines, without any change to the training algorithm or model architecture.

#### Knowledge Graph Expansion: Scaling from $k$ to $K$

**What the knowledge graph is and why it matters.** The data synthesis pipeline begins with a structured knowledge graph $\mathcal{G} = (V, E)$, where $V$ is a set of nodes representing entities or information sources (e.g., Wikipedia articles, web pages, structured data entries) and $E$ is a set of edges representing relationships between those entities (e.g., hyperlinks, citations, semantic connections). This graph is not the training data itself — it is the *generative substrate* from which training questions are synthesized. The critical property of the graph is that its topology constrains what kinds of questions *can* be generated: if the subgraph around a seed node is small and shallow, the only questions that can be synthesized are those answerable from a few closely related sources, which biases the dataset toward simple, single-hop or shallow multi-hop queries.

**How expansion works.** For each seed node $v_{\text{seed}}$ in the graph, the pipeline constructs a local subgraph $\mathcal{G}_{\text{sub}}$ by expanding outward from $v_{\text{seed}}$ following graph edges. In OpenSeeker-v1, this expansion used a budget of $k$ nodes. In OpenSeeker-v2, the budget is increased to $K$, where $K > k$. The paper formalizes this as:

$$\mathcal{G}_{\text{sub}}^{(K)} = \text{Expand}(\mathcal{G}, v_{\text{seed}}, K)$$

where $\mathcal{G}$ is the full knowledge graph, $v_{\text{seed}}$ is the starting seed node, $K$ is the expansion budget (the target size of the subgraph in number of nodes), and $\mathcal{G}_{\text{sub}}^{(K)}$ is the resulting expanded subgraph containing $K$ nodes reachable from $v_{\text{seed}}$.

**What it computes:** the Expand function starts from $v_{\text{seed}}$, follows edges outward in a breadth-first or similar traversal, and accumulates nodes until $K$ nodes have been visited. The resulting subgraph $\mathcal{G}_{\text{sub}}^{(K)}$ contains $v_{\text{seed}}$ plus $K-1$ additional nodes that are topologically related through varying numbers of hops. Crucially, the enlarged subgraph includes nodes at greater topological distance from the seed — in a graph with high branching factor, reaching $K$ nodes may require traversing many hops, which means the subgraph contains evidence chains of length proportional to the graph diameter within that neighborhood. This is operationally important because the question generator (described next) conditions on this subgraph to produce questions; a larger subgraph enables questions that require evidence aggregation across many nodes.

**Why $K > k$ matters.** The expansion budget is not merely a quantity knob — it is a *structural* parameter that changes the qualitative nature of feasible synthetic questions. Consider the difference:

- With a small budget $k$, the subgraph around a typical seed node might contain only the seed's immediate neighbors and perhaps their neighbors. A question generator conditioned on this subgraph is constrained to ask questions that can be answered from, say, 2–3 sources that are all directly connected to the seed. These questions tend to be shallow: "What is the capital of the country that $v_{\text{seed}}$ is located in?" — a two-hop question that can be answered by looking up $v_{\text{seed}}$, finding its country, and looking up the country's capital.

- With a large budget $K$, the subgraph extends much further, encompassing nodes at 4, 5, or more hops from the seed. The question generator can now synthesize questions like: "What scientific discovery, made by a researcher who studied at the same institution as the discoverer of $v_{\text{seed}}$, was later applied in a field pioneered by a third researcher who won the same award as the first?" This question requires aggregating evidence across a chain of 5+ nodes, many of which are only connected through intermediate entities. Such a question is structurally impossible to generate from a small subgraph, because the relevant nodes simply wouldn't be present.

The paper does not specify exact values for $k$ and $K$, but the effect is visible in the outcome: OpenSeeker-v2's training trajectories average **64.67 tool calls**, compared to 46.97 for OpenSeeker-v1 and 36.01 for RedSearcher (Figure 2). This 37.7% increase over OpenSeeker-v1 cannot come from the tool set expansion or filtering alone — it reflects the fact that the underlying questions are structurally more complex, requiring more search steps to resolve because the evidence is distributed across more nodes with more complex interconnections.

**Why this scaling approach rather than alternatives.** The paper could have attempted to increase trajectory difficulty through other means — for example, by designing a more sophisticated question generator that produces complex questions even from small subgraphs, or by post-hoc editing of questions to increase complexity. The graph-expansion approach has a key advantage: it guarantees that the complexity is *intrinsic* to the information topology rather than being an artifact of contrived question phrasing. When a question requires evidence from many topologically distant nodes, the agent genuinely *must* perform multi-hop search to answer it — there is no shortcut. This makes the resulting trajectories more natural training signals for the kind of sustained, branching search behavior that benchmarks like BrowseComp demand.

**A subtle but important point:** the expanded subgraph is used *only* for question generation, not for trajectory generation. The question $q$ is synthesized conditioned on $\mathcal{G}_{\text{sub}}^{(K)}$, meaning the question's answer is verifiable from the information in the subgraph. But when the trajectory $\tau$ is generated, the agent does *not* have direct access to $\mathcal{G}_{\text{sub}}^{(K)}$ — it must discover the relevant information through tool calls (web search, etc.). This separation is critical: it ensures the training data teaches the agent to *find* information through search, not to simply read it from a provided context. The subgraph serves as the "ground truth" information space that the agent must explore, but the exploration itself is unscripted — the trajectory is generated by actually invoking tools and recording the observations.

#### Question Generation Conditioned on the Expanded Subgraph

Once the expanded subgraph $\mathcal{G}_{\text{sub}}^{(K)}$ is constructed, a question generator — likely an LLM prompted for this purpose, though the paper does not specify the generator's architecture — produces a synthetic question $q$ conditioned on the subgraph's content and structure:

$$q \sim \mathcal{P}_{\text{gen}}\left(q \mid \mathcal{G}_{\text{sub}}^{(K)}\right)$$

where $\mathcal{P}_{\text{gen}}$ is the question-generation distribution, $\mathcal{G}_{\text{sub}}^{(K)}$ is the expanded subgraph of $K$ nodes, and $q$ is the generated question.

**What it computes:** the generator takes the set of $K$ nodes and their interconnecting edges as context, identifies chains, clusters, or patterns of relationships that span multiple nodes, and formulates a natural-language question whose answer requires synthesizing information from several nodes in the subgraph. The generator is incentivized (through prompting) to produce questions that cannot be answered from any single node, which is naturally enforced when $K$ is large: if the subgraph contains many nodes with diverse relationships, a question that uses only one or two nodes is an under-utilization of the available context, and a well-prompted generator will instead produce questions that aggregate across the structure.

**Why condition on the subgraph rather than generating questions freely.** An alternative approach would be to generate questions first and then construct a knowledge graph to support them. The paper's approach reverses this: the information structure comes first, and the question is derived from it. This ensures two properties: (1) the question is *guaranteed* to be answerable, because the information exists in the subgraph, and (2) the question's difficulty is *directly controlled* by the subgraph's topological complexity. If the subgraph requires 5-hop traversal to connect the relevant evidence, the generated question will naturally reflect that complexity. This is a form of "difficulty by construction" that is more reliable than post-hoc difficulty estimation.

**The interaction with graph expansion.** The key insight is not that the question generator is novel — it likely follows standard LLM-based question generation techniques — but that scaling $K$ changes the *input distribution* to the generator. With a small $K$, the generator sees a sparse, shallow information space and produces questions that require limited evidence aggregation. With a large $K$, the generator sees a rich, deep information space and naturally produces questions that require multi-hop aggregation. The question generation process itself doesn't change; the *conditions under which it operates* change, and that changes the output distribution in a way that is structurally aligned with the target benchmark difficulty.

#### Expanding the Tool Set for Broader Functionality

**What tools are and why they matter for search agents.** A search agent operates in a ReAct paradigm: at each step, it produces a reasoning trace $r_t$, selects a tool $a_t$ from a predefined set $\mathcal{A}$, receives an observation $o_t$ from that tool, and uses the observation to inform its next reasoning step. The tool set $\mathcal{A}$ defines the *action space* of the agent — what it can *do* in the environment. If $\mathcal{A}$ is small and homogeneous (e.g., only a generic web search tool), the agent is forced to use the same action pattern for all queries, regardless of what strategy would be optimal. If $\mathcal{A}$ is larger and more diverse, the agent can learn to *select* tools strategically based on the query type and the current state of information.

In OpenSeeker-v2, the tool set $\mathcal{A}$ is expanded relative to OpenSeeker-v1, following the tool set design of Team et al. (2026). The paper does not enumerate the exact tools, but in typical search agent implementations, an expanded tool set might include:

- **General web search**: query-based retrieval from a search engine, returning snippets and URLs.
- **Targeted page fetching**: retrieving the full content of a specific URL.
- **Structured data extraction**: parsing tables, lists, or knowledge panels from web pages.
- **Cross-referencing tools**: finding pages that link to or cite a given source.
- **Language-specific search**: searching in a particular language (relevant for BrowseComp-ZH, the Chinese variant).
- **Entity resolution tools**: disambiguating between entities with similar names.
- **Temporal filtering**: restricting search to specific date ranges.
- **Domain-specific search**: searching within particular websites or domains.

The critical design principle is that the tool set should cover the *range of search strategies* that an expert human searcher might employ. A narrow tool set forces the agent to simulate diverse strategies through prompt engineering (e.g., "search for X but pretend you're using a specialized tool"), which is fragile and unlikely to generalize. A broad tool set allows the agent to learn when each tool is appropriate as part of the SFT process.

**How the expanded tool set interacts with trajectory generation.** When the ReAct trajectory $\tau$ is synthesized, each action $a_t$ is selected from the expanded tool set $\mathcal{A}$:

$$\tau = (r_1, a_1, o_1, r_2, a_2, o_2, \ldots, r_T, a_T, o_T, r_{T+1}, y)$$

where $r_t$ is the reasoning trace before the $t$-th action, $a_t \in \mathcal{A}$ is the tool call selected from the expanded set, $o_t$ is the observation returned by that tool, $r_{T+1}$ is the final reasoning step, and $y$ is the answer.

**What this notation means operationally.** At step $t$, the agent (or the trajectory synthesizer, during data generation) thinks about what it knows so far and what it needs to find out — this thinking is $r_t$. It then chooses a specific tool $a_t$ from the available set and invokes it. The tool returns some information — a search result, a page content, a structured data extract — which is $o_t$. The agent then reasons about this new information ($r_{t+1}$) and decides on the next tool call. This loop repeats $T$ times until the agent has enough information to produce a final answer $y$, preceded by a final reasoning trace $r_{T+1}$ explaining how the accumulated evidence supports the answer.

**Why expanding the tool set produces better training data.** The benefit is twofold:

1. **Diverse strategy learning**: When the agent sees trajectories that use different tools for different situations — e.g., using entity resolution to disambiguate before searching, using page fetching to drill down into a specific source, using cross-referencing to verify claims — it learns a *conditional policy* over actions. The SFT objective trains the model to predict $a_t$ given the history $(r_1, a_1, o_1, \ldots, r_t)$, so the distribution of $a_t$ in the training data directly shapes what the model learns to do. An expanded tool set means the training data contains a richer conditional distribution, and the model learns more nuanced tool-selection behavior.

2. **Complementarity with graph expansion**: The expanded knowledge graph produces questions that require diverse evidence-gathering strategies — some evidence might be in structured tables (requiring extraction tools), some in long-form articles (requiring page fetching), some across multiple languages (requiring language-specific search). If the tool set were narrow, the trajectory synthesizer would be forced to use a generic tool for all of these, producing uniform trajectories that don't teach the model to adapt its strategy. The expanded tool set allows the trajectory to *reflect* the information-finding strategy that is actually appropriate for the question's structure, making the training signal more informative.

**The paper's deliberate minimalism in tool expansion.** The paper does not claim to have designed a novel tool set — it explicitly states that it expands the tool set "following Team et al. (2026)." This is consistent with the paper's overall thesis: the innovations are in *data synthesis*, not in tool design or model architecture. The tool set expansion is included because it is a necessary enabler for the primary innovation (high-difficulty trajectories): given a complex question from an expanded graph, the agent needs adequate tools to solve it. Without the tool expansion, the graph expansion would produce questions that the agent *cannot* effectively solve within the ReAct paradigm, and the trajectories would be low-quality.

#### Strict Low-Step Filtering: Enforcing a Minimum Difficulty Floor

**The problem this addresses.** Without explicit filtering, a data synthesis pipeline that generates questions from knowledge graphs will produce a mixture of simple and complex trajectories. Simple trajectories — those solvable in 1–3 tool calls — can arise even with large $K$ if the generator happens to produce a question focused on a small cluster within the subgraph, or if a multi-hop question can be shortcut by a lucky initial search. These simple trajectories are problematic for SFT training because they provide a "gradient signal of least resistance": the model can achieve low loss by learning to answer questions quickly with minimal search, which is exactly the *opposite* of the sustained search behavior needed for benchmarks like BrowseComp. If easy trajectories constitute a significant fraction of the training data, the SFT objective will prioritize fitting them (since they're easier to predict) at the expense of learning the more complex search patterns that appear in longer trajectories.

**The filtering rule.** OpenSeeker-v2 applies a strict, deterministic filter based on trajectory length:

$$\mathcal{D}_{\text{v2}} = \{(q, \tau) \in \mathcal{D}_{\text{raw}} \mid T(\tau) \geq T_{\text{min}}\}$$

where $\mathcal{D}_{\text{raw}}$ is the unfiltered set of synthesized (question, trajectory) pairs, $T(\tau)$ is the number of tool-call steps in trajectory $\tau$, $T_{\text{min}}$ is the minimum acceptable number of tool calls, and $\mathcal{D}_{\text{v2}}$ is the filtered dataset used for SFT training.

**What this computes operationally.** For each synthesized trajectory, the system counts the number of tool-call steps $T$. If $T < T_{\text{min}}$, the entire (question, trajectory) pair is discarded. If $T \geq T_{\text{min}}$, the pair is retained. The filter is applied *after* trajectory generation, meaning trajectories are synthesized normally and then pruned post-hoc. The paper does not specify the exact value of $T_{\text{min}}$, but the average trajectory length of 64.67 tool calls in the final dataset (Figure 2) implies that $T_{\text{min}}$ is substantial — likely in the range of 20–40 tool calls, given that the average is pulled up by some very long trajectories. This means that a large fraction of synthesized trajectories are discarded: OpenSeeker-v2's final dataset has 10.6k examples, which is *fewer* than OpenSeeker-v1's 11.7k, despite starting from a more expansive synthesis process that could have generated more total trajectories.

**Why this form rather than alternatives.** Several alternative approaches to ensuring training difficulty were available:

- **Soft weighting**: Instead of hard-filtering, assign higher training weights to longer trajectories. This would allow simple trajectories to still contribute to training, but with reduced influence. The paper rejects this implicitly by choosing hard filtering, likely because soft weighting still allows the model to see easy examples and potentially overfit to the "shortcut" behavior they represent. Hard filtering guarantees the model *never* sees easy trajectories during training, which forces it to develop long-horizon search skills to reduce loss on *any* training example.

- **Difficulty-conditioned generation**: Instead of filtering post-hoc, condition the question generator to produce only difficult questions. This is harder to implement reliably — it's easier to generate questions and filter them than to guarantee difficulty at generation time. The post-hoc filter is also more transparent: $T_{\text{min}}$ provides a clean, interpretable threshold.

- **Curriculum learning**: Start with easy trajectories and progressively increase difficulty. The paper rejects this by training on only difficult trajectories from the start. This is a bet that the base model (Qwen3-30B-A3B-Thinking-2507) already has sufficient fundamental capabilities (language understanding, basic search, instruction following) that it can learn directly from difficult trajectories without a warm-up phase. The success of the approach validates this bet.

- **RL-based difficulty optimization**: Use RL to reward longer or more complex trajectories. This is exactly the industrial approach the paper is challenging. The filtering approach achieves a similar effect (skewing the data distribution toward difficulty) without any RL infrastructure.

**The counterintuitive aspect: less data can be better.** The filtering step reduces the dataset size — from whatever $\mathcal{D}_{\text{raw}}$ was (potentially 20k, 30k, or more examples, given the expanded synthesis process) down to 10.6k. In most machine learning contexts, reducing training data is harmful. Here, it is beneficial because the examples being removed are *actively harmful* — they teach the model a behavior pattern (shallow search) that is directly opposed to the target behavior (deep search). This is a specific instance of a broader principle: when the training distribution and the target distribution differ in a systematic way, training on *fewer but more representative* examples can outperform training on *more but less representative* examples. The filtering step aligns $\mathcal{D}_{\text{v2}}$ with the distribution of benchmark problems, which are designed to require deep search.

**The interaction with SFT.** SFT minimizes the negative log-likelihood of the training trajectories given the questions. If the training data contains many short trajectories, the model learns that the most likely action sequence for a given question is a short one — it internalizes a prior for brevity. The strict low-step filter removes this prior: every trajectory the model sees during training is long, so the model never learns that short trajectories are likely. At inference time, when faced with a genuinely hard question, the model has no learned tendency to terminate search early — it has only seen examples where sustained search was necessary, so it naturally continues searching until evidence is gathered.

#### The ReAct Trajectory Structure and SFT Training

**What a ReAct trajectory looks like.** The paper adopts the ReAct paradigm (Reasoning + Acting), where the agent interleaves reasoning traces with tool calls. A single trajectory has the form:

$$\tau = (r_1, a_1, o_1, r_2, a_2, o_2, \ldots, r_T, a_T, o_T, r_{T+1}, y)$$

**Component-by-component walkthrough:**

- $r_1$ is the initial reasoning: the agent reads the question $q$, thinks about what information it needs, and formulates an initial search strategy. For example: *"To answer this question about the relationship between X and Y, I first need to find basic information about X. Let me search for X."*

- $a_1$ is the first tool call, selected from the expanded tool set $\mathcal{A}$. The tool call includes a specific query or parameterization. For example: `search("X scientific discovery 2023")`.

- $o_1$ is the observation returned by the tool — search result snippets, a page content, etc. This observation is inserted into the agent's context as new information.

- $r_2$ is the second reasoning step: the agent reads $o_1$, integrates it with what it already knows, identifies what's still missing, and decides on the next action. For example: *"The search results mention that X was discovered by Researcher A at Institution B. I now need to find what other discoveries came from Institution B. Let me search for the institution."*

- This pattern repeats $T$ times. Each step adds to the agent's accumulated knowledge, and the reasoning traces show the agent's evolving understanding of the problem and its information-seeking strategy.

- $r_{T+1}$ is the final reasoning step: the agent reviews all accumulated evidence, synthesizes it, and formulates the answer.

- $y$ is the final answer, extracted from the evidence gathered across the trajectory.

**How trajectories are synthesized.** The paper does not detail the exact trajectory synthesis procedure, but the standard approach in this literature is:

1. Given the question $q$ and the knowledge that the answer exists in the expanded subgraph $\mathcal{G}_{\text{sub}}^{(K)}$, use a strong LLM (possibly the same base model or a more capable one) to simulate the ReAct loop.
2. At each step, the LLM generates a reasoning trace and a tool call. The tool is actually executed against a search environment (web search API, knowledge graph lookup, etc.) to produce a genuine observation.
3. The process continues until the LLM determines it has sufficient information and produces an answer.
4. The trajectory is recorded as the full sequence of reasoning, actions, and observations.

This produces *realistic* trajectories because the observations are genuine — they come from actual tool executions, not from hallucinated content. This matters for SFT: if the model were trained on trajectories with hallucinated observations, it would learn to expect information patterns that don't exist in real tool outputs, leading to poor generalization.

**The SFT training objective.** Once the filtered dataset $\mathcal{D}_{\text{v2}}$ is assembled, the model is trained with standard next-token prediction:

$$\mathcal{L}_{\text{SFT}} = -\sum_{(q, \tau) \in \mathcal{D}_{\text{v2}}} \log P_\theta(\tau \mid q)$$

where $\theta$ are the model parameters (initialized from Qwen3-30B-A3B-Thinking-2507), $q$ is the question, $\tau$ is the full trajectory including reasoning traces, tool calls, observations, and answer, and $P_\theta(\tau \mid q)$ is the model's autoregressive probability of generating the trajectory tokens conditioned on the question tokens.

**What it computes:** for each training example, the model receives the question as input and is trained to predict every subsequent token in the trajectory — reasoning traces, tool calls, observations, and the final answer. The loss is the sum of negative log-probabilities of each token given all previous tokens. The model learns to: (1) produce appropriate reasoning traces given the question and accumulated context, (2) select the right tool and formulate the right queries, (3) interpret tool observations, and (4) synthesize a final answer from accumulated evidence.

**Why this form — and why standard SFT is sufficient.** The SFT objective treats the entire search process as a sequence prediction problem. There is no separate loss for "was the tool call appropriate" or "was the final answer correct" — the model simply learns to imitate the trajectories in the training data. This works because the trajectories are *demonstrations of expert behavior* (synthesized by a capable LLM with access to genuine tool outputs). The model learns the *policy* — what to do in each state — by observing what the expert did.

The paper's key claim is that this SFT objective is *sufficient* to reach frontier performance when the training trajectories are difficult enough. The intuition is that difficult trajectories contain rich information about search strategy: when the expert takes 64 steps to solve a problem, each step encodes a decision about what to search for next given the current state of knowledge. Training on many such trajectories teaches the model a generalizable search policy. In contrast, easy trajectories (3–5 steps) contain much less strategic information per example — the decisions are simpler, and the model can fit them without learning deep search skills.

**Implementation details.** The paper states that OpenSeeker-v2 is instantiated from **Qwen3-30B-A3B-Thinking-2507**, which has **30B total parameters and 3B activated parameters during inference** (a Mixture-of-Experts architecture). The agent uses a **256k context window** and allows **up to 200 tool calls per trajectory**. Training is described as "standard SFT" without additional hyperparameter details — the paper's emphasis is on the data, not the training recipe, so the implicit claim is that standard SFT hyperparameters (learning rate, batch size, epochs) were used without special tuning. This is consistent with the paper's thesis: if the data is high-quality, the training procedure doesn't need to be exotic.

**The base model choice.** Qwen3-30B-A3B-Thinking-2507 is a model specifically designed for reasoning tasks (the "Thinking" designation indicates it was trained with chain-of-thought data). This is important context: the base model already has strong reasoning capabilities before SFT. The SFT stage does not *create* reasoning ability from scratch — it *specializes* the existing reasoning ability for the search agent task. This may explain why difficult trajectories are effective: the base model already understands how to reason, and the SFT data teaches it *what to reason about* in a search context and *how to translate reasoning into search actions*. If the base model lacked reasoning capability, difficult trajectories might be incomprehensible and SFT might fail.

#### End-to-End Synthesis Pipeline Walkthrough

To make the interaction of components concrete, here is how a single training example is produced:

1. **Select seed node**: The system picks a node $v_{\text{seed}}$ from the knowledge graph $\mathcal{G}$ — perhaps a Wikipedia article about a scientific concept, a historical event, or a cultural artifact.

2. **Expand subgraph**: The Expand function traverses outward from $v_{\text{seed}}$ following edges (hyperlinks, semantic relations, citation links) until $K$ nodes have been accumulated. For a well-connected seed, this might reach nodes 5–8 hops away. The resulting subgraph $\mathcal{G}_{\text{sub}}^{(K)}$ contains a diverse set of entities and relationships.

3. **Generate question**: The question generator $\mathcal{P}_{\text{gen}}$ is given $\mathcal{G}_{\text{sub}}^{(K)}$ and prompted to produce a question whose answer requires information from multiple nodes. The generator identifies an interesting chain or cluster — perhaps a chain of influence connecting three researchers across different institutions and time periods — and formulates a question: "What technique, pioneered by the doctoral advisor of the scientist who discovered X, was later independently rediscovered by a team that included a former student of Y?" This question structurally requires tracing the academic genealogy of two researchers and finding the intersection of their intellectual lineages.

4. **Simulate trajectory**: Starting from this question, the trajectory synthesizer (a capable LLM) enters the ReAct loop. It reasons about what to search for, calls tools from $\mathcal{A}$, receives observations, and continues. Because the question is complex, the trajectory is long — perhaps 78 tool calls involving entity resolution of researcher names, targeted searches for their academic affiliations, page fetching for biography pages, cross-referencing to verify connections, and finally synthesis of the answer.

5. **Apply filter**: The system checks $T(\tau) = 78$. Since $78 \geq T_{\text{min}}$, the trajectory passes the filter and is added to $\mathcal{D}_{\text{v2}}$.

6. **Train**: During SFT, the model sees the question and learns to predict the entire 78-step trajectory. Through thousands of such examples, it internalizes the pattern: complex questions require sustained, multi-step search with strategic tool selection.

**Why the trajectories are "informative and high-difficulty."** The title of the paper uses these terms deliberately:

- **High-difficulty**: Enforced by the combination of graph expansion (structural complexity) and low-step filtering (removing any trajectories that don't require sustained search). The average of 64.67 tool calls is a direct quantitative measure of this difficulty.

- **Informative**: Each step in a long trajectory carries information about search strategy — what to search for given what you already know, which tool to use, how to interpret partial results, when to change direction. A 64-step trajectory contains 64 decision points, each teaching the model something about effective search behavior. The expanded tool set makes these decisions more informative because the model sees *diverse* strategic choices, not just repeated use of the same tool.

#### Summary of Design Choices and Their Justifications

- **Graph expansion ($k \to K$)** over prompt-based or post-hoc difficulty manipulation: guarantees difficulty is intrinsic to the information topology, not an artifact of question phrasing; ensures questions structurally require multi-hop evidence aggregation.

- **Tool set expansion** over narrow tool sets: enables trajectories to reflect diverse search strategies appropriate to different question types; prevents the model from learning a single, undifferentiated search pattern; follows established tool set design (Team et al., 2026) to avoid confounding the data-centric thesis with tool innovation.

- **Strict low-step filtering** over soft weighting or curriculum learning: provides a hard guarantee that the model never sees easy trajectories during training; eliminates the "shortcut" learning signal that would bias the model toward premature search termination; reduces dataset size but improves dataset *alignment* with target benchmark difficulty.

- **Standard SFT** over CPT+SFT+RL: isolates data quality as the causal factor; demonstrates that multi-stage training is not *necessary* for frontier performance in this regime; provides a reproducible, low-resource baseline for the academic community; the choice is strategic, not claimed to be universally optimal.

- **Qwen3-30B-A3B-Thinking-2507 base model**: provides strong reasoning capabilities that can be specialized through SFT; the MoE architecture (3B activated out of 30B total) enables efficient inference with long trajectories; the "Thinking" variant's chain-of-thought pre-training aligns with the ReAct reasoning requirement.

## 4. Key Insights and Innovations

### Innovation 1: Data Quality Over Training Pipeline Complexity — A Proof of Concept at the Frontier

The paper's most fundamental contribution is not a new algorithm, architecture, or training method, but an **empirical refutation of a prevailing assumption**: that frontier search agent performance requires multi-stage industrial training pipelines (CPT + SFT + RL). OpenSeeker-v2 demonstrates that a single SFT stage, when fed the right data, achieves 46.0% on BrowseComp — decisively surpassing Tongyi DeepResearch (43.4%) and RedSearcher (42.1%), both trained with CPT+SFT+RL at comparable model scale. This is not an incremental improvement over prior SFT-only agents; it is a **discontinuous jump** from the previous SFT ceiling of ~29.5% (OpenSeeker-v1) to a level that exceeds even RL-enhanced variants like WebSailor-V2-RL (35.3%) and WebLeaper-RL (38.8%).

What makes this intellectually distinctive is the **deliberate minimalism of the claim**. The paper does not argue that SFT is universally superior to RL or CPT. It argues something more precise and falsifiable: *within the ReAct paradigm at ~30B scale, on these benchmarks, the dominant factor differentiating mediocre from frontier performance is training data difficulty and richness, not training pipeline sophistication.* This is a specific, testable hypothesis that challenges the implicit assumption driving the industrial approach — that each additional training stage (CPT, RL) adds capabilities that SFT alone cannot provide. The paper's evidence suggests that these stages may have been compensating for deficiencies in SFT data distribution rather than providing fundamentally new capabilities.

The significance extends beyond the raw numbers. By demonstrating that a purely academic team using only SFT can achieve SOTA within this paradigm, the paper **changes the economics of search agent research**. It provides a reproducible baseline (open-sourced model weights, documented methodology) that eliminates the "you need industrial compute to play" barrier. This is a **structural contribution** to the field's research ecosystem, not merely a performance contribution.

The evidence is anchored in Table 1, where OpenSeeker-v2's SFT-only results sit above every CPT+SFT+RL baseline in the ~30B category. The comparison against OpenSeeker-v1 (29.5% → 46.0% on BrowseComp with *fewer* training examples: 10.6k vs. 11.7k) further isolates data quality as the causal factor, since the training algorithm, base model, and model scale are held constant. This within-family comparison is methodologically stronger than cross-system comparisons because it controls for all variables except the data synthesis modifications.

### Innovation 2: Difficulty-by-Construction — A Structural Alternative to Difficulty-by-Compensation

Prior approaches to building search agents implicitly treated difficulty as something to be *compensated for* through training pipeline complexity. The industrial recipe — CPT to expose the model to diverse web interactions, SFT to demonstrate correct behavior, RL to optimize for reward — can be understood as a sequence of increasingly sophisticated compensations: if SFT data isn't diverse enough, add CPT; if SFT behavior isn't optimal enough, add RL. Difficulty enters only at evaluation time, as a property of the benchmark, not as a *design parameter* of the training data.

OpenSeeker-v2 inverts this logic. It introduces **difficulty-by-construction**: the training data's complexity is engineered directly into the data synthesis pipeline through three interdependent design choices that together produce trajectories whose difficulty is a structural consequence of the information topology, not a post-hoc label or a reward signal. The three modifications — scaling graph size, expanding tools, low-step filtering — function as a **coherent difficulty-engineering stack** rather than independent optimizations.

The intellectual move is to treat difficulty as a **generative constraint** rather than an evaluation metric. By expanding the knowledge graph from $k$ to $K$ nodes, the system *structurally mandates* multi-hop reasoning: the question generator, conditioned on a topologically rich subgraph, cannot produce simple single-source questions because the subgraph's structure doesn't support them (or at least makes them unnatural). By expanding the tool set, the system ensures that the *strategy space* for solving these structurally complex questions is appropriately diverse — a question requiring structured data extraction and cross-referencing will actually generate trajectories that use those tools, rather than awkwardly simulating them through generic search. By applying strict low-step filtering, the system provides a **hard guarantee**: the model never sees a training trajectory solvable in fewer than $T_{\text{min}}$ steps, which eliminates the "shortcut" learning signal that would otherwise bias the model toward premature search termination.

This is fundamentally different from curriculum learning (where difficulty increases over training) or RL-based difficulty optimization (where difficulty is a reward signal). In those paradigms, difficulty is a *scalar* that modulates an existing training process. In OpenSeeker-v2, difficulty is a *structural property* of each training example, engineered through the relationship between the knowledge graph topology, the tool set expressiveness, and the filtering threshold. The resulting trajectories average 64.67 tool calls (Figure 2) — not because the system was told to generate long trajectories, but because the information required to answer the questions is distributed across many topologically distant nodes, and reaching those nodes genuinely requires that many search steps.

The evidence is in the before-and-after comparison with OpenSeeker-v1: same training algorithm, same base model, but the difficulty-engineering stack produces trajectories averaging 64.67 steps (vs. 46.97) and BrowseComp performance of 46.0% (vs. 29.5%). The increase in trajectory length is not an independent goal — it is a *symptom* of the increased structural complexity of the questions, and the improved benchmark performance is evidence that the model successfully learned from this complexity rather than being overwhelmed by it.

### Innovation 3: The Counter-Doctrine of "Less Data, Better Data"

A deeply counterintuitive finding that emerges from this work is that **reducing training dataset size can improve performance** when the removed data teaches behaviors misaligned with the target task distribution. OpenSeeker-v2 uses 10.6k training examples, compared to OpenSeeker-v1's 11.7k, yet substantially outperforms it. This is not a trivial consequence of the filtering step — it is evidence for a specific hypothesis about what makes SFT effective for search agents.

The standard assumption in SFT is that more demonstration data is better, modulo diminishing returns. The implicit model is that each training example provides a positive learning signal, and while some examples may be more informative than others, they all pull the model toward the target behavior. OpenSeeker-v2's results challenge this model for the specific case of search agent training. The strict low-step filter removes trajectories that are *actively harmful* — not merely less informative, but teaching the model a behavior pattern (shallow, rapid search) that is directly opposed to the desired behavior (sustained, multi-step search). An easy trajectory teaches the model: *"When you see a question, try to answer it in 2–3 steps."* A hard trajectory teaches: *"When you see a question, keep searching until you've gathered evidence from multiple sources."* These are contradictory lessons, and if easy trajectories constitute a significant fraction of the training data, the SFT objective — which minimizes average negative log-likelihood across all examples — will split the difference, producing a model that sometimes searches deeply and sometimes gives up early, depending on which training examples happen to dominate the gradient at a given point.

This connects to a broader principle that the paper demonstrates but does not fully theorize: **SFT with a mixed-difficulty dataset produces a model whose behavior is the average of the behaviors in the dataset, not the maximum.** If you want a model that always searches deeply, you must train it on data where deep search is the *only* behavior it sees. This is a specific instance of a distribution-matching problem: the training data distribution over trajectory lengths must match the target inference distribution. If the target is "solve hard problems requiring deep search," the training data must consist exclusively of deep-search trajectories.

The evidence for this interpretation comes from the dramatic performance gap between OpenSeeker-v1 (no explicit filtering, 46.97 average steps, 29.5% BrowseComp) and OpenSeeker-v2 (strict filtering, 64.67 average steps, 46.0% BrowseComp). The 17.7-step increase in average trajectory length is not just a correlation — it's a *causal consequence* of removing short trajectories, which pulls the mean upward. But the key insight is that this upward pull on the training distribution produces an upward pull on the model's *behavior* at test time. The ~11.1 percentage point gap between OpenSeeker-v2 and the next-best SFT-only agent (WebLeaper-30B-SFT at 27.7% BrowseComp, also with 15k examples) suggests that the filtering effect is not a small optimization but a dominant factor.

### Innovation 4: The Trajectory Length as a Proxy for Training Signal Richness

The paper introduces an implicit but powerful diagnostic concept: **average trajectory length in the training data is a meaningful proxy for the information richness of the SFT signal**, and this proxy predicts downstream benchmark performance better than dataset size alone. This is visible in Figure 2, which compares the tool-call distributions of RedSearcher (avg 36.01 steps), OpenSeeker-v1 (avg 46.97 steps), and OpenSeeker-v2 (avg 64.67 steps) — and the corresponding benchmark performance (RedSearcher at 42.1%, OpenSeeker-v1 at 29.5%, OpenSeeker-v2 at 46.0% on BrowseComp) tracks this ordering (with the caveat that RedSearcher uses a heavier training pipeline, making the comparison not purely about data).

The intellectual contribution here is not the observation that longer trajectories correlate with better performance — that could be a spurious correlation. The contribution is the **causal interpretation** embedded in the paper's methodology: longer trajectories are better *because* they contain more decision points per training example. A 64-step trajectory contains 64 instances of "given the current state of knowledge, what should I search for next?" — each of which is a training signal for the model's search policy. A 3-step trajectory contains only 3 such instances. Training on 10,000 long trajectories provides roughly an order of magnitude more strategic decision examples than training on 30,000 short trajectories (300,000 decisions vs. 90,000, in this simplified calculation). This reframes the data efficiency question: **what matters is not the number of trajectories, but the total number of search decisions demonstrated, weighted by their diversity.**

This insight also explains why the tool set expansion is synergistic with graph expansion and filtering. A long trajectory where the agent uses the same tool 64 times provides 64 decision points, but they are all essentially the same decision ("should I search again? yes."). A long trajectory where the agent switches between entity resolution, targeted page fetching, structured data extraction, and cross-referencing provides 64 *diverse* decision points, teaching the model a conditional policy over a richer action space. The expanded tool set makes each decision point more informative, multiplying the effective training signal beyond what trajectory length alone would provide.

This framing has implications beyond search agents. It suggests that for any sequential decision-making task trained via SFT, the quality of training data should be measured not in *episodes* but in *decision diversity × decision count* — a metric that combines trajectory length (decisions per episode) with action space diversity (information per decision). The paper doesn't develop this metric formally, but the success of the approach provides strong suggestive evidence for its validity.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** Four benchmarks are used, all publicly available: **BrowseComp** (Wei et al., 2025), a challenging English-language browsing benchmark requiring complex multi-hop web search and evidence synthesis; **BrowseComp-ZH** (Zhou et al., 2025), the Chinese-language variant of BrowseComp; **Humanity's Last Exam** (HLE) (Phan et al., 2025), a dataset of extremely difficult questions spanning diverse academic and technical domains designed to probe the limits of current AI systems; and **xbench-DeepSearch** (Xbench-Team, 2025), a benchmark for deep research tasks. The paper masks hugging-face-related links when calling web search tools during evaluation to "avoid potential leakage," suggesting that some answers may be directly retrievable from Hugging Face pages if not masked. No dataset sizes or splits are specified in the paper.

- **Base model.** The agent is instantiated from **Qwen3-30B-A3B-Thinking-2507** (Team, 2025), a Mixture-of-Experts (MoE) model with 30B total parameters and 3B activated parameters during inference. This model was chosen because its "Thinking" designation indicates pre-training on chain-of-thought reasoning data, providing a strong reasoning foundation that can be specialized for search agent behavior through SFT. The MoE architecture enables efficient inference when generating long trajectories (up to 200 tool calls) with a 256k context window.

- **Metrics.** The primary metric is **benchmark accuracy** — the fraction of questions for which the agent's final answer matches the ground truth. This is computed independently for each of the four benchmarks (BrowseComp, BrowseComp-ZH, HLE, xbench). No details are provided about answer grading procedures (e.g., exact match vs. fuzzy matching), though BrowseComp typically uses exact-match evaluation against known answers derived from the questions' construction.

- **Baselines.** The paper compares OpenSeeker-v2 against three categories of systems from Table 1:
  - **~30B ReAct-based search agents trained with heavier pipelines**: Tongyi DeepResearch (Team et al., 2025b) trained with CPT+SFT+RL (43.4% BrowseComp, 46.7% BrowseComp-ZH, 32.9% HLE, 75.0% xbench); RedSearcher-30B (Chu et al., 2026) trained with CPT+SFT+RL (42.1% BrowseComp, 49.8% BrowseComp-ZH, 34.3% HLE); WebSailor-V2-30B-SFT (24.4% BrowseComp, 28.3% BrowseComp-ZH, 23.9% HLE, 61.7% xbench) and its RL variant WebSailor-V2-30B-RL (35.3%, 44.1%, 30.6%, 73.7%); WebLeaper-30B-SFT (27.7% BrowseComp, 66.0% xbench) and its RL variant WebLeaper-30B-RL (38.8% BrowseComp, 72.0% xbench).
  - **Larger open-source models**: DeepSeek-V3.1-671B (30.0%, 49.2%, 29.8%, 71.2%), DeepSeek-V3.2-671B (51.4%, 65.0%, 40.8%), GLM-4.6-357B (45.1%, 49.5%, 30.4%), GLM-4.7-357B (52.0%, 66.6%, 42.8%), Minimax-M2-230B (44.0%, 48.5%).
  - **Closed-source proprietary models**: Claude-4-Opus (18.8%, 37.4%), Claude-4.5-Sonnet (24.1%, 42.4%, 32.0%), Gemini-3-pro (37.8%, 66.8%, 45.8%), OpenAI-o3 (49.1%, 68.7%, 20.2%, 65.0%), OpenAI Deep Research (51.5%, 42.9%, 26.6%), GPT-5-High (54.9%, 63.0%, 41.7%).
  - **The direct predecessor**: OpenSeeker-v1-30B-SFT (Du et al., 2026) at 29.5% BrowseComp, 48.4% BrowseComp-ZH, 74.0% xbench, trained with SFT on 11.7k examples.

- **Training budget and infrastructure.** OpenSeeker-v2 is trained with **standard SFT** using 10.6k (question, trajectory) pairs. No details are provided about the number of epochs, learning rate, batch size, optimizer, or hardware used for training. The paper's emphasis is on data quality, with the implicit claim that standard SFT hyperparameters (not specially tuned) are sufficient. The training budget is therefore measured in **number of training examples** (10.6k) rather than FLOPs, GPU-hours, or tokens, and is deliberately smaller than OpenSeeker-v1's 11.7k examples to demonstrate that data quality outweighs quantity. At inference time, the agent operates with a 256k context window, up to 200 tool calls per trajectory, and 3B activated parameters per forward pass.

- **Cross-validation / statistical protocol.** **None reported.** The paper does not describe any cross-validation, train/test splits within the benchmark data, multiple training runs with different seeds, or statistical significance testing. All results in Table 1 appear to be single-run evaluations on the standard benchmark test sets. The comparison against baseline systems relies on numbers reported in their respective technical reports or public leaderboards, with no independent re-evaluation under controlled conditions. This is a meaningful limitation: without error bars or multiple runs, it is impossible to determine whether the 2.6% gap between OpenSeeker-v2 (46.0%) and Tongyi DeepResearch (43.4%) on BrowseComp is statistically reliable or within the range of run-to-run variance.

### Main Quantitative Results

The paper's experimental results are organized around a single, unified comparison (Table 1) that positions OpenSeeker-v2 against a comprehensive landscape of prior systems. There are no separate axes of investigation — no ablations over $K$, $T_{\text{min}}$, or tool set configurations — because the paper's thesis is that the *combined* data synthesis modifications produce a dataset that enables SFT-only training to match or exceed heavier pipelines. The results are therefore best understood by examining the comparisons at each tier of the baseline hierarchy.

#### Head-to-Head Against Comparable-Scale Industrial Pipelines

The central empirical claim is that OpenSeeker-v2, trained with SFT only, **outperforms all ~30B ReAct-based search agents trained with heavier CPT+SFT+RL pipelines** across all four benchmarks. The specific numbers from Table 1:

**On BrowseComp (English browsing):**
- OpenSeeker-v2: **46.0%**
- Tongyi DeepResearch (CPT+SFT+RL): 43.4% — a **2.6 percentage point** advantage
- RedSearcher-30B (CPT+SFT+RL): 42.1% — a **3.9 percentage point** advantage
- WebSailor-V2-30B-RL (SFT+RL): 35.3% — a **10.7 percentage point** advantage
- WebLeaper-30B-RL (RL): 38.8% — a **7.2 percentage point** advantage

The gap is most dramatic against the SFT-only variants of these systems: WebSailor-V2-SFT at 24.4% (21.6 point gap) and WebLeaper-SFT at 27.7% (18.3 point gap). This reinforces the paper's thesis that prior SFT-only approaches were limited by data quality, not by the SFT training paradigm itself. The 2.6 point margin over Tongyi DeepResearch is modest in absolute terms but meaningful given that Tongyi represents the canonical industrial heavyweight approach — it uses all three training stages (CPT, SFT, RL) and likely substantially more training data than OpenSeeker-v2's 10.6k examples.

**On BrowseComp-ZH (Chinese browsing):**
- OpenSeeker-v2: **58.1%**
- Tongyi DeepResearch: 46.7% — an **11.4 percentage point** advantage
- RedSearcher-30B: 49.8% — an **8.3 percentage point** advantage

The BrowseComp-ZH gap is substantially larger than the English BrowseComp gap. This is a notable pattern that the paper does not discuss: OpenSeeker-v2's relative advantage appears stronger on the Chinese benchmark. Several explanations are possible: (1) the base model (Qwen3, developed by Alibaba's Qwen team) may have stronger Chinese-language capabilities than the base models used by Tongyi or RedSearcher; (2) the data synthesis pipeline's knowledge graph may have denser Chinese-language coverage, producing higher-quality Chinese trajectories; (3) the expanded tool set may provide more leverage for Chinese-language search, where language-specific tools are particularly important for disambiguation and source quality. Without ablations or additional analysis, the cause cannot be determined, but the pattern is consistent enough to note.

**On Humanity's Last Exam (HLE):**
- OpenSeeker-v2: **34.6%**
- Tongyi DeepResearch: 32.9% — a **1.7 percentage point** advantage
- RedSearcher-30B: 34.3% — a **0.3 percentage point** advantage

The HLE results show the narrowest margins. HLE is designed to be extremely difficult, probing the absolute limits of AI capabilities with questions spanning advanced mathematics, specialized scientific knowledge, and complex reasoning. The fact that all three systems (OpenSeeker-v2, Tongyi, RedSearcher) cluster within 1.7 points of each other at ~33–35% suggests a potential **ceiling effect**: on problems near the frontier of what 30B-scale models can solve, the training paradigm (SFT vs. CPT+SFT+RL) may matter less than the base model's fundamental reasoning capability, which is roughly equivalent across these systems since they all start from strong 30B-class base models. This is consistent with the paper's implicit thesis: CPT and RL provide diminishing returns when the base model's capability and the SFT data quality are both high.

**On xbench-DeepSearch:**
- OpenSeeker-v2: **78.0%**
- Tongyi DeepResearch: 75.0% — a **3.0 percentage point** advantage
- WebSailor-V2-30B-RL: 73.7%
- WebLeaper-30B-RL: 72.0%

The xbench results show a more compressed range (72–78%) than BrowseComp, suggesting xbench may be an easier benchmark with less discriminating power among frontier systems. The 3.0 point gap over Tongyi is consistent with the pattern on BrowseComp.

#### Comparison Against Larger Open-Source Models

OpenSeeker-v2 also **outperforms several models with substantially more parameters** (Table 1):

- **DeepSeek-V3.1-671B** (671B parameters, 22× larger than OpenSeeker-v2's 30B total): OpenSeeker-v2 leads by 16.0 points on BrowseComp (46.0% vs. 30.0%), 8.9 points on BrowseComp-ZH (58.1% vs. 49.2%), 4.8 points on HLE (34.6% vs. 29.8%), and 6.8 points on xbench (78.0% vs. 71.2%).
- **GLM-4.6-357B** (357B parameters): OpenSeeker-v2 leads by 0.9 points on BrowseComp (46.0% vs. 45.1%), 8.6 points on BrowseComp-ZH (58.1% vs. 49.5%), and 4.2 points on HLE (34.6% vs. 30.4%).
- **Minimax-M2-230B** (230B parameters): OpenSeeker-v2 leads by 2.0 points on BrowseComp (46.0% vs. 44.0%) and 9.6 points on BrowseComp-ZH (58.1% vs. 48.5%).

These comparisons are striking but must be interpreted carefully. The larger models (DeepSeek-V3.1, GLM-4.6, Minimax-M2) are general-purpose LLMs evaluated on search benchmarks, not specialized search agents. They likely do not use the ReAct paradigm with explicit tool-call training, and their BrowseComp performance may reflect their ability to answer questions from pre-training knowledge rather than from live web search. This makes the comparison a test of **specialization vs. scale**: a 30B model specifically fine-tuned for search can substantially outperform a general-purpose model with 20× more parameters on search-specific benchmarks. This is not surprising — it is the expected outcome when a smaller model is fine-tuned on task-specific data — but the magnitude of the gap (16 points on BrowseComp against a 671B model) is noteworthy.

**Models that OpenSeeker-v2 does NOT surpass** include more recent or more heavily optimized large models: DeepSeek-V3.2-671B (51.4% BrowseComp, 5.4 points ahead), GLM-4.7-357B (52.0% BrowseComp, 6.0 points ahead), and the closed-source frontier models like GPT-5-High (54.9% BrowseComp, 8.9 points ahead) and OpenAI Deep Research (51.5% BrowseComp, 5.5 points ahead). This establishes an upper bound: SFT-trained search agents at 30B scale have not yet closed the gap to the absolute frontier, which may require either scale, more sophisticated training, or paradigms beyond ReAct.

#### Within-Family Comparison: OpenSeeker-v1 vs. OpenSeeker-v2

The comparison between OpenSeeker-v1 and OpenSeeker-v2 is the most methodologically controlled result in the paper because it holds the training algorithm (SFT), base model (Qwen3-30B-A3B-Thinking-2507), model scale, and broad data synthesis approach constant, varying only the three data modifications:

- BrowseComp: **29.5% → 46.0%** (+16.5 percentage points, a 55.9% relative improvement)
- BrowseComp-ZH: **48.4% → 58.1%** (+9.7 percentage points)
- xbench: **74.0% → 78.0%** (+4.0 percentage points)

Crucially, this improvement occurs despite OpenSeeker-v2 using **fewer** training examples than OpenSeeker-v1 (10.6k vs. 11.7k), which is the strongest evidence for the paper's data-quality-over-data-quantity thesis. If dataset size were the dominant factor, we would expect OpenSeeker-v2 to perform worse. The fact that it performs dramatically better with less data implies that the *removed* examples (those filtered out by the low-step criterion and possibly those superseded by higher-quality graph-expanded examples) were actively harmful, and the *remaining* examples are substantially more effective training signals.

The differential improvement across benchmarks is informative:

- The largest gain is on BrowseComp (+16.5 points), which is the benchmark most directly testing deep multi-hop search — exactly the capability that the data synthesis modifications target.
- The gain on BrowseComp-ZH is smaller (+9.7 points), possibly because OpenSeeker-v1 was already relatively strong on Chinese-language search (48.4%), leaving less headroom for improvement.
- The gain on xbench is smallest (+4.0 points), consistent with xbench being a less discriminating benchmark where even OpenSeeker-v1 achieved 74.0% — there is simply a ceiling on how much improvement is possible.

#### Trajectory Length as a Diagnostic (Figure 2)

Figure 2 provides the only ablation-adjacent evidence in the paper: a comparison of the **tool-call count distributions** in the training data of RedSearcher, OpenSeeker-v1, and OpenSeeker-v2. The key statistics:

- **RedSearcher**: average 36.01 tool calls per trajectory
- **OpenSeeker-v1**: average 46.97 tool calls per trajectory
- **OpenSeeker-v2**: average 64.67 tool calls per trajectory

The distribution shift is visually dramatic in Figure 2: RedSearcher's distribution is concentrated at relatively low tool-call counts, OpenSeeker-v1's is shifted rightward, and OpenSeeker-v2's is shifted further rightward with a heavier tail extending beyond 150 tool calls. This figure serves as the paper's primary evidence that the three data modifications actually produced the intended effect — training data that is structurally more complex and requires longer search trajectories.

The paper draws a causal inference from this correlation:

> "We hypothesize that such long and difficult synthetic trajectories are crucial for enabling the model to acquire stronger long-horizon retrieval and search capabilities, which further explains the superior performance of OpenSeeker-v2 on challenging deep-research benchmarks."

This hypothesis is consistent with the pattern in Table 1 (longer average training trajectories → better BrowseComp performance across the three systems), but the inference is confounded by the fact that RedSearcher uses a different training pipeline (CPT+SFT+RL), a different base model, and a different data synthesis approach. The within-family comparison (OpenSeeker-v1 vs. v2) partially deconfounds this by holding training algorithm and base model constant, and the +16.5 point BrowseComp gain correlates with a +17.7 step average trajectory length increase. However, the gain could also be attributed to other differences between v1 and v2 that are not captured by average trajectory length — for example, the expanded tool set may improve trajectory *diversity* independently of trajectory *length*, and the graph expansion may improve question *novelty* (reducing train-test overlap) independently of question *complexity*. Without controlled ablations that vary one factor at a time, the causal attribution to trajectory length specifically remains suggestive rather than demonstrated.

### Ablation Studies and Robustness Checks

**No formal ablations are reported.** This is the most significant methodological gap in the paper. The three data synthesis modifications — scaling graph size ($k \to K$), expanding the tool set, and strict low-step filtering ($T \geq T_{\text{min}}$) — are introduced as a package, and their effects are never isolated. We do not know:

- **What is the individual contribution of graph expansion?** Would training on trajectories from a $k$-node subgraph but with the expanded tool set and low-step filtering already produce most of the gain? Or is graph expansion the critical factor?
- **What is the individual contribution of tool set expansion?** Could the same graph-expanded questions be solved effectively with the original, narrower tool set, and would training on those trajectories still improve BrowseComp performance?
- **What is the individual contribution of low-step filtering?** If we trained on the unfiltered set of trajectories from the graph-expanded, tool-expanded pipeline (which would presumably be larger than 10.6k examples), how much performance would be lost? This is the most interesting ablation because it would directly test the "easy trajectories are harmful" hypothesis — if adding easy trajectories *reduces* performance, that is strong evidence for the distribution-matching interpretation; if adding easy trajectories has no effect or slightly improves performance, then the filtering step is incidental and the gains come entirely from graph/tool expansion.
- **What is the sensitivity to $T_{\text{min}}$?** The paper doesn't disclose the value of $T_{\text{min}}$, nor does it show performance as a function of different filtering thresholds. Does performance improve monotonically with $T_{\text{min}}$, or is there an optimal threshold beyond which further filtering removes too much data and harms performance?
- **What is the sensitivity to $K$ (the expansion budget)?** How much larger is $K$ relative to $k$? Does performance improve monotonically with $K$, or are there diminishing returns?
- **What is the sensitivity to dataset size?** OpenSeeker-v2 uses 10.6k examples. What would happen with 5k, 20k, or 50k examples from the same synthesis pipeline? Is 10.6k near the saturation point, or would more data from this pipeline yield further gains?

The absence of these ablations is not necessarily a flaw in the *results* — the paper demonstrates a clear overall improvement — but it limits the *scientific value* of the contribution. Without knowing which of the three modifications is responsible for how much of the gain, other researchers cannot prioritize their efforts when replicating or extending the approach. The paper's title emphasizes "informative and high-difficulty trajectories," but we cannot determine whether "informative" (tool diversity, graph richness) or "high-difficulty" (trajectory length, filtering) is the more important axis, or whether both are necessary and neither is sufficient alone.

**Indirect evidence from cross-system comparison.** The only "ablation-like" signal available is the comparison between OpenSeeker-v1 and OpenSeeker-v2, which provides an estimate of the *combined* effect of all three modifications. The +16.5 point BrowseComp gain is the total effect size. The comparison between OpenSeeker-v1 and RedSearcher provides a much weaker signal, since too many variables differ (training pipeline, base model, data sources, tool set design).

**Robustness across benchmarks.** A form of implicit robustness check is provided by the consistent pattern across four different benchmarks. OpenSeeker-v2 outperforms Tongyi DeepResearch on all four (BrowseComp +2.6, BrowseComp-ZH +11.4, HLE +1.7, xbench +3.0), which suggests the improvement is not benchmark-specific or the result of overfitting to a particular evaluation distribution. However, the varying gap sizes (+1.7 to +11.4) indicate that the benefit is not uniform — it is largest on browsing-specific benchmarks (BrowseComp and BrowseComp-ZH) and smallest on HLE, which tests broader reasoning capabilities beyond search skill.

**No training stability or seed sensitivity analysis.** The paper reports single-run results with no information about training stability, variance across random seeds, or sensitivity to hyperparameters. Given the small dataset size (10.6k examples), training runs may be sensitive to data ordering, random initialization of newly initialized parameters (if any), or optimizer state. The 2.6 point gap on BrowseComp over Tongyi DeepResearch is modest enough that seed variance could plausibly account for it.

### Critical Assessment

#### Claim 1: "Simple SFT can rival or surpass CPT+SFT+RL pipelines for search agents."

**The evidence supports this claim, but with important scope limitations that the paper's framing sometimes obscures.** The comparison in Table 1 shows OpenSeeker-v2 (SFT-only) outperforming Tongyi DeepResearch and RedSearcher (both CPT+SFT+RL) on BrowseComp (+2.6 and +3.9 points, respectively), BrowseComp-ZH (+11.4 and +8.3), HLE (+1.7 and +0.3), and xbench (+3.0 vs. Tongyi). These are genuine cross-system comparisons where OpenSeeker-v2 achieves better numbers.

**However, what the experiments demonstrate is narrower than what the claim might suggest:**

First, the comparison is against *specific implementations* of CPT+SFT+RL, not against the *concept* of multi-stage training. We do not know whether Tongyi DeepResearch's CPT+SFT+RL pipeline is well-optimized, whether their RL reward function is well-designed, or whether their training data is of comparable quality to OpenSeeker-v2's. It is possible that a *better* CPT+SFT+RL pipeline — one that also incorporates graph expansion, tool expansion, and difficulty filtering into its data synthesis — would outperform OpenSeeker-v2 by a wider margin. The paper's claim is really: "OpenSeeker-v2's SFT with high-quality data beats these specific industrial systems," not "SFT is universally better than CPT+SFT+RL." The distinction matters because the latter claim would require controlled experiments varying only the training pipeline while holding data constant, which the paper does not do.

Second, the paper does not test whether adding RL on top of OpenSeeker-v2's SFT training would yield further gains. It's possible that the 46.0% BrowseComp is not the ceiling of what this data synthesis pipeline can achieve — an RL stage that optimizes for answer correctness or search efficiency might push performance substantially higher. The paper's silence on this point is strategic (the thesis is that SFT *alone* is sufficient, not that SFT is *optimal*), but it leaves open the question of whether the industrial pipeline's extra stages are truly *unnecessary* or merely *compensating for data deficiencies that OpenSeeker-v2 has addressed through other means*.

Third, the base model (Qwen3-30B-A3B-Thinking-2507) may be unusually well-suited to SFT-only search agent training. The "Thinking" designation indicates pre-training on reasoning traces, which may provide a stronger initialization for search agent SFT than the base models used by Tongyi or RedSearcher. If those systems started from base models with weaker reasoning capabilities, their CPT and RL stages may have been necessary to teach fundamental reasoning skills that OpenSeeker-v2's base model already possessed. The paper does not discuss this confound.

#### Claim 2: "Data quality — specifically high-difficulty, information-rich trajectories — is the critical factor."

**This claim is strongly suggested by the OpenSeeker-v1 to v2 comparison but is not experimentally isolated.** The +16.5 point BrowseComp improvement from v1 to v2 occurs under identical training algorithm, base model, and model scale, with the only changes being the three data synthesis modifications. This is a clean before-and-after comparison that establishes the *total effect* of the data modifications.

**However, the claim that high-difficulty trajectories specifically are the critical factor is not tested independently.** The three modifications are introduced as a package, and we cannot disentangle their contributions. It is entirely possible that:

- The graph expansion is the dominant factor (by generating more diverse, less train-test-overlapping questions), and the filtering and tool expansion contributed minimally.
- The tool expansion is the dominant factor (by teaching the model more sophisticated search strategies), and the graph expansion and filtering contributed minimally.
- The interaction between all three is necessary — graph expansion without tool expansion produces questions the agent can't solve properly, tool expansion without graph expansion produces diverse tool use on simple questions, etc.

The paper's Figure 2 provides correlational evidence linking trajectory length to performance, but this is a between-system comparison confounded by many other variables. To support the specific claim that trajectory *difficulty* (as measured by length) is causal, we would need an experiment that varies only the difficulty filter threshold while holding graph size and tool set constant, showing that higher $T_{\text{min}}$ produces monotonic (or at least positive) improvements in benchmark performance.

#### Claim 3: "10.6k examples is sufficient; less data can outperform more data when quality is higher."

**This claim is directly supported by the OpenSeeker-v1 vs. v2 comparison.** OpenSeeker-v2 uses 10.6k examples vs. v1's 11.7k and achieves substantially better performance. This is a clean, within-family demonstration that dataset size is not the binding constraint and that pruning low-quality examples improves performance even at the cost of reducing dataset size.

**However, the scope of this claim is limited by the fact that only one dataset size is tested for v2.** We don't know whether OpenSeeker-v2's 10.6k is near-optimal — would 5k examples work nearly as well (suggesting even more aggressive filtering is possible), or would 20k examples from the same pipeline yield further gains (suggesting the filtering is already somewhat aggressive)? The paper states that "our internal observations suggest strong scaling potential of high-quality synthesized data" and that future work will "scale up data quantity, quality, and diversity," which implies the authors believe more data from this pipeline would help. But this is a stated intention, not an experimental result.

#### Claim 4: "OpenSeeker-v2 is the first SOTA search agent at this scale and paradigm developed by a purely academic team."

**This claim is factual given the numbers in Table 1, but "SOTA" requires careful qualification.** OpenSeeker-v2 achieves the highest numbers among ~30B ReAct-based agents on all four benchmarks. However:

- It does **not** achieve SOTA in absolute terms on BrowseComp — GPT-5-High (54.9%), GLM-4.7-357B (52.0%), and DeepSeek-V3.2-671B (51.4%) are all higher, though these are larger models and/or closed-source systems using different paradigms.
- It does **not** achieve SOTA on HLE — GLM-4.7-357B (42.8%), GPT-5-High (41.7%), and DeepSeek-V3.2-671B (40.8%) are higher.
- The SOTA claim is specifically scoped to "~30B ReAct-based search agents," which is a valid but narrow category. Within that category, the claim holds.

#### Missing Experiments That Would Strengthen the Paper

Several experiments are conspicuously absent and would substantially increase confidence in the paper's claims:

1. **Component ablations**: As discussed above, isolating the effect of each of the three data modifications. Even a simple set of three experiments — (a) v1 pipeline + graph expansion only, (b) v1 pipeline + tool expansion only, (c) v1 pipeline + filtering only — would dramatically improve our understanding of which modifications matter and how they interact.

2. **Dataset size scaling curve**: Training OpenSeeker-v2 on random subsets of 1k, 2k, 5k, 10.6k, and (if possible) 20k+ examples from the same synthesis pipeline. This would reveal whether performance is saturating at 10.6k or whether more data would help, which is directly relevant to the paper's future work statements about scaling.

3. **RL-on-top experiment**: Taking the OpenSeeker-v2 SFT checkpoint and applying RL (similar to WebSailor-V2's RL stage) to see whether further gains are possible. This would distinguish between "SFT is sufficient to reach this level" (the paper's claim) and "SFT is sufficient to saturate what's possible at this model scale" (a stronger claim the paper does not make but that readers might infer).

4. **Base model ablation**: Training the same OpenSeeker-v2 data on a non-Thinking base model (e.g., Qwen3-30B-A3B without the Thinking designation) to test whether the "Thinking" pre-training is essential to the result. If performance drops substantially, it suggests the paper's findings may not generalize to base models without specialized reasoning pre-training.

5. **Multiple training runs with error bars**: Even 2–3 runs with different random seeds would allow basic confidence intervals on the 46.0% BrowseComp result, which would clarify whether the 2.6 point gap over Tongyi is statistically meaningful.

6. **Transfer to other base model families**: Training the same pipeline on a non-Qwen base model (e.g., a LLaMA variant, DeepSeek) would test whether the data-centric approach generalizes across model families or is specific to Qwen's pre-training characteristics.

#### Genuine Weaknesses

**The single-run, no-error-bar evaluation is a significant limitation.** With a 500-question BrowseComp test set (the typical size for this benchmark), a 2.6 percentage point difference corresponds to 13 questions. Run-to-run variance from different weight initializations, data orderings, or even inference-time non-determinism could plausibly account for this magnitude of difference. The paper provides no way to assess this.

**The lack of component ablations makes the paper's central causal claim untestable.** We cannot determine from the reported experiments whether the data synthesis modifications *caused* the performance improvement, or whether the improvement is attributable to some other uncontrolled factor (e.g., improvements in the trajectory synthesizer's LLM between the v1 and v2 time periods, undocumented changes in tool implementations, differences in the knowledge graph construction).

**The benchmarks are browsing-centric and answer-extraction-centric.** BrowseComp, BrowseComp-ZH, xbench, and (to some extent) HLE all evaluate the agent's ability to find specific answers through web search. They do not evaluate the quality of the search *process* — whether the agent searches efficiently, whether it avoids redundant tool calls, whether its reasoning traces are coherent and honest. It is possible that OpenSeeker-v2 achieves its scores through exhaustive but inefficient search (200 tool calls per problem), which would be less impressive than achieving similar scores with fewer tool calls. The paper reports no efficiency metrics (average tool calls per benchmark problem, success rate as a function of tool-call budget).

**The masking of Hugging Face links** during evaluation raises a question about data contamination that the paper acknowledges but does not fully address. If some benchmark answers are directly findable on Hugging Face (e.g., model cards that discuss benchmark performance), and the data synthesis pipeline's knowledge graph includes Hugging Face pages, there could be train-test overlap that artificially inflates performance. The masking during evaluation prevents the agent from exploiting this overlap at test time, but it doesn't address whether the *training* data contained similar contamination — i.e., whether some of the 10.6k synthetic questions are isomorphic to benchmark questions because they were generated from the same or similar knowledge graph regions.

#### What the Experiments Actually Demonstrate

What the experiments *do* convincingly demonstrate is:

1. **A specific SFT-trained model (OpenSeeker-v2) achieves specific accuracy numbers on four benchmarks that happen to be higher than specific industrial baselines.** This is a factual result, and the numbers are publicly verifiable (model weights are open-sourced).

2. **The data synthesis modifications — taken together — produce training data that enables better downstream performance than OpenSeeker-v1's data synthesis.** This is demonstrated by the v1-to-v2 improvement under controlled conditions.

3. **Training on 10.6k difficult trajectories produces a more capable search agent than training on 11.7k mixed-difficulty trajectories.** This is the most robust finding in the paper, because the comparison holds everything constant except the data.

4. **Search agent performance at 30B scale is not bottlenecked by the SFT training paradigm — data quality can compensate for the absence of CPT and RL.** This is supported by the cross-system comparisons, though with the caveats about base model differences noted above.

What the experiments do *not* demonstrate, despite being implied by the paper's narrative:

- That any particular one of the three modifications is responsible for the gains.
- That the approach would work with a different base model or at a different scale.
- That the performance level achieved (46.0% BrowseComp) represents anything close to the ceiling of what SFT with high-quality data can achieve.
- That the approach is robust to hyperparameter choices, random seeds, or small variations in the data synthesis pipeline.
- That the approach produces *efficient* search agents, as opposed to agents that achieve accuracy through exhaustive search within a 200-step budget.

## 6. Limitations and Trade-offs

### The Difficulty Estimation Cost Is Borne Entirely During Data Synthesis — But Data Synthesis Itself Is a Black Box

**The assumption or constraint.** The paper's central thesis is that high-difficulty, information-rich training trajectories are the critical ingredient for SFT-only search agents. However, the *cost* of producing these trajectories is never quantified or even described in detail. The paper sketches the data synthesis pipeline — knowledge graph expansion, question generation conditioned on expanded subgraphs, ReAct trajectory simulation with an expanded tool set, strict low-step filtering — but provides no information about:

- **What LLM generated the questions and trajectories** (the paper only says questions are sampled from $\mathcal{P}_{\text{gen}}(q \mid \mathcal{G}_{\text{sub}}^{(K)})$; no model identity, scale, or cost is disclosed).
- **What knowledge graph was used** as the generative substrate (size, domain coverage, construction method).
- **How many raw trajectories were generated** before filtering down to 10.6k — the filtering rate determines the effective cost per training example, and a low yield (e.g., 1 in 10 trajectories surviving the filter) would make the data synthesis far more expensive than the SFT training itself.
- **The wall-clock time, API cost, or compute budget** required to run the synthesis pipeline.

The paper frames its contribution as "accessible to academic teams," but the data synthesis pipeline could easily be the most resource-intensive component. Generating 10.6k trajectories averaging 64.67 tool calls each means approximately **685,000 total tool-call steps** were simulated during trajectory generation (10.6k × 64.67). If each tool call requires a real web search or knowledge-graph lookup, and each reasoning step between tool calls requires an LLM generation, the synthesis cost may rival or exceed the cost of training the model itself — yet this cost is invisible in the paper's accounting.

**The consequence.** A practitioner who wants to replicate OpenSeeker-v2 cannot estimate the total resource requirements. The paper's narrative — "a purely academic team using only SFT" — could be misleading if the data synthesis pipeline requires access to a frontier LLM (e.g., for trajectory generation), a large-scale knowledge graph, or substantial API credits for web search during synthesis. The *training* is simple SFT, but the *data creation* may implicitly depend on the very industrial infrastructure the paper claims to circumvent. If a capable LLM is needed to generate the trajectories, and that LLM was itself trained with CPT+SFT+RL by an industrial lab, then OpenSeeker-v2 is not a demonstration that industrial pipelines are unnecessary — it is a demonstration that their outputs can be *distilled* into an SFT-trained student, which is a different and less surprising claim.

A secondary consequence: without knowing the synthesis pipeline details, it is impossible to assess whether the approach is *scalable* to other domains. Would the same pipeline work for code-generation search agents, legal research agents, or scientific literature review? If the knowledge graph is domain-specific, the pipeline may not transfer without substantial re-engineering.

**What evidence exists in the paper.** **None beyond the methodological sketch in Section 2.1.** The paper does not report the number of raw trajectories generated, the filtering rate, the LLM used for question/trajectory synthesis, the knowledge graph source, or the total synthesis cost. The only quantitative detail about the synthesis pipeline is the final dataset size (10.6k) and the average trajectory length (64.67 tool calls, from Figure 2). Section 3 ("What's next") states that future work will "scale up data quantity, quality, and diversity," which implicitly acknowledges that the current synthesis pipeline is not at its limit, but provides no information about what scaling would cost.

**Mitigation status.** **Not addressed.** The paper treats data synthesis as an input to the system rather than as part of the system itself. The open-sourcing of model weights (via Hugging Face) makes the *output* of the pipeline reproducible, but the pipeline itself remains a black box. A practitioner could use OpenSeeker-v2 as-is without replicating the synthesis pipeline, but could not extend the approach to new domains or improved data without reverse-engineering substantial missing details. The paper would be substantially strengthened by a "data sheet" documenting the synthesis pipeline's cost, model dependencies, and filtering statistics.

### No Controlled Isolation of the Three Data Modifications Weakens the Central Causal Claim

**The assumption or constraint.** The paper introduces three data synthesis modifications — scaling graph size from $k$ to $K$, expanding the tool set, and strict low-step filtering with threshold $T_{\text{min}}$ — as a package. The experiments compare two endpoints: OpenSeeker-v1 (none of these modifications) and OpenSeeker-v2 (all three applied simultaneously). **No experiment varies one modification while holding the other two constant.** The paper's central claim is that "high-quality data of high difficulty and richness" enables SFT to rival CPT+SFT+RL, but we cannot determine which of the three modifications is responsible for how much of the 16.5 percentage point BrowseComp improvement, or whether all three are necessary, or whether any one modification dominates.

This is not an incidental omission — it directly undermines the paper's scientific contribution. If graph expansion alone accounts for most of the gain, then the insight is "bigger knowledge graphs produce better training data," which is a straightforward scaling observation. If strict low-step filtering alone accounts for most of the gain, then the insight is "removing easy trajectories is more important than adding hard ones," which is a more interesting and counterintuitive finding about training data composition. The paper's narrative implies the latter (the title emphasizes "high-difficulty" trajectories), but the experimental design cannot distinguish these interpretations.

**The consequence.** Researchers who want to build on OpenSeeker-v2 cannot prioritize their efforts. Should they invest in building larger, richer knowledge graphs? In designing more diverse tool sets? In aggressive filtering to remove short trajectories? All three? The paper provides no guidance because it never isolates the effects. A team with limited resources might waste effort on the least impactful modification while neglecting the one that matters most.

Furthermore, the absence of ablations makes it impossible to determine whether the three modifications are **complementary** (each contributes independently and their combination is additive or super-additive) or **redundant** (two of them don't matter and one accounts for the entire effect). If the modifications are redundant, the paper's methodological contribution is overstated — a simpler recipe with only one change would achieve the same result.

**What evidence exists in the paper.** The only ablation-adjacent signal is the comparison between OpenSeeker-v1 and OpenSeeker-v2 itself, which provides the total effect size (+16.5 points BrowseComp) but no decomposition. Figure 2 shows the tool-call distribution shift between v1 and v2, but this is an *outcome* of all three modifications acting together (graph expansion makes questions harder, tool expansion enables longer search, filtering removes short trajectories — all three affect the average trajectory length). We cannot attribute the length increase to any single modification.

**Mitigation status.** **Not addressed.** The paper does not acknowledge the absence of ablations as a limitation. The three modifications are presented in Section 2.1 as a coherent recipe, and the results are presented as the outcome of applying that recipe. This is appropriate for a technical report demonstrating a system, but it leaves a gap between what the paper *demonstrates* (a specific system achieves specific numbers) and what it *claims* (data quality is the critical factor). The latter claim requires evidence that the data quality *differences* — not other uncontrolled factors — caused the performance improvement, and that evidence is missing without component ablations.

### Evaluation Is Single-Run with No Statistical Rigor, Making the Margins Over Baselines Uninterpretable

**The assumption or constraint.** All results in Table 1 are single-run evaluations with no reported error bars, confidence intervals, or statistical significance tests. The paper does not describe multiple training runs with different random seeds, multiple evaluation runs, or any form of uncertainty quantification. The baseline numbers are taken from third-party technical reports and public leaderboards, with no independent verification or controlled re-evaluation under identical conditions.

**The consequence.** The key quantitative claims in the paper depend on margins that are modest in absolute terms but presented as decisive:

- OpenSeeker-v2 outperforms Tongyi DeepResearch on BrowseComp by **2.6 percentage points** (46.0% vs. 43.4%).
- On HLE, the margin is only **1.7 points** (34.6% vs. 32.9%) and against RedSearcher it is only **0.3 points** (34.6% vs. 34.3%).

With a typical BrowseComp test set of approximately 500 questions (the standard for this benchmark), a 2.6 point difference corresponds to **13 questions**. Run-to-run variance from different weight initializations during SFT, different data orderings, or even inference-time non-determinism (from sampling during tool calls) could plausibly produce differences of this magnitude. Without error bars, we cannot determine whether OpenSeeker-v2's reported advantage reflects a genuine capability difference or statistical noise.

The 0.3 point HLE margin over RedSearcher (roughly 1–2 questions depending on the HLE test set size) is almost certainly within the range of run-to-run variance, yet the paper presents it as evidence that OpenSeeker-v2 "outperforms" RedSearcher. A fair characterization would be that the two systems are statistically indistinguishable on HLE given the available evidence.

The comparison against larger models introduces additional uncertainty because those numbers come from different evaluation setups (different tool implementations, different search environments, possibly different answer-grading procedures). The 16-point gap over DeepSeek-V3.1-671B on BrowseComp is large enough to be robust to these concerns, but smaller gaps (e.g., the 0.9 point advantage over GLM-4.6-357B) are not.

**What evidence exists in the paper.** **None.** The paper reports point estimates only. There is no mention of multiple runs, variance estimation, or statistical testing anywhere in Sections 2.2–2.3. The experimental setup (Section 2.2) describes the benchmarks, baselines, and implementation details without addressing reproducibility or statistical rigor.

**Mitigation status.** **Not addressed.** This is a structural weakness of the paper's evaluation methodology. The open-sourcing of model weights partially mitigates the concern — other researchers can independently evaluate OpenSeeker-v2 and compute their own error bars — but the paper itself provides no uncertainty quantification. For a paper whose primary contribution is an empirical demonstration (SFT + high-quality data beats CPT+SFT+RL), the lack of statistical rigor weakens the strength of that demonstration. Future work by the authors or others should establish whether the reported margins are robust to training seed variance and inference-time non-determinism.

### The Approach Is Validated on a Single Base Model Family, Leaving Generalization to Other Architectures and Pre-Training Regimes Unknown

**The assumption or constraint.** OpenSeeker-v2 is instantiated from exactly one base model: **Qwen3-30B-A3B-Thinking-2507**, a Mixture-of-Experts model with 30B total and 3B activated parameters, specifically pre-trained with chain-of-thought reasoning data (indicated by the "Thinking" designation). The paper makes no attempt to train on a different base model family (e.g., LLaMA, DeepSeek, Mistral) or to ablate the "Thinking" pre-training by using a non-Thinking Qwen variant.

This matters because the "Thinking" designation is not cosmetic — it indicates that the base model was explicitly trained on reasoning traces, which may provide a uniquely strong initialization for search agent SFT. If the base model already understands how to structure multi-step reasoning before SFT begins, the SFT stage only needs to teach it *what to reason about* in a search context (which tools to use, how to interpret search results, how to synthesize evidence). If a base model lacks this reasoning pre-training, SFT on search trajectories might need to simultaneously teach reasoning structure *and* search-specific behavior, which could be substantially harder.

**The consequence.** The paper's findings may not generalize to practitioners who have access to non-Qwen base models or who prefer to use models without specialized reasoning pre-training. If the "Thinking" pre-training is essential to the result, then the paper's claim — "a simple SFT approach could be surprisingly powerful" — is contingent on starting from a base model that already has strong reasoning capabilities. This does not invalidate the result, but it narrows its applicability: the recipe may work for Qwen-Think-like models but not for general-purpose base models. The paper does not test this boundary.

Furthermore, OpenSeeker-v2 is compared against industrial baselines (Tongyi DeepResearch, RedSearcher) that may have started from base models with *different* pre-training characteristics — possibly models without explicit reasoning pre-training, or models with different strengths and weaknesses. If OpenSeeker-v2's base model is inherently stronger at reasoning than the baselines' base models, the comparison confounds data quality with base model quality. The paper's narrative attributes the performance advantage to data synthesis, but part of the advantage may come from base model selection.

**What evidence exists in the paper.** **None that isolates base model effects.** The paper does not train OpenSeeker-v2 on any model other than Qwen3-30B-A3B-Thinking-2507, nor does it provide an ablation using a non-Thinking Qwen variant. The base model choice is stated in Section 2.2 without justification beyond the factual citation. The paper does not discuss whether the "Thinking" pre-training is expected to be important or incidental to the result.

**Mitigation status.** **Not addressed.** The paper does not acknowledge base model dependence as a limitation or discuss the generalizability of the approach to other model families. The open-sourcing of the training data (through the OpenSeeker project) would allow other researchers to test generalization by training on different base models, but the paper itself provides no such evidence. This is a significant gap because one of the paper's stated goals is to "make frontier search agent research more accessible to the community" — but if the approach only works with Qwen-Think models, its accessibility is limited to those with access to that specific model family.

### Efficiency Metrics Are Entirely Absent — the System May Achieve Accuracy Through Exhaustive Search Within a Generous Budget

**The assumption or constraint.** OpenSeeker-v2 is configured with a **200 tool-call budget** per trajectory (Section 2.2), but the paper reports **no efficiency metrics** for the agent's behavior at test time. We do not know:

- **How many tool calls OpenSeeker-v2 actually uses per benchmark question on average**, or the distribution of tool-call counts. Does it typically use 20–30 calls, or does it regularly approach the 200-call limit?
- **Whether the accuracy numbers in Table 1 were achieved under the same tool-call budget as the baselines** — Tongyi DeepResearch and RedSearcher may have different default or maximum tool-call limits, and a system with a higher budget has an inherent advantage.
- **The success rate as a function of tool-call budget** — if OpenSeeker-v2 were limited to, say, 50 tool calls, would it still outperform Tongyi DeepResearch? Or does its performance advantage depend on the ability to make many more search attempts?
- **Wall-clock time per query** — long trajectories with many tool calls may take minutes or tens of minutes to execute, which matters for practical deployment but is not reported.

This matters because accuracy and efficiency are often in tension for search agents. A system that achieves 46.0% BrowseComp by making 150 tool calls per question is less impressive than one that achieves 43.4% with 40 tool calls per question — the marginal accuracy gain comes at the cost of 3–4× the inference time and API calls. Without efficiency metrics, the accuracy numbers in Table 1 are incompletely specified.

**The consequence.** A practitioner choosing between OpenSeeker-v2 and a competing system cannot make an informed cost-benefit tradeoff. If OpenSeeker-v2's accuracy advantage comes primarily from using more tool calls, a latency-constrained deployment might prefer a slightly less accurate but faster system. Conversely, if OpenSeeker-v2 achieves its accuracy with *fewer* tool calls than baselines, that would be an even stronger result — it would demonstrate not just better accuracy but better search efficiency. The paper provides no way to distinguish these scenarios.

Furthermore, the absence of efficiency metrics makes it difficult to assess whether the training data's long trajectories (averaging 64.67 tool calls) taught the model to be *effective* at long-horizon search or merely *biased* toward making many tool calls regardless of necessity. A model trained exclusively on long trajectories might learn to "oversearch" — making redundant or unnecessary tool calls because it has never seen examples where search terminates early. This would be a direct negative consequence of the strict low-step filtering, which removed all short trajectories from the training data. Without test-time efficiency analysis, we cannot determine whether this failure mode occurs.

**What evidence exists in the paper.** **None beyond the training data distribution (Figure 2).** Figure 2 shows that the *training* trajectories average 64.67 tool calls, but this tells us nothing about the agent's *test-time* behavior. A model trained on long trajectories might learn to search efficiently (quickly identifying when enough evidence is gathered) or might learn to search exhaustively (continuing to make calls until it hits the budget limit). The paper provides no test-time tool-call statistics to distinguish these possibilities. The 200-call budget is mentioned in Section 2.2 as a configuration detail but is never discussed in relation to actual usage patterns.

**Mitigation status.** **Not addressed.** The paper does not acknowledge the absence of efficiency metrics as a limitation, nor does it report any efficiency-related results. This is a notable gap given that the paper's narrative emphasizes the difficulty of the training data — if that difficulty translates into inefficient test-time behavior, the practical value of the approach is diminished. Future work should include efficiency analysis as a standard part of search agent evaluation, reporting accuracy as a function of tool-call budget (e.g., accuracy at 10, 20, 50, 100, and 200 calls) to enable cost-benefit comparisons across systems.

---

### The Benchmark Suite Is Narrowly Scoped to Answer-Extraction Tasks, Providing No Signal on Search Process Quality

**The assumption or constraint.** All four benchmarks — BrowseComp, BrowseComp-ZH, Humanity's Last Exam, and xbench — evaluate the agent on a single dimension: **did it produce the correct final answer?** They do not evaluate:

- **Search process quality**: Was the search efficient? Did the agent avoid redundant queries? Did it backtrack when hitting dead ends? Did it verify information from multiple sources before concluding?
- **Reasoning trace honesty**: Do the agent's stated reasoning traces ($r_t$ steps) accurately reflect its actual information-gathering strategy, or are they post-hoc rationalizations?
- **Source attribution**: Does the agent correctly cite where it found each piece of evidence, and are those citations accurate?
- **Robustness to misleading information**: Can the agent identify and disregard incorrect or low-quality sources, or does it naively trust whatever search results return?
- **Query formulation quality**: Are the agent's search queries well-formulated, or does it succeed through brute-force iteration over many poorly-targeted queries?

These process-level capabilities are essential for real-world search agents — a system that finds correct answers but through inefficient, unverifiable, or brittle processes is not deployable in high-stakes settings. The paper's exclusive focus on final-answer accuracy treats the search process as an unobserved intermediate variable, which is appropriate for a first demonstration but limits what we can conclude about the agent's actual capabilities.

**The consequence.** OpenSeeker-v2's benchmark scores may overstate its practical readiness. A system that achieves 46.0% on BrowseComp by making 150 tool calls, generating hallucinated citations, and occasionally arriving at the correct answer through lucky search rather than systematic reasoning would score identically on the reported metrics as a system that achieves the same accuracy through efficient, well-reasoned, properly-attributed search. The paper provides no signal to distinguish these scenarios, and the training methodology — SFT on synthetic trajectories that may themselves contain imperfect or inefficient search patterns — provides no guarantee that the learned behavior is process-optimal.

Furthermore, the absence of process-level evaluation means we cannot determine whether the data synthesis modifications actually improved the *quality* of the agent's search strategy or merely increased its *persistence* (making more tool calls until it stumbles on the answer). The paper's thesis — that high-difficulty trajectories teach "sustained reasoning, robust information extraction, and long-horizon search behavior" — is a claim about process quality, but the evaluation provides no process-level evidence.

**What evidence exists in the paper.** **None process-level.** All reported metrics are final-answer accuracy. The paper does not analyze search trajectories produced at test time, does not report tool-call efficiency, does not evaluate citation accuracy, and does not assess whether reasoning traces are faithful to the agent's actual decision process.

**Mitigation status.** **Not addressed.** The paper does not acknowledge the narrowness of the evaluation as a limitation, nor does it discuss process-level metrics as a direction for future work. This is consistent with the norms of the search agent benchmarking literature (BrowseComp, HLE, and xbench are all answer-only benchmarks), but it means the paper inherits those benchmarks' limitations without commenting on them. A more comprehensive evaluation — even a small-scale qualitative analysis of a few dozen trajectories — would substantially strengthen confidence that the reported accuracy gains reflect genuine improvements in search capability rather than increased search persistence.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

OpenSeeker-v2 does not introduce a new training algorithm, a novel architecture, or a theoretical framework. What it introduces is a **demonstration that challenges the assumed necessity of multi-stage industrial training pipelines for frontier search agents**, and in doing so, it shifts the burden of proof in an important way. Before this work, the default assumption in the search agent community — reinforced by a sequence of industrial technical reports from Tongyi DeepResearch (Team et al., 2025b), RedSearcher (Chu et al., 2026), and others — was that reaching competitive performance on benchmarks like BrowseComp required the full CPT+SFT+RL stack. This assumption was not irrational: prior SFT-only agents consistently scored in the 24–30% range on BrowseComp (WebSailor-V2-SFT at 24.4%, WebLeaper-SFT at 27.7%, OpenSeeker-v1 at 29.5%), and only systems with RL or CPT pushed beyond 35%. The industrial recipe appeared to be empirically validated by the failure of simpler approaches to cross that threshold.

OpenSeeker-v2 breaks this pattern at a specific, carefully chosen point: it achieves 46.0% on BrowseComp with SFT alone, decisively above not only all prior SFT-only agents but also above the CPT+SFT+RL baselines at comparable scale (Tongyi DeepResearch at 43.4%, RedSearcher at 42.1%). This is not an incremental improvement over the prior SFT ceiling of ~29.5% — it is a discontinuous jump of 16.5 percentage points that redefines what "SFT-only" means as a category. The significance is not that SFT is universally better than RL or CPT (the paper does not claim this, and the absolute frontier on BrowseComp — GPT-5-High at 54.9% — remains out of reach), but rather that **the binding constraint on search agent performance at this scale was never the training algorithm. It was the training data distribution.**

This reframing has a specific, falsifiable implication: if data quality is the dominant factor, then future improvements in search agent performance at 30B scale should come primarily from better data synthesis, not from more complex training recipes. The paper does not prove this implication — it demonstrates a single data point — but it creates a new null hypothesis that subsequent work must either confirm or reject. A team that achieves 50% BrowseComp with CPT+SFT+RL cannot claim the RL stage was essential unless they also show that SFT alone on the same data (or equivalently high-quality data) would have fallen short. The paper raises the bar for what counts as evidence that multi-stage training is necessary.

The practical consequence for the research ecosystem is structural and immediate: **the barrier to entry for search agent research has been lowered in a verifiable way.** The paper open-sources model weights (via Hugging Face) and code (via GitHub), providing a reproducible baseline that any academic team can download, evaluate, and build upon. This matters because prior SOTA search agents in this category (Tongyi DeepResearch, RedSearcher) were not open-sourced, making them inaccessible as baselines for controlled experimentation. A researcher who wants to test a new search strategy, tool design, or data synthesis method now has a transparent, SOTA-level starting point that they can modify and compare against, rather than having to first replicate an industrial pipeline they cannot afford. This is a genuine contribution to the field's infrastructure, independent of whether the specific 46.0% number holds up under re-evaluation.

**Reconciling prior contradictions.** The paper does not directly resolve conflicts in the literature — there is no long-standing debate about whether SFT suffices for search agents that the paper settles — but it does provide a coherent explanation for why prior SFT-only agents underperformed. The explanation is not that SFT is inherently limited, but that prior SFT data synthesis pipelines (including OpenSeeker-v1) produced training distributions that were inadequately difficult and information-rich. The counterintuitive observation that WebSailor-V2's RL stage provided an 11 percentage point BrowseComp boost (24.4% → 35.3%) while OpenSeeker-v2's data improvements provided a 16.5 point boost (29.5% → 46.0%) with no RL at all suggests that RL was compensating for data deficiencies in WebSailor-V2 that OpenSeeker-v2 addresses at the data level. This is a specific, testable hypothesis: if WebSailor-V2 were retrained on OpenSeeker-v2's data, would its RL stage still provide an 11-point boost, or would the gain shrink dramatically?

**Research directions that become more attractive.** The paper makes **data synthesis methodology** the central research question for search agents, displacing training algorithm design from its previously privileged position. Specific directions that gain prominence include: knowledge graph construction and expansion strategies, question generation conditioned on structured information topologies, trajectory synthesis with diverse tool use, and filtering criteria that shape training distributions toward desired test-time behavior. These are fundamentally more accessible to academic labs than RL infrastructure or large-scale CPT, which aligns with the paper's stated democratization goal.

**Research directions that become less attractive** (or require stronger justification). The paper implicitly argues that **incremental improvements to RL reward design for search agents** or **small-scale CPT on web interaction data** are less promising than they previously appeared, because the returns to better data synthesis appear to dominate the returns to better training algorithms at this scale. A team proposing a new RL method for search agents now must contend with the possibility that a comparable investment in data quality would yield larger gains. This does not mean RL or CPT are worthless — the paper explicitly leaves open whether they would further improve OpenSeeker-v2 — but it shifts the default toward data-centric approaches until evidence emerges that data quality has been saturated.

**The most important conceptual shift.** Perhaps the deepest implication of OpenSeeker-v2 is the implicit reframing of SFT from "behavior cloning" to **"capability elicitation."** The paper's base model, Qwen3-30B-A3B-Thinking-2507, already possesses strong reasoning capabilities from pre-training. The SFT stage does not teach the model to reason — it teaches the model *what to reason about in a search context* and *how to translate reasoning into search actions*. The high-difficulty training trajectories serve not as demonstrations to be mimicked but as **prompts that elicit the model's latent search capabilities**. If this framing is correct, the key question for search agent training becomes: "what distribution of problems and solutions maximally elicits the base model's existing capabilities?" rather than "how do we train new capabilities into the model through complex optimization?" This connects OpenSeeker-v2 to a broader trend in the LLM literature — from LIMA (Zhou et al., 2023) to Orca (Mukherjee et al., 2023) — that finds carefully curated SFT data can unlock capabilities that appear to require RL or large-scale pre-training, when in fact those capabilities were latent in the base model and merely needed the right elicitation.

### Follow-Up Research This Work Enables

**Component-level ablation of the three data synthesis modifications.** The most obvious and necessary follow-up is to isolate the contribution of each data modification — scaling graph size ($k \to K$), expanding the tool set, and strict low-step filtering ($T \geq T_{\text{min}}$) — by running the OpenSeeker-v2 synthesis pipeline with each modification individually toggled, while holding the other components at their OpenSeeker-v1 settings. The minimal experiment requires four training runs: (1) v1 baseline (no modifications), (2) graph expansion only, (3) tool expansion only, (4) filtering only. This would directly measure which modification accounts for how much of the 16.5-point BrowseComp gain, and would test whether any single modification dominates. A finding that filtering alone accounts for most of the gain would be particularly useful — it would suggest that the critical insight is removing easy trajectories, not necessarily making trajectories harder through graph expansion, and future work could focus on filtering strategies rather than graph engineering.

**RL-on-top experiment to test whether the data modifications saturate the SFT ceiling.** Train an RL stage starting from the OpenSeeker-v2 SFT checkpoint, using a reward function based on final-answer correctness (and possibly search efficiency), following the RL approaches used by WebSailor-V2 and WebLeaper. The key measurement is the incremental gain from RL: if RL provides a small gain (e.g., 1–3 points on BrowseComp), it suggests OpenSeeker-v2's data is near the ceiling of what SFT can extract from the base model, and the industrial pipeline's extra stages were primarily compensating for data deficiencies. If RL provides a large gain (e.g., 8–12 points, comparable to WebSailor-V2's RL boost), it suggests SFT and RL provide complementary benefits that the paper's data modifications did not exhaust, and the optimal recipe combines high-quality SFT data with RL optimization. The paper's silence on whether RL helps — combined with the authors' statement that "internal observations suggest strong scaling potential" — makes this the highest-value single experiment for refining our understanding of the paper's claims.

**Dataset size scaling curve on the OpenSeeker-v2 synthesis pipeline.** Train OpenSeeker-v2 on random subsets of 1k, 2k, 5k, 10.6k, and (if feasible) 20k+ examples from the same synthesis pipeline, and plot BrowseComp accuracy as a function of dataset size. This would answer two critical questions: (1) is 10.6k near saturation, or would more data from this pipeline yield substantial further gains (testing the authors' stated intention to "scale up data quantity"), and (2) how steep is the scaling curve at small dataset sizes — could a team with even fewer resources achieve, say, 40% BrowseComp with only 5k carefully synthesized examples? The shape of the curve would inform whether the primary bottleneck going forward is synthesis pipeline throughput (if performance scales well with data quantity) or synthesis pipeline design (if performance saturates quickly and further gains require qualitatively better data).

**Base model ablation to test dependence on reasoning pre-training.** Train the same OpenSeeker-v2 data on two additional base models: (1) the non-Thinking variant of the same Qwen3-30B-A3B model (if available), and (2) a comparable-scale model from a different family with no specialized reasoning pre-training (e.g., a 30B LLaMA variant or DeepSeek-V2-Lite). If performance drops substantially on the non-Thinking and cross-family base models — say, to 30–35% BrowseComp — it would indicate that the paper's results depend heavily on the Qwen-Thinking base model's reasoning capabilities, and the approach may not generalize to teams without access to reasoning-specialized models. If performance remains strong across base models, it would substantially strengthen the paper's claim that data quality, not base model selection, is the dominant factor. This experiment is important for the paper's democratization narrative: if the approach only works with Qwen-Think, accessibility is limited to those who can use that specific model family.

**Process-level evaluation of search quality and efficiency.** A detailed analysis of 100–200 test-time trajectories from OpenSeeker-v2 on BrowseComp, measuring: (1) average and distribution of tool calls per question, (2) success rate as a function of tool-call budget (bucketing by 10, 20, 50, 100, 150, 200 calls), (3) rate of redundant or near-duplicate tool calls, (4) citation accuracy (does the agent correctly attribute evidence to sources?), (5) whether reasoning traces describe actual search intent or are post-hoc rationalizations. This analysis would address the paper's most significant evaluation gap — the absence of any efficiency or process-quality metrics — and would distinguish between two interpretations of the results: (a) OpenSeeker-v2 has genuinely learned efficient, strategic search behavior from long training trajectories, or (b) OpenSeeker-v2 has learned to be persistent (making many calls until it finds the answer) but not necessarily efficient. If the agent regularly uses 150+ calls to achieve its 46.0% BrowseComp, the practical value is lower than if it achieves similar accuracy with 30–50 calls, even if the final-answer accuracy is identical.

**Cross-domain transfer to non-browsing search tasks.** Adapt the OpenSeeker-v2 data synthesis pipeline to a domain where the "knowledge graph" is naturally available but structurally different from web hyperlink graphs — for example, code repository search (where the graph is the call graph or dependency graph of a codebase), scientific literature review (where the graph is the citation network), or legal research (where the graph is the network of case citations and statutory references). The question is whether the three modifications — graph expansion, tool expansion, low-step filtering — produce similarly effective training data when the underlying information topology changes. A positive result would establish OpenSeeker-v2 as a general recipe for search agent training, not a web-search-specific technique. A negative result (e.g., the approach works on web graphs but fails on citation graphs because the topology is fundamentally different) would clarify the boundary conditions and motivate domain-specific adaptations.

### Practical Applications and Downstream Use Cases

**Academic research groups building custom search agents for domain-specific literature review.** A research lab studying, for example, materials science wants an agent that can search the scientific literature, cross-reference papers, and synthesize findings across multiple subfields. Before OpenSeeker-v2, the available options were: (a) use a closed-source commercial search product (expensive, inflexible, cannot be customized to domain-specific databases), (b) attempt to replicate an industrial CPT+SFT+RL pipeline (prohibitively expensive), or (c) train an SFT-only agent using naive data synthesis (expected to score in the 24–30% range on general browsing benchmarks, with unknown domain-specific performance). OpenSeeker-v2 provides a fourth option: adapt the data synthesis pipeline to a domain-specific knowledge graph (e.g., a citation network built from the lab's target literature), apply the same three modifications (graph expansion to capture multi-hop citation relationships, tool expansion to include domain-specific search APIs, low-step filtering to ensure questions require deep literature synthesis), and train via SFT on the resulting 10k-example dataset. The key number from the paper is the 16.5-point BrowseComp improvement from v1 to v2 — if a similar improvement transfers to domain-specific search, a lab could go from a barely-functional domain agent to one that reliably synthesizes multi-paper evidence, using only academic-scale compute resources and the open-sourced OpenSeeker-v2 codebase as a starting point.

**On-device or edge-deployed search assistants with limited inference budgets.** OpenSeeker-v2 uses a 30B-parameter MoE model with only 3B activated parameters per forward pass during inference (Section 2.2). This is significant for deployment scenarios where GPU memory or FLOPs are constrained — edge devices, consumer laptops, or privacy-sensitive settings where queries cannot be sent to cloud APIs. The 3B activated parameter count means each reasoning step and tool-call decision requires relatively little compute, while the 200-call budget provides headroom for complex searches. A deployment engineer could run OpenSeeker-v2 locally on a single consumer GPU, achieving BrowseComp-level search capability without sending queries to external servers. The paper's results suggest this locally-deployed agent would outperform a 671B-parameter cloud model (DeepSeek-V3.1) on browsing tasks by 16 points (46.0% vs. 30.0%), while keeping all data local. The tradeoff is latency — 200 tool calls at 3B parameters per forward pass may take minutes per query — but for asynchronous or batch search tasks (e.g., overnight literature review, background research for a report), this is a viable and privacy-preserving deployment model that was not previously possible with SOTA-level search performance.

**Training data generation for self-improving search agents in low-resource languages.** BrowseComp-ZH, the Chinese-language variant, shows OpenSeeker-v2's largest margin over industrial baselines: 58.1% vs. 46.7% for Tongyi DeepResearch (an 11.4-point gap). This suggests the data synthesis pipeline — particularly the knowledge graph expansion and tool set design — may be especially effective for non-English search, where industrial pipelines often have weaker coverage. A team building a search agent for a lower-resource language (e.g., Arabic, Hindi, Swahili) could adapt the OpenSeeker-v2 pipeline by constructing a language-specific knowledge graph (from Wikipedia in that language, local news sources, domain-specific databases), applying the three modifications, and synthesizing 10k training trajectories. Because the approach requires only SFT (no RL, no CPT), the computational cost is dominated by data synthesis (running a strong LLM to generate trajectories), which could be done using a multilingual frontier model as the trajectory generator even if the final agent uses a smaller language-specific base model. The 10.6k dataset size is small enough that synthesis is feasible on an academic budget, and the open-sourced pipeline provides a template rather than requiring design from scratch. This application directly leverages the paper's core finding — that carefully synthesized, high-difficulty data matters more than training pipeline complexity — to a setting where industrial pipelines are least likely to exist.
