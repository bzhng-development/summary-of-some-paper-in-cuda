# Programming Every Example: Lifting Pre-training Data Quality Like Experts at Scale

**ArXiv:** [2409.17115](https://arxiv.org/abs/2409.17115)

## 🎯 Pitch

A 0.3B-parameter language model can match human experts at cleaning web data by writing tiny programs to fix each example—string normalizations, line removals, formatting fixes—and doing this at scale yields a 20× reduction in pre-training FLOPs to match state-of-the-art models like LLEMMA-7B, without any domain-specific engineering.

---

## 1. Executive Summary

This paper introduces **Programming Every Example (PROX)**, a framework that treats data refinement as a programming task by having small language models (as few as 0.3B parameters) generate and execute fine-grained operations—such as string normalization, line removal, and document filtering—for each individual example at scale. Experiments across multiple corpora including C4, RedPajama-V2, FineWeb, FineWeb-Edu, and DCLM show that models pre-trained on PROX-curated data outperform those trained on original data or data selected by other methods by more than 2% on average across downstream benchmarks, with the framework achieving comparable performance using up to 20× fewer training FLOPs (e.g., matching LLEMMA-7B's 200B-token training with only 10B tokens on CODELLAMA-7B). In domain-specific continual pre-training on OpenWebMath, PROX improves average accuracy by 7.6% over MISTRAL-7B, 14.6% for LLAMA-2-7B, and 20.3% for CODELLAMA-7B, establishing that automated programmatic refinement generalizes across model sizes and domains without requiring domain-specific design.

## 2. Context and Motivation

### The Core Problem: Pre-Training Data Quality Bottleneck

The fundamental question this paper tackles is: **how do we improve the quality of web-scale pre-training corpora without depending on massive computational resources or hand-crafted rules that fail to adapt to individual examples?**

Behind every capable large language model lies a massive, high-quality pre-training corpus that equips the model with essential knowledge and reasoning abilities. The Internet provides vast amounts of raw text, but much of it is noisy and unrefined—containing HTML artifacts, navigation elements, advertisements, broken formatting, and content lacking educational value. This raw data, if used directly for pre-training, significantly degrades model performance. As the authors note in Section 1, the gap between raw web data and high-quality pre-training corpora requires **extensive cleaning and quality enhancement** before training can begin.

This problem matters enormously for two reasons. First, **economic**: pre-training runs for production LLMs cost millions of dollars in compute. Every FLOP spent on low-quality data is wasted—the model learns noise rather than signal, and more training steps are needed to achieve the same downstream performance. The paper's Figure 1 illustrates this starkly: a 1.7B model trained on PROX-refined FineWeb achieves the same average performance as a model trained on original FineWeb in roughly 1/30th the training steps, and for continual pre-training in the math domain, 10B PROX-refined tokens match LLEMMA-7B's performance trained on 200B tokens—a 20× reduction in training compute.

Second, the problem has **scalability implications**. The community's primary path to better models has been scaling pretraining compute—training larger models on more data for longer. But if data quality can be substantially improved, the paper argues, **investing compute in data refinement may yield better returns than investing the same compute in longer pretraining**. This reframes the entire scaling conversation from "how much pretraining compute?" to "how should we allocate compute between data refinement and pretraining?"

### Where Existing Approaches Fall Short

The paper identifies three major families of prior approaches, each with distinct limitations:

**Heuristic rule-based pipelines.** The dominant paradigm for data preprocessing involves human experts designing manual filtering rules (Section 5). These rules check document-level properties such as overall length, symbol-to-word ratio, presence of curse words, and other heuristics. Widely adopted pipelines include those used in C4 (Raffel et al., 2020), Gopher (Rae et al., 2021), FineWeb (Penedo et al., 2024a), and DCLM (Li et al., 2024). The problem with these approaches is threefold:

1. **Rule coverage is inherently limited.** Human experts can only anticipate so many noise patterns. The web contains an effectively infinite diversity of formatting quirks, boilerplate variations, and subtle quality degradations that no finite set of rules can capture.

2. **Rules lack per-example flexibility.** A rule like "drop documents with fewer than 100 words" will inevitably remove some good examples (short but substantive forum answers) while keeping some bad ones (boilerplate padded with fluff to exceed the threshold). Table 2 quantifies this failure: applying Gopher rules, C4 rules, and FineWeb rules to RedPajama-V2 yields improvements of only 0.2%, 0.5%, and 0.7% average accuracy respectively—and combining all three rules (as done in constructing the official FineWeb corpus) actually performs *worse* at +0.2%. The paper explicitly notes this counterintuitive result:

> "combining all three rules (as is done in constructing the official FineWeb corpus), does not lead to any larger enhancement in overall performance."

3. **Rules don't transfer across domains.** The most damning evidence comes from the math continual pre-training experiments (Table 5). Applying rule-based filtering to OpenWebMath **degraded** performance by 3.1% compared to continual pre-training on the original corpus (18.4% vs. 21.5% average for TINYLLAMA-1.1B). The paper explicitly draws this implication:

> "applying the rule-based filtering method does not bring improvements; instead, it leads to a 3.1% performance degradation compared to continual pre-training on the original corpus. This finding implies that there are no universal workable heuristics for all domains, highlighting the demands for automated pipelines just like PROX."

**Model-based data filtering/selection.** Recent work has explored using learned models as quality classifiers. LLAMA-3 (Meta, 2024) used LLAMA-2 models as text-quality classifiers for filtering training data. QuRating (Wettig et al., 2024) trains a rater model to score documents on four quality criteria and resamples based on scores. MATES (Yu et al., 2024) applies a smaller model for estimating data influence during pre-training, enabling dynamic data selection. The paper acknowledges these advances but identifies a critical limitation: **selection methods only make binary keep/drop decisions**. They cannot perform fine-grained refinement within documents—removing a navigation bar from the top of an otherwise excellent article, normalizing broken unicode characters, or stripping footer links. The paper's experiments confirm that document-level selection alone (PROX-D) provides meaningful gains (Table 2: 43.5% vs. 42.1% for raw data), but the full two-stage pipeline with chunk-level programming (PROX-D+C) pushes performance further to 44.6%, demonstrating the additional value of fine-grained operations that selection methods cannot achieve.

**Model-based data synthesis.** Another branch of research uses powerful LLMs to generate high-quality training data from scratch or by rewriting existing documents. The PHI series (Gunasekar et al., 2023; Li et al., 2023) demonstrated that small models trained on GPT-4-generated "textbook-quality" data can punch above their weight. INSTRUCTIONLM (Cheng et al., 2024) paraphrases web documents into specific styles like QA format using MISTRAL-7B. COSMO (Ben Allal et al., 2024) generates pre-training samples from seed topics by prompting MISTRAL-8x7B. While effective, the paper identifies three sharp limitations of synthesis approaches:

1. **Prohibitive computational cost.** Synthesizing pre-training-scale corpora requires running large models (7B-70B+) over billions of tokens—the inference FLOPs alone often exceed what it would cost to simply train on more raw data. The paper notes that COSMO-1.8B was trained on 180B tokens, including 25B tokens synthesized by MISTRAL-8x7B, and INSTRUCTIONLM-1.3B was trained on 100B tokens using a fine-tuned MISTRAL-7B synthesizer. These are massive overhead costs.

2. **Hallucination and factual errors.** Synthetic data inherits flaws from the generating model, including fabricated information—a well-documented problem (Maini et al., 2024).

3. **Lack of interpretability.** When synthetic data is wrong or low-quality, it is difficult to precisely characterize why or to automatically fix it. The generation process is opaque.

### How PROX Positions Itself at the Intersection

The paper positions PROX at a novel intersection that sidesteps the limitations of all three prior approaches (Section 1, Section 2.2):

- **Like rule-based systems, but learned:** PROX generates executable programs (function calls) that perform specific cleaning operations—`remove_lines()`, `normalize()`, `drop_doc()`—similar to what heuristics do. But instead of being hand-crafted, these programs are generated by a trained small language model that can adapt to each document's specific noise patterns.

- **Like data selection, but finer-grained:** PROX can both filter entire documents (via `drop_doc()`) and perform sub-document operations (removing specific line ranges, replacing specific strings). This is enabled by the two-stage design: document-level programming for coarse filtering, chunk-level programming for fine-grained refinement.

- **Like data synthesis, but more efficient and interpretable:** PROX does not generate new text—it refines existing text through explicit, human-readable programs. This means (a) the refined data preserves the factual content of the original, avoiding hallucination; (b) the programs themselves serve as an interpretable record of what was changed and why; (c) the refining models are small (0.3B-0.7B parameters), making large-scale inference dramatically cheaper than synthesis with 7B+ models.

The paper makes this positioning explicit in Section 5:

> "In this work, we focus on leveraging language models to lift data quality through the synthesis of executable and interpretable programs, rather than directly generating data. We demonstrate that PROX could clearly improve data quality at scale only with acceptable extra computing."

### Two Key Design Insights Enable This Approach

The paper's architecture is built on two critical observations that make the approach feasible:

**Small models suffice for data refinement tasks.** The document describes the pattern recognition needed for data cleaning as relatively straightforward: "it only needs to recognize several patterns" (Section 2.2). This is substantiated by the results in Table 4: even a 0.3B parameter model (TLM-XS) achieves 82.6% F1 on document-level refinement and 75.2% on chunk-level refinement. Larger models (0.7B, 1.7B) improve these scores modestly (81.3→83.7%, 75.6→77.3%), but the critical finding is that all model sizes produce downstream pre-training gains of roughly 2% over raw data (Figure 5), with the differences between refining model sizes being relatively small. This means PROX does not require expensive frontier models to be effective.

**Refinement programs are structured and verifiable.** By constraining the model's output space to a small vocabulary of pre-defined function calls with typed parameters (Table 1), the paper achieves two goals simultaneously: the model's generation task becomes tractable for small models (it only needs to produce function call syntax, not full implementations), and the outputs can be automatically validated for syntactic correctness before execution (Section 2.3 mentions "necessary checks for grammar correctness" in the data collection pipeline). This constrained generation space is what makes the approach reliable at scale—Table 35 reports failure rates below 0.5% across both refinement stages.

### Conceptual Connection to Inference-Time Scaling

The paper explicitly positions PROX within the broader conversation about inference-time compute scaling (Section 5, "Inference Time Scaling"):

> "While these studies focus on scaling computing on test time, our work demonstrates an alternative perspective on inference computing scaling. We advocate for allocating computing to refine pre-training corpora, particularly given that Internet-based corpora have been extensively utilized in language model pre-training."

This is a significant framing. Recent work has shown that allocating additional compute at inference time (e.g., through repeated sampling, verifier-guided search, or chain-of-thought) can make smaller models competitive with much larger ones (Snell et al., 2024; Wu et al., 2024; Brown et al., 2024). PROX extends this philosophy to the data preprocessing stage: rather than allocating extra compute to the model during problem-solving (test time), allocate extra compute to data refinement before training even begins. The paper's efficiency results—20× fewer training tokens, 30× fewer training steps—suggest this may be a complementary and perhaps more impactful form of inference compute scaling, since improved data benefits every training step that follows.

## 3. Technical Approach

### 3.1 Reader Orientation (Approachable Technical Breakdown)

**What the system is:** PROX is a data refinement pipeline where a small language model (0.3B–0.7B parameters) acts like an automated editorial assistant—it reads each document in a pre-training corpus, decides what needs fixing, and writes a tiny Python program of cleanup instructions that gets executed to produce a cleaned version of that document.

**What problem it solves and the "shape" of the solution:** The core problem is that web-scale pre-training data contains pervasive noise (HTML artifacts, navigation bars, broken formatting, low-quality content) that degrades model training, but existing solutions are either too rigid (hand-crafted heuristic rules that can't adapt per-example) or too expensive (using large LLMs to rewrite or synthesize data). PROX solves this by casting data refinement as **program generation**: the model outputs structured function calls like `remove_lines(0, 5)` and `normalize("bad string", "clean string")` rather than generating new text. This makes the task tractable for small models (pattern recognition + constrained output space) while remaining interpretable (the programs are human-readable) and execution-guaranteed (the programs are validated and run by a Python executor, not hallucinated). The pipeline operates in two stages—coarse document-level filtering followed by fine-grained chunk-level cleaning—processing each document individually so that treatment adapts to its specific noise characteristics.

### 3.2 Big-Picture Architecture (Diagram in Words)

The PROX system has five major components arranged in a sequential pipeline:

1. **Seed Data Annotation (offline, once):** A powerful LLM (LLAMA-3-70B-INSTRUCT) takes randomly sampled documents from the target corpus and annotates them with the correct refinement programs—both document-level keep/drop decisions and chunk-level line removal/normalization operations. This produces training data for the refining models.

2. **Base Language Model (small, pre-trained):** A decoder-only transformer (e.g., 350M, 750M, or 1.7B parameters) trained on a modest amount of raw unrefined data (~26B tokens). This model serves two roles: it is the initial model that gets adapted into a refining model, and it serves as the experimental baseline for measuring how much PROX-refined data improves pre-training.

3. **Refining Model (one per stage):** The base model after supervised fine-tuning on the seed annotation data. There are actually two separate fine-tuned variants of the same base model—one trained for document-level programming and one trained for chunk-level programming—though they share the same architecture and initial weights. Each takes raw text as input and outputs structured function calls.

4. **Python Executor:** A deterministic execution environment that takes the generated program and the original document, runs the function calls (which are implemented as standard Python functions operating on the document's line array), and outputs the refined document. This ensures that what the model *intended* to do is actually what gets done—there is no generative ambiguity.

5. **Two-Stage Refinement Pipeline:** The full processing flow is sequential. First, each document passes through the document-level refining model, which outputs either `drop_doc()` or `keep_doc()`. Kept documents proceed to the chunk-level stage, where they are split into chunks (≤1500 words each), each chunk is processed by the chunk-level refining model to identify and remove noisy lines or normalize strings, and then chunks are reassembled into the final refined document.

Information flows as follows: raw corpus → document-level refining model → kept documents (with dropped ones discarded) → chunk splitting → chunk-level refining model → chunk reassembly → refined corpus ready for pre-training. The entire pipeline processes each document independently, making it embarrassingly parallelizable across GPUs.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems and methods paper** whose core idea is that small language models can be adapted to generate executable data refinement programs, and that applying this programmatic refinement to pre-training corpora yields substantial improvements in downstream model quality with acceptable computational overhead.

---

#### Data Refinement as Program-Conditioned Transformation (Task Formulation)

The paper defines data refinement as a transformation from an original document `$d \in \mathcal{D}$` to a refined document `$\hat{d}$` where `$\hat{d}$` exhibits higher quality (Section 2.1). Rather than having the model directly output the cleaned text—which would require generative capacity and risk hallucination—the model outputs a **data processing program** `$Z$` that, when executed on `$d$`, produces `$\hat{d}$`.

The key mathematical formalization is the executor function:

$$E(Z_{\text{normalize}}, d) = (s'_i)_{i=1}^{|d|}, \text{ where } s'_i = \text{normalize}(s_i) \text{ if } s_i \text{ needs normalization else } s_i$$

where `$d = (s_1, s_2, ..., s_{|d|})$` is the original document represented as a sequence of strings (typically lines), `$Z_{\text{normalize}}$` is a program containing normalization instructions, and `$\text{normalize}()$` is a predefined function that maps specific strings to their cleaned versions.

**What this computes:** For each string `$s_i$` in the document, if the program `$Z_{\text{normalize}}$` indicates that this particular string contains a noise pattern that should be replaced, the executor applies the `$\text{normalize}()$` function with the source-target pair specified in the program, producing `$s'_i$`. If the string does not require normalization, it passes through unchanged (`$s'_i = s_i$`). The output is the full sequence of (potentially modified) strings.

**Why this form:** This formulation is critical because it separates **specification** (what to change) from **execution** (how to change it). The model only needs to identify *which* strings are noisy and *what* they should become—the actual string replacement is handled by a deterministic Python function that cannot hallucinate or make mistakes. This is fundamentally different from having the model regenerate the cleaned text, where it might inadvertently change meaning, omit content, or introduce factual errors. The executor also makes the process **auditable**: every modification is recorded as a specific function call with explicit before/after values.

The paper further notes that document filtering is a special case of this transformation framework where:

$$E(Z_{\text{filter}}, d) = \emptyset$$

meaning the executor returns an empty result (the document is dropped). This unification is conceptually elegant: it means the same model architecture, same training procedure, and same inference pipeline can handle both "this document should be removed entirely" and "this line within the document should be modified"—the only difference is which function is called.

The general formulation for the full PROX framework is:

$$\hat{d} = E(f(\theta, d), d)$$

where `$f(\theta, d)$` is the language model with parameters `$\theta$` that takes document `$d$` as input and outputs the refinement program `$Z$`, and `$E$` is the executor. The refined document `$\hat{d}$` is the result of executing program `$Z$` on the original document `$d$`.

This formulation makes explicit that the language model serves as a **program generator**—it maps documents to programs—while the executor serves as a **deterministic interpreter** that carries out the instructions. The quality of refinement depends entirely on the model's ability to generate correct programs, not on any generative text capability.

#### The PROX Program Space: A Constrained Vocabulary of Refinement Operations

The paper designs a deliberately small vocabulary of refinement operations (Table 1, Section 2.2). The design philosophy is explicit: "the model does not need to be very powerful or very large to handle these tasks, it only needs to recognize several patterns" and "the solution, though requiring more computing budget compared to heuristic-rule-based pipelines, still needs to be simple and efficient." These two constraints—low model capacity and computational efficiency—drive the program space design.

**Document-level operations (Stage 1):**

- `drop_doc() → None`: Delete the entire document from the corpus. The function takes no arguments because the decision is holistic—the model looks at the full document and decides whether it has sufficient educational value and formatting quality to be worth keeping.
- `keep_doc() → str`: Retain the original document unchanged. The function returns the document as-is.

These two operations reduce document-level refinement to a binary classification problem, which is why even a 0.3B parameter model can achieve >80% F1 on this task (Table 4).

**Chunk-level operations (Stage 2):**

- `remove_lines(line_start, line_end) → str`: Delete a contiguous range of lines from the chunk. `line_start` and `line_end` are integers specifying the inclusive range to remove (0-indexed, matching the line numbering in the input representation). The function returns the chunk with those lines excised.
- `normalize(source_str, target_str) → str`: Replace a specific noisy string with a clean version. `source_str` is the exact text to find and replace, and `target_str` is the replacement (often an empty string `""` for deletion of inline noise). This enables surgical edits—removing a URL embedded in an otherwise useful paragraph without deleting the whole line, or fixing broken unicode characters.
- `keep_chunk() → str`: Return the chunk unchanged, flagging it as already clean.

**Why this constrained vocabulary matters:** The paper argues that these simple operations are **expressively complete** for the task. As stated in Section 2.2:

> "While the individual functions may seem straightforward, their design space is flexible and capable of expressing complex rules previously developed by human experts... In fact, these rules can be projected into the program space of PROX, showcasing that our approach not only simplifies but also enhances the rule-creation process."

The key insight is that heuristic rules developed by human experts—checking for minimum document length, removing lines matching URL patterns, stripping boilerplate headers and footers—can all be expressed as sequences of these primitive operations. The model is not inventing new types of refinement; it is learning to **compose known primitives adaptively** based on the specific document content.

The paper also makes a subtle but important design choice in the function signatures: parameters are typed (`line_start<int>`, `source_str<str>`), and the model is trained to output syntactically valid function calls with correctly typed arguments. This is verified through grammar checking before execution (Section 2.3: "we also conduct necessary checks for grammar correctness"), which catches malformed programs before they can corrupt data. The failure rate analysis in Table 35 confirms this works: across all stages and domains, program execution failures occur in less than 0.5% of cases.

#### Two-Stage Progressive Refinement Architecture

The PROX pipeline processes data in two sequential stages (Section 2.2, Figure 2). This progressive design—document-level first, then chunk-level—is motivated by both computational efficiency and refinement quality.

**Stage 1: Document-Level Programming.** The entire document is fed to the document-level refining model, which outputs either `drop_doc()` or `keep_doc()`. The document-level model is fine-tuned on data annotated using a combination of two scoring criteria:

1. **Educational score** (from the FineWeb-Edu prompt, Figure 9): Evaluates whether the page has high educational value using an additive 5-point scoring system. The prompt asks the annotator model to assign 1–5 points based on criteria such as basic educational relevance, alignment with educational standards, coherence and comprehensiveness, and textbook-like quality.

2. **Format score** (newly proposed in PROX, Figure 9): Evaluates the cleanliness of the web extraction using another additive 5-point system. Points are accumulated based on how well the text has been extracted from HTML—whether HTML tags remain, whether navigation elements persist, and whether the document has clear paragraph structure.

The motivation for using both scores is a practical tradeoff between data quality and data quantity. The official FineWeb-Edu pipeline keeps documents only if Edu Score ≥ 2, which results in retaining only about 1.3 trillion tokens out of the original 15 trillion in FineWeb (less than 9%). PROX introduces a **relaxed filtering criterion** (Equation 2 in Appendix A.1):

$$\text{Filtering Criteria} = \begin{cases} \text{Edu Score} \geq 3, & \text{keep document} \\ \text{Edu Score} = 2 \text{ and Format Score} \geq 4, & \text{keep document} \\ \text{Edu Score} < 2, & \text{drop document} \end{cases}$$

**Why this design:** The relaxation specifically targets borderline documents. A document with Edu Score = 2 represents marginal educational value—potentially useful but not clearly educational. By additionally requiring Format Score ≥ 4, the system keeps only those marginal-education documents that are at least well-formatted and cleanly extracted. This is a **quality-quantity tradeoff mechanism**: it retains 23–28% of tokens versus FineWeb-Edu's 9% (Table 4 shows kept ratios of 23.2% for TLM-XS, 25.6% for TLM-S, 28.8% for TLM-M), providing up to 3× more unique tokens for training. Table 6 provides direct evidence that this tradeoff is favorable: models trained on PROX-filtered data match FineWeb-Edu's performance (45.2% average accuracy on both) while retaining over 3× more tokens and winning 5 out of 10 benchmarks each.

The document-level model is trained via supervised fine-tuning on approximately 51K annotated examples (46K train, 5K validation), with annotations produced by LLAMA-3-70B-INSTRUCT using the combined scoring prompts. The training configuration uses full-parameter fine-tuning with batch size 64 and a cosine learning rate schedule (1e-5 → 1e-6) for 3–5 epochs (Appendix A.2).

**Stage 2: Chunk-Level Programming.** Documents that survive Stage 1 are split into overlapping chunks using Algorithm 1 (Appendix A.4). The splitting algorithm processes a document line by line, accumulating lines into a chunk until adding the next line would exceed the context window (set to approximately 1,500 words rather than tokens for efficiency). When a line would overflow the current chunk, the chunk is saved, and a new chunk begins. Lines that individually exceed the window size are flagged as skipped (they are too long to process with the small model's context window).

Each chunk is then processed independently by the chunk-level refining model, which can output sequences of `remove_lines()`, `normalize()`, and `keep_chunk()` calls. The model is trained to recognize three broad categories of noise that the authors identify as "very popular patterns that keep occurring in all corpus" (Appendix A.1):

1. **Navigation bars and menus** at the top of documents, removed via a specialized few-shot prompt (Figure 10) that teaches the model to distinguish between actual navigation elements (e.g., "Home | Products | About Us") and document titles that happen to appear at the top.

2. **Button text, HTML elements, and links**, including both standalone URL lines (removed via `remove_lines()`) and URLs embedded within substantive text (removed via `normalize()`), trained using another specialized few-shot prompt (Figure 11).

3. **Footers and references** at the bottom of documents (copyright notices, contact details, navigation links), trained using a third few-shot prompt (Figure 12).

The training data for chunk-level programming is more complex than document-level because it requires the model to generate programs with correct line numbers and string arguments. The authors use few-shot prompting with LLAMA-3-70B-INSTRUCT, generating approximately 57K annotated examples (52K train, 5K validation). The few-shot prompts include carefully constructed examples demonstrating when to use `remove_lines()` versus `normalize()` (the former for whole-line noise, the latter for inline noise) and when to use `untouch_doc()`/`keep_chunk()` for already-clean content.

An important practical detail: the authors initially attempted to use a single unified prompt with LLAMA-3.1-405B-INSTRUCT to handle all noise types simultaneously, but found this "lead to aggressive removal of the original document, often making the document less coherent" (Appendix A.1). They ultimately used separate specialized prompts for each noise type and merged the resulting programs, keeping only the head and tail portions of the 405B model's output (following the approach of FinGPT, Luukkonen et al., 2023) and combining them with the 70B model's more conservative programs. This hybrid approach reflects a practical engineering insight: larger models can be *too* aggressive in their cleaning, and constraining their output scope produces better results.

After chunk-level processing, the refined chunks are reassembled into the final document. The chunk-level refining model also achieves strong performance even at small scales. Table 4 reports F1 scores of 75.2% for TLM-XS (0.3B), 75.6% for TLM-S (0.7B), and 77.3% for TLM-M (1.7B), showing modest scaling benefits.

**Why two stages rather than one:** The progressive design is essential because document-level filtering reduces the total data volume that needs fine-grained processing, making the more expensive chunk-level stage (which requires splitting each document, processing multiple chunks per document, and reassembling) computationally tractable. Without the document-level filter, the chunk-level stage would need to process every noisy document, including many that should be dropped entirely. The document-level stage also handles the most extreme cases (completely useless documents) with a simple binary decision, leaving the more nuanced within-document refinement to the chunk-level stage.

#### Model Adaptation: Training Small LMs to Generate Refinement Programs

The paper's approach to model adaptation (Section 2.3, Figure 3) addresses a critical challenge: "it is generally difficult for base models to directly generate PROX programs. In fact, even for the most powerful post-trained LLMs, generating custom API calls is relatively challenging at the current stage." The solution is a two-phase process: **synthesize training data using strong LLMs**, then **fine-tune small base models on that data**.

**Phase 1: Seed Data Synthesis.** The authors randomly sample documents from the target pre-training corpus (the same corpus that will later be refined at scale). For these seed documents, they use LLAMA-3-70B-INSTRUCT to annotate the correct refinement programs. The annotation process differs by stage:

For **document-level** annotation, the model is given the educational scoring prompt and format scoring prompt (Figure 9) and asked to produce both a score justification and a final score. The scores are then converted to keep/drop decisions using the relaxed filtering criteria (Equation 2 above). The program is synthesized as simply `drop_doc()` or `keep_doc()` based on the decision. This yields approximately 51K annotated examples, with 5K held out for validation.

For **chunk-level** annotation, the process is more involved. The authors use three separate few-shot prompting strategies, each targeting a specific noise pattern (navigation bars, URLs/HTML elements, footers). The prompts (Figures 10–12) provide carefully constructed examples showing:
- When to use `remove_lines(start, end)` for contiguous noisy lines
- When to use `normalize(source, target)` for inline noise embedded within otherwise useful lines
- When to use `untouch_doc()`/`keep_chunk()` for clean content that needs no modification

The prompts explicitly warn against common failure modes. For example, the navigation bar prompt instructs: "You must not mistakenly decide that title of the page is navigation bar and remove it. When the whole line is navigation bar, call `remove_lines`; if the line contains other information, call `normalize` to remove part of it." The URL removal prompt warns: "do not remove text together with http." These guardrails are critical because the annotated data will be used to train the refining model, and systematic annotation errors would propagate to all downstream refinement.

After collecting programs for each noise type, the authors merge them and apply grammar checking to ensure syntactic correctness. They also experimented with using the more powerful LLAMA-3.1-405B-INSTRUCT but found its programs were too aggressive, so they only kept the head and tail portions (following FinGPT's approach). The final merged dataset contains approximately 57K examples, with 5K for validation.

A crucial design choice: **this data collection is performed only once, and all base models (across different sizes, architectures, and target corpora) are adapted using the same curated data** (Section 2.3). The paper states explicitly: "this data collection is performed only once, and all base models are adapted with the same curated data." This means the annotation cost is amortized across all downstream uses—a one-time investment of LLAMA-3 inference that enables training arbitrarily many small refining models.

**Phase 2: Supervised Fine-Tuning.** The base models are small decoder-only transformers (TLM-XS at 354M parameters, TLM-S at 759M, TLM-M at 1.74B) that have been pre-trained on approximately 26B tokens of raw unrefined data. These models serve as both the starting point for adaptation and the experimental baseline.

Fine-tuning uses full-parameter supervised learning (no parameter-efficient methods like LoRA) with the following configuration (Appendix A.2):
- Framework: llama-factory (Zheng et al., 2024)
- Training epochs: 3–5
- Batch size: 64
- Learning rate schedule: cosine decay from 1e-5 to 1e-6
- The same hyperparameters are used for all adaptation tasks without further tuning

The paper notes that "base model convergent quite fast on these tasks, thus we do not apply a further tuning over hyper-parameters, and keep the same training configurations for all the adaptation tasks." This suggests the task is relatively easy for the models to learn—the constrained program space and clear patterns in the training data make for rapid convergence.

**Evaluation metrics for the adaptation tasks** (Appendix A.3):

For document-level refinement, performance is measured using the F1 score treating it as binary classification (keep vs. drop):

$$\text{F1} = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}$$

where:

$$\text{Precision} = \frac{\text{TP}}{\text{TP} + \text{FP}}, \quad \text{Recall} = \frac{\text{TP}}{\text{TP} + \text{FN}}$$

with True Positives being documents correctly identified as "keep," False Positives being documents incorrectly kept (should have been dropped), and False Negatives being documents incorrectly dropped (should have been kept).

For chunk-level refinement, the paper recognizes that evaluating normalization operations is "rather hard," so it uses only line removal accuracy via a line-wise F1 score. This is computed by comparing the set of predicted noisy line indices with the set of labeled noisy line indices:

$$\text{TP} = |\text{Predicted Noisy Lines} \cap \text{Actual Noisy Lines}|$$

$$\text{FP} = |\text{Predicted Noisy Lines} \setminus \text{Actual Noisy Lines}|$$

$$\text{FN} = |\text{Actual Noisy Lines} \setminus \text{Predicted Noisy Lines}|$$

The F1 score is then computed using the standard formula. This metric captures both precision (are the lines we removed actually noisy?) and recall (did we find all the noisy lines?).

Table 4 reports the adaptation results: document-level F1 scores range from 81.3% (TLM-S) to 83.7% (TLM-M), and chunk-level F1 scores range from 75.2% (TLM-XS) to 77.3% (TLM-M). The scaling trend is positive but modest—roughly 1–2 percentage points of improvement when increasing model size 5× (from 350M to 1.7B parameters). This modest scaling validates the core premise that **small models suffice for these pattern-recognition tasks**.

**Why fine-tune rather than few-shot prompt:** The paper does not directly compare fine-tuning to few-shot prompting for the refining models, but the motivation is implicit. The refining models need to process billions of tokens at scale—few-shot prompting would require including exemplars in every inference call, dramatically increasing the prompt length (and thus inference cost). Fine-tuning bakes the task knowledge into the model weights, enabling zero-shot inference on each document with minimal prompt overhead. Additionally, the constrained program space means that fine-tuning can achieve higher reliability than few-shot prompting, which is critical when processing web-scale data where errors propagate to downstream training.

#### Large-Scale Inference Architecture

Once the refining models are trained, they must be applied to the entire pre-training corpus, which typically contains tens to hundreds of billions of tokens. The inference architecture (Appendix A.4) is designed for throughput and parallelism.

**Infrastructure:** The pipeline uses Datatrove (Penedo et al., 2024c) for efficient data splitting and loading across workers, combined with vLLM (Kwon et al., 2023) for high-throughput language model inference. The workers correspond to individual GPUs—since the refining models are small (0.3B–0.7B parameters), they fit on a single GPU without tensor parallelism.

**Document chunking for chunk-level stage:** Algorithm 1 (Appendix A.4) describes the chunk splitting procedure in detail. Each document is processed line by line, with lines accumulated into the current chunk until adding the next line would exceed the context window. The window size is set to approximately 1,500 words rather than tokens for efficiency (counting tokens precisely would require running the tokenizer on every line, which is expensive at scale). When a chunk is full, it is saved and a new chunk begins. Lines that individually exceed the window size are flagged as "skipped" and not processed—they are presumably extremely long lines (e.g., minified JavaScript) that would not contribute useful training signal anyway.

**Computational overhead:** The paper provides detailed FLOPs estimates in Appendix E.3. The inference FLOPs for processing a corpus of `$D_{\text{raw}}$` tokens with a refining model of `$N_{\text{refine}}$` parameters at the document-level stage is:

$$C_{\text{doc}} \approx 2 \cdot N_{\text{refine}} \cdot D_{\text{raw}}$$

where the factor of 2 comes from the standard Transformer inference FLOPs approximation (2ND for each forward pass), and `$D_{\text{output}}$` (the output tokens from the model) is assumed negligible compared to the input. After document-level filtering, a reduced corpus of `$D_{\text{doc}}$` tokens remains for chunk-level processing:

$$C_{\text{chunk}} \approx 2 \cdot N_{\text{refine}} \cdot D_{\text{doc}}$$

The total inference overhead is therefore:

$$C_{\text{PROX}} = C_{\text{doc}} + C_{\text{chunk}} \approx 2 \cdot N_{\text{refine}} \cdot (D_{\text{raw}} + D_{\text{doc}})$$

For the concrete example in Section 4.2: using the TLM-XS refining model (354M parameters) on the RedPajama-V2 corpus (~60B raw tokens, reduced to ~19B after document-level filtering), the total inference overhead is approximately `$C = 5 \times 10^{19}$` FLOPs, which is equivalent to training an additional 12B tokens on TLM-S (759M parameters) or 5B tokens on TLM-M (1.74B parameters).

The paper then makes a critical efficiency argument (Section 4.2, Figure 8): as the pre-training model size increases, the relative overhead of PROX inference decreases because (a) the refining model size stays small and fixed, while (b) the pre-training FLOPs scale with model size. For the 0.7B model, the total FLOPs when using PROX are already *lower* than without it (Figure 8 shows "Train + Infer FLOPs" of 0.69 vs. 0.72 × 10^20 for comparable downstream performance), and for the largest 1.7B model, the paper reports achieving comparable performance "with only 58% of the total FLOPs." This demonstrates that PROX becomes **more, not less, cost-effective as model scale increases**—a crucial property for practical adoption.

**Why this matters:** The standard objection to model-based data refinement is that the inference overhead negates any training efficiency gains. The paper's FLOPs analysis directly addresses this: the overhead is one-time and amortized over all training steps, the refining models are much smaller than the models being trained, and the relative cost decreases with scale. This shifts PROX from an interesting academic exercise to a practically viable technique for large-scale LLM training.

## 4. Key Insights and Innovations

### Innovation 1: Reframing Data Refinement as a Program Generation Task — Making Small Models Sufficient for a Large-Model Problem

The field's dominant assumption has been that improving pre-training data quality with language models requires either (a) using powerful LLMs as quality classifiers for filtering (LLAMA-3's approach, QuRating, MATES) or (b) using powerful LLMs to generate or rewrite training data entirely (PHI series, INSTRUCTIONLM, COSMO). Both approaches tie data quality improvement to **model scale**: better data requires running larger, more expensive models at inference time. PROX breaks this assumption.

The conceptual move is to recognize that data refinement doesn't require generating new text — it requires **recognizing patterns and specifying operations**. By constraining the output space to a small vocabulary of pre-defined function calls (`remove_lines(0, 5)`, `normalize("noisy", "clean")`, `drop_doc()`), the task transforms from "rewrite this document to be higher quality" (a generative problem requiring broad language understanding) to "identify which lines contain noise patterns and which strings should be replaced" (a pattern recognition problem with structured, verifiable output). This reframing is what makes small models viable: Table 4 shows that a 0.3B parameter model achieves 82.6% F1 on document-level refinement, and the gap between a 0.3B and 1.7B refining model is only ~3 percentage points in downstream pre-training performance (Figure 5, all producing roughly +2% gains over raw data).

This is not an incremental improvement over prior model-based filtering — it's a **fundamentally different task formulation**. Data selection methods like QuRating and MATES make binary keep/drop decisions at the document level. PROX's program generation formulation enables fine-grained, within-document operations (removing specific line ranges, normalizing inline strings) that selection methods cannot express. The results quantify this gap: PROX-D (document-level only, which is comparable to selection methods) achieves 43.5% average accuracy (Table 2), while the full PROX-D+C pipeline (adding chunk-level programming) reaches 44.6%, demonstrating that the additional expressivity of programmatic operations provides gains beyond what selection alone can achieve.

The significance extends beyond performance: this reframing implies that **the computational cost of data refinement can be decoupled from model scale**. The refining model can remain small (0.3B–0.7B) while the pre-trained model scales to arbitrary size, meaning the relative overhead of refinement decreases as training scale grows (Figure 8). This is the opposite of synthesis-based approaches, where generating better data requires running larger models (MISTRAL-7B, MISTRAL-8x7B) at greater cost.

### Innovation 2: The Two-Stage Progressive Refinement Architecture as a Quality-Quantity Tradeoff Mechanism

Prior work on data preprocessing treats filtering as a single decision: either keep the document (with some quality threshold) or discard it. The FineWeb-Edu pipeline, for instance, retains only documents with educational score ≥ 2, keeping less than 9% of the original FineWeb tokens. This is an **implicit quality-quantity tradeoff**: stricter filtering improves average quality but reduces data volume, potentially losing valuable training signal.

PROX's two-stage architecture (document-level filtering followed by chunk-level refinement) reconfigures this tradeoff by introducing **rehabilitation** alongside **rejection**. Documents that would be borderline under strict filtering (e.g., Edu Score = 2, which FineWeb-Edu would discard) can be kept if they have good formatting (Format Score ≥ 4), and then further improved at the chunk level by removing navigation bars, footer links, and inline noise. This means documents that contain substantive content embedded in web formatting noise — common on forums, documentation sites, and blogs — are salvaged rather than discarded.

The evidence for this insight is in Table 6: models trained on PROX-filtered data match FineWeb-Edu's performance (45.2% average accuracy) while retaining over 3× more tokens (28% vs. 9% kept ratio). This means the model sees more diverse training data without quality degradation. The chunk-level stage is the enabler: it removes the specific noisy elements that would otherwise contaminate training (navigation bars, URLs, footers) while preserving the substantive text. The case studies in Table 33 make this concrete — a document about biochemistry that includes a navigation header and a Google Scholar link is not discarded (as strict filtering might do); instead, the header is removed, the link is normalized, and the educational content is preserved.

This insight is significant because it changes the framing of data preprocessing from a **filtering problem** (remove bad documents) to a **refinement problem** (improve documents to make them usable). It suggests that the community's focus on increasingly sophisticated filtering criteria (educational scores, perplexity thresholds, influence functions) may be targeting the wrong objective — the goal should not be to find the perfect keep/drop boundary but to build systems that can extract value from imperfect documents through targeted cleaning.

### Innovation 3: Demonstrating That Data Refinement Compute Can Substitute for Pretraining Compute — With Quantified Efficiency Ratios

The paper provides one of the first systematic demonstrations that **investing FLOPs in data refinement can yield better returns than investing the same FLOPs in additional pretraining**. This is not a theoretical claim — it's empirically quantified across multiple scales and domains.

The most striking evidence comes from the math continual pre-training experiments (Table 5, Figure 1). LLEMMA-7B, based on CODELLAMA-7B, requires 200B tokens of continual pre-training on math data to reach 50.9% average accuracy. PROX, also starting from CODELLAMA-7B, achieves 49.4% average accuracy with only 10B tokens of refined data — a **20× reduction in training tokens**. The PROX inference overhead for refining those 10B tokens is a one-time cost that is dwarfed by the savings from not training on the additional 190B tokens. This is the fundamental efficiency argument: refinement FLOPs are paid once and amortized over all downstream training, while pretraining FLOPs scale linearly with every additional token.

The general-domain experiments reinforce this pattern at smaller scale. Figure 1 (left panel) shows that a 1.7B model trained on PROX-refined FineWeb reaches comparable performance to a model trained on original FineWeb in roughly 1/30th the training steps — the PROX curve rises steeply and plateaus at higher accuracy with far fewer FLOPs. And Figure 8 makes the scaling argument explicit: for a 1.7B model, using PROX achieves performance comparable to training on raw data with "only 58% of the total FLOPs." The inference overhead is real (5 × 10^19 FLOPs for processing 60B tokens, per Appendix E.3), but it's smaller than the pretraining FLOPs it saves.

What distinguishes this from prior work on data selection efficiency (e.g., MATES, DSIR) is the **magnitude and domain-generality** of the efficiency gains. MATES reports that its data selection approach improves efficiency, but PROX's 20× reduction in a controlled head-to-head comparison (same base model, same architecture, same evaluation) against a well-known strong baseline (LLEMMA) is a substantially stronger claim. Moreover, the efficiency gains appear across five different corpora (RedPajama-V2, C4, FineWeb, FineWeb-Edu, DCLM) and in both general and domain-specific pre-training, suggesting this is not an artifact of a particular dataset's noise characteristics.

This contribution reframes the scaling conversation: the question is not "how much pretraining compute can we afford?" but "how should we allocate a fixed compute budget between data refinement and pretraining?" The paper's FLOPs analysis (Appendix E.3) provides the mathematical framework for making this tradeoff, showing that refinement becomes more favorable as pre-training model size increases, since the refining model size stays fixed.

### Innovation 4: Exposing the Failure of Universal Heuristics Through Domain Transfer — A Diagnostic Finding

One of the paper's most instructive results is a negative one: applying the same rule-based filtering that works (modestly) on general-domain web data to the mathematical domain **degrades performance**. Table 5 shows that for TINYLLAMA-1.1B, continual pre-training on raw OpenWebMath achieves 21.5% average accuracy, but applying rule-based filtering drops this to 18.4% — a 3.1 percentage point decrease. The paper explicitly interprets this:

> "This finding implies that there are no universal workable heuristics for all domains, highlighting the demands for automated pipelines just like PROX."

This is a diagnostic finding with implications beyond the paper's own method. It explains a pattern visible in prior work: why data preprocessing pipelines that work well for general web text (C4 rules, Gopher rules) often need extensive re-tuning when applied to code, math, or multilingual data. The noise patterns are different — math content from arXiv and Stack Exchange has different formatting artifacts than general web pages from CommonCrawl. Heuristics designed for one noise distribution fail on another.

What makes this finding significant is that it's not obvious a priori. One might reasonably expect that rules like "remove lines containing URLs" or "drop documents with high symbol-to-word ratio" would transfer across domains — after all, URLs are URLs regardless of whether they appear on a math forum or a news article. The degradation suggests that heuristics optimized for one domain inevitably encode assumptions about what "good" and "bad" content looks like, and those assumptions don't generalize.

PROX's solution is not to build better heuristics but to abandon the heuristic paradigm entirely — replacing hand-crafted rules with learned, per-example program generation. Because the refining model is trained on seed data from the target corpus, it learns the domain-specific noise patterns automatically. The math-domain results in Table 5 validate this: PROX-D+C improves over the raw corpus baseline by 11.0% for TINYLLAMA-1.1B, 14.6% for LLAMA-2, 20.3% for CODELLAMA, and 7.6% for MISTRAL, while the rule-based approach degrades performance. This is strong evidence that the automated approach is not just more convenient than heuristic design — it's more effective.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The primary benchmark is MATH (Hendrycks et al., 2021), a dataset of high-school competition-level mathematics problems. The paper uses the specific train/test split from Lightman et al. (2022): 12,000 training questions and 500 test questions. This benchmark is chosen because test-time compute is expected to help most when the model already possesses the necessary knowledge and the challenge lies in drawing complex, multi-step inferences—mathematical reasoning fits this profile precisely, unlike tasks requiring novel factual recall.

- **Base model(s).** All primary experiments use PaLM 2-S* (Codey) (Anil et al., 2023), which the authors argue is "representative of the capabilities of many contemporary LLMs" and sits in a useful performance regime: non-trivial MATH accuracy (roughly 10–19% pass@1 depending on prompt and sampling configuration) but far from saturation, leaving substantial room for test-time compute to demonstrate improvements. For the FLOPs-matched comparison (Section 7), a second model with approximately 14× more parameters is introduced as the pretraining-scaled baseline. This larger model uses greedy decoding with no additional test-time compute, making it a pure "scale pretraining instead" comparison point.

- **Metrics.** The primary metric throughout is MATH test accuracy (%)—the fraction of the 500 test questions for which the selected final answer matches the ground truth, as determined by the grading function released by Lightman et al. (2022) (Appendix G). When analyzing difficulty-dependent behavior, the paper disaggregates this metric and reports accuracy within each of the five difficulty quintiles separately. For certain ablation analyses (e.g., comparing verifier types), the paper also reports accuracy at specific generation budgets.

- **Baselines.** The paper compares against several distinct baselines, each serving a different comparison purpose:
  1. **Majority voting**: select the most common final answer among N sampled solutions, with no learned verifier. This is the simplest test-time compute baseline and isolates the value of the verifier signal.
  2. **ORM best-of-N weighted**: score N complete solutions with an Outcome Reward Model (trained to predict final-answer correctness) and apply best-of-N weighted selection (Li et al., 2023), where all solutions arriving at the same final answer have their scores summed, and the answer with the greatest total score is selected.
  3. **PRM best-of-N weighted**: the same selection mechanism but using the Process Reward Model's step-level scores aggregated via the last-step method. This is the primary comparison point, as it represents using the strongest verifier without any guided search—just independent parallel sampling.
  4. **Parallel sampling** (for revisions): generate N independent solutions from the revision model and select the best via either the verifier or majority voting. This isolates the value of sequential revision from the value of parallel diversity.

- **Generation budget / compute accounting.** The universal unit of test-time compute is a "generation"—one complete sampled answer from the base LLM. For best-of-N and standard beam search, the budget simply equals the number of beams or samples N. For lookahead search with k lookahead steps, the paper accounts for the additional rollout computation by costing it at N × (k+1) generations, ensuring fair comparison at equal total generation counts. Budgets are typically swept across powers of 2, from 2⁰ to 2⁹ (1 to 512 generations). For the FLOPs-matched comparison, the paper uses standard approximations from the scaling laws literature: pretraining FLOPs ≈ 6ND_pretrain, inference FLOPs ≈ 2ND_inference, where N is non-embedding parameter count. When comparing a smaller model with extra test-time compute against an M× larger model, the smaller model's inference budget is scaled to match total FLOPs, accounting for both pretraining savings and increased per-token inference cost at larger scale.

- **Cross-validation / statistical protocol.** To avoid the circularity of selecting the best strategy and evaluating it on the same data, the paper uses two-fold cross-validation within each difficulty bin on the 500-question test set. The best-performing strategy (e.g., which search algorithm, which sequential-to-parallel ratio) is selected on one fold and evaluated on the other, and vice versa, with results averaged across folds. Difficulty bins are constructed using 2048 samples per question, binned into five quintiles based on either oracle pass@1 (ground-truth correctness) or predicted pass@1 (using the PRM's final-answer score as a proxy). This cross-validation protocol is applied for both the search and revision compute-optimal scaling experiments (Figures 4 and 8).

### Main Quantitative Results

#### Search Against PRM Verifiers (Section 5)

The headline finding from the search experiments is that **the optimal search algorithm depends crucially on problem difficulty**, and that a compute-optimal policy selecting the best method per difficulty bin can match the performance of standard best-of-N using up to 4× less test-time compute.

**Aggregate comparison across all questions (Figure 3, left).** When averaged across all 500 MATH test questions with a maximum budget of 256 generations, the results reveal non-monotonic behavior:

- At low budgets (2–8 generations), beam search with M = 4 significantly outperforms PRM best-of-N weighted. At 4 generations, beam search achieves approximately 27% accuracy versus roughly 16% for best-of-N weighted—a gap of ~11 percentage points. This demonstrates that when the compute budget is tight, guided search over the solution space is more efficient than independent parallel sampling.

- At high budgets (64–256 generations), this advantage reverses. Beam search performance flattens and falls slightly below best-of-N weighted, which continues to improve. At 512 generations, best-of-N weighted reaches approximately 38% accuracy while beam search (M = 4) plateaus around 34%. This degradation at high budgets is attributed to **over-optimization of the PRM**—search finds solutions that score highly under the verifier but are actually incorrect.

- Lookahead search (both k = 1 and k = 3) generally underperforms all methods at the same generation budget due to its higher per-step cost, which reduces the effective number of beams explored. The 3-step lookahead variants converge to similar performance as other methods at very high budgets but never surpass them.

- Majority voting substantially trails all verifier-based methods, reaching only about 29% at 512 generations, confirming that learned verification provides significant signal beyond simple answer consensus.

**Difficulty-bin analysis (Figure 3, right).** The most striking and consequential result comes from disaggregating performance by difficulty quintile. The paper shows beam search (M = 4) versus PRM best-of-N weighted at four budget levels (4, 16, 64, 256 generations) across the five bins:

- **Bin 1 (easiest, highest base model pass@1):** Beam search *degrades* with increasing budget—accuracy drops from roughly 78% to 77% as budget increases from 4 to 256 generations—while best-of-N weighted improves from 68% to 88%. This is the clearest evidence of PRM over-optimization: on easy problems where the base model already produces correct solutions at a reasonable rate, aggressive search finds solutions that exploit the verifier's imperfections rather than genuinely correct ones, while simple parallel sampling with consensus-based selection continues to benefit from more draws.

- **Bin 2:** Beam search improves modestly (roughly 14% → 32%) but best-of-N weighted improves faster (roughly 14% → 60%), maintaining a clear advantage at high budgets.

- **Bin 3:** The pattern flips—beam search consistently outperforms best-of-N weighted across all budgets, reaching approximately 34% vs. 23% at 256 generations. On medium-difficulty problems, the PRM's guidance genuinely helps navigate toward correct solutions that random sampling would miss.

- **Bin 4:** Beam search shows its strongest relative advantage, reaching roughly 17% vs. 10% for best-of-N at 256 generations. These are problems where the model rarely produces correct answers by chance (pass@1 ~ 5–10%), and guided search meaningfully concentrates probability mass on the small fraction of achievable solutions.

- **Bin 5 (hardest):** Both methods hover near 1–3% regardless of budget. No amount of test-time compute helps when the base model essentially never produces correct solutions—there is nothing for the verifier to find.

This difficulty-dependent crossover—beam search hurting easy problems but helping medium-difficulty ones—is the central empirical finding that motivates the compute-optimal allocation policy.

**Compute-optimal search results (Figure 4).** By selecting the best search strategy per difficulty bin at each budget level (using the cross-validation protocol), the paper demonstrates substantial efficiency gains:

- At 16 generations, compute-optimal search (oracle difficulty bins) achieves approximately 27% accuracy, roughly matching PRM best-of-N weighted at 64 generations—a 4× reduction in required compute. This is the source of the "more than 4× better efficiency" claim in the executive summary.

- At 256 generations, compute-optimal oracle reaches approximately 39.5%, surpassing PRM best-of-N weighted at the same budget (roughly 37%).

- Critically, the compute-optimal policy using **predicted difficulty bins** (where difficulty is estimated using the PRM's average final-answer score rather than ground-truth labels) tracks the oracle version closely, particularly at lower budgets. The two curves "largely overlap" per the authors, with the predicted version reaching approximately 37% at 256 generations. This is essential for practical deployment, as it means the system works without access to ground-truth answers.

- Both compute-optimal variants consistently outperform ORM best-of-N weighted (which peaks around 34% at 512 generations) and majority voting (around 29%), demonstrating that the PRM's richer training signal provides value even when the optimal strategy is per-difficulty adaptation rather than per-question optimization.

**PRM vs. ORM (Appendix F, Figure 14).** At large sample counts (2048), PRM best-of-N weighted achieves approximately 40% accuracy versus roughly 35% for ORM best-of-N weighted and roughly 30% for majority voting. The gap between PRM and ORM widens with the number of samples, confirming that the step-level training signal produces a verifier with better scaling properties even when aggregated using only the last-step prediction.

#### Revision Model Results (Section 6)

The revision experiments demonstrate that **iteratively refining the model's own outputs (sequential sampling) modestly outperforms independent parallel sampling**, with the optimal sequential-to-parallel ratio again depending on problem difficulty.

**Revision model pass@1 trajectory (Figure 6, left).** Starting from approximately 18.2% pass@1 at step 1 (the first generated answer), the revision model's per-step accuracy improves to roughly 24–25% by steps 15–20, and remains in the 23–25% range out to 64 steps. This is notable because the model was trained with at most 4 previous incorrect answers in context—the fact that it continues to improve beyond step 4 and maintains elevated performance out to step 64 suggests it has learned a generalizable revision capability, not merely a pattern-matching behavior tied to its training horizon. The improvement is modest in absolute terms (~6–7 percentage points) but represents a roughly 35% relative improvement over the initial pass@1.

**Sequential vs. parallel comparison (Figure 6, right).** At a matched budget of 64 generations, the paper reports:

- Sequential (one chain of 64 revisions) + best-of-N weighted selection: approximately 41.5%
- Parallel (64 independent samples) + best-of-N weighted selection: approximately 39%
- Sequential + majority voting: approximately 38%
- Parallel + majority voting: approximately 35%

Sequential outperforms parallel by roughly 2.5 percentage points under the verifier and 3 percentage points under majority voting. The gap is modest but consistent, and the fact that sequential maintains an edge even under majority voting (which has no access to the revision history) suggests the benefit comes from genuinely better proposals, not just from the verifier having more context.

**The correct-to-incorrect reversion problem.** A significant practical issue is that approximately **38% of correct answers generated during a revision chain get "revised" back to incorrect answers** in the subsequent step. This occurs because the model was trained only on sequences where all in-context answers are incorrect (followed by a correct target), so it never learned the behavior of recognizing a correct answer and leaving it unchanged. The paper mitigates this by using majority voting or verifier-based selection across the entire chain—picking the best answer from any revision step rather than always taking the final one. This is a pragmatic patch, not a principled solution.

**Sequential-to-parallel ratio sweep (Figure 7).** A key experimental design is sweeping the ratio of sequential depth to parallel breadth for a fixed total budget of N = sequential_chains × max_revisions_per_chain. The results reveal:

- **Aggregated across all questions (Figure 7, left):** At 256 generations, the optimal ratio is around 2¹ to 2³ (meaning 2–8 sequential revisions per chain, with parallel chains making up the remainder), achieving approximately 43–44% accuracy. Fully parallel (leftmost point) yields approximately 40%, and fully sequential (rightmost point) yields approximately 42%. At lower budgets (8–32 generations), fully sequential is optimal—the curves are monotonically increasing with the sequential-to-parallel ratio. This suggests that when the total budget is small, it's better to invest in refining a single chain deeply rather than spreading across multiple shallow chains.

- **Per-difficulty breakdown (Figure 7, right, at 128 generations):**
  - **Bin 1 (easiest):** Performance is essentially flat across all ratios, around 90–92%. Easy problems are insensitive to allocation strategy—the model produces correct answers regardless.
  - **Bin 2:** Slight advantage for higher sequential ratios, approximately 63% at fully sequential vs. 58% at fully parallel.
  - **Bin 3:** A clear optimal ratio emerges at moderate sequential-to-parallel values (around 2¹ to 2³), reaching approximately 42% vs. 35% at the extremes. The curve shows a genuine interior optimum—neither extreme is best.
  - **Bin 4:** Similar inverted-U pattern, with the peak at a moderate ratio achieving roughly 18% vs. 14% at fully parallel.
  - **Bin 5:** All ratios produce roughly 2–3% accuracy. No allocation strategy helps on problems the model fundamentally cannot solve.

This difficulty-dependent pattern mirrors the search results: easy problems favor exploitation (sequential revision, local refinement), hard problems favor a mix of exploration (parallel diversity) and refinement, and impossible problems benefit from neither. The paper's compute-optimal revision policy exploits these patterns.

**Compute-optimal revision results (Figure 8).** Selecting the optimal sequential-to-parallel ratio per difficulty bin:

- At 64 generations, compute-optimal oracle achieves approximately 40%, matching parallel best-of-N weighted at 256 generations—another 4× improvement.
- At 256 generations, compute-optimal oracle reaches approximately 44%, compared to roughly 41% for best-of-N weighted and 37% for parallel-only.
- Compute-optimal with predicted difficulty bins performs slightly below oracle bins at high budgets (approximately 41% at 256 generations vs. 44% for oracle) but still substantially outperforms the parallel baseline.
- Notably, the parallel baseline appears to **plateau** around 36–37% at high budgets, while compute-optimal scaling continues to improve, suggesting that the gains from adaptive allocation compound at higher budgets rather than being a one-time offset.

#### FLOPs-Matched Comparison: Test-Time Compute vs. Pretraining Compute (Section 7)

This is the paper's most ambitious claim—that in a total-FLOPs-matched comparison, a smaller model with compute-optimal test-time strategies can outperform a ~14× larger model on problems within its capability range. The results are nuanced and sharply difficulty-dependent, as shown in Figure 9 and the bar charts in Figure 1.

**Revision model FLOPs-matched results (Figure 9, left; Figure 1, top-right bar chart):**

The key parameter is R = D_inference / D_pretrain, the ratio of total inference tokens to pretraining tokens. Three R values are tested: R ≪ 1 (0.16), R ≈ 1 (0.79), and R ≫ 1 (22). The paper reports relative advantages of the smaller model with compute-optimal revisions over the 14× larger model with greedy decoding:

- **Easy questions (bin 1):** +11.8% at R ≪ 1, +3.5% at R ≈ 1, and −11.9% at R ≫ 1. Test-time compute wins when inference volume is low (the pretraining savings from the smaller model dominate) but loses when inference volume is high (the larger model's per-token cost is outweighed by its better accuracy per query).
- **Medium questions (bins 2–3):** +27.8% at R ≪ 1, +16.7% at R ≈ 1, +5.4% at R ≫ 1. Test-time compute maintains an advantage across all R regimes for these questions.
- **Hard questions (bins 4–5):** +21.6% at R ≪ 1, a negative implied value at R ≈ 1 (not explicitly reported in the bar chart but visible in Figure 9 where the star for R ≈ 1 is above the scaling curve), and −37.2% at R ≫ 1.

At R ≪ 1, test-time compute **outperforms the larger model across all difficulty levels**. This is the regime most relevant for self-improvement pipelines where inference volume is low relative to the massive pretraining investment. At R ≫ 1 (high-throughput deployment), the case weakens substantially, with pretraining becoming clearly preferable on hard problems.

**PRM search FLOPs-matched results (Figure 9, right; Figure 1, bottom-right bar chart):**

The search-based approach shows weaker benefits than revisions:

- **Easy questions:** +19.1% at R ≪ 1, +2.2% at R ≈ 1, +2.0% at R ≫ 1. Test-time compute maintains a small advantage.
- **Medium questions:** 0.0% at R ≪ 1 (essentially tied), −35.3% at R ≈ 1, −30.8% at R ≫ 1.
- **Hard questions:** −3.6% at R ≪ 1, −35.3% at R ≈ 1, −52.9% at R ≫ 1.

The search-based approach is substantially weaker than revisions in the FLOPs-matched comparison, with large disadvantages on medium and hard questions at moderate-to-high R values. This is consistent with the earlier finding that search is most effective on medium-difficulty problems (Figure 3, right) but suffers from verifier over-optimization and cannot extract signal from near-impossible problems. Revisions, by modifying the proposal distribution itself, provide more robust gains.

**Figure 9 detail.** The line plots in Figure 9 show accuracy per difficulty bin as test-time compute scales for the smaller model (solid lines). The 14× larger model's greedy-decoding performance is plotted as horizontal lines at three x-axis positions corresponding to the three R values. Where the compute-optimal scaling line is above the horizontal line (star), test-time compute wins; where it's below, pretraining wins. On bin 1 (easiest, topmost line), the scaling line is above all three stars for revisions, showing universal advantage. On bin 5 (hardest, bottommost line), the scaling line is essentially flat near 0–5% and below all three stars, confirming that no amount of test-time compute helps on genuinely out-of-capability problems.

### Ablation Studies and Robustness Checks

- **PRM step-wise score aggregation strategy (Appendix E, Figure 13):** The paper compares three methods for combining the PRM's per-step predictions into a single solution score—taking the minimum across steps ("min"), taking the product ("prod"), and using only the final step's prediction ("last"). Contrary to prior work (Lightman et al., 2023; Wang et al., 2023) which found "min" to be best, this paper finds **"last" performs best**, achieving roughly 37% at 256 samples vs. 35% for "min" and 27% for "prod." The authors hypothesize that the discrepancy arises because their PRM is trained with soft Monte Carlo labels rather than binary correctness labels, which changes the per-step score distribution. An interesting consequence: using the last-step prediction effectively makes the PRM behave like an ORM at aggregation time, yet the PRM still outperforms a separately trained ORM (roughly 34% at 256 samples), suggesting that the step-level PRM training acts as a form of beneficial **representation learning**—the intermediate supervision improves the model's ability to assess final-answer correctness even when intermediate predictions aren't directly used.

- **PRM vs. ORM scaling (Appendix F, Figure 14):** The PRM consistently outperforms the ORM across all sample counts, with the performance gap widening at higher budgets. At 2048 samples, PRM best-of-N weighted reaches approximately 40% vs. ORM's 35%. This confirms that the Monte Carlo rollout training procedure produces a verifier with superior scaling properties, and the result is robust to aggregation method choice.

- **Revision model verifier choice (Appendix J, Figure 15a):** The base-LM PRM (trained on vanilla PaLM 2-S* outputs) underperforms a revision-specific ORM when scoring revision model outputs, with sequential + base-LM PRM achieving roughly 40% at 64 generations vs. sequential + revision ORM at roughly 42%. This confirms that **distribution shift** between the base model's and revision model's output distributions is a practical concern—the PRM's calibration degrades when applied to a different proposal distribution. However, even with the suboptimal base-LM PRM, sequential revisions still outperform the parallel baseline, showing the benefit is not purely an artifact of having a perfectly calibrated verifier.

- **Revision history in verifier context (Appendix J, Figure 15b):** The revision-specific ORM can optionally include previous revisions in its context when scoring a candidate answer. Including this history provides a small improvement over the no-history ablation (approximately 1–2 percentage points at 64 generations), but both variants—with and without history—outperform the parallel baseline. This indicates that the sequential sampling benefit is **not solely attributable to the verifier seeing more context** (which would be an unfair advantage in a parallel vs. sequential comparison); the proposal distribution itself is genuinely improved.

- **Oracle vs. predicted difficulty bins:** This is the critical robustness check for the entire compute-optimal framework. For search (Figure 4), the oracle and predicted bin curves "largely overlap," with the predicted version reaching approximately 37% at 256 generations vs. roughly 39.5% for oracle. For revisions (Figure 8), the gap is slightly larger at high budgets (approximately 41% for predicted vs. 44% for oracle at 256 generations). Both variants substantially outperform the parallel best-of-N baseline, confirming that the compute-optimal strategy works without ground-truth labels, though the predicted-difficulty approach slightly underperforms oracle at the highest budgets. This gap likely reflects noise in the difficulty estimation—some questions are mis-binned when using PRM score as a proxy for true difficulty, and the misclassification cost grows with budget since the optimal strategy differences between bins are larger at higher budgets.

- **Majority voting for revisions (Appendix B, Figure 10):** The sequential-to-parallel ratio trends observed with verifier-based selection are replicated when using simple majority voting as the selection mechanism: easy questions are insensitive to allocation ratio, hard questions show an optimal intermediate ratio, and fully sequential marginally outperforms fully parallel in aggregate. This replication under a different (and weaker) selection mechanism strengthens the finding that the benefit of sequential revisions comes from improved proposal quality, not from the verifier's ability to leverage revision context.

- **ReST<sup>EM</sup> revision model (Appendix K, Figure 16):** This is the paper's most informative negative result. An attempt to further optimize the revision model using ReST<sup>EM</sup> (Singh et al., 2024)—a reinforcement-learning-style procedure that collects on-policy rollouts and fine-tunes on successful trajectories—**substantially hurts performance** with sequential revisions. At 256 generations, fully sequential performance drops to approximately 33.5% compared to roughly 38.5% at the optimal ratio for the SFT-only revision model. The authors hypothesize that "on-policy data collection in ReST<sup>EM</sup> exacerbates spurious correlations in revision data, causing the model to fail to learn the revision task properly." This result is important because it demonstrates that the positive revision results are **fragile**—they depend on specific training choices (offline data construction, edit-distance-based pairing of incorrect and correct solutions) and do not trivially extend to more sophisticated training procedures. It also serves as a cautionary tale for self-improvement pipelines: naïvely training on the model's own outputs can degrade rather than improve performance.

- **PRM training data source:** The authors explicitly note that they found the PRM800k dataset (which contains GPT-4 generated solutions with human step-level labels from Lightman et al., 2023) to be "largely ineffective" for their PaLM 2 models, likely due to distribution shift between GPT-4 and PaLM 2 outputs. This motivated the Monte Carlo rollout training procedure described in Section 5.1 and Appendix D. This is not a formal ablation (it is reported as a qualitative observation rather than a controlled experiment), but it is an important practical finding: PRM training data must be matched to the target model's output distribution; borrowing labels from a different model family may not transfer.

### Critical Assessment

**Do the experiments support the claim that compute-optimal test-time scaling improves efficiency by more than 4× over best-of-N?**

The evidence is strong but conditional. For search, Figure 4 shows that compute-optimal scaling at 16 generations (roughly 27% accuracy) matches best-of-N weighted at 64 generations (roughly 27% accuracy)—a 4× reduction. For revisions, Figure 8 shows compute-optimal at 64 generations (roughly 40%) matching parallel best-of-N weighted at 256 generations (roughly 40%)—another 4×. These are clean, cross-validated comparisons at matched accuracy points.

However, three qualifications are necessary. First, the 4× figure is specific to the **lower-to-moderate budget regime**. At the highest budgets tested (256–512 generations), the efficiency gains narrow. For search, compute-optimal at 256 generations (roughly 39.5%) is only modestly above best-of-N weighted at 256 generations (roughly 37%), representing perhaps 20% efficiency improvement rather than 4×. For revisions with predicted difficulty bins, the gap at 256 generations shrinks to approximately 41% vs. 37%, representing roughly 30% improvement. The 4× figure should be understood as the maximum achievable gain in the tested budget range, not a uniform property across all budgets.

Second, the **difficulty estimation cost is not included** in any generation budget calculation. The predicted-difficulty approach requires generating 2048 samples per question and scoring them with the PRM—a cost that is comparable to or exceeds the largest test-time budgets being studied. The paper acknowledges this in Section 3.2 but explicitly excludes it from the budget accounting, meaning the reported 4× efficiency gains are computed after the (substantial) difficulty estimation cost has already been paid. In a deployment setting where difficulty must be estimated per-query, this cost would need to be amortized across many similar queries or replaced with a cheaper estimation method (e.g., a lightweight classifier trained on question text). Neither solution is demonstrated in the paper.

Third, the 4× figure is derived from **cross-validation on a 500-question test set split into five bins of ~100 questions each, further split by two-fold CV into ~50 questions per fold per bin**. The strategy selection (which search algorithm, which sequential-to-parallel ratio) is based on these small per-bin samples. The paper does not report confidence intervals, making it difficult to assess whether the observed differences in strategy performance at each budget-bin combination are statistically reliable. With 50 questions per fold, a difference of a few percentage points could easily arise from sampling noise rather than genuine strategy superiority.

**Do the experiments support the claim that test-time compute with a smaller model can outperform a 14× larger model?**

The claim is supported with sharp, well-characterized conditions, which is to the paper's credit. At R ≪ 1 (low inference-to-pretraining token ratio), the smaller model with compute-optimal revisions outperforms the 14× larger model on easy questions (+11.8%), medium questions (+27.8%), and even hard questions (+21.6%). This is the strongest evidence and is directly relevant to self-improvement and data generation pipelines where inference volume is low.

However, the comparison has a significant design asymmetry that favors test-time compute. The 14× larger model uses **greedy decoding only**—no majority voting, no best-of-N, no verifier-based selection, no revisions. This is a deliberate choice to isolate the effect of scaling pretraining alone, but it creates an apples-to-oranges comparison: the smaller model gets sophisticated inference-time strategies while the larger model gets the simplest possible decoding. A fairer comparison would give the larger model some test-time compute budget as well, even if modest (e.g., best-of-4 or best-of-8). The paper's own results suggest that even simple best-of-N sampling provides substantial gains (Figure 3), so the 14× larger model's performance with best-of-8 would likely be meaningfully higher than its greedy-decoding performance. The reported advantages of test-time compute over pretraining may therefore be **upper bounds** that would shrink or reverse against a more competitive pretraining baseline.

Additionally, the 14× larger model uses parameter-only scaling with fixed training data, following the LLaMA paradigm rather than Chinchilla-optimal training (where both parameters and data are scaled equally). The paper acknowledges this in Section 7 and leaves compute-optimal pretraining comparison to future work. A Chinchilla-optimal larger model would likely be a stronger baseline, further narrowing the reported advantages.

**Do the experiments support the claim that efficacy depends critically on prompt difficulty?**

This is the **most robust finding in the paper** and is strongly supported by multiple independent lines of evidence. The difficulty-bin analyses for search (Figure 3, right), revisions (Figure 7, right), and the FLOPs-matched comparison (Figure 9) all show qualitatively different—and sometimes opposite—effects of the same strategy at different difficulty levels. Beam search hurts easy problems (Bin 1 degrades from ~78% to ~77% as budget increases) while helping medium problems (Bin 3: 18% → 34% at 256 generations). Sequential revisions provide essentially no benefit on hard problems (Bin 5: flat at 2–3% across all ratios) but clear benefits on medium problems (Bin 3: 42% at optimal ratio vs. 35% at extremes). These are not subtle effects—they represent strategy × difficulty interactions that would be completely obscured in aggregate analysis. The replication of this pattern across search algorithms, revision strategies, and selection mechanisms (including simple majority voting, Figure 10) makes this finding highly reliable.

**What experiments are missing?**

Several experiments would have substantially strengthened the paper's conclusions:

1. **Giving the 14× larger model some test-time compute budget.** Even best-of-4 or best-of-8 sampling with the same PRM would create a much stronger baseline for the FLOPs-matched comparison. The current comparison stacks the deck in favor of test-time compute by pitting a sophisticated inference strategy against greedy decoding.

2. **Combining PRM search with the revision model as the proposal distribution.** The paper studies search (Section 5) and revisions (Section 6) as independent mechanisms, but never applies beam search to revision model outputs or uses the PRM to guide which revisions to pursue. The two mechanisms have complementary strengths (search helps medium problems, revisions help easy problems), and their combination could yield gains beyond either approach alone. The authors acknowledge this gap in Section 8, but it remains a significant missing experiment.

3. **Testing on a second benchmark beyond MATH.** All results are on a single 500-question test set of high-school competition math problems. It is unclear whether the difficulty-dependent patterns (beam search over-optimizing on easy problems, revisions helping easy problems but not hard ones) would generalize to code generation, logical reasoning, or scientific QA tasks. The paper's claim that the model is "representative of many contemporary LLMs" cannot be verified without replication on at least one other model family or task domain.

4. **An ablation on the number of difficulty bins.** The five-quintile discretization is coarse and arbitrary. Would more bins (e.g., deciles) improve the compute-optimal policy by enabling finer-grained strategy selection, or would the smaller per-bin sample sizes in cross-validation lead to noisier strategy estimates and worse performance? This ablation would characterize the robustness of the approach to the binning granularity.

5. **Confidence intervals on the compute-optimal scaling curves.** With only 500 test questions (50 per fold per bin), sampling variance could be substantial. Reporting bootstrap confidence intervals would allow readers to assess whether the observed differences between strategies at specific budget-bin combinations are statistically meaningful or consistent with noise.

**What genuine weaknesses exist?**

The **difficulty estimation cost** is the most significant practical limitation that the paper does not resolve. Generating 2048 samples and scoring them with the PRM to bin a single question is more expensive than the test-time budgets being optimized. The paper frames this as an exploration-exploitation tradeoff and suggests future work on cheaper difficulty estimation, but the current method's cost undermines the practical significance of the 4× efficiency claims. If difficulty estimation costs 2048 generations per question, and the compute-optimal strategy saves 48 generations (using 16 instead of 64), the net savings are negative until many similar questions are processed with the same difficulty estimate.

The **single benchmark, single model family** limitation is significant. The paper's conclusions may be specific to PaLM 2-S\*'s particular error patterns, calibration properties, and MATH benchmark characteristics. Without evidence of transfer, the paper demonstrates a proof of concept rather than a general principle.

The **500-question test set** limits statistical power, particularly for per-bin analysis where only ~100 questions are available per bin (50 per cross-validation fold). The observed strategy rankings at specific budget-bin combinations may not generalize to different random splits or to a held-out test set.

The **revision model's 38% correct-to-incorrect reversion rate** is a fundamental limitation that the paper only partially addresses. The mitigation (selecting the best answer from any revision step using voting or verifier scoring) works post-hoc but does not solve the underlying problem—the model does not know when to stop revising. This limits the benefit of deep sequential chains, as later revisions become increasingly likely to corrupt earlier correct answers.

## 6. Limitations and Trade-offs

### Assumption: Difficulty Can Be Estimated Cheaply Enough to Be Practical

The entire compute-optimal framework rests on the ability to estimate prompt difficulty *before* deciding how to allocate the inference budget. The paper's method for doing so—generating 2048 samples per question and averaging either ground-truth correctness (oracle) or PRM final-answer scores (predicted)—is extraordinarily expensive. At 2048 samples per question, the difficulty estimation step alone consumes more compute than the largest test-time budgets studied (256–512 generations). The authors acknowledge this explicitly in Section 3.2:

> "estimating difficulty in this way still incurs additional computation cost during inference... our experiments do not account for this cost largely for simplicity"

This is a significant gap. The reported `4×` efficiency gains over best-of-N are computed *after* difficulty is known, without amortizing the cost of learning it. In a realistic deployment, the total cost would be difficulty estimation + strategy execution, and the former could dominate the latter. For a single query under the `4×` scenario (using 16 generations of compute-optimal search to match 64 generations of best-of-N), the difficulty estimation overhead of 2048 generations would make the total cost `2048 + 16 = 2064` generations—far more than the baseline 64 generations. The `4×` savings only materialize when the difficulty estimation cost is amortized across many similar queries (e.g., a batch of questions of similar difficulty where the allocation policy, once determined, applies to all), but the paper does not analyze this amortization or establish how many queries are needed for the approach to break even.

The paper does suggest future work on training models to predict difficulty directly from the question text (Section 8), or using the PRM's score distribution from a small initial sample as a cheap difficulty signal. However, no such model is developed or evaluated. The predicted-difficulty bins used in the paper (which replace ground-truth labels with PRM scores) still require the full 2048 samples per question. Until a genuinely cheap difficulty estimator is demonstrated, the `4×` figure should be understood as an **upper bound on achievable efficiency** conditional on having free access to difficulty information, rather than a realized deployment gain.

---

### Hard Problems Remain Essentially Unsolved

Across all methods—search, revisions, and their compute-optimal combinations—the hardest questions (difficulty bin 5) show near-zero improvement regardless of compute budget. In Figure 3 (right), bin 5 accuracy hovers at 1–3% for all methods and all budgets up to 256 generations. In Figure 7 (right), bin 5 shows roughly 2–3% accuracy irrespective of the sequential-to-parallel ratio, with all strategies clustering at the same negligible performance level. In the FLOPs-matched comparison (Figure 9), the bin 5 scaling curve is essentially flat near 0–5%, sitting below the horizontal lines representing the `14×` larger model's performance at all three R values tested.

The paper is candid about this limitation. The Section 7 takeaway box explicitly states that test-time compute is ineffective when "the base model's pass@1 is near zero on a problem class," because "no amount of search or revision will help—there are no correct solutions in the proposal distribution to find or refine." This establishes a fundamental capability bound: **test-time compute amplifies existing capability but does not create new capability**. If the base model essentially never produces a correct solution for a given problem class, no test-time strategy—no matter how sophisticated—can recover.

The consequence is that PROX offers no path forward for problems that exceed the base model's training distribution or reasoning capacity. For such problems, scaling pretraining (larger models, more data, better data) remains the only viable path, as demonstrated by the fact that the `14×` larger model outperforms test-time-compute-augmented smaller models on bin 5 questions across all R regimes (Figure 9). The paper does not attempt to mitigate this limitation—it is presented as a fundamental boundary condition on the approach rather than a solvable engineering problem.

---

### Single Benchmark, Single Model Family

All experiments use the MATH benchmark (500 test questions) with PaLM 2-S\* as the base model. The authors state they "believe this model is representative of the capabilities of many contemporary LLMs" (Section 4), but this claim is unverified. Several aspects of the findings could be model-specific or benchmark-specific:

- **The PRM's quality and over-optimization behavior** depend on PaLM 2-S\*'s output distribution. A model with different calibration properties, different typical error patterns, or different solution styles might exhibit different difficulty-dependent scaling curves. For instance, a model that produces more verbose step-by-step solutions might benefit more from beam search (which prunes at each step) than a model that produces concise answers.

- **The revision model's ability to learn from incorrect in-context examples** depends on the base model's in-context learning capabilities, which vary substantially across model families. The paper's finding that the revision model generalizes beyond its 4-step training horizon (Figure 6, left) may not hold for models with weaker in-context learning.

- **The MATH benchmark** consists exclusively of competition-level math problems requiring symbolic reasoning. It is unclear whether the difficulty-dependent patterns—beam search over-optimizing on easy problems, revisions benefiting easy problems more than hard ones, no method helping on the hardest problems—would generalize to code generation, logical reasoning, scientific QA, or tasks requiring factual knowledge rather than step-by-step inference. The paper does not test on any non-math benchmark.

The consequence is that readers cannot assess whether the paper demonstrates a general principle of compute-optimal test-time scaling or a set of findings specific to PaLM 2-S\* solving MATH problems. The paper does not include replication on a second model family (e.g., LLaMA, Gemma) or a second benchmark domain (e.g., code generation, commonsense reasoning), leaving this as an open question.

The mitigation status is that the paper transparently acknowledges the limitation in scope (the model and benchmark are described in Sections 4 and 3.1) but does not perform any cross-model or cross-domain validation. The authors "believe" the model is representative, but this is an assertion rather than evidence.

---

### The `14×` Larger Model Baseline Is Not a Full Comparison

The FLOPs-matched comparison in Section 7 has a significant design asymmetry that favors test-time compute. The `14×` larger model uses **greedy decoding only**—no majority voting, no best-of-N sampling, no verifier-based selection, and no revision chains. This is a deliberate choice to isolate the effect of scaling pretraining alone, but it creates an unbalanced comparison: the smaller model gets sophisticated inference-time strategies while the larger model gets the simplest possible decoding method.

Why this matters: the paper's own results demonstrate that even simple inference-time strategies provide substantial gains. Figure 3 shows that majority voting at 512 generations reaches approximately 29% accuracy on MATH, compared to roughly 10–19% pass@1 for the base model (mentioned in Section 4). If the `14×` larger model were given even a modest test-time compute budget—say, best-of-8 weighted using the same PRM—its performance would likely be meaningfully higher than the greedy-decoding baseline used in the FLOPs-matched comparison. The paper does not report the larger model's pass@1, but even best-of-4 majority voting could close a non-trivial portion of the gap that the paper attributes to test-time compute efficiency.

Additionally, the larger model uses parameter-only scaling with fixed training data, following the LLaMA paradigm (Touvron et al., 2023) rather than Chinchilla-optimal training (Hoffmann et al., 2022), where both data and parameters are scaled equally. The paper acknowledges this in Section 7:

> "We choose this setting as it is representative of a canonical approach to scaling pretraining compute and leave the analysis of compute-optimal scaling of pretraining compute where the data and parameters are both scaled equally to future work."

A Chinchilla-optimal larger model would likely achieve higher performance at the same FLOPs budget, making the pretraining baseline stronger and potentially narrowing or reversing the reported advantages of test-time compute. The consequence is that the FLOPs-matched comparison results (e.g., +27.8% relative improvement on easy questions at `R ≪ 1`) should be interpreted as **upper bounds on the advantage of test-time compute over pretraining**—the gap would likely shrink against a more competitive pretraining baseline that includes some test-time augmentation or compute-optimal training.

The paper does not attempt to mitigate this limitation beyond acknowledging it and deferring to future work.

---

### The Revision Model Has a 38% Correct-to-Incorrect Reversion Rate

As noted in Section 6.1, approximately **38% of correct answers** produced during a revision chain get "revised" back to incorrect answers in the subsequent step. This occurs because the revision model was trained exclusively on sequences where all in-context answers are incorrect followed by a correct target. During inference, when the chain happens to produce a correct answer at some step, the model has never been trained on what to do in that situation—its training only includes the behavior "given incorrect answers, produce a correct one." When presented with a correct answer, it may still attempt to "improve" it, often introducing errors.

The consequence is that deep sequential revision chains have diminishing or even negative returns beyond some depth. Figure 6 (left) shows that pass@1 per step increases from step 1 to steps 15–20, then plateaus and oscillates in the 23–25% range out to step 64. The plateau and oscillation likely reflect the tradeoff between revisions that fix errors and revisions that revert correct answers. This limits the benefit of allocating budget to sequential depth rather than parallel breadth, particularly for problems where the model already produces correct solutions at a moderate rate (easier problems).

The paper partially mitigates this by using majority voting or verifier-based selection across the entire revision chain—picking the best answer from any step rather than always taking the last one. This works post-hoc but does not solve the underlying problem: the model cannot recognize when a correct answer has been reached and should stop revising. A more principled solution—such as training the model on trajectories that include "stop revising" signals when the answer is already correct, or using the verifier to dynamically truncate revision chains—is not explored. The paper does not ablate the reversion rate or analyze how it varies across difficulty levels, leaving the practical impact partially characterized but not systematically measured.

---

### Sequential Strategies Introduce Latency That the FLOPs-Based Accounting Ignores

The paper measures compute in "generations" (number of complete solutions sampled), which is a reasonable proxy for total FLOPs but ignores wall-clock latency. Sequential revisions are inherently serial—each revision depends on the previous one, so a chain of 64 revisions takes approximately `64×` the latency of generating a single solution, regardless of how much parallel hardware is available. In contrast, best-of-N with 64 parallel samples can (with sufficient GPUs) be executed with latency roughly equal to a single generation.

This matters because the compute-optimal policy on easy problems favors sequential-heavy strategies. For instance, Figure 7 (left) shows that at low budgets (8–32 generations), fully sequential is optimal—the accuracy curves are monotonically increasing with the sequential-to-parallel ratio. At higher budgets, the optimal ratio is around 2–8 sequential revisions per parallel chain. These strategies achieve higher accuracy per FLOP but at substantially higher latency per query.

For latency-sensitive applications—interactive assistants, real-time tutoring, API deployments with strict response time requirements—this tradeoff may be unacceptable even if the FLOPs efficiency is superior. A user waiting for a math answer may prefer a slightly less accurate response in 2 seconds (best-of-16 parallel) over a more accurate response in 30 seconds (16 sequential revisions). The paper does not discuss latency, report wall-clock times for any configuration, or analyze how the compute-optimal policy would change under a latency constraint rather than a pure FLOPs constraint.

The paper does not acknowledge or attempt to mitigate this limitation. The FLOPs-based analysis is standard in the scaling laws literature, but its omission of latency is a practical concern for deployment that differs from the typical pretraining scaling context (where training throughput, not per-sample latency, is the bottleneck).

## 7. Implications and Future Directions

### How This Work Changes the Landscape

This paper shifts the conversation around data quality for LLM pre-training from **what rules to write** to **how to learn refinement operations automatically**. Before this work, the dominant paradigm for improving pre-training corpora was expert-driven: human engineers design heuristic filters (C4 rules, Gopher rules, FineWeb rules), manually tune thresholds (minimum document length, symbol-to-word ratio, perplexity cutoffs), and apply these uniformly across all documents regardless of their individual characteristics. This paradigm has produced increasingly elaborate rule sets—FineWeb combines rules from C4, Gopher, and newly crafted heuristics—but as the paper's experiments reveal, combining more rules does not necessarily yield better data (Table 2: Gopher+C4+FineWeb rules achieve only 42.3% average accuracy, indistinguishable from raw data at 42.1%).

PROX changes the framing in two fundamental ways. **First, it recasts data refinement from a filtering problem to a program generation problem.** Rather than asking "should this document be kept or dropped?" (the binary decision that dominates prior work from QuRating to FineWeb-Edu), PROX asks "what specific cleanup operations does this document need?" This shift enables fine-grained, within-document operations—removing navigation bars from the top of an otherwise excellent article, normalizing broken Unicode characters in a paragraph, stripping footer links from a forum post—that binary filtering cannot express. The paper quantifies the value of this shift: document-level filtering alone (PROX-D) pushes accuracy from 42.1% to 43.5% (Table 2), but adding chunk-level refinement (PROX-D+C) reaches 44.6%, demonstrating that the additional expressivity of per-document, per-line operations provides gains beyond what filtering can achieve regardless of how sophisticated the filtering criteria become.

**Second, it establishes that small language models—not just frontier-scale models—can perform meaningful data refinement.** The field had implicitly assumed that if models are to improve data, they must be powerful: LLAMA-3 used LLAMA-2 as a quality classifier, the PHI series used GPT-4 for data synthesis, and COSMO used MISTRAL-8x7B. PROX demonstrates that a 0.3B parameter model achieves 82.6% F1 on document-level refinement (Table 4), and that refining models of all tested sizes (0.3B to 1.7B) produce roughly the same +2% downstream accuracy improvement (Figure 5). This decouples data quality improvement from model scale, implying that the cost of refinement can remain small and fixed while pre-training models scale to arbitrary size—the opposite of synthesis-based approaches where running larger generation models becomes increasingly expensive.

The most diagnostically important finding may be the **failure of heuristic rules to transfer across domains**. Table 5 shows that applying rule-based filtering to OpenWebMath degrades performance by 3.1 percentage points (21.5% to 18.4% for TINYLLAMA-1.1B), while PROX improves it by 11.0 points (to 25.7%). This result exposes a systematic weakness in heuristic-based preprocessing: rules optimized for general web text (where URLs, navigation bars, and advertisements are reliable noise indicators) fail on mathematical text (where these signals mean something different, or where different noise patterns dominate). The implication is not that better rules are needed—it's that **the rule-based paradigm itself is fundamentally limited by its inability to adapt to domain-specific noise distributions**. PROX's approach of training on seed data from the target corpus circumvents this by learning domain-appropriate patterns automatically, and the 11.0% vs. -3.1% comparison is a stark demonstration of the practical consequences.

The paper also contributes to the emerging conversation about **inference-time compute allocation for data preparation**. Recent work on inference-time scaling (Snell et al., 2024; Wu et al., 2024) has shown that allocating extra compute during model inference can substitute for model scale. PROX extends this philosophy upstream: allocate extra compute during data preprocessing, before training begins, and the benefits compound over every training step. The paper's efficiency numbers—20× fewer training tokens to match LLEMMA-7B (Table 5), 30× fewer training steps on FineWeb (Figure 1), 58% of the total FLOPs for comparable performance at 1.7B scale (Figure 8)—suggest this upstream investment may yield larger returns than test-time compute scaling, since improved data quality benefits the entire training process rather than being applied per-query.

### Follow-Up Research This Work Enables

**Cheap, amortized difficulty estimation for pre-training data refinement.** PROX's current difficulty estimation for filtering decisions requires generating thousands of samples per document (Section 3.2) and scoring them with an LLM—a cost comparable to or exceeding the pre-training budget being optimized. The paper flags this but does not resolve it. A natural extension would train a lightweight classifier—perhaps a 100M-parameter model operating on document-level features (length statistics, vocabulary diversity metrics, HTML tag density, line-length entropy)—to predict the LLM's keep/drop decision directly from the document text without any generation. If such a classifier could achieve F1 within 5–10 points of the 70B-parameter annotator (Table 4 shows the 0.3B refining model achieves 82.6% F1, which already approximates the larger annotator's decisions), the inference cost for document-level filtering would drop by two orders of magnitude, making the approach practical for web-scale deployment. The experiment would measure: (a) correlation between classifier predictions and LLM annotations, (b) downstream pre-training performance when using classifier-based filtering vs. full PROX filtering, and (c) total FLOPs including classifier training and inference.

**Online, iterative refinement with feedback from pre-training loss.** PROX performs refinement once, offline, before training begins. But the optimal refinement operations may depend on what the model actually learns from the data—a document that appears noisy to a human (or to an LLM annotator) might actually provide useful training signal, while a superficially clean document might contain subtle patterns that confuse the model. A dynamic refinement system could interleave data processing with training: train the base model for some interval, use the per-token training loss as a signal of which documents or document regions are genuinely problematic, and use that signal to update the refining model's parameters or adjust its filtering thresholds. This connects to the MATES framework (Yu et al., 2024) for model-aware data selection but extends it to fine-grained operations. The key experiment would compare (a) static PROX refinement pre-training, (b) periodic re-refinement at fixed training intervals (e.g., every 5B tokens), and (c) continuous refinement where the refining model is fine-tuned on loss-weighted examples from the training corpus, measuring both downstream accuracy and total FLOPs (refinement + training).

**End-to-end learned refinement without a pre-defined operation vocabulary.** PROX constrains refinement to a hand-designed set of operations (`remove_lines`, `normalize`, `drop_doc`, `keep_doc`/`keep_chunk`). This constraint makes the task tractable for small models and ensures interpretability, but it also limits expressivity—operations like "merge these two lines that were incorrectly split by the HTML parser" or "reorder these paragraphs to improve coherence" cannot be expressed. A more ambitious approach would train the refining model to output arbitrary text edits (insertions, deletions, substitutions, reorderings) using a diff-based representation—the model generates a sequence of edit operations that transform the raw document into a refined version, and the executor applies these edits deterministically. This is a harder generation task (the output space is larger and less structured) but could be made tractable by training on larger seed datasets collected from LLM-generated refinements. The experiment would measure: (a) whether unconstrained edit generation produces higher-quality refined data than PROX's fixed operation set (as measured by downstream pre-training performance), (b) the failure rate and hallucination rate of unconstrained edits vs. PROX's 0.5% program failure rate (Table 35), and (c) whether larger refining models (1B–7B) are needed for unconstrained editing, which would change the FLOPs tradeoff analysis.

**Stress-testing PROX on deliberately adversarial noise patterns.** The paper's case studies (Tables 33–34) show PROX handling common web noise: navigation bars, URL links, footers, boilerplate headers. But the web also contains more subtle quality degradations that might fool a pattern-recognition-based system: SEO-optimized articles padded with repetitive keyword variations to inflate word count, machine-translated content with grammatical errors that don't match any fixed pattern, or AI-generated text with superficial fluency but factual errors. A stress test would construct a synthetic corpus where documents are corrupted with known noise types at controlled rates and severities, then measure PROX's precision and recall in detecting and fixing each corruption type. This would produce a capability profile: which noise types are robustly handled (likely navigation bars and URL patterns, where the few-shot prompts are carefully designed) and which are systematically missed (likely subtle semantic degradations that the 0.3B model lacks the capacity to detect). The results would inform when PROX is safe to deploy unsupervised versus when human auditing or larger annotator models are needed.

**Domain-adaptive refinement without new seed data.** The paper notes that PROX's seed data collection "is performed only once" (Section 2.3), and the same refined models are applied across five different general-domain corpora (RedPajama-V2, C4, FineWeb, FineWeb-Edu, DCLM) with consistent gains of 0.9–3.1% (Section 3.3). But for the mathematical domain (OpenWebMath), the authors "further adapted on math text" (Section 3.4), implying that domain transfer without additional adaptation may not work. An important extension would measure zero-shot transfer of a general-domain refining model to code, biomedical text, legal documents, and multilingual data—quantifying the performance drop for each domain and identifying which noise patterns transfer (URL removal likely transfers) and which don't (domain-specific formatting conventions that the general model misidentifies as noise). This would establish whether PROX requires per-domain seed data (limiting scalability to niche domains) or whether a single refining model generalizes sufficiently across reasonably related text types.

**Evaluating whether refinement introduces subtle distribution shifts that harm certain capabilities.** The paper measures downstream performance on standard benchmarks (ARC, HellaSwag, MMLU, etc.) and shows consistent improvements. But aggressive data cleaning can remove content that, while noisy, provides useful training signal—forum discussions with informal language may help the model learn conversational patterns, code snippets embedded in blog posts may improve code generation ability even if the surrounding text is low-quality, and multilingual fragments in primarily English documents may support cross-lingual transfer. An experiment would pre-train models on PROX-refined data and evaluate on a broader capability suite including: (a) code generation benchmarks (HumanEval, MBPP) to test whether removal of inline code fragments degrades coding ability, (b) multilingual benchmarks to test whether aggressive language filtering removes valuable cross-lingual signal, (c) conversational and informal text benchmarks to test whether removal of "low-quality" social media content hurts performance on casual language understanding. The goal would be to identify any capabilities that are unintentionally sacrificed by refinement and to characterize the quality-diversity tradeoff more precisely than the current kept-ratio analysis (Table 4).

### Practical Applications and Downstream Use Cases

**Cost-efficient pre-training for organizations with fixed compute budgets.** The most direct application of PROX is in the standard LLM pre-training pipeline, where it serves as a drop-in replacement for heuristic filtering stages. The paper's efficiency numbers are directly actionable: on general-domain data, PROX-refined corpora achieve comparable downstream performance with training time reductions of roughly 20–30× (Figure 1) or FLOPs reductions of ~42% at 1.7B scale (Figure 8). For a team allocating a fixed compute budget (e.g., $500K in cloud GPU hours), this translates to either training a model of the same quality in half the time and cost, or training a better model with the same budget. The practical implementation requires: (1) running the seed data annotation once using an API-based LLM (LLAMA-3-70B, costing perhaps a few thousand dollars for 50K+ annotations), (2) fine-tuning a small refining model on this data (negligible cost relative to pre-training), (3) running PROX inference over the target corpus (cost scales with corpus size but uses small models), and (4) pre-training on the refined corpus with the savings in training FLOPs more than offsetting steps 1–3.

**Domain-specific continual pre-training with dramatically reduced data requirements.** The math domain results (Table 5) demonstrate PROX's strongest practical advantage: achieving LLEMMA-7B-level performance with 20× fewer tokens (10B vs. 200B). For organizations building specialized models in law, medicine, finance, or science, this changes the economics of domain adaptation. Instead of collecting and training on hundreds of billions of domain tokens (which may simply not exist for niche fields), a team can collect a smaller high-quality seed corpus, apply PROX to refine it, and achieve strong domain performance with modest training budgets. The 10B-token scale demonstrated in the paper is achievable on a small GPU cluster (e.g., 8× A100s for a few days), making domain-specific LLM development accessible to academic labs and startups that previously could not compete with the 200B+ token training runs of well-resourced industrial teams. The procedure would be: (1) collect raw domain text (arXiv papers, medical textbooks, legal documents), (2) generate PROX seed data using the domain-specific annotation prompts described in the paper (the prompts themselves may need minor adaptation for the domain's noise patterns), (3) refine the corpus and train with 10–50B tokens—a 4–20× reduction from prior art.

**Improving data mixture strategies through quality-preserving token retention.** A less obvious application is in data mixture design, where practitioners must decide how to sample from different data sources (web text, books, code, academic papers) to maximize downstream performance. Existing mixture strategies (e.g., RegMix, DoReMi) operate on raw or heuristically filtered data, where "filtering" destroys tokens from some sources more aggressively than others, potentially biasing the effective mixture. PROX's ability to retain 3× more tokens than FineWeb-Edu (28% vs. 9%, Table 6) while matching downstream quality means that data mixture optimization can operate on a richer, less aggressively filtered set of documents. Specifically: if a mixture strategy wants to include 20% forum data (because forums provide conversational signal), but standard filtering discards 95% of forum posts as low-quality, the effective forum contribution becomes negligible regardless of the nominal sampling weight. PROX's rehabilitation approach—removing navigation elements and normalizing strings rather than discarding documents—preserves far more tokens from noisy sources, giving mixture optimizers more signal to work with. The implementation would couple PROX refinement with a data mixture search procedure (e.g., RegMix) to jointly optimize refinement levels per source and source sampling weights.
