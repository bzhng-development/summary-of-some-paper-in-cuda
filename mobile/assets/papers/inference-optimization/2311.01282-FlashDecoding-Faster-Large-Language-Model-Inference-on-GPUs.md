## 1. Executive Summary

FlashDecoding++ proposes a fast LLM inference engine that accelerates mainstream LLMs on both NVIDIA and AMD GPUs by addressing three performance bottlenecks: **asynchronized softmax with unified max value** (replacing synchronized partial softmax updates with a shared scaling factor to eliminate ~20% attention overhead), **flat GEMM optimization with double buffering** (padding to 8 rather than 64 in the M-dimension and overlapping memory access with computation for decode-phase GEMV/flat GEMM operations), and **heuristic dataflow with hardware resource adaption** (dynamically selecting CUDA Core vs. Tensor Core implementations based on input shape via offline-profiled inflection points). Across Llama2, OPT, and ChatGLM2 on NVIDIA and AMD GPUs, FlashDecoding++ achieves up to 4.86× speedup over Hugging Face implementations and an average 1.37× speedup over the FlashDecoding baseline, establishing that GPU inference can be substantially accelerated by exploiting statistical regularity in attention inputs and per-operation hardware affinity — but only when the softmax input distribution remains bounded enough to avoid overflow-driven recomputation.

## 2. Context and Motivation

### The Core Problem: LLM Inference Is a Compute Landscape Divided Into Two Distinct Phases, and Neither Is Optimized End-to-End

The fundamental challenge this paper tackles is that **real-world LLM inference on GPUs suffers from three distinct performance bottlenecks that prior work addresses only in isolation**, leaving substantial throughput and latency gains on the table. To understand these bottlenecks, we must first understand the two-phase structure of LLM inference.

LLM inference is not a single operation but a sequence of two qualitatively different computational phases that alternate during generation. The **prefill phase** processes the entire input prompt in parallel, producing the first output token. Here, the model ingests all prompt tokens simultaneously, meaning the attention computation operates over a large matrix of query-key interactions, and the linear projections are conventional GEMMs (General Matrix Multiplications) with substantial parallelism. The **decode phase**, by contrast, generates subsequent tokens auto-regressively — one token at a time — meaning each new token attends to all previously generated tokens plus the original prompt. Crucially, the decode phase's linear operations degenerate into **GEMV** (General Matrix-Vector) when the batch size is 1, or **flat GEMM** (tall-and-skinny matrix multiplication) for small batch sizes. This distinction is laid out explicitly in Figure 2.

Why does this distinction matter? Because the two phases stress different GPU resources in different ways, and previous frameworks apply the same computational strategy to both — or optimize one phase while neglecting the other. The prefill phase is **compute-bound**: there are many tokens to process in parallel, and the limiting factor is raw floating-point throughput. The decode phase is **memory-bound** at small batch sizes: each token generation touches the entire model's weights plus the growing KV-cache, but performs very few arithmetic operations per byte of data moved. A single, static approach to GEMM — such as always dispatching to cuBLAS's Tensor Core implementation — thus leaves performance on the table in one phase or the other.

The paper quantifies this directly: for a Llama2-7B linear layer in the decode phase, the Tensor Core implementation from cuBLAS achieves only 82.15% of the performance of a CUDA Core implementation using FastGEMV on an NVIDIA A100 GPU. Conversely, using CUDA Core for a batch-size-4 decode input achieves only 49.75% of the Tensor Core implementation's performance. This **50.25% performance gap** between the wrong and right hardware resource choice for a given workload is the paper's third challenge — and it exists because prior frameworks make **static** decisions rather than adapting to the actual shape of the computation at runtime.

### The Three Specific Bottlenecks

The paper identifies three concrete performance problems that compound across both phases:

**Bottleneck 1: Synchronized partial softmax update (~20% attention overhead).** Modern attention implementations (FlashAttention, FlashDecoding) divide attention matrices into tiles and compute partial softmax results in parallel. However, the softmax operation is inherently non-decomposable: the denominator is a sum over *all* elements in the row, so each partial result must be updated when a new partial result's maximum value is discovered. Equation 2 in the paper shows the synchronization logic: when a new partial vector is processed, its maximum value `m(x'')` is compared against the running maximum `m(x')`, and both previously computed exponents and sums must be rescaled. This synchronized update — essentially a barrier operation where all partial computations must coordinate — accounts for **18.8% of the attention computation** in Llama2-7B inference on an A100 with 1024 input length, according to the authors' profiling. This is not a small overhead; it means nearly one-fifth of attention time is spent coordinating rather than computing.

**Bottleneck 2: Under-utilized computation in flat GEMM (>50% performance loss from padding zeros).** During the decode phase, the M-dimension of GEMM operations (the batch dimension, corresponding to the number of tokens being processed simultaneously) is small — often exactly 1, or a small batch like 4–8. Modern GPU libraries designed for large GEMMs (cuBLAS, CUTLASS) tile the M-dimension to 64 to hide memory latency. When the actual M is much smaller (e.g., 1 or 8), these libraries **pad the matrix with zeros** to reach the tiling size of 64. This means the GPU still executes all the arithmetic for a 64-wide tile, but most of those multiply-add operations involve zeros and produce no useful output. The paper reports that this leads to **over 50% computation under-utilization** — more than half the GPU's arithmetic capability is wasted multiplying zeros.

**Bottleneck 3: Performance loss from static dataflow (up to 50.25% gap).** Even within a single model and a single phase, the GEMM shapes vary substantially. Figure 9(a) shows the four distinct `[N, K]` shapes in a transformer layer: the K, Q, V projection (`[N, K] = [HD*3, HD]`), the O projection (`[HD, HD]`), FFN1 (`[FD, HD]`), and FFN2 (`[HD, FD]`). Each of these shapes interacts differently with GPU hardware: some are better suited to Tensor Core's matrix-tile parallelism, while small-M variants (as in the decode phase) may run faster on CUDA Cores despite CUDA Cores' lower peak throughput because they avoid the overhead of padding and thread-block orchestration. The 50.25% figure comes from using the wrong choice: Tensor Core where CUDA Core would be faster (82.15% of CUDA Core performance) and CUDA Core where Tensor Core would be faster (49.75% of Tensor Core performance). A static dataflow — always using Tensor Core via cuBLAS for everything — is leaving up to half the available performance unused for certain operations.

### Why This Problem Matters

The paper grounds its motivation in the economics of deployed LLM systems, citing specific industry data:

> "OpenAI reports that GPT-4 inference with 8K context length costs $0.03 per 1K input tokens and $0.06 per 1K output tokens. Currently, OpenAI has 180.5 million users and receives over 10 million queries per day. Consequently, the cost to operate OpenAI's model like ChatGPT is approximately $7 million per day for the necessary computing hardware."

This is the real-world framing: LLM inference is not a one-time research cost but an ongoing operational expense that scales with user demand. A 1.37× speedup — the average improvement over FlashDecoding that FlashDecoding++ achieves — translates directly to a 27% reduction in GPU-hours, which at $7M/day scale is a savings of roughly $1.9M per day. Even modest fractional improvements have massive absolute value.

The two-phase structure also means the bottlenecks shift depending on workload characteristics. For short-input, long-output scenarios (e.g., chat applications where the prompt is brief but the model generates paragraphs of response), the decode phase dominates total time. For long-input, short-output scenarios (e.g., document summarization, retrieval-augmented generation with large contexts), the prefill phase dominates. The paper does not claim to solve one at the expense of the other; the three optimizations target both phases — asynchronous softmax for attention in both phases, flat GEMM optimization for the decode phase, and heuristic dataflow for all GEMM operations across both phases.

### Prior Approaches and Where They Fall Short

The paper situates itself against a landscape of existing inference acceleration techniques, each of which addresses pieces of the problem but none of which addresses all three bottlenecks simultaneously:

**FlashAttention and FlashAttention-2 (Dao et al., 2022, 2023)** optimize the attention computation during the prefill phase by tiling the attention matrix to stay within SRAM and avoid materializing the full N×N attention matrix in HBM. FlashAttention introduced the partial softmax technique (Figure 4b in the paper) that divides the softmax vector into partial vectors, computes each locally, and then performs a synchronized update across partial results. This achieves high parallelism and low memory consumption — but the **synchronized update itself becomes a bottleneck**, which FlashDecoding++ identifies and solves. FlashAttention-2 improved parallelism and work partitioning but left the fundamental synchronization pattern unchanged.

**FlashDecoding (Dao et al., 2023)** extends FlashAttention to the decode phase by splitting K and V across parallel threads, enabling efficient long-context attention during token generation. However, it inherits the same synchronized partial softmax update scheme from FlashAttention, meaning it still pays the ~20% synchronization overhead that FlashDecoding++ eliminates. FlashDecoding is the primary SOTA baseline against which FlashDecoding++ measures its 1.37× average speedup.

**TensorRT-LLM (NVIDIA, 2023)** and **FasterTransformer (NVIDIA)** are C++-based inference engines that employ kernel fusion, memory management, and integration of techniques like FlashAttention. They are among the fastest available engines, but they **rely primarily on cuBLAS for GEMM operations**, which means they use Tensor Core implementations with M-dimension padding to 64. This leaves the flat GEMM under-utilization problem unaddressed, and they do not dynamically switch between hardware resources based on operation shape.

**DeepSpeed (Aminabadi et al., 2022)** provides robust inference via kernel fusion and efficient GPU memory management (particularly for KV-cache), but similarly dispatches GEMM operations to cuBLAS without the fine-grained shape-based adaptation that FlashDecoding++ introduces for the flat GEMM case.

**vLLM (Kwon et al., 2023)** introduced PageAttention to improve GPU memory utilization, enabling larger batch sizes by reducing memory fragmentation. This is a memory-efficiency innovation orthogonal to the kernel-level compute optimizations in FlashDecoding++ — the two are complementary rather than competing.

**OpenPPL** is a C++ inference engine with kernel fusion and scheduling optimizations, again using standard GEMM libraries for linear operations.

**Hugging Face (PyTorch)** serves as the baseline: it uses PyTorch's default implementations, which include no attention tiling, no specialized GEMV kernels, no dynamic hardware resource selection, and no flat GEMM tiling optimization. The paper reports up to 4.86× speedup over this baseline on NVIDIA GPUs and up to 3.93× on AMD GPUs.

The gap across all these prior approaches is that **none of them simultaneously addresses all three bottlenecks**: the softmax synchronization overhead (Bottleneck 1), the flat GEMM under-utilization (Bottleneck 2), and the static hardware resource allocation (Bottleneck 3). FlashDecoding++ positions itself as the first engine that integrates solutions to all three in a single framework, achieving speedups beyond what any individual optimization alone would provide.

### How the Paper Positions Itself Relative to Existing Work

FlashDecoding++ is presented not as a new algorithmic innovation in attention (like FlashAttention was) but as an **engineering and systems contribution** that identifies and fixes specific, measurable performance leaks in the standard LLM inference pipeline. The authors frame their three contributions as addressing specific profiled overheads:

- The **asynchronized softmax** is a systems optimization enabled by a statistical insight: `>99.99%` of softmax input elements in typical LLMs (Llama2-7B, ChatGLM2-6B) fall within a narrow numerical range where a carefully chosen **unified max value** can serve as a shared scaling factor for all partial softmax computations, eliminating the need for cross-partial synchronization. This is not a new mathematical identity — Equation 3 is a standard algebraic property of softmax — but the engineering contribution is the recognition that the statistical distribution of inputs makes this property practically exploitable, and that the rare overflow case can be handled via a cheap fallback recomputation.

- The **flat GEMM optimization** is a tiling strategy informed by an analysis of the computation-to-memory ratio in Equation 5, which reveals a **fundamental tension between parallelism and memory efficiency** in the choice of the N-dimension tiling size BN. For small N, performance is parallelism-bounded (too few tiles to occupy all streaming multiprocessors); for large N, performance is memory-bounded. Previous libraries used BN-tiling heuristics designed for large-N conventional GEMM, which are suboptimal for the flat GEMM regime. FlashDecoding++ pads M to 8 (matching the hardware Tensor Core tile size) rather than 64, and uses double buffering to overlap memory loads with computation when N is large — a technique borrowed from general-purpose GPU optimization but applied specifically to the flat GEMM regime where it provides the largest benefit.

- The **heuristic dataflow** is a practical solution to the challenge of building a mapping from workload shape to optimal implementation. Rather than attempting to model the complex interaction of batch size, sequence length, model architecture, GPU characteristics, and kernel implementation quality analytically, the paper takes an empirical approach: profile the three candidate implementations (FastGEMV on CUDA Core, FlashDecoding++'s flat GEMM on Tensor Core, CUTLASS on Tensor Core) offline for each `[N, K]` shape at increasing M, find the inflection points where one implementation overtakes another, and build a lookup table. The key insight that makes this tractable is that **only four `[N, K]` shapes exist for any given LLM** (Figure 9a), so the offline profiling is bounded and cheap. At runtime, the engine simply checks M against the inflection points and dispatches to the appropriate implementation — a constant-time decision.

A notable aspect of the paper's positioning is its cross-platform validation. While most prior inference engines are NVIDIA-specific (CUDA-only), FlashDecoding++ demonstrates speedups on AMD GPUs (RX7900XTX and MI210), where only the Hugging Face baseline was available for comparison. This establishes that the optimizations are not tied to NVIDIA-specific hardware features; they exploit general GPU characteristics (Tensor vs. CUDA Core tradeoffs, shared memory double buffering) that apply across vendors, making the work relevant to the broader hardware ecosystem beyond NVIDIA's dominant position.

Finally, the paper acknowledges a **scope boundary**: the asynchronous softmax technique requires that softmax inputs fall within a bounded range to avoid overflow. For OPT-6.7B, the input distribution range is too wide (`[-496.8, 363.5]` per Figure 5), and the technique is **not applied** to this model. This honesty about when the technique works — and when it doesn't — is important: it tells the reader that the 1.37× average speedup is not a universal constant but depends on model-specific properties of the attention logit distribution. The recomputation fallback (synchronized partial softmax when overflow is detected) means correctness is never compromised, but the speedup from asynchronous execution is lost for models or inputs where the logit range exceeds the safe thresholds.

## 3. Technical Approach

### 3.1 Reader Orientation (Approachable Technical Breakdown)

FlashDecoding++ is a GPU inference engine — a piece of systems software that takes a trained Large Language Model and runs it efficiently on NVIDIA or AMD graphics cards to generate text. The system solves the problem that standard GPU libraries designed for large matrix multiplications are poorly matched to the specific, irregular shapes of computation that arise during LLM text generation, particularly during the decode phase where only one or a few tokens are processed at a time; the solution takes the form of three targeted kernel-level optimizations (asynchronous softmax, flat GEMM tiling, and dynamic hardware dispatch) that each eliminate a specific profiled performance bottleneck, together achieving up to 4.86× speedup over unoptimized PyTorch and 1.37× over the previous state-of-the-art FlashDecoding engine.

### 3.2 Big-Picture Architecture (Diagram in Words)

The FlashDecoding++ system can be understood as a **drop-in replacement for the GPU kernels that execute the core operations of a transformer layer during LLM inference**. The system is not a new model architecture or a new training method — it is an optimized implementation of the standard transformer operations (linear projections, attention, feedforward networks) that interposes itself between the high-level PyTorch model definition and the low-level GPU hardware. The major components are:

1. **Asynchronized Softmax Kernel** — replaces the standard synchronized partial softmax used in FlashAttention/FlashDecoding with a scheme where each partial softmax computation uses a shared, pre-computed "unified max value" as its scaling factor, eliminating the need for cross-partial synchronization barriers. A fallback recomputation path handles the rare case where the unified max value leads to numerical overflow.

2. **Flat GEMM Kernel with Double Buffering** — replaces cuBLAS/CUTLASS GEMM calls for decode-phase matrix multiplications (where the batch dimension M is small) with a custom kernel that tiles M to 8 (matching the hardware Tensor Core tile size) rather than 64, and when the N-dimension is large, overlaps memory loads of the next tile with computation of the current tile via alternating shared memory buffers.

3. **Heuristic Dataflow Dispatcher** — a runtime decision module that selects, for each GEMM operation in the model, which of three implementations to use: (a) FastGEMV on CUDA Cores for very small M, (b) the custom flat GEMM kernel on Tensor Cores for intermediate M, or (c) CUTLASS on Tensor Cores for large M. The selection is based on an offline-profiled lookup table keyed by the operation's `[N, K]` shape and the current batch size M.

4. **Model-Specific Configuration** — a set of per-model constants: the four `[N, K]` shapes that characterize all GEMM operations in that model's transformer layers, and the statistical bounds on softmax input values that determine whether the asynchronous softmax technique can be safely applied.

Information flows through the system as follows: the PyTorch model executes a transformer layer → for each linear operation, the heuristic dataflow dispatcher checks M against the offline-profiled inflection points for that operation's `[N, K]` shape and routes to the appropriate kernel → for attention operations, the asynchronous softmax kernel computes partial softmax results independently using the unified max value and accumulates numerator/denominator contributions → when all partial contributions are accumulated, the final division produces the attention output → if numerical overflow is detected, the kernel falls back to synchronized partial softmax for that specific vector.

#### Asynchronized Softmax with Unified Max Value

**The Standard Softmax and Why It Resists Parallelization**

The softmax function is mathematically defined for a vector `$x = [x_1, x_2, ..., x_d]$` as:

$$softmax(x)_i = \frac{e^{x_i}}{\sum_{j=1}^{d} e^{x_j}}$$

This is a row-wise operation in the attention mechanism: for each query position, we compute softmax over the attention scores against all key positions. The challenge for GPU parallelization is that the denominator is a sum over *all* elements in the row — it is a global reduction. If we split the row across parallel threads, each thread needs the full sum before it can produce its portion of the output.

The standard numerical recipe adds a stabilization step. Because `$e^{x_i}$` can overflow for large `$x_i$`, the computation is typically performed as:

$$softmax(x)_i = \frac{e^{x_i - m(x)}}{ \sum_{j=1}^{d} e^{x_j - m(x)} }$$

where `$m(x) = \max_j x_j$` is the maximum element of the vector. Subtracting the maximum ensures that all exponentiated values are in `$(0, 1]$`, preventing overflow.

**The Partial Softmax with Synchronized Update**

FlashAttention and FlashDecoding parallelize attention by dividing each row of the attention score matrix into **partial vectors**. Suppose `$x$` is split into two partial vectors `$x'$` and `$x''$`. Each partial vector can compute its own local softmax using its own local maximum. However, these local results are not yet correct because:

1. The local maximum of `$x'$`, call it `$m(x')$`, might differ from the global maximum `$m(x) = \max(m(x'), m(x''))$`.
2. The local sum `$l(x') = \sum_i e^{x'_i - m(x')}$` is computed relative to the *local* maximum, not the *global* maximum.

The synchronized update in Equation 2 of the paper corrects this. When partial result `$x''$` is computed, its maximum `$m(x'')$` is compared against the running maximum from `$x'$`. If `$m(x'') > m(x')$`, the previously accumulated sum `$l(x')$` must be rescaled by `$e^{m(x') - m(x'')}$`, and the previously computed exponentiated values `$f(x')$` must be similarly rescaled. Then the new contributions from `$x''$` are added. This rescaling is the **synchronization operation** that the paper measures as consuming 18.8% of attention computation time.

The key mathematical expression is:

$$l(x) = e^{m(x') - m(x)} \cdot l(x') + e^{m(x'') - m(x)} \cdot l(x'')$$

where `$m(x) = \max(m(x'), m(x''))$`. Each new partial result triggers a comparison and potential rescaling of all previously accumulated values. This is inherently sequential: later partial computations depend on the maximum discovered by earlier ones.

**The Mathematical Insight: The Scaling Factor Is Arbitrary**

Equation 3 in the paper states a property that is mathematically trivial but practically profound:

$$softmax(x) = \frac{[e^{x_1 - m(x)}, ..., e^{x_d - m(x)}]}{\sum_i e^{x_i - m(x)}} = \frac{[e^{x_1 - \phi}, ..., e^{x_d - \phi}]}{\sum_i e^{x_i - \phi}}, \quad \forall \phi \in \mathbb{R}$$

where `$x = [x_1, ..., x_d]$` is the input vector, `$m(x)$` is the maximum element, and `$\phi$` is any real number.

**What it computes:** The softmax of `$x$` can be computed using *any* constant `$\phi$` as the shift factor, not just the true maximum `$m(x)$`. The algebra works because the factor `$e^{-\phi}$` appears in both numerator and denominator and cancels:

$$softmax(x)_i = \frac{e^{x_i} \cdot e^{-\phi}}{\sum_j e^{x_j} \cdot e^{-\phi}} = \frac{e^{-\phi} \cdot e^{x_i}}{e^{-\phi} \cdot \sum_j e^{x_j}} = \frac{e^{x_i}}{\sum_j e^{x_j}}$$

**Why this form:** If `$\phi$` is the *same* for all partial computations, then each partial softmax can use its own independent scaling factor `$e^{-\phi}$` without needing to know other partial results' maxima. The correction-rescaling step — the source of the 18.8% overhead — is eliminated because no partial result ever needs to update another partial result's running maximum. This transforms the softmax from a synchronized multi-pass computation into an embarrassingly parallel one.

**The Practical Constraint: Numerical Range**

The free choice of `$\phi$` is theoretically unlimited but practically constrained by floating-point representation. Given a fixed numerical format (float32), the exponential function has representable outputs only for inputs in a certain range. If `$x_i - \phi$` is too large (positive), `$e^{x_i - \phi}$` overflows to infinity. If `$x_i - \phi$` is too negative, `$e^{x_i - \phi}$` underflows to zero, causing precision loss that can corrupt the final softmax normalization.

The paper's key empirical insight, shown in Figure 5, is that for typical LLMs (Llama2-7B, ChatGLM2-6B), **more than 99.99% of softmax inputs** fall within a narrow, known range. Specifically, for Llama2-7B, the authors report that `$-16.8 < x_i < 6.5$` for `$>99.99\%$` of all `$x_i$` values across different inputs.

If we choose a unified max value `$\phi$` such that `$x_i - \phi$` remains within the safe range for all `$x_i$` in this 99.99% distribution, then for the overwhelming majority of vectors, the asynchronous partial softmax computation will be numerically stable without any synchronization. The choice of `$\phi$` is a single, model-specific constant determined offline by analyzing the empirical distribution of attention logits.

**The Asynchronous Computation**

For a vector `$x$` split into `$p$` partial vectors `$x = [x^{(1)}, ..., x^{(p)}]$`, and a corresponding column `$v$` of the value matrix `$V$` similarly split into `$v = [v^{(1)}, ..., v^{(p)}]$`, the attention output (inner product of softmax result with `$v$`) is:

$$\langle softmax(x), v \rangle = \frac{\sum_{j=1}^{p} \sum_{i=1}^{d/p} e^{x_i^{(j)} - \phi} \cdot v_i^{(j)}}{\sum_{j=1}^{p} \sum_{i=1}^{d/p} e^{x_i^{(j)} - \phi}}$$

where `$x_i^{(j)}$` is the `$i$`-th element of the `$j$`-th partial vector, `$v_i^{(j)}$` is the corresponding value element, `$\phi$` is the unified max value (a scalar constant), and `$d/p$` is the length of each partial vector.

**What it computes:** Each partial vector `$j$` independently computes two running sums:
- A **numerator accumulator**: `$N^{(j)} = \sum_i e^{x_i^{(j)} - \phi} \cdot v_i^{(j)}$`
- A **denominator accumulator**: `$D^{(j)} = \sum_i e^{x_i^{(j)} - \phi}$`

These partial accumulations can proceed in parallel across `$p$` thread blocks without any inter-block communication. When all partial computations complete, a single reduction combines them:

$$\langle softmax(x), v \rangle = \frac{\sum_{j=1}^{p} N^{(j)}}{\sum_{j=1}^{p} D^{(j)}}$$

**Why this form:** The inner product with `$v$` is the *actual operation needed* in attention — we never need the intermediate softmax matrix explicitly, only its product with V. By fusing the softmax and the value multiplication into a single accumulation, the asynchronous kernel avoids writing the full attention matrix to memory and eliminates the inter-partial synchronization that would be required if softmax were computed as a standalone step.

**Example Walkthrough (Figure 6a)**

Consider `$x = [4, 5, 6, 7]$` and `$v = [v_1, v_2, v_3, v_4]$`. The unified max value is `$\phi = 6$`. The vector is split into two partial vectors: `$x' = [4, 5]$` and `$x'' = [6, 7]$`. Two GPU threads process these independently:

**Thread 1 (processes `$x'$`):**
- Computes `$e^{4-6} = e^{-2}$` and `$e^{5-6} = e^{-1}$`
- Accumulates numerator: `$e^{-2} \cdot v_1 + e^{-1} \cdot v_2$`
- Accumulates denominator: `$e^{-2} + e^{-1}$`

**Thread 2 (processes `$x''$`):**
- Computes `$e^{6-6} = e^{0} = 1$` and `$e^{7-6} = e^{1} \approx 2.718$`
- Accumulates numerator: `$1 \cdot v_3 + 2.718 \cdot v_4$`
- Accumulates denominator: `$1 + 2.718$`

When both threads finish, the final result is `$(\text{Thread1\_numerator} + \text{Thread2\_numerator}) / (\text{Thread1\_denominator} + \text{Thread2\_denominator})$`. No thread ever communicated with the other during the accumulation. The synchronization occurs *only* at the final reduction, which involves just two scalar additions and a scalar division.

**The Recomputation Fallback**

The asynchronous approach works only when `$x_i - \phi$` stays within representable range for all `$x_i$`. If an input element violates this bound (either overflowing or underflowing), the partial computation for *that entire row* is abandoned, and the row is recomputed using the standard synchronized partial softmax scheme.

Figure 6b illustrates this: for a vector `$y = [3, 6, 9, 6]$` with `$\phi = 6$` and safe range bounds `$a = -3, b = 3$`, the element `$y_3 = 9$` gives `$y_3 - \phi = 3$`, which equals the upper bound `$b$` and would be borderline. If any element exceeds the bounds, both threads are signaled to terminate, and Thread 1 recomputes the entire row using the synchronized update logic from Equation 2, which uses the true per-partial maximum values and guarantees stability.

The paper argues that because `$>99.99\%$` of inputs fall within the safe range for models like Llama2-7B and ChatGLM2-6B, this fallback path is rarely triggered, and the overhead of the recomputation is negligible in aggregate. The fallback guarantees **correctness**; the statistical insight guarantees **performance**.

**Model-Specific Applicability**

Figure 5 shows the empirical softmax input distributions for three models. Llama2-7B has a narrow range `$[-16.8, 6.5]$`. ChatGLM2-6B has a similarly narrow range `$[-10.5, 13.7]$`. These are suitable for the asynchronous technique. OPT-6.7B, however, has a much wider range `$[-496.8, 363.5]$`, which means no single unified `$\phi$` can keep `$x_i - \phi$` within safe floating-point bounds simultaneously for all inputs. For OPT-6.7B, the paper explicitly states: "we do not apply the technique in this section because of the large range." This is an important scope limitation: the asynchronous softmax technique is not universally applicable; it depends on the attention logit distribution of the specific model.

**Design Choice: Unified Max Value vs. Other Approaches**

Why choose a fixed `$\phi$` rather than, say, computing the global maximum first via a parallel reduction and then broadcasting it? The answer lies in the cost model of GPU computation. A parallel reduction to find the true global maximum `$m(x)$` over a vector of length d requires `$\log_2(d)$` steps of inter-thread communication — this is itself a synchronization overhead. The paper's approach replaces this with a single constant lookup (`$\phi$` is known before computation begins) for 99.99% of cases, and only pays the reduction cost in the 0.01% fallback case. The tradeoff is between a guaranteed constant-time overhead per token (the standard approach) versus a probabilistic near-zero overhead (the paper's approach).

A second alternative would be to simply not stabilize the softmax at all — compute `$e^{x_i}$` directly without any subtraction. This would avoid the synchronized update entirely but would overflow for moderately large `$x_i$` (roughly `$x_i > 88$` in float32). The paper's approach retains the numerical stability of the standard method while eliminating its synchronization cost in the common case.

#### Flat GEMM Optimization with Double Buffering

**The Shape of Decode-Phase Matrix Multiplication**

In the decode phase, the model processes one or a few tokens at a time. The linear operations — multiplying a token's hidden state vector against a weight matrix — take the form of a matrix multiplication with shapes:

$$C = A \times B, \quad A \in \mathbb{R}^{M \times K}, \quad B \in \mathbb{R}^{K \times N}$$

For the decode phase, `$M$` is the batch size (number of tokens being processed simultaneously). When batch size is 1, this is a **GEMV** (matrix-vector multiply) where `$M=1$`. For small batch sizes like 4 or 8, this is a **flat GEMM** — the `$M$` dimension is much smaller than either `$K$` or `$N$`.

**The Padding Problem in cuBLAS and CUTLASS**

State-of-the-art GPU GEMM libraries (cuBLAS, CUTLASS) are designed for conventional GEMM shapes where `$M$` and `$N$` are both large enough to provide substantial parallelism. These libraries typically tile the `$M$` dimension to **64** to amortize memory latency — each thread block processes a 64-row tile of the output. When the actual `$M$` is smaller than 64, the libraries **pad the input with zeros** to reach the tiling size.

The cost of this padding is severe. If `$M=8$` and the library tiles to 64, the GPU still executes `$\frac{64}{8} = 8\times$` more arithmetic operations than necessary — most of them multiplying zeros. The paper reports that this leads to "over 50% computation under-utilization." The GPU's arithmetic units are active but producing useless results.

**Approach: Padding M to 8 Instead of 64**

FlashDecoding++'s first insight is that modern Tensor Core architectures natively support tiling `$M$` to **8**, not 64. The NVIDIA A100's Tensor Cores process 8×8 matrices natively. By padding `$M$` to 8 rather than 64, the kernel eliminates the vast majority of wasted computation: for `$M=1$`, padding to 8 wastes `$\frac{7}{8}$` of the work rather than `$\frac{63}{64}$`; for `$M=4$`, padding to 8 wastes 50% rather than `$\frac{60}{64} \approx 94\%$`.

However, padding to 8 in the `$M$` dimension means the library's standard tiling strategy — which tiles the `$N$` and `$K$` dimensions to hide memory latency — must be rethought for two reasons.

**The Tiling Tradeoff: Computation-to-Memory Ratio**

The paper models the flat GEMM kernel's efficiency through an analysis of the computation-to-memory ratio as a function of the `$N$`-dimension tiling size `$B_N$`. The key equation is:

$$\frac{\text{Computation}}{\text{Memory}} = \frac{2 \times M \times K}{K + \frac{M \times K}{B_N} + M}$$

where `$M$` is the batch dimension (padded to 8), `$N$` is the output dimension, `$K$` is the reduction dimension, and `$B_N$` is the tiling size along the `$N$` dimension.

**What it computes:** This ratio measures how many floating-point operations the kernel performs per byte of data transferred from global memory (HBM) to the compute units. A higher ratio means the kernel is more **compute-bound** (limited by arithmetic throughput); a lower ratio means the kernel is more **memory-bound** (limited by memory bandwidth).

**Derivation logic:** The numerator `$2 \times M \times K$` is the number of floating-point operations to multiply an `$M \times K$` tile by a `$K \times 1$` column of `$B$` (one multiply-add per element pair, hence factor 2). The denominator sums three memory transfer costs: loading the `$M \times K$` tile of `$A$` (cost `$M \times K$`), loading `$B$` tiles (cost `$B_N \times K$` per tile, with `$N/B_N$` tiles total), and writing the `$M \times N$` output (cost `$M \times N$`). The equation simplifies to the form shown after dividing through by the number of tiles.

**The parallelism constraint:** The number of independent thread blocks is `$N / B_N$`. For good GPU utilization, this must be at least as large as the number of streaming multiprocessors (SMs) — 108 on the A100. Larger `$B_N$` means fewer blocks, and eventually insufficient parallelism.

**Why this form matters:** The computation-to-memory ratio increases with `$B_N$` (bigger tiles amortize memory costs better), but the parallelism decreases with `$B_N$` (fewer tiles to distribute across SMs). This creates a **fundamental tradeoff** that depends on `$N$`:

- **Small N:** Performance is **parallelism-bounded**. Even with small `$B_N$`, there are few tiles to distribute. The kernel is limited by how many SMs can be occupied, not by memory bandwidth.
- **Large N:** Performance is **memory-bounded**. There are plenty of tiles for parallelism, so `$B_N$` should be chosen large to maximize the computation-to-memory ratio and hide memory latency.

Figure 7 illustrates this empirically. For small `$N$` (up to about 1024), the best `$B_N$` is relatively small (64–128) and produces a parallelism-bounded regime. For large `$N$` (4096+), the best `$B_N$` is larger (128–256) and the kernel enters a memory-bounded regime.

**Double Buffering for Memory-Bound Cases**

When `$N$` is large and the kernel is memory-bounded, the bottleneck is the time spent waiting for data to arrive from global memory. FlashDecoding++ applies **double buffering** to overlap memory loads with computation.

The mechanism works as follows (Figure 8):

1. The shared memory of each GPU block is partitioned into **two buffers** of equal size — a "left buffer" and a "right buffer."
2. While the GPU block is computing the GEMM for **Tile j** using data in the left buffer, the memory loading unit asynchronously fetches **Tile j+1** into the right buffer.
3. When computation of Tile j finishes, the buffers swap roles: computation begins on Tile j+1 (now in the right buffer) while Tile j+2 loads into the left buffer.
4. This ping-pong continues through all K-dimension tiles.

The timeline at the bottom of Figure 8 shows the difference: without double buffering, the timeline alternates between "compute" and "idle (memory load)" periods. With double buffering, the "compute" periods are continuous — the memory latency is completely hidden behind computation. The GPU is never idle waiting for data.

**Design Choice: When to Apply Double Buffering**

The paper's analysis reveals that double buffering is not universally beneficial. When `$N$` is small, the kernel is parallelism-bounded, not memory-bounded. In this case, there are too few thread blocks to occupy all SMs, and the bottleneck is the lack of parallel work, not memory latency. Double buffering would add shared memory pressure without addressing the actual bottleneck. The paper thus applies double buffering only when `$N$` is large — specifically, in the regime where Figure 7 shows the kernel is memory-bounded — making it a conditional optimization within the flat GEMM kernel.

**Integration with Tensor Core Hardware**

The flat GEMM kernel targets Tensor Cores, which are specialized matrix-multiply units on NVIDIA GPUs. On the A100, each Tensor Core processes a 8×8×4 matrix multiply-accumulate in one cycle. The kernel's tiling strategy must match these hardware constraints: M is tiled to 8 (one Tensor Core dimension), N is tiled to `$B_N$` (which must be a multiple of 8 for Tensor Core compatibility), and K is tiled to `$B_K$` (also a multiple of the Tensor Core's K-dimension).

The key difference from cuBLAS/CUTLASS is *only* the M-dimension tiling: 8 instead of 64. The N and K tiling strategies follow similar principles as existing libraries but are tuned specifically for the flat-GEMM regime where M is small. The paper does not propose a fundamentally new tiling algorithm; rather, it identifies that the standard heuristic of "always tile M to 64" is catastrophic for flat GEMM, and that a much simpler change (tiling to 8 and applying double buffering when memory-bound) recovers most of the lost performance.

#### Heuristic Dataflow with Hardware Resource Adaption

**The Three-Implementation Decision Problem**

The flat GEMM optimization from Section 4 covers only part of the GEMM landscape in LLM inference. Across both phases and all operations, the `$M$` dimension ranges from 1 (decode, batch size 1) to `$\text{sequence length} \times \text{batch size}$` (prefill, tens of thousands). No single kernel implementation is optimal across this entire range. The paper identifies three candidate implementations, each with a distinct performance profile:

- **ImplA: FastGEMV on CUDA Cores.** CUDA Cores are the general-purpose floating-point units on NVIDIA GPUs (as opposed to the specialized Tensor Cores). FastGEMV is an existing optimized GEMV kernel (paper cites wangsiping97/FastGEMV) that leverages CUDA Cores' lower latency and more flexible memory access patterns for vector-matrix operations. CUDA Cores have lower *peak* throughput than Tensor Cores but avoid the fixed tiling overhead and zero-padding waste.

- **ImplB: FlashDecoding++'s flat GEMM on Tensor Cores.** The custom kernel described in Section 4, with M padded to 8 and double buffering applied when N is large. This targets the "flat GEMM" regime where M is small but larger than 1.

- **ImplC: CUTLASS on Tensor Cores.** The standard, highly-optimized GEMM library with M padded to 64. This targets conventional GEMM shapes where both M and N are large enough to provide abundant parallelism, making the padding overhead negligible relative to the total computation.

**Why Static Dispatch Fails**

The paper provides concrete performance comparisons that motivate dynamic dispatch. For a Llama2-7B linear layer in the decode phase:
- Using ImplC (Tensor Core, cuBLAS) when M=1 achieves only **82.15%** of ImplA's (CUDA Core, FastGEMV) performance. The Tensor Core's higher peak throughput is outweighed by the padding waste and thread-block orchestration overhead.
- Using ImplA (CUDA Core, FastGEMV) when M=4 achieves only **49.75%** of ImplC's performance. Here, M is large enough that the Tensor Core's throughput advantage dominates, and CUDA Cores become the bottleneck.

These are not small differences — choosing the wrong implementation can halve performance. A static dispatch (e.g., "always use cuBLAS") leaves substantial performance on the table for every operation in at least one phase.

**The Key Insight: Only Four [N, K] Shapes Exist Per Model**

The search space of GEMM configurations in an LLM is enormous in principle: M, N, and K can each vary continuously. However, the paper observes a structural regularity that dramatically simplifies the problem:

For a given LLM, there are exactly **four distinct `[N, K]` shapes** across all GEMM operations in the transformer layers:

1. **K, Q, V projection:** `$[N, K] = [\text{HD} \times 3, \text{HD}]$` — where HD is the hidden dimension.
2. **O projection:** `$[N, K] = [\text{HD}, \text{HD}]$` — the output projection after attention.
3. **FFN1:** `$[N, K] = [\text{FD}, \text{HD}]$` — the first feedforward layer expands from hidden dimension to feedforward dimension.
4. **FFN2:** `$[N, K] = [\text{HD}, \text{FD}]$` — the second feedforward layer projects back from feedforward dimension to hidden dimension.

For Llama2-7B, these are `$[12288, 4096]$`, `$[4096, 4096]$`, `$[11008, 4096]$`, and `$[4096, 11008]$` respectively. This means the entire search space of GEMM configurations reduces to four `[N, K]` pairs, with only `$M$` varying at runtime (as a function of batch size and sequence length).

**The Offline Profiling and Inflection Point Discovery**

The heuristic dataflow is constructed through an offline, per-model profiling process (Figure 9b and 9c):

1. **For each of the four `[N, K]` shapes**, the system performs a sweep over `$M$` (starting from `$M=1$` and increasing).

2. **At each `$M$` value**, the system benchmarks ImplA (FastGEMV), ImplB (flat GEMM), and ImplC (CUTLASS) to measure their execution time for that particular `$[M, N, K]$` configuration.

3. **Two inflection points are identified:**
   - `$M_1$`: The smallest `$M$` where ImplB outperforms ImplA. Below `$M_1$`, CUDA Cores (ImplA) are faster; at and above `$M_1$`, the Tensor Core flat GEMM (ImplB) becomes faster.
   - `$M_2$`: The smallest `$M$` where ImplC outperforms ImplB. Below `$M_2$`, the custom flat GEMM (ImplB) is faster; at and above `$M_2$`, the standard CUTLASS GEMM (ImplC) becomes faster.

4. **A lookup table is constructed** mapping each `[N, K]` shape to its `$(M_1, M_2)$` inflection points.

**Why offline:** The profiling is done once per model per GPU, before any inference begins. It does not affect runtime performance. The profiling cost is bounded: four sweeps over M, each benchmarking three implementations. For each `$[N, K]$` shape, the sweep continues until `$M_2$` is found (i.e., until CUTLASS overtakes the flat GEMM).

**Runtime Dispatch**

During LLM inference, for every GEMM operation, the heuristic dataflow dispatcher:

1. Identifies the operation type (K/Q/V projection, O projection, FFN1, or FFN2), which determines the `[N, K]` shape.
2. Computes the current `$M$` — which is `$\text{batch size}$` for the decode phase, and `$\text{sequence length} \times \text{batch size}$` for the prefill phase.
3. Looks up `$(M_1, M_2)$` for this `[N, K]` shape from the offline-profiled table.
4. Selects the implementation:
   - If `$M < M_1$`: dispatch to **ImplA** (FastGEMV on CUDA Cores).
   - If `$M_1 \leq M < M_2$`: dispatch to **ImplB** (flat GEMM on Tensor Cores with double buffering).
   - If `$M \geq M_2$`: dispatch to **ImplC** (CUTLASS on Tensor Cores).

This dispatch decision is a constant-time array lookup and integer comparison — it adds negligible runtime overhead per GEMM call.

**Concrete Example: Llama2-7B on A100**

Figure 9(c) shows the resulting dispatch configuration for Llama2-7B. The four operations get their own inflection points:

- **K, Q, V projection (`[12288, 4096]`):** When `$M=1$` (decode, batch size 1), `$M < M_1$`, so FastGEMV on CUDA Cores is used. At larger `$M$` values (larger batch sizes or prefill), the dispatch shifts to flat GEMM or CUTLASS.

- **FFN1 (`[11008, 4096]`):** The inflection point `$M_1$` is encountered at a lower `$M$` value, so for batch-size-8 decode (`$M=8$`), the system uses the flat GEMM kernel (ImplB) rather than FastGEMV.

The specific inflection point values depend on the GPU's hardware characteristics (memory bandwidth, SM count, Tensor Core throughput, cache sizes) and are determined empirically rather than analytically. The paper does not provide a formula for predicting inflection points; it uses measurement.

**Design Choice: Why Three Implementations Instead of Two?**

A natural question is why the paper distinguishes ImplB (flat GEMM with M padded to 8) from ImplC (CUTLASS with M padded to 64). Couldn't CUTLASS be configured to tile M to 8 directly? The answer involves the tight coupling between M-tiling, N-tiling, K-tiling, and the memory hierarchy optimizations inside CUTLASS. CUTLASS's tiling strategies are co-designed: the choice of M-tile size affects shared memory allocation, register pressure, and the schedule of global memory loads. Simply changing the M-tile parameter in CUTLASS from 64 to 8 would likely break the carefully balanced tiling hierarchy that makes CUTLASS fast for large GEMMs. The paper's approach is to build a separate, purpose-built kernel for the flat GEMM regime (ImplB) that is optimized specifically for small M, while retaining CUTLASS (ImplC) for the large-M regime where its full tiling strategy is beneficial. The three-implementation design thus reflects a pragmatic division of labor: one kernel for each qualitatively distinct region of the M-dimension space.

**Cross-Platform Applicability**

The heuristic dataflow is not NVIDIA-specific. The paper reports that the same approach works on AMD GPUs (MI210, RX7900XTX) using ROCm. AMD GPUs have analogous hardware resources (CUDA Cores correspond to AMD's Stream Processors; Tensor Cores correspond to AMD's Matrix Cores), and the same three-way dispatch logic applies with AMD-specific inflection points determined by the same offline profiling procedure. This is a noteworthy practical contribution: the methodology is portable across GPU vendors, even though the specific inflection point values are hardware-dependent.

#### Overall System Integration

FlashDecoding++ is implemented as a set of custom CUDA/ROCm kernels integrated into a PyTorch-based inference runtime. The integration works at the operator level: each transformer operation (attention, linear projection, feedforward) is implemented as a custom PyTorch autograd Function or a direct kernel launch that replaces the default PyTorch implementation. The model definition itself is unchanged — only the backend implementation of each operation is replaced.

The **asynchronous softmax** is integrated into the attention computation, which already uses tiled approaches (FlashAttention for prefill, FlashDecoding for decode). It modifies the softmax step within these tiled attention kernels: instead of the synchronized partial softmax update, it uses the unified max value `$\phi$` and the fused softmax-value accumulation. The attention kernel thus gains the asynchronous partial computation property while retaining the tiling and memory management benefits of FlashAttention/FlashDecoding.

The **flat GEMM optimization** is integrated into the linear operation kernels for the decode phase. For each linear operation (K, Q, V, O projections, FFN1, FFN2), the heuristic dataflow dispatcher checks `$M$` and routes to either the flat GEMM kernel (ImplB) or an alternative. The flat GEMM kernel itself internally decides whether to use double buffering based on `$N$` (large N → memory-bounded → double buffering enabled).

The **heuristic dataflow** is implemented as a thin dispatch layer that wraps each linear operation. The offline-profiled lookup table is hard-coded as a set of constants per model per GPU. At initialization, the engine loads the lookup table for the target model and GPU; at runtime, each GEMM call passes through the dispatcher, which performs the `$M$` comparison and launches the appropriate kernel.

**Per-Model Configuration**

To deploy FlashDecoding++ on a new model, the following configuration steps are required:

1. **Extract the four `[N, K]` shapes** from the model architecture (HD, FD, number of heads).
2. **Profile the softmax input distribution** by running the model on representative inputs, collecting attention logits, and computing the `$>99.99\%$` bounds to determine the unified max value `$\phi$`. If the range is too wide (as with OPT-6.7B), disable the asynchronous softmax technique for this model.
3. **Run the offline profiling** for each `[N, K]` shape on the target GPU by sweeping `$M$` and benchmarking ImplA, ImplB, and ImplC to find `$M_1$` and `$M_2$`.
4. **Compile the lookup table** and provide it to the runtime engine.

The paper does not automate this configuration process; it is manual and model-specific. The authors frame future work on automating difficulty estimation for their softmax technique, but the current system requires per-model profiling.

**Scope Limitations**

As noted in Section 3.4, the asynchronous softmax technique is not applied to OPT-6.7B due to its wide attention logit distribution. This means the speedup for OPT-6.7B comes solely from the flat GEMM optimization and the heuristic dataflow — the softmax contribution is zero. This is visible in the experimental results (Figures 10b, 10e, 12b, 13c), where FlashDecoding++ still achieves speedups over baselines for OPT-6.7B, but potentially smaller than for Llama2-7B or ChatGLM2-6B where all three techniques apply.

Additionally, the flat GEMM optimization targets only the decode phase. The prefill phase uses conventional GEMM shapes (large M), so the flat GEMM kernel is not invoked there — ImplC (CUTLASS) handles prefill GEMMs via the heuristic dataflow. The asynchronous softmax, however, benefits both phases because attention tiling is used in both.

## 4. Key Insights and Innovations

### Innovation 1: Reframing the Partial Softmax Synchronization Problem as a Statistical Sparsity Opportunity

The standard approach to tiled attention since FlashAttention has treated the synchronized partial softmax update as an unavoidable cost of numerical stability — a mathematically necessary consequence of decomposing a non-linear normalization across parallel compute units. The field accepted that the ~20% synchronization overhead was the price of memory-efficient attention. FlashDecoding++ makes a conceptual break: it observes that the scaling factor in softmax is algebraically arbitrary (any constant `$\phi$` works, not just the true maximum), and then asks a *statistical* question rather than a mathematical one — "how often would a fixed, shared `$\phi$` cause numerical problems for real LLM inputs?"

The answer — that `>99.99%` of attention logits in Llama2-7B and ChatGLM2-6B fall within a range where a carefully chosen unified max value is safe — transforms the problem from an algorithmic one (how to parallelize an inherently sequential operation) into an empirical one (how to choose `$\phi$` and handle the rare overflow case). This is fundamentally different from prior work in attention optimization, which focused on memory access patterns (FlashAttention's IO-awareness) or work partitioning (FlashAttention-2, FlashDecoding). Those works accepted the synchronization as given and optimized around it; FlashDecoding++ recognizes that the synchronization itself is not mathematically required — it is only a numerical safety mechanism, and that safety mechanism can be replaced with a probabilistic one backed by a cheap fallback.

This is a **diagnostic reframing** rather than an algorithmic invention. The mathematical identity (Equation 3) is trivial — it's basic algebra that `$e^{x_i - \phi} / \sum e^{x_j - \phi}$` is invariant to `$\phi$`. What's novel is the insight that this trivial identity can be operationalized because LLM attention logits happen to be tightly bounded in practice. The paper doesn't prove this boundedness theoretically — it measures it empirically (Figure 5) and builds the optimization on that measurement. This is analogous to how sparse matrix formats exploit the empirical sparsity of real-world matrices rather than any theoretical guarantee of sparsity.

The **significance beyond performance** is that this opens a class of optimizations that condition on the *statistical regularities of neural network activations at inference time*. Rather than designing kernels that handle worst-case numerical ranges, one can design kernels for the common case and fall back to the general case only when needed. This is a design pattern with applications beyond softmax — any operation with mathematically required synchronization that statistical analysis shows is rarely necessary could be similarly de-synchronized.

The evidence that this works is the 1.37× average speedup over FlashDecoding (which uses synchronized softmax), with the technique disabled entirely for OPT-6.7B — proving that the optimization is not universally applicable but is effective where the statistical precondition holds.

---

### Innovation 2: Identifying the M-Dimension Padding Mismatch as the Root Cause of Flat GEMM Inefficiency, and Showing It's Fixable With a Two-Word Change (Pad to 8, Not 64)

Prior work on GPU GEMM libraries (cuBLAS, CUTLASS) optimized for the large-M regime because that's where GEMM traditionally lives — training, large-batch inference, scientific computing. The decode phase of LLM inference creates a regime (M = 1 to 8) that these libraries never targeted. The standard engineering response when M is too small for the library's tiling strategy is to pad with zeros and accept the waste — a consequence of reusing training-optimized kernels at inference time.

FlashDecoding++ makes two conceptual moves that distinguish it from prior flat-GEMM work. First, it **names the problem precisely**: it's not that flat GEMM is inherently slow, it's that the M-dimension padding size (64) is mismatched to the actual workload size (1–8), and this mismatch causes >50% computation under-utilization. The fix — padding to 8 instead of 64 — is almost embarrassingly simple in concept but requires rewriting the kernel because the tiling strategy (N-tile size, K-tile size, shared memory allocation) is co-designed with the M-tile size. Libraries like CUTLASS can't just be parameterized with a different M-tile; the entire kernel structure assumes M=64.

Second, it **surfaces a fundamental tension** in flat GEMM tiling that prior work didn't articulate: the choice of N-tiling size `$B_N$` trades off parallelism (`$N / B_N$` independent blocks) against the computation-to-memory ratio (larger `$B_N$` amortizes memory costs better). Figure 7 shows that this tradeoff has qualitatively different outcomes depending on `$N$`: for small `$N$`, the kernel is parallelism-bounded (not enough blocks to fill 108 SMs); for large `$N$`, it's memory-bounded. This diagnostic — that the same kernel has different bottlenecks at different `$N$` values even with the same `$M$` — is novel. Prior work treated flat GEMM as uniformly memory-bound; the paper shows it bifurcates.

This is an **incremental engineering contribution elevated by clear diagnosis**. The actual techniques (smaller M-padding, double buffering) are standard GPU optimization tools. What's distinctive is the analysis that reveals *why* standard libraries fail at this workload and *which* standard tools to apply under which conditions. The significance is practical: many LLM inference systems use cuBLAS/CUTLASS for decode-phase GEMMs, and this work shows that a purpose-built kernel for the flat regime is not just a nice-to-have but a necessity — the waste is >50%, which is too large to ignore at deployment scale.

---

### Innovation 3: Collapsing the GEMM Implementation Search Space Using the Structural Regularity of Transformer Layers

The problem of selecting the optimal GEMM kernel for a given (M, N, K) shape seems combinatorially intractable: M, N, K can each vary across orders of magnitude, GPU architectures differ, and kernel implementations have complex performance surfaces. Prior frameworks (DeepSpeed, TensorRT-LLM, FasterTransformer) side-stepped this by dispatching all GEMM operations to the same highly-optimized library (typically cuBLAS), accepting suboptimal performance for edge cases.

FlashDecoding++'s distinctive move is observing that the search space collapses dramatically because **transformer layers have only four distinct (N, K) shapes**, regardless of model size. All K, Q, V projections share one shape; the O projection has another; the two FFN layers have the remaining two. This structural regularity — a consequence of how transformer architectures are defined, not an empirical finding — means the infinite-seeming GEMM configuration space reduces to four one-dimensional sweeps over M. This makes exhaustive offline profiling feasible: for each of four shapes, benchmark three implementations across increasing M until both inflection points are found.

This is a **framing contribution** — the insight that the problem looks harder than it is because we were thinking about it at the wrong level of abstraction. Rather than building a general GEMM autotuner that handles arbitrary shapes (the approach of systems like TVM or Ansor), the paper recognizes that LLM inference has a specific, fixed shape structure that can be exploited with a simple lookup table. The payoff is that the heuristic dataflow is both simpler (no online autotuning, no ML-based cost models) and more reliable (deterministic dispatch, no risk of a learned model making wrong predictions) than general-purpose solutions.

The evidence that this matters is the 50.25% performance gap cited in Section 5: using the wrong implementation (Tensor Core vs. CUDA Core for a given M) can halve performance. Prior systems accepted this gap as the cost of using a general-purpose library; FlashDecoding++ eliminates it with a profiling strategy whose offline cost is bounded by the architecture.

The **significance beyond raw performance** is that this is a design pattern for inference engines: identify the structural invariants of the model family you're targeting, and use them to simplify what would otherwise be a complex optimization problem. For transformer-based LLMs, the invariant is the fixed set of (N, K) shapes. For other model families, the invariants would be different, but the principle — collapse the search space using architectural regularity — generalizes.

---

### Innovation 4: Demonstrating That Inference Optimizations Can Cross GPU Vendor Boundaries Without Modification

The LLM inference acceleration landscape is heavily NVIDIA-centric. FlashAttention, FlashDecoding, TensorRT-LLM, FasterTransformer, and CUTLASS are all CUDA-first or CUDA-only. Even when the algorithms are vendor-agnostic, the implementation investment to port to AMD's ROCm ecosystem is substantial, and few academic systems papers attempt it.

FlashDecoding++ demonstrates that all three of its optimizations work on AMD hardware (RX7900XTX and MI210) without substantive algorithmic changes — only the kernel implementation layer differs (CUDA vs. ROCm). This is not a deep theoretical insight but a **practical validation with ecosystem implications**: it establishes that the performance bottlenecks the paper identifies (synchronized softmax, flat GEMM padding, static dispatch) are not NVIDIA-specific quirks but general GPU characteristics that apply across vendors. The unified max value technique exploits a property of the softmax function itself; the flat GEMM optimization exploits the mismatch between library tile sizes and actual workload shapes; the heuristic dataflow exploits the performance crossover between general-purpose and specialized compute units. All three apply to AMD's hardware architecture as well.

The evidence is Figures 12 and 13, where FlashDecoding++ achieves up to 3.93× speedup over the Hugging Face baseline on AMD MI210 (no other optimized engines were available for comparison). This is significant because it suggests the techniques in FlashDecoding++ could form the basis of a vendor-neutral LLM inference optimization methodology — profiling per-GPU inflection points and per-model softmax bounds once, then benefiting from the same three optimizations regardless of the underlying hardware. In a landscape where AMD, Intel, and others are competing with NVIDIA for LLM inference workloads, this portability is a practical contribution that the paper reports but doesn't emphasize as an innovation — yet it arguably is one.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper evaluates inference performance — not model accuracy — so there is no traditional ML dataset. Instead, the evaluation uses the model weights and architectural configurations of three LLM families (Llama2, OPT, ChatGLM2) with varying input sequence lengths (128, 1K, 2K, 4K, 8K, 32K tokens depending on the model's maximum context length) and batch sizes (1, 2, 4, 8). The "dataset" is effectively the space of inference workloads defined by the Cartesian product of model, input length, and batch size.

- **Base model(s).** Four models spanning two scales and three families: **Llama2-7B** (32 layers, 32 heads, hidden dimension 4096, 4K context), **Llama2-13B** (40 layers, 40 heads, hidden dimension 5120, 4K context), **OPT-6.7B** (32 layers, 32 heads, hidden dimension 4096, 2K context), and **ChatGLM2-6B** (32 layers, 32 heads, hidden dimension 4096, 32K context). Models are chosen to represent mainstream open-source LLMs with varying architectures (standard decoder-only vs. bilingual chat) and context lengths (2K to 32K), enabling testing of whether the optimizations generalize across architectural differences. Note that OPT-6.7B is the model for which the asynchronous softmax technique is explicitly **disabled** due to its wide attention logit range (Figure 5), making it a useful test case for isolating the contributions of the flat GEMM and heuristic dataflow optimizations.

- **Metrics.** The paper reports two primary metrics: **throughput (tokens per second)** for the decode phase, and **first token latency (milliseconds)** for the prefill phase. Throughput is computed as the number of tokens generated per second during autoregressive decoding, measured at batch sizes 1, 2, 4, and 8. First token latency measures the end-to-end time from receiving the input prompt to producing the first output token, which encompasses the entire prefill-phase computation. All results are reported as absolute performance numbers (tokens/s or ms) overlaid with speedup bars relative to baselines (shown as secondary y-axes in Figures 10–13).

- **Baselines.** The paper compares against six baselines: **Hugging Face / PyTorch** (Wolf et al., 2020) — the default PyTorch transformer implementation with no specialized inference optimizations; **vLLM** (Kwon et al., 2023) — the PagedAttention-based serving system; **DeepSpeed** (Aminabadi et al., 2022) — with its inference-optimized kernel fusion and KV-cache management; **TensorRT-LLM** (NVIDIA, 2023) — the C++ inference engine built on FasterTransformer with FlashAttention integration; **OpenPPL** (SenseTime, 2023) — another C++ inference engine with kernel fusion; and **FlashAttention2 / FlashDecoding** (Dao et al., 2023) — the state-of-the-art attention optimization that FlashDecoding++ extends. Not all baselines are available for all models: OpenPPL does not support OPT-6.7B or ChatGLM2-6B; TensorRT-LLM fails to compile models with >8K input length; on AMD GPUs, only Hugging Face is available as a baseline.

- **Generation budget / compute accounting.** The paper does not use a "generation budget" in the machine learning sense (number of sampled solutions). Instead, the relevant resource is **GPU compute time**: all comparisons are wall-clock measurements of inference latency or throughput under identical hardware conditions. The compute cost is implicit in the measured time — the paper's claim is that for the same model, same input, and same hardware, FlashDecoding++ produces correct outputs in less time. There is no tradeoff between compute budget and answer quality; this is a pure systems optimization that preserves numerical correctness while reducing execution time. The "budget" dimension explored is the **batch size × sequence length** space, which determines the computational intensity of each workload configuration.

- **Cross-validation / statistical protocol.** No statistical significance testing, confidence intervals, or cross-validation is reported. The paper presents single-run performance measurements. This is standard for GPU kernel benchmarking papers, where performance is deterministic (fixed hardware, fixed inputs) and variance across runs is negligible. However, the paper does not discuss whether results were averaged over multiple runs, whether warm-up iterations were excluded, or whether any variance was observed. The offline profiling for the heuristic dataflow (finding inflection points `M_1` and `M_2`) is described as a one-time sweep with no mention of measurement noise or reproducibility.

### Main Quantitative Results

#### Decode Phase: End-to-End Throughput on NVIDIA GPUs

**Headline result (Figure 10):** FlashDecoding++ achieves up to **4.86× speedup** over Hugging Face implementations and an **average speedup of 1.37× over FlashDecoding** on the NVIDIA Tesla A100 across Llama2-7B, OPT-6.7B, and ChatGLM2-6B at batch sizes 1, 2, 4, and 8 with input lengths from 128 to 32K tokens.

**By model and GPU (Figure 10, all six subfigures):**

- **Llama2-7B on A100 (Figure 10a):** At batch size 1, FlashDecoding++ achieves roughly 800–1000 tokens/s depending on input length, with speedups of approximately 4× over Hugging Face, 1.3× over vLLM, 1.5× over DeepSpeed, 1.15× over TensorRT-LLM, and 1.37× over FlashDecoding. The absolute throughput decreases as input length increases (from 128 to 32K), but the relative speedup over baselines is maintained or grows. At batch size 8, absolute throughput reaches approximately 1000 tokens/s for short inputs, with FlashDecoding++ showing a more modest advantage (roughly 1.1–1.2× over FlashDecoding and TensorRT-LLM) as the flat GEMM optimization becomes less impactful at larger M.

- **OPT-6.7B on A100 (Figure 10b):** Despite the asynchronous softmax being **disabled** for OPT-6.7B (Figure 5), FlashDecoding++ still achieves up to roughly 3× speedup over Hugging Face. At batch size 1, throughput is approximately 400–600 tokens/s. The speedup over FlashDecoding is approximately 1.1–1.2× — notably **smaller** than for Llama2-7B, consistent with the flat GEMM and heuristic dataflow optimizations alone providing less aggregate benefit than when combined with the asynchronous softmax. At batch size 8, throughput reaches approximately 500 tokens/s.

- **ChatGLM2-6B on A100 (Figure 10c):** FlashDecoding++ achieves up to roughly 3× speedup over Hugging Face. At batch size 1 with 128 input length, throughput is approximately 500 tokens/s, with speedups of approximately 1.3× over FlashDecoding. ChatGLM2-6B supports up to 32K context length, and at 32K input, the throughput drops to roughly 100 tokens/s but the relative speedup over baselines persists (approximately 2× over TensorRT-LLM where it can compile, and 1.2× over FlashDecoding). Notably, TensorRT-LLM cannot compile ChatGLM2-6B with >8K input length (shown as blank bars), while FlashDecoding++ handles 32K context.

- **Llama2-7B on RTX3090 (Figure 10d):** On the consumer-grade RTX3090, absolute throughput is lower (approximately 200–400 tokens/s at batch size 1) due to reduced memory bandwidth and fewer SMs. FlashDecoding++ achieves up to approximately 2.5× speedup over Hugging Face and roughly 1.2–1.3× over FlashDecoding. The pattern of batch-size-dependent advantage (larger gaps at smaller batch sizes) is consistent with the A100 results.

- **OPT-6.7B on RTX3090 (Figure 10e):** Similar to the A100 pattern, speedups are moderate (roughly 1.5–2× over Hugging Face, ~1.1× over FlashDecoding) due to the disabled asynchronous softmax. At batch size 8 with 2K input (max for OPT-6.7B), throughput reaches approximately 400 tokens/s.

- **ChatGLM2-6B on RTX3090 (Figure 10f):** Throughput at batch size 1 is approximately 150–300 tokens/s. Speedups over Hugging Face reach roughly 2.5×, with FlashDecoding++ outperforming FlashDecoding by approximately 1.15–1.25×. The 32K context length configuration produces roughly 50 tokens/s at batch size 1.

**Key observation across all NVIDIA decode results:** The absolute speedup varies by model, batch size, and input length, but the ordering of systems is consistent: FlashDecoding++ ≈ TensorRT-LLM (where available) > FlashDecoding ≈ vLLM ≈ OpenPPL > DeepSpeed ≫ Hugging Face. The gap between FlashDecoding++ and the next-best system widens at small batch sizes (batch size 1) — exactly where the flat GEMM optimization (M padded to 8 instead of 64) provides its largest benefit — and narrows at batch size 8 where M is larger and the conventional GEMM libraries become more efficient.

---

#### Prefill Phase: First Token Latency on NVIDIA GPUs

**Headline result (Figure 11):** FlashDecoding++ achieves up to **1.40× speedup** over Hugging Face implementations on prefill-phase first token latency, with average speedups of 1.05× over DeepSpeed, 1.06× over TensorRT-LLM, 1.09× over FlashAttention2, and 1.08× over FlashDecoding.

**By model (Figure 11, five subfigures):**

- **Llama2-7B on A100 (Figure 11a):** At 1K input length and batch size 1, first token latency is approximately 30–40ms for FlashDecoding++ (labeled "Ours-FTL"), with speedups of roughly 1.3× over Hugging Face, 1.05× over FlashDecoding and FlashAttention2, and approximately 1.0× (parity) with TensorRT-LLM. At 32K input length, latency increases to roughly 4000ms, with FlashDecoding++ maintaining a slight advantage (approximately 1.1×) over FlashDecoding. The prefill speedups are substantially **smaller** than the decode speedups — this is expected because the prefill phase uses conventional GEMMs (large M) where the flat GEMM optimization provides no benefit, and the heuristic dataflow dispatches to ImplC (CUTLASS) which is the same library used by TensorRT-LLM and other baselines. The asynchronous softmax is the primary contributor to prefill gains.

- **Llama2-13B on A100 (Figure 11b):** Similar pattern to Llama2-7B but with higher absolute latency due to the larger model. At 1K input, first token latency is approximately 60–80ms; at 32K, approximately 8000ms. FlashDecoding++ achieves speedups of approximately 1.1× over FlashDecoding at 32K input. TensorRT-LLM fails to compile at >8K input, shown as blank bars beyond 8K.

- **ChatGLM2-6B on A100 (Figure 11c):** At 1K input length, first token latency is roughly 30ms with FlashDecoding++ achieving approximately 1.15× over FlashDecoding. The model supports 32K context but at that length only batch sizes 1 and 2 are shown (batch sizes 4 and 8 are blank, likely due to memory constraints on the 80GB A100). At 32K input, latency is approximately 2000ms.

- **Llama2-7B on RTX3090 (Figure 11d):** First token latency at 1K input is approximately 60–80ms, roughly 2× the A100 latency due to the RTX3090's lower memory bandwidth and fewer compute units. FlashDecoding++ achieves approximately 1.15× speedup over FlashDecoding at 8K input.

- **ChatGLM2-6B on RTX3090 (Figure 11e):** Latency at 1K input is roughly 60ms, with FlashDecoding++ showing approximately 1.1× speedup over FlashDecoding. At 8K input, latency is approximately 1000ms.

**Why prefill gains are modest compared to decode gains:** The paper's three techniques contribute differently to each phase. The asynchronous softmax benefits both phases. The flat GEMM optimization benefits **only** the decode phase (where M is small). The heuristic dataflow benefits both phases but the decode phase is where the alternative implementations (FastGEMV, flat GEMM) matter most; in the prefill phase, M is large enough that all GEMMs dispatch to ImplC (CUTLASS), so the dispatcher adds no value over simply using CUTLASS directly. The 1.05–1.09× prefill speedups over TensorRT-LLM, FlashAttention2, and FlashDecoding thus primarily reflect the asynchronous softmax contribution alone, suggesting it provides roughly a 5–9% reduction in attention time for the prefill phase.

#### Decode Phase on AMD GPUs

**Headline result (Figures 12 and 13):** FlashDecoding++ achieves up to **2.27× speedup** on AMD RX7900XTX and up to **3.93× speedup** on AMD MI210 compared to the Hugging Face baseline. No other optimized inference engines were available for comparison on AMD hardware.

**RX7900XTX results (Figure 12):**

- **Llama2-7B (Figure 12a):** At batch size 1 with 128 input length, FlashDecoding++ achieves approximately 250 tokens/s, roughly 2.0× the Hugging Face baseline (~125 tokens/s). At batch size 8 with 4K input, throughput reaches approximately 400 tokens/s with roughly 1.8× speedup. The absolute throughput drops as input length increases (128 → 1K → 2K → 4K) but the relative speedup is maintained at roughly 1.8–2.3× across all configurations.

- **OPT-6.7B (Figure 12b):** At batch size 1, FlashDecoding++ achieves roughly 150–200 tokens/s with speedups of approximately 1.5–1.8× over Hugging Face. The speedup is smaller than for Llama2-7B, consistent with OPT-6.7B not benefiting from the asynchronous softmax. At batch size 8, throughput reaches roughly 300 tokens/s.

**MI210 results (Figure 13):**

- **Llama2-7B (Figure 13a):** The MI210 is a datacenter GPU with higher memory bandwidth than the consumer RX7900XTX. At batch size 1 with 128 input, FlashDecoding++ achieves approximately 400 tokens/s, roughly 3.5× the Hugging Face baseline. The speedup reaches 3.93× at the best configuration. At batch size 8 with 2K input, throughput reaches approximately 600 tokens/s.

- **Llama2-13B (Figure 13b):** The larger model pushes the MI210's 64GB memory harder. At batch size 1 with 128 input, throughput is approximately 200 tokens/s with roughly 3× speedup. At batch size 8 with 4K input, throughput reaches roughly 300 tokens/s. The configs with 8K input at batch sizes 4 and 8 are blank — likely exceeding the MI210's memory capacity for a 13B model with large KV-cache.

- **OPT-6.7B (Figure 13c):** At batch size 1, throughput is approximately 200–250 tokens/s with roughly 2× speedup. The smaller speedup relative to Llama2-7B on the same GPU again confirms the contribution of the asynchronous softmax optimization.

**Significance of AMD results:** FlashDecoding++ is the **only optimized inference engine evaluated on AMD GPUs** in this paper. The baselines (vLLM, DeepSpeed, TensorRT-LLM, FlashDecoding) are CUDA-only or did not have working ROCm ports at the time of evaluation. This makes the AMD results both a strength (demonstrating cross-platform portability) and a limitation (no comparisons against optimized AMD baselines, only against unoptimized PyTorch). The 3.93× speedup on MI210 cannot be attributed solely to the three optimizations described — part of the gain comes from basic kernel fusion and efficient memory management that any inference engine would provide over raw PyTorch. A fairer comparison would require an optimized ROCm inference engine as baseline, but none was available.

#### Overall Performance Summary

The paper's summary claim in the abstract — "average speedup of 1.37× compared to state-of-the-art LLM inference engines on mainstream LLMs" — refers specifically to the comparison with FlashDecoding on the Tesla A100 across all tested models and configurations. The breakdown of this average:

- **Decode phase on A100:** 1.37× over FlashDecoding (Figure 10), with individual comparisons of 1.24× over vLLM, 1.44× over DeepSpeed, 1.13× over TensorRT-LLM, and 1.24× over OpenPPL.
- **Prefill phase on A100:** 1.08× over FlashDecoding, 1.05× over DeepSpeed, 1.06× over TensorRT-LLM, 1.09× over FlashAttention2 (Figure 11).
- **AMD GPUs:** No comparison with optimized engines available, so no "state-of-the-art" comparison exists — only 2.27× to 3.93× over unoptimized PyTorch.

The 4.86× maximum speedup over Hugging Face occurs on a single configuration (likely Llama2-7B, batch size 1, short input length on A100, where all three optimizations provide their maximum benefit and the baseline is least optimized for small-batch decode).

### Ablation Studies and Robustness Checks

**Implicit ablation: OPT-6.7B as a softmax-disabled baseline:** The paper does not conduct traditional "remove one component" ablation experiments. However, the inclusion of OPT-6.7B — for which the asynchronous softmax is explicitly disabled (Section 3, Figure 5) — serves as an implicit ablation. Comparing the speedup of OPT-6.7B against the speedup of Llama2-7B on the same hardware isolates the contribution of the asynchronous softmax technique. On the A100 decode phase, Llama2-7B achieves approximately 1.37× over FlashDecoding while OPT-6.7B achieves approximately 1.1–1.2× over FlashDecoding (Figures 10a vs. 10b). The difference of roughly 0.17–0.27× can be attributed to the asynchronous softmax, which is consistent with the paper's claim that the synchronized softmax update accounts for ~18.8% of attention computation (Section 3) — note that the 18.8% figure refers to attention computation specifically, not end-to-end inference, so the end-to-end contribution from eliminating this overhead would be somewhat diluted by non-attention operations.

**Varying input length as robustness check:** The paper tests input lengths from 128 to 32K tokens (model-dependent), which demonstrates that the optimizations do not degrade at longer sequences. The flat GEMM optimization's benefit is independent of input length (it depends on M, the batch size, not the KV-cache size). The asynchronous softmax's benefit also scales with input length because longer sequences mean larger attention matrices and more partial softmax computations — the synchronization overhead as a fraction of attention time may increase or stay constant. The results show that relative speedups over baselines are maintained or grow at longer sequences (e.g., Figure 10a, batch size 1: speedup over FlashDecoding is roughly 1.3× at 128 input and roughly 1.4× at 32K input for Llama2-7B), suggesting that FlashDecoding++'s advantages are at minimum not eroded by long contexts.

**Varying batch size as workload characteristic sweep:** The batch size sweep (1, 2, 4, 8) tests the heuristic dataflow's ability to dispatch correctly across the M-dimension range. At batch size 1, the system dispatches to CUDA Cores (ImplA) for the K, Q, V projection in the Llama2-7B example (Figure 9c); at batch size 8, it dispatches to the flat GEMM kernel (ImplB) for FFN1. The fact that FlashDecoding++ maintains performance advantages across all batch sizes — not just at the extremes — is evidence that the offline-profiled inflection points correctly partition the M-dimension space (the heuristic dataflow is not systematically misclassifying some regions).

**Model architecture sweep as generalizability check:** Testing across three model families (Llama2, OPT, ChatGLM2) with different hidden dimensions (4096, 5120), feedforward dimensions (11008 for Llama2-7B), numbers of layers (32, 40), and context lengths (2K, 4K, 32K) demonstrates that the four `[N, K]` shape regularity holds and that the heuristic dataflow profiling strategy generalizes. There is no degradation pattern suggesting that some architectural choices are incompatible with the optimizations.

**GPU hardware sweep:** Testing on four GPUs (A100 datacenter, RTX3090 consumer, MI210 datacenter AMD, RX7900XTX consumer AMD) demonstrates that the optimization principles (padding M to 8, double buffering when memory-bound, CUDA vs. Tensor Core dispatch) are not tied to a specific GPU microarchitecture or vendor. The inflection points `M_1` and `M_2` differ per GPU (as expected given different SM counts, memory bandwidths, and cache sizes), but the methodology of offline profiling to find them is hardware-agnostic.

**No sensitivity analysis on unified max value `$\phi$`:** The paper does not explore how the choice of `$\phi$` affects performance or how sensitive the 99.99% coverage threshold is. It reports a single `$\phi$` per model derived from empirical distributions (Figure 5) but does not vary it to see how much the safe range can be tightened or whether a more aggressive `$\phi$` (e.g., covering only 99% of inputs) with more frequent recomputation would be faster or slower overall. This is a notable missing ablation — the recomputation fallback overhead is claimed "negligible" but never quantified under different `$\phi$` choices.

**No component-wise timing breakdown:** While the paper cites precise overhead percentages (18.8% for synchronized softmax update, >50% for flat GEMM under-utilization, 50.25% gap for static dataflow), these appear to be isolated microbenchmarks, not end-to-end timing breakdowns showing what fraction of total inference time each bottleneck occupies before and after optimization. Figure 10 shows only end-to-end throughput; there is no stacked bar chart showing time spent in attention, linear projections, and feedforward networks with and without FlashDecoding++'s optimizations. This makes it difficult to verify that the claimed overheads (18.8% of attention, >50% of flat GEMM) translate to the expected proportion of end-to-end speedup.

**No comparison against alternative softmax parallelization strategies:** The paper compares against FlashDecoding and FlashAttention (which use synchronized partial softmax updates) but does not compare against alternative softmax parallelization approaches such as computing the global maximum via a parallel reduction tree and then broadcasting (which would also avoid the incremental update scheme but with a different cost profile). This is not necessarily a weakness — the contribution is replacing synchronization with a fixed constant, not exploring all possible synchronization alternatives — but it means the claim that asynchronous softmax is *optimal* (vs. simply *better than the status quo*) is not fully supported.

### Critical Assessment

**Claim from the executive summary: "FlashDecoding++ achieves up to 4.86× speedup over Hugging Face and 1.37× over FlashDecoding."**

**What was tested:** The claim is supported by Figures 10, 11, 12, and 13, which show end-to-end throughput and latency measurements across three model families, four GPUs, multiple batch sizes, and multiple input lengths. The 4.86× figure over Hugging Face appears on an NVIDIA GPU (likely A100, Llama2-7B, decode phase, batch size 1), which is a configuration that maximizes the contrast between optimized and unoptimized execution. The 1.37× figure is an average specifically over FlashDecoding on the A100, not over all baselines or all hardware.

**What was not tested:** The 1.37× is an average, not a median, geometric mean, or any other measure that is less sensitive to outlier configurations. The paper does not specify how the average is computed (arithmetic mean over what units — all configurations weighted equally? over models? over batch sizes?). Without this detail, a few highly favorable configurations could inflate the average. Furthermore, the comparison with TensorRT-LLM — which is arguably the strongest production baseline — shows only a 1.13× advantage for the decode phase, which is substantially smaller than the 1.37× over FlashDecoding. The abstract's framing of FlashDecoding as "the state-of-the-art LLM inference engine" is debatable: TensorRT-LLM outperforms FlashDecoding on most configurations in the paper's own results, making the 1.37× figure somewhat misleading when presented as the primary headline number.

**Qualification:** The speedups are **model-dependent and phase-dependent**. The prefill phase shows only 1.05–1.09× gains, and OPT-6.7B (no asynchronous softmax) shows smaller decode gains than Llama2-7B. A user deploying FlashDecoding++ should expect roughly 5–9% improvement on prefill latency, 10–20% improvement on decode throughput for OPT-like models, and 25–40% improvement on decode throughput for Llama2/ChatGLM2-like models, relative to FlashDecoding. The 4.86× figure should be understood as the maximum possible gain over an unoptimized baseline, not a typical gain over a production system.

---

**Claim: "Asynchronized softmax with unified max value eliminates ~20% overhead of attention computation."**

**What was tested:** The paper reports a profiling result that the synchronized partial softmax update accounts for 18.8% of attention computation in Llama2-7B inference on A100 with 1024 input length (Section 3). Figure 5 demonstrates that >99.99% of softmax inputs fall within the safe range for Llama2-7B and ChatGLM2-6B. The end-to-end results show speedups consistent with removing a fraction of attention time.

**What was not tested:** The paper does not directly measure the reduction in attention computation time attributable to the asynchronous softmax in isolation. There is no microbenchmark showing attention kernel latency with and without the technique, or showing the recomputation fallback rate under realistic workloads. The 18.8% figure is a profiling result from the *original* synchronized implementation, but the paper never reports the corresponding percentage for the *optimized* implementation — what fraction of attention time does the asynchronous version spend? Is the overhead reduced to zero, or does the final reduction step (summing numerator and denominator accumulators across partial results) introduce a new, smaller cost? Additionally, the recomputation fallback rate is claimed "negligible" based on the 99.99% statistical coverage, but the actual measured fallback rate at inference time (e.g., what percentage of softmax rows triggered recomputation during the benchmark runs) is not reported. The coverage statistic in Figure 5 was measured "with different inputs" but the number and diversity of those inputs is unspecified — if they are drawn from the same distribution as the benchmark inputs, the estimate could be optimistic.

**Qualification:** The technique is **not universal** — it is disabled for OPT-6.7B — and even for supported models, it depends on the empirical attention logit distribution remaining bounded under deployment conditions. Distribution shift (e.g., out-of-distribution prompts that produce unusual attention patterns) could increase the recomputation rate and erode the speedup. The paper does not test robustness to input distribution.

---

**Claim: "Flat GEMM optimization eliminates >50% computation under-utilization from zero-padding in cuBLAS/CUTLASS."**

**What was tested:** The paper analyzes the computation-to-memory ratio as a function of tiling parameters (Equation 5), characterizes the parallelism-bounded vs. memory-bounded regimes (Figure 7), and implements a custom flat GEMM kernel with M tiled to 8 and double buffering. The end-to-end decode results show substantial speedups, particularly at small batch sizes where flat GEMM dominates.

**What was not tested:** The paper does not provide a direct before/after comparison of the flat GEMM kernel's utilization (e.g., percentage of Tensor Core cycles spent on non-zero multiplications). The >50% under-utilization figure is described as applying to "previous designs" that pad M to 64, but the actual utilization of FlashDecoding++'s flat GEMM kernel (padding M to 8) is never quantified. For M=1, padding to 8 still wastes 7/8 of the M-dimension computation — this is better than padding to 64 (which wastes 63/64), but it's not zero waste. The paper never states what utilization FlashDecoding++ achieves. A microbenchmark comparing the custom flat GEMM kernel against cuBLAS on identical (M, N, K) shapes would strengthen this claim substantially, but is not provided.

**Qualification:** The benefit of the flat GEMM optimization diminishes as batch size increases — at batch size 8, M=8 matches the hardware tile size, and the advantage over cuBLAS (which pads to 64) is reduced because cuBLAS only wastes 56/64 of its work rather than 63/64. This is consistent with the narrowing speedup gaps at larger batch sizes in Figure 10. The optimization is most valuable for single-query or small-batch serving scenarios.

---

**Claim: "Heuristic dataflow avoids up to 50.25% performance loss from static dispatch."**

**What was tested:** The paper measures the performance gap between using Tensor Core vs. CUDA Core for specific linear layers: for a Llama2-7B linear layer in the decode phase with batch size 1, CUDA Core (FastGEMV) outperforms Tensor Core (cuBLAS) — Tensor Core achieves only 82.15% of CUDA Core performance. Conversely, at batch size 4, Tensor Core achieves 100% while CUDA Core achieves only 49.75% — a 50.25% gap. The heuristic dataflow's offline profiling infrastructure and runtime dispatch logic are described in Figure 9.

**What was tested with the integrated system:** The paper shows that FlashDecoding++ outperforms all baselines across the tested configurations, which is consistent with the heuristic dataflow correctly dispatching to the best implementation for each operation. However, there is **no ablation isolating the heuristic dataflow's contribution**: no comparison where FlashDecoding++ uses a static dispatch strategy (e.g., "always use cuBLAS" or "always use FastGEMV") vs. the heuristic strategy. Without this, we cannot distinguish how much of the end-to-end gain comes from the heuristic dataflow's dynamic dispatch vs. from each individual kernel being faster than the baselines' kernels. It is possible that the flat GEMM kernel (ImplB) is simply faster than cuBLAS (ImplC) across all tested configurations, and the heuristic dispatch to CUDA Cores (ImplA) at batch size 1 is not actually needed — the results would look similar without it.

**Qualification:** The 50.25% gap is between two specific implementations at two specific batch sizes. This is a bound on how badly wrong a static choice can go, not an average expected loss. The paper frames this as representing up to a 50.25% performance loss from static dataflow, but this is an extremum, not a typical value. The *average* loss from static dispatch across all configurations is not reported.

---

**Claim: "Achieves speedups on both NVIDIA and AMD GPUs, proving cross-platform applicability."**

**What was tested:** Figures 12 and 13 show 2.27× to 3.93× speedups over Hugging Face on AMD RX7900XTX and MI210.

**What was not tested:** No optimized AMD baselines exist. The comparison is against unoptimized PyTorch, which includes no attention tiling, no specialized GEMV/GEMM kernels, no kernel fusion, and no KV-cache management. A significant fraction of the 3.93× speedup on MI210 would be achieved by any competent inference engine (e.g., porting FlashDecoding to ROCm would recover some of this gap). The paper cannot claim that FlashDecoding++ is faster than other optimized engines on AMD because no such engines were available. The cross-platform claim is thus narrower than it appears: FlashDecoding++ achieves speedups over an unoptimized PyTorch baseline on AMD GPUs, but its performance relative to a hypothetical optimized ROCm inference engine is unknown.

---

**Missing experiments that would strengthen the paper:**

1. **Component ablation:** FlashDecoding++ with only asynchronous softmax, only flat GEMM, only heuristic dataflow, and all three, to quantify each technique's individual contribution to end-to-end speedup. This is the most conspicuous omission in a systems paper claiming three distinct contributions.

2. **Attention microbenchmark:** Direct latency measurement of the attention kernel (prefill and decode) comparing FlashDecoding++'s asynchronous softmax against FlashAttention's/FlashDecoding's synchronized softmax, with and without the recomputation fallback path triggered.

3. **Flat GEMM microbenchmark:** Direct throughput comparison of FlashDecoding++'s flat GEMM kernel against cuBLAS and CUTLASS on representative flat-GEMM shapes from LLM decode, reporting achieved Tensor Core utilization.

4. **Static dispatch ablation:** FlashDecoding++ with all GEMM operations forced to a single implementation (cuBLAS only, FastGEMV only, flat GEMM only) to measure the end-to-end impact of the heuristic dataflow's dynamic dispatch.

5. **Sensitivity to unified max value:** Varying `$\phi$` and measuring the recomputation fallback rate and end-to-end throughput to determine whether the 99.99% coverage threshold is optimal or conservative.

6. **Standard deviation across runs:** Although GPU kernel performance is largely deterministic, measurement noise from system scheduling, thermal throttling, and GPU clock variability exists. Reporting variance (or stating that it was negligible) would improve reproducibility.

7. **Performance on larger models (30B+, 70B):** All tested models are 6–13B parameters. Scaling trends — whether the flat GEMM optimization becomes more or less important at larger hidden dimensions, whether attention overhead grows with model size — are unexplored.

8. **Memory footprint comparison:** The double buffering technique allocates additional shared memory per thread block. The paper does not report whether this reduces the maximum batch size or sequence length compared to baselines, which would be important for deployment planning.

---

**Overall assessment:** The experiments demonstrate that FlashDecoding++ is a faster LLM inference engine than the tested baselines on the tested configurations. The evidence for the *specific mechanisms* claimed (asynchronous softmax eliminating synchronization, flat GEMM tiling recovering under-utilized computation, heuristic dispatch avoiding static dispatch loss) is indirect — it comes from consistency between the profiling analysis and the end-to-end results, not from controlled component-wise measurements. The paper would be strengthened considerably by ablation studies isolating each technique's contribution. The speedup claims should be understood as **upper bounds** on what a deployment can expect: 4.86× over unoptimized PyTorch (a baseline no production system uses), 1.37× average over FlashDecoding on A100 (with substantial variance by model and phase), and 2.27–3.93× over PyTorch on AMD (where no optimized comparison exists). The techniques are genuine and well-motivated, but the experimental methodology does not fully separate their individual effects from the aggregate system improvement.

## 6. Limitations and Trade-offs

### The Asynchronous Softmax Technique Fails on Models with Wide Attention Logit Distributions

**The assumption or constraint:** The asynchronous softmax with unified max value depends entirely on the empirical observation that `>99.99%` of attention logits in certain models (Llama2-7B, ChatGLM2-6B) fall within a narrow numerical range where a single shared scaling factor `$\phi$` can be chosen without causing overflow or precision loss. The paper states this boundary explicitly:

> "For OPT-6.7B, we do not apply the technique in this section because of the large range in Figure 5."

OPT-6.7B's attention logit range is `$[-496.8, 363.5]$`, more than an order of magnitude wider than Llama2-7B's `$[-16.8, 6.5]$`. In this regime, no single `$\phi$` can keep all `$x_i - \phi$` within safe floating-point bounds, so the technique is disabled entirely.

**The consequence:** The asynchronous softmax optimization — which the implicit ablation via OPT-6.7B suggests contributes roughly 15–20% of the decode-phase speedup — is **not universally applicable**. For any model whose attention logits span a wide range, the technique provides zero benefit. The paper provides no method for predicting whether a new model will have a narrow or wide logit distribution without profiling it first; the property is empirical, not architectural. A practitioner deploying FlashDecoding++ on a new model family must first run a profiling step to measure the attention logit distribution, and if the range exceeds safe bounds (which the paper does not precisely define — the thresholds `a` and `b` from Figure 6 are mentioned but their exact values and how they map to float32 overflow boundaries are not specified), the expected speedup is reduced by the full contribution of this optimization. Furthermore, even for "compatible" models, distribution shift at deployment time (e.g., out-of-distribution inputs that produce unusual attention patterns) could cause the actual recomputation fallback rate to exceed the predicted 0.01%, eroding the speedup in unpredictable ways.

**What evidence exists in the paper:** Figure 5 provides the empirical logit distributions for three models, and Figure 10b/e (OPT-6.7B decode results) shows the consequence: speedups over FlashDecoding drop to 1.1–1.2× for OPT-6.7B compared to 1.37× for Llama2-7B, consistent with the asynchronous softmax being the primary differentiator. However, the paper never measures the actual recomputation fallback rate during inference, never defines the precise overflow/underflow thresholds, and never tests whether the 99.99% coverage holds under out-of-distribution prompts.

**Mitigation status:** The recomputation fallback (reverting to synchronized partial softmax when overflow is detected) is a **correctness safety net**, not a performance mitigation — it guarantees that outputs remain numerically correct, but it recovers none of the lost speedup for the overflow case. The paper does not propose any technique to extend the asynchronous softmax to wide-range models, nor does it provide guidance on what fraction of models in the broader LLM ecosystem would be compatible. The limitation is acknowledged but treated as a model-specific scope constraint rather than a problem to be solved.

### Difficulty Estimation Cost Is Completely Unaccounted for in Reported Speedups

**The assumption or constraint:** The heuristic dataflow with hardware resource adaption requires per-model, per-GPU offline profiling to determine the inflection points `$M_1$` and `$M_2$` for each of the four `$[N, K]$` shapes. Additionally, the asynchronous softmax requires profiling the attention logit distribution to select the unified max value `$\phi$` and verify that the model's logit range is compatible. The paper describes this profiling as offline and one-time:

> "Note that the decision flow are executed offline, it does not affect the performance of runtime LLM inference."

While true at runtime, this profiling is **not free** — it requires benchmarking three kernel implementations across a sweep of M values for four shapes per model, plus collecting attention logit statistics from representative inputs. The paper never quantifies this profiling cost (how many GPU-hours? how many representative inputs are needed for reliable logit statistics?).

**The consequence:** The paper's speedup claims — 1.37× over FlashDecoding, 4.86× over Hugging Face — are measured **after** the profiling investment has been made. For a practitioner deploying FlashDecoding++ on a single model and GPU, the profiling cost might be amortized over millions of inferences and become negligible. But for deployments involving multiple models, frequent model updates, or heterogeneous GPU fleets (different GPU models require separate profiling), the profiling cost could become a meaningful barrier to adoption. More importantly, the profiling methodology itself has no validation: the paper does not demonstrate that inflection points `$M_1$` and `$M_2$` found via one sweep generalize to different input distributions (e.g., different sequence lengths might change the effective memory bandwidth utilization and shift inflection points), nor does it show how many profiling measurements are needed for reliable inflection point estimation. If the profiling is noisy or the inflection points are sensitive to the specific profiling workload, the heuristic dataflow could make suboptimal dispatch decisions at runtime, regressing toward the static-dispatch performance the technique was designed to avoid.

**What evidence exists in the paper:** None. The profiling methodology is described qualitatively (Figure 9b), but profiling time, the sweep granularity over M, the number of profiling iterations per configuration, and the criteria for determining when an inflection point is "found" are all unspecified. The paper includes no analysis of how profiling cost scales with model size or GPU count.

**Mitigation status:** Not addressed. The paper frames offline profiling as a non-issue because it is "offline," but this conflates *when* the cost occurs with *whether the cost exists*. No attempt is made to reduce profiling cost (e.g., via interpolation between M values, transfer learning of inflection points across similar GPUs, or analytical models that predict inflection points from hardware parameters), nor is the profiling cost reported alongside the runtime speedups to enable a holistic cost-benefit analysis.

### No Component-Wise Ablation Prevents Attributing Speedup to Specific Techniques

**The assumption or constraint:** The paper presents three distinct contributions — asynchronous softmax, flat GEMM optimization, and heuristic dataflow — but evaluates them only as an integrated system. The experimental results (Figures 10–13) show end-to-end throughput and latency of the complete FlashDecoding++ engine against baselines, but never isolate the contribution of each technique individually. The paper's framing implies that all three are necessary for the reported speedups, but the evidence does not distinguish between a scenario where each technique provides a roughly equal fraction of the total gain and a scenario where, say, the flat GEMM optimization alone accounts for 80% of the improvement and the other two contribute marginally.

**The consequence:** A practitioner deciding whether to adopt FlashDecoding++ — or to implement only a subset of its techniques — has no basis for estimating the marginal benefit of each component. If the asynchronous softmax requires careful per-model profiling and a fallback code path but contributes only 3% of the total speedup, it may not be worth the engineering complexity. Conversely, if the flat GEMM optimization alone provides most of the gain, a simpler system that only replaces cuBLAS with the custom flat GEMM kernel might achieve nearly the same performance with less integration effort. The lack of ablation also makes it impossible to verify the paper's causal claims: is the 1.37× speedup over FlashDecoding primarily due to the asynchronous softmax (which FlashDecoding lacks), the flat GEMM optimization (which addresses a bottleneck FlashDecoding does not target), or the heuristic dataflow (which FlashDecoding could in principle adopt)? Without ablation, the paper demonstrates that FlashDecoding++ as a whole is faster than FlashDecoding, but not *why*.

**What evidence exists in the paper:** The OPT-6.7B results (Figure 10b/e, 12b, 13c) serve as a partial, implicit ablation: because the asynchronous softmax is disabled for OPT-6.7B, the speedup over FlashDecoding is reduced from ~1.37× (Llama2-7B) to ~1.1–1.2× (OPT-6.7B). This suggests that the asynchronous softmax contributes roughly 0.15–0.25× of speedup, and the flat GEMM + heuristic dataflow contribute the remaining 1.1–1.2×. However, this inference confounds model differences (OPT-6.7B has different hidden dimensions, different layer counts, and different attention patterns than Llama2-7B) with technique contributions — the smaller speedup on OPT could be partly because its particular `$[N, K]$` shapes benefit less from the flat GEMM optimization, not solely because the asynchronous softmax is absent.

**Mitigation status:** None. The paper does not report any ablation study, nor does it discuss the absence of one. This is the most significant gap between the paper's claims (three distinct technical contributions) and its evidence (a single integrated system evaluated end-to-end). Standard practice in systems papers presenting multiple optimizations is to include a breakdown showing each optimization's incremental contribution, either additively (add one technique at a time) or subtractively (remove one technique from the full system). The absence of such a study weakens all three of the paper's technical claims.

### No Optimized AMD Baselines Inflate the Apparent Cross-Platform Speedup

**The assumption or constraint:** FlashDecoding++ is evaluated on AMD GPUs (RX7900XTX and MI210) against only the unoptimized Hugging Face PyTorch baseline. The paper acknowledges, implicitly, that no other baselines were available:

> "Currently, only the original Hugging Face implementation can be executed on AMD GPUs as the baseline."

This means the AMD comparison is between a fully optimized inference engine (FlashDecoding++) and raw PyTorch with no kernel fusion, no attention tiling, no specialized GEMV kernels, and no KV-cache management — a baseline that no production deployment would use.

**The consequence:** The reported 2.27× to 3.93× speedups on AMD GPUs conflate the contribution of FlashDecoding++'s three novel techniques with gains from basic inference engine optimizations that any competent engine would provide. If FlashDecoding or TensorRT-LLM were ported to ROCm, they would likely recover a large fraction of the gap against raw PyTorch. The paper cannot claim that FlashDecoding++ is faster than other inference engines on AMD hardware — only that it is faster than no engine at all. This matters because the paper emphasizes cross-platform applicability as a key strength (the abstract highlights speedups "on both NVIDIA and AMD GPUs"), but the AMD results do not support a comparison against optimized baselines and therefore do not demonstrate superiority over alternative approaches on that platform.

The 3.93× figure is also likely a **substantial overestimate** of the benefit a production AMD deployment would see relative to an optimized baseline. On NVIDIA, where optimized baselines exist, FlashDecoding++ achieves 1.37× over FlashDecoding and 1.13× over TensorRT-LLM. If an optimized ROCm engine achieved similar performance to FlashDecoding on AMD hardware, the incremental benefit of FlashDecoding++'s three techniques on AMD would likely be in the 1.1–1.4× range, not 3.93×.

**What evidence exists in the paper:** Figures 12 and 13 show the AMD results with Hugging Face as the sole baseline. The NVIDIA results (Figures 10 and 11) demonstrate that Hugging Face is 3–5× slower than optimized engines on the same hardware, confirming that a large fraction of the AMD speedup is attributable to basic optimizations, not the three novel techniques. The paper itself provides the evidence for this limitation: on NVIDIA A100 with Llama2-7B at batch size 1, Hugging Face achieves roughly 250 tokens/s while FlashDecoding achieves roughly 600 tokens/s (a ~2.4× gap from basic optimizations alone). FlashDecoding++ achieves roughly 800 tokens/s — adding 1.37× on top of the optimized baseline. The 3.93× AMD speedup should be decomposed similarly: a ~3× gain from basic inference engine optimizations plus an unknown (but likely smaller) gain from FlashDecoding++'s specific techniques.

**Mitigation status:** The paper does not attempt to estimate the contribution of basic vs. novel optimizations to the AMD speedups, nor does it propose any method for doing so without an optimized AMD baseline. The limitation is inherent to the state of the ROCm ecosystem at the time of writing — the paper cannot create a FlashDecoding ROCm port if one does not exist — but the reporting should distinguish more clearly between speedups attributable to "having an inference engine at all" versus "having FlashDecoding++'s specific innovations."

### The Flat GEMM Optimization Still Wastes Computation When M < 8, and the Paper Does Not Quantify the Residual Waste

**The assumption or constraint:** FlashDecoding++ pads the M-dimension of flat GEMM operations to 8 (matching the Tensor Core hardware tile size) rather than 64 (the tiling size used by cuBLAS and CUTLASS). The paper frames this as solving the under-utilization problem:

> "FlashDecoding++ only pads the matrix size to 8 rather than 64 in previous designs for flat-shaped GEMM to improve computation utilization."

However, for the common case of batch size 1 (M=1), padding to 8 still means that **7 out of every 8 rows of the tiled computation involve zero-padded data**. The GPU executes multiply-add operations for 8 rows per tile but only 1 row contributes to the output — an effective utilization of 12.5% for the M-dimension. This is substantially better than padding to 64 (1.6% utilization for M=1), but it is far from eliminating the under-utilization problem.

**The consequence:** The paper's claim of "improving computation utilization" should not be interpreted as "achieving high utilization." For single-batch inference — the most latency-sensitive and common deployment scenario — FlashDecoding++'s flat GEMM kernel still wastes 87.5% of its M-dimension arithmetic. The paper never quantifies the achieved Tensor Core utilization, so a practitioner cannot compare it against theoretical peaks or against alternative approaches (e.g., using CUDA Cores via FastGEMV for M=1, which avoids Tensor Core tiling entirely and may achieve higher effective utilization despite lower peak throughput). The heuristic dataflow does dispatch M=1 cases to FastGEMV (ImplA) for the K, Q, V projection in the Llama2-7B example (Figure 9c), but it uses the flat GEMM kernel (ImplB) for FFN1 even at batch size 8 — and potentially for other operations at M values where ImplB is faster than ImplA despite the M-dimension waste. The actual utilization achieved in these regimes is unknown.

**What evidence exists in the paper:** The paper models the computation-to-memory ratio (Equation 5) and characterizes the parallelism-bounded vs. memory-bounded regimes (Figure 7), but neither analysis includes a utilization metric (e.g., percentage of Tensor Core FLOPS achieved relative to theoretical peak). The >50% under-utilization figure cited in the introduction refers to the *previous approach* of padding to 64, not to FlashDecoding++'s own achieved utilization. The paper never reports what utilization FlashDecoding++ achieves, leaving a quantitative gap in the evaluation of its central flat GEMM contribution.

**Mitigation status:** Not addressed. The paper could mitigate this limitation by reporting achieved Tensor Core utilization (or effective TFLOPS) for the flat GEMM kernel on representative shapes and comparing against both cuBLAS and the theoretical hardware peak. This would let practitioners assess how much headroom remains for further optimization and whether alternative approaches (e.g., mixed-precision, structured sparsity, or vendor-specific GEMV libraries) might close the remaining gap. Without this data, the claim that the flat GEMM optimization "solves" the under-utilization problem is overbroad — it reduces the severity by roughly 8× (from 64× waste to 8× waste) but does not eliminate it.

### The Heuristic Dataflow Does Not Adapt to Sequence Length or KV-Cache Growth, Only to Batch Size

**The assumption or constraint:** The heuristic dataflow dispatches GEMM operations based solely on the `$M$` dimension (batch size for decode, `sequence length × batch size` for prefill) and the `$[N, K]$` shape (which is fixed per operation type). The offline profiling that determines inflection points `$M_1$` and `$M_2$` is described as sweeping over `$M$` for each `$[N, K]$` pair:

> "FlashDecoding++ profiles the performance of ImplA and ImplB for a certain M, and increases M to find an inflection point M1 where the performance of ImplB is better than ImplA."

This assumes that performance depends only on `$[M, N, K]$` at dispatch time. However, GPU kernel performance also depends on factors the dispatcher ignores: total GPU memory pressure (from KV-cache size, which grows with sequence length and number of generated tokens), contention for memory bandwidth from concurrent operations, and the specific data-dependent branching behavior of the kernel.

**The consequence:** The inflection points `$M_1$` and `$M_2$` are profiled under one set of memory conditions (presumably a standalone microbenchmark with no KV-cache pressure). During actual inference, especially at long sequence lengths with large KV-caches, the GPU's memory subsystem is under different load, and the relative performance of ImplA, ImplB, and ImplC may shift. A kernel that is memory-bandwidth-bound (like FastGEMV on CUDA Cores) might degrade more under high memory pressure than a compute-bound kernel (like CUTLASS on Tensor Cores), causing the optimal dispatch boundary to shift. The paper's fixed lookup table cannot adapt to these runtime conditions.

A second, related limitation: the heuristic dataflow treats the four `$[N, K]$` shapes as independent and profiles them separately. However, during end-to-end inference, these operations execute in sequence within each transformer layer, and the GPU's caches and memory bandwidth are shared across operations. The optimal dispatch for one operation may depend on cache state left by the previous operation — an effect that standalone profiling cannot capture.

**What evidence exists in the paper:** The experimental results in Figures 10–13 sweep across input lengths (128 to 32K), which provides an implicit test: if the heuristic dataflow made systematically suboptimal decisions at long sequence lengths, the speedup relative to baselines would degrade as sequence length increases. The results show that relative speedups are generally maintained or grow at longer sequences (e.g., Llama2-7B on A100, Figure 10a: speedup over FlashDecoding is ~1.3× at 128 input and ~1.4× at 32K input), suggesting that if dispatch suboptimality exists, its effect is not large enough to reverse the overall improvement. However, this does not rule out the possibility that further gains could be achieved with sequence-length-aware dispatch.

**Mitigation status:** The paper does not acknowledge this limitation or propose extensions to the dispatch logic (e.g., adding sequence length or available memory as a second dispatch dimension). The authors frame the heuristic dataflow as a solved problem — profile once offline, dispatch via lookup table at runtime — without discussing whether the lookup table's optimality holds under realistic, multi-operation, memory-contended execution conditions. In practice, the risk of dispatch degradation is probably small (GPU kernels tend to be more sensitive to their own launch parameters than to external memory pressure), but the paper provides no evidence to confirm this.
