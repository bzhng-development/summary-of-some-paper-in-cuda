# LServe: Efficient Long-sequence LLM Serving with Unified Sparse Attention

**ArXiv:** [2502.14866](https://arxiv.org/abs/2502.14866)

## 🎯 Pitch

LServe introduces a unified serving system for long-sequence LLMs that accelerates both the prefilling and decoding stages through **hybrid sparse attention**—a framework combining static head-level sparsity (converting half of attention heads into streaming heads with Λ-shaped masks) and dynamic query-centric sparsity (hierarchical KV page selection that prunes pages based on query similarity).

---

## 1. Executive Summary

LServe introduces a unified serving system for long-sequence LLMs that accelerates both the prefilling and decoding stages through **hybrid sparse attention**—a framework combining static head-level sparsity (converting half of attention heads into streaming heads with Λ-shaped masks) and dynamic query-centric sparsity (hierarchical KV page selection that prunes pages based on query similarity). Evaluated on Llama-3-8B, Llama-2-7B, and Minitron-4B across sequence lengths up to 512K tokens, LServe achieves up to 2.9× prefilling speedup and 1.3–2.1× decoding speedup over vLLM while preserving accuracy on LongBench, Needle-in-a-Haystack, RULER, and complex reasoning benchmarks (AIME, MATH500). The system's gains compound from the observation that static and dynamic sparsity are orthogonal—streaming heads provide nearly cost-free computation at short-to-medium contexts while dynamic page pruning bounds decoding complexity to a constant number of KV tokens (e.g., 4096) irrespective of context length—establishing that multiplicative speedups emerge only when these patterns are unified within a single block-sparse attention kernel rather than deployed in isolation.

## 2. Context and Motivation

### The Core Problem: Attention Dominates Everything in Long-Sequence Serving

When we deploy an LLM to process a 256K-token document and generate a 20K-token response—a scenario increasingly common with reasoning models like OpenAI's o1 (OpenAI, 2024)—reality diverges sharply from intuition. Conventional wisdom holds that the **prefilling stage** (processing the input) is the bottleneck: after all, attention has quadratic complexity $O(S^2)$ during prefilling. But the paper presents a striking counterexample in Section 1. Running Llama-3-8B on TensorRT-LLM with 256K input tokens and 20K output tokens (comparable to o1's observed chain-of-thought length), **prefilling takes 116 seconds while decoding takes 540 seconds**—nearly 5× longer. The decoding stage dominates because, although each step is linear $O(S)$ in the sequence length $S$, those linear costs accumulate across 20,000 autoregressive steps. For long-generation workloads, the decoding stage becomes the true performance bottleneck.

Figure 2 quantifies this systematically. As sequence length increases from 8K to 128K on Llama-3-8B with batch size 1 on an A100 GPU, the attention kernel's share of runtime grows from a minority to **at least 50% at 64K and 75% at 128K**, in both the prefilling and decoding stages. QServe (Lin et al., 2024b) further notes that attention's runtime share increases with batch size—which is the realistic serving condition. The remaining computation (GEMM operations for feed-forward networks) exhibits linear complexity in prefilling and constant complexity in decoding, meaning attention's quadratic and linear growth respectively make it the **dominant and asymptotically worsening bottleneck** in both phases.

This problem matters for three intersecting reasons:

**1. Real-world workloads are increasingly long-sequence.** Applications requiring 100K+ token contexts are no longer exotic: multi-turn conversations accumulate extensive history, long-document analysis (Zhang et al., 2024b) processes entire books or legal documents, multi-modal understanding (Xue et al., 2024a) feeds lengthy visual token sequences into LLMs, code completion (Li et al., 2023) involves entire codebases, and complex reasoning tasks (DeepSeek-AI et al., 2025) generate chains of thought spanning 20K+ tokens. Each of these workloads stresses both the prefilling stage (processing the long input) and the decoding stage (generating the long output while attending to the full KV cache).

**2. The decoding bottleneck is underappreciated.** Much of the LLM serving optimization literature has focused on memory bandwidth for the decoding stage (KV cache compression, quantization) because decoding is memory-bound—each token generation must load the entire KV cache from memory. However, as the paper demonstrates with its 540-second figure, the *latency* of decoding over many steps is the dominant user-facing metric. Reducing per-step latency through compute reduction (not just memory reduction) is essential for interactive applications.

**3. There's a gap between algorithm-level sparsity ideas and system-level speedups.** Multiple lines of research have proposed sparse attention patterns that reduce theoretical FLOPs. The paper's key observation is that **theoretical FLOPs reduction does not straightforwardly translate to wall-clock speedup** because of GPU execution constraints. Understanding this translation—why certain sparsity patterns accelerate attention and others don't—requires engaging with kernel-level implementation details.

### Why GPU Architecture Breaks Naïve Sparsity: The Block Iteration Bottleneck

The paper provides critical motivation through a GPU-centric analysis (Section 2.2, Figure 3) that explains why **not all sparsity is created equal** for attention acceleration. This is detailed in Section 2.2 and worth understanding thoroughly.

On modern GPUs, attention computation—both prefilling and decoding—proceeds by iterating over the KV token dimension **sequentially in blocks**. In the prefilling stage, the computation is parallelized across batch size, attention heads, and query tokens. In the decoding stage, query tokens = 1 (there's only one query per sequence per step). In both cases, the loop over KV tokens is sequential: each iteration computes a $T_Q \times T_K$ tile, where $T_Q$ is the number of query tokens in the current thread block (>1 in prefilling, =1 in decoding) and $T_K$ corresponds to the page size in PagedAttention (typically 16–64 tokens).

Now comes the crucial point. Within each iteration, **all threads in a GPU warp execute in lockstep**. If a sparsity pattern says "skip this individual token" but the warp still processes the full block, the threads corresponding to skipped tokens simply wait—they do nothing, but the warp's execution time is determined by the longest-running thread. This means **fine-grained (token-level) sparsity within a block yields minimal wall-clock speedup**. The lockstep execution means all threads march together; idle threads don't accelerate the group.

The effective optimization is therefore **to reduce the number of sequential iterations**—that is, to skip entire blocks rather than individual tokens within blocks. As Figure 3 illustrates in its bottom panel, if a block-sparse pattern allows skipping 2 out of 6 KV blocks, the sequential loop length drops from 6 to 4, directly reducing execution time. The paper formalizes this in Section 3.1: with block sparsity ratio $r$ (fraction of blocks that are empty), the theoretical speedup is $1/(1-r)$. In Figure 4(b)'s example, 10 out of 21 blocks are non-empty, yielding a theoretical 2.1× speedup.

This insight—that **coarse-grained, block-level sparsity is what GPUs need, not fine-grained token-level sparsity**—motivates the entire LServe design. It explains why the paper consistently operates at the granularity of **pages** (blocks of 16–64 tokens, matching PagedAttention's organization) rather than individual tokens, and it sets up the necessity of unifying different sparsity patterns (streaming heads, dynamic page selection) into a single block-sparse kernel.

### Prior Approaches and Their Specific Shortcomings

The paper identifies three broad categories of existing work and pinpoints precise limitations for each.

---

#### Approach 1: KV Cache Quantization Alone

Methods like QServe (Lin et al., 2024b), KIVI (Liu et al., 2024c), and KVQuant (Hooper et al., 2024) apply low-bit quantization (e.g., 4-bit, 2-bit) to the KV cache, reducing memory footprint and I/O traffic during the memory-bound decoding stage. This improves throughput by reducing the bytes that must be loaded from global memory per attention computation.

**The gap (Section 2.1, paragraph 3):** These methods "do not lower the number of computations performed in the attention loop." Quantization reduces the *cost per iteration* of the sequential loop over KV blocks, but it does not reduce *the number of iterations*. As sequence length grows, the loop remains $O(S)$ for each query token, growing linearly with context length. At 256K tokens, even with 4-bit KV cache, each decoding step still iterates over 256K tokens' worth of blocks. The arithmetic complexity is unchanged.

This limitation becomes acute as context windows push toward 512K and beyond. Quantization alone provides a constant-factor improvement per step but cannot change asymptotic scaling: if each new query must examine all of history, the decoding cost grows without bound.

---

#### Approach 2: Approximate Sparse Attention (Decoding-Focused)

Methods like StreamingLLM (Xiao et al., 2023), H2O (Zhang et al., 2024c), and TOVA (Oren et al., 2024) apply **static masking mechanisms** to reduce attention complexity during decoding. StreamingLLM keeps only the first few tokens (attention sinks) plus a local window; H2O and TOVA evict tokens from the KV cache mid-way through the context based on heuristics like attention score accumulation.

**The gap:** These methods suffer from two interconnected problems.

**First, accuracy degradation on long-context tasks.** The paper states (Section 2.1, paragraph 4) that these approaches operate "at the expense of accuracy in long-context tasks." The reason is fundamental: by discarding the majority of the KV cache, they lose the ability to retrieve information from arbitrary positions in the context. On benchmarks like Needle-in-a-Haystack (Kamradt, 2024) and RULER (Hsieh et al., 2024)—which explicitly test retrieval from arbitrary depths—static eviction policies fail when the needed information happens to fall in an evicted region. These methods essentially trade long-context capability for speed, which is unacceptable for applications that specifically need the extended context.

**Second, irregular KV cache memory layouts.** When tokens are evicted non-contiguously, the surviving KV pages lose their sequential organization. This creates fragmentation: the kernel cannot iterate through a simple contiguous block table but must navigate a more complex data structure, which introduces indirection overhead and potentially reduces GPU memory bandwidth utilization. The paper notes this as "irregular KV cache memory layouts" (Section 2.1, paragraph 4).

**DuoAttention (Xiao et al., 2024) as an improvement:** DuoAttention advances beyond these methods by operating at **coarser granularity** (entire attention heads rather than individual tokens) and using an **optimization-based** approach to identify which heads can be pruned. Specifically, DuoAttention classifies attention heads into two categories: **retrieval heads** that require full dense attention (they attend broadly across the context to retrieve information) and **streaming heads** that can function with only local context plus attention sinks (the first few tokens). By converting streaming heads to a Λ-shaped mask (full attention only on sinks and local tokens), DuoAttention reduces computation and memory while maintaining accuracy because the retrieval heads still provide global access when needed. The optimization procedure finds this head partitioning by analyzing attention patterns offline.

**LServe's relationship to DuoAttention:** The paper adopts DuoAttention's head classification method directly (Section 3.3), but it transforms the concept into a **system-level integration** rather than an algorithm-level proposal. Specifically, LServe (1) implements streaming heads with specialized fused CUDA kernels that avoid the conditional branching issues described in Section 3.4, (2) stores separate KV caches for streaming and dense heads (Figure 5), and critically (3) combines static head-level sparsity with the orthogonal dynamic page-level sparsity, which DuoAttention does not address.

---

#### Approach 3: Dynamic Sparse Attention (Stage-Specific)

Two major systems apply query-dependent, dynamic sparsity: **MInference** (Jiang et al., 2024b) for the **prefilling stage** and **Quest** (Tang et al., 2024) for the **decoding stage**. Both identify important tokens based on the current query rather than using a fixed mask.

**MInference:** During prefilling, MInference dynamically determines which tokens each query should attend to, reducing the quadratic prefilling cost by skipping computation for query-token pairs deemed unimportant. It achieves strong prefilling acceleration.

**Quest:** During decoding, Quest estimates the importance of historical tokens for the current query token by maintaining per-page statistical summaries (minimum and maximum values of keys within each page). It then selects the top-K pages to attend to, bounding decoding complexity to a constant number of KV tokens (e.g., 4096) regardless of total context length.

**The gaps:**

**1. Neither method addresses both stages.** MInference optimizes prefilling but uses dense attention in decoding; Quest optimizes decoding but doesn't accelerate prefilling. A complete serving system must handle both stages, and using separate, uncoordinated sparsity mechanisms misses opportunities for **shared infrastructure** (a unified kernel design, a shared KV cache organization) and **compounded benefits** (the multiplicative gains available when static and dynamic sparsity combine, as LServe demonstrates in Figure 15).

**2. Neither method reduces KV cache memory consumption.** Both MInference and Quest perform sparse *computation*—they skip attention operations—but they still maintain the full KV cache in memory. All tokens remain stored; they simply aren't all accessed on every step. For very long sequences (256K+), the memory footprint of the KV cache itself becomes prohibitive, and these methods provide no relief.

**3. Quest specifically suffers from accuracy degradation at larger page sizes.** This is a critical finding presented in Figure 6. When the KV cache is organized with larger page sizes (32 or 64 tokens per page instead of 16), Quest's page-wise statistical indicators (min/max of keys) become **homogenized and less representative**. The statistics average over too many tokens, losing the signal that distinguishes important pages from unimportant ones. Figure 6(b)–(d) show that at the same token budget (4096), increasing page size from 16 to 32 to 64 progressively degrades Needle-in-a-Haystack accuracy, even though the total number of tokens attended to remains constant.

**4. No unified framework exists.** The paper states it directly (Section 2.1, paragraph 4): these approaches "lack a unified framework to address efficiency challenges in both stages simultaneously." They were designed as point solutions, and combining them would require reconciling different sparsity patterns, different kernel implementations, and different memory layouts.

---

#### Approach 4: General Serving System Optimizations

Systems like vLLM (Kwon et al., 2023b), Orca (Yu et al., 2022), SGLang (Zheng et al., 2023), and TensorRT-LLM (NVIDIA, 2023) provide efficient serving infrastructure through PagedAttention, continuous batching, and optimized kernels.

**The gap:** These systems accelerate attention at the **kernel implementation level** (efficient tiling, vectorized operations, memory coalescing) but do not reduce the **algorithmic complexity** of attention. They compute dense attention efficiently, but it's still dense attention—still $O(S^2)$ in prefilling and $O(S)$ per step in decoding. At extreme sequence lengths, optimized dense kernels still become the bottleneck because the fundamental computational cost grows without bound. The paper's profiling in Figure 2 confirms this: even running on TensorRT-LLM (one of the most optimized serving engines available), attention dominates runtime at long contexts.

---

### How LServe Positions Itself

The paper's positioning emerges from this landscape. Rather than proposing a new sparsity *algorithm* (in the sense of a novel attention pattern), LServe is a **system-level integration** that unifies existing sparsity ideas into a framework where their benefits compound. The key contributions are architectural:

**Unification via block-sparse attention.** LServe recognizes that the GPU-friendly approach to sparse attention is to skip entire KV blocks (pages) rather than individual tokens (Section 3.1). This insight—motivated by the lockstep execution analysis—provides a common substrate into which different sparsity patterns can be plugged. Streaming heads map naturally to this: they only keep the initial sink page(s) and recent local pages, skipping everything in between. Dynamic page selection maps naturally: the page selector identifies which blocks to keep, and the kernel only iterates over those blocks.

**Orthogonality of static and dynamic sparsity.** This is the paper's central conceptual insight (stated in the abstract and demonstrated throughout Sections 3–5). Static sparsity (streaming heads) provides a fixed, input-agnostic pruning that is most effective at shorter-to-medium context lengths—it reduces computation on half the heads regardless of query content. Dynamic sparsity (page selection) provides query-dependent pruning that becomes increasingly valuable at extreme context lengths—it caps the number of attended tokens to a constant budget. Figure 15 demonstrates this compounding: static sparsity alone yields 1.3–1.7× speedup; dynamic sparsity alone yields up to 30× on the attention layer at 256K; combining both ("LServe Attention") multiplies these benefits while the individually skipped computations don't overlap (they operate on different heads or different pages).

**System-algorithm co-design for practical speedup.** The paper's deepest contribution may be its treatment of sparsity not as a theoretical FLOPs reduction but as a kernel-level engineering challenge. The iterator-based abstraction (Section 3.4), the hierarchical paging system (Section 3.5.2), and the reusable page selector (Section 3.5.3) all address real implementation bottlenecks that would prevent theoretical sparsity from translating into measured speedup. For instance, without the reusable page selector (Figure 14), the page selection overhead itself grows linearly with sequence length and becomes the bottleneck at 64K+ tokens—nullifying the gains from sparse attention. Without hierarchical paging (Figure 13), larger page sizes required for quantization efficiency destroy the accuracy of page selection. These are not algorithmic contributions but **system design contributions** that make sparse attention practically deployable.

**Compatibility with both long-context retrieval and complex reasoning.** The paper explicitly evaluates not just retrieval benchmarks (LongBench, NIAH, RULER) but also reasoning tasks (AIME2024, MATH500) with DeepSeek-R1-Distill models (Table 4). This positioning matters because reasoning models like o1 and DeepSeek-R1 represent the new frontier of long-sequence workloads—their chain-of-thought traces are effectively long-generation tasks that stress both prefilling and decoding. Demonstrating that LServe preserves accuracy on AIME (43.3% for both dense and LServe) establishes that the sparsity patterns don't interfere with the kind of multi-step logical deduction that these reasoning models perform.

**In summary:** LServe positions itself not as a competitor to DuoAttention, Quest, or MInference (whose sparsity patterns it incorporates), but as a **unified deployment framework** that extracts their combined benefits through careful attention to GPU execution constraints, kernel design, and memory management. The gap it addresses is not the absence of sparsity ideas but their **fragmentation across stages and their failure to compound into system-level speedups**.

## 3. Technical Approach

### 3.1 Reader Orientation (Approachable Technical Breakdown)

**What the system is:** LServe is an LLM serving system—the software infrastructure that takes a trained language model and runs it efficiently on GPUs to process user requests—that replaces the standard dense attention mechanism with a unified block-sparse attention kernel combining two orthogonal sparsity strategies.

**What problem it solves and the "shape" of the solution:** Long-sequence LLM inference is dominated by attention computation in both the prefilling stage (processing the input prompt, where attention cost grows quadratically with input length) and the decoding stage (generating output tokens one at a time, where attention cost grows linearly with accumulated context length). LServe attacks both stages simultaneously by recognizing that (1) half of all attention heads can operate in a cheap "streaming" mode attending only to local and initial tokens, (2) only a constant number of historical KV pages (e.g., 4096 tokens' worth) are actually needed to preserve accuracy regardless of total context length, and (3) these two sparsity patterns are independent and their benefits multiply when unified into a single kernel rather than deployed separately.

### 3.2 Big-Picture Architecture (Diagram in Words)

LServe's architecture has six major components, described here as they would be traversed during LLM inference:

**1. Head Classifier (offline, pre-deployment):** Analyzes each attention head in the pretrained LLM using DuoAttention's optimization-based method, producing a gating value `$\alpha \in [0,1]$` per head. Heads with `$\alpha$` near 1 are classified as **retrieval heads** (dense attention required); heads with `$\alpha$` near 0 are classified as **streaming heads** (can use the cheap Λ-shaped mask). At a target sparsity of 50%, exactly half of all heads become streaming heads.

**2. Dual KV Cache (runtime, memory-resident):** Two separate paged KV caches are maintained—one for dense/retrieval heads and one for streaming heads. The dense-head cache stores full per-page key statistics (`k_max` and `k_min` vectors) needed for the dynamic page selector. The streaming-head cache is dramatically smaller because each streaming head only ever accesses sink tokens (the first few tokens of the context) plus recent local tokens.

**3. Fused Sparse Prefilling Kernel (first stage of inference):** Replaces the standard dense attention kernel during the prefilling stage. It uses an **iterator-based abstraction** that loops only over non-empty KV blocks. For dense heads, the iterator covers all blocks; for streaming heads, the iterator automatically jumps from sink blocks directly to local blocks, skipping the entire intervening context.

**4. Hierarchical Page Selector (decoding stage, per-query):** Before each decoding step (or once per chunk of steps, via reuse), scores every physical KV page in the dense-head cache by its relevance to the current query token using per-page min/max key statistics. Selects the top-K physical pages (e.g., those covering 4096 tokens) to attend to. The hierarchical design decouples the logical page size used for importance estimation (small, e.g., 16 tokens, for accurate statistics) from the physical page size used for memory layout (large, e.g., 64 tokens, for GPU bandwidth efficiency).

**5. Fused Sparse Decoding Kernel (second stage, per generated token):** Takes the page selection results as input (a shortened page table). Iterates only over selected KV pages, applying block-sparse attention where each $1 \times T_K$ tile (one query token × one KV page) is either fully computed or fully skipped. Streaming heads operate with fixed Λ-shaped masks; dense heads operate with the dynamically selected page set.

**6. Reusable Page Selector (decoding stage, overhead reduction):** Rather than running the page selector at every single decoding step, activates it only at the start of pre-defined chunks (e.g., every 4 tokens). Subsequent tokens within the chunk reuse the same page selection, exploiting the temporal locality that adjacent queries attend to similar historical pages.

Information flows: a request enters → the prefilling kernel processes all input tokens using the head-type-specific iterators → KV features are written to the dual cache (streaming heads get sink + local pages; dense heads get full pages plus min/max statistics) → during decoding, the page selector scores dense-head pages using the current query → the decoding kernel iterates only over selected dense pages plus the fixed streaming pattern → output tokens are generated autoregressively, with page selection reused across chunks.

### 3.3 Roadmap for the Deep Dive

- **First, the unified block-sparse attention formulation (Section 3.1 in the paper):** This is the mathematical and engineering foundation—why block-level sparsity, not token-level sparsity, actually accelerates GPUs. Understanding the block iteration model makes everything else follow logically.
- **Second, the static sparsity mechanism (streaming heads) and its kernel implementation (Sections 3.3–3.4):** How LServe classifies heads, what the Λ-shaped mask looks like, and how the iterator-based kernel skips blocks without branching. This establishes the "nearly free" computation on half of all heads.
- **Third, the dynamic sparsity mechanism (page selection) in the decoding stage (Section 3.5):** Why page selection is necessary, the page size dilemma (quantization requires large pages but accurate selection requires small granularity), the hierarchical paging solution, and the reusable page selector that cuts overhead by 4×.
- **Fourth, the decoding kernel implementation (Section 3.6):** How the two-level indexing hierarchy (physical index for GPU iteration, logical index for token position) unifies streaming heads and dynamically-selected dense heads into one kernel.
- **Fifth, how everything composes:** The end-to-end flow through prefilling and decoding, showing where each sparsity pattern activates and how their computational savings compound without overlapping.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems paper** whose core idea is that static head-level sparsity and dynamic query-centric page sparsity are orthogonal optimization axes in long-context LLM attention, and that unifying them into a single block-sparse attention kernel yields multiplicative speedups that neither approach achieves alone. The technical contribution is the integration architecture—the kernel design, the hierarchical paging system, and the reusable selector—that translates theoretical sparsity into measured GPU acceleration across both inference stages.

---

#### 3.4.1 Unified Block-Sparse Attention Formulation

The starting point for all of LServe's acceleration is a precise understanding of **how attention is actually computed on GPUs** and why certain sparsity patterns work while others don't.

**The GPU execution model for attention.** In both the prefilling and decoding stages, the attention kernel iterates sequentially over the KV token dimension in discrete blocks. Each iteration computes a tile of size $T_Q \times T_K$, where $T_Q$ is the number of query tokens handled by the current GPU thread block ($T_Q > 1$ in prefilling, $T_Q = 1$ in decoding) and $T_K$ corresponds to the page size used in PagedAttention (typically 16–64 consecutive tokens, as organized by the KV cache management system). Within each iteration, all threads in a GPU warp execute in lockstep—they process different parts of the tile in parallel but advance to the next work unit together. The GPU's streaming multiprocessor can execute only a limited number of thread blocks simultaneously.

This execution model has a critical consequence: **fine-grained sparsity within a tile does not accelerate execution**. If a sparsity pattern specifies that certain individual query-key pairs within a tile should be skipped, the threads assigned to those pairs simply idle while the rest of the warp completes its work. The warp's execution time is bounded by the longest-running thread, not the average. Therefore, skipping individual attention operations within a block yields negligible wall-clock speedup.

**The block-sparse abstraction.** LServe's solution is to organize sparsity at the **block level**, not the token level. The paper defines block sparsity operationally: for each $T_Q \times T_K$ tile in the attention computation, the tile is either **fully computed** (as in standard causal attention, restricted appropriately by the causal mask) or **fully skipped** (the loop iteration for that block is bypassed entirely). No partial computation within a block is attempted.

Figure 4 illustrates this with three complementary views. Panel (a) shows standard dense causal attention—every token attends to all preceding tokens plus itself, producing the familiar lower-triangular attention matrix. Panel (b) shows the block-sparse generalization: the attention matrix is partitioned into rectangular blocks (matching the $T_Q \times T_K$ tile size), and a subset of blocks (shown in light gray) are fully skipped while the remaining blocks (shown in blue) are computed densely. In this example, 10 out of 21 total blocks are non-empty, yielding a sparsity ratio $r = 11/21 \approx 0.52$ and a theoretical speedup of $1/(1-0.52) \approx 2.1\times$.

**Speedup model.** The paper provides a clean analytical relationship between block sparsity and expected speedup. Since each GPU streaming multiprocessor can only execute a limited number of thread blocks simultaneously, the attention kernel's execution time is approximately proportional to the total count of $T_Q \times T_K$ (and corresponding $T_K \times T_V$) blocks that must be processed:

$$\text{speedup} = \frac{1}{1 - r}$$

where $r$ is the fraction of blocks that are empty (skipped). This is not an exact equality—it assumes perfect parallelism and ignores fixed overheads—but it captures the first-order effect: halving the number of active blocks roughly doubles throughput. The paper uses this model throughout to reason about the benefits of different sparsity patterns.

**Why this abstraction matters beyond the speedup formula.** The block-sparse formulation provides a **common substrate** into which qualitatively different sparsity patterns can be mapped. As the paper proceeds to show, streaming heads (Figure 4c) map naturally: the Λ-shaped mask keeps only the initial "sink" blocks and the most recent "local" blocks, skipping everything in between—a static, input-independent pattern. Dynamic page selection (Figure 4d) maps just as naturally: the page selector identifies which historical blocks are relevant to the current query, and the kernel skips all others—a dynamic, input-dependent pattern. Both produce the same interface to the kernel: a list of block indices to process. This unified interface is what enables a single kernel implementation to serve both sparsity types, and it's what makes the composition of static and dynamic sparsity straightforward rather than a compatibility nightmare.

---

#### 3.4.2 Static Sparsity: Streaming Heads via DuoAttention's Head Classification

LServe's static sparsity component partitions attention heads into two groups, following the method introduced by DuoAttention (Xiao et al., 2024). The core idea is that **not all attention heads need full dense computation**—some heads consistently exhibit a streaming pattern where they attend almost exclusively to local context and initial "sink" tokens, with negligible attention to tokens in the vast middle region of the context.

**Head classification procedure.** The paper adopts DuoAttention's optimization-based method (Section 3.3). For each attention head in the pretrained LLM, the method produces a scalar **gating value** $\alpha \in [0, 1]$. The procedure is offline—it runs once before deployment, analyzing the model's attention patterns on representative data—and does not modify the model weights. Heads with $\alpha$ values close to 1 are classified as **retrieval heads**: they require full dense attention because their function involves accessing information from arbitrary positions across the entire context. Heads with $\alpha$ values close to 0 are classified as **streaming heads**: they can operate with a dramatically restricted attention pattern while preserving model accuracy.

**Sparsity thresholding.** To determine the exact boundary between the two categories, LServe uses a sparsity quantile approach. Given a target sparsity level (e.g., 50%—meaning half of all attention heads should become streaming heads), the threshold $\tau$ is set to the corresponding quantile of the gating value distribution across all heads. For example, with 50% target sparsity, $\tau$ equals the median of all $\alpha$ values, converting exactly half the heads to streaming heads. The paper's experiments use 50% sparsity as the default configuration, which the accuracy evaluations in Tables 2–4 and Figures 9 and 13 confirm does not degrade model performance.

**The Λ-shaped mask (streaming head attention pattern).** Once a head is classified as streaming, its attention mask is replaced with a fixed Λ-shaped pattern (Figure 4c). The name "Λ-shaped" comes from the visual appearance when plotted as an attention matrix: the mask has nonzero entries only at the left edge (the first few tokens, called **attention sinks** after Xiao et al., 2023) and along the main diagonal (the **local window** of recent tokens), forming a shape resembling the Greek letter lambda. The vast middle region—tokens between the sinks and the local window—receives zero attention weight. Concretely, as shown in Figure 4(c), each token in a streaming head attends to exactly one sink block (the very first pages of the context) plus two local blocks (its immediate neighbors), and nothing else. The number of attended blocks per token is constant regardless of context length—in the figure, each row has exactly 3 non-empty blocks out of a total that grows with context length.

**Why this works without accuracy loss.** The effectiveness of streaming heads relies on an empirical finding from attention analysis literature: a subset of attention heads in transformer LLMs function primarily as **positional patterns** rather than content-based retrieval mechanisms. The initial "sink" tokens serve as a kind of learned bias—they accumulate disproportionate attention weight regardless of their actual content, effectively acting as a "null" position that heads attend to when they have no specific content to retrieve. The local window captures the immediate syntactic and semantic context needed for fluent generation. The middle context, which contains semantically meaningful tokens at arbitrary positions, is simply not needed by these particular heads—they never "look there" even when given the opportunity. By restricting streaming heads to match their natural behavior, LServe eliminates computation that was never informative to begin with.

**Design choice: static vs. learned per-input classification.** The head classification is static—it identifies which heads are streaming heads once, offline, and that classification is then reused identically for all inputs and all inference requests. This contrasts with dynamic approaches that might decide per-input which heads to sparsify. The static choice has two advantages: (1) it enables specialized kernel optimization because the sparsity pattern is known at kernel compilation time, and (2) it avoids any runtime overhead for head-type decisions. The tradeoff is that some heads might benefit from dense attention on certain inputs but not others, but the paper's accuracy results suggest that at 50% sparsity, the static classification captures nearly all available benefit.

---

#### 3.4.3 Prefilling Stage Kernel Implementation: Iterator-Based Block Skipping

Translating the streaming head sparsity pattern into actual GPU acceleration requires careful kernel design. The paper identifies and solves a specific challenge (Section 3.4): **naively implementing block sparsity with conditional statements inside the sequential loop is inefficient** because GPU architectures thrive on minimizing branching. If the kernel checks at each iteration "should I process this block or skip it?", the conditional branches cause warp divergence (threads taking different execution paths), which undermines the very speedup that skipping blocks is supposed to provide.

**The iterator-based abstraction.** LServe introduces an abstraction layer—the **iterator**—that standardizes how the kernel determines which blocks to process. Rather than iterating through all blocks and branching on each, the kernel iterates **only over the non-empty blocks**. The iterator is a function that maps an iteration counter $i$ to a position in the KV cache:

$$\text{offset} = \text{iter}(i + 1) - \text{iter}(i)$$

where $\text{iter}(i)$ returns the starting memory offset of the $i$-th block that needs to be processed. The difference between consecutive iterator values gives the size of the data to load for the current iteration, and the iterator automatically skips over empty blocks by design: $\text{iter}(i+1)$ and $\text{iter}(i)$ are non-consecutive when blocks are skipped, reflecting the gap in memory addresses. The kernel loop body sees only valid blocks and processes them densely.

This design yields several practical benefits. First, it **eliminates conditional branches** from the main loop: every iteration processes a full block of computation with no divergence. Second, it requires **minimal changes to the kernel function** itself—the loop structure remains conventional; only the iterator setup changes, enhancing maintainability and reducing the risk of introducing bugs. Third, it **unifies different sparsity patterns**: the iterator is configured differently for streaming heads vs. dense heads vs. dynamically-selected pages, but the kernel code that consumes the iterator is identical.

**Streaming head iterator configuration.** For streaming heads, the iterator pattern is fixed and known before the kernel launches—it does not depend on the input tokens or the query. The iterator is constructed to produce the sequence: sink block(s) first, then local blocks. For a context with $N$ total blocks and a streaming pattern that keeps $S$ sink blocks and $L$ local blocks per query, the iterator for a query at position $p$ (measured in blocks) produces the indices $\{0, 1, ..., S-1, p-L+1, ..., p\}$, skipping everything between block $S$ and block $p-L$. The memory offsets are computed directly from these block indices using the page table: $\text{offset} = \text{page\_table}[\text{block\_idx}] \times \text{page\_size}$.

Once the attention computation for the sink blocks finishes, the iterator automatically updates the memory pointer to the first local token in the KV cache with minimal overhead—there is no branch to check "are we done with sinks?"; the iterator's next value simply points to a different memory region.

**Dense head iterator configuration.** For dense (retrieval) heads, the iterator is configured to produce every block from 0 to $p$ (the full causal range). This means the iterator stride is always 1 (consecutive blocks), but the kernel code is unchanged—it's the same loop structure, just with a different iterator.

**Generalization to arbitrary block-sparse patterns.** The paper notes that the iterator-based formulation "unifies the more general block sparse pattern (see Figure 4)"—meaning it can represent not just streaming heads but any set of selected blocks. This is what enables the decoding-stage kernel to handle both streaming heads and dynamically-selected pages with the same code path, as described in Section 3.6.

**Performance validation (Section 5.1, Figure 12).** The paper benchmarks the block-sparse prefilling kernel against MInference's implementation and a theoretical "oracle" upper bound. The oracle speedup is defined as $\text{Latency}_{\text{oracle}} = \text{Latency}_{\text{dense}} \times (1 - \text{sparsity})$—that is, perfectly linear scaling with the fraction of computation skipped. In practice, LServe's kernel achieves approximately $1.3\times$ speedup over MInference at the same sparsity level (Figure 12), demonstrating that the iterator-based design better exploits the GPU's execution model. The gap between LServe's measured latency and the oracle upper bound reflects fixed overheads (kernel launch, iterator construction, remaining dense heads) that don't scale with sparsity.

#### 3.4.4 Dynamic Sparsity: The Page Size Dilemma

The static streaming head sparsity reduces computation on half of all attention heads. However, for the remaining dense (retrieval) heads, the decoding stage still requires each new query token to potentially attend to the entire historical context—an $O(S)$ operation per step that grows linearly with accumulated context length. LServe's dynamic sparsity component addresses this by introducing **query-centric page pruning**: for each decoding step, only a fixed number of KV pages (corresponding to a constant token budget, e.g., 4096 tokens) are selected for attention computation, regardless of total context length.

Before explaining the selection mechanism itself, the paper identifies a subtle but critical systems challenge: the **page size dilemma** (Section 3.5.1).

**Why page size matters for efficiency.** In the decoding stage, attention is **memory-bound**: the GPU spends most of its time waiting for data to be loaded from global memory into registers and shared memory, not performing arithmetic. Because of this, state-of-the-art serving systems (QServe, TensorRT-LLM) apply KV cache quantization—reducing the bit-width of stored key and value tensors (e.g., from FP16 to INT4)—to reduce memory traffic and improve throughput. However, quantization interacts poorly with small page sizes. Devices have minimum transaction sizes for global memory reads (typically 32 bytes on NVIDIA GPUs, corresponding to a cache line). If a page contains only 16 tokens × 4 bytes per token (for INT4) = 64 bytes, the GPU may end up loading additional unused data to satisfy alignment requirements, or it may issue many small memory transactions that underutilize the memory bus bandwidth. Larger page sizes (32, 64, or 128 tokens) amortize these overheads and achieve higher effective bandwidth.

Table 1 quantifies this effect. On a single A100 GPU running QServe with Llama-3-8B architecture and batch size 32:
- At 512-token sequence length: page size 16 yields 11.0 ms/step; page size 32 yields 10.7 ms; page size 64 yields 10.5 ms. The maximum slowdown from using page size 16 instead of 64 is $1.52\times$ at this length.
- At 8192-token sequence length: page size 16 yields 77.1 ms/step; page size 32 yields 63.0 ms; page size 64 yields 51.0 ms. The slowdown grows to $1.52\times$—a substantial penalty that would erase a significant fraction of any sparsity gains.

**Why page size matters for accuracy of dynamic selection.** The countervailing force comes from the accuracy of page-level importance estimation. Quest (Tang et al., 2024) introduced the idea of estimating page importance using **page-wise statistics**—specifically, computing the channel-wise minimum and maximum values of all keys within a page, and using these min/max vectors as "representatives" of the page's content. The current query is compared against these representatives to compute an importance score for each page, and the top-K pages are selected for attention.

The problem, illustrated dramatically in Figure 6, is that **as page size increases, these statistical representatives become homogenized and less discriminative**. Within a large page (e.g., 64 tokens), the min and max values across all tokens tend to converge toward a wide range that captures almost the entire distribution of key values, making different pages look similar to each other regardless of their actual content differences. The figure panel sequence (a)→(b)→(c)→(d) shows Needle-in-a-Haystack accuracy degrading as page size increases from 16 to 32 to 64, all at the same token budget of 4096. Simply increasing the token budget to compensate for larger pages (panels e, f) does not fully recover the loss: the homogenized statistics fundamentally lose the signal needed to distinguish important pages from unimportant ones.

This creates the dilemma: **small pages are accurate for selection but inefficient for GPU memory access; large pages are efficient but inaccurate for selection**. A system that naively uses the same page size for both purposes must sacrifice either throughput or accuracy.

#### 3.4.5 Dynamic Sparsity: Hierarchical Paging Solution

LServe's hierarchical paging system (Section 3.5.2, Figure 7) decouples the page size used for **importance estimation** (the logical page size $N_L$, chosen to be small enough for accurate statistics) from the page size used for **physical memory layout** (the physical page size $N_P$, chosen to be large enough for GPU bandwidth efficiency). The two are related by a grouping factor $g$:

$$N_P = g \cdot N_L, \quad g \in \mathbb{Z}$$

meaning each physical page contains exactly $g$ logical pages, and tokens within the same logical page collectively contribute to a single importance estimator.

**Concrete example from Figure 7.** The figure assumes $N_P = 8$ tokens per physical page and $N_L = 4$ tokens per logical page, so $g = 2$—each physical page contains two logical pages. The KV cache is organized in physical pages as usual (continuous blocks of $N_P$ tokens each), but the importance estimation operates at the finer logical page granularity.

**Logical page representation.** For each logical page—a group of $N_L$ consecutive key tokens—LServe computes two summary vectors by taking the channel-wise (element-wise) minimum and maximum across all tokens in the logical page. These vectors, denoted `$k_j^{\max}$` and `$k_j^{\min}$` for logical page $j$, each have dimension $D$ (equal to the per-head key dimension, e.g., 128 for Llama models). The motivation, inherited from Quest, is that the min and max values provide a conservative bound on the key distribution: if the query vector falls outside the range spanned by these extremal values for a given channel, there is likely no token in that logical page with strong alignment on that dimension.

These `$k_{\max}$` and `$k_{\min}$` vectors are pre-computed during the prefilling stage and also updated incrementally during decoding (when new tokens are generated, their keys are incorporated into the statistics of the last logical page). They are stored at the end of each physical page in the dense-head KV cache, immediately following the quantized key and value features plus their scaling factors and zero points (for dequantization). This storage layout—statistics co-located with the data they summarize—avoids an additional indirection when the page selector loads statistics.

**Per-page importance scoring.** Given a current query vector $q$ (of dimension $D$, corresponding to a single attention head in a single decoding step), the importance score of logical page $j$ is computed as:

$$S_j = \sum_{i=1}^{D} \max\left(q[i] \cdot k_j^{\max}[i], \; q[i] \cdot k_j^{\min}[i]\right)$$

where $i$ indexes the channel (feature) dimension, $q[i]$ is the $i$-th element of the query vector, $k_j^{\max}[i]$ and $k_j^{\min}[i]$ are the pre-computed extremal values for the $i$-th channel of logical page $j$, and the multiplication $q[i] \cdot k_j^{\max}[i]$ is a scalar product.

**What Equation 2 computes in operational terms:** For each channel (feature dimension) of the query, we ask: "what is the maximum possible dot-product contribution this channel could make with any token in logical page $j$?" We answer this by comparing the query element against both the max and min key elements in that channel—whichever gives the larger product is the upper bound. Summing these upper bounds across all channels gives a scalar score $S_j$ that estimates the maximum possible attention score (pre-softmax dot product) the query could achieve with any token in that logical page. This is a **conservative relevance estimate**: if the maximum possible score is low, no token in the page can have a high attention score.

**Why this form:** The max-of-products formulation (rather than, say, the dot product with the mean key vector) provides a **pessimistic estimate** that errs on the side of retaining pages. If a page contains diverse key vectors spanning a wide range in each channel, the product with either the max or min will capture the possibility of at least one token aligning with the query. Using the mean would average out these extremal tokens and could underestimate importance. This conservative bias is appropriate for a selection mechanism: it's better to retain an unimportant page than to discard a critical one, since the former only wastes computation while the latter causes accuracy loss.

**Physical page importance via max-reduction.** Once each logical page has a score, the importance of a physical page is determined by taking the maximum over the scores of its constituent logical pages:

$$S_{\text{physical}} = \max_{j \in \text{logical\_pages\_in\_this\_physical}} S_j$$

If any logical page within a physical page is important (has a high score), the entire physical page is considered important. This ensures that no critical information is lost: if the query needs even a single token hidden somewhere in a 64-token physical page, the whole page will be retained.

**Selection.** After scoring all physical pages, LServe selects the top-K physical pages with the highest importance scores, where K is determined by the predefined token budget (e.g., with a 4096-token budget and 64-token physical pages, $K = 4096/64 = 64$ pages). These selected pages form the shortened page table that the decoding kernel will iterate over. The remaining pages are skipped entirely during attention computation for this decoding step.

**Addressing the scaling concern: does hierarchical paging require a larger token budget?** The paper identifies and addresses a potential concern (Section 3.5.3). With hierarchical paging, if the truly important tokens are sparsely distributed across different physical pages, a single physical page containing one 4-token important logical page will force the retention of all 64 tokens in that physical page (including 60 potentially irrelevant tokens), whereas a system with 16-token pages would only retain those 16 tokens. This could require a larger total token budget to achieve the same recall of important tokens.

**Why locality mitigates this.** The paper argues that **spatial locality** in natural language attention makes this worst-case sparse distribution unlikely. During decoding, the current query token tends to attend to tokens that are semantically related to itself, and semantically related tokens tend to appear in **consecutive positions** in the context (e.g., paragraphs discussing the same topic, consecutive sentences in a dialogue). As a result, the logical pages with the highest importance scores tend to **cluster within the same physical pages**, rather than being scattered one-per-page. Figure 13 validates this empirically: with $N_P = 64$ and $N_L = 16$ (the same token budget as the baseline with $N_P = N_L = 16$), LServe's Needle-in-a-Haystack accuracy matches the dense baseline, whereas the naive approach (using page-wise statistics at $N_P = 64$, from Figure 6d) shows significant degradation. The hierarchical structure effectively maintains accuracy without requiring a larger budget because the important tokens are naturally clustered.

#### 3.4.6 Dynamic Sparsity: Reusable Page Selection

The hierarchical paging system solves the accuracy-efficiency tradeoff for dynamic selection, but it introduces a new problem: **the page selection itself has non-trivial computational cost that scales linearly with context length**. While the sparse attention kernel's complexity is bounded to a constant (e.g., 4096 tokens) by page pruning, the page selector must score **every physical page** in the context to determine which ones to keep. This scoring operation—computing Equation 2 for each logical page, then max-reducing to physical pages—is $O(S)$ in the total sequence length.

Figure 14 quantifies this overhead. At sequence lengths above 64K tokens, the page selector latency exceeds the sparse attention kernel latency. At 128K with a 4K token budget, the page selector takes 0.24 ms while the sparse attention kernel takes only 0.12 ms—the selector is already $2\times$ slower than the attention computation it's supposed to accelerate. At 256K, the selector reaches approximately 0.50 ms, dominating the per-step cost. This means that without addressing page selection overhead, the theoretical speedup from sparse attention would be largely consumed by the cost of deciding what to attend to.

**Exploiting temporal locality.** The paper identifies a property of the decoding attention mechanism that enables overhead reduction: **temporal locality**—adjacent query tokens in the autoregressive generation sequence tend to attend to similar historical pages. This makes intuitive sense: consecutive tokens in a generated response often relate to the same topic or refer back to the same parts of the input context. The attention patterns of query $t$ and query $t+1$ overlap substantially.

**Reusable page selection mechanism (Section 3.5.3, Figure 8).** LServe activates the full page selector only at the beginning of pre-defined **chunks** of consecutive decoding steps. For all subsequent tokens within the same chunk, the system **reuses** the page selection results from the first token. Figure 8 illustrates this with a chunk size of 2: the page selector runs at steps $T_0$ and $T_0+2$, while steps $T_0+1$ and $T_0+3$ simply reuse the previous selection. The default chunk size in LServe is **4** (selected based on the ablation in Table 6).

**Accuracy impact (Table 6).** The paper evaluates how reuse interval affects long-context accuracy on RULER at 64K sequence length with Llama-3-8B. For LServe with a 4096-token budget:
- No reuse (interval 1): 86.2% accuracy (vs. 86.8% dense baseline)
- Reuse interval 2: 85.6%
- Reuse interval 4: 85.6% (no further degradation)
- Reuse interval 8: 84.8% (minor degradation begins)
- Reuse interval 16: 83.2% (noticeable degradation)

For LServe with an 8192-token budget, the pattern is similar: accuracy remains stable (within 1 point of the 86.8% baseline) through reuse interval 8, with more significant drop-off at interval 16. Based on these results, LServe defaults to reuse interval 4, achieving a **4× reduction in page selection overhead** while preserving accuracy within 1.2 percentage points of the dense baseline.

**Why this works without substantial accuracy loss.** The temporal locality property means that the set of pages important to query $t+1$ is approximately a subset of the pages important to query $t$. By reusing $t$'s selection, $t+1$ may miss a few pages that have slightly increased in relevance, but it will still capture the vast majority of what it needs. The faithfulness of this approximation depends on how rapidly the attention pattern shifts—the paper's results show that shifts are gradual enough that a reuse interval of 4 introduces negligible accuracy loss.

**Context pooling overhead.** The paper also addresses a related overhead: computing the `$k_{\max}$` and `$k_{\min}$` statistics during the prefilling stage. The pooling kernel that computes these per-logical-page statistics executes in "under 1 ms" while the entire prefilling stage takes "approximately 17 seconds with 128K context length." The fraction is negligible (roughly 0.006%), so this overhead is not separately optimized.

#### 3.4.7 Decoding Stage Kernel Implementation: Two-Level Indexing Hierarchy

The decoding kernel must unify two different sparsity patterns within a single implementation: streaming heads that follow a fixed Λ-shaped mask, and dense (retrieval) heads that follow a dynamically-selected page set. The paper's solution (Section 3.6) is a **two-level indexing hierarchy** that separates the GPU's physical iteration order from the logical token positions.

**Physical vs. logical indices.** The GPU kernel iterates using a **physical index**—this is the iteration counter in the sequential loop over blocks. For dense attention, the physical index directly corresponds to the chronological position in the context: physical index $0$ means the first KV page, index $1$ the second, and so on. For sparse attention, the physical index maps to an arbitrary **logical index**—the actual position of the target token within the full KV cache sequence.

**Index tables for sparse attention.** For each dense head with dynamic sparsity, the page selector provides an **index table**—a mapping from physical indices (the iteration order) to logical indices (the actual token positions to load). The kernel iterates sequentially over physical indices 0, 1, 2, ..., $K-1$ (where $K$ is the number of selected pages), and at each step looks up the corresponding logical index in the table, then loads the KV page at that logical position from the KV cache.

For example, if the page selector decides that pages at logical positions 3, 7, 12, and 45 are important, the index table would be `[3, 7, 12, 45]`. The kernel iterates 4 times (physical indices 0–3), loading pages 3, 7, 12, and 45 respectively. The kernel loop body is unchanged from the dense case—it always processes consecutive physical indices—but the data it loads comes from non-consecutive logical positions.

**Streaming heads as a special case.** Streaming heads are treated as a degenerate case of the same mechanism: their index table contains only the logical indices of sink pages and local pages, pre-computed from the fixed Λ-shaped pattern. For a streaming head processing a query at position $p$, the index table might be `[0, 1, ..., S-1, p-L+1, ..., p]` where $S$ is the number of sink pages and $L$ is the number of local pages. The kernel code is identical—it reads the index table and loads the corresponding pages—but the contents of the table are static rather than dynamically determined per step.

**Parallelism across heads.** During the decoding stage, each attention head is processed independently (heads are parallelized across GPU thread blocks). This means different heads can have different index tables—and therefore different sparsity patterns—without any coordination or synchronization overhead. Streaming heads use their pre-computed static tables; dense heads use their dynamically-selected tables from the page selector. Both execute the same kernel with the same code path, unified by the physical-to-logical mapping.

**Why this design matters.** Without the two-level indexing hierarchy, LServe would need separate kernel implementations for streaming heads and dynamically-sparsified dense heads, or it would need to encode sparsity through conditional branches within the kernel (which, as discussed in Section 3.4.3, is inefficient). The index table approach extracts the sparsity-specific logic (determining *which* pages to process) into a pre-processing step and keeps the kernel agnostic to *why* those pages were selected. This separation of concerns enables the multiplicative combination of static and dynamic sparsity: the kernel doesn't need to know whether a particular head's index table came from the Λ-shaped mask, the page selector, or some future sparsity method—it just processes whatever pages it's given.

#### 3.4.8 Composition: How Static and Dynamic Sparsity Compound

The paper's central technical claim—established conceptually in Section 3.1 and validated empirically in Sections 5.4–5.5—is that static and dynamic sparsity are **orthogonal** and their benefits **multiply**. Understanding exactly how this composition works requires tracking computation across both head types.

**Static sparsity removes computation on streaming heads.** Half of all attention heads (by default, at 50% sparsity) operate with the Λ-shaped mask. For these heads, the attention cost is independent of context length—each query attends to a constant number of sink blocks plus local blocks, regardless of whether the total context is 4K tokens or 256K tokens. The paper's analysis (Figure 15, bottom two rows at 256K context) shows that static sparsity alone yields a 1.3–1.7× end-to-end speedup in the attention layer, depending on sequence length.

**Dynamic sparsity caps computation on remaining dense heads.** For the other half of attention heads (the retrieval heads), the dynamic page selector restricts each query to attending to a fixed token budget (e.g., 4096 tokens, corresponding to 64 pages at 64 tokens/page). Without dynamic sparsity, these heads would attend to all 256K tokens in the context, costing 256K operations per query. With dynamic sparsity, they attend to only 4096 tokens—a 62.5× reduction in attended tokens. The paper reports that dynamic sparsity alone (without static streaming heads) delivers up to 30× speedup on the attention layer at 256K context (Figure 15, row 3).

**Why the benefits multiply rather than add.** The two sparsity mechanisms operate on **different heads** and are applied **simultaneously**:

- Streaming heads get the full Λ-shaped mask benefit (constant cost regardless of context length).
- Dense heads get the full dynamic selection benefit (cost bounded to 4096 tokens regardless of context length).
- There is no overlap or conflict: a head is either streaming (using static sparsity) or dense (using dynamic sparsity), never both. The kernel processes both types in the unified two-level indexing framework described previously.

The total cost for the attention layer is therefore approximately:

$$\text{Cost}_{\text{LServe}} \approx 0.5 \cdot \text{Cost}_{\text{streaming}} + 0.5 \cdot \text{Cost}_{\text{dynamic-sparse}}$$

where $\text{Cost}_{\text{streaming}}$ is constant with respect to context length and $\text{Cost}_{\text{dynamic-sparse}}$ is also constant (bounded by the token budget). In contrast, the dense baseline cost is:

$$\text{Cost}_{\text{dense}} = \text{Cost}_{\text{linear-in-S}} \quad \text{(growing without bound)}$$

Figure 15 (bottom row, "LServe Attention") shows the combined effect: at 256K context, the combined kernel achieves over 50× speedup relative to dense attention, which is substantially more than either static sparsity alone (1.7×) or dynamic sparsity alone (30×). The log-scale y-axis makes clear that the combined speedup is multiplicative: $1.7 \times 30 \approx 51\times$, matching the observed 50×+.

**End-to-end composition (Figure 16).** The paper also provides an end-to-end speedup breakdown (not just attention layer) for Llama-3-8B with batch size 1 across sequence lengths from 4K to 256K:
- **+50% streaming heads alone** (static sparsity): up to 1.7× end-to-end speedup at short-to-medium contexts, with benefits diminishing at very long contexts because the remaining dense heads still incur growing cost.
- **+Dynamic sparsity alone** (4K token budget): up to 4.5× end-to-end speedup at 256K, with minimal benefit at short contexts (the overhead of page selection roughly cancels the sparse attention saving at 4K–8K).
- **LServe (combined):** achieves the best of both—the streaming head speedup at short contexts (1.7× at 4K) and the dynamic sparsity speedup at long contexts (7.7× at 256K), without either regime suffering from the other's overhead.

The paper notes that LServe "configures sparse patterns through offline profiling, effectively avoiding slowdowns from dynamic sparsity at shorter context lengths" (Section 5.5). This means the system can selectively disable dynamic sparsity when the context is short enough that the page selection overhead exceeds the sparse attention savings, a practical optimization not explored in depth but mentioned as part of the system's adaptive behavior.

#### 3.4.9 System Integration: LServe's Relationship to the Serving Stack

LServe is built on top of QServe (Lin et al., 2024b), which itself extends TensorRT-LLM (NVIDIA, 2023). The paper describes LServe as enhancing QServe "by introducing sparsity into both prefilling and decoding dataflows" (Section 3.2). Understanding this integration clarifies what LServe modifies and what it inherits.

**What LServe inherits from QServe.** QServe provides W4A8KV4 quantization—weights in 4-bit, activations in 8-bit, and KV cache values in 4-bit—along with optimized GEMM (general matrix multiply) kernels for quantized computation. LServe retains this quantization infrastructure, which means the dense (retrieval) heads in LServe benefit from both quantization (reducing memory traffic per selected page) and sparsity (reducing the number of pages loaded). The two are complementary and compound: quantization reduces the cost of each iteration of the sequential block loop; sparsity reduces the number of iterations.

**What LServe modifies.** The key changes relative to QServe's dataflow are:

1. **Prefilling stage:** The dense attention kernel is replaced with the unified block-sparse kernel (Section 3.4). The KV cache write-back operation uses two separate kernels—one for streaming heads (writing only sink and local pages, dramatically reducing memory requirements) and one for dense heads (writing full pages, including the `$k_{\max}$` and `$k_{\min}$` statistics appended after the quantized features).

2. **Dual KV cache management:** Rather than a single KV cache for all heads, LServe maintains two separate paging systems (Figure 5). The streaming head cache is organized similarly to QServe's pages (with scaling factors and zero points stored immediately after the token features for dequantization) but is much smaller because it only stores sink blocks and recent local blocks. The dense head cache includes the per-page key statistics concatenated after the quantized key and value features.

3. **Decoding stage:** The dense attention kernel is replaced with the combined kernel (Section 3.6), which takes the page selection results as input. The page selector itself is a new component that runs before (or periodically during) decoding.

**Page table structure.** Figure 5's right panel shows the layout. The dense head page table maps logical block IDs to physical memory addresses for K and V pages, with the `K_stats` data (min/max vectors) stored inline. The streaming head page table maps the same logical block IDs, but only sink and local pages are present—intermediate pages are not allocated. The figure illustrates this with placeholder addresses (0x7A40, etc.) showing the physical memory layout.

**Compatibility with batch serving.** While the paper's primary evaluation uses batch size 1 (to isolate the attention overhead), the system supports batched inference through the standard PagedAttention mechanism inherited from vLLM/QServe. Each sequence in a batch has its own KV cache and its own page selection results. The attention kernel processes batch elements in parallel across different GPU thread blocks, with each block independently using its sequence's index table for sparse attention.

## 4. Key Insights and Innovations

### Innovation 1: Orthogonality of Static and Dynamic Sparsity as a Compositional Design Principle

The paper's most intellectually distinctive move is not proposing a new sparsity pattern—it is demonstrating that **static (head-level) and dynamic (query-level) sparsity are orthogonal optimization axes whose benefits multiply when combined in a single kernel**, and that prior work's failure to combine them left substantial performance on the table. This is a conceptual reframing, not an algorithmic invention.

Prior to LServe, the field implicitly treated sparse attention as a **design choice** rather than a **design space**: systems chose either static patterns (StreamingLLM, H2O, DuoAttention) or dynamic patterns (Quest, MInference), but never both simultaneously. The implicit assumption was that these approaches were alternative solutions to the same problem—reduce attention cost—and that picking the best one was the optimization. LServe refutes this by showing the two types of sparsity operate on **different heads** with **non-overlapping computational savings**, so their benefits compound rather than substitute.

The evidence in Figure 15 makes this orthogonality concrete. Static sparsity (50% streaming heads) yields 1.3–1.7× attention layer speedup at 256K context; dynamic sparsity (4K token budget) yields ~30× speedup; LServe's combined kernel yields over 50×. The multiplicative relationship (~1.7 × 30 ≈ 51) is not a coincidence—it reflects the fact that streaming heads and dynamically-pruned dense heads form disjoint sets, so the savings accumulate without interference. Figure 16 reinforces this at the end-to-end level: static sparsity dominates at short contexts (1.7× at 4K), dynamic sparsity dominates at long contexts (7.7× at 256K), and LServe captures both regimes through what the paper calls "offline profiling" to selectively apply each pattern where it is most effective.

The significance of this insight extends beyond LServe's specific implementation. It establishes a **compositional framework** for sparse attention: any future sparsity method can be integrated by mapping its pattern onto the block-sparse abstraction (producing an index table for the kernel), and the framework guarantees that independently-developed static and dynamic methods will compose without conflict as long as they partition the heads (static) or the pages (dynamic) along separate dimensions. This transforms sparse attention from a menu of competing point solutions into a **composable toolkit**—a conceptual shift with implications for how future systems should be architected.

### Innovation 2: The Block-Sparse Abstraction as a GPU-Aware Unification Layer

LServe's second distinctive contribution is diagnostic rather than algorithmic: it identifies **why prior sparse attention methods failed to translate theoretical FLOPs reduction into measured speedup**, and it proposes a specific abstraction—**block-level sparsity with an iterator-based kernel interface**—that closes this gap. This is an engineering insight with conceptual depth: it explains a systematic failure mode and provides a general solution template.

The diagnostic move is in Section 2.2 and Figure 3. The field had accumulated multiple sparse attention algorithms, each claiming FLOPs reductions but often delivering disappointing wall-clock improvements. LServe traces this to a specific GPU execution constraint: **warp-level lockstep execution**. When threads within a GPU warp take different paths (some computing, some skipping), the warp's execution time equals the *maximum* path, not the *average*. Token-level sparsity within a block therefore produces idle threads, not idle time—the warp still waits for the longest computation. Reducing the number of sequential block iterations, by contrast, directly shortens the critical path because *all* threads in the warp finish each iteration together.

This insight leads to the paper's architectural prescription: organize all sparsity at the **block (page) granularity** matching the GPU's natural iteration unit ($T_Q \times T_K$ tiles), and represent sparsity patterns as **index tables** that map a dense physical iteration order to sparse logical positions. The iterator-based kernel (Section 3.4.3) and the two-level indexing hierarchy (Section 3.6) are implementations of this principle, but the principle itself—**sparsity must be coarsened to the GPU's iteration granularity to yield speedup, and the right abstraction is a level of indirection between loop counters and memory positions**—is a transferable lesson for any sparse attention system.

The paper validates this diagnostic through comparison. Figure 12 shows that at the same sparsity level, LServe's block-sparse kernel achieves 1.3× speedup over MInference's implementation, closing a substantial fraction of the gap to the oracle upper bound (where latency scales perfectly with sparsity). The gap that remains quantifies the fixed overhead of dense heads, kernel launch, and iterator setup—costs that would exist in any sparse system but are minimized by LServe's design. This establishes that **implementation architecture, not just sparsity algorithm, determines whether gains materialize**.

### Innovation 3: The Page Size Dilemma and Hierarchical Paging as a Systems-Algorithm Boundary Solution

LServe identifies and solves a previously undocumented tension between **GPU memory bandwidth efficiency** (which demands large page sizes for quantization) and **sparse attention accuracy** (which demands small page granularity for discriminative importance estimation). This is a **systems-algorithm boundary problem**—it arises where hardware constraints (memory transaction sizes, cache line alignment) interact with algorithmic assumptions (statistical representativeness of per-page summaries)—and LServe's hierarchical paging solution is a clean architectural resolution rather than a heuristic compromise.

The dilemma itself is a diagnostic contribution. Table 1 shows that page size 64 yields up to 1.52× better decoding throughput than page size 16 at long sequences—this is the hardware's demand. Figure 6 shows that page size 64 destroys Quest-style page selection accuracy compared to page size 16—this is the algorithm's demand. The field had been navigating this tension implicitly (Quest uses page size 16, trading off some memory bandwidth; QServe uses page size 64, forgoing sparse attention entirely), but LServe is the first paper to **name the dilemma explicitly** and solve it through abstraction rather than compromise.

The solution—decoupling logical page granularity ($N_L = 16$ for accurate statistics) from physical page granularity ($N_P = 64$ for memory bandwidth) through hierarchical max-reduction—is elegant because it recognizes that the two granularities serve different consumers. The logical granularity feeds the **page selector's statistical estimator**, which needs fine-grained min/max values to remain discriminative. The physical granularity feeds the **GPU's memory system**, which needs large contiguous blocks to maximize bandwidth utilization. By computing statistics at the logical level and aggregating them to the physical level via max-reduction, LServe satisfies both consumers without either knowing about the other's requirements.

Figure 13 validates this empirically: hierarchical paging with ($N_P = 64$, $N_L = 16$) preserves Needle-in-a-Haystack accuracy at the same token budget as the baseline with ($N_P = 16$, $N_L = 16$), whereas a naive system with ($N_P = 64$, direct page-wise statistics) degrades substantially. The finding that spatial locality makes this work—important logical pages cluster within the same physical pages, so max-reduction rarely forces retention of large irrelevant blocks—is an empirical observation with theoretical implications for attention's locality properties that the paper documents but does not fully analyze.

### Innovation 4: Temporal Locality as a Mechanism for Reducing Dynamic Selection Overhead

LServe's reusable page selector exploits a property of autoregressive decoding that prior sparse attention systems had not systematically leveraged: **temporal locality in query attention patterns**—the observation that adjacent decoding steps attend to substantially overlapping sets of historical pages. This is a conceptually simple insight with large practical impact, and the paper provides a clean characterization of the accuracy-overhead tradeoff.

Prior dynamic sparse attention systems (Quest, MInference) recomputed token/page importance from scratch at every decoding step. The implicit assumption was that each query is sufficiently different from the previous one that independent selection is necessary. LServe challenges this assumption by measuring the *cost* of reuse versus the *benefit* of freshness, finding that the optimal tradeoff substantially favors reuse.

The evidence is in Figure 14 and Table 6. Without reuse, the page selector dominates per-step latency at sequence lengths above 64K—it becomes the system bottleneck, not the attention computation it's meant to accelerate. With reuse interval 4, page selection overhead drops by 4× while accuracy on RULER at 64K (with 4096-token budget) remains at 85.6%, only 1.2 points below the dense baseline of 86.8%. This is a substantial efficiency gain with negligible accuracy cost.

What makes this an insight rather than an obvious optimization is the characterization of *how far* reuse can be pushed. Table 6 shows that accuracy degrades slowly: reuse interval 8 remains at 84.8% (still only 2 points below dense), and only at interval 16 does the drop-off accelerate. This suggests that attention patterns in decoding exhibit **substantial inertia**—the set of relevant historical tokens changes gradually over 4–8 generation steps—which is a finding about LLM behavior with implications beyond LServe. It implies that systems could potentially predict future attention patterns from recent history, amortize selection across even larger chunks, or use the reuse property to reduce the cost of speculative decoding with sparse attention.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** LongBench (Bai et al., 2023), a bilingual multi-task benchmark for long-context understanding, evaluated across 8 tasks (2WikiMQA, DuReader, HotpotQA, MultiNews, Qasper, QMSum, SamSum, TriviaQA) on the standard test set as referenced in Table 2 and Appendix A. Additional evaluations use Needle-in-a-Haystack (Kamradt, 2024) for retrieval pressure testing across 0–256K context lengths at varying document depths (Figures 6, 9, 13), RULER (Hsieh et al., 2024) at 32K–256K sequence lengths with challenging tasks including multi-hop tracing and aggregation (Tables 3, 6), and reasoning benchmarks AIME2024 (MAA, 2024) and MATH500 (Hendrycks et al., 2021) evaluated on DeepSeek-R1-Distill-Llama-8B (Table 4).

- **Base model(s).** Three architectures spanning different attention designs: Llama-3-8B (Dubey et al., 2024) using grouped-query attention (GQA), Llama-2-7B (Touvron et al., 2023) using multi-head attention (MHA), and Minitron-4B (Muralidharan et al., 2024) as a smaller-scale model. For long-context capability, the context-extended Llama-3-8B variant from Gradient (Pekelis et al., 2024) supports sequences up to 512K tokens. The authors argue these models are "representative of the capabilities of many contemporary LLMs" and cover both MHA and GQA architectures, which have different KV cache organization and therefore different sparsity characteristics. For reasoning evaluation, DeepSeek-R1-Distill-Llama-8B (DeepSeek-AI et al., 2025) is used to test compatibility with chain-of-thought reasoning models.

- **Metrics.** Primary metrics are **generation throughput** and **latency**. For the prefilling stage, time-to-first-token (TTFT) is the key metric, reported as absolute latency (seconds) in Table 5 and as relative throughput normalized to LServe's speed in Figure 11. For the decoding stage, per-token generation latency (milliseconds per step) is the key metric, reported as absolute numbers in Table 1 for the page size ablation, and as relative throughput (normalized to LServe) in Figure 10. End-to-end accuracy is measured on LongBench as task-specific scores (varying by task, reported as percentages in Table 2), on NIAH as retrieval accuracy (heatmaps with 0–1 scale in Figures 6, 9, 13), on RULER as aggregate accuracy percentage (Tables 3, 6), and on AIME/MATH500 as accuracy percentage (Table 4). For the prefilling kernel micro-benchmark (Figure 12), latency is measured in milliseconds per attention kernel invocation at varying sparsity levels.

- **Baselines.** Five systems are compared:
  - **vLLM** (Kwon et al., 2023b), version 0.6.3, one of the most widely-deployed LLM serving systems featuring PagedAttention and continuous batching. Used as the primary dense-attention baseline.
  - **QServe** (Lin et al., 2024b), using W4A8KV4 quantization (4-bit weights, 8-bit activations, 4-bit KV cache). LServe is built on QServe's codebase, making this the most direct comparison for isolating the benefit of sparsity beyond quantization alone.
  - **MInference** (Jiang et al., 2024b), the state-of-the-art long-context prefilling acceleration system using dynamic sparse attention. Note the paper's caveat: MInference exhibits "limited decoding performance due to its unoptimized decoding stage with dense attention," but "when integrated into vLLM, it can achieve throughput comparable to that of vLLM" (Figure 10 caption).
  - **DuoAttention** (Xiao et al., 2024), a strong long-sequence LLM inference framework with static sparse attention (the origin of the retrieval/streaming head classification that LServe adopts).
  - **Quest** (Tang et al., 2024), the state-of-the-art long-context decoding stage acceleration system. Evaluated only on Llama-2-7B in Table 5 because "Quest does not support GQA architecture" (Table 5 caption).

- **Generation budget / compute accounting.** The paper measures compute indirectly through sequence length sweeps rather than a generation budget in the sense of "number of samples." Efficiency experiments compare systems at matched sequence lengths from 4K to 512K (prefilling: Figures 11, 12, Table 5; decoding: Figures 10, 14, 15, 16, Table 1). For the decoding stage, batch size 1 is used for latency profiling (Figures 10, 14, 15, 16), while Table 1 uses batch size 32 for the page size throughput analysis. For accuracy evaluations, LServe uses a fixed configuration: 50% of attention heads converted to streaming heads, dynamic sparsity with a token budget of 4096 (Figures 6, 9, 13; Tables 2, 3, 6) or 8192 (Tables 3, 6). MInference's dynamic sparsity is activated in the prefilling stage after 128K sequence length (Figure 11). The paper does not use a unified "compute budget" metric across methods (such as FLOPs or total GPU cycles) but relies on the natural fairness of comparing systems at identical sequence lengths, batch sizes, and GPU hardware (A100 80GB or L40S 48GB).

- **Cross-validation / statistical protocol.** The paper does not report cross-validation or statistical testing protocols. Accuracy evaluations on LongBench, RULER, AIME, and MATH500 report raw accuracy scores without confidence intervals or multiple runs. NIAH results are presented as heatmaps showing accuracy at each (document length, document depth) combination without error bars. The throughput benchmarks similarly report per-configuration measurements without indication of variance across runs. The paper mentions "offline profiling" for configuring sparse patterns (Section 5.5, Figure 16) but does not detail the profiling methodology or how it separates configuration data from evaluation data.

### Main Quantitative Results

#### End-to-End Accuracy Preservation

The paper's central accuracy claim is that LServe's hybrid sparsity preserves the performance of the original dense models across diverse benchmarks. Table 2 reports LongBench results for Llama-3-8B and Llama-2-7B averaged across 8 tasks. For Llama-3-8B: dense baseline achieves 38.9 average accuracy; LServe achieves 38.6—a difference of 0.3 percentage points. For Llama-2-7B: dense achieves 39.5; LServe achieves 39.4—a difference of 0.1 points. Individual task variations are modest: the largest single-task degradation is on Qasper for Llama-2-7B (32.6 → 29.5, a 3.1-point drop), while some tasks show slight improvements (HotpotQA on Llama-2-7B: 47.4 → 49.6, +2.2 points). These results demonstrate that converting 50% of heads to streaming heads and applying dynamic page pruning with a 4096-token budget introduces negligible aggregate accuracy loss on standard long-context understanding tasks.

Figure 9 extends this to the Needle-in-a-Haystack retrieval stress test, presenting side-by-side heatmaps for Llama-3-8B with dense attention (panel a) and LServe (panel b). The heatmaps are visually nearly identical, showing that LServe maintains the same retrieval pattern: accuracy is near-perfect (dark regions indicating 1.0 accuracy) across all document depths and lengths up to 256K, with no systematic degradation in any region of the (depth, length) space. This is a more demanding test than LongBench because it probes retrieval from arbitrary positions, and the preservation of the dense pattern confirms that the dynamic page selector (with hierarchical paging and 4096-token budget) does not systematically miss information at any document depth.

Table 3 reports RULER benchmarks, which include "challenging tasks such as multi-hop tracing and aggregation to test behaviors beyond searching from context." For Llama-3-8B with a 4096-token budget (LServe-4096): accuracy tracks the dense baseline within ~1–3 points across sequence lengths from 32K to 256K: 91.0 vs. 90.5 at 32K; 85.6 vs. 86.8 at 64K; 81.0 vs. 83.8 at 128K; 79.0 vs. 79.3 at 160K; 76.1 vs. 79.6 at 192K; 75.7 vs. 79.4 at 256K. The gap widens slightly at longer contexts (256K gap = 3.7 points), which the paper attributes to the token budget being insufficient for extreme-length multi-hop reasoning. Doubling the token budget to 8192 (LServe-8192) largely closes this gap: 91.8 vs. 90.5 at 32K; 86.1 vs. 86.8 at 64K; 81.7 vs. 83.8 at 128K; 81.2 vs. 79.3 at 160K; 79.7 vs. 79.6 at 192K; 79.1 vs. 79.4 at 256K. The paper notes that "LServe-8192 is only up to 6% slower than LServe-4096 when the sequence length exceeds 128K" because "latency is not dominated by attention alone in LServe, with page selector and GEMM also contributing to it." This quantifies the accuracy-efficiency tradeoff: doubling the token budget recovers most of the dense performance on the hardest tasks at a modest speed cost.

Table 4 extends the accuracy claim to complex reasoning tasks using DeepSeek-R1-Distill-Llama-8B. On AIME2024: both dense and LServe achieve 43.3% identically. On MATH500: LServe achieves 85.4% vs. dense 84.2%—a 1.2-point improvement (likely within noise, but importantly no degradation). The average across both tasks is 64.4% for LServe vs. 63.8% for dense. This is significant because chain-of-thought reasoning models like DeepSeek-R1 generate long internal reasoning traces, and the result demonstrates that LServe's sparsity patterns—designed primarily for retrieval-oriented long-context tasks—do not interfere with the multi-step logical deduction that reasoning models perform.

Collectively, these accuracy results (Tables 2–4, Figure 9) support the claim that LServe's hybrid sparsity preserves long-context and reasoning capabilities across retrieval benchmarks, multi-hop reasoning, and complex mathematical problem-solving, with aggregate accuracy within 0.3–1.2 points of dense baselines and no systematic degradation pattern.

#### Decoding Stage Throughput

Figure 10 presents the decoding speed evaluation across four configurations (three models on A100, plus Llama-3-8B on L40S), with throughput normalized to LServe's speed (all LServe bars at 1.00). The key comparisons:

**Llama-3-8B on A100 (top-left panel):** Sequence lengths from 64K to 320K with geometric mean across all lengths. vLLM achieves 0.50× LServe's throughput (i.e., LServe is 2.0× faster) at 64K, declining to 0.48× at 320K, with geomean 0.50×—meaning LServe is 2.0× faster on average. QServe achieves 0.12× at 64K, improving relatively to 0.16× at 320K, with geomean 0.15×—meaning LServe is 6.7× faster than QServe on average. DuoAttention achieves 0.63× at 64K, declining to 0.50× at 320K, with geomean 0.50×—LServe is 2.0× faster. MInference shows the widest gap: 0.69× at 64K declining to 0.08× at 320K (geomean 0.31×), with its performance collapsing at longer contexts because it uses dense attention in the decoding stage. At the longest tested length (320K), vLLM's 0.48× means LServe achieves 2.1× speedup.

**Llama-2-7B on A100 (top-right panel):** Sequence lengths from 16K to 224K. vLLM geomean: 0.47× (LServe is 2.1× faster on average). QServe geomean: 0.05× (LServe is 20× faster, though QServe's extremely low throughput likely reflects an out-of-memory or configuration issue not explained in the paper—the values 0.05, 0.03, 0.04, 0.07, 0.12 at lengths 16K–128K seem anomalously low). DuoAttention geomean: 0.47× (LServe is 2.1× faster). MInference geomean: 0.37× (LServe is 2.7× faster). The MHA architecture yields stronger relative benefits than GQA: LServe runs "more than 2.0× faster than baselines on average."

**Minitron-4B on A100 (bottom-left panel):** Sequence lengths from 64K to 512K. At this smaller model scale, vLLM geomean: 0.52× (LServe is 1.9× faster). QServe geomean: 0.06×. MInference geomean: 0.67× (with 0.81× at 512K, showing MInference's relative performance improves at extreme lengths on smaller models). DuoAttention geomean: 0.51×.

**Llama-3-8B on L40S (bottom-right panel):** Demonstrates cross-GPU architecture portability (from A100's Ampere to L40S's Ada Lovelace). vLLM geomean: 0.44× (LServe is 2.3× faster). Many baselines show "OOM" at longer lengths because the L40S has only 48GB memory (vs. A100's 80GB). QServe runs at 0.13× geomean at short lengths before OOM. MInference and DuoAttention largely OOM. At the longest tested length where comparisons exist (256K for vLLM), LServe achieves 1.7× speedup (vLLM at 0.59× relative throughput).

The paper's headline claim of "1.3–2.1× decoding speedup" is derived from these geometric means: approximately 2.0× over vLLM on Llama-3-8B-A100, 2.1× over vLLM on Llama-2-7B, 1.9× over vLLM on Minitron-4B, and 2.3× over vLLM on L40S. The lower end of the range (1.3×) is not prominently visible in Figure 10; it may refer to the Quest comparison in Table 5 or shorter sequence lengths not shown in the geomean aggregates. A notable pattern across all panels: vLLM throughput relative to LServe is relatively flat (0.44–0.52× across all configurations and lengths), indicating LServe's advantage is consistent rather than growing dramatically with sequence length—the benefits of dynamic sparsity (which scale with length) appear to roughly balance with the baseline's growing per-step cost.

#### Prefilling Stage Throughput

Figure 11 presents prefilling speed results, again normalized to LServe (1.00). Two configurations are shown: Llama-3-8B on A100 (left) at lengths 64K–320K, and Llama-2-7B on A100 (right) at lengths 16K–160K. MInference is included for the Llama-2-7B panel up to 128K, after which it goes OOM.

**Llama-3-8B-A100:** vLLM achieves geomean 0.34× LServe's throughput, meaning LServe is 2.9× faster on average (the paper's headline "up to 2.9×"). QServe achieves 0.56× geomean. DuoAttention achieves 0.60× geomean. MInference achieves 0.68× geomean. Notably, vLLM's relative throughput is not monotonic: 0.34× at 64K, 0.20× at 96K, 0.24× at 128K, 0.29× at 192K, 0.45× at 256K, 0.49× at 320K—the worst relative performance occurs at medium lengths. LServe's advantage peaks at 96K (5.0× over vLLM) and narrows at 320K (2.0× over vLLM). The paper notes that LServe activates MInference's dynamic prefilling sparsity after 128K, which may explain the narrowing at longer lengths (MInference's sparsity helps the dense baseline more than it helps LServe, since LServe already has streaming head sparsity).

**Llama-2-7B-A100:** vLLM geomean: 0.56× (LServe is 1.8× faster on average). QServe geomean: 0.43× (with OOM at 96K). DuoAttention geomean: 0.49×. MInference geomean: 0.63× (at lengths where it runs, 16K–128K). The paper reports that "on Llama-2-7B, LServe achieves an average of 1.8× higher prefilling throughput over vLLM."

The prefilling stage results demonstrate that static streaming head sparsity (present in both models) provides substantial acceleration without needing the dynamic page selector (which operates only during decoding). The advantage over DuoAttention at similar sparsity levels (50% streaming heads) suggests that LServe's iterator-based kernel implementation (Section 3.4.3) extracts more of the theoretical FLOPs savings than DuoAttention's kernel does. The advantage over MInference—which applies dynamic sparsity during prefilling—suggests that static sparsity (streaming heads) provides more reliable speedup than dynamic methods for the prefilling stage, at least at the tested sequence lengths, because it avoids the runtime overhead of determining sparsity patterns for each query.

#### End-to-End Comparison with Quest

Table 5 directly compares LServe against Quest on Llama-2-7B, the only model both systems support (Quest does not handle GQA architectures). The table reports both prefilling latency (seconds) and decoding latency (milliseconds per step) at sequence lengths 4K–64K, with Quest going OOM at 64K.

**Prefilling latency:** At 4K: LServe 0.24s vs. Quest 0.51s (2.1× speedup). At 8K: 0.49s vs. 0.82s (1.7×). At 16K: 1.08s vs. 1.62s (1.5×). At 32K: 2.32s vs. 3.61s (1.6×). At 64K: LServe 5.27s, Quest OOM. The speedup ranges from 1.5–2.1× across lengths where both run, with LServe's advantage persisting but narrowing as length increases.

**Decoding latency:** At 4K: LServe 10.02 ms vs. Quest 13.13 ms (1.3× speedup). At 8K: 10.29 vs. 13.58 (1.3×). At 16K: 10.22 vs. 14.08 (1.4×). At 32K: 10.24 vs. 14.86 (1.5×). At 64K: LServe 11.54 ms, Quest OOM. LServe's per-step decoding latency is essentially flat from 4K to 32K (10.02–10.29 ms), then rises modestly to 11.54 ms at 64K, consistent with the claim that dynamic sparsity bounds decoding complexity to a constant (the token budget) regardless of context length. Quest's latency grows from 13.13 to 14.86 ms across the same range, suggesting its page selection or attention kernel has some residual length dependence.

This head-to-head comparison isolates LServe's advantages: the streaming head sparsity (which Quest lacks) accelerates prefilling; the unified kernel with two-level indexing (Section 3.6) and the reusable page selector (Section 3.5.3) reduce decoding overhead per step compared to Quest's approach. The OOM for Quest at 64K (on A100, the same hardware LServe runs on) indicates LServe's dual cache design with separate streaming/dense caches also reduces memory pressure.

### Ablation Studies and Robustness Checks

**Prefilling kernel implementation vs. MInference and oracle upper bound (Figure 12):** LServe's block sparse attention kernel for the prefilling stage is benchmarked against MInference's implementation and a theoretical oracle defined as $\text{Latency}_\text{oracle} = \text{Latency}_\text{dense} \times (1 - \text{sparsity})$. At all sparsity levels from ~4% to ~40%, LServe achieves lower absolute latency than MInference. For example, at approximately 20% sparsity: dense baseline takes 42.3 ms; MInference takes ~30.0 ms; LServe takes ~20.0 ms—a 1.5× speedup over MInference at this point. At approximately 40% sparsity: MInference takes ~21.2 ms; LServe takes ~15.9 ms—a 1.3× speedup. LServe consistently achieves 1.3× speedup over MInference across the range, confirming that the iterator-based design (skipping blocks without conditional branching) translates the same theoretical sparsity into more actual wall-clock improvement. The oracle upper bound is consistently lower than both implementations, with LServe closing roughly half the gap between MInference and the oracle. This gap represents fixed overheads: dense heads (50% of total), kernel launch, iterator setup overhead, and memory access patterns that don't perfectly scale with sparsity.

**Hierarchical paging for dynamic sparsity accuracy (Figure 13):** This ablation tests whether hierarchical paging preserves NIAH accuracy when physical page size is increased while keeping the logical page size (and token budget) constant. Three configurations are compared, all at token budget 3072: (a) $N_P = 16, N_L = 16$ (baseline: physical and logical pages match at 16 tokens), (b) $N_P = 32, N_L = 16$ (physical pages doubled, logical pages unchanged, using hierarchical paging), (c) $N_P = 64, N_L = 16$ (physical pages quadrupled). All three heatmaps show near-identical retrieval patterns across document depths and lengths up to 256K, with no visible degradation in any panel. This contrasts sharply with Figure 6(b)–(d), which showed progressive degradation when page-wise statistics were computed directly at the larger page sizes without hierarchical decomposition. The ablation confirms that the accuracy preservation comes specifically from the hierarchical structure (maintaining fine-grained logical page statistics) rather than from any other property of the system.

**Reusable page selector overhead reduction (Figure 14):** This ablation measures the latency breakdown of a single decoding step into two components: the dynamic page selector and the sparse attention kernel. For the vanilla (no reuse) case: at 8K sequence length, the selector takes ~0.04 ms and attention takes ~0.03 ms. At 32K: selector ~0.07 ms, attention ~0.05 ms. At 64K: selector ~0.13 ms, attention ~0.07 ms. At 128K: selector ~0.24 ms, attention ~0.12 ms—the selector is now 2× the attention kernel. At 256K: selector ~0.50 ms, attention ~0.20 ms—the selector is 2.5× the attention kernel. With the reusable page selector (reuse interval 4, as configured by default): the selector latency is reduced by approximately 4× at each sequence length—at 256K, it drops from ~0.50 ms to ~0.13 ms. The attention kernel latency is unchanged (the same pages are selected; only the frequency of selection changes). At 256K, the reusable selector brings the total per-step overhead (selector + attention) from ~0.70 ms to ~0.33 ms—a 2.1× improvement in per-step latency from this single optimization.

**Reuse interval sensitivity (Table 6):** This ablation characterizes how many decoding steps can reuse the same page selection before accuracy degrades. On Llama-3-8B at 64K sequence length evaluated on RULER: the dense baseline achieves 86.8% accuracy. For LServe-4096: reuse interval 1 (no reuse) = 86.2%; interval 2 = 85.6%; interval 4 = 85.6%; interval 8 = 84.8%; interval 16 = 83.2%. For LServe-8192: interval 1 = 86.1%; interval 2 = 85.8%; interval 4 = 85.5%; interval 8 = 85.6%; interval 16 = 84.8%. The key finding is that accuracy remains essentially flat through reuse interval 4 (within 1.2 points of dense for the 4096-token budget, and within 1.3 points for the 8192-token budget), with noticeable degradation beginning at interval 8 and more substantial loss at interval 16. This supports the default choice of reuse interval 4: it achieves a 4× reduction in page selection overhead while incurring negligible accuracy cost.

**Static vs. dynamic sparsity contribution to attention layer speedup (Figure 15):** This ablation decomposes the speedup of LServe's attention kernel by testing three configurations against the dense baseline: (1) dense attention (baseline), (2) +static sparsity only (50% streaming heads, no dynamic pruning), (3) +dynamic sparsity only (4K token budget, no streaming heads), and (4) LServe (both combined). Reported as latency in microseconds for a single attention layer in Llama-2-7B at sequence lengths from 4K to 256K, with absolute latencies annotated on each bar. At 4K: dense = 82 µs; +static = 82 µs; +dynamic = 118 µs (dynamic sparsity actually slows down at short contexts due to page selection overhead); LServe = 81 µs (static sparsity offsetting the dynamic overhead). At 16K: dense = 2,052 µs; +static = 748 µs (2.7× speedup); +dynamic = 384 µs (5.3× speedup); LServe = 306 µs (6.7× speedup). At 64K: dense = 3,492 µs; +static = 1,238 µs (2.8×); +dynamic = 545 µs (6.4×); LServe = 306 µs (11.4×). At 256K: dense = 3,492 µs (same as 64K? This appears to be an error in the figure—the dense bar at 256K shows 3,492 µs, identical to 64K, when it should be ~4× larger based on the linear scaling of decoding attention with sequence length); +static = 2,052 µs (1.7× over dense at 256K?); +dynamic = 71 µs (49×); LServe = 68 µs (51×). The key insight from this ablation is that static and dynamic sparsity provide speedups that multiply: at 256K, static alone gives ~1.7×, dynamic alone gives ~49×, and the combination gives ~51×, consistent with the product of the individual speedups ($1.7 \times 49 \approx 83\times$, not 51×—suggesting the annotation on +dynamic alone (71 µs) and LServe (68 µs) shows diminishing additional benefit, or the numbers reflect some overlap). The paper's claim is that the benefits compound: the streaming head savings and the page pruning savings operate on different heads and don't interfere.

**End-to-end speedup breakdown by component (Figure 16):** This ablation shows end-to-end throughput (not just attention layer) for Llama-3-8B on A100 at batch size 1, normalized to dense attention throughput at each sequence length (dense = 1.00 at all lengths). At 8K: +streaming = 1.00; +dynamic = 0.94 (dynamic sparsity hurts slightly due to selection overhead); LServe = 1.00. At 16K: +streaming = 1.00; +dynamic = 0.89; LServe = 1.00. At 32K: +streaming = 1.00; +dynamic = 0.22 (dynamic sparsity severely degrades throughput—the selector overhead dominates any sparse attention savings at this length); LServe = 1.00. At 64K: +streaming = 1.00; +dynamic = 0.47; LServe = 1.00. At 128K: +streaming = 0.97 (streaming heads begin to help slightly); +dynamic = 0.61; LServe = 1.00. At 256K: +streaming = 0.13 (this annotation seems inverted—0.13× throughput means 7.7× slower than dense, which contradicts the attention-layer finding that streaming heads provide 1.7× speedup at 256K); +dynamic = 0.35; LServe = 1.00. This figure is difficult to interpret from the paper's description alone—the normalized values appear to be inverted (lower = worse throughput), and the text states "LServe achieves... a 7.7× speedup for sequence lengths of 256K" relative to dense, but the bar shows LServe at 1.00 (implying normalized dense throughput, not speedup). The likely interpretation: LServe's bar at 1.00 represents normalized throughput, and the 7.7× figure comes from comparing absolute throughput at 256K (LServe achieving 7.7× the tokens/second of the dense baseline at that length). The key qualitative finding is that static sparsity yields greater relative benefit at shorter-to-medium contexts while dynamic sparsity dominates at long contexts, and LServe captures both through "offline profiling" that "effectively avoid[s] slowdowns from dynamic sparsity at shorter context lengths."

**Page size impact on system efficiency (Table 1):** This ablation quantifies how physical page size affects per-step decoding latency in QServe (without sparsity) across sequence lengths 512–8192 at batch size 32 with Llama-3-8B architecture. At 512 tokens: page size 16 = 11.0 ms; 32 = 10.7 ms; 64 = 10.5 ms; 128 = 10.5 ms—a 1.05× slowdown from largest to smallest page. At 4096 tokens: 16 = 35.7 ms; 32 = 31.6 ms; 64 = 28.1 ms; 128 = 28.1 ms—a 1.27× slowdown. At 8192 tokens: 16 = 77.1 ms; 32 = 63.0 ms; 64 = 51.0 ms; 128 = 50.6 ms—a 1.52× slowdown from page size 16 to 64. Latency plateaus at page size 64 (64 and 128 yield nearly identical latencies), indicating that 64 tokens per page achieves saturating memory bandwidth on the A100 for quantized KV caches. This ablation provides the hardware motivation for LServe's choice of $N_P = 64$ as the default physical page size: it maximizes throughput, and LServe's hierarchical paging is designed specifically to enable accurate sparse attention at this throughput-optimal page size.

**Context pooling overhead:** While not presented as a standalone ablation, the paper notes (Section 5.3, final paragraph) that the min-max pooling kernel for computing `$k_{\max}$` and `$k_{\min}$` statistics during prefilling executes in "under 1 ms" while the entire prefilling stage takes "approximately 17 seconds with 128K context length"—an overhead of roughly 0.006%. This is presented as evidence that the hierarchical paging infrastructure adds negligible cost to the prefilling stage.

#### Ablation on Reasoning Model Compatibility (Implicit)

Table 4 can be read as an ablation testing whether LServe's sparsity patterns—designed for retrieval-oriented long-context evaluation—generalize to reasoning models that generate long chains of thought. The result (identical AIME accuracy, slightly improved MATH500 accuracy) suggests that the sparsity does not interfere with multi-step logical reasoning, but the evaluation covers only the final answer accuracy, not the intermediate reasoning trace quality. The paper does not report whether LServe affects the length, coherence, or correctness of intermediate reasoning steps—only whether the final answer matches the ground truth. This is a potential blind spot: a reasoning trace that reaches the correct answer through a degraded or less rigorous path might pass the accuracy check but be qualitatively worse.

### Critical Assessment

#### Claim 1: "LServe accelerates LLM prefilling by up to 2.9× and decoding by 1.3–2.1× over vLLM, maintaining long-context accuracy"

**What the experiments actually demonstrate:** Figure 11 shows prefilling geomean speedups of 2.9× over vLLM on Llama-3-8B-A100 and 1.8× on Llama-2-7B-A100. Figure 10 shows decoding geomean speedups of approximately 2.0× on Llama-3-8B, 2.1× on Llama-2-7B, and 1.9× on Minitron-4B, all on A100. The accuracy claim is supported by Tables 2–4 and Figures 9, 13.

**Qualifications and weaknesses:**

- **The 2.9× prefilling figure applies to a specific model (Llama-3-8B) at specific lengths (64K–320K), with the peak advantage at 96K and narrowing to 2.0× at 320K.** The geometric mean flattens what is a non-monotonic relationship (vLLM/LServe ranges from 0.20 to 0.49× across lengths). The "up to" qualifier is appropriate, but readers should understand that 2.9× is the geometric mean across the measured range, not a universally achievable speedup.

- **The 1.3–2.1× decoding range is vague.** Figure 10 shows geomeans of 2.0×, 2.1×, 1.9×, and 2.3× across four configurations, all near the high end of the claimed range. The 1.3× lower bound is not visible in Figure 10's aggregate metrics; it may correspond to the Quest comparison in Table 5 (where 1.3× appears as the decoding speedup at short lengths). If so, the 1.3–2.1× range conflates two different comparisons: LServe vs. vLLM (~2.0×) and LServe vs. Quest (1.3–1.5×). This is a minor presentation issue but obscures the more impressive vLLM comparison.

- **Batch size 1 is used throughout the main throughput figures (10, 11, 14, 15, 16).** The paper acknowledges that QServe notes "the ratio of attention kernels in end-to-end runtime will increase as the batch size scale[s] up" (Section 2.2), implying LServe's advantages might grow with batch size. However, the paper evaluates only batch size 1 for the main speedup claims, leaving the batch-size scaling behavior untested. Table 1 uses batch size 32 for the page size ablation, but this is on the baseline QServe system, not LServe. Whether LServe's speedup compounds or saturates at realistic serving batch sizes (8–64) is unknown.

- **Accuracy "maintenance" is relative, not absolute.** Table 2 shows LServe within 0.3 points of dense on aggregate LongBench, but individual tasks vary: Qasper drops 3.1 points on Llama-2-7B, while HotpotQA gains 2.2 points. Table 3 shows LServe-4096 is 3.7 points below dense at 256K on RULER. The claim "maintaining long-context accuracy" is true in aggregate but elides that the hardest tasks at the longest contexts show measurable degradation (recoverable with larger token budgets, as LServe-8192 demonstrates).

- **The paper does not report variance or statistical significance.** All accuracy numbers are single-run percentages. For a 500-question test set like MATH500, an 84.2% vs. 85.4% difference is 6 questions—well within plausible run-to-run variation. Without multiple runs or confidence intervals, these differences cannot be interpreted as genuine improvements or degradations.

#### Claim 2: "Static and dynamic sparsity are orthogonal... enabling multiplicative speedups"

**What the experiments actually demonstrate:** Figure 15 provides the most direct evidence, showing attention-layer speedups. At 256K, the paper reports: dense = 3,492 µs; +static only = 2,052 µs (1.7×); +dynamic only = 71 µs (49×); LServe = 68 µs (51×). Figure 16 provides the end-to-end view.

**Qualifications and weaknesses:**

- **The Figure 15 numbers contain an apparent inconsistency.** The dense baseline at 256K is annotated as 3,492 µs—identical to the 64K bar. This is almost certainly a plotting error, since decoding attention latency scales linearly with sequence length for dense attention, and 256K should be ~4× the 64K latency. If the 64K bar is correct at 3,492 µs, the 256K bar should be approximately 14,000 µs. This error propagates to all the speedup calculations at 256K and makes them unreliable. The qualitative finding (static and dynamic sparsity multiply) may still hold, but the specific multiplicative factors cannot be verified from the presented data.

- **The orthogonality claim requires that the two sparsity mechanisms operate on disjoint resources.** The paper argues they do: static sparsity changes which heads are computed, dynamic sparsity changes which pages are loaded for the remaining heads. Figures 15 and 16 are consistent with orthogonality (the combined benefit exceeds either alone), but they do not rigorously test it. A proper orthogonality test would measure static speedup at different dynamic budgets (and vice versa) and show that one's benefit is independent of the other's presence. The paper shows only the three conditions (neither, static only, dynamic only, both) at each length, which is suggestive but not definitive.

- **End-to-end composition (Figure 16) shows that at 16K–32K, dynamic sparsity actually degrades throughput relative to dense (0.89, 0.22× respectively).** Static sparsity rescues the combined system back to parity, but this means the "multiplicative" benefit is not uniformly positive—the two mechanisms interact adversarially at short-to-medium lengths (dynamic overhead outweighs savings), and the system relies on static sparsity to compensate. The paper's claim that LServe "effectively avoid[s] slowdowns from dynamic sparsity at shorter context lengths" through offline profiling is mentioned but not described in detail—readers cannot assess how this profiling works or whether it generalizes.

#### Claim 3: "Only a constant number of KV pages is required to preserve long-context and reasoning capabilities, irrespective of context length"

**What the experiments actually demonstrate:** Table 3 shows that a 4096-token budget preserves RULER accuracy within ~1–4 points of dense from 32K to 256K, and an 8192-token budget closes most of the gap. Figure 13 shows NIAH is preserved at 3072-token budget. Table 4 shows AIME/MATH preserved at the default 4096-token budget (though the sequence lengths for these reasoning traces are not reported).

**Qualifications and weaknesses:**

- **"Required" is not established—the paper shows sufficiency, not necessity.** The experiments demonstrate that 4096 tokens (or 8192 for harder tasks) *suffices* to preserve accuracy within a few points. They do not determine the minimum budget required—the point below which accuracy degrades sharply. A systematic sweep of token budgets (e.g., 1024, 2048, 4096, 8192, 16384) at multiple sequence lengths would establish the scaling relationship, but the paper only compares two budgets (4096 and 8192) at a subset of lengths for one benchmark (RULER, Table 3).

- **The claim holds less well for the hardest RULER tasks** (multi-hop tracing, aggregation) at the longest contexts. LServe-4096 is 3.7 points below dense at 256K (75.7 vs. 79.4). While 8192 tokens recovers to 79.1 (only 0.3 points below dense), this reveals that the "constant" budget depends on task difficulty—harder tasks require larger constants. For general deployment, the required budget is unknown without per-task calibration.

- **The reasoning evaluation (Table 4) lacks context length reporting.** The paper does not state the sequence lengths of the DeepSeek-R1 reasoning traces on AIME and MATH500. If these traces are relatively short (a few thousand tokens rather than hundreds of thousands), the constant-budget claim is not tested at long reasoning contexts, which is the regime where it matters most (o1's traces extend to 20K tokens, as the paper notes in Section 1).

#### Claim 4: "The hierarchical KV page selection policy dynamically prunes KV pages based on query-centric similarity" and "reduces page selection overhead by 4×"

**What the experiments actually demonstrate:** Figure 13 shows hierarchical paging preserves accuracy at larger physical page sizes. Figure 14 quantifies the 4× overhead reduction. Table 6 shows accuracy stability under reuse.

**Qualifications and weaknesses:**

- **The 4× figure only applies to the page selector component, not end-to-end latency.** Figure 14 shows that at 256K, the reusable selector reduces selector latency from ~0.50 ms to ~0.13 ms (3.8× reduction). However, the total per-step decoding latency includes the attention kernel itself (~0.20 ms at 256K), so the end-to-end per-step improvement is from ~0.70 ms to ~0.33 ms—approximately 2.1×, not 4×. The paper's wording "reduces page selection overhead by 4×" is precise about scope, but readers should not extrapolate this to a 4× end-to-end decoding speedup.

- **The hierarchical paging ablation (Figure 13) only tests physical page sizes 16, 32, and 64, all at a single token budget (3072).** The paper claims hierarchical paging "enables LServe to preserve the long-context retrieval capabilities... without increasing the key-value (KV) token budget" (Figure 13 caption). But it demonstrates this only at a specific budget—it doesn't show that a naive system would need a *larger* budget to match LServe's accuracy at page size 64. A direct comparison would be: LServe ($N_P=64, N_L=16$, budget=3072) vs. naive selection ($N_P=64$, direct page-wise statistics) at varying budgets to find the budget needed to match LServe's accuracy. This would quantify the budget savings from hierarchical paging, which is not done.

- **The page selector's overhead is measured for a specific budget (4K tokens) and Llama-3-8B.** The selection cost depends on the number of logical pages that must be scored (which scales with context length divided by $N_L$) and the feature dimension. For models with larger head dimensions or different architectures, the overhead may scale differently. The paper's single-configuration measurement establishes the problem but does not characterize its scaling behavior.

#### Missing Experiments and Baselines

**1. No combination of LServe with speculative decoding or other serving optimizations.** The paper positions LServe as a drop-in replacement for the attention mechanism in existing serving systems, but it does not evaluate LServe combined with complementary techniques like speculative decoding, prefix caching, or continuous batching at scale. Real-world deployments combine multiple optimizations, and evaluating LServe in isolation leaves open questions about composition with other methods.

**2. No sensitivity analysis on the 50% streaming head ratio.** The paper uses 50% streaming heads (half of all attention heads) as the default and evaluates accuracy at this level. It does not sweep the sparsity ratio (e.g., 25%, 50%, 75% of heads as streaming) to characterize the accuracy-throughput tradeoff curve. The optimal ratio might be model-dependent or task-dependent, but the paper provides no guidance.

**3. No end-to-end latency measurement for real workloads (TTFT + generation time).** The prefilling and decoding results are presented separately. A complete request with a long input and long output experiences both stages, plus the interaction between them (e.g., the prefilling stage populates the KV cache that the decoding stage reads). Measuring end-to-end request latency for representative workloads (e.g., 128K input + 8K output) would provide the most user-relevant metric but is not reported.

**4. No comparison against token-level sparsity methods like H2O or StreamingLLM in the main results.** These methods are discussed in related work (Section 6) but not included as baselines in Figures 10 or 11. The paper argues they "struggle to retain the original models' long-context capabilities due to limited global context modeling," but a direct throughput-accuracy comparison would quantify the claimed tradeoff.

**5. No multi-GPU or distributed serving evaluation.** All experiments use a single GPU (A100 or L40S). Long-context serving at scale typically uses tensor parallelism or pipeline parallelism across multiple GPUs to handle large KV caches. How LServe's sparsity interacts with model parallelism—whether the streaming heads can be partitioned differently, whether page selection can be parallelized across GPUs, whether the index-table approach introduces cross-GPU synchronization overhead—is unexplored.

**6. The prefilling kernel benchmark (Figure 12) sweeps sparsity level but does not fix sequence length or specify it.** The reader cannot tell whether the benchmark is at a particular context length or averaged across lengths. The oracle upper bound is defined purely in terms of sparsity ratio, but real kernel performance depends on absolute sequence length (which affects parallelism, memory access patterns, and fixed overhead amortization). A more informative presentation would show lines for multiple sequence lengths or declare the test configuration explicitly.

**7. The reasoning evaluation is minimal.** Table 4 reports two numbers for DeepSeek-R1-Distill-Llama-8B with no context length information, no comparison to other sparse attention methods on the same task, and no analysis of whether the reasoning traces differ qualitatively. Given the paper's emphasis on o1-like reasoning workloads (Section 1), the evaluation of this claim is surprisingly thin.

**8. No characterization of when dynamic sparsity activates/deactivates.** The paper mentions "offline profiling" that decides when to use dynamic sparsity, avoiding its overhead at short contexts (Section 5.5, Figure 16). But this profiling methodology is described only in a single sentence. The threshold lengths, the profiling procedure, the overhead of the profiling itself, and whether the thresholds generalize across models are all unspecified. This is a significant gap because Figure 16 shows dynamic sparsity alone can severely degrade throughput at short-to-medium lengths, making the profiling a critical component of the system's practicality.

#### Summary of Experimental Support

The paper's experiments provide **solid evidence** that LServe's unified block-sparse attention kernel achieves 2–3× prefilling speedup and ~2× decoding speedup over vLLM on long-context workloads with Llama-family models at batch size 1 on A100 GPUs, while preserving accuracy within a few percentage points on standard benchmarks. The evidence for the orthogonality and compoundability of static and dynamic sparsity is **strongly suggestive but not rigorously established**—the multiplicative effect is demonstrated at a few points (Figure 15) but with a likely plotting error that undermines confidence in the specific multiplicative factors, and without a systematic sweep of the interaction space. The evidence for the "constant token budget" claim is **conditional on task difficulty**, with harder multi-hop tasks requiring larger budgets at extreme lengths. The hierarchical paging and reusable selector components are individually validated through targeted ablation experiments. The biggest gaps are the absence of batch-size scaling experiments, the minimal evaluation of reasoning workloads (despite their prominence in the motivation), the unspecified profiling methodology, and the lack of multi-GPU or combined-optimization evaluation. The paper convincingly demonstrates LServe's advantages in its evaluated regime; the open question is whether these advantages persist, grow, or diminish in the higher-throughput, multi-GPU, combined-optimization settings that characterize production deployments.

## 6. Limitations and Trade-offs

### 6.1 The Difficulty Estimation Cost Remains Unaccounted For in the Headline Efficiency Numbers

**The assumption or constraint.** LServe's dynamic page selector (Section 3.5) requires per-page key statistics (`$k_{\max}$` and `$k_{\min}$` vectors) to be pre-computed during the prefilling stage. The paper acknowledges this as "context pooling overhead" (Section 5.3, final paragraph) but dismisses its cost as negligible: "a single pooling kernel executes under 1 ms, while the entire prefilling stage completes in approximately 17 seconds with 128K context length." While technically true for that one kernel, this accounting omits a broader and more consequential cost: **the hierarchical page selector itself must score every physical page in the context at the start of each reuse chunk**, an operation whose latency scales linearly with sequence length. As Figure 14 demonstrates, this selector overhead reaches ~0.50 ms per chunk at 256K context length for a single attention head—and the system must perform this across all dense heads at each activation.

**The consequence.** The headline decoding speedup figures (1.3–2.1× over vLLM in Figure 10) are measured at batch size 1 on a single GPU. In this regime, the page selector's overhead—while measurable (Figure 14)—is amortized by the reuse mechanism (reducing frequency by 4×) and partially hidden behind the attention computation itself. However, the paper presents no evidence that this overhead remains manageable at **higher batch sizes**, where the attention kernel's execution time per sequence shrinks (more parallelism) but the page selector must still run independently per sequence (scoring each sequence's separate KV cache). The paper notes in Section 2.2 that "according to QServe, the ratio of attention kernels in end-to-end runtime will increase as the batch size scale[s] up," but this claim applies to dense attention—in LServe, the page selector introduces a **new latency component with linear scaling in context length and linear scaling in batch size** that does not exist in dense systems. If the selector becomes the bottleneck at realistic serving batch sizes (8–64), the measured speedups at batch size 1 would overstate the practical benefit, potentially substantially.

**What evidence exists in the paper.** Figure 14 quantifies the selector overhead at batch size 1: 0.24 ms at 128K, 0.50 ms at 256K for the vanilla selector, reduced by ~4× with reuse. Table 1 uses batch size 32 for the page size ablation, but this is on the baseline QServe system without sparse attention—the selector overhead at batch size 32 is never measured. The paper's entire efficiency evaluation (Figures 10, 11, 14, 15, 16; Table 5) uses batch size 1. There is no batch-size scaling experiment for LServe's end-to-end throughput.

**Mitigation status.** The reusable page selector (Section 3.5.3, Figure 14, Table 6) partially addresses the overhead by reducing activation frequency, but this is a constant-factor reduction—it does not change the linear scaling in sequence length or batch size. The paper does not discuss batch-parallelizing the selector (e.g., processing multiple sequences' page selection in a single fused kernel), does not provide a batch-size scaling analysis, and does not propose more aggressive approximations (e.g., selecting pages once per layer rather than per head, or amortizing across layers) that might reduce the overhead further. The paper flags the overhead explicitly (Figure 14 is dedicated to measuring it), which is commendable transparency, but the lack of batch-size evaluation means the claimed speedups are **validated only for the least demanding serving condition** (single sequence, single GPU).

### 6.2 Single Benchmark, Single Model Family, Single GPU Architecture Limits Generalizability Claims

**The assumption or constraint.** All accuracy evaluations use Llama-family models (Llama-3-8B, Llama-2-7B, Minitron-4B, DeepSeek-R1-Distill-Llama-8B) on a narrow set of text-based benchmarks (LongBench, NIAH, RULER, AIME, MATH500). The authors state they "believe this model is representative of the capabilities of many contemporary LLMs" (Section 4.1), but this is an assertion, not an empirical finding. All efficiency measurements are conducted on a single GPU architecture family: NVIDIA A100 (Ampere) for the main results and a single L40S (Ada Lovelace) for cross-architecture validation (Figure 10, bottom-right panel).

**The consequence.** Several aspects of LServe's design could be model-architecture-specific or benchmark-specific in ways the paper does not characterize:

**Model architecture sensitivity.** The streaming head classification (Section 3.3) relies on DuoAttention's optimization-based identification method, which was developed and validated on Llama-family models. Different model architectures (Gemma, Mistral, Qwen, Phi, Gemma, non-transformer architectures) may exhibit different ratios of retrieval-to-streaming heads. If a model naturally has 80% retrieval heads (e.g., a model optimized for retrieval-heavy tasks), LServe's default 50% streaming head sparsity would either produce accuracy loss (if the classification is respected) or provide less speedup (if fewer heads can be safely converted). Conversely, models with 80% streaming heads would see larger speedups than reported. The paper provides no head-type distribution analysis across model families.

**The 4096-token budget as a universal constant.** The paper's central dynamic sparsity claim is that "only a constant number of KV pages is required to preserve long-context and reasoning capabilities, irrespective of context length" (abstract). However, Table 3 shows that this constant depends on task difficulty: LServe-4096 is 3.7 points below the dense baseline on RULER at 256K, and LServe-8192 is needed to close the gap. RULER was specifically designed to stress-test context utilization beyond simple needle-in-a-haystack retrieval. Real-world applications that require multi-hop reasoning, aggregation, or synthesis across long documents (e.g., legal document analysis, scientific literature review) may demand token budgets substantially larger than 4096—possibly scaling with the complexity of the reasoning task rather than remaining constant. The paper's evaluation on AIME and MATH500 (Table 4) does not report the context lengths of the reasoning traces, so it is impossible to assess whether the 4096-token budget is sufficient for o1-style 20K-token chain-of-thought traces (which the paper itself highlights as a primary motivation in Section 1).

**GPU architecture sensitivity.** The block-sparse attention kernel's efficiency depends on GPU-specific parameters: the streaming multiprocessor's thread block capacity, shared memory size, memory transaction granularity, and warp size. The A100's 108 streaming multiprocessors with 40 MB of L2 cache and 80 GB of HBM2e memory create a specific balance between compute throughput and memory bandwidth. The paper provides only a single cross-architecture measurement (Figure 10, bottom-right: L40S with 48 GB, Ada Lovelace, different SM count, different cache hierarchy), and even there, only decoding throughput is shown—not prefilling, not attention-layer micro-benchmarks. The L40S results are incomplete (multiple baselines show OOM, limiting the comparison) and do not establish that LServe's speedups generalize across GPU generations or vendors (AMD, Intel, Apple Silicon).

**Benchmark coverage gaps.** The evaluation focuses exclusively on text-based understanding and reasoning tasks. Multimodal LLMs (processing images, video, or audio alongside text) constitute a growing fraction of long-context workloads, and the paper cites them as motivation (Section 1: "multi-modal understanding"). However, visual tokens may exhibit different attention locality properties than text tokens (e.g., spatially distant image patches may have stronger long-range dependencies than distant words in a document). Whether LServe's sparsity patterns (particularly the streaming head assumption of extreme locality) transfer to multimodal attention is completely untested.

**Mitigation status.** The paper acknowledges none of these generalizability concerns. The "representative" claim about Llama-3-8B is not hedged or qualified. No experiments test a non-Llama model family (beyond Minitron-4B, which is a pruned/distilled Llama variant). No experiments test a non-NVIDIA GPU or a consumer-grade GPU with different memory hierarchy characteristics. No multimodal evaluation is conducted. The paper's scope is appropriate for a systems paper introducing a new technique, but the generalizability claims in the text exceed the evidence provided.

### 6.3 The Hardest Contextual Reasoning Problems Show Measurable Degradation

**The assumption or constraint.** LServe's dynamic page selector operates on the principle that a fixed token budget (default: 4096) can capture all historically relevant tokens for the current query, because "semantic continuity of natural language endows the attention operation with intrinsic locality" (Section 3.5.3). This is an **inductive bias** about language: that tokens relevant to answering the current query are spatially clustered in the context, enabling effective retrieval even when the vast majority of the context is pruned.

**The consequence.** This assumption breaks down on tasks that require **non-local information integration**—reasoning that depends on facts distributed across widely separated parts of the context. The paper's own results quantify this failure mode. On RULER at 256K sequence length (Table 3), LServe with the default 4096-token budget achieves 75.7% accuracy versus 79.4% for dense attention—a 3.7 percentage point gap. RULER was specifically designed to include "challenging tasks such as multi-hop tracing and aggregation to test behaviors beyond searching from context" (Section 4.2). These tasks require the model to find and combine multiple pieces of information that may be separated by tens of thousands of tokens—precisely the scenario where the spatial locality assumption is weakest.

The gap widens with sequence length: at 32K, LServe-4096 is within 0.5 points of dense (91.0 vs. 90.5); at 64K, within 1.2 points (85.6 vs. 86.8); at 128K, within 2.8 points (81.0 vs. 83.8); at 192K, within 3.5 points (76.1 vs. 79.6); at 256K, within 3.7 points (75.7 vs. 79.4). The **trend is monotonic**: degradation increases with context length, suggesting the fixed budget is progressively less adequate as the context grows and the relevant information becomes more sparsely distributed.

**What evidence exists in the paper.** Table 3 is the primary evidence, showing the degradation pattern. The paper partially mitigates this by testing a larger budget (LServe-8192), which recovers to 79.1% at 256K—within 0.3 points of dense. This demonstrates that the degradation is a **budget insufficiency** problem rather than a fundamental limitation of the sparsity mechanism. However, the paper does not characterize what budget would be needed for even harder tasks (RULER at 512K or 1M tokens, which the paper does not test despite using Minitron-4B models at lengths up to 512K in Figure 10) or for tasks that require attending to an even larger fraction of the context (e.g., summarizing a long document where every paragraph contributes essential information).

**Mitigation status.** The paper is transparent about this limitation through the RULER evaluation and the comparison of LServe-4096 vs. LServe-8192. The authors note that "LServe-8192 is only up to 6% slower than LServe-4096 when the sequence length exceeds 128K" (Table 3 notes), framing the larger budget as a practical option. However, this mitigation has limits: the token budget cannot grow arbitrarily without eroding the speedup that is LServe's primary contribution. If very hard tasks require 16K or 32K token budgets at 256K context, the dynamic sparsity advantage over dense attention shrinks proportionally. The paper provides no characterization of this accuracy-budget-speedup tradeoff curve, leaving practitioners without guidance on how to set the budget for their specific task difficulty and accuracy requirements.

### 6.4 The Streaming Head Ratio Is a Hyperparameter With No Characterized Accuracy-Throughput Tradeoff

**The assumption or constraint.** LServe converts a fixed 50% of attention heads to streaming heads by default (Section 3.3), determined by taking the median of the gating values $\alpha$ from DuoAttention's offline optimization. This is presented as a single operating point—all experiments use exactly this ratio, and the paper states that the target sparsity is determined by a "sparsity quantile" (Section 3.3) without justifying why 50% is the right choice.

**The consequence.** The 50% streaming head ratio is the **primary static sparsity knob** in LServe, directly controlling the tradeoff between computational savings and potential accuracy loss. Intuitively:
- **More streaming heads (e.g., 75%):** Larger speedup, but higher risk that some retrieval-critical heads are incorrectly classified as streaming, causing accuracy degradation on tasks requiring broad context access.
- **Fewer streaming heads (e.g., 25%):** More conservative accuracy preservation, but reduced speedup, especially at shorter-to-medium context lengths where static sparsity dominates (Figure 16).

The paper provides no evidence about where on this tradeoff curve the 50% operating point sits. It could be that 60% or 70% streaming heads would yield substantially more speedup with negligible additional accuracy loss—or that 50% is already near the accuracy cliff and even 55% would cause unacceptable degradation. Without this characterization, practitioners cannot adapt LServe to their specific accuracy requirements. A deployment where 1% accuracy loss is acceptable (e.g., speculative generation or candidate reranking) might benefit from more aggressive sparsity. A deployment where accuracy is paramount (e.g., medical or legal applications) might need more conservative settings, but the paper provides no lower bound on the sparsity ratio that guarantees accuracy preservation.

**What evidence exists in the paper.** None. The paper sweeps no sparsity ratio beyond the default 50%. All accuracy tables (Tables 2–4) and all efficiency figures (Figures 10, 11, 15, 16) use exactly this configuration. The paper does not report an ablation varying the streaming head percentage, does not provide the distribution of $\alpha$ values that would allow readers to estimate how many heads are near the boundary, and does not discuss the sensitivity of accuracy to this choice.

**Mitigation status.** Not addressed. The paper inherits the head classification method from DuoAttention but adapts it without characterizing the method's sensitivity to the threshold choice in LServe's specific serving context. The omission is consequential because the streaming head ratio interacts with the dynamic sparsity budget: heads that are converted to streaming no longer benefit from dynamic page selection (they attend only to sinks and local tokens), so the effective "context access" provided by the remaining dense heads must be sufficient to compensate. If too many heads are converted to streaming, the remaining dense heads—even with perfect dynamic page selection—may collectively lack the capacity to retrieve all needed information. The paper provides no analysis of this interaction.

### 6.5 Batch Size Scaling and Multi-GPU Serving Remain Completely Uncharacterized

**The assumption or constraint.** All of LServe's headline efficiency measurements (Figures 10, 11, 14, 15, 16; Table 5) use **batch size 1** on a **single GPU**—the simplest possible serving configuration. The paper's only batch-size-scaled experiment is Table 1, which measures page size impact on QServe (the dense baseline) at batch size 32, but does not measure LServe at any batch size above 1.

**The consequence.** This is a significant gap because production LLM serving systems are designed around two fundamental throughput mechanisms that interact with LServe's design in non-obvious ways:

**Batched decoding.** In production, the decoding stage processes multiple sequences concurrently in a single kernel invocation. Each sequence has its own KV cache and would require its own page selection. The page selector operates at the granularity of individual attention heads and individual sequences. At batch size 1, the selector runs for a modest number of dense heads per layer (e.g., 16 heads for Llama-3-8B with GQA, half of which are streaming → 8 dense heads per layer). At batch size 32, the selector would run for 32 sequences × 8 heads = 256 independent page selections per layer per reuse interval. The paper provides no evidence about whether the selector's latency scales linearly with batch size (suggesting a potential bottleneck) or whether the selections can be fused into a batched kernel (maintaining efficiency).

Additionally, batch-size scaling changes the compute-vs-memory balance of attention. At batch size 1, attention is strongly memory-bound (each query loads the entire KV cache). At larger batch sizes, the per-sequence memory traffic is partially amortized, and attention becomes more compute-bound. This shift could change the relative benefit of sparsity: reducing memory traffic (dynamic sparsity's primary benefit) might matter less when the bottleneck shifts toward compute.

**Multi-GPU tensor parallelism.** For models or contexts that exceed single-GPU memory, production systems split the model across multiple GPUs using tensor parallelism (each GPU holds a portion of the attention heads or FFN layers). LServe's head classification assigns different sparsity patterns to different heads. In a tensor-parallel setting, this would mean different GPUs see different amounts of computational work depending on their assigned heads. A GPU assigned mostly streaming heads would be underutilized while one assigned mostly dense heads with page selection would be the straggler—a load imbalance problem that does not exist in uniform dense attention. The paper does not discuss this.

**What evidence exists in the paper.** None. The paper's entire efficiency evaluation uses single-GPU, batch-size-1 configurations. The text includes a conceptual nod to batch-size scaling in Section 2.2 ("according to QServe, the ratio of attention kernels in end-to-end runtime will increase as the batch size scale[s] up") but this is presented as motivation for why attention optimization matters, not as an analysis of how LServe's specific mechanisms behave under batching.

**Mitigation status.** Not addressed. The paper does not acknowledge batch-size scaling or multi-GPU deployment as limitations. There are no experiments, no analytical models, and no discussion of how the page selector, the dual KV cache, or the two-level indexing hierarchy would extend to distributed settings. This is a significant omission for a systems paper targeting production deployment, especially given that the primary baselines (vLLM, QServe, TensorRT-LLM) are all designed explicitly for high-throughput, batched, multi-GPU serving and are evaluated as such in their respective papers.

### 6.6 The Reasoning Evaluation Is Too Thin to Support the Central Motivation

**The assumption or constraint.** The paper's introduction (Section 1) heavily emphasizes reasoning models as a primary use case: it opens with a discussion of OpenAI o1's chain-of-thought reasoning traces extending to 20K tokens and provides a motivating calculation showing that "when Llama-3-8B is run using TensorRT-LLM with 256K input tokens and 20K output tokens (comparable to o1's reasoning trace length), the prefilling time is 116 seconds, while decoding takes 540 seconds—almost 5× longer." This positions reasoning workloads—characterized by long generation traces with complex logical dependencies—as the **primary beneficiary** of LServe's decoding-stage acceleration.

**The consequence.** Given this motivation, a reader would expect a substantial evaluation of LServe on reasoning tasks with long chain-of-thought traces: measuring accuracy on multi-step reasoning benchmarks at varying trace lengths, analyzing whether the sparsity patterns interfere with logical deduction steps, and characterizing whether the token budget is sufficient for the long-range dependencies in reasoning traces. Instead, the paper provides exactly **two numbers** in Table 4: AIME2024 accuracy (43.3% for both dense and LServe) and MATH500 accuracy (84.2% dense vs. 85.4% LServe) on a single model (DeepSeek-R1-Distill-Llama-8B). This evaluation has several critical gaps:

**No context length information.** The paper does not report the sequence lengths of the reasoning traces generated by DeepSeek-R1 on AIME and MATH500. If these traces are relatively short (a few thousand tokens), the experiment does not test LServe in the regime it was motivated by (20K-token traces). The constant-budget claim would be untested at the sequence lengths that matter most.

**No trace quality analysis.** Accuracy is measured as final-answer correctness, but reasoning models are valued for their intermediate reasoning process as much as their final answers. The paper provides no analysis of whether LServe's sparsity affects reasoning trace length, coherence, logical structure, or the presence of intermediate verification steps. It is possible—and unexamined—that LServe achieves the same final accuracy by following different, potentially lower-quality reasoning paths.

**No comparison to other sparse methods on reasoning.** Table 4 compares LServe only to the dense baseline. It does not evaluate whether other sparsity approaches (DuoAttention, MInference, Quest, StreamingLLM) also preserve reasoning accuracy, which would contextualize LServe's result.

**No RULER-style multi-hop reasoning at long traces.** RULER includes multi-hop tracing tasks that specifically test a model's ability to chain information across a context. This is conceptually similar to the multi-step deduction in chain-of-thought reasoning. The paper evaluates RULER (Table 3) but only on Llama-3-8B with static input contexts, not on DeepSeek-R1 with self-generated reasoning traces. There is no experiment that tests whether LServe preserves multi-hop reasoning accuracy when the context is *generated by the model itself* (where the attention patterns may differ from human-written text).

**Mitigation status.** The authors present Table 4 as demonstrating "compatibility with the latest reasoning-centric models" (Section 1). While the results are positive (no accuracy degradation on the two benchmarks tested), the evaluation is so minimal that it functions more as an existence proof than a rigorous characterization. The paper does not acknowledge the thinness of the reasoning evaluation as a limitation. The central motivation (o1's 20K-token traces, the 540-second decoding time figure) sets expectations that the experiments do not fulfill. A practitioner considering LServe for reasoning workloads—arguably the most commercially significant long-context use case at the time of writing—would find insufficient evidence to assess whether the approach works for their specific reasoning tasks, trace lengths, and accuracy requirements.
