# REGMIX: Data Mixture as Regression for Language Model Pre-Training

**ArXiv:** [2407.01492](https://arxiv.org/abs/2407.01492)

## 🎯 Pitch

Tiny 1M-parameter models trained on just 1B tokens can predict the optimal data mixture for billion-parameter LLMs, matching or beating specialized methods at 10% of the compute. Common web crawls, not 'high-quality' sources like Wikipedia, actually correlate most strongly with downstream performance.

---

## 1. Executive Summary

This paper proposes **REGMIX**, a method that formulates data mixture selection for LLM pre-training as a regression task — training many small proxy models on diverse mixtures, fitting a regression model to predict unseen mixture performance, and applying the best predicted mixture to large-scale training. Validated on the Pile dataset using models up to 7B parameters and 100B tokens, REGMIX identifies the optimal mixture among 64 candidate 1B-parameter models by training just 512 models with 1M parameters on 1B tokens, achieving a Spearman rank correlation of 97.12% between predicted and actual rankings across a 1000× scale gap. The approach matches or exceeds the flagship DoReMi method using only 10% of the computational resources while outperforming human-selected mixtures by up to 6.8 points on HellaSwag, establishing that small-scale proxy model rankings reliably transfer to large-scale training only when the regression model captures complex, often counterintuitive domain interactions that human intuition fails to predict — interactions where web corpora like CommonCrawl, rather than perceived high-quality sources like Wikipedia, exhibit the strongest positive correlation with downstream performance.

## 2. Context and Motivation

### The Core Problem: We Don't Know How to Mix Pre-Training Data Optimally

Every large language model is trained on a mixture of data from different sources — academic papers, books, code repositories, web crawls, Wikipedia articles. The choice of *how much* of each source to include (the **data mixture**) has enormous consequences: as this paper demonstrates in Table 3, simply varying the data mixture among 64 different 1B-parameter models trained on the same 25B tokens from the Pile dataset produces a gap of **14.6 percentage points** on Lambada accuracy and an **average swing of 4.2 points** across 13 benchmarks. A model that gets 43.4% on HellaSwag with one mixture might achieve only 33.0% with another — a relative difference of over 30%.

Yet despite this sensitivity, the standard practice for determining data mixtures has been remarkably unsystematic. When GPT-3 was created, the authors manually upsampled Wikipedia because it "seemed high-quality." When the Pile dataset was released, its recommended mixture weights were set by human judgment. These manual approaches are not scalable — as the number of available data sources grows into the hundreds or thousands, no human can reason about $n$-way domain interactions — and, as this paper shows, they are frequently suboptimal.

The fundamental research question this paper tackles is: **How can we select the optimal data mixture in a scalable and efficient manner?** This is not a question about *filtering* data within a domain (sample-level selection) or choosing individual tokens (token-level pruning). It is about **group-level selection**: given $n$ domains, each with a large pool of tokens, what fraction of the training budget should be allocated to each?

### Why This Problem Matters

The paper identifies several reasons why data mixture optimization is critical, though it leaves some implications implicit. Reading between the lines, the stakes are:

**1. Performance at fixed compute budget.** The 14.6-point Lambada swing in Table 3 means that two organizations training identically-sized models on identical hardware with the same data *sources* could achieve dramatically different downstream performance simply because they mixed the sources differently. In a competitive landscape where single-digit percentage improvements can determine market viability, data mixture is a high-leverage decision — and currently, it is made largely by intuition.

**2. Accelerating pre-training.** As Section 5.3 and Figure 6 show, a better data mixture means reaching a given validation loss or downstream performance with fewer training tokens. The paper reports that REGMIX can achieve **50% pre-training acceleration** on benchmarks like HellaSwag and up to **75% on PiQA** when scaling to 7B models trained on 100B tokens (Section 5.6, Appendix J). In concrete terms: training for 50B tokens with a good mixture may match the performance of training for 100B tokens with a human-designed mixture. Given that training frontier models costs tens of millions of dollars, halving the required compute is economically transformative.

**3. Understanding what data actually matters.** A secondary but scientifically important motivation is empirical: the paper's analysis reveals surprising truths about which data sources drive downstream performance. Section 5.2 shows that validation loss on Pile-CC (CommonCrawl web data) has the *strongest* correlation with downstream task performance — stronger than Wikipedia, stronger than books, stronger than academic papers. This contradicts the common assumption that "high-quality" curated sources like Wikipedia are the best indicators of model capability. Understanding *why* web corpora are so predictive — perhaps because their diversity mirrors the diversity of downstream tasks — is a question this paper opens but doesn't fully resolve.

**4. Enabling automated data curation at scale.** As pre-training datasets grow from gigabytes to terabytes to petabytes, manual inspection becomes impossible. The Pile alone has 22 components (17 after removing copyrighted subsets); modern datasets like FineWeb or DCLM can have hundreds or thousands of domains. An automated, principled approach to mixing is not a luxury — it is a necessity for continuing to scale.

### Where Prior Approaches Fall Short

The paper categorizes prior work into three levels of granularity (Section 2: Related Work) and identifies specific shortcomings at each level:

**Token-level and sample-level methods don't address the mixture problem.** Methods like Perplexity-based filtering (Ankner et al., 2024) or Rho-1 (Lin et al., 2024) operate by scoring individual tokens or examples and discarding low-quality ones. While valuable, these approaches don't answer the question of how to *weight entire domains* relative to each other. A domain might contain many low-quality individual samples but still be worth including at a 5% weight because its high-quality subset provides unique knowledge. Token-level pruning cannot capture this domain-level tradeoff.

**Prior group-level methods are computationally expensive or unstable.** The paper focuses its critique on two categories of prior group-level methods:

*Online methods* (Albalak et al., 2023; Chen et al., 2023; Wang et al., 2020) dynamically adjust domain weights *during* the training of the final large model. These approaches require training a model for hundreds of thousands of steps while simultaneously running a domain-weight optimization algorithm. The paper argues (Section 1 and Appendix F) that online methods become intractable as pre-training datasets scale to trillions of tokens — training a proxy model for Llama-3-scale data would require processing up to 15T tokens for the proxy alone.

*Offline methods* that use proxy models — most notably **DoReMi** (Xie et al., 2023a) — address the intractability issue by determining weights ahead of time. DoReMi trains a single reference model on a uniform mixture, then trains a proxy model that dynamically upweights domains where the proxy's loss exceeds the reference model's loss. The final domain weights are the average weights from the proxy's training trajectory.

The paper identifies three specific failure modes of the DoReMi approach:

1. **Instability to proxy model scale.** As noted in Appendix F and supported by Xie et al.'s own results (their Figure 8), DoReMi produces wildly different domain weights depending on the size of the proxy model. A 280M-parameter proxy gives Pile-CC a weight of 0.67; a 1B-parameter proxy gives it a weight below 0.20. This means the method's recommendations don't reliably transfer across scales — precisely the property that a proxy model approach *should* guarantee.

2. **Serial training bottleneck.** DoReMi requires training a single proxy model for a very long time (e.g., 100B tokens), which cannot be parallelized. REGMIX instead trains many small models in parallel, converting a latency problem into a throughput problem that can leverage modern GPU clusters.

3. **Computational cost.** The paper estimates that REGMIX's proxy training (512 × 1M models at 1B tokens each) uses approximately **10% of the FLOPs required by DoReMi** (Table 4: 3.5 × 10¹⁸ vs. 3.7 × 10¹⁹ FLOPs). For reference, REGMIX uses less than 2% of the FLOPs required to train the final 1B model.

**Data scaling laws don't fully capture domain interactions.** Recent work (Ye et al., 2024; Ge et al., 2024) has attempted to fit parametric scaling functions that predict validation loss as a function of domain weights. The paper argues (Section 5.5, Figure 8) that these approaches are insufficient because they typically assume each domain's contribution is a simple log-log linear function of its weight. The 1M training logs in Figure 8 show that this assumption breaks down for most domains: only DM Mathematics displays a clean log-log relationship, while domains like Pile-CC, GitHub, and Stack Exchange show complex, non-monotonic patterns. The paper's key insight is that **domain interactions matter** — the contribution of adding 5% more GitHub depends on how much Wikipedia, ArXiv, and Pile-CC are already in the mixture. Scaling laws that treat each domain independently cannot capture these interactions.

### How This Paper Positions Itself

The paper positions REGMIX as a **scalable, parallelizable offline group-level method** that fundamentally differs from prior work in two architectural choices:

**1. Regression instead of dynamic optimization.** Rather than trying to *learn* optimal weights through a training process (like DoReMi), REGMIX *observes* the performance of many mixtures and *predicts* the performance of unseen ones. This is a conceptually elegant shift: it reframes the problem from online learning (which requires sequential steps and suffers from instability) to supervised learning (which is well-understood, parallelizable, and stable). The regression model acts as a surrogate for the expensive process of training and evaluating a model, enabling efficient exploration of the mixture space.

**2. Many ultra-small models instead of one medium model.** Where DoReMi trains one 280M-parameter model, REGMIX trains **512 models with 1M parameters each**. This trades depth (training tokens per model) for breadth (number of mixtures explored), and the paper empirically demonstrates (Figure 4, Section 4.2) that breadth matters more: given a fixed FLOP budget, increasing the number of proxy models consistently improves rank prediction accuracy, while increasing training tokens per proxy model saturates after approximately 0.25B tokens.

The paper explicitly grounds itself in the **rank invariance hypothesis** (Figure 2, left panel): the assumption that the *ordering* of data mixtures by their effectiveness is stable across model sizes and training token counts. This hypothesis is not proven a priori — the paper validates it empirically in Section 4.2 (Table 2), showing Spearman rank correlations of 97.12% between 1M-parameter models trained on 1B tokens and 1B-parameter models trained on 25B tokens — a 1000× scale gap. This validation is the critical bridge between cheap proxy experiments and expensive large-scale training.

The paper's positioning relative to prior work is both collaborative and competitive. It builds on the proxy model paradigm established by DoReMi and DOGE (Fan et al., 2023) but argues that the *method* of extracting mixture weights from proxy training is where prior work went wrong. REGMIX's regression approach is presented not as a minor tweak but as a fundamentally more scalable and stable alternative that matches or exceeds prior methods at a fraction of the computational cost.

## 3. Technical Approach

### 3.1 Reader Orientation

REGMIX is a system that automatically discovers the best way to mix different data sources (like Wikipedia, books, and web crawls) when training a large language model, without requiring a human to guess which sources are most important. It solves the data mixture selection problem by training many very small models on different random mixtures, learning a regression model that can predict how *any* mixture would perform, and then using that regression model to find the optimal mixture for training a model that is orders of magnitude larger.

### 3.2 Big-Picture Architecture (Diagram in Words)

The REGMIX pipeline has four sequential stages, each feeding into the next:

1. **Proxy Model Training** — Train many small-scale models (e.g., 512 models with 1M parameters) on different, randomly sampled data mixtures for a fixed number of tokens (e.g., 1B tokens each). Each model's training produces two outputs: the domain weights of its mixture (the features) and its performance on a target metric like validation loss on a specific domain (the label).

2. **Regression Model Fitting** — Take the `(mixture, performance)` pairs from Stage 1 and fit a supervised regression model (either linear regression with L2 regularization or LightGBM). This model learns a function `f(domain_weights) → predicted_performance` that can estimate how any data mixture would perform without actually training on it.

3. **Simulation and Prediction** — Generate a large number of candidate data mixtures (e.g., 1,000,000 randomly sampled combinations of domain weights), use the fitted regression model to predict the performance of each, and select the mixture predicted to perform best. The top 100 mixtures are typically averaged for robustness.

4. **Large-Scale Training** — Take the predicted optimal mixture from Stage 3 and use it to train the final large language model (e.g., 1B or 7B parameters) with orders of magnitude more compute than the proxy models.

The critical property that makes this pipeline work is the **rank invariance hypothesis**: the assumption that the relative ordering of data mixtures by their effectiveness is stable across model sizes and training token counts. This hypothesis is validated empirically (Section 4.2) rather than assumed, but it is what justifies using 1M-parameter proxy models trained on 1B tokens to make decisions about 1B-parameter models trained on 25B tokens — a 1000× scale gap.

### 3.3 Roadmap for the Deep Dive

I will explain the technical approach in the following order:

- **First**, the formal problem statement and the rank invariance hypothesis — what exactly is being optimized, what "optimal" means, and why the rank invariance assumption is both necessary and empirically testable.
- **Second**, the Dirichlet-sampling procedure for generating diverse data mixtures — this is the mechanism that ensures the regression model sees enough variety to generalize, and it involves non-obvious design choices about how to parameterize the sampling distribution.
- **Third**, the proxy model training setup — the specific architectures, hyperparameters, token budgets, and evaluation protocols used to generate the training data for the regression model.
- **Fourth**, the two regression models (linear ridge regression and LightGBM) — their mathematical forms, their training procedures, and the specific hyperparameter selection methods.
- **Fifth**, the simulation-and-selection procedure — how candidate mixtures are generated, how predictions are made, and how the top mixtures are aggregated into a final recommendation.
- **Sixth**, the large-scale training transfer — how the predicted mixture is applied to models that are 1000× larger in parameters and 25−100× larger in training tokens.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **method paper** whose core idea is that data mixture optimization can be reframed as a standard supervised regression problem, enabling the use of well-understood, stable, and parallelizable machine learning techniques to solve a problem previously approached through unstable online optimization.

#### The Formal Problem and the Rank Invariance Hypothesis

Let there be `n` domains, each containing a large pool of available tokens. A data mixture is a vector `x = (x₁, x₂, ..., xₙ)` where each `xᵢ ≥ 0` represents the fraction of training tokens drawn from domain `i`, satisfying the simplex constraint:

$$\sum_{i=1}^{n} x_i = 1, \quad x_i \geq 0 \ \forall i$$

where `xᵢ` is the weight assigned to domain `i` in the mixture.

**What it computes:** the relative proportion of the total training budget allocated to each domain. When training a model on `T` tokens, approximately `T × xᵢ` tokens come from domain `i`.

**Why this form:** this is the standard simplex representation for mixture proportions, ensuring weights are interpretable as fractions of a whole. The non-negativity constraint is natural (you cannot allocate negative tokens to a domain), and the sum-to-one constraint means weights represent a complete allocation. Alternative representations like unnormalized counts would require an additional parameter (total tokens) and would make the optimization space less structured.

Given a target metric `y` (e.g., validation loss on a specific domain, or downstream task accuracy), the data mixture optimization problem is to find `x*` that minimizes (or maximizes) `y`:

$$x^* = \arg\min_{x \in \Delta^{n-1}} y(x)$$

where `Δⁿ⁻¹` is the `(n−1)`-dimensional probability simplex, and `y(x)` is the unknown function mapping data mixtures to performance. The fundamental challenge is that evaluating `y(x)` requires training and evaluating a model, which is expensive — and evaluating it at the target scale (e.g., 1B parameters, 25B tokens) is prohibitively so.

The **rank invariance hypothesis** is the assumption that makes proxy-based optimization possible. Formally, for any two data mixtures `xᵃ` and `xᵇ`, and any two model sizes `M₁` and `M₂` (with `M₁ < M₂`) trained on token counts `T₁` and `T₂` (with `T₁ < T₂`):

$$\text{rank}(y_{M_1,T_1}(x^a), y_{M_1,T_1}(x^b)) \approx \text{rank}(y_{M_2,T_2}(x^a), y_{M_2,T_2}(x^b))$$

where `y_{M,T}(x)` is the performance metric for a model of size `M` trained on `T` tokens with mixture `x`, and `rank(a, b)` returns whether `a` is better than `b`.

**What it computes:** the statement that if mixture A outperforms mixture B on a small model with few tokens, it will also outperform mixture B on a large model with many tokens. The ranking is preserved even though absolute performance values differ.

**Why this form:** without this hypothesis, there is no justification for spending compute on small proxy models. The hypothesis does not require the *magnitudes* of performance differences to be preserved — only their ordering. This is a weaker assumption than full distributional invariance, but it is strong enough to make optimization tractable. The hypothesis is testable — Section 4.2 explicitly validates it with Spearman rank correlation — and, critically, it can fail (the paper acknowledges in Appendix B that it has only been validated up to 1B parameter models, not 7B or 70B).

#### Generating Diverse Data Mixtures via Dirichlet Sampling

The first computational step in REGMIX is generating the set of data mixtures on which proxy models will be trained. This is not a trivial step — the choice of how to sample mixtures determines whether the regression model sees enough variety to generalize to unseen combinations.

**The Dirichlet distribution.** The Dirichlet distribution is a probability distribution over the simplex. It is parameterized by a concentration vector `α = (α₁, α₂, ..., αₙ)` where each `αᵢ > 0`. A sample from `Dir(α)` is a vector `x` satisfying the simplex constraint, with the property that:

- Large `αᵢ` relative to other `αⱼ` means `xᵢ` tends to be large.
- The sum `α₀ = Σᵢ αᵢ` controls concentration: large `α₀` produces samples concentrated near the mean `α/α₀`, while small `α₀` produces samples near the vertices (sparse mixtures where one domain dominates).

**REGMIX's sampling strategy.** The paper constructs `α` by multiplying the natural token distribution of the available data by a scalar `λ`:

$$\alpha_i = \lambda \cdot t_i$$

where `tᵢ` is the fraction of total available tokens that come from domain `i` (i.e., `tᵢ = (tokens in domain i) / (total tokens across all domains)`), and `λ` is sampled from the range `[0.1, 5.0]`.

**What it computes:** this produces a Dirichlet concentration vector that is proportional to the token availability but scaled by a factor that varies across sampling runs. When `λ` is small (e.g., 0.1), the resulting `α` produces sparse mixtures where one or few domains dominate (because small `α₀` pushes samples toward simplex vertices). When `λ` is large (e.g., 5.0), the resulting `α` produces near-uniform mixtures (because large `α₀` concentrates samples near the mean).

**Why this form:** this design encodes three important constraints simultaneously:

1. **Extreme coverage.** By sweeping `λ` from 0.1 to 5.0, the sampling procedure generates mixtures ranging from nearly single-domain (sparse) to nearly uniform (dense), exposing the regression model to a wide range of behaviors. This is essential because the optimal mixture might be extreme (as indeed REGMIX found: the final mixture places 87% weight on Pile-CC and zero weight on many domains).

2. **Token feasibility.** By basing `α` on the natural token distribution `t`, the procedure ensures that mixtures are statistically consistent with data availability. A domain with only 0.1% of total tokens cannot receive 50% weight in a mixture that will be used for large-scale training, because there simply are not enough tokens. The Dirichlet centered at `t` means that, on average, the sampled mixture reflects what is physically possible to train on.

3. **Directed exploration without uniform random search.** A naive alternative would be to sample uniformly from the simplex (using a flat Dirichlet with `α = (1, 1, ..., 1)`). However, this would waste proxy model budget on mixtures that are infeasible at scale (e.g., 50% weight on a domain with 1% of tokens). The token-distribution-anchored Dirichlet focuses exploration on the region of the simplex that is actually realizable, while still covering extremes through the `λ` sweep.

**Number of mixtures.** In the main experiment, `N = 512` proxy models are trained, each on a different mixture sampled from this procedure. Section 4.2 (Figure 4) shows that increasing `N` consistently improves rank prediction accuracy, while increasing training tokens per model saturates — validating the design choice to prioritize breadth (many mixtures) over depth (many tokens per mixture).

#### Proxy Model Training

Each of the `N` sampled data mixtures is used to train one small-scale language model. The training is standard autoregressive language modeling — the model is trained to predict the next token in sequences drawn according to the mixture proportions — but the specific configurations matter because they determine what the regression model can learn.

**Model architecture.** The paper uses the architecture proposed by Zhang et al. (2024a) (TinyLlama), which is a standard decoder-only transformer, but scaled down:

- **1M parameter models** (the primary proxy scale): `nlayers = 2`, `nheads = 8`, `dembedding = 256`, `dmodel = 512`. The non-embedding parameter count is approximately 1M.
- **60M parameter models** (used for stability analysis): `nlayers = 10`, `nheads = 8`, `dembedding = 768`, `dmodel = 1536`.
- **1B parameter models** (the target scale): `nlayers = 22`, `nheads = 16`, `dembedding = 2048`, `dmodel = 5632`.
- **7B parameter models** (the largest scale tested): `nlayers = 32`, `nheads = 16`, `dembedding = 4096`, `dmodel = 12288`.

The vocabulary size is fixed at 50,432 across all model scales, using the GPTNeoX tokenizer (Black et al., 2022).

**Training hyperparameters.** For 1M and 60M models: 1,000 training iterations with a batch size of 1M tokens, for a total training budget of 1B tokens. Learning rate is `4 × 10⁻⁴` with a cosine learning rate scheduler. For 1B models: 25,000 iterations with the same 1M-token batch size, consuming 25B tokens — a Chinchilla-optimal allocation given the model size (Hoffmann et al., 2022). For 7B models: trained on 100B tokens.

**Target metric evaluation.** After training, each proxy model is evaluated on a **target domain** to produce the label for regression. In the main experiments, the target is the **validation loss on the Pile-CC domain** (CommonCrawl web data). This choice is deliberate and well-motivated: Section 5.2 demonstrates that Pile-CC validation loss has the strongest correlation with downstream task performance across 13 benchmarks, making it a reliable single-number proxy for overall model quality. The validation loss is computed by running the trained model on held-out Pile-CC text and measuring the per-token cross-entropy loss.

**Why this target metric:** directly optimizing for each downstream task would require a separate regression model per task and would be vulnerable to overfitting to specific benchmarks. Pile-CC loss serves as a **general-purpose capability signal** that correlates well with many tasks simultaneously, as demonstrated in Figure 5(a) where the correlation between Pile-CC loss and HellaSwag performance approaches 1.0. This is a pragmatic choice: optimize for one metric that captures most of what we care about, rather than trying to jointly optimize 13 metrics.

**Computational footprint.** The paper estimates that training 512 × 1M models on 1B tokens each consumes approximately **2% of the FLOPs** required to train a single 1B model on 25B tokens, and approximately **10% of the FLOPs** required by DoReMi's proxy training pipeline (Table 4: 3.5 × 10¹⁸ vs. 3.7 × 10¹⁹ FLOPs). This is the key efficiency claim: REGMIX's parallel training of many small models is fundamentally cheaper than serial training of one medium model.

#### Linear Regression Model

The first regression approach is **ridge regression** (linear regression with L2 regularization). This is the simpler of the two models but provides interpretability benefits that the paper exploits for domain interaction analysis.

The ridge regression model assumes a linear relationship between domain weights and the target metric:

$$y = \omega_0 + \omega_1 x_1 + \omega_2 x_2 + \ldots + \omega_n x_n + \epsilon$$

where `y` is the predicted target value (validation loss on Pile-CC), `ω₀` is the intercept term, `ωᵢ` for `i = 1, ..., n` are the coefficients associated with each domain weight `xᵢ`, and `ϵ` represents irreducible error.

**What it computes:** a weighted sum of domain proportions plus a constant offset. Each `ωᵢ` can be interpreted as the expected change in the target metric when the weight of domain `i` is increased by one unit, holding all other domain weights constant (though due to the simplex constraint, this interpretation requires care — increasing one domain's weight necessarily decreases others).

**Why this form:** linear regression makes the strong assumption that the relationship between mixture components and performance is additive and monotonic. The paper shows (Section 5.5, Figure 8) that this assumption is frequently violated — domains like Pile-CC exhibit complex, non-monotonic relationships with validation loss. However, the linear model serves two purposes: (1) as a baseline to quantify how much the non-linearity matters, and (2) as an interpretable tool for visualizing domain interactions via its coefficients (Section 5.4, Figure 7). The coefficient `ωᵢ` can be interpreted as the marginal benefit of increasing domain `i`'s weight, and visualizing these coefficients reveals which domains are "helpful" or "harmful" to other domains' losses.

**Training procedure.** The ridge regression is trained by minimizing the regularized sum of squared residuals:

$$\hat{\omega} = \arg\min_{\omega} \sum_{j=1}^{N} \left(y_j - \omega_0 - \sum_{i=1}^{n} \omega_i x_{j,i}\right)^2 + \alpha \sum_{i=1}^{n} \omega_i^2$$

where `N = 512` is the number of training examples (proxy model runs), `yⱼ` is the observed target metric for the `j`-th proxy model, `x_{j,i}` is the weight of domain `i` in the `j`-th data mixture, and `α` is the L2 regularization strength.

**What it computes:** the standard ridge regression objective, which penalizes large coefficient magnitudes to prevent overfitting. The first term is the ordinary least squares loss (sum of squared prediction errors), and the second term is the L2 penalty on the coefficient vector.

**Why this form:** L2 regularization is preferred over L1 (Lasso) because the paper's primary goal is prediction accuracy, not sparsity in the coefficient vector. Additionally, L2 regularization is differentiable and has a closed-form solution, making hyperparameter search (via cross-validation) computationally efficient. The constraint that `Σᵢ xⱼ,ᵢ = 1` for all mixtures `j` means the design matrix is rank-deficient, which makes regularization necessary — without it, the ordinary least squares solution would be numerically unstable due to perfect collinearity among the features.

**Hyperparameter selection.** The paper uses 5-fold cross-validation to select the optimal L2 regularization strength `α` from the set `{1e-3, 1e-2, 1e-1, 1e0, 1e1, 1e2, 1e3}`. For each candidate `α`, the 512 training examples are split into 5 folds; the model is trained on 4 folds and evaluated on the held-out fold; the `α` that minimizes average held-out mean squared error is selected.

**Performance.** Table 2 shows that linear regression achieves a Spearman rank correlation of 90.08 on held-out 1M-parameter models, 89.26 on 60M-parameter models, and 88.01 on 1B-parameter models. These are respectable numbers but substantially below LightGBM's performance, confirming that the linearity assumption is a significant limiting factor.

**Interpretability use case.** Despite lower predictive accuracy, the linear model's coefficients are directly interpretable and are visualized in Figure 7 to reveal domain interaction patterns. A large negative `ωᵢ` (when the target is validation loss, which we want to minimize) means that increasing domain `i`'s weight strongly reduces the target domain's loss — a desirable property. The paper uses this to show that PhilPapers has a surprising negative coefficient for nearly all target domains, suggesting it is generally helpful despite its small size and apparent niche focus.

#### LightGBM Regression Model

The second and primary regression approach is **LightGBM** (Ke et al., 2017), a gradient-boosted decision tree ensemble. This model captures non-linear relationships and interactions between domains that the linear model misses.

**Gradient boosting overview.** LightGBM builds an ensemble of `K` decision trees sequentially:

$$f_K(x) = \sum_{k=1}^{K} \eta \cdot h_k(x)$$

where `f_K(x)` is the ensemble prediction after `K` trees, `η` is the learning rate (shrinkage), and `h_k(x)` is the prediction of the `k`-th decision tree trained to fit the residual errors from the previous `k−1` trees.

**What it computes:** each tree partitions the input space (the simplex of data mixtures) into rectangular regions and assigns a constant prediction to each region. The ensemble sums these piecewise-constant functions, producing a prediction that can approximate arbitrary non-linear functions. The learning rate `η` controls how much each tree contributes, with smaller values requiring more trees but often producing better generalization.

**Why this form:** decision trees naturally capture **interaction effects** — the relationship between domain `i`'s weight and the target can depend on domain `j`'s weight. For example, adding more GitHub data might be beneficial when Pile-CC weight is low but harmful when Pile-CC weight is high (because GitHub and Pile-CC cover overlapping linguistic patterns). Linear models cannot represent such conditional dependencies; tree-based models can, because each split in a tree conditions on previous splits. This is precisely the kind of complex domain interaction that Section 5.5 argues makes scaling laws insufficient.

**Why LightGBM specifically (over XGBoost or random forests).** The paper does not explicitly compare tree-based methods, but LightGBM has two well-known advantages that are relevant here: (1) it uses **leaf-wise tree growth** rather than level-wise, which can produce more complex trees with fewer nodes, and (2) it uses **Gradient-based One-Side Sampling (GOSS)** to focus training on high-gradient examples, improving efficiency. In the REGMIX context, where `N = 512` training examples and `n = 17` features, computational efficiency is not a bottleneck, but leaf-wise growth provides better function approximation for the same number of trees.

**Hyperparameters.** The paper manually sets:

- Number of iterations (trees): `K = 1000`
- Learning rate: `η = 0.01`
- All other hyperparameters at their default values (for LightGBM's regression mode)

**What these choices mean:** 1000 trees with learning rate 0.01 means the model can fit complex functions but with strong shrinkage that prevents memorization of the training set. Default LightGBM parameters include a maximum of 31 leaves per tree and a minimum of 20 data points per leaf, which together constrain model complexity.

**Why these values:** the paper does not provide a detailed ablation of LightGBM hyperparameters. The learning rate of 0.01 is a standard conservative choice that works well with 1000 trees — the product `K × η = 10` means the final prediction can shift by up to 10 units (in loss space) from the initial constant prediction, which is sufficient given that validation losses are on the order of 3–6. The choice to fix these rather than tune them suggests the method is not highly sensitive to these parameters, though this sensitivity is not explicitly studied.

**Performance.** Table 2 shows that LightGBM dramatically outperforms linear regression:

- On held-out 1M models: Spearman `ρ = 98.45` vs. 90.08 for linear
- On held-out 60M models: `ρ = 98.64` vs. 89.26
- On held-out 1B models: `ρ = 97.12` vs. 88.01

The near-perfect correlation on 1M held-out mixtures (98.45) indicates that LightGBM accurately captures the non-linear performance surface within the proxy model regime. The maintained high correlation on 1B models (97.12) validates the rank invariance hypothesis — the learned performance surface from 1M models transfers to 1000× larger models.

**Why LightGBM outperforms linear regression.** The performance gap (roughly 8–10 correlation points) is the quantitative evidence for the paper's central methodological claim: that domain interactions are complex and non-linear, and that the regression model must be capable of representing these interactions. A linear model sees each domain's contribution as a fixed scalar that is independent of context; LightGBM sees that the benefit of adding more ArXiv depends on how much Pile-CC is already in the mixture. Section 5.5 (Figure 8) visually confirms this: the relationship between domain weight and validation loss is often non-monotonic and depends on the weights of other domains.

---

#### Simulation and Prediction: Finding the Optimal Mixture

Once the regression model `f(x)` is trained (either linear or LightGBM), the next step is to find the data mixture `x*` that minimizes (or maximizes) the predicted target metric. This is done through brute-force simulation:

**Generate candidate mixtures.** The paper generates a large set of candidate data mixtures, typically `M = 1,000,000` random samples from the simplex. The sampling distribution for this simulation step is not explicitly specified, but the natural interpretation is that it can be a flat Dirichlet (all `αᵢ = 1`), because the simulation is computationally free — there is no cost to exploring mixtures that might be infeasible at scale, as long as the infeasibility is handled before deployment.

**Predict performance for each candidate.** For each candidate mixture `xⱼ`, the trained regression model produces a predicted target value `ŷⱼ = f(xⱼ)`. The paper notes that "running prediction for 1,000,000 data mixtures takes less than 10 CPU seconds," which is negligible compared to the proxy training cost.

**Select top mixtures.** The 100 mixtures with the best (lowest, for validation loss) predicted target values are selected. The final recommended mixture is the **average of these top 100 mixtures**:

$$x^* = \frac{1}{100} \sum_{j=1}^{100} x_{(j)}$$

where `x_{(ⱼ)}` is the `j`-th best mixture according to the regression model's predictions.

**Why average the top 100 rather than take the single best.** This is a robustness measure. The regression model's predictions are approximate, and the single predicted-best mixture may exploit idiosyncrasies in the model's fit. Averaging the top 100 reduces variance and produces a mixture that is likely to be genuinely good rather than an artifact of regression noise. This is analogous to ensemble methods in machine learning, where averaging multiple high-scoring hypotheses produces more reliable results than selecting the single best.

**Why 100 specifically.** The paper does not justify the number 100 with an ablation. It is a reasonable heuristic: too few (e.g., top 5) would retain too much variance from the regression model's approximation error; too many (e.g., top 10,000) would dilute the signal by including mediocre mixtures. One hundred is large enough to average out noise but small enough to remain within the high-performing region of the mixture space.

**Feasibility check.** The averaged mixture must respect token availability constraints. If a domain's weight in `x*` exceeds what its available token count can support at the target training scale, the weight would need to be capped and renormalized. The paper does not explicitly describe this step, but it is implied by the Dirichlet sampling procedure in Step 1: by anchoring the sampling distribution to the token distribution, the regression model is trained primarily on feasible mixtures, and its predictions are calibrated to the feasible region of the simplex. Candidate mixtures during simulation that fall outside this region could produce unreliable predictions.

---

#### Large-Scale Model Training with the Predicted Mixture

The final step is the simplest: take the predicted optimal mixture `x*` and use it to train the target large language model. No further optimization or adaptation is performed — the mixture is used exactly as predicted.

**Training scale.** The paper validates at several scales:

- **1B parameters, 25B tokens** — the primary validation, comparing REGMIX against 63 other mixtures (Table 3, Table 4). The REGMIX mixture achieves the best average downstream performance (47.3 vs. 45.1 for human selection).
- **7B parameters, 100B tokens** — a larger-scale validation (Section 5.6, Appendix J, Table 10, Figure 1). REGMIX outperforms human selection by 2.0 points on average across 13 benchmarks, and achieves 50% pre-training acceleration on HellaSwag (matching human-100B performance at 50B tokens with REGMIX mixture).
- **Out-of-distribution setting** (Section 5.3, Figure 6 right) — Pile-CC is excluded from the training corpus, but the regression model is still trained to minimize Pile-CC validation loss. REGMIX still outperforms baselines, demonstrating that the target domain need not be present in the training data for the method to work.

**The REGMIX mixture.** Table 7 reveals the weights derived by REGMIX for the 1B experiment:

- Pile-CC: **0.87** (dominant)
- Ubuntu IRC: 0.064
- PubMed Abstracts: 0.024
- Wikipedia (en): 0.016
- HackerNews: 0.012
- PubMed Central: 0.003
- Four domains at 0.002 (Gutenberg, Enron Emails, USPTO Backgrounds)
- Three domains at 0.001 (ArXiv, FreeLaw, NIH ExPorter)
- Six domains at 0.0 (DM Mathematics, GitHub, PhilPapers, Stack Exchange, EuroParl, and one more)

This is a **sparse mixture** heavily dominated by web data, with small amounts of niche internet text (Ubuntu IRC, HackerNews) and academic abstracts. It bears almost no resemblance to the human-designed Pile mixture (which spreads weight broadly across domains like ArXiv at 13.4%, PubMed Central at 13.6%, Wikipedia at 11.7%, Stack Exchange at 11.8%).

**Why this mixture works.** The paper does not deeply analyze *why* this specific mixture is optimal, but the interpretation is clear from the broader results: web data (Pile-CC) provides the broadest coverage of linguistic patterns and world knowledge, and small amounts of specialized data (Ubuntu IRC for technical conversation, PubMed Abstracts for scientific terminology, HackerNews for tech discourse) provide targeted supplements. The zero-weight assignment to seemingly valuable domains like GitHub and Stack Exchange is surprising but empirically validated — in the context of a mixture that is already 87% web data, these domains apparently provide redundant or even harmful signal.

**The Pile-CC-only baseline.** One of the most striking results in Table 4 is that simply training on **100% Pile-CC** (with no other domains) outperforms human selection, DoReMi, PPL, and ODM on average performance (46.8). REGMIX marginally improves on this (47.3) by adding small amounts of other domains. This suggests that the primary value of domain mixing, at least on the Pile, is in recognizing that web data should dominate — a conclusion that contradicts the human intuition behind the original Pile mixture, which allocated only 14.2% weight to Pile-CC.

---

#### Extension to 100 Domains

Section 5.6 describes preliminary experiments extending REGMIX to 100 finer-grained domains derived from base URLs in the FineWeb dataset (Penedo et al., 2024a). This tests whether the method scales to a larger number of domains with more granular distinctions.

**Domain definition.** Domains are defined by base URLs from FineWeb, chosen based on token availability. Examples include `articles.latimes.com`, `blogs.wsj.com`, `en.wikipedia.org`, `everything2.com`, and `techcrunch.com`. This is a natural way to partition web data: the CommonCrawl corpus contains pages from millions of domains, and aggregating by base URL groups content from the same publisher or website.

**Proxy model scale.** 1,000 small-scale models (1M parameters) are trained across different data mixtures, and the regression model is fitted on these training runs. The number of proxy models is roughly doubled from the main experiment (1,000 vs. 512) to account for the larger feature space (100 domains vs. 17).

**Results.** Table 5 shows that LightGBM achieves `ρ = 99.53` on held-out 1M models and `ρ = 98.80` on 60M models. These correlations are actually *higher* than in the 17-domain case, which is somewhat counterintuitive — one might expect performance to degrade with more domains. The paper does not analyze this, but a plausible explanation is that with 100 URL-based domains, the domains are more homogeneous (all are web text) than the 17 Pile domains (which span web, academic papers, code, books, etc.), making the regression surface smoother and easier to fit.

**Implications.** The 100-domain result demonstrates that REGMIX is not limited to a small number of human-defined categories. As pre-training datasets become more granularly organized (e.g., by URL, by topic cluster, by quality tier), REGMIX can scale to hundreds or potentially thousands of domains. The primary constraint is the number of proxy models needed — the paper's finding that "increasing proxy model count outweighs increasing token count" (Figure 4) suggests that training many small models on many diverse mixtures is the scalable path forward.

---

#### Design Choice Summary

Several key design decisions distinguish REGMIX from prior work and are worth making explicit:

**Regression over online optimization.** The fundamental architectural choice is to treat data mixture selection as a **supervised learning problem** (predict performance from mixture weights) rather than an **online learning problem** (dynamically adjust weights during training). This enables parallel proxy training, stability analysis via cross-validation, and interpretability via coefficient visualization. The cost is the assumption that the relationship between mixtures and performance is learnable from a limited sample — an assumption validated by the near-perfect Spearman correlations but potentially fragile in new domains or at extreme scales.

**Pile-CC validation loss as the optimization target.** Rather than optimizing directly for downstream task performance (which would require a separate regression per task), REGMIX optimizes for validation loss on CommonCrawl data. This is a **proxy metric** justified by the empirical correlation in Figure 5(a), but it is not guaranteed to transfer to all tasks. Tasks that rely on knowledge absent from web data (e.g., highly specialized scientific reasoning, non-English languages, code) might not be well-served by a Pile-CC-loss-optimized mixture. The out-of-distribution experiment (Section 5.3, Figure 6 right) partially addresses this by showing that REGMIX works even when the target domain is excluded from training, but the general question of target metric selection remains open.

**Ultra-small proxy models (1M parameters).** The most radical design choice is the use of models with only 1M non-embedding parameters — smaller than most production classification models. The paper argues (Section 4.2, Figure 4) that this is not just computationally convenient but actually optimal: given a fixed FLOP budget, training many 1M models explores more of the mixture space and yields better predictions than training fewer larger models. This finding only holds, however, if the rank invariance hypothesis is true at the 1M-to-1B gap — a hypothesis validated in this paper for the Pile dataset but not guaranteed to generalize.

**Averaging top-100 mixtures for robustness.** The final mixture is not the single regression-predicted optimum but an average of the top 100. This is an ensemble strategy that reduces variance at the cost of a small bias toward less extreme mixtures. It implicitly regularizes the mixture toward the central tendency of the high-performing region, which is sensible given that the regression model's predictions are approximate.

## 4. Key Insights and Innovations

### Innovation 1: Reframing Data Mixture Optimization as Regression Rather Than Online Learning

The paper's most fundamental conceptual contribution is not a new algorithm but a **reframing of the problem class**: data mixture optimization is treated as a supervised regression task rather than an online learning or dynamic optimization problem. This shift is subtle but consequential across scalability, stability, and interpretability axes.

**Prior paradigm: Online adaptive optimization.** The dominant approach before REGMIX — exemplified by DoReMi (Xie et al., 2023a) and Online Data Mixing (Albalak et al., 2023) — treated mixture optimization as a process that unfolds *during* training. DoReMi trains a proxy model that dynamically adjusts domain weights based on the gap between its own loss and a reference model's loss, producing a weight trajectory that must be averaged post-hoc to extract final recommendations. This is fundamentally a **control problem**: the optimization algorithm interacts with the training process in a feedback loop, and the quality of the final weights depends on the stability of that loop.

This prior paradigm has three structural weaknesses that become apparent at scale: (1) it is **inherently serial** — the optimization must proceed step-by-step alongside training, which cannot be parallelized; (2) it is **unstable to proxy model scale** — DoReMi's weights swing dramatically from 0.67 Pile-CC weight with a 280M proxy to below 0.20 with a 1B proxy (Appendix F), meaning the optimization process itself depends on the scale at which it is run, undermining confidence in transfer; and (3) it provides **no interpretability** — the final weights are a black-box artifact of a training trajectory with no decomposition into domain contributions or interactions.

**REGMIX's reframing: Supervised learning on outcomes.** REGMIX treats the problem as standard regression: collect `(mixture, performance)` pairs from completed training runs, fit a model `f(domain_weights) → predicted_performance`, and optimize over the fitted model's predictions. This is fundamentally a **prediction problem**: the regression model is a surrogate for the expensive process of training and evaluating, and optimization happens over the surrogate rather than during training.

This reframing matters for three reasons beyond the obvious parallelizability benefit. First, it makes the method **verifiable**: the regression model's accuracy can be measured on held-out mixtures (Table 2, Spearman ρ of 97.12% on 1B models) *before* committing to large-scale training, whereas online methods produce final weights whose quality is only known after training the large model. Second, it makes the method **composable with standard ML practice**: cross-validation for hyperparameter selection, regularization for stability, and model selection between linear and tree-based regressors are all standard supervised learning tools that transfer directly. Third, it **decouples exploration from exploitation**: the proxy models can be trained in any order, with any allocation of compute, because they are independent samples from the mixture space — there is no sequential dependency that constrains scheduling.

**Evidence for significance.** The stability analysis in Appendix F (Figure 14) demonstrates the practical advantage of this reframing: when REGMIX uses 1M-parameter and 60M-parameter proxy models, the predicted mixture distributions are "remarkably similar," whereas DoReMi's weights vary drastically with proxy scale. This stability is a direct consequence of the regression framing — the supervised learning objective is agnostic to how the training examples were produced, as long as they cover the relevant region of mixture space.

**Limits of the reframing.** The regression approach assumes the relationship between mixtures and performance is learnable from a modest number of samples (512 in the main experiment). If the performance surface has high-frequency variation that requires dense sampling to capture, the regression model would miss it and the selected mixture could be suboptimal. The paper's finding that LightGBM achieves near-perfect correlation on held-out data suggests this is not a problem for 17-domain mixtures on the Pile, but the assumption may break down with hundreds of highly heterogeneous domains or with target metrics that have noisier relationships to mixture weights.

This is a **fundamental shift**, not a refinement of online methods — it changes the problem class from sequential decision-making under uncertainty to supervised learning on a static dataset, with all the analytical and practical advantages that entails.

---

### Innovation 2: Empirical Demonstration That Web Corpora, Not Curated Sources, Drive Downstream Performance

The paper's most empirically striking finding challenges a widespread assumption in the LLM pre-training community: that "high-quality" curated data sources like Wikipedia are the best indicators of model capability. Section 5.2 (Figure 5a) shows the opposite — validation loss on **Pile-CC** (CommonCrawl web data) has the strongest correlation with downstream task performance across 13 benchmarks, with the correlation between Pile-CC loss and HellaSwag performance approaching 1.0, while Wikipedia validation loss shows substantially weaker correlations with most tasks.

**Why this is surprising.** The standard practice since GPT-3 has been to treat Wikipedia as a gold-standard data source — it is written by humans, fact-checked, well-structured, and covers a broad range of topics. Many papers report WikiText perplexity as a primary quality metric. The implicit assumption is that a model that does well on Wikipedia-like text should do well on downstream tasks, because both require general linguistic competence. The Pile's human-designed mixture (Gao et al., 2021) allocated 11.7% weight to Wikipedia but only 14.2% to Pile-CC, reflecting this assumed quality hierarchy.

REGMIX's correlation analysis inverts this intuition. The finding is not just that Pile-CC is *useful* — it is that Pile-CC is the *most predictive single domain* of overall model quality. The paper hypothesizes (Section 5.2) that this is because CommonCrawl's diversity — spanning news articles, forums, technical documentation, product reviews, creative writing, and every other genre found on the open web — mirrors the diversity of downstream benchmarks. A model that achieves low perplexity on this heterogeneous mixture has effectively learned a broad distribution of language use, which transfers to most tasks. Wikipedia, by contrast, is a single genre (encyclopedic writing) and success on it may reflect genre-specific optimization rather than general capability.

**Evidence beyond correlation coefficients.** Two additional results strengthen this finding. First, Figure 5(b) shows that when Pile-CC is decomposed into 100 URL-level domains (e.g., `www.ign.com`, `www.latimes.com`, `patents.google.com`), more than 85% of these sub-domains independently show the same strong correlation pattern with downstream tasks. This rules out the possibility that Pile-CC's predictiveness is an artifact of some specific subset — the diversity itself appears to be the mechanism. Second, Table 4 shows that **training on 100% Pile-CC** (with no other domains) outperforms the human-designed Pile mixture, DoReMi, and perplexity-based filtering on average downstream performance (46.8), very close to REGMIX's optimized mixture (47.3). The best single thing you can do, according to this evidence, is train on web data — and the optimal mixture is essentially web data plus small targeted supplements.

**Comparison to prior assumptions.** This finding directly contradicts the data curation philosophy behind models like Gopher (Rae et al., 2021), which upsamples books and Wikipedia based on quality heuristics, and the Pile itself. It aligns with more recent results from DataComp-LM (Li et al., 2024) and FineWeb (Penedo et al., 2024b), which also find that web-scale data, properly filtered, produces strong models — but REGMIX provides the cleanest controlled comparison by holding model architecture, training budget, and evaluation protocol constant and varying only the mixture.

**Boundary conditions.** The paper explicitly limits this finding in two ways (Appendix B). First, performance on knowledge-intensive benchmarks like MMLU and GSM8K is "nearly random" for 1B-parameter models and cannot be evaluated — it is possible that more curated sources become important for tasks requiring specialized knowledge that web data lacks. Second, the Pile-CC correlation finding is specific to the Pile's composition; if web data were excluded entirely, a different domain would likely emerge as most predictive. The out-of-distribution experiment in Section 5.3 (Figure 6 right), where Pile-CC is removed from training, shows that REGMIX still finds effective mixtures, but does not identify which remaining domain becomes the best proxy.

This is an **empirical discovery** — it shifts the default assumption about what data matters from "curated sources are best" to "diverse web data is the strongest single signal of model quality" — but its generality across datasets and model scales beyond those tested remains an open question.

---

### Innovation 3: Quantifying That Domain Interactions Are Counterintuitive and Beyond Human Reasoning

The paper provides the most systematic empirical evidence to date that **domain interactions in pre-training mixtures are non-obvious, often contradicting human intuition, and require automated methods to optimize**. This is not a methodological innovation but a **diagnostic demonstration** that justifies the entire research direction.

**The evidence.** Section 5.4 (Figure 7) visualizes the coefficients from the linear regression model, showing how each training domain's weight correlates with validation loss on each target domain. The PhilPapers domain — a tiny collection of philosophy papers comprising 0.3% of the Pile — shows *negative* coefficients for nearly all target domains, meaning that increasing its weight reduces validation loss across the board. This is completely non-obvious: a human would likely dismiss PhilPapers as too small and too niche to matter, or would assume its academic-philosophy content would only help on related academic domains. The regression reveals it as a general-purpose beneficial domain, possibly because its dense, argumentative prose provides a unique training signal not duplicated elsewhere.

More broadly, Figure 7 reveals that domain interactions form a complex, asymmetric matrix that defies simple heuristics. A domain that helps reduce loss on PubMed Central might increase loss on GitHub. The relationship between a domain's weight and validation loss on *itself* is not always monotonic or dominant — adding more of a domain does not always reduce its own validation loss the most, because mixing effects from other domains can provide complementary signals that improve within-domain performance.

**Why this matters beyond the specific finding.** The field's default approach to data mixture has been human judgment informed by intuition about data quality, topic coverage, and avoiding over-representation of low-quality sources. This paper's interaction analysis demonstrates that such intuition is systematically unreliable — the benefits of including a domain depend on what else is in the mixture, and these conditional dependencies are too numerous and too subtle for any human to track. This is a **complexity argument for automation**: the space of possible mixtures is high-dimensional (17 dimensions in this case) with complex, non-separable interactions, making manual optimization essentially hopeless and justifying the cost of automated methods like REGMIX.

The scaling laws critique in Section 5.5 (Figure 8) reinforces this. If domain contributions were independent — if the effect of adding 5% more GitHub were the same regardless of the rest of the mixture — then scaling laws that model each domain separately would suffice. Figure 8 shows that this independence assumption fails for most domains: the scatter plots of validation loss versus domain weight show wide vertical spreads at each weight value, indicating that other domains' weights strongly modulate the effect. This is direct visual evidence that domain interactions are first-order effects, not second-order corrections.

**The REGMIX mixture as a case study in counterintuition.** Table 7 shows that the REGMIX-optimized mixture assigns zero weight to domains that humans considered valuable: DM Mathematics (viewed as useful for reasoning), GitHub (viewed as useful for code and logical structure), Stack Exchange (viewed as high-quality Q&A text), and PhilPapers itself (despite its beneficial coefficient in the linear model — likely because its benefit is outweighed by other domains in the non-linear LightGBM model). Meanwhile, Ubuntu IRC — a collection of technical support chat logs that a human would likely consider noisy and low-quality — receives 6.4% weight, the second-highest after Pile-CC. No human would design this mixture, yet it outperforms all human-designed baselines.

**Connection to broader AI alignment concerns.** This finding has implications beyond efficiency: it suggests that human intuitions about what data is "good" for training are shaped by our own preferences (we *like* Wikipedia) and quality judgments (we *dislike* chat logs) that do not necessarily correspond to what produces capable models. If automated methods like REGMIX consistently recommend mixtures that humans would not choose — and if those mixtures produce better models — it raises questions about what other aspects of model training humans are systematically misjudging.

This is a **diagnostic innovation** — it does not propose a new method but provides the empirical evidence that automated methods are necessary by demonstrating that the alternative (human judgment) fails in measurable, systematic ways.

---

### Innovation 4: Establishing That Ultra-Small Proxy Models (1M Parameters) Are Sufficient for Mixture Optimization

The paper makes a **methodological claim about scale** that challenges assumptions implicit in prior work: that proxy models for data mixture optimization need to be within an order of magnitude of the target model in size. REGMIX uses 1M-parameter proxy models to optimize mixtures for 1B and 7B parameter targets — a 1000× to 7000× scale gap — and demonstrates that this works.

**What prior work assumed.** DoReMi (Xie et al., 2023a) used proxy models of 280M and 1B parameters, comparable in scale to their target models. The instability they observed between these two scales (Appendix F) suggests they believed similar-scale proxies were necessary for reliable transfer — and the fact that the weights *still* changed dramatically between 280M and 1B indicates the approach was not robust even then. Online methods (Albalak et al., 2023) run the optimization during the training of the target model itself, making the proxy and target identical by definition.

The implicit prior assumption was that domain weights are a function of model capacity — that what a 1M model "needs" from data is fundamentally different from what a 1B model needs, because larger models can extract more signal from noisy data or benefit differently from specialized domains. If this assumption were true, optimizing mixtures at 1M scale would produce recommendations that don't transfer.

**REGMIX's counter-demonstration.** The paper validates the 1M-to-1B transfer empirically in Table 2 and Appendix I (Figure 15). The Spearman rank correlation of 97.12% between predicted and actual rankings of 1B-parameter models (trained on 25B tokens) using a regression model fitted only on 1M-parameter models (trained on 1B tokens) is the key number. This means that the *relative ordering* of mixtures — mixture A beats mixture B — is nearly perfectly preserved across a 1000× scale gap in parameters and a 25× gap in tokens.

Furthermore, Appendix K (Table 11) shows that using 128 × 1B proxy models produces a mixture that achieves 56.4 average downstream performance on 7B targets, while 512 × 1M proxy models produces 56.5 — statistically indistinguishable. The 1B proxies require far more compute per model, meaning the 1M approach is dramatically more efficient for the same result.

**Why this is significant beyond computational savings.** If 1M-parameter models are sufficient proxies, it means that the **data mixture signal is largely scale-invariant** — the properties that make a mixture good for a small model are the same properties that make it good for a large model, at least up to the 7B scale tested. This has implications for how we think about pre-training data: it suggests that the optimal mixture is determined more by the *statistical structure of the data itself* (which domains cover which linguistic patterns, which domains provide complementary signals) than by the *model's capacity to absorb data*, at least within the range tested.

**Boundary conditions and open questions.** The paper is appropriately cautious about this claim. The rank invariance hypothesis has only been validated up to 1B parameters for the main correlation analysis and up to 7B parameters for the end-to-end mixture optimization (Table 10, Appendix J). Whether it holds at 70B or 700B parameters — where phenomena like "data quality thresholds" or "emergence" might change the relationship between mixture and performance — is explicitly noted as unknown (Appendix B). Additionally, the finding that "more proxy models outperforms more tokens per proxy" (Figure 4) may saturate at very large numbers of domains, where each proxy model explores an increasingly small fraction of the mixture space.

This is a **methodological innovation with theoretical implications** — it provides the strongest evidence to date for scale-invariance of data mixture quality and enables a research paradigm where data mixture optimization is computationally accessible to academic groups, not just industrial labs with massive compute budgets.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** All experiments use the **Pile dataset** (Gao et al., 2021), specifically the 17 subsets available on HuggingFace after removing 5 components no longer accessible due to copyright concerns (Table 1: Books3, OpenWebText2, OpenSubtitles, BookCorpus2, and YouTubeSubtitles are excluded). The Pile contains 800 GiB of diverse English text spanning academic papers, code repositories, web crawls, books, forums, and domain-specific collections. For the 100-domain extension (Section 5.6), the paper uses the FineWeb dataset (Penedo et al., 2024a), defining domains by base URLs and selecting 100 domains based on token availability.

- **Base model(s).** The paper uses a decoder-only transformer architecture adapted from Zhang et al. (2024a) (TinyLlama), configured at four scales: 1M, 60M, 1B, and 7B non-embedding parameters (Table 9, Appendix E). The 1M-scale model (the primary proxy) uses `nlayers=2`, `nheads=8`, `dembedding=256`, and `dmodel=512`; the 1B-scale model (the primary target) uses `nlayers=22`, `nheads=16`, `dembedding=2048`, and `dmodel=5632`. All models share the GPTNeoX tokenizer with vocabulary size 50,432. The models are trained from scratch rather than fine-tuned from existing checkpoints, making this a pure pre-training data mixture study.

- **Metrics.** The primary proxy metric is **validation loss** (cross-entropy) on the Pile-CC domain, computed on held-out CommonCrawl text. The primary evaluation metrics are **downstream task performance** on 13 benchmarks: Social IQA, HellaSwag, PiQA, OpenBookQA, Lambada, SciQ, ARC Easy, COPA, RACE, LogiQA, QQP, WinoGrande, and MultiRC. Each benchmark score is the **average accuracy from 0-shot to 5-shot** settings, evaluated using the `lm-eval-harness` framework with normalized accuracy where provided. The paper also uses **Spearman rank correlation (ρ)** to measure how well the regression model predicts the ranking of mixtures (not just their absolute performance), and **Mean Squared Error (MSE)** for regression quality.

- **Baselines.** The paper compares against five approaches: **(1) Human selection** — the original domain weights proposed by Gao et al. (2021) for the Pile, re-normalized to the 17 available domains (Table 7 shows these weights: ArXiv 0.134, PubMed Central 0.136, Wikipedia 0.117, Stack Exchange 0.118, Pile-CC 0.142, etc.); **(2) DoReMi** (Xie et al., 2023a) — domain weights from the best-performing 280M-parameter reference model configuration, re-normalized to the 17 available domains (Table 7: Pile-CC 0.743, Wikipedia 0.086, etc.), requiring an estimated 3.7 × 10¹⁹ FLOPs to derive; **(3) PPL** — perplexity-based filtering from Ankner et al. (2024), a sample-level method requiring 1.8 × 10¹⁹ FLOPs; **(4) ODM** — Online Data Mixing from Albalak et al. (2023), an online group-level method; and **(5) Pile-CC Only** — training exclusively on the Pile-CC domain at 100% weight, a simple baseline that emerged as surprisingly competitive.

- **Generation budget / compute accounting.** The paper measures compute in **FLOPs** (floating-point operations) estimated using standard approximations. The primary proxy training uses 512 × 1M models at 1B tokens each, consuming approximately 3.5 × 10¹⁸ FLOPs — roughly 2% of the FLOPs needed to train a single 1B model on 25B tokens, and approximately 10% of DoReMi's estimated FLOPs budget (Table 4). The 1B-parameter target models are trained on 25B tokens, chosen to be Chinchilla-optimal given the model size (Hoffmann et al., 2022). The 7B models are trained on 100B tokens. For the 100-domain experiment, 1,000 proxy models are used. All proxy models are trained with batch size 1M tokens, learning rate 4 × 10⁻⁴, and cosine learning rate schedule.

- **Cross-validation / statistical protocol.** For regression model hyperparameter selection, the paper uses **5-fold cross-validation** on the 512 proxy model training examples: the L2 regularization strength for ridge regression is selected from {1e-3, 1e-2, 1e-1, 1e0, 1e1, 1e2, 1e3} by choosing the value that minimizes average held-out MSE across folds. For downstream evaluation, the paper reports performance averaged across 0-shot to 5-shot settings to reduce sampling variance. In the 7B experiments (Appendix J, Table 10), performance is reported as point estimates without confidence intervals. For the 100-domain regression evaluation in Table 5, the regression model is fitted on 1,000 proxy training runs and evaluated on 64 unseen mixtures for both 1M and 60M models.

---

### Main Quantitative Results

#### Regression Prediction Quality Across Scale Gaps

The foundational experiment tests whether REGMIX's regression model — fitted solely on 1M-parameter proxy models trained on 1B tokens — can predict the performance ranking of mixtures for models up to 1000× larger. Table 2 reports the central result:

- **On held-out 1M-parameter models**: LightGBM achieves Spearman ρ = 98.45 and MSE = 0.04, while linear regression achieves ρ = 90.08 and MSE = 0.13. The near-perfect LightGBM correlation on in-scale held-out data indicates the regression model has effectively learned the performance surface within the proxy regime.
- **On held-out 60M-parameter models** (60× scale gap): LightGBM achieves ρ = 98.64, linear regression achieves ρ = 89.26. The correlation actually *improves* slightly compared to the 1M held-out set, suggesting the regression model's predictions are not overfit to the 1M scale.
- **On held-out 1B-parameter models** (1000× scale gap, trained on 25B tokens — 25× more tokens): LightGBM achieves ρ = 97.12, linear regression achieves ρ = 88.01. This is the critical validation of the rank invariance hypothesis: a regression model trained exclusively on 1M models transfers to 1B models with only a ~1.3 percentage point drop in rank correlation.

The gap between LightGBM and linear regression (roughly 8–10 correlation points across all scales) is consistent and substantial, confirming that the non-linear interactions captured by tree-based models are essential for accurate prediction. The linear model's respectable but inferior performance (ρ ~ 88–90) suggests that while the additive approximation captures the dominant trends, domain interactions are first-order effects that require non-linear modeling to fully represent.

Figure 9 provides a visual complement to Table 2, showing scatter plots of predicted versus true loss on 1M held-out mixtures. The LightGBM points cluster tightly along the diagonal (correlation 0.99), while the linear regression points show substantially more scatter (correlation 0.90). The linear model exhibits systematic underestimation of high-loss mixtures and overestimation of low-loss mixtures — a pattern consistent with its inability to capture synergistic domain interactions that can push performance to extremes.

#### Proxy Model Count vs. Token Count Tradeoff

Figure 4 addresses a practical resource allocation question: given a fixed FLOP budget for proxy training, should we train more models (exploring more mixtures) or train each model longer (getting more reliable performance estimates from each)? The results strongly favor breadth over depth:

- **Increasing proxy model count consistently improves ρ**: For both linear and LightGBM regression, Spearman correlation on held-out mixtures increases substantially as the number of proxy models grows from 64 to 128 to 512, across all token budgets tested.
- **Increasing training tokens saturates after ~0.25B tokens**: For LightGBM with 512 proxy models, ρ rises from ~90 at 0.15B tokens to ~95 at 0.25B tokens, then plateaus — additional tokens beyond this point provide negligible improvement. For linear regression, the saturation is even more pronounced.
- **Concrete comparison**: 512 models trained on 0.2B tokens each (total: 102.4B tokens) produce *better* ρ than 128 models trained on 0.8B tokens each (total: 102.4B tokens) — the same total FLOPs, but allocated across more mixtures rather than more tokens per mixture.

This finding justifies REGMIX's design choice to use ultra-small models (1M parameters) trained on modest token counts (1B tokens) — beyond ~0.25B tokens, additional training provides little new information about the relative ranking of mixtures, while exploring more mixtures consistently improves the regression model's coverage of the mixture space.

#### Data Mixture Significantly Impacts Downstream Performance

Table 3 quantifies the stakes of data mixture optimization by reporting the performance range across 64 different data mixtures used to train 1B-parameter models on 25B tokens. The headline finding: the gap between the worst and best mixture on any single task reaches **14.6 percentage points** (Lambada: 18.9% vs. 33.5%), and the average gap across all 13 benchmarks is **4.2 percentage points** (43.7% vs. 47.9%).

The sensitivity varies substantially by task. The largest gaps appear on tasks evaluating broad language understanding and reasoning: Lambada (14.6), QQP (11.7), HellaSwag (10.4), COPA (9.0), and PiQA (8.8). Tasks with smaller gaps include Social IQA (1.5), WinoGrande (2.9), and LogiQA (4.5). The paper does not analyze *why* certain tasks are more mixture-sensitive than others, but a plausible interpretation is that tasks requiring broad world knowledge and linguistic flexibility (Lambada, QQP) benefit more from diverse data coverage, while tasks that depend on specific reasoning patterns (LogiQA) may be constrained by model capacity regardless of mixture.

#### Web Corpora Benefits Downstream Performance the Most

Figure 5(a) presents the correlation matrix between validation loss on each Pile domain and performance on each downstream task, computed across the 64 × 1B-parameter models. The visualization reveals a pattern that contradicts conventional wisdom:

- **Pile-CC validation loss** shows the strongest positive correlation (approaching 1.0 for HellaSwag) with downstream performance across nearly all 13 benchmarks. The correlation is visibly darker/more intense for Pile-CC than for any other domain.
- **Wikipedia (en) validation loss**, despite Wikipedia's reputation as a "gold standard" quality signal, shows substantially weaker correlations with most downstream tasks. For HellaSwag, PiQA, and Lambada, the Wikipedia correlation is noticeably lighter than Pile-CC's.
- **ArXiv, FreeLaw, and PubMed Central** validation losses show weak or even slightly negative correlations with some tasks, suggesting that optimizing for loss on these academic domains may not translate to general capability improvements.
- **GitHub and Stack Exchange** show moderate correlations on specific tasks (PiQA, ARC Easy) but weaker overall patterns than Pile-CC.

Figure 5(b) deepens this finding by decomposing Pile-CC into 100 URL-level domains from the C4 validation set. The key observation: more than 85% of these sub-domains independently show the same strong correlation pattern with downstream tasks. Specific examples like `www.ign.com` (a video game website), `www.latimes.com` (a newspaper), `patents.google.com`, and `mail-archives.apache.org` all exhibit broad positive correlations. This suggests that Pile-CC's predictiveness is not driven by any particular subset but by the aggregate diversity of web text — a property that is shared across most individual web domains.

#### REGMIX Outperforms Baselines on Downstream Performance

Table 4 presents the central comparison: 1B-parameter models trained on 25B tokens using different data mixture selection methods, evaluated across 14 benchmarks (13 + ARC Challenge, which was included in the experiments but not in the earlier correlation analysis). The results:

- **REGMIX achieves the highest average performance (47.3)**, outperforming the next-best methods (DoReMi and Pile-CC only, both at 46.8) by 0.5 points. It achieves the best score on 7 out of 14 individual benchmarks.
- **Pile-CC Only (46.8) ties DoReMi** and substantially outperforms Human selection (45.1), PPL (46.2), and ODM (45.0). This is perhaps the most surprising result: simply training on 100% CommonCrawl web data — with no domain mixing at all — beats sophisticated learned mixture methods that use domain-specific optimization.
- **REGMIX improves over Human selection by substantial margins on key benchmarks**: HellaSwag 44.2 vs. 37.4 (+6.8), PiQA 69.3 vs. 65.0 (+4.3), Lambada 34.2 vs. 29.8 (+4.4), QQP 58.3 vs. 52.4 (+5.9), RACE 31.3 vs. 29.0 (+2.3), OpenBookQA 30.3 vs. 28.2 (+2.1).
- **DoReMi performs competitively** (46.8 average) but requires approximately 10× more FLOPs than REGMIX (3.7 × 10¹⁹ vs. 3.5 × 10¹⁸ estimated FLOPs). On individual benchmarks, DoReMi achieves the best score on 0 out of 14 tasks — it never beats all other methods simultaneously on any single task.
- **PPL underperforms expectations** (46.2 average) given its computational cost (1.8 × 10¹⁹ FLOPs), suggesting that sample-level perplexity filtering does not capture the domain-level tradeoffs that matter for mixture optimization.
- **Human selection underperforms on most benchmarks** compared to automated methods, achieving the best score on only 2 out of 14 tasks (and those margins are small).

The estimated FLOPs row in Table 4 quantifies the efficiency advantage: REGMIX requires 3.5 × 10¹⁸ FLOPs to derive its mixture, which is approximately 10% of DoReMi's 3.7 × 10¹⁹ FLOPs and approximately 19% of PPL's 1.8 × 10¹⁹ FLOPs. Human selection, Pile-CC Only, and ODM report 0 FLOPs for mixture derivation (human selection because it's manual; Pile-CC Only because it's trivial; ODM presumably because the mixture weights are taken from prior published work), but these zero-FLOP baselines achieve lower performance.

Figure 6 (left) shows the training curves (validation loss on Pile-CC vs. training tokens) for Human, DoReMi, and REGMIX. REGMIX achieves lower validation loss than both baselines at every point from 1B to 25B tokens, and the gap appears to widen slightly as training progresses — suggesting the benefit of the optimized mixture compounds with more training. Figure 6 (right) demonstrates robustness to out-of-distribution settings: when Pile-CC is excluded from the training corpus entirely, REGMIX still finds mixtures that achieve lower Pile-CC validation loss than baselines, meaning the method works even when the optimization target domain is not present in the training data.

The final row of Table 4 ("Best On") tallies how many benchmarks each method wins. REGMIX wins 7, Pile-CC Only wins 5, DoReMi wins 0, Human wins 2, PPL wins 1, ODM wins 0. Note that these counts sum to more than 14 because some benchmarks have ties (the paper's highlighting convention counts all methods achieving the best score on a given benchmark).

#### The Final REGMIX Mixture

Table 7 reveals the actual domain weights derived by REGMIX and the baselines for the 1B experiment. The REGMIX mixture is dominated by Pile-CC at **87%**, with the remaining 13% distributed across a small number of domains: Ubuntu IRC (6.4%), PubMed Abstracts (2.4%), Wikipedia (1.6%), HackerNews (1.2%), PubMed Central (0.3%), Gutenberg (0.2%), Enron Emails (0.2%), and USPTO Backgrounds (0.2%). Six domains receive zero weight: DM Mathematics, GitHub, PhilPapers, Stack Exchange, EuroParl, and NIH ExPorter. ArXiv and FreeLaw receive 0.1% each.

This mixture bears almost no resemblance to the Human mixture, which distributes weight broadly: ArXiv 13.4%, PubMed Central 13.6%, Wikipedia 11.7%, Stack Exchange 11.8%, Pile-CC 14.2%, PubMed Abstracts 10.7%, etc. The DoReMi mixture is intermediate: Pile-CC 74.3%, Wikipedia 8.6%, with small amounts of PhilPapers (3.4%) and other domains. The REGMIX mixture is more extreme than DoReMi in concentrating weight on Pile-CC while completely eliminating domains that DoReMi retained at non-zero weights (ArXiv, GitHub, Stack Exchange).

#### Scaling to 7B Parameters and 100B Tokens

Figure 1 (reproduced across the paper's first page) and Table 10 (Appendix J) extend the validation to 7B-parameter models trained on 100B tokens — a ~150× compute increase over the 1B experiments. The key findings:

- **REGMIX outperforms Human selection on 10 out of 13 benchmarks** at the 100B token mark, with an average improvement of 2.0 percentage points (56.5 vs. 54.5).
- **The performance advantage persists across training duration**: Figure 1 shows REGMIX and Human performance curves at 25B, 50B, 75B, and 100B tokens for 12 benchmarks. On most benchmarks showing positive scaling (HellaSwag, PiQA, Lambada, ARC Easy, COPA, SciQ, OpenBookQA), REGMIX maintains a consistent lead at all token counts. On benchmarks where performance saturates or declines with more tokens (MultiRC, LogiQA, QQP), both methods converge or REGMIX's advantage narrows.
- **Pre-training acceleration is substantial**: REGMIX reaches at 50B tokens roughly the same performance that Human selection achieves at 100B tokens on HellaSwag (~55% vs. ~55%), PiQA (~73% vs. ~72.4%), and Lambada (~48% vs. ~44.9%). This implies that the optimized mixture effectively halves the required training compute for equivalent downstream performance on these benchmarks.
- **Not all tasks benefit equally**: On WinoGrande, Social IQA, and MultiRC, the performance curves for both methods are relatively flat after 25B tokens, and REGMIX's advantage is small or nonexistent. On LogiQA, Human selection slightly outperforms REGMIX at 100B tokens (25.7 vs. 24.1). The paper hypothesizes that REGMIX may not improve tasks whose performance does not scale with additional training data.

#### Extension to 100 Domains

Table 5 reports the regression prediction quality when scaling REGMIX from 17 Pile domains to 100 FineWeb URL domains:

- **LightGBM achieves ρ = 99.53** on held-out 1M-parameter models and **ρ = 98.80** on held-out 60M-parameter models, with MSE = 0.02 and 0.02 respectively.
- **Linear regression achieves ρ = 90.33** on 1M models and ρ = 88.64 on 60M models.
- These correlations are actually slightly *higher* than in the 17-domain case (Table 2: LightGBM ρ = 98.45 on 1M, 98.64 on 60M). The paper does not analyze this counterintuitive improvement, but a plausible explanation is that the 100 URL domains are more homogeneous (all web text) than the 17 Pile domains (web, academic, code, books), making the performance surface smoother and easier to fit even in a higher-dimensional space.

### Ablation Studies and Robustness Checks

**Linear vs. LightGBM regression (Table 2, all rows)**: LightGBM consistently outperforms linear regression by 8–10 Spearman correlation points across all model scales tested (1M, 60M, 1B). The gap does not narrow at larger scales, confirming that non-linear domain interactions are not a small-model artifact that disappears with scale — they persist and must be modeled. The linear model's ρ of 88–90 is far from random but well below the ~97–99 achieved by LightGBM, quantifying the value of non-linear modeling.

**Proxy model count vs. training tokens (Figure 4)**: Increasing the number of proxy models from 64 to 512 consistently improves ρ across all token budgets, with the largest gains occurring between 64 and 128 models. Increasing training tokens per proxy from 0.2B to 1.0B provides diminishing returns, especially for LightGBM where ρ plateaus at ~0.25B tokens. The interaction effect is notable: with only 64 proxy models, more training tokens help substantially (ρ rises from ~80 to ~90 for LightGBM going from 0.2B to 1.0B tokens), but with 512 proxy models, the same token increase produces a negligible gain (ρ from ~96 to ~97). This cross-over pattern validates the paper's strategy of training many small models rather than fewer larger ones.

**Out-of-distribution target domain (Table 6, Figure 6 right)**: When Pile-CC is excluded from the training corpus and REGMIX is asked to optimize for Pile-CC validation loss anyway, LightGBM achieves ρ = 95.47 and MSE = 0.04 on held-out 1M mixtures — slightly lower than with Pile-CC in-distribution (ρ = 98.45) but still very strong. This demonstrates that REGMIX works even when the target domain is not present in the training data, making it applicable to scenarios where the validation set comes from a different distribution than the training data. Figure 6 (right) confirms that the resulting mixture achieves lower Pile-CC validation loss than baselines across training, though the gap is smaller than in the in-distribution setting (Figure 6, left).

**Proxy model scale comparison (Appendix K, Table 11)**: The paper compares mixtures derived from 512 × 1M proxy models versus 128 × 1B proxy models, both applied to 7B target models trained on 100B tokens. The result is a near-tie: the 1B-derived mixture achieves 56.4 average downstream performance, the 1M-derived mixture achieves 56.5. The 1M approach uses dramatically less compute. This equivalence suggests that increasing proxy model size does not provide additional information about mixture quality, at least up to the 7B target scale — further supporting the rank invariance hypothesis and the sufficiency of 1M-scale proxies.

**Stability across proxy model scales (Appendix F, Figure 14)**: The paper compares the distribution of top-1024 predicted mixtures using regression models fitted on 1M versus 60M proxy training logs. The distributions are "remarkably similar" (Figure 14), with both assigning dominant weight to Pile-CC and a long tail of small weights to other domains. This contrasts with DoReMi, where 280M and 1B proxy models produce dramatically different weights (Pile-CC weight swinging from 0.67 to below 0.20 according to Xie et al.'s Figure 8). The stability is attributed to the regression formulation, which does not depend on training dynamics that vary with model scale.

**Rank invariance across model scales and token counts (Appendix I, Figure 15)**: The paper computes Spearman rank correlations between validation loss rankings across all four model scales (1M, 60M, 280M, 1B) and three token scales (1B, 5B for 280M, 25B for 1B) using 64 data mixtures each. The correlation matrix shows values ranging from 0.94 (280M at 5B tokens vs. 1B at 25B tokens) to 0.99 (1M at 1B tokens vs. 280M at 5B tokens). The lowest correlation (0.94) is still very high by conventional standards, and all values are above 0.90, providing strong empirical support for the rank invariance hypothesis within the tested range.

**Evaluation framework comparison (Appendix C.4, Table 8)**: To address potential evaluation variance, the paper replicates the 1B model comparison using LightEval instead of lm-eval-harness, reporting zero-shot only performance averaged over 5 runs with standard deviations. REGMIX achieves 41.5 average performance (vs. 39.5 Human, 41.1 DoReMi, 41.2 Pile-CC), with statistically significant improvements over Human on 6 of 9 benchmarks. The standard deviations are small (0.2–0.8 across methods), indicating that the evaluation protocol is reliable and the performance differences are not artifacts of sampling noise.

**Target metric choice (Section 5.2, Figure 5)**: The paper's choice of Pile-CC validation loss as the optimization target is itself validated by the correlation analysis. If the target were poorly chosen, the regression model would optimize for a metric uncorrelated with downstream performance, and the resulting mixture would underperform baselines despite achieving low predicted loss. The fact that REGMIX *does* outperform baselines on downstream tasks (Tables 4, 8, 10) confirms that Pile-CC loss is an effective proxy — optimizing for it transfers to genuine capability improvements.

**Negative result: ReST\(^{EM}\) training degradation (Appendix K, referenced in Section 6 of the paper)**: The paper reports that attempting to further optimize the revision model using ReST\(^{EM}\) (Singh et al., 2024) caused performance to degrade — though this ablation is in the context of the revision model experiments rather than REGMIX itself. The fact that the authors transparently report this negative result, even though it is not directly about REGMIX, adds credibility to their positive findings.

### Critical Assessment

**Claim: REGMIX identifies the optimal mixture among 64 candidates using only 1M-scale proxy models.** The evidence for this is direct and strong. Table 2 shows LightGBM ρ = 97.12 on 1B models, and Figure 2 (right) visualizes the exact prediction: the red star marking REGMIX's predicted best mixture coincides with the lowest validation loss among all 64 × 1B models. However, the careful reading here is important: the paper demonstrates that REGMIX correctly identifies the *best among the 64 mixtures tested*, not that it identifies the *globally optimal mixture across all possible 17-dimensional simplex points*. The 64 evaluated 1B mixtures are a specific set sampled from the Dirichlet distribution described in Section 3.1. It is possible — though empirically unlikely given the high Spearman correlation — that a mixture outside this set would perform even better. The simulation step (Section 3.3) *does* attempt to find the global optimum by searching 1,000,000 mixtures, but the verification of this global prediction is only through the top-1 rank among 64, not through an exhaustive or adaptive search.

**Claim: REGMIX requires only 10% of DoReMi's computational budget.** Table 4 reports 3.5 × 10¹⁸ FLOPs for REGMIX versus 3.7 × 10¹⁹ for DoReMi. However, this comparison has an important caveat: DoReMi's FLOPs count is an *estimate* derived from the computational cost of training a proxy model of the reported size for the reported number of tokens. The paper does not replicate DoReMi's training — it uses the published weights from Xie et al. (2023a) and re-normalizes them to the 17 available domains. This means the comparison is between REGMIX's *actual* cost and DoReMi's *estimated* cost as configured in a different paper, with potentially different hardware, implementations, and hyperparameters. The 10% figure is therefore approximate and could shift if DoReMi were re-implemented and optimized. Additionally, the re-normalization of DoReMi's weights (to account for the 5 removed copyrighted domains) means the DoReMi baseline in Table 4 is not exactly the DoReMi from the original paper — the original weights are distorted by redistribution, which could either improve or degrade relative performance depending on whether the removed domains were receiving high or low weights. The paper acknowledges this ("This may result in sub-optimal performance for them compared to the originally reported results").

**Claim: The data mixture significantly impacts performance, with gaps up to 14.6% on individual tasks.** Table 3 directly supports this, but the experimental design has a limitation: the 64 mixtures were sampled from a Dirichlet procedure designed to cover extremes (λ ranging from 0.1 to 5.0, Section 3.1). This means the 14.6% gap on Lambada is between mixtures that were deliberately constructed to be diverse and includes extreme cases (e.g., mixtures where one domain receives very high weight and others receive zero). The gap between *reasonable, practically used* mixtures might be smaller. The Human baseline (45.1) versus the best 1B model in Table 3 (47.9) shows a gap of 2.8 average points — which is substantial but smaller than the 4.2-point range across all 64 models. The max-min range in Table 3 is an upper bound on the sensitivity, not a typical gap between plausible mixtures.

**Claim: Web corpora like CommonCrawl have the strongest correlation with downstream performance.** Figure 5(a) is visually compelling, but the analysis has a statistical subtlety: the correlation coefficients are computed across 64 models that vary in *all* domain weights simultaneously. A strong correlation between Pile-CC loss and HellaSwag could arise because Pile-CC weight varies substantially across the 64 mixtures (from near-zero to 100%) while other domains' weights are sometimes zero — making Pile-CC loss a dominant differentiator. If all 64 mixtures contained substantial Pile-CC weight (as the REGMIX mixture does, at 87%), the within-Pile-CC-loss correlation with downstream performance might be weaker. The analysis in Figure 5(b) partially addresses this by showing that the correlation holds across individual URL sub-domains, but the broader point remains: the correlation structure is a property of the specific mixture distribution tested, not necessarily a universal property of these domains.

**Missing experiment: Sensitivity to the number of domains.** The paper demonstrates REGMIX with 17 and 100 domains but does not systematically explore how performance degrades as the number of domains increases. With 100 domains, the simplex is 99-dimensional, and 1,000 proxy models may provide sparse coverage. The high ρ values in Table 5 are encouraging but are evaluated on only 64 held-out mixtures — which, in a 99-dimensional space, are a very small sample. A scaling analysis showing how many proxy models are needed per domain would strengthen confidence in REGMIX's applicability to datasets with hundreds or thousands of domains.

**Missing experiment: Different base model architectures or tokenizers.** All experiments use the GPTNeoX tokenizer and the TinyLlama-derived architecture. The paper acknowledges (Appendix B) that the tokenizer is a fundamental assumption — domain weights optimized for one tokenizer may not transfer to another because tokenization changes the effective information content per token from each domain. An experiment training proxy models with different tokenizers (e.g., Llama tokenizer vs. GPTNeoX) and testing whether the predicted optimal mixtures agree would partially address this concern, but is not included.

**Missing baseline: Uniform mixture.** A natural baseline that is absent from Table 4 is a uniform mixture (equal weights on all 17 domains, or weights proportional to available tokens). This would help distinguish whether REGMIX's gains come from optimizing domain proportions or simply from recognizing that extreme concentration (Pile-CC-heavy) outperforms the diffuse Human mixture. The Pile-CC Only baseline partially fills this gap, but a uniform baseline would provide a more complete picture of the performance landscape.

**Missing analysis: Why does the REGMIX mixture work?** The paper provides the mixture (Table 7) and demonstrates that it outperforms baselines (Table 4), but there is no mechanistic analysis of *why* 87% Pile-CC with 6.4% Ubuntu IRC and zero weight on GitHub/Stack Exchange is optimal. The domain interaction visualizations (Figure 7) suggest that PhilPapers has beneficial linear coefficients, yet it receives zero weight in the final mixture — presumably because the non-linear LightGBM model captures interactions that override the linear signal. But this is speculation; the paper does not analyze the LightGBM model's decision-making or feature importance to explain the final recommendation. This is a missed opportunity for scientific understanding — knowing *why* certain domains are excluded would be valuable for generalization to new datasets.

**Missing experiment: Training beyond Chinchilla-optimal token counts.** The 1B models are trained on exactly 25B tokens (Chinchilla-optimal), and the 7B models on 100B tokens (also approximately Chinchilla-optimal). The paper does not explore whether the optimal mixture changes when training extends into the over-trained regime (more tokens than Chinchilla-optimal), which is increasingly common in practice (e.g., Llama-3 trains on 15T tokens with models far below the Chinchilla-optimal size for that token count). If over-training changes the relative value of different domains (e.g., making diverse web data saturate faster than curated academic data), the 1M-to-1B transfer validated at Chinchilla-optimal tokens might not hold in over-trained regimes.

**Missing analysis: Variance across random seeds.** The paper reports single-run results for the 1B and 7B target models. Language model pre-training has inherent variance from random weight initialization, data ordering, and dropout. Without multiple seeds, it is unclear whether a 0.5-point average improvement (47.3 vs. 46.8, Table 4) is statistically significant or within the noise floor. The LightEval results with standard deviations (Table 8) provide some reassurance — the standard deviations are 0.2–0.8 points, suggesting that differences of 1–2 points on individual benchmarks are likely meaningful — but the average performance difference between REGMIX and Pile-CC Only (47.3 vs. 46.8, a 0.5-point gap) could plausibly be within seed variance and is not explicitly tested.

## 6. Limitations and Trade-offs

### The Rank Invariance Hypothesis Is Validated Only Up to 1B Parameters, Not at Frontier Scales

**The assumption or constraint.** The entire REGMIX framework rests on the rank invariance hypothesis: that the relative ordering of data mixtures by their effectiveness is stable across model sizes and training token counts. The paper validates this hypothesis empirically from 1M parameters up to 1B parameters (Table 2: Spearman ρ = 97.12 for 1B models) and demonstrates end-to-end mixture optimization transferring from 1M proxies to 7B targets (Appendix J, Table 10). However, the paper explicitly acknowledges in Appendix B:

> "Our investigation of the rank invariance assumption currently focuses on model scales from 1M to 1B parameters. While we aimed to verify the hypothesis at larger scales, establishing statistically meaningful correlations for 3B models would require training 64 different models with 50B tokens each, equivalent to training one 3B model on 3.2T tokens, which significantly exceeds our computational resources."

Furthermore: "Due to compute constraints we leave the verification of REGMIX at larger scales to future work."

**The consequence.** At frontier scales — 70B parameters, 400B parameters, or beyond — the rank invariance hypothesis could break down for several physically plausible reasons. Larger models have greater capacity to absorb and differentiate signal from noisy data, which might change the relative value of high-quality curated domains versus massive web crawls. Phenomena like data quality thresholds, where a domain only becomes useful above a certain model capacity, would manifest as rank reversals across scales: a mixture that underperforms at 1M parameters because it includes "difficult" data might outperform at 70B parameters because the larger model can extract useful signal that the small model could not. If such reversals occur, REGMIX's 1M-parameter proxy recommendations could be actively misleading — recommending against mixtures that would actually be optimal at the target scale.

The paper's own evidence hints at subtle scale-dependent effects. In Appendix I (Figure 15), the rank correlation between 1M (1B tokens) and 1B (25B tokens) models is 0.97, but this still means ~3% of pairwise mixture rankings are reversed. If the reversed pairs include the top-ranked mixtures, the "optimal" mixture identified at 1M scale might not be optimal at 1B scale — it might be, say, the fifth-best. The paper does not report the rank of the REGMIX-predicted mixture among the 1B models *as measured by downstream performance* (only by validation loss in Figure 2, right), so the practical impact of these ranking errors on downstream outcomes is not directly quantified.

For practitioners training models at 70B+ scale, this limitation means that REGMIX's recommendations are a best-guess extrapolation, not a validated transfer. The 1M-to-7B validation is encouraging but stops short of the regime where most production LLMs operate today.

**What evidence exists in the paper.** The positive evidence is in Table 2 (ρ = 97.12 for 1B models), Appendix J (Table 10: REGMIX outperforms Human at 7B), and Appendix I (Figure 15: consistently high ρ across scales up to 1B). The negative evidence — the absence of larger-scale validation — is explicitly acknowledged in Appendix B.

**Mitigation status.** Not addressed. The paper flags this as future work and is transparent about the computational constraints that prevented larger-scale validation. No partial mitigation (e.g., theoretical arguments for why rank invariance should hold at larger scales) is offered. A cautious practitioner would validate REGMIX at an intermediate scale (e.g., 3B or 7B) before trusting it for 70B+ training decisions, using the approach of training a modest number of larger-scale models to confirm that the predicted optimal mixture maintains its ranking advantage.

---

### Difficulty Estimation Cost Is Substantial and Not Accounted for in the Headline Efficiency Numbers

**The assumption or constraint.** REGMIX requires training 512 small-scale proxy models (1M parameters each, 1B tokens each) to fit the regression model. The paper reports the estimated FLOPs for this proxy training as 3.5 × 10¹⁸ — approximately 2% of the FLOPs needed to train a single 1B model on 25B tokens, and approximately 10% of DoReMi's estimated FLOPs budget (Table 4). However, these numbers have an important caveat that the paper acknowledges only indirectly: **the cost of exploring the mixture space to find the optimum is not amortized across multiple target models in the reported comparisons**.

Specifically, the 512 × 1M proxy models are trained to optimize a single target — the data mixture for one 1B-parameter model. The total cost of deriving this mixture (3.5 × 10¹⁸ FLOPs) is compared against the cost of training the 1B model (approximately 1.8 × 10²⁰ FLOPs, based on the 25B token budget), yielding the "2%" figure. But this accounting omits the cost of the **64 × 1B evaluation models** used to validate that REGMIX's prediction was correct (Table 3, Table 4, and the 64 models plotted in Figure 2). Training those 64 models consumes approximately 64 × 1.8 × 10²⁰ = 1.15 × 10²² FLOPs — over 3000× the proxy training cost. These evaluation models are part of the paper's experimental validation, not a deployment requirement, but they highlight that the true cost of *developing and validating* REGMIX for a new dataset or domain structure is much higher than the 2% figure suggests.

More importantly for practitioners: the 2% figure represents the cost of optimizing the mixture for a *single* target model. If an organization trains many models at the same scale (e.g., a 7B model for research, then fine-tuned variants, then updated versions), the proxy training cost can be amortized. But if the target model scale, architecture, or data distribution changes, new proxy models may be needed. The paper does not provide guidance on how sensitive the optimal mixture is to these factors.

**The consequence.** The headline efficiency claim — "less than 2% of final training costs" — may lead practitioners to underestimate the true adoption cost of REGMIX. The 512 proxy models require:
- **Infrastructure for parallel training**: 512 small models can be trained in parallel, but this requires either a large GPU cluster or significant wall-clock time on a smaller cluster. The paper does not report wall-clock time for proxy training.
- **Data preparation at 512 different mixture ratios**: Each proxy model requires constructing a training dataset with a specific domain weight distribution, which means 512 separate data preprocessing pipelines or an efficient dynamic sampling system.
- **Regression model tuning**: The LightGBM hyperparameters (1,000 trees, learning rate 0.01) were manually set; for a new dataset, these might need tuning, which requires additional held-out evaluations.

These costs are not prohibitive — they are almost certainly still well below the cost of the large-scale training — but they are real and unquantified in the paper. A team with a single 8-GPU node might find that training 512 models at 1B tokens each takes weeks in wall-clock time, even if the total FLOPs are modest.

**What evidence exists in the paper.** The paper reports estimated FLOPs in Table 4 and notes in the abstract that proxy training uses "nearly 2% of the FLOPs required for one 1B model." The paper does not report wall-clock time, GPU-hours, or data preprocessing costs. The need for 512 separate training runs is a design choice motivated by Figure 4 (more proxy models > more tokens per proxy), but the practical overhead of managing 512 runs is not discussed.

**Mitigation status.** Partially addressed by the finding that 128 proxy models with fewer tokens can approach the performance of 512 models (Figure 4), offering a cost-quality tradeoff that practitioners could exploit. The 100-domain experiment (Section 5.6) uses 1,000 proxy models, suggesting the paper views scaling proxy count as the right direction, but this further increases the overhead. No automated infrastructure or cost-amortization strategy is proposed.

---

### The Method Does Not Provide Guidance for Tasks That Do Not Scale With Training Data

**The assumption or constraint.** REGMIX optimizes data mixtures to improve a target metric — in the paper's experiments, validation loss on Pile-CC, chosen because it correlates strongly with downstream task performance (Figure 5a). The implicit assumption is that improving this proxy metric will improve downstream task performance, and that downstream task performance continues to improve with more training data (positive scaling).

However, Section 5.6 (Appendix J, Table 10, Figures 1) reveals a critical boundary condition: **on tasks whose performance does not increase with training tokens, REGMIX provides no benefit and may even underperform human selection.** Specifically:

- On **LogiQA**, Human selection slightly outperforms REGMIX at 100B tokens (25.7 vs. 24.1), and the performance curves for both methods are essentially flat from 25B to 100B tokens.
- On **MultiRC**, both methods converge at 100B tokens (52.6 vs. 51.0), with flat or declining scaling curves.
- On **QQP**, Human selection outperforms REGMIX (58.9 vs. 56.1), and REGMIX's performance actually declines from 75B to 100B tokens in Figure 1.

The paper itself observes this pattern in Appendix J:

> "RegMix can almost benefit downstream tasks whose performance increases with the amount of training data, but may not improve tasks that do not follow scaling laws. This observation is quite intriguing and warrants further investigation."

**The consequence.** This limitation means that REGMIX's effectiveness is bounded by the scaling behavior of the tasks of interest. If a practitioner cares primarily about a task that does not show positive scaling with additional pre-training data — perhaps because the task requires capabilities that the pre-training data simply does not contain (e.g., specific logical reasoning patterns not well-represented in the Pile) — then optimizing the mixture for general validation loss may not translate to task-specific gains.

More broadly, this finding suggests that REGMIX (and data mixture optimization generally) can only **amplify existing scaling trends**, not create new ones. If a task is fundamentally limited by factors other than data mixture — model architecture, pre-training objective, inherent task difficulty, absence of relevant training data in any domain — REGMIX cannot overcome those limits. The paper does not provide a diagnostic for predicting which tasks will benefit from mixture optimization without running the full experiment.

For practitioners, this means that REGMIX should be paired with an analysis of which downstream tasks actually scale with additional data. The method is most valuable when the target is general-purpose capability (for which Pile-CC loss is a good proxy) and when the tasks of interest show positive scaling. If a specific high-priority task shows flat or negative scaling, REGMIX's mixture optimization may be irrelevant for that task, and alternative approaches (e.g., targeted data collection, architectural modifications, task-specific fine-tuning) would be more productive.

**What evidence exists in the paper.** Figures 1 (the 12-panel performance plot), Table 10, and the quoted observation from Appendix J. The evidence is clear: REGMIX's advantage is largest on tasks with positive scaling (HellaSwag, PiQA, Lambada, ARC Easy, COPA, SciQ) and negligible or negative on tasks with flat or declining scaling (LogiQA, MultiRC, WinoGrande, Social IQA, QQP).

**Mitigation status.** Not addressed as a methodological limitation — the paper treats this as an empirical observation and notes it warrants further investigation. No guidance is offered for predicting ex ante which tasks will benefit. A practitioner could potentially use small-scale scaling experiments (training models at 25B, 50B, 75B tokens with a default mixture) to identify which tasks scale before investing in REGMIX, but this would add to the already-substantial overhead. The paper does not explore whether optimizing for a different proxy metric (e.g., validation loss on a domain more closely matched to the non-scaling tasks) would yield better results.

### The Optimal Mixture Depends on the Tokenizer and Model Architecture, Which Are Fixed in All Experiments

**The assumption or constraint.** REGMIX discovers an optimal mixture for a specific combination of tokenizer and model architecture — in this paper, the GPTNeoX tokenizer and a TinyLlama-derived decoder-only transformer. The paper acknowledges this in Appendix B:

> "All existing data mixture methods require the use of proxy models to obtain domain weights. However, a fundamental assumption of these methods is that the proxy model uses the same tokenizer and vocabulary size as the large model. Generalizing weights across different tokenizers poses significant challenges."

This is not a minor caveat. Tokenization directly affects how many tokens each domain contributes per unit of raw text, and different tokenizers can compress different types of text differently. A tokenizer trained primarily on English web text will encode English Wikipedia efficiently (few tokens per word) but may encode code or multilingual text less efficiently (many tokens per word). Since REGMIX's domain weights are defined in terms of **token proportions** — "X% of training tokens come from domain Y" — changing the tokenizer changes the effective information content allocated to each domain, which could shift the optimal mixture.

Similarly, model architecture choices — depth, width, attention mechanism, positional encoding — affect how efficiently a model can absorb different types of data. A narrow, deep model might benefit more from structured, hierarchical text (academic papers, textbooks), while a wide, shallow model might benefit more from diverse, unstructured text (web data). The paper's architecture sweep (Table 9) varies depth and width jointly to scale model size, but does not ablate architecture at fixed parameter count to test whether the optimal mixture is architecture-dependent.

**The consequence.** If a practitioner wants to use REGMIX with a different tokenizer (e.g., the Llama tokenizer, which has a different vocabulary and different compression characteristics) or a different architecture (e.g., a mixture-of-experts model, or a model with a different attention mechanism), the mixture weights optimized for GPTNeoX + TinyLlama-derived architecture may not transfer. The practitioner would need to re-run the full REGMIX pipeline — training 512+ proxy models with the new tokenizer and architecture — to obtain a reliable recommendation.

This also limits the generality of the paper's specific mixture recommendations (Table 7). The finding that "87% Pile-CC + 6.4% Ubuntu IRC + small supplements" is optimal may be specific to the GPTNeoX tokenization of the Pile. With a different tokenizer, the relative token yields from each domain would shift, and the "optimal" mixture in token space would likely shift as well. The qualitative finding that web data should dominate might be robust, but the specific weights might not be.

**What evidence exists in the paper.** The limitation is explicitly acknowledged in Appendix B but is not experimentally explored. No experiments vary the tokenizer. No experiments vary the architecture at fixed parameter count. All models across all scales use the same basic architecture family.

**Mitigation status.** Not addressed. The paper acknowledges the issue and suggests it as a challenge for future work, but provides no partial solution (e.g., training a small number of proxy models with a different tokenizer to measure sensitivity, or developing a method to re-weight mixtures across tokenizers based on compression ratios). A practitioner adopting REGMIX with a different tokenizer currently has no guidance on whether to expect the paper's specific recommendations to transfer. The safe (and expensive) approach is to re-run REGMIX from scratch.

### The Pile-CC Metric Selection Is Empirically Justified but Not Theoretically Grounded, Limiting Generalization to New Domains

**The assumption or constraint.** REGMIX requires choosing a target metric for the regression model to optimize. The paper selects **validation loss on Pile-CC** based on the empirical observation (Figure 5a) that Pile-CC loss has the strongest correlation with downstream task performance among all Pile domains. This is a pragmatic, data-driven choice — but it is an empirical finding specific to the Pile dataset and the set of downstream benchmarks evaluated. There is no theoretical argument for why web corpora should be the best proxy; the paper hypothesizes that "the high correlation between Pile-CC and downstream task performance may be attributed to its diverse coverage across various topics and domains" (Section 5.2), but this is a post-hoc interpretation, not a predictive principle.

**The consequence.** When applying REGMIX to a new dataset or a new set of downstream tasks, the practitioner must choose a target metric without the benefit of the correlation analysis that the paper used to justify Pile-CC. The paper demonstrates that the choice of target metric matters: Figure 5(a) shows that Wikipedia (en) validation loss — the conventional choice in much prior work — has noticeably weaker correlations with downstream performance than Pile-CC. If a practitioner naively chooses a suboptimal target metric (e.g., WikiText perplexity), REGMIX would faithfully optimize for it, but the resulting mixture might not improve — and could even degrade — downstream task performance.

The out-of-distribution experiment (Section 5.3, Figure 6 right, Table 6) provides partial reassurance: even when Pile-CC is excluded from the training data, REGMIX can optimize for Pile-CC validation loss and find mixtures that outperform baselines. But this experiment still uses Pile-CC as the target — it tests whether the target domain needs to be in the training data, not whether Pile-CC is the right target in the first place.

More fundamentally, the paper does not address the scenario where **no single domain's validation loss** is a good proxy for the downstream tasks of interest. If a practitioner cares about tasks spanning code generation, mathematical reasoning, and multilingual translation, it is unlikely that any single validation domain will correlate strongly with all three. REGMIX's framework could in principle be extended to multi-target optimization (fitting a regression model for each task and searching for a mixture that balances them), but the paper does not explore this, and the single-target approach may produce mixtures that over-optimize for one capability at the expense of others.

**What evidence exists in the paper.** Figure 5(a) shows the correlation matrix that justifies the Pile-CC choice for the Pile + the 13 evaluated benchmarks. Section 5.2 discusses the finding in detail. The paper does not provide an ablation where a different target metric (e.g., Wikipedia loss, average loss across all domains) is used and downstream performance is compared. The out-of-distribution experiment (Figure 6, right) tests robustness to excluding the target domain from training but assumes the target domain is correctly chosen.

**Mitigation status.** The paper does not claim to solve the target metric selection problem — it demonstrates that Pile-CC works well for this specific setup and provides a methodology (the correlation analysis in Figure 5a) that practitioners could replicate on their own datasets. However, replicating this analysis requires training multiple models with different mixtures and evaluating them on downstream tasks — essentially the same cost as the 1B evaluation in Table 3 — which partially defeats the purpose of having an efficient proxy method. A lightweight procedure for selecting the target metric (e.g., using the proxy models themselves to measure which validation domain's loss best predicts held-out proxy performance on downstream tasks) is not described but would be a natural extension.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

REGMIX does not introduce a new neural architecture, training objective, or scaling law. Its contribution is methodological: it reframes data mixture selection from an online control problem — where domain weights are adjusted dynamically during training through unstable feedback loops — into a standard supervised regression problem — where many small models independently sample the mixture space and a regression model maps mixture weights to performance. This reframing is not a paradigm shift in the sense of overturning foundational assumptions about language model training. The goal remains unchanged: find domain weights that maximize downstream performance at a given compute budget. What shifts is the **mechanism by which the weights are discovered** and, consequently, the **scalability, stability, and interpretability of that discovery process**.

The practical significance of this shift is measurable. REGMIX achieves near-perfect mixture ranking prediction across a 1000× scale gap (Spearman ρ = 97.12) while consuming roughly 10% of the compute required by DoReMi, the previous flagship method in offline group-level data selection. More importantly, REGMIX is **inherently parallelizable** — the 512 proxy models can be trained simultaneously — while DoReMi's adaptive weight adjustment during a single long training run imposes a serial bottleneck that cannot be accelerated by adding GPUs. In an era where pre-training datasets are expanding to tens of trillions of tokens and domain taxonomies are growing to hundreds or thousands of categories, methods that scale linearly with wall-clock time (rather than with total FLOPs that can be parallelized) become intractable. REGMIX converts a latency problem into a throughput problem, which is the right direction for scaling to larger datasets.

Beyond efficiency, the paper resolves a tension in the prior literature that has been silently shaping research priorities. DoReMi (Xie et al., 2023a) demonstrated that learned data mixtures could accelerate pre-training, but its instability to proxy model scale — where Pile-CC weight swung from 0.67 with a 280M proxy to below 0.20 with a 1B proxy — created doubt about whether proxy-based mixture optimization was fundamentally reliable or merely an artifact of specific proxy configurations. REGMIX shows, through the stability analysis in Appendix F (Figure 14), that the instability was a property of DoReMi's online optimization algorithm, not of the proxy modeling paradigm itself. When mixture weights are extracted through regression rather than through training trajectory averaging, the predictions from 1M and 60M proxy models produce "remarkably similar" mixture distributions. This is an important reconciliation: it preserves the validity of using small models to inform large-model training decisions while correctly identifying the failure mode in prior work.

The paper also reshapes the conversation around **what data sources are considered valuable for pre-training**. The finding that validation loss on Pile-CC (CommonCrawl web data) has the strongest correlation with downstream performance — stronger than Wikipedia, stronger than books, stronger than academic papers — challenges a decade-long assumption that "curated, high-quality" sources are the best indicators of model quality. The practical manifestation of this finding is stark: simply training on 100% Pile-CC (no domain mixing at all) achieves 46.8 average downstream performance, tying DoReMi and substantially outperforming the human-designed Pile mixture (45.1). This does not mean that curated sources are useless — the REGMIX mixture supplements Pile-CC with small amounts of Ubuntu IRC, PubMed Abstracts, and other domains for a 0.5-point improvement over Pile-CC-only — but it does mean that the **default assumption should be web-data-heavy**, with other domains playing supplementary roles, rather than the balanced, "diverse" mixtures that human intuition has historically favored.

The field's research priorities should shift accordingly. The discovery that human-designed mixtures are systematically suboptimal (Section 5.4: domain interactions "often contradict intuition") makes manual data curation — the approach used for GPT-3, Gopher, and the original Pile release — increasingly difficult to justify for new datasets. Automated methods like REGMIX are not a luxury for efficiency enthusiasts; they are a necessity for correct allocation. Conversely, the finding that REGMIX does not benefit tasks whose performance does not scale with training data (Section 5.6, Appendix J: LogiQA, MultiRC, QQP show flat or declining scaling) suggests that data mixture optimization is not a universal lever. For capabilities that are fundamentally limited by architecture, pre-training objective, or absence of relevant data in any available domain, mixture optimization provides no traction. Research attention should therefore bifurcate: for tasks that scale, invest in mixture optimization; for tasks that do not, invest in data acquisition or architectural innovation.

### Follow-Up Research This Work Enables

**Cheap, continuous difficulty estimation for mixture space exploration.** The paper demonstrates that the regression model can predict mixture performance for 1,000,000 candidate mixtures in "less than 10 CPU seconds" (Section 3.3), but the initial training of 512 proxy models to fit that regression model is the dominant cost. A natural follow-up is to study **active learning for mixture space exploration**: rather than sampling mixtures randomly from a Dirichlet distribution, use the partially-trained regression model's uncertainty estimates to guide which mixtures to evaluate next. LightGBM provides natural uncertainty quantification through the variance of predictions across trees in the ensemble. A concrete experiment would start with 64 randomly sampled mixtures, fit an initial regression model, then iteratively select the next 64 mixtures that maximize expected improvement or upper confidence bound in the predicted performance, training proxy models on these mixtures and refitting the regression. The key metric would be whether active sampling reaches the same Spearman ρ with, say, 256 total proxy models that random sampling requires 512 — a 2× reduction in proxy training cost. This would make REGMIX more practical for very large domain counts where even parallel training becomes expensive.

**Multi-target mixture optimization with Pareto frontier analysis.** REGMIX currently optimizes for a single target metric — validation loss on Pile-CC — chosen because it correlates well with average downstream performance. But practitioners often care about multiple, potentially conflicting capabilities: code generation, mathematical reasoning, multilingual performance, factual accuracy. The paper's own results show that the Pile-CC-optimized mixture underperforms human selection on LogiQA (24.1 vs. 25.7 at 7B, 100B tokens), suggesting that optimizing for one capability can hurt others. A straightforward extension would fit a separate regression model for each target metric (using the same 512 proxy model training runs, just evaluating each proxy on multiple validation sets), then search the mixture space for Pareto-optimal mixtures that balance multiple objectives. The concrete experiment: fit regression models for Pile-CC loss, GitHub loss (as a proxy for code capability), and Wikipedia loss (as a proxy for factual accuracy); simulate 1,000,000 mixtures; compute the Pareto frontier; and train 1B-parameter models on 3-5 mixtures from different regions of the frontier to validate that the trade-offs are real and predictable. The key question is whether the regression models are accurate enough to predict trade-offs between capabilities, or whether the approximation error overwhelms the signal when optimizing for differences rather than absolute performance.

**Stress-testing the rank invariance hypothesis at the 7B-to-70B gap.** The paper validates rank invariance from 1M to 1B parameters (Table 2) and demonstrates end-to-end mixture transfer to 7B parameters (Appendix J). The open question is whether it holds at the 70B scale, where phenomena like in-context learning emergence, data quality thresholds, and regime changes in loss scaling have been documented. A targeted — though expensive — validation experiment: select the top 4 mixtures (including REGMIX and the Human baseline) from the 1B-parameter evaluation in Table 3, train 70B-parameter models on each for some non-trivial token budget (e.g., 200B tokens), and measure whether the ranking is preserved. A Spearman correlation substantially below 1.0 on just those 4 mixtures would be informative — it would establish a boundary on the scale at which proxy-based methods remain reliable. The compute cost is large but comparable to the cost of training a single 70B model checkpoint, making it feasible for well-resourced labs. A negative result (rank reversal at 70B) would be scientifically important: it would force the development of scale-aware mixture optimization methods and would caution against extrapolating REGMIX's recommendations to frontier scales without validation.

**Combining REGMIX with sample-level selection for two-stage data curation.** REGMIX operates at the group level: it determines how much weight each domain should receive. Completely orthogonal are sample-level selection methods (PPL, QuRating, DSIR) that filter individual examples within each domain for quality, relevance, or diversity. These are complementary axes: REGMIX says "train on 87% Pile-CC," while sample-level selection says "within Pile-CC, keep only the top 30% of samples by perplexity score." A natural integration experiment would apply perplexity filtering to each domain at varying thresholds (e.g., keep top 10%, 30%, 50%, 100% of samples), run REGMIX's proxy training on the filtered domains, and observe whether the optimal mixture weights change as filtering becomes more aggressive. The hypothesis to test: aggressive filtering of web data might reduce the need for supplementary domains (since filtering already removes noisy or redundant content), shifting the optimal mixture toward even more Pile-CC concentration. If confirmed, this would mean that data curation at the sample level and the group level are not independent decisions — they interact through the information content of each domain — and a joint optimization framework is needed.

**Transfer across model architectures and tokenizers.** The paper acknowledges (Appendix B) that REGMIX's mixture recommendations depend on the tokenizer and model architecture used for proxy training, but provides no empirical measurement of this sensitivity. A straightforward experiment: train the 512 × 1M proxy models with two different tokenizers (GPTNeoX and Llama tokenizer) on the same domain splits, fit separate regression models, and compare the predicted optimal mixtures. If the mixtures agree (e.g., both recommend >80% Pile-CC with similar supplementary domains), the tokenizer sensitivity is low and the paper's specific recommendations are more generalizable. If they disagree substantially, practitioners using non-GPTNeoX tokenizers must re-run REGMIX from scratch, which substantially increases the adoption cost. A second dimension: train proxy models with different architectural choices (e.g., varying the attention mechanism or the ratio of MLP to attention layers) at fixed 1M parameter count to test whether architecture affects mixture optimality. This experiment is cheap (1M models) and directly addresses a stated limitation.

**Understanding why the REGMIX mixture works: feature importance and interaction decomposition.** The paper provides the final mixture (Table 7: 87% Pile-CC, 6.4% Ubuntu IRC, etc.) and demonstrates it outperforms baselines, but does not analyze *why* these specific domains and weights are recommended. LightGBM provides feature importance scores (gain-based and split-based) that could identify which domains contribute most to the model's predictions. SHAP values could decompose each prediction into additive contributions from each domain, potentially explaining, for example, why GitHub and Stack Exchange receive zero weight despite being large, seemingly valuable domains. A concrete analysis would: compute SHAP values for the top 100 predicted mixtures, identify which domains consistently receive negative SHAP values (meaning they hurt predicted performance) and which receive positive, and cross-reference these with the linear model's coefficients (Figure 7) to understand where the linear and non-linear models agree and diverge. This would transform REGMIX from a black-box optimizer into a diagnostic tool that tells practitioners not just *what* mixture to use, but *why* certain domains are beneficial or harmful — enabling data curation decisions like whether to collect more data from a helpful domain or improve filtering on a harmful one.

### Practical Applications and Downstream Use Cases

**Cost-efficient pre-training for academic and mid-scale industrial labs.** The most direct application is enabling organizations with moderate compute budgets — academic groups, startups, research labs without thousands of GPUs — to optimize their pre-training data mixtures without the computational overhead of prior methods. Training 512 × 1M models on 1B tokens each costs approximately 3.5 × 10¹⁸ FLOPs (Table 4), which is roughly 2% of training a single 1B model or less than 0.1% of training a 7B model on 100B tokens. On a single 8×A100 node, this proxy training can be completed in hours (the models are tiny) with the parallelism benefits of training multiple models simultaneously. The practical workflow: a team preparing to train a 7B model on a new domain taxonomy (e.g., multilingual data, domain-specific corpora) runs REGMIX on their specific data distribution, obtains an optimized mixture, and trains the large model once — rather than training multiple large models with different mixtures or relying on intuition. The 50% pre-training acceleration observed on HellaSwag (Figure 1: REGMIX at 50B tokens matches Human at 100B tokens) means that the cost savings from reduced training time can be 10-50× the cost of running REGMIX itself.

**Automated data mixture selection for continuously updated web-scale datasets.** Modern pre-training datasets like FineWeb (Penedo et al., 2024b) and DCLM (Li et al., 2024) are continuously updated as new web crawls become available, domain quality shifts, and copyright considerations change. Manual mixture rebalancing for each new release is infeasible. REGMIX can be integrated into the dataset release pipeline: when a new crawl is processed and domains are defined (by URL, topic cluster, or quality tier), train a batch of small proxy models on the updated data, refit the regression model, and release the recommended mixture alongside the dataset. The paper's 100-domain experiment (Section 5.6, Table 5: LightGBM ρ = 98.80 on 60M models) demonstrates that this scales to fine-grained domain taxonomies. The incremental cost per dataset release is modest — 1,000 × 1M proxy models is still well under 1% of the cost of training a frontier model — and the benefit is a perpetually optimized mixture that adapts to data distribution shifts without human intervention.

**Diagnostic tool for data quality and domain interaction analysis.** Beyond optimization, REGMIX's regression models — particularly the interpretable linear model — can serve as a diagnostic instrument for understanding data composition. The domain interaction visualization in Figure 7 is a concrete example: it reveals that PhilPapers (a tiny philosophy corpus) has a surprisingly beneficial effect on most target domains' validation losses, while some large domains show weak or negative correlations with downstream-relevant metrics. A data curator could use this analysis to identify: which domains are redundant (providing no unique information beyond what other domains already cover), which domains are complementary (providing signal that no other domain duplicates), and which domains might be actively harmful (increasing loss on important target metrics). This diagnosis can inform data collection priorities — if PubMed Abstracts shows strong positive coefficients, collecting more biomedical text might be high-value; if a domain shows zero or negative contributions, resources spent curating it might be better allocated elsewhere. The analysis is essentially free once the proxy models are trained, since the linear regression coefficients are a byproduct of the optimization pipeline.
