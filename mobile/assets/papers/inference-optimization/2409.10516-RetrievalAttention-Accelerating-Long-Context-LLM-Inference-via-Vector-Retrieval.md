# RetrievalAttention: Accelerating Long-Context LLM Inference via Vector Retrieval

**ArXiv:** [2409.10516](https://arxiv.org/abs/2409.10516)

## 🎯 Pitch

Existing approximate nearest neighbor search breaks down for attention because query vectors sit >10× farther from keys than any key is from another—standard indexes collapse. RetrievalAttention fixes this with an attention-aware search algorithm that adapts to query distributions, serving 128K-token Llama-3-8B on a single 24GB RTX4090 at 0.188 seconds per token with no accuracy loss.

---

## 1. Executive Summary

This paper proposes **RetrievalAttention**, a training-free method that accelerates long-context LLM inference and reduces GPU memory consumption by offloading the majority of key-value (KV) vectors to CPU memory, building approximate nearest neighbor search (ANNS) indexes, and retrieving only the most relevant tokens via vector search during generation. Evaluated on Llama-3-8B, Yi-6B, and Yi-9B across ∞-Bench, RULER, and Needle-in-a-Haystack, RetrievalAttention addresses a newly identified out-of-distribution (OOD) challenge between query and key vectors—conventional ANNS indexes fail because query vectors deviate more than 10× farther from key vectors than in-distribution key vectors do—by designing an attention-aware vector search algorithm that adapts to query vector distributions. RetrievalAttention achieves near full-attention accuracy while scanning only 1–3% of key vectors, yielding a 4.9× decoding-latency reduction over exact KNN and 1.98× over traditional ANNS (IVF) at 128K context on an RTX4090, and is the first system to serve 8B-parameter models with 128K tokens on a single 24GB GPU with acceptable latency and no accuracy degradation.

## 2. Context and Motivation

### The Core Problem: Long-Context Inference Is Prohibitively Expensive

The fundamental challenge this paper tackles is that serving transformer-based LLMs with long context windows incurs costs that are **simultaneously impractical for commodity hardware and expensive at scale**. The paper's Table 1 quantifies this with stark numbers: running Llama-3-8B on a 128K-token prompt without KV caching takes 32.8 seconds per generated token, scaling to a staggering 1,765 seconds (~29 minutes) at 1M tokens. Over 96% of that latency is in the attention operation itself.

But adding KV caching—the standard optimization that avoids recomputing past key-value states—doesn't solve the problem; it trades latency for memory. The same table shows that storing the KV cache for 1M tokens requires 125 GB of memory *just for the cache*, far exceeding a commodity RTX4090 (24 GB) or even a high-end A100 (40–80 GB). The paper frames this as a **dual bottleneck** in Section 2.2:

> "KV caching-based systems face two primary issues: (a) substantial GPU memory requirements, particularly for long contexts... and (b) inference latency increases linearly to the context size, primarily due to the time needed to access cached tokens"

This is not merely an engineering inconvenience. It forces practitioners into two unpalatable choices: scale to multiple GPUs (increasing cost and complexity) or offload the entire KV cache between CPU and GPU over PCIe on every token generation step (as FlexGen does; Sheng et al., 2023), which the paper describes as incurring "excessive communication overhead." Neither approach makes long-context inference accessible on affordable hardware, and both become bottlenecks as context windows grow toward the million-token regimes that flagship models like Gemini 1.5 Pro already support.

### A Promising Observation: Attention Is Dynamically Sparse

The paper builds on an empirical insight that recent work has converged on: attention computation in LLMs exhibits **dynamic sparsity**. Despite large context lengths, each query vector meaningfully interacts with only a small fraction of all key-value vectors. The paper verifies this rigorously in Section 2.3 by profiling the *recovery ratio*—the cumulative sum of attention scores captured by the top-k critical tokens—across all layers and heads of Llama-3-8B on a 100K-token prompt. With the top-1000 tokens (1% of the context), most attention heads recover over 90% of the full attention mass, averaging 89% across all heads (Figure 2, blue curve).

The word *dynamic* is essential here. Tokens that are critical for one query may be irrelevant for the next. The paper demonstrates this by taking the top-1000 tokens identified during the first decoding step and reusing them statically for subsequent tokens. The average recovery ratio drops from 89% to 71% (Figure 2, orange curve). This means that **any method which pre-selects tokens based on a fixed heuristic will necessarily miss tokens that become critical later in generation**—a finding that directly indicts the static pattern methods discussed below.

This dynamic sparsity suggests an attractive path forward: if we can *dynamically* identify which tokens are critical for each new query, we can compute approximate attention over only those tokens, dramatically reducing both memory access and computation while preserving accuracy. The question is how to do that identification efficiently.

### Where Existing Approaches Fall Short

The paper evaluates and categorizes prior work into several families, each with specific failures that motivate RetrievalAttention's design.

**Static KV compression methods** (StreamingLLM, SnapKV, H2O) keep a fixed subset of tokens—typically initial tokens plus a sliding window of recent tokens—and discard the rest. StreamingLLM is the canonical example: it retains the first few tokens (identified as "attention sinks") and the most recent tokens, permanently dropping everything in between. The paper's evaluation reveals that this causes catastrophic accuracy degradation on tasks requiring retrieval of non-local information. On ∞-Bench, StreamingLLM achieves an average accuracy of 20.2% versus 50.4% for full attention on Llama-3-8B—a 30.2 percentage-point drop (Table 2). On the retrieval-heavy tasks (number retrieval and passKey retrieval), it collapses to 5.0% accuracy. The Needle-in-a-Haystack results in Appendix A.2 (Figure 7) visually confirm this: StreamingLLM can only locate the needle when it falls within the perpetual static window. This is the expected failure mode: static pruning is fundamentally incompatible with tasks where critical information can appear anywhere in the context and relevance shifts dynamically across queries.

SnapKV performs better than StreamingLLM by selecting tokens based on attention patterns observed during the prefill phase, but the paper still reports a 2.2 percentage-point average drop on ∞-Bench and a 12.76 point drop on RULER for Llama-3-8B. On the harder KV retrieval task, SnapKV achieves only 0.5% accuracy—essentially zero—because prefill-phase attention patterns don't capture what tokens will become important during generation.

**Block-based dynamic retrieval methods** (InfLLM, Quest) partition the KV cache into contiguous blocks, select representative vectors per block, and then retrieve blocks whose representatives score highly against the current query. This is more dynamic than static methods, but the paper identifies a fundamental accuracy limitation: the quality of the retrieval depends entirely on how well a single representative vector captures the information content of its entire block. The paper reports that these methods "achieve nearly zero accuracy in complex tasks (i.e., KV retrieval) due to the low accuracy of representative vectors" (Section 4.2). On ∞-Bench's KV retrieval task, InfLLM achieves 0.5% and Quest achieves 0.0% on Llama-3-8B. On RULER (Table 3), InfLLM shows catastrophic degradation as context length grows, falling from 85.2% at 4K to 25.7% at 128K—a drop of nearly 60 percentage points.

The problem is granularity: when a single representative stands in for many tokens, many of those tokens are genuinely irrelevant to the representative's score, and the ones that *are* relevant to the current query may be lost in the averaging. The paper frames this as a precision-recall tradeoff that block-based methods resolve in favor of efficiency at the cost of accuracy on any task where critical tokens are sparsely distributed or depend on fine-grained content matching.

**Channel-dimension reduction methods** (SparQ, InfiniGen, LoKi) approximate the top-k key vectors by reducing the hidden dimension before computing attention scores. InfiniGen additionally speculates important tokens for subsequent layers based on layer-to-layer attention score correlation. The paper's evaluation of InfiniGen on RULER (Table 9 in Appendix E) shows a drop from 78.7% to 43.1% average accuracy at 128K context on Llama-3-8B, with particularly poor performance on complex multi-hop tasks (25.0% and 0.0% on the two harder tracing tasks). The paper attributes this to "inaccurate speculation of important tokens from previous layers"—the cross-layer correlation is too weak to reliably identify which tokens will matter in deeper attention heads.

**Full KV cache offloading** (FlexGen) moves all KV vectors to CPU memory and reloads them for attention computation on each step. This solves the GPU memory problem but does nothing to reduce the *amount* of computation—it still performs full attention over all tokens. The PCIe transfer cost of moving the entire KV cache per token makes this approach prohibitively slow for interactive applications, and the paper describes it as an "inefficient and cost-effective solution for long-context inference on commodity GPUs" (Section 2.2).

### A Missed Opportunity: Why Not Just Use Vector Search Directly?

The most natural solution to dynamic sparse attention—one that the paper argues has been overlooked—is to use approximate nearest neighbor search (ANNS) indexes. The reasoning is straightforward and elegant (Section 2.4): attention scores are computed as the scaled dot product between query and key vectors, which is precisely an inner-product similarity measure. If we build an ANNS index over the key vectors using inner product as the similarity function, we can query it with each new query vector to find the top-k most similar keys in sub-linear time. This directly identifies the "critical tokens" for attention without heuristic approximations, block-based granularity losses, or channel-dimension reductions.

However, the paper demonstrates—and this is one of its key contributions—that **naïvely applying off-the-shelf ANNS indexes fails dramatically** due to a distribution mismatch that no prior work had identified in the context of attention computation. This is the OOD problem discussed in Section 2.4 and quantified in Figure 3.

**The OOD problem concretely.** ANNS indexes are designed under the assumption that query vectors and indexed vectors are drawn from the same distribution—both are typically outputs of the same embedding model in information retrieval or recommendation systems. In the attention mechanism, however, queries and keys are projected through different weight matrices ($W_Q$ vs. $W_K$), producing fundamentally different vector distributions even though they operate over the same input representation. The paper uses Mahalanobis distance (Figure 3b) to quantify this: query (Q) vectors are more than 10× farther from the key (K) vector distribution than in-distribution key vectors are from each other.

The practical consequence is shown in Figure 3a. When traditional indexes are queried with Q vectors (the "Q to K" case), cluster-based IVF requires scanning ~30–50% of all key vectors to reach a recall above 0.95—far from the 1% scanning rate needed for meaningful speedup. Graph-based HNSW actually falls into local optima and fails to reach high recall at any scanning rate. The fundamental problem is that indexes built solely on key-key similarity (how close keys are to each other) don't reflect query-key relevance, because the query distribution sits in a different region of the embedding space.

Critically, the paper shows this is *not* an inherent limitation of ANNS—it's specific to the distribution mismatch. When the index is queried with sampled key vectors instead of query vectors (the "K to K" case in Figure 3a), all indexes easily achieve >0.95 recall at 1–5% scanning rates, because the query and indexed vectors now share the same distribution. This demonstrates that the challenge is not the vector search problem itself, but the **cross-distribution nature** of query-key matching in attention.

### The Need for Distribution-Aware Retrieval

The failure of block-based methods on fine-grained retrieval tasks, the collapse of static methods on non-local information, and the inefficiency of traditional ANNS under distribution mismatch collectively point to a specific gap: **there is no method that dynamically retrieves the most relevant tokens for each query at the fine granularity of individual KV vectors, while accounting for the distribution gap between queries and keys, and doing so with minimal data access.**

This gap matters because the scaling trend is toward longer contexts—Gemini 1.5 Pro's 10M-token window is the headline example—but the hardware to serve these models cost-effectively is not keeping pace. Without a method that achieves the trifecta of (1) high accuracy on complex retrieval tasks, (2) minimal GPU memory footprint, and (3) low-latency dynamic retrieval, long-context LLM inference will remain confined to expensive multi-GPU deployments or suffer unacceptable quality degradation.

### How RetrievalAttention Positions Itself

The paper frames RetrievalAttention as the first method to directly solve the cross-distribution ANNS problem for attention. Rather than avoiding vector search due to the OOD issue, it redesigns the index to be **attention-aware**—built not from the perspective of key-key similarity (the traditional approach) but from the perspective of query-key relevance (Section 3.2). The core technical innovation is leveraging the query vectors available during the prefill phase to construct the index, explicitly modeling how queries "see" keys as similar or dissimilar, and projecting those relationships into the key-key index structure so that future decoding queries can efficiently traverse to the right keys despite the distribution gap.

Positioning relative to prior methods is explicit throughout the paper:

- **Versus static methods** (StreamingLLM, SnapKV): RetrievalAttention uses exponentially more context information through dynamic retrieval rather than fixed heuristics, enabling high accuracy on retrieval-intensive tasks.
- **Versus block-based methods** (InfLLM, Quest): RetrievalAttention operates at token granularity via ANNS rather than coarse block-level representatives, eliminating the information loss from block averaging.
- **Versus channel-dimension methods** (SparQ, InfiniGen): RetrievalAttention uses full-dimensionality key vectors with a learned index structure rather than low-rank approximations, avoiding speculation errors.
- **Versus full offloading** (FlexGen): RetrievalAttention retrieves only 1–3% of tokens rather than the entire cache, dramatically reducing PCIe transfer and computation.
- **Versus naïve ANNS**: RetrievalAttention specifically addresses the Q-K distribution gap that makes off-the-shelf indexes (IVF, HNSW) ineffective, achieving the same high recall at a small fraction of the data access cost.

A crucial design choice that reflects the paper's practical orientation: RetrievalAttention is **training-free**. It requires no fine-tuning of the base LLM, no modification to model weights, and no architectural changes. It operates purely at the inference-system level by reorganizing how KV vectors are stored and accessed. This means it can be applied to any pretrained transformer model out of the box—a significant practical advantage over methods that require retraining with sparse attention patterns or learned token selectors.

The paper also adopts a pragmatic CPU-GPU co-execution architecture (Section 3.3) that explicitly acknowledges deployment constraints: GPU memory is scarce and expensive; CPU memory is abundant and cheap. By offloading the bulk of KV vectors to CPU, building indexes there, and only keeping a small predictable subset on GPU, RetrievalAttention makes long-context inference feasible on a single commodity GPU. The paper's headline result—serving an 8B model with 128K tokens on a single RTX4090 (24 GB) at 0.188 seconds per token—is positioned as a first-of-its-kind capability that directly addresses the hardware accessibility gap the paper opens with.

## 3. Technical Approach

### 3.1 Reader Orientation (Approachable Technical Breakdown)

RetrievalAttention is a **training-free inference system** that acts as a drop-in replacement for the standard attention mechanism in transformer-based LLMs, reorganizing how key-value (KV) vectors are stored and accessed during token generation. It solves the problem that serving long-context LLMs on commodity GPUs is either impossibly memory-intensive (the KV cache for 1M tokens requires 125 GB) or painfully slow (recomputing full attention over 1M tokens takes ~30 minutes per token), by observing that attention is dynamically sparse—each query only cares about 1–3% of all tokens—and building a CPU-side vector index that finds exactly those critical tokens without ever loading the full KV cache into GPU memory.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has six major components that operate across CPU and GPU, with information flowing in a specific sequence during each token generation step:

1. **Base LLM (on GPU)** — The pretrained transformer model (e.g., Llama-3-8B) that generates one new token at a time and produces query vectors for each attention head. It is completely unmodified.

2. **Static GPU KV Cache** — A small, permanently resident subset of KV vectors kept in GPU memory, selected based on predictable patterns observed during prefill (initial tokens plus a sliding window of recent tokens). These are the tokens that are consistently important regardless of the current query.

3. **CPU Vector Indexes (one per attention head)** — The bulk of KV vectors offloaded from GPU to CPU memory, organized into approximate nearest neighbor search (ANNS) indexes built using an attention-aware construction algorithm. These indexes are queried with each new query vector during decoding to find the most relevant KV vectors dynamically.

4. **Attention-Aware Index Builder** — A prefill-phase procedure that constructs the CPU indexes not from key-key similarity (the traditional approach) but from query-key relevance, using the query vectors computed during prefill to establish KNN connections and project them into a key-key graph structure.

5. **Parallel CPU-GPU Attention Engines** — During each decoding step, the GPU computes partial attention over the static KV cache (using FlashAttention) while the CPU simultaneously searches its indexes to retrieve the dynamically relevant KV vectors and computes partial attention over them.

6. **Attention Combiner** — A mathematically exact procedure that merges the two partial attention outputs (GPU side and CPU side) into a single attention output that is identical to what full attention would have produced over the union of the static and dynamically retrieved tokens.

**Information flow per decoding step**: The LLM produces a query vector → the query is dispatched simultaneously to GPU FlashAttention over static tokens and to CPU vector search over indexes → CPU retrieves the top-k most relevant KV vectors → CPU computes attention over retrieved tokens using its own implementation → both partial results are merged using re-normalization factors → the combined output feeds into the next transformer layer.

### 3.3 Roadmap for the Deep Dive

- **First**, the **approximated attention formulation** (Equation 2)—the mathematical justification for why we can ignore most tokens, what subset we keep, and how the approximation is structured. This defines the correctness target that everything else must satisfy.

- **Second**, the **Attention-Aware Vector Search algorithm**—how the index is built during prefill to handle the query-key distribution mismatch, why traditional ANNS fails, and the specific operations (KNN connection, projection) that make the index query-aware. This is the core technical innovation.

- **Third**, the **CPU-GPU Co-Execution strategy**—how the system partitions KV vectors between GPU static cache and CPU indexes, how partial attention results are combined using re-normalization factors (Equations 4 and 5), and the parallel execution model. This is where the system design meets hardware constraints.

- **Fourth**, the **implementation optimizations** that make the system practical: multi-head parallelism on CPU, memory minimization via pointer sharing, prefill-phase overlap, and quantization plans.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems paper** whose core technical contribution is an **attention-aware ANNS index construction algorithm** that solves the out-of-distribution problem between query and key vectors, combined with a **CPU-GPU co-execution architecture** that makes long-context inference feasible on a single commodity GPU without model modification.

#### Approximated Attention Formulation

The paper begins by formalizing what it means to compute "approximate attention" in a way that is both computationally cheaper and mathematically principled. The key insight is that the softmax operation in standard attention is dominated by a small number of large dot products—most tokens contribute negligibly. This justifies discarding tokens with attention scores below a threshold, but the threshold must be chosen carefully so that the remaining tokens collectively capture nearly all of the attention mass.

The paper defines `$I_{t,\epsilon}$` as the subset of token indices for which the attention score (before softmax) exceeds a threshold `$\epsilon$`. The standard full attention output is:

$$o_t = \sum_{i \in I_{t,\epsilon}} a_{t,i} \cdot v_i + \sum_{i \notin I_{t,\epsilon}} a_{t,i} \cdot v_i$$

where `$a_{t,i}$` is the post-softmax attention score for token `$i$` given query at position `$t$`, and `$v_i$` is the value vector for token `$i$`. The first sum runs over tokens deemed important enough to keep; the second sum runs over tokens to discard.

**The core approximation** discards the second sum entirely (treating it as approximately zero) and re-normalizes the attention scores over only the kept tokens:

$$o_t \approx \sum_{i \in I_{t,\epsilon}} \tilde{a}_{t,i} \cdot v_i \quad \text{where} \quad \tilde{a}_{t,i} = \frac{e^{z_i}}{\sum_{j \in I_{t,\epsilon}} e^{z_j}}$$

and where `$z_i = \frac{q_t \cdot k_i^T}{\sqrt{d}}$` is the raw pre-softmax attention score (logit) for token `$i$`, with `$q_t$` being the current query vector, `$k_i$` the key vector, and `$d$` the hidden dimension.

**What it computes:** For each query, instead of attending over all `$t$` tokens, we attend only over the subset `$I_{t,\epsilon}$` and re-normalize the softmax over that subset. The output `$o_t$` is a weighted sum of value vectors where the weights sum to 1 by construction (because `$\tilde{a}_{t,i}$` is a proper softmax over the subset). Discarded tokens are implicitly assigned zero attention weight.

**Why this form:** The re-normalization is crucial—without it, simply summing over a subset without re-weighting would systematically underestimate the attention output magnitude, because discarded tokens carry some (small) positive attention mass. The re-normalized softmax `$\tilde{a}_{t,i}$` redistributes the discarded mass proportionally among the kept tokens, maintaining the property that `$\sum_i \tilde{a}_{t,i} = 1$`. This is the same mathematical technique used in FlashAttention's tiling strategy, and it means that if `$I_{t,\epsilon}$` captures most of the attention mass, the approximation error is bounded. The paper's empirical validation (Figure 2) shows that with top-1000 tokens, the recovery ratio averages 89% across all heads, meaning the discarded sum genuinely is small for appropriately chosen `$I_{t,\epsilon}$`.

The operational significance is that RetrievalAttention only needs to find `$I_{t,\epsilon}$`—the set of token indices with sufficiently high attention scores—for each query, rather than computing attention scores for all tokens. The problem reduces to **efficiently identifying which tokens will have the largest dot products with the current query**, which is precisely what ANNS solves.

#### Attention-Aware Vector Search: The Core Innovation

This is the paper's primary technical contribution. The challenge is that standard ANNS indexes are built around the assumption that query and indexed vectors come from the same distribution, but in attention, queries and keys are projected through different weight matrices (`$W_Q$` vs. `$W_K$`), creating a distribution gap. Section 2.4 quantifies this: Mahalanobis distance shows query vectors are more than 10× farther from the key vector distribution than in-distribution key vectors are from each other.

**How traditional ANNS works and why it fails for Q-to-K search.** Standard ANNS indexes operate by exploiting the triangle inequality in vector space. Cluster-based methods like IVF (Sivic & Zisserman, 2003) partition the vector space into clusters (via k-means), select a representative centroid for each cluster, and during search, the query first compares against all centroids to select the most promising clusters, then scans only vectors within those clusters. Graph-based methods like HNSW (Malkov & Yashunin, 2018) build a navigable graph where each vector is connected to its nearest neighbors; during search, the query performs a greedy walk, moving from node to node toward higher-similarity regions.

Both methods fundamentally rely on a property that breaks under distribution shift: **vectors that are close to the same reference vectors (centroids or graph neighbors) should be similar to each other**. When the query distribution is far from the key distribution, a query landing near a particular cluster centroid does not guarantee that the keys in that cluster are the ones with the highest dot products—the query's "nearness" is measured in a coordinate system that the index doesn't understand.

The paper's Figure 3a demonstrates this concretely. IVF requires scanning ~30–50% of all keys to reach a recall of 0.95 for Q-to-K search. HNSW falls into local optima—the greedy graph walk gets stuck because the edges were built based on key-key similarity, not query-key relevance, so following "nearest" edges doesn't lead toward the true top-scoring keys. In contrast, when sampled keys are used as queries (K-to-K search, same distribution), all indexes achieve >0.95 recall at 1–5% scanning.

**The attention-aware index construction algorithm.** The solution is to use the query vectors available during the prefill phase—where full attention is computed anyway—to build an index structure that encodes **how queries perceive key similarity**. The algorithm has four stages:

**Stage 1: Exact KNN from queries to keys (Figure 4b).** During the prefill phase, the LLM computes full attention for all prompt tokens, which means we have a complete set of query vectors `$q_1, q_2, \ldots, q_n$` and key vectors `$k_1, k_2, \ldots, k_n$` for every attention head. For each query vector `$q_i$`, we compute its exact top-`$k$` nearest key vectors using GPU-accelerated matrix multiplication (the same computation that produces the attention scores during prefill). This establishes a **directed mapping** from the query distribution to the key distribution: for every query, we know exactly which keys it considers most similar.

The result is a set of KNN connections: each query `$q_i$` is linked to its `$k$` nearest keys `$k_{i,1}, k_{i,2}, \ldots, k_{i,k}$`. These connections are exact (not approximate) because they're computed with full attention during prefill.

**Stage 2: Project KNN connections into key-key graph.** The KNN connections from Stage 1 are a heterogeneous bipartite graph: queries connected to keys. For efficient search at decoding time, we need a homogeneous graph that can be traversed entirely in key-space, because decoding query vectors are what we want to search with, and we don't want to store or traverse the prefill query vectors. The paper leverages the projection technique from RoarGraph (Chen et al., 2024a), a state-of-the-art cross-modal ANNS index.

The projection works as follows: if two key vectors `$k_a$` and `$k_b$` are both connected to the same query vector `$q_i$` (i.e., both are in `$q_i$`'s top-`$k$` KNN set), then `$k_a$` and `$k_b$` should be considered **neighbors in key-space from the query's perspective**. Even though `$k_a$` and `$k_b$` might be far apart in the key distribution's own metric, they are both relevant to the same queries, so they should be connected in the index graph. The projection creates edges between every pair of keys that share at least one query in their KNN connection sets.

This is the mechanism that reconciles the distribution gap. Instead of connecting keys based on key-key inner products (which would cluster keys that are distributionally similar but potentially irrelevant to queries), the projection connects keys based on **co-occurrence in query KNN sets**—a query-centric notion of similarity. If two keys are often both relevant to the same set of queries, they get connected, regardless of how far apart they are in the raw key embedding space.

**Stage 3: Eliminate query vectors.** After projection, the index structure consists entirely of key vectors connected by edges. The prefill query vectors are no longer needed for search—they served their purpose as a training set for establishing query-key relevance patterns. The resulting graph is a standard ANNS graph (similar to HNSW) but with edges that encode query-aware similarity.

**Stage 4: Decoding-time search.** During token generation, a new query vector `$q_t$` arrives. The search algorithm performs a greedy walk over the query-aware key graph: starting from an entry point (typically the key vector connected to the most queries during prefill, or a random seed), the query computes its inner product with the current node's neighbors, moves to the neighbor with the highest score, and repeats until no neighbor scores higher than the current best. Because the graph edges were built from query-key relevance patterns, following high-similarity edges actually leads toward keys that are genuinely relevant to the query, avoiding the local optima that trap standard HNSW.

The paper's Figure 6 demonstrates the result: RetrievalAttention's attention-aware index achieves >0.95 recall at 1–3% scanning across all three models (Yi-6B, Yi-9B, Llama-3-8B), matching the performance of the in-distribution K-to-K search. The traditional IVF index requires ~30–50% scanning, and HNSW never reaches high recall at all. The efficiency gain—74% reduction in index search latency compared to IVF—comes directly from scanning dramatically fewer vectors.

**Design choice: why KNN projection rather than alternative OOD solutions?** The paper considers and rejects several alternatives. Fine-tuning the base model to bring query and key distributions closer would violate the training-free constraint and might affect model quality. Learning a transformation matrix to map queries into key-space would require training data and add inference overhead. Using the PRM800k-like approach of collecting human labels for query-key relevance is infeasible—there are billions of query-key pairs across all heads and layers. The KNN projection approach is appealing because it is **unsupervised, training-free, and leverages computation that already happens during prefill** (full attention produces the KNN results as a byproduct). The only cost is the projection step itself, which is a one-time graph construction operation.

**Design choice: why per-head indexes?** The paper explicitly builds one vector index per attention head (Appendix C), even for models with Grouped Query Attention (GQA) where multiple query heads share the same key-value vectors. The justification is that "the query vectors from different query heads in the same group exhibit different vector distributions"—each query head has its own `$W_Q$` projection, so the Q-K distribution gap is head-specific. A single index shared across heads would have to accommodate multiple query distributions simultaneously, which would degrade recall for all of them. The cost of per-head indexes is mitigated by sharing KV vector storage (see implementation optimizations below).

#### CPU-GPU Co-Execution Strategy

Having solved the problem of efficiently finding critical tokens, the paper now addresses the hardware architecture: how to split work between GPU and CPU to maximize throughput while minimizing GPU memory.

**Token partitioning: predictable vs. dynamic.** The system divides all KV vectors into two disjoint sets (Equation 3):

$$I_{t,\epsilon} = W \cup \Omega$$

where `$W$` (GPU-resident) is the set of **predictable active tokens**—tokens that are consistently important across all decoding steps regardless of the specific query—and `$\Omega$` (CPU-resident, dynamically retrieved) is the set of tokens whose importance varies with the query and must be found via vector search.

**The predictable pattern.** The paper adopts the pattern from StreamingLLM (Xiao et al., 2024b): the first few tokens of the sequence (initial tokens, typically 128) plus the most recent tokens in a sliding window (typically 512). Initial tokens have been shown to act as "attention sinks"—the model learns to deposit excess attention mass on them, making them universally high-scoring. Recent tokens are important because of local context dependencies. The paper states:

> "RetrievalAttention can be adapted to utilize more complex static patterns (Li et al., 2024; Jiang et al., 2024), achieving the best trade-off between low inference cost and high accuracy" (Section 3.3)

The current implementation uses a fixed 640 tokens on GPU (128 initial + 512 local window). Everything else—potentially tens of thousands of tokens—is offloaded to CPU and indexed. During the prefill phase, these two sets are physically separated: `$W$` tokens are flagged for GPU persistence; all other tokens are moved to CPU for index construction.

**Why this split?** If all tokens were retrieved dynamically, the CPU index search would be slower (more data to partition and index) and the GPU would be underutilized during the static token attention computation. If all tokens were on GPU, we'd hit the memory limit immediately. The hybrid approach balances GPU memory savings (only 640 tokens of KV cache on GPU) with search efficiency (the CPU only searches for the genuinely dynamic tokens) and accuracy (the universally important tokens are always attended to, regardless of index recall).

**Parallel partial attention computation.** During each decoding step, two partial attention computations happen simultaneously:

**GPU side:** FlashAttention (Dao et al., 2022) computes exact attention over the static GPU-resident tokens `$W$`:

$$o_W = \frac{\sum_{i \in W} e^{z_i - \tilde{z}_1} \cdot v_i}{\sum_{i \in W} e^{z_i - \tilde{z}_1}}$$

where `$\tilde{z}_1 = \max_{i \in W} z_i$` is the maximum pre-softmax score within `$W$`, used for numerical stability (standard softmax trick).

**CPU side:** The attention-aware vector index is queried with `$q_t$` to retrieve a dynamic set `$\Omega$` of the top-k most relevant key vectors (typically k=100 for most tasks, k=2000 for complex KV retrieval). The CPU then computes attention over these retrieved vectors:

$$o_\Omega = \frac{\sum_{i \in \Omega} e^{z_i - \tilde{z}_2} \cdot v_i}{\sum_{i \in \Omega} e^{z_i - \tilde{z}_2}}$$

where `$\tilde{z}_2 = \max_{i \in \Omega} z_i$` is the local maximum within `$\Omega$`.

**Why compute partial attention in two places rather than moving all data to one device?** Moving the CPU-retrieved KV vectors to GPU over PCIe for attention computation would add transfer latency. Computing attention on CPU for the retrieved subset and then only transferring the final output vector (much smaller) minimizes PCIe traffic. The GPU remains busy with FlashAttention over the static tokens, so the CPU computation overlaps with useful GPU work.

**Combining partial attention outputs (Equations 4 and 5).** The two partial attention outputs `$o_W$` and `$o_\Omega$` cannot simply be averaged or summed—they are computed over different sets of tokens with different local softmax normalizations. The combination must produce the **exact same output** as if attention had been computed over `$W \cup \Omega$` in one shot. The paper uses the FlashAttention-inspired re-scaling:

$$o_t = \gamma_1 \cdot o_W + \gamma_2 \cdot o_\Omega$$

where `$\gamma_1$` and `$\gamma_2$` are re-normalization factors that account for the different local maxima used in each partial softmax and the total attention mass in each subset:

$$\gamma_1 = e^{\tilde{z}_1 - \tilde{z}} \cdot \frac{\sum_{i \in W} e^{z_i - \tilde{z}_1}}{\sum_{i \in I_{t,\epsilon}} e^{z_i - \tilde{z}}}$$

$$\gamma_2 = e^{\tilde{z}_2 - \tilde{z}} \cdot \frac{\sum_{i \in \Omega} e^{z_i - \tilde{z}_2}}{\sum_{i \in I_{t,\epsilon}} e^{z_i - \tilde{z}}}$$

where `$\tilde{z} = \max_{i \in I_{t,\epsilon}} z_i$` is the global maximum over the complete set `$I_{t,\epsilon} = W \cup \Omega$`.

**What these equations compute:** Each partial attention output `$o_W$` and `$o_\Omega$` was computed with a different numerical-stability offset (`$\tilde{z}_1$` vs. `$\tilde{z}_2$`). The combination factors first undo the local offset (`$e^{\tilde{z}_1 - \tilde{z}}$` shifts `$o_W$` back to the global scale), then weight each partial output by the proportion of total attention mass it carries (the fraction of the global softmax denominator contributed by each subset). The result is mathematically identical to computing attention over the full set `$W \cup \Omega$` with a single softmax.

**Why this form:** Directly computing global softmax would require knowing the sum of `$e^{z_i}$` over all tokens, which requires scanning all tokens—exactly what we're trying to avoid. The two-stage computation with re-scaling factors allows us to limit scanning to only the tokens in `$W \cup \Omega$` (640 + k, where k is small) and combine results post-hoc. This is a standard divide-and-conquer pattern for the softmax function, exploiting its decomposability: the global softmax can be reconstructed from partial softmaxes if we know each subset's local maximum and local sum.

The full algorithm is presented as Algorithm 1 in Appendix B, which shows the complete execution flow including the active-token prediction step, the CPU-GPU data movement (lines 1-5), the parallel attention computations (lines 6-8), and the combination step (line 9).

#### Implementation Optimizations

The paper describes several implementation-level optimizations (Appendix C) that make the system practical at scale.

**Prefill-phase overlap.** During prefill, the GPU computes full attention for all layers while simultaneously moving KV vectors to CPU for index construction. These operations are pipelined: as each layer's attention completes, its KV vectors are immediately transferred to CPU, and index construction begins. This overlaps data transfer with the compute-heavy prefill attention of subsequent layers, hiding much of the offloading latency.

**Sequential attention head execution during prefill.** To minimize peak GPU memory, the prefill attention computation runs sequentially across attention heads (one or a few heads at a time rather than all heads in parallel). This is possible because the attention computation for long prompts is already compute-bound and can fully saturate GPU parallelism with FlashAttention even within a single head. The paper notes that "this approach only slightly impacts the attention computation speed, as longer prompts can fully leverage GPU parallelism with FlashAttention" (Appendix C).

**Multi-head parallelism on CPU during decoding.** During token generation, the vector search across different attention heads is independent—each head has its own index and its own query vector. The system exploits this by launching multiple CPU threads to search different indexes in parallel, leveraging the multi-core architecture of modern CPUs. This parallel search is critical for latency: searching 32+ indexes sequentially would add up, but parallelized across many cores, the wall-clock time is bounded by the slowest single-head search.

**Memory minimization via pointer sharing.** For models with Grouped Query Attention (Ainslie et al., 2023), multiple query heads share the same key and value vectors. However, the paper builds separate indexes per query head (because query distributions differ across heads). To avoid duplicating the KV vectors in CPU memory—which would multiply storage by the number of query heads per KV head—the indexes store only **pointers** to a single shared copy of the KV vectors. Each index has its own graph structure (edges between pointers) but the actual vector data resides in one shared location. This is noted in Appendix C:

> "the indexes in the same attention group share one copy of KV vectors by only storing the pointers to KV vectors in each index"

**Scalar quantization (future work).** The paper mentions plans to implement 8-bit quantization (INT8) for KV vectors instead of the current FP16 format, claiming that "initial results demonstrate that this quantization approach does not compromise the inference accuracy" (Appendix C). This would approximately halve the CPU memory consumption for the vector data, though the index graph structure would remain at full precision.

**Retrieval budget configuration.** By default, RetrievalAttention retrieves the top-100 nearest key vectors for each attention head (Section 4.1). For the more complex KV Retrieval task in ∞-Bench, where the model must retrieve specific key-value pairs embedded in long contexts, the retrieval budget is increased to top-2000. The evaluation shows that top-100 suffices for most tasks (accuracy matches full attention), while top-2000 is needed for the most retrieval-intensive tasks—but even 2000 tokens is only ~1.6% of a 128K context, still far below the 30–50% scanning required by traditional ANNS.

**Dynamic retrieval budget allocation (Appendix F).** The paper briefly experiments with PyramidKV (Cai et al., 2024), a technique that allocates different retrieval budgets per layer based on observed attention sparsity patterns: earlier layers get larger budgets, later layers get smaller budgets. The results (Table 10) show a slight improvement on complex retrieval tasks but a small degradation on question-answering, suggesting that "dynamic budget allocation is promising but may require task-specific allocation strategies." This is framed as a direction for future optimization rather than a core contribution.

#### Summary of Design Choices and Their Justifications

- **Training-free operation:** Avoids fine-tuning costs and model-specific retraining; works with any pretrained transformer; critical for practical adoption where model weights are fixed.
- **Attention-aware index via KNN projection rather than key-clustering:** Solves the OOD problem at its root by encoding query perception into the index structure, achieving the same recall as in-distribution K-to-K search at 1–3% scanning.
- **Per-head indexes rather than shared indexes:** Each attention head has its own query distribution; shared indexes would average across distributions and degrade recall for all.
- **Hybrid CPU-GPU attention with static GPU cache:** Balances GPU memory savings (most tokens on CPU) with leveraging GPU parallelism for universally important tokens and minimizing PCIe transfers (only small attention output vectors move between devices).
- **Re-normalization combination rather than simple averaging:** Mathematically exact reconstruction of full-softmax attention from partial softmaxes, avoiding approximation errors from incorrect normalization.
- **Pointer-based KV sharing for GQA models:** Avoids memory blowup from per-head indexes while preserving per-head index specificity.
- **Decoding-only focus (prefill handled separately):** Aligns with real-world serving architectures where prefill is optimized via context caching (Google Cloud, 2024) or phase splitting (Patel et al., 2024; Qin et al., 2024), and decoding is the latency-sensitive phase.

## 4. Key Insights and Innovations

### Innovation 1: Diagnosing the OOD Gap as the Root Cause of ANNS Failure in Attention

The paper's most conceptually important contribution is not the solution but **the diagnosis itself**: identifying that the fundamental obstacle to using vector search for attention is an out-of-distribution (OOD) problem that the field had not recognized. Prior work had either abandoned vector search for attention entirely (pivoting to block-based heuristics or static patterns) or attempted it without understanding why it underperformed. The paper makes the diagnostic move explicit: the Mahalanobis distance between query and key vectors is more than 10× greater than between in-distribution key vectors (Figure 3b), and this gap is what causes traditional ANNS indexes—IVF, HNSW—to require scanning 30–50% of all vectors rather than the 1–3% they achieve in-distribution (Figure 3a).

This is a **fundamental diagnostic contribution** rather than an incremental algorithmic improvement. It reframes the problem from "how do we build a better sparse attention heuristic?" to "how do we solve the distribution mismatch between queries and keys so that vector search works?" The shift matters because it redirects the research agenda: before this paper, one might reasonably have concluded that ANNS was simply ill-suited to attention and that block-based or static methods were the only viable path. The paper shows instead that ANNS fails for a specific, identifiable, and solvable reason—the index structure encodes key-key similarity when it should encode query-key relevance.

Evidence for the diagnostic quality is in Figure 3a's K-to-K baseline: when the same indexes are queried with sampled key vectors (removing the distribution gap), all methods achieve >0.95 recall at 1–5% scanning. This is a clean controlled experiment that isolates the OOD gap as the causal factor. The paper also tests and rejects an existing OOD-optimized solution—RobustVamana (Jaiswal et al., 2022)—finding it performs poorly on attention vectors (Figure 6), which shows that the OOD challenge in attention is not addressed by generic OOD-ANNS methods and requires domain-specific understanding.

**What was the prior assumption?** The default assumption, implicit in work like InfLLM, Quest, and SparQ, was that attention sparsity should be exploited through heuristic scoring (representative vectors, low-rank approximations, block-level scores) rather than through true vector search. The field had largely accepted that exact nearest-neighbor retrieval was too expensive and approximate retrieval was too inaccurate, settling for coarse-grained methods that traded recall for speed. The paper shows this tradeoff is unnecessary—it's an artifact of using the wrong index structure, not an inherent limitation of ANNS for attention.

### Innovation 2: The Prefill-as-Training-Set Framing for Cross-Distribution Index Construction

The paper's second conceptual contribution is reframing the prefill phase—which is already necessary for computing the initial attention states—as a **free source of supervised training data** for building query-aware indexes. During prefill, the LLM computes full attention over all prompt tokens, producing exact query-key similarity scores as a byproduct. The paper recognizes these scores as perfect KNN labels: for every query vector in the prefill, we know exactly which keys it considers most relevant. Instead of treating prefill only as a computation to be accelerated, the paper treats it as a **distribution-mapping oracle** that teaches the index how queries perceive key similarity.

This reframing is intellectually significant because it converts what appears to be a chicken-and-egg problem—we need query-key relevance to build the index, but we need the index to efficiently find query-key relevance—into a bootstrapping procedure where the expensive full-attention pass during prefill pays for itself by constructing an index that accelerates all subsequent decoding steps. The insight is that **prefill query vectors are representative of decoding query vectors** (both come from the same query projection matrix `$W_Q$` within each attention head), so relevance patterns learned during prefill transfer to decoding.

The KNN-to-projection pipeline (described in Section 3) is the mechanism, but the conceptual move is the recognition that **cross-distribution index construction can be unsupervised and exact** when you have access to one distribution's perspective on the other. The paper draws an implicit parallel to cross-modal retrieval (RoarGraph; Chen et al., 2024a) where the same principle operates: one modality's queries can teach the index how to organize the other modality's data. This is a fundamental contribution because it opens a family of techniques—any setting where you have a batch of expensive but exact cross-distribution similarity scores up front can amortize that cost into an efficient index for future queries.

**Comparison to prior work:** Prior ANNS approaches for attention (MagicPiG's LSH, PQCache's product quantization) built indexes purely from the key vector distribution, ignoring the query perspective entirely. Their degraded recall was the predictable consequence. The paper shows that incorporating query-side information through the prefill KNN mapping makes the difference between requiring 30–50% scanning (IVF) and 1–3% scanning (RetrievalAttention) to reach the same recall—an order-of-magnitude efficiency gain that comes from the framing, not from tuning an existing algorithm.

### Innovation 3: The Predictable-Dynamic Decomposition of Attention Tokens

The paper introduces a conceptual decomposition of attention tokens into **two qualitatively different categories**—predictable (consistently important across all queries) and dynamic (importance varies per query)—and designs the system architecture around this distinction. This is more than an engineering optimization; it represents a diagnostic way of thinking about attention patterns that explains why prior methods partially succeed and where they fail.

The decomposition is grounded in the paper's own empirical observations about attention (Section 2.3): some tokens (initial "sink" tokens, recent local context) receive high attention scores regardless of query content, while others (specific content-bearing tokens in the middle of the context) are only important for specific queries. Prior work had observed each half of this pattern in isolation—StreamingLLM exploited the predictable half by keeping only initial and recent tokens; dynamic retrieval methods like InfLLM exploited the query-dependent half by selecting relevant blocks—but no prior work had recognized that **both types coexist and require different handling**.

The innovation is in the **simultaneous treatment**: predictable tokens stay on GPU for fast, exact attention via FlashAttention; dynamic tokens are indexed on CPU for efficient approximate retrieval. This decomposition explains the failure modes of prior methods. Static-only methods (StreamingLLM, SnapKV) fail on retrieval tasks because they discard the dynamic tokens that would answer those queries. Block-based methods (InfLLM, Quest) fail on fine-grained retrieval because their representatives can't capture which specific tokens within a block are query-relevant. The decomposition shows that these aren't competing approaches—they handle different subsets of the problem—and that a correct solution must handle both.

The evidence for this duality is in the accuracy patterns: StreamingLLM gets 5% on passKey retrieval where the needle is outside the static window (Table 2) but maintains accuracy on local-context tasks; InfLLM gets near-zero on KV retrieval despite dynamic block selection; RetrievalAttention achieves near-full-attention accuracy on both types by keeping predictable tokens always available and retrieving dynamic tokens on demand. The decomposition is a **conceptual reframing with architectural consequences**, not merely a taxonomy.

### Innovation 4: Verifier-Free Sparse Attention as a Training-Free Systems Solution

The paper makes a distinctive architectural choice that carries conceptual weight: RetrievalAttention requires **no model fine-tuning, no architectural modification, and no learned token-selection policy**. The entire system operates at the inference infrastructure level—moving KV vectors between CPU and GPU, building indexes, and retrieving them—without touching the model weights. This is significant because the dominant trend in efficient attention has been toward training-dependent solutions: sparse attention patterns learned during pretraining, distilling larger contexts into smaller models, or fine-tuning models to compress their own KV caches.

The paper's choice to be training-free is not merely pragmatic; it reflects a conceptual bet that **attention sparsity can be captured through data structures rather than learned parameters**. The attention-aware index is a data structure—a graph built from prefill KNN connections—not a learned function. It makes no predictions about which tokens are important; it simply organizes the key vectors so that similarity search finds the genuinely important ones. This is philosophically different from methods like SnapKV (which learns which tokens to keep based on prefill attention patterns) or InfiniGen (which learns to predict important tokens across layers). Those methods learn a policy that approximates attention; RetrievalAttention builds an index that lets attention compute itself over a smaller subset.

**Why this matters beyond performance:** Training-free deployment means RetrievalAttention can be applied to any pretrained model without access to training data, without GPU-hours for fine-tuning, and without the risk of degrading the model's general capabilities through task-specific optimization. This dramatically lowers the barrier to long-context inference. The paper's headline result—serving an 8B model with 128K tokens on a single RTX4090 (24GB) at acceptable latency—is enabled by this design philosophy. A training-dependent approach would face chicken-and-egg problems: you need long-context data to train the sparse attention mechanism, but you can't generate that data efficiently without the sparse attention mechanism.

The paper implicitly contrasts this with the broader field's trajectory toward ever-more-complex training pipelines for efficiency. The conceptual implication is that **for dynamic sparse attention specifically, the problem may be better solved at the systems level than the modeling level**—not because learned approaches are inherently worse, but because the exact similarity structure is already present in the pretrained projections and just needs to be organized efficiently.

### Innovation 5: A Unified Explanation for Contradictory Findings in Sparse Attention Research

The predictable-dynamic decomposition (Innovation 3) and the OOD diagnosis (Innovation 1) together provide something the field lacked: a **unified framework for understanding why different sparse attention methods succeed and fail on different benchmarks**. Before this paper, results were contradictory in ways that were hard to reconcile: StreamingLLM worked well on language modeling perplexity but collapsed on retrieval tasks; InfLLM showed promise on some benchmarks but not others; ANNS-based approaches were attempted but abandoned as ineffective. The paper's analysis provides a coherent explanation for this landscape.

StreamingLLM succeeds when the task requires only predictable tokens (perplexity on local context, simple QA where the answer is nearby) and fails when dynamic retrieval is needed (passKey, number retrieval, KV retrieval). InfLLM succeeds when block-level relevance is a good approximation (coarse-grained topical relevance) and fails when token-level precision matters (exact-match retrieval). Traditional ANNS fails because of the OOD gap, not because vector search is inherently wrong for attention—explaining why earlier attempts like MagicPiG and PQCache needed to retrieve 20% of tokens, which made them practical failures despite conceptual promise.

This is a **field-resolving contribution** that goes beyond a single paper's results. By identifying the OOD gap as the root cause and the predictable-dynamic split as the organizing principle, the paper converts a confusing set of empirical observations into a coherent diagnostic framework. Researchers can now understand *why* a method fails on a given benchmark and what would need to change to fix it, rather than treating method-benchmark outcomes as opaque empirical contingencies. This is the mark of a paper that advances conceptual understanding, not just system performance.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** Three benchmarks are used: ∞-Bench (Zhang et al., 2024b), which consists of 7 tasks (three retrieval tasks: passKey retrieval, number retrieval, KV retrieval; and four realistic tasks: code debugging, math find, dialogue, and multiple-choice questions) with an average context length over 100K tokens; RULER (Hsieh et al., 2024), which comprises 4 categories and 13 tasks including retrieval, multi-hop tracing, aggregation, and QA, with prompt lengths ranging from 4K to 128K tokens; and Needle-in-a-Haystack (Greg Kamradt, 2023), which tests the model's ability to retrieve specific information hidden within long documents at varying depths and context lengths.

- **Base model(s).** Three state-of-the-art long-context LLMs are evaluated: Llama-3-8B-Instruct-262k (Gradient AI, 2024), Yi-6B-200K (01-ai, 2024a), and Yi-9B-200K (01-ai, 2024b). These span 6B to 9B parameters and support context lengths from 200K to 262K tokens. All three use Grouped Query Attention (GQA), though with different configurations: Yi-6B and Yi-9B have 32 query heads and 4 KV heads across 32 and 48 layers respectively, while Llama-3-8B has 32 query heads and 8 KV heads across 32 layers (Table 6 in Appendix A). The paper also evaluates Llama-3-70B-262k on KV retrieval to demonstrate scalability to larger models (Appendix G), and Llama-3-8B-1048K for the 1M-token Needle-in-a-Haystack stress test (Appendix A.3).

- **Metrics.** Task accuracy is the primary metric across all benchmarks, measured as the percentage of test instances where the model produces the correct answer (exact match for retrieval tasks, standard grading for QA tasks). For ∞-Bench, per-task accuracy and an average across all 7 tasks are reported (Table 2). For RULER, accuracy is reported at each context length (4K through 128K) and averaged (Table 3). For Needle-in-a-Haystack, results are visualized as heatmaps showing retrieval success at different document depths and context lengths (Figure 5). Decoding latency is measured in seconds per generated token (Tables 4, 5, 7, 8), broken down into retrieval time, attention computation, and other overhead. Index recall is measured as the overlapping ratio between retrieved top-k results and the ground-truth top-k from full attention, plotted against the percentage of key vectors scanned (Figures 3a and 6).

- **Baselines.** The paper compares against several categories of training-free methods. Full attention without KV cache recomputes attention over all tokens at every decoding step. vLLM (Kwon et al., 2023) enables KV caching with PagedAttention optimization. StreamingLLM (Xiao et al., 2024b) retains only initial tokens plus a fixed-length window of recent tokens. SnapKV (Li et al., 2024) caches critical tokens identified from the last window of the prompt during prefill. InfLLM (Xiao et al., 2024a) partitions KV cache into blocks with representative vectors per block and retrieves top-k blocks per query. Quest (Tang et al., 2024) tracks minimal and maximal key values per page to estimate page criticality for each query. InfiniGen (Lee et al., 2024) prefetches essential KV cache entries by speculating important tokens based on cross-layer attention score correlation. Additionally, two ANNS baselines from Faiss (Douze et al., 2024) are included: Flat, which performs exact KNN via linear scan of all key vectors, and IVF (Sivic & Zisserman, 2003), which clusters key vectors and scans only the most promising clusters.

- **Generation budget / compute accounting.** Compute is measured in several ways to enable fair comparison. The primary metric for retrieval methods is the number of activated tokens—the number of KV vectors that participate in attention computation per query. All indexing-based methods (Flat, IVF, RetrievalAttention) default to retrieving top-100 key vectors, with top-2000 used for the complex KV Retrieval task in ∞-Bench. For static methods (StreamingLLM, SnapKV), the activated token count equals their fixed cache size (2K tokens). The static GPU pattern for RetrievalAttention, Flat, and IVF is consistently 640 tokens (128 initial + 512 local window). Decoding latency comparisons in Tables 4 and 7 use identical hardware configurations, with per-token wall-clock time measured at various context lengths from 4K to 128K on RTX4090 and A100 GPUs. Latency breakdowns (Table 5) separate vector search time from attention computation and other overhead, enabling direct comparison of retrieval efficiency across methods.

- **Cross-validation / statistical protocol.** The paper does not employ explicit cross-validation or statistical significance testing. All experiments use the standard test splits of the benchmarks. For ∞-Bench, results are reported across 7 tasks totaling 500+ test instances per model. For RULER, results span 13 tasks across 6 context lengths (4K to 128K), providing per-length granularity. For Needle-in-a-Haystack, the evaluation covers context lengths from 4K to 128K (and 250K to 1M for the extended test in Appendix A.3) with needle placement at varying depths. The absence of error bars or confidence intervals is a notable limitation—the paper reports point estimates without quantifying variance, and the test sets are moderately sized (∞-Bench averages ~100 instances per task for the per-task breakdown). All experiments run in single-batch scenarios to reflect practical interactive deployment.

### Main Quantitative Results

#### Accuracy on Long-Context Benchmarks (∞-Bench)

The headline result from Table 2 is that RetrievalAttention achieves accuracy nearly identical to full attention across all tasks, with an average accuracy of 48.9% on Llama-3-8B versus 50.4% for full attention—a difference of only 1.5 percentage points. This stands in stark contrast to all non-ANNS baselines. StreamingLLM collapses to 20.2% average accuracy (a 30.2 point drop), confirming that static token retention is fundamentally inadequate for tasks requiring non-local retrieval. SnapKV performs better at 48.2% average but still drops 2.2 points and, more importantly, achieves only 0.5% on KV retrieval—essentially zero. InfLLM achieves 44.7% average (−5.7 points), with particular weakness on En.MC where it scores 37.0% versus full attention's 68.0%. Quest achieves 47.6% (−2.8 points) but similarly scores 0.0% on KV retrieval, confirming the paper's claim that block-level representatives lose critical fine-grained information.

The KV Retrieval task provides the clearest differentiation. Full attention achieves 17.5% on Llama-3-8B. StreamingLLM scores 1.0%, SnapKV 0.5%, InfLLM 0.5%, InfiniGen 0.0%, and Quest 0.0%—all near-zero. In contrast, RetrievalAttention with top-100 retrieval achieves 9.0% and with top-2000 achieves 14.0%, approaching the full-attention ceiling of 17.5%. Flat with top-2000 achieves 14.5% and IVF achieves 14.0%, demonstrating that ANNS retrieval at sufficient granularity can solve this task where heuristic methods cannot, but at the cost of scanning 100% (Flat) or 30% (IVF) of all key vectors versus RetrievalAttention's 1–3%.

The Yi-9B results (Table 2) show the same pattern with different absolute numbers. Full attention achieves 52.8% average. StreamingLLM drops to 20.9% (−31.9 points). RetrievalAttention achieves 50.8% with top-100 and 52.2% with top-2000—within 0.6 points of full attention. Flat achieves 51.2% and 52.5% respectively, showing that exact KNN fully recovers accuracy when scanning everything, while RetrievalAttention achieves the same accuracy at a fraction of the cost.

Yi-6B shows an interesting pattern: RetrievalAttention with top-100 actually achieves 45.0% versus full attention's 45.5%—a drop of only 0.5 points. Flat and IVF both slightly exceed full attention on some tasks (e.g., Math.F at 16.0% for Flat vs. 11.0% for full attention on Yi-6B), which the paper does not explain but may reflect that retrieving the top-k keys and re-normalizing attention can occasionally suppress noise from irrelevant tokens.

#### Accuracy on RULER: Scaling Across Context Lengths

Table 3 presents accuracy across six context lengths (4K to 128K) on all 13 RULER tasks for Llama-3-8B and Yi-9B. The critical finding is that RetrievalAttention maintains accuracy close to full attention as context length scales, while all non-ANNS methods degrade sharply.

On Llama-3-8B, full attention averages 86.54% across all context lengths. RetrievalAttention achieves 84.70% (−1.85 points). The degradation with context length is parallel: full attention drops from 93.13% at 4K to 78.74% at 128K; RetrievalAttention drops from 92.64% to 74.70%. The gap remains narrow (within 1–4 points) at every context length. Flat achieves 84.66% (−1.89 points), nearly identical to RetrievalAttention, while IVF drops to 83.20% (−3.34 points), with the gap widening at longer contexts (68.21% vs. 74.70% at 128K).

The non-ANNS methods tell a different story. StreamingLLM averages 25.01% (−61.53 points), with accuracy falling from 60.10% at 4K to 11.34% at 128K. SnapKV averages 73.78% (−12.76 points) but shows accelerating degradation: from 91.51% at 4K to 58.68% at 128K. InfLLM averages 43.74% (−42.81 points), dropping from 85.20% at 4K to 25.71% at 128K. The paper also includes a "Claimed Effective" column that estimates the maximum context length at which each method maintains reasonable accuracy (defined implicitly by where the drop becomes severe). StreamingLLM is effective only below 4K; SnapKV works to 4K; InfLLM works below 4K; RetrievalAttention and Flat are effective to 16K.

On Yi-9B, the pattern repeats: full attention averages 76.87%, RetrievalAttention 76.43% (−0.44 points), Flat 77.24% (+0.37 points, slightly exceeding full attention), and IVF 76.29% (−0.58 points). Quest averages 47.78% at 128K (−12.73 points from the full attention 128K figure). The paper also reports InfiniGen and Quest on RULER in Appendix E (Table 9), with detailed 128K task-level breakdowns for Llama-3-8B. InfiniGen averages 43.1% (−35.6 points from full attention's 78.7%), with near-zero performance on the harder multi-hop tracing tasks (25.0% and 0.0% on M2 and M3 respectively). Quest averages 60.5% (−18.2 points), with complete failure on M3 (0.0%) and poor performance on M2 (36.5%). RetrievalAttention achieves 74.7% at 128K, maintaining strong performance across all task types, though it does show weakness on the hardest aggregration task (FW: 49.3% vs. full attention's 72.2%) and the complex CW task (1.1% vs. 1.0%).

#### Needle-in-a-Haystack: Position-Independent Retrieval

Figure 5 shows RetrievalAttention's heatmap for Yi-9B on Needle-in-a-Haystack at context lengths from 4K to 128K and needle depths from 0% to 100%. The heatmap is uniformly green (successful retrieval) across all positions and all context lengths, visually demonstrating that RetrievalAttention can locate information regardless of where it appears in the document. This contrasts with StreamingLLM's heatmap (Figure 7b in Appendix A.2), which shows retrieval success only when the needle falls within the initial or most recent segments of the context—a diagonal band of green at the extremes and red elsewhere. InfLLM's heatmap (Figure 7d) shows degradation at longer context lengths and non-trivial depth positions. SnapKV, Flat, and IVF all show uniformly green heatmaps (Figures 7c, 7e, 7f), demonstrating that ANNS retrieval and SnapKV's observation-based selection both handle the needle-in-haystack task well—but the paper's earlier results on ∞-Bench and RULER show that SnapKV fails on more complex retrieval tasks where this benchmark passes it. Appendix A.3 (Figure 8) extends Needle-in-a-Haystack to 1M tokens with Llama-3-8B-1048K, showing RetrievalAttention passes all test cases from 250K to 1M context, which demonstrates the index's scalability.

#### Decoding Latency

Table 4 reports per-token generation latency on Llama-3-8B using an RTX4090 as context length varies from 4K to 128K. Full attention without KV cache shows the expected quadratic scaling: 0.527 seconds at 4K, rising to 43.927 seconds at 128K. vLLM with KV cache hits out-of-memory (OOM) at all context lengths on the 24GB RTX4090, confirming that KV caching alone cannot solve long-context inference on commodity hardware.

Static and block-retrieval methods show flat latency regardless of context length because they operate on a constant number of tokens: StreamingLLM at ~0.029s, SnapKV at ~0.028s, InfLLM at ~0.058–0.069s. However, these latency advantages come at the cost of the severe accuracy degradation documented in Tables 2 and 3.

Among the ANNS methods, Flat shows the steepest latency growth because it scans all key vectors linearly: 0.140s at 4K, 0.178s at 8K, 0.922s at 128K. IVF is faster but still grows with context length: 0.128s at 4K, 0.162s at 16K, 0.373s at 128K. RetrievalAttention shows the slowest growth: 0.137s at 4K, 0.144s at 8K, 0.156s at 16K, and only 0.188s at 128K. This near-flat scaling—only a 1.37× increase from 4K to 128K—is the direct consequence of scanning only 1–3% of vectors regardless of total context size. At 128K, RetrievalAttention achieves a 4.9× speedup over Flat (0.188s vs. 0.922s) and a 1.98× speedup over IVF (0.188s vs. 0.373s). The absolute latency of 0.188s per token means roughly 5.3 tokens generated per second, which is acceptable for interactive use.

Table 5 provides the latency breakdown at 128K context. Flat spends 0.798s (86.6% of total) on vector search, 0.083s on attention computation, and 0.041s on other overhead, totaling 0.922s. IVF spends 0.250s (67.0%) on search, 0.084s on attention, 0.039s on overhead, totaling 0.373s. RetrievalAttention spends only 0.064s (34.0%) on vector search, 0.081s on attention, 0.043s on overhead, totaling 0.188s. RetrievalAttention reduces index search latency by 91% compared to Flat (0.064s vs. 0.798s) and by 74% compared to IVF (0.064s vs. 0.250s). This confirms that the attention-aware index structure, by dramatically reducing the number of vectors scanned, shifts the bottleneck from search to attention computation and other overhead.

Table 7 in Appendix A.4 repeats the latency experiments on an A100 GPU (80GB), demonstrating that RetrievalAttention's advantages persist across hardware tiers. At 128K context on Llama-3-8B, full attention without cache takes 33.38s, vLLM achieves 0.033s but goes OOM at longer contexts (Table 8 shows OOM at 500K and 1M). StreamingLLM achieves 0.031s, SnapKV 0.033s, InfLLM 0.068s. Among ANNS methods: Flat takes 0.564s, IVF 0.345s, RetrievalAttention 0.155s. The 3.6× speedup over Flat and 2.2× over IVF on A100 are somewhat lower ratios than the 4.9× and 1.98× on RTX4090 because the A100's faster compute makes the attention computation proportionally larger relative to search, but the absolute speedup remains significant.

Table 8 extends the A100 latency analysis to context lengths from 100K to 1M tokens on Llama-3-8B, using a machine with 1.72 TB CPU memory to accommodate the indexes. Full attention without cache scales quadratically from 25.47s at 100K to 1,740s at 1M. vLLM works at 100K (0.029s) and 200K (0.046s) but hits OOM at 500K and 1M—the KV cache alone exceeds 80GB. StreamingLLM and SnapKV remain flat at ~0.034s across all lengths because their token count is constant, but their accuracy collapses at scale as shown in previous tables. Flat scales from 0.489s at 100K to 3.69s at 1M (7.5× increase). IVF scales from 0.308s at 100K to 1.889s at 1M (6.1× increase). RetrievalAttention scales from 0.159s at 100K to only 0.172s at 1M—an 8% increase over a 10× expansion of context size. This near-constant latency at extreme scale is the paper's most dramatic demonstration of RetrievalAttention's efficiency.

Figure 1, introduced in the introduction and anchored to the results, is a qualitative quadrant plot showing RetrievalAttention in the upper-left region: high task accuracy (nearly matching full attention) and extremely low decoding latency. RetrievalAttention is the only method in the Pareto-optimal corner of simultaneous high accuracy and low latency.

#### Larger Model Results (Appendix G)

Table 11 in Appendix G evaluates Llama-3-70B-262k on the most challenging task (KV Retrieval from ∞-Bench, 128K context) to test scalability. Full attention achieves 35.0%. StreamingLLM scores 0.0%—complete failure. Quest achieves 13.0%—better than static methods but well below full attention. Flat achieves 24.0% with exact KNN, and RetrievalAttention achieves 23.5%—nearly matching Flat while being 3.5× faster (1.62s vs. 5.68s decoding latency). Quest is faster at 1.36s but achieves only 13.0% accuracy. The paper notes this experiment uses 8× A100 GPUs with model parallelism, demonstrating that RetrievalAttention functions in multi-GPU settings where its CPU-side indexes complement rather than conflict with GPU partitioning.

#### Index Recall vs. Scanning Efficiency (Micro-Benchmark)

Figure 6 is the paper's central micro-benchmark for validating the attention-aware index design. It plots recall@100 (the fraction of the true top-100 key vectors found) against the percentage of total key vectors scanned, across three different models (Yi-6B, Yi-9B, Llama-3-8B) and two search configurations (Q to K and K to K). For the in-distribution K to K search, all methods—IVF, HNSW, RobustVamana, and RetrievalAttention—achieve high recall (~0.95+) at only 1–5% scanning. The curves are tightly clustered, confirming that all indexing methods work well when queries and indexed vectors share a distribution.

For the out-of-distribution Q to K search, the differentiation is stark. IVF requires scanning approximately 30–40% of vectors to reach 0.95 recall on all three models. HNSW plateaus at low recall (below 0.6 on Llama-3-8B, below 0.4 on Yi-9B) regardless of scanning percentage—it falls into local optima and never finds the true top keys. RobustVamana, despite being designed for OOD queries, performs similarly poorly: its Q to K curve sits near zero recall for Yi-6B and Yi-9B, rising only modestly on Llama-3-8B at high scanning percentages. RetrievalAttention's Q to K curve nearly overlaps with its K to K curve and with the K to K curves of other methods, achieving ~0.95+ recall at 1–3% scanning across all three models. The inset zoom on the 0–0.05 x-axis range (for Llama-3-8B) shows that RetrievalAttention reaches >0.95 recall with only ~1–2% of vectors scanned, while IVF and HNSW are far below at the same scanning rate.

This figure directly validates the paper's central technical claim: the attention-aware index, by leveraging prefill query information to encode query-key relevance into the key-key graph, eliminates the OOD penalty and achieves the same search efficiency for Q-to-K as all methods achieve for the in-distribution K-to-K case. The 30–50× reduction in scanning (1–3% vs. 30–50% to reach the same recall) is the mechanism behind the 4.9× end-to-end speedup over Flat and 1.98× over IVF in Table 4.

### Ablation Studies and Robustness Checks

**Retrieval budget size**: The default top-100 retrieval suffices for most tasks; increasing to top-2000 on the most retrieval-intensive task (KV Retrieval in ∞-Bench) recovers near-full-attention accuracy. On Llama-3-8B, RetrievalAttention achieves 9.0% accuracy with top-100 versus 14.0% with top-2000, approaching the full-attention ceiling of 17.5% (Table 2, Retr.KV column). On Yi-9B, the corresponding numbers are 20.0% with top-100 and 30.0% with top-2000 versus 30.5% for full attention. This demonstrates that RetrievalAttention can trade off retrieval budget for accuracy on demanding tasks without changing the index structure.

**Static pattern size**: All GPU-resident static patterns use 640 tokens (128 initial + 512 local window) across all experiments. The paper does not ablate this number, which is a notable omission—the choice of 640 tokens affects both GPU memory consumption (each additional token in GPU cache increases memory linearly) and accuracy (more static tokens means more coverage of predictable attention patterns, but less capacity for dynamic retrieval from CPU). The paper acknowledges that "more complex static patterns" from Li et al. (2024) or Jiang et al. (2024) could be adapted (Section 3.3) but does not explore the tradeoff empirically.

**Per-head vs. shared indexes for GQA**: The paper builds separate vector indexes per query head, even for models with GQA where multiple query heads share KV vectors. This is justified by the observation that query distributions differ across query heads within a GQA group. The paper does not present a direct ablation comparing per-head to shared indexes, but the near-identical accuracy to full attention (Tables 2, 3) and the high recall at low scanning (Figure 6) provide indirect validation—if shared indexes were sufficient, the paper would presumably use them to reduce memory, but instead it uses per-head indexes and achieves strong results. The memory cost is mitigated by pointer sharing (Appendix C).

**Oracle vs. predicted token relevance**: Unlike the difficulty estimation in the reference paper's compute-optimal framework, RetrievalAttention's index construction uses exact KNN labels computed from full prefill attention—this is effectively an oracle signal, not a prediction. The paper does not explore what happens if the prefill is too short to provide representative query vectors for index construction, or if the prefill query distribution shifts relative to decoding queries (e.g., for prompts with unusual structure). The assumption that prefill queries are sufficiently representative is tested implicitly by the Needle-in-a-Haystack results (Figure 5), which show strong retrieval at variable depths, and by the 1M-token test (Figure 8).

**Traditional ANNS baseline (IVF vs. HNSW)**: The paper includes both cluster-based (IVF) and graph-based (HNSW) traditional indexes in its micro-benchmarks (Figures 3a and 6) but only IVF in the full system evaluation (Tables 2–4). HNSW is excluded from system-level comparison because its Q-to-K recall never reaches acceptable levels (Figure 6)—it would produce unacceptably low accuracy. This is itself a finding: graph-based methods that work well in-distribution can catastrophically fail under distribution shift in ways that cluster-based methods partially mitigate. The paper does not explore hybrid or adapted HNSW variants beyond noting RobustVamana's poor performance.

**OOD-optimized ANNS (RobustVamana)**: The paper tests RobustVamana (Jaiswal et al., 2022), a method specifically designed for OOD queries in ANNS, and finds it performs poorly on attention vectors (Figure 6). For Q-to-K search on Yi-6B, RobustVamana's recall at any scanning percentage is near zero—worse than standard HNSW—indicating that the OOD pattern in attention is qualitatively different from what RobustVamana was designed for. This negative result strengthens the paper's claim that the attention OOD challenge is distinctive and requires a domain-specific solution rather than a generic OOD-ANNS method.

**Dynamic retrieval budget allocation (PyramidKV)**: Appendix F (Table 10) ablates the fixed retrieval budget (2000 tokens per head universally) against a PyramidKV-based allocation (Cai et al., 2024) that assigns larger budgets to earlier layers and smaller budgets to later layers. On Llama-3-8B with ∞-Bench, RetrievalAttention with fixed budget achieves 49.9% average accuracy versus 50.1% with PyramidKV allocation—a marginal 0.2 point improvement. However, the PyramidKV variant improves KV Retrieval from 14.5% to 16.0% while slightly decreasing En.QA from 8.7% to 8.5%. The paper concludes that "dynamic budget allocation is promising but may require task-specific allocation strategies"—this is a weak result that suggests the simple fixed-budget approach is already near-optimal for the tested tasks, or that PyramidKV's layer-wise allocation assumptions don't transfer well to the ANNS retrieval setting.

**Hardware generality (RTX4090 vs. A100)**: Table 7 shows that RetrievalAttention's speedup over Flat and IVF persists on both commodity (RTX4090, 24GB) and data-center (A100, 80GB) GPUs. On A100, RetrievalAttention achieves 0.155s/token versus Flat's 0.564s (3.6×) and IVF's 0.345s (2.2×) at 128K on Llama-3-8B. The smaller relative speedup on A100 compared to RTX4090 (4.9× and 1.98×) reflects that the A100's faster GPU makes attention computation a larger fraction of total latency—so the speedup from better search is partially diluted by the fixed cost of attention. This demonstrates that RetrievalAttention's benefits are robust to hardware but that the magnitude depends on the GPU-CPU balance.

**Model architecture generality (GQA variants)**: The three evaluated models span different GQA configurations (Yi-6B: 32Q/4KV heads, Yi-9B: 32Q/4KV with deeper layers, Llama-3-8B: 32Q/8KV heads). RetrievalAttention maintains near-full-attention accuracy on all three, with average ∞-Bench accuracy gaps of −0.5 (Yi-6B), −2.0 (Yi-9B), and −1.5 (Llama-3-8B) points for the top-100 configuration (Table 2). The slightly larger gap on Yi-9B may reflect its deeper architecture (48 layers vs. 32) creating more OOD variance, but the paper does not analyze this. The 70B-parameter model result (Table 11) provides additional evidence of scalability.

**Context length scaling of index efficiency**: Table 8 implicitly ablates context length's effect on search efficiency. As context grows from 100K to 1M, Flat's latency increases 7.5× (linear in context size, as expected for full scan), IVF's increases 6.1× (sub-linear but still growing with cluster count), and RetrievalAttention's increases only 1.08× (near-constant). This demonstrates that the attention-aware graph's traversal cost grows sub-logarithmically with dataset size, a property inherited from the HNSW-like graph structure but only realized because the OOD problem is solved—traditional HNSW would have grown sub-logarithmically too, if it could actually find the right keys.

**Missing ablation: number of KNN connections per query during index construction**: The paper describes connecting each query to its top-k nearest keys during prefill (Stage 1 of index construction) but does not specify k or ablate its effect. This is a critical hyperparameter: too few connections per query may fail to capture the full query-key relevance structure; too many may create an overly dense graph that slows traversal. The strong empirical results suggest the chosen k works well, but without an ablation, practitioners cannot determine whether the method is sensitive to this choice.

**Missing ablation: prefill length needed for representative query sampling**: The index construction relies on prefill queries being representative of decoding queries. If the prompt is short (e.g., a few hundred tokens), the prefill may not provide enough query vectors to adequately sample the query distribution. The paper's experiments all use long prompts (4K to 128K+), so this concern doesn't arise, but the method's behavior under short-prefill, long-generation scenarios is untested. This would matter for applications where the prompt is brief but generation continues for many steps.

**Negative result for HNSW**: HNSW's complete failure on Q-to-K search (Figure 6) is an important negative result that validates the paper's OOD diagnosis. Graph-based methods are typically more efficient than cluster-based methods for in-distribution search, but their greedy traversal relies on local similarity being globally meaningful—an assumption that breaks down catastrophically when query and indexed vectors live in different regions of space. The paper does not analyze *why* HNSW fails more severely than IVF (cluster-based methods are more robust because they compare the query against all cluster centroids first, providing a global view that partially compensates for distribution shift), but the empirical result is clear.

**Negative result for ReST-like optimization**: The paper does not include a negative result for training-based optimization of the index (analogous to the ReST EM failure in the reference paper's revision model), because RetrievalAttention is entirely training-free. The robustness of the method to different models and tasks without any tuning is itself a strength, but also means there are no ablations of training data quality, optimization objectives, or convergence behavior.

### Critical Assessment

**Claim 1: RetrievalAttention achieves near full-attention accuracy while accessing only 1–3% of data.** This claim is strongly supported by the accuracy results on ∞-Bench (Table 2) and RULER (Table 3), where RetrievalAttention matches full attention within 0.5–2.0 points on average across three models and two benchmarks. The micro-benchmark in Figure 6 directly validates that 1–3% scanning achieves >0.95 recall. However, two qualifications are necessary. First, the 1–3% figure is for the index search specifically; the total data access includes the static GPU tokens (640 tokens, or ~0.5% of 128K context), so the actual accessed fraction is ~1.5–3.5%. Second, on the most retrieval-intensive task (KV Retrieval in ∞-Bench), top-100 retrieval leaves a gap of several points versus full attention (9.0% vs. 17.5% on Llama-3-8B), and closing that gap requires top-2000 retrieval (~1.6% scanning plus static tokens = ~2.1% total). The claim is accurate for aggregate performance but understates the retrieval budget needed for the hardest task.

**Claim 2: RetrievalAttention achieves 4.9× decoding latency reduction over exact KNN and 1.98× over traditional ANNS at 128K on RTX4090.** This is directly supported by Table 4 (0.188s vs. 0.922s and 0.373s respectively). The 4.9× figure is specifically for Flat vs. RetrievalAttention at 128K on Llama-3-8B; the ratio varies by model and context length. At shorter contexts, the gap narrows (e.g., at 4K, RetrievalAttention is actually slightly slower than IVF: 0.137s vs. 0.128s) because the fixed overhead of index traversal dominates when there are fewer vectors to scan. The claim should be understood as best-case at long contexts where scanning reduction matters most. The A100 results (Table 7) show smaller ratios (3.6× over Flat, 2.2× over IVF) due to faster GPU compute, so the speedup is hardware-dependent.

**Claim 3: RetrievalAttention is the first system to serve 8B-parameter models with 128K tokens on a single RTX4090 (24GB) with acceptable latency and no accuracy degradation.** The claim about being "first" is difficult to verify from the paper alone—it requires knowledge of all prior systems, which the paper's related work section surveys but does not exhaustively benchmark. However, the paper does demonstrate the capability concretely: the RTX4090 has 24GB memory, the Llama-3-8B model weights occupy ~16GB in FP16, leaving ~8GB for KV cache and activations. The paper's static pattern of 640 tokens on GPU consumes negligible KV cache memory (~0.08GB for 8B model with 32 layers, 8 KV heads, 128-dim per head). The remaining ~124,360 tokens of KV cache are on CPU, where the 128GB DRAM capacity is sufficient. The 0.188s/token latency is presented as "acceptable" for interactive use (~5 tokens/second). No other method in the paper's evaluation achieves this combination: vLLM OOMs (not enough GPU memory), full attention without cache is 233× slower, and static methods sacrifice accuracy. The claim is therefore substantiated within the paper's scope, though "acceptable latency" is subjective—5 tokens/second is functional but not fast for chat applications.

**Potential weaknesses in experimental design:**

- **Single-batch evaluation only.** All experiments use batch size 1, which the paper justifies by following prior work and targeting interactive scenarios. However, throughput-oriented serving (where multiple requests are batched) would change the GPU-CPU balance: GPU attention becomes more efficient with batching, while CPU index search across many queries simultaneously might become a bottleneck. The paper does not explore how RetrievalAttention scales to batch inference.

- **No statistical significance or variance reporting.** All accuracy numbers are point estimates without confidence intervals. The ∞-Bench test set has ~500 instances total, split across 7 tasks (~70 per task). The RULER evaluation spans 13 tasks with varying instance counts. Small per-task sample sizes mean that the reported accuracy numbers could have substantial variance, and the 0.5–2.0 point gaps between RetrievalAttention and full attention may not be statistically distinguishable from zero on some tasks. The paper would be stronger with standard errors or bootstrap confidence intervals, particularly for the KV Retrieval task where the gap between top-100 and top-2000 retrieval (9.0% vs. 14.0% on Llama-3-8B) is based on what appears to be a modest number of test instances.

- **Fixed static pattern without ablation.** The 640-token static pattern (128 initial + 512 local window) is used universally but never varied. The paper cites StreamingLLM and SnapKV as sources for this pattern but doesn't test whether different static sizes affect the accuracy-latency tradeoff. A larger static pattern would increase GPU memory but might improve accuracy by covering more predictable tokens; a smaller pattern might shift more tokens to dynamic retrieval and stress-test the index quality. This ablation is important because the static pattern size is a free parameter that practitioners must set.

- **No comparison to training-based sparse attention methods.** The paper positions itself against training-free methods only, which is a reasonable scope. However, claims about being the "first" to achieve certain capabilities on commodity hardware should be contextualized: training-based methods (e.g., sparse attention patterns learned during pretraining, KV cache distillation) might achieve similar or better accuracy-latency tradeoffs, but they require model modification that RetrievalAttention avoids. The paper doesn't discuss this tradeoff or provide a training-cost comparison.

- **The OOD index construction cost is not characterized.** Building the attention-aware index requires computing exact KNN from all prefill queries to all keys (Stage 1), which is an O(n²) operation—the very cost the method aims to avoid. The paper argues this happens during prefill anyway (full attention is computed), so the KNN extraction adds minimal overhead. But the paper doesn't measure this overhead or verify that the index construction time is negligible compared to the prefill latency. For extremely long prompts (128K+), full attention during prefill already takes substantial time; adding index construction on top could make prefill unacceptably slow even if decoding is fast. A prefill latency breakdown would strengthen the paper.

- **Limited task diversity.** All benchmarks are English-language text tasks with discrete correct answers. The paper does not evaluate generation quality (perplexity, human evaluation), code generation, or tasks requiring open-ended reasoning. The Needle-in-a-Haystack and retrieval tasks test a specific capability (locating information in long contexts) that aligns well with RetrievalAttention's design, but it's unclear whether the method would maintain accuracy on tasks that require synthesizing information from many parts of the context simultaneously—the very tasks where discarding 97–99% of tokens might matter most.

- **Single prompt distribution assumption.** The index construction uses prefill queries to learn query-key relevance patterns. If the prompt's content distribution differs substantially from the generation queries' needs (e.g., the prompt is in one language and generation is in another, or the prompt contains mostly narrative text but generation requires extracting specific facts), the prefill queries might not be representative. The Needle-in-a-Haystack test partially addresses this (the needle is a specific fact in a long document), but more systematic distribution-shift testing is absent.

- **CPU memory consumption not fully characterized.** The paper reports that indexes share KV vector storage via pointers (Appendix C), but doesn't provide total CPU memory consumption numbers for the indexes themselves. The graph structure (edges between key vectors) adds memory overhead beyond the KV vectors. At 1M context with 32 layers and 8 KV heads, the graph edge storage could be substantial. Table 8's 1M-token experiment uses 1.72 TB of CPU memory, which is far more than the KV vectors alone would require (~125GB for the KV cache), suggesting significant index overhead. The paper doesn't break down this memory usage or discuss its scaling properties.

**What experiments would have strengthened the paper:**

- **Ablation of static pattern size** to characterize the accuracy-latency-memory tradeoff.
- **Ablation of KNN connection count per query** during index construction, since this determines graph density and traversal efficiency.
- **Batch inference evaluation** (batch size > 1) to test throughput scaling.
- **Prefill latency measurement** including index construction overhead, to verify that the prefill-phase cost is acceptable.
- **Perplexity or generation quality evaluation** on long-document language modeling tasks, beyond the discrete-answer benchmarks.
- **Comparison to a simple hybrid baseline**: static tokens + random sampling of the remaining tokens (to test whether the index structure provides value beyond just reducing token count).
- **Sensitivity analysis** of recall and accuracy to the number of prefill tokens available for index construction (short-prompt stress test).
- **CPU memory usage breakdown** at various context lengths to help practitioners provision hardware.

**Conditions on claims:** The paper's central claims hold for the evaluated models (6B–9B parameters, GQA architecture) on the evaluated benchmarks (retrieval and QA tasks with discrete answers) at batch size 1. The speedup claims are hardware-dependent—larger on commodity GPUs with slower compute relative to memory bandwidth, smaller on data-center GPUs. The accuracy claims depend on retrieving a sufficient number of tokens (100 for most tasks, 2000 for complex retrieval), which sets a lower bound on latency that cannot be reduced below the cost of accessing those tokens. The "no accuracy degradation" claim is approximately true in aggregate but overstates for the hardest retrieval task, where a small gap remains even with top-2000 retrieval (14.0% vs. 17.5% on Llama-3-8B KV Retrieval). The method is fundamentally bounded by the quality of the prefill query vectors as representatives of decoding queries—if this assumption fails (distribution shift between prompt content and generation needs), accuracy may degrade in ways not captured by the current benchmarks.

## 6. Limitations and Trade-offs

### 6.1 The Index Construction Assumes Prefill Queries Are Sufficiently Representative of Decoding Queries

**The assumption or constraint.** RetrievalAttention's attention-aware index is built from exact KNN connections between prefill query vectors and key vectors (Section 3.2, Stage 1). The decoding-time search then relies on this index structure to efficiently navigate from new query vectors to the relevant keys. This works only if the **query vector distribution during prefill is representative of the query vector distribution during decoding**—specifically, the pattern of which keys are relevant to which types of queries must be learnable from the prefill queries and transferable to generation queries. The paper acknowledges this implicitly when it states that "the queries from Q are significantly distant from the K vectors (OOD) while K themselves are very close" (Section 2.4), but the assumption that prefill queries adequately span the query distribution is never explicitly tested or ablated.

**The consequence.** If the prompt's content structure differs substantially from what the model will need to attend to during generation, the prefill query vectors may not capture the right query-key relevance patterns. Consider a long document followed by a single-sentence question: the prefill queries correspond to the model reading the document sequentially, where attention patterns reflect local coherence and document-level comprehension. The decoding queries for answering the question might require attending to completely different types of token relationships—specific fact lookups, cross-references between disparate parts of the document, or reasoning chains that never appeared during prefill. If the index was built from prefill queries that never needed to perform these types of retrievals, decoding queries may find themselves in regions of the index graph where the edges, projected from prefill KNN connections, point toward keys that are distributionally "nearby" for prefill-style queries but not for the actual retrieval need.

The failure mode would manifest as **degraded recall on generation queries that are OOD relative to the prefill query distribution**, causing critical tokens to be missed during dynamic retrieval and reducing task accuracy. This is distinct from the Q-K OOD problem the paper solves—that problem is about distribution mismatch between query and key vectors within a single attention head; this is about **distribution shift between prefill queries and decoding queries** over the course of generation. The paper's Needle-in-a-Haystack evaluation (Figure 5) partially addresses this by placing the needle at variable positions and testing retrieval, but the task structure (find a specific fact) is similar to what the prefill queries might naturally do while reading. More adversarial distribution shifts—e.g., prompts where the prefill is in one language and generation questions are in another, or prompts consisting primarily of narrative text where the generation task requires extracting tabular data—are not tested.

**What evidence exists in the paper.** The paper provides no direct measurement of prefill-to-decoding query distribution shift. The strong accuracy results on ∞-Bench and RULER (Tables 2 and 3) provide indirect evidence that the assumption holds for the evaluated benchmarks, but these benchmarks were not designed to stress-test query distribution shift. The Needle-in-a-Haystack experiments from 4K to 128K (Figure 5) and 250K to 1M (Figure 8) demonstrate that retrieval works across context lengths, but the query task (find the needle) is consistent throughout. The paper does not ablate prefill length, prompt structure, or task type to measure how representative the prefill queries need to be.

**Mitigation status.** The paper does not address this limitation. Section 8 (Conclusion) does not include it in future work. A natural mitigation would be to periodically update the index during generation as new query vectors become available—essentially, online index adaptation—but this would add substantial overhead and is not explored. Practitioners deploying RetrievalAttention on tasks with unusual prompt-generation mismatches should validate accuracy on their specific distribution.

### 6.2 The Difficulty Estimation and Index Construction Cost Is Not Accounted for in the Headline Latency Numbers

**The assumption or constraint.** RetrievalAttention's decoding latency numbers (Tables 4, 5, 7, 8) exclude the cost of index construction during the prefill phase. The attention-aware index requires computing exact KNN from every prefill query vector to every key vector (Stage 1 of index construction, Section 3.2), which is an `$O(n^2)$` operation in the prefill length `$n$`—the very quadratic complexity the method is designed to avoid during decoding. Additionally, the projection step (Stage 2) that converts the heterogeneous query-key graph into a homogeneous key-key graph requires processing all KNN connections and creating edges between keys that share query neighbors. The paper states that this is done during prefill and that "the KNN results can be efficiently computed via GPU" (Section 3.2), but provides no measurements of the actual cost.

**The consequence.** For interactive applications where users submit long prompts and expect quick responses, the prefill phase—including index construction—is on the critical path from request to first token. If index construction adds substantial latency to prefill, the total time-to-first-token could be significantly longer than with methods that simply compress the KV cache (e.g., SnapKV, StreamingLLM) or offload it without indexing (FlexGen). The paper's optimization in Appendix C notes that "we overlap the cache movement to the CPU with the full attention computation on the GPU in a pipeline manner," but full attention over 128K tokens is already expensive (~32.8 seconds on Llama-3-8B on A100 per Table 1, though this includes all layers), and the KNN computation duplicates some of this work. If index construction adds, say, 20–50% overhead to an already-slow prefill, the total latency from request submission to completed generation could be dominated by prefill despite fast decoding.

The paper's framing of "decoding latency" (Tables 4, 5, 7, 8) is legitimate for scenarios where prefill is handled separately—the paper explicitly cites context caching (Google Cloud, 2024) and prefill-decoding separation (Patel et al., 2024; Qin et al., 2024) as existing infrastructure that supports this separation (Section 3). However, these are specific deployment choices that not all practitioners have access to. For single-GPU deployments without a prefill-serving infrastructure, the prefill cost is part of the user-facing latency and cannot be amortized away.

More subtly, the paper does not characterize the **CPU memory and time cost of index construction itself** beyond the KV vector storage. Building per-head indexes for a 128K context with 32 layers and 8 KV heads means constructing 256 separate indexes (32 layers × 8 KV heads), each containing a graph over ~128K key vectors. The graph edge storage, the KNN computation, and the projection step all consume CPU memory and compute beyond what's measured. Table 8 shows that the 1M-token experiment uses 1.72 TB of CPU memory—far more than the ~125GB needed for the raw KV cache—suggesting substantial index overhead, but the paper does not break down how much is index structure versus KV vectors.

**What evidence exists in the paper.** The paper provides **no prefill latency measurement including index construction**, and **no breakdown of index memory overhead**. The only mention is the pipeline overlap note in Appendix C, which is qualitative. The CPU memory numbers for 128K contexts are not reported; the 1M-token experiment (Table 8) uses a machine with 1.72 TB of CPU memory, implying that the total memory footprint (KV cache + indexes) at 1M tokens is somewhere between 125 GB and 1.72 TB, but the exact breakdown is absent. This is a significant gap for practitioners who need to provision hardware.

**Mitigation status.** The paper does not measure prefill overhead, does not provide index memory breakdowns, and does not include these costs in headline latency claims. The text in Section 3 prefaces the work with "we focus on the acceleration of token generation and assume the prefill of the long-context prompt is done in advance, which is widely supported by existing LLM service providers," which is an honest scoping statement but shifts the burden to infrastructure that not all users have. The paper does not suggest future work on reducing index construction cost, though the planned 8-bit quantization (Appendix C) would reduce memory footprint if implemented.

### 6.3 Performance on the Hardest Retrieval Tasks Leaves a Non-Trivial Accuracy Gap Even with Increased Retrieval Budget

**The assumption or constraint.** RetrievalAttention's core claim is that it achieves "near full attention accuracy while only requiring access to 1–3% of the data" (Abstract). The method retrieves a fixed top-k tokens per attention head (default `$k=100$`, increased to `$k=2000$` for complex tasks). This implicitly assumes that the attention mass outside the top-k tokens is negligible for all tasks—that the `$\epsilon$`-thresholded attention approximation in Equation 2 captures essentially all of the information needed for task performance. The paper's own evidence shows this assumption breaks down on the most retrieval-intensive task.

**The consequence.** On the KV Retrieval task from ∞-Bench—which requires retrieving specific key-value pairs embedded in long synthetic contexts—RetrievalAttention with top-100 retrieval achieves 9.0% accuracy on Llama-3-8B versus 17.5% for full attention (Table 2, Retr.KV column). This is a **8.5 percentage-point gap**, or roughly half the full-attention performance. Increasing the retrieval budget to top-2000 closes most of this gap (14.0% vs. 17.5%), but a **3.5 point gap remains**. On Yi-9B, the corresponding numbers are 20.0% (top-100) and 30.0% (top-2000) versus 30.5% full attention—top-2000 nearly closes the gap, but top-100 leaves a 10.5 point deficit.

This matters because KV Retrieval is not an obscure edge case—it is a canonical long-context capability where the model must locate and reproduce specific information from a large context, directly testing whether sparse attention preserves fine-grained retrieval ability. The fact that even top-2000 (1.6% of a 128K context plus static tokens) cannot fully close the gap suggests that for this task, the attention scores have a **long tail of moderately relevant tokens** whose collective contribution cannot be discarded without measurable accuracy loss. The softmax re-normalization in Equation 2 redistributes the discarded mass proportionally among the kept tokens, but if the discarded mass is spread across many tokens that are individually small but collectively significant, the re-normalized distribution over kept tokens will be subtly but systematically different from the true attention distribution.

This is not a failure of the index—the recall micro-benchmarks (Figure 6) show that RetrievalAttention finds the true top-k keys with high accuracy. The limitation is in the **approximated attention formulation itself** (Equation 2): the method commits to only attending over `$I_{t,\epsilon}$` and discarding everything else, and if the task requires attending over more than `$|I_{t,\epsilon}|$` tokens with non-trivial scores, accuracy will degrade regardless of retrieval quality.

**What evidence exists in the paper.** The KV Retrieval results in Table 2 are the clearest evidence. For Llama-3-8B: Full Attention achieves 17.5%; RetrievalAttention top-100 achieves 9.0% (gap of −8.5); top-2000 achieves 14.0% (gap of −3.5). Even Flat (exact KNN with top-2000) achieves only 14.5%, confirming this is not an index quality problem—exact retrieval of the top-2000 tokens still leaves a 3-point gap, meaning some important tokens fall outside the top-2000. For Yi-9B, the gap narrows: top-2000 achieves 30.0% vs. 30.5% full attention (gap of −0.5), suggesting the needed retrieval budget is model-dependent.

The RULER results (Table 3) show smaller aggregate gaps (1.85 points for Llama-3-8B at 128K with top-100), but the detailed breakdown in Appendix E (Table 9) reveals task-level variation. On the FW (frequent word) aggregation task at 128K, RetrievalAttention achieves 49.3% versus 72.2% for full attention—a **22.9 point gap**—indicating that aggregation tasks where the answer depends on synthesizing information from many tokens are particularly affected by the retrieval budget. The CW (common word) task shows minimal gap (1.1% vs. 1.0%), but both are near floor performance.

**Mitigation status.** The paper acknowledges this implicitly by testing two retrieval budgets (100 and 2000) and showing that increasing the budget improves accuracy on KV Retrieval (Table 2). However, it does not frame the residual gap as a fundamental limitation of the fixed-top-k approximation—it presents the top-2000 result as evidence that RetrievalAttention "achieves nearly the same accuracy as full attention" (Section 4.2). The gap on KV Retrieval is not discussed in the limitations (the paper has no explicit limitations section), and there is no exploration of adaptive retrieval budgets that might vary k based on task difficulty or query characteristics. The PyramidKV experiment in Appendix F (Table 10) explores layer-wise budget reallocation but does not address per-query budget adaptation. For practitioners deploying on retrieval-heavy workloads, the paper does not provide guidance on how to choose k beyond the default values, or how to predict whether their task requires the larger budget.

### 6.4 The Evaluation Is Narrowly Scoped to Single-Batch Interactive Inference on a Single Task Family

**The assumption or constraint.** All experiments in the paper use **batch size 1** in a single-GPU setting. The paper justifies this by stating it follows "previous work (Tang et al., 2024) to run the benchmark in real-world single-batch scenarios" (Section 4.1). All benchmarks evaluate discrete-answer tasks—retrieval, question answering, multiple choice—with no measurement of generation quality, perplexity, or open-ended reasoning. All experiments use English-language text. The evaluation covers three model sizes from two model families (Yi-6B/9B, Llama-3-8B), all using GQA, and one larger model (Llama-3-70B) on a single task.

**The consequence.** The paper's headline claims—4.9× speedup, near-full-attention accuracy, first system to serve 8B models on RTX4090—are established only for the narrow regime of **batch-size-1, retrieval-and-QA tasks, English text, 6B–9B GQA models**. Several practically important regimes are untested:

- **Batch inference (throughput serving).** In production LLM serving, requests are often batched to maximize GPU utilization. With batch size > 1, the GPU's FlashAttention over static tokens becomes more efficient (matrix-matrix rather than matrix-vector), while the CPU-side index search for multiple queries simultaneously may become a bottleneck if the number of CPU cores is insufficient to parallelize across all heads × all batch elements. The relative speedup of RetrievalAttention over Flat and IVF could shrink or even reverse if the CPU search becomes the bottleneck while the GPU handles batched full attention efficiently.

- **Generation quality and perplexity.** The paper does not evaluate whether sparse attention via top-k retrieval affects the linguistic quality, coherence, or diversity of generated text. On language modeling benchmarks (e.g., PG19, BookCorpus), the per-token perplexity impact of discarding 97–99% of attention mass could be measurable even if task accuracy on discrete-answer benchmarks is preserved. This matters for applications like long-document summarization or creative writing, where output quality is not captured by exact-match accuracy.

- **Tasks requiring synthesis across many tokens.** The RULER FW (frequent word) task at 128K shows a 22.9-point gap for RetrievalAttention versus full attention (Table 9). This suggests that tasks requiring the model to aggregate information distributed across many tokens in the context are particularly vulnerable to sparse attention. The paper does not evaluate tasks like long-document summarization, multi-document synthesis, or complex multi-hop reasoning requiring attending to many distinct pieces of evidence—precisely the tasks that motivate long-context LLMs in the first place.

- **Non-GQA model architectures.** All tested models use Grouped Query Attention, which reduces the number of KV heads and thus the number of indexes to build and search. On models with full multi-head attention (e.g., earlier LLaMA or GPT variants), the number of indexes scales with the number of attention heads (often 32–64 per layer rather than 4–8), which would increase both index memory and search latency proportionally. The paper's per-head index design (Appendix C) would multiply costs on such architectures.

- **Mixed-prompt, multi-turn, and conversational settings.** The benchmarks use single-turn prompts with fixed contexts. In a multi-turn conversation, the KV cache grows incrementally across turns, and the prefill phase for each new user message may be short. The paper does not evaluate how the index adapts (or fails to adapt) when prefill is incremental and query distributions may shift across conversation turns.

**What evidence exists in the paper.** The paper provides no batch-inference, perplexity, generation-quality, conversational, or non-English evaluations. The model coverage is explicitly limited to GQA architectures, which the paper documents in Table 6 (Appendix A.1). The single-batch limitation is acknowledged in the setup description but not discussed as a limitation. The task diversity is evident from the benchmark descriptions (∞-Bench, RULER, Needle-in-a-Haystack), all of which are discrete-answer benchmarks.

**Mitigation status.** The paper does not discuss these scope limitations or propose future work to address them. The single-batch framing is presented as a deliberate choice following prior work, not as a limitation requiring future validation. Practitioners considering RetrievalAttention for batch serving, generation-quality-sensitive applications, multi-turn conversations, or non-GQA models should treat the paper's results as unvalidated for their use case and run their own evaluations.

### 6.5 The Static Pattern Size and Composition Are Not Ablated, Leaving a Critical Hyperparameter Unexplored

**The assumption or constraint.** RetrievalAttention's GPU-resident static pattern uses a fixed 640 tokens: 128 initial tokens plus a 512-token sliding window of recent tokens (Section 4.1, Table 2 caption). This decomposition is adopted from StreamingLLM (Xiao et al., 2024b) with the note that "RetrievalAttention can be adapted to utilize more complex static patterns (Li et al., 2024; Jiang et al., 2024), achieving the best trade-off between low inference cost and high accuracy" (Section 3.3). The paper does not vary this number, test alternative static pattern compositions, or measure the sensitivity of accuracy and latency to the static pattern size.

**The consequence.** The static pattern size directly controls three competing objectives:

1. **GPU memory consumption:** Each additional token in the GPU-resident KV cache consumes `$2 \times d \times \text{num\_layers} \times \text{num\_kv\_heads}$` bytes (for FP16 key and value vectors). For Llama-3-8B with `$d=128$`, 32 layers, and 8 KV heads, each token costs ~65 KB. Doubling the static pattern from 640 to 1280 tokens would add ~42 MB—small in absolute terms but potentially meaningful in the tight 24GB budget of an RTX4090 where model weights already occupy ~16GB.

2. **Accuracy on predictable-token tasks:** A larger static pattern covers more of the "attention sink" and local-context tokens that are universally important. This could improve accuracy on tasks where the critical information happens to fall within the static window, or reduce reliance on dynamic retrieval for tokens that are only slightly query-dependent.

3. **Dynamic retrieval quality:** The dynamic retrieval budget (top-k) operates on the remaining tokens after subtracting the static pattern. If the static pattern is too large and captures tokens that are only moderately important on average but query-specifically important in some cases, the dynamic retrieval index won't have the opportunity to retrieve them when they matter. Conversely, if the static pattern is too small, the index must handle more tokens, potentially reducing recall at a fixed scanning budget.

Without an ablation, practitioners cannot determine whether 640 tokens is near-optimal, conservative (trading GPU memory for safety), or aggressive (trading accuracy for GPU memory). The optimal static pattern size likely depends on the model architecture, the task type, and the GPU memory budget—but the paper provides no guidance on how to set it.

**What evidence exists in the paper.** The static pattern size of 640 tokens is stated in the Table 2 caption and used uniformly across all experiments. The paper provides no ablation varying this number. The "Act. Tokens" column in Tables 2 and 3 shows the total active tokens (static + dynamic) for each method, but the static component is never varied independently. The paper cites StreamingLLM and SnapKV as sources for static pattern design but does not evaluate whether those methods' static pattern choices transfer appropriately to a system that also has dynamic retrieval—the optimal static pattern for a pure static method may differ from the optimal static pattern for a hybrid static+dynamic system.

**Mitigation status.** The paper acknowledges in Section 3.3 that "RetrievalAttention can be adapted to utilize more complex static patterns," which implies the current pattern is a starting point rather than an optimized choice. However, the absence of any ablation or guidance means that practitioners must either use the same 640-token default (which may be suboptimal for their model, hardware, or task) or run their own expensive hyperparameter sweep. The paper does not include this in future work or discuss it as a limitation.

### 6.6 The Method Is Untested on Tasks Requiring Dense Attention Across the Full Context

**The assumption or constraint.** RetrievalAttention fundamentally assumes that for each query, only a small number of tokens (1–3%) contribute meaningfully to the attention output, and the remaining 97–99% can be discarded with negligible accuracy loss. This assumption is validated via recovery ratio measurements (Figure 2, blue curve) showing that top-1000 tokens recover ~89% of attention mass on average. However, this average masks head-level and task-level variation: some attention heads may be inherently dense, and some tasks may require the model to integrate weak signals from many tokens rather than strong signals from a few.

**The consequence.** On tasks where the correct answer depends on **aggregating information distributed across a large fraction of the context**—rather than locating a single piece of information—the sparse attention approximation may fail in ways not captured by retrieval accuracy or the benchmark suite used. Consider these hypothetical but realistic task types:

- **Long-document summarization:** Writing a summary of a 128K-token document requires synthesizing themes, facts, and narrative elements from throughout the text. Individual sentences may not be "critical" in the sense of having high attention scores, but collectively they define the document's content. If the model can only attend to 1–3% of tokens, the summary may be biased toward the few highly-attended passages and miss important but less attention-grabbing content.

- **Multi-hop reasoning across long contexts:** Answering a question that requires chaining together facts from paragraphs scattered across a long document may require attending to many intermediate tokens with moderate attention scores, each providing a link in the reasoning chain. If any link in the chain falls outside the top-k retrieval, the reasoning may fail even if each individual token's attention score is modest.

- **Statistical or pattern-analysis tasks:** Counts, frequencies, or comparisons across the context ("how many times does character X appear?" or "compare the arguments in sections 3 and 47") require attending to all relevant tokens, not just a sparse set.

The paper's RULER results provide direct evidence for this limitation. On the FW (frequent word) task at 128K context (Table 9, Appendix E), RetrievalAttention achieves 49.3% accuracy versus 72.2% for full attention—a **22.9 percentage-point gap**. The FW task requires the model to identify which word appears most frequently in a long context, a task that demands integrating weak signals from many token positions. This is the largest single-task gap in the entire evaluation, and it directly demonstrates that RetrievalAttention's sparse attention approximation breaks down when the task requires dense aggregation.

In contrast, tasks that require locating a single piece of information (Needle-in-a-Haystack, passKey retrieval, number retrieval) show minimal gaps (Table 2: 100% vs. 100% for RetrievalAttention on passKey and number retrieval for Llama-3-8B with top-100). The pattern is clear: **RetrievalAttention excels on sparse-retrieval tasks and degrades on dense-aggregation tasks**.

**What evidence exists in the paper.** The FW task result in Table 9 is the primary evidence, but the paper does not call attention to it as a limitation. The recovery ratio measurement in Figure 2 is averaged across all heads and all decoding steps; it does not report per-head variance, per-task variance, or worst-case recovery ratios. The paper does not evaluate on summarization, multi-hop reasoning, or other aggregation-heavy benchmarks. The gap between average recovery ratio (89% with top-1000) and worst-case recovery ratios is unknown—if some heads or queries have recovery ratios of 50–60% even with top-1000, those would be failure points for tasks requiring attention from those specific heads. The paper's focus on discrete-answer retrieval benchmarks means that the dense-attention limitation is underrepresented in the evaluation suite.

**Mitigation status.** The paper does not discuss dense-attention tasks as a limitation, does not evaluate on summarization or aggregation benchmarks beyond RULER's FW task, and does not propose mechanisms for detecting or handling queries that require denser attention (e.g., adaptive retrieval budgets based on query characteristics, head-specific budgets for known dense heads, or a fallback to denser retrieval when the model's confidence is low). The PyramidKV experiment (Appendix F) explores layer-wise budget allocation but does not address per-query or per-task adaptation for dense attention needs. For practitioners deploying on aggregation-heavy or summarization workloads, the FW result should serve as a warning that accuracy degradation may be substantially larger than the 1–2 point averages reported on retrieval-dominated benchmarks.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

RetrievalAttention makes a **diagnostic contribution that reframes a blocked research direction as newly viable**. Before this paper, the field's implicit consensus—formed through work like InfLLM, Quest, SparQ, and various static KV compression methods—was that exact vector search for attention was a dead end. The reasoning, though rarely stated explicitly, was pragmatic: ANNS indexes had been tried (MagicPiG with LSH, PQCache with product quantization) and found to require scanning ~20% of tokens for acceptable accuracy, which made them no faster than simply computing full attention with optimizations. The research community accordingly pivoted to coarser approximations: block-level retrieval, channel-dimension reduction, static heuristics, and learned token-selectors. These methods traded accuracy for speed, and the resulting degradation—StreamingLLM's 30-point accuracy collapse on ∞-Bench, InfLLM's near-zero performance on KV retrieval—was treated as an acceptable cost of long-context inference on commodity hardware.

The paper's core reorientation is to show that **the failure was not of vector search as an approach, but of distribution-unaware index construction**. The OOD diagnosis—query vectors are >10× farther from the key distribution than in-distribution keys are from each other (Figure 3b)—explains *why* prior ANNS attempts required scanning 20–50% of tokens (Figure 3a) and *why* the K-to-K control experiment achieves >0.95 recall at 1–5% scanning. This transforms the problem from "vector search doesn't work for attention" to "we were building the wrong indexes." The shift is conceptually analogous to what happened in neural information retrieval when researchers realized that off-the-shelf word-embedding similarity wasn't enough and that retrieval models needed to be fine-tuned on relevance signals—here, the relevance signal is the exact KNN mapping from prefill queries to keys, and the "fine-tuning" is the projection step that creates a query-aware key-key graph.

The paper also **reconciles conflicting findings in the sparse attention literature** by providing a framework for understanding *when* different approximation strategies fail. The predictable-dynamic decomposition (Section 3.3) explains why StreamingLLM works on local-context perplexity but fails on passKey retrieval (predictable tokens are sufficient for the former, dynamic tokens are essential for the latter), why InfLLM works on coarse-grained topical retrieval but fails on exact-match KV retrieval (block representatives lose token-level precision), and why SnapKV works on tasks where prefill attention patterns transfer to decoding but fails when generation requires attending to tokens not salient during prefill. This is a field-resolving framework: rather than treating method-benchmark outcomes as opaque empirical contingencies, researchers can now predict *which* tasks a given approximation strategy will handle and *why* it will fail on others. The FW task result in Table 9—a 22.9-point gap for RetrievalAttention versus full attention—is not an anomaly but a direct prediction of the framework: dense aggregation tasks require attending to many moderate-scoring tokens that fall outside the top-k retrieval budget.

The paper **shifts the research frontier from "how do we guess which tokens are important?" to "how do we build better indexes for query-key retrieval?"** This matters because index construction is a well-studied problem with decades of algorithmic research (proximity graphs, quantization, clustering, learned indexes), and the paper opens the door to adapting that entire toolkit to attention computation—provided the OOD gap is addressed. Prior work on efficient attention was largely *ad hoc*: each method proposed a new heuristic for token selection (representative vectors, low-rank scoring, static patterns) with limited theoretical grounding. RetrievalAttention repositions the problem as one of **cross-distribution approximate nearest neighbor search**, which has formal guarantees, established benchmarks, and a clear metric (recall vs. scanning percentage). This makes the problem more tractable and the research more cumulative: improvements to the index (better graph construction, learned entry points, adaptive search budgets) translate directly to better attention approximation, without reinventing the token-selection mechanism each time.

The practical impact is to **make long-context inference on commodity hardware a realistic deployment target rather than a research aspiration**. The paper's headline result—serving Llama-3-8B with 128K tokens on a single RTX4090 (24GB) at 0.188s/token—is not just a benchmark number; it's a **capability demonstration that changes what's possible without multi-GPU infrastructure**. Before this work, running an 8B model at 128K context on a consumer GPU meant choosing between (a) sub-minute-per-token latency (full attention without cache), (b) out-of-memory errors (KV cache in GPU memory), or (c) severe accuracy degradation (static compression methods). RetrievalAttention provides the first option that achieves all three desiderata simultaneously: fits in 24GB, runs at ~5 tokens/second, and maintains near-full-attention accuracy on most tasks. This democratizes long-context LLM inference—a researcher with a single consumer GPU can now experiment with 128K+ contexts on 8B models, which was previously the domain of well-resourced labs with multi-A100 setups.

**One direction becomes significantly less attractive after this paper**: developing new heuristic token-selection strategies that don't address the OOD gap. The paper's micro-benchmark (Figure 6) shows that even RobustVamana—a method specifically designed for OOD queries in ANNS—fails on attention vectors, while RetrievalAttention achieves in-distribution-level recall. This suggests that the OOD challenge in attention is distinctive and that generic OOD-ANNS solutions won't transfer without domain-specific adaptation. Research effort is better spent on understanding and exploiting the query-key distribution structure (via prefill KNN, projection, and related techniques) than on inventing new scoring heuristics that implicitly approximate the same thing with less precision.

### Follow-Up Research This Work Enables

**Adaptive retrieval budgets based on query-level difficulty estimation.** The paper shows that top-100 retrieval suffices for most tasks but top-2000 is needed for complex KV retrieval (Table 2), and that the FW aggregation task still shows a 22.9-point gap at top-100 (Table 9). This suggests that different queries—even within the same task—require different retrieval depths. A natural extension is to predict, at query time, how many tokens a given query needs to retrieve for accurate attention. The prediction could use lightweight features: the query vector's distance to the key distribution (larger distance → more OOD → larger budget needed), the entropy of the initial attention distribution over the static GPU tokens (high entropy → query is "uncertain" and needs broader retrieval), or the layer index (deeper layers may need different budgets, as PyramidKV suggests in Appendix F). A concrete experiment: on RULER, measure per-query retrieval budget vs. accuracy and train a small classifier that predicts, from the query vector alone, whether a budget of 100, 500, or 2000 is needed. The baseline is RetrievalAttention with fixed top-100; the target is matching full-attention accuracy on FW and similar aggregation tasks while keeping average scanning below 3%. This would transform RetrievalAttention from a fixed-budget to an adaptive-budget system, directly addressing the limitation in Section 6.3.

**Online index adaptation during generation as a defense against prefill-to-decoding query distribution shift.** Section 6.1 identifies the untested assumption that prefill queries are representative of decoding queries. When they aren't—e.g., when the prompt is narrative text and generation requires tabular fact extraction—the index edges, projected from prefill KNN patterns, may not guide decoding queries to the right keys. A follow-up could implement **lazy index updates**: after every N decoding steps, use the most recent decoding query vectors to compute exact KNN against the full key set (accepting the O(n) cost for these infrequent updates), then add or reweight edges in the index based on these new KNN connections. The key metric is whether decoding-time recall improves for queries that are OOD relative to prefill, and whether the periodic O(n) scans are amortized by sustained accuracy gains. A stress test: construct prompts where the prefill is in French and the generation question is in English (forcing cross-lingual query distribution shift), measure whether RetrievalAttention's accuracy degrades, and test whether online adaptation recovers it. This experiment would directly test the robustness boundary of the current method and provide a mitigation if needed.

**Combining RetrievalAttention with training-based sparse attention for a hybrid accuracy-efficiency frontier.** RetrievalAttention is training-free, which is a strength for deployment but leaves open the question of whether the index could be *improved* by light-weight training. A concrete direction: use the prefill KNN connections not just to project edges, but to train a small neural router (e.g., a 2-layer MLP per attention head) that predicts, from a query vector, which regions of the key space are likely to contain the top-k keys. This router could serve as an "entry point predictor" for the graph traversal, replacing the random or fixed entry point with a learned one that places the query closer to the right neighborhood before greedy search begins. The training signal is the exact KNN from prefill, so no additional labels are needed. The experiment would compare graph traversal steps (and thus latency) with and without the learned router, at equal recall, on Q-to-K search. This hybrid approach—training a small auxiliary component while keeping the base LLM frozen—preserves the practical advantages of RetrievalAttention while potentially pushing the accuracy-efficiency frontier further. It also opens a middle ground between fully training-free methods (this paper) and fully training-dependent methods (learned sparse attention patterns).

**Extending the attention-aware index to the prefill phase for end-to-end acceleration.** The paper explicitly scopes itself to decoding acceleration, assuming prefill is handled separately via context caching or phase splitting (Section 3). But if prefill cannot be amortized (e.g., in single-GPU interactive deployments), the prefill O(n²) attention cost plus index construction overhead may dominate total latency. A natural extension is to apply the same attention-aware index during the *second half* of prefill: after processing the first 25–50% of tokens with full attention (to collect enough query vectors for representative KNN), build the index, and then use it for sparse attention on the remaining prompt tokens. The experiment would measure prefill latency with and without this hybrid strategy, and prefill-to-decoding accuracy on long-context tasks. The key question is whether the index built from partial-prefill queries is good enough to avoid accuracy loss on the later prefill tokens (which are closer to the decoding phase in sequence position). This would extend RetrievalAttention from a decoding-only to a full-inference solution, broadening its applicability.

**Systematic characterization of the static-dynamic token allocation tradeoff with model- and task-specific optimization.** The paper uses a fixed 640-token static pattern (128 initial + 512 window) without ablation, leaving practitioners without guidance for their specific deployment (Section 6.5). A follow-up study could systematically vary static pattern size (from 128 to 4096 tokens), composition (initial-only, window-only, initial+window, SnapKV-style observation-based selection, or entropy-based selection), and dynamic retrieval budget (top-50 to top-4000), measuring the resulting accuracy-latency-memory Pareto frontier on ∞-Bench, RULER, and a new dense-aggregation benchmark (summarization, multi-hop QA). The deliverable would be a **decision tree or lookup table** mapping (model architecture, GPU memory budget, task type, context length) → (optimal static size, optimal retrieval budget). This is engineering work rather than algorithmic innovation, but it's essential for practical adoption and would directly address the paper's most significant unquantified hyperparameter. The FW task from RULER should be weighted heavily in this analysis, since it's the task where RetrievalAttention shows its largest accuracy gap and thus most needs optimized allocation.

**Cross-model and cross-architecture stress testing to establish generality.** The paper evaluates three 6B–9B GQA models from two families (Yi and Llama-3), plus one 70B GQA model on a single task (Appendix G). Open questions: Does RetrievalAttention work on models with full multi-head attention (MHA) rather than GQA, where the number of KV heads (and thus indexes) scales 4–8×? Does it work on non-transformer long-context architectures (e.g., Mamba, RWKV) if adapted? Does it work on encoder-decoder models where prefill queries come from the encoder and decoding queries from the decoder, creating an even larger distribution gap? A systematic evaluation across MHA models (e.g., Llama-2-7B, Mistral-7B with MHA), across parameter scales (1B, 7B, 13B, 70B), and across architectures would establish the method's generality or identify its failure modes. The key metric is whether the per-head index construction from prefill KNN continues to achieve >0.95 recall at 1–3% scanning across these diverse settings, or whether the OOD gap changes character (e.g., becoming larger for MHA due to more diverse query heads, or smaller for certain architectures due to different weight initialization or training dynamics). Negative results on specific architectures would be as informative as positive ones, defining the method's boundary conditions.

### Practical Applications and Downstream Use Cases

**Single-GPU long-context inference for independent researchers and small labs.** The paper's most immediate practical impact is enabling long-context LLM experimentation on consumer hardware. Before this work, running Llama-3-8B at 128K context required either multi-GPU setups (e.g., 3× A100 40GB just for the KV cache, per Table 1) or accepting sub-minute latency per token. With RetrievalAttention on a single RTX4090 (24GB, ~$1,600), a researcher can now achieve 0.188s/token at 128K context—roughly 5 tokens/second—while maintaining near-full-attention accuracy on retrieval tasks. This means a 128K-context experiment that generates 500 tokens takes ~94 seconds, versus ~4.5 hours with full attention without cache, making iterative experimentation feasible. Concrete use case: a computational social scientist analyzing a 100K-token interview transcript with a Llama-3-8B model can run thematic extraction, summarization, or QA on a single GPU workstation rather than requesting cloud GPU cluster access. The paper's results on ∞-Bench and RULER validate that accuracy on retrieval and QA tasks is preserved, covering the most common long-context analysis workflows.

**Cost-efficient batch processing of long documents for enterprise applications.** For organizations running batch inference over large document collections (legal document review, scientific literature mining, customer support ticket analysis), the paper's latency numbers translate directly to cost savings. On an A100 (Table 7), RetrievalAttention processes 128K-context tokens at 0.155s/token versus 0.564s/token for exact KNN—a 3.6× throughput improvement. For a batch of 10,000 documents averaging 100K tokens each, requiring 500 generated tokens per document for summarization, RetrievalAttention would complete in ~215 GPU-hours versus ~783 GPU-hours for Flat, saving ~570 A100-hours. At typical cloud pricing (~$2/A100-hour), this saves ~$1,140 per batch run. The accuracy preservation on the tested benchmarks (Tables 2 and 3) provides confidence that the cost savings don't come at the expense of output quality for retrieval and QA tasks, though practitioners should validate on their specific task type, particularly for aggregation-heavy workloads given the FW task gap.

**On-device or edge deployment of long-context assistants.** The paper's RTX4090 demonstration shows that 8B models with 128K context can run on a single consumer GPU. This opens the possibility of local, privacy-preserving long-context assistants—for example, a medical professional analyzing a 100K-token patient history with an open-source medical LLM, or a lawyer reviewing a 500-page contract, all running locally without sending sensitive data to cloud APIs. The 0.188s/token latency (5 tokens/second) is slower than cloud-based models but acceptable for asynchronous analysis tasks where the user submits a query and reads the response, rather than interactive chat. The key enabler is the GPU memory reduction: without RetrievalAttention, the KV cache alone would require ~15.6GB at 128K (Table 1), leaving only ~8.4GB for model weights on a 24GB card—insufficient for an 8B model. RetrievalAttention's offloading of KV vectors to CPU memory (where 128GB DRAM is cheap and standard) resolves this, making the GPU memory constraint about model weights rather than context length.

**Self-improvement and synthetic data generation pipelines with long contexts.** The paper's FLOPs-matched comparison (Section 7) concept—using test-time compute to substitute for larger models—is relevant here even though RetrievalAttention doesn't perform that analysis itself. For pipelines that use LLMs to generate training data (STaR, ReST, self-instruct) over long documents, the ability to process 128K+ contexts on modest hardware means data generation can scale to document-level tasks. For example, generating question-answer pairs from entire research papers (not just abstracts) or creating multi-turn dialogue datasets from full conversation transcripts. RetrievalAttention's training-free nature is particularly valuable here: the model generating the data is the same model that will be fine-tuned on it, and any modification to its architecture or weights would contaminate the data generation process. By operating purely at the inference-system level, RetrievalAttention allows the base model to generate data with full effective context at lower cost, without altering the distribution of outputs that the fine-tuning process will later learn from.

### When to Prefer This Method

The paper explicitly positions RetrievalAttention against named alternatives—StreamingLLM, SnapKV, InfLLM, Quest, FlexGen, Flat, and IVF—and its evaluation provides clear comparative evidence. The decision rules are grounded in the paper's empirical results rather than generic tradeoffs.

**Prefer RetrievalAttention over static KV compression methods (StreamingLLM, SnapKV) when:**
- Tasks require retrieving information from arbitrary positions in the context (passKey, number retrieval, KV retrieval, Needle-in-a-Haystack), where static methods achieve near-zero accuracy (StreamingLLM: 5.0% on passKey, SnapKV: 0.5% on KV retrieval; Table 2).
- Accuracy parity with full attention matters (gap of 0.5–2.0 points vs. 30.2 points for StreamingLLM on ∞-Bench; Table 2) and a 2–3× latency increase over static methods is acceptable (~0.188s vs. ~0.029s per token at 128K on RTX4090; Table 4).

**Prefer RetrievalAttention over block-based retrieval methods (InfLLM, Quest) when:**
- Tasks require token-level precision rather than block-level relevance (KV retrieval: 14.0% for RetrievalAttention top-2000 vs. 0.5% for InfLLM, 0.0% for Quest on Llama-3-8B; Table 2).
- Context length exceeds the effective range of block-based methods (RULER shows InfLLM accuracy drops from 85.2% at 4K to 25.7% at 128K; Table 3).

**Prefer RetrievalAttention over traditional ANNS (Flat, IVF) when:**
- Latency matters and context length is large—the speedup over Flat is 4.9× and over IVF is 1.98× at 128K on RTX4090 (Table 4), with the gap widening at longer contexts (Table 8).
- Context length is below ~4K, where IVF and Flat have comparable or slightly better latency (Table 4: 0.137s for RetrievalAttention vs. 0.128s for IVF at 4K) due to RetrievalAttention's fixed graph traversal overhead dominating when there are few vectors to scan.

**Prefer RetrievalAttention over full KV offloading (FlexGen) when:**
- Latency matters at all—FlexGen's per-token cost involves reloading the entire KV cache from CPU, which scales linearly with context length, while RetrievalAttention's cost scales sub-linearly (0.188s vs. implied multi-second latency for FlexGen at 128K on RTX4090; the paper describes FlexGen's approach as incurring "excessive communication overhead" in Section 2.2).

**Prefer RetrievalAttention over full attention (with or without KV cache) when:**
- Available GPU memory cannot hold the full KV cache (e.g., 128K context requires 15.6GB for Llama-3-8B KV cache alone, exceeding the 24GB RTX4090 budget when model weights consume ~16GB; Table 1) OR per-token latency with KV cache recomputation is unacceptable (43.9s/token at 128K on RTX4090; Table 4).

**Prefer full attention or exact KNN (Flat) when:**
- The task requires dense aggregation across many tokens (e.g., the FW task where RetrievalAttention shows a 22.9-point accuracy gap at 128K; Table 9), and accuracy is paramount over latency.
- The model architecture lacks GQA (untested in this paper), or prefill query representativeness is suspect (e.g., large prompt-generation distribution shift), and the deployment cannot tolerate unvalidated accuracy risk.
