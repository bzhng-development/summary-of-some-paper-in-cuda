# LazyLLM: Dynamic Token Pruning for Efficient Long Context LLM Inference

**ArXiv:** [2407.14057](https://arxiv.org/abs/2407.14057)

## 🎯 Pitch

This paper introduces **LazyLLM**, a training-free dynamic token pruning technique for accelerating long-context LLM inference that selectively computes KV cache entries only for tokens important to the next token prediction and defers the computation of remaining tokens to later generation steps when they become relevant.

---

## 1. Executive Summary

This paper introduces **LazyLLM**, a training-free dynamic token pruning technique for accelerating long-context LLM inference that selectively computes KV cache entries only for tokens important to the next token prediction and defers the computation of remaining tokens to later generation steps when they become relevant. Evaluated on the LongBench benchmark with Llama 2 7B and XGen 7B, LazyLLM applies progressive, layer-wise token pruning—using the prior transformer layer's attention scores to identify important tokens and pruning increasingly more tokens in later layers—combined with an Aux Cache mechanism that stores hidden states of pruned tokens, enabling them to be revived in subsequent generation steps without recomputation. On the multi-document question-answering task, LazyLLM achieves a 2.34× speedup in time-to-first-token while maintaining accuracy within 1% of the baseline, establishing that static, one-shot prompt pruning is unnecessary and that dynamic token selection across generation steps preserves performance only when pruned tokens can be selectively revived rather than permanently discarded.

## 2. Context and Motivation

### The Core Problem: Time-to-First-Token Is a Neglected Bottleneck

The inference pipeline of a transformer-based generative LLM has two sequential stages: **prefilling** and **decoding**. During prefilling, the model processes the entire input prompt — potentially thousands of tokens — computes the key-value (KV) cache for every token in every layer, and produces the first output token. During decoding, the model appends each newly generated token and reuses the cached KVs to produce subsequent tokens iteratively.

The time required for the prefilling stage is called **time-to-first-token (TTFT)**. For long prompts, TTFT dominates the latency profile. The paper reports a striking statistic from profiling on the LongBench benchmark: for the Llama 2 7B model, TTFT requires **21× the wall-clock time of each subsequent decoding step** and accounts for approximately **23% of total generation time**, even though the average LongBench prompt has only 3,376 tokens and average generation length is only 68 tokens (Section 1). This means that after submitting a long prompt, a user waits several seconds before seeing any response — exactly the kind of latency that creates a poor interactive experience.

The fundamental reason TTFT is slow is the **quadratic cost of self-attention** with respect to sequence length. A prompt of $N$ tokens requires $O(N^2)$ attention computations across all layers. In a deep model like Llama 2 7B, with 32 transformer layers and a model dimension of 4,096, the cost of precomputing KVs for a long prompt constitutes a substantial fraction of the total inference budget.

Despite this, the research community has invested considerably more effort in accelerating the decoding stage — through techniques like speculative decoding (Leviathan et al., 2023), Medusa (Cai et al., 2024), KV cache compression (Zhang et al., 2024; Li et al., 2024), and speculative streaming (Bhendawade et al., 2024) — while **relatively little attention has been paid to improving TTFT**. The paper explicitly calls this out:

> "there is little attention given to improving TTFT"

This asymmetry is the gap that LazyLLM is designed to address.

### Why the Problem Is Important: Practical and Structural

The importance of TTFT reduction extends beyond a single benchmark statistic.

**Practical user experience.** When users interact with LLM-powered assistants, the latency between submitting a query and receiving the first token sets the tone for the interaction. Research on perceived performance in human-computer interaction consistently shows that response times exceeding a few seconds degrade user satisfaction, regardless of how quickly the remainder of the response streams. For long-context applications — document summarization, multi-document QA, repository-level code completion, retrieval-augmented generation with large retrieved contexts — TTFT becomes the dominant contributor to perceived latency.

**Structural limitation of the prefilling-decode paradigm.** The standard inference pipeline treats all prompt tokens uniformly during prefilling: every token's KV is computed and cached, regardless of its actual relevance to generating the first output token. This is inherently wasteful if many tokens in the prompt carry little or no useful information for the initial prediction. The paper's central motivating question is deceptively simple:

> "Are all prompt tokens essential for generating the first token?"

If the answer is "no" — and the paper provides evidence that it is — then TTFT optimization becomes a matter of identifying and leveraging that redundancy, not of making individual attention operations faster.

**Growing relevance with context length scaling.** Recent LLMs increasingly support ultra-long context windows (32K, 128K, even 1M tokens). As models grow more capable of processing longer documents, the ratio of prompt length to generation length will increase, making the prefilling stage an ever-larger fraction of total inference cost. Optimizing TTFT is therefore not a one-time fix but a necessity that scales with the trajectory of LLM development.

### Where Prior Approaches Fall Short

The paper identifies several lines of prior work that touch on inference efficiency but fail to adequately address TTFT:

#### 1. Efficient Long-Context Architectures Require Retraining

Approaches like Longformer (Beltagy et al., 2020), which replaces standard self-attention with a combination of local windowed attention and task-specific global attention, and Reformer (Kitaev et al., 2020), which uses locality-sensitive hashing to reduce attention complexity, can make long-context inference faster. However, these are **architectural innovations** that require changing the model and retraining from scratch. The paper notes this is a critical limitation:

> "Though the above methods can speed up long context inference, they require significant model architecture change and re-training. This drawback makes them impractical to be applied to existing pre-trained LLMs."

For the vast majority of practitioners using off-the-shelf models like Llama 2, these methods are simply not applicable. There is a clear need for techniques that can accelerate inference **without modifying model weights or requiring any training**.

#### 2. Decoding-Stage KV Cache Optimizations Don't Help TTFT

A growing body of work optimizes KV cache usage during decoding. **H2O** (Zhang et al., 2024) identifies "heavy-hitter" tokens based on cumulative attention scores and evicts less important tokens from the KV cache to reduce memory footprint during decoding. **SnapKV** (Li et al., 2024) similarly compresses the KV cache by selecting informative key-value pairs before generation begins. These methods effectively reduce decoding latency and memory usage, but they share a critical characteristic: they **require accumulating full attention maps from the first few generated tokens** to determine which prompt tokens are important. Consequently, the full KV cache must still be computed during prefilling, meaning TTFT is not reduced. As the paper states:

> "these approaches require accumulating the full attention maps of predicting the first few tokens to profile the importance of prompt tokens before starting pruning. Consequently, they are not applicable to reduce TTFT as they still require computing all the KV cache at the prefilling stage."

This is a fundamental limitation: if you need to see which tokens matter by first computing everything, you've already incurred the cost LazyLLM aims to eliminate.

#### 3. Static Token Pruning Is Too Aggressive

Token pruning has been successfully applied to encoder-only models for classification tasks. Learned Token Pruning (Kim et al., 2022) adaptively removes unimportant tokens as an input sequence passes through transformer layers, reducing computation for tasks like text classification that require only a single forward pass. MAGIC Pyramid (He et al., 2021) similarly prunes tokens for BERT-like models.

However, extending token pruning to generative LLMs poses a qualitatively different challenge. In a classification task, the model makes a single prediction — once a token is pruned, it's gone for good, and the only question is whether the pruning damaged the final output. In a generation task, the model produces a sequence of tokens, each conditioned on the full preceding context. A token that seems irrelevant for generating the first output token might become crucial for generating the tenth. As the paper puts it:

> "a natural question arises: Are all prompt tokens essential for generating the first token?"

The mismatch is that static pruning — making a one-time decision about which tokens to keep for the entire generation — is fundamentally at odds with the sequential nature of generation. Different generation steps may need different contextual information. The paper's Figure 3 comparison between standard LLM inference and LazyLLM explicitly shows this: the static approach keeps a fixed subset throughout, while LazyLLM allows different subsets at each step.

#### 4. Prompt Compression Has Prohibitive Overhead

Prompt compression methods like LLMLingua (Jiang et al., 2023) and Selective Context (Li et al., 2023) aim to reduce the prompt length before feeding it to the LLM, thereby reducing both TTFT and overall computation. The idea is straightforward: use a smaller or the same LLM to identify and remove redundant tokens/sentences from the prompt, then run inference on the compressed version.

The paper reports a critical finding that undermines this approach:

> "the overhead of running LLMs to compress the prompt is very computationally expensive. Even though the inference on the reduced prompt is faster, the actual TTFT of the 'prompt compression' baseline is longer than the baseline."

In Table 1, Prompt Compression achieves a TTFT *slowdown* across all tasks: 0.12× speedup for Llama 2 (meaning it's ~8× slower than baseline) and 0.20× for XGen (5× slower). The compression step itself consumes more computation than the savings from operating on a shorter prompt. This is the "you have to spend computation to save computation" paradox — in this case, the spending outweighs the saving. Prompt compression may reduce total FLOPs but does not reduce TTFT, because TTFT is measured from when the user submits the prompt to when the first token appears, and compression happens in that window.

#### 5. Quantization and Structured Pruning Are Orthogonal

Methods like GPTQ (Frantar et al., 2022), Wanda (Sun et al., 2023), and LLM-Pruner (Ma et al., 2023) compress model parameters to reduce the per-operation cost of inference. These are effective techniques that the paper acknowledges, but they operate on a different axis: they make *every* operation cheaper by reducing model size, rather than reducing *how many* operations are performed. LazyLLM is complementary to these approaches — it reduces the number of tokens that need processing, and could presumably be combined with quantized or pruned models for multiplicative speedups.

#### 6. KV Cache Eviction During Decoding Doesn't Help TTFT

Several methods (Zhang et al., 2024; Li et al., 2024; Adnan et al., 2024; Nawrot et al., 2024) optimize the KV cache during decoding by evicting less important KV pairs, reducing memory usage and data transfer. These are effective for accelerating the decoding stage, but they all share the property of starting *after* the prefilling stage, meaning they leave TTFT completely untouched. LazyLLM distinguishes itself by being applicable from the very first inference step — the prefilling stage itself — which is what allows it to reduce TTFT.

### How This Paper Positions Itself

LazyLLM positions itself at the intersection of several design desiderata that no prior method simultaneously satisfies:

1. **Training-free**: requires no fine-tuning, no parameter modification, no architectural changes. Works with off-the-shelf model checkpoints.
2. **TTFT-focused**: reduces computation from the very first inference step (the prefilling stage), not just from decoding onward.
3. **Dynamic, not static**: allows different subsets of tokens to be selected at different generation steps, with the ability to *revive* previously pruned tokens when they become relevant.
4. **Guaranteed worst-case runtime**: the Aux Cache mechanism ensures that each token is computed at most once per layer across the entire generation process, meaning LazyLLM is never slower than the baseline even in pathological cases where all tokens get revived.

The paper's empirical motivation comes from Figure 2, which visualizes the attention scores of input tokens with respect to the first generated token for each layer of Llama 2 7B on a LongBench sample. The attention map is visibly sparse, with most tokens receiving near-zero attention scores across all layers. The distribution plot (Figure 2b) reinforces this: the vast majority of tokens have average attention scores below 0.05, with only a small fraction receiving meaningful attention. This observation — that attention is highly sparse for next-token prediction — is the **empirical foundation** that justifies the core LazyLLM hypothesis:

> "many tokens in the input prompt are redundant and can be safely removed without affecting the next token prediction"

Critically, LazyLLM does not assume that a token pruned early is permanently useless. The framework explicitly allows the model to select different token subsets at each generation step, and the Aux Cache enables efficient revival without recomputation. This distinguishes it from both static pruning and permanent compression, and is what the paper argues is "crucial to retaining the performance" when extending token pruning to generative LLMs.

The paper also explicitly connects to the early exiting literature (Elhoushi et al., 2024), which shows that token hidden states "gradually evolve through the transformer layers." LazyLLM uses this insight to justify progressive pruning: keep more tokens in early layers (where representations are still evolving and importance is harder to judge) and prune more aggressively in later layers (where representations have stabilized and the importance signal is cleaner). The ablation study in Section 5.4 (Figure 6) supports this: pruning at later layers consistently yields better accuracy at the same retention ratio.

## 3. Technical Approach

### 3.1 Reader Orientation

**What the system is:** LazyLLM is a training-free, plug-and-play technique that can be inserted into any existing transformer-based LLM to selectively skip the computation of key-value (KV) cache entries for tokens that are unlikely to influence the next token prediction, deferring that computation to later generation steps when those tokens might become relevant. **What problem it solves:** It reduces time-to-first-token (TTFT) — the latency between submitting a prompt and receiving the first output token — by recognizing that most input tokens receive negligible attention when predicting the first token, and progressively pruning them during the prefilling stage rather than computing their full KV cache up front, while retaining the ability to revive them later if needed via a lightweight caching mechanism.

### 3.2 Big-Picture Architecture (Diagram in Words)

LazyLLM has five interrelated components that operate across every generation step:

1. **Attention-Based Token Importance Scorer:** At each transformer layer, uses the attention map from the *current* layer to assign a confidence score to every input token with respect to the token being predicted. This determines which tokens are worth keeping for the next layer.

2. **Progressive Layer-Wise Token Pruner:** Starting with the full set of input tokens in early transformer layers, progressively removes an increasing fraction of tokens in later layers based on their importance scores. Early layers keep most tokens; later layers operate on an increasingly sparse subset.

3. **Aux Cache (Auxiliary Hidden State Cache):** A secondary cache, separate from the standard KV cache, that stores the hidden states of tokens that are pruned at a given layer. These stored hidden states can later be retrieved without recomputation if a pruned token is revived in a subsequent generation step.

4. **Per-Step Dynamic Token Selection:** In each generation step (prefilling and every subsequent decoding step), the model independently selects which subset of the original prompt tokens to process, using the attention scores from that step. A token pruned in one step can be revived in any later step.

5. **Standard KV Cache:** Operates as in normal LLM inference, but only contains entries for tokens that were actually processed at each layer, not for the full prompt.

**Information flow in one generation step:** The full prompt enters step `$t$` → At each transformer layer `$l$`, the attention map is computed for the tokens currently being processed → Confidence scores are computed from this attention map → Tokens with scores below the `$k_l$`-th percentile are pruned for layer `$l+1$`, and their hidden states are saved to the Aux Cache → For tokens that survive, standard KV computation continues → At the next generation step `$t+1$`, the process repeats from scratch with the full token set available: some tokens will have their KVs in the main KV cache (they were processed previously), others will have their hidden states in the Aux Cache (they were pruned but can be revived), and some may be entirely new.

### 3.3 Roadmap for the Deep Dive

- **First**, the progressive token pruning mechanism — how importance scores are computed, how pruning thresholds are set, and how layers are partitioned into different pruning regimes — since this is the core computational idea that enables TTFT reduction.
- **Second**, the Aux Cache design — why a simple extension of progressive pruning from prefilling to decoding fails without it, what it stores, and how it guarantees the worst-case runtime bound — because this mechanism is what makes the dynamic token revival practically feasible rather than a theoretical possibility.
- **Third**, the full per-generation-step inference procedure — how the KV cache, Aux Cache, and progressive pruner interact in a single generation step — to show the end-to-end system in operation.
- **Fourth**, the design choices and their justifications — the layer-wise percentile-based thresholding, the progressive pruning schedule, the decision to use the prior layer's attention map — to explain why the system works the way it does rather than alternative formulations.
- **Fifth**, the configuration space — the three hyperparameters that control the accuracy-speedup tradeoff and how they interact — because understanding this parameterization is essential for interpreting the experimental results.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems and methods paper** whose core idea is that dynamic, per-step token pruning with the ability to revive previously pruned tokens can reduce TTFT without accuracy loss, and that this can be implemented without model modification by using the model's own attention scores as the importance signal.

---

#### Progressive Token Pruning

**The attention-based importance scoring function.** In each generation step, as the model processes tokens through its transformer layers, LazyLLM uses the attention map of the *current* layer `$l$` to determine which tokens are important for predicting the next token. For each input token `$t_i$`, the system computes a single scalar confidence score `$s^l_i$` that aggregates the attention that the token being predicted (the last position in the sequence, indexed `$N$`) pays to `$t_i$` across all attention heads at layer `$l$`:

$$s^l_i = \frac{1}{H} \sum_{h=1}^{H} A^l_{h,i,N}$$

where `$H$` denotes the number of attention heads, `$N$` is the current sequence length (prompt tokens plus any previously generated tokens), and `$A^l_{h,i,N}$` is the attention probability of the `$N$`-th position attending to token `$t_i$` at the `$h$`-th attention head in layer `$l$`.

**What it computes:** the score `$s^l_i$` is the average attention probability — across all heads — that the next-token-to-be-predicted assigns to input token `$t_i$` at layer `$l$`. A high score means that at layer `$l$`, the model is strongly attending to token `$t_i$` when forming its representation of the next token; a low score means token `$t_i$` is largely being ignored. The result is a single scalar per input token per layer, in the range `$[0, 1]$`.

**Why this form:** using the attention map of layer `$l$` to decide which tokens to keep for layer `$l+1$` reflects the assumption that token importance evolves gradually through the transformer depth. The attention weights at layer `$l$` represent which tokens the model has *already learned to attend to* at that depth; the assumption is that tokens receiving negligible attention at layer `$l$` are unlikely to suddenly become crucial at layer `$l+1$`. Averaging across heads provides robustness — a token that receives high attention from even one head might be important, and averaging captures this rather than being vetoed by other heads that ignore it. The alternative of using a single head's attention would be brittle; using the maximum across heads would be overly conservative and keep too many tokens.

**The top-k percentile selection strategy.** After computing the scores `$s^l_i$` for all input tokens at layer `$l$`, the system must decide which tokens to prune — i.e., which tokens to exclude from computation at layer `$l+1$`. LazyLLM uses a percentile-based threshold rather than an absolute threshold:

> "token `$t_i$` is pruned at layer `$l+1$` if its confidence score `$s^l_i$` is smaller than `$k_l$`th percentile among the input tokens"

Concretely, the system sorts all `$s^l_i$` values, computes the `$k_l$`-th percentile of that distribution, and removes any token whose score falls below that percentile. The parameter `$k_l$` is a number between 0 and 100 that specifies what fraction of tokens are *kept* at layer `$l+1$` — setting `$k_l = 70$` means only the top 70% of tokens by attention score survive to the next layer, and the bottom 30% are pruned. Once a token is pruned at layer `$l$`, it is excluded from all subsequent layers in that generation step — the set of active tokens at layer `$l+1$` is always a subset of the set at layer `$l$`.

**Why percentile-based rather than absolute threshold:** the distribution of attention scores varies across layers and across tasks. Early layers might produce more uniform attention distributions; later layers might spike sharply on a few tokens. An absolute threshold (e.g., prune all tokens with score below 0.01) would prune too aggressively in some layers and too conservatively in others, because the scale of attention scores changes. The percentile approach adapts automatically: regardless of the absolute score values, it prunes a fixed fraction of the least-attended-to tokens.

**Why top-k rather than bottom-k:** the paper describes this as the "top-k percentile selection strategy" — the `$k$` refers to the percentile of tokens that are *kept*, not pruned. This is a design choice that keeps the interpretation simple: for a given `$k$`, the user knows exactly what fraction of tokens will be computed at the next layer. The alternative — specifying what fraction to prune — would be semantically equivalent but less directly connected to the computational cost.

**The progressive pruning schedule.** The paper does not apply a single pruning ratio uniformly across all layers. Instead, it defines a schedule that prunes different fractions of tokens at different depths. This schedule is controlled by three hyperparameters:

1. **The number of pruning layers** — how many times during the transformer stack the system performs a pruning operation.
2. **The locations of these pruning layers** — at which specific layer indices pruning occurs.
3. **The number (or fraction) of tokens pruned at each pruning layer** — what `$k_l$` percentile is used at each pruning location.

The default configuration described in Section 4 and illustrated in Figure 4 uses a three-stage progressive pruning schedule: prune 30% of tokens at an early set of layers, then another 30% at a middle set of layers, then another 30% at a late set of layers. The specific layer assignments mentioned in Figure 4 are: roughly 10% of layers for the first pruning stage, 30% for the middle (non-pruning) layers, then another pruning at approximately 30% of layers, then the final 30% of layers with the most aggressive pruning.

**Why progressive rather than one-shot pruning:** the ablation study in Section 5.4 (Figure 6) provides the empirical justification. When pruning at the same transformer layer, the model's performance degrades monotonically as more tokens are removed. More importantly, pruning at later layers consistently yields better performance than pruning at earlier layers with the same retention ratio. This suggests that earlier layers need access to more context to build good representations, while later layers can operate on a sparser subset because the important information has already been aggregated into the surviving tokens' representations. A progressive schedule — keep more tokens early, prune more aggressively late — exploits this asymmetry.

**The connection to gradual representation evolution:** the paper cites Elhoushi et al. (2024)'s finding that token hidden states "gradually evolve through the transformer layers" as motivation. The intuition is that in early layers, each token's representation is still being refined and enriched with contextual information from other tokens, so pruning early risks discarding tokens before their information has been properly integrated into the surviving tokens' representations. By the later layers, the important information from pruned tokens has already been absorbed by the tokens that survive, making aggressive late-stage pruning safer.

#### The Aux Cache: Enabling Efficient Token Revival Across Generation Steps

**The problem: extending progressive pruning to decoding steps causes missing KV entries.** During the prefilling stage, there is no pre-existing KV cache — every token's representation starts as a raw hidden state (embedding + positional encoding). When LazyLLM prunes a token at layer `$l$` during prefilling, it simply removes that token's hidden state from the computation of layer `$l+1$`. This is straightforward because there's no prior cache to worry about.

However, during *decoding* steps, the model relies on the KV cache computed during prefilling to efficiently compute attention. The standard decoding step works as follows: for each layer, the model retrieves the pre-computed keys and values for all *past* tokens from the KV cache, and only needs to compute the key and value for the *newly generated* token, which are then appended to the cache. But if LazyLLM pruned certain tokens during prefilling, those tokens' KV entries at layer `$l+1$` and beyond were never computed, and therefore don't exist in the KV cache.

**The revival requirement creates a dilemma.** Suppose token `$T_4$` was pruned at layer `$l$` during prefilling, so it has no KV cache entry at layer `$l+1$`. In a subsequent decoding step, the model may decide (based on that step's attention scores) that `$T_4$` *is* important and should be revived — i.e., included in the computation of layer `$l+1$`. This creates a problem: the model needs `$T_4$`'s hidden state at the input to layer `$l+1$`, but that hidden state was never computed (because `$T_4$` was pruned at layer `$l$`). The naive solution — pass `$T_4$` through all layers from the beginning of the transformer again — would cause repetitive computation, undermining the efficiency gains. As the paper states:

> "that would cause repetitive computation for the same token, and eventually slow down the whole generation"

**The Aux Cache solution.** LazyLLM introduces an auxiliary cache — the **Aux Cache** — in addition to the standard KV cache. The Aux Cache stores the **hidden states** of pruned tokens at the layer where they were pruned. Specifically, if token `$T_i$` is pruned at layer `$l$` (meaning it won't be computed at layer `$l+1$`), its hidden state output from layer `$l$` is saved in the Aux Cache associated with layer `$l$`.

When, in a later generation step, the model decides to revive token `$T_i$` at layer `$l+1$` (because its KV doesn't exist in the KV cache for that layer), the system retrieves `$T_i$`'s saved hidden state from the Aux Cache of layer `$l$`. This hidden state — which is exactly the input that `$T_i$` *would have* provided to layer `$l+1$` if it hadn't been pruned — is then fed directly into layer `$l+1$`'s computation. The key property is:

> "The introduction of Aux Cache ensures that each token is computed at most once in every transformer layer, and ensures the worst runtime of LazyLLM is not slower than the baseline."

**What the Aux Cache stores vs. what the KV cache stores.** The standard KV cache stores the key and value vectors for each token at each layer — these are intermediate results needed for computing attention scores and attention outputs, but they are not the token's full hidden state (the output of the MLP + residual connection). The Aux Cache stores the full output hidden state of the pruned token at the pruning layer, which is what the next layer needs as input. This distinction matters: reviving a token from its hidden state allows the model to skip all prior layers for that token and jump directly into the appropriate layer, avoiding recomputation.

**Concrete example from Figure 4.** The figure shows tokens `$T_1$` through `$T_9$` being processed. At layer `$l$`, tokens `$T_2$`, `$T_4$`, and `$T_7$` are pruned (have their hidden states added to the Aux Cache), while `$T_1$`, `$T_3$`, `$T_5$`, `$T_8$`, `$T_9$` survive to layer `$l+1$`. At layer `$l+1$` during a decoding step, the model needs to compute attention. For token `$T_1$`: its KV exists in the KV cache (it was computed during prefilling), so it's retrieved directly with no computation needed. For token `$T_3$`: if it was pruned at layer `$l$` during prefilling but is being revived now, its hidden state is retrieved from the Aux Cache of layer `$l$` and fed into layer `$l+1$`, where it will be computed fresh (its KV will be generated and cached for this layer). For tokens being revived, only the layers from the revival point onward need computation — all earlier layers are bypassed.

**Guarantee against slowdown.** The "at most once" guarantee is significant: in the worst case where every pruned token is revived in every subsequent generation step, the total computation equals exactly what the baseline would have done — no token is ever recomputed from scratch. This means a user can adopt LazyLLM without risk of pathological slowdown. If the pruning heuristics fail and the model decides it needs almost all tokens at every step, performance degrades gracefully to the baseline speed, not worse.

**Why not just re-run through all layers?** Storing the hidden states in the Aux Cache trades memory for compute. The memory overhead is proportional to the number of tokens pruned times the hidden state dimension, which is manageable because hidden states are stored only at pruning boundaries, not at every layer. If instead the system re-ran pruned tokens through all prior layers, it would repeat the most expensive part of the computation (attention over the full sequence in early layers) every time a token was revived, which would compound with the number of decoding steps and easily eliminate any speedup.

#### Full Per-Generation-Step Inference Procedure

This section describes the end-to-end operation of LazyLLM for a single generation step `$t$`, integrating the progressive pruner, KV cache, and Aux Cache into a coherent procedure.

**Step 1: Initialize the active token set.** At the start of generation step `$t$`, all input tokens are conceptually available. The system does not pre-determine which tokens will be pruned — the pruning decisions will be made dynamically at each pruning layer based on that layer's attention scores. The newly generated token from step `$t-1$` (or the first token to be generated, during prefilling) is appended to the sequence.

**Step 2: Process tokens through early layers (no pruning).** The first set of transformer layers operates on the full token set. These early layers compute standard self-attention over all tokens, update hidden states, and populate the KV cache with keys and values for all tokens. No tokens are pruned in this stage. The paper's default configuration has approximately 10% of layers in this phase, though the exact fraction is configurable.

**Step 3: First pruning event.** At a designated pruning layer `$l_1$`, the system computes attention scores `$s^{l_1}_i$` for all input tokens using the attention map from layer `$l_1$` with respect to the last sequence position. It then applies the top-k percentile threshold with a specified `$k_1$` (e.g., keep top 70%, prune bottom 30%). Tokens falling below the `$k_1$`-th percentile are pruned: their hidden states at the output of layer `$l_1$` are saved to the Aux Cache for layer `$l_1$`, and they are excluded from computation at layer `$l_1+1$` and all subsequent layers (unless revived in a future generation step).

**Step 4: Process the surviving tokens through middle layers.** The surviving subset of tokens continues through the next set of transformer layers. At each of these layers, attention is computed only over the surviving tokens (plus the newly generated token), not the full original prompt. This reduces the quadratic attention cost. KV cache entries are created and stored only for these surviving tokens. During these middle layers, no additional pruning occurs — the token set remains constant. The paper's default has approximately 30% of layers in this non-pruning phase.

**Step 5: Second pruning event.** At a second designated pruning layer `$l_2$`, the attention map is again used to compute importance scores `$s^{l_2}_i$` for the *currently active* tokens. A second top-k percentile threshold `$k_2$` is applied (e.g., keep top 70% of *surviving* tokens, pruning another 30% of the original tokens). Pruned tokens' hidden states are saved to the Aux Cache at layer `$l_2$`.

**Step 6: Process through late layers with further pruning.** The further-reduced token set continues through another block of layers (approximately 30%), followed by a third pruning event with threshold `$k_3$`, and finally through the last layers (approximately 30%) with the final reduced token set. By the end of the transformer, the number of active tokens has been progressively reduced to a small fraction of the original prompt.

**Step 7: Produce the output token.** The output of the final transformer layer at the last sequence position is projected to vocabulary logits, and the next token is sampled or greedily selected.

**Step 8: Transition to the next generation step.** For generation step `$t+1$`:
- The newly generated token from step `$t$` has its KV entries in the KV cache for all layers.
- Tokens that survived all pruning stages in step `$t$` have complete KV cache entries for all layers.
- Tokens that were pruned at some layer in step `$t$` have KV entries for the layers they survived, but are missing entries from the layer where they were pruned onward. Their hidden states at the pruning layer are available in the Aux Cache.
- At step `$t+1$`, the process restarts from Step 1 with the full original prompt available. The model may select a completely different subset of tokens. When a previously pruned token is selected for revival at layer `$l+1$`, the system checks: does a KV entry exist in the KV cache for layer `$l+1$`? If yes, use it; if no, retrieve the hidden state from the Aux Cache at layer `$l$` and compute forward from layer `$l+1$`.

**What happens during decoding vs. prefilling.** The primary difference between prefilling and decoding is whether a KV cache already exists. During prefilling, there is no prior KV cache — every active token is computed from scratch at every layer it survives, and the KV cache is being populated for the first time. During decoding, the KV cache contains entries from prefilling and previous decoding steps. The computation in each decoding step is minimal: for surviving tokens that already have KV cache entries at a layer, only retrieval is needed (no computation). For revived tokens, only the layers from the revival point onward need fresh computation. For the newly generated token, KV is computed for all layers. This is why LazyLLM's speedups are most dramatic for TTFT (prefilling) but also extend to overall generation (since some tokens are never computed even across the full decoding trajectory).

---

#### Design Choices and Their Justifications

**Why use the prior layer's attention map for the current layer's pruning decision.** The paper uses the attention map from layer `$l$` to decide which tokens survive to layer `$l+1$`. This introduces a one-layer lag: the decision about layer `$l+1$`'s inputs is based on layer `$l$`'s outputs. The alternative — using layer `$l+1$`'s own attention map — would require computing layer `$l+1$`'s attention over the full token set to get the scores, which defeats the purpose of pruning (the computation has already been done). The one-layer lag is a pragmatic compromise: the attention map from layer `$l$` is a reasonable proxy for token importance at layer `$l+1$` because representations evolve gradually. The empirical validation in Figure 6 shows that pruning decisions made at layer `$l$` do not cause catastrophic degradation at layer `$l+1$`, supporting this assumption.

**Why attention to the last position specifically.** The confidence score `$s^l_i$` measures attention from the *last* sequence position (the token being predicted) to each input token `$t_i$`. This is a natural choice because the goal of pruning is to identify tokens that are unimportant for *predicting the next token*. However, it also means that the pruning decision is made with respect to the model's current prediction state — if the model attends to different tokens at different generation steps (which it typically does, as the generation context shifts), the set of pruned tokens will naturally adapt. This is what enables the "dynamic" property — different steps prune different tokens — without any additional mechanism.

**Why horizontal averaging across heads rather than selecting per head.** Equation 1 averages the attention probability across all `$H$` heads. An alternative would be to prune tokens independently per head (different heads could attend to different subsets of tokens). The paper chooses to prune entire tokens (across all heads) rather than per-head subsets. This is a simplification that makes the implementation cleaner — a token is either fully present or fully absent from a layer's computation — and aligns with the standard transformer architecture where token representations are not head-specific after the attention operation. The tradeoff is that a token receiving high attention from even one specialized head might be pruned because the average is low, but the paper's strong empirical results suggest this is rare enough not to matter in practice.

**Why percentile rather than fixed count.** The percentile-based pruning means the fraction of tokens pruned is constant regardless of prompt length. A fixed-count approach (e.g., always keep exactly 100 tokens) would not scale properly — it would prune too aggressively on short prompts and not aggressively enough on long prompts. The percentile approach naturally adapts to prompt length: a 10,000-token prompt with 70% retention keeps 7,000 tokens; a 1,000-token prompt keeps 700. This makes the speedup proportional to prompt length, which is desirable because longer prompts need more speedup.

**Why three pruning stages.** The paper's default configuration uses a three-stage progressive schedule (10%, 30%, 30% of layers, with pruning at boundaries between them). This is not derived from first principles but from the empirical observation in Figure 6 that pruning at later layers performs better, combined with the practical insight that aggressive early pruning would discard tokens before their information has been aggregated. The three-stage schedule is a flexible template that the paper sweeps over different instantiations to trade off speedup vs. accuracy (Figure 5). A single-stage pruning would be a special case that sits somewhere on the Pareto frontier but does not dominate the progressive schedule.

**Why the Aux Cache stores hidden states rather than recomputed KVs.** When a token is revived at layer `$l+1$`, the system needs that token's hidden state at the input to layer `$l+1$` to compute its new KV entry at that layer. The hidden state stored in the Aux Cache is exactly this input — the output of the token at layer `$l$` before it was pruned. An alternative would be to recompute the hidden state by running the token from the embedding layer through to layer `$l$`, which is what the Aux Cache avoids. Another alternative would be to store the token's computed KV at layer `$l+1$` eagerly (compute it even though the token is pruned), which would eliminate the need for revival but would also compute the KV for all pruned tokens, defeating the purpose of pruning. The Aux Cache strikes the balance: compute the hidden state once (at layer `$l$`, which was computed anyway because the token survived that far), store it, and only compute the KV at layer `$l+1$` if and when the token is actually revived.

---

#### Configuration Space: The Three Hyperparameters

LazyLLM's speedup-accuracy tradeoff is controlled by exactly three dimensions, which can be varied independently to trace out a Pareto frontier (as shown in Figure 5):

**1. The number of pruning layers.** This is the number of distinct points in the transformer stack where pruning operations occur. More pruning layers means more aggressive total token reduction, but also more granular control. With `$P$` pruning layers, the transformer is partitioned into `$P+1$` segments (before first prune, between prunes, after last prune), and tokens are removed at each boundary. Increasing `$P$` from 1 (one-shot pruning) to 3 (progressive) to higher values provides finer-grained control at the cost of more hyperparameters to tune.

**2. The locations of these pruning layers.** Which specific layer indices host the pruning operations. Early pruning (at low layer indices) saves more computation because pruned tokens skip all subsequent layers, but risks removing tokens before they've contributed their information to other tokens' representations. Late pruning is safer for accuracy but saves less computation. The paper's default places pruning operations at roughly the 10%, 40%, and 70% points through the depth.

**3. The fraction of tokens pruned at each pruning layer.** At each pruning layer `$l_j$`, the parameter `$k_j$` (the `$k$`-th percentile) specifies what fraction of *currently active* tokens survive. If `$k_1 = 70$`, `$k_2 = 70$`, `$k_3 = 70$`, then after three pruning stages the fraction of original tokens remaining is `$0.7 \times 0.7 \times 0.7 = 0.343$` — about one-third of the original prompt. These `$k_j$` values can be set independently; the paper's experiments sweep them to produce the tradeoff curves.

**How these parameters produce the speedup-accuracy curves in Figure 5.** Each point on a LazyLLM curve in Figure 5 corresponds to a specific `$(P, \{l_j\}, \{k_j\})$` configuration. More aggressive configurations (higher `$P$`, earlier `$l_j$`, lower `$k_j$`) reduce the fraction of tokens computed and thus reduce TTFT (higher speedup on the x-axis) but may degrade accuracy (lower relative score on the y-axis). The fact that LazyLLM's curve sits above the baselines at nearly all speedup levels means that for a given speedup target, LazyLLM preserves more accuracy than random dropping, static pruning, or prompt compression — or equivalently, for a given accuracy budget, LazyLLM achieves more speedup.

## 4. Key Insights and Innovations

### Innovation 1: The Concept of "Lazy" Computation as a Principled Alternative to Static Pruning

The field's default approach to reducing inference computation has been some form of **static reduction**: either permanently compressing the prompt before inference begins (Li et al., 2023; Jiang et al., 2023), permanently pruning model weights (Frantar et al., 2022; Sun et al., 2023), or permanently evicting KV cache entries based on a one-time importance assessment (Zhang et al., 2024; Li et al., 2024). All of these share an implicit assumption: identify what's unimportant *once* and discard it *forever*.

LazyLLM introduces a fundamentally different computational philosophy: **defer rather than discard**. The paper's title uses the word "lazy" deliberately, evoking the lazy evaluation strategy from programming language theory where expressions are only evaluated when their values are actually needed. The computational model shifts from "decide which tokens are useless and remove them" to "decide which tokens are needed *right now* and defer everything else." This is not a refinement of pruning — it's a different relationship between computation and time.

The significance of this reframing becomes clear when considering *why* static pruning fails for generative LLMs despite working well for classification tasks (Kim et al., 2022; He et al., 2021). In classification, the model makes a single prediction; a token's relevance is time-invariant, so one pruning decision suffices. In generation, the model produces a sequence of tokens, each conditioned on the evolving context of previously generated tokens. The information needed to generate the third output token may be different from what was needed for the first. Static pruning — even if perfectly accurate for step 1 — necessarily discards information that might be needed at step 5. LazyLLM's lazy approach solves this by treating the pruning decision as **step-conditional**: a token not needed now might be needed later, so don't delete it, just don't compute its KV yet.

The empirical consequence is visible in Table 2, where the "% of Prompt Token Computed" across the entire generation trajectory is consistently below 100% (ranging from 63.7% to 99.6% for Llama 2 across tasks) — meaning some tokens are *never* computed even across all generation steps — but critically, this is not because they were pruned upfront. It's because the model, given the freedom to select tokens dynamically at each step, simply never chose to attend to them. The distinction between "we decided these tokens don't matter" and "the model never asked for these tokens" is subtle but important: the former risks discarding information the model would have used; the latter is an observation about what the model actually needed.

This conceptual move — from static discard to lazy deferral — is the intellectual foundation that makes everything else in the paper work. Without it, progressive pruning would be one-shot (and would fail at the accuracy levels reported, as shown by the "Static Token Pruning" baseline in Table 1 and Figure 5). Without it, the Aux Cache would be unnecessary (if you never revive tokens, you don't need a revival mechanism). The lazy computation model is not an implementation detail; it's the paper's core diagnostic insight about *why* generative inference is a different problem from classification inference for token pruning.

### Innovation 2: The Discovery That Token Revival Is Necessary for Accuracy — and the Aux Cache That Makes It Practical

This innovation operates on two levels: an empirical finding and an architectural solution. The empirical finding is that dynamic token selection — allowing the model to choose different subsets of the prompt at different generation steps — **only preserves accuracy when pruned tokens can be revived**, not simply when different subsets are selected from a permanently reduced pool. The architectural solution is the Aux Cache, which makes revival computationally tractable.

**The empirical finding.** The paper compares LazyLLM against a "Static Token Pruning" baseline (Table 1, Figure 5) that prunes tokens once during prefilling based on early-layer attention scores and permanently removes them for all subsequent generation steps. The performance gap is substantial: on multi-document QA with Llama 2, static pruning drops accuracy from 22.43 to 19.93 even with a 2.16× TTFT speedup, while LazyLLM achieves 2.34× speedup at 22.31 accuracy — essentially baseline-level performance at higher speedup. This is not simply a matter of static pruning choosing suboptimally which tokens to keep; it's that even if static pruning chose the *best possible* fixed subset for step 1, that subset would be suboptimal for later steps. The model's information needs *change* across generation steps.

Why didn't prior work on token pruning for transformers (Kim et al., 2022; He et al., 2021) encounter this? Because those methods were designed for tasks requiring a single forward pass — classification, entailment, etc. — where the concept of "different generation steps" doesn't exist. The extension to generative LLMs reveals a qualitatively new requirement that the static pruning literature never had to confront: **temporal dynamics of token importance**. A token might be irrelevant for predicting "The" at the start of a generation but crucial for predicting "1947" three steps later when the model needs to retrieve a specific date from context.

**The architectural solution.** The Aux Cache is what transforms this empirical finding from an observation into a deployable technique. The problem is that revival, if implemented naively, would require re-running pruned tokens through all prior transformer layers, eliminating any speedup gains. The Aux Cache (Section 3.2, Figure 4) solves this by caching the hidden states of pruned tokens at the layer where they were pruned, so that revival at layer `$l+1$` only requires computation from layer `$l+1$` onward. This is not merely an optimization — it's what makes the concept of lazy, revival-capable pruning **economically viable** rather than theoretically interesting but practically self-defeating.

The guarantee — "each token is computed at most once in every transformer layer" — is a stronger statement than it might first appear. It means that in the worst case, where the model revives every pruned token in every subsequent step, the total computation equals the baseline. This is a safety property: adopting LazyLLM can never make inference *slower* than the standard approach, regardless of how poorly the pruning heuristic performs. This de-risks adoption: a practitioner can try LazyLLM without worrying about pathological edge cases where aggressive pruning backfires and causes slowdown.

The Aux Cache is also what distinguishes LazyLLM from KV cache eviction methods like H2O (Zhang et al., 2024) and SnapKV (Li et al., 2024). Those methods evict KV entries permanently — if a token's KV is evicted, it cannot be recovered without recomputation. They accept this because they target decoding-stage memory reduction, not TTFT, and permanent eviction is sufficient when the goal is compressing the cache for future steps. LazyLLM's TTFT focus demands a different tradeoff: accept additional memory overhead (storing hidden states in the Aux Cache) in exchange for the ability to defer rather than discard computation. The Aux Cache is thus not just a caching trick — it's the mechanism that makes "lazy" a viable alternative to "evict."

### Innovation 3: Using the Model's Own Attention as a Zero-Cost, Layer-Local Importance Signal

Prior approaches to identifying important tokens for pruning or compression rely on one of three signals: (1) **cumulative attention scores accumulated across multiple generation steps** (Zhang et al., 2024; Li et al., 2024) — effective for decoding-stage KV eviction but fundamentally incompatible with TTFT reduction because they require full prefilling to collect the signal; (2) **external or auxiliary models** that score token importance (Jiang et al., 2023; Li et al., 2023) — computationally expensive enough that the overhead can exceed the savings, as the paper demonstrates with the prompt compression baseline achieving 0.12× TTFT speedup (i.e., an 8× slowdown); or (3) **learned importance predictors** trained specifically for pruning (Kim et al., 2022) — which require training and may not transfer across tasks.

LazyLLM's importance signal — the attention map from the *immediately prior* transformer layer, averaged across heads and focused on the last sequence position — is distinctive because it is simultaneously: **zero-cost** (it's computed anyway as part of the standard forward pass), **layer-local** (no information needs to be accumulated across steps or layers), and **immediately available from step 1** (no warmup or profiling phase needed).

The "zero-cost" property is what makes TTFT reduction possible at all. If importance scoring required even a single additional forward pass, the overhead would consume the savings on the first token. The "layer-local" property is what enables progressive pruning: layer `$l$`'s attention is used for pruning at layer `$l+1$`, layer `$l+1$`'s attention for pruning at layer `$l+2$`, and so on. No cross-layer information needs to be aggregated. The "immediately available" property is what distinguishes LazyLLM from methods like SnapKV and H2O, which require observing attention patterns across the first few generated tokens before making pruning decisions — meaning they cannot reduce TTFT because the full KV cache must be computed at least once to collect those observations.

There is a subtle assumption here worth articulating: **that the attention map at layer `$l$` is a good predictor of token importance at layer `$l+1$`**. The paper doesn't prove this theoretically, but the empirical validation in Figure 6 provides strong support. When pruning is applied at increasingly later layers, accuracy degrades less for the same retention ratio — meaning the attention-based importance signal becomes more reliable as representations stabilize. This is consistent with the "gradual evolution" of token representations observed by Elhoushi et al. (2024) and justifies the progressive schedule: prune less in early layers (where the signal is noisier) and more in later layers (where the signal is cleaner).

An important negative result is implicit in the design: the paper doesn't use more sophisticated importance metrics (e.g., attention entropy, gradient-based saliency, or learned scorers). The fact that a simple average of attention probabilities across heads — with no learned parameters, no calibration, and no task-specific tuning — provides sufficient signal for effective pruning is itself a significant finding. It suggests that the attention maps of well-trained LLMs encode token importance in a way that is both accessible and reliable, and that the primary barrier to token pruning in generative settings was not the quality of the importance signal but rather the architectural inability to *act on it dynamically* (which the Aux Cache addresses).

### Innovation 4: The Training-Free, Plug-and-Play Design Philosophy

Many inference acceleration techniques require some form of model modification: architectural changes that demand retraining (Beltagy et al., 2020; Kitaev et al., 2020), fine-tuning to learn pruning or early-exit behaviors (Kim et al., 2022; Elhoushi et al., 2024), or auxiliary models for speculative decoding (Leviathan et al., 2023; Cai et al., 2024). LazyLLM's design constraint — **no training, no fine-tuning, no parameter modification** — is not simply a convenience. It's a strategic choice that addresses a specific gap in the inference optimization landscape: the need for techniques that work with *already-deployed*, *off-the-shelf* models.

The paper demonstrates this universality concretely by evaluating on two different model families — Llama 2 7B (Touvron et al., 2023) and XGen 7B (Nijkamp et al., 2023) — using the exact same publicly released checkpoints. Table 1 shows consistent speedup patterns across both models: on multi-document QA, 2.34× for Llama 2 and 2.65× for XGen, both with negligible accuracy change. Figure 6 shows that both models share the same qualitative pattern of layer-wise pruning sensitivity (later layers are less sensitive to pruning). This cross-model consistency strengthens the claim that LazyLLM exploits a general property of transformer attention — its sparsity — rather than model-specific artifacts.

The training-free property also means there is no train-test distribution shift problem. A fine-tuned pruner might learn pruning patterns that work well on the training distribution but fail on out-of-distribution prompts. LazyLLM's pruning decisions are made *online*, based on the model's actual attention patterns on the specific input, so they naturally adapt to whatever distribution the prompt comes from. This is a robustness advantage that training-based methods sacrifice.

However, this design choice also imposes a limitation: LazyLLM cannot *improve* the model's attention patterns. If the model's attention is noisy or poorly calibrated on certain types of inputs, the pruning decisions will inherit that noise. Training-based methods could potentially learn to compensate for systematic attention errors; LazyLLM is stuck with whatever the frozen model provides. The paper doesn't explore this tradeoff explicitly, but it's an inherent consequence of the training-free constraint: universality and simplicity are purchased at the cost of adaptability to model-specific weaknesses.

The "plug-and-play" aspect — that LazyLLM can be "seamlessly integrated with any existing transformer-based LLM" (Section 1) — is not just marketing. It means the technique can be adopted incrementally: a team running Llama 2 in production can add LazyLLM as a configuration change without touching model weights, retraining, or even changing their inference pipeline architecture. In a field where model releases are frequent and fine-tuning is expensive, this property makes LazyLLM unusually practical. Compare this to a method like Longformer, which requires training a new model from scratch with a modified attention mechanism — by the time you've trained it, the base model may have been superseded. LazyLLM rides on top of whatever model is current.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** All experiments use the **LongBench** benchmark (Bai et al., 2023), a multi-task benchmark for long-context understanding comprising 16 datasets across 6 task categories: single-document QA, multi-document QA, summarization, few-shot learning, synthetic tasks, and code completion. The paper follows the official GitHub repository for data preprocessing and prompting in all experiments (Section 4). The average LongBench prompt length is reported as 3,376 tokens with an average generation length of 68 tokens (Section 1, footnote 1).

- **Base model(s).** Two 7-billion-parameter models are evaluated: **Llama 2 7B** (Touvron et al., 2023) and **XGen 7B** (Nijkamp et al., 2023). The paper states these are used "without employing any additional training" — all experiments use the publicly released pretrained checkpoints exactly as provided (Section 5). The choice of 7B-scale models is not explicitly justified beyond representing "contemporary LLMs," but the scale is practical for controlled experimentation and relevant because 7B models are widely deployed. The Llama 2 architecture stacks 32 transformer layers with model dimension 4,096 (Section 1).

- **Metrics.** The primary evaluation framework is the **TTFT speedup vs. accuracy trade-off** (Section 5, opening paragraph). Accuracy is measured as the macro-averaged score across datasets within each task category, using task-specific metrics (ROUGE-L, F1, Accuracy, Edit Sim) as defined by the LongBench evaluation pipeline (Section 4). TTFT speedup is defined as the ratio of wall-clock time to first token for the baseline divided by the wall-clock time for the method under test — so 2.34× means LazyLLM generates the first token in 1/2.34 of the baseline's time. Two additional metrics are reported in Table 2: **% of Prompt Token Computed** (the accumulated percentage of prompt tokens whose KV was computed by the end of generation — lower means more computation was avoided) and **Generation Speedup** (wall-time improvement for the complete generation process, including all decoding steps, relative to baseline).

- **Baselines.** The paper compares against four baselines (Section 5.1, Table 1):
  - **Standard LLM inference ("Baseline")**: runs the full prefilling stage computing KV cache for all tokens, then decodes normally.
  - **Random Token Drop**: based on Yao et al. (2022), randomly prunes prompt tokens before feeding them to the LLM. Results are averaged across 5 runs.
  - **Static Token Pruning**: prunes input tokens at once based on their attention scores from the first few transformer layers during prefilling, permanently removing them for all subsequent generation steps (described in Section 5.1 as the paper's own baseline).
  - **Prompt Compression**: following Li et al. (2023), uses an LLM to compress the prompt by removing redundant tokens before inference. The paper notes this is evaluated as a TTFT baseline, not just an accuracy baseline, explicitly measuring wall-clock time including compression overhead.

- **Generation budget / compute accounting.** LazyLLM is not evaluated under a FLOPs or token-generation budget — it is a method for reducing computation relative to a full-inference baseline, so the natural comparison is **wall-clock time** at equivalent model and task configurations. Speedup is measured empirically on NVIDIA A100 GPUs with 5 warmup runs per experiment to eliminate loading noise (Section 4). No explicit generation budget or per-prompt token limit is imposed; the system processes whatever prompt length each dataset provides. The computational savings derive from reducing the number of tokens processed through transformer layers, which translates to wall-time speedup proportional to the reduction in attention and FFN computation.

- **Cross-validation / statistical protocol.** There is no cross-validation or statistical significance testing reported. The paper sweeps hyperparameters (number of pruning layers, locations, pruning ratios) and reports the resulting accuracy-speedup points directly, tracing out Pareto curves. The random token drop baseline uses 5-run averaging to account for stochasticity; no such averaging is mentioned for LazyLLM or static pruning, presumably because these methods are deterministic given the same model weights and input.

---

### Main Quantitative Results

The experimental results are organized around four primary axes of investigation: (1) TTFT speedup vs. accuracy across tasks compared to baselines, (2) the shape of the accuracy-speedup trade-off curve under hyperparameter variation, (3) the impact of LazyLLM on overall generation speed beyond just TTFT, and (4) the sensitivity of pruning effectiveness to layer location and retention ratio.

#### TTFT Speedup vs. Accuracy Across Tasks

**Headline result.** Table 1 presents the primary results. LazyLLM achieves substantial TTFT speedups — ranging from 1.36× (single-doc QA, Llama 2) to 4.77× (synthetic tasks, XGen) — while maintaining accuracy within approximately 1% of the baseline across most tasks. The multi-document QA task shows the most practically significant combination: 2.34× TTFT speedup on Llama 2 at 22.31 accuracy versus the baseline's 22.43, and 2.65× on XGen at 20.68 versus baseline 20.71. These are essentially accuracy-neutral speedups.

**Comparison against baselines.** Table 1 reveals a clear hierarchy:

- **Random Token Drop** consistently underperforms LazyLLM in both accuracy and speedup. For multi-doc QA on Llama 2, it achieves only 1.19× speedup with accuracy degraded from 22.43 to 16.77 — a ~25% accuracy drop for minimal speedup. The speedup is small because random dropping still feeds the reduced prompt through all layers; the savings come only from the smaller token count, not from progressive reduction.

- **Static Token Pruning** achieves higher speedups than random dropping (2.16× for multi-doc QA on Llama 2) but with significant accuracy degradation: 19.93 vs. 22.43 baseline. This is the critical comparison: static pruning *can* match LazyLLM's speedup, but it cannot match its accuracy. LazyLLM at 2.34× speedup retains 22.31 accuracy; static pruning at 2.16× drops to 19.93. The accuracy gap demonstrates that the dynamic revival mechanism is not merely a refinement — it is the difference between usable and unusable accuracy at high speedup.

- **Prompt Compression** catastrophically fails at improving TTFT: across all tasks and both models, TTFT speedup is below 1.0× — meaning it is *slower* than the baseline. The worst case is few-shot learning on Llama 2 at 0.10× speedup (10× slower than baseline). The paper attributes this directly to the computational overhead of running compression LLMs, stating "the overhead of running LLMs to compress the prompt is very computationally expensive" (Section 5.1). The accuracy of prompt-compressed inference is also generally poor (e.g., 8.42 on multi-doc QA vs. 22.43 baseline), suggesting that aggressive compression discards semantically important content. This baseline serves less as a competitive comparison and more as a cautionary demonstration: TTFT reduction methods that require substantial pre-processing cannot succeed if that pre-processing costs more time than it saves.

**Task-specific patterns.** The speedup magnitudes vary systematically across tasks. Synthetic tasks show the largest speedups (2.89× Llama 2, 4.77× XGen), while summarization shows the smallest (1.46× Llama 2, 1.91× XGen). The paper does not explicitly analyze why, but the pattern is consistent with intuition: synthetic tasks (designed to test long-range retrieval) likely have highly concentrated attention on relevant tokens, making aggressive pruning safe; summarization requires extracting information distributed across the entire document, making aggressive pruning more damaging and forcing the system to retain more tokens.

#### Accuracy-Speedup Trade-Off Curves

**Headline result.** Figure 5 presents six scatter plots (one per task) comparing LazyLLM's accuracy-speedup trade-off against baselines for Llama 2 7B. LazyLLM's curve consistently sits above the baselines across nearly the entire speedup range, meaning it achieves better accuracy at equivalent speedup (or equivalently, more speedup at equivalent accuracy).

**Quantitative reading of Figure 5.** Each point on a LazyLLM curve corresponds to a different hyperparameter configuration (varying the number, location, and aggressiveness of pruning stages). The paper highlights specific operating points:

- At **1% or less accuracy degradation**, LazyLLM achieves the speedups reported in Table 1 (e.g., 2.34× for multi-doc QA). The fact that the LazyLLM curve at these speedups remains near the 100% relative score line while baselines have already dropped substantially is the paper's strongest result.

- At **more aggressive speedups** (~3.0× for multi-doc QA), LazyLLM drops to roughly 90% relative score — a ~10% accuracy degradation. The paper states this explicitly: "LazyLLM can achieve 3.0× TTFT speedup in the multi-document question-answering task with ≤10% degradation in accuracy" (Section 5.2). Random token dropping and static pruning at comparable speedups fall well below LazyLLM.

- The **shape of the curve** varies by task. For few-shot learning, LazyLLM maintains near-100% relative score out to approximately 2.2× speedup before beginning a gradual decline. For code completion, the decline is steeper — relative score drops to roughly 85% by 2.0× speedup. This task-dependent shape reflects the difficulty-specific patterns seen in Table 1.

**Key comparison within Figure 5.** The "Static Pruning" curve (green) is systematically below LazyLLM (blue) across all tasks and speedup levels. This is the direct evidence that dynamic token selection with revival is superior to one-shot pruning. Both methods use attention-based importance scoring; the only difference is whether tokens can be revived. The performance gap quantifies the value of the lazy computation model.

#### Impact on Overall Generation Process

**Headline result.** Table 2 reports two metrics that extend the analysis beyond TTFT to the full generation trajectory. The "% of Prompt Token Computed" ranges from 63.73% (synthetic, Llama 2) to 99.59% (summarization, Llama 2). This means that across the entire generation process — prefilling plus all decoding steps — LazyLLM never computes the KV for 0.4% to 36% of prompt tokens. The corresponding Generation Speedup ranges from 1.01× (code completion, Llama 2) to 3.16× (synthetic, XGen).

**Interpretation of "% of Prompt Token Computed."** This metric captures the cumulative effect of lazy computation: some tokens are never selected by the model in any generation step, even though they remain theoretically available through the Aux Cache. The wide range (63.7% to 99.6%) indicates that task structure strongly influences how much of the context the model actually needs. Synthetic tasks, designed to test the ability to find specific information buried in long contexts, allow the most aggressive pruning because the model needs only the targeted information. Summarization allows the least pruning because synthesizing a coherent summary benefits from broad context access.

**Interpretation of Generation Speedup.** The generation speedup is generally smaller than the TTFT speedup, which is expected: TTFT involves computing KVs for all layers from scratch, while decoding reuses cached KVs and only computes new tokens. The speedup on overall generation comes from two sources: (1) the reduction in prefilling computation (same as TTFT speedup), and (2) the reduction in decoding computation because fewer prompt tokens' KVs need to be retrieved and fewer survive progressive pruning. The fact that generation speedup remains meaningful (e.g., 1.56× for multi-doc QA on Llama 2) shows that LazyLLM's benefits are not confined to the first token.

**The remarkable synthetic task result for XGen.** At 40.54% of Prompt Token Computed and 3.16× Generation Speedup, XGen on synthetic tasks achieves both the lowest token computation and highest overall speedup. This is consistent with Table 1, where synthetic tasks show the largest TTFT speedup (4.77× for XGen). The combination of TTFT speedup *and* decoding-stage savings means LazyLLM delivers end-to-end latency reduction that approaches the theoretical maximum given the fraction of tokens actually needed.

#### Layer-Wise Pruning Sensitivity

**Headline result.** Figure 6 presents a controlled experiment using a simplified version of LazyLLM that prunes tokens exactly once at a single layer, varying both the layer index (x-axis) and the retention ratio (different colored curves). The results for Llama 2 (Figure 6a) and XGen (Figure 6b) show two clear trends:

1. **At the same pruning layer, accuracy decreases monotonically as fewer tokens are kept.** For Llama 2, keeping 90% of tokens (black curve) produces accuracy near the baseline across all layer indices. Keeping 70% (purple) causes a moderate decline. Keeping 10% (blue) causes catastrophic accuracy loss at early layers (score ~0 at layer 5) and substantial degradation even at late layers (score ~12 at layer 30 vs. baseline ~25).

2. **For a given retention ratio, pruning at later layers consistently outperforms pruning at earlier layers.** The curves slope upward from left to right. For Llama 2 at 50% retention (brown curve), pruning at layer 5 yields a score of approximately 8, while pruning at layer 30 yields approximately 22 — nearly baseline-level performance. Critically, the late-layer pruning at 50% retention (score ~22) matches or exceeds early-layer pruning at 90% retention (score ~20 at layer 5), meaning that *when* you prune matters as much as *how much* you prune.

**What this tells us about the progressive pruning schedule.** The paper uses Figure 6 to justify the design choice of progressive pruning: "pruning at later transformer layers consistently yields better performance than pruning at earlier layers, suggesting that later layers are less sensitive to token pruning" (Section 5.4). This motivates keeping more tokens in early layers (where pruning is dangerous) and pruning more aggressively in later layers (where it is safe). The three-stage schedule described in Section 3 and visualized in Figure 4 (keeping ~100% tokens initially, then pruning to ~70%, then ~49%, then ~34%) is a direct operationalization of this insight.

**A subtle pattern in Figure 6.** The curves for both models show that accuracy actually *increases* slightly as the pruning layer moves from very early (layer ~2-5) to early-mid (layer ~5-10) for low retention ratios. For example, keeping 10% of tokens at layer 2 yields near-zero accuracy; at layer 10, it yields a small but non-zero score. This suggests that extremely early pruning is not just slightly worse but qualitatively different — the model hasn't yet integrated enough contextual information for even the most strongly attended-to tokens to serve as adequate proxies for the full context. By layer 10 or so, the representations have matured enough that the attention-based importance signal is reliable.

### Ablation Studies and Robustness Checks

**Progressive KV growth characterization (Figure 7):** The paper profiles the cumulative percentage of prompt tokens processed at each generation time step, broken out by four layer groups (layers 1-9, 10-19, 20-28, 29-32) for Llama 2 7B. Across 1,000 randomly sampled LongBench examples, early layers (1-9) consistently approach 100% token usage because no pruning has occurred yet. Middle layers (10-19) show gradual growth from ~40% to ~60% token usage over the first ~10 generation steps, then plateau. Late layers (20-28, 29-32) use substantially fewer tokens (~20-40%) and remain flat across generation steps. This confirms that progressive pruning is operating as designed — tokens are progressively removed through the layer depth — and that the model does not, on average, progressively increase token usage across generation steps (which would indicate reliance on previously pruned information). As the paper states: "this model retains accuracy on the task(s), we can conclude that the model effectively drops the tokens which do not affect the output quality."

**Effect of varying pruning layer location and retention ratio (Figure 6):** This is both a main result and an ablation. The ablation aspect is the demonstration that pruning sensitivity is not uniform across layers — it varies systematically and predictably. The practical implication is that the progressive pruning schedule is not an arbitrary heuristic but a response to a real structure in how transformer models process information. A counterfactual uniform pruning schedule (prune the same fraction at every layer) would be suboptimal because it would prune too aggressively early and too conservatively late.

**Two-model consistency (Figures 6a vs. 6b):** The fact that Llama 2 and XGen — two independently developed 7B models with different training recipes and architectures — show nearly identical qualitative patterns in Figure 6 is itself a robustness check. It suggests that the layer-wise pruning sensitivity is a general property of transformer LLMs rather than an artifact of a specific training procedure or architectural variant. The paper does not test additional model families or scales, so the claim of "universality" is not fully validated, but the cross-model agreement is encouraging.

**Static token pruning as an ablation of dynamic revival:** The comparison between LazyLLM and Static Token Pruning (Table 1, Figure 5) constitutes an ablation of the dynamic revival mechanism. Both methods use the same attention-based importance scoring. The only difference is whether pruned tokens can be revived in subsequent steps. The consistent and substantial performance gap across all tasks demonstrates that revival is not a minor enhancement — it is the component that makes token pruning viable for generative LLMs. This is a clean ablation because it isolates exactly one mechanism.

**Prompt compression as an ablation of "cheap importance scoring":** The prompt compression baseline uses a separate LLM forward pass to determine token importance, unlike LazyLLM's zero-cost attention-based scoring. The TTFT slowdown (0.10-0.69×, meaning 1.4-10× slower than baseline) demonstrates that the cost of acquiring importance scores can easily exceed the savings from pruning. This validates LazyLLM's design choice of using attention scores that are computed as a byproduct of the standard forward pass.

**Missing ablation: per-head vs. per-token pruning.** The paper does not compare the per-token pruning approach (prune entire tokens across all heads) against per-head pruning (allow different heads to attend to different token subsets). Per-head pruning could theoretically retain more information because a token important to one head but not others could be kept for that head only. However, it would complicate the KV cache structure. The absence of this ablation is a limitation but not a critical one, since the paper demonstrates strong results without it.

**Missing ablation: cross-layer importance aggregation.** The paper uses only the immediately prior layer's attention for pruning decisions (layer `l`'s attention determines pruning for layer `l+1`). An alternative would aggregate attention scores across multiple preceding layers, potentially producing a more stable importance signal. This ablation is not performed, and it represents a plausible direction for improving pruning accuracy at the cost of some additional bookkeeping.

**Missing ablation: effect of Aux Cache memory overhead.** The paper does not report the memory overhead of the Aux Cache relative to the standard KV cache or the total GPU memory footprint. Since the Aux Cache stores hidden states (full model dimension, e.g., 4,096 elements per token) at pruning boundaries, the memory cost scales with (number of pruning layers × prompt length × model dimension). For a 32-layer model with three pruning boundaries and a 3,376-token prompt, this adds approximately 3 × 3,376 × 4,096 × 2 bytes (FP16) ≈ 83 MB — modest relative to the parameter memory (~14 GB for 7B parameters in FP16) but potentially significant for memory-constrained deployments. The paper states the Aux Cache "ensures the worst runtime of LazyLLM is not slower than the baseline" but does not state the worst-case memory cost.

**Negative result: Prompt compression fails as a TTFT optimization.** This is the paper's most unambiguous negative finding. Despite the intuitive appeal of compressing the prompt before inference, the wall-clock cost of running a compression LLM forward pass eliminates any savings from operating on a shorter sequence. This is not a failure of compression per se — it may well reduce total FLOPs or be useful for other goals — but it definitively cannot improve TTFT, which is a wall-time metric that includes the compression step. The paper reports TTFT speedups of 0.10-0.69× (meaning 1.4-10× slowdowns) across all tasks and models for prompt compression (Table 1). This is a valuable negative result because it establishes a boundary condition: TTFT optimization methods must have negligible pre-processing overhead.

**Negative result: Random dropping fails to achieve meaningful speedup.** Random token drop achieves TTFT speedups of only 1.18-1.62× while incurring substantial accuracy degradation (e.g., 16.77 vs. 22.43 baseline on multi-doc QA, Llama 2). This is unsurprising — random dropping pays the full per-layer compute cost for surviving tokens and only saves the cost of dropped tokens, with no progressive reduction. It also demonstrates that attention-based scoring is essential: structureless pruning cannot discriminate between crucial and redundant tokens.

### Critical Assessment

#### Does the Evidence Support the Central Claim That LazyLLM Reduces TTFT Without Accuracy Loss?

The paper's primary claim is that LazyLLM "significantly accelerates the generation without fine-tuning" and achieves up to 2.34× TTFT speedup "while maintaining accuracy" (Abstract). Table 1 and Figure 5 provide substantial evidence for this claim, but with important nuances about what "maintaining accuracy" means in practice.

The strongest evidence comes from multi-document QA on Llama 2: Table 1 reports 22.31 accuracy for LazyLLM at 2.34× speedup versus 22.43 for the baseline — a difference of 0.12 points, or approximately 0.5%. This is well within any reasonable definition of "maintaining accuracy." Similar patterns hold for single-doc QA (25.59 vs. 25.79, ~0.8% drop), summarization (24.75 vs. 24.65 — actually a slight improvement, likely noise), few-shot learning (62.81 vs. 62.90, ~0.1% drop), and synthetic tasks (4.98 vs. 4.97, negligible). These five out of six tasks show accuracy preservation within 1% at meaningful speedups.

However, code completion on Llama 2 shows a non-negligible drop: 53.30 vs. 55.18, representing a 3.4% relative accuracy decrease at 1.94× speedup. The paper does not flag this as an exception, but it's a meaningfully larger degradation than the other tasks. The reader should note that "maintaining accuracy" is task-dependent, and code completion is more sensitive to token pruning than the other tasks tested.

A more fundamental qualification is that Table 1 reports *single operating points* — specific hyperparameter configurations chosen to demonstrate the best accuracy-speedup balance. Figure 5 shows the full trade-off curves, and it's clear from these curves that LazyLLM *does* lose accuracy eventually as speedup increases. The claim "maintains accuracy" only holds at the specific speedup levels reported in Table 1. At 3.0× speedup on multi-doc QA, the paper itself notes "≤10% degradation." This is not a weakness of the method — all pruning techniques face this trade-off — but the abstract's language suggests universality while the evidence shows a conditional, speedup-dependent relationship.

#### Are the Speedup Numbers Trustworthy?

The paper measures wall-clock time on A100 GPUs with warmup runs, which is the appropriate metric for TTFT. However, several factors could influence the reported speedups in ways that make them either optimistic or pessimistic:

**Implementation efficiency.** The paper implements LazyLLM on HuggingFace Transformers (Section 4). HuggingFace is not an inference-optimized framework — systems like vLLM, TensorRT-LLM, or custom CUDA kernels typically achieve much higher throughput and lower latency than vanilla HuggingFace. If the baseline is inefficient (which HuggingFace standard inference often is), then the *absolute* speedup from pruning might be larger than it would be in an optimized deployment, because the baseline has more overhead per token. For example, if the baseline spends 30% of its time in Python overhead rather than compute, reducing compute by 2× might yield more than 2× wall-time speedup because the fixed overhead becomes a smaller fraction. The paper does not discuss this, and it's unclear whether the reported speedups would transfer to optimized inference engines.

**Single-GPU measurement.** All experiments are on single A100 GPUs. At batch size 1 (standard for interactive LLM inference), LazyLLM's token pruning directly translates to reduced computation. However, if the GPU is not compute-bound at batch size 1 (e.g., if it's memory-bandwidth-bound for token generation), the relationship between tokens computed and wall-clock time may not be linear. The paper reports speedups that are broadly consistent with the fraction of tokens computed (e.g., 2.34× TTFT speedup on multi-doc QA vs. the ~66% of tokens computed implied by the progressive pruning schedule), suggesting the GPU is reasonably compute-bound, but this is not explicitly analyzed.

**Warmup runs.** The paper adds 5 warmup runs before measurement (Section 4). This is standard practice and appropriate, but it's worth noting that GPU state (clock speeds, memory allocation patterns) may not fully stabilize after 5 runs. The impact on the reported numbers is likely small.

**Prompt compression baseline measurement.** The paper reports prompt compression TTFT speedups of 0.10-0.69×. It is crucial to verify that this measurement includes the *full* compression time. The paper states "the overhead of running LLMs to compress the prompt is very computationally expensive" and notes that "the actual TTFT of the 'prompt compression' baseline is longer than the baseline." This suggests the measurement does include compression time, but the paper doesn't specify what compression model was used, how many tokens it generated during compression, or whether the compression model's KV cache was computed on the same GPU (potentially causing memory contention). These details matter for interpreting the severity of the prompt compression failure, but they don't affect the validity of the LazyLLM results.

#### Does the Evidence Support Universality Across Models and Tasks?

LazyLLM is evaluated on **two 7B-parameter models** (Llama 2 and XGen) and **six tasks** (via LongBench). The paper claims LazyLLM "can be seamlessly integrated with any existing transformer-based LLM" (Abstract). What the evidence actually supports is more specific: LazyLLM works well on these two 7B models on these six LongBench tasks.

**Model scale.** No experiments are run at different model scales (e.g., Llama 2 13B, 70B). The attention sparsity pattern that LazyLLM exploits (Figure 2) might depend on model scale — larger models tend to have more diffuse attention (because they have more capacity to distribute attention across tokens), which could make pruning less effective or require different schedules. Conversely, larger models might have *more* redundancy, making pruning easier. We simply don't know from this paper.

**Architecture.** Both Llama 2 and XGen are dense autoregressive transformers with standard multi-head attention. LazyLLM's attention-based importance scoring depends on the standard attention mechanism being the primary means of token interaction. Models with mixture-of-experts layers, different attention patterns (e.g., grouped-query attention, multi-query attention), or architectural innovations like sliding window attention might behave differently. Llama 2 uses multi-head attention; XGen's exact architecture is not detailed in the paper, but both are described as standard transformers. The claim of universality to "any existing transformer-based LLM" overreaches the evidence.

**Task diversity.** LongBench provides reasonable diversity — document QA, summarization, few-shot learning, synthetic retrieval, code completion — but all tasks involve processing long text contexts to produce relatively short outputs. Tasks involving chain-of-thought reasoning over long contexts, multi-turn conversation with long history, or long-form generation conditioned on long prompts (e.g., generating a full document from an outline) might stress the dynamic token selection mechanism in different ways. In particular, tasks where generation length is comparable to prompt length would amortize the TTFT savings over many more decoding steps, potentially changing the cost-benefit calculus for the Aux Cache's memory overhead.

#### What Is Missing?

**Memory overhead analysis.** The Aux Cache stores hidden states of pruned tokens at pruning boundaries. The paper never reports the memory cost of this cache, either in absolute terms (MB/GB) or relative to the standard KV cache. For long prompts on memory-constrained hardware, this overhead could be the limiting factor, especially since it scales with (number of pruning layers × prompt length × model dimension). The claim that LazyLLM is "seamlessly integrated" should be qualified by memory requirements.

**Comparison against KV cache eviction methods for decoding.** The paper positions LazyLLM as distinct from methods like H2O and SnapKV because it reduces TTFT, not just decoding speed. However, a natural question is: if you combine LazyLLM (for TTFT) with H2O or SnapKV (for decoding-stage KV cache compression), do the benefits compound? Or do their mechanisms conflict (e.g., does LazyLLM's dynamic revival interact poorly with H2O's permanent eviction)? The paper doesn't explore combinations.

**Statistical rigor.** The paper reports single accuracy and speedup numbers without confidence intervals, standard deviations, or statistical tests. The macro-averaged scores across LongBench datasets are point estimates. For the random token drop baseline, 5-run averaging is performed, but for LazyLLM, no uncertainty quantification is provided. Given that accuracy differences between LazyLLM and baseline are often less than 1 percentage point (e.g., multi-doc QA: 22.31 vs. 22.43), it's possible that some of the "maintained accuracy" results are within measurement noise. The paper would be strengthened by reporting variance across multiple runs or across different random seeds where applicable.

**Per-dataset breakdown.** Table 1 aggregates results by task category (e.g., "Single-Document QA" is the macro-average of multiple LongBench datasets). The individual dataset results are not reported. It's possible that within a task category, some datasets show strong pruning robustness while others degrade substantially, and the aggregate masks this heterogeneity. This matters for practitioners deciding whether LazyLLM is safe for their specific use case.

**Sensitivity to the progressive pruning schedule.** The paper's default configuration uses a three-stage schedule with specific layer assignments and pruning ratios. The results in Figure 5 show different points on the trade-off curve, but the paper doesn't systematically ablate *how* the schedule is constructed — e.g., whether 3 stages is better than 2 or 4, whether equal fraction pruning per stage is optimal, or whether the specific layer boundaries (10%, 30%, 30% of layers) are important. The layer-wise pruning sensitivity analysis in Figure 6 provides the motivation, but the translation from this analysis to the specific three-stage schedule is not rigorously justified.

**Generation speedup disaggregation.** Table 2 reports overall Generation Speedup but doesn't decompose it into TTFT contribution vs. decoding-step contribution. The reader cannot tell whether the generation speedup comes primarily from the faster first token (which is the paper's focus) or from ongoing savings during decoding (which would make LazyLLM more broadly useful). This decomposition would be straightforward to compute from the profiling data but is not provided.

#### Summary Assessment

The experiments **convincingly demonstrate** that dynamic token pruning with revival (LazyLLM) outperforms static pruning, random dropping, and prompt compression on the TTFT-accuracy trade-off for two 7B models on LongBench. The evidence is internally consistent — the main results (Table 1), trade-off curves (Figure 5), and ablations (Figure 6) all point in the same direction — and the method achieves its claimed benefit of meaningful TTFT reduction (1.4-4.8×) with minimal accuracy impact at conservative speedup settings.

The experiments **partially support** the claim of universality across models and tasks. Two models and six task categories provide reasonable breadth, but the absence of scale variation, architectural variation, and statistical error quantification leaves open questions about generalization.

The experiments **raise but do not answer** practical deployment questions: memory overhead of the Aux Cache, behavior under optimized inference frameworks, and interaction with complementary decoding-stage optimization methods. These are not flaws in the experiments that were run — they are experiments that would be valuable for a practitioner evaluating whether to adopt LazyLLM in production.

## 6. Limitations and Trade-offs

### Limitation 1: No Evaluation Across Model Scales or Architectures Beyond Two 7B Dense Models

**The assumption or constraint.** LazyLLM is evaluated exclusively on two 7-billion-parameter dense transformer models: Llama 2 7B and XGen 7B. The paper claims the method "can be seamlessly integrated with any existing transformer-based LLM" (Abstract), but provides no evidence at other scales — 1B, 13B, 70B — and no evidence on non-dense architectures such as mixture-of-experts models, models with grouped-query attention (GQA), or models with multi-query attention (MQA).

**The consequence.** The attention sparsity pattern that LazyLLM exploits (visualized in Figure 2) may not generalize across scales. Larger models often exhibit more diffuse attention distributions because they have greater representational capacity to distribute attention across many tokens. If attention is less concentrated in larger models, LazyLLM's percentile-based pruning would either need to retain a larger fraction of tokens (reducing speedup) or would prune important tokens (degrading accuracy). Conversely, architectures using GQA or MQA share key-value heads across query heads, which could alter how attention scores distribute across tokens — the averaging procedure in Equation 1 averages over `h` heads, and if heads are shared, the effective number of independent importance signals is reduced. A practitioner deploying LazyLLM on a 70B GQA model (e.g., Llama 2 70B) has no direct evidence that the reported speedup-accuracy trade-off will transfer. The failure mode is not a subtle accuracy degradation but potentially a qualitatively different pruning sensitivity curve that makes the method unusable at previously reported speedup levels.

**What evidence exists in the paper.** The only cross-model evidence is the similarity between Llama 2 7B and XGen 7B in Figure 6 — both show the same qualitative pattern of layer-wise pruning sensitivity, but this is a comparison of two models at the same parameter scale with standard multi-head attention. No scale variation experiment exists anywhere in the paper. The authors do not flag scale generalization as a concern — it is simply not discussed.

**Mitigation status.** Not addressed. The paper provides no guidance on how pruning schedules might need to change for different model scales or architectures, nor does it acknowledge this as a limitation to the universality claim.

---

### Limitation 2: Aux Cache Memory Overhead Is Never Measured or Reported

**The assumption or constraint.** The Aux Cache stores the full hidden states of pruned tokens at each pruning boundary to enable efficient token revival. A hidden state vector at layer `l` for a model with dimension `d` requires `d` floating-point values per token. For Llama 2 7B with `d = 4096`, three pruning boundaries (the default progressive schedule), and a prompt of length `N`, the Aux Cache memory footprint is approximately `3 × N × 4096 × 2` bytes in FP16, or roughly `24.6 × N` KB. For a 3,376-token prompt (LongBench average), this is approximately 83 MB — modest in absolute terms. But for a 32K-token prompt, it grows to ~787 MB; for 128K tokens, ~3.1 GB. This is *in addition to* the standard KV cache, which for a 32-layer, 4096-dimensional model with 32K tokens in FP16 is approximately `2 × 32 × 32K × 4096 × 2` bytes ≈ 16.8 GB. The Aux Cache adds roughly 5% to the total KV cache memory at 32K context and more at longer contexts with more pruning boundaries.

**The consequence.** For memory-constrained deployments — edge devices, shared GPU inference servers, or high-throughput batch inference where multiple sequences compete for KV cache space — the Aux Cache memory overhead could become the binding constraint on maximum batch size or maximum context length. The paper guarantees that LazyLLM is "never slower than the baseline" in terms of runtime but provides no corresponding guarantee about memory. In a worst-case scenario where all pruned tokens are revived across many pruning boundaries, the Aux Cache stores hidden states that are all eventually used, and memory is consumed without corresponding compute savings because the model effectively computes everything anyway. A practitioner running at the memory limit of their GPU could find that adding LazyLLM causes out-of-memory errors that don't occur with baseline inference, even though the method is supposed to be a drop-in replacement.

**What evidence exists in the paper.** None. The paper never reports Aux Cache memory usage, either in absolute terms or as a percentage of the standard KV cache, for any configuration. Section 3.2 describes what the Aux Cache stores and Section 4 mentions implementation on HuggingFace, but no memory profiling is included. Table 2 reports "% of Prompt Token Computed" and Generation Speedup, but the memory cost of enabling those savings is absent.

**Mitigation status.** Not addressed. The paper does not mention memory overhead as a consideration, does not report memory measurements, and does not discuss whether the Aux Cache's memory cost could be reduced (e.g., by storing quantized hidden states, storing only at a subset of pruning boundaries, or evicting Aux Cache entries when memory pressure is high).

---

### Limitation 3: The Progressive Pruning Schedule Is Heuristic, Not Learned or Optimized

**The assumption or constraint.** LazyLLM's progressive pruning schedule is controlled by three hyperparameters: the number of pruning layers, their locations in the transformer stack, and the retention ratio at each pruning layer. These are hand-specified and swept manually to trace out accuracy-speedup curves (Figure 5). The paper's default configuration — three pruning stages at roughly 10%, 40%, and 70% depth, each retaining approximately 70% of the currently active tokens — is motivated by the layer-wise sensitivity analysis in Figure 6 but is not derived from an optimization procedure.

**The consequence.** The reported accuracy-speedup trade-off curves in Figure 5 represent an *unknown upper bound* on what a three-stage schedule with these specific layer locations can achieve. There is no guarantee that the swept hyperparameters include the Pareto-optimal configuration for any given speedup target. A more principled approach — learning per-layer retention ratios via a lightweight calibration procedure, or deriving them from a formal analysis of attention entropy across layers — could potentially achieve better accuracy at the same speedup, or higher speedup at the same accuracy. Moreover, the optimal schedule likely depends on the model (as Figure 6 shows, Llama 2 and XGen have similar *qualitative* patterns but the exact accuracy-vs-layer curves differ), meaning that a schedule tuned for Llama 2 7B may be suboptimal for a different model, and the paper provides no procedure for porting the schedule to a new model beyond re-running the full sweep.

A deeper issue is that *uniform* per-stage retention ratios (e.g., keep 70% at every pruning boundary) are likely suboptimal. Figure 6 shows that pruning sensitivity is not linear across layers — the accuracy drop from pruning at layer 5 versus layer 25 is not constant. An optimal schedule would presumably prune different fractions at different layers to reflect this variable sensitivity, but the paper's three-stage approach partitions the transformer into coarse blocks with uniform behavior within each block.

**What evidence exists in the paper.** Figure 5 demonstrates the existence of good configurations through sweeping, but the paper does not compare the three-stage schedule against alternative schedules (e.g., two-stage, four-stage, continuous per-layer retention ratios) at matched speedup. The layer-wise sensitivity analysis in Figure 6 motivates the general principle (prune more later), but does not provide a recipe for translating the single-pruning-layer results into a multi-stage schedule. The paper does not report how many hyperparameter configurations were swept to produce Figure 5, nor the range of speedups that went unexplored.

**Mitigation status.** None. The paper does not address schedule optimization as a limitation or suggest future work on automated schedule selection. A practitioner adopting LazyLLM would need to manually sweep hyperparameters for their specific model and task distribution — a time-consuming process that the paper does not guide.

---

### Limitation 4: No Evidence on Tasks Where Generation Length Rivals Prompt Length

**The assumption or constraint.** The LongBench benchmark has an average prompt length of 3,376 tokens and an average generation length of only 68 tokens — a ratio of roughly 50:1 (Section 1, footnote 1). All six task categories (single-doc QA, multi-doc QA, summarization, few-shot learning, synthetic tasks, code completion) share this characteristic: they involve processing a long context to produce a short answer. The paper's central claim about TTFT optimization is most impactful when TTFT dominates total generation time, which is true when generation is short relative to the prompt.

**The consequence.** LazyLLM's value proposition weakens substantially for tasks with long generation lengths: chain-of-thought reasoning over long contexts, multi-turn conversations with extensive dialogue history, long-form document generation conditioned on a long source, or iterative agent loops that interleave generation with tool calls. In these settings, TTFT accounts for a much smaller fraction of total generation time — if the model generates 2,000 tokens after processing a 3,000-token prompt, TTFT might be only 5-10% of total inference time rather than the 23% reported for LongBench. The speedup on overall generation would then be dominated by the decoding-stage savings (reported as Generation Speedup in Table 2), which are consistently smaller than TTFT speedup. For example, multi-document QA shows 2.34× TTFT speedup but only 1.56× Generation Speedup. On a long-generation task, that 1.56× would be the effective end-to-end speedup, which is less impressive and may not justify the integration complexity and memory overhead.

Furthermore, tasks requiring long generations impose a different kind of stress on the dynamic token selection mechanism. When generating a long response, the model's attention patterns may shift more dramatically across generation steps (the model needs to retrieve different facts for different parts of the response), potentially causing more token revival and reducing the effective pruning rate. The paper's analysis in Figure 7 shows cumulative token usage plateauing after the first ~10 generation steps on LongBench, but LongBench's 68-token average generation length may not be long enough to reveal late-generation dynamics where attention patterns could shift again.

**What evidence exists in the paper.** Table 2 reports Generation Speedup for each task, and these numbers are consistently lower than TTFT speedup, but this is for the same short-generation tasks. No experiments vary generation length systematically. The paper does not evaluate on tasks like long-form summarization (where the output is hundreds of tokens), chain-of-thought reasoning with retrieval, or multi-turn dialogue. The analysis in Section 5.5 (Figure 7) profiles token usage across "absolute generation time steps" but only up to approximately 35 steps — consistent with LongBench's short generation, not with long-generation scenarios.

**Mitigation status.** Not addressed. The paper does not discuss how LazyLLM's benefits scale with generation length or acknowledge this as a scope limitation. The abstract and introduction frame LazyLLM as a general solution for "long context LLM inference" without distinguishing between long-input-short-output and long-input-long-output scenarios.

---

### Limitation 5: The Prompt Compression Baseline Is Weak — Not Representative of the Best Possible Compression

**The assumption or constraint.** The paper compares LazyLLM against a single prompt compression baseline, described as following Li et al. (2023), which "uses an LLM to compress the prompt by removing redundant tokens before inference." The TTFT measurement includes the compression step, and the results are starkly negative: compression achieves 0.10-0.69× TTFT speedup (meaning 1.4-10× slower than baseline) across all tasks (Table 1). From this, the paper concludes that prompt compression is ineffective for TTFT reduction.

**The consequence.** This comparison potentially overstates LazyLLM's advantage over the broader category of prompt reduction methods. The specific compression approach evaluated — using an LLM to compress the prompt — is among the most computationally expensive possible compression strategies. Alternative approaches not evaluated include: (a) **heuristic compression** (e.g., truncating to the first N tokens, keeping only sentences containing keywords from the query, removing stop words), which would have negligible overhead; (b) **small-model compression** (using a much smaller or distilled model for the compression step, trading compression quality for speed); (c) **embedding-based compression** (selecting tokens based on embedding similarity to the query, which can be done with a single matrix multiplication); (d) **cached compression** (pre-computing compressed versions of documents offline, which is feasible when the same documents are queried repeatedly, as in retrieval-augmented generation). Some of these could plausibly achieve meaningful TTFT reduction with much lower overhead than the LLM-based compression tested.

A practitioner reading this paper might conclude that *all* compression-based approaches are futile for TTFT reduction, when in fact the evidence only demonstrates that *one specific expensive approach* is ineffective. This is a limitation of the experimental design rather than of the LazyLLM method itself, but it affects how the paper's contribution is positioned relative to alternatives.

**What evidence exists in the paper.** Table 1 and Figure 5 show the compression baseline results. The paper describes the baseline only as following Li et al. (2023) and states it uses an LLM for compression. No details are provided about which LLM was used, how much it compressed prompts on average, or what the compression ratio was. The paper does not evaluate any lighter-weight compression alternatives.

**Mitigation status.** Not addressed. The paper treats "prompt compression" as a monolithic category represented by one expensive method. No discussion acknowledges the heterogeneity of compression approaches or suggests that lighter-weight compression could be a viable alternative or complement to LazyLLM.

### Limitation 6: No Statistical Error Quantification for Accuracy Measurements

**The assumption or constraint.** The paper reports accuracy as macro-averaged scores across LongBench datasets within each task category, using point estimates without confidence intervals, standard deviations, or any form of uncertainty quantification. The only exception is the random token drop baseline, which is averaged over 5 runs to account for the stochasticity of random dropping. For LazyLLM, static pruning, and the baseline, results are reported as single numbers.

**The consequence.** Many of the paper's headline results involve accuracy differences of less than one percentage point between LazyLLM and the baseline. For multi-document QA on Llama 2: 22.31 (LazyLLM, 2.34× speedup) vs. 22.43 (baseline), a difference of 0.12 points. For single-document QA: 25.59 vs. 25.79, a difference of 0.20 points. For few-shot learning: 62.81 vs. 62.90, a difference of 0.09 points. These differences are claimed as evidence that LazyLLM "maintains accuracy," but without error bars, it is impossible to determine whether they are statistically significant or within the noise floor of the evaluation.

LongBench's 16 datasets vary in size, and the macro-average across them weights each dataset equally regardless of its sample count. A small dataset with high variance could dominate the uncertainty in the macro-average. Furthermore, LazyLLM is deterministic (given fixed model weights and deterministic attention computation), but the LongBench evaluation itself has sources of variance: prompt formatting variations, the grading functions for metrics like ROUGE-L, and potential non-determinism in GPU floating-point operations. Without quantifying this variance, the claim of "negligible accuracy drop" is an assertion, not a statistically grounded finding.

For the code completion task, the LazyLLM accuracy is 53.30 vs. 55.18 baseline — a 1.88-point drop, or 3.4% relative. Whether this is "negligible" depends on the application, but even here, the absence of error bars means the reader cannot assess whether this gap is robust or could be closed with a slightly different hyperparameter configuration.

**What evidence exists in the paper.** Table 1 and Figure 5 present point estimates only. The paper does not discuss measurement uncertainty, does not report the standard deviation of the baseline accuracy across multiple evaluation runs, and does not provide per-dataset breakdowns that would let the reader assess variability. The 5-run averaging for random token drop demonstrates awareness of stochastic variation, but the same rigor is not applied to the method being proposed.

**Mitigation status.** Not addressed. This is a methodological weakness that affects the interpretation of the paper's central accuracy-preservation claims, particularly at the conservative speedup settings where LazyLLM allegedly matches baseline performance.
