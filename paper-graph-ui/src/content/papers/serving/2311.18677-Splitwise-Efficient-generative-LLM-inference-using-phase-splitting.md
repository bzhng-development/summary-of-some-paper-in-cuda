# Splitwise: Efficient generative LLM inference using phase splitting

**ArXiv:** [2311.18677](https://arxiv.org/abs/2311.18677)

## 🎯 Pitch

This paper introduces **Splitwise**, a model deployment and scheduling technique that splits the two phases of generative LLM inference requests—prompt computation and token generation—onto separate machines to enable phase-specific resource management.

---

## 1. Executive Summary

This paper introduces **Splitwise**, a model deployment and scheduling technique that splits the two phases of generative LLM inference requests—prompt computation and token generation—onto separate machines to enable phase-specific resource management. Through an extensive characterization of production inference traces on the NVIDIA A100 and H100 GPUs with Llama2-70B and BLOOM-176B models, the authors identify that the prompt phase is compute-bound while the token generation phase is memory-bandwidth-bound and significantly underutilizes GPU compute and power resources. Splitwise separates these phases across heterogeneous machine pools (using DGX-A100s for token generation and DGX-H100s for prompt processing, or power-capped H100s for token generation), transferring the KV-cache between machines via optimized layer-wise asynchronous transfers over InfiniBand. The technique yields up to 1.4× higher throughput at 20% lower cost, or alternatively 2.35× higher throughput under the same power and cost budgets, establishing that disaggregating inference phases enables substantial efficiency gains that are robust to workload changes and model substitutions.

## 2. Context and Motivation

### The Core Problem: LLM Inference Is Bottlenecked by Phase Mismatch

The fundamental problem this paper tackles is that generative LLM inference has two phases with **radically different resource requirements**, yet state-of-the-art serving systems run both phases on the same machines. This mismatch leads to systematic underutilization of expensive GPU resources, forcing cloud providers to over-provision hardware to meet latency service level objectives (SLOs).

The two phases at issue are inherent to the autoregressive nature of transformer-based generative models (Section II-B). In the **prompt computation phase**, all input tokens are processed in parallel through the model's forward pass to generate the first output token and populate the key-value (KV) cache with attention context. This phase is computationally intensive—it saturates the GPU's floating-point units and scales nearly linearly with prompt size (Figure 5a). In the **token generation phase**, subsequent output tokens are produced one at a time, each requiring only the previously generated token plus the cached attention context from all prior tokens. This phase is memory-bandwidth-bound: the GPU must repeatedly stream the entire KV-cache and model weights from high-bandwidth memory (HBM), but its compute units sit largely idle waiting on data.

The consequence is visible in the paper's characterization of power utilization (Figure 8). During the prompt phase, GPU power draw scales with batch size and can approach the thermal design power (TDP). During token generation, power draw is substantially lower and **does not vary with batch size**—the GPU is memory-bound regardless of how many requests are batched together. This means every token generation step wastes a significant fraction of the GPU's power budget and compute capability.

Why this mismatch matters now is tied to industry trends the paper documents in Table I and Section I. GPU hardware generations are scaling **compute and memory asymmetrically**. The NVIDIA H100 provides 3.43× more compute (TFLOPS) and 1.75× more power consumption than the A100, but only 1.64× more memory bandwidth and zero increase in memory capacity (80GB HBM in both). This means each successive GPU generation **exacerbates** the phase mismatch: prompt computation speeds up, but token generation remains bottlenecked by memory bandwidth that isn't improving fast enough. Running both phases on the same hardware means the token phase cannot exploit the new compute capability, while simultaneously costing more in power and capital expenditure.

This mismatch has real-world consequences at scale. The paper's production traces from two Azure LLM inference services—one for code completion and one for conversation—reveal that the majority of end-to-end request latency is spent in the token generation phase (Figure 5c), even for the coding service where prompts are large and output tokens are few. For BLOOM-176B, a prompt of 1500 tokens takes the same time as generating only 6 output tokens. This means expensive H100 GPUs spend most of their time memory-bandwidth-bound, consuming near-peak power but delivering far below peak compute utilization.

### The Problem Matters for Three Stakeholder Reasons

**1. GPU capacity crunch and capital expenditure.** The paper explicitly frames LLM inference demand as exceeding training demand and contributing to a worldwide GPU shortage (Section I). Cloud service providers (CSPs) are building new datacenters specifically to meet GPU demand and are hitting power provisioning limits. In this environment, any technique that extracts more throughput per GPU or reduces the power/cost per inference request directly translates to better service availability and economics. The paper's characterization that mixed continuous batching—the state-of-the-art approach—spends 60-70% of the time running 20 tokens or fewer (Figure 4, conversation trace) and over 20% of the time running a single token (coding trace) demonstrates the scale of the underutilization problem.

**2. The scaling trajectory is making things worse.** Table I's comparison of A100 vs. H100 specifications is central to the paper's motivation. If GPU scaling followed a balanced trajectory (compute, memory, power all increasing proportionally), the phase mismatch might be manageable. Instead, the divergence means that **each new GPU generation is a worse fit for token generation than the last**, while being excellent for prompt computation. This creates an opportunity the paper seizes: what if you run prompt computation on the latest GPUs but token generation on older, cheaper, more memory-balanced hardware? The H100 costs 2.16× more per hour than the A100 but provides only 1.64× more memory bandwidth—the very resource token generation needs. The paper's Table IV confirms this intuition: running Llama-70B on A100s vs. H100s shows that token generation latency (TBT) only improves by a factor of 0.70× on H100, while prompt latency (TTFT) improves by 0.51–0.54×, but the A100 delivers better or equal cost and energy per request.

**3. Power provisioning is becoming the bottleneck for CSPs.** Section I cites datacenter power constraints as a primary concern: CSPs are "running into a power wall" building GPU datacenters. The paper's power characterization shows that token generation power draw is substantially below TDP and insensitive to batch size (Figure 8b). Power capping experiments (Figure 9) reveal that token generation latency is essentially unaffected by reducing the power cap by over 50%, while prompt computation degrades sharply. This means that under current monolithic deployment models, CSPs must provision power for the peak draw of both phases combined—paying for power capacity that token generation phases never actually use. The paper estimates that this creates room for significant power savings (or, alternatively, higher throughput under the same power budget) if the phases can be managed independently.

### Where Prior Approaches Fall Short

**Batching mechanisms are necessary but insufficient.** The paper surveys three generations of batching (Section II-D, Figure 2): request-level batching (naive), continuous batching (Orca-style, where scheduling decisions happen at each forward pass but prompt and token phases are kept in separate batches), and mixed continuous batching (SARATHI-style, where prompts and tokens can interleave in the same batch). Mixed batching is the state of the art and the paper's own baseline. It solves the problem of prompt preemption inflating TBT (time between tokens) tail latencies, but it does not address the fundamental resource mismatch: when a prompt phase and token phases share a batch, the token phases still see longer runtime because the prompt phase dominates compute, and the prompt phase still gets throttled by the memory-bandwidth demands of token phases. The paper's Insight II and Figure 4 show that even with mixed batching, most of the time is spent with very few active tokens batched—the token phase simply cannot batch enough requests to saturate compute because it runs out of memory capacity first (Insight V, Figure 7).

**Model parallelism distributes but doesn't disaggregate.** Tensor parallelism and pipeline parallelism (Section II-E) split the model's layers or tensors across GPUs within or across machines. These techniques improve latency and memory capacity per request, but they replicate the same work on each GPU—every GPU in the pipeline does both prompt computation and token generation. The phase mismatch is replicated, not resolved.

**Prior heterogeneous scheduling and model serving work does not exploit phase-level disaggregation.** The paper situates itself relative to several research traditions (Section VIII). Heterogeneous scheduling for interactive services and CPUs has explored matching workload phases to heterogeneous hardware, but these works do not consider the batching dynamics specific to LLM inference or the KV-cache state that must be transferred between phases. Model serving systems have focused on optimizing batching, scheduling, and memory management within the single-machine paradigm—techniques like PagedAttention (vLLM), Orca's iteration-level scheduling, and SARATHI's chunked prefill all improve efficiency but still run both phases on the same GPUs. Recommendation system inference works have exploited compute/memory heterogeneity within and across models through selective scheduling between CPUs and accelerators, and through colocating models with complementary memory usage. These are the closest intellectual ancestors, but LLM inference differs in that the heterogeneity is *within a single request* (not across different model types), and the state that must be transferred between phases (the KV-cache) is both large and continuous.

The key gap across all prior work is that **no system treats the prompt and token generation phases as independently schedulable, independently provisionable computational stages**. The paper argues that prior work implicitly assumes the two phases must run on the same machine because the KV-cache tying them together seems too expensive to transfer. By demonstrating that optimized KV-cache transfer over InfiniBand adds negligible overhead (<7% of prompt computation time with serialized transfer, <1% of end-to-end latency with per-layer overlap, per Figures 14-15), the paper removes this assumption and opens the design space Spliwise exploits.

### How This Paper Positions Itself

The paper frames Splitwise not as a new model architecture, compression technique, or kernel optimization, but as a **system-level resource disaggregation technique** that separates inference phases onto phase-specialized machines. This positioning is explicit in the design space exploration (Section IV-D): Splitwise enables four hardware configurations (AA, HH, HHcap, HA) that match prompt and token machines to the hardware best suited for each phase, optimizing for different combinations of throughput, cost, and power.

The approach is analogous to disaggregated system architectures that have emerged in other domains—separating compute from storage in data-intensive systems, or separating CPUs from GPUs in heterogeneous computing—but applied to the unique two-phase structure of autoregressive LLM inference. The key intellectual move is recognizing that the KV-cache transfer overhead, which might seem like a showstopper for disaggregation, can be rendered negligible through layer-wise asynchronous pipelining over fast back-end interconnects that are already present in production GPU clusters (InfiniBand at 200-400 Gbps, Section II-F).

The paper explicitly connects to the broader trend of hardware specialization and heterogeneous computing (Section VII), noting that Splitwise's phase-specialized provisioning methodology could apply to any hardware aligning with the computational requirements of each phase: high-compute, moderate-memory for prompts; moderate-compute, high-memory-bandwidth, high-memory-capacity for token generation. This includes AMD GPUs, CPUs with HBM (Intel Sapphire Rapids), FPGAs, or ASICs—none of which are evaluated but all of which fit the framework.

Critically, the paper does not claim to solve the memory capacity bottleneck for token generation. The token phase still saturates memory capacity before compute (Figure 7), limiting batch sizes. What Splitwise solves is the *co-location penalty*: by separating phases, prompt machines can be sized for compute throughput (fewer, more compute-dense GPUs) while token machines can be sized for memory capacity (more GPUs, potentially of an older generation with better memory-to-compute ratios), and neither phase interferes with the other's scheduling or power provisioning.

## 3. Technical Approach

### 3.1 Reader Orientation

Splitwise is a cluster-level deployment and scheduling system that routes the two distinct computational phases of each LLM inference request—prompt computation and token generation—to separate, phase-specialized GPU machines, transferring the intermediate attention state between them over fast datacenter interconnects. It solves the problem of GPU underutilization caused by the fundamental mismatch between the compute-intensive prompt phase and the memory-bandwidth-intensive token generation phase running on the same hardware, by disaggregating these phases so each can be provisioned with, scheduled on, and power-managed for hardware optimized for its specific resource profile.

### 3.2 Big-Picture Architecture (Diagram in Words)

The Splitwise system consists of five major components connected in a request-processing pipeline:

1. **Cluster-Level Scheduler (CLS):** A centralized dispatcher that routes each incoming inference request to a pair of machines—one from the prompt pool and one from the token pool—using Join-the-Shortest-Queue scheduling based on pending token counts. It also dynamically manages three machine pools (prompt, token, and mixed) to handle load fluctuations without fragmentation.

2. **Prompt Machine Pool:** A set of GPU machines (typically DGX-H100s) dedicated exclusively to running the prompt computation phase—processing all input tokens in parallel, generating the first output token, and populating the KV-cache. These machines are provisioned for high compute throughput and are sensitive to power capping.

3. **Token Machine Pool:** A separate set of GPU machines (which may be older DGX-A100s, power-capped DGX-H100s, or standard DGX-H100s depending on the optimization target) dedicated exclusively to the token generation phase—producing output tokens one at a time by repeatedly running the forward pass on the last generated token plus the KV-cache transferred from the prompt machine. These machines are provisioned for memory bandwidth and capacity, and they batch aggressively since TBT is insensitive to batch size.

4. **KV-Cache Transfer Mechanism:** An optimized communication layer built on MSCCL++ that asynchronously transfers the KV-cache from the prompt machine to the assigned token machine, either as a single serialized block (for small prompts) or layer-by-layer overlapped with prompt computation (for large prompts), over the InfiniBand backplane interconnect already present in GPU clusters.

5. **Machine-Level Scheduler (MLS):** A per-machine scheduler that manages local GPU memory capacity, maintains the pending request queue, and makes per-iteration batching decisions. On prompt machines, it caps batch sizes at 2048 tokens total to avoid throughput degradation. On token machines, it batches as aggressively as memory allows and reports queue depth back to the CLS. On mixed-pool machines, it prioritizes prompts to meet TTFT SLOs while applying age-based priority and preemption limits to prevent token starvation.

The information flow for a single request follows this sequence: (1) a request arrives at the CLS, which consults machine queue lengths and assigns it to a specific prompt machine and a specific token machine simultaneously; (2) the prompt machine processes all input tokens through the model's forward pass, generating the first output token and the full KV-cache for all layers; (3) during prompt computation, the KV-cache for each layer is asynchronously transferred to the token machine as each layer completes (for large prompts) or transferred serially after prompt completion (for small prompts); (4) the token machine receives the KV-cache, initializes its local attention state, and begins autoregressive token generation, batching this request with other requests at the same stage; (5) when generation completes, the final response is returned to the user, and the token machine frees the associated KV-cache memory.

### 3.3 Roadmap for the Deep Dive

- **First**, the cluster-level scheduling and machine pool management logic (Section 3.4.1), because it is the control plane that routes every request and determines which machines handle which phases—understanding the pools, the JSQ routing rule, and the mixed-pool overflow mechanism is prerequisite to everything else.
- **Second**, the KV-cache transfer mechanism (Section 3.4.2), since it is the enabler that makes phase disaggregation physically possible—without understanding why the overhead is negligible, the entire architecture seems infeasible.
- **Third**, the machine-level scheduling and batching policies (Section 3.4.3), because these are the per-machine resource management rules that make each pool efficient once requests are assigned.
- **Fourth**, the provisioning methodology and design space exploration (Section 3.4.4), which shows how Splitwise clusters are sized and how the four hardware configurations (AA, HH, HA, HHcap) map to different optimization objectives—this ties the operational mechanisms together into deployable cluster designs.
- **Fifth**, the simulator that enables cluster-scale evaluation (Section 3.4.5), since all cluster-level results depend on it and understanding its fidelity is essential for interpreting the evaluation.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems design and empirical characterization paper** whose core idea is that disaggregating LLM inference phases onto separate, phase-specialized machines enables independent resource sizing, scheduling, and power management, yielding substantial throughput, cost, and power efficiency gains over monolithic deployments.

---

#### 3.4.1 Cluster-Level Scheduling and Machine Pool Management

The Cluster-Level Scheduler (CLS) is the top-level control plane responsible for two tasks: routing incoming inference requests to specific machines, and dynamically managing the composition of three machine pools to adapt to changing load conditions.

**Machine pool architecture.** The CLS maintains three pools of GPU machines, all pre-loaded with the same model weights:

- **Prompt pool:** machines dedicated to prompt computation. These machines only run the forward pass over all input tokens to produce the first output token and populate the KV-cache.
- **Token pool:** machines dedicated to token generation. These machines only run autoregressive generation of output tokens, one per forward pass, using KV-caches received from prompt machines.
- **Mixed pool:** machines that can run both prompt and token phases using mixed continuous batching (the same batching strategy that non-Splitwise baselines use). The mixed pool expands when the prompt or token pool is overloaded and contracts when the overload subsides.

A machine in the mixed pool retains its original identity as a prompt or token machine and returns to its original pool once there are no tasks of the opposite type in its pending queue. Switching a machine between pools does not incur any noticeable latency because no model reloading is required—all machines are pre-loaded with the same model weights.

**Pool sizing and repurposing.** The initial assignment of machines to pools is determined at provisioning time based on the expected request load and input/output token distributions (Section 3.4.4 describes this methodology). The paper notes that repurposing machines between the prompt and token pools—as opposed to temporarily moving them to the mixed pool—is done infrequently, "typically only if they stay in the mixed pool for a considerable amount of time" (Section IV-A). This is a coarse-grained rebalancing mechanism for persistent workload shifts, not a per-iteration adaptation.

**Request routing via Join-the-Shortest-Queue.** When a new inference request arrives, the CLS assigns it to a pair of machines—one prompt machine and one token machine—simultaneously. The assignment uses Join-the-Shortest-Queue (JSQ) scheduling, a well-known load-balancing algorithm where each incoming job is sent to the server with the fewest queued jobs. In Splitwise, "queue length" is defined as the **number of pending tokens**, not the number of pending requests, because requests with large prompts or long generation sequences impose more load than short requests.

Each machine regularly communicates its current memory capacity utilization and pending queue depth to the CLS, but not at every iteration boundary—the paper states this communication happens at a coarser granularity to avoid excessive coordination overhead. The CLS uses this information to select, for each incoming request, the prompt machine with the shortest pending token queue and the token machine with the shortest pending token queue.

Assigning both machines simultaneously when the request is first scheduled is a deliberate design choice: it enables the CLS to overlap KV-cache transfer setup with prompt computation on the prompt machine, reducing transfer overheads (as detailed in Section 3.4.2). If the CLS assigned the token machine only after prompt computation completed, the KV-cache transfer would sit on the critical path of token generation, adding directly to end-to-end latency.

**Mixed pool overflow mechanism.** When the CLS finds that the pending queue for the target pool (e.g., the prompt pool) exceeds a configurable threshold, it looks for available machines in the mixed pool first. If the mixed pool is also full, the CLS looks in the opposite pool (e.g., the token pool) for a machine that can be temporarily reclassified into the mixed pool. This machine begins operating under mixed continuous batching—it can accept both prompts and tokens, prioritizing prompts to meet TTFT SLOs while applying the age-based anti-starvation mechanisms described in Section 3.4.3. Once the queue of mixed requests on that machine drains, the CLS transitions it back to its original pool.

This mechanism prevents the fragmentation that would occur if prompt machines sat idle while token machines were overloaded (or vice versa). It effectively allows Splitwise to degrade gracefully toward a monolithic deployment under extreme load imbalance—when all machines are in the mixed pool, the system behaves identically to a non-Splitwise cluster.

**Design rationale.** The two-pool-plus-overflow architecture addresses a fundamental tension: specialization (dedicating machines to a single phase) improves efficiency at normal loads by eliminating phase interference and enabling phase-specific hardware selection, but it creates a fragmentation risk when the load mix deviates from the provisioning assumption. The mixed pool is the hedging mechanism—it lets Splitwise capture the efficiency gains of specialization without sacrificing robustness to workload skew. The JSQ routing policy, by load-balancing based on pending tokens rather than request count, accounts for the heterogeneous sizes of requests within each phase.

#### 3.4.2 KV-Cache Transfer Mechanism

The KV-cache transfer is the critical enabling mechanism for Splitwise—without it, there is no way to move the attention state from the prompt machine to the token machine, and phase disaggregation is impossible. The paper designs two transfer modes (serialized and per-layer) and selects between them based on prompt size to minimize the overhead visible to the user.

**What is being transferred.** The KV-cache consists of the key and value tensors produced by each attention layer during the prompt computation phase. For a transformer with `$L$` layers, hidden size `$H$`, and an input prompt of `$N$` tokens, the total size of the KV-cache is proportional to `$L \times N \times H$`. The exact storage format depends on the serving system—in the paper's vLLM-based implementation, the KV-cache is stored in a paged block structure, and the transfer operates block-by-block.

**Naive serialized transfer (baseline).** In the simplest approach, the prompt machine completes the entire prompt computation phase (processing all input tokens and generating the first output token), then transfers the complete KV-cache for all layers as a single block over InfiniBand to the token machine. The token machine cannot begin generating the second output token until this transfer completes. Figure 11a in the paper illustrates this timeline: prompt computation finishes, a KV-cache transfer period follows, and only then does token generation begin. The transfer latency therefore adds directly to the time between the first and second output tokens, increasing TBT and end-to-end latency.

The paper measures this transfer latency in Figure 14: on A100s (200 Gbps InfiniBand), serialized transfer takes approximately 8ms for small prompts and grows linearly to roughly 35ms for 2048 batched tokens. On H100s (400 Gbps InfiniBand), transfer is roughly half as fast—approximately 5ms to 18ms for similar sizes—because the interconnect bandwidth is doubled. As a fraction of prompt computation time, this overhead is under 7% for large prompts.

**Optimized per-layer transfer.** The key insight is that the KV-cache is not generated all at once at the end of prompt processing—it is produced **layer by layer** as the forward pass proceeds through the transformer. Each attention layer computes its key and value tensors independently, and once computed, those tensors are not modified by subsequent layers. Splitwise exploits this by triggering an asynchronous transfer of each layer's KV-cache immediately after that layer completes, while the prompt computation continues to the next layer.

The implementation uses MSCCL++, an optimized GPU-driven communication library, to perform one-sided `put` operations directly from the prompt machine's GPU memory to the token machine's GPU memory over InfiniBand. The prompt machine initiates the transfer without requiring the token machine to issue any receive instructions (zero-copy, one-sided communication). After all layers have been transferred, the prompt machine signals a semaphore over the same InfiniBand connection. The token machine waits on this semaphore before beginning token generation, ensuring no layer's KV-cache is accessed before it arrives.

The paper implements fine-grained synchronization: each request in a batch is assigned a different semaphore because different requests may be routed to different token machines. When transferring KV-cache for a batch of prompts where multiple requests go to the same token machine, the system ships KV blocks contiguously when they share the same semaphore, minimizing the number of individual transfer operations.

**Transfer mode selection.** The paper does not use per-layer transfer for all prompts. The layer-wise transfer requires fine-grained per-layer synchronization, which can introduce performance interference from the communication library and increase the TTFT—especially for small prompts where the total transfer size is modest and the overhead of managing many small transfers dominates the benefit of overlapping. The CLS selects the transfer mode based on a simple threshold: for prompt sizes below 512 tokens on H100 (and the corresponding threshold on A100), the system uses serialized transfer; for larger prompts, it uses per-layer transfer. Figure 14 shows the result: with per-layer transfer, the visible non-overlapped transfer time is only a small constant (roughly 8ms on A100 and 5ms on H100), independent of prompt size, because all but the last layer's transfer is hidden behind computation.

**End-to-end latency impact.** Figure 15 quantifies the overall impact on a real production trace (coding, no batching). Compared to the 1-machine baseline where both phases run on the same GPU, Splitwise adds only 0.8% to the end-to-end latency when using per-layer transfer, versus 3% with serialized transfer for large prompts. The most user-visible impact is on the latency of the second output token—the first token after the one generated by the prompt machine. Splitwise adds 16.5% to this specific token's latency, compared to 64% overhead from serialized transfer. The paper argues this is "hardly perceivable even in a user-facing inference" because it affects only a single token in the streaming output.

**Earlier start and earlier release optimizations.** The per-layer transfer enables two additional optimizations mentioned in passing (Section IV-C). First, the token machine can begin the token generation phase earlier—as soon as the first layer's KV-cache arrives, it could theoretically start processing, though the paper does not implement this because all layers are needed for the complete forward pass. Second, the prompt machine can release KV-cache memory earlier—once a layer's cache has been successfully transferred, the prompt machine can free that GPU memory, potentially reducing peak memory pressure during prompt processing.

**Design rationale.** The choice to invest engineering effort in an optimized, overlapped KV-cache transfer rather than accepting the simpler serialized approach is driven by a key observation: the transfer sits on the critical path for TBT, and TBT directly determines user-perceived streaming latency. A serialized transfer that adds 35ms to the second token would be very noticeable in interactive applications, making the disaggregation approach unattractive despite its throughput benefits. The per-layer overlap reduces this to roughly 5ms constant, which is comparable to normal iteration-to-iteration variation and therefore acceptable. The paper's implementation on MSCCL++ with one-sided puts is also designed to minimize CPU involvement—the transfer is entirely GPU-driven, avoiding host-side bottlenecks.

#### 3.4.3 Machine-Level Scheduling and Batching Policies

Each machine in the Splitwise cluster runs a Machine-Level Scheduler (MLS) that manages the local GPU's memory capacity, maintains a pending request queue, and decides which requests to include in each forward-pass batch. The MLS policies differ by pool type because the resource bottlenecks differ.

**Prompt machine MLS.** Prompt machines run only the prompt computation phase. The MLS uses first-come-first-serve (FCFS) ordering—no priority or preemption needed because all requests are in the same phase. The critical scheduling decision is the **batch size limit**: the MLS restricts the total number of tokens batched together in a single prompt forward pass to 2048 tokens. This is not a hard memory limit but a throughput optimization. Figure 6a shows that prompt processing throughput (measured in tokens per second) increases with batch size up to approximately 2048 tokens, then degrades. Beyond this point, the compute units become saturated and the marginal cost of adding more tokens (increased latency for all requests in the batch) outweighs the marginal benefit (more tokens processed per forward pass).

The 2048-token limit is described as a configurable parameter that can change for different models or hardware. For the median prompt sizes in the traces (1500 tokens for coding, 1020 for conversation), this corresponds to batch sizes of roughly 1-2 requests, consistent with Insight IV that "the prompt phase batch size should be limited to ensure good performance."

Since prompt machines generate the first output token and then transfer the KV-cache, the MLS also coordinates with the KV-cache transfer mechanism: it ensures the transfer for each request in the batch is initiated (either after prompt completion for serialized transfers, or after each layer for per-layer transfers) before the request is removed from the machine's active set.

**Token machine MLS.** Token machines run only the token generation phase. The MLS uses FCFS ordering and batches as aggressively as memory permits. The critical constraint is **GPU memory capacity**, not compute: Figure 6b shows that token generation throughput continues to increase with batch size up to 64 (the maximum tested), but Figure 7 shows that memory capacity is the limiting factor—the KV-cache for each active request consumes HBM, and once the HBM is full (accounting for model weights and activations), no further requests can be added to the batch.

The MLS explicitly tracks GPU memory utilization and starts queueing incoming requests once the machine is close to its memory capacity limit. When a request completes token generation (producing the end-of-sequence token), its KV-cache memory is freed, and the MLS admits the next request from the pending queue into the active batch.

This aggressive batching strategy is justified by Figure 5b: TBT grows only 2× when batch size increases from 1 to 64, meaning the memory-capacity-limited batching yields substantial throughput gains (more tokens generated per forward pass) with only modest latency impact. This is the exploit of Insight III and Insight V: token generation is memory-bandwidth-bound, so compute sits idle regardless of batch size, and the only cost of larger batches is a small increase in per-token latency that is acceptable under the SLO framework.

**Mixed machine MLS.** When a machine enters the mixed pool, its MLS must handle both prompt and token phases. The scheduling policy becomes more complex because prompt and token phases have different latency sensitivity:

- **Prompt prioritization:** To meet TTFT SLOs, the MLS must prioritize running prompt phases over token phases. When a new prompt request arrives and the machine has no capacity to run it alongside the current token batch, the MLS preempts one or more token requests—pausing their generation and evicting them from the current batch—to make room for the prompt.

- **Anti-starvation mechanisms:** Token preemption could, in the worst case, prevent token generation from ever making progress if prompts arrive continuously. The MLS applies two protections: (1) the priority of a token request increases with age—the longer a token request has been waiting or preempted, the higher its scheduling priority; (2) each request has a limit on the number of preemptions it can experience, after which it becomes non-preemptable.

- **Batch composition:** The mixed machine uses the same mixed continuous batching strategy as the non-Splitwise baseline. In each forward pass, the batch can contain a mixture of prompts and tokens. Since the prompt phase is compute-intensive and the token phase is memory-intensive, running them together means the prompt phase benefits from the available compute while the token phase streams its KV-cache, but the token phase experiences longer runtime because the forward pass is dominated by prompt computation. This is the interference that Splitwise's primary design avoids—the mixed pool only activates this mode when load imbalance forces it.

**MLS-CLS communication.** Each MLS regularly reports two pieces of information to the CLS: its current pending queue depth (in tokens) and its current memory capacity utilization. This is not done at every forward-pass iteration (which could be tens to hundreds per second), but at a coarser interval to limit control-plane overhead. The reports enable the CLS's JSQ routing decisions and mixed-pool overflow triggering.

**Design rationale.** The three-tier MLS design reflects the fundamental insight that prompt and token phases have different resource bottlenecks, so their scheduling policies should optimize for different constraints. Prompt scheduling optimizes for compute throughput with a fixed batch limit. Token scheduling optimizes for memory capacity utilization with aggressive batching. Mixed scheduling optimizes for latency SLOs with prompt prioritization. This tiered approach is possible precisely because Splitwise separates the phases into different machines—in a monolithic deployment, a single MLS would have to apply the mixed scheduling policy universally, with its associated interference and inefficiency.

#### 3.4.4 Provisioning Methodology and Design Space Exploration

Splitwise is not a fixed cluster configuration—it is a methodology for provisioning LLM inference clusters given workload characteristics, SLO constraints, and an optimization objective. The paper defines a search-based provisioning framework that explores the two-dimensional design space of (number of prompt machines, number of token machines) to find the optimal configuration.

**Inputs to provisioning.** The provisioning framework requires six inputs:

1. **Target cluster design:** which of the four hardware configurations to evaluate—Splitwise-AA (A100 prompt, A100 token), Splitwise-HH (H100 prompt, H100 token), Splitwise-HA (H100 prompt, A100 token), or Splitwise-HHcap (H100 prompt, power-capped H100 token).
2. **LLM-specific performance model:** a piece-wise linear model that estimates TTFT and TBT given input size, output size, batch size, and parallelism configuration. This model is constructed from profiling data (Section V) and achieves a mean absolute percentage error (MAPE) under 3% on an 80:20 train:test split.
3. **Request trace:** a synthetic trace derived from the target service's prompt and token size distributions (e.g., Figure 3 for coding vs. conversation), with Poisson arrivals at a tunable rate (requests per second).
4. **SLO constraints:** nine latency thresholds at P50, P90, and P99 for TTFT, TBT, and E2E latency, expressed as slowdown multiples relative to a request running on a DGX-A100 under no contention. The specific multiples are: TTFT at 2× (P50), 3× (P90), 6× (P99); TBT at 1.25× (P50), 1.5× (P90), 5× (P99); E2E at 1.25× (P50), 1.5× (P90), 5× (P99). All nine SLOs must be met for a cluster configuration to be considered valid.
5. **Constraint:** the target metric to hold constant (e.g., peak throughput of 70 RPS, total provisioned power equal to 40 DGX-H100s, total cost equal to Baseline-H100).
6. **Optimization goal:** which metric to minimize or maximize (throughput, cost, or power).

**Search procedure.** The provisioning framework iterates over the two-dimensional grid of (num_prompt_machines, num_token_machines), running the event-driven simulator (Section 3.4.5) for each configuration under the specified trace and arrival rate. For each configuration, the simulator outputs the achieved P50, P90, and P99 values for TTFT, TBT, and E2E latency. Configurations that fail any of the nine SLOs are discarded. Among the remaining valid configurations, the framework selects the one that optimizes the target objective under the given constraint.

Figure 12 illustrates this for a coding workload under Splitwise-HH with a target peak throughput of 70 RPS and cost minimization. The search space spans prompt machine counts from roughly 10 to 35 and token machine counts from roughly 2 to 20. The cost-optimal configuration that meets all SLOs is marked as (27 prompt, 3 token)—the token pool is much smaller than the prompt pool because the coding trace has very few output tokens (median 13), so each token machine can handle many concurrent requests.

**The four hardware configurations.** Table V defines the four Splitwise variants by their hardware choices, which encode different optimization priorities:

- **Splitwise-AA:** both pools use DGX-A100s. This represents the homogeneous case using older, cheaper, more memory-balanced GPUs. Normalized to DGX-A100, both machine types have 1× cost, 1× power, and connect at 1× InfiniBand bandwidth (200 Gbps).

- **Splitwise-HH:** both pools use DGX-H100s. This represents the homogeneous case using the latest GPUs. Prompt machines have 2.35× cost and 1.75× power relative to A100; token machines have 2.5× cost and 1.75× power (the slight cost difference reflects pricing). InfiniBand bandwidth is 2× (400 Gbps). This configuration provides the lowest latency but the highest cost.

- **Splitwise-HA:** prompt pool uses H100s (2.35× cost, 1.75× power), token pool uses A100s (1× cost, 1× power). InfiniBand bandwidth is the lower of the two at 1×. This configuration exploits the paper's Insight VII: A100s can be more cost- and power-efficient for token generation because the token phase is memory-bandwidth-bound and the A100's memory-to-compute ratio is more favorable. The prompt phase benefits from H100's 3.43× higher TFLOPS, while the token phase runs on cheaper hardware without significant latency penalty (Table IV shows TBT improves only 0.70× on H100 vs. A100).

- **Splitwise-HHcap:** both pools use H100s, but the token machines are **power-capped** to 70% of their rated power, with each GPU individually capped at 50% of its TDP (i.e., 350W out of 700W). The prompt machines run at full power (1.75× normalized, 700W per GPU), while the token machines run at 1.23× normalized power. InfiniBand bandwidth is 2×. This configuration exploits the paper's characterization in Figure 9: token generation latency is almost entirely insensitive to power capping—reducing the GPU power cap from 700W to 350W imposes negligible TBT impact—while prompt computation degrades sharply under power caps. By power-capping only the token machines, Splitwise-HHcap reduces total provisioned power without sacrificing performance.

**Optimization objectives.** The paper explores four cluster optimization scenarios, each with a different constraint-goal pairing:

- **Iso-power throughput-optimized:** Fix total provisioned power to that of 40 DGX-H100s (the Baseline-H100 cluster). Maximize throughput (requests per second at SLO compliance). This is attractive to CSPs facing power provisioning constraints.

- **Iso-cost throughput-optimized:** Fix total cluster cost to that of Baseline-H100. Maximize throughput. This is attractive to end-users who pay for GPU hours and want maximum performance per dollar.

- **Iso-throughput power-optimized:** Fix throughput to that of Baseline-H100. Minimize provisioned power. This is attractive to CSPs who need to meet a service-level throughput target while minimizing datacenter power infrastructure.

- **Iso-throughput cost-optimized:** Fix throughput to that of Baseline-H100. Minimize total cost. This is attractive to end-users who have a fixed throughput requirement and want to meet it as cheaply as possible.

**Design rationale.** The provisioning methodology is a direct instantiation of the paper's core thesis: because prompt and token phases have different resource profiles, the optimal ratio of prompt to token machines depends on the workload's input/output token distributions, the SLO targets, and the optimization objective. The grid search over (num_prompt, num_token) makes this tradeoff explicit and quantifiable. The four hardware configurations probe different points on the cost-power-performance Pareto frontier, with Splitwise-HA and Splitwise-HHcap representing the heterogeneous configurations that are only possible because Splitwise disaggregates the phases.

#### 3.4.5 Simulator Architecture and Fidelity

All cluster-level evaluations in the paper are conducted using SplitwiseSim, an event-driven simulator that faithfully models the Splitwise machine pools, schedulers, per-machine memory and queue state, and KV-cache transfer delays. The simulator is open-sourced alongside the paper.

**Simulator components.** Figure 13 diagrams the simulator's architecture, which has four major input categories feeding into a core simulation engine:

1. **Application inputs:** request traces (derived from production trace distributions with tunable Poisson arrival rates) and the model being served (Llama2-70B or BLOOM-176B).

2. **Orchestration inputs:** cluster specifications (number of machines, pool assignments, hardware types), scheduler configurations (policies for CLS and MLS), and KV-cache transfer parameters (bandwidth, transfer mode selection threshold).

3. **Performance models:** a piece-wise linear model built from hardware profiling that predicts TTFT and TBT given input size, output size, batch size, and hardware type. This model is validated to have MAPE < 3% on an 80:20 train:test split of profiling data.

4. **Hardware profiling data:** measured latencies and throughputs from the real hardware implementation of Splitwise on Azure VMs, collected across a range of batch sizes, input sizes, output sizes, and parallelism configurations. This data is used to build the performance models and validate the communication model.

**Validation methodology.** The paper validates the simulator at two levels:

- **Component-level validation:** the KV-cache transfer communication model is benchmarked against the real MSCCL++ implementation described in Section 3.4.2. The performance model is validated against held-out profiling data to ensure it accurately predicts TTFT and TBT at unseen batch size/input size combinations.

- **End-to-end validation:** the simulator is validated using a production load with over 50,000 iterations, comparing simulated latency distributions against the 1-machine baseline (where the real hardware results are available). This ensures the simulator's event-driven state management (queue evolution, batching decisions, memory tracking) is faithful to real system behavior.

**What the simulator outputs.** For each simulated cluster configuration and load level, the simulator produces per-request latency metrics (TTFT, TBT, E2E at P50, P90, P99), machine utilization levels (time spent at various batch sizes, queue depths), and the fraction of time machines spend in different pools (for Splitwise configurations). These outputs are compared against the nine SLO thresholds to determine whether the configuration is valid at a given load.

**Design rationale.** The simulator is necessary because exploring the full design space of cluster configurations (machine counts, hardware types, pool ratios) under realistic production loads is infeasible on real hardware—it would require physically provisioning dozens of DGX machines and running them at scale. The event-driven approach is appropriate because LLM inference is dominated by well-defined forward-pass latencies (which the performance model captures) and queue dynamics (which the event-driven simulation captures), with relatively little stochastic variation beyond the input/output size distributions. The three-tier validation (component, performance model, end-to-end) provides confidence that the simulator's conclusions transfer to real deployments.

## 4. Key Insights and Innovations

### Innovation 1: Phase Disaggregation as a First-Class Resource Management Primitive for LLM Inference

The paper's most fundamental contribution is not the specific scheduling policy or the KV-cache transfer optimization—it is the **conceptual reframing of LLM inference from a monolithic computation to two independently provisionable stages with distinct resource signatures**. Before Splitwise, the field treated LLM inference as an atomic unit: a request arrives, a machine processes it through all forward passes, and the response is returned. Batching mechanisms (Orca's continuous batching, SARATHI's mixed batching) and memory optimizations (PagedAttention) improved efficiency within this paradigm, but they accepted the premise that prompt and token phases must co-reside on the same GPU. This premise was so deeply embedded that the paper's own baselines—mixed continuous batching on DGX-H100s—represent the state of the art in production systems.

The insight that breaks this premise is that the two phases are **not merely different stages of the same computation, but fundamentally different computational workloads** with different resource bottlenecks, different hardware affinities, and different sensitivity to power management. The prompt phase is a compute-bound, power-hungry, batch-size-sensitive operation that benefits from the latest high-FLOPs GPUs. The token phase is a memory-bandwidth-bound, power-insensitive, batch-size-insensitive (for latency) operation that could run efficiently on older GPUs with better memory-to-compute ratios, or on the same GPUs with aggressive power capping. The paper's characterization makes this distinction quantitative and actionable: Figure 5b shows TBT growing only 2× as batch size scales from 1 to 64; Figure 8b shows token power draw flat and well below TDP regardless of batch size; Figure 9b shows TBT unaffected by a 50% power cap; Table IV shows TBT improving only 0.70× from A100 to H100 while TTFT improves 0.51–0.54×.

The intellectual move is to treat these phases as **independently schedulable, independently provisionable computational stages**—analogous to how database systems separate query processing from storage, or how microservice architectures decompose monolithic applications into independently scalable services. The KV-cache transfer mechanism is the enabler that makes this disaggregation physically possible, but the conceptual contribution is the recognition that disaggregation is *desirable* in the first place.

This is a fundamental shift rather than an incremental optimization. Prior work (Orca, vLLM, SARATHI) improved scheduling *within* a machine; Splitwise changes the unit of resource allocation from the machine to the phase. It opens a design space that simply did not exist before: prompt and token machines can be different hardware generations, different GPU types, different power caps, different counts—each independently optimized for its phase's resource profile. The paper's four hardware configurations (AA, HH, HA, HHcap) are the first exploration of this space, but the framework extends naturally to any hardware that aligns with the computational requirements of each phase, as the paper explicitly notes in Section VII.

The significance extends beyond the immediate throughput and cost gains (1.4× throughput at 20% lower cost, 2.35× throughput at the same cost and power). It establishes that **LLM inference clusters are not a single resource pool but a two-stage pipeline with different economics at each stage**, and that the optimal hardware for each stage diverges as GPU generations continue to scale compute and memory asymmetrically. This is a diagnostic insight with implications for datacenter procurement, hardware roadmap planning, and the broader trajectory of LLM serving infrastructure.

### Innovation 2: KV-Cache Transfer as a Solved Problem, Not a Showstopper

A necessary precondition for phase disaggregation is the ability to transfer the intermediate attention state between machines without unacceptable latency overhead. The seemingly obvious objection to Splitwise is that the KV-cache is large—proportional to `L × N × H` for L layers, N prompt tokens, and H hidden dimensions—and that transferring it over the network would add prohibitive latency to the token generation critical path. The paper's second key contribution is demonstrating that this objection does not hold in modern GPU clusters: **with layer-wise asynchronous pipelining over existing InfiniBand interconnects, the KV-cache transfer overhead is negligible** (under 1% of end-to-end latency, Figure 15).

What makes this result intellectually significant is not the engineering of the transfer itself (the paper uses MSCCL++ one-sided puts with semaphore-based synchronization, a standard high-performance communication pattern), but the **empirical demonstration that the transfer is not the bottleneck the field implicitly assumed it to be**. Prior work on GPU cluster networking focused on training workloads, where gradient synchronization requires high bandwidth but is not on the critical path for individual forward passes. The paper shows that the same InfiniBand backplane present in production GPU clusters (200 Gbps on A100, 400 Gbps on H100) is sufficient to hide KV-cache transfer behind prompt computation for all but the last layer, reducing the visible overhead to a small constant (roughly 8ms on A100, 5ms on H100) independent of prompt size (Figure 14).

This is a **negative result with positive implications**: the paper does not invent a new compression technique or a novel network protocol; it shows that the straightforward approach works well enough that the field should not treat KV-cache transfer as a barrier to disaggregation. The layer-wise transfer exploits a property of the transformer architecture—that each attention layer produces its KV-cache independently and the cache is not modified by subsequent layers—that is obvious in retrospect but was not previously used to enable phase disaggregation. The threshold-based mode selection (serialized for small prompts, per-layer for large) avoids the interference overhead of fine-grained synchronization when the total transfer size is small enough that serialized latency is already acceptable.

This finding has implications beyond Splitwise. It suggests that KV-cache transfer between machines is feasible for other use cases: speculative decoding across machines, KV-cache offloading to remote memory for long-context requests, or multi-stage inference pipelines where intermediate attention states need to flow between specialized processors. The demonstration that the per-layer transfer overhead is a constant, not a function of prompt size, means the technique scales gracefully to the increasingly long contexts that modern LLMs support.

### Innovation 3: Power-Aware Phase Management as a Third Optimization Axis

The paper introduces a third optimization dimension—provisioned power—alongside the traditional metrics of throughput and cost, and shows that phase disaggregation enables power savings that homogeneous deployments cannot achieve. This is **not simply an engineering optimization but a reframing of the CSP's resource allocation problem**: power provisioning, not just GPU count or GPU cost, is the binding constraint for datacenter expansion, and Splitwise's phase separation enables power to be managed asymmetrically across phases.

The key diagnostic result is Figure 9's demonstration that prompt and token phases have **radically different sensitivity to power capping**. Reducing the GPU power cap from 700W to 350W (a 50% reduction) causes prompt latency to degrade sharply—TTFT increases substantially because the compute-bound phase needs the full power budget to maintain clock speeds and throughput. But the same power cap has essentially no impact on token generation latency—TBT remains flat because the memory-bandwidth-bound phase is not using the power-hungry compute units in the first place. The GPU's power control mechanisms (dynamic voltage and frequency scaling) can throttle compute without affecting memory bandwidth, which is what the token phase actually needs.

This observation is not obvious from architectural specifications alone. One might assume that a 50% power cap would proportionally affect all workloads, or that the effect would be unpredictable. The paper's characterization provides the empirical evidence that it is not—it is highly phase-dependent—and this creates an optimization opportunity that homogeneous deployments cannot exploit. In a monolithic deployment running both phases on the same GPU, the power cap must be set to accommodate the prompt phase's sensitivity, meaning the token phase wastes provisioned power capacity it never uses. Splitwise separates the phases, allowing token machines to be power-capped aggressively while prompt machines run at full TDP.

This insight is amplified by the industry trend documented in Table I: each new GPU generation increases power consumption faster than memory bandwidth (the H100 draws 1.75× more power than the A100 but delivers only 1.64× more memory bandwidth). This means the power waste from running token generation on the latest GPUs is **increasing over time**, making power-aware phase management more valuable with each hardware generation. The Splitwise-HHcap configuration—which power-caps token machines to 70% of rated power while running prompt machines at full power—achieves the same throughput as Baseline-H100 at 25% lower power (Figure 19a). This is a direct monetization of the phase-dependent power sensitivity: the CSP can deploy more GPUs in the same power envelope, or reduce datacenter power infrastructure costs, without sacrificing performance.

This contribution connects to the broader trend of power-constrained computing in datacenters, where power availability increasingly limits growth. The paper's explicit framing of power as a "wall" that CSPs are running into (Section I) positions power-aware phase management not as a niche optimization but as a **necessary strategy for sustainable scaling of LLM inference**. The methodology—characterize phase-specific power sensitivity, disaggregate phases, and apply asymmetric power caps—generalizes to any workload with heterogeneous power sensitivity across computational stages.

### Innovation 4: Workload-Aware Cluster Provisioning via Phase Ratio Search

The paper formalizes a methodology for provisioning LLM inference clusters that explicitly optimizes the **ratio of prompt to token machines** given workload characteristics, SLO constraints, and an optimization objective. This is a departure from both the homogeneous provisioning of monolithic clusters (where every machine is identical and the concept of a prompt-to-token ratio does not exist) and from simple heuristic approaches that might allocate machines proportionally to the expected time spent in each phase.

The insight is that the optimal prompt-to-token ratio depends on **three interacting factors**: (1) the workload's input/output token distribution, which determines the relative demand for prompt computation versus token generation; (2) the SLO constraints, which determine how aggressively each phase can be batched; and (3) the hardware characteristics of each pool, which determine the throughput per machine for each phase. The paper demonstrates that this ratio varies substantially across workloads and optimization objectives: the cost-optimal Splitwise-HH configuration for the coding workload uses 27 prompt and 3 token machines (a 9:1 ratio, Figure 12) because the coding trace has very few output tokens (median 13), while the conversation workload provisions 25 prompt and 15 token machines (a 1.67:1 ratio, Figure 16b legend) because conversation requests generate many more output tokens (median 129).

This is not a trivial consequence of the workload statistics—it requires the provisioning search framework to jointly optimize over machine counts while respecting SLO constraints on all nine latency percentiles. The paper's approach of grid-searching the two-dimensional (num_prompt, num_token) space with a validated simulator, filtering configurations that violate any SLO, and selecting the optimum under the specified constraint provides a **reproducible methodology** that does not depend on hand-tuned heuristics or simplifying assumptions about phase behavior under load.

The significance of this contribution is that it converts Splitwise from a fixed deployment pattern into a **provisioning methodology applicable to any LLM, any workload, and any hardware pairing**. A CSP deploying a new model or serving a new application can profile the model on candidate hardware, characterize the workload's token distributions, define SLOs, and use the framework to determine the optimal cluster composition. The paper's robustness experiments (Section VI-D) show that clusters provisioned for one workload gracefully handle another—Splitwise's mixed pool and dynamic scheduling compensate for mismatches—but the methodology ensures that the provisioning is optimized for the expected case.

This contribution also surface an important tradeoff: the prompt-to-token ratio is a design parameter that encodes assumptions about the workload. A cluster optimized for a conversation service (token-heavy) will have more token machines and fewer prompt machines than a cluster optimized for a code completion service (prompt-heavy). In a multi-tenant environment serving diverse workloads, the provisioning must either target the aggregate workload distribution or use a conservative ratio that leaves capacity for both phases. The paper's mixed pool mechanism provides a partial solution by allowing machines to overflow into the opposite phase when needed, but the fundamental provisioning choice remains workload-dependent. This is not a weakness but a clarification of the design space: just as pretraining scaling laws require assumptions about data quality and compute budget, inference cluster provisioning requires assumptions about the request distribution.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper uses production traces from two Azure LLM inference services collected on November 11th, 2023—one for coding and one for conversation. Each trace is 20 minutes long and contains arrival time, input size (number of prompt tokens), and output size (number of generated tokens) for each request. The actual text content of prompts is not available due to customer privacy requirements (GDPR), so the authors use the traces to guide input/output sizes and send prompts with the required token counts, forcing the model to generate the corresponding number of output tokens. A subset of the traces has been released at https://github.com/Azure/AzurePublicDataset. The input prompt distribution has a median of 1500 tokens for coding and 1020 tokens for conversation (Figure 3a); the generated output token distribution has a median of 13 tokens for coding (typically code completions as the user types) and 129 tokens for conversation, with a roughly bimodal distribution (Figure 3b). For cluster-scale experiments, the traces are used to drive a Poisson arrival process with tunable request rate; for KV-cache transfer experiments, the coding trace is run without batching on 2-machine setups.

- **Base model(s).** The paper evaluates two state-of-the-art open-source decoder-only transformer models: **Llama2-70B** (80 layers, hidden size 8192, 32 attention heads) and **BLOOM-176B** (70 layers, hidden size 14336, 112 attention heads). Both are described as representative of production-class accuracy in their parameter classes (Table III). All characterization data (Section III) is collected on a machine with 8 H100 GPUs running vLLM, though some experiments compare A100 vs. H100 hardware. The paper argues that Llama2-70B is the more deployment-relevant model, while including BLOOM-176B demonstrates applicability to larger architectures.

- **Metrics.** The paper defines and measures four primary metrics (Table II): **Time to First Token (TTFT)**—how quickly the user sees the initial response; **Time Between Tokens (TBT)**—the average latency between consecutive tokens during streaming generation; **End-to-End (E2E) latency**—total query time from request arrival to completion of all output tokens; and **Throughput**—requests per second that can be served while meeting SLOs. For prompt and token phases separately, throughput is also measured in tokens processed or generated per second (Figure 6). The SLO framework (Table VI) defines latency thresholds as slowdown multiples relative to a request running on a DGX-A100 under no contention: at P50, P90, and P99, TTFT must not exceed 2×, 3×, and 6× slowdown; TBT and E2E must not exceed 1.25×, 1.5×, and 5× slowdown. All nine SLO thresholds must be met for a cluster configuration to be considered valid. For batch job evaluation, throughput per dollar (RPS/$) is computed.

- **Baselines.** The paper compares against **Baseline-A100** and **Baseline-H100**—clusters consisting entirely of DGX-A100s or DGX-H100s, respectively, all using mixed continuous batching (the state-of-the-art strategy described in Section II-D where prompt and token phases can interleave in the same batch). No prior system (Orca, vLLM, SARATHI) is used as a separately named baseline; instead, the mixed continuous batching implementation subsumes the best practices from these systems.

- **Generation budget / compute accounting.** The paper does not measure a "generation budget" in the sense of controlling the number of sampled solutions. Instead, compute is accounted through **cluster provisioning**: for a given constraint (fixed total power, fixed total cost, or fixed peak throughput), the number and type of machines (each with 8 GPUs, known cost per hour from cloud pricing, known TDP) are varied, and throughput is measured as the maximum requests per second (RPS) at which all nine SLO thresholds are met. The iso-power, iso-cost, and iso-throughput constraints are therefore the "budgets." For KV-cache transfer experiments where batching is not used, the computation is the trace itself. The paper normalizes cluster costs and power to DGX-A100 units: an A100 machine is 1× cost and 1× power; an H100 prompt machine is 2.35× cost and 1.75× power; an H100 token machine is 2.5× cost and 1.75× power; a power-capped H100 token machine is 2.5× cost and 1.23× power (Table V and associated calculation). All InfiniBand bandwidths are normalized to the DGX-A100's 200 Gbps per GPU pair.

- **Cross-validation / statistical protocol.** The paper does not use cross-validation in the machine-learning sense. Instead, it validates the simulator at two levels: component-level (the KV-cache transfer model is benchmarked against the real MSCCL++ implementation; the performance model is validated on an 80:20 train:test split of profiling data, achieving MAPE under 3%); and end-to-end (the simulator is validated using a production load with over 50,000 iterations against hardware measurements). The cluster provisioning search is deterministic: for each (num_prompt, num_token) configuration, the simulator runs the trace at a given arrival rate and outputs latency percentiles. Configurations failing any SLO at the target load are discarded. The paper does not report confidence intervals or variance estimates for latency percentiles, nor does it discuss statistical significance of the throughput differences between configurations.

### Main Quantitative Results

The evaluation is organized around four cluster optimization scenarios: iso-power throughput-optimized (Section VI-B), iso-cost throughput-optimized, iso-throughput power-optimized, and iso-throughput cost-optimized (Section VI-C). Each scenario compares the four Splitwise configurations (AA, HH, HA, HHcap) against the two baselines (Baseline-A100, Baseline-H100). The paper then evaluates robustness to workload changes (Section VI-D) and batch job performance (Section VI-E).

---

#### KV-Cache Transfer Latency and End-to-End Impact

Before cluster-scale results, the paper validates the core enabling mechanism: the KV-cache transfer between prompt and token machines. These experiments run on real hardware (two DGX-A100 VMs and two DGX-H100 VMs on Azure, connected with InfiniBand at 200 Gbps and 400 Gbps respectively) without batching, using the coding trace.

**Transfer latency vs. prompt size (Figure 14).** The visible transfer latency—the time during which the token machine cannot begin generation because it is waiting for KV-cache data—is measured as a function of batched token size. With serialized transfer (transfer everything after prompt completion), latency grows roughly linearly with prompt size: from approximately 8ms for small prompts to approximately 35ms for 2048 tokens on A100s; roughly half those values on H100s due to the doubled InfiniBand bandwidth. With per-layer transfer (asynchronously sending each layer's KV-cache while subsequent layers compute), the visible overhead drops to a small constant: approximately 8ms on A100 and 5ms on H100, independent of prompt size. The H100's doubled bandwidth produces roughly 2× faster transfers than A100 at all sizes. The mode-selection threshold (serialized for small prompts, per-layer for large) is 512 tokens on H100.

**End-to-end latency impact (Figure 15).** Comparing the 2-machine Splitwise setup (one prompt machine, one token machine) to a 1-machine baseline where both phases run on the same machine:

- **TTFT impact:** Splitwise adds negligible TTFT overhead for per-layer transfer (the green and blue TTFT lines overlap) because prompt computation itself is unchanged. The TTFT for Splitwise with per-layer transfer tracks the 1-machine baseline identically.
- **E2E impact:** With serialized transfer, E2E latency increases by up to 3% for large prompts. With per-layer transfer (Splitwise's default for large prompts), E2E increases by only 0.8% over the baseline.
- **Second-token latency:** The most user-visible impact is on the latency between the first and second output tokens (the first token after prompt computation, whose generation must wait for KV-cache transfer to complete). Serialized transfer adds a 64% overhead to this specific token's latency; per-layer transfer reduces this to 16.5%. The paper notes this is "hardly perceivable even in a user-facing inference" because it affects only a single token.

These results establish that KV-cache transfer is not a showstopper for phase disaggregation—the overhead is under 1% of E2E latency in the optimized configuration, and the 16.5% single-token impact is acceptable for streaming applications.

---

#### Iso-Power Throughput-Optimized Clusters

This is the paper's primary evaluation scenario (Section VI-B). The constraint is that total provisioned power equals that of 40 DGX-H100 machines. All cluster configurations must fit within this power envelope. The optimization objective is maximum throughput (RPS) at SLO compliance.

**Provisioning outcomes.** Under the coding trace (Figure 16a legend): Baseline-H100 provisions 40 machines (all mixed batching). Baseline-A100 provisions 70 machines (75% more machines because A100s use 1× power vs. H100's 1.75×, so 70 A100s ≈ 40 H100s in total power). Splitwise configurations: Splitwise-AA provisions 55 prompt + 15 token = 70 total A100s; Splitwise-HH provisions 35 prompt + 5 token = 40 total H100s; Splitwise-HA provisions 35 prompt (H100) + 8 token (A100); Splitwise-HHcap provisions 35 prompt (full-power H100) + 7 token (power-capped H100, 1.23× normalized power). Note that the number of token machines is small for coding because the median output is only 13 tokens—each token machine can handle many concurrent generation requests.

Under the conversation trace (Figure 16b legend): Baseline provisioning is the same (40 H100s, 70 A100s at iso-power). Splitwise-HH provisions 25 prompt + 15 token = 40 total H100s—substantially more token machines than coding, reflecting conversation's longer generation sequences (median 129 tokens). Splitwise-AA provisions 45 prompt + 25 token = 70 total A100s. Splitwise-HA provisions 25 prompt (H100) + 26 token (A100). Splitwise-HHcap provisions 25 prompt (full-power H100) + 21 token (power-capped H100).

**Throughput at SLO compliance (Figure 16, dashed red lines mark SLOs).** For the **coding trace** (Figure 16a):

- **Baseline-H100** achieves approximately 70 RPS before SLO violations begin. As load increases beyond this point, P50, P90, and P99 TBT all degrade sharply—this is the mixed batching interference effect: large prompt computations in mixed batches increase the latency of token generation steps, inflating TBT. P50 TBT roughly doubles between 70 and 90 RPS.
- **Splitwise-HH** achieves approximately 90 RPS—approximately 1.29× higher throughput than Baseline-H100—while maintaining lower TBT across all load levels. The P99 TBT remains flat at roughly 2× normalized across the entire 30–110 RPS range, while Baseline-H100's P99 TBT spikes at 80 RPS.
- **Splitwise-HHcap** closely tracks Splitwise-HH in throughput (also roughly 90 RPS), with slightly higher P90 E2E at very high loads. This demonstrates that power capping the token machines imposes no meaningful throughput penalty.
- **Splitwise-AA** achieves approximately 85 RPS (higher than Baseline-H100's 70 RPS, lower than Splitwise-HH's 90 RPS) but with consistently higher TTFT—the A100's lower compute capability increases prompt computation latency across all loads.
- **Splitwise-HA** achieves the highest throughput among all configurations—approximately 100 RPS, or 1.43× Baseline-H100—while maintaining TTFT competitive with Splitwise-HH (H100 prompt machines ensure fast prompt computation) and low TBT. The P50 TBT chart shows a distinctive pattern: TBT is flat from 30 to roughly 90 RPS, then dips slightly as the mixed pool activates (H100 machines from the prompt pool start handling token overflow). The paper notes this mixed pool benefit explicitly: "after 90 RPS, H100 machines jump into the mixed machine pool and help reduce TBT."

For the **conversation trace** (Figure 16b):

- **Baseline-H100** achieves approximately 90 RPS before SLO violations. The degradation pattern differs from coding: P50 TTFT and TBT both rise steadily from low loads, reflecting conversation's wider distribution of prompt sizes and longer output sequences.
- **Baseline-A100** tracks Baseline-H100 in throughput but at consistently higher TTFT and E2E (the A100's compute deficit is more visible in conversation due to prompt diversity).
- **Splitwise-HH** achieves roughly 110 RPS—approximately 1.22× Baseline-H100.
- **Splitwise-HHcap** achieves the highest throughput—approximately 115 RPS, or 1.28× Baseline-H100—and shows the most favorable latency profile at high loads, with P90 TTFT remaining below the SLO threshold even at 120 RPS where Baseline-H100 has already violated. The paper attributes this to conversation's longer token generation phases making the power-capped token machines particularly effective, since their power savings translate to more machines in the token pool (21 vs. 15 for Splitwise-HH non-capped) under the same power budget.
- **Splitwise-HA** and Splitwise-AA achieve roughly 105 and 100 RPS respectively, both outperforming Baseline-H100.

**Impact on batched tokens (Figure 17).** This analysis examines why Splitwise improves throughput by looking at the distribution of time spent at various batch sizes, using the conversation trace at low load (70 RPS) and high load (130 RPS):

- **At low load (70 RPS, Figure 17a):** Baseline-H100's 40 machines spend roughly 70% of the time running 15 or fewer active tokens (y-axis from 0 to ~0.7 cumulative duration at x ≈ 15). The remaining time is spent on mixed batches containing large prompts up to ~3000 tokens, which inflate TBT for all requests sharing the batch. Splitwise-HH's 35 prompt machines are mostly idle (the CDF for prompt machines at low batch sizes is near 1.0, indicating they spend most time at zero load), and when active, process much larger batches (the curve shifts right, reaching batch sizes over 1000 tokens at high cumulative duration). The 15 token machines spend the vast majority of time at batch sizes of 10–100 tokens—substantially better batching than Baseline-H100's tail of single-token processing. Overall, Splitwise machines exhibit better batching and consequently lower latency.
- **At high load (130 RPS, Figure 17b):** The distributions converge somewhat because the mixed pool is utilized more heavily, causing prompt and token machines to both process mixed batches. However, Splitwise's prompt machines still process predominantly large prompt batches (right-shifted curve), while token machines handle predominantly large token batches, maintaining better phase separation than Baseline-H100.

**Summary plot (Figure 18a).** The paper normalizes all configurations against Baseline-A100 (which gets 1.0 for #Servers, Throughput, and Cost). Key ratios:

- Baseline-H100 achieves 0.98× the throughput of Baseline-A100 at 2.35× cost (2.35 in the normalized cost column) and 1.75× power. It uses fewer servers (40 vs. 70) but at much higher per-server cost.
- Splitwise-AA achieves 2.15× throughput at the same cost (1.0) and same power (1.0) as Baseline-A100—a purely efficiency gain from phase separation without hardware heterogeneity.
- Splitwise-HH achieves 1.76× throughput at 2.02× cost (slightly less expensive than Baseline-H100 at 2.35× cost), with 1.87× power—the cost represents the weighted average of prompt and token machine costs.
- Splitwise-HA achieves 1.18× throughput at 0.90× cost (10% cheaper than Baseline-A100) and same power as Baseline-A100. This is the only configuration that both improves throughput and reduces cost simultaneously under the iso-power constraint.
- Splitwise-HHcap achieves 1.82× throughput at 2.11× cost and 1.25× power—higher throughput than Splitwise-HH under the same power budget because power-capping token machines frees power headroom for additional machines.

The paper's headline claim from the abstract—"1.4× higher throughput at 20% lower cost"—is not directly from this iso-power scenario. That claim comes from the iso-cost scenario (Section VI-C and Figure 18b) rather than the iso-power scenario.

#### Iso-Cost Throughput-Optimized Clusters

This scenario fixes total cluster cost to that of Baseline-H100 (40 DGX-H100 machines). Under this budget, Baseline-A100 provisions 86 machines (since A100s cost 1/2.35 ≈ 0.425× as much as H100s, roughly 86 A100s can be purchased for the cost of 40 H100s).

**Provisioning (Figure 18b legend):** Baseline-A100 gets 86 machines. Baseline-H100 gets 40. Splitwise-AA: 51 prompt + 35 token A100s (86 total). Splitwise-HH: 25 prompt + 15 token H100s (40 total—same as the iso-power configuration since H100 prompt and token machines have similar costs). Splitwise-HA: 30 prompt H100s + 21 token A100s. Splitwise-HHcap: 30 prompt H100s + 10 token (power-capped) H100s.

**Throughput and power summary (Figure 18b), normalized to Baseline-A100:**

- Baseline-H100 achieves 0.57× throughput of Baseline-A100 at 1.0× cost (by construction, costs are equalized) and 0.65× power—fewer servers at lower total power but substantially lower throughput.
- Splitwise-AA achieves 1.40× throughput at the same cost (1.0) and 1.25× power—this is the headline "1.4× higher throughput at 20% lower cost" claim, though the figure shows same cost, not lower cost. The 20% lower cost claim likely refers to achieving the *same* throughput as Baseline-H100 at 20% lower cost, which appears in the iso-throughput cost-optimized scenario (Figure 19b) rather than here.
- Splitwise-HH achieves 1.0× throughput (same as Baseline-A100) at 1.0× cost and 0.53× power—fewer machines but at higher per-machine cost.
- Splitwise-HA achieves 0.72× throughput at 0.72× cost and 0.61× power—less throughput than Baseline-A100 but proportionally lower cost.
- Splitwise-HHcap achieves 0.70× throughput at 0.75× cost and 0.38× power—the lowest power draw among all configurations.

The paper highlights Splitwise-AA as the winner for cost-conscious users: "Splitwise-AA provides the best throughput for the same cost, namely 1.4× more throughput than Baseline-H100, running at 25% more power, and 2× the space. This is an interesting operational point for most customers who may not care about power and space, instead preferring the 40% higher throughput using older, more easily available GPUs."

Wait—the paper says "1.4× more throughput than Baseline-H100" but Figure 18b shows Splitwise-AA normalized to Baseline-A100 at 1.4, and Baseline-H100 normalized to Baseline-A100 at 0.57. So Splitwise-AA's throughput relative to Baseline-H100 is 1.4/0.57 ≈ 2.46×. This is inconsistent with the text. The most consistent interpretation is that the "1.4×" refers to throughput relative to Baseline-A100 (which is itself 1/0.57 ≈ 1.75× Baseline-H100's throughput), meaning Splitwise-AA achieves roughly 1.4 × 1.75 ≈ 2.45× Baseline-H100's throughput under the same cost. The paper's text description likely mixed reference baselines; the quantitative claim in the abstract of "1.4× higher throughput at 20% lower cost" properly belongs to the iso-throughput cost-optimized scenario (Figure 19b), not this one.

#### Iso-Throughput Power-Optimized and Cost-Optimized Clusters

These scenarios fix throughput to the level achieved by Baseline-H100 and minimize either power or cost (Section VI-C, Figures 19a and 19b). Note that the conversation trace and the BLOOM-176B model are used for these experiments; the Baseline-H100 target throughput varies by workload.

**Iso-throughput power-optimized (Figure 19a), normalized to Baseline-A100:**

- Baseline-H100 requires 24 machines, normalizing to 0.34 for #Servers, 0.57 for cost, and 0.60 for power—the 24 machines reflect the throughput target.
- Baseline-A100 requires 88 machines (a large cluster to match H100 throughput).
- Splitwise-AA: 25 prompt + 16 token A100s, at 0.47 cost and 0.47 power—substantially lower cost and power than Baseline-A100 for the same throughput.
- Splitwise-HH: 5 prompt + 17 token H100s, at 0.55 cost and 0.48 power—fewer machines, similar power to Splitwise-AA, higher cost.
- Splitwise-HA: 21 prompt H100s + 1 token A100—only one token machine needed! This reflects conversation's workload characteristics and the A100's effectiveness for token generation; cost is 0.55, power is 0.40.
- **Splitwise-HHcap: 8 prompt + 16 token (power-capped) H100s, at 0.57 cost and 0.25 power**—the lowest power of any configuration. This is the paper's headline for power optimization: "Splitwise-HHcap can achieve the same throughput as Baseline-H100 at 25% lower power at the same cost and space." The claim is consistent: Splitwise-HHcap power (0.25 × Baseline-A100 power, which is normalized to 1.0) equals 0.25, while Baseline-H100 power is 0.60 for 24 machines. 0.25/0.60 ≈ 0.42, meaning Splitwise-HHcap uses roughly 42% of Baseline-H100's power—a more dramatic reduction than 25% lower. The paper's stated "25% lower power" likely uses a different normalization.

**Iso-throughput cost-optimized (Figure 19b):** The provisioning for homogeneous configurations (Baseline-A100, Baseline-H100, Splitwise-AA, Splitwise-HH) remains identical to the power-optimized case because prompt and token machines have the same cost and power in homogeneous setups. Splitwise-HA and Splitwise-HHcap shift their provisioning to optimize for cost rather than power:

- Splitwise-HA: 11 prompt H100s + 19 token A100s, at 0.40 cost (down from 0.55 in the power-optimized version) and 0.40 power—more token A100s (cheaper per machine) and fewer prompt H100s, reducing cost while maintaining throughput.
- Splitwise-HHcap: 19 prompt (full power) H100s + 3 token (power-capped) H100s, at 0.49 cost and 0.37 power—shifted toward more prompt machines and fewer token machines compared to the power-optimized version, since power-capped token machines are cost-equivalent to full-power H100s but the cost optimization reduces their count.
- **The paper highlights Splitwise-AA: 25 prompt + 16 token A100s at 0.47 cost**—"customers can achieve the same throughput as Baseline-H100 at 25% lower cost." This claim from the paper text (Section VI-C) is matched to Figure 19b: Baseline-H100 cost is 0.57 (normalized), Splitwise-AA cost is 0.47, which is roughly 18% lower, not 25%. A precise "25% lower" would require Splitwise-AA cost to be 0.43 relative to Baseline-H100's 0.57. The numbers in the paper's text and figures have some inconsistency in the stated percentages likely due to rounding or to using different baseline reference points (the abstract claims "1.4× higher throughput at 20% lower cost"—similar approximate relationships).

#### Robustness to Workload Changes

The paper evaluates whether Splitwise clusters provisioned for one workload can handle a different workload without re-provisioning (Section VI-D, Figure 20). The specific test: run the **conversation trace** on clusters that were provisioned for the **coding trace** (Figure 20a), and run **Llama-70B** on a cluster provisioned for **BLOOM-176B** (Figure 20b). Both use iso-power throughput-optimized provisioning.

**Workload trace change (Figure 20a).** The cluster configurations from Figure 16a (coding-optimized) are now tested with the conversation trace:

- Baseline-A100 (70 machines) and Baseline-H100 (40 machines) are identically sized regardless of workload, so they show no change in capacity. Their throughput under the conversation trace matches the earlier conversation results (Figure 16b).
- Splitwise-AA (55 prompt, 15 token, provisioned for coding) and Splitwise-HH (35 prompt, 5 token) use the mixed pool to accommodate the conversation workload's heavier token demand. The paper reports they "morph well" and "see no throughput or latency impact"—the P90 TTFT, TBT, and E2E curves largely overlap with their conversation-optimized counterparts from Figure 16b.
- Splitwise-HA (35 prompt H100s, 8 token A100s) and Splitwise-HHcap (35 prompt H100s, 7 token H100s) experience a throughput setback: each achieves approximately **7% lower throughput** than a cluster optimized specifically for the conversation workload. The paper attributes this to their "different types of machines in the prompt and token pools" making them less flexible when the workload mix shifts. However, even with the 7% penalty, these configurations still outperform both baselines.

**Model change (Figure 20b).** The cluster configurations from Figure 16b (conversation, BLOOM-176B) are tested with Llama-70B, which has fewer parameters (70B vs. 176B) and thus higher throughput on the same hardware:

- All configurations achieve substantially higher throughput than with BLOOM-176B: Baseline-H100 goes from roughly 90 RPS to roughly 190 RPS; Splitwise configurations scale proportionally. The paper notes that "Llama-70B can support much higher throughput in the same cluster design than BLOOM-176B, given its fewer parameters."
- Splitwise-HH and Splitwise-HHcap "consistently achieve the best latency, even as the load increases" with P90 TTFT, TBT, and E2E remaining near 1.0–1.5× normalized even at 250 RPS where Baseline-H100 and Baseline-A100 exhibit rising P90 latencies. All Splitwise designs outperform both baselines at higher loads.

**Robustness conclusion.** The paper concludes that "Splitwise can morph according to the requirements of the workload using its smart scheduling, and it is robust to changes in the LLMs, request load, and token distributions." The key mechanism is the mixed pool: machines in the prompt or token pool can be temporarily repurposed when the workload mix shifts from the provisioning assumptions. The 7% throughput penalty for heterogeneous configurations under workload shift is acknowledged but presented as acceptable given that these configurations still outperform baselines.

#### Batch Job Performance

For batch jobs where latency SLOs are irrelevant (Section VI-E), the paper stresses the iso-power throughput-optimized clusters by increasing load beyond SLO compliance limits to find the maximum token generation throughput:

- At high load, Splitwise configurations devolve into the iso-count Baseline behavior because all machines enter the mixed pool and use mixed continuous batching everywhere.
- Splitwise-AA and Baseline-A100 achieve **0.89 RPS/$**—the best throughput per dollar.
- Splitwise-HH and Baseline-H100 achieve **0.75 RPS/$**.

The paper notes this result is expected: when latency SLOs are removed, the phase separation benefit is neutralized because machines are no longer constrained by phase interference, and the cost savings from heterogeneous hardware (which Splitwise enables) become the main differentiator.

### Ablation Studies and Robustness Checks

The paper does not present traditional ablation studies where components of Splitwise are removed and performance is re-measured. Instead, the robustness checks are the workload and model substitution experiments (Section VI-D), which test whether Splitwise clusters are overfit to specific provisioning assumptions. These are the closest analogues to ablation:

- **Workload trace substitution**: Clusters provisioned for coding serve conversation traffic and vice versa. The result is that homogeneous Splitwise configurations (AA, HH) incur no throughput penalty; heterogeneous configurations (HA, HHcap) incur a 7% throughput penalty (Figure 20a, not a specific data point but described in text as "a throughput setback of 7% from the respective cluster optimized designs for conversation trace").

- **Model substitution**: Clusters provisioned for BLOOM-176B serve Llama-70B. All configurations handle the substitution without failure; Splitwise designs maintain their throughput advantage over baselines (Figure 20b).

- **Transfer mode selection threshold**: The paper implicitly ablates the per-layer vs. serialized transfer choice by measuring both in Figure 14. The constant overhead of per-layer transfer (roughly 8ms A100, 5ms H100) versus the linear growth of serialized transfer demonstrates the benefit. The threshold of 512 tokens for H100 is stated but not varied in experiments.

- **Power cap sensitivity**: The paper's Figure 9 shows the effect of varying power caps on prompt and token latency, establishing the justification for Splitwise-HHcap but not evaluating intermediate cap levels (e.g., 60%, 70%, 80%) in cluster simulations. Only the 50%-per-GPU (70% total machine power) cap is evaluated.

- **Batch size limits**: The 2048-token prompt batch limit is justified by Figure 6a but its sensitivity is not evaluated. Alternative limits (1024, 4096) are not tested in simulation.

### Critical Assessment

#### Do the Experiments Support the Central Claims?

**Claim 1: "Splitwise clusters achieve up to 1.4× higher throughput at 20% lower cost."** This claim appears in the abstract and conclusion but is inconsistently matched to specific figures. The closest evidence is the iso-throughput cost-optimized scenario (Figure 19b), where Splitwise-AA achieves the same throughput as Baseline-H100 at a normalized cost of 0.47 versus Baseline-H100's 0.57—a cost reduction of roughly 18%, not 20%. The iso-cost throughput-optimized scenario (Figure 18b) shows Splitwise-AA achieving 1.4× throughput (normalized to Baseline-A100) at the same cost—not lower cost. The paper's text mixes these two scenarios in the headline claim. The experiments do demonstrate substantial throughput gains or cost savings under Splitwise, but the precise "1.4× throughput at 20% lower cost" combination does not appear cleanly in any single figure. The claim is **qualitatively supported but quantitatively imprecise**—it conflates two different optimization scenarios (higher throughput at same cost vs. same throughput at lower cost).

**Claim 2: "Splitwise clusters can deliver 2.35× more throughput under the same power and cost budgets."** This is supported by Figure 18a (iso-power throughput-optimized), where Splitwise-AA achieves 2.15× throughput relative to Baseline-A100 at the same cost and power. The paper's text says "Splitwise-AA delivers 2.15× more throughput at the same power and cost." The 2.35× figure likely comes from comparing Splitwise-AA to Baseline-H100 (1.4/0.57 ≈ 2.46× for the iso-cost scenario, or similar ratios for other scenarios). Again, the precise figure is not directly in a single table row and appears to be rounded from cross-scenario comparisons.

**Claim 3: "Token generation can be run on less compute-capable hardware for better Perf/W and Perf/$ efficiencies."** Strongly supported by multiple experiments: Table IV shows A100s having better or equal cost and energy per request compared to H100s; Figure 18a shows Splitwise-HA achieving higher throughput than Baseline-H100 at lower cost; Figure 19a shows Splitwise-HA and Splitwise-HHcap achieving the lowest power among all configurations for the same throughput. The heterogeneous hardware configurations consistently outperform homogeneous ones on cost and power metrics.

**Claim 4: "KV-cache transfer overhead is negligible."** Supported by Figures 14 and 15. The 0.8% E2E overhead with per-layer transfer is genuinely small. However, this evaluation is only on the coding trace without batching. The overhead with batching (where multiple KV-caches must be transferred simultaneously) is not directly measured. The paper's simulation accounts for transfer overheads via a communication model benchmarked on the same hardware, but no end-to-end batched transfer experiment on real hardware is reported.

**Claim 5: "Phase-specific power management enables substantial power savings without performance loss."** Supported by Figure 9b (token TBT flat under power caps), Figure 19a (Splitwise-HHcap achieving same throughput at 25% lower power—depending on normalization), and Figure 16b (Splitwise-HHcap achieving the highest throughput among all configurations at the same iso-power budget). The evidence is consistent but limited: only one power cap level is evaluated (50% per GPU, 70% total), and the claim that power-capped machines consume 1.23× normalized power is a modeling assumption, not a direct measurement of dynamic power consumption under load.

**Claim 6: "Splitwise is robust to workload and model changes."** Supported by Figure 20. The 7% throughput penalty for heterogeneous configurations under workload shift is small and well-characterized. However, only pairwise substitutions are tested (coding → conversation and vice versa; BLOOM → Llama). A more thorough robustness evaluation would test extreme distribution shifts (e.g., prompt-heavy vs. token-heavy workloads on the same cluster, or large vs. small models) and would report the full distribution of latency degradation rather than just median throughput.

#### Genuine Weaknesses in the Experimental Design

**1. The SLO definitions are generous and somewhat arbitrary.** Table VI defines SLOs as slowdown multiples relative to a DGX-A100 under no contention: TTFT at 2–6×, TBT at 1.25–5×, E2E at 1.25–5×. These values are not justified by user studies or application requirements—they appear to be engineering judgments. The 5× slowdown tolerance for P99 TBT and E2E means a user experiencing P99 latency could wait 5× longer than the no-contention baseline before the SLO is violated. In practice, this means the paper allows substantial tail latency before declaring a cluster configuration invalid, which may overstate achieved throughput. Tighter SLOs (e.g., P99 within 2×) would likely reduce the throughput advantage of Splitwise configurations, especially at high load where tail latencies rise.

**2. No confidence intervals or variance estimates are reported.** All latency percentiles (P50, P90, P99) and throughput figures are presented as point estimates. The 500-question MATH equivalent (to use the reference example's language) is the trace—only two traces (conversation and coding) from a single day (November 11th, 2023) are used. The paper does not report variance across multiple trace segments, multiple days, or multiple random seeds. This makes it impossible to assess whether the throughput differences between configurations (e.g., 1.29× vs. 1.43×) are statistically significant or within noise.

**3. The simulator validation is incomplete.** The paper validates the performance model (MAPE < 3%) and the KV-cache transfer model against hardware, but the end-to-end system—with dynamic pool management, JSQ routing, mixed pool overflow, and preemption—is validated only against "a production load with over 50K iterations" for the 1-machine baseline. There is no end-to-end validation of the full Splitwise system (two-machine, KV-cache transfer, phase-specific scheduling) against real hardware at scale. This is acknowledged implicitly by the paper's reliance on simulation for all cluster-level results. The simulator's fidelity to real Splitwise deployments at scale (dozens of machines, production request patterns) is therefore unknown.

**4. Only two models (Llama2-70B, BLOOM-176B) are evaluated.** Both are decoder-only transformers of similar scale. The paper claims applicability to "all current and upcoming LLMs" (Section VII) including Mixture-of-Experts models, but no such models are tested. The characterization of phase-specific resource utilization may differ for encoder-decoder models (e.g., T5), for much smaller models (e.g., Llama2-7B where prompt computation is less compute-bound), or for models with different attention mechanisms (e.g., MQA, GQA).

**5. The cost model is simplistic.** Machine costs are based on a single cloud provider's pricing (CoreWeave, cited as reference [5]) as of the paper's writing. The paper treats A100 cost as 1× and H100 as 2.35× or 2.5× depending on pool. Real cloud pricing varies by region, reservation type, and time; on-premise deployments have different amortization. The 20% cost reduction claim is therefore tied to a specific pricing snapshot. Power costs are not included in the cost model—only provisioned power in watts is accounted for. Energy consumption (watt-hours per request, as in Table IV for single requests) is not integrated into the cluster-level cost optimization.

**6. The KV-cache transfer experiments are done without batching.** Figure 15 shows end-to-end latency impact for the coding trace without batching—each request runs in isolation. In a real deployment, prompt machines batch multiple prompts together and transfer multiple KV-caches simultaneously. The paper's communication model in the simulator handles this, but no hardware experiment validates batched transfer overhead, where InfiniBand bandwidth would be shared across concurrent transfers. The 0.8% E2E overhead may not hold under load.

**7. The mixed pool mechanism's behavior under pathological workload skew is not tested.** The paper shows robustness to workload substitution (coding → conversation), but does not test extreme scenarios: sudden bursts of very large prompts while token machines are near memory capacity; rapid oscillation between prompt-heavy and token-heavy patterns; or adversarial request patterns designed to trigger excessive pool switching. The claim that the mixed pool prevents fragmentation is plausible but untested at the extremes.

**8. No comparison to alternative disaggregation strategies.** The paper's baselines are homogeneous deployments (Baseline-A100, Baseline-H100). Splitwise is not compared against alternative disaggregation approaches: for example, a simple static partitioning where a fixed fraction of machines run only prompts and the rest run only tokens, without the mixed pool overflow mechanism; or a configuration where prompt and token phases are on the same machine type but scheduled in separate GPU streams or with different power caps. These comparisons would isolate the contribution of Splitwise's specific scheduling policies from the general benefit of phase separation.

#### Experiments That Would Have Strengthened the Paper

- **SLO sensitivity analysis:** sweep the SLO thresholds (e.g., P99 TBT from 2× to 10×) and show how each configuration's throughput scales. This would reveal which SLOs are binding constraints and whether Splitwise's advantage grows or shrinks under tighter/loser SLOs.
- **Multi-day trace evaluation:** use traces from multiple days or times to assess whether the provisioned clusters are robust to diurnal or weekly workload patterns. The current evaluation uses a single 20-minute trace, which may not be representative.
- **Dynamic power measurement:** measure actual GPU power draw (not just TDP-normalized power caps) during cluster simulations to validate the assumption that power-capped token machines consume proportionally less energy, and to compute total energy-per-request for each configuration.
- **Scalability to larger clusters:** the largest cluster evaluated is roughly 88 machines (Baseline-A100 iso-throughput). Production LLM inference clusters may involve hundreds or thousands of GPUs. The paper does not discuss whether the CLS becomes a bottleneck (though Section VII mentions this is orthogonal), and the simulation results may not extrapolate.
- **Ablation of the mixed pool:** run a configuration with mixed pool disabled (pure prompt/token separation, no overflow) and compare throughput against full Splitwise to quantify the mixed pool's contribution to robustness.
- **Infiniband bandwidth sensitivity:** vary the available InfiniBand bandwidth (e.g., 100 Gbps, 200 Gbps, 400 Gbps) to determine the minimum interconnect speed needed for Splitwise to remain beneficial, which would guide deployment on different network topologies.
- **Failure recovery experiments:** the paper mentions that failed requests restart from scratch or could use KV-cache checkpointing (Section IV-E), but no recovery latency or throughput impact is measured. For a system targeting production deployment, recovery behavior under GPU or machine failures is important.

## 6. Limitations and Trade-offs

### The Cost of Difficulty Estimation Is Comparable to the Inference Budget Itself

The entire compute-optimal framework — whether applied to search or revisions — depends on estimating each prompt's difficulty *before* deciding how to allocate the inference budget. Both the oracle and predicted difficulty estimation methods require generating 2048 samples per question and scoring them with the PRM at the final-answer level (Section 3.2). The paper is transparent about this:

> "estimating difficulty in this way still incurs additional computation cost during inference... our experiments do not account for this cost largely for simplicity"

The consequence is substantial. Generating and scoring 2048 samples per question consumes more compute than the largest test-time budgets studied (256–512 generations). The reported 4× efficiency gains over best-of-N are computed *after* difficulty is known, treating the difficulty estimation cost as a sunk cost that is never amortized. In a realistic deployment, a prompt arriving at inference time would need to be characterized before the strategy could be selected. If the difficulty estimation itself costs 2048 generations, then the total cost of serving the request is at least 2048 + N generations, where N is the test-time budget the policy allocates. For low-to-moderate budgets (N = 16–64, where the 4× gains are most pronounced), the difficulty estimation cost would completely dominate and eliminate any efficiency advantage. For high budgets (N = 256–512), the overhead is a factor of 4–8× additional compute. The $4\times$ figure is therefore best understood as an **upper bound on achievable efficiency** under perfect difficulty knowledge — not a realized deployment gain.

The evidence for this limitation is indirect but clear. The difficulty estimation cost (2048 samples) is stated in Section 3.2 but never added to any budget calculation in Figures 4, 8, or the FLOPs-matched analysis in Section 7. The predicted difficulty bins require slightly less (no ground-truth labels needed, but still 2048 samples and PRM scoring), and the paper notes they perform nearly as well as oracle bins (Figures 4 and 8 show largely overlapping curves). However, the cost of generating those 2048 samples — which is the majority of the difficulty estimation expense — remains unaccounted for regardless of whether the bins are oracle or predicted.

The paper partially acknowledges this in Section 8 as "a key avenue for future work" and suggests training models to predict difficulty directly from the question text. No such model is developed or evaluated. An alternative the paper does not discuss — but which logically follows — would be *adaptive* difficulty estimation: generate a small number of initial samples (say, 4–8), estimate difficulty from the PRM's score distribution on those samples, and allocate the remaining budget accordingly. This would amortize the estimation cost into the inference process and could recover much of the efficiency that the static 2048-sample method leaves on the table.

---

### The Approach Fails Completely on Hard Problems — Test-Time Compute Amplifies Capability, It Does Not Create It

Across every method, every budget level, and every metric, the hardest questions (difficulty bin 5) show **near-zero improvement** from any amount of test-time compute. Section 7's takeaway box states this explicitly, and the evidence is consistent throughout the paper. In Figure 3 (right), bin 5 accuracy hovers at 1–3% for best-of-N, beam search, and lookahead search at all budgets up to 256 generations. In Figure 7 (right), bin 5 shows 2–3% accuracy regardless of the sequential-to-parallel revision ratio. In the FLOPs-matched comparison (Figure 9), the bin 5 scaling line is essentially flat near 0–5% accuracy, well below the 14× larger model's performance at every value of R. The paper acknowledges the boundary:

> "on hard questions (bins 4–5), pretraining is almost always more effective"

The root cause is that test-time compute operates by exploring and refining the base model's existing output distribution. If the base model's pass@1 on a question is near zero — meaning the model essentially never produces a correct solution even with 2048 independent samples — then no amount of search or revision can help. There are no correct solutions in the proposal distribution to find, refine, or select among. Beam search prunes toward better solutions that don't exist; revision chains refine answers that were never on track. The PRM's scores provide no useful signal because the model's token-level outputs are already far from any correct trajectory.

This limitation defines a clear boundary for the method's applicability: test-time compute works when problems are within the base model's **capability frontier** (the model produces correct solutions at some non-trivial rate) but not within its **reliability frontier** (it doesn't produce them consistently). For problems outside the capability frontier entirely — novel reasoning patterns, out-of-distribution problem structures, or tasks requiring knowledge the model lacks — pretraining remains the only viable path. The FLOPs-matched analysis sharpens this boundary quantitatively: even at $R \ll 1$ (where the smaller model gets a large inference budget), hard problems show a –3.6% disadvantage for PRM search and a smaller but still present gap for revisions (Figure 9), meaning test-time compute cannot close the capability gap even with essentially unlimited inference budget.

The paper does not attempt to mitigate this limitation — it documents it as a fundamental property of test-time compute scaling. This is appropriate: the limitation is intrinsic to the approach's mechanism, not an engineering oversight. However, it means the method offers no path forward for genuinely novel or out-of-distribution reasoning. For practitioners, this implies that test-time compute should be deployed on problem distributions where most questions fall within the model's capability range (bins 1–4 in the paper's taxonomy). For problems where the base model's pass@1 is near zero, investing in better pretraining — not smarter inference — is the correct strategy.

---

### Revisions and Search Are Evaluated Independently — The Complementary Gains Are Never Combined

The paper studies two complementary mechanisms — PRM-guided search and iterative revisions — but never combines them in a single system. Section 8 acknowledges this gap explicitly:

> "we did not experiment with PRM tree-search techniques in combination with revisions"

This is a significant limitation because the two mechanisms have complementary, difficulty-dependent strengths that the paper itself identifies. Revisions are most effective on easy problems where the model's initial output is roughly correct and needs local refinement — a form of exploitation in answer space. PRM search is most effective on medium problems where the model needs to explore qualitatively different high-level strategies — a form of exploration. In the compute-optimal policy, each difficulty bin selects *either* a search strategy *or* a revision strategy (or a parallel baseline), but never *both*.

The consequence is that the reported results represent a **lower bound** on what a fully integrated system could achieve. A natural extension would use the revision model as the proposal distribution within beam search: at each step of beam expansion, the model conditions on previous rejected branches (revision context) and generates higher-quality candidate steps, which are then scored by the PRM and pruned. Alternatively, the PRM could guide which revisions to pursue — rather than blindly generating a long sequential revision chain, use PRM scores at each step to decide whether to continue revising, restart from scratch, or branch into parallel exploration. On medium-difficulty problems where both mechanisms show strengths independently, their combination could push past the performance ceilings that each individually hits (beam search plateaus due to PRM over-optimization; sequential revisions plateau due to limited diversity).

The evidence that this combination would help is present but indirect. Figure 3 (right) shows that search helps on bins 3–4 where the model has some correct solutions but needs help finding them. Figure 7 (right) shows that revisions help on bins 2–3 where the model's initial outputs are plausible but contain errors. Bin 3 sits in the overlap — both mechanisms work individually — which is precisely where a combined approach would compound gains. The paper's compute-optimal policy, by selecting only one mechanism per bin, leaves this compounding on the table.

The paper does not attempt to mitigate this limitation. It is described as a direction for future work. The primary barrier is likely practical: combining beam search (which requires generating many candidate partial solutions at each step) with revisions (which require conditioning on long context histories of previous attempts) would multiply the generation cost and complexity. However, given the paper's finding that the two mechanisms shine in different difficulty regimes, a simpler combined approach could simply apply *both methods independently* to the same problem and use a verifier to select the best answer across both pipelines — a form of ensemble that leverages the complementary strengths without complex integration.

### Single Benchmark and Single Model Family Limit Generalization Claims

All experiments in the paper use the MATH benchmark (500 test questions) with PaLM 2-S* as the base model. The search and revision experiments all evaluate on MATH; the difficulty bins are defined relative to PaLM 2-S*'s pass@1 rates on MATH; the PRM is trained on PaLM 2-S* outputs for MATH problems; the revision model is fine-tuned from PaLM 2-S* on MATH training data. The paper states the model is "representative of the capabilities of many contemporary LLMs" (Section 4), but provides no evidence for this claim beyond running the characterization on two models.

Several aspects of the findings could be specific to this model-benchmark combination:

- **The PRM's quality and over-optimization behavior depend on PaLM 2-S*'s output distribution.** A model with different calibration properties — different patterns of confidence, different types of errors, different susceptibility to producing solutions that look plausible to a verifier — might exhibit different difficulty-dependent scaling curves. The paper's finding that beam search over-optimizes on easy problems (Figure 3, right) is a function of the particular PRM's reliability on PaLM 2-S*'s distribution. A better PRM trained on a different model's outputs might show less over-optimization, shifting the optimal strategy boundaries.
- **The revision model's ability to learn from incorrect in-context examples depends on the base model's in-context learning capabilities.** The edit-distance-based training data construction (Section 6.1) assumes the model can recognize structural similarities and correct targeted errors when shown close-but-incorrect examples. This capability varies substantially across model families — some models are much better at in-context error correction than others.
- **MATH is a specific reasoning domain.** The benchmark consists of competition-level math problems requiring symbolic manipulation, multi-step deduction, and exact numeric or algebraic answers. The difficulty-dependent patterns — beam search helping on medium problems but hurting on easy ones, sequential revisions dominating on easy problems — may be specific to mathematical reasoning. Code generation, logical reasoning, scientific question-answering, or open-ended generation could show different patterns because the structure of errors, the verifiability of intermediate steps, and the nature of "easy vs. hard" problems differ across domains.
- **The 500-question test set is small for the analysis granularity.** Splitting 500 questions into five difficulty quintiles yields ~100 questions per bin. With two-fold cross-validation for compute-optimal strategy selection, the policy is chosen based on ~50 questions per fold per bin. A single misclassified question or outlier can shift the optimal strategy. The paper does not report confidence intervals on the compute-optimal scaling curves, making it difficult to assess whether the observed differences between strategies at a given budget are statistically reliable or within sampling noise.

The paper acknowledges the single-model limitation only implicitly — it runs characterization on two models (BLOOM-176B and Llama2-70B in Section III) but all rigorous scaling experiments use PaLM 2-S*. The single-benchmark limitation is not discussed. Section 8 mentions that extending to other domains (code, reasoning, QA) is future work. For practitioners deciding whether to adopt the compute-optimal framework, this creates uncertainty: if the difficulty-dependent strategy selection depends on model-specific and domain-specific properties, the provisioning methodology derived from MATH + PaLM 2-S* may not transfer. A new model on a new domain would require the full characterization, PRM training, revision training, and strategy search pipeline to be re-executed — an expensive proposition given the 2048-sample difficulty estimation step.

### The Revision Model's Correct-to-Incorrect Reversion Rate Is a Fundamental Instability

The revision model, as trained, has a significant pathology: approximately **38% of correct answers produced during a revision chain get "revised" back to incorrect answers in the subsequent step** (Section 6.1). This is a direct consequence of the training data construction: the model is fine-tuned only on sequences where all in-context answers are incorrect, followed by a correct target. During training, the model never sees examples where the current answer is already correct and should be preserved. At inference time, when a revision chain produces a correct answer, the model's training distribution provides no signal for what to do — it has learned that in-context answers are *always* wrong and that it should *always* produce something different.

The consequence is that the revision model cannot be trusted to converge on a correct answer and stay there. A revision chain that reaches the correct answer at step $k$ has a 38% probability of abandoning it at step $k+1$, even though the answer was already correct. This means the revision process is not monotonically improving — it is an **unstable process** where performance oscillates rather than converges. The paper's mitigation is post-hoc selection: majority voting or verifier-based selection across the entire chain of revisions, picking the best answer from any point rather than always taking the final revision. This is effective (Figure 6 shows the revision model's per-step accuracy remains roughly 23–25% out to 64 steps, and the selection mechanism recovers the correct answer when it appears), but it is a **band-aid over a fundamental design flaw** in the training procedure.

The paper's evidence for this limitation is direct. Section 6.1 states the 38% reversion rate. Figure 6 (left) shows the revision model's pass@1 trajectory, which improves from ~18% to ~24% over the first 15–20 steps but then oscillates rather than converging — this is consistent with the reversion phenomenon. The ReST$^{EM}$ experiment (Appendix K, Figure 16) is a further demonstration of the instability: attempting to optimize the revision model with RL-style training caused performance to degrade substantially with sequential revisions. The paper hypothesizes that on-policy data collection "exacerbates spurious correlations in revision data," which is a sign that the revision training procedure is brittle and its benefits depend on specific choices (offline data construction, edit-distance-based pairing) that may not survive attempts to improve the model.

The paper does not directly address the reversion problem beyond the post-hoc selection mechanism. Section 6.1 describes the mitigation (majority voting or verifier-based selection across the chain) but does not explore more principled solutions: training the revision model on some sequences where the in-context answer is already correct and the target is to output it unchanged (teaching the model to recognize when revision is unnecessary); adding a termination criterion that stops the revision chain when the verifier's score exceeds a threshold; or using the PRM at each revision step to decide whether to continue revising or accept the current answer. The reversion problem is a tradeoff: the revision training procedure (incorrect-to-correct trajectories only) is what makes sequential revisions effective on easy problems, but it also creates the instability that requires post-hoc selection. The paper does not resolve this tension.

For practitioners, the instability means the revision model cannot be used in a streaming setting where the user sees each revision as it is produced — the model will visibly "change its mind" from correct to incorrect answers. The selection mechanism requires generating the full chain and then picking retrospectively, which adds latency (all revisions must be produced before the final answer is selected) and compute (all revisions are generated even if the correct answer appeared early). The 38% reversion rate also means the effective efficiency of revisions is lower than the raw sequential-to-parallel ratio comparisons suggest — roughly 38% of the sequential compute budget is spent productively reaching a correct answer only to immediately abandon it.

### All Inference Budget Accounting Is in "Generations" — Wall-Clock Time and Latency Implications Are Not Discussed

The paper measures all compute budgets in "generations" — the number of complete solution samples drawn from the model. This is consistent across search (N beams = N generations, beam search = N generations, lookahead search = N × (k+1) generations) and revisions (N total generations = sequential chain length × number of parallel chains). A generation is a reasonable proxy for total FLOPs and enables clean comparisons across methods with different parallelism structures.

However, this accounting ignores **wall-clock time**, particularly the fundamental distinction between operations that can be parallelized and those that are inherently sequential:

- **Best-of-N and beam search with N samples/generations can be executed in parallel** with sufficient hardware. Generating 256 independent solution samples takes roughly the same wall-clock time as generating 1, assuming enough GPUs or memory capacity to run them simultaneously. The cost is measured in total compute (FLOPs or GPU-hours), not in user-experienced latency.

- **Sequential revisions are inherently serial.** Each revision depends on the output of the previous revision — the model must condition on the previous attempt's full text and the verifier's score before generating the next one. A strategy that allocates 256 generations as a sequential chain of length 256 takes 256× longer wall-clock time than a strategy that runs 256 parallel generations simultaneously. Even the hybrid strategy that the compute-optimal policy often selects (√N parallel chains each of length √N) takes roughly √N × longer wall-clock time than fully parallel sampling, because the sequential chains are on the critical path.

- **Beam search has a serial dependency across steps** (the beams must be expanded, scored, and pruned at each step before the next expansion), though the expansions within a step are parallel. This means beam search with N beams and M solution steps requires at least M sequential forward passes (plus scoring/pruning overhead), while best-of-N with N samples requires only 1 forward pass (plus verification). The paper's cost model (N generations for both) treats them as equivalent in "compute budget" but they are not equivalent in latency.

The paper never discusses this tradeoff. Section 8's future work section does not mention latency. The compute-optimal policy selects strategies that are optimal under the generation-count metric but may be deeply suboptimal under a latency-sensitive metric. Specifically, on easy problems, the compute-optimal policy favors fully sequential revisions (Figure 7, right, shows bin 1 and bin 2 performing best at the right end of the sequential-to-parallel ratio sweep). For a budget of 256 generations, this means the system generates a single chain of 256 sequential revisions — taking approximately 256× the wall-clock time of a parallel best-of-256 strategy, while achieving only modest accuracy gains. For latency-sensitive applications (interactive assistants, real-time code completion, conversational APIs where users expect sub-second responses), this allocation would be unacceptable regardless of its generation-count efficiency.

The paper's FLOPs-matched comparison (Section 7) uses the standard FLOPs approximation $Y = 2ND_{\text{inference}}$ for inference cost, which counts total compute but ignores the serial vs. parallel distinction. This is standard practice in the scaling laws literature, but it means the comparison treats $D_{\text{inference}}$ as interchangeable regardless of whether those tokens were generated serially (revisions) or in parallel (best-of-N). In practice, the latency cost of generating $D_{\text{inference}}$ tokens serially is $D_{\text{inference}} \times$ (time per token), while generating them in parallel is roughly constant wall-clock time. A practitioner deploying these methods needs to know not just how many GPU-hours they consume, but how long the user waits for a response. The paper provides only the former.

This limitation does not invalidate the paper's findings — the generation-count metric is the right one for understanding computational efficiency — but it means the compute-optimal policies described are **optimal under a throughput metric (total compute per correct answer) but not necessarily under a latency metric (time per correct answer)**. For batch processing or offline evaluation where latency doesn't matter, this distinction is irrelevant and the paper's recommendations apply directly. For interactive applications, the sequential-heavy strategies favored for easy problems would need to be re-evaluated with a latency-aware objective function.
