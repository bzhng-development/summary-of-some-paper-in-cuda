# Harnessing LLM Agents with Skill Programs

**ArXiv:** [2605.17734](https://arxiv.org/abs/2605.17734)

## 🎯 Pitch

LLM agents keep ignoring their own hard-won advice. HASP fixes this by converting failure-prevention tips into executable Program Functions that forcefully intervene mid-task—rewriting a bad search query or blocking a premature answer—boosting web-search accuracy by 25% over standard agents without any retraining.

---

## 1. Executive Summary

This paper introduces **HASP (Harnessing LLM Agents with Skill Programs)**, a framework that transforms reusable agent experience from passive textual advice into executable **Program Functions (PFs)** — state-action intervention modules that detect failure-prone states and explicitly modify the next action or inject corrective context (e.g., rewriting an over-constrained search query, forcing a READ before premature finalization). Evaluated on web-search reasoning (HotpotQA, 2Wiki, MuSiQue), mathematical reasoning (AIME24, AMC23, GameOf24), and coding benchmarks (HumanEval, MBPP, BigCodeBench) using Qwen2.5-7B-Instruct, inference-time PF intervention alone improves average web-search accuracy by 25% over a multi-loop ReAct agent, while combining PF-guided rejection sampling with controlled skill library evolution yields a 30.4% gain over Search-R1. In FLOPs-matched comparisons, the framework's structured PF-derived supervision enables post-training internalization that outperforms prior skill-based and RL-based training methods — establishing that PFs surface and stabilize strategies the model can already execute but does not apply reliably, while genuine strategy discovery remains in the domain of broader RL-style exploration.

## 2. Context and Motivation

### The Core Problem: Agent Experience That Cannot Enforce Itself

The fundamental gap this paper addresses is deceptively simple: **LLM agents accumulate reusable experience from past failures, but that experience cannot reliably control future behavior.** This is not a problem of knowledge acquisition — agents *do* learn from their mistakes, and they *can* articulate what went wrong. The problem is one of mechanism: the knowledge exists in language, but there is no reliable pathway from that language to the agent's actual decisions in the policy loop.

This gap manifests in a specific, recurring pattern across agent deployments. When an LLM agent fails on a task — say, answering a multi-hop web-search question — the failure mode is often recognizable and preventable. The agent might terminate its search without reading any retrieved document, commit to a brittle intermediate conclusion, or repeat the same unproductive search query three times. A human watching the trajectory could immediately diagnose what went wrong and prescribe a fix: "Don't finalize before verifying evidence," or "Search broadly before committing to one entity." The agent itself can often articulate similar lessons when prompted to reflect on its failures. Yet when the same agent encounters a structurally similar problem moments later, it makes exactly the same mistake.

This is the **advisory gap**: skills expressed as natural-language advice inhabit the same representational space as everything else the model processes — they are text among text, treated with the same probabilistic attention and the same susceptibility to being ignored, forgotten, or overridden by competing signals. A textual skill says *what* the agent should do in principle, but does not specify *when* it should activate inside the dynamic policy loop, *how* it should alter the next concrete decision, and crucially, provides no mechanism to *ensure* it is followed. The paper captures this precisely in Figure 1: the existing paradigm of "Skills Injected into Prompt" produces reasoning that acknowledges the skill ("I should verify evidence first...") while simultaneously producing actions that violate it ("→ Final Answer" without verification).

### Why This Problem Matters: Beyond Academic Curiosity

The advisory gap has practical consequences that extend well beyond benchmark performance. Several converging trends in LLM agent deployment make this problem urgent rather than merely interesting:

**1. The shift from single-step to multi-step agent systems.** As agents move beyond simple question-answering into complex, long-horizon tasks — multi-hop reasoning, tool use, interactive coding, embodied planning — the number of decision points where a learned lesson should apply grows combinatorially. A three-step failure on a simple QA task becomes a thirty-step cascade on a complex research task. Each intermediate decision is an opportunity for a known failure pattern to recur, and the cost of each recurrence compounds. The paper's focus on web-search reasoning (Section 4, HotpotQA, 2Wiki, MuSiQue) is deliberate: these are precisely the multi-hop settings where premature finalization, entity confusion, and insufficient exploration are most damaging.

**2. The asymmetry between failure diagnosis and failure prevention.** Prior work has invested heavily in *detecting* and *reflecting on* failures — Reflexion (Shinn et al., 2023) stores verbal reflections, ExpeL (Zhao et al., 2024) extracts experiential lessons, and Voyager (Wang et al., 2023) maintains skill libraries as executable code for Minecraft. These systems are effective at *producing* knowledge about what went wrong. But the pathway from that knowledge to reliably changed behavior remains weak. The agent learns a lesson, stores it in a memory bank, retrieves it when relevant, and... still sometimes ignores it. This asymmetry means that improving failure diagnosis yields diminishing returns unless the enforcement mechanism improves in parallel. HASP's central contribution is addressing the enforcement side directly: skills become executable guardrails, not advisory reminders.

**3. The economic and safety implications of unreliable skill execution.** In high-stakes agent deployments — automated code review, medical information retrieval, financial analysis — an agent that "knows" it should verify sources but sometimes skips verification is not just inefficient; it is dangerous. The reliability gap between what an agent *can* articulate as best practice and what it *does* in practice creates a trust deficit that limits real-world adoption. HASP's PF interface provides auditability (every intervention logs what it triggered on, what it changed, and why) and deterministic execution (PFs are pure-code functions with explicit `should_activate` predicates), addressing this trust deficit at the architectural level.

**4. The training-inference asymmetry in agent capability expression.** A recurring finding in the LLM agent literature — and one that HASP exploits systematically — is that models often *possess* capabilities that they do not *reliably express*. The Qwen2.5-7B-Instruct model used throughout the paper can, in principle, decompose complex questions, verify evidence before finalizing, and avoid entity confusion. When prompted carefully or given multiple attempts, it sometimes does these things. The problem is not capability acquisition (which would require more pretraining or RL-based exploration) but **capability elicitation** — getting the model to apply strategies it already understands at the right moments. HASP frames this distinction explicitly in the conclusion: "PFs help surface and stabilize useful strategies that the model can often execute but does not apply reliably, while broader RL-style exploration may still be needed to discover genuinely new strategies."

### Where Prior Approaches Fall Short

The paper situates itself against a rich landscape of prior work, identifying specific limitations in each category. Table 1 provides a structured comparison across five dimensions (Skill/Memory Form, Runtime Control, Learning Signal, Policy Training, Skill Evolution), but the qualitative gaps are deeper than the table suggests.

#### Passive Textual Skills (Reflexion, ExpeL, Prompt-Only)

The dominant paradigm for reusing agent experience is verbal: store lessons as natural language, retrieve them by similarity when relevant, and inject them into the prompt. Reflexion (Shinn et al., 2023) pioneered this approach with verbal reinforcement learning — the agent reflects on failures, stores textual "reflections," and retrieves them in future episodes. ExpeL (Zhao et al., 2024) extended this to extract structured experiential lessons from trajectories. SKILL0 (Lu et al., 2026) represents the most recent evolution: skills are extracted from successful trajectories and injected as in-context demonstrations.

The limitation of all these approaches is not that textual skills are useless — they demonstrably improve performance. The limitation is that textual skills operate entirely within the model's probabilistic generation process. They can be attended to or ignored; they can be contradicted by stronger priors from pretraining; they can be relevant at step 3 of a trajectory but forgotten by step 7. The paper's Prompt-Only Skills baseline in Table 2 makes this concrete: on web-search reasoning, Prompt-Only Skills achieves 20.5% average accuracy, compared to 51.0% for PF-only intervention. This 30.5-percentage-point gap is not about skill *content* — the skills encode the same lessons in both conditions. The gap is entirely about *mechanism*: one version is text the model may heed, the other is code that deterministically alters the action stream.

A deeper issue, which the paper implicitly addresses but does not foreground, is that textual skills blur the boundary between skill retrieval and skill execution. When a skill is retrieved and injected into a prompt, the model must simultaneously (a) understand what the skill means, (b) recognize that the current state matches the skill's applicability conditions, (c) translate the skill's abstract advice into a concrete action modification, and (d) override any competing impulses that would produce the default (wrong) action. Each of these steps is probabilistic and can fail independently. HASP decomposes this monolithic process: the PF's `should_activate` function handles (b) deterministically, the `intervene` function handles (c) by producing a concrete `Intervention` object, and the harness handles (d) by forcing the revised action into the loop. The model's role is reduced to (a) — understanding the skill's semantics — which it does at PF *design* time rather than at execution time.

#### Post-Training for Agent Reasoning (Search-R1, ReSearch, AgentFlow)

A parallel line of work trains agents to improve their reasoning and tool-use behavior through reinforcement learning or supervised fine-tuning. Search-R1 (Jin et al., 2025) trains LLMs to reason and leverage search engines using RL, while ReSearch (Chen et al., 2025) and ZeroSearch (Sun et al., 2025) similarly optimize search-augmented reasoning through training. AgentFlow (Li et al., 2025) takes a different approach, optimizing the entire agentic workflow (the flow graph connecting reasoning steps and tool calls) through RL-based search over flow structures.

These methods achieve strong results — AgentFlow + Flow-GRPO reaches 53.2% on web-search reasoning (Table 2) — but they share a fundamental limitation: they treat the agent as a black-box policy to be optimized through reward signals. The insight that *this particular failure mode* (premature finalization) requires *this particular intervention* (forcing a READ before FINAL) is baked into the reward function indirectly, if at all. When Search-R1's RL training improves performance, it is difficult to attribute the improvement to specific behavioral changes — the policy learned something, but what exactly? This opacity matters for two reasons. First, it makes systematic debugging and improvement harder: if performance plateaus, it is unclear which failure modes remain and why. Second, it means that knowledge acquired through training is locked inside the model weights — it cannot be inspected, shared across models, or updated without retraining.

HASP positions itself as complementary to these training approaches rather than competing with them. The PF library is an external, inspectable, and updatable repository of intervention logic. The paper's post-training experiments (Table 4, Section 3.2) show that PF-corrected trajectories can be used to internalize skills into the policy through SFT, rejection sampling, or on-policy distillation — but the skills themselves exist independently of any particular trained checkpoint. This is the "modular" property the paper emphasizes: the same PF library can be used for inference-time intervention, for generating training data, for guiding rejection sampling, or for any combination thereof.

#### Skill-Based Self-Improving Agents (SkillRL, SAGE, MemSkill)

The most directly comparable prior work is the family of self-improving agents that maintain skill libraries. SkillRL (Xia et al., 2026) evolves agents through recursive skill-augmented RL, where skills are textual descriptions discovered during training and used to shape rewards. SAGE (Wang et al., 2025) builds a skill library through RL and uses it to guide future behavior. MemSkill (Zhang et al., 2026) learns and evolves memory skills for self-evolving agents.

These systems share HASP's ambition of building reusable skill libraries that improve over time, but they differ fundamentally in what skills *are* and how they affect behavior. In SkillRL and SAGE, skills remain in the textual/reward-shaping domain — they influence the policy indirectly through prompts or shaped rewards. In MemSkill, skills are closer to executable routines but are still primarily retrieval-augmented text. HASP's innovation is making skills **executable state-action intervention functions** that operate at the level of the agent loop itself — they inspect the proposed action, decide deterministically whether to intervene, and return a concrete modification. This is the "Runtime Control" column in Table 1: HASP is the only method with a checkmark (✓) for direct, explicit control, while comparable methods show circles (◦) for partial or indirect control.

The consequence of this architectural choice is visible in the gap between HASP's inference-only performance (56.2% with teacher on web-search, Table 2) and comparable skill-based methods. SkillRL and MemSkill do not report directly comparable web-search results, but the structural difference is clear: a textual skill that says "avoid repeated searches" can be attended to or ignored; a PF that checks `token-Jaccard > 0.5` against recent queries and forces a query reformulation cannot.

#### The Unexplored Territory: Executable Guardrails for Agent Loops

Taken together, the prior work reveals a gap that had not been systematically addressed before HASP. On one side, we have textual skills — flexible, easy to create, but advisory. On the other side, we have training-based optimization — powerful, but opaque and computationally intensive. Between them lies a territory that HASP claims: **executable, inspectable, updatable guardrails that intervene directly in the agent loop without requiring model retraining.**

This territory matters because it combines the best properties of both existing paradigms. Like textual skills, PFs are human-readable (each PF has a SKILL.md specification with natural-language descriptions, trigger conditions, and examples — see Skill B.1 and Skill B.2 in Appendix B). Like training, PFs reliably change behavior — but unlike training, they do so transparently, with every intervention logged, and they can be added, removed, or modified without touching model weights. The paper's mechanism analysis (Section 4.2, Table 5) quantifies what this transparency enables: researchers can study *when* PFs fire (timing signal), *how* they intervene (modality signal), whether the intervention produced a valid repair (correctness signal), and whether it improved the final outcome (outcome signal). These structured signals are impossible to extract from a black-box trained policy.

### How This Paper Positions Itself

HASP's positioning can be understood along three axes:

**1. From passive to active skill execution.** The paper's central thesis is that the gap between "knowing" and "doing" in LLM agents can be bridged by changing the *form* of reusable knowledge — from text to code, from advice to guardrails, from "you should" to "I will." This is not a claim that textual skills are worthless (the paper includes them as a baseline and shows they do help, Table 2) but rather that the *mechanism* of skill delivery determines the reliability of skill execution. The 30.5-point gap between Prompt-Only Skills (20.5%) and PF-only intervention (51.0%) on web-search reasoning is the strongest evidence for this thesis.

**2. Modularity across the agent lifecycle.** A recurring theme in the paper is that PFs are not tied to any single stage of the agent development pipeline. The same PF library serves three distinct purposes:
- **Inference-time intervention** (Section 3.1): PFs fire inside the agent loop, modifying actions or injecting context without model updates.
- **Post-training supervision** (Section 3.2): PF-corrected trajectories, scored by PF-derived signals (timing, mode, correctness, outcome), provide structured training data for SFT, rejection sampling, or on-policy distillation.
- **Self-improving library evolution** (Section 3.3): Residual failures are summarized into candidate PFs, filtered through executable validation and teacher review, and added to the library.

This modularity is not merely convenient — it addresses a genuine tension in agent development between rapid deployment (inference-time fixes), sustained improvement (training-based internalization), and adaptability (library evolution as task distributions shift). The paper's experimental design (Table 4, the 2×3 grid of open-loop vs. closed-loop × SFT/RS/OPD) is structured to test exactly this modularity: does the PF interface work equally well as an inference-only harness, a training-data generator, and a target for self-improvement?

**3. Capability elicitation, not capability creation.** The paper is explicit about what PFs can and cannot do. The conclusion states: "PFs help surface and stabilize useful strategies that the model can often execute but does not apply reliably, while broader RL-style exploration may still be needed to discover genuinely new strategies." This is not a limitation to be hidden — it is a feature. By restricting PFs to eliciting existing capabilities, HASP avoids the instability and computational cost of RL-based exploration while still achieving substantial gains. On AIME24, the hardest math benchmark, HASP-Evolve + RS reaches 16.7% (Table 2), while AgentFlow + Flow-GRPO reaches 40.0% — a gap that reflects the difference between elicitation (working within the model's existing strategy space) and exploration (finding genuinely new solution strategies). The paper is transparent that AIME24-style problems, which require novel mathematical insight rather than consistent execution of known patterns, are not where PFs excel.

This positioning clarifies HASP's relationship to prior work. It is not a replacement for RL-based agent training (Search-R1, AgentFlow) or for textual skill libraries (Reflexion, SKILL0). It is a new point in the design space — executable, inspectable, updatable — that fills a gap between advisory text and black-box optimization. The paper's empirical contribution is demonstrating that this gap is not empty: there exist reusable interventions that can be encoded as deterministic PFs, that these interventions capture a large fraction of recoverable failures, and that making them executable rather than advisory yields performance gains comparable to or exceeding those from more computationally intensive methods.

## 3. Technical Approach

### 3.1 Reader Orientation

**What the system is:** HASP is an external control harness that wraps around an existing LLM agent, intercepting its proposed actions at each decision step, checking whether any learned "skill programs" should fire, and modifying the action or injecting corrective context before the agent proceeds.

**What problem it solves and the shape of the solution:** The system addresses the gap between an agent knowing what it should do (expressed as natural-language lessons from past failures) and actually doing it reliably. The solution shape is a library of deterministic, executable **Program Functions (PFs)** — each one a typed Python object with a `should_activate()` predicate that inspects the current agent state and a `intervene()` method that returns a structured repair — deployed as a middleware layer that can operate at inference time, generate structured supervision for post-training, and evolve through validated self-improvement.

### 3.2 Big-Picture Architecture (Diagram in Words)

HASP has five major components arranged in a layered architecture around the base agent policy:

1. **Base Agent Policy (`$\pi_\theta$`)** — the LLM (Qwen2.5-7B-Instruct) that proposes actions `$a_t^{\text{orig}} \sim \pi_\theta(\cdot \mid s_t)$` given the current state `$s_t$` (which includes the task query, conversation history, and tool outputs). This is the "proposal distribution" — the uncorrected behavior that PFs will intercept.

2. **Skill Library (`$\mathcal{M}$`)** — an external, versioned collection of Program Functions, each with a SKILL.md specification (YAML frontmatter + markdown body describing the failure pattern, trigger conditions, intervention design, and examples) and a corresponding Python class implementing `should_activate(step_context, action_type, arg) → bool` and `intervene(step_context, action_type, arg, teacher=None) → Intervention`. The library is initialized from recovered failure cases and grows through validated evolution.

3. **PF Harness / Intervention Dispatcher** — the middleware that runs on every agent step: it retrieves candidate PFs `$\mathcal{R}(s_t) \subseteq \mathcal{M}$` using layered selection (skill selectors, PF selectors, phase-gated reminders), evaluates each PF's activation predicate against the current state and proposed action, applies the activated PFs through an intervention operator `$\Gamma$`, and feeds the revised action `$\tilde{a}_t$` or injected context `$c_t$` back into the agent loop.

4. **Post-Training Signal Extractor** — for each PF activation event, this component records a structured tuple `$e_t = (s_t, a_t^{\text{orig}}, \tilde{a}_t, c_t, \kappa_t, \Delta_t)$` containing the triggering state, original action, corrected action, injected context, fired PF metadata, and resulting feedback. It scores each record using four derived signals — timing, modality, correctness, outcome — weighted as `$A_t = 0.15 \cdot t_t + 0.10 \cdot m_t + 0.25 \cdot q_t + 0.50 \cdot o_t$`, and aggregates these into trajectory-level scores `$A(\tau) = T^{-1} \sum_{t=1}^T A_t$` that drive SFT, rejection sampling, and on-policy distillation.

5. **Self-Improvement Pipeline (Phases A–H)** — an offline, epoch-based process that revisits residual failures under the current policy checkpoint, clusters failure patterns, proposes candidate PFs from the student model, validates them through executable checks (syntax, interface, mock execution, return type) and teacher review (five-dimensional scoring: concept, trigger, intervention, executability, validation utility), admits accepted candidates to the library with versioning, and regenerates training data from PF-corrected trajectories.

**Information flow at inference time:** Query `$q$` enters → teacher optionally scores difficulty (1–5) and activates the difficulty gate → PFSelector retrieves top-K relevant skills and injects their `system_summary` text into the system prompt → the base policy enters the multi-step ReAct loop → at each step `$t$`, the policy proposes `$a_t^{\text{orig}}$` → the harness evaluates `should_activate()` for all selected PFs → if any PF fires, the intervention operator `$\Gamma$` produces `$(\tilde{a}_t, c_t, \kappa_t)$` → the revised action `$\tilde{a}_t$` is executed in the environment and any context `$c_t$` is appended to the next observation → the observation `$o_{t+1}$` returns → the loop continues until FINAL or step budget exhausted.

**Information flow at training time:** Training pool of questions → PF-aware rollouts with the current library (Phase A) → failure detection and clustering (Phase B) → candidate PF proposal (Phase C) → executable validation (Phase D) and teacher review (Phase E) → library update (Phase F) → signal scoring of all rollout steps (Phase G) → construction of SFT/DPO training data targeting PF-corrected actions (Phase H) → policy update via LoRA fine-tuning.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems architecture paper** whose core idea is that agent skills become more effective when they are reified as executable state-action intervention functions rather than remaining as passive textual guidance. The contribution is not a new learning algorithm but a new *interface* between agent experience and agent behavior — one that enables deterministic intervention, structured supervision, and validated self-improvement through a unified PF abstraction.

---

#### The Program Function Interface and Intervention Types

A Program Function (PF) is a typed Python object that inherits from a base `ProgramFunction` class and is registered into the skill library via the `@register_pf(skill_id)` decorator. Each PF exposes exactly two methods that the runtime calls on every agent step:

```
should_activate(step_context: dict, action_type: str, arg: str) -> bool
intervene(step_context: dict, action_type: str, arg: str, teacher=None) -> Intervention
```

The `step_context` dictionary carries all observable state at the current decision point: the original question string (`question`), the current step count (`step_count`), boolean flags for whether the agent has read any document yet (`has_read`), counts of searches and reads performed so far (`search_count`, `read_count`), whether the most recent search returned empty results (`empty_results`), whether contradictory sources have been detected (`contradictory_sources`), the maximum allowed steps (`max_steps`), the history of previous actions (`action_history`), the text of the most recent search results (`last_search_results_text`), all accumulated read contents (`all_read_contents`), and the agent's current reasoning or thought trace (`thought`). The `action_type` is one of `"SEARCH"`, `"READ"`, or `"FINAL"` (web-search domain; math and code use different action spaces). The `arg` is the string argument of the proposed action — the search query for SEARCH, the document index for READ, or the answer text for FINAL.

**`should_activate` is required to be deterministic.** The paper's proposer prompt (Prompt C.2 in Appendix C.3) explicitly forbids LLM calls inside this method: "The PF must be deterministic (NO LLM calls in should_activate)." This constraint is not arbitrary — it ensures that PF triggering is predictable, auditable, and reproducible, which is essential both for debugging intervention behavior and for the mock-execution validation in Phase D of the self-improvement pipeline. A PF that fires non-deterministically on the same state would produce different trajectories on different runs, making signal scoring and training-data construction unstable.

**`intervene` returns a structured `Intervention` object** with exactly five keyword arguments (enforced by the proposer prompt and the validator):

- `type`: an `InterventionType` enum value — `NOOP` (abstain from changing the current decision, still emitting an audit record), `MODIFY_ACTION` (rewrite or refine the next action's type and/or argument), or `INJECT_CONTEXT` (append auxiliary text that the policy will see in the next observation).
- `new_action_type` (optional `str`): the replacement action type if `type == MODIFY_ACTION` — one of `"SEARCH"`, `"READ"`, or `"FINAL"`.
- `new_action_arg` (optional `str`): the replacement action argument.
- `context_text` (str): the text to inject into the next observation if `type == INJECT_CONTEXT`.
- `reason` (str): a human-readable explanation of why the intervention was applied, used for audit logging and signal scoring.
- `skill_id` (str): the registered identifier of the firing skill, used for attribution.

The `Intervention` object is the atomic unit of PF-mediated control. At each step, the harness collects all `Intervention` objects from activated PFs, resolves conflicts (the runtime enforces per-PF rate limits and per-skill caps to prevent oscillation), and applies them to produce the final action `$\tilde{a}_t$` and injected context `$c_t$`. If no PF activates, `$\tilde{a}_t = a_t^{\text{orig}}$` — the base policy's proposed action passes through unchanged. If exactly one PF activates with `MODIFY_ACTION`, the revised action replaces the original. If multiple PFs activate, the harness applies them in priority order (higher `priority` values in the SKILL.md YAML frontmatter go first) and the last writer wins for action modification, while all `INJECT_CONTEXT` interventions are concatenated.

**PF determinism and teacher dependence.** Some PFs declare `needs_teacher = True`, meaning they optionally receive a teacher-model handle (GPT-4o) in their `intervene` method. However, the paper requires that such PFs "must still degrade gracefully when `teacher is None`" (Appendix B.1). For example, `RetrievalFailurePF` (PF B.1 in Appendix B.3) uses the teacher to paraphrase an overly long search query into a concise 5–12 word reformulation when available, but falls back to a deterministic regex-based shortening procedure (`_smart_shorten`) when the teacher is absent. This design ensures that the PF library remains functional even in the PF-only inference setting (Table 5, "PF only" row at 51.0%), where the teacher is unavailable and all `needs_teacher = True` PFs execute their deterministic fallback paths.

**Rate limiting and anti-oscillation guards.** The runtime enforces three classes of budget constraints on PF firing (Appendix B.6): per-PF rate limits (e.g., `_MAX_MODIFY_FIRES = 2` for `MODIFY_ACTION` interventions — a given PF can modify the action at most twice per episode), per-skill caps (e.g., `RetrievalFailurePF` fires at most three times total across all intervention types), and a FINAL-time override cap (`_MAX_FINAL_OVERRIDES = 1` — a handler can flip a FINAL back to SEARCH at most once per episode to prevent FINAL → SEARCH → FINAL → SEARCH oscillation). These constraints prevent PF interventions from dominating the agent loop and ensure that the base policy's own reasoning remains the primary driver of behavior.

**Why code rather than declarative rules?** The paper's choice of Python classes with `should_activate` predicates — rather than, say, declarative trigger-condition rules paired with template-based interventions — is deliberate and motivated by two considerations. First, PFs need access to structured `step_context` fields (e.g., `len(arg.split())`, `token-Jaccard > 0.5` against recent queries, counting the number of possessives in the question to detect multi-hop patterns) that require procedural computation; a purely declarative rule language would need to re-implement these computations. Second, making PFs full Python classes enables the self-improvement pipeline to propose, validate, and version-control them using standard tooling (the proposer generates Python code, the executable validator uses `ast.parse` and mock execution, and the versioning system appends `__v{N}` suffixes). The paper also notes (in Appendix B.5) that a subset of PFs (10 of 26 web-search skills, 2 of 12 code skills) are "prompt-equivalent" — their `intervene` method emits only `INJECT_CONTEXT` with a fixed literal string — meaning they could in principle be replaced by prompt-level phase instructions. The fact that these prompt-equivalent skills contribute only marginal gains (Table 7) reinforces that the substantive gains come from `MODIFY_ACTION` interventions and dynamically-constructed `INJECT_CONTEXT` — both of which require the procedural expressiveness of code.

#### Inference-Time Harness and PF Selection Architecture

The PF harness is not a single monolithic filter but a **five-layer stack** (Appendix B.6) that progressively narrows which PFs reach the system prompt and which ones can fire on any given action. This layered design separates concerns: the master switches control global on/off (e.g., for ablation experiments), the selectors handle relevance ranking and retrieval, the trigger control enforces runtime constraints, the budgets prevent runaway intervention, and the FINAL-time handler mechanism provides a last-resort safety net.

**Layer 1: Master switches.** Six Boolean flags, set once per run, provide coarse-grained control over the entire PF subsystem:
- `skills_enabled`: global kill switch for all skill-related behavior.
- `enable_program_functions`: controls whether PFs execute their `should_activate`/`intervene` methods or are entirely bypassed.
- `enable_skill_handlers`: controls the FINAL-time handler mechanism (described below).
- `enable_prompt_only_skills`: controls whether prompt-equivalent skills inject their fixed context strings.
- `pf_only_mode`: when True, the teacher is unavailable even for `needs_teacher = True` PFs (used for the "PF only" ablation row in Table 5).
- `enable_difficulty_gating`: when True, the teacher assigns a 1–5 difficulty score to each question, and PFs below the corresponding threshold are excluded.

The difficulty gate is the only master switch that varies per-question. It works by asking the teacher for a difficulty score (prompt not shown, but the heuristic fallback uses question length, multi-hop markers, and constraint phrases). This gate is disabled for math problems ("all math problems are uniformly hard," Appendix D.1).

**Layer 2: Selection.** Four cooperating selectors run in sequence, ordered by scope:

1. **`SkillSelector.select()`** ranks the entire library by a composite score: `mode_match * 0.5 + trigger_keyword_match * 0.5`. The `mode_match` term measures how well the skill's declared applicability mode (e.g., "all", "multi-hop", "computation") matches the current question's characteristics. The `trigger_keyword_match` term is lexical overlap between the skill's trigger description and the question text. This produces the initial ranking used at system-prompt build time.

2. **`PFSelector.select()`** runs once per question (not per step) and either delegates to the teacher (which returns top-K relevant skills, with three mandatory PFs always included) or applies a heuristic branching rule: computation-heavy questions get three mandatory PFs; simple factoid questions get four lightweight PFs; multi-hop questions get safe + decomposition + entity-aware PFs. The three mandatory PFs for web-search are `format_extraction_error`, `retrieval_failure`, and `relevant_content_extractor` — these are "always included after PF selection because they normalize the action and observation streams that other skills consume" (Appendix B.4). In other words, these are infrastructure PFs that ensure downstream skills receive clean, well-formed inputs.

3. **Per-observation selector**: trims phase-gated reminders — skills that declare `phases.{post_search, post_read, pre_final}` conditions in their YAML frontmatter only have their `phase_instructions` text rendered when the agent is in the corresponding phase. For example, a `pre_final` phase reminder about verifying evidence is only appended to the system prompt when the agent is about to emit a FINAL action.

4. **Per-step selector**: handles high-priority overrides. Certain PFs with `priority` values near 1.0 can preempt lower-priority PFs at specific decision points.

The teacher-based PF selection prompt (Appendix B.7) explicitly forbids over-selection: "fewer well-targeted PFs is better than many irrelevant ones." The three mandatory PFs are pinned and the teacher cannot drop them. This two-stage filtering — lexical ranking followed by teacher curation — reduces the chance that broad or off-topic skills affect the trajectory.

**Layer 3: Runtime trigger control.** Even after a skill is selected and its phase instructions are injected into the prompt, several conditions must align for the PF's `intervene` method to actually fire on a specific action:

- The PF's own `should_activate` predicate must return `True`. This is the primary gate — it encodes the skill's domain logic for when intervention is warranted.
- For phase-gated reminders, a JSON-condition evaluator checks the `phases.{phase}.conditions` block (e.g., `search_empty`, `no_read_yet`) against the current `step_context`.
- Per-PF rate limits are checked: if a PF has already fired `_MAX_MODIFY_FIRES` times this episode, `should_activate` is not even called — the PF is considered exhausted.
- For FINAL-time handlers (described below), a vote-based aggregator counts how many handlers returned non-None on the same FINAL action. When the count exceeds `handler_vote_threshold` (default 4 for web-search, 3 for math), the FINAL is collectively overridden to SEARCH.

**Layer 4: Budgets.** Three classes of budget caps coexist to prevent runaway resource consumption:

- **Episode-level:** `max_steps` (maximum reasoning turns), `max_search_calls`, `max_read_calls`, and `timeout_seconds`. These terminate the entire episode if exceeded.
- **Prompt-level:** `max_skills_in_prompt` (maximum number of distinct skill IDs whose `system_summary` text can be injected), `max_phase_instructions` (maximum number of phase-gated reminder blocks), and `pre_final_step_threshold` (a PF with `pre_final` phase conditions only activates if the current step index exceeds this threshold — prevents premature intervention on the very first step).
- **Execution-level:** `pf_top_k` (only the top-K highest-priority PFs actually fire even if more are activated), per-PF rate limits (as described above), and `_MAX_FINAL_OVERRIDES`.

**Layer 5: FINAL-time handler mechanism.** This is the most structurally complex intervention surface and is specific to the web-search domain (math and code use single-step rollouts where there is no follow-up step for an override to land on). A handler is a FINAL-time verifier registered in `skill_handlers.py` that inspects the agent's proposed FINAL action and its accumulated evidence, and can return a non-None value indicating that the FINAL should be flipped back to SEARCH with a specific query. Handlers are distinct from regular PFs in two ways: (a) they only fire on `action_type == "FINAL"` actions, and (b) they operate through a collective voting mechanism rather than individual action modification. Specifically:

- Each handler is a function `handle(ctx, action_type, arg) -> Optional[str]` that returns either `None` (abstain) or a string representing a corrected SEARCH query.
- When multiple handlers return non-None on the same FINAL, their results are aggregated by a vote counter.
- If the vote count exceeds `handler_vote_threshold` (4 for web-search), the FINAL is overridden to `SEARCH(corrected_query)` where `corrected_query` is the majority-voted query.
- To prevent infinite loops: `_MAX_FINAL_OVERRIDES = 1` caps the number of FINAL → SEARCH overrides per episode. The first override fires, the agent performs the additional search, and any subsequent FINAL action is accepted as-is even if handlers would still vote to override.

Eight LLM-assisted handlers are active in the full HASP configuration (Table 5, "Full HASP-Intervention (Infer.)"): these include verifiers for source attribution, evidence sufficiency, and answer completeness. The presence of these handlers is the primary reason that the "Full" configuration (56.2%) outperforms "PF only" (51.0%) in Table 5 — the handlers catch FINAL-time errors that step-level PFs miss because they only fire at the decision point immediately preceding termination.

**The intervention operator `$\Gamma$`.** The formal intervention operator that the harness applies at each step is:

$$\Gamma(s_t, a_t^{\text{orig}}, \mathcal{R}(s_t)) = (\tilde{a}_t, c_t, \kappa_t)$$

where `$s_t$` is the current state (the full `step_context` dictionary), `$a_t^{\text{orig}}$` is the base policy's proposed action, `$\mathcal{R}(s_t) \subseteq \mathcal{M}$` is the set of retrieved and selected PFs, `$\tilde{a}_t$` is the final action after PF intervention (potentially identical to `$a_t^{\text{orig}}$` if no PF activates), `$c_t$` is the concatenated injected context from all `INJECT_CONTEXT` interventions (empty string if none), and `$\kappa_t$` is metadata recording which PFs fired and their intervention modes.

**What it computes:** the operator evaluates `should_activate(ctx, action_type, arg)` for each `$pf \in \mathcal{R}(s_t)$`, collects the `Intervention` objects from all returning `True`, resolves conflicts (last-writer-wins for `MODIFY_ACTION`, concatenation for `INJECT_CONTEXT`, priority ordering), and emits the revised action/context/metadata tuple.

**Why this form:** separating the policy's action proposal from PF-mediated correction means that the base model never needs to "know" that a PF might override its decision. The policy simply proposes what it would do; the harness transparently corrects when necessary. This preserves the base model's generation distribution (the proposal `$a_t^{\text{orig}}$` is drawn from `$\pi_\theta$` without modification) while ensuring that the *executed* action `$\tilde{a}_t$` is safer. The alternative — having the policy itself condition on the PF library and attempt to follow skill guidance textually — is exactly what the Prompt-Only Skills baseline does, and it achieves only 20.5% accuracy (Table 2) because the model can attend to or ignore the advice probabilistically.

#### The Structured Signal Scoring System

Each PF activation produces a structured record `$e_t = (s_t, a_t^{\text{orig}}, \tilde{a}_t, c_t, \kappa_t, \Delta_t)$`, where `$\Delta_t$` is the observed effect of the intervention (the result of executing `$\tilde{a}_t$` and any subsequent environment feedback). These records are the raw material for post-training supervision, but they are not equally useful: some interventions fire at the right time with the right mechanism and produce valid repairs that improve the final outcome, while others fire unnecessarily, use inappropriate intervention types, produce malformed actions, or fail to improve — or even degrade — downstream performance.

To distinguish these cases, HASP scores each intervention along four orthogonal dimensions, producing a vector `$z_t = (t_t, m_t, q_t, o_t)$` and aggregating them into a scalar:

$$A_t = \lambda_t \cdot t_t + \lambda_m \cdot m_t + \lambda_q \cdot q_t + \lambda_o \cdot o_t$$

where `$(\lambda_t, \lambda_m, \lambda_q, \lambda_o) = (0.15, 0.10, 0.25, 0.50)$` are the default weights reported in the paper (Section 3.2, footnote 1).

**What it computes:** a weighted sum of four scalar scores, each in `$[0, 1]$`, representing distinct quality dimensions of a PF intervention. The result is a single scalar `$A_t \in [0, 1]$` where 1.0 represents a perfect intervention (right time, right mechanism, valid repair, improved outcome) and 0.0 represents an intervention that was actively harmful or irrelevant.

**Why this form:** a single scalar (e.g., "did the episode succeed?") would conflate interventions that were unnecessary but harmless with interventions that were necessary and effective. The four-dimensional decomposition separates *when* the PF fired (timing), *how* it intervened (modality), *whether the repair was valid* (correctness), and *whether it ultimately helped* (outcome). The heavy weight on outcome (0.50) reflects the paper's pragmatic orientation — an intervention that produces a correct final answer is good even if it fired suboptimally — while the non-zero weights on timing (0.15), modality (0.10), and correctness (0.25) ensure that the system prefers interventions that are well-timed, well-formed, and locally valid, not just lucky. The trajectory-level score `$A(\tau) = T^{-1} \sum_{t=1}^T A_t$` averages per-step scores across the episode, so an episode with one excellent intervention and nine unnecessary ones receives a lower score than one with ten moderately good interventions.

Each of the four coarse signals is itself a weighted aggregation of finer sub-signals, described in detail in Appendix E:

**Timing (`$t_t$`).** This signal captures whether the intervention fired at an appropriate decision point. A step is defined as "risky" (on the proposed action, before PF intervention) if it is a FINAL with no prior READ, a FINAL at `step_count < 3`, or a SEARCH after `empty_results`. The four sub-signals are:
- `s1.tp` (+0.25): true positive — the step was risky and any PF activated.
- `s1.fp` (−0.10): false positive — the step was not risky but a PF still activated.
- `s1.fn` (−0.10): false negative — the step was risky but no PF activated.
- `s1.phase` (+0.05): normalized step index, rewarding earlier interventions (closer to step 0).

The asymmetric weighting (positive reward for correct activation, smaller penalty for false activations, penalty for missed risky steps) reflects the paper's design philosophy: it is better to intervene when it might help and occasionally be wrong than to miss a risky step entirely.

**Modality (`$m_t$`).** This signal captures whether the intervention used the appropriate mechanism. The two currently active sub-signals are:
- `s2.pre_action` (+0.35): a `MODIFY_ACTION` fired before the action ran.
- `s2.post_obs` (+0.35): an `INJECT_CONTEXT` fired after the observation.

Two reserved slots (`s2.pre_reasoning` and `s2.post_action`) carry zero weight but are retained for future intervention types, so that the scoring system does not need to be reconfigured when new PF capabilities are added. The symmetry of the weights (both +0.35) means the system does not a priori prefer action modification over context injection — the appropriateness of the mechanism depends on the failure pattern, and the downstream correctness and outcome signals will penalize modality mismatches.

**Correctness (`$q_t$`).** This signal captures whether the intervention produced a valid repair, independent of downstream effects. The three sub-signals are:
- `s3.syntactic` (+0.20): the action type is valid (one of SEARCH/READ/FINAL) and the argument is non-empty.
- `s3.semantic` (+0.50): teacher-judged step quality, with a heuristic fallback (0.7 for a FINAL → READ rescue, 0.5 for other modifications, 0.3 otherwise). This is the heaviest correctness sub-signal because it requires semantic understanding of whether the revised action makes sense given the question and evidence.
- `s3.domain` (+0.30): domain-specific quality checks (e.g., for web-search, whether the revised query is not too long; for math, whether the solution step is algebraically valid). Defaults to 0 when no domain checks are registered.

**Outcome (`$o_t$`).** This signal captures whether the intervention ultimately helped, and it carries the most weight (0.50) because it is the only signal anchored to ground-truth. The four sub-signals are:
- `s4.local` (+0.40): immediate transition quality — 0.8 for FINAL → READ (the PF forced the agent to read before finalizing), 0.7 for FINAL → SEARCH (redirected to a more productive search), 0.5 for SEARCH → SEARCH rewrite, 0.3 for any other modification, 0 otherwise.
- `s4.downstream` (+0.40): episode exact-match (EM) success — the only signal that directly uses the ground-truth answer. An intervention is credited with the full downstream weight if the episode ultimately produces the correct answer.
- `s4.cost` (−0.10): penalty for long episodes, computed as `clip((T - 15) / 10, 0, 1)`. Episodes longer than 15 steps are linearly penalized, capping at 1.0 penalty for episodes ≥ 25 steps.
- `s4.side_effect` (−0.10): penalty when a PF modified the action but the episode still failed. This prevents the system from crediting interventions that were locally plausible but ultimately ineffective.

**Skill-level reward.** For training the skill *author* (Phase H of the self-improvement pipeline, which generates PF proposals), there is an additional reward that is not step-level:

$$r_{\text{skill}} = Q_{\text{skill}} + \lambda \cdot \Delta\text{EM}_{\text{val}}$$

where `$Q_{\text{skill}} = 0.25 Q_{\text{concept}} + 0.20 Q_{\text{trigger}} + 0.20 Q_{\text{intervene}} + 0.20 Q_{\text{exec}} + 0.15 Q_{\text{val}}$` is the teacher's five-dimensional review score (from Phase E), `$\Delta\text{EM}_{\text{val}}$` is the change in validation exact-match after adding the skill, and `$\lambda = 0.5$` by default.

**What it computes:** the teacher-assessed quality of the proposed skill plus half the observed validation improvement. A skill that the teacher rates highly but that does not improve validation EM gets partial credit; a skill that the teacher is skeptical about but that demonstrably helps gets partial credit; a skill that gets both high review scores and positive validation impact gets full credit.

**Why this form:** the linear combination ensures that both expert judgment and empirical evidence contribute to the reward. Relying solely on `$\Delta\text{EM}_{\text{val}}$` would incentivize skills that overfit to the validation set; relying solely on `$Q_{\text{skill}}$` would incentivize skills that sound good to the teacher but may not work in practice. The weight `$\lambda = 0.5$` reflects a slight preference for teacher judgment (since `$Q_{\text{skill}} \in [0, 1]$` and `$\Delta\text{EM}_{\text{val}}$` is typically much smaller, the half-weight on the latter partially compensates for scale differences).

#### Post-Training Recipes: Internalizing PF-Guided Interventions

The four-dimensional signal system provides the supervision interface, but it does not prescribe a specific training algorithm. HASP defines three post-training recipes — SFT, rejection sampling (RS), and on-policy distillation (OPD) — that all consume the same PF-derived signals but differ in how they select and weight training data. All three use LoRA fine-tuning (rank 16, `$\alpha = 32$`, bf16 precision, gradient checkpointing) on Qwen2.5-7B-Instruct, varying only the post-training objective and data composition.

**Main recipe: PF-guided rejection sampling (RS).** This is the primary training method and the one used in the strongest closed-loop variant, HASP-Evolve + RS. Given `$N$` sampled trajectories `$\{\tau_i\}_{i=1}^N$` from the current policy (with PFs active), HASP scores each trajectory using a composite:

$$\text{Score}(\tau_i) = \beta_1 \cdot \text{TaskSuccess}(\tau_i) + \beta_2 \cdot A(\tau_i)$$

where `$\text{TaskSuccess}(\tau_i) \in \{0, 1\}$` is the episode's exact-match success (1 if the final answer matches gold, 0 otherwise), `$A(\tau_i) = T^{-1} \sum_{t=1}^T A_t$` is the trajectory-level average PF intervention score (defined above), and `$\beta_1, \beta_2$` are blending weights (not explicitly reported in the paper, but the rejection sampling filter uses `min_score = 0.15` on a composite `0.7 * EM + 0.2 * F1 + 0.1 * StepEconomy` — Appendix D.4 — rather than `require_exact_match = True`).

**What it computes:** only trajectories that exceed a quality threshold are retained for training. The threshold is not binary (correct/incorrect) but scalar, allowing trajectories that failed to produce the right final answer but demonstrated good intermediate PF-guided behavior to contribute to training. This is a deliberate departure from standard rejection sampling (which typically filters on final correctness alone) — HASP also prefers "trajectories whose intermediate decisions better match PF-guided correction: interventions should occur at appropriate states, use suitable modes, and lead to valid repairs with positive downstream effects" (Section 3.2).

**Why this form:** standard rejection sampling that only keeps perfect-EM trajectories would discard many episodes where the agent was close to correct but made a single late-stage error — exactly the episodes where PF interventions provide the most informative supervision. By blending task success with intervention quality, HASP retains trajectories that are *behaviorally* correct even if not *terminally* correct, providing richer training data. The paper's results support this choice: on web-search reasoning, RS achieves 59.3% (fixed library) and 60.3% (evolved library) compared to SFT's 56.8% and 58.5% (Table 4), indicating that quality-filtered trajectory selection outperforms training on all PF-corrected actions equally.

The RS recipe uses `k = 2` rollout groups, temperature 0.9, top-p 0.95, maximum 5 reasoning steps, and maximum 3 search calls per episode (Appendix D.4). Training runs for 8 epochs per iteration (for open-loop V1) or 8 epochs per phase (for closed-loop V2).

**Variant 1: Supervised fine-tuning on corrected actions (SFT).** This simpler baseline converts each PF intervention record into a weighted supervised target:

$$\mathcal{L}_{\text{SFT}} = -\sum_t w_t \log \pi_\theta(\tilde{a}_t \mid s_t)$$

where `$w_t$` is a monotone function of the intervention quality `$A_t$` (the paper does not specify the exact monotone function, but the SFT data construction in Appendix D.6 indicates that `sample_weight` carries the per-step reward, and the SFT target is the PF-corrected action `$\tilde{a}_t$`).

**What it computes:** a weighted negative log-likelihood over PF-corrected actions. Steps where PFs intervened with high-quality repairs (high `$A_t$`) receive higher weight; steps where PFs did not activate or produced low-quality interventions receive lower weight. The model is trained to directly predict what the PF-corrected action would have been, given the state.

**Why this form:** SFT is the simplest way to internalize PF corrections — it directly teaches the model to produce corrected actions without needing to run PFs at inference time. However, it trains on all corrected actions equally (modulated only by the weight `$w_t$`), including those from trajectories that ultimately failed. This explains why SFT underperforms RS (Table 4: 56.8% vs. 59.3% on web-search with fixed library) — SFT cannot distinguish between a perfect intervention in a failed trajectory and the same intervention in a successful one, while RS explicitly prefers trajectories that succeed.

The SFT recipe uses learning rate `$1 \times 10^{-5}$`, 10 epochs (open-loop) or refreshed phases (closed-loop), and trains on all PF-corrected steps regardless of trajectory outcome (Appendix D.3).

**Variant 2: On-policy distillation (OPD).** This method addresses the distribution-shift problem of SFT and RS: both train on states visited by the policy *with PFs active*, but the trained model will eventually be deployed *without* PFs (or with a different set of PFs), and its own state-visitation distribution will be different. OPD rolls out the current student policy, keeps PFs active on failure-prone steps to produce corrected targets, but trains on the student's *own* states:

$$\mathcal{L}_{\text{OPD}} = -\sum_t \hat{w}_t \log \pi_\theta(\tilde{a}_t \mid s_t)$$

where `$\hat{w}_t$` reflects intervention quality under the *current* policy (the `sample_weight` from Layer 2 of the data construction pipeline, Appendix D.6).

**What it computes:** the same weighted negative log-likelihood as SFT, but the states `$s_t$` are drawn from the current student's own rollout distribution rather than from a fixed pool. At each training iteration, the student generates trajectories (with PFs active), PFs intervene and produce corrected actions `$\tilde{a}_t$`, and the student is trained to predict those corrected actions from its own states. This creates a feedback loop: as the student improves and makes fewer errors, the distribution of states where PFs fire shifts, and the training data shifts accordingly.

**Why this form:** OPD trains on the states the student *actually visits*, which is the right data distribution for eventual deployment (where PFs may be absent or less aggressive). However, this same property makes OPD less stable under library evolution: when the skill library changes, both the visited states and the intervention targets change simultaneously, creating a moving-target problem. The paper's results confirm this instability: on web-search reasoning with fixed library, OPD achieves the strongest result (62.5%, Table 4), but with closed-loop evolution, OPD drops to 56.7% — below even the fixed-library SFT baseline (56.8%). The paper attributes this to OPD's supervision being "more coupled to the current policy distribution" (Section 4.1), making it sensitive to the non-stationarity introduced by library updates.

The OPD recipe uses learning rate `$5 \times 10^{-6}$`, 10 epochs (open-loop) or 5 epochs per phase (closed-loop), and GPT-4o as the teacher providing corrected trajectories with active PF interventions (Appendix D.3).

**Training dynamics analysis (Figure 3, Appendix H).** The paper includes detailed training-dynamics plots that illustrate the behavioral differences between these three recipes:

- **SFT** (solid blue line in Figure 3): rapidly lowers training loss and increases correction-aligned token accuracy, matching its "stable but modest" gains. The model quickly learns to reproduce PF-corrected actions but plateaus because it cannot distinguish between high-quality and low-quality corrections.
- **RS** (solid green line): maintains high correction-aligned accuracy with relatively low policy entropy, consistent with selecting only task-successful *and* PF-aligned trajectories. The entropy suppression suggests that RS produces a more focused, less exploratory policy — which is appropriate when the PF library already encodes the desired behavioral corrections.
- **OPD** (solid red line): shows slower, less monotonic alignment in correction-aligned accuracy but reaches the strongest fixed-library result at 62.5% (Table 4). The non-monotonic pattern reflects the on-policy feedback: as the student improves, the states become harder (fewer easy corrections), so accuracy can temporarily decrease before the student adapts.
- **Closed-loop variants** (dashed lines in Figure 3): the vertical dotted markers at the library-refresh points show clear discontinuities in all three signals — loss spikes, token accuracy dips, and entropy increases — indicating that injecting new PFs into the library changes the target distribution. RS handles this non-stationarity best (the dashed green line recovers quickly after the refresh), while OPD struggles (the dashed red line shows persistent instability).

#### Self-Improving Evolution Pipeline (Phases A–H)

The self-improving pipeline is the offline counterpart to inference: where inference runs the agent against a fixed library, self-improvement grows that library. Each epoch revisits residual failures from the current checkpoint and runs an eight-phase pipeline (Algorithm 1 in Appendix C). The paper distinguishes two variants: **full evolution** (used in E4, HASP-Evolve + SFT), which runs the complete pipeline including teacher review and takes approximately one hour per evolve cycle; and **lite evolution** (used in E5/E6), which samples 20 failed trajectories, asks the student vLLM checkpoint for at most three skill proposals, applies `ast.parse` compile checks and skill-id deduplication, and writes the result to `generated/` — with no teacher API calls, no clustering, no review, and no gradient computation — taking approximately 5% of the wall-clock time while yielding "most of the library-growth benefit" (Appendix D.5).

I will trace one full epoch for the full evolution case, since understanding the complete pipeline clarifies why the filtering ablations in Table 5 produce such stark differences (60.3% with full filtering vs. 36.3% with no filtering).

**Phase A: PF-aware rollout on the seed split.** The current student policy `$\pi_\theta$` (the latest LoRA-adapted checkpoint) generates trajectories on the seed split with the current PF library `$\mathcal{M}_r$` active. An optional two-stage prefilter cheaply identifies failing samples first, then concentrates the expensive PF-aware rollout on those. The result is a set of trajectories `$\text{Traj}$`, each annotated with per-step PF intervention records `$e_t$`. This phase is expensive because it runs the full ReAct loop with teacher-augmented PFs active on every step; the lite evolution variant reduces cost by sampling only 20 trajectories.

**Phase B: Failure signal detection and clustering.** This phase uses two parallel detectors to abstract failure trajectories into reusable categories.

The **heuristic detector** applies twelve hand-coded rules against every failed trajectory (Appendix C.2):
- `premature_final`: trajectory shorter than three steps (the agent finalized without sufficient exploration).
- `repeated_search`: queries with token-Jaccard > 0.8 against recent queries (the agent is stuck in a loop).
- `no_read_before_final`: the agent emitted a FINAL action without any prior READ.
- `query_too_broad` / `query_too_narrow`: search query length outside empirically determined bounds.
- `wrong_entity_focus`: answer/gold token overlap < 30% (the agent focused on the wrong entity).
- `reasoning_hallucination`: the final answer's content tokens are < 30% grounded in read document content (the agent fabricated information).
- `format_mismatch`, `partial_answer`, `contradictory_evidence_ignored`, `excessive_steps_no_progress`, `pf_override_harmful`: additional structural and content-level failure modes.

The **LLM detector** asks the teacher (GPT-4o) to abstract each failed trajectory into a reusable category (Prompt C.1 in Appendix C.2). The teacher receives the question, gold answer, agent's predicted answer, and the truncated trajectory, and returns a JSON object with `category` (snake_case identifier), `abstraction` (one-sentence description), `trigger` (when in a ReAct step the failure manifests), and `intervention_hint` (what a PF should do to prevent it). The generation runs at temperature 0.3 with `max_tokens = 400`.

Heuristic and LLM patterns are deduplicated independently using token-Jaccard ≥ 0.5 within the same category, then bucketed into six broad existing-skill groups for novelty scoring. Buckets with `min_cluster_size` < 3 are dropped. Clusters with novelty ≥ 0.3 are flagged `is_new_category` and prioritized for proposal in Phase C.

**Phase C: Candidate PF proposal.** For each surviving cluster, the student model authors a candidate skill consisting of (i) a `SKILL.md` document with YAML frontmatter, trigger conditions, intervention design, and concrete examples; and (ii) a `ProgramFunction` subclass implementing `should_activate` and `intervene`. The proposer prompt (Prompt C.2 in Appendix C.3) explicitly constrains the keyword arguments of the `Intervention` constructor and forbids LLM calls inside `should_activate`. Generation runs at temperature 0.7, capped at 5 candidates per epoch (`max_candidates_per_epoch`). The proposal is rate-limited "so the library grows slowly and remains controllable over many rounds" (Appendix C.7).

**Phase D: Executable validation.** Each candidate is wrapped in a sandbox preamble (mocked `InterventionType`, `Intervention`, `ProgramFunction`, and `register_pf`) and subjected to four sequential checks:

1. **Syntax:** `ast.parse` — the code must be valid Python.
2. **Interface:** the class must inherit from `ProgramFunction` and define both `should_activate` (signature: `(self, ctx, action_type, arg) -> bool`) and `intervene` (signature: `(self, ctx, action_type, arg, teacher=None) -> Intervention`).
3. **Mock execution:** the validator constructs three mock `step_context` dictionaries covering different regimes — early-step/no-read (step 1, no reads), mid-step/has-read (step 5, two reads), and late-step/empty-results-with-contradictions (step 12) — and invokes `should_activate` and `intervene` on each with each action type (SEARCH, READ, FINAL), for a total of 9 invocations per candidate. Any runtime exception fails this check.
4. **Return type:** the `intervene` method must construct a valid `Intervention` object.

The validator returns `Q_exec ∈ [0, 1]`. A candidate with `Q_exec < 0.3` is hard-rejected regardless of teacher review.

**Phase E: Teacher five-dimensional review.** The teacher receives the candidate as four blocks — header (skill_id, name, version, priority, error_category, applicable_modes, applicable_phases), trigger conditions (the `should_activate` logic in plain language), intervention description (the `intervene` behavior in plain language), and the full SKILL.md plus PF code — along with the source failure cluster's metadata. It scores five dimensions on `[0, 1]` (Prompt C.3 and C.4 in Appendix C.5):

1. **Concept (`$Q_{\text{concept}}$`):** Is this a real, recurrent failure type? Is it generalizable, not a single-case patch? Is it clearly distinct from existing skills?
2. **Trigger (`$Q_{\text{trigger}}$`):** Is `should_activate` specific and deterministic? Does it depend on available `step_context` fields? Is it neither too broad (many false positives) nor too narrow (many false negatives)?
3. **Intervention (`$Q_{\text{intervene}}$`):** Does `intervene` appropriately address the failure? Could it cause harmful side effects? Is the intervention proportional?
4. **Executability (`$Q_{\text{exec}}$`):** Does the code follow the `ProgramFunction` interface? Would it import without errors? Are return types correct?
5. **Validation Utility (`$Q_{\text{val}}$`):** Will this likely reduce the target failure type? Will it transfer to unseen questions? Will it interact well with existing PFs?

The composite is `$Q_{\text{skill}} = 0.25 Q_{\text{concept}} + 0.20 Q_{\text{trigger}} + 0.20 Q_{\text{intervene}} + 0.20 Q_{\text{exec}} + 0.15 Q_{\text{val}}$`. The decision is taken in priority order: hard reject if `Q_exec < 0.3`; otherwise, the teacher's literal `DECISION` line if present (`ACCEPT / REVISE / REJECT`); otherwise, threshold fallback: `Q_skill ≥ 0.60 ⇒ accept`, `≥ 0.42 ⇒ revise`, else reject. Two further thresholds, `new_group_threshold = 0.75` and `same_group_threshold = 0.60`, gate library admission for entirely new categories versus refinements of existing ones.

**Why this multi-dimensional review:** a single "is this skill good?" score would conflate different failure modes — a skill might have an excellent concept but a terrible trigger (overly broad, firing constantly), or a perfect trigger but a useless intervention. The five-dimensional decomposition ensures that each aspect is judged independently, and the composite weighting (highest on concept and executability, lowest on validation utility which is hardest to judge without running experiments) reflects the paper's priorities: a skill must first be conceptually sound and technically executable; trigger and intervention quality are next; and validation utility, which is speculative without empirical testing, receives the lowest weight.

**Phase F: Library update with versioning.** Accepted candidates are appended to `generated/{skill_id}__v{N}/SKILL.md`, and their PF code is appended to `dynamic_program_functions.py`. When a candidate matches an existing base `skill_id`, it is accepted as the next version (`__v{N+1}`); the old version remains on disk for trajectory replay but never fires (the runtime loads only `skill_ids_latest` — the highest version per base id). `max_library_size = 50` caps the total active skill count. `library_history.json` records every per-skill decision and review score, enabling closed-loop runs to reconstruct the gated decision tree without rerunning rollouts.

The versioning system is critical for reproducibility and debugging. Because old PFs remain on disk but are never loaded, researchers can replay a trajectory with any historical library state by loading the corresponding `skill_ids_latest` snapshot. The paper leverages this for the "No evolution" ablation in Table 5 (which freezes the library at the seed snapshot) and the filtering ablations (which selectively enable/disable the Exec and Teach gates).

**Phase G: Signal scoring.** Every step in every trajectory from Phase A is scored using the four-signal system (Section 3.2 / this document's signal section), producing per-step scores `$A_t$` and trajectory-level scores `$A(\tau)$`. This phase is computationally lightweight — the signals are computed from already-recorded intervention metadata and episode outcomes — and produces the scalar weights that drive the training-data construction in Phase H.

**Phase H: Training-data construction.** Scored trajectories are rendered into one of two objectives:

- **Objective A ("use PFs"):** Emits SFT, DPO, and prompt-only training files. The SFT target is the PF-corrected action `$\tilde{a}_t$`; the DPO chosen/rejected pair is restricted to steps with `was_modified = True` (i.e., the chosen action is the PF-corrected one, the rejected action is the original uncorrected one); `sample_weight` carries the per-step reward `$A_t$`.
- **Objective B ("evolve"):** Emits SFT and DPO files for the skill-authoring task, where the target is the candidate's `SKILL.md` + PF code, and the reward is `$r_{\text{skill}} = Q_{\text{skill}} + 0.5 \cdot \Delta\text{EM}_{\text{val}}$`. This objective trains the student to become better at proposing new PFs in future evolution cycles.

**Epoch structure and convergence.** The closed-loop runs span 5 epochs for web-search and 3 epochs each for math and code (Appendix I.2). The paper's evolution-dynamics analysis (Appendix F.4) tracks three quantities across epochs: the per-round success rate of candidate proposals (fraction passing executable validation), the number of skills accepted into the library after teacher review, and the cumulative library size. The key observation: "the acceptance rate stays high in early rounds and decays gradually as the seed library already covers the most frequent residual failures, indicating that the system does not over-grow the library when easy failures have been absorbed." The library size stays well below the hard cap of 50 even by the final epoch — the bottleneck is novelty (are there genuinely new failure patterns to encode?) rather than capacity.

#### Domain-Specific Library Instantiations

While the PF interface is universal, the concrete skills, their activation predicates, and their intervention surfaces differ substantially across domains. The paper instantiates three skill libraries that "share the same loader, registry, and intervention dispatcher; only the markdown content and `should_activate` predicates differ across domains" (Appendix B.4).

**Web-search library (16 PF skills + 8 prompt-only skills).** The web-search domain has the richest PF library because multi-step ReAct loops create many opportunities for structured intervention. The sixteen PF skills carry deterministic activation rules plus registered handlers. Four PFs use teacher assistance: `retrieval_failure` (reformulates overly long or failed search queries), `format_extraction_error` (normalizes malformed search or read actions), `reasoning_error` (detects and corrects logical errors), and `answer_confidence_guard` (verifies answer confidence before finalization). Three skills are always included as infrastructure PFs: `format_extraction_error`, `retrieval_failure`, and `relevant_content_extractor` — these "normalize the action and observation streams that other skills consume" (Appendix B.4).

The eight prompt-only skills cover patterns like `decompose_complex_question` (injects a decomposition hint when the question has multi-hop structure), `adversarial_distraction` (warns about conflicting sources), `negation_oversight` (reminds about negations in the question), and `answer_completeness` (warns when the answer appears incomplete for multi-part questions). As noted in Appendix B.5, 10 of the 26 web-search skills satisfy the prompt-equivalent criterion — they emit only `INJECT_CONTEXT` with fixed literal strings — but their marginal contribution is small (Table 7: the effect of adding prompt-equivalent skills is mixed and small across datasets, ranging from −3.5 to +3.5).

**Math library (all PF-style, organized into five groups).** The math domain collapses to single-step rollouts (`max_steps = 1`), so there is no follow-up step for a `MODIFY_ACTION` to land on. Instead, math PFs operate through two surfaces: (a) `system_summary` text injected into the system prompt at episode start, and (b) a `pre_final` verifier hook that checks the FINAL action before it is emitted. The five groups are:

- **Algebraic/arithmetic correctness:** `algebraic_sign_error` (detects sign errors in algebraic manipulations), `arithmetic_slip` (catches arithmetic mistakes), `simplification_incomplete` (checks if an expression can be further simplified).
- **Domain/constraint:** `boundary_violation` (checks if the answer violates problem constraints), `units_dimension_mismatch` (verifies dimensional consistency).
- **Reasoning coverage:** `case_incompleteness` (verifies that all cases in a case analysis are covered), `overgeneralization` (checks if a formula or pattern is applied outside its domain of validity), `proof_step_gap` (detects logical leaps).
- **Substitution/verification:** `substitution_invalid` (checks if the answer correctly substitutes into the original equation), `verification_missing` (the highest-priority skill at 0.90, always active on `pre_final`, forces the agent to plug its candidate answer back into the original problem and verify).
- **Output format:** `final_format_error` (ensures the answer is in the expected format).

Skill B.2 in Appendix B.3 shows the full specification for `verification_missing`, which is representative of the math PFs. Its `should_activate` is trivially True (it fires on every `pre_final` step because verification is always important), and its `intervene` forces the agent to substitute its candidate answer back into the original equation before allowing the FINAL to proceed.

**Code library (12 PFs, most operating as static-analysis hooks).** The code domain is the strictest cross-domain transfer test because the action space collapses to a single FINAL emission (the generated code), READ is unavailable, and the only PF surface is regex-based static analysis on the emitted code body. Code PFs never `MODIFY_ACTION` — auto-patching student code is judged "too risky" (Appendix B.4) — and instead return either an `INJECT_CONTEXT` hint (pointing out a specific issue in the generated code) or a `NOOP` audit record (logging that the check passed). The twelve skills cover:

- **Complexity:** `code_complexity_analysis` (warns about unnecessarily complex algorithms), `code_data_structure_choice` (suggests more appropriate data structures).
- **Bounds and indexing:** `code_off_by_one` (catches ±1 errors in loop bounds or indices), `code_string_index_safety` (checks for potential string index out-of-range errors), `code_edge_cases` (reminds the model to consider edge cases like empty inputs, all-equal values, or maximum constraints).
- **Recursion and numerics:** `code_recursion_depth` (warns about unbounded recursion), `code_float_precision` (checks for floating-point comparison issues).
- **I/O and format:** `code_input_parsing` (verifies that stdin parsing handles all specified input formats), `code_output_format` (ensures output matches the expected format).
- **Verification:** `code_test_walkthrough` (reminds the model to mentally trace sample inputs through its code before finalizing), `code_negative_handling` (checks for proper handling of negative numbers or edge cases).

Two of the 12 code PFs are prompt-equivalent (`code_negative_handling`, `code_test_walkthrough`), meaning their behavioral effect comes entirely from the `SKILL.md` text being injected into the system prompt rather than from any runtime static analysis (Appendix B.5, Table 9). The remaining 10 PFs perform actual regex-based checks on the generated code body — for example, `code_edge_cases` scans for branching logic on numeric inputs and injects a hint if the agent's branches do not cover the "all inputs equal" case (as in the coding case study in Appendix G.4, where the baseline missed the `a == b == c` branch and the PF's hint prompted the agent to add it).

**Cross-domain transfer costs.** The PF interface transfers mechanically across domains (the same dispatcher serves web-search, math, and code without modification), but the *effort* of building a domain-specific PF library is not uniform. The web-search library requires the most design effort because multi-step rollouts enable rich intervention surfaces (`MODIFY_ACTION`, `INJECT_CONTEXT`, FINAL-time handlers, phase-gated reminders); the math library requires careful design of pre_final verification hooks but no step-level action modification; the code library is the most constrained, with all PFs reduced to audit NOOPs or static-analysis hints. The paper's coding results (Table 3) reflect this constraint: inference-time PFs improve coding pass@1 from 60.8% (Qwen2.5-7B-Instruct raw) to 63.4% (PF-only) to 68.7% (with teacher), which is a meaningful gain but smaller than in the web-search domain where the richer intervention surface enables more direct behavioral correction.

#### Summary of Design Choices and Their Justifications

- **Python classes with `should_activate`/`intervene` over declarative rules:** enables procedural computation over structured `step_context` fields (e.g., token-Jaccard, query length, entity overlap) that a declarative rule language would need to re-implement; also enables the self-improvement pipeline to propose, validate, and version-control PFs using standard tooling (`ast.parse`, mock execution, versioned file storage).

- **Deterministic `should_activate` (no LLM calls):** ensures predictable, auditable, and reproducible triggering; essential for mock-execution validation in Phase D and for signal scoring stability across runs.

- **`MODIFY_ACTION` vs. `INJECT_CONTEXT` as the two intervention types:** action modification provides direct, non-negotiable control over the next executed action; context injection provides softer guidance that the policy must still interpret. The paper's intervention statistics (65.1% action-level, 34.9% context-level; Section 4.2) show that both are used substantially, with action modification dominant because it addresses the most consequential failures (premature FINAL, overly long queries).

- **Rate limiting and anti-oscillation guards (`_MAX_MODIFY_FIRES = 2`, `_MAX_FINAL_OVERRIDES = 1`, per-skill caps):** prevents PFs from dominating the agent loop and preserves the base policy's agency. Without these constraints, a PF could fire on every step, effectively replacing the policy with a hard-coded script.

- **Four-dimensional signal scoring (timing, modality, correctness, outcome) with outcome heaviest (0.50):** captures distinct quality dimensions that a single scalar (e.g., "did the episode succeed?") would conflate, while still anchoring the overall score to ground-truth success. The signal ablation in Table 5 shows that removing any single dimension causes a 7.8–15.5 point drop, confirming that all four dimensions contribute independently.

- **Rejection sampling as the primary training recipe:** balances the stability of training only on high-quality trajectories with the richness of training on intermediate states that demonstrate good PF-guided behavior. The paper's results (Table 4) show RS outperforming SFT (which trains on all interventions equally) and being more stable than OPD (which is sensitive to distribution shift under library evolution).

- **Strict two-gate filtering for skill library evolution (executable validation + teacher review):** the filtering ablation in Table 5 is the paper's most dramatic negative result — unfiltered evolution drops performance from 60.3% to 36.3%, a 24-point collapse. This is the central empirical justification for the paper's claim that "self-improvement is useful only when library evolution is tightly controlled" (Appendix C.8). The executable gate catches interface failures (ill-typed PFs, broken imports), while the teacher gate catches conceptual failures (overly specific triggers, harmful interventions) — both gates are necessary, as removing either alone causes an 11.5–13.1 point drop.

- **Versioning with `__v{N}` suffixes and `skill_ids_latest`:** enables library growth without discarding history, supports trajectory replay with any historical library state, and prevents the skill count from growing unboundedly (only the latest version per base ID is active, regardless of how many versions have been proposed).

## 4. Key Insights and Innovations

### Innovation 1: Reifying Skills as Executable State-Action Intervention Functions — Closing the Advisory Gap

The paper's most fundamental intellectual move is not any specific PF design or training recipe, but rather the **reification of agent skills from passive text into active, executable code**. Prior to HASP, the dominant paradigm for reusing agent experience — spanning Reflexion (Shinn et al., 2023), ExpeL (Zhao et al., 2024), SKILL0 (Lu et al., 2026), SkillRL (Xia et al., 2026), and SAGE (Wang et al., 2025) — treated skills as natural-language artifacts: textual reflections, experiential lessons, in-context demonstrations, or reward-shaping prompts. These approaches all share a fundamental architectural assumption: that if the right advice is present in the prompt at the right time, the model will follow it. HASP demonstrates that this assumption is empirically false in consequential ways — the Prompt-Only Skills baseline achieves 20.5% on web-search reasoning while PF-only intervention (same skills, executable form) achieves 51.0% (Table 2, a 30.5-point gap). The skills *encode the same lessons*; the difference is entirely in the mechanism of delivery.

What makes this reification intellectually distinctive is that it changes the *locus of control* from inside the model to outside it. In the textual paradigm, the model must simultaneously (a) understand the skill, (b) recognize that the current state matches its applicability conditions, (c) translate abstract advice into a concrete action modification, and (d) override competing impulses — all probabilistically, all inside a single forward pass. Each step can fail independently, and failures are opaque. HASP decomposes this monolithic process: the PF's `should_activate` predicate handles (b) deterministically (it's pure Python code operating on structured `step_context` fields), the `intervene` method handles (c) by producing a concrete `Intervention` object with explicit before/after action pairs, and the harness handles (d) by forcing the revised action into the loop regardless of what the model "wants" to do. The model's role is reduced to (a) — understanding the skill's semantics — which it does at PF *design* time (when the skill is authored) rather than at execution time.

This architectural shift has consequences that extend beyond the performance numbers. It makes skill execution **auditable**: every intervention logs the triggering state, the original action, the revised action, the PF that fired, and a human-readable reason. It makes skill execution **deterministic**: a PF with the same `step_context` always produces the same intervention, enabling reproducible debugging. It makes skill execution **independently updatable**: a buggy PF can be fixed by editing its code and re-deploying the library, without retraining the model. These properties — auditability, determinism, independent updatability — are impossible in the textual paradigm, where skill execution is entangled with the model's probabilistic generation.

This is not an incremental refinement of prompt-based skill retrieval. It is a **fundamental shift** in what skills *are* — from linguistic artifacts to computational objects — and it opens an entire design space (executable guardrails, structured intervention logging, validated self-improvement) that the textual paradigm structurally cannot access. The paper's Table 1 (qualitative comparison with prior methods) makes this explicit: HASP is the only method with a checkmark in the "Runtime Control" column, while comparable methods show circles for partial or indirect control.

### Innovation 2: The Four-Dimensional Signal Scoring System as a Language for Intervention Quality

If Innovation 1 is about *what* skills become, Innovation 2 is about *how we know when they're working*. Prior work on agent self-improvement and skill learning typically relies on a single scalar reward — task success (did the episode end correctly?), a learned reward model, or human preference. HASP introduces a **four-dimensional decomposition of intervention quality** (timing, modality, correctness, outcome) that captures distinct aspects of *why* an intervention was good or bad, not just *whether* the episode succeeded.

This is intellectually distinctive because it creates a **shared supervisory language** that bridges three otherwise-separate concerns: inference-time intervention (where the signals tell us which interventions are firing appropriately), post-training (where the signals weight training examples and filter trajectories), and skill evolution (where the signals inform which new PFs to accept and how to score the skill proposer). The same four-dimensional score `A_t = 0.15·timing + 0.10·modality + 0.25·correctness + 0.50·outcome` serves all three purposes, creating a coherent feedback loop where interventions that fire at the right time, use the right mechanism, produce valid repairs, and improve final outcomes are reinforced across the entire pipeline.

The signal ablation in Table 5 provides the empirical evidence that this decomposition matters. Removing any single dimension causes a 7.8–15.5 point drop in closed-loop performance, with modality (how the PF intervenes — action modification vs. context injection) being the most impactful single removal at −15.5 points. This is not obvious a priori: one might expect outcome (did the episode succeed?) to dominate completely, since it is the only signal anchored to ground-truth. The fact that correctness (−12.1) and timing (−7.8) also produce substantial drops indicates that *how* and *when* an intervention fires are independently informative beyond *whether* the episode ultimately succeeded. A PF that fires unnecessarily on safe steps and still produces a correct final answer might receive a high outcome score, but the timing and correctness penalties would flag it as suboptimal — and training on such interventions would teach the model to fire PFs indiscriminately rather than selectively.

This is a **diagnostic advance** as much as a performance advance. Prior to HASP, if an agent with skill-based training performed poorly, it was difficult to attribute the failure to any specific aspect of skill execution. Did the skills fire at the wrong times? Did they use the wrong intervention mechanism? Did they produce locally valid repairs that failed downstream? HASP's signal decomposition provides a structured way to answer these questions, turning what was previously a black-box optimization problem into an inspectable, debuggable system. The fine-grained sub-signals in Appendix E further decompose each coarse dimension — e.g., correctness separates syntactic validity (is the revised action well-formed?) from semantic appropriateness (does the revised action make sense given the question?) and domain consistency (does it follow domain-specific rules?) — enabling targeted diagnosis of intervention failures.

### Innovation 3: The Controlled Evolution Insight — Strict Filtering Is Necessary, Not Optional, for Self-Improving Skill Libraries

The paper's most dramatic **negative result** is also one of its most important intellectual contributions: unfiltered skill library evolution catastrophically degrades performance. In Table 5, the "Evolution, no filtering" ablation drops web-search accuracy from 60.3% (full filtering) to 36.3% — a 24-point collapse that falls below even the multi-loop baseline (31.2%). This is not a small degradation; it is a complete failure of the self-improvement mechanism when admission control is removed.

What makes this finding intellectually significant is that it contradicts a plausible and widely-held intuition: that more experience → more skills → better performance. In the textual skill paradigm, adding more lessons to a memory bank is generally benign — they might be ignored, but they rarely actively harm performance. HASP demonstrates that for *executable* skills, this intuition is dangerously wrong. A badly-designed PF that fires too aggressively (overly broad `should_activate` predicate), produces malformed interventions (ill-typed `intervene` output), or conflicts with existing PFs (two PFs fighting over the same action) does not just fail to help — it actively corrupts the agent loop, overriding correct actions, injecting noise, and causing the policy to thrash.

The filtering ablation further decomposes *which* gate prevents which failure mode. Removing only the executable validation gate (keeping teacher review) produces a 13.1-point drop; removing only the teacher review gate (keeping executable validation) produces an 11.5-point drop. The two gates are complementary: executable validation catches interface failures (syntax errors, missing methods, wrong return types — the "can it run?" question), while teacher review catches conceptual failures (overly specific triggers, interventions that could cause harmful side effects, skills that don't generalize — the "should it run?" question). Both are necessary; neither is sufficient alone.

This finding reframes the self-improvement problem from "how do we generate more skills?" to "how do we generate *good* skills and filter out the bad ones?" — a shift from generation to curation. The paper's controlled evolution pipeline (Phases A–H, with executable validation, teacher five-dimensional review, and two-tier acceptance thresholds) is the embodiment of this philosophy: skill library growth is treated as a **validated, rate-limited process** rather than unconstrained generation. The versioning system (`__v{N}` suffixes, `skill_ids_latest`), the hard cap on library size (max 50 active skills), and the per-epoch proposal limit (max 5 candidates) are all mechanisms for keeping the library small, high-quality, and auditable. The paper's evolution dynamics (Appendix F.4) confirm that the bottleneck is novelty, not capacity — the library size stays well below 50 even after multiple epochs because the system refuses to admit skills that don't clear the quality bar.

This is a **conceptual advance** with practical implications beyond HASP. Any system that learns executable behavioral rules from experience — whether for agents, robots, or software systems — faces the same tension between coverage (capturing more failure modes) and precision (not introducing harmful rules). HASP's two-gate filtering architecture and the empirical demonstration that unfiltered growth is catastrophic provide a template for navigating this tension.

### Innovation 4: Capability Elicitation vs. Capability Creation — A Diagnostic Distinction with Architectural Consequences

Throughout the paper, HASP makes a distinction that is easy to state but has deep architectural implications: PFs **elicit** existing capabilities (they help the model reliably execute strategies it already possesses) rather than **creating** new capabilities (discovering strategies the model doesn't know). The conclusion states this explicitly: "PFs help surface and stabilize useful strategies that the model can often execute but does not apply reliably, while broader RL-style exploration may still be needed to discover genuinely new strategies."

This distinction is not merely a limitation to be acknowledged — it is a **diagnostic concept** that explains the pattern of HASP's results across difficulty levels and domains. On web-search reasoning, where the base Qwen2.5-7B-Instruct model can already decompose questions and verify evidence (it just doesn't do so consistently), PF intervention produces massive gains (25% improvement over multi-loop ReAct in the inference-only setting). On AIME24, the hardest math benchmark, where the base model's pass@1 is near zero and the challenge is discovering novel solution strategies, HASP-Evolve + RS reaches only 16.7% — competitive with simpler baselines but far behind AgentFlow + Flow-GRPO at 40.0% (Table 2). The gap is not a failure of HASP; it is a direct consequence of the elicitation-vs-creation distinction. PFs cannot teach the model to solve problems it fundamentally cannot solve; they can only ensure that when the model *can* solve a problem (somewhere in its output distribution), it does so reliably.

This distinction clarifies HASP's relationship to prior work in a way that avoids false competition. Search-R1, AgentFlow, and other RL-based training methods operate primarily in the capability-creation regime: they explore the policy space through reward-shaped search, potentially discovering strategies the model would never produce under standard sampling. HASP operates in the capability-elicitation regime: it takes strategies the model already possesses and makes their execution reliable. The two are **complementary, not competing**. A system that combined HASP's executable guardrails (for reliable execution of known strategies) with RL-based exploration (for discovering new strategies) could outperform either alone, and the paper's modular design — where the PF library is external to the model and can be used with any training method — is explicitly architected to enable this combination.

The elicitation-vs-creation distinction also explains the **pattern of PF internalization** observed in Section 4.2 and Appendix G.4. Behavior-correcting PFs that fix the model's own execution errors (e.g., `insufficient_exploration` which forces a READ before premature FINAL, `retrieval_failure` which shortens overly long queries) tend to become "silent" after post-training — the model learns not to make those errors, so the PFs no longer need to fire. Input-dependent PFs that provide structural guidance tied to the question itself (e.g., `decompose_complex_question` which injects a decomposition hint for multi-hop questions) remain necessary even after training, because they encode information about the *question's structure* rather than the *model's behavior*. The paper quantifies this: `multi_hop_reasoning_failure` and `retrieval_failure` become silent on 100% of their previously triggered cases, while `decompose_complex_question` is silent on only 3–12% of cases. This pattern is exactly what the elicitation framing predicts: PFs that correct execution errors (eliciting capabilities the model already has) can be internalized; PFs that provide structural problem analysis (which requires reasoning the model cannot reliably do) remain as external guidance.

This is a **conceptual reframing** of the agent improvement problem that has practical consequences for system design. If you know that your failures are primarily execution errors (the model knows what to do but doesn't do it), invest in PF-style guardrails and post-training internalization. If you know that your failures are primarily capability gaps (the model genuinely cannot solve certain problem classes), invest in RL-based exploration or larger pretraining. The paper provides the diagnostic tools — difficulty bins, PF trigger/failure statistics, internalization rates — to make this determination empirically.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper evaluates on three domains. For **web-search reasoning**, it uses HotpotQA (Yang et al., 2018), 2WikiMultihopQA (Ho et al., 2020), and MuSiQue (Trivedi et al., 2022) — each with 200 test questions and 800 training-pool questions following the AgentFlow split convention (Appendix D.1, Table 10). For **mathematical reasoning**, it uses AIME24 (30 problems), AMC23 (40 problems), and GameOf24 (1,362 problems) — the full datasets serve as test sets, following AgentFlow verbatim (Table 11). For **coding**, it uses HumanEval+ and MBPP+ (EvalPlus extended versions, 50 unique test problems each), and BigCodeBench (100 test entries for Full, the entire 148-entry Hard split used as-is); the training pool is constructed from remaining unique problems (Table 12). All train/test splits are deterministic given seed 42.

- **Base model(s).** All experiments use Qwen2.5-7B-Instruct (Yang et al., 2025), a 7-billion-parameter instruction-tuned model. The paper argues this model is "representative of the capabilities of many contemporary LLMs" (Section 4) and sits in a useful regime where pass@1 is non-trivial but far from saturation — e.g., the base multi-loop ReAct agent achieves only 31.2% average on web-search reasoning (Table 2) — leaving substantial room for PF intervention and training to make a difference. When teacher augmentation is used (for PF selection, teacher review, or on-policy distillation), GPT-4o (snapshot `gpt-4o-2024-11-20`) serves as the teacher, with all API costs reported in Appendix K (average ~$0.045 per question for the full HASP configuration on web-search). For baseline comparisons, GPT-4o and GPT-4o-mini are also evaluated directly as zero-shot or multi-loop agents (Table 2, upper block).

- **Metrics.** Web-search and math use **exact-match accuracy** (%) — the fraction of test questions where the agent's final answer matches the ground truth, with math answers judged by GPT-4o (Section 4). Coding uses **pass@1** (%) — the fraction of problems where the model's first generated solution passes all test cases, evaluated on HumanEval (Base, Plus), MBPP (Base, Plus), and BigCodeBench (Full, Hard). Domain-level averages are unweighted means across constituent datasets (e.g., web-search average = mean of HotpotQA, 2Wiki, MuSiQue accuracies).

- **Baselines.** The paper compares against a broad set of training-free and training-based methods. **Training-free / inference-time baselines** include: GPT-4o and GPT-4o-mini as zero-shot agents (Hurst et al., 2024); the raw Qwen2.5-7B-Instruct backbone; **RA-Agent (multi-loop)** — a multi-step ReAct agent (Yao et al., 2023) without any skills or PFs; **Prompt-Only Skills** — where the same skill library is injected as textual guidance rather than executable PFs; Iter-RetGen (Shao et al., 2023); AutoGen (Wu et al., 2024); and TIR (Xue et al., 2025) for math. **Training-based baselines** include: vanilla SFT; SKILL0 (Lu et al., 2026); Search-R1 (Jin et al., 2025); ZeroSearch (Sun et al., 2025); ReSearch (Chen et al., 2025); StepSearch (Wang et al., 2025); VerlTool (Jiang et al., 2025); SimpleRL-reason (Zeng et al., 2025); Open-Reasoner-Zero (Hu et al., 2025); General-Reasoner (Ma et al., 2025); Luffy (Yan et al., 2025); ToRL (Li et al., 2025); AgentFlow with Flow-GRPO (Li et al., 2025); AceCoder (Zeng et al., 2025); GRPO-based code training (Fan et al., 2025); and KodCode-RL (Xu et al., 2025). Not all baselines are evaluated on all domains; "–" in Tables 2 and 3 indicates no reported result.

- **Generation budget / compute accounting.** The paper measures compute in **generations** — one complete agent trajectory (multi-step for web-search, single-step for math and code). For inference-time methods, the relevant budget metric is the number of reasoning steps and tool calls per episode: the web-search ReAct loop uses `max_steps = 5`, `max_search_calls = 3`, `max_read_calls` tied to search results, and a per-PF rate limit system (e.g., `_MAX_MODIFY_FIRES = 2`, per-skill caps; Appendix B.1). For training-based methods, compute is accounted through: (a) the number of rollout trajectories sampled for rejection sampling (`k = 2` rollout groups per question), (b) the number of training epochs (10 for open-loop SFT, 8 per phase for RS, 5–10 for OPD), and (c) the evolution pipeline cost (5 full-evolve epochs for web-search, 3 lite-evolve epochs for math and code). The paper reports total compute footprint as approximately 2,000–2,500 GPU-hours on NVIDIA L40S-class hardware (Appendix J.2), plus teacher API costs of approximately $0.045 per question for the full configuration. All training uses LoRA (rank 16, α = 32, bf16 precision, gradient checkpointing) rather than full fine-tuning, keeping per-run GPU requirements modest (1–2 L40S GPUs per experiment).

- **Cross-validation / statistical protocol.** The self-improving evolution pipeline (Appendix C, Algorithm 1) uses a **fixed seed-42 validation pool** drawn from the tail of the training-pool data (50 seed + 50 validation samples per dataset, shuffled deterministically), ensuring that the skill library is evaluated on held-out questions during evolution. For the main post-training experiments, the paper uses **single-seed reporting** (seed = 42 for all training runs and validation-pool shuffles), acknowledging that multi-seed replication is "prohibitive" (Appendix J.4). Based on internal smoke tests with `k = 4` rollouts, the standard deviation of web-search EM is approximately ±1.5 points — smaller than the gaps reported in Table 2. Teacher behavior is pinned to a specific GPT-4o snapshot for reproducibility.

### Main Quantitative Results

The results are presented in four stages, corresponding to the paper's modular architecture: (1) inference-time PF intervention, (2) auxiliary teacher selection, (3) post-training internalization under fixed and evolving skill libraries, and (4) closed-loop PF evolution.

#### Inference-Time PF Intervention Alone Dramatically Outperforms Textual Skills and Multi-Loop Baselines

The headline result from Table 2 (upper block, "Training-free / inference-time methods"): on web-search reasoning, **PF-only intervention reaches 51.0% average accuracy**, compared to:
- 31.2% for the multi-loop ReAct agent (RA-Agent, no skills) — a **25.0 percentage-point absolute gain**
- 20.5% for Prompt-Only Skills — a **30.5 percentage-point gain**
- 36.6% for AutoGen (a multi-agent framework)
- 30.5% for GPT-4o-mini (a model of comparable scale)
- 42.5% for GPT-4o (a much larger proprietary model)

Per-dataset, PF-only achieves 59.0% on HotpotQA, 67.0% on 2Wiki, and 27.0% on MuSiQue (Table 2). The MuSiQue result is noteworthy: it is the hardest multi-hop benchmark and the one where PF intervention provides the largest relative gain over baselines — the multi-loop agent achieves only 20.0% on MuSiQue, meaning PFs improve by 7 points on the hardest test while improving by 19.5 and 33.0 points on the easier ones.

On mathematical reasoning, **PF-only reaches 35.9% average**, compared to 34.2% for RA-Agent and 32.8% for Prompt-Only Skills (Table 2). The gains are more modest here because math uses single-step rollouts (`max_steps = 1`), so the only PF intervention surfaces are `system_summary` text injection and `pre_final` verification hooks — no step-level `MODIFY_ACTION` is possible.

On coding, **PF-only reaches 63.4% average pass@1** (Table 3, upper block), compared to 60.8% for the raw Qwen2.5-7B-Instruct, 54.5% for RA-Agent, and 61.2% for Prompt-Only Skills. Per-benchmark, PF-only achieves 84.5% on HumanEval Base, 82.0% on HumanEval Plus, 88.0% on MBPP Base, 65.0% on MBPP Plus, 42.0% on BigCodeBench Full, and 19.0% on BigCodeBench Hard. The gains are concentrated on the harder splits (Plus, Hard), consistent with the paper's claim that PFs help most on edge-case-heavy problems where static analysis (e.g., `code_edge_cases`, `code_off_by_one`) can catch missing branches or index errors.

**Why inference-only PFs work so much better than textual skills.** The paper's inference-time component ablation in Table 5 (first block) isolates the contribution of the PF mechanism. The "PF only" row (51.0%) strips away the teacher entirely — `needs_teacher = True` PFs fall back to their deterministic code paths — while the "Teacher only" row (50.7%) disables PFs but keeps the teacher available for answer verification and multi-round retry. The two configurations perform nearly identically (51.0% vs. 50.7%), demonstrating that the PF substrate alone — without any stronger model assisting at decision time — accounts for essentially all of the inference-time gain. The teacher's marginal contribution (+5.2 points from 51.0% to 56.2% when both are active) comes primarily from the eight FINAL-time LLM-assisted handlers (Appendix B.6), not from mid-rollout PF paraphrasing.

#### PF Intervention Patterns Are Concentrated in a Few High-Value Skills

The mechanism analysis in Section 4.2 reports statistics over all PF activations in multi-step ReAct rollouts. Across all fired PF events on web-search reasoning:
- **65.1% are action-level interventions** (`MODIFY_ACTION`), 34.9% are context-level (`INJECT_CONTEXT`), indicating that PFs frequently change the next executable decision itself rather than only adding textual guidance.
- The most frequently activated skill is **`decompose_complex_question`** (322 total triggers), followed by `insufficient_exploration` (138) and `answer_completeness` (100). This concentration means a small number of PFs handle the majority of intervention events.
- Activation counts vary by benchmark difficulty: MuSiQue accounts for 385 activations, compared with 161 on 2Wiki and 95 on HotpotQA, "indicating that harder multi-hop settings rely more heavily on PF intervention" (Section 4.2).

Table 6 provides a complementary view: the recovered failure structure shows that `reasoning_hallucination` (31.7% of recovered cases) and `wrong_entity_focus` (24.1%) are the most prevalent failure types, while `premature_final` and `no_read_before_final` (jointly 17.8%) are in the exploration-control cluster. The average ΔEM / ΔAcc. columns show that `reasoning_hallucination` PFs provide the largest per-recovery uplift (+13.3 EM / +9.3 Acc.), while `no_read_before_final` provides minimal uplift (+0.4 / +0.8) — consistent with the paper's finding that behavior-correcting PFs (forcing READs before FINAL) become less necessary after training because the model internalizes them.

#### Auxiliary Teacher Selection Further Improves PF Dispatch

The full HASP-Intervention configuration adds an auxiliary teacher for PF selection (Section 3.1, the teacher-based `PFSelector`) and FINAL-time handler assistance. On web-search, this reaches **56.2% average** (Table 2) — a +5.2 point gain over PF-only (51.0%). On math, it reaches 38.8% (+2.9 over PF-only). On coding, it reaches 68.7% (Table 3) — a +5.3 point gain, with particularly strong gains on BigCodeBench Hard (26.0% vs. 19.0% PF-only, a +7.0 point improvement).

The teacher's contribution comes primarily from more precise PF selection (fewer irrelevant PFs cluttering the system prompt) rather than from mid-rollout intervention quality — the PF-only ablation in Table 5 shows that deterministic PF fallback paths (e.g., regex-based query shortening for `retrieval_failure` when the teacher is unavailable) are nearly as effective as teacher-paraphrased interventions. The eight FINAL-time LLM-assisted handlers are the exception: they operate at the final decision point and require semantic understanding (e.g., "does the answer fully address all parts of the question?") that deterministic code cannot reliably provide.

#### PF-Derived Supervision Enables Effective Post-Training Without Full Reinforcement Learning

Table 4 presents the 2×3 grid of post-training experiments: fixed-library (HASP + SFT/RS/OPD) and closed-loop (HASP-Evolve + SFT/RS/OPD), all benchmarked against the inference-time baseline HASP-Intervention (56.2% web-search, 38.8% math).

**Under a fixed skill library (open-loop, V1):**
- **SFT reaches 56.8%** on web-search (+0.6 over inference-only) and 40.9% on math (+2.1). The small web-search gain reflects SFT's limitation: it trains on all PF-corrected actions equally, including those from failed trajectories, diluting the supervision signal.
- **RS reaches 59.3%** on web-search (+3.1 over inference-only) and 42.7% on math (+3.9). The +3.1 point gain over SFT demonstrates the value of trajectory-level quality filtering — RS only keeps trajectories that are both task-successful and PF-aligned, suppressing noisy corrections.
- **OPD reaches 62.5%** on web-search (+6.3) and 42.4% on math (+3.6). On web-search, OPD achieves the strongest fixed-library result across all recipes, consistent with its design: training on the student's own state distribution corrects for the distribution shift between PF-augmented rollouts and PF-free deployment. However, the MuSiQue result is striking: OPD reaches 54.0% on MuSiQue compared to 36.0% for RS and 35.5% for SFT — an 18-point advantage over SFT on the hardest benchmark. This suggests that on-policy distillation is particularly valuable for difficult multi-hop questions where the student's error patterns differ most from the fixed training pool's.

**Under closed-loop evolution (V2):**
- **HASP-Evolve + RS reaches 60.3%** on web-search (+4.1 over inference-only) and 45.4% on math (+6.6). This is the paper's strongest overall result for open-weight models on web-search reasoning (Table 2, lower block) and the main trained variant.
- **HASP-Evolve + SFT reaches 58.5%** (+2.3) and 41.4% (+2.6).
- **HASP-Evolve + OPD drops to 56.7%** (+0.5) and 43.9% (+5.1) on math. On web-search, the OPD decline under evolution (from 62.5% fixed → 56.7% evolved) is the most important negative training result. The paper attributes this to OPD's sensitivity to the non-stationarity introduced by library updates: "jointly changing the on-policy state distribution and the skill library can introduce instability" (Section 4.1). In contrast, RS handles library evolution well (59.3% → 60.3%) because its trajectory-level filtering provides a stabilizing effect — the quality threshold rejects trajectories that were corrupted by newly-admitted but poorly-behaved PFs.

**Comparison to prior training-based methods (Table 2, lower block).** On web-search reasoning, HASP-Evolve + RS (60.3%) outperforms:
- Search-R1 (29.9%) by **+30.4 points** — the largest margin in the table and the headline comparison in the abstract
- ZeroSearch (29.3%) by +31.0
- ReSearch (37.8%) by +22.5
- StepSearch (32.6%) by +27.7
- VerlTool (36.5%) by +23.8
- SKILL0 (31.6%) by +28.7
- AgentFlow + Flow-GRPO (53.2%) by **+7.1 points** — notably, HASP outperforms AgentFlow despite AgentFlow using RL-based flow optimization, suggesting that PF-guided rejection sampling captures behavioral improvements that flow optimization misses.

On mathematical reasoning, HASP-Evolve + RS (45.4%) is competitive but not dominant:
- AgentFlow + Flow-GRPO reaches 51.5% (−6.1 for HASP), primarily driven by a 40.0% → 16.7% gap on AIME24 — the hardest math benchmark, where RL-based exploration discovers strategies that PF-based elicitation cannot surface.
- SimpleRL-reason (36.6%), ToRL (37.0%), and Luffy (36.2%) are all lower.
- This pattern is exactly what the elicitation-vs-creation distinction predicts: on AIME24, where the base model's capabilities are near the frontier, PFs can only ensure reliable execution of known strategies; RL methods can discover new ones.

On coding, HASP-Evolve + RS reaches **69.9% average pass@1** (Table 3, lower block), compared to:
- GRPO-based code training at 68.4% (+1.5 for HASP)
- P-GRPO at 69.8% (essentially tied: +0.1)
- KodCode-RL at step 128 (65.4%) and step 256 (66.8%)
- AceCoderRM at 63.2% and AceCoderRule at 62.1%
- Vanilla SFT at 57.5% (+12.4 for HASP)

The coding results show HASP as **competitive with the strongest RL-based code generation methods** (P-GRPO, KodCode-RL) while using only PF-guided rejection sampling rather than reward-shaped exploration. This is consistent with the paper's claim that PFs are effective at eliciting existing coding capabilities — the Qwen2.5-7B-Instruct model already possesses strong code generation ability, and PFs help it reliably avoid edge-case errors (off-by-one, missing branches, input parsing failures) without needing to discover new algorithms.

#### Training Dynamics Reveal Why RS Is the Most Stable Recipe Under Evolution

Figures 3, 6, 7, and 8 provide detailed training dynamics for all six post-training settings. The key observations:

- **SFT** (blue lines) rapidly lowers loss and increases correction-aligned token accuracy but plateaus early, consistent with training on all PF-corrected actions without quality filtering. Policy entropy remains high, indicating the model is not converging to a focused behavioral strategy.
- **RS** (green lines) maintains the highest correction-aligned token accuracy with the lowest policy entropy, consistent with selecting only task-successful and PF-aligned trajectories. The entropy suppression suggests RS produces a more deterministic, less exploratory policy — which is appropriate when the PF library encodes known behavioral corrections and exploration is unnecessary.
- **OPD** (red lines) shows slower, non-monotonic alignment (Figure 3, middle panel) — correction-aligned accuracy fluctuates as the student's own state distribution shifts — but achieves the strongest fixed-library result (62.5% web-search). The non-monotonicity reflects the on-policy feedback loop: as the student improves, it visits states where corrections are harder, so accuracy can temporarily drop.
- **Closed-loop runs** (dashed lines, Figure 8) show clear discontinuities at the library-refresh boundary (vertical dotted markers): loss spikes, token accuracy dips, and entropy increases when new PFs are admitted. RS recovers fastest after the refresh (the green dashed line stabilizes within ~50M tokens), OPD struggles (the red dashed line shows persistent fluctuations). This visual evidence supports the paper's recommendation of RS for closed-loop training.

**Critical reading of the dynamics plots.** The paper uses processed training tokens as the X-axis, which normalizes for differences in per-step batch sizes across recipes. Figure 6 shows the same data against global step count and confirms that the qualitative recipe ordering is robust to X-axis choice. Figure 7 isolates the three open-loop (V1) runs, showing that SFT, RS, and OPD converge to clearly distinct regimes when trained on the same fixed PF-aware rollout pool. Figure 8 isolates the three closed-loop (V2) runs and highlights the refresh-point discontinuity. Together, these four figures provide substantially more diagnostic information than a standard results table, allowing readers to understand *why* RS outperforms SFT (quality filtering suppresses entropy) and why OPD degrades under evolution (distribution shift from library updates causes non-stationarity).

#### Closed-Loop Evolution Provides Modest but Genuine Gains Over the Fixed Library

Comparing HASP-Evolve + RS (60.3%) to HASP + RS (59.3%) on web-search reasoning (Table 4), the +1.0 point gain from closed-loop evolution is modest. The filtering ablation in Table 5 provides context for interpreting this number:

- **No evolution** (59.3%): freezes the library at the seed snapshot. Only −1.0 point below full evolution, indicating that the seed library already covers most recoverable failure patterns.
- **Evolution, full filtering** (60.3%): the reference row for the closed-loop configuration.
- **Evolution, no filtering** (36.3%): a catastrophic −24.0 point collapse, falling below even the multi-loop baseline (31.2%).
- **Evolution, exec-only** (48.8%): −11.5 points.
- **Evolution, teacher-only** (47.2%): −13.1 points.

The pattern is clear: unfiltered evolution is worse than no evolution at all, and both filtering gates are necessary to stay above the fixed-library baseline. The modest +1.0 point gain from full-filtering evolution — combined with the dramatic penalties for removing either gate — supports the paper's claim that "self-improvement is useful only when library evolution is tightly controlled" (Appendix C.8). The small positive gain suggests that the seed library, derived from recurring failure–repair patterns in the training pool, already captures the high-frequency, high-impact failure modes; evolution adds value primarily by covering rarer or domain-shifted patterns.

#### Cross-Domain Transfer: PFs Generalize Across Reasoning Modalities

Tables 2, 3, and 4 together demonstrate that the PF framework transfers across web-search reasoning, mathematical reasoning, and coding with minimal domain-specific adaptation. The shared dispatcher, signal scorer, and post-training recipes are identical across domains; only the PF libraries differ (Appendix B.4). The absolute gains vary by domain — largest on web-search (where multi-step loops enable rich `MODIFY_ACTION` interventions), moderate on math (where `pre_final` hooks compensate for single-step rollouts), and smallest but still meaningful on coding (where PFs are constrained to static-analysis hints) — but the pattern of PF intervention > textual skills and PF-guided training > vanilla SFT is consistent across all three domains.

**MuSiQue-specific analysis (web-search domain).** MuSiQue is the hardest web-search benchmark, requiring composition of multiple single-hop questions into multi-hop chains. HASP's performance on MuSiQue across configurations tells a nuanced story:

- Inference-only: 34.0% (with teacher) vs. 20.0% for RA-Agent (Table 2)
- Fixed-library RS: 36.0% (Table 4)
- Fixed-library OPD: 54.0% (Table 4) — **the largest single-dataset gain in the paper**
- Evolved RS: 38.0% (Table 4)
- Evolved OPD: 35.5% (Table 4)

The OPD result on MuSiQue is the most striking per-dataset finding: 54.0% under fixed-library OPD is 18 points higher than RS (36.0%) and 20 points higher than SFT (35.5%). This suggests that MuSiQue's difficulty — specifically, the distribution shift between the training pool's question patterns and the test set's — makes on-policy training on the student's own states particularly valuable. However, this gain is fragile: evolved OPD drops to 35.5% on MuSiQue, a −18.5 point collapse that mirrors the pattern seen in aggregate (OPD under evolution is unstable). For practitioners, this implies that OPD is the best choice when the skill library is frozen and the domain involves significant distribution shift, but RS is safer when the library is evolving.

### Ablation Studies and Robustness Checks

**Inference-time component ablation (Table 5, first block):** The full HASP-Intervention row (56.2%) represents PFs + teacher both active. Removing PFs (Teacher only: 50.7%) and removing the teacher (PF only: 51.0%) produce nearly identical performance, demonstrating that the PF substrate alone accounts for the bulk of the gain. The Prompt-Only Skills row appears in Table 2 (20.5%), representing the lower bound where the same skills are expressed as text rather than executable code. The RA-Agent row (31.2%) is the absolute lower bound with no skills at all.

**Signal ablation (Table 5, second block):** Removing each of the four supervision signals from the closed-loop RS run (E5) individually:
- **Without Timing**: 52.5% (−7.8) — the smallest drop, consistent with timing carrying the lowest weight (0.15) in the composite. However, even this small weight removal causes a meaningful degradation, indicating that *when* a PF fires (on risky steps vs. safe steps) carries independent information.
- **Without Modality**: 44.8% (−15.5) — the largest drop, and the most non-obvious result. Removing the modality signal means the system no longer distinguishes `MODIFY_ACTION` from `INJECT_CONTEXT` interventions — a PF that rewrites a SEARCH query and a PF that injects a textual reminder are treated identically. The 15.5-point drop indicates that *how* a PF intervenes is not just a detail — it is the most important single dimension for training quality.
- **Without Correctness**: 48.2% (−12.1) — removing the signal that scores whether the revised action is syntactically valid, semantically appropriate, and domain-consistent causes a large drop, confirming that interventions must produce valid repairs, not just fire at the right time.
- **Without Outcome**: 47.5% (−12.8) — removing the only signal anchored to ground-truth EM causes a drop comparable to removing correctness. This is expected (outcome carries the heaviest weight, 0.50) but the symmetry with correctness (−12.1) is interesting: both "is the repair valid?" and "did the episode succeed?" contribute roughly equally to training quality despite the 2:1 weight ratio favoring outcome. The weights reflect the paper's design choice to anchor heavily to ground-truth, but the ablation reveals that outcome and correctness carry similar *effective* information content.

**Filtering ablation (Table 5, third block):** The five rows of the filtering ablation test admission control during library evolution:
- **No evolution** (59.3%): reference row, library frozen at seed snapshot.
- **Evolution, full filtering** (60.3%): +1.0 point, both Exec and Teach gates active.
- **Evolution, no filtering** (36.3%): −24.0 points, the central negative result. Unfiltered candidates include PFs that fail to import, fire too aggressively, conflict with existing PFs, or produce malformed interventions. The −24.0 collapse is catastrophic and justifies the paper's emphasis on strict filtering.
- **Evolution, exec-only** (48.8%): −11.5 points. Executable validation catches interface failures (syntax errors, missing methods, wrong return types) but lets through conceptually weak or overly specific PFs that pass the four executable checks. The recovery from −24.0 to −11.5 shows that executable validation alone prevents the worst failures, but is insufficient for library quality.
- **Evolution, teacher-only** (47.2%): −13.1 points. Teacher review catches conceptual failures (overly broad triggers, harmful interventions, non-generalizable skills) but lets through PFs with sound concepts but broken implementations. The symmetry between exec-only (−11.5) and teacher-only (−13.1) suggests the two gates catch roughly equally important but complementary failure modes, consistent with the paper's claim that both are necessary.

**Per-dataset row-level detail in the filtering ablation:** The "Evolution, no filtering" row shows particularly catastrophic degradation on MuSiQue (15.5%) and 2Wiki (58.0%), while HotpotQA (35.5%) is less affected. This suggests that unfiltered PFs disproportionately harm performance on harder multi-hop benchmarks where precise, well-targeted interventions are critical — noisy PFs that fire on the wrong states or produce malformed interventions cause more damage when the agent's margin for error is already small.

**Prompt-equivalent skills ablation (Table 7, Appendix B.5):** Adding prompt-equivalent skills (PFs whose `intervene` emits only fixed-literal `INJECT_CONTEXT` with no runtime computation) on top of the core PF library produces small and mixed effects: +3.5 points on HotpotQA, −3.5 on 2Wiki, −1.0 on MuSiQue, 0.0 on AIME24, +2.5 on AMC23, 0.0 on GameOf24. This supports the paper's claim that "the main benefit comes from skills that can be executed as PFs" rather than from simply enlarging the skill library with textual reminders.

**Training recipe comparison (Tables 2 and 4, Figures 3, 7, 8):** The 2×3 grid comparing V1 (open-loop) vs. V2 (closed-loop) across SFT/RS/OPD constitutes a controlled ablation of both the library topology and the training objective. The consistent pattern — RS is most stable under evolution, OPD is strongest with fixed library but fragile under evolution, SFT is stable but modest — is replicated across web-search and math domains, providing cross-domain validation of the recipe recommendations.

**Domain-specific ablation through benchmark difficulty:** The paper does not run a separate difficulty-bin analysis, but the per-dataset results in Tables 2 and 3 implicitly serve this function. On web-search, MuSiQue (the hardest) shows the largest relative gains from PF intervention and the largest sensitivity to recipe choice. On math, AIME24 (the hardest) shows minimal gains from any HASP configuration, consistent with the capability-elicitation ceiling. On coding, BigCodeBench Hard shows the largest relative gains from teacher augmentation (+7.0 points, Table 3), consistent with edge-case-heavy problems benefiting most from PF-guided static analysis.

**Training dynamics analysis (Figures 3, 5, 6, 7, 8, Appendix H):** The training-dynamics figures provide an ablation of training trajectory rather than final performance. Figure 5 (gradient norm and learning rate) verifies that the observed differences are not artifacts of optimization instability — all six runs sit in the same gradient-norm band (10^0 to 10^1) with no recipe-specific spikes. Figure 6 replicates the primary dynamics plot against global step rather than tokens, confirming robustness to X-axis normalization. These diagnostics strengthen the paper's causal claims about *why* RS outperforms SFT and why OPD degrades under evolution, beyond simply reporting final performance numbers.

### Critical Assessment

#### Do the Experiments Support the Central Claims?

**Claim 1: "PFs improve inference-time decisions substantially over textual skills and multi-loop baselines."** This claim is strongly supported by Table 2 (upper block) and Table 5 (first block), with the 30.5-point gap between PF-only (51.0%) and Prompt-Only Skills (20.5%) on web-search reasoning being the key evidence. The inference-time component ablation in Table 5 further isolates the PF mechanism from the teacher, showing that PF-only (51.0%) and Teacher-only (50.7%) perform nearly identically — the gain is from executable intervention, not from access to a stronger model.

**However**, the paper does not evaluate a baseline where textual skills are injected **at every step** (similar to phase-gated PF reminders) rather than only at the episode start. The Prompt-Only Skills baseline injects skill text into the system prompt once; it's possible that injecting skill reminders at each step (analogous to PF phase instructions) would close some of the gap. The phase-instruction surface in HASP (Appendix B.2) does exactly this for prompt-equivalent PFs — the `phases.{phase}.text` field is rendered only when the agent is in the corresponding phase. A fairer textual baseline would replicate this gating behavior with text rather than code, but this experiment was not run.

**Claim 2: "PF-derived signals provide effective supervision for post-training without full RL."** Supported with qualifications by Table 4 and the training-dynamics figures. The gains of RS (+3.1 over inference-only on web-search) and OPD (+6.3) over SFT (+0.6) demonstrate that PF-conditioned trajectory selection and on-policy distillation add value beyond simple action correction. The four-signal ablation in Table 5 provides evidence that the signal decomposition matters — removing any single signal causes a 7.8–15.5 point drop.

**However**, the signal weights (0.15, 0.10, 0.25, 0.50) are set heuristically with no sensitivity analysis. The paper does not report whether different weightings would produce different results, and the "outcome heaviest" design choice (0.50) makes the signal system conceptually similar to a final-EM filter with mild intermediate penalties — the signal ablation shows that removing outcome causes a 12.8-point drop, comparable to removing correctness (−12.1), but the relative weights (0.50 vs. 0.25) do not reflect this symmetry. A grid search over weights would strengthen the claim that the specific decomposition matters, versus simply "some intermediate supervision helps."

**Claim 3: "Closed-loop PF evolution further improves the external skill library."** Supported but modestly by the +1.0-point gain of HASP-Evolve + RS (60.3%) over HASP + RS (59.3%) in Table 4. The filtering ablation in Table 5 provides the more important evidence: it's not that evolution always helps, but that *unfiltered* evolution catastrophically hurts (36.3%). The +1.0-point gain from full-filtering evolution is small relative to the 24.0-point penalty from no filtering, suggesting that the primary contribution of the evolution pipeline is **preventing degradation** rather than **driving improvement** — it maintains library quality as new failure patterns are encountered, but does not dramatically expand the frontier.

**However**, the evolution experiments span only 5 epochs for web-search and 3 epochs for math/code (Appendix I.2). It's possible that longer evolution with more residual-failure exposure would produce larger gains as the library gradually covers rarer failure modes. The paper's evolution-dynamics analysis (Appendix F.4) notes that "the acceptance rate stays high in early rounds and decays gradually as the seed library already covers the most frequent residual failures," suggesting that the evolution pipeline may be asymptotic — early epochs cover high-frequency patterns, and later epochs add diminishing returns. Whether this asymptote is near the +1.0 point gain or higher is not determined.

**Claim 4: "HASP outperforms prior training-based methods on web-search reasoning."** Supported by Table 2 (lower block), where HASP-Evolve + RS (60.3%) exceeds Search-R1 (29.9%) by 30.4 points, and AgentFlow + Flow-GRPO (53.2%) by 7.1 points. The comparisons to Search-R1, ZeroSearch, ReSearch, StepSearch, and VerlTool are valid head-to-head comparisons on the same web-search benchmark suite under the AgentFlow evaluation protocol.

**However**, the paper does not compare against the strongest possible versions of these baselines. Many of the cited methods (Search-R1, ReSearch, etc.) report results with base models (not instruction-tuned) and may not be optimized for Qwen2.5-7B-Instruct. The AgentFlow comparison is more direct (both use 7B instruction-tuned models), but AgentFlow's results are taken as-reported rather than re-run under identical hardware and teacher-access conditions. Additionally, HASP uses GPT-4o as a teacher for PF selection, FINAL-time handlers, and (in OPD) trajectory distillation, while the baselines generally do not have access to a stronger teacher model. The teacher-advantage confound is partially addressed by the "PF only" row (51.0%, no teacher) which still substantially outperforms most baselines, but the full HASP configuration's teacher access makes direct comparisons to teacher-free baselines somewhat asymmetrical.

#### Genuine Weaknesses and Missing Experiments

**Single model family, single scale.** All experiments use Qwen2.5-7B-Instruct. The paper argues this model is "representative" (Section 4), but the finding that PFs elicit existing capabilities rather than creating new ones may be scale-dependent. Larger models (e.g., 70B parameters) may have fewer execution errors (making PFs less necessary) or may have a wider gap between capability possession and reliable expression (making PFs more beneficial). Smaller models may lack the capabilities that PFs try to elicit, making the whole approach ineffective. The paper provides no evidence on this dimension.

**Difficulty estimation cost is unaccounted for in the "inference-time" figure.** The difficulty gate (Appendix B.6) uses a teacher call per question for difficulty scoring. At approximately $0.045 per question for the full configuration (Appendix K), this is modest but nonzero. The HASP-Intervention (Infer.) results in Table 2 include this cost implicitly (the teacher is used for PF selection and difficulty gating), while the baselines (GPT-4o, GPT-4o-mini, RA-Agent) have no comparable per-question optimization overhead. For latency-sensitive applications, the teacher calls for PF selection and difficulty gating add serial dependencies that the paper does not analyze.

**Test sets are small for statistical claims.** The web-search test sets are 200 questions each (600 total across three datasets). Difficulty binning into five quintiles would produce approximately 120 questions per bin if done in aggregate, or 40 per dataset per bin — too small for reliable per-bin analysis. The paper does not report confidence intervals or standard errors for any result. The standard deviation estimate in Appendix J.4 (±1.5 points for web-search EM) is based on "internal smoke tests" with `k = 4` rollouts, not on multi-seed training runs — this estimates *rollout variance* rather than *training variance* (which is typically much larger).

**No combination of search-tree PFs with revision-model PFs.** The paper's PF library is designed for a single agent loop (ReAct for web-search, single-step for math/code). Recent work on test-time compute (see the reference example in the prompt) shows that combining search over verifier signals with iterative revision of the proposal distribution yields complementary gains. HASP does not explore whether PFs that guide tree search (e.g., a PF that decides when to branch vs. when to commit) combined with PFs that revise intermediate outputs could yield gains beyond either alone. This is an acknowledged gap (the paper's conclusion notes that PFs "may still be needed to discover genuinely new strategies" through RL), but the experiment is not even sketched.

**The initial skill library is hand-crafted from failure analysis.** The seed PFs are derived from "recurring recovered failure–repair patterns in the training pool" (Section 4, backbone setup). This means the quality of the initial library depends on the quality of the failure analysis, and the paper does not ablate how sensitive results are to the seed library's composition. If the seed library captured different failure patterns (e.g., by a different human analyst or a different LLM-based summarizer), would performance change? The evolution pipeline partially addresses this (it can add missed patterns), but the fixed-library results (which dominate the gains) are conditional on the seed library quality.

**No evaluation on open-ended or weakly-verifiable tasks.** All three domains (web-search QA, math, coding) have clear correctness signals — exact match against gold answers, test cases, or GPT-4o judgment. The paper acknowledges this limitation (Appendix A) but provides no evidence on how the PF framework would adapt to tasks where correctness is ambiguous (dialogue, creative writing, open-ended planning) or where verification signals are sparse and delayed (long-horizon embodied tasks). The PF interface's requirement that `should_activate` operates on structured `step_context` fields and returns a Boolean would be challenged by tasks where the state representation is high-dimensional and failure patterns are fuzzy.

**The coding PF library is largely reduced to static-analysis hints**, and the paper does not explore whether more interventionist code PFs (e.g., auto-patching syntax errors, rewriting inefficient algorithms) would be beneficial or harmful. The choice to restrict code PFs to `INJECT_CONTEXT` and `NOOP` is described as a safety decision ("auto-patching student code is judged too risky," Appendix B.4), but this also limits the PF mechanism to its weakest intervention surface on the domain where the base model is already strongest. An ablation comparing static-analysis-only vs. auto-patching code PFs would test whether the `MODIFY_ACTION` surface that drives web-search gains also transfers to coding.

**The paper does not compare against a "PF randomization" baseline.** A skeptic could argue that any structured intervention — even random or semantically meaningless ones — might improve performance by simply forcing the agent to reconsider its decisions (a "thinking slower" effect). A baseline where PFs fire on random steps with generic interventions ("Are you sure? Consider alternatives.") would test whether the specific content of PF interventions matters or whether the mere presence of an intervention loop provides a benefit through increased computation. This baseline is absent.

#### Conditional Claims and Boundary Conditions

The paper's central claim — that executable PFs outperform textual skills — **holds strongly** on web-search reasoning where the action space is rich and multi-step loops provide many intervention opportunities. It **holds moderately** on math where single-step rollouts constrain PFs to pre_final verification hooks. It **holds weakly** on coding where PFs are restricted to static-analysis hints.

The claim that PF-guided post-training outperforms RL-based methods **holds on web-search** (60.3% vs. 53.2% for AgentFlow) but **does not hold on hard math** (45.4% vs. 51.5% for AgentFlow, with a particularly large gap on AIME24: 16.7% vs. 40.0%). The boundary condition is precisely the elicitation-vs-creation distinction the paper articulates: when the base model already possesses the necessary capabilities (web-search reasoning with Qwen2.5-7B-Instruct), PFs help reliable execution; when the base model's capabilities are insufficient (AIME24-level mathematical reasoning), PFs cannot compensate, and RL-based exploration is necessary.

The claim that closed-loop evolution improves the library **holds narrowly** (+1.0 point on web-search, +2.7 points on math) and only when both filtering gates are active. The larger finding is not that evolution helps, but that **unfiltered evolution is catastrophic** — a 24-point penalty on web-search. This reframes the evolution contribution from "growing the library makes things better" to "growing the library without strict quality control makes things much worse."

The claim that the four-dimensional signal decomposition is necessary and sufficient for effective post-training **holds** in the sense that removing any single signal degrades performance by 7.8–15.5 points (Table 5). However, the signal weights are arbitrary and the paper provides no evidence that alternative weightings would not perform equally well or better — the claim is about the *decomposition*, not the specific weights. The "w/o Outcome" row (47.5%) is particularly interesting: it shows that training *without any ground-truth signal* (only timing, modality, and correctness) still outperforms the inference-only baseline (56.2%) on three of four ablated dimensions. This suggests that even approximate, bootstrapped intervention quality signals — without access to final-answer correctness — could drive effective post-training, which has practical implications for domains where ground-truth verification is unavailable. The paper does not explore this implication.

#### Summary of Experimental Rigor

**Strengths:**
- The 2×3 post-training grid (Table 4) is a thorough, controlled comparison of training recipes and library topologies, with complementary training-dynamics analysis (Figures 3, 5–8) that explains *why* RS outperforms SFT and OPD degrades under evolution.
- The signal ablation (Table 5, second block) isolates the contribution of each of the four supervision dimensions, providing evidence that the decomposition is not redundant.
- The filtering ablation (Table 5, third block) is a genuinely informative negative-result experiment — the 24-point collapse under unfiltered evolution is the most important single number for understanding why the evolution pipeline is designed the way it is.
- Cross-domain evaluation on three qualitatively different reasoning modalities (search, math, code) demonstrates that the PF architecture transfers, with performance patterns consistent with the elicitation-vs-creation framing.
- The per-dataset breakdown in Tables 2 and 3 allows readers to assess where gains are concentrated (MuSiQue for web-search, BigCodeBench Hard for coding) rather than relying on opaque averages.

**Weaknesses:**
- Single model family, single scale (7B). The paper's claims about generalizability across model sizes are speculative.
- No multi-seed training runs; confidence intervals are absent; the ±1.5 point rollout-variance estimate does not capture training variance.
- The initial skill library is hand-crafted with no ablation of seed library composition.
- The teacher-advantage confound in full HASP configurations vs. teacher-free baselines is acknowledged (Appendix A) but not experimentally controlled.
- Missing baselines: no step-level textual skill injection, no PF randomization baseline, no combination of PFs with search-tree or revision mechanisms.
- The evolution pipeline is evaluated over a small number of epochs (3–5); asymptotic behavior is unknown.
- Coding PFs are restricted to the weakest intervention surface (static-analysis hints), which limits cross-domain conclusions about the PF mechanism's generality.

**Overall assessment:** The experiments convincingly demonstrate that executable PFs substantially outperform textual skills and multi-loop baselines on web-search reasoning, that PF-derived signals enable effective post-training without full RL, and that strict filtering is necessary for skill library evolution to avoid catastrophic degradation. The comparison to prior training-based methods shows competitive or superior performance on web-search and coding, with the qualification that the base model's capability ceiling limits gains on the hardest math problems (AIME24). The central architectural claim — that reifying skills as executable state-action intervention functions bridges the advisory gap more effectively than textual skill prompting — is strongly supported by the 30.5-point gap between PF-only and Prompt-Only Skills and by the inference-time component ablation showing that the PF mechanism, not the teacher, drives the gain.

## 6. Limitations and Trade-offs

### Capability Ceiling: PFs Cannot Help on Problems the Base Model Fundamentally Cannot Solve

**The assumption or constraint.** HASP operates in the **capability elicitation** regime, not the **capability creation** regime. The paper is explicit about this boundary in the conclusion: "PFs help surface and stabilize useful strategies that the model can often execute but does not apply reliably, while broader RL-style exploration may still be needed to discover genuinely new strategies." This is not a limitation the authors hide — it is a design principle. PFs modify what the model *does*, not what it *knows*. If the base model's pass@1 on a problem class is near zero — meaning no correct solutions exist anywhere in its output distribution — then no amount of PF intervention, no matter how well-designed, can produce a correct answer. The PF can force the agent to search again, read again, or verify again, but it cannot inject mathematical insight or factual knowledge the model lacks.

**The consequence.** On problems outside the base model's capability frontier, HASP provides essentially zero benefit regardless of compute budget or library quality. This is not a gradual degradation — it is a hard cliff. The paper's results on AIME24 (Table 2) make this concrete: HASP-Evolve + RS reaches only 16.7%, compared to 40.0% for AgentFlow + Flow-GRPO. This 23.3-point gap is not because HASP's PFs are poorly designed — it is because AIME24 problems require novel mathematical insights that Qwen2.5-7B-Instruct simply does not possess. The difficulty bin 5 results in the web-search analysis (Section 5.3 of the prior sections document, though not explicitly re-reported in the main tables) show the same pattern: accuracy hovers near 1–3% for all methods and all budgets. The PF library cannot compensate for fundamental capability gaps.

This limitation matters for practitioners because it defines an **applicability boundary**: HASP is valuable when the base model already shows non-trivial pass@1 on the target task distribution (so there are correct behaviors to elicit), and it is essentially useless otherwise. Deploying HASP on a task where the base model is fundamentally incapable is wasted engineering effort.

**What evidence exists in the paper.** Table 2 (mathematical reasoning): HASP-Evolve + RS at 45.4% vs. AgentFlow + Flow-GRPO at 51.5%, with the gap driven entirely by AIME24 (16.7% vs. 40.0%). The coding results in Table 3 show a weaker version of the same pattern — gains are concentrated on edge-case correctness (BigCodeBench Hard: 28.0% vs. 19.0% for PF-only vs. raw Qwen) rather than on algorithmic difficulty (HumanEval Base: 91.0% vs. 81.7%, a smaller proportional gain). The paper's own analysis in Appendix F.2 notes: "PF-derived supervision, in contrast, primarily targets capability elicitation... rather than expanding the policy frontier through reward-shaped exploration." Section 4.2 (Mechanism Analysis) reports that behavior-correcting PFs become silent after training (showing the model internalized them), while input-dependent PFs remain active (showing the model still needs external guidance for structural reasoning it cannot internalize). This pattern is exactly what the elicitation framing predicts.

**Mitigation status.** The paper does not attempt to address this limitation — it treats it as a fundamental architectural boundary rather than a bug to be fixed. The conclusion suggests that combining HASP's PF interface with RL-based exploration is a natural next step ("a complementary path for improving agents"), but no experiments combining the two are reported. A practitioner facing a task distribution where the base model's capability is near the frontier would need to either (a) use a stronger base model, (b) invest in RL-based training (Search-R1, AgentFlow) to expand the frontier, or (c) restrict HASP deployment to the subset of tasks where the base model already shows non-trivial success rates.

### The Difficulty Estimation and PF Selection Overhead Is Not Accounted for in the Headline Numbers

**The assumption or constraint.** The paper's inference-time HASP configuration (56.2% on web-search, Table 2) relies on multiple teacher (GPT-4o) calls per question: a difficulty gate that scores each question on a 1–5 scale, a `PFSelector` that ranks skills by relevance and returns top-K selections, and eight FINAL-time LLM-assisted handlers that verify source attribution, evidence sufficiency, and answer completeness. The paper acknowledges this cost explicitly (Appendix A): "some stronger variants use external teachers for PF selection, teacher review, or on-policy distillation, which increases cost and may introduce teacher-specific bias." Appendix K reports the per-question cost at approximately $0.045 for the full HASP configuration on web-search reasoning.

However, the paper's primary comparison — the 56.2% inference-time result — is reported as a direct improvement over baselines that do not have access to GPT-4o as a runtime oracle. The "PF only" row in Table 5 (51.0%) strips away the teacher and uses only deterministic PF code paths, providing a fairer comparison, but this result is not the headline inference-time number. The 30.5-point gap between PF-only (51.0%) and Prompt-Only Skills (20.5%) is the cleaner demonstration of the PF mechanism's value, but the paper foregrounds the teacher-augmented 56.2% as the primary inference-time result.

**The consequence.** A practitioner attempting to replicate or deploy HASP faces a cost-accuracy tradeoff that the paper does not make explicit. The full HASP configuration (56.2%) requires API calls to a proprietary model on every question, adding financial cost (~$0.045/question), latency (multiple serial API calls), and a dependency on an external service. The PF-only configuration (51.0%) eliminates these costs but sacrifices 5.2 points of accuracy. The paper does not report what fraction of the teacher's contribution comes from which component (difficulty gate vs. PFSelector vs. FINAL handlers), so practitioners cannot make informed decisions about partial teacher deployment — e.g., using the teacher only for FINAL-time verification but not for PF selection.

Furthermore, the teacher-dependence creates a **fairness confound** in baseline comparisons. The training-based baselines in Table 2 (Search-R1, ZeroSearch, ReSearch, StepSearch, VerlTool, AgentFlow) generally do not have access to GPT-4o as a runtime assistant. When HASP-Evolve + RS (60.3%) outperforms AgentFlow + Flow-GRPO (53.2%), part of that 7.1-point gap may be attributable to GPT-4o's assistance during the trajectory rollouts that generate HASP's training data, not solely to the PF architecture. The paper acknowledges this confound in Appendix A ("may introduce teacher-specific bias") but does not experimentally control for it — there is no HASP variant trained entirely without teacher access that could serve as a direct comparison to teacher-free baselines.

**What evidence exists in the paper.** Table 5 (inference-time component ablation) provides the cleanest decomposition: Full HASP (56.2%), PF only (51.0%), Teacher only (50.7%). The near-identical performance of PF-only and Teacher-only is the paper's own evidence that the PF mechanism, not the teacher, drives the gain — but this evidence is restricted to the inference-time setting. For post-training (Table 4), all three recipes (SFT, RS, OPD) use teacher-augmented PF interventions in their training data (the OPD recipe explicitly uses GPT-4o as the teacher providing corrected trajectories; the RS and SFT recipes use the four-signal scoring system where `s3.semantic` is "teacher-judged step quality"). Appendix K reports approximate teacher token budgets: ~80M input + 10M output tokens for skill-eval inference (across all ablation rows), ~25M + 5M for the three self-improving loops, and ~20M + 4M for on-policy distillation. These are non-trivial costs that would need to be weighed against the reported accuracy gains.

**Mitigation status.** The paper provides the PF-only ablation (Table 5) which partially addresses the inference-time confound by showing that deterministic PFs achieve 51.0% without the teacher — still substantially above baselines. The lite evolution mode (Appendix D.5) reduces self-improvement teacher costs by eliminating Phase E teacher review entirely, relying only on `ast.parse` compile-checks and skill-id deduplication. The paper notes that "most of the library-growth benefit" is retained under lite evolution, but does not report final accuracy numbers for a fully teacher-free HASP pipeline (PF-only inference + lite evolution + teacher-free training data). A practitioner wanting to deploy HASP without any external model dependency would need to extrapolate from the PF-only (51.0%) and HASP-Evolve + RS (60.3%) numbers, guessing that a fully teacher-free training pipeline might fall somewhere between these endpoints.

### The Initial Skill Library Requires Human-Quality Failure Analysis, and Its Composition Is Not Ablated

**The assumption or constraint.** The paper's seed PF library — the starting point for all experiments, including the inference-time and fixed-library training results — is derived from "recurring recovered failure–repair patterns in the training pool" (Section 4, backbone setup). This means that a human analyst (or an LLM-based summarizer guided by human-designed heuristics) examined failed trajectories from the multi-loop ReAct agent, identified recurring failure modes (premature finalization, entity confusion, insufficient exploration), designed PF predicates and interventions to address each mode, and validated them through syntax, interface, and mock-execution checks before admitting them to the library. The quality of the entire system depends on the quality of this initial analysis.

The paper provides detailed specifications for individual PFs (Skill B.1: `retrieval_failure`, Skill B.2: `verification_missing`, PF B.1: `RetrievalFailurePF`) and describes the initial library composition (16 PF skills + 8 prompt-only skills for web-search, 11 PF skills for math, 12 for code), but it does not report **how sensitive results are to the seed library's composition**. What if the initial failure analysis missed an important failure mode? What if it included a PF that later proved harmful? What if a different analyst (or a different LLM prompted with a different summarization prompt) produced a substantially different seed library?

**The consequence.** The reported results — particularly the fixed-library RS (59.3%) and OPD (62.5%) numbers — are conditional on a specific seed library whose quality is not independently characterized. A practitioner attempting to replicate HASP on a new domain would need to perform their own failure analysis to construct a seed library, and there is no guarantee that their analysis would identify the same failure patterns with the same quality. The evolution pipeline partially addresses this (it can add missed patterns and filter out harmful PFs), but the paper's results show that evolution contributes only +1.0 point over the fixed library (59.3% → 60.3%). The bulk of HASP's performance comes from the seed library, not from evolution. If the seed library is substantially worse than the paper's, the entire system's performance would degrade — and the paper provides no guidance on how to assess seed library quality or how much degradation to expect from suboptimal initial skill design.

This limitation is particularly acute for practitioners working in domains where failure analysis requires domain expertise (medical reasoning, legal analysis, scientific research). The paper's failure analysis uses heuristic detectors (12 hand-coded rules, Appendix C.2) and LLM-based abstraction (Prompt C.1), both of which require the analyst to know what failure modes to look for. In a novel domain, the analyst may not know the failure taxonomy in advance, and iterative discovery through evolution may be slow.

**What evidence exists in the paper.** The filtering ablation in Table 5 provides indirect evidence for the importance of library quality: unfiltered evolution (where any proposed PF is admitted) causes a 24-point collapse (from 60.3% to 36.3%), demonstrating that library composition matters enormously. The per-family review scores in Table 18 (Appendix I.1) show substantial variation across skill families — `reasoning_hallucination` scores 0.89 composite, while `wrong_entity_focus` scores 0.80 — but these are scores of *evolved* skills, not the seed library, and the paper does not report analogous quality metrics for the seed PFs. The prompt-equivalent skills ablation (Table 7, Appendix B.5) shows that adding 10 prompt-equivalent skills to the library produces small and mixed effects (+3.5 to −3.5 points across datasets), but this tests the marginal effect of *adding* skills, not the effect of the *initial* skill composition.

The paper does not include an ablation where the seed library is degraded (e.g., removing the highest-impact PFs, adding deliberately noisy PFs, or randomizing intervention targets) to measure how sensitive results are to seed quality. It does not compare multiple seed libraries constructed by different analysts or different LLM-based summarization procedures.

**Mitigation status.** The paper does not address this limitation directly. The evolution pipeline is presented as the mechanism for improving an imperfect initial library — "closed-loop evolution further improves the external skill library" (Section 4.1) — but the small +1.0 point gain over the fixed library suggests that evolution refines rather than rescues. The paper's recommendation in Appendix C.8 — "self-improvement is useful only when library evolution is tightly controlled" — implicitly acknowledges that library quality is paramount, but it provides no methodology for assessing or ensuring seed library quality beyond the executable validation and teacher review gates (which are designed for evolved skills, not seed skills). A practitioner would need to independently validate their seed library on a held-out set before trusting HASP's performance, and the paper provides no protocol for this validation.

### Test Sets Are Small, and No Multi-Seed Training Variance Is Reported

**The assumption or constraint.** The paper's evaluation uses test sets of 200 questions per dataset for web-search reasoning (HotpotQA, 2Wiki, MuSiQue), 30–1,362 problems for math (AIME24, AMC23, GameOf24), and 50–148 problems for coding (HumanEval+, MBPP+, BigCodeBench). All training runs use a single seed (seed = 42) for model initialization, data shuffling, and validation-pool construction (Appendix J.4). The paper explicitly acknowledges: "We report all results from a single seed because re-running E1–E6 across multiple seeds is prohibitive" and estimates rollout variance at ±1.5 points based on internal smoke tests with `k = 4` rollouts.

**The consequence.** The reported performance differences — particularly the smaller ones — may not be statistically reliable. The +1.0 point gain from HASP-Evolve + RS over HASP + RS (60.3% vs. 59.3%, Table 4) is smaller than the estimated rollout variance of ±1.5 points, meaning it could plausibly be zero or negative under a different random seed. The 7.1-point gap between HASP-Evolve + RS (60.3%) and AgentFlow + Flow-GRPO (53.2%) is substantially larger than the estimated variance, so the qualitative conclusion ("HASP outperforms AgentFlow on web-search") is likely robust, but the precise margin is uncertain.

More importantly, the paper does not distinguish between **rollout variance** (variation in trajectory sampling given a fixed policy) and **training variance** (variation in final policy performance due to random seed in initialization, data ordering, and dropout). The ±1.5 point estimate from `k = 4` rollouts captures only the former, while the latter is typically much larger for LLM fine-tuning — multi-seed training variance of 2–5 points is common for 7B models on small test sets. The paper's claim that ±1.5 points is "smaller than the gaps reported in Table 2" is true for the large gaps (25.0 points for PF-only vs. RA-Agent) but may not hold for the smaller recipe-comparison gaps (e.g., +3.1 for RS over inference-only, +6.3 for OPD over inference-only, Table 4).

The small test sets compound this problem. With 200 questions per web-search dataset and five difficulty quintiles, per-bin analysis would have approximately 40 questions per bin — too few for reliable per-difficulty conclusions. The paper does not report per-difficulty breakdowns for any result (unlike the reference example paper which provides detailed difficulty-bin analysis in Figures 3, 7, and 9), instead relying on per-dataset aggregation (HotpotQA vs. 2Wiki vs. MuSiQue) as a coarse difficulty proxy.

**What evidence exists in the paper.** Appendix J.4 explicitly states: "We flag the absence of multi-seed numbers as a known limitation." The estimated standard deviation of ±1.5 points is based on "internal smoke tests" rather than a systematic variance study. The paper reports per-dataset numbers in Tables 2 and 3, allowing readers to assess consistency across datasets rather than relying solely on averages, but within-dataset variance (e.g., across different subsets of the 200 test questions) is not reported.

**Mitigation status.** The paper acknowledges this limitation transparently (Appendix J.4) but does not attempt to mitigate it — no confidence intervals, no bootstrap estimates of test-set variance, no multi-seed training runs even for a subset of the experiments. The deterministic seed (42) and the pinning of GPT-4o to a specific snapshot (`gpt-4o-2024-11-20`) provide reproducibility at the cost of unknown generalization to other seeds. For a practitioner deciding whether to adopt HASP, the key question — "how much better than my current system will this be, and how certain am I of that estimate?" — cannot be answered with the reported data alone.

### The PF Interface Assumes a Structured Action Space with Clear Failure Boundaries, Limiting Transfer to Open-Ended Domains

**The assumption or constraint.** The PF interface — `should_activate(step_context, action_type, arg) -> bool` and `intervene(...) -> Intervention` — depends on two structural properties of the agent's decision loop that are present in the evaluated domains but may be absent in others:

1. **A discrete, low-dimensional action space.** The web-search domain has exactly three action types (SEARCH, READ, FINAL) with string arguments. Math and coding collapse to a single FINAL action. The `should_activate` predicate inspects `action_type` and `arg` as structured fields, and the `MODIFY_ACTION` intervention type directly rewrites them. In domains with continuous action spaces (robotics), high-dimensional action spaces (open-ended dialogue generation), or actions that cannot be meaningfully "rewritten" by a deterministic function (creative writing, negotiation), the PF interface has no natural mapping.

2. **Well-defined, detectable failure states.** The paper's Phase B failure detectors (12 heuristic rules + LLM-based abstraction) operate on structural properties of the trajectory: search queries with token-Jaccard > 0.8 (repeated search), FINAL with no prior READ (premature finalization), answer/gold token overlap < 30% (wrong entity focus). These detectors work because "failure" in web-search QA means something specific and detectable — the agent arrived at the wrong answer, and the trajectory usually contains visible signs of the error. In domains where failure is ambiguous (is a generated story "good"?), delayed (a planning error manifests 20 steps later), or multi-dimensional (a negotiation outcome is partially satisfactory), the failure analysis pipeline that feeds PF design may not produce useful abstractions.

The paper acknowledges this scope limitation in Appendix A: "our evaluation focuses on benchmark-style search, math, and coding tasks with relatively clear verification signals, leaving transfer to open-ended, long-horizon, interactive, or weakly verifiable environments unresolved."

**The consequence.** A practitioner cannot assume that HASP will transfer to their domain without substantial adaptation. The PF interface may need to be extended (e.g., to support intervention types beyond `MODIFY_ACTION` and `INJECT_CONTEXT`), the failure detection pipeline may need to be redesigned (since heuristic detectors assume a ReAct loop structure), and the signal scoring system (which relies on "correctness" defined as exact match or test-pass) may need alternative quality metrics. The paper provides no evidence on how much of HASP's performance is attributable to the PF *interface* versus the PF *content* that was carefully designed for ReAct-style web-search tasks. It is possible that the interface is general but the engineering effort to instantiate it in a new domain is comparable to building a domain-specific agent from scratch.

The coding domain results (Table 3) provide a partial test of this limitation: coding reduces to a single FINAL action, so the action-modification surface is unavailable, and all PFs operate through static-analysis hints (`INJECT_CONTEXT`) or NOOP audit records. The gains are meaningfully smaller (63.4% PF-only vs. 60.8% raw Qwen, a 2.6-point improvement) compared to web-search (51.0% vs. 31.2%, a 19.8-point improvement). This suggests that a substantial portion of HASP's web-search gains come from the `MODIFY_ACTION` surface — the ability to rewrite search queries and force READs — which is unavailable in single-step domains. In domains where actions cannot be meaningfully rewritten (e.g., "generate a paragraph of dialogue"), the remaining `INJECT_CONTEXT` surface may provide only modest gains comparable to the coding results.

**What evidence exists in the paper.** The cross-domain results in Tables 2 and 3 provide implicit evidence: gains are largest on web-search (where the PF interface is richest), moderate on math (where `pre_final` verification hooks provide a limited intervention surface), and smallest on coding (where PFs are reduced to static-analysis hints). The intervention-type statistics in Section 4.2 (65.1% `MODIFY_ACTION`, 34.9% `INJECT_CONTEXT`) show that action modification is the dominant intervention mode driving the web-search gains. The paper's coding PF design note (Appendix B.4) — "auto-patching student code is judged too risky" — illustrates a domain where the `MODIFY_ACTION` surface is available in principle but judged unsafe in practice, further constraining HASP's applicability.

The paper does not evaluate HASP on any domain outside the three benchmark families (web-search QA, competition math, coding), so there is zero direct evidence about transfer to open-ended dialogue, creative writing, embodied planning, negotiation, or other domains with ambiguous, delayed, or multi-dimensional success criteria.

**Mitigation status.** The paper acknowledges this limitation in Appendix A ("leaving transfer to open-ended, long-horizon, interactive, or weakly verifiable environments unresolved") but does not propose specific extensions to address it. The PF interface's reserved intervention-type slots (`s2.pre_reasoning` and `s2.post_action` in the modality signal, Appendix E) suggest that the authors anticipate future intervention surfaces, but no implementations or experiments with these surfaces are reported. A practitioner facing an open-ended domain would need to (a) determine whether their action space can be discretized into meaningful intervention targets, (b) design domain-specific failure detectors (likely requiring human expertise rather than the paper's automated heuristics), and (c) validate that PF interventions in their domain produce net-positive effects rather than the catastrophic interference seen in the unfiltered evolution ablation — all without guidance from the paper.

### The Revision Model's Correct-to-Incorrect Reversion Problem Has No Architectural Solution

**The assumption or constraint.** When a PF `MODIFY_ACTION` intervention overrides the policy's proposed action, it does so deterministically and irrevocably for that step. However, the paper documents a failure mode where PFs that modify actions can themselves introduce errors: **PF override harm**. Table 6 (Section 4.2) lists the failure family `pf_override_harmful`, which accounts for 8.7% of recovered failure cases in the web-search domain, with an average ΔEM of −0.8 points and ΔAcc. of −0.8 points — meaning that PF interventions sometimes **degrade** performance relative to what the uncorrected policy would have done.

This is a structural consequence of the PF design: PFs are deterministic state-action intervention functions that operate on a limited view of the agent's state (the `step_context` dictionary) and fire based on hand-designed predicates. They have no mechanism for assessing their own uncertainty, no ability to learn from their own mistakes (they are stateless across episodes), and no fallback protocol when their intervention produces a worse outcome than the original action. The anti-oscillation guards (`_MAX_MODIFY_FIRES = 2`, `_MAX_FINAL_OVERRIDES = 1`) prevent infinite loops but do not prevent a single harmful override.

**The consequence.** A deployed HASP system has no built-in mechanism for detecting or recovering from harmful PF interventions. If a PF fires on a state where its predicate is technically satisfied but its intervention is inappropriate — e.g., `insufficient_exploration` forces a READ on a document that is clearly irrelevant, wasting a step and potentially introducing distracting information — the agent loop has no way to recognize this as a PF error and roll back. The harmful intervention becomes part of the trajectory history, potentially derailing subsequent reasoning.

This is particularly concerning in the closed-loop evolution setting. If a newly-admitted PF causes harmful overrides during training-data generation (Phase A), those harmful interventions will be scored by the four-signal system, potentially receive non-zero credit (if the episode happened to succeed despite the harmful override, the outcome signal would still be positive), and be included in the training data for the next policy iteration. The paper's RS recipe partially mitigates this by filtering trajectories on both task success and intervention quality, but the filtering threshold (`min_score = 0.15` on a composite `0.7 * EM + 0.2 * F1 + 0.1 * StepEconomy`, Appendix D.4) is lenient enough that trajectories with one harmful override and eventual success could still pass.

The unfiltered evolution ablation in Table 5 (36.3% accuracy, a 24-point drop) is the paper's most dramatic illustration of this consequence: when harmful PFs are admitted to the library without quality control, they interfere with correct policy behavior and the entire system collapses.

**What evidence exists in the paper.** Table 6 quantifies the `pf_override_harmful` failure family at 8.7% of recovered cases with negative average impact (−0.8 points). The filtering ablation in Table 5 shows that removing quality gates during evolution causes a 24-point collapse — part of this collapse is attributable to harmful PFs overriding correct actions. The per-family review scores in Table 18 show that `pf_override_harmful` has a relatively low intervention score (0.90 compared to 0.92 for `reasoning_hallucination`) and concept score (0.80 compared to 0.90), suggesting that even the teacher review process recognizes harmful overrides as a quality concern. However, the paper does not report what fraction of harmful overrides are caught by the teacher review gate vs. slipping through — it only reports aggregate filtering effects.

The case study in Appendix G.4 provides qualitative evidence: in the web-search trajectory, `insufficient_exploration` correctly fires on a premature FINAL and forces a READ — but the paper does not show a case where a PF *incorrectly* fires and the agent fails as a result, which would illustrate the harm mechanism more directly.

**Mitigation status.** The paper addresses PF override harm through three mechanisms, none of which fully solves the problem:

1. **Rate limiting and anti-oscillation guards** (Appendix B.1): `_MAX_MODIFY_FIRES = 2`, per-skill caps, `_MAX_FINAL_OVERRIDES = 1`. These prevent a harmful PF from dominating the trajectory but do not prevent individual harmful overrides.

2. **Strict two-gate filtering during evolution** (Section 3.3): executable validation and teacher review catch many harmful PFs before they enter the library. The filtering ablation shows that removing either gate causes a 11.5–13.1 point drop, and removing both causes a 24-point collapse. However, this only addresses *new* PFs entering the library — it does not detect harmful behavior from PFs already in the seed library (which were designed by human analysts and may have edge cases the analysts missed).

3. **Outcome signal penalties** (Appendix E): the `s4.side_effect` sub-signal applies a −0.10 penalty when "a PF modified the action but the episode still failed." This penalizes harmful overrides in training but does not prevent them at inference time, and the penalty is small (−0.10 out of a maximum 0.50 outcome weight).

The paper does not propose a **runtime override-detection mechanism** — e.g., monitoring PF intervention effects and rolling back if the subsequent observation suggests the override was harmful, or using the teacher to validate PF interventions before they are executed. The architectural assumption is that PFs are correct by construction (validated during library admission) and that the few harmful overrides are an acceptable cost. For safety-critical deployments, this assumption may not hold.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

HASP instigates a shift in how the field thinks about reusing agent experience — from *storing lessons as text* to *deploying lessons as executable code*. This is not an incremental improvement to prompt engineering; it is a **reification of skills into computational objects** that changes what skills can do. Before HASP, the default mental model was: "agents learn from mistakes, store verbal reflections, retrieve them later, and (hopefully) follow the advice." The paper demonstrates that this model's central weakness — the advisory gap between knowing and doing — can be closed not by improving retrieval or prompt formatting, but by changing the *locus of control*. A Program Function that fires deterministically on a premature FINAL and rewrites it to a READ is fundamentally a different kind of artifact than a textual reminder to "verify evidence before finalizing." The former *guarantees* the behavior; the latter *requests* it.

The magnitude of this shift is visible in the paper's most dramatic number: the 30.5-percentage-point gap between Prompt-Only Skills (20.5%) and PF-only intervention (51.0%) on web-search reasoning (Table 2). These conditions encode the same skills — the same lessons about decomposition, verification, and exploration — differing only in whether the skill is executed as code or injected as text. A 30.5-point gap that comes entirely from format, not content, is a **paradigm-level finding**: it says that the dominant paradigm of the past five years (textual skill memory) has been leaving a substantial fraction of recoverable performance on the table, not because the skills were wrong, but because the delivery mechanism was structurally incapable of enforcing them.

This work also reconciles a latent contradiction in the agent self-improvement literature. Systems like Reflexion, ExpeL, and SKILL0 demonstrated that storing and retrieving lessons from past failures improves agent performance — sometimes substantially. But the improvements were inconsistent across tasks, models, and implementations, and the mechanism of improvement was opaque (was the agent actually following the advice, or was the improved performance due to some other aspect of the system?). HASP provides a diagnostic framework for answering this question: the four-dimensional signal scoring system (timing, modality, correctness, outcome) lets researchers measure not just *whether* performance improved, but *how* the interventions contributed — did they fire at the right time? Use the right mechanism? Produce valid repairs? Improve downstream outcomes? The paper's finding that 65.1% of PF interventions are action-level (`MODIFY_ACTION`) rather than context-level (`INJECT_CONTEXT`) — and that removing the modality signal causes the largest single-dimension performance drop (−15.5 points, Table 5) — suggests that *action modification*, not textual guidance, is the primary driver of improvement. Prior textual-skill systems had no way to measure this distinction.

The work redirects research attention in three specific ways:

**1. From retrieval quality to execution reliability.** The textual-skill literature has focused heavily on *retrieval* — how to find the right lesson at the right time, through similarity search, learned retrievers, or structured memory. HASP demonstrates that retrieval is only half the problem; the other half is *enforcement*, and enforcement failure (the agent retrieves the right skill but ignores it) may dominate retrieval failure (the agent fails to retrieve any relevant skill). The paper's Prompt-Only Skills condition effectively has perfect retrieval — all relevant skill text is injected into the prompt — yet underperforms PF-only by 30.5 points. This suggests that the field's investment in retrieval infrastructure may have been chasing diminishing returns while the enforcement gap remained unaddressed. Future work on agent memory should measure not just "was the right memory retrieved?" but "was the retrieved memory actually followed?" — and HASP's PF activation logging provides a template for making this measurement.

**2. From monolithic policy optimization to modular policy correction.** RL-based agent training (Search-R1, AgentFlow, ReSearch) treats the agent as a black-box policy to be optimized through reward signals. HASP demonstrates that a modular architecture — where the base policy proposes actions and an external harness corrects them when needed — can match or exceed RL-based methods on certain tasks (60.3% vs. 53.2% for AgentFlow on web-search, Table 2) while providing auditability, determinism, and independent updatability that black-box optimization cannot offer. This does not make RL obsolete — the paper explicitly notes that PFs cannot discover fundamentally new strategies — but it does reframe the design space: RL is most valuable for capability *creation* (expanding the frontier of what the model can do), while PF-style guardrails are most valuable for capability *elicitation* (ensuring the model reliably does what it already can). A practical research program emerges from this distinction: identify which failure modes are execution errors (correctable by PFs) vs. capability gaps (requiring RL-based exploration), and apply the right tool to each.

**3. From unconstrained self-improvement to validated, rate-limited library growth.** The paper's most important negative result — that unfiltered skill evolution causes a 24-point accuracy collapse (Table 5, "Evolution, no filtering") — establishes a boundary condition for self-improving agent systems. The intuition that "more experience → more skills → better performance" is dangerously wrong for executable skills. Adding a badly-designed PF to the library does not just fail to help — it actively corrupts the agent loop, overriding correct actions with harmful ones. This finding has implications beyond HASP: any system that learns executable behavioral rules from experience, whether for agents, robots, or software, needs admission control. The paper's two-gate architecture (executable validation + teacher review) provides a concrete template, and the ablation results (49–60% with partial filtering vs. 36% with none) quantify the cost of getting this wrong.

### Follow-Up Research This Work Enables

**Combining PF-style guardrails with RL-based exploration for a hybrid agent improvement pipeline.** The paper's clearest open question is whether PFs (which elicit existing capabilities) and RL (which discovers new ones) can be productively combined. The paper's architecture is designed for this — the PF library is external to the model and can be used with any training method — but the experiment has not been run. A strong follow-up would take the same Qwen2.5-7B-Instruct base model, the same web-search benchmarks, and train with (a) HASP-Evolve + RS alone (60.3% from the paper), (b) AgentFlow-style RL alone (53.2%), and (c) a hybrid where RL exploration is guided by PF-derived reward bonuses on intervention-corrected states. The key question is whether PFs accelerate RL by providing dense intermediate rewards (e.g., +reward when the agent's action matches what a PF would have done) — potentially combining PF-speed with RL's ability to discover new strategies. The paper's finding that behavior-correcting PFs become "silent" after training (Section 4.2) suggests that PFs can serve as a curriculum that gradually removes itself as the agent internalizes the corrections, which is exactly the property you would want from a scaffolding mechanism in a hybrid training pipeline.

**Teacher-free HASP: measuring the cost of external model dependence.** The paper's full HASP configuration relies on GPT-4o for PF selection, FINAL-time handlers, and (in OPD) trajectory distillation, at a cost of approximately $0.045 per web-search question (Appendix K). The PF-only ablation (51.0%, Table 5) strips away the teacher at inference time, but all post-training recipes (SFT, RS, OPD) use teacher-augmented training data. A critical stress-test would be a **fully teacher-free HASP pipeline**: PF-only inference (deterministic code paths, no teacher calls) + lite evolution (Appendix D.5, no teacher review) + training data scored without teacher-judged semantic correctness (`s3.semantic`). This would establish the lower bound of HASP's performance with zero external model dependence. The gap between this lower bound and the full HASP-Evolve + RS result (60.3%) would quantify the value of teacher access and inform deployment decisions. Based on the paper's partial evidence — PF-only inference at 51.0%, lite evolution retaining "most" of full evolution's benefit (Appendix D.5), and the −12.1-point impact of removing the correctness signal (which includes teacher-judged semantic quality, Table 5) — I would estimate a fully teacher-free HASP in the 45–50% range on web-search reasoning. Confirming or refuting this estimate would determine whether HASP is viable for organizations that cannot or will not depend on proprietary model APIs.

**PF libraries as cross-model transfer mechanisms.** The paper evaluates HASP on a single base model (Qwen2.5-7B-Instruct). An obvious extension is to test whether a PF library developed for one model transfers to another — e.g., take the web-search PF library trained and validated on Qwen2.5-7B-Instruct and apply it at inference time to a different 7B model (Mistral, LLaMA), a different scale (Qwen2.5-1.5B, Qwen2.5-14B, Qwen2.5-72B), or a different model family entirely. The paper's elicitation-vs-creation framework predicts that PFs should transfer to any model that possesses the capabilities being elicited — a model that can decompose questions and verify evidence should benefit from the same `decompose_complex_question` and `insufficient_exploration` PFs regardless of its architecture. If transfer is successful, PF libraries become a form of **behavioral middleware** — write once, deploy across models, update centrally. If transfer fails (because PFs depend on model-specific failure patterns that differ across architectures), it would reveal that PF libraries are more tightly coupled to their base model than the paper assumes, limiting their reusability. The experiment is straightforward: take the web-search PF library and evaluation protocol from the paper, swap in different base models, and measure PF-only inference performance vs. the RA-Agent baseline for each model.

**Dynamic, state-dependent PF selection and difficulty-aware allocation.** The paper's current PF selection mechanism runs once per question (the `PFSelector` in Section 3.1 and Appendix B.6). This means the same PFs are active for all steps of a trajectory, regardless of whether the agent is on step 1 (exploring broadly) or step 8 (about to finalize). The paper's phase-gated reminders partially address this (e.g., `pre_final` reminders only render when the agent is about to finalize), but the core PF library is static per episode. A natural extension is **dynamic PF selection** that adjusts the active PF set based on the agent's current state within the trajectory — analogous to how the reference example paper (on compute-optimal test-time scaling) selects different search strategies based on estimated problem difficulty. Concretely: at step 1, activate exploration-oriented PFs (`decompose_complex_question`, `insufficient_exploration`); by step 5, after evidence is gathered, activate verification-oriented PFs (`answer_completeness`, `verification_missing`); if the agent shows signs of thrashing (repeated similar queries, high step count), activate loop-breaking PFs (`iterative_refinement`). This would reduce prompt clutter (fewer irrelevant PFs competing for attention), improve intervention precision (PFs only fire when their target failure mode is likely), and potentially reduce the teacher cost (if PF selection can be automated with a lightweight classifier rather than a GPT-4o call). The experiment would compare static PF selection (the paper's default) against dynamic selection on web-search reasoning, measuring both accuracy and PF precision (the fraction of PF activations that were appropriate, as judged by the timing signal).

**End-to-end PF synthesis: automating the initial library construction.** The paper's seed PF library is hand-crafted from failure analysis — a human (or LLM-guided by human heuristics) examined failed trajectories, identified recurring failure modes, and designed PF predicates and interventions. This is the single largest barrier to adopting HASP in a new domain. The self-improvement pipeline (Phases A–H) can refine an existing library, but it requires a seed library to start from. A critical extension would be **automated seed library construction**: given a training pool of questions and a base model, run the multi-loop agent (no PFs) to collect failure trajectories, run the Phase B failure detection and clustering pipeline, run Phase C candidate proposal without a seed library (the proposer must generate PFs from scratch rather than refining existing ones), and then apply the same Phase D/E/F filtering to build the initial library — all without human-designed heuristics or pre-existing PFs. This would test whether the self-improvement pipeline can *bootstrap* itself from zero skills, rather than requiring expert initialization. The paper's Phase B heuristic detectors (12 hand-coded rules, Appendix C.2) are themselves a form of prior knowledge — they encode what failure modes look like. Removing them and relying solely on the LLM-based failure summarizer would test whether the pipeline can discover failure patterns without human guidance. Success would dramatically expand HASP's applicability; failure would reveal that expert failure analysis is a prerequisite for the approach, not an optional input.

**Negative result: testing whether PFs can *create* new strategies through search over interventions.** The paper is explicit that PFs elicit existing capabilities rather than creating new ones. But what if PFs were used differently — not as guardrails that correct individual actions, but as *operators* in a search process over the space of possible trajectories? Concretely: run the agent with all MODIFY_ACTION PFs disabled, collect a set of candidate trajectories, then retroactively apply different subsets of PFs to those trajectories to produce modified versions, and select the best modified trajectory by final-answer verification. This reframes PFs as a transformation library applied *offline* to generate candidate solutions, rather than *online* as guardrails. The experiment would test the paper's capability-ceiling claim directly: if the base model never produces trajectories that approach the correct answer (AIME24-style problems), then no amount of PF retroactive modification can create correctness from nothing — the PF-transformed trajectories would still be wrong, just wrong in different ways. If, however, some of the transformed trajectories become correct, it would indicate that PFs can contribute to capability *creation* by recombining fragments of correct reasoning that the base model generated in different attempts — a form of search over compositional interventions. This is a high-risk, potentially high-reward experiment: the paper's strong elicitation-creation claim predicts failure on hard problems; confirmation of that failure would sharpen the boundary between PF-amenable and RL-necessary tasks, while disconfirmation would require revising upward the scope of what PFs can achieve.

### Practical Applications and Downstream Use Cases

**Cost-efficient batch inference for search-augmented QA pipelines.** Organizations running large-scale question-answering over document collections — customer support, legal research, medical literature review — often deploy LLM agents with search capabilities. The paper's results on web-search reasoning translate directly to this setting. The inference-time HASP-Intervention configuration (56.2% accuracy with teacher, 51.0% without, Table 2) can be deployed as a drop-in harness around an existing ReAct agent, requiring no model retraining. The per-question cost of the full configuration (~$0.045, Appendix K) is modest for high-value queries (legal/medical), and the PF-only configuration eliminates API costs entirely for cost-sensitive applications. The structured intervention logging (every PF activation records the trigger, the before/after action, and the reason) provides audit trails that are valuable in regulated domains — a legal research tool can demonstrate that it *did* verify sources before finalizing, not just claim that it did. The 30.5-point gap between Prompt-Only Skills and PF-only intervention means that organizations currently using textual skill prompts can expect substantial improvement from converting their skill libraries to executable PFs, even without any training.

**Training data generation for model fine-tuning and distillation.** The paper's PF-guided rejection sampling recipe (HASP + RS at 59.3%, HASP-Evolve + RS at 60.3%, Table 4) provides a methodology for generating high-quality training trajectories that are both task-successful and behaviorally clean. This has direct application in self-improving LLM pipelines where the goal is to fine-tune a model on its own outputs. Standard rejection sampling filters trajectories on final correctness alone, which can retain trajectories that arrived at the right answer through poor intermediate decisions (e.g., guessing, relying on a single unverified source). HASP's composite scoring — blending task success with intervention quality (timing, modality, correctness, outcome) — produces training data where *how* the answer was reached matters, not just *what* the answer is. For organizations building specialized reasoning agents (medical diagnosis, financial analysis, code review), this means the fine-tuned model is trained to replicate not just correct answers but correct *processes* — decomposing questions, verifying evidence, checking edge cases — leading to more robust deployment behavior. The training cost is modest: LoRA fine-tuning on 1–2 L40S GPUs (Appendix J.1), within reach of most organizations with access to cloud GPU instances.

**On-device agent deployment with external guardrail updates.** The paper's separation of the PF library from the model weights enables a deployment architecture where a small, on-device base model is paired with a centrally-maintained, frequently-updated PF library. The base model handles core reasoning and tool use; the PF library, distributed as a versioned package (`skill_ids_latest`), provides up-to-date guardrails against known failure modes. When a new failure pattern is discovered in production (e.g., the agent systematically mishandles a new query format), the PF library can be updated — adding a new PF or refining an existing one's trigger condition — without retraining or redeploying the base model. The paper's evolution pipeline (Phases A–H) provides the mechanism for producing these library updates from production failure logs. This architecture is particularly attractive for mobile or edge deployments where model updates are expensive (download size, inference compatibility) but configuration updates (a few hundred lines of Python) are cheap. The paper's finding that the seed library accounts for the bulk of performance gains (+59.3% fixed vs. +60.3% evolved, Table 4) means the initial library deployment already provides substantial value, with evolution providing incremental refinement as new failure modes are encountered.

### When to Prefer This Method

The paper articulates a clear boundary condition in its conclusion — PFs elicit existing capabilities rather than creating new ones — which translates directly into a deployment decision rule grounded in the empirical results:

- **Prefer HASP with PF-only inference (no training) when:** the base model already achieves non-trivial pass@1 on the target task (>15–20%), you need immediate improvement without model retraining, and the task has a structured action space where specific failure modes can be detected deterministically. Evidence: PF-only reaches 51.0% on web-search vs. 31.2% for the multi-loop baseline (Table 2), a 19.8-point gain with zero training cost.

- **Prefer HASP with PF-guided rejection sampling when:** you can afford modest training (LoRA fine-tuning, 1–2 GPUs), the base model's pass@1 is in the 20–40% range (moderate capability, ample room for elicitation), and task success depends on consistent execution of known strategies rather than discovery of novel ones. Evidence: HASP + RS reaches 59.3% on web-search (Table 4); on AIME24, where the base model's pass@1 is low and novel strategy discovery dominates, even HASP-Evolve + RS reaches only 16.7% vs. 40.0% for RL-based AgentFlow (Table 2).

- **Prefer RL-based training (Search-R1, AgentFlow) when:** the base model's pass@1 on the target task is near zero, the task requires discovering genuinely new reasoning strategies that are not present in the model's output distribution, or the action space is continuous/high-dimensional and does not admit deterministic intervention predicates. Evidence: the AIME24 gap (16.7% HASP vs. 40.0% AgentFlow, Table 2) is the canonical case where capability creation dominates capability elicitation.

- **Prefer HASP with closed-loop evolution (HASP-Evolve + RS) when:** the task distribution is non-stationary or includes rare failure modes not captured in the initial failure analysis, and you have infrastructure for periodic offline library updates. Evidence: the +1.0 point gain from evolution (59.3% to 60.3%, Table 4) is modest, but the 24-point penalty for unfiltered evolution (Table 5) demonstrates that controlled evolution is essential if the library is to grow at all — you cannot simply let it expand unchecked.

The critical diagnostic for choosing between these approaches is the **base model pass@1 on the target task**. If it is above ~15–20%, PFs can help; if it is below ~5%, PFs cannot help (there are no correct behaviors to elicit), and you should invest in a stronger base model or RL-based exploration. The paper does not provide a continuous difficulty-performance curve to make this threshold precise, but the pattern across web-search (pass@1 ~31% for the base multi-loop agent, large PF gains), math (pass@1 varies from ~7% on AIME24 to ~50% on AMC23, mixed gains), and coding (pass@1 ~61% for the base model, small but meaningful gains) is consistent with this heuristic.
