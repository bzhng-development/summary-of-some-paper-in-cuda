# Fiddler: CPU-GPU Orchestration for Fast Inference of Mixture-of-Experts Models

**ArXiv:** [2402.07033](https://arxiv.org/abs/2402.07033)

## 🎯 Pitch

This paper proposes **Fiddler**, a resource-efficient inference system for Mixture-of-Experts (MoE) models running on heterogeneous CPU-GPU architectures with limited GPU memory.

---

## 1. Executive Summary

This paper proposes **Fiddler**, a resource-efficient inference system for Mixture-of-Experts (MoE) models running on heterogeneous CPU-GPU architectures with limited GPU memory. Fiddler introduces a **compute-optimal execution strategy** that dynamically routes expert layer computation between CPUs and GPUs based on the number of input tokens each expert receives, exploiting the differing batching effects of the two processors—CPU latency scales nearly linearly with input size while GPU latency stays near-constant, but GPU execution incurs a weight-transfer overhead when expert weights aren't already resident in GPU memory. Evaluated on the uncompressed Mixtral-8x7B model (47B parameters, >90GB of weights) across two single-GPU environments, Fiddler achieves 1.26× speedup in single-batch inference, 1.30× in long-prefill processing, and 11.57× in beam search inference over state-of-the-art baselines, establishing that resource-constrained MoE deployment benefits from adaptive CPU-GPU orchestration rather than the fixed strategies of existing offloading-based or CPU-based systems.

## 2. Context and Motivation

### The Core Problem: Running Massive MoE Models on Scarce GPU Resources

This paper addresses a practical deployment challenge that is growing in urgency: **how do you run Mixture-of-Experts (MoE) language models efficiently when your GPU memory is far smaller than the model itself?** This isn't a niche problem — it's a scenario that affects almost anyone who wants to run state-of-the-art open-weight LLMs locally without access to multi-GPU server clusters.

To make the problem concrete, consider the dimensions involved. The paper's evaluation model, Mixtral-8x7B, uses 16-bit precision and requires over 90GB of storage for its 47 billion parameters. An NVIDIA A100 80GB GPU can't hold it all. The situation gets worse rapidly: more recent MoE models push into the hundreds of billions of parameters — Mixtral-8x22B at 141B, DBRX at 132B, DeepSeek-V2 at 236B, Grok-1 at 314B, and Snowflake Arctic at 479B parameters (Section 1). Storing Arctic's weights alone in 16-bit precision would demand nearly a terabyte of memory. These aren't exotic numbers; they represent the current trajectory of open-weight model releases.

The fundamental mismatch is structural. MoE models scale primarily by adding more experts per layer (Switch Transformer's largest variant has 2,048 experts per layer at 1.6T total parameters) or by increasing the hidden dimension, which inflates each expert's weight matrix. But **the number of GPUs available isn't scaling with model size** — and even when multiple GPUs are accessible, the economics are punishing. GPU costs have been driven up by soaring demand for generative AI, meaning that only major cloud providers ("hyperscalers") can justify large GPU clusters because they achieve high utilization through substantial batching across many concurrent users. For researchers, small organizations, and individual practitioners running inference locally — whether for privacy, customization, or cost reasons — this creates a stark barrier to entry.

### The MoE Property That Creates an Opportunity — and a Problem

MoE models have a distinctive characteristic that makes this problem both harder and solvable: **sparse activation**. For each token processed, the gating network in each MoE layer activates only a small subset of experts (typically 2 out of 8, or similar ratios). This means that at any given moment, the vast majority of the model's parameters are sitting idle.

This sparse activation creates two opposing forces for resource-constrained systems:

- **It's an opportunity**: not all weights need to be in fast memory at once. If you could somehow keep only the active experts accessible and store the rest somewhere cheaper, you could run massive models with modest hardware.

- **It's also a problem**: GPUs need weights in GPU memory to compute efficiently. If you move all weights to CPU memory and transfer them to GPU on-demand, you introduce enormous data movement overhead. The paper quantifies this: a single expert layer in Mixtral-8x7B has three weight matrices of size 4096×14336 each, consuming over 300MB at 16-bit precision. If you need to shuffle multiple 300MB chunks across the PCIe bus for every token during generation, the latency becomes prohibitive (Section 3.2, Appendix A).

The critical comparison in Appendix A bears emphasis: **transferring one expert's weight from CPU to GPU takes 2–5× longer than actually computing the expert on the GPU**. This means that in a naive offloading scheme, you spend most of your time waiting for data to cross the PCIe bus, not doing useful computation. The GPU's parallel processing capabilities are wasted while it idles waiting for the next weight transfer to complete.

### Prior Approaches and Their Specific Shortcomings

The paper identifies two major lines of existing work, each with a distinct failure mode when applied to MoE models in resource-constrained settings.

#### Offloading-Based Systems: The Bandwidth Bottleneck

Offloading approaches store model weights in CPU memory (which is abundant — hundreds of gigabytes or more) and transfer required weights to GPU memory on demand at runtime. Systems like DeepSpeed-MII with ZeRO-Infinity optimization, Mixtral-Offloading, and MoE-Infinity fall into this category. The idea is sound: use CPU memory as extended storage and only pay the transfer cost for what you actually need.

However, the paper identifies a fundamental mismatch between this approach and the properties of MoE models. The key issue is **PCIe bandwidth versus GPU memory bandwidth**. PCIe Gen3 x16 (used in the paper's Environment 1, Table 1) provides 32GB/s; PCIe Gen4 x16 provides 64GB/s. GPU memory bandwidth for even a consumer-grade card is an order of magnitude higher. When you're processing the attention layers (which are dense and used for every token), transferring their weights once is manageable. But for MoE layers, where different experts are activated for different tokens, you're potentially transferring different 300MB chunks on every decoding step. This is why the paper states these systems "suffer significant latency overhead due to the frequent transfer of expert weights between the CPU and the GPU over the PCIe connection" (Section 2.2).

The consequence: offloading-based systems perform well in throughput-oriented scenarios (where you can batch many requests together and amortize the transfer cost) but show "suboptimal performance for the settings where latency is critical for user experience" — which is exactly the scenario that matters for local, interactive inference.

#### CPU-Based Inference Frameworks: The Batching Blind Spot

Frameworks like llama.cpp take a different approach. Rather than moving weights from CPU to GPU, they move computation across devices: some layers run on GPU, the rest run on CPU. When an expert's weight isn't in GPU memory, rather than transferring the weight to the GPU, they transfer the activation (a much smaller piece of data — for Mixtral-8x7B, an activation is typically 4096 elements per token versus 300MB for the weight) to the CPU and compute the expert layer there.

This solves the weight-transfer bottleneck: activation sizes for small batch sizes are negligible compared to weight sizes, so the communication overhead is minimal. But the paper identifies a critical shortcoming: these systems "do not consider the different batching effects of GPUs and CPUs and the properties of MoE models" (Section 2.2). Specifically:

- **CPU computation scales roughly linearly with input size** because CPUs have limited parallel execution resources. When you give an expert on the CPU 1 token to process, it takes some time T. Give it 2 tokens, it takes roughly 2T. The paper's microbenchmarks in Appendix A confirm this: CPU execution latency is proportional to the number of input tokens, because the computation dominates — the CPU is weakly parallel and becomes compute-bound.

- **GPU computation is nearly constant across input sizes** within reasonable ranges. Give an expert on the GPU 1 token, it takes time T′. Give it 32 tokens, it still takes roughly T′. The GPU's massive parallelism makes it memory-bandwidth-bound rather than compute-bound for small-to-medium batch sizes, and the latency is dominated by the fixed cost of loading the weight from GPU memory.

This means that a strategy that works perfectly for single-batch decoding (where each expert typically receives 1–2 tokens — one per decoding step, multiplied by the top-k experts per layer) breaks down catastrophically during **long prefill** (where a single prompt might route hundreds or thousands of tokens to a single expert) and **beam search** (where each step processes B beam candidates × top-k experts, dramatically increasing the per-expert batch size). In these scenarios, computing expert layers on the CPU becomes prohibitively slow because the linear scaling of CPU latency turns a 1-token compute cost into a 512-token or 2048-token compute cost — at which point the CPU execution time can exceed the weight-transfer time that offloading-based systems pay.

#### Why Existing Systems Can't Just Switch Strategies Dynamically

A natural question at this point is: why can't an offloading system just switch to CPU computation when the batch size is small, and a CPU-based system switch to GPU computation when the batch size is large? The answer is that **these systems lack the architectural mechanism and the decision logic to make this choice per-expert, per-execution-step**. Offloading systems are designed around one fundamental operation: move weight to GPU, compute on GPU. CPU-based systems are designed around the opposite: keep weight on CPU, move activation to CPU, compute on CPU. Neither framework was built to make this decision dynamically based on the current input distribution across experts.

This is precisely the gap Fiddler fills.

### Where Model Compression Fits — and Doesn't Fit

The paper explicitly acknowledges that model compression techniques like quantization (QMoe, ATOM) and sparsification (Deja Vu, PowerInfer) exist and can reduce model size. However, the authors make the case that these are complementary rather than competitive with their approach, for two specific reasons:

First, aggressive compression introduces output quality degradation, "especially when trying to fit large models to a GPU with limited memory capacity" (Section 2.2). The more you compress, the more quality you lose — and for the uncompressed Mixtral-8x7B at 90GB+, fitting it into a 24GB GPU would require extreme compression ratios.

Second, and more technically interesting, the paper provides a detailed analysis in Appendix B explaining why **activation sparsity techniques don't easily transfer to modern MoE models**. Prior work like PowerInfer exploits ReLU activation sparsity — ReLU nullifies negative inputs, creating many exact zeros that allow entire channels to be pruned. But Mixtral-8x7B uses SiLU (Sigmoid Linear Unit) as its activation function. SiLU outputs are rarely close to zero: across all 32 layers, fewer than 2% of values have absolute magnitude below 0.001, fewer than 5% below 0.01, and fewer than 30% below 0.1 for most layers. This is fundamentally different from ReLU activations, where over 90% of values can be exact zeros (as reported for OPT models). Converting a SiLU model to ReLU would require additional training and cause model quality degradation. So the "cheap win" of activation sparsity exploitation doesn't apply to state-of-the-art MoE models.

The authors position Fiddler as orthogonal to compression: "these optimizations could be applied on top of Fiddler" (Section 2.2). Fiddler solves the scheduling problem; compression solves the storage problem. They can be stacked.

### How Fiddler Positions Itself

The paper's positioning is clear and pragmatic: it doesn't claim to invent fundamentally new computing paradigms, but rather to identify and exploit a **decision-making opportunity that existing systems miss**. The core insight is that for MoE models in heterogeneous CPU-GPU architectures, there is no single best strategy for expert computation — the optimal choice depends on the per-expert batch size, which varies dramatically across different inference scenarios (single-batch decode, long prefill, beam search) and even across different layers and steps within a single request.

Specifically, Fiddler's contributions are framed as:

1. **A scheduling algorithm** that makes the CPU-vs-GPU execution decision **per expert, per layer, at runtime**, based on the current input token count for that expert. This is Algorithm 1 in Section 3.3.

2. **A latency model** that captures the different batching effects: CPU latency increasing approximately linearly with input size, GPU latency staying near-constant, and weight-transfer overhead being a fixed cost independent of batch size. The model parameters are measured once during initialization via microbenchmarks (Appendix A).

3. **An expert placement optimization** that maximizes the hit rate of expert weights in GPU memory by profiling expert popularity on calibration data and placing the most frequently activated experts in scarce GPU memory (Section 3.4, Appendix C).

The paper is careful to define its scope: it targets the scenario where GPU memory capacity is insufficient to store all model parameters, where the number of concurrent queries is small (latency matters, not just throughput), and where the model doesn't need to be modified (no compression, no retraining for sparsity). This is exactly the setting of local/edge LLM inference — interacting with a model on a personal computer or small server, where you want low latency for a single user's requests.

The connection back to the Executive Summary's efficiency numbers is through this decision-making framework: the 1.26× single-batch speedup comes from routing small-batch expert computations to the CPU to avoid weight transfer overhead; the 1.30× long-prefill speedup comes from intelligently routing large-batch expert computations to the GPU despite weight transfer cost, avoiding the linear-scaling CPU penalty; and the dramatic 11.57× beam search speedup comes from handling a scenario where the per-expert batch size is multiplied by the beam width, making the CPU-compute cost absolutely prohibitive relative to just paying the weight-transfer cost to use the GPU.

## 3. Technical Approach

### 3.1 Reader Orientation

Fiddler is a runtime scheduler that decides, for each expert layer in an MoE model, whether to execute that expert's computation on the CPU or the GPU, using a simple cost model that compares the latency of CPU computation (which grows with batch size) against the latency of GPU computation plus weight transfer (which is roughly constant). The system solves the problem of running models too large for GPU memory by avoiding a single fixed strategy — it adapts per expert, per layer, per inference step, routing small-batch expert work to the CPU to save weight-transfer overhead and large-batch expert work to the GPU to avoid the CPU's linear scaling penalty.

### 3.2 Big-Picture Architecture (Diagram in Words)

Fiddler has four major components that operate across two phases:

**Initialization phase (happens once, before any inference):**
1. **Memory Allocator** — distributes model weights between CPU and GPU memory. Non-expert layers (attention, gating, embedding, output) always go to GPU because they're used for every token. Expert layers are selectively placed on GPU based on popularity profiling; the rest stay in CPU memory.
2. **Latency Profiler** — measures, for each device, the time to execute an expert layer at different input sizes and the time to transfer weights between CPU and GPU. These measurements become constants in the runtime cost model.

**Runtime phase (happens per layer, per inference step):**
3. **Gating Network** (part of the model itself, not added by Fiddler) — for each token in the current batch, determines which experts to activate. Fiddler reads these assignments to learn how many tokens each expert receives.
4. **Execution Strategy Selector** — applies Algorithm 1: for each expert, checks whether its weight is in GPU memory already. If yes, execute on GPU (no transfer needed). If no, compares predicted CPU latency (input size × per-token CPU cost) against predicted GPU latency (constant compute time + weight transfer time). Chooses whichever is faster.

Information flows as: input tokens → non-expert layers produce activations → gating selects experts → Strategy Selector reads per-expert token counts, consults latency model, chooses CPU or GPU for each expert → selected experts execute on their assigned devices → outputs merged back on GPU → next layer.

### 3.3 Roadmap for the Deep Dive

- **First, the initialization phase**: how Fiddler allocates model weights between CPU and GPU memory and how it profiles device latencies. This establishes the "inputs" to the runtime decision — which experts are where, and what each execution option costs.
- **Second, the three execution scenarios**: the concrete operations that Fiddler can choose among for each expert (GPU-local, GPU-with-transfer, CPU-with-activation-transfer), their costs, and their trade-offs. This provides the option space the scheduler navigates.
- **Third, the runtime algorithm**: Algorithm 1 in detail, including the latency model's functional form, how the decision threshold works, and what happens at each branch. This is the core intellectual contribution — the decision logic.
- **Fourth, the optimizations**: expert placement based on popularity profiling (to maximize GPU hit rate) and the custom AVX512_BF16 CPU kernel. These are practical engineering choices that amplify the algorithm's effectiveness.
- **Fifth, the latency model's justification**: why CPU latency is modeled as linear and GPU latency as constant, grounded in the microbenchmarks of Appendix A. This validates the simplified model used in the algorithm.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is a **systems design paper** whose core idea is that for MoE models where expert weights don't all fit in GPU memory, the optimal execution device for each expert (CPU or GPU) depends on the number of tokens routed to that expert, because CPUs and GPUs exhibit fundamentally different batching behavior. Fiddler exploits this by making per-expert, per-layer, per-step scheduling decisions using a latency model with two simple terms: a linear-scaling CPU cost and a constant-plus-transfer GPU cost.

---

#### Initialization Phase: Weight Allocation and Latency Profiling

Before any inference request is served, Fiddler performs two one-time setup operations: deciding which expert weights live in scarce GPU memory, and measuring how long each operation takes on the available hardware.

**Weight allocation strategy.** The GPU memory is a scarce resource, so Fiddler must choose which parameters get the "fast lane." The allocation follows a strict priority order:

1. **Non-expert layers are always placed on GPU memory.** These include the attention layers, the gating networks, the embedding layer, and the output projection. The justification is simple: these layers are activated for every single token regardless of expert routing, so they would dominate communication costs if placed on the CPU. For Mixtral-8x7B, the non-expert layers total less than 2 billion parameters — small enough that the authors assume they fit in any GPU with at least 24GB of memory.

2. **Expert layers fill the remaining GPU memory in order of popularity.** Fiddler profiles expert activation frequency offline using a calibration dataset (ShareGPT conversations), counting how many tokens each expert receives across all layers. It then selects the top-`$K$` most popular experts that fit in the remaining GPU memory, where `$K$` is determined by memory capacity. In Environment 1, with 24GB GPU memory, this means 56 out of 256 total experts (32 layers × 8 experts per layer) can be GPU-resident. In Environment 2, with 48GB, 125 experts fit.

3. **All remaining expert weights stay in CPU memory.** These experts will be accessed through one of two "remote" execution strategies at runtime.

The popularity-based selection is an explicit optimization: "we select as many experts as the memory capacity permits in order of popularity to maximize the hit rate, i.e., the likelihood an expert's weight is in GPU memory" (Section 3.4). The paper reports (Section 3.4 and Appendix C) that this yields a hit rate improvement of roughly 3–5 percentage points over random placement — from a baseline of `$K/256$` (random expectation) to a higher value based on the skewed popularity distribution. Appendix C provides the empirical distribution: average expert popularity is 0.71 (normalized to the most popular expert at 1.0), with standard deviation 0.08, and only 15 experts fall below 0.6. So while the distribution isn't extremely skewed, there is enough variation for popularity-based placement to matter.

**Latency profiling.** During initialization, Fiddler measures four quantities through microbenchmarks (reported in Appendix A, Figure 7):

- **Weight copy latency:** The time to transfer one expert's weight matrix (3 matrices of size 4096×14336 at 16-bit precision, roughly 300MB total) from CPU memory to GPU memory over PCIe. In Environment 1 (PCIe Gen3 x16, 32GB/s theoretical), this is approximately 2–5× the GPU compute time.

- **Activation copy latency:** The time to transfer one activation vector (4096 elements per token at 16-bit precision) from GPU memory to CPU memory. This is negligible — less than 1% of the single-input CPU compute latency.

- **GPU execution latency at various input sizes N:** The time for the GPU to compute one expert layer on N tokens, *excluding* any data transfer time. The paper reports this as "largely constant" across input sizes (with a minor exception in Environment 1 where the single-input case uses a different PyTorch code path, causing a ~10% difference — small enough to ignore in the latency model).

- **CPU execution latency at various input sizes N:** The time for the CPU to compute one expert layer on N tokens. The paper reports this as scaling "almost linearly" with N.

These profiled values are distilled into the two functions used by Algorithm 1: `cpu_lat(s)` returns a value proportional to `s` (the number of input tokens), and `gpu_lat(s)` returns a constant independent of `s`. The proportionality constant and the constant value are hardware-specific and measured once at startup.

---

#### The Three Execution Scenarios

When processing an MoE layer at runtime, the gating network assigns each input token to one or more experts (for Mixtral-8x7B, each token activates 2 out of 8 experts per layer). For each expert, Fiddler faces one of three situations, illustrated in Figure 3 of the paper:

**Scenario A: Expert weight is already in GPU memory.** This is the ideal case — it happens with probability equal to the hit rate (25.2% in Environment 1, 53.0% in Environment 2, assuming popularity-based placement). The computation proceeds with zero data transfer: the activations are already on the GPU (they were produced by the previous layer, which ran on the GPU), the weights are in GPU memory, and the GPU simply multiplies them. The latency is `gpu_lat(s)`, which is essentially constant regardless of `s`.

**Scenario B: Expert weight is in CPU memory; transfer weight to GPU, then compute on GPU.** This is the offloading strategy. The sequence is: (1) detect that the expert weight is missing in GPU memory, (2) copy the 300MB weight from CPU memory to GPU memory over PCIe, (3) execute the expert layer on the GPU. The latency is `gpu_lat(s) + transfer_lat()`. Because GPU computation time is roughly constant, and weight transfer time is fixed (the weight doesn't change size based on how many tokens use it), the total latency is approximately constant regardless of input size `s`. The key cost is the ~2–5× multiplier that weight transfer adds over pure GPU computation (Appendix A).

**Scenario C: Expert weight is in CPU memory; transfer activations to CPU, compute on CPU, transfer results back to GPU.** This is the strategy used by CPU-based frameworks like llama.cpp. The sequence is: (1) detect that the expert weight is missing in GPU memory, (2) copy the activation vectors from GPU to CPU memory (the activation size is `s × 4096 × 2` bytes for 16-bit precision — for `s=1`, this is about 8KB; for `s=1024`, about 8MB — always much smaller than the 300MB weight), (3) execute the expert layer on the CPU, (4) copy the output activations back to GPU memory. The paper states that steps (2) and (4) are negligible — "the time needed to transfer activations is negligible (less than 1% of the latency with a single input)" (Appendix A). So the dominant cost is `cpu_lat(s)`, which scales approximately linearly with `s`.

**The trade-off between B and C.** The decision hinges on comparing `cpu_lat(s)` against `transfer_lat() + gpu_lat(s)`. Since `gpu_lat(s)` is roughly constant (call it `G`), `cpu_lat(s)` is roughly `s × C` for some per-token CPU cost `C`, and `transfer_lat()` is a constant `T`, the comparison reduces to:

$$s \cdot C \quad \text{vs.} \quad T + G$$

For small `s`, the left side is smaller — CPU computation is cheaper than paying the weight-transfer overhead. For large `s`, the left side grows and eventually exceeds the right side — at some threshold number of tokens, it becomes cheaper to transfer the weight once and use the GPU than to process all those tokens sequentially on the CPU. The threshold is `s_threshold = (T + G) / C`. This threshold varies by hardware (Table 1: different GPUs, different PCIe generations, different CPU core counts all shift `T`, `G`, and `C`), which is why Fiddler profiles these values at initialization rather than hard-coding them.

For long prefill or beam search, `s` can be large enough that Scenario C becomes dramatically slower than Scenario B — this is the root cause of the 11.57× beam search speedup reported in Section 4.2.

#### Runtime Algorithm: Per-Expert Execution Strategy Selection

Algorithm 1 (Section 3.3) is the operational core of Fiddler. It runs once per MoE layer per inference step. Here is the algorithm in detail:

**Inputs.** The algorithm receives three pieces of information:
- `ne`: the number of experts in the current layer (8 for Mixtral-8x7B).
- `i`: the layer index (0 to 31 for Mixtral-8x7B's 32 layers).
- `inp_size`: an array of length `ne` where `inp_size[j]` is the number of input tokens routed to expert `j` by the gating network in this layer.

**Step-by-step execution.** The algorithm iterates over each expert `j` from 1 to `ne`:

1. **Read the input size:** `s ← inp_size[j]`. If `s == 0` (no tokens were routed to this expert), skip it — there's nothing to compute.

2. **Check GPU residency:** Call `is_at_gpu(i, j)`, which returns `true` if expert `j` in layer `i` was placed in GPU memory during initialization (based on popularity ranking). If `true`, execute the expert on the GPU (Scenario A) — no further decision needed.

3. **Compare CPU vs. GPU-with-transfer:** If `is_at_gpu(i, j)` is `false`, evaluate the condition:
   ```
   cpu_lat(s) > gpu_lat(s) + transfer_lat()
   ```
   - If `true`: the CPU execution time exceeds the GPU execution time plus weight transfer overhead. Execute on GPU (Scenario B) — accept the weight transfer cost because CPU computation is too slow at this batch size.
   - If `false`: the CPU execution time is less than or equal to the GPU-with-transfer time. Execute on CPU (Scenario C) — avoid the weight transfer cost because the small batch size makes CPU computation acceptable.

**The latency model functions.** The paper specifies the functional forms:
- `gpu_lat(s)` returns a constant value (the GPU compute time is independent of `s`, justified by microbenchmarks showing GPU computation is memory-bandwidth-bound, not compute-bound).
- `cpu_lat(s)` returns a value proportional to `s`, multiplied by a hardware-specific constant (justified by microbenchmarks showing linear scaling: "CPU execution time is assumed to increase linearly with the number of input tokens").
- `transfer_lat()` returns a constant (the weight size is fixed, and PCIe bandwidth is roughly constant for bulk transfers).

These constants are measured once during initialization by running an expert computation on the CPU and GPU at various input sizes, and timing a weight transfer, then fitting the linear model for CPU and taking the average for GPU and transfer. The paper does not report the specific fitted constants, but they are implicit in the threshold behavior — for the hardware in Environment 1, the threshold `s` where CPU and GPU-with-transfer break even falls somewhere between typical single-batch sizes (~1–2 tokens) and typical prefill/beam-search batch sizes (hundreds to thousands of tokens).

**Why per-expert, per-layer?** The alternative would be a global decision — either all experts run on CPU this step, or all run on GPU. That would be suboptimal because different experts in the same layer receive different numbers of tokens (due to the skewed but not perfectly uniform popularity distribution). Expert 0 might receive 100 tokens (should run on GPU), while Expert 5 receives 2 tokens (should run on CPU). Making a global decision would force one of them into a suboptimal execution strategy. The per-expert granularity is what allows Fiddler to capture the 1.26× single-batch speedup and 1.30× prefill speedup simultaneously.

**Why at runtime rather than ahead of time?** The expert selection depends on the actual input tokens, which aren't known until inference time. Pre-computing a static schedule would require predicting the gating network's output, which is effectively a language modeling problem itself. Dynamic scheduling based on observed token counts is simpler, more accurate, and adds negligible overhead — the decision logic is just a few integer comparisons and table lookups per layer per step.

#### Expert Placement Optimization: Popularity-Based GPU Caching

The algorithm's effectiveness depends on `is_at_gpu(i, j)` returning `true` as often as possible — every time it returns `true`, we avoid both weight transfer *and* CPU computation, paying only the constant GPU compute cost. The hit rate directly multiplies the algorithm's efficiency.

**Profiling methodology.** Fiddler profiles expert popularity offline using calibration data (ShareGPT conversations). For each layer, it runs inference on the calibration samples and counts how many tokens are routed to each expert. Appendix C reports the distribution for Mixtral-8x7B: average popularity 0.71 (relative to the most popular expert at 1.0), standard deviation 0.08, 25th percentile 0.67, 75th percentile 0.76. Only 15 experts out of 256 fall below 0.6 popularity, and 27 experts exceed 0.8. This is a relatively balanced distribution — no expert is dramatically more popular than others — but there is enough variation for informed placement to outperform random placement.

**Selection mechanism.** Fiddler sorts all 256 experts (across all 32 layers) by their profiled popularity and takes the top `K` that fit in the remaining GPU memory after non-expert layers are placed. `K` is determined purely by memory capacity: each expert is roughly 300MB (16-bit, 3 matrices of 4096×14336 each), so with 24GB available and non-expert layers occupying some fraction, roughly 56 experts fit in Environment 1. The paper reports expected hit rates:

- **Environment 1 (56/256 experts on GPU):** best-case hit rate 25.2% (placing the 56 most popular experts), worst-case 18.7% (placing the 56 least popular), random expectation 21.9%. The improvement from random to best is approximately 3.3 percentage points.
- **Environment 2 (125/256 experts on GPU):** best-case 53.0%, worst-case 44.6%, random 48.8%. The improvement from random to best is approximately 4.2 percentage points.

**Why the hit rate improvement matters, even at 3–5 percentage points.** A 3.3pp improvement on a 21.9% base means roughly 15% more expert computations avoid any transfer or CPU overhead — they execute in the fast Scenario A path. Given that expert computation dominates MoE inference time (the dense layers are a minority), this proportional reduction in expensive scenarios translates to a noticeable end-to-end speedup. The paper doesn't present an ablation isolating the impact of popularity-based placement versus random placement, but the hit rate improvement is a direct multiplier on the algorithm's efficiency: every percentage point of hit rate increase converts Scenarios B or C into the much faster Scenario A.

**Generality assumption.** The paper states that "the popularity of experts is almost universal across different input domains" (Section 3.4), citing prior work on Mixtral and OpenMoE. This is important because it means the offline calibration doesn't need to be redone for each deployment or each user — the expert popularity distribution is more a property of the model's training than the specific inputs it receives. Appendix D provides a sensitivity study showing that Fiddler's performance on the LMSYS-Chat-1M dataset is similar to its performance on ShareGPT (1.56× speedup vs. 1.81× over llama.cpp), supporting this claim of cross-domain robustness.

#### Custom CPU Computation Kernel: AVX512_BF16

The paper mentions a custom CPU kernel for expert computation "using the AVX512_BF16 instruction set, which is not supported in the native PyTorch implementation" (Section 3.4). This is important for maximizing the speed of Scenario C execution (CPU computation), since the linear-scaling CPU cost `C` directly determines the threshold `s_threshold` at which GPU-with-transfer becomes preferable. A lower `C` (faster CPU computation) shifts the threshold higher, meaning more expert computations can be profitably done on the CPU before switching to GPU.

The AVX512_BF16 instruction set provides hardware-accelerated 16-bit brain-float matrix multiplication on modern Intel Xeon processors. The native PyTorch implementation does not use these instructions for its CPU backend, instead relying on less optimized BLAS libraries or generic float32 operations. By writing a custom kernel that uses the BF16 intrinsics directly, Fiddler reduces `cpu_lat(s)` for any given `s`.

The paper does not quantify the improvement from this kernel alone versus PyTorch's default CPU execution, which is a minor omission — the kernel is presented as an optimization that makes the algorithm more effective rather than as a core contribution. The evaluation results inherently include its benefit.

#### Latency Model Justification: Why Linear CPU and Constant GPU

The latency model's correctness is essential to the algorithm's optimality. If the model is wrong — if CPU latency doesn't actually scale linearly, or if GPU latency varies significantly with batch size — then the decision threshold `s_threshold` would be wrongly computed, and Fiddler would make sub-optimal scheduling choices.

The microbenchmarks in Appendix A (Figure 7) provide the empirical grounding:

**GPU computation latency.** For both environments tested, the GPU expert execution time (excluding weight transfer) is approximately flat across input sizes. The paper reports this as "largely constant regardless of batch size." The physical explanation is that GPUs have such high computational parallelism that, for batch sizes typical in MoE inference (1 to a few hundred tokens), the GPU's tensor cores are underutilized, and the limiting factor is the time to load the weight matrix from GPU memory into the compute units — which is the same regardless of how many tokens you multiply it by. This is the "memory-bandwidth-bound" regime. Only at much larger batch sizes (thousands or tens of thousands) would the GPU become compute-bound, and latency would start to increase.

The one caveat is Environment 1 at batch size 1, where PyTorch uses a different implementation (likely a vector-multiply kernel instead of a batched matrix-multiply kernel) that introduces a small difference. However, the paper reports this difference as "approximately 10% compared to the overall latency, which includes weight transfer" — small enough that the constant-GPU-latency approximation holds well.

**CPU computation latency.** The CPU execution time scales "almost linearly with the size of the input batch." The physical explanation is that CPUs have limited vector width (512 bits for AVX-512, processing 32 BF16 values per cycle) and a limited number of cores (48 in Environment 1, 112 in Environment 2). As the number of tokens increases, the CPU must iterate through the batch sequentially or with limited parallelism, and the total compute work scales linearly with the number of token-weight multiplications. The constant factor is determined by the CPU's clock speed, core count, and memory bandwidth.

**Weight transfer latency.** The PCIe transfer time is approximately constant for a fixed-size weight — a 300MB transfer at 32GB/s (PCIe Gen3) takes roughly 9 milliseconds, at 64GB/s (PCIe Gen4) roughly 4.5 milliseconds. The slight variations are due to PCIe overhead and contention but are small relative to the total.

**Activation transfer latency.** As noted, this is "negligible (less than 1% of the latency with a single input)" — for `s=1`, activation size is 4096×2 = 8KB, which transfers in microseconds even over slow PCIe. Even for `s=1024`, the 8MB activation transfers in about 0.25ms on Gen3 and 0.125ms on Gen4 — still small relative to the weight transfer latency of 4.5–9ms.

**Why not a more complex model?** The paper's model is intentionally simple — just a linear CPU term, a constant GPU term, and a constant transfer term. More complex models could account for non-linear scaling at extreme batch sizes, contention between concurrent CPU and GPU operations, or PCIe bandwidth sharing. However, the authors judge that for the batch sizes encountered in single-user MoE inference (tens to low thousands of tokens per expert), the simple model is accurate enough to make correct decisions, and the complexity of a more sophisticated model would add overhead that could negate its benefits. The evaluation results (the speedups over baselines) provide implicit validation that the model works well enough in practice.

---

#### End-to-End Runtime Flow

Putting all components together, here is the complete execution sequence for one inference step (one transformer layer) in Fiddler:

1. **Attention computation:** The dense attention layer executes on the GPU (its weights are always GPU-resident). This produces output activations of shape `[batch_size, seq_len, hidden_dim]`.

2. **Gating:** The gating network (also GPU-resident, part of non-expert layers) takes the attention output and produces, for each token, a routing decision — which 2 experts (for Mixtral-8x7B) should process that token. Fiddler aggregates this into `inp_size`, the count of tokens assigned to each expert.

3. **Expert scheduling:** Algorithm 1 executes for this layer. For each of the 8 experts:
   - If `inp_size[j] == 0`, skip.
   - If expert `j` is in GPU memory, launch GPU kernel for Scenario A.
   - If expert `j` is not in GPU memory, compare `s × C` against `T + G`. If CPU is cheaper, launch Scenario C (copy activations to CPU, compute on CPU, copy results back). If GPU-with-transfer is cheaper, launch Scenario B (copy weight to GPU, compute on GPU).

4. **Expert computation:** The scheduled operations execute. CPU and GPU computations can overlap to some degree (the GPU can process experts A and B while the CPU processes expert C), though the paper doesn't explicitly model this concurrency in the latency model — it treats latencies as sums, which may be slightly conservative.

5. **Output aggregation:** The results from all experts are combined on the GPU (the MoE layer's output is the weighted sum of the selected experts' outputs, as defined by the gating weights). The combined output becomes the input to the next transformer layer.

6. **Repeat:** Steps 1–5 for all 32 layers of the model.

For the prefill stage (processing the input prompt), steps 1–6 happen once per layer for the entire prompt in parallel — this is where per-expert token counts can be large (each of the prompt's tokens gets routed to 2 experts, so if the prompt has 2048 tokens and the distribution is roughly uniform, each expert might receive ~512 tokens). For the decode stage (generating output tokens one at a time), steps 1–6 repeat for each new token — here, per-expert token counts are typically 1–2 (since only one token is being generated, and it activates 2 experts). For beam search, the decode stage processes `B` tokens simultaneously (one per beam), so per-expert token counts are `B` times higher — this is why the CPU strategy collapses for beam search and the GPU-with-transfer strategy dominates, producing the 11.57× speedup.

---

#### Design Choices Summary

**Why separate memory allocation from execution strategy?** The initialization-phase allocation (placing popular experts on GPU) is a coarse-grained, offline decision that maximizes the expected hit rate. The runtime execution strategy (Algorithm 1) is a fine-grained, online decision that handles the cases where the allocation "misses." Separating them means the system can optimize for the common case (high hit rate) while having a fallback that adapts to the actual input distribution, which may deviate from the profiled popularity.

**Why not profile expert popularity continuously online?** The paper's approach uses static, offline popularity profiling. An online approach could dynamically adjust which experts are GPU-resident based on recent routing patterns, potentially achieving higher hit rates for domain-specific inputs. However, swapping expert weights in and out of GPU memory would incur PCIe transfer costs that might exceed the benefit. The paper implicitly assumes the cost of dynamic re-allocation isn't worth it, given that expert popularity is "almost universal across different input domains" and the static profile works well enough.

**Why is the latency model not learned or adaptive?** The model uses fixed constants measured once at startup. Learned or adaptive models could correct for measurement noise or handle changes in system state (thermal throttling, memory pressure from other processes). The simplicity of the model (just three constants per hardware configuration) suggests the authors prioritized low overhead and predictability over potential marginal accuracy improvements from more sophisticated estimation.

**Why Algorithm 1 uses a hard threshold rather than probabilistic scheduling?** The comparison `cpu_lat(s) > gpu_lat(s) + transfer_lat()` makes a deterministic choice. A probabilistic approach (e.g., routing a fraction of tokens to CPU and a fraction to GPU) could smooth out the threshold discontinuity and potentially exploit concurrency better. However, the per-expert granularity already provides some smoothing — different experts receive different decisions in the same layer — and deterministic scheduling is simpler to implement and reason about.

**Why expert, not token-level scheduling?** The algorithm schedules at the expert level (all tokens routed to expert `j` go to the same device). A finer-grained token-level schedule (splitting the tokens for expert `j` between CPU and GPU) would add complexity without clear benefit: the linear scaling means the total CPU time for processing half the tokens is half, and the GPU time plus transfer is the same either way. There's no nonlinearity that would make splitting advantageous, and it would add synchronization overhead.

## 4. Key Insights and Innovations

### Innovation 1: Runtime Per-Expert Scheduling as the Resolution to the Offloading-vs-CPU-Compute Impasse

Before Fiddler, the two dominant strategies for running large models with limited GPU memory — offloading weights to CPU and transferring on demand, versus keeping weights on CPU and moving activations — were treated as architectural commitments. An inference system picked one and lived with its failure modes: offloading-based systems like DeepSpeed-MII and Mixtral-Offloading suffered from PCIe bandwidth bottlenecks whenever the batch size was small (since the weight transfer cost dominated), while CPU-compute systems like llama.cpp collapsed when the batch size grew (since CPU latency scaled linearly with input tokens, making prefill and beam search agonizingly slow). Each system made a *global* choice that was optimal in some regimes and catastrophic in others.

Fiddler's conceptual contribution is to recognize that for MoE models, this choice doesn't need to be global at all. The sparse activation pattern of MoE layers means that, at any given inference step, different experts receive different numbers of tokens — some might get a single token during decode, others might get hundreds during prefill. A global strategy forces all experts to use the same execution path, even when that path is grossly suboptimal for some. By dropping the scheduling granularity from *the model* to *each individual expert*, Fiddler transforms the problem from "which strategy is best?" to "which strategy is best *for this expert, right now, given these inputs*?" This shift in granularity is the enabling intellectual move — the algorithm (Section 3.3) is almost trivially simple once you accept that per-expert decisions are possible and worth making.

The significance of this reframing extends beyond the immediate speedup numbers. It establishes that in heterogeneous CPU-GPU architectures, the right abstraction for MoE inference is a **scheduler** that makes device placement decisions per computation unit, not a **compiler** that pre-commits to a single execution plan. This is a conceptual parallel to how operating systems schedule processes across heterogeneous cores (big.LITTLE architectures), where the optimal core for a task depends on its current computational intensity. The paper doesn't make this analogy explicit, but the intellectual structure is identical: profile, model, decide per-task.

The evidence that this scheduling granularity is the key insight — rather than just the specific latency model or the popularity-based placement — comes from the breadth of Fiddler's gains across incompatible scenarios. The 1.26× single-batch speedup (Figure 4) comes from routing small-batch experts to the CPU, avoiding weight transfer. The 1.30× long-prefill speedup (Figure 5) comes from routing large-batch experts to the GPU, avoiding CPU's linear-scaling penalty. The 11.57× beam-search speedup (Figure 6) comes from the same logic applied to an extreme case. A system committing to either CPU or GPU globally couldn't achieve all three simultaneously. The fact that Fiddler does — and that neither offloading-based nor CPU-based baselines can — isolates per-expert scheduling as the decisive factor, not any single optimization.

This is fundamentally an **architectural insight** rather than a theoretical one. The paper doesn't prove optimality or derive formal bounds; it shows that a design pattern the field had overlooked — dynamic, fine-grained scheduling in the inference stack — unlocks efficiency that fixed-strategy systems leave on the table. The contribution is diagnosing *why* existing systems fail across workloads (they commit to one strategy) and showing that the fix requires rethinking the granularity of decision-making, not just better implementations of existing strategies.

---

### Innovation 2: The Batching Effect Asymmetry as a First-Class Latency Model

The paper's latency model — CPU time linear in input size, GPU time constant, transfer time constant — appears so simple that a reader might dismiss it as obvious. This would miss the intellectual contribution. What makes this model *non-obvious* is not the functional forms themselves, but the recognition that **the batching characteristics of CPUs and GPUs are different enough in the MoE inference context to create a clean decision threshold**, and that this threshold can be reliably exploited with a model having just two parameters.

The microbenchmarks in Appendix A reveal a specific physical reality: expert computation on a GPU is memory-bandwidth-bound for the batch sizes encountered in single-user MoE inference (tens to low hundreds of tokens), meaning execution time is dominated by the fixed cost of loading the 300MB weight matrix from GPU memory into compute units — a cost that doesn't increase with batch size because the weight is loaded once, then multiplied against all tokens in the batch. The CPU, by contrast, lacks the parallel memory bandwidth and compute throughput to saturate either; it becomes compute-bound almost immediately, and the total work scales with the number of tokens. This asymmetry is *contingent* — it holds for this specific workload (matrix multiplications of a fixed 300MB weight against variable-size activation batches) on contemporary hardware (PCIe Gen3/4, AVX-512 CPUs, GPUs with limited memory bandwidth relative to their tensor core throughput). Prior work had not characterized this asymmetry for the MoE expert-computation setting specifically, which is why CPU-based systems like llama.cpp treated CPU computation as always acceptable (it's fine at batch size 1) without modeling its scaling behavior.

The conceptual leap is turning this physical observation into a **dispatch policy with a single crossing point**. Because CPU cost grows linearly from near-zero and GPU-with-transfer cost is flat and elevated, there is exactly one input size where they cross. Below that size, CPU wins; above it, GPU wins. This means the scheduling problem reduces to a single comparison per expert — no need for complex cost models, online learning, or multi-dimensional optimization. The paper doesn't claim this is a general property of heterogeneous computing (it isn't — many workloads have more complex cost surfaces). It claims this holds *for MoE expert layers on current hardware*, and the empirical results validate that the simple model is sufficient to make correct decisions across a wide range of workloads.

What elevates this from "reasonable engineering choice" to "insight" is that the model's simplicity is not an approximation or a compromise — it's an accurate characterization of the underlying physics. The linear-CPU/constant-GPU model isn't an abstraction layered on top of a messier reality; the microbenchmarks show that the messier reality (the ~10% deviation in Environment 1 at batch size 1, the slight non-linearities at extreme scales) genuinely doesn't matter for the decision being made. The crossing point is far enough from the noise that a two-parameter model is *exact enough*, not just *simple enough*. Recognizing when a simple model is sufficient — rather than reflexively reaching for more complexity — is a genuine intellectual contribution in systems research.

---

### Innovation 3: Static Popularity-Based Placement as a Sufficient Substitute for Online Caching

One might expect that to maximize GPU hit rates, Fiddler would need an online caching policy — track which experts are being activated, evict cold ones, prefetch hot ones, similar to how CPU caches or key-value caches work. Fiddler instead uses a static, offline popularity ranking: profile expert activation frequencies once on calibration data, place the top-K most popular experts in GPU memory, and never change them. This choice seems almost naive until you examine the evidence that justifies it.

The paper reports that expert popularity follows a relatively balanced distribution (Appendix C): average popularity 0.71 relative to the most popular expert, standard deviation only 0.08, with only 15 out of 256 experts falling below 0.6. This means there are no "dominating" experts that absorb a large fraction of tokens — the distribution is close to uniform. In such a regime, an online caching policy that dynamically swaps experts would incur PCIe transfer costs to achieve only marginally better hit rates than a static placement. The 3–5 percentage point hit rate improvement from popularity-based static placement over random placement is modest but essentially free (no runtime overhead, no transfer cost for cache maintenance). An online policy might squeeze out another few percentage points but would pay for them with weight transfers and bookkeeping.

The deeper insight is that **MoE models, as currently trained, produce routing distributions that are engineered to be roughly balanced**. This is a training objective — load-balancing losses are standard in MoE training to prevent expert collapse, where all tokens route to a few experts and the rest are unused. The consequence for inference systems is that expert popularity is inherently "flat enough" that the difference between a sophisticated online cache and a simple static placement is small. The paper doesn't frame it this way, but it's a finding with design implications: MoE training objectives create distributions that are inherently friendly to static resource allocation. If future MoE models move away from load-balancing (e.g., toward more specialized, unbalanced expert routing), this insight would need revisiting, and Fiddler's static placement might need replacement with an online policy.

The generality of static popularity across input domains (the paper claims "almost universal," citing Mixtral and OpenMoE analyses, and provides supporting evidence in Appendix D where LMSYS-Chat-1M performance is similar to ShareGPT) strengthens this insight. If expert popularity varies dramatically with input domain, static calibration on one dataset would fail on another, and online adaptation would be necessary. The paper's evidence suggests it doesn't, at least for Mixtral-8x7B, which means the offline-static approach is robust as well as simple.

---

### Innovation 4: Beam Search as the Killer App for CPU-GPU Orchestration (or: Why 11.57× Matters)

The 11.57× beam search speedup is the paper's most dramatic number, but its significance is conceptual, not just quantitative. It reveals something about the interaction between MoE models, beam search decoding, and heterogeneous hardware that wasn't previously recognized: **beam search multiplies the per-expert batch size by the beam width, which pushes CPU-based execution from acceptable to catastrophically slow without changing anything about the model or the weights**.

In single-batch decode, each expert receives 1–2 tokens per step. The CPU can handle this comfortably — the linear scaling penalty is applied to a small base, so the absolute latency is still modest. In beam search with width B=16, each expert receives roughly 16× as many tokens per step (one per beam, multiplied by the routing probability). The CPU's linear scaling turns a 1-token cost into a 16-token cost — still linear, but the absolute latency is now 16× higher. Meanwhile, the GPU-with-transfer option sees no meaningful increase in latency (the weight transfer cost is the same, the GPU compute is still memory-bandwidth-bound at batch size 16). The crossing point that was above 1–2 tokens (so CPU won in single-batch) is now well below 16 tokens (so GPU-with-transfer wins in beam search).

The conceptual point is that **beam search is not "just another workload" — it amplifies the batching effect asymmetry in a way that makes CPU-only strategies fundamentally untenable**. Existing CPU-based frameworks like llama.cpp, which performed adequately in single-batch scenarios (within 20–30% of Fiddler in some configurations), degrade by an order of magnitude or more when beam search is introduced. The paper doesn't just show that Fiddler is faster; it shows that the CPU baseline becomes *unusable* (in a latency-sensitive interactive setting) under beam search, while Fiddler maintains reasonable performance by dynamically switching its strategy. The 11.57× number is less a celebration of Fiddler's cleverness and more a demonstration of how catastrophically wrong the static-CPU strategy is for this workload.

This insight has implications for how the field should evaluate MoE inference systems. A system that looks competitive on single-batch decode benchmarks may completely collapse on beam search; evaluating only one scenario gives a misleading picture of real-world usability. The paper's decision to report three distinct workload types (single-batch, long prefill, beam search) is not just thorough benchmarking — it's a methodological argument that inference systems for MoE models must be evaluated across workload diversity because the interaction between batching and device choice creates qualitatively different performance regimes.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The evaluation uses ShareGPT, a dataset of human-chatbot conversations, to model realistic expert selection behavior. A random subset of conversations is selected, and for experiments with a specific input length N, samples with N or more prompt tokens are randomly chosen, using only the initial N tokens. No train-test split is described — the 500-question test set convention from the prior sections does not apply here; this is a systems performance evaluation, not a model accuracy benchmark.

- **Base model(s).** All experiments use Mixtral-8x7B (Jiang et al., 2024) with 16-bit precision. This model has 47 billion parameters distributed across 32 MoE layers, each containing 8 experts, totaling 256 experts. The uncompressed model requires over 90GB of storage, exceeding the GPU memory of both test environments. The authors choose Mixtral-8x7B because it "represents the architecture of most of the recent MoE models" and is supported by all baseline systems, enabling fair comparison. Appendix E additionally evaluates Phi-3.5-MoE against DeepSpeed-MII (the only baseline supporting it) to demonstrate model-agnostic applicability.

- **Metrics.** Three distinct performance metrics are measured, each targeting a different inference scenario: (1) **Tokens per second** for end-to-end latency, computed as the number of generated tokens divided by the total time from receiving the inference request to generating the final token (including both prefill and decode). This is the metric for single-batch inference (scenario a) and beam search (scenario c). (2) **Time To First Token (TTFT)** for long-context prefill processing (scenario b), measuring the latency from receiving the request to producing the first output token, which primarily reflects prefill-stage computation. (3) **Inter-Token Latency (ITL)** is reported separately in Appendix F as a breakdown of end-to-end latency. Higher tokens-per-second is better; lower TTFT and ITL are better.

- **Baselines.** Three state-of-the-art systems are compared: **DeepSpeed-MII** version v0.2.3 (Microsoft), configured with ZeRO-Infinity optimization for parameter offloading and `pin_memory` enabled for paged-locked CPU memory; **Mixtral-Offloading** (Eliseev & Mazur, 2023), extended by the authors to support 16-bit precision (the original supports only quantized models), with `offload_per_layer` set to 7 for Environment 1 and 5 for Environment 2 (the best configurations for the tested hardware); and **llama.cpp** version b2956 (ggml authors, 2023), with the `ngl` parameter controlling GPU-offloaded layers set to 8 for Environment 1 and 16 for Environment 2. For beam search (scenario c), Fiddler is compared only against llama.cpp since the other baselines do not support beam search inference.

- **Generation budget / compute accounting.** The paper does not use a generation budget in the same sense as search-revision papers. Instead, fair comparison is maintained by evaluating all systems on identical hardware with identical workloads — same model (Mixtral-8x7B at 16-bit), same input-output length configurations, same beam widths. No system is given a compute advantage; the measured metric is wall-clock time, which inherently accounts for all overhead. The environments have fixed hardware (Table 1) and memory limits, so each system must fit the model within those constraints however it can.

- **Cross-validation / statistical protocol.** No cross-validation or statistical significance testing is reported. The evaluation is a deterministic systems benchmark: for each configuration (input length, output length, environment), all systems process the same prompts, and wall-clock latency is measured. Results are averaged across 15 different input/output length configurations for scenario a (end-to-end), across 4 input length configurations for scenario b (long prefill), and across 4 beam widths for scenario c (beam search), with the rightmost bar in each figure showing the average. The paper does not report variance, confidence intervals, or statistical tests — this is standard for systems performance evaluation where deterministic hardware behavior is expected and measurement noise is typically small relative to effect sizes, but it means the reader cannot assess whether observed differences are statistically reliable.

### Main Quantitative Results

#### Single-Batch End-to-End Inference (Scenario a)

**Headline result:** Across all 15 input/output length configurations and two environments, Fiddler achieves 1.26 times faster performance on average compared against the best baseline (llama.cpp), as shown in Figure 4. The specific input lengths tested are [32, 64, 128, 256] tokens and output lengths are [64, 128, 256, 512] tokens, representing a range from short prompt–short response to medium prompt–long response scenarios.

**Per-baseline comparison (Figure 4):** The figure displays four grouped bar charts (two environments, each with 15 configurations plus an average). While the paper reports the 1.26× number as the average improvement over llama.cpp, the bar charts show that Fiddler consistently outperforms all three baselines across nearly every configuration in both environments. DeepSpeed-MII and Mixtral-Offloading (the offloading-based systems) generally achieve the lowest tokens-per-second, reflecting the weight-transfer overhead that dominates in small-batch scenarios. llama.cpp performs better than the offloading systems (since it avoids weight transfer for small batches by computing on CPU), but Fiddler surpasses it by dynamically routing small-batch experts to the CPU when appropriate and only paying GPU transfer costs when batch sizes warrant it.

**Environment sensitivity:** The paper evaluates on two environments (Table 1) spanning different GPU generations (Quadro RTX 6000 with 24GB vs. RTX 6000 Ada with 48GB), different PCIe generations (Gen3 at 32GB/s vs. Gen4 at 64GB/s), and different CPU core counts (48 vs. 112 cores). The fact that Fiddler's advantage persists across both environments demonstrates that the scheduling algorithm adapts to different hardware profiles — the latency model constants are re-measured per environment, so the decision threshold shifts appropriately.

**Latency breakdown (Appendix F):** Figure 11 shows the Time To First Token separately, where Fiddler achieves on average 1.13× speedup across all baselines in both environments. Figure 12 shows the Inter-Token Latency, where Fiddler achieves on average 1.43× speedup across all baselines. The larger improvement in ITL (1.43× vs. 1.13×) suggests that Fiddler's benefits are more pronounced during the decode phase than the prefill phase in single-batch scenarios — this is consistent with the mechanism, since decode steps have very small per-expert batch sizes (1–2 tokens), making CPU computation advantageous and avoiding weight transfer, whereas prefill in single-batch scenarios still has relatively small per-expert batch sizes but benefits less dramatically from the scheduling choice.

#### Long Prefill Processing (Scenario b)

**Headline result:** Fiddler outperforms all baselines on long prefill processing, as shown in Figure 5. On average across four input length configurations [512, 1024, 2048, 4096], Fiddler outperforms DeepSpeed-MII by 1.07× and Mixtral-Offloading by 1.65×. The four bar groups in Figure 5 show that Fiddler's advantage is consistent across all prefills lengths, with the rightmost "average" bars summarizing the mean performance.

**Baseline trade-off reversal:** This scenario reveals the opposite pattern from single-batch inference. In Figure 5, the offloading-based systems (DeepSpeed-MII and Mixtral-Offloading) significantly outperform the CPU-based system (llama.cpp). This is because long prefills route large numbers of tokens to each expert (e.g., a 4096-token prompt with top-2 routing and roughly uniform expert distribution sends ~1024 tokens to each expert), making CPU computation prohibitively expensive due to linear scaling. The offloading systems, despite paying the weight-transfer cost, benefit from the GPU's constant compute time for large batches. Fiddler outperforms even the offloading systems because it can still route small-batch experts (those that happen to receive fewer tokens due to non-uniform routing) to the CPU, while using GPU-with-transfer for the large-batch experts — extracting the best of both strategies rather than committing entirely to one.

**Quantitative context for 1.07× and 1.65×:** The improvement over DeepSpeed-MII (1.07×) is modest — a 7% TTFT reduction. DeepSpeed-MII's ZeRO-Infinity offloading is already well-optimized for large-batch scenarios, so Fiddler's room for improvement is limited when the dominant cost is weight transfer, which both systems must pay for non-GPU-resident experts. The larger improvement over Mixtral-Offloading (1.65×) likely reflects Mixtral-Offloading's less optimized transfer pipeline (it was originally designed for quantized models and extended by the authors for 16-bit) rather than a fundamental algorithmic gap.

#### Beam Search Inference (Scenario c)

**Headline result:** Fiddler achieves 11.57× better performance than llama.cpp on beam search inference on average across beam widths [4, 8, 12, 16], as shown in Figure 6. The experiments use a fixed input length of 32 tokens and output length of 64 tokens, varying only the beam width.

**Why only llama.cpp comparison:** The other baselines (DeepSpeed-MII and Mixtral-Offloading) do not support beam search inference, so the comparison is restricted to llama.cpp. This is an important caveat — the 11.57× number measures Fiddler against a system known to degrade severely under beam search (due to CPU linear scaling being multiplied by beam width), not against a hypothetical offloading-based beam search implementation.

**Mechanism for the dramatic speedup:** Beam search with width B processes B candidate sequences in parallel during decode. For each decoding step, each of the B beams generates one token, which gets routed to 2 experts. If routing were perfectly uniform, each expert would receive approximately 2B/8 = B/4 tokens per step. For B=16, this is ~4 tokens per expert — still modest. However, routing is not perfectly uniform, and some experts may receive substantially more tokens. More importantly, the CPU-based llama.cpp executes ALL experts on the CPU, and the per-expert CPU latency (which dominates) scales linearly with the number of tokens that expert processes. If any expert receives, say, 8 tokens at B=16, the CPU compute time for that expert is 8× the single-token cost — and this cost is paid for every layer, every decoding step. The GPU-with-transfer strategy in Fiddler avoids this scaling entirely by routing larger-batch experts to the GPU, where the compute time stays near-constant regardless of whether an expert processes 2 or 8 tokens. The divergence between CPU-linear and GPU-constant costs grows with beam width, producing the 11.57× average speedup.

**Beam width scaling:** Figure 6 shows four bars per system (one per beam width) plus an average. The paper does not report per-beam-width speedup numbers individually, but the bar chart visually indicates that the performance gap widens as beam width increases — consistent with the mechanism that higher beam width multiplies the CPU's linear-scaling penalty while leaving GPU-with-transfer latency roughly unchanged.

#### Sensitivity to Input Dataset Distribution (Appendix D)

**Headline result:** Fiddler's performance advantage over llama.cpp is robust to input data distribution. Using the LMSYS-Chat-1M dataset (Zheng et al., 2024) instead of ShareGPT, Fiddler achieves 1.81× speedup on ShareGPT and 1.56× on LMSYS, both tested in Environment 1 under scenario a conditions (Figure 9). Both are conversation datasets, so the routing behavior is expected to be similar, but the 1.56× on LMSYS confirms that the advantage doesn't depend on a specific calibration-data distribution.

#### Model-Agnostic Validation (Appendix E)

**Headline result:** Fiddler's design extends beyond Mixtral-8x7B. Figure 10 shows that on the Phi-3.5-MoE model (Abdin et al., 2024), Fiddler outperforms DeepSpeed-MII by 6.5× on average across 15 input/output length configurations in the end-to-end scenario a metric. This 6.5× is dramatically larger than the Mixtral improvements, which likely reflects that Phi-3.5-MoE has different expert configuration and DeepSpeed-MII's offloading is less optimized for its architecture, giving Fiddler more room to improve — or that Fiddler's scheduling logic transfers well while the baseline struggles with model-specific characteristics. The paper provides only Figure 10 without detailed breakdown, so the reader should treat this as existence-proof of cross-model applicability rather than a claim of uniform 6.5× gains across all MoE models.

### Ablation Studies and Robustness Checks

The paper does not present traditional ablation studies in the machine learning sense (removing components and measuring accuracy degradation). Instead, the robustness analysis is distributed across appendices and the comparison of different workload types, each revealing how the system's components contribute to its behavior.

- **Granularity of scheduling (implicit ablation via baseline comparison):** The primary implicit ablation is the comparison between Fiddler (per-expert scheduling) and the baselines (global strategies). llama.cpp represents the "always Scenario C" extreme (compute on CPU, never transfer weights). DeepSpeed-MII and Mixtral-Offloading represent the "always Scenario B" extreme (always transfer weights to GPU when not resident). Fiddler's consistent outperformance of both across workloads demonstrates that per-expert granularity — not just better implementation of either strategy — drives the gains. The fact that llama.cpp beats offloading systems on single-batch but loses badly on prefill and beam search, while Fiddler wins across all three, isolates scheduling granularity as the decisive factor. However, this is not a controlled ablation (each baseline differs from Fiddler in implementation quality, memory management, and other details beyond strategy), so the comparison establishes practical superiority but not scientific attribution.

- **Expert placement strategy (popularity-based vs. random):** The paper quantifies the hit rate improvement from popularity-based GPU expert placement over random placement: in Environment 1, the expected hit rate is 25.2% (best) vs. 21.9% (random), a 3.3 percentage point improvement; in Environment 2, 53.0% (best) vs. 48.8% (random), a 4.2 percentage point improvement (Section 3.4). No end-to-end performance comparison between popularity-based and random placement is reported — the hit rate improvement is a proxy metric. This means the reader cannot directly assess how much of Fiddler's speedup is attributable to smarter expert placement versus the runtime scheduling algorithm. Given the modest absolute improvement in hit rate (3–5pp), it's likely that the scheduling algorithm accounts for the majority of the gains, but this is not empirically verified.

- **CPU kernel optimization (AVX512_BF16):** The paper states that a custom CPU computation kernel using AVX512_BF16 instructions was implemented because this instruction set "is not supported in the native PyTorch implementation" (Section 3.4). No ablation comparing the custom kernel against PyTorch's default CPU backend is presented. The kernel improves Scenario C execution speed, which shifts the CPU-vs-GPU decision threshold and makes CPU execution viable for larger batch sizes, indirectly improving Fiddler's scheduling flexibility. Without a comparison, the reader cannot know whether Fiddler's strategy would still outperform baselines using unoptimized CPU computation — or how much of the single-batch speedup specifically comes from faster CPU execution versus better scheduling.

- **Calibration data sensitivity (Appendix D):** The comparison between ShareGPT and LMSYS-Chat-1M datasets (Figure 9) shows Fiddler outperforming llama.cpp by 1.81× and 1.56× respectively in Environment 1. This 0.25× difference in improvement factors indicates some sensitivity to the calibration data distribution — llama.cpp's relative performance varies, or Fiddler's scheduling effectiveness shifts. The paper interprets this as showing "Fiddler's robustness to different distributions of inputs" (Appendix D), and the advantage remains substantial (>1.5×) in both cases, but the non-trivial difference between 1.81× and 1.56× suggests that routing behavior differences between datasets do affect the relative benefit of dynamic scheduling. A more thorough sensitivity analysis (testing on out-of-domain data unlike the calibration distribution, such as code or scientific text) would strengthen the robustness claim.

- **Latency model accuracy (Appendix A):** The microbenchmarks in Figure 7 validate the core assumptions of the latency model: GPU execution time is largely constant across input sizes (with a minor ~10% deviation in Environment 1 at batch size 1 due to PyTorch implementation differences), CPU execution time scales approximately linearly, weight transfer dominates over activation transfer by orders of magnitude, and activation transfer is negligible (<1% of single-input CPU latency). This is not an ablation of Fiddler but a validation of the model Fiddler relies on. The microbenchmarks are measured once per environment at initialization time, and the paper performs no runtime validation to confirm that the profiled constants remain accurate under sustained inference load (e.g., with thermal throttling, memory contention, or varying system state). This is a reasonable simplification for a research prototype but would matter in production deployment.

- **Latency breakdown by phase (Appendix F):** The separation of end-to-end latency into TTFT (Figure 11) and ITL (Figure 12) reveals that Fiddler's advantage is larger during the decode phase (ITL: 1.43× average speedup) than during the prefill phase (TTFT: 1.13× average speedup). This breakdown is informative rather than an ablation, but it illuminates where the system's strengths lie: the decode phase has the smallest per-expert batch sizes (maximizing the benefit of CPU routing) and repeats for every generated token (amplifying any per-step advantage), while the prefill phase processes all input tokens in parallel and has larger per-expert batch sizes that push more experts toward GPU execution anyway, reducing the differentiation between strategies.

### Critical Assessment

#### Claim 1: "Fiddler achieves 1.26× speedup in single batch inference"

**What the experiments actually demonstrate:** Figure 4 shows Fiddler consistently outperforming all baselines across 15 input/output length configurations in two environments, with an average 1.26× improvement over the best baseline (llama.cpp). This claim is well-supported by the presented data. However, several qualifications apply:

First, the 1.26× is an average over configurations with input lengths of 32–256 and output lengths of 64–512. The paper does not report whether the speedup varies systematically with input or output length — for very short outputs (where prefill dominates), the speedup may be smaller (as suggested by the 1.13× TTFT improvement in Figure 11); for very long outputs (where decode dominates), it may be larger (as suggested by the 1.43× ITL improvement in Figure 12). The average 1.26× conceals this heterogeneity.

Second, the baselines include only three systems, and one of them (llama.cpp) is the clearly dominant competitor in this regime. A stronger baseline might be a hypothetical hybrid system that manually applies a static rule (e.g., "use CPU for decode, GPU for prefill") without Fiddler's per-expert dynamic scheduling. The absence of such a baseline means we cannot distinguish how much of the 1.26× comes from the per-expert granularity specifically versus from simply using CPU sometimes and GPU other times.

Third, the paper does not isolate the contribution of the custom AVX512_BF16 kernel. If llama.cpp's CPU implementation is substantially slower than Fiddler's optimized kernel for reasons unrelated to scheduling strategy, then part of the reported speedup may be attributable to better CPU code rather than better scheduling decisions. The paper would be stronger with an ablation comparing Fiddler using PyTorch's default CPU backend against Fiddler using the custom kernel, to separate scheduling gains from implementation gains.

#### Claim 2: "Fiddler achieves 1.30× speedup in long prefill processing"

**What the experiments actually demonstrate:** Figure 5 shows Fiddler outperforming baselines with an average 1.07× improvement over DeepSpeed-MII and 1.65× over Mixtral-Offloading. The 1.30× figure in the paper's abstract and conclusion appears to be an average over *all* baselines, not over the best baseline. Against the best baseline (DeepSpeed-MII), the improvement is only 1.07× — a modest 7% TTFT reduction. This is an important qualification: Fiddler is not dramatically better than state-of-the-art offloading in long-prefill scenarios; it's slightly better than a well-optimized offloading system and substantially better than a less-optimized one.

The prefill scenario is where weight transfer costs can be amortized over many tokens, making offloading naturally efficient. Fiddler's dynamic scheduling provides only marginal benefit because most experts receive enough tokens to justify GPU execution, so the scheduling decisions largely converge to the same strategy offloading systems use. The paper's abstract and introduction claims of "1.30×" should be understood in this context — the number reflects improvement over all baselines, not over the strongest baseline for this specific workload.

#### Claim 3: "Fiddler achieves 11.57× speedup in beam search inference"

**What the experiments actually demonstrate:** Figure 6 shows Fiddler achieving 11.57× better performance than llama.cpp on beam search across widths 4–16. This is a valid measurement, but the comparison is against a single baseline that is known to be fundamentally unsuited for beam search workloads. The CPU-based strategy that llama.cpp uses degrades dramatically as beam width increases because per-expert batch sizes grow linearly with beam width, and CPU computation scales linearly with batch size. The 11.57× number primarily reflects how poorly CPU-only strategies handle beam search, not necessarily how uniquely effective Fiddler's scheduling is.

The paper does not compare against a hypothetical baseline that simply switches to GPU-with-transfer for all experts during beam search — which would be a natural "dumb hybrid" strategy. If such a baseline were close to Fiddler's performance, it would suggest that Fiddler's per-expert granularity provides limited additional value in beam search beyond the global decision to use GPU. Without this comparison, the reader cannot assess whether the dramatic 11.57× number is primarily due to Fiddler's scheduling intelligence or primarily due to avoiding a known-bad strategy that no well-informed practitioner would use for beam search.

Additionally, the other baselines (DeepSpeed-MII, Mixtral-Offloading) do not support beam search, so we don't know how an offloading-based system would perform. It's possible that a pure offloading system (Scenario B for all non-resident experts) would also substantially outperform llama.cpp on beam search, and the gap between Fiddler and offloading might be much smaller than 11.57×. The paper's framing of "11.57×" without this context somewhat overstates Fiddler's contribution to beam search specifically.

#### Claim 4: "Fiddler integrates the advantages of different types of existing systems"

**What the experiments actually demonstrate:** The three workload scenarios collectively show that Fiddler outperforms offloading-based systems (strong on prefill, weak on single-batch) AND CPU-based systems (strong on single-batch, weak on prefill and beam search). The key evidence is: Fiddler beats DeepSpeed-MII on single-batch (Figure 4) while beating llama.cpp on prefill (Figure 5) and beam search (Figure 6). No single baseline dominates across all three workloads. This claim is well-supported — Fiddler demonstrably avoids the failure modes of both strategy families.

However, the claim would be stronger with head-to-head comparisons against baselines that attempt similar integration. For instance, does llama.cpp have configuration options that would allow it to trade off CPU vs. GPU execution differently for prefill vs. decode? Can DeepSpeed-MII be configured to route some small-batch experts to CPU? If these baselines have such capabilities but Fiddler's dynamic policy still outperforms them, the integration claim is strengthened; if they lack such capabilities entirely, then Fiddler is being compared against systems that weren't designed for the same flexibility, which is a weaker claim.

#### Missing Experiments and Open Questions

**No ablation isolating the scheduling algorithm from the CPU kernel optimization:** The custom AVX512_BF16 kernel is an implementation detail that could independently provide speedup on CPU computation. Without comparing Fiddler-optimized-CPU against Fiddler-stock-PyTorch-CPU, we cannot quantify how much of the improvement comes from better scheduling versus faster CPU execution. If the custom kernel is the dominant factor in single-batch speedup (where CPU execution is heavily used), then the intellectual contribution of dynamic scheduling is less empirically grounded.

**No measurement of scheduling overhead:** Algorithm 1 runs once per layer per step, performing integer comparisons and table lookups. The paper reports no measurement of this overhead relative to total latency. For single-batch decode with very short per-step times (milliseconds), even microsecond-level scheduling overhead could be non-trivial. The paper implicitly assumes overhead is negligible, which is likely true given the simplicity of the algorithm, but without measurement this remains an assumption.

**No evaluation with concurrent requests:** The paper targets "resource-constrained environments where a small number of concurrent queries are given" but evaluates only single-request scenarios. What happens when 2–4 concurrent users submit requests? The latency model assumes CPU and GPU computations can be launched independently, but concurrent requests would create contention for both the CPU cores and the GPU — potentially breaking the constant-GPU-latency assumption if multiple requests compete for GPU memory bandwidth or compute units simultaneously. The evaluation scope is therefore narrower than what "small number of concurrent queries" might imply.

**No evaluation with dynamic batching or continuous batching:** Modern LLM serving systems use continuous batching to improve throughput. Fiddler's evaluation uses single requests with fixed input/output lengths. In a continuous batching setting, the per-expert batch size would vary continuously as new requests arrive and existing requests complete — which is exactly the regime where dynamic scheduling should provide the most value (since batch sizes are unpredictable and heterogeneous across experts). The absence of continuous batching evaluation means Fiddler's benefits in production serving scenarios are not demonstrated.

**Limited sensitivity analysis on popularity calibration:** The paper tests two conversation datasets (ShareGPT and LMSYS-Chat-1M) and finds similar performance. But both are conversation datasets — they likely induce similar expert routing distributions. The paper's claim that "expert popularity is almost universal across different input domains" is cited from prior work but not tested with a radically different domain like code generation, mathematical reasoning, or non-English text. If routing distributions shift substantially across domains, the static popularity-based placement would be suboptimal, and Fiddler's performance on those domains might degrade relative to a system with online expert caching.

**No evaluation of startup/initialization cost:** The initialization phase includes profiling latencies by running expert computations on CPU and GPU at various input sizes. For Mixtral-8x7B with 256 experts, this could involve thousands of microbenchmark runs. The paper does not report the initialization time, which matters for user experience if Fiddler is deployed in an interactive setting where model loading time is part of the perceived latency.

## 6. Limitations and Trade-offs

### 6.1 Difficulty Estimation Is Prohibitively Expensive and Unaccounted For

**The assumption or constraint.** Fiddler's runtime scheduling algorithm relies on knowing, per expert, how many tokens are routed to that expert — the `inp_size[j]` array in Algorithm 1. This information is available *after* the gating network executes, which is cheap (the gating network is a small feed-forward layer that runs on the GPU as part of the non-expert computation). So unlike the difficulty-estimation bottleneck in the prior paper, Fiddler's runtime decision does not require expensive pre-computation.

However, the expert placement optimization — placing the most popular experts in GPU memory — requires offline profiling of expert selection frequencies on calibration data. The paper describes this as: "we determine the popular experts based on the profile of expert selection using calibration data" (Section 3.4). The calibration involves running inference on a batch of samples from ShareGPT and counting expert activations. The paper does not report how many calibration samples are used or how long this profiling takes, but running a representative set of samples through a 47B-parameter model to convergence on routing statistics is non-trivial computational overhead. More importantly, the profile is static: once computed at initialization, it does not update. If the deployment domain differs from the calibration domain (e.g., calibrating on English conversation but serving code generation requests), the popularity ranking may be suboptimal.

**The consequence.** The consequence is that Fiddler's hit rate — the fraction of expert computations that follow the fast Scenario A (GPU-local) path — is tied to the representativeness of calibration data. If expert popularity shifts significantly for out-of-domain inputs, hit rates degrade from the reported 25.2% (Environment 1) and 53.0% (Environment 2) toward random-expectation baselines (21.9% and 48.8% respectively). Every percentage point of hit rate loss converts a Scenario A execution into Scenario B or C, directly increasing end-to-end latency. For a domain like code generation where token distributions and expert routing patterns might differ substantially from conversation data, the drop could be larger than the 3–5pp margin that popularity-based placement provides over random placement.

In the extreme, if a deployment serves highly diverse or continually shifting input distributions, the static profile effectively becomes random placement — losing 3–5pp of hit rate advantage. This doesn't break the system (Algorithm 1 still works for non-resident experts), but it erodes the benefit of the placement optimization. An online caching policy that dynamically swaps experts based on observed routing could maintain higher hit rates across distribution shifts, but Fiddler does not implement such a policy.

**What evidence exists in the paper.** Appendix D provides a sensitivity study comparing performance on ShareGPT versus LMSYS-Chat-1M, showing Fiddler achieves 1.81× and 1.56× speedup over llama.cpp respectively (Figure 9). Both are conversation datasets, so the routing distributions should be similar, and the 0.25× difference in speedup factors indicates some sensitivity to dataset despite the domain similarity. The paper acknowledges that "the popularity of experts is almost universal across different input domains" (Section 3.4) but cites this claim from prior work on Mixtral and OpenMoE rather than testing it with radically different domains. No experiment compares shareGPT-calibrated placement against a code-domain or math-domain workload to quantify the hit-rate degradation from distribution shift.

**Mitigation status.** The paper does not address this limitation beyond the cross-dataset comparison in Appendix D and the citation to prior work claiming cross-domain popularity universality. Future work could explore online popularity tracking with lazy expert reallocation, amortizing the reallocation cost over many inference requests, or training a lightweight predictor of expert popularity from input features to anticipate distribution shifts.

### 6.2 Single-Request, Fixed-Length Evaluation Leaves Real-World Serving Scenarios Unexplored

**The assumption or constraint.** All evaluation in Section 4 uses single requests with predetermined, fixed input and output lengths — scenarios a, b, and c each specify exact token counts for input and output. The paper states it targets "resource-constrained environments where a small number of concurrent queries are given, and the latency is critical for the user experience" (Section 4), but the evaluation never tests concurrency of even 2–4 simultaneous requests.

The latency model underlying Algorithm 1 assumes CPU and GPU latencies are independent and additive. The microbenchmarks in Appendix A measure each operation in isolation. Under concurrent load, multiple requests would compete for CPU cores (contention), GPU compute units (time-slicing), GPU memory bandwidth (saturation), and PCIe bandwidth (sharing). The constant-GPU-latency assumption — that GPU expert execution time is independent of batch size because it's memory-bandwidth-bound — could break if multiple requests' expert computations compete for the same memory bandwidth simultaneously. The linear-CPU-latency assumption could break if multiple threads contend for the same CPU cores, causing super-linear degradation from context switching.

**The consequence.** In concurrent serving, Fiddler's scheduling decisions may become suboptimal because the latency model no longer accurately predicts execution times. Specifically:

- If two requests both decide to execute large-batch experts on the GPU (Scenario B), the GPU memory bandwidth is shared, potentially causing both to take longer than the profiled `gpu_lat(s)` constant. This could shift the break-even threshold, making CPU execution preferable for batch sizes where the model predicted GPU execution would be better.

- If multiple requests route small-batch experts to the CPU simultaneously, the total CPU load may exceed available cores, causing queueing delays not captured by the per-token linear model. The paper's assumption that CPU latency scales linearly with the number of tokens *within a single expert* does not account for cross-request contention.

- PCIe bandwidth is shared across all concurrent transfers. The constant `transfer_lat()` assumes exclusive access to the full PCIe bandwidth. Under concurrent load, weight transfers for different experts (or different requests) would share the bus, increasing effective transfer latency.

The practical consequence is that Fiddler's scheduling policy — which was validated only in single-request scenarios — may not be optimal (or even correct) under concurrent load. The speedup numbers reported in Figures 4, 5, and 6 are upper bounds on what a concurrent deployment would achieve.

**What evidence exists in the paper.** None. The paper does not evaluate concurrent requests, does not measure contention effects, and does not discuss how the latency model would need to be extended for multi-request scenarios. The evaluation setup (Section 4.1) explicitly uses single requests with fixed lengths. The microbenchmarks (Appendix A) measure latencies in isolation without concurrent load.

**Mitigation status.** Not addressed. The paper does not discuss concurrency, contention, or multi-request scheduling. Extending Fiddler to concurrent serving would require: modeling contention for shared resources (GPU memory bandwidth, CPU cores, PCIe bus) in the latency functions; potentially replacing the deterministic per-expert decision with a global optimization that accounts for resource contention across all concurrently executing experts; and validating the approach under realistic multi-user load. This is a significant gap between the research prototype and production deployment.

### 6.3 Beam Search Comparison Is Against Only One (Known-Bad) Baseline

**The assumption or constraint.** The 11.57× beam search speedup — the most dramatic number in the paper — is measured against a single baseline, llama.cpp, because "the other baselines do not support beam search inference" (Section 4.1). llama.cpp uses a CPU-compute strategy (Scenario C) that is known to scale poorly with batch size, and beam search multiplies per-expert batch sizes by the beam width, making CPU computation pathologically slow. The 11.57× number therefore primarily reflects how terrible the CPU-only strategy is for beam search, not necessarily how uniquely effective Fiddler's scheduling is.

The paper does not compare against a simple hybrid baseline: use CPU computation for the single-batch decode steps (Scenario C) but switch entirely to GPU-with-transfer (Scenario B) during beam search, without Fiddler's per-expert granularity. Nor does it modify DeepSpeed-MII or Mixtral-Offloading to support beam search, which would likely perform substantially better than llama.cpp since they already execute non-resident experts on GPU.

**The consequence.** The 11.57× number is not a fair measure of Fiddler's contribution to beam search inference. A more meaningful comparison would be: Fiddler versus an offloading system (Scenario B for all non-resident experts) on beam search. Since Fiddler's scheduling likely converges to Scenario B for most experts during beam search (per-expert batch sizes are large enough that GPU-with-transfer wins the comparison in Algorithm 1), the gap between Fiddler and a pure-offloading baseline would be much smaller — possibly under 2×. The paper's abstract and conclusion prominently feature the 11.57× figure without context about the baseline's known inadequacy for this workload, which overstates Fiddler's specific contribution to beam search.

**What evidence exists in the paper.** Figure 6 shows the beam search results against only llama.cpp. The paper acknowledges the baseline limitation explicitly — "we compare Fiddler only against llama.cpp as the other baselines do not support beam search inference" (Section 4.1) — but does not discuss how this affects interpretation of the 11.57× number. No attempt is made to construct a stronger beam search baseline (e.g., by modifying DeepSpeed-MII to generate multiple sequences and score them).

**Mitigation status.** Partially addressed through transparency (the baseline limitation is stated) but not mitigated. The paper does not attempt to create a fairer comparison, nor does it qualify the 11.57× number in the abstract or conclusion with the baseline context. Future work could implement beam search in offloading-based frameworks to establish a proper comparison point, or could break down the 11.57× into "how much comes from avoiding CPU execution" versus "how much comes from Fiddler's per-expert scheduling."

### 6.4 No Ablation Isolating the Scheduling Algorithm from Implementation Optimizations

**The assumption or constraint.** Fiddler includes two distinct contributions: the runtime scheduling algorithm (Algorithm 1, which makes per-expert CPU-vs-GPU decisions) and implementation-level optimizations (the custom AVX512_BF16 CPU kernel, Section 3.4). The evaluation compares Fiddler (with both contributions) against baselines (with neither), so the measured speedups conflate the scheduling intelligence with the faster CPU code.

Specifically, the custom CPU kernel accelerates Scenario C execution, which is the path taken for small-batch experts during single-batch decode. Faster CPU execution not only reduces the absolute latency of Scenario C but also shifts the break-even threshold in Algorithm 1 — with a lower `cpu_lat(s)`, the CPU remains the better choice for larger batch sizes, meaning the scheduling algorithm can route more experts to the CPU before crossing into GPU-with-transfer territory. If llama.cpp's CPU implementation is substantially slower than Fiddler's optimized kernel for reasons unrelated to scheduling strategy, then some fraction of the 1.26× single-batch speedup is attributable to better CPU code rather than better scheduling decisions.

**The consequence.** Without an ablation, the paper cannot distinguish how much of the performance improvement comes from the intellectual contribution (dynamic per-expert scheduling) versus the engineering contribution (faster CPU matrix multiplication). This matters for: (a) practitioners deciding whether to adopt Fiddler's approach versus simply optimizing their CPU kernels within an existing framework like llama.cpp; (b) researchers trying to understand whether the scheduling algorithm generalizes to hardware without AVX512_BF16 support (the algorithm may still make correct decisions, but the absolute performance would be lower, narrowing the gap against baselines); and (c) fair attribution of the speedup — if the custom kernel accounts for, say, 40% of the single-batch improvement, then the 1.26× number overstates the value of dynamic scheduling specifically.

**What evidence exists in the paper.** No ablation comparing Fiddler with custom CPU kernel versus Fiddler with stock PyTorch CPU backend (or versus llama.cpp's CPU backend with Fiddler's scheduling logic). The paper mentions the custom kernel as an optimization (Section 3.4) but does not measure its isolated impact. The microbenchmarks in Appendix A measure CPU latency using Fiddler's implementation, not a baseline CPU implementation, so the reader cannot compare `cpu_lat(s)` between Fiddler and llama.cpp.

**Mitigation status.** Not addressed. The paper treats the AVX512_BF16 kernel as an implementation detail and does not discuss the need to separate its contribution from the scheduling algorithm's. A simple ablation — running Fiddler with PyTorch's default CPU matmul versus the custom kernel, in an otherwise identical system — would resolve this. Future work should ideally report the scheduling algorithm's benefit independently of implementation optimizations, or at minimum provide a breakdown.

### 6.5 Single Model (Mixtral-8x7B) as Primary Evaluation Target

**The assumption or constraint.** The core evaluation in Section 4 uses exclusively the Mixtral-8x7B model. The paper justifies this choice as: "this model not only represents the architecture of most of the recent MoE models but is also supported by all the baseline systems, ensuring a fair performance comparison" (Section 4.1). However, MoE models vary substantially in architectural parameters that could affect Fiddler's effectiveness: number of experts per layer (8 for Mixtral-8x7B, but some models have 16, 32, or hundreds), number of layers (32 for Mixtral-8x7B), expert hidden dimensions (14336 for Mixtral-8x7B, but DeepSeek models use different dimensions and shared experts), and gating mechanisms (top-2 routing for Mixtral, but some models use top-1, top-8, or learned routing with different sparsity patterns).

These parameters affect the core dynamics Fiddler exploits. More experts per layer means each expert receives fewer tokens on average, potentially shifting more decisions toward CPU execution. Larger hidden dimensions increase the weight size per expert (making weight transfer more expensive and GPU computation relatively more attractive). Different gating sparsity (top-1 vs. top-2 vs. top-8) changes the per-expert batch size distribution. Shared experts (used by DeepSeek-V2) are activated for all tokens and would always be GPU-resident, potentially changing the GPU memory allocation trade-off.

**The consequence.** Fiddler's scheduling thresholds and the relative benefit of per-expert decisions may not transfer to MoE architectures with different parameters. The modest improvement on Phi-3.5-MoE (6.5× over DeepSpeed-MII, Appendix E) is promising but measured against a single baseline and may not generalize to other architectures or configurations. Models with fewer, larger experts (making weight transfer more expensive) might favor CPU execution more heavily. Models with many small experts (Switch Transformer with 2048 experts) might be dominated by weight-transfer overhead unless GPU capacity can hold a larger fraction of experts. Practitioners considering Fiddler for a specific MoE model cannot confidently extrapolate from the Mixtral-8x7B results without understanding how architectural differences affect the scheduling dynamics.

**What evidence exists in the paper.** Appendix E evaluates Phi-3.5-MoE against DeepSpeed-MII, showing 6.5× speedup (Figure 10). This provides some evidence of cross-model applicability but is limited in two ways: (1) only one alternative model is tested, (2) the comparison is against a single baseline (DeepSpeed-MII) rather than the full set, so the result confirms Fiddler works on another model but doesn't characterize how architectural differences affect the scheduling advantage. The paper does not analyze how Phi-3.5-MoE's architecture (number of experts, hidden dimensions, gating configuration) differs from Mixtral-8x7B's or how those differences affect Fiddler's decisions.

**Mitigation status.** Partially addressed by the Phi-3.5-MoE experiment in Appendix E. The paper states that "our system is designed to be model-agnostic within the family of MoE models" (Appendix E), which is true at the algorithmic level (Algorithm 1 doesn't hard-code model-specific parameters) but doesn't guarantee consistent effectiveness across architectural variation. Future work could characterize Fiddler's performance as a function of MoE architectural parameters (number of experts, expert size, gating sparsity) to provide deployment guidance for model selection.

### 6.6 No Accounting for Serial Dependency in the Scheduling Algorithm

**The assumption or constraint.** Algorithm 1 makes independent decisions for each expert — for expert `j`, compare `cpu_lat(s)` against `gpu_lat(s) + transfer_lat()` and choose. This treats each expert's computation as an isolated operation. In reality, when multiple experts are assigned to the CPU (Scenario C), their computations must share CPU cores. When multiple experts are assigned to the GPU via weight transfer (Scenario B), their weight transfers must share the PCIe bus and their computations share GPU resources. The algorithm does not account for these interactions — it assumes the profiled latencies hold regardless of what other decisions are made for other experts in the same layer.

This is not just a concurrency issue (covered in Limitation 6.2). Even within a single request, a single MoE layer, if 4 out of 8 experts are routed to the CPU (Scenario C), they will compete for CPU cores and memory bandwidth. The effective per-expert CPU latency will be higher than the profiled value because multiple experts are executing concurrently on a shared CPU resource. Similarly, if 3 experts need weight transfers (Scenario B), the transfers will serialize or share PCIe bandwidth, making each transfer take longer than `transfer_lat()`. The algorithm's per-expert independence assumption means it may schedule too many experts to the CPU (or too many weight transfers to the GPU) simultaneously, creating resource contention that makes the actual latency worse than the model predicts.

**The consequence.** Under high contention — e.g., a layer where many experts receive moderate numbers of tokens and the algorithm independently decides CPU is better for each — the actual CPU execution time may be substantially higher than `cpu_lat(s)` times the number of CPU-routed experts, because they can't all run in parallel on finite CPU cores. This could cause the algorithm to make globally suboptimal decisions: it might choose CPU for experts where, if it accounted for contention, GPU-with-transfer would be faster. The 1.26× single-batch speedup may understate the achievable improvement if contention-aware scheduling could avoid overloading the CPU during decode steps with many CPU-routed experts.

Conversely, in scenarios where PCIe bandwidth is the bottleneck (e.g., Environment 1 with slower Gen3 PCIe), scheduling multiple simultaneous weight transfers could saturate the bus, increasing effective `transfer_lat()` and making GPU-with-transfer less attractive than the algorithm predicts. The algorithm might over-commit to GPU-with-transfer, causing congestion that CPU execution could have avoided.

**What evidence exists in the paper.** None. The latency model (Section 3.3) and microbenchmarks (Appendix A) measure operations in isolation. The paper does not discuss contention between concurrently executing experts within a single layer or single request, nor does it present experiments measuring the accuracy of the latency model under varying levels of intra-layer parallelism. The fact that Fiddler outperforms baselines despite this simplification suggests the contention effects may be modest for single-request scenarios, but this is not verified.

**Mitigation status.** Not addressed. The paper's latency model is intentionally simple and does not account for resource sharing. Incorporating contention into the model would require profiling resource utilization (CPU core occupancy, PCIe bandwidth usage, GPU streaming multiprocessor occupancy) as a function of concurrent operations and extending Algorithm 1 to make globally coherent decisions — e.g., solving a small optimization problem per layer that allocates experts to devices while respecting capacity constraints. The authors presumably judged this complexity unnecessary for the single-request, resource-constrained setting, but the limitation should be acknowledged when considering extensions to higher-load or concurrent-serving scenarios.
