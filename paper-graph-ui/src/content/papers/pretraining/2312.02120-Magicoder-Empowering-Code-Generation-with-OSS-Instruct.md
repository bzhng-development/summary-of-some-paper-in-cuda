# Magicoder: Empowering Code Generation with OSS-Instruct

**ArXiv:** [2312.02120](https://arxiv.org/abs/2312.02120)

## 🎯 Pitch

This paper introduces **OSS-INSTRUCT**, a novel data generation method that leverages open-source code snippets as inspiration for a teacher LLM to automatically synthesize diverse, realistic programming problems and solutions, then uses this synthetic data to instruction-tune smaller code models.

---

## 1. Executive Summary

This paper introduces **OSS-INSTRUCT**, a novel data generation method that leverages open-source code snippets as inspiration for a teacher LLM to automatically synthesize diverse, realistic programming problems and solutions, then uses this synthetic data to instruction-tune smaller code models. Training CODELLAMA-PYTHON-7B on 75K OSS-INSTRUCT examples yields Magicoder-CL, which outperforms all studied open-source models at or below 16B parameters on HumanEval+, MBPP+, MultiPL-E, and DS-1000, while the enhanced MagicoderS-CL—combining OSS-INSTRUCT with the orthogonal Evol-Instruct method—surpasses ChatGPT on HumanEval+ (66.5% vs. 65.9% pass@1) with only 7B parameters. The paper establishes that distilling open-source inspired synthetic instruction data triggers a base model's latent coding capabilities beyond simple teacher distillation, as demonstrated by a Magicoder variant trained with a weaker Mixtral teacher that nevertheless outperforms its own instructor on both HumanEval+ and MBPP+.

## 2. Context and Motivation

### The Core Problem: Synthetic Instruction Data Is Biased and Narrow

The fundamental challenge this paper addresses is a critical bottleneck in building capable open-source coding LLMs: **how do you generate high-quality, diverse instruction-tuning data without inheriting the biases of the LLMs that produce it?** Since the advent of instruction tuning (Wei et al., 2022) and its application to code via Alpaca-style distillation (Taori et al., 2023; Chaudhary, 2023), the standard recipe for creating an instruction-following code model has been:

1. Take a handful of seed tasks (Code Alpaca uses only 21).
2. Prompt a powerful teacher LLM (typically ChatGPT or GPT-4) to generate variations of those tasks.
3. Fine-tune a weaker base model on the teacher's outputs.

This pipeline has produced models like Code Alpaca (Chaudhary, 2023) and WizardCoder (Luo et al., 2023b) that achieve strong results. But the paper identifies a structural flaw in this approach: the synthetic data generation process is **fundamentally self-referential**. The teacher LLM is asked to "create a coding problem," and the only thing guiding its creativity is a small set of seed tasks or a handful of heuristics (Evol-Instruct uses exactly 5 heuristics: add constraints, deepen, concretize, increase reasoning, and complicate input). The LLM cannot draw on anything outside its own training distribution — it simply recombines patterns it has memorized.

This matters because, as Yu et al. (2023) and Wang et al. (2023a) have noted, such approaches "may significantly inherit the system bias inherent in the LLMs as well as the predefined tasks." The resulting instruction data clusters around a narrow region of problem space: the problems an LLM thinks look like "typical coding problems." The student model then learns to solve exactly that narrow class of problems, and its performance improvements may partially reflect **overfitting to the data generation distribution** rather than genuine capability gains.

### Why This Problem Matters: The Open-Source vs. Closed-Source Gap

This bias problem has real consequences. At the time of the paper's writing, the coding benchmark landscape was dominated by closed-source models — GPT-3.5 Turbo and GPT-4 — while even the best open-source code models (WizardCoder-CL-34B, CODELLAMA-PYTHON-34B) lagged behind, despite having comparable or larger parameter counts. The gap was most pronounced on rigorous evaluation sets:

- On HumanEval+, which augments the standard HumanEval benchmark with **80× more test cases** to catch false positives, the open-source WizardCoder-CL-34B scored 64.6% vs. GPT-3.5 Turbo's 65.9% (Table 1). But getting there required **34B parameters** — roughly 5× the size of a 7B model.
- On HumanEval, the 7B WizardCoder-CL scored only 48.2%, leaving a massive 24-point gap to GPT-3.5 Turbo's 72.6%.

The practical implication is straightforward: deploying capable code assistants requires either paying for closed-source APIs (with associated costs, latency, and privacy concerns) or running very large open-source models (with high hardware requirements). A genuinely diverse instruction-tuning dataset could enable **smaller models** to close this gap, making capable code generation accessible on consumer hardware.

The theoretical significance runs deeper. If synthetic data from LLMs simply reflects LLM biases, then the self-improvement pipeline that many researchers envision — use LLMs to generate training data for better LLMs — hits a ceiling: models can only get as good as their training data, and if the data is bottlenecked by the generating model's distribution, progress stalls. Breaking this circularity requires **injecting external information** into the data generation process. OSS-INSTRUCT's core insight is that open-source code provides exactly this — a universe of real programming patterns far more diverse than any single LLM's internal representation.

### Where Prior Approaches Fall Short

The paper identifies specific limitations in the two dominant prior methods:

**SELF-INSTRUCT (Wang et al., 2023a) and its code adaptation, Code Alpaca (Chaudhary, 2023).** These methods start with a small set of human-written seed tasks and ask an LLM to generate new instructions that are "similar but different." The paper notes that Code Alpaca "only relies on 21 seed tasks to generate new code instructions using an identical prompt template" (§1). Twenty-one examples are a vanishingly small window into the space of possible programming problems. The LLM's generations will be fundamentally constrained by the patterns present in those seeds — a 21-point sampling of a high-dimensional space. Moreover, the prompt template itself is static, meaning all generations share the same structural framing. The quantitative evidence in Figure 3 confirms the consequence: SELF-INSTRUCT data shows the **highest average cosine similarity to HumanEval** (0.169) among the three methods studied, suggesting it produces problems that cluster near benchmark-like distributions rather than exploring broadly.

**Evol-Instruct / Code Evol-Instruct (Luo et al., 2023b).** This method improves on Code Alpaca by applying heuristics to increase problem complexity: it takes existing instructions and asks the LLM to add constraints, deepen reasoning requirements, concretize vague descriptions, or increase input complexity. The paper explicitly notes that WizardCoder "takes Code Alpaca as seeds and merely depends on 5 heuristics to evolve the dataset" (§1). While this increases diversity relative to the original seeds, it still operates within the conceptual boundaries of the seed problems. An evolved version of a "sort a list" problem is still about sorting — it might add a time complexity constraint or a custom comparator, but it won't become a problem about implementing a network protocol or building a reinforcement learning agent. The cosine similarity analysis supports this: Evol-Instruct achieves lower similarity to HumanEval than SELF-INSTRUCT (0.131 vs. 0.169), suggesting broader diversity, but it remains fundamentally bounded by its seed distribution.

**Direct fine-tuning on raw code.** A natural question is whether fine-tuning on high-quality open-source code directly — without the intermediate step of generating problem-solution pairs — could work just as well. This is an important baseline because OSS-INSTRUCT starts from open-source code, so the method's value hinges on the transformation step being beneficial rather than wasteful. The paper addresses this head-on in Section 4.2: mining semantically relevant comment-function pairs from the same source corpus and fine-tuning on them **actually worsened performance** (Table 6), dropping MultiPL-E pass@1 from 29.6 to 24.1. The authors attribute this to "substantial noise and inconsistency that exists intrinsically in the data pairs" — raw code comments often don't cleanly specify a function's behavior, and real-world code contains many edge cases, workarounds, and incomplete fragments that make poor training examples.

### How OSS-INSTRUCT Positions Itself

OSS-INSTRUCT is fundamentally different from all prior methods because **it breaks the self-referential loop**. Rather than asking an LLM to generate problems *from nothing* (which forces it to draw on its internal biases), OSS-INSTRUCT gives the LLM an *external seed* — 1 to 15 consecutive lines of real open-source code — and asks it to generate a problem and solution *inspired by* that seed.

This seemingly simple change has profound implications for data diversity:

**1. The seed space is effectively infinite.** The seed corpus, `starcoderdata` (Li et al., 2023), contains billions of lines of permissively licensed code spanning dozens of programming languages. Every code document encodes a unique combination of algorithms, data structures, library usage patterns, error handling strategies, and domain-specific conventions. By randomly sampling 1–15 line windows from 80K documents, OSS-INSTRUCT draws from a vast, high-entropy distribution that no LLM could internally represent. As Figure 2 demonstrates, this produces problems ranging from "implement a reinforcement learning agent" (inspired by imports of `gym_electric_motor` and `numpy`) to "build a full Spring Boot banking application" (inspired by `@SpringBootApplication` and `AxonbankApplication` class signatures) to "generate error files from datasets" (inspired by a single shell command).

**2. The seeds provide controllability without constraining diversity.** OSS-INSTRUCT directly addresses the paper's stated goal of producing "controllable" instruction data — you can influence what kinds of problems are generated by controlling the distribution of seed snippets (e.g., sampling more from Python repositories to bias toward Python problems). But unlike the 21-seed or 5-heuristic approaches, this controllability doesn't come at the cost of narrowness, because the seed space itself is broad.

**3. The orthogonal combination with Evol-Instruct is by design.** The paper explicitly positions OSS-INSTRUCT as orthogonal to Evol-Instruct — they operate on different principles (external inspiration vs. heuristic complexity increase) and can be combined. The MagicoderS models, trained on OSS-INSTRUCT data followed by Evol-Instruct data, demonstrate this complementary effect by outperforming models trained on either alone.

The contrast with prior work is sharpest when considering *where* OSS-INSTRUCT draws creativity from. SELF-INSTRUCT and Evol-Instruct draw creativity from the LLM's parametric memory — a compressed, lossy representation of its training distribution. OSS-INSTRUCT draws creativity from the actual source distribution itself, with the LLM serving as a *translator* (code fragment → coherent problem-solution pair) rather than a *generator* (nothing → problem). This is analogous to the difference between asking someone to "come up with a coding problem" versus "look at this snippet of unfamiliar code and imagine what problem it solves" — the latter leverages external information that circumvents the person's default patterns of thought.

The paper also distinguishes its work from the concurrent DeepSeek-Coder series (Guo et al., 2024), which uses undisclosed training data and methods. By fully open-sourcing OSS-INSTRUCT's data, weights, and code, Magicoder provides a transparent baseline for the research community — a sharp contrast to models whose strong performance may depend on proprietary data generation pipelines.

## 3. Technical Approach

### 3.1 Reader Orientation

Magicoder is a family of instruction-tuned code generation models built by fine-tuning a base LLM on **synthetically generated programming problem-solution pairs**, where the problems are not created from a handful of seed tasks or heuristic rewriting rules but instead generated by a teacher LLM that draws inspiration from randomly sampled fragments of real open-source code. The core technical problem is how to produce diverse, realistic instruction data for code that avoids the narrowness and inherited bias of prior self-instruction methods, and the solution takes the shape of a **two-stage pipeline**: (1) a data generation stage where a teacher LLM (GPT-3.5 Turbo) translates open-source code snippets into self-contained programming problems with solutions, and (2) a supervised fine-tuning stage where a base code model (CODELLAMA-PYTHON-7B or DeepSeek-Coder-Base-6.7B) is trained on this synthetic data to internalize the instruction-following patterns and coding knowledge it encodes.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components arranged in a sequential pipeline:

1. **Seed Corpus (`starcoderdata`)** — a massive, pre-filtered collection of permissively licensed source code files spanning languages like Python, Java, C++, TypeScript, and others. It serves as the external entropy source that breaks the self-referential loop of prior methods.
2. **Seed Snippet Extractor** — a simple random sampler that draws 1–15 consecutive lines from each of 80K selected code documents (40K Python, 5K each from 8 other languages), producing raw, context-agnostic code fragments.
3. **Teacher LLM (GPT-3.5 Turbo, `gpt-3.5-turbo-1106`)** — a powerful, instruction-following language model that takes each seed snippet and a carefully designed prompt template, and outputs a self-contained programming problem description and a corresponding solution. The teacher is run in **greedy decoding mode** to maximize consistency between the generated problem and solution.
4. **Data Cleaning & Decontamination Module** — a post-processing pipeline that removes duplicate samples (identical pairs or same seed snippet), filters out exact matches of known benchmark contents (HumanEval, MBPP, APPS, DS-1000, GSM8K docstrings/solutions), and produces the final ~75K-entry OSS-INSTRUCT dataset.
5. **Base Model + Fine-Tuning Loop** — CODELLAMA-PYTHON-7B (or DeepSeek-Coder-Base-6.7B) is fine-tuned via standard supervised learning on the OSS-INSTRUCT dataset for 2 epochs using the Adafactor optimizer, producing Magicoder-CL (or Magicoder-DS). An optional second fine-tuning stage on the open-source Evol-Instruct dataset (`evol-codealpaca-v1`, ~110K samples) produces MagicoderS variants.

Information flows strictly forward through this pipeline: seed corpus → random snippet extraction → teacher LLM generation → cleaning/decontamination → fine-tuning → deployed Magicoder model. There are no feedback loops or iterative refinement stages; each component is executed once.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **data-centric paper** whose core technical innovation is OSS-INSTRUCT, a method for generating diverse, realistic synthetic instruction-tuning data for code by using open-source code snippets as external inspiration seeds for a teacher LLM, rather than relying on the LLM's internal parametric knowledge or a small set of predefined heuristics.

#### Seed Snippet Extraction from starcoderdata

The foundation of OSS-INSTRUCT is the seed code corpus and the procedure for extracting snippets from it. The paper selects **`starcoderdata`** as the source corpus, which is a filtered, permissively licensed subset of The Stack (Kocetkov et al., 2022) — a 3TB collection of source code from GitHub. The authors chose `starcoderdata` for three stated reasons: it is widely adopted in the research community, it contains massive high-quality code snippets, and it has already undergone rigorous post-processing for data decontamination (Li et al., 2023; Allal et al., 2023). This last point is critical because it means the seed corpus itself has been screened to avoid containing benchmark test sets — reducing the risk that OSS-INSTRUCT will inadvertently generate benchmark-like problems through contaminated seeds.

The extraction procedure operates as follows:

1. **Document selection:** 80,000 code documents are randomly sampled from `starcoderdata` with a deliberate language distribution: **40,000 from Python** and **5,000 each from C++, Java, TypeScript, Shell, C#, Rust, PHP, and Swift**. This yields a Python-heavy mixture (50% Python, 50% distributed across 8 other languages) that balances the primary target language (Python, which dominates the evaluation benchmarks) against multilingual diversity. The authors do not explain the specific choice of 40K/5K splits, but the asymmetry reflects the practical goal of maximizing Python performance while still exposing the model to cross-lingual code patterns.
2. **Snippet extraction:** For each of the 80K selected documents, **1 to 15 consecutive lines** are randomly extracted. The length is uniformly random within this range — the paper states "randomly extract 1–15 consecutive lines as the seed snippet." This range is intentionally chosen to provide snippets of varying completeness: a single line might be a lone import statement or variable declaration, while 15 lines could capture a full function body or a meaningful code block. The randomness ensures that the teacher LLM encounters a wide spectrum of code granularities, from tiny fragments requiring substantial imaginative extrapolation to relatively complete units requiring only contextual framing.
3. **Output:** 80K raw seed snippets, each an unaltered excerpt from a real codebase, with no filtering for syntactic validity, no requirement that the snippet be executable, and no annotation of the snippet's semantic meaning. The snippets are deliberately kept as they appear in the source — incomplete, potentially referencing undefined variables or external dependencies, with whatever indentation and formatting the original author used.

**Design rationale for the snippet approach.** The key insight behind the 1–15 line random window is that it provides **partial information** — enough to anchor the teacher LLM's generation in a specific coding context, but not enough to fully specify what problem the code solves. This forces the LLM into a creative act of *interpretation*: it must infer from a fragment (e.g., a few `import` statements, a function signature, a block of array manipulation) what the broader programming scenario might be. The authors explicitly contrast this with using entire code files or well-documented functions, which would reduce the generation task to a bland summarization exercise. In Figure 2's qualitative examples, we see this effect in action: a single line of shell script (`python3 makeErrorFile.py data/test_dataset_14 14`) inspires a full Python program with command-line argument parsing, file I/O, and error handling — the LLM extrapolated an entire application architecture from a usage example.

#### OSS-INSTRUCT Prompt Template and Generation Protocol

The teacher LLM transforms each seed snippet into a complete training example (problem + solution) using a carefully designed prompt template and a controlled generation protocol. The full prompt template is reproduced in Figure 4 of the paper and consists of three sections:

1. **High-level task description:**
   > "You are exceptionally skilled at crafting high-quality programming problems and offering precise solutions. Please gain inspiration from the following random code snippet to create a high-quality programming problem. Present your output in two distinct sections: [Problem Description] and [Solution]."

   This framing instruction establishes the teacher's role, the source of inspiration, and the required output format.

2. **Seed code snippet insertion:**
   > "Code snippet for inspiration: ```\n{code}\n```"

   The `{code}` placeholder is replaced with the 1–15 randomly extracted lines of source code, presented as a code block.

3. **Detailed output guidelines:**
   > "Guidelines for each section: 1. [Problem Description]: This should be \*\*completely self-contained\*\*, providing all the contextual information one needs to understand and solve the problem. Assume common programming knowledge, but ensure that any specific context, variables, or code snippets pertinent to this problem are explicitly included. 2. [Solution]: Offer a comprehensive, \*\*correct\*\* solution that accurately addresses the [Problem Description] you provided."

   The emphasis on "completely self-contained" is technically significant: the generated problem must not reference the original code snippet or assume the student model has seen it. The problem must stand alone as a coherent task description that any programmer (or code LLM) could read and solve. This constraint forces the teacher LLM to **recontextualize** the code snippet — extracting its *essence* (the algorithmic idea, the library usage pattern, the data structure manipulation) and expressing it in natural language, rather than just describing what the snippet does.

**Generation protocol.** For each seed snippet, the teacher model (`gpt-3.5-turbo-1106`) is prompted with this template and run with **greedy decoding** (temperature = 0). The paper states the reason explicitly: "Given the numerous seed code snippets, we perform greedy decoding to maximize the consistency between the generated problems and solutions." This is a crucial design decision that trades off diversity-at-the-output-level (which stochastic decoding would increase) for **internal consistency** — the teacher must produce a problem whose solution is correct, and greedy decoding increases the probability that the solution actually addresses the stated problem. Since diversity is already injected by the highly varied seed snippets, additional output-level randomness is unnecessary and potentially harmful (it could produce problem-solution mismatches).

The teacher model outputs two sections delimited by `[Problem Description]` and `[Solution]` headers. These are parsed and stored as a single instruction-tuning example, with the problem serving as the instruction/prompt and the solution serving as the expected response. No additional filtering based on the presence of both sections is described — the data cleaning stage handles obvious failures.

**What the teacher model actually does.** Operationally, the generation process performs three cognitive transformations on each seed snippet:

- **Abstraction:** The teacher extracts the generalizable programming concept from the concrete code. If the seed contains `import gym_electric_motor as gem`, the teacher abstracts this to "reinforcement learning environment for electric motor control" — not just "import a library."
- **Problem formulation:** The teacher constructs a natural language task description that, if solved, would produce code structurally and semantically related to the seed. This involves inventing plausible context (e.g., "You are building a banking system..."), specifying requirements, and defining input/output formats — all elements absent from the raw snippet.
- **Solution authoring:** The teacher generates complete, runnable code that satisfies the problem. The solution is not required to match the original seed code — it is a *new* implementation inspired by the seed's patterns. In the reinforcement learning example (Figure 2), the seed is two imports and a plotting library import, but the generated solution includes a full `DQNAgent` class with training loops, state reshaping, and environment interaction — far beyond what the seed contained.

#### Data Cleaning, Deduplication, and Decontamination

The raw outputs from GPT-3.5 Turbo undergo a multi-stage cleaning pipeline to produce the final OSS-INSTRUCT training dataset.

**Deduplication.** The first cleaning stage removes exact duplicate entries. Two types of duplication are checked:
- Samples with **identical problem description and solution text** (exact string match).
- Samples that share the **same seed code snippet** (since the teacher model could plausibly generate different problems from the same seed, but these would be semantically correlated).

The paper does not specify the exact number of duplicates removed, but the final dataset size is approximately 75K from 80K initial seeds, implying roughly 5K samples were filtered across all cleaning stages.

**Soft noise retention.** The authors make an explicit, empirically motivated decision to **not remove** certain types of noisy data. Specifically, samples where "the solution is incomplete" or otherwise imperfect are retained. The paper cites Honovich et al. (2023) as precedent for this choice: "inspired by Honovich et al. (2023), they are not removed as we believe they still contain valuable information for LLMs to learn." The intuition is that even flawed solutions teach the student model something — partial code, incomplete implementations, and imperfect solutions still encode programming patterns, library usage conventions, and algorithmic thinking. Removing them would discard potentially useful training signal.

The paper validates this decision in Appendix C.3 with a concrete ablation: removing Python samples containing `pass` or `NotImplemented` tokens (indicating stub/unfinished implementations) reduces the dataset from 75K to 68K entries, and the resulting model achieves **54.9% pass@1 on HumanEval+** versus **55.5% with the noisy data included** (Table 10). This small but consistent gap supports the claim that even imperfect synthetic data contributes marginally to training.

**Decontamination.** The most critical cleaning step is preventing benchmark leakage — training data that contains the exact problems or solutions from evaluation benchmarks. The paper applies the exact same decontamination logic as StarCoder (Li et al., 2023), checking each generated problem and solution against the following benchmarks:

- **HumanEval (Chen et al., 2021):** Check for exact matches of docstrings or solutions.
- **MBPP (Austin et al., 2021):** Check for exact matches of docstrings or solutions.
- **APPS (Hendrycks et al., 2021):** Check for exact matches of docstrings.
- **DS-1000 (Lai et al., 2022):** Check for exact matches of prompts.
- **GSM8K (Cobbe et al., 2021):** Check for exact matches of questions.

The paper reports that **only 9 additional samples** were filtered out of the OSS-INSTRUCT dataset through decontamination, a remarkably small number. From this observation, the authors draw an important inference: "Since the seed corpus starcoderdata has already gone through rigorous data decontamination, this observation suggests that OSS-INSTRUCT is unlikely to introduce additional data leakage beyond the seeds." In other words, the teacher LLM is not memorizing benchmark problems and reproducing them — the very low contamination rate implies that the generation process genuinely produces novel problems rather than regurgitating training data.

The same decontamination procedure is also applied to the Evol-Instruct dataset (`evol-codealpaca-v1`) used for MagicoderS, filtering out 89 samples from its ~110K entries.

**Final dataset.** After cleaning, the OSS-INSTRUCT dataset contains approximately **75K problem-solution pairs**. Appendix A.3 characterizes this dataset along two dimensions:

- **Category breakdown:** Using the INSTRUCTOR embedding model (Su et al., 2022) with 10 manually defined coding categories inspired by GitHub topic tags and OctoPack (Muennighoff et al., 2023), each sample is classified via cosine similarity to category embeddings. Figure 6 shows the resulting distribution, which the paper describes as exhibiting "diversity and balance across different categories." The categories are not enumerated in the main text, but the diversity claim is supported by the low average similarity to HumanEval (Section 2.3, Figure 3).
- **Length distribution:** Figure 7 plots the token count distribution for problems and solutions separately. The distributions span from roughly 50 to over 600 tokens per problem and 50 to over 700 tokens per solution, with peaks in the 100–300 token range for both. This wide variation in length, driven naturally by the diversity of seed snippets (a single import line produces shorter problems than a 15-line class definition), is an emergent property of the random extraction procedure rather than a manually engineered distribution.

**Cosine similarity analysis (Figure 3).** To demonstrate that OSS-INSTRUCT produces genuinely diverse data rather than HumanEval-like memorized patterns, the paper computes pairwise cosine similarities between each sample in the 75K dataset and each of the 164 HumanEval problems, using **TF-IDF embeddings**. The key comparison is:

- **SELF-INSTRUCT (Code Alpaca, 20K samples):** average similarity = **0.169**
- **Evol-Instruct (evol-codealpaca-v1, 110K samples):** average similarity = **0.131**
- **OSS-INSTRUCT (75K samples):** average similarity = **0.105**

The interpretation: OSS-INSTRUCT data is, on average, **less similar to HumanEval** than data from prior methods. This is evidence that the performance improvements from Magicoder are not simply due to training on data that happens to look like the test set. The lower similarity means the model must generalize from a broader distribution of problems to solve the benchmark.

#### Fine-Tuning Procedure

**Base models.** The paper uses two base LLMs for all experiments:

- **CODELLAMA-PYTHON-7B (Rozière et al., 2023):** The primary base model for Magicoder-CL and MagicoderS-CL. This is a 7-billion parameter decoder-only transformer, pre-trained on both code and natural language, with specialized Python training that gives it strong baseline coding capabilities. The paper selected it because it is "representative of the capabilities of many contemporary LLMs" and because its 7B size makes fine-tuning experiments feasible on 2 GPUs while still showing meaningful room for improvement (its base pass@1 on HumanEval is 37.8%, leaving a large gap to frontier models).
- **DeepSeek-Coder-Base-6.7B (Guo et al., 2024):** A stronger base model used for Magicoder-DS and MagicoderS-DS, selected because DeepSeek-Coder demonstrated exceptional coding performance concurrent with this work. This allows the paper to show that OSS-INSTRUCT benefits generalize beyond a single base model family.

**Single-stage training (Magicoder).** The base model is fine-tuned on the 75K OSS-INSTRUCT dataset using the Hugging Face `transformers` library with the following hyperparameters:

| Hyperparameter | Value | Where Specified |
|---|---|---|
| Epochs | 2 | Appendix B.3 |
| Optimizer | Adafactor (Shazeer & Stern, 2018) | Appendix B.3 |
| Initial learning rate | 5e-5 | Appendix B.3 |
| Learning rate schedule | Linear decay | Appendix B.3 |
| Warmup steps | 15 | Appendix B.3 |
| Batch size | 512 (sequences per update) | Appendix B.3 |
| Max sequence length | 1216 tokens (truncated) | Appendix B.3 |
| Hardware | 2 × NVIDIA A100-80GB | Appendix B.3 |
| Parallelism | PyTorch Distributed Data Parallel (DDP) | Appendix B.3 |

The choice of **Adafactor** over the more common AdamW deserves attention. Adafactor is an adaptive optimizer that stores only row- and column-wise second-moment estimates for matrix parameters rather than full per-element estimates, dramatically reducing memory consumption — a practical necessity when fine-tuning a 7B parameter model on two 80GB GPUs with a batch size of 512. The paper does not explicitly state this memory motivation, but it follows standard practice for large-scale transformer fine-tuning where parameter-state memory dominates.

The **2-epoch training** duration is also notable. The paper does not discuss early stopping or validation-based checkpoint selection; the model is simply trained for 2 full passes over the 75K dataset. This implies roughly 293 update steps (75,000 / 512 ≈ 147 per epoch) — a relatively short training procedure compared to base model pretraining. The short duration is consistent with the instruction-tuning paradigm: the goal is to adapt the model's output distribution to follow instructions, not to learn new fundamental capabilities from scratch.

**Two-stage training (MagicoderS).** For the enhanced MagicoderS models, a second fine-tuning stage is applied:

1. **Stage 1:** Train on OSS-INSTRUCT (75K samples) as described above, producing Magicoder.
2. **Stage 2:** Continue fine-tuning from the Magicoder checkpoint on the **evol-codealpaca-v1** dataset (theblackcat102, 2023), an open-source reproduction of Evol-Instruct containing approximately **110K samples** generated by GPT-4.

The Stage 2 hyperparameters are identical to Stage 1 except for **15 warmup steps** and a **maximum sequence length of 1024 tokens** (reduced from 1216). The reduction in sequence length for Evol-Instruct data is likely because Evol-Instruct problems tend to have longer problem descriptions (due to the complexity-increasing heuristics) and the model needs to accommodate both long instructions and long solutions within the context window — reducing sequence length forces truncation of very long examples rather than running out of GPU memory.

The Evol-Instruct dataset used (`evol-codealpaca-v1`) is **not** the official WizardCoder dataset, which was not publicly released. The paper explicitly notes this substitution: "We resort to the open-source implementation because the official Code Evol-Instruct (Luo et al., 2023b) dataset is not released." This means MagicoderS is trained on a GPT-4-generated dataset that follows the Evol-Instruct methodology (applying 5 heuristics to increase complexity: add constraints, deepen, concretize, increase reasoning, complicate input) but was produced by a different implementation than the one used to train WizardCoder. This is methodologically sound for demonstrating orthogonality — the *method* of Evol-Instruct, not specific dataset artifacts, is what matters — but it means MagicoderS is not directly comparable to WizardCoder in a "same data, different base model" sense.

**Why two-stage rather than mixed?** The paper does not explicitly justify why OSS-INSTRUCT and Evol-Instruct data are presented sequentially rather than shuffled together in a single training stage. The implicit motivation, based on the stated orthogonality of the two methods, is that sequential training allows each dataset to contribute its distinct signal: OSS-INSTRUCT first teaches the model a broad, diverse set of coding patterns drawn from real open-source code, while Evol-Instruct then refines the model's ability to handle **complex, multi-step reasoning** within those patterns. Mixing them would interleave the signals, potentially causing the model to average between two different data generation philosophies rather than building on them hierarchically.

---

#### The Evol-Instruct Combination Strategy

The claim of "orthogonality" between OSS-INSTRUCT and Evol-Instruct is central to the MagicoderS design and deserves precise technical definition. The paper uses "orthogonal" to mean that the two methods achieve data diversity through **mechanistically independent processes** that do not interfere with or duplicate each other:

- **OSS-INSTRUCT** increases diversity by expanding the **breadth of problem topics** — the seed snippets expose the teacher LLM to code patterns it would never spontaneously generate, producing problems about reinforcement learning, Spring Boot applications, shell-to-Python wrappers, and so on. The diversity comes from the external information injected by the seeds.
- **Evol-Instruct** increases diversity by expanding the **depth of problem complexity** — it takes existing problems and applies heuristic transformations that add constraints, require deeper reasoning, or concretize vague specifications. The diversity comes from recursively applying these transformations.

These mechanisms are orthogonal because:
1. They operate on different axes (topic breadth vs. solution depth).
2. They use different sources of variation (external code vs. heuristic rewriting).
3. They can be applied sequentially without one undermining the other — OSS-INSTRUCT generates the initial problems, and Evol-Instruct could theoretically be applied to OSS-INSTRUCT outputs to further increase their complexity.

In practice, the paper does not apply Evol-Instruct *to* OSS-INSTRUCT data; it simply concatenates the two datasets sequentially during training. The MagicoderS result (70.7% on HumanEval vs. 60.4% for Magicoder-CL, Table 1) demonstrates that this combination provides complementary benefits — the gap between the two models is larger than what either dataset alone would predict (since Magicoder-CL already captures OSS-INSTRUCT's benefit, the 10.3 percentage point improvement is attributable to Evol-Instruct's complementary depth signal).

---

#### Key Design Choices and Their Technical Justifications

**Why 1–15 lines per seed snippet?** The range is a deliberate trade-off between *specificity* and *open-endedness*. A single line (e.g., `import numpy as np`) provides almost no information about the intended task, forcing the teacher LLM to imagine an entire problem from scratch — this maximizes diversity but risks generating incoherent or trivial problems. Fifteen lines (e.g., a full function body with error handling) provides substantial structure that constrains the problem formulation — this increases realism but reduces the teacher's creative latitude. Sampling uniformly across this range ensures that the dataset contains both extremes and everything in between, naturally creating a varied distribution of problem types and abstraction levels. No ablation is provided for different range bounds.

**Why greedy decoding for the teacher?** The explicit justification is "to maximize the consistency between the generated problems and solutions" (Appendix B.1). A stochastic decoding strategy (temperature > 0 or top-p sampling) would increase output diversity but risk generating a problem that the accompanying solution does not actually solve — a form of hallucination at the training-data level. Since the seed snippets already provide the diversity, the teacher's job is to reliably translate diversity into correctness, and greedy decoding optimizes for that translation. The paper does not report experiments with different decoding strategies, so this remains a reasoned design choice rather than an empirically validated one.

**Why 75K training examples?** The paper does not provide a direct justification for the dataset size, but it can be inferred from the seed selection: 80K seeds were collected based on the language distribution, reduced to ~75K after cleaning. No ablation studies vary the dataset size (e.g., 25K, 50K, 100K), so the optimality of 75K is untested. In principle, larger datasets from more seeds (starcoderdata contains billions of lines) would be possible, suggesting 75K is a practical budget constraint rather than a saturation point.

**Why retain noisy/incomplete solutions?** The empirical result in Table 10 shows a small but positive effect (55.5% vs. 54.9% on HumanEval+). The theoretical justification follows Honovich et al. (2023): instruction tuning benefits from data quantity as much as quality, and even incomplete code contains useful token-level patterns (API calls, variable naming conventions, control flow structures) that the model can learn from. Filtering aggressively risks discarding valid training signal. The paper does not explore more sophisticated filtering (e.g., based on solution executability or test-case validation), leaving open the question of whether a quality-filtered subset would outperform the full noisy set.

**Why 2 epochs?** Two epochs is a common default in instruction tuning when working with synthetic data of moderate size and a pre-trained base model. Training for only 1 epoch risks underfitting (especially with a dataset that contains substantial diversity, as OSS-INSTRUCT does), while training for many epochs risks overfitting to the specific distribution of synthetic problems at the expense of the base model's general coding knowledge. The paper does not report validation curves or epoch ablations, so 2 epochs is presented as a fixed protocol rather than an optimized choice.

**Why 40K Python + 5K × 8 other languages?** The 50:50 Python-to-non-Python ratio reflects a pragmatic bet on evaluation relevance. All primary benchmarks (HumanEval, MBPP, DS-1000) are Python-only, so heavy Python representation in training is natural. However, the paper shows in Section 4.1 (Table 5) that the multilingual data contributes meaningfully: when trained only on the ~32K non-Python examples, Magicoder-CL still sees a 10.4 percentage point improvement on HumanEval+ over the base model (44.5% vs. 34.1%). This inter-language transfer suggests that even non-Python training data teaches general programming concepts (algorithmic thinking, code structure, error handling patterns) that transfer across languages.

**Why start from a pre-trained base model rather than training from scratch?** This is standard in the instruction-tuning paradigm and is not unique to Magicoder. The base model (CODELLAMA-PYTHON-7B) has already internalized fundamental syntax, semantics, and common coding patterns from pre-training on hundreds of billions of tokens. OSS-INSTRUCT's 75K examples represent a tiny fraction of this pre-training volume — they cannot teach the model what Python is or how programming works. Instead, they teach the model to **follow instructions in a code generation context**: to interpret a natural language problem description, to produce well-structured solutions, and to handle the diversity of real-world programming scenarios that the pre-training data may have underrepresented.

**Why not use a more powerful teacher?** The paper uses `gpt-3.5-turbo-1106` primarily for cost-effectiveness ("due to its high cost-effectiveness," Appendix B.1). Generating 80K problem-solution pairs with GPT-4 would have been significantly more expensive. The Section 4.3 experiment with Mixtral-8x7B-Instruct-v0.1 as the teacher (a weaker, open-source model) demonstrates that even a non-frontier teacher can produce effective OSS-INSTRUCT data — Magicoder-CL-Mixtral-7B outperforms its own instructor on HumanEval+ (55.5% vs. 39.6%, Table 7). This finding is significant because it shows OSS-INSTRUCT is **not merely distilling the teacher model's capability**; the seed-driven generation process triggers latent capabilities in the *student* model that exceed the teacher's own coding ability. The teacher's role is as a *catalyst* — it translates code snippets into instruction format, but the actual capability gain comes from the student model learning from the diverse *content* of the generated problems, not from mimicking the teacher's solution quality.

**Why not directly fine-tune on open-source code?** This is the central counterfactual design choice. Section 4.2 (Table 6) demonstrates that fine-tuning on comment-function pairs extracted from the same seed documents **worsened** performance: HumanEval+ dropped from 34.1% (base model) to 34.1% (flat), and MultiPL-E dropped from 29.6% to 24.1% — a substantial regression on multilingual code generation. The degradation is attributed to "substantial noise and inconsistency that exists intrinsically in the data pairs" — real-world code comments are often ambiguous, incomplete, or written in non-English languages, and the corresponding code often handles edge cases, internal logic, and implementation details that distract from the core algorithmic lesson. OSS-INSTRUCT transforms this noisy signal into a clean one: the teacher LLM extracts the semantic essence of the code and expresses it as a coherent, self-contained problem, filtering out implementation-specific noise and re-expressing the concept in a pedagogically useful form. This is fundamentally a **denoising and restructuring** operation on the open-source code signal.

## 4. Key Insights and Innovations

### Innovation 1: External Seed-Driven Data Generation as a Debiasing Mechanism

The paper's deepest conceptual move is reframing synthetic data generation from an *introspective* process (the LLM draws on its own parametric knowledge) to an *extrospective* one (the LLM interprets external, real-world artifacts). This is not an incremental tweak to existing methods — it is a fundamental shift in where diversity comes from.

Prior work in code instruction tuning — SELF-INSTRUCT (Wang et al., 2023a), Code Alpaca (Chaudhary, 2023), and Evol-Instruct (Luo et al., 2023b) — all operate on the same core assumption: a sufficiently capable LLM can generate diverse training data by creative recombination of its internal knowledge, guided by seed tasks or heuristics. The limiting factor in these methods is the **seed description space**: Code Alpaca's 21 seed tasks define a tiny region of possible problems, and Evol-Instruct's 5 heuristics can only complexity-varying transformations within that region. No matter how cleverly the LLM recombines, it cannot generate a problem about controlling electric motors via reinforcement learning unless that concept is explicitly seeded or emerges from its pretraining distribution — and if it emerges from pretraining, it reflects the biases and gaps of that distribution.

OSS-INSTRUCT breaks this assumption by recognizing that the **inspiration space** needs to be as large as the space of possible programs, and the only thing that approximates that space is the actual corpus of human-written code. The 1–15 line random snippet extraction is the mechanism, but the *insight* is that partial, decontextualized code fragments serve as **unbiased probes** into programming concepts the LLM would never spontaneously enumerate. A single import of `gym_electric_motor` doesn't trigger the LLM's "common coding problem" template — it forces the LLM to interpret an *unfamiliar* signal and construct a coherent problem around it. This is fundamentally different from asking the LLM to "create a machine learning problem," which predictably produces MNIST classifiers and linear regressions.

The quantitative evidence for this debiasing effect is Figure 3: OSS-INSTRUCT data exhibits the **lowest average cosine similarity to HumanEval** (0.105) compared to SELF-INSTRUCT (0.169) and Evol-Instruct (0.131). This is not just a "diversity win" — it is evidence that the data generation process is not **overfitting to the benchmark distribution**. The fact that only 9 samples were filtered by decontamination (Section 2.2) further supports the claim: the teacher LLM is not memorizing and reproducing HumanEval-like problems. It is genuinely generating novel problems from external inspiration.

The significance of this reframing extends beyond code generation. Any domain where synthetic data generation risks collapsing into a narrow distribution of "what the LLM thinks is typical" — mathematical reasoning, scientific question answering, creative writing — could benefit from external seed-driven generation. The paper opens a research direction where the question is not "how do we write better prompts to elicit diversity from the LLM" but "what external corpus provides the right kind of uncontrolled variation to break the LLM's default priors."

---

### Innovation 2: The Teacher as Translator, Not Oracle

A second conceptual shift — and one that the paper explicitly validates — is that the teacher LLM's role in OSS-INSTRUCT is not to provide *correct answers* that the student imitates, but to **translate unstructured code fragments into a pedagogically useful format**. The student model's capability gain comes primarily from the *content diversity* of the translated problems, not from distilling the teacher's specific solution style or correctness.

This is a sharp departure from standard knowledge distillation in code LLMs. In the Code Alpaca and WizardCoder paradigms, the teacher model (ChatGPT or GPT-4) generates both problems and solutions, and the student learns by mimicking those solutions. The implicit assumption is that the teacher is an oracle — it produces higher-quality code than the student can, and the student improves by learning to replicate that quality. If this assumption holds, then using a *weaker* teacher should produce *weaker* student models.

Section 4.3 (Table 7) falsifies this assumption in the OSS-INSTRUCT context. When the teacher is **Mixtral-8x7B-Instruct-v0.1** — a model that scores only 39.6% pass@1 on HumanEval+ and 47.4% on MBPP+ — the resulting Magicoder-CL-Mixtral-7B achieves **55.5% on HumanEval+ and 50.4% on MBPP+**, substantially outperforming its own teacher. The student is not learning to code like the teacher; it is learning from the *conceptual content* of the problems the teacher generated, and then deploying its own (superior) coding ability to solve them during inference.

This finding reframes what "instruction tuning" accomplishes. Rather than being a distillation process where capability flows from teacher to student, it is better understood as a **capability activation** process: the diverse instruction data teaches the student *how to map natural language instructions to its latent coding knowledge*, and the quality of that mapping depends more on the diversity and realism of the instructions than on the quality of the embedded solutions. The 75K OSS-INSTRUCT examples are effective not because GPT-3.5 Turbo writes brilliant code (it doesn't, compared to GPT-4 or DeepSeek-Coder), but because the *problems* span a vast range of programming scenarios that force the student model to exercise capabilities it already possesses but cannot reliably access without appropriate prompting.

The practical implication is significant: OSS-INSTRUCT can be run with weaker, cheaper, or open-source teacher models without sacrificing downstream performance. This democratizes the data generation process — organizations without API access to GPT-4 can still produce effective instruction-tuning data, as long as the teacher is capable of the *translation* task (interpreting code fragments) even if it is mediocre at the *solution* task.

---

### Innovation 3: Synthetic Data as a Denoising Operator on Raw Code

Section 4.2 confronts the most natural objection to OSS-INSTRUCT: if open-source code is so valuable, why not fine-tune directly on it? The experimental result — that comment-function pair fine-tuning **actually degrades performance** (Table 6: MultiPL-E drops from 29.6 to 24.1) — is not just an ablation; it is a diagnostic finding about the nature of effective training data for code models.

The degradation reveals that **format matters less than semantic coherence**. Comment-function pairs extracted from real repositories share the same surface structure as HumanEval or OSS-INSTRUCT problems (a natural language description followed by code), yet they harm performance. The paper attributes this to "substantial noise and inconsistency" — real code comments are fragmentary, assume shared context, reference internal APIs, and often describe *what* the code does in implementation terms rather than *what problem* it solves. The model trained on these pairs learns to associate ambiguous comments with implementation details rather than learning generalizable instruction-following.

OSS-INSTRUCT's value proposition is therefore not "open-source code is useful training data" but rather **"open-source code filtered through an LLM interpreter becomes useful training data."** The teacher LLM performs a semantic transformation that extracts the *conceptual core* of a code fragment (the algorithmic idea, the library usage pattern, the data structure relationship) and re-expresses it as a self-contained, pedagogically clear problem. This is a denoising operation: the teacher strips away implementation-specific noise (error handling boilerplate, logging statements, internal variable names) and preserves the transferable programming concept.

This positions synthetic data generation as a **signal processing problem** rather than a data scaling problem. The bottleneck is not the volume of source material (starcoderdata contains billions of lines), but the fidelity of the transformation from raw code to clean training example. This suggests future research directions around improving the *translation quality* — better prompts, multi-step refinement, or automated quality filtering — rather than simply generating more data.

The finding also explains why prior attempts at "documentation-guided" code generation (fine-tuning on raw docstrings) have had mixed results: the noise in real documentation swamps the signal unless an intermediate curation step (which OSS-INSTRUCT automates) is applied.

---

### Innovation 4: Orthogonality of Breadth-Oriented and Depth-Oriented Data Augmentation

The MagicoderS result — where sequential training on OSS-INSTRUCT (breadth via external seeds) followed by Evol-Instruct (depth via heuristic rewriting) produces a 10.3 percentage point improvement over Magicoder-CL on HumanEval (Table 1) — is not merely an ensemble trick. It demonstrates that data augmentation methods operating on **different axes of variation** can be **composed without interference**.

This is not an obvious property. One could imagine that the complexity-increasing heuristics of Evol-Instruct would be redundant when applied to problems that are already diverse (since diversity and complexity might be correlated), or that the two data distributions would conflict during sequential training (the model might forget OSS-INSTRUCT patterns when adapting to Evol-Instruct patterns). The strong positive result suggests otherwise: the two methods contribute complementary signals that the model can integrate.

The conceptual contribution here is a **taxonomy of data augmentation axes** for instruction tuning. OSS-INSTRUCT operates on the **topic axis** — *what* the problem is about (reinforcement learning vs. banking systems vs. file processing). Evol-Instruct operates on the **complexity axis** — *how demanding* the problem is (adding constraints, requiring deeper reasoning, concretizing vague specs). These axes are independent in principle: any topic can be made arbitrarily complex, and any complexity level can apply to any topic. The sequential training procedure effectively teaches the model first to handle a wide range of topics at moderate complexity, then to handle high complexity across that range.

This taxonomy is a useful intellectual tool for designing future data generation pipelines. Rather than asking "what method produces the best data," researchers can ask "which axes of variation are we covering, and which are we neglecting?" The paper's success with only two orthogonal methods suggests that **additional orthogonal axes** — perhaps *interactivity* (multi-turn problem-solving), *correctness* (problems with explicit test cases), or *domain specificity* (problems from scientific computing, web development, systems programming) — could be combined for further gains. The framework of orthogonal composability, rather than any single data generation trick, is the reusable insight.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The evaluation spans multiple benchmarks. For Python text-to-code generation, the paper uses **HumanEval** (Chen et al., 2021; 164 hand-written programming problems) and **MBPP** (Austin et al., 2021; ~1,000 crowd-sourced programming tasks), both augmented by the **EvalPlus framework** (Liu et al., 2023b) to produce HumanEval+ (80× more tests) and MBPP+ (35× more tests) for more rigorous evaluation. For multilingual code generation, **MultiPL-E** (Cassano et al., 2022) extends HumanEval to 18 programming languages; the paper evaluates on Java, JavaScript, C++, PHP, Swift, and Rust. For data science problems, **DS-1000** (Lai et al., 2022) provides 1,000 problems across 7 Python libraries (Matplotlib, NumPy, Pandas, PyTorch, SciPy, Scikit-learn, TensorFlow) with unit tests for validation. An additional evaluation on **APPS** (Hendrycks et al., 2021) uses a 300-problem subset (60 introductory, 180 interview, 60 competition) following Olausson et al. (2024). All evaluations use the respective benchmarks' standard test splits.

- **Base model(s).** The primary base model is **CODELLAMA-PYTHON-7B** (Rozière et al., 2023), a 7-billion parameter decoder-only transformer pre-trained on code and natural language with specialized Python training. The paper also applies the same fine-tuning recipe to **DeepSeek-Coder-Base-6.7B** (Guo et al., 2024), producing Magicoder-DS and MagicoderS-DS variants. The 7B scale was chosen for practical fine-tuning feasibility (2 GPUs) while providing meaningful headroom for improvement (base pass@1 on HumanEval is only 37.8%).

- **Metrics.** The primary metric throughout is **pass@1** — the probability that a single generated sample passes all test cases — computed using **greedy decoding** (temperature = 0) for HumanEval(+) and MBPP(+) to ensure deterministic, reproducible evaluation. For MultiPL-E and DS-1000, following the WizardCoder paper (Luo et al., 2023b), pass@1 is estimated from 50 and 40 samples respectively with temperature = 0.2 and top-p = 0.95 (for MultiPL-E) or 0.5 (for DS-1000). The EvalPlus framework (Liu et al., 2023b) is used to report results consistently across models, with all comparisons drawn from the EvalPlus leaderboard (hash: 1895d2f).

- **Baselines.** The paper compares against a comprehensive set of open-source and closed-source models at various scales. At 34B parameters: **CODELLAMA-PYTHON-34B** (Rozière et al., 2023) and **WizardCoder-CL-34B** (Luo et al., 2023b). At 15–16B: **StarCoder-15B** (Li et al., 2023), **WizardCoder-SC-15B** (Luo et al., 2023b), **CodeT5+-16B** (Wang et al., 2023b), and **CodeGen-Mono-16B** (Nijkamp et al., 2023). At 6–7B: **StarCoder-7B**, **Mistral-7B** (Jiang et al., 2023a), **CodeT5+-6B**, **CodeGen-Mono-6B**, **CODELLAMA-PYTHON-7B** (the base model), and **WizardCoder-CL-7B**. Closed-source baselines include **GPT-3.5 Turbo** (Nov 2023) and **GPT-4 Turbo** (Nov 2023). For DS-1000, additional baselines include **INCODER-6.7B** (Fried et al., 2023) and **Code-Cushman-001** (Microsoft, 2023a). For the DeepSeek-Coder comparison, **DeepSeek-Coder-Base-6.7B**, **DeepSeek-Coder-Instruct-6.7B**, and **DeepSeek-Coder-Instruct-33B** serve as baselines.

- **Generation budget / compute accounting.** Since this is a data-centric paper comparing models trained with different data generation methods, there is no test-time compute budget analysis (unlike the scaling laws paper in the reference example). The "budget" concept applies to training data volume rather than inference compute: Magicoder-CL uses 75K OSS-INSTRUCT examples, MagicoderS-CL adds 110K Evol-Instruct examples, and comparisons are made against models trained on different instruction-tuning datasets (Code Alpaca's 20K, evol-codealpaca-v1's 110K). The DeepSeek-Coder comparison in Table 4 explicitly reports training tokens to account for data volume: Magicoder-DS uses +90M tokens (75K examples × ~1,200 tokens), MagicoderS-DS uses +240M tokens, while DeepSeek-Coder-Instruct-6.7B uses +2B tokens (8× more).

- **Cross-validation / statistical protocol.** The paper does not employ cross-validation or report confidence intervals. All results are single-run evaluations with deterministic greedy decoding for the primary benchmarks (HumanEval+, MBPP+). For MultiPL-E and DS-1000, multiple samples are drawn (40 or 50) to estimate pass@1, providing more stable estimates, but no variance estimates or statistical tests are reported. The decontamination procedure (Section 2.2) serves as the main safeguard against data leakage, removing benchmark contents from training data via exact string matching.

### Main Quantitative Results

#### Python Text-to-Code Generation (HumanEval+ and MBPP+)

Table 1 presents the central head-to-head results. **Magicoder-CL-7B achieves 60.4% pass@1 on HumanEval and 55.5% on HumanEval+**, representing a 22.6 percentage point improvement over the CODELLAMA-PYTHON-7B base (37.8% → 60.4%) and a 12.2 percentage point improvement over WizardCoder-CL-7B (48.2% → 60.4%) on the standard benchmark. On the more rigorous HumanEval+, the gap over WizardCoder-CL-7B is even larger: 55.5% vs. 40.9% — a 14.6 percentage point advantage.

On MBPP, Magicoder-CL-7B scores 64.2% (52.6% on MBPP+), improving over CODELLAMA-PYTHON-7B's 57.6% (45.4%) and WizardCoder-CL-7B's 56.6% (47.1%). Notably, Magicoder-CL-7B outperforms **all models at or below 16B parameters** on every benchmark variant, including the 15B WizardCoder-SC (51.9%/45.1% on HumanEval/HumanEval+) and the 34B CODELLAMA-PYTHON (42.7%/36.6%).

**MagicoderS-CL-7B pushes further to 70.7% on HumanEval and 66.5% on HumanEval+**, representing a 10.3 percentage point gain over Magicoder-CL on the standard benchmark. The HumanEval+ result (66.5%) surpasses ChatGPT's 65.9%, meaning MagicoderS-CL-7B — a 7B parameter open-source model — generates more robust code (as measured by the augmented test suite) than the proprietary GPT-3.5 Turbo. MagicoderS-CL-7B also overtakes WizardCoder-CL-34B on HumanEval+ (66.5% vs. 64.6%) while being roughly 5× smaller. On MBPP+, MagicoderS-CL-7B scores 56.6%, improving over the 15B WizardCoder-SC's 52.6%.

**Comparison hierarchy (from Table 1):** MagicoderS-CL-7B > Magicoder-CL-7B > CODELLAMA-PYTHON-34B > WizardCoder-SC-15B > WizardCoder-CL-7B > CODELLAMA-PYTHON-7B, with the 7B MagicoderS-CL competitive with or exceeding the 34B models across all four benchmark variants.

#### Multilingual Code Generation (MultiPL-E)

Table 2 reports pass@1 across 6 non-Python languages. **Magicoder-CL-7B improves over CODELLAMA-PYTHON-7B by 6.3 to 10.2 percentage points** across languages: Java (29.1 → 36.4), JavaScript (35.7 → 45.9), C++ (30.2 → 36.5), PHP (29.0 → 39.5), Swift (27.1 → 33.4), and Rust (27.0 → 30.6). The average improvement across all 6 languages is 8.2 percentage points.

Against the 15B WizardCoder-SC, Magicoder-CL-7B achieves higher pass@1 on **3 of 6 languages** (JavaScript: 45.9 vs. 41.9; PHP: 39.5 vs. 39.3; Rust: 30.6 vs. 27.1) and comparable results on the others, despite being less than half the size. The 34B WizardCoder-CL maintains an advantage on Java (44.9 vs. 36.4) and C++ (47.2 vs. 36.5).

**MagicoderS-CL-7B shows gains across all languages:** Java (36.4 → 42.9), JavaScript (45.9 → 57.5), C++ (36.5 → 44.4), PHP (39.5 → 47.6), Swift (33.4 → 44.1), and Rust (30.6 → 40.3). At 7B parameters, MagicoderS-CL-7B is competitive with or exceeds the 34B WizardCoder-CL on several languages: JavaScript (57.5 vs. 55.3), PHP (47.6 vs. 47.2), and Swift (44.1 vs. 44.3). The improvement over the base model is most dramatic on Swift (27.1 → 44.1, +17 points) and JavaScript (35.7 → 57.5, +21.8 points).

A notable observation: Magicoder-CL was trained on only ~32K non-Python examples (from the multilingual seed snippets), yet the improvements transfer broadly across languages. The paper notes that "although the harness evaluates models in completion formats which are for base models, Magicoders still show significant improvements despite being only instruction-tuned. This implies that LLMs can learn knowledge from the data beyond its format."

#### Code Generation for Data Science (DS-1000)

Table 3 shows DS-1000 results (completion format). **Magicoder-CL-7B achieves 29.9% overall pass@1**, outperforming WizardCoder-CL-7B (28.4%), WizardCoder-SC-15B (29.2%), and CODELLAMA-PYTHON-7B (28.0%). The gains are library-specific: notable improvements over WizardCoder-SC-15B appear in Pandas (19.0% vs. 16.7%) and TensorFlow (28.9% vs. 26.7%).

**MagicoderS-CL-7B achieves 37.5% overall**, representing an 8.3 percentage point absolute gain over WizardCoder-SC-15B (29.2%) and an 8.3 percentage point gain over Magicoder-CL. The improvements are particularly pronounced on library-specific tasks: PyTorch (40.4% vs. WizardCoder-SC's 26.2%, +14.2 points), Pandas (28.4% vs. 16.7%, +11.7 points), Scikit-learn (35.8% vs. 24.9%, +10.9 points), and SciPy (28.8% vs. 24.2%, +4.6 points). This suggests that the combination of OSS-INSTRUCT (providing diverse library-usage patterns) and Evol-Instruct (adding complexity) particularly benefits data-science workflows that require multi-step reasoning with specific APIs.

#### Comparison with DeepSeek-Coder

Table 4 compares Magicoder-DS and MagicoderS-DS against the DeepSeek-Coder family. **Magicoder-DS-6.7B (trained on +90M OSS-INSTRUCT tokens) achieves 66.5% on HumanEval and 60.4% on HumanEval+**, substantially improving over DeepSeek-Coder-Base-6.7B (47.6%/39.6%) and approaching DeepSeek-Coder-Instruct-6.7B (73.8%/70.1%), which was instruction-tuned on **+2B tokens (22× more than the OSS-INSTRUCT stage)**. On MBPP+, Magicoder-DS reaches 61.9%, exceeding the base model's 56.6%.

**MagicoderS-DS-6.7B (combined OSS-INSTRUCT + Evol-Instruct, +240M total tokens) reaches 76.8% on HumanEval and 70.7% on HumanEval+**, surpassing DeepSeek-Coder-Instruct-6.7B (73.8%/70.1%) on HumanEval but slightly trailing on HumanEval+. On MBPP+, MagicoderS-DS achieves 64.4% vs. DeepSeek-Coder-Instruct-6.7B's 63.4%. Crucially, MagicoderS-DS matches or exceeds DeepSeek-Coder-Instruct-33B on HumanEval+ (70.7% vs. 72.6%) and MBPP+ (64.4% vs. 66.7%) while using **only ~12% of the instruction-tuning tokens** (240M vs. 2B) and with roughly 5× fewer parameters.

**Key takeaway:** The OSS-INSTRUCT data generation method transfers effectively across base model families, and the gains are not merely a function of the base model's strength — MagicoderS-DS substantially outperforms DeepSeek-Coder-Instruct-6.7B on HumanEval with 8× fewer fine-tuning tokens, suggesting that data *quality and diversity* (via OSS-INSTRUCT) can substitute for data *quantity*.

### Ablation Studies and Robustness Checks

**Impact of language distribution (Table 5):** When CODELLAMA-PYTHON-7B is fine-tuned on only the ~43K Python-targeted OSS-INSTRUCT examples, HumanEval+ reaches 47.6% (up from 34.1% base) but MultiPL-E only improves to 32.7% (up from 29.6%). When fine-tuned on only the ~32K non-Python examples, HumanEval+ still improves to 44.5% (+10.4 points) and MultiPL-E reaches 38.3% (+8.7 points). The combined 75K dataset achieves 55.5% on HumanEval+ and 37.8% on MultiPL-E. The finding that non-Python data boosts Python performance (+10.4 points) demonstrates inter-language transfer of general coding concepts, while the slight MultiPL-E decrease from 38.3% (non-Python only) to 37.8% (combined) is attributed to "the dominant amount of Python data (around 57%) during instruction tuning" diluting the multilingual signal.

**OSS-INSTRUCT vs. direct fine-tuning on open-source code (Table 6):** Fine-tuning on 75K comment-function pairs extracted from the same seed corpus produced flat HumanEval+ performance (34.1% — identical to the unfine-tuned base model) and degraded MultiPL-E performance (24.1% vs. 29.6% base, a 5.5-point regression). The paper attributes this degradation to "substantial noise and inconsistency that exists intrinsically in the data pairs" — even though the pairs share surface format similarity with HumanEval, the semantic noise in real-world code comments undermines learning. This result is critical because it demonstrates that the OSS-INSTRUCT transformation step (code → coherent problem-solution pair via LLM interpretation) is not merely beneficial but **necessary** — raw open-source code in a superficially instruction-like format actively harms performance.

**OSS-INSTRUCT with a weaker teacher model (Table 7):** When 20K OSS-INSTRUCT examples are generated using **Mixtral-8x7B-Instruct-v0.1** (which scores only 39.6% on HumanEval+ and 47.4% on MBPP+) as the teacher, the resulting Magicoder-CL-Mixtral-7B achieves **55.5% on HumanEval+ and 50.4% on MBPP+** after fine-tuning CODELLAMA-PYTHON-7B for 2 epochs. This student model substantially outperforms its own teacher across both benchmarks, demonstrating that OSS-INSTRUCT is "not simply distilling a teacher model, but also triggering the base model's own capability and effectively leveraging the information encapsulated in seed code snippets." The teacher's role is to translate code fragments into instruction format; the student's coding capability comes from its pre-training, activated by the diverse problem distribution.

**Impact of removing noisy data (Table 10, Appendix C.3):** Removing Python samples containing `pass` or `NotImplemented` tokens (indicating incomplete/stub implementations) reduces the dataset from 75K to 68K entries. The resulting model achieves **54.9% on HumanEval+** vs. **55.5% with the noisy data retained** — a small 0.6 percentage point difference that supports the paper's decision to retain imperfect samples. The finding aligns with Honovich et al. (2023)'s observation that even noisy synthetic data contains useful signal for instruction tuning.

**Data decontamination analysis (Section 2.2):** Only 9 out of 75K OSS-INSTRUCT samples were filtered by benchmark decontamination (matching HumanEval, MBPP, APPS, DS-1000, or GSM8K content). Combined with the starcoderdata corpus's pre-existing decontamination, this extremely low contamination rate supports the claim that OSS-INSTRUCT does not introduce data leakage — the teacher LLM generates genuinely novel problems rather than memorizing benchmark tasks. For comparison, the Evol-Instruct dataset required filtering 89 samples out of ~110K, a roughly 6× higher contamination rate despite being only 1.5× larger.

**Cosine similarity analysis (Figure 3):** Using TF-IDF embeddings and pairwise cosine similarity to HumanEval problems, OSS-INSTRUCT data shows the lowest average similarity (0.105) compared to SELF-INSTRUCT (0.169) and Evol-Instruct (0.131). This quantitative diversity metric supports the qualitative observation that seed-driven generation produces problems less concentrated around benchmark-like distributions, partially ruling out the hypothesis that Magicoder's gains come from training on inadvertently HumanEval-similar data.

**Category distribution and length analysis (Figures 6, 7, Appendix A.3):** The OSS-INSTRUCT dataset spans 10 manually defined coding categories (classified via INSTRUCTOR embeddings), showing "diversity and balance" across categories. Token length distributions for problems and solutions both span roughly 50–700+ tokens with peaks at 100–300 tokens, indicating wide natural variation driven by seed snippet diversity rather than manual curation.

### Critical Assessment

**Claim 1: OSS-INSTRUCT generates more diverse, realistic, and controllable instruction data.** The diversity claim is supported by the cosine similarity analysis (Figure 3: OSS-INSTRUCT at 0.105 vs. SELF-INSTRUCT at 0.169), the low decontamination count (9 samples), and the qualitative breadth demonstrated in Figures 2 and 5 (spanning shell scripts, library imports, class signatures, and code statements). However, "realistic" is demonstrated only qualitatively — there is no quantitative metric for how much OSS-INSTRUCT problems resemble real-world programming tasks. The "controllable" claim is argued but not experimentally demonstrated: the paper does not show that varying the seed language distribution systematically shifts the generated problem distribution in predictable ways (beyond the coarse Table 5 ablation). The claim about controllability is therefore **theoretically motivated but empirically thin** — an experiment showing that increasing Python seed proportion increases Python-problem proportion in the output would have strengthened this substantially.

**Claim 2: Magicoder substantially improves the base LLM and outperforms SOTA models at similar scales.** This is **strongly supported by Tables 1–4.** Magicoder-CL-7B improves over CODELLAMA-PYTHON-7B by +22.6 percentage points on HumanEval, and outperforms all studied models ≤16B on every benchmark. The results are consistent across five evaluation benchmarks (HumanEval+, MBPP+, MultiPL-E, DS-1000, APPS) and two base model families (CODELLAMA-PYTHON and DeepSeek-Coder). However, the comparison against WizardCoder-CL-7B uses an open-source Evol-Instruct reproduction (`evol-codealpaca-v1`) rather than the proprietary WizardCoder training data, because the official dataset was not released. This means the Magicoder-vs-WizardCoder comparison is **partially confounded by data differences**: MagicoderS-CL benefits from 75K OSS-INSTRUCT + 110K evol-codealpaca-v1, while WizardCoder-CL-7B was trained on the (unreleased) official Evol-Instruct data. The 14.6-point gap on HumanEval+ is convincing, but the precise attribution to OSS-INSTRUCT vs. different implementations of Evol-Instruct is ambiguous.

**Claim 3: OSS-INSTRUCT is orthogonal to Evol-Instruct, and combining them yields further gains.** Supported by the MagicoderS results (Table 1: +10.3 points on HumanEval and +11 points on HumanEval+ over Magicoder-CL). However, the "orthogonality" claim is tested only indirectly: the paper demonstrates that sequential training on both datasets outperforms either alone, but does not compare against alternatives like training on a larger OSS-INSTRUCT-only dataset (e.g., 185K samples) or an Evol-Instruct-only dataset applied to the base model without the OSS-INSTRUCT pre-training. Without these baselines, the claim that the methods are *orthogonal and composable* specifically (as opposed to "more diverse data is better") is **supported in outcome but not in mechanism**. The paper would be stronger with an experiment showing that OSS-INSTRUCT + Evol-Instruct outperforms an equivalent volume of Evol-Instruct-only data, which would isolate the complementary benefit.

**Claim 4: OSS-INSTRUCT triggers the base model's latent capabilities beyond teacher distillation.** The Mixtral experiment (Table 7) is the key evidence: Magicoder-CL-Mixtral-7B outperforms its own teacher (Mixtral-8x7B-Instruct) on HumanEval+ (55.5% vs. 39.6%) and MBPP+ (50.4% vs. 47.4%). This is a clean and compelling result — the student strongly surpasses the teacher, falsifying the hypothesis that Magicoder's gains are purely teacher distillation. However, the experiment uses only 20K examples (not the full 75K), and the comparison is against the Mixtral teacher's zero-shot performance rather than its performance when similarly fine-tuned on OSS-INSTRUCT data (which is impossible, as the teacher is the generator, not the student). The result demonstrates that the *content* of OSS-INSTRUCT data matters more than the teacher's *capability*, but does not fully characterize the relationship.

**Claim 5: Direct fine-tuning on open-source code is inferior to OSS-INSTRUCT.** Strongly supported by Table 6, where comment-function pair fine-tuning on 75K samples from the same seed corpus degrades MultiPL-E to 24.1% (below the 29.6% base) and leaves HumanEval+ unchanged at 34.1%. This is a clean negative result that strongly motivates the need for the OSS-INSTRUCT transformation. However, the paper does not ablate whether a different method of extracting training pairs from open-source code (e.g., using LLM-summarized docstrings, filtering for high-quality comments, using entire functions rather than comment-function pairs) would similarly fail or partially succeed. The conclusion that "OSS-INSTRUCT specifically works where raw code fine-tuning fails" is supported; the stronger claim that "no direct fine-tuning approach could work" is not tested.

**Genuine Weaknesses:**

- **No validation curve or epoch ablation:** The paper fixes training at 2 epochs without reporting whether this is the optimal checkpoint or whether overfitting occurs at later epochs. Given the 75K dataset and a 512 batch size, the model sees only ~293 update steps, which may be insufficient to saturate learning — a 4-epoch run might yield further gains, but this is unexplored.

- **No dataset size scaling study:** There is no experiment varying the number of OSS-INSTRUCT examples (e.g., 25K, 50K, 75K, 150K). The 75K size was determined by the initial 80K seed budget, not by saturation analysis. It is unknown whether Magicoder's performance would continue to improve with more data or has plateaued.

- **No teacher model comparison within OSS-INSTRUCT:** The Mixtral experiment shows OSS-INSTRUCT works with a weaker teacher, but there is no head-to-head comparison of different teacher models (GPT-3.5 vs. GPT-4 vs. Mixtral vs. others) on the same seed set to quantify how teacher quality affects downstream performance. The GPT-3.5 → GPT-4 gap could be substantial given GPT-4's stronger code generation capabilities.

- **Single seed corpus:** All experiments use `starcoderdata`. It is unknown whether OSS-INSTRUCT would work equally well with other open-source code corpora (e.g., GitHub repository-level data, Stack Overflow snippets, code from specific domains like scientific computing) or whether `starcoderdata`'s specific filtering (permissive licenses, decontamination) is partially responsible for the results.

- **No human evaluation of data quality:** The diversity metrics (cosine similarity, category distribution, length distribution) are all automated. The paper provides qualitative examples (Figures 2, 5) but no systematic human assessment of whether OSS-INSTRUCT-generated problems are well-posed, realistic, or correctly solved.

- **The "controllability" claim is underexplored:** The paper states that OSS-INSTRUCT enables "controllable" data generation, but the only control experiment is the coarse language split in Table 5. Controllability over problem difficulty, topic domain, or coding paradigm is not demonstrated. This weakens the practical utility claim — a user wanting to generate SQL-specific problems, for instance, receives no guidance from these experiments.

**Missing experiments that would strengthen the paper:**

1. A **dataset scaling curve** (10K, 25K, 50K, 75K, 150K OSS-INSTRUCT examples) to characterize the relationship between data volume and downstream performance.
2. A **teacher model ablation** comparing GPT-3.5, GPT-4, and Mixtral on the identical seed set to measure how teacher quality affects student performance.
3. An **OSS-INSTRUCT-only scaling** experiment that compares 75K OSS-INSTRUCT against 185K OSS-INSTRUCT (matching the combined OSS-INSTRUCT + Evol-Instruct volume) to isolate whether the MagicoderS gains are from additional data volume or specifically from the orthogonal Evol-Instruct signal.
4. **Confidence intervals** for all pass@1 estimates, particularly for MultiPL-E and DS-1000 where results are based on 40–50 samples per problem and statistical noise could meaningfully affect rankings.
5. A **failure analysis** examining cases where Magicoder underperforms the base model or baselines — all reported results are aggregate improvements, but understanding the pattern of failures would help characterize the method's limitations.

**Conditional validity of claims:**

- The claim that Magicoder "outperforms all studied LLMs with less than or equal to 16B parameters" is **time-bound**: it is true as of the December 2023 evaluation, but the rapidly evolving landscape of code LLMs means this is a moving target. The concurrent DeepSeek-Coder results already challenge this framing (DeepSeek-Coder-Instruct-6.7B initially leads on some metrics before MagicoderS is applied to the same base).
- The claim that MagicoderS-CL-7B "surpasses the prominent ChatGPT on HumanEval+" (66.5% vs. 65.9%) is **specific to the November 2023 GPT-3.5 Turbo snapshot** and should be interpreted cautiously — API model performance evolves, and the margin (0.6 percentage points) is small enough that it could flip with a different evaluation run or minor benchmark variation.
- The "orthogonality" of OSS-INSTRUCT and Evol-Instruct is demonstrated only for the specific combination and ordering used (OSS-INSTRUCT first, then Evol-Instruct). Whether the reverse ordering or simultaneous training would work similarly is unknown.

## 6. Limitations and Trade-offs

### Limitation 1: The Data Generation Pipeline Depends on a Proprietary Teacher Model

**The assumption or constraint.** OSS-INSTRUCT requires a capable instruction-following LLM to serve as the teacher that translates raw code snippets into coherent problem-solution pairs. The primary experiments use **GPT-3.5 Turbo (`gpt-3.5-turbo-1106`)** — a closed-source, proprietary model whose behavior, availability, and pricing are controlled by a third party. The paper acknowledges this dependency implicitly through its choice of teacher, but does not frame it as a limitation. The 75K-example dataset was generated through paid API calls, and the quality of the output depends on GPT-3.5 Turbo's specific capabilities at the time of generation (November 2023). API model updates, deprecations, or pricing changes could make the exact dataset unreproducible.

**The consequence.** A practitioner attempting to replicate Magicoder or apply OSS-INSTRUCT to a new domain faces a **reproducibility and cost barrier**. The total API cost for generating 80K problem-solution pairs is not reported, but at standard GPT-3.5 Turbo pricing (~$0.001-0.002 per request), it likely amounts to $80-160 for generation alone — a non-trivial expense for academic labs or individual researchers. More critically, the dataset cannot be exactly reproduced if the specific `gpt-3.5-turbo-1106` model snapshot is deprecated, because different GPT-3.5 versions produce different outputs from identical prompts. This makes OSS-INSTRUCT-generated datasets **version-locked** to a specific, ephemeral API endpoint. For organizations with restrictions on sending code to external APIs (common in enterprise settings), using GPT-3.5 Turbo as the teacher is entirely infeasible, and the paper provides no guidance on minimum teacher capability requirements.

**What evidence exists in the paper.** Section 4.3 provides the only relevant ablation: generating a 20K subset using **Mixtral-8x7B-Instruct-v0.1**, an open-source model. The resulting Magicoder-CL-Mixtral-7B achieves 55.5% on HumanEval+ (Table 7), matching the full Magicoder-CL's 55.5% on the same benchmark — but this comparison is confounded by the different dataset size (20K vs. 75K) and by evaluation on different problem subsets (HumanEval+ includes all 164 problems, but the 20K model was trained on 27% of the data volume). No head-to-head comparison of different teachers on the same seed set at the same data volume exists. Without this experiment, the paper provides **only weak evidence** that open-source teachers can substitute for GPT-3.5 without quality loss. The Mixtral result is suggestive but does not close the case.

**Mitigation status.** Partial. The paper releases the generated 75K dataset in full (Appendix B: "We fully open source the model weights, training data, and source code"), which eliminates the need for future practitioners to regenerate it. This is a strong mitigation for exact replication of Magicoder, but it does not address the scenario where OSS-INSTRUCT needs to be applied to a new seed corpus, a new programming language, or a new domain — in those cases, the teacher dependency remains. The Mixtral experiment (Section 4.3) gestures toward open-source alternatives but at insufficient scale to be a validated replacement protocol. The paper states in Section 6: "In the near future, we will apply OSS-INSTRUCT to larger base models. We will also continue advancing OSS-INSTRUCT by generating higher-quality data with a strategically designed distribution of the seed code snippets and with more advanced teacher LLMs such as GPT-4," which suggests the authors view stronger proprietary teachers as the path forward rather than open-source alternatives.

---

### Limitation 2: All Evaluations Are on a Single Task Family (Python Text-to-Code) with Limited Statistical Rigor

**The assumption or constraint.** The paper's headline claims — "MagicoderS-CL-7B surpasses ChatGPT on HumanEval+" and "Magicoder-CL-7B outperforms all studied models ≤16B" — are based on **five Python-centric benchmarks**: HumanEval(+) and MBPP(+) for text-to-code, MultiPL-E for multilingual completion, DS-1000 for data science, and APPS for competitive programming. All of these evaluate generating code from natural language descriptions against test-case-based correctness. The paper does not evaluate on code understanding tasks (code summarization, defect detection, clone detection), repository-level code generation (where context spans multiple files), interactive coding scenarios (multi-turn conversation, iterative refinement), or code generation in non-Python languages beyond MultiPL-E's completion format. Section 5 ("Related Work") catalogs many of these alternative evaluation paradigms, making their absence from the Magicoder evaluation conspicuous.

**The consequence.** The paper's claims of general coding capability are **bounded by the task distribution it evaluates on**. A practitioner evaluating Magicoder for, say, a code review assistant, an automated refactoring tool, or a multi-file project generator would find no evidence to guide their decision. The strong Python focus (all primary benchmarks are Python, even MultiPL-E uses Python-inspired problems translated to other languages) means the paper has effectively demonstrated that OSS-INSTRUCT produces strong **Python instruction-following** — a narrower claim than "code generation." The MultiPL-E results (Table 2) partially address this by showing gains across 6 other languages, but MultiPL-E evaluates in a **code completion format** (fill-in-the-middle or left-to-right continuation) on problems structurally identical to HumanEval, not the instruction-following format in which Magicoder was trained and is strongest. The paper itself notes this mismatch: "the harness evaluates models in completion formats which are for base models, Magicoders still show significant improvements despite being only instruction-tuned" (Section 3.2) — an admission that the evaluation setup is suboptimal for the model's intended use case.

**What evidence exists in the paper.** All evaluation results in Section 3 and Appendix C are on these five benchmarks. The paper acknowledges the narrow scope only implicitly, through the benchmarks it chooses not to evaluate on. No negative results are reported — the paper does not test Magicoder on a task where it *fails* to improve over the base model, which would help characterize the method's generalization boundaries. The APPS evaluation (Appendix C.1, Table 8) comes closest to out-of-distribution testing, since competitive programming problems differ substantially from standard function-generation tasks, and Magicoder's improvements there are moderate (MagicoderS-DS-6.7B achieves 13.3% overall pass@1 on APPS vs. DeepSeek-Coder-Instruct-6.7B's 10.3%). The absolute performance on APPS is low enough (87% of problems unsolved) that conclusions about capability are tentative.

**Mitigation status.** Not addressed. The paper does not discuss evaluation breadth as a limitation, does not call for future work on broader evaluation, and does not characterize the expected domain of applicability. The benchmarks used are standard in the code LLM literature, so the evaluation scope is defensible by convention, but the claims made ("Magicoder substantially boosts the base LLM," "achieves SOTA results among all code models") are phrased in general terms that exceed the evidence. A practitioner reading the abstract would reasonably assume Magicoder is a general-purpose code model; the evaluation section reveals it has been tested primarily on a narrow, albeit important, task slice.

---

### Limitation 3: Hard Programming Problems Remain Effectively Unsolved — OSS-INSTRUCT Does Not Create New Capabilities

**The assumption or constraint.** The paper's approach is **instruction tuning** — fine-tuning a pretrained base model to better follow instructions in a code generation context. As with all instruction tuning, the method amplifies and redirects existing capabilities; it does not teach fundamentally new knowledge. This is an implicit assumption of the entire paradigm, not specific to Magicoder, but it creates a **hard ceiling on what OSS-INSTRUCT can achieve**: if the base model cannot produce correct solutions to a class of problems at any non-trivial rate, no amount of instruction tuning on synthetic data will enable it.

**The consequence.** Magicoder's strong performance on standard benchmarks masks a capability distribution that is likely **highly skewed toward easier problems**. HumanEval and MBPP contain problems that are, by design, solvable in a single function with a few dozen lines of code — they test algorithmic reasoning at the undergraduate CS level, not industrial-scale software engineering. On the APPS benchmark (Table 8), which includes harder competitive programming problems, **MagicoderS-DS-6.7B solves only 13.3% of problems overall**, and only **3.3% of competition-level problems** (the hardest subset). While this is an improvement over the base model (7.7% overall), the absolute numbers reveal that the vast majority of even moderately difficult problems remain unsolved. The MultiPL-E results for harder languages also show significant gaps: MagicoderS-CL-7B's 40.3% on Rust and 42.9% on Java (Table 2) leaves more than half of problems unsolved.

More broadly, OSS-INSTRUCT cannot teach the model programming concepts that are absent from both the base model's pretraining and the seed snippets. If the seed corpus lacks examples of a particular programming paradigm (e.g., formal verification, GPU kernel programming, distributed systems), and the base model was not exposed to it during pretraining, OSS-INSTRUCT will not generate problems in that paradigm and the student will learn nothing about it. The method is thus **bounded by the union of the base model's pretraining distribution and the seed corpus's content**, and this bound is passed through the narrow bottleneck of what the teacher LLM happens to generate from the seeds.

**What evidence exists in the paper.** The APPS results (Table 8) provide the clearest signal: a 13.3% pass@1 ceiling on the overall APPS subset and 3.3% on competition problems. The paper does not analyze performance by problem difficulty within HumanEval or MBPP, so it is unknown whether Magicoder's improvements are concentrated on easier problems or distributed evenly across difficulties. The paper also does not report performance on any benchmark specifically designed to test novel or out-of-distribution reasoning. The qualitative examples in Appendices D and E demonstrate Magicoder generating complex programs (a snake game, an Othello game, a Gradio application, an MNIST classifier), but these are cherry-picked successes — the failure modes, where Magicoder produces plausible-looking but incorrect code for hard problems, are not characterized.

**Mitigation status.** Not discussed. The paper does not frame this capability ceiling as a limitation, does not analyze per-difficulty performance, and does not suggest that augmenting the seed corpus or combining with retrieval-based methods could address harder problems. This is a consequential omission because it leaves practitioners with **no guidance on when Magicoder will fail**: a user encountering a novel algorithmic challenge or a domain-specific coding task has no way to predict whether Magicoder's improvements translate to their use case or whether the model is merely overfitting to the benchmark distribution.

### Limitation 4: The "Controllability" Claim Is Unsubstantiated

**The assumption or constraint.** The paper repeatedly claims that OSS-INSTRUCT enables **controllable data generation** and positions this as a key advantage over prior methods. The abstract states: "the wealth of open-source references for the production of more realistic and controllable data," and Section 1 frames OSS-INSTRUCT as producing "diverse, realistic, and controllable code instructions by providing distinct seed code snippets." The implicit claim is that practitioners can **steer the data generation process** toward desired problem types, domains, or programming languages by selecting appropriate seed snippets.

**The consequence.** If the controllability claim is unsubstantiated — or weaker than the paper implies — practitioners may overestimate OSS-INSTRUCT's utility for domain-specific applications. A team wanting to generate instruction data for, say, embedded systems programming in C or SQL query generation would need to know: does increasing the proportion of C or SQL seed snippets produce a corresponding increase in C or SQL problems? What is the mapping between seed distribution and output distribution? How many seeds are needed to reliably shift the generated problem distribution? The paper provides **no answers** to these questions beyond the coarse language ablation in Table 5, which shows that training on Python-only vs. non-Python data shifts performance but does not characterize the data generation distribution itself.

**What evidence exists in the paper.** Table 5 demonstrates that fine-tuning on ~43K Python-generated examples improves Python performance (HumanEval+ 47.6%) while fine-tuning on ~32K non-Python-generated examples improves multilingual performance (MultiPL-E 38.3%). This shows that the language of the seed influences the language of the generated problem — a coarse form of controllability. However, this is a **post-hoc correlation** measured through downstream performance, not a characterization of how the seed distribution maps to the output distribution. The paper does not report what fraction of OSS-INSTRUCT problems are in Python vs. other languages, does not measure whether a Python seed snippet always produces a Python problem (the paper notes that "LLMs performing OSS-INSTRUCT may produce code in a different programming language than the seed"), and does not experiment with intentionally biased seed distributions to test steering. The category breakdown in Figure 6 (Appendix A.3) shows diversity but does not link categories to seed characteristics.

The more ambitious forms of controllability — generating problems of a specific difficulty level, from a specific domain (e.g., scientific computing, web development, systems programming), or requiring specific libraries — are entirely undemonstrated. The qualitative examples (Figures 2, 5) show impressive diversity, but diversity is not controllability: a method that randomly samples from a broad distribution is diverse, but a practitioner cannot direct it to produce more of X and less of Y.

**Mitigation status.** Not addressed. The paper treats "controllable" as an inherent property of seed-driven generation — because you choose the seeds, you control the output — without testing whether this intuition holds in practice. The Section 6 future work mentions "generating higher-quality data with a strategically designed distribution of the seed code snippets" as a direction, which implicitly acknowledges that the current work did not explore strategic seed distribution design. However, this framing presents controllability as a future enhancement rather than clarifying that the current paper's controllability claims are aspirational. The distinction between "OSS-INSTRUCT enables controllability in principle" and "Magicoder's training data was controllably generated" is blurred throughout the paper, and the experimental evidence supports only the former.

---

### Limitation 5: The Dataset Size and Training Duration Are Not Optimized

**The assumption or constraint.** Magicoder models are trained on **75K OSS-INSTRUCT examples for exactly 2 epochs** (Appendix B.3), with MagicoderS adding a second stage of 110K Evol-Instruct examples. The 75K dataset size was determined by the initial collection of 80K seeds (minus deduplication and decontamination), not by a scaling analysis that characterized the relationship between dataset size and downstream performance. The 2-epoch training duration is a fixed protocol with no validation-based early stopping or epoch ablation. The batch size (512), learning rate (5e-5), and optimizer (Adafactor) are similarly fixed without sensitivity analysis.

**The consequence.** A practitioner applying OSS-INSTRUCT to a new base model or domain faces significant uncertainty about **how much data to generate and how long to train**. The paper provides no guidance on whether 75K examples are sufficient or excessive. If the method's gains follow a log-linear scaling curve (as is common in instruction tuning), doubling the dataset might yield substantial additional improvements — or the model might already be at the point of diminishing returns, meaning the same 75K budget could achieve similar results with half the data and half the training cost. The 2-epoch fixed training is particularly risky for transfer: a different base model with a different pretraining distribution might overfit to OSS-INSTRUCT data in 2 epochs (degrading its general coding knowledge) or might require 5 epochs to fully absorb the diverse problem distribution.

The DeepSeek-Coder results (Table 4) provide an indirect signal about data efficiency: MagicoderS-DS-6.7B (trained on +240M OSS-INSTRUCT + Evol-Instruct tokens) achieves results comparable to DeepSeek-Coder-Instruct-6.7B (trained on +2B tokens), suggesting OSS-INSTRUCT is **data-efficient relative to the DeepSeek-Coder instruction-tuning pipeline**. But this comparison is confounded by differences in data quality, base model, and training details — it does not isolate the effect of OSS-INSTRUCT data volume.

**What evidence exists in the paper.** No dataset scaling curve, no epoch ablation, and no sensitivity analysis for any hyperparameter. The only indirect evidence about data volume comes from comparing Magicoder-CL (75K OSS-INSTRUCT) to Magicoder-CL-Mixtral (20K OSS-INSTRUCT, different teacher) — they achieve identical 55.5% on HumanEval+ (Tables 1 and 7). This suggests that 20K high-quality OSS-INSTRUCT examples may approach the same performance as 75K, but the comparison is confounded by the different teachers, making it impossible to draw a firm conclusion. The paper also does not report training loss curves, validation performance over time, or any signal that would help practitioners select a training duration.

The Appendix C.3 ablation (Table 10) removing noisy samples (75K → 68K, +0.6 percentage point difference on HumanEval+) suggests that modest changes in data volume have small effects, but this is a 9% reduction, not a systematic scaling study. A proper scaling experiment varying data volume across an order of magnitude (e.g., 10K, 25K, 50K, 75K, 150K) would characterize the data efficiency curve and is entirely absent.

**Mitigation status.** Not addressed. The paper does not discuss the lack of dataset scaling or hyperparameter optimization as a limitation, and Section 6's future work mentions only "applying OSS-INSTRUCT to larger base models" and "generating higher-quality data" — not understanding the scaling properties of the method itself. This is a significant gap for a method whose core contribution is a **data generation protocol**. If the number of seeds, the snippet length distribution, or the training duration are arbitrary choices, the paper's conclusions may be specific to these choices and may not transfer to practitioners who must make their own resource-allocation decisions.

### Limitation 6: Instruction Tuning with OSS-INSTRUCT Does Not Inherently Guarantee Correctness or Executability of Generated Code

**The assumption or constraint.** OSS-INSTRUCT-generated problems include solutions generated by the teacher LLM, which are **assumed correct but not verified**. The paper's data cleaning pipeline (Section 2.2) removes only duplicate samples and benchmark-contaminated samples; it does **not** execute the generated solutions, check them against test cases, or validate them through any automated correctness criterion. The authors explicitly retain noisy or incomplete solutions: "inspired by Honovich et al. (2023), they are not removed as we believe they still contain valuable information for LLMs to learn" (Section 2.2). The implicit assumption is that the teacher LLM produces solutions that are correct *enough* that fine-tuning on them, including the imperfect ones, improves downstream performance — an assumption validated to a degree by the small positive effect of retaining noisy data (+0.6 percentage points, Table 10).

**The consequence.** The student model (Magicoder) learns from solution data that may contain subtle bugs, incorrect edge-case handling, inefficient algorithms, or outright logical errors. During training, the model is rewarded for predicting these flawed solutions, which could encode **incorrect programming patterns** into its learned behavior. At inference time, Magicoder may reproduce these patterns — generating code that *looks* plausible (and may even pass the limited test cases in HumanEval) but fails under rigorous testing or real-world deployment. The paper's own evaluation on HumanEval+ (80× more tests) partially addresses the *evaluation* side of this problem by catching solutions that pass HumanEval's weak tests but fail stronger ones, but it does nothing to address the *training data* side — the model was still trained on unvalidated solutions.

The EvalPlus results (Table 1) provide indirect evidence about this issue: the gap between HumanEval and HumanEval+ performance (which measures overfitting to weak tests) is **smaller for Magicoder-CL (60.4% → 55.5% = -4.9 points) than for WizardCoder-CL-7B (48.2% → 40.9% = -7.3 points)**. This suggests that Magicoder produces relatively more robust code, but does not speak to whether training on validated solutions would further close this gap or improve absolute performance.

More critically, the paper does not analyze *what kinds* of errors Magicoder makes. If the model has learned a systematic bug pattern from incorrect training solutions (e.g., off-by-one errors in certain loop structures, misuse of a specific API), this would be invisible in aggregate pass@1 metrics but could make the model unreliable for certain problem types.

**What evidence exists in the paper.** Table 10 (Appendix C.3) shows that retaining noisy data provides a small positive effect (55.5% vs. 54.9% on HumanEval+), which supports the paper's decision but does not address the correctness concern — the noisy data may help in aggregate while introducing specific failure modes. The qualitative examples in Appendices D and E demonstrate Magicoder generating complex, apparently correct programs (snake game, Othello game, Gradio app, MNIST classifier), but these are cherry-picked success cases, not systematic error analysis. The paper provides **no failure analysis**: no taxonomy of common errors, no breakdown of error types by problem category, and no investigation of whether certain error patterns correlate with specific seed snippet types. The modest absolute performance on APPS (13.3% overall pass@1, Table 8) and the low pass@1 on harder MultiPL-E languages like Rust (40.3%, Table 2) are aggregate metrics that hide potentially systematic failure modes.

**Mitigation status.** Not addressed as a limitation. The paper treats the teacher LLM's solutions as ground truth for training purposes, and the retention of noisy data is framed positively (citing Honovich et al., 2023) rather than as a tradeoff. The EvalPlus evaluation is a mitigation at the *evaluation* level (catching overfitted solutions) but not at the *training* level. The paper does not discuss approaches to improve training data correctness — such as executing generated solutions against the problem's implicit test cases, using the teacher to self-critique and refine solutions, or filtering solutions by execution success — nor does it characterize what fraction of OSS-INSTRUCT solutions are actually correct. A practitioner deploying Magicoder in a safety-critical or high-reliability setting (e.g., infrastructure automation, financial calculations) has no information about the model's expected error rate on specific problem types, only aggregate benchmark scores that may mask systematic vulnerabilities.

A natural direction that the paper does not explore is **execution-guided filtering**: for each OSS-INSTRUCT-generated problem, generate multiple candidate solutions, execute them against simple test cases (which the teacher could also generate), and retain only solutions that pass. This would close the training-evaluation correctness gap and potentially yield cleaner training data, at the cost of additional teacher API calls and compute. The paper's decision to forgo any correctness validation is a pragmatic choice that limits both the ceiling of achievable performance and the reliability guarantees practitioners can assume.
