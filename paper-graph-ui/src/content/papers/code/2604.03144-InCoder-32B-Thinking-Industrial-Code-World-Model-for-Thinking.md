# InCoder-32B-Thinking: Industrial Code World Model for Thinking

**ArXiv:** [2604.03144](https://arxiv.org/abs/2604.03144)

## 🎯 Pitch

A 32B open-source model beats 397B competitors on industrial coding by learning to predict its own execution errors before compiling. The key insight is not just teaching the model to think, but training a surrogate "world model" on GPU profiles and Verilog simulations so it can self-verify hardware-level reasoning without a real toolchain.

---

## 1. Executive Summary

This paper proposes **InCoder-32B-Thinking**, a thinking-augmented code model that bridges general code intelligence and industrial software development by integrating two synergistic mechanisms: **Error-driven Chain-of-Thought (ECoT) synthesis** (generating reasoning traces that explicitly model multi-turn error-correction processes, such as diagnosing GPU shared-memory faults across successive kernel revisions) and an **Industrial Code World Model (ICWM)** (a learned proxy trained on domain-specific execution traces—Verilog simulation logs, GPU profiling output, compiler diagnostics—that predicts hardware behavior without invoking real toolchains, enabling self-verification and scalable reasoning-trace synthesis). On general benchmarks, the model achieves 81.3% on LiveCodeBench v5, the highest among open-weight models including those with an order of magnitude more parameters, while on industrial benchmarks it establishes top-tier open-source results across chip design (75.6% RealBench module-level Syn@1), GPU optimization (38.0% on KernelBench L2), embedded systems (51.0% on EmbedCGen), and 3D modeling (84.0% on CAD-Coder compilation), surpassing even the proprietary Claude-Sonnet-4.6 on CAD-Coder and SuperCoder. The paper further demonstrates through a 180M→540M token thinking-data scaling analysis that chain-of-thought synthesis grounded in world-model execution feedback produces consistent industrial improvements, establishing that learned environment dynamics are key to industrial code reasoning only when the thinking traces reflect the naturally varying difficulty of real execution backends rather than an externally imposed reasoning budget.

## 2. Context and Motivation

### The Core Problem: Industrial Code Generation Requires Reasoning About Hardware, and We Have No Data to Learn From

The fundamental problem this paper addresses is deceptively simple: **large language models cannot write correct industrial code because the web-scale corpora they are trained on contain almost no examples of how expert engineers reason about hardware constraints during development.** When a human engineer writes a CUDA kernel, debugs a Verilog module, or optimizes embedded firmware, they engage in a diagnostic process that is fundamentally invisible in the final code artifact. The engineer thinks about shared memory budgets, warp divergence, clock domain crossings, register timing, and pipeline hazards — reasoning that happens in their head and is discarded once the correct implementation is produced. The resulting source code repositories, from which LLMs are typically trained, contain none of this cognitive trace.

This gap is not merely a matter of missing comments or documentation. It is a **structural absence of reasoning data** for an entire class of programming tasks that differ qualitatively from general software engineering. Section 1 of the paper characterizes this difference precisely:

> "Tasks such as CUDA optimization, Verilog description, firmware programming, and compiler optimization require reasoning about specialized semantics and hardware constraints absent from web-scale corpora. Verification depends on complex toolchains whose behavior must be learned for domain-specific feedback injection."

The paper identifies this as a **triple deficit** in existing training data for industrial code:

1. **No reasoning traces**: The step-by-step diagnostic thinking that engineers perform when debugging a shared-memory overflow, diagnosing a timing violation, or reasoning about floating-point tolerances in CAD geometry is simply not recorded. Final code commits show the solution, not the path to it.

2. **No error-correction patterns**: Industrial programming is inherently iterative — write code, compile/simulate, get an error, diagnose, revise. These multi-turn correction trajectories capture the causal logic of debugging (e.g., "the Yosys synthesis log shows a combinational loop on line 47, therefore I need to add a pipeline register between stages 2 and 3") but are absent from standard code datasets.

3. **No environment dynamics**: Understanding how code modifications affect hardware behavior — that increasing `BLOCK_N` from 128 to 256 in a Triton kernel will exceed the SM's 48 KB shared memory budget and trigger a `MEMORY_FAULT` — requires internalizing the causal dynamics of execution backends. Existing models lack this grounding because they have never been trained on execution-outcome pairs across the space of possible code revisions.

### Why This Problem Matters

The significance of this gap is both practical and conceptual.

**Practical significance: Industrial code generation is precisely where LLMs currently fail.** The paper cites benchmark evidence that leading models exhibit a sharp capability drop when moving from general programming to hardware-aware tasks:

> "Benchmarks show leading models achieve limited success on Triton generation and Verilog checking despite strong general performance."

Table 5 reveals the magnitude of this drop. On CAD-Coder (text-to-CAD generation), even strong general-purpose models like Qwen3-Coder-480B-A35B-Instruct achieve only 10.0% compilation rate and 4.7% IoU. On KernelBench Level 2 (kernel fusion tasks), DeepSeek-V3.2 — a 671B parameter model — achieves 0% pass rate (the dash in the table indicates the metric was not reported or was effectively zero). This is not a small degradation; it is a near-complete collapse of capability. The models that score 90%+ on HumanEval and 70%+ on SWE-bench Verified cannot produce a valid CAD script or an optimized GPU kernel at rates above single digits.

The stakes are high because industrial code domains — chip design (a $500B+ industry), GPU optimization (critical for AI infrastructure), embedded systems (the backbone of IoT and automotive), and compiler optimization — are economically foundational. A model that could reason about hardware constraints at human-expert level would transform these industries, enabling faster design cycles, automated optimization, and democratized access to specialized engineering expertise.

**Conceptual significance: It reveals a structural limitation in current LLM training paradigms.** The failure of large general-purpose models on industrial tasks is not primarily a scale problem — it persists even at 671B parameters (DeepSeek-V3.2) and 480B parameters (Qwen3-Coder-480B-A35B). The problem is a **data distribution gap**: standard pretraining corpora contain abundant examples of Python scripting, web development, and algorithmic problem-solving, but they contain almost no examples of the specialized reasoning patterns that define industrial engineering. This means that simply scaling model size or training data volume along existing trajectories will not close the gap — a qualitatively different data source is needed.

The paper frames this as a problem of **environment grounding**. In general programming, a model can often produce correct code from a natural language specification because the mapping between intent and implementation is relatively direct and well-represented in training data. In industrial programming, the mapping is mediated by complex execution backends (simulators, compilers, synthesis tools) whose behavior must be *learned*:

> "Industrial code reasoning needs environment grounding to predict hardware effects of code execution and validate via a learned simulator before actual execution."

Without this grounding, a model cannot anticipate that a particular register configuration will cause a bus fault on an STM32 microcontroller, or that a specific CadQuery Boolean operation will produce a degenerate zero-thickness edge and trigger a `GEOMETRY_ERROR`. These failures are not due to insufficient "reasoning ability" in the abstract — they are due to the model lacking the **world model** of the execution environment that would enable it to simulate outcomes before committing to code.

### Prior Approaches and Where They Fall Short

The paper surveys a landscape of prior work (Section 5, Related Work) that can be organized into four categories, each with identifiable limitations that motivate the proposed approach.

#### 1. General-Purpose Thinking Models Applied to Code

The thinking model paradigm — inaugurated by OpenAI's o1 and extended by DeepSeek-R1, QwQ, and Qwen3-Thinking — has demonstrated that training models to produce extended chains of thought before answering can dramatically improve performance on complex reasoning tasks. The paper acknowledges the power of this approach:

> "On the open-source side, DeepSeek-R1 showed that pure RL can incentivize emergent reasoning without supervised fine-tuning, while QwQ and Qwen3 introduced hybrid modes that dynamically switch between fast and slow thinking."

However, the paper identifies a specific limitation when these methods are applied to industrial code:

> "For code-specific reasoning, structured chain-of-thought prompting, o1-Coder, and rStar-Coder have adapted thinking techniques to programming tasks, yet none target industrial code domains, nor do they leverage execution feedback to synthesize reasoning traces."

The key phrase is **"none target industrial code domains."** General thinking models are trained on mathematical reasoning, competitive programming, and general coding tasks. Their chains of thought reflect the reasoning patterns appropriate for those domains — algebraic manipulation, algorithmic analysis, API usage — not the hardware-aware diagnostic reasoning that industrial tasks demand. A DeepSeek-R1 style chain of thought about a CUDA kernel might discuss algorithmic complexity but is unlikely to include reasoning about warp scheduling, bank conflicts, or shared memory allocation, because its training data contains no examples of engineers performing such reasoning.

Even code-specific thinking approaches (o1-Coder, rStar-Coder) share this limitation: they are trained on competitive programming and general software engineering data, not on Verilog synthesis logs or GPU profiling traces. The thinking format exists, but the thinking *content* — the domain-specific knowledge and diagnostic patterns — is missing.

#### 2. Industrial Code Models: Fragmented, Single-Domain Solutions

The paper provides a comprehensive survey of prior work targeting specific industrial sub-domains (Section 5.1). The pattern is consistent: each approach targets exactly one domain with custom architectures, training pipelines, and evaluation protocols:

- **Chip design**: Early fine-tuning efforts for RTL generation (Thakur et al., 2023; Liu et al., 2024), followed by reinforcement learning with hardware-specific rewards (CodeV-R1, VeriReason), and specialized debugging models (VeriDebug). Each addresses Verilog specifically and cannot transfer to other domains.

- **GPU kernel optimization**: Kevin (RL for CUDA), CUDA Agent (agentic RL for CUDA), and AscendKernelGen (NPU-specific). Each is tied to a specific hardware target and optimization paradigm.

- **Embedded systems**: EmbedAgent and EmbedGenius focus on microcontroller programming with domain-specific toolchains.

- **Compiler optimization**: LLM Compiler and related work target x86/LLVM optimization passes.

- **3D modeling**: CAD-Coder and ReCAD focus on parametric CAD generation with geometric constraints.

The paper's assessment of this landscape is direct:

> "Despite these advances, existing work remains fragmented, with each model or benchmark tailored to a single industrial sub-domain."

This fragmentation has concrete consequences. A practitioner working across chip design and GPU optimization would need separate models, separate training pipelines, and separate evaluation setups. There is no shared reasoning framework, no reusable world model of execution environments, and no common understanding of how error-correction patterns generalize across domains. The paper's precursor, InCoder-32B, is identified as "a significant step toward unification" because it spans multiple domains, but it lacks the thinking capability that the current work introduces.

#### 3. Execution-Grounded Reasoning: RL and Self-Refinement Without World Models

A separate line of work has explored grounding LLM reasoning in execution feedback, which is conceptually aligned with this paper's goals. Self-Refine introduced iterative refinement driven by model-generated feedback. LeDex trained models to self-debug by learning from execution diagnostics. RLEF grounded code LLMs in execution feedback via reinforcement learning, demonstrating that real execution outcomes can serve as powerful reward signals.

These approaches address part of the problem — they close the loop between code generation and execution feedback — but the paper identifies a critical missing piece:

> "InCoder-32B-Thinking unifies these research threads: it synthesizes long thinking content from multi-turn execution-grounded correction trajectories... and trains an industrial code world model to amplify reasoning data at scale without repeated access to real backends."

The limitation of prior execution-grounded approaches is twofold. First, **they are expensive**: each interaction requires invoking real toolchains (Verilog simulators, GPU compilers, CAD kernels), which are computationally intensive and brittle to maintain at scale. Second, **they do not produce reusable reasoning traces**: the feedback guides the model toward a correct solution, but the diagnostic reasoning that the model performed is not captured as training data for future use. The paper's ICWM directly addresses the first limitation (by providing a learned proxy that avoids real toolchain invocation), and the ECoT synthesis framework addresses the second (by explicitly recording the reasoning content from each correction round as training data).

#### 4. Thinking Data Synthesis: Distillation and RL Without Domain Grounding

A central challenge for building thinking models is synthesizing high-quality chains of thought. The paper identifies two dominant approaches:

- **RL-based methods**: GRPO provides an efficient algorithm for incentivizing reasoning emergence through reinforcement learning, used by DeepSeek-R1 and subsequent work.
- **Distillation-based methods**: STILL-2 proposed a three-stage pipeline of distillation from strong teacher models, exploration via rejection sampling, and iterative self-improvement. OpenCodeReasoning advanced data distillation for competitive coding.

The paper acknowledges these as valid approaches but identifies their shared limitation for industrial code: **they lack domain grounding**. RL methods need a reward signal, which in general coding can be test-pass rates, but in industrial coding requires execution against complex toolchains whose behavior must be simulated efficiently. Distillation methods need a teacher model that can produce high-quality industrial reasoning traces, but — as the benchmark results show — even the strongest existing models (DeepSeek-V3.2, Claude-Sonnet-4.6) struggle with industrial tasks, so distilling from them would propagate their limitations.

The paper positions ECoT as a fundamentally different approach to thinking data synthesis:

> "ECoT generates reasoning traces by explicitly modeling the error-correction process through contrasting incorrect attempts and their environmental feedback with correct solutions."

Rather than eliciting reasoning from a model in a vacuum (via prompting) or rewarding reasoning that leads to correct answers (via RL), ECoT creates training data where the reasoning *content* is grounded in real execution outcomes. The model sees not just "here is a correct solution" but "here is an incorrect attempt, here is what the simulator said about it, here is how an engineer would diagnose that error, and here is the corrected version." This captures the causal structure of industrial debugging in a way that pure reasoning distillation cannot.

### How This Paper Positions Itself

The paper's positioning can be understood as filling a specific gap in a 2×2 matrix: the intersection of **thinking models** (models that produce extended chains of thought) and **industrial code environments** (domains with complex execution backends). Figure 1 in the paper visually reinforces this: it shows thinking traces across six domains (GPU optimization, competitive programming, chip design, 3D modeling, tool use, agentic coding), with industrial domains highlighted and the reflective depth scale emphasizing that thinking length is driven by execution-feedback complexity.

The paper makes no claim to invent thinking models, industrial code models, execution-grounded reasoning, or data distillation. Its contribution is the *integration* of these threads into a unified framework with two novel components:

1. **ECoT synthesis**: A data generation methodology that produces thinking traces by running real multi-turn error-correction trajectories against execution backends, capturing the diagnostic reasoning that occurs at each step. This is distinct from prior thinking data synthesis because the content is shaped by the actual difficulty of each execution-feedback cycle, not by a fixed prompting template or an externally imposed reasoning budget.

2. **ICWM**: A learned world model that predicts execution outcomes without invoking real backends, trained on the same trajectories used for ECoT synthesis. This enables scaling reasoning-trace generation beyond what is practical with real toolchains. The paper explicitly frames this as an **amplification mechanism**: real execution provides high-quality but expensive supervision, the ICWM learns to approximate it, and the ICWM then drives large-scale trajectory synthesis with periodic audits to maintain calibration.

The paper positions InCoder-32B-Thinking as building directly on InCoder-32B (the authors' prior work), which established a multi-domain industrial code foundation model through a three-stage training pipeline. The thinking variant adds chain-of-thought reasoning on top of this foundation:

> "Building upon it, InCoder-32B-Thinking is a Thinking variant that integrates chain-of-thought reasoning to further enhance the model's capacity for complex industrial code generation."

This framing makes clear that the contribution is not a new pretraining recipe or architecture, but rather a **reasoning data synthesis methodology** that unlocks thinking capabilities for industrial domains where such data is naturally scarce. The paper's evaluation strategy — testing on both general benchmarks (to show that thinking capability transfers broadly) and industrial benchmarks (to show domain-specific gains) — reflects this dual positioning: the model should be a strong general coder *and* a specialized industrial engineer.

The paper also positions itself relative to the **scale vs. thinking** debate. The benchmark results (Tables 1–5) consistently show InCoder-32B-Thinking at 32B parameters outperforming models with 10–20× more parameters on industrial tasks, and achieving top-tier results on general code reasoning (81.3% on LiveCodeBench v5, surpassing 480B and 671B models). This is presented as evidence that thinking grounded in environment dynamics can compensate for model scale — a claim that the scaling analysis in Section 4.3 (180M → 540M thinking tokens producing consistent improvements) is designed to support.

Finally, the paper identifies its work as addressing a **validation gap** in thinking model research. While prior thinking models (o1, DeepSeek-R1) rely on self-consistency or reward model scores for verification, InCoder-32B-Thinking's reasoning traces are validated against real execution outcomes during training:

> "All synthesized reasoning traces are validated through domain toolchains, creating training data matching the natural reasoning depth distribution of industrial tasks."

This provides a form of ground-truth grounding that purely self-supervised thinking approaches lack, and it is the mechanism that enables the model to learn the causal dynamics of hardware behavior rather than merely producing plausible-sounding reasoning.

## 3. Technical Approach

### 3.1 Reader Orientation

The system being built is a **data synthesis pipeline that produces training examples of expert reasoning about hardware-constrained code, paired with a learned simulator that mimics real execution environments to scale up that synthesis cheaply.** It solves the problem that industrial code domains (chip design, GPU optimization, embedded systems, 3D modeling) have almost no recorded reasoning traces showing how engineers diagnose and fix hardware-level errors, which means standard LLM training cannot teach models to think about shared memory budgets, timing violations, or geometric constraints. The solution's shape is a feedback loop: real toolchains provide expensive but accurate supervision for a limited number of code-correction trajectories; those trajectories train a "world model" that approximates the toolchains; the world model then drives large-scale synthesis of thinking traces without invoking real backends; and the combined corpus (real + world-model-generated) trains the final thinking model.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components connected in a two-phase pipeline (summarized in Figure 4):

1. **Task Seeding and Environment Bundling** — The input stage: for each industrial coding task, assemble the problem specification together with the execution environment (testbenches, synthesis scripts, memory layouts, linker scripts) into a self-contained, reproducible package called `⟨𝑠task, 𝑠env⟩`. This bundling ensures every downstream step has the context needed to actually compile, simulate, and verify generated code.

2. **Execution Grounded Trajectory Synthesis** — Phase 1 (real execution): A frontier generator model (DeepSeek-V3.2) receives the task bundle, is prompted with domain-specific instructions via a lightweight prompt router, and produces an initial reasoning trace and candidate code. The code executes against real backends (Triton/CUDA, Renode, CadQuery, Yosys/Icarus). Execution outcomes (pass/fail labels plus diagnostic logs) are fed back to the generator, which must diagnose the error and produce a revised trace and implementation. This iterates for up to `K = 4` correction rounds, yielding multi-turn trajectories `D_real` that pair reasoning content with concrete execution outcomes.

3. **Industrial Code World Model (ICWM) Training** — The single-turn (code, execution outcome) pairs extracted from `D_real` train a language model that, given an environment bundle `𝑠env` and candidate code `𝑐`, predicts what a real backend would return: outcome label (PASS, COMPILATION_ERROR, MEMORY_FAULT, etc.), diagnostic message, and task-specific outputs. This is a learned proxy for industrial execution backends.

4. **ICWM-Driven Data Amplification** — Phase 2 (simulated execution): The trained ICWM replaces real backends in the feedback loop. The same generator model produces code, the ICWM predicts the execution outcome in a single forward pass (rather than real compilation/simulation), the generator revises based on the predicted feedback, and the cycle repeats. This produces `D_ICWM`, a large corpus of simulated multi-turn reasoning trajectories, at a fraction of the cost of real execution. Periodic audits with real backends check the ICWM's calibration and retrain it when drift is detected.

5. **InCoder-32B-Thinking Training** — The final reasoning model is trained on `D = D_real ∪ D_ICWM`, a corpus where every trajectory is either produced by real execution or verified against it (via the audit mechanism). The model learns to produce thinking traces whose depth and content are shaped by the actual difficulty of the execution-feedback cycle, not by a fixed template.

Information flows sequentially: task seeds → environment bundles → initial code generation → real execution → error feedback → revised code → (repeat K times) → D_real trajectories → ICWM training → ICWM-driven synthesis → D_ICWM trajectories → combined D corpus → InCoder-32B-Thinking model training. The critical feedback loop is that D_real serves double duty: it directly contributes to the thinking model's training data, and it provides the supervision signal for the ICWM that makes large-scale amplification possible without recurring real-toolchain costs.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **data synthesis paper** whose core idea is that thinking traces for industrial code must be generated through multi-turn error-correction dialogues grounded in real execution feedback, and that a learned world model of execution environments can then amplify this synthesis to a scale that makes thinking-model training practically feasible.

---

#### Task Seeding and Environment Bundling

The pipeline begins with task seeds reused from the authors' prior work, InCoder-32B. Each seed consists of a query (the natural language specification of the industrial coding task), associated unit tests, and the execution environment configuration needed to verify solutions. The critical design decision at this stage is that every task is **bundled with its full environmental context** before any generation occurs:

> "Each task seed is packaged with its required environmental context: Verilog modules are bundled with testbenches and Yosys synthesis scripts; STM32 firmware snippets are coupled with the corresponding memory layout, CMSIS headers, and linker scripts."

This bundling produces a pair `⟨𝑠_task, 𝑠_env⟩` that provides a "fully specified, reproducible execution context for every downstream step." The technical motivation is that industrial code verification is **not self-contained** — a Verilog module cannot be tested without a testbench and a simulator configuration; an STM32 firmware snippet cannot be compiled without the correct memory layout and CMSIS headers. If these environmental artifacts were not bundled with the task, the execution step (subsection 2.2) would fail not because the model wrote incorrect code, but because the verification infrastructure was missing. The bundling eliminates this confounding factor.

The bundling also serves a second purpose: it provides the **input context for the ICWM** (subsection 2.3). The world model needs to see the same environmental context that a real backend would see in order to predict execution outcomes. By making `𝑠_env` an explicit, structured component of every task representation, the paper ensures that the ICWM's training data (which consists of `(𝑠_env, 𝑐, 𝑜)` triples extracted from `D_real`) has a consistent input format across all tasks and domains.

The paper does not detail the exact structure of `𝑠_env` per domain, but the examples make clear that it is domain-specific: for chip design, it includes testbenches and synthesis scripts (typically TCL or Makefile wrappers around Yosys); for GPU kernels, it includes the Triton/CUDA build configuration and test input tensors; for embedded systems, it includes memory layout descriptors (linker scripts), CMSIS header paths, and Renode platform description files; for 3D modeling, it includes the CadQuery Python environment and geometry validation scripts. The prompt router (described next) is responsible for interpreting the environment bundle and selecting appropriate domain-specific generation instructions.

---

#### Prompt Router and Domain-Specific Generation Instructions

Before the generator model produces any code, a **lightweight prompt router** inspects the environment bundle `𝑠_env` and selects domain-specific generation instructions:

> "For example, GPU kernel tasks require the generator to reason about warp divergence and shared memory budgets; RTL tasks require reasoning about combinational path depth and clock domain crossings; CAD tasks about wall thickness and manifold validity; firmware tasks about peripheral register sequencing."

The prompt router is not a trained model — it is a rule-based classifier that determines the domain from the contents of `𝑠_env` (presence of `.v` files + testbenches → chip design; `.cu` or `.py` with Triton imports → GPU kernels; `.c` with CMSIS headers → embedded systems; CadQuery imports → 3D modeling) and prepends the corresponding instruction block to the generator's prompt.

This mechanism is important for two reasons. First, it **grounds the generator's reasoning in domain-specific vocabulary and constraints** from the very first generation step. Without these instructions, the generator might produce generic Python code for a GPU kernel task — syntactically valid but ignoring hardware constraints — because its default "code generation" behavior is biased toward general-purpose programming. The domain instructions redirect its attention to the specific reasoning dimensions that matter for each domain.

Second, the prompt router's output **propagates through the entire multi-turn trajectory**. Each round of execution feedback and revision includes these domain instructions in the generator's context, ensuring that even after multiple correction rounds, the generator continues to reason in domain-appropriate terms rather than reverting to generic coding patterns.

The paper does not report the exact text of the domain-specific instructions, which is a minor omission — the quality of these instructions likely has a significant impact on the quality of the generated reasoning traces, and their design is part of the intellectual contribution. However, the examples given (warp divergence, shared memory budgets, combinational path depth, clock domain crossings, wall thickness, manifold validity, peripheral register sequencing) are sufficiently specific that the intended scope is clear: each instruction block guides the generator toward the first-order correctness constraints for its domain.

---

#### Execution Grounded Trajectory Synthesis — The Multi-Turn Feedback Loop

This is the core of Phase 1. Given the bundled task and the domain-specific generation instructions from the prompt router, a frontier model generates an initial reasoning trace and candidate code, executes it against real backends, and iterates through correction rounds.

**Generator model choice.** The generator is DeepSeek-V3.2, a 671B-parameter mixture-of-experts model that the paper describes in its baseline comparisons (Tables 1–5) as having strong general code performance. The choice of a frontier closed-source model as the generator (rather than, say, the authors' own InCoder-32B base model) is a practical one: to produce high-quality initial reasoning traces and correction revisions, the generator must itself have strong code capabilities. The paper's premise is not that InCoder-32B-Thinking will learn to *imitate* DeepSeek-V3.2 — it is that the ECoT synthesis framework will produce training data that teaches industrial reasoning patterns, and a strong generator is needed to produce exemplars of those patterns that are correct enough to be useful.

This is a form of **teacher-student training**, where the teacher (DeepSeek-V3.2) demonstrates diagnostic reasoning in industrial contexts, and the student (InCoder-32B-Thinking) learns to internalize those reasoning patterns. The paper explicitly references this in the abstract:

> "InCoder-32B-Thinking is trained on the data from ECoT synthesis and the data from teacher-student distillation, where complex cases accumulate multi-step error-correction and reasoning traces."

**The first generation round (turn 0).** With the domain-specific instructions and the bundled task `𝑠_task` in its context, the generator DeepSeek-V3.2 outputs an initial pair of reasoning content and code: `(𝑟^(0), 𝑐^(0))`. The reasoning content `𝑟^(0)` is a natural language explanation of the generator's design decisions, constraint analysis, and implementation approach. The candidate code `𝑐^(0)` is the actual implementation (Verilog module, Triton kernel, C firmware, or CadQuery script).

**Distributed execution.** The candidate code `𝑐^(0)` is sent to real execution backends that match its domain, as determined by the environment bundle:

> "Triton/CUDA for GPU kernels, Renode for microcontroller firmware, CadQuery for CAD geometry, and Yosys/Icarus for RTL."

This is a **distributed system** — the paper explicitly labels it "Distributed Real Execution" in Figure 4 — because the backends are heterogeneous: Triton requires NVIDIA GPU hardware, Renode is a system-level simulator, CadQuery is a Python library built on OpenCascade, and Yosys/Icarus are command-line synthesis and simulation tools. Each backend must be maintained as an operational service that can accept code, execute it, and return structured results.

**Structured execution results.** Each backend returns a structured result containing two components:

1. An **outcome label** drawn from a domain-specific finite set: PASS, COMPILATION_ERROR, MEMORY_FAULT, GEOMETRY_ERROR, etc. The exact labels vary by domain but the paper standardizes them so that the ICWM can learn to predict them uniformly.

2. An **associated diagnostic log** — the full text output from the compilation, simulation, or execution process. For Triton kernels, this includes the compiler error messages, register allocation reports, and shared memory usage diagnostics. For Verilog, it includes Yosys synthesis warnings and Icarus simulation assertion failures. For CadQuery, it includes geometry validation errors like "BRep check: edge has zero length."

The structured result is the `observation` that drives the next round of reasoning.

**Correction rounds (turns k = 1 through K).** When execution produces an error, the concrete output — "compilation logs, hardware exceptions, geometric diff reports" — is packaged as an observation `𝑜^(𝑘)` and fed back to the generator. The generator must then:

1. **Diagnose the fault** — infer from the diagnostic log what went wrong and why. This is the reasoning content `𝑟^(𝑘)`.
2. **Produce revised code** — `𝑐^(𝑘)`, the corrected implementation based on that diagnosis.

The generator sees the full history: the original task specification, all previous reasoning traces `𝑟^(0), ..., 𝑟^(𝑘-1)`, all previous code versions `𝑐^(0), ..., 𝑐^(𝑘-1)`, and all previous observations `𝑜^(1), ..., 𝑜^(𝑘-1)`. This context enables the generator to avoid repeating previously attempted (and failed) approaches and to build a coherent diagnostic narrative across multiple correction rounds.

The paper sets the maximum number of correction rounds to `K = 4`. A trajectory terminates when the code passes all checks (outcome label = PASS) or when the maximum number of turns is reached:

> "We allow up to `K = 4` correction rounds, yielding a multi-turn trajectory"

The choice of K=4 is a hyperparameter that balances two concerns. Too few rounds (K=1 or 2) would mean that difficult tasks frequently terminate with errors, producing training trajectories that end in failure — these are still useful (they capture common failure modes), but the paper wants trajectories that reach correct solutions to teach successful diagnostic patterns. Too many rounds (K=8 or more) would increase the real-execution cost per task, since each round requires a full compilation or simulation cycle. K=4 is a pragmatic middle ground informed by the observation (visible in the scaling analysis of Section 4.3) that thinking depth varies naturally by domain: GPU kernel optimization demands deeper reasoning than agentic coding, and K=4 provides enough headroom for the most demanding domains while keeping costs bounded.

**Trajectory structure.** The full multi-turn trajectory is formalized in Equation 1:

> $$\tau = \langle s_{\text{init}}, r^{(0)}, c^{(0)} \rangle \rightarrow \langle r^{(1)}, c^{(1)} \rangle \cdots \rightarrow \langle r^{(k)}, c^{(k)} \rangle$$
>
> where `$s_{\text{init}}$` is the initial task description together with its environment bundle, `$r^{(k)}$` is the reasoning content at turn `$k$`, `$c^{(k)}$` is the corresponding candidate code, and each arrow represents one round of execution feedback followed by the generator's revision.
>
> **What it represents:** a linear sequence of alternating generation and execution-feedback steps. Each `$\langle r^{(k)}, c^{(k)} \rangle$` is the generator's response to seeing the task plus all prior feedback; each arrow is the real backend producing an observation from the code.
>
> **Why this form:** this is a structured record of the diagnostic process — unlike a single-turn (query, correct answer) pair, it preserves the *causal chain* of error → diagnosis → revision → verification. This matters because the thinking model needs to learn not just what correct code looks like, but how to *arrive* at it through iterative debugging. A trajectory that goes directly from empty context to correct answer would teach the model what to output in the ideal case, but not how to respond when its first attempt fails — which is the common case in industrial programming.

**Retention of unsuccessful intermediate turns.** A crucial design decision:

> "Both successful and unsuccessful intermediate turns are retained so that training data captures common failure modes alongside the reasoning steps that resolve them."

This means the training corpus includes trajectories where the final answer is incorrect (e.g., the K=4 limit is reached without a PASS), as well as trajectories where intermediate turns produced errors that were later corrected. The motivation is that seeing *how* errors are diagnosed — what the generator looked at in the diagnostic log, what hypothesis it formed, what revision it attempted — teaches the reasoning process, not just the final answer. A model trained only on successful trajectories would learn to produce correct code in easy cases but would have no training signal for what to do when it encounters an error.

#### Industrial Code World Model (ICWM) — Definition, Training, and Design

The ICWM is the component that makes large-scale thinking-trace synthesis practical. Real execution is accurate but expensive: each invocation of a Triton compiler, Verilog simulator, or CadQuery kernel requires computational resources comparable to model inference itself, and maintaining a robust distributed execution stack across four heterogeneous backends at scale is operationally complex. The ICWM addresses this by learning to approximate backend feedback from data.

**Preliminaries — what is "the world" in this context?** The paper defines its terms carefully:

> "We define the world in an industrial coding task as the executable environment that determines the consequence of a code revision. Concretely, an environment bundle `𝑠_env` contains the task-specific artifacts required for execution and verification, such as testbenches, simulators, compiler settings, configuration files, memory layouts, and domain constraints."

This definition is important because it scopes the ICWM's responsibility: it does not need to model the entire physics of a GPU or the full behavior of an STM32 microcontroller — it only needs to model the *observable outputs that the execution backend would produce* given a piece of code and its environmental context. This is a much more tractable learning problem than full hardware simulation.

The observation at turn k, `𝑜^(𝑘)`, is the structured result returned by the real backend: an outcome label (PASS, COMPILATION_ERROR, etc.), a diagnostic message, and, when applicable, numerical outputs or diff summaries.

**ICWM definition — Equation 2:**

> $$\text{ICWM}_\theta: (s_{\text{env}}, c^{(k)}) \mapsto \hat{o}^{(k)}$$
>
> where the predicted output `$\hat{o}^{(k)}$` includes an outcome label (PASS, COMPILATION_ERROR, etc.), a diagnostic message, and, when applicable, numerical outputs or diff summaries.
>
> **What it computes:** given an environment bundle `$s_{\text{env}}$` and a candidate program `$c^{(k)}$`, the ICWM predicts what a real backend would have returned. The prediction `$\hat{o}^{(k)}$` is a structured text output that mimics the format of real execution results.
>
> **Why this form:** the ICWM is a text-to-text mapping, not a numerical simulator. This is a deliberate choice — it means the ICWM can be implemented as a language model (the same architecture and training infrastructure as the thinking model) and can be trained on exactly the same data format as the thinking model. A numerical simulator would require engineering a domain-specific state representation (GPU register values, Verilog signal traces, CAD mesh topologies), which would scale poorly across four heterogeneous domains. The text-to-text approach means a single model architecture serves all domains, differentiated only by the domain tag prepended to the input.

**Training data for the ICWM.** The ICWM is trained on "every real execution turn in `D_real`." Each turn provides a training example `(𝑠_env, 𝑐^(𝑘)) → 𝑜^(𝑘)`. The paper does not report the total number of training examples, but given that `D_real` contains multi-turn trajectories across all four domains with up to K=4 rounds each, the number is substantial — likely on the order of tens to hundreds of thousands of execution turns.

**Domain unification via tags and templates:**

> "To handle the differences across domains, we prepend a domain tag to each input and use domain specific output templates, so that a single model can serve all four verticals."

The domain tag (e.g., "[GPU Kernel]", "[Chip Design]", "[3D Modeling]", "[Embedded System]") signals to the ICWM which execution backend's behavior to emulate. The domain-specific output templates constrain the ICWM's predictions to the structured format expected for that domain — for example, GPU kernel outputs must include execution status and memory usage diagnostics, while CAD outputs must include geometry validity and potential error locations.

This is a form of **multi-task learning**: by training a single model on execution traces from four different backends, the ICWM can share representational capacity across domains while using the domain tag to specialize its behavior. The alternative — training four separate world models — would require four times the training data and inference infrastructure, and would lose any cross-domain transfer (e.g., general patterns of how compilation errors are reported might be shared across Verilog and C code).

The paper does not report the specific architecture, parameter count, or training hyperparameters of the ICWM. Given that it is described as "a language model" and is trained on the same infrastructure as the thinking model, it is likely based on the same 32B-parameter base architecture as InCoder-32B, but this is not confirmed.

**What the ICWM is NOT.** The paper is clear about the ICWM's limitations: it is a learned proxy that approximates backend feedback, not a perfect simulator. The fidelity analysis in Section 4.1 quantifies exactly how close the approximation is (mean outcome prediction accuracy 96.7%, mean trajectory agreement 94.4%). The gap — roughly 2–3 percentage points from per-turn accuracy to end-to-end verdict consistency — is attributed to error compounding across multi-turn trajectories.

#### ICWM-Driven Data Amplification — The Synthesis Loop

Once trained, the ICWM replaces real backends in the feedback loop described in subsection 2.2. The paper formalizes this as the ICWM-driven version of the trajectory synthesis equation (Equation 3):

> $$\tau = \langle s_{\text{init}}, r^{(0)}, c^{(0)} \rangle \xrightarrow{\text{ICWM}_\theta} \langle r^{(1)}, c^{(1)} \rangle \cdots \xrightarrow{\text{ICWM}_\theta} \langle r^{(k)}, c^{(k)} \rangle$$
>
> where each arrow represents one round of ICWM feedback rather than execution feedback followed by the generator's revision, since each prediction is a single forward pass rather than a real compilation or simulation.
>
> **What it represents:** the same multi-turn trajectory structure as Equation 1, but with the execution step replaced by ICWM inference. The generator produces `$(r^{(k)}, c^{(k)})$`; instead of sending `$c^{(k)}$` to a real backend, the system sends `$(s_{\text{env}}, c^{(k)})$` to the ICWM; the ICWM returns `$\hat{o}^{(k)}$`; the generator uses `$\hat{o}^{(k)}$` to produce `$(r^{(k+1)}, c^{(k+1)})$`.
>
> **Why this form:** it is structurally identical to the real-execution loop, which means the generated trajectories `$D_{\text{ICWM}}$` have the same format as `$D_{\text{real}}$`. This is essential — the thinking model trains on the union `$D = D_{\text{real}} \cup D_{\text{ICWM}}$`, and if the two halves had different formats or distributions, the model would learn spurious artifacts of the synthesis mechanism rather than genuine reasoning patterns.

**Cost advantage.** The critical difference between Equations 1 and 3 is computational cost. Real execution (Equation 1) requires:

- Compiling Verilog with Yosys (seconds to minutes per compilation)
- Simulating with Icarus (seconds to minutes per testbench)
- Running Triton kernels on GPU hardware (seconds per kernel, plus GPU allocation overhead)
- Executing CadQuery geometry operations (seconds per Boolean operation)
- Running Renode system-level simulations (seconds to minutes per firmware build)

ICWM inference (Equation 3) requires a single forward pass of a language model — typically milliseconds to tens of milliseconds on modern hardware. This is **orders of magnitude faster** than real execution, and it does not require maintaining GPU clusters, Verilog toolchains, or embedded system simulators as operational services.

The paper does not report the exact speedup factor, but the implication is clear from the framing: real execution provides "reliable supervision but is expensive for complex industrial tasks because each interaction requires invoking domain-specific toolchains and maintaining a robust execution stack." The ICWM provides a "fast proxy environment for large-scale trajectory synthesis."

**Periodic audits to maintain calibration.** The ICWM is not a fixed model — it is periodically checked against real execution to detect and correct calibration drift:

> "The ICWM then serves as a fast proxy environment for large-scale trajectory synthesis, with periodic real execution audits that keep the world model calibrated."

The audit mechanism is not described in detail, but the paper's case study in Section 4.1 suggests how it works: spot-check a sample of ICWM-generated trajectories against real backends, identify mismatches (e.g., the 3D modeling false positive where the ICWM predicted PASS but real CadQuery raised GEOMETRY_ERROR), and use the corrected labels to retrain the ICWM. This is an **online learning loop** — the ICWM improves over successive synthesis rounds as more real-execution ground truth is accumulated.

The frequency of audits, the sampling strategy, and the retraining protocol are not specified. This is a limitation of the paper's description — the audit mechanism is conceptually important (it is what guarantees that `D_ICWM` trajectories are "verified against" real execution, as claimed in the abstract) but the details needed to reproduce it are absent.

**The final reasoning corpus.** After both phases:

> "The final reasoning training set is `D = D_real ∪ D_ICWM`. Every trajectory in D is either produced by real execution or verified against it, ensuring the code model learns from grounded feedback rather than hallucinated outputs."

The "verified against it" clause refers to the audit mechanism: `D_ICWM` trajectories are generated using the ICWM, but periodic real-execution checks validate that the ICWM's predictions match what real backends would have produced, creating a statistical guarantee that the simulated trajectories are reliable.

#### InCoder-32B-Thinking Training Configuration

The paper reports the training data scale: a total of 540M tokens of thinking training data, trained at three checkpoints (180M, 360M, and 540M tokens) for the scaling analysis in Section 4.3. This is substantially larger than the 250M tokens used for the non-thinking InCoder-32B:

> "This amount is much larger than the 250M tokens used for InCoder-32B. The reason for this difference is the chain of thought method. This reasoning process naturally creates longer texts and increases the total token count."

The training data consists of the multi-turn thinking trajectories from `D`, formatted as sequences where each turn includes:

1. The task specification and environment context
2. The generator's reasoning content `𝑟^(𝑘)` — labeled as "THINK" blocks in Figure 1
3. The generator's candidate code `𝑐^(𝑘)` — labeled as "ANSWER" blocks in Figure 1
4. The execution outcome `𝑜^(𝑘)` or `ô^(𝑘)` — the observation that triggered the next revision

Figure 1 visualizes this format with explicit "THINK" and "ANSWER" block statistics per domain, showing the median token counts for thinking content versus answer content across GPU optimization, competitive programming, chip design, 3D modeling, tool use, and agentic coding. The "Reflective Depth" annotation in Figure 1 emphasizes that thinking traces are "reasoning refined by execution errors" — each round of error feedback adds to the reasoning depth.

The paper does not report the detailed training hyperparameters for InCoder-32B-Thinking — learning rate, batch size, optimizer, number of epochs, or early stopping criteria. The model is described as "trained on the data from ECoT synthesis and the data from teacher-student distillation," which suggests that the training procedure is a continuation of the InCoder-32B training pipeline (the three-stage Code-Flow pipeline described in the related work) with the addition of the thinking corpus as a fine-tuning or continued-pretraining stage. This is a significant omission for reproducibility, though the paper's focus on data synthesis methodology rather than training recipe partially explains it.

**Adaptive thinking depth — a property of the data, not the training.** A key claim the paper makes about InCoder-32B-Thinking's behavior is that it learns to **adaptively calibrate its thinking effort** to the complexity of the problem:

> "Because the thinking traces in D originate from real or ICWM-simulated execution feedback rather than a fixed prompting template, the training corpus naturally covers the full spectrum of reasoning depths. The model therefore learns to adaptively calibrate its thinking effort, investing deep multi-step reasoning where complex industrial backends demand it while keeping traces succinct for tasks with short feedback loops."

This is an emergent property of the training data distribution, not an explicit training objective. Figure 6 quantifies this: median thinking length spans a 209× range, from 91 characters per step in agentic coding to 19,015 characters in GPU kernel optimization. The paper argues that this variation is "not engineered by hand" but is a direct consequence of the error-driven synthesis pipeline — tasks with complex execution feedback naturally accumulate longer reasoning traces through successive correction rounds, while tasks with self-evident errors produce shorter ones.

This is significant because it distinguishes InCoder-32B-Thinking from thinking models that use fixed reasoning budgets (e.g., "always generate 4096 tokens of thinking before answering"). Those models waste computation on easy problems and may truncate reasoning on hard ones. InCoder-32B-Thinking's adaptive behavior is grounded in the actual difficulty of the problem as measured by the number and complexity of correction rounds needed to reach a correct solution.

#### ICWM Fidelity Analysis — Validating the Core Assumption

Although this analysis appears in Section 4 of the paper, it is a direct validation of the ICWM design described in Section 2.3 and is essential for understanding the technical approach's viability. I include it here to complete the reasoning about the ICWM component.

The core assumption of Phase 2 is that the ICWM can faithfully replace real execution backends during large-scale trajectory synthesis. The paper validates this with two complementary metrics evaluated on a held-out set of 2,000 execution turns per domain from `D_real`:

1. **Outcome prediction accuracy**: the fraction of individual turns where the ICWM's predicted outcome label (PASS, COMPILATION_ERROR, etc.) exactly matches the real backend's label. This measures per-turn fidelity.

2. **Trajectory agreement**: the fraction of full multi-turn trajectories whose final pass/fail verdict is identical under real and ICWM-driven execution. This measures end-to-end fidelity, which matters because a single mispredicted turn can redirect the generator onto a divergent correction path, compounding the initial error.

**Results (Figure 5):**

- **Mean outcome prediction accuracy: 96.7%** across all five domains (GPU kernels, chip design, 3D modeling, code optimization, embedded systems).
- **Mean trajectory agreement: 94.4%** across all five domains.
- **Best domain: Chip design** at 97.4% outcome accuracy / 95.8% trajectory agreement. The paper attributes this to Yosys and Icarus producing "structurally template-like diagnostics" that the world model learns reliably — Verilog compiler errors follow predictable patterns because the language syntax and synthesis rules are well-defined.
- **Worst domain: 3D modeling** at 95.9% outcome accuracy / 93.1% trajectory agreement. The paper attributes this gap to CadQuery geometry checks involving "floating-point tolerances and implicit Boolean operations whose outcomes are harder to predict from code text alone." The case study provides a concrete example: a script that creates a degenerate zero-thickness edge is syntactically valid but semantically invalid, and the ICWM misclassifies it as PASS because the code text looks plausible.

**Error compounding mechanism.** The consistent 1.6–2.8 percentage point drop from outcome accuracy to trajectory agreement is expected and explained:

> "The consistent 1.6∼2.8 score drop from outcome accuracy to trajectory agreement is expected: a single mispredicted turn can redirect the generator onto a divergent correction path, compounding the initial error."

This is a simple probabilistic argument: for a trajectory of length L turns, the probability that the full trajectory's verdict agrees with real execution is approximately `(outcome_accuracy)^L` if errors are independent. With L=2–4 turns and outcome accuracy ~96%, theoretical trajectory agreement would be `0.96^2 ≈ 0.92` to `0.96^4 ≈ 0.85`. The actual trajectory agreement of 94.4% is better than this independent-error model predicts, suggesting that errors are not independent — the ICWM tends to be consistently correct or consistently incorrect on a given trajectory, perhaps because some tasks are inherently harder to predict (like degenerate geometric edge cases) and the ICWM either gets the whole task right or wrong.

**Interpretation of 94.4% trajectory agreement.** The paper's framing is that "more than nine out of ten ICWM-driven trajectories are functionally equivalent to their real-execution counterparts, confirming that the world model provides a reliable proxy for large-scale synthesis." This is a reasonable interpretation: 94.4% agreement means that for most training trajectories in `D_ICWM`, the sequence of execution outcomes the thinking model sees during training is identical to what it would have seen with real execution. The 5.6% of trajectories that diverge introduce noise into the training data, but the periodic audit mechanism provides a safeguard — real-execution spot checks detect these divergences and feed the corrected labels back into ICWM retraining, so the fidelity should improve over successive synthesis rounds.

**Case study: correct GPU kernel diagnosis.** The paper provides a concrete example of ICWM fidelity:

> "A Triton kernel for fused attention allocates a `tl.zeros([BLOCK_M, BLOCK_N])` tile in shared memory while launching with `num_warps=8`, exceeding the SM's 48 KB shared-memory budget. The real Triton compiler returns MEMORY_FAULT with diagnostic 'shared memory request (49152 B) exceeds per-SM limit'. The ICWM predicts the same MEMORY_FAULT label with a quantitatively matching diagnostic message. In the subsequent turn, the generator reduces BLOCK_N from 128 to 64; the ICWM correctly predicts PASS. This two-turn trajectory is identical under real execution, illustrating how the world model preserves the causal chain that drives error-correction reasoning."

This example demonstrates three important properties of the ICWM:

1. **Quantitative accuracy**: the ICWM reproduces not just the error category (MEMORY_FAULT) but the specific diagnostic detail (49152 B = 128 × 128 × 3 bytes, matching the formula for shared memory allocation).
2. **Causal chain preservation**: after the generator fixes the error (reducing BLOCK_N from 128 to 64, bringing shared memory to 128 × 64 × 3 = 24576 B, within the 48 KB limit), the ICWM correctly predicts PASS. The cause-effect relationship (exceeding budget → error; staying within budget → success) is learned.
3. **Multi-turn coherence**: the two-turn trajectory is "identical under real execution" — the ICWM's feedback produces the same revision behavior from the generator as real execution would have, which is the essential requirement for `D_ICWM` training data to be useful.

**Case study: 3D modeling false positive.** The paper also provides a failure case to illustrate the ICWM's limitations:

> "A CadQuery script constructs a mounting bracket by subtracting a cylindrical bore from a rectangular body. The candidate code places the cylinder axis exactly tangent to one face, creating a degenerate zero-thickness edge. Real CadQuery raises GEOMETRY_ERROR with diagnostic 'BRep check: edge has zero length'. The ICWM classifies this turn as PASS because the code is syntactically valid and the specified dimensions appear plausible, producing a false positive."

This failure mode is instructive: the ICWM fails because it operates on code text, not on geometric reasoning. The code is syntactically correct CadQuery — it calls the right functions with the right argument types — and the dimensions (placement of the cylinder relative to the body) are specific numbers that look reasonable in isolation. The error arises from the geometric interaction of those numbers (tangency → zero-thickness edge), which requires 3D spatial reasoning beyond what a text-based world model can reliably perform. The paper identifies this as the root cause of the wider fidelity gap in 3D modeling and notes that the periodic audit mechanism progressively corrects such errors by detecting them via real-execution spot checks.

#### Design Choices and Their Justifications

**Why DeepSeek-V3.2 as the generator?** The generator must produce high-quality reasoning traces and correct code to serve as effective training data. The paper's benchmark results show that DeepSeek-V3.2 has strong general code performance (Tables 1–3), and it is a 671B-parameter model — much larger and more capable than the target 32B student model. This creates a **capability gap** between teacher and student, which is a standard desideratum for distillation: the teacher should be stronger than the target student so that the student learns from better examples than it could produce itself. The alternative — using InCoder-32B as its own generator — would be circular: the model would be learning from its own error patterns, which might reinforce rather than correct its weaknesses.

**Why K=4 correction rounds?** The choice balances trajectory depth against real-execution cost. Each additional round requires a full compilation or simulation cycle against a real backend. Four rounds provides enough depth for most hardware-level errors to be diagnosed and corrected (the GPU kernel case study shows a two-round correction for a shared memory fault; more complex errors like timing violations or multi-stage pipeline hazards might require 3–4 rounds). Increasing K would increase the cost per trajectory linearly without necessarily producing proportionally richer reasoning traces, because after 4+ rounds of failure, the generator is likely stuck and further rounds would not reach a correct solution.

**Why a single ICWM with domain tags rather than four separate world models?** Multi-task learning across domains enables the ICWM to share representational capacity for general patterns of compiler/simulator feedback (error categories like COMPILATION_ERROR vs. RUNTIME_ERROR have similar semantics across domains) while the domain tag specializes behavior. Four separate models would require four times the training data and deployment infrastructure, and would lose any cross-domain transfer. The domain-specific output templates ensure that the ICWM's predictions for each domain conform to the expected format, preventing format confusion (e.g., the ICWM predicting GPU diagnostics for a Verilog task).

**Why text-to-text rather than numerical simulation for the ICWM?** The ICWM predicts text outputs (diagnostic messages, outcome labels) rather than numerical hardware states. This is a deliberate engineering simplification: representing the full state of a GPU (register values, memory contents, warp states), a Verilog circuit (signal values at every net, clock states), or a CAD model (mesh vertex coordinates, face normals, topology) would be prohibitively complex and domain-specific. By predicting text diagnostics — which is what the generator model would see in a real execution loop — the ICWM provides exactly the information needed for the error-correction process without attempting full hardware simulation.

**Why retain unsuccessful intermediate turns?** This is one of the most important design choices. Standard supervised fine-tuning on correct code examples teaches the model what correct code looks like, but not how to respond to errors. By including trajectories where:
- An early turn produces incorrect code that is later corrected
- The final turn fails (K=4 reached without PASS)

The training data teaches the model **diagnostic behavior**: given an error message, here is what an expert engineer would look at, what hypothesis they would form, and what revision they would attempt. Even failed trajectories provide value: they show the model that some approaches don't work for specific reasons, which is knowledge it can use to avoid those approaches in future attempts. This is analogous to how human engineers learn — not just from successful designs, but from understanding why failed designs failed.

## 4. Key Insights and Innovations

### Innovation 1: Industrial Code Reasoning is a Data Distribution Problem, Not a Scale Problem

The paper's most fundamental intellectual move is reframing the failure of LLMs on industrial code tasks from a question of model capability to a question of **training data distribution**. The dominant assumption in the field — visible in the scaling of models like DeepSeek-V3.2 (671B parameters) and Qwen3-Coder-480B (480B parameters) — is that larger models trained on more web-scale code will eventually saturate industrial benchmarks, just as they have for general programming tasks like HumanEval and SWE-bench. The paper's benchmark results directly falsify this assumption: DeepSeek-V3.2 achieves 0% on KernelBench Level 2 kernel fusion tasks, Qwen3-Coder-480B achieves 10.0% compilation rate and 4.7% IoU on CAD-Coder, and even Claude-Sonnet-4.6 — a proprietary frontier model — reaches only 28.0% on KernelBench L2. These are not marginal degradations from strong general performance; they are near-complete capability collapses, occurring at model scales where general coding benchmarks show 70-90%+ accuracy.

The paper's diagnostic move is to identify **why** this collapse happens: web-scale code corpora contain abundant examples of Python scripting, web development, and algorithmic problem-solving — domains where the mapping between natural language intent and correct code is relatively direct and well-sampled in training data — but contain almost no recorded examples of the diagnostic reasoning that engineers perform when debugging hardware-level errors. The paper's contribution is not the observation that industrial code is hard (which is obvious) but the specific causal claim that the hardness arises from a **structural absence of reasoning traces** in standard training corpora, not from an inherent limitation of language model architectures.

This framing has significant implications beyond the paper's own results. It suggests that the path to industrial code intelligence is not primarily through scaling model parameters or pretraining data volume along existing trajectories — as the Chinchilla-style scaling laws community might advocate — but through **qualitatively different data sources** that capture the error-correction dynamics invisible in final code artifacts. It also explains why prior single-domain approaches (CodeV-R1 for Verilog, Kevin for CUDA, CAD-Coder for 3D modeling) achieved partial success: each introduced domain-specific feedback signals, but none addressed the underlying data distribution gap at the reasoning-trace level. The paper's ECoT framework is not just a better data synthesis method; it is an operationalization of this reframing, producing training data whose distribution matches the causal structure of industrial debugging rather than the surface statistics of web code.

**Significance beyond performance**: This is a conceptual reframing, not an incremental performance improvement. It changes the question from "how do we make models better at industrial code?" to "what data would teach a model to reason like an industrial engineer, and how do we generate it?" The distinction matters because the former question invites scaling-as-usual answers (more parameters, more web data), while the latter demands domain-grounded data synthesis.

**Evidence**: The near-zero performance of 480B+ models on industrial benchmarks in Tables 4-5, contrasted with InCoder-32B-Thinking's strong performance at 32B parameters, directly supports the claim that scale is not the bottleneck. The scaling analysis in Figure 7 further reinforces this: industrial performance improves consistently as thinking data scales from 180M to 540M tokens, while general coding performance (Table 1-3) remains broadly competitive, suggesting that thinking data — not parameter count — is the active ingredient.

### Innovation 2: A Learned World Model of Execution Environments as a Data Amplification Engine

Prior work on execution-grounded reasoning for code (Self-Refine, LeDex, RLEF) uses real execution feedback as a reward or correction signal during training or inference, but treats the execution backend as an external oracle that must be invoked at each interaction. This creates a fundamental scalability bottleneck: each invocation of a Verilog simulator, GPU compiler, or CAD kernel costs seconds to minutes of wall-clock time and requires maintaining heterogeneous, brittle execution infrastructure. The paper identifies this as the reason prior approaches remained small-scale demonstrations rather than industrial-scale training pipelines.

The intellectual innovation is recognizing that **the execution backend itself can be learned as a text-to-text model** and that this learned proxy can then drive large-scale reasoning-trace synthesis at a cost reduction of orders of magnitude. This reframes the execution environment from an external oracle into a learnable component of the training pipeline. The ICWM is not merely a speed optimization — it is a **data amplification engine** that makes the ECoT synthesis framework practically scalable. Without the ICWM, every thinking trace in the training corpus would require real toolchain invocations, limiting the corpus size to what is affordable with available compute and engineering resources. With the ICWM, real execution provides high-quality but expensive supervision for a limited number of trajectories (enough to train the world model to 96.7% per-turn accuracy), and the world model then drives large-scale synthesis where each "execution" is a single forward pass.

This is conceptually analogous to how world models are used in model-based reinforcement learning (Sutton's Dyna architecture, Ha and Schmidhuber's World Models), but the application to **text-based code reasoning** is novel. In RL, a learned dynamics model enables planning and data generation without interacting with the real environment. In this paper, the ICWM enables trajectory synthesis without interacting with real toolchains. The domain-specific adaptation — using domain tags and output templates so a single text-to-text model serves four heterogeneous backends — is an engineering contribution that makes the conceptual analogy practically viable.

**Why this is not just an engineering trick**: The ICWM's fidelity analysis (Section 4.1, Figure 5) reveals a subtle property that makes the approach intellectually substantive. The 1.6–2.8 percentage point gap between per-turn outcome accuracy (96.7%) and multi-turn trajectory agreement (94.4%) quantifies the **error compounding** inherent in replacing real execution with a learned proxy. The paper does not just report this gap — it explains it (a single mispredicted turn redirects the generator onto a divergent path), characterizes its domain dependence (worst in 3D modeling due to geometric corner cases), and provides a mitigation mechanism (periodic real-execution audits with retraining). This transforms what could be dismissed as "a learned verifier that is sometimes wrong" into a **characterized uncertainty** — we know how wrong it is, in what ways, and on which domains, and we have a calibration loop to improve it over time.

The ICWM also represents a novel answer to the question of how to make execution feedback scalable for code LLMs. Prior approaches treated real execution and learned verifiers as alternatives: either use real compilers (accurate but slow) or use learned reward models (fast but potentially inaccurate). The paper's hybrid approach — use real execution to train the world model, then use the world model for scale, with periodic audits to maintain calibration — occupies a previously unexplored point in the accuracy-efficiency tradeoff space.

**Evidence**: Figure 5 directly validates the ICWM's fidelity with 96.7% outcome accuracy and 94.4% trajectory agreement across 2,000 held-out turns per domain. The case studies (correct GPU kernel diagnosis, 3D modeling false positive) provide qualitative evidence that the ICWM preserves causal chains in successful cases and fails in interpretable ways in challenging cases. The fact that InCoder-32B-Thinking trained on D_real ∪ D_ICWM outperforms the non-thinking InCoder-32B by large margins on industrial benchmarks (Tables 4-5) provides indirect validation that ICWM-generated data is effective for training.

### Innovation 3: Execution-Grounded Thinking Traces as a New Modality of Training Data

The paper introduces a new category of training data for code LLMs: **multi-turn execution-grounded reasoning trajectories** that capture not just what correct code looks like, but how an expert engineer arrives at it through iterative diagnosis and revision. This is distinct from the three dominant paradigms for code training data: (1) supervised fine-tuning on (problem, correct solution) pairs, which shows the destination but not the journey; (2) RL with execution feedback (RLEF, CodeRL), which uses execution outcomes as rewards but does not capture the reasoning that led to the rewarded behavior; and (3) reasoning distillation (STILL-2, OpenCodeReasoning), which transfers chain-of-thought from teacher models but does not ground those chains in execution outcomes.

The intellectual move is recognizing that the **causal structure** of industrial debugging — error → diagnosis → revision → verification — is itself the valuable training signal, not merely a means to produce correct final answers. This is why the paper retains unsuccessful intermediate turns in D_real: a trajectory where turn 2 misdiagnoses a memory fault but turn 3 correctly identifies it teaches the model what a failed diagnosis looks like and how to recover from it. A trajectory that terminates in failure after K=4 rounds teaches the model that some approaches do not work and why. Standard SFT on correct answers would discard all of this information.

This framing has a subtle but important implication: **the quality of a reasoning trace is not measured by whether it reaches the correct answer, but by whether it faithfully captures the diagnostic reasoning that an engineer would perform given the same error feedback.** A trajectory that reaches a wrong answer after K=4 valid but ultimately unsuccessful diagnostic attempts is still useful training data, because it teaches the model the diagnostic *process* — how to parse a Yosys synthesis log, how to map a GPU memory fault to a specific tile size adjustment, how to infer from a CadQuery geometry error that a Boolean operation created a degenerate edge. The model learns these skills even from trajectories where the final answer is incorrect.

This is a departure from the correctness-centric evaluation that dominates code generation research. In standard code benchmarks, only the final answer matters — a model gets credit for producing correct code and nothing for producing a plausible but incorrect solution with good reasoning. The paper is not arguing against correctness evaluation (it reports standard benchmark scores throughout), but it is arguing that training data should include a broader distribution of reasoning quality than just (problem, correct answer) pairs. The claim is that exposure to diagnostic reasoning — including failed diagnoses — is what enables the model to generalize to novel industrial tasks, because those tasks will inevitably involve debugging cycles that require diagnostic skill beyond pattern-matching correct solutions.

**Why this matters beyond this paper**: If execution-grounded reasoning trajectories prove to be a generally effective training modality for code LLMs, it opens a new research direction that is orthogonal to both scale (more parameters) and distillation (better teacher models). It suggests that future code models should be trained not just on what correct code looks like, but on what the process of discovering correct code looks like — a shift from product-oriented to process-oriented training. This aligns with findings in mathematical reasoning (DeepSeek-R1 showing that long chains of thought emerge from RL training) but differs in a crucial way: the reasoning traces are grounded in external execution feedback rather than internal self-consistency, providing a verifiability guarantee that purely self-supervised thinking approaches lack.

**Evidence**: The adaptive thinking depth analysis (Section 4.2, Figure 6) directly demonstrates the consequence of this training modality. The 209× range in median thinking length (91 characters for agentic coding to 19,015 characters for GPU optimization) is not an engineered feature — it emerges from the fact that different execution backends have different error-feedback complexity, and the model learns to calibrate its thinking effort accordingly. The scaling analysis (Figure 7) shows that adding more thinking data (180M → 540M tokens) consistently improves industrial performance, confirming that the thinking traces are a productive training signal, not just padding.

### Innovation 4: Difficulty-Conditioned Adaptive Reasoning via Multi-Turn Execution Feedback

The paper demonstrates — though it does not theorize as explicitly as it could — that **the depth of thinking traces in training data should be proportional to the difficulty of the execution-feedback cycle, not determined by a fixed budget.** This emerges naturally from the ECoT pipeline: tasks where errors are obvious from a single compilation log (e.g., syntax errors in Verilog) produce short correction trajectories with brief reasoning; tasks where errors require multi-step diagnosis (e.g., shared memory faults that manifest only at specific grid configurations) produce long trajectories with detailed reasoning about hardware constraints. The model then learns from this distribution that some problems warrant 91 characters of thinking and others warrant 19,015 characters — a 209× difference.

This is a meaningful departure from how thinking budgets are typically allocated in chain-of-thought models. Approaches like o1 and DeepSeek-R1 train models to produce extended chains of thought, but the length of those chains is driven by the model's internal reasoning dynamics and reward shaping, not by an external measure of problem difficulty. The result can be that the model over-thinks easy problems (wasting inference compute) or under-thinks hard problems (truncating reasoning before reaching a correct diagnosis). The paper's approach provides an implicit difficulty signal — the number and complexity of correction rounds needed to reach PASS — that is grounded in real execution outcomes, not in the model's self-assessment of difficulty.

The conceptual contribution is the recognition that **execution backends provide a natural difficulty curriculum**. Easy industrial tasks are those where the first code attempt compiles and passes tests; the reasoning trace is short because there is nothing to diagnose. Hard tasks are those that require multiple correction rounds, each reacting to specific diagnostic feedback; the reasoning trace grows with each round. By training on this naturally varying distribution, the model learns to allocate thinking compute adaptively — deep reasoning where the backend demands it, shallow reasoning where it does not.

This insight connects to the broader literature on adaptive computation time and difficulty-aware inference. Prior work has shown that test-time compute allocation should vary with problem difficulty (Snell et al., 2024, on compute-optimal test-time scaling), but that work manually selected strategies per difficulty bin. The paper's contribution is showing that the **training data itself can encode difficulty-appropriate reasoning depths** if the data generation process is grounded in real execution feedback, and that models trained on such data learn adaptive behavior without explicit difficulty-conditioned training objectives.

**Evidence**: Figure 6 provides direct quantitative support: the median thinking length varies by domain in ways that match the complexity of the corresponding execution backends. GPU kernel optimization demands the deepest reasoning (19K characters median) because each correction round requires diagnosing hardware-level issues. Chip design shows an inverted profile (1.5K thinking, 6.9K answer) because Yosys/Icarus diagnostics are concise but code generation is verbose. Figure 7 shows that this adaptive behavior is productive: as thinking data scales, industrial benchmarks that demand deep reasoning (KernelBench L2: 16.0 → 38.0) improve much more than benchmarks where thinking is naturally short (TritonBench G-exe stays at 100% throughout).

### Innovation 5: Unified Multi-Domain Industrial Code Intelligence as a Viable Research Target

Prior to this work, industrial code intelligence research was fragmented: each sub-domain (chip design, GPU optimization, embedded systems, 3D modeling) had its own models, benchmarks, and training methodologies, with essentially zero cross-pollination. The authors' prior work, InCoder-32B, took the first step toward unification by training a single model on data from multiple industrial domains, but it did not have thinking capabilities. InCoder-32B-Thinking demonstrates that thinking capabilities — specifically, the diagnostic reasoning that ECoT synthesis produces — **transfer across heterogeneous industrial domains** without domain-specific architectural modifications.

The evidence for this claim is the consistent strong performance across all nine industrial benchmarks (Tables 4-5): 75.4 on VeriScope, 75.6 RealBench Syn@1 (module), 84.0 CAD-Coder compilation, 47.9 SuperCoder Acc., 38.0 KernelBench L2. These benchmarks span chip design, GPU optimization, embedded systems, compiler optimization, and 3D modeling — domains whose execution backends (Yosys vs. Triton vs. Renode vs. CadQuery) have essentially no technical overlap. The fact that a single model achieves top-tier open-source results across all of them suggests that the **reasoning patterns learned from ECoT synthesis — diagnosis from error logs, hypothesis formation, targeted revision — are general cognitive skills that transfer across execution environments**, even though the specific knowledge (Verilog syntax vs. CUDA memory models vs. CadQuery geometry) is domain-specific.

This finding has practical implications: it suggests that the industrial code intelligence community does not need a separate model and training pipeline for each domain. A unified model trained on ECoT-synthesized data from multiple domains can serve as a general-purpose industrial code assistant, amortizing the substantial engineering cost of building and maintaining execution backends across all target domains. It also suggests that adding a new industrial domain to the model's repertoire requires only bundling its execution environment and collecting real-execution trajectories — the ECoT + ICWM pipeline handles the rest without architectural changes.

**Significance beyond performance**: This is primarily a **demonstration that unification works** — the paper shows it is possible, not that it is optimal. There may be domain-specific architectures or training procedures that outperform the unified approach on individual benchmarks. But the paper's contribution is establishing that the unified approach is viable at all, which was not obvious given the profound differences between, say, GPU kernel optimization (numerical, performance-focused, hardware-parallelism reasoning) and 3D modeling (geometric, constraint-satisfaction, spatial reasoning). The fact that the same model can achieve 84.0% on CAD-Coder and 38.0% on KernelBench L2 — both strong open-source results — suggests that these apparently disparate reasoning modalities share a common cognitive substrate that ECoT synthesis successfully instills.

**Evidence**: Tables 4-5 collectively demonstrate that InCoder-32B-Thinking is competitive with or exceeds all open-weight models across every industrial domain, and even surpasses Claude-Sonnet-4.6 (a proprietary model) on CAD-Coder and SuperCoder. The fact that no other model achieves this breadth — models that are strong on Verilog (e.g., Kimi-K2-Instruct on VeriScope) are weak on CAD (2.0% compilation), and vice versa — shows that the unified performance profile is distinctive, not a byproduct of general strong coding ability.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper evaluates on two families of benchmarks: 14 general code benchmarks and 9 industrial code benchmarks. The general benchmarks include EvalPlus (HumanEval and MBPP with augmented test cases), BigCodeBench (1,140 task-oriented prompts), FullStackBench (4,000+ problems across 16 languages), CRUXEval (800 programs for execution tracing), LiveCodeBench (competitive programming from LeetCode/AtCoder/Codeforces, versions V5 and V6), Mercury (code efficiency), Spider and BIRD (text-to-SQL), Terminal-Bench v1.0/v2.0 (multi-turn terminal interactions), SWE-bench Verified (real GitHub issue resolution), Mind2Web (web navigation), BFCL V3 (function calling), and τ2-bench (multi-turn conversational agent in Airline, Retail, Telecom). The industrial benchmarks include VeriScope (568 Verilog problems across five difficulty tiers), VeriRepair (300 test samples for Verilog error repair), RealBench (60 module-level and 4 system-level Verilog subtasks), ArchXBench (51 complex digital-system designs), KernelBench (250 PyTorch ML workloads across three levels), TritonBench (184 real-world Triton operators across two tracks), EmbedCGen (500 bare-metal embedded C problems), SuperCoder (8,072 x86-64 assembly optimization tasks), and CAD-Coder (text-to-CAD generation with CadQuery). Detailed descriptions of each benchmark, including evaluation protocols and metric definitions, appear in Appendix A.

- **Base model.** InCoder-32B-Thinking is a 32B-parameter model built as a thinking-augmented variant of the authors' prior InCoder-32B. The non-thinking InCoder-32B serves as a direct ablation baseline. For the general-code comparison, the paper evaluates against a comprehensive set of open-weight models spanning 6B to 671B parameters, including DeepSeek-Coder-V2-Lite-Instruct (2.4/16B MoE), Qwen2.5-Coder variants (7B, 14B, 32B), Qwen3-Coder variants (30B-A3B and 480B-A35B MoE), Qwen3-235B-A22B variants (Instruct and Thinking), DeepSeek-V3.2 (37/671B MoE), Kimi-Dev-72B, Kimi-K2 variants (32B/1T MoE, Instruct and Thinking), KAT-Dev (32B) and KAT-Dev-72B-Exp, Seed-Coder-8B-Instruct, and GLM-4.7 (32/355B MoE). For industrial-code comparison, additional baselines include Qwen3.5 variants (9B, 27B, 397B-A17B), GPT-OSS variants (20B and 120B), MiniMax-M2.5 (10/230B MoE), GLM-5 (40/744B MoE), Kimi-K2.5 (32B/1T MoE), Seed-OSS-36B-Instruct, and Claude-Sonnet-4.6 as a proprietary reference. The baseline set is deliberately broad to cover both dense and mixture-of-experts architectures across an order-of-magnitude parameter range.

- **Metrics.** Metrics vary by benchmark and are defined in Appendix A. For code generation, accuracy is measured by functional correctness against test cases (pass@1 for HumanEval/MBPP, Syn@k and Func@k for RealBench, compilation success rate and IoU for CAD-Coder). For code reasoning, output prediction accuracy is used (CRUXEval) and problem solve rate (LiveCodeBench). For code efficiency, Mercury reports Beyond@1 and Pass@1. For chip design, VeriScope reports average score across problems with a three-level scheme (0/50/100), VeriRepair reports fix rate (Fix%), ArchXBench reports (n, t) where n is syntactically correct candidates and t is the percentage of testbench assertions passed by the best candidate. For GPU optimization, KernelBench reports fast₁ (fraction of tasks where generated kernel is correct and achieves at least 1× speedup), and TritonBench reports call accuracy and execution accuracy per track (G-call, G-exe, T-call, T-exe). For embedded systems, EmbedCGen reports average pass rate (Main%) across 500 problems. For code optimization, SuperCoder reports accuracy (Acc.%) and speedup (Spd.). The diversity of metrics reflects the heterogeneity of industrial verification — each domain has correctness criteria that cannot be unified into a single pass@k framework.

- **Baselines.** General-code baselines are enumerated in Table 1, Table 2, and Table 3, drawn from contemporary open-weight coding models as described above. Industrial-code baselines are enumerated in Table 4 and Table 5. The paper does not train its own baselines; all comparison numbers are reproduced from published results or evaluated by the paper's authors using standard evaluation protocols. For industrial benchmarks, the inclusion of Claude-Sonnet-4.6 provides a proprietary frontier reference point. For the scaling analysis in Section 4.3, the baselines are intermediate checkpoints of InCoder-32B-Thinking itself (trained on 180M, 360M, and 540M tokens), with the 180M checkpoint serving as the initial comparison point — this is an internal scaling baseline rather than an external method comparison.

- **Generation budget / compute accounting.** The paper does not use a unified compute budget or FLOPs-matched comparison framework. Instead, each benchmark has its own evaluation protocol: generation of k independent samples per problem (k varies by benchmark — e.g., RealBench uses k=20 samples per task, ArchXBench uses 5) and selection via domain-specific verification pipelines. The model is evaluated in a zero-shot or few-shot setting as specified by each benchmark's standard protocol. There is no mechanism for comparing test-time compute allocation across methods; all models are evaluated under the same per-benchmark protocol. This is a notable difference from test-time scaling studies where compute budgets are explicitly equalized — here, the "budget" is implicitly determined by the number of samples the benchmark protocol requests.

- **Cross-validation / statistical protocol.** The paper does not report confidence intervals, standard deviations, or statistical significance tests for benchmark results. For the scaling analysis in Section 4.3, three checkpoints (180M, 360M, 540M tokens) are evaluated, providing a coarse view of scaling trends but without error bars. For the ICWM fidelity analysis in Section 4.1, 2,000 execution turns per domain are held out from D_real, providing a reasonably sized validation set, but again without confidence intervals. The absence of variance estimates is a limitation — for benchmarks with small test sets (e.g., KernelBench L2 with 250 problems, CAD-Coder with 110K triplets but evaluated on a subset), the reported accuracy differences between models may not be statistically reliable.

### Main Quantitative Results

#### General Code Benchmarks: Competitive but Not Dominant

Tables 1, 2, and 3 report results across code generation, reasoning, efficiency, text-to-SQL, agentic coding, and tool use. The headline finding is that InCoder-32B-Thinking achieves **81.3% on LiveCodeBench V5, the highest among all open-weight models** including those with an order of magnitude more parameters (Table 2). This is the paper's strongest general-code claim. The model also achieves 95.5% on CRUXEval Output-COT (Table 2), again the highest open-weight score, confirming that thinking capability transfers to code execution tracing.

However, the results are not uniformly positive. On code generation benchmarks (Table 1), InCoder-32B-Thinking scores 95.1% on HumanEval and 89.6% on HumanEval+, which is competitive with the non-thinking InCoder-32B (94.5%/89.6%) but below Qwen3-235B-A22B-Thinking (98.8%/93.3%) and Kimi-K2-Thinking (98.2%/92.7%). On MBPP+, the thinking variant scores 92.1% versus 91.8% for the non-thinking variant — a marginal improvement. On BigCodeBench Full (78.3%) and Hard (47.4%), the thinking model is essentially tied with its non-thinking counterpart (78.3%/49.8%). The paper acknowledges this pattern:

> "a moderate trade-off appears on benchmarks that favor concise responses (e.g., Mercury, Text2SQL), a pattern shared by other thinking-augmented systems."

This trade-off is visible in Table 2: InCoder-32B-Thinking scores 62.4% on Mercury Beyond@1 (vs. 71.4% for the non-thinking version), and 47.9% on Bird (vs. 55.4% for non-thinking). The thinking model underperforms the non-thinking baseline on efficiency and text-to-SQL tasks, which the paper attributes to thinking models generating longer responses that may be penalized by benchmarks favoring concise outputs.

On agentic coding (Table 3), InCoder-32B-Thinking achieves 70.4% on SWE-bench Verified, slightly below the non-thinking InCoder-32B at 74.8% — the only benchmark where the thinking variant shows a meaningful regression. The paper does not comment on this specific drop, but it is consistent with the pattern of thinking models underperforming on tasks where multi-turn interaction already distributes reasoning across turns (see Figure 6: agentic coding has the shortest median thinking length at 91 characters, suggesting the thinking format may be redundant or counterproductive for tasks structured as many short interaction steps).

On tool use (Table 3), InCoder-32B-Thinking achieves 63.9% on BFCL V3 and 95.6% on τ2-bench Retail, both strong results. The τ2-bench Retail score is the highest reported among all models (the next best is 96.2% from DeepSeek-V3.2 on Telecom, a different domain), and the 62.0% on Mind2Web is competitive.

**Key pattern**: The thinking model's advantage is concentrated in benchmarks requiring deep reasoning (LiveCodeBench, CRUXEval) rather than broad code generation or efficiency. This aligns with the paper's framing — the thinking traces teach diagnostic reasoning, which transfers to competitive programming and execution tracing, but does not improve (and may slightly degrade) performance on tasks where concise solution generation is optimal.

#### Industrial Code Benchmarks: Broadly Competitive, Domain-Specific Breakthroughs

**Chip design (Table 4).** On VeriScope, InCoder-32B-Thinking achieves 75.4, which is lower than the non-thinking InCoder-32B (80.7) and several baselines (Claude-Sonnet-4.6: 87.7; GLM-5: 83.2; Kimi-K2-Instruct: 82.4; GPT-OSS-120B: 82.2). This is an unexpected regression — for a benchmark measuring Verilog generation correctness, the thinking variant underperforms the instruct variant by 5.3 points. The paper does not offer an explanation, but the adaptive thinking depth analysis in Figure 6 shows that chip design has an inverted profile (1.5K thinking characters, 6.9K answer characters), suggesting that Verilog generation requires extensive code output with relatively brief diagnostic reasoning, and the thinking format may misallocate tokens toward reasoning at the expense of code quality.

On VeriRepair, InCoder-32B-Thinking achieves 83.3% Fix, which is the second-best open-weight result behind GLM-5 (90.0%) and tied with Claude-Sonnet-4.6 and Kimi-K2.5 (both 83.3%). This is a 3.3 point improvement over the non-thinking InCoder-32B (80.0%), suggesting that diagnostic reasoning helps specifically for error repair tasks — exactly what the ECoT synthesis framework is designed to teach.

On RealBench, InCoder-32B-Thinking achieves **75.6 module-level Syn@1, the best open-weight result** and substantially ahead of the next-best model (Kimi-K2-Instruct at 50.1). The module-level Syn@5 (82.4), module-level Func@1 (63.1), and Func@5 (69.8) are all top-tier open-source scores. However, the system-level metrics show a regression: ArchXBench performance (3.12 for n, 46.7 for t) is below the non-thinking InCoder-32B (3.4/51.0) and substantially below Claude-Sonnet-4.6 (4.4/58.2). This pattern — strong module-level performance, weaker system-level performance — is consistent with the thinking traces being generated from module-sized tasks in D_real (RealBench construction provides module-level subtasks) and may not adequately cover system-level integration reasoning.

**GPU kernel optimization (Table 5).** On KernelBench, InCoder-32B-Thinking achieves 20.2% on L1, **38.0% on L2, and 12.0% on L3**. The L2 result is a standout: it is the best among all evaluated models, substantially ahead of Claude-Sonnet-4.6 (28.0%), GLM-5 (23.0%), and Kimi-K2.5 (23.0%). This is the paper's strongest industrial result by margin and directly supports the claim that thinking grounded in GPU execution feedback teaches effective kernel fusion optimization. The L1 result (20.2%) is slightly below the non-thinking InCoder-32B (22.2%), possibly because single-operator kernels (L1 tasks) do not require the multi-step diagnostic reasoning that thinking enables — the non-thinking model's advantage on simpler kernel tasks mirrors the general-code pattern where thinking provides less benefit on straightforward generation.

On TritonBench, results are mixed: G-call at 15.2% (below DeepSeek-V3.2 at 19.6% and Qwen3-Coder-480B at 20.1%), G-exe at 100% (perfect, tied with several models), T-call at 22.9% (competitive with top models), and T-exe at 89.5% (below GLM-5 at 100% and Kimi-K2.5 at 84.8%, but above many baselines). The perfect G-exe score is notable — it suggests that when the model can generate executable Triton code (which is rare, at 15.2% call rate), that code is always functionally correct. This "low recall, high precision" pattern is characteristic of models that are conservative in generation but accurate when they succeed.

**Code optimization and embedded systems (Table 5).** On SuperCoder, InCoder-32B-Thinking achieves 47.9% accuracy and **3.93× speedup**, which is the best speedup among all evaluated models including proprietary Claude-Sonnet-4.6 (4.6× — wait, actually Claude-Sonnet-4.6 reports 4.6× speedup, which is higher than 3.93×) and substantially ahead of the non-thinking InCoder-32B (1.3×). The accuracy of 47.9% is below Claude-Sonnet-4.6 (79.0%) and GLM-5 (90.2%), but the combination of moderate accuracy and high speedup suggests the model is making aggressive optimizations that sometimes violate correctness — a classic speed-vs-safety tradeoff. On EmbedCGen, InCoder-32B-Thinking achieves 51.0% Main, which is the second-best open-source result behind GLM-5 (89.6%) and above Claude-Sonnet-4.6 (46.0%). The non-thinking InCoder-32B scored 35.2%, so the thinking variant shows a 15.8 point improvement — one of the larger gains from thinking data.

**3D modeling (Table 5).** On CAD-Coder, InCoder-32B-Thinking achieves **84.0% compilation rate, the highest among all evaluated models** including Claude-Sonnet-4.6 (77.0%). The IoU of 48.6% is substantially above all open-weight models (GLM-5: 18.8% is the next best; Kimi-K2.5: 12.1%) and above Claude-Sonnet-4.6 (32.4%). This is the paper's second-strongest industrial result and directly supports the claim that thinking outperforms proprietary models on specialized industrial tasks. However, the non-thinking InCoder-32B achieves 82.0% compilation and 53.5% IoU — the thinking variant improves compilation rate but *degrades* IoU by 4.9 points. This tradeoff (higher probability of generating executable code, but somewhat lower geometric fidelity) is not discussed in the paper.

**Synthesis across domains.** The two domains where InCoder-32B-Thinking achieves clear best-in-class results are KernelBench L2 (GPU kernel fusion) and CAD-Coder (3D modeling compilation). These domains share a common characteristic: they require multi-step reasoning about physical/geometric constraints — shared memory budgets and warp configurations for GPU kernels, manifold validity and Boolean operation outcomes for CAD geometry. The domains where the thinking variant underperforms the instruct variant — VeriScope (Verilog generation), Mercury (code efficiency), SWE-bench Verified (software engineering) — are those where the primary challenge is generating correct code in a single pass rather than iteratively diagnosing and revising. This pattern supports the paper's implicit claim that thinking is most valuable when the task *inherently requires diagnostic iteration*, but it also reveals a limitation: for tasks that can be solved without iteration, the thinking overhead may be counterproductive.

#### ICWM Fidelity Results

These results were covered in the Technical Approach section (3.4) because they validate a core design assumption. In summary: Figure 5 reports **mean outcome prediction accuracy of 96.7%** and **mean trajectory agreement of 94.4%** across five domains on 2,000 held-out execution turns per domain. Chip design achieves the highest fidelity (97.4%/95.8%); 3D modeling the lowest (95.9%/93.1%). The consistent 1.6–2.8 percentage point gap between per-turn and end-to-end metrics is attributed to error compounding across multi-turn trajectories.

#### Thinking Data Scaling Analysis

Figure 7 visualizes performance on nine industrial benchmarks as thinking training data scales from 180M to 540M tokens, measured at three checkpoints. The paper reports:

> "As shown in Figure 7, most metrics improve steadily as the amount of thinking data grows. This proves that the thinking process is a strong driver for core industrial coding skills."

Key quantitative changes from 180M to 540M tokens:
- VeriScope Score: 61.8 → 75.4 (+13.6 points)
- VeriRepair Fix: ~72 → ~82 (+10 points, estimated from figure)
- RealBench Syn@1 (System): ~18 → ~20 (modest improvement)
- RealBench Syn@1 (Module): ~55 → ~76 (+21 points, the largest relative gain)
- CAD-Coder Comp.: ~77 → ~84 (+7 points)
- EmbedCGen Main: ~44 → ~47 (+3 points, modest)
- SuperCoder Acc.: ~80 → ~48 (significant *decrease* — from figure, estimated)
- SuperCoder Spd.: ~3.0× → ~3.9× (modest speedup improvement)
- KernelBench L2: 16.0 → 38.0 (+22.0 points)
- KernelBench L3: remains at 12.0 (no improvement)

The paper acknowledges two metrics that stay flat:

> "TritonBench GPU execution correctness stays at a perfect 100 across all three stages. This shows that the thinking ability helps the model quickly master basic execution tasks. Similarly, the KernelBench L3 score remains at 12.0. This suggests that solving the hardest optimization problems requires specific strategies, not just more data volume."

The SuperCoder accuracy decrease (estimated from Figure 7 as dropping from ~80% to ~48% while speedup increases from ~3.0× to ~3.9×) is not explicitly discussed in the text but is visible in the visualization. This suggests that more thinking data leads the model to make more aggressive optimizations that sacrifice correctness — a tradeoff that may be undesirable depending on the deployment context.

**Interpretation.** The scaling analysis demonstrates that thinking data is productive for most industrial benchmarks, with particularly large gains on RealBench module-level tasks (+21 points) and KernelBench L2 (+22 points). However, the flat or negative trends on some metrics (KernelBench L3, SuperCoder accuracy, ArchXBench n) indicate that scaling thinking data alone does not solve all industrial challenges. The paper's characterization — "a highly reliable engine for unlocking deep reasoning skills" — is supported for the metrics that improve, but the qualifier "most" before "metrics improve steadily" is important: the improvements are selective, not universal.

### Ablation Studies and Robustness Checks

**Non-thinking InCoder-32B vs. InCoder-32B-Thinking (implicit ablation of thinking data).** The most important ablation is the comparison between InCoder-32B (no thinking) and InCoder-32B-Thinking (with ECoT-synthesized thinking data) across all benchmarks in Tables 1–5. This comparison isolates the effect of thinking data, since both models share the same base architecture and pretraining. Key findings: thinking improves LiveCodeBench V5 from 53.3% to 81.3% (+28.0 points) — the largest gain on any general benchmark; improves CRUXEval Output-COT from 73.9% to 95.5% (+21.6 points); improves RealBench module Syn@1 from 74.8% to 75.6% (+0.8 points, minimal); improves KernelBench L2 from 22.2% to 38.0% (+15.8 points); improves CAD-Coder compilation from 82.0% to 84.0% (+2.0 points); *degrades* SWE-bench Verified from 74.8% to 70.4% (−4.4 points); degrades VeriScope Score from 80.7 to 75.4 (−5.3 points); degrades Mercury Beyond@1 from 71.4% to 62.4% (−9.0 points). The pattern confirms that thinking data helps most on reasoning benchmarks and industrial debugging tasks, but can hurt on tasks requiring concise generation or multi-turn interaction where thinking overhead is redundant.

**Domain tag and output template design for ICWM.** The paper states that a single ICWM serves all four industrial domains via domain tags and domain-specific output templates (subsection 2.3). No ablation is reported comparing this unified approach to separate per-domain world models, leaving open the question of whether multi-task training helps or hurts individual-domain fidelity. The per-domain fidelity results in Figure 5 (chip design 97.4%, GPU kernels ~96.5%, embedded systems ~96.2%, code optimization ~97.1%, 3D modeling 95.9%) show some variation but do not indicate whether a chip-design-only ICWM would exceed 97.4% or a 3D-modeling-only ICWM would exceed 95.9%.

**K=4 correction rounds.** The choice of maximum 4 correction rounds is stated but not ablated. No results compare trajectories with K=2, K=4, or K=8 to determine whether deeper trajectories produce better thinking models or whether diminishing returns set in. The adaptive thinking depth distribution in Figure 6 shows that GPU kernel optimization produces the longest thinking traces (median 19K characters), suggesting that K=4 may be insufficient for the most complex GPU tasks that require more than 4 rounds to converge — these trajectories would terminate in failure and contribute only failure-mode data, not successful diagnostic patterns.

**ICWM audit mechanism and frequency.** The paper describes periodic real-execution audits to keep the ICWM calibrated but provides no ablation studying audit frequency (e.g., every 1K vs. 10K vs. 100K synthesized trajectories) or the impact of audits on downstream thinking model performance. Without this, the practical reliability of the ICWM-driven amplification over extended synthesis runs remains unquantified.

**Prompt router design.** The prompt router selects domain-specific generation instructions before code generation. No ablation compares this domain-aware prompting to a generic prompting baseline, so the contribution of the prompt router to trajectory quality cannot be separated from the contribution of the ECoT framework itself.

**Edit-distance-based pairing for revision training.** The paper references (in the prior InCoder-32B work) that incorrect-to-correct answer pairing uses character-level edit distance to select the "closest" incorrect answer for revision training. No ablation compares edit-distance pairing to random pairing, leaving open the question of whether this design choice matters for thinking trace quality. Given that ECoT synthesis produces multi-turn trajectories from generator revisions (not post-hoc pairing), this ablation would apply to the revision training component of the prior InCoder-32B pipeline, not directly to the thinking data — but the paper's Results section includes both.

**Comparison of ICWM-generated vs. real-execution trajectories.** The paper reports ICWM fidelity against held-out real execution data (Figure 5), but does not ablate whether a thinking model trained *only* on D_real (no ICWM amplification) would perform differently from one trained on D_real ∪ D_ICWM. This is a significant omission: the central claim that ICWM enables "large-scale synthesis" implicitly assumes that ICWM-generated data is as valuable as real-execution data for training, but this assumption is never tested. The 94.4% trajectory agreement suggests that 5.6% of ICWM trajectories contain at least one mispredicted execution outcome — whether these erroneous trajectories harm or merely fail to help the thinking model is unknown.

**Negative result: ReST^EM training degrades revision model.** While this ablation appears in the prior InCoder-32B paper (Appendix K, referenced in the related work of this paper), it is relevant context: an attempt to optimize the revision model using ReST^EM caused substantial degradation in sequential revision performance, with fully sequential revisions dropping from ~38.5% to ~33.5% at 256 generations. The paper attributes this to on-policy data collection amplifying spurious correlations. This negative result is not reproduced or discussed in the current paper's evaluation of InCoder-32B-Thinking.

### Critical Assessment

The paper makes several central claims that can be evaluated against the reported experiments. I examine each in turn.

**Claim: "InCoder-32B-Thinking achieves 81.3% on LiveCodeBench V5, the highest among all open-weight models."**

This claim is **directly supported** by Table 2. The 81.3% score exceeds every open-weight model listed, including DeepSeek-V3.2 (not reported for V5), Qwen3-235B-A22B-Thinking (80.2%), and all 6B-30B models. However, the LiveCodeBench V5 column in Table 2 has several blank entries for strong models (DeepSeek-V3.2: dash; Kimi-K2-Thinking: dash; GLM-4.7: dash), which means the comparison set is incomplete. The V6 column (where more models report scores) shows InCoder-32B-Thinking at 77.1%, which is higher than Qwen3-235B-A22B-Thinking (74.1%) and GLM-4.7 (84.9% — actually GLM-4.7 scores higher at 84.9% on V6). So the "highest among all open-weight models" claim holds for V5 specifically but not for V6, where GLM-4.7 reports a higher score. The claim is accurate as stated but context-dependent on the benchmark version.

**Claim: "Top-tier open-source results across chip design, GPU optimization, embedded systems, and 3D modeling."**

This claim is **selectively supported**. On GPU kernel optimization (KernelBench L2 at 38.0%) and 3D modeling (CAD-Coder compilation at 84.0%, IoU at 48.6%), InCoder-32B-Thinking is indeed best-in-class among open-weight models, surpassing not only all open-source models but also Claude-Sonnet-4.6 on CAD-Coder. On chip design, the results are mixed: RealBench module-level Syn@1 (75.6) is the best open-weight score, but VeriScope Score (75.4) is substantially below the non-thinking InCoder-32B (80.7) and several baselines, and ArchXBench metrics (3.12/46.7) are middling. On embedded systems, EmbedCGen Main (51.0%) is strong but far below GLM-5 (89.6%). The phrase "top-tier" is defensible — the model is competitive with the best open-weight models across all domains — but "best" would be inaccurate, since no single model is uniformly best across all industrial benchmarks. The distinctive contribution is breadth, not peak single-domain performance.

**Claim: "Thinking models grounded in learned environment dynamics are key to real-world industrial code intelligence."**

This is the paper's central thesis, and the evidence is **circumstantial rather than causal**. The experiments show that (a) InCoder-32B-Thinking performs well on industrial benchmarks, and (b) the ICWM achieves high fidelity in predicting execution outcomes. However, no experiment directly tests the causal claim that *the ICWM specifically* (as opposed to any form of execution-grounded reasoning data) is responsible for the performance gains. To test this, one would need to compare: (1) a thinking model trained only on D_real (real execution trajectories, no ICWM amplification) vs. (2) a thinking model trained on D_real ∪ D_ICWM (the paper's actual model) vs. (3) a thinking model trained on D_ICWM with no real execution data. This ablation would isolate the contribution of ICWM-amplified data and test whether ICWM fidelity (94.4% trajectory agreement) is sufficient for training. The paper does not report this comparison.

What the experiments *do* demonstrate is narrower: that ECoT-synthesized thinking data (produced by a pipeline that happens to include an ICWM) improves industrial performance relative to no thinking data. Whether the ICWM component specifically is necessary, or whether the same improvements could be achieved by simply scaling up real-execution trajectory collection (at higher cost), is an open question.

**Claim: "Scaling thinking data from 180M to 540M tokens yields consistent industrial improvements."**

This claim is **supported with qualifications**. Figure 7 shows that most metrics improve from 180M to 540M tokens, with the largest gains on VeriScope (+13.6 points), RealBench module Syn@1 (+21 points, estimated), and KernelBench L2 (+22 points). The word "consistent" in the paper's text is modified by "most metrics improve steadily," which acknowledges that not all metrics improve. The flat metrics (KernelBench L3 at 12.0, TritonBench G-exe at 100) and the declining metric (SuperCoder accuracy, from ~80% to ~48% estimated from figure) are explicitly noted. The claim would be stronger with confidence intervals — at a sample size of three checkpoints, the trend for metrics with small absolute changes (e.g., EmbedCGen Main from ~44% to ~47%) is not robustly distinguishable from noise.

**Claim: "Thinking can compensate for model scale" (implied by comparisons against larger models).**

While not stated as an explicit bullet-point claim, the paper repeatedly highlights that InCoder-32B-Thinking at 32B parameters outperforms much larger models (e.g., Qwen3-Coder-480B, DeepSeek-V3.2 at 671B, Claude-Sonnet-4.6). This claim is **supported on specific benchmarks but not generalizable**. On LiveCodeBench V5, the 32B model beats 480B and 671B models — strong evidence for compensation on competitive programming. On KernelBench L2, it beats all larger models — strong evidence for GPU kernel fusion. On CAD-Coder, it beats all models including proprietary — strong evidence for 3D modeling. However, on SWE-bench Verified, the 32B model (70.4%) is substantially below DeepSeek-V3.2 (73.1%) and GLM-4.7 (73.8%), and on VeriScope it is below GPT-OSS-120B (82.2) and GLM-4.7 (81.2). The compensation claim is domain-dependent: thinking helps on tasks where diagnostic iteration is the primary challenge (kernel optimization, geometry debugging, competitive programming), but not on tasks where breadth of code knowledge or multi-turn interaction competence is more important (software engineering, Verilog generation). The paper does not characterize these boundary conditions, presenting the scale-compensation results as if they are general rather than selective.

**Weaknesses and missing experiments.**

1. **No ablation of D_real vs. D_ICWM**: The most important missing ablation, as discussed above. Without it, the ICWM's contribution to model performance is asserted rather than demonstrated.

2. **No confidence intervals or statistical tests**: All benchmark results are point estimates without variance. For benchmarks with small test sets (KernelBench: 250 problems; RealBench: 64 subtasks; VeriRepair: 300 test samples), differences of a few percentage points may not be statistically significant. The 0.8-point improvement on RealBench module Syn@1 (74.8% → 75.6%) could easily be noise.

3. **No audit frequency ablation**: The ICWM periodic audit mechanism is described but never tested. How many audits are needed to maintain 94.4% trajectory agreement over long synthesis runs? Does audit frequency affect downstream model performance?

4. **No K (correction rounds) ablation**: The choice of K=4 is stated but not justified empirically. Would K=2 produce thinking traces that are nearly as good at half the real-execution cost? Would K=8 enable solving harder tasks that K=4 leaves unfinished?

5. **Single generator model (DeepSeek-V3.2)**: All trajectories are generated by one teacher model. The paper does not test whether trajectory quality depends on the generator's capability, or whether a weaker generator (e.g., the non-thinking InCoder-32B itself) would produce useful trajectories at lower cost.

6. **No separation of ECoT from general thinking benefits**: The thinking model is compared to the non-thinking InCoder-32B, but not to a hypothetical "InCoder-32B with generic chain-of-thought training" (e.g., trained on distilled thinking traces from a general coding teacher without execution grounding). Without this comparison, the specific contribution of execution grounding (ECoT) versus general chain-of-thought training cannot be isolated.

7. **Benchmark-specific evaluation protocols are inconsistent**: Different industrial benchmarks use different numbers of samples (k=20 for RealBench, k=5 for ArchXBench, single-sample for others), different selection mechanisms, and different metrics. The paper does not discuss whether these protocol differences affect model comparisons — e.g., a model that benefits from multiple samples (because it is high-variance but sometimes excellent) would look better on RealBench (k=20) than on ArchXBench (k=5), potentially confounding cross-benchmark comparisons.

8. **No latency or throughput evaluation**: The thinking model generates thinking blocks before answering, which adds inference time. The paper does not report thinking length statistics at inference time or compare end-to-end latency against the non-thinking model. For deployment, this tradeoff matters — a 28-point improvement on LiveCodeBench might not justify a 10× increase in tokens generated if latency is critical.

9. **Single model family**: All experiments use the InCoder-32B base architecture. The paper does not test whether ECoT synthesis benefits other base models (e.g., applying the same pipeline to Qwen or DeepSeek base models), so the generalizability of the approach across architectures is unknown.

**Summary.** The experiments provide strong evidence that ECoT-synthesized thinking data improves performance on industrial benchmarks that require multi-step diagnostic reasoning, and that these improvements scale with thinking data volume for most (but not all) metrics. The evidence for the ICWM specifically — as opposed to execution-grounded thinking data in general — is weaker, since the ICWM's contribution to model quality was not directly ablated. The paper's strongest empirical contributions are the benchmark results on KernelBench L2 and CAD-Coder (where InCoder-32B-Thinking achieves clear best-in-class performance) and the demonstration that thinking data scaling produces consistent gains on industrial tasks. The paper's central causal claim — that a learned world model of execution environments is necessary for these gains — remains an intriguing hypothesis supported by the ICWM's high fidelity but not directly tested by the reported experiments.

## 6. Limitations and Trade-offs

### 6.1 The ICWM's Contribution to Model Quality Is Asserted, Not Demonstrated

**The assumption or constraint.** The paper positions the Industrial Code World Model (ICWM) as a core innovation — a learned proxy that "enables large-scale simulation without repeated access to real backends" (Section 2) and "amplifies reasoning data at scale" (Abstract). The implicit claim is that ICWM-generated trajectories (`D_ICWM`) are necessary for the model's strong industrial performance, because real execution alone would be too expensive to produce sufficient training data. However, the paper never tests this claim directly. The final reasoning corpus is `D = D_real ∪ D_ICWM` (Section 2.3), and all model checkpoints (180M, 360M, 540M tokens) are trained on this combined data. There is no ablation comparing a model trained *only* on `D_real` against one trained on the combined corpus.

**The consequence.** Without this ablation, the paper cannot distinguish between two hypotheses: (1) the ICWM is essential — `D_real` alone is too small to teach industrial reasoning, and the ICWM's amplification is what makes thinking-model training viable; or (2) the ICWM is incidental — the same improvements could be achieved by collecting more real-execution trajectories, and the ICWM is merely a cost-reduction mechanism, not a capability-enabling one. A practitioner deciding whether to adopt this method needs to know whether building, training, and maintaining an ICWM is *necessary* or merely *convenient*. If `D_real` alone (which any practitioner with access to execution backends can collect) is sufficient, the substantial engineering effort of implementing the ICWM pipeline is unjustified.

A secondary consequence concerns data quality: the ICWM achieves 94.4% trajectory agreement (Section 4.1, Figure 5), meaning approximately 5.6% of `D_ICWM` trajectories contain at least one mispredicted execution outcome. Whether these erroneous trajectories harm the thinking model — by teaching it to respond to incorrect diagnostic feedback — or are simply ignored during training is unknown. The 3D modeling case study (Section 4.1) demonstrates a concrete false positive: the ICWM predicts PASS for a CadQuery script that real execution rejects with GEOMETRY_ERROR due to a degenerate zero-thickness edge. A model trained on this trajectory would learn that plausible-looking but geometrically invalid code passes verification — precisely the wrong lesson.

**What evidence exists in the paper.** The ICWM fidelity analysis (Section 4.1, Figure 5) validates that the world model is *accurate* (96.7% per-turn, 94.4% trajectory-level), but does not test whether exposure to ICWM-generated trajectories during training *improves* the thinking model relative to training only on real-execution trajectories. The scaling analysis (Section 4.3, Figure 7) shows that increasing total thinking data from 180M to 540M tokens improves performance, but this conflates two variables: data quantity (more tokens) and data source composition (what fraction comes from ICWM vs. real execution at each checkpoint). The per-domain ICWM fidelity varies from 93.1% (3D modeling) to 95.8% (chip design), and the CAD-Coder results (84.0% compilation, 48.6% IoU) — where the ICWM is least reliable — do not show evidence of degradation from ICWM errors specifically, but this is because no comparison to a real-execution-only baseline exists.

**Mitigation status.** The paper does not address this limitation. No ablation of `D_real` vs. `D_real ∪ D_ICWM` is reported, and this is not flagged as future work. The periodic audit mechanism (Section 2.3) provides a safeguard against ICWM calibration drift by retraining the world model when real-execution spot checks detect mismatches, but this addresses the accuracy of the ICWM itself, not the impact of ICWM errors on downstream model training. A practitioner must take on faith that ICWM-generated data is net-beneficial for training, despite containing demonstrable errors.

### 6.2 The Cost of Difficulty-Driven Thinking at Inference Time Is Unaccounted For

**The assumption or constraint.** The paper's adaptive thinking depth property — the model learns to produce reasoning traces whose length is proportional to task difficulty, spanning a 209× range from 91 to 19,015 characters (Section 4.2, Figure 6) — is presented as a strength. However, the paper reports only benchmark accuracy, never inference cost or latency. The thinking format (THINK blocks followed by ANSWER blocks, visualized in Figure 1) means that the model generates potentially thousands of tokens of reasoning before producing executable code. For industrial tasks that demand deep reasoning (GPU kernel optimization: median 19,015 thinking characters), this adds substantial inference-time overhead compared to a non-thinking model that directly generates code.

**The consequence.** A practitioner deploying InCoder-32B-Thinking in a latency-sensitive industrial setting faces an unquantified tradeoff. The paper shows that thinking improves KernelBench L2 from 22.2% to 38.0% (+15.8 points) and CAD-Coder compilation from 82.0% to 84.0% (+2.0 points), but it does not report how many additional tokens are generated per problem to achieve these gains. For GPU kernel optimization, where thinking traces are 19K characters median, a typical inference might generate 5,000–10,000 tokens of reasoning before producing the kernel code — approximately 10–20× the token count of a direct code generation approach. If inference latency scales linearly with tokens generated, this means a 10–20× slowdown per problem.

This matters particularly because industrial code generation is often embedded in iterative development workflows where an engineer runs the model, gets a result, tests it, gets an error, and runs again. A model that takes 30 seconds to produce a kernel (due to extended thinking) versus one that takes 2 seconds may be unacceptable even if its eventual success rate is higher, because the total cycle time (model inference + human review + compilation + testing) is dominated by the inference latency. The paper's implicit assumption — that benchmark accuracy is the only metric that matters — ignores the throughput-latency dimension that determines practical deployability.

Furthermore, the paper's non-thinking baseline (InCoder-32B) outperforms the thinking variant on several benchmarks: VeriScope Score (80.7 vs. 75.4), Mercury Beyond@1 (71.4% vs. 62.4%), SWE-bench Verified (74.8% vs. 70.4%), and CAD-Coder IoU (53.5% vs. 48.6%). On these tasks, the thinking variant is both **slower** (generating unnecessary reasoning tokens) and **less accurate** — a strict Pareto loss. Without latency measurements, a practitioner cannot determine whether the benchmarks where thinking *does* help are worth the slowdown on benchmarks where it *hurts*, or whether a hybrid deployment (non-thinking model for latency-sensitive tasks, thinking model for deep-reasoning tasks) is preferable.

**What evidence exists in the paper.** Figure 6 provides training-corpus statistics on thinking length (median, inter-quartile range per domain), which gives a rough sense of how many reasoning tokens the model *tends* to produce, but this is training data distribution, not inference-time behavior. The paper does not report: inference latency comparisons between InCoder-32B and InCoder-32B-Thinking, tokens-per-query statistics at inference time, throughput benchmarks (queries per second), or any cost-adjusted accuracy metric (e.g., accuracy per 1,000 tokens generated). The scaling analysis (Section 4.3) measures performance vs. training data volume, not inference compute.

**Mitigation status.** The paper does not discuss inference latency, does not propose a mechanism for controlling thinking depth at inference time (e.g., a budget token limit or early stopping), and does not acknowledge this as a limitation. The adaptive thinking depth property is framed entirely as a benefit (the model avoids over-thinking on easy tasks) without considering the cost of deep thinking on hard tasks. A simple mitigation — limiting the maximum thinking tokens at inference time — is not evaluated.

### 6.3 The Approach Fails to Improve Hardest-Task Performance Despite Scaling Thinking Data

**The assumption or constraint.** The paper claims that scaling thinking data from 180M to 540M tokens "yields consistent industrial improvements" (Section 6) and that the thinking process is a "strong driver for core industrial coding skills" (Section 4.3). However, this claim has a sharp boundary: the hardest problems show no improvement whatsoever from additional thinking data.

**The consequence.** The paper's approach encounters a capability ceiling that additional thinking data does not breach. In Section 4.3, the paper acknowledges:

> "KernelBench L3 score remains at 12.0. This suggests that solving the hardest optimization problems requires specific strategies, not just more data volume."

But this is an understated framing of a deeper limitation. KernelBench Level 3 consists of end-to-end model architectures — tasks like implementing an entire Transformer block or a ResNet backbone as a fused kernel. These are precisely the high-value industrial tasks where automated optimization would have the greatest impact (replacing days of expert engineer time with minutes of model inference). The fact that thinking data scaling produces zero improvement on these tasks (12.0% at both 180M and 540M tokens) suggests that the ECoT synthesis framework may be fundamentally unable to teach the kind of global architectural reasoning that L3 tasks demand. The training trajectories in `D_real` are generated by DeepSeek-V3.2 with up to K=4 correction rounds — if the teacher model itself cannot solve L3-level tasks within 4 rounds, the training data contains no successful L3 trajectories, and the thinking model learns only failure patterns.

A similar pattern appears on other hard-task metrics. ArchXBench `n` — the number of syntactically correct candidates out of 5 — decreases from 3.4 (non-thinking InCoder-32B) to 3.12 (thinking variant, Table 4), and `t` (testbench assertions passed) drops from 51.0 to 46.7. The system-level Verilog tasks in RealBench and ArchXBench require integrating multiple modules into a coherent digital system, which is a different cognitive skill than the module-level diagnosis that ECoT trajectories capture. The SuperCoder accuracy trend in Figure 7 — estimated as dropping from ~80% to ~48% as thinking data scales from 180M to 540M tokens — suggests that more thinking data may actively harm performance on some hard optimization tasks, possibly because the model learns to produce over-aggressive optimizations that sacrifice correctness.

The implication for practitioners: InCoder-32B-Thinking is best deployed on tasks where the base model (or its teacher) already has some non-trivial success rate, so that `D_real` contains successful correction trajectories. For tasks beyond the teacher's capability, the approach provides no benefit and may regress relative to a non-thinking baseline.

**What evidence exists in the paper.** The scaling analysis in Section 4.3 and Figure 7 directly shows KernelBench L3 flat at 12.0% across all three checkpoints, with the paper explicitly noting this. The ArchXBench and SuperCoder regressions are visible in Table 4, Table 5 (comparison to non-thinking InCoder-32B), and Figure 7 (SuperCoder accuracy trend). The paper does not report pass@k statistics for the teacher model (DeepSeek-V3.2) on industrial benchmarks, so the relationship between teacher capability and student performance cannot be directly verified, but the KernelBench L2 result (InCoder-32B-Thinking: 38.0% vs. DeepSeek-V3.2: 3.0% on L1, dash on L2) suggests the teacher's raw performance on industrial tasks is low — supporting the interpretation that the teacher cannot produce successful L3 trajectories for `D_real`.

**Mitigation status.** The paper notes the KernelBench L3 flatness explicitly, characterizing it as a need for "specific strategies, not just more data volume," but does not propose what those strategies might be. No mechanism for breaking through the capability ceiling — such as using a stronger teacher model, increasing K beyond 4 to allow more correction rounds on hard tasks, or incorporating architectural reasoning priors — is discussed or suggested as future work. The flatness is treated as an observation, not as a limitation of the approach that requires remediation.

### 6.4 Evaluation Is Limited to a Single Base Model Architecture and a Single Teacher Model

**The assumption or constraint.** All experiments in the paper use exactly one student architecture (InCoder-32B, a 32B-parameter dense model) and exactly one teacher model for trajectory generation (DeepSeek-V3.2, a 671B-parameter MoE model). The paper's claims about the effectiveness of ECoT synthesis and ICWM-driven amplification are therefore conditioned on this specific teacher-student pair, with no evidence that the approach generalizes.

**The consequence.** A practitioner with a different base model — say, a Qwen-based architecture, a Llama-based model, or a smaller 7B model for resource-constrained deployment — has no guidance on whether ECoT synthesis would produce similarly effective thinking data. The paper's results show that InCoder-32B-Thinking at 32B parameters outperforms many larger models (480B, 671B) on specific benchmarks, but this could be due to an interaction between the InCoder architecture and the ECoT training format, or to the specific teacher-student capability gap (DeepSeek-V3.2 as a strong teacher for a 32B student). A weaker teacher (e.g., a 70B open model) might produce lower-quality trajectories that teach less useful reasoning patterns; a stronger teacher might produce trajectories that are too advanced for a small student to learn from.

A separate concern is that DeepSeek-V3.2 is a closed-source model whose training data and architecture details are not fully public. If DeepSeek-V3.2 was itself trained on industrial code data (the paper's benchmarks show it has non-zero performance on VeriScope, CAD-Coder, etc.), then the ECoT trajectories may contain knowledge *distilled* from the teacher's pretraining rather than *discovered* through the execution-feedback loop. In that case, ECoT synthesis is acting as a distillation mechanism from a stronger closed model, and the approach would not replicate with a teacher that lacks industrial code knowledge. The paper's framing ("Error-driven thinking synthesis") emphasizes the execution feedback as the source of reasoning quality, but the teacher's own capability is a confounding variable that is never isolated.

**What evidence exists in the paper.** Tables 1–5 show DeepSeek-V3.2's performance on benchmarks where it has scores reported, but many industrial benchmark entries are blank (e.g., KernelBench, CAD-Coder compilation, EmbedCGen for DeepSeek-V3.2), making it difficult to assess the teacher's industrial code capability directly. The paper does not ablate the teacher model choice — there is no comparison of trajectories generated by DeepSeek-V3.2 vs. trajectories generated by Qwen3-235B or another strong model, and no experiment applying the same ECoT pipeline to a different student architecture.

**Mitigation status.** The paper does not claim generalization across architectures or teacher models, so this limitation is a scope restriction rather than a failed claim. However, it is a significant practical limitation because the paper's pipeline — task seeding, environment bundling, multi-turn execution, ICWM training — represents substantial engineering investment. A practitioner who wants to adopt the method for their own model family must either (a) assume it transfers, without evidence, or (b) replicate the full pipeline and discover empirically whether it works. The paper does not suggest future work on cross-architecture validation.

### 6.5 The ICWM Fidelity Gap Is Most Severe in Precisely the Domain Where Thinking Helps Most

**The assumption or constraint.** The ICWM's fidelity varies by domain (Section 4.1, Figure 5). The paper reports that 3D modeling has the lowest fidelity: 95.9% outcome prediction accuracy and 93.1% trajectory agreement — a 2.8 percentage point gap from per-turn to end-to-end consistency, the widest across all domains. The case study explains why: CadQuery geometry errors arise from floating-point tolerances and implicit Boolean operation outcomes "whose outcomes are harder to predict from code text alone" — the ICWM, operating purely on text, cannot reliably detect degenerate geometric edge cases.

Simultaneously, 3D modeling (CAD-Coder) is one of the two domains where InCoder-32B-Thinking achieves its strongest results: 84.0% compilation rate (best across all models including proprietary) and 48.6% IoU (best among open-weight models by a wide margin). This means the largest performance gains occur in the domain where the training data synthesis pipeline is least reliable.

**The consequence.** This creates an interpretability problem for the method's mechanism. If the ICWM is frequently wrong about geometric validity (misclassifying GEOMETRY_ERROR as PASS, as in the case study), then a non-trivial fraction of the 3D modeling trajectories in `D_ICWM` contain incorrect execution feedback. The thinking model trained on this data might learn to:
- Trust its initial output when the ICWM predicts PASS, even if a real backend would reject it — explaining the improved compilation rate (the model confidently produces code, some of which happens to compile) but degraded IoU (the generated geometry is less accurate because the model didn't receive corrective feedback on geometric errors).
- Or, conversely, over-correct in response to ICWM-predicted errors that a real backend wouldn't flag, wasting thinking tokens on spurious fixes.

The paper reports that CAD-Coder IoU *decreases* from 53.5% (non-thinking InCoder-32B) to 48.6% (thinking variant), even as compilation rate improves from 82.0% to 84.0% (Table 5). This is consistent with the hypothesis that ICWM errors in the 3D modeling domain are introducing noise that degrades geometric accuracy while boosting the model's willingness to generate (compilable) code. A practitioner deploying the model for CAD generation faces a tradeoff: more generated scripts that run successfully, but with lower geometric fidelity to the specification — and it is unclear whether this tradeoff is inherent to thinking-based training or an artifact of ICWM inaccuracy.

**What evidence exists in the paper.** The ICWM fidelity results (Figure 5) quantify the per-domain accuracy gap, and the case study (Section 4.1) provides a concrete example of a 3D modeling false positive. The CAD-Coder results (Table 5) show the compilation-IoU divergence between thinking and non-thinking variants. However, the paper does not connect these two observations — it does not analyze whether the ICWM fidelity gap in 3D modeling causally contributes to the IoU regression, or whether a higher-fidelity ICWM (e.g., trained on more real-execution data for geometric corner cases) would close the IoU gap.

**Mitigation status.** The periodic audit mechanism (Section 2.3) is partially mitigating: real-execution spot checks detect ICWM errors and the corrected labels are used to retrain the ICWM, "progressively narrowing the gap." However, the paper provides no evidence that this retraining actually improves ICWM fidelity over synthesis rounds or downstream model performance. The audit frequency, the number of spot checks per round, and the retraining protocol are not specified. The fundamental challenge — that text-based prediction cannot fully capture geometric validity — may require a different ICWM architecture for 3D modeling (e.g., incorporating lightweight mesh analysis or voxel-based validation), but this is not discussed.

### 6.6 The Difficulty Estimation Cost for Adaptive Reasoning Is Absorbed Into the Training Pipeline, Not Available at Inference

**The assumption or constraint.** The paper claims that InCoder-32B-Thinking learns to "adaptively calibrate its thinking effort, investing deep multi-step reasoning where complex industrial backends demand it while keeping traces succinct for tasks with short feedback loops" (Section 4.2). This adaptive behavior emerges from the training data distribution — ECoT trajectories naturally vary in length based on how many correction rounds were needed to reach PASS. However, this property exists in the *training data*, not as an explicit mechanism at inference time. The model generates thinking tokens autoregressively; it has no access to execution feedback to determine whether a task is "hard" and therefore warrants deeper reasoning. The adaptation is purely a learned prior: the model has seen that certain patterns of problem specification correlate with longer or shorter thinking traces in training, and it reproduces those patterns at inference.

**The consequence.** This learned adaptation is brittle in ways that explicit difficulty estimation would not be. If the model encounters a problem that *looks* easy (e.g., a short prompt for a simple-sounding kernel) but is actually hard (because the specification has subtle hardware constraints that aren't obvious from the text), the model may allocate too little thinking, fail to diagnose the hidden difficulty, and produce incorrect code. Conversely, a problem that *looks* hard (long specification, complex-sounding task) but is actually straightforward may trigger unnecessarily deep thinking, wasting inference compute. The paper provides no mechanism for the model to **detect that its initial allocation was wrong** — there is no mid-inference execution feedback loop, no "thinking budget" that can be expanded if the model realizes it is stuck, and no dynamic adjustment of thinking depth based on partial progress. The training data shows multi-turn correction trajectories, but at inference time the model produces a single continuous stream of thinking tokens until it decides to output an answer, with no external feedback to validate or correct its reasoning.

This contrasts with approaches that use explicit verifier-guided search or iterative refinement at inference time (as studied in test-time compute scaling literature), where the model can sample multiple solutions, evaluate them with a reward model or execution oracle, and allocate more compute to promising candidates. InCoder-32B-Thinking does none of this — its "adaptivity" is entirely baked into the weights during training and is not responsive to the actual difficulty of the specific problem instance at hand.

A related concern: the paper does not report whether the model's generated thinking traces at inference time would actually *pass* execution if checked. The ECoT training process validates intermediate steps against real backends, ensuring that the training trajectories contain causally correct diagnostic reasoning. But at inference, the model generates thinking autoregressively with no verification — it can produce plausible-sounding diagnostic reasoning that is factually incorrect (e.g., diagnosing a "shared memory overflow" for a kernel that actually has a race condition), and then generate code based on this incorrect diagnosis. The paper provides no evaluation of thinking-trace correctness at inference time, only of final answer correctness on benchmarks.

**What evidence exists in the paper.** The adaptive thinking depth analysis (Section 4.2, Figure 6) shows training-data statistics but nothing about inference-time behavior. The benchmark results report final-answer accuracy, not intermediate reasoning accuracy. There is no experiment where the model is given a problem, its thinking trace is extracted, and that trace is evaluated against execution feedback to check whether the model's self-diagnosis was correct. The case studies (Figure 3 for CUDA kernel implementation, Section 4.1 for GPU kernel diagnosis) show successful examples of reasoning, but these are cherry-picked illustrations, not systematic evaluation.

**Mitigation status.** The paper does not address this limitation. The adaptive thinking depth property is presented as an unqualified strength. The paper does not propose augmenting inference with execution feedback (which would be natural given the ICWM's existence — the ICWM could in principle be used to validate thinking traces at inference time), does not discuss the calibration of thinking depth to actual problem difficulty, and does not suggest future work on closing the loop between inference-time reasoning and execution verification. The ICWM, which could serve as a verification mechanism during inference, is used only during training — a missed opportunity that the paper does not acknowledge.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

This paper introduces a **new methodology for constructing training data** — execution-grounded, multi-turn reasoning trajectories synthesized through iterative error-correction against real toolchains and amplified via a learned world model — rather than a new model architecture or training objective. Its primary intellectual contribution is reframing the challenge of industrial code generation from a capability deficit (models aren't smart enough) to a data distribution deficit (models have never seen examples of how engineers diagnose hardware-level errors). This reframing has concrete consequences for how the field allocates research effort.

**A new data modality for code intelligence.** Prior to this work, the dominant paradigms for code training data were supervised fine-tuning on (problem, correct solution) pairs and reinforcement learning from execution feedback. Both treat execution as an external reward signal — useful for scoring, but not captured as structured training data. The paper introduces a third paradigm: execution-grounded reasoning trajectories where the full causal chain of error → diagnosis → revision → verification is preserved as training text. This is a qualitatively different data type. It does not just tell the model what correct code looks like; it shows the model what the *process of arriving at correct code* looks like, including failed attempts, diagnostic reasoning, and targeted revisions.

The significance of this shift is that it opens a new axis for improving code LLMs that is orthogonal to both scaling parameters and scaling web data. The paper's benchmark results demonstrate that 540M tokens of reasoning data (a tiny fraction of a modern pretraining corpus) can produce performance gains equivalent to what would otherwise require 10–20× more parameters on specific tasks — the 32B thinking model outperforms 480B and 671B models on LiveCodeBench V5 and KernelBench L2. If execution-grounded reasoning traces prove to be a generally effective training modality (not merely a one-off result on these specific benchmarks), it changes the economics of building specialized code models: invest in data synthesis infrastructure (execution backends + world models) rather than in ever-larger pretraining runs.

**Reconciling contradictory findings in thinking-model research.** Prior work on chain-of-thought for code presents a fragmented picture. General thinking models (DeepSeek-R1, QwQ, Qwen3-Thinking) show strong improvements on mathematical reasoning and competitive programming but limited evaluation on hardware-aware tasks. Code-specific thinking models (o1-Coder, rStar-Coder) adapt thinking techniques to programming but rely on self-consistency or reward model scores rather than execution ground truth for verification. Meanwhile, execution-grounded approaches (Self-Refine, LeDex, RLEF) demonstrate that real compiler/simulator feedback improves code generation, but do not capture the diagnostic reasoning that occurs during iterative debugging as reusable training data.

The paper reconciles these threads by showing that thinking and execution grounding are complementary, not alternative, strategies. The ECoT framework produces reasoning traces that are *both* extended chains of thought (like DeepSeek-R1) *and* grounded in real execution outcomes (like RLEF). The key insight is that execution feedback provides the **structure** for thinking traces — the length and complexity of the chain of thought is not determined by an arbitrary budget or by the model's internal dynamics, but by the actual number of correction rounds needed to resolve real errors. This resolves the tension between "thinking is beneficial" (DeepSeek-R1 results) and "thinking without grounding produces plausible-sounding but incorrect reasoning" (known failure mode of self-consistency approaches). When thinking traces are shaped by real compiler errors, they are forced to be causally correct — a diagnosis that misidentifies the error would lead to an incorrect revision that fails on the next execution round, which would itself be captured in the trajectory.

**A learned world model as a data amplification engine.** The paper demonstrates — though without the direct ablation that would make the case airtight — that learning a text-to-text proxy for complex execution backends is feasible and useful. The ICWM achieving 96.7% per-turn outcome prediction accuracy and 94.4% trajectory agreement across 2,000 held-out turns per domain (Figure 5) is a strong empirical result in its own right. It suggests that a relatively simple language model can internalize the causal dynamics of Verilog synthesis, GPU compilation, embedded system simulation, and CAD geometry validation — enough to serve as a reliable substitute for real toolchains in data synthesis pipelines. This is not obvious a priori; one might reasonably expect that predicting GPU compiler errors from code text alone would require simulating shared memory allocation and register pressure, operations that a language model cannot perform. The paper shows that for the purpose of generating training data (where occasional errors are tolerable, and periodic audits provide correction), text-level prediction is sufficient.

This finding has implications beyond this paper's specific pipeline. If execution backends can be approximated by learned text-to-text models at high fidelity, then any code generation task with a verifiable correctness criterion — unit test suites for general code, type-checking for typed languages, SQL query execution, API response validation — could potentially benefit from world-model-driven data amplification. The ICWM is domain-specific in its training data but domain-agnostic in its architecture (a language model with domain tags), suggesting that the approach could be extended to new verification backends without architectural changes.

**Shifting research priorities.** The paper's results suggest that certain research directions become more attractive, while others become less so:

- **More attractive**: Training data synthesis methods that capture the *process* of code development (not just final artifacts), learned proxies for execution environments, multi-turn correction trajectories as a training modality, and unified multi-domain industrial code models. The paper demonstrates that these investments pay off in benchmark performance, and the infrastructure (execution backend bundling, prompt routing, ICWM training) is described in sufficient detail to replicate.

- **Less attractive**: Scaling model parameters as the primary path to industrial code capability. The paper shows that 480B and 671B models achieve near-zero performance on several industrial benchmarks (KernelBench L2, CAD-Coder compilation) while the 32B thinking model achieves 38.0% and 84.0% respectively. This does not mean that scale is irrelevant — it means that scale without execution-grounded reasoning data is insufficient, and that reasoning data at modest scale can outperform pure parameter scaling for specific task families. For practitioners with limited compute budgets, investing in data synthesis infrastructure is likely higher-ROI than renting more GPUs for pretraining.

- **Conditionally more attractive**: Single-domain industrial code models vs. unified models. The paper's unified model achieves strong results across all four industrial domains, but does not demonstrate that a unified approach is *better* than four domain-specific models trained on the same ECoT data. This remains an open question — the paper shows unification is viable, not that it is optimal. Researchers interested in peak single-domain performance (e.g., the best possible Verilog model) may still prefer domain-specific architectures, but the burden of proof has shifted: the default assumption can no longer be that separate models are necessary.

### Follow-Up Research This Work Enables

**Ablation of D_real vs. D_ICWM training data to isolate the ICWM's causal contribution.** The paper's most significant unvalidated claim is that the ICWM is necessary (not merely convenient) for the thinking model's performance. A direct experiment would train three models: (1) on `D_real` only (real execution trajectories, no ICWM), (2) on `D_real ∪ D_ICWM` (the paper's actual configuration), and (3) on an equivalent token budget of `D_real` data artificially upsampled to match the total token count of configuration 2. If model 2 substantially outperforms model 3, the ICWM contributes genuine training signal beyond what real-execution data alone provides. If model 2 ≈ model 3, the ICWM is a cost-reduction mechanism but not a capability-enabling one. If model 1 ≈ model 2, the ICWM contributes nothing and can be eliminated. This experiment would resolve the paper's central causal ambiguity and is feasible with the existing pipeline — it requires only training additional checkpoints on data subsets.

**Dynamic ICWM-guided inference-time verification and correction.** The paper trains an ICWM that predicts execution outcomes but uses it only during training data synthesis, not during inference. A natural extension is to close the loop at inference time: given a problem, have the thinking model generate a reasoning trace and candidate code, run the ICWM to predict the execution outcome, and if the outcome is an error, feed the predicted diagnostic back to the model for a revision — effectively replicating the ECoT synthesis loop at inference time without real toolchains. This would give the model the ability to **iterate on its own output** using the same diagnostic reasoning patterns it learned during training. The key evaluation would be whether ICWM-guided iteration at inference improves pass rates beyond single-pass thinking, and whether the ICWM's fidelity (94.4% trajectory agreement) is sufficient for this purpose or whether inference-time errors compound differently than training-time errors. The existing ICWM architecture (text-to-text, domain-tagged) already supports this use case — the implementation requires only an inference loop around the thinking model + ICWM pair.

**Scaling K (correction rounds) beyond 4 to probe the capability ceiling for hard tasks.** The paper's most important negative result is that KernelBench L3 (end-to-end model architectures) shows zero improvement from thinking data scaling (12.0% at all three checkpoints, Figure 7). The paper attributes this to L3 tasks requiring "specific strategies, not just more data volume" but does not test whether the fundamental limitation is that K=4 correction rounds are insufficient for DeepSeek-V3.2 to solve L3 tasks within `D_real`. A diagnostic experiment would sweep K from 4 to 8 to 16 on a subset of hard industrial tasks, measuring whether the teacher model's success rate increases with more correction rounds. If DeepSeek-V3.2 *can* solve L3 tasks given more rounds, then the bottleneck is K (fixable by increasing the correction budget), and the thinking model should eventually learn L3 strategies when trained on deeper trajectories. If DeepSeek-V3.2 *cannot* solve L3 tasks even with many rounds, the bottleneck is teacher capability (requiring a stronger generator or fundamentally different training approach). This experiment would distinguish between "the method fails on hard tasks because we didn't let it try long enough" and "the method fails on hard tasks because the teacher doesn't know how."

**Cross-architecture replication: applying ECoT + ICWM to a different base model family.** The paper's results are confined to the InCoder-32B architecture. To test whether ECoT synthesis is a general methodology or an architecture-specific recipe, replicate the pipeline with a different base model — for example, applying the same D_real trajectories (generated by DeepSeek-V3.2) to fine-tune Qwen2.5-Coder-32B-Instruct or a Llama-based code model into a thinking variant. If the resulting models show similar industrial benchmark improvements relative to their non-thinking counterparts, ECoT synthesis is a general data methodology. If the improvements are architecture-specific (e.g., InCoder's Code-Flow pretraining enables better utilization of thinking data than standard autoregressive pretraining), the paper's claims need to be scoped accordingly. This experiment also tests whether the teacher-student capability gap (DeepSeek-V3.2 → student) matters: if a weaker student architecture fails to learn from the same trajectories, the approach requires sufficiently capable base models.

**Training the ICWM on human-written execution diagnostics to improve fidelity in challenging domains.** The paper identifies 3D modeling as the domain where the ICWM is least reliable (95.9% outcome accuracy, 93.1% trajectory agreement, Figure 5) because geometric corner cases like degenerate zero-thickness edges are "harder to predict from code text alone." A targeted experiment would augment the ICWM training data with human-written explanations of *why* certain CadQuery scripts produce geometry errors — for example, annotating the zero-thickness edge case with "tangent placement creates non-manifold edge; offset the cylinder axis by at least 0.01 mm from the face." This would test whether the ICWM's limitation is fundamental (text cannot capture geometric validity) or data-driven (the model has not seen enough examples of the mapping between code patterns and geometric failure modes). If human-curated diagnostic examples improve ICWM fidelity on geometric corner cases, the periodic audit mechanism could be augmented with targeted human annotation for the lowest-fidelity error categories, creating a human-in-the-loop improvement cycle. This experiment connects to broader questions about whether learned world models can eventually replace simulation for physical reasoning tasks or whether certain domains inherently require numerical simulation.

**Measuring and mitigating the thinking-vs-latency tradeoff for deployment.** The paper reports benchmark accuracy but never inference cost. A systematic characterization would measure end-to-end latency and tokens-per-query for InCoder-32B-Thinking versus InCoder-32B across all industrial benchmarks, producing a scatter plot of accuracy improvement vs. latency overhead per task category. This would enable practitioners to make informed decisions about which tasks justify the thinking overhead. A follow-up experiment would test simple mitigation strategies: (1) a "thinking budget" where the model is limited to a maximum number of thinking tokens before being forced to produce an answer, and accuracy is measured as a function of the budget; (2) a hybrid deployment where a lightweight classifier (similar to the prompt router in Section 2.1) estimates task difficulty from the prompt and routes easy tasks to the non-thinking model and hard tasks to the thinking model, optimizing the accuracy-latency Pareto frontier. The paper's Figure 6 provides difficulty estimates per task category (median thinking length per domain) that could seed such a classifier.

### Practical Applications and Downstream Use Cases

**Automated GPU kernel optimization for ML infrastructure teams.** The KernelBench L2 result — 38.0% fast₁, the highest among all evaluated models including Claude-Sonnet-4.6 (28.0%) — targets a concrete and economically valuable task: fusing sequences of PyTorch operators into optimized GPU kernels. ML infrastructure teams at companies deploying large models routinely spend engineer-weeks hand-optimizing kernel fusion for attention mechanisms, normalization layers, and activation functions. InCoder-32B-Thinking can serve as a first-pass optimization tool: given a PyTorch reference implementation, the model generates a fused Triton or CUDA kernel with embedded reasoning about shared memory allocation, warp scheduling, and register pressure. The ~10× cost advantage of inference over human engineering time (a forward pass costs fractions of a cent; an engineer's week costs thousands of dollars) means that even a 38% success rate is economically viable if the model is run speculatively on many candidate optimizations and the successful ones are validated by testing. The failure mode — generating kernels that don't compile or produce incorrect results — is observable and recoverable (test suites catch errors), so the automation can be deployed in a supervised loop where the model proposes, the test infrastructure validates, and failures are discarded.

**Automated CAD script generation for parametric design workflows.** The CAD-Coder result — 84.0% compilation rate and 48.6% IoU, both best-in-class — makes the model deployable as a text-to-CAD assistant for parametric design. In mechanical engineering and industrial design, generating CadQuery scripts from natural language specifications is a bottleneck: the specification ("a mounting bracket with a cylindrical bore subtracted from a rectangular body") is easily described, but translating it into valid CadQuery code requires expertise in the OpenCascade geometry kernel and iterative debugging of Boolean operations. InCoder-32B-Thinking automates this: given a natural language description, it generates an executable CadQuery script with embedded reasoning about wall thickness, manifold validity, and geometric constraints. The 84.0% compilation rate means the majority of generated scripts run without errors, producing valid 3D geometry. The 48.6% IoU means approximately half of those produce geometry that matches the specification with reasonable fidelity. For a design iteration workflow — where an engineer describes a part, gets a rough CAD model, inspects it, and iterates — this represents a substantial acceleration: the engineer starts from a generated model rather than a blank script, and the thinking trace provides diagnostic reasoning they can inspect if the output needs adjustment.

**Self-improvement data generation for industrial code models.** The ECoT synthesis pipeline — generate code, execute against real backends, capture error feedback, revise, repeat — is a general mechanism for generating training data from any problem specification that has a verifiable correctness criterion. A model trained with ECoT could be used to generate additional ECoT trajectories for *new* industrial tasks, creating a self-improvement loop: (1) deploy InCoder-32B-Thinking on novel industrial problems (e.g., new Verilog modules for emerging RISC-V extensions, new GPU kernels for novel attention mechanisms), (2) execute the generated code against real backends, (3) capture the multi-turn error-correction trajectories (the model diagnosing its own failures), (4) use these trajectories as additional training data to fine-tune the model further. This is distinct from typical self-play or self-distillation because the verification signal is external (real toolchains) rather than internal (model confidence). The ICWM can accelerate this loop by providing fast approximate feedback between real-execution rounds, making it practical to generate large volumes of self-improvement data. The key risk — model collapse from training on self-generated errors — is mitigated by the real execution filter: only trajectories that eventually reach PASS contribute successful diagnostic patterns; failed trajectories contribute failure-mode awareness.

**Unified industrial code assistant for multi-domain engineering teams.** The paper's demonstration that a single 32B model achieves competitive or best-in-class results across chip design, GPU optimization, embedded systems, and 3D modeling (Tables 4-5) makes it viable as a single deployment for organizations that work across multiple hardware domains. A semiconductor company designing both digital logic (Verilog) and GPU kernels for ML accelerators, or an IoT company developing both embedded firmware (C for STM32) and mechanical enclosures (CAD), could deploy one model instead of maintaining separate domain-specific tools. The practical benefit is reduced operational complexity (one model server, one inference pipeline, one set of integration tests) and shared reasoning capability (diagnostic skills learned from GPU debugging may transfer to embedded system debugging within the same model weights). The performance tradeoffs — the thinking variant underperforms the instruct variant on VeriScope (75.4 vs. 80.7) and SWE-bench Verified (70.4 vs. 74.8) — mean the deployment should include a router that selects between thinking and non-thinking inference modes based on the task, using the prompt router design already described in Section 2.1 as a template.
