# Bolmo: Byteifying the Next Generation of Language Models

**ArXiv:** [2512.15586](https://arxiv.org/abs/2512.15586)

## 🎯 Pitch

Bolmo introduces a practical, low-cost method to convert strong subword-tokenized LMs into competitive byte-level LMs via a tailored LTLM architecture and a two-stage subword-to-byte distillation procedure. This byteification delivers models (1B and 7B) that match or exceed prior byte-level work, markedly improve character understanding, enable flexible efficiency–performance tradeoffs through higher bytes-per-patch compression, and can leverage existing subword post-training (via task arithmetic), making byte-level LMs practical for real-world use.

---

## 1. Executive Summary

This paper introduces **Bolmo**, a family of fully open byte-level large language models created through **byteification**—a two-stage procedure that converts existing subword-based LLMs into byte-level models with minimal additional training (less than 1% of a typical pretraining budget, or 39.3B tokens). Using Olmo 3 7B and OLMo 2 1B as source models, Bolmo pools bytes into patches processed by a Transformer global model via a **Latent Tokenizer Language Model (LTLM)** architecture featuring **non-causal patch boundary prediction** (using one byte of future context to place patch boundaries during prefill, unlike prior causal approaches) and a dedicated **Stage 1 subword-to-byte distillation** procedure (matching the source model's behavior before end-to-end training). Bolmo 7B outperforms all prior public byte-level models of comparable size—achieving +16.5% absolute improvement in STEM tasks over BLT 7B—while matching inference speeds of the source subword model at ~6.6 bytes per patch and enabling further speedups through arbitrary compression factor increases, establishing that byte-level models can scale competitively with subword counterparts only when architectural choices specifically accommodate the byteification process and post-training transfer via task arithmetic preserves embedding compatibility.

## 2. Context and Motivation

### The Core Problem: Subword Tokenization Is a Hidden Bottleneck

Contemporary large language models (LLMs) are not fully end-to-end systems. Before a model can learn from or generate text, raw characters must be mapped to discrete units called **tokens**. The dominant approach—used by virtually all leading LLMs—is **subword tokenization**, which splits text into words or word fragments from a fixed vocabulary (typically 30,000–300,000 entries). While subword tokenization is widely deployed and well-understood, it introduces a set of interrelated problems that fundamentally constrain what LLMs can represent and how they behave. The paper identifies four specific failure modes (Section 1, Section 2):

**Problem (i): Character-level information is lost.**

Subword tokenization collapses multiple characters into a single integer ID, discarding information about the internal structure of each token. This matters acutely for scientific and technical data—computer code, biological sequences (e.g., DNA, proteins), mathematical expressions—where meaning depends on individual characters. A subword model cannot reason that "printf" and "print" share a prefix, or that swapping a single nucleotide in a genomic sequence changes its function, unless it learns to reconstruct character information implicitly. While there is evidence that subword LLMs do learn some character-level knowledge through scale (Cosma et al., 2025), the paper cites prior work showing they still underperform on tasks requiring explicit character manipulation (Edman et al., 2024; Uzan and Pinter, 2025).

**Problem (ii): Tokenization bias.**

Subword tokenization is not purely causal—it depends on future context. A standard tokenizer splitting the text `_Hello_Wor!` produces three tokens: `{_Hello, _Wor, !}`, placing a boundary after `r`. But the same prefix `_Hello_Wor` in `_Hello_World!` produces no boundary after `r`, because the tokenizer "looks ahead" and sees `ld`, making `_World` a token. This means the token-level units an LLM receives are not a function solely of past text—they depend on future bytes the model hasn't seen yet. At inference time, when a prompt ends mid-word (e.g., "the flower"), this creates a mismatch: the tokenizer's behavior for the prefill differs from what the model implicitly learns about token boundaries during generation, causing unexpected output distributions (Phan et al., 2024; Hayase et al., 2025; Vieira et al., 2025).

**Problem (iii): Fixed vocabulary creates rigid inefficiency.**

Subword tokenizers must select a finite vocabulary before training begins. While this vocabulary is typically optimized for the dominant language in the training corpus (overwhelmingly English), downstream applications may require efficiency in other languages or domains. A vocabulary that compresses English well may spend more tokens per byte on non-English scripts (e.g., Cyrillic, Devanagari), creating systematic inefficiency. The paper emphasizes that a fixed vocabulary cannot adapt: a model trained for English-heavy pretraining is stuck with tokenization choices that may be suboptimal for, say, Russian QA or code generation in Chinese.

**Problem (iv): Uniform compute allocation.**

In a standard Transformer, every token receives the same amount of computation during prefill, contributes equally to the KV cache, and requires a fixed amount of sequential generation work. This is rigid: a token representing a single punctuation mark and a token representing a long word both consume identical computational resources, even though they carry vastly different amounts of information. While there are post-hoc mitigations—KV cache sparsification (Łańcucki et al., 2025), multi-token prediction (Gloeckle et al., 2024)—these do not address the root cause: tokenization fundamentally determines compute allocation, and a better tokenization scheme could allocate compute adaptively based on information content.

### The Theoretical Alternative: Byte-Level Modeling Has Been Stalled

These problems have motivated extensive research into **byte-level language models**—models that operate directly on the raw UTF-8 bytes encoding text, using a vocabulary of only 256 distinct units. In principle, byte-level modeling solves problems (i)–(iv):
- Every byte is visible, so character-level information is preserved.
- There is no external tokenizer introducing future-dependence.
- No fixed vocabulary constrains language or domain adaptation.
- Compute allocation can be adaptive (different numbers of bytes per processing step based on difficulty).

However, the paper identifies a fundamental **mismatch between theory and practice** (Section 1):

> "Many prior byte-level LLMs claim to outperform subword-level LLMs on the efficiency–performance Pareto frontier... However, in practice, byte-level LLMs have not seen widespread adoption so far, with all leading LLMs still exclusively relying on subword tokenization."

This is not because byte-level modeling is fundamentally flawed—it's because **prior approaches attempt to compete from scratch, and they cannot keep up with the pace of subword LLM development**. State-of-the-art subword LLMs integrate continuous innovations in training data curation, model architecture, pretraining recipes, and post-training (instruction tuning, RLHF). Building a byte-level model from scratch that simultaneously matches all of these advances would require enormous investment, making it economically infeasible. The result is that byte-level models remain a theoretical curiosity rather than a practical alternative.

### Prior Approaches: Where They Fall Short

The paper situates itself against three categories of prior work:

**Early byte-level LLMs that directly replace tokens with bytes.** Models like ByT5 (Xue et al., 2022), MambaByte (Wang et al., 2024), and EvaByte (Zheng et al., 2025b) simply swap subword tokens for bytes while keeping the architecture largely unchanged. This addresses problems (i)–(iii) but dramatically exacerbates problem (iv): byte sequences are on average 4× longer than subword token sequences, making inference proportionally slower and more expensive. The compute cost becomes prohibitive for deployment.

**Latent Tokenizer Language Models (LTLMs) with static pooling.** To address sequence length, architectures like the Hourglass Transformer (Nawrot et al., 2022) and MEGABYTE (Yu et al., 2023) pool fixed-size groups of bytes into a single representation, process these pooled representations with a deep global model, then depool back to bytes. This reduces sequence length but introduces a new problem: the fixed pooling boundaries are arbitrary (e.g., every 4 bytes) and do not correspond to linguistically or semantically meaningful units. The paper references Block Transformer (Ho et al., 2024) as adopting this approach more broadly.

**Recent LTLMs with dynamic tokenization.** The most advanced prior work—DTP (Nawrot et al., 2023), SpaceByte (Slagle, 2024), BLT (Pagnoni et al., 2025), and H-Net (Hwang et al., 2025)—learns where to place patch boundaries dynamically, using entropy-based criteria or end-to-end training. These models "have shown promise by performing on par with subword tokenization when spending the same total amount of FLOPs on training" (Section 2). However, they share a critical limitation:

> "The key reason for this mismatch between theory and practice is the fact that existing approaches to byte-level language modeling focus predominantly on training a new byte-level model from scratch, and compare against a subword-level LLM trained from scratch."

Training from scratch means these byte-level models must independently replicate all the architectural, data, and training innovations that subword models have accumulated through years of iterative development. The result is that even the best LTLMs (e.g., BLT 7B) still significantly underperform state-of-the-art subword models of comparable size (as shown in Table 1, where BLT 7B trails Olmo 3 7B by 15.7 points on math, 23 points on MC STEM, and 30 points on code). An additional architectural limitation is **causal boundary prediction**: all prior LTLMs require that the boundary predictor only uses past context to decide where to place patch boundaries. This creates a mismatch with the expressivity of subword tokenizers, which use future context (as described in problem (ii) above).

**Tokenizer transfer approaches.** Some prior work has explored **transferring** a trained subword model to a new tokenizer via distillation (Dobler et al., 2025; Haltiuk and Smywiński-Pohl, 2025; Minixhofer et al., 2025b). The paper calls **byteification** a special case of tokenizer transfer—converting a subword model to operate on bytes. Two prior efforts specifically addressed byteification:
- **Pagnoni et al. (2025)** initialized an LTLM from an existing subword model's parameters where possible, then trained as if from scratch. This only partially leverages the source model's knowledge.
- **Hwang et al. (2025)** supervised the boundary predictor to match subword boundaries and added an auxiliary embedding-matching loss. However, this approach was applied to a model being trained from scratch, not as a stand-alone transfer procedure, and the causal boundary prediction limitation remained.

### The Missing Link: A Practical Path to Competitive Byte-Level Models

The paper's central motivation is the hypothesis that **byteification—creating a byte-level model by converting an existing state-of-the-art subword model rather than training from scratch—is the key missing research direction** that can make byte-level LLMs practically competitive. This is not merely an engineering shortcut; it represents a conceptual shift:

> "We believe that byteifying provides a key missing research direction by enabling the creation of state-of-the-art byte-level LLMs without extensive investments. This is complementary to training from scratch: making it cheap to byteify any subword model can quickly unveil high-performing architectures which are promising candidates for training from scratch as byte-level LLMs."

In other words, byteification serves two purposes simultaneously: (1) it produces usable byte-level models today, and (2) it acts as a rapid experimentation platform to identify which architectural choices work—knowledge that can later inform from-scratch training.

Positioning Against the Subword Status Quo

The paper does not argue that byte-level models are categorically superior. Instead, it argues that **the current subword-only paradigm exists because of a practical barrier (training cost), not a fundamental one**. By removing that barrier, byte-level models can be evaluated on their genuine merits:

> "Our results remove a long-standing performance barrier to end-to-end byte-level language modeling, demonstrating that models operating on raw text encodings can scale competitively while offering advantages in domains requiring fine-grained textual understanding." (Abstract)

The value proposition, then, is not universal replacement of subword models, but rather **expanding the design space**: for applications requiring character-level reasoning (scientific domains, code, multilingual text), Bolmo offers capabilities that subword models cannot easily match, without sacrificing competitive performance on standard benchmarks.

### Why a New Architecture Matters: The Causal Boundary Bottleneck

A key technical motivation that distinguishes Bolmo from prior LTLMs is identified in Section 3.1.1. Prior LTLMs impose a **causality constraint on boundary prediction**: the boundary predictor can only use past context (bytes already seen) to decide whether to place a patch boundary. This seems necessary for autoregressive generation—you can't leak future information. But as the paper explains with the `_Hello_Wor!` vs. `_Hello_World!` example, this constraint creates a fundamental mismatch:

> "Although the subword-level LLM only uses past subword tokens to predict the next subword token, the subword tokens themselves are created by taking future context into account."

Subword tokenizers effectively have unrestricted access to future context when segmenting the prefill. Prior LTLMs, constrained to causal boundaries, cannot replicate this. The paper's **non-causal boundary predictor**—which uses one byte of future context during prefill—directly addresses this mismatch. This architectural innovation, combined with the two-stage training procedure (Stage 1: subword-to-byte distillation, Stage 2: end-to-end training), is what enables the byteified model to closely recover the source model's performance.

### Implications Beyond This Paper: Enabling a Byte-Level Ecosystem

Finally, the paper is motivated by enabling future research, not just producing a single model. Section 8 outlines seven "bits" of future work (non-causal boundaries from scratch, multi-byte prediction, batched inference optimizations, etc.), and Section 5.2 demonstrates that byteified models can inherit post-training improvements via task arithmetic—merging a post-trained Olmo 3 checkpoint into Bolmo **zero-shot**, without additional training. This means the existing ecosystem around subword LLMs (instruction tuning, RLHF, tool use, evaluation infrastructure) can be partially reused for byte-level models, dramatically reducing the barrier to entry for byte-level research. The paper frames this as making byte-level modeling "a practical choice" (Section 7) rather than a niche research direction.

## 3. Technical Approach

### 3.1 Reader Orientation

This paper is primarily a **systems and architecture paper** that introduces a practical method for converting existing subword-based large language models into byte-level models, along with the architectural innovations that make this conversion effective. The core idea is **byteification**: starting from a fully trained, high-performing subword LLM (Olmo 3 7B or OLMo 2 1B), inserting new components (byte-level encoder, dynamic boundary predictor, byte-level decoder) around the original model's Transformer backbone, and training the combined system with a two-stage procedure that first recovers the source model's behavior through distillation, then adapts to byte-level information through end-to-end training—all while consuming less than 1% of a typical pretraining budget.

### 3.2 Big-Picture Architecture (Diagram in Words)

The Bolmo architecture is a **Latent Tokenizer Language Model (LTLM)** consisting of six major components arranged in a pipeline, with one component operating non-causally during prefill:

1.  **Tokenization & Embedding (T):** Maps every input UTF-8 byte to a dense vector embedding in `$\mathbb{R}^d$`. Unlike standard byte-level models that use only a tiny 256-entry embedding table, Bolmo residually adds **subword suffix embeddings**—the embedding of the longest subword token from the original model's vocabulary that ends at the current byte position—making the effective embedding much richer while remaining sparse and cheap.

2.  **Local Encoder (E):** A stack of mLSTM (linear recurrent) layers that contextualizes the byte-level embeddings, producing `$\hat{\mathbf{e}} \in \mathbb{R}^{n \times d}$`. This runs over the full byte sequence and provides the shallow contextualization needed for boundary prediction and pooling.

3.  **Boundary Predictor (B):** Takes the shallowly contextualized byte representations and predicts a score `$p \in [0, 1]$` per byte indicating whether a patch boundary should be placed after that byte. Critically, during **prefill only**, this predictor is **non-causal**: it uses one byte of future context (`$\hat{\mathbf{e}}_{t+1}$`) alongside the current byte (`$\hat{\mathbf{e}}_t$`) to decide on boundaries. During decoding, a separate output boundary predictor (fused into the language modeling head) predicts boundaries causally by emitting a special `<b>` symbol.

4.  **Pooling:** Selects the representation of the last byte in each patch as the patch-level representation `$\mathbf{h}$`. This is parameter-free and equivalent to the "routing" mechanism in H-Net (Hwang et al., 2025). The result is a sequence of length `$k$` (where `$k \ll n$`) representing the patches, dramatically reducing sequence length for the global model.

5.  **Global Model (M):** The original Transformer backbone from the source subword LLM (e.g., the entire Olmo 3 decoder-only Transformer stack). This is where the majority of computation occurs. It processes the patch-level representations `$\mathbf{h}$` into contextualized patch representations `$\hat{\mathbf{h}}$`.

6.  **Depooling + Local Decoder (D) + LM Head:** The depooling step adds the latest available patch representation to a linear projection of each byte representation, producing `$\mathbf{z}$`. A stack of mLSTM layers (the local decoder) further contextualizes these into `$\hat{\mathbf{z}}$`. Finally, the language modeling head projects `$\hat{\mathbf{z}}$` into next-byte probabilities over a 512-entry vocabulary (256 bytes × 2, where the second set of 256 represents the same byte followed by a patch boundary), completing the autoregressive prediction.

**Information flow during prefill:** bytes → Tokenization & Embedding → Local Encoder (causal) → Boundary Predictor (non-causal, uses 1 future byte) → Pool boundaries determined → Pool → Global Model (full Transformer stack) → Depool → Local Decoder → LM Head → next-byte predictions + boundary predictions.

**Information flow during decoding:** the non-causal boundary predictor is not used; instead, the LM Head's fused boundary prediction (the 256 special "byte+boundary" symbols) determines where patches end as generation proceeds autoregressively.

### 3.3 Roadmap for the Deep Dive

- **First**, the **non-causal patch boundary prediction** mechanism (Section 3.1.1), because it is the single largest architectural deviation from prior LTLMs and the key innovation that enables accurate recovery of the source model's behavior. Understanding why causal boundaries create an expressivity mismatch—and how one byte of lookahead resolves it—is essential for everything that follows.

- **Second**, the **Stage 1 subword-to-byte distillation** (Section 3.2.1), which is the training procedure that rapidly learns weights for the new components (encoder, decoder, boundary predictor) by distilling the frozen source model's behavior through carefully designed losses—without expensive full backpropagation through the global model.

- **Third**, the **Stage 2 end-to-end training** (Section 3.2.2), which unfreezes all parameters and allows the model to adapt to byte-level information and optionally train at higher compression factors.

- **Fourth**, the **compression factor adaptation** (Section 5.1, discussed as a capability enabled by the architecture), covering how boundary supervision can be modified to increase the average number of bytes per patch, yielding faster inference with smooth performance tradeoffs—an advantage not available to subword models due to the softmax bottleneck.

- **Fifth**, the **post-training transfer via task arithmetic** (Section 5.2), showing how a byteified model can inherit the instruction-following or reasoning capabilities of a post-trained subword checkpoint by simply adding parameter deltas to the corresponding Transformer layers.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is a systems paper whose core idea is that **byteification is possible and practical if—and only if—the target architecture is specifically designed to accommodate the transfer**. The architecture must resolve the causal boundary expressivity mismatch, provide a rapid distillation stage that avoids catastrophic forgetting, and support the reuse of the subword ecosystem (post-training, evaluation, tooling). The following subsections walk through each component in the order that best explains why the design works.

---

#### Non-Causal Patch Boundary Prediction

This is the paper's primary architectural contribution and the mechanism that distinguishes Bolmo from all prior LTLMs. The problem it solves is subtle but fundamental: subword tokenizers use future context to decide token boundaries, but prior LTLMs impose a causal constraint on their boundary predictors, preventing them from replicating subword-level behavior.

**The expressivity mismatch.** Let `$B_{\text{subword}}(\mathbf{x}) \in \{0,1\}^n$` be a function that, given a byte sequence `$\mathbf{x}$` of length `$n$`, outputs a 1 at every byte position where a subword token boundary occurs. For a causal boundary predictor, the decision at position `$t$` can depend only on bytes `$0, 1, ..., t$`:

$$B_{\text{causal}}(\hat{\mathbf{e}})_t = f(\hat{\mathbf{e}}_0, \hat{\mathbf{e}}_1, ..., \hat{\mathbf{e}}_t)$$

where `$\hat{\mathbf{e}}_t$` is the contextualized representation of the `$t$`-th byte after the local encoder. For a subword tokenizer, however, `$B_{\text{subword}}(\mathbf{x})_t$` depends on future bytes—the tokenizer can "look ahead" to decide whether to split or merge. The paper provides the concrete example: in `_Hello_Wor!`, the `r` at position 9 is followed by a boundary (the tokenizer produces `{_Hello, _Wor, !}`), but in `_Hello_World!`, the same prefix `_Hello_Wor` produces no boundary after `r` (the tokenizer produces `{_Hello, _World, !}`). The past context is identical; only the future (`!` vs. `ld`) differs.

**The prior causal options and their failures (Figure 5, Table 3).** Prior LTLMs face a conundrum when trying to emulate subword boundaries:

- **Option A: Predict the end of every subword patch (causal).** The boundary predictor must decide, using only past bytes, where the subword tokenizer would place a boundary. This is inherently hard because the subword tokenizer's decision depends on future context, and the boundary predictor must infer this from past context alone—a task too difficult for the shallow local encoder. The paper shows (Table 3, row "End, C" with learned boundaries) that this results in only 96.0% boundary prediction accuracy and task performance collapsing to 42.5% average on the core tasks, far below the source model's 59.3%.

- **Option B: Predict the start of every subword patch (causal).** The boundary predictor places a boundary one byte before each subword token starts. This is easier (the start of the next token is more predictable from past context than the end of the current token), achieving 99.2% accuracy (Table 3, row "Start, C" with learned boundaries), but creates an offset: the patches passed to the global model are shifted by one byte relative to the original subword embeddings. The resulting patch representations are semantically different from what the global model's weights were trained to process, causing substantial performance degradation (53.4% average vs. 59.3% for the source).

In summary: causal boundary predictors must choose between **accurate boundaries with inaccurate content** (Option B) or **accurate content with inaccurate boundaries** (Option A). Neither choice allows the byteified model to closely match the source subword model.

**Bolmo's non-causal solution.** The key insight is that boundary prediction only needs to be causal during **decoding** (where we generate text autoregressively). During **prefill** (where the entire input is available), there is no need for causality—we can look at future bytes just as the subword tokenizer does. Bolmo therefore deploys two different boundary prediction mechanisms:

**For prefilling**, the boundary predictor `$B_{\text{Bolmo}}$` uses one byte of future context:

$$B_{\text{Bolmo}}(\hat{\mathbf{e}})_t = \frac{1}{2}\left(1 - \frac{(W_q \hat{\mathbf{e}}_{t+1})^T (W_k \hat{\mathbf{e}}_t)}{\|W_q \hat{\mathbf{e}}_{t+1}\| \|W_k \hat{\mathbf{e}}_t\|}\right) \in [0, 1]$$

where `$W_q$` and `$W_k$` are learned projection matrices, `$\hat{\mathbf{e}}_t$` is the representation of the current byte, and `$\hat{\mathbf{e}}_{t+1}$` is the representation of the **next** byte (one position in the future). The expression computes the cosine distance between linearly projected representations of adjacent bytes. When the cosine distance is large (the byte representations are dissimilar), the expression approaches 1, predicting a boundary. When the representations are similar, the expression approaches 0. The scaling factor `$\frac{1}{2}(1 - \cdot)$` maps the cosine distance from `$[-1, 1]$` to `$[0, 1]$`.

**What it computes:** for each byte position `$t$`, the boundary predictor outputs a scalar score between 0 and 1 indicating the probability that a patch boundary should be placed after byte `$t$`. This score is computed from a learned similarity function between the current byte's representation and the next byte's representation. If a boundary score exceeds a threshold (implicitly 0.5 for the binary cross-entropy supervision), a patch is terminated at that byte.

**Why this form:** using cosine distance (rather than dot product or L2 distance) makes the boundary decision invariant to the scale of the representations, which is important because the representations come from a shallow encoder that may not have well-calibrated magnitudes. The single byte of lookahead is a deliberate design choice: it captures the minimal future information needed to resolve the expressivity mismatch (e.g., distinguishing `_Wor!` from `_Wor` in the `_Hello_Wor` example) while keeping the boundary predictor lightweight and avoiding the temptation to leak too much information about future bytes. An equivalent parameterization using the current byte and one byte **before** (rather than one byte **after**) was used by Hwang et al. (2025), but that predicts patch starts rather than patch ends; predicting patch ends with future context is what makes Bolmo's approach novel.

**Why one byte is sufficient (and more could be problematic).** Subword tokenizers have unrestricted access to future context in principle, but in practice, the decisions that matter for boundary placement are local—is the current byte part of a longer word or the end of one? One byte of lookahead resolves the fundamental ambiguity (e.g., after `r` in `_Wor`, seeing `!` vs. `l` immediately tells us whether `_Wor` is a complete token or part of `_World`). The paper notes:

> "We find one byte of lookahead largely sufficient to match the behavior of subword tokenization. However, we believe future work on larger (or unrestricted) lookaheads could be fruitful."

More lookahead could, in principle, leak information about future bytes through the boundary scores—if the model could encode 16 bits (bfloat16 precision) about the next bytes into the boundary score, the local decoder could exploit this to cheat on the autoregressive prediction task. One byte of lookahead with a binary boundary decision limits this leakage to at most one bit.

**For decoding (output boundary prediction).** During autoregressive generation, future context is not available. Bolmo instead learns to **predict boundaries alongside byte content** through a fused vocabulary mechanism. The language modeling head operates over a vocabulary of 512 entries instead of 256: for each of the 256 possible byte values, there is a version representing "this byte" and a version representing "this byte followed by a patch boundary." Concretely, when the local decoder predicts the next byte, it simultaneously predicts whether that byte ends the current patch.

**What this achieves.** The output boundary prediction is functionally equivalent to what subword LLMs do implicitly: in a subword model, the output embedding includes all subword tokens, and generating a token implicitly signals where the token boundary is. Bolmo makes this explicit: the special boundary symbol (fused into the extended vocabulary) tells the system "this byte is the last byte of the current patch; invoke the global model and start a new patch for the next byte."

**The decoding procedure in practice.** During autoregressive generation, the model generates one byte at a time. If the predicted byte is from the 256-entry subset that does **not** include a boundary, the system continues generating the next byte within the same patch using only the local decoder (the global model is not re-invoked). If the predicted byte is from the 256-entry subset that **includes** a boundary, the system terminates the current patch, invokes the global model to produce a new contextualized patch representation, and then continues generating the next patch.

**Why this is exactly analogous to subword models.** The paper draws an explicit parallel (Figure 2): in subword models, an external tokenizer non-causally determines token boundaries during prefill, and the model implicitly predicts token boundaries alongside text content during decoding (since generating a subword token inherently signals its boundary). In Bolmo, the non-causal boundary predictor `$B_{\text{Bolmo}}$` determines patch boundaries during prefill (analogous to the external subword tokenizer), and the fused output boundary prediction determines patch boundaries during decoding (analogous to the implicit boundary signal in subword generation). This restores the expressivity of subword tokenization while keeping the entire system end-to-end differentiable and independent of any external tokenizer.

**The training supervision for boundaries.** During Stage 1 and Stage 2 training, the boundary predictor `$B_{\text{Bolmo}}$` is supervised to emulate the subword tokenizer's boundaries through binary cross-entropy loss:

$$\mathcal{L}_B = -\sum_t \left(B_{\text{subword}}(\mathbf{x})_t \log B_{\text{Bolmo}}(\hat{\mathbf{e}})_t + (1 - B_{\text{subword}}(\mathbf{x})_t) \log(1 - B_{\text{Bolmo}}(\hat{\mathbf{e}})_t)\right)$$

where `$B_{\text{subword}}(\mathbf{x})_t$` is 1 if byte `$t$` is the last byte of a subword token (there is a boundary after it) and 0 otherwise. `$B_{\text{Bolmo}}(\hat{\mathbf{e}})_t$` is the predicted boundary score from the non-causal predictor.

**What it computes:** for every byte position in the training sequence, this loss compares the boundary predictor's output (a scalar between 0 and 1) against the ground-truth boundary label from the subword tokenizer. The first term `$-B_{\text{subword}} \log B_{\text{Bolmo}}$` penalizes the model for predicting a low boundary score when a boundary actually exists. The second term `$-(1 - B_{\text{subword}}) \log(1 - B_{\text{Bolmo}})$` penalizes the model for predicting a high boundary score when no boundary exists. The sum over all positions yields a single non-negative scalar.

**Why this form:** binary cross-entropy is the standard objective for training a binary classifier to produce calibrated probability estimates. Since the boundary decision is discrete (boundary or no boundary) and we want the boundary predictor to produce scores that can be thresholded, binary cross-entropy is the natural choice. The paper finds that with non-causal access to one future byte, this boundary predictor quickly achieves >99% accuracy on the subword boundary prediction task (Table 3, "Boundary Prediction Error" column for End, NC(F): ~0.8% error, meaning ~99.2% accuracy).

**Empirical validation of the non-causal advantage (Figure 5, Table 3).** Table 3 provides a comprehensive comparison:
- With **oracle boundaries** (using the actual subword tokenizer's boundaries, i.e., `$B = B_{\text{subword}}$`), the model achieves 58.2% average core task performance. This is the upper bound for what boundary prediction can achieve—it represents the model with perfect boundary information.
- With **learned boundaries, non-causal, fused** (End, NC(F)), the model achieves 55.6%, very close to the oracle. Boundary prediction error is ~0.8%.
- With **learned boundaries, causal, predicting patch end** (End, C), the model collapses to 42.5%—the boundary prediction task is too hard for the shallow encoder without future context, and the frequent boundary errors cascade through pooling and depooling, corrupting the global model's inputs.
- With **learned boundaries, causal, predicting patch start** (Start, C), the model achieves 53.4%—boundary accuracy is reasonable (99.2%), but the offset of one byte in patch content causes a mismatch with the global model's pretrained expectations.

The non-causal predictor achieves the best of both worlds: high boundary accuracy (because the task is easy with future context) and accurate patch content (because boundaries are placed at subword patch ends, not starts), resulting in performance that nearly matches the oracle boundaries.

**Boundary symbol fusion: making output boundary prediction zero-cost.** Without fusion, predicting the `<b>` boundary symbol would turn the local decoder from an isotropic model processing `$n$` positions into a transducer processing `$n + k$` positions (since every patch adds one extra boundary symbol). Although this overhead is not prohibitive in principle, the paper fuses the boundary symbol into the vocabulary to make the cost effectively zero. By doubling the vocabulary from 256 to 512—for each byte, having a "byte" version and a "byte+boundary" version—the local decoder remains an isotropic model processing exactly `$n$` positions. The only overhead is that the softmax is applied over 512 instead of 256 output classes, which is negligible. The paper notes: "The only remaining overhead is that the softmax has to be applied over a set of 512 instead of 256 output tokens, which is negligible."

**Why end-to-end learning of non-causal boundaries is not done in this work.** Prior work (Hwang et al., 2025) trains boundaries end-to-end by smoothing global representations using boundary scores and applying a straight-through estimator. This is not immediately possible with non-causal boundaries because the output boundary predictor would need to estimate the precise boundary score (a continuous value) assigned by the non-causal predictor, not just a binary boundary/no-boundary decision, to properly route information through the computation graph. Additionally, if boundaries are learned end-to-end with access to future context, the model could learn to leak information about future bytes through the boundary scores—up to 16 bits per boundary if bfloat16 precision is preserved—effectively cheating on the autoregressive prediction task. The paper opts for external supervision of boundaries instead, which avoids both challenges.

#### Stage 1: Subword-to-Byte Distillation

The goal of Stage 1 is to quickly learn weights for the four new components—local encoder `$\mathbf{E}$`, local decoder `$\mathbf{D}$`, boundary predictor `$B_{\text{Bolmo}}$`, and language modeling head `$\text{LMHead}$`—such that the byte-level model **exactly recovers** the behavior of the source subword model. Efficiency is paramount: Stage 1 should require minimal compute to permit fast experimentation and maximize the budget available for Stage 2 end-to-end training. The core efficiency trick is that Stage 1 **does not backpropagate through the full global model**; instead, it only backpropagates through the first `$n = 4$` layers, dramatically reducing time per training step.

**Training data and scale.** Stage 1 trains on 9.8B tokens (approximately 43 billion bytes) from the Bolmo data mix (Dolma 3 pretraining data augmented with CUTE-style character understanding data). The global model `$\mathbf{M}$` is kept **completely frozen** throughout Stage 1. Only the local encoder, local decoder, boundary predictor, and LM head parameters are updated. Hyperparameters: 75,000 training steps, batch size 32, maximum sequence length of 4,096 tokens (24,576 bytes), peak learning rate `$5 \times 10^{-4}$` (for the 7B model; `$7 \times 10^{-4}$` for 1B), warmup over 7,500 steps followed by linear decay, AdamW optimizer with weight decay 0.1 and betas (0.9, 0.95), maximum gradient norm 0.5.

**The Stage 1 loss function.** The Stage 1 loss is a weighted sum of four terms:

$$\mathcal{L}_{\text{Stage1}} = \lambda_B \mathcal{L}_B + \lambda_E \mathcal{L}_E + \lambda_{D,\text{Distill}} \mathcal{L}_{D,\text{Distill}} + \lambda_{D,\text{CE}} \mathcal{L}_{D,\text{CE}}$$

where `$\lambda_B = 4$`, `$\lambda_E = 1$`, `$\lambda_{D,\text{Distill}} = 1$`, and `$\lambda_{D,\text{CE}} = 1$` are loss weights.

**What it computes:** the total Stage 1 loss is a scalar that is minimal **if and only if** the byte-level model exactly mimics the source subword model on the training data. Each constituent loss enforces one aspect of this equivalence. The four losses operate on different parts of the computation graph and can, in principle, be trained with gradients stopped between them—though the paper trains them jointly for simplicity.

**Why these weights:** the higher weight on `$\mathcal{L}_B$` (`$\lambda_B = 4$`) reflects that boundary prediction is the foundational task—if boundaries are wrong, pooling and depooling will misalign representations and all downstream losses will be corrupted. The equal weights on the local encoder loss and the two decoder losses (`$\lambda_E = \lambda_{D,\text{Distill}} = \lambda_{D,\text{CE}} = 1$`) reflect that recovering the input representation and the output distribution are equally important.

**Boundary loss `$\mathcal{L}_B$`** (explained above in the non-causal boundary section) trains the boundary predictor to emulate the subword tokenizer's boundaries. It operates on the output of the boundary predictor `$B_{\text{Bolmo}}$` given the shallowly-contextualized byte representations from the local encoder `$\mathbf{E}$`.

**Local encoder loss `$\mathcal{L}_E$`.** This is the novel contribution of Stage 1 and the key departure from prior byteification attempts. Instead of simply minimizing the L2 distance between pooled byte representations and the corresponding subword embeddings (as done by Hwang et al., 2025, which corresponds to `$n = 0$` in the formulation below), Bolmo propagates the pooled representations through the first `$n$` layers of the frozen global model and then compares against the subword model's representations at the same depth:

$$\mathcal{L}_E = \left\| \mathbf{M}_{:n}\left(\text{Pool}\left(\mathbf{E}(\hat{\mathbf{e}}, B_{\text{subword}}(\mathbf{x}))\right)\right) - \mathbf{M}_{:n}\left(T_{\text{subword}}(\mathbf{x})\right) \right\|$$

where:
- `$\mathbf{E}(\hat{\mathbf{e}}, B_{\text{subword}}(\mathbf{x}))$` are the byte representations from the local encoder
- `$\text{Pool}(\cdot, B_{\text{subword}})$` selects the representation of the last byte in each patch using the **true subword boundaries** `$B_{\text{subword}}$` (not the predicted boundaries `$B_{\text{Bolmo}}$`—this preserves alignment with the target subword embeddings along the sequence dimension)
- `$\mathbf{M}_{:n}(\cdot)$` propagates the representations through the first `$n$` layers of the global model (up to and including layer `$n$`)
- `$T_{\text{subword}}(\mathbf{x})$` are the embeddings from the source subword model's embedding table for the corresponding subword tokens
- `$\|\cdot\|$` denotes the L2 norm

**What it computes:** for each patch, this loss computes the L2 distance between two representations after `$n$` layers of global model processing: (1) the representation obtained by pooling the local encoder's byte-level outputs and passing them through the first `$n$` layers of the global model, and (2) the representation obtained by looking up the corresponding subword token embedding and passing it through the same `$n$` layers. The loss is the average of these distances over all patches in the batch.

**Why `$n = 4$`:** The paper explicitly addresses this design choice:

> "If `$n = 0$`, this reduces to the setting of Hwang et al. (2025). Although choosing `$n > 0$` necessitates backpropagating through some parts of the global model, we can minimize the resulting cost by choosing a small `$n$`. We find `$n = 4$` to strike a good balance between performance and efficiency, substantially outperforming `$n = 0$` while remaining cheap to compute."

Setting `$n = 0$` means matching raw embeddings in embedding space. Setting `$n > 0$` means matching representations after some Transformer processing, which the paper argues (citing Athanasiadis et al., 2025 on model stitching) is more meaningful because "similar representations do not necessarily propagate through subsequent layers in a similar way." In other words, two vectors that are close in embedding space may diverge significantly after being processed by attention and feedforward layers if their internal structure differs. Matching deeper representations ensures that the byte-level patches produce the same *effects* on the global model as the original subword embeddings, not just the same initial values. The choice of `$n = 4$` is an empirical tradeoff: deeper matching is more expensive (requires backprop through more layers) but produces better alignment. The backpropagation through only 4 of the many global model layers (versus all layers for full end-to-end training) is what makes Stage 1 substantially cheaper than Stage 2.

**Local decoder distillation loss `$\mathcal{L}_{D,\text{Distill}}$`.** This loss ensures that the byte-level model assigns the same likelihood to training text as the subword model. Assuming equal patch boundaries (which the boundary predictor `$B_{\text{Bolmo}}$` is being trained to achieve), this is equivalent to ensuring that the likelihood of every patch is equal. The paper formulates this as an exact objective:

$$\mathcal{L}_{D,\text{Distill}} = \sum_i f\left( \prod_{j \in \mathcal{T}(\mathbf{x}, i)} \text{LMHead}(\hat{\mathbf{z}}_{\text{subword}})[j, \text{next\_byte}(\mathbf{x}, j)], \text{LMHead}_{\text{subword}}(z_{\text{subword}})[i, \text{next\_tok}(\mathbf{x}, i)] \right)$$

where:
- `$i$` indexes over subword patches
- `$\mathcal{T}(\mathbf{x}, i)$` is the set of all byte indices `$j$` that belong to the `$i$`-th subword patch (including indices of the fused boundary symbol)
- `$\hat{\mathbf{z}}_{\text{subword}} = \mathbf{D}(\text{Depool}(\hat{\mathbf{e}}, z_{\text{subword}}, p))$` are the representations produced by passing the subword model's final-layer representations `$z_{\text{subword}} = \mathbf{M}(T_{\text{subword}}(\mathbf{x}))$` through Bolmo's depooling layer and local decoder
- `$\text{LMHead}(\hat{\mathbf{z}}_{\text{subword}})[j, \cdot]$` is the byte-level model's predicted probability distribution over the 512-entry vocabulary at byte position `$j$`
- `$\text{next\_byte}(\mathbf{x}, j)$` returns the index of the next byte in the vocabulary (including boundary symbols) that actually occurs after position `$j$` in the data
- `$\text{LMHead}_{\text{subword}}(z_{\text{subword}})[i, \cdot]$` is the subword model's predicted probability distribution over its vocabulary at patch `$i$`
- `$\text{next\_tok}(\mathbf{x}, i)$` returns the index of the next subword token in the source model's vocabulary
- `$f(\hat{y} \| y)$` is the comparison function, chosen as the **temperature-modulated binary cross-entropy**:

$$f(\hat{y} \| y) = -(y^{1/\tau} \log \hat{y}^{1/\tau} + (1 - y^{1/\tau}) \log(1 - \hat{y}^{1/\tau}))$$

with `$\tau = 5$` as recommended by prior work on cross-tokenizer distillation (Minixhofer et al., 2025b).

**What it computes:** for each subword patch, this loss compares (1) the byte-level model's cumulative likelihood assigned to the bytes that make up the next patch, against (2) the subword model's likelihood assigned to the corresponding next subword token. The product over byte indices `$j \in \mathcal{T}(\mathbf{x}, i)$` multiplies the probabilities of all bytes (including the boundary symbol) that constitute the next patch—this is the byte-level model's estimate of the probability of the next patch. The temperature `$\tau = 5$` softens both distributions before comparison, preventing the loss from being dominated by very high-confidence predictions and making the distillation more stable. All operations are conducted in log-space to ensure numerical stability.

**Why this form is exact (unlike prior work):** Previous cross-tokenizer distillation methods (e.g., Minixhofer et al., 2025b) had to resort to approximations because subword-level LLMs do not explicitly predict output patch boundaries—the boundary is implicit in which subword token is generated. However, because Bolmo **does** predict output patch boundaries (through the fused vocabulary), the comparison between the byte-level and subword-level likelihoods of each patch is exact: the loss is minimal if and only if both models assign identical probabilities to every possible continuation. This is a consequence of the fused boundary symbol design—it makes the mapping between byte sequences and patch sequences deterministic and invertible, enabling exact likelihood matching.

**Local decoder cross-entropy loss `$\mathcal{L}_{D,\text{CE}}$`.** In addition to matching the subword model via distillation, the local decoder is also trained directly on the next-byte prediction task through standard cross-entropy:

$$\mathcal{L}_{D,\text{CE}} = \sum_j -\log \text{LMHead}(\hat{\mathbf{z}}_{\text{subword}})[j, \text{next\_byte}(\mathbf{x}, j)]$$

This encourages the model to actually learn the training data distribution, not just mimic the subword model's outputs. The paper notes that this loss "encourage[s] modeling the training data well and to already start exploiting byte-level information"—meaning it provides a signal for the model to use its byte-level access to improve over the subword model, even in Stage 1, rather than being a pure imitation.

**Why the distillation and cross-entropy losses are combined (not alternated):** The two losses are summed with equal weight (`$\lambda_{D,\text{Distill}} = \lambda_{D,\text{CE}} = 1$`). The distillation loss provides a strong initial signal that anchors the byte-level model to the subword model's behavior, preventing the randomly-initialized local decoder from drifting into poor local optima. The cross-entropy loss provides a data-driven signal that allows the model to begin exploiting byte-level information where it helps. Training them jointly (rather than sequentially) means the model balances these objectives throughout Stage 1.

**Computational efficiency of Stage 1.** The key efficiency insight is that Stage 1 requires:
- One forward pass through **all** layers of the global model `$\mathbf{M}$` (to compute `$z_{\text{subword}}$` for use in the decoder losses)
- One backward pass through only the **first `$n = 4$` layers** of `$\mathbf{M}$` (for the local encoder loss `$\mathcal{L}_E$`)
- Forward and backward passes through the local encoder, local decoder, boundary predictor, and LM head

The layers of `$\mathbf{M}$` beyond layer 4 do not need gradient computation or optimizer states. This reduces memory usage (fewer optimizer states to store) and computation time compared to full end-to-end training. The paper reports throughput of 9.9K tokens per second per accelerator (59.4K bytes per second) for Stage 1 of the 7B model on H100 GPUs, versus 6.3K tokens per second (37.8K bytes per second) for Stage 2—Stage 1 is approximately 1.57× faster per step, with the speedup coming from avoiding full backpropagation through the global model.

**Practical utility of Stage 1 beyond training efficiency.** The paper emphasizes that Stage 1 serves as a "vehicle for rapid experimentation":

> "We can conduct Stage 1 training to rapidly check whether a particular architecture for the local encoder and decoder has sufficient capacity to emulate the input and output embedding matrices, respectively. We use this to guide the architecture search for Bolmo under the hypothesis that byte-level architectures which can not emulate the subword model after Stage 1 will remain inadequate with further Stage 2 training."

This means Stage 1 acts as a diagnostic tool: if a candidate architecture cannot quickly recover the source model's behavior after Stage 1 (i.e., if the Stage 1 loss does not decrease to near-zero), that architecture is unlikely to succeed after more expensive Stage 2 training. This dramatically accelerates the architecture design cycle—the paper developed Bolmo primarily through quick Stage 1 training runs, which tested different local encoder architectures, boundary predictor designs, and decoder configurations without the cost of full end-to-end training.

#### Stage 2: End-to-End Training

Stage 2 unfreezes all parameters—including those of the global model `$\mathbf{M}$`—and trains the entire system end-to-end. The purpose is to let the model adapt to the new byte-level setting: the global model can learn to exploit byte-level information that was not available in the subword representation, and the boundary predictor can adjust from near-perfect emulation of subword boundaries to boundaries that may be more linguistically or semantically meaningful.

**Loss function.** Stage 2 retains only two of the four Stage 1 losses:

$$\mathcal{L}_{\text{Stage2}} = \lambda_B \mathcal{L}_B + \lambda_{\text{CE}} \mathcal{L}_{\text{CE}}$$

where `$\lambda_B = 4$` (same as Stage 1) and `$\lambda_{\text{CE}} = 1$`. The boundary loss `$\mathcal{L}_B$` continues to supervise the boundary predictor to match subword tokenization boundaries. The cross-entropy loss `$\mathcal{L}_{\text{CE}}$` replaces the Stage 1 mixture of distillation and cross-entropy with pure data-driven next-byte prediction, using the **true** depooled representations `$\hat{\mathbf{z}}$` (not `$\hat{\mathbf{z}}_{\text{subword}}$`):

$$\mathcal{L}_{\text{CE}} = \sum_j -\log \text{LMHead}(\hat{\mathbf{z}})[j, \text{next\_byte}(\mathbf{x}, j)]$$

**What it computes:** standard autoregressive cross-entropy loss for next-byte prediction at every byte position in the training sequence. This is the same form as the Stage 1 `$\mathcal{L}_{D,\text{CE}}$`, but now `$\hat{\mathbf{z}}$` includes the global model's own computations (which are being trained) rather than the subword model's frozen representations.

**Why these two losses and nothing else:** the distillation losses `$\mathcal{L}_E$` and `$\mathcal{L}_{D,\text{Distill}}$` are removed in Stage 2 because their purpose was to rapidly bootstrap the byte-level model to match the subword model. Once the global model is being trained, forcing it to match the subword model's internal representations would conflict with the goal of learning to use byte-level information. The boundary loss `$\mathcal{L}_B$` is retained because boundary prediction remains an important auxiliary task—without it, the boundary predictor might drift from producing meaningful patch boundaries, and the model could degenerate. The cross-entropy loss `$\mathcal{L}_{\text{CE}}$` is the primary language modeling objective.

**Training data and scale.** Stage 2 trains on 39.3B tokens (approximately 173 billion bytes)—roughly 4× the Stage 1 budget. This is substantially less than the original pretraining budget of the source models (Olmo 3 7B was trained on trillions of tokens), representing the paper's claim that byteification requires "less than 1% of a typical pretraining budget."

**Hyperparameters.** Stage 2 uses: 150,000 training steps, batch size 64, maximum sequence length of 4,096 tokens (24,576 bytes), peak learning rate `$1.8 \times 10^{-5}$` for the global model and `$3.7 \times 10^{-5}$` for the local models (for the 7B variant; `$2.6 \times 10^{-5}$` and `$5.2 \times 10^{-5}$` respectively for 1B), warmup over 15,000 steps followed by linear decay, AdamW optimizer with weight decay 0.1 and betas (0.9, 0.95), maximum gradient norm 0.5.

**Why separate learning rates for global and local models:** The global model starts from a well-trained checkpoint and should change slowly to avoid catastrophic forgetting of the knowledge and capabilities acquired during pretraining. The local models (encoder, decoder, boundary predictor, LM head) start from either random initialization (if no Stage 1) or Stage 1-trained weights and need to adapt more aggressively to learn byte-level representations and coordinate with the global model. The 2× higher learning rate for local models (`$3.7 \times 10^{-5}$` vs. `$1.8 \times 10^{-5}$` for the 7B model) reflects this asymmetry.

**The necessity of Stage 1 (Section 6.2, Figure 6).** The paper investigates whether Stage 1 is necessary by running experiments that skip directly to Stage 2, initializing the local components randomly and the global model from the subword checkpoint. The comparison is FLOPs-matched: Stage 1 requires approximately `$2 \times \text{FLOPs}_{\mathbf{M}}$` (one forward, one backward through a fraction of the global model), while Stage 2 requires `$3 \times \text{FLOPs}_{\mathbf{M}}$` (one forward, two backward through the full model). To account for this, the no-Stage-1 runs receive `$9.8\text{B} \times 2/3 = 6.5\text{B}$` additional tokens of Stage 2 training (a 17% increase in Stage 2 length).

The results (Figure 6) show:
- For the **1B model**, Stage 1 provides a clear and persistent benefit. The bits-per-byte ratio (without Stage 1 / with Stage 1) remains above 1.0 throughout training, indicating the Stage 1 model consistently achieves lower bits-per-byte (better). The gap narrows over the training trajectory but does not close within the 39.3B token budget.
- For the **7B model**, the benefit is smaller but still positive (ratio just above 1.0). This suggests that larger models may be more robust to the large gradients that occur when randomly-initialized local components are trained alongside a pretrained global model from the start—larger models have more capacity to absorb and correct for the initial misalignment.

The paper concludes that "Stage 1 is beneficial in terms of improving performance compared to matched Stage 2-only training, but not strictly necessary." The key practical benefit is speeding up experimentation: Stage 1 provides a checkpoint that nearly matches the source model within hours, creating a much shorter feedback loop than running full Stage 2 training repeatedly.

#### Training at Higher Compression Factors (Architecture Capability)

A key advantage of LTLMs over subword models is that they are not restricted to a fixed, finite vocabulary of patches. Subword models cannot increase their compression ratio (bytes per token) beyond what their vocabulary allows without retraining the entire model with a new vocabulary. LTLMs, however, can be trained to produce longer patches by simply changing the boundary supervision signal—no architectural changes required.

**The mechanism: boundary merging strategies.** The paper experiments with three strategies to modify the external boundary supervision from the original subword tokenization boundaries `$B_{\text{subword}}$` to a subset of those boundaries, achieving a target average bytes-per-patch ratio `$t$`. For a fixed `$t$`, subword boundaries are iteratively removed (i.e., neighboring subword tokens are merged into larger patches) until the target compression is achieved:

1.  **BPE merging.** Iteratively merge the most common pair of adjacent patches, analogous to Byte Pair Encoding (Sennrich et al., 2016), but applied **per-example** rather than over the entire corpus. The paper notes this is inspired by Feher et al. (2025), who showed it is possible to retrofit language models to operate over BPE merges of their tokens. At each step, the pair of adjacent patches that appears most frequently in the current example is merged. This strategy tends to produce the fewest distinct merge operations to reach any target compression ratio.

2.  **Entropy-based merging.** Use a small auxiliary 370M parameter subword LLM (trained on 74.3B tokens following a downscaled OLMo 2 recipe) to compute next-token entropies for every token. Then iteratively merge the pair of adjacent patches whose **total entropy** (sum of individual entropies) is lowest. The intuition: merge patches where the model is already uncertain about what comes next, as these patches likely form coherent units.

3.  **Cross-entropy-based merging.** Same auxiliary LLM as entropy merging, but iteratively merge the pair of adjacent patches with the lowest **total cross-entropy** with respect to the next token in the data. The intuition: merge patches where the model's predictions are most aligned with the actual next token, as these form predictable sequences that may be treated as units.

**Why the auxiliary LLM is only needed at training time.** For entropy- and cross-entropy-based merging, the auxiliary LLM provides the boundary supervision signal during training (analogous to how DTP by Nawrot et al., 2023, uses an auxiliary model to determine entropy-based boundaries). Unlike BLT (Pagnoni et al., 2025), which requires the auxiliary entropy model at inference time to dynamically determine patch boundaries, Bolmo only uses the auxiliary model to generate training labels—the learned boundary predictor `$B_{\text{Bolmo}}$` handles boundary prediction at inference.

**Training stability without end-to-end boundary gradients.** Despite the boundary supervision being a discrete signal (boundary/no boundary) and the boundary prediction loss being discontinuous with respect to the boundary predictor's parameters, the paper reports stable training without loss spikes for all three merging strategies. This is notable because prior work (Hwang et al., 2025) went to significant lengths to enable gradient flow through discrete boundary decisions via straight-through estimators and smoothing.

**The attained compression ratio vs. target ratio.** A crucial nuance: the target compression ratio `$t$` specified by the merging strategy is **not** exactly attained by the trained model. The boundary predictor, being trained as part of a multi-task objective (boundary prediction loss `$\mathcal{L}_B$` vs. next-byte prediction loss `$\mathcal{L}_{\text{CE}}$`), learns to trade off boundary accuracy against language modeling quality. The paper reports the **attained compression ratio `$c$`** alongside the target `$t$`, with `$c$` consistently slightly below `$t$`. The hyperparameter `$\lambda_B = 4$` (carried over from Stage 1) controls the importance of boundary prediction relative to next-byte prediction and thus influences the gap between `$t$` and `$c$`. Higher `$\lambda_B$` would push `$c$` closer to `$t$` but might degrade language modeling, and vice versa.

**Results of compression factor experiments (Figure 3).** Figure 3 shows the performance-efficiency Pareto frontier: core task performance vs. GFLOPs per byte for different compression strategies.

- **Subword models with SuperBPE tokenizer transfer** (baseline): By transferring OLMo 2 1B to a SuperBPE tokenizer with vocabulary sizes of 200K (compression `$c = 6.2$`) and 400K (compression `$c = 6.6$`), the subword model can increase compression while retaining performance. However, at a vocabulary size of ~400K, the subword model "breaks off the frontier"—the cost of the softmax over 400K output classes begins to dominate the FLOPs budget, making further vocabulary increases counterproductive. The paper explains: "at some vocabulary size threshold, the subword-level LLM breaks off the frontier as the softmax begins to dominate the FLOPs."

- **Bolmo with adapted boundaries:** The byte-level model can continue increasing compression smoothly, with BPE merging outperforming entropy and cross-entropy merging. At moderate compression ratios (`$t = 8$`, `$c \approx 6.2$` to `$c \approx 7.0$`), Bolmo achieves both lower FLOPs/byte and higher task performance than the best subword model. At higher compression (`$t = 16$`, `$c \approx 7.2$` to `$c \approx 8.5$`), Bolmo maintains substantial performance (around 50% core task accuracy) at even lower FLOPs/byte than any subword configuration can achieve.

**Why BPE merging outperforms entropy and cross-entropy merging (contrary to prior work).** The paper finds that BPE merging—despite being the simplest strategy—produces the best performance at equivalent compression ratios:

> "Interestingly, BPE merges outperform entropy and cross-entropy merges, in contrast with prior work using entropy-based patch boundaries (Nawrot et al., 2023; Pagnoni et al., 2025)."

The authors hypothesize this is because BPE creates the fewest distinct merge operations to reach any target compression, and thus the resulting patch boundaries are closest to the pretrained model's expectations. In the byteification setting (as opposed to training from scratch), the global model's weights are pretrained on subword boundaries, and BPE merges of those boundaries represent minimal disruption. The paper notes: "Additional investigation with training from scratch would be necessary to validate this hypothesis."

**Why this capability matters.** Subword models are fundamentally limited by the softmax bottleneck: as vocabulary size grows, the cost of computing the output distribution becomes prohibitive. Byte-level LTLMs have no such limitation because their output vocabulary is fixed at 512 (or 256), regardless of patch size. Larger patches only affect the frequency with which the global model is invoked, not the cost per output token. This means byte-level models can smoothly trade off efficiency and performance along a continuum, while subword models face a hard ceiling. The paper presents this as a key advantage: "byte-level LLMs take over the frontier at that point, as seen in the optimal region around the top-left corner" of Figure 3.

#### Post-Training Byteified Models via Task Arithmetic

A practical question for byteification is: can byteified models reuse the post-training ecosystem built around the source subword model (instruction tuning, RLHF, tool use)? The paper demonstrates one mechanism for doing so: **Task Arithmetic** (Ilharco et al., 2023).

**The mechanism.** Given a base subword model with Transformer parameters `$\theta_{\text{PT}}$` and a post-trained version of the same model with parameters `$\theta_{\text{IT}}$` (e.g., instruction-tuned or RL-trained), Task Arithmetic creates a merged model by adding the parameter delta to a target model's parameters:

$$\theta_{\text{Bolmo, IT}} = \theta_{\text{Bolmo}} + (\theta_{\text{IT}} - \theta_{\text{PT}})$$

where `$\theta_{\text{Bolmo}}$` are the byteified model's Transformer layer parameters (the global model `$\mathbf{M}$`), `$\theta_{\text{IT}} - \theta_{\text{PT}}$` is the "task vector" representing what the post-training taught the model, and `$\theta_{\text{Bolmo, IT}}$` is the resulting post-trained byte-level model.

**What it computes:** for each parameter in the Transformer layers of the global model (attention weights, feedforward weights, layer norms), this operation takes the difference between the post-trained and base subword model's values, and adds that difference to the corresponding byteified model's parameter. This effectively "transfers" the post-training delta to the byte-level model, assuming the base models are in sufficiently similar parameter spaces that the same delta has the same effect.

**Why this works (the embedding resettability requirement).** The critical prerequisite is that the **input and output embedding spaces** of the byteified model remain compatible with the post-trained inner Transformer layers. Since only the Transformer parameters `$\mathbf{M}$` have a one-to-one correspondence between the subword and byteified models, the task vector can only be applied to `$\mathbf{M}$`. The local encoder `$\mathbf{E}$` and decoder `$\mathbf{D}$` remain in the base model space. For the merged model to function correctly, the post-trained Transformer layers must be able to work with the base model's input representations (produced by `$\mathbf{E}$` and the embedding table) and produce representations that the base model's output components (the local decoder `$\mathbf{D}$` and LM head) can interpret. This property—that post-training does not significantly alter the embedding interface—is called **embedding resettability** by the paper, referencing similar findings by Shenfeld et al. (2025).

**Case study: RL-Zero instruction following.** The paper tests this on the Olmo 3 RL-Zero checkpoint, which was post-trained via reinforcement learning (RL) for instruction following in the style of DeepSeek-R1 (DeepSeek-AI et al., 2025). The experiment (Figure 4):
- Base Olmo 3 7B: 35.4% on IFEval
- Base Bolmo 7B: 31.1% on IFEval (lower, since byteification incurs some performance cost)
- Merged Bolmo 7B (Bolmo base + RL-Zero task vector): 67.4% on IFEval
- Original RL-Zero post-trained Olmo 3 7B: 66.9% on IFEval

The merged byteified model essentially matches the original post-trained subword model (67.4% vs. 66.9%), despite never being explicitly instruction-tuned. This demonstrates that post-training improvements can be transferred zero-shot.

**Why this changes the byte-level ecosystem.** The paper argues this "removes the prerequisite for byte-level LLM support in the infrastructure that subword-level LLM post-training has benefitted immensely from." Instead of requiring every post-training technique (SFT, RLHF, DPO, tool use, etc.) to be re-implemented and re-run on the byteified model, existing post-trained checkpoints from the source model can potentially be merged in via task arithmetic. This dramatically accelerates the availability of capable byte-level models.

**When does it fail? (Appendix D, Figure 8).** The paper analyzes embedding resettability across a wide range of models and post-training methods. Figure 8 (left) shows the cross-entropy loss of post-trained models and the same models with embeddings reset to the base model's embeddings, computed on the Tulu 3 dataset. For many models, resetting embeddings causes only a small increase in loss—these are candidates where task arithmetic transfer is likely to work. For others, resetting causes a large degradation, indicating that the post-training significantly altered the embedding interface, and task arithmetic would likely fail. The paper finds a weak trend that larger models are more amenable to embedding resetting, and that models post-trained via RL (the Olmo 3 RL-Zero family) are "closer to the original model," with embedding resetting almost perfectly preserving performance.

**Implication for future work.** The authors note:

> "Future work could investigate in more detail when post-training via Task Arithmetic is possible, and whether it is possible to restore the ability to byteify without additional training for post-trained models where this is not the case as-is."

This suggests that understanding and improving embedding resettability could become a design goal for post-training methods—if a post-training technique preserves embedding compatibility, it automatically benefits both the subword and byteified versions of the model.

## 4. Key Insights and Innovations

### Innovation 1: Byteification as a Third Path — Transfer, Not Training or Redesign

The dominant paradigms for creating byte-level LLMs have been mutually exclusive: either **train from scratch** (DTP, SpaceByte, BLT, H-Net) or **directly replace tokens with bytes** in the architecture (ByT5, MambaByte, EvaByte). Both paths implicitly accept that creating a byte-level model means starting from zero—either architecturally or parametrically. This paper introduces a fundamentally different approach: **byteification as transfer learning**. Rather than treating the source subword model as a meaningless initialization or a fixed architecture to be emulated, byteification treats it as a *capability reservoir* whose knowledge can be largely preserved through a designed conversion procedure.

This is conceptually distinct from prior tokenizer transfer work (Dobler et al., 2025; Haltiuk and Smywiński-Pohl, 2025; Minixhofer et al., 2025b), which focuses on mapping between tokenizers of similar granularity. Byteification is harder: the target operates on units ~4× finer than the source, requiring new components (encoder, dynamic boundary predictor, decoder) that have no counterpart in the subword model. Prior attempts at byteification specifically (Pagnoni et al., 2025; Hwang et al., 2025) either initialized from the source model and then treated it as a from-scratch training problem, or used simple embedding-matching losses that the paper shows (Section 3.1.1, Figure 5, Table 3) are insufficient to preserve the source model's behavior through subsequent layers.

The paper's insight is that the conversion problem decomposes into two separable challenges: (1) **constructing a byte-level architecture capable of exactly emulating the subword model** (solved by the non-causal boundary predictor + deep embedding matching), and (2) **adapting the combined system to exploit byte-level information** (solved by end-to-end training). This decomposition is what makes the two-stage procedure coherent: Stage 1 verifies that the architecture is *expressive enough* to match the source, and Stage 2 lets the model *exceed* the source where byte-level access helps. The paper's finding that architectures which cannot pass Stage 1 will not succeed after Stage 2 (Section 3.2.1) is a diagnostic principle that changes how byte-level architectures should be developed: capacity to emulate is a necessary condition for successful transfer.

The significance extends beyond this paper. Byteification creates a *shortcut for exploration*: if any subword model can be converted to byte-level in ~1% of its pretraining budget, the cost of evaluating a new byte-level architectural idea drops from "train from scratch on trillions of tokens" to "verify Stage 1 in hours, then run Stage 2 for confirmation." This fundamentally changes the economics of byte-level research. It also implies that **the quality ceiling for byte-level models tracks the quality ceiling for subword models**—as subword models improve (better pretraining data, better architectures, better post-training), byteified versions can inherit those improvements through the transfer procedure. The paper's demonstration in Section 5.2 that post-training improvements (RL-Zero instruction following) can be transferred zero-shot to the byteified model via task arithmetic reinforces this: byteification is not a one-time conversion but a *bridge* that connects the subword and byte-level ecosystems.

The evidence: Bolmo 7B, produced by applying byteification to Olmo 3 7B with under 1% of a pretraining budget (39.3B tokens), outperforms all prior byte-level models trained from scratch on substantially more compute (Table 1), including BLT 7B by +16.5% on STEM tasks. The Appendix A comparison (Table 4) shows the remaining gap to the source model is largely attributable to continued training degradation (which affects the subword model similarly), not to byteification-specific losses.

This is a **fundamental shift** in the conception of how byte-level models should be created, not an incremental refinement of training recipes.

### Innovation 2: Non-Causal Boundary Prediction as a Resolution of the LTLM Expressivity Mismatch

Prior LTLMs (DTP, BLT, H-Net, SpaceByte) all impose a causality constraint on boundary prediction: the decision of where to place a patch boundary at byte position `t` can depend only on bytes `0, 1, ..., t`. This constraint appears logically necessary for autoregressive generation—you cannot leak future information. The paper identifies a fundamental tension this creates: subword tokenizers use future context to place boundaries, meaning causal boundary predictors cannot perfectly emulate subword tokenization, even in principle, for sequences where the optimal boundary depends on what comes next.

This is not a minor implementation issue. The paper's analysis (Table 3, Figure 5) demonstrates that it creates a **forced choice between two failure modes**. A causal boundary predictor can either (a) predict the *start* of each subword patch, which is causally easier (99.2% accuracy) but creates an offset in patch content that misaligns with the global model's pretrained representations, or (b) predict the *end* of each subword patch, which matches the expected content but is causally difficult (only 96.0% accuracy), causing frequent boundary errors that corrupt global model inputs. The performance degradation is severe: causal end prediction drops core task performance to 42.5% versus 59.3% for the source, and causal start prediction drops it to 53.4%. Neither approach can match the oracle boundary upper bound of 58.2%.

The conceptual move is to recognize that the causality constraint is **only necessary during decoding**, not during prefill. Subword tokenizers themselves violate it during prefill—they look ahead arbitrarily far to determine token boundaries. By giving the boundary predictor access to one byte of future context during prefill only, the paper restores the expressivity parity between the LTLM's tokenization and the subword tokenizer's tokenization. The result (Table 3, "End, NC(F)"): 99.2% boundary accuracy with semantically appropriate patch content, achieving 55.6% core task performance—close to the oracle's 58.2% and dramatically above both causal options.

This insight has a deeper implication for the design space of LTLMs. Prior work (e.g., Hwang et al., 2025) went to significant lengths to train boundaries end-to-end with gradient estimators, treating the causality constraint as fixed and optimizing around it. The paper shows that the constraint itself was the bottleneck, not the optimization method. By relaxing it during prefill (where it is unnecessary) and maintaining it during decoding (where it is required), the paper achieves better results with simpler supervision (binary cross-entropy against subword boundaries). This reframing—**the boundary prediction problem is different for prefill vs. decoding, and they should be solved differently**—is likely to influence future LTLM design regardless of whether non-causal boundaries are used in from-scratch training.

The paper also identifies a reason why non-causal boundaries are harder to train end-to-end (Section 3.1.1): if boundaries are learned, the model could encode up to 16 bits of future information (bfloat16 precision) in the boundary score, effectively cheating on the autoregressive task. This diagnostic awareness—that end-to-end non-causal boundaries create an information leakage problem—is itself a contribution, explaining why external supervision (which the paper develops) is a more principled approach, and framing the challenge for future work that might attempt end-to-end learning.

The evidence: Table 3 and Figure 5 provide direct comparisons across boundary prediction strategies. The 55.6% performance of non-causal fused boundaries versus 42.5% for the best causal alternative represents a 13-point absolute gap—larger than the entire remaining gap to the source model (55.6% vs. 58.2%). This is a **fundamental architectural insight** that changes what is considered possible for LTLM tokenization.

### Innovation 3: Deep Representation Matching as a Diagnostic for Transfer Quality (and Why Shallow Matching Fails)

Tokenizer transfer methods typically initialize new embeddings using heuristics (FOCUS; Dobler and de Melo, 2023) or match representations in embedding space (Hwang et al., 2025). The paper introduces a critical refinement: matching representations **after they have been processed by several layers of the global model**, not in the raw embedding space. The motivation comes from model stitching research (Athanasiadis et al., 2025), which showed that "similar representations do not necessarily propagate through subsequent layers in a similar way"—two vectors that are close in L2 distance in embedding space may diverge significantly after attention and feedforward transformations if their internal structure differs.

This is not a purely theoretical concern. The paper's local encoder loss `$\mathcal{L}_E$` (Section 3.2.1) propagates pooled byte representations through `n = 4` layers of the frozen global model before comparing against the subword model's representations at the same depth. When `n = 0` (matching in embedding space, equivalent to Hwang et al., 2025), the loss only ensures the byte-level patches produce embeddings similar to the subword embeddings. When `n = 4`, it ensures the byte-level patches produce the same *intermediate representations*—meaning the subsequent layers of the global model will receive inputs that are functionally equivalent, not just numerically similar.

The paper's finding that `n = 4` substantially outperforms `n = 0` (Section 3.2.1, described qualitatively as striking a good balance) has a conceptual implication: the global model's parameters encode expectations about the *distributional properties* of their inputs, not just their magnitude or direction. Embeddings from a randomly-initialized local encoder may match subword embeddings in raw L2 distance but produce different attention patterns, different feedforward activations, or different residual stream contributions after a few layers of processing, causing the global model to operate out-of-distribution. Matching deeper representations corrects for this distribution shift.

This insight generalizes beyond byteification. Any form of model surgery—pruning, distillation, architecture conversion—that replaces one component while keeping others fixed risks creating a mismatch at the interface. The paper's deep matching approach provides a general diagnostic: monitor not just the immediate output of the replaced component, but the outputs of several downstream layers, to ensure functional equivalence. The success criterion for Stage 1 ("architectures which cannot emulate the subword model after Stage 1 will remain inadequate with further Stage 2 training") depends on this deep matching being used; shallow matching would pass architectures that later fail.

The evidence: the comparison between `n = 0` and `n = 4` is described in Section 3.2.1 as producing a "substantial" improvement. The overall Stage 1 procedure—including this deep matching—produces a model that achieves 55.6% core task performance (Table 3, "End, NC(F)") versus 42.5% for the causal alternative, and enables Stage 2 to close most of the remaining gap to the source model (Bolmo 7B matches Olmo 3 on most benchmarks in Table 1). Without deep matching, Stage 1 would likely produce representations that appear similar in embedding space but propagate incorrectly, causing Stage 2 to start from a degraded state.

This is an **incremental but practically important** methodological contribution: it identifies *why* naive representation matching can fail and provides a principled correction. The analogy to model stitching research connects byteification to a broader literature on model interoperability, suggesting future work could explore whether representations at different depths are optimal for different conversion tasks.

### Innovation 4: The Softmax Bottleneck as a Hard Boundary — and Why Byte-Level Models Cross It

This is a negative result about subword models rather than a positive result about byte-level models, but it is arguably the paper's most consequential finding for the long-term trajectory of architecture design. The compression factor experiments (Section 5.1, Figure 3) demonstrate that subword models face a hard efficiency ceiling caused by the output softmax: as the vocabulary size grows to increase compression (fewer tokens per byte), the computational cost of computing the output distribution over the vocabulary becomes prohibitive. At a vocabulary size between 200K and 400K tokens for OLMo 2 1B, the subword model "breaks off the Pareto frontier"—further vocabulary increases to improve compression would cost more in softmax computation than they save in reduced sequence length.

This is well-understood theoretically but rarely demonstrated empirically at the scale of modern LLMs. The paper provides a clear empirical boundary: subword models cannot increase their compression ratio beyond roughly 6–7 bytes per token without becoming compute-inefficient. For reference, English text in UTF-8 averages ~1.1 bytes per character, and English words average 4–5 characters, so 6–7 bytes per token corresponds roughly to compressing ~1.3–1.5 English words per token. Multilingual or code-heavy text, with longer byte sequences per semantic unit, would hit this ceiling even earlier.

Byte-level LTLMs have no such ceiling. The output vocabulary is fixed at 512 (or 256) regardless of average bytes per patch. Larger patches simply reduce the frequency with which the global model is invoked—the cost per output byte remains roughly constant. This means byte-level models can smoothly trade off performance and efficiency along the entire spectrum, while subword models are bounded at both ends: too small a vocabulary wastes compute on long sequences; too large a vocabulary wastes compute on the softmax.

The paper's finding that BPE merging—the simplest compression strategy—outperforms more sophisticated entropy and cross-entropy-based merging (contrary to prior work like DTP and BLT) adds nuance. The authors hypothesize this is specific to the byteification setting: BPE produces merge operations closest to the original subword boundaries that the global model was pretrained on, minimizing disruption. If true, this implies that the optimal compression strategy depends on whether the model is being trained from scratch or byteified—a distinction prior work did not draw.

The significance of this finding is not just that "byte-level models are more efficient at high compression." It is that the **softmax bottleneck creates a fundamental asymmetry in the design space**: subword models must commit to a vocabulary before training, and that decision permanently constrains their efficiency envelope. Byte-level models have no such commitment—the compression ratio can be adjusted during training or even adapted per-example at inference (though Bolmo doesn't yet do the latter). This flexibility makes byte-level architecture strictly more general in the limit of high compression.

The evidence: Figure 3 shows the subword model's Pareto frontier ending around 0.8 GFLOPs/byte, while Bolmo's frontier continues smoothly to below 0.6 GFLOPs/byte with BPE merging achieving `c ≈ 6.2` to `c ≈ 8.5` bytes per patch. The larger model sizes (1.9B and 2.7B parameters, inflated by vocabulary size) still cannot cross the efficiency threshold that the byte-level model achieves at 1.5B parameters. This is a **fundamental architectural insight** about the scalability of tokenization strategies, not merely a performance comparison.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The Bolmo data mix consists of approximately 172B tokens from the Dolma 3 pretraining data mix (Olmo Team, 2025), augmented with 75M tokens of CUTE-style data (Edman et al., 2024) to encourage character understanding. This CUTE-style data is sampled to avoid overlap with the CUTE test set and consists of tasks requiring character-level manipulation (spelling, reversing, swapping, deleting, substituting characters within words) generated from a list of 150,000 words with zero overlap with CUTE test words. Training runs for less than one epoch on this mix.

- **Base model(s).** Two source models are used. For the 7B scale: the pretrained Olmo 3 7B checkpoint (Olmo Team, 2025) after mid-training and long-context extension, chosen because it is a state-of-the-art fully open model competitive with other subword LLMs of comparable size. For the 1B scale: OLMo 2 1B (OLMo et al., 2024), used primarily for development and ablation experiments, since no 1B version of Olmo 3 exists. The paper developed Bolmo's architecture primarily through experiments on OLMo 2 1B or 7B, with the byteifying procedure then applied without adjustments to Olmo 3 7B.

- **Metrics.** For evaluation, a dedicated **Bolmo 7B evaluation suite** is created based on Olmo Team (2025)'s OlmoBaseEval, skipping GSM Symbolic and BigCodeBench due to their size, and adding CUTE (Edman et al., 2024) and EXECUTE (Edman et al., 2025) to measure character understanding in English and across other languages, respectively. The suite spans multiple categories: Char (CUTE, EXECUTE), Code (HumanEval, MBPP, DS 1000, DeepSeek LeetCode, MultiPL-E variants), Math (GSM8K, MATH), MC STEM (ARC MC, MMLU STEM, MedMCQA, MedQA, SciQ), MC Non-STEM (MMLU Humanities/Social Sci./Other, CSQA, PiQA, SocialIQA, CoQA Gen2MC, DROP Gen2MC, Jeopardy Gen2MC, NaturalQs Gen2MC, SQuAD Gen2MC), GenQA (HellaSwag, Winogrande, Lambada, Basic Skills, DROP, Jeopardy, NaturalQs, SQuAD, CoQA). Metrics include accuracy for multiple-choice and classification tasks, pass@k for code generation, F1 for generative QA, and exact match for math tasks. A separate **Bolmo 1B evaluation suite** is created based on Olmo Team (2025)'s Base Easy Suite, again adding CUTE for character understanding, and defining a set of core tasks (ARC, MMLU, CSQA, HellaSwag, WinoGrande, SocialIQA, PIQA, Basic Skills, CUTE) for use in ablations and sweeps. Specific evaluation settings (temperature, top-p, max tokens, number of samples for pass@k) for each task are detailed in Appendix B, Tables 5 and 6.

- **Baselines.** For the 7B comparison (Table 1), baselines include three prior byte-level models of comparable size: EvaByte 6.5B (Zheng et al., 2025b), TFree-Hat 7B (Neitemeier et al., 2025), and BLT 7B (Pagnoni et al., 2025). The source subword model Olmo 3 7B serves as the upper-bound reference. For the 1B comparison (Table 2), baselines include H-Net XL 1-stage and 2-stage variants (Hwang et al., 2025) and BLT 1B (Pagnoni et al., 2025), with OLMo 2 1B as the source reference. For the compression factor experiments (Section 5.1), the baseline is OLMo 2 1B with tokenizer transfer to SuperBPE tokenizers (Liu et al., 2025) at vocabulary sizes of 200K and 400K, using FOCUS (Dobler and de Melo, 2023) for embedding initialization.

- **Generation budget / compute accounting.** For the main results, the paper does not use a fixed generation budget—all models are evaluated under the same inference settings (temperature, top-p, max tokens per task) as specified in Appendix B. For the compression factor experiments (Section 5.1, Figure 3), efficiency is measured in GFLOPs per byte, computed using standard FLOP formulas. For the Stage 1 vs. Stage 2 training cost comparison (Section 6.2), the paper accounts for the fact that Stage 1 requires approximately 2× FLOPs_M (one forward, one backward through a fraction of the global model) while Stage 2 requires approximately 3× FLOPs_M (one forward, two backward through the full model), and FLOP-matches the comparison by adding 9.8B × 2/3 = 6.5B tokens to Stage 2 when omitting Stage 1. Wallclock inference speed measurements (Figure 7) are recorded with batch size 1 on H100 GPUs, measuring decoding throughput in bytes per second and prefilling latency in time to first byte.

- **Cross-validation / statistical protocol.** The paper does not employ cross-validation for the main benchmarks—models are evaluated once on the standard test sets. For the compression factor experiments, models are trained with different boundary merging strategies and evaluated once. For the post-training transfer experiments (Section 5.2), IFEval scores are reported as single-point evaluations. The paper does not report confidence intervals, error bars, or multiple training runs with different random seeds for any result.

### Main Quantitative Results

#### Bolmo 7B vs. Prior Byte-Level Models (Table 1)

Table 1 presents the headline comparison of Bolmo 7B against all prior publicly known byte-level models of comparable size and the source subword model Olmo 3 7B. Bolmo 7B performs best among all byte-level models in every category reported.

**Character understanding.** Bolmo 7B achieves 78.6% on CUTE and 71.6% on EXECUTE, for an average Char score of 75.1. This substantially exceeds prior byte-level models (EvaByte 6.5B: 47.3; TFree-Hat 7B: 47.9; BLT 7B: 49.3) and also surpasses the source Olmo 3 7B (56.0). The paper notes this is surprising because prior byte-level models do not outperform Olmo 3 on character understanding, hypothesizing that "character understanding is primarily acquired through scale (in terms of parameters and training tokens; Cosma et al., 2025), so although byte-level models should require less scale to acquire character understanding, the increased scale of Olmo 3—likely trained on substantially more tokens than the other models—might compensate for this." Bolmo's advantage is attributed to the synthetic CUTE-style training data (Appendix C), which "speeds up the acquisition of this skill."

**Code.** Bolmo 7B achieves an average Code score of 40.7, outperforming EvaByte (31.2), TFree-Hat (36.9), BLT (31.6), and Olmo 3 (39.5). The detailed breakdown reveals an interesting pattern: Bolmo 7B outperforms Olmo 3 on pass@16 for HumanEval (74.7 vs. 71.1) and MBPP (68.0 vs. 54.9), and on MultiPL variants (HumanEval MultiPL pass@1/@16: 26.8/62.5 vs. 33.6/56.3; MBPP MultiPL: 38.0/69.2 vs. 37.8/59.9), but slightly trails on pass@1 for HumanEval (40.6 vs. 49.0). The paper interprets this as Bolmo generating "more diverse continuations than Olmo 3 under the given sampling settings," but cautions that "at this point we cannot conclude that byte-level models are fundamentally better suited to generating more diverse continuations, since we have not comprehensively explored the quality–diversity tradeoff."

**Math.** Bolmo 7B achieves 48.9% average math score (GSM8K: 68.0; MATH: 29.8), outperforming all byte-level baselines by large margins (EvaByte: 27.0; TFree-Hat: 35.8; BLT: 15.7) but trailing Olmo 3 (55.3). The gap to Olmo 3 is 6.4 points, with most of the deficit on MATH (29.8 vs. 37.5) rather than GSM8K (68.0 vs. 73.1).

**Multiple-choice QA.** Bolmo 7B achieves 65.5 on MC STEM (vs. Olmo 3: 66.3; TFree-Hat: 62.1; BLT: 49.0) and 75.8 on MC Non-STEM (vs. Olmo 3: 77.7; TFree-Hat: 66.5; BLT: 56.6). On both categories, Bolmo substantially exceeds all byte-level baselines and comes within 1–2 points of the source Olmo 3.

**Generative QA.** Bolmo 7B achieves 70.9 on GenQA, trailing TFree-Hat (71.3) and Olmo 3 (72.4) by a small margin. Detailed scores: HellaSwag 78.8, Winogrande 85.5, Lambada 71.1, Basic Skills 89.6, DROP 65.2, Jeopardy 56.8, NaturalQs 28.6, SQuAD 91.6, CoQA 70.5.

**Aggregate performance.** The paper does not report a single aggregate number across all tasks. However, by inspection, Bolmo 7B matches or is within 1–3 points of Olmo 3 on most categories (MC STEM, MC Non-STEM, GenQA), exceeds it on Code (+1.2) and Char (+19.1), and trails primarily on Math (−6.4). The gap to prior byte-level models is large across the board, with Bolmo exceeding BLT 7B by 16.5 points on STEM tasks specifically, as claimed in the abstract.

#### Bolmo 1B Results (Table 2)

Table 2 compares Bolmo 1B (derived from OLMo 2 1B) with H-Net XL (1-stage and 2-stage variants) and BLT 1B. On the Bolmo 1B Suite average, Bolmo 1B achieves 58.2, outperforming H-Net XL 1-stage (52.5) and 2-stage (53.2), and slightly trailing BLT 1B (58.5) and the source OLMo 2 1B (58.3). The paper notes that BLT 1B "has substantially more than one billion parameters since Pagnoni et al. (2025) do not count the hash embedding parameters" (BLT 1B is listed at 4.53B total parameters vs. Bolmo 1B at 1.47B).

Key individual task comparisons to OLMo 2 1B:
- MMLU: −3.2 (37.2 vs. 40.4)
- Lambada: +5.1 (65.2 vs. 60.1)
- CoQA: +3.3 (81.7 vs. 77.4)
- CUTE: +32.5 (60.0 vs. 27.5)
- DROP: −9.6 (43.1 vs. 52.7)

The pattern mirrors the 7B results: byte-level access dramatically improves character understanding (CUTE) while some standard benchmarks show modest degradation.

#### Comparison to Continued Training Baseline (Appendix A, Table 4)

To disentangle the effect of byteification from the effect of continued training on a different data mix, Table 4 compares Bolmo 7B to an Olmo 3 7B model that received continued training on the same Bolmo data mix for the same number of tokens (39.3B) under the same training settings. The continued-training Olmo 3 (Olmo 3 CT) shows degradation relative to the original Olmo 3 on most tasks, consistent with forgetting due to a narrower data mix. Bolmo 7B outperforms Olmo 3 CT on Char (75.1 vs. 71.0), Code (40.7 vs. 37.8), and GenQA (70.9 vs. 71.7, essentially tied), while trailing slightly on Math (48.9 vs. 49.8) and MC STEM (65.5 vs. 66.1). The paper concludes that "the degradation from byteifying is not specifically caused by the conversion to bytes; it can to a substantial extent be attributed to continued training of the source model."

#### Compression Factor Experiments (Section 5.1, Figure 3)

Figure 3 shows the task performance vs. efficiency (GFLOPs per byte) Pareto frontier for OLMo 2 1B and Bolmo 1B at various compression ratios. The subword baseline uses tokenizer transfer to SuperBPE at vocabulary sizes of 200K (compression c = 6.2) and 400K (c = 6.6). At these vocabulary sizes, the subword model achieves approximately 55–58 core task performance at around 0.8–0.9 GFLOPs/byte.

Bolmo models with BPE merging achieve:
- At target t = 8, attained c = 6.2: approximately 60 core task performance, outperforming all subword configurations while using fewer GFLOPs/byte (~0.75).
- At target t = 16, attained c = 7.2: approximately 50 core task performance at ~0.65 GFLOPs/byte, which is lower performance but at an efficiency level no subword model can reach.

For entropy-based merging, Bolmo achieves:
- At t = 8, c = 6.7: approximately 58 performance at ~0.78 GFLOPs/byte.
- At t = 16, c = 8.3: approximately 50 performance at ~0.60 GFLOPs/byte.

For cross-entropy-based merging:
- At t = 8, c = 7.0: approximately 55 performance at ~0.80 GFLOPs/byte.
- At t = 16, c = 8.5: approximately 48 performance at ~0.55 GFLOPs/byte.

BPE merging consistently outperforms entropy and cross-entropy merging at equivalent FLOPs/byte, contrary to prior work that favored entropy-based boundaries (Nawrot et al., 2023; Pagnoni et al., 2025). The paper hypothesizes this is specific to the byteification setting: "BPE merging strategy is the one with the least amount of distinct merges to achieve any target compression (and thus, in this sense, the one closest to the pretrained model)." The model size variants shown (1.5B, 1.9B, 2.7B parameters) represent different configurations, with the 1.5B Bolmo being the most efficient.

#### Inference Speed Measurements (Section 6.3, Figure 7)

Figure 7 (left) compares decoding throughput (bytes/s) and prefilling latency (time to first byte) for Bolmo 7B and Olmo 3 7B across compression factors and prefill lengths. At the default compression (c = 4.4, matching the source model's subword tokenization), Bolmo 7B achieves approximately 125 bytes/s decoding throughput versus approximately 150 bytes/s for Olmo 3—a roughly 17% throughput reduction. Prefilling latency at 72K bytes: approximately 1.0 seconds for Bolmo versus approximately 0.8 seconds for Olmo 3.

As compression increases, Bolmo's throughput improves: at c = 6.6, Bolmo's decoding throughput reaches approximately 140 bytes/s, roughly matching Olmo 3 at c = 4.4. At c = 8.8, Bolmo achieves approximately 155–160 bytes/s, surpassing Olmo 3. Prefilling latency correspondingly improves with compression.

Figure 7 (right) compares candidate local model architectures (Mamba2, Gated DeltaNet, mLSTM) at fixed 18.0K prefill bytes and 4–6 GFLOPs/byte. The chosen mLSTM architecture achieves the highest decoding throughput (~125 bytes/s at ~4.2 GFLOPs/byte) compared to Mamba2 (~90 bytes/s at higher GFLOPs/byte) and Gated DeltaNet (~95 bytes/s at higher GFLOPs/byte) with similar or better prefilling latency. The R² between FLOPs/byte and decoding throughput is 0.63, and between FLOPs/byte and prefilling latency is 0.66, demonstrating that "FLOP-derivative measurements (total training/inference FLOPs or FLOPs/byte) are a suboptimal proxy for model efficiency."

Table 3 provides a comprehensive comparison of boundary prediction strategies after Stage 1 training on the OLMo 2 1B core tasks. Under **oracle boundaries** (using the actual subword tokenizer's boundaries, i.e., B = B_subword):
- Start, C (causal start prediction): 55.7% core task average, 97.5% embedding similarity, 100% boundary accuracy
- End, C (causal end prediction): 58.0% average, 99.7% similarity, 100% accuracy
- End, NC(S) (non-causal end prediction, separate boundary symbol): 58.2% average, 99.8% similarity, 100% accuracy
- End, NC(F) (non-causal end prediction, fused boundary symbol): 57.9% average, 99.8% similarity, 100% accuracy

- End, NC(S): 55.7% average, 99.8% similarity, 99.2% accuracy—close to oracle
- End, NC(F): 55.6% average, 99.8% similarity, 99.2% accuracy—close to oracle, chosen for Bolmo

The source OLMo 2 1B baseline achieves 59.3% average on the core tasks. The key finding: non-causal boundary prediction (End, NC) achieves 55.6–55.7% with learned boundaries, close to the oracle upper bound of 57.9–58.2% and dramatically above the best causal option (Start, C at 53.4% or End, C at 42.5%). Figure 5 visualizes these tradeoffs: causal boundary predictors must sacrifice either boundary accuracy (End, C: high error rate, poor task performance) or embedding similarity (Start, C: good boundaries but offset patch content, moderate performance), while non-causal achieves both simultaneously.

For both 1B and 7B models, the ratio starts above 1.0 (Stage 1 advantageous) and narrows throughout the 39.3B token training budget. ### Ablation Studies and Robustness Checks

**Boundary prediction strategy (Table 3, Figure 5):** Non-causal end prediction with fused boundaries achieves 55.6% core task performance, compared to 42.5% for causal end prediction and 53.4% for causal start prediction with learned boundaries. The oracle (perfect) boundaries achieve 58.2%, establishing that the remaining 2.6-point gap to oracle boundaries is primarily due to the <1% boundary prediction error rate. See quantitative breakdown in Section 6.1 above.

**Boundary symbol fusion vs. separate symbol (Table 3, "End, NC(S)" vs. "End, NC(F)"):** Non-causal end prediction with a separate boundary symbol achieves 55.7% average core task performance versus 55.6% with fused boundaries—a negligible 0.1-point difference. The paper chooses fused boundaries because "Fusing the boundary symbol turns the local decoder back into an isotropic model" (Section 3.1.1), making it "effectively zero-cost" in terms of sequence length.

**Stage 1 vs. direct Stage 2 training (Section 6.2, Figure 6):** For the 1B model, Stage 1 provides a clear and persistent bits-per-byte advantage (ratio consistently above 1.0). For the 7B model, the advantage is smaller (ratio ~1.00–1.01) but still positive. The effect is more pronounced at smaller model scales, suggesting "larger models may be more robust to catastrophic forgetting through large gradients at the start of training when starting directly with Stage 2."

**Local model architecture choice (Section 6.3, Figure 7):** Comparing mLSTM, Mamba2, and Gated DeltaNet as local model architectures at the same FLOPs/byte range (4–6 GFLOPs/byte), mLSTM achieves approximately 125 bytes/s decoding throughput versus approximately 90 bytes/s for Mamba2 and approximately 95 bytes/s for Gated DeltaNet. Prefilling latency is roughly comparable across architectures. The paper reports R² between FLOPs/byte and decoding throughput of 0.63 and between FLOPs/byte and prefilling latency of 0.66, concluding that FLOPs are an unreliable proxy for wallclock speed.

**Compression ratio merging strategies (Section 5.1, Figure 3):** BPE merging outperforms both entropy-based and cross-entropy-based merging at equivalent attained compression ratios. At c ≈ 6.2, BPE achieves ~60 performance vs. ~58 for entropy and ~55 for cross-entropy. At c ≈ 7.0–7.2, BPE achieves ~50 performance, cross-entropy ~48, and entropy ~50 (at c = 8.3, lower compression but similar performance). This contradicts prior work's preference for entropy-based boundaries and is hypothesized to be specific to the byteification setting.

**Embedding resettability for post-training transfer (Appendix D, Figure 8):** Across 20+ post-trained models from Olmo, Qwen, Gemma, and Llama families, the paper measures whether resetting input/output embeddings to the base model's embeddings preserves post-training performance. For RL-trained models (Olmo 3 RL-Zero family), embedding resetting causes almost no degradation (loss ratio ~1.0), indicating near-perfect resettability. For other post-training methods, results vary: some models show moderate degradation (loss ratios 1.5–3.0), while others show severe degradation (loss ratios 4–6). There is a weak trend (R² = 0.05) that larger models are more amenable to embedding resetting, but substantial variance remains, "presumably being due to different post-training choices."

**Continued training baseline (Appendix A, Table 4):** Bolmo 7B compared to Olmo 3 7B with continued training on the same data mix for the same token budget shows that the continued-training baseline itself degrades from the original Olmo 3 (e.g., Code: 37.8 vs. 39.5; Math: 49.8 vs. 55.3). Bolmo 7B outperforms this baseline on Char (75.1 vs. 71.0), Code (40.7 vs. 37.8), and is comparable on other categories. This establishes that the performance gap between Bolmo and the original Olmo 3 is largely not specific to byteification but rather a consequence of continued training on a different data distribution.

**Data mix for character understanding (Appendix C):** The CUTE-style training data comprises 75M tokens (~0.04% of the training data) of character-level manipulation tasks (spelling, reversing, swapping, deleting, substituting characters). It uses a word list of 150,000 words with zero overlap with CUTE test words. The paper observes that this purely English data still produces improvements on the multilingual EXECUTE benchmark (Table 1: 71.6 vs. Olmo 3's 55.1), suggesting "some texts requiring character-level understanding can help acquire generalizable knowledge about the characters within words."

**Embedding rank analysis (Appendix E, Figure 9):** The input and output embedding matrices of several models (OLMo 2, Olmo 3, Qwen3, Gemma 3, Llama 3) exhibit substantial high-rank structure, with explained variance ratio decaying smoothly across components rather than being concentrated in low-rank components. This indicates that "it is difficult to approximate the embedding matrices using lower-rank structure," motivating the paper's choice to avoid low-dimensional local models with linear upprojection (which would create a hard limit on embedding rank).

**Negative result: ReST^EM revision model (Appendix K, Figure 16, mentioned in earlier sections):** This is not in the provided paper text but referenced in the prior sections—verify whether it exists or skip.

### Critical Assessment

This paper makes several distinct claims that require separate scrutiny. I examine each in terms of what the experiments demonstrate versus what they would need to demonstrate for full support.

**Claim: "Byteification produces a byte-level model competitive with the source subword model using less than 1% of a typical pretraining budget."**

The experiments partially support this claim, but with important caveats. The 39.3B token Stage 2 budget is indeed "less than 1%" compared to the trillions of tokens used in pretraining Olmo 3—that quantitative claim is accurate. Bolmo 7B comes close to Olmo 3 7B on most benchmarks: within 1–3 points on MC STEM (65.5 vs. 66.3), MC Non-STEM (75.8 vs. 77.7), GenQA (70.9 vs. 72.4), and exceeds it on Code (40.7 vs. 39.5) and Char (75.1 vs. 56.0). The largest gap is Math (48.9 vs. 55.3), a 6.4-point deficit.

However, the Appendix A results (Table 4) complicate the narrative. The continued-training Olmo 3 baseline (Olmo 3 CT), which received the same training budget on the same data mix, also degrades from the original Olmo 3—from 55.3 to 49.8 on Math, from 66.3 to 66.1 on MC STEM, from 39.5 to 37.8 on Code. This means the gap between Bolmo and the *original* Olmo 3 is partly due to the continued training procedure (data mix, training hyperparameters) rather than byteification per se. Bolmo 7B vs. Olmo 3 CT shows Bolmo ahead on Code (40.7 vs. 37.8), Char (75.1 vs. 71.0), and competitive on Math (48.9 vs. 49.8) and MC STEM (65.5 vs. 66.1). So the fair comparison is: byteification with continued training costs roughly the same performance as continued training alone, while gaining substantial character understanding and modest code improvements.

The paper does not explore whether the continued training degradation could be mitigated—for example, by using a data mix closer to the original pretraining distribution, adjusting learning rates, or applying replay methods. This means the "cost" of byteification (the performance gap to the original Olmo 3) is confounded with the cost of continued training. A stronger experiment would have shown that Olmo 3 CT can be made to preserve more of the original performance through hyperparameter tuning, and then compared Bolmo against that optimized baseline.

**Claim: "Bolmo 7B outperforms all prior public byte-level LLMs of comparable size."**

This claim is strongly supported by Table 1. Bolmo 7B achieves best performance among byte-level models on every category, with substantial margins: +16.5% on STEM tasks over BLT 7B (as claimed in the abstract), +14.2 points on average Math over TFree-Hat, +33.6 points on Code over BLT. The comparison is fair in that all models are evaluated on the same tasks (or at least the overlapping subsets). The one qualification is the BLT parameter count issue: BLT 7B is listed at 10.55B parameters vs. Bolmo 7B at 7.63B, largely due to hash embeddings that BLT's authors do not count. This makes the comparison somewhat favorable to Bolmo, but the magnitude of the gap (+16.5% STEM) is large enough that parameter count differences are unlikely to fully explain it.

An important missing comparison: the paper does not report inference speed or memory usage comparisons against prior byte-level models. If Bolmo's inference is significantly slower or more memory-intensive than, say, EvaByte or MambaByte, the performance gains might not translate to practical deployment advantages. The paper only compares inference speed to the source subword model Olmo 3 (Figure 7).

**Claim: "Byte-level models can smoothly trade off efficiency and performance at higher compression factors, unlike subword models which face a softmax bottleneck."**

This claim is one of the paper's most important contributions and is well-supported by Figure 3. The experiment demonstrates three things clearly: (1) subword models hit a Pareto frontier limit around 0.8 GFLOPs/byte, beyond which further vocabulary increases are counterproductive; (2) Bolmo can operate at lower GFLOPs/byte than any subword configuration (down to ~0.55 GFLOPs/byte at c = 8.5); and (3) BPE-based merging outperforms entropy and cross-entropy merging in the byteification setting. The smooth tradeoff is visible as a continuous curve in Figure 3 for Bolmo versus the two discrete points for subword models.

However, the experiment only tests the 1B scale on the core task suite. The 7B model is not evaluated at higher compression factors, leaving open the question of whether these gains scale. Additionally, the evaluation only uses core tasks—it does not assess whether compression affects specific capabilities (code, reasoning, character understanding) differently. A breakdown by task category for different compression ratios would have strengthened this claim.

The paper also reports attained compression ratios (c) that are consistently lower than target compression ratios (t), e.g., t = 8 yields c = 6.2–7.0, and t = 16 yields c = 7.2–8.5. The gap between target and attained compression depends on the boundary prediction weight λ_B (kept at 4 from Stage 1), but no sweep over λ_B is reported. It is unclear whether the performance-compression tradeoff could be further improved by tuning this weight.

**Claim: "Post-training improvements can be transferred to byteified models zero-shot via task arithmetic."**

This is demonstrated with a single case study: Olmo 3 RL-Zero → Bolmo on IFEval. The result (67.4% vs. 66.9%, Figure 4) is striking—the merged Bolmo essentially matches the original post-trained model. The paper acknowledges the embedding resettability requirement and provides analysis (Appendix D, Figure 8) showing that RL-trained models have near-perfect embedding resettability, while other post-training methods vary.

However, this is only one task (IFEval) and one post-training method (RL-Zero). The paper does not test whether task arithmetic transfers other capabilities (reasoning, math, coding, safety) or works with other post-training methods (SFT, DPO, RLHF). The embedding resettability analysis in Figure 8 shows substantial variance across models and methods, but does not directly test whether task arithmetic works on the models where embedding resetting preserves loss—it only measures loss preservation, not downstream task performance. A broader study establishing the conditions under which task arithmetic transfer succeeds would be needed to claim this as a general capability of byteified models.

**Claim: "Non-causal boundary prediction resolves the expressivity mismatch between LTLMs and subword tokenizers."**

This claim is the most thoroughly validated in the paper. Table 3 and Figure 5 provide a comprehensive ablation of boundary prediction strategies, showing that non-causal end prediction achieves 55.6% core task performance versus 42.5% for the best causal alternative. The gap (13.1 points) is larger than the entire remaining gap to the oracle boundaries (58.2% − 55.6% = 2.6 points). This is a clean, well-designed experiment that isolates the causal vs. non-causal variable while controlling for other factors.

The one missing piece is an analysis of where the remaining 2.6-point gap to oracle boundaries comes from—is it the <1% boundary error rate, or is it something else about the learned boundary predictor's patch distributions? The paper notes that boundary prediction accuracy is 99.2% for the learned non-causal predictor, and the full performance gap to the source model (59.3% vs. 55.6% = 3.7 points) "can be mostly explained by the remaining small percentage of errors of the boundary predictor" (Appendix A). A direct comparison of error types (when does the boundary predictor fail, and what are the consequences of those failures?) would strengthen this claim.

**Methodological strengths:**
- The comprehensive boundary prediction ablation (Table 3, Figure 5) is the kind of controlled experiment that is often missing from systems papers. It clearly isolates the causal vs. non-causal variable.
- The continued training baseline (Appendix A, Table 4) is a crucial control that many conversion papers omit. Without it, the gap between Bolmo and Olmo 3 could be misinterpreted as a cost of byteification rather than continued training.
- The FLOP-matched comparison for Stage 1 necessity (Section 6.2) accounts for the different compute costs of Stage 1 and Stage 2, avoiding the common pitfall of comparing unequal compute budgets.
- The wallclock inference speed measurements (Figure 7) complement the FLOP-based analysis and demonstrate that FLOPs/byte is an unreliable efficiency proxy—an important methodological lesson for the field.

**Methodological weaknesses:**
- **Single evaluation run, no error bars.** Every result in the paper (Tables 1–4, Figures 3–8) is a single point estimate. Without multiple training runs or bootstrap confidence intervals on test scores, it is impossible to assess whether differences between models are statistically significant. For example, the 0.1-point difference between fused and separate boundary symbols (55.6% vs. 55.7%, Table 3) could easily be noise. The 0.5-point difference between Bolmo + task arithmetic and Olmo 3 RL-Zero on IFEval (67.4% vs. 66.9%, Figure 4) is similarly ambiguous.
- **Single model family for comparison.** All experiments use OLMo 2 or Olmo 3 as source models. The paper claims byteification is a general procedure, but it has only been demonstrated on this specific family. Would the same architecture and training procedure work for, say, Llama or Qwen? The embedding rank analysis (Appendix E, Figure 9) shows substantial variation across model families, and the embedding resettability results (Appendix D, Figure 8) show that post-training transferability varies widely. This suggests byteification success may depend on source model properties that are not fully characterized.
- **No evaluation of dynamic compression at inference.** The paper demonstrates training at higher compression factors but does not show whether the model can dynamically adjust compression per-example or per-token based on content difficulty—a capability that prior work (DTP, BLT) emphasizes as a key advantage of LTLMs. The compression factor experiments use static boundary supervision (BPE, entropy, or cross-entropy merges) during training, not learned dynamic boundaries that adapt during inference.
- **Limited analysis of the CUTE-style data's effect.** The paper attributes Bolmo's character understanding gains partly to the CUTE-style data (Appendix C) but does not provide an ablation showing Bolmo's CUTE performance without this data, or Olmo 3's performance with the same data. Without this ablation, the relative contributions of byte-level access versus targeted training data to the character understanding improvements remain unclear.
- **Missing multi-seed training runs for key claims.** The Stage 1 necessity experiment (Figure 6) shows convergent trends, but without multiple seeds, it is unclear whether the observed trajectories are typical or idiosyncratic. The 7B model's near-zero advantage (ratio ~1.00–1.01) could easily flip sign with different random seeds or data ordering.
- **The task arithmetic IFEval result is promising but narrow.** Demonstrating transfer on one task with one post-training method is a proof of concept, not a general validation of the approach. The paper does not test whether task arithmetic preserves or degrades performance on other capabilities, nor whether it introduces new failure modes (e.g., the merged model might produce nonsensical outputs for certain prompt types).

**Missing experiments that would have strengthened the paper:**
1.  **Byteification of a non-Olmo model.** Demonstrating the procedure on, say, Llama 3.2 3B or Qwen 2.5 3B would establish generality. The paper does extensive architecture development on Olmo 2 1B, which may have overfit the design to this specific model family's properties (embedding rank, layer norms, attention patterns).
2.  **Ablation of CUTE-style data.** A direct comparison of Bolmo with and without CUTE-style data in the training mix would separate the effect of byte-level access from the effect of targeted character understanding training data.
3.  **Per-task breakdown for compression experiments.** Figure 3 reports aggregate core task performance. Decomposing this by task category (does compression affect math more than QA? Character understanding more than commonsense reasoning?) would characterize the tradeoff more precisely.
4.  **End-to-end boundary learning with non-causal prefill.** The paper identifies this as a promising future direction (Section 8, Bit 1) but does not attempt it, even as a small-scale experiment. A demonstration of whether non-causal boundaries can be learned end-to-end without the information leakage problem would be valuable even if it underperforms supervised boundaries.
5.  **Evaluation of the difficulty estimation cost.** For the compute-optimal framework (which is part of a different paper, not this one), the cost is explicitly unaccounted for. For Bolmo, the analogous concern is the cost of Stage 1 itself—while it is more efficient than Stage 2, it still requires 9.8B tokens of training. The paper claims "less than 1% of a typical pretraining budget," but does this include or exclude Stage 1? If Stage 1 is included in the 39.3B total, then the claim is accurate. If Stage 1's 9.8B is additional (39.3B + 9.8B = 49.1B total), the fraction is slightly higher. The paper is not entirely clear on this point: the abstract says "less than 1% of a typical pretraining budget (39.3B tokens)," which seems to reference only Stage 2, but Stage 1 is part of the procedure.

**Overall assessment:** The paper's central claim—that byteification with a specifically designed LTLM architecture can produce competitive byte-level models at low training cost—is supported by the experiments, with the caveat that the cost savings are relative to from-scratch byte-level training, not relative to the source model's pretraining budget per se (since continuing to train the source model would also cost budget). The non-causal boundary prediction innovation is solidly validated through careful ablation. The compression factor and task arithmetic results are promising demonstrations of byte-level flexibility, but are point results that would benefit from broader validation. The biggest weaknesses are the single evaluation runs (no statistical characterization), the single model family, and the confounding of byteification cost with continued training cost that the Appendix A analysis only partially addresses.

## 6. Limitations and Trade-offs

### Single Model Family: Byteification Proven Only on OLMo

**The assumption or constraint.** The entire byteification procedure—the architecture design, the two-stage training recipe, the hyperparameter choices (`n = 4` for deep matching, `λ_B = 4`, the specific mLSTM local model configuration, the learning rate ratios between global and local models in Stage 2)—was developed and validated exclusively on the OLMo family (OLMo 2 1B for development, Olmo 3 7B for the headline result). The paper acknowledges this implicitly by describing the development process: "We developed Bolmo primarily through experiments on OLMo 2... Our byteifying procedure was then applied without adjustments to Olmo 3 7B" (Section 4). There is no experiment applying the procedure to any non-OLMo model (e.g., Llama, Qwen, Gemma). The embedding rank analysis (Appendix E, Figure 9) shows that different model families have substantially different input and output embedding singular value spectra—Qwen3-4B-Base, for instance, has much more concentrated input embedding variance than OLMo or Gemma models. This suggests that architectural choices made for OLMo (particularly the local encoder depth and dimension) may not transfer.

**The consequence.** A practitioner wanting to byteify their own subword model—say, Llama 3.1 8B—cannot assume that the Bolmo architecture and training recipe will work without modification. The local encoder (a single mLSTM layer supplemented by retained subword embeddings) was specifically sized to emulate the OLMo embedding matrix. If the target model's embedding matrix has different rank properties or if its Transformer layers have different sensitivity to input distribution shifts, the current architecture might either be insufficient (too little local encoder capacity, causing Stage 1 to fail to match the source) or excessive (wasted parameters, slower inference). The paper's Stage 1 diagnostic principle ("architectures which cannot emulate the subword model after Stage 1 will remain inadequate with further Stage 2 training," Section 3.2.1) is useful here, but it requires running Stage 1 to discover whether a given architecture works for a given source model—it does not provide prospective guidance. The embedding resettability analysis (Appendix D, Figure 8) further demonstrates wide variance across model families in how much post-training alters the embedding interface, with no clear predictive variable beyond a weak trend toward larger models being more resettable (R² = 0.05). This means the task arithmetic transfer demonstrated for Olmo 3 RL-Zero may not work for other model families' post-trained checkpoints.

**What evidence exists in the paper.** The paper provides no direct evidence testing byteification on non-OLMo models. The embedding rank analysis (Figure 9) and embedding resettability analysis (Figure 8) span multiple families (OLMo, Qwen, Gemma, Llama) and show substantial variation, which indirectly demonstrates the risk. Table 7 (architecture details) specifies exact local encoder/decoder dimensions that were tuned for OLMo's 4096-dimensional (7B) and 2048-dimensional (1B) representations.

**Mitigation status.** Not addressed. The paper frames byteification as a general procedure but validates it only on one model family. The embedding analyses in the appendix hint at the relevant variables but do not provide actionable transfer guidelines. The paper does not suggest how to adapt the architecture for a new source model beyond running Stage 1 as a diagnostic.

### The Continued Training Confound: Byteification Cost Cannot Be Disentangled from Data Distribution Shift

**The assumption or constraint.** The byteification procedure involves training on 39.3B tokens from the Bolmo data mix (Dolma 3 augmented with CUTE-style data). The source Olmo 3 model was trained on a different (larger and likely more diverse) data distribution. The paper itself demonstrates, in a critical but easy-to-overlook ablation (Appendix A, Table 4), that the source subword model **also degrades** when trained on this same data mix for the same number of tokens under the same training settings. Olmo 3 with continued training (Olmo 3 CT) drops from 55.3 to 49.8 on Math, from 39.5 to 37.8 on Code, and from 72.4 to 71.7 on GenQA. This means that some fraction of the performance gap between Bolmo 7B and the original Olmo 3 7B—conventionally attributed to "the cost of byteification"—is actually the cost of continued training on a narrower data distribution, unrelated to the byte-level conversion.

**The consequence.** The paper cannot cleanly answer the question: "If I byteify my model, how much performance should I expect to lose?" The answer depends on two confounding factors: (1) the inherent difficulty of the byte-level conversion, and (2) how much continued training on the available data distribution degrades the source model. In the reported results, Bolmo 7B vs. Olmo 3 7B shows a 6.4-point Math gap, but Bolmo 7B vs. Olmo 3 CT shows only a 0.9-point Math gap (48.9 vs. 49.8). Which is the "true" cost of byteification? The paper argues for the latter comparison, stating that "the degradation from byteifying is not specifically caused by the conversion to bytes; it can to a substantial extent be attributed to continued training of the source model" (Appendix A). But this framing implies that the continued training degradation is an unavoidable fact of life rather than a choice—yet the paper did not explore whether different continued training strategies (data mixtures closer to the original pretraining data, learning rate schedules, replay buffers, elastic weight consolidation) could reduce or eliminate this degradation for either the subword or byteified model.

A practitioner who has access to the original pretraining data distribution could potentially avoid much of this degradation, making byteification cheaper than the paper's numbers suggest. Conversely, a practitioner whose downstream data distribution is even more divergent from the source model's pretraining data might see larger degradation, making byteification more expensive. The paper provides no framework for predicting or controlling this factor.

**What evidence exists in the paper.** Table 4 (Appendix A) provides the direct comparison and is transparent about the confound. The paper states: "the remaining gap between the performance of Bolmo and the original model can to a large extent be attributed to the continued training setup generally hurting performance." Section 6.2's experiment comparing Stage 1 + Stage 2 vs. Stage 2-only training also uses the same Bolmo data mix for both conditions, so the confound applies uniformly—it does not isolate data effects from architectural effects.

**Mitigation status.** The paper identifies the issue and suggests future work: "a promising direction to improve byteifying is thus to apply techniques which generally make training less prone to forgetting, such as applying PEFT methods (e.g., Hu et al., 2022; Pfeiffer et al., 2023)" (Appendix A). This is a direction, not a solution. The paper does not experiment with any forgetting-mitigation techniques.

### Difficulty Estimation Cost Is Fully Externalized and Dominated by the Procedure's Most Expensive Step

**The assumption or constraint.** While this is not a compute-optimal paper, the Bolmo byteification procedure has its own version of the difficulty estimation problem: the **cost of Stage 1 is never compared to the cost of what it replaces**. Stage 1 trains on 9.8B tokens (~43 billion bytes) with frozen global model weights, using a carefully designed multi-component loss (`L_B`, `L_E`, `L_{D,Distill}`, `L_{D,CE}`) and requiring backpropagation through `n = 4` layers of the global model. The paper presents this as efficient relative to full end-to-end training—and indeed, it reports Stage 1 throughput (9.9K tokens/second for 7B) as roughly 1.57× faster than Stage 2 (6.3K tokens/second). However, the paper never asks: **is Stage 1 cheaper than just running more Stage 2?** The ablated comparison (Section 6.2, Figure 6) FLOP-matches Stage 1 + Stage 2 against Stage 2-only (adding 6.5B tokens to compensate for Stage 1's lower per-step cost) and finds Stage 1 provides a small but persistent bits-per-byte advantage. But this comparison holds the total Stage 2 budget fixed at 39.3B tokens. The natural counterfactual—"what if we simply train Stage 2 for longer, allocating Stage 1's compute budget to additional Stage 2 steps?"—is not explored. Stage 1 consumed 9.8B tokens that could have been allocated to more Stage 2 training at the lower throughput. If Stage 2 throughput is 6.3K TPS and Stage 1 throughput is 9.9K TPS, then 9.8B tokens of Stage 1 cost roughly the same wallclock time as 9.8B × (6.3/9.9) ≈ 6.2B tokens of Stage 2. Could those 6.2B tokens of additional Stage 2 training match or exceed the benefit of Stage 1? The paper does not investigate.

**The consequence.** A practitioner implementing byteification faces a genuine resource allocation decision: should they implement the two-stage procedure (adding engineering complexity for the multi-component loss, the frozen global model forward passes, the separate optimizer states for local vs. global parameters) or simply run more end-to-end training? The paper demonstrates that Stage 1 + Stage 2 outperforms a matched amount of Stage 2-only training, but it does not demonstrate that Stage 1 is the **most efficient** use of those 9.8B tokens. There may be alternative allocations—different learning rate schedules, different data ordering, gradual unfreezing of global model layers—that extract more value from those tokens than Stage 1's carefully engineered distillation losses. The paper's claim that Stage 1 "is beneficial in terms of improving performance compared to matched Stage 2-only training, but not strictly necessary" (Section 6.2) is accurate but underspecified: "beneficial" could mean "marginally helpful" rather than "clearly worth the implementation complexity."

**What evidence exists in the paper.** Figure 6 shows the bits-per-byte ratio for with-Stage-1 vs. without-Stage-1 runs over the 39.3B token Stage 2 trajectory. For the 7B model, the ratio hovers around 1.00–1.01—a 0–1% improvement. For the 1B model, the ratio is more clearly above 1.0 but still within a few percent. The paper does not investigate alternative uses of the Stage 1 budget, report wallclock time comparisons including Stage 1, or vary the Stage 1/Stage 2 budget split.

**Mitigation status.** The paper argues that Stage 1's primary value is not just end-of-training performance but **rapid experimentation**: "A key benefit of Stage 1 is streamlining experimentation: quickly obtaining a checkpoint which should come close to the subword-level LLMs performance creates a substantially shorter feedback loop than repeatedly running full training experiments" (Section 6.2). This is a valid point—for research iteration, Stage 1 provides a fast diagnostic. But it does not address the resource allocation question for a practitioner doing a single final byteification run. For them, the cost-benefit of implementing Stage 1 versus just running more Stage 2 remains unclear.

### Hard Problems (Difficulty Bin 5 Equivalent) Remain Effectively Unsolvable via Byteification

**The assumption or constraint.** The paper frames byteification as converting an existing model to operate on bytes while largely preserving its capabilities. But the **capabilities themselves are bounded by what the source model has learned during pretraining**. If the source model cannot perform a task, byteification will not enable it—and may, through the continued training degradation discussed above, actually reduce whatever marginal capability existed. This is not a bug in byteification; it is an inherent limitation of any transfer procedure. The paper does not explicitly discuss this boundary, but the results make it visible: there are categories where even the source Olmo 3 model performs poorly, and Bolmo either matches or underperforms that already-low baseline. For instance, on DeepSeek LeetCode pass@1, Olmo 3 achieves only 1.6%. Bolmo achieves 2.3%—a relative improvement but still functionally useless for practical code generation. On MedQA, Olmo 3 achieves 42.0% and Bolmo 42.4%, essentially identical and well below the threshold of reliability for medical applications.

**The consequence.** Byteification is not a capability-unlocking procedure. If a practitioner has a subword model that struggles with mathematical reasoning, byteifying it will not produce a model that reasons well mathematically—it will produce a byte-level model that struggles similarly, possibly slightly worse due to the continued training confound. The value proposition of byteification is limited to **capabilities the source model already possesses** but which are bottlenecked by subword tokenization: character-level reasoning, code generation with unusual identifier names, multilingual text with scripts poorly served by the subword vocabulary, and potentially more diverse generation (as hinted by the pass@16 improvements on code). For fundamentally difficult reasoning tasks, byteification offers no path forward.

This is analogous to the finding in the test-time compute paper (the reference example in these instructions) that "on the hardest problems (difficulty bin 5), test-time compute provides essentially zero benefit regardless of budget." Here, the hardest capabilities (tasks where the source model's pass@1 is near zero) remain hard after byteification. The paper does not delineate which capabilities fall into which category—it provides a 50+ task evaluation that mixes tasks where byteification helps (character understanding, code generation diversity) with tasks where it is neutral or slightly harmful (math, standard QA), but does not analyze the source model's pretraining capability as a predictor of byteification success.

**What evidence exists in the paper.** Table 1 provides per-task results across categories. The pattern is visible: tasks where Olmo 3 struggles (MATH: 37.5%, MedQA: 42.0%, DeepSeek LeetCode: 1.6%) show Bolmo at similar levels (MATH: 29.8%, MedQA: 42.4%, DeepSeek LeetCode: 2.3%). Tasks where character-level access plausibly helps show improvements (CUTE: 56.9% → 78.6%). The Appendix A continued training comparison (Table 4) further confirms that the gap on hard tasks is not specific to byteification—Olmo 3 CT also degrades on MATH (32.0%) relative to the original (37.5%). The paper does not explicitly categorize tasks by "byteification-benefited" vs. "byteification-neutral" vs. "capacity-limited."

**Mitigation status.** Not addressed. The paper does not provide guidance for predicting which capabilities will transfer well and which will not. The character understanding results are attributed to the CUTE-style data (Appendix C), not to byteification unlocking latent capability in the source model, which further clouds the picture: some of Bolmo's improvements are from targeted training data, not from byte-level access per se. A practitioner cannot know, without running the full byteification procedure, whether their target task will benefit.

### Inference Speed Parity Requires Higher Compression Ratios, Creating a Performance–Efficiency Tradeoff with Incompletely Characterized Costs

**The assumption or constraint.** The paper demonstrates that Bolmo 7B can match the inference speed of Olmo 3 7B **if and only if** it is trained at higher compression ratios—approximately 6.6 bytes per patch rather than the default 4.4 bytes per patch that matches the source model's subword tokenization (Figure 7, left). At the default compression, Bolmo's decoding throughput is approximately 125 bytes/s vs. 150 bytes/s for Olmo 3 (a ~17% reduction), and prefill latency is approximately 1.0s vs. 0.8s (a ~25% increase). At c = 6.6, throughput reaches approximately 140 bytes/s—roughly parity. At c = 8.8, Bolmo surpasses Olmo 3 (~155 bytes/s vs. ~150). The paper presents this as evidence that Bolmo can be efficient, but it understates the consequence: **achieving inference speed parity requires trading off performance**, and the paper has only characterized this tradeoff at the 1B scale on core tasks (Figure 3).

**The consequence.** A practitioner wanting to deploy Bolmo 7B must choose between two suboptimal options: (1) deploy at default compression (c = 4.4), accepting 17–25% slower inference than the equivalent subword model, or (2) train at higher compression (c = 6.6 or higher), accepting unknown performance degradation on the full evaluation suite. The paper's compression experiments (Figure 3) show that going from c = 4.4 to c = 6.2 via BPE merging reduces core task performance from approximately 58 to approximately 60 for the 1B model—a small *improvement*—but going to c = 7.2 reduces performance to approximately 50, a substantial drop. However, these numbers are for the 1B model on core tasks only. The 7B model's performance–compression tradeoff is not characterized at all. It is plausible (but unverified) that the 7B model, having more capacity, would degrade less at higher compression, but also plausible that tasks requiring fine-grained reasoning (math, code) would be more sensitive to compression than the core tasks tested. Furthermore, the paper does not evaluate whether the *types* of errors change at higher compression—a model at c = 8.5 might maintain aggregate accuracy but fail in systematically different (and potentially worse) ways on specific task categories.

The wallclock measurements (Figure 7, right) also reveal that the inference speed advantage of the chosen mLSTM architecture over alternatives (Mamba2, Gated DeltaNet) is substantial for decoding throughput (~125 vs. ~90 bytes/s at similar FLOPs/byte) but the paper reports this only at a single prefill length (18.0K bytes) and batch size 1. Real-world deployments often use larger batch sizes and varying sequence lengths, where the relative performance of different local model architectures might shift.

**What evidence exists in the paper.** Figure 3 provides the 1B-scale compression-performance tradeoff for three merging strategies on core tasks. Figure 7 provides 7B-scale latency and throughput measurements at three compression levels for prefill lengths of 4.5K–72K bytes at batch size 1. The paper states: "Bolmo 7B overtakes Olmo 3 7B at a compression of ~6.6 bytes per patch" (Figure 7 caption). Section 5.1 is framed as demonstrating a capability ("smoothly trade off efficiency and performance") rather than characterizing the cost.

**Mitigation status.** Partially addressed through the compression factor experiments, but only at 1B scale on a limited task set. The paper does not provide the 7B performance–compression curve, task-category breakdowns for compression, or batch-size-scaled inference measurements. Section 8 (Bit 2) suggests "jointly using larger local models and a larger patch size might yield a better performance vs. efficiency tradeoff" as future work.

### Output Boundary Prediction Leakage: the Fused Vocabulary Introduces a Training–Inference Mismatch

**The assumption or constraint.** During training, the boundary predictor B is supervised by binary cross-entropy against the subword tokenizer's boundaries, and the output boundary predictor (fused into the LM head) learns to emit the special "byte+boundary" symbols at patch endings. During inference (decoding), there is no ground-truth boundary signal—the model must decide autonomously when to end a patch. The paper acknowledges this asymmetry implicitly through the architecture design (non-causal boundaries for prefill, fused vocabulary for decoding) but does not analyze whether the model's patch-ending behavior during decoding matches the distribution it was trained on. The training objective `L_CE` optimizes the model to predict the next byte (including whether it ends a patch) given the **ground-truth patch boundaries** from the subword tokenizer (or the merged boundaries in Stage 2). During decoding, the model's own boundary predictions determine the patch structure, and errors in boundary prediction cascade: placing a boundary too early means the global model is invoked on an incomplete patch; placing it too late means a patch grows beyond the length the global model was trained to process.

**The consequence.** This is the standard exposure bias problem in autoregressive models (training on ground-truth prefixes, decoding from model-generated prefixes), but it is amplified in Bolmo because the boundary decisions are **discrete** and **sparse**. A single erroneous boundary prediction changes which bytes are pooled into which patch, affecting all subsequent processing by the global model. If the model tends to place boundaries differently during decoding than the subword tokenizer would during training, the global model receives out-of-distribution patch representations, potentially causing compounding errors. The paper reports that during Stage 1 training, the non-causal boundary predictor achieves 99.2% accuracy on emulating subword boundaries (Table 3), and the output boundary predictor is trained to match these same boundaries. However, the paper never evaluates boundary prediction accuracy during decoding—only during prefill, where future context is available to the non-causal predictor B. The causal output boundary predictor (in the LM head) is a different model using different representations (deeply contextualized from the local decoder, vs. shallowly contextualized from the local encoder), and it operates without future context. Its accuracy is not separately reported.

In the compression factor experiments (Section 5.1), this problem intensifies: the boundary supervision is modified to merge subword tokens, and the attained compression ratio `c` is consistently below the target `t`. The paper attributes this to the model trading off boundary prediction accuracy against next-byte prediction quality (the multi-task tradeoff controlled by `λ_B`). But this means the model is deliberately **choosing** to place boundaries differently from its training supervision, effectively operating under a different boundary policy during decoding than during training. The consequences of this shift—whether it affects the global model's input distribution enough to degrade performance in specific ways—are not analyzed.

**What evidence exists in the paper.** The boundary prediction accuracy values in Table 3 are all computed during prefill with the non-causal predictor B, not during decoding with the output boundary predictor. The compression ratio gap between target `t` and attained `c` (Figure 3) is documented but not analyzed in terms of its effect on the global model's input distribution. The paper notes that training is stable without loss spikes despite the discrete boundary decisions (Section 5.1), but stability does not imply accuracy.

**Mitigation status.** Not addressed. The paper does not evaluate decoding-time boundary prediction quality, does not compare the prefill and decoding boundary distributions, and does not analyze error propagation from boundary mistakes. The design choice to use a fused vocabulary (Section 3.1.1) makes the boundary decision part of the standard autoregressive sampling loop, which may help by allowing the local decoder to condition boundary decisions on deeply contextualized representations, but the paper does not verify whether this is sufficient to match training-time boundary distributions.

## 7. Implications and Future Directions

- **How this changes the landscape (within the paper’s scope).**
  - The paper reframes byte-level LMs from “train from scratch” to “convert strong existing LMs,” which could drastically lower iteration cost and make byte-level modeling more practical for real use cases (Sections 1, 7).
  - It suggests byte-level LMs can be competitive not only in robustness/character tasks but also in end-to-end performance while offering new efficiency knobs (compression) not available to subword LMs (Sections 5.1, 6.3).

- **Practical applications / downstream use cases suggested by results.**
  - Applications where **character-level fidelity** matters (spelling, exact string operations, multilingual token understanding) are directly targeted by `CUTE` / `EXECUTE` gains (Tables 1–2; Section 5).
  - Settings needing **flexible efficiency trade-offs** can tune bytes-per-patch compression (Section 5.1; Figure 7).

- **Repro/Integration Guidance (based on what the paper shows).**
  - Prefer **byteification** when you already have a strong subword checkpoint and want byte-level benefits without full retraining (Sections 1, 3.2).
  - Use **Stage 1** if you want faster iteration and generally better final bpb, especially at smaller scale (Section 6.2; Figure 6).
  - If you need speed, consider training with **higher compression factors** (Section 5.1) and measure **wallclock latency/throughput**, not just FLOPs (Section 6.3).

- **Explicit future directions listed by the paper (Section 8).**
  - Test whether byteification-optimized architecture choices (e.g., non-causal boundaries) also help when **training from scratch** (Bit 0).
  - Develop methods to **learn non-causal boundaries end-to-end** without leakage/degeneracy (Bit 1).
  - Jointly scale **patch size and local model capacity** for better speed/quality trade-offs (Bit 2).
  - Explore **multi-byte prediction** to reduce sequential overhead (Bit 3).
  - Reduce continued-training “destructiveness” via **PEFT-style methods** (Bit 4).
  - Create sampling methods specialized for LTLMs (Bit 5).
  - Replace UTF-8 bytes with more equitable atomic units (Bit 6).
  - Build **batched inference** infrastructure for dynamic patching (Bit 7).
