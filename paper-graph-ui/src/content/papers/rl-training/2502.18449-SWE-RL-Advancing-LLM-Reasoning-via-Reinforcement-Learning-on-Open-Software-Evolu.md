# SWE-RL: Advancing LLM Reasoning via Reinforcement Learning on Open Software Evolution

**ArXiv:** [2502.18449](https://arxiv.org/abs/2502.18449)

## 🎯 Pitch

Training on GitHub pull requests with a simple patch-similarity reward yields an open LLM that bests GPT-4o on real-world bug fixing and spontaneously gets better at math and language understanding—while supervised fine-tuning on the same data makes performance worse.

---

## 1. Executive Summary

This paper introduces **SWE-RL**, the first reinforcement learning approach designed to enhance LLMs for real-world software engineering tasks by training on open-source software evolution data—the record of entire software development cycles including pull requests, issues, and code changes—using a lightweight rule-based reward (the `difflib.SequenceMatcher` similarity score between the predicted patch and the ground-truth oracle patch). Applied to Llama-3.3-70B-Instruct, the resulting model Llama3-SWE-RL-70B achieves a 41.0% solve rate on SWE-bench Verified, the best reported performance among medium-sized models with less than 100B parameters and comparable to proprietary models like GPT-4o. The paper further demonstrates that RL applied exclusively to software issue-solving data yields emergent generalized reasoning capabilities—improving performance on five out-of-domain tasks including function coding, library use, code reasoning, mathematics, and general language understanding—while a supervised fine-tuning baseline degrades performance on average, establishing that reinforcement learning on software evolution data transfers reasoning skills broadly, not only within the training domain.

## 2. Context and Motivation

### The Core Problem: RL for Real-World Software Engineering Remains Unexplored

The fundamental gap this paper addresses is deceptively specific yet practically significant: **no one has successfully applied reinforcement learning (RL) to improve LLMs on real-world software engineering tasks using only publicly available data and rule-based rewards.** The field has seen explosive progress in applying RL—particularly rule-based RL following the DeepSeek-R1 paradigm—to competitive programming and mathematics (Section 1), where rewards are clean and binary (does the code pass the unit tests? does the answer match exactly?). But real-world software engineering is different: code is not self-contained, execution environments are expensive or unavailable, and the correct fix is seldom a single predetermined answer. Prior to this paper, there was no demonstrated method for making RL work in this messier, more realistic setting.

This gap is not academic—it has direct implications for how the field builds LLMs for software engineering:

- **Competitive programming is a poor proxy for real development.** Benchmarks like Codeforces or LeetCode evaluate isolated algorithmic problem-solving. A developer fixing a GitHub issue must navigate an existing codebase, understand a bug described in natural language by a stranger, reason about which files are relevant among thousands, and produce a minimal, correct set of edits. The reward design problem is fundamentally harder: there's no test harness to execute, no binary pass/fail signal, and the "correct" answer is a patch that can be semantically equivalent to the oracle while differing textually.

- **Proprietary LLMs dominate, but open models lag severely.** Table 1 shows Claude-3.5-Sonnet hitting 50.8% on SWE-bench Verified with Agentless. Meanwhile, open models like SWE-Llama-7B and SWE-Llama-13B (Jimenez et al., 2023) barely crack 1.4%. This isn't just a scaffold gap—the underlying models lack the reasoning capability to perform the multi-step diagnosis and targeted editing that proprietary LLMs handle. Closing this gap requires a training methodology that improves the *model itself*, not just prompt engineering around it.

- **Training with proprietary teacher models creates a dependency ceiling.** The existing approaches that *have* improved open models on SWE-bench—Lingma-SWE-GPT (Ma et al., 2024), SWE-Gym (Pan et al., 2024), SWE-Fixer (Xie et al., 2025)—all share a common thread: they distill outputs from GPT-4o or Claude-3.5-Sonnet into their training data. This means the open models can only ever approach the teacher's capability and are fundamentally bottlenecked by what the proprietary model can generate. Moreover, it creates licensing and reproducibility concerns. The paper explicitly identifies this dependency as a limitation of existing approaches (Section 1, Section 4.2):

> "all these works incorporate distilled samples from either GPT-4o or Claude-3.5-Sonnet in their training data"

- **SFT on synthetic data teaches task specialization, not general reasoning.** The paper demonstrates that an SFT baseline—trained with a carefully curated mixture of synthetic code editing data generated in the Magicoder style, general coding SFT data, and Llama 3 general SFT data—actually *degrades* average performance across five out-of-domain benchmarks compared to the base Llama-3.3-70B-Instruct (Table 3). This is a critical negative result: supervised fine-tuning on software engineering data steers the model toward a specific task distribution at the expense of generalized reasoning capability. What the field needs is a training method that improves SWE-bench performance *without* sacrificing—and ideally *enhancing*—general capabilities.

### Where Prior Approaches Fall Short

The paper identifies specific limitations across three axes of prior work:

**RL in coding has been confined to competitive programming with execution-based rewards.** DeepSeek-R1 (DeepSeek-AI, 2025) and subsequent work like RLEF (Gehring et al., 2025) and AceCoder (Zeng et al., 2025) demonstrate that RL with rule-based rewards (unit test pass/fail, exact match to ground-truth output) can dramatically enhance coding and mathematical reasoning. But these approaches assume code is self-contained and executable—a condition that fails for real-world software engineering:

> "This is challenging to apply to real-world SE tasks due to the execution cost and lack of executable environments" (Section 1)

A GitHub issue in the SWE-bench collection might require setting up a full Django environment with specific dependencies, database state, and mock configurations just to run a single test that checks whether the bug was fixed. This is not merely inconvenient—in many cases, the exact execution environment is not reconstructable from the repository snapshot alone, making execution-based rewards fundamentally infeasible at scale. The paper's key insight is that **software evolution data provides an alternative reward signal**: the ground-truth patch applied by the developer who resolved the issue. Instead of "does the modified code pass tests?", the reward becomes "how similar is the generated patch to the one a human developer wrote?"

**DeepSeek-R1's application to software engineering was limited and produced underwhelming results.** The DeepSeek-R1 technical report (DeepSeek-AI, 2025) did attempt to apply its RL framework beyond competition coding and math, including to software engineering—but the authors of this paper explicitly note that "their effectiveness in SE tasks remains limited" (Section 1). DeepSeek-R1's 49.2% on SWE-bench Verified (Table 1), while strong, was achieved with a 671B-parameter MoE model—an entirely different scale regime. The paper does not speculate on *why* DeepSeek-R1's SE performance was relatively limited, but the implication is clear: the recipe of competition-coding-style RL (binary rewards on execution results) does not translate straightforwardly to real-world issue resolution, and a task-specific RL formulation is needed.

**SFT-based approaches teach task-specific patterns, not reasoning.** The paper's SFT baseline (Llama3-SWE-SFT-70B) is instructive as a negative result. Despite being trained on high-quality synthetic data with chain-of-thought reasoning, general coding SFT data, and general Llama 3 dialog data, it underperforms the base model on four of five out-of-domain benchmarks (Table 3). On HumanEval+, it drops from 76.2 to 73.2; on BigCodeBench-Hard (C), from 29.1 to 24.3; on MMLU, from 86.49 to 85.26. Only on CRUXEval (both input and output prediction) does SFT improve—likely because the synthetic code editing data trains the model to reason about execution behavior, which transfers to execution reasoning tasks. The authors diagnose this as SFT "steering the language model towards a specific task distribution, leading to performance declines on tasks with lower emphasis" (Section 3.5). This observation is crucial for the paper's thesis: if the goal is broadly capable software engineering models, SFT is insufficient or even counterproductive. RL, in contrast, incentivizes the model to develop *generalizable reasoning strategies* (self-reflection, exploring alternatives, divide-and-conquer) that emerge from the optimization process rather than being baked into training examples.

**Existing training environments for SWE-bench rely on teacher distillation, not self-improvement.** The paper points out that Lingma-SWE-GPT, SWE-Gym, and SWE-Fixer all "incorporate distilled samples from either GPT-4o or Claude-3.5-Sonnet in their training data" (Section 4.2). Beyond the dependency ceiling this creates, there is a more subtle issue: these models are learning to *imitate* the behavior of a powerful proprietary LLM on SWE-bench-style tasks, which may include brittle patterns (specific diagnostic steps, formatting conventions, error-handling strategies) that do not generalize. In contrast:

> "The seed dataset for RL is sourced exclusively from publicly available repositories, allowing Llama3-SWE-RL to self-improve its issue-solving capabilities through the RL incentive" (Section 4.2)

The word "self-improve" is load-bearing here: the model is not learning to mimic a teacher but rather discovering effective strategies through trial-and-error optimization against the reward signal. This is a fundamentally different learning paradigm with different generalization properties—a claim the paper substantiates through the out-of-domain evaluation results.

### How This Paper Positions Itself

The paper frames itself not as an incremental improvement on SFT-based SWE-bench methods, but as a **paradigm shift** from supervised imitation to reinforcement-driven self-improvement for real-world software engineering. The central argument is that RL on software evolution data unlocks capabilities that SFT cannot:

**First RL approach for real-world SE.** The paper explicitly claims this as a "first" multiple times—"the first RL method to improve LLMs on SE tasks by directly using rule-based rewards and software evolution data" (Section 1), "the first approach to scale RL-based LLM reasoning for real-world software engineering" (Abstract). This first-ness is not merely rhetorical; it represents a non-trivial technical achievement because real-world SE lacks the clean reward signals that make RL straightforward in competition coding and math. The paper's solution—using patch similarity as a continuous reward, training a model to reason about fault locations from full file context, and scaling this on massive open-source PR data—represents a novel combination of data curation, reward design, and prompt engineering that makes RL viable in this domain.

**The reward design is task-specific and deserves motivation.** In competitive coding, the reward is typically binary: pass the test suite (1) or fail (0). In math, it's exact answer matching. The paper's choice of `difflib.SequenceMatcher`—a sequence similarity metric that returns a float between 0 and 1—is deliberate. Real-world patches are highly diverse; even two developers fixing the same bug might produce textually different patches that are semantically equivalent. A binary "exact match" reward would be sparse to the point of uselessness, as the discrete reward ablation demonstrates: "the average discrete reward remains approximately zero upon the completion of training" (Section 3.6). The continuous reward "better captures partial correctness and incremental improvements, allowing the model to learn more nuanced and effective repair strategies."

**FLOPs-matched comparison with proprietary models is not the goal—showing the training paradigm's generalization is.** The paper does not claim to beat GPT-4o or Claude-3.5-Sonnet. The 41.0% on SWE-bench Verified is framed as "comparable to leading proprietary LLMs like GPT-4o" (which scores 38.8% with Agentless) and "state-of-the-art among medium-sized LLMs with less than 100B total parameters" (Section 3.2). The real claim is about *how* this performance was achieved: through RL on open-source data without proprietary teacher models, and with evidence that the resulting model *generalizes better* than an SFT counterpart. The out-of-domain evaluation (Table 3) is not an afterthought—it is central to the paper's thesis that RL on software data teaches transferable reasoning.

**The "aha moments" framing connects to DeepSeek-R1's narrative.** The paper explicitly invokes DeepSeek-R1's concept of emergent "aha moments" during reinforcement learning (Section 2.2, Figure 3), claiming to be "the first study demonstrating the existence of such aha moments in the realm of real-world software engineering tasks." This positions the work within the broader RL-for-reasoning research program while carving out the specific domain contribution. The examples in Figure 3—self-reflection ("But wait...", "And then it hits me..."), exploring alternative approaches ("Alternatively, we can use..."), and divide-and-conquer strategies—are presented as qualitative evidence that the same emergent reasoning behaviors observed in DeepSeek-R1's math and coding training also appear when the training domain is real-world issue resolution.

## 3. Technical Approach

### 3.1 Reader Orientation

This is fundamentally a **reinforcement learning paper** whose core idea is that a language model can learn to solve real-world GitHub issues by being rewarded for generating patches that are textually similar to the ones human developers actually wrote—without needing executable test suites, proprietary teacher models, or human preference labels. The system is an RL training pipeline that takes raw GitHub pull requests as input, converts them into a form where a policy LLM can practice generating code fixes through reasoning, computes a similarity-based reward against the ground-truth patch, and optimises the model using Group Relative Policy Optimization (GRPO). The resulting model not only gets better at issue-solving but also emerges with generalized reasoning capabilities that transfer to out-of-domain tasks like mathematics and function-level coding.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components that operate in a pipeline, feeding into an RL training loop:

1. **Raw PR Data Curation Pipeline** — collects, aggregates, filters, and enriches GitHub pull requests into a structured dataset containing issues, code context, and oracle patches. This operates once, offline, before RL training begins.

2. **Seed RL Dataset** — a curated subset of 273k high-quality PR instances, each containing (a) an issue description, (b) the full content of all files that need modification plus some relevant unmodified files, and (c) the oracle patch—the exact code changes the human developer merged to resolve the issue.

3. **Policy LLM** — the language model being trained (initialised from Llama-3.3-70B-Instruct). It receives an instantiated prompt containing an issue and full file contents, then generates a response consisting of a thinking section followed by search/replace edit blocks.

4. **Reward Function** — a rule-based evaluator that checks two things: (a) whether the model's output is correctly formatted (if not, reward = -1), and (b) if formatted correctly, the `difflib.SequenceMatcher` similarity score between the predicted patch and the oracle patch (a float from 0 to 1).

5. **GRPO Optimiser** — the reinforcement learning algorithm that updates the policy LLM's weights. For each training prompt, it samples 16 rollouts from the current policy, normalises their rewards within the group, computes advantage estimates, and maximises a clipped surrogate objective with a KL penalty against a reference policy.

Information flows as follows: raw GitHub events and git clones enter the data curation pipeline, which produces the seed RL dataset. During RL training, a batch of 32 issues is sampled, each instantiated into the prompt template with its code context. The policy LLM generates 16 rollouts per issue (512 total rollouts per batch). Each rollout's reward is computed by extracting the patch from the model's output and comparing it to the oracle patch. The GRPO objective is computed from these rewards, and one Adam optimisation step is performed per global batch. This loop runs for 1,600 steps.

### 3.3 Roadmap for the Deep Dive

- **First**, the raw PR data curation pipeline (Appendix A), because the entire approach depends on having high-quality training instances where the "correct answer" (the oracle patch) is known. Understanding the filtering, aggregation, and enrichment steps explains what the model actually learns from.

- **Second**, the seed RL dataset construction, which takes the raw curated PRs and applies additional heuristics to select 273k high-quality instances—the actual training data for RL. This is the bridge between data curation and the RL training loop.

- **Third**, the prompt template and reward function (Section 2.1), which together define the task interface and the optimisation signal. The prompt template determines what input the model sees and what output format it must produce; the reward function determines what constitutes progress. These are the core design choices that make RL work for software engineering.

- **Fourth**, the GRPO training objective, including the mathematical formulation, hyperparameters, and training configuration. This explains how the reward signal is converted into weight updates.

- **Fifth**, the scaffolding for evaluation—Agentless Mini (Appendix B)—because the model is trained on one subtask (repair given complete file context) but evaluated on a multi-step pipeline (localisation, repair, test generation, reranking). Understanding this gap explains the generalisation claim.

- **Sixth**, the SFT baseline construction (Appendix C), which serves as the key experimental control to isolate the effect of RL versus supervised imitation.

### 3.4 Detailed, Sentence-Based Technical Breakdown

#### The Raw Pull Request Data Curation Pipeline

The foundation of SWE-RL is a massive dataset of GitHub pull requests, constructed through a multi-stage pipeline detailed in Appendix A and illustrated in Figure 6. The pipeline draws from two data sources and applies several processing stages before producing the raw PR instances from which the RL seed dataset is sampled.

**Data Sources.** The curation requires two complementary sources of information. First, **all GitHub events** occurring on pull requests—including issue mentions, user discussions, review comments, and code changes—are obtained from GHArchive (Grigorik, 2025), which archives every public GitHub event. The authors collect events from January 1, 2015 to August 31, 2024. Second, to obtain the actual source code at the correct point in each repository's history, the authors clone entire repositories with full commit history using `git clone`, rather than downloading specific code snapshots via the GitHub API (GitHub, 2022). This decision matters because pull requests occur at different commit stages—a developer might fork a repository, work on a branch, and submit a PR, but the target branch may have advanced in the meantime. Cloning the full repository preserves the commit graph needed to identify the correct merge base. The authors report successfully cloning and processing 4.6 million repositories.

**PR Data Aggregation.** The collected events and git clones are disconnected entities that must be unified per-PR. The aggregation stage first filters for merged PRs only (open or rejected PRs are discarded, since they have no ground-truth patch to serve as a reward target). For each merged PR, the system gathers all associated conversational events and sorts them chronologically. Critically, it uses the PR's `base_commit` and `head_commit` hashes to identify the merge base—the common ancestor commit where the developer's branch diverged from the target branch. This is the actual starting point of the developer's work, and retrieving file contents at the merge base (rather than at the time of the PR or at the time of merge) ensures the model sees the code as the developer saw it when they began their fix. The system saves all intermediate commits between the merge base and the head commit, as well as the full cumulative patch representing all changes from start to finish. Finally, it scans each aggregated PR to identify patterns resembling issue references (e.g., "Fixes #123", "Closes #456") and associates matched issues with the PR. This produces 24 million aggregated PR instances.

**Relevant Files Prediction.** An aggregated PR includes only the files actually modified. The authors observed a critical problem in early experiments: when the model is conditioned only on files that need editing, it learns a bias—it always generates edits for every file presented and cannot handle "noisy" files (files that are present but not intended for modification). This issue was also noted in the SWE-bench paper's fine-tuning experiments (Jimenez et al., 2023). To counter this, the pipeline uses Llama-3.1-70B-Instruct to predict a list of files that are relevant to the issue but do NOT need modification. These unmodified relevant files are included alongside the actually changed files in the training context. This teaches the model to discriminate: it must determine which files to edit and which to leave untouched, a crucial skill for real-world issue resolution where the set of candidate files is not pre-filtered.

**Data Filtering.** GitHub PRs are noisy, containing many instances unsuitable for training (bot-generated updates, version bumps, documentation-only changes). The authors implement a series of filters designed to "maximize the recall of high-quality PRs while permitting a certain level of noise." First, any PR whose title, description, or author username contains keywords like "[bot]", "dependabot", "renovate", "bump", or "automerge" is removed. Second, PRs with empty changes or extremely large numbers of changed files (e.g., accidental data file uploads) are excluded. Third, a fine-grained set of filters from CodeLlama (Rozière et al., 2023) examines each code change hunk individually, flagging changes like lock file updates or version number increments; PRs where ALL code hunks are flagged by these filters are removed entirely. After filtering, approximately 11 million unique PR instances remain.

**Decontamination.** Throughout the curation process, all repositories used by SWE-bench are excluded to prevent the model from seeing the evaluation instances during training.

#### The Seed RL Dataset

From the 11 million filtered PR instances, the authors select 273k high-quality instances to form the seed RL dataset $D_{\text{seed}}$. This selection applies additional heuristics (Section 2, Appendix C): a PR should include at least one linked issue, the issue should describe a bug-fixing request (not a feature addition or documentation change), and the code changes should involve programming files (not configuration, documentation, or data files). Each item in $D_{\text{seed}}$ contains three components:

- **`issue`**: the issue description, which is the natural language text describing the bug or problem. This is what the model receives as the problem statement.
- **`ctx`**: the code context required to solve the issue. This includes both files that need to be modified and the unmodified but relevant files predicted by Llama-3.1-70B-Instruct. Critically, the complete content of each file is provided, not just snippets or diffs. This design choice is deliberate: by providing the full file, the model is implicitly forced to identify the precise location of the bug within the file before suggesting edits, teaching it both diagnosis and repair.
- **`patch_gt`**: the oracle patch—the cumulative code changes the human developer merged to resolve the issue. This is the ground truth used for reward computation.

#### The Prompt Template

Each data item is transformed into a training prompt using the template shown in Figure 2 (with the complete version in Appendix D). The template has three structural components:

**System message.** Instructs the model about its task and output format:

```
A user will ask you to solve a task. You should first draft your thinking
process (inner monologue). Then, generate the solution.
Your response format must follow the template below:
 thinking
Your thoughts or/and draft, like working through an exercise on scratch
paper. Be as casual and as long as you want until you are confident to
generate a correct solution.
 response
<solution>
Final solution presented to the user.
</solution>
```

**User message.** Contains the concrete problem instance, structured into three parts: the issue text delimited by `--- BEGIN ISSUE ---` and `--- END ISSUE ---` markers, the code segments from each relevant file delimited by `--- BEGIN FILE ---` and `--- END FILE ---` markers with each file's full content in a code block, and instructions for the output format—specifically, that the model must generate SEARCH/REPLACE edit blocks following the format:

```
### path/to/file
<<<<<<< SEARCH
[lines to find in existing code]
=======
[lines to replace with]
>>>>>>> REPLACE
```

The prompt explicitly notes that proper indentation must be preserved and that each edit block should be wrapped in a code block.

**Assistant header.** The `<|start_header_id|>assistant<|end_header_id|>` token triggers the model's response.

The design of this template embodies several important choices. First, the thinking/response separation incentivises the model to reason before acting—the model is trained (via RL) to use the thinking section for diagnosis, reflection, and planning before committing to specific edits. Second, the SEARCH/REPLACE format (inherited from Agentless, Xia et al., 2024) is a structured patch format that is both human-readable and parseable: the SEARCH block specifies exactly what lines to find in the existing file, and the REPLACE block specifies what to substitute. This format is deterministic to parse and directly comparable to the oracle patch. Third, providing the entire file content in the prompt (rather than line ranges or diffs) means the model must learn to locate the fault itself—this is the "localisation" skill that is trained implicitly during RL rather than as a separate step.

#### The Reward Function

This is the central technical contribution that enables RL for real-world software engineering. The reward function $R(o)$ takes a single rollout $o$ (the model's complete output, including thinking and solution sections) and produces a scalar reward:

$$R(o) = \begin{cases} -1, & \text{if } o \text{ has wrong format} \\ \text{compare}(\text{patch}_{\text{pred}}, \text{patch}_{\text{gt}}), & \text{otherwise} \end{cases}$$

where $\text{patch}_{\text{pred}}$ is the patch extracted from the model's correctly formatted output, $\text{patch}_{\text{gt}}$ is the oracle patch from the seed dataset, and $\text{compare}$ is Python's `difflib.SequenceMatcher` (Ratcliff and Metzener, 1988).

**What it computes:** first, a format check determines whether the model's output can be parsed into valid SEARCH/REPLACE edit blocks. If the output is malformed—missing the required section delimiters, containing unparseable edit blocks, or failing to produce syntactically valid patches—the reward is $-1$, a hard penalty that strongly discourages format violations. If the output is correctly formatted, the predicted patch is extracted and compared to the oracle patch using `SequenceMatcher`, which computes a similarity score between 0 and 1 based on the longest contiguous matching subsequence. A score of 0 means no similarity; 1 means exact text match.

**Why this form:** the binary format penalty is essential because the training system must later extract patches for SWE-bench evaluation—an unparseable output is useless regardless of its reasoning quality. The choice of `SequenceMatcher` over alternatives (e.g., exact match, edit distance, semantic equivalence) is carefully motivated. An **exact match** reward (1 if the patches are textually identical, 0 otherwise) is far too sparse. The authors' ablation (Section 3.6, Figure 5) demonstrates this: with discrete rewards, "the average discrete reward remains approximately zero upon the completion of training, meaning it struggles to obtain patches exactly matching the oracles." Real-world patches are highly diverse; two developers fixing the same bug might choose different variable names, reorder statements, or restructure logic, producing semantically equivalent but textually different patches. A **semantic equivalence** check (e.g., compiling and testing both patches) would require execution environments that are unavailable at scale. The authors explicitly acknowledge this limitation (Section 5): "This may prevent the policy LLM from exploring alternative, functionally equivalent solutions." The `SequenceMatcher` represents a pragmatic middle ground: it provides a continuous, informative reward signal that captures partial progress (getting 80% of the patch right yields a reward of ~0.8), while being computationally cheap and requiring no execution environment. The continuous reward allows the model to learn incrementally—improving from similarity 0.3 to 0.5 demonstrates progress even if the patch is not yet correct, enabling the RL process to shape behaviour toward human-like edits.

**How the reward is used in the RL loop:** for each issue in a training batch, the policy LLM generates $G = 16$ rollouts (where $G$ is the group size). Each rollout receives its own reward $r_i = R(o_i)$ computed independently. These rewards are then normalised within the group to compute advantages (described in the GRPO section below). The penalty reward of $-1$ serves a second function beyond simple discouragement: because disadvantages are computed relative to the group mean, a rollout with reward $-1$ in a group where most rollouts achieve positive similarity scores will receive a very negative advantage, causing a strong gradient signal away from format-violating behaviour. Conversely, in early training when most rollouts may be format-violating, the group mean will be close to $-1$, and a correctly formatted but imperfect patch with similarity 0.2 will receive a positive advantage, encouraging the model to at least produce valid outputs.

#### Group Relative Policy Optimization (GRPO)

SWE-RL uses GRPO (Shao et al., 2024) as the policy optimisation algorithm. GRPO is a variant of policy gradient methods that eliminates the need for a separate value function (critic) by normalising rewards within a group of rollouts sampled from the same prompt. The objective for a single training step is:

$$J(\theta) = \mathbb{E}\left[\frac{1}{G}\sum_{i=1}^{G} \min\left(\frac{\pi_{\theta}(o_i \mid q)}{\pi_{\theta_{\text{old}}}(o_i \mid q)} A_i, \text{clip}\left(\frac{\pi_{\theta}(o_i \mid q)}{\pi_{\theta_{\text{old}}}(o_i \mid q)}, 1 - \epsilon, 1 + \epsilon\right) A_i\right) - \beta D_{\text{KL}}(\pi_{\theta} \parallel \pi_{\text{ref}})\right]$$

where `$(\text{issue}, \text{ctx}, \text{patch}_{\text{gt}}) \sim D_{\text{seed}}$` is a data point sampled from the seed RL dataset, `$q = \text{form-prompt}(\text{issue}, \text{ctx})$` is the instantiated prompt, and `$\{o_i\}_{i=1}^G \sim \pi_{\theta_{\text{old}}}(\cdot \mid q)$` are the $G$ rollouts sampled from the current policy.

The per-rollout advantage is computed as:

$$A_i = \frac{r_i - \text{mean}(r_1, \dots, r_G)}{\text{std}(r_1, \dots, r_G)}$$

where $r_i = R(o_i)$ is the reward for rollout $i$, $\text{mean}(r_1, \dots, r_G)$ is the average reward across the $G$ rollouts in the group, and $\text{std}(r_1, \dots, r_G)$ is the standard deviation.

The importance ratio $\frac{\pi_{\theta}(o_i \mid q)}{\pi_{\theta_{\text{old}}}(o_i \mid q)}$ measures how much more (or less) likely the current policy is to generate rollout $o_i$ compared to the policy that generated it. The clip operation constrains this ratio to the interval $[1 - \epsilon, 1 + \epsilon]$, preventing excessively large policy updates.

The KL penalty term $D_{\text{KL}}(\pi_{\theta} \parallel \pi_{\text{ref}})$ measures the divergence between the current policy and a reference policy (typically the initial model), keeping the policy from drifting too far from its starting distribution.

**What it computes:** for each of the $G$ rollouts in a group, the objective computes a clipped surrogate loss. The advantage $A_i$ is positive for rollouts that are better than the group average and negative for those that are worse. The min operation implements a conservative update: when the advantage is positive, the policy is encouraged to increase the probability of the rollout, but only up to the clip boundary $1 + \epsilon$; when the advantage is negative, the policy is encouraged to decrease the probability, but only down to $1 - \epsilon$. This clipping—inherited from PPO (Proximal Policy Optimization)—prevents destructively large updates from single batches. The KL penalty provides an additional regularisation force toward the reference policy.

**Why this form:** GRPO is chosen over alternatives like standard PPO or REINFORCE for two reasons. First, by using group-relative normalisation rather than a learned value function, GRPO eliminates the need to train a separate critic network, which would double the memory and compute requirements for a 70B-parameter model. The group-based normalisation is well-suited to this setting because all 16 rollouts share the same prompt, so their rewards are directly comparable—a rollout achieving similarity 0.8 is clearly better than one achieving 0.1 for the same issue. Second, the clipping mechanism is critical for stable training at scale: the policy is a 70B-parameter transformer, and unconstrained policy gradients can cause rapid divergence. The combination of clipping and KL penalty ensures that the model improves gradually while remaining within a trust region around the initial Llama-3.3-70B-Instruct distribution, preserving the base model's general capabilities while specialising its issue-solving behaviour.

**Training Configuration.** The model is trained for 1,600 steps with a global batch size of 512. This means 32 distinct issues are sampled per batch, and from each issue, 16 rollouts are generated (32 × 16 = 512). For every global step, a single Adam optimisation step is performed. The authors use 512 NVIDIA H100 GPUs; a full training run takes approximately 32 wall-time hours. The context window is 16k tokens. The hyperparameters $\epsilon$ and $\beta$ are mentioned as components of the GRPO objective but their specific values are not provided in the paper's main text. The reference policy $\pi_{\text{ref}}$ is initialised from the same Llama-3.3-70B-Instruct checkpoint as the policy, and $\pi_{\theta_{\text{old}}}$ is updated periodically to track the current policy.

**Why 1,600 steps and 512 batch size:** the paper does not provide explicit justification for these numbers, but they reflect the practical constraints of large-scale RL fine-tuning. With 273k seed instances, 1,600 steps at 32 issues per step means the model sees approximately 51,200 issues in total—less than one full epoch over the training data. This is consistent with the RL fine-tuning paradigm: the model starts from a strong pretrained checkpoint and needs only enough RL steps to learn the reward-maximising behaviour without overfitting to the specific patch format or reward function quirks. The 16-rollout group size balances two competing needs: too few rollouts per group would give noisy advantage estimates (high variance in the group mean and standard deviation), while too many would reduce the number of distinct issues seen per step (since the global batch size is fixed).

#### Agentless Mini: The Evaluation Scaffold

While the RL training focuses on a single task—generating repair edits given an issue and complete file contents—evaluation on SWE-bench requires additional capabilities: file-level fault localisation, reproduction test generation, regression test selection, and reranking. To bridge this gap, the authors developed Agentless Mini, a simplified and enhanced version of the Agentless scaffold (Xia et al., 2024). The design principles, described in Appendix B and illustrated in Figure 7, are straightforward component decomposition, parallelisation, and scalability—each step can be independently scaled.

**Step 1: Localisation and repair.** The localisation step uses a prompting-based approach: given the issue description and the repository's file structure (a tree of all file paths), the model generates multiple samples predicting which files are likely to contain the bug. These predictions are consolidated into unique file sets. This is a significant simplification from the original Agentless, which employed two additional detailed steps to identify related code elements and files, plus a separate embedding-based retrieval model. During repair, the model is conditioned on the full content of the predicted relevant files (the same format as training) and generates SEARCH/REPLACE edits. Multiple repair samples are generated from different localisation sets to explore the patch space comprehensively.

**Step 2: Reproduction tests generation and selection.** The model generates reproduction tests—Python test functions that exhibit specific behaviour: they must output "Issue reproduced" when run on the buggy code and "Issue resolved" when run on the fixed code. Agentless Mini improves on the original Agentless in two ways. First, rather than generating tests from the issue description alone, the model first retrieves a relevant test file to use as a style guide and context. Second, instead of selecting a single majority-voted test, Agentless Mini selects multiple top test samples based on voting results. In the main evaluation, the top 30 reproduction tests are used (scaling experiments in Section 3.4 explore the effect of varying this number). Tests are filtered by executing them on the original codebase and verifying they output "Issue reproduced"—tests that fail this check are discarded.

**Step 3: Regression test selection.** This step identifies passing tests in the original codebase that should still pass after the fix. The process begins by executing all tests before any modifications (this is model-free and needs to be done only once per repository). An optional inference step then filters out tests that are expected to fail after the issue is fixed (these are not considered regression tests). The remaining passing tests serve as a correctness guard: any candidate patch that breaks previously passing tests is penalised.

**Step 4: Reranking.** This is the selection mechanism that picks the single best patch from potentially hundreds of candidates. For each issue, every candidate patch is first executed against the regression tests; patches that cause the fewest existing test failures are preferred. Then, for each patch, the top-N reproduction tests are run. A patch is marked as passing a reproduction test if execution outputs "Issue resolved". The final selection uses the dual execution agreement objective from CodeT (Chen et al., 2023): patches that pass the SAME set of reproduction tests form a consensus group, and each group is scored as $|P| \times |T|^2$, where $|P|$ is the number of patches in the group and $|T|$ is the number of reproduction tests they all pass. This scoring prioritises test coverage (the quadratic $|T|^2$ term heavily rewards passing more tests) over patch count (the linear $|P|$ term provides a secondary sorting criterion within groups with equal test coverage). The consensus group with the highest score is identified, and the best patch within that group is selected by majority voting among the group's patches.

**Why this scaffold design matters for the paper's claims:** the fact that Llama3-SWE-RL-70B can perform Steps 1, 2, and 3—which it was never explicitly trained for—is the evidence for the paper's claim of generalisation. During RL training, the model only practices generating repair edits from full file contexts (Step 1, repair). The localisation (predicting files from repository structure), test generation, and test selection capabilities emerge through the RL process. The authors attribute this to the model developing general reasoning skills (self-reflection, exploring alternatives, systematic decomposition) that transfer to these superficially different but structurally related sub-tasks.

#### The SFT Baseline: Controlled Comparison with Imitation Learning

To isolate the effect of RL versus supervised fine-tuning, the authors construct a strong SFT baseline, Llama3-SWE-SFT-70B, trained on the same base model (Llama-3.3-70B-Instruct) using a carefully constructed data mixture. The data generation pipeline, detailed in Appendix C and Figure 8, is inspired by Magicoder's OSS-Instruct technique (Wei et al., 2024).

**Seed selection.** From the raw PR dataset, high-quality PR seeds are selected using the same heuristics as the RL seed dataset: at least one linked issue, a bug-fix description, and programming file changes. These serve as the seeds for synthetic data generation.

**Synthetic data generation.** Using Llama-3.3-70B-Instruct (the same base model, used as a teacher for data generation), two types of training data are synthesised. For **localisation data**, the model receives the issue description, repository structure, and file paths of edited and relevant files as hints, and is asked to generate a reasoning process followed by a prioritised list of relevant files. For **code editing data**, the model receives the ground-truth PR and patch as guidance and is prompted to generate the SEARCH/REPLACE edit blocks with chain-of-thought reasoning.

**Filtering.** Both types of synthetic data are filtered against ground truth. For localisation, the model's predicted file list must include all genuinely edited files, and these must be ranked with high priority. For editing, all SEARCH/REPLACE blocks must adhere to the correct format, and all search paths and blocks must accurately match within the provided file context. This filtering ensures the SFT data has high precision but potentially at the cost of diversity—only generated outputs that closely match the human-written patches survive.

**Data mixture.** The final SFT dataset is a mixture of the synthetic localisation and editing data, coding SFT data from Llama 3 (Dubey et al., 2024), and general SFT data from Llama 3. The inclusion of general coding and dialog data is deliberate: without it, an SFT model trained only on issue-solving data would catastrophically forget general capabilities. The authors note that this careful mixture was necessary to maintain generalisability—a requirement the RL model does not have, since the KL penalty in GRPO naturally constrains deviation from the base model.

**Training.** Llama3-SWE-SFT-70B is trained on a 16k context window for 2 billion tokens, using the same base model initialisation as the RL model.

**Key differences from RL training.** Unlike the RL model, which requires only the seed PR dataset to trigger the RL loop, the SFT baseline needs synthetic data generation (requiring expensive inference from the 70B teacher model for chain-of-thought generation), additional data mixture curation to maintain generalisation, and ground-truth filtering. The SFT model learns to imitate the specific patterns in the synthetic data, including the teacher model's reasoning style and formatting conventions. The RL model, in contrast, discovers strategies through trial-and-error optimisation against the reward signal, without being shown examples of "good" reasoning or correct edits. This fundamental difference in learning paradigm—imitation versus reinforcement—is what the paper argues leads to the observed generalisation gap.

## 4. Key Insights and Innovations

### Innovation 1: Reinforcement Learning Can Be Made to Work for Real-World Software Engineering Using Patch Similarity as a Reward—No Execution, No Teacher, No Human Labels

The dominant assumption in applying RL to coding tasks—established by DeepSeek-R1 and subsequent work—is that *execution feedback* is the necessary reward signal: pass the unit tests (1), fail the unit tests (0). This assumption is so deeply embedded that it has shaped the entire research direction, confining RL for coding to competitive programming benchmarks (Codeforces, LiveCodeBench, APPS) where code is self-contained and test harnesses are readily available. SWE-RL breaks this assumption by demonstrating a different type of reward altogether: **textual similarity between the model's generated patch and the ground-truth patch written by a human developer**. No test execution. No sandbox environments. No human preference labels. Just `difflib.SequenceMatcher`.

This is a conceptual shift, not merely a domain adaptation. The prior paradigm treats correctness as a binary property—the code either works or it doesn't—and RL's role is to search the space of programs until one satisfies the test oracle. SWE-RL treats correctness as a *continuous similarity metric*, where the model receives partial credit for partial progress. An exact-match reward (the "discrete" ablation in Section 3.6) is functionally useless: the average reward stays near zero throughout training because real-world patches are too diverse to match exactly. The continuous reward provides a gradient of improvement—going from 0.3 similarity to 0.5 similarity is rewarded, which shapes the model's behaviour incrementally. This is not an incremental tweak; it is a fundamentally different reward hypothesis that opens RL to the entire class of software engineering tasks where execution is impractical.

The significance extends beyond performance. If execution-based rewards were the only viable RL signal for coding, then RL for software engineering would remain bottlenecked by the availability of executable environments—a requirement that fails for most real-world repositories due to dependency complexity, non-deterministic behaviour, and missing configurations. By showing that a purely text-based reward produces a model that achieves 41.0% on SWE-bench Verified (Table 1), the paper establishes that **the oracle patch itself carries sufficient information to serve as a training signal**—a finding that will generalise to any domain where human-generated reference solutions exist in large quantities (code review history, bug-fix databases, refactoring commits). This converts software evolution data from a passive record of what happened into an active training resource.

The reward ablation (Figure 5) is the key piece of evidence here. The continuous reward reaches 34.8% repair accuracy (oracle localisation) versus 29.0% for discrete, and the training curves show discrete rewards flatlining near zero—confirming that the continuity of the reward signal, not just its existence, is what enables learning.

---

### Innovation 2: Reinforcement Learning on Software Data Produces Generalised Reasoning, While Supervised Fine-Tuning Produces Task-Specific Specialisation

The paper's most provocative claim is not about SWE-bench performance—it is about what happens *outside* the training distribution. Table 3 presents a result that, if robust, changes how the field should think about training software engineering models: the RL-trained model outperforms its base model on five out-of-domain benchmarks (HumanEval+, BigCodeBench-Hard, CRUXEval, MATH, MMLU), while the SFT-trained model *degrades* on four of five. This is not a metric gain on the target task; it is evidence of a fundamentally different learning dynamic.

The prior paradigm—established by Lingma-SWE-GPT, SWE-Gym, SWE-Fixer, and essentially all SWE-bench fine-tuning efforts—treats SFT on task-relevant data (often distilled from proprietary teachers) as the natural path to improvement. The implicit assumption is that more task-specific training data produces better task-specific performance, and that generalisation is maintained by mixing in general-domain SFT data. The paper's SFT baseline follows this recipe precisely: synthetic code editing data + general coding SFT + general Llama 3 dialog data, trained for 2B tokens. The result is what should be a strong baseline—it achieves 36.2% on SWE-bench Verified (Table 1), substantially better than base Llama-3.3-70B-Instruct. But it regresses on HumanEval+ (76.2 → 73.2), BigCodeBench-Hard (29.1 → 24.3), and MMLU (86.49 → 85.26).

What SWE-RL shows is that **task performance and generalisation are not in tension when using RL**—they appear to reinforce each other. The model trained exclusively on issue-solving data (no math, no function-level coding, no general knowledge) improves on MATH from 63.2 to 73.7 (strict) and on CRUXEval-I from 60.5 to 71.6. The authors attribute this to emergent reasoning behaviours—self-reflection, exploring alternatives, divide-and-conquer (Figure 3)—that are incentivised by the RL objective but not explicitly present in the training data. SFT, by contrast, teaches the model to reproduce the *surface patterns* of the synthetic data distribution, which may include reasoning-like language but does not generalise because the model hasn't been optimised to *discover* reasoning strategies; it has been optimised to *mimic* them.

This is a negative result with positive implications. The negative result is that even carefully curated SFT with general-domain data mixing causes capability regression on out-of-domain tasks—a finding that calls into question the dominant SWE-bench fine-tuning paradigm. The positive implication is that RL provides a path around this tradeoff: by constraining the policy to remain close to the reference model (via the KL penalty in GRPO) while optimising for task reward, the model learns to add reasoning capabilities without overwriting existing knowledge. This is not a small refinement—it suggests that the choice of training objective (SFT cross-entropy vs. RL policy gradient) determines whether the model generalises or specialises, independent of what data is used.

---

### Innovation 3: The Concept of "Aha Moments" in Software Engineering—Emergent Reasoning Behaviours That Were Never Explicitly Programmed

DeepSeek-R1 introduced the memorable framing of "aha moments"—instances during RL training where the model spontaneously allocates more thinking time, re-evaluates its initial approach, and discovers a correct solution through reflection rather than through direct pattern matching. These were observed in competition-level math and coding. SWE-RL claims to demonstrate the same phenomenon in real-world software engineering, which carries a different weight.

The reason this matters is that real-world software engineering has a fundamentally different structure from competition math. In math, the reasoning path is self-contained—the problem statement contains all necessary information, and the solution follows a deductive chain. In software engineering, the model must navigate an existing codebase, interpret an often-ambiguous natural language issue description, identify which of potentially thousands of files contains the bug, understand the *intent* of the surrounding code, and produce a minimal edit. The reasoning is not purely deductive—it involves hypothesis formation, evidence gathering across multiple files, and iterative refinement of understanding. If "aha moments" emerge in this setting, it suggests that RL incentivises a general cognitive strategy—**re-evaluating assumptions when encountering inconsistency**—rather than a domain-specific reasoning pattern.

The examples in Figure 3 are qualitative and should be treated as suggestive rather than definitive (the paper doesn't quantify how frequently such moments occur or whether they causally produce correct solutions). But the framing is intellectually productive because it connects SWE-RL to DeepSeek-R1's broader narrative about RL as a *reasoning unlock* rather than a *task trainer*. The model isn't just learning what patches look like—it's learning *how to think about bugs*. And critically, the same behaviours appear in out-of-domain tasks (Figure 3, right panels), where the model applies self-reflection and exploring-alternatives strategies to math and function implementation problems it was never trained on. This transfer suggests that the reasoning behaviours are not surface-level patterns from the issue-solving data but genuine cognitive strategies that the model has *discovered* through interaction with the reward signal.

The evidence is primarily the qualitative examples in Figure 3 plus the quantitative out-of-domain improvements in Table 3, which together suggest that the emergent behaviours are real and consequential. But the paper does not provide a mechanistic analysis of how or why they emerge—this remains an observation in need of deeper study.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** All experiments use SWE-bench Verified (OpenAI, 2024), a human-verified subset of SWE-bench containing 500 real-world GitHub issues. The authors explicitly exclude all repositories used by SWE-bench during data curation to prevent contamination. Performance is reported as the fraction of these 500 issues for which the model's selected patch correctly resolves the issue (pass@1). The evaluation uses the standard SWE-bench grading infrastructure.

- **Base model(s).** The RL model, Llama3-SWE-RL-70B, is trained on top of Llama-3.3-70B-Instruct (Dubey et al., 2024). The authors argue this model is a strong, representative open-weight LLM at the sub-100B scale. For the SFT baseline, the same Llama-3.3-70B-Instruct checkpoint is used as the starting point. The out-of-domain evaluation in Table 3 compares Llama3-SWE-RL-70B against the original Llama-3.3-70B-Instruct and the SFT variant.

- **Metrics.** The primary metric is **SWE-bench Verified pass@1 (%)**—the percentage of the 500 test issues for which the single submitted patch passes all evaluation tests. For repair-only analysis (Table 2), the metric is **repair performance (oracle)**—accuracy with oracle file localisation, using greedy decoding. For out-of-domain tasks (Table 3), metrics follow each benchmark's standard: pass@1 for HumanEval+, BigCodeBench-Hard, CRUXEval, and MATH; macro-averaged accuracy across categories for MMLU. For MATH, a "strict" version requires the exact "Answer: ..." format, while a "lenient" version relaxes this to include any `\boxed{...}` output.

- **Baselines.** The paper compares against several categories:
  - **Base model:** Llama-3.3-70B-Instruct with greedy decoding and with 20-sample majority voting (Table 2).
  - **SFT baseline:** Llama3-SWE-SFT-70B, trained on synthetic code editing data, Llama 3 coding SFT, and general Llama 3 SFT data using the Magicoder-style generation pipeline (Appendix C).
  - **External open-source models:** SWE-Llama-13B and SWE-Llama-7B (Jimenez et al., 2023), Lingma-SWE-GPT-7B and -72B (Ma et al., 2024), SWE-Gym-32B (Pan et al., 2024), and SWE-Fixer-72B (Xie et al., 2025)—all reported with their respective open-source scaffolds.
  - **Proprietary models:** GPT-4o, Claude-3.5-Sonnet, o1-preview, DeepSeek-V3, and DeepSeek-R1—all reported with their best-performing open-source scaffolds as listed on the SWE-bench leaderboard.

- **Generation budget / compute accounting.** For the main SWE-bench evaluation, the authors generate 500 repair patches per issue using a temperature of 1.0 and use the top 30 reproduction tests for execution and reranking. The scaling analysis (Section 3.4) systematically varies both the number of repair samples (20, 40, 80, 160, 320, 500) at a fixed 30 test samples, and the number of test samples (1, 5, 10, 20, 30) at a fixed 500 repair samples. For the baseline comparison (Table 2), only a single repair edit is generated with greedy decoding. For RL training, the generation budget is 16 rollouts per prompt per global step, with the prompt template (Figure 2) enforcing a thinking-then-solution structure. The paper does not report FLOPs for training—only wall-clock time (32 hours on 512 H100 GPUs for 1,600 steps).

- **Cross-validation / statistical protocol.** The paper does not use cross-validation for SWE-bench evaluation—each issue is evaluated once with the single selected patch (standard SWE-bench practice). No error bars are reported for SWE-bench results due to the expense of multiple evaluation runs. For statistical significance of out-of-domain improvements, the paper uses Eval Arena (Wang et al., 2024a) to assess whether observed gains meet significance thresholds: improvements of approximately 0.8 percentage points on MMLU, 3 points on CRUXEval, and over 3 points on full MATH are reported as individually significant, and the aggregate across benchmarks achieves significance at the 0.05 level.

#### SWE-bench Verified End-to-End Performance

**Headline result.** Llama3-SWE-RL-70B achieves a **41.0% solve rate** on SWE-bench Verified with Agentless Mini (Table 1). This is the best reported performance among medium-sized models with less than 100B parameters and is comparable to GPT-4o's 38.8% with the same scaffold. Table 1 presents the full comparison:

**Key comparisons.** Llama3-SWE-RL-70B's 41.0% is substantially ahead of the next-best medium-sized model (SWE-Fixer-72B at 32.8%) and also exceeds its SFT counterpart (36.2%) by 4.8 percentage points—a 13.3% relative improvement. The gap between the RL model and the SFT baseline on the same scaffold demonstrates that the RL training process specifically improves end-to-end issue-solving capability beyond what supervised imitation achieves. Compared to proprietary models, Llama3-SWE-RL-70B surpasses GPT-4o's 38.8% (with Agentless) and approaches o1-preview's 41.3%, despite being a 70B open model. The paper explicitly notes that all other open-source baselines "include distilled outputs from GPT-4o or Claude-3.5-Sonnet in the training data" (Table 1 notes), while Llama3-SWE-RL is "trained solely with publicly available data through our reinforcement learning technique SWE-RL, without relying on any proprietary LLMs in the pipeline."

**The SFT baseline scores 36.2%**, which is itself notable—it outperforms Lingma-SWE-GPT-72B (28.8%), SWE-Gym-32B (32.0%), and SWE-Fixer-72B (32.8%), despite these models incorporating proprietary teacher distillation into their training. The paper does not elaborate on why the SFT baseline is this strong, but it likely reflects the carefully curated data mixture (synthetic code editing + Llama 3 coding SFT + general SFT) and the quality of the Magicoder-style generation pipeline.

#### Baseline Comparison: Repair-Only Performance

**Repair ability in isolation.** Table 2 provides a controlled comparison of the base model, the SFT variant, and the RL model on repair-only performance—given oracle-localised files (the model doesn't need to find the buggy file, only fix it), how often does it produce a correct repair?

| Model | Setting | Correct format | Repair (oracle) |
|---|---|---|---|
| Llama-3.3-70B-Instruct | Greedy | 12.2% | 5.4 |
| Llama-3.3-70B-Instruct | Majority voting (20) | 44.6% | 16.6 |
| Llama3-SWE-SFT-70B | Greedy | 96.2% | 29.6 |
| Llama3-SWE-RL-70B | Greedy | 95.6% | 34.8 |

**Interpretation.** The base Llama-3.3-70B-Instruct is profoundly incapable of producing correctly formatted SEARCH/REPLACE edits: only 12.2% of greedy outputs are parseable. Even with 20-sample majority voting (pre-filtering malformed outputs), only 44.6% are correctly formatted, and repair accuracy reaches just 16.6%. This is the starting point—the model has essentially no inherent ability to perform structured code editing. SFT dramatically improves format accuracy to 96.2% and boosts repair performance to 29.6%—the model learns the output conventions and the basic mapping from issues to patches. The RL model achieves essentially the same format accuracy (95.6%) but reaches 34.8% repair performance, a 5.2 percentage-point gain over SFT. This gap is the direct evidence that RL teaches the model something about *correctness* beyond what SFT's imitation learning provides—the model is not just better formatted but actually better at producing patches that resolve the issue.

**The gap between RL and SFT (34.8 vs. 29.6) on oracle-localised repair is the cleanest signal of RL's benefit**, because it eliminates confounding factors from the localisation, test generation, and reranking pipeline steps. Under identical input conditions (same files, same decoding strategy), the RL model produces correct patches 17.6% more often than the SFT model.

#### Scaling Analysis: More Samples → Better Results

**Figure 4 (left) - scaling repair samples.** With 30 fixed reproduction tests, varying the number of repair samples from 20 to 500:

| Repair samples | SWE-bench Verified score |
|---|---|
| 20 | 33.6 |
| 40 | 35.6 |
| 80 | 37.0 |
| 160 | 40.0 |
| 320 | 40.6 |
| 500 | 41.0 |

The largest gain occurs between 20 and 160 samples (33.6 → 40.0, a 6.4 percentage-point jump). Beyond 160, the improvement decelerates sharply (40.0 → 40.6 → 41.0), suggesting the model's pass@k for correct patches saturates around this point—additional samples beyond 160 rarely produce patches that are both correct AND survive the reranking process.

**Figure 4 (right) - scaling reproduction tests.** With 500 fixed repair samples, varying the number of reproduction tests from 1 to 30:

| Test samples | SWE-bench Verified score |
|---|---|
| 1 | 38.8 |
| 5 | 39.8 |
| 10 | 40.6 |
| 20 | 41.0 |
| 30 | 41.0 |

More reproduction tests improve reranking accuracy, likely because they provide more discriminating signals for the CodeT dual-execution-agreement scoring (more tests → finer-grained consensus groups → better selection among candidate patches). The saturation at 20 tests suggests that the benefit of additional tests plateaus once the consensus groups are sufficiently refined.

**Joint effect.** The best configuration (500 repair samples + 20-30 reproduction tests) reaches 41.0%. The paper does not explore whether further scaling beyond 500 repair samples would continue to yield gains, but the flattening curve suggests diminishing returns.

#### Generalisation to Out-of-Domain Tasks

**Table 3** evaluates Llama-3.3-70B-Instruct, Llama3-SWE-SFT-70B, and Llama3-SWE-RL-70B on five out-of-domain benchmarks using zero-shot greedy decoding:

| Benchmark | Llama-3.3-70B-Instruct | SFT | RL | Δ (RL - Base) | Δ (RL - SFT) |
|---|---|---|---|---|---|
| HumanEval+ | 76.2 | 73.2 | **79.9** | +3.7 | +6.7 |
| BigCodeBench-Hard (I) | 28.4 | 25.7 | **28.4** | 0.0 | +2.7 |
| BigCodeBench-Hard (C) | 29.1 | 24.3 | **29.1** | 0.0 | +4.8 |
| CRUXEval-I | 60.5 | 68.4 | **71.6** | +11.1 | +3.2 |
| CRUXEval-O | 61.9 | 75.1 | **75.5** | +13.6 | +0.4 |
| MATH (strict) | 63.2 | 54.0 | **73.7** | +10.5 | +19.7 |
| MATH (lenient) | 70.9 | 71.7 | **73.7** | +2.8 | +2.0 |
| MMLU | 86.49 | 85.26 | **86.82** | +0.33 | +1.56 |

**The pattern is consistent.** The RL model outperforms both the base model and the SFT variant on every benchmark—7 of 7 in the strict comparison, 8 of 8 including MATH (lenient). The SFT model, in contrast, underperforms the base model on 4 of 7 strict benchmarks (HumanEval+, BigCodeBench-Hard at both instruction and completion settings, MATH strict, and MMLU), with notable drops on MATH strict (63.2 → 54.0, a 9.2-point decline) and BigCodeBench-Hard (C) (29.1 → 24.3).

**The largest RL gains are on reasoning-intensive tasks.** CRUXEval-I (+11.1 over base, +3.2 over SFT), CRUXEval-O (+13.6 over base, +0.4 over SFT), and MATH strict (+10.5 over base, +19.7 over SFT) show the biggest improvements. CRUXEval requires reasoning about code execution—predicting input from output (I) and output from input (O)—while MATH requires multi-step mathematical deduction. These are precisely the tasks where the "aha moment" behaviours (self-reflection, exploring alternatives) would be most beneficial. HumanEval+ shows a more modest gain (+3.7 over base), consistent with the base model already being strong on simple function implementation.

**BigCodeBench-Hard shows zero net change from base to RL.** Both the base model and the RL model score 28.4 (I) and 29.1 (C), while the SFT model regresses. This could suggest that library-use code generation is less amenable to the reasoning skills developed through issue-solving RL, or that the base model's ceiling on this benchmark is close to 29 and RL does not push past it.

**MATH strict vs. lenient is revealing.** The strict evaluation requires the model to output answers in a specific "Answer: ..." format that only the RL model consistently follows. The base model scores 63.2 strict vs. 70.9 lenient (a 7.7-point gap), suggesting many correct answers are embedded in non-standard formatting. The RL model closes this gap entirely (73.7 both strict and lenient)—it has learned to produce structured, parseable outputs even in a domain (math) it was never trained on. This is consistent with the RL process rewarding format compliance in the code editing context, and that meta-skill transferring to math answer formatting.

**Statistical significance.** The paper reports that improvements of >0.8 points on MMLU, >3 points on CRUXEval, and >3 points on full MATH are individually significant by Eval Arena thresholds, and the aggregate across benchmarks is significant at the 0.05 level. However, individual benchmark gains like +3.7 on HumanEval+ or +0.33 on MMLU by themselves may not reach significance—the strength of the claim comes from the consistent direction across all benchmarks.

### Ablation Studies and Robustness Checks

**Reward function type: continuous vs. discrete.** Figure 5 and the accompanying table show the comparison:

| Reward type | Correct format | Repair (oracle) |
|---|---|---|
| Discrete (exact match) | 94.2% | 29.0 |
| Continuous (SequenceMatcher) | 95.6% | 34.8 |

The continuous reward achieves substantially better repair performance (34.8 vs. 29.0) despite nearly identical format accuracy. The training dynamics reveal why: the discrete reward curve remains near zero throughout training, indicating the model almost never produces patches that exactly match the oracle, even after 1,600 steps. Without partial credit, the RL signal is too sparse to guide learning. The continuous reward provides a meaningful gradient—the model can observe that moving from similarity 0.3 to 0.5 improves its advantage, shaping incremental improvement toward human-like patches. This ablation directly tests the paper's core design choice and confirms it is essential: reward sparsity makes RL non-viable for real-world SE.

**Number of repair samples (Figure 4, left).** Varying repair samples from 20 to 500 with 30 fixed test samples: performance improves substantially from 33.6 to 40.0 between 20 and 160 samples, then plateaus (40.0 → 40.6 → 41.0). The diminishing returns suggest that beyond ~160 samples, the model's pass@k for correct patches is largely exhausted—additional samples rarely produce novel correct solutions that survive reranking. This also implies that inference-time compute scaling has a ceiling determined by the model's inherent repair capability.

**Number of reproduction tests (Figure 4, right).** Varying test samples from 1 to 30 with 500 fixed repair samples: performance improves from 38.8 to 41.0, with gains concentrated between 1 and 20 tests. The saturation at 20 tests suggests that the CodeT consensus-based selection has sufficient discriminating power at this point—additional tests don't meaningfully alter the consensus groups. The 2.2-point gain from 1 to 20 tests indicates that reproduction test generation quality is non-trivial and that scaling test samples provides a modest but reliable improvement.

**SFT baseline as a negative result.** The SFT baseline itself serves as an ablation of training methodology: same base model, same seed PR data (for the synthetic generation), but supervised fine-tuning instead of RL. The results are striking:
- On SWE-bench, SFT achieves 36.2% (vs. 41.0% for RL)—a gap of 4.8 points (Table 1).
- On repair-only with oracle localisation, SFT achieves 29.6% (vs. 34.8% for RL)—a gap of 5.2 points (Table 2).
- On out-of-domain tasks, SFT degrades average performance, while RL improves it (Table 3).

This triple gap—end-to-end, repair-only, and OOD—constitutes the paper's strongest evidence that RL and SFT produce qualitatively different models, not just quantitatively different levels of task mastery. The repair-only gap (5.2 points) is the cleanest measure because it controls for scaffold differences and localisation quality.

**No ablation of the KL penalty or clip parameter.** The paper does not report experiments varying β or ϵ in the GRPO objective, nor does it compare GRPO to alternative RL algorithms (PPO, REINFORCE with baseline). This is a notable omission—the paper's claims depend on GRPO being a suitable optimisation algorithm, but the reader cannot assess whether the RL gains are specific to GRPO's variance reduction strategy or would generalise to other policy gradient methods. Given that the paper's contribution is primarily the application of RL to SE rather than a novel algorithm, this omission is understandable but limits the analysis.

**No ablation of group size G.** The GRPO objective uses G=16 rollouts per prompt. The paper does not explore how sensitive training dynamics or final performance are to this choice. In principle, larger G provides lower-variance advantage estimates but reduces the number of distinct prompts seen per step, while smaller G increases diversity but may produce noisier gradients. This is a standard GRPO hyperparameter that could affect training efficiency and final performance.

**No ablation of the KL penalty reference model.** The reference model π_ref is initialised from the same Llama-3.3-70B-Instruct checkpoint as the policy. The paper does not explore whether periodically updating π_ref or using a frozen reference throughout training affects the generalisation behaviour. The KL penalty is the mechanism hypothesised to preserve base model capabilities during RL, so understanding its sensitivity would strengthen the paper's central claim about RL vs. SFT generalisation.

**No ablation of the relevant-files prediction step.** The data curation pipeline includes predicting unmodified but relevant files to include in the training context, motivated by the observation that models otherwise learn to edit every file they see. The paper does not ablate this feature to quantify its impact. If removing unmodified files significantly degrades repair-only performance (by causing the model to edit irrelevant files), that would confirm the design choice but also reveal a limitation: the model is using file presence as a signal for whether editing is needed, rather than reasoning about bug location from the issue text alone.

**No direct comparison of RL-only vs. SFT+RL.** The paper presents RL starting from the base Llama-3.3-70B-Instruct and SFT starting from the same base. It does not explore whether RL on top of the SFT model (SFT → RL) would yield further improvements or whether the SFT checkpoint's distribution shift would harm RL training dynamics. This multi-stage approach is common in RLHF pipelines and would be a natural extension.

### Critical Assessment

#### Claim 1: SWE-RL is the first RL approach for real-world software engineering using software evolution data and rule-based rewards.

**What the experiments demonstrate.** The paper clearly demonstrates that RL with a continuous patch-similarity reward applied to a 70B Llama model produces substantial improvements on SWE-bench Verified (41.0% vs. essentially 0% for the base model with greedy decoding). The reward ablation (Figure 5) shows that the continuous reward is necessary—the discrete exact-match variant fails to learn. The baseline comparison (Table 2) shows that the base model cannot produce formatted SEARCH/REPLACE edits (12.2% format accuracy) and has negligible repair capability (5.4% with greedy, 16.6% with majority voting), confirming that the RL process is teaching the model a capability it did not previously possess.

**What is not demonstrated.** The claim of "first" is historical and can only be assessed relative to the literature, not experimentally. The paper does not compare against an RL baseline that uses execution-based rewards on the same data (which would test whether patch similarity is superior to execution, or merely a workaround for unavailable execution environments). It also does not compare against alternative reward formulations—e.g., BLEU score between predicted and oracle patches, edit distance, or AST-level similarity—that might provide different learning dynamics. The choice of `SequenceMatcher` is pragmatic but not empirically validated against alternatives.

**Bottom line.** The claim that SWE-RL is the first RL approach for real-world SE is plausible based on the literature review, but the experiments only test one instantiation of the idea (GRPO + SequenceMatcher reward). They do not establish that the specific reward design is optimal or that RL is superior to other training paradigms beyond SFT.

#### Claim 2: Llama3-SWE-RL-70B achieves 41.0% on SWE-bench Verified, the best among medium-sized models and comparable to GPT-4o.

**What the experiments demonstrate.** Table 1 provides a clear comparison: 41.0% vs. 32.8% for the next-best open medium-sized model (SWE-Fixer-72B) and vs. 38.8% for GPT-4o on the same scaffold (Agentless). The scaling analysis (Figure 4) shows how performance varies with compute budget, and the 41.0% is achieved with 500 repair samples and 30 reproduction tests.

**Caveats.** The comparison across models is not perfectly controlled—different models use different scaffolds (RAG, SWE-SynInfer, OpenHands, SWE-Fixer, Agentless, Agentless Mini), and scaffold quality affects performance independently of model quality. GPT-4o's 38.8% with Agentless vs. its 50.8% with the same scaffold but using Claude-3.5-Sonnet (Table 1) illustrates that scaffold matters enormously. Llama3-SWE-RL-70B uses Agentless Mini, which was developed by the same authors and incorporates specific design choices (full file context in repair, multiple reproduction tests for reranking) that may advantage the model. The fairer comparison might be Llama3-SWE-RL-70B vs. GPT-4o both using Agentless Mini, but that comparison is not provided.

**Bottom line.** The 41.0% is a genuine achievement and the best reported for sub-100B models, but the headroom between this result and what proprietary models achieve with the same or similar scaffolds (Claude-3.5-Sonnet at 50.8% with Agentless) is still ~10 points—the RL model is state-of-the-art for medium-sized open models but not yet competitive with the strongest proprietary systems.

#### Claim 3: RL on issue-solving data produces generalised reasoning skills that transfer to out-of-domain tasks, while SFT degrades them.

**What the experiments demonstrate.** Table 3 shows the RL model outperforming both base and SFT on all five out-of-domain benchmarks. The improvements on reasoning-intensive tasks (CRUXEval, MATH) are substantial (10+ points over base on CRUXEval, 10+ on MATH strict). The SFT model's degradation on 4 of 7 strict benchmarks is consistent with the "task specialisation" hypothesis.

**Caveats and limitations.**

- **The SFT baseline, while carefully constructed, may not be the strongest possible SFT baseline.** The paper mixes in general-domain data to prevent catastrophic forgetting—but the mixture ratio, data sources, and training duration are not ablated. A different SFT recipe (more general data, less synthetic editing data, different generation approach) might not show the same degradation pattern. The claim "SFT degrades generalisation" is demonstrated for *this specific SFT recipe* but may not generalise to all possible SFT approaches.

- **The RL model's OOD gains could be partially attributable to the KL penalty preserving base model capabilities rather than RL actively improving them.** The base model scores 76.2 on HumanEval+; the RL model scores 79.9. This is a meaningful improvement, but it might reflect that the base model's capability was present but latent, and the RL process uncovered it through format training (learning to produce structured outputs) rather than creating genuinely new reasoning ability. The MATH strict vs. lenient gap supports this interpretation: the base model scores 70.9 lenient but only 63.2 strict, suggesting it often knows the correct answer but fails to format it properly. The RL model scores 73.7 both ways, having learned to produce structured outputs. Some fraction of the OOD "gains" may be format improvements rather than reasoning improvements.

- **Single evaluation per benchmark with zero-shot greedy decoding.** The paper does not report multiple runs or confidence intervals for the OOD benchmarks. While Eval Arena significance thresholds are cited, these are general guidelines, not significance tests computed on the actual data distributions. The 0.33-point gain on MMLU (86.49 → 86.82) is small enough that model variability alone could produce it.

- **The benchmarks chosen may not represent "generalisation" in the most rigorous sense.** HumanEval+ and BigCodeBench are both code generation benchmarks—they are "out-of-domain" relative to issue-solving but still within the broad umbrella of coding. MATH is genuinely different in content but shares structural properties with coding (formal reasoning with a deterministic correct answer). MMLU is the only benchmark testing knowledge and reasoning across diverse topics. The RL model's gain on MMLU is the smallest (0.33 points), which might better represent the true extent of generalisation than the larger gains on coding-adjacent benchmarks.

**Experiments that would strengthen the claim.**
- A broader set of OOD benchmarks including natural language reasoning (e.g., GSM8K, BBH), factual knowledge (e.g., TriviaQA), and safety evaluations would test whether the generalisation is broad or confined to structured reasoning tasks.
- Multiple random seeds of RL training would assess whether the OOD improvements are consistent or driven by training noise.
- An ablation where the base model is simply prompt-tuned on the same SEARCH/REPLACE format without RL would test how much of the gain comes from format training alone.

**Bottom line.** The evidence for RL-driven generalisation is suggestive and internally consistent across five benchmarks, but it is not airtight. The strongest evidence is the SFT baseline's *degradation* on OOD tasks—this is a negative result that would likely replicate because SFT is known to cause distributional shift. The RL model's improvements are positive and consistent in direction, but the magnitude on some benchmarks is small, and the mechanism (preservation via KL penalty vs. active improvement via emergent reasoning) is not disentangled.

#### Claim 4: "Aha moments"—emergent reasoning behaviours—occur during RL for software engineering.

**What the experiments demonstrate.** Figure 3 provides qualitative examples of self-reflection, exploring alternatives, and divide-and-conquer reasoning in the model's outputs for both in-domain (issue-solving) and out-of-domain (function implementation, math) tasks. The quantitative OOD improvements (Table 3) provide indirect evidence that these behaviours translate to better performance.

**What is not demonstrated.** The paper does not quantify how frequently "aha moments" occur, whether they causally lead to correct solutions (as opposed to being epiphenomenal reasoning language that doesn't affect the final output), or whether they increase in frequency over the course of training. The examples in Figure 3 are cherry-picked illustrations, not a systematic analysis. Without quantitative metrics (e.g., frequency of self-correction language, correlation between reflection and correctness, trajectory analysis showing revisions mid-response), the claim of "aha moments" is more narrative framing than empirical finding.

**Bottom line.** The emergent reasoning narrative is compelling and consistent with DeepSeek-R1's observations, but the paper treats it as a qualitative observation rather than a quantitatively supported claim. This is reasonable for the scope of this paper (the examples are in Figure 3, not in a results table), but the reader should understand that the existence and importance of "aha moments" in software engineering RL is suggested rather than proven.

#### General Methodological Strengths and Weaknesses

**Strengths.**
- The controlled SFT vs. RL comparison on the same base model with the same seed data source provides a clean test of training paradigm effects.
- The evaluation spans in-domain (SWE-bench), controlled repair-only (oracle localisation), and out-of-domain (five benchmarks), giving a multi-faceted view of model capability.
- The scaling analysis (Figure 4) shows how performance varies with compute budget, which is important for practical deployment decisions.
- The reward ablation (Figure 5) directly tests the central design choice and confirms its necessity.

**Weaknesses.**
- **Single model family, single scale.** All experiments use Llama-3.3-70B-Instruct. The paper does not test whether SWE-RL works on smaller models (8B, 13B) or different families (Qwen, DeepSeek-Coder), which would test the generality of the approach.
- **Single scaffold for evaluation.** Agentless Mini is developed by the same authors and incorporates design choices informed by the RL training setup. Performance might not transfer to other scaffolds (SWE-agent, OpenHands), which would limit the model's practical utility.
- **No direct comparison between SWE-RL and existing training approaches on identical footing.** The paper compares to published numbers from Lingma-SWE-GPT, SWE-Gym, and SWE-Fixer, but these use different base models (Qwen2.5 variants) and different scaffolds. A comparison where all models are evaluated with the same scaffold would be more informative but is not provided.
- **Training data is not released**, and the data curation pipeline (Appendix A) involves multiple proprietary components (heuristics, filtering rules, LLM-based relevant file prediction). This limits reproducibility and makes it difficult to assess whether the 273k seed instances are representative of typical GitHub PRs or a highly curated subset that happens to work well for SWE-bench-style issues.
- **No analysis of failure modes.** The paper does not report what kinds of issues the model fails on, whether errors are due to incorrect localisation, incorrect repair logic, or test generation failures, or whether specific repository characteristics predict success/failure. This limits the reader's ability to understand the model's capabilities and limitations.
- **The computational cost of inference is high.** The main evaluation uses 500 repair samples and 30 reproduction tests per issue, plus regression test execution and reranking. For the 500-issue SWE-bench Verified set, this is a substantial compute investment (250k repair inferences + 15k test inferences + test execution across all candidates). The paper does not report the total inference cost or wall-clock time for a full evaluation run.

## 6. Limitations and Trade-offs

### The Reward Function Cannot Distinguish Between Textually Different but Semantically Equivalent Patches

**The assumption or constraint.** SWE-RL's reward is defined as the `difflib.SequenceMatcher` similarity score between the model's generated patch and the ground-truth oracle patch written by the human developer who resolved the issue (Section 2.1, Equation 1). This is a purely textual similarity metric—it measures whether the model produces the same sequence of characters as the human developer, not whether the model's patch *semantically* fixes the bug. The authors explicitly acknowledge this in the Limitations section (Section 5):

> "our reward implementation compares the sequence similarity between the predicted and oracle patch rather than their semantic equivalence. This may prevent the policy LLM from exploring alternative, functionally equivalent solutions."

**The consequence.** Because the reward is anchored to a single reference patch, the RL process actively penalises any solution that deviates textually from what the human developer wrote—even if that solution is semantically correct and arguably better (cleaner, more efficient, more maintainable). Consider a developer who fixes a null-pointer bug by adding a null check at the function entry point. An alternative fix might restructure the calling code to never pass null in the first place—semantically equivalent in outcome, but with zero textual overlap with the reference patch. The model receives a reward near zero for this alternative, despite it being a valid fix.

This has several cascading effects:

- **The model is incentivised to exactly memorise and reproduce common patch patterns rather than learn generalisable debugging skills.** If a specific kind of bug (e.g., off-by-one error in a loop) is typically fixed in a particular way in the training data, the model learns to reproduce that exact text pattern rather than understand the underlying logic. This may explain why the model's repair-only accuracy (34.8%, Table 2) is substantially below what one might expect given the training scale—the model is being penalised for exploring the space of valid solutions.

- **The model may fail on bugs whose fixes are structurally different from anything in the training distribution.** If the training data contains no examples of a particular patch pattern (e.g., adding a new helper function to fix a concurrency issue), the model has no reward signal guiding it toward that solution, even if it could reason about the correct approach.

- **The reward does not scale to open-ended software engineering tasks** where there is no single correct patch—e.g., refactoring, performance optimisation, or feature addition, where multiple valid solutions exist with no oracle to match against.

**What evidence exists in the paper.** The discrete reward ablation (Figure 5) provides indirect evidence: the exact-match reward variant achieves only 29.0% repair accuracy vs. 34.8% for the continuous reward. The fact that exact text matching is *that* difficult (the discrete reward curve flatlines near zero throughout training) confirms that the model rarely produces patches textually identical to the human-written oracle. The continuous reward helps by giving partial credit, but both variants fundamentally share the same limitation—they compare against a single reference answer. The paper does not report how often the model produces a *semantically correct but textually different* patch that gets scored below 0.5, which would quantify the severity of this limitation.

**Mitigation status.** The authors acknowledge the limitation explicitly (Section 5) but propose no mitigation. The continuous `SequenceMatcher` reward is a pragmatic workaround for reward sparsity, not a solution to the semantic equivalence problem. Potential mitigations—execution-based verification (running the original and patched code against the issue's reproduction test), using multiple reference patches per issue, or training a learned verifier that assesses semantic equivalence—are noted as future directions only by implication. The core architecture of SWE-RL (match against a single oracle patch) would need to change to address this limitation.

### Difficulty Estimation and Strategy Selection Costs Are Not Accounted For, Making the Headline 4× Efficiency Gain Misleading

**The assumption or constraint.** The paper's central claim—that SWE-RL achieves 41.0% on SWE-bench Verified—was obtained using 500 repair samples and 30 reproduction tests per issue (Section 3.1, Section 3.4). This is an **extraordinarily expensive inference budget**: for each of the 500 evaluation issues, the model generates 500 independent repair candidates (each requiring a forward pass through a 70B model to produce reasoning tokens and code edits), plus 30 reproduction tests per issue (each also requiring model inference), plus regression test selection. No difficulty estimation is performed upfront to allocate this budget adaptively. The scaling analysis (Figure 4) shows that performance improves substantially with more samples—from 33.6% at 20 samples to 41.0% at 500 samples—meaning the 41.0% headline number depends on this large inference budget.

**The consequence.** The 41.0% solve rate is not a "cheap" result. A practitioner deploying Llama3-SWE-RL-70B to fix real GitHub issues would need to run up to 500 repair inferences per issue, each of which may involve generating hundreds to thousands of tokens of reasoning text before producing the edit blocks. For a 70B-parameter model, this is computationally expensive—easily costing dollars per issue in cloud compute, and potentially minutes of wall-clock time. The paper does not report the total inference FLOPs or dollar cost for a full SWE-bench Verified evaluation run.

Compare this to the baselines: GPT-4o with Agentless achieves 38.8% (Table 1) but likely uses far fewer samples (Agentless's default configuration is not specified in the paper, but typical agentic scaffolds generate perhaps 3-10 repair candidates per issue). The RL model's 41.0% may represent a *Pareto improvement* in the accuracy dimension but could easily be *worse* in the cost-per-issue dimension. The paper frames the RL model as "comparable to leading proprietary LLMs like GPT-4o" (Section 1), but this comparison is valid only in the accuracy dimension, not in cost or latency.

The scaling curves (Figure 4) also reveal an uncomfortable truth: at more modest sample budgets, the model's performance is substantially lower. At 20 repair samples and 1 test sample, Llama3-SWE-RL-70B would score approximately 33.6% (extrapolating from the leftmost points on both curves). A practitioner operating under a tight latency or cost budget might prefer a simpler approach (e.g., SFT with fewer samples) that gets to 30% more cheaply.

**What evidence exists in the paper.** Figure 4 explicitly shows the performance-vs-samples curves, which the paper honestly presents. The gap between 33.6% (20 samples) and 41.0% (500 samples) is reported without comment on the cost implication. Table 2 provides an anchor: the base model with greedy decoding achieves 5.4% repair accuracy and the SFT model achieves 29.6%, both with a single sample—demonstrating that the RL process improves sample efficiency *somewhat* (the RL model achieves 29.6%+ at presumably fewer samples), but the paper never reports the sample budget at which RL matches SFT's single-sample performance.

**Mitigation status.** None. The paper does not report the total compute cost of evaluation, does not compare cost-adjusted performance against baselines, and does not explore adaptive sampling strategies that would allocate the 500-sample budget only to issues where it helps. The scaling analysis (Figure 4) is presented as a strength but actually reveals an efficiency weakness: the model needs hundreds of samples to reach its peak performance. Future work on difficulty estimation, early stopping, or cascade approaches (try 10 samples first, escalate to 500 only if needed) would directly address this limitation.

### RL Training Uses a Single 70B Model from a Single Model Family; Generality Across Model Scales and Architectures Is Untested

**The assumption or constraint.** All experiments in the paper use exactly one base model: Llama-3.3-70B-Instruct (Dubey et al., 2024). The data curation pipeline, the RL training configuration (1,600 steps, 512 batch size, 16-rollout groups, 16k context window, 512 H100 GPUs for 32 hours), the prompt template, and the reward function are all designed, tuned, and validated on this specific model. The paper does not report results for smaller Llama variants (8B, 13B), for models from other families (Qwen2.5, DeepSeek-Coder, CodeLlama), or for base models (non-instruct-tuned variants). The authors state (Section 3.2) that they "believe this model is representative of the capabilities of many contemporary LLMs," but this belief is not tested.

**The consequence.** Several aspects of SWE-RL's success could be specific to Llama-3.3-70B-Instruct:

- **Format following ability.** The base model has only 12.2% format accuracy for SEARCH/REPLACE edits (Table 2)—essentially no capability. The RL process teaches this capability from scratch. A different base model with stronger inherent instruction-following might start at 40% format accuracy and need less RL, or a model with weaker instruction-following might never learn the format reliably. The optimal reward function, prompt template, and training duration could vary substantially across base models.

- **Instruction tuning matters.** The paper uses the *Instruct* variant of Llama 3.3, which has been fine-tuned for dialogue and instruction following. This likely provides a starting point where the model at least understands the system/user/assistant conversation format and can engage in structured reasoning. A base (non-instruct) model might fail entirely on the same task because it cannot interpret the prompt template or engage in the thinking/response split.

- **The 70B scale may be special.** The paper's sub-100B models comparison (Table 1) includes models from 7B to 72B. SWE-RL is only tested at 70B. It is unknown whether the approach works at 8B or 32B—the reward signal might be too sparse at smaller scales, or the base capability threshold for learning from patch-similarity rewards might not be met. The DeepSeek-R1 experience showed that emergent reasoning behaviours ("aha moments") appear most prominently at larger scales (671B). Whether they would appear during SWE-RL at 8B parameters is an open question.

- **The KL penalty calibration is model-specific.** The GRPO objective includes a KL penalty term β D_KL(π_θ || π_ref) that constrains the policy from drifting too far from the reference model. The choice of β (not reported in the paper) presumably depends on the base model's output distribution characteristics. A different base model would require re-tuning β, and suboptimal KL penalty strength could lead to either catastrophic forgetting (if β is too small) or no learning (if β is too large).

**What evidence exists in the paper.** The paper provides no ablation or test across model scales, families, or instruction-tuning status. The out-of-domain evaluation (Table 3) shows that the RL model improves over the base model on several benchmarks, which provides some evidence that the learned capabilities are not absurdly specific to the SWE-bench distribution, but it does not address whether the training *method* transfers to other models. The SFT baseline is trained on the same base model, providing a controlled comparison within the Llama-3.3-70B-Instruct family, but not across families.

**Mitigation status.** None. The paper's title and abstract position SWE-RL as a general approach ("the first RL method to improve LLMs on SE tasks by directly using rule-based rewards and software evolution data"), but the evidence is limited to a single model at a single scale. The authors do not explicitly flag this as a limitation in Section 5 (Limitations), which focuses instead on the reward function, localisation simplification, and Agentless Mini's pipeline structure. Testing on additional models and scales is left entirely to future work.

### The Training Data Curation Pipeline Involves Multiple Proprietary and Unreleased Components, Limiting Reproducibility

**The assumption or constraint.** The seed RL dataset of 273k high-quality PR instances is constructed through a multi-stage curation pipeline described in Appendix A and Section 2. This pipeline involves:

- Cloning and processing 4.6 million GitHub repositories with full commit history (Section A).
- Aggregating PR events (issues, discussions, review comments, code changes) into 24 million PR instances using custom heuristics.
- Using **Llama-3.1-70B-Instruct to predict relevant but unmodified files** for inclusion in the training context (Section A, "Relevant files prediction").
- Applying "various filtering strategies" and "fine-grained filters used in CodeLlama" to eliminate bot-generated PRs, lock file changes, version bumps, and extremely large changes (Section A).
- Selecting the 273k highest-quality instances from the filtered ~11 million using additional heuristics: the PR must include at least one linked issue, the issue must describe a bug fix, and the code changes must involve programming files (Section 2).

The training data, the data curation code, and the training pipeline are not released. The NeurIPS checklist response states: "At this time, we cannot share the training data or training pipeline due to privacy and proprietary considerations. However, once the necessary reviews are completed and associated risks are addressed, we will make these resources available."

**The consequence.** A researcher attempting to reproduce SWE-RL faces substantial barriers:

- **The GHArchive dataset of all GitHub events from 2015-2024 is public**, but the clone-and-process pipeline for 4.6 million repositories is enormously expensive (storage, bandwidth, compute) and involves custom infrastructure not described in the paper. The paper does not specify how long the curation pipeline takes or what computational resources it requires.

- **The heuristics for PR aggregation, issue matching, and filtering are underspecified.** The paper mentions "scanning each aggregated PR to identify patterns that resemble issues" (Section A) and "various filtering strategies" but does not provide the exact pattern-matching rules, keyword lists, or threshold values. Small differences in these heuristics could produce meaningfully different training datasets with different difficulty distributions, patch formats, and issue types.

- **The Llama-3.1-70B-Instruct relevant-file prediction step** introduces a proprietary LLM inference dependency. If a researcher cannot access this specific model (or its weights become unavailable), they cannot reproduce this step. Even with access, the prompt used for relevant-file prediction is not provided, and the model's temperature, sampling parameters, and output format are not specified.

- **The 273k seed selection heuristics are coarse.** The criteria ("at least one linked issue, the issue should describe a bug-fixing request, and the code changes should involve programming files") likely still admit substantial noise—issues that describe feature requests labelled as bugs, PRs that touch programming files but primarily modify configuration, etc. Without access to the actual dataset, a researcher cannot assess the quality or representativeness of the training instances.

- **The decontamination process excludes SWE-bench repositories** but the paper does not specify how repository identity is matched or whether near-duplicate repositories (forks, mirrors) are also excluded. Incomplete decontamination could inflate SWE-bench scores.

**What evidence exists in the paper.** Figure 6 provides a high-level diagram of the curation pipeline, and Appendix A contains approximately one page of prose describing each stage. The pipeline is described in general terms; specific parameters, prompt templates, filtering rules, and quality metrics are absent. The paper reports producing 24 million aggregated PRs and filtering to 11 million and then to 273k, but does not report what fraction of the 24 million PRs pass each filter stage, what a typical training instance looks like, or how the difficulty distribution of the training set compares to SWE-bench Verified. The baseline comparison (Table 2) shows that the RL model achieves substantially better format accuracy (95.6%) and repair accuracy (34.8%) than the base model, confirming that the data+RL combination works, but it cannot distinguish whether the success is due to the RL algorithm, the data quality, or their interaction.

**Mitigation status.** The paper states intent to release data and code after review (NeurIPS checklist, Question 5). At time of writing, these are not available. Even if released, the data curation pipeline's dependence on GHArchive (an external service with its own availability constraints) and git cloning at massive scale means that full end-to-end reproduction would remain challenging for most academic labs. The paper does not discuss this as a limitation in Section 5—the Limitations section focuses on technical shortcomings (reward semantic equivalence, localisation simplification, pipeline structure) rather than reproducibility concerns.

### The Model Is Evaluated on a Single Benchmark with a Custom Scaffold; Practical Generalisation to Real-World Repositories and Alternative Scaffolds Is Unmeasured

**The assumption or constraint.** All evaluation is on SWE-bench Verified, a carefully curated set of 500 GitHub issues from 12 Python repositories. Agentless Mini was developed by the same authors specifically to work with Llama3-SWE-RL-70B, incorporating design choices (full file content in the repair step, file-level-only localisation, multiple reproduction tests for reranking) that align with how the model was trained. The paper does not evaluate the model on:

- Any repository outside SWE-bench's 12 repos, which span a limited set of domains (Django, Flask, matplotlib, requests, scikit-learn, seaborn, etc.).
- Any non-Python language or framework.
- Any alternative scaffold (SWE-agent, OpenHands, CodeR, Moatless Tools) to test whether the model's capabilities transfer.
- Any task other than issue resolution, despite the paper's claim of generalised reasoning capabilities (Table 3's OOD evaluation tests only *standalone benchmarks*, not *real-world SE tasks* like code review, refactoring, documentation generation, or test suite augmentation).

**The consequence.** The 41.0% solve rate may not reflect real-world deployability for several reasons:

- **Distribution shift from SWE-bench to arbitrary GitHub issues.** SWE-bench Verified issues were specifically selected because they have clear issue descriptions, well-defined scope, and testable solutions. The authors of SWE-bench manually filtered the original SWE-bench to remove ambiguous, under-specified, or otherwise problematic instances. Real-world GitHub issues are much noisier—they may contain incomplete information, multiple interleaved bugs, discussions spanning dozens of comments, or domain-specific jargon that doesn't appear in the 12 SWE-bench repositories. The model's performance on a random sample of GitHub issues could be substantially lower.

- **Agentless Mini is co-designed with the model.** The scaffold's simplifications—file-level localisation with full file content in repair (rather than Agentless's multi-step element-level localisation), multiple reproduction tests for reranking—directly match the RL training setup. The model was trained to reason about fault locations given full files and to generate SEARCH/REPLACE edits. If deployed with a different scaffold that does multi-turn interactive debugging (SWE-agent style) or that uses embedding-based retrieval for file localisation, the model might underperform because it has not been trained to interact with tools, interpret environment observations, or reason about partial code snippets.

- **The OOD benchmarks in Table 3 are not real-world SE tasks.** HumanEval+ tests function-level completion from a docstring; BigCodeBench tests library use from a structured instruction; CRUXEval tests execution prediction; MATH tests mathematical proof generation; MMLU tests multiple-choice knowledge. None of these captures the experience of a developer using the model to fix a bug in their actual codebase with their actual build system, dependencies, and coding conventions. The paper's claim that SWE-RL "enhances an LLM's general reasoning abilities" (Section 3.5) is supported for *standardised benchmark reasoning* but not for *deployed software engineering reasoning*.

- **The 12 SWE-bench repositories may have characteristics that differ from the RL training data.** The paper decontaminates against SWE-bench repositories, but the relationship between training and evaluation domains matters beyond simple overlap. If the training data contains many Django-related PRs (a popular open-source project) and SWE-bench's Django issues are structurally similar, the model may perform well on Django but poorly on less-represented repositories. The paper does not report per-repository breakdowns of SWE-bench performance.

**What evidence exists in the paper.** The paper provides no evaluation outside SWE-bench Verified, no comparison across scaffolds, and no per-repository breakdown. The OOD results in Table 3 are presented as evidence of generalisation, but they measure performance on *different benchmark types*, not on *real-world SE tasks* with the same scaffold. The paper does not test whether the model generalises to, for example, SWE-bench Multimodal (Yang et al., 2024c) or SWE-bench Lite, or to non-Python issues.

**Mitigation status.** The authors do not discuss this as a limitation in Section 5. The Limitations section mentions that Agentless Mini's localisation "is simplified to mapping repository structures to file paths, which lacks comprehensive context" and that "as a pipeline-based approach, Agentless Mini divides all steps into distinct inference stages." These are criticisms of the *scaffold design*, not of the limited evaluation scope. The paper's conclusion states that "SWE-RL opens a new direction for enhancing the software engineering capabilities of LLMs through RL," which implicitly acknowledges that the current evaluation is a proof of concept, but this is not framed as a limitation that limits the strength of the 41.0% claim.

### Hard Problems (Where the Base Model Has Near-Zero Pass@1) Receive No Benefit from RL, Establishing a Capability Ceiling

**The assumption or constraint.** The RL training process starts from Llama-3.3-70B-Instruct and optimises the policy to maximise patch-similarity reward on the training distribution. The model only learns to produce patches that are textually similar to human-written patches. If the base model cannot produce a *partially* correct patch on a given problem—i.e., its initial pass@1 for any plausible fix is essentially zero—then the RL process has no meaningful reward signal to shape improvement. The reward function (`SequenceMatcher`) requires some textual overlap between the generated and oracle patches to provide a non-zero reward; if the model's outputs are entirely unrelated to the oracle, all rollouts receive rewards near zero, and the advantage estimates become noise.

**The consequence.** There exists a class of issues—presumably the hardest ones, requiring novel reasoning, unfamiliar APIs, or creative architectural changes—for which SWE-RL provides no benefit whatsoever. The base model's pass@1 on these issues is near zero, and RL cannot create capability ex nihilo. This is analogous to the phenomenon observed in the reference paper summary (Section 3.4, Figure 3): on the hardest difficulty quintile (bin 5), no amount of test-time compute helps because the base model simply lacks the capability to produce correct solutions. Similarly, SWE-RL's improvements are concentrated on issues where the base model can produce *approximately* correct patches that the reward function can incrementally refine.

This limitation has several implications:

- **The 41.0% solve rate may represent saturation for this model scale.** Further scaling of RL training steps, reward design, or inference budget may not substantially improve performance on the hardest 59% of SWE-bench Verified issues. Closing the gap to Claude-3.5-Sonnet's 50.8% (Table 1) may require fundamentally different capabilities—better base model reasoning, execution-based verification, or interactive debugging—that SWE-RL does not provide.

- **The model may exhibit a bimodal performance distribution**: near-perfect on issues resembling the training distribution and near-zero on issues requiring novel reasoning strategies. The paper's failure to report per-repository or per-difficulty breakdowns of SWE-bench performance prevents the reader from assessing whether this is the case.

- **The RL process cannot teach the model to handle fundamentally new types of bugs.** If a repository contains a concurrency bug causing a race condition, and the training data contains no examples of concurrency fixes, the model has no reward signal guiding it toward the correct solution. It may learn to produce superficially plausible patches (adding `sleep()` calls, wrapping code in `try/except`) that score non-zero similarity but don't fix the issue—reward hacking analogous to the PRM over-optimisation observed in the reference paper.

**What evidence exists in the paper.** The paper does not directly measure this limitation—it does not report performance broken down by issue difficulty, does not analyse failure modes, and does not compare the RL model's performance distribution to the base model's. The discrete reward ablation (Figure 5) provides indirect evidence: the discrete reward stays near zero throughout training, confirming that the model almost never produces patches that exactly match the oracle. If exact matches are this rare, it suggests that even on issues where the model *does* receive non-zero continuous rewards, the oracle patch is not within easy reach of the base model's initial distribution—RL is navigating the model through a space of *approximately* correct patches, not teaching it to discover entirely novel solutions.

The tuning curves (the off-policy validation trajectory) are not shown, so the reader cannot assess whether the model's per-issue reward distribution is heavy-tailed (most issues receive near-zero reward, a few receive high reward) or whether it is roughly uniform.

**Mitigation status.** The paper does not acknowledge this limitation explicitly. The Limitations section (Section 5) focuses on the reward function's inability to recognise semantic equivalence and on Agentless Mini's pipeline simplifications. There is no discussion of a capability ceiling, no analysis of which issues the model fails on, and no proposal for how to address issues that are fundamentally outside the base model's reach. The conclusion (Section 5) states that "SWE-RL opens a new direction for enhancing the software engineering capabilities of LLMs through RL," which implies that further progress is possible, but the paper provides no evidence about whether that progress is likely to come from better RL, better base models, or fundamentally different training paradigms. This is a significant gap for a practitioner considering whether to invest in SWE-RL versus alternative approaches.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

This paper establishes a new research paradigm for training LLMs on software engineering tasks: **reinforcement learning on software evolution data with a text-similarity reward can replace supervised fine-tuning on teacher-distilled data, producing models that are both better at the target task and better at generalising to unrelated domains**. This is not an incremental improvement on existing SFT-based SWE-bench methods—it is a demonstration that the entire training approach can be rerouted through RL, bypassing the dependency on proprietary teacher models that has defined the entire subfield to date.

The conceptual shift is best understood along three dimensions. **First, the reward hypothesis for coding RL is generalised from execution-based to reference-based.** Prior work (DeepSeek-R1, RLEF, AceCoder) treated execution feedback—pass the tests or fail them—as the necessary and sufficient signal for RL on coding. SWE-RL demonstrates that a continuous textual similarity metric against a reference patch can serve the same function, even in settings where execution is infeasible. This decouples the applicability of RL from the availability of executable environments, which is the binding constraint that has confined coding RL to competitive programming benchmarks. The reward ablation (Figure 5) is the critical piece of evidence: the discrete exact-match reward flatlines near zero throughout training, confirming that the reference patch is a useful signal only when its similarity is graded continuously. The practical implication is that **any domain with a large corpus of reference solutions paired with problem descriptions—code review history, refactoring commits, security patch databases—is now potentially amenable to RL-driven capability improvement**, not only those with executable test suites.

**Second, the paper provides the first controlled evidence that RL and SFT on the same seed data produce qualitatively different models, not merely quantitatively different task performance.** The SFT baseline (Llama3-SWE-SFT-70B) achieves a respectable 36.2% on SWE-bench Verified (Table 1) but regresses on four of five out-of-domain benchmarks compared to its base model (Table 3). The RL model, trained on the same seed PR data, improves on all five OOD benchmarks while simultaneously outperforming the SFT baseline on SWE-bench. This is not a nuance—it is a direct empirical refutation of the assumption, implicit in the SFT-distillation paradigm, that task-specific training data plus a general-domain data mix is sufficient to maintain (let alone improve) broad capabilities. The mechanism the paper proposes—that the KL penalty in GRPO preserves base model knowledge while RL incentivises the discovery of general reasoning strategies—suggests that **the choice of training objective matters as much as the choice of training data for determining whether a model specialises or generalises**. This finding, if it replicates across model families and domains, would shift the field's default training recipe from "SFT with data mixing" toward "RL with a reference policy constraint" for tasks where broad capability preservation is important.

**Third, the paper introduces the concept of emergent reasoning behaviours ("aha moments") in real-world software engineering RL**, explicitly connecting to DeepSeek-R1's narrative while establishing a domain-specific claim. The qualitative examples in Figure 3—self-reflection during bug diagnosis, exploring alternative fix strategies, decomposing complex issues into sub-problems—are presented as behaviours the model was never explicitly trained to perform but that emerge from the RL optimisation process. Unlike math or competition coding, where the reasoning path is self-contained and deductive, real-world issue resolution requires navigating an existing codebase, interpreting ambiguous natural-language descriptions, and producing minimal edits within a larger system. The claim that RL incentivises general cognitive strategies (re-evaluating assumptions, exploring alternatives, divide-and-conquer reasoning) rather than domain-specific pattern-matching is the paper's most provocative idea, because it implies that the training domain acts as a "reasoning gymnasium" where the model practices transferable cognitive skills. The OOD results in Table 3 are the quantitative evidence for this claim; the "aha moment" examples in Figure 3 are the qualitative illustration. Together, they support a narrative where **RL's value is not in teaching the model what patches look like, but in teaching it how to think about problems**.

**Reconciling prior contradictions.** The paper implicitly resolves a tension in the literature between the success of proprietary LLMs on SWE-bench (Claude-3.5-Sonnet at 50.8%, GPT-4o at 38.8%) and the stagnation of open models below 33% (Table 1). The prior approach—distill from proprietary teachers—appeared to work for task-specific performance but left open models with a dependency ceiling (they could only approach teacher quality) and with degraded general capabilities (as the SFT baseline's OOD results show). SWE-RL demonstrates an alternative path: open models can self-improve on SE tasks using only publicly available data, reaching 41.0% on SWE-bench Verified without any proprietary teacher involvement, while simultaneously improving on broad reasoning benchmarks. This reconciles the contradictory finding that "open models underperform on SWE-bench despite strong base coding capabilities" by identifying the training paradigm (SFT distillation) rather than the base model quality as the limiting factor.

**Research directions that become more attractive.** The paper redirects attention away from:

- Better SFT data generation pipelines (the Magicoder-style approach used for the SFT baseline) and toward better reward functions and RL algorithms for SE.
- Scaling the teacher model (GPT-4o → Claude-3.5 → o1) for distillation and toward scaling the RL budget (more training steps, larger group sizes, longer reasoning horizons) on open-source data.
- Multi-stage SFT pipelines that separately train localisation, repair, and test generation and toward end-to-end RL approaches that let these skills emerge from a unified reward signal.

Conversely, it redirects attention toward:

- **Verifier robustness** in non-execution settings: the `SequenceMatcher` reward is a pragmatic workaround, but its limitation (textual similarity rather than semantic equivalence) is the primary bottleneck for further scaling. Research on learned verifiers, execution-based validation, or multi-reference rewards becomes critical.
- **Understanding the RL vs. SFT generalisation gap:** the paper demonstrates the phenomenon but does not mechanistically explain it. Does it arise from the KL penalty, from the exploration dynamics of policy gradients, from the continuous reward signal, or from some interaction of these factors? Answering this question would determine whether the finding generalises beyond this specific configuration.
- **Scaling laws for reasoning emergence:** the paper demonstrates emergent reasoning at 70B parameters with 1,600 RL steps. Does this behaviour appear at smaller scales (8B, 13B)? Is there a phase transition in reasoning capability as a function of RL compute or base model size? These scaling questions are directly analogous to those that DeepSeek-R1 opened for math and coding but are completely unexplored for software engineering.

### Follow-Up Research This Work Enables

**Mechanistic analysis of the RL vs. SFT generalisation gap.** The paper's central empirical finding is that RL on issue-solving data improves out-of-domain performance while SFT on similar data degrades it (Table 3). But the causal mechanism is unclear. Is the RL model's OOD improvement caused by: (a) the KL penalty to the reference policy preserving base model knowledge that SFT overwrites, (b) the exploratory dynamics of policy gradient optimisation discovering general reasoning strategies that SFT's maximum-likelihood objective does not incentivise, (c) the continuous reward signal encouraging incremental improvement rather than exact imitation, or (d) the "thinking" section of the prompt template forcing the model to generate intermediate reasoning that transfers across domains? A strong follow-up would systematically ablate these factors: train an SFT model with a KL regularisation term matched to the GRPO beta; train an RL model with a binary reward to test whether reward continuity matters; train an RL model without the thinking section in the prompt to test whether forced reasoning is necessary; and train an RL model whose reference policy is periodically updated to the SFT checkpoint to test whether the base model's knowledge distribution or the SFT checkpoint's task specialisation drives the generalisation effect. The key measurements would be OOD benchmark scores, KL divergence from the base model over training, and qualitative analysis of reasoning content across conditions.

**Execution-based verification as a reward signal for SWE-RL.** The paper's primary technical limitation—that the `SequenceMatcher` reward cannot distinguish semantically equivalent but textually different patches (Section 5)—has a natural resolution if execution environments can be provided at training time. A direct follow-up would replicate SWE-RL but replace (or augment) the text-similarity reward with an execution-based signal: run the reproduction tests (which are included as part of the SWE-bench infrastructure for each issue) on the model's generated patch, and reward based on whether the patched code passes the issue-reproduction-and-resolution tests. This would test whether the 34.8% repair-only accuracy ceiling (Table 2) is due to the reward function restricting exploration of alternative patches, or due to a fundamental capability limitation of the 70B model. If execution-based RL pushes repair accuracy significantly above 34.8%—say, to 45% or 50%—it would establish that the text-similarity reward is the bottleneck and that execution-based RL should be the target for future work (with the caveat that execution environments are expensive). If execution-based RL shows no improvement, it would suggest that the model's reasoning capability, not the reward signal, is the limiting factor, redirecting attention to base model scaling or architecture improvements.

**SWE-RL at smaller model scales (8B, 13B, 32B).** The paper demonstrates SWE-RL exclusively at 70B parameters on Llama-3.3-70B-Instruct. Whether the approach transfers to smaller models has enormous practical implications: if SWE-RL produces a competent 8B SWE-bench model, it enables on-device or low-latency deployment for software engineering tools. A strong follow-up would apply the identical SWE-RL recipe (same data, same prompt template, same reward function, same GRPO hyperparameters) to Llama-3.1-8B-Instruct, Llama-3.1-70B (for scale comparison), and Qwen2.5-Coder-7B-Instruct (cross-family test). The key measurements would be SWE-bench Verified performance with a consistent scaffold across all models, repair-only accuracy under oracle localisation (to isolate model capability from localisation skill), and out-of-domain benchmark performance (to test whether the RL-vs-SFT generalisation pattern holds at smaller scales). The critical question is whether the emergent reasoning behaviours documented at 70B appear at 8B, or whether there is a minimum scale threshold below which RL provides only format training without reasoning improvement.

**Adaptive inference budgets for SWE-RL models.** The scaling analysis (Figure 4) reveals that Llama3-SWE-RL-70B's SWE-bench performance improves substantially with more repair samples—from 33.6% at 20 samples to 41.0% at 500 samples—but the cost per sample is high (70B-parameter forward passes with reasoning tokens). A natural follow-up is to train a lightweight difficulty predictor that, given an issue description and repository structure, estimates how many repair samples are needed to achieve a target confidence level. This predictor could be trained on the RL training data by measuring per-issue pass@k from the policy model's rollouts and regressing required sample count against issue features (length, number of files, presence of specific error keywords, base model's average reward on the issue). At inference time, the predictor allocates samples adaptively: easy issues get 10-20 samples, medium issues get 50-100, hard issues get 200-500. The key evaluation would be the cost-accuracy Pareto frontier: does the adaptive allocation achieve (say) 39% solve rate at 150 average samples per issue, matching the 40% that requires 160 uniform samples? This would directly address the paper's unexamined efficiency limitation.

**Combining SWE-RL with interactive debugging scaffolds.** The paper's RL training is conducted entirely on a single-turn repair task (issue + file context → patch), while state-of-the-art SWE-bench results (Claude-3.5-Sonnet at 53.0% with OpenHands, DeepSeek-R1 at 49.2% with Agentless) use interactive scaffolds where the model can search the codebase, run tests, inspect outputs, and iteratively refine its fix. A natural extension would be to adapt SWE-RL to a multi-turn RL setting: the policy LLM receives an issue and repository structure, can request file contents or test execution results through tool calls, and produces a final patch after multiple rounds of interaction. The reward would remain patch similarity (or execution-based if available), but the RL process would now train the model to use tools strategically—when to search, when to run tests, when to read files, when to commit to a fix. This would require reformulating the GRPO group sampling to handle multi-turn trajectories and potentially a more sophisticated reward that credits effective intermediate actions. The key question is whether RL can teach effective tool use without explicit demonstrations, or whether supervised warm-starting is necessary—directly testing the paper's claim that RL can autonomously develop complex reasoning strategies.

**Cross-lingual generalisation of SWE-RL.** All SWE-RL training and evaluation is on Python repositories (SWE-bench Verified is exclusively Python). Real-world software engineering spans dozens of languages with different conventions, error patterns, and testing frameworks. A stress-test follow-up would curate a multi-language version of the seed RL dataset—including JavaScript, TypeScript, Java, Go, and Rust PRs from GitHub—and train SWE-RL on this multilingual dataset, then evaluate on SWE-bench Multimodal (which includes non-Python issues) and on a newly constructed multi-language issue-resolution benchmark. The key measurements would be per-language repair accuracy and out-of-domain performance on language-specific benchmarks. If SWE-RL transfers across languages (e.g., a model trained only on Python issues improves on Java bug-fixing), it would confirm that the emergent reasoning skills are truly language-agnostic. If multilingual training degrades Python performance (negative transfer), it would suggest that the reward signal is entangled with Python-specific patch patterns, a limitation that would require language-conditional reward design or separate per-language policies.

### Practical Applications and Downstream Use Cases

**Automated bug-fixing for open-source projects at scale.** The most direct application of Llama3-SWE-RL-70B is as an automated triage-and-fix system for open-source repositories. A project maintainer could configure a bot that, for each new GitHub issue labelled "bug," automatically runs Agentless Mini with the RL model, generates a candidate patch (or multiple ranked candidates), and submits it as a pull request for human review. With 500 repair samples, the model resolves 41.0% of SWE-bench Verified issues (Table 1)—issues that are, by design, representative of real-world GitHub bugs in popular Python repositories. Even at a more modest 160 samples, the model resolves 40.0% (Figure 4, left), making the cost-accuracy tradeoff explicit. For a maintainer of a project like Django or Flask, where the issue tracker receives hundreds of bug reports, this could meaningfully reduce the triage burden: the model handles the ~40% of issues it can fix autonomously, and human developers focus on the remaining ~60% that require novel reasoning or architectural changes. The key practical requirement is access to 512 H100 GPUs for training (32 hours, Section 3.1), putting this within reach of well-resourced organisations but not individual maintainers—though once trained, the model checkpoint can be served for inference at lower cost.

**Self-improving software engineering assistants with RL-based fine-tuning loops.** The paper's finding that RL on issue-solving data improves general reasoning while SFT degrades it (Table 3) has direct implications for organisations building internal developer tools. A company with a large codebase and a history of resolved issues and PRs could use SWE-RL to periodically fine-tune their deployed code assistant on their own software evolution data. The assistant would improve at fixing issues specific to the company's codebase (learning conventions, common bug patterns, dependency structures) while preserving—and potentially enhancing—its general coding and reasoning capabilities, avoiding the catastrophic forgetting that SFT-based fine-tuning would cause. The 1,600-step RL training with a 16k context window (Section 3.1) is relatively lightweight compared to pretraining, making periodic retraining feasible as new issues are resolved and new code is committed.

**Cost-efficient alternative to proprietary LLMs for SWE-bench-style evaluations.** For researchers and organisations that benchmark software engineering models on SWE-bench, Llama3-SWE-RL-70B at 41.0% (Table 1) provides an open-weight alternative to GPT-4o (38.8% with Agentless) that avoids per-query API costs, rate limits, and model deprecation concerns. A single SWE-bench Verified evaluation run with 500 repair samples and 30 test samples per issue requires approximately 250,000 inference calls to a 70B model, which on proprietary APIs would cost thousands of dollars. Running the same evaluation with an open model on owned or rented GPU infrastructure provides cost predictability and reproducibility—critical for research settings where evaluation budgets are constrained and multiple experimental conditions must be compared. The availability of the model checkpoint (once released, per the NeurIPS checklist response) also enables ablation studies, representation analysis, and fine-tuning experiments that are impossible with API-only models.

### When to Prefer This Method

The paper explicitly positions SWE-RL against SFT-based training approaches for software engineering (the SFT baseline is constructed for this purpose, and Section 4.2 contrasts against SFT-distillation methods like Lingma-SWE-GPT, SWE-Gym, and SWE-Fixer). The tradeoff is cleanly articulated by the results in Tables 1-3. The decision rule is:

- **Prefer SWE-RL (RL on software evolution data) when:** you have access to a large corpus of real-world pull requests with linked issues and oracle patches; you are training an open-weight model and want to avoid dependency on proprietary teacher models; preserving or improving broad reasoning capabilities (math, general coding, language understanding) matters as much as or more than the target SE task; and you can afford the computational cost of RL training (32 hours on 512 H100 GPUs for a 70B model). The expected outcome is moderate-to-strong improvement on the target task (41.0% on SWE-bench Verified, 34.8% repair-only accuracy) with gains on out-of-domain reasoning benchmarks.

- **Prefer SFT (supervised fine-tuning with synthetic data generation) when:** you need a simpler, faster training pipeline (SFT requires only standard next-token prediction, no reward computation or advantage estimation); you have access to a strong proprietary teacher model whose outputs you can distill; you are willing to trade some general capability for task specialisation; and your primary concern is the target task performance rather than broad reasoning preservation. The expected outcome is competitive but generally lower target-task performance (36.2% vs. 41.0% on SWE-bench Verified, 29.6% vs. 34.8% repair-only) with likely regression on out-of-domain benchmarks.

This tradeoff is grounded in the paper's specific comparison (same base model, same seed data source, different training paradigm) and does not generalise to settings where RL or SFT would use different data sources, reward structures, or model scales. The paper does not compare SWE-RL against other RL formulations (execution-based reward, different RL algorithms) or against multi-stage training pipelines (SFT warm-start followed by RL), so the preference is only defined relative to the SFT baseline constructed in this work.
