# Skeleton-of-Thought: Prompting LLMs for Efficient Parallel Generation

**ArXiv:** [2307.15337](https://arxiv.org/abs/2307.15337)

## 🎯 Pitch

This paper proposes **Skeleton-of-Thought (SoT)**, a data-centric prompting strategy that reduces end-to-end generation latency by guiding an LLM to first produce a concise skeleton of the answer and then expand each skeleton point in parallel — via batched decoding for open-source models or parallel API calls for proprietary ones — rather than generating tokens sequentially.

---

## 1. Executive Summary

This paper proposes **Skeleton-of-Thought (SoT)**, a data-centric prompting strategy that reduces end-to-end generation latency by guiding an LLM to first produce a concise skeleton of the answer and then expand each skeleton point in parallel — via batched decoding for open-source models or parallel API calls for proprietary ones — rather than generating tokens sequentially. Evaluated across 12 LLMs ranging from LLaMA2-Chat-7B to GPT-4 on the Vicuna-80 and WizardLM assistant-style benchmarks, SoT achieves speed-ups up to 2.39× while maintaining or improving answer quality on question categories whose answers naturally decompose into independent points — such as knowledge, generic, and common-sense — and a router-based extension (**SoT with router, SoT-R**) adaptively falls back to normal decoding for step-by-step reasoning or coding tasks, establishing that structured parallel generation is viable and beneficial only when the answer’s internal points lack sequential dependencies.

## 2. Context and Motivation

### The Core Problem: Sequential Decoding Makes LLM Inference Slow

The paper identifies a fundamental bottleneck in how state-of-the-art large language models generate text: **autoregressive, token-by-token sequential decoding**. Every LLM response — whether a single-word answer or a multi-paragraph essay — is produced one token at a time, with each token generation depending on all previous tokens. This sequential dependency means the computation for generating token $t_i$ cannot begin until token $t_{i-1}$ is complete. For long responses, this creates substantial end-to-end latency that degrades user experience in interactive applications.

The paper quantifies this latency concretely in its opening: Claude (accessed through Slack) takes 22 seconds to answer the example question in Figure 1, while Vicuna-33B V1.3 running locally on one NVIDIA A100 GPU takes 43 seconds. These latencies are not merely an inconvenience — they fundamentally limit the deployment scenarios where LLMs can serve as interactive assistants. Whether in chatbot interfaces, real-time agent-agent communication, or low-latency serving systems, users must wait for the entire sequential generation pipeline to complete before seeing the full response.

The paper traces this latency problem to **three distinct causes**, but argues that prior work has addressed only two of them:

1. **Large model size**: FP16 weights of a 175B model consume 350 GB of GPU memory, requiring multiple high-end GPUs just to load the model. The memory access and computation per token are substantial.
2. **Quadratic attention complexity**: The transformer's self-attention mechanism scales quadratically in sequence length, creating I/O bottlenecks and large memory footprints for long contexts.
3. **Sequential decoding itself**: The autoregressive generation paradigm forces tokens to be produced one at a time, creating a fundamental serial dependency that **prevents parallelization across tokens within a single response**.

The first two axes — model size and attention complexity — have been the focus of extensive research (model compression, quantization, efficient attention mechanisms, serving systems). The third axis, however, has been largely taken as an **unquestioned assumption**: that LLMs *must* decode sequentially because each token depends on all prior tokens. This paper challenges that assumption directly, asking whether the *content* of the answer can be organized in a way that enables parallel generation of different parts, even while individual tokens within each part are still generated autoregressively.

### Why This Problem Matters: Beyond Reading Speed

The paper argues that reducing end-to-end generation latency matters for reasons beyond simply matching human reading speed. It identifies two specific scenarios where low latency is critical:

**User experience in structured information extraction.** Users do not always read responses linearly from start to finish. They may want to (1) quickly scan the response structure to verify the LLM understood the question, or (2) jump directly to specific information without waiting for introductory paragraphs or preceding points to be generated. In these scenarios, getting the skeleton/structure to the user quickly — even before every detail is expanded — provides immediate utility. The paper notes (Appendix L) that "a well-defined structure in responses assists us in quickly parsing all the information."

**Emerging agent-agent interaction scenarios.** Beyond human-facing chatbots, the paper points to the growing importance of LLM-to-LLM communication, where one model's output feeds into another model's input. In such pipelines, the end-to-end latency of each link in the chain compounds, and reducing per-response latency becomes essential for overall system responsiveness. This is positioned as a forward-looking motivation that will grow in importance as multi-agent LLM systems proliferate.

### Prior Approaches to LLM Efficiency: Where They Fall Short

The paper taxonomizes existing efficiency techniques into three levels and explains why each fails to address the sequential decoding bottleneck:

#### Model-Level Optimization: Changes the Model, Requires Retraining

Extensive work has redesigned transformer architectures for efficiency: mixture-of-experts (Lepikhin et al., 2021; Fedus et al., 2022) for conditional computation, efficient attention mechanisms (Kitaev et al., 2020; Wang et al., 2020; Shazeer, 2019) to reduce quadratic complexity, and compression techniques including quantization (Xiao et al., 2022; Frantar et al., 2022; Lin et al., 2023) and sparsification (Mishra et al., 2021; Zaheer et al., 2020; Wang et al., 2021). These methods can benefit both latency and throughput, but they share a critical limitation: **they require modifying the model architecture or weights**, which means substantial retraining or fine-tuning cost. More importantly from the paper's perspective, they do not address the sequential decoding paradigm — a quantized or sparse model still generates tokens one at a time, fundamentally limited by the autoregressive bottleneck.

#### System-Level Optimization: Improves Throughput, Not Latency

Serving systems employ numerous techniques to maximize hardware utilization: computational graph optimization (Dao et al., 2022), pipeline and tensor parallelism for model sharding (Lu et al., 2017; Huang et al., 2019; Narayanan et al., 2019; Rajbhandari et al., 2020), and crucially, **batching** (Fang et al., 2021; NVIDIA, 2021; Google, 2021; Yu et al., 2022) where multiple queries are packed together to improve GPU utilization during decoding. The paper makes an important distinction: these techniques primarily target **throughput** (serving many users simultaneously) rather than **end-to-end latency** for a single query. As stated in Section 5 (expanded in Appendix D.1), these methods "mainly aim at enhancing the throughput rather than the end-to-end latency." When a single user waits for one long response, batching provides no benefit — there is only one query to process.

The paper further contextualizes its relationship to system-level techniques by noting a **synergistic opportunity**: SoT converts a single sequential workload into multiple parallel point-expanding requests. These parallel requests can then benefit from throughput-oriented batching techniques, effectively "making these throughput-oriented techniques help with end-to-end latency." SoT operates at what the paper calls a novel "inter-content" parallelism level — distinct from existing parallelism dimensions like inter-instance, inter-operation, and intra-operation parallelism in current serving systems.

#### Decoding-Specific Optimizations: Target Token-Level Parallelism, Not Content-Level

Two existing research lines specifically target the decoding bottleneck:

**Speculative decoding (SD)** methods (Stern et al., 2018; Leviathan et al., 2022; Chen et al., 2023a; Gante, 2023) use a smaller, faster "draft" model to generate candidate token sequences sequentially, then have the target LLM verify these candidates in parallel. Tokens that match the target LLM's predictions are accepted; mismatched tokens are regenerated. This achieves some parallelism at the verification stage, but the generation of candidates remains sequential. The paper notes these methods "rely on either assisting models" — requiring a compatible small model — and operate at the level of consecutive tokens within a response, not at the level of organizing answer content.

**Non-autoregressive generation (NAG)** methods (Gu et al., 2018; Xiao et al., 2023; Santilli et al., 2023) sample and refine multiple tokens simultaneously, completely abandoning the left-to-right generation order. However, these methods typically require "specially designed models, training schemes, or sampling schemes" — they are not applicable to off-the-shelf, instruction-tuned LLMs without modification. Moreover, the quality of non-autoregressive generation often lags behind autoregressive models, requiring multiple refinement iterations that partially negate the speed benefits.

Both SD and NAG operate at the **token level**: they try to parallelize the generation of consecutive words or subwords within a response. SoT takes a fundamentally different approach by operating at the **content level**: it restructures *what* the answer says (into independent, parallel-expandable points) rather than changing *how* individual tokens are generated. As the paper emphasizes (Appendix D.1):

> "SoT prompts the LLM itself to plan the contents in a way that permits the parallel generation of multiple tokens in different segments. SoT exploits the emerging instruction-following and planning ability of SoTA LLMs rather than relying on specially designed modeling, sampling, and training schemes."

### The Missing Piece: Data-Centric Efficiency Optimization

The paper positions SoT within a broader paradigm it calls **"data-centric optimization for efficiency"** or "content co-organization for efficiency." Just as data-centric AI focuses on improving data quality to enhance model quality, this paper proposes that organizing the *output content structure* — rather than modifying the model or the serving system — can improve inference efficiency. This perspective is framed as becoming "feasible and expected to grow in importance, owing to the evolving capabilities of state-of-the-art LLMs" — meaning that as LLMs become better at instruction-following and planning, explicitly instructing them about answer structure becomes a viable efficiency lever.

The paper explicitly connects this to the broader prompting literature, which has extensively explored how to elicit better *quality* from LLMs through structured thinking (Chain-of-Thought, Tree-of-Thoughts, ReAct) but has not been applied to improving *efficiency*. As the paper states (Section 5, expanded in Appendix D.2):

> "Instead of focusing on answer quality, SoT is a first attempt at exploiting the power of prompting to improve efficiency."

### Prior Work on Hierarchical Text Generation: Quality, Not Efficiency

The paper also situates SoT relative to hierarchical text generation methods (Li et al., 2015; Shao et al., 2019; Puduppully et al., 2019; Fan et al., 2018) which organize text into high-level (sentence/document) and low-level (word) structures. These methods share a superficial similarity with SoT's skeleton-then-expand structure, but differ in three critical ways:

1. **Objective**: Prior hierarchical methods focus entirely on improving *answer quality* — coherence, topic relevance, reducing redundancy — not on generation efficiency. They still generate text sequentially word-by-word within each hierarchical level; no parallelism is exploited.

2. **Architecture**: They require designing "hierarchical neural architectures that contain different modules to model high-level and low-level dependencies" or training "dedicated planning modules" — specialized models that cannot be applied to off-the-shelf LLMs.

3. **Planning representation**: Their plans are either "implicit latent variables" (not interpretable text) or "closed-form planning that only reorders and groups input keywords" (not free-form reasoning about what to say). SoT instead uses explicit, free-form natural language as the plan — the skeleton is human-readable text describing *what points to make* and *in what order*.

The paper acknowledges that this prior work "could provide inspiration for future expansions of SoT to generate high-quality answers for broader types of questions," but emphasizes that SoT's core contribution — using planning for *efficiency*, applied to *existing models without modification* — is novel.

### How This Paper Positions Itself

The paper does not claim to propose a universal, one-size-fits-all acceleration method. Instead, it is explicit about its **scope and limitations**, which strengthens its positioning:

- SoT is **suitable for questions whose answers can be decomposed into relatively independent points** that can be expanded without referencing each other's content. This includes a wide range of real-world assistant queries (knowledge questions, advice-giving, explanations, roleplay scenarios, counterfactual reasoning) but excludes step-by-step problem-solving (math, Fermi problems) and tasks with strong sequential dependencies (code generation, narrative writing).

- The paper does not claim that SoT always improves quality — it presents mixed results showing quality improvements on some question categories and models, competitive parity on others, and degradation on a few. This honesty about limitations makes the positive results more credible.

- The router extension (SoT-R) is presented as making SoT "more practical" by adaptively falling back to normal generation for unsuitable questions, acknowledging that real-world deployment requires handling heterogeneous query types.

- SoT is positioned as **complementary to, not competing with**, model- and system-level optimizations. The paper explicitly shows combined speed-ups with quantization (Appendix J) and discusses how its batched point-expanding can leverage throughput-oriented batching systems. The vision is that SoT adds a new dimension to the efficiency toolbox, not that it replaces existing techniques.

### The Fundamental Intuition: Humans Don't Always Think Sequentially

Ultimately, the paper grounds its motivation in an analogy to human cognition:

> "Humans do not always think about questions and write answers in a sequential fashion. In contrast, for many question types, we first derive the skeleton according to some protocols and strategies, and then add evidence and details to explain each point."

This observation — that effective human communication often involves outlining before writing — serves as the **intuitive justification** for questioning the necessity of fully sequential decoding. If humans can produce high-quality answers by first planning the structure and then filling in details (potentially in parallel, if multiple writers were available), perhaps LLMs can too. The paper's contribution is demonstrating that current instruction-tuned LLMs *already possess* the capability to do this when appropriately prompted, without any model modification, training, or specialized serving infrastructure. This positions SoT not as a new capability being taught to models, but as an *elicitation* of an existing capability (structured planning and independent point expansion) that has been latent in instruction-tuned LLMs but untapped for efficiency purposes.

## 3. Technical Approach

### 3.1 Reader Orientation

This paper presents a purely prompt-based system — no model modification, fine-tuning, or specialized infrastructure — that accelerates LLM inference by restructuring *how* an answer is generated rather than *how fast* individual tokens are produced. The problem it solves is the high end-to-end latency of sequential decoding for long-form responses; the "shape" of the solution is a two-stage pipeline where the LLM first produces a short, structured outline (the skeleton) and then fills in each outline point independently and in parallel, with the parallelism coming from batched decoding on open-source models or concurrent API calls on proprietary ones.

### 3.2 Big-Picture Architecture (Diagram in Words)

The SoT pipeline has **three sequential stages** that process a user question into a final answer:

1. **Skeleton Stage**: The question is wrapped in a skeleton prompt template (`T_s`) that instructs the LLM to output *only* a concise, numbered list of short skeleton points (3–10 points, each 3–5 words) covering the key aspects of the answer. A single LLM call produces the skeleton response `R_s`. A regular expression extracts each point's index and skeleton text.

2. **Point-Expanding Stage (Parallel)**: For each of the `B` extracted skeleton points, an independent point-expanding request is constructed by wrapping the *original question*, the *full skeleton*, and the *specific point's index and text* into a point-expanding prompt template (`T_pe`). These `B` requests are sent to the LLM **simultaneously** — as a batch for local open-source models, or as parallel API calls for proprietary models — and each returns a 1–2 sentence expansion of its assigned point. The parallel execution is the sole source of speed-up.

3. **Aggregation**: The point-expanding responses `{R_pe_b}` are concatenated in skeleton order, with the skeleton point headers optionally included, to form the final answer returned to the user.

For the **SoT with Router (SoT-R)** extension, a **Router** component precedes the skeleton stage: it examines the question and decides whether SoT should be triggered (if the answer can be decomposed into independent points) or whether normal sequential decoding should be used instead (for step-by-step reasoning, coding, etc.). The router can be implemented via LLM prompting or a trained lightweight classifier.

### 3.3 Roadmap for the Deep Dive

- **First**, the skeleton prompt design, because the quality and format of the skeleton determines everything downstream — how many points are generated, whether they are truly independent, and whether the point-expanding stage can succeed.
- **Second**, the point-expanding prompt design and the parallel execution mechanism, because the speed-up comes entirely from batching these independent point-expanding requests, and understanding *why* batching works requires explaining the prefilling-vs-decoding latency breakdown.
- **Third**, the router design (both prompting-based and trained), because it determines the practical applicability of SoT across heterogeneous question types and represents the key mechanism for graceful degradation.
- **Fourth**, the latency estimation methodology, because all speed-up numbers in the paper are computed analytically from profiling tables rather than measured end-to-end, and the reader needs to understand how those numbers are derived to assess their validity.
- **Fifth**, the answer quality evaluation protocol, because the paper's claims about quality improvement or maintenance depend on an LLM-as-judge framework with specific design choices to avoid bias.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is a **prompt engineering and systems paper** whose core idea is that the autoregressive decoding bottleneck — universally assumed to be fundamental because each token depends on all previous tokens — can be circumvented at the *content level*: by having the LLM itself plan the answer as independent segments *before* generating detailed content, the segment-level expansions become parallelizable even though token-level generation within each segment remains sequential. The approach requires no model modification, no retraining, and no changes to the serving infrastructure beyond what batching already provides.

---

#### Skeleton Prompt Design and Point Extraction

The skeleton stage is the critical planning step that determines whether parallel expansion is possible. The skeleton prompt template `T_s` (shown as Prompt 1 and Prompt 3 in the paper) is engineered to satisfy four constraints simultaneously:

**Constraint 1: Conciseness.** The prompt instructs: "Instead of writing a full sentence, each skeleton point should be very short with only 3∼5 words." This is essential for efficiency — if the skeleton is long, the prefilling cost of the skeleton stage negates the speed-up from parallel expansion. It also ensures that the point-expanding stage receives a focused, non-redundant starting point for each segment.

**Constraint 2: Consistent, machine-parseable format.** The prompt specifies: "Provide the skeleton in a list of points (numbered 1., 2., 3., etc.) to answer the question." A partial answer `1.` is appended to the prompt as the assistant's first token, forcing the LLM to continue numbering from 1. This design trick ensures the skeleton response follows a predictable format that can be parsed with a simple regular expression: `(\d+)\.\s?([\s\S]+?)(?=\n|\n*$)` — matching a digit followed by a period, then whitespace, then capturing all content until the next newline or end of string.

**Constraint 3: Appropriate point count.** The prompt instructs: "Generally, the skeleton should have 3∼10 points." This bounds the parallelism — too few points would limit speed-up, while too many points would create excessive prefilling overhead. The actual number of points produced varies by model and question category: across all models on Vicuna-80, the average is 6.8 points (Figure 11a, Appendix G), with GPT-4 and StableVicuna-13B generating the most (~9 on average) and LLaMA2, Vicuna-7B V1.1, Vicuna-7B V1.3, and ChatGPT-3.5 generating fewer (<6).

**Constraint 4: Demonstrated format via examples (for weaker models).** The paper finds that GPT-4 can follow the skeleton instructions without demonstrations, but all other models require two-shot demonstrations embedded in the prompt (Prompt 3 vs. Prompt 1). The two demonstrations show examples of questions with their corresponding short skeleton lists — one about Chinese dishes (8 skeleton points: Dumplings, Noodles, Dim Sum, etc.) and one about reducing carbon emissions (6 skeleton points: Energy conservation, Efficient transportation, etc.). These demonstrations serve as in-context examples of the desired output format without requiring model retraining.

**Why the partial answer trick works.** By providing the partial answer `1.` as if the assistant has already begun responding, the LLM's next-token prediction is constrained to continue within the established numbering format. This leverages the autoregressive nature of LLMs — they are trained to continue text in the style and format they observe — rather than relying on out-of-distribution instruction-following. For ChatGPT-3.5 specifically, the implementation is described as "not a documented approach": the partial answer is provided as a last message in the chat history from the assistant role. The paper notes this "works well in most cases" but occasionally causes ChatGPT-3.5 to repeat the provided partial answer.

**Model-specific prompt variations.** The paper documents the following variations in skeleton prompting across models (Section 2.1, Appendix B.1):
- GPT-4: uses Prompt 1 (no demonstrations, since it follows instructions without examples).
- All other models: use Prompt 3 (with two-shot demonstrations).
- Claude (over Slack API): has "no obvious way to give the API a partial answer," so the prompt is modified to include "Please start your answer from `{partial answer}` and do not output other things before that" at the end. The paper notes "Claude understands and obeys it well."
- System message: not included for open-source models except LLaMA2.
- Conversation templates: different models use different string delimiters for user/assistant messages (e.g., Vicuna uses "USER:" and "ASSISTANT:", UltraLM uses "User:" and "</s>Assistant:"), and these are handled via the FastChat codebase's conversation template system.

**Skeleton extraction.** After receiving the skeleton response `R_s`, the system applies the regular expression to extract point indices and their associated short skeleton text. The example in Figure 1 shows a clean extraction: for the question about conflict resolution strategies, the skeleton yields points like "1. Active listening," "2. Identify issues," "3. Compromise." In practice, some models sometimes fail to follow the format — for example, OpenChat-13B and LLaMA2-Chat-13B occasionally "complete the skeleton points" by writing full paragraphs instead of short phrases during the skeleton stage (Appendix I.1.1), which both wastes computation and violates the assumed independence of the point-expanding stage.

**What happens when the skeleton embeds the full answer.** The paper observes an interesting emergent behavior: for questions requiring step-by-step reasoning (Fermi problems, math), some models — particularly on Fermi questions — produce a skeleton that already contains complete computation steps and results, essentially embedding the full answer in the skeleton stage. The paper notes this "sheds light on a promising direction for making SoT a general framework: in the problem where step-by-step thinking is needed, the SoT model automatically falls back to the sequential generation mode by outputting the complete answer in the skeleton stage and skipping the point-expanding stage" (Appendix I.1.2). This behavior is not explicitly designed into the prompt but emerges from the model's understanding that the skeleton should be substantive when the answer is inherently sequential.

#### Point-Expanding Prompt Design and Parallel Execution

Once the skeleton is extracted, each point is expanded independently. The point-expanding prompt template `T_pe` (Prompt 2) assembles four pieces of context:

1. The original question `q` (so the LLM remembers the full context).
2. The complete skeleton `R_s` (so the LLM knows how this point fits into the overall answer structure — though the paper notes this is imperfect, as the LLM does not have access to the *expanded content* of other points).
3. The specific point index `b` (to identify which skeleton point is being expanded).
4. The point skeleton text `R_s^b` (the short phrase describing what this point should cover).

The prompt template then instructs: "Continue and only continue the writing of point {point index}. Write it **very shortly** in 1∼2 sentence and do not continue with other points!" A partial answer `{point index}. {point skeleton}` is provided so the LLM continues from exactly that text.

**Design choices in the point-expanding prompt:**

- **The "very shortly" instruction**: This is critical for maintaining speed-up. If point-expanding responses are long, the decoding time per point increases, reducing the benefit of parallelism. The paper evaluates this: "Claude and GPT-4 follows the instruction 'Write it **very shortly** in 1∼2 sentence and do not continue with other points!' in Prompt 2 very well, so that the answers are very short. Therefore, we delete '**very shortly**' from the prompt template in Claude and GPT-4" (Appendix B.1). This means for Claude and GPT-4, the instruction is simply "Write it in 1∼2 sentence" — the emphasis on brevity is removed because these models obey the instruction too well, producing responses that are *too* short and lacking detail.

- **"Do not continue with other points"**: This instruction prevents the LLM from preemptively expanding the next skeleton point. Without it, some models would chain together multiple point expansions in a single response, breaking the independence assumption and preventing parallel execution.

- **No demonstrations in the point-expanding prompt**: Unlike the skeleton prompt, the paper finds that "demonstrations are not necessary to get reasonable results" for point expansion, even for weaker models. The task — given a topic phrase, write 1–2 sentences about it — is sufficiently simple that in-context examples provide no benefit.

- **The partial answer trick revisited**: The same partial answer mechanism from the skeleton stage is used: appending `{point index}. {point skeleton}` to the prompt so the LLM continues from there. For ChatGPT-3.5, this is provided as the last assistant message; for Claude over Slack, the text "Please start your answer from '{partial answer}' and do not output other things before that" is appended.

**Parallel execution mechanism (open-source models).** This is where the speed-up actually materializes. The paper explains the mechanism in detail (Section 2.1, expanded in Appendix E):

A typical LLM generative process has two phases:

1. **Prefilling phase**: The entire input prompt is processed in one forward pass to compute the key-value (KV) cache for all input tokens. This phase is **compute-bound**: the GPU's tensor cores are relatively well-utilized because the attention computation over the full prompt length involves substantial matrix multiplications. For LLaMA-7B on an NVIDIA A100, prefilling 128 tokens achieves 43 TFLOPS (13.8% of the A100's FP16 peak of 312 TFLOPS), taking 40 ms (Table 5, Appendix E).

2. **Decoding phase**: Tokens are generated one at a time, with each new token attending to all previous tokens via the KV cache. This phase is **memory-bound**: for each token, all model weights (7B parameters for LLaMA-7B, occupying ~14 GB in FP16) must be loaded from GPU HBM (high-bandwidth memory) onto the compute units at least once, but only a tiny amount of activation data (~20M values = 0.02 GB for a context length of 64) is transferred. The result is severe under-utilization: LLaMA-7B achieves only 0.31 TFLOPS (0.1% utilization) during decoding, taking 2,735 ms to decode 64 tokens.

The critical insight: **in the decoding phase, processing a batch of B sequences incurs roughly the same per-token latency as processing a single sequence**. This is because the weights — which dominate memory access — are loaded once and shared across all sequences in the batch. As the batch size B increases, the GPU's compute utilization increases almost linearly (Figure 10b, Appendix E: 0.31→~5 TFLOPS as B goes from 1 to 9 for LLaMA-7B), but the per-token latency stays nearly constant (Figure 10a: 2,735→~3,500 ms for LLaMA-7B as B goes from 1 to 9). The peak memory overhead grows slowly (Figure 10c: ~20→~65 GB for LLaMA-33B as B goes from 1 to 9) because the model weights dominate memory consumption regardless of batch size.

**Operational consequence for SoT**: If the sequential answer would be N tokens long, and SoT decomposes it into B roughly equal segments of length N/B, then decoding all B segments as a batch takes approximately the same time as decoding one segment of length N/B sequentially — a theoretical B× speed-up for the decoding phase. In practice, the speed-up is less than B because: (a) the prefilling cost is higher for SoT (B independent prompts must be prefilled vs. one prompt for normal generation), (b) the segment lengths are imbalanced (some points require more tokens than others), and (c) the total answer length with SoT is often longer than the normal answer (Figure 11f: on average 1–2× longer for most models).

**Parallel execution mechanism (API-based models).** For proprietary models accessed via API (ChatGPT-3.5, GPT-4, Claude), the paper issues multiple parallel API calls — one per skeleton point. The end-to-end latency is the skeleton API call latency plus the maximum latency among the B point-expanding API calls. This achieves speed-up because the B point expansions execute concurrently rather than sequentially. The cost is increased total API token consumption (due to the repeated skeleton and prompt text in each point-expanding request) and increased number of API requests.

**Actual latency numbers (Appendix G.1.2, Figure 12).** The latency breakdown reveals that the decoding phase dominates total latency across all models and question categories. For example, on Vicuna-33B V1.3 (Figure 12a), normal generation takes ~37,000 ms total, with ~35,000 ms in the decoding phase and ~2,000 ms in prefilling. SoT's skeleton stage takes ~5,000 ms total (prefill + decode), while the batched point-expanding stage takes ~8,000 ms total (with the per-point decoding latency roughly matched to normal decoding of a single short segment). The total SoT latency is ~13,000 ms — achieving ~2.8× speed-up — because the point-expanding decodes B shorter segments simultaneously rather than one long segment sequentially.

**Dealing with the prefilling overhead.** The paper acknowledges that SoT increases prefilling cost significantly because each point-expanding request includes the full skeleton and original question. For API-based models, the prefilling overhead ratio (SoT total prefilling / normal prefilling) is 60–89× (Table 6, Appendix H). For open-source models, a trick is used: "prefill the common prefix of point-expanding requests with a batch size of 1 during Stage 2," reducing the ratio to 30–39× (Table 7). The paper suggests future optimizations: reusing the KV cache containing the question and skeleton from Stage 1 during Stage 2 (rather than re-prefilling them), and using prompt tuning to design shorter SoT prompts.

**Supporting multi-round conversation (Appendix B.2).** To avoid the prefilling overhead compounding across conversation turns, SoT stores only the final aggregated answer in conversation history, not the intermediate SoT prompts. This means subsequent conversation turns are not affected by the SoT-specific prompt structure.

#### Router Design: Adaptively Triggering SoT

The fundamental limitation of vanilla SoT is that it forces all questions through the skeleton-then-expand pipeline, regardless of whether the answer naturally decomposes into independent points. As the quality analysis in Section 3.2.3 shows, SoT performs poorly on math, coding, Fermi problems, and writing — question types where answer segments have sequential dependencies, where the skeleton is hard to formulate a priori, or where the answer should read as a coherent passage rather than a bulleted list.

SoT-R addresses this by inserting a **router** that decides, for each question, whether to use SoT or fall back to normal sequential decoding. The router is a binary classifier: output "positive" means use SoT; output "negative" means use normal generation. The paper explores two implementations with different training requirements and deployment characteristics.

**Prompting Router (Section 4.1).** This approach uses GPT-4 itself as the router, querying it with a structured prompt (Prompt 4, Appendix C.1) that asks whether the answer to the question should be:

- **A**: "Organize the answer as a list of points or perspectives ... and the points or perspectives can be answered independently without referring to the contents of the previous points." → **Trigger SoT**.
- **B**: "Organize the answer as a list of points or perspectives ... and the contents of later points or perspectives cannot be answered independently without referring to the contents of the previous ones." → **Do not trigger SoT** (sequential dependencies exist).
- **C**: "Do not organize the answer as a list of points or perspectives." → **Do not trigger SoT** (answer is not list-structured).

The prompt includes "Just say A, B, or C. Do not explain. Do not provide an answer to the question." to minimize token cost. GPT-4 is chosen "given its strong capability" for this classification task. The key advantage: no model training is required, making this approach immediately deployable. The key disadvantage: "its performance remains sensitive to prompt design" and the router latency for GPT-4 API calls is non-trivial (average 0.65 seconds on Vicuna-80, ranging 0.39–1.37 seconds per question; Appendix G.2).

**Trained Router (Section 4.2).** This approach frames routing as a standard sequence classification task: fine-tune a lightweight model to predict whether a question is suitable for SoT, using human-annotated data.

The training pipeline has the following components:

*Dataset*: The training uses the **LIMA dataset** (Zhou et al., 2023), which contains 1,030 Q&A pairs from Stack Exchange, wikiHow, and Reddit. The paper annotates this dataset with binary labels (1 = suitable for SoT, 0 = not suitable). The annotation process uses GPT-4 to assist: GPT-4's response to each question is analyzed, and the question receives a positive label if it meets two criteria: "(1) it contains a list of points that can be expanded in parallel, (2) each point provides sufficient details (i.e., the point-expanding response is not too short), which will enable SoT to achieve a speed-up" (Appendix C.2.1). Two of the paper's authors independently annotate and discuss disagreements. The final annotated distribution: 371 out of 1,030 questions are suitable for SoT. The Vicuna-80 and WizardLM datasets are also annotated for evaluation (not training).

*Model architecture*: A RoBERTa-base model (Liu et al., 2019) with 120M parameters is fine-tuned. The model takes a question text as input and outputs a binary classification score.

*Training hyperparameters*: AdamW optimizer (Loshchilov & Hutter, 2019) with weight decay 0.01. Learning rate warms up during the first 1% of iterations to `5e-5` and then decays linearly. Trained for 2 epochs with batch size 32. Input sequences are padded or truncated to 512 tokens. The entire fine-tuning completes in 2 minutes on one NVIDIA A100 GPU.

*Loss function*: The paper uses **Tversky loss** (Wang et al., 2023b) with parameters α = 0.7 and β = 0.3, which penalizes false positives more heavily than false negatives. This asymmetric penalty reflects the deployment priority: "false positives (SoT is incorrectly triggered when it should not be, resulting in degraded answer quality) are of more significant concern than false negatives (the router misses a potential SoT trigger, resulting in a reduced speed-up)" (Appendix C.2.2). Label smoothing (Szegedy et al., 2016) with factor ε = 0.2 is also applied to improve calibration.

*Inference*: At test time, the fine-tuned RoBERTa model takes a question text as input and outputs a classification score. A threshold (not explicitly specified in the paper, but implicitly the model's decision boundary) determines whether SoT is triggered.

*Router latency*: The trained router is extremely fast — average 0.04 seconds on Vicuna-80 (ranging 0.008–1.55 seconds) — compared to 0.65 seconds for the GPT-4 prompting router (Appendix G.2).

**Router Consistency Analysis (Appendix C.3).** The paper compares the three routers (human annotation, GPT-4 prompting, and trained RoBERTa) using confusion matrices on Vicuna-80 (Tables 3) and WizardLM (Tables 4). On Vicuna-80 (80 questions), there is "a notable level of agreement among the three routers": the GPT-4 router agrees with human annotations on 75 out of 80 questions (38 true negatives + 37 true positives, with 5 false positives and 0 false negatives); the trained router agrees on 69 out of 80 questions (37 true negatives + 32 true positives, with 6 false positives and 5 false negatives). On WizardLM (218 questions), the GPT-4 router shows many false positives (66 questions classified as suitable that humans considered unsuitable), while the trained router aligns more closely with human annotations (135 true negatives + 27 true positives).

**Human router as benchmark.** For evaluation purposes, the paper includes a "human router" where two of the authors manually judge whether SoT should be applied for each question. This serves as an upper bound on router performance — it represents the quality achievable if a perfect classifier existed — and provides context for interpreting the automated routers' performance.

**Concurrent execution (Appendix C.4, Figure 9).** The paper sketches an alternative architecture where the router, normal generation, and SoT generation run concurrently: "Once the router makes a decision, one of the normal and SoT generation processes can be aborted." This would eliminate the router latency from the critical path but at the cost of wasted computation (either the SoT skeleton or the beginning of normal generation would be aborted). The paper does not implement this approach.

#### Latency Estimation Methodology

The paper does not measure end-to-end wall-clock latency for each individual SoT invocation. Instead, it uses a **profiling-based analytical estimation** that is more scalable for comparing 12 models across 80–218 questions with different skeleton point counts and token lengths.

**Latency profiling for open-source models (Appendix F).** For each LLaMA architecture (7B, 13B, 33B), the authors construct two profiling tables on the target GPU (NVIDIA A100-80G with CUDA 11.7, Hugging Face Transformers 4.28.1, PyTorch 2.0.1):

1. **Decoding latency table**: For each batch size `B = 1, ..., 16` and each context length `k = 1, ..., 1024`, the latency of decoding the `(k+1)`-th token, denoted `t_D^B(k)`, is measured using `torch.cuda.Event`. Each measurement runs "three times continuously," and the geometric mean is taken.

2. **Prefilling latency table**: For each batch size `B = 1, ..., 16` and each input token length `k` in `range(1, 700, 10)` (i.e., lengths 1, 11, 21, ..., 691), the latency of prefilling all tokens, denoted `t_P^B(k)`, is measured. Each measurement runs "seven times continuously, regard the first two times as the warmup tests, and take the geometric mean of the last five times."

**Latency computation for a single request.** Given an input of length `l_i` tokens, an output of length `l_o` tokens, and a decoding batch size `B`, the total latency is:

$$T(l_i, l_o, B) = \tilde{t}_P^B(l_i) + \sum_{k=l_i}^{l_i + l_o - 1} t_D^B(k)$$

where `T(l_i, l_o, B)` is the total latency in milliseconds, `l_i` is the number of input (prefill) tokens, `l_o` is the number of output (decode) tokens, `B` is the batch size of sequences being decoded together, `\tilde{t}_P^B(l_i)` is the estimated prefilling latency for `l_i` tokens at batch size `B`, and `t_D^B(k)` is the latency of decoding the `(k+1)`-th token at batch size `B` with context length `k`.

**What it computes:** given the input prompt length, the desired output length, and the batch size, this formula sums the prefilling latency (one forward pass over `l_i` tokens) and the cumulative decoding latency (iterating token-by-token from context length `l_i` to `l_i + l_o - 1`, looking up each per-token latency from the profiling table). The result is the estimated total latency for that request in that batching configuration.

**Why this form:** the prefilling phase is treated as a single operation because all input tokens are processed in one forward pass with full parallelism across the sequence dimension. The decoding phase is treated as a sum of per-token latencies because each token depends on all previous tokens and must be generated sequentially — the fundamental autoregressive bottleneck that SoT aims to circumvent. The geometric mean over multiple runs reduces variance from GPU timing fluctuations.

**Interpolation for unmeasured prefilling lengths.** Since prefilling latency is measured only at every 10th token length (1, 11, 21, ..., 691), intermediate lengths are estimated by:

$$\tilde{t}_P^B(l_i) = t_P^B(\lfloor \frac{l_i}{10} \rfloor \times 10 + 1)$$

where `\lfloor \cdot \rfloor` is the floor function. This rounds the input length down to the nearest measured multiple of 10 and adds 1 (the smallest measured length), creating a conservative estimate (slightly underestimating latency, since the actual length may be longer than the rounded-down value).

**SoT latency computation.** The total SoT latency is computed as the sum of the skeleton stage latency and the point-expanding stage latency:

$$L_s(l_i^s, l_o^s) = T(l_i^s, l_o^s, 1)$$

$$L_{pe}(l_i^{pe}, l_o^{pe}, B) = T(l_i^{pe}, l_o^{pe}, B)$$

where `L_s` is the skeleton stage latency (computed with batch size 1 since there is only one skeleton request), `l_i^s` is the token length of the skeleton request, `l_o^s` is the token length of the skeleton response, `L_{pe}` is the point-expanding stage latency (computed with batch size `B` — the number of skeleton points — since all `B` point-expanding requests are batched together), `l_i^{pe}` is the token length of the *longest* point-expanding request, and `l_o^{pe}` is the token length of the *longest* point-expanding response.

**Why the longest-point assumption.** The latency of a batched operation is determined by the slowest element in the batch. Since the paper pads all point-expanding requests to uniform length (padding is added to the left), the prefilling cost is determined by the longest request. Similarly, during decoding, all `B` sequences generate tokens simultaneously, but the overall batch decoding continues until the longest sequence finishes — so the decoding cost is determined by the longest point-expanding response. This is why Figure 11c reports "maximum point-expanding response length" and Figure 11d reports its ratio to the normal answer length — these metrics directly affect achievable speed-up: if one point is much longer than others, the batch decoding time is dictated by that outlier, reducing parallelism benefits.

**API-based model latency measurement.** For API-based models (ChatGPT-3.5, GPT-4, Claude), profiling tables cannot be constructed because the paper lacks access to internal serving infrastructure. Instead, actual API call latencies are recorded using `time.time()` before and after each call. The SoT latency is: `(skeleton API call latency) + max(point-expanding API call latencies)` — the skeleton call must complete before point-expanding calls can be issued (since the skeleton text is needed to construct the point-expanding prompts), and the overall latency is determined by the slowest parallel point-expanding call.

**GPU performance computation.** The profiling tables also enable computing the average GPU performance (in TFLOPS) during decoding:

$$P^D(l_i, l_o, B) = \frac{\sum_{k=l_i}^{l_i + l_o - 1} f_B^D(k)}{\sum_{k=l_i}^{l_i + l_o - 1} t_B^D(k)}$$

where `P^D(l_i, l_o, B)` is the average GPU performance in floating-point operations per second (FLOPS), and `f_B^D(k)` is the number of floating-point operations required to decode one token with context length `k` at batch size `B` — computed using DeepSpeed's FLOPs profiler.

**What it computes:** the ratio of total FLOPs required to total time taken, giving the average computational throughput during decoding. This formula explains *why* batched decoding provides speed-up: as `B` increases, `f_B^D(k)` (the numerator) scales roughly linearly with `B` (proportional to the amount of computation), while `t_B^D(k)` (the denominator) grows sub-linearly (because weight loading, the bottleneck, is shared across the batch). The result is higher FLOPS — better GPU utilization — without proportionally higher latency.

**Validation.** The paper also reports "actual latency testing" (Appendix G.1.4, Figure 14) where the end-to-end SoT and normal latencies are measured directly (not via profiling tables) for the 9 open-source models on Vicuna-80, with 5 runs per test. The actual speed-ups (Figure 14a) range from 0.97× (StableVicuna-13B, negligible) to 2.88× (Vicuna-7B V1.1), with 6 out of 9 models achieving >2× speed-up. These directly measured results are consistent with the analytically estimated results in Figure 2a, validating the profiling methodology.

#### Answer Quality Evaluation Protocol

Since SoT changes the structure and potentially the content of answers, the paper needs a systematic way to compare answer quality between SoT and normal sequential generation. Manual human evaluation is acknowledged as ideal but impractical: "it is easy for a human to tell whether an answer is generated with SoT due to its distinctive pattern, which might cause evaluation bias" (Section 6). Instead, the paper adopts **LLM-as-judge** evaluation using two established frameworks.

**Evaluation frameworks.** Two frameworks are used, with GPT-4 as the primary judge (ChatGPT-3.5 results are reported in Appendix I.4 for comparison):

1. **FastChat** (Zheng et al., 2023): Provides a single metric for "general answer quality." The evaluation prompt presents the question and two answers (one from SoT, one from normal generation) to GPT-4 and asks which is better. Specialized evaluation prompts are available for coding and math questions to enable more accurate assessment.

2. **LLMZoo** (Chen et al., 2023c): Provides five detailed metrics beyond general quality: **coherence** (logical flow), **diversity** (range of perspectives), **immersion** (role-playing authenticity), **integrity** (completeness), and **relevance** (pertinence to the question). LLMZoo does not provide specialized prompts for coding and math, so those categories are excluded from LLMZoo evaluations.

**Order bias mitigation.** A known issue with LLM-as-judge evaluation is that the order in which two answers are presented can bias the judge's preference. The paper implements a simple but effective mitigation: "we extend FastChat and LLMZoo evaluation frameworks by running the evaluation twice with either ordering of the two answers" (Section 3.2).

The scoring rules are:
- For each evaluation run, a score of `+1` is assigned when SoT wins, `0` when it ties, and `-1` when it loses.
- After both orderings are evaluated, the **sum of the two scores** determines the final outcome:
  - Sum > 0 → SoT wins (e.g., win + tie = +1, win + win = +2)
  - Sum = 0 → tie (e.g., win + lose = 0, tie + tie = 0)
  - Sum < 0 → SoT loses

**What this achieves:** if the judge has a systematic bias toward the first or second answer, the two evaluations with swapped orderings will produce opposite preferences, and the sum will cancel out to zero — resulting in a "tie." Only if the judge consistently prefers SoT's answer *regardless of ordering* (or vice versa) will the outcome be a definitive win or loss. This is a principled approach to debiasing without requiring counterbalancing across a large number of judges or questions.

**Net win rate metric.** To provide a single summarized number for quality comparison across many questions, the paper defines:

$$\text{Net Win Rate} = \frac{\#\text{win} - \#\text{lose}}{\text{total number of questions}}$$

where `#win` is the count of questions where SoT won (sum of two-order scores > 0), and `#lose` is the count of questions where SoT lost (sum of two-order scores < 0).

**Interpretation:** A net win rate of 0% means SoT performs competitively to the normal baseline (equal number of wins and losses). Positive values mean SoT is better on net; negative values mean SoT is worse. The net win rate masks the tie rate — two scenarios with the same net win rate could have very different tie proportions (e.g., 60% win, 20% tie, 20% lose gives +40% net win rate, as does 40% win, 60% tie, 0% lose). The paper addresses this by reporting full win/tie/lose breakdowns in figures (Figures 3, 6, 28, 32) before summarizing with net win rates.

**Cross-model and cross-category averaging.** When reporting net win rates per model (Figure 4) or per question category (Figure 5), the paper averages across the complementary dimension. For example, the net win rate for Vicuna-13B V1.3 in Figure 4a is the average across all 80 Vicuna-80 questions for that model. The net win rate for the "knowledge" category in Figure 5a is the average across all 12 models on questions in that category.

**Discrepancy between FastChat and LLMZoo.** The paper notes a persistent discrepancy: "LLMZoo tends to be more optimistic about the quality of SoT than FastChat" (Section 3.2.3). For example, in Figure 3, the overall win rate for SoT vs. normal is 45.8% with FastChat but only 29.5% with LLMZoo's general quality metric (though LLMZoo has a much higher tie rate: 29.3% vs. 19.6%). Despite the absolute value differences, the *rankings* across models and categories are consistent between the two frameworks (Figures 4a vs. 4b, Figures 5a vs. 5b). The paper does not investigate the cause of this discrepancy but reports both metrics transparently.

**Why GPT-4 as judge.** The paper uses GPT-4 (specifically the gpt-4-0613 version) as the primary judge, with ChatGPT-3.5 results relegated to the appendix. This choice aligns with findings from prior work (Li et al., 2023b) showing that "GPT-4-based evaluation usually aligns with human better than ChatGPT-3.5." The paper explicitly notes that readers should "refer to the results in the main paper (with GPT-4 as the judge) for a more accurate view of the performance of SoT" (Appendix I.4).

**Limitations acknowledged.** The paper is candid about evaluation limitations (Section 6): "Our answer quality evaluation is far from perfect due to the limited prompt set, the potential bias of GPT-4 judges, and the inherent difficulty of evaluating LLM generations." The absence of human evaluation is justified by the distinctive pattern of SoT answers making blinding impossible, which would introduce its own bias. This transparency means the quality results should be interpreted as indicative rather than definitive — a limitation the paper shares with much LLM-as-judge evaluation work.

## 4. Key Insights and Innovations

### Innovation 1: Reframing Inference Efficiency from Model/System Optimization to Data-Centric Content Organization

The paper's most fundamental conceptual move is arguing that inference efficiency — and specifically the sequential decoding bottleneck — can be addressed not by changing *how* the model computes (model-level optimization), *where* it computes (system-level optimization), or *how fast* it generates tokens (speculative decoding, non-autoregressive generation), but by changing **what the model is asked to produce**. This is a genuinely distinct axis of optimization that the paper terms "data-centric optimization for efficiency" or "content co-organization for efficiency."

Prior work across three established research communities treated the autoregressive decoding bottleneck as either (a) a hardware utilization problem to be solved by batching and parallelism at the serving-system level, (b) a model architecture problem to be solved by designing efficient attention or non-autoregressive decoders, or (c) a token-level speculation problem to be solved by draft-then-verify pipelines. All three accept as axiomatic that the *content* of a response is a monolithic, sequentially-dependent sequence. The paper questions this axiom directly: if the answer itself can be restructured into independent, parallel-expandable segments, the sequential dependency is **eliminated at the content level** even though token-level generation within each segment remains autoregressive.

This framing matters because it opens an entirely new dimension in the efficiency landscape — one that is orthogonal and potentially composable with all three existing optimization axes. The paper demonstrates this composability concretely by combining SoT with 4-bit quantization (Appendix J), achieving combined speed-ups from 1.54× to 2.07× over unquantized normal generation. The speed-ups from content restructuring and model compression are multiplicative because they attack different bottlenecks: quantization reduces per-token weight-loading latency, while SoT parallelizes across content segments.

The framing also represents a philosophical shift in how we think about LLM capabilities. Rather than treating the autoregressive generation process as an unchangeable constraint imposed by the model architecture, SoT treats it as a *default behavior* that can be overridden through prompting when the task structure permits. The paper's observation that "LLMs [are] able to do that occasionally without special prompting or tuning" (Section 3.2.3, referring to models occasionally falling back to embedding the full answer in the skeleton stage for sequential-reasoning questions) suggests this capability is emergent from instruction tuning rather than explicitly engineered. The paper is essentially proposing that we **elicit a latent planning-and-parallel-execution capability** that instruction-tuned LLMs already possess but that no prior prompt design has attempted to activate for efficiency purposes.

This is a conceptual contribution with significance beyond the specific speed-up numbers. It establishes that the boundary between "how to compute efficiently" and "what to compute" is blurrier for LLMs than for traditional software systems, because the LLM itself can participate in reorganizing computation through its instruction-following and planning capabilities. This insight is likely to grow in importance as LLM capabilities continue to improve — the paper explicitly forecasts this: "data-centric techniques could become more useful in the future" as "LLM capabilities and the amount of LLM-generated data are growing rapidly" (Section 6).

### Innovation 2: Diagnosing and Characterizing the Failure Modes of Parallel Content Generation

While the concept of restructuring content for parallelism is the paper's primary intellectual contribution, its second key insight is empirical: a detailed characterization of **when and why** parallel content generation succeeds or fails, establishing boundary conditions that are more informative than the aggregate speed-up numbers. The paper does not merely report that SoT works on some question types and not others; it provides a systematic analysis that enables readers to predict *a priori* whether SoT would be suitable for a new task.

The diagnostic framework centers on one structural property: **whether the answer's constituent points can be expanded independently without referring to each other's content**. This single criterion cleanly separates the question categories where SoT succeeds (knowledge, generic, common-sense, roleplay, counterfactual — all categories where answers naturally decompose into parallel-expandable aspects) from those where it fails (math, Fermi problems, coding, writing — where sequential dependencies, either logical or stylistic, prevent independent expansion).

The failure mode analysis in Appendix I.1.2 is particularly insightful because it identifies **three distinct failure mechanisms** rather than treating all failures as equivalent:

1. **Sequential dependency failure** (math, Fermi): The answer itself requires step-by-step reasoning where later steps depend on results computed in earlier steps. The skeleton can capture *what* steps are needed, but the point-expanding stage cannot execute them independently because the LLM, when expanding point 3, does not have access to the computed result from point 2. The paper shows concrete examples: ChatGPT-3.5 correctly identifies the skeleton steps for solving a linear equation but makes arithmetic errors when expanding later steps without access to intermediate results from earlier steps. This failure is **fundamental to the approach** — no amount of prompt engineering can eliminate the dependency — and motivates the router-based fallback.

2. **Format violation failure** (coding): The model either (a) generates only a natural language description of the implementation without producing actual code (observed in Claude, likely due to the "write it very shortly" instruction being too aggressively followed), or (b) generates the complete code repeatedly in multiple skeleton points (observed in OpenChat-13B, creating redundant and potentially inconsistent code). These failures are partially **prompt-addressable** — better code-specific prompts could instruct the model to produce code snippets rather than descriptions, and to avoid repeating the full solution — but the paper acknowledges that the coding questions in Vicuna-80 are inherently sequential (variables and imports must be shared across code sections), making parallel expansion structurally inappropriate regardless of prompt quality.

3. **Stylistic coherence failure** (writing): Writing tasks require a coherent passage with introduction, body, and conclusion — a structure that bulleted lists with embedded skeleton headers inherently violate. The paper observes that "simply removing the skeleton points would greatly improve the answer quality" for writing tasks, and suggests future work on "letting the LLM itself decide whether the point index and point skeleton should be included to make the final answer more natural and fluent." This failure is **partially addressable** through post-processing or dynamic formatting, but the fundamental tension between structured parallelism and narrative flow remains.

The paper also identifies an **emergent compensatory behavior**: on some Fermi problems, models embed the full sequential computation into the skeleton stage itself, effectively short-circuiting the point-expanding stage and producing a complete answer in the skeleton. The paper characterizes this not as a failure but as a "promising direction for making SoT a general framework" — if models can learn to recognize when sequential reasoning is needed and adaptively switch to a different generation strategy within the SoT framework, the router might become unnecessary. This observation transforms an apparent limitation into a research direction.

The diagnostic contribution matters because it **converts SoT from a black-box acceleration technique into a predictively deployable tool**. A practitioner reading this paper can determine, before running any experiments, whether their target task is likely to benefit from SoT: does the task's answer decompose into aspects that can be discussed independently? If yes (knowledge Q&A, advice-giving, multi-perspective analysis), SoT is likely suitable. If the answer requires sequential deduction, shared state, or narrative coherence, a router-based fallback or alternative approach is needed. This diagnostic specificity is more valuable than the raw speed-up numbers because it enables principled deployment decisions.

---

### Innovation 3: Exploiting the Prefilling/Decoding Latency Asymmetry Through Content-Level Batching

While the hardware insight that decoding is memory-bound and benefits from batching is not new (it is standard knowledge in LLM serving systems), the paper's contribution is recognizing that this hardware characteristic can be **exploited through prompt engineering alone** — without changes to the serving infrastructure — by restructuring the generation workload at the content level.

The key numbers that motivate this insight are in Table 5 and Figure 10 (Appendix E): for LLaMA-7B on an A100, decoding a single token achieves only 0.31 TFLOPS (0.1% GPU utilization) because weight loading from HBM dominates, while prefilling 128 tokens achieves 43 TFLOPS (13.8% utilization). When decoding as a batch, per-token latency stays nearly constant as batch size increases (Figure 10a: 2,735 ms at B=1, ~3,500 ms at B=9 for LLaMA-7B), while GPU utilization scales roughly linearly (Figure 10b: 0.31→~5 TFLOPS). The peak memory overhead is mild (Figure 10c: LLaMA-7B stays well within 80 GB even at B=9) because model weights dominate memory regardless of batch size.

Prior work exploited this asymmetry through system-level batching: the serving system waits for multiple independent user queries to arrive and processes them together. This improves *throughput* (total queries per second) but does not reduce *latency* for a single user waiting for one response — if you are the only user, there is nothing to batch with.

SoT's innovation is **creating artificial batchability within a single query** by decomposing the response into independent segments. The skeleton stage produces B independent point-expanding requests that can be processed as a batch, converting what would have been 1 long sequential decoding (low GPU utilization, high latency) into B shorter parallel decodings (higher GPU utilization, each with latency proportional to 1/B of the original). The speed-up does not require multiple users, does not require a modified serving system, and does not require a draft model — it requires only that the LLM can follow instructions to restructure its output.

This insight is significant because it **bridges the gap between throughput-oriented system techniques and latency-sensitive single-query scenarios**. The paper explicitly notes this synergy: "SoT can harness the power of these throughput-oriented techniques and make them help with the end-to-end latency, offering a new dimension for better trading off latency and throughput in future serving systems" (Appendix D.1). A serving system that already implements continuous batching could see SoT's parallel point-expanding requests automatically interleaved with other users' requests, further improving overall system utilization while still providing latency benefits to individual SoT users.

The insight also explains **why the router's false negatives (not triggering SoT when it could help) are less harmful than false positives (triggering SoT when it hurts)** — a point reflected in the trained router's asymmetric Tversky loss (α=0.7, β=0.3). A false negative means a missed speed-up opportunity; a false positive means wasted prefilling overhead, redundant computation, and potentially degraded answer quality. This asymmetry would not be obvious without understanding the underlying hardware dynamics: the prefilling overhead of SoT (30-90× more prefilling tokens than normal generation, Tables 6 and 7) means that incorrectly triggering SoT on a question that should be answered sequentially incurs substantial wasted computation with no latency benefit.

### Innovation 4: Establishing That Eliciting Structured Thinking Can Simultaneously Improve Quality and Efficiency — but Only for the Right Question Types

The paper's quality evaluation results contain a finding that is more interesting than the aggregate numbers suggest: SoT **simultaneously improves both answer quality and generation speed** on specific question categories (knowledge, generic, common-sense, roleplay, counterfactual), achieving what appears to be a free lunch. Figure 1 shows multiple models in the upper-right quadrant (speed-up > 1.0, positive net win rate), indicating both faster and better answers compared to normal sequential generation.

The mechanism behind this quality improvement is revealed by the LLMZoo detailed metric analysis (Figure 6): SoT substantially improves **diversity** (99.9% win rate, meaning SoT nearly always wins or ties on diversity) and **relevance** (61.4% win rate), at the cost of some degradation in **immersion** (40.5% win rate) and **coherence** (29.8% win rate). The paper's qualitative analysis (Appendix I.1.3) makes the causal chain explicit: the skeleton stage *forces* the LLM to explicitly consider multiple perspectives before writing detailed content — "The skeleton stage of SoT explicitly require[s] LLMs to discuss the answers from multiple aspects without filler words." This pre-writing planning step produces answers that are more comprehensive (diversity) and more tightly focused on the question (relevance) because the LLM commits to a structure before generating prose.

This is a **double dissociation** from standard prompting assumptions. The prevailing wisdom from Chain-of-Thought (Wei et al., 2022; Kojima et al., 2022) is that *explicitly articulating intermediate reasoning steps* improves quality but increases latency (more tokens generated). SoT inverts this: explicitly articulating *the answer structure* improves both quality and latency by enabling parallel expansion of the structure's components. This suggests that **different types of explicit planning serve different purposes**: step-by-step reasoning helps with logical deduction (quality at the cost of latency), while outline-based structuring helps with comprehensive coverage (quality and latency simultaneously when parallelizable).

The paper is careful not to overclaim: the quality improvements are not universal. On writing tasks, the bulleted-list format imposed by SoT degrades immersion and coherence — the answer reads like an outline, not a passage. On models with already-strong normal generation (Claude, ChatGPT-3.5), the quality margin is smaller or negative because the baseline is already high. The paper characterizes this honestly: "For models that are able to understand the SoT prompts and the normal answers are not good enough, SoT can improve the answer quality" (Appendix I.1.1).

The significance of this finding extends beyond SoT itself. It suggests a broader principle: **structured planning prompts can serve dual purposes — efficiency through parallelization and quality through enforced comprehensiveness — but only when the task's output structure matches the planning structure**. This principle could inform prompt design even in non-parallel settings: if you want a comprehensive, multi-perspective answer, forcing the model to outline first (even if you then generate sequentially) might improve diversity and relevance. The paper opens this direction explicitly in Section 6: "it is interesting to explore how the SoT answers can be used to fine-tune LLMs to generate more structured answers in a self-improving way," and in Appendix D.2: the "large literature on prompting methods has been aiming at uncovering different capabilities of LLM and improving the answer quality on different downstream tasks. In contrast, SoT is a first attempt at exploiting the power of prompting to improve efficiency." The quality co-benefit suggests these two goals — quality and efficiency — may not always be in tension.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The primary evaluation uses **Vicuna-80** (Chiang et al., 2023), a set of 80 questions spanning nine categories: coding, math, fermi, roleplay, writing, knowledge, generic, counterfactual, and common-sense. A secondary dataset, **WizardLM** (Xu et al., 2023) with 218 questions across 29 categories of diverse difficulty, is used for router evaluation and reported in appendices. Both datasets are recent assistant-style benchmarks designed to test instruction-following LLMs in multi-turn conversational settings.

- **Base model(s).** Twelve models are evaluated: 9 open-source (LLaMA2-Chat-7B, LLaMA2-Chat-13B, OpenChat-13B, Vicuna-7B V1.3, Vicuna-13B V1.3, Vicuna-33B V1.3, StableVicuna-13B, UltraLM-13B, Vicuna-7B V1.1) and 3 API-based (Claude, ChatGPT-3.5, GPT-4). All open-source models are fine-tuned from LLaMA architectures (7B, 13B, or 33B parameters). The range spans weak-to-strong instruction followers, enabling analysis of how model capability affects SoT's success. Complete model sources and release dates are cataloged in Tables 1 and 2 (Appendices A).

- **Metrics.** Two metrics are tracked: (1) **Speed-up**: the ratio of normal sequential generation latency to SoT generation latency. For open-source models, latency is estimated analytically from GPU profiling tables (Appendix F); for API-based models, it is measured via wall-clock `time.time()` calls. Speed-up > 1.0 means SoT is faster. (2) **Answer quality**: evaluated using LLM-as-judge frameworks (FastChat and LLMZoo) with GPT-4 as the primary judge. The key summary metric is **net win rate** = (#win − #lose) / total questions, where each question is evaluated twice with answer orderings swapped, and a final verdict (win/tie/lose) is determined by the sum of the two scores (+1/0/−1 per evaluation). Positive net win rates indicate SoT answers are preferred over normal generation on net.

- **Baselines.** The primary baseline is **normal sequential generation**: the LLM receives the user question directly (without skeleton or point-expanding prompts) and generates the full answer autoregressively. For the SoT-R extension, two router variants are compared: a **prompting router** (GPT-4 queried with a structured classification prompt, no training needed) and a **trained router** (a fine-tuned RoBERTa-base model with 120M parameters, trained on human-annotated LIMA data). A **human router** (manual annotation by paper authors) serves as an upper-bound benchmark. For quality evaluation, answers from SoT are compared head-to-head against normal generation answers.

- **Generation budget / compute accounting.** The paper does not use a generation budget in the conventional sense (no search over number of samples). SoT's "compute" is measured in **wall-clock latency** (milliseconds), not FLOPs or token counts. For fair comparison, both SoT and normal generation receive the same question and their end-to-end response latencies are compared directly. The paper acknowledges that SoT increases total token consumption (prefilling overhead is 30–90× higher than normal generation; Tables 6 and 7) and notes this tradeoff explicitly. For API-based models, the cost model includes both latency and the increased number of API calls.

- **Cross-validation / statistical protocol.** No cross-validation or statistical significance testing is applied. For the trained router, the LIMA dataset (1,030 questions, 371 suitable for SoT) is used for training; Vicuna-80 and WizardLM are held-out evaluation sets. Router consistency is evaluated via confusion matrices (Tables 3 and 4) comparing human, GPT-4, and RoBERTa router decisions. Latency measurements on open-source models use geometric means over 3–7 repeated runs with warmup iterations discarded (Appendix F). Quality evaluation uses the two-ordering swap protocol described above to mitigate position bias in LLM-as-judge evaluation.

### Main Quantitative Results

#### Speed-Up Results: SoT Achieves >2× Speed-Up on Most Models

The headline efficiency result appears in Figure 2a: across all 12 models averaged over all 9 question categories on Vicuna-80, SoT achieves speed-ups ranging from 1.13× (StableVicuna-13B) to 2.39× (LLaMA2-Chat-7B). Eight out of 12 models achieve >2× speed-up. The speed-up ranking across models is:

- **Highest**: LLaMA2-Chat-7B (2.39×), LLaMA2-Chat-13B (2.38×), Vicuna-7B V1.1 (2.30×)
- **Moderate**: OpenChat-13B (2.28×), Vicuna-33B V1.3 (2.24×), UltraLM-13B (2.18×), Vicuna-7B V1.3 (2.01×), GPT-4 (2.00×)
- **Lower**: ChatGPT-3.5 (1.97×), Vicuna-13B V1.3 (1.91×), Claude (1.31×)
- **Lowest**: StableVicuna-13B (1.13×)

The paper attributes StableVicuna-13B's poor speed-up to its failure to follow the "Write it **very shortly**" instruction in the point-expanding prompt: "StableVicuna-13B's longest point-expanding responses for many question categories can be as lengthy as the overall normal answer" (Section 3.1.1), negating the parallelism benefit because the batch decoding time is dominated by the longest point. Figure 11d quantifies this: StableVicuna-13B's maximum point-expanding response length ratio (relative to normal answer length) averages 0.9 across categories, meaning its longest point is nearly the full length of a normal answer. In contrast, API-based models (ChatGPT-3.5, Claude, GPT-4) achieve ratios of 0.1–0.2 — their point expansions are genuinely short.

Figure 2b shows speed-ups broken down by question category (averaged across all models). The five categories for which SoT provides high-quality answers (marked in green) achieve speed-ups of 1.89× to 2.33×: knowledge (2.33×), generic (2.31×), common-sense (2.26×), writing (2.24×), roleplay (1.95×), counterfactual (1.89×). Categories where SoT is not suitable for quality reasons (marked in red) still achieve speed-ups: coding (2.06×), fermi (1.69×), math (1.34×). The fact that unsuitable categories still show speed-ups reflects that the SoT pipeline executes regardless of output quality — the speed-up metric is purely about latency, not correctness.

The latency breakdown in Figure 12 (Appendix G.1.2) reveals why speed-ups materialize: across all models, the decoding phase dominates total latency (typically 80–95% of end-to-end time). In SoT, the batched point-expanding decoding processes B shorter segments simultaneously rather than one long segment sequentially. For Vicuna-33B V1.3 (Figure 12a), normal generation decoding takes ~35,000 ms; SoT's skeleton decoding takes ~4,000 ms and the batched point-expanding decoding takes ~7,000 ms, totaling ~13,000 ms — the ~2.8× speed-up comes from replacing one 35-second sequential decode with 7 seconds of batched parallel decodes (plus skeleton overhead).

Figure 11 provides detailed statistics explaining model-level speed-up variation:
- **Number of points** (Figure 11a): averages range from 4.4 (LLaMA2-Chat-7B on some categories) to 9.7 (StableVicuna-13B, GPT-4). More points generally enable higher potential speed-up but also increase prefilling overhead.
- **Maximum point-expanding response length** (Figure 11c): API-based models produce much shorter point expansions (48–67 tokens on average for GPT-4) compared to open-source models (100–216 tokens). Shorter per-point responses mean less decoding time per batch element.
- **Length imbalance** (Figure 11e): The standard deviation of point token lengths varies widely — from ~6.5 tokens for GPT-4 to ~64.7 tokens for StableVicuna-13B. Higher imbalance reduces speed-up because the batch decoding time is determined by the longest point.
- **Overall SoT answer length ratio** (Figure 11f): SoT answers are on average 1–2× longer than normal answers (ranging from 0.5× for ChatGPT-3.5 to 6.8× for StableVicuna-13B). Surprisingly, this length increase does not negate speed-up because the parallel decoding of shorter segments outweighs the total token increase.

Actual measured latencies (not profiling-based estimates) are reported in Figure 14 (Appendix G.1.4) for the 9 open-source models with 5 runs each. The directly measured speed-ups confirm the profiling-based estimates: Vicuna-7B V1.1 achieves 2.88×, Vicuna-7B V1.3 achieves 2.82×, UltraLM-13B achieves 2.75×, LLaMA2-Chat-7B achieves 2.20×, Vicuna-13B V1.3 achieves 2.19×, and LLaMA2-Chat-13B achieves 2.14×. OpenChat-13B and Vicuna-33B V1.3 achieve 1.97× and 1.75× respectively. StableVicuna-13B achieves only 0.97× — essentially no speed-up.

#### Quality Results: SoT Maintains or Improves Quality on Decomposable Questions

Figure 3 presents the overall win/tie/lose rates of SoT vs. normal generation across all models and all 80 Vicuna-80 questions, using the general quality metrics from FastChat and LLMZoo with GPT-4 as judge. The headline: **SoT is not worse than normal generation in ~60% of cases** (45.8% win + 19.6% tie = 65.4% for FastChat; 29.5% win + 29.3% tie = 58.8% for LLMZoo). The win rates are close to the lose rates (34.5% lose for FastChat, 41.2% for LLMZoo), suggesting SoT is roughly competitive with normal generation in aggregate.

However, the aggregate masks substantial variation across models (Figure 4):

**High net win rate models (SoT quality improvement):**
- StableVicuna-13B: ~12% net win rate (FastChat), ~50% (LLMZoo)
- UltraLM-13B: ~8% (FastChat), ~30% (LLMZoo)
- Vicuna-13B V1.3: ~8% (FastChat), ~20% (LLMZoo)
- GPT-4: ~2% (FastChat), ~5% (LLMZoo)

**Low net win rate models (SoT quality degradation):**
- Claude: ~-7% (FastChat), ~-12% (LLMZoo)
- Vicuna-7B V1.1: ~-5% (FastChat), ~-12% (LLMZoo)
- OpenChat-13B: ~-3% (FastChat), ~-18% (LLMZoo)

The paper's qualitative analysis (Appendix I.1.1) diagnoses two distinct causes for low net win rates: (1) **Weak instruction following**: OpenChat-13B and Vicuna-7B V1.1 sometimes fail to follow the skeleton format (e.g., writing full paragraphs instead of short skeleton points, or producing empty point expansions when details are needed). (2) **Strong baseline**: Claude's normal generation is already high-quality, leaving little room for SoT to demonstrate improvement. The high-net-win-rate models occupy a "sweet spot": capable enough to follow SoT instructions, but with normal generation quality that has room for improvement.

Quality variation across question categories (Figure 5) reveals the core conditional pattern:

**Categories where SoT improves quality (positive net win rates, FastChat):**
- Counterfactual: ~20%
- Generic: ~15%
- Common-sense: ~8%
- Knowledge: ~5%
- Roleplay: ~2%

**Categories where SoT degrades quality (negative net win rates, FastChat):**
- Fermi: ~-20%
- Writing: ~-25%
- Math: ~-45%
- Coding: ~-65%

The paper's qualitative analysis (Appendix I.1.2) provides detailed explanations for each failure category. **Math**: the skeleton can capture step labels but the point-expanding stage cannot execute them independently because later steps need intermediate results from earlier steps. Example: ChatGPT-3.5 correctly identifies five skeleton steps for solving a linear equation (move x terms, move constants, simplify, divide, check) but makes arithmetic errors in step 2 because it doesn't know the result of step 1. **Fermi**: similar sequential dependency — estimating "number of Earth orbits since life began" requires the age of Earth and the timing of life's origin, but expanding these points independently leads to inconsistent assumptions (the model uses 3.5 billion years in one point and 4.54 billion in another). **Coding**: the model either generates only descriptions without code (Claude, following "write very shortly" too aggressively) or generates the complete program redundantly in multiple points (OpenChat-13B). **Writing**: the bulleted-list format with embedded skeleton headers is stylistically inappropriate for passages, emails, and scripts that require narrative flow.

#### Detailed Metric Analysis: SoT Improves Diversity and Relevance, Degrades Coherence and Immersion

Figure 6 (LLMZoo metrics, GPT-4 judge) decomposes quality into five dimensions, revealing a consistent tradeoff:

- **Diversity** (99.9% win rate): SoT nearly always wins or ties. The skeleton stage explicitly requires discussing multiple aspects without filler words, producing more comprehensive answers.
- **Relevance** (61.4% win rate): SoT's answers are more tightly focused on the question because each skeleton point constrains what the LLM discusses.
- **Integrity** (23.2% win rate): SoT answers are roughly comparable to normal on completeness.
- **Coherence** (29.8% win rate): SoT degrades logical flow because answers are formatted as discrete bullet points rather than connected prose. Transition sentences and introductory/concluding paragraphs are usually missing.
- **Immersion** (40.5% win rate): For roleplay tasks where the LLM should embody a character (e.g., "pretend to be a medieval knight"), the bulleted-list format reads stiffly and breaks character immersion.

The paper provides concrete examples for each metric (Appendix I.1.3). For diversity: on "How can you determine if a person is genuinely interested in a conversation?", SoT's answer covers five aspects (body language, engaged responses, eye contact, follow-up questions, tone of voice) while normal generation only mentions one generic tip ("maintain eye contact, lean in, nod"). For coherence: on a YouTube script about jazz history, SoT's answer is a flat list of 11 historical points with no introduction, transitions, or conclusion, while normal generation provides a script with "Hey everyone!" opening, smooth chronological transitions, and a call-to-action closing.

#### SoT-R Results: Router Enables Graceful Degradation on Unsuitable Questions

Figure 7 presents the speed-up comparison between vanilla SoT and SoT-R with both router variants on Vicuna-80. The key finding: **SoT-R reduces speed-up compared to SoT** (as expected, since some questions fall back to normal generation with no speed-up), but **maintains >1× speed-up for most models**. For example, with the trained router, LLaMA2-Chat-7B drops from 2.39× (SoT) to 1.69× (SoT-R); Vicuna-7B V1.1 drops from 2.30× to 1.59×. The trained router achieves slightly higher speed-ups than the prompting router for 7 out of 12 models on Vicuna-80.

Figure 8 shows the quality impact of SoT-R across question categories (FastChat metric, GPT-4 judge, averaged across all models). For categories where SoT originally performed poorly:

- **Coding**: net win rate improves from ~-65% (SoT) to ~-10% (SoT-R with either router)
- **Math**: improves from ~-45% to ~-10%
- **Writing**: improves from ~-25% to ~5%
- **Fermi**: improves from ~-20% to ~10%

For categories where SoT already performed well (counterfactual, generic, knowledge, roleplay, common-sense), SoT-R maintains positive or near-neutral net win rates. This confirms that the router successfully identifies unsuitable questions and falls back to normal generation, preventing quality degradation without sacrificing benefits on suitable questions.

Notably, the **trained router sometimes surpasses the human router**: on roleplay questions (Figure 8), the trained router achieves a higher net win rate than the human router. The paper interprets this as the trained router being "dedicated to this task" (Appendix I.2) and potentially more consistent than human judgment across ambiguous cases.

Figure 9 and the confusion matrices in Tables 3 and 4 (Appendix C.3) provide router consistency analysis. On Vicuna-80 (Table 3), the three routers show strong agreement: the GPT-4 router agrees with human annotations on 75/80 questions (94% agreement), and the trained router agrees on 69/80 (86% agreement). On WizardLM (Table 4), the GPT-4 router produces many false positives (66 questions classified as suitable that humans considered unsuitable), while the trained router aligns more closely with human annotations (135 true negatives + 27 true positives). The paper attributes this to "the intricate answer structure and the presence of many ambiguous cases" in WizardLM that challenge GPT-4's classification.

### Ablation Studies and Robustness Checks

**Skeleton prompt design: two-shot demonstrations are necessary for non-GPT-4 models.** The paper compares Prompt 1 (no demonstrations) and Prompt 3 (with two-shot demonstrations). GPT-4 works well without demonstrations, but "for all other models, the two demonstrations are included" (Appendix B.1). No ablation table is provided; this is stated as a design experience rather than a quantified result. The demonstrations serve as in-context examples of the desired output format for weaker instruction-followers.

**Point-expanding instruction: "very shortly" removed for Claude and GPT-4.** The paper finds that Claude and GPT-4 follow the 1–2 sentence instruction "very well, so that the answers are very short" — too short, lacking sufficient detail. The instruction is softened for these models by removing "**very shortly**," effectively asking them to "Write it in 1∼2 sentence" (Appendix B.1). This is a qualitative design choice without a comparative ablation table.

**Conversation template handling across models.** Different open-source models use different string delimiters for user/assistant messages (Vicuna: "USER:" / "ASSISTANT:", UltraLM: "User:" / "</s>Assistant:"). The paper implements these via FastChat's conversation template system and adds custom templates for OpenChat-13B, StableVicuna-13B, and UltraLM-13B according to their official guides (Appendix B.1). No ablation is provided, but this implicitly tests robustness to prompt formatting variations.

**Partial answer mechanism: effective across models with minor failures.** The paper uses a partial answer (appending `1.` to the skeleton prompt and `{point index}. {point skeleton}` to the point-expanding prompt) to encourage format compliance. This works for most models but "in some rare cases, ChatGPT-3.5 repeats the provided partial answers" (Appendix B.1). For Claude (Slack API, which lacks a standard way to provide partial assistant responses), the prompt is modified to include "Please start your answer from `{partial answer}`" — Claude "understands and obeys it well."

**Router design: Tversky loss with asymmetric penalties reduces false positives.** The trained router uses Tversky loss with α = 0.7 and β = 0.3, penalizing false positives (triggering SoT when it shouldn't be) more heavily than false negatives (missing a SoT opportunity). Label smoothing (ε = 0.2) is also applied. The ablation is implicit in the design choice: the paper states this reflects the deployment priority that "false positives... are of more significant concern than false negatives" (Appendix C.2.2). No comparison to standard cross-entropy loss is provided.

**Latency estimation validation: profiling-based estimates match actual measurements.** Figure 14 (Appendix G.1.4) reports directly measured end-to-end latencies for all 9 open-source models on Vicuna-80, with 5 repeated runs per model. The measured speed-ups (Figure 14a) are consistent with the profiling-based estimates (Figure 2a): e.g., Vicuna-7B V1.1 achieves 2.88× measured vs. 2.30× estimated; LLaMA2-Chat-7B achieves 2.20× measured vs. 2.39× estimated. The agreement validates the profiling methodology.

**ChatGPT-3.5 as judge: similar rankings but more optimistic absolute values.** Appendix I.4 replicates the entire quality evaluation using ChatGPT-3.5 instead of GPT-4 as the judge. The key finding: "the takeaway messages from ChatGPT-3.5 are similar to the ones from GPT-4" — the same models and categories rank similarly — but absolute net win rates are shifted. For example, using FastChat with ChatGPT-3.5 (Figure 29a), the overall win rate for SoT is 50.2% vs. 45.8% with GPT-4 (Figure 3). Using LLMZoo with ChatGPT-3.5 (Figure 29b), the win rate is 12.4% vs. 29.5% with GPT-4. The paper explicitly recommends readers "refer to the results in the main paper (with GPT-4 as the judge) for a more accurate view" given prior evidence that GPT-4 aligns better with human evaluation (Li et al., 2023b).

**Multi-round conversation: SoT does not compound prefilling overhead across turns.** Appendix B.2 describes that when SoT is used in one conversation round, only the final aggregated answer is stored in history — not the intermediate SoT prompts. This means "using SoT in one conversation round will not introduce additional prefill cost in future rounds." No quantitative ablation is provided, but this design choice is motivated by the prefilling overhead concern.

**Hardware robustness: SoT achieves speed-ups on both A100 and RTX 3090.** Figure 13 (Appendix G.1.3) reports SoT speed-ups on three 7B models running on an NVIDIA RTX 3090 (a consumer GPU with 24 GB memory). Speed-ups range from 1.94× (Vicuna-7B V1.3) to 2.40× (LLaMA2-Chat-7B), demonstrating that SoT's benefits are not specific to datacenter GPUs. The five suitable categories achieve 1.96× to 2.52× speed-up on RTX 3090.

**Quantization composability: SoT-R combined with GPTQ 4-bit quantization achieves multiplicative speed-ups.** Appendix J evaluates SoT-R on quantized models (GPTQ 4-bit weight-only quantization; Frantar et al., 2022). Figure 33 shows SoT-R speed-ups on quantized models ranging from 1.08× (UltraLM-13B) to 1.99× (LLaMA2-Chat-13B) compared to quantized normal generation. Figure 35 shows the combined speed-up of quantized SoT-R vs. unquantized normal generation: 1.54× to 2.07× across models. This demonstrates orthogonality between model-level (quantization) and data-level (SoT) optimization. The suitable categories achieve 1.33× to 3.41× combined speed-up on RTX 3090 (Figure 36).

**Peak memory overhead: minimal across models and categories.** Figures 38 and 39 (Appendix K.2) report peak memory overhead of SoT-R compared to normal generation. In the prefilling phase, overhead is 1.02–1.03× across models; in the decoding phase, 1.04–1.07×. Across question categories, decoding memory overhead ranges from 1.00× (math, coding — SoT not triggered) to 1.11× (generic). The paper notes this is "quite small" and that "in all of our experiments, we managed to use one GPU to run SoT without seeking help from other peak memory optimization techniques" (Appendix E).

**Speed-up vs. number of points: not monotonic.** Figure 40 (Appendix K.3) plots speed-up against the number of skeleton points for three representative models (LLaMA2-Chat-7B, UltraLM-13B, GPT-4). There is no clear monotonic relationship — more points do not necessarily yield higher speed-up — because the overall answer length and point length balance also affect parallelism efficiency.

### Critical Assessment

**Claim: "SoT provides considerable speed-ups (up to 2.39×) across 12 LLMs."**

This claim is well-supported by both profiling-based estimates (Figures 2a, 7) and direct measurements (Figure 14). The 2.39× ceiling is consistent across methodologies. However, three important qualifications emerge from the data: (1) The speed-up is **model-dependent** in ways that are not fully predictable — StableVicuna-13B achieves only 1.13× (estimated) or 0.97× (measured), essentially no benefit. The paper attributes this to instruction-following failure, but this means that **a practitioner cannot assume SoT will accelerate any given model without testing**. (2) The speed-up varies substantially across **question categories** even for a single model, from 0.90× (SoT-R on math with prompting router, Figure 18a) to 2.26× (SoT-R on generic with trained router, Figure 18b). (3) The speed-up numbers **do not include the router latency** for SoT-R comparisons (router latency is reported separately in Appendix G.2: 0.04–0.65 seconds, which is negligible compared to multi-second generation latencies but non-zero).

A more subtle concern: the speed-up metric is latency reduction for a **single isolated query**. In a production serving system handling multiple concurrent users, the batching that SoT creates internally (multiple point-expanding requests) might compete with the system's own query batching. The paper acknowledges this (Section 6, Appendix H) but does not evaluate it. The discussion notes that when "there is a saturated number of concurrent queries, SoT is still useful for improving answer quality" but "it is important to consider the computation overhead from SoT." This means the reported speed-ups should be interpreted as **single-query latency improvements** — they may not translate to throughput improvements in high-load serving scenarios.

**Claim: "SoT can also potentially improve the answer quality on several question categories."**

This claim is supported with extensive LLM-judge evaluation (Figures 3–6, 8, 22–32), but there are fundamental limitations to how "quality" is measured that constrain the strength of this claim:

**(1) No human evaluation.** The paper explicitly states: "Currently, we did not conduct human evaluation since it is easy for a human to tell whether an answer is generated with SoT due to its distinctive pattern, which might cause evaluation bias" (Section 6). This is a legitimate concern — SoT answers are visibly formatted as numbered lists with skeleton headers, making blinding impossible — but it means all quality claims are mediated through GPT-4's preferences, which may not align with human preferences. The paper acknowledges this limitation honestly.

**(2) Position bias mitigation may be incomplete.** The two-ordering swap protocol (Section 3.2) cancels out systematic position bias (always preferring first or second answer), but it does not address other forms of LLM-judge bias such as **length bias** (GPT-4 may prefer longer answers) or **format bias** (GPT-4 may prefer structured, bulleted answers regardless of content). Appendix I.3 provides a partial check on length bias by comparing SoT against a "longer normal answer" (normal generation with added "give a long answer" instruction). When answer lengths are matched, quality is comparable (Figure 26), suggesting length bias alone does not explain SoT's quality results.

**(3) The "win rate" metric collapses important nuance.** A net win rate of 0% could mean SoT wins 40%, ties 20%, and loses 40% — or wins 0%, ties 100%, loses 0%. The paper reports full win/tie/lose breakdowns in bar charts (Figures 3, 6), but the headline net win rate numbers (Figures 4, 5, 8) discard tie information. For question categories with high tie rates (e.g., LLMZoo immersion: 42.1% tie rate in Figure 6), the net win rate overstates the practical difference between SoT and normal generation.

**(4) The "diversity" and "relevance" quality improvements may be artifacts of the evaluation framework.** The near-100% diversity win rate (99.9% in Figure 6) is so extreme that it raises suspicion: is SoT genuinely producing dramatically more diverse content, or is GPT-4 simply rewarding the format (list of labeled points) when asked to evaluate "diversity"? The LLMZoo prompt defines diversity as "The response should be comprehensive and provide a range of information that is not limited to a single perspective." A bulleted list with 5–10 labeled perspectives is structurally more diverse than a prose paragraph — even if the prose paragraph covers the same content. The paper does not control for this format confound.

**(5) The quality improvements are conditional on model capability.** The models with highest net win rates (StableVicuna-13B, UltraLM-13B, Vicuna-13B V1.3) are those where "normal sequential generation performance has a larger room for improvement" (Appendix I.1.1). For the strongest models (Claude, ChatGPT-3.5), SoT often degrades quality or is neutral. This suggests SoT's quality benefit is primarily **compensating for weaker normal generation** rather than providing an absolute improvement — it helps weaker models organize their thoughts, but for already-capable models, the format constraints may hinder more than they help.

**Claim: "SoT-R can adaptively trigger SoT only for suitable questions."**

This claim is supported by the quality improvements on unsuitable categories when the router is introduced (Figure 8) and the router consistency analysis (Tables 3, 4). However, the evaluation has several weaknesses:

**(1) The "human router" is an upper bound constructed by the paper's authors, not an independently validated ground truth.** The fact that the trained router sometimes surpasses the human router (Figure 8, roleplay) could indicate either that (a) the trained router is genuinely better at the task, or (b) the human annotations are noisy or inconsistent. Without an external quality benchmark, it is impossible to distinguish these explanations. Two authors independently annotating and discussing disagreements (Appendix C.2.1) is a reasonable process, but the resulting labels may still reflect shared assumptions or biases about what makes a question "suitable" for SoT.

**(2) The router is trained on LIMA (1,030 questions, 371 suitable) and evaluated on Vicuna-80 (80 questions) and WizardLM (218 questions).** These are small datasets by classification standards, and the trained router's performance may not generalize to substantially different question distributions. The confusion matrices (Tables 3 and 4) show that on WizardLM, the GPT-4 router produces many false positives (66 out of 218 questions), suggesting the classification boundary is sensitive to the question distribution.

**(3) The router introduces a deployment dependency on either GPT-4 API access (prompting router) or a fine-tuned classification model (trained router).** The paper positions SoT as a method requiring "no model modification," but SoT-R with the trained router does require training a separate model — albeit a lightweight one (120M parameters, 2 minutes on one A100). This is a small cost, but it means the claim of "no training needed" applies only to the vanilla SoT, not to the practical SoT-R deployment.

**Missing experiments that would strengthen the paper:**

- **Human evaluation** on a subset of questions, even if not fully blinded (e.g., blind evaluation of answer *content* by presenting SoT answers with skeleton headers removed).
- **Comparison to other prompting strategies** that also encourage structured answers (e.g., "list your answer as bullet points" without the skeleton stage) — this would isolate whether the quality improvement comes from the two-stage skeleton-then-expand structure or simply from encouraging bulleted output.
- **Throughput evaluation in a multi-user serving scenario** — the paper acknowledges this as future work but presents no data, leaving the practical applicability in high-load settings unverified.
- **Quality evaluation on the questions where SoT *actually* provides speed-up** — the paper reports quality across all questions, but a practitioner only cares about quality on questions that trigger SoT. The SoT-R quality results partially address this.
- **Analysis of how skeleton quality affects downstream point-expanding quality** — if the skeleton is poor (missing key points, incorrectly scoped), can the point-expanding stage recover? The paper shows examples of skeleton failures but doesn't quantify their frequency or impact.

**Overall assessment:** The experiments convincingly demonstrate that SoT reduces single-query end-to-end latency for a wide range of models and question types, with the speed-up magnitude depending on model instruction-following ability and question decomposability. The quality results establish that SoT does not catastrophically degrade answer quality on decomposable questions, and may improve it on some dimensions (diversity, relevance) at the cost of others (coherence, immersion). The router extension is a necessary practical addition that recovers performance on unsuitable question types. The paper's strengths are its breadth (12 models) and detailed qualitative analysis of failure modes; its main weaknesses are the absence of human evaluation, the reliance on a single LLM-judge framework for quality claims, and the lack of multi-user throughput evaluation to complement the single-query latency results.

## 6. Limitations and Trade-offs

### Limitation 1: Difficulty Estimation Cost Dominates the Headline Efficiency Gains

**The assumption or constraint.** The compute-optimal scaling policy depends entirely on estimating a prompt's difficulty *before* allocating the test-time compute budget. The paper's method for doing so — generating 2048 samples per question and either checking correctness against ground truth (oracle) or averaging the PRM's final-answer scores (predicted) — is prohibitively expensive. The paper states this explicitly in Section 3.2:

> "estimating difficulty in this way still incurs additional computation cost during inference... our experiments do not account for this cost largely for simplicity"

Generating and scoring 2048 samples per question consumes more compute than the largest test-time budgets studied (256–512 generations), meaning the difficulty estimation step alone would dominate the total inference cost in any deployment. The reported 4× efficiency gains over best-of-N are computed *after* difficulty is known, without amortizing the cost of learning it.

**The consequence.** The central claim of the paper — that compute-optimal test-time scaling achieves >4× better efficiency than best-of-N — is an **upper bound** that assumes difficulty labels are available for free. In a realistic deployment, the total cost would be difficulty estimation (2048 generations) plus the selected strategy (16–256 generations), and the former would dwarf the latter. Until a cheap difficulty estimator is demonstrated, the practical efficiency gain relative to a baseline that spends the same total budget (including difficulty estimation) is unknown and likely substantially smaller than 4×.

**What evidence exists in the paper.** The cost of difficulty estimation is acknowledged but never measured or included in any budget calculation. Figures 4 and 8 (compute-optimal search and revision scaling curves) plot accuracy vs. generation budget with difficulty bins assumed known, without adding the 2048 samples used to estimate those bins. The fact that predicted (PRM-based) difficulty bins track oracle bins closely (the curves "largely overlap" per Section 5.3 and Figure 4) demonstrates that difficulty *can* be estimated without ground-truth labels, but does not address the *cost* of that estimation.

**Mitigation status.** Not addressed. The paper flags "developing a much cheaper method to estimate question difficulty" as "critical" future work (Section 8) and suggests possibilities — training a lightweight classifier, using the PRM score distribution from a small number of initial samples, or adaptive difficulty estimation — but none are implemented or evaluated. The paper frames the difficulty estimation cost as an "exploration vs. exploitation tradeoff" (Section 3.2) but provides no analysis of how to balance it.

---

### Limitation 2: The Method Provides No Benefit on the Hardest Problems

**The assumption or constraint.** Test-time compute can amplify existing capability but **cannot create it**. The paper's framework assumes the base model has a non-trivial probability of producing correct answers — i.e., that there are correct solutions somewhere in the model's output distribution to be found (via search) or refined (via revisions). On problems where the base model's pass@1 is near zero, no amount of test-time compute helps.

**The consequence.** For the hardest difficulty quintile (bin 5 in the paper's taxonomy), **all methods — search, revisions, and their compute-optimal combinations — fail to produce meaningful improvements** regardless of budget. In Figure 3 (right), bin 5 accuracy hovers at 1–3% for all methods and all budgets (4–256 generations). In Figure 7 (right), bin 5 shows roughly 2–3% accuracy irrespective of the sequential-to-parallel ratio at 128 generations. In the FLOPs-matched comparison (Figure 9), the bin 5 scaling line is essentially flat near 0–5%, well below the ~14× larger model's performance at all values of the inference-to-pretraining ratio R. The paper states this boundary clearly in the Section 7 takeaway:

> "test-time compute cannot compensate for the ability gap required to solve hard problems"

The practical implication is that for users or applications whose query distribution skews toward genuinely hard problems, the compute-optimal framework offers no improvement — the compute would be better spent on pretraining a larger model. This is not a failure of the method but a fundamental constraint, and it limits the applicability to domains where the base model already possesses the necessary knowledge and reasoning primitives.

**What evidence exists in the paper.** Every difficulty-bin analysis (Figures 3 right, 7 right, and the FLOPs-matched comparison in Figure 9) shows bin 5 near zero and flat across all budgets and strategies. The consistence across search methods, revision strategies, and selection mechanisms makes this one of the most robust findings in the paper.

**Mitigation status.** Not addressed, and the paper is candid that this is not a solvable problem within the test-time compute paradigm. The only path to improving hard-problem performance is scaling pretraining. The paper's contribution is precisely characterizing *where* the boundary lies, enabling practitioners to make informed allocation decisions.

---

### Limitation 3: Verifier Over-Optimization Imposes a Hard Ceiling on Search-Based Scaling

**The assumption or constraint.** All search methods rely on the process reward model (PRM) to score partial or complete solutions and guide the search toward correct answers. The PRM is an imperfect proxy — it is trained on base-model outputs and can be exploited by aggressive search algorithms that find solutions scoring highly under the PRM but actually incorrect.

**The consequence.** The paper identifies **verifier over-optimization as the primary bottleneck** preventing unbounded improvements from additional test-time compute. The evidence is concrete and striking:

- On easy questions (bin 1, Figure 3 right), beam search *degrades* accuracy at high budgets (from ~78% at 4 generations to ~77% at 256 generations), while best-of-N continues to improve (68% → 88%). This is interpreted as beam search finding solutions that exploit flaws in the PRM's scoring on problems where the PRM is otherwise reliable.

- Lookahead search — the most powerful optimization method (it uses k-step rollouts to improve step-level scoring) — paradoxically *underperforms all other methods* at the same generation budget (Figure 3 left). Its extra per-step cost reduces the number of beams explored, and the more powerful optimization amplifies PRM exploitation rather than improving accuracy.

- Qualitative examples in Appendix M show degenerate outputs from search: repetitive low-information steps at the end of solutions, overly short 1–2 step "solutions" that score highly under the PRM because the first step looks plausible.

The compute-optimal policy *mitigates* this by routing easy problems to best-of-N (weaker optimization, less exploitation) and reserving beam search only for medium-difficulty problems where the PRM signal provides genuine guidance. But it does not solve the underlying problem — on medium problems where beam search is deployed, over-optimization still limits the scaling ceiling. The beam search curves in Figure 3 flatten and sometimes begin declining before the maximum budget is exhausted.

**What evidence exists in the paper.** Figure 3 (right) shows the difficulty-dependent over-optimization pattern clearly. Figure 3 (left) shows lookahead search's consistent underperformance. The qualitative examples in Appendix M (Figures 29 and surrounding) document specific failure modes. Section 5.3 explicitly discusses over-optimization: "search finds solutions that score highly under the PRM but are actually incorrect."

**Mitigation status.** Partially addressed through the compute-optimal policy (routing easy problems away from aggressive search), but not fundamentally solved. The paper frames improving verifier robustness as the key research priority: "verifier quality is the key bottleneck for further scaling test-time compute" (Section 8). Potential mitigation directions — adversarial PRM training, ensemble verification, KL-penalized search — are suggested but not explored.

---

### Limitation 4: Single Benchmark and Single Model Family

**The assumption or constraint.** All experiments use the MATH benchmark (500 test questions, competition-level high-school math) with PaLM 2-S* as the base model (and its ~14× larger variant for the FLOPs-matched comparison). The paper states that it "believe[s] this model is representative of the capabilities of many contemporary LLMs" (Section 4), but no evidence is provided for this claim.

**The consequence.** The generalizability of the paper's central findings — the difficulty-dependent efficacy of different strategies, the 4× efficiency improvement from compute-optimal allocation, the specific mix of strategies per difficulty bin — to other models, benchmarks, or task domains is unverified and uncertain. Several aspects could be model- or domain-specific:

- **PRM quality and over-optimization behavior** depend on PaLM 2-S*'s output distribution, calibration, and error patterns. A model with different characteristics (e.g., better calibration, different types of reasoning errors) could exhibit different difficulty-dependent scaling curves.

- **Revision model effectiveness** depends on the base model's in-context learning and self-correction capabilities, which vary substantially across model families. The 38% correct-to-incorrect reversion rate is specific to the paper's revision model training procedure and base model.

- **MATH** is a narrow domain — symbolic mathematical reasoning with ground-truth answers. The findings may not transfer to code generation (where unit tests provide verification), open-ended reasoning (where correctness is ambiguous), or knowledge-intensive tasks (where factual recall, not logical reasoning, is the bottleneck).

- The **test set of 500 questions**, split into five quintiles of ~100 each, with two-fold cross-validation halving each bin, means strategy selection is based on **~50 questions per fold per bin**. The paper does not report confidence intervals on scaling curves or strategy rankings, so it is unclear whether the observed differences between strategies at specific budget levels (e.g., beam search M=4 vs. best-of-N at 64 generations in bin 3) are statistically reliable at this sample size.

**What evidence exists in the paper.** None. The paper contains no experiments on any benchmark other than MATH, and no experiments with any base model other than PaLM 2-S*. The MATH dataset choice is justified (Section 4) as a domain where test-time compute is expected to help because the model already possesses mathematical knowledge and the challenge is drawing complex inferences, but this justification applies to the domain, not to the model choice.

**Mitigation status.** Not addressed. The paper does not claim generalizability, but the framing (e.g., Section 7's discussion of on-device deployment implications) implies broader applicability. Future work on other domains and models is explicitly called for (Section 8): "We leave the analysis of compute-optimal scaling of pretraining compute where the data and parameters are both scaled equally to future work."

---

### Limitation 5: Revisions and Search Are Studied Independently; Their Combination Is Unexplored

**The assumption or constraint.** The paper studies two complementary axes — PRM-guided tree search (verifier optimization) and iterative revisions (proposal distribution modification) — as independent mechanisms. They are never combined in a single system. The paper acknowledges this explicitly (Section 8):

> "we did not experiment with PRM tree-search techniques in combination with revisions"

**The consequence.** The paper's results represent a **lower bound** on what a fully integrated system could achieve. The two mechanisms have complementary, difficulty-dependent strengths: revisions improve the proposal distribution (generating better candidates, especially on easy problems where refinement is sufficient) while PRM search improves candidate selection (finding the best among generated candidates, especially on medium problems where exploration is needed). Combining them — e.g., using the revision model as the proposal distribution within beam search, or using the PRM to guide which revisions to pursue — could yield gains beyond either method alone.

This gap is significant for several reasons: (1) The FLOPs-matched comparison (Section 7) shows revisions outperform search on easy questions and search outperforms revisions on medium-hard questions. A combined system could leverage both strengths per-question. (2) The revision model's correct-to-incorrect reversion problem (~38% rate) could potentially be addressed by using PRM scores to select the best point in the revision chain rather than relying on majority voting or a separately trained ORM. (3) The verifier over-optimization problem might be partially mitigated by using the revision model's outputs (which are closer to the base model's distribution than aggressively searched outputs), as the PRM is trained on base-model data.

**What evidence exists in the paper.** The difficulty-bin analyses (Figure 3 right for search, Figure 7 right for revisions) provide indirect evidence of complementarity: easy problems favor revisions (fully sequential is optimal), medium problems favor a balanced sequential-parallel ratio, and hard problems favor parallel search. But no experiment combines PRM tree search with the revision model as the proposal distribution, so the magnitude of potential gains is unknown.

**Mitigation status.** Not addressed. The paper identifies this as future work (Section 8): combining search and revisions, and "distilling the outputs of applying additional test-time compute back into the base LLM, enabling an iterative self-improvement loop." The paper's framework of proposal-vs-verifier axes (Section 2) provides intellectual scaffolding for such combination, but the experimental validation is absent.

---

### Limitation 6: Sequential Revisions Introduce Fundamental Latency That Is Not Accounted For

**The assumption or constraint.** The paper measures all test-time compute budgets in "generations" — the number of complete solutions sampled. This is a reasonable proxy for total FLOPs but completely ignores **wall-clock latency**. Sequential revisions are inherently serial: each revision depends on the previous one, so a chain of 64 revisions must be generated one at a time. In contrast, parallel best-of-N can execute all 64 samples simultaneously given sufficient hardware.

**The consequence.** The compute-optimal policy — which favors sequential revisions on easy problems and sequential-parallel hybrids on medium problems — would produce generation allocations that are **impractical for latency-sensitive applications**:

- A strategy allocating 128 generations as 64 sequential × 2 parallel takes roughly **64× longer wall-clock time** than a strategy running 128 parallel samples simultaneously, even though both consume similar total FLOPs. For interactive assistants, chatbots, or any real-time application, waiting for 64 sequential revisions (even if each is fast) would produce unacceptable user-perceived latency.

- The paper's difficulty-dependent policy recommendations (Section 5.3 for search, Section 6.2 for revisions) are derived from maximization of accuracy under a *generation count* budget, not a *wall-clock time* budget. If the budget were measured in wall-clock time with realistic parallelism constraints, the optimal strategy per difficulty bin would likely shift toward more parallelism and less sequential depth, because parallel execution amortizes hardware latencies that sequential chains cannot.

- For the FLOPs-matched comparison (Section 7), the paper compares total training + inference FLOPs but assumes inference can use arbitrary sequential revision chains without latency penalty. A latency-aware comparison would penalize sequential strategies, potentially shifting the pretraining-vs-inference boundary toward pretraining for latency-constrained regimes.

**What evidence exists in the paper.** None. The paper does not discuss wall-clock latency, does not model parallelism constraints, and does not report the actual time taken by revision chains vs. parallel sampling in any experiment. The efficiency metric throughout is generation count, which treats one sequential generation and one parallel generation as equivalent units of compute. The FLOPs accounting (Section 7) uses the standard formulas X = 6ND_pretrain and Y = 2ND_inference, which measure total floating-point operations but not the time required to execute them under hardware parallelism constraints.

**Mitigation status.** Not addressed. The paper does not acknowledge latency as a constraint distinct from total compute, and does not suggest latency-aware strategy optimization as future work. This is a significant gap for any practitioner considering deployment in interactive or latency-sensitive settings.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

This paper establishes that **inference efficiency can be pursued through content restructuring rather than model or system modification** — a genuinely new axis in the efficiency optimization landscape. Prior work across three established communities (model compression, serving systems, and speculative/non-autoregressive decoding) all accepted the autoregressive decoding bottleneck as an architectural given to be worked around through hardware utilization, model redesign, or token-level speculation. Skeleton-of-Thought demonstrates that **the bottleneck can be eliminated at the content level** by having the LLM itself plan its output as independent, parallel-expandable segments, using only prompt engineering and standard batching — no model modification, no draft models, no specialized serving infrastructure.

This is not a paradigm shift in the sense of upending existing efficiency techniques, but it **opens a complementary dimension** that was previously invisible. The paper explicitly demonstrates this orthogonality by combining SoT with 4-bit quantization (Appendix J), achieving multiplicative speed-ups (1.54× to 2.07× over unquantized normal generation). The implication is that future efficiency-optimized deployments should operate on three levels simultaneously: model-level (compression, efficient architectures), system-level (batching, parallelism, memory management), and now data-level (content organization for parallelizability). The paper's own framing as "data-centric optimization for efficiency" positions this as an emerging category that will grow in importance as LLM instruction-following capabilities improve.

The paper also resolves a latent tension in the prompting literature. Chain-of-Thought and related techniques demonstrate that **explicitly articulating intermediate reasoning improves quality but increases latency** (more tokens generated sequentially). SoT demonstrates the inverse: **explicitly articulating answer structure can improve both quality and latency simultaneously** — at least for question types whose answers naturally decompose into independent aspects. The LLMZoo detailed metrics (Figure 6) reveal the mechanism: the skeleton stage forces the LLM to consider multiple perspectives before writing, improving diversity (99.9% win rate) and relevance (61.4% win rate), while the parallel expansion reduces wall-clock latency. This suggests that **different types of explicit planning serve different purposes**: step-by-step reasoning helps with logical deduction (quality at latency cost), while outline-based structuring helps with comprehensive coverage (quality and latency simultaneously when parallelizable). Future prompt designers should consider not just whether to elicit explicit reasoning, but **what structure of explicit reasoning** best matches the task's parallelism properties.

A perhaps underappreciated contribution is the paper's **diagnostic characterization of when parallel content generation fails**. By identifying three distinct failure modes — sequential dependency (math, Fermi), format violation (coding), and stylistic coherence loss (writing) — the paper provides a predictive framework for determining *a priori* whether SoT will help for a new task. This converts SoT from an empirical trick into a deployable tool with well-understood boundary conditions. The paper's observation that some models **emergent-compensate** for sequential dependencies by embedding the full answer in the skeleton stage (Appendix I.1.2, Fermi problems) suggests that the boundary between "structured parallel" and "sequential" generation may itself be learnable or promptable, opening a path toward unified frameworks that adapt their generation structure to the task.

The paper's framing also **repositions the relationship between throughput-oriented and latency-oriented optimization**. Serving systems have long used batching to improve throughput at the cost of per-query latency (batching requires waiting for multiple queries). SoT creates **artificial intra-query batchability** — converting one long sequential decode into multiple shorter parallel decodes — enabling throughput-oriented techniques to directly reduce single-query latency. This insight could influence serving system design: rather than only batching across users, systems could support "content-aware batching" where a single complex query is decomposed into parallel sub-queries by the LLM itself.

### Follow-Up Research This Work Enables

**1. Fine-tuning LLMs to internalize the skeleton-then-expand pattern without explicit prompting.** The current approach requires carefully engineered two-stage prompts with model-specific variations (two-shot demonstrations for non-GPT-4 models, softened brevity instructions for Claude/GPT-4, partial-answer tricks for format compliance). This fragility makes SoT's speed-up unpredictable across models: StableVicuna-13B achieves only 0.97× measured speed-up because it fails to follow the "write very shortly" instruction (Figure 14a, Appendix G.1.4). A natural follow-up would fine-tune instruction-tuned models on a dataset of (question, skeleton, expanded answer) triples — perhaps generated by GPT-4 using SoT prompts on a diverse question set — so that the model internalizes the structured generation pattern and can be triggered with a lightweight instruction (e.g., "answer in parallel-expandable format") rather than multi-shot prompts. The key metric would be whether fine-tuned models achieve consistent speed-ups across model sizes and architectures without model-specific prompt tuning, and whether the structured generation generalizes to out-of-distribution question types. The paper's own suggestion of "self-improving" (Section 6) using SoT-generated answers as fine-tuning data is a concrete starting point.

**2. Dynamic Graph-of-Thoughts with dependency-aware parallel scheduling.** The paper identifies that SoT "currently ignores the dependencies between points" and proposes Graph-of-Thoughts as a generalization: nodes represent answer components, edges represent dependencies, and each node is decoded conditioned on its ancestors' expanded content rather than just the skeleton (Section 6). This would address the fundamental limitation on sequential-reasoning tasks (math, Fermi, coding) where later steps genuinely depend on earlier results. A concrete experiment: on the MATH dataset, construct a dependency graph where each solution step is a node, edges indicate which prior results are needed, and a topological ordering determines which nodes can be expanded in parallel. Compare against both Chain-of-Thought sequential generation (quality baseline) and vanilla SoT (latency baseline). The key research question: can the LLM itself generate the dependency graph during the skeleton stage, or does this require external planning? The paper notes that contemporary work (Besta et al., 2023) has "attempted to design Graph-of-Thoughts to elicit reasoning" — SoT extends this to efficiency. A strong follow-up would measure the trade-off between parallelism (speed-up) and answer quality as dependency edge density increases.

**3. Adaptive skeleton granularity based on point complexity estimation.** The current SoT generates all skeleton points at a uniform granularity (3–5 words each, 1–2 sentence expansion), but different aspects of an answer may require different levels of detail. A point like "Energy conservation" in a climate answer might need 3–4 sentences with specific examples, while "Sustainable travel" might need only 1 sentence. The paper shows that length imbalance between points (Figure 11e, standard deviation ranging from ~6.5 tokens for GPT-4 to ~64.7 for StableVicuna-13B) directly impacts speed-up because the batch decoding time is determined by the longest point. A system that estimates per-point complexity (perhaps by querying the LLM for a "detail level" score during skeleton generation) could allocate expansion budgets adaptively — keeping short points short and giving complex points more tokens — improving both speed-up (by reducing the maximum-point bottleneck) and quality (by preventing superficial treatment of complex aspects). The experiment would measure speed-up and quality as a function of the load-balancing quality (ratio of longest to average point expansion length), comparing adaptive vs. uniform allocation.

**4. Combining SoT with speculative decoding for compound token-level + content-level parallelism.** SoT achieves parallelism at the content level (different answer segments decoded in parallel), while speculative decoding achieves parallelism at the token level (draft model generates candidate tokens, target model verifies in parallel). These are orthogonal: a SoT point-expanding batch could itself use speculative decoding within each sequence to accelerate per-point token generation, or conversely, the draft model in speculative decoding could be replaced by a SoT-structured generation where the draft produces multiple segments simultaneously. A concrete experiment: take an open-source model pair (e.g., LLaMA-7B as draft, LLaMA-13B as target), measure the end-to-end latency of (a) speculative decoding alone, (b) SoT alone, and (c) both combined (SoT decomposes the answer, each point expands using speculative decoding). The key metric is whether the speed-ups are multiplicative (e.g., 2× from SoT × 1.5× from speculative decoding ≈ 3× combined) or sub-multiplicative due to shared overhead. The paper's latency profiling methodology (Appendix F) provides the measurement infrastructure to isolate where additional gains materialize or saturate.

**5. Router training on a larger, more diverse question corpus with continuous suitability scores.** The current trained router uses only 1,030 LIMA questions (371 suitable for SoT) and binary labels, leading to 5 false negatives and 6 false positives on Vicuna-80 (Table 3, Appendix C.3). A binary decision boundary may be too coarse: some questions benefit slightly from SoT, others substantially, and a continuous "suitability score" that predicts the expected net win rate or speed-up would enable more nuanced deployment decisions (e.g., trigger SoT only when the expected quality gain exceeds some threshold, or only when the expected speed-up exceeds 1.2×). A concrete follow-up: annotate a dataset of 5,000–10,000 diverse questions with (a) binary suitability labels, (b) quality ratings for both SoT and normal answers, and (c) measured speed-up. Train a regression model to predict both quality difference and speed-up from question text alone, and evaluate whether threshold-based triggering outperforms binary classification on a held-out set. The paper's router consistency analysis (Tables 3, 4) and Tversky loss design already establish the importance of asymmetric error costs; a continuous scorer would extend this to cost-aware decision thresholds.

**6. Stress-testing SoT on out-of-distribution question types and adversarial inputs.** The paper evaluates on two assistant-style benchmarks (Vicuna-80, WizardLM) that are broadly representative of chatbot queries but do not include edge cases that might break the skeleton extraction or parallel expansion. What happens when the question is ambiguous (multiple valid skeleton structures), self-referential ("What would be a good skeleton for answering this question?"), or designed to produce circular dependencies between points? What if the question requests a specific format incompatible with bulleted lists (e.g., "Write a single flowing paragraph")? The paper shows that SoT gracefully degrades on math and coding via the router, but a systematic stress test would characterize failure modes that the router might miss — for example, questions that *appear* decomposable but contain subtle cross-point dependencies (like Fermi problems where independence is ambiguous). The router's confusion matrices on WizardLM (Table 4) already show 66 false positives from the GPT-4 router on questions with "intricate answer structure," suggesting the classification boundary is fragile. A strong stress test would construct an adversarial benchmark of 100–200 deliberately tricky questions and measure both router accuracy and SoT answer quality, establishing safety boundaries for deployment in open-ended chatbot settings.

### Practical Applications and Downstream Use Cases

**1. Single-user, latency-sensitive interactive assistants.** The most immediate deployment scenario is edge-side applications with a single user — personal AI assistants running on-device or accessed via API — where end-to-end latency directly determines user experience. The paper's speed-up numbers are most reliable for this setting: on Vicuna-80's suitable question categories (knowledge, generic, common-sense, roleplay, counterfactual), SoT-R with the trained router achieves 1.79× to 2.26× speed-up on Vicuna-80 (Figure 18b) while maintaining or improving answer quality. For the 7B models evaluated on a consumer RTX 3090 (Appendix G.1.3), SoT provides 1.96× to 2.52× speed-up on these categories. The combination with 4-bit quantization (Appendix J, Figure 36b) pushes combined speed-ups to 2.42× to 3.41× over unquantized normal generation. A deployment on a laptop with a quantized 7B model could reduce response times from 15–20 seconds to 5–7 seconds for typical knowledge questions — crossing the threshold from "noticeably slow" to "conversationally acceptable." The trained router's low latency (0.04 seconds on average, Appendix G.2) means the routing decision adds negligible overhead.

**2. API-based applications where per-call latency matters more than token cost.** For proprietary models accessed via API (ChatGPT-3.5, GPT-4, Claude), SoT achieves speed-up through parallel API calls rather than batched decoding. The paper reports 1.31× (Claude) to 2.00× (GPT-4) speed-up on suitable questions (Figure 2a). However, SoT substantially increases total token consumption — 60–89× more prefilling tokens for API-based models (Table 6, Appendix H) — meaning the cost-per-query is higher even though latency is lower. This trade-off makes SoT suitable for applications where **user-perceived responsiveness dominates cost**: real-time agent-agent communication (where one LLM's output feeds into another's input with compounding latency), interactive demos and prototypes (where user engagement depends on speed), and premium-tier services (where subscribers pay for low latency). The paper explicitly notes this trade-off in Appendix L and suggests prompt tuning to reduce token overhead. A practical deployment would monitor both latency and cost, routing only latency-sensitive queries through SoT while using normal generation for throughput-oriented batch processing.

**3. Structured content generation for downstream consumption.** Beyond live chat, the skeleton-then-expand structure naturally produces answers that are **more parseable by downstream systems** than free-form prose. The numbered, labeled-point format with independent expansions for each aspect makes SoT outputs suitable as input to retrieval systems (each point can be indexed separately), summarization pipelines (the skeleton already provides a summary), or multi-document synthesis (points from different SoT answers on related questions can be merged). The paper's quality analysis shows that SoT improves diversity (99.9% win rate, Figure 6) and relevance (61.4% win rate) — precisely the properties desired in content that will be indexed, searched, or aggregated. A practical example: a customer support knowledge base where SoT generates structured answers to common questions (skeleton: categories of solutions; expansions: specific steps), enabling users to navigate directly to relevant points rather than reading through prose paragraphs.

**4. Model evaluation and capability probing.** SoT's requirement that the model follow a two-stage structured generation protocol makes it a **diagnostic tool for instruction-following capability**. The paper's per-model analysis (Appendix I.1.1) reveals stark differences: Vicuna-13B V1.3 successfully produces well-structured skeletons and focussed expansions, while OpenChat-13B and Vicuna-7B V1.1 fail at basic format compliance — writing full paragraphs in the skeleton stage or producing empty point expansions. The per-model speed-up variation (0.97× to 2.88× measured, Figure 14a) and quality variation (net win rates from −7% to +12%, Figure 4a) effectively rank models on a "structured planning + constrained generation" axis that is not captured by standard benchmark scores. A practical evaluation pipeline could use SoT performance — skeleton format compliance rate, point expansion length adherence, speed-up achieved, quality relative to normal generation — as a lightweight proxy for instruction-following robustness, complementing existing benchmarks like AlpacaEval or MT-Bench that focus on output quality rather than process adherence.
