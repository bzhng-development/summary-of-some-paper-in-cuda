# Nemotron-Cascade: Scaling Cascaded Reinforcement Learning for General-Purpose Reasoning Models

**ArXiv:** [2512.13607](https://arxiv.org/abs/2512.13607)

## 🎯 Pitch

This paper proposes **Cascaded Reinforcement Learning (Cascade RL)**, a post-training framework that applies sequential, domain-wise reinforcement learning to build general-purpose reasoning models capable of operating in both thinking and non-thinking modes without a performance gap relative to a dedicated thinking-only counterpart.

---

## 1. Executive Summary

This paper proposes **Cascaded Reinforcement Learning (Cascade RL)**, a post-training framework that applies sequential, domain-wise reinforcement learning to build general-purpose reasoning models capable of operating in both thinking and non-thinking modes without a performance gap relative to a dedicated thinking-only counterpart. Using pretrained Qwen3-8B-Base and Qwen3-14B-Base as starting points, Cascade RL orchestrates RLHF (human preference alignment via scalar reward models), IF-RL (instruction-following via rule-based verifiers), Math RL (symbolic rule-based verification), Code RL (execution-based unit-test verification), and SWE RL (execution-free, LLM-based semantic similarity scoring) in a staged pipeline, finding that each subsequent domain-specific RL stage rarely degrades and often improves performance attained in earlier domains. The 14B dedicated thinking model surpasses its SFT teacher DeepSeek-R1-0528 on LiveCodeBench v5/v6/Pro and achieves silver-medal performance in the 2025 International Olympiad in Informatics (IOI), while the 8B unified model matches the dedicated 8B-Thinking variant across reasoning benchmarks despite additional non-thinking training, establishing that unified thinking/instruct reasoning models can close the performance gap to dedicated thinking models when SFT data is curated with parallel thinking and instruct responses for the same prompts and RLHF training allocates an equal split of prompts to each mode in every batch.

## 2. Context and Motivation

### The Core Problem: Heterogeneity Complicates General-Purpose RL Training

The fundamental challenge this paper tackles is the **substantial cross-domain heterogeneity** inherent in training general-purpose reasoning models with reinforcement learning. When a single model must excel at human preference alignment, strict instruction following, mathematical problem-solving, competitive programming, and software engineering, the RL training process encounters incompatible demands across domains:

- **Response length variability**: Mathematical reasoning can require tens of thousands of tokens of chain-of-thought analysis, while instruction-following tasks (e.g., "write a summary within 300 words") demand conciseness. Training on both simultaneously creates tension — the model cannot simultaneously optimize for both verbosity and brevity within the same RL update.

- **Verification latency heterogeneity**: Rule-based math verification executes in milliseconds (symbolic checking of boxed answers), while code execution-based verification requires running generated programs against test suites, often taking seconds to minutes per sample. Software engineering patch validation is even slower, requiring Docker environment setup and test suite execution. When prompts from all domains are blended into a single training batch as in conventional approaches, the fastest verifiers (math) must wait for the slowest (code, SWE) before gradient updates can proceed, creating a bottleneck that the paper explicitly identifies:

> "Rule-based math verification can be executed rapidly and is orders of magnitude faster than code verification, allowing the model to be updated immediately without waiting for longer verification cycles required for code prompts."

- **Reward signal type incompatibility**: RLHF uses scalar outputs from learned reward models (unbounded, noisy, OOD-sensitive), instruction-following RL uses binary rule-based verifiers (rigid constraints that ignore response quality), math RL uses symbolic boxed-answer checking, code RL uses unit-test pass/fail signals, and SWE RL uses execution-free LLM-based semantic similarity scores. These reward functions have fundamentally different scales, noise characteristics, and optimization landscapes. Joint training requires careful reward balancing and normalization — a fragile engineering challenge the paper argues is avoided entirely by training sequentially.

This heterogeneity manifests concretely in the infrastructure: "Such variability complicates the RL infrastructure, slows training, and makes training curriculum (e.g., response length extension) and hyperparameter selection challenging."

### Why This Problem Matters

**Practical deployment fragmentation.** Since the introduction of OpenAI o1 (OpenAI, 2024), the LLM community has bifurcated into two model types: *thinking models* that generate extensive reasoning traces before answering (DeepSeek-R1, o3, o4-mini, Kimi-K2-Thinking, Qwen3-Thinking) and *instruct/non-thinking models* that produce instant answers (DeepSeek-V3, GPT-4.5, Kimi-K2-Instruct). This bifurcation creates significant deployment overhead — organizations must maintain two separate models, route queries appropriately, and manage versioning across both. The paper argues for a single *unified reasoning model* that can operate in both modes at each conversational turn, activated by per-user-prompt control flags (`/think` and `/no_think`):

> "It would be ideal to build one unified reasoning model that can operate in both non-thinking and thinking modes while integrating all capabilities together in a single model. This would i) greatly simplify model release and production pipelines, and ii) align more closely with the ultimate goal of artificial general intelligence."

**The performance gap problem.** Prior unified models exhibit a consistent, frustrating pattern: when operating in thinking mode, they underperform dedicated thinking-only models trained on the same reasoning data. The paper documents this explicitly:

> "Although the Qwen3 series was initially released as a set of unified reasoning models, it was later reverted to separate thinking and instruct variants, with the dedicated thinking models significantly outperforming the unified models in thinking mode."

GPT-5 "explored routing between two specialized models" rather than achieving true unification. DeepSeek-V3.1 achieved thinking-mode performance comparable to DeepSeek-R1-0528 but was built on a different base model with undisclosed technical details. The paper thus identifies a **credibility gap** in the community: can a single model genuinely match dedicated thinking models on reasoning benchmarks while retaining instruct capabilities, or is there an inherent trade-off that makes unification impossible — especially for smaller models (8B parameters)? The paper directly challenges the assumption that "LLMs, especially smaller ones, lack the capacity to learn effectively from both non-thinking and thinking data."

**Infrastructure and curriculum design.** The dominant approach to training general-purpose reasoning models — exemplified by DeepSeek-R1 and Qwen3 — is to blend diverse prompt distributions from all domains and perform joint RL training. While conceptually simple, this "blend and train" paradigm creates practical engineering challenges:

- The curriculum (when to extend response length, whether to use overlong filtering) must be a one-size-fits-all compromise across domains with very different length distributions.
- Hyperparameters (learning rate, temperature, KL penalty) must work simultaneously for RLHF (sensitive to OOD rewards, benefits from KL regularization with small RMs) and RLVR (where KL regularization can inhibit exploration needed for long chain-of-thought).
- The infrastructure must handle the slowest verification step in any batch, creating GPU idle time.

The paper positions Cascade RL as a systematic solution to these engineering challenges while simultaneously improving final performance.

### Prior Approaches and Their Shortcomings

**Joint blended RL (DeepSeek-R1, Qwen3).** The prevalent approach applies RL across all domains simultaneously, with prompts sampled from a blended distribution. This approach faces the heterogeneity problems described above. More subtly, it creates *cross-domain interference* — updates from RLHF (which penalize verbosity and encourage concise, helpful responses) can conflict with updates from math RL (which reward extended chain-of-thought reasoning), particularly when prompts from both domains appear in the same or adjacent batches. The paper documents concrete interference: when math-related prompts were accidentally included in RLHF training, "a 2% performance drop on the AIME25 benchmark" resulted.

**Dedicated thinking models (OpenAI o1/o3/o4-mini, DeepSeek-R1).** These achieve strong reasoning performance but sacrifice the instruct capability entirely, requiring separate deployment of instruct-oriented models for non-reasoning tasks. This doubles serving infrastructure, complicates routing, and fragments the user experience — a user asking a simple factual question must wait for a thinking model to generate unnecessary reasoning traces, or the system must implement routing logic that adds latency and failure modes.

**SFT-only or SFT+distillation approaches.** Off-policy distillation (training student models on teacher-generated reasoning traces) can produce strong initial reasoning performance without RL, as demonstrated by the paper's SFT baselines achieving 83.8% and 86.9% on AIME24 for 8B and 14B respectively. However, these approaches plateau — the paper's SFT models are substantially outperformed by the same models after RL (89.5% and 89.7% respectively), demonstrating that distillation alone cannot match on-policy RL's ability to explore and improve beyond the teacher distribution.

**Prior cascaded RL work (AceReason-Nemotron).** The authors' own prior work (Chen et al., 2025) applied cascaded RL across math and code domains only, establishing that math RL improves code benchmarks and code RL does not degrade math performance. However, this prior work was limited to pure reasoning domains, leaving open the question of whether the cascaded paradigm extends to fundamentally different RL types — specifically, whether RLHF (with learned reward models) can be integrated into the cascade without causing the alignment tax or interference that plagues joint training. The current paper scales the cascaded paradigm "to a much broader range of domains."

**RLHF + RLVR integration gap.** The paper identifies a specific underexplored area: "We systematically investigate the interplay between RLHF and RLVR — a topic that has been underexplored in existing literature." Most reasoning models (DeepSeek-R1, AceReason-Nemotron) focus exclusively on RLVR for reasoning domains and apply RLHF separately or not at all. The paper's integration of RLHF as the *first* stage of the cascade, before any domain-specific RLVR, is a novel design choice motivated by an empirical finding: RLHF "substantially improves overall response quality (e.g., reduces verbosity), thereby enhancing reasoning performance" — a counterintuitive result suggesting alignment training is not merely orthogonal to reasoning capability but positively synergistic.

### How This Paper Positions Itself

The paper frames Cascade RL as a **scalable engineering paradigm** rather than a single algorithmic contribution. The key positioning claims are:

1. **Sequential over joint training.** Cascade RL "orchestrates sequential, domain-wise RL, reducing engineering complexity and delivering state-of-the-art performance" — the claim is both about final accuracy and about developer experience (easier hyperparameter tuning, simpler curriculum design, more debuggable training dynamics).

2. **RLHF as a foundation, not an afterthought.** Departing from the common practice of applying RLHF as a final alignment step, Cascade RL places RLHF first, finding it "boosts the model's reasoning ability far beyond mere preference optimization" and provides a cleaner, less verbose policy initialization that makes subsequent RLVR stages more efficient: "initialization from RLHF-trained models is highly beneficial because it provides a much stronger initial math reasoning capability than SFT checkpoints... and significantly reduces the number of steps required for math RL training."

3. **Resistance to catastrophic forgetting as a property of cascaded RL for LLMs.** The paper provides a theoretical argument (Section 4.1.1) for why sequential domain-wise RL does not suffer from catastrophic forgetting in the LLM context — a claim that runs counter to standard supervised learning intuition. The argument rests on four pillars: (i) RL data is policy-dependent, so old behaviors persist if they remain reward-relevant; (ii) RL optimizes cumulative reward, not token-level distributions, so old knowledge naturally persists when new tasks share structure with old ones; (iii) reward structures across domains (alignment, math, code, SWE) share the common goal of making outputs "better, more accurate, and more aligned"; and (iv) prompt overlap across domains is minimized by construction (math/code prompts are explicitly removed from RLHF training data) and the cascade proceeds from general to specialized domains.

4. **Transparent, open recipe for the community.** The paper emphasizes that its contributions include "transparently sharing our training and data curation recipes" and releasing "the full collection of models and training data." This positions Cascade RL not as a proprietary technique but as a replicable, open post-training methodology that the community can adopt, adapt, and improve upon — using publicly available base models (Qwen3-8B-Base, Qwen3-14B-Base) and datasets.

The paper's central bet is that **domain-wise decomposition of RL training is both more practical and more performant than joint training**, that the feared catastrophic forgetting does not materialize in practice for LLM RL (a finding validated across five RL stages and dozens of benchmarks), and that unification of thinking and instruct modes is achievable even at the 8B scale without compromise.

## 3. Technical Approach

### 3.1 Reader Orientation

This paper builds a **post-training pipeline** that takes a pretrained base language model and applies a sequence of reinforcement learning stages, each focused on a single domain, to produce a general-purpose reasoning model that can switch between thinking and non-thinking modes on demand without sacrificing performance in either mode. The core problem is that joint RL training across heterogeneous domains (alignment, instruction-following, math, code, software engineering) creates incompatible demands on infrastructure, hyperparameters, and training curriculum; the solution is to decompose the problem into a **sequential cascade** where each stage trains on a single domain's prompts with its own tailored reward function, verification method, and length budget, and the cascade is ordered from general to specialized to prevent interference.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components, applied in a fixed order after an initial supervised fine-tuning (SFT) stage:

1. **Supervised Fine-Tuning (SFT)** — a two-stage process (16K then 32K max sequence length) that teaches the base model foundational skills across general conversation, math, code, science, tool use, and software engineering, using responses generated by teacher models (DeepSeek-R1, DeepSeek-R1-0528, DeepSeek-V3-0324). For unified models, each prompt contains parallel responses in both thinking and non-thinking formats.

2. **RLHF (Reinforcement Learning from Human Feedback)** — the first RL stage, using a 72B scalar-output reward model trained with the Bradley-Terry objective on preference pairs. This stage improves response quality, reduces verbosity, and provides a cleaner initialization for subsequent stages. It is applied with a 12K max response length, no overlong filtering, and no KL penalty.

3. **IF-RL (Instruction-Following RL)** — a two-stage RL process using rule-based verifiers that check whether responses satisfy explicit instruction constraints (word counts, formatting, content requirements). For unified models, this is applied only in non-thinking mode to avoid reward-hacking. For dedicated thinking models, a combined reward function blends the binary IF verifier with the normalized RLHF reward model score.

4. **Math RL** — a three-stage RL process (24K → 32K → 40K max response lengths) using symbolic rule-based verification of boxed answers, with dynamic filtering to remove overly easy or unsolvable problems. The staged length curriculum compresses overlong reasoning, stabilizes length, then extends reasoning chains.

5. **Code RL** — a single-stage RL process (44K–56K max response length) using execution-based unit-test verification with asynchronous reward computation. Applied after Math RL, which serves as a warm-up that stabilizes training and improves general reasoning.

6. **SWE RL** — a two-stage RL process (16K → 24K input context length, 16K output length) using an execution-free LLM-based semantic similarity reward function that compares generated code patches to human-written golden patches. The two-stage curriculum progressively expands the input context window to handle multiple retrieved files.

Information flows sequentially: the SFT checkpoint initializes RLHF, the RLHF checkpoint initializes IF-RL, the IF-RL checkpoint initializes Math RL, and so on. At each stage, the model generates its own training data on-policy (using GRPO with 8–16 rollouts per prompt), receives domain-specific rewards, and performs a single gradient update before generating new rollouts for the next iteration.

### 3.3 Roadmap for the Deep Dive

- **First**, the Chat Template and unified mode control mechanism (Section 3.1.2 of the paper), since it defines the fundamental interaction schema that determines whether the model thinks or not at each turn — this is prerequisite context for understanding all training stages.
- **Second**, the Multi-Stage SFT process (Section 3.1.1, 3.2 of the paper), which creates the foundation that RL refines. Understanding what data the model sees, how thinking and non-thinking responses are paired, and how the 16K→32K curriculum works is essential context for the RL stages.
- **Third**, the Cascade RL training framework (Section 4.1 of the paper), covering the GRPO objective, on-policy training, and the theoretical argument for why sequential domain-wise RL resists catastrophic forgetting — this is the core algorithmic mechanism shared across all RL stages.
- **Fourth**, the Reward Model (RM) for RLHF (Section 4.2 of the paper), since it is the verifier for the first RL stage and its quality determines the effectiveness of the entire cascade's foundation.
- **Fifth**, each RL stage in cascade order — RLHF (§4.3), IF-RL (§4.4), Math RL (§4.5), Code RL (§4.6), SWE RL (§4.7) — with their domain-specific reward functions, data curation, training recipes, and hyperparameters. This order mirrors the actual training sequence so the reader can understand how each stage builds on the previous one.
- **Sixth**, the SWE Agentless framework and execution-free reward model (Section 3.3, 4.7, 7.2 of the paper), since SWE RL uses fundamentally different verification than the other stages and requires understanding the localization→repair→validation pipeline.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily an **engineering systems paper** whose core idea is that sequential, domain-wise RL training with domain-tailored reward functions, verification methods, and hyperparameters produces better general-purpose reasoning models than joint blended RL training, without suffering catastrophic forgetting.

#### Chat Template and Unified Mode Control

The chat template is the **interaction protocol** that defines how users communicate with the model and how the model distinguishes between thinking and non-thinking generation modes. It is defined in Section 3.1.2 and illustrated in Figure 3 (left panel).

**Template structure.** The paper adopts the standard ChatML format (OpenAI) with `<|im_start|>` and `<|im_end|>` tokens delimiting each conversational turn. The template supports three roles: `system`, `user`, and `assistant`. The system prompt is a fixed instruction (e.g., "You are a helpful and harmless assistant."), and each user turn appends one of two **control flags** to the prompt text:

- `/think` — instructs the model to generate a reasoning trace before the final answer. The model produces a ` thinking` block containing chain-of-thought analysis, followed by a ` response` block containing the final answer.
- `/no_think` — instructs the model to produce a direct answer without any reasoning trace, skipping the ` thinking` block entirely.

**Design choice: per-user-prompt flags over system-prompt flags.** Prior work by Bakouch et al. (2025) places the `/think` and `/no_think` control in the system prompt, which globally controls the entire conversation. The paper argues this design "controls the entire conversation globally" and therefore cannot support dynamic mode switching within a single conversation — for example, thinking for a complex math question in one turn and answering directly for a simple factual follow-up in the next. By appending the flag to each individual user prompt, the template supports both global control (by using the same flag on every turn) and local control (by varying flags across turns).

**Design choice: flag-only over flag-plus-template mechanisms.** Qwen3 (Yang et al., 2025) employs a redundant dual mechanism: users can control thinking mode either through explicit flags (`/think`, `/no_think`) or by modifying the template itself via the `enable_thinking` argument, which prepends an empty ` thinking` block to activate non-thinking mode. The paper found in early experiments that "explicit flags result in more reliable mode transitions than template-based cues" and that "the flag-only design covers all use cases without any performance degradation." Consequently, the paper omits the empty ` thinking` block in non-thinking mode entirely, simplifying the template.

**Tool calling template.** For tasks requiring external function calls, all available tools are specified in the system prompt within `<tools>` and `</tools>` XML tags as JSON objects with `name`, `description`, and `parameters` fields (Figure 3, right panel). The model is instructed to emit tool calls within `<tool_call>` and `</tool_call>` XML tags, formatted as JSON objects with `name` and `arguments` keys.

**Implication for training.** The template design means that during SFT and RL, every training sample must be labeled with either `/think` or `/no_think` depending on the desired mode. For unified models, this creates parallel training data for the same prompt — one response in thinking format and one in non-thinking format — which the model must learn to generate depending on the flag.

#### Multi-Stage Supervised Fine-Tuning

The SFT stage equips the pretrained base model (Qwen3-8B-Base or Qwen3-14B-Base) with foundational conversational, reasoning, and tool-use capabilities. It is the **prerequisite foundation** on which all subsequent RL stages build. The training framework and data curation are described in Section 3.

**Two-stage curriculum.** SFT proceeds in two stages, distinguished by maximum sequence length and data composition:

- **Stage 1 (16K max sequence length, one epoch):** Includes general-domain data, math reasoning data, science reasoning data, and code reasoning data. For general-domain data, each prompt contains parallel responses in both thinking and non-thinking modes. For math, science, and code data, only thinking-mode responses are included. The 16K budget constrains responses to prevent the model from initially generating excessive reasoning traces before it has learned to reason efficiently.

- **Stage 2 (32K max sequence length, one epoch):** Recombines the general-domain data with new Stage-2 math, science, and code reasoning data (generated with up to 32K tokens), plus tool-use and software engineering datasets. Except for general-domain data, all other domains contain only thinking-mode responses. The longer budget allows the model to learn extended chain-of-thought reasoning on harder problems.

**General-domain data curation (2.8M samples, 3.2B tokens).** The corpus spans daily dialogue, question answering, creative writing, safety, instruction following, role-playing, and knowledge-intensive tasks. The paper identifies three quality challenges with the raw datasets:

1. Many responses are "excessively brief" — single-word or minimal-sentence outputs that lack detail.
2. Response quality varies widely across datasets.
3. Stylistic inconsistencies arise from diverse labeling conventions.

To address these, for each prompt the authors generate parallel responses using DeepSeek-R1-0528 (for thinking format) and DeepSeek-V3-0324 (for non-thinking format), both with a maximum sequence length of 16K. This ensures stylistic and qualitative consistency across the entire corpus. For prompts with verifiable ground-truth answers (multiple-choice questions), responses that deviate from the ground truth are discarded. For samples without ground-truth answers, an auxiliary model (Qwen2.5-32B-Instruct) cross-validates the generated responses to filter out low-quality generations. To enrich diversity in data-scarce domains (instruction following, creative writing), multiple responses are generated per prompt using different random seeds. Multi-turn conversational data is augmented by two methods: adding a second turn that asks the model to edit its previous response, and randomly concatenating single-turn samples into multi-turn conversations.

**Math reasoning data.** Stage 1 uses SFT prompts from AceReason-Nemotron-1.1, encompassing AceMath, NuminaMath, and OpenMathReasoning sources, with responses generated by DeepSeek-R1 at max 16K context length. The resulting dataset has 353K unique prompts with 2.77M total samples (average 7.8 responses per prompt). Stage 2 uses DeepSeek-R1-0528, which "produces longer and more detailed reasoning trajectories," with max 32K context length. The Stage 2 prompt set is obtained by filtering Stage 1 to remove easy questions (those whose DeepSeek-R1 responses contain fewer than 2K tokens), yielding 163K prompts and 1.88M samples (average 11.5 responses per prompt). All math data is formatted in thinking mode. Data decontamination removes any samples with 9-gram overlap with test samples from standard math benchmarks.

**Code reasoning data.** Stage 1 uses prompts from AceReason-Nemotron-1.1 (TACO, APPs, OpenCoder-Stage-2, OpenCodeReasoning sources), deduplicated to 172K distinct prompts, with responses generated by DeepSeek-R1 at max 16K context length (1.42M samples, average 8.3 responses per prompt). Stage 2 uses prompts from OpenCodeReasoning and OpenCoder-Stage2, with DeepSeek-R1-0528 at max 32K context length (79K prompts, 1.39M samples, average 17.6 responses per prompt). The higher response average for Stage 2 reflects the increased difficulty of the prompt set. All code data is formatted in thinking mode. Decontamination uses 9-gram filtering against test samples from coding benchmarks.

**Science reasoning data.** Prompts are curated from S1K and Llama-Nemotron post-training datasets, with a focus on problems requiring "strong scientific knowledge and involve substantial reasoning or complex calculations" rather than simple multiple-choice option analysis. Synthetic question generation using DeepSeek-R1-0528 creates rarer question types from each prompt. The final dataset has 226K science prompts, generating 289K samples (up to 16K) for Stage 1 with DeepSeek-R1, and 345K samples (up to 32K) for Stage 2 with DeepSeek-R1-0528. Stage 2 science data is upsampled by 2× before blending. All science data is in thinking mode.

**Tool calling data.** This dataset from Llama-Nemotron covers single-turn, multi-turn, and multi-step tool-use interactions, including scenarios where the model must ask clarification questions or handle multiple rounds of tool calls. Each conversation includes all available tools (average 4.4 tools) in the system prompt. Responses are generated by Qwen3-235B-A22B. The dataset contains 310K conversations with 1.41M user-assistant turns, all in thinking mode. Used only in Stage 2 SFT.

**Software engineering data (three sub-tasks).** The SWE task is decomposed into code localization, code repair, and test code generation:

- **Code localization:** Given a problem statement and repository structure (folder/file names), the model identifies and ranks potentially buggy files. Responses generated by DeepSeek-R1-0528 with 8 responses per prompt (4 for the larger SWE-Fixer-Train dataset). Filtering retains only samples where all ground-truth buggy files are included (recall = 1.0), yielding 92K samples.

- **Code repair:** Given a problem statement and contents of buggy code files, the model generates diff-style patches. Filtering uses Unidiff similarity to the golden patch: instances with at least 4 of 8 responses exceeding 0.5 similarity go to SFT (127K samples); instances with at least 1 of 8 responses achieving non-zero similarity (excluding SFT samples) are reserved for SWE RL (Section 4.7). The dataset composition is 17K from SWE-Bench-Train, 17K from SWE-reBench, 18K from SWE-Smith, and 77K from SWE-Fixer-Train.

- **Test code generation:** Given a problem statement, localization, and repair patches, the model generates unit tests and reproduction tests. Filtering retains only trajectories that parse and execute without syntax errors, yielding 31K samples.

All SWE datasets are upsampled by 3× before Stage 2 SFT blending. All SWE data is in thinking mode.

**SFT training hyperparameters.** The paper uses global batch size 256, AdamW optimizer (β₁=0.9, β₂=0.95), weight decay 1e-4, cosine learning rate schedule with minimum learning rate 0. Stage 1 uses max learning rate 5e-5 for 8B and 14B, with 20K steps (8B) and 22K steps (14B). Stage 2 uses max learning rate 2e-5 for 8B and 5e-5 for 14B, with 32K steps (8B) and 41K steps (14B).

**Key design choice: parallel thinking/non-thinking responses for general-domain data.** For the unified model, general-domain prompts include both a thinking response (from DeepSeek-R1-0528) and a non-thinking response (from DeepSeek-V3-0324). This teaches the model to generate different response formats for the same prompt depending on the control flag. For math, code, science, tool, and SWE data, only thinking-mode responses are included, reflecting that these domains naturally require reasoning.

#### Cascade RL Training Framework

The Cascade RL framework is the **central organizational principle** of the paper. It is defined by the sequential application of domain-wise RL stages, each with its own reward function, training data, and hyperparameters. The framework is described in Section 4.1.

**Training sequence.** The cascade proceeds in a fixed order: RLHF → IF-RL → Math RL → Code RL → SWE RL. The paper justifies this order with two principles:

1. **General before specialized:** "Domain-wise RL is organized from more general domains (e.g., RLHF, instruction-following) to more specialized ones (e.g., math, code, SWE), preventing specialized capabilities from being overwritten by generic behaviors."

2. **RLHF first:** "We first apply RLHF and then RLVR (e.g., Math RL), as RLHF substantially improves the quality of generated responses by reducing verbosity and repetition, thereby enhancing the reasoning performance within constrained response lengths (e.g., 64K tokens)."

**GRPO objective.** All RL stages use Group Relative Policy Optimization (GRPO; Shao et al., 2024) with strict on-policy training. The objective is simplified by removing the KL divergence term entirely, reducing it to a standard REINFORCE objective with group-normalized rewards and token-level loss:

$$\mathcal{J}_{\text{GRPO}}(\theta) = \mathbb{E}_{(q,a)\sim\mathcal{D}, \{o_i\}_{i=1}^G \sim \pi_\theta(\cdot|q)} \left[ \frac{1}{\sum_{i=1}^G |o_i|} \sum_{i=1}^G \sum_{t=1}^{|o_i|} \hat{A}_{i,t} \right]$$

where:

$$\hat{A}_{i,t} = \frac{r_i - \text{mean}(\{r_i\}_{i=1}^G)}{\text{std}(\{r_i\}_{i=1}^G)} \quad \text{for all } t$$

Here, `$q$` is a prompt drawn from the domain-specific dataset `$\mathcal{D}$`, `$a$` is the ground-truth answer (used only in RLVR stages for verification), `$G$` is the group size (number of rollouts per prompt, typically 8 or 16), `$\{o_i\}_{i=1}^G$` are `$G$` responses sampled from the current policy `$\pi_\theta$`, `$|o_i|$` is the number of tokens in response `$o_i$`, `$r_i$` is the scalar reward assigned to response `$o_i$` by the domain-specific reward function, and `$\hat{A}_{i,t}$` is the normalized advantage applied uniformly to every token in response `$o_i$`.

**What it computes:** For each prompt in a batch, the policy generates `$G$` complete responses. Each response receives a domain-specific scalar reward `$r_i$` (e.g., 1 for correct math answer, 0 for incorrect; or a continuous score from a reward model). The rewards are normalized within the group by subtracting the group mean and dividing by the group standard deviation, producing an advantage `$\hat{A}_{i,t}$` that is positive for above-average responses and negative for below-average responses. This advantage is applied uniformly to every token in the response. The total loss is the average token-level advantage over all tokens in all `$G$` responses, weighted by policy gradient. The policy gradient update increases the log-probability of tokens in high-reward responses and decreases it for tokens in low-reward responses.

**Why this form:** Removing the KL divergence term "simplifies the GRPO objective to the standard REINFORCE objective" and is justified by the strict on-policy setup — "the policy used for data collection always matches the one being updated, making the importance sampling ratio exactly 1." This eliminates the need for KL regularization because the policy cannot drift far from the reference in a single gradient step when only on-policy data is used. The token-level loss (averaging over all tokens directly, rather than averaging within each sample and then across samples) is noted as beneficial for "long-CoT RL" but can be switched to sequence-level loss if RLHF training shows instability (Section 6.3).

**On-policy training protocol.** At each iteration, the current policy `$\pi_\theta$` generates a group of `$G$` complete responses for each prompt in the batch. These responses are scored by the domain-specific reward function. A single gradient update is then performed using the GRPO objective, and the updated policy `$\pi_{\theta'}$` is used to generate rollouts for the next iteration. This is "strict on-policy" — there is no replay buffer, no importance sampling correction, and no off-policy data. The paper argues this "contributes to stable RL training and mitigates entropy collapse."

**Training configuration shared across stages.** All Cascade RL training is conducted using the verl repository (Sheng et al., 2025). The training configuration includes: AdamW optimizer, entropy loss coefficient set to 0, KL loss coefficient set to 0. Specific hyperparameters (learning rate, batch size, rollout count, temperature, response length limits, overlong filtering behavior) vary by domain and model size and are specified in each stage's subsection.

#### Why Cascade RL Resists Catastrophic Forgetting

Section 4.1.1 provides a theoretical argument for why sequential domain-wise RL does not cause the model to forget previously learned capabilities. This is a critical claim because it contradicts standard supervised learning intuition where training on task B after task A degrades performance on task A.

**Argument 1: RL data is policy-dependent.** In RL, "the training data distribution is policy-dependent; the LLM generates its own experience." When a new domain is introduced, the policy still explores across all states it has previously learned. If old behaviors remain useful (high-reward), they will continue to be sampled and reinforced. This contrasts with supervised fine-tuning, where the training samples from domain A "disappear unless explicitly replayed" when the model moves to domain B.

**Argument 2: RL optimizes expected cumulative reward, not token-level targets.** Unlike SFT where the loss explicitly tries to match a specific target distribution for each input (pushing the model away from its previous distribution), RL updates "focus on improving long-term outcomes rather than explicitly fitting a new token-level distribution." Old knowledge that remains "reward-relevant naturally persists." When new tasks share structure with old ones, "updates tend to generalize rather than overwrite."

**Argument 3: Reward structures overlap across domains.** The paper argues that the reward functions for RLHF, IF-RL, Math RL, Code RL, and SWE RL "overlap substantially across domains, since they all aim to make outputs better, more accurate, and more aligned." For example, "reducing verbosity or hallucination generally benefits all domains." This shared reward structure means that updates from a new domain often reinforce behaviors that were already rewarded by previous domains.

**Argument 4: Prompt overlap is minimized by construction.** Math and competitive programming prompts are "explicitly removed from the RLHF stage to reduce cross-domain interference." The cascade order (general to specific) further reduces the risk of specialized behaviors being overwritten by generic updates.

The paper validates this claim with comprehensive evaluation after each Cascade RL stage (Tables 2–8), showing that "subsequent domain-specific RL stages rarely degrade the benchmark performance attained in earlier domains and may even improve it" — RLHF improves math and code benchmarks, Math RL improves code and SWE benchmarks, Code RL maintains or improves math performance, and SWE RL causes minimal variance in other domains.

#### Reward Model for RLHF

The reward model (RM) is the **verifier for the RLHF stage**. Its quality directly determines the effectiveness of the cascade's foundation stage, which in turn affects all subsequent stages. The RM is described in Section 4.2.

**Data curation (82K preference pairs).** The preference dataset is a mixture of open-source and in-house data:

- **HelpSteer2 (10K pairs):** Human-annotated with multi-aspect annotations (helpfulness, correctness, coherence, complexity, verbosity).
- **HelpSteer3 (36K after filtering):** Originally 40K pairs spanning general, STEM, code, and multilingual domains, annotated with preference scores from –3 (Response 1 much better) to +3 (Response 2 much better). Samples with score 0 (similar responses) are filtered out.

The paper also generates synthetic preference data inspired by Park et al. (2024). The key insight is that preference pairs are most informative when the dispreferred response comes from a stronger model and the preferred response from a weaker one — this creates "hard" pairs where the reward model must learn subtle distinctions. The procedure: (1) DeepSeek-V3 writes an off-topic prompt by rewriting the original prompt, (2) DeepSeek-V3 (the strong model) generates a response to the off-topic prompt (a "bad" response to the original question), and (3) DeepSeek-V3-0324 (the weaker model) generates a response to the original prompt (a "good" response). The paper notes that "inducing the stronger LLM to generate bad responses is crucial for making the data effective; otherwise, the preference pairs would be too easy for the reward model to distinguish." Attempting to explicitly instruct strong LLMs to produce subtly erroneous answers "was unsuccessful."

**Training recipe.** The reward model is initialized from Qwen2.5-72B-Instruct with a linear predictor added on top of its last hidden layer. It is trained with the Bradley-Terry objective:

$$\mathcal{L}(\theta) = \mathbb{E}_{(x, y^+, y^-) \sim \mathcal{D}} \left[ \log P_{\text{BT}}(y^+ \succ y^- | x) \right]$$

where:

$$P_{\text{BT}}(y^+ \succ y^- | x) = \frac{\exp(r_\theta(x, y^+))}{\exp(r_\theta(x, y^+)) + \exp(r_\theta(x, y^-))}$$

Here, `$x$` is a prompt, `$y^+$` is the preferred response, `$y^-$` is the dispreferred response, and `$r_\theta(x, y)$` is the scalar score produced by the reward model for response `$y$` given prompt `$x$`.

**What it computes:** For each prompt, two responses (one preferred, one dispreferred) are compared. The model assigns a scalar score to each, and the Bradley-Terry probability that `$y^+$` beats `$y^-$` is the softmax of their scores. The loss maximizes the log-probability of the preferred response being ranked higher. The result is a trained model that outputs higher scores for responses that match human preferences and lower scores for responses that do not.

**Why this form:** The Bradley-Terry model is the standard statistical model for pairwise preference data, assuming that preferences satisfy Luce's choice axiom (the probability of choosing A over B depends only on the ratio of their intrinsic worth). The log-likelihood objective is convex in the score parameters, making training stable. The scalar output (rather than, say, a policy head) enables the RM to serve as a plug-in reward function in the GRPO objective where `$r_i$` is simply the RM's output for the generated response.

**RM ablation findings (Table 3):**

1. **Model size scaling:** RMs trained on Qwen2.5-Instruct at 7B, 14B, 32B, and 72B show RewardBench scores of 91.98, 93.22, 93.56, and 95.15 respectively — "performance scales positively with model size." Larger RMs are "more robust to stylistic artifacts in the preference data," while smaller RMs "tended to focus more on the style of a response rather than its overall quality."

2. **Preference pre-training:** Initializing from WorldPM (a Qwen2.5-72B further pretrained on 15M preference pairs) provides better early training but the vanilla Qwen2.5-72B-Instruct "eventually catch[es] up and slightly outperform[s] them on RewardBench" — 95.15 vs. 94.08.

3. **Reasoning vs. instruct backbone:** Qwen3-14B (thinking mode) achieves only 46.38 on RewardBench, dramatically worse than Qwen2.5-Instruct-14B at 93.22. Even in non-thinking mode, Qwen3-14B reaches only 91.72, still below Qwen2.5-Instruct-14B. The paper hypothesizes this is because "Qwen3 reasoning models are primarily optimized for reasoning-centric tasks (e.g., math and code) rather than general human preference alignment."

**RM selection for RLHF:** The paper uses RewardBench as a proxy for RM quality but notes that "the RM with the highest RewardBench score does not necessarily yield the best aligned policy model," since RewardBench can be an "imperfect proxy" and RLHF introduces additional variance. The final choice is the 72B RM trained from Qwen2.5-72B-Instruct without preference pre-training.

#### RLHF Stage

The RLHF stage is described in Section 4.3. It is the **foundation of the cascade**, serving triple duty: improving helpfulness and harmlessness, compressing reasoning traces to improve efficiency, and providing a cleaner initialization for subsequent RLVR stages.

**Data curation.** The RLHF prompt set is a subset of the prompts from the RM's preference dataset, with math and competitive programming prompts explicitly removed. The paper's early experiments revealed that "failing to exclude math-related prompts during RLHF resulted in a 2% performance drop on the AIME25 benchmark" — evidence of cross-domain interference when reward model scores (which lack the precision of rule-based math verification) are used on math tasks. The resulting dataset focuses on helpfulness, harmlessness, and alignment with human preferences.

**Training recipe.** RLHF initializes from the SFT checkpoint and uses the same GRPO objective and on-policy protocol described in Section 4.1.2. For dedicated thinking models, RLHF is performed in thinking mode. For unified models, RLHF operates in both non-thinking and thinking modes, with "an equal split of prompts allocated to each mode within every batch" — the "Half-Half" strategy that Section 6.1 demonstrates is superior to training in either mode alone (Figure 9).

**Reward function.** The reward for each generated response is the scalar output of the 72B RM. The response is extracted differently for each mode:

- **Non-thinking mode:** The model's answer after the `assistant` role marker is directly concatenated with the question and fed to the RM.
- **Thinking mode:** The reasoning trace (everything before the `<\think>` token) is excluded; only the final summary after the `<\think>` token is sent to the RM.
- **Fallback:** If the thinking process does not terminate properly (missing `<\think>` token), the entire unfinished response is sent to the RM. Such incomplete generations typically receive low scores because "the reward model was not trained on unfinished or unseen reasoning traces."

**Code-switch penalty.** When the prompt is purely in English but the generated response (including thinking traces) contains non-English tokens, the reward is adaptively set to "the lowest score in the batch minus 10." Under the group-normalized GRPO advantage, this becomes the lowest relative score, providing the strongest possible penalty for language mixing.

**Hyperparameters.** Max response length is set to 12K tokens for both 8B and 14B models. Overlong filtering is disabled ("without applying overlong filtering, which effectively encourages more succinct generations"). Batch size is 128 (or 256 depending on table — the paper reports 128 in Section 4.3.2 text and 256 in Table 15; the text description is more authoritative), generating `$G=8$` rollouts per prompt. Sampling uses temperature 0.6 and top-p 0.95. Learning rate is 2e-6 with AdamW. Both entropy loss and KL loss coefficients are set to 0. Training runs for approximately 800 steps (8B) and 900 steps (14B).

**Design choice: no KL penalty for 72B RM.** Section 6.3 provides an ablation showing that with the 7B RM, RLHF training collapses early without KL regularization, sequence-level loss aggregation, and reward shaping. However, with the 72B RM, "RLHF training is already stable, and omitting these techniques yields comparable—and in some cases slightly better—downstream performance" (Table 11). The paper's recommendation is that the "bag of tricks" should be deployed "only when training shows signs of instability."

**Why 12K max length without overlong filtering:** The short budget (12K vs. the 64K used at evaluation) deliberately penalizes verbosity. By not filtering overlong responses (which would give them zero reward and exclude them from the gradient), the model still sees the penalty through the reward model scoring incomplete or verbose responses poorly. This "effectively encourages more succinct generations" while avoiding the training instability that overlong filtering can cause when too many samples are excluded.

**Results after RLHF (Table 4).** RLHF produces dramatic improvements on ArenaHard (from ~72 to ~90 for 8B-Thinking, from ~77 to ~93 for 14B-Thinking), substantial gains on AIME (from ~84 to ~86 for 8B, ~87 to ~88 for 14B), and significant jumps on LiveCodeBench (from ~60 to ~70 for 8B, ~66 to ~75 for 14B). The only degradation is on IFEval, which drops from ~66–71 to ~46–56 — the paper attributes this to "unavoidable semantic overlap between the prompts used during RLHF training and the test prompts in IFEval" and to the RM encouraging response qualities that "can conflict with the strict instruction-following constraints." IF-RL is designed to recover this degradation.

#### Instruction-Following RL (IF-RL) Stage

The IF-RL stage is described in Section 4.4. It addresses the IFEval degradation from RLHF while attempting to minimize damage to the alignment gains (ArenaHard).

**Data curation.** The dataset starts with 56K synthetically generated prompts from Llama-Nemotron, each containing 1–10 instruction constraints from the IFEval taxonomy, reduced to 40K after "extensive preprocessing and filtering" to remove noise. An additional 60K custom samples are curated by pairing user prompts from LMSYS-Chat-1M with instruction constraints from the IFEval taxonomy. Finally, the IF-RLVR training data from Pyatkin et al. (2025) is incorporated, which pairs prompts with constraints from either the IFEval or IF-Bench-Train taxonomy to enhance robustness to unseen constraint types.

**Two-stage curriculum.** The first stage focuses on IFEval taxonomy constraints. The second stage focuses on IF-Bench-Train taxonomy constraints (58 new constraint types unseen during first-stage training, testing generalization).

**Reward function design — the core challenge.** A naive approach using only the binary IF verifier causes the model to reward-hack: producing responses that satisfy instruction constraints but are low-quality (e.g., a poorly written summary that happens to be under 300 words gets full reward). This degrades ArenaHard scores.

The paper develops two different solutions depending on the model type:

**For unified models: IF-RL in non-thinking mode only.** The unified model first undergoes RLHF in both thinking and non-thinking modes, then IF-RL is applied only in the non-thinking mode. The paper's hypothesis is that "applying IF-RL to an RLHF-trained model in the non-thinking mode is far less likely to generate low-quality responses than applying it in the thinking mode, and therefore is much less prone to reward-hacking the rule-based IF verifier." This strategy "minimizes negative mutual interference between RLHF and IF-RL, while still yielding substantial improvements in the model's instruction-following capability in the thinking mode" — the 8B unified model achieves IFEval 85.3 in thinking mode despite IF-RL training only in non-thinking mode.

**For dedicated thinking models: combined reward function.** The reward for response `$o_i$` given prompt `$q$` is:

$$r_i = \begin{cases} R_{\text{IF}}(o_i) + \text{sigmoid}(\hat{R}_{\text{RM}}(o_i)) & \text{if } R_{\text{IF}}(o_i) = 1 \\ 0 & \text{otherwise} \end{cases}$$

where:

$$\hat{R}_{\text{RM}}(o_i) = \frac{R_{\text{RM}}(o_i) - \text{mean}(\{R_{\text{RM}}(o_i)\}_{i=1}^G)}{\text{std}(\{R_{\text{RM}}(o_i)\}_{i=1}^G)}$$

Here, `$R_{\text{IF}}(o_i) \in \{0, 1\}$` is the binary reward from the instruction-following verifier (1 if all constraints are satisfied, 0 otherwise), `$R_{\text{RM}}(o_i)$` is the scalar score from the same 72B RM used in RLHF, `$\hat{R}_{\text{RM}}$` is the group-normalized RM score (mean 0, std 1), and `$\text{sigmoid}(\cdot)$` scales the normalized score to (0, 1).

**What it computes:** If the response fails any instruction constraint, the reward is exactly 0 — no amount of response quality can compensate. If all constraints are satisfied, the reward is 1 + a quality bonus between 0 and 1 from the reward model, after normalizing within the group so the bonus is relative to other constraint-satisfying responses in the same batch. This ensures that among responses that all satisfy the constraints, the model still prefers higher-quality ones.

**Why this form:** The additive combination with sigmoid scaling puts the RM bonus on the same scale as the binary IF reward, preventing the RLHF signal from dominating. The gating by `$R_{\text{IF}}(o_i) = 1$` ensures the model cannot trade off instruction following for quality. The group normalization of `$\hat{R}_{\text{RM}}$` prevents batch-to-batch scale differences from affecting the relative importance of the RM bonus.

**Training hyperparameters.** Batch size 128 (or 256 — Table 16 reports 256; the text discusses 128 for the unified models' first stage, which takes ~2000 steps, and second stage takes ~800 steps), 8 rollouts per prompt. Sampling uses temperature 0.6, top-p 0.95, top-k 20. Learning rate is 2e-6 with AdamW. For unified models in non-thinking mode: max response length 8K for both stages, no overlong filtering. For dedicated thinking models: max response length 8K with overlong filtering in stage 1, extended to 16K with overlong filtering in stage 2 (to accommodate longer reasoning for difficult prompts). Stage 1 training runs ~500–550 steps for thinking models, stage 2 runs ~120–300 steps.

**Dynamic filtering.** The paper notes that dynamic filtering (removing prompts where all rollouts succeed or all fail) "largely stabilizes the IF-RL training and improves the results at both stages by ensuring all prompts in the batch with effective gradients."

**Results after IF-RL (Table 5).** IFEval recovers dramatically from the RLHF drop — from ~46 to ~83 for 8B-Thinking, from ~50 to ~90 for 8B-unified, from ~56 to ~81 for 14B-Thinking. IFBench also surges (from ~24–26 to ~40–42). ArenaHard degrades modestly (from ~90 to ~86 for 8B-Thinking, ~90 to ~88 for 8B-unified, ~93 to ~90 for 14B-Thinking) — the paper considers this acceptable given the IFEval gains and notes that "IF-RL generally reduces model entropy and shortens the average length of reasoning tokens" which "on the positive side, compresses the reasoning trace and improves token efficiency." Reasoning benchmarks (AIME, LiveCodeBench) show minor degradation (0.5–3 points), but the paper notes "most of them (except ArenaHard) are fully recoverable and are further improved after the subsequent Math RL, Code RL, and SWE RL stages."

#### Math RL Stage

The Math RL stage is described in Section 4.5. It enhances mathematical reasoning through three stages of length-extended RL training with symbolic verification.

**Data curation (18K problems after filtering).** The base dataset is the AceReason-Math corpus, which merges DeepScaleR blend and NuminaMath, covering algebra, geometry, combinatorics, and number theory. The filtering process is extensive:

1. Apply 9-gram decontamination against AIME 2024/2025 and MATH benchmarks.
2. Exclude questions unsuitable for rule-based verification: multiple-choice/true-false questions (answers can be guessed), proof-based problems (difficult to verify), problems with multiple sub-questions, non-English problems, and problems referencing figures.
3. Verify each problem using DeepSeek-R1 with up to 8 attempts; retain only problems where majority-voted answers are correct according to a rule-based verifier.
4. Remove overly simple problems that AceReason-Nemotron-7B can solve with ≥75% success rate over 16 samples, reducing from 49K to 14K problems from the filtered subset. The final dataset has 18K problems total after including additional sources.

**Reward function.** Rewards are binary: 1 if the extracted boxed answer (`\boxed{}`) matches the ground truth according to the AceMath rule-based verifier, 0 otherwise. An additional code-switching penalty assigns a reward of "−1 whenever tokens from a language (e.g., Chinese) different from the original prompt's language (e.g., English) are detected in the reasoning chain."

**Initialization from RLHF.** The paper emphasizes that "initializing Math RL from RLHF-trained models is highly beneficial." The reasons: (i) RLHF provides "a much stronger initial math reasoning capability than SFT checkpoints" with substantially improved response quality and token efficiency (less verbosity, less repetition), and (ii) it "significantly reduces the number of steps required for math RL training." The paper validated this recipe on "five different 8B checkpoints and consistently achieved accuracies of around 90% on AIME24 within 500 RL steps."

**Three-stage length extension curriculum.** The core driver of math RL improvement is the model's ability to produce longer, more thorough reasoning chains. The curriculum compresses, stabilizes, then extends:

- **Stage 1: 24K (Compression Stage).** SFT checkpoints for small/medium models "tend to generate overlong reasoning chains, leading to incomplete ratios of 15–20% on the AIME benchmark under a 32K token budget." Starting with 24K forces the model to compress and refine its reasoning. Overlong filtering is applied — "we skip generations exceeding 24K tokens rather than assigning a reward of 0, as doing so may excessively penalize long reasoning on difficult problems, causing a sharp performance drop." Models start with 30–50% incomplete ratios that drop to ~15% after ~100 steps.

- **Stage 2: 32K (Extension Stage).** The token budget is extended to 32K. Overlong filtering is disabled — models assign reward 0 to overlong generations instead, which "regularize[s] reasoning length to fit the 32K context." Checkpoints from Stage 1 vary in efficiency (5–10% incomplete ratios), so this stage serves as controlled adaptation to the larger budget.

- **Stage 3: 40K (Long Reasoning Stage).** After 32K training, easy/medium AIME problems "nearly saturate" (99% and 85% respectively), but hard problems plateau below 30%. Since evaluation uses 64K tokens (with YaRN scaling factor 2), the model is "not fully exploiting the available context." The 40K stage "explicitly incentivizes the model to leverage more tokens during reasoning," improving hard-problem accuracy from ~30% to ~40%.

**For 14B models:** The initial policy already achieves high accuracy, so the curriculum starts at 28K to avoid accuracy drop, then extends directly to 40K.

**Dynamic filtering (epoch-based).** After each epoch, problems achieving 100% or 0% accuracy are filtered out because they "provide no useful policy gradient signal when using the group-normalized advantage function." Hard problems (0% accuracy) are re-sampled with 10% probability, as the policy may learn to solve them within the epoch. Easy problems (100% accuracy) are re-sampled with 1% probability to stabilize training and prevent forgetting. This "ensures that ~90% of training samples contribute meaningful learning signals and significantly stabilizes model accuracy during training, especially at later training stages." The choice of epoch-based filtering over batch-based dynamic sampling (Xiaomi et al., 2025; Yu et al., 2025) is motivated by efficiency: batch-based filtering "requires substantially more rollouts to construct a fixed-size batch free of overly simple or unsolvable prompts."

**Hyperparameters.** Batch size 128, 8 rollouts per prompt, learning rate 2 or 2.5 × 10⁻⁶ with AdamW. Stage 1: temperature 1, top-p 0.95, overlong filtering enabled, ~190 steps (8B) or ~120 steps (14B). Stage 2: temperature 1, top-p 0.95, overlong filtering disabled, ~240 steps (8B) or ~100 steps (14B). Stage 3 (8B only): temperature 0.8, overlong filtering disabled, ~70 steps. For 14B, Stage 1 uses temperature 1.2, Stage 2 uses temperature 1.1.

**Training dynamics (Figure 4).** The 8B unified model's AIME24 accuracy rises from ~86% to ~90% over 500 steps, while AIME25 accuracy rises from ~74% to ~82%. The curve shows characteristic RL behavior: rapid initial improvement, followed by gradual, noisier gains as the policy explores harder problems.

**Results after Math RL (Table 6).** AIME 2024 improves from ~86 to ~90 for 8B models, from ~89 to ~90 for 14B. AIME 2025 improves from ~72–75 to ~80–82 for 8B, from ~82 to ~83 for 14B. LiveCodeBench shows modest gains (1–2 points). SWE-bench Verified improves slightly (30.2 → 30.6 for 8B unified, 39.7 → 39.7 for 14B). Most other benchmarks show changes within evaluation variance. The paper notes that while the code benchmark improvements are "not as pronounced as those reported in AceReason-Nemotron, this is largely because our starting models already exhibit strong general reasoning capabilities prior to Math RL."

#### Code RL Stage

The Code RL stage is described in Section 4.6. It improves competitive programming performance through execution-based verification.

**Data curation (9.8K problems).** The dataset is based on the AceReason-Nemotron coding corpus from open-source sources with unit tests (TACO, APPS, DeepCoder, and others). Three filtering steps are applied:

1. Remove problems incompatible with standard output comparison (interactive formats, special judges) and those with insufficient unit test coverage for edge cases — this "substantially reduces false-positive and false-negative reward signals during training, which are known to degrade Code RL performance."
2. Remove duplicates and prevent benchmark contamination using 9-gram filtering and raw problem URL matching.
3. Calibrate difficulty by excluding trivial problems solved by AceReason-Nemotron-7B in all 8 of 8 rollouts and intractable problems unsolved by DeepSeek-R1-0528 in all 8 rollouts, resulting in 9.8K training samples.

**Why after Math RL:** Math RL "serves as an effective warm-up that stabilizes future RL training and enhances the model's general reasoning capabilities," consistent with the AceReason-Nemotron finding that math RL improves both math and code benchmarks.

**Reward function.** Binary: 1 if the generated code passes all test cases for the problem, 0 otherwise. Verification uses the parallelized code verifier from the AceReason Evaluation Toolkit. Asynchronous reward computation is employed because "code verification incurs significant overhead" — with 8 DGX H100 nodes, batch size 128, rollout 8, asynchronous computation reduces verification time from 1172.4 seconds to 416.2 seconds per batch.

**Code-switching penalty.** Unlike Math RL where code-switching receives reward −1, Code RL assigns reward 0 for code-switching. The paper found that "assigning a reward of −1 for code-switching negatively impacts coding performance. This is likely because the additional penalty encourages the model to produce incorrect answers without code-switching in GRPO training when all rollouts in the group are either incorrect or contain language mixing."

**Training recipe.** Single-stage, on-policy Code RL initialized from the final Math-RL checkpoint. Max response length is 44K (8B-Thinking), 44K→48K (8B unified, with the extension during training), or 56K (14B-Thinking). Overlong filtering is disabled. Batch size 128, 8 rollouts, learning rate 4 × 10⁻⁶ with AdamW. Temperature is noted as a critical hyperparameter — Section 5.2 shows that training with temperature 1.0 yields better accuracy than 0.6 or 0.8, but "may suffer from training instability" due to entropy explosion (Figure 6). The 8B-Thinking model uses temperature 1.2, the 8B unified model uses temperature 1.0 → 0.8, and the 14B model uses temperature 1.0. Training runs for ~64–90 steps.

**Design choice: higher temperature for code versus math.** Code generation has a "large, noisy sampling space" where "higher temperatures encourage exploration and improve sample efficiency under limited rollout budgets." Math RL can use lower temperatures because the answer space is more constrained — once the correct reasoning chain is found, the answer is deterministic.

**Results after Code RL (Table 7).** LiveCodeBench v5 improves from ~71–75 to ~74–78. LCB v6 improves from ~67–72 to ~71–75. The 8B unified model reaches 75.3 on LCB v5 and 71.5 on LCB v6, "matching the performance of DeepSeek-R1-0528 (671B), which achieves 74.8 and 73.3, respectively." The 14B-Thinking reaches 78.0 and 74.8, "outperforming DeepSeek-R1-0528 by a clear margin." AIME 2024 shows minor fluctuations (~89 for 8B, ~90 for 14B), AIME 2025 shows slight improvement for 8B-Thinking (~82) and stable for 14B (~84). IFEval shows a 1–2 point drop attributed to checkpoint variance.

**Topic-wise analysis (Figure 7).** Code RL provides the largest accuracy boost across all five code sub-categories (Math, String, Graph, Data Structure, Geometry), with particularly strong gains on String and Data Structure problems — topics that Math RL barely improved.

#### SWE RL Stage

The SWE RL stage is described in Section 4.7. It is the most complex stage, involving a novel execution-free reward model and a two-stage input context extension curriculum.

**Data curation for RL.** The SWE RL dataset consists of code repair instances that are more challenging than those used in SFT — specifically, instances where fewer than 4 of 8 DeepSeek-R1-0528 responses exceeded the 0.5 Unidiff similarity threshold but at least 1 response achieved non-zero similarity (indicating the problem is solvable but hard). The prompts are constructed with two variants:

1. **Ground-truth only:** Similar to SFT, prompts include only the ground-truth files that contain bugs or require modification.
2. **Mixed localization:** Prompts include both files localized by DeepSeek-R1-0528 and ground-truth files, up to 5 files total. Ground-truth files are guaranteed to be present. Noisy files are added incrementally until the total prompt length would exceed a threshold `$l$`. If adding any noisy file exceeds the threshold, the instance is discarded. File order is randomized.

To handle the out-of-distribution input lengths (the SFT model was trained with max 32K total sequence length but evaluation requires up to 60K tokens with YaRN scaling factor 3), both subsets discard prompts shorter than 8K tokens.

**Two-stage input context extension curriculum.** Preliminary experiments revealed a "strong positive correlation between input context length and SWE task performance" but also that "directly initializing training with a 24K context length leads to suboptimal convergence and degraded final performance," attributed to "the model's initial difficulty in attending to and synthesizing information across extended sequences."

- **Stage 1: 16K input context (warmup).** The model learns "fundamental long-context utilization skills and develops stable attention mechanisms for multi-file analysis within a manageable context window." Training continues until the reward plateaus.
- **Stage 2: 24K context extension.** Once the 16K setup reaches diminishing returns, the context is extended to 24K. The model demonstrates "more advanced cross-file reasoning and improved synthesis of information across retrieved files."

For the final 8B models, the two-stage curriculum uses 16K→24K. For the 14B model, a single stage at 32K is used (the base model has stronger long-context capability).

**Reward function — execution-free similarity.** The core innovation is a reward function that does not require executing code patches in Docker containers, which "significantly limits scalability, constraining prior work to training datasets of around 10k unique instances." The reward `$r$` for a generated patch `$\hat{p}$` given a golden patch `$p^*$` is:

$$r(\hat{p}, p^*) = \begin{cases} 1 & \text{if } s_{\text{lex}}(\hat{p}, p^*) = 1 \\ 0 & \text{if } \hat{p} \text{ is identical to the original code snippet} \\ -1 & \text{if } \hat{p} \text{ cannot be parsed} \\ s_{\text{sem}}(\hat{p}, p^*) & \text{otherwise} \end{cases}$$

where `$s_{\text{lex}}(\hat{p}, p^*)$` is lexical similarity computed with the Unidiff library (following Wei et al., 2025), and `$s_{\text{sem}}(\hat{p}, p^*)$` is the semantic similarity score from the Kimi-Dev-72B model, obtained by prompting it with a yes/no question about whether the generated patch successfully resolves the issue, and using the probability assigned to the "YES" token as the reward score.

**What it computes:** If the generated patch is lexically identical to the golden patch, reward is 1 (maximum). If the patch is identical to the original buggy code (no change), reward is 0 (the model made no attempt). If the patch cannot be parsed, reward is −1 (invalid output). Otherwise, the Kimi-Dev-72B model evaluates the semantic equivalence of the generated and golden patches, outputting a probability between 0 and 1 that serves as a continuous reward signal.

**Why this form:** The tiered structure provides clear gradient signals: −1 strongly penalizes unparseable output (a common failure mode in early training), 0 penalizes no-change outputs, 1 provides a strong positive signal for exact matches, and the continuous semantic similarity provides a smooth training signal for partially correct patches. The choice of an LLM-based semantic scorer over pure lexical similarity is validated by ablation (Table 12, cond. 4 vs. cond. 2): semantic similarity yields higher resolve rates (43.0% vs. 42.6% with ground-truth localization, 42.3% vs. 41.2% with top-4 localization).

**Reward shaping ablation.** Adding reward shaping (setting rewards below 0.5 to 0) helps lexical similarity (cond. 2 vs. cond. 1 in Table 12: 42.8% vs. 42.6% with ground-truth localization) but does not help semantic similarity (cond. 4 vs. cond. 3: 42.9% vs. 43.0%), suggesting "semantic similarity continues to provide meaningful training signals even when code similarity is low." The paper defaults to the unshaped semantic similarity reward (cond. 3).

**Hyperparameters.** Batch size 128, 16 rollouts per prompt (higher than other stages to compensate for the noise in the execution-free reward signal), learning rate 2.5 × 10⁻⁶ with AdamW. Sampling uses temperature 1 and top-p 0.95. Max response length is 16K output tokens. Stage 1 (16K input) runs ~30 steps with overlong filtering. Stage 2 (24K input) runs ~30 steps. For 14B (single stage at 32K input), training runs ~120 steps with overlong filtering (Table 20).

**Ablation on input context length (Table 13).** Training with longer prompts improves repair capability: with top-4 localization, 16K prompts yield 41.6% avg@4, 24K yields 42.3%, 32K yields 42.7%. However, 40K drops to 41.5% — the paper hypothesizes that "the pretrained Qwen3-14B-Base has limited long-context capability at 32K" or that longer prompts introduce noise into the RL training. The final models use 24K max prompt length for 8B and 32K for 14B.

**Results after SWE RL (Table 8).** SWE-bench Verified resolve rate improves substantially: 8B-Thinking from 33.3% (after Code RL) to 38.5%, 8B unified from 31.6% to 37.2%, 14B-Thinking from 39.6% to 43.1%. The paper highlights that the 14B-Thinking's 43.1% "already outperforming the recent open 32B specialized models, DeepSWE-32B (42.2) and SWE-agent-LM-32B (40.2)." All other benchmarks show minor fluctuations (within 1–2 points) attributed to evaluation and checkpoint variance. The gap between the unified 8B and dedicated 8B-Thinking on SWE-bench Verified (26.1 vs. 30.2 after SFT) is "largely mitigated after the full Cascade RL process (37.2 vs. 38.5)."

#### Agentless Framework for SWE Evaluation

The SWE task is decomposed into three sub-tasks, described in Section 3.3.1:

**1. Code localization.** Given a problem statement and repository structure, identify the files likely to contain bugs. The paper uses a dual approach combining generation and retrieval:

- **Generation-based:** The model is prompted with the problem description and the repository's folder/file structure (not file contents). For evaluation, results from 16 rollouts are aggregated, and candidate files are ranked by frequency of appearance.
- **Retrieval-based:** An embedding model (NV-Embed-Code, 7B) encodes the problem description and retrieves files whose code contents are semantically similar.
- **Fusion:** The two ranked lists are combined using reciprocal rank fusion with hyperparameter `$k=0$`.

Localization performance (Figure 11): retrieval alone outperforms generation alone at all cutoffs. Generation with 16 rollouts + retrieval fusion achieves the best performance, reaching ~89% recall at top-8 cutoff for the 14B-Thinking model.

**2. Code repair.** Given the problem statement and contents of localized files, the model generates diff-style patches. The prompt concatenates multiple localized files and surrounding code snippets into a unified context, enabling cross-file reasoning. The model produces SEARCH/REPLACE edits in a structured format (<<<<<<< SEARCH, =======, >>>>>>> REPLACE).

**3. Patch validation.** Three-phase process:
- **Regression phase:** Candidate patches are tested against the repository's existing regression tests to filter out patches that break previously working functionality.
- **Reproduction phase:** The framework generates 10 reproduction tests per instance to verify the bug exists before patching and is resolved after patching. Tests that fail to trigger the original bug are discarded.
- **Majority voting phase:** Among the highest-scoring candidates, the most frequently generated patch is selected. Ties are broken by preferring shorter generation sequences or minimal edit distance.

**Test-time scaling (Section 7.4, Figure 12).** The model generates `$k$` candidate repair patches and 40 reproduction tests. The `best@k` selection procedure ranks candidates by: (1) number of regression tests passed, then (2) number of reproduction tests passed. The selected patch is the one with the highest combined pass rate, with ties resolved by majority voting and then minimum solution length. For 14B-Thinking, `best@32` achieves 53.8% resolve rate on SWE-bench Verified, a substantial improvement over pass@1's 43.1%. The `pass@k` curve continues to rise at `$k=32$` (reaching 67.0%), suggesting further test-time scaling headroom. The gap between `pass@k` and `best@k` (67.0% vs. 53.8% at `$k=32$`) indicates that "downstream filtering and validation remain powerful mechanisms for boosting patch-repair performance without modifying model weights," but also that improved selection procedures could close this gap.

#### Summary of Key Design Choices

**Why sequential RL over joint RL:** Joint blended RL training creates incompatible demands — math verification is milliseconds, code verification is minutes; RLHF penalizes verbosity, math RL rewards extended reasoning; SWE RL needs long input contexts, IF-RL needs short, constrained outputs. Sequential training allows each domain's hyperparameters, verification method, and curriculum to be tailored independently, and the cascade order (general→specific) prevents overfitting to narrow domains.

**Why RLHF first:** RLHF with a 72B RM substantially improves response quality and reduces verbosity, providing a cleaner, more efficient policy initialization that reduces the steps needed for subsequent RLVR stages. The paper's early experiments with RLHF after RLVR produced worse results.

**Why no KL penalty:** With strict on-policy training (each batch uses rollouts from the current policy only) and a large, high-quality RM (72B), the policy cannot drift far enough in a single update to cause instability. KL regularization becomes unnecessary overhead that can inhibit the exploration needed for long chain-of-thought reasoning.

**Why execution-free SWE reward:** Docker-based patch execution is a scalability bottleneck, limiting prior work to ~10K training instances. The LLM-based semantic similarity scorer enables training on larger, more diverse datasets without infrastructure constraints. The ablation in Table 12 confirms that semantic similarity provides effective training signals.

**Why staged length extension for Math RL:** The 24K→32K→40K curriculum addresses three distinct problems: (1) SFT models overgenerate, so 24K forces compression; (2) compressed models need controlled adaptation to larger budgets; (3) saturating performance on easy/medium problems requires explicit incentivization to use more tokens for hard problems.

**Why 16-rollout for SWE RL versus 8-rollout for other stages:** The execution-free reward is noisier than binary execution-based or symbolic verification. More rollouts per prompt provide better group normalization and more reliable advantage estimates, compensating for the reward noise.

## 4. Key Insights and Innovations

### Innovation 1: Sequential Domain-Wise RL as a First-Class Training Paradigm

The dominant assumption in post-training reasoning models — as practiced by DeepSeek-R1 (Guo et al., 2025) and Qwen3 (Yang et al., 2025) — is that RL training across domains should be conducted *jointly*, with a blended prompt distribution and a unified training configuration. This approach is conceptually simple but creates a fundamental engineering tension: the same hyperparameters (learning rate, response length budget, temperature, overlong filtering behavior) must simultaneously serve domains with radically different characteristics. Math verification runs in milliseconds, code verification runs in seconds to minutes, and SWE verification requires managing Docker containers. RLHF uses unbounded scalar reward model outputs while RLVR uses binary pass/fail signals. The training infrastructure must bottleneck on the slowest verification step, and curriculum choices — such as when to extend maximum response length — become one-size-fits-all compromises.

Cascade RL reframes this problem by treating domain-wise decomposition not as a hack but as a *first-class training paradigm* with its own theoretical justification. The key conceptual move is the argument (Section 4.1.1) that catastrophic forgetting — the standard objection to sequential training — does not apply to LLM RL in the way it applies to supervised learning. In supervised fine-tuning, training on domain B after domain A overwrites the model's ability to perform well on A because the training data for A disappears. In RL, the model generates its own training data through exploration. If behaviors learned in domain A remain useful (high-reward) in the presence of domain B's reward structure, they will continue to be sampled and reinforced. The reward structures of all domains share a common goal — making outputs "better, more accurate, and more aligned" — so updates tend to generalize rather than overwrite.

This reframing is supported by a concrete empirical finding that runs counter to the joint-training default: RLHF, when applied *first* rather than as a final alignment step, directly improves reasoning performance on math and code benchmarks (Table 4 — AIME 2024 improving from ~84% to ~86% for 8B after RLHF, LiveCodeBench v5 improving from ~60% to ~70%). This is not merely alignment staying out of the way — it is alignment *helping* reasoning, because RLHF penalizes verbosity and repetition, compressing reasoning traces and providing a cleaner, more efficient policy initialization for subsequent RLVR stages. The paper's claim that this "significantly reduces the number of steps required for math RL training" (Section 4.5.2) is a direct consequence of the sequential paradigm.

What distinguishes this from an incremental engineering improvement is the *falsifiability* of the central claim. If catastrophic forgetting were a real concern for cascaded LLM RL, we would expect to see progressive degradation on earlier-domain benchmarks as the cascade proceeds. The paper's comprehensive stage-by-stage evaluation (Tables 2 through 8) provides a direct test: each table reports results on *all* benchmarks after each RL stage, not just the domain being trained. Across five RL stages and dozens of benchmarks spanning knowledge reasoning, alignment, math, code, and software engineering, the dominant pattern is stability or improvement in previously-trained domains, with occasional small fluctuations attributed to "checkpoint and evaluation variance." The 8B unified model's AIME 2024 accuracy goes from 83.6% (SFT) to 86.1% (RLHF) to 86.2% (IF-RL) to 90.2% (Math RL) to 89.1% (Code RL) to 89.5% (SWE RL) — Math RL does the heavy lifting, and subsequent stages preserve the gains. SWE-bench Verified goes from 26.1% (SFT) to 28.2% (RLHF) to 28.3% (IF-RL) to 30.6% (Math RL) to 31.6% (Code RL) to 37.2% (SWE RL) — earlier RLVR stages modestly improve SWE performance before the dedicated SWE RL stage provides the large jump.

The significance of this finding extends beyond this paper. If sequential domain-wise RL genuinely avoids catastrophic forgetting in the LLM context, then the entire post-training pipeline can be modularized — different teams can work on different RL stages independently, stages can be reordered or swapped without retraining from scratch, and new domains can be added to the end of an existing pipeline without retraining earlier stages. This is a fundamentally more scalable approach to building general-purpose models than the "blend everything and train jointly" paradigm. The paper's commitment to releasing "the full collection of models and training data" makes this hypothesis directly testable by the community.

### Innovation 2: Unified Thinking/Instruct Without Compromise — The "Half-Half" RLHF Strategy

A persistent challenge in the LLM community, documented explicitly in the paper (Section 1), is that unified reasoning models — models that can operate in both thinking and non-thinking modes — consistently underperform dedicated thinking-only models on reasoning benchmarks when evaluated in thinking mode. Qwen3 "was later reverted to separate thinking and instruct variants, with the dedicated thinking models significantly outperforming the unified models in thinking mode." GPT-5 resorted to routing between two specialized models rather than achieving true unification. The implicit assumption in the community has been that there is a fundamental capacity trade-off: training a model to handle both thinking and non-thinking generation dilutes its ability to do either well, particularly for smaller models (8B parameters) where capacity is more constrained.

The paper directly challenges this assumption and provides a concrete mechanism that closes the gap. The key insight, demonstrated in Section 6.1 (Figure 9), is that the *mode allocation strategy during RLHF* is the critical variable. The paper compares three strategies for training the unified 8B model with the 72B reward model:

- **Non-thinking only:** RLHF trains the model to generate in non-thinking mode exclusively.
- **Thinking only:** RLHF trains the model to generate in thinking mode exclusively.
- **Half-Half:** Each batch contains an equal split of prompts allocated to non-thinking and thinking modes.

The result is striking: despite ArenaHard, AIME, and LiveCodeBench all being evaluated in thinking mode, the Half-Half strategy produces the *strongest* thinking-mode performance on all three benchmarks. Training in thinking mode alone produces worse thinking-mode results than training with half non-thinking data. The paper's interpretation is that "including samples in the non-thinking mode during RLHF can improve cross-mode transfer and alignment, leading to stronger general capabilities across both reasoning and non-reasoning settings."

This finding is reinforced by the IF-RL design choice for unified models: applying IF-RL only in non-thinking mode (Section 4.4.2) actually improves instruction-following capability in thinking mode (the 8B unified model achieves IFEval 85.3 in thinking mode without any thinking-mode IF-RL training). The mechanism appears to be that non-thinking mode training provides a regularization effect — it prevents the model from overfitting to reasoning-trace patterns and encourages it to learn general capabilities that transfer across modes.

The significance of this finding is not primarily about RLHF — it is about the *relationship between generation modes* in unified models. The paper demonstrates that thinking and non-thinking capabilities are not in zero-sum competition for model capacity. Instead, training them jointly with the right allocation strategy produces a model that outperforms single-mode training even on the mode you care about. This runs counter to the intuition that led to the Qwen3 reversal and GPT-5 routing decisions, and it provides a concrete, replicable mechanism (Half-Half batch allocation) that other unified model efforts can adopt directly.

The evidence for the claim that the gap is truly closed comes from the final comparison between the unified 8B model and the dedicated 8B-Thinking model (Table 8). After the full Cascade RL pipeline, the unified model achieves: AIME 2024 89.5% vs. 89.7% (gap of 0.2 points), AIME 2025 80.1% vs. 81.4% (gap of 1.3 points), LiveCodeBench v5 74.3% vs. 74.5% (gap of 0.2 points), LiveCodeBench v6 71.1% vs. 71.4% (gap of 0.3 points), SWE-bench Verified 37.2% vs. 38.5% (gap of 1.3 points). These differences are within the range of evaluation variance, and the unified model substantially outperforms the dedicated thinking model on IFEval (90.2% vs. 83.7%). The "capacity trade-off" assumption is empirically falsified at the 8B scale.

### Innovation 3: Execution-Free Reward for Scaling SWE RL

Software engineering RL — training models to generate code patches that fix real-world GitHub issues — has been bottlenecked by the cost and complexity of execution-based verification. Prior work (Jain et al., 2025; Luo et al., 2025) requires running model-generated patches inside Docker containers against test suites, which "significantly limits scalability, constraining prior work to training datasets of around 10k unique instances." Every rollout generation must wait for Docker setup, environment configuration, test execution, and teardown — a process that can take minutes per sample and requires managing container orchestration across GPU clusters.

The paper's conceptual contribution is demonstrating that an *LLM-based semantic similarity scorer* can serve as an effective substitute for execution-based verification in code repair RL training. The reward function (Section 4.7.2) prompts Kimi-Dev-72B with the problem statement, the golden patch, and the model's generated patch, and uses the probability assigned to the "YES" token (indicating the generated patch successfully resolves the issue) as a continuous reward signal. This is not merely a computational convenience — it represents a claim about the nature of the training signal needed for SWE RL. The paper argues that *semantic equivalence to a reference solution* provides sufficient gradient information, even without verifying functional correctness through execution.

The evidence supporting this claim comes from the ablation in Table 12. When comparing execution-free semantic similarity rewards against lexical (Unidiff-based) similarity rewards, the semantic similarity reward produces better performance (43.0% vs. 42.6% resolve rate with ground-truth localization, 42.3% vs. 41.2% with top-4 localization), and critically, does not benefit from reward shaping below 0.5 — suggesting that "semantic similarity continues to provide meaningful training signals even when code similarity is low." The lexical similarity reward, by contrast, improves when low-similarity rewards are zeroed out (42.8% with shaping vs. 42.6% without), indicating that lexical similarity below 0.5 provides noisy or misleading signals.

What makes this finding significant is its implications for scaling. If execution-free reward models can match or exceed the training effectiveness of execution-based verification, the scaling bottleneck disappears. SWE RL can be trained on datasets orders of magnitude larger than the ~10K instances currently feasible with Docker-based approaches. The paper does not claim that execution-free rewards are *better* than execution-based verification — the ablation does not compare against execution-based rewards directly — but it establishes that they are *sufficient* for effective training, which opens a path to scaling SWE RL far beyond current constraints.

The paper also implicitly demonstrates that the reward model does not need to be the policy model. The Kimi-Dev-72B scorer is a separate, frozen model — the policy (Qwen3-8B/14B) never sees the reward model's weights. This decoupling means the reward model can be arbitrarily large and compute-intensive without affecting training throughput for the policy, and it can be swapped or improved independently.

### Innovation 4: The Staged Length Curriculum — Compression Before Extension

A recurring challenge in reasoning RL is managing response length. Models trained to think longer tend to improve on hard problems but can become inefficient on easy ones, wasting inference compute and potentially generating incomplete reasoning when they hit the token budget. The standard approach to length management has been simple length extension — start with a budget, train until performance plateaus, increase the budget, repeat (e.g., DeepScaleR; Luo et al., 2025).

The Math RL curriculum (Section 4.5.2) introduces a counterintuitive first step: *compression before extension*. The three-stage curriculum (24K → 32K → 40K) begins by *reducing* the token budget relative to what the model naturally generates, forcing it to compress and refine its reasoning. The paper documents that SFT checkpoints for small models "tend to generate overlong reasoning chains, leading to incomplete ratios of 15–20% on the AIME benchmark under a 32K token budget." The 24K stage deliberately induces high incomplete ratios (30–50% initially) to penalize inefficient reasoning, dropping to ~15% after ~100 steps. Only after this compression does the budget extend to 32K and then 40K.

The conceptual insight is that length extension and reasoning quality are not monotonically related. Adding tokens to an inefficient reasoning chain gives the model more room to be verbose without improving correctness. Compressing first forces the model to allocate its reasoning budget more effectively — to identify which reasoning steps are actually necessary — before giving it more budget to allocate. The result is that when the budget does extend, the additional tokens go toward deeper reasoning on hard problems rather than more verbosity on easy ones.

The evidence for this claim is in the described training dynamics: after Stage 2 (32K), easy and medium AIME problems "nearly saturate" (99% and 85% respectively), but hard problems plateau below 30%. The Stage 3 extension to 40K then "explicitly incentivizes the model to leverage more tokens during reasoning" and improves hard-problem accuracy from ~30% to ~40%, while easy and medium performance remains high. This is precisely the pattern you would expect from a model that has learned to allocate tokens efficiently: the extension benefits hard problems that genuinely need more reasoning, without causing regression on problems the model already handles well.

This finding matters because it suggests that length management in reasoning RL is not simply about providing larger budgets — it is about teaching the model *how to use budgets effectively*. The compression stage acts as a form of regularization that prevents the model from learning that "more tokens = better" in a way that wastes compute. The paper demonstrates this on math but the principle likely generalizes to any domain where response quality and length have a non-monotonic relationship, including code generation (where verbose solutions can be less correct than concise ones) and software engineering (where analyzing irrelevant files wastes context).

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper evaluates on a comprehensive suite of benchmarks spanning knowledge reasoning, alignment, mathematical reasoning, competitive programming, software engineering, and tool use. Specific benchmarks and their properties: **MMLU** (14,079 test questions across 57 subjects, evaluated in thinking mode with exact match, single generation), **MMLU-Pro** (over 12,000 graduate-level questions with 10 answer choices, exact match, single generation), **GPQA-Diamond** (198 graduate-level physics/biology/chemistry questions, pass@1 averaged over 8 generations, thinking mode), **IFEval** (541 prompts with 25 verifiable instructions, evaluated using "prompt strict" — percentage of prompts where all instructions are satisfied — averaged over 8 generations, unified models evaluated in non-thinking mode, thinking models in thinking mode), **IFBench** (294 prompts with 58 novel constraint types from a taxonomy disjoint from IFEval, pass@1 averaged over 8 generations, thinking mode), **ArenaHard 1.0** (500 diverse user prompts, judged by GPT4-Turbo-2024-0409 against a baseline model, without style control to enable comparison with official results, thinking mode), **AIME 2024 and AIME 2025** (30 problems each from the American Invitational Mathematics Examination, pass@1 averaged over 64 generations, thinking mode with 64K-token budget and YaRN scaling factor 2), **LiveCodeBench v5** (279 problems from 08/2024–02/2025) and **v6** (454 problems from 08/2024–05/2025, pass@1 averaged over 8 generations, thinking mode with 64K-token budget), **LiveCodeBench Pro 25Q1** (166 problems from 01/2025–04/2025) and **25Q2** (167 problems from 04/2025–07/2025, reported by Easy/Med difficulty splits, pass@1 averaged over 8 generations, thinking mode with 64K-token budget), **SWE-bench Verified** (500 human-validated instances, pass@1 averaged over 4 generations, thinking mode with 32K-token budget, YaRN scaling factor 2 for 8B and 3 for 14B, max input prompt length 32K for 8B and 64K for 14B), and **BFCL V3** (tool-calling benchmark, details not elaborated but results reported for completeness). All benchmarks are described in Appendix B with detailed evaluation setups including temperature (0.6), top-p (0.95), and token budgets.

- **Base model(s).** The paper uses **Qwen3-8B-Base** and **Qwen3-14B-Base** (Yang et al., 2025) as the starting pretrained models, deliberately chosen to "support transparent comparison and facilitate knowledge sharing within the community." The 8B model is used to train both a dedicated 8B-Thinking model and a unified 8B model (supporting both thinking and non-thinking modes), while the 14B model is trained only as a dedicated 14B-Thinking model "due to resource constraints." For baseline comparison, the paper evaluates against models at multiple scales: **Qwen3-8B** and **Qwen3-14B** (the base instruct models), **Nemotron-Nano-9B-v2** (NVIDIA's smaller reasoning model), **Phi-4 reasoning (14B)**, **Ministral-3-14B-Reasoning-2512**, **DeepSeek-R1-0528 (671B)** (the SFT teacher model), **Gemini-2.5-Flash-Thinking** and **Gemini-2.5-Pro-06-05** (proprietary), **OpenAI o4-mini (medium)**, **OpenAI o3-mini (high)**, **Qwen3-235B-A22B** and **Qwen3-235B-A22B-Thinking-2507**, and **Qwen3-Next-80B-A3B-Thinking**. For SWE-bench specifically, the paper also compares against **DeepSWE-Preview-32B** and **SWE-agent-LM-32B** (specialized 32B models). Baseline results are from official reported numbers whenever available; otherwise, models are evaluated using their recommended inference configuration or the same settings as Nemotron-Cascade.

- **Metrics.** The primary metric across all benchmarks is **pass@1 accuracy** — the fraction of prompts for which the model's selected answer matches the ground truth on the first attempt. For small test sets with high variance (GPQA-Diamond, AIME, LiveCodeBench, IFEval, IFBench, SWE-bench Verified), pass@1 is reported as an **average over k generations (avg@k)** per prompt, where k ranges from 4 to 64 depending on test set size and variance (e.g., avg@8 for GPQA-Diamond and LiveCodeBench, avg@64 for AIME, avg@4 for SWE-bench Verified). For MMLU and MMLU-Pro, exact match (EM) accuracy from a single generation is reported due to the large test set size. For SWE-bench Verified, additional test-time scaling metrics are reported: **pass@k** (fraction of instances solved in at least one of k generations), **majority@k** (most frequently generated patch across k samples), and **best@k** (patch selected by the multi-phase validation pipeline). For Codeforces Elo ratings, the paper reports **estimated performance rating** computed by simulating model participation in 51 recent contests, ranking against human participants, and solving for an Elo rating consistent with the model's rank using standard Elo formula (Section 5, Appendix E).

- **Baselines.** The paper compares against a broad cross-section of models released in 2024–2025. Strong open-weight models at comparable scales include: **Qwen3-8B** (83.0 MMLU, 67.3 AIME 2025, 58.3 LCB v6, 20.5 SWE-bench Verified) and **Qwen3-14B** (84.9 MMLU, 70.4 AIME 2025, 63.5 LCB v6, 27.4 SWE-bench Verified). The SFT teacher model is **DeepSeek-R1-0528 (671B)** (89.9 MMLU, 87.5 AIME 2025, 73.3 LCB v6, 57.6 SWE-bench Verified) — serving as the upper bound that Cascade RL aims to surpass. Proprietary frontier models include **Gemini-2.5-Pro-06-05** (73.6 LCB v6), **Gemini-2.5-Flash-Thinking** (72.0 AIME 2025, 61.9 LCB v6), **OpenAI o4-mini (medium)** (74.2 LCB v6), and **OpenAI o3-mini (high)** (82.5 LCB v6, 67.4 SWE-bench Verified). Specialized reasoning models include **Nemotron-Nano-9B-v2** (NVIDIA's 9B reasoning model), **Ministral-3-14B-Reasoning-2512**, and **Phi-4 reasoning (14B)**. For SWE tasks specifically, baselines include **DeepSWE-Preview-32B** (42.2% resolve rate), **SWE-agent-LM-32B** (40.2%), and the Agentless framework applied to other models. The paper also benchmarks against longer-thinking-capability models like **Klear-Reasoner-8B**, **AReaL-Boba-2-14B**, **AceReason-Nemotron series**, **OpenReasoning-Nemotron-32B**, **Llama-3.3-Nemotron-Super-49B-v1.5**, **Magistral-Medium-1.2-2509**, and **Meta-CWM-32B** for competitive programming (Table 9).

- **Generation budget / compute accounting.** The paper measures inference compute primarily through **maximum response length** (token budget for generation): 12K for RLHF, 8K–16K for IF-RL, 24K–40K during Math RL training (but 64K at evaluation with YaRN scaling factor 2), 44K–56K for Code RL training (64K at evaluation), and 16K output tokens with 16K–32K input context for SWE RL (32K output tokens at evaluation with up to 64K input). For competitive programming benchmarks, the model is allowed up to **128K tokens** of thinking budget (Section 5) or **64K tokens** (Table 1). For test-time scaling on SWE-bench, the model generates k candidate patches (up to k=32) and 40 reproduction tests, with compute scaling with k. For IOI 2025, the pipeline allows up to 50 submissions per problem, each with 20 candidate generations and up to 128K thinking tokens per generation (Section 5.1). Importantly, all Cascade RL stages use the same GRPO training budget metrics: batch size 128 (or 256), rollout count 8 or 16, and training steps varying by stage (800–900 for RLHF, hundreds for domain-specific stages). The paper does not normalize by total FLOPs across stages for comparison — the comparison logic is "final model after complete pipeline vs. baselines" rather than "compute-matched at each stage."

- **Cross-validation / statistical protocol.** The paper does not employ formal cross-validation for model selection. Instead, checkpoint selection relies on monitoring validation performance on held-out subsets of training data or on benchmark development sets. For Math RL, checkpoint selection is based on AIME24 and AIME25 accuracy monitored during training (Figure 4). For RLHF, the best checkpoint is selected from training trajectories before collapse based on ArenaHard scores (Tables 10, 11). For SWE RL, the stage transition from 16K to 24K input context occurs "when the 16K setup reaches a reward plateau, with little improvement over successive iterations" (Section 4.7.2). The final model evaluation is on standard benchmark test sets, with data decontamination performed during SFT data curation (9-gram filtering) and during RL data curation to prevent overlap with evaluation benchmarks. For the Codeforces Elo rating (Appendix E), the model's submissions are simulated with 8 independent attempts per problem, and expected penalties are estimated assuming uniform distribution of correct and incorrect submissions — a Monte Carlo approach rather than true sequential contest simulation. The paper acknowledges that Elo ratings show "large variance across contests" (the 14B model achieves above 2600 on one round but below 1000 on another where it solves zero problems).

### Main Quantitative Results

The paper reports results after each Cascade RL stage. Rather than presenting only final results, the paper provides a stage-by-stage progression that demonstrates the cumulative effect and validates the claim of no catastrophic forgetting. We organize the main results by the cascade order, tracking how each stage transforms performance across all benchmark categories.

#### SFT Results (Table 2)

After the two-stage SFT process, the models establish strong baselines that RL will refine. The **8B unified model** achieves 83.0 MMLU, 74.4 MMLU-Pro, 83.6 AIME 2024, 72.8 AIME 2025, 59.2 LiveCodeBench v5, 56.7 LiveCodeBench v6, and 26.1 SWE-bench Verified — essentially matching or slightly trailing the dedicated 8B-Thinking model across reasoning benchmarks (83.6 vs. 83.8 MMLU, 83.6 vs. 83.8 AIME 2024, 56.7 vs. 56.7 LCB v6), while surpassing it on IFEval (70.8 vs. 66.3). The 14B-Thinking SFT model achieves 84.9 MMLU, 76.0 MMLU-Pro, 86.9 AIME 2024, 81.1 AIME 2025, 66.1 LCB v5, 63.1 LCB v6, and 34.5 SWE-bench Verified — approximately 2–5 points ahead of the 8B models across these benchmarks. These SFT checkpoints are already competitive with other 8B–14B models (Qwen3-8B achieves 83.0 MMLU, 67.3 AIME 2025 vs. the 8B-Thinking SFT's 71.6; Qwen3-14B achieves 70.4 AIME 2025 vs. 14B-Thinking SFT's 81.1). However, the gap to the teacher model DeepSeek-R1-0528 remains large: the 14B-Thinking SFT trails by roughly 6 points on AIME 2025 (81.1 vs. 87.5), 7 points on LCB v6 (63.1 vs. 73.3), and 23 points on SWE-bench Verified (34.5 vs. 57.6).

#### RLHF Results (Table 4)

After RLHF — the first RL stage — the models show dramatic improvements on alignment benchmarks and surprising gains on reasoning benchmarks. For the **8B-Thinking model**, ArenaHard jumps from 71.7 (SFT) to 89.9 (+18.2 points), AIME 2024 improves from 83.8 to 86.4 (+2.6), AIME 2025 improves from 71.6 to 75.1 (+3.5), LCB v5 jumps from 59.6 to 70.3 (+10.7), LCB v6 from 56.7 to 67.3 (+10.6), and SWE-bench Verified from 30.2 to 33.3 (+3.1). The **8B unified model** shows similar patterns: ArenaHard from 70.0 to 90.1 (+20.1), AIME 2024 from 83.6 to 86.1 (+2.5), LCB v5 from 59.2 to 70.2 (+11.0). The **14B-Thinking model** reaches ArenaHard 93.1 (+19.2 over SFT), AIME 2024 88.4 (+1.5), LCB v5 75.2 (+9.1), and SWE-bench Verified 38.8 (+4.3). The only consistent degradation is on IFEval: 8B-Thinking drops from 66.3 to 45.5 (−20.8), 8B unified drops from 70.8 to 50.1 (−20.7), 14B-Thinking drops from 69.8 to 56.2 (−12.4). The paper attributes this to "unavoidable semantic overlap between the prompts used during RLHF training and the test prompts in IFEval" and the reward model encouraging human-preferred qualities that conflict with strict instruction-following constraints.

The most remarkable finding from this stage is that RLHF — designed for alignment, not reasoning — produces some of the largest code benchmark improvements in the entire cascade. The 14B-Thinking model's LCB v5 gain of +9.1 points from RLHF alone exceeds the gains from Math RL (+0.0) and approaches those from Code RL (+2.8 from the Math RL checkpoint, but the cumulative effect from SFT through Code RL is +11.9). This validates the paper's claim that RLHF "substantially improves overall response quality (e.g., reduces verbosity), thereby enhancing reasoning performance" and justifies placing RLHF first in the cascade.

#### IF-RL Results (Table 5)

IF-RL recovers the IFEval degradation while causing only modest regression on alignment and reasoning benchmarks. For the **8B-Thinking model**, IFEval rebounds from 45.5 to 83.3 (+37.8), IFBench from 23.9 to 42.1 (+18.2), while ArenaHard drops from 89.9 to 86.3 (−3.6). Reasoning benchmarks show minor degradation: AIME 2025 from 75.1 to 72.3 (−2.8), LCB v6 from 67.3 to 65.9 (−1.4). For the **8B unified model** (trained in non-thinking mode only for IF-RL), IFEval reaches 90.4 (+40.3 over RLHF) — the highest IFEval score across all model variants — while ArenaHard drops only to 88.0 (−2.1) and AIME 2025 actually improves from 75.0 to 75.2 (+0.2). The **14B-Thinking model** (using the combined IF+RM reward function) achieves IFEval 81.3 (+25.1) and IFBench 40.4 (+14.8), with ArenaHard dropping to 90.2 (−2.9) and AIME 2025 improving to 82.3 (+0.5).

The paper notes that IF-RL "generally reduces model entropy and shortens the average length of reasoning tokens" (evident in Figure 8, which shows a ~20% reduction in reasoning token counts for LCB v6 after IF-RL), which "on the positive side, compresses the reasoning trace and improves token efficiency" but "on the negative side, introduces minor degradations on reasoning benchmarks." The unified model's non-thinking-mode IF-RL strategy proves superior for preserving alignment while gaining instruction-following capability — it achieves higher IFEval (90.4 vs. 83.3) and higher ArenaHard (88.0 vs. 86.3) than the dedicated thinking model's thinking-mode IF-RL.

#### Math RL Results (Table 6)

Math RL further improves mathematical reasoning while maintaining or slightly improving other domains. The **8B unified model** reaches AIME 2024 90.2 (+4.0 over IF-RL), AIME 2025 81.9 (+6.7), with LCB v5 improving from 70.2 to 70.6 (+0.4) and SWE-bench Verified from 28.3 to 30.6 (+2.3). The **8B-Thinking model** achieves AIME 2024 90.2 (+4.6), AIME 2025 80.2 (+7.9), LCB v5 71.2 (+2.2), and LCB v6 68.1 (+2.2). The **14B-Thinking model** reaches AIME 2024 90.4 (+1.3), AIME 2025 83.3 (+1.0), with SWE-bench Verified improving to 39.7 (+1.3). ArenaHard shows minor regression across all models (8B-Thinking: −2.3, 8B unified: −1.0, 14B: −0.9), which the paper attributes to evaluation variance and checkpoint selection rather than genuine degradation.

The training dynamics (Figure 4) show the 8B unified model's AIME24 accuracy rising from ~86% to ~90% over 500 steps, with AIME25 rising from ~74% to ~82%. The curve demonstrates characteristic RL behavior — rapid early improvement followed by gradual, noisier gains. The paper emphasizes that Math RL has "minimal effect on knowledge reasoning and alignment benchmarks" and that the code benchmark improvements, while positive, are "not as pronounced as those reported in AceReason-Nemotron" because the starting models after RLHF and IF-RL already have strong general reasoning.

#### Code RL Results (Table 7)

Code RL produces the largest domain-specific gains in the cascade. The **8B unified model** reaches LCB v5 75.3 (+4.7 over Math RL) and LCB v6 71.5 (+4.1), matching the teacher DeepSeek-R1-0528 (74.8 and 73.3, respectively). The **8B-Thinking model** achieves LCB v5 74.3 (+3.1) and LCB v6 71.0 (+2.9). The **14B-Thinking model** reaches LCB v5 78.0 (+2.8) and LCB v6 74.8 (+2.4), surpassing DeepSeek-R1-0528 (74.8 and 73.3). AIME 2025 shows mixed changes: 8B-Thinking improves from 80.2 to 81.8 (+1.6), 8B unified drops from 81.9 to 80.5 (−1.4), 14B-Thinking stays stable at 83.3 to 83.5 (+0.2). SWE-bench Verified shows small improvements: 8B unified from 30.6 to 31.6 (+1.0), 8B-Thinking from 32.5 to 33.3 (+0.8), 14B-Thinking from 39.7 to 39.6 (−0.1). IFEval shows slight regression across all models (8B-Thinking: −1.6, 8B unified: −1.4, 14B: −2.5), attributed to checkpoint variance.

The topic-wise analysis (Figure 7) reveals that Code RL provides the largest benefit on computer-science-oriented sub-categories: String problems improve from 51.8% after Math RL to 56.2% after Code RL (+4.4 points), and Data Structure problems improve from 56.2% to 53.1% (actually a decrease — the paper reports this figure but does not explain the anomaly). Math-related topics (Math, Graph, Geometry) improve more modestly, consistent with Math RL having already addressed those.

The competitive programming results in Table 9 expand the analysis beyond LiveCodeBench. The **8B unified model** achieves 65.7 on LiveCodeBench Pro 25Q2 Easy, 6.4 on LiveCodeBench Pro 25Q2 Medium, and a Codeforces Elo of 1789 (95.7th percentile). The **14B-Thinking model** achieves 68.9 Easy, 10.5 Medium, and Elo 1932 (97.2nd percentile). These results place the 8B model ahead of OpenReasoning-Nemotron-32B (1766 Elo) and the 14B model ahead of Gemini-2.5-Pro-06-05 (2034 Elo? — the table is organized differently, showing the 14B model at 1932 vs. Gemini-2.5-Pro at 2034; however, the paper text claims the 14B model "outperforms Gemini-2.5-Pro-06-05" on LiveCodeBench v5/v6 specifically, which the table supports: 77.5 vs. 73.5 on v5).

#### SWE RL Results (Table 8 — Final Models)

SWE RL provides the final boost to software engineering capability. The **8B-Thinking model** reaches SWE-bench Verified 38.5 (+5.2 over Code RL), the **8B unified model** reaches 37.2 (+5.6), and the **14B-Thinking model** reaches 43.1 (+3.5). The 14B model's 43.1 surpasses specialized 32B models DeepSWE-32B (42.2) and SWE-agent-LM-32B (40.2), and substantially outperforms other 14B general-purpose models (Qwen3-14B at 27.4, Ministral-3-14B-Reasoning-2512 at 25.5). Other benchmarks show minimal changes: AIME 2024 ranges from 88.8 to 89.7 across the three models (changes within 0.4–0.7 points), LCB v5 ranges from 74.3 to 77.5 (the 14B model drops 0.5 from 78.0), and IFEval remains stable (8B unified: 90.2, −0.5 from Code RL). The paper highlights that "the performance gap on SWE-bench Verified between the dedicated 8B thinking SFT model and the 8B unified SFT model (30.2 vs. 26.1 in Table 2) is largely mitigated after the full Cascade RL process (38.5 vs. 37.2)" — a 1.3-point gap compared to the initial 4.1-point gap.

Test-time scaling on SWE-bench Verified (Figure 12) amplifies these results. For the **8B model**, best@32 reaches 43.6% resolve rate (vs. 37.2% pass@1), pass@32 reaches 57.7%, and majority@32 plateaus at 39.7%. For the **14B-Thinking model**, best@32 reaches 53.8% (vs. 43.1% pass@1), pass@32 reaches 67.0%, and majority@32 reaches 50.7%. The gap between pass@k and best@k (67.0% vs. 53.8% at k=32 for 14B) indicates substantial headroom for improved patch selection. The paper notes that the 14B model's best@32 of 53.8% is competitive with the specialized DeepSWE-32B, which achieves a 52.4% resolve rate with execution-based verifier TTS.

#### IOI 2025 Results (Section 5.1, Figure 5)

The 14B-Thinking model achieves a total score of 343.37 on IOI 2025, "corresponding to a solid silver medal performance with at most 1000 generations (20 generations × 50 rounds), and no more than 50 official submissions to each problem" (silver threshold: 338.01, gold threshold: 438.30). On IOI 2025 Problem 2 (Triples), which requires iterative construction algorithm refinement, the pipeline scores 90.37 points — outperforming both "OpenAI's internal IOI-gold model (75.29 points) and DeepSeek-V3.2-Speciale (82 points)." The test-time scaling curve (Figure 5) shows monotonic improvement with rounds: the total score rises from ~200 at round 10 to 343.37 at round 50, while Problem 2 specifically rises from ~40 to 90.37 over the same period. The feedback-driven pipeline — conditioning later generations on submission history, cross-subtask insights from solved subtasks, and official judge verdicts — is essential to this scaling (the paper compares only to the internal evaluation pipeline for other models, not to simpler test-time scaling approaches on the same model).

#### Codeforces Elo Analysis (Appendix E, Tables 21–22)

The Elo analysis reveals a performance pattern that the paper frankly acknowledges as inconsistent: the 8B model achieves Elo estimates ranging from 977 (Codeforces Round 1012 Div. 1, where it solved 0 of 7 problems) to 2482 (Round 1004 Div. 1, where it solved 3 of 7). The 14B-Thinking model ranges from 938 (Round 1024 Div. 1, 0 of 6 solved) to 2673 (Round 1028 Div. 1, 2 of 7 solved). The paper notes that "the model tends to perform well on problems solvable by standard techniques, heavy implementation, or straightforward intuition, but often struggles on problems that require hypothesis-driven exploration on small-scale data or ad hoc ideas, such as constructive or interactive problems." This variance is not merely academic — it means the Elo rating is a noisy summary statistic that can be heavily influenced by which contests the model encounters, and direct comparison of Elo numbers across models should be interpreted with caution.

### Ablation Studies and Robustness Checks

**Reward model backbone choice (Table 3):** RewardBench scores scale from 91.98 (7B) to 93.22 (14B) to 93.56 (32B) to 95.15 (72B), confirming scaling laws for reward models. Initializing from WorldPM (15M-scale preference pre-training) provides early training benefits but the vanilla Qwen2.5-72B-Instruct catches up (95.15 vs. 94.08). Qwen3 reasoning models dramatically underperform as RM backbones — Qwen3-14B in thinking mode scores only 46.38, and even in non-thinking mode reaches only 91.72, trailing Qwen2.5-Instruct-14B at 93.22. This suggests that reasoning-optimized models are poorly suited for preference discrimination tasks.

**RLHF training strategies for unified models (Figure 9):** The Half-Half strategy (equal split of thinking and non-thinking prompts per batch) produces the best results across ArenaHard, AIME, and LiveCodeBench compared to thinking-only or non-thinking-only training. Training in non-thinking mode alone produces the worst ArenaHard and reasoning results, while thinking-only training produces competitive ArenaHard but worse AIME and LCB performance than Half-Half. The paper interprets this as evidence of cross-mode transfer.

**Reward model size impact on RLHF (Figure 10):** Using the 7B RM for RLHF produces the worst ArenaHard scores, especially under style control (45.76 vs. 52 for the non-style-controlled score), indicating that smaller RMs are vulnerable to reward hacking via response length. The 72B RM produces the best ArenaHard under style control (~55) and the best AIME25 accuracy (~55), approximately 3 points higher than the 7B RM. Code benchmarks show minimal sensitivity to RM size (differences within 1 point).

**RLHF stabilization techniques (Tables 10, 11):** With the 7B RM, KL penalty (1e-3) + sequence-level loss + reward shaping extends stable training from 350 to 950 steps and improves ArenaHard from 46.63 to 50.78. With the 72B RM, omitting all stabilization techniques (KL=0, token-level loss, no reward shaping) actually produces slightly better ArenaHard (91.04 vs. 90.03) and better AIME25 (75.03 vs. 73.80) than using them — the larger RM's reward signals are sufficiently clean to not require stabilization.

**Code RL training temperature (Figure 6):** Training with temperature 1.0 achieves higher LCB v5 accuracy (~75) than temperature 0.8 (~73) or 0.6 (~69), but exhibits higher and more volatile token-level entropy. Temperature 0.6 shows stable entropy but the worst final accuracy. The paper's chosen approach uses high temperature (1.0–1.2) despite the instability risk, accepting occasional entropy spikes for better exploration.

**Cascade RL's progressive effect on code reasoning (Figure 8):** On LiveCodeBench v6, RLHF sharply reduces reasoning tokens (from 20K–45K to 15K–30K while improving accuracy from 95% to 99% on easy problems and from 25% to 40% on hard problems). IF-RL further reduces token counts by ~20% with 0.5% accuracy drop. Math RL expands token usage and improves medium-problem accuracy. Code RL provides the final lift on medium and hard problems with substantially expanded reasoning traces (medium problems rise from 80–85% to 85–90%, hard problems from 40% to 45%).

**Code localization methods (Figure 11):** Retrieval-based localization (NV-Embed-Code) outperforms generation-based localization at all cutoffs — at top-1, retrieval achieves ~71% recall vs. ~65% for generation (1 rollout). Aggregating 16 generation rollouts improves generation's top-1 recall to ~73%, and fusing retrieval with 16-rollout generation achieves ~74%. The retrieval advantage is most pronounced at low cutoffs, suggesting that semantic similarity to code content is more reliable than reasoning over repository structure for identifying the single most relevant file.

**SWE RL reward function design (Table 12):** Using semantic similarity (Kimi-Dev-72B) as the reward function produces better repair performance than lexical similarity (Unidiff) — 43.0% vs. 42.6% resolve rate with ground-truth localization, 42.3% vs. 41.2% with top-4 localization. Reward shaping (zeroing rewards below 0.5) helps lexical similarity (42.8% vs. 42.6% with ground-truth localization) but does not help semantic similarity (42.9% vs. 43.0%), indicating that lexical similarity below 0.5 provides noisy signals while semantic similarity remains informative at low similarity values.

**SWE RL input context length (Table 13):** Training with progressively longer input prompts improves repair capability: 16K prompts yield 44.0% resolve rate with ground-truth localization, 24K yields 43.0% (slightly worse), 32K yields 44.1% (best), and 40K drops to 42.8%. With top-4 localization, 32K yields 42.7% (best). The paper interprets the 40K degradation as evidence that "the pretrained Qwen3-14B-Base has limited long-context capability at 32K" or that excessive context introduces noise. The final models use 24K (8B) and 32K (14B).

**SWE test-time scaling (Figure 12):** The `best@k` selection procedure consistently outperforms majority voting, with the gap widening as k increases. For the 14B model at k=32, best@k achieves 53.8% vs. majority@k at 50.7% — a 3.1-point advantage. The `pass@k` curve continues rising to 67.0% at k=32, suggesting that improved selection procedures could recover additional performance from already-generated patches. The 8B model's best@k of 43.6% at k=32 matches the 14B model's pass@1 of 43.1%, demonstrating that test-time scaling can compensate for model size to some extent.

### Critical Assessment

#### Claim 1: Cascade RL improves over joint blended RL and resists catastrophic forgetting.

What the experiments actually demonstrate: The paper provides comprehensive stage-by-stage evaluation (Tables 2–8) showing that performance on previously-trained domains remains stable or improves as new domains are added. However, there is no direct comparison between Cascade RL and a joint blended RL approach on the same models with the same data — such a comparison would require training a model with the same total RL steps but with blended prompts from all domains, which was not done. The evidence is therefore **circumstantial**: the cascade works and doesn't catastrophically forget, but we cannot quantify how much better or worse it is than the alternative from this paper alone. The closest comparison is between the Cascade RL approach and existing models trained with blended RL (DeepSeek-R1, Qwen3), but those models differ in base architecture, training data, and total compute budget, making the comparison only weakly informative about the cascade-vs-blend question specifically.

A stronger test would have been to train a variant of the same model with the same total compute budget but with blended prompts at each RL stage (or all RL stages combined), and compare final performance. The absence of this experiment is understandable given compute constraints — the paper already trains models through five RL stages — but it means the central architectural claim rests on indirect evidence and the theoretical argument in Section 4.1.1 rather than a controlled comparison.

#### Claim 2: RLHF, applied first, boosts reasoning ability beyond mere preference optimization.

What the experiments actually demonstrate: Table 4 shows substantial reasoning benchmark improvements after RLHF — AIME 2024 +2.6 for 8B, LCB v5 +10.7 for 8B, SWE-bench Verified +3.1 for 8B. These are genuine and surprising gains. However, the mechanism is attributed to "reducing verbosity and repetition" and the evidence for this mechanism is qualitative (Figure 8 shows reduced reasoning tokens, the paper describes improved token efficiency). There is no ablation that isolates the verbosity effect — for example, training with a length penalty instead of RLHF to see if the reasoning gains can be achieved without the alignment component, or training RLHF with length-controlled rewards to separate the quality signal from the length signal. The claim that RLHF provides a "cleaner, more efficient policy initialization" is plausible and consistent with the data, but the causal pathway is not experimentally isolated.

Additionally, the paper's early experiment where math prompts accidentally included in RLHF caused a 2% AIME25 drop is cited as evidence for domain separation, but this is reported anecdotally without data — the experiment, the magnitude, and the conditions are not presented in a table or figure.

#### Claim 3: The unified 8B model closes the thinking-only performance gap.

What the experiments actually demonstrate: The final comparison (Table 8) shows the unified 8B model within 0.2–1.3 points of the dedicated 8B-Thinking model on AIME 2024 (89.5 vs. 89.7), AIME 2025 (80.1 vs. 81.4), LCB v5 (74.3 vs. 74.5), LCB v6 (71.1 vs. 71.4), and SWE-bench Verified (37.2 vs. 38.5). These gaps are small and the unified model substantially outperforms on IFEval (90.2 vs. 83.7). This is convincing evidence that the gap has been largely closed at the 8B scale. However, the paper acknowledges two caveats: (1) "due to resource constraints, we only train a 14B-Thinking model" — there is no 14B unified model to test whether the gap closes at larger scales; (2) the unified model's slightly lower SWE-bench Verified scores after SFT (26.1 vs. 30.2) and throughout the cascade suggest some residual penalty from the additional non-thinking training, even if it narrows. The claim is well-supported for the 8B scale tested but its generalization to other scales or base model families is untested.

#### Claim 4: The 14B-Thinking model surpasses its SFT teacher DeepSeek-R1-0528.

What the experiments actually demonstrate: On LiveCodeBench v5, the 14B model achieves 77.5 vs. DeepSeek-R1-0528's 74.8; on LCB v6, 74.6 vs. 73.3; on LCB Pro 25Q2 Easy, 68.9 vs. 63.9; on LCB Pro 25Q2 Medium, 10.5 vs. 7.0. This is a clear and consistent margin of 2–3 points across all four code benchmarks. On AIME 2025, the 14B model scores 83.3 vs. the teacher's 87.5 — actually trailing by 4.2 points, but AIME is a math benchmark where the teacher's advantage from 671B parameters and extensive math-specific RL training is expected to persist. On SWE-bench Verified, the 14B model scores 43.1 vs. the teacher's 57.6 — trailing substantially, again reflecting the teacher's scale advantage on a complex task. The claim that the 14B model "surpasses" the teacher is true specifically for competitive programming benchmarks, not across all domains, and this qualification is present in the paper's own framing (Section 1 specifies "on LiveCodeBench v5/v6/Pro"). The achievement is nonetheless remarkable given the 48× parameter reduction.

#### Claim 5: Execution-free reward models enable scalable SWE RL.

What the experiments actually demonstrate: The ablation (Table 12) shows that semantic similarity rewards produce effective training, improving resolve rate from 38.8% to 43.0% (ground-truth localization). However, the paper does not compare execution-free rewards against execution-based rewards directly — the claim is about scalability (the ability to train on larger datasets without Docker bottlenecks), not about superiority of the reward signal. The ablation shows execution-free rewards work for training, but we don't know if they work as well as execution-based rewards would on the same data. The paper's training dataset (127K SFT samples plus the RL dataset of hard instances) is larger than the ~10K instances typical of prior work using Docker-based verification, consistent with the scalability claim, but this is correlational rather than causal — larger datasets were used, and training succeeded, but whether the larger dataset or the execution-free reward was the enabling factor is not isolated.

#### Genuine Weaknesses

1. **No direct cascade-vs-blend comparison.** The paper's central architectural claim — that sequential domain-wise RL is better than joint blended RL — rests on theoretical argument and stage-by-stage stability evidence, not on a controlled experiment. A blended RL baseline trained for the same total steps on the same data would have been the most direct test and was not attempted. This is the most significant missing experiment.

2. **Difficulty estimation and compute accounting are unclear for some stages.** For Math RL, the paper describes dynamic filtering that removes problems with 100% or 0% accuracy after each epoch, but this requires generating rollouts and scoring them — a computation cost that is not quantified. For SWE RL, the execution-free reward model (Kimi-Dev-72B) must be run for every rollout, adding inference cost that is not compared to the Docker execution cost it replaces. The "reduced infrastructure complexity" is real but the total FLOPs comparison is missing.

3. **Small test sets for key benchmarks.** AIME 2024 and 2025 each have only 30 problems — a 2–3 point accuracy difference represents less than one additional problem solved, making the per-stage differences (e.g., "AIME 2024 improved from 86.2 to 90.2" for 8B unified between IF-RL and Math RL, representing ~1.2 problems) highly sensitive to which specific problems are solved. GPQA-Diamond has 198 questions but the paper averages over 8 generations for reliability. The paper does not report confidence intervals, making it difficult to assess whether stage-to-stage differences are statistically significant or within evaluation noise — the paper's frequent attribution of small changes to "checkpoint and evaluation variance" cuts both ways.

4. **Single base model family.** All experiments use Qwen3-8B-Base and Qwen3-14B-Base. Whether the Cascade RL recipe transfers to other architectures (Llama, DeepSeek, Mistral) or other scales (e.g., 32B, 70B) is untested. The paper's claim that the Math RL recipe was validated on "five different 8B checkpoints" (Section 4.5.2) suggests some robustness, but these were all within the same training run, not different model families.

5. **RLHF evaluation is confounded by prompt overlap.** The paper states that RLHF degrades IFEval performance because "the prompts used during RLHF training [have] unavoidable semantic overlap with the test prompts in IFEval." This is a data contamination concern — if RLHF training prompts resemble IFEval test prompts, the IF-RL stage that recovers IFEval performance may be benefiting from memorization rather than generalization, and the stage-to-stage IFEval numbers are not a clean measure of instruction-following capability.

6. **IOI 2025 results are not compared to simpler test-time scaling baselines.** The IOI pipeline involves feedback loops, cross-subtask insights, history caching, and Tail-10 selection — it's unclear whether the 14B model's silver medal performance is due to the model's underlying capability or the sophistication of the test-time scaling strategy. Evaluating the same model with a simpler strategy (e.g., majority voting over N generations, best-of-N without feedback) would have distinguished model quality from pipeline engineering.

7. **The unified-vs-dedicated comparison is not fully controlled.** The 8B unified model and 8B-Thinking model are trained on the same thinking data during SFT and RL stages, with the unified model receiving additional non-thinking data. However, the paper does not train a dedicated 8B-Thinking model that *also* receives the non-thinking data (treated as additional reasoning-format data) to test whether the non-thinking formatted data itself or the Half-Half training strategy is responsible for the unified model's strong thinking-mode performance. The "Half-Half" strategy is tested only for RLHF (Section 6.1), not for IF-RL (where the unified model uses non-thinking mode only) or other stages.

#### Missing Experiments That Would Strengthen the Paper

- A blended RL baseline: train with the same total RL steps but with prompts from all domains mixed in each batch, with reward functions appropriately normalized, and compare final performance and per-domain trajectories to the cascade.
- An execution-based SWE RL comparison: train SWE RL with Docker-based verification on a subset of the data (feasible at up to 10K instances) and compare to the execution-free reward on the same subset to quantify the reward quality gap.
- Confidence intervals on benchmark scores: particularly for AIME (30 problems) and SWE-bench Verified (500 instances), reporting the variance across evaluation runs or bootstrapped confidence intervals would help distinguish genuine improvements from noise.
- Ablation of RLHF's verbosity-reduction effect on downstream RLVR: train Math RL from a checkpoint that achieved verbosity reduction through a non-RLHF method (e.g., length-penalized SFT) and compare training dynamics and final accuracy to isolate the specific benefit of RLHF initialization beyond length compression.
- A 14B unified model: the paper demonstrates unification at 8B but only trains a 14B dedicated thinking model, leaving open the question of whether the Half-Half strategy scales to larger models.

## 6. Limitations and Trade-offs

### 6.1 No Controlled Comparison Against Joint Blended RL

**The assumption or constraint.** The paper's central architectural claim is that sequential, domain-wise RL (Cascade RL) is superior to the dominant paradigm of joint blended RL training where prompts from all domains are mixed in each batch. This claim is supported by theoretical argument (Section 4.1.1) and stage-by-stage stability evidence, but not by a direct, controlled experiment. The paper states:

> "Cascade RL trains models sequentially across domains, in contrast to approaches such as DeepSeek-R1 and Qwen3, which blend diverse prompt distributions from all (reasoning) domains for joint RL training." (Section 1)

**The consequence.** Without a blended RL baseline — a model trained for the same total RL steps on the same data but with domain prompts mixed in each batch, with reward functions appropriately normalized — we cannot quantify how much of Cascade RL's performance comes from the sequential training paradigm itself versus the total training compute, the quality of the reward functions, or the specific hyperparameter choices. The comparison against DeepSeek-R1-0528 and Qwen3 (Table 1) is confounded by differences in base model architecture, training data, total compute budget, and SFT recipe. A practitioner deciding whether to adopt Cascade RL over blended RL for their own model cannot determine from this paper alone whether the sequential paradigm provides a genuine advantage or whether equivalent performance could be achieved by simply training with blended prompts for longer. The risk is adopting a more complex multi-stage pipeline when a simpler blended approach might suffice.

**What evidence exists in the paper.** The paper provides comprehensive stage-by-stage evaluation (Tables 2–8) showing that performance on previously-trained domains remains stable or improves as new domains are added — strong evidence against catastrophic forgetting, but only indirect evidence for the superiority of sequential over blended training. The theoretical argument in Section 4.1.1 identifies reasons why catastrophic forgetting should be less severe in LLM RL than in supervised learning (policy-dependent data distribution, cumulative reward optimization, shared reward structures, minimized prompt overlap), but this argument applies equally to why *blended* training should not suffer from interference between domains — it does not uniquely support sequential training.

**Mitigation status.** Not addressed. The paper does not train or evaluate a blended RL baseline, and the absence of this experiment is not acknowledged as a limitation. A blended RL comparison would require retraining from the same SFT checkpoint with the same total compute budget, which the paper may have omitted due to compute constraints. The paper's release of "the full collection of models and training data" (Section 1) does, however, enable the community to conduct this comparison independently.

---

### 6.2 Difficulty Estimation and Reward Model Inference Cost Are Unaccounted For

**The assumption or constraint.** Several Cascade RL stages require substantial auxiliary computation whose cost is not quantified or amortized into the headline efficiency claims. Specifically:

- **Math RL dynamic filtering** (Section 4.5.2): After each epoch, the model generates rollouts on the full training set and computes accuracy to determine which problems to filter (100% or 0% accuracy). This requires inference passes over the entire training set at each epoch boundary — a computation cost that scales with dataset size and model size but is never quantified.

- **SWE RL execution-free reward model** (Section 4.7.2): Every rollout during SWE RL training must be scored by Kimi-Dev-72B, a separate 72B-parameter model, which generates a "YES"/"NO" judgment and returns the probability assigned to "YES" as the reward. This adds inference cost proportional to the policy model's generated tokens times the rollout count — for SWE RL with batch size 128, 16 rollouts per prompt, and up to 16K output tokens, this represents a substantial additional inference budget that is not compared to the Docker execution cost it replaces.

- **RLHF reward model inference** (Section 4.3.2): Every rollout during RLHF training is scored by the 72B reward model. While this is standard for RLHF and the cost scales with the smaller 12K max response length used during RLHF, it is still a non-trivial auxiliary compute overhead.

- **IF-RL combined reward function** (Section 4.4.2): The dedicated thinking model's IF-RL stage runs both the rule-based IF verifier and the 72B RM for every rollout when rewards are non-zero.

**The consequence.** The paper's headline efficiency claims — that Cascade RL "reduces engineering complexity" and that sequential domain-wise RL enables more efficient training — are based on developer experience and wall-clock infrastructure simplicity, not on total FLOPs accounting. A practitioner attempting to replicate Cascade RL must provision inference capacity not only for the policy model being trained but also for auxiliary models (72B RM, 72B semantic scorer) and for the dynamic filtering passes. The total cost of training may be substantially higher than the policy model's training FLOPs alone, and the scaling behavior with model size — where a 72B auxiliary model scoring an 8B policy's outputs becomes proportionally more expensive — is not analyzed. In the extreme, for very large policy models, the auxiliary model inference cost could dominate the training budget.

**What evidence exists in the paper.** For Code RL, the paper does quantify verification overhead reduction: asynchronous reward computation reduces "averaged code verification time per batch" from 1172.4 seconds to 416.2 seconds (Section 4.6.2) — a concrete cost metric. No comparable quantification exists for Math RL dynamic filtering, SWE RL reward model inference, or the total auxiliary compute budget across the cascade. The paper describes the execution-free SWE reward as enabling "scalable RL training" compared to Docker-based verification (Section 4.7.2), but does not compare the inference cost of a 72B model against Docker execution cost.

**Mitigation status.** Partially addressed for Code RL through the asynchronous verification timing. Not addressed for Math RL dynamic filtering, SWE RL reward model, or the total auxiliary compute budget. The paper frames Cascade RL's advantage as reduced "engineering complexity" rather than reduced total FLOPs, which is a legitimate but narrower claim. A practitioner would need to benchmark auxiliary model inference cost for their specific hardware configuration to determine whether Cascade RL is actually cheaper than alternatives.

### 6.3 No Unified Model Trained at 14B Scale

**The assumption or constraint.** The paper demonstrates that a unified 8B model — capable of operating in both thinking and non-thinking modes — can match the dedicated 8B-Thinking model's reasoning performance while substantially outperforming it on instruction-following. However, this result is limited to the 8B scale. The paper explicitly acknowledges:

> "Due to resource constraints, we only train a 14B-Thinking model and provide stronger results than 8B models." (Section 3.4)

**The consequence.** The primary claim about unified models — that "the reasoning performance gap between the 8B unified model in thinking mode and a dedicated 8B-Thinking model can be closed" (Section 1) — is validated only at 8B. Whether the Half-Half RLHF strategy (Section 6.1), the non-thinking-mode-only IF-RL strategy (Section 4.4.2), and the parallel thinking/non-thinking SFT data curation (Section 3.2.1) scale to larger models is unknown. At larger scales, models may have more capacity to represent both modes without interference, making unification easier, or they may develop stronger mode-specific specializations that make unification harder. The paper's 14B-Thinking model achieves strong results (including IOI silver medal), but we cannot determine whether training it as a unified model would have incurred a performance penalty, because no 14B unified model was trained. A practitioner deciding whether to build a unified model at their target scale cannot extrapolate from the 8B result with confidence.

**What evidence exists in the paper.** The comprehensive comparison between the 8B unified and 8B-Thinking models across all Cascade RL stages (Tables 2–8) provides strong evidence at 8B: after SFT, the unified model trails the dedicated thinking model on reasoning benchmarks by 0–2 points (AIME 2024: 83.6 vs. 83.8; SWE-bench Verified: 26.1 vs. 30.2); after the full cascade, the gaps shrink to 0.2–1.3 points (AIME 2024: 89.5 vs. 89.7; SWE-bench Verified: 37.2 vs. 38.5). The unified model's IFEval advantage (90.2 vs. 83.7) demonstrates that the additional non-thinking training provides genuine capability gains. However, the residual SWE-bench gap of 1.3 points after the full cascade suggests the unification penalty is not completely eliminated even at 8B, and we have no data on whether the penalty grows, shrinks, or stays constant at 14B or larger scales.

**Mitigation status.** Not addressed. The paper acknowledges the resource constraint and reports only 14B dedicated thinking model results. Training a 14B unified model and a 14B-Thinking model on identical data would require roughly twice the compute budget for the 14B scale, which may have been prohibitive. The paper's release of training recipes and data enables community replication at other scales.

### 6.4 Hard Problems Remain Largely Unsolved Despite the Cascade

**The assumption or constraint.** The Cascade RL framework improves across all domains, but its effectiveness is bounded by the base model's fundamental capability. On the hardest problems in each domain, the cascade provides diminishing or negligible returns. The paper documents this pattern across multiple benchmarks:

- **Math RL on hard AIME problems** (Section 4.5.2): After the 32K stage, "hard problems remain challenging, with accuracy plateauing below 30%." The 40K extension stage improves this to ~40%, but 60% of hard AIME problems remain unsolved even after the full Math RL curriculum.

- **Code RL on LiveCodeBench Pro Medium** (Table 9): The 8B model achieves only 6.4% on LCB Pro 25Q2 Medium, and the 14B model reaches only 10.5%. On the hardest competition problems, even the best Cascade RL model solves roughly 1 in 10.

- **SWE-bench Verified test-time scaling gap** (Figure 12): The 14B-Thinking model's pass@32 is 67.0%, meaning that even with 32 attempts, 33% of SWE-bench issues are never correctly resolved. The best@k curve plateaus around 53.8%, indicating that improved selection cannot close this gap — the model simply cannot generate correct patches for roughly half the benchmark, regardless of sampling budget.

- **Codeforces Elo variance** (Appendix E, Tables 21–22): The 14B model achieves above 2600 Elo on one round and below 1000 on another, demonstrating that capability is highly problem-dependent and that there exist contest problems the model fundamentally cannot solve even with 8 attempts.

- **IOI 2025 gold threshold** (Section 5.1): Despite achieving a solid silver medal (343.37 points), the model falls well short of the gold threshold (438.30). The slope of the improvement curve in Figure 5 appears to be flattening by round 50, suggesting that simply adding more rounds would not reach gold.

**The consequence.** Cascade RL amplifies existing capability — it makes the model better at problems it could already sometimes solve — but does not appear to create fundamentally new capabilities. For problems where the base model's pass@1 is effectively zero (the hardest IOI tasks, the most complex SWE-bench issues, the most difficult Codeforces Div. 1 problems), the cascade provides negligible improvement. This is a hard ceiling on the approach: no amount of sequential RL training can teach the model to solve problems that are outside its representational or knowledge capacity, regardless of how well the training is organized. A practitioner deploying Cascade RL for challenging real-world tasks must accept that there exists a difficulty threshold beyond which the model will not improve, and they must either increase the base model size, improve the pretraining data, or use a different base model architecture.

**What evidence exists in the paper.** The difficulty-dependent performance is most clearly documented in Figure 8 for LiveCodeBench v6: easy problems reach ~99% accuracy after RLHF and saturate, medium problems improve from ~85% to ~90% through Math RL and Code RL, but hard problems only improve from ~25% to ~45% — less than half solved after the full cascade. The Codeforces Elo analysis in Appendix E provides the most granular evidence: the model's performance varies from contest to contest based on problem characteristics, with constructive and interactive problems being particularly difficult (the paper notes this explicitly: "the model tends to perform well on problems solvable by standard techniques, heavy implementation, or straightforward intuition, but often struggles on problems that require hypothesis-driven exploration on small-scale data or ad hoc ideas"). The SWE-bench pass@k vs. best@k gap (67.0% vs. 53.8% at k=32 for 14B, Figure 12) demonstrates that generation capability exceeds selection capability, and that even with 32 attempts, roughly one-third of issues are never correctly addressed.

**Mitigation status.** The paper acknowledges these limitations implicitly through the reported numbers but does not discuss the capability ceiling as a systematic limitation of the Cascade RL approach. The paper suggests that "designing training frameworks that retain the benefits of high-temperature sampling while ensuring entropy stability is a promising direction for future work" (Section 5.2), and that for Codeforces, "it could be an interesting direction for understanding and improving such reasoning abilities in the future" (Appendix E). However, these are suggestions for improving within the existing paradigm rather than addressing the fundamental scalability limits. The paper does not explore whether larger base models, different pretraining objectives, or fundamentally different RL exploration strategies could break through the capability ceiling on hard problems.

### 6.5 Evaluation on Small, High-Variance Test Sets Without Confidence Intervals

**The assumption or constraint.** Several key benchmarks used to demonstrate Cascade RL's effectiveness have very small test sets, making the reported accuracy differences sensitive to which specific problems are solved. Specifically:

- **AIME 2024 and AIME 2025:** 30 problems each. A 2–3 point accuracy difference represents 0.6–0.9 additional problems solved — well within the range of random seed variance.
- **GPQA-Diamond:** 198 problems, but reported as avg@8 to reduce variance. The paper does not report the variance of the estimate.
- **LiveCodeBench Pro Medium splits:** 25Q1 has 166 problems but the Medium subset is smaller; 25Q2 has 167 problems with the Medium subset also small. The 14B-Thinking model's Medium accuracy varies from 10.5% (25Q2) to 16.3% (25Q1) — a 5.8-point swing that could represent genuine temporal difficulty variation or statistical noise from a small number of problems.

The paper does not report confidence intervals, standard errors, or bootstrapped uncertainty estimates for any benchmark. Small differences are frequently attributed to "checkpoint and evaluation variance" (e.g., the 14B-Thinking's 1.0-point drop on GPQA Diamond between IF-RL and Math RL in Table 6, attributed to "evaluation variance and checkpoint selection"), but the paper provides no quantitative characterization of what variance should be expected.

**The consequence.** Stage-to-stage comparisons — which form the core evidence for the paper's claims about the cascade's cumulative effect and resistance to forgetting — may be unreliable when differences are small. For example, Table 8 reports that SWE RL caused the 8B-Thinking model's MMLU to drop by 0.3 points (84.3 to 84.0), which the paper attributes to normal variance. But without confidence intervals, we cannot distinguish genuine degradation from noise. Similarly, claims about the 8B unified model "closing the gap" with the 8B-Thinking model rest on differences of 0.2 points (AIME 2024) to 1.3 points (SWE-bench Verified) — small enough that the gap might not be statistically significant.

More subtly, the selection of "best checkpoints" from training trajectories introduces an implicit multiple-comparisons problem. For Math RL, checkpoint selection is based on AIME24 and AIME25 accuracy (Figure 4), which means the reported numbers on these benchmarks may be optimistically biased relative to the model's true expected performance. The paper would ideally report held-out validation performance or use a fixed selection criterion applied uniformly across all stages, but the selection procedure varies by stage (RLHF uses ArenaHard, Math RL uses AIME, SWE RL uses reward plateau).

**What evidence exists in the paper.** The paper's evaluation methodology (Section 2, Appendix B) describes the benchmarks and metrics in detail but does not mention confidence intervals or statistical testing. The paper does employ avg@k averaging (k=4, 8, or 64) to reduce variance from single-generation sampling, but this addresses generation variance, not test-set variance. The final results table (Table 1) reports single-point estimates for all benchmarks without error bars or uncertainty quantification.

**Mitigation status.** Not addressed. The paper does not discuss the statistical reliability of the reported differences, does not provide confidence intervals, and does not apply corrections for multiple comparisons across stages. The paper's transparency about evaluation configurations (temperature, top-p, max tokens, YaRN scaling) is commendable and enables replication, but replication is not the same as uncertainty quantification. A practitioner trying to determine whether a 1–2 point difference between two checkpoints is meaningful or noise cannot do so from the reported data. The paper's frequent use of "evaluation variance" as an explanation for small differences would be more convincing if accompanied by estimated variance magnitudes.

### 6.6 Generalizability Limited to Qwen3 Base Models on English-Dominant Reasoning Tasks

**The assumption or constraint.** All experiments use Qwen3-8B-Base and Qwen3-14B-Base as starting points. The paper justifies this choice as enabling "transparent comparison and facilitate[ing] knowledge sharing within the community" (Section 1), but does not evaluate whether the Cascade RL recipe transfers to other model families (Llama, DeepSeek, Mistral), other scales (1B, 32B, 70B), or other languages and modalities. The paper notes in passing that the Math RL recipe was applied to "five different 8B checkpoints and consistently achieved accuracies of around 90% on AIME24 within 500 RL steps" (Section 4.5.2), but these were intermediate checkpoints from the same training pipeline, not different base model families.

Additionally, the entire Cascade RL pipeline is designed around English-language benchmarks and English-language training data. The code-switching penalty mechanisms (Sections 4.5.2, 4.6.2) are explicitly designed to suppress non-English token generation, which improves English benchmark performance but may harm multilingual capability. The paper does not evaluate on multilingual benchmarks or discuss how the cascade would need to be modified for non-English-centric models.

**The consequence.** A practitioner using a non-Qwen3 base model (or a Qwen3 variant with different pretraining data) cannot assume that the hyperparameters, stage ordering, reward function designs, or curriculum schedules described in this paper will transfer. The paper makes specific claims that depend on properties of the Qwen3 base models: the need for a 24K compression stage in Math RL is motivated by Qwen3's tendency to "generate overlong reasoning chains" after SFT (Section 4.5.2); the SWE RL input context length curriculum is bounded by the Qwen3 base models' "limited long-context capability at 32K" (Section 7.3); the choice of Qwen2.5-72B-Instruct over Qwen3-14B as the reward model backbone is based on Qwen3's poor RewardBench performance on preference discrimination (Table 3). These are contingent findings that may not hold for other model families with different pretraining characteristics.

More broadly, the entire difficulty-dependent picture — which problems are "easy," "medium," or "hard," and therefore where the cascade provides benefit — is specific to the Qwen3 base model's capabilities and the English-centric MATH, LiveCodeBench, and SWE-bench benchmarks. A model with different pretraining data might find different problem categories challenging, requiring different curriculum designs.

**What evidence exists in the paper.** The paper's robustness evidence is limited to internal consistency across 8B and 14B scales within the Qwen3 family, and across five intermediate checkpoints during Math RL training. The paper does not report results using any other base model family, nor does it evaluate on non-English benchmarks or multilingual tasks beyond the code-switching penalty's implicit effect.

**Mitigation status.** The paper does not claim generalizability to other model families and acknowledges using Qwen3 base models as a deliberate choice for transparency. The release of full training recipes and data (Section 1) partially mitigates this limitation by enabling the community to test transfer to other base models. However, the paper's specific findings about hyperparameters, curriculum design, and stage ordering may not transfer, and a replication effort on a different base model family would need to re-tune many of these choices from scratch. The paper does not provide guidance on which design choices are likely to be model-family-specific versus universal.
