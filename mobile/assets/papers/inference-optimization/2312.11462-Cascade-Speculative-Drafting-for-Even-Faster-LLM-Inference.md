# Cascade Speculative Drafting for Even Faster LLM Inference

**ArXiv:** [2312.11462](https://arxiv.org/abs/2312.11462)

## 🎯 Pitch

By making draft models review each other instead of generating tokens autoregressively, and by using larger models only for easier, earlier tokens, CS Drafting eliminates the main bottleneck in speculative decoding—achieving up to 81% additional speedup without sacrificing output quality.

---

## 1. Executive Summary

This paper introduces **Cascade Speculative Drafting (CS Drafting)**, a speculative-execution algorithm that improves LLM inference latency by incorporating two orthogonal cascades: the **Vertical Cascade**—which recursively applies speculative decoding so that each neural draft model is itself drafted by a smaller model, ultimately eliminating autoregressive generation from neural models by bottoming out at a statistical language model—and the **Horizontal Cascade**—which allocates larger draft models to generate earlier, higher-acceptance-probability tokens and progressively smaller models for later tokens to optimize time allocation. Evaluated on GSM8K and MMLU with FLAN-T5-XXL as the target model and Vicuna-7B in decoder-only settings, CS Drafting achieves up to an 81% additional speedup over standard speculative decoding on MMLU and a 44% additional speedup on GSM8K, while preserving the target model's exact output distribution, establishing that drafting efficiency can be substantially improved by eliminating autoregressive neural generation and by difficulty-aware token allocation without sacrificing generation quality.

## 2. Context and Motivation

### The Core Problem: The Drafting Bottleneck in Speculative Decoding

The fundamental problem this paper addresses is deceptively specific yet practically consequential: **while speculative decoding accelerates LLM inference by using a smaller draft model to propose tokens that a larger target model verifies in parallel, the drafting process itself remains a significant bottleneck.** The draft model must still generate tokens autoregressively—one after another, each conditioned on all previous tokens—and this sequential generation incurs latency that fundamentally limits how much speedup speculative decoding can achieve.

To understand why this matters, consider the arithmetic of speculative decoding. In standard speculative decoding (Leviathan et al., 2023), each forward pass of the target model is preceded by $k$ forward passes of the draft model (generating $k$ candidate tokens, one at a time). If the target model's forward pass takes time $T$ and the draft model's forward pass takes time $D$, then each speculative step costs $kD + T$ time and produces (on average) some number $\alpha$ of accepted tokens, where $\alpha > 1$ but is typically between 2 and 4. The speedup over autoregressive generation (which costs $T$ time per token) is thus $\alpha T / (kD + T)$. As this expression makes clear, **reducing $D$—the draft model's per-token generation time—directly increases speedup**, potentially more substantially than increasing $\alpha$ (the acceptance rate). Yet prior work focused almost exclusively on improving $\alpha$ through better draft models, while the structure of the drafting cost itself went largely unexamined.

The authors identify two specific inefficiencies within this drafting cost structure:

**First, the draft model generates tokens autoregressively from a neural network, which is inherently slow relative to non-neural alternatives.** Even a draft model two orders of magnitude smaller than the target model requires a full forward pass through its transformer layers for every token it produces. Leviathan et al. explicitly observed that very small models (e.g., ~100× smaller than the target) are usually the best choice for drafting, not because larger draft models produce better-quality drafts (they do), but because the **latency cost** of running a larger draft model $k$ times outweighs the benefit of its higher acceptance rate. The paper quotes this directly: the observation that "very small models... are usually the best choice for drafting because their inference cost is lower compared to that of a larger draft model, despite the fact that larger draft models usually have higher-quality generation" underscores that drafting efficiency—not just draft quality—is the binding constraint.

**Second, all draft tokens are treated as equally worthy of the draft model's time, despite having dramatically different probabilities of being accepted.** The probability that the $i$-th draft token is even *considered* for acceptance by the target model is conditioned on all $i-1$ preceding tokens being accepted. Under the simplifying assumption that each token has independent acceptance probability $p$, the $i$-th token's chance of being reviewed is $p^{i-1}$. Figure 2 quantifies this empirically: on the GSM8K dataset with FLAN-T5-SMALL as the draft model generating 30 tokens per step, the acceptance rate drops from roughly 0.75 for the first token to approximately 0.15 by the 30th token. The pattern is similarly steep for FLAN-T5-BASE and FLAN-T5-LARGE, and replicates on MMLU. Yet standard speculative decoding allocates the same model (and thus the same per-token latency) to generating every draft token, regardless of its position in the sequence. This is a **misallocation of computational effort**: the model spends as much time on the 30th token—which has a ~15% chance of even being reviewed and a lower chance of being accepted conditional on review—as it does on the 1st token with its ~75% review probability.

These two inefficiencies are multiplicative, not additive. A larger draft model both costs more per token and wastes proportionally more of that cost on low-value trailing tokens. The consequence is that speculative decoding hits a speedup ceiling well below what might be theoretically possible if drafting itself could be made faster and more selectively allocated.

### Why This Problem Is Important

The significance of this problem extends well beyond academic curiosity about speculative decoding. It touches on the fundamental economics of LLM deployment.

**Scale amplifies small improvements.** The paper notes that LLM-powered applications "involve an extremely high number of users, up to hundreds of millions daily." At this scale, even marginal latency reductions translate into enormous aggregate compute savings and improved user experience. A 44% additional speedup over speculative decoding (the maximum reported on GSM8K) means that a service previously requiring 100 GPU-hours to process its daily query volume could now do so in approximately 69 GPU-hours—a 31% reduction in absolute cost. For a $14\times$ larger model than the draft models used in this paper, the absolute wall-clock savings per generated token are proportionally larger.

**Latency, not just throughput, is user-facing.** The paper emphasizes that "a low-latency system is not only cost-saving but also crucial for keeping the service running." In interactive applications (chatbots, coding assistants, real-time translation), users experience latency directly. Speculative decoding reduces latency by parallelizing verification, but the draft model's autoregressive generation remains a sequential bottleneck that adds latency before each target model verification step can begin. The Horizontal Cascade's strategy of using faster models for later tokens directly attacks this sequential latency: generating the 30th draft token with a statistical bigram model is effectively instantaneous, whereas generating it with even a small neural model requires a full forward pass.

**The drafting bottleneck is a structural limitation, not a model-specific one.** The inefficiencies the paper identifies are inherent to the speculative decoding paradigm itself—they arise from the autoregressive nature of draft generation and the uniform allocation of drafting effort across token positions. Any system that uses speculative decoding with neural draft models will face these constraints, regardless of the specific architecture, dataset, or task. This means that solving the drafting bottleneck has broad applicability, not narrow model-specific benefits.

**It opens the door to using better draft models.** Recall the counterintuitive finding from Leviathan et al.: larger draft models, despite producing higher-quality drafts, are often *worse* for overall speedup because their per-token cost outweighs their acceptance-rate advantage. If the drafting cost can be reduced—by eliminating autoregressive neural generation through the Vertical Cascade, and by allocating the most expensive model only to the highest-value tokens through the Horizontal Cascade—then the calculus changes. Larger draft models may become net beneficial again, potentially pushing speedup factors higher than currently achievable.

### Where Existing Approaches Fall Short

The paper situates itself against three categories of prior work, each of which leaves the drafting bottleneck unaddressed in different ways.

**Standard speculative decoding (Leviathan et al., 2023; Chen et al., 2023).** The foundational work established that a draft-then-verify paradigm can accelerate sampling without altering output distributions. However, its focus was on the *verification* mechanism—the rejection sampling scheme that guarantees distributional equivalence—rather than on optimizing the *drafting* process. The draft model is treated essentially as a black box: you pick one, you set $k$, and you accept whatever speedup results. Leviathan et al. acknowledged the drafting cost problem implicitly by noting that smaller draft models often win, but they did not propose architectural changes to the drafting process to reduce that cost. CS Drafting can be understood as a drop-in replacement for the drafting component of speculative decoding that leaves the verification mechanism (and thus the distributional guarantee) untouched.

**Methods that reduce rejection rate.** A substantial line of work attacks the speculative decoding speedup equation from the $\alpha$ side: increase acceptance rate, and you get more tokens per target model run. Zhou et al. (2023) use knowledge distillation to train draft models that more closely match the target's distribution. Self-drafting approaches (Zhang et al., 2023; Hooper et al., 2024) reuse parts of the target model itself for drafting, achieving higher acceptance rates without a separate draft model. Tree attention methods (Miao et al., 2024; Cai et al., 2024, as in Medusa) generate multiple candidate tokens at each position, increasing the probability that at least one matches the target model's output. These approaches improve $\alpha$, but they leave the $D$ term—the per-token drafting cost—unchanged or even increased (tree attention generates *more* tokens, not fewer, and self-drafting still requires forward passes through model components). CS Drafting is complementary to all of these: reducing $D$ through cascading and statistical models helps *regardless* of what $\alpha$ is, and the paper explicitly demonstrates this by combining CS Drafting with tree attention for additional gains over Medusa alone (Table 3).

**Staged speculative decoding (Spector and Re, 2023).** The closest prior work to the Vertical Cascade is staged speculative decoding, which also uses speculative decoding to speed up the draft model itself—i.e., a draft model for the draft model. The paper acknowledges this similarity but identifies two critical limitations of the staged approach. First, staged speculative decoding only implements two layers of speculation (draft-of-draft → draft → target) and does not observe the **recursive** nature that the Vertical Cascade exploits: once you accept that a draft model can itself be drafted, you can recurse all the way down to a statistical model whose cost is negligible. Stopping at two layers leaves neural autoregressive generation still present in the innermost draft model. Second, staged speculative decoding does not apply **lenience** among draft models. Lenience (Section 3.1) is a hyperparameter that loosens the acceptance criterion, trading a small distributional deviation for faster rejection and thus faster drafting. The paper's key insight is that lenience can be safely applied at intermediate verification steps (where a draft model verifies a smaller draft model's output) because it does not affect final output distribution—only the target model's verification determines that. Staged speculative decoding misses this optimization. The paper's theoretical analysis (Corollary 4.4) formalizes why recursing fully to a negligible-cost statistical model (where the cost coefficient $c_{d2} \ll 1$) almost always improves efficiency over a single-draft-model system.

**Non-neural drafting is dismissed prematurely.** The paper observes that statistical language models have been overlooked in the speculative decoding literature because, taken alone, their tokens "usually do not have a high probability of being accepted by the target model." But the authors reframe this: a statistical model doesn't need to compete with a neural draft model directly. Instead, it serves as the *foundation* of a cascade where its cheap tokens are refined by progressively larger neural models. The statistical model eliminates the innermost autoregressive loop; the neural models correct its low-quality tokens where necessary. This reframing—that weak drafters become viable when embedded in a verification hierarchy—is a conceptual shift that the paper contributes beyond just the algorithmic mechanics.

### How This Paper Positions Itself

The paper frames CS Drafting not as a competitor to speculative decoding, but as an **orthogonal optimization to the drafting component** that composes with existing speculative decoding methods and their improvements. This is evident in several design choices:

**The verification mechanism is inherited unchanged.** CS Drafting uses the same rejection sampling scheme as standard speculative decoding for the final target model review. This means the distributional guarantee (exact match to target model output) is preserved, and any analysis that applies to speculative decoding's verification applies here as well. The Vertical Cascade introduces intermediate verification steps between draft models, but these use lenience and thus do not affect the final output distribution—the target model's verification is the only one that matters for correctness.

**The algorithm is parameterized to degenerate to standard speculative decoding.** If you set the draft model list to a single neural model and don't use MaG, CS Drafting reduces exactly to speculative decoding. This means CS Drafting can be adopted incrementally: add one statistical model as a foundation drafter, see speedup; add the horizontal cascade, see more speedup; add intermediate draft models, see further speedup. There is no all-or-nothing adoption barrier.

**Composability with orthogonal improvements is demonstrated.** The paper explicitly shows that CS Drafting combined with tree attention (as used in Medusa) outperforms Medusa alone on Vicuna-7B, achieving 63.81 tokens/second vs. 61.87 on GSM8K and 63.37 vs. 56.19 on MMLU (Table 3). This is a direct empirical claim that CS Drafting's drafting optimization stacks with acceptance-rate-improving methods, rather than being rendered redundant by them. The paper positions further combinations—with distillation-based draft models, self-drafting, and other speculative decoding variants—as natural future work.

**The theoretical framework (Section 4) establishes a unified cost model.** By introducing the Expected Walltime Improvement Factor (EWIF) and analyzing both cascades within it, the paper provides a language for reasoning about *any* multi-model drafting system. The generating function approach for the Vertical Cascade (Theorem 4.3) and the position-dependent cost model for the Horizontal Cascade (Theorem 4.5) are not merely justifications for CS Drafting—they are analytical tools that could guide the design of future drafting systems with different model configurations, cost ratios, and acceptance patterns.

**The empirical scope is deliberately broad.** Rather than demonstrating CS Drafting on a single model family or a single task, the paper evaluates on both encoder-decoder (FLAN-T5) and decoder-only (Vicuna-7B) architectures, on two distinct benchmarks (GSM8K: mathematical reasoning; MMLU: factual knowledge across 57 subjects), and under two standardized walltime improvement metrics (model-size-based and prior-work-reported-latency-based) plus raw walltime. This breadth supports the claim that the drafting bottleneck is structural and that the cascading solution is general, not an artifact of a particular model's properties.

In essence, the paper argues that the speculative decoding literature has been asking "How can we make the draft model's outputs more acceptable to the target model?" while neglecting the equally important question: "How can we make the drafting process itself faster and more cost-effective?" CS Drafting answers that second question through two principled mechanisms—recursive speculation to eliminate neural autoregression, and position-dependent model allocation to match drafting cost to token value—that can be combined both with each other and with existing acceptance-rate improvements.

## 3. Technical Approach

This is primarily a **systems paper** that designs an efficient drafting mechanism for speculative decoding. The core idea is that the drafting process itself can be made substantially faster by (1) recursively applying speculation so that no neural model ever generates autoregressively, and (2) allocating drafting effort proportionally to token importance, with larger models generating high-value early tokens and progressively smaller models generating lower-value later tokens.

### 3.1 Reader Orientation

CS Drafting is a **drop-in replacement for the drafting component of speculative decoding** that uses a tiered hierarchy of progressively smaller models—ranging from a full neural draft model down to an instant statistical lookup—to generate candidate tokens for the target model to verify. It solves the dual problem that (a) neural draft models waste time on slow autoregressive generation that could be done by cheaper non-neural models, and (b) standard speculative decoding wastes equal drafting time on all token positions despite later tokens having exponentially lower probability of ever being accepted, by cascading models both vertically (recursive speculation) and horizontally (position-dependent model assignment).

### 3.2 Big-Picture Architecture (Diagram in Words)

The CS Drafting system has four major component types:

1.  **Target Model ($M_t$)** — the large LLM whose output distribution we want to sample from exactly. It verifies complete draft sequences and generates one additional token after acceptance, just as in standard speculative decoding. All distributional guarantees are preserved because the target model's verification mechanism is unchanged.

2.  **Neural Draft Models ($M_{d1}, M_{d2}, \ldots$)** — one or more smaller LLMs from the same family as the target model (e.g., FLAN-T5-BASE and FLAN-T5-SMALL when $M_t$ is FLAN-T5-XXL). Each neural draft model, except the largest, plays a dual role: it is a *draft model* for a larger reviewer (generating token proposals) AND a *reviewer* for a smaller drafter (verifying and correcting its proposals). The largest neural draft model only reviews; the smallest neural draft model only proposes. No neural model ever generates autoregressively from scratch—each is always drafting from a smaller model's output.

3.  **Max-Gram (MaG) Statistical Model** — the foundational drafter at the bottom of the vertical cascade. It is a non-neural model that combines greedy maximal-prefix matching against the input and existing generation with a Wikipedia-trained bigram model as a fallback. Its cost is negligible (memory proportional to vocabulary size, no matrix multiplications), and it eliminates the innermost autoregressive loop entirely.

4.  **Verification and Selection Logic** — the same rejection sampling algorithm as standard speculative decoding, applied recursively. Each reviewer (whether a neural draft model or the target model) receives a sequence of proposed tokens and their probabilities from the smaller drafter, then accepts tokens probabilistically based on the ratio of reviewer to proposer probabilities. The key innovation is that **lenience** (a loosened acceptance criterion) can be applied at intermediate verification steps to speed up rejection without affecting final output distribution, because only the target model's verification determines what the user sees.

**Information flow:** An input prompt enters the system $\rightarrow$ The MaG model greedily matches tokens from the input and generates a batch of cheap draft tokens $\rightarrow$ The smallest neural draft model reviews and refines these tokens (using lenience to quickly reject poor matches) $\rightarrow$ This refined draft is passed to a larger neural draft model for further review and refinement $\rightarrow$ The cascade continues until the largest neural draft model produces a final draft $\rightarrow$ The target model reviews this draft using the standard (non-lenient) speculative decoding acceptance criterion $\rightarrow$ Accepted tokens are emitted as output, and the target model generates one additional token $\rightarrow$ The process repeats for the next chunk. Additionally, the **Horizontal Cascade** is overlaid on this process: within each neural draft model's generation step, the largest available model generates the earliest (highest-value) tokens, while progressively smaller models are allocated to later (lower-value) tokens, controlled by a hyperparameter matrix $K_{nn}$.

### 3.4 Detailed, Sentence-Based Technical Breakdown

---

#### 3.4.1 Max-Gram (MaG) for Statistical Drafting

The MaG algorithm is the foundation that makes both cascades viable. Its purpose is to **generate draft tokens with effectively zero computational cost** compared to neural models, providing a floor from which neural draft models can refine. Without MaG, the vertical cascade would bottom out at some neural model that must still generate autoregressively—defeating the purpose of eliminating autoregressive neural generation. The algorithm operates in two modes: greedy maximal-prefix matching against existing context, and bigram fallback for novel tokens.

**Motivation: input-output token reuse.** The authors observed a general pattern in LLM generation: "some words and phrases from the input query frequently reappear in the generated content." This is particularly true for tasks like summarization (where words from the source article appear in the summary) and mathematical reasoning (where numbers and operators from the problem statement are repeated in the solution steps). The MaG algorithm exploits this by greedily finding the longest matching suffix between the current generation prefix and any substring of the input (or existing generation), then using the token(s) that follow that match in the source as the next predicted token(s).

**Greedy maximal-suffix matching.** Given an input sequence (e.g., the concatenation of the prompt and any previously generated tokens) and the current generation prefix, MaG performs the following search:

1.  Start with the longest possible suffix of the generation prefix—the entire prefix itself.
2.  Check if this suffix appears anywhere in the input sequence.
3.  If it does, return the token(s) immediately following that matched occurrence in the input sequence as the prediction.
4.  If it does not, shorten the suffix by one token (removing the earliest token) and repeat from step 2.
5.  If no match is found even for a single-token suffix, fall back to the bigram model.

This is a **deterministic greedy procedure**: it always finds the longest possible match, and for each match length, it simply checks existence, without probabilistic ranking among multiple matches. In the GPU-friendly implementation (Appendix A, Listing 1), this is implemented efficiently using tensor equality checks and cumulative matching logic rather than iterative Python loops.

**Bigram fallback model.** When no match exists between the current suffix and any input substring, the model falls back to a **bigram language model trained on Wikipedia**. A bigram model estimates $P(\text{next\_token} \mid \text{current\_token})$—it has exactly one conditional token of context. The authors chose Wikipedia "to maintain the generality" of the model across diverse domains, avoiding overfitting to any specific task distribution. The bigram model's parameters are a matrix of size $V \times V$ where $V$ is the tokenizer vocabulary size, making its memory cost negligible by modern standards.

**Why MaG works as a foundation.** The key property that makes MaG useful is not its standalone acceptance rate (which is low compared to neural models) but its **cost-to-quality ratio**. Since MaG incurs essentially zero latency (a few tensor lookups vs. a full transformer forward pass), any token it produces that is eventually accepted saves a full neural forward pass. The vertical cascade then refines MaG's low-quality tokens through successive neural reviewers: even if MaG's acceptance rate by the smallest neural model is modest, the *marginal cost* of generating those tokens is near-zero, so the net efficiency still improves (formalized in Corollary 4.4). The horizontal cascade further benefits because MaG is the ideal model for generating low-value trailing tokens with <15% acceptance probability—allocating a neural model to those positions would be wasteful, but MaG's cost is so low that even rare acceptances are net-positive.

**GPU-friendly implementation.** Appendix A provides the full PyTorch implementation. The core operation is a cumulative matching loop: for suffix length $i$, the algorithm checks whether `input_ids[:, :- (i-1)] == prefix[:, -i:]`, combining this with previous match results via an integer-addition trick (`2 - new_matches == matches[1:]`) to detect sustained matches that extend previous matches. When a match breaks, the algorithm identifies the longest previous match index using `nonzero` and returns the following tokens. The `torch_index` helper wraps `nonzero` for single-value lookup. This implementation avoids Python-level loops over token positions and executes entirely in tensor operations, making it compatible with GPU execution.

**Configuration.** In practice, the authors configure MaG to generate **10 tokens at once** ("it is rare for more than 10 tokens to be accepted"), treating this as a fixed generation length rather than a tunable hyperparameter. This choice is pragmatic: since the probability of all 10 tokens being accepted drops rapidly with length (roughly $p^{10}$), generating more is rarely beneficial, and generating fewer would under-utilize MaG's capacity.

#### 3.4.2 Vertical Cascade

The Vertical Cascade is the **recursive speculative decoding mechanism** that eliminates autoregressive generation from neural models. The key insight is that speculative decoding's principle—a smaller model generates, a larger model verifies—can be applied not just to the target model, but to every neural draft model in the system. Each neural model, rather than generating its draft tokens autoregressively from its own distribution, **receives draft tokens from an even smaller model and only verifies/refines them**. This recursion terminates at the MaG statistical model, whose marginal cost is effectively zero.

**Why recursion matters beyond two layers.** Prior work on staged speculative decoding (Spector and Re, 2023) used exactly two layers: a small neural model drafts for a larger neural model, which drafts for the target model. The Vertical Cascade generalizes this observation: **the recursion can be applied at every level**, not just once. The rationale is formalized in Corollary 4.4, which states: if the cost coefficient $c_{d2}$ of the smaller drafter is much less than 1 (as is the case for MaG), adding that drafter almost always improves net efficiency over a single-draft-model system. This means there is **no natural stopping point** for the recursion—you should keep adding smaller drafters until you hit a model whose cost is negligible. MaG provides exactly such a termination point.

**Mechanism of a single vertical cascade step.** Consider three models: the reviewer $M_r$, the drafter $M_d$, and the sub-drafter $M_{sd}$ (which drafts for $M_d$). The step proceeds as follows:

1.  **Sub-drafting:** $M_{sd}$ proposes a sequence of tokens $\{x_1, \ldots, x_u\}$ along with their probabilities under $M_{sd}$. This is not autoregressive generation from $M_{sd}$—it could be MaG's greedy matching, or it could be the output of a further recursive call if $M_{sd}$ is itself neural and has its own sub-drafter. The critical point is that $M_{sd}$ never runs autoregressively; if it's neural, it's always in reviewer mode.

2.  **Verification by $M_d$:** $M_d$ processes the proposed tokens in parallel (as in standard speculative decoding, the reviewer can evaluate all tokens in a single forward pass). For each token $x_i$, $M_d$ outputs its own probability distribution $M_d(\text{context} + x_1, \ldots, x_{i-1})$ and compares it to $M_{sd}$'s proposal probability. The acceptance criterion uses **lenience** $l \geq 1$:

    For greedy decoding: the token is accepted if $\arg\max M_d = \arg\max M_{sd}$ OR $M_{sd}(x_i) \leq l \times M_d(x_i)$.

    For sampling: the token is accepted if $M_{sd}(x_i) \leq l \times M_d(x_i)$; if not, it is rejected with probability $1 - \frac{l \times M_d(x_i)}{M_{sd}(x_i)}$.

    Lenience $l > 1$ makes acceptance easier for the sub-drafter (the reviewer is more lenient). If a token is rejected, it and all subsequent tokens are discarded, and $M_d$ resamples the rejected token from a recalibrated distribution $\text{norm}(\max(0, M_d - M_{sd}))$.

3.  **Output to next level:** The sequence of accepted tokens (possibly with a resampled final token) becomes the draft for the next reviewer up the cascade—either a larger neural draft model or the target model itself.

**Why lenience at intermediate levels is safe.** The crucial design choice is that **lenience is applied only when draft models review, never when the target model reviews**. The final verification (step where $M_t$ reviews) uses $l = 1$, i.e., the standard exact speculative decoding criterion. This means any distributional "error" introduced by lenient acceptance at intermediate levels gets corrected by the target model's final, exact verification. The intermediate lenience merely determines which tokens survive to be seen by the target model—it does not affect what the target model would have produced autoregressively, because the target model's rejection sampling overrides any intermediate decisions. The authors explicitly state: "this can ensure the final output is not altered while further reducing latency."

**Lenience values and tuning.** The paper uses $l = 3$ or $l = 5$ in practice for intermediate verification steps (Table 5 hyperparameter details), with the exact value treated as a tunable hyperparameter. Higher lenience means faster rejection of poor sub-drafts (the sub-drafter has to clear a lower bar), which reduces the number of wasted verification passes but may let through tokens that the reviewer would not have produced itself. The sweet spot balances these two effects. Lenience is **not applied** between MaG and its reviewer ("since there is still a significant performance gap between MaG and a neural model"), meaning the smallest neural model uses exact ($l=1$) verification on MaG's proposals—the authors presumably found that lenience here lets through too many low-quality tokens that then waste time at higher levels.

**Recursion termination.** The vertical cascade is implemented as a recursive function call (Algorithm 1). The termination condition—the base case—is when the `draftList` is empty, meaning there are no neural draft models left. At that point, the algorithm calls the MaG model directly on the current generation prefix, which returns tokens via greedy matching or bigram fallback. Since MaG is a deterministic function (for a given prefix and input) with negligible cost, this base case eliminates the last autoregressive loop.

**Relationship to cost coefficients.** The theoretical analysis in Theorem 4.3 frames the vertical cascade with two draft models ($M_{d1}$ and $M_{d2}$) in terms of cost coefficients $c_{d1} = \text{time}(M_{d1}) / \text{time}(M_t)$ and $c_{d2} = \text{time}(M_{d2}) / \text{time}(M_t)$. The EWIF (Expected Walltime Improvement Factor) expression (Equation 2) shows that as $c_{d2} \to 0$ (the sub-drafter becomes costless), $\phi_{\alpha', k}(\alpha) < \alpha$, which makes the numerator larger than the single-drafter case while the denominator only grows by the negligible $nk c_{d2}$. In plain terms: **adding a near-zero-cost sub-drafter improves net efficiency almost unconditionally** because the sub-drafter's negligible cost is more than compensated by the drafting speedup it provides to the neural model above it.

#### 3.4.3 Horizontal Cascade

The Horizontal Cascade addresses the **position-dependent value of draft tokens** by allocating larger, slower models to earlier token positions and progressively smaller, faster models to later token positions. The justification is the empirical observation in Figure 2: the probability of a draft token being accepted drops steeply with its position in the draft sequence, roughly following an exponential decay (the $n$-th token requires $n$ preceding acceptances, each with probability $\sim p$, giving acceptance probability $\sim p^n$).

**The exponential decay of token value.** The paper formalizes this in the theoretical setup for Theorem 4.5 using i.i.d. Bernoulli acceptance events. Let $\alpha_i$ be the probability that token $i$ is accepted by the target model, conditional on all previous tokens being accepted. Then:

-   The probability that token $i$ is even *reviewed* by the target model is $\prod_{j=1}^{i-1} \alpha_j$.
-   The *marginal contribution* of token $i$ to the expected number of accepted tokens is $\prod_{j=1}^{i} \alpha_j$, which decreases with $i$ (since $\alpha_j < 1$ for all $j$).

Figure 2 empirically validates this. On GSM8K with FLAN-T5-SMALL generating 30 tokens per step, $\alpha_1 \approx 0.75, \alpha_5 \approx 0.40, \alpha_{15} \approx 0.25, \alpha_{30} \approx 0.15$. The cumulative probability of the 15th token being reviewed is the product of the first 14 acceptance rates—already well below 1%. This means the 15th through 30th draft tokens contribute very little to expected output but cost exactly as much to generate as the 1st token.

**Position-dependent model allocation.** The Horizontal Cascade partitions the $k$ draft tokens that a given neural reviewer will verify into segments, with each segment generated by a different model. The **largest available neural draft model** generates the first segment (e.g., tokens 1–5), a smaller neural model generates the next segment (e.g., tokens 6–10), an even smaller model generates the following segment (e.g., tokens 11–15), and MaG generates the trailing segment (e.g., tokens 16+). The intuition is:

-   Early tokens have high acceptance probability, so investing a larger model's higher quality (and thus higher $\alpha_i$) here directly increases the expected number of accepted tokens.
-   Later tokens have low acceptance probability, so using a cheaper model here saves cost even if the per-token acceptance rate is lower—the savings in drafting time outweigh the expected loss in accepted tokens.

The combined effect is formalized in Theorem 4.5's EWIF expression:

$$T(k, \alpha_1, \ldots, \alpha_k, c_1, \ldots, c_k) = \frac{\sum_{i=0}^k \prod_{j=1}^i \alpha_j}{1 + \sum_{i=1}^k c_i}$$

where $k$ is the number of draft tokens, $\alpha_j$ is the acceptance probability of drafting model $M_j$ (the model assigned to position $j$) by the target model, and $c_j$ is the cost coefficient for model $M_j$ (its forward pass time relative to the target model's).

**What it computes:** the numerator is the expected number of accepted tokens per speculative step, summing over all possible acceptance counts $i$ (from 0 to $k$) weighted by the probability that exactly $i$ tokens survive. The denominator is the total cost of one speculative step: 1 for the target model's forward pass, plus the sum of cost coefficients for each draft model's forward pass. The ratio gives the expected tokens-per-unit-time, normalized by the target model's per-token autoregressive cost so that $T(k, \ldots) > 1$ means speedup.

**Why this form matters:** it makes the tradeoff between model quality ($\alpha_i$) and model cost ($c_i$) explicit and position-dependent. In standard speculative decoding, $\alpha_i = \alpha$ and $c_i = c$ for all $i$, so the expression simplifies to the known speculative decoding speedup formula. The Horizontal Cascade replaces uniform $(\alpha, c)$ with a sequence $\{(\alpha_i, c_i)\}$ where $\alpha_i$ decreases (weaker models for later tokens) but $c_i$ decreases faster (cheaper models for later tokens). The net effect depends on the relative slopes of these two curves.

**Corollary 4.6: sensitivity analysis.** The paper computes the partial derivative of EWIF with respect to $\alpha_l$:

$$\frac{dT}{d\alpha_l} = \frac{\sum_{i=l}^k \prod_{j=1, j \neq l}^i \alpha_j}{1 + \sum_{i=1}^k c_i}$$

This derivative has a clear interpretation: **the impact of improving acceptance at position $l$ is proportional to the cumulative acceptance probability of all positions from $l$ to $k$.** For early positions ($l = 1$), this sum is large (many downstream tokens benefit from a good start). For late positions ($l \approx k$), the sum is small (only the token itself and any even-more-trailing tokens benefit, and those are already low-probability). This directly justifies the Horizontal Cascade's allocation: invest quality where the derivative is largest (early positions) and save cost where it is smallest (late positions).

**The hyperparameter matrix $K_{nn}$.** The division of draft tokens into position-dependent segments is governed by an **upper-triangular matrix** $K_{nn}$, where $n$ is the number of neural draft models. Each row $i$ of this matrix specifies how many tokens the $i$-th draft model (counting from largest to smallest) should generate when drafting for the model directly above it, with the column index determining which smaller models generate which token ranges. The upper-triangular structure reflects causality: a larger model can allocate tokens to itself and all smaller models, but a smaller model cannot allocate tokens to a larger model.

In practice (Table 5), the hyperparameters are simplified. For a two-draft-model system (BASE, SMALL, MaG) on GSM8K with model-size-based SWI, the effective structure is $k_{11} = 8$ (BASE generates up to 8 tokens when drafting for the target model, with the first few from itself and later ones from SMALL/MaG) and $k_{12} = 13$ (the combined token limit when including SMALL-drafted tokens within BASE's review), with $k_{22} = 1$ (a detail controlling SMALL's review of MaG). The exact allocation logic is encoded in the for-loop of Algorithm 1, where each draft model iterates and calls the recursive function with a `curK` submatrix representing the allocation for draft models below it.

**Integration with the Vertical Cascade.** The horizontal cascade is implemented as the **for-loop** structure in Algorithm 1, operating within each layer of the vertical cascade. When a reviewer $M_{d_i}$ receives a draft from its sub-drafter, it doesn't simply verify all tokens at once. Instead, it iterates through the draft models below it (the for loop from $i$ to $n$), for each one:

1.  Checking the $K_{nn}$ matrix to determine how many tokens the current sub-drafter should contribute.
2.  Calling the recursive `CascadeSpeculativeDraftingStep` to get that sub-drafter's generation.
3.  Accumulating the accepted tokens into `curGen`.
4.  Moving to the next (smaller) model in the cascade for the next token range.

This means each neural reviewer sees tokens from potentially multiple sub-drafters in a single draft sequence, with the allocation following the position-dependent principle: earlier positions come from the first (largest) sub-drafter in the list, later positions from smaller sub-drafters, and the final positions from MaG.

**Simulated validation.** Before running full experiments, the authors validated the horizontal cascade concept via EWIF simulation (Table 1) using Bernoulli acceptance assumptions and cost coefficients from Leviathan et al. (2023). On CNN/DailyMail, standard speculative decoding with FLAN-T5-SMALL (9 draft tokens) achieved EWIF 2.65; with FLAN-T5-BASE (8 tokens), EWIF 2.96. Adding a horizontal cascade where BASE generates the first 5 tokens and SMALL generates the next 3 tokens improved EWIF to 3.03—a 2.4% improvement over BASE alone, despite using the same total number of draft tokens. On WMT EnDe, the improvement was larger: from 3.75 (BASE, 11 tokens) to 3.93 (BASE 5 + SMALL 8) with more tokens drafted. This simulation provided proof-of-concept that allocating position-specific models can improve upon any single model's performance.

#### 3.4.4 The Combined CS Drafting Algorithm

Algorithm 1, `CascadeSpeculativeDraftingStep`, unifies the vertical and horizontal cascades in a single recursive procedure. The algorithm takes as input:

-   `draftModels`: an ordered list of neural draft models $[M_{d1}, M_{d2}, \ldots, M_{dn}]$ from largest to smallest.
-   `targetModel`: $M_t$, the target model.
-   `prefix`: the current generation prefix (prompt + previously accepted tokens).
-   `isFirstCall`: a boolean flag that distinguishes the top-level call (where $M_t$ reviews) from intermediate recursive calls (where a neural draft model reviews).
-   `Knn`: the hyperparameter matrix controlling horizontal token allocation across draft model tiers.
-   `l`: the lenience hyperparameter (applied at intermediate levels but overridden to 1 for the target model review).

**Core structure.** The algorithm interleaves two mechanisms:

1.  **Recursive calls (vertical cascade).** The function calls itself with a reduced `draftList` (removing the current reviewer, so the next call has one fewer model) and a reduced `curK` (the submatrix of $K_{nn}$ for the remaining draft models). This recursion continues until `draftList` is empty, at which point the base case executes (calling MaG).

2.  **For-loop iteration (horizontal cascade).** Within each recursive level, the reviewing model (either a neural draft model or the target model) iterates through the remaining draft models in order, calling the recursive function for each to obtain that sub-drafter's generation, and accumulating tokens until the $k_i$ limit for the current position range is reached. The while-loop condition `curGen.length - curPrefix.length < k_i` ensures that enough tokens are generated from the current sub-drafter before moving to the next.

**Step-by-step execution for a concrete example.** Consider the three-draft-model setup from Figure 1: $M_{d1}$ = BASE, $M_{d2}$ = SMALL, $M_{d3}$ = MaG, with target model $M_t$ = XXL. The top-level call is `CascadeSpeculativeDraftingStep([BASE, SMALL, MaG], XXL, prefix, True, Knn, l)`.

1.  **Initialize:** `curGen = prefix`, `curProbs` is a list of ones (the prefix tokens are deterministically given, so their "proposal probabilities" for acceptance computation are 1), `draftList = [BASE, SMALL, MaG]`.

2.  **Unpack $K_{nn}$ first row:** For the top-level call, the first row of $K_{nn}$ specifies the token allocation for models below XXL. Let's say $[k_1, k_2] = [8, 13]$, meaning BASE will contribute up to a total of 8 tokens (with the earliest from itself via further recursion, and later ones from SMALL/MaG), and the cumulative allocation across all drafters won't exceed 13.

3.  **For loop ($i=1$):** `curTarget = BASE` (the first element of `draftList`), `curDraftList = [SMALL, MaG]`, `curK` is the submatrix starting at $(2,2)$. The while-loop runs until BASE's token contribution limit $k_1 = 8$ is reached.
    -   Inside the while-loop, the recursive call is `CascadeSpeculativeDraftingStep([SMALL, MaG], BASE, curPrefix, False, curK, l)`. This is the **second-level call**.
    -   In this second-level call: `draftList = [SMALL, MaG]`, `prefix` is whatever BASE has accepted so far, `isFirstCall = False` (so lenience $l$ will be applied), and the unpacked $k$-values come from the first row of `curK` (e.g., [1, 11]).
    -   The for-loop iterates: $i=1$ (SMALL reviews), `curDraftList = [MaG]`, `curK` submatrix starts at $(2,2)$. The while-loop runs until SMALL's token limit is reached. Inside, recursive call: `CascadeSpeculativeDraftingStep([MaG], SMALL, curPrefix, False, curK, l)`.
    -   In this **third-level call**: `draftList = [MaG]`. The for-loop runs once ($i=1$), with `curTarget = MaG`, `curDraftList = []`.
    -   Inside this for-loop, recursive call: `CascadeSpeculativeDraftingStep([], MaG, curPrefix, False, curK, l)`.
    -   **Base case reached:** `draftList` is empty! The algorithm calls `M = MaG`, executes `M(curGen)` to produce tokens via greedy matching/bigram fallback, and returns these tokens and a dummy logits value.

4.  **Unwinding the recursion:** The base case returns MaG's proposed tokens to SMALL. SMALL reviews these tokens with lenience $l$, accepting/rejecting/resampling as per the lenient speculative decoding rule. SMALL accumulates tokens until its limit is reached (controlled by the while-loop in the third-level call). Then SMALL's accepted tokens are returned to BASE in the second-level call. BASE reviews them with lenience $l$, again accepting/rejecting/resampling. BASE accumulates tokens until its limit $k_1$ is reached. Then BASE's accepted tokens are returned to the top-level call.

5.  **Target model review:** Back in the top-level call, after the for-loop completes (all draft models have contributed their tokens), the algorithm sets $l = 1$ (because `isFirstCall` is True) and calls `review(Mt, curGen, curProbs, l=1)`. This applies the standard, exact speculative decoding verification to the entire draft sequence produced by the cascade. Any tokens not accepted by $M_t$ are resampled from the target model's own distribution, guaranteeing exact output matching.

**The `isFirstCall` flag and lenience.** The purpose of this flag is to ensure that **only the intermediate verification steps use lenience**. When `isFirstCall` is True (the top-level call where $M_t$ is the reviewer), `l` is set to 1 regardless of the configured lenience value. When `isFirstCall` is False (intermediate calls where a neural draft model is the reviewer), the configured `l > 1` is used. This is what the paper means by "we can limit the application of lenience in the vertical cascade only when draft models review and do not apply lenience when the target model reviews."

**The incremental accumulation of `curGen` and `curProbs`.** The algorithm maintains `curGen` (current accumulated accepted token sequence) and `curProbs` (a list of proposal probabilities for each token) throughout the recursion unwinding. Each recursive call returns both the generated token sequence and the probability logits, which the parent call uses for its own review step. The `s` variable tracks the starting index for new probability entries, ensuring they are appended at the correct position.

**Review function.** The `review` function at the end of Algorithm 1 implements the speculative decoding acceptance/rejection logic described in Section 2 (Preliminary). It takes the reviewer model, the draft token sequence, the draft probabilities, and the lenience parameter, and returns the accepted tokens with their reviewer-assigned probabilities. The paper does not provide separate pseudocode for this function because it is exactly the standard speculative decoding verification step with the addition of the lenience parameter modifying the acceptance criterion (the lenience factor $l$ scales $M_t(x)[i]$ or modifies the rejection probability formula).

**Why this recursive design is efficient.** The recursion and for-loop structure might appear to add overhead, but the key property is that **each neural model runs at most once per speculative step** (in reviewer mode, which is a single parallel forward pass), and the MaG model runs at most once per call chain (a deterministic O(prefix length) matching operation). This replaces the standard speculative decoding's $k$ sequential forward passes of the draft model (autoregressive generation) with: one parallel forward pass of each neural draft model (in reviewer mode) + negligible MaG matching. The tradeoff is that the acceptance rates at intermediate levels (draft model reviewing sub-draft model) are lower than if the draft model generated autoregressively, because the sub-drafter is weaker. But since the intermediate review is fast (the reviewer evaluates all tokens in parallel) and lenience speeds up rejection, the net effect is positive as long as the cost savings from eliminating autoregression exceed the acceptance-rate penalty—which Corollary 4.4 guarantees when the innermost drafter has near-zero cost.

**Default hyperparameters for decoder-only models.** To demonstrate practicality without per-task tuning, the paper provides a fixed default hyperparameter setting for decoder-only experiments: $K_{nn} = [[2, 10], [0, 10]]$. This means: at the top level, the first draft model contributes up to 2 tokens (early, high-value positions) and the total draft length with all drafters is up to 10; at the second level, the second draft model contributes up to 10 tokens when reviewing for the first draft model. This simple configuration already outperforms standard speculative decoding, supporting the claim that "end users who do not require maximum performance can use a simple setup to achieve near-optimal performance."

## 4. Key Insights and Innovations

### Innovation 1: The Drafting Process Itself Is the Bottleneck—Not Just Draft Quality

The dominant assumption in speculative decoding research, from Leviathan et al. (2023) onward, has been that the primary route to better speedup is improving **draft quality**—that is, increasing the acceptance rate α so that more tokens are accepted per target model forward pass. This assumption motivated a substantial body of follow-up work: knowledge distillation to align draft and target distributions (Zhou et al., 2023), self-drafting from the target model's own parameters (Zhang et al., 2023; Hooper et al., 2024), and tree attention to propose multiple candidates per position (Miao et al., 2024; Cai et al., 2024). All of these attack the numerator of the speedup equation.

CS Drafting makes a fundamentally different diagnostic move: it argues that **the drafting cost itself—the denominator of the speedup equation—is the binding constraint, not merely draft quality**. The paper's reframing is visible in how it reads the Leviathan et al. finding that very small models are usually the best drafters. The standard reading of that finding was: "small draft models are good enough." CS Drafting's reading is: "even when larger draft models produce better tokens, their **latency cost** outweighs that benefit, which means the drafting process is structurally too expensive." This shift from "draft quality is what matters" to "draft efficiency is what's limiting us" is the conceptual foundation on which both cascades rest.

The evidence for this reframing is partly the empirical observation in Figure 2—that later tokens have exponentially diminishing value, yet cost the same to generate—and partly the broader structural argument that autoregressive generation from *any* neural model, however small, incurs a per-token latency that fundamentally caps speedup. The paper's language is deliberate: "the drafting process in speculative decoding includes slow autoregressive generation and allocates equal time to generating tokens, irrespective of their importance. These inefficiencies collectively contribute to the suboptimal performance of speculative decoding." Note the dual diagnosis: slow generation AND equal allocation. Neither alone is the full story; together they define the drafting bottleneck.

This is a **fundamental reframing** rather than an incremental improvement. It doesn't propose a better draft model or a better verification scheme—it questions whether the drafting architecture itself (one model, autoregressive, uniform across positions) is the right one. The practical consequence is that CS Drafting's gains stack with *all* quality-improving methods, because it operates on a different term in the speedup equation. Table 3 demonstrates this directly: CS Drafting + tree attention (63.81 tokens/s on GSM8K) outperforms Medusa (tree attention alone, 61.87 tokens/s), because tree attention improves α while CS Drafting reduces drafting cost—and the improvements are additive.

### Innovation 2: Statistical Language Models Become Viable When Embedded in a Verification Hierarchy

Statistical language models (bigrams, n-grams) have been largely ignored in the speculative decoding literature for an obvious reason: their tokens have low probability of being accepted by a large neural target model. The paper acknowledges this directly—"tokens generated by statistical language models usually do not have a high probability of being accepted by the target model"—and the field's implicit conclusion has been that statistical models are therefore not useful as drafters.

CS Drafting overturns this conclusion through a **conceptual reframing of what a drafter needs to be**. A statistical model does not need to compete with a neural draft model on acceptance rate. It needs only to be **useful as the foundation of a cascade**, where its cheaply-generated tokens are refined by progressively larger neural models. The key insight is that verification is much cheaper than generation (the reviewer processes all tokens in parallel in one forward pass), so a neural model can *correct* a statistical model's low-quality output far more efficiently than it can *generate* tokens from scratch autoregressively.

The formal backing comes from Corollary 4.4: when the cost coefficient $c_{d2}$ of the innermost drafter approaches zero (as it does for MaG, which requires only vocabulary-sized memory lookups), adding that drafter almost always improves net efficiency, even if its acceptance rate is modest. The intuition: the statistical model's cost is so low that *any* token it contributes that survives the verification chain is essentially a free token—it displaces a neural forward pass that would otherwise have been required. The paper's finding that CS Drafting with a single neural model plus MaG (e.g., BASE + MaG) consistently outperforms the best single-draft-model speculative decoding setup (e.g., BASE alone, or SMALL alone, whichever was optimal) demonstrates this empirically. On MMLU, BASE + MaG achieves a 70% speedup over the fastest speculative decoding baseline; on GSM8K, 32%.

This is a **fundamental shift** in how to think about drafter design. Prior work asked: "How can we train or select a draft model that produces tokens the target model will accept?" CS Drafting asks: "What is the cheapest possible source of tokens that, after refinement through intermediate verifiers, still contributes net-positive to efficiency?" The answer turns out to include models that would be rejected as standalone drafters. This opens a new design space: the optimal drafter is not the one with the highest α, but the one with the best **α-to-cost ratio** at its position in the hierarchy, which can include non-neural models at the bottom.

### Innovation 3: Position-Dependent Value of Draft Tokens Demands Position-Dependent Allocation

Figure 2 is the paper's most important empirical diagnostic. It shows, across three model sizes and two datasets, that the probability of a draft token being reviewed (and thus potentially accepted) drops steeply with its position in the draft sequence—from roughly 0.75 at position 1 to roughly 0.15 at position 30 for FLAN-T5-SMALL on GSM8K. This exponential decay is a structural consequence of speculative decoding: token $i$ can only be reviewed if all $i-1$ preceding tokens are accepted, so its review probability compounds all previous acceptance probabilities.

The field has been implicitly aware of this phenomenon—it follows directly from the speculative decoding mechanism—but **no prior work had treated it as an optimization lever**. Standard speculative decoding allocates the same model (and thus the same per-token cost) to every draft token regardless of position. Spector and Re's staged speculative decoding (2023) uses different models at different *stages* of the pipeline, but the allocation is based on model hierarchy (a draft model for the draft model), not on token position within a single draft sequence.

CS Drafting's Horizontal Cascade is the **first explicit, principled framework for position-dependent drafter allocation**. The theoretical analysis in Theorem 4.5 and Corollary 4.6 provides the formal justification: the partial derivative of speedup with respect to acceptance rate at position $l$ is proportional to the cumulative acceptance probability of all positions from $l$ to $k$. This derivative is largest at position 1 (improving early-token quality benefits all downstream tokens) and smallest at position $k$ (improving late-token quality benefits almost nothing, since most sequences never reach that far). The prescription follows directly: allocate the most expensive, highest-quality model to position 1, and progressively cheaper models to later positions.

The significance of this insight extends beyond the specific models used in the paper. It provides a **general design principle** for any multi-model drafting system: the cost-quality Pareto frontier should be navigated *along the token position axis*, not just along the model-selection axis. If a practitioner has access to three draft models of different sizes, the Horizontal Cascade tells them to use the largest for the first few tokens, the medium for the middle tokens, and the smallest for the trailing tokens—a concrete allocation strategy that emerges from the EWIF optimization, not an ad hoc heuristic. The simulated EWIF results in Table 1, showing that a position-dependent allocation (BASE for first 5 tokens, SMALL for next 3) exceeds the performance of either model alone, validate the principle in a controlled setting before the full experimental deployment.

### Innovation 4: Lenience Is a Safe Optimization When Scoped to Intermediate Verification

Lenience in speculative decoding—loosening the acceptance criterion so that the reviewer rejects draft tokens more aggressively—was introduced by Leviathan et al. (2023) as an optional speed-quality tradeoff: you can go faster, but you deviate from the target model's exact output distribution. For most applications where distributional fidelity matters, lenience is therefore "generally undesirable" (as the paper acknowledges).

CS Drafting makes a **critical scoping insight**: lenience only affects the final output distribution if it is applied at the **final** verification step, where the target model reviews. If lenience is applied at **intermediate** verification steps—where a neural draft model reviews a smaller drafter's output—it does not change what the target model would ultimately produce, because the target model's exact verification overrides all intermediate decisions. The target model sees only the tokens that survive the lenient intermediate reviews and applies the standard (non-lenient) acceptance criterion to them. Any tokens that sneak through due to lenience but would not have been produced by the target model will still be rejected at the final step; any tokens correctly rejected early due to lenience were going to be rejected anyway, and lenience just saved the computational cost of carrying them through additional intermediate reviews.

This is a **subtle architectural insight** rather than an algorithmic one. It doesn't change what the speculative decoding algorithm does—it changes *where* in the recursive cascade a known technique is safe to apply. The paper's explicit handling of this in Algorithm 1, with the `isFirstCall` flag overriding lenience to 1 for the target model review, demonstrates the care required. The empirical consequence is that CS Drafting gets the speed benefit of aggressive intermediate rejection without the distributional cost that would normally accompany lenience.

The significance is practical but substantial: it makes the vertical cascade more efficient than it would be with exact verification at every level. If each intermediate reviewer had to use $l=1$, it would spend more time on tokens from the sub-drafter that are marginally below the reviewer's own distribution—tokens likely to be rejected by the next level up anyway. Lenience accelerates this by letting the intermediate reviewer quickly discard marginal tokens, reducing the total verification work throughout the cascade. The paper uses $l=3$ or $l=5$ in practice (Table 5) without reporting any distributional deviation, confirming empirically that scoped lenience is safe.

### Innovation 5: Unified Cost Model for Multi-Model Drafting Systems

Prior work on speculative decoding with multiple models (Spector and Re, 2023) provided empirical demonstrations but no unifying theoretical framework for reasoning about cost, acceptance, and allocation tradeoffs. CS Drafting contributes the **Expected Walltime Improvement Factor (EWIF)** framework that formalizes these tradeoffs for arbitrary cascades of drafting models, with the Vertical Cascade analyzed via generating functions (Theorem 4.1, Theorem 4.3) and the Horizontal Cascade analyzed via position-dependent cost and acceptance coefficients (Theorem 4.5, Corollary 4.6).

What distinguishes this from the standard speculative decoding analysis (Leviathan et al., 2023) is that EWIF is **compositional**: it handles recursive model hierarchies (vertical) and position-dependent model assignments (horizontal) within a single analytical language. The generating function approach for the vertical cascade is particularly elegant. Rather than manually computing expected acceptance lengths for $n$ speculative steps of a two-model system (which would involve nested sums), the generating function $\phi^n(x)$ represents the entire distribution of summed acceptance lengths in closed form, and the operator $T_\alpha(f(x)) = \frac{1-\alpha f(\alpha)}{1-\alpha}$ extracts the expected accepted tokens from that generating function in one step. This makes the analysis of the vertical cascade as tractable as the single-drafter case, despite the recursive structure.

The practical value of this framework is that it enables **reasoning about design choices without exhaustive experimentation**. Corollary 4.4 proves, under the i.i.d. Bernoulli acceptance assumption, that adding a sub-drafter with near-zero cost always improves EWIF—a result that would be difficult to establish convincingly through empirical sweeps alone, given the combinatorially many hyperparameter configurations. The simulated EWIF results in Table 1 demonstrate using the model to predict that a horizontal cascade of BASE + SMALL will outperform either model alone, before the full algorithm is implemented and tested. This shifts the development process from "try configurations and measure" to "model the tradeoffs analytically, then verify empirically"—a more principled approach to systems design.

This is an **incremental but methodologically significant** contribution. The Bernoulli i.i.d. assumption is known to be a simplification, and Leviathan et al. already demonstrated that it aligns reasonably well with empirical results in the single-drafter case. The innovation here is extending that modeling approach to the **compositional** setting—showing that the same simple assumptions yield tractable, predictive analyses for multi-model, position-dependent systems. Whether the i.i.d. assumption holds as well for MaG's acceptance patterns (which are deterministic and input-dependent) as for neural models' remains an open question, but the framework itself is a reusable tool for future multi-drafter system design.

## 5. Experimental Analysis

### Evaluation Methodology

**Datasets.** The paper evaluates on two benchmarks: **GSM8K** (Cobbe et al., 2021), a dataset of 8,500 grade-school math word problems requiring multi-step arithmetic reasoning (2–8 steps typically), and **MMLU** (Hendrycks et al., 2021), a benchmark covering 57 diverse subjects from elementary science to advanced law designed to test broad factual knowledge. Both datasets represent tasks where LLMs are commonly deployed and where long-form generation makes latency a practical concern. Crucially, these datasets differ in nature—GSM8K demands structured, multi-step reasoning, while MMLU requires fact retrieval across domains—providing evidence that the method's benefits are not confined to a single task type. All experiments use a zero-shot chain-of-thought prompting setup (Kojima et al., 2022; Wei et al., 2023), meaning no task-specific fine-tuning or few-shot examples are provided, aligning with "current common usage" where models are expected to generalize without per-task adaptation.

**Base model(s).** Two model families are tested to demonstrate generality across architectures. For **encoder-decoder** experiments, the paper uses the FLAN-T5 family (Chung et al., 2022), with FLAN-T5-XXL (11B parameters) as the target model and FLAN-T5-BASE (~250M parameters) and FLAN-T5-SMALL (~80M parameters) as neural draft models. This family was chosen because "there is a large variation in model sizes within the FLAN-T5 family (ranging from 77 million to 11 billion parameters)," providing a natural range of draft-to-target size ratios. For **decoder-only** experiments, the target model is Vicuna-7B (Zheng et al., 2023), a fine-tuned version of LLaMA (Touvron et al., 2023), with a 68M-parameter model sharing the same tokenizer as the reviewing draft model. The decoder-only setup additionally incorporates tree attention (Miao et al., 2024; Cai et al., 2024, as used in Medusa) to demonstrate composability with orthogonal speculative decoding improvements. The Max-Gram (MaG) statistical model serves as the generating (bottom-level) drafter in all CS Drafting configurations.

**Metrics.** Three latency metrics are reported:

- **Standardized Walltime Improvement (SWI) with Model Size (MS):** assumes each forward pass of a model takes time proportional to its parameter count. This is fully reproducible across hardware and serves as a hardware-independent speedup metric. The speedup is computed as the ratio of autoregressive generation time to the speculative method's generation time under this assumption.

- **Standardized Walltime Improvement (SWI) with Prior Work (PW):** uses the recorded time cost data from Leviathan et al. (2023) as the per-model latency assumption. This anchors the cost model to a specific prior empirical measurement while still being reproducible.

- **Raw Walltime:** the actual elapsed time measured in tokens generated per second on the experimental GPU (a single NVIDIA A40). This represents real-world performance for an individual user but is sensitive to hardware variation, GPU load, and implementation details. The paper acknowledges this sensitivity explicitly (Section 8, Limitations).

All experiments use **greedy decoding (temperature 0)** , which the paper justifies by noting no significant difference between temperature-1 sampling and greedy decoding was observed in prior speculative decoding experiments (Leviathan et al., 2023), and because greedy decoding ensures full reproducibility. This is an important constraint on the scope of the empirical validation: results for stochastic sampling with non-zero temperature are not directly demonstrated, though the theoretical framework (Theorem 4.1, etc.) covers the sampling case.

**Baselines.** The paper compares against:

- **Autoregressive generation:** the target model generating tokens one-by-one without any speculative execution. This is the 1× speedup baseline against which all improvements are measured.

- **Speculative Decoding (Leviathan et al., 2023):** standard speculative decoding with a single neural draft model. Multiple draft model sizes are tested (FLAN-T5-BASE, FLAN-T5-SMALL for encoder-decoder; 68M model for decoder-only) to find the best single-drafter configuration. This is the primary head-to-head baseline, as CS Drafting is a drop-in replacement for the drafting component.

- **Medusa (Cai et al., 2024):** for the decoder-only experiments, Medusa's tree attention approach is included as an additional baseline representing the state of the art in acceptance-rate-focused speculative decoding improvements. CS Drafting is also combined with tree attention to test composability, creating a "CS Drafting + Tree Attention" configuration.

For CS Drafting itself, multiple cascade depths are evaluated: one neural model + MaG (e.g., BASE + MaG or SMALL + MaG), and two neural models + MaG (e.g., BASE + SMALL + MaG). This provides an ablation over cascade depth within the CS Drafting framework.

**Generation budget / compute accounting.** The paper does not impose a fixed "generation budget" in the way that static compute-allocation papers do (e.g., "allocate 256 forward passes"). Instead, the accounting is **implicit in the speedup metric**: all methods generate the same output distribution at different wall-clock speeds. The SWI and walltime metrics naturally account for the cost of all forward passes (target, neural draft, and MaG matching) because they measure total elapsed time or per-token cost coefficients, not just the number of accepted tokens. The hyperparameters controlling how many tokens each drafter attempts to generate ($K_{nn}$ matrix values) are swept and reported (Table 5, Appendix B), with the understanding that more aggressive drafting (larger $k$ values) increases both the expected number of accepted tokens AND the drafting cost. The optimal hyperparameters balance these two effects.

For the standardized metrics, the SWI (MS) assumes the cost coefficient $c(M_t, M_d)$ is the ratio of parameter counts (e.g., FLAN-T5-BASE has 250M parameters to FLAN-T5-XXL's 11B, giving $c \approx 0.023$). The SWI (PW) uses the latency ratios reported in Leviathan et al. (2023), which presumably reflect actual measured forward-pass times on their hardware. These two SWI variants provide a sensitivity analysis: if the parameter-count heuristic overestimates or underestimates the true cost ratio, the PW variant using measured times should capture that.

**Cross-validation / statistical protocol.** The paper does **not** report cross-validation, confidence intervals, or statistical significance tests. Hyperparameter selection is done per-dataset (Table 5 reports the chosen hyperparameters for each configuration) without specifying a held-out validation procedure. The decoder-only experiments deliberately use a fixed default hyperparameter setting ($K_{nn} = [[2, 10], [0, 10]]$) across datasets "to better align with most users who do not perform hyperparameter tuning," which is a practical choice but means the reported decoder-only results may under-represent the peak achievable performance if per-dataset tuning were performed. The reproducibility of walltime measurements is not explicitly addressed (e.g., number of runs, variance across runs, warmup steps), which is a limitation for the raw walltime results given the sensitivity to hardware state.

### Main Quantitative Results

#### Encoder-Decoder Results on FLAN-T5 (Table 2, Table 5)

Table 2 presents the primary experimental results for the FLAN-T5 family on GSM8K and MMLU under two SWI metrics (MS and PW). The headline finding is that **CS Drafting consistently outperforms standard speculative decoding across all configurations and datasets**, with the maximum improvement occurring when both cascades are fully deployed (BASE + SMALL + MaG).

**GSM8K results.** On GSM8K with the model-size SWI metric:
- Standard speculative decoding achieves speedup of 3.38× with FLAN-T5-BASE as drafter and 3.06× with FLAN-T5-SMALL. BASE is the stronger single drafter here.
- CS Drafting with BASE + MaG (one neural model cascade) achieves 3.70× speedup, a **9.5% improvement** over the best single-drafter speculative decoding (3.38× → 3.70×).
- CS Drafting with SMALL + MaG achieves 3.19×, which is a 4.2% improvement over SMALL speculative decoding alone (3.06× → 3.19×). Notably, SMALL + MaG does not outperform BASE speculative decoding alone, indicating that the vertical cascade's benefit depends on the quality of the neural drafter being cascaded—a weak drafter with MaG may still underperform a stronger standalone drafter.
- CS Drafting with BASE + SMALL + MaG (two neural models) achieves **3.88× speedup**, a **14.8% improvement** over the best single-drafter speculative decoding (3.38× → 3.88×) and a 4.9% improvement over the one-neural-model cascade (BASE + MaG, 3.70×). This demonstrates that adding intermediate draft models in the vertical cascade provides additional gains beyond a single neural + statistical cascade.

Under the prior-work SWI metric (PW), the pattern holds with slightly different absolute numbers:
- BASE speculative decoding: 2.99×; SMALL: 2.76×.
- BASE + MaG: 3.27× (9.4% over BASE alone); SMALL + MaG: 2.82× (2.2% over SMALL alone).
- BASE + SMALL + MaG: 3.43× (14.7% over BASE alone).

The consistency between MS and PW metrics is important: it shows the gains are not an artifact of the parameter-count heuristic overestimating the cost ratios. The PW metric uses independently measured latency ratios from Leviathan et al. (2023), which would differ from the simple parameter-count ratio if, for example, FLAN-T5 models have different hardware utilization efficiency than the models Leviathan et al. measured. The fact that both metrics show similar relative improvements strengthens confidence that the gains are real and not an artifact of the cost model.

**MMLU results.** On MMLU, the pattern is similar but with notably larger relative gains:
- MS metric: BASE speculative decoding achieves 3.97×; SMALL achieves 4.12×. Here, SMALL is the stronger single drafter (unlike GSM8K where BASE was stronger), which the paper does not explain but likely reflects differences in how the two models' output distributions align with the target model's on factual vs. reasoning tasks.
- BASE + MaG: 4.56×, a **14.9% improvement** over the best single drafter (4.12×) and a **47.4% improvement** over BASE speculative decoding alone—a much larger jump than the 9.5% on GSM8K.
- SMALL + MaG: 4.39×, a **6.6% improvement** over SMALL alone.
- BASE + SMALL + MaG: **4.88×**, an **18.5% improvement** over the best single drafter and a **23.0% improvement** over BASE speculative decoding alone.
- PW metric: BASE: 3.42×; SMALL: 3.51×; BASE + MaG: 4.21×; SMALL + MaG: 3.99×; BASE + SMALL + MaG: 4.32×.

The paper quotes a maximum additional speedup of **44% on GSM8K and 81% on MMLU** over speculative decoding. Computing these figures: for GSM8K, PW metric, CS Drafting (BASE + SMALL + MaG) achieves 3.43× vs. 2.76× (SMALL speculative decoding), giving (3.43 - 2.76) / 2.76 × 100 ≈ 24.3%. Using the MS metric: (3.88 - 3.06) / 3.06 × 100 ≈ 26.8%. Neither yields 44% straightforwardly, suggesting the 44% figure may be computed differently (e.g., as the maximum gain over the *slower* baseline rather than the *best* baseline, or as the percentage reduction in latency rather than percentage increase in speedup factor, or using a specific model-pair comparison not fully detailed in the table). The 81% figure for MMLU appears to compare the best CS Drafting MS result (4.88×) against the weaker single-drafter result (BASE speculative decoding at 3.97×), giving (4.88 - 3.97) / 3.97 × 100 ≈ 22.9%—again not directly matching 81%. The discrepancy suggests either these headline numbers aggregate over additional experiments not fully tabulated, or they represent a different computation (e.g., latency reduction rather than speedup improvement). This is a notable lack of clarity in the paper's headline claims.

**Key pattern: larger draft models benefit more from cascading.** An intriguing result visible in Table 2: while FLAN-T5-SMALL outperforms FLAN-T5-BASE as a standalone drafter on MMLU (4.12× vs. 3.97× MS), in CS Drafting, BASE + MaG (4.56×) solidly outperforms SMALL + MaG (4.39×). The paper notes this explicitly: "Despite FLAN-T5-SMALL mostly outperforming FLAN-T5-BASE as a draft model for speculative decoding, in CS Drafting with the aid of MaG, FLAN-T5-BASE consistently outperforms FLAN-T5-SMALL." The interpretation offered is that "with the limitation of a single draft model, the ideal size of the draft model might increase with the assistance of the MaG model." In other words, the vertical cascade changes the cost-quality calculus: when the drafting cost is reduced by MaG's contribution, the higher acceptance rate of a larger neural model becomes worth its higher per-token cost. This is a concrete demonstration of the paper's claim that cascading "opens the door to using better draft models" that were previously suboptimal due to their latency.

**Hyperparameter details (Table 5).** The full hyperparameter table reveals the $K_{nn}$ matrix values and lenience settings used. For BASE + SMALL + MaG on GSM8K (MS metric): $k_{11} = 8, k_{12} = 13, k_{22} = 1, l = 3$. This means BASE reviews up to 8 tokens when presenting to the target model, with SMALL + MaG contributing up to 13 tokens total in the sub-cascade below BASE, and SMALL reviews MaG with a length-1 window ($k_{22} = 1$). Lenience $l = 3$ is applied at intermediate reviews (SMALL reviewing MaG, BASE reviewing SMALL) but not at the target model review. The $k$ values are larger for MMLU than GSM8K (e.g., standard speculative decoding: $k=13$ or $k=19$ for MMLU vs. $k=10$ or $k=11$ for GSM8K, across BASE and SMALL), suggesting that MMLU's factual-knowledge generations have higher per-token acceptance rates, making longer draft sequences worthwhile.

#### Decoder-Only Results on Vicuna-7B (Table 3)

Table 3 presents walltime results (tokens/second) on a single NVIDIA A40 GPU for the Vicuna-7B decoder-only setup. The headline numbers:
- Autoregressive generation: 33.34 tokens/s on GSM8K, 33.11 tokens/s on MMLU.
- Standard speculative decoding: 44.31 tokens/s (GSM8K) and 43.65 tokens/s (MMLU), representing ~1.33× speedup over autoregressive.
- CS Drafting (without tree attention): **56.72 tokens/s (GSM8K) and 55.60 tokens/s (MMLU)** , representing ~1.70× and ~1.68× over autoregressive, and a **28.0% and 27.4% walltime improvement** over standard speculative decoding respectively.
- Medusa (tree attention): 61.87 tokens/s (GSM8K) and 56.19 tokens/s (MMLU).
- CS Drafting + Tree Attention: **63.81 tokens/s (GSM8K) and 63.37 tokens/s (MMLU)** , representing ~1.91× and ~1.91× over autoregressive, and a **3.1% and 12.8% walltime improvement** over Medusa alone respectively.

Several observations from these decoder-only results:

**CS Drafting outperforms standard speculative decoding by a substantial margin in raw walltime.** The 28% and 27% improvements are in the same ballpark as the SWI-based improvements on encoder-decoder models, suggesting the cascade mechanism transfers across architectures. However, the absolute speedup factors are lower for decoder-only than for encoder-decoder (1.7× vs. 3.9×). This is expected given the different model architectures and the different draft model used (68M vs. the FLAN-T5 family), and underscores that speedup factors are highly model-family-dependent.

**CS Drafting and tree attention are additive.** The combination (63.81 tokens/s on GSM8K) outperforms both CS Drafting alone (56.72) and Medusa alone (61.87). The improvement over Medusa is modest on GSM8K (+3.1%) but more substantial on MMLU (+12.8%). This directly supports the paper's core positioning claim: CS Drafting's drafting-cost optimization is orthogonal to acceptance-rate improvements, and the two can be combined. The fact that the additive benefit is not simply the sum of individual improvements (CS Drafting gives +12.4 tokens/s, Medusa gives +17.6 tokens/s, but combined gives +19.2 tokens/s incremental over CS Drafting alone, or +2.0 incremental over Medusa alone on GSM8K) suggests some overlap in which tokens are accelerated—both methods accelerate different "parts" of the generation, but there is diminishing return when both are applied, as expected.

**The default hyperparameter is not tuned per-dataset.** The decoder-only results use a fixed $K_{nn} = [[2, 10], [0, 10]]$ across both datasets, with tree attention configured as "only the lead node with the highest probability of having children" and the number of children per leading node being 8. This means the decoder-only results represent a **conservative estimate** of what CS Drafting could achieve with per-dataset tuning, aligning with the stated goal of showing that "end users who do not require maximum performance can use a simple setup to achieve near-optimal performance." The paper does not report what the tuned performance would be, so the ceiling is unknown.

**Absolute walltime speedups are smaller than SWI speedups.** The autoregressive baseline produces ~33 tokens/s on Vicuna-7B, and the best configuration (CS Drafting + Tree Attention) reaches ~64 tokens/s—less than 2× speedup. Compare this to the FLAN-T5 results where SWI speedups reach 3.88× to 4.88×. This gap reflects several factors: (1) the draft-to-target model size ratio differs (68M vs. 7B for Vicuna, compared to 80M–250M vs. 11B for FLAN-T5), (2) SWI assumes idealized constant per-forward-pass times that may not match real GPU behavior (e.g., the target model's forward pass may be relatively cheaper in practice due to better GPU utilization at larger batch sizes), and (3) the decoder-only architecture has fundamentally different latency characteristics than encoder-decoder, particularly for the encoder portion of the target model's forward pass which processes the entire prompt in parallel.

### Ablation Studies and Robustness Checks

**Cascade depth (Table 2).** The progression from speculative decoding (no cascade) → one neural model + MaG (vertical cascade, depth 2) → two neural models + MaG (vertical cascade, depth 3) shows monotonic improvement in nearly all cases. On GSM8K (MS): 3.38× → 3.70× → 3.88×. On MMLU (MS): 4.12× → 4.56× → 4.88×. The only exception is SMALL + MaG on GSM8K (3.19×), which underperforms BASE speculative decoding (3.38×)—but this is a difference in *which* neural model is used, not the cascade depth per se, and the paper's point is that with MaG assistance, BASE (the larger drafter) becomes viable and outperforms any SMALL configuration. The takeaway is that deeper cascades improve efficiency, but **the quality of the neural drafters in the cascade determines the ceiling**—adding more layers of weak drafters without a strong drafter near the top is not beneficial.

**Hyperparameter $K_{00}$ sensitivity (Table 4).** The paper conducts an ablation on $K_{00}$, described as "the hyperparameter with the greatest effect on our experiments," using Vicuna-7B on GSM8K. Varying $K_{00}$ from 1 to 3 yields walltimes of 56.16, 55.51, and 53.73 tokens/s respectively. The optimal value ($K_{00} = 1$) gives only a 1.2% improvement over $K_{00} = 2$ and a 4.5% improvement over $K_{00} = 3$. The paper interprets this as evidence that "the performance of CS Drafting only decreases slightly when this hyperparameter is sub-optimal," supporting the claim that the method is robust to hyperparameter choice and usable without extensive tuning. However, the paper does not define what $K_{00}$ represents in the $K_{nn}$ matrix, which is a clarity issue. Presumably $K_{00}$ is the top-left entry of the $K_{nn}$ matrix, controlling the number of tokens the first neural draft model generates directly (the early, high-value segment). The observed pattern—lower $K_{00}$ is better—is consistent with the Horizontal Cascade's logic: the first neural drafter should focus on a small number of high-value early tokens rather than spreading its cost across many positions.

**Horizontal cascade ablation.** The paper reports that "removing the horizontal cascade" on GSM8K with Vicuna-7B and $K_{00} = 1$ results in a performance drop from 56.16 to 53.55 tokens/s—a **4.6% reduction**. This ablation is described only briefly without a dedicated table, and the exact mechanism of "removing" the horizontal cascade is not specified (does it revert to uniform allocation across positions? Does it remove the for-loop in Algorithm 1 and use only the vertical cascade? Does the vertical cascade remain?). Despite the limited detail, this ablation provides evidence that the horizontal cascade contributes non-trivially to the overall improvement—the 4.6% drop is not negligible relative to the 28% total improvement over standard speculative decoding.

**Effectiveness of MaG (implicit ablation, Table 2).** The comparison between speculative decoding with a single neural model and CS Drafting with that same neural model + MaG directly measures MaG's contribution. On MMLU (MS), BASE + MaG (4.56×) vs. BASE alone (3.97×) gives a 14.9% improvement. On GSM8K (MS), BASE + MaG (3.70×) vs. BASE alone (3.38×) gives a 9.5% improvement. These are the pure vertical cascade effects, isolating MaG's benefit. As the paper notes, "the MaG algorithm only involves a bigram model with parameters equal to the tokenizer size, making its memory cost negligible," so this speedup comes with essentially zero additional deployment cost—no extra GPU memory for model weights, no additional loading time, no fine-tuning. This is the paper's strongest practical selling point: the MaG cascade can be added to any existing speculative decoding setup with minimal engineering effort.

**SWI metric sensitivity (Table 2).** The SWI (MS) and SWI (PW) metrics produce different absolute speedup values (e.g., 3.38× vs. 2.99× for BASE on GSM8K) but consistent relative rankings. PW speedups are consistently lower than MS speedups, suggesting that the parameter-count heuristic overestimates the cost ratio between draft and target models (i.e., the draft models are relatively *more* expensive per parameter than the target model in actual measured times). This is plausible: very small models may not fully saturate GPU compute, resulting in proportionally higher latency per parameter. The key point is that **the relative improvement from CS Drafting over speculative decoding is consistent across both cost assumptions**, indicating the cascading benefit is not an artifact of a particular cost model.

**Model size effect under cascading (Table 2 cross-comparison).** An implicit ablation: BASE vs. SMALL as the neural drafter in CS Drafting. On GSM8K (MS), BASE + MaG (3.70×) outperforms SMALL + MaG (3.19×). On MMLU (MS), BASE + MaG (4.56×) outperforms SMALL + MaG (4.39×). This is the reverse of the standalone speculative decoding ranking on MMLU, where SMALL (4.12×) outperformed BASE (3.97×). The paper interprets this as the vertical cascade "increasing the ideal size of the draft model." A more precise characterization: **the vertical cascade shifts the optimal point on the cost-quality Pareto frontier toward higher quality (and higher cost) because MaG absorbs some of the drafting cost**. Before cascading, the cost of BASE's 250M parameters was too high relative to its acceptance-rate advantage over SMALL. With MaG providing cheap foundational tokens, BASE's per-token cost remains the same, but it now reviews rather than generates—a single parallel forward pass rather than $k$ sequential ones—which changes the cost structure. The paper does not provide a formal analysis of this shift, but the empirical result is clear and practically significant: practitioners who previously selected SMALL as their optimal single drafter may find that BASE + MaG is superior, meaning the hardware provisioning and model selection decisions change under CS Drafting.

**Lenience settings (Table 5).** For BASE + SMALL + MaG configurations, lenience $l = 3$ (GSM8K) or $l = 5$ (MMLU) is applied. The paper does not provide a lenience ablation (e.g., $l=1$ vs. $l=3$ vs. $l=5$ for the same configuration), so the sensitivity to this hyperparameter and the speedup attributable specifically to lenience (as opposed to the cascade structure itself) cannot be isolated from the reported results. This is a missing ablation that would clarify how much of the vertical cascade's benefit comes from the recursive structure versus from the aggressive intermediate rejection that lenience enables.

**Tree attention combinations (Table 3).** The comparison of CS Drafting alone, Medusa alone, and CS Drafting + Tree Attention serves as an ablation over composability with orthogonal improvements. The key result is that CS Drafting + Tree Attention (63.81 tokens/s on GSM8K) exceeds both CS Drafting alone (56.72) and Medusa alone (61.87). However, the gap over Medusa alone is small on GSM8K (1.94 tokens/s, 3.1%), raising the question of whether the improvement is statistically significant given the unstated measurement variance. On MMLU, the gap is larger (7.18 tokens/s, 12.8%), suggesting the composability benefit is task-dependent. The paper does not explore why MMLU benefits more—one hypothesis is that MMLU's factual-knowledge generations have shallower acceptance-rate decay curves, leaving more room for tree attention's multiple-candidate strategy to find matches, which then benefit from CS Drafting's faster drafting.

**No fine-tuning required (design choice, not an ablation).** The paper explicitly states that "to align our experiment with current common usage, we do not perform fine-tuning for CS Drafting, and the generation is conducted in a zero-shot manner." This means all results are obtained with off-the-shelf models and a purely algorithmic drafting mechanism (MaG). This is a strength for adoption (no training cost, no data requirements) but also means that the results represent a **lower bound**—fine-tuning draft models for the cascade structure, or training MaG on domain-specific data rather than Wikipedia, could further improve performance. The paper does not explore these possibilities.

### Critical Assessment

#### Claim: CS Drafting "achieves greater speedup compared to the baselines" while "preserving the same output distribution as the target model."

**What the experiments demonstrate.** Tables 2 and 3 unequivocally show that CS Drafting configurations produce higher speedup factors (SWI) and higher tokens-per-second (walltime) than standard speculative decoding with the same neural draft models, across both encoder-decoder and decoder-only architectures, on both GSM8K and MMLU. The maximum reported gains—3.88× vs. 3.38× (GSM8K, MS) and 4.88× vs. 4.12× (MMLU, MS)—are substantial and consistent. The walltime results on Vicuna-7B (56.72 vs. 44.31 tokens/s on GSM8K) confirm that these gains materialize in actual elapsed time, not just in idealized cost models.

**Where the evidence is thinner.** Three issues merit attention:

1. **The headline "44%" and "81%" additional speedup figures cannot be directly verified from the tables.** As noted above, computing (max CS Drafting - best speculative decoding) / best speculative decoding from Table 2 yields ~15-27% (depending on metric and dataset), not 44% or 81%. These headline numbers may use a different computation (e.g., percentage reduction in latency: $1 - 1/3.88 \approx 0.74$ for CS Drafting vs. $1 - 1/3.38 \approx 0.70$ for speculative decoding, giving a ~5.7% latency reduction—also not 44%). Alternatively, they may reference experiments not fully tabulated, or use worst-case rather than best-case speculative decoding baselines. This lack of clarity undermines the paper's most prominently quoted result.

2. **Output distribution preservation is assumed, not measured.** The paper states that lenience is only applied at intermediate reviews and that the target model uses $l=1$, which theoretically guarantees exact distribution matching (the standard speculative decoding proof applies to the final verification step). However, no empirical verification of output distribution equivalence is reported—no comparison of generated token distributions, no measurement of output quality metrics (e.g., task accuracy on GSM8K/MMLU), no statistical tests for distributional divergence. The claim relies entirely on the theoretical guarantee inherited from speculative decoding. In practice, this guarantee could break if there is any implementation error in the lenience scoping (ensuring $l$ is exactly 1 for the target model review) or if the MaG model's deterministic outputs create edge cases not covered by the standard proof. While the theoretical guarantee is strong, an empirical sanity check (e.g., reporting that task accuracy is identical between autoregressive and CS Drafting) would have been straightforward and reassuring.

3. **Greedy decoding only.** All experiments use temperature 0, which the paper justifies by prior findings that speculative decoding with temperature 1 shows "no significant difference" from greedy. However, this means the results do not directly validate performance for the stochastic sampling case, despite the theoretical analysis (Section 4) covering both greedy and sampling. For applications that use non-zero temperature (chatbots, creative generation), the acceptance rates and thus the speedup factors may differ. The paper does not quantify this gap.

#### Claim: The vertical cascade "eliminates autoregressive generation from neural models."

**What the experiments demonstrate.** The core mechanism—each neural model operates only in reviewer mode (parallel forward pass), never autoregressively—is inherent in the algorithm design (Algorithm 1). The fact that CS Drafting with BASE + MaG (3.70×) outperforms BASE speculative decoding (3.38×) on GSM8K (MS) is evidence that the mechanism works: if BASE were still generating autoregressively somewhere in the cascade, the speedup over standard speculative decoding would be difficult to explain, since the only change is adding MaG as a sub-drafter. The ablation showing that removing the horizontal cascade reduces performance from 56.16 to 53.55 tokens/s also indirectly supports the vertical cascade's contribution (since what remains after removing the horizontal cascade is presumably the vertical cascade alone, though the paper's description is vague).

**What's not demonstrated.** The paper does not provide a direct measurement of whether autoregressive generation has been eliminated—e.g., profiling the number of sequential forward passes per token, or measuring the proportion of time spent in autoregressive vs. parallel operations. Without such profiling, a skeptical reader could wonder whether some unoptimized part of the implementation inadvertently introduces sequential dependencies. The algorithm description is clear that no neural model generates autoregressively, but the empirical validation relies entirely on end-to-end speedup numbers rather than internal timing breakdowns. This is a reasonable choice for a systems paper focused on end-to-end performance, but it means the mechanism's claimed efficiency gain is validated only indirectly.

#### Claim: The horizontal cascade "optimizes time allocation in drafting" based on position-dependent token value.

**What the experiments demonstrate.** The ablation removing the horizontal cascade (performance drop from 56.16 to 53.55 tokens/s) is the most direct evidence. The simulated EWIF results in Table 1, showing that BASE (5 tokens) + SMALL (3 tokens) achieves EWIF 3.03 vs. BASE alone (3.96? actually, the table shows BASE alone at 2.96 and SMALL alone at 2.65, so 3.03 is indeed better than either alone), provide analytical validation of the position-dependent allocation principle under i.i.d. Bernoulli assumptions. The theoretical analysis in Theorem 4.5 and Corollary 4.6 provides formal justification.

**Where the evidence is weaker.** Several gaps exist:

1. **The ablation is only 4.6%.** The horizontal cascade's contribution, while positive, is small—4.6% out of the total 28% walltime improvement over standard speculative decoding. This means the vertical cascade (recursive speculation + MaG) is responsible for the bulk of the gains, and the horizontal cascade is a more modest refinement. The paper's narrative treats the two cascades as roughly co-equal innovations, but the empirical evidence suggests the vertical cascade is the dominant contributor.

2. **No position-specific acceptance rate data for the cascaded system.** Figure 2 shows acceptance rates for single-drafter speculative decoding, but there is no corresponding figure for CS Drafting showing per-position acceptance rates when different models handle different positions. Such data would directly validate the assumption that the early/late token value disparity persists in the cascaded setting and that the allocation matches it. Without this, the horizontal cascade's benefit is validated only through the net speedup and the theoretical model, not through direct measurement of the mechanism at work.

3. **The $K_{nn}$ hyperparameter matrix is opaque.** Table 5 reports the chosen hyperparameters, but the paper does not explain how they were selected (grid search? manual tuning? Bayesian optimization?), how sensitive performance is to suboptimal choices, or what principles guide their selection for new model families. The $K_{00}$ ablation (Table 4) addresses sensitivity for one entry but does not provide a general tuning methodology. For practitioners wanting to deploy CS Drafting with their own models, the hyperparameter selection process is under-specified.

#### Claim: CS Drafting achieves these gains while being a drop-in, no-training-required method.

**What the experiments demonstrate.** The paper clearly states that no fine-tuning is performed, and all models are used off-the-shelf. The MaG model uses Wikipedia bigram statistics—a generic resource requiring no task-specific data. This claim is well-supported by the experimental setup description.

**What's assumed but not tested.** The claim of "no additional deployment overhead" for the one-neural-model cascade (BASE + MaG) is reasonable given MaG's negligible memory footprint, but for the two-neural-model cascade (BASE + SMALL + MaG), there is a genuine deployment consideration: the system must hold three models in GPU memory simultaneously (target + two neural drafters + MaG's bigram table). The paper does not report GPU memory usage for the different configurations. For the FLAN-T5 experiments, FLAN-T5-XXL (11B) + BASE (~250M) + SMALL (~80M) is likely manageable on a single A40 (48GB), but for larger target models, loading multiple neural drafters could exceed memory budgets. The decoder-only experiment uses only one neural drafter (68M) alongside Vicuna-7B, which is conservative in this regard. The paper's claim of "no additional deployment overhead" should be qualified: no *training* overhead, but potentially non-trivial *memory* overhead as cascade depth increases.

#### Claim: CS Drafting composes with orthogonal speculative decoding improvements (tree attention).

**What the experiments demonstrate.** Table 3 shows CS Drafting + Tree Attention (63.81 tokens/s) > Medusa alone (61.87 tokens/s) and CS Drafting alone (56.72 tokens/s) on GSM8K, with similar patterns on MMLU. This directly supports the composability claim.

**What's missing.** The paper does not explore composition with other speculative decoding variants—knowledge-distilled draft models (Zhou et al., 2023), self-drafting (Zhang et al., 2023; Hooper et al., 2024), or other tree-attention configurations beyond the single-leaf-node variant tested. The composability claim is demonstrated for exactly one orthogonal method (Medusa-style tree attention) with one specific configuration, which is a proof of concept but not a comprehensive validation. The paper appropriately labels further exploration of compositions as future work.

#### Missing experiments that would have strengthened the paper.

1. **Task accuracy verification for distributional equivalence.** A simple table showing that autoregressive, speculative decoding, and CS Drafting all achieve identical accuracy on GSM8K and MMLU (within measurement noise) would directly validate the output preservation claim. This would require only running the standard evaluation metrics for these benchmarks, which the paper already has the infrastructure to do (since it generates from these models).

2. **Lenience ablation.** Comparing $l=1$ (no lenience anywhere) vs. $l=3$ vs. $l=5$ for a fixed cascade configuration would isolate lenience's contribution. Without this, we cannot tell whether the vertical cascade's benefit comes primarily from the recursive structure or from aggressive intermediate rejection—two mechanisms that are conceptually distinct but confounded in the reported results.

3. **MaG-only baseline.** Running speculative decoding with MaG alone as the drafter (no neural draft model at all) would establish a lower bound: how bad is MaG when used directly rather than embedded in a cascade? This would quantify the refinement benefit that the neural models provide over MaG's raw output, clarifying the value of the cascade structure beyond simply switching to a faster drafter.

4. **Memory usage profiling.** Reporting peak GPU memory for autoregressive, speculative decoding, and each CS Drafting configuration would address the practical deployment concern of multi-model memory overhead.

5. **Statistical characterization of walltime measurements.** Reporting mean, standard deviation, and number of runs for the walltime measurements in Table 3 would allow assessment of whether the 3.1% improvement of CS Drafting + Tree Attention over Medusa on GSM8K is statistically significant or within measurement noise.

6. **Scaling with target model size.** All experiments use a single target model size (FLAN-T5-XXL at 11B, Vicuna-7B at 7B). How do the relative gains change as the target model scales to 70B, 175B, or beyond? The theoretical framework (Theorem 4.3) predicts that as the target model's cost dominates (i.e., $c_{d1}$ and $c_{d2}$ become even smaller relative to the target), the EWIF should increase—but this prediction is not tested empirically.

#### Overall assessment.

The experiments substantiate the paper's core claim—CS Drafting achieves meaningful speedup over standard speculative decoding by optimizing the drafting process—with consistent evidence across two architectures, two datasets, and multiple evaluation metrics. The mechanism-level validation is somewhat indirect (end-to-end speedup rather than internal profiling), and several of the paper's strongest rhetorical claims ("44%," "81%") are difficult to reproduce from the reported tables. The horizontal cascade's contribution, while real, is modest compared to the vertical cascade's, and the paper's framing somewhat overstates the parity between these two innovations. The composability demonstration with tree attention is a valuable proof of concept but is limited to a single orthogonal method. The absence of output quality verification, memory profiling, and lenience ablation represent the most significant gaps in experimental coverage. Nevertheless, the core empirical pattern—CS Drafting > speculative decoding across all tested configurations, with especially strong gains from the MaG cascade—is robustly demonstrated and practically significant for LLM serving systems.

## 6. Limitations and Trade-offs

### The "44%" and "81%" Headline Speedup Claims Cannot Be Verified from Reported Results

**The assumption or constraint.** The paper prominently claims that CS Drafting achieves "an additional speedup of up to 81% over speculative decoding" on MMLU and "up to 44%" on GSM8K (Abstract, Section 6.2). These headline figures are meant to summarize the net benefit of the method. However, they cannot be reproduced by straightforward computation from the main results tables. As noted in Section 5's critical assessment, computing improvement over the best single-drafter baseline yields substantially lower percentages: on GSM8K (MS metric), CS Drafting best (3.88×) vs. best speculative decoding (3.38×) gives a 14.8% improvement; on MMLU (MS), the gain is roughly 18.5% over the best single drafter and 23% over BASE alone.

**The consequence.** This makes it impossible for readers or practitioners to determine what exactly the headline numbers represent—are they computed relative to the *weakest* speculative decoding baseline rather than the best? Do they use percentage reduction in latency rather than percentage improvement in speedup factor? Do they reference experiments not fully tabulated in the paper? Without clarity on methodology, the headline claims are not actionable and risk overstating the practical benefit. A practitioner expecting an 81% walltime reduction over their current speculative decoding setup based on these numbers would likely be disappointed by the realized gains shown in the actual tables.

**What evidence exists in the paper.** Table 2 contains all the MS and PW speedup factors from which any "additional speedup" percentage must be computed. Table 5 provides the hyperparameter details. Nowhere does the paper define the computation used to arrive at 44% or 81%. This is a gap in reporting transparency, not a flaw in the underlying measurements.

**Mitigation status.** The paper does not address this discrepancy or clarify the computation. The absolute speedup factors in Tables 2 and 3 are unambiguous and well-supported, so practitioners should rely on those raw numbers rather than the headline percentages when assessing expected gains. The SWI and walltime metrics themselves are clearly defined and reproducible.

---

### Difficulty Estimation Is Neither Scalable Nor Accounted For in Cost Models

**The assumption or constraint.** The entire compute-optimal framework depends on assigning each prompt to a difficulty bin before applying a strategy. The method used to estimate difficulty—generating 2048 samples per question and averaging either pass@1 (oracle) or PRM final-answer scores (predicted)—is extraordinarily expensive. The authors acknowledge this directly (Section 3.2): "Our experiments do not account for this cost largely for simplicity." At 2048 samples per question, the difficulty estimation step alone consumes more compute than the largest test-time budgets studied (256–512 generations), meaning the reported efficiency gains are computed *after* difficulty is known, without amortizing the cost of learning it.

**The consequence.** In a realistic deployment, the total cost would be `difficulty_estimation_cost + strategy_execution_cost`, and the former would dominate the latter for any moderate-compute budget. The claimed 4× efficiency gains over best-of-N are therefore an **upper bound**, not a realized deployment gain. A system that naively spends 2048 generations to estimate difficulty and then 16 generations on the optimal strategy has spent 2064 generations total—vastly more than a baseline best-of-N with 64 generations, making the "4× more efficient" comparison meaningless without cost amortization. For applications where each prompt is seen only once (e.g., interactive user queries), this is intractable. For batch processing where the same prompts are solved repeatedly, the cost could be amortized, but the paper does not characterize this regime.

**What evidence exists in the paper.** Section 3.2 describes the difficulty estimation method. Figures 4 and 8 show the compute-optimal curves assuming difficulty is already known, without including estimation cost on the x-axis. Appendix C (Figures 11–12) shows oracle vs. predicted difficulty bins. None of the FLOPs-matched comparisons in Figure 9 account for difficulty estimation FLOPs in the test-time compute budget.

**Mitigation status.** The paper acknowledges this explicitly as an important limitation and frames cheap difficulty estimation as "a key avenue for future work." Specifically, Section 8 suggests "pretraining or finetuning models to directly predict difficulty of a question." However, no such model is developed or evaluated, and no analysis of how much the difficulty estimation cost would need to be reduced to make the framework net-beneficial is provided. Until a cheap, accurate difficulty estimator is demonstrated, the compute-optimal framework remains a proof of concept rather than a deployment-ready system.

---

### All Experiments Are on a Single Benchmark and a Single Model Family

**The assumption or constraint.** The paper's entire empirical validation is conducted on the MATH benchmark (competition-level math problems) using PaLM 2-S* as the base model. The authors "believe this model is representative of the capabilities of many contemporary LLMs" (Section 4), but this claim is not tested. MATH is a specific domain—symbolic mathematical reasoning with exact-match ground-truth answers—and PaLM 2-S* is a specific model family. The paper does not evaluate on code generation, logical reasoning, scientific QA, summarization, or any non-math domain.

**The consequence.** Several of the paper's key findings may not generalize. The difficulty-dependent behavior of search vs. revisions (beam search hurts easy problems, revisions help easy problems) might be specific to mathematical reasoning, where mistakes often involve arithmetic errors or missing steps that sequential revision can fix. For factual QA, the relationship between difficulty and optimal strategy could be entirely different. The PRM's over-optimization characteristics depend on PaLM 2-S*'s specific output distribution and error patterns—other models might have different verifier vulnerabilities. The FLOPs-matched finding that test-time compute can substitute for a 14× larger model is contingent on the specific pretraining recipe and model architecture, which may not hold for model families with different scaling properties. The revision model's training procedure (edit-distance-based pairing, MC rollout PRM training) might not transfer to code or natural language tasks where edit distance is less meaningful.

**What evidence exists in the paper.** All figures (Figures 3–9) and tables in Sections 5–7 use MATH test-set data with PaLM 2-S* models. Section 4 describes the dataset and model choices but provides no cross-domain validation. The PRM training uses the MATH training split (12,000 questions). The revision model is fine-tuned on MATH data.

**Mitigation status.** The paper does not address this limitation—it makes no claims about generality and does not acknowledge the single-domain, single-model scope as a limitation to be addressed in future work. The "representative" claim is presented without caveat. For practitioners, this means the findings should be treated as **validated for mathematical reasoning with PaLM 2-S*, and plausible but unverified for other domains and models.** Replication on at minimum one additional domain (e.g., code generation) and one additional model family (e.g., LLaMA, GPT) would substantially strengthen generalizability claims.

---

### The 14× Larger Model Baseline Is Not Compute-Optimally Trained

**The assumption or constraint.** The FLOPs-matched comparison in Section 7 compares PaLM 2-S* with compute-optimal test-time scaling against "a model with approximately 14× more parameters" using greedy decoding. The paper explicitly acknowledges (Section 7) that it scales model parameters while holding training data fixed, following the LLaMA paradigm (Touvron et al., 2023), rather than compute-optimally scaling both parameters and data as prescribed by the Chinchilla laws (Hoffmann et al., 2022): "We choose this setting as it is representative of a canonical approach to scaling pretraining compute and leave the analysis of compute-optimal scaling of pretraining compute where the data and parameters are both scaled equally to future work."

**The consequence.** A Chinchilla-optimal model trained with 14× more total FLOPs would allocate the additional compute to both more parameters AND more training data, likely outperforming the parameter-only-scaled model on downstream tasks. This makes the pretraining baseline **weaker than it could be**, and the reported advantages of test-time compute over pretraining—e.g., +27.8% relative improvement on easy-to-medium questions at R << 1 (Figure 1, top-right bar chart)—may **shrink or reverse** against a compute-optimally trained larger model. The FLOPs-matched analysis is therefore a comparison against a specific, potentially suboptimal pretraining strategy, not against the best-possible use of pretraining compute. This matters for practitioners deciding how to split their total compute budget: if the pretraining alternative is stronger than the one tested, the regime where test-time compute is preferable narrows.

Additionally, the 14× larger model uses only greedy decoding with no test-time augmentation. Giving the larger model even a modest test-time compute budget (e.g., best-of-8 with majority voting) would create a stronger baseline. The paper's finding that test-time compute can substitute for pretraining is therefore most applicable when comparing against a deployment scenario where the larger model is also used with greedy decoding—a reasonable but not maximally strong baseline.

**What evidence exists in the paper.** Section 7 describes the FLOP accounting and the parameter-only scaling approach. Figure 9 and the bar charts in Figure 1 present the comparison results. The acknowledgment of the non-Chinchilla-optimal pretraining is in Section 7 text.

**Mitigation status.** The paper is transparent about this limitation and flags compute-optimal pretraining comparison as explicit future work. However, until such a comparison is performed, the central claim that "test-time compute can substitute for pretraining on easy-to-medium problems" should be understood as **validated against a parameter-scaled baseline, not against the best possible use of equivalent pretraining FLOPs.** The quantitative tradeoff ratios (e.g., "4× less compute" or "14× larger model equivalent") may not hold in a fully optimized pretraining regime.

---

### Verifier Over-Optimization Is the Hard Performance Ceiling, Not a Solved Problem

**The assumption or constraint.** The paper documents that verifier over-optimization limits test-time search scaling: beam search degrades easy-problem performance at high budgets (Figure 3, right), lookahead search—the strongest optimizer—paradoxically performs worst overall (Figure 3, left), and qualitative examples show degenerate outputs scoring highly under the PRM (Appendix M). The compute-optimal policy mitigates this by routing easy problems away from aggressive search, but it does not solve the underlying problem: on medium-difficulty problems where beam search is deployed, over-optimization still causes performance to flatten or decline at high budgets (Figure 3, right, bins 3–4 flatten around 64–256 generations). The revision model has a related failure mode: approximately 38% of correct answers get revised back to incorrect ones during sequential revision chains (Section 6.1).

**The consequence.** This means test-time compute scaling has a **hard ceiling** determined by verifier quality, not by the amount of compute allocated. No matter how much additional budget you give the system, accuracy on a given difficulty tier cannot exceed what the verifier can reliably distinguish. This ceiling is not merely theoretical—the paper shows it empirically for bin-3 problems with beam search plateauing around 34% accuracy and bins 4–5 never exceeding ~17% and ~3% respectively, regardless of budget. For practitioners, this means that improving the PRM (better training data, adversarial robustness, ensemble methods) is a prerequisite for further scaling, and that the compute-optimal policy's gains are bounded by the verifier's reliability frontier, not by the allocation strategy's cleverness. The revision model's correct-to-incorrect reversion problem means that even on easy problems, unlimited sequential revision will eventually degrade performance, not improve it indefinitely—the gains from revisions are bounded by the model's ability to recognize when no correction is needed.

**What evidence exists in the paper.** Figure 3 (right) shows the beam search degradation pattern across bins. Figure 3 (left) shows lookahead search underperforming simpler methods. Appendix M provides qualitative failure examples. Section 6.1 reports the 38% reversion rate for the revision model. Figure 6 (left) shows revision pass@1 saturating around 24–25% after 15–20 steps, indicating diminishing returns. Figure 8 shows the compute-optimal revision curve continuing to improve while parallel baselines plateau, but it does not show what happens at even higher budgets to determine if the compute-optimal curve also plateaus.

**Mitigation status.** The paper identifies verifier over-optimization as a bottleneck and notes in Section 8 that it "highlights the need for developing stronger verifiers" but does not propose concrete mitigations beyond suggesting ensemble verification as future work. The revision model's reversion problem is partially patched by majority voting or verifier-based selection across the revision chain (rather than always taking the last revision), but this is a workaround, not a solution—it means some correct answers are still lost in revisions where the chain never recovers, and the selection mechanism adds its own overhead. The paper does not explore training the revision model to recognize when no revision is needed. For practitioners, this limitation means that deploying CS Drafting's compute-optimal policy requires investing in verifier quality improvement to raise the ceiling, and that the revision model should be used with chain-wide selection rather than trusting the final output.

---

### No Mechanism for Dynamic, Mid-Computation Strategy Adjustment

**The assumption or constraint.** The compute-optimal framework assigns a prompt to a difficulty bin before computation begins, then executes a fixed strategy (search algorithm, beam width, revision depth, sequential-to-parallel ratio) for that difficulty tier. The strategy is static: once allocated, it does not change based on intermediate results. For example, if the system starts with beam search on a medium-difficulty problem and the first few beams reveal the problem is actually easy (the model quickly finds a high-scoring solution), the system cannot switch to a more efficient strategy mid-execution. Similarly, if a problem estimated as hard starts showing promise after a few parallel samples (suggesting it might actually be medium-difficulty), the system cannot allocate additional budget to search. The difficulty bins are pre-computed and fixed, with no online updating.

**The consequence.** This static allocation wastes compute in two directions. First, **over-allocation**: a problem estimated as medium-difficulty might be solved by the first few beams, but the system continues to exhaust the full budget because the strategy is fixed. Second, **under-allocation**: a problem estimated as hard might show early signs of solvability but is abandoned prematurely because the hard-bin strategy allocates minimal effort (since the paper shows bin-5 problems benefit negligibly from any strategy). In the revision setting, a similar rigidity exists: if the first revision already produces a correct answer, the system might still continue revising (and risk the 38% reversion) rather than stopping early. This inefficiency is especially costly given that difficulty estimation itself is expensive—a dynamic system that estimates difficulty *during* solution generation could amortize this cost into the problem-solving process.

The paper flags this implicitly in Section 3.2 when describing the difficulty estimation cost as an "exploration-exploitation tradeoff," but the current framework only explores during a separate pre-computation phase (the 2048-sample difficulty estimation), never jointly with exploitation.

**What evidence exists in the paper.** The entire experimental methodology (Section 5) and the compute-optimal policy description (Section 3.2) assume static, pre-determined strategy selection per bin. Algorithm 1 in the original paper's Appendix is a fixed lookup, not an adaptive procedure. The cross-validation protocol selects one best strategy per bin per budget, not a conditional policy that adapts mid-execution. No experiments test dynamic strategy switching, and no analysis measures how much efficiency is lost due to static allocation vs. an oracle that knows the optimal stopping point per problem.

**Mitigation status.** The paper does not address dynamic strategy adjustment as a limitation or future direction. The framing ("compute-optimal test-time scaling strategy") implies that the allocation is optimal, but this optimality is with respect to a *static, per-bin policy*, not with respect to what could be achieved with online, per-instance adaptation. For practitioners, this means the reported 4× efficiency gains over best-of-N are lower bounds on what could be achieved with more sophisticated adaptive policies, but also that the current system leaves efficiency on the table by treating difficulty as fixed and pre-estimated rather than continuously updated. Implementing dynamic adjustment would require solving a non-trivial sequential decision problem (when to switch strategies based on partial results), which the paper does not attempt.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

This paper fundamentally reframes where the optimization frontier lies for speculative decoding. Since Leviathan et al. (2023), the field has operated under the implicit assumption that **draft quality**—the acceptance rate α between draft and target model—is the primary lever for improving speedup. This assumption motivated a substantial research program: knowledge distillation to align draft and target distributions (Zhou et al., 2023), self-drafting from the target model's own parameters (Zhang et al., 2023; Hooper et al., 2024), and tree attention to propose multiple candidates per position (Miao et al., 2024; Cai et al., 2024). All of these attack the *numerator* of the speedup equation: more accepted tokens per target-model forward pass.

CS Drafting makes a **diagnostic shift**: it argues that the *denominator*—the drafting cost itself—has been the binding constraint all along, and that improving draft quality while leaving drafting cost untouched provides diminishing returns. The paper's reframing is most visible in how it reinterprets Leviathan et al.'s observation that very small draft models (two orders of magnitude smaller than the target) are usually optimal. The standard reading of that finding was: "small draft models are good enough, so we don't need to invest in better drafters." CS Drafting's reading is: "even when larger draft models produce higher-quality tokens, their **latency cost** outweighs that benefit, which means the drafting process is structurally too expensive, not that draft quality is unimportant."

This reformulation is significant because it **redirects research attention from draft-quality improvement to draft-cost reduction**. Prior to this work, there was no conceptual framework for asking "how can we make drafting itself faster?" as a first-class research question separate from "how can we make drafts more acceptable?" The paper's decomposition of the speedup equation into drafting cost (the denominator) and draft quality (the numerator) as independent optimization targets, combined with the demonstration that the two can be improved orthogonally and their benefits composed (Table 3, CS Drafting + Tree Attention), reorients the field's optimization landscape. Research that focuses purely on acceptance rate now looks incomplete; research that also addresses the drafting cost structure (through model cascades, non-neural drafters, position-dependent allocation) now looks essential.

The paper also **reconciles a tension** in the speculative decoding literature that was previously undertheorized. On one hand, the field knew that very small draft models were empirically optimal (Leviathan et al., 2023). On the other hand, the field also knew that larger draft models have higher acceptance rates and produce higher-quality drafts. The tension was: if larger models are better drafters in principle, why do they produce *worse* speedup in practice? CS Drafting provides a clean resolution: larger models are better drafters *conditional on being free*, but they are not free, and their per-token cost dominates the speedup equation in the standard speculative decoding architecture. The Vertical Cascade changes this calculus by making the larger model a **reviewer** rather than a **generator**—it processes tokens in a single parallel forward pass rather than $k$ sequential ones—which dramatically reduces its effective per-token cost. This explains why, in CS Drafting, FLAN-T5-BASE (the larger neural drafter) consistently outperforms FLAN-T5-SMALL (Table 2) even on MMLU where SMALL was the better standalone drafter: the cascade structure makes BASE's higher quality affordable.

Perhaps most provocatively, the paper challenges the implicit assumption that **statistical language models are irrelevant for modern LLM inference**. The n-gram models that preceded neural LMs have been treated as obsolete for generation tasks, and the speculative decoding literature had no reason to reconsider them—their standalone acceptance rates against large neural models are too low. CS Drafting demonstrates that **cost-quality ratio**, not absolute quality, determines a drafter's value, and that statistical models have an extreme advantage on this metric (their cost is effectively zero). The MaG algorithm, combining greedy input-output prefix matching with a Wikipedia bigram fallback, achieves a cost coefficient so close to zero that Corollary 4.4 guarantees it almost always improves net efficiency when embedded in a verification hierarchy. This is a **conceptual rehabilitation of non-neural drafting**—not as a replacement for neural drafters, but as a foundation that makes neural drafters more cost-effective by eliminating their autoregressive generation. The practical implication is that every speculative decoding deployment should now consider adding a statistical drafter beneath its neural drafter, since the implementation cost is negligible (vocabulary-sized lookup tables) and the speedup benefit is demonstrated (9–15% improvement over the best standalone drafter, from Table 2).

The paper's **composability demonstration** (Table 3, CS Drafting + Tree Attention outperforming Medusa alone on Vicuna-7B) establishes a methodological precedent: drafting-cost optimization and acceptance-rate optimization are **independent axes** that can be combined. This means the research community does not need to choose between "better draft models" and "faster drafting"—both can be pursued simultaneously and their benefits are additive, at least to first order. The modest 3.1% walltime improvement from adding CS Drafting to Medusa on GSM8K (63.81 vs. 61.87 tokens/s) suggests the additivity is not perfect—there is some overlap in which inefficiencies each method addresses—but the direction is clear. This composability finding makes speculative decoding research more cumulative: a new acceptance-rate improvement published next year can be evaluated both standalone and in combination with CS Drafting, and a new drafting-cost optimization can be tested against existing acceptance-rate methods. The field no longer needs to treat "which speculative decoding variant is best?" as a winner-take-all question.

The work also introduces a **unified analytical toolkit** that was previously missing. The EWIF framework with generating functions (Theorem 4.1, 4.3) and position-dependent cost models (Theorem 4.5, Corollary 4.6) provides a language for reasoning about any multi-model drafting system's efficiency tradeoffs. This is significant methodologically because it shifts design from "try configurations and measure" (which is combinatorially explosive with multiple draft models, cascade depths, and position allocations) to "model analytically, then verify empirically." The fact that the simulated EWIF in Table 1 correctly predicted that BASE (first 5 tokens) + SMALL (next 3 tokens) would outperform either model alone, before the full CS Drafting algorithm was deployed, demonstrates the framework's predictive value.

The **limitation** worth noting is that this reframing is specific to the drafting component of speculative decoding. It does not challenge the verification mechanism (the rejection sampling scheme) or the target model's role. CS Drafting inherits all the limitations of speculative decoding's verification: it requires the draft and target models to share a tokenizer, it assumes the ratio of per-token costs between models is roughly constant, and it relies on the target model's forward pass being substantially more expensive than any drafter's. For applications where the target model is not dramatically larger than available drafters, or where the cost ratios are unfavorable, the cascading approach provides diminishing returns—a fact visible in the decoder-only results where absolute speedups are ~1.7×, substantially lower than the 3.9–4.9× achieved with the larger FLAN-T5 size ratios.

### Follow-Up Research This Work Enables

**Characterizing the optimal cascade depth as a function of draft-model cost ratios.** The paper demonstrates that going from one neural drafter + MaG to two neural drafters + MaG improves speedup on both datasets (Table 2: 3.70× → 3.88× on GSM8K, 4.56× → 4.88× on MMLU, both MS metric), but provides no principled way to determine when adding another intermediate drafter ceases to be beneficial. The theoretical framework in Theorem 4.3 handles the two-drafter case, but extending it to $n$ drafters is not provided. A natural follow-up would derive the EWIF for an $n$-layer vertical cascade as a function of the cost coefficients $\{c_{d1}, c_{d2}, \ldots, c_{dn}\}$ and pairwise acceptance rates, then empirically measure these parameters for a range of model families (FLAN-T5, LLaMA, OPT) to produce **cascade-depth scaling laws** analogous to the pretraining scaling laws that motivated Chinchilla. The specific experiment: for a fixed target model (e.g., LLaMA-2-70B), construct cascades with 1, 2, 3, 4, and 5 draft models drawn from available smaller model sizes in the same family, measure the actual speedup on a standardized benchmark (GSM8K, HumanEval, or a custom diverse-prompt set), and determine at which depth the marginal speedup gain falls below, say, 1%. This would establish a practical guideline for practitioners: "for a target-to-smallest-drafter size ratio of $R$, the optimal cascade depth is approximately $\log(R)$"—or whatever the empirical relationship turns out to be.

**Training position-aware draft models for the Horizontal Cascade.** The Horizontal Cascade currently uses off-the-shelf models and allocates them to token positions purely based on their existing quality and cost characteristics. But if the downstream deployment is known to use a horizontal cascade with position-dependent allocation, the draft models themselves could be **fine-tuned for their specific position in the cascade**, analogous to how mixture-of-experts models train different experts for different input regions. The largest drafter (assigned to tokens 1–3) would be trained to maximize acceptance rate on early tokens specifically, potentially by fine-tuning on data where the loss weights early tokens more heavily. The medium drafter (assigned to tokens 4–8) would be trained to produce tokens that are acceptable *conditional on the first 3 tokens being accepted by the largest drafter*, which is a different distribution than standard next-token prediction. The specific experiment: take a base draft model, generate a dataset of target-model outputs, fine-tune three copies of the draft model with position-specific loss masks (first copy trained only on tokens 1–3, second on tokens 4–8, third on tokens 9+), then deploy them in a horizontal cascade and measure the acceptance rate improvement at each position compared to using the same model for all positions. This would test whether position-specific training can amplify the horizontal cascade's benefit beyond the current 4.6% walltime improvement (from the horizontal cascade ablation on Vicuna-7B, Section 5.2).

**Domain-adaptive MaG with retrieval-augmented matching.** The current MaG algorithm uses two static knowledge sources: the input prefix for maximal matching, and a Wikipedia-trained bigram model as fallback. Neither is adapted to the target task. A natural extension would replace or augment the Wikipedia bigram with **domain-specific n-gram statistics** retrieved at inference time. For example, on GSM8K (math word problems), the bigram could be trained on a corpus of mathematical text (arXiv, StackExchange math) rather than Wikipedia, potentially improving the fallback quality when prefix matching fails. More ambitiously, MaG could be replaced by a **retrieval-augmented generation (RAG) drafter** that retrieves similar problems from a training corpus and copies token sequences from their solutions. This would be analogous to how kNN-LM (Khandelwal et al., 2020) augments neural LMs with nearest-neighbor retrieval, but operating entirely outside the neural model. The specific experiment: on GSM8K, train a bigram model on the GSM8K training set solutions (rather than Wikipedia), measure the acceptance rate of MaG tokens by the smallest neural drafter (SMALL) with Wikipedia vs. in-domain bigram, and quantify the downstream speedup impact. If the in-domain bigram improves MaG's acceptance rate from, say, 0.15 to 0.25 for trailing tokens, the Horizontal Cascade's benefit would increase because those cheap tokens are now more valuable. This experiment would also test the paper's claim that the Wikipedia choice was "to maintain generality"—it may be that domain-specific MaG variants substantially improve per-task performance while remaining zero-cost at inference time.

**Direct measurement of the autoregressive elimination claim through latency profiling.** The paper's central architectural claim is that the Vertical Cascade "eliminates autoregressive generation from neural models." This is supported by end-to-end speedup measurements but never directly profiled. A valuable follow-up would instrument the CS Drafting implementation to log, for each speculative step, the wall-clock time spent in: (a) target model forward pass, (b) neural draft model forward passes (which should all be parallel reviews, not autoregressive generation), (c) MaG matching operations, and (d) verification/rejection logic. The key measurement: confirm that the neural draft models' time scales as O(1) per speculative step (a single parallel forward pass) rather than O(k) (k sequential forward passes for autoregressive generation). This profiling would provide a mechanistic validation of the paper's core efficiency claim, identify any residual sequential bottlenecks in the implementation, and guide further optimization (e.g., if verification/rejection logic turns out to be a surprisingly large fraction of walltime, it could be optimized). The experiment would also reveal whether the relative time breakdown differs between encoder-decoder and decoder-only architectures, potentially explaining the larger absolute speedups observed on FLAN-T5 vs. Vicuna-7B.

**Stress-testing lenience scoping: does intermediate lenience ever cause distributional drift?** The paper claims that applying lenience only at intermediate verification steps and using $l=1$ for the target model review preserves exact output distribution. This claim is theoretically justified but never empirically validated. A rigorous stress test would: (1) run CS Drafting with a high lenience value ($l=10$, $l=50$, $l=\infty$) at intermediate steps on a benchmark with measurable output metrics (e.g., GSM8K accuracy, MMLU accuracy, or BLEU score on a translation task), (2) compare the output distribution (via task accuracy and token-level distributional divergence metrics like KL divergence between output token empirical distributions) against autoregressive generation and standard speculative decoding, and (3) determine whether any implementation artifacts (numerical precision, edge cases in greedy decoding with lenience, interactions between lenience and the recalibrated resampling distribution) cause measurable deviations. If deviations are found even at modest lenience values ($l=3$ or $l=5$ as used in the paper), this would surface a previously undocumented failure mode of scoped lenience and motivate more careful lenience scheduling. If no deviations are found even at very high lenience, that would strengthen the paper's argument that intermediate lenience is unconditionally safe. This experiment is straightforward—it only requires instrumenting the existing CS Drafting implementation to capture output distributions—and would address the most significant empirical gap in the paper's validation.

**Scaling the FLOPs-matched pretraining–inference tradeoff analysis to Chinchilla-optimal baselines and larger models.** The paper's Section 7 provides the first systematic comparison of test-time compute vs. pretraining compute, but has two acknowledged weaknesses: the pretraining baseline uses parameter-only scaling (not Chinchilla-optimal joint scaling of parameters and data), and the model sizes are limited to PaLM 2-S* and a ~14× larger variant. A definitive follow-up would replicate the tradeoff analysis using: (a) a Chinchilla-optimal model family where both data and parameters are scaled (e.g., the Chinchilla model series itself, or LLaMA models where the compute-optimal training recipe is known), (b) a wider range of model sizes extending to the 70B+ parameter regime where inference cost dominates practical deployment decisions, and (c) additional reasoning benchmarks beyond MATH (code generation, scientific reasoning, multi-step planning) to test whether the difficulty-dependent results generalize. The specific experiment: for a Chinchilla-optimal 7B model, train (or obtain) Chinchilla-optimal 1B, 3B, 30B, and 70B variants, then for each target-drafter pair, measure the compute-optimal test-time scaling curve following the paper's methodology, and perform the FLOPs-matched comparison. The key question is whether the paper's finding that "test-time compute can substitute for a ~14× larger model on easy-to-medium problems" (Figure 9, $R \ll 1$ regime) holds, shrinks, or reverses when the pretraining baseline is compute-optimally trained. If the finding holds, it establishes a robust practical guideline; if it shrinks substantially, it refines our understanding of the pretraining–inference boundary.

### Practical Applications and Downstream Use Cases

**Cost-efficient LLM serving with a single additional lookup table.** The most immediately deployable finding is that adding the MaG model beneath an existing speculative decoding setup requires **no model loading, no fine-tuning, and negligible memory** (the bigram table is $V \times V$ where $V$ is the vocabulary size—typically 32K–50K entries, totaling a few megabytes). The paper demonstrates that this single addition improves speedup by 9.5% (BASE, GSM8K, MS) to 14.9% (BASE, MMLU, MS) over the best standalone speculative decoding configuration (Table 2). For a production LLM serving system processing billions of tokens daily, a 10–15% latency reduction with zero additional model parameters and zero training cost translates directly to either serving the same user base with fewer GPUs (and thus lower cloud costs) or serving more users with the same hardware (and thus higher throughput). The implementation path is straightforward: insert a MaG matching step before the existing neural drafter's forward pass, and configure the neural drafter to review MaG's proposed tokens using standard speculative decoding (with optional lenience for further gains). The paper's default hyperparameters (10 tokens generated by MaG per step, no lenience between MaG and the neural reviewer) provide a sensible starting point that already improves over the non-MaG baseline.

**Enabling larger, higher-quality draft models in production.** The paper's finding that the vertical cascade shifts the optimal draft model size upward (BASE outperforming SMALL in CS Drafting even when SMALL was the better standalone drafter, per Table 2 on MMLU) has direct implications for model selection in LLM serving systems. Production teams previously faced a dilemma: larger draft models produce better drafts but cost too much per token to be net-beneficial; smaller draft models are affordable but leave speedup on the table. CS Drafting resolves this by making larger draft models cost-effective again—their per-token cost remains the same, but they operate as parallel reviewers rather than autoregressive generators, and MaG absorbs some of the total drafting burden. The practical consequence: a team currently using FLAN-T5-SMALL (80M) as their optimal single drafter for an 11B target model can instead deploy BASE (250M) + MaG and expect higher speedup without increased memory overhead beyond the MaG lookup table. This means the engineering effort previously invested in making very small draft models work well (which often involves compromises on draft quality) can be redirected to using naturally higher-quality drafters that were previously rejected on cost grounds. The paper's hyperparameter details in Table 5 provide concrete starting configurations for this transition.

**Low-latency interactive applications where every millisecond counts.** For interactive LLM applications (chatbots, code completion, real-time translation), latency is user-facing and directional improvements are valuable even when absolute speedup factors appear modest. The decoder-only results on Vicuna-7B (Table 3: 56.72 tokens/s for CS Drafting vs. 44.31 tokens/s for standard speculative decoding on GSM8K, a 28% improvement) mean that a response that took 1.0 seconds with standard speculative decoding now takes 0.78 seconds—a 220ms reduction that is perceptible to users. For applications where the target model is larger than Vicuna-7B (e.g., 70B models deployed for high-quality chat), the absolute walltime savings per token are proportionally larger because the target forward pass dominates total latency. The paper's fixed default hyperparameter ($K_{nn} = [[2, 10], [0, 10]]$ for decoder-only) provides a zero-tuning deployment recipe: production engineers can integrate CS Drafting with this default configuration and expect improved latency, then optionally tune per-application if the marginal improvement is worth the engineering effort. The key practical insight is that CS Drafting's benefit does not depend on per-task hyperparameter optimization—Table 4 shows that varying $K_{00}$ from 1 to 3 changes walltime from 56.16 to 53.73 tokens/s, a small range that suggests default settings are robust.

**Integration with existing speculative decoding infrastructure.** Because CS Drafting is a drop-in replacement for the drafting component of speculative decoding (the verification mechanism is inherited unchanged), it can be integrated into existing serving frameworks that already support speculative decoding—such as NVIDIA's TensorRT-LLM, vLLM, or custom serving systems—without modifying the verification logic, the target model, or the serving infrastructure. The only code changes required are: (1) implementing the MaG matching function (Appendix A provides a GPU-friendly PyTorch implementation), (2) modifying the draft-generation loop to call MaG first and use the neural drafter as a reviewer, and (3) optionally adding the horizontal cascade logic (the for-loop structure in Algorithm 1) if multiple neural drafters are available. For teams that have already invested in speculative decoding deployment, adopting CS Drafting is an incremental engineering change rather than a system redesign, making the barrier to adoption low relative to the demonstrated speedup gains.
