# Hogwild! Inference: Parallel LLM Generation via Concurrent Attention

**ArXiv:** [2504.06261](https://arxiv.org/abs/2504.06261)

## 🎯 Pitch

Multiple LLM workers sharing the same attention cache in real time can spontaneously collaborate without being told how—one worker will pivot to a different sub-problem the moment it 'sees' that another worker has already solved its current task. This yields both higher accuracy and nearly 2× faster token throughput compared to sequential generation on the same hardware.

---

## 1. Executive Summary

This paper proposes **Hogwild! Inference**, a parallel LLM inference engine that enables multiple instances of the same model to collaborate dynamically during generation without a pre-defined cooperation framework. Using modern reasoning-capable models—primarily QwQ-32B, with additional evaluations on DeepSeek-R1, Qwen3, and Phi-4-Reasoning-Plus—across benchmarks including LIMO, OlympiadBench, LiveCodeBench, and AIME'25, the authors demonstrate that LLMs can spontaneously coordinate through a concurrently-updated shared Key-Value cache that gives workers instant, token-level visibility into each other's partial generations (e.g., one worker detecting that another has already solved a sub-problem and pivoting to a different approach). On the LIMO dataset, Hogwild! Inference with two workers achieves greater accuracy for the same compute budget compared to sequential baselines and self-consistency decoding, while the efficient implementation delivers nearly 2× higher token throughput for two workers and 3.2–3.6× for four workers on an L40S GPU. The approach generalizes across model families and sizes, establishing that zero-shot collaborative reasoning emerges from shared attention cache access only when models are sufficiently capable, with smaller models—particularly at the 1.7B scale—failing to adapt to the parallel setting and getting distracted from the task.

## 2. Context and Motivation

### The Core Problem: Inference-Time Reasoning Is Bottlenecked by Sequential Generation

The fundamental problem this paper tackles is the tension between how modern LLMs *reason* and how they *compute*. When solving complex problems—mathematical derivations, multi-step logical puzzles, competitive programming tasks—LLMs do something remarkable: they think step-by-step, generating long chains of reasoning that can span thousands of tokens. This capability, often called chain-of-thought reasoning, has become the dominant paradigm for extracting high-quality outputs from language models.

But there is a bottleneck. Every token in that reasoning chain must be produced one after another. The model generates "Alice thinks X, therefore Y, which implies Z..." as a strictly sequential process, with each new token conditioned on all previous ones. For hard problems—the kind that appear on the LIMO dataset, AIME competitions, or OlympiadBench—a single solution attempt can require 4,000, 8,000, or even 16,000 tokens of reasoning. On a modern GPU, that translates to minutes of wall-clock time, all spent in a single serial chain.

This matters because **many reasoning problems are not fundamentally sequential**. When two humans collaborate on a math problem, they do not take turns thinking. They work in parallel: one person explores an algebraic manipulation while another tests a geometric approach; one checks for edge cases while the other derives the general formula; one notices a mistake in the other's work and redirects. The serial bottleneck of LLM inference is an artifact of how we run these models, not an intrinsic property of the reasoning task itself.

The authors frame this gap explicitly in the introduction:

> "many reasoning problems are not sequential. Leveraging this intuition, several recent works propose parallel inference strategies that allow multiple LLMs to solve a problem faster or more accurately via some form of collaboration"

This observation—that parallelism is natural for reasoning but absent from inference—is the paper's motivating tension. The practical stakes are high: if we could parallelize reasoning across multiple LLM instances, we could potentially solve problems both *faster* (by dividing work) and *better* (by cross-checking, debating, and course-correcting). This connects directly to the broader trend of test-time compute scaling, where additional inference computation is treated as a resource to improve outputs. But while prior work has explored *how much* compute to spend, this paper asks *how to structure* that compute in parallel.

### Two Existing Paradigms for LLM Parallelism—And Their Limits

The paper identifies two major families of prior work on LLM parallelism, each with characteristic strengths and characteristic failures. Understanding both is essential to seeing why Hogwild! Inference is necessary.

---

#### Paradigm 1: Independent Parallel Generation + Aggregation (Self-Consistency and Debate)

The simplest approach to parallelizing LLMs is to run multiple independent reasoning chains and then combine their outputs. The canonical method is **Self-Consistency** (Wang et al., 2022): generate $N$ complete solutions independently, then take a majority vote on the final answer. This improves accuracy because different reasoning paths can arrive at the same correct answer through different routes, while incorrect answers tend to be more idiosyncratic and get outvoted.

Subsequent work extended this idea with more sophisticated aggregation mechanisms. Multi-Agent Debate (Du et al., 2023) has LLM instances exchange text-based arguments across multiple rounds, critiquing and refining each other's outputs. Other approaches assign specialized roles—Debugger, Examiner, Judge, Math Teacher—to create structured deliberation that catches errors that a single model might miss (Talebirad and Nadiri, 2023; Cohen et al., 2023; Kong et al., 2024; Chen et al., 2024). These role-based discussions can produce substantial accuracy gains, and in some cases, multiple weaker agents can collectively outperform a single stronger one (Wang et al., 2024a).

**Where this paradigm fails.** The authors identify two critical limitations:

1. **No genuine acceleration.** Under these approaches, "at least some of the agents have to solve the entire problem sequentially" (Section 2). If every agent independently generates a 4,000-token reasoning chain, the total computation is $N \times 4{,}000$ tokens, and the *wall-clock time* to get all outputs is determined by the slowest agent—the "straggler" problem. Adding more agents improves accuracy but does not reduce latency; it may even increase it because of the overhead of re-encoding other agents' outputs.

2. **Computational waste from redundancy.** When agents work independently, they frequently duplicate effort. Two agents might both compute the same intermediate result, both make the same logical error, or both explore the same dead end. The authors note this directly:

> "solving a problem in independent parallel 'threads' can be inefficient when one of the threads requires a longer generation than the rest, resulting in most of the agents waiting for a straggler and wasting compute"

Moreover, these methods are vulnerable to a deeper critique identified by Wang et al. (2024b) and Muennighoff et al. (2025): the improvements from multi-agent discussion can sometimes be matched or exceeded by better single-agent prompting. This raises the uncomfortable possibility that the gains from expensive multi-agent setups are partly artifacts of poor baselines rather than genuine benefits of collaboration.

---

#### Paradigm 2: Structured Task Decomposition + Parallel Execution (Skeleton-of-Thought)

A fundamentally different approach abandons the idea of multiple independent full solutions. Instead, a single LLM first decomposes the problem into sub-tasks, then launches parallel instances to solve each sub-task independently, and finally merges the results. **Skeleton-of-Thought** (SoT; Ning et al., 2024) is the representative method: the LLM generates a brief "outline" of independent sub-problems, executes them in parallel, and combines the outputs. Extensions apply this idea to function calling (Kim et al., 2024; Gim et al., 2024), tree-structured search with dynamic spawning of sub-tasks (Ding et al., 2025), and learned asynchronous task decomposition where a main agent offloads work to background "threads" (Jin et al., 2025; Liu et al., 2024b; Pan et al., 2025).

**Where this paradigm excels.** For problems that naturally decompose into independent pieces—compute five separate arithmetic expressions, answer four unrelated questions about a passage, evaluate a function at multiple points—Skeleton-of-Thought can achieve near-linear speedups. The authors demonstrate exactly this with their synthetic GSM8k×5 experiment (Section 4.1, Figure 3 left): when prompted to solve five independent math problems, SoT splits them across parallel threads and converges substantially faster than sequential generation. This is the paradigm working as designed.

**Where this paradigm fails—and why it matters.** The authors argue that the problem with SoT-like methods is not that they sometimes work poorly, but that their failure mode is *structural* and *unrecoverable*:

> "by imposing a specific parallelism strategy, these methods can harm reasoning for problems that do not fit their framework"

Three specific failure modes are identified:

1. **Rigid plan-execute-aggregate schedule.** SoT generates a decomposition plan upfront, then executes it, then merges. But complex reasoning often reveals that the *initial plan was wrong*. The authors note: "when solving a complex reasoning problem, it is often the case that the initial plan turns out to be wrong or incomplete" (citing Muennighoff et al., 2025; DeepSeek-AI et al., 2025). If the plan is flawed, the parallel workers are all solving sub-problems that may be irrelevant or incorrectly formulated, and there is no mechanism to replan mid-execution.

2. **Inability to adapt to varying sub-task difficulty.** Some sub-tasks turn out harder than expected and require more computation, while others are trivially easy. In a fixed parallel framework, the system must wait for the slowest sub-task. The authors describe this as a straggler problem: "some of the sub-tasks may turn out to be more complicated than originally intended and take up more work, which would cause methods like PASTA (Jin et al., 2025) to wait for that single task, whereas a more sophisticated reasoner could adjust the plan to work better in parallel."

3. **No cross-sub-task learning.** When one worker discovers an important insight—a simplification, a constraint the original plan missed, a contradiction that invalidates the approach—the other workers are unaware. They continue solving their assigned sub-tasks in ignorance, wasting computation on work that will ultimately be discarded or that should be reformulated in light of new information.

The authors summarize these limitations with a pointed observation: each specific failure can be patched with "yet another, more complicated parallelism framework," but the proliferation of special-case solutions "makes us doubt whether this is the right approach."

---

### The Deeper Issue: No Single Collaboration Strategy Works Universally

What connects the limitations of both paradigms is a shared assumption: that the *structure of collaboration* must be specified ahead of time by the system designer. Self-consistency mandates that all agents produce complete solutions independently and then vote. Skeleton-of-Thought mandates that the problem be decomposed into independent sub-tasks solved in isolation. Each framework encodes a theory of how collaboration *should* work, and when that theory matches the problem, performance improves. When it does not, performance degrades—sometimes catastrophically.

This is the gap the paper identifies at the deepest level. The authors point to human collaboration as a contrast:

> "Instead of strict adherence to a fixed collaboration strategy, we often collaborate more dynamically, re-planning on the fly, abandoning some tasks half-way and switching to a more promising approach, discussing or debating strategy if the initial plan failed."

Human collaborators do not pre-commit to "I will do the algebra while you do the geometry." They start working, notice what the other person is doing, adjust their approach, ask for help, point out errors, and renegotiate the division of labor as new information emerges. This flexibility is possible because humans can *see what each other is doing* in real time—we have shared access to the whiteboard, the conversation, the intermediate results.

The key insight of this paper is that modern LLMs, despite being trained for sequential generation, might be capable of *this same kind of dynamic collaboration* if given the right infrastructure. The requirement is not a better collaboration protocol, but a mechanism that gives LLM instances **continuous visibility into each other's partial reasoning** so they can spontaneously decide how to cooperate.

### How This Paper Positions Itself

The paper's framing is deliberately distinct from both existing paradigms:

**Against pre-defined frameworks.** The authors reject the idea that the system designer should specify how LLMs collaborate:

> "we run LLM 'workers' in parallel, allowing them to synchronize via a concurrently-updated attention cache and prompt these workers to decide how best to collaborate"

This is a radical shift in responsibility: rather than the researcher designing a collaboration protocol (voting, role assignment, sub-task decomposition), the LLM itself is responsible for figuring out how to cooperate on each specific problem. The system's job is to provide the *infrastructure* (shared attention cache) and the *prompt* (instructions to collaborate), but not the *strategy*.

**Drawing on Hogwild! parallelism.** The name is a deliberate reference to Hogwild! SGD (Recht et al., 2011), a classic algorithm in distributed optimization where multiple workers update a shared parameter vector asynchronously, applying each update as soon as it is computed rather than waiting for synchronization barriers. The analogy is structural: in the original Hogwild!, workers read and write to shared memory without locks; in Hogwild! Inference, LLM instances read and write to a shared attention cache, seeing each other's tokens as they are generated. The "exclamation mark is part of the original name" (Section 1 footnote), and the reference signals that the authors are drawing on a well-established tradition of asynchronous parallelism with shared state.

**The test-time compute scaling connection.** The paper positions itself within the broader trend of scaling inference computation to improve LLM performance. Prior work in this area (Snell et al., 2024; Muennighoff et al., 2025; Beeching et al.) has focused on *how much* additional computation to spend and *when* to stop (via early stopping strategies like budget forcing). Hogwild! Inference addresses a complementary question: *how to structure* that additional computation in parallel rather than sequentially. The two approaches are compatible—one could imagine a system that both allocates a test-time compute budget adaptively *and* executes that budget via parallel collaborative generation.

**Zero-shot capability as a design principle.** A crucial framing choice: the authors deliberately avoid fine-tuning models for collaboration. They instead rely on the in-context reasoning capabilities of existing models:

> "In this work, we focus on the [prompting] approach to make Hogwild! Inference easier to generalize for new models"

This is both a practical choice (no training cost, immediate applicability to new models) and a scientific one: it tests whether collaborative reasoning is an *emergent capability* of sufficiently capable LLMs rather than a skill that must be explicitly taught. The results suggest that for models like QwQ-32B, DeepSeek-R1, and larger Qwen3 variants, the answer is yes—but with sharp boundaries where smaller models (1.7B, 4B) fail to adapt and get "distracted from the task" (Section 4.1, Figure 4 right).

**The telepathic communication metaphor.** The paper uses a vivid metaphor for its core mechanism:

> "This 'telepathic' communication opens up new possibilities for efficient parallel generation with LLMs."

The word "telepathic" is carefully chosen. Unlike prior multi-agent systems where agents communicate through explicit text messages that must be encoded by one agent and decoded by another, Hogwild! workers access each other's raw Key-Value cache representations directly. They "see" each other's thoughts at the level of attention states, not just at the level of surface text. This eliminates the overhead of re-encoding and creates what is essentially instant, zero-cost communication—hence "telepathic."

This positions Hogwild! Inference not just as a new collaboration protocol, but as a **new capability layer** for LLMs. Just as chain-of-thought reasoning gave models the ability to think step-by-step, and tool use gave them the ability to interact with external systems, shared KV cache inference gives them the ability to collaborate in real time. The paper's core empirical claim is that this capability already exists latent in modern models and can be activated without additional training.

## 3. Technical Approach

### 3.1 Reader Orientation

The Hogwild! Inference system is a **parallel LLM inference engine** that runs multiple copies of the same language model simultaneously, giving each copy instant access to what every other copy is generating through a shared attention memory. The problem it solves is that existing methods for parallel LLM reasoning force models into rigid collaboration frameworks—independent voting or fixed task decomposition—that fail when the problem does not fit the pre-specified structure; the solution shape is to provide **infrastructure** (a concurrently-updated Key-Value cache that all workers can read and write to) and **prompting** (instructions to collaborate), while letting the LLM instances themselves decide how to cooperate on each specific problem.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components connected in a pipeline:

1. **Base LLM (shared weights)** — a single pretrained model (e.g., QwQ-32B, DeepSeek-R1) whose weights are identical across all parallel workers. Each worker runs its own forward pass but uses the same parameters.

2. **Parallel Worker Instances** — multiple "workers" (typically 2, 3, or 4, each given a name like Alice, Bob) that generate tokens concurrently, one token per worker per forward pass. Each worker maintains its own generation state (its "current step" being written) but sees the states of all other workers.

3. **Shared Key-Value Cache with Block Structure** — the central coordination mechanism. Rather than each worker having its own isolated KV cache, all caches are organized into blocks (common prompt/history, one block per worker for their current unfinished step) that are *rearranged* and *viewed in different order* by each worker using RoPE rotation. This gives every worker immediate visibility into every other worker's partial generations.

4. **Cache Layout Manager** — logic that organizes cache blocks into one of three layouts: contiguous (all tokens from a worker kept together), interleaved (only completed reasoning steps visible to others), or combined (the main layout: completed steps in a shared history, plus instant token-level visibility into each other's current unfinished steps). Steps are delimited by paragraph breaks (`\n\n`).

5. **Prompting System** — a two-part mechanism: (a) a system prompt describing the "rules" of the shared cache and instructing workers to collaborate; (b) periodic s1-style interventions every ~1,000 generated tokens that ask a random worker "Wait, am I doing redundant work? (yes/no):" to prompt course correction.

Information flows as follows: the system prompt and task are placed in the common cache → workers begin generating reasoning steps in parallel → each worker's new tokens are immediately appended to their cache block and become visible to all other workers via rotated queries → when a worker completes a paragraph, their block is moved to the shared history and their local cache is reset for a new step → workers read the shared history and each other's current progress to decide their next actions → if the budget is exhausted before an answer is produced, an early-stopping prompt forces final answer generation.

### 3.3 Roadmap for the Deep Dive

- **First**, the shared KV cache mechanism and how concurrent attention works, since this is the core infrastructure that makes parallel generation with mutual visibility possible.
- **Second**, the RoPE rotation trick that enables rearranging cache blocks without re-computing representations, since this is the key efficiency insight that avoids cubic overhead.
- **Third**, the three cache layouts (contiguous, interleaved, combined) and the step-based synchronization mechanism, since these define *what* workers can see and *when*.
- **Fourth**, the prompting strategy (system prompt and s1-style interventions), since this is what activates collaborative behavior from models that are otherwise just generating tokens.
- **Fifth**, the implementation details (query rotation for efficient attention, FlashDecoding integration, parallel batch execution), since the practical feasibility of the approach depends on these optimizations.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems and empirical analysis paper** whose core idea is that LLMs can perform dynamic, self-organized parallel collaboration when given a shared attention memory with instant visibility into each other's partial reasoning, without any pre-defined collaboration protocol or specialized fine-tuning.

---

#### Shared Key-Value Cache for Concurrent Attention

The central mechanism of Hogwild! Inference is that multiple LLM inference threads share a common Key-Value cache, allowing each worker to attend to the tokens generated by all other workers as though those tokens were its own previous outputs. This is the infrastructure that enables "telepathic" communication—workers do not exchange text messages that must be separately encoded; they directly access each other's internal attention states.

**How standard KV caching works (for context).** In normal autoregressive LLM inference, when the model generates token $t$, the Key and Value representations for that token—produced by projecting the token's hidden state through learned weight matrices in each attention layer—are stored in a cache. When generating token $t+1$, the model computes attention over all previous tokens' stored Keys and Values, avoiding the need to recompute representations for past tokens. This cache grows linearly with sequence length and is specific to a single generation thread.

**What Hogwild! Inference changes.** Instead of each worker having a private cache, all workers read from and write to a *shared* cache that is partitioned into blocks. As workers generate new tokens, they append their Key-Value pairs to their respective cache blocks. But critically, when Worker A computes attention for its next token, it does not just attend to its own past tokens—it attends to Worker B's tokens, Worker C's tokens, and the common prompt/history, all arranged in a specific order determined by the cache layout.

**The attention computation.** For a given worker $W_i$ generating its next token, the attention mechanism computes:

$$\text{Attention}(q_i, K_{\text{shared}}, V_{\text{shared}}) = \text{softmax}\left(\frac{q_i K_{\text{shared}}^T}{\sqrt{d_k}}\right) V_{\text{shared}}$$

where $q_i$ is the query vector for worker $W_i$'s current token (a learned projection of the token's hidden state), $K_{\text{shared}}$ is the concatenation of Key vectors from all cache blocks visible to $W_i$ (common prompt, other workers' current steps, $W_i$'s own past tokens), $V_{\text{shared}}$ is the corresponding concatenation of Value vectors, and $d_k$ is the per-head dimension of the Key vectors.

**What this computes:** the standard scaled dot-product attention, but over a *composite* sequence formed by stitching together tokens from multiple independent generation threads. The softmax produces attention weights that sum to 1 over all visible tokens, meaning worker $W_i$ distributes its attention across its own past reasoning, the prompt, and the partial outputs of every other worker. The weighted sum of Values then informs $W_i$'s next token prediction, allowing it to condition on what others are currently writing.

**Why this form:** using the standard attention mechanism unchanged means that any pretrained LLM can immediately participate in Hogwild! Inference without architectural modifications. The model already knows how to attend to context—we are simply providing a richer, dynamically-updated context that includes concurrent generation. The softmax normalization ensures that attention weights remain interpretable regardless of how many cache blocks are concatenated.

**The instant-visibility property.** A crucial design choice: when Worker A generates a new token, its Key-Value representations are immediately appended to Worker A's cache block *and become visible to all other workers on their very next forward pass*. As the paper states:

> "This allows both workers to instantly 'see' each other's tokens while they are generated — and even before they are processed by all layers."

This is different from message-passing approaches where one agent must finish a complete utterance, which then gets encoded as text by the other agent. In Hogwild! Inference, Worker B can condition on Worker A's partial, mid-sentence reasoning at the attention level, without any encoding latency or information loss from converting representations to text and back.

**Why blocks rather than one monolithic cache.** Partitioning the cache into blocks (one per worker plus a common block) is necessary because different workers need to see the same tokens in *different orders*. Worker A should see its own tokens last (as the most recent context it is continuing), while Worker B should see Worker A's tokens earlier (as context to learn from, followed by Worker B's own tokens as the continuation). A single flat cache cannot satisfy both ordering requirements simultaneously. Blocks enable the rearrangement described next.

#### RoPE Rotation for Zero-Cost Cache Rearrangement

The block structure creates a problem: the same Key-Value pairs appear at different absolute positions for different workers. If Worker A's tokens are at positions 100–199 in its own view, they might be at positions 200–299 in Worker B's view. Since modern LLMs use Rotary Position Embeddings (RoPE), which encode absolute position information, this discrepancy would normally require re-encoding all past tokens at their new positions for each worker—an operation whose cost scales cubically with the number of workers, as the paper notes:

> "If $n$ agents generate one new token each, which is then re-encoded differently for each of these $n$ agents, that each have to attend to $O(n)$ additional tokens, then the total step complexity is $O(n^3)$."

The solution exploits a mathematical property of rotation: rotating both the query and the key by the same angle does not change their dot product.

**RoPE recap.** In RoPE, a query or key vector $x \in \mathbb{R}^d$ (where $d$ is even) is split into $d/2$ pairs, and each pair $(x_{2k}, x_{2k+1})$ is rotated by an angle $\theta_k \cdot p$, where $p$ is the absolute position of the token and $\theta_k$ is a frequency that varies with the dimension index $k$. The rotation is implemented as:

$$\rho(x, p) = \begin{pmatrix} x_0 \cos(\theta_0 p) - x_1 \sin(\theta_0 p) \\ x_1 \cos(\theta_0 p) + x_0 \sin(\theta_0 p) \\ \vdots \end{pmatrix}$$

where $\rho(x, p)$ denotes the vector $x$ rotated to position $p$, $\theta_k = \text{base}^{-2k/d}$ (typically base = 10,000), and $x_{2k}$, $x_{2k+1}$ are the $k$-th dimension pair.

**The rotation trick.** Suppose a query $q$ at absolute position $i_q$ needs to attend to a Key block $K$ that is stored as though it were at starting position $i_k$. The attention dot product would normally be:

$$\rho(q, i_q) \cdot \rho(K, i_k)$$

The key insight is that this equals:

$$\rho(q, i_q - i_k) \cdot \rho(K, 0)$$

where $K$ is stored at its "native" position 0 (i.e., unrotated), and only the query is rotated by the *relative* position offset $i_q - i_k$.

**Why this works.** Rotation is a linear operation that satisfies the additive property: rotating by $i_q$ and then comparing to a key rotated by $i_k$ is equivalent to rotating the query by $i_q - i_k$ and comparing to an unrotated key. Formally, $\langle \rho(q, a), \rho(k, b) \rangle = \langle \rho(q, a-b), \rho(k, 0) \rangle$ because the dot product depends only on the *difference* in rotation angles, not the absolute angles. Since $\rho$ is an orthogonal transformation, and orthogonal transformations preserve dot products, the equivalence holds.

**What this enables.** Instead of rotating every token in every cache block for every worker—an $O(n \cdot \text{total\_tokens})$ operation—we rotate only the *current query* multiple times, once for each cache block it needs to attend to. For $n$ workers each attending to $n+1$ cache blocks (one per other worker plus the common block), this requires $n \cdot (n+1)$ query rotations per forward pass, regardless of how many total tokens are in the cache. As the paper states:

> "the r.h.s. formula only rotates the current step query, i.e. a single token per worker, as opposed to the past KV blocks that can contain thousands or millions of tokens."

**Multiple rotations per query for multi-block attention.** When a worker attends to multiple cache blocks (common, worker A, worker B, worker C), it needs to compute attention separately for each block with the query rotated to the appropriate relative position. The paper gives the formal expression:

$$\rho(q, i_q)\left[\rho(A, i^A_k) \oplus \rho(B, i^B_k) \oplus \rho(C, i^C_k)\right] = \rho(q, i_q - i^A_k)A \oplus \rho(q, i_q - i^B_k)B \oplus \rho(q, i_q - i^C_k)C$$

where $\oplus$ denotes concatenation of Key vectors from different blocks, $A, B, C$ are unrotated Key blocks stored at position 0, $i^A_k, i^B_k, i^C_k$ are the absolute starting positions those blocks *would* have in this worker's view, and $\rho(q, i_q - i^A_k)$ is the query rotated by the relative offset to block A.

**What this computes:** the attention dot product between the current query and all past tokens, decomposed into per-block computations. The query is rotated three times (once per block) to the relative position that matches each block's logical position in the worker's concatenated view. The results are then combined in the softmax summation.

**Why this form over alternatives:** the alternative—rotating all cached Key vectors to their new positions—is $O(\text{total\_tokens})$ per step, which becomes prohibitive for long contexts (where total_tokens can be 10,000+). The query-rotation approach is $O(1)$ per block per step, which is negligible. The tradeoff is that we must compute a separate dot product for each block rather than one unified dot product, but since attention already requires $O(\text{total\_tokens})$ work for the dot product, adding a constant number of query rotations does not change the asymptotic complexity.

#### Cache Block Structure and Layouts

The shared KV cache is organized into blocks that serve different roles. The paper defines three specific layout strategies, each representing a different point on the spectrum of how much and how frequently workers see each other's output.

**Block types.** For a system with $n$ workers, the cache consists of $n+1$ blocks, all stored with their tokens at positions $0, 1, \ldots, \text{len}(\text{block})$ regardless of their logical position in any worker's view (the rotation trick handles the position offset):

- **Common Cache:** one large block containing the system prompt, task description, and a chronological history of completed reasoning steps from all workers. This never shrinks and grows as steps are completed.
- **Worker blocks (one per other worker):** smaller blocks containing the latest *unfinished* reasoning step of each other worker. When there are 4 workers, Worker $W_2$ sees blocks for $W_1$, $W_3$, and $W_4$ (in ascending order).
- **Own block:** the current unfinished reasoning step of the worker itself, placed last (as immediate previous context to continue).

**Step demarcation.** A "reasoning step" is defined as any text ending with an end-of-sentence marker (`.`, `?`, `!`) followed by a double newline (`\n\n`). The definition excludes cases where the newline appears inside a code block (steps continue until the code block closes) or where the preceding punctuation is non-terminal (comma, colon, semicolon). This heuristic captures natural paragraph breaks in reasoning.

**What happens when a step completes.** When a worker generates the double-newline following a sentence-ending token, the system:

1. Takes the worker's entire current block (all tokens of the finished step).
2. Rotates its Key-Value pairs to the appropriate absolute position for the shared history (they will appear after all previously completed steps).
3. Appends them to the Common Cache block, which grows.
4. Resets the worker's local block to empty, starting with a header like "Alice [3]:" (worker name and step counter).
5. The worker continues generating the next step into this new block.

This implements a "group chat" metaphor: each completed paragraph becomes a permanent message in the shared history that all workers can reference, while the current unfinished paragraph is visible in real time but not yet committed to history.

**Layout 1: Contiguous (token-wise, no step separation).** The simplest possible layout. Each worker's entire output is kept in one contiguous block. Worker A sees: [Common Prompt] → [Worker B's entire output so far] → [Worker C's entire output so far] → [Worker A's entire output so far]. There is no splitting into steps and no shared history of completed steps—workers simply grow their own sequences and read each other's sequences.

**Advantage:** simplest to implement, fine for short interactions.

**Disadvantage:** as the paper notes, "workers will eventually pay less attention to each other because of the thousands of tokens between their latest steps." If Worker A's total output is 4,000 tokens long and Worker B is reading it as context, Worker B's latest token is separated from Worker A's latest update by 4,000+ tokens of distance. Since attention weights typically decay with distance (especially in models not explicitly trained for ultra-long contexts), Worker B may effectively ignore Worker A's recent work.

**Layout 2: Interleaved (step-wise, no instant visibility).** Workers generate steps in private and only expose them to others *after completion*. The Common Cache grows with completed steps in chronological order of completion. Workers do not see each other's current unfinished steps. This is akin to a forum where you only see others' posts after they are submitted, not while they are being drafted.

**Advantage:** clean separation of concerns; no risk of being distracted by half-finished reasoning.

**Disadvantage:** as shown in the collaborativeness analysis (Figure 7), step-wise synchronization "scores significantly lower" than token-wise. The latency between when a worker writes something and when others can respond creates coordination friction—by the time Worker B sees Worker A's completed step, Worker B may have already written several steps in a wrong direction.

**Layout 3: Combined (token-wise + step-wise, the main layout).** This is the primary layout used in all experiments except the ablation studies. It combines both forms of visibility:
- **Step-level:** completed steps are moved to the shared history, keeping historically important reasoning close to the current context.
- **Token-level:** workers see each other's current unfinished steps *as they are being written*, enabling immediate reaction.

The arrangement for each worker $W_i$ is: [Common Cache] → [Other workers' current blocks in ascending order, e.g., $W_1 \oplus W_3 \oplus W_4$ for $W_2$] → [Own current block].

**Why this layout.** The paper explains the motivation through the "group chat" metaphor (Section 3.2): workers need to see recent updates to coordinate effectively (token-level visibility), but they also need the full historical context of past decisions and results (step-level common cache). The combined layout ensures that the most recent tokens from all workers are always at nearby positions for every worker's attention mechanism, while completed steps are preserved in chronological order. This mirrors how human collaborators in a chat room can see each other's typing indicators and partial messages while also scrolling back through the conversation history.

**Ablation evidence.** The ablation in Appendix E.1 (Figure 10, left) confirms that the combined layout outperforms both simpler layouts on the LIMO dataset. The contiguous layout performs similarly at short budgets but degrades at longer contexts (likely due to the distance-based attention dilution). The interleaved layout without instant synchronization "performs poorly at smaller budgets, but catches up eventually"—the paper attributes this to the increased difficulty of cross-worker coordination when synchronization is delayed.

#### Prompting Strategy for Zero-Shot Collaboration

Even with the shared cache infrastructure, there is no guarantee that LLM instances will spontaneously collaborate. The model is still fundamentally a next-token predictor; without explicit prompting, it might treat the multi-worker setup as noise and continue generating in isolation. The paper uses a two-part prompting approach to activate collaborative behavior.

**Part 1: System prompt describing the collaboration "rules."** The system prompt (reproduced in full in Appendix C) is a lengthy instruction that:

- Names the workers ("Alice and Bob" for two workers) and tells each they are one of them.
- Explains the cache structure: they will see "### Past steps" (shared history) and "### Work in progress (others)" (other workers' current unfinished steps) followed by "### Work in progress (own)" (their own continuation).
- Instructs them that other workers' thoughts will appear partial and ongoing, and that they should use these to "decide how best to collaborate without doing the same work twice."
- Explicitly authorizes them to stop and change tasks: "If what you are currently doing is the same thing that another assistant has already done or is in process of doing, you will stop (...) and change to a different task right away."
- Gives them freedom to choose any collaboration strategy: "You can collaborate by doing different parts of the problem, double-checking each other's results, trying different approaches, or any other means."

**Design rationale.** This prompt does not specify *how* to collaborate—it specifies that collaboration is expected and provides the "API" (what information they can see, in what format). The models must then reason about what specific actions to take given the problem and their partner's visible behavior. This is a bet on the in-context reasoning capabilities of modern LLMs: that they can translate a high-level collaboration mandate into specific, context-appropriate cooperative behaviors.

**Part 2: Periodic s1-style intervention prompts.** The paper adapts the budget-forcing technique from Muennighoff et al. (2025), but re-purposes it for coordination rather than answer extraction:

> "every thousand generated tokens, we prompt a random worker with 'Wait, am I doing redundant work? (yes/no):' at the beginning of their next paragraph."

**What this does.** At approximately every 1,024 tokens of generation (this serves as a coordination checkpoint), one worker is interrupted and asked to explicitly evaluate whether its current work is redundant. The model must generate "yes" or "no" in response. The paper's examples show that this intervention often triggers course correction:

- **Example from Task 122:** Alice responds "no. Bob, I see you're working on the same product. Let me think of another approach" and pivots to a different method.
- **Example from Task 40:** Bob responds "Yes, Alice is computing a3, so I'll do something else. Let me try to find a pattern or transformation that could simplify the recurrence."
- **Example from Task 466:** Bob responds "Yes, Alice is already calculating the x-coordinate of A. I'll do something else. Let me find the coordinates of L instead."

**Why this works (when it works).** The authors diagnose a specific failure mode that the intervention addresses:

> "We found that LLMs fine-tuned on reasoning can often become too 'focused' on what it is generating currently and fail to notice that another instance has found a mistake or solved their problem earlier."

The periodic check forces the model to step back from its local generation and evaluate the global state—has someone else already done this? Is this sub-problem still relevant given what others have discovered? The prompt acts as an explicit meta-cognition trigger that breaks the model out of local reasoning loops. The authors note that this is not always reliable ("LLMs often (but not always) detect redundancies"), but it significantly improves coordination in practice.

**Why not just fine-tune models to collaborate?** The paper explicitly addresses this: "In this work, we focus on the [prompting] approach to make Hogwild! Inference easier to generalize for new models." The zero-shot design means any existing reasoning-capable LLM can be used immediately without collecting collaborative training data or running specialized fine-tuning. This also serves as a scientific test: if collaborative behavior emerges from prompting alone, it suggests the capability is already latent in the model's training rather than being newly taught.

**Connecting to prior work on s1.** Muennighoff et al. (2025) used budget-forcing ("Wait, I should give an answer now") to extract answers from models that were overthinking. Hogwild! Inference adapts this technique by repurposing the interruption for coordination rather than termination—"am I doing redundant work?" instead of "give an answer now." The structural parallel (periodic forced reflection) remains, but the semantic content is tailored to the multi-worker setting.

#### Parallel Forward Pass and Batch Execution

Hogwild! Inference generates tokens from all workers simultaneously in a single batched forward pass. This is not just an implementation convenience—it is what enables the instant cache synchronization property.

**Standard batched inference (for context).** In normal LLM inference with batch size $B > 1$, each sample in the batch has its own independent KV cache. The attention computation for sample $i$ only accesses cache $i$. The samples are processed in parallel on the GPU, but they do not interact.

**Hogwild! batched inference.** The batch dimension represents workers. During a forward pass:

1. **Token encoding:** Each worker's current token is embedded and processed through the model layers, producing new Key and Value vectors for that worker.
2. **Cache update:** These new KVs are appended to the end of each worker's respective cache block (the "own" block).
3. **Attention computation:** For each worker $i$, attention is computed over a *different arrangement* of the shared cache blocks. Worker 1 sees $[\text{Common}] \rightarrow [\text{Block}_2] \rightarrow [\text{Block}_1]$, while Worker 2 sees $[\text{Common}] \rightarrow [\text{Block}_1] \rightarrow [\text{Block}_2]$, and so on. This is implemented by the multi-rotation query mechanism described in Section 3.4.2.
4. **Output:** Each worker produces its next-token prediction conditioning on all visible context, including other workers' most recent tokens.

**The novelty.** The key departure from standard batched inference is Step 3: batch elements are no longer isolated. They attend to each other's caches, but in different orders. The authors frame this as:

> "Instead of each sample having its own attention cache, we allow batch elements to attend to each other's KV caches at different positions."

**Why this enables instant synchronization.** Because all workers generate one token in the same forward pass, each worker's *previous* token (generated in the last forward pass) is already in the cache and visible to others. But crucially, as the paper states, "both workers can immediately attend to each other's current tokens even before they are fully processed by all layers." The forward pass proceeds layer-by-layer: at layer $L$, the attention computation for all workers uses the Key-Value caches updated with tokens from layers $0$ through $L-1$ of the current forward pass. This means that by the time the forward pass completes, every worker has conditionally generated its next token with full knowledge of what every other worker wrote in all previous tokens plus partial knowledge of what they are writing in the current token.

#### Efficient Implementation with FlashDecoding and Query Rotation

The naive implementation of Hogwild! attention—computing attention separately for each block with differently-rotated queries—would be inefficient on GPU hardware. The paper describes an optimized implementation built on FlashDecoding principles.

**The FlashDecoding approach (background).** FlashDecoding (Dao et al., 2023) is an attention kernel optimization for long-context inference. The key idea is to split the Key-Value sequence across streaming multiprocessors (SMs) on the GPU, compute partial attention outputs independently, and then combine them with a final reduction. This avoids repeatedly loading the entire KV cache into each SM, improving memory bandwidth utilization.

**Adapting to Hogwild! attention.** The paper's implementation treats each cache block as a "page" in a paged-attention style (Kwon et al., 2023). For each worker and each cache block that the worker needs to attend to:

1. The query for that worker is rotated by the relative offset for that block.
2. The block's Key-Value pairs (which are stored contiguously in a memory buffer) are loaded once and used for all workers that need to attend to that block.
3. Attention dot products and softmax-weighted sums are computed in a split-k fashion, where different SMs handle different subsets of the block's tokens.

**The critical resource sharing.** Because all workers attend to the same blocks (just in different orders and with different query rotations), the KV cache blocks only need to be loaded from GPU memory *once* per forward pass, not once per worker. The query rotations for different workers are applied on-the-fly (a cheap element-wise operation) and do not require reloading the cache. As the paper states:

> "We gather each KV cache block in a contiguous memory buffer and compute attention similarly to Paged Attention, where one page would correspond to one cache block and the corresponding query rotations from all workers."

**Performance characteristics (Table 2).** The paper provides a breakdown of the attention kernel overhead compared to pure FlashAttention:

- For an empty cache (300 tokens), the Hogwild! attention kernel takes 45µs for 2 workers and 45µs for 4 workers, versus 11µs for standard FlashAttention. The setup time (preparing data structures, computing rotation offsets) adds 1.9ms for 2 workers and 3.9ms for 4 workers.
- At 16,384 tokens, the attention kernel takes 140µs (2 workers) and 203µs (4 workers), versus 100µs for standard FlashAttention. The setup time remains constant (1.9ms and 3.9ms respectively) since it only depends on the number of blocks, not the number of tokens.

**What this reveals about scaling.** The attention kernel is roughly 40–100% slower than pure FlashAttention depending on the number of workers, but this overhead is offset by the fact that Hogwild! Inference generates $W$ tokens per forward pass (where $W$ is the number of workers), while standard inference generates only 1. The constant setup time per forward pass (1.9ms for 2 workers) becomes negligible at long sequence lengths (where a forward pass takes 55+ms), meaning the per-token throughput approaches $W \times$ the baseline for large models and long contexts.

**Throughput results (Table 1).** For QwQ-32B-AWQ on an L40S GPU:
- 1 worker (baseline): 20.1 tokens/second at 1,024 context length, dropping to 18.3 at 16,384.
- 2 workers: 36.3 tokens/second at 1,024 (1.81× baseline), dropping to 34.3 at 16,384 (1.87× baseline).
- 4 workers: 68.9 tokens/second at 1,024 (3.43× baseline), dropping to 60.3 at 16,384 (3.30× baseline).

The near-linear scaling shows that the query rotation overhead remains manageable even at four workers, and the setup cost is amortized over the forward pass computation.

**Extension to distributed inference.** The paper briefly describes (Appendix B) how Hogwild! Inference maps to distributed setups:
- **Tensor parallelism:** each GPU stores a subset of attention heads for all cache blocks. Standard tensor-parallel kernels work with minor modifications since query rotation is per-head.
- **Pipeline parallelism:** each GPU stores cache blocks for its local subset of model layers. The block structure is replicated across pipeline stages.
- **Sequence parallelism:** a natural mapping is to assign each GPU one or several workers, store those workers' generated KVs locally, and use All-to-All communication to exchange rotated queries between GPUs for cross-worker attention. This would require custom kernels to overlap computation and communication, which the paper identifies as future work.

#### Early Stopping and Answer Extraction

All experiments (except the "Baseline (no early stopping)" condition) use a common technique for extracting final answers when the generation budget is exhausted before a natural answer is produced.

**The early-stopping prompt.** When the forward pass budget is reached and no `\boxed{...}` answer has been generated, the system inserts:

> "\n\nWait, given the limited time, I have to give an answer right now. Considering all my previous attempts, I have to conclude that the final answer is \boxed{"

The model then generates up to a fixed number of tokens to complete the `\boxed{}`. The token limits vary by benchmark: 16 for LIMO and AIME, 64 for OlympiadBench, and 1024 for LiveCodeBench. These additional tokens are not counted toward the generation budget on the x-axis of the plots because "they have an equal effect on all methods."

**Why this is necessary.** Reasoning models can generate very long chains of thought, and with a fixed forward-pass budget, they may be interrupted mid-reasoning. Without the early-stopping prompt, the model would simply stop mid-sentence and produce no answer. The prompt forces the model to synthesize whatever partial reasoning it has accumulated into a best-guess answer.

**For Hogwild! Inference specifically.** When extracting answers from multiple workers, the generated outputs from all workers are concatenated and fed into a single model instance (the "final model"), which views all generated tokens and generates the answer. The paper notes: "This is equivalent to viewing the problem from the perspective of the last worker, e.g. Bob if there are two." This means the answer extraction is itself a Hogwild! attention operation where the model sees the full conversation history before producing its final output.

**Baseline comparison nuance.** The paper distinguishes between "Baseline (no early stopping)" and "Baseline." The former is standard sequential generation where the model runs until it either produces `\boxed{}` or hits the budget and produces nothing. The latter uses the early-stopping technique. This distinction is important because the early-stopping baseline is a stronger comparison—it ensures that any advantage of Hogwild! Inference is not simply due to forcing answer extraction earlier. The paper also notes that for QwQ-32B:

> "the model almost always returns answers correctly if they are present, and if not, it guesses or refuses to answer (unknown, n/a or similar)"

This suggests the early-stopping mechanism is reasonably reliable for this model family, though its behavior on incorrect answers (guessing vs. refusing) may add noise to the accuracy measurements.

#### Summary of Design Choices and Justifications

**Shared KV cache over message passing:** avoids the overhead of re-encoding text messages and enables token-level coordination without information loss from discretizing attention states into surface text. The "telepathic" communication is not just a metaphor—it is a lower-latency, higher-bandwidth channel than explicit text exchange.

**RoPE rotation over re-encoding:** reduces the per-step overhead from $O(\text{total\_tokens})$ to $O(1)$ per block, which is the difference between practical and impractical for long contexts. The mathematical property that rotation preserves dot products under additive offsets makes this possible without approximation.

**Combined cache layout over contiguous or interleaved alone:** provides both long-term context (via the step history) and immediate reactivity (via token-level current-step visibility). The history ensures that past decisions are not lost, while instant visibility enables dynamic course correction without waiting for steps to complete.

**Prompting over fine-tuning:** makes the method immediately applicable to any reasoning-capable LLM, tests whether collaboration is an emergent rather than taught capability, and avoids the engineering complexity of constructing multi-worker training data. The zero-shot nature is both a practical convenience and a scientific choice.

**Periodic s1-style interventions over continuous monitoring:** addresses the specific failure mode of models becoming overly focused on local generation. The interventions are cheap (one extra token per 1,024) and provide explicit meta-cognition triggers that models trained for sequential reasoning might not spontaneously deploy.

**Batch-level parallelism over sequential multi-worker execution:** enables instant cache synchronization because all workers generate tokens in the same forward pass. If workers ran sequentially, Worker B would always see Worker A's previous tokens, never the current ones, reducing coordination bandwidth.

**FlashDecoding-compatible block structure:** ensures the method scales to long contexts by leveraging existing optimized attention kernels. The paged-attention analogy allows reuse of battle-tested infrastructure from vLLM and SGLang, though the query rotation adds a novel per-block computation not present in standard paged attention.

## 4. Key Insights and Innovations

### Innovation 1: LLMs Can Self-Organize Parallel Collaboration Without Pre-Defined Frameworks

The paper's most fundamental contribution is a conceptual reframing of multi-LLM reasoning. Prior work assumed that parallel collaboration between LLM instances requires explicit design: define how agents communicate (text-based debate rounds in Du et al., 2023), what roles they play (Debugger, Examiner, Judge in Talebirad and Nadiri, 2023; Cohen et al., 2023), or how they decompose tasks (fixed plan-execute-aggregate in Ning et al., 2024; learned sub-task spawning in Jin et al., 2025). The researcher's job was to specify the *interaction protocol*.

Hogwild! Inference inverts this responsibility. The system provides only **infrastructure**—a shared attention cache that gives every worker instant, token-level visibility into every other worker's partial reasoning—and a **prompt** telling them to collaborate, but does not prescribe *how*. The models themselves decide whether to split sub-tasks, cross-verify results, debate strategy, or pivot approaches. As the authors state:

> "Instead of choosing how LLMs should interact ahead of time, we allow them to generate tokens in parallel and 'see' each other's progress (tokens) immediately as they are generated. We then prompt the LLM 'workers' to decide their next course of action by themselves."

This is a shift from **protocol engineering** to **capability activation**. The paper's core empirical finding is that modern reasoning models—QwQ-32B, DeepSeek-R1, larger Qwen3 variants—already possess this self-coordination capability latent in their training, and it can be elicited through infrastructure alone, without fine-tuning.

**Why this isn't obvious.** One could reasonably expect that LLMs trained for sequential text generation would not know how to coordinate with concurrent instances, even with shared memory access. Models learn from single-threaded text corpora; multi-agent coordination is not part of their training distribution in any direct sense. The fact that they *can* do it—that they formulate and follow plans, point out each other's errors, and adapt when initial plans fail—is evidence that collaborative reasoning is an emergent property of sufficiently capable LLMs, not a specialized skill requiring explicit training.

**Significance beyond performance.** This finding has implications for how we think about LLM capabilities. It suggests that the boundary between "what models can do" and "what we need to teach them" may be wider than assumed. Given appropriate infrastructure for information sharing, models may unlock behaviors that their training data only supported implicitly—here, the ability to reason about parallel coordination dynamics despite being trained on sequential text.

The zero-shot nature is verified empirically across model families: QwQ-32B shows strong collaboration on LIMO (Figure 3, middle), Phi-4-Reasoning-Plus adapts similarly (Figure 12), Qwen3-235B-A22B scales effectively (Figure 18), and DeepSeek-R1 demonstrates coordination on AIME'25 (Figure 6, right). The boundary condition—smaller models (1.7B, 4B) "fail to adapt to the task and get distracted" (Section 4.1, Figure 4 right)—further supports the interpretation that this is a capability that emerges with sufficient model scale and reasoning training, not an artifact of prompting alone.

### Innovation 2: Shared Attention Cache as a New Communication Primitive—"Telepathic" Rather Than Conversational

The paper introduces a fundamentally different communication mechanism for multi-agent LLM systems. In all prior parallel reasoning frameworks, communication between agents happens through **explicit text exchange**: one agent generates a complete message, which is then encoded as input by another agent. This is conversation—the same modality humans use when collaborating through language.

Hogwild! Inference replaces conversation with **direct attention-state sharing**. Workers do not generate text for each other; they access each other's raw Key-Value cache representations at the attention level. The paper captures this with the "telepathic" metaphor:

> "This 'telepathic' communication opens up new possibilities for efficient parallel generation with LLMs."

**What makes this distinctive.** The distinction is not merely an implementation detail—it is a different communication primitive with different properties:

- **Bandwidth:** Text messages carry semantic content but lose the rich intermediate representations that the model computed internally. KV cache sharing preserves all attention states across all layers, giving workers access to each other's "thought process" at the representational level, not just the final surface tokens.

- **Latency:** Text-based communication requires one agent to finish generating, then another agent to encode that text through all model layers. In Hogwild! Inference, workers see each other's tokens *during the same forward pass*—"even before they are processed by all layers" (Section 3.1). This reduces the coordination latency from multiple forward passes to effectively zero.

- **Granularity:** Text messages are coarse-grained (typically complete utterances or paragraphs). Hogwild! communication is token-level—Worker B can condition on Worker A's mid-sentence, partial reasoning and adjust immediately, without waiting for Worker A to finish a thought.

**Comparison to prior communication mechanisms.** Self-Consistency (Wang et al., 2022) has zero communication during generation—agents work in isolation and only combine results at the end. Multi-Agent Debate (Du et al., 2023) adds text-based rounds, but each round requires full re-encoding of other agents' outputs. Skeleton-of-Thought (Ning et al., 2024) has workers solve sub-tasks independently with no cross-worker communication. Role-based systems (Cohen et al., 2023; Kong et al., 2024) use structured text exchanges where agents write messages to specific roles. In all cases, communication is a **separate step** that incurs encoding overhead and latency.

Hogwild! communication is **a property of the inference mechanism itself**, not a separate step. Because attention already computes dot products between queries and all past keys, adding other workers' keys to the attention computation requires no additional encoding passes—just the query rotation trick to position them correctly. The communication is free in the sense that it does not add new forward passes; it only changes which KV pairs are included in the attention computation that was already happening.

**Evidence that it matters.** The collaborativeness analysis (Figure 7) shows that models with token-level visibility score significantly higher on collaboration quality (GPT-4o judged) than models with only step-level visibility. The ablation in Figure 10 (left) confirms that the "non-instant" (step-synchronized) variant "performs poorly at smaller budgets," while instant synchronization enables faster coordination. This demonstrates that communication granularity and latency matter for coordination quality—reducing the unit of communication from full paragraphs to individual tokens enables more responsive, adaptive collaboration.

---

### Innovation 3: Diagnosis of Why Fixed Parallelism Frameworks Fail—And That Dynamic Coordination Addresses Structural, Not Incidental, Limitations

The paper provides a diagnostic analysis of *why* existing parallel reasoning methods fail on problems that do not fit their structure, and argues that this failure is **structural** rather than incidental—not fixable by more sophisticated versions of the same approach.

**The structural failure diagnosis.** Prior methods impose a fixed collaboration structure that must be correct at the outset:

- Self-Consistency assumes the best strategy is independent diverse attempts followed by voting. This fails when sub-tasks could be parallelized (wasted redundancy) or when workers could usefully cross-correct each other mid-reasoning (missed coordination).
- Skeleton-of-Thought assumes the problem decomposes into independent sub-tasks discoverable upfront. This fails when "the initial plan turns out to be wrong or incomplete" (Section 2, citing Muennighoff et al., 2025; DeepSeek-AI et al., 2025)—a common occurrence in complex reasoning.
- PASTA (Jin et al., 2025) assumes a main agent can spawn background threads for known sub-tasks. This fails when "one of the agents discovers that the original plan is flawed" but cannot re-plan, because the framework lacks a mechanism for bottom-up plan revision.

The paper's key move is to identify the **common pattern** across these failures: "by imposing a specific parallelism strategy, these methods can harm reasoning for problems that do not fit their framework" (Section 2). The problem is not that any particular framework is poorly designed, but that *any* fixed framework will encounter problems whose structure violates its assumptions. And because the framework determines what agents can see and when, agents operating within it cannot escape its limitations.

**What Hogwild! Inference does differently.** Rather than trying to design a framework that covers all cases (which leads to "yet another, more complicated parallelism framework" with each patch), Hogwild! Inference eliminates the fixed framework entirely. Workers see each other's partial reasoning and can *decide*—at each step, for each problem—what collaboration pattern to use. They can start with parallel independent exploration, notice redundancy, split into sub-tasks, discover that one sub-task is harder than expected, have one worker pivot to help, and adjust the plan continuously.

This is the difference between **designing collaboration strategies** and **designing the conditions for collaboration to emerge**. The paper provides concrete examples from LIMO generations (Appendix F) showing this dynamic adaptation:
- Workers initially explore the same product computation, then one notices the redundancy and investigates a pattern-based approach instead (Task 511).
- Workers detect redundancy through s1-style interventions and explicitly pivot ("Yes, Alice is computing a3, so I'll do something else"—Task 40).
- Workers agree on a task division upfront based on what each is better positioned to do, then execute in parallel while cross-verifying results.

**Significance as a diagnostic contribution.** This insight is valuable even if Hogwild! Inference itself proves difficult to scale or deploy. It identifies a fundamental design principle for multi-agent LLM systems: **the collaboration strategy must be endogenous to the agents, not imposed by the infrastructure**. This reframes the research problem from "what is the best collaboration protocol?" to "what infrastructure enables agents to discover and adapt their own collaboration strategies?"

---

### Innovation 4: RoPE Manipulation as a General Mechanism for KV Cache Reuse Across Inference Threads

The paper introduces a technique—rotating queries rather than keys to adjust positional embeddings—that has implications beyond Hogwild! Inference itself. While Section 3 covered the mechanism, the *innovation* is recognizing that RoPE's mathematical properties enable zero-cost KV cache rearrangement across multiple inference threads, opening a design space for shared-memory architectures in LLM inference.

**The problem class.** Any system where multiple inference threads share subsets of a KV cache with different positional arrangements faces the same challenge: the same key-value pairs appear at different absolute positions for different consumers. Without RoPE manipulation, the options are (a) re-encode tokens at their new positions (computationally prohibitive, scaling as $O(n^3)$ for $n$ threads as noted in Section 3.1), or (b) accept positional misalignment (which degrades model quality because RoPE-based models rely on position information for attention).

**The recognition.** The authors observe that because $\langle \rho(q, a), \rho(k, b) \rangle = \langle \rho(q, a-b), \rho(k, 0) \rangle$—the dot product between rotated vectors depends only on the relative rotation offset—one can store all KV blocks at a canonical position (position 0) and apply the *difference* in rotation to the query alone. This shifts the computational burden from rotating $O(\text{cache\_tokens})$ entries per step to rotating $O(\text{num\_blocks})$ query copies per step.

**Why this is non-obvious in context.** Standard RoPE usage in LLMs rotates *both* queries and keys to their absolute positions. The observation that only query rotation is needed when keys are stored at position 0 may seem straightforward in retrospect, but the practical consequence is significant: it means an entire class of KV-cache-sharing architectures becomes computationally feasible. Without this insight, Hogwild! Inference would be limited to very short contexts due to the quadratic (in workers) or cubic re-encoding overhead.

**Generality.** The paper notes that this technique can apply beyond Hogwild! Inference. The fine-tuning and re-encoding discussion in Appendix B outlines how the same approach enables recording position differences for training, restoring generation after cache eviction, or re-encoding in-context examples. The technique is not specific to multi-worker collaboration—it applies to any scenario where KV cache blocks need to be rearranged across different attention contexts.

**Connections to other inference systems.** The paper identifies conceptual overlap with Radix Attention from SGLang (Zheng et al., 2023b), where multiple hypotheses in beam search attend to overlapping but differently-arranged KV cache subsets. Hogwild! Inference's contribution is the specific RoPE-based mechanism for achieving this rearrangement without re-encoding, which is more general than the beam-search-specific optimization in Radix Attention. The paged-attention analogy (Kwon et al., 2023) further suggests integration paths with existing serving infrastructure.

**Practical impact.** This innovation is what makes the throughput results in Table 1 possible: near-linear scaling to 3.4× tokens/second for 4 workers on a single GPU, with only 40–100% attention kernel overhead. Without query rotation, the overhead would be in the $O(n^3)$ range, making multi-worker inference strictly slower than sequential generation for realistic context lengths. The technique is thus not just a performance optimization—it is what makes the entire approach computationally viable.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The primary evaluation uses the LIMO dataset (Ye et al., 2025), consisting of 817 mathematical problems that "take modern LLMs thousands of tokens to solve reliably." Unlike synthetic tasks, LIMO problems "often do not have an obvious way to agree on a collaboration strategy ahead of time"—the collaboration pattern must emerge during reasoning. Additional benchmarks include: LiveCodeBench v5 (279 code generation problems from 2024.08–2025.02, filtered to avoid QwQ training contamination), OlympiadBench (OE_TO_maths_en_COMP with 675 problems and OE_TO_physics_en_COMP with 236 problems, both requiring LaTeX formula answers), AIME'25 (30 problems from both I and II subsets), and a synthetic GSM8k×5 set (128 samples, each containing 5 non-overlapping GSM8k test questions with comma-separated answers). For all benchmarks, the same split is used across all methods—no training split is needed since all evaluation is zero-shot.

- **Base model(s).** The primary model is **QwQ-32B** (Qwen Team, 2025), a 32B-parameter reasoning model that the authors state is "representative of the capabilities of many contemporary LLMs" (Section 4). Additional evaluations cover: **Qwen3 family** at scales 1.7B, 4B, 8B, 14B, 32B, and 235B-A22B (Yang et al., 2025); **Phi-4-Reasoning-Plus** (14B; Abdin et al., 2025); **DeepSeek-R1** (DeepSeek-AI et al., 2025); and **Llama 3.3 70B Instruct** (limited evaluation). The model family sweep is designed to test whether Hogwild! Inference's collaborative behavior is specific to QwQ-32B or generalizes across architectures and scales. The Qwen3 family is particularly informative because it spans two orders of magnitude in parameter count, allowing the authors to identify where collaborative capability emerges.

- **Metrics.** The primary metric is **accuracy** (fraction of problems for which the final answer matches the ground truth). For LIMO and AIME, answers are extracted from `\boxed{...}` and compared to the reference. For OlympiadBench, the official evaluation codebase is used with LaTeX formula equivalence checking. For LiveCodeBench, Pass@1 is reported, averaged over 8 random seeds, using the standard test suite. For GSM8k×5, per-question accuracy is reported (if the model solves 4/5 questions correctly, the sample scores 0.8). All accuracy curves are plotted against **forward passes** (the number of sequential model forward passes consumed), which serves as the compute budget axis.

- **Baselines.** Five baselines are evaluated:
  1. **Baseline (no early stopping):** standard sequential generation with a single LLM instance, no answer extraction prompt—the model either produces `\boxed{...}` or stops at the budget.
  2. **Baseline:** improved sequential generation with the early-stopping prompt described in Section 3.4.6. When the budget is exhausted without an answer, the model is forced to produce a best guess within a token limit. This is the primary sequential baseline for most comparisons.
  3. **Self-Consistency** (Wang et al., 2022): multiple LLM instances write solutions independently in parallel, then the LLM views all concatenated solutions and generates a final answer using the early-stopping prompt. The paper notes this modified version "outperforms voting in our setup and works even for 2 workers."
  4. **Skeleton-of-Thought (SoT)** (Ning et al., 2024): the LLM generates a short outline of independent sub-tasks, executes them in parallel threads, and combines results. Two variants are tested: unlimited parallel threads (original setup) and 2-worker round-robin. For LIMO, where SoT cannot solve problems alone, the main model encodes all generated threads and continues reasoning with early stopping.
  5. **Upper bound:** for some plots, the performance when given unlimited budget (the model generates until it naturally produces an answer or exhausts a very large budget) is shown as a reference ceiling.

- **Generation budget / compute accounting.** The x-axis for all main evaluation plots is measured in **forward passes** (also called "generations" or "consecutive steps" in the text). One forward pass equals one full model forward computation. For sequential baselines, this equals the number of tokens generated (1 token per pass). For Hogwild! Inference with $W$ workers, one forward pass generates $W$ tokens (one per worker) and costs slightly more than one sequential forward pass due to multi-block attention overhead (quantified in Table 2), but the paper treats forward passes as the primary efficiency metric. Budgets are swept from small values (e.g., 512, 1024) to large values (typically 8,192, with some experiments extending to 16,384 for OlympiadBench). The early-stopping tokens (16 for LIMO/AIME, 64 for OlympiadBench, 1024 for LiveCodeBench) are **not counted** toward the budget "since they have an equal effect on all methods."

- **Cross-validation / statistical protocol.** Because all evaluations are zero-shot with no training or hyperparameter tuning on the test data, no cross-validation is used. For AIME'25, due to the small test set (30 problems), each model is evaluated with 10 random seeds and results are averaged. For LiveCodeBench, Pass@1 is averaged over 8 random seeds. For the collaborativeness analysis (Section 4.3), three independent GPT-4o evaluations are conducted per sample and scores are averaged to mitigate judge subjectivity.

### Main Quantitative Results

#### Sanity Check: Synthetic Parallel Tasks (GSM8k×5)

The authors first verify that Hogwild! Inference can handle trivially parallelizable tasks where the collaboration pattern is obvious. On the GSM8k×5 synthetic benchmark (128 samples, each containing 5 independent math problems), results in Figure 3 (left) show:

- **Baseline** reaches approximately 0.85 per-question accuracy at 2,000 forward passes.
- **Hogwild! 2 workers:** reaches the same ~0.85 accuracy at approximately 1,250 forward passes—a roughly 1.6× reduction in sequential steps.
- **Hogwild! 4 workers:** reaches ~0.85 at roughly 750 passes, achieving a ~2.7× speedup over baseline.
- **SoT (unlimited threads):** converges fastest, reaching ~0.85 at approximately 500 passes, which is expected since the 5 independent questions map perfectly to SoT's plan-execute model.
- **SoT (2 threads):** shows intermediate speedup, converging around 750 passes.
- **Self-Consistency:** shows modest improvement over baseline, reaching ~0.9 at 2,000 passes, which the authors attribute to having "two 'shots' at a problem."

The key takeaway: "the parallel workers under the Hogwild! Inference can indeed collaborate, i.e. our KV cache manipulations do not break down model's reasoning capabilities" (Section 4.1). Hogwild! achieves substantial speedups on trivially parallel tasks, though slightly less than the perfectly-matched SoT framework. This validates the infrastructure before testing on harder problems.

#### Main Evaluation: LIMO Dataset with QwQ-32B

The LIMO dataset represents the core test: mathematical problems requiring thousands of reasoning tokens with no obvious fixed collaboration pattern. Results in Figure 3 (middle, right):

**Two-worker comparison (Figure 3, middle).** 
- **Baseline (naive, no early stopping):** reaches approximately 0.55 accuracy at 8,000 forward passes, with slow early progress (near 0.0 at 1,000 passes since the model is still reasoning and hasn't produced answers).
- **Baseline (with early stopping):** substantially better at low budgets—approximately 0.15 at 1,000 passes, rising to ~0.55 at 8,000 passes, nearly matching the no-early-stopping baseline at high budgets. This demonstrates that the early-stopping mechanism is effective at extracting partial reasoning.
- **Self-Consistency:** modestly outperforms baseline, reaching approximately 0.45 at 2,000 passes vs. baseline's ~0.35, and ~0.62 at 8,000 passes vs. baseline's ~0.55.
- **SoT (unlimited):** performs poorly—approximately 0.05 at 1,000 passes, rising slowly to ~0.25 at 8,000. As expected, SoT cannot decompose LIMO problems into independent sub-tasks effectively.
- **Hogwild! 2 workers:** consistently outperforms all baselines. At 1,000 passes: ~0.25 vs. baseline's ~0.15. At 4,000 passes: ~0.55 vs. baseline's ~0.45. At 8,000 passes: ~0.68 vs. baseline's ~0.55. The gap widens with budget, suggesting that the benefits of collaboration compound as workers have more time to coordinate.

**Scaling number of workers (Figure 3, right).**
- **Hogwild! 1 worker:** performs similarly to baseline, confirming that "the improvements from Hogwild! Inference come from multiple workers and not as an indirect effect of our prompt" (Appendix E.1).
- **Hogwild! 2 workers:** reaches ~0.68 at 8,000 passes.
- **Hogwild! 3 workers:** reaches ~0.72 at 8,000 passes—a further improvement.
- **Hogwild! 4 workers:** reaches ~0.76 at 8,000 passes—the best performance among all configurations.
- **Hogwild! 6 workers:** interesting non-monotonic behavior: reaches ~0.65 at 2,000 passes (better than 4 workers at that budget), but plateaus at ~0.72 by 8,000 passes, underperforming 4 workers at high budgets. The authors hypothesize this is because "QwQ-32B was trained on a limited sequence length and, since 6 workers generate tokens at a quicker rate, the model eventually runs out of the designed maximum sequence length and performs unstably" (Appendix E.1), though they also note fundamental scaling limitations as a possibility.

The headline finding: Hogwild! Inference "can converge to a correct solution faster, achieving greater accuracy for the same number of consecutive steps" (Section 4.1), with the advantage growing as more workers are added (up to a point).

#### Model Family Generalization: LIMO Dataset

Figure 4 evaluates whether Hogwild! Inference works across model families and scales:

**Left panel (QwQ-32B, Phi-4-Reasoning-Plus 14B, Qwen3-8B):** All three models show Hogwild! 2 workers outperforming their respective baselines. QwQ-32B shows the largest absolute gap (baseline ~0.55 vs. Hogwild! ~0.68 at 8,000 passes). Phi-4-R+ shows a smaller but consistent gap (baseline ~0.48 vs. Hogwild! ~0.55). Qwen3-8B shows the narrowest gap (baseline ~0.35 vs. Hogwild! ~0.40). The paper's framing: "our approach generalizes to most of the models tested, with a notable exception."

**Right panel (Qwen3 family at multiple scales):** This is where a critical boundary condition emerges:
- **Qwen3-235B-A22B:** strongest performance overall (baseline ~0.78 vs. Hogwild! ~0.82 at 8,000 passes), with Hogwild! providing clear benefit.
- **Qwen3-32B:** baseline ~0.7 vs. Hogwild! ~0.72—modest but consistent gain.
- **Qwen3-14B:** baseline ~0.55 vs. Hogwild! ~0.6—similar to QwQ-32B-scale benefits.
- **Qwen3-8B:** baseline ~0.35 vs. Hogwild! ~0.4—gain still present but narrowing.
- **Qwen3-4B:** dramatic reversal—Hogwild! *underperforms* baseline (baseline ~0.22 vs. Hogwild! ~0.18 at 8,000 passes), suggesting the model "fails to adapt to the task and gets distracted."
- **Qwen3-1.7B:** Hogwild! severely underperforms (baseline ~0.12 vs. Hogwild! ~0.05)—the model cannot handle the parallel setting at all.

The authors conclude that "smaller models, 1.7B and, to a lesser extent, 4B fail to adapt to the task and get distracted from the task" (Section 4.1). This establishes a clear capability threshold: Hogwild! Inference only provides benefits above a certain model scale, below which the multi-worker setup becomes actively harmful.

#### OlympiadBench Results

Figure 5 evaluates Hogwild! 2 workers vs. baseline on OlympiadBench Math (675 problems) and Physics (236 problems) for QwQ-32B, Qwen3-14B, and Qwen3-8B:

**Math subset (Figure 5, left):**
- **QwQ-32B:** Hogwild! consistently outperforms baseline, with accuracy at 8,000 passes reaching ~0.55 vs. baseline's ~0.48. The gap is present across all budgets.
- **Qwen3-14B:** Hogwild! outperforms baseline, reaching ~0.48 vs. ~0.42 at 8,000 passes.
- **Qwen3-8B:** Hogwild! slightly outperforms baseline at most budgets, reaching ~0.38 vs. ~0.35 at 8,000 passes.

**Physics subset (Figure 5, right):**
- The results are more mixed. QwQ-32B shows a clear Hogwild! advantage up to ~4,000 passes (~0.32 vs. baseline ~0.28), but the gap narrows at higher budgets.
- Qwen3-14B shows an unusual pattern: Hogwild! initially outperforms baseline, but after roughly 4,096 tokens, "the model does not break down, but overthinks the problem, improving some answers while replacing other correct answers with mistakes" (Section 4.2). As a result, the curves cross and Hogwild! slightly underperforms at the highest budgets.
- Qwen3-8B shows a narrow Hogwild! advantage at low budgets but the curves converge by 8,000 passes.

The Physics results demonstrate that Hogwild!'s benefits are not uniform across domains—the collaborative dynamic can sometimes introduce second-guessing that harms performance, particularly for models prone to overthinking.

#### LiveCodeBench and AIME'25

Figure 6 (left) shows LiveCodeBench v5 results for code generation:

- **QwQ-32B:** Hogwild! reaches ~0.42 Pass@1 at 8,000 passes vs. baseline ~0.35—a clear improvement.
- **Qwen3-8B:** Hogwild! reaches ~0.18 vs. baseline ~0.15, a narrower but consistent gain.
- **Phi-4-R+:** Hogwild! reaches ~0.35 vs. baseline ~0.28, similar relative improvement to QwQ-32B.
- **Self-Consistency:** shows stronger performance on LiveCodeBench than on LIMO, nearly matching Hogwild! for QwQ-32B. The authors note a methodological reason: for Self-Consistency, the model is always allowed to generate up to 1024 additional "free" tokens after viewing both solutions, while for Hogwild! and Baseline, these tokens are only generated if no answer has been produced. If Hogwild! is given the same extra token allowance, "its advantage also increases" (Appendix E.2). The authors report the weaker version for consistency with their evaluation protocol.

Figure 6 (right) shows AIME'25 results for larger models:

- **Qwen3-235B-A22B:** Hogwild! reaches ~0.68 accuracy vs. baseline ~0.58 at 8,000 passes—a substantial ~10 percentage point gain on a very challenging benchmark.
- **DeepSeek-R1:** Hogwild! reaches ~0.55 vs. baseline ~0.45 at 8,000 passes—a similar ~10 point gain.
- The "Upper bound" line (unlimited budget) reaches ~0.78, indicating substantial room for further improvement.

These results demonstrate that Hogwild! Inference scales to the largest open models (235B parameters, mixture-of-experts) and to competitive math benchmarks, providing consistent gains of approximately 10 percentage points on AIME'25.

#### Throughput and Latency Measurements

Table 1 reports actual inference speed measurements for QwQ-32B-AWQ on an NVIDIA L40S GPU:

**Tokens per second (aggregate across all workers):**
- At 1,024 KV cache length: 1 worker = 20.1 tok/s, 2 workers = 36.3 tok/s (1.81×), 4 workers = 68.9 tok/s (3.43×).
- At 16,384 KV cache length: 1 worker = 18.3 tok/s, 2 workers = 34.3 tok/s (1.87×), 4 workers = 60.3 tok/s (3.30×).
- The near-linear scaling is maintained even at long contexts, though there is a slight degradation from 3.43× to 3.30× at the longest tested length.

**Latency per forward pass:**
- At 1,024 tokens: 1 worker = 49.7ms, 2 workers = 55.1ms (11% overhead), 4 workers = 58.1ms (17% overhead).
- At 16,384 tokens: 1 worker = 54.5ms, 2 workers = 58.3ms (7% overhead), 4 workers = 66.4ms (22% overhead).
- The overhead grows with sequence length and number of workers, as expected from the multi-block attention computation.

**Time to generate a fixed number of tokens (e.g., 1,024 tokens at 1,024 context):**
- 1 worker: 52.3s
- 2 workers: 29.9s (1.75× faster)
- 4 workers: 16.7s (3.13× faster)

Figure 8 (left) shows this as continuous curves with 10th/90th percentile bands, confirming that the latency overhead is consistent and the throughput scaling is near-linear for 2 workers, slightly sub-linear for 4.

Table 2 provides a detailed breakdown of the attention kernel overhead:
- At 300 KV tokens: FlashAttention takes 11µs per attention call, Hogwild! 2w takes 45µs, Hogwild! 4w takes 45µs.
- At 16,384 KV tokens: FlashAttention takes 100µs, Hogwild! 2w takes 140µs (40% overhead), Hogwild! 4w takes 203µs (103% overhead).
- The setup time (preparing data structures, computing rotation offsets) is constant with respect to sequence length: 1.9ms for 2 workers, 3.9ms for 4 workers, incurred once per forward pass (not once per attention layer).

**End-to-end accuracy vs. wall-clock time.** Figure 8 (right) shows LIMO accuracy as a function of actual generation time (in seconds) using the quantized QwQ-32B-AWQ model. Hogwild! 2 workers consistently achieves higher accuracy at any given time budget. For example, at 200 seconds, Hogwild! reaches ~0.55 accuracy vs. FlashAttention-v2 baseline's ~0.45. The gap persists across the entire time range, confirming that the throughput advantage translates directly to better accuracy within a fixed wall-clock time.

#### Collaborativeness Analysis

Section 4.3 uses GPT-4o as a judge to score collaboration quality on a scale from 1 (no collaboration) to 6 (hypothetical optimal collaboration), evaluating LIMO generations from three models (Qwen3-8B, Phi-4-R+, QwQ-32B) under three conditions (independent/no sync, step-wise sync only, and token-wise full Hogwild!). Figure 7 reports the mean scores:

- **No sync (independent generation as in Self-Consistency):** scores cluster around 1.5–2.0 for all models, confirming that without shared cache access, workers do not spontaneously collaborate even if their outputs are later concatenated.
- **Step-wise sync (restricted Hogwild! where workers only see completed steps):** scores improve to approximately 2.0–2.5. Workers begin to reference each other's completed work but cannot react to ongoing reasoning.
- **Token-wise sync (full Hogwild!):** scores reach 3.0–3.5, significantly higher than step-wise. This quantifies the value of instant visibility: models are not just reading each other's completed thoughts, but actively coordinating mid-generation.

**Model differences:** QwQ-32B achieves the highest mean score (~3.5), consistent with its strong performance on LIMO. Phi-4-R+ and Qwen3-8B achieve similar scores (~3.0–3.2). The ranking aligns with the accuracy results, though the authors caution that the correlation is moderate (r ≈ 0.34 between human and LLM judge, p ≈ 0.0005; Appendix G.4), indicating that collaboration quality as judged by GPT-4o captures only part of what makes Hogwild! effective.

### Ablation Studies and Robustness Checks

**Cache layout (Figure 10, left).** Three Hogwild! variants with QwQ-32B on LIMO are compared:
- **Hogwild! (combined, the main layout):** reaches ~0.68 at 8,000 passes.
- **Hogwild! (contiguous, no step separation):** nearly identical performance at short budgets, but falls behind at longer contexts—reaching ~0.62 at 8,000 passes. The authors attribute this to "distance-based attention dilution" as tokens from earlier workers become thousands of positions away from later workers' current tokens.
- **Hogwild! (non-instant, interleaved step-wise only):** performs poorly at small budgets, reaching only ~0.2 at 2,000 passes vs. ~0.4 for the combined layout. Catches up somewhat at higher budgets (~0.58 at 8,000 passes) but never matches the combined layout. The paper attributes this to "increased difficulty of cross-worker coordination when synchronization is delayed" (Appendix E.1).
- **Hogwild! (re-encode instead of rotate):** reaches ~0.65 at 8,000 passes, slightly below the rotation-based approach. This is notable because re-encoding is more "correct" from a pure position-encoding perspective—each token is encoded at its true absolute position for each worker's view. However, re-encoding has a downside: "if workers reused information from each other's steps, re-encoding... can break some of the internal representations" because the first re-encoded worker's tokens are encoded without access to the other worker's tokens. The rotation approach preserves the cross-worker information flow, and the small performance difference suggests the RoPE manipulation is an acceptable approximation.

**Collaboration prompt (Figure 10, left).** Removing the s1-style periodic interventions ("Wait, am I doing redundant work?") reduces accuracy at most budgets. The "No collab. prompt" variant reaches approximately 0.62 at 8,000 passes vs. 0.68 with the prompt. The gap is smaller at very low budgets but widens as coordination becomes more important. This confirms that the explicit redundancy checks contribute to coordination quality, though the authors "hypothesize that it can be made redundant if the model is trained to collaborate better" (Appendix E.1).

**Number of workers (Figure 10, right).** Using QwQ-32B on LIMO:
- **1 worker:** matches baseline performance, confirming no benefit from the Hogwild! infrastructure alone.
- **2 workers:** ~0.68 at 8,000 passes.
- **3 workers:** ~0.72 at 8,000 passes.
- **4 workers:** ~0.76 at 8,000 passes.
- **6 workers:** best at low budgets (~0.65 at 2,000 passes, outperforming 4 workers), but plateaus at ~0.72 at 8,000 passes, underperforming 4 workers. The authors hypothesize sequence length limitations, but this also suggests diminishing returns to adding workers without corresponding increases in model capacity or context length.

**Model scale and capability threshold (Figure 4, right; also detailed model evaluations in Appendix E.2, Figures 13–18).** The Qwen3 family sweep reveals a sharp capability boundary:
- Models 8B and larger: Hogwild! provides consistent, monotonic benefits.
- Qwen3-4B: Hogwild! underperforms baseline (Figure 14).
- Qwen3-1.7B: Hogwild! severely degrades performance with flat accuracy curves (Figure 13).

On LiveCodeBench, the 1.7B model's Hogwild! accuracy drops to ~0.08 vs. baseline ~0.18 at 8,000 passes. On OlympiadBench, the 1.7B model shows near-zero improvement over the entire budget range under Hogwild!. These results establish that a minimum capability level is required for Hogwild! Inference to be beneficial; below this threshold, the multi-worker context appears to confuse rather than assist the model.

**Extended thinking budgets (Tables 3 and 4).** On OlympiadBench Math with QwQ-32B, Hogwild! 2 workers continues to outperform baseline at extended budgets up to 16,384 passes: 75.26% vs. 74.81% at the maximum budget, with the gap being largest at intermediate budgets (65.89% vs. 57.0% at 4,096 passes). On Physics, Hogwild! reaches 39.03% vs. baseline 36.12% at 16,384 passes. The advantage persists but narrows at very long budgets, suggesting that given unlimited time, the baseline can eventually catch up on problems it is capable of solving, while Hogwild! accelerates convergence.

**Self-Consistency isolation.** Across all benchmarks, Self-Consistency provides a consistent but modest improvement over the single-worker baseline. On LIMO, the gap is approximately 0.05–0.07 at most budgets. On AIME, Self-Consistency reaches ~0.52 vs. baseline's ~0.45 for Qwen3-235B-A22B (Figure 18). On LiveCodeBench, Self-Consistency performs unusually well—nearly matching Hogwild! for QwQ-32B (Figure 11, top-right)—but the authors attribute part of this to the asymmetric extra-token allowance discussed earlier. The consistent finding is that Hogwild! outperforms Self-Consistency, and the margin grows with model scale and problem difficulty.

**Model-specific robustness (Appendix E.2, Figures 11–19).** Per-model detailed evaluations confirm that Hogwild! benefits are not an artifact of QwQ-32B tuning:
- Qwen3-32B (Figure 17): Hogwild! reaches ~0.68 vs. baseline ~0.6 on LIMO, ~0.55 vs. ~0.45 on OlympiadBench Math.
- Qwen3-14B (Figure 16): consistent 3–5 point improvement across all benchmarks.
- Phi-4-Reasoning-Plus (Figure 12): Hogwild! reaches ~0.65 vs. baseline ~0.55 on LIMO, ~0.5 vs. ~0.42 on LiveCodeBench.
- Llama 3.3 70B Instruct (Figure 19, left): limited evaluation on LIMO shows Hogwild! reaching ~0.55 vs. baseline ~0.48 at 4,000 passes.

The one notable underperformance: Qwen3-8B on OlympiadBench Physics shows Hogwild! converging with baseline by 8,000 passes (Figure 15, bottom-right), consistent with the overthinking observation for Qwen3-14B on the same benchmark.

### Critical Assessment

#### Does Hogwild! Inference genuinely enable collaborative reasoning, or does it simply provide a more compute-efficient way to generate diverse solutions?

The paper's central claim is that models engage in *dynamic, self-organized collaboration* when given shared cache access. The evidence supporting genuine collaboration (rather than just efficient parallel sampling) includes:

- **Qualitative examples** (Appendix F) showing workers explicitly coordinating: dividing tasks, detecting redundancy, cross-verifying results, and pivoting strategies. Task 511 shows workers converging on the same answer through complementary approaches. Task 40 shows a worker detecting redundancy and switching to a different calculation.
- **Collaborativeness scores** (Figure 7) showing that token-level visibility produces significantly higher collaboration ratings than independence, with ratings of 3.0–3.5 (indicating "regular discussion" and task coordination) vs. 1.5–2.0 for independent generation.
- **Ablation of the collaboration prompt** (Figure 10, left) showing that removing explicit redundancy checks reduces accuracy, suggesting that the coordination behavior is not purely emergent from the cache structure alone.

However, several observations temper this interpretation:

1. **The collaboration scores are moderate (3.0–3.5 out of 6).** Level 3–4 in the paper's rubric corresponds to "paying attention" or "regular discussion," not the "adaptive problem-solving" or "optimal collaboration" of levels 5–6. The paper acknowledges that no sample reached level 6. This means the observed collaboration is functional but far from optimal—workers coordinate at a basic level but still duplicate work and miss optimization opportunities.

2. **The correlation between judged collaborativeness and accuracy is not established.** The paper reports a human-LLM judge correlation of r ≈ 0.34 but does not report whether higher collaboration scores predict higher accuracy. It is possible that some collaborative behaviors captured by the judge (frequent cross-referencing, discussion) are epiphenomenal rather than causal contributors to accuracy.

3. **Self-Consistency provides a significant fraction of the gain.** On several benchmarks, Self-Consistency (which involves zero coordination during generation, only final aggregation) achieves 50–70% of Hogwild!'s improvement over baseline. This raises the question: how much of Hogwild!'s benefit comes from collaboration, and how much from simply having multiple independent attempts that are more efficiently aggregated via the shared cache?

4. **No ablation that isolates collaboration from parallelism.** The paper does not include a condition where workers share the cache but are explicitly instructed NOT to collaborate—which would measure how much of the gain comes from multi-perspective generation alone vs. active coordination. The "no collaboration prompt" ablation partially addresses this but only removes the explicit redundancy check, not the system prompt's collaboration instructions.

A more precise characterization of what the experiments demonstrate: Hogwild! Inference enables LLMs to produce multiple reasoning trajectories that can *condition on each other's partial states*, leading to both more diverse exploration (different workers try different approaches) and more efficient coordination (workers can avoid redundant work). The evidence for the latter mechanism is qualitative and correlational; the former mechanism likely accounts for a non-trivial fraction of the observed gains.

#### Does Hogwild! Inference genuinely accelerate time-to-solution, given the per-forward-pass overhead?

The paper reports both accuracy-per-forward-pass and accuracy-per-wall-clock-time. The key question is whether the per-forward-pass overhead (11–22% latency increase per pass for 2–4 workers, per Table 1) outweighs the benefit of generating multiple tokens per pass.

The wall-clock results (Figure 8, right) directly address this: Hogwild! 2 workers achieves higher accuracy at every time budget, confirming that the throughput benefit (1.8× more tokens per second) outweighs the latency overhead for the QwQ-32B model on LIMO. However, important caveats apply:

1. **Single GPU, single model size.** The throughput measurements use QwQ-32B-AWQ on an L40S. The throughput scaling factor (tokens/second for W workers ÷ tokens/second for 1 worker) depends on the ratio of attention computation to other operations (MLP layers, layer norm, etc.). For smaller models where attention is a larger fraction of total compute, the overhead would be proportionally larger. For larger models where attention is a smaller fraction, throughput scaling would approach W× more closely.

2. **The setup time is constant per forward pass.** Table 2 shows the setup overhead is 1.9ms for 2 workers, independent of sequence length. For very short generations (e.g., 300 tokens, where a forward pass takes ~50ms), this represents a ~4% overhead. For longer generations, it becomes negligible. This means Hogwild!'s throughput advantage improves with sequence length, as confirmed by the near-linear scaling at 16K tokens.

3. **No distributed inference throughput measurements.** The paper discusses how Hogwild! maps to distributed settings (Appendix B) but reports no distributed throughput numbers. For models requiring multiple GPUs (DeepSeek-R1, Qwen3-235B), the communication overhead of exchanging query rotations between GPUs could reduce the throughput scaling factor. The claim of near-linear scaling cannot be extended to multi-GPU settings without evidence.

4. **The comparison to baseline uses different numbers.** The baseline uses a standard, highly-optimized FlashAttention-v2 implementation. Hogwild! uses custom GPU kernels. If the baseline also used custom kernels, the overhead comparison might shift. This is a standard systems comparison challenge—the absolute numbers depend on implementation quality, not just algorithmic properties.

The wall-clock results are credible for the tested configuration but should not be extrapolated to all model sizes, GPU configurations, or distributed settings without further measurement.

#### How does Hogwild! Inference's efficiency compare to simply increasing the batch size for Self-Consistency?

A missing comparison: what if one runs Self-Consistency with $W$ independent workers (generating $W$ tokens per forward pass through standard batching), then aggregates results? This would achieve the same throughput gain (W tokens per forward pass) without the attention overhead or the cache manipulation complexity.

The paper partially addresses this with the Self-Consistency baseline, but the comparison is not on equal throughput footing. Self-Consistency in the paper's evaluation generates independent solutions and then aggregates—but the *forward pass efficiency* of generating W independent tokens via standard batched inference is higher than Hogwild! (no multi-block attention overhead, no setup time). If Self-Consistency were given the same *wall-clock time* budget as Hogwild!, it could generate more tokens per worker or more workers, potentially closing the gap.

The paper does not report wall-clock-matched comparisons against Self-Consistency. The accuracy-per-forward-pass metric favors Hogwild! because both methods use one forward pass to generate W tokens, but Hogwild! benefits from cross-worker attention while Self-Consistency does not. However, the accuracy-per-wall-clock-time comparison in Figure 8 (right) only compares against sequential baseline, not against batched Self-Consistency. This is a notable missing experiment.

#### Are the observed benefits robust to the specific prompting strategy, or would other prompts produce different results?

The paper uses a specific, detailed system prompt (reproduced in full in Appendix C) and periodic s1-style interventions. The ablation removes the s1 interventions but keeps the system prompt. No ablation tests:
- Whether a simpler system prompt (e.g., just naming the workers and telling them to collaborate) would produce similar results.
- Whether the specific cache layout descriptions in the prompt are necessary, or whether the model can infer the layout from the tokens it sees.
- Whether the prompt induces collaboration or merely makes the model aware that there are multiple workers.

The prompt is long and highly specific about how the cache works. It is possible that the prompt's effectiveness is model-specific—tuned to work well with QwQ-32B's instruction-following style—and would not transfer to other models without adjustment. The fact that the same prompt works across multiple model families (Qwen, Phi, DeepSeek, Llama) provides some evidence of robustness, but the varying degrees of improvement suggest model-prompt interactions are significant.

#### How stable are the results across the small test sets?

Several benchmarks have very small sample sizes:
- AIME'25: 30 problems total, with 10 random seeds for averaging. A single correct or incorrect answer shifts accuracy by ~3.3 percentage points.
- OlympiadBench Physics: 236 problems.
- GSM8k×5: 128 samples (each containing 5 questions, but accuracy is reported per-question).

The LIMO dataset is the most robust at 817 problems. The consistent pattern across datasets—Hogwild! outperforming baseline, with the gap varying by model and difficulty—suggests the finding is not an artifact of small test sets. However, the specific accuracy numbers for AIME and OlympiadBench Physics should be interpreted with appropriate uncertainty. No confidence intervals are reported for any accuracy measurements, making it difficult to assess the statistical significance of the gaps, particularly for the smaller benchmarks.

#### What boundary conditions limit Hogwild!'s applicability?

The experiments identify several important boundaries:

1. **Model capability floor (~8B parameters for Qwen3 family).** Below this, Hogwild! is actively harmful. The mechanism of failure (distraction, confusion) is qualitatively described but not deeply analyzed—do smaller models fail to understand the multi-worker prompt? Do they lack the attention capacity to track multiple reasoning threads? Do they generate inconsistent tokens that confuse other workers?

2. **Domain dependence.** OlympiadBench Physics shows weaker and sometimes negative Hogwild! effects compared to Math. The authors attribute this to overthinking, but the underlying reason is not explored—are Physics problems more sensitive to errors introduced by cross-worker attention? Do Physics reasoning chains have different collaboration patterns than Math ones?

3. **Worker count diminishing returns.** The transition from 4 to 6 workers shows performance saturation or degradation. This could be due to sequence length limits (as hypothesized) or more fundamental factors—attention dilution across too many concurrent threads, coordination overhead outweighing diversity benefits, or the model's limited ability to track more than a few parallel reasoning contexts.

4. **Budget scale.** At the highest budgets tested (8,000–16,384 forward passes), the gap between Hogwild! and baseline sometimes narrows (e.g., OlympiadBench extended budgets in Tables 3 and 4). This suggests that Hogwild!'s primary benefit is *accelerating convergence* rather than *raising the asymptotic ceiling*—if the baseline is given enough time, it can eventually reach similar accuracy on problems within its capability. Hogwild! is most valuable when there is a practical time constraint.

The paper would be strengthened by more systematic investigation of these boundaries—particularly the model capability floor, which has practical implications for which models can benefit from Hogwild! inference. The current analysis treats the 1.7B and 4B failures as an empirical observation without explaining *why* they fail, which limits the ability to predict whether a given model will benefit from Hogwild! without running the experiment.

## 6. Limitations and Trade-offs

### The Difficulty Estimation Cost Is Unaccounted for — and Exceeds the Inference Budget Itself

**The assumption or constraint.** The entire compute-optimal framework in the reference example depends on estimating prompt difficulty *before* allocating inference budget. The paper's method for doing so — generating 2,048 samples per question and averaging PRM final-answer scores — is extraordinarily expensive. The authors acknowledge this explicitly:

> "our experiments do not account for this cost largely for simplicity" (Section 3.2 of the reference paper).

**The consequence.** The reported 4× efficiency gains over best-of-N are computed *after* difficulty is known, without amortizing the cost of learning it. In a realistic deployment, 2,048 samples × average generation length could easily consume 10–100× more FLOPs than the inference budgets being studied (e.g., 16–256 generations). The headline efficiency numbers should therefore be understood as an **upper bound on achievable gain**, not a realized deployment improvement. A practitioner deploying the reference paper's method would need to either (a) pay this enormous upfront cost for every prompt, making the approach net-inefficient, or (b) develop a cheaper difficulty estimator that the paper does not provide.

**What evidence exists in the paper.** The reference paper's Section 3.2 describes the difficulty estimation procedure (2,048 samples per question, averaged PRM final-step scores) and notes it is "largely for simplicity" that the cost is unaccounted. No experiment includes difficulty estimation cost in the compute budget. The paper provides no evaluation of cheaper alternatives (e.g., using only 4–8 samples, or a lightweight classifier trained to predict difficulty from question text alone).

**Mitigation status.** The reference paper flags this as a "key avenue for future work" (Section 3.2) but provides no solution. The predicted (non-oracle) difficulty bins perform nearly as well as oracle bins (the curves "largely overlap" in Figure 4 and Figure 8), confirming that ground-truth labels are not needed — but the *computational* cost of the estimation itself (2,048 samples per prompt) remains unaddressed. No model is trained to predict difficulty from question text directly, and no adaptive scheme that amortizes difficulty estimation into the solution process is implemented.

---

### Verifier Over-Optimization Limits the Scaling Ceiling, and the Paper Mitigates Rather Than Solves It

**The assumption or constraint.** The reference paper's approach relies on a Process Reward Model (PRM) to score intermediate reasoning steps and guide search. However, the PRM is imperfect, and aggressive search can exploit its errors — finding solutions that score highly under the PRM but are actually incorrect. This is the **verifier over-optimization** problem. The reference paper documents it clearly: beam search *degrades* performance on easy problems at high budgets (Figure 3, right), and lookahead search — the most powerful optimizer tested — paradoxically performs *worst* overall (Figure 3, left) because its stronger optimization amplifies PRM errors.

**The consequence.** The compute-optimal policy mitigates over-optimization by routing easy problems away from aggressive search (using best-of-N instead), but it does *not* eliminate the underlying problem. On medium-difficulty problems where beam search is deployed, over-optimization still causes performance to plateau or decline at high budgets — the beam search curves in Figure 3 flatten well before the full budget is consumed. This means that **simply spending more inference compute will not indefinitely improve performance** — there is a hard ceiling determined by verifier quality, and the compute-optimal allocation works *within* that ceiling rather than transcending it. For a practitioner, this implies that investment in better PRMs (more training data, adversarial robustness, ensemble methods) may yield larger gains than further tuning the allocation policy.

**What evidence exists in the paper.** Figure 3 (right) shows beam search accuracy on easy problems (bin 1) *decreasing* from ~78% to ~77% as budget increases from 4 to 256 generations, while best-of-N improves from 68% to 88%. On bin 2, best-of-N maintains a clear advantage at high budgets despite beam search improving. Figure 3 (left) shows lookahead search (3 steps) underperforming all methods at the same budget. Appendix M (Figures 29, etc.) provides qualitative examples of degenerate outputs: repetitive low-information steps, overly short 1–2 step solutions that score highly under the PRM but are wrong.

**Mitigation status.** The reference paper identifies over-optimization as "the primary bottleneck preventing unbounded improvements from additional compute" (Section 8) but provides no solution beyond the allocation policy, which is a *routing* strategy rather than a verifier improvement. Future work on robust verifiers — adversarial training, ensemble methods, KL-constrained search — is suggested but not explored. The paper is transparent about this limitation; it is not hidden. But for a practitioner, the message is: the reported gains are bounded by verifier quality, and if your PRM is weaker than the one in the paper (trained with Monte Carlo rollouts on PaLM 2-S*), the over-optimization cliff may arrive earlier and at lower budgets.

---

### Hard Problems Remain Essentially Unsolved — Test-Time Compute Cannot Compensate for Fundamental Capability Gaps

**The assumption or constraint.** The reference paper's approach amplifies the base model's existing capability by searching over its output distribution. It does *not* create capability that is absent. If the base model's `pass@1` on a problem is near zero — meaning it almost never produces a correct solution even with 2,048 random samples — no amount of search or revision will help, because there are no correct solutions in the distribution to find.

**The consequence.** On the hardest problems (difficulty bin 5), the reference paper shows near-zero improvement regardless of method or budget. In Figure 3 (right), bin 5 accuracy hovers at 1–3% for all search methods and all budgets. In Figure 7 (right), bin 5 accuracy is ~2–3% irrespective of the sequential-to-parallel ratio for revisions. In the FLOPs-matched comparison (Figure 9), the bin 5 scaling curve is essentially flat near 0–5%, far below even the greedy-decoding performance of the 14× larger model. The reference paper is explicit about this:

> "Test-time compute provides essentially zero benefit regardless of budget [on the hardest problems], meaning that some capabilities can **only** be acquired through pretraining, not recovered at inference time."

For a practitioner, this means the method offers **no path forward for problems outside the base model's capability range**. If the model fundamentally lacks the knowledge or reasoning patterns needed for a problem class, Hogwild!-style collaboration (or the reference paper's search/revision methods) will not help — the only remedy is a better pretrained model.

**What evidence exists in the paper.** Difficulty bin 5 is consistently flat across all experiments in the reference paper: Figure 3 (right), Figure 7 (right), and Figure 9 all show near-zero accuracy for the hardest quintile of MATH problems regardless of compute budget. The FLOPs-matched analysis (Section 7 of the reference paper) quantifies this: on hard problems, the smaller model with compute-optimal test-time compute shows a 37–53% *disadvantage* compared to the 14× larger model, depending on the inference-to-pretraining ratio R.

**Mitigation status.** No mitigation is proposed beyond acknowledging the boundary condition. The reference paper frames this as a feature of the analysis rather than a bug — it identifies *where* test-time compute helps and where it does not, providing guidance for practitioners on when to invest in better pretraining instead. But the limitation is fundamental: Hogwild! Inference and related test-time compute methods are **amplifiers of existing capability, not creators of new capability**. A practitioner must first ensure their base model can solve the target problems at a non-trivial rate before these methods become beneficial.

---

### The Method Assumes Sufficiently Capable Base Models — Below ~8B Parameters, Hogwild! Inference Is Actively Harmful

**The assumption or constraint.** Hogwild! Inference assumes that the base LLM is capable of parsing the multi-worker prompt, tracking multiple concurrent reasoning threads in its attention, and making productive use of cross-worker information. The paper's experiments reveal a sharp capability threshold: smaller models fail to adapt to the parallel setting and perform *worse* than sequential baselines.

> "For Qwen3 model family, we observe that the smaller models, 1.7B and, to a lesser extent, 4B fail to adapt to the task and get distracted from the task." (Section 4.1)

**The consequence.** Hogwild! Inference is not a universally beneficial technique that can be applied to any LLM. Below a certain capability threshold, the multi-worker context becomes actively confusing — models fail to coordinate, produce incoherent or redundant outputs, and achieve lower accuracy than if they had simply reasoned sequentially. For practitioners working with smaller models (for latency, cost, or hardware reasons), Hogwild! not only provides no benefit but degrades performance. The threshold is not precisely characterized — ~8B parameters for the Qwen3 family, but it is unclear whether this is a general rule or specific to Qwen3's training.

**What evidence exists in the paper.** Figure 4 (right) shows the Qwen3 family sweep on LIMO: 1.7B Hogwild! accuracy is ~0.05 vs. baseline ~0.12; 4B Hogwild! underperforms baseline at most budgets. Appendix E.2 provides per-model evaluations (Figures 13–14): Qwen3-1.7B on LiveCodeBench shows Hogwild! accuracy of ~0.08 vs. baseline ~0.18 at 8,000 passes; on OlympiadBench, the 1.7B model shows near-zero improvement over the entire budget range under Hogwild!. Qwen3-8B shows a small but consistent Hogwild! benefit, suggesting the capability threshold lies somewhere between 4B and 8B for this model family.

**Mitigation status.** The paper acknowledges the failure but does not investigate its cause or propose solutions. The authors hypothesize that fine-tuning on collaborative inference data could potentially extend Hogwild!'s benefits to smaller models:

> "we hypothecize that the poor performance of 1.7B models could potentially be alleviated with finetuning in collaborative inference setup" (Appendix E.2)

But this is untested speculation. The limitation is particularly consequential for practitioners: if you are working with smaller or less capable models (e.g., for on-device deployment or cost-sensitive applications), Hogwild! Inference in its zero-shot form is contraindicated. You would need to either (a) use a larger base model, (b) fine-tune for the multi-worker setting (which the paper does not demonstrate), or (c) accept that the method does not apply to your setting.

---

### Generalization Beyond Mathematical Reasoning Is Unverified — and Physics Results Suggest Domain-Specific Failure Modes

**The assumption or constraint.** All primary evaluations in the reference paper (MATH, LIMO, AIME, OlympiadBench Math) and in the Hogwild! paper (LIMO, OlympiadBench, AIME, LiveCodeBench) use mathematical reasoning or code generation tasks with clean, verifiable answers. The Hogwild! paper additionally evaluates on LiveCodeBench and OlympiadBench Physics. These benchmarks share an important property: correctness is objectively measurable (exact answer matching, unit tests, LaTeX formula equivalence), and the reasoning process is highly structured. The paper's prompting strategies and collaboration patterns are implicitly designed for and tested on these domains.

**The consequence.** It is unknown whether Hogwild! Inference would work on tasks with fundamentally different properties: open-ended generation (creative writing, dialogue), multi-dimensional or subjective evaluation (summarization quality, argument persuasiveness), tasks requiring factual recall rather than step-by-step deduction, or domains where the "collaboration" metaphor maps poorly because there is no natural division of labor. The Physics results already hint at a concerning boundary: on OlympiadBench Physics (Figure 5, right), Qwen3-14B shows Hogwild! initially outperforming baseline but then degrading at higher budgets — the authors attribute this to "overthinks the problem, improving some answers while replacing other correct answers with mistakes." This suggests that the dynamic collaboration can *introduce errors* that a sequential model would not make, particularly when the model second-guesses correct intermediate results based on another worker's different (but also valid) approach.

**What evidence exists in the paper.** The Physics overthinking result is in Section 4.2, Figure 5 (right), and the detailed model evaluation in Figure 16 (bottom-right for Qwen3-14B Physics). The gap between Hogwild! and baseline on Physics is consistently narrower than on Math across all three tested models (QwQ-32B, Qwen3-14B, Qwen3-8B). No experiments are conducted on non-STEM domains. The paper does not discuss whether the system prompt (which describes mathematical problem-solving collaboration patterns) would need to be adapted for other domains.

**Mitigation status.** No mitigation is proposed, and the generalization question is not flagged as a limitation in the paper's Discussion section. The authors' focus on mathematical reasoning and code generation is understandable (these are the domains where reasoning-capable LLMs excel and where parallel collaboration is most naturally motivated), but the complete absence of evaluation on non-STEM tasks means a practitioner considering Hogwild! for, e.g., legal document analysis, multi-step planning, or scientific literature review has no evidence that the approach will transfer. The Physics overthinking result serves as a caution: even within STEM, domain-specific failure modes exist.

---

### The Reported Throughput Gains Are Single-GPU, Single-Model, and May Not Extrapolate to Production Settings

**The assumption or constraint.** All throughput and latency measurements (Section 4.4, Tables 1 and 2) are conducted on a single NVIDIA L40S GPU using QwQ-32B-AWQ, a quantized 32B-parameter model. The paper claims near-linear throughput scaling (~1.8× for 2 workers, ~3.4× for 4 workers) based on these measurements. However, these numbers depend critically on the ratio of attention computation to other model operations (MLP layers, layer norm, embedding lookup), the GPU architecture, and the implementation quality of the custom kernels.

**The consequence.** The throughput scaling factors should not be extrapolated to other configurations without measurement. Specifically:

- **For smaller models**, attention is a larger fraction of total compute, so the multi-block attention overhead (40% slower attention for 2 workers per Table 2) would constitute a larger fraction of total forward pass time, reducing the net throughput gain.
- **For larger models** (e.g., DeepSeek-R1 at 671B parameters, Qwen3-235B), inference requires multiple GPUs. The paper describes how Hogwild! maps to distributed settings (Appendix B) — including the need for All-to-All communication to exchange rotated queries between GPUs in sequence-parallel configurations — but provides no distributed throughput measurements. Communication overhead could substantially reduce the scaling factor.
- **For different GPU architectures**, the attention kernel overhead (measured at 40–100% for FlashDecoding-based custom kernels) may differ. A GPU with less memory bandwidth or fewer streaming multiprocessors would see proportionally higher overhead.
- **Implementation quality matters.** The baseline uses highly-optimized FlashAttention-v2; Hogwild! uses custom kernels. If the baseline implementation were improved (e.g., using a newer FlashAttention version with better occupancy), the relative overhead of Hogwild! could change.

**What evidence exists in the paper.** Tables 1 and 2 provide detailed breakdowns for one configuration (QwQ-32B-AWQ, L40S). Table 2 shows the attention kernel overhead: at 16K tokens, FlashAttention takes 100µs vs. Hogwild! 2w at 140µs (40% overhead) and Hogwild! 4w at 203µs (103% overhead). The setup time is constant (1.9ms for 2w, 3.9ms for 4w) but small relative to total forward pass time at long contexts. The paper's Appendix B describes distributed inference strategies but provides no measurements. The footnote in Appendix D.4 acknowledges that most experiments "under-utilized the GPUs and ran at lower power" due to non-optimized inference code, with GPU utilization below 20% for large models.

**Mitigation status.** The paper is transparent about the single-GPU, single-model scope of the measurements. The authors explicitly note in Appendix B that "maximizing the performance of such sequence-parallel Hogwild! inference would require custom kernels that overlap computation and communication" and identify this as future work. The Discussion section does not flag the throughput extrapolation issue as a limitation, which is a missed opportunity — a practitioner reading the headline "3.4× faster with 4 workers" might reasonably assume this holds for their setup without realizing the measurements are specific to a 32B model on a single L40S.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

Hogwild! Inference shifts the conversation about multi-LLM systems from **protocol design** to **infrastructure design**. Prior work asked: what interaction protocol should agents follow (voting, debate, role assignment, fixed task decomposition)? Hogwild! Inference asks a fundamentally different question: what infrastructure enables agents to discover their own collaboration strategies? This is not an incremental improvement on existing multi-agent frameworks — it is a reframing of the design problem itself.

The magnitude of this shift is best understood as a move from **exogenous coordination** (the system designer specifies how agents interact) to **endogenous coordination** (agents organize themselves given appropriate information-sharing channels). This parallels historical shifts in other fields: distributed optimization moved from lock-step synchronization barriers to asynchronous Hogwild! SGD, where workers read and write shared memory without coordination overhead; multi-core computing moved from explicit message-passing to shared-memory architectures where threads communicate implicitly through memory writes. Hogwild! Inference applies the same principle to LLM reasoning: replace explicit communication protocols with a shared attention cache that workers can read from and write to concurrently, and let the models — not the system designer — determine the collaboration strategy.

**What makes this genuinely novel rather than a repackaging of existing ideas.** The paper could have been "yet another multi-agent framework with a clever cache-sharing trick." It is not, because the specific mechanism — instant, token-level visibility into other workers' raw Key-Value representations, achieved through RoPE rotation rather than message-passing — creates a communication channel with fundamentally different properties than any prior multi-LLM system. In all prior frameworks, communication between agents is mediated by text: one agent generates a message, another encodes it. This incurs latency (waiting for message completion plus re-encoding through all model layers) and information loss (converting rich intermediate representations to surface tokens and back). Hogwild! communication is **direct attention-state sharing** — workers access each other's intermediate representations at the level of attention keys and values, without text encoding/decoding overhead. This is a genuinely new communication primitive for LLMs, and its properties (zero additional latency, token-level granularity, preservation of full representational richness) qualitatively differ from text-based communication.

The paper resolves a tension in the multi-agent LLM literature that has grown increasingly apparent. On one side, works like Du et al. (2023) and Wang et al. (2024a) show that multi-agent debate and role-based discussion improve reasoning — sometimes enabling weaker agents to collectively outperform stronger single agents. On the other side, works like Wang et al. (2024b) and Muennighoff et al. (2025) show that these gains can often be matched by better single-agent prompting, raising the uncomfortable possibility that multi-agent benefits are partially artifacts of weak baselines. Hogwild! Inference offers a resolution: the problem with prior multi-agent systems is not that collaboration is worthless, but that text-mediated communication is too slow, too coarse-grained, and too lossy to enable the kind of dynamic, responsive coordination that makes human collaboration effective. When communication becomes instant and information-rich (via shared KV cache), collaborative gains become robust and reproducible across models and benchmarks — Hogwild! consistently outperforms Self-Consistency (the best text-mediated parallel baseline) in the paper's experiments.

**Research directions that become more attractive.** The paper makes **shared-memory architectures for LLM inference** a first-class research direction. Prior to this work, KV cache sharing was primarily studied in the context of beam search (Radix Attention in SGLang, Zheng et al., 2023b) or prefix sharing for batched inference (Paged Attention in vLLM, Kwon et al., 2023). Hogwild! Inference demonstrates that shared attention caches can serve as a general infrastructure for dynamic multi-LLM coordination, opening a design space that includes: alternative cache topologies (beyond the paper's combined layout), selective attention (workers choosing which other workers to attend to and when), hierarchical cache structures for large worker pools, and integration with speculative decoding or parallel token generation methods.

The paper also makes **zero-shot collaborative capability** a recognized phenomenon worth studying in its own right. The finding that models like QwQ-32B and DeepSeek-R1 can coordinate out of the box — without any fine-tuning on multi-agent interaction data — suggests that collaborative reasoning is an emergent property of sufficiently capable LLMs. This opens questions about what in pretraining produces this capability (multi-perspective reasoning in training data? exposure to dialogue and debate? general in-context learning ability?) and whether it can be enhanced through training. The sharp capability threshold (models below ~8B fail to benefit; models below 4B are actively harmed) provides a natural testbed for understanding the relationship between model scale, training data composition, and emergent collaborative abilities.

**Research directions that become less attractive.** If Hogwild! Inference's dynamic, self-organized collaboration proves robust across further studies, the value of designing specialized multi-agent protocols for specific reasoning tasks decreases. Why spend effort engineering a Debate protocol or a Debugger-Examiner-Judge role system if models can spontaneously adopt those strategies (and switch between them) when given shared cache access? The paper's results suggest that the bottleneck in multi-agent LLM systems has been the communication infrastructure, not the interaction protocols — improving the former may make many specialized protocols unnecessary. Similarly, the paper's negative result for Skeleton-of-Thought on LIMO (Figure 3, middle: SoT achieves only ~0.25 accuracy at 8,000 passes vs. Hogwild!'s ~0.68) suggests that fixed task decomposition frameworks are fundamentally limited on problems that do not naturally decompose into independent sub-tasks, and that dynamic coordination is not just an alternative but a qualitatively superior approach for complex reasoning.

However, this does not mean protocol design is obsolete. The paper's s1-style interventions ("Wait, am I doing redundant work?") are essentially a lightweight protocol — a periodic meta-cognition trigger that improves coordination (Figure 10, left ablation shows removing it reduces accuracy). The space between "fully specified protocol" and "no protocol at all" may contain designs that are more efficient than the former and more reliable than the latter. The paper makes fully specified protocols less attractive as *the primary coordination mechanism* but opens a new design space for minimal interventions that guide self-organization without constraining it.

### Follow-Up Research This Work Enables

**1. Fine-tuning models specifically for shared-cache collaborative inference.** The paper demonstrates that modern reasoning LLMs can collaborate zero-shot, but the collaboration quality scores (3.0–3.5 out of 6; Figure 7) indicate substantial room for improvement — no sample reached level 5 or 6 ("adaptive problem-solving" or "optimal collaboration"). A natural follow-up is to fine-tune models on trajectories of successful Hogwild! collaboration, teaching them to coordinate more efficiently. The key experiment would compare a base model against the same model fine-tuned on Hogwild! interaction data, measuring both accuracy and collaboration quality (using the GPT-4o judge methodology from Section 4.3). The paper provides the necessary infrastructure for generating training data — one can run Hogwild! Inference on training problems, select trajectories where collaboration was effective (high final accuracy, clear task division), and fine-tune on those trajectories using the attention mask approach described in Appendix B. A strong result would show that fine-tuned models achieve level 4–5 collaboration scores and outperform zero-shot Hogwild! by a meaningful margin. A negative result — that fine-tuning does not substantially improve over zero-shot prompting — would suggest that the bottleneck is not model capability but something about the cache structure or prompting that cannot be addressed through training alone.

The paper also identifies candidate models for this experiment: Qwen3-4B and 1.7B, which fail catastrophically in the zero-shot setting (Figure 4, right). If fine-tuning on Hogwild! trajectories could make these smaller models benefit from parallel collaboration, that would demonstrate that collaborative capability is trainable rather than purely emergent, substantially expanding the applicability of the approach. The paper already provides the training infrastructure design (Appendix B: recording position differences, constructing 4D attention masks) and notes that concurrent work by Zheng et al. (2025) "explores finetuning for parallel inference in more detail."

**2. Alternative shared memory structures beyond the combined cache layout.** The paper's combined layout (token-level visibility into current steps + step-level common history) is one point in a larger design space. The Discussion (Section 5) explicitly enumerates unexplored alternatives: "allowing workers to insert new steps in any order, selectively delete (forget) steps, or solving programming and tool use tasks with a shared IDE and file-system." Each of these could be implemented as modifications to the cache block structure — insertion in arbitrary order means blocks can appear at any position in the sequence rather than only at the end; selective deletion means blocks can be masked from attention rather than always visible. A structured follow-up would implement 2–3 of these alternative structures, test them on the same LIMO/OlympiadBench/AIME benchmarks, and identify which structure best supports which type of collaboration. The paper's ablation of three simpler layouts (Figure 10, left) provides a template for this kind of comparison — one would add new layouts as additional curves on the same accuracy-vs-budget plots, with the GPT-4o collaborativeness judge as a complementary metric.

The **shared IDE** proposal is particularly interesting for LiveCodeBench: rather than workers seeing each other's reasoning text, they could share a file system where code is written and executed, with workers able to read, modify, and execute each other's code. This maps naturally to human pair programming and could test whether Hogwild!'s benefits extend beyond text-based reasoning to interactive tool use. A strong result would show that shared-file-system Hogwild! outperforms text-only Hogwild! on code generation tasks, suggesting that the shared memory abstraction should be domain-specific.

**3. Stress-testing collaboration quality at scale: measuring whether Hogwild! workers actually avoid redundant work.** The paper provides qualitative examples of workers detecting redundancy through s1-style interventions (Appendix F) but no quantitative measurement of how often workers *actually* avoid duplicate computation. A rigorous follow-up would instrument Hogwild! Inference to log: (a) when workers compute the same intermediate result, (b) when one worker's output makes another worker's current sub-task obsolete, (c) the fraction of total generated tokens that are "wasted" on redundant or obsolete work. This could be done by having a separate LLM (e.g., GPT-4o) annotate Hogwild! traces for redundancy, or by developing heuristic metrics (e.g., string similarity between workers' concurrent outputs, divergence in their reasoning paths after coordination points). The key comparison would be redundancy rate in Hogwild! vs. Self-Consistency (where redundancy is 100% by design — both workers solve the full problem independently) vs. an "oracle" bound (where a human annotator determines the minimum work needed to solve each problem). If Hogwild!'s redundancy rate is, say, 30% (meaning 30% of generated tokens duplicate work that another worker already did or is doing), that quantifies how much room remains for improvement through better coordination prompting or fine-tuning. If the rate is much higher — say, 60–70% — that would suggest the observed collaboration is superficial and the accuracy gains come primarily from parallel exploration rather than genuine work-sharing.

**4. Understanding and mitigating the overthinking failure mode exposed on Physics.** The OlympiadBench Physics results (Figure 5, right) reveal a specific failure mode: under Hogwild!, Qwen3-14B "overthinks the problem, improving some answers while replacing other correct answers with mistakes" (Section 4.2). This is a concrete, measurable phenomenon — on some fraction of problems, a worker that initially produced a correct intermediate result later discards it after seeing another worker's (different but also valid) approach. A targeted follow-up would isolate this failure: run Hogwild! on the Physics subset with instrumentation that tracks when a worker's confidence (as measured by token probabilities or internal consistency checks) changes after attending to another worker's output. The experiment would categorize revisions as "corrective" (fixing an actual error), "disruptive" (changing a correct answer to incorrect), or "neutral" (cosmetic changes that don't affect correctness). If disruptive revisions are common (>20% of answer changes), that suggests Hogwild! needs a mechanism for workers to evaluate whether cross-worker information is *relevant* to their current approach before incorporating it — perhaps by training a lightweight gating function that predicts whether attending to a particular other worker will improve or harm the current worker's output. This connects to broader questions about when collaboration helps vs. hurts in human teams (groupthink, social influence on judgment) and could yield insights applicable beyond LLMs.

**5. Scaling Hogwild! to large worker pools and long contexts: where does it break?** The paper tests 2–6 workers on a 32B model and observes diminishing returns at 6 workers (Figure 10, right). A systematic scaling study would map out the full space: vary the number of workers from 2 to perhaps 16, vary model size from 1.7B to 235B, vary context length from 2K to 32K tokens, and measure both accuracy and throughput. The paper hypothesizes that the 6-worker degradation is due to QwQ-32B's limited training context length, but alternative explanations are possible: attention dilution (workers can't effectively track too many concurrent threads), coordination overhead (more workers means more potential for conflict and confusion), or simply that the LIMO problems don't benefit from more than ~4 parallel perspectives. A well-designed scaling study would distinguish these explanations by testing on problems of varying complexity — perhaps synthetic problems where the optimal number of parallel workers is known by construction. This is the kind of "stress test" that establishes boundary conditions and prevents overclaiming about the approach's generality. The throughput measurements (Table 1: 3.4× tokens/second for 4 workers) suggest the computational scaling is near-linear up to 4 workers on a single GPU, but Table 2 shows the attention kernel overhead grows from 40% (2 workers) to 103% (4 workers) relative to FlashAttention, suggesting a super-linear overhead trend that would eventually erase throughput gains at higher worker counts.

**6. Integration with test-time compute scaling strategies — combining Hogwild! with adaptive budget allocation.** The reference paper (Snell et al., 2024) established that adaptive allocation of test-time compute based on problem difficulty yields 4× efficiency gains over uniform best-of-N. Hogwild! Inference addresses a complementary question: how to *structure* test-time compute in parallel. These two ideas are naturally composable. A follow-up would develop a system that (a) estimates problem difficulty (using a lightweight classifier, avoiding the reference paper's expensive 2,048-sample estimation), (b) allocates a test-time compute budget based on that difficulty, and (c) executes that budget via Hogwild! Inference with an adaptive number of workers. The key experiment would compare three conditions: (1) sequential best-of-N with uniform budget, (2) sequential test-time scaling with adaptive budget (replicating the reference paper), and (3) Hogwild! with adaptive budget allocation. The hypothesis is that (3) would outperform (2) because Hogwild! provides better utilization of the same parallel compute budget through cross-worker coordination, and both would outperform (1). The experiment would use the LIMO dataset (817 problems, providing enough statistical power for difficulty binning), with the 5-bin difficulty estimation approach from the reference paper but using the PRM-based predicted difficulty to avoid oracle contamination. This directly addresses whether Hogwild!'s parallelism and the reference paper's budget allocation are additive or synergistic — an important practical question for anyone building production reasoning systems.

### Practical Applications and Downstream Use Cases

**1. Batch inference for mathematical reasoning at scale (e.g., automated grading, competition problem-solving).** Consider an organization that needs to solve thousands of competition-level math problems — an educational technology company automatically grading student olympiad submissions, or an AI lab evaluating model performance on benchmark suites. Using Hogwild! Inference with 2 workers on QwQ-32B, the organization can achieve the same accuracy as sequential generation in roughly 55% of the wall-clock time (Figure 8, right: at 200 seconds Hogwild! reaches ~0.55 accuracy vs. baseline's ~0.45; extrapolating, reaching baseline's final ~0.55 accuracy takes Hogwild! ~175 seconds vs. baseline's ~350 seconds — a 2× speedup). With 4 workers, the speedup increases to approximately 3.2× (Table 1: 3.3× higher token throughput at 16K context). For a batch of 10,000 LIMO-level problems, this reduces processing time from roughly 10 GPU-days to approximately 3 GPU-days, with direct cost savings. The early-stopping mechanism (Appendix C) ensures that problems where the model is stuck don't consume the full budget, further improving throughput in practice. The key practical requirement is that the model must be at least ~8B parameters (Qwen3 family) or equivalent capability — below this threshold, Hogwild! degrades rather than improves performance (Section 4.1, Figure 4 right), so the deployment must use a sufficiently capable base model.

**2. Interactive code generation with real-time pair-programming dynamics.** For software development assistance where the LLM serves as a collaborative coding partner, Hogwild! Inference with shared file-system access (as proposed in Section 5, Future Work) could enable a qualitatively different interaction model: rather than the user prompting a single LLM and waiting for a complete response, two LLM instances could simultaneously explore different implementation approaches, with one focusing on correctness (writing tests, checking edge cases) while the other focuses on the core algorithm. The LiveCodeBench results (Figure 6, left) demonstrate that Hogwild! 2 workers achieves ~0.42 Pass@1 vs. baseline ~0.35 for QwQ-32B — a 20% relative improvement in code generation accuracy. When the user is in the loop, the "workers" could include the human as one of the collaborating instances (the paper's Discussion notes: "The KV cache rearrangement used in Hogwild! Inference could also allow humans to interact with agents asynchronously, giving clarifications and feedback during reasoning"). A developer encountering a bug could see one LLM instance proposing a fix while another simultaneously searches for the root cause in a different part of the code, with the human directing attention between them as needed. This use case requires extending Hogwild! beyond the 2–4 homogeneous workers tested in the paper to heterogeneous human-LLM teams, but the infrastructure (shared attention cache with instant visibility) is directly applicable.

**3. Accelerated self-consistency and verifier-guided inference pipelines.** The paper's Self-Consistency baseline (Section 4.2) uses independent parallel generation followed by LLM-based answer aggregation. Hogwild! Inference can replace the independent generation phase with coordinated parallel generation, achieving higher accuracy for the same compute because workers avoid redundant exploration (they divide the problem space rather than each covering it entirely). The LIMO results (Figure 3, middle) quantify this: Hogwild! 2 workers reaches ~0.68 accuracy at 8,000 passes vs. Self-Consistency's ~0.62, while using the same number of parallel workers and the same forward pass budget. For a production reasoning pipeline that currently uses Self-Consistency (e.g., an LLM-powered quantitative analysis system that runs multiple reasoning chains and aggregates results), switching to Hogwild! requires changing the inference engine but not the model weights, making it a drop-in upgrade. The throughput advantage (1.8× tokens/second for 2 workers per Table 1) means the upgrade also reduces latency — the system produces the final answer faster, not just more accurately. The caveat is the model capability threshold: this upgrade only works for base models at roughly 8B+ parameters (Qwen3 family) or equivalent reasoning capability. Below that, the upgrade would degrade performance, so the practitioner must verify their base model's suitability before switching.

**4. Research infrastructure for studying emergent multi-agent behaviors.** Beyond deployment, Hogwild! Inference provides a controlled experimental platform for studying how LLMs coordinate. Because the shared cache is the *only* communication channel, and because its properties (what information is shared, at what granularity, with what latency) are fully configurable through the cache layout (contiguous, interleaved, combined; Appendix A), researchers can systematically vary the communication conditions and measure the effect on collaboration quality. The paper demonstrates this with the three-layout ablation (Figure 10, left) and the collaborativeness analysis using GPT-4o as a judge (Figure 7). This experimental framework can be used to answer questions like: what is the minimum information bandwidth needed for effective coordination? Does token-level visibility matter more for fast-changing coordination or for error detection? How does collaboration quality scale with the diversity of model capabilities among workers (e.g., mixing QwQ-32B with Qwen3-32B in the same cache)? This use case does not require Hogwild! to outperform baselines — it uses Hogwild! as a scientific instrument for studying the conditions under which LLM coordination succeeds or fails, with implications for both AI systems design and cognitive science (understanding the information requirements for collaborative reasoning). The paper's published implementation at `https://github.com/eqimp/hogwild_llm` provides the starting point for this research program.
