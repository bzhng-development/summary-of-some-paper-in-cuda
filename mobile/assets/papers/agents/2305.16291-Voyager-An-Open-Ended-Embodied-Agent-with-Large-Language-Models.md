# Voyager: An Open-Ended Embodied Agent with Large Language Models

**ArXiv:** [2305.16291](https://arxiv.org/abs/2305.16291)

## 🎯 Pitch

This paper introduces **VOYAGER**, the first LLM-powered embodied lifelong learning agent that continuously explores, acquires diverse skills, and makes novel discoveries without human intervention in Minecraft.

---

## 1. Executive Summary

This paper introduces **VOYAGER**, the first LLM-powered embodied lifelong learning agent that continuously explores, acquires diverse skills, and makes novel discoveries without human intervention in Minecraft. VOYAGER operates through three key components—an **automatic curriculum** (a bottom-up, curiosity-driven task proposer that adapts to the agent's current state and exploration progress), an ever-growing **skill library** (a vector-indexed store of executable JavaScript programs that compound into increasingly complex behaviors), and a new **iterative prompting mechanism** (a refinement loop that incorporates environment feedback, execution errors, and self-verification for program improvement using GPT-4 via blackbox queries). Empirically, VOYAGER obtains **3.3× more unique items**, travels **2.3× longer distances**, and unlocks key tech tree milestones up to **15.3× faster** than prior state-of-the-art baselines, while also demonstrating zero-shot generalization to novel tasks in a new world by reusing its learned skill library—establishing that an agent can achieve strong in-context lifelong learning through code-generating LLMs without model parameter fine-tuning, though performance depends critically on GPT-4's code generation quality.

## 2. Context and Motivation

### The Core Problem: Building Lifelong Learning Agents for Open-Ended Worlds

The fundamental challenge this paper addresses is deceptively simple: **how do you build an embodied agent that can explore an open-ended world, progressively acquire new skills, and continue improving without human intervention?** This is not just about solving a predefined task—it's about creating an agent that behaves like a human player in a sandbox game: starting with basic abilities, learning from mistakes, compounding knowledge, and setting increasingly ambitious goals.

This problem sits at the intersection of several long-standing challenges in AI. The paper frames it around three capabilities that human Minecraft players naturally exhibit (Section 1):

1. **Context-aware task proposal**: The ability to propose appropriate tasks based on current skill level and world state—for example, learning to harvest sand and cactus before iron if the agent finds itself in a desert, rather than blindly following a fixed progression.
2. **Skill refinement and memory**: The ability to improve behaviors based on environmental feedback and commit mastered skills to memory for reuse in similar future situations—fighting zombies and fighting spiders share common patterns that should transfer.
3. **Self-driven exploration**: The drive to continually seek out new tasks and discoveries rather than waiting for external instruction.

Existing approaches fail to achieve all three simultaneously. The gap VOYAGER targets is what the paper calls **embodied lifelong learning**—the sustained, self-directed accumulation of capabilities over extended time spans in a rich 3D environment with no predefined goal.

Why Minecraft? The paper positions Minecraft as uniquely demanding (Section 1): "Minecraft does not impose a predefined end goal or a fixed storyline but rather provides a unique playground with endless possibilities." Unlike Atari games or board games where the rules, objectives, and state spaces are bounded, Minecraft presents procedural 3D terrains, a hierarchical tech tree (wood → stone → iron → diamond), and an open-ended crafting system that requires agents to gather resources, craft intermediate tools, and progressively unlock access to rarer materials. This makes it an ideal testbed for the kind of lifelong learning the paper aims to demonstrate—success requires sustained, adaptive exploration over hundreds of decision steps.

### Why This Problem Matters

The significance goes beyond Minecraft. The paper operates at the intersection of three major AI research threads:

**Practical: enabling autonomous agents in open-ended environments.** Real-world deployment—whether in robotics, virtual assistants, or scientific discovery—rarely comes with a well-defined reward function or a fixed task list. An agent that can explore, learn, and set its own goals without human scaffolding could operate in novel environments that designers cannot fully anticipate. The paper's explicit goal of "discovering as many diverse things as possible" (Section 2.1) is a proxy for this kind of open-ended competence acquisition.

**Theoretical: reconciling LLM capabilities with lifelong learning constraints.** Pre-trained LLMs like GPT-4 contain enormous world knowledge—they know Minecraft recipes, game mechanics, and strategic concepts—but they suffer from well-documented limitations that clash with the requirements of lifelong embodied learning:

- **Catastrophic forgetting** in continual learning: When neural networks learn new tasks, they tend to overwrite previously acquired knowledge. The paper positions its skill library as a mechanism to _compound_ abilities rather than replace them, with each skill stored as explicit, reusable code (Section 2.2).
- **One-shot planning failures**: LLMs often produce plausible-sounding but incorrect plans when reasoning about extended multi-step tasks, because they cannot execute and verify their own proposals. The iterative prompting mechanism directly addresses this by closing the loop with three types of feedback—environment state, execution errors, and self-verification of task completion.
- **Static knowledge without adaptation**: GPT-4's knowledge is frozen at training time. It cannot learn new game states, adjust to unexpected outcomes, or remember what worked on a previous attempt. VOYAGER's architecture encodes these capabilities through the skill library and the curriculum's tracking of completed and failed tasks.

**Emergent perspective: testing whether LLMs alone (without fine-tuning) can drive autonomous behavior.** The paper makes a deliberate architectural choice: all learning happens in-context through prompting, with no gradient updates or parameter fine-tuning (Section 1). This tests a provocative hypothesis—that sufficiently capable LLMs, when scaffolded with the right external memory and feedback loop structures, can exhibit emergent lifelong learning behaviors without any internal parameter changes. If true, this would dramatically simplify the pipeline for building embodied agents (no GPU clusters for RL training, no demonstration datasets, no hyperparameter tuning of learning rates).

### Where Prior Approaches Fall Short

The paper identifies specific limitations across multiple categories of prior work (Section 5, Related Work):

**1. Low-level control through reinforcement learning and imitation learning.** This is the dominant paradigm in Minecraft AI research. Methods like VPT (Baker et al., 2022) learn policies from YouTube videos that output keyboard-mouse commands given screen pixels, while DreamerV3 (Hafner et al., 2023) learns a world model to collect diamonds through RL. These approaches have notable weaknesses for the lifelong learning goal:

- **Systematic exploration is challenging** with primitive actions (Ecoffet et al., 2019; Huizinga and Clune, 2022). Exploring a 3D world by trial-and-error through low-level motor commands is sample-inefficient and often gets stuck in local patterns. The paper cites Kanitscheider et al. (2021), who designed a curriculum based on success rates for curated items, but notes their "objectives are limited to curated items"—not the open-ended discovery VOYAGER targets.
- **Interpretability:** Low-level policies are opaque. A neural network that moves a mouse cursor left doesn't explain _why_ it chose that action, making debugging and skill composition difficult (the paper emphasizes that programs are "temporally extended, interpretable, and compositional" in Section 1).
- **Generalization:** Policies learned on specific tasks often fail when transferred to new terrains or item combinations (Fan et al., 2021).

**2. LLM-based high-level planners that decompose fixed goals.** Recent work leverages LLMs to generate plans in Minecraft. DEPS (Wang et al., 2023) and DECKARD (Nottingham et al., 2023) decompose a high-level task like "craft a diamond pickaxe" into subgoals following Minecraft recipes. Volum et al. (2022) use few-shot prompting with Codex to generate executable policies but "require additional human interaction." The paper identifies a critical limitation in this family of approaches: **they lack full exploration flexibility.** They can execute a prescribed plan but cannot autonomously decide what to do next, adapt to unexpected environmental conditions, or set their own goals. They assume a human-provided task and a known recipe book, which breaks down in open-ended settings where the interesting tasks are not known in advance.

**3. Text-domain agents without embodiment.** Methods like ReAct (Yao et al., 2022), Reflexion (Shinn et al., 2023), and AutoGPT (Significant-gravitas, 2023) demonstrate impressive capabilities in text-based reasoning tasks, but the paper highlights three gaps when extending them to embodied settings:

- **No skill library for accumulating knowledge**: These agents reason and act but do not explicitly store and retrieve successful behaviors for future reuse. The paper positions its skill library as the missing component that enables compounding complexity over time (Section 2.2).
- **No systematic verification of task completion**: AutoGPT decomposes goals into subgoals but "lacks the self-verification for assessing task success" (Section 3.2). In an embodied setting, knowing when a task is actually complete is non-trivial—did you actually mine 5 coal or did the program just finish running? VOYAGER's self-verification module (Section 2.3) uses another GPT-4 instance as a critic to check task completion against the agent's state.
- **No exploration curriculum**: AutoGPT and ReAct execute given tasks but don't generate their own. In an open-ended world, the agent must decide _what to do next_, not just _how to do it_. The paper's automatic curriculum fills this gap.

**4. Prior curriculum learning approaches.** Curriculum learning in Minecraft has been explored (Kanitscheider et al., 2021), but with human-designed, fixed curricula that do not adapt to the agent's situation. A manual curriculum requires significant Minecraft-specific expertise and cannot adjust when, say, the agent spawns in a snow biome where wood is scarce. The paper explicitly notes that "a manually designed curriculum requires significant Minecraft-specific expertise, and does not take into account the agent's live situation" (Section 3.4). The random curriculum ablation (Section 3.4) demonstrates the opposite problem: randomly selecting tasks ignores prerequisite dependencies, proposing tasks the agent cannot possibly complete with its current resources.

**5. Code generation with execution feedback.** Prior work on execution-guided program synthesis (Chen et al., 2019; Ellis et al., 2019; Ni et al., 2023) uses execution results to improve code generation, but typically in the context of algorithmic problems or isolated function synthesis. CLAIRIFY (Skreta et al., 2023) generates code for planning chemistry experiments with a rule-based verifier. VOYAGER distinguishes itself by integrating three feedback types—environment feedback, execution errors, _and_ task-level self-verification—into a unified iterative prompting loop specifically for embodied control, where "success" is not just code execution but achieving a semantically meaningful change in the simulated world.

### How VOYAGER Positions Itself Relative to Existing Work

The paper frames its contribution not as a single algorithmic innovation but as a **system architecture** that combines existing ideas (LLM prompting, code as action space, vector databases for retrieval) in a specific configuration that enables lifelong learning for the first time. The key architectural decisions:

**Code as action space (not low-level controls):** Following Liang et al. (2022) and Volum et al. (2022), VOYAGER uses executable JavaScript programs as actions rather than discrete keyboard-mouse commands. Programs naturally represent temporally extended, compositional behaviors—a single `mineBlock(bot, "coal", 5)` call replaces hundreds of low-level look-and-move actions. The paper argues this is essential for long-horizon tasks in Minecraft (Section 1). This is not novel in itself (Code as Policies and ProgPrompt used code for robotics), but VOYAGER is the first to build a lifelong learning system around it.

**Skill library as external memory:** The paper draws on ideas from program synthesis (DreamCoder; Ellis et al., 2020) and retrieval-augmented generation but applies them to embodied skill accumulation. Each skill is stored as executable code indexed by the embedding of its natural language description in a vector database (Section 2.2). This serves several functions simultaneously: (1) preventing catastrophic forgetting by making all past skills retrievable, (2) enabling composition by allowing new skills to call older ones as subroutines, and (3) providing in-context examples for GPT-4's code generation. The paper explicitly contrasts this with Generative Agents (Park et al., 2023), which stores memories but "its agent actions are not executable" (Section 5, Related Work).

**Automatic curriculum as in-context novelty search:** Rather than training a separate RL policy or using predefined task sequences, VOYAGER uses GPT-4 itself to propose tasks based on the agent's situation. The paper frames this as "an in-context form of novelty search" (Section 1, citing Eysenbach et al., 2019 and Conti et al., 2018). This leverages GPT-4's internet-scale knowledge of Minecraft progression (what tools unlock what resources, what biomes contain what materials) while adapting to the agent's specific circumstances through the prompt's inclusion of inventory, nearby entities, and completed/failed tasks. The warm-up schedule (Appendix A.3.3) gradually introduces more context into the prompt as the agent completes more tasks, creating a natural difficulty progression.

**Iterative prompting as system-level self-improvement:** The paper synthesizes execution-guided code refinement (from the program synthesis literature) with self-reflection (from Shinn et al., 2023) and adds a task-level critic. The critical insight is that "self-verification is more comprehensive than self-reflection by both checking success and reflecting on mistakes" (Section 2.3). This loop operates within each task attempt (up to 4 rounds of code refinement) and feeds into the curriculum via the completed/failed task tracker. The paper positions this as qualitatively different from prior work where LLMs produce code once and hope it works.

**Gradient-free lifelong learning:** A deliberate constraint: VOYAGER interacts with GPT-4 via blackbox API queries. There is no fine-tuning, no reinforcement learning reward signal, no gradient backpropagation. The paper's implicit argument is that this is both sufficient and potentially preferable—it simplifies deployment (no GPU training infrastructure needed), avoids catastrophic forgetting (skills are stored externally, not in model weights), and makes the system inherently interpretable (skills are readable JavaScript functions). The paper acknowledges the cost of this choice (GPT-4 API calls are expensive and "15× more expensive than GPT-3.5" per Section 4), but frames it as a necessary tradeoff given that GPT-3.5's code generation quality is insufficient for the task.

**Reconciling conflicting intuitions:** The paper implicitly addresses a tension in the LLM-agent literature. On one hand, LLMs clearly possess remarkable Minecraft knowledge—they can describe recipes, explain game mechanics, and strategize about progression. On the other hand, naïve LLM agents (like the ReAct and Reflexion baselines in Section 3.3) fail miserably at open-ended exploration, discovering only a handful of items in 160 prompting iterations. VOYAGER's thesis is that the missing ingredients are external scaffolding for memory, verification, and self-directed goal-setting—the LLM provides the "raw intelligence," but the system architecture determines whether that intelligence translates into sustained autonomous behavior.

The paper is therefore positioned as an integration and synthesis effort: "VOYAGER serves as a starting point to develop powerful generalist agents without tuning the model parameters" (Section 6). It does not claim to solve 3D perception or motor control (Section 3.2 explicitly states this is orthogonal and can be combined with gradient-based approaches), but rather demonstrates that for the _planning and exploration_ challenge in open-ended worlds, LLMs with the right prompt-based scaffolding can exhibit emergent lifelong learning behaviors that prior approaches—both RL-based and simpler LLM-based agents—cannot match.

## 3. Technical Approach

### 3.1 Reader Orientation

VOYAGER is a software system that wraps GPT-4 in a feedback loop with a Minecraft simulation, enabling it to write, execute, and refine JavaScript code to control an in-game bot—all without any model fine-tuning. The core problem it solves is: *How can an LLM-based agent continuously explore an open-ended world, accumulate reusable skills, and set progressively harder goals without getting stuck, forgetting what it learned, or requiring human guidance?* The solution's shape is a three-component architecture where an automatic curriculum proposes "what to do next," a vector-indexed skill library stores and retrieves "how to do things I've done before," and an iterative prompting mechanism serves as the execution and debugging layer that translates high-level tasks into working code through trial, error, and self-verification.

### 3.2 Big-Picture Architecture (Diagram in Words)

The VOYAGER system has five major interacting pieces—three core components plus an environment interface and an LLM backbone:

1.  **The Environment (Minecraft via Mineflayer):** A JavaScript-controllable bot inside a Minecraft world. It exposes a set of control primitive APIs (e.g., `mineBlock(bot, name, count)`, `craftItem(bot, name, count)`, `killMob(bot, mobName, timeout)`) and provides state observations (inventory, nearby blocks, entities, biome, time, health, position) and execution feedback (chat logs, error traces). This is the embodied reality against which code is tested.

2.  **GPT-4 (the reasoning, curriculum, and code-generation engine):** Called via blackbox API queries. Three distinct prompt templates use GPT-4 for three different roles: the *curriculum agent* (deciding what task to attempt next), the *action agent* (generating the JavaScript code to accomplish a task), and the *critic agent* (verifying whether a task was successfully completed). GPT-3.5 is used for auxiliary cheap NLP tasks like self-questioning and skill description embedding, while `text-embedding-ada-002` provides embedding vectors for the skill library. All GPT-4 calls use temperature 0 except the automatic curriculum, which uses 0.1 to encourage task diversity.

3.  **Automatic Curriculum:** Takes the agent's current state (inventory, equipped items, nearby blocks and entities, biome, time, health, hunger, position, chest contents), the history of completed and failed tasks, plus additional context from a GPT-3.5 self-question-answering mechanism, and prompts GPT-4 to output a single next task phrased concisely (e.g., "Mine 5 coal ores," "Craft 1 stone pickaxe," "Kill 1 zombie"). The curriculum agent is guided by directives to "discover as many diverse things as possible" while ensuring the next task is "not too hard since I may not have the necessary resources."

4.  **Skill Library:** A persistent external memory implemented as a vector database. Each successfully verified program becomes a new skill stored as the `<key, value>` pair `(embedding(program_description), executable_code)`. When a new task arrives, the system retrieves the top-5 most relevant past skills by embedding similarity and includes them in the action prompt as in-context examples. This enables compositional skill building—new skills call previously learned skills as subroutines (e.g., a `craftIronPickaxe()` function might call `smeltIron()` and `craftStick()`) and prevents catastrophic forgetting by making all past knowledge retrievable.

5.  **Iterative Prompting Mechanism:** The execution-and-refinement loop. For a given task, the action agent generates code, which is executed in the environment. The environment returns chat-log feedback (e.g., "I cannot make sticks because I need 2 more planks") and any JavaScript execution errors (e.g., "No item named acacia_axe"). This feedback is incorporated into the next GPT-4 prompt for a refined code attempt. After each execution, the critic agent (another GPT-4 instance) checks the agent's state against the task specification and outputs a boolean success flag and an optional critique (e.g., "Find and mine an amethyst shard underground"). This loop runs up to 4 rounds per task. If the critic declares success, the verified code is added to the skill library and the curriculum generates the next task. If all 4 rounds fail, the task is marked as failed and a new task is proposed.

**Information flow:** The curriculum proposes a task → the skill library retrieves relevant past skills → the action agent generates code using task description, currently retrieved skills, environment state, and any prior feedback → the code executes in Minecraft, producing new state and feedback → the critic evaluates success → if success, code is added to the skill library; if failure, refined code is regenerated with feedback, up to 4 times → regardless of outcome, progress is recorded and the curriculum proposes the next task. This loop continues indefinitely, with the skill library growing and the curriculum advancing based on accumulated progress.

### 3.3 Roadmap for the Deep Dive

- **First: The Code-as-Action Interface and Control Primitives.** The foundation layer—what APIs the agent uses, why code rather than motor commands, and how the environment provides feedback. This establishes the "physics" within which everything else operates.

- **Second: The Automatic Curriculum.** How GPT-4 decides what task to do next, what information goes into that decision, the warm-up schedule that gradually exposes complexity, and why the curriculum must be *automatic* and *situation-aware* rather than manually designed or random.

- **Third: The Skill Library.** How skills are stored, indexed, and retrieved; the embedding mechanism; how retrieved skills serve as in-context examples for code generation; and the role of composition in enabling increasingly complex behaviors without catastrophic forgetting.

- **Fourth: The Iterative Prompting Mechanism.** The core self-improvement loop—environment feedback, execution errors, and self-verification. This is where we walk through exactly how each type of feedback is captured, formatted, and fed back into GPT-4, and why the three-feedback-type design is critical.

- **Fifth: The Self-Verification Module (Critic Agent).** A detailed look at how a separate GPT-4 instance judges task completion, provides critiques on failure, and why this is "more comprehensive than self-reflection."

- **Sixth: Integration of the Three Components.** How the curriculum, skill library, and iterative prompting mechanism interact as a coherent lifelong learning system, including the pseudocode-level algorithm.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is a **systems integration and empirical demonstration paper** whose core idea is that a large language model (specifically GPT-4), when scaffolded with external memory (a skill library), a self-directed goal-setting mechanism (an automatic curriculum), and a closed-loop code refinement process (iterative prompting with three feedback types), can exhibit emergent lifelong learning behaviors in an open-ended embodied environment without any gradient-based training or model fine-tuning. The paper does not introduce a single new algorithm but rather a **specific architectural configuration** of existing techniques that collectively enable sustained autonomous exploration, skill accumulation, and transfer.

#### The Code-as-Action Interface and Control Primitives

VOYAGER controls a Minecraft bot through **executable JavaScript code** rather than low-level motor commands, following the "code as policies" paradigm. The bot is built on Mineflayer, a JavaScript API that wraps Minecraft's protocol into programmable functions. The paper provides two layers of control primitives that GPT-4 can invoke in its generated code:

**Layer 1: High-level custom utilities implemented by the authors.** These are the primary building blocks that GPT-4 is instructed to use. Each abstracts a common Minecraft activity into a single function call with built-in exploration, pathfinding, and error handling:

| Function | Purpose | Key Behavior |
|----------|---------|-------------|
| `exploreUntil(bot, direction, maxTime=60, callback)` | Explore in a fixed direction until a condition is met | `direction` is a `Vec3` with values only in `{-1, 0, 1}`. The `callback` is evaluated each second; exploration stops when it returns non-null. Returns the callback's return value if successful, `null` if timeout. |
| `mineBlock(bot, name, count=1)` | Mine and collect a specified number of blocks | Searches within a 32-block radius, uses `bot.collectBlock.collect` for pathfinding and breaking. |
| `craftItem(bot, name, count=1)` | Craft an item using a nearby crafting table | Requires a crafting table within a 32-block radius. Uses `bot.recipesFor` to look up the recipe, then `bot.craft`. |
| `placeItem(bot, name, position)` | Place a block at a specified position | Finds a reference block adjacent to the target position, navigates to the block, equips the item, and calls `bot.placeBlock`. |
| `smeltItem(bot, itemName, fuelName, count=1)` | Smelt `itemName` using `fuelName` as fuel in a furnace | Requires a furnace within a 32-block radius. Opens the furnace, inserts fuel and input, waits 12 seconds (240 ticks) per item, extracts output. |
| `killMob(bot, mobName, timeout=300)` | Attack and kill a mob, collect dropped items | Finds the nearest entity with the specified name within a 32-block radius, attacks using `bot.pvp.attack`, navigates to the death location. |
| `getItemFromChest(bot, chestPosition, itemsToGet)` | Withdraw specified items from a chest | Navigates to the chest position, opens the container, withdraws the specified items by name and count. |
| `depositItemIntoChest(bot, chestPosition, itemsToDeposit)` | Deposit specified items into a chest | Same mechanical pattern as `getItemFromChest` but in reverse—finds items in inventory, deposits them. |
| `checkItemInsideChest(bot, chestPosition)` | Open a chest and immediately close it (to reveal contents) | Used when chest contents are unknown and need to be inspected. |

**Layer 2: Low-level Mineflayer APIs.** These provide more granular control and are available to GPT-4 when the high-level utilities are insufficient. Key API calls include:

- `await bot.pathfinder.goto(goal)` — the main navigation primitive. Goals can be:
  - `new GoalNear(x, y, z, range)` — move within `range` of a position
  - `new GoalXZ(x, z)` — navigate to a horizontal coordinate (ignoring Y, useful for long-range travel)
  - `new GoalGetToBlock(x, y, z)` — get adjacent to a specific block (for fishing, beds, farming)
  - `new GoalFollow(entity, range)` — follow a moving entity
  - `new GoalPlaceBlock(position, bot.world, {})` — position to place a block
  - `new GoalLookAtBlock(position, bot.world, {})` — position where a block face is visible
- `await bot.equip(item, destination)` — equip an item to `"hand"`, `"head"`, `"torso"`, `"legs"`, `"feet"`, or `"off-hand"`
- `await bot.consume()` — consume the held item (for food or potions)
- `await bot.fish()` — begin fishing (bot must be near water with a fishing rod equipped)
- `await bot.sleep(bedBlock)` — sleep in a bed until sunrise
- `await bot.activateBlock(block)` — right-click a block (for doors, buttons, etc.)
- `await bot.lookAt(position)` — look at a position (required before filling a bucket with water)
- `await bot.activateItem()` — right-click with held item (for buckets, etc.)
- `await bot.useOn(entity)` — right-click an entity (for shearing sheep, etc.)
- `bot.isABed(bedBlock)` — check if a block is a bed (returns boolean)
- `bot.blockAt(position)` — get the block at a position

**Why code over low-level actions:** The paper argues this choice is essential for three reasons. First, **temporal extension**: a single `mineBlock(bot, "iron_ore", 5)` call represents potentially hundreds of low-level look-move-click actions, dramatically reducing the planning horizon. Second, **compositionality**: programs can call other programs as subroutines. A skill to "craft an iron pickaxe" can internally call a previously learned "smelt iron" skill and a "craft sticks" skill. Third, **interpretability**: the generated code is readable JavaScript that a human can inspect and debug. The paper explicitly describes skills as "temporally extended, interpretable, and compositional" actions.

**Why these specific control primitives:** The primitive set is designed to cover the complete tech tree progression from wood tools through diamond tools. Each primitive handles a category of Minecraft interaction: resource gathering (`mineBlock`, `exploreUntil`), crafting (`craftItem`), placement (`placeItem`), processing (`smeltItem`), combat (`killMob`), storage (`getItemFromChest`, `depositItemIntoChest`), and navigation (`bot.pathfinder.goto` with multiple goal types). The paper also provides `bot.chat()` as a primitive, instructing GPT-4 to use it to "show the intermediate progress"—this generates the environment feedback that feeds the iterative prompting mechanism.

**Code generation constraints:** The prompt for code generation (Prompt 4 in Appendix A.4.2) includes 11 explicit rules that shape GPT-4's output:

> 1. "Write an async function taking the bot as the only argument."
> 2. "Reuse the above useful programs as much as possible."
> 3. "Your function will be reused for building more complex functions. Therefore, you should make it generic and reusable. You should not make strong assumption about the inventory."
> 4. "Functions in the 'Code from the last round' section will not be saved or executed. Do not reuse functions listed there."
> 5. "Anything defined outside a function will be ignored, define all your variables inside your functions."
> 6. "Call `bot.chat` to show the intermediate progress."
> 7. "Use `exploreUntil(bot, direction, maxDistance, callback)` when you cannot find something. You should frequently call this before mining blocks or killing mobs. You should select a direction at random every time instead of constantly using (1, 0, 1)."
> 8. "`maxDistance` should always be 32 for `bot.findBlocks` and `bot.findBlock`. Do not cheat."
> 9. "Do not write infinite loops or recursive functions."
> 10. "Do not use `bot.on` or `bot.once` to register event listeners. You definitely do not need them."
> 11. "Name your function in a meaningful way (can infer the task from the name)."

These constraints enforce a specific programming paradigm: stateless functions that check preconditions (what's in inventory), use exploration to find required resources, call existing utilities and skills as subroutines, report progress via `bot.chat()`, and produce side effects on the Minecraft world. The prohibition on event listeners (rule 10) and infinite loops (rule 9) prevents GPT-4 from generating non-terminating or event-driven code that would be difficult to debug.

**The `exploreUntil` function in detail.** This is arguably the most architecturally important primitive because it bridges the gap between GPT-4's symbolic knowledge ("iron ore exists underground") and the spatial reality of the procedurally generated world. The function signature is:

```javascript
async function exploreUntil(bot, direction, maxTime = 60, callback)
```

where `direction` is a `Vec3` specifying which way to move (e.g., `Vec3(0, -1, 0)` for downward exploration when seeking underground ores, or `Vec3(1, 0, 1)` for surface-level exploration when seeking animals), `maxTime` is the maximum exploration duration in seconds, and `callback` is a function called each second that returns `null` to continue exploring or a non-null value to stop and return that value.

The paper instructs GPT-4 to "select a direction at random every time instead of constantly using (1, 0, 1)" to encourage diverse exploration patterns. This is a direct architectural response to the exploration-exploitation challenge: rather than hardcoding search strategies, VOYAGER lets GPT-4 make context-dependent decisions about which direction to explore based on the target (downward for ores, horizontal for animals and water, upward for surface-level items).

#### The Automatic Curriculum

The automatic curriculum is the component responsible for answering "what should the agent try to do next?" Unlike prior work that uses human-designed task sequences or fixed goal lists, VOYAGER's curriculum is generated on-the-fly by GPT-4, conditioned on the agent's complete situation.

**Input to the curriculum prompt.** The prompt (Prompt 1 in Appendix A.3.4) provides GPT-4 with seven categories of information:

1. **Directives and constraints:** A system prompt setting the overarching goal:
   > "My ultimate goal is to discover as many diverse things as possible, accomplish as many diverse tasks as possible and become the best Minecraft player in the world."

   Eight specific criteria constrain task proposals:
   - Act as a mentor guiding the next task based on current learning progress
   - Be specific about resources to collect, items to craft, or mobs to kill
   - Use a concise single-phrase format ("Mine [quantity] [block]", "Craft [quantity] [item]", "Smelt [quantity] [item]", "Kill [quantity] [mob]", "Cook [quantity] [food]", "Equip [item]")
   - Tasks should not be too hard given current resources and learned skills
   - Tasks should be novel and interesting, seeking rare resources and equipment upgrades
   - Repetition is acceptable only when necessary to collect more resources for harder tasks
   - Do not propose shelter-building or staying in one place even at night
   - Avoid tasks requiring visual confirmation (placing torches, digging holes of specific dimensions, building, planting, trading)

2. **Agent's current state:**
   - Inventory: a dictionary of item counts (e.g., `{'oak_planks': 3, 'stick': 4, 'crafting_table': 1}`)
   - Equipment: currently equipped armor and weapons
   - Nearby blocks: a set of block names within a 32-block radius
   - Other blocks recently seen (for blocks no longer nearby)
   - Nearby entities: a set of entity names within a 32-block radius, sorted nearest-to-farthest
   - Chests: positions and contents (or "Unknown" if unopened)
   - Biome: current biome name (e.g., 'river', 'flower_forest', 'desert')
   - Time: one of 'sunrise', 'day', 'noon', 'sunset', 'night', 'midnight'
   - Health: numerical value (max 20)
   - Hunger: numerical value (max 20)
   - Position: 3D coordinates (x, y, z)

3. **Previously completed and failed tasks:** Two lists tracking the agent's exploration progress and capability frontier. This prevents the curriculum from re-proposing tasks the agent has already mastered or repeatedly suggesting tasks that are beyond the agent's current reach.

4. **Additional context:** A set of question-answer pairs generated by a GPT-3.5 self-questioning mechanism. GPT-3.5 is prompted to ask 5–10 questions about the agent's current situation based on biome, inventory, and progress, then answer them. For example, given an agent in a sparse jungle biome, it might ask "What are the items that I can find in the sparse jungle?" and "What are the mobs that I can find in the sparse jungle?" and answer using its pre-trained knowledge. This provides additional strategic context that may not be directly observable in the agent state.

5. **Chain-of-thought instruction:** The response format requires GPT-4 to first output "Reasoning:" with analysis of the current situation, then "Task:" with the concise task phrase.

**Warm-up schedule.** The curriculum prompt is not static—it follows a deliberate warm-up schedule (Table A.1) that gradually introduces more information as the agent completes more tasks:

| Information added | After completing how many tasks? |
|-------------------|-----------------------------------|
| Core inventory (only logs, planks, sticks, crafting table, furnace, dirt, coal, pickaxes, swords, axes), equipment, nearby blocks, position | 0 tasks (immediately) |
| Nearby entities | 5 tasks |
| Full inventory | 7 tasks |
| Other recently-seen blocks | 10 tasks |
| Biome | 10 tasks |
| Health bar | 15 tasks |
| Hunger bar | 15 tasks |
| Time | 15 tasks |
| Additional context (GPT-3.5 Q&A) | 15 tasks |

This warm-up design reflects a pedagogical philosophy: early on, the agent should focus on basic wood-and-stone tools without distraction. As it demonstrates competence (completing more tasks), it gains access to richer situational awareness, enabling more sophisticated task proposals that account for biome-specific resources (cacti in deserts, bamboo in jungles), time-sensitive dangers (zombies at night), and strategic considerations (what to do next after crafting a wooden pickaxe).

**Why an automatic curriculum versus alternatives?** The ablation study (Section 3.4, Fig. 9) compares against two baselines:

- **Manual curriculum:** A hardcoded sequence of 10 tasks: "Mine 3 wood log" → "Craft 1 crafting table" → "Craft 1 wooden pickaxe" → "Mine 11 cobblestone" → "Craft 1 stone pickaxe" → "Craft 1 furnace" → "Mine 3 iron ore" → "Smelt 3 iron ore" → "Craft 1 iron pickaxe" → "Mine 1 diamond". This requires "significant Minecraft-specific expertise" and cannot adapt to what the agent actually encounters.

- **Random curriculum:** Randomly select a task from a curated list of 101 items obtained by VOYAGER. This ignores prerequisite dependencies entirely—the agent might be asked to craft an iron pickaxe before it has ever obtained wood.

The automatic curriculum outperforms both, with the random curriculum causing a 93% drop in discovered items. The key advantage is **situational awareness**: the automatic curriculum considers what the agent currently possesses, where it is located, what it has already tried, and what Minecraft progression logically comes next. If the agent spawns in a desert beside a river (Fig. 3 example), the curriculum proposes "Catch 1 fish" because it sees the fishing rod in inventory, the river biome, and the opportunity for food. If the agent is at night with zombies nearby and has a stone sword and shield equipped, it proposes "Kill 1 zombie."

**The self-questioning mechanism for additional context.** Before the curriculum prompt is constructed (and only after 15 tasks have been completed, per the warm-up schedule), another GPT-3.5 call generates strategic context. The prompt (Prompt 2, Appendix A.3.4) instructs GPT-3.5 to ask 5–10 questions about the agent's situation, each paired with a "concept" for wiki retrieval. The questions must be self-contained (not requiring the agent's specific state), e.g., "What are the items that I can find in the sparse jungle?" rather than "What blocks can I find in my current biome?" Each question-concept pair is used to retrieve relevant documents from a Minecraft wiki knowledge base (optional; GPT-3.5's pre-trained knowledge usually suffices). A separate GPT-3.5 call (Prompt 3) answers each question, and the resulting Q&A pairs are included in the curriculum prompt as additional context. This mechanism's purpose is to surface strategic knowledge that GPT-4 might not spontaneously consider—such as what resources are unique to the current biome or what mobs are dangerous given current equipment—without requiring the expensive GPT-4 model for routine knowledge retrieval tasks.

**Temperature and diversity.** The curriculum prompt uses temperature = 0.1 (versus 0 for all other GPT-4 calls) "to encourage task diversity." This is a deliberate tradeoff: slightly higher stochasticity makes the curriculum less deterministic, which is desirable for open-ended exploration where the agent should not always follow the identical progression path on different runs.

#### The Skill Library

The skill library is the persistent external memory that distinguishes VOYAGER from prior LLM-based agents. It solves two fundamental problems simultaneously: **catastrophic forgetting** (skills are stored externally, not in model weights that get overwritten) and **compositional skill development** (new skills build on old ones by calling them as subroutines).

**Storage mechanism.** When a task is successfully completed and verified by the critic agent, the generated code is stored as a new skill. The storage process (Fig. 4, top) works as follows:

1. A GPT-3.5 agent (Prompt 5, Appendix A.4.2) is prompted with the JavaScript code and asked to write a concise natural language description of what the function does, in no more than 6 sentences, without mentioning the function name or `bot.chat` calls. For example, given a function that mines 8 cobblestone, GPT-3.5 would produce: "The function is about mining 8 cobblestones using a wooden pickaxe. First check if a wooden pickaxe is in the inventory. If not, craft one. If the wooden pickaxe is available, equip the wooden pickaxe in the hand. Next, explore the environment until finding a stone block. Once a stone block is found, mine a total of 8 cobblestone blocks using the wooden pickaxe."

2. This description is embedded using OpenAI's `text-embedding-ada-002` API, producing a high-dimensional vector.

3. The `<key, value>` pair `(embedding_vector, javascript_code)` is inserted into a vector database (the paper does not specify which vector database, but the mechanics are standard: approximate nearest neighbor search over cosine similarity).

**Retrieval mechanism.** When the agent receives a new task from the curriculum, relevant past skills are retrieved through a two-step process (Fig. 4, bottom):

1. **Query construction:** GPT-3.5 is prompted to generate "a general suggestion for solving the task," which is combined with the current environment feedback to form a query context. For a task like "Craft an iron pickaxe," GPT-3.5 might produce a suggestion like "You need 3 iron ingots and 2 sticks. Use a crafting table to combine them."

2. **Similarity search:** This query text is embedded using the same `text-embedding-ada-002` model, and the top-5 most similar skill descriptions (by cosine similarity of their embeddings) are retrieved from the vector database.

3. **In-context inclusion:** The full JavaScript code of these top-5 skills is included in the action agent's prompt (in the `{retrieved_skills}` placeholder in Prompt 4), serving as few-shot examples for GPT-4's code generation.

The paper reports retrieval accuracy in Table A.4, evaluated on 309 samples: top-1 accuracy of 80.2%, top-2 of 89.3%, top-3 of 93.2%, top-4 of 95.2%, and top-5 of 96.5%. The paper includes top-5 skills in the prompt, so the effective retrieval failure rate is approximately 3.5%—the remaining cases where none of the top 5 are relevant.

**Why top-5 and why descriptions as keys?** The top-5 threshold balances information content against prompt length. Including only the top-1 would miss useful related skills (e.g., "kill zombie" might be relevant to "kill spider" but might not be the top match). Including more than 5 would consume excessive API tokens without marginal retrieval accuracy gains (top-5 is already 96.5%). The choice of *description* rather than code as the embedding key exploits the semantic understanding of `text-embedding-ada-002`: two functions that do conceptually similar things (fighting two different mobs) will have nearby description embeddings even if their code structure differs slightly. Embedding the code directly would be more sensitive to syntactic similarity and less sensitive to semantic relatedness.

**Composition through subroutines.** The skill library enables hierarchical skill development because GPT-4, when generating code for a new task, can call previously stored skills by name. The paper provides multiple examples in Appendix A.4.3. For instance, a `craftWoodenPlanks` function calls `mineWoodLog` (a previously learned skill) as a subroutine:

```javascript
async function craftWoodenPlanks(bot) {
    const logNames = ["oak_log", "birch_log", "spruce_log", ...];
    const plankNames = ["oak_planks", "birch_planks", ...];
    const logInInventory = logNames.find(logName => 
        bot.inventory.count(mcData.itemsByName[logName].id) > 0
    );
    if (!logInInventory) {
        bot.chat("No wooden log in inventory. Mining a wooden log...");
        await mineWoodLog(bot);  // calls a previously stored skill
    }
    // ... craft planks from the log type found
}
```

Similarly, a `smeltFiveRawIronV2` function calls `craftFurnace(bot)` as a subroutine to ensure the prerequisite furnace exists before attempting smelting. This composition is the mechanism by which VOYAGER "compounds the agent's abilities rapidly"—each new skill adds a new reusable building block that all future skills can leverage.

**Why the skill library addresses lifelong learning challenges:**

- **Catastrophic forgetting:** In traditional continual learning, neural network parameters are overwritten when learning new tasks, causing performance on old tasks to degrade. The skill library stores each skill as explicit, immutable code in a database. Retrieval ensures old skills remain accessible regardless of how many new skills are added.

- **Sample efficiency:** The agent does not need to re-learn "how to mine a wood log" every time a new task requires wood. The existing skill is retrieved and either called directly or used as an in-context example.

- **Scalability:** The vector database can grow indefinitely. Unlike a fixed-size prompt or a limited context window, the skill library has no inherent capacity limit—only retrieval accuracy matters, and the paper demonstrates strong accuracy out to at least 309 stored skills.

- **Transfer and generalization:** The zero-shot generalization experiments (Section 3.3, Table 2, Fig. 8) demonstrate that the skill library is a "plug-and-play asset" (Section 3.3): giving AutoGPT access to VOYAGER's skill library enables it to solve some tasks it otherwise cannot, and VOYAGER itself solves all four novel tasks (crafting a diamond pickaxe, golden sword, lava bucket, and compass) significantly faster with the skill library than without it (e.g., 19 vs. 36 iterations for a diamond pickaxe).

#### The Iterative Prompting Mechanism

The iterative prompting mechanism is the closed-loop refinement engine that converts a high-level task description into working, verified code. It operates as a multi-round code generation process where each round incorporates feedback from the previous execution attempt, and it terminates either when the self-verification module confirms success or when 4 rounds have been exhausted.

**The action agent prompt structure.** For each round of code generation, GPT-4 receives a prompt (Prompt 4, Appendix A.4.2) containing 12 components:

1. **Guidelines for code generation:** The 11 rules described in section 3.4.1 (async function taking bot as argument, reuse primitives, be generic and reusable, etc.).

2. **Control primitive APIs:** Full documentation for all high-level custom utilities (`exploreUntil`, `mineBlock`, `craftItem`, `placeItem`, `smeltItem`, `killMob`, `getItemFromChest`, `depositItemIntoChest`, `checkItemInsideChest`) and low-level Mineflayer APIs (`bot.pathfinder.goto`, `bot.equip`, `bot.consume`, `bot.fish`, etc.). Each API is presented with its signature, a brief description of its purpose, and often an example call.

3. **Retrieved skills from the skill library:** The top-5 most relevant previously stored skills, presented as full JavaScript code with their descriptions.

4. **Code from the last round:** The exact code that was generated and executed in the previous iteration. This provides a baseline for refinement and allows GPT-4 to identify what went wrong.

5. **Environment feedback:** The chat log produced by `bot.chat()` calls during execution, showing what the bot attempted and what happened. Example from Fig. 5 (left): "I cannot make stick because I need: 2 more planks" and "I cannot make stone_shovel because I need: 2 more stick." This feedback reveals resource deficiencies and execution flow.

6. **Execution errors:** Any JavaScript errors thrown during execution, with stack traces. Example from Fig. 5 (right): "throw new Error(`No item named ${name}`); No item named acacia_axe at line 18: await craftItem(bot, 'acacia_axe', 1);" This reveals API misuse, hallucinated item names, or syntax errors.

7. **Critique from the self-verification module:** If the previous round did not succeed, the critic agent provides a specific suggestion for what to do differently. Example from Fig. 6: "Critique: Find and mine an amethyst shard underground."

8. **Agent's current state:** The same state information provided to the curriculum: inventory, equipment, nearby blocks, nearby entities, biome, time, health, hunger, position, chest contents.

9. **Task:** The concise task phrase from the curriculum.

10. **Task context:** General suggestions about how to solve the task, generated by GPT-3.5 (shared with the curriculum's question-answering mechanism), e.g., "To craft an iron pickaxe, you need 3 iron ingots and 2 sticks."

11. **Chain-of-thought instruction:** The response format requires GPT-4 to output in order: "Explain:" (analysis of why the previous code failed, if applicable), "Plan:" (step-by-step plan for completing the task, paying attention to current inventory), and "Code:" (the JavaScript function).

**The three feedback types in detail:**

**Type 1: Environment feedback (chat log).** The authors instrumented their control primitives with `bot.chat()` calls that report intermediate progress, inventory checks, and failure reasons. The prompt explicitly instructs GPT-4 to use `bot.chat()` in generated code to "show the intermediate progress." This serves as a rudimentary form of runtime introspection: when GPT-4 generates code that calls `craftItem(bot, "stick", 4)` and the environment reports "I cannot make stick because I need: 2 more planks," GPT-4 can infer that it miscalculated the plank-to-stick conversion ratio or failed to check the plank inventory before attempting to craft.

The environment feedback is not structured or machine-parsed—it's raw natural language chat messages that GPT-4 reads and interprets in the next round's prompt. This design choice exploits GPT-4's language understanding capabilities rather than requiring a formal environment feedback protocol, making the system more flexible (any `bot.chat()` message becomes interpretable feedback) but potentially less reliable (GPT-4 might misinterpret ambiguous messages).

**Type 2: Execution errors.** These are JavaScript exceptions caught by the Mineflayer runtime, with error messages and line numbers. They serve two purposes: catching syntactic errors (GPT-4 generates invalid JavaScript that can't be parsed, though this is rare with GPT-4) and catching semantic errors (referencing non-existent items, calling functions with wrong argument types, violating API preconditions). The Fig. 5 example shows GPT-4 learning from a runtime error that "acacia_axe" is not a valid item name—in the refined code, it substitutes "wooden_axe" instead.

Execution errors provide a signal that environment feedback cannot: they unambiguously indicate that the code attempted something impossible according to the game's mechanics. Environment feedback might say "I cannot make an acacia axe" but this could mean "I lack materials" or "I lack a crafting table" rather than "that item doesn't exist." The execution error `No item named acacia_axe` is definitive.

**Type 3: Self-verification and critique.** After each code execution, a separate GPT-4 call (the critic agent) evaluates whether the task was successfully completed. (Detailed in section 3.4.5 below.) The critic outputs a boolean `success` flag and, if `success` is `false`, a `critique` string suggesting corrective action. This feedback is included in the next round's action prompt, providing task-level guidance that neither environment feedback nor execution errors can supply. Environment feedback might say "I mined 3 iron ore," and execution might succeed with no errors, but if the task was "Mine 5 iron ore," only the critic can identify the shortfall.

**Why three feedback types?** The ablation study (Section 3.4, Fig. 9, right panel) quantifies their relative importance. Removing self-verification causes a 73% drop in discovered items—the largest single-component ablation impact among the three feedback types. Removing environment feedback and removing execution errors each cause smaller but still significant drops. The paper argues that the three feedback types are complementary: environment feedback reveals resource deficiencies, execution errors reveal API misuse, and self-verification provides task-level completion assessment and strategic guidance.

**Iteration limit and failure handling.** The loop runs at most 4 rounds per task. If the critic has not declared success after 4 rounds (1 initial generation + 3 refinements), the task is marked as failed and the curriculum proposes a new task. The limit prevents infinite loops on tasks that are genuinely beyond the agent's current capabilities or where GPT-4 has a persistent blind spot. The failed task is recorded and may be retried later when the agent has acquired more resources or skills—the curriculum includes "failed tasks that are too hard" in its prompt, so it can strategically defer and retry tasks.

#### The Self-Verification Module (Critic Agent)

The self-verification module is arguably the most architecturally innovative component of the iterative prompting mechanism. Rather than hardcoding success checkers for each possible task (which would be impossible given the open-ended nature of the curriculum), VOYAGER uses a separate GPT-4 instance as a critic that evaluates task completion based on the agent's state and provides actionable critique on failure.

**Input to the critic prompt.** The prompt (Prompt 6, Appendix A.5.2) provides:

1. **Agent's state after code execution:** Inventory, equipment, nearby blocks, biome, time, health, hunger, position, chest contents. Notably, "other blocks recently seen" and "nearby entities" are explicitly excluded because "they are not useful for assessing the task's completeness" (Appendix A.5.1).

2. **Task:** The concise task phrase from the curriculum.

3. **Task context:** General suggestions about how to solve the task (same GPT-3.5-generated context used in the action prompt).

4. **Few-shot examples:** The prompt includes 7 in-context examples demonstrating correct verification across different task types:

   - **Mining tasks:** Assessed by checking if the required items (or their mined equivalents) are in inventory. Example: For "Mine 3 wood logs," the critic checks for wood logs in the inventory—"You have 2 oak logs and 2 spruce logs, which add up to 4 wood logs" → success.
   
   - **Crafting tasks:** Assessed by checking if the crafted item appears in inventory or equipment. Example: For "Craft a wooden pickaxe," the critic checks inventory—"You have enough materials to craft a wooden pickaxe, but you didn't craft it" → failure, with critique "Craft a wooden pickaxe with a crafting table using 3 spruce planks and 2 sticks."
   
   - **Smelting tasks:** Assessed by checking if the smelted product appears in inventory. Example: For "Mine 5 iron_ore" (where mining iron_ore produces raw_iron), the critic checks for raw_iron count—"Mining iron_ore in Minecraft will get raw_iron. You have 5 raw_iron in your inventory" → success.
   
   - **Planting tasks:** Assessed by checking nearby blocks rather than inventory, since planted seeds are in the world, not in the inventory. Example: For "Plant 1 wheat seed," the critic checks nearby blocks for farmland with wheat—"In nearby blocks, there is farmland and wheat, which means you succeed to plant the wheat seed" → success.
   
   - **Combat tasks:** Assessed by checking for mob drops in inventory. Example: For "Kill 1 zombie," the critic checks for rotten flesh—"You have rotten flesh in your inventory, which means you successfully killed one zombie" → success.
   
   - **Eating tasks:** Assessed by checking hunger level—"For all eating task, if the player's hunger is 20.0, then the player successfully ate the food" → success.
   
   - **Storage tasks:** Assessed by checking if the inventory has been appropriately reduced. Example: For "Deposit useless items into the chest," the critic checks if inventory is still overfull and provides specific guidance: "Deposit more useless items such as copper_block, diorite, granite, cobbled_deepslate, feather, and leather."

**Response format.** The critic outputs in JSON format:

```json
{
    "reasoning": "string explaining the assessment logic",
    "success": boolean,
    "critique": "string, empty if success, otherwise suggestion for improvement"
}
```

The paper adds the instruction: "Ensure the response can be parsed by Python `json.loads`, e.g.: no trailing commas, no single quotes, etc." This reflects a practical concern—GPT-4 occasionally generates malformed JSON, and strict formatting helps reduce parsing failures.

**Why self-verification is more than self-reflection.** The paper explicitly distinguishes its self-verification from Reflexion's self-reflection (Shinn et al., 2023): "self-verification is more comprehensive than self-reflection by both checking success and reflecting on mistakes." In Reflexion, the agent reflects on its actions to improve future attempts but does not have an explicit success-checking mechanism. In VOYAGER, the critic makes a binary assessment of task completion and provides specific, actionable critique for correction. This is closer to the actor-critic architecture in reinforcement learning (the paper cites Mnih et al., 2016; Schulman et al., 2017; and Lillicrap et al., 2016), where a critic evaluates the quality of actions to guide improvement.

**How the critic handles ambiguity.** The few-shot examples reveal a pragmatic approach to verification: the critic uses heuristics and game knowledge rather than formal verification. For "Mine 5 iron_ore," it knows that mining iron_ore produces raw_iron and checks the raw_iron count. For "Kill 1 zombie," it knows that zombies drop rotten flesh. These heuristics come from GPT-4's pre-trained Minecraft knowledge and are not explicitly programmed. The downside is that sometimes "self-verification module may also fail, such as not recognizing spider string as a success signal of beating a spider" (Section 4, Limitations)—a limitation the paper acknowledges.

**Connection to the broader loop.** The critic's output serves as both a termination condition and a feedback signal. When `success` is `true`, the code is added to the skill library, the task is recorded as completed, and the curriculum generates the next task. When `success` is `false`, the `critique` string is fed into the next round's action prompt (under the "Critique" component), helping GPT-4 generate a more informed code revision.

#### Integration: The Complete VOYAGER Algorithm

The paper provides a full pseudocode for the VOYAGER algorithm (Pseudocode 1, Appendix A.1), which integrates the three components into a single lifelong learning loop. Here is the algorithm restated with explicit mechanics:

The agent initializes in the Minecraft environment. Then, in an infinite loop:

1. **Get exploration progress:** The curriculum agent compiles the lists of completed and failed tasks.

2. **Propose next task:** The curriculum agent generates a task based on the current agent state and exploration progress. This involves constructing Prompt 1 with the warm-up-scheduled state components and receiving a "Reasoning: ... Task: ..." response.

3. **Attempt task (up to 4 rounds):**
   - For each round:
     - **Retrieve relevant skills:** The skill library queries for the top-5 skills matching a GPT-3.5-generated task plan combined with environment feedback from the previous execution attempt.
     - **Generate code:** The action agent (GPT-4) receives Prompt 4 containing the task, retrieved skills, agent state, any code from the previous round, environment feedback, execution errors, and critique. It outputs "Explain: ... Plan: ... Code: ..."
     - **Execute code in environment:** The generated JavaScript function is called with the bot as argument. The environment runs the code, updating the agent state and producing environment feedback (chat log) and any execution errors.
     - **Check success:** The critic agent (GPT-4) receives Prompt 6 with the agent state and task, and returns a JSON object with `success` and `critique`.
     - If `success` is `true`, break out of the round loop.

4. **Update records:**
   - If successful: add the verified code to the skill library (embed its GPT-3.5-generated description and store it), and add the task to the completed tasks list.
   - If failed after 4 rounds: add the task to the failed tasks list.

5. **Repeat from step 1.**

The loop runs indefinitely, with the agent continuously proposing new tasks, generating code, refining it with feedback, and growing its skill library. The paper evaluates this loop over 160 prompting iterations (each iteration being one complete task attempt), measuring cumulative unique items discovered, tech tree progression, map coverage, and zero-shot transfer performance.

**Key design choices in the integration:**

- **Skill library as both memory and teaching aid:** Retrieved skills serve dual purposes. They can be called as subroutines in generated code (enabling composition) and they serve as in-context examples for GPT-4's code generation (demonstrating coding patterns and API usage). This dual role means the skill library both stores learned behaviors and teaches GPT-4 how to write new ones.

- **Stateless functions with state-checking preambles:** The code generation guidelines (rule 3: "You should not make strong assumption about the inventory ... you should always check whether you have the required items before using them") enforce a specific programming paradigm where each skill begins by checking its own preconditions—do I have a crafting table? A pickaxe? Enough raw materials?—and acquiring missing prerequisites before attempting the main task. This makes skills robust to being called in different contexts with different inventory states.

- **Separation of concerns between curriculum and action:** The curriculum agent proposes *what* to do but not *how* to do it. The action agent (with skill library support) handles the *how*. This separation means the task vocabulary can expand arbitrarily (the curriculum can propose "Craft a spyglass" without knowing the recipe), and the skill library can grow to handle new tasks without changing the curriculum architecture.

- **Graceful failure handling:** Tasks that fail after 4 rounds are recorded as failed but not permanently abandoned. The curriculum can re-propose a modified version later. This mirrors how human players approach difficult tasks in Minecraft: attempt, fail, build up resources and skills, and try again.

- **Self-verification as the meta-cognitive layer:** The critic agent serves as the system's metacognition—it observes the outcome of actions, judges success, and guides improvement. Without it, the agent has no way to know whether a task is truly complete or whether to move on to the next objective. The ablation showing a 73% performance drop when self-verification is removed quantifies its critical role.

## 4. Key Insights and Innovations

### Innovation 1: Lifelong Learning Through Externalized, Executable Skill Memory Rather Than Weight Updates

The dominant assumption in continual and lifelong learning research—from regularization-based methods (EWC) to dynamic architectures—is that an agent accumulates knowledge by modifying its internal parameters, and the central challenge is preventing those modifications from overwriting previously learned capabilities (catastrophic forgetting). VOYAGER makes a fundamentally different move: it **externalizes all learning into a vector-indexed database of executable programs**, leaving the underlying model (GPT-4) frozen.

This is not merely an engineering convenience. It represents a conceptual reframing of what "learning" means for an LLM-based agent. In VOYAGER, "learning a skill" means (1) generating working code through iterative refinement, (2) verifying it, (3) writing a natural-language description, and (4) storing the `(embedding, code)` pair for future retrieval. The model itself never changes. When a new task requires an old skill, the system retrieves it and injects it into the prompt context. This sidesteps catastrophic forgetting entirely—the skill library can grow indefinitely with no interference between stored skills—while also producing **interpretable, auditable artifacts** (readable JavaScript functions) rather than opaque weight deltas.

This is distinctive from prior LLM-based agent memory architectures. Generative Agents (Park et al., 2023) store natural-language memory traces for retrieval but those traces are not executable—they inform planning but cannot be invoked as subroutines. Reflexion (Shinn et al., 2023) maintains a self-reflective memory but does not persist verified action programs. The closest analog is DreamCoder (Ellis et al., 2020), which also builds a library of programs through wake-sleep Bayesian learning—but DreamCoder requires gradient-based training of a neural synthesizer, while VOYAGER achieves program library growth through purely in-context learning with a frozen LLM. The skill library is thus a **gradient-free, interpretable, composable form of persistent learning** for LLM agents, a concept that is likely to influence how the field thinks about agent memory.

The evidence for its significance is multi-layered. The ablation (Fig. 9, left) shows that removing the skill library causes performance to plateau in later stages—the agent cannot compound capabilities. The zero-shot generalization experiments (Table 2) demonstrate that the skill library functions as a genuine "plug-and-play asset": giving it to AutoGPT (which lacks its own memory mechanism) enables AutoGPT to solve tasks it otherwise cannot, and VOYAGER itself solves novel tasks 1.5–2× faster with the library than without it. Perhaps most telling: the skill library enables **compositional skill building**, where a `craftIronPickaxe()` function internally calls `smeltIron()` and `craftStick()` as subroutines (Appendix A.4.3 examples). This is a form of hierarchical reinforcement learning achieved without any hierarchical RL training—the compositional structure emerges from GPT-4's code generation and the retrieval mechanism's ability to surface relevant sub-skills.

This is a **fundamental shift** rather than an incremental refinement. Prior LLM agents either had no memory (ReAct, AutoGPT), used unstructured textual memory that couldn't be composed (Generative Agents), or relied on gradient updates that risk forgetting (VPT, DreamerV3). VOYAGER's externalized, executable skill library is a qualitatively new category.

---

### Innovation 2: The Automatic Curriculum as In-Context Novelty Search—Situated Goal Generation Without Training

The field of curriculum learning has historically operated on a spectrum between two poles: **manually designed curricula** (human experts specify a task sequence based on domain knowledge, as in Kanitscheider et al., 2021) and **learned curricula** (a separate model or algorithm—often RL-based—learns to propose tasks that maximize some combination of learning progress and diversity, as in POET (Wang et al., 2019) or goal-GANs). VOYAGER introduces a third category: **in-context curriculum generation using a frozen LLM's pre-trained world knowledge**, conditioned on the agent's current situation and exploration history.

This is not simply "using GPT-4 to list tasks." What makes it intellectually distinctive is that it demonstrates that a frozen LLM, when provided with rich situational context (inventory, biome, nearby entities, completed/failed task history) and the right directive framing ("discover as many diverse things as possible"), can serve as an **effective novelty search mechanism without any training, reward function, or explicit diversity metric**. The curriculum agent reasons about what would be *novel* and *achievable* given the current state, leveraging GPT-4's pre-trained understanding of Minecraft progression (wood → stone → iron → diamond), biome-specific resources, and prerequisite relationships—knowledge that would otherwise need to be either hand-coded as a task graph or learned through thousands of exploratory episodes.

This is a reframing of what counts as a "curriculum." Prior work treated curriculum generation as an optimization problem requiring explicit objectives (learning progress, success rate, diversity). VOYAGER shows that for sufficiently rich domains where an LLM has strong pre-trained knowledge, the curriculum can be generated through *prompting* rather than *optimization*, achieving adaptive, situation-aware goal selection with no task-specific training.

The evidence is stark. The manual curriculum ablation (a hardcoded 10-task sequence requiring Minecraft expertise) and the random curriculum ablation (sampling from a list of 101 items) both dramatically underperform the automatic curriculum—the random curriculum causes a 93% drop in unique items discovered (Fig. 9, left). Automatic curriculum is the single most important architectural component in the ablation study. Moreover, the curriculum's situational awareness is qualitatively impressive: Fig. 3 shows it proposing "Catch 1 fish" when the agent has a fishing rod and is near a river, "Kill 1 pig" when hunger is 0 and pigs are nearby, and "Smelt 4 raw iron" when raw iron and coal are in inventory alongside a furnace. These are not generic progression steps—they are context-specific, opportunistic, and human-like in their responsiveness to the current state.

The warm-up schedule (Table A.1) adds an additional layer of sophistication: by gradually exposing more state information (nearby entities at 5 tasks, full inventory at 7, biome at 10, health/hunger/time at 15), the curriculum creates a natural difficulty progression from basic resource gathering to sophisticated, context-aware planning. This is curriculum design achieved through *information management* rather than reward shaping.

This innovation is **fundamental**—it establishes a new paradigm for open-ended agent goal-setting. The paper explicitly frames it as "an in-context form of novelty search" (Section 1), connecting it to the quality-diversity literature (Eysenbach et al., 2019; Conti et al., 2018) while showing that the mechanism can be implemented through LLM prompting rather than evolutionary algorithms or RL.

### Innovation 3: The Three-Feedback Iterative Prompting Loop as a Unified Self-Improvement Mechanism for Embodied Code Generation

Prior work on improving LLM-generated code through execution feedback has largely operated in isolated feedback regimes. Execution-guided program synthesis (Chen et al., 2019; Ellis et al., 2019) uses execution results—intermediate program states, output values, or assertion violations—to guide search. Self-reflection approaches (Shinn et al., 2023; Madaan et al., 2023) use LLMs to critique their own outputs. CLAIRIFY (Skreta et al., 2023) uses a rule-based verifier for chemistry experiments. VOYAGER's contribution is not any single feedback type but the **integration of three qualitatively different feedback channels into a unified refinement loop**, and the empirical demonstration that each channel plays a complementary, non-redundant role.

The three channels are:

- **Environment feedback** (chat logs): Reveals *resource deficiencies and execution flow*—"I cannot make stick because I need: 2 more planks." This is feedback about the *world state* relative to the code's assumptions.
- **Execution errors** (JavaScript exceptions): Reveals *API misuse and hallucinated entities*—"No item named acacia_axe." This is feedback about the *code's correctness* relative to the environment's API.
- **Self-verification and critique** (a separate GPT-4 critic): Reveals *task completion status and strategic guidance*—"You have 3 copper ingots but no amethyst shards. Find and mine an amethyst shard underground." This is feedback about the *task-level semantics*—whether the right thing happened, not just whether the code ran.

The intellectual contribution is the recognition that these three feedback types are **not substitutable**. Environment feedback tells you *what went wrong in the world*, execution errors tell you *where the code is invalid*, and self-verification tells you *whether the goal was achieved and what to try next*. An agent receiving only environment feedback might see success messages for individual actions without realizing the overall task is incomplete. An agent receiving only execution errors might fix syntax issues without understanding the strategic error. The ablation study (Fig. 9, right) quantifies this complementarity: removing self-verification causes a 73% drop in unique items, the largest single-component impact, but removing environment feedback or execution errors also causes significant performance degradation. No single feedback type is sufficient.

This is more than an engineering integration. It is a diagnostic framework for understanding what makes embodied code generation hard: the problem requires feedback at the **execution level** (does it run?), the **world level** (did the intended effects happen?), and the **task level** (was the goal achieved?). Prior systems addressed at most one or two of these levels. VOYAGER's three-feedback loop is a principled architecture for closing all three loops simultaneously, and the paper's ablation results serve as an empirical argument that all three are necessary for sustained autonomous behavior.

The self-verification module in particular represents a conceptual upgrade over self-reflection (Shinn et al., 2023). Reflexion's self-reflection produces *general insights* for future attempts; VOYAGER's self-verification produces a *binary success judgment* plus an *actionable critique*. The paper explicitly notes this difference (Section 2.3): "self-verification is more comprehensive than self-reflection by both checking success and reflecting on mistakes." The few-shot examples in Prompt 6 (Appendix A.5.2) show the critic handling diverse task types—mining, crafting, smelting, planting, combat, eating, storage—each with different success criteria (item count in inventory, hunger level, nearby blocks for planted crops, mob drops). This task-type awareness comes from GPT-4's pre-trained knowledge, not from programmed rules, making the critic adaptable to novel tasks the curriculum might propose.

This innovation is **incremental in its components but fundamental in its synthesis**. Each feedback type has precedents, but their integration into a cohesive loop—and the empirical demonstration that all three are necessary—changes how embodied LLM agent architectures should be designed.

### Innovation 4: Code as the Universal Medium for Skill Representation, Composition, and Transfer in Embodied Agents

Using code as an action space for LLM-based agents is not new—Code as Policies (Liang et al., 2022) and ProgPrompt (Singh et al., 2022) pioneered this for robotics, and Volum et al. (2022) applied it to Minecraft. VOYAGER's contribution is in demonstrating that code serves as a **universal medium that simultaneously enables temporal abstraction, hierarchical composition, long-term memory, and zero-shot transfer**—and that this convergence of properties makes it uniquely suited for lifelong embodied learning in a way that no alternative action representation achieves.

Consider the alternatives. Low-level motor commands (keyboard-mouse, joint torques) are temporally myopic—a single action achieves almost nothing, requiring long sequences for meaningful behaviors—and they compose poorly (how do you reuse a "walk forward while looking down" subroutine in a different task?). Natural language plans (as in ReAct or DEPS) are expressive and can be reasoned about, but they are not directly executable—they must be translated into actions, and the translation is itself a source of error. Neural network policies (as in VPT or DreamerV3) are executable, but they are opaque (you cannot inspect why a policy chose an action), they compose only through additional architectural mechanisms (hierarchical RL), and they suffer from catastrophic forgetting when trained on new tasks.

VOYAGER's code-as-action-space unifies these desiderata:

- **Temporal extension:** A single `mineBlock(bot, "iron_ore", 5)` call replaces potentially hundreds of low-level actions. The abstraction boundaries are meaningful—they correspond to Minecraft's own mechanics (mine, craft, smelt, kill).
- **Composition through subroutines:** Because skills are JavaScript functions, new skills can call old ones by name. The `craftWoodenPlanks` function calls `mineWoodLog`; the `smeltFiveRawIronV2` function calls `craftFurnace`. This is hierarchical RL achieved through ordinary function calls, with no hierarchical architecture or training.
- **Persistent, retrieval-indexed memory:** Each skill is stored with its description embedding, making it retrievable by semantic similarity. This is a form of episodic memory (what worked in the past for similar tasks) implemented through standard vector database operations.
- **Zero-shot transfer through code reuse:** In the generalization experiments (Table 2, Fig. 8), VOYAGER solves unseen tasks in a new world by retrieving and reusing skills learned in the original world. The skill library is a transferable asset—giving it to AutoGPT enables that agent to solve tasks it otherwise cannot.
- **Interpretability:** The generated code is readable JavaScript. A human can inspect any skill and understand what the agent learned to do.

The intellectual contribution is the **demonstration of convergence**: these properties are not independently engineered (one system for memory, another for composition, another for transfer) but emerge from a single representational choice—representing skills as executable code. This is a conceptual simplification with practical consequences. It means that improving code generation quality (by switching from GPT-3.5 to GPT-4, as the ablation in Fig. 9 shows yields 5.7× improvement) simultaneously improves all these properties.

The paper provides concrete evidence for each claim. Composition is visible in the skill library examples (Appendix A.4.3) where `mineWoodLog`, `craftFurnace`, and other subroutines are called within higher-level functions. Transfer is demonstrated in Table 2: VOYAGER with its skill library solves diamond pickaxe crafting in 19 iterations vs. 36 without—a 1.9× speedup from compositional reuse. Interpretability is inherent in the code output format. Temporal extension is the entire premise—the agent operates at the level of "craft an iron pickaxe" rather than "move cursor to inventory slot 5."

This innovation is **incremental in its individual elements (code as action existed) but fundamental in its synthesis and empirical demonstration**. Prior work used code for single-task planning; VOYAGER shows that the same code representation, when embedded in a lifelong learning loop, unifies memory, composition, and generalization into a single coherent mechanism.

## 5. Experimental Analysis

### Evaluation Methodology

**Dataset and Environment.** All experiments use the **Minecraft** environment built on top of MineDojo (Fan et al., 2022) with the Mineflayer JavaScript API for motor controls. Unlike evaluation on a fixed benchmark dataset, VOYAGER's performance is assessed through open-ended interaction in procedurally generated Minecraft worlds—the agent spawns in a randomly initialized world and explores freely for up to **160 prompting iterations** (one iteration = one complete task attempt, including up to 4 rounds of code refinement). The Minecraft environment provides a **tech tree** progression (wooden tools → stone tools → iron tools → diamond tools) and an unbounded set of craftable items, offering a natural difficulty hierarchy without a predefined endpoint.

**Base Model(s).** VOYAGER uses **GPT-4** (`gpt-4-0314`) as its primary reasoning, code generation, and verification engine through blackbox API queries, with **GPT-3.5** (`gpt-3.5-turbo-0301`) for auxiliary NLP tasks (self-questioning for curriculum context, skill description generation) and **`text-embedding-ada-002`** for embedding skill descriptions. All GPT-4 calls use temperature 0 except the automatic curriculum, which uses temperature 0.1 to encourage task diversity. The paper also reports an ablation replacing GPT-4 with GPT-3.5 for code generation (`VOYAGER w/ GPT-3.5`), and a robustness check with `gpt-4-0613` in Appendix B.4.5. No model fine-tuning or parameter access is used—all learning occurs through in-context prompting and external memory, constraining the system design space to what can be achieved with frozen LLM queries.

**Metrics.** The paper evaluates along four axes:

- **Unique items discovered:** The cumulative count of distinct items collected by the agent over prompting iterations. This is the primary exploration metric, reflecting the agent's ability to continuously discover new resources, craft new items, and diversify its inventory. Items are tracked by name (e.g., 'iron_ingot', 'diamond', 'cooked_beef'). Full item lists for all trials are provided in Appendix B.4.1.

- **Tech tree mastery:** The number of prompting iterations required to reach each tech tree level (Wooden Tool, Stone Tool, Iron Tool, Diamond Tool). Each level represents crafting a pickaxe of the corresponding material, which requires systematic progression through resource gathering, smelting, and crafting. Faster progression (fewer iterations) indicates more efficient exploration and skill composition. The metric is reported as the average ± standard deviation over three independent trials, with `N/A (0/3)` indicating the method failed to reach that level in any trial within 160 prompting iterations.

- **Map coverage:** The traversed distance approximated by the smallest circle enclosing the agent's trajectory across three trials, visualized as bird's-eye views of the Minecraft map. Longer traversal indicates more extensive spatial exploration and access to diverse terrains (biomes). The paper reports VOYAGER's coverage as 2.3× longer than baselines.

- **Zero-shot generalization:** The number of prompting iterations required to solve four unseen tasks in a newly instantiated world with an empty inventory: "Craft a diamond pickaxe," "Craft a golden sword," "Craft a lava bucket," and "Craft a compass." This tests whether the skill library built during lifelong learning transfers to novel tasks from scratch. Results are reported as average ± standard deviation over three attempts per task, with a maximum budget of 50 prompting iterations.

**Baselines.** The paper reimplements three representative LLM-based agent methods originally designed for NLP tasks, adapting them to be executable in MineDojo with access to the same control primitives and environment feedback:

- **ReAct** (Yao et al., 2022): Uses chain-of-thought prompting to interleave reasoning traces and action plans. In the Minecraft adaptation, ReAct receives environment feedback and agent states as observations, generates code from scratch, then refines it for up to 3 additional rounds per task (1 initial + 3 refinements = 4 total rounds, matching VOYAGER's per-task budget). The process repeats until the maximum prompting iteration limit.

- **Reflexion** (Shinn et al., 2023): Builds on ReAct with self-reflection to infer better future actions. The Minecraft adaptation provides it with environment feedback, agent states, execution errors, and VOYAGER's self-verification module (to maintain fairness in available information). Like ReAct, it follows the 1 + 3 round structure per task.

- **AutoGPT** (Significant-gravitas, 2023): A popular software tool that decomposes a high-level goal into subgoals and executes them in a ReAct-style loop. The reimplementation uses GPT-4 for task decomposition and provides agent states, environment feedback, and execution errors. During subgoal execution, if no execution error occurs, the subgoal is marked complete; otherwise, the program is refined for up to 3 rounds. If three consecutive subgoals yield no new items, the system replans by rerunning task decomposition. Compared with VOYAGER, AutoGPT lacks three components: an automatic curriculum (it relies on a fixed high-level goal), a skill library for accumulating knowledge, and self-verification for assessing task success.

All baselines receive the same overarching task: "explore the world and get as many items as possible." Note that the paper explicitly does not compare against RL-based or imitation-learning-based Minecraft agents (VPT, DreamerV3, DEPS, DECKARD, Plan4MC) because those methods either operate on pixel observations and low-level motor commands (making comparisons to a code-level API agent not "apple-to-apple," per Section 3.2) or require human-provided task decomposition following Minecraft recipes. The paper's focus is on pushing the limits of GPT-4 for lifelong embodied agent learning through prompting, not on solving 3D perception or sensorimotor control.

**Generation Budget / Compute Accounting.** The primary unit of comparison is **prompting iterations**—one complete task attempt from curriculum proposal through code execution and self-verification. Each iteration involves at most 4 rounds of code generation (1 initial + 3 refinements). All methods are run for a maximum of **160 prompting iterations** for exploration experiments and **50 iterations** for zero-shot generalization. The paper also reports **GPT-4 API costs** (Section 4): GPT-4 is "15× more expensive than GPT-3.5," making VOYAGER's reliance on GPT-4 a significant cost consideration. However, cost is not factored into performance comparisons—all methods have equal access to GPT-4 for their respective operations.

**Cross-Validation / Statistical Protocol.** All exploration experiments are run for **three independent trials** (three separate Minecraft worlds with different random seeds), with results reported as averages ± standard deviations where applicable. The tech tree mastery table (Table 1) reports fractions indicating the number of successful trials out of three (e.g., `3/3` means all three runs reached that level; `1/3` means only one run succeeded). The zero-shot generalization experiments also use three attempts per task. No cross-validation, statistical significance testing, or confidence intervals are reported—the evaluation is primarily qualitative and performance-gap-based rather than statistical.

### Main Quantitative Results

#### Open-Ended Exploration: Unique Item Discovery

**Headline result:** VOYAGER discovers **63 unique items** within 160 prompting iterations, which is **3.3× more** than the best baseline (AutoGPT, which discovers approximately 19 unique items; estimated from Fig. 1).

The core exploration results are presented in **Figure 1** (main exploration curve) and detailed in Appendix B.4.1 (complete item lists for each trial). The figure plots cumulative unique items discovered against prompting iterations, showing:

- **VOYAGER** follows a steadily increasing trajectory that does not plateau within the 160-iteration window, reaching approximately 63 unique items. The slope remains positive throughout, indicating the agent continues to make novel discoveries without saturating its capability in the allotted time.

- **AutoGPT** follows a slower trajectory that shows initial progress (reaching roughly 12–19 items) but significantly lags VOYAGER. It plateaus more quickly, suggesting its lack of a skill library and automatic curriculum limits its ability to compound discoveries. The paper notes that AutoGPT lacks the "skill library for accumulating knowledge, self-verification for assessing task success, and automatic curriculum for open-ended exploration" (Section 3.2), positioning VOYAGER's advantage as resulting from the combination of all three missing components.

- **ReAct and Reflexion** struggle to make significant progress, discovering only approximately 3–5 unique items each across their trials. The paper attributes this to "the abstract nature of the open-ended exploration goal that is challenging to execute without an appropriate curriculum" (Section 3.3). These methods lack any mechanism for self-directed goal-setting—they attempt to explore but cannot decompose "discover as many diverse things as possible" into concrete, achievable subgoals.

The item lists in Appendix B.4.1 reveal the qualitative nature of the gap. VOYAGER's trial 3 collected 64 distinct items including 'diamond', 'diamond_sword', 'iron_chestplate', 'copper_block', 'gold_ingot', and 'ender_pearl'—items that require navigating deep tech tree dependencies. ReAct's trial 1 collected only 'bamboo', 'dirt', 'sand', and 'wheat_seeds'—items obtainable through the most basic interactions. Reflexion's trial 1 collected 'crafting_table', 'orange_tulip', 'oak_planks', 'oak_log', and 'dirt.' This is not merely a quantitative gap but a qualitative one—the baselines never reach the crafting and smelting stages that VOYAGER routinely achieves.

**What the exploration metric measures and what it doesn't.** The unique items count is a cumulative metric—once an item is discovered, it is permanently counted. This rewards *breadth* of exploration (trying many different activities) and *depth* (reaching items that require complex crafting chains). However, it does not capture whether the agent can reliably reproduce a discovery, how efficiently it uses resources, or whether discovered items are used productively. An agent could theoretically discover many items through random wandering, but the ablation results (Section 3.4) show that random curricula perform poorly, confirming that structured exploration drives the item count, not chance.

---

#### Tech Tree Mastery

**Headline result:** VOYAGER unlocks the wooden tool level **15.3× faster** than AutoGPT (6 ± 2 vs. 92 ± 72 iterations), the stone level **8.5× faster** (11 ± 2 vs. 94 ± 72), the iron level **6.4× faster** (21 ± 7 vs. 135 ± 103), and is the **only method to reach the diamond level** at all (1 out of 3 trials, at iteration 102). ReAct and Reflexion fail to unlock any tech tree level.

These results are presented in **Table 1**. The table reports the number of prompting iterations (mean ± standard deviation over 3 trials) required to craft the corresponding pickaxe, along with the fraction of successful trials. The structural pattern across methods is stark:

- **ReAct and Reflexion** achieve 0/3 at all four levels. They never craft a wooden pickaxe—the most basic milestone—within the 160-iteration budget. This is consistent with their exploration failure: without a mechanism to set concrete goals, they cannot maintain the directed effort needed to collect wood logs, craft planks and sticks, and assemble a pickaxe.

- **AutoGPT** successfully crafts wooden to iron pickaxes in all three trials but with extremely high variance. Wooden tool: 92 ± 72 iterations (minimum ~20, maximum ~164 across trials). Stone tool: 94 ± 72 iterations. Iron tool: 135 ± 103 iterations. The large standard deviations indicate that AutoGPT sometimes gets stuck for long periods before making progress, likely because its fixed task decomposition cannot adapt when prerequisites are missing or when the agent finds itself in unfavorable terrain.

- **VOYAGER w/o Skill Library** performs better than AutoGPT (wooden: 7 ± 2, stone: 9 ± 4, iron: 29 ± 11) but cannot reach diamond in any trial (0/3). The gap between this ablation and full VOYAGER is most pronounced at the iron level (29 vs. 21 iterations) and in the diamond-level failure, demonstrating that the skill library becomes increasingly important as tasks grow more complex. Without retrieved past skills as in-context examples and subroutines, the agent struggles to compose the multi-step smelting and crafting chains needed for higher-tier tools.

- **Full VOYAGER** achieves low-variance rapid progression through the first three levels (standard deviations of 2, 2, and 7 iterations) and reaches diamond in one trial. The diamond-level partial success (1/3) is noteworthy: it demonstrates that diamond-tier progression is within the system's *possible* capability envelope, but the conditions for success (favorable world generation, consistent code generation across all intermediate steps) are not yet reliably met.

The tech tree results corroborate the exploration findings with a structure that the unique-items metric cannot show: the *variance* in performance. AutoGPT's large standard deviations suggest brittleness—it sometimes progresses quickly but often gets derailed. VOYAGER's small standard deviations (especially at early levels) suggest robustness—the automatic curriculum and skill retrieval keep the agent on a productive trajectory across different world instances.

---

#### Map Coverage and Spatial Exploration

**Headline result:** VOYAGER traverses **2.3× longer distances** than baselines while crossing diverse terrains. The baseline agents "often find themselves confined to local areas, which significantly hampers their capacity to discover new knowledge" (Section 3.3).

The map coverage results are visualized in **Figure 7** (main paper) and **Figure A.2** (Appendix B.4.2). The main figure shows bird's-eye view circles enclosing each agent's trajectory, with VOYAGER's circle substantially larger. The appendix figure shows the actual trajectory paths plotted as connected position points where each agent interacted with GPT-4.

The qualitative difference in traversal patterns is informative. Appendix B.4.2 lists the terrains each agent crossed:
- **VOYAGER Trial 1:** meadow, desert, river, savanna, forest, plains, bamboo_jungle, dripstone_caves (8 distinct biomes)
- **AutoGPT Trial 2:** snowy_taiga only (1 biome, despite discovering 22 items by efficiently exploiting local resources)
- **ReAct Trial 1:** plains, desert, jungle (3 biomes, but few items discovered)

VOYAGER's extensive traversal is not merely a byproduct of exploration—it is likely *caused by* the automatic curriculum, which proposes biome-specific tasks (catching fish near rivers, mining sand in deserts) that require movement. The baseline agents lack this "situational awareness," as the paper calls it, and thus have no reason to leave their local area. However, an alternative interpretation is possible: the traversal metric may partially reflect VOYAGER's random exploration directions (`exploreUntil` direction chosen "at random every time," per code generation rule 7) combined with task-driven movement, rather than purely task-driven exploration. The paper does not disentangle these factors.

#### Zero-Shot Generalization to Unseen Tasks

**Headline result:** VOYAGER with its skill library successfully solves all four unseen tasks within 50 prompting iterations, requiring **19 ± 3 iterations** for a diamond pickaxe, **18 ± 7** for a golden sword, **21 ± 5** for a lava bucket, and **18 ± 2** for a compass. All baselines **fail to solve any task** within the 50-iteration budget (0/3 on all tasks). VOYAGER without the skill library solves 3/4 tasks but requires significantly more iterations (e.g., 36 vs. 19 iterations for diamond pickaxe in the successful trials). AutoGPT with VOYAGER's skill library (but not its curriculum or self-verification) solves 3 of 4 tasks (diamond pickaxe: 1/3 at 39 iterations; golden sword: 1/3 at 30 iterations; compass: 2/3 at 30 iterations; lava bucket: 0/3).

These results are presented in **Table 2** and **Figure 8** (with **Figure A.3** covering the additional two tasks). The experimental setup is important: for zero-shot evaluation, the agent's inventory is cleared, it is placed in a newly instantiated world, and it is given an explicit task to solve (e.g., "Craft a diamond pickaxe"). For both VOYAGER and AutoGPT, GPT-4 is used to decompose the high-level task into subgoals (mimicking AutoGPT's approach for the zero-shot setting). The key variable being tested is whether **the skill library accumulated during lifelong learning** transfers to solving these specific tasks more efficiently.

**The skill library as a transferable asset.** The most striking finding is not just that VOYAGER solves these tasks, but that the skill library functions as a "plug-and-play asset" (Section 3.3) that benefits even AutoGPT, which lacks its own memory mechanism:

- AutoGPT alone: 0/3 on all four tasks.
- AutoGPT with VOYAGER's skill library: Successfully solves 3 of 4 tasks, albeit with low reliability (1/3 or 2/3 on those it solves).

This is a **cross-architecture transfer demonstration**: skills learned under VOYAGER's curriculum-driven exploration are reusable by a completely different planning architecture (AutoGPT's task decomposition) for directed task completion. The skill library encodes Minecraft procedural knowledge that is independent of how tasks are *proposed*.

**Why VOYAGER without the skill library still outperforms baselines on three tasks.** VOYAGER without the skill library solves the diamond pickaxe (2/3 at 36 iterations), golden sword (3/3 at 30 ± 9), lava bucket (3/3 at 27 ± 9), and compass (3/3 at 26 ± 3). This variant retains the automatic curriculum, iterative prompting with three feedback types, and self-verification—only the retrieval of past skills is removed. Its success (compared to baselines' complete failure) demonstrates that the curriculum and iterative prompting alone provide substantial capability for task completion. However, the skill library provides an additional 1.5–2× speedup: the full system solves tasks faster, with lower variance, and achieves 100% success rates on all tasks.

**Figure 8** and **Figure A.3** visualize intermediate task progress as inventory state snapshots at different iteration counts. For "Craft a diamond pickaxe," VOYAGER progresses through wood planks → crafting table → wooden pickaxe → stone pickaxe → furnace → iron pickaxe → diamond at iteration 19. AutoGPT (even with the skill library) shows a more erratic trajectory, sometimes circling back to earlier states.

**Note on experimental protocol:** The zero-shot generalization tasks are *explicitly specified* by the experimenters, not self-proposed by the agent. This means the evaluation measures skill reuse under directed goal-setting, not the agent's ability to *discover* that a diamond pickaxe is a worthwhile goal. The lifelong learning contribution is the construction of the skill library; the zero-shot experiment tests whether that library is genuinely useful for downstream tasks.

### Ablation Studies and Robustness Checks

All ablations are evaluated on the exploration performance metric (unique items discovered) and presented in **Figure 9** (left and right panels). Each ablation removes or replaces one component while keeping the rest of VOYAGER's architecture intact. The paper reports the cumulative item discovery trajectories, allowing comparison of both the final item count and the rate of discovery over the 160-iteration budget.

#### Automatic Curriculum Ablations (Figure 9, left)

- **Manual Curriculum:** A hardcoded 10-task sequence (wood log → crafting table → wooden pickaxe → cobblestone → stone pickaxe → furnace → iron ore → smelt iron → iron pickaxe → diamond) reduces unique item discovery dramatically compared to the automatic curriculum. The paper notes this "falls short in the experimental results compared to our automatic curriculum" (Section 3.4) but does not report a specific percentage drop. The visual in Figure 9 (left) shows the manual curriculum reaching approximately 10–15 unique items—roughly 20% of full VOYAGER's 63. This ablation demonstrates that a fixed curriculum, even when designed with Minecraft expertise, cannot adapt to the agent's actual situation, biome, or inventory state, and cannot propose opportunistic tasks outside the prescribed sequence.

- **Random Curriculum:** Selecting tasks randomly from a curated list of 101 items obtained by VOYAGER causes a **93% drop** in discovered items. The agent is essentially paralyzed—it receives tasks for which it lacks prerequisites (e.g., being asked to craft an iron pickaxe before obtaining wood), cannot complete them, and makes minimal progress. This is the only ablation for which a specific percentage drop is reported in the main text, underscoring the severity of the curriculum contribution. The result validates a core design premise: the order of task attempts matters immensely, and random ordering is essentially equivalent to no useful guidance at all.

These two ablations together establish the necessity of *adaptive*, *situation-aware* curriculum generation. Neither human expertise (manual curriculum) nor domain randomization (random curriculum) can substitute for the ability to observe the agent's current inventory, biome, nearby entities, and past progress when deciding what to attempt next.

#### Skill Library Ablation (Figure 9, left)

- **VOYAGER w/o Skill Library:** Removing the skill library (eliminating skill retrieval; GPT-4 generates code for each task without access to past successful programs) causes the exploration curve to "exhibit a tendency to plateau in the later stages" (Section 3.4). The curve initially tracks full VOYAGER closely—early tasks like mining wood and crafting basic tools do not benefit much from retrieval because the skill library is empty or sparse—but diverges increasingly as tasks grow more complex. The paper's interpretation is that the skill library "helps create more complex actions and steadily pushes the agent's boundaries by encouraging new skills to be built upon older ones." The plateau suggests that without retrieval, GPT-4 eventually hits a ceiling on what it can generate from scratch for complex multi-step tasks. This is consistent with the tech tree results (Table 1), where the no-skill-library variant cannot reach the diamond level.

#### GPT-4 vs. GPT-3.5 for Code Generation (Figure 9, left)

- **VOYAGER w/ GPT-3.5:** Replacing GPT-4 with GPT-3.5 for code generation (while keeping GPT-4 for curriculum and self-verification) results in **5.7× fewer unique items**. This is a massive difference—far larger than any other single ablation—and the paper attributes it to GPT-4's "quantum leap in coding abilities" (Section 3.4), a finding that "corroborates recent studies in the literature" (citing Bubeck et al., 2023; Liu et al., 2023). The implication is stark: VOYAGER's entire architecture depends on the code generation quality of the underlying LLM. With GPT-3.5, the iterative prompting mechanism cannot compensate for fundamentally weaker code synthesis—the three feedback types cannot fix code that is too far from correct. This is simultaneously a limitation (VOYAGER is locked to GPT-4's API and cost structure, as acknowledged in Section 4) and a prediction: as LLM code generation capabilities improve, VOYAGER-like systems should improve correspondingly without architectural changes.

#### Iterative Prompting Mechanism Ablations (Figure 9, right)

- **w/o Self-Verification:** Removing the self-verification module causes a **73% drop** in discovered items—the single largest impact among the three feedback types. Without the critic, the agent has no mechanism to determine whether a task succeeded, and therefore cannot correctly decide when to move on to the next curriculum proposal or when to refine the current code. The paper emphasizes this module's role as the termination and quality-control mechanism: "Self-verification serves as a critical mechanism to decide when to move on to a new task or reattempt a previously unsuccessful task." The magnitude of the drop reinforces the architectural insight that task-level success determination is not a luxury but a necessity for sustained autonomous behavior.

- **w/o Environment Feedback:** Removing the chat log from the code generation prompt reduces item discovery notably (the exact percentage is not reported in the text, but the visual gap in Figure 9 right is smaller than the self-verification gap but still substantial). Without environment feedback, GPT-4 cannot see the intermediate progress of its code execution—it cannot learn that "I cannot make sticks because I need 2 more planks" (the Fig. 5 example) and therefore cannot adjust its resource calculations in the next refinement round.

- **w/o Execution Errors:** Removing execution errors from the prompt similarly reduces performance. Without error traces, GPT-4 lacks the signal that it hallucinated a non-existent item name (like "acacia_axe" in Fig. 5) or misused an API. The paper positions this as complementary to environment feedback: execution errors reveal *code validity* problems, while environment feedback reveals *world state* problems.

The relative ordering of importance (self-verification > environment feedback ≈ execution errors, based on the magnitude of drops in Figure 9 right) suggests a hierarchy of feedback criticality. Task-level assessment is the most fundamental—without it, the agent cannot even define success. World-level feedback and code-level feedback are both important for *efficiency* (reducing the number of refinement rounds needed) but the agent can potentially stumble through without them. The paper does not run the ablation where all three feedback types are removed simultaneously, which would likely show near-total failure.

#### Robustness to Model Version (Appendix B.4.5, Figure A.4)

- **GPT-4-0314 vs. GPT-4-0613:** The main experiments use `gpt-4-0314`. The authors additionally test VOYAGER with `gpt-4-0613` and find that "performance is roughly the same" (Appendix B.4.5). The exploration curves in Figure A.4 track closely, indicating that VOYAGER is not exploiting version-specific quirks of the March 2023 GPT-4 snapshot. This robustness check addresses a reasonable concern—API models are updated over time, and methods that are hypersensitive to specific model versions would have limited reproducibility.

#### Skill Retrieval Accuracy (Appendix B.4.4, Table A.4)

- **Retrieval evaluation:** On 309 samples, the skill library achieves **top-1 accuracy of 80.2%**, top-2 of 89.3%, top-3 of 93.2%, top-4 of 95.2%, and **top-5 of 96.5%** (with standard deviations of approximately 3.0, 1.8, 0.7, 1.8, and 0.3 respectively). Since the action prompt includes the top-5 retrieved skills, the effective failure rate is roughly 3.5%. This establishes that the embedding-based retrieval mechanism is reliable enough for practical use—in approximately 96.5% of cases, at least one of the top-5 retrieved skills is relevant to the current task. The paper does not analyze the 3.5% failure cases or characterize what types of tasks cause retrieval failures, which would be informative for understanding the library's coverage gaps.

#### Human-in-the-Loop Extension (Section 3.5, Figure 10)

- **Multimodal feedback for 3D construction:** As a qualitative demonstration, VOYAGER is shown to construct complex 3D structures (a Nether Portal and a house) when provided human feedback in two roles: (1) human as critic (replacing self-verification with visual feedback about spatial errors in the structure), and (2) human as curriculum (breaking down a complex building task into incremental steps). This is not a systematic evaluation but a proof-of-concept that the architecture generalizes to tasks beyond item collection and crafting. It also highlights a current limitation—VOYAGER lacks visual perception (GPT-4's API was text-only at time of writing), and the human feedback serves as a proxy for what a multimodal model might eventually provide automatically.

### Critical Assessment

#### Claim 1: "VOYAGER obtains 3.3× more unique items [than baselines]" and demonstrates "strong in-context lifelong learning capability"

**What the experiments demonstrate:** The 3.3× figure is unambiguous relative to AutoGPT, the best-performing baseline. VOYAGER reaches ~63 unique items versus AutoGPT's ~19 in 160 prompting iterations (Fig. 1). The gap relative to ReAct and Reflexion is far larger (~63 vs. ~3–5). The trajectory continues rising at iteration 160, suggesting further gains with more iterations.

**What is genuinely tested:** The experiments test whether a specific architectural combination (automatic curriculum + skill library + three-feedback iterative prompting + GPT-4 for code generation) produces sustained exploration in Minecraft better than simpler LLM-agent architectures (ReAct, Reflexion, AutoGPT) that lack some or all of these components. The phrase "lifelong learning" is operationalized as "continuous item discovery over 160 iterations without plateauing" plus "accumulation of a skill library that transfers to new tasks."

**What is not tested:** 
- **Beyond 160 iterations:** The paper does not demonstrate that VOYAGER continues to discover items indefinitely. The slope of the exploration curve in Figure 1 appears positive but may gradually decay. True "lifelong" learning would require demonstrating sustained discovery over much longer horizons—days or weeks of real-time play, thousands of iterations.
- **Skill degradation over time:** The paper claims the skill library "alleviates catastrophic forgetting," but this is demonstrated only through retrieval accuracy (Table A.4) and the tech tree progression—not through a dedicated experiment where old skills are explicitly tested after many new skills are added. An agent that can craft a diamond pickaxe at iteration 102 should still be able to craft a wooden pickaxe at iteration 10,000; this property is not verified.
- **Beyond Minecraft:** All claims are domain-specific. The paper argues the architecture is "generally applicable to other domains" (Section 7) but provides no evidence outside Minecraft. The reliance on GPT-4's pre-trained Minecraft knowledge for curriculum generation and self-verification suggests the approach may not transfer to domains where LLMs lack detailed procedural knowledge.
- **The 160-iteration ceiling:** The paper does not explain why 160 iterations was chosen. If VOYAGER was still improving, a longer horizon would strengthen the "lifelong" claim. If it was approaching a ceiling, that would bound the lifelong learning capability.

**Conditional nature of the result:** The exploration performance depends critically on GPT-4's code generation quality. The GPT-3.5 ablation (5.7× fewer items, Fig. 9) shows that the same architecture with a weaker model performs dramatically worse—not incrementally worse, but qualitatively failing at the lifelong learning objective. This means VOYAGER's "lifelong learning" is currently contingent on access to a specific, expensive, closed-source model. The robustness to GPT-4 version updates (Fig. A.4) provides some reassurance, but the fundamental dependency remains.

#### Claim 2: "VOYAGER unlocks key tech tree milestones up to 15.3× faster than prior SOTA"

**What the experiments demonstrate:** The tech tree progression times in Table 1 are internally consistent and the speedups are large. VOYAGER reaches wooden tools in ~6 iterations versus AutoGPT's ~92 (15.3×), stone in ~11 vs. ~94 (8.5×), iron in ~21 vs. ~135 (6.4×). The variance is far lower (standard deviations of 2–7 vs. 72–103), indicating reliability, not just speed.

**What is genuinely tested:** Efficiency of directed progression through a known prerequisite hierarchy. The tech tree tasks are concrete, with clear success criteria (the pickaxe appears in inventory), favoring VOYAGER's self-verification mechanism which is designed for such verifiable tasks.

**Concerns:** 
- **AutoGPT as "SOTA":** The paper positions AutoGPT as the state-of-the-art LLM agent baseline, but AutoGPT is a general-purpose NLP tool repurposed for Minecraft by the authors. It was not designed for or optimized for embodied environments. The comparison is legitimate (it's the best available LLM-based agent that can be adapted), but calling it "prior SOTA" in the context of Minecraft agents is debatable—RL-based methods like DreamerV3 have demonstrated diamond acquisition in Minecraft (albeit with different assumptions about action space and perception). The paper explicitly excludes these comparisons as not "apple-to-apple" (Section 3.2), which is reasonable but means the "SOTA" claim refers specifically to *LLM-based prompt-only agents*, not to all Minecraft agents.
- **The speedup factors decrease as difficulty increases (15.3× → 8.5× → 6.4×).** This trend is never discussed but is informative: VOYAGER's relative advantage narrows at higher tech tree levels. The diamond level (only 1/3 success for VOYAGER, 0/3 for all baselines) shows that neither approach reliably achieves the hardest milestone. The paper's framing ("15.3× faster") highlights the largest number, but the narrowing ratio suggests that VOYAGER's advantage may diminish as tasks approach the frontier of GPT-4's code generation capability.

#### Claim 3: "VOYAGER traverses 2.3× longer distances" and crosses diverse terrains

**What the experiments demonstrate:** The trajectory circles in Figure 7 and the paths in Figure A.2 show VOYAGER covering more ground. The biome lists in Appendix B.4.2 confirm it visits more diverse terrain types.

**Concerns:** The 2.3× figure is a suggestive but coarse metric. It is computed as the diameter of a minimum enclosing circle, which is sensitive to outliers—a single long excursion inflates the circle dramatically. The paper reports this as "distance" but it is actually spatial extent, not path length. More importantly, traversal distance is a *means*, not an *end*—the paper values it because it "significantly hampers [baselines'] capacity to discover new knowledge" (Section 3.3). The correlation between traversal distance and item discovery is intuitive but not quantified. An agent could theoretically traverse extensively without discovering anything useful, or discover many items in a compact area. The paper does not regress items discovered against distance traveled or otherwise establish that the traversal *causes* the discovery advantage.

#### Claim 4: "VOYAGER is able to utilize the learned skill library in a new Minecraft world to solve novel tasks from scratch"

**What the experiments demonstrate:** VOYAGER with its skill library consistently solves all four unseen tasks (Table 2), solves them faster than VOYAGER without the skill library, and the skill library transfers to AutoGPT (enabling it to solve 3 of 4 tasks it otherwise completely fails on). This is a strong, clean demonstration of transfer.

**What is genuinely tested:** Zero-shot generalization within the same domain (Minecraft) to tasks that require skills similar to those in the library. All four generalization tasks (diamond pickaxe, golden sword, lava bucket, compass) are crafting tasks that use the same control primitives and build on mid-to-late tech tree skills. This is transfer, but it is *in-distribution* transfer—the tasks are of the same type as those the agent practiced during exploration.

**What is not tested:** 
- **Out-of-distribution generalization:** Would VOYAGER's skill library help with tasks requiring fundamentally different skills, such as building complex structures (the human-in-the-loop demonstration in Section 3.5 suggests not, since human feedback was required), redstone engineering, or combat with the Ender Dragon? The paper doesn't test whether the library's utility extends beyond crafting-related tasks.
- **Catastrophic interference in the skill library:** The vector database grows unboundedly. At some scale, retrieval accuracy may degrade as the embedding space becomes cluttered with similar skills. The 309-sample evaluation (96.5% top-5 accuracy) is far below the scale where this would manifest. The paper does not characterize how retrieval accuracy scales with library size.
- **Cross-domain transfer:** Could VOYAGER's Minecraft skill library help it in a different game or a real-world robotic task? The paper makes no such claim, but the phrase "generalizable to novel tasks" (Section 1) could be interpreted more broadly than "novel Minecraft crafting recipes."

#### Missing Experiments That Would Strengthen the Paper

**1. Longer-horizon evaluation.** 160 iterations represent a few hours of gameplay at most. Running VOYAGER for 1,000+ iterations would reveal whether the exploration curve continues upward or asymptotes, and whether the skill library remains coherent or accumulates redundant or conflicting skills.

**2. Comparison against an RL-based Minecraft agent with equivalent API access.** The paper's argument that RL comparisons are not "apple-to-apple" is reasonable given the action-space difference, but a version of DreamerV3 or VPT adapted to use the same Mineflayer API would directly test whether the LLM-based approach offers advantages over gradient-based learning when both operate in the same action space. Without this, the 3.3×, 15.3×, and 2.3× figures are comparisons against weak LLM-agent baselines only.

**3. Ablation of the warm-up schedule.** The curriculum warm-up schedule (Table A.1) gradually introduces state information. The paper never ablates this design choice—would the curriculum perform better or worse if all state information were provided from the start? The warm-up design implies a hypothesis (too much information early distracts from basic tasks) but this hypothesis is untested.

**4. Ablation of skill library size on performance.** Does retrieval quality degrade as the library grows? The 309-sample evaluation doesn't track accuracy as a function of library size. A systematic evaluation showing retrieval accuracy at library sizes of 10, 50, 100, 200, 300 would characterize scalability.

**5. Statistical rigor.** No confidence intervals on the exploration curves, no significance tests on differences between methods. The 3-trial design for exploration means each data point in Figure 1 is the mean of only three runs with unshown variance. The tech tree results (Table 1) show standard deviations, but the exploration curves (Fig. 1) and map coverage (Fig. 7) do not. Given the inherent stochasticity of Minecraft world generation, procedure generation, and GPT-4 outputs, reporting variance is essential.

**6. Cost analysis integrated with performance.** The paper mentions GPT-4's cost (15× GPT-3.5) in limitations but never quantifies the total API cost of a 160-iteration run. Knowing that VOYAGER achieves 3.3× more items is useful; knowing that this comes at, say, $200 in API costs versus $5 for AutoGPT would be equally important for practitioners.

#### Overall Assessment

The experimental evidence supports the paper's central claim—that the specific combination of an automatic curriculum, skill library, and iterative prompting mechanism enables sustained exploration and skill acquisition in Minecraft significantly beyond what simpler LLM-agent architectures achieve. The effect sizes are large (3.3× more items, 15.3× faster tech tree progression, zero-shot transfer that baselines completely fail at), and the ablation studies demonstrate that each component contributes non-trivially to the overall performance.

However, the evidence supports a narrower claim than the paper's framing sometimes implies. What is demonstrated is that **a frozen GPT-4, scaffolded with external memory and feedback loops, can explore a complex embodied environment more effectively than other LLM agents within a bounded 160-iteration horizon in Minecraft**. The "lifelong" qualifier is aspirational at the demonstrated scale—160 iterations is a long experimental run but a short lifespan. The "generalist agent" framing is speculative without cross-domain evidence. The dependency on GPT-4's code generation quality (5.7× drop with GPT-3.5) means the results are contingent on a specific, expensive, and evolving model.

The strongest experimental contributions are the **ablation analyses** (Figure 9), which provide a decomposition of which components matter and why, and the **zero-shot transfer with skill library sharing** (Table 2, AutoGPT + skill library), which cleanly isolates the skill library's contribution independent of VOYAGER's other components. The weakest aspect is the **lack of statistical characterization**—three trials with no confidence intervals make it difficult to assess whether the reported differences would replicate or whether they reflect lucky world seeds.

The experiments that would most strengthen the work are: longer-horizon runs (to test the "lifelong" claim), comparison against an RL agent with equivalent API access (to test the "no gradient updates needed" claim against a real alternative), and cross-domain transfer (to test the "generalist" claim). As it stands, the paper demonstrates that LLM scaffolding works remarkably well for Minecraft exploration, but leaves open how much of this success is due to the architectural innovations versus GPT-4's specific strengths on Minecraft-related code generation.

## 6. Limitations and Trade-offs

### The Method Depends on GPT-4's Code Generation Quality—Performance Collapses With Weaker Models

**The assumption or constraint.** VOYAGER's entire architecture assumes the underlying LLM can generate working JavaScript code for embodied control tasks with sufficient reliability that iterative refinement can converge to correct solutions. The paper is explicit about this dependency: "VOYAGER requires the quantum leap in code generation quality from GPT-4, which GPT-3.5 and open-source LLMs cannot provide" (Section 4). The assumption is not just that the LLM can produce code—it is that the LLM can produce code that is *close enough* to correct that three rounds of environment feedback, execution error, and critique-driven refinement can close the gap.

**The consequence.** When GPT-4 is replaced with GPT-3.5 for code generation, unique item discovery drops by **5.7×** (Section 3.4, Figure 9, left). This is the single largest performance gap in any ablation, larger than removing the automatic curriculum, the skill library, or any feedback type. The implication is sobering: the architectural innovations (curriculum, skill library, iterative prompting) are *necessary* but not *sufficient*—without a sufficiently capable code-generating model, the system fails regardless of how well-designed the scaffolding is. This creates a hard dependency on a specific, expensive, closed-source, and continuously evolving model API. Practitioners cannot swap in a different LLM without risking catastrophic performance degradation. The paper also notes that "hallucinations" occur during code generation, such as GPT-4 using cobblestone as a fuel input (despite being invalid) or calling functions that don't exist in the control primitive APIs (Section 4), but these are framed as errors that the iterative mechanism can sometimes fix—a claim that holds for GPT-4 but would not generalize to weaker models.

**What evidence exists in the paper.** The GPT-3.5 ablation (Section 3.4, Figure 9, left) provides direct comparative evidence. The robustness check with `gpt-4-0613` (Appendix B.4.5, Figure A.4) shows stability across GPT-4 versions but does not address whether the architecture would work with models from other providers or open-source alternatives. The paper also acknowledges that "improvements in the GPT API models as well as novel techniques for finetuning open-source LLMs will overcome these limitations in the future" (Section 4), implicitly conceding that the current approach is model-locked.

**Mitigation status.** The paper does not mitigate this limitation. It is explicitly acknowledged as a constraint (Section 4) and a future direction. The cost implication—GPT-4 is "15× more expensive than GPT-3.5" (Section 4)—is noted but not factored into any performance-cost tradeoff analysis. The paper does not experiment with fine-tuning open-source models on Minecraft code generation data, which would be the natural bridge to reducing this dependency.

---

### Difficulty Estimation Cost Is Unaccounted for in Headline Efficiency Numbers

**The assumption or constraint.** The automatic curriculum generates tasks by prompting GPT-4 with rich situational context: full inventory, nearby blocks and entities, biome, time, health, hunger, position, chest contents, completed and failed task history, plus GPT-3.5-generated question-answer context (Section 2.1, Appendix A.3.1). This prompt construction requires querying the Minecraft environment for state, running a separate GPT-3.5 call for self-questioning (5–10 questions with answers, after 15 completed tasks per the warm-up schedule in Table A.1), and making a GPT-4 call for curriculum generation. None of these costs are accounted for when the paper reports that VOYAGER discovers 63 unique items in 160 prompting iterations—the "160 iterations" metric counts only task attempts, not the auxiliary API calls for curriculum generation, skill retrieval, skill description generation, and self-verification.

**The consequence.** The actual number of GPT-4 API calls per iteration is substantially larger than 1. For each task attempt, the system makes at minimum: one curriculum call (GPT-4, to propose the next task, although this is amortized across tasks), up to 4 action agent calls (GPT-4, for code generation), up to 4 critic calls (GPT-4, for self-verification), one GPT-3.5 call for task context generation, and one GPT-3.5 call for skill description generation if the task succeeds. The embedding calls for skill retrieval add additional API costs. The headline efficiency comparisons (3.3× more items, 15.3× faster tech tree progression) are computed based on prompting iteration counts, not total API costs. Given that GPT-4 is 15× more expensive than GPT-3.5, and VOYAGER uses GPT-4 far more heavily than the baselines (AutoGPT primarily uses GPT-4 for task decomposition and code generation but lacks the separate curriculum and critic GPT-4 calls), the cost-adjusted efficiency advantage may be significantly smaller—or could even reverse—compared to the iteration-count advantage.

**What evidence exists in the paper.** The paper reports the cost differential in Section 4 but does not provide any cost accounting: no total API call counts, no dollar figures, no cost-per-item-discovered metric. The warm-up schedule (Table A.1) and the prompt descriptions (Appendix A.3–A.5) document the auxiliary calls explicitly, so the information to reconstruct costs is partially available, but the analysis is not performed. The paper frames cost as a limitation to be addressed by future model improvements, not as a factor that should qualify the reported performance claims.

**Mitigation status.** Not mitigated. The authors state that "VOYAGER serves as a starting point" (Section 6) and express confidence that "improvements in the GPT API models" (Section 4) will reduce costs over time, but the current work provides no cost-efficiency analysis to contextualize the performance gains.

---

### Hard Tasks Near the Frontier of GPT-4's Code Generation Capability Remain Unreliable or Unsolved

**The assumption or constraint.** VOYAGER's capability is bounded by the difficulty of tasks that GPT-4 can generate correct code for within 4 refinement rounds. For tasks that require complex, multi-step reasoning with multiple prerequisite crafting chains, error-prone spatial reasoning, or API usage patterns that GPT-4 has not reliably internalized, the iterative prompting mechanism may fail to converge. The paper acknowledges this in Section 4: "Despite the iterative prompting mechanism, there are still cases where the agent gets stuck and fails to generate the correct skill."

**The consequence.** The diamond tech tree level—the hardest milestone in the evaluation—is achieved in only **1 out of 3 trials** (Table 1), requiring 102 iterations in the successful case. The other two trials never reach diamond within the 160-iteration budget. For the hardest exploration difficulty tier (analogous to the "bin 5" problems in the compute-optimal scaling paper), VOYAGER's performance is unreliable: it can succeed under favorable conditions (favorable world generation, lucky code generation in the critical crafting steps) but cannot guarantee success. For practitioners deploying VOYAGER-like systems, this means there is no performance floor for hard tasks—the system may succeed quickly, succeed after many iterations, or never succeed at all, and there is no mechanism to predict which outcome will occur.

Additionally, the automatic curriculum "occasionally proposes unachievable tasks" due to hallucinations—for example, asking the agent to craft a "copper sword" or "copper chestplate," which are items that do not exist in Minecraft (Section 4). When this happens, the agent wastes up to 4 refinement rounds attempting an impossible task before the curriculum marks it as failed and proposes a new task. This is not merely an efficiency loss; it means the agent's exploration budget is partially consumed by tasks that no amount of code refinement can solve.

**What evidence exists in the paper.** The diamond tech tree results (Table 1: 1/3 success) and the hallucination discussion (Section 4) provide direct evidence. The item lists in Appendix B.4.1 show that VOYAGER's trial 3 acquired a diamond and a diamond sword, while trials 1 and 2 did not, demonstrating the inconsistency. The failed diamond attempts are not analyzed in detail—the paper does not characterize *why* the two failed runs failed (was it world generation? code generation errors? resource shortages?).

**Mitigation status.** Partially mitigated by the curriculum's ability to mark tasks as failed and reattempt them later. The paper notes that "the automatic curriculum has the flexibility to reattempt this task at a later time" (Section 4). However, there is no mechanism to diagnose *why* a task failed and adjust the approach accordingly—the curriculum simply records the failure and may propose it again when the agent's state has changed. The hallucination problem (impossible tasks) has no mitigation beyond the 4-round limit, after which the task is abandoned. The paper expresses confidence that "improvements in the GPT API models" (Section 4) will reduce hallucinations, but this is an external dependency, not a solved problem within the current architecture.

---

### The Method Is Evaluated on a Single Environment (Minecraft) With a Single Model Family (GPT-4/GPT-3.5), and the Gap Between VOYAGER and Baselines Depends on Baseline Weakness

**The assumption or constraint.** All experiments use Minecraft as the environment, GPT-4 (`gpt-4-0314`) as the primary reasoning/code-generation engine, and GPT-3.5 (`gpt-3.5-turbo-0301`) for auxiliary tasks (Section 3.1). The baselines—ReAct, Reflexion, and AutoGPT—are NLP methods originally designed for text-based tasks, reimplemented by the authors for Minecraft compatibility (Section 3.2). The paper explicitly does not compare against RL-based or imitation-learning-based Minecraft agents (VPT, DreamerV3, DEPS, DECKARD, Plan4MC), arguing that "it would not be an apple-to-apple comparison, because we rely on the high-level Mineflayer API to control the agent" (Section 3.2).

**The consequence.** Two distinct generalizability concerns arise. First, **environment generalizability**: Minecraft has specific properties that make it favorable for VOYAGER's approach—a well-documented tech tree, extensive coverage in GPT-4's training data (game mechanics, crafting recipes, biome information), a deterministic crafting system with clear success criteria, and an API (Mineflayer) that abstracts away perception and motor control. It is unknown whether VOYAGER's architecture would work in environments where LLMs lack detailed procedural knowledge (novel games, real-world robotics scenarios, enterprise software with proprietary APIs) or where task success is ambiguous or subjective. The curriculum generation, self-verification, and even the skill library retrieval all exploit GPT-4's Minecraft-specific pre-training—the self-verification few-shot examples (Prompt 6) reference Minecraft-specific knowledge like "mining iron_ore will get raw_iron" and "zombies drop rotten flesh." In a domain without this baked-in knowledge, the critic agent would need different (possibly hardcoded) success criteria.

Second, **baseline strength**: the 3.3×, 15.3×, and 2.3× figures are comparisons against LLM-based agents that were not designed for embodied environments and were adapted by the authors. While this is a fair comparison for the paper's stated scope ("pushing the limits of GPT-4 for lifelong embodied agent learning," Section 3.2), it means the performance gap reflects a combination of VOYAGER's architectural strengths and the baselines' domain mismatch. The absence of RL-based comparisons means we cannot assess whether the code-as-action, LLM-prompted approach offers advantages over gradient-based learning when both have equivalent action-space abstraction. For instance, could a DreamerV3 variant trained on the Mineflayer API achieve comparable or better exploration with lower inference cost? The paper provides no evidence either way.

**What evidence exists in the paper.** The single-environment, single-model-family evaluation is evident from the experimental setup (Section 3.1). The baseline selection rationale is discussed in Section 3.2. The system-level comparison table (Table A.2) documents the differences between VOYAGER and RL-based methods, but this is a feature comparison, not a performance comparison. The human-in-the-loop 3D construction demonstration (Section 3.5) hints at generality but requires human-provided visual feedback that the autonomous system lacks, underscoring rather than resolving the environment-specificity concern.

**Mitigation status.** The paper acknowledges the scope limitation implicitly through its framing: "VOYAGER serves as a starting point to develop powerful generalist agents" (Section 6) and "VOYAGER is designed to be generally applicable to other domains, such as robotics" (Section 7). However, no cross-domain experiments are conducted, and the paper provides no analysis of which Minecraft-specific properties are load-bearing for the architecture's success versus which would transfer. The reliance on GPT-4's pre-trained domain knowledge is not treated as a limitation to be mitigated but as a resource to be exploited.

---

### Lifelong Learning Is Demonstrated Over Only 160 Iterations—True Lifelong Scalability Is Untested

**The assumption or constraint.** The paper evaluates VOYAGER's exploration over **160 prompting iterations** (Section 3.3) and claims "strong in-context lifelong learning capability" (Section 1) and that the skill library "compounds the agent's abilities rapidly and alleviates catastrophic forgetting" (Abstract). The term "lifelong learning" implies sustained, indefinite capability accumulation without degradation, but the experimental horizon is finite and relatively short (a few hours of gameplay).

**The consequence.** Several fundamental lifelong learning questions are unanswered. First, **exploration saturation**: does the unique item discovery curve (Figure 1) continue its positive slope indefinitely, or does it asymptote? If VOYAGER saturates at, say, 100 unique items after 300 iterations, then it is not a lifelong learner in the meaningful sense—it is an agent that explores effectively within a bounded capability envelope, after which it stops making novel discoveries. Second, **skill library coherence at scale**: as the skill library grows, retrieval accuracy may degrade (the embedding space becomes cluttered), the library may accumulate redundant or conflicting skills (multiple versions of "smelt iron" with slightly different implementations), and the prompt may become bloated with retrieved skills of marginal relevance. The 309-sample retrieval evaluation (Table A.4) shows 96.5% top-5 accuracy at that scale, but this is an order of magnitude below what a truly lifelong system would accumulate. Third, **catastrophic forgetting in practice**: while the paper argues that external memory avoids catastrophic forgetting, this argument holds only if retrieval remains accurate and if old skills remain callable as subroutines without breaking when composed with newer skills that may have different side effects or assumptions. Neither property has been tested at scale.

**What evidence exists in the paper.** The exploration curve (Figure 1) shows a positive slope at iteration 160 but provides no projection beyond that horizon. VOYAGER without the skill library "exhibits a tendency to plateau in the later stages" (Section 3.4, Figure 9, left), suggesting that the skill library is what sustains progress—but this is a comparative claim about two variants at the same 160-iteration scale, not evidence that the full system avoids plateauing at longer horizons. The retrieval accuracy evaluation (Table A.4) uses 309 samples drawn from the 160-iteration runs, which is the full accumulated library size, but does not characterize how accuracy changes as the library grows from 0 to 309 skills (which would reveal scaling trends).

**Mitigation status.** Not mitigated and not acknowledged as a limitation in the paper. The "lifelong" framing is presented as an achieved property rather than an aspirational one. The paper does not discuss horizon effects, library scaling, or the distinction between "learning over an extended session" and genuine open-ended lifelong capability acquisition. The experiments simply end at 160 iterations, and no analysis is provided of whether the system's performance trajectory justifies the "lifelong" label.

---

### The System Has No Mechanism for Dynamic Strategy Adjustment or Meta-Learning Across Task Attempts

**The assumption or constraint.** VOYAGER's architecture makes several fixed design choices that do not adapt based on the agent's experience: the warm-up schedule (Table A.1) follows a predetermined progression of information disclosure regardless of how quickly or slowly the agent is learning; the 4-round refinement limit is fixed per task regardless of whether the task is close to success (round 3 almost succeeded) or fundamentally misaligned (the task is impossible); the curriculum proposes tasks based on the current state and history but has no mechanism for recognizing that a particular *type* of strategy (e.g., exploring in a certain direction, prioritizing certain resource types) has been consistently productive or counterproductive. In reinforcement learning terms, VOYAGER learns at the skill level (acquiring new programs) but not at the meta-level (learning how to learn more effectively in this environment).

**The consequence.** The system cannot improve its own learning process over time. If the agent consistently fails at combat-related tasks because GPT-4's combat code generation is weaker than its crafting code generation, the curriculum has no way to learn this pattern and adjust—it will continue proposing combat tasks at the same rate, wasting iteration budget. If a particular refinement strategy (e.g., checking inventory before crafting versus attempting to craft and handling the error) proves more effective, this insight is not captured or propagated. The fixed 4-round limit means that tasks requiring 5 or 6 refinement rounds—which might be solvable if given more budget—are abandoned, while tasks that are clearly hopeless after 2 rounds still consume 2 additional rounds before abandonment. The warm-up schedule exposes state information at fixed task counts (entities at 5, full inventory at 7, biome at 10, etc.) regardless of whether the agent has already demonstrated competence that would benefit from earlier exposure to this information.

**What evidence exists in the paper.** The paper does not directly address meta-learning or dynamic strategy adjustment. The fixed design choices are documented (4-round limit in Pseudocode 1, warm-up schedule in Table A.1) but never ablated or analyzed for optimality. The fact that tasks can be marked as failed and retried later (Section 2.1) provides a coarse form of adaptation (the agent doesn't repeatedly attempt the same impossible task indefinitely), but this is a binary succeed/retry-later mechanism, not a learned adjustment of strategy. The self-verification module provides task-specific critique (e.g., "Find and mine an amethyst shard underground") but this critique is task-scoped and not accumulated into broader strategic knowledge.

**Mitigation status.** Not directly mitigated. The paper's approach to exploration is implicitly "the curriculum will eventually propose diverse enough tasks that the agent will make progress," which relies on the assumption that the curriculum's diversity and situation-awareness are sufficient to overcome the lack of meta-learning. For the 160-iteration horizon, this appears to work. Whether it would continue to work over longer horizons—or whether the lack of meta-learning would cause the agent to repeatedly encounter the same failure modes—is unaddressed. The paper does not suggest future work on meta-learning or dynamic strategy adjustment, focusing instead on improving the underlying model capabilities and combining with gradient-based approaches.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

VOYAGER represents a **reframing of the lifelong learning problem for embodied agents** rather than a paradigm shift in the underlying algorithms. The individual components—LLM code generation, vector databases for retrieval, execution-guided refinement—existed before. What changes is the demonstration that these components, assembled in a specific architectural configuration with a sufficiently capable LLM (GPT-4), can produce sustained autonomous exploration and skill accumulation that qualitatively exceeds what simpler LLM-agent architectures achieve, and does so without any gradient-based training or model fine-tuning.

The conceptual shift is from **lifelong learning as weight-space optimization** (where the challenge is preventing parameter interference across tasks) to **lifelong learning as external memory management** (where the challenge is storing, indexing, and retrieving executable knowledge in a way that compounds rather than interferes). This is not entirely new—DreamCoder (Ellis et al., 2020) explored program library growth through wake-sleep learning—but VOYAGER demonstrates that the program library can be built through **in-context learning alone** when the underlying LLM is sufficiently capable. This substantially lowers the barrier to entry: no GPU clusters for RL training, no demonstration datasets, no hyperparameter tuning of learning rates. The "agent training loop" becomes a prompt engineering and API integration problem.

The paper also provides a **reconciliation mechanism for conflicting intuitions in the LLM-agent literature**. Prior work showed both that LLMs possess remarkable Minecraft knowledge (they can describe recipes, explain mechanics, strategize about progression) and that naive LLM agents fail at open-ended exploration (ReAct and Reflexion discover only 3–5 items in 160 iterations). VOYAGER's ablation results (Figure 9) diagnose the gap: the LLM's knowledge is a necessary but insufficient condition for sustained autonomous behavior. The missing ingredients are external scaffolding for goal-setting (automatic curriculum), memory (skill library), and closed-loop verification (iterative prompting with three feedback types). This reframes the research question from "can LLMs drive embodied agents?" to "what scaffolding turns LLM knowledge into sustained autonomous behavior?"—a more productive framing that opens specific engineering and design questions.

**Research directions that become more attractive:**

- **Scaffolding design for LLM-based agents**: The paper's ablation study provides a blueprint for which components matter and by how much. Future work can systematically vary scaffolding architectures (different retrieval mechanisms, different feedback types, different curriculum generation strategies) with the expectation that component-level improvements will translate to agent-level gains.
- **External memory as a first-class architectural component**: The skill library's dual role—as both persistent memory and in-context teaching aid—suggests that retrieval-augmented generation for agents is qualitatively different from retrieval for question-answering. The retrieved items are not just "facts to reference" but "subroutines to call" and "examples to imitate." This opens a research area at the intersection of retrieval-augmented generation and program synthesis.
- **Gradient-free agent learning for rapid prototyping**: VOYAGER's architecture can be adapted to new domains (with API documentation and control primitives) without any training, making it attractive for domains where collecting demonstration data or running RL is expensive or impractical. The gradient-free nature also means improvements to the underlying LLM automatically improve the agent—as demonstrated by the 5.7× gap between GPT-4 and GPT-3.5 (Figure 9, left).

**Research directions that become less attractive:**

- **Naive LLM agents without memory or curriculum**: The abysmal performance of ReAct and Reflexion (3–5 items in 160 iterations) makes a strong empirical case that simply prompting an LLM to "explore and discover items" with chain-of-thought reasoning is insufficient for sustained embodied behavior. Future work that proposes LLM agents for open-ended environments without some form of persistent memory and self-directed goal-setting now bears the burden of explaining why the VOYAGER baselines' failure does not apply.
- **Manual curriculum design for open-ended domains**: The manual curriculum ablation (Section 3.4, Figure 9, left) demonstrates that even a well-designed 10-step Minecraft progression underperforms the automatic curriculum dramatically. Given the effort required to design such curricula and their inability to adapt to the agent's situation, manual task sequencing for exploration-heavy domains is likely a dead end except for the simplest cases.

**Limits of the reframing.** The paper's approach is not a paradigm shift in the sense of replacing gradient-based learning. The dependence on GPT-4's code generation quality (5.7× drop with GPT-3.5) means the approach is currently **model-locked**: it works because GPT-4 happens to be very good at generating Minecraft JavaScript code. If GPT-4 had been trained on less Minecraft data, or if the task required capabilities GPT-4 lacks (precise spatial reasoning, long-horizon causal chains, novel tool use), the same architecture might fail regardless of scaffolding quality. The paper does not demonstrate that the scaffolding generalizes across models or domains—it demonstrates that the scaffolding amplifies GPT-4's existing Minecraft competence. The distinction matters for researchers deciding whether to invest in better scaffolding versus better models.

### Follow-Up Research This Work Enables

**1. Systematic scaling of the skill library: does retrieval quality degrade, and does the library become self-contradictory?** The paper evaluates retrieval accuracy at 309 skills (96.5% top-5, Table A.4) but does not characterize how accuracy changes as the library grows from 0 to 309, or what would happen at 1,000 or 10,000 skills. A concrete experiment: run VOYAGER for 1,000+ iterations, log retrieval accuracy at each library size, and fit a scaling curve. The hypothesis to test is whether retrieval accuracy asymptotes below 100% (due to embedding space saturation) or continues to degrade (due to semantic overlap between increasingly fine-grained skills). A second dimension: test whether the library accumulates **conflicting skills**—e.g., two different `smeltIron` implementations that make incompatible assumptions about fuel availability—and whether GPT-4 can resolve such conflicts when both are retrieved. The paper's skill library growth is currently monotonic (skills are added, never pruned or reconciled), which is unlikely to scale indefinitely. A negative result (retrieval accuracy collapses at ~500 skills) would bound the "lifelong" claim and motivate library maintenance mechanisms (deduplication, versioning, conflict detection).

**2. Cross-domain transfer of the scaffolding architecture to an environment where GPT-4 lacks detailed pre-trained knowledge.** The paper exploits GPT-4's Minecraft expertise for curriculum generation, code generation, and self-verification. An essential stress test: apply VOYAGER's architecture to a **procedurally generated environment with novel mechanics** that GPT-4 could not have seen during pre-training—for example, a custom Minecraft mod with new crafting recipes, new biomes, and new mobs, where the API documentation is provided in the prompt but the mechanics are not in GPT-4's training data. The experiment would measure: (a) whether the automatic curriculum can propose meaningful tasks when it cannot rely on memorized progression knowledge; (b) whether the self-verification module can judge task success without pre-existing knowledge of item names and crafting rules; (c) whether the skill library accumulates useful knowledge or becomes a collection of domain-irrelevant Minecraft heuristics. A positive result would demonstrate that the architecture works as a general exploration engine. A negative result would reveal that VOYAGER's success is largely due to GPT-4's domain-specific pre-training, and that truly novel environments require different mechanisms (e.g., explicit world-model learning, exploration bonuses).

**3. Combining VOYAGER's skill library with RL-based low-level control for perception-to-code end-to-end learning.** The paper explicitly notes that VOYAGER is "orthogonal and can be combined with gradient-based approaches" for 3D perception and sensorimotor control (Section 3.2). A natural integration: train a vision-language model (e.g., a fine-tuned PaLM-E or GPT-4V) to produce the structured state observations that VOYAGER currently receives from the Mineflayer API (inventory dictionaries, nearby block lists, entity names), while keeping VOYAGER's curriculum, skill library, and iterative prompting as the planning layer. The research question is whether the skill library—built through API-based exploration—can guide a pixel-based agent that must *perceive* the same items and entities the API previously provided directly. A concrete experiment: pre-train VOYAGER with API access to build a skill library, then deploy the agent in a version of Minecraft where it receives only pixels and must use a learned perception module to produce structured state for the planning layer. Measure: (a) whether the skill library transfers (can the agent recognize when a `mineBlock` skill is applicable based on visual input?); (b) whether the iterative prompting mechanism can correct perception errors (e.g., the perception module misidentifies a block, the skill fails, and the refinement loop corrects the misidentification).

**4. Dynamic budget allocation across task attempts: learning when to persist versus when to abandon.** VOYAGER uses a fixed 4-round refinement limit per task regardless of difficulty or progress trajectory. This is an unexplored optimization opportunity. A concrete improvement: train a lightweight classifier (or use a few-shot prompted GPT-3.5 call) to predict, after round 2 of refinement, whether the task is likely to succeed within the remaining budget. The classifier would use features such as: whether execution errors decreased between rounds 1 and 2, whether environment feedback shows progress toward subgoals (e.g., raw materials acquired even if the final craft failed), and the semantic similarity of the current task to previously succeeded skills. Tasks predicted to fail would be abandoned early, freeing budget for more promising tasks. Tasks predicted to succeed but requiring more refinement could be allocated additional rounds beyond the 4-round limit. The evaluation metric would be unique items discovered *per API call* (rather than per prompting iteration), directly addressing the unaccounted cost problem. This connects VOYAGER to the compute-optimal inference scaling literature, treating the per-task refinement budget as an adaptive resource rather than a fixed hyperparameter.

**5. Skill library compression and hierarchical indexing for genuine lifelong operation.** As the skill library grows, the prompt length for code generation increases (top-5 retrieved skills consume tokens) and retrieval latency increases (larger vector database). A practical scaling experiment: after accumulating 500+ skills, apply **hierarchical clustering** to group skills by semantic category (mining skills, crafting skills, combat skills, exploration skills) and index each cluster with a summary embedding. Retrieval would then be two-stage: first identify the relevant cluster, then search within that cluster. The research question is whether hierarchical indexing preserves the 96.5% top-5 accuracy of flat indexing while reducing computational cost. A second compression direction: **skill deduplication and library pruning**. As the agent learns multiple variants of similar skills (e.g., `smeltIron`, `smeltIronV2`, `smeltFiveRawIron`), the library accumulates near-redundant entries that may confuse retrieval. A deduplication experiment would measure: (a) what fraction of the 309-skill library is functionally redundant; (b) whether GPT-4 can be prompted to merge redundant skills into a single parameterized version (e.g., `smeltItem(itemName, fuelName, count)` generalizing from specific instances); (c) whether the merged library maintains or improves task-solving efficiency compared to the raw accumulated library.

**6. The role of the warm-up schedule: is gradual information disclosure necessary, or would full state access from the start outperform it?** The curriculum warm-up schedule (Table A.1) gradually adds state information (nearby entities at 5 tasks, full inventory at 7, biome at 10, health/hunger/time at 15). This design implies a hypothesis—too much information early distracts the curriculum agent, causing it to propose overly complex or inappropriate tasks—but this hypothesis is never tested. A clean ablation: compare the standard warm-up schedule against (a) full state access from iteration 0, and (b) no warm-up but with state information filtered by a GPT-3.5 relevance check (i.e., only include state information that GPT-3.5 deems relevant to the current task proposal). Measure both unique items discovered and the *appropriateness* of proposed tasks (e.g., what fraction of proposed tasks are completable within 4 refinement rounds). A null result (full state access performs equally well) would simplify the architecture. A positive result (the warm-up schedule is load-bearing) would motivate more sophisticated attention mechanisms for curriculum generation.

### Practical Applications and Downstream Use Cases

**1. Rapid game testing and content exploration for game developers.** Minecraft-style open-world games undergo extensive playtesting to ensure that crafting recipes work, tech tree progression is balanced, and all biomes contain appropriate resources. VOYAGER's architecture—with environment-specific control primitives and an automatic curriculum targeting "discover as many diverse things as possible"—could be adapted as an automated exploration tool. A game studio would provide the control API and a directive to explore, and VOYAGER would systematically attempt to craft every item, visit every biome, and interact with every entity, reporting which attempts succeeded and which failed (with execution traces). The 3.3× item discovery advantage over AutoGPT (Figure 1) and the ability to reach diamond-tier crafting (1/3 trials, Table 1) suggest that VOYAGER explores the crafting space more thoroughly than alternative LLM agents. The skill library would serve as a persistent record of discovered game content, and failed task attempts would highlight potential game balance issues (recipes that are too difficult, resources that are too scarce, progression bottlenecks). The cost-per-item-discovered would need to be reduced (GPT-4 API costs are currently high, Section 4), but for professional game development, the cost of automated exploration may compare favorably to human playtester hours.

**2. Bootstrapping training data for RL agents in new environments.** A major bottleneck in applying RL to complex embodied tasks is the need for demonstration data or carefully shaped reward functions. VOYAGER's skill library—accumulated through exploration—represents a collection of verified, executable programs that accomplish semantically meaningful tasks (mine wood, smelt iron, craft tools, fight mobs). These programs could serve as **demonstration trajectories** for training an RL policy: execute each skill in the environment, record the resulting sequence of low-level actions (through the Mineflayer API) and state observations, and use this dataset for behavioral cloning or offline RL. The 63 unique items and 309 accumulated skills (Appendix B.4.1, Table A.4) provide dense coverage of early-to-mid-game Minecraft activities. More importantly, because the skills are compositional (new skills call old ones as subroutines, as shown in Appendix A.4.3), the demonstrations would include hierarchical structure—high-level task completion decomposed into lower-level subroutines—which is valuable for training hierarchical RL policies. The key advantage over human demonstration collection is scalability: VOYAGER generates demonstrations autonomously, can be run in parallel across many Minecraft instances, and produces programs with explicit success verification rather than relying on human judgment of task completion. The cost is currently high (GPT-4 API), but if the resulting RL policy can eventually operate without GPT-4 at inference time, the upfront API cost may be justified by the downstream savings.

**3. Assistive agents for complex software with API documentation but no training data.** Many enterprise software systems—CAD tools, ERP systems, scientific laboratory automation platforms—have comprehensive API documentation but lack training corpora for building LLM-based assistants. VOYAGER's architecture can be adapted by: (1) replacing the Mineflayer control primitives with the target software's API functions, (2) replacing the Minecraft-specific curriculum directives with task directives relevant to the software domain (e.g., "create and modify 3D mechanical parts" for CAD, "process inventory transactions and generate reports" for ERP), and (3) providing API documentation in the code generation prompt. The agent would then explore the software's functionality, building a skill library of common operations and discovering edge cases (API functions that don't work as documented, parameter combinations that cause errors). The iterative prompting mechanism's three feedback types—environment feedback from API return values, execution errors from the runtime, and self-verification of task completion—would handle the discovery that real API behavior often diverges from documentation. The key transfer risk is that GPT-4's pre-training may not cover the specific software system, meaning the automatic curriculum and self-verification would need to rely on the provided API documentation rather than pre-existing knowledge. The paper provides no evidence about this transfer scenario, but the architecture's modularity (the curriculum, skill library, and iterative prompting are all prompt-based, not trained) makes such adaptation a prompt-engineering exercise rather than a retraining problem.

### When to Prefer This Method

The paper does not articulate explicit tradeoffs against named alternative agent architectures (e.g., "use VOYAGER when X, use DreamerV3 when Y")—it explicitly avoids direct comparison with RL-based Minecraft agents, positioning VOYAGER as orthogonal and potentially complementary (Section 3.2). The ablation results (Figure 9) provide component-level guidance (the automatic curriculum, skill library, and self-verification are each critical; GPT-4 is dramatically better than GPT-3.5 for code generation) but these are design recommendations for building VOYAGER-like systems, not decision rules for choosing between VOYAGER and alternatives. The paper's stated focus is on "pushing the limits of GPT-4 for lifelong embodied agent learning" (Section 3.2), not on establishing VOYAGER as the preferred approach in specified regimes. A forced decision matrix would therefore extrapolate beyond what the paper's experiments support.
