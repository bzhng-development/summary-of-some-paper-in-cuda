# SkVM: Revisiting Language VM for Skills across Heterogenous LLMs and Harnesses

**ArXiv:** [2604.03088](https://arxiv.org/abs/2604.03088)

## 🎯 Pitch

Over 100,000 AI agent skills exist, yet enabling a skill actually degrades performance on 15% of tasks and leaves another 17% unchanged. SkVM solves this by treating skills as code and LLMs as processors, compiling skills against a model’s primitive capabilities before execution to improve task completion by 15.3% while cutting token use by 40%.

---

## 1. Executive Summary

This paper introduces **SkVM**, a compilation and runtime system that treats skills—reusable, distributable knowledge packs for LLM agents—as code and LLMs as heterogeneous processors, enabling portable and efficient skill execution across different models and agent harnesses. Analyzing over 118,000 skills from two major distribution platforms and evaluating across eight LLMs (from Claude Opus 4.6 to Devstral Small) and three harnesses (BareAgent, OpenCode, OpenClaw) on SkillsBench and representative skill tasks, SkVM applies ahead-of-time compilation (capability-based compilation using 26 primitive capabilities, environment binding, and concurrency extraction) and just-in-time optimization (adaptive recompilation and code solidification) to adapt skills to specific targets. The system improves average task completion rates by 15.3% across models and harnesses while reducing token consumption by up to 40%, achieves up to 3.2× speedup through parallelism extraction, and delivers 19–50× latency reduction via code solidification—establishing that skills can be made portable across heterogeneous execution environments only when their implicit capability requirements, environment dependencies, and latent parallelism are explicitly analyzed and compiled before execution rather than passed as raw context.

## 2. Context and Motivation

### The Core Problem: Skills Are Portable in Name Only

The fundamental problem this paper addresses is that **skills—the dominant abstraction for composing LLM agent behavior—are distributed as though they are portable but behave as though they are not**. A skill is a self-contained knowledge pack: a structured file containing natural-language instructions, workflow descriptions, tool references, and bundled scripts that teaches an agent how to perform a specific class of tasks, such as merging PDFs, creating PowerPoint presentations, or debugging an incident response. Over 118,000 such skills exist across major distribution platforms (clawhub.ai and skills.sh), spanning data analysis, finance, office automation, and programming.

The promise of skills is that an agent can load one and immediately become more capable at a task—no fine-tuning, no retraining, just context injection. In practice, this promise breaks down when the same skill is deployed across different LLMs and different agent harnesses. The paper identifies three distinct failure modes that collectively undermine skill portability.

**Model mismatch (P1).** Skills carry implicit assumptions about what the model can do. When a PowerPoint-creation skill recommends PptxGenJS (a JavaScript library), it assumes the model can distinguish a library API from a command-line tool. Frontier models like Claude Opus 4.6 handle this without issue, achieving a perfect score on the task. But a weaker model like Devstral Small misreads PptxGenJS as a CLI and repeatedly executes incorrect shell commands, scoring 95 without the skill but only 45 with it loaded. This is not an isolated case. Across the eight models tested, enabling skills **degrades performance on 15% of tasks overall** (7% for Claude Opus 4.6, 25% for Qwen3-30B), leaves scores unchanged on 17% of tasks, and yields no improvement for at least one model on 87% of tasks. Recent independent work on the SWE-benchmark reached similar conclusions: 39 out of 49 skills showed no score improvement, and 3 skills experienced significant degradation.

**Harness mismatch (P2).** Agent harnesses—the runtime frameworks that sit between the model and the operating environment—provide different tool sets, different system prompts, and different context management strategies. The same model with the same skill can produce wildly different results depending on the harness. In one documented case, Gemini 3 Flash scores 100 on a workday-scheduling task on BareAgent (a minimal harness with only basic tools and a short system prompt), but 0 on OpenCode (a full-featured code agent harness). The failure occurs because OpenCode prepends extensive tool documentation to the context, which lengthens the combined prompt and triggers a malformed JSON key that makes the output unparseable. The skill was written without knowledge of how the harness shapes the model's context window, and the interaction between the two creates a failure that affects neither the model nor the harness in isolation. Across the heatmap in Figure 2, harness-induced variance is comparable in magnitude to model-induced variance.

**Environment mismatch (P3).** Skills have dependencies on external libraries, CLI tools, and system services, but the user's execution environment may lack them. Some skills list prerequisites, but those instructions are generic and target an idealized machine rather than the actual host. Other skills omit dependencies entirely. When a required package is absent, even strong models pay a cost: Claude Opus 4.6 still succeeds on every run when a library is missing, but generates 56–69% more output tokens because it must diagnose the mismatch and install the package at runtime. Weaker models suffer worse consequences. Qwen models drop to 33–67% success rates while generating 2–4× more output tokens on failed workarounds. Every missing dependency becomes a repeated tax on both correctness and efficiency across all invocations of the skill.

### Why This Problem Matters

The fragility of skill execution matters for reasons that go beyond a single benchmark. Skills represent a bet on a particular vision of how AI agent capabilities will scale: rather than training monolithic models that know everything, the ecosystem is moving toward **composable, distributable knowledge packs** that can be mixed and matched per task. This vision is already being adopted across the industry. Anthropic's Claude platform treats skills as a first-class abstraction. Cursor, Google Antigravity, and the Coze platform have all converged on similar skill mechanisms. The Agent Skills Initiative has published an open specification (SKILL.md) to standardize skill portability across platforms. Over 100,000 skills have been authored and shared, and the number is growing.

If skills are to fulfill their role as the agent-era equivalent of shared libraries or packages, then their portability cannot depend on the assumption that the executing model and harness match the author's development environment. The problem is structural: skills are authored once (typically by a human developer using a frontier model on a specific platform), but executed many times (by different users with different models on different machines). This **author–executor asymmetry** mirrors the classical compile-once, run-anywhere motivation behind the Java Virtual Machine and other language VMs, but with a crucial difference—in the agent era, the "processor" is an LLM whose capabilities vary dramatically, and the "operating system" is a harness whose tool surface and context management strategies are similarly heterogeneous.

The three failure modes interact combinatorially. A skill that needs adaptation along one dimension (say, a weak model on a rich harness) may need a completely different adaptation when two dimensions change together (the same weak model on a minimal harness). The adaptation space cannot be covered by a fixed set of rewrite rules. Without a systematic approach, skill portability remains a brittle, best-effort property that works for the strongest models on well-provisioned environments and fails silently for everything else.

### Prior Approaches and Their Shortcomings

The current state of skill execution—what the paper calls **interpreted execution**—is to load the raw skill text into the agent's context and pass it to the model with no preprocessing. This is the analogue of feeding source code directly to a processor without compilation. It is simple and universal (any agent that accepts text can load any skill), but it leaves every adaptation burden on the model at runtime. The model must parse the skill's instructions, figure out what tools and dependencies it needs, adjust its own behavior to follow the prescribed workflow, and recover from mismatches when its assumptions turn out wrong. This works when the model is powerful enough to do all of that implicitly; it fails when the model is not.

**Skill-Creator (Anthropic's optimization tool).** The only existing attempt at systematic skill improvement is Anthropic's Skill-Creator, a tool that uses Claude Opus 4.6 to rewrite and optimize a skill's instructions. Skill-Creator improves on raw unoptimized skills in some cases but has two fundamental limitations. First, it optimizes for a single target—the model that does the optimizing—and does not adapt to different models or harnesses. A skill optimized by Claude Opus 4.6 is still optimized for Claude Opus 4.6; when loaded by Qwen3-30B or Devstral Small, its assumptions about model capabilities may still be wrong. Second, Skill-Creator operates purely at the prompt level, restructuring instructions without addressing environment dependencies or parallelism opportunities. In the evaluation (Figure 10), Skill-Creator improves over the original skill baseline but consistently underperforms SkVM's target-aware compilation, with the gap widening substantially for weaker models. For Qwen3-30B on BareAgent, SkVM-optimized skills improve over Skill-Creator by 25%.

**The broader landscape of agent optimization.** Outside of skill-specific tooling, general approaches to improving LLM agents—better prompting, chain-of-thought, reflection, multi-agent debate, tool-use training—treat the model or the task as the unit of optimization but do not treat the skill as a first-class artifact that needs compilation. These approaches either assume a fixed model and optimize the task description, or assume a fixed task and optimize the model through fine-tuning. Neither addresses the cross-target portability problem that arises when a skill is authored in one context and executed in another.

**Fine-tuning as an alternative.** One could argue that skill execution failures on weaker models should be addressed by fine-tuning those models to better follow skill instructions. The paper does not directly evaluate this alternative, but several observations point to why fine-tuning alone is insufficient. First, skills are designed to be lightweight, composable, and distributable—the promise is that new capabilities can be added without weight modification. If every new skill requires fine-tuning, the economic and operational model changes fundamentally. Second, fine-tuning addresses model mismatch but not harness or environment mismatch; a fine-tuned model will still encounter context-window conflicts from verbose harness system prompts and will still fail when runtime dependencies are missing. Third, skills evolve over time (authors update instructions, add new workflows), and keeping fine-tuned models synchronized with skill versions creates a deployment coordination problem that skill-level compilation avoids.

### How This Paper Positions Itself

The paper draws an explicit analogy between the evolution of programming abstractions and the current state of AI agent skills (Figure 1). In classical computing, the progression from assembly language to high-level languages to managed runtimes (compilers, linkers, the JVM) was driven by the need to make code portable across heterogeneous hardware and operating systems. Each step in that progression introduced a new layer of abstraction that separated *what the program means* from *how it executes on a specific target*.

The paper's thesis is that **skills are the natural-language analogue of code in the agent era**, and that the agent ecosystem needs the equivalent of a compiler and runtime—a system that can analyze a skill's implicit requirements, map them to the capabilities of the target model and harness, and generate a specialized form that executes reliably and efficiently. This positions SkVM not as a prompt optimization tool or a fine-tuning method, but as **infrastructure**: a persistent system component that sits between skill distribution and skill execution, doing for skills what the JVM does for Java bytecode or what AOT compilation does for native binaries.

The paper also positions itself against the prevailing narrative that skills "just work" or that their failures are minor edge cases. The large-scale analysis of 118,000 skills and the controlled experiments across eight models and three harnesses are designed to establish that the problem is **quantitative and structural**, not anecdotal. The 15% degradation rate, the 87% of tasks where at least one model sees no benefit from a skill, and the 39-of-49 skills that showed no improvement on SWE-benchmark provide evidence that current interpreted execution is failing at scale.

The paper's positioning is also temporal: skills are proliferating rapidly, and without compilation infrastructure, the ecosystem will accumulate fragile, target-dependent skills whose portability degrades as the diversity of models and harnesses grows. Building that infrastructure now—defining primitive capabilities, developing compilation passes, establishing runtime optimization mechanisms—lays the groundwork for skills to fulfill their architectural promise rather than becoming another layer of brittle prompt engineering.

## 3. Technical Approach

### 3.1 Reader Orientation

SkVM is a compilation and runtime system that processes skills—the natural-language knowledge packs that teach LLM agents how to perform tasks—before they are loaded into an agent, transforming them from raw, target-agnostic text into optimized variants specialized for the specific model, agent harness, and execution environment that will run them. The system solves the problem that skills carry implicit assumptions about model capabilities, available tools, and runtime dependencies that are frequently violated when the executing target differs from the author's development environment, by introducing a classical compiler pipeline (AOT analysis, target profiling, optimization passes, JIT monitoring, and runtime scheduling) adapted to the unique challenge that the "source code" is unstructured natural language and the "hardware" is a heterogeneous population of LLMs with varying capabilities.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components arranged in a pipeline from installation time to execution time, shown in Figure 5:

1. **AOT Compiler (Install Time)** — executes three sequential passes over every skill after it is installed but before any task invokes it: **Pass 1 (Capability-Based Compilation)** measures the gap between what the skill demands and what the target (model + harness) provides, then applies compensation or substitution transforms; **Pass 2 (Environment Binding)** extracts a dependency manifest from the optimized skill and generates an idempotent setup script that checks and repairs missing libraries, CLI tools, and services; **Pass 3 (Concurrency Extraction)** decomposes the skill's procedural structure into a workflow DAG and rewrites the skill to expose data-level, instruction-level, and thread-level parallelism.

2. **Target Profiler (Offline)** — runs once per (model, harness) pair before any skills are installed, executing microbenchmarks to measure each target's proficiency across 26 primitive capabilities (each with multiple proficiency levels), producing a capability profile that is cached and reused across all subsequent skill compilations for that target.

3. **Runtime (Execution Time)** — receives a task, selects the skill variant compiled for the current (model, harness) pair, executes the environment-binding script to verify runtime dependencies, then loads the variant into the agent through the standard progressive disclosure mechanism, making multiple variants invisible to the agent.

4. **JIT Optimizer (Runtime Background)** — operates on top of normal execution in two sub-components: **Adaptive Recompilation** monitors execution outcomes across invocations, detects systematic capability gaps that the AOT compiler missed, and recompiles the skill with aggregated failure logs and self-recovery traces as input; **Code Solidification** watches LLM-generated code across invocations, identifies structurally recurrent patterns whose only variation is input parameters, and promotes them into callable functions that bypass LLM inference entirely after a confidence threshold is reached.

5. **Resource-Aware Scheduler (Runtime)** — bridges the compile-time parallelism annotations from Pass 3 and run-time system conditions by dynamically monitoring CPU, memory, and API rate limits, throttling sub-agent launches, and selectively suspending running sub-agents when resource pressure exceeds a threshold, while recording effective concurrency from previous runs as hints for future executions.

Information flows as follows: a developer authors and distributes a skill → the user installs the skill into SkVM → the AOT compiler reads the raw skill text, consults the cached capability profile for the target, and produces one or more optimized skill variants plus environment-binding scripts → a task arrives at runtime → the runtime selects the appropriate variant and executes the binding script → the agent executes the task with the optimized skill while the JIT optimizer monitors outcomes and the resource-aware scheduler manages parallelism → if systematic failures are detected, the adaptive recompiler triggers a new compilation cycle using failure logs → for recurrent code patterns, code solidification gradually promotes LLM-generated code to native functions.

### 3.3 Roadmap for the Deep Dive

- **First**, the primitive capability system (§4.1.1–4.1.2), which is the foundational abstraction that enables the compiler to reason about model–skill gaps without embedding target-specific knowledge. Understanding how primitive capabilities are defined, how they are organized into proficiency levels, how skills' requirements are extracted, and how targets are profiled is essential because every other compilation pass depends on this gap analysis.
- **Second**, the three capability-aware transform strategies—compensation, substitution, and omission (§4.1.3)—and the gap analysis algorithm that selects among them. This is the core compilation logic that adapts the skill's natural-language instructions to the target's profiled capabilities.
- **Third**, the environment binding pass (§4.2), which resolves the dependency problem (P3) by shifting environment setup from the model's runtime reasoning loop to a pre-execution script, eliminating a major source of token waste and failure for weaker models.
- **Fourth**, the concurrency extraction pass (§4.3), which recovers latent parallelism from the skill's procedural structure by constructing a workflow DAG and mapping parallel opportunities to three granularities (DLP, ILP, TLP), including how the compiler selects concurrency primitives based on what the harness supports.
- **Fifth**, the runtime's JIT optimization mechanisms (§5.2), including the adaptive recompilation pipeline (failure detection, log aggregation, targeted recompilation, rollback) and the three-stage code solidification pipeline (AOT candidate generation, runtime signature matching, promotion to callable functions).
- **Sixth**, the resource-aware scheduler (§5.3), which bridges the static parallelism annotations from AOT compilation and the dynamic conditions at execution time, including the monitoring, throttling, and suspension mechanisms and the use of historical concurrency hints from prior runs.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems paper** whose core idea is that skills—natural-language programs for LLM agents—require a compilation and runtime infrastructure analogous to classical language VMs to achieve portability across heterogeneous targets, and that this infrastructure can be built by decomposing the portability problem into independent optimization passes (capability adaptation, environment binding, concurrency extraction) that each operate on a shared representation of the skill's requirements expressed in terms of primitive capabilities.

#### Primitive Capabilities: A Shared Vocabulary for Skill Requirements and Target Proficiency

The central difficulty in making a skill portable is that the skill's instructions are written in natural language, while the target's strengths and weaknesses are implicit in its training data and architecture. There is no type system, no formal specification of what an instruction like "use python-pptx to create a presentation" actually requires the model to be able to do. The compiler needs an **intermediate representation**—a vocabulary that both sides can be translated into—so that the gap between what the skill demands and what the target can provide becomes measurable and actionable.

**Definition and design principles.** A primitive capability is an indivisible unit that describes one basic ability a target must possess to complete a task defined by a skill. The paper defines 26 primitive capabilities organized into four categories (generation, reasoning, tool use, and instruction following), guided by three design principles:

- **Composability:** any concrete task within a skill must be expressible as a combination of primitive capabilities. This ensures the vocabulary has enough expressive power to cover the skill corpus without gaps.
- **Generality:** each primitive capability must be broad enough to appear across many skills, keeping the total set small and the compiler's workload bounded. If a capability appeared in only a handful of skills, the profiling cost would not amortize.
- **Semantic independence:** a primitive capability concerns structural correctness rather than whether the output is insightful or well-argued. This distinguishes what the compiler optimizes (can the model execute the right tool with the right arguments?) from what it cannot (is the model's generated content high-quality?).

The key design choice is that primitive capabilities are defined **purely from the demand side**—from the perspective of what skills require—rather than from the supply side of what models are known to do well. This is analogous to how JVM bytecodes define what operations a program can request without encoding knowledge of which specific CPU instructions will satisfy them on a given hardware platform.

**Derivation process.** The capability set was derived from a corpus of 15,063 skills (the subset of the 118,000-skill dataset with more than 100 downloads per skill) through a two-stage process. In the first stage, the authors curated 50 representative skills spanning document generation, script execution, data analysis, and code development, and used LLM-assisted analysis guided by the three design principles to decompose them into an initial set of 19 primitive capabilities. Each primitive capability was manually reviewed against the three principles. In the second stage, the authors validated the initial set against the full 15,063-skill corpus by checking whether each skill's requirements could be expressed as a combination of the existing primitives. Skills that could not be covered revealed missing capabilities, and a missing capability was added to the set only when it appeared in at least 1% of the corpus—a frequency threshold that filters out rare or domain-specific requirements while ensuring sufficient coverage. This process converged on 26 primitive capabilities that cover the requirements of 95% of the skills.

**Proficiency levels.** The authors observed that different tasks demand the same primitive capability at different depths. For example, `gen.code.shell` might require only basic commands (`ls`, `cat`) in one skill (a file-organizing task) but require complex pipelines with `sed` and `awk` in another (a log-parsing task). A model that can handle the former may still fail on the latter. To capture this, each primitive capability is divided into multiple proficiency levels (L1, L2, L3, and in some cases more), with each higher level representing a strictly deeper use of the capability. An L3 requirement cannot be satisfied by L2 ability. Table 1 shows representative examples from the full catalog: `tool.exec` progresses from single-command execution (L1) through parameterized commands with relative paths (L2) to chained multi-step execution (L3); `follow.procedure` progresses from three sequential steps (L1) through five-to-seven steps with branches (L2) to loops with verification (L3).

**Level calibration and validation.** The proficiency level hierarchy is not assumed to be correct a priori. The authors validate it by generating a suite of microbenchmarks for each level and evaluating them across different models. If a model succeeds on higher-level microbenchmarks while failing on lower-level ones for the same primitive capability, the authors interpret this inconsistency as evidence that the level hierarchy is miscalibrated—the L3 benchmark might actually be easier than the L2 benchmark for that particular model, suggesting the level definitions need revision. The level definitions are then revised and the evaluation repeated. This calibration step ensures that the level hierarchy is empirically meaningful rather than merely plausible, which is critical because the compiler relies on the hierarchy to decide whether compensation (bridging a small level gap) or substitution (switching to an entirely different capability path) is appropriate.

**Representative primitive capabilities.** Table 1 in the paper provides examples that illustrate the four-category structure:
- `gen.code.shell` (generation): L1 covers basic commands like `ls` and `cat`; L2 covers pipes, redirection, and loops; L3 covers complex pipelines with `sed` and `awk`.
- `reason.arithmetic` (reasoning): L1 covers single-step operations; L2 covers multi-step sequences; L3 covers compound arithmetic expressions.
- `tool.exec` (tool use): L1 covers single-command execution; L2 covers parameterized commands with relative file paths; L3 covers chained multi-step tool execution.
- `follow.procedure` (instruction following): L1 covers sequences of three sequential steps; L2 covers five to seven steps with conditional branches; L3 covers loops with verification steps.

The full catalog of 26 primitives is not exhaustively listed in the paper, but the four-category organization with representative examples establishes the structure: every skill's requirements can be decomposed into a vector of (primitive, required_level) pairs, and every target can be profiled into a vector of (primitive, attained_level) pairs, enabling a direct gap computation.

#### Target Profiling: Measuring What a Model–Harness Pair Can Do

The compiler needs a **capability profile** for the target—a mapping from each primitive capability to the highest proficiency level the target can reliably achieve. This profile is generated once per (model, harness) pair, cached, and reused for all subsequent skill compilations on that same target.

**Profiling procedure.** For each primitive capability and each proficiency level, the paper generates a suite of microbenchmarks—small, self-contained tasks that isolate the specific capability at the specific level. A microbenchmark for `gen.code.shell` L2 might ask the model to write a shell command that pipes the output of one command through `grep` and redirects to a file. A microbenchmark for `tool.exec` L2 might ask the model to execute a tool with a relative file path. The model's success or failure on each microbenchmark determines whether it has attained that level for that capability. The profiling is performed when the user sets up the agent and model, meaning it is an initial one-time cost that does not recur per skill or per task.

**Profiling cost.** The paper measures the overhead of a full profile across all 26 primitive capabilities on two small models (Figure 13). For Devstral Small, profiling completes in 7.3 minutes and costs $0.033. For Qwen3-30B, profiling takes 31.1 minutes and costs $0.079. The cost is broken down by category (Generation, Reasoning, Tool Use, Instruction), with Generation and Tool Use dominating the duration for Qwen3-30B (approximately 750 and 250 seconds respectively out of the 31.1 minutes total). This profiling cost is amortized across all skills subsequently compiled for that target. If a user installs ten skills for the same model–harness pair, the per-skill profiling overhead is roughly one-tenth of these figures—and decreases further with each additional skill.

**What the profile captures.** The profile is specific to the (model, harness) pair, not just the model alone. This is critical because the harness affects what the model can accomplish. A harness that provides batch tool dispatch enables instruction-level parallelism that a sequential-only harness cannot; a harness with extensive system prompts may consume context-window space and interfere with the model's ability to follow long procedures. By profiling the pair rather than the model in isolation, the compiler accounts for the interaction effects documented in Figure 2, where the same model on different harnesses produces substantially different results.

#### Skill Requirement Extraction: Decomposing Instructions into Capability Demands

On the demand side, the compiler must extract the skill's **capability requirements**—the set of (primitive, required_level) pairs that the skill implicitly demands. This extraction happens at skill installation time as part of AOT compilation.

**Decomposition process.** The compiler reads the raw skill text and decomposes it into concrete tasks using LLM-assisted analysis. Each task is then mapped to the primitive capabilities it requires, including the proficiency level. For example, a PDF-processing skill that instructs the model to "use pdfplumber to extract tables, then use pypdf to merge the output" might decompose into requirements for `gen.code.python` at L2 (to write the pdfplumber and pypdf code), `tool.exec` at L2 (to execute the scripts with the correct file paths), and `follow.procedure` at L2 (to follow the multi-step workflow of extract-then-merge).

**Handling alternative implementation paths.** During requirement extraction, the compiler also identifies equivalence classes—alternative combinations of primitive capabilities that could achieve the same goal through different paths. For instance, a task that requires creating a data visualization might be achievable via `gen.code.python` with matplotlib (one capability path) or via `gen.code.javascript` with D3 (another capability path). These equivalence classes are identified during requirement extraction and stored with the skill's capability specification. They become the options that the substitution transform can select from when the primary path's capabilities are not met by the target.

**Coverage validation.** The 26-primitive-capability set was validated to cover 95% of the 15,063-skill corpus. The remaining 5% of skills represent cases where the current capability vocabulary is insufficient—possibly because those skills require domain-specific capabilities (e.g., knowledge of a specialized API, domain-specific reasoning patterns) that do not meet the 1% frequency threshold for inclusion. For these uncovered skills, the compiler falls back to passing the raw skill through without capability-based adaptation, relying on the other compilation passes (environment binding, concurrency extraction) and the runtime's JIT mechanisms to provide whatever improvements they can.

#### Gap Analysis and Transform Selection: The Core Compilation Logic

With the skill's capability requirements and the target's capability profile in hand, the compiler computes the gap between them and selects an optimization strategy per requirement. This is the core compilation logic that produces the adapted skill variant.

**Gap computation.** For each (primitive, required_level) pair extracted from the skill, the compiler looks up the target's profiled level for that same primitive. Three cases are possible:

- **Target meets or exceeds the requirement** (profiled_level ≥ required_level): no gap exists. The skill's instructions for this capability are left unchanged.
- **Target is below the requirement but above zero** (1 ≤ profiled_level < required_level): a **compensable gap** exists. The model has some proficiency in this capability but not enough to handle the skill's demands as written.
- **Target lacks the capability entirely** (profiled_level = 0, or the capability is not in the profile because the model consistently fails at even L1): an **uncompensable gap** exists. The model cannot execute the primary path. The compiler must substitute an alternative capability path if one exists, or else the skill will execute with this requirement unresolved (and likely fail).

**Transform selection algorithm.** The compiler walks through each capability requirement and selects one of three transforms based on the gap:

1. **Compensation** is preferred whenever the gap is compensable. The compiler identifies the distinctions between the required level and the profiled level for this primitive capability—what specific sub-ability does the model lack that prevents it from bridging the gap? It then transforms the skill's instructions to reduce the effective requirement from the higher level to the lower one. This can take the form of providing examples (showing the model exactly what a correct execution looks like, rather than assuming it can infer), making instructions more explicit (replacing implicit assumptions with explicit steps), strengthening constraints (adding guardrails that prevent the model from wandering into failure modes it cannot recover from), or decomposing complex steps into simpler sub-steps that individually fall within the model's attested capability range. Compensation preserves the skill's original intent because it still uses the same primary capability path; it only adjusts the level of detail and scaffolding.

2. **Substitution** is the fallback when compensation is not viable: the target lacks the capability entirely (profiled_level = 0), or the level gap is too large for compensation to bridge reliably. The compiler switches to one of the alternative implementation paths identified during requirement extraction—an equivalence class that achieves the same goal using different capabilities that the target does possess. For example, if a skill requires `gen.code.python` at L3 for a pandas-based data analysis workflow but the target only reaches L1, the compiler might switch to an SQL-based path if the target's `gen.code.sql` reaches L2. The compiler selects the substitution path whose capabilities best match the target's profile, which may require evaluating multiple equivalence candidates.

3. **Omission** applies when neither compensation nor substitution is viable for a given capability requirement because the target lacks all paths that could satisfy it. The requirement is effectively dropped from the compiled skill variant, with the understanding that the corresponding part of the task will either be handled differently by the model at runtime (if it can improvise) or will fail. The paper does not detail the frequency of omission, but the coverage of 95% of the skill corpus by the 26 primitive capabilities suggests it is relatively rare.

**The compilation output.** After applying the selected transforms to every capability requirement in the skill, the compiler produces an **optimized skill variant**—a modified version of the original skill text whose instructions are now aligned with the target's profiled capabilities. This variant is stored per target. If compensation was applied to (say) the `tool.exec` requirement, the variant might include explicit instructions for resolving file paths rather than assuming the model can do so. If substitution was applied, the variant replaces the original capability path with the alternative one. The compiled variant is what the runtime loads when a task arrives, not the original skill.

**Case Study: PPTX creation (Figure 6).** The paper provides a concrete walkthrough of capability-based compilation on a real skill that teaches an agent to create PowerPoint presentations using `python-pptx`. The skill requires five primitive capabilities: `gen.code.python` at L3 (to write python-pptx code, which is a third-party library), `tool.exec` at L2 (to execute the script with relative file paths), `reason.planning` at L1 (to plan slide layouts), `gen.text.structured` at L1 (to generate slide content), and `follow.procedure` at L2 (to follow the multi-step create-and-save workflow). The target is a mid-tier model on the OpenCode harness. The profile shows that the target matches four of the five requirements directly but provides `tool.exec` only at L1, while the skill requires L2—a one-level gap. The compiler identifies a possible substitution path: switching to PptxGenJS via `gen.code.javascript` would replace `python-pptx` and lower the `tool.exec` requirement to L1, eliminating the gap. However, because the `tool.exec` gap is only one level, the compiler prefers compensation over substitution. The L2 profiling results reveal that this specific model fails specifically at resolving relative file paths when executing commands—it can handle the rest of L2 tool execution but gets confused by relative paths. The compiler injects absolute path resolution into the compiled skill, replacing relative file paths with absolute paths to the skill directory. The result is a variant that still uses `python-pptx` (preserving the skill's original intent, which is preferred) but no longer exposes the model to the relative-path failure mode it cannot handle.

#### Environment Binding: Resolving Dependencies Before the Model Sees the Skill

The second pass of AOT compilation addresses the environment mismatch problem (P3): skills have dependencies on external libraries, CLI tools, and system services that may not be present on the user's machine. Leaving dependency resolution to the model at runtime—as interpreted execution does—turns every missing dependency into a repeated tax on correctness and efficiency. The paper's experimental data (Figure 4) shows that when a required library is absent, even a strong model like Claude Opus 4.6 generates 56–69% more output tokens diagnosing and installing the dependency, while weaker Qwen models drop to 33–67% success rates and generate 2–4× more output tokens on failed workarounds.

**Design principle: shift environment setup from runtime reasoning to pre-execution scripting.** The core insight of environment binding is that the model should not be responsible for diagnosing and repairing its execution environment. The compiler knows what the skill needs; the hosting system knows what is installed. Reconciling the two is a deterministic matching problem, not a reasoning problem. By solving it before the skill is loaded, the compiler eliminates the environment-related failure modes that dominate the model mismatch taxonomy.

**Dependency manifest extraction.** The compiler first extracts a **dependency manifest** from the output skill of the first compilation pass (capability-based compilation) and from any explicit prerequisites listed in the original skill. The manifest covers three categories: external libraries (Python packages, JavaScript modules, system libraries), CLI tools (executables invoked via shell commands), and system services (daemons, API endpoints, network services the skill expects to be available). For each manifest entry, the compiler runs a lightweight presence check at installation time—for example, `pip show` for Python packages, `which` for CLI tools—to determine whether the dependency is already satisfied.

**System-aware probing.** When the presence check fails (the dependency is not found), the compiler performs deeper, **system-aware probing** to determine how to resolve the dependency on the specific host. The probing considers the current operating system, hardware architecture, installed package managers, and version constraints. This is not generic advice like "install pdfplumber"; it is host-specific resolution that accounts for whether the machine runs macOS or Linux, whether `pip` or `conda` is the package manager, and what version constraints exist. The paper describes this as using a "built-in env-binding skill"—effectively, the compiler itself uses a skill (treating the compiler as an agent specialized for this task) to reconcile the skill's declared dependencies against the actual host environment.

**Idempotent env-binding script.** The output of environment binding is an **idempotent shell script** that checks for each required dependency and, if missing, installs or configures it. The script is idempotent because it runs before every skill execution (not just at installation time), which means it must correctly handle the case where dependencies are already satisfied (the check passes and the install step is skipped). The script is generated by the compiler, not written by the skill author. When the environment changes (e.g., a package is uninstalled between skill invocations), the script detects the change and repairs the dependency.

**Execution timing and fallback.** The env-binding script executes at **runtime, before the skill context is loaded into the agent**, as part of the skill registration and execution sequence described in Section 5.1. If the script executes successfully, the model never sees the dependency problem—it simply encounters an environment where everything it expects is present. If the script itself fails (e.g., because a package repository is unreachable or a version conflict cannot be resolved), execution falls back to the model: the script's output (including error messages) is passed to the model as additional context, and the model takes over the diagnosis and repair process. This fallback ensures that environment binding is strictly an optimization—it cannot introduce new failures, only eliminate existing ones when it succeeds.

**Validation (Figure 14).** The paper evaluates environment binding on two tasks (pdf-create and document-xlsx) across three models, comparing three configurations: a complete environment where all dependencies are pre-installed, a deps-removed environment where required libraries are deliberately absent, and an env-bound environment where the env-binding script is applied to the deps-removed environment. The results show that for the strongest model (Claude Opus 4.6), env-bound performance returns to complete-environment levels in terms of correctness (100% average score), while also substantially reducing output tokens and execution duration compared to the deps-removed baseline (where the model had to diagnose and install the missing package itself). For the weakest model (Qwen3.5-122B), env-bound fully restores execution correctness from near-zero to complete-environment levels, and reduces both token consumption and duration below the complete-environment baseline—suggesting that even in a fully provisioned environment, the model benefits from the script's explicit setup because it eliminates token-consuming verification reasoning.

#### Concurrency Extraction: Recovering Parallelism from Sequential Prose

The third AOT pass identifies parallel execution opportunities that are present in the skill's logical structure but hidden by its sequential natural-language description. The paper reports that 76% of the 15,063 classified skills contain explicit procedural structure: numbered steps, conditional branches, and data dependencies between steps. These multi-step workflows are described in sequential prose, but not every step actually depends on the one before it. Many steps operate on independent data or invoke independent tools, and can be executed concurrently if the compiler can extract the dependency information and the harness supports parallel dispatch.

**Workflow DAG construction.** The compiler uses LLM-assisted analysis to decompose the skill into discrete steps. For each step, it identifies what inputs the step consumes and what outputs it produces. It then builds a **workflow DAG** (directed acyclic graph): nodes are steps, and a directed edge from step A to step B exists when B consumes an output of A. Steps with no edges between them are independent and can, in principle, execute concurrently. Figure 7 illustrates this on an incident-response skill: the original prose describes a five-step sequential process (search error reports in Jira, collect logs from each server, debug the backend service, debug the database layer, write a combined incident report), but the DAG reveals that Jira search (S1), log collection (S2), and the two independent debug tasks (S3, S4) have no data dependencies—the report-writing step (S5) is the only step that depends on outputs from the others. The DAG exposes parallelism that the sequential prose obscured.

**Within-step analysis.** In addition to between-step dependencies, the compiler also analyzes each step internally for sub-operations that can proceed concurrently. A single step that says "collect logs from each server" might be executed sequentially (ssh to server A, collect, ssh to server B, collect, ...) but actually applies the same operation to multiple independent data items—a classic data-parallel pattern. A single step that says "run code-analysis, lint-checker, and dependency-audit on the project" invokes multiple independent tools with no data dependencies between them. The compiler identifies both kinds of within-step parallelism.

**Three levels of parallelism.** For each parallel opportunity—whether between steps or within a step—the compiler selects one of three concurrency primitives based on the task structure and what the target harness supports:

**Data-Level Parallelism (DLP).** A single step applies the same operation to multiple independent data items. The compiler rewrites the step to process items concurrently using language-level parallelism primitives appropriate to the skill's implementation: shell-level parallel execution (e.g., `xargs -P` to parallelize a command across multiple inputs), Python's `multiprocessing`, or JavaScript's `Promise.all`. In Figure 7, the log-collection step (S2) is identified as DLP because it runs the same collection command on each server independently. The compiler rewrites it to use `xargs -P` with bash parallel execution, mapping the DLP opportunity to a single shell command rather than multiple sequential commands. DLP requires no special harness support—it operates entirely within the language runtime of the skill's implementation language.

**Instruction-Level Parallelism (ILP).** Multiple independent steps each need a tool call with no data dependency between them. The compiler groups the corresponding DAG nodes into one parallel stage and rewrites the skill so that their tool invocations are issued together in a single LLM turn, rather than one after another in sequential prose. This is the compiler analogue of VLIW (Very Long Instruction Word) architectures: the compiler identifies independent operations and packs them into a single "issue slot" for the agent. The compiler annotates the skill with metadata specifying which step outputs should be bound back to which downstream DAG inputs after the batch completes. ILP requires the harness to support **batch tool dispatch**—the ability to execute multiple tool calls in a single agent turn rather than requiring a separate turn per call.

**Thread-Level Parallelism (TLP).** The workflow decomposes into independent sub-tasks that each require multi-turn reasoning—not just a single tool call but an entire agent loop (reason → act → observe → reason → ...). The compiler rewrites the skill to extract each sub-task into a separate **sub-agent block** with an explicit task description, declared input context (what information from the parent workflow the sub-agent needs), and an expected output specification (what the sub-agent must produce for the parent to consume). The annotation marks this block for sub-agent dispatch, so the runtime spawns one sub-agent per block in its own independent session and merges the returned outputs back into the DAG at the appropriate dependency point. In Figure 7, the two debug tasks (S3: debug backend, S4: debug database) are independent, multi-turn reasoning tasks; the compiler extracts each into a TLP sub-agent block and annotates them for parallel dispatch. TLP requires harness support for **sub-agent spawning**—the ability to fork independent agent sessions that run concurrently and communicate results back to the parent.

**Fallback and harness-awareness.** Opportunities whose required primitive is unavailable on the target harness fall back to sequential execution. For example, if a harness does not support batch tool dispatch, ILP opportunities are not exposed in the compiled variant—the compiler emits sequential instructions instead. If a harness does not support sub-agent spawning, TLP opportunities fall back to sequential. The compiler's output is therefore not a single parallelized skill but a **harness-specific variant** that exposes only the parallelism the target harness can actually execute.

**Compilation output format.** For each viable parallel opportunity, the compiler either rewrites the skill's natural-language instructions to execute items concurrently (for DLP, where the parallelism is expressed in code syntax) or emits **execution annotations** that mark the parallel structure without rewriting the instructions (for ILP and TLP, where the parallelism requires harness support). For ILP, the annotation is a parallel-stage marker over a group of DAG nodes. For TLP, the annotation is a sub-agent task block with declared input contracts (what context to pass) and output contracts (what result to return). The runtime reads these annotations and dispatches them using the corresponding harness primitive—batch tool calls for ILP, sub-agent sessions for TLP—while the agent itself sees the skill's instructions with the parallel structure made explicit.

#### Adaptive Recompilation: JIT Optimization Based on Runtime Failure Patterns

AOT compilation handles gaps that can be detected statically from the capability profile, but some problems only surface at execution time. The model's actual behavior on a specific skill may reveal capability gaps that the profiling microbenchmarks did not capture—the microbenchmarks are isolated probes, while the skill exercises capabilities in combination and under the constraints of a full agent loop with tool outputs, observations, and context accumulation. The **adaptive recompilation** mechanism addresses this by treating execution outcomes as a signal for iterative skill improvement.

**Failure monitoring and log structure.** The runtime tracks the outcome of every task executed with a skill. When a skill execution fails—defined as the agent aborting, the task returning an incorrect result, or receiving human feedback indicating failure—the runtime records a **structured failure log**. This log captures what went wrong (the specific error or incorrect behavior), at what step of the workflow it occurred, and what context the model had at that point. When the model performs self-correction through reflection (the agent loop detects an error and retries with a corrected approach), the runtime also records the **self-recovery trace**: what the model changed in its subsequent attempt and whether the correction succeeded.

**Systematic vs. task-specific failures.** Not every failure warrants recompilation. Some failures are task-specific—the model happened to make an error on a particular input, but the skill's instructions are sound. Others are **systematic**—the same failure pattern repeats across different task instances, indicating that the skill's instructions assume a capability the model consistently lacks or that a particular instruction is consistently misinterpreted. The adaptive recompiler distinguishes these cases by aggregating failure logs across multiple invocations of the same skill. Only when a failure pattern repeats across distinct tasks does the runtime trigger recompilation, because task-specific failures are better handled by the model's own reflection loop than by modifying the skill.

**Recompilation process.** When a systematic failure is detected, the runtime feeds the accumulated failure logs and the model's self-recovery traces as input to the capability-based compilation pass (the same compiler that performed AOT compilation). The compiler uses this richer signal—real execution data rather than only microbenchmark results—to apply targeted compensation transforms to the skill. The compensation is more precise than AOT compensation because it targets the specific failure pattern rather than the general capability gap. For example, if the profiled gap was `tool.exec` L2 → L1 (a one-level gap that AOT compensation addressed by adding absolute path resolution), but the runtime reveals that the model also consistently fails on a specific edge case (e.g., paths with spaces or special characters), the recompilation can add explicit examples or guardrails for that edge case.

**Rollback mechanism.** Recompilation is not guaranteed to help. The compiler may over-correct, introducing new instructions that confuse the model or create new failure modes. The paper documents a concrete regression case: in the Line Chart task during staged optimization (Figure 11), the JIT compiler added an example file to the skill that was too long and triggered parsing errors, causing the score to drop. To handle this, the runtime maintains a **performance record** for each compiled variant. After recompilation, it compares the new variant's performance (task completion rate, failure frequency) against the previous variant. If the recompiled variant performs worse, the runtime **rolls back** to the previous version. Each subsequent recompilation starts from the best-performing variant observed so far—this is a hill-climbing strategy where the compiler only advances when it can demonstrate improvement, and regressions are immediately reversed.

**Iterative improvement.** The adaptive recompilation process is iterative. After a recompiled variant is deployed, the runtime continues monitoring its execution outcomes. If new failure patterns emerge (or old patterns persist because the compensation was insufficient), a second round of recompilation is triggered, building on the failure logs accumulated since the first recompilation. Figure 11 shows this iterative effect across up to three JIT rounds: after one JIT round, 8 of 14 skill categories achieve full scores on the evaluation tasks; after three rounds, 10 of 14 do so. The iterative process is bounded by the model's fundamental capability ceiling—some skills may never achieve full scores on a given model regardless of how many compensation rounds are applied, because the model simply lacks the underlying capability at any level—but the adaptive mechanism ensures that the skill converges to the best form achievable for the target.

#### Code Solidification: JIT Promotion of Recurrent Code Patterns to Native Functions

The second JIT mechanism addresses a different kind of optimization opportunity: reducing the computational cost of executing skills by eliminating redundant LLM inference. The paper reports that 75% of skills contain **solidifiable code**—code fragments (shell commands, API call patterns, script snippets) whose overall structure is fixed, varying only in input-specific parameters. In normal interpreted execution, the LLM re-executes the full reasoning and code-generation cycle every time the skill is invoked, even when the generated code is structurally identical to what it generated on the previous invocation. This wastes tokens and latency on a process whose output is predictable.

**The three-stage pipeline (Figure 8).** Code solidification proceeds through an offline analysis stage (performed once at AOT compilation time), a validation stage (spanning multiple runtime invocations), and a promotion stage (after a confidence threshold is reached):

**Stage 1: AOT Candidate Generation.** The AOT compiler analyzes code and script segments within each skill to identify whether they contain parameterized patterns eligible for solidification. Not every code fragment qualifies. The compiler looks for fragments where the code structure is invariant across task instances—the sequence of operations, the API calls, the control flow are the same, and only the specific arguments (file names, search terms, format options) change. For each eligible segment, the compiler generates a **JIT candidate** containing four components:

- **Keywords:** a set of terms that filter relevant invocations. When a task arrives, the runtime checks whether the task's description or context contains these keywords to determine whether the solidified code is applicable. For example, a weather-current skill's JIT candidate might have keywords like `weather`, `current`, `temperature` to match tasks requesting current weather data.
- **Code signature:** a pattern (implemented as a regular expression) that captures the expected output structure of the code the LLM generates. This is the match pattern that the runtime uses to determine whether the LLM's generated code is structurally consistent with the template. For a PDF-merge skill, the code signature might match the pattern `from pypdf import PdfWriter` followed by `add_page` calls and a `write` call.
- **Code template:** the parameterized code skeleton itself, with slots for the variable parameters. For the weather skill, the template might be a `curl` command with placeholders for the city name, output format, and API key.
- **Parameter schema:** a description of the extractable arguments—what parameters the code expects, their types, and how to extract them from the task context. For the weather skill, the schema might specify that `city` is extracted from the task prompt, `format` defaults to JSON if not specified, and `api_key` is read from an environment variable.

The AOT compiler bundles these JIT candidates with the compiled skill variant, so they are available at runtime without further analysis.

**Stage 2: Runtime Validation and Signature Matching.** When the skill is invoked, the runtime monitor watches the LLM's code generation outputs. For each invocation, it first checks the task's keywords against the JIT candidate's keyword set—a cheap filter that avoids the overhead of signature matching for irrelevant invocations. If the keywords match, the runtime extracts the LLM-generated code and matches it against the code signature. A match occurs when the generated code's structure conforms to the expected pattern: the same imports, the same function calls in the same order, the same control flow, differing only in parameter values.

The critical design choice is the **promotion threshold**: code solidification is triggered only after the code signature matches successfully across **multiple consecutive invocations**. This is the gate that prevents incorrect promotion. If the model generates code that diverges from the expected pattern (e.g., it uses a different library, a different API pattern, or a different control flow because the task context is slightly different), the signature does not match, the counter resets, and the system stays on the safe LLM path. Only when the model consistently produces the same code structure across distinct invocations—indicating that the pattern is genuinely recurrent and the LLM's behavior is predictable—does the system promote the template. The paper illustrates this safety mechanism with the weather-forecast task (Figure 15b): the AOT compiler identified a candidate for solidification, but at runtime the model generated code in multiple different formats depending on the specific forecast parameters requested, so the code signature never consistently matched across invocations, and the candidate was never promoted. This prevented the system from replacing flexible LLM generation with a rigid template that would have produced incorrect results for some forecast formats.

**Stage 3: Promotion and Instantiation.** When the promotion threshold is reached, the code template is instantiated into a **callable function**. The instantiation step is lightweight and mechanical—the AOT compiler already did the analysis; the runtime only needs to wrap the template code with parameter extraction logic (parsing the task context using the parameter schema to extract the arguments) and output handling (returning the result in the format the agent expects). The instantiated function can be a standalone shell script, a Python function, a JavaScript module, or any executable form appropriate to the skill's implementation language. The paper describes the instantiation as producing a "standalone shell script or code function" that bypasses the LLM entirely.

Once promoted, subsequent invocations of the skill that trigger the same code pattern do not call the LLM at all. The runtime extracts parameters from the task context, calls the instantiated function with those parameters, and returns the result directly to the agent harness as if the LLM had executed a tool call and returned the observation. From the agent's perspective, the execution is indistinguishable from normal tool use—the agent reasons about the task, issues what it believes to be a code-generation step, and receives the result—but the code generation step is handled by the solidified function rather than by the model.

**Fallback and safety.** The paper explicitly addresses the correctness risk of solidified code execution: what happens if the instantiated function produces a wrong result or encounters a runtime exception? SkVM implements a **fallback mechanism**: if solidified code execution causes the agent task to fail (the agent's subsequent steps produce an error because the solidified code's output was incorrect or the function raised an exception), the runtime re-enables LLM-based code generation for that pattern. The promotion is not permanent; it is a soft optimization that is reversed when it causes correctness regressions. This is analogous to a JIT compiler deoptimizing a compiled method when a runtime assumption (e.g., about the monomorphic type of a receiver) is violated.

**Quantified results (Figure 15).** The paper evaluates code solidification on four cases from two skills: weather-current, weather-forecast, PDF-extract, and PDF-merge. For the two PDF tasks, despite variations in task inputs (different PDF files, different extraction queries), the LLM-generated code consistently matched the code signature. After promotion (the dashed line marks the promotion point in Figure 15), solidified execution achieves dramatic speedups: PDF-extract goes from 10,469–15,116 ms of LLM inference to 206–568 ms of native code execution, a **19–50× latency reduction**. PDF-merge achieves similar orders of magnitude. For weather-current, the solidified code calls an external weather API, so the speedup is bounded by network latency—execution drops from approximately 9,000 ms to 2,000 ms, a **~5× improvement**. For weather-forecast, as discussed above, the code signature never consistently matches across invocations because the model uses flexible formats, so no invocations are promoted—all eight invocations rely on LLM generation. This case validates that the promotion gate effectively prevents premature or incorrect solidification.

#### Resource-Aware Parallel Scheduling: Bridging Static Parallelism and Dynamic Conditions

Pass 3 of AOT compilation identifies where parallelism is possible, but whether that parallelism is actually efficient depends on conditions that change at run time. A skill that the compiler marked for TLP with four sub-agents might execute perfectly when the system has idle CPU cores and available API rate-limit budget, but cause contention, throttling, or out-of-memory errors when those resources are scarce. The compiler cannot predict the runtime resource state, so the scheduling decision must be made dynamically.

**Monitoring dimensions.** The resource-aware scheduler continuously monitors three dimensions of system state that affect parallel execution viability:

- **API-bound workloads:** for skills that make external API calls (weather services, web search, third-party tools), the scheduler watches response latencies and HTTP 429 (rate limit) signals. If response times increase or rate-limit errors appear, it indicates that the current level of API concurrency is unsustainable.
- **Compute-bound workloads:** for CPU-intensive skills (data processing, code analysis, document generation), the scheduler monitors CPU utilization and memory usage.
- **Execution history:** the scheduler records the **effective concurrency** of each skill from its previous run on the current system—not the maximum parallelism the compiler extracted, but the actual number of parallel workers that executed successfully without contention. This history is used as a **concurrency hint** for subsequent executions of the same skill on the same system.

**Throttling and suspension mechanisms.** When resource pressure rises above a configurable threshold, the scheduler applies two mechanisms to reduce contention, applied in priority order:

1. **Throttling new sub-agent launches.** Before spawning each TLP sub-agent, the scheduler checks current resource pressure. If pressure is high, the launch is deferred—the sub-agent is queued rather than immediately started, reducing the number of concurrently active agents. This is a soft backpressure mechanism that prevents the system from adding more load when it is already saturated.

2. **Selective suspension of running sub-agents.** If throttling new launches is insufficient (existing sub-agents are already consuming too many resources), the scheduler can **suspend** a subset of running sub-agents—pausing their agent-loop execution rather than killing them. The suspension is selective: the scheduler chooses which sub-agents to suspend based on per-agent resource usage (suspend the most resource-intensive sub-agents first) or launch order (suspend the most recently launched sub-agents, on the assumption that earlier sub-agents have made more progress). A suspended sub-agent retains its state (conversation history, tool outputs, current reasoning context) and can be resumed when resource pressure subsides. This is analogous to OS process suspension, applied at the granularity of agent loops rather than CPU instructions.

**Concurrency hints from history.** After each skill execution completes, the scheduler records the effective concurrency level—how many sub-agents actually ran in parallel without triggering throttling or suspension. On the next execution of the same skill on the same system, the scheduler uses this recorded value as a starting concurrency limit, reducing the need to rediscover the system's capacity through trial and error. If system conditions have changed (e.g., other processes are consuming resources, making the previously effective concurrency level now too aggressive), the monitoring mechanisms will still detect pressure and reduce concurrency further as needed. The hint is advisory, not a hard limit.

## 4. Key Insights and Innovations

### Innovation 1: Skills as Compilable Code — A Category Shift from Prompt Engineering to Systems Infrastructure

The paper's most fundamental intellectual move is not any specific compilation pass but the **category shift** it enacts: treating skills not as prompts to be optimized but as **source code that requires compilation before execution**. This reframing transforms the skill portability problem from a prompt-engineering concern (can we write better instructions?) into a systems-infrastructure concern (can we build a compiler and runtime that adapts instructions to heterogeneous targets?). 

Prior to this work, the dominant paradigm was what the paper calls **interpreted execution**: skills are authored as natural-language documents, distributed as plain Markdown, and loaded into the agent's context with no preprocessing. The only systematic optimization tool, Anthropic's Skill-Creator, operates purely at the prompt level—it rewrites instructions to be clearer or more structured—but fundamentally treats the skill as text destined for direct model consumption. This is the agent-era equivalent of feeding C source code directly to a CPU without a compiler, relying on the CPU to figure out the target-specific optimizations at execution time. It works when the processor is powerful enough (frontier models) but fails when it isn't, and it fails unpredictably because the adaptation burden is invisible.

SkVM's reframing makes the adaptation burden **explicit and mechanical**. By drawing the analogy to the JVM and classical compilation pipelines (Figure 1), the paper argues that the agent ecosystem needs the same architectural separation that made software portable across hardware: a representation of *what the program means* (the skill's capability requirements expressed in primitive capabilities) that is independent of *how it executes on a specific target* (the compiled variant tailored to the model–harness pair). This is not a prompt-writing technique; it is a claim about **where in the system stack portability must be enforced**. The paper's evidence for the necessity of this shift is the 15% degradation rate when skills are used as raw context, the 87% of tasks where at least one model sees no benefit, and the 39-of-49 skills that showed no improvement on SWE-benchmark in independent work—all of which indicate that interpreted execution is failing at scale, not in edge cases.

The significance of this reframing extends beyond the specific compilation techniques SkVM introduces. It establishes a **new layer in the agent system stack**—a skill compilation and runtime layer that sits between skill distribution platforms and agent harnesses, analogous to how language VMs sit between compiled code and operating systems. This layer has its own abstractions (primitive capabilities), its own optimization passes (AOT compilation, JIT optimization), its own safety mechanisms (rollback, fallback), and its own resource management (parallel scheduling). By demonstrating that this layer can be built and that it produces substantial, measurable improvements (15.3% average score improvement, 4× token reduction, 3.2×–50× speedups), the paper makes a case that skill compilation is not an optimization but **infrastructure**—something the agent ecosystem needs to fulfill the portability promise that skills implicitly make.

This is a fundamental shift, not an incremental refinement, because it changes what skills *are*: from static text to compiled artifacts with target-specific variants. It also changes the author–executor contract: skill authors no longer need to anticipate every model and harness their skill will run on; they express requirements in terms of primitive capabilities, and the compiler handles the mapping. This is the same contract that C compilers provide to programmers who don't need to know the target CPU's instruction set.

---

### Innovation 2: Primitive Capabilities as an Intermediate Representation — Making Model–Skill Gaps Measurable

The paper's second distinctive contribution is the concept of **primitive capabilities as an intermediate representation** for skill compilation. Prior work on model evaluation (AgentBench, SWE-Bench, SkillsBench) measures what models can do on aggregate benchmarks, producing scalar scores or task-completion rates. But these benchmarks don't provide the kind of structured, composable capability profile that a compiler needs. A score of 75 on a benchmark tells you the model is imperfect; it doesn't tell you *which specific abilities are missing* or *at what proficiency level the model starts to fail*, which is what a compiler must know to decide between compensation and substitution.

The primitive capability system solves this by establishing a **shared vocabulary** that both the skill's requirements and the target's abilities can be translated into. The 26 primitive capabilities with multiple proficiency levels create a **capability vector**—a structured description of what a target can do—that is:
- **Composable**: any skill's requirements can be decomposed into combinations of these primitives (validated on 95% of the 15,063-skill corpus).
- **General**: each primitive appears across many skills, so the profiling cost amortizes.
- **Semantically independent**: each primitive concerns structural correctness (can the model execute the right tool with the right arguments?) rather than output quality (is the content insightful?), establishing a clean boundary for what the compiler can and cannot optimize.

The key design insight is that primitive capabilities are defined **purely from the demand side**—from what skills require—rather than from the supply side of known model behaviors. This is analogous to how JVM bytecodes define operations a program can request without encoding which CPU instructions will satisfy them. It makes the vocabulary extensible as the skill corpus grows (the paper describes an iterative process for adding capabilities when uncovered skills exceed a 1% frequency threshold) and target-agnostic (the same capability vocabulary applies to any model on any harness).

The proficiency levels add a second dimension that is conceptually significant. The observation that the same capability (`tool.exec`, `gen.code.shell`, `follow.procedure`) is demanded at different depths by different skills, and that a model may satisfy one level but not the next, creates a **graded capability space** rather than a binary has/doesn't-have space. This gradation is what makes compensation possible: if the gap were binary (the model either has `tool.exec` or it doesn't), the only options would be substitution or failure. With levels, the compiler can bridge small gaps (L2 → L1) through targeted instruction modifications while reserving substitution for large or complete gaps. The validation that levels are empirically meaningful—by checking that models don't pass higher-level microbenchmarks while failing lower-level ones—is a calibration step that distinguishes this from arbitrary difficulty labels.

This is a fundamental conceptual contribution, not an incremental evaluation technique, because it creates a new **type system for skills**. Just as programming languages use type systems to make implicit constraints explicit and checkable by tools, primitive capabilities make the implicit assumptions in natural-language skill instructions explicit and checkable by a compiler. The 26-capability vocabulary is not presented as final or complete; it is presented as the first iteration of what could become a standard capability specification that skill authors target and that compiler builders implement—analogous to the role that bytecode specifications play in language VM ecosystems.

---

### Innovation 3: The Diagnosis That Portability Failures Are Combinatorial, Not Unidimensional

The paper's third insight is a **diagnostic contribution**: the demonstration that skill execution failures arise from the interaction of three independent axes (model, harness, environment) that vary combinatorially, not from any single axis in isolation. This is not obvious from prior work, which typically studies model capability (AgentBench), harness design (SWE-Agent), or environment dependencies separately, but never their interaction under a shared skill.

The heatmap in Figure 2 provides the empirical evidence for this diagnosis. The same skill on the same model produces different scores across harnesses (Gemini 3 Flash: 100 on BareAgent vs. 0 on OpenCode for workday-scheduling), and the same skill on the same harness produces different scores across models (the PPTX-creation skill on OpenCode: 100 for Claude Opus 4.6 vs. 0 for Devstral Small). The heatmap shows that harness-induced variance is comparable in magnitude to model-induced variance—a finding that challenges the implicit assumption in most agent research that the model is the dominant variable and the harness is a transparent conduit.

The theoretical significance of this diagnosis is that it explains **why prompt-level optimization cannot solve the portability problem**. Prompt optimization (including Skill-Creator) operates on one axis (the skill text) and implicitly targets one model. But if the failure arises from an interaction—a verbose harness system prompt interacting with a model's context-window behavior to cause malformed JSON—then optimizing the skill text for one (model, harness) pair doesn't guarantee portability to another pair. The adaptation space is combinatorial: a skill that needs one adaptation for (weak model, rich harness) may need a different adaptation for (weak model, minimal harness) because the harness's tool surface changes what the model must do independently. A fixed set of rewrite rules cannot cover this space.

This diagnosis has practical implications for how skill platforms and agent frameworks should evolve. It suggests that skill portability cannot be achieved by standardizing skill formats (the SKILL.md specification) or by optimizing skill content (Skill-Creator); it requires an intermediate layer—SkVM's role—that can **independently profile each axis and compose the adaptations**. It also explains why the skill ecosystem's long-tailed distribution (89% of skills on skills.sh have fewer than 86 downloads) may persist: if skills only work reliably for the author's specific (model, harness, environment) combination, their value to other users is limited.

This is a diagnostic innovation, not a methodological one. It establishes the **problem structure** that a compilation-based solution must address. It also connects to a broader pattern in systems research: the recognition that interaction effects between independently varying components create complexity that cannot be managed by optimizing each component separately, and that systematic infrastructure (compilers, schedulers, resource managers) is needed to handle the composition.

---

### Innovation 4: Verifying That Test-Time Skill Adaptation Is Bounded by Model Capability — Not a Universal Fix

The paper's fourth contribution is a **negative result with positive implications**: the demonstration that skill compilation fundamentally cannot help on tasks where the base model's capability is zero, and that its benefits are concentrated in the regime where the model has *some* capability but not enough to execute the skill reliably as written. This is a boundary-condition finding that distinguishes SkVM from claims that better prompting or better skill design can compensate for arbitrary model weaknesses.

The evidence for this boundary is distributed across the evaluation. In the compilation effectiveness heatmap (Figure 9), the strongest gains from SkVM optimization appear for weaker models (Qwen3-30B, Devstral Small) and on harder harnesses (OpenClaw), where the baseline performance with original skills is low but non-zero—the model has some capability, but the skill's assumptions push it into failure modes. For frontier models (Claude Opus 4.6, DeepSeek V3.2) on well-matched skills, SkVM provides modest accuracy gains but substantial efficiency gains (token reduction up to 40%, Figure 12)—the model can already execute correctly, but compilation eliminates the overhead of diagnosing mismatches and recovering from errors.

In the staged optimization breakdown (Figure 11), the pattern is starker: in 11 of 14 skill categories, the original skill performs *worse than using no skill* with Qwen3-30B on BareAgent—the skill is actively harmful because its instructions lead the model into failure modes it wouldn't encounter if it followed its own judgment. After AOT compilation, the average task score improves by 88%, and after three JIT rounds, 10 of 14 categories achieve full scores. This demonstrates that the model had the capability all along—the skill's instructions were the obstacle. But the 4 categories that didn't reach full scores even after three JIT rounds indicate the existence of a capability ceiling that compilation cannot breach.

This finding has important implications for how the community thinks about skill authorship and distribution. It suggests that skills should not be evaluated in isolation (as a generic quality metric) but **relative to a specific target's capability profile**—a skill that is excellent for Claude Opus 4.6 may be harmful for Qwen3-30B, and the difference is measurable and systematic. It also suggests that the 15% degradation rate when skills are loaded (Section 2.4) is not evidence that skills are poorly written, but evidence that interpreted execution exposes models to instructions they cannot follow, and that compilation can close most of this gap. The finding is fundamentally a **localization of the problem**: skill failures are not primarily about model capability or skill quality in isolation, but about the **gap** between them, which is what compilation addresses.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The evaluation uses SkillsBench (Li et al., 2026) and PinchBench, extended by the authors to cover 118 tasks spanning code generation, data analysis, document creation, and system administration. Each task is paired with at least one skill sourced from Anthropic-skills, OpenClaw skills, or skills.sh. For each task across all experiments, the authors generate **five diverse input instances** and measure the average across them, meaning each reported score in the heatmaps represents the average of five independent runs per task per condition. The evaluation suite combines static analysis and LLM-based assessment against predefined criteria, following the evaluation methodology of SWE-bench (Jimenez et al., 2024) and MT-Bench (Zheng et al., 2023).

- **Base models.** Eight LLMs spanning three capability tiers are evaluated: **SOTA tier** — Claude Opus 4.6 and DeepSeek V3.2; **Mid-tier** — Gemini 3 Flash, Qwen3.5-397B, Qwen3.5-122B, and Claude 3.5 Haiku; **Small tier** — Qwen3-30B and Devstral Small. The tiered selection is deliberate: it tests whether SkVM's compilation benefits scale inversely with base model capability (i.e., whether weaker models gain more from skill adaptation because they suffer more from the model–skill mismatch the compiler addresses). The models span closed-source frontier systems (Claude, Gemini, DeepSeek), open-weight large models (Qwen3.5 family), and small open-weight models (Qwen3-30B, Devstral Small), providing coverage across both capability and accessibility dimensions.

- **Metrics.** Three metrics are reported: (1) **Task completion rate** (or "score"), measured as the average correctness score across five diverse input instances per task, assessed by automated static analysis and LLM-based evaluation against predefined criteria—this is the primary metric throughout and is the value displayed in cell labels in Figures 9 and 11; (2) **Token consumption**, measured as the total input plus output tokens consumed during agent execution, reported as a relative reduction percentage in Figures 12 and 14; (3) **End-to-end execution latency**, measured as wall-clock duration in milliseconds for individual invocations (Figures 13, 15, 16), used to evaluate parallelism speedup and code solidification latency reduction. The paper does not report standard deviations or confidence intervals for any metric—only means are given.

- **Baselines.** Three baselines are compared: (1) **No Skill** — the agent executes the task without any skill loaded, measuring the model's raw task capability; (2) **Original** — the agent executes with the original, unmodified skill loaded as raw context, representing the current interpreted-execution baseline that the paper critiques; (3) **Skill-Creator** — the skill is optimized using Anthropic's Skill-Creator tool (using Claude Opus 4.6 as the optimizer), representing the only existing systematic skill optimization approach. Skill-Creator optimizes skills purely at the prompt level and targets a single model (the optimizer), making it a relevant but fundamentally different baseline from SkVM's multi-target compilation approach.

- **Agent harnesses.** Three harnesses are evaluated: **BareAgent** — a minimal custom harness that injects the compiled skill directly into the system prompt with only basic read, write, and exec tools, providing the simplest possible execution environment; **OpenCode** — a full-featured code agent harness with batch tool dispatch capabilities and a rich tool set for code execution; **OpenClaw** — a general-purpose agent harness with integrated functional modules designed for complex multi-step task execution. These three harnesses span a range of complexity and tool surfaces, allowing the evaluation to test whether SkVM's compilation benefits generalize across harness designs and whether the harness-induced variance documented in Figure 2 is reduced by compilation.

- **Generation budget / compute accounting.** The paper does not use a uniform generation budget constraint across experiments. Different experiments measure different resources: the skill compilation effectiveness experiments (Figures 9, 10) compare at fixed task instances (five per task) regardless of token consumption; the token efficiency analysis (Figure 12) reports actual token consumption per execution; the parallelism speedup experiments (Figure 16) report wall-clock time; and the code solidification experiments (Figure 15) report per-invocation latency in milliseconds. There is no FLOPs-matched comparison or compute budget controlled across methods—the comparisons are at the task level, measuring whether SkVM raises completion rates and reduces costs relative to baselines on the same tasks. This is appropriate for a systems paper optimizing execution efficiency, but it means the paper does not answer the question "given a fixed compute budget, does SkVM outperform baselines?"—the experiments answer "on the same tasks, does SkVM produce higher success rates and lower costs?"

- **Cross-validation / statistical protocol.** The paper does not employ cross-validation or statistical significance testing. The evaluation methodology consists of running each task–skill–model–harness configuration on five diverse input instances and averaging the results. For the staged optimization breakdown (Figure 11), different task instances are used in each JIT round ("tasks used in each round are of the same type but differ in contents"), but there is no held-out evaluation split or cross-validation to ensure that JIT optimization does not overfit to the specific task instances. The adaptive recompilation mechanism (§5.2.1) uses a rollback mechanism based on observed performance rather than held-out validation, which is pragmatic for online optimization but does not provide statistical guarantees. For the skill compilation effectiveness heatmap (Figure 9), the same tasks are used for both baseline evaluation and SkVM evaluation, meaning there is no independent test set—the improvements shown are on the same task instances used during compilation. This is a meaningful limitation for assessing generalizability, though it is partially mitigated by the use of five diverse input instances per task.

### Main Quantitative Results

#### Skill Compilation Effectiveness Across Models and Harnesses (Figure 9, Figure 10)

**Headline result.** SkVM-optimized skills improve task completion rates over the original unoptimized skills across all eight models and three harnesses, with an average improvement reported as 15.3% (from the abstract) and with the largest absolute gains concentrated on weaker models and on the most complex harness (OpenClaw). For Qwen3-30B on BareAgent, SkVM-optimized skills improve over the Skill-Creator baseline by 25 percentage points. Compiled skills reduce regression rates from 15% (original skills) to 4.5% of tasks.

**Detailed findings from Figure 9.** The compilation effectiveness heatmap displays task completion rates (cell values) and score deltas relative to the original skill baseline (cell colors: green for improvement, red for regression) across 20 tasks, eight models, and three harnesses. Several patterns emerge:

- **Weaker models benefit more.** For Devstral Small on BareAgent, the heatmap shows numerous green cells where original performance was 0–45 and SkVM-optimized performance reaches 85–100. For Claude Opus 4.6, most cells are already at 85–100 with the original skill, so SkVM improvements appear as modest per-task gains but substantial token savings (documented separately in Figure 12). The tier gradient is visible: SOTA models show mostly small green improvements (many cells already at ceiling), while Small-tier models show dramatic green improvements from very low baselines.

- **Harness complexity matters.** The OpenClaw harness, which provides the richest tool surface and most complex execution environment, shows the largest gaps between original and SkVM-optimized skills. On OpenClaw with Qwen3-30B, tasks like PDF Merge, Weather Travel, and File Dedup show original scores of 0 that rise to 85, 75, and 68 respectively after compilation. This supports the paper's diagnosis that harness-induced complexity interacts with model capability to create failures that compilation can address by adapting the skill to the specific harness context.

- **The 4.5% regression rate.** Compared to the 15% of tasks where the original skill degrades performance relative to no-skill (Section 2.4), SkVM-compiled skills reduce this regression rate to 4.5%. This is a key validation that compilation primarily removes harmful skill–model mismatches rather than introducing new ones, though the 4.5% residual indicates that even compiled skills can occasionally be counterproductive—possibly in cases where the compiler's transforms introduce new failure modes that the AOT analysis did not anticipate.

**Aggregated scores (Figure 10).** Averaging across all tasks for each model–harness combination, SkVM-optimized skills achieve the highest score in every single combination. The improvement over the Skill-Creator baseline grows with decreasing model capability: for Qwen3-30B on BareAgent, SkVM improves over Skill-Creator by approximately 25 points (from roughly 50 to roughly 75); for Devstral Small on BareAgent, the improvement is approximately 10 points (from roughly 55 to roughly 65). For the strongest models (Claude Opus 4.6, DeepSeek V3.2), SkVM-optimized skills achieve scores comparable to the original and Skill-Creator baselines (all near ceiling), with the primary benefit being token reduction rather than accuracy improvement.

**Cross-harness variance reduction.** Using the original skill, OpenCode and OpenClaw differ by up to 13 points depending on the model—harness behavior alone materially changes outcomes. SkVM optimization raises scores on both harnesses and reduces this cross-harness gap to at most 5 points. This is direct evidence that capability-based compilation addresses harness mismatch (P2) by adapting the skill to the specific harness context, making skill execution more consistent across execution environments.

---

#### Staged Optimization Breakdown (Figure 11)

**Headline result.** On Qwen3-30B with BareAgent across 14 skill categories, 11 of 14 categories show the original skill performing *worse than no skill*, with an average score improvement of 88% after AOT compilation alone. After one round of JIT optimization, 8 of 14 categories achieve full scores; after three rounds, 10 of 14 do so. JIT optimization can introduce regressions—documented in the D3 Line Chart task—but the iterative rollback mechanism eventually corrects them.

**AOT-only improvement.** The most striking finding in Figure 11 is the baseline degradation: in 11 of 14 skill categories (PDF Merge, Feed Digest, Git Branch Ops, SQL Query, Parallel WC, D3 Line Chart, Data Report, Regex Extract, Data Clean, Batch Rename, and several others denoted only by category name), the original skill performs *worse* than using no skill at all—the blue "Orig" bars are lower than the gray "None" bars. For example, in the SQL Query category, the no-skill baseline achieves a score of roughly 60, the original skill drops to roughly 30, and AOT compilation raises it to roughly 85. This pattern reinforces the paper's central argument that skills, when loaded as raw context without compilation, can be actively harmful for weaker models because their instructions lead the model into failure modes it would not encounter if it followed its own reasoning.

After AOT compilation (the orange "AOT" bars), the average score across all 14 categories improves by 88% relative to the original skill baseline. Several categories that were at 0 with the original skill (Data Report, Regex Extract, Data Clean, Batch Rename) rise to 50–100 after AOT compilation alone. This indicates that capability-based compilation and environment binding resolve the majority of model–skill mismatches without requiring runtime feedback.

**JIT iterative improvement.** The paper reports up to three rounds of JIT optimization (JIT.1, JIT.2, JIT.3), with each round using different task instances of the same type. After JIT.1, 8 of 14 categories achieve full scores (100). The categories that do not reach 100 after JIT.1 include D3 Line Chart (which regresses), Data Report (which improves but not to 100), FJSP Schedule (remains low), Economic Dispatch (remains moderate), and File Organize (improves partially). After JIT.3, 10 of 14 categories achieve full scores, with Data Report, Economic Dispatch, FJSP Schedule, and File Organize remaining below 100—indicating a capability ceiling that even iterative compilation cannot breach.

**Documented regression and recovery.** The D3 Line Chart task provides the paper's clearest example of JIT-induced regression followed by recovery. The JIT.1 round added an example file to the skill, but the file was too long and triggered parsing errors, causing the score to drop below the AOT-only level. After subsequent rounds of revision guided by prior failure logs, the JIT compiler removed the problematic example and the score recovered. This validates the rollback mechanism described in Section 5.2.1: the runtime tracks whether a recompiled variant performs better or worse, and rolls back when performance degrades.

#### Token and Cost Efficiency (Figure 12, Figure 14)

**Headline result.** For most model–harness combinations, SkVM compilation simultaneously improves task success and reduces token consumption. The strongest model and weakest harness pairing (DeepSeek V3.2 + BareAgent) achieves token savings approaching 40%. For weaker models, SkVM may occasionally consume additional tokens because it enables longer successful execution traces rather than short failure traces—but this additional cost comes with substantially higher task completion rates.

**Score-token tradeoff visualization (Figure 12).** Figure 12 plots each (model, harness) pair as a point on a two-dimensional plane: the x-axis shows token reduction (as a percentage, with negative values indicating SkVM uses more tokens), and the y-axis shows score improvement (in percentage points). The plot is divided into four quadrants: upper-right = better quality and fewer tokens (the ideal); upper-left = better quality but more tokens; lower-left = worse quality and more tokens; lower-right = worse quality but fewer tokens.

Most points land in the upper-right quadrant—SkVM improves both dimensions simultaneously. The DeepSeek V3.2 + BareAgent point shows approximately 38–40% token reduction with a positive score improvement (roughly 2–3 percentage points)—the token savings are dramatic because this combination eliminates the interaction overhead of agent loops correcting environment-related and tool-invocation errors. For Claude Opus 4.6, token savings are more modest (5–15% depending on harness) but consistently positive, with small score improvements.

For weaker models (Qwen3-30B, Devstral Small, Claude 3.5 Haiku), the points cluster near the y-axis or slightly to the left—score improvements are large (15–25 percentage points), but token savings are small or slightly negative (0 to −10%). The paper explains this as a consequence of SkVM enabling successful execution: the baseline agent may fail quickly (consuming few tokens on a short, incorrect trace), while the compiled skill enables the agent to succeed after a longer trace, consuming more tokens but achieving the task. This is not a failure of the compilation—it is a tradeoff between cost and correctness that the user must evaluate.

**Environment binding token efficiency (Figure 14).** Figure 14 shows the performance of three models (Claude Opus 4.6, Qwen 397B, Qwen 122B) across three environment configurations on two representative tasks (pdf-create and document-xlsx). In the "Deps-removed" configuration (required libraries deliberately absent), all models suffer relative to the "Complete" configuration where dependencies are pre-installed. Claude Opus 4.6 maintains 100% average score but generates substantially more output tokens (roughly 7–8k vs. 4–5k in the complete environment) and takes much longer (roughly 250s vs. 100s). The Qwen models experience both correctness degradation (dropping to roughly 33–67% scores) and increased token consumption.

With environment binding ("Env-bound"), all three models return to complete-environment level correctness, and token consumption either matches or falls below the complete-environment baseline. For Qwen 122B, env-bound execution actually uses fewer tokens than the complete-environment baseline (roughly 4k vs. 5k), suggesting that even in a fully provisioned environment, the model benefits from the explicit setup because it eliminates token-consuming verification behavior—the model doesn't need to check whether dependencies are installed because the script handles it.

#### Parallelism Extraction Performance (Figure 16)

**Headline result.** SkVM's concurrency extraction achieves up to 3.2× end-to-end speedup over sequential execution, with TLP (thread-level parallelism) yielding the largest average improvements because its coarser-grain parallelism produces more pronounced optimization effects. DLP gains scale directly with the degree of data parallelism in the task.

**Per-task results (Figure 16).** Figure 16 displays wall-clock time for eight representative tasks (Batch Analysis, Log Parsing, Metrics Profiler, Code Scanner, Dependency Audit, Lint Checker, Multi-Service Debug, Test Suites, CLI Debug) under four execution modes: Sequential, DLP, ILP, and TLP. The speedup numbers above each parallel bar indicate the improvement relative to sequential:

- **Multi-Service Debug** achieves the largest speedup at 3.2× under TLP, consistent with the paper's description of TLP as applying to "independent sub-tasks that each require multi-turn reasoning"—debugging multiple independent services is the prototypical TLP case, where each service can be debugged by a separate sub-agent in parallel.

- **CLI Debug** achieves 2.4× speedup under TLP.

- **Dependency Audit** and **Test Suites** achieve 2.4× under TLP.

- **Log Parsing** achieves 2.5× under DLP, reflecting the data-parallel nature of log analysis where the same operation applies to multiple independent log files.

- **Batch Analysis** achieves 1.5× under DLP. The relatively modest gain suggests limited data parallelism in this task type—fewer independent data items to parallelize.

- **Metrics Profiler** achieves 1.3× under DLP.

- **Code Scanner** achieves 1.0× under DLP—no speedup, indicating that the compiler identified a DLP opportunity but that in practice the overhead of parallelization offset the gains, or that the degree of data parallelism was insufficient to overcome coordination costs.

- **Lint Checker** achieves 1.7× under ILP.

The paper notes inherent variability in agent execution due to LLM throughput fluctuations and varying numbers of agent loop iterations—the timing variations within a "reasonable range" are attributed to this non-determinism. No error bars or variance measures are reported.

**TLP advantage.** TLP yields the largest average improvements because it parallelizes at the coarsest granularity: entire sub-agent sessions that run independently in separate contexts, with no shared state or synchronization overhead beyond the final result merge. ILP, operating at the instruction level, reduces both execution time and the number of LLM invocations (by batching independent tool calls into a single turn), but the gains are bounded by the fact that the model still processes each call sequentially within the turn. DLP gains scale directly with the degree of data parallelism—for tasks with many independent data items, DLP can approach linear speedup; for tasks with few items, the gains are modest.

#### Code Solidification Performance (Figure 15)

**Headline result.** For code patterns that successfully promote (PDF-extract, PDF-merge, weather-current), code solidification achieves 5× to 50× latency reduction compared to LLM-based code generation. For patterns that do not promote (weather-forecast), the safety gate correctly prevents solidification because the model's generated code structures diverge across invocations.

**Per-case analysis (Figure 15).** Figure 15 shows per-invocation latency for eight invocations of four code patterns, with blue bars representing LLM inference latency and green bars representing solidified execution latency. The dashed vertical line marks the promotion point—the invocation after which the runtime switches from LLM generation to solidified execution.

- **PDF-extract (Figure 15c).** LLM inference latency ranges from 10,469 ms to 15,116 ms across invocations. After promotion to solidified code, execution drops to 206–568 ms—a **19–50× latency reduction**. The variation in the solidified execution time likely reflects differences in PDF file size or complexity, since the solidification replaces LLM inference but not the actual PDF processing work.

- **PDF-merge (Figure 15d).** Similar pattern: LLM inference ranges from roughly 8,000 ms to 14,000 ms; solidified execution drops to sub-500 ms levels.

- **Weather-current (Figure 15a).** LLM inference at approximately 9,000 ms per invocation drops to approximately 2,000 ms after solidification—a **~5× improvement**. The smaller speedup relative to PDF tasks is because the solidified code still makes an external weather API call, so network latency bounds the improvement. The LLM inference overhead is eliminated, but the API call remains.

- **Weather-forecast (Figure 15b).** All eight invocations use LLM generation (no green bars). The paper explains that weather-forecast uses "more flexible formats, so the generated code structures diverge from the code signature and fail to match." The AOT compiler identified a candidate, but the signature validation gate prevented promotion because the model's output was not structurally consistent across invocations. This is presented as validation of the safety mechanism: the system correctly avoids solidification when it would produce incorrect results, rather than blindly promoting.

**Token consumption in solidified mode.** The figure also shows token consumption bars below the latency bars. For invocations where solidification is active (green bars), the token consumption drops to zero for the code generation step—the solidified function executes natively without any LLM tokens consumed. The tokens shown for those invocations represent the surrounding agent reasoning, not the code generation itself. This is consistent with the paper's claim that solidified code "bypasses LLM inference entirely."

**Promotion threshold.** The paper does not specify the exact number of consecutive signature matches required for promotion, but the figures show that promotion occurs after a variable number of invocations: weather-current promotes after 3 invocations (the dashed line appears between invocations 3 and 4), while PDF-extract and PDF-merge promote after variable numbers of invocations as well (the exact count varies per case in Figure 15). The paper states only that promotion occurs "after the code signature matches successfully across multiple consecutive invocations."

#### Target Profiling Overhead (Figure 13)

**Headline result.** Full capability profiling across all 26 primitive capabilities costs $0.033 (7.3 minutes) for Devstral Small and $0.079 (31.1 minutes) for Qwen3-30B, with Generation and Tool Use categories dominating the profiling duration for the larger model.

**Per-category breakdown (Figure 13).** The profiling overhead is broken down into four categories (Generation, Reasoning, Tool Use, Instruction) for both models, with side-by-side bar charts showing duration (in seconds) and cost (in millidollars). For Devstral Small: Generation dominates at roughly 250s, Tool Use at roughly 150s, Reasoning and Instruction each under 50s, totaling approximately 440s (7.3 minutes). For Qwen3-30B: Generation dominates at roughly 750s, Tool Use at roughly 250s, Reasoning at roughly 100s, Instruction at roughly 100s, totaling approximately 1,200s (roughly 20 minutes—though the paper reports 31.1 minutes, suggesting additional overhead not captured in the visible bar heights of Figure 13, perhaps including harness overhead or API round-trip latency). The cost follows the same pattern, scaling with duration.

**Amortization argument.** The paper emphasizes that profiling is a one-time cost per (model, harness) pair—subsequent skill compilations reuse the cached profile. If a user installs N skills for the same target, the per-skill profiling overhead is approximately $0.079/N for Qwen3-30B, which becomes negligible for typical skill libraries of 10–100 skills.

### Ablation Studies and Robustness Checks

**Staged compilation breakdown (Figure 11):** The paper ablates the contribution of AOT compilation vs. JIT optimization by showing scores at six stages (no skill, original skill, AOT-only, JIT round 1, JIT round 2, JIT round 3) across 14 skill categories. The key finding is that AOT compilation provides the majority of the improvement (88% average score increase over the original skill), with JIT providing additional refinement—8 of 14 categories achieve full scores after one JIT round, and 10 of 14 after three rounds. This confirms that AOT capability-based compilation is the primary mechanism; JIT's contribution is in edge-case refinement (identifying capability defects missed by static profiling) and iterative correction.

**Environment binding (Figure 14):** The paper ablates three environment configurations (complete, deps-removed, env-bound) to isolate the effect of environment binding independent of capability-based compilation. The finding that env-bound restores performance to complete-environment levels across all three models—including the weakest model (Qwen 122B) that drops to near-zero correctness without dependencies—validates that environment binding addresses P3 independently of model capability.

**Code solidification promotion gate (Figure 15b):** The weather-forecast case serves as a natural ablation for the code solidification safety mechanism. By including a case where the code signature does not match and promotion never occurs, the paper demonstrates that the gate correctly prevents incorrect solidification rather than blindly promoting all candidates. No ablation is shown for what happens if the threshold is lowered (e.g., promoting after a single match rather than multiple consecutive matches), so the sensitivity to the promotion threshold is untested.

**JIT adaptive recompilation rollback (D3 Line Chart in Figure 11):** The D3 Line Chart task provides an implicit ablation of the rollback mechanism: JIT.1 introduced a regression (an example file that was too long and triggered parsing errors), and subsequent rounds corrected it. The paper describes this as evidence that the rollback mechanism works, but does not show what would happen without rollback—there is no ablation comparing "JIT with rollback" vs. "JIT without rollback."

**Harness diversity (Figures 9, 10, 12):** By evaluating on three harnesses with substantially different designs (minimal BareAgent, code-focused OpenCode, general-purpose OpenClaw), the paper ablates whether compilation benefits are harness-specific. The consistent improvement across all three harnesses—with the largest gains on the most complex harness (OpenClaw)—suggests that capability-based compilation generalizes across harness architectures.

**Model tier gradient (Figures 9, 10, 12):** The three-tier model selection (SOTA, Mid, Small) serves as a capability ablations: the finding that smaller models benefit more from compilation than larger models is a consistent pattern across all result figures and provides evidence that compilation addresses the model-mismatch problem (P1) specifically, not a general prompt improvement effect that would benefit all models equally.

**Missing ablations.** Several ablations that would strengthen the paper are absent: (1) no comparison of SkVM compilation against fine-tuning the base model on skill-following—this would test whether compilation provides benefits beyond what model adaptation can achieve; (2) no ablation of the primitive capability set size—what happens with 13 capabilities instead of 26, or with a different categorization?; (3) no sensitivity analysis on the 1% frequency threshold for adding new primitive capabilities—how would coverage change with a 5% or 0.5% threshold?; (4) no ablation of the promotion threshold for code solidification—how does the safety–speedup tradeoff change with stricter or looser thresholds?; (5) no ablation isolating the contribution of each compilation pass independently for the task completion metric (Figure 11 shows staged breakdown but only for Qwen3-30B on BareAgent—it is not replicated across models or harnesses).

### Critical Assessment

**Claim from the executive summary: "SkVM improves average task completion rates by 15.3% across models and harnesses."**

The evidence supporting this claim is distributed across Figures 9 and 10. The 15.3% figure (from the abstract) appears to represent an average improvement over the original skill baseline across all model–harness–task combinations. The heatmap in Figure 9 visually supports large improvements for weaker models and modest improvements for stronger models. However, the paper does not report this aggregate number with precise calculation details (e.g., micro-average vs. macro-average, whether tasks with ceiling scores are included, how the five diverse input instances per task are aggregated). The 15.3% figure is not traceable to a specific table that shows the per-model, per-harness, per-task breakdown with the mathematical aggregation. Readers must infer the calculation from the heatmap cell values and the aggregated bar chart in Figure 10, where the SkVM bars are consistently the tallest. This weakens the precision of the headline number but does not undermine the qualitative finding that compilation improves task completion across the board.

A more important qualification: the improvement is measured on the **same task instances used during compilation**, not on held-out test tasks. The staged optimization breakdown (Figure 11) explicitly states that tasks in each JIT round are "of the same type but differ in contents," which provides some separation, but the AOT compilation (capability-based compilation) operates on the skill's requirements extracted from the full skill text, not from specific task instances. The skill's capability requirements are inherent to the skill, not to the evaluation instances, so the concern about overfitting is primarily about JIT optimization rather than AOT compilation. The JIT rounds in Figure 11 use different task instances per round, providing evidence that JIT improvements generalize beyond the instances used for recompilation—the fact that scores improve or maintain from JIT.1 through JIT.3 on different instances supports generalizability.

**Claim from the executive summary: "SkVM reduces token consumption by up to 40%."**

The evidence for this claim is in Figure 12, where the DeepSeek V3.2 + BareAgent point shows token reduction approaching 40%. The "up to" qualifier is important: this is the maximum observed reduction, not the average. Figure 12 shows that for most SOTA and Mid-tier models, token reductions are in the 5–25% range, with weaker models occasionally showing negative token savings (more tokens consumed) because SkVM enables longer successful traces. The 40% figure is the best case, achieved on the strongest model with the simplest harness—the combination where the model would otherwise spend the largest fraction of tokens on unnecessary error-recovery interactions. This is an honest ceiling, not a typical case, but the paper would benefit from reporting the average token reduction across all model–harness pairs to contextualize the "up to 40%" figure.

**Claim from the executive summary: "SkVM achieves up to 3.2× speedup through parallelism extraction."**

The evidence is in Figure 16, where Multi-Service Debug under TLP achieves 3.2× speedup over sequential execution. This is measured as end-to-end wall-clock time. The "up to" is again the maximum: other tasks show speedups of 1.0×–2.5×, and the paper notes that inherent agent execution variability makes precise timing comparisons noisy. The figure reports single speedup numbers without error bars, so the statistical reliability of the 3.2× vs. 2.4× distinction is unclear.

A more fundamental question: the parallelism extraction experiment appears to measure speedup on tasks that the agent successfully completes, but it does not report whether the parallelized execution changes task completion rates. If TLP introduces coordination errors or sub-agent failures that don't occur in sequential mode, the speedup might come at a correctness cost. The paper does not report correctness for the parallelism experiments, making the speedup numbers incomplete as an efficiency assessment.

**Claim from the executive summary: "SkVM delivers 19–50× latency reduction via code solidification."**

The evidence is in Figure 15, where PDF-extract shows LLM inference at 10,469–15,116 ms and solidified execution at 206–568 ms. This is the strongest quantitative result in the paper—the latency reductions are dramatic and the waterfall charts clearly show the step change before and after promotion. The mechanism is well-motivated (75% of skills contain solidifiable code) and the safety gate is validated by the weather-forecast non-promotion case.

However, the evaluation shows only four cases from two skills. The paper claims 75% of the 15,063 analyzed skills contain solidifiable code patterns, but evaluates solidification on only a tiny fraction of this population. The generalizability of the 19–50× speedup to the broader skill corpus is untested. Additionally, the evaluation does not measure end-to-end task completion time with and without solidification—it measures only the latency of the code generation step that was solidified. If the code generation step represents 80% of the total task execution time, the 19–50× reduction is transformative; if it represents 5%, the impact is modest. The paper does not report what fraction of end-to-end task execution time is consumed by the solidifyable code patterns.

**Claim implicit in the system design: "Primitive capabilities are general and sufficient."**

The paper validates that the 26 primitive capabilities cover 95% of the 15,063-skill corpus. This is a reasonable coverage claim, but the validation methodology has potential weaknesses. The capabilities were derived from 50 representative skills and validated against the full corpus using LLM-assisted analysis—the same LLM that might miss capability gaps. The paper does not report whether the validation was done by a single model or multiple models, and does not report inter-annotator agreement or human verification. If the LLM used for validation is systematically blind to certain types of capability requirements, the 95% coverage could be an overestimate.

Additionally, coverage of the skill corpus does not guarantee that the capabilities are **sufficient for compilation to produce correct skill variants**. The 4.5% regression rate (tasks where SkVM-compiled skills perform worse than original skills) and the 4 of 14 categories that don't reach full scores even after three JIT rounds suggest that the capability vocabulary, even if it covers the expressed requirements, may not capture everything needed for successful adaptation—or that the compiler's transform logic has limitations beyond the vocabulary.

**What the experiments do not test.**

The evaluation does not test SkVM on any benchmark other than SkillsBench and representative skill tasks. The skill tasks are drawn from mainstream skill sources (Anthropic-skills, OpenClaw skills, skills.sh), but the specific selection criteria for the 118 tasks are not described. It is unclear whether the evaluation tasks are representative of the skill ecosystem or selected to showcase SkVM's strengths.

The evaluation does not include a comparison against a **target-unaware skill rewriting** baseline that uses the same LLM-based rewriting as SkVM's compilation but without the capability profiling—i.e., what if you just asked an LLM to "adapt this skill for model X on harness Y" without the primitive capability framework? This would test whether the primitive capability system adds value beyond the general ability of LLMs to rewrite skills.

The evaluation does not test the **dynamic difficulty estimation** or **runtime strategy switching** aspects of the system in isolation from the AOT compilation. The adaptive recompilation and resource-aware scheduler are evaluated only in the context of the full system, making it difficult to attribute improvements to specific mechanisms.

The evaluation does not measure **compilation cost itself**—the token consumption and wall-clock time of running the AOT compiler and the initial profiling. The target profiling cost is reported (Figure 13), but the per-skill compilation cost is not. If compiling a skill costs 50,000 tokens and the skill is executed 5 times, the token savings from compilation (40% of, say, 20,000 tokens per execution = 8,000 tokens saved per execution) would require many executions to amortize the compilation cost. Without reporting the compilation cost, the system's net efficiency cannot be assessed.

**Overall assessment.** The experiments demonstrate that SkVM improves task completion rates, reduces token consumption, and accelerates execution for the tested combination of models, harnesses, and tasks. The headline numbers are directionally convincing and the qualitative patterns (weaker models benefit more, harness complexity matters, AOT provides the bulk of improvement, JIT refines) are consistent across experiments. However, the evaluation's scope is narrow (a single suite of 118 tasks, no held-out test set for compilation, limited code solidification cases), the statistical rigor is limited (no error bars, no significance testing), and several important ablations are missing (no comparison to fine-tuning, no measurement of compilation cost, no sensitivity analysis on key hyperparameters like the promotion threshold and capability set size). The claims are best understood as demonstrating **feasibility and potential** rather than providing a complete, statistically robust characterization of SkVM's performance in deployment.

## 6. Limitations and Trade-offs

### Limitation 1: The Compilation Cost Is Unmeasured and Potentially Dominant

**The assumption or constraint.** SkVM's AOT compiler uses LLM-assisted analysis across three passes (capability extraction, dependency resolution, concurrency analysis) that each invoke an LLM. The paper explicitly acknowledges this cost in Section 7: "AOT compilation invokes an LLM, which incurs token costs." The argument for why this is acceptable rests on amortization: "since skills are executed repeatedly at runtime, the compilation overhead is amortized across multiple invocations" and "compiled skills can be shared across users and applications, further reducing the per-skill compilation cost."

**The consequence.** The headline efficiency claims (up to 40% token reduction, 3.2× speedup, 19–50× latency reduction) are measured at execution time without accounting for the compilation cost. If compiling a single skill costs, say, 50,000–200,000 tokens across the three AOT passes plus JIT candidate generation, and the skill is executed only a handful of times (which is plausible given that 89% of skills on skills.sh have fewer than 86 downloads), the token savings from compilation may never recoup the compilation investment. The amortization argument holds for heavily reused skills on platforms with many users, but the skill ecosystem's long-tailed distribution (Figure 3) suggests that the median skill is executed infrequently, not frequently. For the 79,601 skills on skills.sh with fewer than 86 downloads, the per-execution amortized compilation cost could easily exceed the per-execution token savings, making SkVM a net efficiency loss rather than a gain.

This is not merely a bookkeeping concern. It means the paper's efficiency numbers are **gross execution savings, not net system efficiency**, and the distinction matters most for the deployment scenarios where SkVM would otherwise be most valuable—individual developers installing skills from a marketplace for occasional use, not large-scale platforms serving millions of identical skill invocations.

**What evidence exists in the paper.** The paper reports target profiling cost (§6.5, Figure 13): 7.3 minutes and $0.033 for Devstral Small, 31.1 minutes and $0.079 for Qwen3-30B. But this is the one-time, per-target cost—it amortizes across all skills compiled for that target. The paper does **not** report the per-skill AOT compilation cost. Section 7 states only that the cost exists and that amortization mitigates it, without quantifying the cost itself. The staged optimization breakdown (Figure 11) shows the benefit of AOT and JIT compilation but does not report the compilation tokens consumed to achieve those benefits. The code solidification pipeline (Figure 8) shows the three-stage process but does not report the AOT cost of generating JIT candidates. The evaluation datasets (118 tasks) are used to measure execution outcomes but not compilation overhead.

**Mitigation status.** The paper acknowledges the limitation ("Compilation cost" in Section 7) and appeals to amortization, but provides no measurement, no breakeven analysis (how many executions per skill are needed for token savings to exceed compilation cost), and no sensitivity analysis (how compilation cost varies with skill length, complexity, or LLM choice for the compiler). The claim that "compiled skills can be shared across users and applications" assumes a centralized distribution model where one compilation serves many executions—this is plausible for platform operators (Anthropic, skills.sh) but not for individual users who install skills locally. The limitation remains **unquantified and unmitigated** in the evaluation.

### Limitation 2: Capability Profiling Cost Is Significant and Its Sufficiency Is Unvalidated

**The assumption or constraint.** SkVM's core compilation mechanism—capability-based compilation—depends on a catalog of 26 primitive capabilities that serve as the intermediate representation for expressing skill requirements and profiling target proficiency. This catalog was derived from 15,063 skills using LLM-assisted analysis. The paper states that these 26 capabilities "cover the requirements of 95% of the skills" and that the profiling cost is "a one-time cost per (model, harness) pair" that is "cached and reused for all subsequent skill compilations for the same target."

**The consequence.** Two distinct problems arise from the capability catalog's design and validation.

First, **the profiling cost is high in absolute terms.** A full profile costs 31.1 minutes and $0.079 for Qwen3-30B (Figure 13). For a developer evaluating whether to deploy SkVM across, say, 5 models on 2 harnesses (10 targets), the profiling cost is approximately $0.79 and 5+ hours of wall-clock time—before any skill is compiled or executed. This is a one-time cost, but for individual developers or small teams experimenting with different model–harness combinations, it represents a meaningful barrier to adoption. More importantly, profiling must be **repeated whenever the model changes** (model updates, new model releases, switching between model versions) and **whenever the harness changes** (harness version updates, configuration changes). The paper does not discuss how frequently profiles become stale or whether partial re-profiling is possible when a model is updated rather than replaced.

Second, **the 95% coverage claim is self-validated.** The capability catalog was derived and validated using LLM-assisted analysis—the same methodology that could be systematically blind to certain types of capability requirements. The paper does not report whether the validation was performed by multiple models, whether there was human verification of the coverage analysis, or what inter-annotator agreement looked like. If the LLM used for validation systematically missed certain capability dimensions (e.g., capabilities related to multimodal understanding, long-context reasoning, or safety-constrained behavior), the true coverage could be lower. The paper also does not report what the 5% of uncovered skills look like—whether they cluster in specific domains (suggesting systematic gaps) or are scattered randomly (suggesting rare edge cases). If the uncovered skills are concentrated in important domains like security, compliance, or scientific reasoning, the 95% headline number overstates practical coverage.

**What evidence exists in the paper.** Section 4.1.1 describes the derivation process: 50 representative skills → initial 19 capabilities → validation against 15,063 skills with a 1% frequency threshold for adding new ones → convergence on 26 capabilities covering 95%. The coverage number is stated without confidence intervals, without breakdown by skill category, and without description of the validation methodology's rigor (e.g., what LLM performed the validation? Was there a human audit?). The 4.5% regression rate (Figure 9: SkVM-compiled skills reduce task completion on 4.5% of tasks) and the 4 of 14 categories that fail to reach full scores even after three JIT rounds (Figure 11) provide indirect evidence that the capability vocabulary may not capture everything needed for successful compilation in all cases, though these failures could also stem from the compiler's transform logic rather than the vocabulary itself.

**Mitigation status.** The paper proposes an iterative approach for expanding capabilities as the skill library grows: "we can adopt the iterative approach described in §4.1 to expand the primitive capabilities" (Section 7). This addresses future coverage but not the validation gap in the current catalog. The proficiency level calibration (checking that higher-level microbenchmarks are genuinely harder) is described in §4.1.1 but the results of this calibration are not reported—the paper states the methodology without showing that the calibration succeeded for all 26 primitives. The limitation is **partially mitigated** by the JIT adaptive recompilation mechanism, which can catch capability gaps that static profiling missed (Figure 11 shows JIT improving scores beyond AOT-only levels), but JIT recompilation requires multiple execution failures to trigger, meaning users still pay the cost of those failures.

### Limitation 3: Evaluation Is on a Single Narrow Benchmark with No Held-Out Test Set

**The assumption or constraint.** All experiments in the paper are conducted on SkillsBench and representative skill tasks (118 tasks total) spanning code generation, data analysis, document creation, and system administration. The paper does not evaluate on any other benchmark, any other task domain, or any other modality.

**The consequence.** The paper's central claim—that SkVM improves skill portability across heterogeneous models and harnesses—is demonstrated only within the specific task distribution of SkillsBench. Several aspects of SkVM's design could fail to generalize to other domains:

- **Primitive capabilities were derived from skills, not from general agent tasks.** The 26-capability vocabulary was extracted from the same skill corpus that the evaluation draws from. If the capability set overfits to the structural properties of the specific skills in this corpus—e.g., the 76% that contain explicit procedural structure, the 75% that contain solidifiable code fragments—then performance on skills with different structural properties (e.g., skills that emphasize creative generation rather than procedural execution, skills that require multimodal reasoning, skills that involve interactive dialogue rather than tool-use loops) is unknown.

- **The evaluation does not use a held-out test set for compilation validation.** The skill compilation effectiveness results (Figure 9, 10) compare SkVM-optimized skills against baselines on the same tasks used during compilation. The staged optimization breakdown (Figure 11) uses different task instances per JIT round ("tasks used in each round are of the same type but differ in contents"), which provides some separation, but the AOT compilation operates on the full skill text and does not have a train/test split at the skill level. A skill is compiled once per target, and then evaluated on tasks associated with that skill. There is no held-out set of skills that were compiled but not used during system development, meaning the compilation strategies (which transforms to apply for which capability gaps) could be overfit to the specific skills in the evaluation set.

- **No evaluation on non-English skills or culturally specific tasks.** The skill corpus and evaluation tasks appear to be English-language and drawn from a specific ecosystem (Anthropic-skills, OpenClaw, skills.sh). The paper does not test whether primitive capabilities, environment binding, or concurrency extraction generalize to skills authored in other languages or for task domains common outside the current skill platforms (e.g., enterprise resource planning, legal document review, medical guideline following).

**What evidence exists in the paper.** The paper's entire evaluation (Figures 9–16) is based on SkillsBench plus representative skill tasks. The abstract states "covering SkillsBench and representative skill tasks (118 tasks)" but does not specify what makes them "representative" or what population they represent. The paper does not claim generalizability beyond the evaluated domains—but it also does not discuss the scope of the evaluation as a limitation. The skill taxonomy in Section 2.3 classifies skills into tool-reference (52%), procedural guidance (28%), and content generation (20%), but the evaluation does not report results broken down by these categories, so the reader cannot assess whether SkVM's benefits differ across skill types (e.g., does capability-based compilation help more for tool-reference skills than generative skills?).

**Mitigation status.** **Not addressed.** The paper does not discuss the limited benchmark scope as a limitation, does not propose evaluation on additional benchmarks, and does not analyze whether the 118-task evaluation set is representative of the broader 118,000-skill ecosystem. The paper would be substantially strengthened by evaluating on at least one additional skill benchmark (e.g., the SWE-benchmark skill evaluation from Han et al., 2026, which is cited in the paper but not used for evaluation) or by analyzing whether SkVM's performance varies systematically across the three skill categories identified in the taxonomy.

### Limitation 4: Code Solidification Is Evaluated on Only Four Cases and Its Real-World Speedup Impact Is Unquantified

**The assumption or constraint.** The code solidification mechanism (§5.2.2) is one of SkVM's two JIT optimization components and produces the paper's most dramatic headline number: "19–50× latency reduction." The paper claims that 75% of skills contain solidifiable code, based on analysis of the 15,063-skill corpus.

**The consequence.** The evaluation of code solidification (Figure 15) demonstrates the mechanism on only **four code patterns from two skills** (weather and PDF-processing). This is an evaluation of 4 cases out of a claimed population of 75% of 15,063 skills—roughly 11,300 skills. The gap between the claim and the evidence is enormous. Several specific concerns arise:

- **The 19–50× speedup may not be representative.** The four evaluated cases were presumably selected because they are clear examples of solidifiable code. But the 75% statistic covers all skills that contain "code-like fragments: shell commands, API call patterns, or script snippets whose overall shape recurs across invocations while only the input-specific parameters change" (§2.3). Within this population, there will be a spectrum of solidifiability: some code fragments have perfectly invariant structure (like PDF-merge, which always calls the same library functions in the same order), while others have partially variant structure (like the weather-forecast case that never promoted because the model used flexible formats). The paper does not report what fraction of solidifiable code patterns successfully promote, how many invocations are typically needed for promotion, or what the distribution of speedup factors looks like across a larger sample.

- **The end-to-end impact is unquantified.** The latency reduction is measured for the solidified code step in isolation, not for the full task execution. If the solidified code step represents 80% of the end-to-end task latency, the 19–50× reduction is transformative. If it represents 5%, the impact on user-perceived latency is modest. The paper does not report what fraction of task execution time the solidifyable code patterns consume before or after solidification.

- **The token savings from solidification are similarly unquantified.** Figure 15 shows token bars that drop to zero for the code generation step after promotion, but the paper does not report the total token consumption for the full task with and without solidification, or what fraction of total tokens the solidified code represents.

- **The promotion threshold sensitivity is unexplored.** The paper states that promotion occurs after the code signature matches "across multiple consecutive invocations" but does not specify the exact threshold or analyze how it affects the safety–speedup tradeoff. A lower threshold (e.g., 2 matches) would promote faster but risk more false promotions. A higher threshold (e.g., 10 matches) would be safer but delay speedup. The weather-forecast case (Figure 15b) demonstrates that the safety gate works in one case, but without a threshold sensitivity analysis, the reader cannot assess whether the gate is well-calibrated in general.

**What evidence exists in the paper.** Figure 15 provides the only quantitative evidence for code solidification. The 75% statistic is from the skill corpus analysis in Section 2.3. The paper does not evaluate solidification on any additional skills, does not report the fraction of the four evaluated skills' execution time represented by the solidified code, does not report end-to-end task latency with and without solidification, and does not analyze threshold sensitivity.

**Mitigation status.** The paper does not acknowledge this as a limitation. The weather-forecast non-promotion case is presented as validation of the safety mechanism, but the extremely narrow evaluation scope is not discussed. The paper would benefit from either a larger-scale evaluation of code solidification across a representative sample of the 75% of skills claimed to contain solidifiable code, or a more cautious framing of the code solidification results as a proof-of-concept rather than a validated system property.

### Limitation 5: Correctness of Parallelized Execution Is Not Evaluated — Speedup Numbers Are Incomplete

**The assumption or constraint.** The concurrency extraction pass (§4.3) and resource-aware scheduler (§5.3) enable parallel execution of skill steps that the compiler identifies as independent. The evaluation (Figure 16) measures wall-clock time under sequential, DLP, ILP, and TLP execution modes and reports speedup factors up to 3.2×.

**The consequence.** The parallelism speedup evaluation measures only execution time, not task completion correctness. This is a critical gap because parallelism in agent execution introduces new failure modes that do not exist in sequential execution:

- **TLP sub-agent failures.** When the compiler extracts TLP blocks and spawns independent sub-agents, each sub-agent runs in its own session with its own context window and tool access. A sub-agent may fail independently (producing an incorrect result, timing out, or crashing) without the parent agent knowing. The parent agent's workflow depends on the sub-agent's output being merged back into the DAG at the correct dependency point. If a sub-agent fails or produces a malformed output, the parent's subsequent steps may fail in ways that don't occur in sequential mode (where the agent would see the failure and retry). The paper does not report whether TLP-parallelized tasks complete correctly at the same rate as sequential tasks.

- **ILP batching errors.** ILP batches independent tool calls into a single LLM turn. This changes the model's context—it sees multiple tool calls at once rather than reasoning about each one individually—which could affect the correctness of individual calls (e.g., the model might confuse arguments between calls, or might skip a call because the batch is long). The paper reports that ILP reduces execution time and the number of LLM invocations, but does not report whether the batched calls produce correct results at the same rate as sequential calls.

- **Resource contention and scheduler side effects.** The resource-aware scheduler (§5.3) throttles and suspends sub-agents under resource pressure. Suspending a sub-agent mid-execution and resuming it later could introduce issues with stale context (the environment may have changed while the sub-agent was suspended) or timeout handling (external API calls made before suspension may have timed out by the time the sub-agent resumes). The paper does not evaluate whether the scheduler's interventions affect correctness.

- **DLP correctness in edge cases.** DLP rewrites steps to use language-level parallelism (e.g., `xargs -P`, `multiprocessing`). If the parallel implementation has subtle differences from the sequential version (e.g., output ordering, error handling, race conditions in shared file access), tasks that succeed sequentially may fail under DLP. The paper does not test for this.

The consequence is that the speedup numbers in Figure 16 are **incomplete as efficiency metrics**. A 3.2× speedup that comes with a 10% correctness degradation is a different proposition than a 3.2× speedup with identical correctness. Without reporting correctness alongside speedup, the reader cannot assess whether parallelism is a net win.

**What evidence exists in the paper.** Figure 16 reports wall-clock time for eight tasks under four execution modes. The paper states: "We also observe inherent variability in agent execution due to LLM throughput fluctuations and varying numbers of agent loop iterations. Consequently, timing variations within a reasonable range are acceptable." This acknowledges timing variance but not correctness variance. No task completion scores are reported for the parallelism experiments. The paper does not compare the task completion rates of sequential vs. parallel execution for any of the eight evaluated tasks.

**Mitigation status.** **Not addressed.** The paper does not discuss the correctness implications of parallelized execution, does not report correctness numbers for the parallelism experiments, and does not propose a mechanism to ensure that parallelized execution preserves correctness (beyond the resource-aware scheduler, which addresses resource contention but not logical correctness). This is a significant omission given that SkVM is fundamentally a system for improving skill execution reliability, and parallelism introduces a tradeoff between speed and reliability that the evaluation does not characterize.

### Limitation 6: The Registration and Loading Mechanism for Compiled Skill Variants Is Underspecified and Its Overhead Is Unmeasured

**The assumption or constraint.** Section 5.1 describes the runtime's skill registration and execution process: "When a new task arrives, the runtime selects the variant compiled for the current (model, harness) pair. From the agent's perspective, the complexity of multiple variants is invisible: it sees a single set of skills and loads them through the same progressive disclosure mechanism described in §2." The paper also states: "Before loading the full skill context, the runtime will first execute the env-binding script to verify whether runtime dependencies are satisfied."

**The consequence.** This description glosses over several implementation details that have practical consequences for adoption:

- **How does the runtime select the correct variant?** If a user has compiled Skill X for three different (model, harness) pairs, and then switches from OpenCode to OpenClaw mid-session (or runs the same skill with a different model for a different task), the runtime must select the correct variant. The paper does not specify the variant identification and selection mechanism—e.g., is there a naming convention? A manifest file? A database? How does the runtime ensure that the model and harness identifiers used at compile time match those used at runtime, especially when models and harnesses are versioned (Claude Opus 4.6 vs. 4.5, OpenCode v1.2 vs. v1.3)?

- **What is the latency overhead of variant selection and env-binding script execution?** The runtime must load the compiled variant and execute the env-binding script before the skill context enters the agent's context window. For a skill with a large env-binding script (many dependencies, complex system probing), this pre-execution step adds latency to every task invocation. The paper does not measure this latency or report how it scales with the number of dependencies or the complexity of the env-binding script.

- **How are skill variants stored and updated?** AOT compilation produces multiple variants per skill (one per target). If a user has 5 models and 3 harnesses, each skill generates up to 15 variants. For a library of 100 skills, that's 1,500 compiled variants plus env-binding scripts. The paper does not discuss storage management, variant versioning (what happens when the original skill is updated? Do all variants need recompilation?), or the disk/memory footprint.

- **What happens when the agent framework's progressive disclosure mechanism conflicts with SkVM's variant loading?** The paper says the agent "sees a single set of skills and loads them through the same progressive disclosure mechanism described in §2." But progressive disclosure in agent frameworks typically means the skill's metadata (name, description) is loaded into the context first, and the full skill content is loaded only when the skill is triggered by a task. If SkVM replaces the raw skill text with a compiled variant, the progressive disclosure mechanism must be modified to load the variant's content instead of the original. The paper mentions extending the agent harnesses with "custom loading and management mechanisms that enable SkVM's optimizations" (§6.1), but does not describe what modifications were necessary or whether they are compatible with all harnesses.

**What evidence exists in the paper.** Section 5.1 is less than a paragraph long and provides no quantitative detail about variant selection, env-binding script execution latency, storage overhead, or harness modifications. Section 6.1 states that the authors "extend the agent harnesses with custom loading and management mechanisms" but does not specify what extensions were needed or what their overhead is. The evaluation does not measure the latency of variant selection or env-binding script execution, and does not report on the storage footprint of compiled variants.

**Mitigation status.** The paper does not acknowledge this as a limitation. The implementation details of variant management are treated as an engineering concern below the level of the paper's contribution. However, for a practitioner evaluating whether to adopt SkVM, these details matter: they determine the complexity of integrating SkVM into an existing agent pipeline, the runtime latency overhead of the compilation infrastructure, and the operational burden of managing compiled variants across model and harness updates. Without this information, the paper's claim that "the complexity of multiple variants is invisible" to the agent is an assertion rather than a demonstrated property.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

This paper enacts a **category shift** in how the field thinks about skills for LLM agents. Before SkVM, the dominant paradigm was that skills are portable by default—they are distributed as plain Markdown, any agent can load them, and the only question is whether the skill's instructions are clear enough. The paper's large-scale analysis (118,000 skills, 15% degradation rate when skills are loaded, 87% of tasks where at least one model sees no benefit) systematically demolishes this assumption. The problem is not that some skills are poorly written; it is that **skills carry implicit assumptions about model capabilities, harness tool surfaces, and execution environments that are frequently violated in practice**, and those violations cannot be fixed by better prompt writing alone because they arise from interactions between independently varying components.

The conceptual shift is to treat skills as **compilable source code** rather than final-form text. This is not an incremental improvement to prompting techniques—it is a claim about where in the system stack the portability problem must be solved. The paper's architecture (AOT compiler with three passes, JIT optimizer with adaptive recompilation and code solidification, resource-aware runtime scheduler) establishes a new layer between skill distribution and skill execution: a **skill compilation and runtime system** analogous to the JVM for Java or AOT compilers for native binaries. The primitive capability vocabulary (26 capabilities with graded proficiency levels) functions as an **intermediate representation**—a type system for skills that makes implicit assumptions explicit and mechanically checkable.

This reframing changes the **author–executor contract**. Currently, skill authors must anticipate the models and harnesses their skill will run on, write defensively for the weakest expected target, and accept that their skill will behave unpredictably when loaded by an unfamiliar model. Under SkVM's model, authors express requirements in terms of primitive capabilities (a shared, target-agnostic vocabulary), and the compiler handles the mapping to specific targets. This is the same separation of concerns that made high-level programming languages viable: the programmer writes against an abstract specification, and the compiler handles target-specific optimization. If adopted, this would make skill authorship more scalable (authors don't need to test on every model) and skill distribution more reliable (compilation happens at installation time, not authoring time).

The paper also reconciles a **latent contradiction** in the agent skills literature. On one side, skill platforms (Anthropic, skills.sh, ClawHub) operate on the premise that skills improve agent performance—and they do, demonstrably, on frontier models in well-provisioned environments. On the other side, recent work (Han et al., 2026; the SkillsBench study by Li et al., 2026) finds that skills often provide no benefit or actively degrade performance, particularly for non-frontier models. The SkVM diagnosis resolves this: **both claims are true, conditional on the target**. Skills help when the model's capabilities match the skill's implicit assumptions; they hurt when there is a gap. The observed contradiction was an artifact of evaluating skills on different implicit difficulty distributions (frontier vs. non-frontier models). SkVM's contribution is not to choose sides but to provide the mechanism—capability profiling and gap-aware compilation—that makes the skill consistently helpful regardless of target.

The paper also establishes that **compilation can substitute for model capability within a bounded regime**. The finding that Qwen3-30B on BareAgent improves from actively worse-than-no-skill to near-ceiling on most tasks after compilation (Figure 11: 11 of 14 categories below no-skill with original skill, 10 of 14 at full score after three JIT rounds) is not a claim that compilation makes a weak model strong—the 4 categories that never reach full scores demonstrate a capability ceiling. Rather, it shows that a large fraction of observed skill failures are not capability failures but **instruction-following failures** caused by the gap between what the skill assumes and what the model can handle. Compilation bridges this gap without changing the model. This reframes the conversation around model capability: the question is not just "what can this model do?" but "what can this model do *when the instructions are adapted to its capability profile*?"—and the answer can be dramatically different.

Research directions that become **more attractive** after this paper:

- **Skill compilation infrastructure as a shared service.** The paper demonstrates that compilation works, but the per-target profiling cost ($0.033–$0.079) and per-skill compilation cost (unmeasured) create a natural incentive for centralized compilation services that profile models and harnesses once and distribute compiled variants to many users. This could become the agent-era equivalent of package repositories that provide pre-compiled binaries for multiple architectures—a skill platform that stores not just the raw Markdown but also compiled variants for popular model–harness pairs.
- **Verifier robustness and over-optimization studies for skill compilation.** The adaptive recompilation mechanism (§5.2.1) treats execution failures as a signal for recompilation, but the paper documents cases where recompilation introduced regressions (the D3 Line Chart example in Figure 11). This opens a research direction on **compilation safety**: how do you verify that a compiled variant is genuinely better than the original before deploying it, and how do you bound the risk that compilation makes things worse? The 4.5% regression rate for compiled skills (vs. 15% for original skills) is an improvement but not a solution—understanding when and why compilation fails is critical.
- **Primitive capability specification as a community standard.** The paper's 26-capability vocabulary is the first iteration of what could become a standard intermediate representation for skills. If multiple platforms adopt a shared capability specification, skill authors could target capabilities rather than specific models, and compiler builders could optimize against a common interface. This is the agent-era analogue of bytecode standardization, and the paper provides both the initial vocabulary and the methodology (iterative derivation from corpus analysis) for evolving it.

Research directions that become **less attractive**:

- **Pure prompt-level skill optimization without target awareness.** The paper shows that Skill-Creator, the only existing systematic skill optimization tool, consistently underperforms SkVM's target-aware compilation, with the gap widening to 25 percentage points for Qwen3-30B on BareAgent (Figure 10). This suggests that prompt-level optimization without a model of the target is hitting a ceiling—it can improve instruction clarity but cannot close capability gaps that require compensation or substitution. The diminishing returns of prompt optimization for skill portability argue for shifting research effort toward compilation infrastructure.
- **Fine-tuning as a complete solution to skill execution.** The paper does not directly evaluate fine-tuning, but its results imply that fine-tuning alone cannot solve the skill portability problem because it addresses only model mismatch (P1), not harness mismatch (P2) or environment mismatch (P3). A fine-tuned model on a specific harness will still face context-window conflicts from a different harness's system prompt, and will still fail when runtime dependencies are missing. The paper's multi-dimensional diagnosis of portability failures (model × harness × environment) suggests that fine-tuning is one component of a solution, not a substitute for compilation.

### Follow-Up Research This Work Enables

**Measuring compilation cost and breakeven analysis across the skill ecosystem's long-tailed distribution.** The paper shows execution-time benefits (up to 40% token reduction, 15.3% average score improvement) but does not measure the AOT compilation cost per skill. This is the single most important missing number for assessing net system efficiency. A strong follow-up would: (1) measure the token consumption and wall-clock time of SkVM's three AOT passes on a stratified sample of 500 skills drawn from different length, complexity, and category tiers; (2) compute the breakeven point—how many executions of a skill are needed before token savings exceed compilation cost—as a function of skill type, model tier, and harness complexity; (3) compare this breakeven distribution to the actual download distribution from skills.sh and clawhub.ai (Figure 3) to determine what fraction of the ecosystem's skills would yield net positive efficiency under SkVM. This would directly address the unspoken question: is SkVM a net win for the median skill (which has <86 downloads and may be executed only a handful of times), or only for heavily reused head skills? The result would determine whether SkVM is a deployment-ready system or a head-skills-only optimization.

**Evaluating code solidification across a representative sample of the 75% of skills that contain solidifiable code.** The paper's most dramatic quantitative result—19–50× latency reduction via code solidification—is demonstrated on only four code patterns from two skills. The paper claims that 75% of the 15,063 analyzed skills contain solidifiable code, creating an enormous gap between the claimed population and the evaluated sample. A strong follow-up would: (1) randomly sample 100 skills from the 75% that contain code fragments; (2) run SkVM's AOT candidate generation on all 100; (3) execute each skill on 50 diverse task instances and measure how many code patterns successfully promote (reach the signature-match threshold) and how many fail to promote (like weather-forecast); (4) for promoted patterns, measure the latency reduction and what fraction of end-to-end task time the solidified code represents; (5) report the distribution of speedup factors and the promotion rate, not just the best case. This would establish whether code solidification is a broadly applicable optimization (most solidifiable code promotes, most speedups are large) or a narrowly applicable one (few patterns promote, or most promoted patterns represent a small fraction of execution time). The weather-forecast failure case suggests the latter may be common—determining which is true is critical for assessing solidification's practical value.

**Measuring the correctness of parallelized skill execution under DLP, ILP, and TLP.** The paper's concurrency extraction results (Figure 16) measure only wall-clock speedup, not whether parallelized tasks complete correctly. A strong follow-up would: (1) for the eight tasks evaluated in Figure 16, run 50 trials each under sequential, DLP, ILP, and TLP execution modes and measure both task completion rate and execution time; (2) identify failure modes specific to parallelism: sub-agent crashes under TLP, batched call confusion under ILP, race conditions under DLP; (3) evaluate whether the resource-aware scheduler's throttling and suspension mechanisms (§5.3) introduce new failure modes (stale context after suspension, timeout on resumed API calls) and at what resource pressure thresholds these failures emerge; (4) test whether the concurrency hints from prior runs (§5.3) correctly predict sustainable parallelism levels or whether they lag behind changing system conditions. This would transform the speedup numbers from unqualified performance claims into a characterized speed–correctness tradeoff curve—essential information for any practitioner deciding whether to enable parallelism in production.

**Comparing SkVM compilation against fine-tuning the base model to follow skills, both separately and in combination.** The paper positions compilation as an alternative to weight modification, but does not empirically compare them. A strong follow-up would: (1) fine-tune a mid-tier model (e.g., Qwen3.5-122B) on a dataset of (skill, task, correct execution trace) pairs to improve skill-following ability; (2) evaluate the fine-tuned model with original (uncompiled) skills, SkVM-compiled skills, and no-skill baselines on a held-out skill set; (3) measure whether fine-tuning reduces the gap between original and compiled skills (i.e., does a fine-tuned model need compilation less?) or whether the benefits are additive (compilation helps even after fine-tuning). The paper's diagnosis that failures arise from model–skill interaction rather than model capability alone predicts that compilation should still help after fine-tuning, because fine-tuning improves general instruction-following but does not give the model knowledge of specific skill–harness interactions. Testing this would clarify whether compilation and fine-tuning are substitutes or complements, with direct implications for how platform operators allocate resources between training and compilation infrastructure.

**Stress-testing the capability vocabulary: what capabilities are missing, and what happens at the coverage boundary?** The paper claims 95% coverage of the 15,063-skill corpus with 26 primitive capabilities, but this is self-validated using LLM-assisted analysis. A strong follow-up would: (1) manually audit a random sample of 50 skills from the 5% that are supposedly uncovered, classifying the specific capability requirements that the 26-capability vocabulary fails to capture; (2) determine whether these missing capabilities cluster in specific domains (suggesting systematic vocabulary gaps) or are scattered (suggesting rare edge cases); (3) for the 4.5% of tasks where SkVM-compiled skills regress relative to original skills (Figure 9), analyze whether the regression is caused by a missing capability (the compiler could not adapt because the vocabulary lacked the concept), a miscalibrated proficiency level (the compiler thought the model could handle L2 when it actually cannot), or an interaction between compensation transforms that created a new failure mode; (4) test whether adding capabilities for the identified gaps (following the iterative methodology in §4.1) reduces the regression rate below 4.5%. This would directly test the paper's central design claim—that the intermediate representation is sufficient for compilation—and identify where the abstraction breaks down.

**Extending SkVM to dynamic, runtime skill adaptation without per-target pre-compilation.** The paper's AOT compilation model requires profiling every (model, harness) pair before any skills are installed, and compiling each skill for each target. This is feasible for platform operators with known, stable targets, but impractical for individual developers who experiment with different models or custom harnesses. A strong follow-up would explore whether the compilation can be done **lazily and adaptively**: (1) when a skill is first loaded for a new (model, harness) pair, run a lightweight, fast profiling pass (a subset of microbenchmarks rather than all 26 capabilities) to estimate the target's capability profile; (2) start execution with a minimally adapted skill variant based on this rough profile; (3) use the JIT adaptive recompilation mechanism to refine the variant based on execution outcomes, effectively discovering the capability gaps at runtime rather than pre-measuring them; (4) compare the cold-start performance (first few executions) and steady-state performance (after JIT refinement) against full AOT pre-compilation. This would test whether the profiling cost can be subsumed into normal execution, making SkVM practical for ad-hoc or exploratory model use without the upfront profiling barrier.

### Practical Applications and Downstream Use Cases

**Skill marketplace operators (skills.sh, ClawHub) providing pre-compiled skill variants for popular model–harness pairs.** The paper shows that the same skill behaves dramatically differently across models and harnesses (Figure 2), and that compilation can close most of this gap (Figure 9). A marketplace operator could run SkVM's AOT compiler on every skill at upload time, producing compiled variants for (say) the top 10 most popular model–harness combinations on the platform. Users downloading a skill would receive the variant compiled for their specific target rather than the raw author version. The operator would absorb the one-time compilation cost (unmeasured but presumably tens of thousands of tokens per skill), amortized across all users of that skill. The benefit for users would be: (1) the skill works reliably on their setup without the 15% degradation rate that current raw skills exhibit; (2) token savings of up to 40% per execution (Figure 12) from eliminated error-recovery loops, which for paid API models translates directly to cost savings; (3) the env-binding script would prevent the common failure mode of missing dependencies (Figure 14), which currently affects weaker models disproportionately. The paper's finding that the predicted (non-oracle) difficulty bins perform nearly as well as oracle bins in the search setting (though this is from a different paper referenced in the prior sections) provides a precedent for believing that automated, non-expert compilation can approach the quality of ground-truth-informed adaptation.

**Enterprise deployment of agent skills across heterogeneous internal models.** Many organizations deploy multiple LLMs for different use cases—a frontier model for complex reasoning, a smaller open-weight model for routine tasks, a specialized fine-tuned model for domain-specific work—all running on different internal harnesses. Currently, skills authored for one model–harness pair may behave unpredictably when loaded by another, creating a maintenance burden where skills must be manually tested and adjusted for each deployment target. SkVM's capability profiling and compilation pipeline would allow an enterprise to: (1) profile each of their internal model–harness pairs once (cost: $0.03–$0.08 per pair from Figure 13); (2) compile their internal skill library for all targets automatically; (3) deploy skills with the confidence that they have been adapted to each target's specific capability profile, harness tool surface, and execution environment. The 25 percentage point improvement for Qwen3-30B over the Skill-Creator baseline (Figure 10) suggests that compilation provides the largest value precisely in the scenario where organizations are trying to use cheaper, weaker models for high-volume tasks—exactly the economic incentive that drives multi-model deployment in the first place. The cross-harness variance reduction (from 13 points to 5 points, visible in Figure 9–10) means that skill behavior becomes more consistent across the organization's different execution environments, reducing troubleshooting and manual adjustment overhead.

**Self-improving skill pipelines where JIT recompilation continuously refines skills based on production execution traces.** The paper's adaptive recompilation mechanism (§5.2.1) enables skills to improve over time without human intervention: execution failures are aggregated, systematic patterns are identified, and the skill is recompiled with compensation transforms targeting the specific failure patterns. This opens a deployment model where skills are released in a basic form, compiled AOT for the target, and then refined in production as users invoke them on diverse tasks. The 88% average score improvement from AOT compilation alone (Figure 11) provides a strong starting point; the additional improvement from JIT rounds (8 of 14 categories at full score after one round, 10 of 14 after three rounds) provides the steady-state quality. For a platform operator, this means the skill library's quality improves over time without requiring authors to manually update skills in response to user-reported failures. The rollback mechanism (demonstrated in the D3 Line Chart recovery in Figure 11) provides a safety net: if a JIT recompilation makes things worse, the system reverts. The key operational question—which the paper does not answer but which a deployment would need to address—is how many executions are needed before a systematic failure pattern is detected with enough confidence to trigger recompilation, and whether users experience degraded performance during that detection window.

### When to Prefer This Method

The paper positions SkVM against two alternatives: **interpreted execution** (loading raw skill text as context, the current default for all agent platforms) and **Skill-Creator** (Anthropic's prompt-level skill optimization tool). The tradeoffs are explicitly characterized:

- **Prefer SkVM compilation over interpreted execution when:** (1) the skill will be executed on models other than the one it was authored for (the 15% degradation rate and 87% no-benefit rate make interpreted execution unreliable across models); (2) the skill will be used on harnesses with different tool surfaces or context management strategies than the author's development environment (harness-induced variance of up to 13 points on original skills, reduced to 5 points under SkVM); (3) the execution environment may not have all dependencies pre-installed (environment binding restores performance to complete-environment levels even for weak models that fail entirely without dependencies, Figure 14); (4) the skill contains procedural workflows with exploitable parallelism (76% of skills, up to 3.2× speedup from concurrency extraction); or (5) the skill contains structurally invariant code patterns invoked repeatedly (75% of skills, 19–50× latency reduction for promoted patterns). The cost is the compilation overhead (unmeasured per-skill cost plus per-target profiling at $0.03–$0.08) and the integration effort of extending agent harnesses with SkVM's loading and management mechanisms.

- **Prefer interpreted execution over SkVM compilation when:** (1) the skill will be executed exactly once or a very small number of times on a known target (if the compilation cost exceeds the cumulative execution savings, interpreted execution is more efficient—though the paper does not report the breakeven point); (2) the executing model and harness exactly match the skill author's development environment and the author has already tested the skill on that specific combination (no gap to close, so compilation provides no benefit beyond what testing already achieved); or (3) the integration effort of modifying the agent harness to support SkVM's variant loading, annotation parsing (ILP, TLP), and resource-aware scheduling is prohibitive for the deployment context.

- **Prefer SkVM compilation over Skill-Creator when:** (1) the skill will be deployed on models other than Claude Opus 4.6 (Skill-Creator uses Claude Opus 4.6 as the optimizer and produces skills optimized for that model—the paper shows SkVM outperforming Skill-Creator by widening margins for weaker models, reaching 25 percentage points for Qwen3-30B on BareAgent, Figure 10); (2) environment dependencies need to be resolved automatically (Skill-Creator operates at the prompt level and does not address P3); or (3) parallelism or code solidification optimizations are desired (Skill-Creator provides neither). Skill-Creator remains simpler to use for single-target, single-model scenarios where the author controls both the skill and the deployment environment, and where compilation infrastructure overhead is not justified.
