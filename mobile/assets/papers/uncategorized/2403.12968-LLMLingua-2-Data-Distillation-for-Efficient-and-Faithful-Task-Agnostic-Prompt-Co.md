# LLMLingua-2: Data Distillation for Efficient and Faithful Task-Agnostic Prompt Compression

**ArXiv:** [2403.12968](https://arxiv.org/abs/2403.12968)

## 🎯 Pitch

This paper introduces **LLMLingua-2**, a task-agnostic prompt compression method that reformulates compression as a binary token classification problem — preserving or discarding each word — trained via a data distillation procedure that extracts compression knowledge from GPT-4 into an extractive dataset built from MeetingBank transcripts.

---

## 1. Executive Summary

This paper introduces **LLMLingua-2**, a task-agnostic prompt compression method that reformulates compression as a binary token classification problem — preserving or discarding each word — trained via a data distillation procedure that extracts compression knowledge from GPT-4 into an extractive dataset built from MeetingBank transcripts. Using a lightweight Transformer encoder (XLM-RoBERTa-large or mBERT) to leverage full bidirectional context rather than the unidirectional information entropy metrics employed by prior methods like LLMLingua and Selective-Context (which rely on LLaMA-2-7B), the approach explicitly learns the compression objective while guaranteeing faithfulness to the original text. On out-of-domain benchmarks including LongBench, ZeroScrolls, GSM8K, and BBH, the smaller LLMLingua-2 model achieves significant performance gains over task-agnostic baselines while being 3×–6× faster in compression latency (0.4–0.5 seconds vs. 1.5–15.9 seconds for prior methods) and accelerating end-to-end LLM inference by 1.6×–2.9× at compression ratios of 2×–5×, establishing that learned bidirectional compression generalizes across diverse tasks and target LLMs — from GPT-3.5-Turbo to Mistral-7B — despite being trained only on meeting transcripts.

## 2. Context and Motivation

### The Core Problem: Prompt Compression Is Critical but Existing Methods Are Suboptimal

The fundamental problem this paper tackles is **how to shorten prompts for large language models without losing information crucial for downstream task performance**. This matters because modern prompting paradigms — Chain-of-Thought reasoning (Wei et al., 2022), in-context learning with multiple demonstrations (Dong et al., 2023), and Retrieval-Augmented Generation where retrieved documents are prepended to queries (Lewis et al., 2020) — routinely produce prompts that span **tens of thousands of tokens**. These lengthy prompts impose real costs: increased computational overhead during inference (since transformer attention scales quadratically with sequence length), higher financial costs when using API-based LLMs charged per token, and a well-documented degradation in LLM information perception ability with longer contexts (Liu et al., 2024, "Lost in the Middle").

Prompt compression offers a straightforward solution: shorten the original prompt before feeding it to the target LLM, ideally without sacrificing the quality of the LLM's eventual response. This is not merely about saving money — it addresses a fundamental tension in how we interact with LLMs. We want to provide rich, detailed context to maximize answer quality, but LLMs struggle to effectively utilize information buried in long contexts, and the computational cost grows superlinearly. A good compression method resolves this tension by distilling the essential signal from the noise before the LLM ever sees it.

### Two Families of Prior Approaches — and Their Distinct Limitations

Prior work on prompt compression falls into two categories, each with characteristic weaknesses that motivate this paper's approach.

#### Task-Aware Compression: Powerful but Impractical for General Deployment

Task-aware methods compress prompts using information about the specific downstream task or query. LongLLMLingua (Jiang et al., 2023b) exemplifies this approach: it performs question-aware coarse-to-fine compression, estimating token information entropy and adjusting the estimates based on relevance to the current question. Reinforcement learning-based methods (Jung and Kim, 2023; Huang et al., 2023) train compression models using reward signals from downstream task performance. Soft prompt tuning approaches (Wingate et al., 2022; Mu et al., 2023) fine-tune models for specific tasks. Xu et al. (2024) trains a summarization model that compresses context conditional on the question.

These methods achieve strong performance — often surpassing the original uncompressed prompt on specific benchmarks — but their task dependency creates two practical problems:

**The recomputation problem in multi-query settings.** Consider a RAG application where a user asks multiple questions about the same set of retrieved documents. A task-aware method must **re-compress the identical documents each time** because the compression depends on the specific query. If a document appears in ten different retrieval contexts across ten different user queries, it gets compressed ten different times. This is both inefficient (redundant computation) and potentially inconsistent (the same fact about the document might be preserved for one query but pruned for another, confusing any downstream caching or result comparison).

**Limited generalizability.** Task-aware methods are typically tailored to specific compression ratios and task formulations. A model trained to compress for question answering at 3× compression may not perform well when applied to summarization at 5× compression, or when the downstream task format changes. In real-world deployments where the same compression pipeline must serve diverse, evolving use cases, this specialization becomes a liability.

#### Task-Agnostic Compression: General but Relying on Weak Heuristics

Task-agnostic methods avoid these problems by compressing prompts without considering the downstream task. The dominant paradigm, represented by **Selective-Context** (Li et al., 2023) and **LLMLingua** (Jiang et al., 2023a), is grounded in an insight from information theory: natural language contains substantial redundancy (Shannon, 1951) — words and structures that aid human comprehension but carry little information that an LLM actually needs for reasoning. These methods therefore propose to compress prompts by **removing tokens or lexical units according to their information entropy**, estimated using a causal small language model (typically LLaMA-2-7B).

The procedure works as follows: for each token in the original prompt, the causal LM computes a perplexity score (how "surprising" or informative that token is given its preceding context). Tokens with low information content — common function words, predictable continuations, redundancies — are pruned. Tokens with high perplexity — rare words, named entities, numbers, unexpected syntactic turns — are preserved because their information content is higher. The compression is purely structural: it depends only on the statistical properties of the text itself, not on what task will be performed with it.

This paradigm has genuine appeal. It works on any prompt regardless of the downstream task. It can be applied once per document and reused across queries. It requires no task-specific training data. However, the paper identifies **two fundamental shortcomings** that prevent information entropy-based methods from optimal compression:

**Challenge 1: Information entropy is not aligned with the compression objective.** Information entropy, as estimated by a causal language model, measures **predictability given left context** — how expected a token is given what came before it. This is fundamentally different from measuring **whether a token is necessary for an LLM to perform a downstream task correctly**. A token can have high entropy (an unusual but irrelevant stylistic flourish) or low entropy (an article like "the" that, if removed, creates an ungrammatical and potentially misleading prompt). The metric correlates with importance but is not optimized for it. The paper frames this explicitly:

> "Information entropy is an empirical metric for prompt compression. Relying on it for prompt trimming may be suboptimal, as it is not aligned with the prompt compression objective."

This is a classic proxy objective problem: perplexity serves as a convenient, unsupervised signal, but it captures only one dimension of token importance (statistical surprise), missing dimensions like syntactic necessity, semantic load, and relevance to downstream reasoning.

**Challenge 2: Unidirectional context misses essential information.** Causal language models like LLaMA-2-7B process text left-to-right. When estimating the importance of a token at position *t*, they can condition only on tokens 1 through *t*-1. They cannot incorporate **future context** — what comes *after* the token — into their importance estimate. This is a significant blind spot for compression. Consider a sentence like: "The patient was prescribed aspirin, which turned out to be exactly the wrong medication for her condition." A unidirectional model estimating the importance of "aspirin" based only on left context ("The patient was prescribed") may assign it moderate importance. But considering the right context ("exactly the wrong medication") reveals that "aspirin" is **critically important** — it names the specific drug that was harmful, the central fact of the sentence. A bidirectional model can capture this: the right context amplifies the importance of "aspirin." A unidirectional model simply cannot.

This limitation means that entropy-based methods may systematically **undervalue tokens whose importance is signaled by subsequent context** — a pattern that is extremely common in natural language, where the significance of an entity or claim often only becomes clear after reading further.

#### Additional Shortcomings Beyond the Two Core Challenges

Beyond these two primary theoretical limitations, entropy-based task-agnostic methods suffer from practical drawbacks:

**High computational overhead from the estimator itself.** Selective-Context and LLMLingua both require running a 7-billion-parameter language model (LLaMA-2-7B) to estimate token-level perplexity. This compression step itself consumes 1.5–2.9 seconds of GPU time (as shown in Table 5 of the paper), which can be a significant fraction of the end-to-end inference latency on short-to-medium prompts. The compression model's own inference cost eats into the savings from shorter prompts.

**No learning from compression examples.** These methods are training-free: they apply the same fixed entropy heuristic regardless of the domain, style, or information density of the text. A meeting transcript full of disfluencies ("um," "you know," false starts) has a very different redundancy pattern than a dense legal document or a math problem with embedded equations. An entropy threshold that works well for one may aggressively over-prune the other. Because there is no learned compression objective, there is no mechanism to adapt the pruning strategy to these domain-specific characteristics.

#### Summarization-Based Compression: Fast but Lossy

An alternative task-agnostic approach uses summarization models to generate compressed prompts (Chen et al., 2023; Packer et al., 2023). These methods treat compression as an abstractive generation task: rephrase the original text into a shorter version. While conceptually appealing — summarization is exactly what we want — the paper notes two critical failures:

- **Omission of crucial details.** Summarization models are trained to capture the main idea, not to preserve every fact that might be relevant to a downstream question. In question answering over long documents, the answer often depends on a specific detail (a date, a name, a number) that a summarizer would naturally omit as non-essential to the "gist." Appendix G of the paper provides concrete examples from existing extractive compression datasets (SentComp, DebateSum) where the compressed text drops the exact entities needed to answer a question.
- **Hallucination and unfaithfulness.** Abstractive methods can introduce content not present in the original — a well-known problem in neural summarization (Zhao et al., 2020). For prompt compression, this is disastrous: the LLM may answer based on hallucinated facts in the compressed prompt, producing confident but incorrect responses. The chain of trust (original document → compressed prompt → LLM answer) is broken.

The paper explicitly notes this faithfulness concern as a key motivation for pursuing extractive (preserve-or-discard) compression rather than abstractive (rewrite) compression:

> "We formulate prompt compression as a token classification problem to guarantee the faithfulness of the compressed prompt to the original one"

### The Missing Piece: A Learned, Bidirectional, Extractive Compression Model

The landscape of prior work reveals a clear gap. Task-aware methods are performant but impractical for general deployment. Task-agnostic entropy-based methods are general but rely on a misaligned heuristic (information entropy) computed with an incomplete view of context (unidirectional). Summarization-based methods are fast but hallucinate and drop details.

What is missing is a method that is:

1. **Task-agnostic** — compresses once, works across tasks.
2. **Learned** — directly optimized for the compression objective, not a proxy like entropy.
3. **Bidirectional** — leverages full left and right context to assess token importance.
4. **Extractive** — faithfully preserves original tokens without hallucination.
5. **Lightweight** — fast enough that compression overhead doesn't negate inference savings.

This is exactly the gap LLMLingua-2 fills. The paper does not propose a wholly new compression paradigm but rather a systematic re-engineering of the task-agnostic approach to address each of these identified failures. The entropy heuristic is replaced with a learned token classifier trained on a purpose-built dataset. The unidirectional causal LM is replaced with a bidirectional Transformer encoder (XLM-RoBERTa-large or mBERT). The training-free approach is replaced with supervised learning on GPT-4-distilled compression examples. The result inherits the generality of task-agnostic methods while addressing their theoretical and practical weaknesses.

### How This Paper Positions Itself

The paper explicitly frames its contribution as answering two research questions that emerge directly from the limitations of prior work (Section 1):

> **Q1.** How can we identify or build a suitable dataset to align the SLM towards effective prompt compression?
> 
> **Q2.** How can we design a compression algorithm that effectively leverages the full bidirectional context for better performance?

Q1 addresses the proxy objective problem: instead of relying on unsupervised entropy, can we construct a dataset where a capable LLM (GPT-4) demonstrates what "good compression" looks like, and then train a smaller model to imitate that behavior? This is the **data distillation** contribution — extracting compression knowledge from an LLM and encoding it into a training dataset.

Q2 addresses the unidirectional context problem: by using a Transformer encoder rather than a causal language model, can we capture the bidirectional dependencies that entropy-based methods miss? This is the **architectural** contribution — reformulating compression as token classification with full context.

The paper positions itself within the LLMLingua family (hence "LLMLingua-2") but represents a fundamental departure from its predecessor's mechanism. LLMLingua (Jiang et al., 2023a) used perplexity from a causal LM with a coarse-to-fine budget controller. LLMLingua-2 replaces the core scoring mechanism entirely — learned probabilities instead of entropy, bidirectional encoder instead of unidirectional decoder — while retaining the option to integrate with the coarse-to-fine budget controller from the original LLMLingua for very high compression ratios (∼15×, as described in Appendix K). This creates a modular system: the coarse-grained budget allocation strategy from prior work can be paired with the new fine-grained token scoring model.

### Why MeetingBank as the Training Data Source?

The choice of MeetingBank (Hu et al., 2023) — a dataset of city council meeting transcripts — as the sole source of training data is deliberate and illuminating. Meeting transcripts are an ideal compression training domain for several reasons:

- **Natural redundancy.** Spoken language contains extensive disfluencies: filled pauses ("um," "uh"), false starts, repetitions, self-corrections, and conversational filler. This creates a high ceiling for compression — there is genuinely a lot to remove — but also demands that the model distinguish between redundant disfluencies and content-bearing speech.
- **Named entities and domain-specific terminology.** Council meetings contain dense references to ordinances, resolutions, budgets, names, dates, and legal procedures. Misclassifying any of these as redundant could catastrophically change the meaning of the compressed text.
- **Availability of a clear quality signal.** Meeting transcripts are factual records where information preservation can be objectively assessed. Unlike creative or subjective text, there is broad agreement on what constitutes "essential information" in a procedural meeting record.

Crucially, training on MeetingBank and testing on radically different domains (math word problems in GSM8K, logical reasoning in BBH, document QA in LongBench) serves as a **strong test of generalization**. If the model only learns meeting-transcript-specific compression patterns (e.g., "always remove 'um'"), it will fail on out-of-domain data. If it succeeds, it suggests it has learned something more fundamental about linguistic redundancy and information density that transfers across domains. The paper's positive out-of-domain results (Tables 2, 3, 4) are therefore evidence for the latter — that the learned compression objective captures general principles of token importance rather than domain-specific heuristics.

## 3. Technical Approach

### 3.1 Reader Orientation

This paper builds a **task-agnostic prompt compressor** — a lightweight neural model that takes any piece of text and decides, for each individual word, whether to keep it or throw it away, such that when the surviving words are fed to a large language model (like GPT-3.5-Turbo or Mistral-7B), the LLM's performance on downstream tasks (question answering, summarization, reasoning) degrades as little as possible. The core insight is that this word-keeping decision can be **explicitly learned** from examples of good compression produced by a strong LLM (GPT-4), and that using a **bidirectional encoder** (like RoBERTa) rather than a causal language model lets the compressor see both left and right context when judging each word's importance — fixing the two fundamental weaknesses (misaligned entropy heuristic, unidirectional context) that limited prior task-agnostic methods like LLMLingua and Selective-Context.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components, deployed in two phases — an offline training phase and an online inference phase:

**Offline Training Phase:**

1. **Data Distillation (GPT-4)**: GPT-4 is prompted to compress meeting transcripts by removing words only, producing `(original_text, compressed_text)` pairs. This extracts compression knowledge from the powerful LLM into a training dataset — teaching us what GPT-4 considers "essential" vs. "removable."
2. **Data Annotation Algorithm**: An automatic word-matching procedure assigns binary labels (`preserve` / `discard`) to every word in the original text by finding which words survived in GPT-4's compressed version. This converts GPT-4's output (a string of compressed text) into a supervision signal (per-word labels).
3. **Quality Control Filtering**: Two metrics — Variation Rate and Alignment Gap — measure how faithfully GPT-4 followed instructions, and low-quality examples are discarded.
4. **Token Classifier Training**: A Transformer encoder (XLM-RoBERTa-large or mBERT) is fine-tuned on the labeled data to predict, for each word in any input text, a probability `$p_{\text{preserve}}$` that it should be kept. The training objective is standard binary cross-entropy against the automatically assigned labels.

**Online Inference Phase:**

5. **Prompt Compression**: Given a new prompt and a target compression ratio `$1/\tau$` (e.g., 2× means keep half the words), the trained classifier scores every word, the top `$\tau N$` highest-scoring words are retained (maintaining their original order), and the rest are discarded. The compressed prompt is then sent to the target LLM for whatever downstream task the user cares about.

Information flows linearly: raw text → GPT-4 compression → annotation → training data → classifier training → (at deployment) new text → classifier scoring → word selection → compressed prompt → target LLM.

### 3.3 Roadmap for the Deep Dive

- **First**, the data distillation procedure — how the paper extracts compression knowledge from GPT-4 and why nave prompting fails, requiring a carefully designed instruction and chunk-wise processing. This is the foundation: without good training data, the learned compressor has nothing to learn from.
- **Second**, the data annotation algorithm — how binary word labels are automatically derived from GPT-4's compressed output, and the three obstacles (ambiguity, variation, reordering) that the sliding-window fuzzy-matching algorithm must overcome. This explains how natural-language compression outputs get converted into token-level classification targets.
- **Third**, the quality control metrics — Variation Rate and Alignment Gap — that filter bad training examples. These are crucial because GPT-4 does not always follow instructions, and training on hallucinated or poorly matched compressed texts would teach the compressor the wrong behavior.
- **Fourth**, the token classification model architecture and training procedure — the XLM-RoBERTa-large / mBERT encoder, the linear classification head, the cross-entropy loss, and the training hyperparameters. This is the learned component that replaces the entropy heuristic.
- **Fifth**, the compression strategy at inference time — how the per-word probabilities are thresholded to achieve a target compression ratio, how subword tokenization challenges are handled, and how the method integrates with the coarse-to-fine budget controller from the original LLMLingua for very high compression ratios (∼15×).

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **dataset-and-training paper** whose core technical contribution is a procedure for constructing supervised training data for prompt compression by distilling GPT-4, combined with a token classification architecture that leverages bidirectional context. The fundamental insight is that prompt compression is not fundamentally an unsupervised information-theoretic problem (as prior entropy-based methods assumed) but a **supervised learning problem** — if you can generate examples of good compression, you can train a model to imitate them, and the trained model will outperform the unsupervised heuristic because it directly optimizes the compression objective rather than a proxy.

---

#### The Data Distillation Procedure: Extracting Compression Knowledge from GPT-4

**The core challenge.** The entire supervised learning approach hinges on having high-quality training examples of compressed text. The paper's key move is to use GPT-4 itself as the "teacher" — prompt it to compress text, and then train a smaller model to imitate its compression decisions. However, simply asking GPT-4 to "compress this text" fails badly. The paper reports that in preliminary experiments (and consistent with findings from Jiang et al., 2023a), GPT-4 when naively prompted:

- **Modifies expressions**: rephrases words, changes tense, substitutes synonyms — producing an abstractive summary rather than an extractive compression.
- **Hallucinates content**: adds words or facts not present in the original, which is catastrophic for prompt compression because the target LLM may then answer based on fabricated information.
- **Struggles to retain essential information**: when forced to compress aggressively, it drops crucial details that downstream tasks depend on.

These failures mean that a naive GPT-4-compressed dataset would be actively harmful to train on: the model would learn to hallucinate and paraphrase rather than faithfully select which original tokens to keep.

**The designed instruction (Figure 2).** The solution is a carefully crafted prompt that constrains GPT-4's behavior through explicit prohibitions. The full instruction (reproduced in Figure 2 and Appendix A, Figure 9) contains a system prompt establishing the role ("You are an excellent linguist and very good at compressing passages into short expressions by removing unimportant words, while retaining as much information as possible") and a user prompt with five explicit conditions:

> 1. You can ONLY remove unimportant words.
> 2. Do not reorder the original words.
> 3. Do not change the original words.
> 4. Do not use abbreviations or emojis.
> 5. Do not add new words or symbols.

These five constraints together define **extractive compression**: the compressed output must be a subsequence of the original text, preserving the original token identities and their relative order, with no insertions, substitutions, or reorderings. Condition 1 is the core instruction (remove only), while conditions 2–5 are guardrails that prevent GPT-4's known failure modes — reordering (condition 2, which would make annotation ambiguous since we lose track of which original word each compressed word came from), morphological changes (condition 3, which would create the "variation" problem discussed in Section 3.2), abbreviation (condition 4, which would introduce out-of-vocabulary tokens the compressor cannot learn to predict), and hallucination (condition 5, which would introduce content not grounded in the original).

**Why no fixed compression ratio?** Prior work (Jiang et al., 2023a; Huang et al., 2023) typically specified a target compression ratio or token count in their instructions. The paper deliberately removes this restriction, instead instructing GPT-4 to "compress the origin as short as you can, while retaining as much information as possible." This design choice has two justifications:

- **GPT-4 cannot reliably hit a specific ratio.** The paper's preliminary experiments showed that GPT-4 often fails to adhere to numeric compression targets — it either over-compresses (dropping essential information) or under-compresses (leaving too much redundancy) when forced toward a specific number.
- **Information density varies across texts.** A fixed compression ratio would be inappropriate because different texts contain different amounts of redundancy. As the paper notes: "news articles typically contain denser information compared to meeting transcripts. Furthermore, even within the domain of meeting transcripts, the information density from different speakers may vary."

By letting GPT-4 choose the compression ratio organically, each chunk gets compressed to its "natural" information density. Figure 3 confirms this: the distribution of compression ratios across chunks is broad (ranging from roughly 1× to 20×), meaning GPT-4 is making content-dependent decisions rather than blindly applying a uniform threshold. Some sentences get compressed heavily, others lightly, and some (those with no salient information) get compressed to zero tokens — effectively deleted.

**Chunk-wise compression (Figures 4, 9, and Section 3.1).** A critical implementation detail is that long texts are not compressed in one pass. The paper found empirically that GPT-4's compression behavior degrades with input length: "GPT-4 tends to apply a high compression ratio when processing very long context, which might be due to GPT-4's limited ability to handle long context." Figure 4 illustrates this — as context length grows beyond roughly 10,000 tokens, the compression ratio spikes, indicating aggressive (and likely information-destructive) compression.

The solution is **chunk-wise compression**: each long text is segmented into chunks that satisfy two constraints: (1) each chunk ends with a period (at a sentence boundary, to avoid splitting mid-thought), and (2) each chunk contains no more than **512 tokens**. Each chunk is then compressed independently by GPT-4 using the same instruction, and the compressed chunks are concatenated to form the full compressed text. This prevents the long-context degradation by ensuring GPT-4 always operates within its comfortable context window.

The choice of 512 tokens per chunk is likely informed by GPT-4's effective context utilization — keeping chunks well within the model's strong attention range avoids the "lost in the middle" problem (Liu et al., 2024) that would cause GPT-4 to miss information in the middle of long chunks. It also makes the compression task more tractable: compressing a 512-token passage to its essence is a well-scoped task, whereas compressing a 20,000-token document in one shot is effectively asking GPT-4 to understand and distill an entire book chapter simultaneously.

**Implementation details (Appendix A).** The data distillation uses GPT-4-32k (the 32,000-token context variant) with temperature 0.3, top_p 1.0, and a maximum output token limit of 4096. Meeting transcripts exceeding 28,000 tokens are truncated (leaving a 4,000-token budget for the compressed output). The final dataset (Table 8) contains 5,169 training examples, each consisting of an original text chunk and its GPT-4 compressed version, with an average compression ratio of **2.57×** (3,635 tokens compressed to 1,415 tokens on average).

**The primacy of the instruction design.** Table 7 quantifies the importance of the instruction design through an ablation study. Four alternative instructions from prior work (Instruction1 through Instruction4, detailed in Appendix Figure 10) are tested alongside LLMLingua-2's instruction, both with and without chunk-wise compression. The metrics reported are compression ratio (how aggressively GPT-4 compresses), Variation Rate (fraction of words in the compressed output not found in the original — a measure of hallucination), and downstream QA F1 score on LongBench Single Document QA (how well the compressed prompts preserve information needed for answering questions).

The results are stark. Instruction1 (which asks GPT-4 to "rephrase the paragraph to make it short, and keep 5% tokens") achieves a 123× compression ratio but a 13.7% variation rate and only 19.1 QA F1 — it's aggressively compressing but hallucinating and losing essential information. Instruction2 produces a 27× ratio with a 7.8% variation rate and 26.1 QA F1 — better, but still substantially worse than LLMLingua-2's instruction. Instruction3 and Instruction4 show similar patterns.

LLMLingua-2's instruction (with chunk-wise compression) achieves a 2.6× compression ratio (much less aggressive — it's not being forced to hit an artificial target), a 2.2% variation rate (dramatically lower hallucination), and 36.7 QA F1 (far better information preservation). The ablation on chunk-wise compression ("LLMLingua-2 w/o Chunk") shows that compressing without chunking increases the compression ratio to 21× (GPT-4 becomes over-aggressive on long contexts) and drops QA F1 to 27.9 — confirming that chunk-wise processing is essential for information preservation.

The takeaway: the five-condition instruction (remove only, don't reorder, don't change, don't abbreviate, don't add) is not a minor prompt engineering detail — it is **the mechanism that makes the data distillation procedure work at all**. Without it, GPT-4 produces abstractive summaries with hallucinated content that would teach a compressor the wrong behavior.

#### The Data Annotation Algorithm: From Compressed Text to Per-Word Labels

**The annotation problem.** The data distillation step produces pairs of `(original_text, compressed_text)`, but the compressor needs a different format: for every word in the original text, a binary label indicating whether that word should be preserved (1) or discarded (0) after compression. The annotation algorithm must convert GPT-4's compressed string into these per-word labels by identifying which words in the original text survive in the compressed version.

This is non-trivial because GPT-4, despite the five-condition instruction, does not perfectly comply with it. The paper identifies **three obstacles** (illustrated in Figure 5) that make simple string matching fail:

**Obstacle 1: Ambiguity.** A word in the compressed text may appear multiple times in the original text. For example, in Figure 5, the compressed text contains "City Manager Recommendation adopt three resolutions," but the original contains both "City Manager Recommendation to adopt three resolutions" and later "report from City Manager Recommendation." The word "City" appears at least twice in the original — which occurrence corresponds to the compressed output? A naive global matching strategy might label the wrong instance.

**Obstacle 2: Variation.** Despite instruction condition 3 ("Do not change the original words"), GPT-4 sometimes modifies word forms — tense changes ("adopt" vs. "to adopt"), plural/singular shifts ("properties" vs. "property"), or voice alterations. In Figure 5, the original says "consenting to to inclusion of certain properties within the jurisdiction," and the compressed version says "Consent properties inclusion jurisdiction." The original word "consenting" became "Consent" — a morphological change that an exact string match would miss, causing the algorithm to incorrectly label "consenting" as discarded.

**Obstacle 3: Reordering.** Despite instruction condition 2 ("Do not reorder the original words"), GPT-4 sometimes changes word order. In Figure 5, the original says "Second, to join the California first program," but the compressed version mentions "California first program" in a different sequential context. If the algorithm assumes words appear in the same order, it may match "California" to the wrong occurrence or fail to match entirely.

These obstacles mean that a simple greedy left-to-right exact string matching procedure (find the first occurrence of each compressed word in the original, label it as preserved) would produce many incorrect labels.

**Algorithm 1: Sliding window with fuzzy matching.** The solution (Algorithm 1 in the paper, with full details in Appendix B) combines two techniques:

*Sliding window search.* Instead of searching the entire original text for each compressed word, the algorithm constrains the search to a local window centered on the last matched position. Formally, for each word `$w$` in the compressed text `$S_{\text{comp}}$`, the algorithm searches positions `$\text{prev} - i$` (to the left) and `$\text{prev} + i$` (to the right) in the original text, where `$\text{prev}$` is the index of the last successfully matched word position in the original, and `$i$` iterates from 1 up to `$s/2$` (where `$s$` is the window size parameter). The search is **bidirectional** — it checks rightward positions first (natural forward progression, since most words maintain order) and then leftward positions (to handle localized reorderings where GPT-4 swapped adjacent words or phrases). By constraining the search to a window, the algorithm avoids the ambiguity problem: if "City" appears at position 10 and position 50 in the original, and the last match was at position 8, the window will only see the position 10 occurrence, correctly matching the compressed word to the nearest original occurrence in the expected reading order.

*Fuzzy matching with lemmatization.* To handle the variation obstacle, the algorithm does not perform exact string equality. Instead, it first applies **lemmatization** (using the spaCy library's lemmatizer) to reduce words to their base dictionary form: "consenting" → "consent," "properties" → "property," "adopt" (base form) stays "adopt." Matching is then performed on the lemmatized forms rather than the raw surface forms. When the compressed word "Consent" is being matched, the algorithm lemmatizes it to "consent," lemmatizes candidates in the window, and successfully matches the original "consenting" (also lemmatized to "consent"). This fuzzy matching absorbs GPT-4's morphological variations without requiring the compressor to learn those variations — the annotation produces consistent labels even when GPT-4 slightly deviates from instruction.

*New word handling.* If GPT-4 introduces a word not present in the original (violating instruction condition 5), the constrained window prevents false positives: the search will not find a match within the window, and the word is simply skipped — no original word gets incorrectly labeled as preserved. The sliding window thus serves double duty: ambiguity prevention (preventing wrong matches) and hallucination resilience (preventing fabricated words from corrupting labels).

**Walkthrough of Algorithm 1.** The procedure initializes all labels `$L$` for the original words `$S_{\text{ori}}$` to `False`. It maintains a `prev` pointer initialized to 0, tracking the last successful match position in the original. For each word `$w$` in the compressed text `$S_{\text{comp}}$`:

1. For `$i$` from 1 to `$s/2$` (searching progressively outward from the last match):
   - Compute `$\text{right} = \min(|S_{\text{ori}}|, \text{prev} + i)$` — a candidate position to the right.
   - If `fuzzy_match(w, S_{\text{ori}}[\text{right}])` succeeds (lemmatized forms match), set `$L[\text{right}] = \text{True}$`, update `$\text{prev} = \text{right}$`, and break to the next compressed word.
   - If the rightward search fails, compute `$\text{left} = \max(0, \text{prev} - i)$`.
   - If `fuzzy_match(w, S_{\text{ori}}[\text{left}])` succeeds, set `$L[\text{left}] = \text{True}$`, update `$\text{prev} = \text{left}$`, and break.

The bidirectional search (right first, then left) handles the common case where GPT-4 mostly preserves word order (most matches are rightward) while gracefully absorbing occasional local reorderings (the leftward fallback). The window size `$s$` controls the tradeoff: too small and reorderings beyond `$s/2$` positions will be missed; too large and ambiguous matches become likely. The paper does not specify the exact value of `$s$` used, but the description implies it is large enough to handle sentence-level reorderings while small enough to prevent cross-sentence ambiguity.

**Output.** The algorithm outputs a binary label vector `$L$` of length `$|S_{\text{ori}}|$` where `$L[j] = \text{True}$` means the `$j$`-th word of the original text is preserved in the compressed version (it was matched to some word in GPT-4's output), and `$L[j] = \text{False}$` means it is discarded.

#### Quality Control: Filtering Low-Quality Training Examples

Not all GPT-4 compressed outputs are created equal. Even with the carefully designed instruction, GPT-4 occasionally violates constraints — introducing new words, failing to match terms properly, or producing outputs that cannot be reliably aligned with the original text. Training on such low-quality examples would teach the compressor to reproduce GPT-4's mistakes. The paper introduces two filtering metrics and discards examples that score poorly on either.

**Variation Rate (VR) — Equation 1.** This metric measures the extent to which GPT-4 introduced words not present in the original text:

$$\text{VR} = \frac{1}{|S_{\text{comp}}|} \sum_{w \in S_{\text{comp}}} \mathbb{I}(w \notin S_{\text{ori}})$$

where `$S_{\text{comp}}$` is the set of word types (unique words) in the compressed text, `$S_{\text{ori}}$` is the set of word types in the original text, and `$\mathbb{I}(\cdot)$` is the indicator function (1 if the condition is true, 0 otherwise). The notation `$|\cdot|$` denotes set cardinality — the number of distinct word types, not tokens.

**What it computes:** the fraction of distinct word types in the compressed output that do not appear anywhere in the original text. If GPT-4 perfectly followed the "remove only" instruction, VR would be 0 — every word in the compressed output came from the original. A VR of 0.13 (as observed for Instruction1 in Table 7) means 13% of the compressed output's vocabulary is fabricated — words GPT-4 invented that weren't in the source.

**Why this form:** using set membership rather than token counts normalizes for word frequency — a hallucinated word that appears 20 times in the compressed output counts once, preventing high-frequency hallucinations from dominating the metric. Using word types also aligns with the annotation concern: even one hallucinated word type means GPT-4's output contains information not grounded in the original, which could mislead the downstream LLM or corrupt the training labels.

The paper discards examples with the **top 5% highest VR scores** — a lenient threshold that removes the most egregious hallucination cases while keeping the majority of examples. This is appropriate because some variation is inevitable (e.g., punctuation changes, capitalization differences) and a small amount of noise in training data can actually improve robustness.

**Alignment Gap (AG) — Equations 2–4.** This metric evaluates whether the annotation algorithm (Alg. 1) produced a reasonable label assignment by comparing two quantities:

First, the **Matching Rate (MR)** — what fraction of original word types received a `True` (preserved) label:

$$\text{MR} = \frac{1}{|S_{\text{ori}}|} \sum_{w \in S_{\text{ori}}} \mathbb{I}(l(w) = \text{True})$$

where `$l(w)$` is the label assigned by Algorithm 1 (True if the word was matched to some word in `$S_{\text{comp}}$`, False otherwise), and `$|S_{\text{ori}}|$` is the number of distinct word types in the original text.

Second, the **Hitting Rate (HR)** — what fraction of compressed word types were successfully matched to some original word type:

$$\text{HR} = \frac{1}{|S_{\text{ori}}|} \sum_{w \in S_{\text{comp}}} \mathbb{I}(w \in S_{\text{ori}})$$

Note that HR is normalized by `$|S_{\text{ori}}|$` (not `$|S_{\text{comp}}|$`), which makes it comparable in scale to MR — both are expressed as fractions of the original vocabulary size.

**The Alignment Gap** is the difference:

$$\text{AG} = \text{HR} - \text{MR}$$

**What AG captures:** In a perfect annotation, every word in the compressed text matches exactly one word in the original (high HR), and the matching is comprehensive — there aren't large swaths of original text that should have been matched but weren't (high MR). In this ideal case, HR ≈ MR, so AG ≈ 0.

A **large positive AG** indicates a problematic annotation: HR is high (most compressed words found matches in the original) but MR is low (few original words received True labels). This pattern emerges when Algorithm 1's sliding window repeatedly matches to the *same* original words — for example, if GPT-4's compressed output consists of a few key terms repeated, and the fuzzy matcher always latches onto the same high-frequency original occurrences, leaving other legitimate matches undiscovered. High AG means the annotation is "lazy" — it tagged too few words as preserved, even though the compressed text was longer and richer than the labels suggest.

**Why this form:** The subtraction HR − MR directly measures the discrepancy between "how much of the compressed vocabulary was matched" and "how much of the original vocabulary was matched." If both are commensurate, the annotation is balanced; if HR dominates, the annotation is under-labeling (many compressed words map to few original words). The paper discards examples with the **top 10% highest AG scores** — slightly more aggressive filtering than for VR because annotation quality is more directly tied to training signal quality.

**Filtering results.** After applying both filters, the resulting dataset (Table 8) contains **5,169 training examples** with an average original length of 3,635 tokens per chunk compressed to 1,415 tokens — a 2.57× compression ratio. This dataset is publicly released as part of the paper's contribution.

#### Token Classification Model: Architecture, Training, and Design Rationale

**Architecture.** The compressor is a **Transformer encoder** (Devlin et al., 2019) with a linear classification head on top. The paper experiments with two backbone encoders:

- **LLMLingua-2**: XLM-RoBERTa-large (Conneau et al., 2020), a 355M-parameter multilingual Transformer encoder pretrained on 100 languages. Training takes approximately 23 hours on the MeetingBank compression dataset.
- **LLMLingua-2-small**: multilingual-BERT (mBERT; Devlin et al., 2019), a 110M-parameter multilingual encoder (BERT-base size). Training takes approximately 16 hours.

Both are substantially smaller than the LLaMA-2-7B (7 billion parameters) used by Selective-Context and LLMLingua for entropy estimation — LLMLingua-2 is roughly 20× smaller (355M vs. 7B parameters), and LLMLingua-2-small is roughly 64× smaller (110M vs. 7B). This size reduction is possible because the model learns a focused token-level classification task rather than needing to model the full next-token distribution.

**Forward pass.** Given an original prompt consisting of `$N$` words `$\mathbf{x} = \{x_i\}_{i=1}^N$`, the computation proceeds as:

$$\mathbf{h} = f_\theta(\mathbf{x})$$

where `$f_\theta$` is the Transformer encoder (XLM-RoBERTa-large or mBERT) with parameters `$\theta$`, and `$\mathbf{h} = \{\mathbf{h}_i\}_{i=1}^N$` is the sequence of hidden state vectors — one `$d$`-dimensional vector per input token, where `$d$` is the model's hidden dimension (1024 for XLM-RoBERTa-large, 768 for mBERT-base). Each `$\mathbf{h}_i$` encodes the token `$x_i$` in the context of the **entire sequence** (both left and right neighbors), thanks to the bidirectional self-attention in the Transformer encoder.

Then, a linear classifier maps each hidden state to a 2-dimensional logit vector:

$$\mathbf{p}(x_i, \Theta) = \text{softmax}(\mathbf{W}\mathbf{h}_i + \mathbf{b})$$

where `$\mathbf{W} \in \mathbb{R}^{2 \times d}$` is the classification weight matrix, `$\mathbf{b} \in \mathbb{R}^2$` is the bias vector, and `$\Theta = \{\theta, \mathbf{W}, \mathbf{b}\}$` are all trainable parameters. The output `$\mathbf{p}(x_i, \Theta) \in \mathbb{R}^2$` is a probability distribution over the two classes: `$p_{\text{preserve}}$` (the probability that word `$x_i$` should be kept) and `$p_{\text{discard}} = 1 - p_{\text{preserve}}$`.

**Training loss.** The model is trained to minimize binary cross-entropy between its predictions and the automatic labels `$\mathbf{y} = \{y_i\}_{i=1}^N$` produced by Algorithm 1:

$$\mathcal{L}(\Theta) = \frac{1}{N} \sum_{i=1}^N \text{CrossEntropy}(y_i, \mathbf{p}(x_i, \Theta))$$

where each `$y_i \in \{0, 1\}$` (0 for discard, 1 for preserve), and the cross-entropy for a single token expands to `$-[y_i \log p_{\text{preserve}}(x_i) + (1 - y_i) \log (1 - p_{\text{preserve}}(x_i))]$`.

**What it computes:** For each word in each training example, the model produces a scalar probability `$p_{\text{preserve}}$` that the word should survive compression. The loss penalizes deviations from the ground-truth label: predicting high probability when the label is 0 (keep) is penalized by the first term; predicting low probability when the label is 1 (discard) is penalized by the second term. The loss is averaged over all `$N$` words in the example, then over all examples in the batch via stochastic gradient descent.

**Why this form:** Binary cross-entropy is the standard maximum-likelihood objective for binary classification. It is well-calibrated for probability estimation — unlike mean squared error, it heavily penalizes confident wrong predictions (e.g., predicting `$p_{\text{preserve}} = 0.99$` when `$y = 0$` costs `$-\log(0.01) \approx 4.6$` nats, while predicting `$p_{\text{preserve}} = 0.51$` costs only `$-\log(0.49) \approx 0.71$` nats). This is appropriate because the compression strategy (selecting the top `$\tau N$` words by `$p_{\text{preserve}}$`) relies on the probabilities being well-ordered — we care more about whether high-scoring words are truly important than about the exact probability values for low-scoring words.

**Training hyperparameters.** Both models are fine-tuned for **10 epochs** using the **Adam optimizer** (Kingma and Ba, 2015) with a **learning rate of 1e-5** and a **batch size of 10**. The training data consists of labeled examples from MeetingBank training split, processed through the data distillation, annotation, and quality control pipeline described above.

**Why a Transformer encoder rather than a causal LM?** This architectural choice is the paper's direct response to Challenge 2 (unidirectional context misses essential information). A causal language model processes text left-to-right: the representation of word `$x_i$` depends only on `$x_1, \dots, x_{i-1}$`. A Transformer encoder uses bidirectional self-attention: every token attends to every other token, so the representation of `$x_i$` depends on the full sequence `$x_1, \dots, x_N$`. 

Concretely, consider the earlier example: "The patient was prescribed aspirin, which turned out to be exactly the wrong medication for her condition." A bidirectional encoder can let the word "aspirin" attend to the later phrase "wrong medication," boosting its importance score because the right context reveals it as a critical entity. A unidirectional model cannot — "aspirin" is processed before "wrong medication" is seen, so right-context signals are invisible.

The paper emphasizes this in Section 4.1:

> "We employ a Transformer encoder as the feature extractor to leverage information from the bidirectional contexts of each token."

This is not a minor implementation detail — it is the architectural mechanism that addresses the paper's identified limitation of prior work. The bidirectional context enables the model to learn patterns like: "this noun is important because a later clause contrasts it" or "this function word is actually structurally necessary because removing it would make the following clause ungrammatical."

**Why train rather than use entropy zero-shot?** Training on GPT-4-distilled data directly addresses Challenge 1 (information entropy is not aligned with compression objective). Instead of using an unsupervised proxy (perplexity), the model learns from examples where GPT-4 — prompted with the explicit compression objective — made decisions about what to keep and what to remove. The training signal is supervision from a model that was itself trying to solve the compression task, not a byproduct of language modeling.

This is an instance of **knowledge distillation** (hence the paper's term "data distillation"): the teacher (GPT-4) demonstrates compression behavior on a training corpus, and the student (XLM-RoBERTa-large) learns to imitate that behavior. The student generalizes this behavior to new, unseen texts because the input features (word identities, syntactic structures, semantic roles) that predict GPT-4's keep/discard decisions on meeting transcripts also predict compression decisions on other domains — the redundancy patterns that GPT-4 learned to recognize (filled pauses, redundant modifiers, predictable syntactic completions) are properties of natural language generally, not just of meeting transcripts.

#### Compression Strategy at Inference Time

Once the token classifier is trained, compressing a new prompt at inference time involves three steps.

**Step 1: Determine the target number of tokens to preserve.** The user specifies a target compression ratio `$1/\tau$`, where `$\tau \in (0, 1]$` is the fraction of original tokens to retain. For example, 2× compression means `$1/\tau = 2$`, so `$\tau = 0.5$` — keep half the tokens. 5× compression means `$\tau = 0.2$` — keep one-fifth. Given an original prompt with `$N$` words, the target number of preserved words is:

$$\tilde{N} = \tau N$$

**Step 2: Score every word.** Run the original prompt through the trained token classifier. For each word `$x_i$`, the model outputs a scalar probability `$p_i = p_{\text{preserve}}(x_i)$` — its estimated likelihood of being preserved in a good compression. The model scores all `$N$` words in a single forward pass (since the encoder processes the full sequence in parallel), not sequentially.

**Step 3: Select top-`$\tilde{N}$` words by score.** Sort all `$N$` words by their `$p_i$` scores in descending order. Retain the `$\tilde{N}$` words with the highest scores. Crucially, these retained words are kept in their **original order** — the compression is a subsequence of the original, maintaining syntactic coherence. The discarded words are simply removed from the sequence. The resulting compressed prompt `$\tilde{\mathbf{x}}$` contains exactly `$\tilde{N}$` words, a faithful (extractive) subset of the original.

**Handling subword tokenization.** The paper notes an important engineering detail (footnote 2, Section 4.2). Transformer tokenizers (BPE for RoBERTa, WordPiece for BERT) split words into subword units. A single word like "compression" might be tokenized as `["compress", "ion"]` — two subword tokens. The classifier produces a separate `$p_{\text{preserve}}$` probability for each subword token. This creates a problem: if the model assigns high probability to "compress" but low probability to "ion," the word might be partially preserved ("compress" survives), producing a nonsensical output.

The solution: **word-level aggregation.** For a word that tokenizes into `$k$` subword tokens `$t_1, \dots, t_k$` with predicted probabilities `$p_{t_1}, \dots, p_{t_k}$`, the word's aggregate preservation probability is the **average** of its subword token probabilities:

$$p_{\text{word}} = \frac{1}{k} \sum_{j=1}^k p_{t_j}$$

The word is then preserved or discarded as a whole unit based on this aggregated score. This ensures that words are never split — either all subword tokens of a word survive or none do, maintaining the integrity of the original vocabulary and preventing the generation of partial words. The aggregation by averaging (rather than, say, taking the minimum) gives each subword token equal weight in the word's overall importance score.

**Integration with coarse-to-fine compression for very high ratios.** The paper notes (Section 4.2) that LLMLingua-2 can be integrated with the coarse-to-fine framework from the original LLMLingua (Jiang et al., 2023a) for tasks requiring very high compression ratios (∼15×) — for example, when compressing prompts containing multiple lengthy demonstrations or many retrieved documents. The integration is modular:

- The **coarse-grained** level (budget controller from original LLMLingua) allocates different compression budgets to different parts of the prompt based on a question-conditioned perplexity estimate — parts more relevant to the query get a larger token budget (less compression), less relevant parts get a smaller budget (more compression).
- The **fine-grained** level (LLMLingua-2's token classifier) performs the actual word selection within each part, replacing the original LLMLingua's perplexity-based iterative token removal with learned `$p_{\text{preserve}}$` probabilities.

This hybrid approach (described in Appendix K and evaluated in Table 11) benefits from LLMLingua-2's superior token-level decisions while retaining the query-conditioned budget allocation that makes LongLLMLingua effective for retrieval-augmented generation tasks.

**Dynamic (sample-wise) compression ratio (Appendix L).** The default inference strategy applies a fixed compression ratio `$\tau$` to every sample. The paper also explores a **sample-wise dynamic** approach: instead of fixing `$\tilde{N} = \tau N$` per sample, set a global probability threshold `$\theta$`, and for each sample, preserve all words with `$p_{\text{preserve}} > \theta$`. The threshold `$\theta$` is chosen such that, across the entire corpus, the average compression ratio equals the target `$1/\tau$`. Some samples (with many high-probability words) get compressed less; others (with few high-probability words) get compressed more.

Table 12 shows the impact on LongBench SingleDoc QA under a 7× target compression ratio. With a fixed ratio per sample, LLMLingua-2 achieves 25.1 QA score at 2,131 tokens. With dynamic per-sample ratios, it achieves 29.5 QA score at 2,125 tokens — a 4.4-point improvement with essentially the same average compression. The dynamic strategy helps because it allocates more token budget to information-dense samples (which need more words to preserve essential content) and less to redundant samples (which can be compressed more aggressively without information loss), whereas the fixed strategy uses the same compression ratio for both, over-compressing dense examples and under-compressing sparse ones.

#### Summary of Design Choices and Their Justifications

- **Extractive compression (remove only, no reordering, no new words)** over abstractive: guarantees faithfulness of compressed prompt to original content, preventing hallucination that could mislead downstream LLMs. Enables the compression task to be formulated as token classification rather than sequence generation, which is faster and more controllable.
- **Data distillation from GPT-4** over human annotation: scales to 5,169 training examples without manual labeling cost. The five-condition instruction constrains GPT-4's output to be extractive, making automatic annotation feasible.
- **Chunk-wise compression (512-token chunks)** over whole-document compression: prevents the degradation in GPT-4's compression quality observed with long inputs (Figure 4), ensuring consistent information preservation across document length.
- **Sliding window fuzzy matching with lemmatization** over exact string matching: absorbs GPT-4's occasional instruction violations (morphological changes, local reorderings) while preventing ambiguous matches through window constraint.
- **Binary token classification with Transformer encoder** over causal LM entropy estimation: directly optimizes the compression objective (learned from data) rather than using a proxy metric; leverages bidirectional context to capture importance signals from both left and right neighbors.
- **Small encoder models (355M, 110M parameters)** over large language models (7B parameters): reduces compression latency by 3×–6× (Table 5: 0.4–0.5 seconds vs. 1.5–15.9 seconds for LLaMA-2-7B-based methods) and GPU memory usage by 8× (2.1GB vs. 16.6–26.5GB; Appendix I), making the compressor practical for deployment.
- **Word-level aggregation of subword token probabilities (averaging)** over token-level decisions: prevents words from being split mid-word during compression, maintaining lexical integrity of the output.
- **Training on MeetingBank only** over multi-domain training: tests (and demonstrates) generalization — the learned compression patterns transfer across domains because linguistic redundancy (disfluencies, function words, predictable completions) is a general property of natural language, not domain-specific.

## 4. Key Insights and Innovations

### Innovation 1: Prompt Compression as a Supervised Learning Problem, Not an Information-Theoretic One

The field's dominant paradigm for task-agnostic prompt compression — exemplified by Selective-Context (Li et al., 2023) and LLMLingua (Jiang et al., 2023a) — treated compression as an **unsupervised signal processing problem**: run a language model over the text, compute a statistical measure of each token's "information content" (typically perplexity or entropy), and prune low-information tokens. This framing rests on a seductive but unverified assumption: that statistical predictability under a causal language model is a good proxy for importance to downstream task performance.

LLMLingua-2's central intellectual move is rejecting this assumption and reframing prompt compression as a **supervised learning problem with a learnable objective**. The question shifts from "what is the information-theoretic optimal way to compress text?" to "can we learn from examples what GPT-4 considers worth keeping, and then imitate those decisions?" This is not an incremental tweak — it is a fundamental reconceptualization of the problem class.

The significance of this reframing extends beyond the immediate performance gains. It opens the door to **compressors that adapt their behavior to specific requirements** by changing the training data rather than redesigning the algorithm. If you need a compressor that preserves legal terminology more aggressively than conversational filler, you train on legal-domain compression examples. If you need to guarantee that names and dates are always preserved, you construct training data where GPT-4 is explicitly instructed to do so. The entropy-based approach offers no such lever — you get whatever the LM's perplexity distribution gives you, and you cannot inject domain-specific preferences without building an entirely new heuristic.

The evidence for the superiority of the learned approach is not subtle. Table 1 shows that on the in-domain MeetingBank benchmark, LLMLingua-2 achieves 86.92% QA EM with a 3.1× compression ratio, close to the original prompt's 87.75%, while LLMLingua (entropy-based, using LLaMA-2-7B) achieves only 67.52% — a ~19-point gap despite using a smaller model (355M vs. 7B parameters). Table 7's ablation on instruction design makes explicit that the distillation procedure, not just any supervision, matters — the same supervised framework fails when trained on data produced by GPT-4 under weaker instructions (Instruction1 achieves only 19.1 QA F1 vs. LLMLingua-2's 36.7), because the training signal itself was corrupted by GPT-4's abstractive tendencies and hallucinated content.

This innovation also implicitly challenges a deeper assumption in prompt compression research: that **compression can be done without understanding what the downstream LLM needs**. Entropy-based methods operate entirely on the source text, with no signal about what matters for LLM reasoning. By using GPT-4 as the teacher — a model that itself is an LLM making judgments about what to preserve — the learned compressor indirectly learns something about what LLMs find useful in prompts, not just what is statistically anomalous in text. This is a form of **implicit preference learning**: GPT-4's compression decisions encode its own (unstated) model of what information is important for language understanding, and the student model absorbs that preference without ever being explicitly told why a particular word matters.

### Innovation 2: Bidirectional Context as a Mechanism for Capturing Non-Local Token Importance

Prior task-agnostic methods all used **causal language models** (LLaMA-2-7B in Selective-Context and LLMLingua) to score tokens. This architectural choice was inherited from the language modeling literature, where causal architectures are natural for next-token prediction. But prompt compression is not next-token prediction — it is a **global evaluation task**: determining whether a token at position i matters requires considering what comes after it as much as what came before.

LLMLingua-2 identifies this mismatch between architecture and task as a fundamental limitation, not a minor implementation detail. The replacement of a causal LM with a **bidirectional Transformer encoder** (XLM-RoBERTa-large or mBERT) is the architectural manifestation of a conceptual insight: token importance is a **whole-sequence property**, not a left-context property. A word's significance can be signaled by right context (contrast, elaboration, resolution), left context (setup, topic establishment), or both in combination (the word is the pivot between setup and resolution).

This is a genuinely non-obvious diagnostic. The entropy-based literature had not identified unidirectional context as a bottleneck because the information-theoretic framing made the causal architecture seem natural — perplexity is defined over left context by definition. The paper's contribution is recognizing that this architectural constraint is not intrinsic to the compression problem but rather an artifact of the metric choice, and that switching the metric (to learned classification) creates the freedom to choose an architecture better suited to the task.

The practical impact of bidirectional context is visible qualitatively in Figure 6, where LLMLingua-2's compression decisions show **context awareness**: at 2× compression, the model preserves words that carry semantic weight ("report," "City Manager," "Recommendation," "adopt," "three resolutions") while discarding function words and filler. As compression increases to 5×, it retains an even sparser set of words that still capture the core meaning of the passage. This graded behavior — preserving more words when budget allows, fewer when it doesn't, while maintaining semantic coherence at each level — requires understanding which words are load-bearing for meaning, which in turn requires seeing how each word relates to the whole. A unidirectional model would struggle with cases where a word's importance is only apparent from what follows (e.g., "the patient was prescribed aspirin, which turned out to be exactly the wrong medication" — "aspirin" matters because of the right-context revelation that it was harmful).

The significance of this innovation extends beyond prompt compression. It suggests a broader principle: **for any task involving selection or filtering of elements within a sequence, bidirectional encoders may be systematically better than causal decoders**, because they can leverage the full information context for each decision. This has implications for related tasks like text highlighting, keyphrase extraction, and evidence selection — all of which have often defaulted to causal architectures or simple statistical heuristics without considering the bidirectional alternative.

### Innovation 3: Data Distillation as a General Strategy for Constructing Task-Specific Training Data from LLMs

The paper's method for building training data — prompt a strong LLM (GPT-4) with carefully constrained instructions to produce examples of desired behavior, automatically annotate those examples to create supervision signals, filter low-quality instances, and train a smaller model on the result — is presented as a solution to the specific problem of prompt compression, but it represents a more general **data creation methodology** that the paper both demonstrates and implicitly advocates.

What makes this contribution distinctive is not the idea of using LLM outputs as training data (which is common in the distillation literature), but the **engineering of the distillation pipeline to produce a specific, constrained type of output** (extractive compression, in this case) from a model that naturally produces something else (abstractive summarization or free-form text). The paper identifies that naive prompting fails (GPT-4 rephrases, hallucinates, cannot hit compression targets), diagnoses the failure modes, and designs a multi-component solution:

- **Instruction constraints** (five explicit prohibitions) that narrow GPT-4's output space to be extractive rather than abstractive.
- **Chunk-wise processing** that prevents the degradation observed with long inputs (Figure 4), ensuring consistent behavior across document lengths.
- **Fuzzy annotation** (Algorithm 1) that absorbs residual instruction violations (variation, reordering) without requiring perfect compliance.
- **Quality control metrics** (Variation Rate, Alignment Gap) that automatically identify and filter corrupted training examples.

Each of these components individually is not novel — constrained prompting, chunking, fuzzy matching, and filtering are all standard techniques. The innovation is the **systematic integration** of these components into a pipeline that reliably produces high-quality labeled data for a task where no natural labeled dataset exists. The ablation in Table 7 demonstrates that the pipeline's success is not attributable to any single component — removing the chunk-wise compression drops QA F1 from 36.7 to 27.9; switching to weaker instructions (Instruction1 through Instruction4) produces variation rates of 7.8–13.7% and QA F1 scores of 19.1–26.1, far below LLMLingua-2's 36.7 with 2.2% variation rate. The combination matters.

The broader implication is that **LLMs can be used to bootstrap supervised datasets for tasks that lack natural supervision**, but only if the distillation pipeline is engineered to overcome the LLM's natural tendencies (verbosity, abstraction, instruction non-compliance) that produce outputs misaligned with the target task format. This is a lesson that transfers to other domains: if you want an LLM to produce extractive rationales, structured annotations, or format-constrained outputs for training data, you need more than a prompt — you need a pipeline that constrains, annotates, and filters the outputs to enforce the desired structure.

### Innovation 4: Verifying That Learned Compression Generalizes Across Domains and Target LLMs — Establishing a New Baseline

A reasonable prior expectation, given that the compressor is trained exclusively on meeting transcripts from MeetingBank, would be that its learned compression policy overfits to the disfluencies, vocabulary, and discourse patterns of procedural government meetings. If the model learned domain-specific heuristics ("always remove 'um' and 'council member'"), it would fail catastrophically on out-of-domain data like math word problems (GSM8K) or logical reasoning tasks (BBH).

The paper's out-of-domain results (Tables 2, 3, 4) constitute a **strong empirical refutation of this overfitting hypothesis** and thereby establish a conceptual finding: **there exist general, transferable patterns of linguistic redundancy that can be learned from one domain and applied to others**. On LongBench under the 2,000-token constraint, LLMLingua-2 achieves a 39.1 average score vs. 34.6 for LLMLingua and 24.8 for Selective-Context — approaching the original prompt's 44.0 despite a 5× compression. On GSM8K, it matches full-shot accuracy (79.08%) at 5× compression and retains 77.79% at 14× compression. On the Chinese LongBench benchmarks (Table 10, Appendix J), despite being trained only on English meeting data, LLMLingua-2 achieves 38.1 average score vs. 28.6 for LLMLingua — demonstrating cross-lingual generalization that leverages the multilingual pretraining of XLM-RoBERTa-large.

What makes this finding interesting beyond the raw numbers is what it implies about **the nature of redundancy in natural language**. The fact that a compressor trained on meeting transcripts works on math problems and logical reasoning tasks suggests that the core compression skill is not domain-specific content filtering (e.g., "keep legal terms") but rather a more fundamental ability to distinguish **structurally essential words** from **structurally optional words** — a distinction that holds across domains because it reflects universal properties of how meaning is encoded in language, not domain-specific content importance. Nouns, verbs, numerals, and adjectives tend to carry more semantic weight than articles, auxiliaries, and filled pauses regardless of whether the text is about city budgets or arithmetic.

The generalization across target LLMs (from GPT-3.5-Turbo to Mistral-7B, Table 4) is equally significant. It shows that the compressor is not learning to preserve what GPT-3.5-Turbo specifically needs (which would be a form of target-model overfitting) but rather what **any competent LLM** needs — the information that is genuinely essential for understanding the text. The finding that LLMLingua-2 sometimes **improves** over the original prompt with Mistral-7B (Table 4, LongBench SingleDoc QA: 35.0 vs. 31.4 for the original) suggests that the compression is not merely lossless but potentially beneficial — by removing distracting or redundant content, it may help the target LLM focus on what matters, particularly for models like Mistral-7B that are less adept at handling very long contexts.

This establishes LLMLingua-2 not just as a method but as a **new baseline for task-agnostic prompt compression** — the first task-agnostic approach that consistently approaches original-prompt performance across diverse benchmarks while using a fraction of the tokens and substantially less compression overhead than prior methods. Future work in this space must now compare against a learned, bidirectional compressor rather than only entropy-based heuristics.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper evaluates on five benchmarks spanning multiple tasks and domains. For in-domain evaluation, the test split of **MeetingBank** (Hu et al., 2023) is used — 862 meeting transcripts for which GPT-4-generated QA pairs and summaries serve as ground truth. For out-of-domain evaluation: **LongBench** (Bai et al., 2023), a bilingual multitask benchmark for long-context understanding covering single-document QA, multi-document QA, summarization, few-shot learning, synthetic tasks, and code completion; **ZeroSCROLLS** (Shaham et al., 2023), a zero-shot benchmark for long text understanding; **GSM8K** (Cobbe et al., 2021), a dataset of grade-school math word problems requiring multi-step reasoning; and **Big Bench Hard (BBH)** (bench authors, 2023), a suite of challenging reasoning tasks from BIG-Bench. Chinese benchmarks from LongBench are also evaluated (Appendix J). The MeetingBank training split is used exclusively for constructing the compression dataset (via GPT-4 distillation) and training the compressor; all reported results are on held-out test sets.

- **Base model(s).** The primary target LLM for downstream task evaluation is **GPT-3.5-Turbo-0613**, accessed via the OpenAI API with greedy decoding (temperature 0) for stability across experiments. Additional evaluations use **Mistral-7B-v0.1** (Jiang et al., 2024; Mistral AI) as the target LLM to test generalization across model families (Table 4, Table 13). For data distillation, **GPT-4-32k** is used as the teacher model to generate compression examples from MeetingBank transcripts. The compressor itself uses either **XLM-RoBERTa-large** (355M parameters; Conneau et al., 2020) — referred to as LLMLingua-2 — or **multilingual-BERT** (110M parameters; Devlin et al., 2019) — referred to as LLMLingua-2-small.

- **Metrics.** For MeetingBank QA, the metric is **Exact Match (EM)** — the fraction of questions for which the model's answer exactly matches the ground-truth answer. For MeetingBank summarization, the paper reports **Rouge1, Rouge2, RougeL** (Lin, 2004) and **BERTScore** (Zhang et al., 2020) against GPT-4-generated reference summaries. For LongBench and ZeroSCROLLS, the evaluation follows the protocols and metrics established by each benchmark (which include F1, Rouge-L, and exact match depending on the sub-task), averaged across sub-tasks to produce the reported "AVG" score. For GSM8K and BBH, **Exact Match** is the primary metric. All metrics are computed after the compressed prompt (or original prompt, for baselines) is fed to the target LLM.

- **Baselines.** Two primary task-agnostic baselines are compared: **Selective-Context** (Li et al., 2023), which estimates token importance using self-information from LLaMA-2-7B and prunes low-importance lexical units; and **LLMLingua** (Jiang et al., 2023a), which uses perplexity from LLaMA-2-7B within a coarse-to-fine budget-controlled compression framework. Both baselines use the same LLaMA-2-7B backbone for importance estimation. For some comparisons, task-aware baselines are also reported: **SBERT** (a retrieval-based compression method), **OpenAI** embeddings-based retrieval, and **LongLLMLingua** (Jiang et al., 2023b), a question-aware extension of LLMLingua that conditions compression on the query. The **Original Prompt** (uncompressed) and **Zero-Shot** (no prompt, only the question) serve as upper and lower reference points, respectively.

- **Generation budget / compute accounting.** Compression is measured in **token count** — the number of words in the compressed prompt vs. the original. Compression ratio is expressed as `$1/\tau$`, where `$\tau$` is the fraction of original words retained (e.g., 3× means `$\tau = 1/3$`). All methods are compared at equivalent compression ratios or token budgets: for a fair comparison, the paper reports both the achieved accuracy and the actual token count after compression, confirming that methods achieve similar compression levels. For latency evaluation (Table 5), wall-clock time is measured on a V100-32G GPU, with "End2End" reporting the total time from receiving the original prompt to receiving the LLM's response (including compression overhead). The compression model's own inference latency is reported separately to isolate overhead.

- **Cross-validation / statistical protocol.** No formal cross-validation is described — the compressor is trained once on the full MeetingBank training set and evaluated on held-out test benchmarks. However, the paper does employ **sample-wise dynamic compression** as a robustness check (Appendix L): instead of fixing the same compression ratio per sample, a global probability threshold is set such that the average compression ratio across the corpus matches the target, allowing information-dense samples to be compressed less aggressively. For the comparison with GPT-4 compression (Table 9, Appendix O), GPT-4 is prompted with the same instruction and chunking procedure used during data distillation. For the Mistral-7B experiments (Table 13, Appendix P), a subset excluding samples with inputs exceeding Mistral-7B's 8K-token training context length is evaluated to isolate the effect of context length from compression quality.

### Main Quantitative Results

#### In-Domain Evaluation on MeetingBank

**Table 1** reports the primary in-domain comparison on the MeetingBank test set at approximately 2.5–3.1× compression. The headline result is that LLMLingua-2 achieves **86.92% QA EM** with a compressed prompt of 970 tokens (3.1× compression), approaching the original prompt's 87.75% with 3,003 tokens. LLMLingua-2-small achieves 85.82% with 984 tokens (3.0×). In contrast, LLMLingua (entropy-based) achieves only **67.52%** (a 19.4-point gap) and Selective-Context achieves 66.28% (a 20.6-point gap), despite both using a 20× larger language model (LLaMA-2-7B) for importance estimation. Both entropy-based methods produce compressed prompts roughly 20% shorter than LLMLingua-2's (1,176–1,222 tokens vs. 970–984), yet deliver substantially worse downstream performance.

On the summarization task, the pattern differs. All compression methods reduce Rouge scores relative to the original prompt (Rouge1: 48.64 for LLMLingua-2 vs. 47.28 original; Rouge2: 22.96 vs. 26.66; RougeL: 34.24 vs. 35.15). LLMLingua-2 slightly outperforms the entropy-based baselines (e.g., Rouge1: 48.64 vs. 37.98 for LLMLingua) but the summarization metrics show smaller absolute gaps than the QA metrics. BERTScore, which measures semantic similarity rather than n-gram overlap, is nearly identical across methods (88.27 for LLMLingua-2 vs. 88.96 original vs. 86.42 for LLMLingua), suggesting that compressed prompts largely preserve the gist even when they drop specific details needed for exact-match QA.

The key interpretation: QA performance is the more stringent test of information preservation because answering a specific question often requires retaining a particular named entity, number, or clause that a summarization would naturally omit. LLMLingua-2's strong QA performance — nearly matching the original prompt — indicates it preserves these crucial details that entropy-based methods lose.

#### Out-of-Domain Evaluation on Long-Context Scenarios

**Table 2** reports results on LongBench and ZeroSCROLLS under two token budget constraints: 2,000 tokens (approximately 5× compression) and 3,000 tokens (approximately 3× compression). Under the 2,000-token constraint (5× compression), LLMLingua-2 achieves an **average score of 39.1** on LongBench, compared to 34.6 for LLMLingua and 24.8 for Selective-Context. On ZeroSCROLLS, LLMLingua-2 achieves **33.4** vs. 27.2 for LLMLingua and 19.4 for Selective-Context. Under the 3,000-token constraint (3× compression), the gap narrows but persists: 42.4 for LLMLingua-2 vs. 37.4 for LLMLingua and 32.0 for Selective-Context on LongBench.

Breaking down by LongBench sub-task reveals an important pattern. LLMLingua-2's advantage is most pronounced on **FewShot** tasks (66.4 at 2,000 tokens vs. 61.2 for LLMLingua), **Synthetic** tasks (21.3 vs. 10.4), and **Code** tasks (58.9 vs. 56.8). On **Summarization** tasks, all methods perform similarly (24.5–25.3), consistent with the MeetingBank summarization finding that compressed prompts preserve high-level meaning across methods. On **SingleDoc QA** and **MultiDoc QA**, LLMLingua-2 shows consistent improvement (29.8 vs. 22.4 and 33.1 vs. 32.1, respectively) but the gap is smaller. This pattern suggests the learned compressor particularly excels at preserving the detailed reasoning steps and structured information needed for few-shot demonstrations and code, whereas summarization tasks are less sensitive to compression quality since they only require the gist.

On the Zero-shot baseline (no demonstrations, only the task instruction and question), GPT-3.5-Turbo achieves only 23.5 on LongBench and 10.8 on ZeroSCROLLS — substantially below all compression methods even at 5× compression. This confirms that compression preserves useful information beyond what the LLM already knows, and that the compressed prompts are genuinely informative rather than merely shorter versions of already-uninformative text.

Comparing LLMLingua-2 against task-aware methods reveals the expected tradeoff. **LongLLMLingua**, which conditions compression on the query, achieves **48.0** on LongBench under the 2,000-token constraint and 48.8 under the 3,000-token constraint — 8.9 and 6.4 points ahead of LLMLingua-2, respectively. The paper explicitly acknowledges this gap (Section 5): "While our approach has shown promising results, it falls short when compared to other task-aware compression methods... We attribute this performance gap to the additional information that they leverage from the question." The task-aware advantage is largest on FewShot and Synthetic tasks, where knowing the downstream question helps identify which demonstration details are relevant.

#### Out-of-Domain Evaluation on Reasoning and In-Context Learning

**Table 3** reports results on GSM8K (math reasoning) and BBH (logical reasoning) under two compression settings: 1-shot (one demonstration compressed to roughly 450 tokens, 5× compression) and half-shot (the same demonstration compressed to roughly 170 tokens, 11–14× compression). 

On **GSM8K 1-shot**, LLMLingua-2 achieves **79.08% EM**, matching both LLMLingua (79.08%) and full-shot accuracy (78.85%). Selective-Context drops substantially to 53.98%, suggesting its compression aggressively removes numeric and procedural tokens essential for math reasoning. The compressed prompts from LLMLingua-2 and LLMLingua are of similar length (457 and 446 tokens, respectively). On the **half-shot** setting (14× compression to 178 tokens), LLMLingua-2 achieves 77.79%, slightly above LLMLingua's 77.41% and close to the full-shot 78.85%. Remarkably, compressing the demonstration to one-fourteenth its original length loses only about 1 percentage point of accuracy — the demonstration's core reasoning pattern is preserved despite aggressive pruning.

On **BBH 1-shot** (3× compression), LLMLingua-2 achieves **70.02%**, essentially tied with LLMLingua (70.11%) and the full-shot prompt (70.07%). On the half-shot setting (5× compression to 176 tokens), LLMLingua-2 achieves 61.94% vs. 60.35% for LLMLingua-2-small and 61.60% for LLMLingua — all within approximately 1.5 points of each other. The zero-shot baseline (32.32%) confirms that the compressed demonstrations still carry substantial useful information even at 5× compression.

The GSM8K and BBH results reveal that on reasoning tasks with structured demonstrations (step-by-step solutions), **LLMLingua-2 performs roughly equivalently to the entropy-based LLMLingua** — the learned advantage observed on long-context understanding tasks (LongBench, ZeroSCROLLS) does not translate into a clear margin on reasoning tasks. Possible explanations: (1) reasoning demonstrations are dense with information (every step matters), leaving less redundancy for learned patterns to exploit; (2) the entropy heuristic may be adequate for identifying key reasoning tokens, since they tend to be statistically surprising (numbers, operators, logical connectives) relative to surrounding text; (3) the compressor was trained on meeting transcripts, whose redundancy patterns differ from the highly structured format of math and logic demonstrations.

#### Generalization Across Target LLMs: Mistral-7B

**Table 4** evaluates all methods using **Mistral-7B** as the target LLM on MeetingBank and LongBench SingleDoc QA. This is a critical test: if the compressor learned compression patterns specific to GPT-3.5-Turbo's preferences, it would underperform when the target LLM changes. The results refute this hypothesis.

On MeetingBank QA, LLMLingua-2 achieves **76.22% EM** with 970 tokens (3.0× compression), substantially outperforming both the original prompt (66.95% with 3,003 tokens) and the entropy baselines (Selective-Context: 58.13%, LLMLingua: 50.45%). The compressed prompt not only preserves essential information but **improves** over the original — a 9.3-point gain. The paper speculates that "Mistral-7B might be less adept at managing long contexts than GPT-3.5-Turbo. Our method, by offering shorter prompts with higher information density, effectively improves Mistral-7B's final inference performance."

On LongBench SingleDoc QA under the 2,000-token constraint, LLMLingua-2 achieves **26.8%** vs. 24.5% for the original prompt (14,511 tokens) — another case where compression improves over the raw input. On the 3,000-token constraint, LLMLingua-2 achieves 27.3% vs. 24.5% original. The entropy baselines also sometimes improve over the original with Mistral-7B (Selective-Context achieves 26.0% under the 3,000-token constraint), but LLMLingua-2 consistently outperforms them.

**Table 13** (Appendix P) reports the same experiment restricted to samples with original prompts under 8,000 tokens (Mistral-7B's training context length). On this subset, LLMLingua-2 achieves 81.75% QA EM on MeetingBank (vs. 71.27% original) and 35.0% on LongBench SingleDoc (vs. 31.4% original) under the 2,000-token constraint. The pattern holds: compression helps Mistral-7B even when the original prompt is within its training context length, suggesting the benefit is not merely about staying within context limits but about **reducing the cognitive load** of processing redundant information.

The generalization across target LLMs is a genuinely surprising and important finding. It implies that the compressor is learning a notion of "essential information" that is **not LLM-specific** — it preserves what any competent language model needs for understanding, rather than what a particular model happens to rely on. This universality makes the approach significantly more practical for deployment with black-box or changing backend LLMs.

#### Latency and Efficiency Evaluation

**Table 5** reports wall-clock latency on a V100-32G GPU for MeetingBank compression at various ratios. The key numbers:

- **End-to-end latency without compression**: 14.9 seconds (prompt + GPT-3.5-Turbo inference).
- **End-to-end latency with LLMLingua-2**: 9.4 seconds at 2× (1.6× speedup), 7.5 seconds at 3× (2.1× speedup), 5.2 seconds at 5× (2.9× speedup).
- **Compression overhead only (LLMLingua-2)**: 0.5 seconds at 2×, 0.4 seconds at 3–5× — negligible relative to end-to-end time.
- **Compression overhead for baselines**: Selective-Context takes 15.5–15.9 seconds for compression alone (longer than the uncompressed end-to-end time, making it useless as an accelerator on this hardware). LLMLingua takes 1.5–2.9 seconds.

LLMLingua-2 is **3×–6× faster at compression** than LLMLingua and roughly **30–40× faster** than Selective-Context. The speedup comes from two sources: the compressor model is ~20× smaller (355M vs. 7B parameters), and it processes the entire sequence in one parallel forward pass (bidirectional encoder) rather than token-by-token autoregressive scoring (causal LM). The compression overhead of 0.4–0.5 seconds is small enough that the end-to-end speedup closely tracks the token reduction: 2× compression yields 1.6× end-to-end speedup (not quite 2× because the LLM's per-token cost varies with sequence position), 5× compression yields 2.9× speedup.

**Appendix I** reports GPU memory usage: LLMLingua-2 peaks at 2.1GB, compared to 16.6GB for LLMLingua and 26.5GB for Selective-Context — an 8×–13× reduction. This lower memory footprint is significant for deployment on resource-constrained hardware where loading a 7B-parameter model solely for prompt compression would be impractical.

#### Integration with Task-Aware Coarse-Grained Compression

**Table 11** (Appendix K) evaluates the integration of LLMLingua-2 with LongLLMLingua's coarse-grained budget controller on NaturalQuestions with 20 retrieved documents. Under a 4× compression constraint, LLMLingua-2+ (LLMLingua-2 with query-conditioned budget allocation from LongLLMLingua) achieves **74.0%** on the first retrieved document position, compared to 75.0% for the full LongLLMLingua system and 48.6% for question-agnostic LLMLingua-2 alone. Averaged across positions 1 through 20 (the "Reorder" column), LLMLingua-2+ achieves 71.9% vs. 75.5% for LongLLMLingua and 46.2% for LLMLingua-2 alone.

The gap between LLMLingua-2+ (71.9%) and pure LLMLingua-2 (46.2%) demonstrates that when the task involves identifying which of many documents is relevant to a query, the question-agnostic compression alone cannot match question-aware budget allocation — it spreads the token budget evenly across all documents rather than concentrating it on the relevant ones. The gap between LLMLingua-2+ (71.9%) and LongLLMLingua (75.5%) reflects the remaining advantage of question-conditioned fine-grained token scoring (LongLLMLingua adjusts per-token importance based on query relevance, whereas LLMLingua-2+ only uses the question for coarse budget allocation and applies the learned task-agnostic token classifier within each document).

This integration demonstrates that LLMLingua-2's token classifier is **modular** — it can replace the entropy-based scoring in prior systems while preserving their architectural innovations (coarse-grained budget control), yielding a hybrid that outperforms either pure approach on retrieval-heavy tasks.

#### Additional Generalization Tests

**Table 10** (Appendix J) evaluates on **Chinese LongBench benchmarks**. Despite being trained solely on English meeting transcripts, LLMLingua-2 achieves **38.1** average score vs. 28.6 for LLMLingua under 5× compression — a 9.5-point improvement. The paper attributes this to "the multilingual capabilities of the xlm-roberta-large or multilingual-BERT compressor acquired from the pre-training phase." Supporting this interpretation: LLMLingua-2 uses XLM-RoBERTa-large, which was pretrained on 100 languages including Chinese; LLMLingua uses LLaMA-2-7B, which is predominantly English-trained. The cross-lingual transfer works because (1) the compressor's pretrained multilingual representations capture word-level importance patterns that generalize across languages, and (2) the underlying redundancy patterns (function words, filled pauses, syntactic completions) are similar across languages even though the specific words differ.

**Table 12** (Appendix L) compares fixed-ratio vs. sample-wise dynamic compression on LongBench SingleDoc QA. Under a 7× target compression ratio, LLMLingua-2 with fixed per-sample ratio achieves 25.1 QA score at 2,131 tokens. With dynamic per-sample ratios (same average compression, different per-sample ratios), it achieves **29.5** at 2,125 tokens — a 4.4-point improvement for the same average token budget. Under a 5× target, dynamic achieves 32.2 vs. 27.4 fixed. The dynamic strategy works because some samples are information-dense (needing more tokens) while others are redundant (able to be compressed more aggressively); the fixed strategy over-compresses the former and under-compresses the latter.

**Table 6** reports results when the training dataset is expanded with 50,000 examples from TriviaQA-wiki (in addition to MeetingBank), labeled as "LLMLingua-2‡." The expanded-data model achieves 39.5 average on LongBench vs. 39.1 for the MeetingBank-only LLMLingua-2 under the 2,000-token constraint — a 0.4-point improvement. The paper notes this is "not that significant" and conjectures that "although the semantics of texts from different domains may vary a lot, their redundancy pattern might be similar. Such pattern or knowledge may be learned during in-domain training, and then act as an anchor that can transfer across different domains." This is a key finding about the nature of the learned compression: it appears to capture domain-invariant redundancy patterns, with limited marginal benefit from additional in-domain data.

**Table 9** (Appendix O) directly compares LLMLingua-2 compressed prompts against **GPT-4 compressed prompts** (using the same instruction and chunking procedure as training data generation) on MeetingBank QA. LLMLingua-2 achieves **86.92% EM** with 970 tokens, outperforming GPT-4 compression (84.86% with 1,221 tokens) despite using fewer tokens (31× vs. 2.5× compression ratio). The paper conjectures that "LLMLingua-2's ability to learn compression knowledge from the entire dataset helps mitigate the influence of noise and information loss present in each GPT-4 compressed example, leading to superior performance." In other words, the student (LLMLingua-2) surpasses the teacher (GPT-4) on this specific task by aggregating knowledge across many imperfect demonstrations, averaging out the idiosyncratic errors in any single GPT-4 compression.

### Ablation Studies and Robustness Checks

**Instruction design and chunk-wise compression (Table 7):** The ablation compares four alternative instructions (Instruction1 through Instruction4, proposed in prior work) against LLMLingua-2's instruction, with and without chunk-wise compression. LLMLingua-2's instruction with chunk-wise compression achieves 2.6× compression ratio, 2.2% variation rate, and 36.7 QA F1. Without chunk-wise compression ("LLMLingua-2 w/o Chunk"), the compression ratio jumps to 21× (GPT-4 over-compresses long contexts), variation rate rises to 6.0%, and QA F1 drops to 27.9 — a clear demonstration that chunk-wise processing is essential for information preservation. The alternative instructions (Fig. 10) produce substantially worse results: Instruction1 achieves 123× compression but 13.7% variation rate and only 19.1 QA F1; Instruction2 achieves 27× compression, 7.8% VR, and 26.1 F1. The ablation establishes that both the instruction design (five extractive constraints) and the chunk-wise processing are necessary for the distillation pipeline to produce useful training data.

**Compression ratio vs. performance (Figure 15, Appendix M):** Performance of LLMLingua-2, LLMLingua, and Selective-Context is plotted against compression ratio (1× to 10×) on a 100-sample subset of MeetingBank for both QA (Fig. 15a) and summarization (Fig. 15b). LLMLingua-2's QA accuracy degrades gracefully from ~80% EM at 1× (uncompressed) to ~65% at 5× and ~55% at 10×, while LLMLingua drops from ~65% at 1× to ~20% at 10×. Selective-Context shows erratic behavior with a sharp drop-off. On summarization, LLMLingua-2's Rouge1 stays within 40–48% across all ratios up to 10×, while baselines decline more steeply. The curves demonstrate LLMLingua-2's superior **robustness** to increasing compression — it maintains useful performance at ratios where entropy-based methods collapse.

**Compressor model size (LLMLingua-2 vs. LLMLingua-2-small, across all tables):** The smaller mBERT-based compressor (110M parameters) achieves performance close to the larger XLM-RoBERTa-large variant (355M) in nearly all evaluations. On MeetingBank QA (Table 1): 85.82% vs. 86.92%. On LongBench 2,000-token (Table 2): 38.2 vs. 39.1 average. On GSM8K 1-shot (Table 3): 78.92% vs. 79.08%. The small model occasionally matches or exceeds the large model (e.g., GSM8K half-shot: 77.48% vs. 77.79%). This suggests that the compression task is **not parameter-intensive** — even a BERT-base-sized model can capture the redundancy patterns needed for effective token classification, making the approach viable for extremely resource-constrained deployment.

**Training data expansion with TriviaQA (Table 6):** Adding 50,000 examples from TriviaQA-wiki to the MeetingBank training data yields LLMLingua-2‡, which achieves 39.5 average on LongBench (2,000-token constraint) vs. 39.1 for the MeetingBank-only model — a marginal 0.4-point gain. On ZeroSCROLLS, both models achieve identical 33.4 average. The paper interprets the small improvement as evidence that the compression patterns learned from meeting transcripts already generalize broadly, and that additional in-domain data provides diminishing returns because "their redundancy pattern might be similar." This is a negative result with important practical implications: training on a single domain may be sufficient, reducing the need for diverse compression training data.

**Sample-wise dynamic compression ratio (Table 12, Appendix L):** Allowing per-sample compression ratios (while maintaining a corpus-level average) improves LongBench SingleDoc QA from 25.1 to 29.5 under a 7× target and from 27.4 to 32.2 under a 5× target. This ablation demonstrates that the compressor's probability scores are well-calibrated for **relative** comparisons across samples — tokens in information-dense samples receive systematically lower preservation probabilities than tokens in redundant samples, allowing a global threshold to naturally produce variable per-sample compression ratios that match information density. If the probabilities were miscalibrated (e.g., all samples produced similar score distributions), dynamic compression would not outperform fixed-ratio compression.

**Verifier / teacher model: GPT-4 Direct Compression vs. LLMLingua-2 (Table 9, Appendix O):** LLMLingua-2's compressed prompts achieve higher QA EM (86.92%) than GPT-4's own compressed prompts (84.86%) on MeetingBank, despite using fewer tokens (970 vs. 1,221). This counterintuitive result — the student outperforms the teacher — is attributed to the student's ability to learn from the aggregate pattern across all training examples, smoothing out the noise and inconsistency present in individual GPT-4 outputs. It also confirms that the compression model has genuinely learned something beyond simple imitation of GPT-4's specific decisions.

**Target LLM sensitivity (Mistral-7B vs. GPT-3.5-Turbo, Tables 4 and 13):** The compressed prompts from LLMLingua-2 transfer effectively across target LLMs, as demonstrated by the Mistral-7B results. Notably, LLMLingua-2-compressed prompts often improve over the original prompt with Mistral-7B (e.g., MeetingBank QA: 76.22% vs. 66.95% original), whereas with GPT-3.5-Turbo the compressed prompts roughly match or slightly underperform the original. This asymmetry suggests that **stronger LLMs are more robust to prompt length**, extracting useful information from redundant text that weaker LLMs find distracting. The compressor effectively "translates" verbose natural language into a denser form that helps weaker LLMs focus on essential content.

**Coarse-to-fine integration (Table 11, Appendix K):** Replacing LLMLingua's perplexity-based token scoring with LLMLingua-2's learned classifier, while retaining LongLLMLingua's question-conditioned budget allocation, yields LLMLingua-2+ with 71.9% average accuracy on NaturalQuestions reorder task vs. 75.5% for the full LongLLMLingua and 46.2% for pure LLMLingua-2. The ablation demonstrates modularity — LLMLingua-2's token classifier can be dropped into existing budget-allocation frameworks, and it substantially improves over the entropy-based token scoring within those frameworks, even if the question-conditioned budget allocation provides additional gains.

**Qualitative analysis of compression outputs (Figures 6, 11, 12):** Figure 6 visualizes LLMLingua-2's compression at three ratios (2×, 3×, 5×) on two meeting transcript examples, with color coding showing which words survive at each ratio. The visualizations reveal **graded, context-aware compression**: at 2×, most content words are preserved with function words pruned; at 3×, moderate pruning of content words; at 5×, only the most essential information-bearing words remain, yet the semantic thread is still recoverable. Figures 11 and 12 compare LLMLingua-2's compressed outputs against LLMLingua's on BBH and GSM8K examples. LLMLingua's compressed outputs show artifacts of the entropy heuristic — partial words, broken syntactic structures, and apparently random preservation patterns — while LLMLingua-2's outputs maintain readable, syntactically coherent text even at aggressive compression ratios, despite being trained only on meeting transcripts. This cross-domain coherence is qualitatively striking and supports the quantitative finding of strong out-of-domain generalization.

**GPT-4 compression patterns (Figure 16, Appendix N):** Analysis of GPT-4's compression decisions by part-of-speech shows that nouns, adjectives, and numerals are preferentially preserved (their frequency in compressed vs. original text increases), while determiners, prepositions, and pronouns are preferentially discarded (their frequency decreases). This POS distribution provides insight into what GPT-4 considers "important" — content words that carry semantic weight — and explains why the learned compressor generalizes: it learns to prioritize the same word classes that GPT-4 prioritizes, which are universally information-bearing across domains.

### Critical Assessment

#### Claim 1: LLMLingua-2 significantly outperforms task-agnostic baselines (Selective-Context, LLMLingua) while being faster.

**What the experiments demonstrate:** The claim is strongly supported for long-context understanding tasks (LongBench, ZeroSCROLLS, MeetingBank QA) at moderate compression ratios (2×–5×). Table 2 shows LLMLingua-2 achieving 39.1 vs. 34.6 (LLMLingua) and 24.8 (Selective-Context) on LongBench under 2,000-token constraint. Table 5 confirms the latency advantage: 0.4–0.5 seconds compression overhead vs. 1.5–2.9 seconds for LLMLingua and 15.5–15.9 seconds for Selective-Context.

**Where the claim weakens:** On reasoning tasks (GSM8K, BBH), the performance gap between LLMLingua-2 and LLMLingua essentially vanishes (Table 3: 79.08% vs. 79.08% on GSM8K 1-shot; 70.02% vs. 70.11% on BBH 1-shot). The paper does not explicitly discuss this narrowing, but it implies that the learned compression advantage is domain-dependent — large on meeting transcripts and long-form document tasks, small on structured reasoning demonstrations. A reader might reasonably ask whether the learned approach is worth the additional complexity (training pipeline, dataset construction) for tasks where the simpler entropy heuristic performs equivalently. The latency advantage remains across all tasks, but the performance advantage is not uniform.

**What is not tested:** The comparison is against two specific entropy-based baselines, both using LLaMA-2-7B. The paper does not test whether a **larger entropy estimator** (e.g., LLaMA-2-13B or Mixtral) would close the performance gap on long-context tasks. If the entropy heuristic's weakness stems partly from the small estimator size (7B) rather than the entropy metric itself, the learned approach's advantage might be overstated. Similarly, the paper does not test whether a **bidirectional entropy estimator** (e.g., masked language model scoring rather than causal LM scoring) would partially address the unidirectional context limitation without requiring supervised training.

#### Claim 2: The compressor generalizes across domains (trained on MeetingBank, tested on diverse benchmarks).

**What the experiments demonstrate:** This claim is well-supported by the breadth of out-of-domain evaluation. The compressor, trained exclusively on meeting transcripts, performs effectively on long-document QA (LongBench), math reasoning (GSM8K), logical reasoning (BBH), Chinese text (LongBench-Zh), and retrieval-augmented QA (NaturalQuestions). The Chinese generalization (Table 10: 38.1 vs. 28.6 for LLMLingua) is particularly convincing because it crosses both domain and language boundaries simultaneously. The qualitative examples in Figures 11 and 12 show that LLMLingua-2 produces coherent compressed prompts on BBH and GSM8K despite being trained only on meeting data, while LLMLingua produces garbled output.

**Genuine weaknesses:** The paper's claim of generalization rests on out-of-domain test performance, but it does not analyze **what specifically** the model learned that enables this transfer. The POS analysis (Figure 16) shows GPT-4 preferentially preserves nouns, adjectives, and numerals — but this is a property of the teacher's decisions, not necessarily evidence that the student learned a domain-invariant compression principle. A simpler hypothesis is that the student learned to mimic GPT-4's POS-based filtering, and this filtering strategy happens to work across domains because content words are universally important. The paper does not test whether a simple POS-based baseline (e.g., preserve all nouns, verbs, adjectives, numerals; discard everything else) would achieve comparable out-of-domain performance. If such a trivial baseline performed well, the learned model's "generalization" would be less impressive.

**Missing experiment:** The paper does not evaluate on **truly out-of-distribution text types** such as highly technical scientific articles, legal contracts, or creative writing. Meeting transcripts, math problems, and reasoning tasks all share relatively straightforward informational prose. Testing on poetry, dialogue with heavy implicature, or domain-specific jargon would more rigorously test the claim that the compressor has learned universal redundancy patterns rather than patterns common to the specific genres evaluated.

#### Claim 3: The compressor generalizes across target LLMs (GPT-3.5-Turbo to Mistral-7B).

**What the experiments demonstrate:** Table 4 provides convincing evidence: LLMLingua-2-compressed prompts outperform the original prompt with Mistral-7B (MeetingBank QA: 76.22% vs. 66.95%), and outperform entropy-based baselines. Table 13 confirms this on a subset within Mistral-7B's training context length.

**Caveats:** Only two target LLMs are tested — both instruction-tuned models in a similar capability class. The paper does not test on (1) much larger models (e.g., GPT-4, Claude 3.5), (2) much smaller models (e.g., LLaMA-2-7B), or (3) base models without instruction tuning. It is possible that instruction-tuned models share similar "preferences" for prompt structure that the compressor learned to satisfy, and that base models or models from different training paradigms would respond differently to the same compressed prompts. The Mistral-7B result that compression **improves** over the original prompt raises an interesting question: is the compressor learning what information is universally important, or is it learning to format prompts in a way that instruction-tuned models find easier to process? These are different claims, and the current experiments cannot distinguish them.

#### Claim 4: The data distillation procedure produces high-quality training data that enables learning effective compression.

**What the experiments demonstrate:** The ablation in Table 7 shows that the designed instruction + chunk-wise compression produces substantially lower variation rate and higher downstream QA F1 than alternative instructions. The comparison in Table 9 shows that the trained compressor outperforms GPT-4 itself on the same task. These results support the claim that the distillation pipeline works.

**What is missing:** The paper does not report **inter-annotator agreement** or any human evaluation of the GPT-4 compressed texts. The quality control metrics (VR, AG) are automatic and measure instruction compliance (did GPT-4 introduce new words? did the annotation algorithm work?) — they do not measure whether GPT-4's compression decisions are **actually good** at preserving information needed for downstream tasks. It is possible that GPT-4 consistently makes reasonable-looking but subtly wrong compression decisions (e.g., preserving the topic of a passage but dropping a critical qualifier), and the student model learns to reproduce these systematic errors. The strong downstream performance argues against this being a major problem, but the paper provides no direct evidence that the training labels are "correct" in a human-judged sense.

Additionally, the quality control filtering uses fixed thresholds (top 5% VR, top 10% AG) without ablation on these thresholds. Would stricter filtering (top 1% VR) improve or degrade performance? Would no filtering at all substantially hurt? The paper provides no sensitivity analysis for these design choices.

#### Claim 5: Bidirectional context and learned compression objective lead to better token-level decisions than unidirectional entropy.

**What the experiments demonstrate:** The overall performance improvements (Tables 1–4) are consistent with this claim, but the paper provides **no direct ablation isolating the effect of bidirectional vs. unidirectional context**. The comparison is always between the full LLMLingua-2 system (bidirectional encoder + learned objective + smaller model) and LLMLingua (unidirectional + entropy + larger model). These systems differ in three ways simultaneously, making it impossible to attribute the performance gain to any single factor. 

A clean ablation would replace the causal LM in LLMLingua with a bidirectional masked LM (e.g., BERT) computing a bidirectional entropy-like score, keeping the entropy heuristic but adding bidirectional context. If this partial fix closed most of the gap, the learned objective would be less important than claimed. Conversely, training a causal LM (e.g., LLaMA-2-7B fine-tuned as a token classifier) on the same distillation data would isolate the effect of bidirectional context while keeping the learned objective. Neither ablation is reported.

**What the qualitative evidence shows:** Figures 11 and 12 provide suggestive evidence that LLMLingua-2 makes qualitatively better compression decisions than LLMLingua — the compressed outputs are more coherent, contain fewer broken words, and better preserve the reasoning structure. However, qualitative examples are cherry-picked and do not substitute for controlled ablation.

#### Claim 6: LLMLingua-2 is 3×–6× faster than existing prompt compression methods.

**What the experiments demonstrate:** Table 5 directly measures this on a V100-32G GPU, and the claim is numerically accurate: LLMLingua-2 compression latency is 0.4–0.5 seconds vs. 1.5–2.9 for LLMLingua and 15.5–15.9 for Selective-Context. The end-to-end speedup (1.6×–2.9×) is also measured. Appendix I confirms lower GPU memory usage (2.1GB vs. 16.6–26.5GB).

**Subtleties:** The latency comparison is somewhat unfair to the baselines because they use a 7B-parameter model while LLMLingua-2 uses a 355M-parameter model. Part of the speed advantage is architectural (encoder vs. decoder), but part is simply model size. The paper does not test whether a smaller causal LM (e.g., LLaMA-2-1B or a distilled variant) would narrow the latency gap for entropy-based methods. The claim "3×–6× faster" should be understood as "3×–6× faster than the specific implementations of Selective-Context and LLMLingua as evaluated," which use LLaMA-2-7B. A practitioner willing to use a smaller entropy estimator might achieve different tradeoffs.

The end-to-end speedup numbers (1.6×–2.9×) are measured on MeetingBank with GPT-3.5-Turbo. The speedup depends on the ratio of compression time to LLM inference time — for very fast LLMs (local models on powerful hardware) or very short prompts, the compression overhead may become a larger fraction of total latency. The paper does not provide end-to-end measurements with local LLMs or across a range of prompt lengths and LLM inference speeds, limiting the generalizability of the speedup claims.

#### Overarching assessment

The paper's experimental evidence is strongest for its **practical claim**: LLMLingua-2 is a faster, more memory-efficient, and generally more accurate task-agnostic compressor than existing entropy-based methods when evaluated on the specific benchmarks and compression ratios tested. The breadth of evaluation (five benchmarks, two target LLMs, multiple compression ratios, Chinese cross-lingual test) is commendable and exceeds what is typical for prompt compression papers.

The evidence is weaker for the paper's **explanatory claims** about *why* LLMLingua-2 works better. The contributions are framed as addressing two specific challenges (misaligned entropy metric, unidirectional context), but the experiments do not cleanly isolate these factors. The performance gains could equally be attributed to (1) using a bidirectional architecture, (2) learning from supervised examples rather than using an unsupervised heuristic, (3) using a smaller model that is less prone to certain failure modes, or (4) some interaction of all three. The paper's narrative attributes the gains to (1) and (2), but the experimental design does not rule out alternative explanations.

The most notable missing experiments are: (1) a bidirectional entropy baseline (masked LM scoring), (2) a causal LM fine-tuned as a token classifier on the same distillation data (isolating architecture from objective), (3) a simple POS-based or rule-based compression baseline (testing whether learned compression beats simple linguistic heuristics), and (4) evaluation on more diverse text genres (poetry, legal, scientific) to test the true limits of domain generalization. These omissions are significant for a paper whose contributions are framed around the superiority of learned bidirectional compression over unsupervised unidirectional compression, but they do not undermine the paper's practical value as a demonstration that data distillation + token classification produces an effective, deployable compressor.

## 6. Limitations and Trade-offs

### Limitation 1: Training Data Comes from a Single Domain (Meeting Transcripts)

**The assumption or constraint.** The entire data distillation pipeline — GPT-4 compression examples, automatic annotation, and compressor training — uses **only the MeetingBank dataset**, which consists of city council meeting transcripts. The paper explicitly acknowledges this scope limitation in Section 6 (Limitations):

> "Our text compression dataset was constructed using only training examples from MeetingBank, a dataset of summarization over meeting transcripts. This raises concerns about the generalization ability of our compressor."

While the paper argues that out-of-domain evaluation addresses these concerns, the training domain is nevertheless narrow: procedural spoken language with characteristic disfluencies ("um," "uh," false starts, repetitions), a specific vocabulary (municipal governance, ordinances, budgets), and predictable discourse structure (agenda items, motions, public comments). The compressor is never trained on written prose, technical documentation, narrative text, dialogue from other domains, or any non-English text.

**The consequence.** A practitioner deploying LLMLingua-2 on text that differs substantially from meeting transcripts — dense legal contracts, scientific papers with specialized terminology and mathematical notation, creative writing with figurative language, informal social media text — is operating in an **unproven regime**. The paper's out-of-domain evaluation covers long-document QA (LongBench), math reasoning demonstrations (GSM8K), and logical reasoning tasks (BBH), but these are all relatively structured, information-dense text types. Meeting transcripts share with these domains a core property: they are **procedural or expository text where information is conveyed through straightforward declarative sentences**. It is unknown how the compressor would handle texts where meaning depends on non-literal language (sarcasm, metaphor, implicature), where information density is extremely high (mathematical proofs, patent claims), or where the distinction between "redundant" and "essential" is inherently ambiguous (literary prose, poetry).

Additionally, despite the paper's positive cross-lingual results on Chinese LongBench (Table 10), the compressor was trained on **English-only data**. The Chinese generalization relies entirely on the multilingual pretraining of XLM-RoBERTa-large — the compression-specific training signal (GPT-4's English meeting compression decisions) provides no cross-lingual supervision. For low-resource languages not well-represented in XLM-RoBERTa's pretraining data, compression quality may degrade substantially.

**What evidence exists in the paper.** The out-of-domain results (Tables 2, 3, 4, 10) provide evidence that the compressor transfers to several distinct domains and one additional language. Table 6 shows that expanding the training data with 50,000 TriviaQA-wiki examples (LLMLingua-2‡) yields only a 0.4-point improvement on LongBench (39.5 vs. 39.1 average) and no improvement on ZeroSCROLLS (33.4 vs. 33.4). The paper interprets this as evidence that "redundancy pattern might be similar" across domains, suggesting diminishing returns to domain diversification.

However, this evidence cuts both ways: the fact that adding 50,000 diverse examples barely moves the needle could indicate that the compressor has **already saturated whatever compression patterns are learnable from the MeetingBank data**, and that further improvement requires fundamentally different training signals (e.g., task-conditioned compression, human-annotated importance labels) rather than more data. Alternatively, it could indicate that TriviaQA-wiki is too similar to MeetingBank in its redundancy structure to provide complementary training signal — both are factual QA-adjacent text. The paper provides no analysis of what the expanded-data model does differently.

**Mitigation status.** The paper partially addresses this through extensive out-of-domain evaluation (four benchmarks + Chinese + two target LLMs) and through the data-expansion experiment (Table 6). However, these evaluations cover a limited range of text types — all are relatively formal, information-dense, and procedurally structured. The paper does not evaluate on genuinely dissimilar genres (social media, creative writing, technical documentation, legal text). The authors acknowledge this implicitly in Section 6: "We leave this for future work." No concrete mitigation strategy (e.g., domain-adaptive fine-tuning, multi-domain training, confidence estimation for out-of-domain inputs) is proposed or evaluated.

### Limitation 2: The Compressor Depends on GPT-4 as a Teacher — With No Validation of the Teacher's Compression Quality

**The assumption or constraint.** The entire supervised learning pipeline depends on **GPT-4's compression decisions serving as a gold standard** for what constitutes good prompt compression. The five-condition instruction (Figure 2) constrains GPT-4 to produce extractive output, but it does not guarantee that GPT-4's decisions about *which specific words to remove* are optimal — or even good — for downstream LLM performance. The paper provides no human evaluation of GPT-4's compression quality. The two quality control metrics (Variation Rate and Alignment Gap, Section 3.3) measure **instruction compliance** (did GPT-4 introduce new words? was the annotation algorithm successful?) rather than **compression quality** (does the compressed text retain the information needed for downstream tasks?).

**The consequence.** The student model (LLMLingua-2) learns to imitate whatever systematic biases or blind spots GPT-4 exhibits during compression. If GPT-4 consistently over-preserves certain word classes (e.g., named entities) and under-preserves others (e.g., negations, modals, quantifiers that dramatically change meaning), the student will reproduce those errors. The paper's positive downstream results argue against catastrophic failure from such biases, but subtler systematic errors could persist undetected. For example:

- GPT-4 might preferentially preserve **content words** (nouns, verbs, adjectives) at the expense of **function words** that carry critical logical relationships (negations like "not," modals like "must" vs. "may," quantifiers like "all" vs. "some"). Figure 16's POS analysis confirms that GPT-4 preferentially preserves nouns, adjectives, and numerals while discarding determiners and prepositions. If this preference is too aggressive, the compressed text could invert the meaning of a passage by dropping a negation ("the patient did **not** respond to treatment" → "the patient did respond to treatment").
- GPT-4's compression decisions on meeting transcripts may reflect **genre-specific redundancy judgments** that do not transfer. A filled pause ("um") in a meeting transcript is genuinely redundant; a hedging expression ("potentially," "may suggest") in a medical report may be essential for accurate interpretation. GPT-4 was not instructed to distinguish these cases, and the student has no mechanism to learn the distinction if it is not present in the training data.
- **Conservatism bias**: GPT-4 may err on the side of preserving more words than necessary (since the instruction penalizes information loss but not verbosity), producing training labels that are biased toward preservation. A student model learning from such labels may be insufficiently aggressive, preserving words that could safely be removed. The paper reports that LLMLingua-2's compression ratios in evaluation (2×–5×) are sometimes less aggressive than the baselines' at equivalent settings (Table 1: LLMLingua-2 achieves 3.1× compression with 970 tokens vs. LLMLingua's 2.5× with 1,176 tokens — note the contradiction: LLMLingua-2 achieves higher compression ratio *and* better performance, so this specific concern may not apply, but the broader point about teacher bias stands).

**What evidence exists in the paper.** Table 9 (Appendix O) provides the only direct comparison: LLMLingua-2 achieves 86.92% QA EM on MeetingBank with 970 tokens (3.1× compression), outperforming GPT-4's own compressed prompts (84.86% with 1,221 tokens, 2.5× compression). The student outperforms the teacher on this metric. The paper attributes this to "LLMLingua-2's ability to learn compression knowledge from the entire dataset [which] helps mitigate the influence of noise and information loss present in each GPT-4 compressed example."

This result is suggestive but incomplete. It shows that the student is not merely memorizing GPT-4's decisions — it is learning something more general from the aggregate pattern across examples. However, it does not validate that GPT-4's decisions are *correct* in any absolute sense. Both teacher and student could share a systematic blind spot (e.g., both drop negations at similar rates) that the QA benchmark does not probe because the questions happen not to depend on the dropped information. The MeetingBank QA pairs were generated by GPT-4 itself (Appendix F), creating a potential circularity: GPT-4 generates questions it believes are answerable from the text, then compresses the text in a way that preserves the information needed for those questions. A human-authored QA dataset might reveal different compression failures.

**Mitigation status.** There is **no human evaluation of GPT-4's compression quality** anywhere in the paper. The quality control metrics (VR, AG) operate entirely automatically and measure compliance with the extractive constraint, not downstream information preservation. The paper does not report inter-annotator agreement between GPT-4 and human compressors, does not conduct a human study asking raters to judge whether GPT-4-compressed texts retain essential information, and does not analyze specific cases where GPT-4's compression decisions are provably wrong (e.g., dropping a negation that changes the truth value of a statement). The strong downstream task performance provides indirect validation — if GPT-4 systematically dropped essential information, the compressor trained on its outputs would perform poorly on QA tasks — but does not quantify the residual error rate or characterize its failure modes.

### Limitation 3: Compression Quality Degrades as Ratio Increases, and the Paper Does Not Characterize the Failure Regime

**The assumption or constraint.** All prompt compression methods face an inherent tradeoff: more aggressive compression saves more inference cost but risks losing essential information. The paper evaluates LLMLingua-2 primarily at compression ratios of 2×–5× (Tables 1–4) and briefly at higher ratios (Figure 15 shows performance declining from ~80% EM at 1× to ~55% at 10× on MeetingBank QA). The paper does not provide a systematic characterization of **when and how compression fails** — at what ratio does performance drop below an acceptable threshold? What types of information are lost first? Are there predictable failure modes that practitioners can anticipate?

**The consequence.** A practitioner deploying LLMLingua-2 in a production setting needs to choose a compression ratio. The paper demonstrates that 2×–5× is generally safe across the evaluated benchmarks, but (1) the acceptable ratio likely depends on the downstream task's tolerance for information loss, (2) the relationship between ratio and performance appears to vary by domain (Figure 15a shows a steeper decline for QA than summarization), and (3) there is no guidance for how to set the ratio for a new, unstudied domain. A practitioner who pushes compression to 10× or beyond — motivated by cost savings — has no way to predict whether their specific task will degrade gracefully (like MeetingBank summarization, which maintains ~40 Rouge1 at 10× in Figure 15b) or catastrophically (like MeetingBank QA, which drops to ~55% EM at 10× in Figure 15a).

Furthermore, the paper's headline numbers for LLMLingua-2's performance are measured at **fixed compression ratios that differ slightly from the baselines' actual achieved ratios**. In Table 1, LLMLingua-2 is reported at 3.1× compression (970 tokens retained) while LLMLingua is at 2.5× (1,176 tokens). LLMLingua-2 achieves both higher compression and higher accuracy — a strictly dominant result. But at higher ratios (Figure 15), the performance curves for different methods may cross. A practitioner wanting to compress at 8× cannot simply look up the 5× results and extrapolate — they need the full ratio-vs-performance tradeoff curve, which the paper provides only for a 100-sample subset of MeetingBank (Figure 15), not for the out-of-domain benchmarks where the learned compressor's advantage is most salient.

**What evidence exists in the paper.** Figure 15 (Appendix M) provides the most direct evidence, plotting QA EM and summarization Rouge1 against compression ratio (1×–10×) for LLMLingua-2, LLMLingua, and Selective-Context on a 100-sample MeetingBank subset. LLMLingua-2 degrades more gracefully than the baselines in both tasks: at 10× compression, its QA EM is ~55% (vs. ~20% for LLMLingua), and its summarization Rouge1 is ~40% (vs. ~32% for LLMLingua). However, this is a single small subset of the in-domain data — the shape of the degradation curve on out-of-domain benchmarks (LongBench, GSM8K, BBH) at ratios beyond 5× is unknown. The main out-of-domain tables (Tables 2, 3) report only two compression settings (~5× and ~3× for LongBench; ~5× and ~11–14× for GSM8K/BBH) rather than full ratio sweeps.

**Mitigation status.** The paper partially addresses this through the sample-wise dynamic compression ratio experiment (Table 12, Appendix L), which shows that allowing per-sample ratios within a corpus-level constraint improves performance. This provides some robustness to the ratio-choice problem: rather than forcing all samples to the same aggressive ratio, the dynamic strategy allows information-dense samples to be compressed less. However, the dynamic strategy still requires setting a corpus-level target ratio, and it does not eliminate the need to understand what ratio is safe for a given task. The paper does not provide a principled method for selecting the compression ratio a priori — no confidence score, no predicted task performance as a function of ratio, no "safe compression ratio" estimator.

### Limitation 4: The FLOPs and Latency Analysis Ignores the Cost of the Data Distillation Pipeline

**The assumption or constraint.** The paper's latency and efficiency claims (Table 5: 3×–6× faster compression, 1.6×–2.9× end-to-end speedup) measure **inference-time costs only** — the time to run the trained compressor on a new prompt and feed the compressed output to the target LLM. The paper does not account for the substantial upfront cost of constructing the training dataset and training the compressor model. While this is standard practice for papers introducing trained models, it matters here because the data distillation pipeline is **resource-intensive**:

- GPT-4-32k API calls to compress 5,169 MeetingBank chunks (Table 8), each up to 512 tokens input with output up to 4096 tokens, at GPT-4-32k pricing.
- The training of the compressor itself: ~23 hours on a GPU for XLM-RoBERTa-large (355M parameters), ~16 hours for mBERT (110M parameters), as reported in Appendix H.
- The quality control and annotation pipeline, including lemmatization and fuzzy matching across all examples.

**The consequence.** A practitioner cannot simply download LLMLingua-2 and use it for a new domain or language. If the pre-trained compressor (trained on MeetingBank) performs poorly on their text type — a scenario the paper does not rule out for genres far from meeting transcripts — they must **replicate the entire data distillation pipeline**: obtain a corpus of in-domain text, chunk it, call GPT-4 (or another strong LLM) to compress each chunk, run the annotation algorithm, filter with VR and AG, and train a new compressor. The cost of this pipeline may exceed the inference-time savings from compression for many use cases, especially low-volume applications.

Furthermore, the paper does not provide guidance on how much in-domain training data is required. The 5,169 MeetingBank examples were sufficient for strong out-of-domain generalization, but a practitioner working in a highly specialized domain (e.g., internal legal documents, proprietary technical specifications) has no way to estimate whether 500, 5,000, or 50,000 examples would be needed. Table 6 hints that adding 50,000 TriviaQA examples provides marginal benefit (0.4-point LongBench improvement), suggesting diminishing returns — but this is measured on general benchmarks, not on a specialized target domain where the MeetingBank-trained model might perform poorly and additional in-domain data might be essential rather than incremental.

**What evidence exists in the paper.** The paper provides no analysis of the cost of the data distillation pipeline. Appendix A reports the GPT-4-32k parameters used (temperature 0.3, top_p 1.0, max output 4096 tokens) but does not report the total API cost, number of API calls, or wall-clock time for distillation. Appendix H reports training times (23 hours for LLMLingua-2, 16 hours for LLMLingua-2-small) but does not report the hardware used beyond the inference-time V100-32G mentioned in Section 5 and Table 5. The training GPU, batch size implications for memory, and total FLOPs for training are unstated.

**Mitigation status.** Not at all. The paper does not frame the distillation cost as a limitation and does not suggest strategies for reducing it (e.g., using a cheaper teacher model, active learning to select which examples to distill, few-shot adaptation from the MeetingBank-trained compressor). The released model weights mitigate this for users whose text domain is similar to MeetingBank or the evaluated out-of-domain benchmarks, but any user outside that distribution faces the full distillation cost with no guidance on whether it will be worthwhile.

### Limitation 5: The Task-Agnostic Design Fundamentally Cannot Match Task-Aware Methods on Query-Dependent Tasks

**The assumption or constraint.** LLMLingua-2 is designed as a **task-agnostic** compressor: it compresses text without access to the downstream task, question, or query. This is the core differentiator from methods like LongLLMLingua (Jiang et al., 2023b), which condition compression on the query to preserve query-relevant information. The design choice trades performance on query-dependent tasks for generality and efficiency (compress once, reuse across queries).

**The consequence.** On tasks where the relevant information depends heavily on the specific question — particularly retrieval-augmented generation with multiple documents, where most documents are irrelevant to the current query — task-agnostic compression allocates its token budget **uniformly across all content**, spending tokens preserving information in irrelevant documents and starving relevant documents of needed detail.

The magnitude of this consequence is visible in Table 11 (Appendix K). On NaturalQuestions with 20 retrieved documents, pure LLMLingua-2 (task-agnostic) achieves **46.2%** on the reorder task (averaged across all document positions), while LongLLMLingua (task-aware) achieves **75.5%** — a 29.3-point gap. The integrated LLMLingua-2+ (which uses LongLLMLingua's query-conditioned coarse-grained budget allocation but LLMLingua-2's token classifier for fine-grained selection) achieves 71.9%, partially closing the gap but still 3.6 points below fully task-aware compression.

Similarly, on LongBench (Table 2), LongLLMLingua achieves 48.0 under the 2,000-token constraint vs. 39.1 for LLMLingua-2 — an 8.9-point gap. The gap is largest on FewShot tasks (70.6 vs. 66.4) and Synthetic tasks (53.0 vs. 21.3), where question-conditioned budget allocation can concentrate tokens on the most relevant demonstrations or passages.

This limitation is not a flaw in LLMLingua-2 per se — it is an inherent tradeoff of task-agnostic design. The paper is transparent about this gap (Section 5):

> "While our approach has shown promising results, it falls short when compared to other task-aware compression methods like LongLLMLingua on LongBench. We attribute this performance gap to the additional information that they leverage from the question."

However, a practitioner choosing a compression method must understand this tradeoff: LLMLingua-2 is preferable when (a) the same text will be queried multiple times with different questions (compress once, reuse), (b) the downstream task is unknown at compression time, or (c) compression latency and model size are primary constraints. LongLLMLingua (or LLMLingua-2+ with coarse-grained query conditioning) is preferable when (a) each compression is for a single known query, (b) the text contains multiple documents of varying relevance, and (c) accuracy on the specific query is paramount.

**What evidence exists in the paper.** Table 11 provides the most direct quantification of the gap on a multi-document retrieval task. The gap on LongBench (Table 2) is also informative, though less extreme because LongBench's tasks include some where the full context is broadly relevant (SingleDoc QA, Summarization) rather than a needle-in-haystack retrieval problem. The ablation LLMLingua-2+ in Table 11 demonstrates that the gap can be partially closed by adopting the query-conditioned budget allocation from LongLLMLingua while keeping LLMLingua-2's token classifier — a modular integration that the paper explicitly supports.

**Mitigation status.** Partially addressed. The paper acknowledges the performance gap and provides LLMLingua-2+ as a modular upgrade path for users who need query-conditioned compression. Appendix K describes the integration in detail: "We utilize LongLLMLingua's coarse-grained compression to assign varying compression ratios to different documents based on the question's perplexity conditioned on each document. Consequently, it allocates more token budgets to the documents which are more relevant to the question." This hybrid approach recovers most of the gap (71.9% vs. 75.5%) while preserving LLMLingua-2's faster and more accurate token-level decisions within each document.

However, the hybrid still requires running a question-conditioned perplexity estimator (LLaMA-2-7B in LongLLMLingua's original implementation) for budget allocation, sacrificing some of LLMLingua-2's latency and simplicity advantages. The paper does not explore whether a lightweight question-conditioned budget allocator (e.g., a small cross-encoder) could achieve similar budget allocation at lower cost, which would make the hybrid more consistent with LLMLingua-2's efficiency goals.

### Limitation 6: The Compressor May Not Preserve Information Critical for Tasks Requiring Exact Wording

**The assumption or constraint.** LLMLingua-2 formulates compression as binary token classification — each word is independently scored for preservation probability, and the top `$\tau N$` highest-scoring words are retained in their original order. The scoring is contextual (bidirectional encoder sees the full sequence), but the **decision is per-word**: the model does not explicitly consider the interaction between words or the effect of removing a word on the interpretability of surrounding words. The training labels (from GPT-4, via Algorithm 1) are also per-word — there is no explicit supervision for preserving multi-word expressions, syntactic dependencies, or discourse coherence.

**The consequence.** For most tasks, the per-word scoring with original-order retention produces coherent text (Figures 6, 11, 12), because the bidirectional context enables the model to learn that certain words are structurally necessary for surrounding content words to remain interpretable. However, tasks that require **exact verbatim preservation of specific phrases** may suffer:

- **Legal and contractual text**: Changing "the party shall not be liable" to "the party shall be liable" (dropping "not") inverts the meaning. A token classifier might assign low preservation probability to "not" if it appears in a predictable syntactic position, even though its presence vs. absence determines the truth value.
- **Mathematical and logical statements**: Dropping a quantifier ("for all x" vs. "there exists x") or a scope delimiter (parentheses) changes the formal meaning. GSM8K results (Table 3) show LLMLingua-2 maintaining full-shot accuracy at 5×–14× compression, suggesting mathematical reasoning demonstrations are compressed safely, but the paper does not analyze specific failure cases where a dropped token changed the answer.
- **Negation, modality, and hedging**: Words like "not," "never," "possibly," "allegedly," "might," and "unless" carry enormous semantic weight relative to their length and statistical predictability. A compressor trained on meeting transcripts — where such words are less prevalent than in, say, medical diagnoses or legal opinions — may not learn to protect them adequately.

The paper's extractive design (remove only, don't change words) guarantees that any preserved word is **verbatim correct** — there is no hallucination or paraphrasing. But the flip side of this guarantee is that **discarded words are gone forever**, and if a critical negation or quantifier is discarded, the compressed text becomes actively misleading rather than merely vague. A generative compression method might rephrase "the patient did not respond to treatment" as "the patient failed to respond to treatment" — preserving the negation through rephrasing. An extractive method that drops "not" produces "the patient did respond to treatment" — a statement with the opposite meaning.

**What evidence exists in the paper.** The paper provides no direct analysis of this failure mode. The strong QA performance on MeetingBank (86.92% EM at 3.1×, Table 1) and GSM8K (79.08% at 5×, Table 3) suggests that, on these benchmarks, critical tokens are being preserved. The qualitative examples in Figures 6, 11, and 12 do not highlight any cases where dropping a word changed meaning. The prompt reconstruction experiment (Figures 7 and 8, Appendix E) shows that GPT-4 can approximately reconstruct the original prompt from the compressed version, suggesting no catastrophic information loss — but approximate reconstruction is not the same as exact preservation of logical operators.

**Mitigation status.** Not addressed. The paper does not discuss the risk of meaning-inverting drops, does not analyze cases where dropping a function word changes the truth conditions of a statement, and does not propose mechanisms to protect against this (e.g., a blacklist of never-drop words, syntax-aware scoring that penalizes removal of negation or modality markers, or post-compression verification). The sample-wise dynamic compression ratio (Appendix L) may partially mitigate this — information-dense samples with many load-bearing function words would receive lower compression ratios — but only if the compressor's scores happen to be lower for those words, which the training data may not encourage. The paper's POS analysis (Figure 16) shows that GPT-4 preferentially drops determiners and prepositions — a pattern that would also drop negations and modals, which share the same POS categories. If the student model learns this preference, it may systematically under-preserve semantically critical closed-class words.
