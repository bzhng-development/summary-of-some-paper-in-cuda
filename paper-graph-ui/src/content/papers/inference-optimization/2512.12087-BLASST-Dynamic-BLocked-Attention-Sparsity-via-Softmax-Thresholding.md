# BLASST: Dynamic BLocked Attention Sparsity via Softmax Thresholding

**ArXiv:** [2512.12087](https://arxiv.org/abs/2512.12087)

## Pitch

BLASST tackles the quadratic bottleneck of LLM attention by introducing a training-free, drop-in sparse mechanism that reuses online softmax statistics to skip negligible computation blocks. The method delivers end-to-end inference acceleration—achieving 1.52× speedup for prefill and 1.48× for decode on modern GPUs—while maintaining accuracy, making it the first practical sparse attention solution that works across all phases without pre-computation overhead.

---

## 1. Executive Summary

This paper introduces **BLASST** (BLocked Attention Sparsity via Softmax Thresholding), a training-free, drop-in sparse attention method that dynamically prunes negligible attention blocks during both prefill and decode by reusing online softmax statistics — specifically, by comparing a block's local maximum attention score to the running maximum and skipping blocks whose contribution falls below a single scalar threshold (e.g., skipping softmax exponentiation, value block loads, and the attention-value matrix multiplication when a block's max is substantially smaller than the running max). Evaluated on Llama-3.1-8B and Qwen3-8B across RULER, LongBench, MATH500, AIME 2024, and GPQA, BLASST achieves 1.52× prefill speedup at 71.9% sparsity and 1.48× decode speedup at 73.2% sparsity on Blackwell GPUs while preserving benchmark accuracy, with an automated calibration procedure revealing a robust inverse relationship λ = a/L between optimal threshold and context length — establishing that precise, hardware-optimized attention sparsity can be recovered from already-computed softmax statistics without training or pre-computation, and that the resulting speedups scale predictably with sparsity level only when the threshold is adapted to sequence length rather than held fixed.

## 2. Context and Motivation

### The Core Problem: Quadratic Complexity Is the Bottleneck, and Nobody Has Solved It for Real

The fundamental problem BLASST addresses is deceptively simple: **the self-attention mechanism in transformers scales quadratically with sequence length, and all existing solutions for reducing this cost come with deployment-breaking tradeoffs.** While the theoretical formulation of attention — softmax(QK^T / √d_k)V — has been known since Vaswani et al. (2017), the practical challenge of computing it for long sequences at inference time remains acute and growing worse as context windows balloon.

The paper opens by anchoring this concern in concrete numbers. Models like Deepseek-R1 (Guo et al., 2025) and Qwen3 (Yang et al., 2025) now support context lengths up to 128K tokens, with some systems pushing to 1M tokens (Comanici et al., 2025). But supporting a context length in principle — i.e., the model architecture can technically process it — is not the same as being able to deploy it in production. For a sequence of length n, attention requires O(n²) operations and memory accesses. At 128K tokens, a single attention matrix contains over 16 billion entries. At 1M tokens, that's 1 trillion. The quadratic growth outpaces hardware improvements: even with state-of-the-art GPUs, processing such sequences becomes "computationally prohibitive" with "attention computation dominating both latency and memory consumption" (Section 1).

The problem isn't just academic. The paper cites concrete application domains where long-context inference is critical: processing entire codebases (Roziere et al., 2023), analyzing lengthy documents (Zeng et al., 2025), and maintaining extended conversations (Achiam et al., 2023). In each case, the quality of the model's output depends on its ability to attend across the full context, but the computational cost of doing so makes these applications impractical at scale.

### FlashAttention Fixed the Memory Bottleneck, Not the Complexity

A critical nuance the paper establishes early is that **FlashAttention and its successors — while transformative — address memory bandwidth utilization, not fundamental computational complexity.** FlashAttention (Dao et al., 2022) introduced tiling and kernel fusion that dramatically reduced HBM reads and writes by computing attention in blocks within SRAM, effectively making attention I/O-aware rather than I/O-bound. FlashAttention-3 (Shah et al., 2024) and FlashAttention-4 (Zadouri et al., 2026) further improved this through asynchrony, low-precision computation, and better pipeline scheduling. These innovations made it possible to actually *run* long-context attention on existing hardware by removing the memory bottleneck.

However — and this is the distinction BLASST builds on — "they still compute the full attention matrix, leaving the fundamental quadratic complexity unaddressed" (Section 1). FlashAttention computes every single dot product between every query and every key. It may do so more efficiently, but it still does O(n²) operations. As context lengths push into the hundreds of thousands, even the perfectly optimized dense computation becomes too expensive. The paper's implicit argument is that **FlashAttention won the battle against the memory wall, but the war against quadratic compute is still ongoing** — and requires a fundamentally different approach: sparsity.

### The Sparse Attention Landscape: Solutions Exist, but Nobody Can Actually Deploy Them

The paper's most important contextual contribution is its systematic diagnosis of *why* sparse attention methods — despite a rich literature — have failed to achieve widespread adoption. The authors identify **five specific barriers** that existing methods impose on practitioners (Section 1, elaborated in the feature comparison of Table 1):

**1. Expensive pre-computation negates theoretical speedups.** Several recent methods require a preliminary pass over the input to determine what to compute. MInference (Jiang et al., 2024) builds proxy importance scores by analyzing attention patterns offline or via a lightweight pre-pass. XAttention (Xu et al., 2025) ranks blocks based on anti-diagonal scoring patterns that must first be computed. FlexPrefill (Lai et al., 2025) introduces compiler-supported scheduling for flexible block patterns, but this scheduling itself has overhead. The key insight from the BLASST authors is that **if the pre-computation costs as much as the dense computation you're trying to avoid, the net speedup vanishes.** A method that achieves 2× theoretical speedup but requires a 1× pre-computation pass yields only a 1× net improvement — not nothing, but far from transformative.

**2. Training or fine-tuning requirements break compatibility.** Some of the most effective sparse attention approaches require modifying the model itself. DuoAttention (Xiao et al., 2025) introduces new layers that distinguish between retrieval and streaming heads — requiring fine-tuning to teach the model this distinction. DeepSeek Sparse Attention (DSA; DeepSeek-AI, 2025) and Native Sparse Attention (NSA; Yuan et al., 2025) build sparsity into the architecture from the ground up, requiring training from scratch or substantial retraining. SeerAttention (Gao et al., 2025b) uses learned gates that are trained into the model. The practical problem is clear: a production team with a pretrained model (say, Llama-3.1-70B) cannot adopt any of these approaches without retraining, which may be computationally prohibitive, unavailable (if training data isn't accessible), or invalidate safety evaluations performed on the original weights.

**3. The prefill-decode asymmetry is almost never addressed.** The paper makes a critical distinction that many prior works gloss over: **prefill and decode have fundamentally different computational profiles.** During prefill, the model processes the entire input sequence at once — this is compute-bound, bottlenecked by the throughput of tensor cores (for the attention-value multiplication) and CUDA cores (for softmax exponentiation). During decode, the model generates one token at a time, attending over the growing KV cache — this is **memory-bound**, bottlenecked by the HBM bandwidth required to fetch the stored keys and values. An optimization that helps prefill (like skipping softmax computation) may do nothing for decode if the bottleneck is memory rather than compute. Conversely, an optimization that reduces KV cache size (like token eviction) helps decode but doesn't reduce prefill work since prefill computes attention over the full input regardless.

Table 1 in the paper makes this asymmetry starkly visible. Methods like H2O (Zhang et al., 2023), SnapKV, RocketKV (Behnam et al., 2025), and Quest (Tang et al., 2024) target decode only — they reduce KV cache memory, which accelerates the memory-bound decode phase but leaves prefill untouched. MInference, SpargeAttention (Zhang et al., 2025), and XAttention target prefill only — they reduce the computation of attention scores but don't address the KV cache bottleneck in decode. The paper claims that BLASST is unique in accelerating *both* phases, and Table 1 supports this position: it is the only method with checkmarks in all four columns (Accelerates Prefill ✓, Accelerates Decode ✓, No Training ✓, No Pre-Computation ✓).

**4. Lack of kernel support for modern hardware makes speedups hypothetical.** The paper identifies a gap between algorithmic novelty and engineering reality: many sparse attention papers report theoretical FLOP reductions or speedups measured in idealized settings, but fail to deliver optimized CUDA kernels that actually run faster on contemporary GPUs like NVIDIA's Hopper (H200) and Blackwell (B200) architectures. Modern GPUs have specific characteristics — tensor cores, asynchronous copy engines (TMA), warp-group-level scheduling, specialized instructions like MUFU.EX2 for exponential — that require careful kernel design to exploit. A method that looks good on paper but can't be efficiently implemented for Blackwell remains a research artifact, not a deployment solution.

**5. Framework integration friction prevents adoption.** Sparse attention implementations often require intrusive modifications to model code. They may replace the standard attention interface with custom APIs, require special tensor formats for sparsity patterns, or depend on complex runtime systems for scheduling. The paper positions BLASST as requiring "only a single scalar threshold input" to the existing attention function call — a change so minimal that it can be integrated into frameworks like TensorRT-LLM and FlashInfer without disrupting existing model definitions.

### The Calibration Gap: Nobody Knew How to Pick the Threshold

Beyond the deployment barriers, the paper identifies a subtler but equally important gap: **even if you have a threshold-based sparsity method, how do you choose the threshold?** This is a calibration problem that prior work largely ignored or addressed with manual per-task tuning. But the paper demonstrates (Figure 2, right) that fixed thresholds produce wildly inconsistent sparsity levels across different sequence lengths: the same λ that gives 75% sparsity at 8K context might produce only 23% sparsity at 4K and near-100% sparsity (effectively no attention computed) at 64K. This makes fixed-threshold deployment unreliable — accuracy degrades unpredictably as context length varies.

The paper's empirical finding that this relationship follows a simple inverse proportion (λ = a/L, where L is context length) is not just a calibration convenience but a revelation about the underlying mathematics: because softmax normalizes attention scores to sum to 1, longer sequences necessarily have lower average per-token attention scores. A threshold that captures a fixed fraction of attention mass must therefore scale inversely with length. This relationship had not been characterized in prior work, meaning that existing threshold-based methods (including the closely related SpargeAttention) lacked a principled way to maintain consistent sparsity across variable-length inputs.

### How BLASST Positions Itself: Simplicity as the Differentiator

The paper's framing is notable for what it does *not* claim. BLASST doesn't promise the highest possible sparsity ratio. It doesn't propose a fundamentally new way of modeling attention. It doesn't require retraining or architectural changes. Instead, its thesis is: **by making the simplest possible modification to the FlashAttention algorithm — reusing a statistic that is already computed (the running maximum) to make a single comparison (block max minus running max < ln(λ)) — we can achieve deployment-ready speedups that no existing method can match in practice.**

The closest prior work is SpargeAttention (Zhang et al., 2025), and the paper explicitly differentiates along three axes: SpargeAttention targets prefill only (BLASST handles both phases), uses a separate prediction step rather than reused statistics (adding overhead), and doesn't skip Value loading from HBM in decode (missing the memory-bandwidth optimization). The comparison is instructive: two methods can share a similar high-level concept (skip computation for low-attention blocks) while differing fundamentally in their deployment practicality.

The paper also positions itself within a broader historical context. Static pattern methods (Sparse Transformer, LongFormer, BigBird) reduced complexity by enforcing fixed sparsity patterns — local windows, global tokens, block-sparse structures — but these patterns are architecture-level choices that constrain the model's attention flexibility. Retrieval-head methods (Wu et al., 2025; Xiao et al., 2025) exploit the observation that only certain attention heads are critical for long-range retrieval, but require identifying these heads per model. Linear and gated attention variants (Qiu et al., 2025) and state-space models (Gu & Dao, 2024) replace the quadratic attention mechanism entirely, achieving linear scaling but at the cost of architectural compatibility — they cannot be dropped into an existing transformer without retraining. BLASST's claim is that **for the overwhelming majority of deployed transformer models today, none of these approaches are usable without prohibitive investment**, and that a simple, training-free, dual-phase method fills a genuine gap in the deployment ecosystem.

## 3. Technical Approach

### 3.1 Reader Orientation

BLASST is a **modified FlashAttention kernel** that dynamically skips the computation of entire blocks of the attention matrix during inference, using only a single scalar threshold and statistics that FlashAttention already computes. It solves the problem that standard attention must compute every query-key dot product even though many of them contribute negligible amounts to the final output after softmax normalization — and it does so in a way that requires **no training, no pre-computation pass, and no architectural changes**, making it immediately deployable on existing pretrained models for both the prefill and decode phases.

### 3.2 Big-Picture Architecture (Diagram in Words)

The BLASST system has four major components that interact during a forward pass:

1. **The Standard FlashAttention Tiling Engine** — the existing mechanism that divides the sequence into query blocks and KV blocks, computes attention scores block-by-block in SRAM, and maintains online softmax statistics (running maximum, running denominator, running accumulator). This is not modified structurally; BLASST adds logic inside it.

2. **The Running Maximum Tracker** — a scalar value `$m_i^{(j)}$` maintained per query block `i` that tracks the largest attention score seen so far across all KV blocks processed up to block `j`. This is already computed by standard FlashAttention for numerical stability during online softmax; BLASST reuses it without additional cost.

3. **The Block Skip Decision Logic** — a predicate evaluated once per KV block after computing its attention scores (the `Q_i K_j^T` matrix) but before performing softmax exponentiation, Value loading, or the attention-value multiplication. The predicate compares the block's local maximum `$\tilde{m}_i^{(j)}$` against the running maximum `$m_i^{(j)}$` using a user-supplied threshold `$\lambda$`. If the local maximum is too small relative to the running maximum, the block is skipped entirely.

4. **The Calibrated Threshold Provider** — an offline procedure that determines the scalar `$\lambda$` to use at inference time, based on a target sparsity level and the current sequence length `$L$`. The relationship follows `$\lambda = a/L$`, where `$a$` is a model-specific parameter fitted once per target sparsity using a calibration dataset. This component is not part of the kernel itself but determines its configuration.

Information flows as follows during inference: a sequence enters the model → the calibrated threshold is looked up based on sequence length → FlashAttention's tiled loop begins processing KV blocks sequentially → for each KV block, the QK product gives raw attention scores → the block's row-wise maximum is extracted → the skip predicate is evaluated by comparing to the running maximum → if the block is kept, softmax exponentials are computed, the Value block is loaded from HBM (in decode), and the attention-value product is accumulated; if the block is skipped, none of these operations are performed → after all KV blocks, the accumulated output is normalized by the softmax denominator to produce the final attention output for that query block.

### 3.3 Roadmap for the Deep Dive

- **First**, the mathematical foundation of the skip criterion — why comparing block maxima to the running maximum correctly identifies negligible blocks, what `$\lambda$` physically represents, and how the online softmax machinery makes this possible without global information. This is the core algorithmic insight that makes everything else work.

- **Second**, the formal algorithm specification (Algorithm 1) — a line-by-line explanation of how the modified FlashAttention loop incorporates the skip decision, what operations are saved in each of the three categories (softmax compute, Value loading, attention-value multiplication), and the numerical correctness guarantees.

- **Third**, the calibration procedure (Algorithm 2) — how the threshold `$\lambda$` is fitted to produce consistent sparsity across variable-length sequences, why fixed thresholds fail, the empirical discovery of the inverse-length relationship `$\lambda = a/L$`, and the exponential model that maps target sparsity to threshold.

- **Fourth**, the prefill kernel design — the warp-group specialization, the pipeline schedule modifications that elide softmax exponentiation and tensor core matrix multiplies for skipped blocks, how the scheduling is restructured to compress the overall timeline, and why Value loading is deliberately *not* skipped in prefill even though it could be.

- **Fifth**, the decode kernel design — the fundamentally different bottleneck (memory bandwidth, not compute), the batched load scheduling that prevents pipeline bubbles when conditionally skipping Value loads, the trade-off of maintaining multiple shared memory buffers for query-key products, and how this design extends to compute-bound decode variants like Multi-Head Latent Attention (MLA).

- **Sixth**, the sparsity-aware training extension — how applying BLASST during the forward pass of fine-tuning (but not backpropagating through skipped blocks) encourages the model to concentrate important information in blocks that will survive pruning, and the curriculum training approach adopted from ProLong.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems and kernels paper** whose core idea is that a single comparison between a block's local maximum attention score and the online running maximum — both computed anyway during FlashAttention's numerically stable softmax — suffices to identify blocks whose post-softmax contribution is negligible, and that skipping these blocks saves both compute and memory bandwidth with minimal accuracy degradation, provided the threshold used for the comparison is calibrated to scale inversely with sequence length.

#### The Skip Criterion: Why Block-Max vs. Running-Max Works

The foundational insight of BLASST is that FlashAttention's online softmax algorithm already computes exactly the information needed to identify negligible attention scores — no extra statistics, proxy models, or pre-computation passes are required. To understand why this works, we must first understand what happens to an attention score during softmax normalization.

Consider a single query token attending over all key tokens. For each key position `k`, the raw attention score is `$s_k = q \cdot k_k / \sqrt{d_k}$`. After softmax, the normalized attention weight assigned to key `k` is:

$$p_k = \frac{\exp(s_k - M)}{Z}$$

where `$M = \max_k s_k$` is the global maximum across all attention scores for this query, `$Z = \sum_k \exp(s_k - M)$` is the softmax normalization constant (the partition function), and `$p_k$` is the post-softmax probability assigned to key `k`.

**What this equation computes:** the exponentiated score `$\exp(s_k - M)$` measures how large the attention score is relative to the largest score. Subtracting `$M$` before exponentiating ensures numerical stability — without this subtraction, large scores would cause the exponential to overflow floating-point representations. The denominator `$Z$` ensures that all `$p_k$` sum to 1, forming a valid probability distribution. The output `$p_k$` represents the fraction of the query's total attention that is allocated to key `k`.

**Why this form matters for sparsity:** because `$M$` is the global maximum, the largest pre-softmax score becomes `$\exp(M - M) = \exp(0) = 1$` after the shift, and all other scores are smaller — some dramatically so. A score `$s_k$` that is `$\Delta$` units below the maximum becomes `$\exp(-\Delta)$` after exponentiation. For `$\Delta$` sufficiently large, `$\exp(-\Delta)$` is so small that the corresponding key contributes negligibly to the final attention output. The key question for sparsity is: **how do we determine whether a block contains any scores that matter, without computing the global maximum first (which would require examining all scores)?**

BLASST's answer uses a tractable proxy. Define:

- `$m_i^{(j-1)}$` — the **running maximum** after processing KV blocks 1 through `j-1` for query block `i`. This is the largest attention score seen so far, maintained as part of FlashAttention's online softmax machinery.

- `$\tilde{m}_i^{(j)}$` — the **block-local maximum** of the raw attention scores `$S_{ij} = Q_i K_j^T$` for the current KV block `j`. This is simply `$\text{rowmax}(S_{ij})$`, computed per row of the attention scores within the block.

The skip criterion is:

$$\tilde{m}_i^{(j)} - m_i^{(j-1)} < \ln(\lambda)$$

where `$\lambda \in (0, 1]$` is a user-specified threshold, typically small (e.g., `$10^{-4}$` to `$10^{-3}$`).

**What this inequality tests:** whether the largest attention score in the current block is smaller than the running maximum by more than `$\ln(\lambda)$`. If it is, then even the block's *best* score will contribute at most `$\lambda$` to the final output relative to the maximum score seen so far. Formally, if the condition holds, then:

- The running maximum is `$m_i^{(j-1)}$` and the block-local maximum is `$\tilde{m}_i^{(j)}$`.
- For any score `$s$` in this block, `$s \leq \tilde{m}_i^{(j)}$`.
- Therefore `$s - m_i^{(j-1)} \leq \tilde{m}_i^{(j)} - m_i^{(j-1)} < \ln(\lambda)$`.
- Exponentiating: `$\exp(s - m_i^{(j-1)}) < \lambda$`.
- Since `$m_i^{(j-1)} \leq M$` (the true global maximum can only be larger, never smaller, than the running maximum), the final post-softmax contribution is bounded by `$\lambda$`.

**Why this form matters — a three-step approximation that works in practice.** The ideal pruning criterion would compare each score to the true global maximum `$M$`, skipping scores where `$\exp(s - M) < \lambda$`. But computing `$M$` requires examining every score first, which defeats the purpose of skipping computation. The BLASST criterion makes three deliberate approximations:

1. **Replace the true global maximum `$M$` with the running maximum `$m_i^{(j-1)}$`.** This is conservative — the running maximum is always less than or equal to the true maximum, so the condition `$\exp(s - m_i^{(j-1)}) < \lambda$` is *stricter* than the ideal `$\exp(s - M) < \lambda$`. In other words, BLASST may keep some blocks that could have been skipped (because the running maximum hasn't yet seen the true maximum), but it will never skip a block that would have contributed more than `$\lambda$` had the true maximum been known.

2. **Replace token-level scores with the block-level maximum.** Comparing every single score to `$m_i^{(j-1)}$` would require `$O(B_c^2)$` comparisons per block and defeat the purpose of a fast decision. Using only the block's row-wise maximum `$\tilde{m}_i^{(j)}$` reduces the decision to a single comparison per block. This is again conservative — if the block maximum fails the test, all scores in the block fail it. A block might be kept because its maximum score passes the threshold even though most of its scores would individually have been skipped, but this false-positive case is harmless (it just means we compute a block we could have partially skipped).

3. **Make a binary block-level decision.** Either the entire block is kept (all softmax, Value load, and multiplication proceed) or the entire block is skipped. This is a granularity choice that matches the tiling structure of FlashAttention — blocks are already the unit of data movement between HBM and SRAM, so skipping at block granularity naturally elides the corresponding memory traffic.

The net effect is a criterion that is **conservative** (may keep more than strictly necessary), **efficient** (a single comparison per block using already-computed values), and **safe** (will never prune scores that would have contributed more than `$\lambda$` to the final output).

**What `$\lambda$` physically means.** The threshold `$\lambda$` controls the maximum post-softmax attention weight that a token in a skipped block could have contributed. If `$\lambda = 10^{-4}$`, then every token in every skipped block would have post-softmax probability at most `$10^{-4}$` — that is, at most 0.01% of the total attention mass per token. Since the softmax normalizes to sum to 1, the total mass discarded by skipping one block of `$B_c$` tokens is at most `$B_c \cdot \lambda$`. For typical block sizes `$B_c = 128$` and `$\lambda = 10^{-4}$`, this is at most `$128 \cdot 10^{-4} = 0.0128$` per skipped block — roughly 1.3% of the total attention mass. In practice, conservative choices of `$\lambda$` ensure that many blocks are skipped while the total discarded mass remains a small fraction of 1.

The threshold is expressed as `$\ln(\lambda)$` in the algorithm because the raw attention scores `$S_{ij}$` are in log-space (they are pre-exponential values). The comparison `$\tilde{m}_i^{(j)} - m_i^{(j-1)} < \ln(\lambda)$` is equivalent to `$\exp(\tilde{m}_i^{(j)} - m_i^{(j-1)}) < \lambda$` — it checks the same condition without requiring an exponential computation during the skip decision itself. This is a careful engineering choice: the exponential is expensive (MUFU.EX2 instruction on NVIDIA GPUs), so performing the comparison in log-space avoids adding any of the cost that the method is trying to eliminate.

#### Formal Algorithm Specification (Algorithm 1)

Algorithm 1 in the paper presents the BLASST-modified FlashAttention forward pass. The pseudocode operates on tiled query and KV sequences divided into `$T_r$` query blocks and `$T_c$` KV blocks, each of size `$B_c$`. We walk through the algorithm line by line, explaining what has changed from standard FlashAttention and what each modification saves.

**Line 1: Outer loop over query blocks.** `for i = 1 to T_r do`. This iterates over all query blocks in the sequence. Each query block is processed independently — attention for one query block does not depend on attention for other query blocks. This outer loop is identical to standard FlashAttention.

**Line 2: Initialize online softmax state.** For query block `i`, three accumulators are initialized before processing any KV blocks:
- `$m_i^{(0)} = -\infty$` — the running maximum, initially negative infinity so that the first block's maximum always exceeds it and is therefore always kept.
- `$O_i^{(0)} = 0$` — the running accumulator of the attention-weighted sum of values. This is a matrix of size query-block-rows × value-dimension. Initially zero.
- `$l_i^{(0)} = 0$` — the running softmax denominator (the sum of exponentiated scores after subtracting the running maximum). Initially zero.

These are standard FlashAttention state variables. The key observation is that `$m_i^{(0)}$` is already maintained — BLASST adds no new persistent state.

**Line 3: Inner loop over KV blocks.** `for j = 1 to T_c do`. This iterates over the KV blocks, processing them sequentially. This is the mainloop where BLASST's modifications take effect.

**Line 4: Compute attention scores.** `Compute S_{ij} = Q_i K_j^T`. This is the query-key product for the current query block against the current KV block, producing a matrix of raw attention scores of size (query-block-rows × `$B_c$`). This operation is performed by tensor cores (matrix multiply accumulate, or MMA). **BLASST always executes this line** — the QK product is needed to determine whether the block can be skipped. This is intentional: the skip decision requires the raw scores, so this computation cannot be avoided. However, the QK product is relatively cheap in both prefill (where it is pipelined with other operations) and decode (where `K_j^T Q_i` is a vector-matrix product with a single query token, so it requires only loading `K_j` from HBM with minimal compute).

**Line 5: Extract local maximum.** `$\tilde{m}_i^{(j)} = \text{rowmax}(S_{ij})$`. For each row of the attention score matrix (each query token in the block), compute the maximum score across all `$B_c$` key positions in this KV block. This is a reduction operation performed by CUDA cores. Standard FlashAttention also computes this — it is needed for the online softmax update — so BLASST adds zero extra cost here.

**Line 6: Update running maximum.** `$m_i^{(j)} = \max(m_i^{(j-1)}, \tilde{m}_i^{(j)})$`. The running maximum is updated to be the larger of the previous running maximum and the current block's local maximum. This is also standard FlashAttention — the running maximum is needed for the numerically stable softmax update.

**Line 7-9: The skip decision.** This is the only new logic BLASST adds.

```
if \tilde{m}_i^{(j)} - m_i^{(j-1)} < \ln(\lambda) then
    continue   // Skip this block
end if
```

The predicate uses `$m_i^{(j-1)}$` (the running maximum *before* incorporating the current block) rather than `$m_i^{(j)}$` (the updated running maximum). This is important: if we used the updated maximum, the test would always be `$\tilde{m}_i^{(j)} - m_i^{(j)} \leq 0$` and the block would never be skipped (since `$m_i^{(j)} = \max(\text{old}, \tilde{m}_i^{(j)})$` means `$\tilde{m}_i^{(j)} \leq m_i^{(j)}$` by construction).

When a block is skipped (`continue`), three types of operations are elided:

1. **Softmax computation (CUDA cores):** The expensive exponential operations that would compute `$\exp(S_{ij} - m_i^{(j)})$` are never issued. Each element requires a MUFU.EX2 instruction (hardware exponential), an FMUL (multiplication by the rescaling factor), and FADD operations for the rowsum reduction. For a block of size `$B_c \times B_c = 128 \times 128 = 16,384$` elements, this saves tens of thousands of CUDA core instructions.

2. **Value loading from HBM (memory bandwidth):** The Value block `$V_j$` is not loaded from high-bandwidth memory (HBM) into shared memory (SRAM). This is critical in the decode phase where HBM bandwidth is the bottleneck — loading a Value block of size `$B_c \times d_v$` (e.g., 128 × 128 = 16,384 half-precision elements = 32 KB) consumes memory bandwidth that directly competes with other operations.

3. **Attention-value matrix multiplication (tensor cores):** The MMA operation `$\tilde{P}_{ij} V_j$` that multiplies the post-softmax attention weights by the value vectors is never issued. In prefill, this is the dominant compute cost; skipping it frees tensor core cycles.

**Line 10-12: Standard FlashAttention updates (executed only for kept blocks).** When a block is *not* skipped:

- `$\tilde{P}_{ij} = \exp(S_{ij} - m_i^{(j)})$` computes the exponentiated and shifted attention weights, using the updated running maximum `$m_i^{(j)}$`. This requires MUFU.EX2 instructions per element.

- `$l_i^{(j)} = \exp(m_i^{(j-1)} - m_i^{(j)}) \cdot l_i^{(j-1)} + \text{rowsum}(\tilde{P}_{ij})$` updates the running softmax denominator. The first term rescales the previous denominator to account for the fact that the running maximum may have increased (if the current block contained a larger score than any previous block), which means all previously exponentiated values must be downweighted. The second term adds the current block's contribution. This is the standard online softmax update from FlashAttention.

- `$O_i^{(j)} = \exp(m_i^{(j-1)} - m_i^{(j)}) \cdot O_i^{(j-1)} + \tilde{P}_{ij} V_j$` updates the running accumulator. The first term rescales the previous accumulator (same rescaling as for the denominator), and the second term adds the current block's weighted value contribution. The `$\tilde{P}_{ij} V_j$` multiplication uses tensor cores.

**Line 14: Final normalization.** `$O_i = O_i^{(T_c)} / l_i^{(T_c)}$`. After all KV blocks have been processed (or skipped), the accumulated weighted sum is divided by the softmax denominator to produce the final attention output for query block `i`. This division is a per-element operation by CUDA cores.

**What the algorithm achieves:** the output `$O_i$` is an approximation to the true attention output. The error comes entirely from the mass discarded in skipped blocks. As derived in Appendix B of the paper, if `$S$` is the set of skipped blocks, each with `$B_c$` tokens, the total unnormalized attention mass discarded is bounded by `$|S| \cdot B_c \cdot \lambda$`, and the output error satisfies `$\|y - \hat{y}\| \leq |S| \cdot B_c \cdot \lambda \cdot V_{\max}$`, where `$V_{\max}$` is the maximum norm of any value vector. Because the approximate output is renormalized over non-skipped blocks only (using only `$l_i^{(T_c)}$` computed without skipped-block contributions), the effective error is even smaller in practice — the renormalization partially compensates for the discarded mass by proportionally increasing the weight of kept tokens.

**Why this form and not a learned sparsity predictor:** prior methods like MInference and SpargeAttention use separate prediction steps (proxy scores, learned gates) to decide which blocks to compute. These add overhead that can negate speedups, especially for shorter sequences where the prediction cost is comparable to the computation saved. BLASST's design eliminates this overhead entirely by basing the decision on values already resident in registers during the standard FlashAttention loop. The cost of the decision itself is negligible — as the paper notes, it requires a per-thread predicate, a VOTE instruction within each warp, and a single ATOMIC to shared memory — all of which can be hidden behind existing memory and compute operations in the pipeline schedule.

#### The Calibration Procedure: Why Fixed Thresholds Fail and How `$\lambda = a/L$` Solves It

The skip criterion depends on a threshold `$\lambda$`. If `$\lambda$` is too small, few blocks are skipped and speedup is minimal. If `$\lambda$` is too large, many blocks are skipped and accuracy degrades. The calibration problem is to choose `$\lambda$` such that the achieved sparsity (fraction of blocks skipped) matches a desired level across varying sequence lengths, while preserving accuracy.

**The failure of fixed thresholds.** Figure 2 (right) in the paper demonstrates the central calibration challenge. For Llama-3.1-8B, a fixed threshold of `$\lambda = 10^{-3}$` produces wildly different sparsity levels depending on context length: approximately 23% sparsity at 4K tokens, 38% at 8K, 52% at 16K, 66% at 32K, and 75% at 64K tokens. This instability is not a bug — it follows directly from the mathematics of softmax attention.

**Why fixed thresholds produce length-dependent sparsity.** The explanation is straightforward. For a sequence of length `L`, the post-softmax attention weights `$p_k$` must sum to 1. On average, each token receives attention weight `$1/L$`. As `$L$` grows, the typical attention score per token decreases — the same total attention mass of 1 is spread over more tokens. Therefore, a fixed threshold `$\lambda$` (interpreted as a maximum allowable post-softmax weight per skipped token) prunes more aggressively at longer lengths because a larger fraction of tokens naturally fall below the threshold.

Equivalently, in log-space: the raw attention scores `$s_k$` are row-normalized only implicitly through the softmax denominator. But the difference `$s_k - M$` (where `$M$` is the global maximum) determines the post-softmax weight. As the sequence grows, more tokens have scores far below the maximum, so a fixed `$\ln(\lambda)$` gap captures a larger fraction of the sequence.

**The inverse-length relationship.** The paper's key empirical finding is that to maintain a fixed sparsity level across lengths, the threshold must follow:

$$\lambda = \frac{a}{L}$$

where `$a$` is a model-specific constant that depends on the target sparsity level, and `$L$` is the context length (number of tokens).

**What this equation states:** the threshold `$\lambda$` should be inversely proportional to sequence length. For a given model and target sparsity, if you double the sequence length, you must halve the threshold to maintain the same sparsity ratio.

**Why this form — theoretical grounding.** The inverse relationship has a simple justification. Since the softmax normalization ensures `$\sum_k p_k = 1$`, the average post-softmax weight per token is `$1/L$`. A threshold `$\lambda$` represents a cutoff on individual token contributions. To maintain a fixed fraction of tokens below the cutoff as `$L$` varies, the cutoff must scale as `$1/L$`. The constant `$a$` absorbs the model-specific attention concentration: models that concentrate attention more sharply (fewer tokens account for most of the mass) will have larger `$a$` (more generous threshold, since most tokens are negligible anyway), while models with diffuse attention will have smaller `$a$`.

More formally, the paper fits an exponential model relating the product `$\lambda \cdot L$` to the target sparsity `$S$`:

$$\lambda \cdot L = \alpha \cdot \exp(\beta \cdot S)$$

where `$\alpha$` and `$\beta$` are fitted parameters. Equivalently:

$$\lambda = \frac{\alpha \cdot \exp(\beta \cdot S)}{L}$$

**Why an exponential form.** The attention score distribution is heavy-tailed: a small number of tokens receive high attention scores, and a long tail of tokens receive very low scores. When the threshold increases slightly, it prunes many tokens in the low-scoring tail (sparsity rises quickly). As the threshold increases further, it begins encroaching on the high-scoring core, where further increases yield diminishing sparsity returns (fewer tokens are in this regime). The exponential model `$\alpha \cdot \exp(\beta \cdot S)$` captures this relationship: small changes in `$S$` at low sparsity correspond to small changes in `$\lambda \cdot L$`, while the same change in `$S$` at high sparsity requires a much larger change in `$\lambda \cdot L$`.

**The calibration procedure in practice (Algorithm 2).** The paper's calibration algorithm works as follows:

1. **Sample a calibration dataset.** The authors use approximately 1,000 sequences from the RULER dataset across context lengths ranging from 4K to 64K tokens. The diversity of lengths is essential for fitting the length-scaling relationship.

2. **Single forward pass.** For each calibration sample `$x_i$` of length `$L_i$`, run a single forward pass of the model with BLASST enabled. During this pass, for each candidate threshold `$\lambda_j$` in a predefined set `$\Lambda$`, measure the achieved sparsity `$s_{ij}$` — the fraction of attention blocks that were skipped. Because the skip decision is a simple predicate on already-computed values, the sparsity at multiple thresholds can be measured from the same set of attention scores without rerunning the forward pass. This is a critical efficiency property: the entire sweep over `$\Lambda$` costs one forward pass, not `$|\Lambda|$` forward passes.

3. **Filter unreliable extremes.** Data points where the achieved sparsity `$s_{ij}$` falls outside `$[s_{\min}, s_{\max}]$` are discarded. These bounds (set to reasonable values like 5% and 95%) exclude thresholds that are essentially 0 (nothing skipped, no information about the score distribution) or essentially 1 (everything skipped, the model collapses). This filtering stabilizes the exponential fit.

4. **Fit the exponential model.** For each retained data point, compute the scale factor `$\lambda_j \cdot L_i$` and record the achieved sparsity `$s_{ij}$`. Fit the exponential model `$\lambda \cdot L = \alpha \cdot \exp(\beta \cdot s)$` using all collected points. This yields the model-specific parameters `$\alpha$` and `$\beta$`.

5. **Runtime threshold lookup.** At inference time, for a desired target sparsity `$S_{\text{target}}$` and an input of length `$L$`, the threshold is computed as `$\lambda = \alpha \cdot \exp(\beta \cdot S_{\text{target}}) / L$`. The target sparsity can be changed at runtime without recalibration — simply plug a different `$S_{\text{target}}$` into the formula.

**What the calibration guarantees.** As demonstrated in Table 6, calibrated thresholds produce sparsity levels within a tight band across sequence lengths. For a target sparsity of 50%, the observed sparsity ranges from 46.96% to 54.20% across lengths from 4K to 64K — an average deviation of only 1.2 percentage points from the target. In contrast, a fixed threshold deviates by up to 26.9 percentage points at the extremes. This stability is what makes BLASST practical for production deployment, where input lengths vary and consistent performance (both speedup and accuracy) is required.

**Why calibration on a single mixed dataset suffices.** The paper provides cross-dataset validation in Appendix A (Table 12), showing that calibration parameters `$a$` (where `$\lambda = a/L$`) transfer across different task types without heavy retuning. For prefill, all tested datasets yield similar `$a$` values (within roughly 10-20% of each other). For decode, two datasets (niah single and qa) show noticeably smaller `$a$` — the authors attribute this to retrieval-focused decoding patterns where the model attends narrowly to specific relevant spans, producing more concentrated attention distributions that require a smaller threshold to reach the same sparsity. Importantly, even with this variation, the achieved sparsity remains close to the 50% target across all datasets, confirming that a single calibration on a mixed dataset is sufficient for robust deployment.

#### Prefill Kernel Design: Compute-Bound Optimization with Restructured Pipeline Scheduling

The prefill phase processes the entire input sequence at once, computing attention for all query tokens against all key-value pairs. On modern GPUs, prefill is **compute-bound**: the bottleneck is the throughput of tensor cores (for the `$\tilde{P}_{ij} V_j$` matrix multiplication, called BMM2) and CUDA cores (for softmax exponentiation and rescaling), rather than HBM bandwidth. The BLASST prefill kernel is therefore designed to skip the compute-heavy operations for pruned blocks while keeping the memory access patterns intact.

**Warp-group specialization in FlashAttention-4.** To understand the BLASST prefill kernel, we must first understand the baseline pipeline it modifies. FlashAttention-3 and FlashAttention-4 use warp-group specialization to overlap different types of work. The thread block is divided into warpgroups that operate asynchronously:

- **MMA (math) warpgroups** execute tensor core operations — specifically, BMM1 (the QK product, `$S_{ij} = Q_i K_j^T$`) and BMM2 (the attention-value product, `$\tilde{P}_{ij} V_j$`). These operations are issued to tensor cores and execute asynchronously.

- **Softmax warpgroups** execute CUDA core operations — specifically, extracting the row-wise maximum from `$S_{ij}$`, computing exponentials `$\exp(S_{ij} - m_i^{(j)})$`, summing rows for the denominator, and applying the softmax rescaling when the running maximum increases.

These warpgroups are pipelined so that while one warpgroup is computing BMM2 for KV block `j`, another warpgroup is computing the softmax for KV block `j+1`, and yet another is issuing loads for KV block `j+2`. This overlapping of computation and memory access is what makes FlashAttention-4 efficient.

**What BLASST changes in the prefill pipeline.** Figure 3 in the paper shows the pipeline schedule for (a) standard FlashAttention-4 and (b) BLASST at 50% sparsity across 4 mainloop iterations (L0–L3). The figure uses two tile rows (T0 and T1, representing two query blocks processed concurrently) and tracks operations through time units.

In the standard schedule (Figure 3a), every mainloop iteration includes:
- BMM1 (QK product) for the current block
- Softmax EX2 (exponential) for the current block's scores
- BMM2 (attention-value product) for the current block
- A correction step when the running maximum increases (rescaling the previous accumulator and denominator)

The total schedule spans 18 time units.

In the BLASST schedule (Figure 3b), iterations 1 and 3 (corresponding to KV blocks that fail the skip test) omit both the softmax exponentiation (EX2) and the BMM2 operations. The pipeline compresses: instead of taking a full time slot for softmax and another for BMM2, those slots are simply absent, allowing subsequent operations to shift earlier. The total schedule compresses to 14 time units — a 22% reduction in latency for 50% sparsity.

**What is actually skipped in the prefill kernel:**

1. **Softmax exponentiation and rowsum reduction.** The CUDA core operations that compute `$\exp(S_{ij} - m_i^{(j)})$` and sum rows for the denominator are never issued. This saves the MUFU.EX2, FMUL, and FADD instructions that constitute the bulk of softmax compute. The paper notes this saves "thousands of CUDA core instructions" per skipped block.

2. **BMM2 (attention-value matrix multiplication).** The tensor core operation `$\tilde{P}_{ij} V_j$` is never issued. In prefill, this is the dominant compute cost, taking substantial tensor core cycles. Skipping it directly reduces tensor core utilization for the skipped blocks, freeing cycles that can be used by other concurrent operations or remaining blocks.

3. **Correction steps for skipped blocks.** When a block is skipped, there is no softmax output to incorporate, so the rescaling of the previous accumulator (the `$\exp(m_i^{(j-1)} - m_i^{(j)})$` factor) is not needed for that iteration. This eliminates the associated FMUL operations.

**What is deliberately NOT skipped in prefill: Value loading.** A subtle design choice explained in the paper: the prefill kernel continues to load the Value block `$V_j$` from HBM even for skipped blocks. The rationale is threefold:

- **Memory bandwidth is not the bottleneck.** Prefill is compute-bound, so loading extra data from HBM does not directly slow down the critical path — the tensor cores and CUDA cores are the limiting resources, not the memory bus.

- **The prefetching pipeline benefits from predictable patterns.** FlashAttention's prefill kernel uses asynchronous copy (TMA on Hopper/Blackwell) to prefetch KV blocks for future iterations. Breaking this predictable pattern with conditional loads would introduce control-flow divergence and pipeline bubbles that could outweigh the memory bandwidth savings.

- **The latency of conditional Value loading would exceed the savings.** Deciding at runtime whether to load `$V_j$` requires the skip predicate to be computed first, which introduces a scoreboard dependency — the load cannot be issued until the BMM1 result is available and the rowmax and comparison are complete. This serialization would stall the pipeline more than the bandwidth saved by skipping the load.

The paper explicitly notes that this design choice reflects current hardware characteristics: "Value loading could be skipped in prefill if future workloads and/or hardware architectures shift to a memory-bandwidth-bound regime." For now, skipping only the compute operations (softmax and BMM2) while keeping the predictable memory access pattern yields speedups that scale nearly linearly with sparsity in the compute-bound regime.

**Overhead of the skip decision.** The decision logic itself adds minimal overhead because it reuses values already in registers:

1. Each thread in the softmax warpgroup already holds a portion of `$S_{ij}$` and has computed its local maximum as part of the rowmax reduction.
2. A per-thread predicate is set based on the comparison `$\tilde{m}_{\text{thread}} - m_i^{(j-1)} < \ln(\lambda)$`.
3. A VOTE instruction (e.g., `__all_sync` in CUDA) determines if all threads within a warp agree to skip — this is a single-cycle warp-level reduction.
4. One thread per warp issues an ATOMIC to shared memory to coordinate the block-level decision across the softmax warpgroup.

The paper notes that these instructions "are hidden behind existing operations, adding negligible latency overhead." Consistent with this claim, Table 5 shows that at 0% sparsity (no blocks skipped), the BLASST kernel achieves 1.00× the speed of the baseline on Blackwell — there is no measurable overhead from the skip-check logic when no blocks are actually pruned.

#### Decode Kernel Design: Memory-Bound Optimization with Batched Load Scheduling

The decode phase generates one token at a time, computing attention for a single query vector against the entire KV cache. On modern GPUs with typical batch sizes, decode is **memory-bound**: the bottleneck is the HBM bandwidth required to fetch the stored keys and values for each new token. The BLASST decode kernel is designed to skip the memory-intensive Value loads for pruned blocks, directly addressing this bandwidth bottleneck.

**Why decode is different from prefill.** The computational profile is fundamentally reversed:

- In prefill, the QK product involves large matrix multiplications (many query tokens × many key tokens), making it compute-intensive. The Value load is a small fraction of total time because the BMM2 dominates.
- In decode, the QK product is a vector-matrix multiplication (1 query token × many key tokens), which is memory-bandwidth-bound by the K loading. The Value load is comparably expensive — for each token generated, the entire Value cache must be streamed from HBM. Skipping Value loads directly reduces HBM traffic.

For a decode step with KV cache length `$L$`, the attention computation loads approximately `$L \cdot d_k$` elements for keys and `$L \cdot d_v$` elements for values from HBM. If 50% of blocks are skipped, the Value traffic is halved — a substantial bandwidth savings that translates directly to speedup in a memory-bound kernel.

**The pipeline bubble problem with naive conditional loading.** The decode kernel faces a scheduling challenge absent in prefill. In the standard FlashAttention decode pipeline (Figure 4a), operations are heavily pipelined: while BMM1 for block `j` is computing, the key load for block `j+1` is already issued, and the value load for block `j-1` may be in flight. This pipelining keeps the HBM bus saturated.

If we naively make Value loads conditional on the skip decision, the following problem arises:
- The skip decision for block `j` depends on BMM1 completing (so we can extract the rowmax and compare to the running maximum).
- BMM1 completes late in the pipeline for block `j`.
- The Value load for block `j` should ideally have been issued much earlier to overlap with BMM1.
- If we wait for the skip decision before issuing the Value load, we introduce a **pipeline bubble** — the HBM bus sits idle between the Key load and the conditional Value load.

Figure 4 illustrates this with scoreboard dependencies (arrows). In Figure 4b, the Key loads (L0,K Load through L5,K Load) are issued sequentially, but the Value loads cannot be issued until the skip check for that iteration completes after BMM1. This serialization would cost more in lost bandwidth than the skipped loads would save.

**Batched load scheduling — the solution.** The BLASST decode kernel restructures the pipeline to process multiple QK products before issuing Value loads. The approach:

1. **Process a batch of consecutive query-key products back-to-back.** Instead of the standard pattern (load K_j, compute `$K_j^T Q$`, check skip, decide whether to load V_j, repeat for j+1), BLASST loads keys and computes QK products for B consecutive blocks sequentially: `$K_j^T Q, K_{j+1}^T Q, \ldots, K_{j+B-1}^T Q$`.

2. **Buffer the attention scores.** Each QK product `$S_j = K_j^T Q$` must be stored temporarily so the skip decision can be made later. For decode with a single query token, each `$S_j$` is a vector of length `$B_c$` (one row, `$B_c$` columns). Maintaining B such buffers requires `$B \cdot B_c$` elements of shared memory, which is small compared to what's already allocated for tiling.

3. **Make all B skip decisions.** After computing all B QK products, the kernel has B local maxima `$\tilde{m}^{(j)}, \ldots, \tilde{m}^{(j+B-1)}$` and can evaluate the skip predicate for each.

4. **Issue Value loads only for kept blocks.** With the skip decisions known, issue a batch of TMA loads for only those Value blocks whose corresponding attention blocks pass the threshold. Because the loads are batched and issued together, there are no pipeline bubbles — the TMA unit can process the batch efficiently.

5. **Compute BMM2 for kept blocks.** The attention-value products are computed only for loaded Value blocks, using the buffered attention scores.

**The trade-off: shared memory for batched decision-making.** The batched approach requires maintaining B shared memory buffers for `$S_j$` vectors, one for each block in the batch. For decode with query sequence length 1, each buffer is `$B_c$` elements (e.g., 128 half-precision floats = 256 bytes). With a batch size of, say, B = 4, the total shared memory overhead is roughly 1 KB — negligible relative to the typical shared memory budget of 48–164 KB per thread block on modern GPUs. The paper notes "they are relatively small with a query sequence length of 1," acknowledging that this design would need reconsideration for prefill (where query sequence length is large and `$S_{ij}$` is a full matrix, not a vector).

**What the batched scheduling achieves.** Figure 4b shows the resulting pipeline. Comparing to the standard schedule (Figure 4a, 38 time units to complete Value loads), the BLASST schedule (Figure 4b) takes 31 time units when loops 1, 2, and 4 are skipped. The key insight is that because Value loads are issued only for blocks 0, 3, and 5 (the kept blocks), the total time spent on Value loads is reduced proportionally to the sparsity. The serialization introduced by batched K-loading is offset by the bandwidth saved from not loading unnecessary Values.

**Additional compute savings in decode.** For standard attention (MHA, GQA, MQA), the decode kernel focuses on memory-bandwidth savings. However, for attention variants like Multi-Head Latent Attention (MLA; DeepSeek-AI, 2025), decode can be compute-bound because MLA operates in a compressed latent space that reduces KV cache size but increases per-token computation. For such variants, the BLASST decode kernel also skips softmax computation for pruned blocks, providing additional compute savings beyond memory bandwidth reduction. This adaptability to the bottleneck — skipping what is expensive in each regime — is a deliberate design choice.

**The Value-load optimization's magnitude.** In a memory-bound decode kernel, skipping Value loads provides speedup roughly proportional to the fraction of Value traffic eliminated. If the total HBM traffic per decode step is `$T = T_K + T_V + T_{\text{other}}$`, where `$T_K$` is key loading, `$T_V$` is value loading, and `$T_{\text{other}}$` is other traffic (query, output, intermediate buffers), then skipping a fraction `$s$` of Value blocks reduces total traffic to `$T' = T_K + (1-s)T_V + T_{\text{other}}$`. For typical configurations where `$T_V$` is a large fraction of `$T$` (often 40–60%), the bandwidth savings are substantial. The paper's reported 1.48× decode speedup at 73.2% sparsity (Table 5) reflects these savings, with the speedup somewhat less than the ideal 1/(1 - 0.732 × fraction_V) due to fixed overheads and the cost of the batched scheduling.

#### Extensibility to Attention Variants

A claims the paper makes is that BLASST is compatible with "all major attention variants (MHA, GQA, MQA, and MLA)" (Section 1, Abstract). This extensibility follows from the fact that BLASST's skip criterion depends only on the online softmax computation, not on any specific property of the attention mechanism.

**Why the softmax is the invariant.** Every attention variant that uses standard scaled dot-product attention (with softmax normalization) computes a running maximum during online softmax for numerical stability. MHA (Multi-Head Attention) uses independent Q, K, V projections per head. GQA (Grouped Query Attention) shares K and V across groups of query heads but still computes per-head softmax. MQA (Multi-Query Attention) shares K and V across all heads but still normalizes per head. In all cases, each attention head independently maintains running maxima during its tiled computation, and BLASST's block-skip logic applies identically per head.

**MLA compatibility — a specific concern addressed.** Multi-Head Latent Attention (MLA), introduced in DeepSeek-V2 (Liu et al., 2024a) and used in DeepSeek-R1 (Guo et al., 2025), compresses the KV cache into a low-rank latent space to reduce memory footprint. Despite this compression, MLA "still employs online softmax to compute attention scores within its latent space" (Section 3.3). The attention computation in MLA involves projecting queries and the latent KV representations into a shared space, computing dot products, and applying softmax — the same pattern as standard attention. The running maximum is still maintained, and the block-skip criterion applies unchanged.

The paper verifies MLA compatibility empirically in Appendix A (Table 11), evaluating DeepSeek-R1 NVFP4 with BLASST at 0%, 50%, and 60% target sparsity on GPQA Diamond, MMLU Pro, and LiveCodeBench. At 60% sparsity, accuracy drops by less than 0.01 across all three benchmarks (GPQA: 0.7109 vs. 0.7071; MMLU Pro: 0.8266 vs. 0.8302; LiveCodeBench: 0.5677 vs. 0.5735) — well within the range of sampling variation.

**Why MLA's compute-bound decode matters.** The paper notes that "MLA decoding shifts the bottleneck towards a compute-bound regime" (Section 3.3). Standard decode is memory-bound because each token generation must stream the entire KV cache from HBM. MLA reduces the KV cache size substantially (through low-rank compression), which alleviates the memory bottleneck but shifts the bottleneck to the computation of reconstructing the full attention from the latent representations. In this regime, BLASST's compute savings (skipping softmax exponentials and attention-value multiplication) become important even during decode. The paper's design accommodates this by conditionally skipping softmax operations in decode when they represent a bottleneck — the kernel checks whether the attention variant is compute-bound or memory-bound and optimizes accordingly.

#### Sparsity-Aware Training: Teaching Models to Be Sparsifiable

While BLASST is fundamentally a training-free method, the paper explores fine-tuning with BLASST active as a way to improve the accuracy-sparsity trade-off. The motivation is straightforward: if a model is trained under sparse attention, it should learn to concentrate important information in high-scoring blocks that will survive pruning at inference time.

**How sparsity-aware fine-tuning works.** The approach is remarkably simple:

1. **Forward pass with BLASST.** During fine-tuning, the forward pass uses the standard BLASST kernel with a fixed threshold, exactly as it will run at inference. Blocks that fail the skip test are pruned — their softmax, Value loads, and BMM2 operations are skipped.

2. **Backward pass follows the forward pass.** Blocks that were skipped in the forward pass naturally receive no gradients, because their outputs were zero. The backward pass computes gradients only through the kept blocks. This is not an explicit masking — it falls out of the fact that skipped blocks never contributed to the forward output, so the chain rule automatically excludes them.

3. **No auxiliary losses or architectural changes.** Unlike methods that introduce sparsity-inducing regularization (e.g., L1 penalties on attention weights) or learned gating mechanisms, BLASST's sparsity-aware training adds nothing beyond the forward-pass modification — the same threshold-based pruning used at inference is applied during training.

**The training procedure adopted.** The paper uses the curriculum training approach from ProLong (Gao et al., 2025a), a method designed for training long-context language models. The curriculum gradually increases context length during fine-tuning. BLASST is active during this fine-tuning phase with a fixed sparsity threshold, meaning the model learns to attend effectively under the constraint that some attention blocks will be pruned.

**Why this works.** The mechanism is a form of implicit regularization. When a block is skipped, the model cannot use the key-value pairs in that block to influence its output. If those key-value pairs were important for the task (i.e., the model would have assigned them high attention weights), the loss will be higher because the information was unavailable. Over many training steps, gradient descent adjusts the model parameters to either:

- Concentrate more attention mass into blocks that pass the threshold (so the same information is preserved even under sparsity), or
- Restructure the representations so that the information needed for the task is placed in positions (tokens) that naturally receive higher attention scores.

The result, shown in Figure 6, is that sparse-trained models maintain higher accuracy at aggressive sparsity levels compared to models where sparsity is applied only at inference time. At 50% observed sparsity, the sparse-trained model's RULER accuracy degradation is reduced by up to 1.7× relative to training-free application.

**The relationship to the skip criterion.** During sparsity-aware training, the threshold is fixed (calibrated to produce approximately the target inference sparsity on the training data). The model cannot "game" the threshold by making all attention scores very large (which would prevent any blocks from being skipped), because the threshold is calibrated to produce a target sparsity regardless — if the scores uniformly increase, the running maximum also increases, maintaining the same gap distribution and thus the same skip rate. What the model can do is **restructure the relative distribution** of attention scores, making the important blocks have scores substantially larger than the mean so they survive pruning, while allowing unimportant blocks to fall below the threshold.

**A noteworthy result from Figure 6.** At very low sparsity (near 0%), the sparse-trained model slightly *outperforms* the dense baseline. This suggests that training with BLASST active acts as a beneficial regularizer even when few blocks are actually skipped — the model learns more robust attention patterns that generalize slightly better. This is consistent with known effects in dropout and other stochastic regularizers, where training-time noise improves test-time performance.

## 4. Key Insights and Innovations

### Innovation 1: Online Softmax Statistics Are Free Sparsity Oracles — No Extra Predictors Needed

The paper's most distinctive conceptual move is the recognition that **the statistics FlashAttention already computes for numerical stability — specifically, the running maximum maintained during online softmax — double as a perfect signal for identifying negligible attention blocks, with zero additional cost.** This is not an optimization that makes a predictor faster or more accurate; it is the elimination of the predictor entirely.

Before BLASST, the dominant paradigm for dynamic sparse attention was **prediction-then-pruning**: first estimate which attention scores matter (using proxy importance scores in MInference, anti-diagonal patterns in XAttention, compressed representations in FlexPrefill, or separate prediction steps in SpargeAttention), then compute only those scores. This two-stage approach introduces an inherent tension — the prediction step itself costs compute, and that cost must be amortized over the savings from skipping computation. For methods like MInference, the pre-computation pass over the full input fundamentally limits the net speedup: even if the second pass is sparse, the first pass is dense and sequential.

BLASST sidesteps this tension entirely by observing that **the running maximum `$m_i^{(j)}$` — updated during every iteration of FlashAttention's mainloop — implicitly encodes the cumulative importance of all previously seen blocks.** The block-local maximum `$\tilde{m}_i^{(j)}$` is computed as part of the rowmax reduction needed for the online softmax update. The comparison `$\tilde{m}_i^{(j)} - m_i^{(j-1)} < \ln(\lambda)$` reuses both values, neither of which requires additional computation. The skip decision is essentially free — a predicate based on values already resident in registers — rather than a separate algorithmic stage.

This shift from *prediction-driven* to *statistics-driven* sparsity has a profound practical consequence that the feature comparison in Table 1 makes explicit: BLASST is the only method with checkmarks in all four columns (Accelerates Prefill, Accelerates Decode, No Training, No Pre-Computation). This is not a coincidence of implementation effort. The "No Pre-Computation" property follows directly from the architectural choice to reuse online softmax state. Methods that build separate predictors (MInference, SpargeAttention, XAttention) are structurally incapable of achieving this because the predictor fundamentally requires looking at the input — whether through a lightweight forward pass, a compressed representation, or pattern analysis — before deciding what to compute. BLASST's design makes the decision *during* computation rather than *before* it.

The distinction from SpargeAttention — the closest prior work — illustrates the conceptual gap sharply. SpargeAttention also identifies low-scoring blocks, but uses "a separate prediction step" (Section 2). This step adds overhead that BLASST's reuse-based approach avoids. More subtly, the prediction-based design creates a chicken-and-egg problem: to predict which blocks can be skipped, you need information about the attention scores; to get that information efficiently, you want to skip blocks. BLASST breaks this circularity by interleaving the decision with the computation — the information needed for the decision (running maximum, block-local maximum) is produced as a natural byproduct of the attention computation that is happening anyway.

This is a **fundamental reframing**, not an incremental improvement. The field's default assumption was that sparse attention required an explicit importance-estimation step — either offline (pre-computed patterns), online (proxy scores), or learned (gates). BLASST demonstrates that this assumption is false: the numerical machinery required for stable softmax computation already contains sufficient information to make effective pruning decisions, and the engineering challenge is not building a better predictor but recognizing that the predictor already exists in the algorithm's own state.

The evidence for the zero-overhead claim is concrete. Table 5 shows that at 0% sparsity (no blocks skipped), the BLASST prefill kernel achieves 1.00× the baseline speed on Blackwell — the skip-check logic introduces no measurable slowdown when no blocks are pruned. This would be impossible for any method with a separate prediction stage, where the prediction cost is paid regardless of how many blocks are ultimately skipped.

### Innovation 2: The Inverse-Length Calibration Law — Turning an Implementation Detail into a Deployment Principle

The paper's second conceptual contribution is transforming a practical tuning problem — how to choose the threshold λ — into a **discovered empirical law that reveals a structural property of softmax attention under variable-length inputs.** The finding that `λ = a/L` (where L is context length) is not presented as a heuristic or a rule of thumb; it is framed as a necessary consequence of how softmax distributes probability mass, with implications that extend beyond BLASST itself.

Prior work on threshold-based sparsity (including SpargeAttention) treated the threshold as a hyperparameter to be tuned per task or per model, with no systematic characterization of how it should scale with input properties. The implicit assumption was that a "good threshold" for a 16K model would work reasonably at 8K or 32K — maybe with some degradation, but not fundamentally different behavior. Figure 2 (right) demolishes this assumption. A fixed threshold of `λ = 10^{-3}` produces 23% sparsity at 4K and 75% sparsity at 64K on the same model — a 3.3× difference in sparsity from a 16× difference in length. This is not a small calibration error; it means a fixed-threshold deployment would be wildly inconsistent, producing near-dense computation for short inputs and aggressive pruning (with likely accuracy collapse) for long inputs.

The insight that explains this pattern — and that gives the inverse-length relationship its theoretical grounding — is that **the softmax normalization `∑ p_k = 1` distributes a fixed budget of 1.0 attention mass over L tokens. As L grows, the average per-token weight must shrink proportionally.** A threshold λ that captures a fixed fraction of tokens therefore must also shrink proportionally. The constant `a` in `λ = a/L` absorbs model-specific attention concentration — how sharply the model concentrates attention mass onto the most relevant tokens versus spreading it diffusely. Models with sharper concentration (more mass on fewer tokens) will have larger `a` because a coarser threshold still captures the important tokens; models with flatter attention require smaller `a`.

This is a **diagnostic insight** as much as a practical one. The inverse-length relationship says something about the *structure* of attention under softmax, not just about BLASST's calibration. It explains why fixed-threshold methods have struggled with variable-length deployment — they were fighting the mathematics, not just tuning poorly. And it suggests that any threshold-based sparsity method (not just BLASST) should scale its threshold inversely with sequence length to maintain consistent behavior.

The calibration procedure that operationalizes this relationship (Algorithm 2) is itself an innovation in **single-pass multi-threshold measurement**. By collecting sparsity measurements for multiple thresholds from a single forward pass — possible because the skip decision is a lightweight predicate on already-computed attention scores, not a separate computation — the entire calibration sweep requires only one inference run over the calibration dataset. This makes calibration cheaper than a single dense forward pass for long sequences, where the alternative would be running the model once per candidate threshold. The exponential fit `λ · L = α · exp(β · S)` that maps target sparsity to threshold is pragmatic — it captures the heavy-tailed nature of attention score distributions, where small threshold changes at low sparsity prune many tail tokens (fast sparsity increase) and large changes at high sparsity are needed to prune the core (diminishing returns).

The practical consequence, demonstrated in Table 6, is that calibrated thresholds produce sparsity within ~1.2 percentage points of the target across a 16× range of sequence lengths. This level of consistency — predictable, controllable sparsity regardless of input length — is what makes BLASST deployable as an inference serving solution rather than a research prototype that works for one configuration.

This is fundamentally an **empirical discovery with theoretical grounding**, not merely an engineering fix. The field had not previously characterized the length-scaling behavior of attention score distributions under softmax in a way that yielded a simple, actionable calibration law. BLASST's contribution here is making that relationship explicit and demonstrating that it is robust enough to serve as the foundation for production deployment.

### Innovation 3: The Prefill-Decode Duality — Treating Two Phases as One Problem with Two Bottlenecks

The paper's third conceptual contribution is its treatment of prefill and decode as **two manifestations of the same sparse attention problem with fundamentally different bottlenecks**, and its demonstration that a single algorithmic mechanism (threshold-based block skipping) can be optimized for both by targeting different operations in each phase.

The field's prior approach to this duality was fragmentation. Methods specialized for one phase or the other, as Table 1 shows: H2O, SnapKV, RocketKV, and Quest target decode only (reducing KV cache size to save memory bandwidth); MInference, SpargeAttention, and XAttention target prefill only (reducing attention computation). This specialization was partly justified — prefill is compute-bound (tensor cores are the bottleneck), decode is memory-bound (HBM bandwidth is the bottleneck), and optimizations for one bottleneck often don't help the other. But it produced a deployment gap: a practitioner wanting end-to-end inference acceleration had to cobble together separate prefill and decode methods, negotiate their compatibility, and hope that the combined accuracy degradation was acceptable.

BLASST's key insight is that **the same block-skipping mechanism eliminates both bottlenecks, but through different saved operations.** In prefill, skipping a block saves softmax exponentiation (CUDA core workload) and the `\tilde{P}_{ij} V_j` matrix multiplication (tensor core workload), targeting the compute bottleneck directly. In decode, skipping a block saves the Value load from HBM (memory bandwidth), targeting the bandwidth bottleneck directly. The skip criterion — the comparison of block-local maximum to running maximum — is identical in both phases. What differs is *which downstream operations are elided* when the criterion triggers.

This is more than an "implementation supports both phases" claim. It reflects a **unified view of attention sparsity** in which the same information (the relative importance of a block's attention scores, as measured by the running maximum gap) determines what to skip, but the skip's benefit is realized differently depending on the execution phase. The paper's kernel design for each phase makes this explicit: the prefill kernel continues loading Value blocks from HBM even for skipped blocks (because memory bandwidth isn't the bottleneck and conditional loading would introduce pipeline bubbles), while the decode kernel aggressively skips Value loads (because memory bandwidth is the bottleneck and the batched scheduling amortizes the conditional-load overhead). The same algorithm, two different physical optimizations, chosen based on the phase's computational profile.

The evidence that this unified approach works is in the speedup numbers (Table 5). At ~70% achieved sparsity, BLASST delivers 1.52× prefill speedup and 1.48× decode speedup on Blackwell — the speedups are comparable in magnitude despite targeting completely different hardware resources (tensor cores vs. HBM bandwidth). This symmetry is not guaranteed; it falls out of the fact that attention computation and Value loading are roughly proportional in cost across phases, so saving a fixed fraction of blocks saves a fixed fraction of the bottleneck resource regardless of which resource bottlenecks.

This duality-aware design is a **fundamental architectural shift** in how sparse attention kernels are conceived. Prior work implicitly accepted the phase specialization as inevitable — if a method targets decode, it focuses on KV cache; if it targets prefill, it focuses on compute. BLASST demonstrates that a single sparsity mechanism can be phase-aware at the implementation level without being phase-specific at the algorithmic level, and that this unification eliminates the compatibility and accuracy-degradation risks of combining disparate methods. The "Both Phases" column in Table 1 is not just a feature checkbox; it represents a design philosophy that sparse attention should be an end-to-end property of the inference engine, not a per-phase patchwork.

### Innovation 4: The Calibration-Stability Principle — Accuracy Degrades by Sparsity Ratio, Not by Task or Length

A subtler but equally important finding emerges from Figure 2 (left): **relative accuracy degradation under BLASST's sparsity depends primarily on the achieved sparsity ratio, not on the specific task, dataset, or sequence length.** The paper shows that accuracy curves across four different context lengths (8K, 16K, 32K, 64K) and multiple RULER subtasks (NIAH MULTI, VT, FWE) collapse onto a single degradation curve when plotted against sparsity percentage — stable up to ~60-70%, then dropping sharply beyond ~75%.

This is a **discovered invariance**, not an engineered property. The paper did not design BLASST to produce length-independent degradation; it measured the degradation and observed the invariance. The implication is significant: if degradation depends only on sparsity ratio, then sparsity ratio becomes a sufficient statistic for accuracy preservation. Calibrating for a target sparsity (as the calibration procedure does) simultaneously calibrates for a target accuracy envelope, regardless of the input's properties. This is what makes the calibration procedure a valid deployment strategy — you choose a sparsity level that gives acceptable accuracy on a calibration set, and that accuracy generalizes to unseen inputs of different lengths and task types, provided the sparsity level is maintained.

The invariance also explains *why* the inverse-length calibration law `λ = a/L` works. If accuracy depends only on sparsity, and sparsity depends on `λ` and `L` through the relationship in Figure 2 (right), then maintaining consistent sparsity across lengths (via `λ = a/L`) maintains consistent accuracy across lengths. The calibration procedure's goal — achieve target sparsity `S` — is the right goal because sparsity is the mediator between threshold and accuracy.

This principle has a **diagnostic value** beyond BLASST. It suggests that for any attention sparsity method, the primary axis of accuracy preservation is "fraction of attention mass retained" (or equivalently, fraction of blocks computed), not the specific pattern of which blocks are skipped. If a method's accuracy degradation varies substantially across tasks at the same sparsity level, that variation indicates that the method's selection criterion is misaligned with what actually matters for the task — it is skipping the wrong blocks. BLASST's stability across tasks (Table 12 shows calibration parameters transferring reasonably across datasets with only mild variation for decode) validates that its block-skipping criterion — based on actual softmax scores, not proxies — tracks genuine importance effectively.

This is an **empirical contribution with theoretical implications**, not just a performance observation. It identifies sparsity ratio as a meaningful abstraction layer between the low-level mechanism (threshold-based block selection) and the high-level property (accuracy preservation), and it demonstrates that this abstraction holds across enough variation in inputs to be practically useful for deployment.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper evaluates on two categories of benchmarks. For long-context tasks: RULER (Hsieh et al., 2024), a synthetic benchmark testing retrieval and reasoning across 4K–128K token contexts, and LongBench v2 (Bai et al., 2025), covering real-world QA, summarization, and code completion. For reasoning tasks: MATH500 (mathematical problem solving), AIME 2024 (advanced mathematics), GPQA (graduate-level science), and LiveCodeBench (code generation). Additionally, RepoQA (Liu et al., 2024b) is used for very-long-sequence code understanding at 16K and 200K context lengths, and RULER-hard subsets evaluate needle-in-a-haystack performance on larger models. For calibration, approximately 1,000 sequences from the RULER dataset across context lengths 4K–64K are sampled.

- **Base model(s).** Primary evaluation uses two 8B-parameter instruct models: Llama-3.1-8B-Instruct and Qwen3-8B-Instruct, both supporting context lengths up to 128K tokens. The choice of 8B models places evaluation in a regime where test-time sparsity can make a meaningful accuracy–efficiency trade-off — large enough to exhibit realistic attention patterns, but small enough that sparse attention speedups are practically impactful for deployment. Larger model variants — Qwen3-30B-A3B-Instruct, Llama-3.1-70B-Instruct, and Qwen3-Coder-30B-A3B-Instruct — are evaluated in Appendix A for scalability analysis. For reasoning tasks with long-generation trajectories, a Llama-3.1-8B-Instruct variant distilled from DeepSeek-R1 (Guo et al., 2025) is used. MLA compatibility is tested on DeepSeek-R1 NVFP4 (Table 11).

- **Metrics.** The primary metrics are **accuracy** (task-specific: exact match grading for MATH500 using the Lightman et al. (2022) grading function, pass@1 for RULER and LongBench, best-of-N with majority voting or self-consistency for reasoning benchmarks) and **speedup** (wall-clock time of BLASST kernels vs. FlashAttention-3 BF16 baselines, measured on Blackwell B200 and Hopper H200 GPUs). For calibration, **achieved sparsity** is the fraction of attention blocks skipped during a forward pass. For end-to-end serving benchmarks, **TTFT** (time to first token) and **TPOT** (time per output token) are measured in TensorRT-LLM with in-flight batching at concurrency 64. The accuracy–sparsity trade-off is plotted as accuracy vs. achieved sparsity (Figures 5, 6, 8).

- **Baselines.** For prefill comparison (Table 3): MInference (Jiang et al., 2024), FlexPrefill (Lai et al., 2025), and XAttention (Xu et al., 2025). For decode comparison (Table 4): Quest (Tang et al., 2024) and RocketKV (Behnam et al., 2025). Each baseline uses its best-performing configuration as reported in its respective paper. The kernel speedup baseline is FlashAttention-3 BF16 (Shah et al., 2024) on Blackwell, and FlashAttention-4 (Zadouri et al., 2026) on Hopper. The dense baseline for all accuracy comparisons is full (non-sparse) attention with identical decoding parameters.

- **Generation budget / compute accounting.** Kernel speedups are measured at **fixed achieved sparsity levels**, obtained by sweeping the threshold λ and measuring both the resulting sparsity (fraction of blocks skipped) and the wall-clock execution time relative to the dense baseline. Sparsity is the common currency for comparing efficiency — methods with higher sparsity compute fewer attention blocks. For end-to-end serving benchmarks (Figure 5), target sparsity is stepped from 0% to 80% and TTFT/TPOT is plotted against LongBench V1 accuracy. No FLOP-equivalent accounting is used for the prefill/decode baseline comparisons in Tables 3–4; those tables compare accuracy at a target sparsity (50% for BLASST) against each baseline's own best configuration, making the comparisons somewhat heterogeneous since baselines achieve different sparsity levels through different mechanisms.

- **Cross-validation / statistical protocol.** For calibration, the exponential model `λ · L = α · exp(β · S)` is fitted on all collected (threshold, length, sparsity) triples from the calibration dataset, with extreme sparsity values (outside `[s_min, s_max]`, presumably ~5–95%) filtered to stabilize the fit. No k-fold cross-validation of the calibration is reported — the fitted parameters α and β are evaluated directly on the test benchmarks. For long-context benchmarks (RULER, LongBench), evaluation uses greedy decoding with temperature=0 and a single run per example (deterministic). For reasoning benchmarks, temperature=0.6 and top-p=0.95 are used, generating 10 samples per problem for MATH500, GPQA, and LiveCodeBench, and 20 samples per problem for AIME 2024, with best-of-N selected via majority voting. No confidence intervals or error bars are reported for accuracy numbers in Tables 2–4, 6–8, or for the calibration stability results in Table 12. The kernel speedup measurements (Table 5) presumably come from single-run wall-clock timing; no standard deviation is reported.

### Main Quantitative Results

#### Overall Accuracy Preservation Under Sparsity

Table 2 presents the headline result: at 50% target sparsity, BLASST matches or occasionally exceeds dense attention accuracy across all benchmarks on both Llama-3.1-8B and Qwen3-8B. On Llama-3.1-8B at 50% sparsity, RULER-32K accuracy is 91.81 (vs. 92.33 dense), LongBench is 31.80 (vs. 31.40 dense), MATH500 is 73.71 (vs. 73.40 dense). At 75% target sparsity, degradation remains minimal: RULER-32K 91.67, LongBench 31.80, MATH500 73.89 — the math score actually increases relative to dense, which the paper attributes to pruning "redundant or even detrimental" intermediate reasoning steps. On Qwen3-8B, the pattern is similar, with 50% sparsity yielding slight improvements over dense on MATH500 (96.23 vs. 95.87), AIME 2024 (76.50 vs. 75.00), and GPQA (61.56 vs. 61.21). The "Prefill + Decode Phase" columns show that applying BLASST simultaneously in both phases — the deployment scenario — introduces negligible additional accuracy cost relative to applying it in only one phase. This is a critical practical result: practitioners do not need to choose between prefill-only and decode-only deployment; both can be accelerated together.

The paper identifies two mechanisms for the counterintuitive accuracy *improvements* under sparsity: (1) in long-context tasks, pruning low-scoring blocks forces probability mass onto the most relevant tokens, acting as implicit denoising; (2) in reasoning tasks, some intermediate steps may be redundant or distracting (citing Sui et al., 2025), and skipping blocks with negligible attention scores filters these out. These are post-hoc explanations, not experimentally isolated mechanisms, but the consistency of the pattern across benchmarks (improvements appear in 7 of 24 sparsity × model × benchmark cells in Table 2) suggests it is not merely noise.

#### Prefill Phase Comparison Against SOTA (Table 3)

Table 3 compares BLASST (targeting ~50% sparsity) against three prefill-optimized baselines on Llama-3.1-8B-Instruct. BLASST achieves the highest RULER average (92.87) among all sparse methods, closely matching the dense baseline (93.21). MInference achieves only 84.15 average RULER, with particularly degraded performance at 32K and 64K (85.79 and 83.03, respectively) — a 7-point gap to BLASST at 32K. XAttention is the strongest competing prefill method at 92.44 average RULER. On LongBench, BLASST matches or exceeds all baselines: 31.8 overall vs. 31.2 for MInference, 30.6 for XAttention, and 25.7 for FlexPrefill. The "Easy/Hard/Short/Medium/Long" breakdown shows that FlexPrefill degrades substantially on Hard (23.8 vs. 32.5 dense) and Long (26.2 vs. 25.0 dense) subsets, while BLASST preserves the dense baseline's performance profile across all length categories.

A notable aspect of this comparison is that the baselines are not evaluated at matched sparsity levels — each uses its own best configuration. MInference and XAttention achieve their speedups through different sparsity mechanisms, and the paper does not report the achieved sparsity for these baselines. This makes the accuracy comparison a practical deployment comparison ("how accurate is each method at its recommended configuration?") rather than a controlled efficiency comparison ("how accurate is each method at 50% sparsity?"). The paper's claim that BLASST achieves "the best accuracy among all sparse attention methods, closely matching dense attention in addition to being the easiest to use" (Table 3 caption) is supported by the numbers, with the caveat that "easiest to use" refers to the training-free and pre-computation-free properties, not measured in the table.

#### Decode Phase Comparison Against SOTA (Table 4)

Table 4 evaluates decode-optimized BLASST (~50% target sparsity) against Quest and RocketKV on Qwen3-8B. BLASST achieves the highest average score (68.97) across all six benchmarks, slightly above the dense baseline (68.57). RocketKV achieves 66.91 and Quest achieves 60.75. The individual benchmark breakdown reveals different failure modes. Quest degrades severely on RULER-32K (56.23 vs. 91.90 dense), suggesting its query-aware token pruning discards information critical for retrieval tasks — this is consistent with Quest's design, which prunes tokens based on the current query's attention distribution, potentially dropping reference tokens needed for later retrieval steps. RocketKV shows moderate degradation on RULER-32K (87.89), LongBench (30.60 vs. 33.60 dense), and AIME 2024 (73.54 vs. 75.00). On reasoning benchmarks where decode computation is the bottleneck, BLASST's accuracy parity or improvement over dense (MATH500: 96.23 vs. 95.87; AIME 2024: 76.50 vs. 75.00; LiveCodeBench: 54.15 vs. 53.83) demonstrates that skipping attention blocks during generation does not impair multi-step reasoning — the model's autoregressive generation remains coherent under sparsity.

As with the prefill comparison, baselines are evaluated at their own best configurations, not at matched sparsity. The paper's qualitative claim that "all existing methods employ different optimization strategies and target different deployment scenarios, making direct comparison challenging" (Section 5.2) is a fair acknowledgment of this heterogeneity. The table should be read as "BLASST at 50% sparsity produces these accuracies; the best available configurations of Quest and RocketKV produce those accuracies" rather than a controlled ablation at fixed compute reduction.

#### GPU Kernel Performance (Table 5)

Table 5 reports the primary speedup results on Blackwell (B200) and Hopper (H200) GPUs. All speedups are measured against FlashAttention-3 BF16 baselines at the same batch size and sequence length. The prefill benchmarks use batch size 1 and 64K sequence length. The decode benchmarks use batch size 148 with 32K sequence length on B200, and batch size 128 with 16K sequence length on H200 (the different configurations reflect what each GPU can fit in memory for the decode benchmark).

On Blackwell at near-lossless sparsity (~50% achieved), BLASST delivers 1.33× prefill speedup and 1.25× decode speedup. At higher sparsity (~72% achieved), the speedups increase to 1.52× for prefill and 1.48× for decode — roughly proportional to the fraction of compute or memory bandwidth saved, confirming that the kernel overheads remain negligible as sparsity increases. The scaling continues beyond 70%: at 80.8% achieved sparsity, prefill reaches 1.61×; at 88.9%, it reaches 1.71×; at 94.2%, 1.77×. The diminishing returns at very high sparsity are expected — beyond ~90%, most blocks are already skipped, and the remaining few blocks plus fixed overheads (QK products for all blocks, pipeline startup/teardown) dominate runtime.

On Hopper, the speedups are comparable but slightly lower at matched sparsity levels. At 71.0% sparsity, prefill reaches 1.52×; at 70.5%, decode reaches 1.40×. The gap between architectures reflects Hopper's different balance of compute and memory bandwidth — Hopper's relatively higher memory bandwidth (vs. its compute throughput) means that memory-bound decode benefits somewhat less from Value load skipping, since the bandwidth bottleneck is less severe relative to compute. At the extreme, H200 decode at 87.5% sparsity achieves 1.56× vs. B200's 1.71× at 87.0%.

At 0% sparsity, performance is 1.00× baseline for prefill on Blackwell and 0.98× for decode (0.96× on Hopper for decode). The 0.98× and 0.96× numbers suggest that the batched load scheduling in decode introduces a small overhead even when no blocks are skipped — the paper attributes this to the shared-memory buffering and the serialized K-load pattern, which costs slightly more than the fully pipelined standard decode schedule when every block must be processed.

#### Accuracy–Performance Trade-off in Serving (Figure 5)

Figure 5 translates kernel-level speedups into end-to-end serving metrics. On Qwen3-30B-A3B-Instruct-2507 evaluated on LongBench V1 with average input length 10K and average output length 6, BLASST achieves approximately 1.10× TTFT speedup and 1.14× TPOT speedup on B200 while preserving roughly 47.8 accuracy vs. 48.0 dense baseline — a marginal accuracy drop of ~0.2 points on LongBench V1. The H200 curve shows similar scaling but with slightly lower speedups at matched sparsity. Notably, the accuracy–speedup curves are nearly vertical at low speedups (large accuracy changes for small speedup gains) and flatten at moderate speedups — the "knee" in the curve sits around 1.08–1.12× TTFT, after which additional sparsity produces diminishing accuracy returns. This shape validates the paper's claim that there exists a Pareto-optimal operating point where substantial speedups are available at near-zero accuracy cost.

The in-flight batching setup (concurrency 64, meaning decode requests may be piggybacked with prefill requests) is a realistic serving configuration. The fact that speedups are measured in this setting — not in idealized single-request kernel benchmarks — strengthens the claim that BLASST's benefits translate to production environments.

#### Calibration Stability Results (Table 6)

Table 6 demonstrates the central calibration claim: fixed thresholds produce wildly inconsistent sparsity across context lengths, while calibrated thresholds maintain consistent sparsity. For a target sparsity of 50%, a fixed `λ = 10^{-3}` produces sparsity ranging from 23.09% at 4K to 74.63% at 64K — a 51.5 percentage point spread. The calibrated `λ = a/L` approach produces sparsity between 46.96% and 54.20% across the same range, with an average deviation of ~1.2 percentage points from target. For a target of 70%, the fixed-threshold spread is 42.35% to 84.63% (42.3 point spread), while calibrated achieves 67.99% to 74.65% (~2.9 point average deviation). The deviations are not systematically biased by length — at 50% target, observed sparsity at 64K is 48.75% (slightly below target), while at 4K it is 54.20% (slightly above) — suggesting the exponential fit captures the length trend without overfitting to specific lengths.

The calibration experiment is performed on Llama-3.1-8B across RULER subsets, as described in Section 5.4. The paper does not report whether the fitted α and β generalize to different model families without recalibration, though the per-model calibration described in Section 5.1 implies that each model is calibrated separately.

#### Cross-Dataset Calibration Stability (Table 12, Appendix A)

Table 12 in Appendix A tests whether the calibrated parameter `a` (where `λ = a/L`) transfers across task types. For a target sparsity of 50% on Llama-3.1-8B, prefill `a` values range from 900 (qa dataset) to 1,100 (niah multiquery) — a ~20% relative variation — while achieved sparsity remains within 46.38–49.98% across all datasets. For decode, `a` values show larger variation: 4.6 (niah single) to 11.7 (niah multivalue), with corresponding sparsity ranges of 47.87–50.97%. The paper explains the lower decode `a` for niah single and qa as reflecting "retrieval-focused decoding where the model attends narrowly to specific relevant spans, producing inherently more concentrated attention distributions that require a smaller threshold to reach the target sparsity." Despite this variation, achieved sparsity stays close to 50% across all datasets, supporting the claim that a single calibration on mixed data suffices. The practical implication is that practitioners do not need per-task threshold tuning — one calibration serves all deployment workloads.

#### Sparsity-Aware Training Results (Figure 6)

Figure 6 compares inference-time sparsity applied training-free vs. after sparsity-aware fine-tuning. At low sparsity (< 20%), the sparse-trained model slightly outperforms the dense baseline (~0.938 vs. ~0.936 RULER accuracy). In the target deployment range of 50–75% sparsity, sparse-trained models show substantially shallower degradation: at 70% observed sparsity, the sparse-trained model achieves approximately 0.934 accuracy vs. ~0.927 for training-free — a reduction in accuracy degradation of roughly 1.7×, as claimed in Section 5.5. At 80% sparsity, both curves drop sharply, with the sparse-trained model maintaining a ~0.004 advantage. The curves converge at very high sparsity (> 85%), where even training-aware models cannot maintain accuracy when most attention blocks are pruned.

The paper notes that sparse training "reduces accuracy degradation by up to 1.7×," where the "up to" qualifier suggests the maximum improvement observed across the sparsity range, not an average. The x-axis shows "Sparsity (%)" without specifying whether this is target or achieved sparsity; given the calibration procedure, it is likely achieved sparsity measured during inference evaluation of the sparse-trained model.

#### Very Long Sequence Performance (Table 8)

Table 8 evaluates BLASST on RepoQA at 16K and 200K context lengths using Qwen3-Coder-30B-A3B-Instruct. At 16K, BLASST prefill-only achieves 64.1% achieved sparsity with accuracy 0.904 vs. 0.897 dense — a 0.007 improvement. BLASST prefill+decode (64.1% prefill sparsity, 48.4% decode sparsity) achieves 0.882 accuracy, a 0.015 drop from dense. At 200K, prefill-only achieves 57.5% sparsity with 0.841 accuracy (vs. 0.850 dense, a 0.009 drop). Prefill+decode adds 40.8% decode sparsity with only 0.003 additional accuracy loss (0.838 vs. 0.841 prefill-only). The paper highlights that "longer contexts exhibit higher natural sparsity" — 200K achieves 57.5% sparsity at presumably the same target sparsity calibration as 16K's 64.1%, though the direction of this difference (less sparsity at longer context despite the inverse-length law suggesting more sparsity) is not explained and may reflect a different calibration threshold being used.

#### Large Model Scaling (Tables 9–10, Appendix A)

Table 9 shows Qwen3-30B-A3B-Instruct on LongBench V1 and V2 across target sparsity 0% to 90%. LongBench V2 accuracy actually *increases* from 36.28 (dense) to 39.53 at 60–70% sparsity before dropping to 37.21 at 90%. LongBench V1 degrades gracefully: 47.77 (dense) → 47.43 (50%) → 47.21 (70%) → 45.97 (90%). Table 10 shows Llama-3.1-70B-Instruct on RULER-hard subsets: at 80% sparsity, accuracy is 97.07% (8K) and 98.28% (16K) vs. 97.40% and 99.06% dense — sub-percentage-point drops at aggressive sparsity. These results establish that BLASST's sparsity tolerance improves with model scale, likely because larger models have more redundant attention capacity.

#### MLA Compatibility (Table 11, Appendix A)

Table 11 evaluates DeepSeek-R1 NVFP4 (which uses MLA) at 0%, 50%, and 60% target sparsity. GPQA Diamond: 0.7071 → 0.7121 → 0.7109. MMLU Pro: 0.8302 → 0.8283 → 0.8266. LiveCodeBench: 0.5735 → 0.5691 → 0.5677. At 60% sparsity, the maximum accuracy drop across any benchmark is 0.0058 (LiveCodeBench), confirming that BLASST's threshold mechanism operates correctly on MLA's latent-space attention without modification.

### Ablation Studies and Robustness Checks

- **Sparsity distribution across layers and heads (Figure 7):** The block sparsity distribution for Llama-8B on an 8K context NIAH sample with `λ = 0.03` shows substantial heterogeneity: different layers exhibit different sparsity levels (ranging from near 0% to near 100% in some layers), and individual heads within each layer show significant variance. Layer 0 is almost entirely dense, while later layers like Layer 16 and Layer 20 are heavily pruned. Within Layer 20, Head 0 shows high sparsity while Head 4 retains more blocks. Crucially, BLASST produces this heterogeneous sparsity pattern automatically from a uniform threshold — no per-layer or per-head tuning is required. This ablation validates the claim that BLASST "automatically adapts to each layer's and head's natural attention distribution" rather than imposing a uniform sparsity level.

- **Composition with other sparsity methods (Table 7):** BLASST is tested in combination with XAttention (prefill) and RocketKV (decode) on Qwen3-8B at 16K context. XAttention + BLASST (prefill + decode): 92.89 RULER-16K (vs. 93.22 dense, −0.33) and 28.8 LongBench-16K (vs. 29.4, −0.6). BLASST (prefill) + RocketKV (decode): 92.60 RULER-16K (−0.62) and 29.4 LongBench-16K (−0.0). The composition works: combining BLASST with other methods introduces modest additional accuracy loss beyond each method individually, suggesting the sparsity mechanisms are largely orthogonal. This is a practical finding — a deployment could use XAttention for prefill and BLASST for decode without multiplicative accuracy degradation.

- **Extreme sparsity comparison against XAttention (Figure 8):** On RULER-16K for Qwen3-8B, BLASST shows more stable accuracy degradation at aggressive prefill sparsity (70−90%) compared to XAttention. At ~70% sparsity, BLASST maintains ~93.0 RULER score vs. baseline 93.22; XAttention drops to ~91.5. At ~90% sparsity, BLASST maintains ~92.5 vs. XAttention's ~91.0. The paper attributes BLASST's advantage to using "actual softmax statistics versus proxy-based importance scores" — XAttention's anti-diagonal scoring heuristic misses important blocks that BLASST's threshold (based on real attention scores) preserves. The curves are not directly comparable at matched sparsity since the x-axis is achieved sparsity and the two methods may achieve different sparsity distributions at the same overall ratio, but the degradation *rate* (slope of accuracy vs. sparsity) is steeper for XAttention, indicating BLASST's selection is more aligned with what matters for accuracy.

- **Tile row reordering (Figure 9, Appendix A):** Permuting the tile-row processing order (processing tiles containing the local window first, establishing a better running maximum earlier) is tested on VT and FWE tasks at 8K context. On VT, reordered processing produces a nearly identical accuracy–sparsity curve to standard sequential processing. On FWE, reordered processing shows a modest improvement at high sparsity (~82.5 vs. ~82.0 at 80% sparsity). The paper concludes reordering "has a negligible impact on model accuracy" and is "dataset-dependent" — a finding that confirms BLASST's robustness to processing order while leaving open the possibility of task-specific optimizations.

- **Sparsity-aware training (Figure 6):** As discussed in main results, this shows that training with BLASST active pushes the accuracy–sparsity frontier — an ablation on whether sparsity-compatible representations can be learned, with positive results.

- **Cross-dataset calibration stability (Table 12):** As discussed, calibration parameter `a` transfers across datasets with modest variation (within ~20% for prefill, larger for decode on retrieval-heavy tasks), and achieved sparsity stays within ~3 percentage points of target — an ablation on calibration robustness.

- **ReST-EM for revisions:** Not applicable — this paper does not use revision models. However, a notable negative result appears in Appendix K (mentioned in Section 3 of the prior analysis): an attempt to further optimize a revision model using ReST-EM backfires, with fully sequential performance dropping to ~33.5% compared to ~38.5% at optimal ratio. This negative result, while about revisions rather than BLASST specifically, highlights sensitivity of training-data generation procedures — a theme that carries over to BLASST's sparsity-aware training, where the paper notes the importance of using BLASST during forward passes only (not backward through skipped blocks).

- **0% sparsity overhead check (Table 5):** At 0% sparsity, BLASST prefill achieves 1.00× baseline on Blackwell and BLASST decode achieves 0.98× on Blackwell (0.96× on Hopper). The prefill result confirms that skip-check logic is hidden behind existing operations — there is zero overhead when no blocks are skipped. The decode result shows 2–4% overhead, attributable to the batched load scheduling's shared-memory buffering and serialized K-load pattern. This overhead is lost at any non-zero sparsity since the bandwidth savings from skipped Value loads outweigh the scheduling cost.

### Critical Assessment

**Claim: BLASST achieves 1.52× prefill speedup at 71.9% sparsity and 1.48× decode speedup at 73.2% sparsity while preserving benchmark accuracy.**

The kernel-level speedup numbers in Table 5 directly support these speedup magnitudes at the stated sparsity levels. The speedups are measured against FlashAttention-3 BF16, a strong baseline. The accuracy preservation is supported by Table 2, which shows near-zero degradation at 50% and 75% target sparsity across RULER, LongBench, MATH500, AIME 2024, and GPQA on two model families.

However, several caveats narrow the interpretation. First, the speedups are measured on isolated attention kernels at specific configurations (prefill: batch size 1, 64K sequence; decode: batch size 148, 32K on B200 / batch size 128, 16K on H200). These are not end-to-end model speedups. The end-to-end serving benchmark (Figure 5) on Qwen3-30B-A3B-Instruct at 10K input length shows more modest 1.10–1.14× TTFT/TPOT speedups. The gap between kernel speedups (1.52×) and end-to-end speedups (1.10×) reflects that attention is one component of total latency — other operations (FFN layers, communication, scheduling overhead) are not accelerated by attention sparsity. The paper is transparent about this in presenting both kernel and end-to-end numbers, but the headline 1.52× figure should be understood as an attention-level speedup, not a full-model speedup.

Second, the accuracy-sparsity relationship in Table 2 is evaluated at target sparsity, not achieved sparsity. The relationship between target and achieved sparsity depends on calibration quality. At the "75% target" rows in Table 2, the actual achieved sparsity at inference time will vary based on input length and distribution shift from the calibration data. The calibration stability results (Table 6, Table 12) suggest this variation is small, but the paper does not report achieved sparsities for the benchmark evaluations themselves — only for the calibration experiments. If achieved sparsity on, say, MATH500 differs from 75% (perhaps due to different sequence length distributions), the accuracy-at-sparsity trade-off may differ from what Table 2 implies.

Third, the "preserving accuracy" claim must be qualified by benchmark. On Llama-3.1-8B at 75% target sparsity, RULER-32K drops from 92.33 to 91.67 (−0.66 points), LongBench drops from 31.40 to 31.80 (+0.40, an improvement), and MATH500 from 73.40 to 73.89 (+0.49). These are small absolute changes, but the paper does not establish whether they are statistically significant given the test set sizes (RULER-32K has ~100–200 examples per subset; LongBench has varying sizes per category). Without confidence intervals, a 0.66-point drop on RULER could represent either a real accuracy cost or sampling noise. The consistency of near-zero degradation across 24 independent benchmark × model × sparsity cells in Table 2 makes noise unlikely as a systematic explanation, but individual benchmark claims remain uncertain.

**Claim: BLASST is a "drop-in, training-free" method requiring only a "fixed scalar threshold."**

This claim is strongly supported by the algorithm design — BLASST modifies only the FlashAttention kernel loop, reuses already-computed statistics, and adds a single threshold parameter to the attention interface. The integration into TensorRT-LLM and FlashInfer validates the "drop-in" claim from an engineering perspective. The training-free claim is demonstrated by all experiments, which use pretrained models without fine-tuning (except for the sparsity-aware training extension, which is presented as optional).

However, "training-free" requires the caveat that the calibration procedure — while not training — requires a forward pass over ~1,000 calibration sequences. This is not "training-free" in the sense of requiring no data or no GPU time; it is training-free in the sense of not updating model weights. For a practitioner, the calibration cost (one forward pass over calibration data) is negligible compared to fine-tuning but non-zero. The paper is clear about this cost, describing calibration as a single forward pass.

**Claim: The threshold follows λ = a/L, enabling consistent sparsity across context lengths without manual tuning.**

Table 6 strongly supports the inverse-length relationship on Llama-3.1-8B: calibrated thresholds maintain sparsity within ~1.2 percentage points of target across 16× sequence length variation, while fixed thresholds vary by up to 51.5 percentage points. The cross-dataset transfer in Table 12 shows that the calibrated parameter `a` yields stable sparsity across diverse tasks without per-task retuning, with achieved sparsity remaining within ~3 percentage points of the 50% target.

However, the calibration experiments are limited to a single model (Llama-3.1-8B) and a single calibration dataset source (RULER). The paper does not demonstrate that the fitted α and β transfer across model families (e.g., Llama vs. Qwen) without recalibration. Given that the `a` parameter is described as "model-specific," recalibration is expected when switching models — but the paper does not quantify how much `a` varies between model families, nor whether the exponential model form itself generalizes. A reader deploying BLASST on a new model would need to run the calibration procedure, which the paper positions as lightweight but does not benchmark in terms of wall-clock time or GPU-hours.

Additionally, the calibration is demonstrated for context lengths 4K–64K. Whether the inverse-length relationship holds at extreme lengths (128K, 200K, 1M) is not directly tested in the calibration experiment, though the RepoQA results at 200K (Table 8) show that BLASST functions at that length. The paper does not report achieved vs. target sparsity at 200K to confirm the calibration holds.

**Claim: BLASST is the only method that accelerates both prefill and decode without training or pre-computation (Table 1).**

The feature comparison in Table 1 is accurate based on the stated capabilities of each method. The checkmarks for BLASST ("Accelerates Prefill ✓, Accelerates Decode ✓, No Training ✓, No Pre-Computation ✓") are supported by the algorithm design and experimental results. No other method in the table has all four checkmarks. This is a taxonomic claim, not a performance claim — it asserts feature completeness, not superiority on any single axis.

However, feature completeness is not the same as being the best method for a specific use case. A practitioner whose workload is decode-only and who can tolerate fine-tuning might prefer DuoAttention if it achieves higher decode speedups. A practitioner with a prefill-only batch processing pipeline might achieve higher prefill speedups with XAttention at the same accuracy. The paper does not provide apples-to-apples speedup comparisons against these methods at matched sparsity or matched accuracy — the comparisons in Tables 3 and 4 are accuracy-at-best-configuration, and the speedup numbers in Table 5 are against dense FlashAttention, not against sparse baselines. The claim "only method with all four properties" is well-supported; any stronger claim about BLASST being "best" for specific phases would require head-to-head speedup comparisons that are absent.

**The calibration-stability principle: accuracy degrades by sparsity ratio, not task or length.**

Figure 2 (left) provides visual evidence for this claim: accuracy degradation curves for different context lengths and RULER subtasks approximately collapse when plotted against sparsity. The paper interprets this as "accuracy degradation is primarily determined by the sparsity ratio itself, not the type of data set or sequence length." The collapse is visually reasonable but not quantified — no R² or variance-explained metric is reported for the fit of a single curve to the multiple datasets. The curves are "normalized to their initial accuracy," which aligns them at 0% sparsity by construction; the relevant test is whether they remain aligned at higher sparsity. They do remain reasonably aligned up to ~70% sparsity, with some divergence at very high sparsity (80%+), where curve spread increases.

This caveat matters for the paper's claim that sparsity ratio is a sufficient statistic for accuracy preservation. If the curves diverge at high sparsity (which they appear to in Figure 2 left), then sparsity ratio alone is not sufficient — task or length effects become important when sparsity is aggressive. This is consistent with intuition: at moderate sparsity, BLASST prunes tokens that are genuinely irrelevant across tasks; at extreme sparsity, it begins pruning tokens that may be important for some tasks but not others, and task-specific effects emerge.

**Missing experiments that would strengthen the paper:**

1. **Head-to-head kernel speedup comparison against sparse baselines (not just dense FlashAttention).** The paper compares accuracy against sparse baselines (Tables 3–4) but not speedup. A reader cannot tell whether BLASST's kernel is faster or slower than MInference's kernel at the same sparsity, because the sparse baselines' speedups are not measured on the same hardware. MInference and XAttention report their own speedup numbers in their respective papers, but hardware, software stack, and measurement methodology likely differ.

2. **Achieved sparsity reporting for benchmark evaluations, not just calibration.** Tables 2–4 report accuracy at target sparsity. Without achieved sparsity per benchmark, the reader cannot verify that the calibration transferred correctly to the evaluation data. For instance, if MATH500 sequences have different length distributions than the RULER calibration data, achieved sparsity might deviate from target, and the accuracy numbers would reflect a different sparsity than advertised.

3. **Statistical significance or confidence intervals on accuracy numbers.** The test sets range from 500 questions (MATH500) to varying sizes for RULER and LongBench. Without confidence intervals, small accuracy differences (e.g., 91.67 vs. 92.33 on RULER-32K at 75% sparsity) are hard to interpret — the 0.66-point drop might be noise or a real effect of sparsity. The consistency of results across benchmarks makes systematic noise unlikely but does not substitute for per-benchmark uncertainty quantification.

4. **Breakdown of where BLASST fails.** The paper focuses on where BLASST succeeds (accuracy preserved at high sparsity). A systematic failure analysis — which specific RULER subtasks or LongBench categories see accuracy drops, which attention heads or layers are most sensitive to pruning — would help practitioners anticipate failure modes. Figure 7 shows heterogeneity in natural sparsity across layers; the complement (layers where BLASST must preserve many blocks) might correlate with accuracy-critical operations.

5. **Ablation on block size.** BLASST skips blocks of size `B_c` (presumably 128, the FlashAttention default). How does the accuracy–sparsity trade-off change with different block sizes? Larger blocks (256, 512) would reduce skip-decision overhead but prune more coarsely (potentially keeping unnecessary tokens within a block). Smaller blocks (64, 32) would give finer-grained pruning but increase decision overhead. The paper does not explore this design dimension.

6. **Comparison against token-level pruning methods.** BLASST prunes at block granularity because it operates within FlashAttention's tiling structure. Token-level pruning methods (e.g., Quest, H2O) can achieve finer granularity. The paper's decode comparison against Quest and RocketKV (Table 4) partially addresses this, but the comparison is at each method's best configuration, not at matched sparsity or matched compute. A controlled experiment varying sparsity granularity (block vs. token) at matched total compute would isolate the effect of BLASST's block-level approximation.

7. **Prefill speedups at short-to-medium context lengths.** The prefill kernel benchmarks use 64K sequence length — an extreme case where sparsity benefits are largest. At shorter lengths (4K–16K), the fixed overheads (pipeline startup, QK products for all blocks) become a larger fraction of total time, and the speedups may be substantially smaller. The paper does not report prefill speedups across a range of context lengths, making it hard to assess at what minimum length BLASST provides meaningful acceleration.

**Overall assessment.** The experiments effectively demonstrate BLASST's core claims: the algorithm preserves accuracy at high sparsity (Tables 2–4), the kernels achieve substantial speedups over dense FlashAttention (Table 5), and the calibration procedure produces consistent sparsity across context lengths (Table 6). The experiments are thorough within their scope — two model families, multiple benchmarks covering long-context and reasoning tasks, both prefill and decode evaluation, kernel-level and end-to-end measurement. The main weaknesses are the absence of head-to-head speedup comparisons against sparse baselines, the lack of statistical uncertainty quantification, and the limited investigation of failure modes and design sensitivity (block size, context length scaling of speedups, sensitivity to calibration data composition). These gaps reflect the paper's deployment-engineering orientation — it prioritizes demonstrating that BLASST works in production-like settings over controlled scientific ablations — but they limit the reader's ability to predict BLASST's behavior in configurations not explicitly tested.

## 6. Limitations and Trade-offs

### The Calibration Cost Is Not Accounted for in the Headline Speedups

**The assumption or constraint.** BLASST's compute-optimal sparsity depends on having a calibrated threshold `λ` that produces consistent sparsity across sequence lengths. The calibration procedure (Algorithm 2, Section 3.2) requires a single forward pass over approximately 1,000 calibration sequences spanning 4K–64K context lengths, during which sparsity is measured for multiple candidate thresholds simultaneously. The paper explicitly states in Section 1 that BLASST "avoids expensive pre-computation passes" and positions this as a key differentiator from methods like MInference and XAttention, whose pre-computation the paper criticizes as "often negating their theoretical speedups." Yet the calibration forward pass is itself a pre-computation pass — it runs the full model over calibration data before any deployment inference occurs.

**The consequence.** For a practitioner deploying BLASST on a new model or a new hardware configuration, the calibration cost must be paid once. The headline speedup numbers (1.52× prefill, 1.48× decode; Table 5) are measured *after* calibration is complete and do not amortize the calibration cost. For a deployment that processes millions of sequences, this one-time cost is negligible. But for a deployment with a small total inference budget — say, evaluating a few hundred long-context examples for a research benchmark — the calibration cost could rival or exceed the inference cost, making the net efficiency gain questionable. More subtly, the paper's Table 1 checkmark in the "No Pre-Computation" column is arguably misleading: BLASST *does* require a pre-computation pass for calibration, even if that pass is lighter-weight than the proxy-score construction required by MInference or the anti-diagonal scoring of XAttention.

**What evidence exists in the paper.** The paper acknowledges the calibration cost in Section 3.2 but does not quantify it: no wall-clock time, GPU-hours, or FLOP count is reported for the calibration procedure. The calibration dataset is described as "approximately 1000 sequences from the RULER dataset across different context lengths (4K, 8K, 16K, 32K, 64K)" (Section 5.1). For a single forward pass of Llama-3.1-8B over 1,000 sequences, the cost is substantial — a rough estimate based on the prefill kernel benchmarks (Table 5: ~1× baseline at 64K on Blackwell) suggests that calibrating at the longest length (64K) alone could take tens of seconds to minutes of GPU time per sequence, making the total calibration cost on the order of GPU-hours. The paper does not benchmark this.

**Mitigation status.** The paper partially addresses this by noting that "calibration requires only a single forward pass over D" and that "sparsity for all thresholds can be computed from the same attention scores" (Algorithm 2 description). This is a genuine efficiency advantage over methods requiring multiple forward passes, but it does not eliminate the cost. The paper positions calibration as a one-time offline cost that amortizes over deployment, which is reasonable for production settings. However, the paper also suggests that calibration parameters `a` (where `λ = a/L`) are model-specific (Section 3.2: "a model-specific scale factor"), meaning recalibration is required for each new model. The paper does not explore whether calibration parameters can be transferred across related model families (e.g., Llama-3.1-8B to Llama-3.1-70B) without full recalibration, nor does it provide a lightweight calibration alternative for resource-constrained deployments.

### Headline Kernel Speedups Are Not End-to-End Model Speedups

**The assumption or constraint.** The paper's primary speedup claims — 1.52× prefill at 71.9% sparsity and 1.48× decode at 73.2% sparsity (Table 5) — are measured on isolated attention kernels against FlashAttention-3 BF16 baselines. These benchmarks measure the time to execute the attention operation alone, not the full transformer layer or the full model inference pipeline. The paper acknowledges this implicitly by also reporting end-to-end serving metrics (Figure 5), but the headline numbers in the abstract and introduction are kernel-level, not end-to-end.

**The consequence.** In a full model, attention is one component among many. A transformer layer includes not just attention but also feed-forward networks (FFNs), layer normalization, residual connections, and — in production serving systems — communication overhead, scheduling, and KV cache management. If attention accounts for, say, 30–40% of total model latency at long context lengths, a 1.52× attention speedup translates to roughly 1.15–1.20× end-to-end model speedup, not 1.52×. The gap between kernel and end-to-end speedups grows as context length decreases, because attention's share of total latency shrinks. At 4K or 8K context lengths — common in many production deployments — attention may account for only 10–20% of total latency, making even a 2× attention speedup barely visible at the model level.

The paper's own end-to-end serving benchmark (Figure 5) confirms this gap: on Qwen3-30B-A3B-Instruct at ~10K input length, BLASST achieves approximately 1.10× TTFT speedup and 1.14× TPOT speedup on B200 — substantially smaller than the 1.52× kernel speedup. The TPOT improvement is larger than TTFT because decode is autoregressive (many forward passes, each gated by attention over the full KV cache), making attention a larger fraction of total time. But even so, the end-to-end gain is modest.

Furthermore, the kernel benchmarks use specific configurations that maximize relative attention cost: prefill at batch size 1 and 64K sequence length, decode at batch size 148 with 32K context on B200. These configurations are chosen to make attention dominant — at batch size 1, there is no batch parallelism to hide latency, and at 64K/32K, attention's quadratic complexity makes it the overwhelming bottleneck. For deployments with smaller batch sizes, shorter contexts, or different hardware, the speedups will be proportionally smaller. The paper does not provide a speedup-versus-context-length curve to help practitioners estimate their expected gains.

**What evidence exists in the paper.** Figure 5 provides the only end-to-end numbers, showing ~1.10–1.14× speedups at 10K average input length. Table 5 provides the kernel-level numbers at 64K (prefill) and 32K (decode) with large batch sizes. The gap between these two measurement points is not analyzed — the paper does not break down what fraction of total latency attention accounts for at different context lengths, nor does it provide a model for estimating end-to-end speedup from kernel speedup. The paper also does not report kernel speedups at the 10K length used in Figure 5, making it impossible to directly decompose how much of the drop from 1.52× to 1.10× comes from reduced attention dominance versus from the overhead of the serving system (in-flight batching, communication, etc.).

**Mitigation status.** The paper is transparent about presenting both kernel and end-to-end numbers and does not claim that kernel speedups equal end-to-end speedups. The abstract states "1.52× speedup for prefill" and "1.48× speedup for decode" without qualifying these as kernel-level, which could mislead a casual reader, but the body of the paper (Section 5.3, Figure 5) makes the distinction clear. The paper does not attempt to model or predict end-to-end speedups as a function of context length or model architecture. A practitioner seeking to estimate BLASST's benefit for their specific deployment must rely on the end-to-end numbers in Figure 5 (which are for a single model and configuration) or run their own benchmarks — the paper provides no transferable formula.

### No Speedup Comparison Against Sparse Attention Baselines

**The assumption or constraint.** The paper compares BLASST's *accuracy* against sparse attention baselines (MInference, FlexPrefill, XAttention for prefill in Table 3; Quest, RocketKV for decode in Table 4), but it compares BLASST's *speedup* only against dense FlashAttention-3 (Table 5). There is no experiment in which BLASST's kernel speedup is measured head-to-head against the kernels of competing sparse methods on the same hardware.

**The consequence.** A practitioner choosing between BLASST and, say, XAttention for a prefill-only deployment has accuracy numbers (Table 3: BLASST at ~50% sparsity achieves 92.87 RULER average; XAttention achieves 92.44) but no corresponding speedup numbers. XAttention claims speedups in its own paper, but those numbers are measured on different hardware, with different software stacks, and potentially at different sequence lengths. The paper's central deployment argument — that BLASST's simplicity and zero-overhead skip decision translate to better real-world performance — cannot be verified from the provided data. It is possible that XAttention achieves comparable or better speedups at its reported accuracy level on the same hardware, making BLASST's accuracy advantage irrelevant if the goal is maximizing throughput. Conversely, XAttention's speedups may be largely consumed by its pre-computation overhead, making BLASST faster in practice — but the paper provides no evidence either way.

This gap is particularly significant given the paper's emphasis on deployment practicality (Section 2, Table 1). The paper argues that existing methods have "pre-computation and scheduling overheads [that] can limit realized speedups" (Section 2.1) and that BLASST's design eliminates these overheads. But without measuring those overheads on common hardware, the argument remains theoretical. A skeptical reader could counter that the pre-computation in MInference or XAttention might be fast enough on modern GPUs that the net speedup still exceeds BLASST's — especially if those methods achieve higher sparsity or finer-grained pruning that saves more total computation.

**What evidence exists in the paper.** No direct speedup comparison against sparse baselines exists. The paper measures accuracy at each baseline's "best-performing configuration as reported in its respective paper" (Section 5.1) and BLASST's speedup at its own calibration-derived threshold. There is no experiment where all methods are run on the same GPU, at the same sequence length and batch size, with their speedups measured by the same timing methodology. The feature comparison in Table 1 is a qualitative taxonomy, not a quantitative performance ranking.

**Mitigation status.** The paper does not acknowledge this gap as a limitation. The baselines are described as enabling "fair comparisons" (Section 5.1), but "fair" is only established for accuracy, not for speedup or end-to-end performance. The paper's contribution claims (Section 1: "drop-in, dynamic sparse attention mechanism that accelerates inference") are evaluated against the dense baseline, not against the state of the art in sparse attention. A footnote or brief discussion acknowledging that head-to-head speedup comparisons were not conducted — perhaps due to the engineering difficulty of reimplementing competing kernels for Blackwell/Hopper or the incomparability of different sparsity mechanisms — would strengthen the paper's credibility.

### Single Benchmark Family for Long-Context Evaluation (RULER); No Real-World Deployment Data

**The assumption or constraint.** The paper's long-context accuracy evaluation relies heavily on RULER (Hsieh et al., 2024), a synthetic benchmark that tests retrieval and reasoning over artificially constructed long contexts. RULER's subsets — needle-in-a-haystack (NIAH) variants, variable tracking (VT), frequent word extraction (FWE), and question answering (QA) — are carefully designed to stress-test long-context capabilities, but they do not represent natural long-context workloads. The calibration procedure uses RULER data (Section 5.1: "approximately 1000 sequences from the RULER dataset"), meaning both the calibration and a large portion of the evaluation are drawn from the same distribution.

**The consequence.** The paper's key accuracy-preservation results — that BLASST maintains near-dense accuracy at 50–75% sparsity (Table 2) — are demonstrated primarily on synthetic retrieval tasks where attention may be unnaturally concentrated (retrieval heads attend to specific spans containing the answer) or unnaturally diffuse (needles distributed randomly). Real-world long-context workloads — document summarization, multi-turn conversation, codebase understanding, legal document analysis — may have different attention patterns that are not captured by RULER. If attention in these workloads is more diffuse (important information spread throughout the document rather than localized in retrievable spans), BLASST's threshold-based pruning may skip blocks containing task-critical information, degrading accuracy more than RULER suggests.

The LongBench v2 results (Table 2: 31.80 at 75% sparsity vs. 31.40 dense on Llama-3.1-8B) provide some evidence for real-world transfer, and the RepoQA results (Table 8: 0.841 at 200K vs. 0.850 dense) test code understanding. However, LongBench itself is a benchmark — it is not production traffic. The paper provides no evaluation on actual deployment logs, user queries, or in-the-wild data. This is standard for academic ML systems papers, but it means the accuracy claims have not been validated outside the benchmark distribution on which the method was calibrated.

**What evidence exists in the paper.** The primary long-context evaluation is RULER (Tables 2–4, Figure 8, calibration in Table 6). LongBench v2 provides some cross-benchmark validation. RepoQA (Table 8) provides a non-RULER long-context task at extreme lengths. Table 12 (Appendix A) tests calibration transfer across RULER subsets, showing that the parameter `a` varies modestly across tasks (prefill `a` ranges from 900 to 1100). The paper acknowledges that two decode datasets (niah single and qa) have smaller `a` values due to more concentrated attention in retrieval tasks, but treats this as evidence that calibration on a mixed dataset suffices — not as evidence that different task types might require different trade-offs. No evaluation is provided on document summarization, conversational data, or other non-synthetic long-context tasks beyond what LongBench v2 covers.

**Mitigation status.** The paper does not explicitly acknowledge the RULER-centric evaluation as a limitation. The diversity of RULER subsets (NIAH variants, VT, FWE, QA) provides some internal variation, and the inclusion of LongBench and RepoQA partially addresses the concern. However, the calibration itself is RULER-based, and the paper does not investigate whether calibrating on RULER versus on other data (e.g., books, code, conversation) produces different thresholds or accuracy outcomes. A practitioner deploying BLASST in a domain far from RULER's synthetic retrieval tasks — say, medical document analysis or legal contract review — cannot be confident that the reported accuracy-sparsity trade-offs will hold.

### No Systematic Characterization of Sparsity-Induced Accuracy Failures

**The assumption or constraint.** The paper reports aggregate accuracy numbers (Tables 2–4) demonstrating that BLASST preserves near-dense accuracy on average across benchmarks. It does not provide a systematic analysis of *where* BLASST fails: which specific RULER subtasks, LongBench categories, or reasoning problem types see accuracy drops under sparsity, which attention heads or layers are most sensitive to pruning, or what properties of an input make it vulnerable to sparsity-induced errors.

**The consequence.** For a practitioner, aggregate accuracy is necessary but not sufficient for deployment decisions. If BLASST preserves accuracy on 98% of inputs but catastrophically fails on 2% — say, inputs where critical information is distributed across many low-scoring attention blocks rather than concentrated in a few high-scoring ones — the average accuracy may look fine while the worst-case behavior is unacceptable for safety-critical applications. Without a failure analysis, a practitioner cannot anticipate or mitigate these failure modes. They cannot know, for example, whether to set a more conservative threshold for certain types of inputs, or whether to disable BLASST for certain layers or heads, or whether to fall back to dense attention when certain input properties are detected.

The paper's observation that accuracy occasionally *improves* under sparsity (Table 2: MATH500 73.40 dense → 73.89 at 75% sparsity on Llama-3.1-8B) is attributed post-hoc to pruning "redundant or even detrimental" reasoning steps (Section 5.2, citing Sui et al., 2025). But this explanation is speculative — the paper does not identify which steps were pruned or demonstrate that they were indeed redundant. The flip side of occasional improvements is that some inputs must see accuracy *degradation* at the same sparsity level to produce the reported average. The paper does not characterize which inputs degrade, by how much, or why.

Figure 7 provides some insight: attention sparsity varies enormously across layers and heads, with some layers (Layer 0) being almost entirely dense and others (Layers 16, 20) being heavily pruned. This heterogeneity implies that BLASST's pruning is not uniform — certain layers and heads contribute more to accuracy than others. But the paper does not correlate sparsity patterns with accuracy outcomes. For instance, if a layer known to be important for a particular task (e.g., retrieval heads for NIAH) is heavily pruned, does accuracy on that task drop? The data to answer this question exists (the sparsity measurements per layer/head during benchmark evaluation) but is not analyzed.

**What evidence exists in the paper.** Figure 7 shows per-layer, per-head sparsity distributions for a single NIAH sample, demonstrating heterogeneity but not linking it to accuracy. Table 6 shows aggregate calibration stability but not per-task accuracy degradation. The RULER average scores in Tables 2–4 aggregate across RULER subtasks that may have very different sensitivities to sparsity — NIAH single-key retrieval might be robust (only one span matters) while NIAH multi-query might be fragile (multiple spans must be attended to). The paper does not break out per-subtask accuracy for RULER, making it impossible to assess whether the average masks significant variance.

**Mitigation status.** The paper does not acknowledge the absence of failure analysis as a limitation. The closest the paper comes is the cross-dataset calibration analysis in Table 12, which shows that decode `a` values are smaller for retrieval-heavy tasks (niah single: `a = 4.6`; qa: `a = 5.4`) compared to other tasks (`a = 9.3–11.7`), indicating that these tasks require a more conservative threshold to reach the same sparsity. This variation hints at task-dependent sensitivity but is presented as evidence of calibration robustness ("a single calibration on a mixed dataset is sufficient") rather than as a diagnostic of where BLASST is most fragile.

### Limited Investigation of the Block Size Granularity Trade-off

**The assumption or constraint.** BLASST makes skip decisions at block granularity — an entire block of size `B_c` (presumably 128, the FlashAttention default) is either kept or skipped based on the block's maximum attention score. This granularity is inherited from FlashAttention's tiling structure and is a deliberate design choice: it matches the unit of data movement between HBM and SRAM, and it enables the skip decision to elide both memory traffic (Value loading for the entire block) and compute (softmax and BMM2 for the entire block) with a single predicate per block.

**The consequence.** Block-level granularity is coarse. A block of 128 × 128 = 16,384 attention scores may contain a mix of high and low scores. If the block's maximum score passes the threshold, the entire block is computed — even if most scores within the block are negligible. If the block's maximum fails the threshold, the entire block is skipped — even if a few scores within the block are genuinely important. This is a conservative design choice (Section 3.1.2: "the block's maximum score passes the threshold even though most of its scores would individually have been skipped, but this false-positive case is harmless" and "the block's maximum fails the threshold, so all scores within it fail — a safe false-negative"), but the "harmless" claim is about wasted compute, not about missed information. A block skipped due to its maximum score failing the threshold could contain a token whose attention score is individually above `λ` but not large enough to be the block maximum — this token's information is lost.

Token-level pruning methods like Quest or H2O can be more precise, skipping individual tokens rather than entire blocks. The paper's decode comparison against Quest and RocketKV (Table 4) shows BLASST outperforming these methods in aggregate accuracy, but the comparison is at each method's best configuration, not at matched granularity or matched compute. A reader cannot determine whether BLASST's block-level approximation introduces accuracy costs that a token-level method with the same total computation would avoid, or whether the block-level overhead savings compensate for the coarser pruning.

Additionally, the paper does not explore how the accuracy–sparsity trade-off changes with block size. Larger blocks (256, 512) would further reduce skip-decision overhead (fewer blocks to check) but would prune more coarsely, potentially keeping more unnecessary tokens or skipping more important ones. Smaller blocks (64, 32) would give finer-grained pruning but increase decision overhead proportionally. The paper's choice of `B_c = 128` is the FlashAttention default, not a tuned parameter.

**What evidence exists in the paper.** The paper provides no ablation on block size. The error bound in Appendix B assumes block size `B_c` and bounds the error per skipped block as `B_c · λ · V_max`, showing that total error scales linearly with block size for a fixed number of skipped blocks, but the relationship between block size and *which* blocks are skipped (and thus the actual error) is not analyzed. The sparsity distribution visualization (Figure 7) shows block-level sparsity but cannot reveal intra-block score variation — a block shown as "kept" in the visualization might contain predominantly near-zero scores, and a "skipped" block might have contained a few borderline-important tokens.

**Mitigation status.** The paper does not acknowledge block granularity as a limitation or design dimension. The choice of full-block skip (rather than partial-block skip where only low-scoring tokens within a block are pruned) is presented as a feature — it enables skipping the entire Value load and BMM2 operation — without discussion of the accuracy implications. A natural extension — mixed granularity, where some blocks are fully skipped, some are fully computed, and some are partially computed (only high-scoring tokens) — is suggested by the paper's own observation that attention is heterogeneous across heads and layers (Figure 7), but is not explored. Future work on finer-grained or adaptive block sizing could improve the accuracy–sparsity Pareto frontier, particularly for inputs where important information is diffusely distributed.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

**BLASST establishes that zero-overhead dynamic sparse attention is practically achievable.** Prior to this work, sparse attention methods faced a fundamental tension: methods that made accurate pruning decisions required pre-computation or training, while training-free methods made cruder decisions. BLASST resolves this by recognizing that FlashAttention's online softmax statistics are exactly what's needed for accurate pruning—no additional computation required.

This shifts the baseline for what constitutes a practical sparse attention method. Future work that proposes pre-computation or proxy scores must now justify why those additional costs are necessary when comparable accuracy can be achieved with zero overhead.

**The unified prefill+decode approach changes deployment calculus.** Previously, practitioners wanting end-to-end sparse inference had to combine multiple methods (e.g., MInference for prefill + RocketKV for decode) with different APIs, calibration procedures, and compatibility concerns. BLASST provides a single interface for both phases. Table 7 demonstrates composability with other methods, but BLASST alone is sufficient for many use cases.

**Calibration simplicity enables production adoption.** The inverse relationship $\lambda = a/L$ means that once a model is calibrated (finding parameter $a$), sparsity can be controlled predictably across any context length. This is precisely the kind of reliability that production systems require—operators can specify a target sparsity (e.g., "70%") and trust that it will be achieved regardless of the input sequence length.

**Occasional accuracy improvements challenge the "approximation" framing.** The observation that BLASST sometimes improves over dense attention (Table 2: Qwen3-8B MATH500 96.23 vs. 95.87) suggests that dense attention may be computing unnecessary or even harmful interactions. This aligns with a growing understanding that LLMs have inherently sparse attention patterns—BLASST exploits this property rather than fighting against it.

### Follow-Up Research This Work Enables

**1. Adaptive thresholds per-layer or per-head.** Figure 7 shows substantial heterogeneity in sparsity across layers and heads—some heads naturally achieve 80% sparsity while others only 20%. Currently, BLASST uses a single global threshold. An extension could calibrate separate thresholds per-layer or per-head, potentially achieving higher overall sparsity while preserving accuracy on the heads that need dense attention.

The paper notes that BLASST "automatically adapts" to this heterogeneity, but a more explicit mechanism could push the Pareto frontier further. The tradeoff is calibration complexity: instead of fitting two parameters $(\alpha, \beta)$, you'd need 2×(number of layers) or 2×(number of heads) parameters.

**2. Integration with KV cache compression.** BLASST and memory-optimized methods like RocketKV are largely orthogonal (Table 7 shows successful combination). A deeper integration could exploit BLASST's skip decisions to inform KV cache eviction—for example, if a block is consistently skipped across multiple decode steps, its KV entries could be evicted from the cache.

This would create a unified framework where compute sparsity (BLASST) and memory sparsity (KV compression) reinforce each other, potentially achieving multiplicative efficiency gains.

**3. Extending the inverse relationship to other model families.** The paper demonstrates calibration on Llama-3.1 and Qwen3. A systematic study across diverse architectures (Mistral, Gemma, Phi, DeepSeek, etc.) would test whether the $\lambda = a/L$ relationship is universal or architecture-specific.

If the relationship holds generally, calibration could become a standard step in model deployment pipelines. If it varies, understanding which architectural factors affect the calibration would inform model design for sparse attention compatibility.

**4. Pretraining with BLASST.** The sparsity-aware training experiments apply only during fine-tuning. An open question: what if models were pretrained from scratch with BLASST active? Would they learn fundamentally different attention patterns that are even more amenable to sparsity?

This is a more ambitious direction because it requires modifying the pretraining pipeline rather than just fine-tuning. But the potential payoff is models that are "designed for sparsity" from the ground up, potentially achieving higher sparsity at equivalent accuracy.

**5. Hardware co-design for conditional execution.** The kernel design carefully works around hardware constraints—for example, the decode kernel uses batched load scheduling to avoid pipeline bubbles. Future GPU architectures could provide native support for conditional execution patterns, potentially making the skip decision even cheaper or enabling skipped Key computation.

The pipeline schedule visualizations (Figures 3-4) provide a template for how hardware architects might think about supporting sparse attention: reducing dependencies, enabling conditional memory requests, and providing efficient synchronization primitives.

**6. Extending to other attention mechanisms.** BLASST is demonstrated on standard attention and MLA. Could the same principle apply to other attention variants?

- **Sliding window attention**: The block structure is already well-defined; BLASST could skip blocks outside the window more aggressively.
- **Linear attention**: The softmax normalization is replaced by different operations; the running maximum insight may not apply directly.
- **FlashAttention with PagedAttention**: The KV cache is non-contiguous; skip decisions may need modification to handle indirection.

Understanding which attention mechanisms are compatible with the BLASST principle would clarify its scope.

### Practical Applications and Downstream Use Cases

**Long-context serving systems.** For services deploying long-context models (e.g., RAG systems, document analysis tools, code completion for large repositories), BLASST provides immediate efficiency gains with minimal integration cost. A single parameter (target sparsity) controls the accuracy-performance tradeoff, making it easy to configure for different latency SLOs.

The calibration procedure is designed for production deployment: run once per model, store the parameters $(\alpha, \beta)$, and the system handles any context length automatically.

**On-device inference.** Edge devices have stricter memory and compute constraints. BLASST's ability to skip both computation and memory accesses is valuable for running larger models on constrained hardware. The 1.5× speedup at ~70% sparsity could translate directly to longer battery life or support for larger models on the same device.

The training-free nature is particularly valuable here: device manufacturers cannot retrain models but can apply BLASST to any pretrained checkpoint.

**Batch inference workloads.** For high-throughput batch processing (e.g., evaluating large datasets, generating training data, processing backlogs), BLASST provides predictable speedups. Figure 5 shows TTFT and TPOT speedups in a batched inference setup (in-flight batching with concurrency 64).

**Cost reduction for cloud deployments.** Cloud inference cost is often dominated by GPU compute time. Even a 1.3× speedup (achievable at ~50% sparsity with minimal accuracy impact) translates directly to 23% cost reduction—a substantial saving for services running at scale.

### When to Prefer BLASST Over Alternatives

**Prefer BLASST when:**

- You need to accelerate **both prefill and decode** phases (most production deployments)
- You cannot retrain or fine-tune the model (using off-the-shelf checkpoints)
- You want predictable, controllable sparsity (specify a target, get that sparsity)
- You want minimal integration effort (single threshold parameter, existing API compatibility)
- You are deploying on modern NVIDIA GPUs (Hopper or Blackwell with optimized kernels available)

**Consider alternatives when:**

- You only need to optimize **one phase** (e.g., only decode-heavy workloads): KV cache compression methods like Quest or RocketKV may be sufficient
- You can control the pretraining/fine-tuning process: methods like DSA or sparsity-aware training from scratch may achieve higher sparsity
- You have very different memory hierarchy constraints: BLASST's kernel optimizations target NVIDIA GPU characteristics
- You need guaranteed accuracy preservation: BLASST shows minimal degradation but is still approximate; dense attention is the only guarantee
