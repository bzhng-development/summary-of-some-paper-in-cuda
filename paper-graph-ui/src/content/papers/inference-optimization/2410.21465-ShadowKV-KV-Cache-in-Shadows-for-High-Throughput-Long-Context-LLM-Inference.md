# ShadowKV: KV Cache in Shadows for High-Throughput Long-Context LLM Inference

**ArXiv:** [2410.21465](https://arxiv.org/abs/2410.21465)

## 🎯 Pitch

ShadowKV introduces a high-throughput inference system for long-context LLMs that **stores the low-rank key cache on GPU and offloads the value cache to CPU**, reducing GPU memory footprint to enable up to 6× larger batch sizes while boosting throughput by up to 3.04× on an A100 GPU without accuracy degradation.

---

## 1. Executive Summary

ShadowKV introduces a high-throughput inference system for long-context LLMs that **stores the low-rank key cache on GPU and offloads the value cache to CPU**, reducing GPU memory footprint to enable up to 6× larger batch sizes while boosting throughput by up to 3.04× on an A100 GPU without accuracy degradation. The system combines two mechanisms: **low-rank pre-RoPE key compression** (applying online, prompt-dependent SVD to pre-RoPE keys, which exhibit sharp singular value decay enabling 6× compression, while offloading the non-low-rank value cache to CPU) and **accurate KV selection via landmark-based chunk approximation** (computing chunk-mean landmarks on post-RoPE keys to select only 1.56% of KV pairs for sparse attention, with a small set of 0.3% outlier chunks stored statically on GPU). Across RULER, LongBench, and Needle In A Haystack benchmarks with models including Llama-3.1-8B, Llama-3-8B-1M, GLM-4-9B-1M, and Yi-9B-200K at contexts up to 1M tokens, ShadowKV matches full-attention accuracy while delivering 3.04× throughput gains (surpassing even the performance achievable with infinite batch size under the assumption of infinite GPU memory), establishing that test-time KV cache compression can substitute for GPU memory capacity only when the compression targets the intrinsically low-rank pre-RoPE key representations rather than post-RoPE keys or value caches.

## 2. Context and Motivation

### The Core Problem: The KV Cache Is the Bottleneck for Long-Context Throughput

The fundamental tension this paper addresses is deceptively simple: **as LLM context lengths grow, the KV cache grows linearly with sequence length, but GPU memory does not**. This tension creates two compounding bottlenecks that crush throughput during inference.

**Memory footprint bottleneck.** In transformer-based LLMs, the key-value (KV) cache stores the intermediate key and value activations computed during the pre-filling phase so they don't need to be recomputed for every subsequent token generation. For a model with $L$ layers, $H$ attention heads, hidden dimension $d$, and sequence length $S$, the KV cache memory footprint is:

$$2 \times L \times H \times S \times d \text{ elements}$$

For a model like Llama-3-8B-1M processing a 1M-token context, this amounts to tens of gigabytes **per sequence**. On an A100 GPU with 80 GB of memory, only a single 512K-token sequence or a small handful of shorter sequences can fit simultaneously. This directly limits batch size, and since throughput scales with batch size in GPU-accelerated inference, the memory ceiling imposes a hard throughput constraint.

**Memory bandwidth bottleneck (the "memory wall").** Even when KV cache *fits* in GPU memory, accessing it for each token generation incurs a bandwidth cost. Standard attention requires loading the full $S \times d$ key and value caches from GPU global memory for every generated token. For an A100 with 2 TB/s memory bandwidth, a 128K-token context with 128-dimensional per-head keys/values across 32 heads requires reading roughly $2 \times 128\text{K} \times 128 \times 32 \times 2 \text{ bytes} \approx 2$ GB per token generation step. At 2 TB/s bandwidth, this alone takes approximately 1 ms — not including the actual attention computation, feed-forward network execution, or any additional overhead. When generating thousands of tokens across multiple sequences, this bandwidth cost dominates latency.

These two bottlenecks compound: **larger batch sizes require more memory per batch, but smaller batch sizes leave memory bandwidth underutilized** because GPU compute units idle while waiting for data. The result, as the paper's Table 3 shows, is that full-attention inference on Llama-3-8B-1M with 122K contexts can only support a batch size of 4, yielding just 80.77 tokens/s — a fraction of the GPU's theoretical throughput potential.

### Why This Matters Now

The paper identifies three converging trends that make this problem urgent:

**1. Context lengths are exploding.** Models in 2024 routinely support 128K, 200K, and 1M-token contexts: Llama-3.1 supports 128K, GLM-4 extends to 1M, Gemini handles millions of tokens. Longer contexts enable qualitatively different applications — multi-document QA, repository-scale code understanding, legal document analysis, full-book summarization — but the KV cache footprint scales as $O(S)$, making these applications economically unviable at scale without memory optimization.

**2. High-throughput serving is the dominant deployment mode.** Most production LLM deployments handle many concurrent requests (chat applications, API services, batch document processing). In these settings, throughput (tokens generated per second across all users) matters more than per-request latency. Batch size directly controls throughput, and memory-efficient approaches that support larger batches translate immediately to cost savings and capacity gains.

**3. The economic case for smaller models with smarter inference is strengthening.** The paper's broader context — though not the primary focus — connects to the emerging paradigm where inference-time compute augmentation can substitute for model scale. A system that triples throughput effectively provides the capacity of three GPUs on one GPU. For organizations running inference at scale, this represents a direct 3× reduction in hardware costs or a 3× increase in serving capacity.

### The Inadequacy of Existing Approaches

The paper identifies three families of prior work, each with critical limitations:

#### Token Eviction Strategies (StreamingLLM, H2O, SnapKV, LESS)

These methods permanently discard a subset of KV pairs to maintain a fixed, smaller cache. StreamingLLM (Xiao et al., 2023) observed that initial tokens ("attention sinks") and recent tokens dominate attention, allowing intermediate tokens to be dropped. H2O (Zhang et al., 2023) accumulates cumulative attention scores to identify "heavy hitter" tokens worth retaining. SnapKV (Li et al., 2024) uses the local window of prompts to select attention-important tokens. LESS (Dong et al., 2024) maintains a constant-size low-rank cache to partially preserve discarded information.

**Why they fall short:** Evicted tokens are gone forever. For tasks requiring multi-turn conversations — where a user might ask about different parts of a long document across multiple queries — the tokens needed for turn 3 might have been evicted during turn 1 because they weren't relevant *then*. The paper's Figure 7 demonstrates exactly this: SnapKV accuracy drops significantly from the second conversation round because token selection for the first query isn't appropriate for the second. As the authors note, "they suffer from performance degradation and information loss since the evicted tokens will never be recovered" (Section 2). For ambiguous queries where relevance can't be determined until the query arrives, eviction is fundamentally risky.

#### Dynamic Sparse Attention (SparQ, Quest, Loki, TriForce)

These methods retain all KV cache on GPU but compute attention with only a selected subset of KV pairs to reduce computation. SparQ (Ribar et al., 2023) uses query norms to identify important key channels. Quest (Tang et al., 2024) segments KV cache into pages and selects pages based on approximate attention scores. Loki (Singhania et al., 2024) performs PCA on key caches offline and selects tokens using attention scores computed in low-dimensional space. TriForce (Sun et al., 2024) combines sparse attention with speculative decoding for acceleration.

**Why they fall short:** They solve the *computation* bottleneck but not the *memory* bottleneck. Retaining the full KV cache on GPU means the maximum batch size is still limited by memory capacity. As the paper states, "this line of work does not mitigate the memory footprint, thereby limiting the batch size and preventing accommodation of extremely long contexts (e.g., 1M tokens)" (Section 1). For serving scenarios where throughput is the primary metric, leaving memory unaddressed means these methods can't support the batch sizes needed to saturate GPU compute.

#### CPU Offloading (FlexGen, InfiniGen, FastDecode)

These methods move the KV cache to CPU memory to relieve GPU pressure. FlexGen (Sheng et al., 2023) offloads KV cache to CPU and prefetches them in bulk via PCIe, accepting high latency for throughput gains. InfiniGen (Lee et al., 2024) offloads KV cache to CPU but prefetches only the entries predicted to be important by a precomputed SVD projection, reducing data transfer. FastDecode (He and Zhai, 2024) uses heterogeneous pipelines for offloading.

**Why they fall short:** PCIe bandwidth is a severe bottleneck. An A100 GPU has 2 TB/s of internal memory bandwidth but only 31.5 GB/s of PCIe bandwidth — a roughly 64× gap. InfiniGen's approach of prefetching only important entries partially addresses this, but as the paper's Figure 4 illustrates, the KV selection in InfiniGen is inaccurate (it uses a fixed offline SVD projection that doesn't adapt to the prompt), and overlapping KV fetching with computation becomes increasingly difficult as the total KV cache size grows. The paper's Table 1 shows InfiniGen suffers significant accuracy degradation on complex tasks like multi-key needle retrieval and multi-document QA, even when only the value cache is offloaded.

### The Crucial Insight Gap: Where Is Low-Rank Structure?

Prior work had noticed the KV cache exhibits low-rank properties. Palu (Chang et al., 2024) decomposes the KV weight matrices offline and caches low-rank projections. DeepSeek-V2 (DeepSeek-AI, 2024) uses multi-head latent attention to compress the KV cache. Several works (Saxena et al., 2024; Xu et al., 2024; Yu et al., 2024) apply low-rank approximations to keys.

**But these methods apply low-rank decomposition to the wrong target.** The paper's critical empirical finding — presented in Figure 1 (left panel) — is that the **rank structure varies dramatically depending on where in the computation pipeline you look**:

- **Pre-RoPE keys** (key activations *before* rotary position embedding is applied) show exceptionally sharp singular value decay, indicating strong low-rank structure. A rank-160 decomposition captures nearly all the information from a 128-dimensional key cache.
- **Post-RoPE keys** (after position embedding, which is where most prior work applies compression) show much slower decay — the rotary embeddings "spread out" the singular values, making low-rank approximation much less effective.
- **Value caches** show the slowest singular value decay of all, meaning low-rank approximation directly on values would cause severe information loss.

Figure 5 (left) quantifies the practical impact: compressing post-RoPE keys to rank 256 maintains only ~60% accuracy on needle retrieval, while compressing pre-RoPE keys to the same rank maintains near-100% accuracy. The compression ratio is over 6× with no accuracy drop for pre-RoPE keys.

**Why pre-RoPE keys are low-rank while post-RoPE keys aren't** is a subtle but important point. The rotary position embedding (RoPE) applies a rotation matrix that depends on token position. Pre-RoPE, tokens with similar semantic content produce similar key vectors regardless of position, creating a low-rank structure in the semantic subspace. Post-RoPE, each position's rotation effectively "scrambles" this structure — semantically similar tokens at different positions map to different regions of the space, flattening the singular value spectrum. This means **compression must happen before RoPE, not after**, which prior methods failed to recognize.

### Additional Insight: Low-Rank Subspaces Are Sequence-Specific

The paper's Figure 1 (middle panel) reveals another critical property: **the low-rank subspace of pre-RoPE keys varies significantly between sequences but is shared within a sequence and its continuations**. The authors define a subspace similarity metric $D(H_1, H_2) = \langle H_1, H_2 \rangle / r$ (the normalized Frobenius inner product of projection matrices from truncated SVDs), finding:

- Inter-sequence similarity (between two unrelated 16K-token sequences) measures only 0.75–0.80, meaning the low-rank subspaces differ substantially.
- Extended context similarity (between a 16K context and its 16K+2K continuation) measures 0.95–1.00, meaning newly generated tokens share the same low-rank subspace as the original context.

This has direct algorithmic implications: **offline, data-independent low-rank projections won't work well across sequences**, explaining why InfiniGen's fixed SVD projections lead to accuracy degradation. But **online, prompt-dependent SVD that computes the low-rank basis for each sequence individually can be highly effective**, and the same projection can be reused for generated tokens (as the paper tests in its ShadowKV+ variant, Appendix A.1).

### How ShadowKV Positions Itself

The paper frames its contribution through a unified lens: **an ideal system must simultaneously solve three problems that prior work addressed separately and incompletely**:

1. **Reduce GPU memory** (not addressed by dynamic sparse attention alone).
2. **Minimize inference latency** (not addressed by naive CPU offloading, where PCIe bandwidth dominates).
3. **Maintain accuracy** (not addressed by token eviction, where discarded information is permanently lost, or by offline low-rank projections, where sequence-specific subspace variation causes degradation).

The paper's core premise is that these three goals can be achieved simultaneously by **correctly identifying what to compress (pre-RoPE keys, not post-RoPE keys or values) and what to offload (values, which aren't low-rank)**, combined with an **accurate, prompt-adaptive KV selection mechanism** that minimizes how much data must be fetched from CPU and how many KV pairs must be reconstructed for attention.

Critically, ShadowKV is positioned as a **system that makes sparse attention actually practical for high-throughput serving**, not as a fundamentally new sparse attention algorithm. As Figure 4 illustrates, prior sparse attention methods that offload KV cache to CPU (Quest with CPU offloading, InfiniGen) either incur prohibitive latency from fetching full KV pairs or lose accuracy from inaccurate KV selection. ShadowKV's architecture — overlapping key reconstruction with value fetching, using landmarks for accurate selection, and caching outlier chunks statically — transforms sparse attention from a latency-memory tradeoff into a throughput win.

The concept of **theoretical equivalent bandwidth** (Section 4.2) crystallizes this positioning. ShadowKV achieves an equivalent bandwidth of 7.2 TB/s on an A100, which is 3.6× the GPU's raw memory bandwidth of 2 TB/s, by avoiding the need to read the full KV cache from GPU memory. This means ShadowKV effectively operates as if it had access to 3.6× faster memory — exceeding even what would be possible with an infinitely large GPU memory (the "infinite batch size" baseline in Table 3) because infinite memory still requires reading full KV caches at 2 TB/s bandwidth.

## 3. Technical Approach

### 3.1 Reader Orientation

ShadowKV is a **GPU-CPU hybrid inference system** that rearranges where and how the key-value cache is stored during long-context LLM generation. It solves the problem of **limited GPU memory crushing batch sizes** (and therefore throughput) during long-context inference by keeping a compressed version of the key cache on the GPU while moving the value cache to CPU, then reconstructing only the tiny fraction of KV pairs actually needed for each attention computation — all without changing the model's output quality.

### 3.2 Big-Picture Architecture (Diagram in Words)

Think of ShadowKV as having four major subsystems that operate in sequence across two phases (pre-filling and decoding):

1. **Low-Rank Key Compressor** — Applies truncated SVD to the pre-RoPE key cache during pre-filling, storing only a small low-rank factorization on GPU instead of the full key cache. This is the memory-saving engine.

2. **Landmark-Based Outlier Detector** — Segments the post-RoPE key cache into chunks, computes each chunk's mean vector (the "landmark"), identifies chunks where the mean poorly represents individual tokens (outliers), and stores those outlier tokens' full KV pairs on GPU as a static cache. The remaining chunks are represented only by their compact landmarks, while their full values are offloaded to CPU.

3. **Sparse KV Selector** — During decoding, computes approximate attention scores between the query and the stored landmarks to identify which chunks are most relevant. Only the KV pairs from these selected chunks (plus the static outliers) are fetched and reconstructed for attention computation.

4. **Overlapped Reconstruction Engine** — Uses CUDA multi-streams to simultaneously reconstruct selected key cache from the low-rank factorization (GPU-side) and fetch the corresponding value cache from CPU (PCIe-side), hiding the latency of both operations behind each other.

Information flows as follows: a prompt enters → pre-filling computes full attention and populates the full KV cache → low-rank compression reduces the key cache on GPU while values move to CPU → landmarks and outliers are computed and stored → during decoding, each new query uses landmarks to select relevant chunks → selected keys are reconstructed from low-rank factors while selected values stream from CPU → sparse attention computes only on the selected KV pairs plus static outliers → the generated token's KV pair gets appended (either as a full entry or as a low-rank projection, depending on the ShadowKV+ variant).

### 3.3 Roadmap for the Deep Dive

This section walks through the technical machinery in the order it executes:

- **First, the low-rank key compression mechanism** — why pre-RoPE keys specifically, what the SVD decomposition looks like, how compression ratio is chosen, and why values must be offloaded instead of compressed. This is the core memory-saving innovation.

- **Second, the landmark construction and outlier detection** — how post-RoPE keys are chunked and approximated, why cosine similarity between chunk means and individual tokens reveals spatially structured vs. irregular regions, and how outlier chunks get promoted to a static GPU cache.

- **Third, the sparse KV selection algorithm during decoding** — how landmarks enable approximate attention scoring, how chunk indices are selected via top-K over aggregated scores, and how the cache-hit mechanism exploits temporal locality between adjacent decoding steps to avoid redundant reconstruction.

- **Fourth, the overlapped reconstruction and fetching pipeline** — how low-rank key reconstruction and CPU-to-GPU value fetching are interleaved using CUDA multi-streams, and the concept of equivalent bandwidth that explains why ShadowKV can exceed raw GPU memory bandwidth.

- **Fifth, the handling of newly generated tokens (ShadowKV+)** — how the same low-rank projection from pre-filling extends to tokens generated during decoding, enabling memory savings for long outputs.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems paper** whose core idea is that: (1) pre-RoPE keys are uniquely low-rank among all KV cache representations, (2) this low-rank structure is prompt-dependent and must be computed online, (3) values and outliers resist low-rank approximation and must be handled separately, and (4) accurate sparse KV selection plus overlapping reconstruction can turn memory savings into throughput gains without accuracy loss.

---

#### 3.4.1 Low-Rank Pre-RoPE Key Compression and Value Offloading

The central memory-saving mechanism in ShadowKV is a recipe with three parts: **compress pre-RoPE keys via online SVD, offload values to CPU, and leave a small set of outlier tokens uncompressed as static cache**.

##### What Happens During Pre-Filling

During the standard pre-filling phase, the model processes the entire input prompt and computes key, query, and value activations at every layer. In a normal inference system, the full key cache `$K$` and value cache `$V$` — each of shape `$b \times h_{kv} \times s \times d$` where `$b$` is batch size, `$h_{kv}$` is the number of KV heads, `$s$` is sequence length, and `$d$` is head dimension — are stored in GPU memory for use during decoding. ShadowKV intervenes at this point with the following procedure, formalized in Algorithm 1 of the paper:

**Step 1: SVD on pre-RoPE keys.** Before rotary position embeddings are applied, the key activations `$K \in \mathbb{R}^{b \times h_{kv} \times s \times d}$` are decomposed using truncated singular value decomposition (SVD). For each sequence and each head, the SVD factors `$K$` into:

$$K \approx A \cdot B$$

where `$A \in \mathbb{R}^{b \times s \times r}$` is the left singular matrix (mapping token positions to a low-rank latent space), `$B \in \mathbb{R}^{b \times h_{kv} \times r \times d}$` is the right singular matrix (mapping the latent space back to the original key dimension), and `$r$` is the truncation rank — the dimensionality of the compressed representation.

**Step 2: Store only the low-rank factors.** Instead of storing the full `$K$` of size `$b \times h_{kv} \times s \times d$`, ShadowKV stores the two smaller matrices `$A$` and `$B$`. The storage required drops from `$s \cdot d$` per head to `$s \cdot r + h_{kv} \cdot r \cdot d$`. When `$r \ll d$` and `$s$` is large, this yields significant compression. For the paper's default configuration with `$r = 160$`, `$d = 128$`, and `$s = 128K$`, the compression ratio for keys alone is approximately:

$$\frac{s \cdot d}{s \cdot r + h_{kv} \cdot r \cdot d} = \frac{128K \cdot 128}{128K \cdot 160 + 8 \cdot 160 \cdot 128} \approx 0.79$$

but since values are offloaded entirely (see below), the total KV cache memory reduction is much larger — approximately `$7.08\times$` overall as computed in Appendix A.2.

**Step 3: Offload value cache to CPU.** The value cache `$V$` does not exhibit low-rank structure (Figure 1, left panel, shows the slowest singular value decay of any component). Attempting to compress values via SVD would lose critical information. Instead, ShadowKV moves the entire value cache to CPU memory, which is abundant (system RAM can be hundreds of GB) but accessed via slow PCIe (31.5 GB/s on A100). The key insight is that only a tiny fraction of values will ultimately need to be fetched back during decoding, making the PCIe bottleneck manageable.

**Step 4: Store static outlier cache on GPU.** A small number of tokens (identified via the landmark procedure described in Section 3.4.2) are exempted from both compression and offloading: their full key and value caches remain on GPU as a static cache. With only 48 outlier chunks (0.3% of tokens at 128K sequence length with chunk size 8), this static cache adds negligible memory overhead.

##### Why Pre-RoPE Keys Specifically

The paper's Figure 1 (left panel) is the empirical foundation for this design choice. The authors visualize the relative singular value distributions of six components in the attention computation pipeline:

- **Model weights `$W_K$` and `$W_V$`** — these are fixed across sequences and have moderate singular value decay.
- **Layer input `$X$`** — the hidden states fed into the attention projection, which show moderate decay.
- **Post-RoPE key cache** — key activations *after* rotary position embedding is applied, showing significantly slower decay than pre-RoPE keys.
- **Value cache** — showing the slowest decay of all, confirming values are not meaningfully low-rank.
- **Pre-RoPE key cache** — key activations *before* RoPE, showing the sharpest singular value decay — the "most low-rank" of any component.

The reason pre-RoPE keys are more compressible than post-RoPE keys is subtle but important. Rotary Position Embedding (RoPE) applies a position-dependent rotation to each key vector. Before RoPE, tokens with similar semantic content produce similar key vectors regardless of their position in the sequence — "the word 'cat' at position 5 and position 500 have similar pre-RoPE key representations because they encode the same semantic concept. After RoPE, each position's rotation matrix transforms these similar vectors into different regions of the space — effectively "scrambling" the semantic similarity across the positional axis. This scrambling flattens the singular value spectrum, making low-rank approximation much less effective.

The quantitative impact is shown in Figure 5 (left panel): at SVD rank 256, compressing pre-RoPE keys maintains near-100% accuracy on needle retrieval tasks, while compressing post-RoPE keys at the same rank drops accuracy to approximately 60%. The difference is stark — compressing pre-RoPE keys allows for over 6× reduction with no quality loss, while compressing post-RoPE keys is fundamentally lossy at any practical compression ratio.

##### Why Online, Prompt-Dependent SVD

Figure 1 (middle panel) reveals the critical dynamic property: the low-rank subspace of pre-RoPE keys **varies significantly between different sequences** but **remains consistent within a sequence and its continuations**. The authors define a subspace similarity metric `$D(H_1, H_2) = \langle H_1, H_2 \rangle / r$` — the normalized Frobenius inner product of the rank-`$r$` projection matrices:

$$H_1 = \Psi_1 \Psi_1^\top, \quad H_2 = \Psi_2 \Psi_2^\top$$

where `$\Psi_1, \Psi_2 \in \mathbb{R}^{d \times r}$` are the right singular matrices from truncated SVDs of two different key caches. The metric `$D(H_1, H_2) \in [0, 1]$` measures how much the two low-rank subspaces overlap, with 1 indicating identical subspaces and 0 indicating orthogonal subspaces.

For a 16K-token "context" sequence and a 16K+2K continuation of the same sequence, the subspace similarity measures 0.95–1.00 — the continuation shares essentially the same low-rank subspace as the original context. But for two unrelated 16K sequences, the similarity drops to 0.75–0.80 — the subspaces differ substantially.

This has direct algorithmic implications. An **offline SVD** computed on a calibration dataset (as InfiniGen does) will produce a fixed projection matrix that is mismatched to any particular test sequence's actual low-rank subspace, causing accuracy degradation. An **online, prompt-dependent SVD** that computes the low-rank basis from each input sequence's actual pre-RoPE keys will be perfectly matched to that sequence. The cost of this online SVD — addressed next — turns out to be acceptable because attention computation dominates pre-filling latency at long sequence lengths.

##### The Cost of Online SVD Scales Favorably with Sequence Length

Figure 1 (right panel) shows the relative overhead of SVD computation as a percentage of total pre-filling time. The key finding: as sequence length grows from 64K to 384K, the SVD overhead drops from roughly 5% to under 1% of total pre-filling latency. This is because:

- **Attention computation scales quadratically with sequence length** (`$O(S^2)$`), dominating pre-filling time for long sequences.
- **SVD computation scales roughly linearly with sequence length** (`$O(S \cdot d \cdot r)$`), since it operates on a matrix of shape `$S \times d$` and produces a rank-`$r$` decomposition.
- **Feed-forward network (FFN) computation also scales linearly**, growing proportionally with `$S$`.

At 64K sequences, attention takes approximately 186 ms per transformer block while SVD takes approximately 17 ms (Table 12) — a 6.65% overhead. At 512K sequences, attention takes approximately 11,720 ms while SVD takes approximately 108 ms — a 0.97% overhead. The proportional cost of SVD shrinks as sequences get longer, meaning ShadowKV's compression mechanism actually becomes *cheaper* relative to total pre-filling cost at the extreme context lengths where memory savings matter most.

The paper also notes (in a footnote, Section 4.1) that in practical scenarios, the key cache can be offloaded to CPU to perform SVD asynchronously, or the low-rank projection can be precomputed and stored as part of a prefix cache for shared-prefix scenarios.

#### 3.4.2 Landmark Construction and Outlier Detection

With the low-rank key cache stored on GPU and values offloaded to CPU, ShadowKV needs a mechanism to determine **which KV pairs to fetch and reconstruct** during decoding — it cannot afford to reconstruct everything, or the memory savings would be negated by the bandwidth cost of fetching all values from CPU.

The solution is a two-part selection infrastructure built during pre-filling: **landmarks** that enable cheap approximate attention scoring, and **outlier detection** that identifies tokens where the landmark approximation fails.

##### How Landmarks Are Built

The post-RoPE key cache `$K_{\text{RoPE}} \in \mathbb{R}^{b \times h_{kv} \times s \times d}$` is segmented into chunks of size `$c$` (default `$c = 8$` tokens per chunk). For each chunk, the mean key vector is computed:

$$L = \text{Reduce}(K_{\text{RoPE}}) \in \mathbb{R}^{b \times h_{kv} \times s/c \times d}$$

where the reduce operation averages over the chunk dimension. This mean vector `$L$` is the **landmark** for that chunk — a single `$d$`-dimensional vector that represents all `$c$` tokens in the chunk.

The landmark tensor `$L$` has `$s/c$` entries per head instead of `$s$` entries, reducing the data that must be accessed during KV selection by a factor of `$c$`. For `$c = 8$` and `$s = 128K$`, there are only 16K landmark vectors per head instead of 128K key vectors — an 8× reduction in the KV selection computation.

##### How Outlier Chunks Are Identified

Not all chunks are equally well-represented by their mean. The paper quantifies this by computing the **minimum cosine similarity within each chunk**:

$$S = \text{CosineSimilarity}(L_i, K_{\text{RoPE}, i})$$

for each token `$i$` within its chunk, where `$L_i$` is the chunk's mean vector and `$K_{\text{RoPE}, i}$` is the individual token's post-RoPE key. The minimum similarity across all tokens in a chunk tells us how well the mean represents the chunk's most "outlying" token.

Figure 5 (middle panel) visualizes this minimum similarity across all 16,384 chunks of a 128K-token sequence (with chunk size 8). The vast majority of chunks have minimum similarity above 0.6 or even 0.8, meaning even the most dissimilar token in those chunks is still fairly well-aligned with the chunk mean. But a small number of chunks — roughly 0.2–0.3% of the total — have minimum similarity values that drop dramatically, even below 0.0 (indicating orthogonal or negatively correlated key vectors within the same chunk).

These are the **outlier chunks** — tokens whose post-RoPE key representations deviate sharply from their neighbors. They cluster in specific positions (often at the beginning of the sequence, consistent with the "attention sink" phenomenon where initial tokens receive disproportionately high attention regardless of query) and in small, isolated regions.

##### Why Outlier Chunks Need Special Treatment

If outlier chunks were represented only by their landmarks, the approximate attention scores computed during KV selection would be inaccurate — the landmark doesn't capture the extreme key vectors within these chunks, causing the selection algorithm to either miss them (when they're actually important to the query) or incorrectly select them (when the landmark overestimates their relevance). Either error propagates to the attention computation, which would use the reconstructed (but inaccurate) keys for these tokens.

ShadowKV's solution is elegantly simple: **exempt outlier chunks from the approximation entirely**. The full KV pairs for tokens in outlier chunks are stored on the GPU as a static cache, bypassing both low-rank key compression and CPU offloading. During decoding, these tokens are always included in the sparse attention computation alongside the dynamically selected chunks.

The number of outlier chunks is `$o$`, with the paper defaulting to `$o = 48$` (48 chunks × 8 tokens/chunk = 384 tokens out of 128K, or 0.3%). At this scale, the memory overhead is negligible, but the accuracy impact is substantial. Appendix Table 15 shows that with 0 outliers, ShadowKV achieves 74.05% average accuracy on RULER; with 48 outliers, accuracy rises to 86.88% — essentially matching full attention at 86.68%.

The outlier detection algorithm (from Algorithm 1):

1. Compute cosine similarity between each chunk's mean and its constituent tokens: `$S \leftarrow \text{CosineSimilarity}(C, K_{\text{RoPE}})$`.
2. Find the minimum similarity per chunk: `$\text{Min}(S, \dim = -1)$` which identifies the worst-approximated token in each chunk.
3. Select the top-`$o$` chunks with the lowest minimum similarity: `$I \leftarrow \text{ArgTopK}(-\text{Min}(S, \dim = -1), o)$` — the negation converts "lowest similarity" to "highest priority" for the TopK operation.
4. Gather the full key and value caches for these outlier chunk indices: `$K_{\text{outlier}}, V_{\text{outlier}} \leftarrow \text{Gather}(K_{\text{RoPE}}, V, I)$`.
5. Remove outlier chunks from the landmark set and value cache: `$V_{\text{CPU}} \leftarrow V \setminus V_{\text{outlier}}$`, `$L \leftarrow C \setminus \text{Gather}(C, I)$`.

The non-outlier chunks continue to be represented only by their landmarks (stored on GPU) and their offloaded values (on CPU). The result is a hybrid representation: **compact landmarks for the well-behaved majority of tokens, full KV cache for the irregular minority**.

##### What Makes Outlier Chunks Interesting

The paper's analysis (Figure 5, middle panel) reveals that outlier chunks are not randomly distributed. They appear at specific positions and layers, with some heads in certain layers exhibiting more outliers than others. This is consistent with the attention sink phenomenon documented by Xiao et al. (2023): the first few tokens of a sequence often act as "sinks" that attract disproportionate attention regardless of query content. These tokens have key vectors that differ structurally from subsequent tokens, making them ill-suited for the chunk-mean approximation.

By detecting and preserving these outliers, ShadowKV effectively identifies and protects the tokens that are most important for attention while still compressing the vast majority. This is a fundamentally different approach from eviction-based methods like StreamingLLM, which *discard* intermediate tokens while keeping the attention sinks — ShadowKV compresses everything but gives outliers a lossless bypass.

#### 3.4.3 Sparse KV Selection During Decoding

When a new token is generated during the decoding phase, the model produces a query vector `$Q \in \mathbb{R}^{b \times h_q \times s_q \times d}$` (where `$s_q$` is typically 1 for autoregressive generation). ShadowKV needs to select a small subset of the full KV cache to use for attention against this query — the "sparse budget" of `$k$` chunks plus the `$o$` static outlier chunks.

##### Step 1: Compute Approximate Attention Scores Using Landmarks

The query `$Q$` is multiplied against the landmark tensor `$L$` (which has shape `$b \times h_{kv} \times s/c \times d$`) to produce chunk-level attention scores:

$$P \in \mathbb{R}^{b \times h_q \times s_q \times n_c} \leftarrow \text{MatMul}(Q, L^\top)$$

where `$n_c = s/c$` is the number of chunks. This operation computes, for each query head and each chunk, the dot product between the query and the chunk's mean key vector — an approximation of how much attention that chunk would receive if full attention were computed.

These raw scores are then normalized:

$$S \in \mathbb{R}^{b \times h_q \times s_q \times n_c} \leftarrow \text{Softmax}(P / \sqrt{d})$$

producing a probability distribution over chunks for each query position. This softmax is the same temperature-scaled normalization used in standard attention, with the `$1/\sqrt{d}$` scaling factor preventing dot products from growing too large in high dimensions.

##### Step 2: Aggregate Scores Across Query Heads and Positions

The scores need to be reduced to a single importance score per chunk per KV head. This happens in two aggregation steps:

$$S_1 \in \mathbb{R}^{b \times h_q \times n_c} \leftarrow \text{sum}(S, \dim = -2)$$

This sums the softmax scores across all query positions (the `$s_q$` dimension) for each chunk, producing a per-query-head importance score for each chunk.

$$S_2 \in \mathbb{R}^{b \times h_{kv} \times n_c} \leftarrow \text{maxkv\_group}(S_1)$$

The `maxkv_group` operation handles the case where the number of query heads differs from the number of KV heads (as in Grouped Query Attention, where multiple query heads share one KV head). It takes the maximum score across the query heads assigned to each KV head, ensuring that if any query head finds a chunk important, that chunk is considered important for the shared KV head.

##### Step 3: Select Top-K Chunks

For each KV head, the `$k$` highest-scoring chunk indices are selected:

$$I \in \mathbb{R}^{b \times h_{kv} \times k} \leftarrow \text{ArgTopK}(S_2, k)$$

where `$k$` is the sparse budget expressed in number of chunks. With the paper's default chunk size `$c = 8$` and a sparse budget of 1.56% of total tokens, at `$s = 128K$` this gives `$k = 0.0156 \times 128K / 8 = 256$` chunks, totaling 2,048 tokens per head.

##### Step 4: Fetch Values and Reconstruct Keys

For the selected chunk indices `$I$`, two operations happen in parallel (see Section 3.4.4 for the overlapping mechanism):

- **Value fetching:** The corresponding values are gathered from CPU memory: `$V_{\text{sparse}} \leftarrow \text{Gather}(V_{\text{CPU}}, I)$`. These are the full, uncompressed value vectors.
- **Key reconstruction:** The corresponding pre-RoPE keys are reconstructed from the low-rank factors: `$K_{\text{sparse}} \leftarrow \text{MatMul}(\text{Gather}(A, I), B)$`. This multiplies the selected rows of the left singular matrix `$A$` (of shape `$k \times c \times r$`, since each chunk contains `$c$` tokens) by the right singular matrix `$B$` (of shape `$r \times d$`), producing the approximate pre-RoPE keys. These are then passed through RoPE to produce the post-RoPE keys needed for attention: `$K_{\text{sparse}} \leftarrow \text{RoPE}(K_{\text{sparse}})$`.

The reconstructed keys are approximate — they represent the rank-`$r$` reconstruction of the original pre-RoPE keys, losing the information in the truncated singular values. However, since the rank `$r = 160$` was chosen to capture essentially all the signal (Figure 5, left panel, shows no accuracy degradation at this rank), the approximation is essentially lossless.

##### Step 5: Assemble Final KV Cache and Compute Sparse Attention

The final KV cache for attention computation concatenates three sources:

$$K \leftarrow [K_{\text{outlier}}; K_{\text{sparse}}; K_{\text{new}}] \quad V \leftarrow [V_{\text{outlier}}; V_{\text{sparse}}; V_{\text{new}}]$$

where `$K_{\text{outlier}}, V_{\text{outlier}}$` are the static outlier caches, `$K_{\text{sparse}}, V_{\text{sparse}}$` are the reconstructed/fetched sparse KV pairs, and `$K_{\text{new}}, V_{\text{new}}$` are the KV pairs for newly generated tokens (stored uncompressed by default, or low-rank projected in the ShadowKV+ variant).

Attention is then computed normally using FlashAttention or another efficient attention kernel, but only on this small subset of tokens. With the default configuration of 256 selected chunks (2,048 tokens) plus 48 outlier chunks (384 tokens) for a 128K-token context, the attention computation processes only 2,432 tokens instead of 128K — a 52.6× reduction in attention FLOPs.

##### The Cache Hit Mechanism: Exploiting Temporal Locality

The paper observes that KV selection exhibits significant temporal locality: "the KV pairs selected by the queries of two adjacent decoding steps have a high repetition rate" (Section 3.2). This is because adjacent tokens in the generated output are semantically similar, so their queries tend to attend to similar chunks of the context.

ShadowKV exploits this by maintaining a **cache of previously selected chunk indices**. At each decoding step, before executing the full landmark-based selection pipeline, the system checks whether the current query's top-scoring chunks overlap with the cached indices from the previous step. The "hit rate" — the fraction of chunks that were already selected and reconstructed in the previous step — is typically around 60% (Figure 5, right panel, and Figure 9, left panel analysis).

Concretely, the cache mechanism operates as follows (from Algorithm 2 and the system implementation description):

1. After computing new chunk selections `$I$`, compare with the previous step's selections.
2. Identify "missed" chunks — those in `$I$` that were not in the previous cache.
3. Only fetch values and reconstruct keys for the missed chunks.
4. Reuse the previously reconstructed KV pairs for the hit chunks (they are still in GPU memory from the previous step).

The 60% hit rate means that in practice, ShadowKV only needs to fetch and reconstruct 40% of the sparse budget on each decoding step, reducing both PCIe data transfer and key reconstruction computation by an additional 2.5× compared to selecting and reconstructing everything from scratch. The paper notes this is implemented "with optimized CUDA kernels" that efficiently scan chunk indices and manage the cache.

##### Why Chunk-Level Selection Over Token-Level Selection

The choice to select chunks rather than individual tokens is a deliberate tradeoff. Token-level selection (selecting the top-`$k \cdot c$` individual tokens) would theoretically be more precise, since the importance of individual tokens within a chunk can vary. However, chunk-level selection offers three advantages:

1. **Reduced selection computation:** Computing attention scores against landmarks requires `$s/c$` dot products instead of `$s$` dot products, an `$c\times$` reduction. For `$c = 8$`, this means the approximate attention computation is 8× cheaper.

2. **Efficient data transfer:** Fetching value cache from CPU benefits from reading contiguous chunks of memory. Selecting individual tokens scattered across the sequence would require many small, non-contiguous PCIe reads, dramatically reducing effective bandwidth.

3. **Coherent key reconstruction:** When reconstructing keys from the low-rank factors, tokens within the same chunk are contiguous in the `$A$` matrix, enabling efficient batched matrix multiplication.

The chunk size `$c = 8$` is chosen as the sweet spot: small enough that the chunk-mean is a good approximation for most tokens (as validated by the cosine similarity analysis), but large enough to provide meaningful computational savings. Figure 9 (left panel) shows that `$c = 8$` achieves the best balance — larger chunk sizes enable bigger batch sizes (since there are fewer landmarks to process) but degrade accuracy because the mean becomes a poorer approximation. The hit rate remains around 60% regardless of chunk size, suggesting temporal locality is robust to this parameter.

##### The Sparse Budget Parameter

The sparse budget — expressed as a percentage of total tokens or as the number of selected chunks `$k$` — directly controls the tradeoff between accuracy and throughput. The paper experiments primarily with a 1.56% sparse budget, which for 128K contexts means selecting 256 chunks (2,048 tokens) plus 48 outlier chunks (384 tokens).

Figure 8 shows the accuracy impact of varying the sparse budget from 0.2% to 100% (full attention). ShadowKV consistently outperforms Quest at all budget levels, and with a 1.56% budget, it matches full attention accuracy on most RULER tasks. Some tasks (like variable tracking) actually show *improved* accuracy with sparse attention — a phenomenon the authors attribute to the sparse selection acting as a form of regularization that filters out irrelevant context.

#### 3.4.4 Overlapped Reconstruction and the Equivalent Bandwidth Model

The throughput gains of ShadowKV depend critically on **hiding the latency of key reconstruction and value fetching behind each other and behind computation**. This section explains the concurrency mechanism and the theoretical model that quantifies its benefit.

##### CUDA Multi-Stream Overlapping

The key and value reconstruction/fetching operations are placed on separate CUDA streams, allowing them to execute concurrently:

- **Stream 1 (GPU compute):** Reconstructs selected key cache from low-rank factors: `$K_{\text{sparse}} \leftarrow \text{MatMul}(\text{Gather}(A, I), B)$`. This is a GPU-side matrix multiplication using the GPU's high-bandwidth memory.

- **Stream 2 (PCIe data transfer):** Fetches the corresponding value cache from CPU: `$V_{\text{sparse}} \leftarrow \text{Gather}(V_{\text{CPU}}, I)$`. This is a CPU-to-GPU memory copy over the PCIe bus.

Because these operations use different hardware resources (GPU tensor cores for the matrix multiply, PCIe DMA engines for the data transfer), they can genuinely execute in parallel. The CUDA runtime's multi-stream scheduler interleaves them automatically, with the GPU alternating between compute work and memory transfer initiation.

The paper refers to this as "concealing the construction of the key cache" — the key reconstruction latency is hidden behind the value fetching latency, and vice versa. Since value fetching over PCIe is typically the slower operation (31.5 GB/s vs. 2 TB/s), the key reconstruction effectively happens "for free" during the value transfer.

Figure 4 illustrates how this overlapping strategy compares to alternatives:
- **Prefetch Full KV (a):** The naive approach — sequentially fetch all KV pairs from CPU to GPU, then compute attention. The fetch latency fully adds to the decoding time.
- **Fetch Sparse KV (b):** Quest-style sparse attention with CPU offloading — select important KV pairs, fetch them from CPU, then compute attention. Better than (a) because less data is transferred, but the fetch is still sequential with computation.
- **Prefetch Sparse KV (c):** InfiniGen's approach — prefetch predicted important KV pairs in advance while computing other operations. Limited by the inaccuracy of offline SVD-based prediction.
- **ShadowKV (d):** Only fetches values (not keys, since keys are reconstructed from low-rank factors), and overlaps the fetch with key reconstruction.

The critical insight: ShadowKV's reduction in data transferred (values only, not keys) plus the overlapping of fetch with reconstruction gives it a 2× reduction in effective fetch overhead compared to fetching full KV pairs.

##### Theoretical Equivalent Bandwidth

The paper formalizes the throughput benefit through the concept of **equivalent bandwidth** — the effective memory bandwidth that ShadowKV achieves, accounting for both GPU memory access and PCIe data transfer.

The model considers each K or V vector as being `$M$` bytes in size (M = 1024 for BF16 precision with 128-dimensional head and 8 KV heads), with sequence length `$S$`, chunk size `$C$`, selected chunk budget `$K$`, `$O$` outliers, and hit rate `$\alpha$`.

The equivalent bandwidth `$\widetilde{B}$` is:

$$\widetilde{B} = \frac{2 S B_{\text{GPU}}}{S/C + 2(K + O)C + (1 - \alpha) K C B_{\text{GPU}} / B_{\text{PCIe}}}$$

where `$B_{\text{GPU}} = 2$` TB/s is the A100 GPU memory bandwidth and `$B_{\text{PCIe}} = 31.5$` GB/s is the PCIe bandwidth.

**What this equation computes:** The denominator represents the effective data that must be moved to perform sparse attention on one token, broken into three terms:

1. **`$S/C$`:** The bytes of landmark data loaded from GPU memory during KV selection. With `$S = 128K$` and `$C = 8$`, this is 16K vectors × `$M$` bytes.

2. **`$2(K + O)C$`:** The bytes loaded and stored during the actual sparse attention computation on the selected `$K$` chunks and `$O$` outlier chunks. The factor of 2 accounts for reading keys and values.

3. **`$(1 - \alpha) K C B_{\text{GPU}} / B_{\text{PCIe}}$`:** The effective cost of fetching missed value chunks from CPU, weighted by the GPU-to-PCIe bandwidth ratio. The `$(1 - \alpha)$` factor accounts for the cache hit rate — with `$\alpha = 0.6$`, only 40% of value chunks need fetching. The `$B_{\text{GPU}} / B_{\text{PCIe}}$` term converts PCIe latency into the equivalent amount of GPU bandwidth that could have been used instead.

The numerator `$2 S B_{\text{GPU}}$` represents the data that would need to be moved for full attention (reading all `$S$` keys and values).

**Numerical example:** With `$C = 8$`, `$S = 128K$`, `$K = 256$`, `$O = 48$`, `$B_{\text{GPU}} = 2$` TB/s, `$B_{\text{PCIe}} = 31.5$` GB/s, and `$\alpha = 0.6$`:

$$\widetilde{B} = \frac{2 \cdot 128K \cdot 2 \text{ TB/s}}{16K + 2(256 + 48) \cdot 8 + 0.4 \cdot 256 \cdot 8 \cdot 2 \text{ TB/s} / 31.5 \text{ GB/s}}$$

Simplifying the denominator: `$16K + 4,864 + 0.4 \cdot 2,048 \cdot 63.5 \approx 16K + 4,864 + 52,019 \approx 72,883$` (in units of `$M$` bytes). The numerator is `$256K \cdot 2$` TB/s (in the same units). The resulting equivalent bandwidth is:

$$\widetilde{B} \approx 7.2 \text{ TB/s}$$

**Why this matters:** The equivalent bandwidth of 7.2 TB/s is 3.6× the A100's raw memory bandwidth of 2 TB/s. This means ShadowKV effectively operates as if it had memory that is 3.6× faster than DRAM — more than would be achievable with HBM3 or any near-term memory technology. It achieves this not through faster hardware but through **reading less data**: the sparse KV selection and low-rank compression reduce the total data accessed per attention computation by a factor proportional to the bandwidth ratio.

Crucially, this equivalent bandwidth exceeds even what would be possible with an "infinite batch size" baseline. If GPU memory were infinite, full attention could still only achieve 2 TB/s effective bandwidth because it must read the entire KV cache from memory. ShadowKV's equivalent bandwidth of 7.2 TB/s means it can achieve higher throughput than a hypothetical system with infinite GPU memory but no compression.

This is the theoretical underpinning for the paper's empirical claim in Table 3: ShadowKV "even surpass[es] infinite batch size under the assumption of infinite GPU memory." The infinite-batch baseline uses the full 2 TB/s bandwidth for attention, while ShadowKV's effective 7.2 TB/s bandwidth allows it to process more tokens per second despite having the same raw hardware.

##### Latency Breakdown in Practice

Table 13 provides the actual measured latency components during decoding for various context lengths and batch sizes. For a 24×128K configuration (24 sequences of 128K tokens each, the maximum batch size ShadowKV supports at this context length), the per-transformer-block latencies are:

- **GEMM + Softmax + Max + TopK (selection):** 0.58 + 0.07 + 0.07 + 0.15 = 0.87 ms — the landmark-based chunk selection.
- **Recompute K (overlapped):** 1.36 ms — key reconstruction from low-rank factors, running concurrently with value fetch.
- **Fetch V:** 1.66 ms — PCIe transfer of missed value chunks, running concurrently with key reconstruction.
- **Attention:** 0.21 ms — the actual sparse attention computation on the selected KV pairs.
- **FFN + QKV:** 0.29 + 0.05 = 0.34 ms — feed-forward network and query/key/value projection for the new token.

The total decode time per layer is approximately 1.42 ms when accounting for overlapping (the 0.87 ms selection + 1.66 ms for the slower of the two overlapped operations + 0.21 ms attention + 0.34 ms FFN/QKV). Without overlapping, the key reconstruction and value fetch would add serially: 0.87 + 1.36 + 1.66 + 0.21 + 0.34 = 4.44 ms, meaning the overlapping reduces decode latency by roughly 3.1×.

Notice that at longer sequences but smaller batch sizes (6×512K in the table), the latency remains roughly constant — the key reconstruction and value fetch times scale modestly because the sparse budget `$K$` is fixed, not proportional to `$S$`. This is the key to ShadowKV's scalability: doubling the context length does not double the decoding latency because only the fixed-size selection step grows slightly (more landmarks to score), while the reconstruction and fetch times are bounded by the sparse budget.

#### 3.4.5 Handling Newly Generated Tokens (ShadowKV+)

The pre-filling phase computes the low-rank projection for the input context's pre-RoPE keys. But what about the keys of tokens generated during decoding? As the output grows to thousands of tokens, their KV cache can become significant, potentially undermining the memory savings.

The paper's extension, ShadowKV+, addresses this by reusing the same low-rank projection from pre-filling for newly generated tokens. The key insight connects back to Figure 1 (middle panel): **new tokens within the same sequence share the same low-rank subspace as the original context**.

Concretely, let `$\Psi \in \mathbb{R}^{d \times r}$` be the right singular matrix computed from the SVD of the pre-filling context's pre-RoPE keys. For a newly generated token with pre-RoPE key `$k' \in \mathbb{R}^d$`, instead of storing the full `$d$`-dimensional vector, ShadowKV+ stores:

$$a' = \Psi^\top k' \in \mathbb{R}^r$$

This is the token's representation in the low-rank subspace — a vector of dimension `$r$` instead of `$d$`. When the key is needed for attention (either for subsequent tokens or, in a multi-turn setting, for a future query), it can be approximately reconstructed:

$$\hat{k}' = \Psi a' \in \mathbb{R}^d$$

The memory savings are proportional: each generated token's key cache requires `$r$` floats instead of `$d$` floats. With `$r = 160$` and `$d = 128$`, this is actually a slight *increase* for individual heads, but since `$\Psi$` is shared across all tokens in the sequence, the right singular matrix storage cost is amortized. For long output sequences (thousands of tokens), the `$r \times d$` overhead of `$\Psi$` becomes negligible compared to the per-token savings.

The value cache for generated tokens is handled similarly to the pre-filling context: it is stored on GPU initially (since generated tokens' values will be needed immediately for subsequent token generation due to the autoregressive causal mask) and can be offloaded to CPU for multi-turn scenarios.

Appendix A.1 (Tables 5 and 6) evaluates ShadowKV+ against the base ShadowKV (which stores generated tokens' full KV cache). The results show that ShadowKV+ maintains accuracy — on RULER with Llama-3-8B-1M, the average accuracy drops only from 86.88% (base ShadowKV) to 86.23% (ShadowKV+) — while providing additional memory savings for long outputs.

#### 3.4.6 Design Choices and Their Justifications: A Summary

The paper makes several non-obvious design choices that deserve explicit justification:

**Why pre-RoPE keys and not post-RoPE keys?** Because RoPE's position-dependent rotation "scrambles" the semantic subspace, making post-RoPE keys significantly less low-rank. Compressing post-RoPE keys (as Loki and InfiniGen do, either offline or with PCA) suffers a fundamental accuracy-compression tradeoff that pre-RoPE compression avoids. Figure 5 (left panel) is the smoking gun: at rank 256, pre-RoPE compression maintains ~100% accuracy while post-RoPE compression drops to ~60%.

**Why SVD and not a learned projection?** Because the low-rank subspaces are sequence-dependent (Figure 1, middle panel). An offline learned projection — whether from PCA on a calibration set (Loki) or a fixed SVD (InfiniGen) — cannot adapt to the specific subspace of each input. Online SVD computes the optimal rank-`$r$` approximation for the exact key cache being compressed, guaranteeing minimal reconstruction error in the Frobenius norm (by the Eckart-Young-Mirsky theorem).

**Why offload values instead of compressing them?** Because values are not low-rank (Figure 1, left panel). Any low-rank compression of values would be fundamentally lossy. Since values are only needed for the small fraction of tokens selected during sparse attention, offloading them and fetching on demand is more bandwidth-efficient than storing a lossy compressed version on GPU that would degrade accuracy.

**Why chunk-based selection and not token-based?** Because chunks enable efficient approximations (8× reduction in selection computation), coherent PCIe transfers (contiguous memory reads), and batched key reconstruction. The small loss in selection precision (tokens within a chunk may have varying importance) is mitigated by the outlier mechanism, which exempts chunks with high internal variance.

**Why static outlier caching and not dynamic outlier detection per query?** Because the "outlier-ness" of a chunk is a property of the key cache itself (how well the mean represents individual tokens), not a property of the query. Outliers are structural features of the context that can be detected once during pre-filling and reused for all subsequent queries. Dynamic per-query outlier detection would add latency to every decoding step without providing benefit.

**Why 48 outlier chunks and not more or fewer?** Appendix Table 15 shows the accuracy progression: 0 outliers → 74.05%, 8 outliers → 86.22%, 16 outliers → 86.42%, 32 outliers → 86.73%, 48 outliers → 86.88%. The gains saturate around 48, suggesting this captures essentially all the tokens that resist chunk-mean approximation. More outliers would add memory overhead without accuracy benefit.

**Why `$c = 8$` and `$r = 160$`?** Figure 9 (left panel) shows that chunk sizes larger than 8 degrade accuracy because the mean becomes a poorer approximation. Figure 9 (right panel) shows that rank 160 achieves near-full-rank accuracy across tasks while providing 6× compression. These values were empirically determined through the ablation studies rather than derived analytically, but they represent careful engineering tradeoffs validated across multiple models and benchmarks.

**Why the cache hit mechanism instead of just selecting and reconstructing everything each step?** Because the 60% hit rate means 60% of the work is redundant if done naively. The hit rate is a robust empirical observation (Figure 5, right panel, and Figure 9 analysis) stemming from the smooth, slowly-varying nature of attention patterns during autoregressive generation. Avoiding redundant PCIe transfers and GPU computation for hit chunks directly improves throughput.

## 4. Key Insights and Innovations

### Innovation 1: Pre-RoPE Keys as the Optimal Target for KV Cache Compression — A Diagnostic Finding That Resolves a Class of Design Mistakes

The paper's most fundamental conceptual contribution is not a compression technique but a **diagnostic observation that identifies where low-rank structure actually lives in the KV cache computation pipeline**. Prior to this work, multiple lines of research had applied low-rank approximations to KV caches — Palu (Chang et al., 2024) decomposes the KV weight matrices offline, Loki (Singhania et al., 2024) performs PCA on post-RoPE key caches, InfiniGen (Lee et al., 2024) applies offline SVD to post-RoPE key and query states, and DeepSeek-V2 (DeepSeek-AI, 2024) uses multi-head latent attention to compress post-projection KV representations. All of these methods target either the weight matrices, the post-RoPE key cache, or the full KV cache indiscriminately.

What every one of these approaches missed — and what ShadowKV's Figure 1 (left panel) makes unmistakably clear — is that the **rank structure varies dramatically depending on where in the computation pipeline you measure it**. The paper systematically visualizes the singular value decay of six distinct components: model weights $W_K$ and $W_V$, layer input $X$, pre-RoPE key cache, post-RoPE key cache, and value cache. The finding is stark: pre-RoPE keys show the sharpest singular value decay, post-RoPE keys show substantially slower decay, and values show the slowest decay of all. The quantitative consequence, shown in Figure 5 (left panel), is that compressing pre-RoPE keys to rank 256 maintains near-100% accuracy on retrieval tasks, while compressing post-RoPE keys at the same rank drops accuracy to approximately 60%.

This is not merely an empirical curiosity — it reveals a **mechanism-level explanation** for why prior low-rank KV cache methods achieved limited compression rates or suffered accuracy degradation. RoPE applies a position-dependent rotation matrix to each key vector. Before RoPE, tokens with similar semantic content produce similar key vectors regardless of their position in the sequence, creating a low-rank structure in the semantic subspace. After RoPE, each position's rotation effectively "scrambles" this structure — semantically similar tokens at different positions map to different regions of the space, flattening the singular value spectrum. This means **compression must happen before RoPE, not after** — a constraint that, to the authors' knowledge, no prior work had recognized or articulated.

The significance of this finding extends beyond ShadowKV's specific implementation. It reframes the KV cache compression problem from "can we find a compression-friendly representation?" to "**where** in the computation pipeline is the representation compression-friendly?" The answer — pre-RoPE keys — is a diagnostic that any future KV cache compression method must account for. This is a conceptual advance, not an incremental performance improvement: it identifies a design principle (compress before position embedding, not after) that prior work had violated without knowing it.

The paper reinforces this diagnostic with a second, equally non-obvious observation: the **low-rank subspaces of pre-RoPE keys are sequence-dependent** (Figure 1, middle panel). The inter-sequence subspace similarity measures only 0.75–0.80, while the intra-sequence continuation similarity measures 0.95–1.00. This means offline, data-independent low-rank projections — exactly what InfiniGen and Loki use — are structurally mismatched to any given test sequence because they capture an average subspace, not the specific subspace of the prompt at hand. The practical consequence, visible in Table 1, is that InfiniGen suffers substantial accuracy degradation on complex tasks (multi-key needle retrieval: 53.13% vs. 98.96% full attention on Llama-3-8B-1M) while ShadowKV's online, prompt-dependent SVD maintains full accuracy.

Together, these two observations — **compress pre-RoPE, not post-RoPE, and compress online, not offline** — constitute a fundamental correction to the field's approach to low-rank KV cache compression. The paper proves, through systematic comparison against multiple methods and multiple models, that violating either principle leads to significant accuracy loss, and that following both enables over 6× compression with no accuracy degradation. This is less a new algorithm than a **new understanding of the problem structure**, and its value is that it prevents future work from repeating the same design mistakes.

### Innovation 2: The Landmark-Outlier Decomposition as a Unifying Framework for Sparse Attention Selection

The second conceptual contribution is a **framework for thinking about KV cache structure that splits tokens into two qualitatively different classes** — tokens that can be well-approximated by local neighborhood statistics and tokens that cannot — and handles each class with fundamentally different mechanisms. This framework is crystallized in the landmark-outlier decomposition (Section 3.2, Figure 5 middle panel) and represents a genuine departure from how prior sparse attention methods approach token selection.

Prior sparse attention methods fall into two camps. **Position-based methods** (StreamingLLM, window attention) select tokens based on their position in the sequence — keep the first few and the last few, discard the middle — making no attempt to distinguish which intermediate tokens matter. **Score-based methods** (Quest, SparQ, Loki) compute per-token importance scores — via query-key dot products, PCA projections, or channel-norm heuristics — and select the top-scoring tokens. Both camps treat all tokens as the same type of object, differing only in estimated importance. The underlying assumption is that a single selection mechanism can work uniformly across the entire sequence.

ShadowKV's landmark analysis reveals that this assumption is **empirically false**. When the post-RoPE key cache is segmented into chunks of size 8 and the minimum cosine similarity within each chunk is computed (Figure 5, middle panel), the distribution is sharply bimodal. The vast majority of chunks (~99.7%) have high minimum similarity (>0.6), meaning every token within these chunks is well-represented by the chunk's mean vector. But a tiny fraction (~0.3%) have dramatically lower similarity — some even negative — indicating tokens whose key representations deviate sharply from their immediate neighbors. These are not just "more important" tokens in the score-based sense; they are **structurally different** — they violate the local smoothness assumption that makes the chunk-mean approximation valid.

The conceptual innovation is recognizing that these two classes require fundamentally different handling. **Landmark-compatible tokens** (the 99.7%) can be aggressively compressed: store only the chunk mean, use it to compute approximate attention scores, and reconstruct the individual tokens only when their chunk is selected. **Outlier tokens** (the 0.3%) cannot be compressed this way; their information is destroyed by the mean approximation. Instead, they must be stored losslessly and included in every attention computation — effectively a static cache that bypasses the selection mechanism entirely.

This decomposition is more than a practical trick. It provides a **diagnostic language** for understanding why prior sparse attention methods fail in specific regimes. When Quest or Loki misses an important token, the failure mode isn't just "the importance score was wrong" — it's that the token was an outlier whose importance could not be inferred from the compressed representation used for scoring. By explicitly separating outliers from the landmark-based selection pipeline, ShadowKV eliminates this failure mode without over-provisioning the sparse budget for the well-behaved majority.

The quantitative evidence supports this interpretation. Appendix Table 15 (the outlier ablation) shows that with zero outlier chunks, ShadowKV achieves 74.05% average accuracy on RULER — substantially worse than full attention (86.68%) and even worse than Quest (82.03%). With just 8 outlier chunks (0.049% of tokens), accuracy jumps to 86.22%. With 48 outliers (0.293%), it reaches 86.88%. The fact that fewer than 0.3% of tokens account for essentially all the accuracy gap between the pure landmark approximation and full attention demonstrates that the landmark-outlier decomposition is not just effective but **conceptually correct**: the tokens that resist local approximation really are the ones that matter most for attention quality.

This finding has implications beyond ShadowKV. It suggests that future sparse attention methods should not treat all tokens as exchangeable objects with varying importance scores, but should instead **classify tokens by compressibility type** and apply different mechanisms accordingly. This is a reframing of the sparse attention problem from a 1D selection problem (which tokens to keep) to a 2D problem (which compression strategy to apply to each token, based on its local structure). The landmark-outlier decomposition is one instance of this approach; future work might identify additional token classes with different structural properties.

### Innovation 3: Theoretical Equivalent Bandwidth as a Conceptual Tool for Reasoning About System Design Tradeoffs

The paper's third distinctive contribution is a **conceptual model — the theoretical equivalent bandwidth — that unifies GPU memory capacity, GPU memory bandwidth, and PCIe bandwidth into a single figure of merit** for KV cache compression systems. This model makes explicit what prior systems work left implicit: the end-to-end throughput of a hybrid GPU-CPU inference system is determined not by any single hardware bottleneck but by the interaction of compression ratio, selection accuracy, and the ratio of GPU to PCIe bandwidth.

The idea of "equivalent bandwidth" is not entirely new — FlashAttention (Dao et al., 2022) made similar arguments about IO-aware algorithms achieving effective bandwidth beyond raw DRAM speeds — but ShadowKV **extends this reasoning to the GPU-CPU hybrid setting** in a way that captures the specific tradeoffs of CPU-offloaded KV caches. The model (Section 4.2) expresses equivalent bandwidth as:

$$\widetilde{B} = \frac{2 S B_{\text{GPU}}}{S/C + 2(K + O)C + (1 - \alpha) K C B_{\text{GPU}} / B_{\text{PCIe}}}$$

where the denominator's three terms represent, respectively, the cost of reading landmarks for KV selection, the cost of performing sparse attention on the selected tokens, and the cost of fetching missed value chunks from CPU (weighted by the GPU-to-PCIe bandwidth ratio to convert PCIe latency into GPU-bandwidth-equivalent terms).

This equation is not deeply mathematically novel. What makes it a genuine conceptual contribution is that it **isolates the key architectural parameters that determine whether a CPU-offloaded sparse attention system can outperform full on-GPU attention**. The model reveals that:

1. **The cache hit rate $\alpha$ is a first-order term.** With $\alpha = 0.6$, only 40% of the selected value chunks need PCIe fetching, reducing the third denominator term by 2.5×. Without the cache mechanism, this term would dominate, and the equivalent bandwidth would drop substantially.

2. **The GPU-to-PCIe bandwidth ratio ($B_{\text{GPU}} / B_{\text{PCIe}} \approx 63.5$ on A100) magnifies the cost of PCIe transfers.** Even a small number of PCIe-fetched bytes gets weighted heavily in GPU-bandwidth-equivalent terms. This explains why ShadowKV's choice to **only fetch values, not keys** (since keys are reconstructed from low-rank factors on GPU) is structurally advantageous — it halves the PCIe data transfer compared to fetching full KV pairs.

3. **The chunk size $C$ has competing effects.** Larger chunks reduce the landmark-reading cost (fewer landmarks to score) but increase both the sparse attention cost (more tokens per selected chunk) and the PCIe cost (more bytes per fetched chunk). The model explains why $C = 8$ is the sweet spot — it balances these terms.

The model's value is primarily **explanatory, not predictive**. It doesn't predict the exact throughput ShadowKV will achieve (that requires empirical measurement with specific CUDA kernels and hardware), but it **explains why ShadowKV achieves the throughput it does** and, crucially, **identifies which factors future work should optimize**. For instance, the model shows that improving the cache hit rate $\alpha$ (currently 60%) would directly improve equivalent bandwidth by reducing PCIe transfers, while increasing the chunk size $C$ would have ambiguous effects depending on the relative magnitudes of the three denominator terms.

The paper's claim that ShadowKV achieves 7.2 TB/s equivalent bandwidth — 3.6× the A100's raw 2 TB/s memory bandwidth — is a striking illustration of the model's implications. It means that **bandwidth-efficient algorithms can effectively "create" faster memory through data reduction**, and that the hardware memory bandwidth is not a hard ceiling if you can avoid reading most of the data. This is a systems-level insight that generalizes beyond KV caches to any scenario where a small fraction of a large dataset is accessed per operation.

The model also explains the apparently paradoxical claim in Table 3 that ShadowKV "surpass[es] infinite batch size under the assumption of infinite GPU memory." The infinite-batch baseline uses the full 2 TB/s bandwidth for attention — it can read from an infinitely large KV cache at 2 TB/s, but it must still read all of it. ShadowKV, by reading only a tiny fraction of the KV cache, achieves an effective bandwidth of 7.2 TB/s, which translates to higher throughput even though the raw hardware is identical. This reframes the throughput problem from "how much memory do we have?" to "how efficiently do we use the bandwidth we have?" — a conceptual shift with direct implications for hardware-software co-design.

### Innovation 4: The Demonstration That Test-Time KV Cache Sparsity and Compression Are Sufficient to Match Full Attention Across Diverse, Realistic Benchmarks

While not a theoretical advance, the paper's **empirical demonstration of accuracy retention under extreme compression and sparsity** constitutes a distinct contribution because it establishes a new capability frontier that prior work had not credibly reached. The claim is specific: ShadowKV matches full attention accuracy on the RULER, LongBench, and Needle In A Haystack benchmarks across six different long-context models (Llama-3.1-8B, Llama-3-8B-1M, GLM-4-9B-1M, Yi-9B-200K, Phi-3-Mini-128K, Qwen2-7B-128K) at contexts up to 1M tokens, using only a 1.56% sparse KV budget and 6× key cache compression, while simultaneously reducing GPU memory footprint by over 7×.

Prior work made accuracy claims on narrower evaluation scopes. StreamingLLM (Xiao et al., 2023) demonstrated accuracy on language modeling perplexity and simple retrieval but was not evaluated on complex multi-hop reasoning or multi-document QA. H2O (Zhang et al., 2023) showed results on standard benchmarks like CNN/DailyMail and XSum, which have much shorter contexts than modern long-context LLM evaluation suites. InfiniGen (Lee et al., 2024) was evaluated primarily on retrieval tasks and showed accuracy degradation on more complex benchmarks. Quest (Tang et al., 2024) achieved strong accuracy but retained the full KV cache on GPU, meaning its accuracy claims were made under conditions that don't address the memory bottleneck.

What distinguishes ShadowKV's empirical contribution is the **combination of (1) extreme compression ratios, (2) diverse and challenging benchmarks, (3) multiple model families, and (4) context lengths scaling to 1M tokens**. The RULER benchmark is particularly demanding because it includes multi-key needle retrieval (where the model must find multiple pieces of information scattered across the context), multi-hop tracking (where information must be aggregated across variable numbers of hops), and aggregation tasks — all of which are sensitive to KV cache sparsity because missing a single relevant token can break the reasoning chain. The fact that ShadowKV maintains 97.92% on multi-key needle retrieval (N-MK2 on Llama-3-8B-1M, Table 1) while using only 1.56% of the KV cache — and that InfiniGen degrades to 53.13% on the same task — is evidence that the combination of low-rank pre-RoPE compression, online SVD, and outlier preservation captures genuinely important information rather than just surface-level statistical patterns.

The LongBench results (Table 1, right side) extend this demonstration to a different class of tasks: single-document QA, multi-document QA, document summarization, code completion, and information retrieval. These tasks stress different attention patterns — summarization requires broad context, code completion requires precise local matches, multi-document QA requires cross-document reasoning. ShadowKV maintains accuracy within 1 percentage point of full attention on the aggregate score across all nine LongBench subtasks for all four models tested — a level of consistency that prior sparse methods did not demonstrate.

The Needle In A Haystack results (Figure 6, Appendix Figure 11) further show that performance is maintained across all needle depths and context lengths, with ShadowKV occasionally even *outperforming* full attention (as noted for Yi-9B-200K). This is not claimed as a systematic benefit — the paper is careful not to argue that sparsity improves accuracy — but it demonstrates that the sparse selection is not introducing systematic biases against information at particular positions.

The multi-turn conversation experiment (Figure 7) is particularly revealing because it exposes a failure mode of eviction-based methods that ShadowKV avoids. SnapKV and StreamingLLM permanently discard tokens based on their importance to the first-turn query, so when a second-turn query requires different tokens, those tokens are gone and accuracy drops sharply (SnapKV falls from ~80% to ~20% by turn 3). ShadowKV retains the ability to access any token through on-demand reconstruction, so accuracy remains stable across turns. This demonstrates that ShadowKV's accuracy claims are not just about single-turn benchmarks — they extend to the interactive, multi-query scenarios that characterize real-world LLM applications.

This empirical contribution matters because it **shifts the burden of proof** for future KV cache compression work. Prior to ShadowKV, it was plausible to argue that aggressive compression and sparsity inevitably trade off against accuracy and that the best one could do was to minimize the degradation. ShadowKV demonstrates that this tradeoff is not fundamental — with the right compression target (pre-RoPE keys), the right decomposition (online SVD), and the right handling of structural outliers, it is possible to achieve memory reduction and throughput gains *without* accuracy loss across a broad evaluation suite. This raises the bar for subsequent methods: the claim to beat is no longer "better than eviction" but "matches full attention."

### Innovation 5: The Implicit Insistence That KV Cache Compression Must Be Evaluated as a Full-Stack System, Not a Model-Level Operation

A final, more subtle contribution is the paper's **reframing of KV cache compression from a model-level accuracy problem to a full-stack systems problem**. This is not articulated as a headline claim but is embodied in the paper's structure: accuracy results (Section 5.1), throughput results (Section 5.2), and ablation studies (Section 5.3) are treated as co-equal, and the "contributions" are not limited to the compression algorithm but encompass the entire pipeline — overlapping CUDA streams, cache hit mechanisms, fused kernels, landmark-based selection, and value offloading.

Prior work on KV cache compression largely separated "algorithm" and "system." H2O and SnapKV proposed eviction policies and evaluated them in terms of accuracy on benchmarks, leaving the throughput implications to be addressed by separate systems work. InfiniGen (OSDI 2024) is a systems paper but treated the SVD-projection-based KV selection as essentially a pre-processing step. Quest proposed a page-based selection algorithm and measured both accuracy and latency, but did not address the memory bottleneck, meaning its latency gains are bounded by the batch size that fits in GPU memory.

ShadowKV integrates these concerns by **designing the compression and selection algorithms with explicit awareness of the hardware constraints that will execute them**. The choice of chunk size $C = 8$ is driven not just by approximation quality but also by the need for contiguous PCIe reads. The choice to reconstruct keys from low-rank factors rather than fetching them from CPU is driven by the 63.5:1 GPU-to-PCIe bandwidth ratio. The cache hit mechanism is a systems optimization that would not be motivated by accuracy alone — it exploits a property of decoder attention patterns (temporal locality) that is invisible to per-sample accuracy metrics. The entire architecture is a **co-design** where algorithmic choices (rank $r$, chunk size $C$, sparse budget $K$, number of outliers $O$) are tuned jointly with system parameters (PCIe bandwidth, GPU memory bandwidth, CUDA stream concurrency) rather than optimized independently.

This reframing has methodological implications. It implies that KV cache compression methods cannot be fairly compared on accuracy alone — a method that achieves higher accuracy at the same sparse budget but requires random-access PCIe reads (which are much slower than contiguous reads) may be practically worse than a method with slightly lower accuracy but more efficient data access patterns. ShadowKV's approach of reporting **both accuracy and throughput at realistic batch sizes** (Tables 3 and 4) sets a standard that future work should follow.

The concept of **theoretical equivalent bandwidth** (Innovation 3) is the intellectual tool that makes this co-design possible, because it provides a common language for reasoning about how algorithmic choices affect system-level performance. But the broader contribution is the **demonstration that this co-design approach works**: by jointly optimizing across the algorithm-systems boundary, ShadowKV achieves throughput gains (3.04×) that would be impossible through algorithmic improvements alone (which would hit the PCIe wall) or systems improvements alone (which would hit the accuracy wall). This is a methodological lesson for the field, not just a specific system.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** ShadowKV is evaluated on three long-context benchmarks: **RULER** (Hsieh et al., 2024) — 13 complex tasks including multi-key needle retrieval, multi-hop tracking, variable tracking, frequent word extraction, and QA, with adjustable context lengths up to 1M tokens; **LongBench** (Bai et al., 2023) — 21 diverse tasks across 6 categories including single-/multi-document QA, summarization, code completion, and information retrieval, with samples filtered to those exceeding 4K tokens for the main evaluation; and **Needle In A Haystack (NIAH)** (Kamradt, 2023) — a retrieval benchmark testing whether models can locate information at various positions within contexts ranging from 16K to 1M tokens. Additionally, **InfiniteBench** (Zhang et al., 2024) — 10 tasks averaging 214K tokens in length — is evaluated in Appendix B.4. The RULER test sets use 128K contexts for the main comparison and scale from 8K to 256K for the MInference integration experiment.

- **Base model(s).** Six long-context models spanning different architectures and context windows: **Llama-3-8B-1M** (Gradient, 2024, based on Llama-3-8B extended to 1M context), **GLM-4-9B-1M** (GLM Team, 2024, 1M context), **Llama-3.1-8B** (Meta AI, 2024, 128K context), **Yi-9B-200K** (01.AI, 2024, 200K context), **Phi-3-Mini-128K** (Abdin et al., 2024, 128K context), and **Qwen2-7B-128K** (Yang et al., 2024, 128K context). The paper also evaluates **Llama-3-70B-1M** on 512K contexts in Appendix A.5 for scalability testing. These models are chosen to span a representative range of architectures (grouped-query attention with varying numbers of KV heads: 8 for Llama-3, 4 for GLM-4 and Yi-9B) and context lengths, testing ShadowKV's generality beyond a single model family.

- **Metrics.** **Accuracy on downstream benchmarks**: For RULER, per-task and average accuracy across all 13 subtasks at 128K context length (Table 1). For LongBench, per-subtask accuracy on samples longer than 4K and aggregate average across subtasks (Table 1). For NIAH, retrieval accuracy at each (context length, depth percent) combination, visualized as heatmaps (Figure 6, Appendix Figure 11). For InfiniteBench, per-task accuracy (Appendix Table 16). **Throughput during decoding**: Tokens generated per second across all sequences in a batch, measured by executing the full model end-to-end on an A100 GPU (Tables 3 and 4). **Batch size scaling**: Maximum batch size supported under the GPU memory constraint, reported as the scaling factor relative to the full-attention baseline (Table 4, Figure 9 left panel). **Latency breakdown**: Per-component time in milliseconds for a single transformer block during pre-filling and decoding, measured at various context lengths and batch sizes (Tables 12 and 13 in Appendix A.6).

- **Baselines.** Three dynamic sparse attention methods are compared: **Quest** (Tang et al., 2024) — segments tokens into pages, selects pages by approximating maximum attention within each page via chunk-level max and min operations; **Loki** (Singhania et al., 2024) — performs PCA on key caches using a calibration dataset, selecting tokens based on attention scores computed in low-dimensional space; and **InfiniGen** (Lee et al., 2024) — offloads entire KV cache to CPU and prefetches predicted important entries using precomputed offline SVD projections. Each baseline is tested in two variants: one where the full KV cache (keys and values) is offloaded to CPU (matching ShadowKV's GPU memory reduction), and another marked "(V)" where only the value cache is offloaded (matching ShadowKV's sparse budget but consuming more GPU memory for the key cache). Additionally, two eviction-based methods — **SnapKV** (Li et al., 2024) and **StreamingLLM** (Xiao et al., 2023) — are compared on the multi-turn NIAH experiment (Figure 7). For throughput experiments, the **Full Attention** baseline uses FlashAttention with the largest batch size that fits entirely in GPU memory, and an **Infinite Batch Size** baseline simulates unlimited GPU memory by evaluating a single transformer block and projecting throughput using the A100's theoretical memory bandwidth of 2 TB/s for attention computations (Table 3).

- **Generation budget / compute accounting.** The primary budget parameter is the **sparse KV cache budget**, expressed as a percentage of the total KV cache or as the number of selected chunks `$k$`. For the main experiments, ShadowKV uses a **1.56% sparse budget** (256 chunks of size 8 for 128K-token contexts, totaling 2,048 tokens selected per head per decoding step, plus 48 outlier chunks of 384 tokens). For LongBench, which has shorter inputs, the sparse budget is set to 256 chunks. The paper sweeps sparse budgets from 0.2% to 100% in the ablation study (Figure 8). The **SVD rank** is fixed at `$r = 160$`, **chunk size** at `$c = 8$`, and **number of outlier chunks** at `$o = 48$` for main experiments. All methods are compared at equivalent sparse budgets: baselines are configured so that "the computation cost is set to 1/16 of full attention for selecting sparse KV pairs" (Section 5.1). For throughput measurements, batch sizes are chosen as the maximum that fit in GPU memory for each method and context length configuration.

- **Cross-validation / statistical protocol.** No cross-validation or statistical significance testing is reported. The RULER and LongBench results are single-run evaluations on standard test sets. The NIAH heatmaps are generated from single-run retrieval tests at each (context length, depth) combination. For ablation studies, accuracy is measured as single-run performance on the specified benchmarks. The paper does not report confidence intervals, standard deviations, or statistical tests for any result.

### Main Quantitative Results

#### Accuracy on Long-Context Benchmarks (RULER, LongBench, NIAH)

**Headline finding: ShadowKV matches full attention accuracy while using only 1.56% of the KV cache per decoding step, consistently outperforming all dynamic sparse attention baselines at the same sparse budget across four model families on both RULER and LongBench.**

**RULER results at 128K contexts (Table 1, left side).** On Llama-3-8B-1M, full attention achieves an average accuracy of 86.68% across all 13 RULER subtasks. ShadowKV, with a 1.56% sparse budget, achieves **86.88%** — essentially identical, and marginally higher than full attention (a 0.20 percentage point difference). By contrast, the best baseline variant — Quest with only value offloading (Quest V) — achieves 83.99%, representing a 2.69 percentage point degradation from full attention. InfiniGen with value offloading (InfiniGen V) achieves 78.31%, an 8.37 point degradation. Loki with value offloading achieves only 24.46%.

The per-task breakdown reveals where the baselines fail and ShadowKV succeeds. On the multi-key needle retrieval tasks that are most sensitive to KV cache sparsity:

- **N-MK2 (multi-key needle retrieval with 2 keys):** Full attention achieves 98.96%. ShadowKV achieves **98.96%** — a perfect match. InfiniGen drops to 53.13%, InfiniGen V to 76.04%, Quest to 77.08%, and Quest V to 85.42%. The gap is dramatic: InfiniGen loses nearly half the accuracy on this task while ShadowKV loses none.
- **N-MK1 (multi-key needle retrieval with 1 key):** Full attention 98.96%. ShadowKV **97.92%** (1.04 point drop). Quest maintains 98.96%, but InfiniGen drops to 84.38%.

On aggregation tasks requiring broad context:

- **N-MV (multi-value retrieval):** Full attention 95.57%. ShadowKV **95.83%** (matching full attention). Quest achieves 93.49%, Quest V 95.49%, InfiniGen 54.95%, InfiniGen V 77.08%.
- **QA-1:** Full attention 75.00%. ShadowKV **72.92%** (2.08 point drop). Quest achieves 60.42%, Quest V 70.83%.
- **QA-2:** Full attention 48.96%. ShadowKV **52.08%** (3.12 point improvement over full attention). Quest achieves 50.00%, Loki 13.54%.

On variable tracking:

- **VT:** Full attention 78.54%. ShadowKV **81.67%** — a 3.13 point improvement over full attention. This improvement is consistent with the paper's observation that sparse attention can act as a regularizer, filtering irrelevant context.

On GLM-4-9B-1M, the pattern holds: full attention achieves 86.82%, ShadowKV achieves **85.62%** (1.20 point drop), while Quest V achieves 81.47% (5.35 point drop) and InfiniGen V achieves 72.91% (13.91 point drop). On Llama-3.1-8B: full attention 85.53%, ShadowKV **83.57%** (1.96 point drop), Quest V 79.72% (5.81 point drop), InfiniGen V 68.76% (16.77 point drop). On Yi-9B-200K (Table 7 in Appendix A.3): full attention 65.73%, ShadowKV **65.53%** (0.20 point drop), Quest V 61.36%, InfiniGen V 54.69%.

A notable pattern: ShadowKV's relative advantage over baselines is larger on models with fewer KV heads. On GLM-4 and Yi-9B (4 KV heads), the gap between ShadowKV and Quest V is 4.25 and 4.17 percentage points respectively. On Llama-3 variants (8 KV heads), the gap is 3.11 and 3.85 points. The paper notes this in Section 5.2: "the gains for GLM-4-9B-1M and Yi-9B-200K are slightly lower, the improvements still reach up to 2.56× and 2.66× respectively, highlighting ShadowKV's adaptability even with fewer KV heads." The accuracy pattern suggests ShadowKV's selection mechanism is robust regardless of head count, while baseline selection quality may degrade with fewer, more heavily loaded KV heads.

**LongBench results (Table 1, right side).** On Llama-3-8B-1M, full attention averages 39.86% across the nine LongBench subtasks. ShadowKV achieves **39.94%** — essentially identical. Quest V achieves 38.17% (1.69 point drop), InfiniGen V 35.00% (4.86 point drop), Loki V 21.74%.

On GLM-4-9B-1M: full attention 48.24%, ShadowKV **47.89%** (0.35 point drop), Quest V 43.68%, InfiniGen V 44.62%. On Llama-3.1-8B: full attention 48.96%, ShadowKV **48.13%** (0.83 point drop), Quest V 46.81%, InfiniGen V 46.18%.

The per-subtask results show ShadowKV maintaining accuracy across diverse task types. On HotpotQA (multi-hop QA), ShadowKV achieves 38.29% vs. 36.79% full attention on Llama-3-8B-1M — a small improvement. On LCC (code completion), ShadowKV achieves 63.93% vs. 56.07% full attention — a substantial 7.86 point improvement. The paper does not explore why code completion specifically benefits from sparse attention, but it may relate to code having high local redundancy where sparse selection successfully filters irrelevant context.

On PassRetr (passage retrieval), ShadowKV achieves 80.00% vs. 81.50% full attention — a small degradation. On SAMSum (summarization), ShadowKV achieves 35.87% vs. 35.96% — essentially identical. The consistency across these qualitatively different tasks (summarization requires broad context, code completion requires precise local matches, retrieval requires identifying specific passages) demonstrates that ShadowKV's selection mechanism is not biased toward any particular attention pattern.

**NIAH results across context lengths (Figure 6, Appendix Figure 11).** For Llama-3-8B-1M with ShadowKV, the NIAH heatmap at contexts from 16K to 1M tokens shows retrieval accuracy near 100% across essentially all context lengths and needle depths. There is a small degradation at 1M tokens at certain depth percentages (the heatmap shows some lighter-shaded cells indicating retrieval failures), but the vast majority of positions maintain full accuracy. The paper does not quantify the exact accuracy at 1M, but the heatmap visual inspection suggests it remains above 90% for most positions.

For GLM-4-9B-1M, Llama-3.1-8B, Yi-9B-200K, Phi-3-Mini-128K, and Qwen2-7B-128K (Appendix Figure 11), ShadowKV's heatmaps are essentially indistinguishable from the full attention heatmaps across all tested context lengths (up to 1M for GLM-4, up to 128K or 200K for the other models). The Yi-9B-200K heatmap shows "even a slight performance improvement" with ShadowKV compared to full attention — the paper notes this in Appendix B.3 but does not quantify the improvement.

**Multi-turn conversation capability (Figure 7).** The multi-turn NIAH experiment simulates 8 conversation turns where each turn requires retrieving a different needle from the context. Full attention maintains near-100% accuracy across all turns. ShadowKV also maintains near-100% accuracy across all turns, with no visible degradation. In contrast:

- **SnapKV** drops from ~80% accuracy on turn 1 to ~20% by turn 3, and continues declining to near 0% by turn 8. This is the catastrophic failure mode of eviction: tokens evicted after turn 1 can never be recovered for later turns.
- **StreamingLLM** drops even more sharply, from ~60% on turn 1 to ~10% by turn 2, and stays below 20% for subsequent turns. StreamingLLM's fixed policy of keeping attention sinks and recent tokens is even more brittle to multi-turn scenarios where the needed information varies across turns.

This result demonstrates that ShadowKV is functionally equivalent to full attention for interactive, multi-query use cases — a property that eviction-based methods fundamentally cannot provide because their discarded information is permanently lost.

#### Throughput and Batch Size Scaling

**Headline finding: ShadowKV supports up to 6× larger batch sizes and boosts decoding throughput by up to 3.04× compared to full attention at a small batch size, surpassing the throughput achievable with a hypothetical infinite GPU memory.**

**Throughput scaling across models and context lengths (Table 3).** On Llama-3.1-8B at 60K context length, full attention achieves 160.93 tokens/s with a batch size of 8 (the maximum that fits in GPU memory). ShadowKV supports a batch size of 48 (6× larger) and achieves **472.77 tokens/s** — a 2.94× throughput increase. The "Full Attn (Inf)" column — representing the hypothetical throughput if GPU memory were infinite but attention still required reading the full KV cache at 2 TB/s — achieves 168.72 tokens/s at batch size 48 and 273.07 tokens/s at infinite batch size. ShadowKV at 472.77 tokens/s substantially exceeds both, demonstrating that bandwidth efficiency (reading less data) matters more than memory capacity for throughput.

At 122K context length, the gains are even larger: full attention achieves 80.78 tokens/s (batch size 4), ShadowKV achieves **245.90 tokens/s** (batch size 24, a 6× increase) — a 3.04× throughput gain. The infinite batch baseline achieves only 134.30 tokens/s, again well below ShadowKV. This validates the theoretical equivalent bandwidth analysis: by reading only 1.56% of the KV cache, ShadowKV's effective bandwidth of 7.2 TB/s (computed in Section 4.2) translates directly to throughput exceeding what infinite memory at 2 TB/s can deliver.

On Llama-3-8B-1M at 60K: 160.62 → **455.14 tokens/s** (2.83× gain). At 122K: 80.77 → **239.51 tokens/s** (2.97×). At 244K: 40.37 → **119.01 tokens/s** (2.95×). The multiplicative gain is remarkably stable across context lengths, suggesting ShadowKV's overhead scales in proportion to the full attention cost.

On GLM-4-9B-1M, the gains are slightly lower: at 60K, 241.05 → **615.89 tokens/s** (2.56×); at 122K, 122.67 → **293.40 tokens/s** (2.39×); at 244K, 61.13 → **136.51 tokens/s** (2.23×). The paper attributes this to GLM-4's architecture having only 4 KV heads (vs. 8 for Llama-3), meaning each KV head carries more tokens, and the sparse selection's overhead constitutes a larger fraction of total compute. On Yi-9B-200K (also 4 KV heads): at 60K, 204.81 → **544.36 tokens/s** (2.66×); at 122K, 101.44 → **260.03 tokens/s** (2.56×); at 244K, 46.74 → **118.55 tokens/s** (2.54×).

**Batch size scaling with sequence length (Table 4).** Table 4 provides a detailed view of how batch size scales under ShadowKV vs. full attention for Llama-3-8B-1M at context lengths from 60K to 488K:

- **At 60K:** Full attention supports batch sizes up to 8 (160.62 tokens/s). ShadowKV scales smoothly from batch size 2 (89.69 tokens/s) to 48 (455.14 tokens/s), with throughput continuing to increase at every step. Full attention runs out of memory (OOM) at batch size 12.
- **At 122K:** Full attention supports batch sizes 2-4 only (65.12 to 80.77 tokens/s), OOM beyond 4. ShadowKV scales from batch size 2 (65.61 tokens/s) to 24 (239.51 tokens/s), OOM beyond 24.
- **At 244K:** Full attention supports only batch size 2 (40.37 tokens/s), OOM beyond 2. ShadowKV scales from batch size 2 (48.39 tokens/s) to 12 (119.01 tokens/s), OOM beyond 12.
- **At 488K:** Full attention cannot support even batch size 1 (OOM). ShadowKV supports batch sizes 2-5 (29.82 to 53.46 tokens/s), OOM beyond 5.

The throughput at batch size 2 under ShadowKV consistently exceeds full attention even when both support the same batch size (e.g., at 244K: 48.39 vs. 40.37 tokens/s) — because sparse attention has lower per-token latency even at the same batch size, due to the reduced attention computation. This means ShadowKV provides throughput benefits even when batch size is constrained by factors other than KV cache memory (e.g., request rate).

**Efficiency at 1M contexts (Appendix A.7, Table 14).** At 1M context length with batch size 3, full attention cannot fit in GPU memory (OOM). Full attention with CPU offloading achieves a mere 0.21 tokens/s, crippled by PCIe bandwidth. Quest with CPU offloading achieves 9.34 tokens/s — better but still slow, because fetching full KV pairs over PCIe dominates. ShadowKV achieves **45.32 tokens/s** — a 4.85× improvement over Quest with CPU offloading, and 216× improvement over full attention with CPU offloading. This demonstrates that at extreme context lengths where CPU offloading is unavoidable, ShadowKV's architecture (fetching only values, overlapping with key reconstruction, caching hits) provides compound benefits that simple sparse selection plus offloading cannot match.

#### Integration with Pre-Filling Optimization (MInference)

**Headline finding: ShadowKV is compatible with efficient pre-filling methods, maintaining accuracy when combined with MInference's dynamic sparse attention during pre-filling (Table 2).**

On RULER with Llama-3-8B-1M and MInference-enabled pre-filling, full attention achieves an average accuracy of 81.98% across context lengths from 8K to 256K. ShadowKV combined with MInference achieves **82.04%** — a marginal 0.06 percentage point improvement. At individual context lengths, the accuracies are: 90.47% vs. 89.92% at 8K, 88.12% vs. 88.02% at 16K, 83.28% vs. 82.81% at 32K, 77.71% vs. 78.45% at 64K, 78.32% vs. 78.12% at 128K, and 74.31% vs. 74.57% at 256K. The differences are all within 1 percentage point and show no systematic bias — sometimes ShadowKV slightly improves, sometimes it slightly degrades.

This result is important for practical deployment because MInference addresses the pre-filling latency bottleneck (which ShadowKV does not optimize), while ShadowKV addresses the decoding throughput bottleneck. The compatibility demonstrates that these two optimizations target orthogonal costs in the inference pipeline and can be combined without interference.

#### Precision Sensitivity

**Headline finding: ShadowKV maintains accuracy when KV cache and model weights use FP8 precision instead of BF16 (Appendix Tables 9 and 10).**

On RULER with Llama-3-8B-1M at 128K and FP8 precision, full attention drops from 86.68% (BF16) to 84.94% (FP8) — a 1.74 point degradation from the reduced precision itself. ShadowKV in FP8 achieves **85.95%** — actually 1.01 points higher than full attention in FP8, and only 0.73 points below full attention in BF16. Quest V in FP8 achieves 83.88% (1.06 points below full attention FP8).

On LongBench with FP8, full attention achieves 39.49%, ShadowKV achieves **39.25%** (0.24 point drop), Quest V achieves 36.76%. The pattern is consistent: ShadowKV's relative advantage over baselines is preserved under reduced precision, and the absolute accuracy degradation from FP8 is modest (~1-2 points).

This robustness is non-obvious because SVD computation is sensitive to numerical precision — FP8's reduced dynamic range (5 exponent bits, 2 mantissa bits) could in principle cause the low-rank decomposition to lose significant information beyond the truncation error. The results suggest either that the pre-RoPE key cache's low-rank structure is sufficiently robust to survive FP8 quantization, or that the SVD is being computed in higher precision and only the stored factors use FP8. The paper does not clarify the precision of the SVD computation itself.

### Ablation Studies and Robustness Checks

**Sparse KV cache budget (Figure 8):** ShadowKV's accuracy is evaluated across sparse budgets from 0.2% to 100% (full attention) on multiple RULER subtasks for Llama-3-8B-1M and GLM-4-9B-1M. On multi-key NIAH for Llama-3-8B-1M, ShadowKV maintains near-1.0 accuracy at all budgets down to 1.56%, with a small dip to ~0.95 at 0.78% and a sharp decline below 0.39%. Quest at the same budget drops to ~0.7 at 1.56% and degrades more rapidly at lower budgets. On QA, ShadowKV maintains ~0.7 accuracy from 100% down to 1.56% (actually increasing slightly to ~0.72 at 1.95%), while Quest declines from ~0.7 to ~0.5 over the same range. On variable tracking, ShadowKV at 1.56% achieves ~0.86 (marginally above full attention's ~0.84), while Quest at 1.56% achieves ~0.72. On frequent words extraction, ShadowKV maintains ~0.71 at 1.56% (matching full attention), while Quest achieves ~0.63. The consistent pattern is that ShadowKV's accuracy remains flat or slightly improves as the budget decreases to 1.56%, while Quest's accuracy degrades monotonically. The GLM-4-9B-1M results show the same pattern, confirming the finding across model architectures. The 1.56% budget is thus empirically validated as a safe operating point where accuracy matches full attention.

**Chunk size (Figure 9, left panel):** Chunk size is swept from 1 to 64, measuring both the batch size scaling factor and the chunk hit rate. The batch size scaling factor increases monotonically with chunk size — from ~1× at chunk size 1 to ~8× at chunk size 64 — because fewer landmarks mean less memory and faster selection. However, the paper notes that "accuracy declines when the chunk size exceeds eight" (Section 5.3), though the specific accuracy numbers for each chunk size are not provided in the figure — the right y-axis shows hit rate (remaining around 60% for chunk sizes 2 through 64, dropping slightly to ~50% at chunk size 1), not accuracy. The accuracy degradation at larger chunk sizes is attributed to the chunk mean becoming a poorer approximation for individual tokens, causing the landmark-based selection to miss important tokens within selected chunks or select irrelevant chunks. The choice of chunk size 8 represents the sweet spot where accuracy is maintained (as validated by the main benchmark results) while enabling substantial batch size scaling.

**Rank of pre-RoPE key cache (Figure 9, right panel):** SVD rank is swept from 0 to 1000 for Llama-3-8B-1M on multiple RULER subtasks. Accuracy on NIAH-S (single-key needle retrieval) reaches ~0.95 at rank 160 and plateaus, with essentially no improvement beyond rank 200. NIAH-MK (multi-key) reaches near-1.0 at rank 160. NIAH-MQ (multi-query) reaches ~1.0 at rank 160. FWE (frequent words extraction) shows increasing accuracy up to rank 400, but the gains from 160 to 400 are modest (~0.72 to ~0.76). QA shows accuracy increasing from ~0.4 at rank 0 to ~0.7 at rank 160, with continued but diminishing improvements up to rank 1000. The paper states that "accuracy increases with the rank up to approximately 160, after which it stabilizes near full-rank performance." The key observation is that "trends vary across tasks, and in some cases, low-rank approximations achieve better performance" — a finding the paper notes but does not explore further. This could indicate that SVD-based compression acts as a denoising mechanism for certain attention patterns, filtering out high-frequency components that contribute to spurious correlations.

**Number of outlier chunks (Appendix Table 15):** The number of outlier chunks `$o$` is swept from 0 to 48 on RULER with Llama-3-8B-1M at 128K. With 0 outliers, average accuracy is 74.05% — substantially below full attention (86.68%) and even below Quest (82.03%). With 1 outlier chunk (0.006% of tokens), accuracy jumps to 85.01%. With 8 outliers (0.049%), accuracy reaches 86.22% — already within 0.46 points of full attention. With 48 outliers (0.293%), accuracy reaches 86.88% — essentially matching full attention. The per-task breakdown reveals that the most outlier-sensitive tasks are the complex reasoning tasks: N-MK2 improves from 85.42% (0 outliers) to 98.96% (48 outliers), N-MQ from 73.18% to 96.88%, VT from 73.54% to 81.67%. Simple retrieval (N-S1, N-S2) maintains 100% accuracy regardless of outlier count. This ablation is crucial because it quantifies the contribution of the landmark-outlier decomposition — without outliers, the pure landmark-based approximation underperforms even Quest's min-max approach, but with just 0.3% of tokens preserved as outliers, the approximation matches full attention.

**Outlier detection mechanism:** The ablation table implicitly validates that outlier detection via minimum within-chunk cosine similarity is effective — the large accuracy jump from 0 to 1 outlier (74.05% → 85.01%) shows that identifying even the single worst-approximated chunk captures disproportionately important information. The diminishing returns beyond 16–32 outliers (86.42% at 16, 86.73% at 32, 86.88% at 48) confirm that the cosine similarity metric successfully ranks chunks by their impact on attention quality, with the top-ranked outliers accounting for most of the accuracy recovery.

**ShadowKV+ (low-rank projection for generated tokens, Appendix Tables 5 and 6):** The extended variant that applies the same low-rank projection to newly generated tokens shows minimal accuracy impact. On RULER with Llama-3-8B-1M, ShadowKV achieves 86.88% average, ShadowKV+ achieves 86.23% (0.65 point drop). On GLM-4-9B-1M: 85.62% → 85.63% (no change). On Llama-3.1-8B: 83.57% → 83.47% (0.10 point drop). On Yi-9B-200K: 65.53% → 65.41% (0.12 point drop). On LongBench, the differences are similarly small (within 0.5 percentage points on average across all models). This validates the paper's claim that generated tokens share the same low-rank subspace as the original context (Figure 1, middle panel) and that the pre-filling SVD projection can be reused throughout decoding without accuracy loss. The memory savings from ShadowKV+ are not separately quantified but would be significant for long generation sequences (thousands of output tokens).

**Precision robustness (Appendix Tables 9 and 10):** As discussed in Section 5.1, ShadowKV maintains accuracy under FP8 precision. Full attention degrades from 86.68% (BF16) to 84.94% (FP8) on RULER — the 1.74 point degradation represents the unavoidable cost of reduced precision. ShadowKV in FP8 achieves 85.95%, actually 1.01 points above full attention FP8, suggesting the low-rank compression may provide some robustness to quantization noise (perhaps because SVD filters high-frequency components that are most vulnerable to FP8's limited mantissa precision). Quest V in FP8 achieves 83.88%, demonstrating that ShadowKV's advantage over baselines persists at reduced precision.

**Scalability to larger models and longer contexts (Appendix Table 11):** On Llama-3-70B-1M at 512K contexts (RULER), full attention achieves 75.23% average accuracy. ShadowKV achieves **74.87%** — a 0.36 point drop. Quest V achieves 67.14%, InfiniGen V 54.69%. On Llama-3-8B-1M at 1M contexts, full attention achieves 72.89%, ShadowKV achieves **72.98%** (0.09 point improvement), Quest V achieves 57.57%. This demonstrates that ShadowKV's benefits scale to both larger models (70B parameters) and longer contexts (1M tokens), with the accuracy advantage over baselines actually widening at these scales (17.30 point gap vs. Quest V at 1M, compared to 5.56 point gap at 128K). The NIAH heatmap for Llama-3-70B-1M (Appendix Figure 10) confirms near-perfect retrieval accuracy across all context lengths from 16K to 1M tokens with ShadowKV.

**Efficiency comparison with Quest at 1M contexts (Appendix Table 14):** At 1M context with batch size 3, full attention OOM, full attention with CPU offloading 0.21 tokens/s, Quest OOM, Quest with CPU offloading 9.34 tokens/s, ShadowKV **45.32 tokens/s**. This 4.85× improvement over Quest with CPU offloading is attributed to two factors: (1) ShadowKV only fetches value cache from CPU (not both keys and values), and (2) the cache hit mechanism reduces effective PCIe transfers by 60%. This is the most extreme test of ShadowKV's architecture, where both GPU memory and PCIe bandwidth constraints are binding — and the combined effect of low-rank compression, value-only offloading, landmark-based selection, and temporal caching compound to deliver throughput that is usable (45 tokens/s) vs. unusable (0.21–9.34 tokens/s for alternatives).

### Critical Assessment

The experiments strongly support the paper's central efficiency claims but provide incomplete evidence for the generality claims. The throughput improvements (3.04× over full attention at small batch, 4.85× over Quest at 1M contexts) are well-demonstrated under the tested configurations. However, several important limitations and untested scenarios deserve explicit attention.

**Claim: ShadowKV supports up to 6× larger batch sizes and boosts throughput by up to 3.04× without sacrificing accuracy.**

This claim is **strongly supported** for the specific models, context lengths, and hardware (A100) tested, with the nuance that accuracy is evaluated on benchmark datasets while throughput is measured in a controlled benchmark setting. The batch size scaling is convincingly demonstrated in Table 4 — at 60K context, full attention OOM at batch 12 while ShadowKV reaches batch 48 (4× increase, not quite 6×; the 6× figure applies to specific comparisons like 122K context where full attention maxes at 4 and ShadowKV reaches 24). The throughput gain of 3.04× at 122K on Llama-3.1-8B is the maximum reported; the minimum gain among tested configurations is 2.23× (GLM-4-9B-1M at 244K). The claim of "no accuracy sacrifice" is quantitatively validated: ShadowKV achieves 86.88% vs. 86.68% full attention on RULER for Llama-3-8B-1M (Table 1) — within normal measurement variation for a single-run evaluation.

However, the throughput numbers are measured under an assumption that bears examination: the batch size for ShadowKV is set to the maximum that fits in GPU memory. In real deployments, the achievable batch size depends on request arrival patterns. If requests arrive slowly, a system may never fill the maximum batch, meaning the throughput gains would only be realized under high load. The paper does not model or simulate request-level dynamics. This is a standard limitation of throughput benchmarks, not a flaw specific to ShadowKV, but it means the reported gains represent an upper bound under ideal batching conditions.

A second caveat: throughput is measured during the decoding phase only. Pre-filling latency is not included in the throughput numbers. ShadowKV adds SVD computation during pre-filling (shown to be 6.65% of pre-filling time at 64K, dropping to 0.97% at 512K in Table 12). For applications with long outputs (where decoding dominates total time), this overhead is negligible. For applications with short outputs (single tokens or few tokens generated), the pre-filling overhead could meaningfully reduce end-to-end throughput gains. The paper does not provide end-to-end latency measurements that include both pre-filling and decoding.

**Claim: ShadowKV matches full-attention accuracy on RULER, LongBench, and NIAH across six model families at contexts up to 1M.**

This claim is **supported with qualifications** regarding the specific benchmarks and the single-run evaluation protocol. The accuracy results are comprehensive across models and benchmarks. However:

- **Single-run evaluation.** All accuracy numbers appear to be from single evaluation runs with no reported variance. RULER's 500-sample test set and LongBench's task-specific sample counts (ranging from 200 to 1,000+ samples per subtask) provide reasonable statistical power, but without confidence intervals, the 0.2–1.9 percentage point differences between ShadowKV and full attention cannot be distinguished from sampling noise. When ShadowKV shows higher accuracy than full attention (e.g., 86.88% vs. 86.68% on RULER), this is plausibly noise rather than genuine improvement.

- **The "matches full attention" claim is task-dependent.** On RULER with Llama-3-8B-1M, ShadowKV degrades by 2.08 points on QA-1 (75.00% → 72.92%) and improves by 3.12 points on QA-2 (48.96% → 52.08%) and 3.13 points on VT (78.54% → 81.67%). The average across tasks masks per-task variation that may be meaningful for applications focused on specific task types. A user who cares primarily about QA accuracy might experience a small degradation, while a user focused on variable tracking might see an improvement.

- **Limited benchmark selection.** While RULER, LongBench, and NIAH cover retrieval, QA, summarization, and reasoning, they do not include certain long-context use cases: mathematical reasoning over long proofs, multi-step planning with long state descriptions, or few-shot learning with many examples (where each example token's KV might be important). The paper does not argue for completeness of its benchmark coverage, but the claim of generality is limited to the tested task types.

- **No evaluation on non-English or multilingual tasks.** LongBench includes Chinese tasks, but the main evaluation uses English models. The behavior of the landmark-based selection for languages with different tokenization patterns or different attention structures is untested.

**Claim: ShadowKV surpasses the performance achievable with infinite batch size under the assumption of infinite GPU memory.**

This claim is **valid for the theoretical model presented in Section 4.2**, but its empirical demonstration requires careful interpretation. The "infinite batch size" baseline in Table 3 is computed by: measuring a single transformer block's attention time, projecting to the full model, and assuming 2 TB/s memory bandwidth for the attention computation. This is a best-case estimate — it ignores kernel launch overhead, load imbalance at very large batch sizes, and the FFN component's scaling behavior. The fact that ShadowKV achieves 472.77 tokens/s while the infinite baseline at batch 48 achieves 168.72 tokens/s (and the infinite batch baseline at truly infinite batch achieves 273.07 tokens/s) is a valid demonstration of bandwidth efficiency, but the baseline numbers should be understood as upper bounds on what is physically possible, not achievable throughputs. Real systems with large GPU memory would still have scheduling and synchronization overheads that the theoretical model omits.

**Untested scenarios and missing experiments:**

- **No evaluation with continuous batching or real request traces.** Throughput is measured with static batch sizes where all sequences in the batch are at the same decoding step. In continuous batching (as used in production systems like vLLM), sequences enter and leave the batch at different times, and the KV cache management becomes more complex. ShadowKV's low-rank compression handles this implicitly (each sequence has its own SVD), but the interaction between the cache hit mechanism and continuously changing batch composition is untested.

- **No comparison against 4-bit or 2-bit KV cache quantization methods.** The paper mentions that quantization is orthogonal (Section 2) but does not combine ShadowKV with quantization nor compare against quantized baselines at equivalent memory footprint. KIVI (Liu et al., 2024) achieves 2-bit KV cache quantization — if 2-bit quantization achieves 8× memory reduction (from 16-bit) with minimal accuracy loss, how does ShadowKV's accuracy-throughput tradeoff compare to quantized full attention at the same memory budget? This comparison would clarify whether the engineering complexity of ShadowKV's hybrid GPU-CPU pipeline is justified relative to simpler quantization approaches.

- **No evaluation of the SVD computation's impact on time-to-first-token (TTFT).** Pre-filling latency directly affects user experience in interactive applications. The paper reports SVD overhead as a percentage of pre-filling time per transformer block (Figure 1, right panel; Table 12), but does not report total end-to-end time-to-first-token with and without ShadowKV. At 128K context, the SVD adds 26.62 ms per block for Llama-3-8B-1M (Table 12). For a 32-layer model, this is approximately 852 ms of added latency — potentially noticeable for interactive use. The footnote about asynchronous SVD on CPU suggests a mitigation but this is not implemented or evaluated.

- **No sensitivity analysis of the chunk hit rate to generation length or task type.** The 60% hit rate is reported as a single number, but the paper does not investigate whether this rate varies with the type of text being generated (e.g., factual QA vs. creative writing), the decoding temperature (higher temperature might reduce temporal locality), or the length of generation (early tokens vs. late tokens). If the hit rate degrades in certain regimes, throughput would be lower than reported.

- **No ablation on the impact of the cache hit mechanism on accuracy.** The cache mechanism reuses KV pairs from the previous decoding step — if the previous step's selection was slightly suboptimal (selected a chunk that was borderline), the cache could propagate that suboptimality to subsequent steps. The paper reports the hit rate's throughput benefits but does not test whether disabling the cache mechanism (always recomputing KV selection from scratch) improves accuracy.

**Potential weaknesses in the experimental design:**

- **The oracle-like status of the difficulty estimation in the KV selection is not addressed.** ShadowKV's landmark-based selection uses the true post-RoPE key means, meaning the selection algorithm has perfect knowledge of the KV cache structure. In contrast, InfiniGen's offline SVD is fundamentally information-limited. This is by design (ShadowKV stores the landmarks on GPU), but it means the comparison is between a method with online access to KV cache statistics and methods with only offline approximate access. Under equal-memory constraints, ShadowKV's landmarks consume GPU memory (the `$S/C$` term in the equivalent bandwidth model) — for extremely large contexts, even the landmarks might not fit. The paper does not test at what context length the landmarks themselves become a memory bottleneck.

- **The single A100 evaluation limits generality to other hardware configurations.** The 63.5:1 GPU-to-PCIe bandwidth ratio on A100 is a key parameter in ShadowKV's design. On hardware with different ratios (e.g., H100 with 3.35 TB/s HBM3 bandwidth and 128 GB/s PCIe Gen5, giving a ~26:1 ratio), the tradeoff between GPU-side reconstruction and CPU-side fetching would shift. ShadowKV's design choices (rank, chunk size) were tuned for the A100 ratio and may not be optimal elsewhere.

- **No evaluation of power consumption or total energy.** ShadowKV adds SVD computation and PCIe transfers that full attention avoids. For data-center deployments where energy costs matter, the throughput-per-watt may be a more relevant metric than raw throughput. The paper does not address energy efficiency.

## 6. Limitations and Trade-offs

### 6.1 The Cost of Online SVD Is Not Accounted for in Throughput or Latency Measurements

**The assumption or constraint.** ShadowKV's core memory-saving mechanism — applying truncated SVD to pre-RoPE keys during pre-filling — is an online, prompt-dependent operation whose cost scales with sequence length. The paper measures this cost as a *percentage* of pre-filling latency (Figure 1, right panel; Table 12) and emphasizes that this percentage shrinks as context grows: from 6.65% at 64K to 0.97% at 512K. The paper states in a footnote that "the key cache can be offloaded to the CPU to perform SVD asynchronously or precomputed and stored as part of the prefix cache," but this is presented as a possibility, not as an implemented or evaluated optimization.

**The consequence.** The time-to-first-token (TTFT) — the latency from when a user submits a prompt to when the first output token appears — is a critical metric for interactive applications. ShadowKV's headline throughput numbers (Tables 3 and 4) are measured exclusively on the *decoding* phase and do not include pre-filling latency. For Llama-3-8B-1M at 128K context, Table 12 shows that SVD adds 26.62 ms per transformer block. With 32 layers, this is approximately **852 ms of additional pre-filling latency** — potentially doubling or tripling the TTFT compared to full attention, which has no such overhead. For applications where users wait for responses (chat, coding assistants, search), this added latency is directly visible and may be unacceptable even if the *average* throughput across many users improves.

The misalignment between the paper's primary metrics (decoding throughput, batch size) and this latency cost is significant because ShadowKV is explicitly motivated by "high-throughput" serving (Section 1), and high-throughput production systems must balance both pre-filling and decoding costs. A system that achieves 3× decoding throughput but 2× pre-filling latency may be net-worse for interactive workloads with short output lengths, where pre-filling dominates total time.

**What evidence exists in the paper.** Table 12 provides the per-block latency breakdown during pre-filling. At 128K context, SVD adds 26.62 ms per block compared to 721.13 ms for attention and 193.32 ms for FFN — a 3.25% overhead per block. At 64K, the overhead is 6.65%. The paper does not report end-to-end TTFT for any configuration, does not include pre-filling time in throughput calculations, and does not measure TTFT with the asynchronous SVD suggestion implemented.

**Mitigation status.** The asynchronous SVD approach (offloading key cache to CPU for SVD computation while the next layer begins processing) is mentioned as a possibility but **not implemented or evaluated**. The paper does not report whether this approach would add PCIe transfer overhead for the key cache movement, whether SVD on CPU is fast enough to complete before it is needed for the low-rank factors, or whether the pipeline bubbles introduced by asynchronous SVD would reduce throughput. The limitation is acknowledged only in a footnote, not in the main text's performance claims.

---

### 6.2 All Results Are on a Single GPU Architecture (A100), and the PCIe-to-HBM Bandwidth Ratio Is a First-Order Design Parameter

**The assumption or constraint.** ShadowKV's entire architecture is tuned for the A100 GPU, which has a specific ratio between GPU memory bandwidth (2 TB/s HBM2e) and PCIe bandwidth (31.5 GB/s PCIe Gen4) — a ratio of approximately 63.5:1. The equivalent bandwidth model (Section 4.2) makes this ratio explicit as the `$B_{\text{GPU}} / B_{\text{PCIe}}$` term, which directly weights the cost of CPU value fetching in the denominator. The chunk size `$C = 8$`, SVD rank `$r = 160$`, sparse budget `$K = 256$`, and number of outliers `$O = 48$` are all fixed hyperparameters validated empirically on A100 hardware.

**The consequence.** On hardware with a different GPU-to-PCIe bandwidth ratio, the optimal hyperparameters — and potentially the entire design strategy — would change. On an H100 with HBM3 (3.35 TB/s) and PCIe Gen5 (128 GB/s), the ratio drops to approximately **26:1**. Under ShadowKV's equivalent bandwidth model, the PCIe term in the denominator would be weighted roughly **2.4× less**, making CPU value fetching relatively cheaper. This might shift the optimal tradeoff toward fetching *more* values from CPU and reconstructing *fewer* keys on GPU, or toward different chunk sizes that favor larger PCIe transfers. On older hardware with PCIe Gen3 (15.75 GB/s) and the same GPU bandwidth, the ratio would be approximately 127:1, making PCIe transfers 2× more expensive than on A100 and potentially changing whether value offloading is beneficial at all compared to keeping more data on GPU.

More fundamentally, the paper provides no evidence that ShadowKV's design principles generalize across hardware generations. The 3.04× throughput claim is specific to the A100's bandwidth bottleneck — on a GPU with proportionally larger memory bandwidth (e.g., H100 with HBM3 at 3.35 TB/s), the *absolute* throughput improvement might be smaller or larger depending on how the bottleneck shifts.

**What evidence exists in the paper.** All throughput measurements in Tables 3 and 4, all latency breakdowns in Tables 12 and 13, and the equivalent bandwidth computation in Section 4.2 use A100-specific numbers ($B_{\text{GPU}} = 2$ TB/s, $B_{\text{PCIe}} = 31.5$ GB/s). The paper does not evaluate on any other GPU, does not provide a sensitivity analysis of throughput to the bandwidth ratio, and does not discuss how hyperparameters should be re-tuned for different hardware.

**Mitigation status.** **Not addressed at all.** The paper offers no guidance for practitioners deploying on non-A100 hardware. This is a significant practical gap because the A100, while widely used, is being superseded by H100/H200 GPUs in many production deployments, and the transition from PCIe Gen4 to Gen5 changes the key hardware parameter in ShadowKV's design.

---

### 6.3 Accuracy Is Evaluated on a Narrow Slice of Long-Context Tasks, and the "Matches Full Attention" Claim Does Not Generalize to All Regimes

**The assumption or constraint.** The accuracy evaluation covers three benchmarks (RULER, LongBench, NIAH) and one additional benchmark in the appendix (InfiniteBench), all focused on retrieval, QA, summarization, and code completion tasks. These benchmarks represent a specific distribution of attention patterns: retrieval requires precise localization of a few key tokens; QA requires aggregating information from scattered context; summarization requires broad but coarse context access. The paper explicitly acknowledges that test-time compute approaches generally work best when "the problem distribution includes a substantial fraction of easy-to-medium problems" — and here, the analogous claim is that the benchmark tasks fall within regimes where sparse attention with 1.56% KV budget is sufficient.

**The consequence.** There exist long-context tasks where 1.56% of the KV cache is structurally insufficient, and the paper provides no characterization of when this regime begins. Potential failure modes include:

- **Multi-step mathematical reasoning** over long proofs, where each intermediate step's KV state may be necessary to reconstruct the reasoning chain, and missing any step breaks the derivation. In such tasks, the attention pattern may be dense across the entire context rather than sparse.
- **Few-shot learning with many long examples**, where the model must attend to and compare details across many examples simultaneously. If the examples are long and information-dense, 1.56% of tokens may not cover enough content to distinguish between examples.
- **Adversarial contexts** where important information is deliberately distributed across many tokens at low density, making it inherently hard to capture with any fixed sparse budget.

The paper's evaluation on RULER partially addresses the "distributed information" concern (multi-key needle retrieval tests exactly this), but RULER's tasks use synthetic needle-insertion patterns rather than naturally occurring dense reasoning. A practitioner deploying ShadowKV for legal document analysis, scientific literature review, or long-form mathematical tutoring cannot infer from the existing benchmarks whether their specific use case will be within the safe operating regime.

**What evidence exists in the paper.** Table 1 shows per-subtask accuracy on RULER and LongBench. On RULER with Llama-3-8B-1M, ShadowKV degrades by 2.08 points on QA-1 (75.00% → 72.92%) and improves on other tasks. The paper does not analyze *which* specific samples ShadowKV gets wrong versus full attention — there is no error analysis, no per-sample accuracy comparison, and no characterization of failure patterns. Without this analysis, it is impossible to predict whether a new task type will be safe.

The ablation study on sparse budget (Figure 8) shows that accuracy drops sharply below 0.78% budget on multi-key NIAH, but the "safe floor" varies by task — frequent words extraction maintains accuracy down to ~0.4%, while variable tracking degrades below ~1.2%. This suggests the 1.56% budget is task-dependent in ways the paper does not systematically map.

**Mitigation status.** **Partially addressed** through the breadth of models and benchmarks evaluated, but **not systematically analyzed**. The paper does not provide a diagnostic or decision rule for determining whether a new task or deployment scenario will be within ShadowKV's safe operating regime. This is a fundamental limitation for any practitioner who cannot run their own internal benchmarks at the same scale.

### 6.4 ShadowKV Adds Substantial Engineering Complexity for Gains That Quantization Methods May Achieve More Simply

**The assumption or constraint.** ShadowKV's system involves: online SVD during pre-filling (with its associated numerical and performance considerations), landmark construction and outlier detection, a GPU-side key reconstruction pipeline, CPU-side value offloading with PCIe transfers, a cache hit management system with custom CUDA kernels, and overlapping CUDA streams for concurrent reconstruction and fetching. This is a non-trivial software stack that must be integrated with existing inference frameworks (the paper implements it on PyTorch with custom CUTLASS kernels and FlashInfer components).

The paper mentions that "quantization methods reduce the KV cache bit width, which is orthogonal to our approach" (Section 2) but does not compare against quantization-only solutions at equivalent memory budgets.

**The consequence.** For many practitioners, a simpler approach — quantizing the KV cache to 4-bit or 2-bit precision — may achieve comparable memory reduction with substantially less engineering complexity. KIVI (Liu et al., 2024) achieves 2-bit KV cache quantization with a tuning-free asymmetric scheme, providing up to 8× memory reduction from standard 16-bit precision with minimal accuracy loss on standard benchmarks. If 4-bit KV quantization (4× compression) is sufficient to double the batch size in a given deployment, the additional 6–7× compression from ShadowKV may not justify the system's complexity, especially given that ShadowKV requires online SVD, CPU memory management, custom fused kernels, and ongoing maintenance as GPU hardware and inference frameworks evolve.

The "orthogonal" framing is accurate but incomplete: for a practitioner deciding *which* memory optimization to implement, ShadowKV and quantization are *substitutes* — both reduce GPU memory footprint. The paper provides no guidance on when to prefer one over the other, or what the incremental benefit of ShadowKV is beyond what quantization alone can achieve. A system combining both (ShadowKV's low-rank compression plus 2-bit quantization of the stored factors) could achieve even larger compression, but this is neither tested nor discussed.

**What evidence exists in the paper.** No comparison against any quantization method at any bit width. No experiment combining ShadowKV with quantization. No discussion of the relative engineering effort required for ShadowKV vs. quantization-only solutions. The "orthogonal" claim (Section 2) is stated without empirical support or analysis of the practical tradeoffs.

**Mitigation status.** **Not addressed.** The paper treats quantization as outside its scope, which is a valid research framing but a significant practical limitation for deployment decisions. A practitioner reading this paper cannot determine whether the 3.04× throughput gain justifies the implementation complexity compared to simply quantizing the KV cache and accepting a potentially smaller but simpler gain.

---

### 6.5 The SVD Rank and Sparse Budget Are Static, While Optimal Settings Likely Depend on Input Properties

**The assumption or constraint.** ShadowKV uses fixed hyperparameters for all inputs: SVD rank `$r = 160$`, chunk size `$c = 8$`, sparse budget `$K = 256$` chunks (1.56%), and `$O = 48$` outlier chunks. These were empirically determined through ablation studies (Figure 9) and are held constant across all models, all benchmarks, all context lengths, and all inputs. The paper's difficulty estimation methodology — determining per-prompt optimal strategies — is entirely absent; there is no mechanism for adapting these hyperparameters to individual inputs.

**The consequence.** The fixed hyperparameters represent a compromise across the evaluation distribution, but they are likely suboptimal for specific inputs or deployment scenarios. For example:

- **Shorter contexts** (e.g., 16K tokens): 1.56% of 16K is only 256 tokens — potentially too few for tasks requiring broad context. The paper uses a fixed 1.56% budget rather than adapting the budget to context length.
- **Information-dense vs. information-sparse contexts**: A legal contract with dense factual information in every paragraph may require a higher sparse budget than a narrative story with redundant descriptions.
- **Task-dependent optimal rank**: Figure 9 (right panel) shows that some RULER subtasks (NIAH-MK) plateau at rank 160 while others (FWE) continue improving to rank 400+. Using rank 160 for all tasks leaves potential accuracy on the table for tasks that benefit from higher-rank representations.

The paper's compute-optimal allocation framework — the central contribution — relies on per-prompt difficulty estimation and adaptive strategy selection. ShadowKV, by contrast, uses a **one-size-fits-all** configuration that ignores per-input variability in both the low-rank structure (how compressible the pre-RoPE keys are) and the attention sparsity pattern (how many chunks are needed).

**What evidence exists in the paper.** The ablation studies (Figure 9) show that accuracy varies with rank and chunk size, and that different tasks have different optimal settings, but this task-level variation is not translated into an adaptive allocation policy. The chunk hit rate (Figure 9, left panel) is reported as a single aggregate number (~60%), but the paper does not analyze whether hit rate varies with input properties, generation length, or task type.

**Mitigation status.** **Not addressed.** The paper presents a static system and does not discuss adaptive hyperparameter selection. Given that this is the same research group that pioneered compute-optimal test-time scaling, the absence of any adaptive allocation mechanism is notable and suggests this is an area for future work rather than a deliberate omission.

### 6.6 The Cache Hit Mechanism's Dependence on Decoding Temperature and Generation Diversity Is Unexplored

**The assumption or constraint.** The cache hit mechanism — which reuses KV selections from the previous decoding step, avoiding redundant PCIe transfers and key reconstruction — is predicated on the observation that "the KV pairs selected by the queries of two adjacent decoding steps have a high repetition rate" (Section 3.2). The paper reports a ~60% hit rate (Figure 5, right panel; Figure 9, left panel) and uses this in the equivalent bandwidth model (the `$(1 - \alpha)$` term in Section 4.2). All experiments appear to use a single decoding configuration.

**The consequence.** The hit rate is likely sensitive to decoding parameters that affect the diversity and trajectory of generated tokens:

- **Sampling temperature**: At high temperature, the model produces more diverse, less predictable token sequences. Query vectors for adjacent tokens may diverge more sharply, reducing the overlap in selected KV chunks and lowering the hit rate. The paper does not report hit rates at different temperatures.
- **Top-p / top-k sampling**: Aggressive truncation of the sampling distribution may make the output more deterministic, potentially increasing hit rate. Conversely, diverse sampling strategies may reduce it.
- **Task type**: Factual QA with deterministic answers likely has high hit rates because the model follows a consistent reasoning path. Creative generation with open-ended outputs may have lower hit rates as the model explores different narrative directions.

The 60% hit rate is not a guaranteed property — it is an empirical observation under the paper's specific decoding configuration. If the hit rate drops to, say, 30% in a deployment with high-temperature sampling, the equivalent bandwidth would decrease from 7.2 TB/s to roughly 5.5 TB/s (a 24% reduction, recalculating from the equivalent bandwidth formula with `$\alpha = 0.3$` instead of 0.6), and the throughput gains would be correspondingly lower.

**What evidence exists in the paper.** Figure 5 (right panel) shows the hit rate across generated token indices for three different (layer, KV head) combinations, all showing rates clustered around 0.6–0.8. Figure 9 (left panel) shows hit rate as a function of chunk size, with rates around 0.6 for chunk sizes 2–64. The paper does not report hit rate as a function of temperature, sampling strategy, task type, or generation length beyond the initial tokens shown in Figure 5.

**Mitigation status.** **Not addressed.** The paper treats the hit rate as a fixed empirical property rather than a parameter that varies with deployment conditions. No sensitivity analysis is provided. A practitioner deploying ShadowKV with non-default generation parameters cannot predict their hit rate from the paper's results and may experience lower throughput than the headline numbers suggest.
