Here are the takeaways from this Ryan Peterman interview (author of The Peterman Post, reflecting on how LLM-based coding is reshaping software engineering practice):

**The Weekend Project That Changed Everything**

Ryan built a side project in a single weekend using Cursor, an LLM-based IDE, without writing a single line of code himself. The project would have taken at least a week otherwise. The speedup was dramatic enough to force a re-examination of fundamental engineering behaviors. The experience crystallized a counterintuitive practice: **it becomes more efficient to throw away code and retry with a tweaked prompt than to debug the broken output**. "Debugging the broken code is much slower than prompt engineering," he says. This represents a genuine inversion of traditional software development, where understanding and fixing existing code was almost always cheaper than starting over. But the speed comes with a tradeoff: "I get things done way faster, but also have much less understanding of the code." This burned him several times — he'd accept generated code that looked fine in isolation but was "clowny when I zoomed out." At one point, he ended up with two competing data models for the same concept, a design mistake he would have caught immediately if he'd written the code himself.

**Print Statements Over Debuggers**

LLMs have changed Ryan's debugging workflow entirely. He used to prefer debuggers because they let you inspect arbitrary program state without manually typing out print statements. But with LLMs, "you don't need to type out print statements manually anymore." A single prompt can inject quality print statements everywhere, letting you run and inspect your program much faster. When you're done, another prompt cleans them all up. This combination — effortless instrumentation and effortless cleanup — shifts the ergonomic calculus: debuggers are now slower relative to the LLM-assisted print-statement workflow, even for complex state inspection.

**Goodbye Google (Mostly)**

For most problems, LLMs now provide "more targeted answers so you don't need to read tutorials or Stack Overflow answers." Ryan found himself reaching for Google only in two specific failure modes. The first was **niche answers** — when building a Chrome extension, he wanted to draw over a page without modifying its DOM; LLMs kept suggesting obvious solutions that injected components into the DOM, while a Google search surfaced the approach he actually needed. The second was **weird bugs** where the symptom misled the model — an OpenAI API key without a registered credit card returned a 429 "too many requests" error, causing LLMs to suggest caching and rate-limiting fixes that made sense but didn't work. A quick Google search revealed the real issue was the missing credit card. These edge cases reveal a persistent blind spot: when the true cause is a non-obvious configuration quirk rather than a code-level problem, LLMs reliably diagnose the wrong thing.

**The "Know Your LLM" Playbook**

After a day or two of experimentation, Ryan developed a clear sense of what LLMs do well and poorly. They are nearly perfect at **small, focused changes** — "almost perfect if it was a small algorithm, regardless of how complex." He suspects they're "super-human at Leetcode." They excel at **basic UI**: "my side project looks good (although simple) without me having to tweak much CSS." And they shine at **transpiling** — he converted all his vanilla JavaScript to TypeScript "in just a minute or two" after realizing he wanted types a few hours into the project. On the failure side, they're unreliable at **changes outside the code**, like setting up the environment or managing cross-project references. And they fail badly on **open-ended features**: "the more ambiguity the feature had, the more likely the prompt would fail. I needed to give it specific bulleted instructions the bigger the feature was."

**Model Selection as a Skill**

Ryan's strategy for model selection is pragmatic and tiered. His default is **claude-3.5-sonnet** — "it runs fast and works most of the time." When Claude struggles, he escalates to the most capable model he knows, **OpenAI's o1-preview**, which often succeeds but is slow ("takes a few minutes") and expensive ("$0.40 per request"). If that fails too, he falls back to manually breaking the feature into well-scoped tasks. He wishes LLM tooling would one day automatically select models based on task difficulty, but until then, "it's good to understand what each model can do to balance quality and cost by hand." This tiered escalation — fast/cheap model first, then slow/powerful, then human decomposition — is a pattern he thinks will eventually be automated but for now requires deliberate judgment.

**What Matters Most Now**

With LLMs handling the well-scoped, detailed work, Ryan argues the skills that gain leverage are **high-level planning and design** — "planning out your feature roadmap and technical design matters more since LLMs don't do this well yet" — and **debugging**. He could sometimes dump errors into the LLM and get a fix, but "there were many times when it had trouble with even obvious errors (e.g. deleted critical code or changed function names)." He also acknowledges his project was a simple, full-stack app with abundant training data and unambiguous boilerplate patterns. The approach "would have been much less effective for cutting-edge, proprietary code in many parts of the industry." The core insight: LLMs are powerful for simple, well-scoped code, but "that doesn't mean AI is taking our jobs. Play around with it for a while and you'll see that it is still far from that."

**The Satisfaction of English-Driven Programming**

Ryan circles back to the subjective experience: "It feels powerful to program in English. I can express myself with much less time and effort." He compares the feeling to the satisfaction he got as his career grew and he started doing higher-leverage work — removing frustrating implementation details like "compiler errors and missing semicolons" frees you to do "interesting, creative work." The LLM doesn't eliminate the need for engineering judgment; it eliminates the tedious part, leaving the planning, design, and debugging work that actually engages the mind.
