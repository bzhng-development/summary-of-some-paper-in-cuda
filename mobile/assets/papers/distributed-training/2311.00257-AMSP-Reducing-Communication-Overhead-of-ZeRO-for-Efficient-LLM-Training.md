## 1. Executive Summary

This paper proposes **AMSP**, a system that optimizes ZeRO for scalable LLM training by introducing three flexible sharding strategies—Full-Replica, Full-Sharding, and Partial-Sharding—allowing each component within the model states (Parameters, Gradients, Optimizer States) to independently choose a sharding strategy and device mesh, and then formulating an optimization problem to discover the minimal-communication configuration under GPU memory constraints. Evaluated on LLaMA-based models (7B, 13B, 30B) trained on up to 1024 NVIDIA Ampere GPUs, AMSP achieves up to 52% Model FLOPs Utilization (MFU) and a 1.56× improvement in training throughput over systems like MiCS and ZeRO++ (e.g., 51% MFU vs. 35% for MiCS on LLaMA-7B at 1024 GPUs), establishing that communication-efficient ZeRO scaling is achievable through individualized per-component sharding decisions rather than uniform strategies—though with the trade-off of higher GPU memory consumption relative to aggressive sharding approaches like ZeRO-3.

## 2. Context and Motivation

### The Core Problem: ZeRO Communication Becomes a Bottleneck at Scale

The fundamental problem this paper tackles is the **communication overhead that ZeRO introduces when training LLMs across large GPU clusters**. ZeRO (Zero Redundancy Optimizer) is widely deployed in production training frameworks—DeepSpeed, PyTorch FSDP, ColossalAI—because it elegantly solves the memory problem: by sharding model states (parameters, gradients, optimizer states) across GPUs, it enables training models that would otherwise exceed single-GPU memory. But ZeRO achieves this memory efficiency at the cost of extensive collective communication operations (AllGather, ReduceScatter, AllReduce, Broadcast) that must run on every training step.

This communication cost is not a constant factor. It **degrades disproportionately as training scales up**. The paper quantifies this clearly in Section I: training LLaMA-7B on 8 GPUs with ZeRO-1 achieves 63% MFU, but scaling the same workload to 1024 GPUs at the same global batch size drops MFU to 36%. For LLaMA-13B with ZeRO-3, the degradation is even steeper—from 47% MFU at 8 GPUs to a catastrophic 4% MFU at 1024 GPUs. This means that adding more GPUs does not translate into proportionally faster training; in fact, beyond a certain scale, the marginal benefit of each additional GPU can approach zero because communication dominates the execution time.

### Why This Problem Matters

The communication scaling problem has direct, high-stakes practical consequences:

**1. The prevalence of mid-sized models.** As the paper notes in Section II-A, the landscape has shifted. While early work focused on giant models like GPT-3 (175B), recent evidence suggests optimal performance often comes from smaller models trained on larger data (the Chinchilla scaling laws, Hoffmann et al., 2022). The LLaMA family (7B–65B), Mistral (7B), InternLM2 (7B–20B), and Baichuan2 (7B–13B) exemplify this trend. These models are small enough that their model states fit comfortably on a few GPUs with ZeRO-1 or ZeRO-2—but organizations training them want to use hundreds or thousands of GPUs to reduce wall-clock training time. It is exactly in this regime that ZeRO's communication overhead becomes the dominant inefficiency, because *the computational load per GPU shrinks as the cluster grows* while the communication load remains linked to the model size.

**2. The compute-to-communication ratio imbalance.** When training on many GPUs, practitioners face a harsh constraint: the global batch size must stay within a range that preserves model convergence quality. This means the per-GPU micro-batch size gets very small at large scale—often just 1 sequence of 4096 tokens. As Figure 2(b) shows, computation time per step drops nearly linearly with GPU count (because each GPU processes fewer tokens), but communication time does not scale down commensurately. The ratio of useful computation to communication cost collapses, and GPUs spend increasing fractions of each training step idle, waiting for network transfers.

**3. The inter-node bandwidth bottleneck.** Modern GPU nodes provide enormous intra-node bandwidth (600 GB/s bidirectional per GPU via NVLink on DGX-A100 nodes, as the paper notes) but inter-node bandwidth is considerably lower (400 GB/s bidirectional *per node*, not per GPU). Figure 3 quantifies this with NCCL microbenchmarks: as communication crosses node boundaries, effective bandwidth drops substantially. The ratio between intra-node and inter-node bandwidth is approximately 2× in their testbed, but compounding this is the increased latency and reduced effective bandwidth when collective operations span many nodes (Figure 3, moving from 8×1 GPUs to 8×64 GPUs shows significant degradation in AllGather, ReduceScatter, and AllReduce effective bandwidth, especially for smaller message sizes).

**4. The latency scaling of collective operations.** Collective communication operations have a non-trivial latency component (the α term in the α-β model) that scales with the number of participating ranks. More GPUs mean more rounds of data transfer in ring-based algorithms, more complex tree topologies, and more opportunities for network congestion. Figure 2(c) directly measures this: for a fixed 256 MB message, AllGather latency increases substantially as the number of GPUs grows from 8 to 512. Figure 3 provides a more granular view, showing that effective bandwidth for AllGather, ReduceScatter, AllReduce, and Broadcast all degrade as the number of participating nodes increases, with the effect being most pronounced at small message sizes (which are common when sharding individual Transformer layer modules).

The combined effect is that **large-scale LLM training with ZeRO leaves enormous amounts of GPU compute idle**. AMSP's trace analysis (Figure 14, discussed in Section VI-C) reveals computation resource "bubbles" during the backward pass where GPUs wait for ReduceScatter and AllReduce operations to complete. On LLaMA-7B trained on 32 GPUs, these bubbles are directly visible in DeepSpeed's traces for ZeRO-3, MiCS, and ZeRO++. The paper's stake is that recovering this wasted compute through better communication scheduling and sharding strategy can dramatically improve training throughput without any hardware changes.

### Prior Approaches and Where They Fall Short

Before AMSP, several systems attempted to address ZeRO's communication overhead. Each makes a different design tradeoff, and each has specific failure modes that AMSP is designed to address.

#### ZeRO++: Secondary Parameter Shards and Quantization

ZeRO++ (Wang et al., 2023) introduces two mechanisms. First, it maintains a **secondary shard of parameters** within a small subgroup of GPUs (typically within the same node, e.g., `s0_p=8, s1_p=1`). During the forward pass, parameters are gathered across all GPUs as in standard ZeRO-3, but they are also stored in this secondary shard. During the backward pass (which requires parameters again for gradient computation), parameters are fetched from the secondary shard rather than from the full cluster, reducing communication scale for the backward pass. Second, ZeRO++ applies **quantization** to compress parameters and gradients during inter-node transfers, reducing the communication volume at the cost of some precision loss.

**Where it falls short.** The paper identifies two critical limitations. First, ZeRO++ still requires `sp = sg = sos = sdp` for the primary model states—the same uniform, inflexible sharding as ZeRO-3. The secondary shard helps backward-pass parameter collection but does not address the communication for gradient synchronization or optimizer state management. Second, the paper's evaluation shows ZeRO++ performs **worse than ZeRO-1** on LLaMA-7B at 1024 GPUs (4% MFU vs. 36%), despite being a more sophisticated system. The trace analysis in Figure 14 reveals why: ZeRO++ fails to effectively overlap its ReduceScatter operations with backward computation, leaving GPUs idle. Additionally, ZeRO++ encounters out-of-memory (OOM) errors when training LLaMA-30B on 32 GPUs (Figure 11c), revealing that its memory overhead from the secondary parameter shard and quantization buffers can exceed GPU capacity.

#### MiCS: Subgroup Sharding and Cross-Group Replication

MiCS (Zhang et al., 2022) takes a different approach: rather than sharding model states across all GPUs, it **shards them within a subgroup and replicates across subgroups**. For example, with `sp = sg = sos = 8 × 1`, all model states are sharded within a single node (8 GPUs) and replicated across nodes. This reduces the communication scale for AllGather and ReduceScatter operations from the full cluster to single-node groups, which dramatically reduces latency since intra-node NVLink bandwidth is much higher than inter-node InfiniBand. For gradient synchronization across the full cluster, MiCS uses ReduceScatter within subgroups followed by AllGather across subgroups.

**Where it falls short.** The paper shows that MiCS's performance **degrades below ZeRO-1** when scaling LLaMA-7B to 1024 GPUs (35% MFU vs. 36%), despite its conceptually superior communication pattern (Section III-C). This counterintuitive result stems from an inflexible sharding mechanism that forces `sp = sg = sos ≤ sdp` in all cases. The uniform sharding prevents MiCS from making per-component optimization decisions. For instance, on LLaMA-7B, optimizer states represent 12Φ bytes (the largest memory consumer), gradients represent 2Φ, and parameters represent 2Φ. Sharding all three uniformly means that either memory is wasted (if the sharding factor is chosen to accommodate the largest component) or communication is suboptimal (if components that could benefit from different sharding patterns are forced into the same configuration). The paper's trace (Figure 14) also reveals that MiCS fails to overlap ReduceScatter with AllReduce during the backward pass—a missed optimization opportunity that AMSP exploits.

#### Standard ZeRO Variants (ZeRO-1, ZeRO-2, ZeRO-3)

The original ZeRO family provides three fixed configurations:
- **ZeRO-1**: Shard only optimizer states (`sos = sdp`). Parameters and gradients are replicated. This has the lowest communication overhead (only AllReduce for gradients and AllGather for updated parameters) but the highest memory consumption.
- **ZeRO-2**: Shard optimizer states and gradients (`sg = sos = sdp`). Parameters are replicated. Reduces memory while adding gradient sharding communication.
- **ZeRO-3**: Shard all three—parameters, gradients, and optimizer states (`sp = sg = sos = sdp`). Minimizes memory but maximizes communication, requiring AllGather before every forward/backward pass and ReduceScatter after.

**Where they fall short.** These fixed configurations offer no flexibility to tune the tradeoff between memory and communication on a per-component basis. ZeRO-3, while memory-efficient, becomes communication-bound at scale (the 88% MFU reduction from 8 to 1024 GPUs is catastrophic). ZeRO-1 has acceptable communication but cannot fit larger models like LLaMA-30B into GPU memory. There is no mechanism in standard ZeRO to, for example, use ZeRO-3 style full-sharding for optimizer states (the largest memory consumer) while keeping parameters fully replicated (avoiding per-layer AllGather/ReduceScatter overhead)—which is exactly the kind of configuration AMSP discovers and deploys.

#### FSDP and Other Training Frameworks

PyTorch FSDP (Zhao et al., 2023) implements a ZeRO-3-equivalent sharding strategy and is mentioned as another baseline. The paper notes that FSDP, like MiCS, allows sharding within subgroups and replication across subgroups (`sp = sg = sos < sdp`), but suffers from the same inflexibility: all three model state components must use the same sharding factor. Other automated parallelism frameworks (Alpa, OptCNN, FlexFlow, TensorOpt) are mentioned in Section VII but focus on optimizing operator-level parallelism strategies (data, tensor, pipeline parallelism) for the computational graph, without considering orthogonal placement strategies for model states—a design space that AMSP uniquely explores.

### How AMSP Positions Itself

AMSP's positioning relative to prior work can be understood through three claims:

**Claim 1: The uniform sharding requirement (`sp = sg = sos`) is unnecessarily restrictive.** The paper's key insight in Section III-C is that the three components of model states—Parameters (2Φ bytes in FP16), Gradients (2Φ bytes), and Optimizer States (12Φ bytes)—have *asymmetric memory footprints* and are accessed at *different points* in the training loop. Parameters need to be assembled before each layer's forward and backward computation. Gradients are produced during backward and must be synchronized and sharded. Optimizer states are updated once per step after all gradients are accumulated. Because their lifecycles differ, the optimal sharding strategy for each component may differ, and forcing them to be the same leaves performance on the table.

The paper formalizes this as an optimization problem (Equations 1–7 in Section V-B): find `s0_p, s1_p, s0_g, s1_g, s0_os, s1_os` (the intra-node and inter-node sharding factors for each component) that minimize total communication cost `T_comm` subject to GPU memory constraints. The dependency rule (`s_p ≤ s_g ≤ s_os ≤ s_dp`) ensures correctness (no unnecessary data movement from sharding a downstream component more aggressively than its upstream dependencies), but *within* this constraint, the components can vary independently. This is a fundamentally larger search space than prior systems explored, and the paper shows it produces configurations like `sp=1, sg=1, sos=8` for LLaMA-7B that are neither ZeRO-1, ZeRO-3, nor MiCS—they are hybrid configurations that shard only the largest memory consumer (optimizer states) while keeping parameters and gradients fully replicated.

**Claim 2: Communication-computation overlap matters as much as sharding strategy, and existing implementations do it poorly.** Section VI-C and the trace visualizations (Figures 14, 15) present compelling evidence that even when the sharding configuration is identical, AMSP's execution engine substantially outperforms DeepSpeed's implementation due to better overlap. The paper identifies specific failures in existing systems:

- **ReduceScatter blocking computation:** In DeepSpeed-ZeRO3/MiCS/ZeRO++ (Figure 14), ReduceScatter operations launched during the backward pass are not effectively overlapped with gradient computation for subsequent layers. GPUs sit idle waiting for communication to complete.
- **ReduceScatter blocking AllReduce:** In DeepSpeed-MiCS, the ReduceScatter operation for gradient distribution blocks the concurrent execution of AllReduce operations needed for cross-subgroup gradient synchronization, serializing what could be parallel communication.
- **No Broadcast overlap:** Existing systems do not overlap the Broadcast of updated parameters (after the optimizer step) with the forward computation of the next training step—a natural overlap opportunity that AMSP exploits (Figure 15a).

AMSP's overlap strategy (Section V-C) addresses each of these: it prefetches parameters for the next layer during current-layer computation (AllGather ↔ forward overlap), launches ReduceScatter asynchronously after GradWeight computation and overlaps it with GradInput computation, decouples the ReduceScatter lifecycle from the backward function so that the next layer's backward can start without blocking, and uses a bucketing strategy for AllReduce that flattens gradients incrementally during backward rather than in a post-hoc synchronization phase.

**Claim 3: Topology-aware placement can reduce cross-switch communication.** The paper observes that GPU clusters typically use a leaf-spine network topology where communication across spine switches incurs additional latency and potential congestion (Section V-D). When `s1_{p,g,os} > 1` (sharding across nodes), AMSP strategically groups the participating nodes under the same leaf switches whenever possible, avoiding unnecessary cross-spine traffic. This is a pragmatic optimization that prior systems do not exploit—they treat the network as a flat communication domain.

### The Analytical Foundation: A Profiling-Based Communication Model

A key methodological contribution that underpins the optimization is the paper's decision to use **real-system profiling** rather than an analytical α-β model for predicting communication costs (Section IV-A). The authors acknowledge that the α-β model, while common in distributed systems research, fails in modern GPU cluster environments for three reasons: (1) NCCL uses multiple communication algorithms (Ring, Tree, Collnet, CollnetDirect, CollnetChain) that the α-β model does not capture, (2) In-Network Aggregation (e.g., SHARP) modifies communication semantics in ways the model cannot account for, and (3) effective bandwidth varies non-linearly with message size and scale (as shown in Figure 3).

Instead, AMSP pre-profiles effective bandwidth `w(o, v, p0 × p1)` for each collective operation `o` (AllGather, ReduceScatter, AllReduce, Broadcast), message size `v`, and device mesh `p0 × p1` on the target cluster, and uses linear interpolation for unprofiled sizes. This replaces a potentially inaccurate theoretical model with empirical measurements that capture the actual behavior of the production network fabric. The communication time for each sharding configuration then becomes a straightforward calculation using the profiled bandwidths and the known message sizes from the model architecture, rather than an unreliable analytical prediction.

### Summary of the Motivation Narrative

The paper constructs a clear, empirically-grounded argument: (1) ZeRO's communication overhead is the dominant bottleneck for training mid-sized LLMs at scale, (2) existing mitigation strategies (ZeRO++, MiCS) are insufficient because they enforce uniform sharding across all model state components and implement suboptimal communication-computation overlap, and (3) a system that independently chooses sharding strategies per component, optimizes overlap, and leverages topology-aware placement can recover the majority of wasted GPU cycles. The paper's explicit framing of the problem as an optimization over independent sharding factors (`sp`, `sg`, `sos`) subject to memory constraints—combined with a profiling-based communication cost model—positions AMSP as the first system to fully explore the tradeoff space between memory efficiency and communication efficiency in ZeRO-style distributed training.

## 3. Technical Approach

This is a **systems paper** that designs and implements a communication optimization framework for distributed LLM training. The core idea is that the three components of model states—Parameters (P), Gradients (G), and Optimizer States (OS)—have asymmetric memory footprints and different access patterns during training, so forcing them to use identical sharding strategies (as ZeRO, ZeRO++, and MiCS do) leaves significant performance on the table. AMSP allows each component to independently choose its sharding factor and device mesh, formulates the resulting communication cost as an optimization problem subject to GPU memory constraints, and implements an execution engine that overlaps communication with computation far more effectively than prior systems.

### 3.1 Reader Orientation

AMSP is a **planner-executor system** that sits between the user's model specification and the distributed training runtime. You give it your model architecture, training hyperparameters, and cluster description; it figures out how to shard parameters, gradients, and optimizer states across GPUs to minimize communication time without exceeding GPU memory, then runs the training with those sharding decisions and a heavily optimized communication-computation overlap schedule. The problem it solves is that ZeRO's communication overhead scales poorly with GPU count—training LLaMA-7B drops from 63% MFU on 8 GPUs to 36% on 1024 GPUs (Section I)—and the solution's "shape" is a two-component architecture: an offline planner that solves a constrained optimization over independent per-component sharding factors, and an online executor that implements the chosen strategy with fine-grained overlap between NCCL collectives and PyTorch computation.

### 3.2 Big-Picture Architecture (Diagram in Words)

AMSP has two major components connected by a simple workflow:

**Component 1: The Planner (offline, before training starts).** This component takes the model specification (number of layers, hidden dimensions, parameter count `Φ`), training configuration (micro-batch size `B`, micro-batch number `M`, sequence length `S`), and cluster description (GPUs per node `R`, total nodes `N`, GPU memory capacity). It has three internal submodules:

- **Pre-Filter:** Eliminates sharding configurations that would cause unnecessary communication (e.g., sharding across nodes when intra-node sharding would suffice, based on rules in Section IV-B).
- **Communication-Profiler:** An offline-profiled lookup table mapping `(operation, message_size, device_mesh)` → effective bandwidth, built by running NCCL microbenchmarks on the target cluster once before any training job.
- **Solver:** Formulates and solves the integer programming problem (Equations 1–7) to find the `(s0_p, s1_p, s0_g, s1_g, s0_os, s1_os)` tuple that minimizes total communication time `T_comm` subject to `D_total ≤ GPU_Memory_Capacity` and the dependency constraints.

The Planner outputs a single optimal sharding configuration—six integers plus the device mesh layout—that the Executor will use.

**Component 2: The Executor (online, during training).** This component runs the actual distributed training loop using the Planner's chosen sharding factors. It has two internal mechanisms:

- **Communication Overlap Scheduler:** Uses PyTorch hooks (Table III) to launch NCCL collectives at precise points in the forward/backward computation graph so that communication runs concurrently with computation rather than blocking it. This handles AllGather for parameter prefetching, ReduceScatter for gradient distribution, AllReduce for gradient synchronization, and Broadcast for updated parameter dissemination—all interleaved with layer computations.
- **Topology-Aware Communication Placement:** When sharding spans multiple nodes (`s1_{p,g,os} > 1`), groups the participating nodes under the same leaf switches in the spine-leaf network topology to minimize cross-spine traffic.

**Information flow (step by step):**

1. User provides model architecture + training hyperparams + cluster info → Planner.
2. Pre-Filter narrows the search space of valid `(s0, s1)` tuples.
3. Communication-Profiler supplies `w(o, v, p0×p1)` values for the target cluster.
4. Solver runs integer programming to find the `(s0, s1)` tuple minimizing `T_comm` subject to memory constraint.
5. Executor initializes the distributed training process with the chosen sharding factors.
6. During each training step, hooks fire at specific points (pre-forward, post-forward, pre-backward, post-backward, tensor gradient accumulation) to launch NCCL operations, overlapping them with computation according to the schedule in Section V-C.
7. At the end of each step, Broadcast operations disseminate updated parameters, overlapping with the next step's forward pass.

#### Communication Cost Model: Profiling-Based Instead of Analytical

Before explaining how AMSP optimizes sharding, we must understand how it *predicts* the communication cost of any given sharding configuration—because the solver needs accurate cost estimates to choose between alternatives. The paper explicitly rejects the standard α-β analytical model and instead uses offline profiling.

The α-β model (Thakur and Gropp, 2003) predicts the time for a collective communication operation on `p` GPUs with message size `v` as:

$$t = \alpha + \beta \cdot v$$

where `α` is the per-message latency (startup overhead, independent of size) and `β` is the inverse bandwidth (time per byte transferred). For ring-based algorithms, this generalizes to formulas like:

$$t_{rs} = (p - 1)\left(\alpha + \frac{v}{w \cdot p}\right)$$

for ReduceScatter, where `w` is the physical link bandwidth.

**Why this fails in modern GPU clusters.** The paper identifies three reasons (Section IV-A). First, NCCL uses multiple communication algorithms beyond ring—Tree, Collnet, CollnetDirect, and CollnetChain—and switches between them dynamically based on message size and topology. A single α-β formula cannot capture this algorithm selection. Second, production clusters often deploy In-Network Aggregation solutions (e.g., Mellanox SHARP) that offload reduction operations onto network switches, fundamentally changing the communication pattern in ways the α-β model does not describe. Third, effective bandwidth is demonstrably non-linear with both message size and scale (Figure 3): AllGather bandwidth drops from ~1500 Gb/s at 1G messages to ~500 Gb/s at 1M messages on the same 8×64 GPU configuration, and ReduceScatter bandwidth at a fixed 256M message degrades from ~1200 Gb/s on 8×1 GPUs to ~600 Gb/s on 8×64 GPUs.

**AMSP's profiling-based alternative.** Instead of analytical formulas, AMSP pre-profiles the effective bandwidth for each collective operation on the target cluster:

$$t(o, v, p_0 \times p_1) = \frac{v}{w(o, v, p_0 \times p_1)}$$

where `o ∈ {AG, RS, AR, BC}` is the collective operation type (AllGather, ReduceScatter, AllReduce, Broadcast), `v` is the message size in bytes, `p_0 × p_1` is the device mesh (intra-node GPUs × inter-node count), and `w(o, v, p_0 × p_1)` is the **empirically measured effective bandwidth** obtained by running NCCL performance tests on the target cluster once before any training job.

**What it computes:** given an operation type, the number of bytes to transfer, and the set of participating GPUs organized by their node topology, this formula divides the data volume by the measured sustainable bandwidth to get wall-clock communication time. For message sizes `v` that were not explicitly profiled, AMSP uses linear interpolation between the nearest profiled sizes.

**Why this form:** the profiling approach captures all the real-world complexities that analytical models miss—NCCL algorithm selection, switch-level aggregation, network congestion patterns, and topology asymmetries—by measuring the actual end-to-end performance of the production fabric. The trade-off is that profiling must be repeated if the cluster configuration changes (new NICs, different switch topology, GPU generation upgrade), but the cost is a one-time offline expense amortized across all subsequent training jobs. The interpolation for unprofiled sizes assumes local linearity in the bandwidth-vs-size curve, which Figure 3 suggests is reasonable for the mid-range message sizes (64M–1G) that dominate LLM training communication.

#### Flexible Model States Sharding and the Dependency Rule

AMSP's central innovation is allowing each of the three model state components—Parameters (P), Gradients (G), and Optimizer States (OS)—to independently select from three sharding strategies and to specify their own device mesh. This requires formalizing what "sharding strategy" means and establishing correctness constraints.

**The three sharding strategies.** For any component `c ∈ {p, g, os}`, AMSP defines a sharding factor `s_c = s0_c × s1_c` where `s0_c` is the number of GPUs **within a single node** over which the tensor is sharded (≤ `R`, the GPUs per node), and `s1_c` is the number of **nodes** across which the tensor is sharded (≤ `N`, the total node count). The product `s0_c × s1_c` is the total number of GPUs participating in the shard group for that component. Three regimes emerge:

- **Full-Replica:** `s0_c × s1_c = 1`. Every GPU holds a complete copy of the tensor. If all three components use Full-Replica, this degenerates to standard data parallelism (no ZeRO).
- **Full-Sharding:** `s0_c × s1_c = sdp` (the total data-parallel group size). The tensor is split across all GPUs, with each GPU holding `1/sdp` of the data. If all three use Full-Sharding, this is equivalent to ZeRO-3.
- **Partial-Sharding:** `1 < s0_c × s1_c < sdp`. The tensor is sharded within a subgroup of GPUs and replicated across subgroups. If all three use the same Partial-Sharding factor, this is equivalent to MiCS.

The key departure from prior work is that `sp`, `sg`, and `sos` can be *different* from each other, enabling configurations like `sp=1, sg=1, sos=8` (parameters and gradients fully replicated, optimizer states sharded within a node) that no existing system can express.

**The dependency rule (why `sp ≤ sg ≤ sos` is mandatory).** The paper identifies a critical correctness constraint that governs the relationship between sharding factors. Throughout training, the framework uses three data flows:

1. Parameters → forward/backward computation → Gradients are computed with respect to those parameters.
2. Gradients are synchronized and sharded → Optimizer uses local gradients to update local optimizer states → Updated parameters are produced.
3. Updated parameters are disseminated → Next training step uses them.

If a GPU holds gradients or optimizer states for parameters it does not manage locally, it must communicate to obtain those parameters or send those gradients, incurring unnecessary data movement. Figure 4 illustrates the failure case: with `sp=2, sg=2, sos=1`, GPU-0 and GPU-2 share the same parameter shard (since `sp=2` means each shard is replicated across `sdp/sp` GPUs), but `sos=1` means each GPU stores complete optimizer states. GPU-0 would update parameters that GPU-2 also stores, and without additional communication, the two copies would diverge. Alternatively, forcing synchronization would add communication that the sharding was supposed to avoid.

The dependency rule formalizes the correct ordering:

$$R \geq s0_{dp} \geq s0_{os} \geq s0_g \geq s0_p$$

$$N \geq s1_{dp} \geq s1_{os} \geq s1_g \geq s1_p$$

**What these constraints mean operationally.** The intra-node sharding factor for parameters (`s0_p`) must be ≤ the intra-node factor for gradients (`s0_g`), which must be ≤ the intra-node factor for optimizer states (`s0_os`), which must be ≤ the total intra-node DP group size (`s0_dp`), which must be ≤ the GPUs per node (`R`). The same ordering applies inter-node with `s1`. The intuition: you can shard optimizer states *more* aggressively (across more GPUs) than parameters, because each optimizer state shard only needs to update one parameter shard, but you cannot shard parameters more aggressively than optimizer states without creating mismatches between which GPU holds a parameter and which GPU holds its optimizer state. Setting `sp = sg = sos` (the uniform sharding of prior systems) trivially satisfies the constraint, but AMSP's flexibility comes from allowing strict inequality, e.g., `sp < sg < sos`.

**Device mesh semantics.** The notation `s0 × s1` defines both the group size and the topology. `s0` GPUs within the same node (connected by NVLink) and `s1` such groups across nodes (connected by InfiniBand). This matters because intra-node communication uses much higher effective bandwidth (NVLink at 600 GB/s bidirectional per GPU on DGX-A100) than inter-node (InfiniBand HDR at 400 GB/s bidirectional per *node* total, shared across 8 GPUs). By making `s0` and `s1` explicit optimization variables rather than collapsing them into a single `s`, AMSP can prefer configurations that keep collective operations within nodes (high `s0`, low `s1`) when possible, reducing the more expensive inter-node traffic.

#### Communication Time Analysis: Parameters Sharding (`T_p`)

When `sp = s0_p × s1_p > 1`, parameters are sharded across `sp` GPUs. Each GPU holds `Φ/sp` parameters. Before any forward or backward computation that uses those parameters, the missing shards must be gathered; after gradients are computed, they must be redistributed and aggregated. The paper analyzes this at the granularity of individual modules within Transformer layers (e.g., the Q, K, V, and output projection linear layers, each with its own parameter tensor).

**Per-module AllGather before forward and backward.** For each of the `K` modules in each of the `L` layers, and for each of the `M` micro-batches in a training step, the system launches an AllGather operation on the `sp = s0_p × s1_p` GPUs in the parameter sharding group. The input to AllGather is each GPU's local parameter shard; the output is the fully assembled parameter tensor for that module. Since parameters are stored in FP16 during mixed-precision training, the message size per module is `2Φ_i` bytes, where `Φ_i` is the number of parameters in module `i`. This AllGather happens twice per module per micro-batch—once for the forward pass, once for the backward pass (which needs the parameters again to compute gradients with respect to weights and inputs).

**Per-module ReduceScatter after backward.** After the backward pass computes gradients for module `i`, those gradients exist in full on each GPU (since the forward/backward operated on assembled parameters). To return to the sharded state, the system launches ReduceScatter on the same `sp` GPUs. ReduceScatter sums the gradients across all participating GPUs (reduction) and scatters the result so that each GPU receives only the gradient shard corresponding to the parameters it manages (scatter). The message size is again `2Φ_i` bytes.

**The total communication time formula:**

$$T_p = M \cdot L \cdot \sum_{i=0}^{K} \left[2 \cdot t(AG, 2\Phi_i, s0_p \times s1_p) + t(RS, 2\Phi_i, s0_p \times s1_p)\right]$$

where `M` is the number of micro-batches per step, `L` is the number of Transformer layers, `K` is the number of modules per layer (indexed from 0 to K), `Φ_i` is the parameter count of module `i`, and `t(o, v, mesh)` is the profiled communication time function from Section IV-A.

**What it computes:** the total wall-clock time spent in AllGather and ReduceScatter operations due to parameter sharding, summed across all modules, layers, and micro-batches. The factor of 2 before the AllGather term accounts for one AllGather in the forward pass and one in the backward pass per module per micro-batch.

**Why this form:** the per-module granularity is essential because AMSP overlaps the AllGather for module `i+1` with the computation of module `i` (Section V-C). Treating communication at the whole-layer or whole-model granularity would miss this overlap opportunity. The formula exposes that `T_p` scales linearly with `M`, `L`, and the number of modules—meaning parameter sharding becomes especially expensive when training with many micro-batches (large `M`), deep models (large `L`), or when the model has many small modules (each requiring its own collective launch, incurring per-operation latency).

**Overlap potential.** The paper notes that "parameters sharding allows for overlapped communication with computation" because the AllGather for module `i+1` can be launched while module `i` is still computing, and similarly ReduceScatter for module `i` can be launched while module `i+1`'s GradInput is computing. This overlap is not captured in `T_p` (which represents total communication time, not exposed critical-path time), but the solver's objective minimizes `T_comm` as a proxy for exposed communication, and the Executor's overlap mechanisms (Section V-C) ensure that as much of this `T_p` as possible is hidden behind computation.

#### Communication Time Analysis: Optimizer States Sharding (`T0_os + T1_os`)

Optimizer states consume the most memory (12Φ bytes in FP32 for Adam's `m` and `v` moments) and have a different access pattern than parameters or gradients. They are updated **once per training step** after all micro-batches have been processed and gradients accumulated, not per-micro-batch or per-layer. This means the communication for optimizer states sharding has two distinct phases:

**Phase 1: Gradient synchronization via AllReduce (`T0_os`).** When `sos > sp`, each set of `Φ/sp` parameters is managed by `sos/sp` GPUs (the optimizer states sharding subgroup), with each GPU in the subgroup holding `1/(sos/sp)` of the optimizer states for those parameters. Before any GPU can update its optimizer states, it needs the gradients for the parameters corresponding to its states. Since gradients were computed using the `sp`-way sharded parameters, gradients for the same parameter set are replicated across `sdp/sp` GPUs (all GPUs that share that parameter shard). The system must sum these replicated gradients and deliver the relevant portions to each GPU in the optimizer subgroup.

AMSP uses **AllReduce on `sdp/sp` GPUs** (the parameter-sharing group) rather than ReduceScatter. The input is `Φ/sp` parameters' worth of gradients (FP16, so `2Φ/sp` bytes). AllReduce sums gradients across all GPUs in the group and delivers the complete summed result to every participant. Then each GPU applies a **select-and-drop mechanism**: it keeps only the gradient elements corresponding to its optimizer state shard and discards the rest. This is necessary because the inter-tensor sharding scheme for optimizer states (discussed below) means different GPUs in the subgroup manage different *whole* parameters, so which elements to keep varies per GPU.

The system processes gradients in buckets of size `U` (a configurable byte count) to enable pipelining: as soon as a bucket is full of gradients from the backward pass, AllReduce launches on that bucket without waiting for the entire backward pass to finish. With `Φ` trainable parameters (counting only those requiring gradients), the total number of FP16 gradient elements is `Φ`, consuming `2Φ` bytes. Divided into buckets of size `U`, this yields `2Φ/U` AllReduce operations. However, each AllReduce operates on `sdp/sp` GPUs, and only one such group is active at a time per parameter set. Since there are `sp` independent parameter shards, the effective number of concurrent AllReduce operations scales with `sp`, but the formula simplifies by amortizing:

$$T0_{os} = \frac{2\Phi}{U \cdot sp} \cdot t\left(AR, U, \frac{s0_{dp}}{s0_p} \times \frac{s1_{dp}}{s1_p}\right)$$

**What it computes:** the total time spent in gradient-synchronization AllReduce operations for a single training step, assuming bucketed processing where each AllReduce transfers `U` bytes (the bucket size). The divisor `sp` in the denominator accounts for the fact that the `2Φ` total gradient bytes are partitioned across `sp` parameter sharding groups, each operating independently.

**Why this form and not ReduceScatter:** the paper explicitly considers ReduceScatter as an alternative (Section IV-C, Gradients Sharding subsection) but rejects it for optimizer states sharding because of the inter-tensor distribution scheme. In inter-tensor sharding (Figure 6b), each optimizer state tensor is assigned as a whole to a GPU using a greedy balancing algorithm, meaning different GPUs in the subgroup hold different numbers of parameter tensors. ReduceScatter requires that all participants receive equal-sized chunks after the scatter, which is incompatible with inter-tensor distribution. AllReduce with select-and-drop sidesteps this: everyone gets everything, and each GPU keeps what it needs. The memory overhead of temporarily holding the full AllReduce result is acceptable because the select-and-drop happens immediately.

**Phase 2: Updated parameter dissemination via Broadcast (`T1_os`).** After each GPU updates its local optimizer states and produces updated parameter values, these updated parameters must be propagated to all other GPUs in the optimizer states sharding subgroup that share the same parameter set but hold different optimizer state shards. For example, in Figure 4(b), GPU-0 and GPU-2 share parameter shard A but hold different halves of the optimizer states for those parameters. After GPU-0 updates its half and GPU-2 updates its half, each needs the other's updated parameters.

Because of inter-tensor distribution, the updated parameters are not evenly sized across GPUs—one GPU may have updated 3 large parameter tensors, another may have updated 5 small ones. Direct AllGather would require all participants to have equal-sized contributions, which doesn't hold. Instead, AMSP uses **a group of Broadcast operations**: for each of the `sos/sp` GPUs in the subgroup, one GPU broadcasts its updated parameters (averaging `2Φ/sos` bytes) to the other `sos/sp - 1` GPUs. This requires `sos/sp` separate Broadcast calls, each initiated as an NCCL group call:

$$T1_{os} = \frac{sos}{sp} \cdot t\left(BC, \frac{2\Phi}{sos}, \frac{s0_{os}}{s0_p} \times \frac{s1_{os}}{s1_p}\right)$$

**What it computes:** the total time to disseminate updated parameters within each optimizer states sharding subgroup, as the sum of `sos/sp` Broadcast operations, each moving `2Φ/sos` bytes on average across `sos/sp` GPUs.

**Why Broadcast and not AllGather:** the inter-tensor sharding scheme (Figure 6b) distributes each optimizer state tensor in its entirety to one GPU and uses a greedy algorithm to balance total bytes per GPU. This produces variable-sized per-GPU contributions. AllGather requires equal-sized inputs from all participants; Broadcast places no such constraint. The paper notes (Section IV-C) that intra-tensor sharding (Figure 6a, where a single parameter tensor is split evenly into sub-tensors) *would* allow AllGather, but inter-tensor sharding is preferred because it is compatible with FP8 training where per-tensor scaling factors must be distributed alongside the tensor shards—a practical consideration for future low-precision training.

**Overlap potential with optimizer states communication.** The backward pass's AllReduce on gradients (Phase 1) can be overlapped with the backward computation of preceding layers: as layer `i` finishes computing gradients, its gradients are bucketed, and AllReduce launches asynchronously while layers `i-1`, `i-2`, etc. continue their backward computation. The Broadcast of updated parameters (Phase 2) occurs after the optimizer step, which happens between training steps, and AMSP overlaps it with the forward computation of the *next* step—as the forward pass processes layer 0, updated parameters for layer 1 are being broadcast.

#### Communication Time Analysis: Gradients Sharding (`T_g`)

Gradients sharding provides an intermediate option between fully replicated gradients (`sg = 1`, where each GPU holds complete gradients) and fully sharded gradients (`sg = sp`, where each GPU holds only the gradients for its parameter shard). The paper introduces the flexibility to set `sg > sp` for additional memory savings, with the constraint that `sg ∈ {sp, sos}` (gradients must be sharded at either the parameter sharding granularity or the optimizer states sharding granularity—no other values).

**When `sg = sp`:** This is the default case already handled by parameter sharding. After each micro-batch's backward pass, ReduceScatter on `sp` GPUs distributes and aggregates gradients. No additional communication is needed for gradient sharding. `T_g = 0` in this case.

**When `sg = sos > sp`:** Each GPU manages only `Φ/sg` gradients (matching its optimizer states shard) rather than `Φ/sp` gradients. Between micro-batches (except the last one, where gradients are used for the optimizer step), the system must aggregate and redistribute gradients so that each GPU accumulates only the gradient elements it will eventually use for the optimizer update.

AMSP uses **AllReduce on `sg/sp` GPUs** for each of the `M-1` non-final micro-batches. The `sg/sp` GPUs are the subset of the parameter-sharing group that collectively hold the full gradient set for those parameters. AllReduce sums the gradients across these GPUs and delivers the result to all participants, after which each GPU applies the same select-and-drop mechanism as in optimizer states sharding—keeping only its allocated gradient elements.

$$T_g = (M - 1) \cdot \frac{2\Phi}{U \cdot sp} \cdot t\left(AR, U, \frac{s0_g}{s0_p} \times \frac{s1_g}{s1_p}\right)$$

**What it computes:** the total time for gradient-distribution AllReduce operations across all non-final micro-batches. The factor `(M - 1)` reflects that the last micro-batch's gradients are handled by the optimizer states sharding phase (`T0_os`). The divisor `sp` accounts for the `sp` independent parameter sharding groups operating in parallel.

**Why not ReduceScatter here either:** the same inter-tensor distribution argument applies. Gradients are associated with parameters, and since parameters are distributed unevenly across GPUs in the inter-tensor scheme, gradients have uneven sizes too. AllReduce with select-and-drop is the uniform solution.

**Overlap potential.** The AllReduce for layer `i`'s gradients can be launched while layer `i-1`'s backward computation is still running, using the same bucketing strategy as for optimizer states. The paper notes this is "facilitated through hooks integrated into the AccumulateGrad of parameters" (Section V-C3).

#### GPU Memory Consumption Model

The memory model decomposes total GPU memory `D_total` into three components: model states, activations, and temporary buffers. The model state memory is directly determined by the sharding factors:

$$D_{modelstate}(s0_p, s1_p, s0_g, s1_g, s0_os, s1_os) = \frac{2\Phi}{s0_p \cdot s1_p} + \frac{2\Phi}{s0_g \cdot s1_g} + \frac{12\Phi}{s0_{os} \cdot s1_{os}}$$

**What each term means:** The three terms correspond to parameters (stored in FP16, 2 bytes per parameter, divided by the sharding factor `sp = s0_p × s1_p`), gradients (FP16, 2 bytes per parameter, divided by `sg`), and optimizer states (FP32 for Adam's first and second moment buffers `m` and `v`, 4 bytes each × 2 = 8 bytes, plus FP32 master parameters = 4 bytes, total 12 bytes per parameter, divided by `sos`). The total model state memory is `2Φ/sp + 2Φ/sg + 12Φ/sos` bytes per GPU.

**Example calculation.** For LLaMA-7B (`Φ ≈ 7 × 10^9`), using AMSP's optimal configuration `sp=1, sg=1, sos=8` (Table IV): parameters occupy `2 × 7B / 1 = 14 GB`, gradients occupy `2 × 7B / 1 = 14 GB`, and optimizer states occupy `12 × 7B / 8 = 10.5 GB`, totaling `38.5 GB` for model states. Compare to ZeRO-3 with `sp = sg = sos = 1024`: each component occupies only 0.014–0.082 GB, totaling ~0.11 GB, but at the cost of massive communication.

**Total memory:**

$$D_{total} = D_{modelstate} + D_{activation} + D_{tmp}$$

where `D_activation` is the memory for intermediate activations stored during the forward pass (needed for gradient computation in the backward pass, with optional activation recomputation trading compute for memory) and `D_tmp` covers communication buffers (e.g., the temporary full AllReduce results before select-and-drop) and other transient allocations like cuBLAS workspace. The paper states that existing methodologies for analyzing activation memory (from Megatron-LM and the original ZeRO papers) are "seamlessly integrated," meaning AMSP uses standard activation memory estimation rather than contributing a new model for `D_activation`.

**Why this decomposition matters for the solver.** The model state memory `D_modelstate` is the only term that changes with the sharding factors—it is the control variable. `D_activation` depends on model architecture, micro-batch size, sequence length, and whether activation recomputation is enabled, but not on sharding. The solver's constraint `D_total ≤ GPU_Memory_Capacity` (Equation 2) becomes: given the fixed activation and temporary memory overhead for this model configuration, how much can we afford to spend on model state replication to reduce communication? A model with small activations (e.g., LLaMA-7B with activation recomputation disabled, as in the paper's experiments) has more headroom for aggressive replication (smaller `sp`, `sg`, `sos` values, meaning less sharding, more memory, less communication). A model with large activations (e.g., LLaMA-30B with long sequences) forces more aggressive sharding to stay within memory limits.

#### The Planner: Formulating and Solving the Optimization Problem

The Planner's solver takes the profiled communication costs, the memory model, and the user's configuration, and finds the sharding factors that minimize total communication time without exceeding GPU memory. This is formulated as an integer programming problem (Equations 1–7).

**Objective function (Equation 1):**

$$\text{Minimize } T_{comm}(s0_p, s1_p, s0_g, s1_g, s0_{os}, s1_{os})$$

where `T_comm = T_p + T_g + T0_os + T1_os` (the sum of all four communication time components from Section IV-C).

**What it computes:** the single-step communication overhead for a given six-tuple of sharding factors. The solver searches over valid tuples to find the one with minimum `T_comm`.

**Why this objective and not throughput or MFU:** minimizing communication time is a well-defined, tractable objective that directly corresponds to improving throughput—less time spent communicating means more time available for computation, assuming the overlay strategy successfully hides as much communication as possible. Throughput or MFU would require modeling the overlap effectiveness, which depends on the specific computation graph and is harder to capture in a static optimization. `T_comm` serves as a reliable proxy: configurations with lower `T_comm` consistently produce higher MFU in the paper's evaluation.

**Constraint 2: GPU memory capacity.**

$$D_{total} \leq GPU\_Memory\_Capacity$$

The total memory (model states + activations + temporary buffers) must fit within the GPU's physical memory. On the A800 GPUs used in the evaluation, this is 80 GB.

**Constraints 3–4: Dependency rule.**

$$1 \leq s0_p \leq s0_g \leq s0_{os} \leq s0_{dp} \leq R$$

$$1 \leq s1_p \leq s1_g \leq s1_{os} \leq s1_{dp} \leq N$$

These enforce the correctness ordering from Section IV-B: parameters cannot be sharded more aggressively than gradients, which cannot be sharded more aggressively than optimizer states. All are bounded above by the total data-parallel group size (intra-node `s0_dp` and inter-node `s1_dp`) and the physical topology limits (`R` GPUs per node, `N` nodes).

**Constraints 5–6: Divisibility (Pre-Filter 1).**

$$s0_i \times k = s0_{dp}, \quad k \in \mathbb{Z}, \quad i \in \{p, g, os\}$$

$$s1_j \times k = s1_{dp}, \quad k \in \mathbb{Z}, \quad j \in \{p, g, os\}$$

The intra-node sharding factor for each component must evenly divide `s0_dp` (the number of GPUs per node in the data-parallel group), and similarly for the inter-node factor dividing `s1_dp`. This ensures that all GPUs participate in the training—there are no "leftover" GPUs that are neither in a sharding subgroup nor usefully employed. For example, if `s0_dp = 8` (all 8 GPUs in a node participate in DP), `s0_p` can only be 1, 2, 4, or 8. It cannot be 3 or 6 because those would leave 2 GPUs unused per node.

**Constraint 7: Cross-node minimization (Pre-Filter 2).**

$$s0_i = s0_{dp}, \quad \text{if } s1_i > 1, \quad i \in \{p, g, os\}$$

If a component is sharded across multiple nodes (`s1_i > 1`), then it must use all available GPUs within each node (`s0_i = s0_dp`). The rationale (illustrated in Figure 8): selecting `(s0_p=1, s1_p=2)` would shard parameters across 2 GPUs on different nodes, forcing every AllGather and ReduceScatter to cross the inter-node network. The alternative `(s0_p=2, s1_p=1)` shards across 2 GPUs within the same node, keeping all communication on NVLink. Since intra-node bandwidth is substantially higher (and latency lower) than inter-node, the solver should always prefer intra-node sharding when the total sharding factor `sp` is small enough to fit within a single node. Constraint 7 encodes this preference by prohibiting inter-node sharding unless the component is already using all intra-node GPUs—you only "spill over" to inter-node when intra-node capacity is exhausted.

**How the solver works in practice.** With these constraints, the search space is small enough for brute-force enumeration. For a typical configuration with `R=8, N=128` (1024 GPUs total), `s0_dp=8`, `s1_dp=128`. The divisibility constraint limits `s0` values to {1, 2, 4, 8} and `s1` values to divisors of 128 (powers of 2 up to 128). The dependency constraint `s0_p ≤ s0_g ≤ s0_os` and the cross-node constraint further prune the tree. The solver iterates over all valid six-tuples, computes `T_comm` for each using the profiled bandwidths, computes `D_total` using the memory model, and selects the tuple with minimum `T_comm` that satisfies the memory constraint. If no tuple satisfies the memory constraint (possible for very large models on small GPU counts), the solver reports infeasibility, and the user must enable activation recomputation, reduce micro-batch size, or add GPUs.

**Output of the solver.** A concrete sharding strategy—for LLaMA-7B on 1024 GPUs, the solver outputs `(s0_p=1, s1_p=1, s0_g=1, s1_g=1, s0_os=8, s1_os=1)`, meaning: parameters fully replicated, gradients fully replicated, optimizer states sharded within each node (8 GPUs per shard group) and replicated across nodes. For LLaMA-13B: `(s0_p=4, s1_p=1, s0_g=4, s1_g=1, s0_os=8, s1_os=1)`—partial sharding for parameters and gradients within half a node, full replication across nodes, and optimizer states sharded within a node. For LLaMA-30B: `(s0_p=8, s1_p=1, s0_g=8, s1_g=1, s0_os=8, s1_os=4)`—parameters and gradients fully sharded within a node, optimizer states sharded across 4 nodes × 8 GPUs = 32 GPUs total.

#### The Executor: Computation-Communication Overlap via PyTorch Hooks

The Planner provides optimal sharding factors; the Executor implements them efficiently. The core mechanism is **fine-grained overlap** between NCCL collective operations and PyTorch module computations, orchestrated through specific hooks in PyTorch's autograd system.

**Hooks used (Table III).** AMSP leverages five PyTorch hook types:

- `register_forward_pre_hook` on `nn.Module`: called immediately **before** the module's forward method executes. Used to wait for prefetched AllGather of parameters to complete before the module can use them.
- `register_forward_hook` on `nn.Module`: called immediately **after** the module's forward method completes. Used to release gathered parameters (free memory) after the module no longer needs them.
- `register_full_backward_pre_hook` on `nn.Module`: called before the module's backward computation. Used to launch AllGather for the next module's parameters during the backward pass.
- `register_full_backward_hook` on `nn.Module`: called after the module's backward computation completes. Used to launch ReduceScatter on GradWeight.
- `register_hook` on `torch.Tensor`: called when a tensor's gradient is accumulated (AccumulateGrad). Used to trigger AllReduce on bucketed gradients and to ensure ReduceScatter completion before gradient-dependent operations.

**Overlap for parameters sharding (Figure 9).**

*Forward pass (Figure 9a).* Before the forward computation of layer `l` begins, the system has already launched AllGather operations to prefetch parameters for each module in layer `l+1`. When layer `l`'s modules execute their forward methods, these AllGather operations run concurrently on the GPU's communication stream (NCCL uses a separate CUDA stream from computation). At the start of layer `l+1`'s forward, `register_forward_pre_hook` on each module of layer `l+1` calls `wait()` on the corresponding AllGather stream, ensuring parameters are available before computation starts. After each module's forward completes, `register_forward_hook` releases the assembled parameter tensor (the gathered version is a temporary; the shard is persistent). This means the forward computation of layer `l` overlaps with the parameter collection for layer `l+1`, hiding communication latency behind useful compute.

*Backward pass without activation recomputation (Figure 9b).* The backward pass is more complex because it involves both gathering parameters (for gradient computation) and scattering gradients (after computation). For each module `i` in a layer, the backward pass computes `GradWeight` (gradients with respect to the module's weights) and `GradInput` (gradients with respect to the module's input, to propagate to the previous layer). AMSP's strategy:

1. Before the backward of module `i` starts, `register_full_backward_pre_hook` launches AllGather to fetch parameters for the **next** module `i+1` (not the current one—those were prefetched earlier).
2. Module `i`'s backward computation runs: first `GradWeight` is computed, then `GradInput`.
3. Immediately after `GradWeight` computation, AMSP launches ReduceScatter on `GradWeight` asynchronously.
4. The ReduceScatter runs concurrently with the computation of `GradInput` for module `i`.
5. `register_full_backward_pre_hook` on module `i+1` waits for the AllGather launched in step 1.

A critical design choice: launching all AllGather operations for an entire layer simultaneously (rather than per-module) would block the ReduceScatter operations because NCCL serializes operations on the same communicator when they target the same device memory. By fetching parameters one module at a time, AMSP interleaves AllGather and ReduceScatter, allowing both communication streams to make progress without blocking each other.

*Decoupling ReduceScatter lifecycle from the backward function.* A subtlety: ReduceScatter may not complete by the time `GradInput` computation finishes and the backward function returns. Standard PyTorch semantics would block here (autograd expects gradients to be ready when the backward function completes). AMSP decouples this by not waiting on the ReduceScatter inside the backward function. Instead, an additional `register_hook` on the `AccumulateGrad` of each parameter waits for the corresponding ReduceScatter to finish before those gradients are used in subsequent operations (e.g., AllReduce for optimizer states sharding, or the optimizer step itself). This allows the backward computation of the next module to begin immediately, without stalling for communication.

*Backward pass with activation recomputation (Figure 9c).* When activation recomputation is enabled, the backward pass for a layer includes an additional forward computation (to recompute the activations that were discarded during the initial forward pass to save memory). AMSP adapts its overlap strategy:

1. At the start of the recomputation forward for layer `l`, AllGather is launched to prefetch parameters for layer `l+1`.
2. The recomputation forward runs for layer `l`.
3. **Unlike the first forward pass**, AMSP retains the gathered parameters after the recomputation forward—they will be needed for the subsequent backward computation on layer `l`, so discarding and re-gathering them would be wasteful.
4. The backward computation proceeds as in the non-recomputation case: `GradWeight` launches ReduceScatter, `GradInput` runs concurrently, and the next module's parameters are prefetched.

Retaining parameters across the recomputation forward and backward saves one AllGather operation per module per layer per micro-batch, which is significant given that activation recomputation already adds computational overhead.

**Overlap for optimizer states sharding.**

*Gradient AllReduce during backward.* During the backward pass of the last micro-batch (the only one where optimizer states will be updated), gradients must be synchronized via AllReduce across `sdp/sp` GPUs. AMSP uses a **bucketing strategy**: as each parameter's gradient is computed and accumulated, it is placed into a fixed-size bucket (size `U` bytes, flattened into a contiguous buffer). When a bucket is full, AllReduce launches on that bucket immediately, without waiting for the rest of the backward pass to finish. This AllReduce overlaps with the backward computation of earlier layers. The bucketing is triggered by `register_hook` on `AccumulateGrad`—the same hook that waits for ReduceScatter completion, ensuring gradients are fully reduced (within the parameter sharding group) before being AllReduced across the larger DP group.

*Broadcast overlap with next step's forward.* After the optimizer updates parameters at the end of a step, the updated values must be broadcast within each optimizer states sharding subgroup. AMSP launches these Broadcast operations asynchronously and overlaps them with the forward computation of the **next training step**. Two optimizations make this work:

1. **Forward pre-hook synchronization:** Each module's `register_forward_pre_hook` calls `wait()` on the Broadcast for that module's parameters before the forward computation begins. This ensures the forward pass sees the most recent parameter values without requiring all Broadcasts to complete before the forward pass starts.

2. **Forward computation ordering aligned with Broadcast order:** AMSP deliberately orders the forward computation of layers to match the sequence in which Broadcast operations are issued. If the Broadcast for layer 0's parameters finishes quickly (small parameter tensors, or early in the NCCL schedule), layer 0 can start computing immediately. If layer 31's Broadcast is still in flight, the forward pass can process layers 0–30 while waiting, rather than stalling at the beginning. This is a scheduling optimization that reduces head-of-line blocking.

**Overlap for gradients sharding (when `sg > sp`).**

For non-final micro-batches when `sg = sos > sp`, each GPU must AllReduce gradients across `sg/sp` GPUs to aggregate and redistribute them. This uses the same bucketing strategy as the optimizer states AllReduce: gradients are accumulated into buckets during the backward pass, and AllReduce launches asynchronously as each bucket fills. After AllReduce completes, each GPU applies select-and-drop (keeping only gradients for its assigned parameters) and releases the rest to conserve GPU memory. These AllReduce operations overlap with the backward computation of subsequent layers.

#### Topology-Aware Communication Placement

Modern GPU clusters use a **leaf-spine network architecture**: GPU nodes connect to leaf switches (typically top-of-rack), and leaf switches connect to spine switches that provide full bisection bandwidth across the cluster. Communication between GPUs under the same leaf switch stays within that switch; communication across leaf switches must traverse spine switches, incurring additional latency (switch processing delay) and potential congestion (if multiple leaf-spine paths contend for the same spine port).

**The optimization (Figure 10).** When a sharding factor requires inter-node communication (`s1_{p,g,os} > 1`), AMSP selects the participating nodes to **minimize the number of distinct leaf switches involved**. In Figure 10(a), with `s1 = 4` nodes needed, AMSP groups them under the same leaf switch when possible—all intra-leaf, zero spine traffic. In Figure 10(b), the nodes are scattered across different leaf switches, forcing all communication through spine switches. AMSP queries the cluster topology (which nodes connect to which leaf switches) and assigns the `s1` nodes for each sharding subgroup to colocate under as few leaf switches as possible, ideally one.

**Why this matters quantitatively.** The paper does not break out the isolated benefit of topology-aware placement in an ablation, but the mechanism addresses the effective bandwidth degradation observed in Figure 3 when moving from `8×1` to `8×64` GPUs: part of that degradation is due to cross-spine traffic. By keeping collective communication within a single leaf switch's domain, AMSP avoids the worst of the inter-switch bandwidth and latency penalties, effectively operating closer to the `8×1` (intra-leaf) bandwidth regime even when the total cluster is much larger.

**Implementation detail.** AMSP does not modify NCCL's internal topology detection or routing; it simply selects *which* GPUs form each communication group. NCCL's topology-aware algorithms will then automatically use the best available paths within that group. By constraining the group to nodes under the same leaf switch, AMSP ensures those best paths do not traverse spines.

## 4. Key Insights and Innovations

### Innovation 1: Decomposing ZeRO's Uniform Sharding Into Independent Per-Component Decisions

The dominant assumption in every prior ZeRO-based system—standard ZeRO (Rajbhandari et al., 2020), ZeRO++ (Wang et al., 2023), MiCS (Zhang et al., 2022), and PyTorch FSDP (Zhao et al., 2023)—is that the three model state components must share the same sharding factor: `sp = sg = sos`. This is not an arbitrary choice; it follows naturally from the mental model that "sharding" is a property of the training process as a whole, not of individual tensors. ZeRO-1 means "shard optimizer states," ZeRO-3 means "shard everything," and MiCS means "shard everything within a subgroup." The configuration space is a single knob, not a vector.

AMSP's fundamental conceptual move is to **treat Parameters (2Φ bytes), Gradients (2Φ bytes), and Optimizer States (12Φ bytes) as independent entities with asymmetric memory footprints and distinct communication lifecycles, each of which can independently select its sharding factor and device mesh.** The optimizer states are the elephant in the room: at 12Φ bytes in FP32 for Adam's moments plus master weights, they consume 6× more memory than parameters or gradients individually, and 3× more than both combined. Yet they are accessed only once per training step (during the optimizer update), not per-micro-batch or per-layer. Parameters, by contrast, are needed for every forward and backward pass of every micro-batch and every layer—their access frequency is `2 × M × L × K` times higher than optimizer states. Forcing these components into identical sharding means either (a) over-communicating on optimizer states to match the aggressive sharding needed for parameters (ZeRO-3's failure mode at scale: 4% MFU on LLaMA-7B at 1024 GPUs), or (b) over-consuming memory on parameters to match the conservative sharding sufficient for optimizer states (the memory bottleneck that ZeRO-1 hits with larger models).

The paper's evidence that this decomposition matters comes from the optimal configurations in Table IV. For LLaMA-7B, the solver selects `sp=1, sg=1, sos=8`: parameters and gradients fully replicated (zero communication for AllGather/ReduceScatter), optimizer states sharded within a node. This is neither ZeRO-1 (`sos=1024` on 1024 GPUs), ZeRO-3 (`sp=sg=sos=1024`), nor MiCS (`sp=sg=sos=8`). It is a hybrid that shards only the largest memory consumer while leaving the high-access-frequency components replicated, eliminating all per-layer per-micro-batch communication (`T_p = 0, T_g = 0`) and retaining only the per-step optimizer state communication (`T0_os + T1_os`). The result: 51% MFU vs. 36% for ZeRO-1 and 35% for MiCS on 1024 GPUs (Figure 11a). This is not an incremental tuning of an existing strategy—it is a qualitatively different configuration that no prior system could express.

The conceptual significance extends beyond this paper's results. By demonstrating that the `sp = sg = sos` constraint is an artificial limitation rather than a mathematical necessity, AMSP opens a design space that future systems can explore more systematically. The dependency rule (`sp ≤ sg ≤ sos ≤ sdp`) defines the valid region of this space and shows that correctness does not require equality—only ordering. This is analogous to how the Chinchilla scaling laws (Hoffmann et al., 2022) showed that model size and data quantity can be scaled independently rather than in fixed proportion, overturning the previous assumption that they should grow together. AMSP does for ZeRO sharding what Chinchilla did for pretraining compute allocation: it replaces a one-dimensional knob with a multi-dimensional optimization, and shows the gains are not marginal.

---

### Innovation 2: Formulating Sharding Strategy Selection as a Solvable Integer Programming Problem

Prior systems select their sharding strategy through hardcoded rules: ZeRO-1/2/3 are human-specified levels, MiCS shards within a configured subgroup size, and ZeRO++ adds a secondary parameter shard on top of ZeRO-3. There is no optimization—the user picks a strategy based on intuition or trial-and-error, and hopes it works for their model size, batch size, and cluster scale. When the strategy underperforms (as MiCS does vs. ZeRO-1 on LLaMA-7B at 1024 GPUs), there is no systematic mechanism to discover a better one.

AMSP reframes sharding strategy selection as a **constrained optimization problem** with a well-defined objective (minimize total communication time `T_comm`), a single constraint (GPU memory capacity), and a structurally constrained search space (dependency rules, divisibility, cross-node minimization). This is a conceptual shift from "configuration" to "solver"—the system figures out what to do rather than being told.

What makes this formulation intellectually distinctive is not the integer programming itself (which is straightforward, brute-forced over a small search space), but rather **what makes it possible**: the combination of (a) the per-component decomposition (Innovation 1), which creates the six-dimensional search space `(s0_p, s1_p, s0_g, s1_g, s0_os, s1_os)`; (b) the profiling-based communication cost model (Section IV-A), which replaces unreliable analytical formulas with empirical bandwidth measurements that capture real cluster behavior; and (c) the dependency rule (Section IV-B), which defines the feasible region of the search space without requiring the solver to reason about training correctness. Each of these is necessary; none is sufficient alone. Prior systems had none of them: they couldn't search over per-component factors (because they enforced `sp = sg = sos`), couldn't accurately predict communication costs (because the α-β model is unreliable on modern clusters with SHARP and multi-algorithm NCCL), and hadn't formalized the dependency constraints (because they never considered independent sharding).

The solver's practical tractability is itself a finding worth noting. The search space for 1024 GPUs with `R=8, N=128` is constrained by divisibility to `{1,2,4,8}` for `s0` and powers of 2 for `s1`, with the dependency ordering and cross-node rule further pruning branches. The paper doesn't report the exact number of valid tuples, but the fact that brute-force enumeration is "efficient" (Section V-B) without requiring heuristics, ILP solvers, or approximation algorithms is significant: it means the problem is naturally small enough for exact solution in practice. This contrasts with general auto-parallelism systems like Alpa (Zheng et al., 2022) or FlexFlow (Jia et al., 2018), which face exponentially large search spaces over operator placement and require sophisticated search algorithms (dynamic programming, MCMC). AMSP's restricted but high-impact search space is a case of finding the right abstraction—the optimization is over 6 integers with tight constraints, not over a general computation graph.

The evidence that the solver produces meaningfully better configurations than human-designed rules comes from the ablation in Section VI-D1 (Figures 16, 17): on 1024 GPUs, the solver's optimal configuration achieves 1.3×, 1.1×, and 1.13× higher MFU than the MiCS configuration for the 7B, 13B, and 30B models respectively, even when both run on AMSP's execution engine (controlling for the overlap implementation). This isolates the contribution of the sharding strategy from the execution engine improvements, confirming that the solver discovers configurations that the MiCS rules miss.

---

### Innovation 3: Identifying Communication-Computation Overlap Failures as a First-Class Bottleneck, Not Just an Implementation Detail

The paper's trace analysis (Section VI-C, Figures 14, 15, 18–20) reveals something that is easy to dismiss as "engineering" but is actually a **diagnostic finding with broad implications**: existing production-grade implementations of ZeRO (DeepSpeed-ZeRO3, DeepSpeed-MiCS, DeepSpeed-ZeRO++) systematically fail to overlap their communication with computation during the backward pass, leaving substantial GPU idle time even when the "overlap" configuration flag is enabled. This is not a missing feature—it is a failure of the overlap mechanism in practice, visible in the CUDA stream traces.

What makes this an insight rather than a bug report is the identification of **specific, recurring failure modes** that span multiple systems:

- **ReduceScatter blocking computation:** In all three DeepSpeed-based systems (Figure 14), ReduceScatter operations launched during the backward pass are not overlapped with GradInput computation for subsequent layers. The GPU sits idle waiting for communication to finish before proceeding to the next module's backward computation. This is visible as empty "bubbles" in the trace.

- **ReduceScatter blocking AllReduce:** In DeepSpeed-MiCS, the ReduceScatter for gradient distribution within a sharding subgroup blocks the concurrent launch of AllReduce operations for cross-subgroup gradient synchronization, serializing two operations that could run in parallel on separate CUDA streams targeting different device memory buffers.

- **No Broadcast-forward overlap:** None of the baseline systems overlap the Broadcast of updated parameters (after the optimizer step) with the forward computation of the next training step—a natural overlap opportunity since the forward pass needs parameters layer-by-layer, and Broadcasts can be issued in the same order.

These failures matter because they mean that **even if you choose the right sharding strategy, you may not realize its performance potential** due to execution inefficiencies. The paper quantifies this in the ablation (Table V): for LLaMA-7B with `M=1` (the large-scale regime where communication dominates), disabling the Broadcast overlap reduces MFU by 5%, further disabling AllReduce overlap costs an additional 16%, and the full overlap stack (including AllGather/ReduceScatter) is essential. For LLaMA-30B, the full overlap stack provides a 1.48× throughput improvement over no overlap. These are not marginal gains—they are the difference between communication-dominated and compute-bound training.

The conceptual contribution is the reframing of overlap not as a passive optimization (launch communication early, hope it finishes in time) but as an **active scheduling problem** that requires (a) decoupling communication lifecycles from autograd function boundaries (the ReduceScatter decoupling trick), (b) managing contention between communication operations (avoiding AllGather blocking ReduceScatter by issuing them at per-module granularity rather than per-layer), and (c) coordinating forward computation order with communication completion order (the Broadcast-forward synchronization optimization). These are not obvious from a high-level system design; they emerge from empirical trace analysis and require understanding both the PyTorch autograd engine's hook semantics and NCCL's stream behavior.

This insight has implications beyond AMSP. It suggests that the gap between theoretical communication lower bounds (what the α-β model says collective operations cost) and realized performance in distributed training frameworks is driven in significant part by **overlap implementation quality**, not just communication volume. Future systems work on distributed training should treat overlap scheduling as a first-class design concern, not an afterthought, and should provide trace-based diagnostics (as AMSP does in Figures 14–15) to identify overlap failures. The paper's detailed documentation of where prior systems fail provides a concrete benchmark for what "good overlap" looks like.

### Innovation 4: The Difficulty-Insensitive Optimal Configuration Pattern

A less obvious but practically significant finding emerges from Table IV: AMSP's solver selects a **single, static sharding configuration that is used uniformly across all GPU scales from 8 to 1024 GPUs** for each model size. For LLaMA-7B, the configuration `sp=1, sg=1, sos=8` is optimal at 8 GPUs and remains optimal at 1024 GPUs. For LLaMA-13B, `sp=4, sg=4, sos=8` is used at all scales. For LLaMA-30B, `sp=8, sg=8, sos=32`.

This is counterintuitive. One might expect that as the cluster scales, the optimal sharding strategy would change—perhaps sharding more aggressively at large scale to reduce per-GPU communication volume, or sharding less aggressively to reduce the number of participating ranks in each collective. The paper's scaling results (Figures 11, 12) show that AMSP's MFU degrades only modestly (from ~64% to 51% on LLaMA-7B, a 15% relative reduction) while ZeRO-3 degrades catastrophically (88% reduction). The static configuration achieves this by **keeping communication scale constant as cluster size grows**: `sos=8` means Broadcast groups are always 8 GPUs (one node), regardless of whether the cluster has 1 node or 128 nodes. The per-step communication cost does not increase with cluster size—only the per-GPU computation decreases (because the global batch is fixed at 4M tokens), which is an unavoidable consequence of strong scaling.

This finding reframes the communication scaling problem. The conventional wisdom is that ZeRO's communication overhead *inherently* grows with cluster size because AllReduce, AllGather, and ReduceScatter involve all GPUs. AMSP shows that this is only true if you choose `s = sdp` for the high-frequency components (parameters, gradients). By keeping `sp` and `sg` small (fully replicated for 7B, intra-node for 13B and 30B), AMSP eliminates the scaling-dependent communication entirely, and by keeping `sos` at a modest fixed value (8 or 32), it bounds the scaling-dependent communication to a per-step operation that is amortized over all micro-batches and layers. The "scaling problem" is not inherent to ZeRO—it is an artifact of the `sp = sg = sos = sdp` design choice.

The practical implication is that **for mid-sized models (7B–30B) trained with large global batch sizes, the optimal ZeRO configuration is scale-invariant**: you can determine it once on a small cluster and deploy it unchanged on a much larger one. This simplifies operational complexity and suggests that the solver's role is more about initial configuration discovery than continuous adaptation—a different value proposition than auto-parallelism systems that must re-optimize for each scale.

The evidence supporting this finding is implicit across Figures 11 and 12: AMSP's MFU and TGS curves show consistent relative performance across all GPU counts, with no regime changes or crossover points where a different configuration would be better. The ablation in Figures 16 and 17 further confirms that switching from the optimal configuration to the MiCS configuration degrades performance at all scales, with the gap widening at larger GPU counts (1.3× at 1024 GPUs for 7B vs. a smaller gap at 8 GPUs), supporting the claim that the optimal configuration is static and the MiCS configuration is uniformly worse.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset / Task.** The evaluation uses three LLaMA-based models—LLaMA-7B, LLaMA-13B, and LLaMA-30B—trained on a dedicated GPU cluster. This is not a benchmark dataset in the conventional sense (no fixed train/test split of examples); rather, the evaluation measures throughput and efficiency during LLM training runs. The models are the workload. The global batch size is fixed at 4 million tokens with a sequence length of 4096 tokens across all experiments, representing a realistic large-scale training configuration.

- **Base model(s).** The paper evaluates LLaMA (Touvron et al., 2023) models at three scales: 7 billion, 13 billion, and 30 billion parameters. These are chosen because they represent the prevalent "mid-sized" model regime (7B–30B) where ZeRO's communication overhead becomes the dominant bottleneck—the models are large enough to require sharding for memory but small enough that their computational load per GPU becomes tiny at large cluster scales. This is the regime where AMSP's optimizations should matter most.

- **Metrics.** The paper uses two primary metrics:
  - **Model FLOPs Utilization (MFU):** the ratio of achieved training throughput (in FLOPs per second) to the theoretical peak FLOPs of the GPU hardware. MFU captures how effectively the system converts available compute into useful training progress, with higher values indicating less time wasted on communication or idle cycles. FLOPs are calculated using the formula from Megatron-LM and PaLM (Chowdhery et al., 2023), where attention FLOPs are not halved despite the causal mask—the paper explicitly notes this follows the convention in FlashAttention and many other libraries for consistency, though technically only approximately half the attention elements require computation.
  - **Tokens per GPU per Second (TGS):** the number of training tokens processed per second per GPU. This is a direct throughput measure that accounts for both computation and communication. MFU and TGS are directly related: given the theoretical peak FLOPs per GPU, MFU determines the achieved FLOPs, and TGS reflects how many tokens can be processed at that FLOP rate given the model architecture.

- **Baselines.** Four systems are compared:
  - **DeepSpeed-ZeRO1** (Rajbhandari et al., 2020): shards only optimizer states; parameters and gradients are replicated. The lightest communication, highest memory consumption.
  - **DeepSpeed-ZeRO3** (Rajbhandari et al., 2020): shards parameters, gradients, and optimizer states across all GPUs (`sp = sg = sos = sdp`). The most memory-efficient, most communication-heavy baseline.
  - **DeepSpeed-ZeRO++** (Wang et al., 2023): extends ZeRO-3 with a secondary parameter shard within small subgroups (typically `s0_p=8, s1_p=1`) to reduce backward-pass parameter collection cost. Quantization is not enabled to ensure consistent model quality. The secondary shard number is tuned for optimal performance.
  - **DeepSpeed-MiCS** (Zhang et al., 2022): shards model states within subgroups and replicates across subgroups (`sp = sg = sos < sdp`). Configured with subgroup sizes as specified in Table IV (e.g., `s0_p=s0_g=s0_os=8, s1_p=s1_g=s1_os=1` for LLaMA-7B).

  Communication-computation overlap configurations are enabled in all baselines. Activation recomputation is applied during LLaMA-30B training for all systems but disabled for 7B and 13B.

- **Generation budget / compute accounting.** There is no "generation budget" as this is a training throughput paper, not an inference paper. The controlled resource is the **GPU cluster scale**: experiments sweep from 8 GPUs to 1024 GPUs (1 to 128 nodes, each with 8 NVIDIA A800 GPUs). The global batch size is held constant at 4M tokens across all scales, meaning the micro-batch number `M` decreases as GPU count increases (e.g., `M=128` at 8 GPUs, `M=1` at 1024 GPUs). The micro-batch size is always 1 sequence of 4096 tokens. This strong-scaling setup means that as more GPUs are added, each GPU does proportionally less computation while communication load remains linked to model size, making communication overhead increasingly dominant—exactly the regime where AMSP's optimizations are tested. Data parallelism is used exclusively across all experiments (`s0_dp = R, s1_dp = N`), without tensor or pipeline parallelism, to isolate the effect of ZeRO sharding strategy.

- **Cross-validation / statistical protocol.** No cross-validation or statistical protocol is reported; this is consistent with systems benchmarking, where measurements are deterministic (fixed hardware, fixed software, fixed model) and the relevant variation comes from sweeping hardware scale and model size rather than sampling variability.

- **Hardware.** All experiments run on a dedicated cluster of 128 GPU servers, each with 8 NVIDIA Ampere GPUs (A800, 80GB memory) and 128 CPU cores, totaling 1024 GPUs. Intra-node communication uses NVLink; inter-node communication uses 4 Mellanox HDR InfiniBand adapters per node (800 Gbps total bidirectional bandwidth) without SHARP (in-network aggregation is disabled, which is worth noting because the communication cost model in Section IV-A explicitly accounts for SHARP, but the testbed doesn't use it—this means the profiled bandwidths reflect a non-SHARP environment, and results might differ on SHARP-enabled clusters).

- **Software.** AMSP implements its execution engine using PyTorch 2.1 hooks (Table III). The paper states that AMSP incorporates FlashAttention-v2 (Dao, 2023) and uses mixed-precision training with BF16 to ensure comparable computational performance with baseline systems, which also use these optimizations.

### Main Quantitative Results

#### Scalability Performance Across GPU Counts

The headline result (Figures 11, 12): AMSP achieves significantly higher MFU and TGS than all baselines across all model sizes and GPU counts, with the advantage widening dramatically at large scale.

**LLaMA-7B results (Figures 11a, 12a):**

At 8 GPUs, AMSP and ZeRO-1 both achieve approximately 63–64% MFU—they are essentially tied because they use the same sharding configuration (`sp=1, sg=1, sos=8` for AMSP, `sp=1, sg=1, sos=64` for ZeRO-1 on 64 GPUs in a node configuration, but on a single node the difference is minimal). This validates that AMSP does not introduce computational overhead that degrades performance when communication is not the bottleneck.

At 1024 GPUs, the differences are stark:

- **AMSP: 51% MFU** (a modest 15% relative reduction from 8 GPUs)
- **ZeRO-1: 36% MFU** (43% relative reduction)
- **MiCS: 35% MFU** (30% relative reduction from its peak, and notably *worse than ZeRO-1*)
- **ZeRO-3: 4% MFU** (92% relative reduction—essentially communication-bound)
- **ZeRO++: 4% MFU** (similar catastrophic degradation)

In absolute TGS at 1024 GPUs: AMSP achieves approximately 4,300–4,500 TGS for LLaMA-7B (Figure 12a), roughly 1.4× the throughput of ZeRO-1 (~3,200 TGS) and MiCS (~3,100 TGS), and over 10× the throughput of ZeRO-3 and ZeRO++ (~300 TGS). The paper claims a 1.56× improvement over MiCS and ZeRO++ in the abstract; this figure appears to represent the maximum speedup across all model sizes.

**Why ZeRO-1 outperforms MiCS on LLaMA-7B at scale.** This is a non-obvious and important finding. MiCS uses `sp=sg=sos=8` (intra-node sharding), which should reduce communication scale for AllGather and ReduceScatter compared to ZeRO-1's full-cluster AllReduce. Yet MiCS achieves 35% MFU vs. ZeRO-1's 36% at 1024 GPUs. The paper attributes this to MiCS generating *more* total communication traffic than ZeRO-1 for this model size: MiCS requires per-module AllGather and ReduceScatter (3 collective operations per module per micro-batch, as analyzed in `T_p`), while ZeRO-1 only requires per-step AllReduce for gradients and per-step AllGather for updated parameters. The reduced communication scale (8 GPUs vs. 1024) does not compensate for the increased frequency (per-module-per-micro-batch vs. once-per-step). AMSP's configuration avoids this by keeping parameters and gradients fully replicated (`sp=sg=1`, so `T_p=T_g=0`), incurring zero per-module communication, while still sharding optimizer states within a node (`sos=8`) to stay within memory limits.

**LLaMA-13B results (Figures 11b, 12b):**

At 1024 GPUs:

- **AMSP: 52% MFU** (the highest MFU across all model sizes—LLaMA-13B hits the sweet spot where AMSP's configuration fits well in memory while communication is effectively hidden)
- **MiCS: 33% MFU**
- **ZeRO-1:** Not reported directly for 13B at 1024 GPUs (Table IV shows ZeRO-1 is configured with `s0_os=R=8, s1_os=N=128`, memaning optimizer states sharded across all 1024 GPUs, but Figure 11b shows ZeRO-1 falls between MiCS and ZeRO-3—significantly below AMSP)
- **ZeRO-3: ~4% MFU**
- **ZeRO++: 6% MFU** (slightly better than ZeRO-3 but still catastrophically low)

The MFU degradation from 8 to 1024 GPUs is approximately 18% for AMSP (from ~63% to 52%), compared to much larger drops for baselines. TGS at 1024 GPUs follows the same ordering, with AMSP achieving roughly 2,000–2,100 TGS (Figure 12b).

**LLaMA-30B results (Figures 11c, 12c):**

At 1024 GPUs:

- **AMSP: 42% MFU**
- **MiCS: 29% MFU**
- **ZeRO-3: ~3–4% MFU**
- **ZeRO++: 5% MFU**

ZeRO-1 is not evaluated for LLaMA-30B (it would run out of memory without parameter sharding). ZeRO++ encounters an **out-of-memory (OOM) error** when training LLaMA-30B on 32 GPUs (Figure 11c, marked "oom"), while other methods achieve around 40% MFU at that scale. This is a notable failure: ZeRO++'s secondary parameter shard and quantization buffers add memory overhead that, for this model size and GPU count, exceeds the 80GB A800 capacity. AMSP's configuration (`sp=8, sg=8, sos=32`) avoids this by sharding parameters and gradients within a node (reducing memory enough to fit) while keeping optimizer state sharding at a moderate scale (32 GPUs across 4 nodes).

**Scaling trajectory analysis.** The MFU curves in Figure 11 reveal qualitatively different scaling behaviors:

- **AMSP and MiCS** show relatively flat curves—they degrade gracefully as GPU count increases because their communication scale is bounded (AMSP's `sos` stays at 8 or 32; MiCS's `sp=sg=sos` stays at 8 or 16). The degradation comes primarily from the reduction in per-GPU computation as `M` decreases with more GPUs, which is unavoidable.
- **ZeRO-3 and ZeRO++** show steep, near-linear degradation—their MFU drops by 80–90% from 8 to 1024 GPUs because their communication involves all GPUs and the compute-to-communication ratio collapses. At very large scales, they spend almost all their time in collectives.
- **ZeRO-1** falls between these regimes: it degrades more than AMSP/MiCS (because its AllReduce and Broadcast involve all GPUs) but less than ZeRO-3 (because it only communicates once per step, not per-layer per-micro-batch).

#### GPU Memory Analysis

Figure 13 reports peak allocated memory during training for all systems across GPU scales and model sizes.

**ZeRO-3 is consistently the most memory-efficient**, as expected: by sharding all three components across all GPUs, each GPU holds only a tiny fraction of model states. For LLaMA-30B on 1024 GPUs, ZeRO-3 uses approximately 15 GB. The memory consumption becomes nearly constant at large scales—moving from 512 to 1024 GPUs changes memory for LLaMA-30B from 16 GB to 15 GB—because the per-GPU shard size asymptotically approaches zero and other memory consumers (activations, buffers) dominate.

**MiCS uses approximately 2× the memory of ZeRO-3** across all configurations, because it replicates model states across subgroups. For LLaMA-30B on 1024 GPUs, MiCS consumes roughly 30 GB—well within the 80 GB limit, but noticeably higher than ZeRO-3. This is the explicit tradeoff: MiCS trades memory for reduced communication scale.

**AMSP consistently shows the highest memory consumption** among the evaluated systems, particularly for LLaMA-7B. On 1024 GPUs, AMSP's LLaMA-7B memory footprint is approximately **2× that of MiCS** (AMSP ~55–60 GB vs. MiCS ~28–30 GB, estimated from Figure 13a). This is because AMSP's optimal configuration for 7B keeps parameters and gradients fully replicated (`sp=sg=1`), consuming 14 GB each for parameters and gradients (2Φ = 14 GB for 7B parameters), while MiCS shards them within a node (`sp=sg=8`), using only 1.75 GB each. The additional ~25 GB for model states is the price AMSP pays for eliminating all per-module AllGather/ReduceScatter communication—and it is affordable because the 80 GB GPU still has sufficient headroom for 7B models.

For LLaMA-13B and LLaMA-30B, the memory gap between AMSP and MiCS narrows. The paper notes (Section VI-B2): "Although AMSP and MiCS demonstrate similar memory consumption for the 13B and 30B models, their memory utilization compositions vary." This is because AMSP's optimal configurations for these models use partial sharding for parameters and gradients (e.g., `sp=sg=4` for 13B, `sp=sg=8` for 30B), bringing their memory footprint closer to MiCS's uniform sharding, while AMSP's optimizer state sharding factor may differ from MiCS's, changing the distribution of memory across components.

**ZeRO++'s OOM on LLaMA-30B at 32 GPUs** (Figure 13c) is a critical negative result. At 32 GPUs, ZeRO++ exceeds the 80 GB limit while all other systems operate at 40–50 GB. This indicates that the secondary parameter shard mechanism, combined with quantization buffers (even though quantization itself is disabled, the buffer infrastructure remains), imposes a non-trivial and potentially unpredictable memory tax.

#### Trace Analysis: Why AMSP Outperforms Even With the Same Sharding Configuration

Section VI-C and Figures 14–15 provide trace-level evidence that AMSP's execution engine is substantially more efficient than DeepSpeed's, even controlling for sharding strategy.

**Figure 14: DeepSpeed trace for LLaMA-7B on 32 GPUs (backward phase of last micro-batch).** The trace reveals computation resource "bubbles"—gaps where the GPU is idle, waiting for communication—in all three DeepSpeed-based systems:

- **DeepSpeed-ZeRO3:** ReduceScatter operations are launched but do not overlap effectively with backward computation. The trace shows serialized execution: computation block → ReduceScatter → computation block → ReduceScatter, rather than concurrent execution.
- **DeepSpeed-ZeRO++:** Similar pattern to ZeRO-3. The secondary parameter shard helps backward-pass parameter collection but does not address ReduceScatter overlap.
- **DeepSpeed-MiCS:** Two distinct problems are visible: (1) ReduceScatter does not overlap with computation, creating bubbles identical to ZeRO-3's, and (2) ReduceScatter operations **block the concurrent execution of AllReduce**, serializing what should be parallel communication. This is the more serious issue—MiCS requires both intra-subgroup gradient distribution (ReduceScatter within `sp` GPUs) and cross-subgroup gradient synchronization (AllReduce across `sdp/sp` subgroups), and serializing them doubles the exposed communication time.

**Figure 15: AMSP trace for LLaMA-7B, 13B, 30B (full training step).** The trace shows substantially better overlap:

- **Forward pass (Figures 15b, 15c):** AllGather operations for the next layer's parameters run concurrently with the current layer's computation. The GPU streams show interleaved compute and communication kernels with minimal idle time.
- **Backward pass:** AllReduce and ReduceScatter operations are interleaved with computation blocks. Unlike MiCS, AMSP's ReduceScatter and AllReduce execute concurrently on separate communication streams, eliminating the serialization bottleneck.
- **Between-step Broadcast:** The broadcast of updated parameters after the optimizer step overlaps with the forward computation of the next training step (visible in Figure 15a).

The paper notes that DeepSpeed's overlap failures persist even when the communication-computation overlap configuration flag is enabled, indicating these are not user configuration errors but systematic limitations of the implementation. The complete traces are provided in Appendix A (Figures 18–20), showing the full forward and backward phases for all baselines.

### Ablation Studies and Robustness Checks

#### Analysis of Sharding Strategy (Section VI-D1, Figures 16, 17)

**AMSP's Planner-based optimal configuration vs. MiCS's rule-based configuration, both running on AMSP's execution engine:** The optimal configuration yields substantially higher MFU and TGS than the MiCS configuration across all scales, with the gap widening at larger GPU counts.

At 1024 GPUs:

- **LLaMA-7B:** Optimal config MFU is **1.3×** the MiCS config MFU (Figure 16a). This is the largest gap—for 7B, the optimal config (`sp=1, sg=1, sos=8`) and MiCS config (`sp=sg=sos=8`) differ qualitatively: the optimal config eliminates all per-module communication, while MiCS retains it within each node.
- **LLaMA-13B:** Optimal config MFU is **1.1×** the MiCS config MFU (Figure 16b). The gap is smaller because both configurations use partial sharding for parameters and gradients (AMSP optimal: `sp=4`, MiCS: `sp=8`), so the communication difference is less dramatic.
- **LLaMA-30B:** Optimal config MFU is **1.13×** the MiCS config MFU (Figure 16c). A similar pattern to 13B, with the gap attributable to finer-grained differences in optimizer state sharding (AMSP uses `sos=32`, MiCS uses `sos=16`).

Importantly, **implementing MiCS under AMSP's execution engine yields higher performance than DeepSpeed's native MiCS implementation** (compare "Ours (MiCS Config)" bars in Figures 16, 17 to the "MiCS" bars in Figures 11, 12). For LLaMA-7B at 1024 GPUs, AMSP's execution of the MiCS configuration achieves approximately 40–42% MFU (estimated from Figure 16a) vs. 35% on DeepSpeed-MiCS (Figure 11a). This ~5–7 percentage point gap isolates the contribution of AMSP's overlap optimizations from the sharding strategy: even with identical sharding factors, AMSP's execution engine extracts more performance through better communication-computation overlap. The paper states this improvement "can be attributed to our optimizations for communication-computation overlap."

#### Analysis of Overlap Strategies (Section VI-D2, Table V)

**Incremental disabling of overlap optimizations:** The paper systematically deactivates overlap strategies and measures the performance impact at 64 GPUs with varying micro-batch numbers (`M=1, 2, 4, 8`). Table V reports TGS and MFU for each configuration.

The overlap strategies are disabled in sequence, each adding communication that was previously hidden:

1. **Full overlap (AllGather/ReduceScatter + AllReduce + Broadcast):** The baseline with all overlap enabled.
2. **Disable Broadcast overlap:** Removes the overlap between updated parameter broadcast and the next step's forward computation.
3. **Disable AllReduce overlap (on top of disabled Broadcast):** Additionally removes the overlap between gradient synchronization AllReduce and backward computation.
4. **Disable AllGather/ReduceScatter overlap (on top of disabled Broadcast and AllReduce):** Removes the overlap between parameter prefetching/redistribution and layer computation. This state is "No Overlap."
5. **"No Overlap":** Identical to step 4 in the tested configurations because AllGather/ReduceScatter overlap is the only remaining overlap after Broadcast and AllReduce are disabled.

Key findings from Table V:

**The impact of overlap is largest when `M=1` (the large-scale regime).** For LLaMA-7B with `M=1`:
- Full overlap: 3,525 TGS / 0.57 MFU
- Disable Broadcast: 3,346 TGS / 0.54 MFU (**−5% MFU**)
- Disable Broadcast + AllReduce: 2,812 TGS / 0.45 MFU (**additional −16% MFU** from the previous step)
- No Overlap: 2,812 TGS / 0.45 MFU (same as previous step—for this configuration with `sp=1, sg=1`, there are no AllGather/ReduceScatter operations to overlap, so disabling them has no effect)

The Broadcast overlap contributes 5% MFU improvement, and the AllReduce overlap contributes 16%—these are the two relevant overlap mechanisms for LLaMA-7B's optimal configuration (`sp=1, sg=1, sos=8`). The sum effect of overlapping both is approximately 21% MFU improvement (from 0.45 to 0.57) over no overlap, or a **1.25× throughput improvement**.

**For LLaMA-13B with `M=1`:** Going from No Overlap to Full Overlap improves TGS from 1,527 to 1,918, a **1.25× improvement**. For this model, `sp=4`, so AllGather/ReduceScatter overlap is relevant: even at `M=1`, the full overlap stack provides benefits beyond just Broadcast and AllReduce.

**For LLaMA-30B with `M=1`:** Going from No Overlap to Full Overlap improves TGS from 557 to 825, a **1.48× improvement**—the largest relative gain. This model has the most communication (due to its size and `sp=8` configuration) and benefits the most from overlap. All three overlap categories (Broadcast, AllReduce, AllGather/ReduceScatter) contribute meaningfully.

**As `M` increases (more micro-batches, more computation relative to communication), the relative benefit of overlap decreases.** For LLaMA-7B at `M=8`, full overlap achieves 4,503 TGS vs. 4,286 TGS without overlap—only a 5% improvement. This is intuitive: with more micro-batches, the backward pass has more computation to overlap with, and the per-step communication (Broadcast) is amortized over more micro-batches, so the marginal benefit of explicit overlap shrinks.

**The "No Overlap" state is identical to "Overlap AllGather/ReduceScatter" state for LLaMA-7B** (both show 2,812 TGS for `M=1`). This is a sanity check: for `sp=1`, there are no AllGather or ReduceScatter operations, so disabling their overlap has no effect. The table correctly reflects this.

#### Robustness to Model Size

The consistent pattern across 7B, 13B, and 30B models (Figures 11, 12) demonstrates that AMSP's approach generalizes across model scales. The optimal configurations differ per model (Table IV), but the methodology—independent per-component sharding, solver-based optimization, fine-grained overlap—produces substantial improvements for all three. The MFU at 1024 GPUs ranges from 42% (30B) to 52% (13B), compared to 4–6% for ZeRO-3/ZeRO++ and 29–36% for MiCS/ZeRO-1.

A potential concern is that larger models (65B, 70B, 175B) are not tested. The methodology should generalize—the solver would simply be constrained by memory more tightly, potentially forcing more aggressive sharding—but the paper does not demonstrate this. The memory analysis (Figure 13) suggests that AMSP's configurations for 30B already approach the memory limits at small GPU counts (requiring 64 GPUs minimum for LLaMA-30B training), hinting that for 65B+ models, AMSP might be forced toward configurations closer to ZeRO-3 (full sharding for all components), narrowing the advantage over baselines.

#### Analysis of Communication Placement (No Quantitative Ablation)

The paper describes topology-aware communication placement (Section V-D, Figure 10) as a mechanism to minimize cross-spine traffic, but **no ablation isolates its contribution**. There is no Table or Figure comparing training performance with and without this optimization. This is a notable omission—the mechanism is described in detail, but its practical impact is not quantified. Given that the testbed uses InfiniBand without SHARP (Section VI-A2), the cross-spine penalty might be less severe than in Ethernet-based clusters (where congestion is more common), potentially making this optimization less impactful in the paper's specific environment than it would be elsewhere. The lack of an ablation leaves the reader uncertain about whether this is a meaningful optimization or a minor enhancement.

### Critical Assessment

#### Do the Experiments Support the Claim That AMSP Improves Training Throughput by 1.56× Over MiCS and ZeRO++?

**Yes, with precise conditions specified.** The abstract claims a 1.56× improvement, and Figures 11–12 support this as a representative figure—though the actual speedup varies by model size and GPU count. The paper is transparent about the variation: the abstract says "a 1.56 times improvement in training throughput compared to newly proposed systems like MiCS and ZeRO++," and the conclusion states "improves the training throughput by 1.4−12.7×" over these systems. The 1.56× appears to correspond to the LLaMA-7B comparison at 1024 GPUs, where AMSP achieves 51% MFU vs. 35% for MiCS and 4% for ZeRO++ (51/35 ≈ 1.46, and 51/4 ≈ 12.75—the 1.4 and 12.7 bounds are well-supported). The 1.56× figure may represent the maximum speedup against MiCS specifically, though the paper does not explicitly map the number to a specific experiment. Readers should understand this as a **representative improvement number, not a universal constant**—the actual gain depends on model size, GPU scale, and which baseline is considered.

#### Do the Experiments Support the Claim That Per-Component Independent Sharding Is the Key Mechanism?

**Yes, the ablation in Figures 16–17 cleanly isolates this.** By running both AMSP's optimal configuration and the MiCS configuration on the same execution engine, the experiment controls for overlap implementation and isolates the sharding strategy. The 1.1–1.3× improvement from the optimal config over the MiCS config at 1024 GPUs directly quantifies the benefit of per-component independent sharding. This is a well-designed ablation.

However, the ablation only compares against the MiCS configuration. It does not compare against other plausible manual configurations (e.g., ZeRO-1 style, ZeRO-2 style, or variants with different subgroup sizes). The claim that AMSP's solver finds the *optimal* configuration is supported by the exhaustive enumeration argument (the search space is small enough for brute force) but not by empirical comparison against a range of alternatives. This is a reasonable approach—given the solver's formulation, it should find the optimum within its modeled space—but it means the paper demonstrates that the solver finds a *good* configuration, not necessarily that it is provably optimal in practice (the communication cost model uses interpolation for unprofiled message sizes, introducing approximation error).

#### Do the Experiments Support the Claim That Overlap Quality Is as Important as Sharding Strategy?

**Yes, and this is one of the paper's strongest empirical contributions.** Two pieces of evidence converge:

1. **The gap between "Ours (MiCS Config)" and "DeepSpeed (MiCS Config)" in Figures 16–17:** Running the identical sharding configuration on AMSP's engine vs. DeepSpeed's engine produces ~5–7 percentage points higher MFU at 1024 GPUs (for LLaMA-7B). This is purely attributable to better overlap.

2. **The ablation in Table V:** Disabling overlap optimizations reduces MFU by up to 21% for LLaMA-7B (`M=1`) and up to 32% for LLaMA-30B (from 0.48 to 0.33 MFU). These are large effects that rival or exceed the contribution of the sharding strategy itself.

3. **The trace evidence (Figures 14–15):** The visualization of computation bubbles in DeepSpeed's traces provides qualitative evidence that overlap failures are real and substantial, not theoretical concerns.

The combined evidence makes a compelling case that implementation quality—specifically, the ability to effectively overlap communication with computation—is a first-class performance factor, not a secondary optimization. This is a genuinely useful finding for the systems community.

#### Weaknesses and Missing Experiments

**No ablation of topology-aware communication placement.** As noted above, the Section V-D mechanism is described but never isolated in an experiment. Given that the testbed does not use SHARP (which would make in-network aggregation paths less predictable) and uses InfiniBand (often more deterministic than Ethernet), it is unclear how much this optimization contributes. A simple ablation comparing training throughput with random node assignment vs. leaf-switch-aware assignment, at a scale where cross-switch communication is unavoidable (e.g., 32+ nodes), would have clarified the benefit.

**Single hardware configuration, single network topology.** All experiments use 8×A800 nodes with NVLink intra-node and 4×HDR InfiniBand inter-node. The results may not transfer to clusters with different bandwidth ratios (e.g., PCIe-only intra-node communication, or 8× InfiniBand adapters), different GPU memory capacities (40 GB A100, 80 GB H100), or Ethernet-based interconnects. The profiling-based communication model should adapt to new hardware—that is its design intent—but the paper does not demonstrate this portability.

**No pipeline or tensor parallelism experiments.** The paper explicitly disables tensor and pipeline parallelism (`stp = spp = 1`) to isolate ZeRO sharding effects (Section VI-A). This is methodologically clean but limits the claims' applicability to production training, where 3D parallelism is standard for models above ~30B parameters. The interaction between AMSP's sharding and other parallelism dimensions—particularly tensor parallelism, which also involves AllReduce operations on partial parameters—is unexplored. The paper's scope is specifically "reducing communication overhead of ZeRO" (title), not "optimizing all dimensions of distributed training," so this is a scope limitation rather than a weakness per se, but it should be noted.

**No convergence or model quality evaluation.** The paper measures throughput (MFU, TGS) but does not evaluate whether the training produces models of equivalent quality. The binary is whether different sharding/overlap strategies affect floating-point determinism or gradient noise. This is standard for systems papers—throughput is the metric of interest—but readers deploying AMSP in production might want confirmation that the optimizations are loss-neutral. The paper's ZeRO++ comparison disables quantization "to ensure consistent model quality," which is appropriate, but does not address whether AMSP itself introduces any numerical differences.

**Difficulty estimation cost is not a concern here** (unlike the inference-time scaling paper in the example), but an analogous concern exists: the offline profiling step requires running NCCL benchmarks on the target cluster. The paper does not report how long this profiling takes or how often it needs to be repeated. For a production cluster with stable hardware, this is a one-time cost amortized over all jobs, making it negligible. But for dynamic or heterogeneous clusters, the profiling overhead could be non-trivial.

**The "optimal configuration is static across scales" finding (Innovation 4 in Section 4) is an empirical observation, not a proven property.** The paper shows that for the three LLaMA models on this specific hardware, the solver picks the same configuration at all GPU counts. This is an interesting finding, but the paper does not analyze *why* this holds—is it a general property of the optimization problem, or an artifact of these specific model sizes and memory capacities? A model just slightly larger than 30B might force a different configuration at small GPU counts (due to memory pressure) while allowing the same configuration as 30B at large GPU counts, breaking the scale-invariance. Readers should treat the static-configuration finding as a useful empirical observation, not a theoretical guarantee.

**No comparison against fully automated parallelism frameworks.** The related work section (VII) mentions Alpa, OptCNN, FlexFlow, and TensorOpt but does not benchmark against them. These systems automate the placement of operators across data and tensor parallelism dimensions, which is a different problem than ZeRO model state sharding, but the boundaries blur: Alpa, for instance, could theoretically configure different sharding for different tensors. The paper's argument is that these systems focus on operator parallelism, not model state sharding—a reasonable distinction—but a head-to-head comparison against at least one auto-parallelism system would strengthen the claim that AMSP explores an underexplored design space.

**The testbed is a dedicated cluster with exclusive access.** The paper does not discuss performance under multi-tenancy, network contention from other jobs, or variability in InfiniBand performance. Production training often shares network fabric with other workloads; AMSP's sensitivity to such variability is not evaluated. The topology-aware placement mechanism (Section V-D) would likely *help* under contention by localizing traffic, but this is speculative without experiments.

## 6. Limitations and Trade-offs

### The Difficulty Estimation Cost Is Unaccounted for and Makes the Headline Gains Partially Aspirational

**The assumption or constraint.** AMSP's Planner requires the Communication-Profiler to have pre-measured effective bandwidth `w(o, v, p0 × p1)` for all collective operations, message sizes, and device meshes on the target cluster (Section IV-A). The paper presents this as an offline, one-time cost: "profiling on the target GPU cluster in advance." However, the paper does not report how long this profiling takes, how many `(operation, message_size, device_mesh)` combinations must be measured, or how frequently profiling must be repeated when the cluster configuration changes (new NICs, firmware updates, NCCL version upgrades, or node additions/removals).

**The consequence.** In a production environment, the profiling cost could be non-trivial. Figure 3 shows performance evaluations for 4 collective operations × multiple message sizes (spanning 1M to 1G bytes) × multiple device meshes (8×1 through 8×64). Each data point requires running NCCL performance tests at sufficient iteration count for stable measurements. For a 1024-GPU cluster, fully profiling the search space might require hours of dedicated cluster time—time during which the cluster is not training models. Moreover, the profiling is not a true one-time cost: NCCL algorithm selection depends on the NCCL version, GPU driver version, and network firmware, all of which evolve over a cluster's lifetime. In multi-tenant clusters where network fabric is shared, effective bandwidth varies with background load, making a static profile potentially inaccurate during periods of contention.

Additionally, the interpolation method for unprofiled message sizes (Section IV-A: "In cases where v is not profiled, we employ the interpolation method") introduces approximation error into the communication cost model `T_comm`. The solver minimizes this approximated cost, not the true cost on the actual cluster under production load. If the interpolation error is large for certain message size ranges (and Figure 3 shows non-trivial non-linearity, particularly at small message sizes where bandwidth drops sharply), the solver may select suboptimal sharding factors.

**What evidence exists in the paper.** The paper does not report profiling overhead, interpolation accuracy, or sensitivity of solver decisions to bandwidth estimation errors. There is no ablation comparing solver-chosen configurations against configurations chosen using the true bandwidth (measured at the exact message sizes used by the model). The paper also does not evaluate AMSP under multi-tenant network conditions or with varying background load—the experiments use a "dedicated cluster" (Section VI-A2) with exclusive access. Section VI-A2 explicitly notes the InfiniBand fabric operates "without SHARP," meaning the cluster lacks in-network aggregation, which is noted as a feature the communication model accounts for (Section IV-A) but cannot validate.

**Mitigation status.** The paper does not address this limitation. It presents profiling as a solved prerequisite, not as a deployment challenge. Section VIII (Conclusion) does not mention profiling cost or model accuracy as areas for future work. A practitioner deploying AMSP would need to independently assess whether the profiling investment is justified by the throughput gains, and whether their cluster's stability and workload isolation make static profiling reliable enough for solver decisions to remain optimal over time.

---

### Single Hardware Architecture, Single GPU Generation—No Evidence of Portability

**The assumption or constraint.** All experiments are conducted on a single, homogeneous cluster: 128 nodes, each with 8 NVIDIA A800 GPUs (80 GB), NVLink intra-node, and 4× Mellanox HDR InfiniBand (800 Gbps total per node) inter-node (Section VI-A2). The A800 is an Ampere-generation GPU with specific NVLink bandwidth, SM count, and memory capacity. The intra-node-to-inter-node bandwidth ratio in this testbed is approximately 2:1 (600 GB/s bidirectional per GPU NVLink vs. 400 GB/s bidirectional per node InfiniBand, or roughly 75 GB/s per GPU intra-node vs. 12.5 GB/s per GPU inter-node when amortized across 8 GPUs per node—a ~6:1 ratio in practice).

**The consequence.** AMSP's optimal sharding configurations are a function of this bandwidth ratio and memory capacity. On hardware with different characteristics, the solver would produce different configurations—but the paper provides no evidence that the *methodology* (profiling-based communication model + independent per-component sharding + overlap) produces meaningful gains across hardware architectures. Specific concerns:

- **Lower intra-node bandwidth (e.g., PCIe-based GPU interconnect instead of NVLink):** The paper's optimal configurations keep most communication within a node (e.g., `sos=8` for LLaMA-7B). If intra-node bandwidth were substantially lower, the solver might prefer different sharding factors, and the overlap strategies (which rely on launching communication early enough to hide latency) might be less effective because communication takes longer and is less likely to complete within a single layer's computation time.

- **Different GPU memory capacity (e.g., 40 GB A100, 80 GB H100):** The memory constraint (Equation 2) is the binding constraint that forces sharding. With 40 GB GPUs, AMSP's optimal configuration for LLaMA-7B (`sp=1, sg=1, sos=8`, consuming ~38.5 GB for model states plus activations and buffers) might not fit, forcing more aggressive sharding and reducing the advantage over baselines. With larger memory (H100 80 GB, or forthcoming GPUs with 141 GB), the solver might select even less aggressive sharding, potentially increasing the advantage.

- **Higher inter-node bandwidth (e.g., 8× InfiniBand NDR at 400 GB/s per adapter, or NVIDIA Spectrum Ethernet at 400 Gb/s per GPU):** If inter-node bandwidth were higher, the penalty for cross-node sharding (`s1 > 1`) would be lower, potentially making configurations that shard across nodes more attractive. The paper's constraint 7 (cross-node minimization: "a priority is placed on employing fewer nodes when sharding") might become suboptimal on networks where inter-node bandwidth approaches intra-node bandwidth.

- **SHARP-enabled clusters:** The paper explicitly evaluates on a cluster "without SHARP" (Section VI-A2) but notes that SHARP changes communication semantics (Section IV-A). On SHARP-enabled clusters, AllReduce operations are offloaded to switches, potentially reducing their exposed latency and changing the relative cost of different communication primitives. The profiling-based model would capture this, but whether the conclusions about optimal configurations translate is untested.

**What evidence exists in the paper.** None. The paper acknowledges the profiling-based approach is designed to be portable ("performance profiling on the target GPU cluster in advance"), but provides zero cross-cluster validation. There is no experiment on a different GPU generation, a different interconnect topology, or a different memory configuration. The paper's claim that AMSP "has been used for training InternLM on thousands of GPUs" (Section I footnote) hints at production deployment but provides no details about hardware differences or performance on that deployment.

**Mitigation status.** The profiling-based approach is, in principle, the portability mechanism—re-profile on the new cluster, re-run the solver, and deploy. But principle is not evidence. The paper does not demonstrate a single successful port, and does not discuss whether the profiling methodology itself has hardware-specific assumptions (e.g., that NCCL's algorithm selection behaves similarly across GPU generations). A practitioner considering AMSP for a non-A800, non-InfiniBand cluster would be taking an unquantified risk.

### The System Never Combines AMSP Sharding with Tensor or Pipeline Parallelism

**The assumption or constraint.** The paper explicitly constrains all experiments to pure data parallelism with ZeRO: "we adopt `s0_dp = R, s1_dp = N` across all experiments, excluding tensor or pipeline parallelism" (Section VI-A3). This is methodologically deliberate—the paper aims to isolate ZeRO communication overhead—but it means all results are measured in a regime that production training of models above ~30B parameters rarely uses. The standard approach for models like LLaMA-65B or LLaMA-70B is 3D parallelism: tensor parallelism within a node (to reduce memory and communication), pipeline parallelism across nodes (to reduce communication scale), and data parallelism with ZeRO across the remaining dimension.

**The consequence.** AMSP's contribution is specifically about reducing ZeRO communication, but in a 3D parallelism setting, the ZeRO communication is only one component of the total communication budget. Tensor parallelism introduces its own AllReduce operations on partial activations and gradients. Pipeline parallelism introduces point-to-point sends/receives of activations and gradients between pipeline stages. The relative importance of ZeRO optimization diminishes when these other communication sources are present, and the interactions between parallelism dimensions create new constraints that AMSP's solver does not model:

- **Memory interaction with tensor parallelism:** Tensor parallelism shards parameters within a layer across `stp` GPUs, reducing each GPU's parameter memory by a factor of `stp`. This changes the memory budget available for the ZeRO sharding decision. AMSP's solver assumes parameters occupy `2Φ/sp` bytes (Section IV-D), but with tensor parallelism, the per-GPU parameter footprint is `2Φ/(stp × sp)`. The solver might select different `sp` values if tensor parallelism is enabled.

- **Communication interaction with tensor parallelism:** Tensor parallelism's AllReduce operations compete for the same NVLink and InfiniBand bandwidth as ZeRO's AllGather, ReduceScatter, and Broadcast operations. AMSP's communication cost model (`T_comm`) assumes these ZeRO collectives are the only communication; with tensor parallelism, the total communication load is higher, and NCCL stream contention might reduce the effectiveness of AMSP's overlap strategies.

- **Pipeline parallelism changes the micro-batch structure:** Pipeline parallelism divides micro-batches across pipeline stages, changing the relationship between `M` (micro-batches per step) and communication overlap opportunities. AMSP's overlap strategies are designed around a specific micro-batch schedule; with pipeline parallelism, the timing of forward and backward passes changes, potentially breaking the AllGather/ReduceScatter overlap assumptions.

**What evidence exists in the paper.** None. The paper acknowledges the existence of 3D parallelism in Section II-B and states that "ZeRO could work in cooperation with 3D parallelism," but provides no experiments, no modeling, and no discussion of how AMSP's solver would interact with tensor or pipeline parallelism dimensions. Section VII notes that other systems (Alpa, FlexFlow) "focus on optimizing the sharding and placement strategies for the optimal operators within the computational graph" but "overlook strategies related to the orthogonal placement of the model states"—implying that AMSP's model state optimization is complementary and could be combined with these systems, but this combination is never demonstrated or even sketched.

**Mitigation status.** The paper does not address this limitation. The scope is explicitly "reducing communication overhead of ZeRO" (title), not optimizing all parallelism dimensions, and Section VIII does not propose 3D parallelism integration as future work. For a practitioner training a model that requires tensor or pipeline parallelism to fit in memory (e.g., LLaMA-70B on A100-40GB), the paper provides no guidance on how AMSP's solver should be used alongside those dimensions, or whether the throughput gains demonstrated in the pure data-parallel setting would persist.

### Memory Overhead Relative to ZeRO-3 Limits Applicability to Larger Models and Smaller GPU Counts

**The assumption or constraint.** AMSP achieves its communication reduction by trading off memory: it keeps model state components less aggressively sharded than ZeRO-3, consuming more GPU memory per component. The paper is transparent about this, showing in Figure 13 that AMSP's peak memory consumption is substantially higher than ZeRO-3 and often higher than MiCS. For LLaMA-7B on 1024 GPUs, AMSP uses approximately 55–60 GB vs. ZeRO-3's ~15–18 GB (estimated from Figure 13a). For LLaMA-30B on smaller GPU counts, AMSP requires a minimum of 64 GPUs (Figure 11c shows no data point below 32 GPUs, and 32 GPUs appears to be marginal based on the memory trend in Figure 13c), while ZeRO-3 can train the same model on far fewer GPUs.

**The consequence.** AMSP's approach is fundamentally limited to a regime where GPU memory is abundant relative to model size. This regime exists—the paper's target of mid-sized models (7B–30B) trained on large GPU clusters with 80 GB GPUs—but it excludes several practically important scenarios:

- **Larger models (65B, 70B, 175B):** For these models, even 80 GB GPUs are memory-constrained. ZeRO-3 is essentially mandatory because full replication of any model state component would exceed memory. AMSP's solver might be forced to choose configurations very close to ZeRO-3 (all components fully sharded), at which point the advantage over ZeRO-3 would come primarily from better overlap (Table V) rather than from sharding strategy. The paper's largest model is 30B; the extrapolation to 70B+ is untested.

- **Smaller GPU counts:** For a team training LLaMA-30B on 16 or 32 GPUs (perhaps their entire cluster), AMSP's memory overhead might make training infeasible, while ZeRO-3 can train (slowly, but it completes). Figure 13c shows ZeRO-3's memory for LLaMA-30B drops from ~45 GB at 8 GPUs to ~16 GB at 128 GPUs, while AMSP requires at least 32–64 GPUs for the model to fit. This means AMSP is not a drop-in replacement for ZeRO-3—it is suitable for training *at scale* (many GPUs), not for enabling training on resource-constrained clusters.

- **GPU generation transitions:** As GPU memory capacity increases (80 GB A100 → 141 GB H200), AMSP's memory overhead becomes more affordable, potentially expanding its applicable regime. Conversely, on earlier GPUs with less memory (40 GB A100, 32 GB V100), AMSP's configurations might not fit even for models the paper tested. The paper does not discuss this sensitivity.

**What evidence exists in the paper.** Figure 13 directly quantifies the memory gap. AMSP's peak memory for LLaMA-7B at 1024 GPUs is roughly 2× MiCS and 3–4× ZeRO-3. For LLaMA-30B, the gap narrows but AMSP remains the highest-memory system. Section VI-B2 explicitly notes: "AMSP consistently exhibits high memory consumption, particularly noticeable when comparing it to MiCS." The OOM result for ZeRO++ on LLaMA-30B at 32 GPUs (Figure 11c) is a cautionary tale—memory overhead can unexpectedly cause failures—but the paper does not discuss at what GPU count AMSP itself would encounter OOM for each model size. The minimum GPU counts for AMSP to fit each model are not reported.

**Mitigation status.** The paper acknowledges the memory tradeoff but treats it as an acceptable cost rather than a limitation to be solved. There is no mechanism in AMSP to dynamically adjust sharding based on available memory (the solver is an offline, one-time optimization for a fixed cluster configuration), no fallback to more aggressive sharding if memory pressure increases, and no discussion of how to extend AMSP's approach to memory-constrained regimes. The conclusion (Section VIII) does not mention reducing memory overhead as future work, framing the contribution entirely around communication reduction. For a practitioner whose primary constraint is GPU memory rather than communication bandwidth, AMSP offers no advantage and is potentially unusable, but the paper does not provide clear guidance on when this is the case.

### No Evaluation of Training Convergence or Model Quality

**The assumption or constraint.** AMSP changes the sequence and timing of communication operations relative to computation, uses select-and-drop mechanisms that discard gradient elements after AllReduce (Section IV-C), and employs inter-tensor distribution of optimizer states (Figure 6b) that assigns whole parameter tensors to different GPUs. The paper assumes these changes are numerically equivalent to standard ZeRO training—that they produce identical gradient updates and therefore identical model convergence. This assumption is stated implicitly rather than argued: the paper focuses exclusively on throughput metrics (MFU, TGS) and never measures training loss, validation perplexity, downstream task performance, or any convergence-related metric.

**The consequence.** Several mechanisms in AMSP could, in principle, affect numerical precision or optimization dynamics:

- **Select-and-drop after AllReduce (Sections IV-C2, IV-C3):** AMSP computes AllReduce on the full gradient buffer, then each GPU discards elements it does not need. If floating-point reduction order changes (because different GPUs participate in AllReduce groups compared to standard ZeRO, or because the bucketing strategy changes which gradients are reduced together), the resulting gradient values could differ at the level of floating-point rounding. In practice, these differences are usually negligible for training convergence, but the paper provides no evidence.

- **Inter-tensor vs. intra-tensor optimizer state distribution (Section IV-C2, Figure 6):** The inter-tensor approach assigns each parameter tensor in its entirety to a GPU, using a greedy algorithm to balance memory. This changes which GPU updates which parameters compared to intra-tensor sharding (where a single parameter tensor is split across GPUs). The optimizer state update (Adam) operates on per-tensor statistics; changing the assignment of tensors to GPUs does not change the math, but the greedy balancing could produce different memory access patterns, and the Broadcast operations for updated parameter dissemination (Phase 2) could introduce different communication ordering. The paper argues inter-tensor is necessary for FP8 compatibility (Section IV-C2), but does not verify that inter-tensor and intra-tensor produce identical model quality.

- **Decoupling ReduceScatter lifecycle from backward function (Section V-C1):** AMSP defers waiting for ReduceScatter completion until AccumulateGrad hooks fire, rather than blocking at the end of the backward function. This changes when gradients become available for subsequent operations. If there is any implicit synchronization in PyTorch's autograd engine that AMSP bypasses, gradient computation ordering could change, potentially affecting floating-point determinism.

**What evidence exists in the paper.** None. There is no training loss curve, no validation perplexity, no comparison of final model quality between AMSP and baselines. This is standard for systems papers focused on throughput, and the paper's comparison with ZeRO++ explicitly disables quantization "to ensure consistent model quality" (Section VI-A4), suggesting the authors are attentive to model quality concerns. But this makes the absence of any model quality evaluation for AMSP itself more notable—the paper takes care to ensure baselines are quality-equivalent while never verifying that AMSP itself is.

**Mitigation status.** The paper does not address this limitation. It does not claim that AMSP is numerically equivalent to standard ZeRO, nor does it provide convergence results. Section VIII mentions AMSP "has been used for training InternLM on thousands of GPUs" (footnote), which implies production use and suggests that model quality is acceptable in practice (otherwise the InternLM team would not use it), but this is circumstantial—no InternLM training results or quality comparisons are reported. For a practitioner deploying AMSP in a setting where training stability is critical and training runs are expensive (weeks on thousands of GPUs), the absence of convergence validation would require running their own quality checks before adoption, adding risk and cost not captured in the paper's throughput numbers.

### The Solver's Objective Minimizes Communication Time, Not End-to-End Throughput, and Ignores Overlap Effectiveness

**The assumption or constraint.** The Planner's optimization problem (Equations 1–7, Section V-B) minimizes total communication time `T_comm = T_p + T_g + T0_os + T1_os` subject to a memory constraint. This objective assumes that reducing total communication time directly improves throughput—that every saved microsecond of communication translates into faster training. The objective does not account for whether communication can be overlapped with computation, which determines how much of `T_comm` is actually *exposed* (visible in the critical path) versus *hidden* (absorbed behind computation).

**The consequence.** The solver might prefer a configuration with lower `T_comm` but worse overlap characteristics over one with slightly higher `T_comm` that overlaps far more effectively. For example, consider two hypothetical configurations:

- **Config A:** `T_comm = 100 ms`, but 80 ms can be overlapped with computation, exposing only 20 ms on the critical path.
- **Config B:** `T_comm = 80 ms`, but only 10 ms can be overlapped, exposing 70 ms on the critical path.

The solver would choose Config B (lower `T_comm`), but Config A would produce higher throughput (lower exposed communication).

This is not purely hypothetical. The paper's own analysis (Section V-C) shows that overlap effectiveness depends on the sharding configuration: when `sp = 1` (no parameter sharding), there are no AllGather/ReduceScatter operations to overlap, so Broadcast and AllReduce overlap are the only mechanisms. When `sp > 1`, AllGather/ReduceScatter overlap becomes available and can hide substantial communication. A naive solver minimizing `T_comm` might prefer `sp = 1` (which gives `T_p = 0`, eliminating a large communication term) even when `sp = 2` or `sp = 4` with good overlap would produce higher actual throughput because the `T_p` communication is almost entirely hidden behind computation.

**What evidence exists in the paper.** The paper partially addresses this by showing (Figures 16–17) that the solver's chosen configurations produce higher throughput than MiCS configurations, suggesting the objective is a reasonable proxy in practice. However, the paper never validates that the solver's configuration is throughput-optimal—only that it is better than a selection of baselines. There is no experiment comparing the solver's choice against a grid search of configurations evaluated by actual throughput measurement. The static-configuration finding (Innovation 4 in Section 4) is consistent with the solver making good choices, but does not rule out the possibility that a different configuration with slightly higher `T_comm` but better overlap would outperform the solver's choice.

The paper's overlap ablation (Table V) is informative but limited: it shows that *for a fixed configuration*, enabling overlap improves throughput. It does not show how the optimal configuration changes when overlap effectiveness is considered. The `M=1` regime (most relevant for large-scale training) is where the `T_comm` proxy is most reasonable because computation time per GPU is minimal, making overlap less effective (there is less computation to hide communication behind) and communication time more likely to be fully exposed. In this regime, minimizing `T_comm` directly is close to minimizing exposed communication. But for `M > 1` (smaller GPU counts), the mismatch between `T_comm` minimization and throughput maximization could be larger.

**Mitigation status.** The paper does not address this limitation. Section V-B states the objective is to "minimize the sum of communication costs subject to memory constraints" without discussing why `T_comm` is an appropriate proxy for throughput. The ablation in Section VI-D validates that the solver-chosen configuration outperforms the MiCS configuration, but does not validate that the solver's objective function correctly ranks configurations by throughput. A more rigorous approach would model exposed communication (accounting for overlap potential) or evaluate configurations by actual throughput measurement, but the paper's integer programming formulation does not capture overlap dynamics. For a practitioner, this means the solver's output should be treated as a strong heuristic rather than a guaranteed optimum—and if training throughput is the absolute priority, running a small grid search of solver-nearby configurations at the target scale to verify throughput would be advisable, which adds deployment complexity.
