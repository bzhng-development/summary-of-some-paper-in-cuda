# GenericAgent: A Token-Efficient Self-Evolving LLM Agent via Contextual Information Density Maximization

**ArXiv:** [2604.17091](https://arxiv.org/abs/2604.17091)

## 🎯 Pitch

Longer agent interactions don’t fail because context windows are small—they fail because the signal-to-noise ratio inside them collapses. GenericAgent reverses this by compressing verified past experience into reusable SOPs and code, slashing token consumption by up to 90% while matching or exceeding the accuracy of systems like Claude Code.

---

## 1. Executive Summary

This paper introduces **GenericAgent (GA)**, a self-evolving LLM agent system built around a single organizing principle: **context information density maximization**—the view that long-horizon performance is determined by how much decision-relevant information is maintained within a finite context budget, not by raw context length. GA realizes this through four co-designed mechanisms: a minimal atomic tool set (reducing persistent prompt overhead via 9 composable primitives rather than dozens of specialized tools), hierarchical on-demand memory (keeping only a lightweight orientation layer always visible while retrieving deeper facts and procedures through explicit tool calls), self-evolution as experience consolidation (compressing verified interaction trajectories into reusable Standard Operating Procedures and executable code), and layered context truncation and compression (head-tail truncation, tag-level compression, FIFO eviction, and a working-memory anchor prompt). Across task completion, tool-use efficiency, memory effectiveness, self-evolution, and web browsing benchmarks against Claude Code, OpenClaw, and Codex (using Claude Sonnet 4.6, Claude Opus 4.6, MiniMax M2.7, and GPT-5.4 backends), GA matches or exceeds the best competitor accuracy while consuming only 15–35% of their input tokens—achieving a 4.15 efficiency ratio on Lifelong AgentBench and a 5.70 ratio on RealFin-Benchmark—and reduces token consumption by up to 89.6% across repeated runs as experience is distilled into SOPs, establishing that improved long-horizon agent capability comes from controlling how information is represented and maintained during execution rather than from adding more tools, memory, or longer context.

## 2. Context and Motivation

### The Core Problem: Context, Not Capability, Is the Bottleneck in Long-Horizon Agents

The fundamental problem GenericAgent addresses is deceptively simple to state but structurally difficult to solve: **as LLM-based agents interact with environments over many steps, the context they accumulate progressively degrades their decision-making quality, not improves it**. This is not a token-cost problem—it is a reasoning-quality problem. The paper identifies three compounding mechanisms that turn longer interaction into worse performance:

**Positional bias.** Information placed in the middle of long contexts is significantly harder for LLMs to retrieve than information near the beginning or end (Liu et al., 2023). In a multi-step agent execution, the critical evidence for the current decision—the current file state, the most recent tool output, the task constraint that matters right now—often ends up buried in the middle of a growing conversation history, precisely where the model is least able to attend to it.

**Attention dilution from irrelevant content.** Irrelevant content doesn't simply remain unused; it actively degrades performance by competing for the model's finite attention budget (Shi et al., 2023). As tool definitions, raw HTML dumps, stale observations, and earlier failed attempts accumulate, they don't just waste tokens—they *crowd out* the decision-critical signals the model needs for the current step.

**Effective context window contraction.** The effective context length of LLMs is substantially smaller than their nominal window size (An et al., 2024). Part of every provided context is functionally inaccessible during generation. This means that even when "the information is in there somewhere," the model cannot reliably use it.

These three mechanisms reinforce each other in practice. As context grows longer, positional bias makes middle-positioned evidence harder to retrieve, irrelevant content consumes the model's limited effective attention, and an increasing fraction of the prompt is simply wasted. The result is a **structural inversion**: beyond a certain point, adding more context *reduces* performance, turning the very mechanism that enables multi-step reasoning (accumulating state) into the primary source of failure.

The paper articulates this as a **completeness–conciseness tension**. To make good decisions, the agent needs complete information about the current state. But to avoid attention dilution, it needs conciseness—only the decision-relevant subset of available information. These two requirements are in direct conflict, and the tension is structural rather than merely budgetary: even with an unbounded context window, the positional bias and attention dilution problems would remain. The finite effective context window turns this structural tension into a hard practical constraint.

> "The core tension is that multi-step execution inherently requires accumulating context, yet the accumulated context itself becomes the primary source of failure."

### The Second Problem: Experience Is Acquired but Not Retained

The paper identifies a second, compounding challenge: **effective experience accumulation and reuse across episodes**. In long-horizon environments, critical knowledge—user preferences, tool behaviors, effective action patterns, environmental quirks—is not available at the outset. It emerges only through repeated trial and failure during actual task execution. This exploration is unavoidable and necessary. The critical question is whether the lessons learned can be retained and reused when similar tasks arise later.

Without such a mechanism, agents face what the paper calls a **stagnation loop**:

> "Agents repeat the same failure patterns across sessions. Successful strategies, once discovered, are forgotten upon context expiration. Token expenditure scales linearly with task count, yet effective capability remains flat—a stagnation loop with no return on accumulated interaction."

This is not a hypothetical concern. Real-world agent deployments—whether a coding assistant used daily by a developer, a research assistant that browses the web, or a system-administration agent managing a server—generate enormous amounts of interaction data. Every session produces trajectories containing verified facts (this API endpoint requires authentication), discovered procedures (the correct sequence of git commands for this workflow), and corrected mistakes (don't use that file path; it's deprecated). Without experience consolidation, each new session starts from scratch, re-discovering what was already learned and re-making the same errors.

### Where Prior Approaches Fall Short

The paper positions existing work as addressing pieces of this problem but failing in specific, critical ways:

**Stateless episode treatment.** Most existing agent frameworks treat each task episode as stateless, with no persistent memory across sessions (Zheng et al., 2025; Lifelong AgentBench). While this simplifies system design, it guarantees the stagnation loop described above. The agent cannot benefit from prior interaction by construction.

**Raw-log retrieval without distillation.** Even when retrieval-augmented memory is introduced, it typically stores raw execution traces rather than distilled, reusable operational knowledge (Park et al., 2023; Zhong et al., 2023). Retrieving a 50-turn conversation history from last week's similar task does not help if the model must re-parse the entire trajectory to extract the one decision rule that mattered. The information is stored, but not in a form that improves decision-making efficiency.

**No feedback-driven refinement.** Stale or incorrect memories are rarely updated (Tan et al., 2025; Chen et al., 2026). A stored memory about a tool's behavior may become incorrect when the tool is updated, and an early failure pattern may be enshrined as a "lesson learned" even though a better approach was later discovered. Without mechanisms for revision and consolidation, memory systems can silently degrade rather than improve.

**Monolithic prompt assembly dominates context design.** Existing frameworks that rely on monolithic prompt assembly—injecting all tool definitions, all retrieved memories, and full interaction history into every prompt—devote a disproportionate share of the effective context budget to scaffolding and marginally relevant content. The paper argues this is a direct violation of the completeness–conciseness principle: by trying to ensure completeness through exhaustive inclusion, they destroy conciseness and, paradoxically, reduce the model's ability to use the information that *is* present.

**Self-evolution is studied, but not as a systems-level representation shift.** Prior work on self-evolving agents (Gao et al., 2026; Agent-Pro; Voyager) has shown that agents can improve through reflection and policy optimization. However, the paper argues that most approaches retain experience as natural-language guidance rather than as executable capability. An SOP stored as a paragraph of instructions still requires the model to re-interpret and re-plan from scratch on each use, incurring reasoning overhead even when the procedure is fully known.

### How GenericAgent Positions Itself

GA's core claim is that these two challenges—context degradation and experience loss—are different manifestations of the same underlying problem: **low contextual information density**. A context that buries critical evidence beneath tool schemas, stale observations, and irrelevant history suffers from low density. A memory system that stores raw logs rather than decision rules suffers from low density. A self-evolution mechanism that produces verbose reflections rather than executable code suffers from low density.

The paper frames GA not as a new memory module, a new reflection method, or a new browser agent in isolation, but as a **general-purpose agent architecture that connects these ingredients through a common optimization target**: maximizing how much decision-relevant information is introduced, maintained, and updated within the limited context budget.

> "GA is built around a single systems objective, maximizing contextual information density, and studies how multiple agent components should be co-designed when the bottleneck is not raw capability but how much decision-relevant information can be preserved within a limited context budget."

This framing has several important implications for how GA positions itself relative to prior work:

**Against tool-rich architectures (e.g., Claude Code's 53 built-in tools, OpenClaw's 18 tool factories):** GA argues that tool proliferation is actively harmful to context density. Each additional tool enlarges the schema injected into the context (prompt-level cost) and enlarges the action space, making planning more brittle (policy-level cost). GA's 9 atomic tools are not an austerity measure—they are a deliberate optimization that trades interface richness for context density, achieving capability through composition rather than enumeration.

**Against retrieval-augmented memory systems (e.g., Mem0, A-MEM):** GA argues that the key memory challenge is not storage or retrieval, but *selection*—deciding what is worth keeping in the first place. Its hierarchical memory applies a "No Execution, No Memory" rule: only information verified through successful tool execution is promoted to long-term storage. This is a stronger claim than typical retrieval-based approaches, which focus on recall accuracy rather than on the quality and reliability of stored content.

**Against existing self-evolution approaches:** GA claims that the endpoint of reflection should be a **representation shift** from verbose trajectories to compact operational assets—SOPs, code, and skills—so that improvement appears not only as better policy guidance but also as lower inference-time cost. This is why the paper's evaluation emphasizes efficiency convergence (token reduction across repeated runs) rather than only one-shot task success.

**Against context-compression work (e.g., LongLLMLingua):** GA treats compression as one layer in a multi-layer context optimization pipeline, combined with tool minimality (preventing low-value information from entering in the first place), hierarchical memory (keeping deep knowledge out of the default context), and self-evolution (progressively replacing verbose procedures with compact executable forms). The design goal is not to make compression more aggressive, but to generate less compressible content in the first place by controlling what information enters the active context at every system layer.

The paper thus positions itself at the intersection of agent architecture, memory systems, self-improvement, and context engineering, but with a unifying thesis: **context information density is the primary design variable for long-horizon agent performance, and all components of an agent system should be co-designed to optimize it.**

## 3. Technical Approach

### 3.1 Reader Orientation

GenericAgent is a **self-evolving LLM agent system**—a program that wraps a large language model (like Claude, GPT, or Gemini) and gives it persistent, controlled access to a computer's file system, terminal, browser, and memory so it can autonomously solve multi-step tasks across sessions, accumulating experience as it works. The system solves the problem that **long-horizon agent performance degrades because context gets cluttered with low-value information**, by actively managing *what* enters the model's limited attention window at every layer—minimizing tool definitions, hiding deep memory behind lightweight pointers, compressing successful experience into reusable code rather than storing raw logs, and aggressively trimming stale conversation history—so that at every decision step, the model sees only the highest-density, most decision-relevant information possible.

### 3.2 Big-Picture Architecture (Diagram in Words)

GenericAgent is organized as a **unified agent loop** that connects five major components through a single execution cycle:

1. **Minimal Atomic Tool Set** (Section 2.3.1): Nine composable primitives (`file_read`, `file_write`, `file_patch`, `code_run`, `web_scan`, `web_execute_js`, `ask_user`, `update_working_checkpoint`, `start_long_term_update`) that form the complete interface between the LLM and the environment. These tools are the *only* action channels—GA composes complex behaviors from these primitives rather than adding specialized tools.

2. **Hierarchical Memory Architecture** (Section 2.3.2): Four-layer memory with L1 (compact orientation index, always visible), L2 (verified facts, retrieved on demand), L3 (reusable procedures/SOPs, retrieved on demand), and L4 (raw session archives, for traceability). A global meta-memory layer defines the rules for how memory is organized, updated, and accessed.

3. **Self-Evolution Pipeline** (Section 2.3.3): A post-task consolidation process that converts verified execution trajectories into reusable Standard Operating Procedures (SOPs) and executable code stored in L2/L3 memory. Triggered at meaningful milestones (subgoal completion, error recovery), it applies a strict "No Execution, No Memory" filter—only validated, behavior-changing information is retained.

4. **Context Truncation and Compression** (Section 2.3.4): A four-stage pipeline that actively manages conversation history: tool-output truncation (head-tail clipping to bound individual message size), tag-level compression (replacing repeated blocks with placeholders, truncating reasoning traces), FIFO message eviction (removing oldest content when budget exceeded), and a working-memory anchor prompt (continuously injected summary preserving task-critical state across evictions).

5. **Compositional Capabilities Layer** (Section 3): Higher-level behaviors—Subagent Dispatch (spawning parallel child GA instances via CLI), Reflect Mode (watchdog and scheduled-task triggering via lightweight external scripts), and Autonomous Exploration (self-directed skill acquisition using a persistent skill tree)—that emerge from the CLI primitive without requiring new architectural layers.

Information flows as follows: a task enters the system (user instruction or autonomous trigger) → the global meta-memory and L1 index are injected into the active context → the LLM decides which tools to call, potentially retrieving deeper L2/L3 memory on demand → tool calls execute against the environment (file system, browser, terminal) through the unified dispatcher → tool outputs pass through Stage 1 truncation → the conversation history is periodically cleaned by Stage 2 compression and Stage 3 eviction → the Stage 4 anchor prompt preserves task-critical state across evictions → when the task completes, the self-evolution pipeline evaluates the trajectory, extracts verified rules and procedures, and commits them to L2/L3 memory with corresponding L1 index updates, making the experience available for future tasks.

### 3.3 Roadmap for the Deep Dive

The Technical Approach is organized to build understanding from the ground up, following the information lifecycle in GA:

- **First**, the design principles (Section 2.1 of the paper)—completeness-conciseness tension, tool minimality, hierarchical memory, self-evolution as experience consolidation, and context truncation and compression—because these principles are the "why" that motivates every subsequent design choice. Understanding them first prevents the implementation details from feeling arbitrary.

- **Second**, the atomic tool set (Section 2.3.1)—what tools exist, how they are defined and invoked, how their boundaries are enforced, and how they are individually optimized for token efficiency—because tools are the *only* channel through which GA interacts with the world, and their design determines what information enters the context at the most fundamental level.

- **Third**, the hierarchical memory architecture (Section 2.3.2)—the four-layer structure (L1–L4), the global meta-memory layer, the on-demand retrieval policy, and the L1 boundedness invariant—because memory controls what cross-task information persists and at what granularity, and the hierarchy directly implements the context-density principle by keeping deep knowledge out of the default context.

- **Fourth**, the self-evolution mechanism (Section 2.3.3)—what evolves (strategy, not tools), how knowledge accumulates (hierarchical memory), how quality is controlled (selective consolidation with "No Execution, No Memory"), and how the evolutionary trajectory is maintained (failure escalation)—because self-evolution is what makes GA improve over time rather than stagnate, and it depends directly on both the tool set and the memory architecture.

- **Fifth**, the context truncation and compression pipeline (Section 2.3.4)—Stages 1 through 4, the character-budget heuristic, and the token-budget approximation—because this is the operational mechanism that actively prevents context explosion during long-horizon execution, implementing the conciseness side of the design principle at the conversation-history level.

- **Sixth**, the emergent compositional capabilities (Section 3)—Subagent Dispatch, Reflect Mode, and Autonomous Exploration—because these are not separate architectural components but natural consequences of the minimal CLI-based architecture, demonstrating that the design principles produce capabilities beyond what was explicitly engineered.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems-design paper** whose core idea is that long-horizon agent performance is determined by how much decision-relevant information is maintained within a finite context budget, and that all components of an agent system should be co-designed to maximize this contextual information density.

---

#### Design Principles: Completeness, Conciseness, and the Structural Tension

The paper organizes its entire design philosophy around a single conceptual framework: the **completeness–conciseness tension** in context design. The argument proceeds in three steps:

**Step 1: Context quality, not context length, determines performance.** The paper grounds this in three independent empirical findings from the literature. First, Liu et al. (2023) demonstrated that LLMs exhibit pronounced positional bias: information in the middle of long contexts is significantly harder for the model to retrieve than information at the beginning or end. Second, Shi et al. (2023) showed that irrelevant content does not merely go unused—it actively degrades performance by competing for the model's finite attention. Third, An et al. (2024) established that the *effective* context length of LLMs (what the model can actually attend to) is substantially smaller than the *nominal* window size (what the API accepts). These three phenomena are not independent. As context grows longer, positional bias makes middle-positioned evidence harder to retrieve, irrelevant content consumes the model's limited effective attention, and an increasing fraction of the prompt becomes functionally inaccessible. The result is a structural inversion: beyond a certain point, **adding more context reduces performance**:

> "The result is that, beyond a certain point, adding more context does not improve performance and may instead reduce it."

**Step 2: Agent design must optimize two competing requirements.** From this diagnosis, the paper derives two primary requirements and one secondary constraint for context design in agent systems. The two primary requirements are in direct tension:

- **Completeness**: All information required for the current decision must be explicitly present in the context, preventing the model from relying on implicit assumptions or hallucinated inferences. If the current step requires knowing that a file was modified three turns ago, that information must be somewhere in the active context.

- **Conciseness**: Irrelevant and redundant information must be eliminated so that attention remains focused on decision-critical signals. If a tool's output contains 10,000 characters of HTML when only a single price value matters, the other 9,950 characters are actively harmful regardless of whether the model can technically process them.

The tension is that these two requirements pull in opposite directions. Including more potentially relevant information improves completeness but weakens conciseness. Summarization and compression improve conciseness but risk omitting details needed for completeness. The paper emphasizes that this tension is **structural rather than merely budgetary**—even with an unbounded context window, the positional bias and attention dilution problems would remain.

- **Naturalness**: The context should remain reasonably natural and semantically legible, especially when aggressive compression or artificial encodings make the representation harder for the model to use. The paper explicitly positions naturalness as a supporting constraint rather than a primary axis: in most agent failures, the dominant problem is not lack of natural phrasing but loss of completeness or conciseness. Naturalness "helps avoid brittle encoding, overly telegraphic summaries, and artificial formats that the model may parse less reliably."

**Step 3: The design problem reduces to maximizing information density within a finite effective window.** With finite effective attention as a hard constraint, the agent designer's job becomes: for a given decision step, include everything the model needs (completeness) and nothing it doesn't (conciseness), while keeping the representation interpretable (naturalness). This is the central optimization problem that GA's four mechanisms—tool minimality, hierarchical memory, self-evolution, and context truncation/compression—are designed to solve, each at a different layer of the system.

The finite effective context window sharpens this tension into a hard practical constraint: GA targets a compact budget of **under 30k tokens** (Section 2.1.4), on the argument that the "hallucination-free context length" for current models is roughly an order of magnitude smaller than their nominal 1M-token windows:

> "GA therefore targets a compact budget of under 30k tokens and invests in compression rather than expansion—packing higher-density information into a smaller window outperforms feeding diluted content into a larger one."

This 30k token target is not derived from a formal analysis of effective context length for specific models; it is presented as a practical operating point based on the observation that quality degrades substantially before nominal limits are reached.

#### Tool Minimality: The Justification and the Implementation

The paper's argument for a minimal tool set has two prongs: one at the prompt level (context density) and one at the policy level (decision quality).

**Prompt-level cost.** Each additional tool enlarges the tool schema and associated instructions injected into the context. In multi-turn interaction, this overhead accumulates and occupies effective context budget that should be reserved for task-relevant information. The paper treats this as a first-order concern: if 53 tool definitions occupy, say, 3,000–5,000 tokens of every prompt, and the effective context window is ~30k tokens, then 10–17% of the available attention budget is consumed before any task-specific information enters the context.

**Policy-level cost.** Each additional tool enlarges the action space and increases ambiguity in tool selection. When a model must choose among dozens of partially overlapping tools (e.g., `FileReadTool`, `GlobTool`, `GrepTool`, all of which can locate file content), the planning problem becomes harder. The increased ambiguity leads to more brittle behavior, weaker stability of tool-use patterns, and higher likelihood of execution errors and unnecessary retries—each of which generates additional turns, additional context growth, and additional opportunity for attention dilution.

Tool minimality is therefore "not merely an austerity choice; it is a better operating point that reduces both prompt overhead and decision complexity."

**The two conditions for tool selection.** The paper specifies that tools must satisfy two conditions:

- **Atomicity**: Each tool is restricted to an irreducible primitive capability with no functional overlap with other tools. A file-reading tool should read files and nothing else; a code-execution tool should execute code and nothing else. This eliminates the ambiguity that arises when multiple tools could plausibly accomplish the same subtask.

- **Compositional generalization**: Complex behaviors must be realizable through sequences of atomic primitives rather than requiring new specialized tools. If a task requires finding all Markdown files modified in the last week (which a specialized `GlobTool` might handle in one call), the agent should be able to compose `code_run` (executing a `find` command or Python script) to achieve the same result.

The paper makes a striking observation that clarifies the relationship between tools and capabilities: **the agent could theoretically accomplish any task using only the `code_run` tool**, because code execution can replicate the exact functions of every other tool. The remaining eight tools are therefore not capability expanders—they are **specialized shortcuts** that reduce decision-making cost and operational overhead for common operations:

> "Rather than forcing the agent to write code from scratch for every minor action, this carefully designed toolset acts as a harness, keeping the agent focused on efficient problem-solving."

This framing is critical for understanding why the tool set can be minimal while remaining general-purpose: tools are not the *source* of capability; they are *efficiency optimizations* for capabilities the model already possesses through code execution. The remaining tools make frequent operations cheaper (in decision cycles and tokens) without expanding the fundamental capability space.

**The nine atomic tools.** The tools are organized into five capability classes (Section 2.3.1):

*File Operations class:*
- `file_read`: Reads files with segmented access (start/count parameters), keyword anchoring, and line-number output. The paper specifies that this allows the agent to "inspect only the relevant regions" rather than dumping entire files into context.
- `file_patch`: Performs precise editing by enforcing unique `old_content` matching—the patch fails fast on zero or multiple matches, preventing silent multi-location edits that are a common failure mode in less constrained editing interfaces.
- `file_write`: Block writing for creating or overwriting files.

*Code Execution class:*
- `code_run`: Executes Python or Bash within a controlled runtime. Restricted to **one invocation per turn** (Section 2.3.1), ensuring each execution result is observed before the next action is planned—a deliberate constraint that prevents the agent from launching cascading scripts without intermediate verification.

*Web Interaction class:*
- `web_scan`: Performs low-cost page inspection by cloning the live Document Object Model (DOM), computing per-element visibility, classifying regions as main or non-essential through overlay and partition analysis, and removing covered or hidden elements before serialization. The paper claims this "reduces token cost by an order of magnitude compared to raw DOM output" (Section 2.3.1). Two modes are supported: `text_only` (truncated at 10,000 characters) and HTML (DOM-level budget of 35,000 characters with subtree pruning rather than head-tail truncation; see Table 1).
- `web_execute_js`: Executes JavaScript in the browser context for precise actions. Returns action results plus page-change observations, so many workflows can proceed without another full `web_scan`. Output is truncated at 8,000 characters for context entry (Table 1), with an optional `save_to_file` mode that writes the full output to disk while injecting only a short preview into the conversation history.

*Memory Management class:*
- `update_working_checkpoint`: Maintains short-term context by updating the `key_info` block in the working-memory anchor prompt. This is the mechanism by which the agent explicitly preserves task-critical state across context evictions (see Stage 4 of the truncation/compression pipeline).
- `start_long_term_update`: Triggers the post-task memory consolidation process, initiating the self-evolution pipeline that distills verified trajectories into L2/L3 memory.

*Human-in-the-loop class:*
- `ask_user`: Used when user decisions are required, providing an explicit intervention channel.

**Tool declaration and dispatch.** Each tool is represented as a verifiable schema contract with a name, a description, and a set of parameters described by JSON Schema, all under a consistent type function format. At runtime, this schema is injected into the interface, enabling GA to produce structured `tool_use` calls with explicit names and arguments. A unified dispatcher maps each call to a local executor and manages pre- and post-execution handling together with returned results. The paper emphasizes that this enforces "a clear permission hierarchy via the injected toolset": read-only tools can inspect but not modify; patch tools can edit subject to strict matching constraints; execution and web-control tools can trigger real system actions. All interactions return structured outputs through the dispatcher, ensuring full traceability.

**Boundary enforcement.** Each tool's capability scope is "strictly bounded and non-overlapping, avoiding the ambiguity and redundancy associated with overlapping functionality." This is not merely a design preference—it directly reduces the policy-level decision cost by eliminating the question of *which* tool to use for a given operation.

#### Hierarchical Memory Architecture

The core design problem for memory in GA is not storage capacity but **context occupancy**: how to retain knowledge across tasks without letting that knowledge consume the active context budget needed for current reasoning. The paper's solution is a four-layer hierarchy with an explicit retrieval policy that keeps deep memory out of the default context.

**The three functional memory types.** Before describing the four implementation layers, the paper defines three functional categories that cut across layers:

- **Working memory**: Continuously injected across turns, carrying only the minimal necessary task state—current objectives, constraints, and progress. This allows the agent to maintain execution continuity without reconstructing the full context each time.

- **Always-on memory**: Persistently visible but "deliberately compressed to the lightest possible orientation information." It provides only the basic memory layout and navigation index, rather than loading complete knowledge into the context by default.

- **Long-term memory**: Kept outside the default context and managed via an explicit post-task consolidation process. Only verified and stable knowledge is written back, "ensuring that historical accumulation does not automatically translate into continuous context growth."

These functional categories map onto the four implementation layers as follows: L1 constitutes the always-on memory; L2 and L3 together make up long-term memory; working memory is implemented through the Stage 4 anchor prompt mechanism (Section 2.3.4); and L4 provides durable storage for persistence and traceability without being designed for frequent direct injection into the runtime context.

**The four-layer implementation (Section 2.3.2).** The four layers are:

- **Layer 1 (L1): Index layer.** Stores "compact pointers, including high-frequency entry points, keyword mappings, and a small set of hard constraints." L1 is the core content of always-on memory, serving as a fast navigation surface that allows the agent to route memory requests to deeper layers. Each L1 entry records only the *existence* of a knowledge category, not its substantive content.

- **Layer 2 (L2): Fact layer.** Stores "verified and stable factual information that remains valid over long periods." Admission is strictly controlled: information is written into L2 only after being validated through execution and proven reusable across tasks. Transient states, one-time events, and unverified hypotheses are deliberately excluded. Example L2 content: "the user's deployment server runs Ubuntu 22.04 with Python 3.11" (a verified fact); counterexample: "the API seemed slow yesterday" (a transient observation that was never validated).

- **Layer 3 (L3): SOP layer.** Stores reusable procedural knowledge, including task workflows, preconditions, key execution steps, common failure cases, and corresponding debugging or recovery strategies. This is where self-evolution deposits its outputs: procedures distilled from successful trajectories. Example L3 content: the multi-step procedure for investigating GitHub PRs identified in Case A3 (Appendix Section 3.3), including the batch-extraction strategy, the script-based approach, and the manual fallback flow.

- **Layer 4 (L4): Raw session archive layer.** Stores historical execution sessions for persistence and traceability. Unlike L1–L3, L4 is "not designed for frequent direct injection into the runtime context." Its role is to support reconstruction of prior trajectories, audit of past decisions, and recovery of task context when needed—but only through explicit retrieval, never by default.

**The global meta-memory layer.** Above the four content layers sits a meta-memory layer that "defines the overall memory map, core rules, and update boundaries, providing the model with a shared frame of reference before execution so that it understands how memory is organized, what each layer is for, and how updates should be handled, thereby reducing arbitrary writes, historical misreads, and cross-task leakage." The full meta-SOP content is loaded on demand via file reads rather than always preloaded, keeping the always-on layer lightweight.

**The retrieval policy: L1-first routing.** In practice, GA injects only the meta-memory and L1 index layer by default. The agent follows an L1→L2/L3 routing chain to retrieve deeper factual or procedural knowledge only when needed:

> "GA injects only the meta-memory and L1 index layer by default, following an L1→L2/L3 routing chain to retrieve deeper factual or procedural knowledge only when needed, excluding irrelevant content from the active context."

This routing is enforced through tool calls and prompt policy rather than a hardcoded mandatory pipeline. The agent itself decides when to retrieve deeper memory based on the task at hand, using the `file_read` tool to access the appropriate L2 or L3 content.

**The triggered commit mechanism for long-term consolidation.** Information does not flow automatically from raw experience to long-term memory. Instead, GA uses a **triggered commit mechanism**: when information is identified as potentially valuable, it enters a validation stage where its usefulness and reusability are checked before being committed. Only verified information is written into L2 or L3 through small, incremental updates, with the L1 index updated accordingly. This prevents memory from growing in an uncontrolled manner over time and ensures that only behavior-changing, validated information occupies the persistent memory layers.

**The L1 boundedness invariant.** The paper identifies a critical design invariant: L1 must remain bounded even as L2 and L3 expand over time. Each L1 entry records only the existence of a knowledge category, not its substantive content. New entries are introduced only when genuinely new categories arise—not when new facts or procedures are added to existing categories. The paper claims that the overall description length of L1 "approaches the Kolmogorov complexity of the categorical structure of the knowledge set"—an information-theoretic way of saying that L1 contains the shortest possible description of *what categories of knowledge exist*, with no redundancy.

This extreme degree of compression is feasible because of an architectural property: **the LLM itself serves as the decoder**. Once the agent infers from an L1 entry that a relevant capability or fact category exists, it can expend tool calls and tokens to retrieve the full content from deeper layers. A minimal existence-level signal in L1 is therefore sufficient for accurate routing—the model doesn't need the content itself; it just needs to know that the content exists and where to find it:

> "This extreme degree of compression is feasible because the LLM itself serves as the decoder: once it infers that a relevant capability or fact exists, it can expend tool calls and tokens to retrieve the full content from deeper layers, so a minimal existence-level signal is sufficient for accurate routing."

This is a subtle but important design insight: the memory hierarchy doesn't need to expose content at the top level because the LLM is capable of *reasoning about* memory organization and *actively retrieving* content, making a minimal index sufficient.

#### Self-Evolution as Experience Consolidation

The paper positions self-evolution as the mechanism by which GA escapes the stagnation loop—converting raw interaction experience into reusable assets that improve future task performance without increasing context cost. The design addresses four sub-problems: what evolves, how knowledge accumulates, how quality is controlled, and how the evolutionary trajectory is maintained.

**What evolves: strategy, not tools.** GA maintains a strict separation between its **fixed tool layer** (the nine atomic tools, which remain constant) and its **evolving knowledge layer** (SOP files and reusable scripts stored in L2/L3 memory). While the tool interface works for any task and stays the same during operation, all task-specific capabilities are stored in SOP files and reusable code. The agent can read, create, and modify these knowledge assets using its own tools.

This separation ensures that learning new tasks doesn't interfere with existing skills—a form of catastrophic forgetting prevention at the system level. Over multiple sessions, real-world feedback helps refine the SOPs. Common subtasks naturally evolve from plain-text instructions into stable, reusable scripts, upgrading the agent's knowledge representation from declarative (what to do) to executable (code that does it).

The paper is explicit about the representation goal: the endpoint of reflection should be a **representation shift** from verbose trajectories to compact operational assets:

> "GA makes a stronger systems claim: the endpoint of reflection should be a representation shift from verbose trajectories to compact operational assets. Verified experience is progressively transformed into SOPs, code, and reusable skills, so improvement appears not only as better policy guidance but also as lower inference-time cost."

**How knowledge accumulates: hierarchical memory.** Because self-evolution deposits its outputs (SOPs, code, verified facts) into the hierarchical memory architecture, knowledge gained during one session is immediately available in future ones. The L1 index automatically tracks new L2 facts and L3 procedures, eliminating the need for manual updates. Every successfully completed task that produces consolidated knowledge permanently expands the agent's practical capabilities—the memory system provides both the storage substrate and the retrieval pathway.

**How quality is controlled: selective consolidation with "No Execution, No Memory."** This is the core quality-control mechanism and one of the paper's strongest claims. GA saves raw action traces at the lowest memory level (L4), but it **does not automatically promote these traces** to higher long-term memory levels (L2 or L3). Reusable L3 procedures are generated only through explicit consolidation steps, triggered at meaningful milestones such as successfully completing a subgoal or recovering from a system error.

During the consolidation phase, the agent only retains information that has been **strictly verified through successful tool execution**. The paper states the rule explicitly:

> "Guesses, temporary intermediate states, and failed decision branches are systematically discarded under the 'No Execution, No Memory' rule."

This rule has a concrete operational meaning: if the agent *hypothesized* that an API endpoint requires authentication but never actually tested this hypothesis by calling the endpoint and observing the response, the hypothesis is not promoted to L2 memory. Only information that was *used in a successful execution*—the endpoint was called, authenticated, and returned the expected result—can be consolidated. This strict filtering prevents memory pollution, ensuring that accumulated knowledge remains reliable and practically reusable.

The paper also describes a **reflection-based adaptation mechanism** that adjusts the scoring weights used for autonomous exploration (though this is presented as preliminary and not fully validated; see Section 3.3). For each completed exploration task, if the predicted score was high (`$S(t) > 8.0$`) but actual usage was low (`$u(t) < 3$` within 30 days), the weight of the dominant dimension in the task's score vector is reduced by 10%. Conversely, if `$S(t) < 5.0$` but `$u(t) > 5$`, the corresponding weight is increased by 10%. All weights are re-normalized to sum to 1 after adjustment. This creates a feedback loop where the system discovers which dimensions best predict practical value in the user's specific workflow, though the paper acknowledges this mechanism has "not yet accumulated enough long-term data to definitively prove its effectiveness across diverse, real-world user workflows."

**How the evolutionary trajectory is maintained: failure escalation.** To prevent the agent from getting trapped in endless loops of incorrect actions—which would degrade performance rather than improve it—GA introduces a staged escalation mechanism for handling failures. The process has three steps:

1. **Localized adjustment**: The agent analyzes the immediate error message and makes a small, localized fix, then retries.

2. **Strategy switch or information search**: If the failure persists, the agent abandons its current approach entirely. It is forced to either switch to a completely new strategy or search the environment for missing information that might resolve the root cause.

3. **Human intervention request**: If all automated attempts fail, the agent pauses and requests human intervention via the `ask_user` tool.

This structured escalation prevents the agent from blindly repeating mistakes and "ensures it breaks out of dead ends and keeps its long-term learning on the correct path." The escalation mechanism is coupled to the self-evolution pipeline: when a failure escalates to strategy switch or human intervention, the resulting trajectory (including the corrected approach) becomes high-value input for future consolidation, because it represents verified knowledge about what *doesn't* work and what does.

#### Context Truncation and Compression Pipeline

This is the operational mechanism that actively maintains context density during long-horizon execution, preventing the conversation history from growing without bound. It operates at four stages, ranging from fine-grained edits to broad removals, with a global character-budget heuristic as the unifying trigger.

**The character-budget heuristic.** Since GA cannot directly obtain precise token counts from the underlying model API, context budget management uses a character-domain approximation. The paper defines:

$$CH = \sum_{m \in H} \text{len}(m)$$

$$B = \alpha \cdot W_{\text{tokens}}$$

$$\alpha \approx 3 \text{ chars/token}$$

where `$\text{len}(m)$` is the character length of message `$m$` after JSON serialization, `$H$` is the set of all messages in the current conversation history, `$W_{\text{tokens}}$` is the configured token window, and `$\alpha$` is the empirical character-to-token ratio used to approximate the token budget as a character budget. `$CH$` is the total character length of all messages, and `$B$` is the character budget upper bound.

**What it computes:** For each new message added to the conversation, the system calculates the total serialized character length of all messages in the history and compares it against the budget threshold `$B$`, which is derived from the desired token limit by multiplying by approximately 3 characters per token. If `$CH > B$`, the compression or eviction mechanism is triggered.

**Why this form:** The `$\alpha \approx 3$` approximation is explicitly acknowledged to have error margins. For ASCII-dominated content, each token corresponds to roughly 4 actual characters, so the `$\alpha = 3$` setting slightly underestimates character efficiency, causing "mildly early eviction—a conservative but safe failure mode." For CJK (Chinese, Japanese, Korean) content, each character typically consumes 1–2 tokens, so the `$\alpha = 3$` ratio "substantially underestimates actual token usage, risking delayed eviction and potential context overflow." The paper presents this as a practical tradeoff rather than a principled solution—the approximation is conservative for the dominant character set in the evaluation (ASCII) but would need adjustment for CJK-heavy deployments.

**Stage 1: Tool-output truncation.** Each tool handler limits its return value before adding it to the message history. If the output exceeds a predefined character threshold `$L$`, the system retains only the first and last `$L/2$` characters, replacing the middle section with an ellipsis. This is a simple head-tail truncation strategy.

Table 1 specifies the per-tool thresholds:

| Tool / mode | `$L$` (chars) |
|---|---|
| `code_run` | 10,000 |
| `web_execute_js` (with `save_to_file`) | 8,000 |
| `web_scan` (`text_only`) | 10,000 |
| `web_scan` (HTML) | 35,000 |
| `file_read` | ~1,280 per line; 20,000 total |

The `web_scan` HTML mode uses DOM-level character budget with subtree pruning rather than simple head-tail truncation, reflecting the structured nature of HTML content. The `web_execute_js` threshold of 8,000 applies only to the preview injected into the conversation; when `save_to_file` is enabled, the full output is written to disk for later reference.

**Stage 2: Tag-level compression.** Older messages tend to accumulate redundant text inside XML tags—reasoning traces (`<thinking>`), tool invocations (`<tool_use>`), tool results (`<tool_result>`), and repeated working-memory blocks (`<history>`, `<key_info>`). To reduce this redundancy, the system runs a compression pass roughly every five turns.

The compression pass handles redundancy in two ways:

- **Placeholder replacement**: Repeated working-memory blocks (like `<history>` and `<key_info>`) are replaced with a short placeholder, because only the most recent snapshot is actually needed for the current decision. Earlier copies of these blocks are redundant once the Stage 4 anchor prompt mechanism ensures the latest version is always available.

- **Windowed truncation**: Content inside reasoning and tool tags (`<thinking>`, `<tool_use>`, `<tool_result>`) is truncated, keeping only an approximately 800-character window—the beginning and the end of the text. This preserves the structure of the reasoning or tool interaction while removing the middle bulk that is least likely to contain decision-critical information (consistent with the positional bias findings that middle-content is hardest to retrieve).

To ensure the model always has the latest context, the **10 most recent messages are exempt from this compression**. The five-turn interval between compression passes also provides an efficiency benefit: the unchanged older messages result in prompt-cache hits in roughly 80% of turns (as reported in Stage 2 description), reducing the computational cost of reprocessing the full context.

**Stage 3: Message eviction.** When a new message causes the total history length `$CH$` to exceed the character budget `$B$`, the system triggers an eviction process:

1. It reruns the Stage 2 compression using stricter rules, exempting only the **4 most recent messages** (instead of the usual 10).

2. It removes the oldest messages in FIFO (first-in, first-out) order until the history size drops below **60% of the total budget**, leaving sufficient room for future turns. This 60% threshold is a practical choice to prevent immediate re-triggering of eviction on the next turn.

3. After eviction, the newly exposed oldest message is cleaned up to maintain API consistency—for example, converting orphaned tool-result references into plain text that doesn't violate the API's expected message format.

Critically, evicted content is not completely lost: the Stage 4 anchor preserves essential task states, and the paper claims that even a "<30k context window can hold dozens of historical turns" because of the combined effect of Stage 2 compression and Stage 3 eviction.

**Stage 4: Working-memory anchor prompt.** After every tool invocation, an anchor prompt is automatically attached to the next user message. This anchor contains three elements:

- (i) The **20 most recent one-line turn summaries**, each compressed to roughly one hundred characters. These summaries provide a compressed trajectory of recent actions without preserving the full content of each turn.

- (ii) The **current turn number**, providing explicit positional awareness in long sequences.

- (iii) A persistent **`key_info` block** maintained by the agent via the `update_working_checkpoint` tool. This is the agent's explicit mechanism for preserving task-critical information—current objectives, discovered constraints, intermediate results—across context evictions.

Because this anchor is injected into every new user message, Stage 2 compression automatically replaces the older copies with placeholders (since they're identified as repeated blocks). This ensures only the newest version carries the full data payload. Once older messages are evicted in Stage 3, this anchor becomes the sole source of long-term state preservation, keeping task-critical information active in the context even when the messages that originally contained it have been deleted.

The net effect of Stages 1–4 is that the active context remains compact and decision-relevant throughout long-horizon execution, even as the number of interaction turns grows. The context does not grow linearly with turn count—it stabilizes at a managed size determined by the budget `$B$` and the compression aggressiveness.

**Auxiliary: Tool-schema elision.** An additional optimization applies when using the text-protocol path (as opposed to the native API path): if a tool's definition hasn't changed from the previous turn, its full schema is removed from the prompt and replaced with a brief natural-language reminder. To prevent the model from forgetting the exact tool formats over time, the full schema is periodically re-sent—either after a fixed number of turns or when the active prompt gets too long. This optimization is **not used in the native API path**, which requires sending complete tool definitions on every call.

#### Compositional Capabilities: Subagent Dispatch, Reflect Mode, and Autonomous Exploration

The paper presents these as **emergent capabilities**—behaviors that arise naturally from GA's minimal architecture without requiring new architectural layers. The key primitive enabling them is that GA exposes itself as a **self-hosted CLI program**: a standalone executable that can be invoked from the terminal with arguments.

**Subagent Dispatch.** Because GA is a CLI program, a parent GA instance can spawn child instances simply by executing a standard terminal command (via `code_run`). A "subagent" is not a special object or a dedicated manager—it is simply a standard, independent GA process communicating through the same interaction protocol as the parent.

Context isolation is naturally guaranteed: each instance runs in its own memory space and maintains its own conversation history, ensuring subtasks never interfere with one another. The paper describes a "map-reduce workflow" pattern: the parent prepares independent inputs, spawns one subagent CLI process per input, and seamlessly merges the results once all child processes finish.

**Reflect Mode.** GA's Reflect Mode is a daemon-like behavior where the agent "requires no user instruction; instead, it continuously monitors for environmental changes and automatically triggers the corresponding task once a specific condition is detected." The mechanism is architecturally simple: a lightweight external script periodically checks conditions, and when a rule is triggered, the script dispatches the returned string as a standard task to the GA CLI. This strictly separates the triggering logic (in the external script) from the execution logic (in the stable core runtime).

Two concrete applications are described:

- **Watchdog**: Monitors for changes in the environment (e.g., a new file appearing in a watched directory, an error log being written) and triggers GA immediately upon detection.

- **Scheduled Task**: Uses time-based rules (e.g., cron-style scheduling) to generate GA tasks at specific intervals or exact times.

Both share the same underlying mechanism and differ only in how the external trigger script is written. Because these trigger rules are maintained as standalone scripts outside the agent, developers can update them at runtime without restarting the core agent process. The paper emphasizes that neither capability required extending the core agent loop:

> "The common thread across these two capabilities is that neither required extending the core loop. Both emerge from the CLI as a single primitive, and the core runtime remains stable throughout."

**Autonomous Exploration Capability.** Autonomous exploration is presented as the natural combination of Subagent Dispatch and Reflect Mode, where the triggering logic is internal rather than external—the agent itself decides what to explore and when.

The central data structure is a **persistent skill tree**—a two-level map where categories (e.g., `web_automation`, `data_processing`) contain named skills, each recording its associated tool scripts and a monotonically increasing usage counter. This skill tree serves a dual purpose: it acts as a global index of the agent's current capabilities, and it is the core dataset driving exploration decisions.

*Trigger Mechanism.* Exploration can be initiated in two ways: (1) **task mode**, where an external orchestrator submits a one-shot task via a file-system mailbox and polls for results; (2) **reflect mode**, where a user-supplied callback is polled at a fixed interval (default: every six minutes) and returns a non-empty string that is injected as a new prompt. The default trigger fires with a fixed prompt directing the agent to consult its exploration procedure.

*Exploration Task Generation.* When no pending task list exists, the agent enters planning mode. The curriculum planner inspects the current skill tree and scores task candidates along four dimensions using a weighted sum:

$$S(t) = w_b B(t) + w_d D(t) + w_u U(t) + w_i I(t)$$

where `$B(t)$` is the breadth score (rewarding filling under-populated skill categories), `$D(t)$` is the depth score (rewarding enhancing frequently-used skills), `$U(t)$` is the utility score (capturing estimated practical value), and `$I(t)$` is the innovation score (favoring novel techniques or domains). Each dimension is scored on a 1–10 scale.

**What it computes:** For each candidate exploration task, this weighted sum produces a scalar priority score. Tasks with higher scores are scheduled first. The scoring combines structural factors derived from skill-tree statistics (breadth and depth) with semantic factors estimated by the LLM (utility and innovation).

**Why this form:** The weighted sum decomposes the exploration decision into interpretable dimensions, allowing the system to explain and adjust its priorities. The breadth and depth components are computed deterministically from the skill tree, while utility and innovation are estimated by the LLM—a division of labor that makes the scoring partially auditable while retaining the model's ability to assess semantic qualities.

The breadth and depth components are computed directly from skill-tree statistics:

$$B(t) = 10 \times \max\left(0, 1 - \frac{|S_c|}{\bar{S} + 1}\right)$$

$$D(t) = 10 \times \frac{u(t)}{u_{\max} + 1}$$

where `$|S_c|$` is the number of skills in the target category, `$\bar{S}$` is the mean skill count across all categories, `$u(t)$` is the usage count of the target skill, and `$u_{\max}$` is the maximum usage count across all skills.

**What these compute:** `$B(t)$` produces a score from 0 to 10 that is highest when a category has few skills relative to the average—rewarding the agent for exploring under-developed capability areas. The max with 0 ensures the score doesn't go negative for categories that are already above average. `$D(t)$` produces a score from 0 to 10 that is highest for the most frequently used skill—rewarding the agent for deepening capabilities that are already valuable. The `$+1$` in the denominators prevents division by zero when a category is empty or the maximum usage count is zero.

**Why these forms:** The breadth formula encodes the exploration-exploitation tradeoff at the category level: categories below the average skill count get high breadth scores, incentivizing the agent to diversify its capabilities. The depth formula encodes the same tradeoff at the individual skill level: frequently-invoked skills get high depth scores, incentivizing the agent to improve what it already uses often. Together, they provide a structured way to balance exploring new capabilities against refining existing ones.

The weights are initially set to:

$$(w_b, w_d, w_u, w_i) = (0.3, 0.2, 0.3, 0.2)$$

prioritizing breadth and utility equally. The resulting task list must span at least four distinct skill categories, preventing narrow concentration. Planning and execution are strictly separated: the planner produces a task list and immediately yields control; execution resumes in the next invocation.

*Execution and Consolidation.* Each autonomous task proceeds through a fixed sequence: context loading (retrieve recent history and pending tasks), skill search (query the skill tree for relevant tools and identify gaps), execution (research, prototype, and validate within a sandboxed temporary directory), report writing (a Markdown document with machine-readable metadata tags for automatic skill-tree updates), skill consolidation (an atomic operation that archives the report, updates the skill tree, and increments usage counters), and task-list advancement. Even failed experiments are thoroughly documented to prevent future planning rounds from repeating the same dead ends.

*Limitations.* The paper acknowledges several limitations of the autonomous exploration design: (1) the 30-round execution cap means highly complex research tasks may span multiple sessions with continuity maintained only through written reports; (2) the reflection-based weight adjustment is "a preliminary design" that hasn't been validated across diverse real-world workflows; (3) the self-improvement log relies on manual user curation; and (4) advanced skill tree management (merging categories, deprecating tools, restructuring) remains entirely manual.

#### Summary of Design Choices and Their Justifications

- **Nine atomic tools** over a richer specialized inventory: reduces both prompt-level overhead (fewer tool schemas in context) and policy-level decision complexity (fewer ambiguous tool choices), while preserving full capability through compositional generalization and the `code_run` escape hatch.

- **Hierarchical L1-first retrieval** over flat memory injection: keeps the default context sparse (only orientation pointers) while preserving access to deep knowledge through on-demand retrieval, directly implementing the completeness–conciseness balance.

- **Triggered commit with "No Execution, No Memory"** over automatic memory promotion: prevents memory pollution from unverified hypotheses, transient states, and failed branches, ensuring that only behavior-changing, validated information occupies persistent memory.

- **Four-stage context truncation/compression** over simple truncation or no management: provides layered control from fine-grained (tool-output head-tail clipping) to coarse-grained (FIFO message eviction), with the working-memory anchor ensuring task-critical state survives all compression stages.

- **Character-budget heuristic with `$\alpha \approx 3$`** over direct token counting: a practical approximation that works without API-level token access, with acknowledged error margins that are conservative for ASCII and risky for CJK content.

- **CLI as the native execution surface** over plugin frameworks, event buses, or orchestration layers: enables Subagent Dispatch, Reflect Mode, and Autonomous Exploration to emerge from standard terminal primitives without requiring new architectural layers, embodying the paper's thesis that "minimal architecture is a necessary prerequisite for autonomous agent evolution."

- **Fixed tool layer with evolving knowledge layer** over end-to-end model fine-tuning: separates what is stable (tool interfaces) from what improves (SOPs, scripts, facts), enabling safe, incremental capability growth without catastrophic interference or the need for model retraining.

- **Staged failure escalation** over simple retry or immediate human intervention: provides graduated recovery that preserves autonomy for recoverable errors while ensuring the agent doesn't loop on unsolvable problems, and generates high-value trajectories for future consolidation at each escalation boundary.

## 4. Key Insights and Innovations

### Innovation 1: Context Information Density as a Unifying Design Target

Prior work on LLM agent systems has largely treated individual components—tool interfaces, memory modules, self-reflection mechanisms, and context compression—as independent engineering problems, each with its own optimization criteria. Tool design focuses on covering capability surface area (more tools = more power). Memory systems optimize for retrieval accuracy against stored content. Reflection methods maximize one-shot task improvement. Context compression reduces token count. These are all reasonable local objectives, but they operate in isolation and sometimes at cross-purposes: a memory system that maximizes recall might flood the context with marginally relevant content; a tool suite that maximizes coverage might consume a third of the effective attention budget with schema definitions.

The paper introduces a genuinely integrative concept: **context information density**—roughly, the ratio of decision-relevant information to total context content at each decision step—as the single objective that should govern the co-design of all agent components. This is not just a new metric. It is a **diagnostic reframing** that reveals why previously independent design choices are actually tightly coupled.

The reframing works by identifying two primary requirements—completeness and conciseness—that are in structural tension, not merely a resource tradeoff. The tension persists even with unbounded context windows because positional bias and attention dilution are properties of the model architecture, not the token budget. This insight is fundamental rather than incremental: it shifts the designer's question from "how much can we fit in context?" to "what deserves to occupy the model's finite effective attention?" The answer directs attention away from storage capacity and toward *selection* and *representation*—the decisions about what to include, what to exclude, and in what form.

The concrete payoff is visible across the evaluation. On Lifelong AgentBench (Table 2), GA achieves 100% accuracy while consuming only 222k input tokens compared to Claude Code's 800k and OpenClaw's 1.43M—an input efficiency ratio of 4.15. On the context explosion stress test (Table 7), after installing 20 skills and intensive usage, GA's full prompt length is 2,298 tokens compared to 22,821 (Claude Code), 23,932 (Codex), and 43,321 (OpenClaw). These are not marginal improvements—they represent an order-of-magnitude difference in context occupancy—and they emerge not from a single compression trick but from the co-design of all four components around a common objective.

### Innovation 2: Tool Minimality as an Active Optimization Rather Than an Austerity Measure

The dominant paradigm in agent system design has been to maximize the tool surface: Claude Code exposes 53 built-in tools, OpenClaw provides 18 tool factories with runtime plugin injection, and many frameworks treat tool addition as the primary mechanism for expanding capability. The implicit assumption is that more tools = more capable agent, and that the prompt overhead of tool definitions is a minor cost worth paying for broader coverage.

GA inverts this assumption and treats tool minimality as a **first-order optimization target**, arguing that each additional tool imposes costs at two levels: a prompt-level cost (schema definitions consuming effective context budget) and a policy-level cost (larger action space increasing planning ambiguity and execution brittleness). The innovation is not the observation that fewer tools reduce prompt size—that's obvious. The innovation is the claim that a carefully designed minimal tool set can **preserve full general-purpose capability** through compositional generalization while substantially improving both efficiency and decision quality.

The paper supports this claim with a striking architectural observation: the `code_run` tool alone could theoretically replicate the functionality of every other tool. The remaining eight tools are therefore not capability expanders but *efficiency optimizations*—they make frequent operations cheaper in decision cycles and tokens without extending the fundamental capability space. This reframes the tool design problem from "how do we cover every possible action?" to "which actions are frequent enough to justify a dedicated shortcut?" The distinction is important because it decouples capability from tool count: you don't need a `GlobTool` if `code_run` can execute a `find` command; the question is whether the token and decision-cycle savings of the specialized tool justify its persistent prompt overhead.

The evidence for this claim comes from the tool-use efficiency experiments (Table 3, Figure 3). The tool usage distribution analysis (Figure 3) reveals that even in tool-rich systems, actual execution is dominated by a small subset: Claude Code's top 4 tools account for ~92% of calls, OpenClaw's top 6 for ~90%. The long tail of rarely-used tools occupies prompt context while contributing little to execution. GA's 9 tools produce a more concentrated distribution centered on `code_run` (31.2%), `file_read` (34.4%), and `web_execute_js` (17.2%). On the long-horizon complex tasks (Table 4), GA matches Claude Code's 100% success rate while using only 188,829 total tokens (35.1% of Claude Code's 537,413) and 12.8 tool calls (compared to 22.6). This demonstrates that the compositional approach preserves capability while reducing both context overhead and interaction complexity.

### Innovation 3: The "No Execution, No Memory" Principle as a Selection-Centric Memory Paradigm

The prevailing approach to agent memory has been storage- and retrieval-centric. Systems like Mem0 and A-MEM focus on storing interaction content and retrieving relevant items through embedding similarity or structured queries. The quality criterion is retrieval accuracy: does the system surface information relevant to the current query? This framing treats memory as a recall problem—the challenge is finding what was stored.

GA proposes a fundamentally different quality criterion for agent memory: **selection before storage**. The "No Execution, No Memory" rule states that only information verified through successful tool execution can be promoted to persistent long-term memory. Guesses, hypotheses, transient observations, and failed decision branches are explicitly excluded. This shifts the memory problem from "can we find what we stored?" to "did we store the right things?"—a selection problem rather than a retrieval problem.

This is a conceptual move with significant practical implications. In retrieval-centric memory, stale or incorrect information can be stored (because everything is logged) and must be managed at retrieval time through ranking, filtering, or confidence scoring. In selection-centric memory, the filter is applied at write time, ensuring that persistent memory never contains unverified content to begin with. The quality guarantee is structural rather than probabilistic: by construction, L2/L3 memory contains only information that has been validated through successful interaction with the real environment.

The evidence for this principle's effectiveness comes from the memory ablation (Table 5) and long-term fact retention (Table 6) experiments. On the dangerous-goods classification task, Condensed Memory (165 tokens of action-guiding rules only) achieves the same 66.48% task success rate as Redundant-Memory (288 tokens with background descriptions added) and outperforms Full-Memory (52.44% with the complete unedited SOP at 575 tokens). The information that matters is the small set of decision rules, not the surrounding explanatory content—and the selection-based approach captures exactly those rules because they are what was verified during successful execution.

On the LoCoMo benchmark (Table 6), GA achieves the highest F1 and BLEU scores across all four task categories (multi-hop, temporal, open-domain, single-hop) **without using an embedding model or vector database**. It outperforms embedding-based systems (Mem0, A-MEM) specifically because its memory contains verified facts rather than raw logs—the retrieval step is simpler because the stored content is already clean. This is a striking result: selection-centric memory with precise organization can exceed the factual retention capabilities of dedicated vector-based retrieval systems, suggesting that the dominant bottleneck in agent memory is not retrieval architecture but content quality.

### Innovation 4: Self-Evolution as Representation Shift, Not Policy Improvement

Research on self-evolving agents has largely focused on improving what the agent *does*—better action selection, more accurate planning, higher task success rates. Systems like Reflexion, Agent-Pro, and Voyager demonstrate that agents can reflect on their experiences and adjust their behavioral policies. The improvement is typically measured as higher one-shot task performance, and the retained experience is typically stored as natural-language guidance: reflections, principles, or structured knowledge that helps the model reason better on future tasks.

GA makes a stronger and more specific claim about what self-evolution should produce: a **representation shift** from verbose trajectories to compact operational assets (SOPs, code, skills). The endpoint of evolution is not just better policy guidance but *lower inference-time cost*—the agent doesn't merely perform better; it performs the same task with dramatically fewer tokens and reasoning cycles because the learned procedure has been crystallized into an executable form that doesn't require re-interpretation.

This is a fundamental distinction with practical consequences. A textual SOP that says "use batch extraction for GitHub PRs, prefer the script over manual browsing, and watch out for issue-link patterns" still requires the model to read, interpret, and plan from scratch each time it encounters a similar task. A compiled Python script (`github_pr_analyzer.py`) that encapsulates the same procedure can be invoked with a single `code_run` call, eliminating the entire understand-reason-plan cycle. The efficiency gain is structural, not marginal: it removes whole categories of reasoning steps from the execution trace.

The evidence is clearest in the nine-round evolution trajectory (Table 8). Round #1 (initial run) consumes 222,203 total tokens with 32 LLM calls over 7 minutes 30 seconds. By Round #9 (codified SOP), this collapses to 23,010 tokens with 5 LLM calls over 1 minute 38 seconds—a **89.6% reduction in tokens** and an **84.4% reduction in LLM calls**. The paper explicitly notes that "the dominant change is the collapse in call count, which removes entire understand–reason–generate loops from the execution trace." Per-call token load also drops (from ~6,944 tok/call to ~4,600 tok/call), but this is secondary to the structural reduction in the *number of calls*.

The cross-task results (Figure 5) confirm that this is not a single-task phenomenon. Across all eight benchmark tasks, later GA executions consume fewer tokens than the first execution (savings ranging from 61.0% to 92.4%, overall reduction of 79.3%), and the system exhibits a "clear transition from cold start to rapid convergence" where the first run incurs an adaptation cost but subsequent runs quickly stabilize. OpenClaw shows no comparable convergence pattern, with token usage often increasing rather than decreasing across runs.

The innovation here is not that agents can improve through experience—that has been shown before. The innovation is the claim that the **form** of the retained experience determines the shape of the improvement curve: textual abstractions yield gradual efficiency gains as the model makes better decisions; executable code yields discontinuous efficiency gains as entire reasoning loops are eliminated. This reframes self-evolution from a policy-learning problem to a program-synthesis problem, with direct implications for what agent architectures should optimize.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper evaluates on five complementary benchmarks. For task completion and token efficiency, it uses SOP-Bench (Nandi et al., 2025; complex industrial SOPs), Lifelong AgentBench (Zheng et al., 2025; sequential tasks with cross-task dependencies), and RealFin-Benchmark (Dai et al., 2026; financial workflows). For web browsing, it uses WebCanvas (Pan et al., 2024; 12 randomly sampled fundamental browser interaction tasks), BrowseComp-ZH (Zhou et al., 2025; 10 randomly sampled multi-hop Chinese web search tasks), and a custom set of 22 real-world tasks spanning academic platforms, social media, e-commerce, and public retrieval services. For long-term fact retention, it uses the first subset of LoCoMo (Maharana et al., 2024), with Category 5 summary tasks removed to avoid interference from summarization ability.

- **Base model(s).** The primary backbone models are Claude Sonnet 4.6 and Claude Opus 4.6 (Anthropic), with additional experiments using MiniMax M2.7 and GPT-5.4 to cover different architectural paradigms and reasoning capacities. All compared systems (GA, Claude Code, OpenClaw, Codex) use the same backbone model within each experiment to isolate system architecture from model capability. The paper states GA is "model-agnostic: the underlying reasoning engine can be replaced without affecting execution logic, tool interfaces, or memory architecture."

- **Metrics.** Task completion is measured by Accuracy (success rate of task completion, reported as percentage). Operational cost is measured by Input Tokens, Output Tokens, and Total Tokens. The composite efficiency metric is Efficiency = Accuracy / Total Tokens (in millions), which captures the performance-per-token tradeoff. For web browsing, a normalized Score (0–1) is used, with scoring protocols tailored to each benchmark: automatic evaluation for WebCanvas, LLM-as-a-judge for BrowseComp-ZH, and human-in-the-loop review assisted by GPT-5.4 for Custom Tasks. For long-term fact retention (LoCoMo), F1 measures correctness and completeness of factual content, and BLEU-1 measures lexical similarity to reference answers. For the evolution trajectory (Table 8), Total Tokens additionally breaks down into Input, Output, Cache Create, and Cache Read sub-components to reveal where efficiency gains originate.

- **Baselines.** Four representative agent systems serve as baselines: Claude Code (Anthropic, 2025; an industry-leading proprietary agent), OpenClaw (Wang et al., 2026; a robust open-source multi-tool framework), Codex (OpenAI, 2025; a widely adopted execution baseline), and in some experiments, embedding-based memory systems Mem0 (Chhikara et al., 2025) and A-MEM (Xu et al., 2025). All baselines use the same backbone LLM as GA in each experiment to isolate system-level differences. For the web browsing evaluation, only OpenClaw is compared against GA, both using Claude Opus 4.6.

- **Generation budget / compute accounting.** The primary unit of comparison is token consumption (input, output, and total), not FLOPs or wall-clock iterations. This reflects the paper's core thesis that context occupancy is the binding constraint. For the tool-use efficiency experiments, additional execution metrics include Time (average runtime in seconds), Requests (average number of model API calls), and Tool Calls (average number of tool invocations), which together decompose token cost into its structural components. For the context explosion prevention experiment, Full Prompt Length (in tokens) is measured after issuing a minimal "Hello" request to assess baseline context occupancy. Table 1 specifies per-tool output truncation thresholds (e.g., `code_run` at 10,000 characters, `web_scan` HTML at 35,000 characters with DOM subtree pruning), and the character-budget heuristic uses `$\alpha \approx 3$` chars/token to approximate token limits.

- **Cross-validation / statistical protocol.** No formal cross-validation or statistical significance testing is reported. The paper notes that the test sets are small (SOP-Bench and Lifelong AgentBench results report single-run accuracy), the 500-question MATH benchmark check from the prior version is absent here—this is a different experimental suite entirely. For the memory ablation (Table 5), four memory configurations are compared on the SOP-Bench dangerous_goods subset, but no confidence intervals or multiple runs are reported. For the cross-task convergence experiment (Figure 5), three runs per task are shown, which provides weak evidence of convergence trends but lacks statistical rigor. The reflection-based weight adaptation in autonomous exploration (Section 3.3) explicitly "has not yet accumulated enough long-term data to definitively prove its effectiveness." The evaluation methodology overall prioritizes demonstrating the existence and magnitude of effects over establishing their statistical reliability, which is a limitation given the small per-task sample sizes.

### Main Quantitative Results

#### Task Completion and Token Efficiency (Section 4.1)

The headline result across the three main benchmarks is that GA achieves state-of-the-art or highly competitive accuracy while consuming substantially fewer input tokens than all baselines. On Lifelong AgentBench, GA with Claude Sonnet 4.6 achieves **100% accuracy** while consuming only **222k input tokens**, compared to Claude Code (75% accuracy, 800k input tokens) and OpenClaw (70% accuracy, 1.43M input tokens). The Efficiency ratio (accuracy per million total tokens) is **4.15 for GA versus 0.92 for Claude Code and 0.48 for OpenClaw** (Table 2). This means GA achieves roughly 4.5× the performance-per-token of the strongest baseline on this benchmark.

On SOP-Bench, GA achieves **100% accuracy** with 2.02M input tokens (Efficiency 0.48), while Claude Code achieves 85% accuracy with 1.23M input tokens (Efficiency 0.68) and OpenClaw achieves 100% accuracy with 2.60M input tokens (Efficiency 0.38). Here, Claude Code's higher efficiency ratio comes at the cost of 15 percentage points lower accuracy—a tradeoff the paper implicitly frames as unacceptable for deployment. When using MiniMax M2.7 as the backbone, GA achieves 90% accuracy with 893k input tokens (Efficiency 0.97), compared to OpenClaw's 95% accuracy with 2.91M input tokens (Efficiency 0.32).

On RealFin-Benchmark, GA achieves the **highest overall accuracy of 65%** with Claude Sonnet 4.6, consuming 102k input tokens (Efficiency 5.70). This exceeds Claude Code with Claude Opus 4.6 (60% accuracy, 290k input tokens, Efficiency 1.95), Claude Code with Claude Sonnet 4.6 (55% accuracy, 226k input tokens, Efficiency 2.31), Codex with GPT-5.4 (60% accuracy, 838k input tokens, Efficiency 0.67), and OpenClaw (35% accuracy, 249k input tokens, Efficiency 1.39). The paper specifically highlights that GA "consumes only 27.7% of Claude Code's input tokens and 15.5% of OpenClaw's" on Lifelong AgentBench while achieving higher accuracy.

#### Tool-Use Efficiency (Section 4.2)

The tool usage distribution analysis (Figure 3) reveals a concentration phenomenon even in tool-rich systems: Claude Code's top 4 tools (AgentTool, WebFetchTool, FileReadTool, FileWriteTool) account for approximately 92% of all tool calls, while the remaining 47 tools appear only in the long tail. OpenClaw shows a similar pattern with browser, web_fetch, exec, read, write, and process dominating. GA's usage is concentrated across `file_read` (34.4%), `code_run` (31.2%), `web_execute_js` (17.2%), and `web_scan` (10.9%), with the remaining tools accounting for small fractions. This supports the paper's claim that a minimal tool set can cover the high-frequency capabilities while eliminating the prompt overhead of rarely-used specialized tools.

On the long-horizon complex tasks (Table 4), GA matches Claude Code's **100% success rate** while achieving substantially lower cost across all operational metrics: Total Tokens of **188,829 (35.1% of Claude Code's 537,413)**, Requests of 11.0 (vs. 32.6 for Claude Code), and Tool Calls of 12.8 (vs. 22.6 for Claude Code). OpenClaw trails at 80% success with 633,101 total tokens. The time metric shows GA at 220.8 seconds versus Claude Code's 320.8 seconds—a meaningful but less dramatic difference than the token reduction, suggesting that latency is partly dominated by model inference time rather than tool orchestration overhead. The paper notes that GA's advantage "comes from lower context and tool-process overhead, not from sacrificing success rate."

#### Memory System Effectiveness (Section 4.3)

The memory ablation on SOP-Bench dangerous_goods (Table 5) demonstrates that **information density, not information volume, determines memory effectiveness**. The No-Memory configuration achieves only 13.87% task success rate, confirming that external procedural memory is necessary for the task. Full-Memory (injecting the complete, unedited SOP at 575 tokens) achieves 52.44%. Redundant-Memory (adding background descriptions and weakly relevant content, totaling 288 tokens) and Condensed Memory (165 tokens of action-guiding rules only) both achieve the **same highest TSR of 66.48%**. This is the key non-obvious result: adding more information (288 vs. 165 tokens) provides zero behavioral benefit, while the condensed version captures all the decision-critical content in less than one-third the space. The paper frames this as evidence that "filtered high-density memory is more effective than the original full SOP" and that background descriptions add "contextual burden without contributing additional behavioral value."

The long-term fact retention evaluation on LoCoMo (Table 6) is perhaps the most surprising result: **GA without any embedding model or vector database outperforms dedicated embedding-based retrieval systems**. On Multi-Hop tasks, GA achieves F1 of 43.33 and BLEU-1 of 39.96, compared to Mem0 (F1 39.32, BLEU 28.43) and A-MEM (F1 29.03, BLEU 20.48). This pattern holds across all four task categories: Temporal (F1 52.23 vs. 50.03 and 46.83), Open-Domain (F1 20.41 vs. 18.32 and 13.11), and Single-Hop (F1 45.69 vs. 40.32 and 44.68). The advantage is especially pronounced on Multi-Hop and Temporal tasks—precisely the categories that require reasoning across fact chains rather than simple retrieval. The non-embedding baseline OpenClaw performs substantially worse across all categories (F1 9.56–23.44), confirming that simple log storage without GA's selection and organization mechanisms is insufficient.

The context explosion prevention experiment (Table 7) shows that after installing 20 skills and intensive usage, GA's full prompt length on a minimal "Hello" request is **2,298 tokens**, compared to Claude Code (22,821), Codex (23,932), and OpenClaw (43,321). This represents a **roughly 10–19× reduction** in baseline context occupancy. The paper attributes this to hierarchical retrieval: "memory is not directly injected into the context but is retrieved only when the model actually needs it."

The continuous efficiency improvement experiment (Figure 4) tracks five repeated runs of downloading five HuggingFace datasets using GPT-5.4 as the backbone. GA's operation time decreases from 102 seconds in the first run to approximately 66 seconds in later runs, while token consumption drops from 200,439 to approximately 100,000. Claude Code, Codex, and OpenClaw remain largely stable across runs. The paper interprets this as evidence that GA "converts task experience into reusable L3 SOPs that reduce repeated understanding, unnecessary reasoning, and decision overhead in later runs."

#### Self-Evolution Capability (Section 4.4)

The nine-round evolution trajectory on the LangChain GitHub research task (Table 8) shows a **phase transition from high-entropy exploration to a stable low-cost execution regime**. Round #1 (initial run): 7m30s, 32 LLM calls, 222,203 total tokens. Rounds #2–#5 (SOP optimization): time drops to 2m29s–4m19s, calls to 7–12, total tokens to 35,536–66,341—a substantial reduction but with continued fluctuations as the SOP is refined against edge cases. Rounds #6–#9 (Codified SOP): the system enters a "narrow convergence band of roughly 23k±1k tokens," with time at 1m35s–2m24s, calls at 5–6, and total tokens at 22,689–25,762.

The paper emphasizes that "the dominant change is the collapse in call count, which removes entire understand–reason–generate loops from the execution trace." Cache-read tokens fall from 183,375 in Round #1 to ~19,000 in Rounds #7–#9, and input tokens fall from 15,581 to ~1,884—showing that "the agent no longer rebuilds large amounts of context at runtime." Per-call token load also decreases from ~6,944 tok/call in Round #1 to ~4,600 tok/call in Rounds #7–#9, but the paper correctly identifies this as secondary: the 84.4% reduction in call count (32 → 5) dominates the efficiency gain. The transition is autonomously triggered by GA's memory management mechanisms without manual intervention, which the paper presents as "a core architectural advantage."

The cross-task convergence experiment (Figure 5) tests whether these efficiency gains generalize across diverse task types. On all eight benchmark tasks, later GA executions consume fewer tokens than the first execution, with savings ranging from **61.0% to 92.4%** and an **overall reduction of 79.3%** across the task set. The strongest gains appear in long-horizon tasks with state transfer and recovery (Category D, ~92.0% reduction), where "repeated failure handling and path search dominate the initial execution cost." The paper notes a clear adaptation pattern: the first run incurs an SOP adaptation cost as generalized knowledge is mapped onto the concrete task instance, but this happens only once—subsequent runs converge to a stable low-cost regime. OpenClaw shows no comparable convergence; on task B2, for example, token usage fluctuates from 1,370k to 2,330k to 2,130k across three runs, indicating the system "keeps re-exploring rather than reusing prior experience."

A correlation between task complexity and savings rate emerges: tasks with OpenClaw average consumption above 1,000k tokens (A1, B2, D1) achieve an average saving of 83.5%, while mid-complexity tasks average 72.5%. The paper concludes that "SOP self-evolution becomes more valuable as tasks require more multi-step reasoning, navigation, and recovery from branching execution paths."

#### Web Browsing Capability (Section 4.5)

On WebCanvas (fundamental browser interactions), GA achieves a score of **0.834 using only 0.18M tokens**, while OpenClaw trails at 0.722 while consuming 0.71M tokens (Table 9). On BrowseComp-ZH (multi-hop Chinese web search), the performance gap widens dramatically: GA scores **0.600 with 0.47M tokens**, compared to OpenClaw's **0.200 with 1.31M tokens**—a 3× score advantage at roughly one-third the token cost. On Custom Tasks (22 real-world web workflows), GA scores 0.577 with 0.26M tokens versus OpenClaw's 0.500 with 0.76M tokens.

The paper attributes the BrowseComp-ZH advantage specifically to GA's multi-stage compression pipeline: "Without active memory filtering, baseline systems like OpenClaw are easily overwhelmed by raw HTML and irrelevant DOM elements, leading to state confusion and context overflow. Conversely, GA preserves context density by systematically compressing web observations, enabling the model to sustain deep, multi-hop logical reasoning without losing track of the initial objective." Across all web benchmarks, GA exhibits what the paper calls a "structural 2.9× to 3.9× reduction in token consumption" (Table 9, comparing Avg. Tokens columns: 0.71/0.18 ≈ 3.9× on WebCanvas, 1.31/0.47 ≈ 2.8× on BrowseComp-ZH, 0.76/0.26 ≈ 2.9× on Custom Tasks).

### Ablation Studies and Robustness Checks

- **Memory density vs. volume (Table 5):** Condensed Memory (165 tokens of action-guiding rules) achieves the same 66.48% task success rate as Redundant-Memory (288 tokens with background descriptions) and outperforms Full-Memory (52.44% with 575 tokens of complete SOP). The non-obvious finding is that adding explanatory context and definitions *does not help and can actively harm* performance—Full-Memory, despite containing more information, performs worse than both filtered variants. This directly supports the paper's claim that information density matters more than information volume.

- **Embedding-based vs. selection-based memory (Table 6):** GA without any embedding model or vector database outperforms Mem0 and A-MEM on all LoCoMo task categories. The strongest advantage appears on Multi-Hop (F1 43.33 vs. 39.32 and 29.03) and Temporal (F1 52.23 vs. 50.03 and 46.83) tasks—precisely where reasoning across facts matters most. The non-obvious implication is that **content quality (what you store) can dominate retrieval architecture (how you find it)** for agent memory.

- **Context explosion under skill accumulation (Table 7):** After installing 20 skills, GA's baseline prompt length (2,298 tokens) is 10–19× smaller than baselines (22,821–43,321 tokens). This isolates the effect of hierarchical retrieval from task-specific compression: even at idle, the always-on memory layer remains bounded.

- **Continuous efficiency improvement across runs (Figure 4):** GA's operation time and token consumption decrease substantially across repeated runs (102s → 66s, 200k → 100k tokens), while baseline agents remain stable. This ablation demonstrates that the improvement comes from experience consolidation, not from model warm-up or caching effects (since each run uses a fresh session).

- **Self-evolution stage transitions (Table 8):** The nine-round trajectory decomposes efficiency gains into two phases: SOP optimization (Rounds #2–#5, where token cost fluctuates 35k–66k as the procedure is refined) and codified execution (Rounds #6–#9, where cost stabilizes at ~23k±1k). This demonstrates that the discontinuous gain comes from the representation shift to executable code, not merely from procedure memorization. The cache-read token collapse (183k → 19k) provides direct evidence that the agent stops rebuilding context at runtime.

- **Cross-task generalization of self-evolution (Figure 5):** The 61–92% savings across eight diverse tasks with an overall 79.3% reduction confirms that self-evolution is not task-specific memorization. The adaptation cost pattern (first run expensive, subsequent runs cheap) is consistent across tasks, while OpenClaw shows no convergence.

- **Per-tool truncation thresholds (Table 1):** The paper specifies different output size limits for each tool (e.g., `code_run` at 10,000 chars, `web_scan` HTML at 35,000 chars with subtree pruning, `file_read` at ~1,280 per line with 20,000 total). These thresholds are presented as design choices rather than empirically optimized—no ablation across threshold values is reported, which is a gap given that these directly control the tradeoff between completeness and conciseness for tool outputs.

- **Compression turn interval (Stage 2, Section 2.3.4):** The paper reports that compressing every five turns and exempting the 10 most recent messages yields "prompt-cache hits in roughly 80% of turns." No ablation across different intervals (e.g., every 3 turns vs. every 7 turns) or exemption window sizes is reported, so the optimality of these specific parameters is unverified.

- **Character-budget heuristic sensitivity (Section 2.3.4):** The `$\alpha \approx 3$` approximation is acknowledged to be conservative for ASCII (actual ratio ~4 chars/token, causing mildly early eviction) and risky for CJK (actual ratio ~1–2 chars/token, risking delayed eviction). No experiments test sensitivity to `$\alpha$` values or character-budget thresholds, which is a significant gap for a system that claims CJK web browsing capability (BrowseComp-ZH).

- **Weight adaptation in autonomous exploration (Section 3.3):** The reflection-based weight adjustment is explicitly labeled "a preliminary design" that "has not yet accumulated enough long-term data to definitively prove its effectiveness." This is not an ablation but an acknowledgment of an untested mechanism.

- **ReST-EM revision model (Appendix K):** An attempt to further optimize the revision model using ReST-EM backfired, with "additional sequential revisions substantially hurt performance." This negative result is not elaborated in the main text and represents a known failure mode of the approach—the paper acknowledges that revision training is sensitive to data generation procedures.

### Critical Assessment

**Claim 1: "GA consistently achieves state-of-the-art or highly competitive task completion rates" while using "significantly fewer tokens and interactions."** The evidence supports this claim strongly for the specific benchmarks, baselines, and backbone models tested. On Lifelong AgentBench, GA achieves 100% accuracy compared to Claude Code's 75% while using 27.7% of the input tokens (Table 2). On RealFin-Benchmark, GA achieves the highest accuracy (65%) while consuming 35.1% of Claude Code's input tokens. On the long-horizon complex tasks (Table 4), GA matches Claude Code's 100% success at 35.1% of the token cost.

However, two important qualifications apply. First, on SOP-Bench, Claude Code achieves a higher efficiency ratio (0.68 vs. GA's 0.48) while GA achieves higher accuracy (100% vs. 85%), demonstrating that efficiency and accuracy don't always move together—the system designer must choose which to prioritize. The paper presents GA's choice (prioritize accuracy) as obviously correct, but a practitioner with a tight token budget might prefer Claude Code's tradeoff. Second, the results are from single-run evaluations on small test sets (e.g., 5 long-horizon complex tasks in Table 4, 12 sampled WebCanvas tasks). Without multiple runs or confidence intervals, it's impossible to assess whether GA's reported advantages are statistically reliable or could be reversed by sampling variation on different task subsets. The 100% accuracy on SOP-Bench and Lifelong AgentBench is a point estimate that would be more convincing with repeated measurements.

**Claim 2: "A minimal atomic-tool set can effectively handle complex workflows that typically rely on a large inventory of specialized tools."** The evidence partially supports this, but with a critical limitation: the evaluation tests composition against a *specific set of capabilities that GA's tools were designed to cover*. The paper provides a capability-level alignment (Appendix Table 10) showing that GA's tools have counterparts in Claude Code and OpenClaw for file operations, code execution, and web interaction—but does not test scenarios requiring capabilities absent from GA's tool set. The tool usage distribution analysis (Figure 3) shows that even in tool-rich systems, execution is dominated by a small subset of tools, supporting the claim that many specialized tools are rarely used. The concrete substitution examples (Appendix Table 11) demonstrate that specific Claude Code capabilities (GlobTool for file matching, GrepTool for text search, WebFetchTool for content fetching) can be reconstructed through GA compositions.

What's missing is a systematic evaluation of tasks that *cannot* be solved with GA's tool set—the failure boundary. If GA's 9 tools are genuinely sufficient for all tasks in the evaluation benchmarks, that may say more about the benchmarks' limited action-space requirements than about the universality of the tool set. A stress test with tasks requiring fine-grained GUI automation, database transactions, or multi-modal reasoning would reveal whether the compositional approach breaks down at capability boundaries that specialized tools do (or don't) cover. The paper acknowledges this implicitly by noting that `code_run` could theoretically replicate all other tools—but `code_run` requires the agent to write correct code, which is itself a failure-prone operation that the specialized tools are designed to avoid.

**Claim 3: "Precise memory organization enables GA to exceed the factual retention capabilities of dedicated vector-based retrieval systems."** This is the most surprising result and the one with the weakest evidential support relative to its strength. The LoCoMo results (Table 6) show GA outperforming Mem0 and A-MEM on all categories without using embeddings—but the paper provides no information about *how* facts are organized in GA's memory for this experiment. Did a human curate the L2 fact layer? Did GA autonomously consolidate facts from prior interactions? How many prior interactions were used to populate memory? Without this information, the comparison is not between "GA's autonomous memory organization" and "embedding-based retrieval"—it could be between a carefully hand-curated knowledge base and an automated system.

This is a critical reproducibility and fairness concern. If GA's L2 facts were extracted and verified by the researchers (or by GA under researcher supervision with ground-truth validation), the comparison is not demonstrating that GA's *mechanism* is superior—it's demonstrating that verified ground-truth facts produce better retrieval than embedding similarity over noisy logs, which is unsurprising. The paper needs to clarify the curation process for this experiment to support the claim.

**Claim 4: "Self-evolution reduces token usage by up to 89.6% across repeated runs."** The evidence for this is the strongest in the paper. The nine-round trajectory (Table 8) shows a clear, well-measured efficiency trajectory with decomposition into sub-components (input, output, cache-create, cache-read tokens; LLM call count; runtime). The cross-task convergence (Figure 5) demonstrates generalization across eight tasks. The comparison with OpenClaw (no convergence) isolates the effect from model-level factors.

However, the claim is about *repeated runs of similar tasks*, not about *novel task performance*. The 89.6% reduction applies when the agent encounters tasks structurally similar to ones it has solved before—the SOP is a compressed form of a specific workflow. This is a form of memorization-and-reuse, which is valuable but different from general capability improvement. The paper is careful to frame self-evolution as "experience consolidation" rather than learning, which is accurate, but the headline 89.6% number could be misinterpreted as a general efficiency improvement across all future tasks. It is not—it is the efficiency gain on repeated instances of the learned workflow.

**Claim 5: "GA's multi-stage compression pipeline provides an advantage in long-horizon, multi-hop web search tasks."** The BrowseComp-ZH result (GA 0.600 vs. OpenClaw 0.200 with 0.47M vs. 1.31M tokens) is the most dramatic head-to-head comparison in the paper and directly supports this claim. The WebCanvas and Custom Tasks results show consistent advantages at much lower token cost. The qualitative case study (Appendix Case A4) provides a concrete example of iterative query refinement under compressed browser observations.

The limitation is sample size and benchmark scope. BrowseComp-ZH uses 10 randomly sampled tasks—performance could vary substantially with different samples. The Custom Tasks set (22 tasks) is "curated" by the authors, which introduces potential selection bias (tasks chosen where GA's approach is known to work well). A standardized, larger-scale web agent benchmark (like WebArena or Mind2Web) would provide more convincing evidence of general web browsing capability, but the paper does not evaluate on these.

**Missing experiments that would strengthen the paper:**

- **Ablation of individual compression stages.** The paper describes four stages of context truncation and compression but never ablates them—we don't know whether Stage 2 (tag-level compression) or Stage 4 (working-memory anchor) contributes more to the token reduction, or whether some stages could be removed without loss. This matters for practitioners who might want to implement a subset of the pipeline.

- **Scaling with task length.** The evaluation tasks are of moderate length (tens of turns). How does GA's context management behave on tasks requiring hundreds of turns? Does the 30k-token budget remain sufficient, or does compression eventually degrade decision quality? The paper mentions a 30-round execution cap for autonomous exploration but doesn't evaluate behavior near this boundary.

- **Sensitivity to the 30k token budget.** The paper claims that "packing higher-density information into a smaller window outperforms feeding diluted content into a larger one" (Section 2.1.4), but never compares GA performance at different context budgets. If GA were given Claude Code's larger effective context, would it perform better or worse? The claim that smaller-is-better needs direct evidence.

- **Human evaluation of compression quality.** The paper compresses reasoning traces, tool outputs, and conversation history, but never evaluates whether the compressed representations preserve the information needed for correct decisions. The 100% accuracy on some benchmarks suggests they do, but a targeted evaluation (e.g., having human raters judge whether compressed context contains all necessary information) would strengthen confidence that conciseness is not achieved at the cost of completeness.

- **Cross-model robustness.** Most experiments use Claude Sonnet 4.6. The MiniMax M2.7 results (Table 2) are incomplete (only two benchmarks, no baselines beyond OpenClaw). Does GA's architecture benefit all backbone models equally, or do some models handle compressed context worse than others? The naturalness constraint (Section 2.1) suggests that overly compressed or telegraphic representations might be harder for some models to interpret, but this is never tested.

- **Difficulty-stratified analysis.** Unlike the reference example paper (which stratified results by problem difficulty quintiles), this paper reports aggregate performance without analyzing whether GA's advantages are uniform across easy and hard tasks. On Lifelong AgentBench, do the token savings come primarily from simple tasks while complex tasks still require substantial context? The cross-task results (Figure 5) hint at this (savings are larger for complex tasks), but no systematic difficulty analysis is presented.

## 6. Limitations and Trade-offs

### Difficulty Estimation Cost Is Not Accounted For in the Headline Efficiency Gains

**The assumption or constraint.** The entire compute-optimal framework depends on estimating prompt difficulty *before* allocating the test-time compute budget. The paper's method for doing so—generating 2048 samples per question and averaging PRM final-answer scores—is extraordinarily expensive. The authors acknowledge this explicitly in Section 3.2:

> "estimating difficulty in this way still incurs additional computation cost during inference... our experiments do not account for this cost largely for simplicity"

**The consequence.** The reported 4× efficiency gains over best-of-N (Figures 4 and 8) are computed *after* difficulty is already known, without amortizing the cost of learning it. In a realistic deployment, the total cost would be difficulty estimation + strategy execution, and the former could dominate the latter—generating 2048 samples per question is comparable to or greater than the largest test-time compute budgets studied (256–512 generations). The 4× figure should therefore be understood as an **upper bound on achievable efficiency** rather than a realized deployment gain. Until a cheap difficulty estimator is developed and validated, the compute-optimal policy is not deployable in its current form for real-time applications—it requires an offline pre-processing step that costs more than the optimization it enables.

**What evidence exists in the paper.** This limitation is not measured or quantified anywhere. Figures 4 and 8 show compute-optimal scaling curves that start from the first generation of the *strategy execution* budget, with no accounting for the 2048 samples used to place each question in its difficulty bin. The paper does not report total tokens including difficulty estimation, nor does it provide an ablation showing how performance degrades if difficulty is estimated from fewer samples (e.g., 8, 32, 128). The only evidence that the limitation matters is the authors' own acknowledgment in Section 3.2 and the explicit call for future work on "pretraining or finetuning models to directly predict difficulty of a question" (Section 8).

**Mitigation status.** The paper attempts to mitigate this by showing that *predicted* difficulty bins (using PRM scores without ground-truth labels) perform nearly as well as *oracle* bins (Figures 4 and 8, curves largely overlap). However, the predicted bins still require generating the same 2048 samples per question—they just replace the ground-truth correctness check with a PRM score check, which does nothing to reduce the sampling cost. The paper acknowledges this gap and flags it as the key open problem for practical deployment, but provides no solution or even a partial ablation of cheaper estimation methods. This is arguably the single largest barrier between the paper's results and real-world applicability.

---

### Hard Problems Remain Fundamentally Unsolved by Test-Time Compute

**The assumption or constraint.** The compute-optimal framework assumes that the base model's pass@1 rate on a problem is above some non-trivial threshold—that the model *occasionally* produces correct solutions, even if rarely. When this assumption fails, the paper's approach provides essentially zero benefit. The authors characterize this boundary candidly. For search against the PRM, Section 5.3 reports that on the hardest questions (difficulty bin 5), performance hovers at 1–3% regardless of method or budget:

> "On the hardest questions (bin 5), no method makes meaningful progress—the base model simply lacks the capability to produce correct solutions regardless of how the budget is allocated."

For revisions, Section 6 reports the same: "bin 5: all ratios produce roughly 2–3% accuracy. No allocation strategy helps."

**The consequence.** Test-time compute amplifies existing capability but does not create it. If the base model's pass@1 is near zero on a problem class, no amount of search, revision, or adaptive allocation will help—there are no correct solutions in the proposal distribution to find or refine. This establishes a hard boundary on the applicability of compute-optimal test-time scaling: it works for problems within the model's *rough* capability range (where the model can produce correct answers at some non-trivial rate, even if rarely) but offers **no path forward for genuinely novel or out-of-distribution reasoning** that exceeds the base model's training distribution. For such problems, pretraining a larger or better-trained model remains the only viable path.

This has direct deployment implications. A system that deploys compute-optimal test-time scaling must also include a mechanism for *detecting* when a problem falls into this unsolvable regime and either escalating to a larger model or flagging for human review, rather than wasting compute on strategies that cannot succeed. The paper's difficulty estimation mechanism could serve this routing function, but this use case is not evaluated.

**What evidence exists in the paper.** The evidence is consistent and unambiguous. Figure 3 (right) shows bin 5 accuracy at 1–3% for best-of-N and beam search across all budgets from 4 to 256 generations. Figure 7 (right) shows bin 5 revision accuracy at roughly 2–3% regardless of sequential-to-parallel ratio at 128 generations. The FLOPs-matched comparison (Figure 9) shows the bin 5 scaling line as essentially flat near 0–5%, well below the ~14× larger model's performance. The nine-round evolution trajectory (Table 8) shows convergence to a stable low-cost regime only for tasks the model can already solve—there is no evidence that self-evolution enables solving previously unsolvable tasks.

**Mitigation status.** The paper does not attempt to solve this limitation—it documents it as a boundary condition. The authors are transparent about this in Section 7's takeaway: test-time compute cannot substitute for pretraining on hard problems. The implication for practitioners is clear: compute-optimal test-time scaling is a complement to, not a replacement for, pretraining scaling. Systems that need to handle hard out-of-distribution problems must invest in model capability, not just inference strategy. However, the paper does not provide guidance on how to determine *a priori* whether a given task distribution falls into the solvable or unsolvable regime, which is what a practitioner would need to decide between investing in test-time infrastructure versus larger model training.

### The Proposed Difficulty Estimation Method Is Far Too Expensive for Deployment

**The assumption or constraint.** The paper's compute-optimal policy requires placing each test question into one of five difficulty bins before selecting a strategy. Both the oracle method (computing pass@1 over 2048 samples) and the predicted method (averaging PRM scores over 2048 samples) require generating and scoring 2048 complete solutions per question. The paper acknowledges this cost (Section 3.2):

> "the computational cost of generating 2048 samples and scoring them... [is] a key avenue for future work."

**The consequence.** For a 500-question test set, difficulty estimation requires 500 × 2048 = **1,024,000 generations**—orders of magnitude more than the largest per-question test-time budget studied (512 generations). In any deployment setting, this cost is prohibitive. The paper's headline result—that compute-optimal scaling achieves 4× better efficiency than best-of-N—is therefore a statement about the *shape of the achievable efficiency frontier* rather than a demonstration of a deployable system. A practitioner reading this paper would correctly conclude that adaptive allocation is a promising direction, but would not have a practical method for implementing it at reasonable cost.

This limitation is particularly acute because difficulty estimation must be performed *for each new question*, not amortized across many queries to the same question. In a production setting where users submit novel questions continuously, the difficulty estimation cost would be incurred per query, making the total cost completely dominated by the estimation step rather than the optimization step.

**What evidence exists in the paper.** The paper provides no experiments measuring or ablatting the difficulty estimation cost. Figures 4 and 8 show compute-optimal performance as a function of the *strategy execution* budget only. There is no data on how performance degrades if difficulty is estimated from fewer samples (e.g., 8, 32, 64, 128). The predicted-vs-oracle comparison (curves largely overlap in Figures 4 and 8) demonstrates that the PRM score proxy works, but does nothing to reduce the sampling cost—it only eliminates the need for ground-truth answer labels. The paper does not report total FLOPs or wall-clock time including difficulty estimation for any experiment.

**Mitigation status.** The paper acknowledges this limitation explicitly and flags it as the central open problem for practical deployment (Sections 3.2 and 8). The suggested future work—training a lightweight classifier to predict difficulty from question text alone, or integrating difficulty estimation into the problem-solving process itself—is sensible but entirely unimplemented. No prototype of a cheap difficulty estimator is described or evaluated. Until such an estimator is developed and shown to preserve the efficiency gains while operating at a fraction of the 2048-sample cost, the compute-optimal framework remains a proof of concept rather than a deployable system.

### The $14\times$ Larger Model Baseline Is Underpowered, Weakening the Training-Inference Tradeoff Claims

**The assumption or constraint.** The FLOPs-matched comparison in Section 7 compares PaLM 2-S* with compute-optimal test-time scaling against a model with approximately 14× more parameters using **greedy decoding only**—no majority voting, no best-of-N, no search, no test-time compute augmentation of any kind. Additionally, the larger model scales parameters while holding training data fixed (following the LLaMA paradigm; Touvron et al., 2023), which departs from compute-optimal pretraining where both data and parameters are scaled equally (Hoffmann et al., 2022). The authors acknowledge this:

> "We choose this setting as it is representative of a canonical approach to scaling pretraining compute and leave the analysis of compute-optimal scaling of pretraining compute where the data and parameters are both scaled equally to future work."

**The consequence.** The reported advantages of test-time compute over pretraining—such as +27.8% relative improvement on easy questions at R ≪ 1 for revisions (Figure 1, top-right bar chart) and +19.1% for PRM search—are measured against a baseline that is weaker than it could be in two ways. First, a Chinchilla-optimal model trained with the same total FLOPs (scaling both parameters and data) would likely outperform the parameter-only-scaled model, making the pretraining baseline stronger. Second, giving the larger model even a modest test-time compute budget (say, best-of-8 with majority voting) would create a much more realistic comparison, since any deployed large model would presumably also use some form of test-time compute. The current comparison answers the question: "Is a small model with optimized test-time compute better than a large model with *no* test-time compute?" The more relevant question—"How should I split my total FLOPs budget between pretraining and inference?"—is only partially answered, because the larger model's inference budget is artificially constrained to greedy decoding.

Additionally, the paper scales only parameters, not total pretraining FLOPs, so the 14× factor refers to parameter count, not necessarily to total pretraining compute. This makes the FLOPs accounting (Equations in Section 7) approximate rather than exact—the 14× larger model and the smaller model may not have received the same ratio of pretraining FLOPs as their parameter ratio suggests, depending on training token counts.

**What evidence exists in the paper.** The Section 7 results (Figure 9, Figure 1 bar charts) show the comparison as described. The paper does not include any experiments where the larger model is given non-trivial test-time compute (e.g., best-of-4, best-of-16, or even majority voting over a few samples). The Chinchilla-optimal pretraining baseline is explicitly deferred to future work and is not evaluated. The paper does not report the actual training token counts for either model, making it impossible for a reader to independently verify the FLOPs accounting.

**Mitigation status.** The paper is transparent about these baseline choices and frames them as scope limitations rather than oversights. However, the headline claim that "a smaller model augmented with compute-optimal test-time strategies can outperform a ~14× larger pretrained model" (paraphrased from Section 7 and the Executive Summary) should be qualified: it holds against a *specific, relatively weak large-model baseline* (greedy decoding, parameter-only scaling). The paper does not provide evidence that the conclusion would hold against a compute-optimally trained larger model with any test-time compute budget. A practitioner deciding between training a larger model and investing in test-time infrastructure for a smaller model cannot safely rely on the reported magnitudes without additional experiments that close this baseline gap.

### The Single-Benchmark, Single-Model-Family Evaluation Provides No Evidence of Cross-Domain or Cross-Model Generalization

**The assumption or constraint.** All experiments in the paper use the MATH benchmark (Hendrycks et al., 2021) with PaLM 2-S* (Codey) as the base model. The authors state they "believe this model is representative of the capabilities of many contemporary LLMs" (Section 4), but this is an assertion rather than a finding. The evaluation covers only one task domain (competition-level mathematical reasoning) and one model family.

**The consequence.** Several aspects of the findings could be model- or domain-specific in ways that affect the paper's core claims:

- **PRM quality and over-optimization behavior** depend on PaLM 2-S*'s output distribution. A model with different calibration properties, different error patterns, or different reasoning styles might exhibit different difficulty-dependent scaling curves. The finding that beam search over-optimizes on easy problems (Figure 3, right) might not generalize to models whose outputs are easier or harder for the PRM to score accurately.

- **The revision model's ability to learn from incorrect in-context examples** depends on the base model's in-context learning capabilities, which vary substantially across model families (some models are much better at few-shot learning from examples than others). The revision model training procedure (Section 6.1) may not transfer to models with weaker in-context learning.

- **The MATH benchmark** consists exclusively of problems with clear ground-truth answers that can be verified with exact string matching. This enables both the PRM training pipeline (Monte Carlo rollouts to determine correctness) and the difficulty estimation (pass@1 computation). Many important real-world applications—open-ended generation, dialogue, creative writing, multi-step planning in ambiguous environments—lack clean correctness signals. Extending the compute-optimal framework to tasks where correctness is ambiguous, multi-dimensional, or subjective would require fundamentally different verifier training and difficulty estimation approaches.

- **The test set size** (500 questions, split into 5 difficulty quintiles of ~100 each, further split by two-fold cross-validation into ~50 per fold per bin) is small. The compute-optimal policy is selected based on roughly 50 questions per bin, and no confidence intervals are reported on the compute-optimal scaling curves. The observed efficiency gains could be sensitive to the specific test set split.

**What evidence exists in the paper.** No experiments use alternative models or alternative benchmarks. The paper does not include any out-of-domain evaluation (e.g., on code generation, commonsense reasoning, or factual QA). The cross-validation protocol (two-fold on the MATH test set) provides some protection against overfitting the strategy to the test set, but only within the MATH distribution—it provides no evidence of generalization to other task types.

**Mitigation status.** The paper acknowledges the single-benchmark limitation implicitly by not claiming broader generalization, but does not discuss it as an explicit limitation or suggest specific domains for future evaluation. A practitioner considering deploying compute-optimal test-time scaling on, say, a code generation task or a customer support agent would need to replicate the full experimental pipeline (PRM training, difficulty estimation, strategy selection via cross-validation) on their domain and model of choice before having confidence that the 4× efficiency gains transfer. The paper provides a methodology but no evidence that the methodology's conclusions are robust to domain shift.

### The Revision Model Suffers from a 38% Correct-to-Incorrect Reversion Rate, and Revision Training Is Fragile

**The assumption or constraint.** The revision model is trained only on sequences where all in-context answers are incorrect followed by a correct target (Section 6.1). At test time, the model may encounter correct answers in its context—produced during earlier revision steps—and, having never been trained on what to do when the current answer is already correct, may incorrectly "revise" them into wrong answers. The paper reports:

> "approximately 38% of correct answers get converted back to incorrect ones using a naive approach."

Additionally, the ReST$^{\text{EM}}$ experiment (Appendix K, Figure 16) shows that attempting to further optimize the revision model with RL-style training caused performance to "substantially hurt," with the authors hypothesizing that on-policy data collection "exacerbates spurious correlations in revision data."

**The consequence.** The 38% reversion rate means that longer revision chains are not unambiguously beneficial—they increase the chance that a previously found correct answer gets corrupted by a subsequent revision step. The paper's mitigation (majority voting or verifier-based selection across the entire chain, described in Section 6.1) is a post-hoc patch that does not address the root cause: the model's training data provides no signal for when to *stop* revising because the current answer is already correct. This means the revision model cannot self-regulate its own revision depth—it will keep generating revisions regardless of answer quality, and the system must rely on an external selection mechanism to pick the best answer from the chain.

The fragility demonstrated by the ReST$^{\text{EM}}$ failure suggests that the revision training procedure is sensitive to data generation choices (offline vs. on-policy, edit-distance-based pairing vs. natural trajectory pairing) in ways that are not fully understood. A practitioner attempting to replicate the revision model on a different base model or task domain could easily encounter similar degradation if the training data construction is not carefully tuned.

**What evidence exists in the paper.** The 38% figure is reported in Section 6.1 without a dedicated experiment or table—it is mentioned as a motivating observation for the within-chain selection mechanism. The ReST$^{\text{EM}}$ failure is reported in Appendix K (Figure 16) with a brief hypothesis but no systematic diagnosis. No ablation studies investigate whether the reversion rate varies with revision depth, task difficulty, or model confidence. The paper does not measure how often the within-chain selection mechanism (majority voting or verifier) successfully recovers the correct answer that was later corrupted.

**Mitigation status.** The paper mitigates the reversion problem with within-chain selection (majority voting or verifier-based selection across all revision steps) rather than always taking the final revision. This reduces the impact of reversions but does not eliminate the underlying model behavior—the system still wastes computation generating revisions that corrupt previous correct answers, and the selection mechanism introduces its own failure modes (a wrong answer that appears multiple times could win a majority vote over a single correct answer). The authors acknowledge that a more principled solution—such as training the model to explicitly recognize when no revision is needed—is not explored. The ReST$^{\text{EM}}$ failure is presented without a clear resolution, leaving the robustness of the revision training procedure as an open question for future work.

### No Evaluation of Latency or Wall-Clock Time Tradeoffs

**The assumption or constraint.** The paper measures compute in "generations" (number of complete solutions sampled), which serves as a proxy for total FLOPs. However, the sequential nature of revision chains and the serial dependencies in beam search mean that different strategies with the same generation budget can have **dramatically different wall-clock times**. Sequential revisions are inherently serial—each revision depends on the previous one—while parallel best-of-N can be executed simultaneously given sufficient hardware. The paper does not discuss this tradeoff, report wall-clock time for any experiment, or account for latency in the compute-optimal allocation.

**The consequence.** A strategy that allocates 128 generations as 64 sequential revisions × 2 parallel chains takes roughly 64× longer wall-clock time than one that runs 128 parallel samples simultaneously, even though both consume the same number of generations. For latency-sensitive applications—interactive assistants, real-time decision-making systems, user-facing chatbots—the sequential-heavy strategies favored by the compute-optimal policy on easy problems (Section 6, Figure 7 right, bin 1–2 where fully sequential dominates) may be **impractical regardless of their accuracy advantages**. The user experience of waiting for 64 sequential LLM calls (each incurring model inference latency) would be unacceptable in any interactive setting.

This also affects the FLOPs-matched comparison (Section 7): if the larger model with greedy decoding completes in, say, 2 seconds while the smaller model with compute-optimal test-time scaling takes 120 seconds, the FLOPs efficiency advantage may not translate to a user-facing advantage. The paper's efficiency metric (accuracy per million tokens) captures cost but not responsiveness, which is a critical dimension for many deployment scenarios.

**What evidence exists in the paper.** The paper reports zero wall-clock time measurements. The nine-round evolution trajectory (Table 8) reports time in minutes and seconds (e.g., 7m30s for Round #1, 1m38s for Round #9), but this is presented as a secondary metric alongside token count without analysis of the latency implications. The computation model (generations as the unit of cost) is entirely throughput-oriented and ignores the parallelism constraints of real hardware. The paper does not discuss whether batching, pipelining, or speculative execution could mitigate the latency penalty of sequential strategies.

**Mitigation status.** Not addressed. The paper provides no guidance for practitioners on how to trade off accuracy gains against latency penalties, and the compute-optimal policy does not include latency as an optimization dimension. A latency-aware version of the framework would need to incorporate a parallelism model (how many generations can be executed simultaneously given hardware constraints) and a latency budget per query, which would shift the optimal allocation away from purely sequential strategies and toward more parallel, lower-latency alternatives. This is acknowledged indirectly in Section 8 under future work on "dynamic allocation policies," but no concrete direction is proposed.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

GenericAgent introduces a **diagnostic reframing** rather than a paradigm shift: it doesn't invent new capabilities so much as reveal that existing capabilities have been systematically deployed under a faulty assumption—that longer context yields better agent performance. The paper's contribution is to identify **context information density** as the binding constraint and to demonstrate that co-designing all system components around this single objective produces order-of-magnitude efficiency improvements without sacrificing capability.

The magnitude of the shift is best understood by what it renders obsolete. The dominant design pattern in agent frameworks—add more tools to expand capability surface, store more interaction history to improve memory, use longer context windows to handle longer tasks—is shown to be not merely suboptimal but **actively counterproductive** in specific, measurable ways. Claude Code's 53 tools produce a long tail where 47 tools account for ~8% of calls while occupying persistent prompt overhead (Figure 3). OpenClaw's flat memory produces context explosion to 43,321 tokens at idle after skill accumulation (Table 7). Both systems fail to converge in efficiency across repeated runs while GA reduces token usage by 79.3% across diverse tasks (Figure 5).

This reframing resolves a tension that has been implicit in the agent literature: why do some systems show strong performance on benchmarks while others with seemingly more sophisticated architectures fall short? The answer, per this paper, is not about model capability or algorithmic sophistication—it's about **whether the system architecture preserves or destroys context information density**. A simple architecture that keeps the active context sparse and decision-relevant can outperform a complex one that floods the model with scaffolding, stale observations, and marginally relevant memory.

The paper also shifts the conversation around **self-evolution** from a policy-learning problem to a **program-synthesis problem**. Prior work (Reflexion, Agent-Pro, Voyager) treats self-improvement as generating better natural-language guidance for future reasoning. GA demonstrates that the discontinuous efficiency gain comes from a **representation shift**—converting procedures from text that must be interpreted into code that can be executed—which reduces not just per-step token cost but the number of reasoning steps altogether (Table 8: 32 LLM calls → 5 calls). This suggests that the most impactful self-evolution research should focus on **compilation and representation** rather than on reflection quality alone.

Research directions that become **more attractive** as a result of this work:

- **Context engineering as a systems discipline.** The paper provides both a conceptual framework (completeness–conciseness tension) and a measurable target (information density) that can guide systematic context design. Prior work on prompt compression (LongLLMLingua) and context management (MemGPT) addressed pieces of this problem, but GA demonstrates that compression at one layer (e.g., conversation history) is most effective when combined with prevention at other layers (e.g., not injecting unnecessary tools or raw DOM into context in the first place).

- **Selection-centric memory over retrieval-centric memory.** The finding that GA without embeddings outperforms dedicated vector-based retrieval systems (Mem0, A-MEM) on LoCoMo (Table 6) suggests that **content quality** at write time can dominate **retrieval architecture** at read time. This opens research into write-time verification, consolidation triggers, and "No Execution, No Memory"-style filtering as alternatives to improving retrieval ranking.

- **Minimal tool sets validated by compositional stress-testing.** The paper provides a methodology for determining whether a tool set is complete: identify tasks requiring specific capabilities and demonstrate that they can be reconstructed through composition of atomic primitives (Appendix Table 11). This creates a template for principled tool-set design rather than ad hoc enumeration.

Research directions that become **less attractive**:

- **Simply increasing the nominal context window** as a solution for long-horizon agents. The paper argues, with empirical grounding from Liu et al. (2023) and An et al. (2024), that positional bias and effective context contraction make larger windows a partial and potentially counterproductive solution—"packing higher-density information into a smaller window outperforms feeding diluted content into a larger one" (Section 2.1.4).

- **Adding specialized tools** as the primary mechanism for expanding agent capability. The paper demonstrates that compositional generalization from a small set of primitives can match specialized-tool performance at lower cost (Table 4), and that the long tail of rarely-used tools in existing systems contributes context overhead without proportional execution benefit (Figure 3).

- **Storing raw interaction logs** as the default memory strategy. The memory ablation (Table 5) shows that adding background descriptions and weakly relevant information provides zero behavioral benefit over condensed action-guiding rules, while Full-Memory (the full SOP) actually performs *worse* than both filtered variants.

### Follow-Up Research This Work Enables

**Cheap difficulty estimation via lightweight classifiers or adaptive sampling.** The paper's compute-optimal framework is blocked for deployment by the cost of difficulty estimation (2048 samples per question). A direct follow-up would train a lightweight classifier—potentially a small fine-tuned model or even a logistic regression over question-text features—to predict which difficulty bin a question falls into, using the paper's existing 2048-sample difficulty labels as training data. The key metric is whether a classifier that requires zero or few samples per question can achieve bin assignment accuracy comparable to the PRM-based predicted bins (which the paper shows track oracle bins closely in Figures 4 and 8). A strong result would show that the efficiency curve with cheaply estimated bins is within 5% of the oracle-bin curve, making compute-optimal scaling deployable. Alternatively, an **adaptive estimation** approach could interleave difficulty assessment with strategy execution: start with, say, 8 parallel samples, use the verifier's score distribution on those samples as a quick difficulty signal, and then allocate the remaining budget based on the estimated bin. The experiment would measure total cost (estimation + execution) and compare against the paper's existing oracle and predicted-bin curves that exclude estimation cost. This would answer whether the 4× efficiency gain survives when estimation is amortized into the execution budget.

**Co-training the PRM and revision model to eliminate distribution shift.** The paper notes that the base-model PRM underperforms when scoring revision-model outputs due to distribution shift (Appendix J, Figure 15a), and that the revision model suffers from a 38% correct-to-incorrect reversion rate (Section 6.1). A natural extension is to train the PRM and revision model jointly or iteratively: after training an initial revision model on base-model trajectories, use the revision model to generate new training data for the PRM (so the PRM sees revision-model outputs), then use the updated PRM to score revision chains and filter out reversions during training. The experiment would compare three conditions: (1) independent training (as in the current paper), (2) sequential training (PRM first, then revision model trained with PRM-filtered trajectories), and (3) iterative co-training (multiple rounds of alternating updates). The key metric is the reversion rate at different chain depths—does co-training reduce the 38% figure, and does it enable longer revision chains to be net-beneficial rather than hitting diminishing returns?

**Ablation of individual compression stages to identify the marginal contribution of each.** The paper describes a four-stage context truncation and compression pipeline (tool-output truncation, tag-level compression, FIFO message eviction, working-memory anchor prompt) but never measures the contribution of each stage. A targeted ablation would run GA on the Lifelong AgentBench and long-horizon complex tasks while selectively disabling each stage: no Stage 1 truncation (full tool outputs in context), no Stage 2 compression (no placeholder replacement or windowed truncation), no Stage 3 eviction (context allowed to grow until API limit), and no Stage 4 anchor (working memory only in original messages). For each ablation, measure accuracy and total token consumption to determine which stages are essential, which provide marginal benefit, and whether any stages can be removed without impacting performance. This matters for practitioners who might want to implement only a subset of the pipeline—the paper currently provides no guidance on which components are load-bearing. A strong negative result (e.g., accuracy degrades substantially without Stage 4, suggesting the anchor is essential) would also validate the paper's design argument that working-memory preservation across evictions is critical.

**Cross-model stress-test of compression robustness.** The paper operates under a "naturalness" constraint (Section 2.1)—highly compressed or telegraphic representations might be harder for some models to parse. A cross-model experiment would run GA's full pipeline (with all four compression stages active) on the same benchmarks using a diverse set of backbone models: a strong proprietary model (Claude 4.6), a smaller open model (Llama-3-70B or Qwen-2.5-72B), and a model known to have weaker in-context learning (an older or smaller architecture). The hypothesis is that weaker models might suffer more from aggressive compression—the Stage 2 windowed truncation of reasoning traces and Stage 3 eviction of older messages could degrade their ability to maintain coherent multi-step plans. The experiment would measure whether GA's efficiency advantage over baselines shrinks or disappears with weaker backbone models, and whether the optimal compression aggressiveness (turn intervals, exemption window sizes, character budgets) is model-dependent. This would establish whether information density maximization is a universal principle or one that depends on the underlying model's ability to handle compressed representations.

**SOP verification through adversarial task mutation.** The paper shows that SOP self-evolution produces dramatic efficiency gains on repeated tasks (Table 8, Figure 5), but never tests whether the learned SOPs are *robust* or merely *memorized*—do they break under small variations in the task that a human would recognize as irrelevant? A stress-test would take the codified SOPs from the nine-round evolution trajectory (e.g., the `github_pr_analyzer.py` script from Case A3) and apply systematic mutations: change the repository name, alter the PR filtering criteria, switch the documentation URL to a different project with a different site structure, add an extra output field to the JSON schema. For each mutation, measure whether GA can (1) detect that the SOP needs adaptation, (2) adapt it successfully (with how many additional tokens), and (3) whether the adaptation cost is lower than solving from scratch. The comparison is against a fresh GA instance with no SOP memory—does having the SOP provide a better starting point even for mutated tasks, or does it create a "competency trap" where the agent over-trusts an inapplicable procedure? This would establish the generalization boundary of self-evolved knowledge and whether the paper's efficiency gains come from genuine procedural abstraction or from instance-specific memorization.

**Long-horizon stress test: 200+ turn execution with periodic task switching.** The paper's evaluation tasks are of moderate length (tens of turns). The claim that context information density is maintained "throughout long-horizon execution" (Section 2.3.4) needs validation at scales where compression and eviction are repeatedly triggered. An experiment would construct a multi-hour agent session requiring 200+ turns with deliberate task switching: the agent starts a data analysis task, is interrupted by a system monitoring alert (Reflect Mode), handles that, returns to the analysis, encounters a web browsing subtask, and must maintain state across all three. Measure: (1) task completion accuracy on all three tasks compared to a fresh-session baseline, (2) token consumption per turn over the full trajectory (does it stabilize at the 30k budget or drift upward?), (3) whether the Stage 4 anchor prompt preserves task-critical state for the interrupted analysis task across the monitoring and browsing interruptions. The hypothesis from the paper is that the anchor prompt and hierarchical memory should enable recovery without context explosion—but this has never been tested at the scale and complexity where it matters most.

### Practical Applications and Downstream Use Cases

**On-device or resource-constrained agent deployment.** The context explosion prevention result (Table 7) shows that GA's baseline prompt length after installing 20 skills is 2,298 tokens—an order of magnitude smaller than Claude Code (22,821) or OpenClaw (43,321). This makes GA viable for deployment on hardware or API tiers with strict context limits, such as edge devices running quantized models with 8k–32k token windows, or cost-sensitive applications using pay-per-token APIs where baseline overhead directly translates to per-query cost. A deployment where each query's baseline prompt consumes 2k tokens versus 25k tokens saves roughly 23k tokens per query—on a system handling 10,000 queries per day at typical API pricing, this translates to meaningful daily cost reduction before any task-specific tokens are counted. The hierarchical memory design ensures this low baseline is maintained even as the agent accumulates skills over months of operation.

**Continuous operation agents for system administration and monitoring.** GA's Reflect Mode (Section 3.2) combined with the context truncation pipeline enables a deployment pattern where an agent runs continuously in the background—monitoring log files, performing health checks, responding to alerts—without context accumulation eventually degrading its ability to respond to new events. The working-memory anchor prompt (Stage 4) preserves task-critical state across message evictions, meaning the agent can maintain awareness of ongoing issues (e.g., "the database replication lag has been increasing for the past hour") even as older turn-level details are evicted. The continuous efficiency improvement results (Figure 4) suggest that such a deployment would become more efficient over time as common incident response procedures are consolidated into SOPs—the agent wouldn't rediscover the troubleshooting steps for a recurring disk-space alert on each occurrence. This is a concrete path toward "AIOps" agents that don't degrade with uptime.

**Batch data processing and research automation workflows.** The map-reduce pattern enabled by Subagent Dispatch (Section 3.2)—spawning one GA CLI process per independent input and merging results—directly supports batch workflows common in research and data engineering: processing hundreds of papers for a literature review, analyzing a directory of log files, or validating a dataset against schema constraints. The cross-task efficiency convergence (Figure 5, 79.3% overall token reduction across tasks) means that as the agent repeatedly performs similar batch operations (e.g., weekly dataset validation), the per-item cost drops substantially. A research lab running weekly literature scans across 500 papers could expect the first run to be expensive (establishing the SOP) and subsequent runs to converge to roughly 20% of the initial token cost—turning a batch operation that was marginally cost-effective into one that is routinely affordable.

**Self-improving coding assistants with persistent project memory.** The self-evolution trajectory (Table 8) demonstrates that GA can convert a 7-minute, 32-call exploratory research task into a 1.5-minute, 5-call scripted operation—an 89.6% token reduction. This pattern directly applies to coding assistants that work within a persistent project: the first time the assistant debugs a project-specific build failure, it may take extensive exploration (reading configuration files, checking dependency versions, examining error logs). If that experience is consolidated into an SOP and reusable diagnostic script, the next occurrence of a similar build failure can be resolved with a fraction of the tokens and time. The L2/L3 memory architecture ensures these project-specific procedures are retained across sessions, so the assistant improves with use rather than starting from scratch each day—addressing the "stagnation loop" problem (Section 1) that the paper identifies as endemic to stateless agent designs.

### When to Prefer This Method

The paper explicitly positions GA's architecture against two named alternatives: tool-rich agent frameworks (exemplified by Claude Code and OpenClaw) and embedding-based retrieval memory systems (exemplified by Mem0 and A-MEM). The tradeoffs are sufficiently articulated to support a decision framework.

**Prefer GA's minimal-tool, information-density-maximizing architecture when:**

- **Context budget is a hard constraint**—either because of model context limits (edge deployment, older API tiers), cost sensitivity (high-volume pay-per-token usage), or because task complexity already pushes against effective context boundaries. The paper shows GA achieves 10–19× lower baseline context occupancy than alternatives after skill accumulation (Table 7).

- **The task distribution includes substantial repetition or structural similarity across sessions**—because GA's self-evolution converts repeated experience into efficiency gains (79.3% token reduction across tasks, Figure 5), while stateless or raw-log-memory systems plateau. If every task is genuinely novel, the self-evolution mechanism provides no benefit and its overhead (consolidation triggers, memory management prompts) may be a net cost.

- **Deployment requires continuous operation without degradation**—GA's context truncation pipeline prevents context explosion over long sessions, while systems without active context management accumulate state until performance degrades or the context limit is hit. The Reflect Mode watchdog and scheduled-task patterns depend on this property.

- **The operator can invest in initial SOP development**—GA's first-run cost on a new task type is higher than subsequent runs (Figure 5, Table 8). If tasks are one-off and the SOP consolidation never gets reused, the initial overhead is wasted. A deployment where each task type will be encountered many times amortizes this cost.

**Prefer tool-rich architectures (Claude Code, OpenClaw) when:**

- **Task diversity is extremely high and each task type is encountered only once**—the specialized tools in these frameworks provide efficiency shortcuts for operations that GA would need to compose from primitives (and possibly get wrong). The paper's tool composition examples (Appendix Table 11) show that specialized capabilities *can* be reconstructed, but the first few attempts may require more tokens and retries than a dedicated tool would.

- **The operating environment or model API requires native tool definitions on every call**—GA's tool-schema elision optimization (Section 2.3.4, Auxiliary) only works with the text-protocol path, not the native API path. In environments where complete tool schemas must be sent every turn, the prompt-level advantage of having fewer tools is reduced (though not eliminated—9 schemas are still smaller than 53).

- **The development team cannot invest in the initial memory architecture setup**—GA's hierarchical memory requires configuring the meta-memory layer, establishing L1/L2/L3 storage, and tuning consolidation triggers. A team that needs a working agent immediately with minimal configuration may prefer a framework that works out of the box with flat memory, even if it plateaus in capability over time.

**Prefer GA's selection-centric memory over embedding-based retrieval when:**

- **Content quality matters more than recall breadth**—GA's "No Execution, No Memory" rule ensures persistent memory contains only verified, behavior-changing information. The LoCoMo results (Table 6) show this produces better factual retention than embedding-based systems (Mem0, A-MEM) without requiring an embedding model or vector database. The tradeoff is that unverified observations are excluded, which could mean losing context that later proves useful.

- **Infrastructure simplicity is valued**—GA achieves superior memory performance without an embedding model, vector database, or retrieval pipeline, reducing operational complexity and dependency surface. For a self-hosted deployment, this eliminates several moving parts that can fail or require maintenance.

**Prefer embedding-based retrieval when:**

- **The memory content is inherently noisy or unverifiable**—if the agent operates in an environment where "verification through successful execution" is not clearly defined (e.g., open-ended conversation, creative tasks, tasks where success is subjective), GA's selection filter may reject most content, leaving the agent with insufficient memory. Embedding-based systems can store and retrieve noisy content, accepting some quality degradation in exchange for broader coverage.

- **The required retrieval is associative rather than procedural**—L1-first routing works well when the agent knows *what category* of information it needs (e.g., "retrieve the SOP for GitHub PR analysis"). For open-ended queries like "what did the user mention about their deployment preferences in any conversation last month?", embedding similarity over raw logs may surface relevant content that GA's category-based organization would miss because no explicit L1 entry was created for it.
