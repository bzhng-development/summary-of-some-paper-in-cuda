# Clover: Regressive Lightweight Speculative Decoding with Sequential Knowledge

**ArXiv:** [2405.00263](https://arxiv.org/abs/2405.00263)

## 🎯 Pitch

Parallel speculators like Medusa ignore the sequential dependency between tokens they predict, crippling accuracy for later positions. Clover fixes this with a regressive connection that feeds each speculated token's embedding into the next prediction, boosting top-5 accuracy by over 20% on later heads and lifting throughput gains to 91–146% over vanilla decoding—up to 57% better than Medusa.

---

## 1. Executive Summary

This paper introduces **Clover**, a speculative decoding algorithm that enhances the Medusa framework by incorporating **sequential knowledge** into parallel token speculation. Clover transmits information from previously predicted tokens through a **Regressive Connection** (feeding the embedding of the i-1th speculated token into the prediction of the ith token), integrates these tokens with the input context via an **Attention Decoder** (a cross-attention block that merges hidden states from the previous speculation step with the current token embedding), and refines the hidden states through an **Augmenting Block** (an additional transformer layer appended to the target model). Evaluated on Baichuan-Small (7B parameters) and Baichuan-Large (over 100B parameters) across ten dialogue tasks, Clover achieves up to 91% throughput improvement over vanilla auto-regressive decoding on the smaller model and 146% on the larger model, surpassing the prior state-of-the-art Medusa by up to 37% and 57% respectively—gains that widen with model scale. The improvement concentrates on later speculation heads (+21.7% to +26.4% top-5 accuracy), establishing that regressive mechanisms amplify speculative accuracy but benefit subsequent positions substantially more than the first head, where the gain is only 11.7%.

## 2. Context and Motivation

### The Core Problem: GPU Hardware and Autoregressive Decoding Are Fundamentally Mismatched

The paper addresses a well-known but structurally deep efficiency problem in large language model deployment: **autoregressive decoding underutilizes GPU hardware by design**. To understand why this is a fundamental architectural tension rather than a temporary implementation issue, we need to walk through exactly what happens during inference.

Modern GPUs derive their computational power from massive parallelism — they can perform thousands of matrix multiplications simultaneously. The standard transformer forward pass is well-suited to this: you feed in a sequence of tokens, compute attention across all positions in parallel, and produce output representations for every token in one shot. This is what happens during the **prefilling phase** (Section 1), where the model processes the entire input prompt at once. The GPU's compute units are saturated; memory bandwidth is used efficiently because large chunks of model weights are loaded once and applied to many tokens.

The problem emerges during the **decoding phase**. After generating the first output token, the model must generate each subsequent token one at a time, because each new token depends on all previously generated tokens. Specifically:

1. Load the entire model (billions to trillions of parameters) from GPU memory (HBM) into the compute units.
2. Perform a full forward pass through every transformer layer.
3. Produce exactly **one** new token.
4. Append that token to the sequence.
5. Repeat until the response is complete.

Step 2 is the bottleneck: the GPU spends most of its time **moving weights from memory to the compute units** (memory-bound operation) rather than actually computing, because the batch of tokens being processed at each decoding step is tiny — typically just one token per request. As the paper states:

> "billions to trillions of parameters must be loaded to the GPU cache through its limited memory bandwidth for computation, but only a small batch of tokens is actually computed"

This is the **memory-bandwidth bottleneck**, and it means the GPU's peak FLOPS are never approached during decoding. The hardware is capable of far more computation, but the sequential dependency in autoregressive generation prevents batching across time steps.

The consequence is not merely academic — it directly translates to **latency and throughput ceilings** that affect real users. When you interact with a chatbot, the time between your question and the complete answer is dominated by these memory-bound forward passes, one per output token. For a model with billions of parameters, each token adds measurable wall-clock time, and a response of a few hundred tokens requires hundreds of sequential GPU operations that cannot be parallelized.

### Why This Problem Is Important

The paper's framing makes clear that this is a **deployment-critical problem** with direct economic and user-experience consequences:

**1. Real-time serving is economically constrained.** As Figure 2 demonstrates (discussed in Section 1 and elaborated below), production systems handle inference requests in batches — multiple users' prompts are processed simultaneously to amortize the cost of loading model weights across requests. When batch sizes are large and the model is compute-bound (many tokens being processed at once), speculative decoding strategies that generate large token trees can actually hurt performance because they add computation overhead without proportional gains in accepted tokens. The paper explicitly grounds its design choices in this production reality: Clover is optimized for **large batch sizes and small token trees**, which the authors argue has been "not sufficiently addressed in previous speculative decoding work" (Section 5).

**2. The gap between hardware capability and realized throughput is substantial.** The raw numbers in the paper illustrate the magnitude: on the Baichuan-Large model (over 100B parameters), vanilla auto-regressive decoding achieves only 84.2 tokens/second on math tasks at batch size 4 (Table 1). With Clover, this becomes 207.3 tokens/second — a 146% improvement. This is not a marginal optimization; it represents the difference between a system that can serve 1 user versus 2.5 users with the same hardware.

**3. The problem compounds with model scale.** Larger models have more parameters to load per token, meaning the memory bottleneck becomes more severe — not less — as models grow. The paper shows that Clover's advantage over Medusa actually increases from 1.26× on the 7B model to 1.47× on the 100B+ model (Section 4.2), precisely because the speculator overhead becomes a smaller fraction of total computation at larger scales, while the accuracy gains from better speculation compound.

### Prior Approaches and Where They Fall Short

The paper situates itself within the **speculative decoding** literature, which represents the primary family of solutions to the memory-bandwidth bottleneck. The core idea behind all speculative decoding methods is identical: **use a cheap mechanism to guess multiple future tokens, then verify them all in a single forward pass of the target model**. If the guesses are correct, you generate multiple tokens for the cost of one memory-loading operation. If they're wrong, you've wasted some computation on rejected speculations, but the correct tokens up to the first mismatch are still kept.

The paper identifies two generations of speculative decoding approaches, both with limitations that Clover is designed to address:

#### First Generation: Independent Draft Models

Early speculative decoding works ([13, 6] in the references — the foundational papers by Leviathan et al. and Chen et al.) used **separate, smaller language models** as speculators. The workflow:

1. A small "draft model" (e.g., a model with 100M parameters compared to the target's 7B+) auto-regressively generates several candidate next tokens very quickly.
2. The target model takes these candidates as input and verifies them in a single forward pass.
3. Tokens that match the target model's own predictions are accepted; the first mismatched token and all subsequent ones are rejected.

The advantage is that draft models can generate speculations with minimal overhead because they're orders of magnitude smaller. The limitations, which the paper identifies indirectly by noting the shift toward integrated approaches, include:

- **Deployment complexity**: You must maintain, deploy, and synchronize two separate models in the serving pipeline. This doubles the model management burden.
- **Distribution shift**: The draft model and target model may disagree systematically, requiring careful training to align their output distributions.
- **Memory overhead**: The draft model occupies GPU memory that could otherwise be used for larger batch sizes or longer contexts.
- **Training data requirements**: The draft model must be trained on the same data distribution as the target model, which may be impractical when the target model's training data is proprietary.

Numerous works explored variations: online speculative decoding ([15] — adapting the draft model during inference), staged speculative decoding ([19] — using multiple draft stages), knowledge distillation for draft models ([28] — training the draft to mimic the target), and training-free draft architectures ([22, 10, 9] — using n-gram caches or retrieval to generate speculations without a separate model). However, all of these share the fundamental limitation of requiring a **separate draft model**, which introduces deployment friction.

#### Second Generation: Integrated Speculators (Medusa)

More recent work, which the paper explicitly builds on, eliminates the separate draft model entirely by **integrating lightweight speculator heads directly into the target model**. The Medusa paper ([5], Cai et al., 2024) is the primary baseline that Clover extends.

Medusa's architecture (Figure 1a) works as follows:

1. The target model processes the input normally through all transformer layers.
2. The hidden states from the **final transformer block** are fed into multiple independent **Medusa heads**.
3. Each Medusa head is a single MLP layer with its own small language model head (lm_head_i) that predicts a specific future token: head 1 predicts the next-1 token, head 2 predicts the next-2 token, head 3 predicts the next-3 token, etc.
4. All heads operate **in parallel and independently** — head 2 does not know what head 1 predicted.
5. The speculations from all heads are combined into a token tree using Cartesian product (if head 1 predicted {A, B} and head 2 predicted {C, D}, the tree contains {A→C, A→D, B→C, B→D}).
6. The target model verifies this tree in a single forward pass using tree attention (Section 2.2).

The key advantage of Medusa over draft models is its **lightweight and deployment-friendly design**: the heads add minimal parameters (a few MLP layers and small lm_heads), require no separate model, and can be trained with the target model frozen. The paper acknowledges this as a significant advance ("The lightweight head mechanism has led to substantial improvements in inference speed").

However, the paper identifies **three specific shortcomings** of Medusa that motivate Clover's design. These are not minor quibbles — they represent fundamental architectural limitations:

**Shortcoming 1: Independence of heads ignores sequential dependencies.** This is the paper's central critique. Each Medusa head predicts its designated future token based solely on the final hidden states of the target model. The head predicting the next-3 token has no access to what was predicted for next-1 or next-2. In natural language, subsequent tokens are heavily dependent on preceding ones: knowing that the next word is "Bayesian" should dramatically change what you predict for the word after "Bayesian" (likely "optimization," "inference," or "network" — as illustrated in Figure 4).

The paper quantifies this failure: Medusa heads suffer from "decreased accuracy" because they cannot condition on their sibling heads' outputs. The Cartesian product combination strategy further compounds this: because heads are independent, Medusa must consider all possible combinations, creating an exponentially large token tree where most branches are linguistically implausible sequences that would never arise if heads could see each other's predictions.

> "Each layer independently speculates on a word at a specified position beyond the next, disregarding the sequential dependencies from previously predicted tokens"

**Shortcoming 2: Tree explosion under independence leads to computational waste in production settings.** Because the Medusa heads are independent, the token tree formed from their Cartesian product grows exponentially with the number of heads. If each head proposes K candidates, the tree size grows as K^n for n heads. The paper states:

> "Because the Medusa heads operate independently, the tokens they speculate are combined using a Cartesian product to form an exponentially large token tree. This approach can lead to suboptimal performance when the decoding phase is not constrained by memory, as it generates a surplus of redundant tokens, particularly as the batch size increases."

This is the practical context that Figure 2 establishes: in real-time serving with large batch sizes, the system becomes **compute-bound**. Adding more speculative tokens increases FLOPs without proportionally increasing accepted tokens, because the GPU's compute units are already saturated. In the compute-bound regime (right side of Figure 2), speculative decoding's advantage over auto-regressive decoding diminishes — the inflection point where additional computation becomes counterproductive.

The paper argues that most prior speculative decoding work has operated under an assumption of **memory-bound conditions** (small batch sizes, where the GPU has spare compute capacity), but production systems more typically operate at large batch sizes where **compute-bound conditions** prevail. This insight is critical for understanding why Clover's regressive design matters: by making heads dependent, the token tree can be smaller (no need to explore implausible combinations) while maintaining or improving speculator accuracy.

> "the actual size of the token tree in practice is usually smaller than what is assumed in previous studies"

**Shortcoming 3: Single MLP layer is a weak speculator.** The Medusa head architecture consists of only a single MLP layer that receives input from the final hidden states. The paper doesn't dwell on this limitation extensively (since it's the most obvious), but the implication is clear: predicting a token 2, 3, or more positions ahead from static hidden states is a difficult learning problem that a single MLP layer with no attention mechanism over the input sequence cannot perform well. This is why Clover introduces both the Attention Decoder (to process sequential information) and the Augmenting Block (to refine the hidden states before speculation begins).

### Other Regressive Approaches and How Clover Positions Itself

The paper acknowledges in Section 5 that it is not the first to recognize the value of sequential dependency in speculators. Several concurrent works have explored **regressive speculators**, and the paper explicitly differentiates Clover from them:

- **Zhang et al. [26]** (Recurrent Drafter): Uses an MLP layer as a regressive block, passing speculated tokens through a simple feedforward network. The paper argues this is suboptimal because "MLP layer itself will not distinguish different embedding vectors, make it hard to learn valid sequential knowledge" (Section 4.3). The Ablation Study provides evidence: when Clover's Attention Decoder is replaced with an MLP layer, top-5 accuracy drops by 4.8%, 9.0%, and 11.5% across the three heads (Figure 7a).

- **Hydra [2]** (Ankner et al.): Also adds a sequential dependency mechanism and an additional block. The paper positions Clover as distinct through its specific architecture choices (cross-attention decoder rather than whatever mechanism Hydra uses) and its focus on the Augmenting Block.

- **Eagle [14]** (Li et al.): Introduces a regressive transformer block for speculation. The paper says Clover's "primary distinction" is the cross Attention Decoder and the exploration of the Augmenting Block, with the aim of "optimising the utilisation of sequential knowledge derived from both pre-specified tokens and the input sentence."

- **Chimera [25]** (Zeng et al.): Proposes a Trigram Encoder and Full Context Encoder as regressive speculators. Again, Clover distinguishes itself through the cross-attention mechanism and the specific Augmenting Block design.

The paper's positioning can be summarized as: **Clover is the first to systematically combine (1) cross-attention-based regressive decoding that merges the previous speculated token embedding with the full-sentence hidden states, with (2) an additional augmenting transformer block that refines the hidden states before speculation begins, all optimized for (3) production-typical large batch sizes with small token trees.**

### How Clover Positions Itself: Not Just "Medusa + Sequential Dependencies"

The paper's framing goes beyond a simple architectural add-on. The deeper argument is about **rethinking what makes a good speculator in production conditions**. Medusa optimized for the memory-bound regime where you can afford large token trees and the primary goal is maximizing accepted length regardless of computational cost. Clover optimizes for the **compute-bound regime** where the efficiency metric is not just "tokens per step" but "tokens per second," which accounts for the computational overhead of the speculator itself.

This shift in optimization target has architectural consequences:

1. **Sequential dependency isn't just about accuracy** — it produces token trees with "greater information density" (Section 3.1), meaning fewer but better candidates. A regressive speculator that predicts token sequences {A→B→C, A→D→E} naturally captures the dependency structure, whereas Medusa's Cartesian product would enumerate {A→B, A→D, A→C, A→E, ...} with many implausible combinations.

2. **The Augmenting Block is a targeted investment** — adding an entire transformer layer sounds expensive, but at large batch sizes, the additional computation (roughly 1/N_layers of total inference time) pays for itself through higher acceptance rates that reduce the total number of decoding steps.

3. **The cross-attention design choice matters** — using attention rather than concatenation + MLP for the regressive block is not an incidental preference. The ablation shows it's worth 4.8–11.5% top-5 accuracy, and the paper attributes this to attention's ability to selectively aggregate information from the previous token embedding based on the hidden state context, rather than forcing a fixed combination.

4. **Measurements target production-relevant metrics** — the paper evaluates at batch sizes up to 48 and explicitly sets token tree size to 4 (validated in Appendix A.2, Figure 8, as the point of diminishing returns), conditions under which Medusa's tree explosion becomes a liability rather than an asset.

This strategic positioning — solving speculative decoding for compute-bound production settings, not just memory-bound research settings — is what distinguishes Clover from both the Medusa baseline and other regressive speculator proposals.

## 3. Technical Approach

### 3.1 Reader Orientation

Clover is a **speculative decoding system** — a set of lightweight neural network heads bolted onto a frozen large language model that guess multiple future tokens cheaply so the target model can verify them all in a single forward pass, effectively generating several tokens per decoding step instead of one. It solves the **memory-bandwidth bottleneck** of auto-regressive decoding by making speculators more accurate through sequential knowledge (knowing what was already guessed helps guess what comes next), which increases the number of accepted tokens per verification step and reduces the total number of expensive forward passes through the large model.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components bolted onto a frozen target LLM:

1. **Target LLM (Baichuan, frozen)** — the large language model whose weights are never updated. It processes the input prompt through all transformer layers normally, producing hidden states from its final block. These hidden states serve as the "context embedding" for speculation.

2. **Augmenting Block** — an additional transformer layer (or attention-only sublayer) appended after the target model's final transformer block. It takes the target model's final hidden states as input and refines them specifically for the task of predicting multiple future tokens (rather than the original next-token prediction task the target model was pretrained for). Its output `$h_0$` becomes the initial hidden state for the speculative chain.

3. **Attention Decoder (cross-attention block)** — a regressive block that runs once per speculated token position. At the i-th speculation step, it takes two inputs: the hidden states `$h_{i-1}$` from the previous speculation step (which encode the full input context) and the embedding `$e_{i-1}$` of the token just speculated at position i-1. It uses cross-attention (with `$h_{i-1}$` as query and `$e_{i-1}$` as key/value) to merge sequential knowledge from the previous token into the hidden state, producing `$h_i$`. This is the mechanism that creates sequential dependency between speculated tokens.

4. **Clover Heads (MLP + shared LM head)** — at each speculation depth i, a single MLP layer takes `$h_i$` from the Attention Decoder and projects it into the vocabulary space through the target model's **original shared LM head** to predict the next-i token. Unlike Medusa, which has independent per-head LM heads, Clover shares the target model's pre-trained LM head across all speculative heads.

5. **Regressive Connection** — the wiring pattern that chains speculations together: the embedding `$e_i$` of the token predicted by head i is fed into the Attention Decoder at step i+1. This is what makes the speculation chain regressive rather than parallel.

Information flows as follows: user prompt → frozen target LLM forward pass → final transformer block hidden states → **(Optional: Augmenting Block)** → `$h_0$` → **Head 1**: MLP_1 → LM head → token_1 + embedding `$e_1$` → **Attention Decoder with `$h_0$` and `$e_1$`** → `$h_1$` → **Head 2**: MLP_2 → LM head → token_2 + `$e_2$` → **Attention Decoder with `$h_1$` and `$e_2$`** → `$h_2$` → **Head 3**: MLP_3 → LM head → token_3 → all speculated tokens form a dependency tree → target model verifies all tokens in a single forward pass using Tree Attention.

### 3.3 Roadmap for the Deep Dive

- **First**, the Regressive Connection: how embedding vectors flow between speculation steps, why this creates a dependency chain, and what the tradeoff is between lost parallelism and gained accuracy.
- **Second**, the Attention Decoder: the actual neural mechanism that merges sequential information, including the precise cross-attention formulation with query/key/value projections, why cross-attention rather than self-attention or concatenation, and the ablation evidence for this choice.
- **Third**, the Augmenting Block: why appending an additional transformer layer before speculation helps, what architectural variants were explored (full transformer, attention-only, MLP-only, none), and the quantitative evidence for which components matter.
- **Fourth**, the shared LM head design and embedding lookup mechanism, including the specific computation used to convert tokens to embedding vectors and why this was chosen over a standard embedding table lookup.
- **Fifth**, the training procedure: what gets trained versus frozen, the data, hyperparameters, initialization strategy for each component, and the reasoning behind these choices.
- **Sixth**, the tree construction differences from Medusa and how regressive dependency naturally produces token trees with sequential structure rather than Cartesian product trees.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems architecture paper** that proposes three incremental modifications to the Medusa speculative decoding framework. The core idea is that **sequential dependency between speculated tokens** (knowing what was guessed for position i-1 before guessing position i) substantially improves speculator accuracy, particularly for later positions in the speculation chain, and that a cross-attention mechanism is the right way to implement this dependency.

---

#### Regressive Connection

The Regressive Connection is the architectural wiring pattern that transforms Clover from a parallel speculator (like Medusa, where all heads predict independently) into a **sequential speculator** where each head conditions on the outputs of previous heads. It is not a separate neural network component but rather the **data flow topology** — the "blue dotted lines" in Figure 5 — that routes predicted token embeddings from one speculation step to the next.

**How it works mechanically:**

1. The first Clover head (i=1) takes hidden state `$h_0$` from either the target model's last transformer block or the Augmenting Block, passes it through a single MLP layer, and projects it through the shared LM head to produce a probability distribution over the vocabulary. The predicted token `$t_1$` (the next-1 token) is sampled or selected from this distribution.

2. Crucially, rather than discarding `$t_1$` after prediction, Clover converts it into an **embedding vector** `$e_1$`. The paper specifies a non-standard embedding lookup: instead of using the model's token embedding table, `$e_1$` is computed by multiplying the one-hot vector of `$t_1$` by the **transposed normalized weight matrix** of the shared LM head (the "look up" arrow in Figure 1b, right side).

3. This embedding `$e_1$` is fed into the Attention Decoder at step i=2, together with `$h_1$` (the output of the Attention Decoder from the previous step, or `$h_0$` for the first step). The Attention Decoder merges them into `$h_2$`, which feeds into the MLP head for position 2.

4. The process repeats: token `$t_2$` is predicted, converted to `$e_2$`, fed to step 3 alongside `$h_2$`, and so on for as many heads as configured (the paper uses 3 heads, matching Medusa-3).

**The dependency chain visualized:**

```
h_0 → [Head 1 MLP] → t_1 → e_1 ─┐
                                  ↓
h_0 ──────→ [Attention Decoder 1] → h_1 → [Head 2 MLP] → t_2 → e_2 ─┐
                                                                      ↓
h_1 ──────────────────────→ [Attention Decoder 2] → h_2 → [Head 3 MLP] → t_3
```

Each step depends on the embedding of the previous step's token, creating a **linear chain of sequential dependence**. The hidden state `$h_i$` accumulates information from all previous steps because it's recursively updated through the Attention Decoder (see Equation 2 below).

**Why this introduces sequential dependency in a meaningful sense:**

The paper draws a clean contrast with Medusa, where all heads receive the same hidden state `$h_0$` and operate independently. In Medusa, the head predicting next-3 cannot exploit the fact that next-1 was predicted as "Bayesian" to sharpen its prediction toward "optimization," "inference," or "network." In Clover, the embedding of "Bayesian" (`$e_1$`) is explicitly present in the computation of `$h_2$` and `$h_3$`, directly influencing the predictions at positions 2 and 3.

**The parallelism-accuracy tradeoff:**

The paper is explicit about the cost of this design:

> "Although the critical path of the computation becomes proportional to the depth of the speculation and loses a certain amount of parallelism, the increase in speculation accuracy rather improves the overall latency."

In Medusa, all heads can compute their MLP forward passes in parallel because they share the same input `$h_0$` and don't depend on each other. In Clover, head i must wait for the Attention Decoder at step i-1 to produce `$h_{i-1}$` and for head i-1 to produce `$e_{i-1}$`. This makes the critical path length O(depth) rather than O(1).

However, the paper argues this serialization is **worth it for two reasons**:

1. **Higher hit rate reduces total decoding steps.** Even though each speculation takes slightly longer, the model accepts more tokens per verification step, meaning fewer total forward passes through the expensive target model. Since the target model's forward pass dominates latency (the speculator is, by design, lightweight), this is a net win.

2. **Smaller, higher-quality token trees.** Because each position's predictions depend on the previous position's chosen token, the token tree is not a Cartesian product of independent distributions. This reduces computational waste and makes tree pruning more effective. The paper claims:

> "Since every speculated token in the latter position has one token in its previous location as the precursor, the token tree for verification phase can have greater information density."

This "information density" concept is key: Medusa's Cartesian product tree contains many branches corresponding to linguistically implausible token combinations (e.g., "Bayesian cat table"), but Clover's dependency structure means the tree only contains sequences where each token is predicted conditioned on a specific predecessor, effectively pruning implausible branches before they're generated.

**Evidence for this tradeoff working:**

The ablation in Figure 7a provides direct evidence. When the Regressive Connection is removed (the "− Regressive Connection" bar), the architecture reverts to parallel heads receiving the same input. The top-5 accuracy drops by:

- Head 1: −2.6% (from the already-reduced baseline without Attention Decoder)
- Head 2: −4.6%
- Head 3: −6.0%

The accuracy loss increases with head position, which is exactly what you'd expect if sequential dependency matters more for later positions (where the benefit of knowing the preceding token accumulates across the chain). This validates the core hypothesis: regressive connection provides information that independent heads cannot exploit.

---

#### Attention Decoder

The Attention Decoder is the **actual neural mechanism** that implements the regressive connection. It is a cross-attention block that takes two inputs — the hidden states from the previous speculation step and the embedding of the just-predicted token — and produces a new hidden state that merges both sources of information. The paper evaluates it against a simpler alternative (an MLP block) and provides evidence for why cross-attention is the right choice.

**Inputs and outputs:**

For the i-th speculation step (predicting the next-i token):

- **Query source:** The hidden states `$h_{i-1}$` from the previous step, after RMS normalization. For the first step (i=1), `$h_0$` comes from either the target model's last transformer block or the Augmenting Block.
- **Key and Value source:** The embedding vector `$e_{i-1}$` of the token predicted at the previous step. For the first step, `$e_0$` is the embedding of the actual next-0 token `$t_0$` generated by the target model's original lm_head.
- **Output:** A new hidden state `$h_i$` that is the residual sum of `$h_{i-1}$` and the attention output, which then feeds into the MLP layer for head i.

**Cross-attention formulation:**

The computation is spelled out in Equations 1 and 2:

$$Q_i = W_Q \cdot \text{normalize}(h_{i-1}), \quad K_i = W_K \cdot e_{i-1}, \quad V_i = W_V \cdot e_{i-1}$$

$$h_i = h_{i-1} + \text{Attention}(Q_i, K_i, V_i)$$

where:

- `$W_Q$`, `$W_K$`, `$W_V$` are learnable projection matrices specific to the Attention Decoder (not shared with the target model's attention blocks).
- `$\text{normalize}(\cdot)$` is RMS normalization (the standard normalization used throughout the Baichuan model architecture).
- `$e_{i-1}$` is the embedding vector of the token speculated at step i−1 (for i=1, `$e_0$` is the embedding of the actual output token).
- `$h_{i-1}$` is the hidden state vector from the previous step (for i=1, `$h_0$` comes from the Augmenting Block or target model).
- `$\text{Attention}(Q, K, V)$` is standard scaled dot-product attention with `$\text{softmax}(QK^T/\sqrt{d})V$`.

**What Equation 1 computes:**

The three linear projections map the two input vectors into a shared attention space. The query is produced from the full hidden state `$h_{i-1}$` (which encodes the entire input sentence through recursive propagation), while the key and value are produced from the single token embedding `$e_{i-1}$`. This is a **cross-attention** pattern: the query asks "what in this single proposed token is relevant to the full context?", and the attention mechanism computes a weighted representation that merges the two.

Contrast this with the alternative the paper explicitly rejects: concatenating `$h_{i-1}$` and `$e_{i-1}$` and feeding them through an MLP. Cross-attention allows the hidden state to **selectively attend** to different aspects of the token embedding based on context. The query `$Q_i$` (derived from the full context) determines which dimensions of the token embedding `$e_{i-1}$` get amplified or suppressed. An MLP, by contrast, applies a fixed transformation regardless of the relationship between the two inputs.

**What Equation 2 computes:**

The attention output is added back to `$h_{i-1}$` via a residual connection, producing `$h_i$`. This is the standard residual formulation used throughout the transformer architecture. The residual connection ensures that:

1. The model can learn to ignore the token embedding if it's not useful (by learning to set the attention output near zero, so `$h_i \approx h_{i-1}$`).
2. The hidden state `$h_{i-1}$` is preserved and augmented rather than replaced, maintaining the full input context throughout the chain.
3. Gradient flow during training is unimpeded through the residual path.

Operationally: hidden state `$h_{i-1}$` (which already encodes the input sentence and any previous speculated tokens) is **enriched** with information from the just-predicted token `$e_{i-1}$`, producing `$h_i`$, which then serves as the input to MLP head i. This enriched state tells head i: "based on everything in the input sentence AND the fact that the previous token is `$e_{i-1}$`, what should the next token be?"

**Why the sequence `$h_i = h_{i-1} + \text{Attention}(Q_i, K_i, V_i)$` matters for sequential knowledge accumulation:**

Since Equation 2 is applied recursively — `$h_1$` depends on `$h_0$` and `$e_0$`, `$h_2$` depends on `$h_1$` and `$e_1$`, etc. — the hidden state `$h_i$` accumulates a **path of residual updates** encoding the sequence of previously speculated tokens. By the time head 3 receives `$h_2$`, it has information about both `$e_0$` (the actual output token) and `$e_1$` (the first speculated token), merged with the full input context. This is the "sequential knowledge" that gives Clover its name and its advantage.

**MLP ablation and why it matters:**

The paper explicitly tested replacing the Attention Decoder with an MLP block. This MLP block takes concatenated `$[h_{i-1}, e_{i-1}]$` as input and produces `$h_i$` as output — a standard feedforward approach to merging two vectors. The results (Figure 7a, "− Attention Decoder" bar) show:

- Head 1 top-5 accuracy drops by 4.8%
- Head 2 top-5 accuracy drops by 9.0%  
- Head 3 top-5 accuracy drops by 11.5%

The paper interprets this as evidence that:

> "MLP layer itself will not distinguish different embedding vectors, make it hard to learn valid sequential knowledge"

What this means concretely: an MLP applies the same learned weights regardless of the relationship between `$h_{i-1}$` and `$e_{i-1}$`. If the previous token embedding is similar to the current context (e.g., the token "Bayesian" in a math context), the MLP must learn a general-purpose transformation that works for all possible token-context pairs. Attention, by contrast, computes query-key affinities that allow the model to dynamically adjust how much each dimension of the token embedding influences the output based on the specific context. The larger accuracy drop at later heads (9.0% at head 2, 11.5% at head 3) suggests the attention mechanism is particularly valuable for disambiguating longer-range dependencies, where the accumulated context in `$h_{i-1}$` is richer and more variable.

**Overhead analysis:**

The paper claims the Attention Decoder has "negligible overhead" because its inputs are "only two vectors per request or beam." This is accurate in the context of speculative decoding: the attention computation operates on single vectors (the hidden state and the token embedding, both of dimension d_model ≈ 4096 for the 7B model), not on sequences of tokens. A standard transformer attention block computes attention over sequence length, with O(L²) complexity. The Attention Decoder computes attention over **one key/value pair** (since `$e_{i-1}$` is a single vector), making it more like a learned gating mechanism than a full self-attention block. The cost is a few matrix multiplications (the QKV projections) plus a trivial attention computation — negligible compared to the target model's forward pass.

#### Augmenting Block

The Augmenting Block is an additional transformer layer (or attention-only sublayer) appended **after the target model's final transformer block** but **before the speculative heads begin predicting**. Its purpose is to transform the hidden states from "representations optimized for next-token prediction" (the target model's pretraining objective) into "representations optimized for predicting multiple future tokens" (the speculation objective).

**Motivation: The pretraining-speculation objective mismatch.**

The target model was pretrained with a single objective: predict the next token given all previous tokens. Its hidden states at every layer are optimized to extract features that are useful specifically for predicting token_{t+1}. When Medusa or Clover tries to predict token_{t+2}, token_{t+3}, etc., from the same hidden states, it is using representations that were never trained to support those predictions. The Augmenting Block addresses this by learning to **augment** the hidden states with features that are useful for predicting multiple future positions simultaneously.

The paper states this rationale concisely:

> "The original target LLM is pre-trained for just predicting the next token. To extract more information for speculators to predict more succeeding tokens, we append an additional transformer block to augment features from the entire input sentence."

**Architecture variants explored:**

The paper systematically evaluates four configurations for the Augmenting Block (Figure 7b):

1. **Full transformer block** (attention sublayer + MLP sublayer, with residual connections) — this is the actual Clover architecture used in all main experiments.
2. **Attention only** — a single self-attention sublayer over the input sequence, without the subsequent MLP.
3. **MLP only** — a single feedforward sublayer without attention.
4. **No Augmenting Block** — hidden states go directly from the target model to the first speculative head (this is equivalent to Medusa's behavior after removing all Clover components).

**Quantitative findings (Figure 7b, all numbers are top-5 accuracy):**

Starting from "No Augmenting" as baseline:

| Augmenting Block type | Head 1 gain | Head 2 gain | Head 3 gain |
|---|---|---|---|
| Full Transformer | +4.9% | +9.0% | +9.4% |
| Attention Only | +1.9% | +4.4% | +5.1% |
| MLP Only | +1.0% | +1.2% | +0.7% |

**Interpreting the ablation:**

The attention sublayer contributes the majority of the accuracy gain. This is not surprising: self-attention over the input sequence can learn to extract long-range dependencies and contextual features that are specifically predictive of future tokens at various offsets. For example, if the input sentence ends with "We should apply," the attention block can learn to attend to earlier mentions of methodologies (e.g., "Bayesian optimization," "gradient descent") to help predict both the immediate next token and tokens further ahead.

The MLP sublayer contributes a small but consistent additional gain (the difference between "Full Transformer" and "Attention Only" rows). The paper notes:

> "We still add the MLP block in our Clover implementation since it does indeed increase accuracy, while incurring only negligible overhead."

The TL;DR assessment (`"we leave it as an optional component"`) is a practical engineering judgment: the MLP adds ~1% accuracy for a modest increase in parameters and computation, so it's included by default but could be dropped for resource-constrained deployments.

**Why self-attention rather than just more MLP layers matters:**

The Augmenting Block's attention sublayer operates over the full input sequence, allowing it to **re-weight and re-contextualize** the hidden states across all token positions before they're used for speculation. This is fundamentally different from the target model's frozen attention blocks (which were optimized for next-token prediction) — the Augmenting Block's attention is trained specifically to extract features useful for predicting tokens at multiple future offsets (next-1, next-2, next-3, etc.).

The paper provides a conceptual rationale:

> "The attention mechanism focuses on extracting relationships between tokens in the sentence, making it easier to learn for feature augmentation."

In operational terms: the self-attention in the Augmenting Block can learn attention patterns like "when predicting the second and third tokens after a preposition, attend strongly to the noun phrase that the preposition heads," which is a pattern that wouldn't be useful for next-token prediction (where the preposition itself is the most informative context) but is crucial for multi-token speculation.

**Computational overhead:**

The paper quantifies the overhead as "approximately 1/N_layers of inference time," where N_layers is the number of transformer layers in the target model. For a 7B model with roughly 32 layers, this is about 3% additional computation per forward pass. The argument is that this 3% overhead pays for itself many times over through increased acceptance rates that reduce the number of total forward passes needed. This is particularly true at large batch sizes, where the target model's forward pass dominates and the Augmenting Block's cost is amortized across all requests in the batch.

**Initialization:**

> "the initial weights in the Augmenting Block are identical to the last transformer block in the target model"

This is an important practical detail. Rather than initializing randomly, Clover copies the weights from the target model's final layer. This provides a warm start: the Augmenting Block begins as a copy of a layer that already produces useful representations for next-token prediction, and fine-tuning gradually shifts it toward multi-token speculation. Random initialization would require the block to learn basic language modeling features from scratch, which would be inefficient and potentially unstable given the limited training data (0.15B tokens).

#### Shared LM Head and Embedding Computation

Clover departs from Medusa in how speculative tokens are projected onto the vocabulary and how their embeddings are computed. These are orthogonal design choices that affect both parameter count and the quality of the regressive connection.

**Shared LM head:**

In Medusa, each speculator head has its own independent LM head (lm_head_i in Figure 1a) — a linear layer mapping from hidden dimension to vocabulary size. For a model with hidden size 4096 and vocabulary size 125K (typical for a 7B model), each lm_head contains 4096 × 125K ≈ 512M parameters. Three heads would add 1.5B parameters for the LM heads alone.

Clover eliminates this redundancy:

> "In Clover, all the speculative heads share the original LM head in the target model."

Each Clover head's MLP layer outputs a hidden state `$h_i$` of the same dimension as the target model's hidden states, and this is directly projected through the frozen original lm_head to produce logits over the vocabulary. This means:

1. **Parameter savings:** No additional vocabulary-projection parameters are needed, reducing the speculator's total trainable parameters.
2. **Consistent output space:** The speculative heads use the same projection as the target model, meaning the logit distributions are in the same space, potentially improving verification consistency.
3. **Faster training:** Fewer parameters to optimize means faster convergence and lower memory requirements during training.

The paper reports that the total trainable parameters are "approximately 0.2B and 2B" for the 7B and 100B+ models respectively, which includes the Augmenting Block, Attention Decoder, and the MLP layers of each Clover head — but not any LM head parameters.

**Embedding computation from LM head weights:**

The Regressive Connection requires converting each predicted token into an embedding vector `$e_i$`. The standard approach would be to look up the token in the model's token embedding table (the input embedding layer). Clover instead computes embeddings from the **LM head weights**:

> "Specifically, the embedding vector `$e_i$` is given by: the one-hot vector of token `$t_i$` multiplied by the transposed normalized weight matrix in the LM head."

Let `$W_{\text{lm}}$` be the weight matrix of the shared LM head, of shape `$(\text{vocab\_size}, d_{\text{model}})$`, and let `$\mathbf{1}_{t_i}$` be the one-hot vector for token `$t_i$` of length `vocab_size`. The embedding is:

$$e_i = \mathbf{1}_{t_i} \cdot W_{\text{lm}}^T$$

where `$W_{\text{lm}}^T$` is the transposed weight matrix (shape: `$(d_{\text{model}}, \text{vocab\_size})$`), and the result `$e_i$` is a vector of dimension `$d_{\text{model}}$`. Additionally, the paper specifies that the weight matrix is **normalized** before transposition (the "look up" operation in Figures 1b and 5).

**What this equation computes:**

The one-hot vector selects a single row from `$W_{\text{lm}}^T$` — specifically, the row corresponding to token `$t_i$`. This row is a learned vector that represents token `$t_i$` in the same space as the hidden states that feed into the LM head. In other words, this is the representation space where hidden states and token predictions interact.

Operationally: for each speculated token `$t_i$`, extract the corresponding row from the (normalized) LM head weight matrix `$W_{\text{lm}}$`. This row serves as the embedding `$e_i$` fed into the next step's Attention Decoder.

**Why use LM head weights rather than the embedding table:**

The paper provides a specific justification:

> "Compared with looking up from the embedding table, we believe such embedding distribution is much closer to the hidden states from the last transformer block, where the weights are used to initialize the augmenting block, reducing the difficulty of fine-tuning."

There are two distinct arguments here:

1. **Distribution alignment:** The LM head weights map from hidden states → logits. The rows of `$W_{\text{lm}}$` represent what each token "looks like" in hidden-state space (since the dot product `$h \cdot W_{\text{lm}}[\text{token}]^T$` gives the logit for that token). These row vectors live in the same space as the hidden states `$h_i$` that the Attention Decoder manipulates. In contrast, the token embedding table maps from token indices → a different representation space (the input embedding space), which may have different statistics and geometry. Using LM head rows means the embedding `$e_i$` is naturally compatible with the hidden state `$h_{i-1}$` in the Attention Decoder's query-key computations.

2. **Initialization synergy:** The Augmenting Block is initialized from the target model's last transformer block. The last transformer block's output hidden states are the inputs to the LM head during pretraining. By using LM head rows as embeddings, the Attention Decoder is operating in a space where the relationship between hidden states and token representations is already well-defined (the model was trained to maximize `$h \cdot W_{\text{lm}}[\text{correct\_token}]^T$`). This reduces the learning burden on the Attention Decoder during fine-tuning — it doesn't have to learn a mapping between incompatible spaces.

#### Training Procedure

The paper provides a concise but specific training recipe, with several design choices that are important for reproducibility and understanding the method's practical requirements.

**What is frozen vs. trained:**

- **Frozen:** All weights of the target LLM (Baichuan). This includes all transformer layers, the original LM head, the token embedding table, and all normalization layers. The target model is treated as a fixed feature extractor.
- **Trained:** The Augmenting Block, the Attention Decoder (projection matrices `$W_Q$`, `$W_K$`, `$W_V$`), and the MLP layers of each Clover head (MLP_i for i = 1, 2, 3).

This "target model frozen, speculator trained" paradigm is identical to Medusa's approach and is what makes these methods practical: they don't require retraining or even fine-tuning the expensive large model, and they can be added to any pre-trained model without access to its training pipeline or data.

**Training data:**

> "We employ the Baichuan internal supervised fine-tuning (SFT) dataset, containing approximately 0.15B tokens, 95% of which are Chinese"

This is roughly 150 million tokens — a modest amount compared to the trillions of tokens used for pretraining, but typical for fine-tuning runs. The heavy Chinese skew (95%) reflects Baichuan's design as a Chinese-focused model. Training on SFT data (conversation-style examples) rather than pretraining corpora ensures the speculator is optimized for the type of dialogue interactions it will encounter in deployment.

**Training duration:**

> "We train the heads for 1 epoch"

A single epoch over 0.15B tokens is a relatively short training run, consistent with the goal of quick, low-cost speculator training. This is possible because (a) the target model is frozen, so the speculator heads only need to learn to project from the target model's representations, not learn language modeling from scratch, and (b) the Augmenting Block and Attention Decoder are initialized in ways that reduce the learning burden.

**Optimizer configuration:**

> "with `$(\beta_1 = 0.9, \beta_2 = 0.999)$` for the AdamW optimizer"

Standard AdamW hyperparameters (β₁=0.9, β₂=0.999), consistent with most LLM fine-tuning practices.

**Learning rates:**

> "The learning rate is set to 1e-3 for Baichuan Small, and 6e-4 for Baichuan Large. Cosine decay is applied to the learning rate."

The learning rates are high relative to typical LLM fine-tuning (which often uses 1e-5 to 5e-5), which is appropriate because the trained components are initialized randomly or from copies of frozen weights and need to move substantially. The larger model gets a lower learning rate (6e-4 vs. 1e-3), which is standard practice — larger models are more sensitive to large weight updates. Cosine decay provides a smooth annealing schedule that reduces the learning rate to near zero by the end of training.

**Training resources:**

> "taking 2 hours to train on 8x A800 NVIDIA GPU and 32x H800 NVIDIA, respectively"

The 7B model trains on 8 A800 GPUs (80GB each) in 2 hours. The 100B+ model requires 32 H800 GPUs (80GB each, higher bandwidth), also in 2 hours. The training cost is modest by LLM standards, making Clover practical to adopt.

**Initialization strategies:**

The paper provides specific initialization recipes for each trained component, which is important because good initialization can dramatically reduce training time and improve final performance:

1. **Augmenting Block:** "the initial weights in the Augmenting Block are identical to the last transformer block in the target model." This copies both the attention sublayer and MLP sublayer weights from the target model's final layer. The rationale is discussed above: this provides a warm start with weights that already produce useful representations.

2. **MLP layers in Clover heads:** "the initialization of the MLP layer is the same as in Medusa's method." The paper does not elaborate on what Medusa's initialization is, but it's likely a standard approach (e.g., Xavier/Glorot initialization or small random weights).

3. **Attention Decoder (`$W_Q$`, `$W_K$`, `$W_V$`):** "the weights of Q and K are initialized with identical matrix with Gaussian noise added, while the V matrix is set to all zero." This is a carefully chosen initialization:
   - Q and K start as copies of the same matrix (with small Gaussian perturbations), which means the attention mechanism initially computes nearly uniform attention weights — the model initially treats all dimensions of the key/value equally, letting training shape the attention patterns.
   - V is initialized to zero, which means `$\text{Attention}(Q, K, V) \approx 0$` regardless of the attention weights. Combined with the residual connection in Equation 2 (`$h_i = h_{i-1} + \text{Attention}(\dots)$`), this means the Attention Decoder initially acts as an identity map: `$h_i \approx h_{i-1}$`. The model starts from the parallel-decoding behavior (all heads receive essentially the same hidden state) and gradually learns to incorporate sequential information as training progresses. This is a classic "zero-initialized residual" strategy that ensures stable training dynamics.

**Why this zero-V initialization is clever:**

Without it, the randomly initialized Attention Decoder would inject noise into `$h_i$` at each step of the speculative chain, making early training unstable. By starting with V=0, the model initially behaves like Medusa (ignoring the regressive connection), allowing the MLP heads to learn basic token prediction. As training progresses, the model gradually learns to use the regressive information by moving V away from zero, improving predictions at later positions without disrupting the already-useful predictions at earlier positions.

#### Tree Construction and Verification Differences from Medusa

The paper does not provide an explicit algorithm for how Clover's token trees are constructed, but the implications of the regressive architecture are clear and discussed in the text.

**Medusa's tree construction (for contrast):**

In Medusa, each head independently produces a set of top-k candidate tokens. If head 1 produces candidates {A, B} and head 2 produces candidates {C, D}, the token tree contains the Cartesian product: the root (actual token) branches to A and B, and each of A and B branches to C and D, for a total of 4 leaf nodes. With 3 heads each producing k candidates, the tree size grows as O(k³). This exponential growth is a direct consequence of the independence assumption: since head 2's predictions don't depend on head 1's output, all combinations must be considered.

**Clover's tree construction:**

Because Clover heads are sequentially dependent, the tree is constructed differently. The paper doesn't fully specify the algorithm, but the logical construction is:

1. Head 1 produces top-k candidates for the next-1 token. Each candidate becomes a branch from the root.
2. For each candidate `$t_1$` from head 1, head 2 produces top-k candidates conditioned on `$e_1$` (the embedding of `$t_1$`). This means head 2's predictions are **specific to each branch** — the predictions following candidate A might differ from those following candidate B.
3. Head 3 similarly conditions on each (candidate from head 1, candidate from head 2) pair.

The tree is still k-ary (each node has k children), but the children differ per node because predictions are conditioned on the specific parent. The paper claims this produces "a token tree with more comprehensive dependency information" that is "easy for pruning."

**Why this matters for efficiency:**

The paper emphasizes that in compute-bound regimes (large batch sizes), tree size must be kept small to avoid overwhelming the GPU's compute units. The Appendix A.2 (Figure 8) validates this by showing diminishing returns: doubling the tree size from 2 to 4 to 8 to 16 produces progressively smaller gains in accepted tokens per step. The paper sets tree size to 4 for all main experiments.

In Medusa, a tree of size 4 with 3 independent heads means the tree must be aggressively pruned to fit within the size budget, potentially discarding useful branches. In Clover, the dependency structure means that the generated tree naturally contains more plausible sequences (since each token is predicted conditioned on its predecessor), so a smaller tree retains more of the useful speculation capacity.

The paper claims Clover generates "50% - 76% more extra tokens (except the first) per step than the Medusa method, thanks to the regressive mechanism" (Section 1 contributions bullet). This statistic — computed across different tasks in Figure 6 — shows that even with the same tree size constraint, Clover's trees contain more tokens that survive verification, confirming that the regressive tree structure does indeed have "greater information density."

**Verification remains identical:**

The paper does not modify the verification process. Both Medusa and Clover use the same **Tree Attention** mechanism (Section 2.2) to verify all speculated tokens in a single forward pass of the target model. The target model receives the entire token tree as input (with appropriate causal masking to respect the tree topology), computes logits for all positions simultaneously, and accepts tokens that match its own predictions. The first mismatched token and all tokens in branches beyond it are rejected.

The key point is that Clover only changes the **proposal distribution** (how tokens are speculated), not the **acceptance mechanism** (how tokens are verified). The output distribution is still identical to what the target model would produce autoregressively (lossless decoding), because the verification step ensures that only tokens the target model would have generated are accepted.

---

#### Summary of Design Choices and Their Justifications

- **Regressive Connection (sequential dependency)** over parallel independence: improves accuracy at the cost of serialized computation, with net win because higher acceptance rates reduce total target-model forward passes. The ablation shows this is worth 2.6–6.0% top-5 accuracy per head.

- **Cross-Attention Decoder** over MLP concatenation: attention allows selective, context-dependent fusion of the previous token embedding with the hidden state, whereas MLP applies a fixed transformation. Ablation: 4.8–11.5% top-5 accuracy advantage.

- **Augmenting Block (full transformer)** over no augmentation: adds a learnable layer between the target model and speculators to adapt hidden states from next-token-prediction to multi-token-speculation. Ablation: 4.9–9.4% top-5 accuracy advantage.

- **Shared LM head** over independent per-head LM heads: reduces parameter count, ensures consistent output space with the target model, and enables the embedding computation from LM head rows.

- **LM-head-row embeddings** over token embedding table lookup: keeps embeddings in the same distribution as hidden states (since LM head rows are the target of hidden-state dot products), reducing the learning burden on the Attention Decoder.

- **Zero-initialized V matrix** in Attention Decoder: ensures the regressive connection starts as an identity function, allowing stable training that progressively incorporates sequential information without disrupting early predictions.

- **Single epoch training** over multiple epochs: sufficient because only lightweight heads are trained on top of a frozen target model with good initialization, making convergence fast and overfitting unlikely on 0.15B tokens.

- **Cosine learning rate decay** over constant LR: provides smooth annealing that stabilizes late-stage training and avoids overshooting the optimum.

## 4. Key Insights and Innovations

### Innovation 1: Treating Sequential Dependency as an Information-Density Strategy, Not Merely an Accuracy Trick

The most intellectually distinctive move in Clover is not the observation that "knowing the previous token helps predict the next one" — that is obvious from the structure of language itself and has been explored in other regressive speculators (Hydra, Eagle, Chimera). What Clover recognizes, and what prior regressive approaches largely miss, is that introducing sequential dependency fundamentally changes **the structure and efficiency of the token tree**, not just the accuracy of individual predictions. This reframes the problem from "how do we get better speculations?" to "how do we construct higher-quality token trees under compute-bound constraints?"

**What prior work assumed:** The dominant speculative decoding paradigm — whether using independent draft models (Leviathan et al. [13], Chen et al. [6]) or integrated parallel heads like Medusa [5] — treated speculation as a **combinatorial enumeration problem**. Each position in the speculation chain produces a set of candidates, and the verification tree is formed by taking the Cartesian product across positions. This produces exponentially many candidate sequences, most of which are linguistically implausible, because the candidates at position i+1 are not conditioned on what was chosen at position i. The tree grows as O(k^n) for k candidates and n positions. Prior work accepted this explosion as the price of parallel speculation and relied on tree pruning heuristics or simply lived with the redundancy in memory-bound regimes where compute was cheap.

**What Clover recognizes:** By making speculation **regressive** — each head's predictions are conditioned on the specific token chosen by the previous head — the token tree is no longer a Cartesian product. Instead, it becomes a **conditional tree**: for each candidate at position 1, there is a different set of candidates at position 2, and so on. This has a subtle but profound consequence: the tree naturally contains only sequences where each token is linguistically plausible *given its specific predecessor*. The paper captures this in the concept of **"greater information density"** (Section 3.1), a framing that doesn't appear in prior speculative decoding work.

The significance of this reframing goes beyond the metric gains. It shifts the optimization target: rather than asking "how can we afford larger trees?", Clover asks "how can we make smaller trees contain more useful information?" This is precisely the right question for the compute-bound production regime that Figure 2 establishes — where large batch sizes mean additional speculative computation is not free, and tree size must be constrained. The paper empirically validates this logic: even with tree size fixed at 4 (a small budget by research standards, but realistic for production), Clover generates 50–76% more accepted extra tokens per step than Medusa (Figure 6). This means the conditional tree with 4 leaves contains roughly as much "useful speculation" as a Medusa Cartesian tree with 8–12 leaves, because the Medusa tree wastes capacity on implausible token combinations.

This is a **conceptual reframing** rather than a purely architectural innovation. The architectural mechanisms (Regressive Connection, Attention Decoder) are the means, but the intellectual contribution is recognizing that **sequential dependency is a tree-efficiency strategy, not just an accuracy strategy**. This distinguishes Clover from concurrent regressive approaches like Hydra and Eagle, which motivate sequential dependency primarily as a way to improve per-head prediction accuracy, without the same emphasis on tree structure and information density under compute-bound constraints.

The evidence anchoring this claim is Figure 6, which shows Clover's per-step acceptance advantage across ten diverse tasks. The consistent 1.50× to 1.76× ratio of accepted tokens (Clover over Medusa) cannot be explained by accuracy improvements alone — it reflects that Clover's trees waste fewer positions on implausible sequences that verification would reject.

### Innovation 2: The Augmenting Block as an Objective-Mismatch Diagnostic

The Augmenting Block — an additional transformer layer inserted between the frozen target model and the speculative heads — appears at first glance to be a straightforward capacity upgrade: "add more parameters and performance improves." But the paper's ablation analysis (Figure 7b) reveals something more interesting: **the attention sublayer contributes 4.4–5.1% top-5 accuracy to later heads, while the MLP sublayer contributes only 0.7–1.2%**. This asymmetry is not an incidental architectural preference — it constitutes a diagnostic finding about the nature of the gap between pretraining objectives and speculation objectives.

**The diagnostic insight:** The target model was pretrained exclusively to predict the immediate next token. Its hidden states, at every layer, are optimized for features that support next-token prediction. When Medusa (and early Clover) attempts to predict tokens 2, 3, or more positions ahead from these same hidden states, it is using representations that were never shaped for this task. The question the Augmenting Block ablation answers is: *what kind of computation is needed to bridge this gap?*

The answer — that attention dominates and MLP is nearly negligible — tells us something specific. Attention layers compute **position-aware context aggregation**: they can learn to re-weight information across the input sequence based on what's useful for predicting tokens at specific future offsets. For example, an attention head in the Augmenting Block can learn to attend to the main verb when predicting tokens 3–4 positions ahead (where the verb's object or complement is likely), or to attend to a question word when predicting the structure of an answer several tokens later. These are **non-local re-weighting operations** that cannot be performed by the frozen target model's attention layers (which were trained only for next-token prediction) or by simple MLP transformations.

The MLP near-irrelevance is equally diagnostic. MLP layers perform position-independent feature transformations — they can amplify or suppress certain feature dimensions regardless of where in the sequence those features appear. The fact that MLP adds negligible value implies that the gap between next-token-prediction hidden states and multi-token-speculation hidden states is not primarily about having the wrong features (which MLP could correct), but about having the **wrong attention-weighted context aggregation** for positions beyond the immediate next token. The features are present in the hidden states (the model does know about the verb, the question word, etc.), but they're weighted wrong — too much emphasis on the immediate preceding token's context, not enough on the broader structural information needed for longer-range prediction.

**Why this is a conceptual contribution, not just an ablation:** This finding reframes what it means to adapt a pretrained model for speculation. Rather than thinking of speculation as "we need more capacity to predict future tokens" (which would suggest adding MLP layers or deeper heads), the Augmenting Block ablation suggests the problem is specifically about **re-weighting existing features across positions**. This implies that the minimal sufficient augmentation is attention, not general-purpose computation, and that future work on integrated speculators should focus on position-aware context refinement rather than simply adding depth.

The comparison to prior work is instructive. Medusa [5] added no augmentation layer at all — the heads received raw hidden states. Concurrent regressive approaches (Hydra, Eagle) added blocks but did not systematically ablate attention versus MLP contributions, leaving it ambiguous whether the gains came from additional capacity or specifically from attention-based re-weighting. Clover's ablation (Figure 7b) isolates this distinction, making it a diagnostic insight rather than just a performance report.

**Evidence:** Figure 7b, comparing "Attention Only" (+1.9%, +4.4%, +5.1% across heads) to "MLP Only" (+1.0%, +1.2%, +0.7%). The widening gap at later heads is particularly telling — by head 3, attention contributes 5.1% while MLP contributes only 0.7%, a 7:1 ratio. This suggests the re-weighting operation becomes more critical the further ahead you try to predict, which is consistent with the hypothesis that later positions require more restructuring of the input context.

### Innovation 3: Cross-Attention as the Mechanism for Token-Conditioned Context Refinement

While regressive speculators as a category are not unique to Clover (Section 5 catalogs several concurrent approaches: Recurrent Drafter [26], Hydra [2], Eagle [14], Chimera [25]), Clover's specific choice of **cross-attention** as the regressive fusion mechanism — and the ablation evidence for why it outperforms the more obvious MLP-concatenation alternative — constitutes a distinct insight about *how* sequential knowledge should be integrated.

**The default approach in prior regressive speculators:** The Recurrent Drafter [26] uses an MLP layer to combine the previous token embedding with the current hidden state — essentially concatenating the two vectors and passing them through a feedforward network. This is the natural first approach: "we have two pieces of information, let's concatenate them and learn a transformation." It is computationally cheap, architecturally simple, and consistent with how transformers typically handle multi-source inputs.

**Why cross-attention is superior for this specific problem:** Clover's Attention Decoder formulates the fusion differently: the hidden state produces a **query**, and the previous token embedding produces **keys and values**. This means the hidden state *actively interrogates* the token embedding — it computes, for each dimension of its own representation, "how relevant is this aspect of the previous token to my current context?" The result is a **context-dependent selective gating** of the token embedding's information.

The key distinction from MLP concatenation is **adaptivity**. An MLP applies the same learned weights to every (hidden_state, token_embedding) pair. If the previous token is "Bayesian," the MLP must transform the concatenated vector the same way regardless of whether the input sentence is about statistics, machine learning, or the philosopher Thomas Bayes. Cross-attention allows the hidden state (which encodes the full input context) to modulate how the token embedding is incorporated. When the input is about statistics, the query derived from `h_{i-1}` might attend to different dimensions of the "Bayesian" embedding than when the input is about philosophy.

The ablation evidence (Figure 7a, "− Attention Decoder" bars) quantifies this: replacing cross-attention with an MLP regressive block costs 4.8%, 9.0%, and 11.5% top-5 accuracy across the three heads. The **increasing penalty at later heads** is the key diagnostic signal. At head 1, the Attention Decoder processes `e_0` (the actual output token), which is always correct ground truth, so the distinction between attention and MLP is modest (4.8%). By head 3, the Attention Decoder processes `e_2` (a speculated token that may be wrong), and the hidden state `h_2` has accumulated information from two previous fusion steps. At this point, cross-attention's ability to selectively incorporate or suppress information from a potentially incorrect `e_2` — based on whether it's consistent with the accumulated context in `h_2` — provides a much larger advantage (11.5%) than a fixed MLP transformation.

This is not merely an architectural preference; it's a **principled finding about the nature of the fusion problem**. When merging speculative information (which may be erroneous) with context information (which is ground truth), the fusion mechanism needs to be sensitive to the **reliability** of the speculative input. Cross-attention provides this implicitly: if the previous speculated token is incongruent with the context, the attention weights can learn to down-weight it. An MLP cannot dynamically adjust its reliance on the token embedding based on its compatibility with the hidden state.

**Comparison to concurrent approaches:** Neither Hydra nor Eagle, as far as the paper's descriptions indicate, systematically evaluate the choice of fusion mechanism through this lens. The Recurrent Drafter's use of MLP for fusion is directly challenged by Clover's evidence. This makes Clover's contribution less about "we used attention" and more about **"the adaptivity of cross-attention is specifically valuable when merging potentially unreliable speculative information with reliable context"** — a conceptual point with implications for future speculator design beyond the specific architecture.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** Training uses the Baichuan internal supervised fine-tuning (SFT) dataset, containing approximately 0.15B tokens with 95% Chinese content. Evaluation is conducted on a separate internal Baichuan dataset covering ten task categories: retrieval augmentation (RA), multi-turn conversation (MC), code (Code), information processing (IP), creation (CA), logical reasoning (RS), math (Math), tabular (Tab), question answering (QA), and medical suggestion (Med). Each task contains exactly 100 dialogues.

- **Base model(s).** Experiments use two models from the Baichuan family [21]: Baichuan-Small (7B parameters) and Baichuan-Large (over 100B parameters). The paper states these represent different model scales to demonstrate that Clover's advantages persist and actually grow with model size. Both models are kept completely frozen during speculator training.

- **Metrics.** The paper uses two primary metrics: (1) **tokens/step** — the average number of extra tokens (beyond the first, which is always generated by the target model) accepted per verification step, directly measuring speculator accuracy; and (2) **tokens/second** — end-to-end system throughput, which accounts for both the increased tokens per step and the computational overhead of the speculator itself. Top-k accuracy of individual speculator heads is reported in ablation studies only, to provide "more intuitive insight into diverse model architecture" (Section 4.1).

- **Baselines.** Three decoding methods are compared: (1) **Vanilla (auto-regressive) decoding** — the standard approach of generating one token per forward pass with no speculation; (2) **Medusa(Baichuan)** — the Medusa architecture [5] with 3 heads, trained on the same data with the same inference engine, tree construction, and tree sampling algorithm as Clover to ensure "fairness of the comparison" (Section 4.1); and (3) **Clover(Baichuan)** — the proposed method, also with 3 heads. The paper emphasizes that the inference engine, tree construction, and tree sampling algorithm are identical across Medusa and Clover, isolating the architectural differences as the only variable.

- **Generation budget / compute accounting.** Fairness between Medusa and Clover is ensured through two mechanisms: (1) both use identical tree size (set to 4 for all main experiments, validated as the point of diminishing returns in Appendix A.2, Figure 8), and (2) the token tree size is the same across methods, meaning the target model processes the same number of speculative tokens per verification step. The paper does not explicitly account for Clover's additional computational overhead (the Augmenting Block, the serialized Attention Decoder computations) in a budget-constrained comparison — rather, it measures end-to-end throughput (tokens/second) which inherently accounts for all overhead, making the comparison a real-world efficiency evaluation rather than a compute-matched controlled experiment. The batch sizes evaluated span 4, 8, 16, 24, 32, and 48 to cover both memory-bound and compute-bound regimes.

- **Cross-validation / statistical protocol.** The paper does not report any cross-validation or statistical significance testing. The evaluation is straightforward: train once on the SFT dataset, evaluate on the held-out internal benchmark of 10 tasks × 100 dialogues each. Performance is reported as raw metrics without confidence intervals. The absence of multiple training runs or statistical testing is a methodological limitation — we cannot assess the variance of the reported improvements or whether they are statistically reliable at the sample size of 100 dialogues per task.

### Main Quantitative Results

#### End-to-End Throughput: Clover vs. Medusa vs. Vanilla Decoding

The paper reports two categories of end-to-end results: per-step acceptance (tokens/step) and throughput (tokens/second). The full results are split between the main paper (Table 1, covering CA and Math tasks across both model sizes and six batch sizes) and the appendix (Table 2, covering all ten tasks for the Baichuan-Large model only).

**Per-step acceptance (Figure 6, both model sizes):**

Clover consistently generates more accepted extra tokens per step than Medusa across all ten tasks. The vertical axis reports only the extra tokens beyond the first (which is always accepted, since it's the target model's own output). The reported ratios of Clover to Medusa on Baichuan-Small range from 1.50× (Tab task) to 1.66× (CA and Med tasks). On Baichuan-Large, the ratios range from 1.51× (Math) to 1.76× (CA).

The paper summarizes these results as "50% - 76% more extra tokens per step than Medusa method on all tasks." This is the direct evidence for the regressive mechanism's accuracy benefit — each verification step accepts substantially more of Clover's speculations than Medusa's.

Notably, the absolute number of extra tokens per step is modest in all cases. On Baichuan-Small, Clover achieves between approximately 1.5 and 1.7 extra tokens per step across tasks (judging from the bar heights in Figure 6). With a 3-head speculator and a maximum possible of 3 extra tokens per step, this represents a practical acceptance rate in the range of 50–57% of maximum speculation capacity. The remaining ~43% of speculations are rejected during verification and represent wasted computation.

**Throughput on CA and Math tasks (Table 1):**

The headline numbers from the abstract — "up to 91% on Baichuan-Small and 146% on Baichuan-Large" throughput improvement over vanilla decoding — come from the Math task at batch size 4. Specifically:

- Baichuan-Small, Math, bs=4: Clover achieves 232.2 tokens/second vs. vanilla 121.5 → +91%.
- Baichuan-Large, Math, bs=4: Clover achieves 207.3 tokens/second vs. vanilla 84.2 → +146%.

The improvements over Medusa are also pronounced at this batch size:
- Baichuan-Small, Math, bs=4: Clover 232.2 vs. Medusa 187.6 → +23.8% (1.24×).
- Baichuan-Large, Math, bs=4: Clover 207.3 vs. Medusa 159.1 → +30.3% (1.30×).

**Batch size scaling behavior (Table 1):**

A consistent pattern emerges across both model sizes and both tasks: the relative advantage of Clover over Medusa increases with model scale, while the advantage of all speculative methods over vanilla decoding decreases with increasing batch size.

On Baichuan-Small, Math task:
- bs=4: Clover +91% over vanilla, Medusa +54%
- bs=8: Clover +76%, Medusa +46%
- bs=16: Clover +57%, Medusa +50%
- bs=24: Clover +67%, Medusa +32%
- bs=32: Clover **−5%** (underperforms vanilla), Medusa **−18%**
- bs=48: Clover **−21%**, Medusa **−28%**

The transition to negative improvement (speculative decoding being slower than vanilla) at batch sizes 32–48 occurs because the system becomes compute-bound. At large batch sizes, the target model can already saturate the GPU's compute units processing many requests simultaneously, and the additional speculative computation becomes pure overhead without proportional throughput gains.

On Baichuan-Large, Math task:
- bs=4: Clover +146%, Medusa +89%
- bs=8: Clover +103%, Medusa +60%
- bs=16: Clover +81%, Medusa +32%
- bs=24: Clover +62%, Medusa +26%
- bs=32: Clover +63%, Medusa +31%
- bs=48: Clover +36%, Medusa +0%

The larger model maintains positive improvement at larger batch sizes because the target model's forward pass is proportionally more expensive (dominating the speculator overhead), and the memory bandwidth bottleneck is more severe, giving speculative decoding more room to help. The paper explicitly notes this:

> "The advantages of our system over Medusa are even more pronounced for larger model sizes, as the speculator module makes up a smaller proportion of the overall model."

**Clover-to-Medusa throughput ratio across batch sizes (Table 1):**

On Baichuan-Small (Math): Clover/Medusa ratio ranges from 1.09× (bs=32) to 1.24× (bs=4), averaging approximately 1.17× across the four batch sizes where both methods beat vanilla.

On Baichuan-Large (Math): Clover/Medusa ratio ranges from 1.25× (bs=8) to 1.37× (bs=16), averaging approximately 1.30× across all six batch sizes.

The paper reports the maximum Clover/Medusa ratios as "1.26× and 1.47× for Baichuan Small and Baichuan Large, respectively" (Section 4.2), though Table 1 shows the maximums are actually 1.24× on Small (Math, bs=4) and 1.37× on Large (Math, bs=16) — the 1.26× and 1.47× likely come from other tasks shown in Table 2. On CA task: Small max is 1.22× (bs=4), Large max is 1.47× (bs=48). The 1.47× figure for Baichuan-Large appears at bs=48 on the CA task (Clover 938.2 vs. Medusa 638.0), which is notable because it's the largest batch size where Medusa significantly underperforms vanilla (−28%).

**Full task results on Baichuan-Large (Table 2, Appendix A.1):**

The appendix provides throughput numbers for all ten tasks at all six batch sizes on Baichuan-Large. Clover outperforms Medusa in essentially every cell (task × batch size combination). The Clover/Medusa ratios range from approximately 1.10× (e.g., RA task, bs=48: 372.5 vs. 300.3) to 1.47× (CA task, bs=48: 938.2 vs. 638.0).

Several patterns are worth noting:

- **Code tasks** show particularly high absolute throughput: Clover achieves 717.6 tokens/second at bs=48 on Code, vs. 562.3 for Medusa and 539.0 for vanilla. The absolute throughput on code tasks is higher than on conversational tasks (MC: 408.9 at bs=48), likely because code tokens tend to be shorter and more predictable.

- **Math and RS (logical reasoning)** tasks show the strongest relative improvement over vanilla: Clover achieves 1067.8 and 1076.1 tokens/second at bs=48 on Math and RS respectively, while vanilla manages only 780.9 and 984.1. This aligns with the hypothesis that tasks requiring structured reasoning benefit more from accurate multi-token speculation because the output follows more rigid patterns.

- **The cross-over point** where vanilla overtakes Medusa varies by task: For Math, Medusa matches vanilla at bs=48 (781.8 vs. 780.9). For CA, Medusa drops below vanilla at bs=24 (486.8 vs. 515.5). For RA, Medusa stays above vanilla even at bs=48 (300.3 vs. 295.1). Clover generally stays above vanilla longer due to its higher acceptance rate, but also eventually loses advantage at the largest batch sizes for some tasks.

- **Performance fluctuation:** The paper acknowledges "performance fluctuation is due to unpredictable random factors during the inference and a not fully optimized implementation of our engine" (Section 4.2). This is visible in non-monotonic patterns — e.g., on Small, Math, the vanilla baseline jumps from 591.6 at bs=24 to 1202.4 at bs=32, which cannot be explained by batch size scaling alone and suggests measurement noise or engine artifacts.

### Ablation Studies and Robustness Checks

All ablation results are reported as top-k accuracy of individual speculator heads on the Baichuan-Small model. The paper does not report ablation throughput numbers (tokens/second), only accuracy, meaning we cannot directly assess how accuracy changes translate to end-to-end speedups for individual components.

**Ablation of Components (Figure 7a): Starting from complete Clover, components are removed in sequence.**

- **Removing Attention Decoder (replacing with MLP regressive block):** Top-5 accuracy drops by 4.8% (head 1), 9.0% (head 2), and 11.5% (head 3). This is the single largest component-level accuracy loss. The paper attributes this to the MLP's inability to "distinguish different embedding vectors," making it hard to learn valid sequential knowledge. The increasing penalty at later heads (9.0% at head 2, 11.5% at head 3 vs. 4.8% at head 1) supports the interpretation that the attention mechanism's adaptive fusion is particularly valuable when the preceding speculated token (which may be incorrect) must be conditionally integrated with accumulated context.

- **Removing Regressive Connection (after already removing Attention Decoder):** Further top-5 accuracy drops of 2.6% (head 1), 4.6% (head 2), and 6.0% (head 3). After this removal, the architecture has parallel heads receiving the same input, similar to Medusa but still with the Augmenting Block. The accuracy levels at this point are: head 1 at approximately 85%, head 2 at approximately 72%, head 3 at approximately 64% (estimating from the bar chart heights). The staggered losses (2.6% → 4.6% → 6.0%) show that sequential dependency matters more for later heads.

- **Removing Augmenting Block (reducing to Medusa-equivalent):** Final top-5 accuracy drops of 4.3% (head 1), 8.1% (head 2), and 8.9% (head 3). At this point, the architecture is identical to Medusa(Baichuan). The cumulative accuracy loss from complete Clover to Medusa-equivalent is approximately 11.7% (head 1), 21.7% (head 2), and 26.4% (head 3) for top-5 accuracy. These are the numbers quoted in the abstract and conclusion as Clover's accuracy advantage over Medusa.

- **Pattern across heads:** The fact that the majority of Clover's accuracy gain concentrates on later heads (+21.7% and +26.4% for heads 2 and 3 vs. +11.7% for head 1) is the central evidence for the paper's claim that "the auto-regressive mechanism is an effective approach to improve the accuracy of speculation" (Section 6). Head 1 benefits from the Augmenting Block and the larger MLP hidden dimension but does not benefit from sequential dependency (since it's the first head, there's no previous speculation to condition on). Heads 2 and 3 benefit from all three components, including the regressive mechanism, and show proportionally larger gains. This is internally consistent and supports the paper's narrative.

**Exploration of Augmenting Block Architectures (Figure 7b):**

- **Full transformer (Clover default):** Top-5 accuracy of 4.9% (head 1), 9.0% (head 2), 9.4% (head 3) above the "No Augmenting" baseline.

- **Attention only:** Gains of 1.9% (head 1), 4.4% (head 2), 5.1% (head 3). The attention sublayer accounts for roughly 40–55% of the full transformer's gain.

- **MLP only:** Gains of 1.0% (head 1), 1.2% (head 2), 0.7% (head 3). The MLP contribution is small and relatively flat across heads.

- **Interpretation:** The attention sublayer is the dominant source of accuracy gain, and its contribution increases with head depth (1.9% → 4.4% → 5.1%), while the MLP contribution remains approximately constant. This pattern is consistent with the hypothesis that the Augmenting Block primarily works by re-weighting positional context (attention's strength) rather than by adding general-purpose feature transformations (MLP's strength). The paper uses this as justification for making the MLP optional.

**Effect of Token Tree Size (Figure 8, Appendix A.2):**

- On both MC and Math tasks with Baichuan-Small, increasing the token tree size from 2 to 4 to 8 to 16 produces diminishing returns in extra tokens per step for both Clover and Medusa.
- Clover maintains a consistent advantage over Medusa at all tree sizes. On Math, the Clover/Medusa ratio of extra tokens per step ranges from 1.09× to 1.43× across tree sizes, with the largest gap at tree size 4 (approximately 1.43×).
- The paper uses this finding to justify setting tree size to 4: "Since doubling the token tree size brings much more computation and gets closer to the computational bound, we set token tree size to 4 in our evaluation to adapt to the large batch size scenario." This is a practical engineering tradeoff rather than a principled finding, but it's consistent with the production-oriented framing.

**Negative results and unexpected findings:**

- The paper does not explicitly report negative results for Clover components (all components contribute positively), but there are contextual negatives: (1) The "MLP only" Augmenting Block adds negligible accuracy for the computational cost of an entire additional MLP layer, making it a poor design choice if used in isolation. (2) The ReST^EM experiment mentioned in the prior sections (Appendix K) showed that further optimization of the revision model hurt performance — though this is about revisions, not Clover-specific.

- The throughput results at large batch sizes (Table 1, bs=32 and bs=48) show Clover underperforming vanilla decoding in several configurations, which the paper acknowledges but does not analyze in depth. On Baichuan-Small, CA task, bs=48: Clover gets −39% vs. vanilla, meaning speculative decoding is substantially slower than no speculation. This is a genuine limitation — at sufficiently large batch sizes, any speculative overhead becomes net-negative regardless of speculator accuracy.

- The paper does not ablate the **number of speculator heads**. All experiments use exactly 3 heads, matching Medusa's configuration. It would be informative to see whether Clover's regressive mechanism changes the optimal number of heads (potentially allowing more heads since the accuracy decay across heads is reduced) or whether the serialization cost of deeper dependency chains eventually outweighs accuracy gains.

- The paper does not ablate the **shared LM head design**. There is no comparison showing whether sharing the LM head is strictly better than, equal to, or slightly worse than having independent per-head LM heads (as Medusa does). The shared head is motivated by parameter efficiency, but it's possible independent heads could achieve higher accuracy at the cost of more parameters — this trade-off is not quantified.

### Critical Assessment

**Claim 1 from the executive summary: Clover achieves up to 91% throughput improvement over vanilla on Baichuan-Small and 146% on Baichuan-Large.**

The experiments directly support these numbers: Table 1 shows 232.2 vs. 121.5 tokens/second on Baichuan-Small Math at bs=4 (+91%), and 207.3 vs. 84.2 on Baichuan-Large Math at bs=4 (+146%). These are the best-case numbers across all configurations. However, several qualifications are necessary:

- The 91% and 146% figures are **peak improvements at the smallest batch size (bs=4)**. As the batch size increases, the relative improvement declines substantially. At bs=24 on Baichuan-Small Math, the improvement is +67%; at bs=32 it becomes negative (−5%). The abstract's framing as "up to" is technically accurate but potentially misleading — a reader might assume these are typical gains rather than best-case small-batch numbers.

- The improvement is **task-dependent**. On Baichuan-Large at bs=4, Math shows +146% while CA shows +86% (Table 1). The variation across the ten tasks in Appendix A.1 is substantial: from approximately +78% (RA, Clover 120.7 vs. Vanilla 67.9 at bs=4) to +168% (Tab, Clover 178.8 vs. Vanilla 66.7 at bs=4). The abstract's single-number summary obscures this variability.

- The baseline is **vanilla auto-regressive decoding with no speculation heuristics**. A reader might reasonably ask: would a simpler baseline (e.g., using the models with smaller-but-still-independent draft models, or with n-gram-based speculation) already capture a large fraction of the gain? The paper doesn't include non-Medusa speculative baselines because its contribution is specifically about improving integrated speculators over Medusa, but the improvement over "vanilla" is partly a measure of speculative decoding in general, not Clover specifically.

**Claim 2: Clover surpasses Medusa by up to 37% on Baichuan-Small and 57% on Baichuan-Large.**

These numbers appear consistent with the throughput ratios in the tables, though calculating exact percentages is complicated by the fact that the maximum Clover/Medusa ratio varies by task and batch size. On Baichuan-Small Math at bs=4: Clover 232.2 vs. Medusa 187.6 → +23.8%. On Baichuan-Large CA at bs=48: Clover 938.2 vs. Medusa 638.0 → +47.1%. The 57% figure for Baichuan-Large likely comes from a specific task not shown in the main paper.

The more meaningful summary is probably the **range** of Clover/Medusa throughput ratios: approximately 1.10× to 1.47× across all tasks and batch sizes on Baichuan-Large (from Table 2). The average improvement over Medusa is in the 20–35% range, with the 1.47× maximum representing an outlier at a specific batch size where Medusa performs particularly poorly.

**Claim 3: Accuracy gains concentrate on later heads (+21.7% to +26.4% vs. +11.7% for the first head).**

The ablation in Figure 7a directly supports this: the cumulative accuracy difference between full Clover and Medusa-equivalent is approximately 11.7% for head 1, 21.7% for head 2, and 26.4% for head 3 (top-5 accuracy). This pattern is internally consistent with the regressive mechanism's expected behavior: head 1 benefits only from the Augmenting Block (since there's no previous speculation to condition on), while heads 2 and 3 benefit from both the Augmenting Block and the sequential dependency.

However, the paper does not report whether these accuracy gains translate proportionally to throughput gains. It's possible that a 26.4% accuracy improvement on head 3 produces a smaller throughput improvement than a 11.7% improvement on head 1, because head 3's speculations are accepted less frequently overall (later positions are harder to predict correctly). The end-to-end throughput numbers aggregate all effects, making it difficult to isolate the contribution of per-head accuracy improvements to overall speedup.

**Genuine weaknesses in the experimental design:**

**1. No multiple training runs or confidence intervals.** All reported numbers are from a single training run with a fixed random seed. Given the relatively small evaluation set (100 dialogues per task), the measured throughput differences could be affected by training variance or evaluation noise. The paper acknowledges "performance fluctuation due to unpredictable random factors," but reports no error bars, standard deviations, or statistical tests. This makes it impossible to assess whether a 1.22× throughput improvement is reliably distinguishable from, say, a 1.15× improvement.

**2. Single model family, single language distribution.** All experiments use Baichuan models trained on heavily Chinese data (95% Chinese SFT data). The paper does not evaluate on English benchmarks, code generation benchmarks, or any standardized external dataset. This makes it impossible to assess whether Clover's advantages generalize beyond the specific Baichuan architecture and Chinese-language dialogue distribution. The paper's claims are about Clover as a general method, but the evidence supports only Clover-as-applied-to-Baichuan-deployed-on-Chinese-dialogue-tasks.

**3. No comparison to non-Medusa regressive speculators.** The paper positions itself relative to Concurrent regressive approaches (Recurrent Drafter [26], Hydra [2], Eagle [14], Chimera [25]) in Section 5, but does not experimentally compare against any of them. The only baseline is Medusa. This means we cannot assess whether Clover's specific architectural choices (cross-attention decoder, Augmenting Block, shared LM head) provide advantages over other regressive designs — the paper demonstrates that Clover beats Medusa, and that each Clover component improves over not-having-it, but not that Clover's design is superior to alternative regressive architectures.

**4. Training data is proprietary and unreproducible.** The training data is Baichuan's internal SFT dataset, which is not publicly available. This makes it impossible for other researchers to reproduce the exact training conditions or to assess whether Clover's improvements depend on specific properties of this dataset (e.g., the 95% Chinese composition, the distribution of dialogue lengths, the conversation style).

**5. The ablation studies measure top-k accuracy, not throughput.** The ablation analysis (Figures 7a, 7b) reports per-head accuracy changes, which is an intermediate metric. An accuracy improvement of X% on a speculator head does not translate linearly to an X% throughput improvement, because (a) the head's computational overhead changes with architecture, (b) the acceptance rate depends on the interaction between all heads and the target model's verification, and (c) the serialization cost of regressive dependencies increases with head depth. The paper does not close the loop by measuring end-to-end throughput for the ablated configurations, leaving unclear whether the accuracy improvements from individual components are actually worth their computational cost in production.

**6. Limited exploration of tree size and head count.** The tree size is set to 4 based on diminishing returns (Figure 8), and the number of heads is fixed at 3. There is no systematic sweep across (tree size, head count) combinations to find the compute-optimal configuration. It's possible that Clover's regressive mechanism shifts the optimal tree size (since conditional trees have higher information density, a smaller tree might suffice) or the optimal head count (since accuracy decays more slowly across heads, more heads might be justified). This is a missed opportunity to provide prescriptive guidance for practitioners.

**7. The inference engine is described as "not fully optimized."** This admission ("a not fully optimized implementation of our engine") raises questions about whether the absolute throughput numbers are representative of what a production-optimized deployment would achieve, and whether implementation artifacts (e.g., kernel fusion, memory management, batch scheduling) might differentially affect Clover versus Medusa. A poorly optimized engine might exaggerate Clover's relative advantage if Medusa's parallelism is underutilized, or vice versa.

**Missing experiments that would strengthen the paper:**

- **Training data ablation:** Measure Clover's accuracy with varying amounts of SFT training data to establish the data efficiency of the approach. The paper uses 0.15B tokens — would 0.05B suffice? Does Clover require more or less data than Medusa to reach equivalent accuracy?

- **Head count ablation:** Compare Clover and Medusa with 1, 2, 3, 4, and 5 heads to see whether Clover's regressive mechanism changes the optimal tradeoff between speculation depth and per-head accuracy.

- **Latency measurement:** The paper focuses exclusively on throughput (tokens/second), but the regressive mechanism introduces serial dependencies that increase per-step latency. A latency analysis (milliseconds per decoding step, or time-to-first-token vs. time-per-output-token) would clarify whether Clover's throughput gains come at the cost of higher interactive latency, which matters for real-time applications.

- **Comparison to an accuracy-matched Medusa with larger tree size:** If Medusa can achieve the same tokens/step as Clover by simply using a larger token tree (at higher computational cost), a FLOPs-matched comparison would reveal whether Clover's efficiency advantage is architectural or simply a consequence of using a different point on the accuracy-cost curve.

- **Evaluation on standard public benchmarks:** At minimum, evaluation on a subset of English tasks (e.g., GSM8K for math, HumanEval for code, MT-Bench for conversation) would allow cross-model comparisons and establish whether Clover's claims hold beyond the Baichuan ecosystem.

## 6. Limitations and Trade-offs

### Single Model Family, Single Language, Proprietary Evaluation

**The assumption or constraint:** All experiments are conducted on two models from the Baichuan family (7B and 100B+ parameters), trained and evaluated on Baichuan's internal datasets with a 95% Chinese composition. The paper acknowledges this implicitly by restricting its claims to "Baichuan-Small" and "Baichuan-Large" models, but it frames Clover as a general method applicable to "large language models" without qualification (Section 1):

> "We conducted experiments on both Baichuan-Small (with 7B parameters) and Baichuan-Large (with over 100B parameters)."

The evaluation uses ten proprietary internal task categories, each with 100 dialogues, and training uses a non-public 0.15B-token SFT dataset (Section 4.1). No public benchmark (GSM8K, HumanEval, MT-Bench, or any English dataset) is evaluated.

**The consequence:** A practitioner considering Clover for an English-language model (e.g., Llama, Mistral, Qwen) or a different architecture family cannot determine from this paper whether the reported gains transfer. The 95% Chinese training distribution may interact with Clover's architectural choices in unknown ways — for instance, Chinese tokenization produces different token boundaries and vocabulary statistics than English, which could affect speculator head accuracy and the relative benefit of sequential dependency. The proprietary evaluation suite further prevents independent verification: no external researcher can reproduce the throughput numbers or assess whether the ten task categories adequately represent production workloads. The paper effectively demonstrates "Clover works on Baichuan models deployed on Baichuan's internal Chinese dialogue tasks," but provides no evidence for the broader claim that Clover is a general improvement over Medusa.

**What evidence exists in the paper:** The limitation is structural — all tables (Table 1, Table 2) and figures (Figure 6, 7) report results exclusively on Baichuan models with Baichuan datasets. The paper does not claim to evaluate on public benchmarks, nor does it discuss the language distribution as a potential confound. Section 5 references concurrent regressive approaches (Hydra, Eagle, Chimera) but does not experimentally compare against them, meaning we cannot assess whether Clover's specific design choices outperform alternative regressive architectures that have been validated on English models and public benchmarks.

**Mitigation status:** Not addressed. The paper does not acknowledge the single-family, single-language limitation, nor does it suggest evaluation on public benchmarks as future work. The availability of only two model sizes within the same family is presented as a strength (demonstrating scaling behavior) rather than noted as a constraint on generalizability.

---

### Training Data Is Proprietary and Unreproducible

**The assumption or constraint:** Both Medusa(Baichuan) and Clover(Baichuan) are trained on "the Baichuan internal supervised fine-tuning (SFT) dataset, containing approximately 0.15B tokens, 95% of which are Chinese" (Section 4.1). This dataset is not publicly available, and the paper provides no information about its construction, distribution of task types, dialogue lengths, or quality filtering. The evaluation dataset is similarly proprietary: "another internal Baichuan dataset" with ten named categories but no examples or descriptive statistics beyond "each of the ten tasks contains 100 dialogues" (Section 4.1).

**The consequence:** Independent reproduction of Clover's results is impossible. A researcher or practitioner attempting to apply Clover to their own model must guess at the appropriate training data characteristics — is the 0.15B token figure necessary, or would 0.05B suffice? Does the SFT data distribution (dialogue format, response length, topic diversity) materially affect speculator head accuracy? The ablation study (Figure 7) reports per-head accuracy but provides no guidance on how accuracy varies with training data quantity or composition. This is particularly consequential because speculative head training is a form of behavioral cloning from the frozen target model's representations: if the training data does not cover the types of sequences the model will encounter in deployment, the speculators may be poorly calibrated for those scenarios. Without data transparency, practitioners cannot assess whether their own training datasets match the conditions under which Clover was validated.

**What evidence exists in the paper:** Section 4.1 states the dataset size and language composition but provides no further detail. The paper does not ablate training data quantity, data composition, or data quality. There is no comparison of Clover trained on SFT data versus pretraining data versus task-specific data — all training uses the same 0.15B-token SFT corpus. The training duration (1 epoch) is reported, but without knowing the data distribution, it is unclear whether this represents underfitting, appropriate fitting, or potential overfitting.

**Mitigation status:** Not addressed. The paper does not flag proprietary data as a limitation and does not suggest public dataset evaluations as future work. Given that Medusa — Clover's primary baseline — was validated on public benchmarks (Vicuna, MT-Bench), the absence of any public evaluation is a notable gap in reproducibility.

### No Latency Analysis Despite Serialized Speculation

**The assumption or constraint:** Clover's central architectural innovation — the Regressive Connection — replaces Medusa's parallel head computation with a sequential chain where each head depends on the output of the previous head. The paper explicitly acknowledges this serialization cost (Section 3.1):

> "Although the critical path of the computation becomes proportional to the depth of the speculation and loses a certain amount of parallelism, the increase in speculation accuracy rather improves the overall latency."

The paper then measures only **throughput** (tokens/second), which is a system-level metric that can be improved by increasing batch size or amortizing overhead across many concurrent requests. It never reports **latency** (milliseconds per token, time-to-first-token, or per-step decoding time), which is the user-facing metric for interactive applications.

**The consequence:** Throughput and latency are not interchangeable. The serialized Attention Decoder chain means that for a single request, Clover takes strictly longer to generate speculations than Medusa (which computes all heads in parallel), because head 3 cannot begin computing until head 2 has produced its token embedding `e_2`, and head 2 cannot begin until head 1 has produced `e_1`. In a low-batch-size interactive setting (single user, single request), this serialization penalty could make Clover **slower** than Medusa at producing the first few tokens, even if it eventually catches up through higher acceptance rates. The paper's claim that "the increase in speculation accuracy rather improves the overall latency" is asserted, not demonstrated — there is no latency measurement anywhere in the paper to support it.

The practical concern: throughput gains from higher batch sizes (the regime where the paper's experiments excel) are valuable for batch processing and high-traffic serving, but interactive applications (chatbots, coding assistants, real-time translation) care about per-request responsiveness. A practitioner deploying Clover in an interactive setting cannot determine from this paper whether the per-token latency is acceptable or whether the regressive mechanism introduces a noticeable delay between user input and first response token.

**What evidence exists in the paper:** No latency measurements are reported. All evaluation metrics are tokens/second at batch sizes ranging from 4 to 48 (Table 1, Table 2) and extra tokens per step (Figure 6). The paper does not report time-to-first-token, per-step decoding wall-clock time, or any metric that isolates the speculative head computation from the target model's verification. The "not fully optimized implementation" admission (Section 4.2) further complicates latency assessment — implementation artifacts (e.g., kernel launch overhead, memory allocation patterns) could disproportionately affect the serialized Clover heads versus the parallel Medusa heads.

**Mitigation status:** Not addressed. The paper frames the parallelism-accuracy tradeoff as settled in favor of accuracy but provides no empirical evidence for this claim. No latency experiment is conducted, and no guidance is given for practitioners who need to choose between Clover and Medusa based on latency constraints rather than throughput.

### Difficulty Estimation and Adaptation Are Completely Absent

**The assumption or constraint:** Clover applies the same speculation strategy (3 heads, fixed tree size of 4, fixed sequential chain depth) to every input, regardless of the prompt's content, the task type, or the base model's confidence. The method has no mechanism for assessing whether a particular prompt is "easy" (where aggressive speculation might safely use more heads or larger trees) or "hard" (where speculation is likely to generate incorrect tokens that waste verification computation). The paper acknowledges that throughput improvements vary dramatically across tasks — from +168% on Tabular to +78% on RA at bs=4 on Baichuan-Large (Table 2) — but does not investigate _why_ some tasks benefit more than others or how to allocate the speculation budget accordingly.

**The consequence:** Clover wastes computation in two directions. On tasks where the base model's outputs are highly predictable (e.g., code with rigid syntax, or structured data extraction), the speculators likely achieve high acceptance rates, and a more aggressive configuration (more heads, larger trees, deeper sequential chains) could extract additional throughput. On tasks where outputs are unpredictable (creative writing, open-ended reasoning), the speculators likely achieve low acceptance rates, and the computational overhead of the Augmenting Block and serialized Attention Decoder may be net-negative — the system would be better served by reducing tree size, using fewer heads, or falling back to vanilla decoding entirely.

The paper's fixed configuration (3 heads, tree size 4) represents a one-size-fits-all compromise that leaves efficiency on the table across the task distribution. A practitioner cannot determine from this paper how to set these hyperparameters for their own workload, or whether an adaptive strategy that adjusts speculation depth based on online acceptance-rate monitoring would outperform the static configuration.

**What evidence exists in the paper:** The task-level variation in throughput improvement is visible in Table 2 — Clover achieves 717.6 tokens/second on Code at bs=48 versus only 372.5 on RA at the same batch size, but this variation is not analyzed, and no per-task acceptance rates or per-task optimal configurations are reported. Figure 6 shows accepted tokens per step varying from ~1.5 to ~1.7 across tasks, but this is a narrow range that may not capture the full difficulty spectrum (the internal Baichuan dataset's difficulty distribution is unknown). The paper does not stratify results by prompt length, output length, or any measure of task difficulty.

**Mitigation status:** Not addressed. The paper does not propose or evaluate any adaptive strategy, difficulty estimation mechanism, or hyperparameter selection heuristic. The tree-size analysis (Appendix A.2, Figure 8) sweeps a single hyperparameter but does so globally rather than per-task, and does not connect tree size to any task characteristic that could guide deployment decisions.

### The FLOPs Comparison Is Asymmetric and the Baselines Are Weak

**The assumption or constraint:** Clover is compared against Medusa using identical tree size (4) and head count (3), ensuring that the target model processes the same number of speculative tokens per verification step. However, this comparison does **not** account for Clover's additional computational overhead: the Augmenting Block (an entire additional transformer layer, roughly 1/N_layers of total inference FLOPs), the serialized Attention Decoder computations (three additional cross-attention operations per verification step), and the increased memory footprint of these additional parameters. The paper measures tokens/second, which inherently captures all overhead, but the **baseline is not optimized** for the comparison: Medusa could be configured with a larger tree size (using the computational budget that Clover spends on its Augmenting Block) to achieve higher acceptance rates, potentially narrowing or closing the throughput gap.

**The consequence:** The reported Clover-to-Medusa throughput ratios (1.10× to 1.47×) represent a comparison between **Clover with augmentation** and **Medusa without augmentation**, not a comparison at equal computational cost. A FLOPs-matched comparison — e.g., Clover with tree size 4 versus Medusa with tree size 6 or 8 (using the FLOPs saved by not having an Augmenting Block or regressive attention) — would answer the question a practitioner actually faces: "given a fixed computational budget per verification step, should I spend it on Clover's architectural improvements or on a larger Medusa token tree?" This experiment is not conducted.

The paper's own analysis (Figure 8, Appendix A.2) shows that increasing tree size improves Medusa's accepted tokens per step, albeit with diminishing returns. The trend is not flat: doubling tree size from 2 to 4 produces a meaningful gain. A FLOPs-matched Medusa with a larger tree might recover a substantial fraction of Clover's advantage, but we cannot determine how much from the reported experiments.

**What evidence exists in the paper:** The tree-size analysis (Figure 8) shows Medusa's extra tokens per step increasing from approximately 0.85 at tree size 2 to approximately 1.05 at tree size 4 on Math, and from approximately 0.95 to 1.15 on MC. No FLOPs accounting is provided for the Augmenting Block or Attention Decoder. The paper does not measure or report the relative computational cost of Clover's speculator versus Medusa's speculator, making it impossible to construct a FLOPs-matched comparison from the reported data. The statement that the Augmenting Block incurs "approximately 1/N_layers of inference time" (Section 3.3) is the only cost estimate provided, and it is not validated experimentally.

**Mitigation status:** Partially addressed through the choice of throughput (tokens/second) as the primary metric, which does account for all overhead in the end-to-end measurement. However, the question is not whether Clover's overhead is _included_ in the measurement (it is), but whether the comparison is _fair_ — i.e., whether Medusa is given an equivalent computational budget to achieve its best performance. The paper does not conduct a FLOPs-matched sweep, does not report Clover's per-step computational cost relative to Medusa, and does not justify why tree-size-equated rather than FLOPs-equated comparison is the appropriate evaluation framework. A practitioner reading this paper cannot determine whether the 1.10×–1.47× throughput advantage represents genuine architectural superiority or simply a larger effective computational budget per verification step.

### Evaluation Set Size and Statistical Reliability

**The assumption or constraint:** All evaluation is conducted on 100 dialogues per task across ten tasks, for a total of 1,000 evaluation examples. Throughput measurements (tokens/second) are reported as point estimates without confidence intervals, standard deviations, or any indication of measurement variance. The paper acknowledges measurement noise (Section 4.2):

> "The performance fluctuation is due to unpredictable random factors during the inference and a not fully optimized implementation of our engine."

Despite this acknowledgment, no statistical treatment is applied.

**The consequence:** The reported throughput numbers have unknown reliability. Non-monotonic patterns in the data — such as the vanilla baseline on Baichuan-Small Math jumping from 591.6 tokens/second at bs=24 to 1202.4 at bs=32 (Table 1), a physically implausible 2× increase from adding 8 more concurrent requests — suggest substantial measurement noise or engine artifacts. If the baseline can vary by a factor of 2 due to "unpredictable random factors," then a 1.22× Clover-to-Medusa improvement at a single batch size cannot be confidently distinguished from noise. The small evaluation set (100 dialogues per task) further amplifies this concern: rare but impactful events (e.g., a single very long or very short dialogue) can meaningfully shift average throughput in a 100-example sample.

For a practitioner deciding whether to adopt Clover over Medusa, the key statistics are not the best-case improvement at the most favorable batch size (e.g., +47% on CA at bs=48) but the **expected improvement across their workload distribution**, with an estimate of variance. This paper provides only point estimates from a single run, making the expected improvement unknowable.

**What evidence exists in the paper:** The anomalous vanilla baseline jump (591.6 → 1202.4 tokens/second at bs=24 → bs=32 on Baichuan-Small Math) is visible in Table 1 but is not discussed, investigated, or explained. The paper does not report any form of statistical analysis — no error bars, no multiple runs, no significance tests. The training procedure involves a single run with a single random seed. The admission of "unpredictable random factors" suggests the authors are aware of measurement instability but chose not to address it methodologically.

**Mitigation status:** Not addressed. The paper does not propose any statistical methodology, does not report multiple runs, and does not qualify its numerical claims with confidence bounds. The limitation is acknowledged indirectly through the "performance fluctuation" note, but this acknowledgment is not accompanied by any mitigation. A practitioner must treat all reported throughput numbers as suggestive rather than definitive, and should expect potentially different results when deploying on their own hardware with their own engine implementation.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

Clover does not introduce a paradigm shift — speculative decoding was already established as the primary solution to the memory-bandwidth bottleneck, and regressive speculators were already being explored concurrently by Hydra [2], Eagle [14], and Chimera [25]. Rather, Clover makes two specific contributions that refine the research direction: **a diagnostic decomposition of where sequential knowledge matters**, and **a reframing of regressive speculation as a tree-efficiency strategy for compute-bound regimes**.

**The diagnostic contribution** is the most durable part of the paper. The ablation in Figure 7a decomposes Clover's accuracy advantage over Medusa into component-level contributions, revealing a stark pattern: the cumulative gain is +11.7% top-5 accuracy for head 1, but +21.7% and +26.4% for heads 2 and 3. This is not an obvious result — one could have hypothesized that sequential dependency would provide a uniform benefit across all positions, or that the Augmenting Block would dominate. The finding that the majority of Clover's advantage concentrates on later heads, and that cross-attention fusion contributes roughly twice as much as the Augmenting Block at head 3 (11.5% vs. ~9.4%), provides a concrete architecture-level lesson: **if you can only afford one modification to a Medusa-style speculator, replace the parallel MLP heads with cross-attention regressive heads; if you can afford two, add an Augmenting Block.**

This decomposition matters because it tells subsequent researchers which components are worth porting to new architectures (cross-attention regressive fusion appears highly transferable) and which are more situational (the Augmenting Block's attention sublayer contributes the bulk of its gain, and its marginal benefit beyond cross-attention is modest at ~4–5% per head). The paper's finding that the MLP sublayer of the Augmenting Block contributes only 0.7–1.2% top-5 accuracy (Figure 7b) is a negative result that is itself valuable: it tells future work not to waste parameters on additional feedforward layers when attention-based re-weighting is the bottleneck.

**The compute-bound reframing** is more subtle but potentially more impactful for deployment-oriented research. Prior speculative decoding work, including Medusa and most concurrent regressive approaches, implicitly targeted the memory-bound regime where large token trees are free (in terms of compute) and the goal is maximizing accepted tokens per step. Clover explicitly argues — and Figure 2 provides evidence — that production deployments at large batch sizes are compute-bound, making tree size a scarce resource. The conceptual shift is from "how do we generate more speculative tokens?" to **"how do we make each position in a small tree more likely to contain a correct token?"** The regressive connection is not merely an accuracy trick — it is a **tree structure optimization** that increases the information density of a fixed-size token budget by eliminating branches corresponding to linguistically implausible token combinations.

This reframing has a specific methodological implication: evaluations should be conducted at **production-realistic batch sizes** (Clover evaluates up to bs=48) with **constrained tree sizes** (fixed at 4, validated by diminishing returns in Figure 8), and the primary metric should be **throughput (tokens/second)** rather than accepted length (tokens/step), because throughput accounts for speculator overhead. Future speculative decoding papers that continue to evaluate only at batch size 1 with unlimited tree sizes are optimizing for a regime that does not match production serving — Clover's results provide the empirical justification for changing this norm.

**Contradictions Clover reconciles:** The paper implicitly reconciles a tension in the speculative decoding literature between "independent heads are efficient because they compute in parallel" (Medusa's design philosophy) and "sequential heads are accurate because they condition on context" (the regressive speculator design philosophy). Clover's measured throughput results — 1.10× to 1.47× over Medusa across production batch sizes — demonstrate that the accuracy gain from sequential dependency outweighs the serialization penalty in end-to-end throughput, at least for the Baichuan model family on the evaluated task distribution. This is not a theoretical resolution but an empirical one: the debate is settled by measurement, not by argument.

**Research directions that become more attractive:**

- **Cross-attention as the default fusion mechanism for multi-source speculation.** Clover's ablation (4.8–11.5% top-5 accuracy advantage of attention over MLP for regressive fusion) provides strong evidence that adaptive, query-key gating is superior to fixed concatenation when merging speculative information with context. Future regressive speculators should default to attention-based fusion and justify any deviation.
- **Attention-based feature augmentation for speculative heads.** The Augmenting Block ablation (Figure 7b) establishes that attention contributes the majority of the accuracy gain while MLP is nearly negligible. This suggests a leaner augmentation strategy: append a single attention sublayer (no MLP) between the target model and the speculator heads, trading a small accuracy loss (~1% top-5) for reduced memory and latency overhead.
- **Tree-efficiency analysis as a standard evaluation dimension.** Clover introduces the concept of "information density" for token trees but does not formalize it. A metric like "accepted tokens per tree position" would allow systematic comparison of tree construction strategies across methods and would naturally reward regressive approaches that eliminate implausible branches.

**Research directions that become less attractive:**

- **Further parameter scaling of independent parallel speculator heads.** Clover's regressive mechanism achieves +21.7% to +26.4% top-5 accuracy on later heads by adding sequential dependency — a gain that would be difficult to match by simply making Medusa heads deeper or wider while keeping them independent. The ablation shows that removing Clover's components in sequence (Figure 7a) produces monotonically decreasing accuracy, with the final Medusa-equivalent configuration substantially below Clover. This suggests that independent parallel heads are hitting diminishing returns that architectural change (sequential dependency) can overcome more efficiently than capacity scaling.
- **Large Cartesian-product trees as a research target.** Clover's production-oriented evaluation (tree size 4, batch sizes up to 48) and the diminishing returns documented in Figure 8 suggest that the regime of "unlimited tree size at batch size 1" is a research artifact rather than a deployment reality. Work that proposes methods whose primary advantage manifests only at large tree sizes should be evaluated against Clover's efficiency baseline, not just against Medusa with equivalent tree budgets.

### Follow-Up Research This Work Enables

**1. FLOPs-matched comparison of Clover against tree-expanded Medusa.** The paper compares Clover against Medusa at identical tree size (4) and head count (3), but Clover has additional computational overhead: one Augmenting Block (an entire transformer layer) and three serialized cross-attention operations per verification step. The natural question is whether Medusa, given the equivalent additional FLOPs budget — say, by expanding the tree size from 4 to 8 or the head count from 3 to 4 — would match or exceed Clover's throughput. A FLOPs-matched sweep would measure Clover at tree size 4 versus Medusa at tree sizes {6, 8, 10, 12} (estimating the Augmenting Block as equivalent to 1/N_layers ≈ 3% of total inference FLOPs) and identify the crossover point where tree expansion compensates for architectural simplicity. If Medusa matches Clover at some FLOPs-equivalent tree size, Clover's contribution is primarily about tree-efficiency (achieving the same acceptance with a smaller, more manageable tree) rather than absolute throughput superiority. If Clover maintains an advantage even against FLOPs-matched Medusa, the architectural improvements are genuinely more FLOP-efficient.

**2. Cross-model-family replication on English benchmarks.** All Clover results are on Baichuan models with 95% Chinese training data. A strong replication study would train Clover heads on Llama-3 (8B and 70B) or Mistral (7B) using a public English SFT dataset (e.g., ShareGPT, OpenHermes) and evaluate on standard speculative decoding benchmarks: MT-Bench for conversation, HumanEval for code, GSM8K for math. The key measurements would be: (a) whether the head-level accuracy advantage pattern (+11.7% head 1, +21.7% head 2, +26.4% head 3) replicates across model families with different architectures, tokenizers, and training data; (b) whether the throughput improvement over Medusa at production batch sizes (16–48) is consistent in magnitude or varies with model family; and (c) whether the relatively small English proportion of the training data (5% in Clover's case) materially affects English-task performance — a finding that would inform data composition recommendations for practitioners.

**3. Head count and speculation depth optimization under latency constraints.** Clover fixes head count at 3 (matching Medusa) and never varies this parameter. The regressive mechanism fundamentally changes the tradeoff: in Medusa, adding heads costs minimal additional latency (all heads compute in parallel) but produces rapidly declining accuracy, making 3–4 heads the practical limit. In Clover, adding heads increases serialization depth (each head must wait for the previous head's Attention Decoder and token embedding), but accuracy decays more slowly because each head benefits from sequential context. A latency-aware sweep across head counts {2, 3, 4, 5, 6} measuring both throughput and per-step wall-clock time would identify whether Clover's optimal depth is different from Medusa's. The hypothesis is that Clover can productively use more heads (4–5 vs. Medusa's 3) because accuracy holds up better, and the additional serialization is amortized over the higher acceptance rates. This experiment would also clarify whether the paper's "1.26×–1.47× throughput advantage" could be widened further by increasing head count beyond 3 — or whether serialization eventually catches up.

**4. Dynamic tree size and depth allocation based on online difficulty estimation.** Clover applies a fixed speculation strategy (3 heads, tree size 4) to all inputs, but Figure 6 shows task-level variation in acceptance rates, and Table 2 shows task-level variation in throughput improvement (from +78% on RA to +168% on Tab at bs=4). A natural extension is to estimate input difficulty online — for instance, by monitoring the acceptance rate of the first few speculation steps and using it to adjust tree size or head count for the remainder of the response. The specific experiment: during a single response generation, start with a conservative configuration (tree size 2, 2 heads). If the observed acceptance rate exceeds a threshold (say, 0.6), increase to tree size 4 with 3 heads for subsequent steps. If it drops below 0.3, fall back to vanilla decoding with no speculation. Measuring the throughput of this adaptive strategy against static Clover and static Medusa would quantify the value of difficulty-conditioned allocation — a concept explored in the test-time compute scaling literature but not yet applied to speculative decoding hyperparameters. The paper's existing data (task-level variation in Figure 6 and Table 2) provides the motivation and the baselines for this experiment.

**5. Ablation of shared versus independent LM heads with parameter-matched budgets.** Clover uses a shared LM head (the target model's original frozen lm_head) for all speculative heads, while Medusa trains independent per-head lm_heads. The paper motivates this by parameter efficiency but never experimentally compares shared versus independent heads at equal parameter budgets. A controlled experiment would compare three configurations: (a) Clover with shared LM head (the current design); (b) Clover with independent per-head lm_heads (architecturally identical to Medusa heads but with regressive connection and Augmenting Block); and (c) Medusa with shared LM head (adding the shared-head design to the baseline). This would isolate whether the shared LM head is a genuine contributor to Clover's accuracy advantage (by ensuring output-space consistency with the target model) or merely a parameter-saving convenience that has neutral or slightly negative accuracy impact. If independent heads outperform shared heads given equal overall parameter budgets, a Clover variant that uses independent heads but retains the regressive connection and Augmenting Block could achieve even higher throughput — a finding that would directly improve the method.

**6. Speculator overhead profiling to identify the throughput ceiling for regressive approaches.** The paper measures end-to-end throughput but never breaks down where time is spent: what fraction of per-step latency goes to the target model's forward pass, the Augmenting Block, the serialized Attention Decoder chain, tree verification, and token sampling? A detailed latency breakdown — measured via GPU kernel profiling (e.g., NVIDIA Nsight, PyTorch Profiler) — would reveal whether the Augmenting Block (estimated at ~3% overhead) and the Attention Decoder (claimed as "negligible") are accurately characterized. More importantly, it would identify the scaling limit: at what batch size and tree size does the serialized speculator chain become the latency bottleneck, and does this crossover point depend on model size? This profiling data is essential for practitioners deciding whether to deploy Clover in latency-sensitive interactive settings versus throughput-oriented batch processing settings. The paper's "not fully optimized implementation" admission makes this profiling particularly urgent — a well-optimized kernel implementation might shift the latency profile substantially, potentially making the serialization penalty smaller than the current throughput numbers suggest.

### Practical Applications and Downstream Use Cases

**1. Production LLM serving at scale for dialogue and coding assistants.** The paper's explicit focus on large batch sizes (up to bs=48) and constrained tree sizes (tree size 4) directly targets real-time LLM serving infrastructure where multiple user requests are batched together. A deployment team operating a 100B+ parameter model (similar to Baichuan-Large) for customer-facing chatbots or code completion would see Clover's throughput improvements translate directly to serving capacity: the 1.47× improvement over Medusa at bs=48 on creation tasks (Table 1: 938.2 vs. 638.0 tokens/second) means the same GPU hardware can serve approximately 47% more concurrent users before latency degrades. On math and reasoning tasks, the 1.37× improvement at bs=16 (Table 1: 549.5 vs. 401.3 tokens/second) provides headroom for computationally intensive workloads. For a deployment processing millions of requests per day, this translates to reduced GPU-hours, lower infrastructure costs, or higher throughput under existing hardware constraints. The key deployment consideration is that Clover's advantage is largest precisely in the compute-bound regime (medium-to-large batch sizes) that production systems actually operate in — the "up to 146%" headline number at bs=4 is less relevant than the sustained 20–40% improvement at production batch sizes (16–48).

**2. Offline batch inference for data generation and evaluation pipelines.** When LLMs are used to generate training data (for distillation, instruction tuning, or RLHF), process large document corpora, or evaluate benchmark suites, the workload is throughput-constrained rather than latency-constrained — the goal is to process as many tokens as possible within a compute budget. Clover's throughput advantage (1.10× to 1.47× over Medusa, Table 2) directly reduces the cost and time of these batch operations. For a concrete scenario: generating 1 billion tokens of synthetic training data with a Baichuan-Large model using Medusa at bs=32 on math tasks would take approximately 1 billion / 706 tokens/second ≈ 393 GPU-hours. Clover at the same batch size achieves 874 tokens/second, reducing this to approximately 318 GPU-hours — a savings of 75 GPU-hours per billion tokens, or roughly 3 full GPU-days on an 8-GPU node. For organizations running regular data generation pipelines, this cost reduction accumulates significantly over time.

**3. Deployment of large models on bandwidth-constrained hardware.** The paper shows that Clover's advantage over Medusa increases with model scale — from 1.26× maximum on Baichuan-Small (7B) to 1.47× maximum on Baichuan-Large (100B+). This scaling trend suggests Clover is particularly valuable for the largest deployable models, where the memory-bandwidth bottleneck is most severe and the speculator's overhead (as a fraction of total computation) is smallest. For edge deployment scenarios where a large model must run on hardware with limited memory bandwidth (e.g., inference on consumer GPUs, or multi-GPU setups with inter-GPU communication bottlenecks), Clover's higher acceptance rate means fewer expensive forward passes through the target model, reducing both latency and the total volume of weight transfers. A team deploying a quantized 70B model on 4× consumer GPUs would benefit proportionally more from Clover's accuracy improvements than a team running a 7B model on a single datacenter GPU, because the target model's forward pass dominates total latency more completely at larger scales. The paper's training cost (2 hours on 8× A800 for 7B, 2 hours on 32× H800 for 100B+) is a one-time investment that pays back through sustained inference throughput improvements.

**4. Hybrid deployment with adaptive fallback for diverse workloads.** Clover's performance varies across task types (Table 2 shows +78% to +168% improvement over vanilla at bs=4), which suggests a deployment strategy where Clover is selectively enabled for tasks where it provides the largest gains (code, math, tabular reasoning, logical reasoning) and disabled (or reconfigured with smaller tree size and fewer heads) for tasks where gains are modest (retrieval augmentation) or where the speculator overhead becomes net-negative at very large batch sizes. A production router could classify incoming requests by task type (using a lightweight classifier or the system prompt) and apply different Clover configurations, or fall back to Medusa or vanilla decoding, based on pre-measured per-task throughput characteristics. Table 2 provides the necessary data to make these routing decisions — for each of the ten task categories and six batch sizes, a practitioner can look up whether Clover, Medusa, or vanilla decoding maximizes throughput and configure their serving system accordingly. This is a direct operational application of the paper's per-task throughput breakdown, which is more actionable than the aggregate "1.26×–1.47× over Medusa" claim.
