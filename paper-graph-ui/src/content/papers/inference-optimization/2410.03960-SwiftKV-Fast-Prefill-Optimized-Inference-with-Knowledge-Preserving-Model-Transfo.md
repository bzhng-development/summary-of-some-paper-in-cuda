# SwiftKV: Fast Prefill-Optimized Inference with Knowledge-Preserving Model Transformation

**ArXiv:** [2410.03960](https://arxiv.org/abs/2410.03960)

## 🎯 Pitch

Later transformer layers barely change hidden states—SwiftKV exploits this to skip up to half the layers during prompt processing, slashing prefill compute by 50% with under 2% accuracy loss. The key trick: training tiny, lightweight projections to generate accurate KV caches for skipped layers directly from an early layer’s output, then distilling knowledge back using under 1B tokens. In production settings with long prompts, this doubles throughput and cuts time-per-token by 60%, hitting 560 TFlops/GPU on Llama-3.1-70B.

---

## 1. Executive Summary

SwiftKV introduces a model transformation and distillation procedure that reduces prefill computation in large language models by rewiring later transformer layers to derive their KV cache from an earlier layer's output, allowing prompt tokens to skip those later layers entirely during the prefill phase. The paper evaluates SwiftKV across several model families—including Llama-3.1-Instruct (3B to 405B), Qwen2.5-14B-Instruct, Mistral-Small, and Deepseek-V2-Lite-Chat—on standard benchmarks such as ARC-Challenge, Winogrande, HellaSwag, TruthfulQA, MMLU, and GSM8K. SwiftKV combines three mechanisms: a **model transformation** that projects KV cache for skipped layers from the last unskipped layer's hidden state (reducing prefill compute by 25–50%), an optional **AcrossKV** strategy that merges KV caches across consecutive skipped layers (achieving up to 46.875% KV cache memory reduction), and a **knowledge-preserving distillation procedure** that trains only the Q, K, and V projection weights (<10% of model parameters) on under 1B tokens to recover accuracy. The method achieves up to 2× higher aggregate throughput and 60% lower time-per-output-token in end-to-end inference serving, with minimal accuracy degradation (<1–2% on average), while reaching 560 TFlops/GPU of normalized inference throughput for Llama-3.1-70B—establishing that prefill-dominated enterprise workloads can benefit substantially from this approach, though gains diminish on harder problems and for model families with lower inter-layer hidden-state similarity at deeper layers.

## 2. Context and Motivation

### The Core Problem: Prefill Dominance in Enterprise LLM Workloads

The fundamental motivation for SwiftKV is an empirical observation about how large language models are actually used in production enterprise settings: **prompts are substantially longer than the generated responses**. The paper reports that typical enterprise workloads—code completion, text-to-SQL, summarization, and retrieval-augmented generation (RAG)—exhibit roughly a 10:1 ratio of input to output tokens, with average prompt lengths between 500 and 1,000 tokens observed in Snowflake's own production deployments (Section 1).

This matters because transformer inference has two computationally distinct phases:

- **Prefill**: The model processes the entire input prompt in parallel, computing keys (K), values (V), and queries (Q) for every token through every layer. This is typically compute-bound because it involves dense matrix multiplications across all tokens and all layers simultaneously.
- **Decode**: The model generates one output token at a time, attending to all previously computed K and V (stored in a KV cache) while only computing Q, K, and V for the single new token. This is typically memory-bound because the per-token computation is small, but the entire KV cache must be read from memory at each step.

When prefill dominates—as it does in the 10:1 input-to-output ratio the paper observes—the total cost of inference (in FLOPs, latency, and throughput) is disproportionately determined by how efficiently the system can process prompt tokens. Reducing prefill computation therefore emerges as the highest-leverage target for improving end-to-end inference performance.

This is not a niche observation. The paper situates it in the broader context of LLM economics: "the cost and speed of inference determine their practicality" (Section 1). For enterprise deployments where models serve thousands or millions of requests daily, the total FLOPs spent on prefill directly translates to hardware provisioning costs, energy consumption, and user-facing latency. A method that reduces prefill FLOPs by 25–50% without meaningfully degrading output quality is therefore a direct reduction in the cost of operating LLM-powered services.

### Why Existing Methods Fall Short: The Gap SwiftKV Addresses

Prior approaches to accelerating LLM inference cluster into several categories, each with specific limitations that SwiftKV is designed to overcome.

**Model pruning and distillation.** Techniques like LLM-Pruner (Ma et al., 2023), Minitron (Sreenivas et al., 2024), Sheared LLaMA (Xia et al., 2024), and DarwinLM (Tang et al., 2025) permanently remove weights or entire structural components (e.g., attention heads, neurons, layers) from a model, typically followed by extensive post-training on 10–100B tokens to recover accuracy. The paper argues these methods have two critical drawbacks for prefill-dominant workloads:

1. **They reduce compute for both prefill and decode indiscriminately.** This is misaligned with workloads where prefill is the bottleneck. Pruning that removes compute uniformly may under-invest in the prefill phase specifically.
2. **The recovery cost is substantial.** Training on 10–100B tokens represents a non-trivial engineering investment. SwiftKV trains on less than 1B tokens and <10% of model parameters, making it dramatically cheaper to apply to an existing model. As evidence, Nemotron-51B (Sreenivas et al., 2024) is distilled from Llama-3.1-70B on 40B tokens and achieves 28% prefill reduction with an average accuracy of 82.78% across seven benchmarks, while SwiftKV at 50% prefill reduction achieves 82.98% on the same benchmarks with <1B tokens of distillation (Table 2).

**Layer skipping without pruning.** A separate line of work explores adaptively skipping layers at inference time without removing weights, using signals like hidden-state similarity to decide which layers a given token can bypass. FFN-SkipLLM (Jaiswal et al., 2024) skips only feed-forward network (MLP) layers. ShortGPT (Men et al., 2024), LaCo (Yang et al., 2024), LayerSkip (Elhoushi et al., 2024), and SliceGPT (Ashkboos et al., 2024) skip entire layers including attention and MLP. The paper's critique of these methods is twofold:

1. **They reduce compute for both prefill and decode tokens equally.** As with pruning, this fails to target the specific phase (prefill) that dominates enterprise workloads. SwiftKV is explicitly designed so that decode tokens still propagate through all layers, preserving the model's full capacity for generation while reducing prefill computation.
2. **They typically skip at most 25% of layers** without significant accuracy loss. SwiftKV demonstrates 25–50% prefill reduction (Table 2), with the ability to sustain higher skipping ratios because the approach does not permanently remove information from the forward pass—the KV projections for skipped layers are still computed, just from an earlier layer's representation rather than their own.

The paper makes the comparison concrete in Table 2: FFN-SkipLLM applied to Llama-3.1-8B-Instruct skips 12–19% of MLP layers (varying adaptively per token) but achieves only 70.62% average accuracy versus the baseline's 73.71%, while SwiftKV's 50% prefill reduction (skipping both MLP and attention for half the layers) achieves 72.70%. For Mistral-Small, FFN-SkipLLM at 34–37% MLP reduction catastrophically drops to 45.71% average accuracy versus the baseline's 78.23%, while SwiftKV's 50% reduction reaches 77.24%.

**KV cache compression.** Reducing the memory footprint of the KV cache—rather than compute—has been a major research focus. Techniques include:

- **Quantization**: KVQuant (Hooper et al., 2024) uses FP8/FP4 representations to reduce memory.
- **Architectural compression**: Multi-Query Attention (MQA) (Shazeer, 2019) and Grouped-Query Attention (GQA) (Ainslie et al., 2023b) share K and V heads within a layer.
- **Low-rank decomposition**: Palu (Chang et al., 2024) compresses the KV cache using low-rank projections.
- **Cross-layer merging**: MiniCache (Liu et al., 2024a) merges KV caches across adjacent layer pairs.

The paper's central critique of these approaches is captured in a concrete experiment (Section 5.1, Table 3). They construct an idealized "best-case" KV compression scheme called **Merge-all-Layers**, where every layer's KV cache is merged into a single shared layer, achieving compression ratios of 32× for Llama-3.1-8B and 80× for Llama-3.1-70B—far beyond any published technique—with zero computational overhead. Under an 80GB memory constraint (typical for an H100 GPU), Merge-all-Layers improves throughput by only ~10% over the baseline (25.1K vs. 22.9K tokens/s for Llama-3.1-8B). In contrast, 50% SwiftKV without any KV compression achieves a 35% improvement (31.0K tokens/s). The implication is clear: **in compute-bound regimes with sufficient memory, reducing KV cache memory alone does little to improve throughput** because the bottleneck is FLOPs, not memory capacity. SwiftKV addresses both compute and memory, and the paper shows it is the compute reduction that drives the majority of the throughput gains.

**Sparse attention.** Methods like ALISA (Zhao et al., 2024) and MInference (Jiang et al., 2024) exploit natural sparsity patterns in attention matrices to reduce the quadratic complexity of the attention operation. The paper acknowledges these are effective for very long sequences (100K–1M tokens) where attention dominates total compute. However, the critique is that **for moderate-length inputs (<100K tokens), the MLP layers—not attention—dominate the compute**. SwiftKV skips both attention and MLP for prefill tokens in the skipped layers, making it more broadly effective across sequence lengths where attention sparsity provides diminishing returns.

### Conflicting Demands in the Inference Landscape

The paper identifies an implicit tension in the existing optimization landscape that helps explain why a method like SwiftKV is needed. Most prior inference optimizations target **memory reduction** (KV cache compression, quantization, low-rank approximations), which primarily benefits low-memory or long-context scenarios. Yet the paper argues, based on Snowflake's production observations, that many enterprise deployments are **compute-bound** rather than memory-bound:

> "production deployments are often compute-bound rather than memory-bound, and such long-context requests are rare amongst diverse enterprise use cases" (Section 1)

This creates a mismatch: the most widely researched inference optimizations target a bottleneck that is not the primary constraint in typical production settings. SwiftKV directly addresses the compute bottleneck by reducing the FLOPs required for prefill, while optionally incorporating KV cache compression (AcrossKV) for scenarios where memory is also constrained.

### Theoretical Motivation: Deep Layer Redundancy

Beyond the practical motivation of prefill dominance, the paper grounds its approach in an empirical finding about the behavior of deep transformer layers: **hidden states become increasingly similar as depth increases**. Section 3.2 formalizes this with a similarity score:

$$\text{SimScore}(x_l) = \frac{\sum_{j=l+1}^{L} \text{Similarity}(x_l, x_j)}{L - l}$$

where $\text{Similarity}(x_l, x_j)$ is the average cosine similarity between all token-level hidden states at layer $l$ and layer $j$. Figure 2 (left and middle) shows this metric for several model families (Llama-3.1-8B, Mistral-7B, Qwen2.5-7B; Llama-3.1-70B, Mistral-Large, Qwen2.5-72B). The consistent finding: at around half the model's depth, the average similarity of a layer's input with all deeper layers is above 0.5 for all models. This means that the representations in later layers are not changing dramatically from layer to layer—a finding consistent with prior work (Liu et al., 2024b; Gromov et al., 2024).

This redundancy is what makes SwiftKV plausible: if the hidden state $x_{l+1}$ at layer $l$ is similar to what would be produced if the prompt tokens continued propagating through layers $l+1, l+2, ..., L$, then computing the KV cache for those later layers directly from $x_{l+1}$—rather than from each layer's own output—should produce representations that are functionally similar enough to preserve model accuracy after lightweight distillation.

The paper explicitly cites this as the motivating observation:

> "This is motivated by the observation that the hidden states of later layers do not change significantly" (Section 1)

The theoretical connection is implicit but important: SwiftKV's design is not an arbitrary architectural modification but rather an exploitation of a measurable property (inter-layer hidden state similarity) that exists across diverse model families and scales systematically with depth.

### Distinguishing SwiftKV from Prior Layer-Skipping Approaches

A key architectural distinction that the paper emphasizes is that **SwiftKV does not require additional decoding heads**. Prior layer-skipping methods that skip layers for both prefill and decode tokens must decide how to produce the output token—either by exiting early (requiring an additional language modeling head at each possible exit point, as in LayerSkip) or by completing all layers (defeating the purpose for decode). SwiftKV sidesteps this entirely:

> "We note that decoding tokens still propagate through all layers, so additional decoding heads are not necessary for SwiftKV." (Section 3.2)

This is a deliberate design choice that reflects the workload asymmetry the paper targets. Since decode tokens are few relative to prefill tokens, the marginal cost of propagating decode tokens through all layers is small. The benefit is architectural simplicity: no additional heads to train, no routing logic to determine when to exit, and full model capacity preserved for the generation phase where autoregressive errors compound.

### Positioning Summary

SwiftKV positions itself at the intersection of several trends:

- It targets **compute reduction** primarily, where most prior work targets memory reduction (KV cache compression, quantization) or uniform compute reduction (pruning, layer skipping).
- It is **phase-asymmetric**: unlike pruning and prior layer-skipping methods that reduce compute for both prefill and decode, SwiftKV specifically targets prefill while preserving full capacity for decode. This is tailored to the 10:1 input-to-output ratio observed in enterprise workloads.
- It requires **minimal distillation cost** (<1B tokens, <10% of parameters, <3 hours on 8 H100 GPUs for an 8B model) versus 10–100B tokens for prune-and-distill methods, making it practical to apply to existing deployed models.
- It is **architecturally simple**: no custom kernels, no sparse computation, no additional model heads—just a re-wiring of existing layers that integrates into standard serving systems (vLLM, SGLang) with minimal engineering effort.
- It exploits a **measured empirical regularity** (inter-layer hidden state similarity) rather than imposing an external inductive bias, and the paper provides model-specific measurements (Figure 2) to explain both its successes (Llama, Mistral, Deepseek) and its partial failure (Qwen, where similarity is lower at mid-depth, correlating with larger accuracy drops in Table 2).

## 3. Technical Approach

### 3.1 Reader Orientation

SwiftKV is a **post-training model transformation** applied to an existing, fully-trained large language model. It rewires the transformer architecture so that during the prefill phase of inference, prompt tokens can skip a configurable fraction of the later layers without recomputing those layers' KV caches from scratch. The system solves the problem of prefill-dominated inference costs by exploiting a measured property of deep transformers—that hidden states become increasingly similar at deeper layers—to project the KV cache for all skipped layers from a single earlier layer's output. This reduces prefill FLOPs while keeping the model's original weights intact and recovering any accuracy loss through a very lightweight distillation procedure that trains only the Q, K, and V projection matrices of the affected layers.

### 3.2 Big-Picture Architecture

The SwiftKV pipeline has five major components:

1. **Base LLM** — the pretrained, instruction-tuned model (e.g., Llama-3.1-8B-Instruct) whose architecture will be rewired. All original weights are preserved.
2. **Similarity Analyzer** — computes the average cosine similarity between each layer's hidden state and all deeper layers' hidden states (Equation 1, Figure 2). This empirically determines where the model's representations stabilise, informing the choice of the cutoff layer `$l$`.
3. **SwiftKV Model Transformation** — rewires the transformer so that for all layers `$j > l$`, the KV cache is computed from the hidden state `$x_{l+1}$` (the output of layer `$l$`) rather than from each layer's own input `$x_j$`. During prefill, prompt tokens only compute through layer `$l$` plus the KV projections of layers `$l+1$` to `$L$`; all other operations (Q, O, attention, MLP) in layers `$>l$` are skipped. During decode, all tokens propagate through all layers normally.
4. **AcrossKV (optional)** — merges the KV caches of multiple consecutive skipped layers so that a single layer's KV projection serves several consecutive layers, reducing KV cache memory by `$(g-1)/g$` for a group size `$g$`.
5. **Knowledge Distillation Procedure** — trains only the WQKV weight matrices (Q, K, and V projections) for layers `$l+1$` to `$L$` using a teacher-student setup where the original model generates logit targets. Trains on under 1B tokens and <10% of model parameters.

Information flows as follows: an input sequence enters the base model → the similarity analyzer (run once offline) determines the cutoff layer `$l$` → the model is rewired so that layers `$>l$` receive their KV cache inputs from `$x_{l+1}$` rather than from their own hidden state → a lightweight distillation loop trains only the QKV projections of the rewired layers using the original model's logits as soft targets → at inference time, prompt tokens compute only through layer `$l$` plus the KV projections of later layers, while decode tokens complete all layers normally → the now-reduced prefill compute translates directly to lower latency and higher throughput in vLLM or SGLang.

### 3.3 Roadmap for the Deep Dive

- **First, the transformer preliminaries and the prefill-decode asymmetry**, because SwiftKV's entire design hinges on understanding *which* operations are expensive during prefill versus decode and *why* skipping layers for prefill but not decode is appropriate for enterprise workloads.
- **Second, the inter-layer similarity measurement**, since this is the empirical foundation that makes the transformation plausible—without it, projecting KV cache from an earlier layer would be an arbitrary architectural hack rather than a principled exploitation of measured redundancy.
- **Third, the SwiftKV transformation itself**, covering the exact rewiring of the forward pass, what gets computed for prefill versus decode tokens, and the FLOPs accounting that quantifies the savings.
- **Fourth, the AcrossKV extension**, which adds KV cache memory compression on top of the compute reduction, including the design decision to share KV caches across groups of consecutive layers rather than across all layers.
- **Fifth, the knowledge distillation procedure**, covering the teacher-student setup, why only WQKV parameters are trained, the distillation loss function, training data, and hyperparameters.
- **Sixth, the inference system integration**, explaining how SwiftKV maps onto chunked prefill in vLLM and SGLang and why this integration requires no custom kernels.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems and model transformation paper** whose core idea is that prefill-dominant workloads can be accelerated by exploiting inter-layer hidden state redundancy to project KV caches from earlier layers, combined with a lightweight distillation that trains only the projection weights to recover accuracy.

#### Transformer Preliminaries and the Prefill-Decode Asymmetry

Before explaining SwiftKV's modifications, it is essential to understand the standard transformer forward pass and why prefill and decode have fundamentally different computational profiles.

**Standard transformer layer operations.** For a sequence of input tokens `$x^{(1)}, x^{(2)}, ..., x^{(n)}$`, each transformer layer `$l$` takes as input a matrix `$X_l \in \mathbb{R}^{n \times d}$` (the hidden states for all `$n$` tokens from the previous layer, with embedding dimension `$d$`) and produces three projections:

$$Q = X_l W_Q, \quad K = X_l W_K, \quad V = X_l W_V$$

where `$W_Q \in \mathbb{R}^{d \times d_k}$` is the query projection matrix, and `$W_K, W_V \in \mathbb{R}^{d \times d_g}$` are the key and value projection matrices, with `$d_g \mid d_k$` (the grouped-query attention head dimension divides the query head dimension). The paper also refers to `$W_K$` and `$W_V$` jointly as a single matrix `$W_{KV} \in \mathbb{R}^{d \times 2d_k}$` for notational convenience.

**What this computes:** each projection matrix maps the `$d$`-dimensional token representations into a lower-dimensional space suitable for attention computation. The query determines what each token is "looking for" in other tokens; the key determines what each token "offers" as a match criterion; the value determines what information each token contributes when matched. The output of attention combines values weighted by query-key similarity scores, after which a feed-forward network (MLP) applies a position-wise non-linear transformation. After layer `$l$` completes, its output `$x_{l+1}$` becomes the input to layer `$l+1$`.

**Why this form:** the QKV decomposition is the standard transformer attention mechanism (Vaswani et al., 2017). What matters for SwiftKV is the asymmetry: `$Q$` is needed for new tokens during both prefill and decode, but `$K$` and `$V$` for past tokens are computed once (during prefill) and then reused for all subsequent decode steps via the KV cache. This is the architectural property SwiftKV exploits—if the KV cache can be computed accurately from an earlier layer's output, the bulk of prefill computation (Q, attention, MLP) for later layers becomes unnecessary.

**Prefill versus decode computation.** During the prefill phase, the model processes all `$n$` input tokens in parallel. For each of the `$L$` layers, this involves:
- Computing `$Q$`, `$K$`, and `$V$` for all `$n$` tokens (three matrix multiplications of size `$n \times d$` times weight matrices of size `$d \times d_k$` or `$d \times d_g$`).
- Computing the attention operation, which is `$O(n^2 \cdot d_k)$` per layer (quadratic in sequence length).
- Computing the output projection `$O$` and the MLP, which together dominate the FLOPs for moderate sequence lengths (the paper's Table 1 shows MLP at 113 GFLOPs per prefill token for Llama-3.1-70B versus only 4.3 for vocab and 2.6 for K/V projections).

During the decode phase, the model generates tokens one at a time. When predicting token `$t+1$`, only the query `$Q^{(t+1)}$` for the single new token needs to be computed, while the keys and values `$K^{(1)}, ..., K^{(t)}$` and `$V^{(1)}, ..., V^{(t)}$` of all previous tokens are read from the KV cache. The per-new-token computation is therefore `$O(L \cdot t \cdot d_k)$`—linear in sequence length rather than quadratic, and dominated by memory bandwidth rather than compute.

**Why this asymmetry matters for SwiftKV's design.** If a workload has a 10:1 input-to-output token ratio (as observed in Snowflake's production), the prefill phase accounts for the overwhelming majority of total FLOPs. Reducing prefill compute is therefore far more impactful than reducing decode compute. Equally important, keeping decode tokens propagated through all layers preserves the model's full representational capacity for generation—where autoregressive errors compound—while saving compute on the phase where the model is merely encoding information it will later attend to. This is the central design principle: SwiftKV is _phase-asymmetric_, reducing prefill computation while leaving decode computation unchanged.

#### Measuring Inter-Layer Hidden State Similarity

The theoretical justification for projecting KV caches from earlier layers rests on a measurable empirical regularity: **hidden states at deeper layers become increasingly similar to each other**. Section 3.2 defines the similarity metric:

$$\text{SimScore}(x_l) = \frac{\sum_{j=l+1}^{L} \text{Similarity}(x_l, x_j)}{L - l}$$

where `$L$` is the total number of layers, `$x_l$` is the input to layer `$l$` (the hidden state after layer `$l-1$` completes), and `$\text{Similarity}(x_l, x_j)$` is the average cosine similarity between all token-level hidden states at layer `$l$` and the corresponding tokens at layer `$j$`. Formally, for a sequence of `$n$` tokens:

$$\text{Similarity}(x_l, x_j) = \frac{1}{n} \sum_{i=1}^{n} \frac{x_l^{(i)} \cdot x_j^{(i)}}{\|x_l^{(i)}\| \cdot \|x_j^{(i)}\|}$$

where `$x_l^{(i)}$` is the `$i$`-th token's hidden state at layer `$l$`.

**What it computes:** `$\text{SimScore}(x_l)$` is the average pairwise cosine similarity between the hidden states at layer `$l$` and every deeper layer from `$l+1$` through `$L$`. A value of 1.0 means all deeper layers produce identical representations; a value near 0 means representations are orthogonal and contain no shared structure. The metric is computed per-layer and aggregated across a sample of input sequences to produce the curves in Figure 2.

**Why this form:** cosine similarity is a natural choice because it is invariant to the magnitude of the hidden state vectors and captures only directional alignment in the `$d$`-dimensional embedding space. Layer normalisation and residual connections in transformers mean that hidden state magnitudes can fluctuate, but the _direction_ of the representation captures semantic content. Averaging across tokens and then across layers provides a robust, interpretable scalar per layer that directly measures how much additional transformation deeper layers are applying. The paper notes that this metric increases monotonically with depth in all models tested (Figure 2), meaning later layers progressively refine representations less and less, until they are "unreasonably ineffective" (to borrow the language of Gromov et al., 2024, which the paper cites).

**Empirical findings (Figure 2, left and middle).** For smaller models (Llama-3.1-8B-Instruct, Mistral-7B-Instruct-v0.1, Qwen2.5-7B-Instruct), `$\text{SimScore}(x_l)$` rises from approximately 0.2 at layer 0 to 0.6–0.8 by the final layers, crossing 0.5 at roughly half the model's depth. For larger models (Llama-3.1-70B-Instruct, Mistral-Large-Instruct-2407, Qwen2.5-72B-Instruct), the pattern is similar but with a notable difference: **Qwen2.5-72B shows lower similarity at mid-depth** compared to Llama and Mistral models of comparable size. This observation directly explains the paper's later finding (Table 2) that Qwen2.5-14B-Instruct suffers larger accuracy degradation under SwiftKV (7.4% drop at 50% reduction vs. 1–2% for Llama and Mistral models): the lower similarity means that projecting KV caches from an earlier layer introduces a larger representational mismatch, which even distillation struggles to fully recover.

**The practical implication.** The similarity scores define the feasible range for the cutoff layer `$l$`. The paper selects `$l$` at 50% of depth (`$l = L/2$`) for most experiments because this is approximately where `$\text{SimScore}(x_l)$` exceeds 0.5—meaning deeper layers are, on average, more similar to `$x_{l+1}$` than they are dissimilar. A smaller cutoff (25%, `$l = 3L/4$`) keeps more layers, reducing prefill less but with higher accuracy; a larger cutoff (75%, `$l = L/4$`) skips more layers but accuracy degrades more severely (as shown with 62.5% SwiftKV on Llama-3.1-8B-Instruct in Table 2, which drops to 66.09% average accuracy from 73.71%).

#### The SwiftKV Model Transformation

The core architectural change is deceptively simple: **compute the KV cache for all layers `$j > l$` using the hidden state output of layer `$l$`, rather than using each layer's own input.**

**The rewiring rule.** In a standard transformer, layer `$j$` computes its KV cache as:

$$KV_j = W_{KV}^{(j)} \cdot x_j$$

where `$x_j$` is the input hidden state to layer `$j$` (the output of layer `$j-1$`). Under SwiftKV, for all layers `$j > l$`, this is replaced with:

$$KV_j = W_{KV}^{(j)} \cdot x_{l+1}$$

where `$x_{l+1}$` is the output of the cutoff layer `$l$` after it completes its full computation (including attention and MLP). The weight matrices `$W_{KV}^{(j)}$` are retained from the original model—they are not structurally modified, but they now receive a different input distribution and must therefore be fine-tuned (this is the role of the distillation step in Section 3.4's distillation subsection).

**What this means operationally:** after layer `$l$` finishes processing, the system immediately computes `$W_{KV}^{(j)} \cdot x_{l+1}$` for all `$j \in \{l+1, ..., L\}$` and stores the results in the KV cache slots for those layers. This is a one-time computation per prefill token, costing `$(L - l)$` matrix multiplications of size `$d \times 2d_k$` (the key and value projections for each skipped layer). All other operations in layers `$j > l$`—the query projection `$W_Q^{(j)}$`, the output projection `$W_O^{(j)}$`, the attention operation, and the MLP—are entirely skipped for prefill tokens.

**Prefill token behaviour.** A prefill token flows through the model as follows:
1. **Layers 1 through `$l$`:** Normal transformer forward pass. The token computes Q, K, V, attention, output projection, and MLP at each layer exactly as in the original model.
2. **Layer `$l$` completes, producing `$x_{l+1}$`:** This hidden state now serves as the single source for all deeper-layer KV projections.
3. **Layers `$l+1$` through `$L$`:** For each layer `$j$`, only the KV projection `$W_{KV}^{(j)} \cdot x_{l+1}$` is computed (or, in the case of AcrossKV, only a subset of these projections). No Q, attention, or MLP computation occurs. The prefill token's forward pass effectively terminates after the KV projections are stored.

**Decode token behaviour.** Decode tokens process every layer `$1$` through `$L$` normally—they compute Q, K, V, attention, output projection, and MLP at each layer, using the KV cache populated during prefill. This is a deliberate design choice: because decode tokens are few relative to prefill tokens (in the paper's target 10:1 ratio), the marginal cost of full processing is small, and preserving the model's full depth for generation avoids compounding errors. The paper states this explicitly:

> "We note that decoding tokens still propagate through all layers, so additional decoding heads are not necessary for SwiftKV" (Section 3.2)

**The edge case of the last prefill token.** The very last token of the input prompt also serves as the first token for which a decode output must be generated. This token must therefore compute all layers normally to produce the first generated token's hidden state—it cannot skip layers `$>l$`. The paper notes this (Section 3.2, footnote 2) as a minor exception to the prefill skipping rule, but its cost is negligible relative to the total prompt length.

| 50% SwiftKV + 4× AcrossKV | 4.3 | 1.7 | 11 | 56 | 80 | 153 | 50.7% |

The breakdown reveals several important patterns:

- **MLP dominates total FLOPs.** At 113 GFLOPs per token in the baseline, the MLP accounts for 37% of total compute. This is why methods that skip only attention (sparse attention) or only KV cache (compression) provide limited benefit—the bulk of compute is in the position-wise feed-forward layers.
- **Attention is the second-largest contributor** at 160 GFLOPs (53% of total). However, the paper notes that this is for the specific sequence length under consideration; attention scales quadratically with sequence length, so its relative contribution grows for longer contexts.
- **SwiftKV reduces all three major components** (Q/O, MLP, and Attention) proportionally by skipping `$(L-l)/L$` of the layers. At 50% SwiftKV, prefill FLOPs per token drop from 302 to 154—a 51% reduction. The decrease is not exactly 50% because the vocab projection (4.3 GFLOPs) and the KV projections for the skipped layers (2.6 GFLOPs) are still computed.
- **AcrossKV adds negligible additional FLOP savings** (154 → 153 at 50% SwiftKV) because it only reduces the number of KV projections computed, which are already a minor fraction of total FLOPs (2.6 GFLOPs out of 302). AcrossKV's benefit is primarily in memory reduction, not compute reduction.

**Right panel of Figure 2** validates that these FLOPs reductions translate to wall-clock time savings. For a forward pass of Llama-3.1-8B-Instruct at varying batch sizes (128 to 2048 tokens), the baseline requires 50–350 ms, 50% SwiftKV reduces this to roughly 30–250 ms, and 25% SwiftKV falls between. The time reduction tracks the FLOPs reduction closely, confirming that the operation is compute-bound and that the skipped computations are not being bottlenecked by memory or other overheads.

**Why this specific rewiring and not alternatives?** Several alternative designs were apparently considered or can be inferred from the paper's choices:

1. **Skip layers entirely without computing KV caches for them?** This would break the decode phase, because decode tokens attend to the KV cache of all layers. If layers `$>l$` have no KV cache, decode tokens would have nothing to attend to in those layers, destroying the model's autoregressive capability.
2. **Compute KV caches from `$x_l$` instead of `$x_{l+1}$`?** The input to layer `$l$` might be a worse proxy for deeper-layer representations than the output of layer `$l$`, because layer `$l$`'s transformation (attention + MLP) adds information. Using `$x_{l+1}$` incorporates this transformation. The paper does not ablate this choice, but it is consistent with the similarity analysis in Figure 2, which shows that output similarity increases with depth.
3. **Share KV projection weights across layers?** This would break the model's ability to learn different attention patterns at different depths. SwiftKV preserves separate `$W_{KV}^{(j)}$` matrices for each layer, each projecting the same `$x_{l+1}$` into layer-specific key and value spaces. The distillation step then adapts these weights to the new input distribution.
4. **Skip layers for decode tokens too?** This would compound errors autoregressively and require additional decoding heads at each possible exit point, increasing architectural complexity. The paper's choice to keep decode tokens at full depth is a deliberate simplification justified by the prefill-dominant workload.

**The relationship to early exit and self-speculative decoding.** Appendix B.4 explores an extension where decode tokens can optionally exit early using an additional language modeling head trained on the cutoff layer's output. This is presented as preliminary exploration, not a core contribution, but it illustrates that the SwiftKV transformation naturally enables early exit for decode tokens if desired—because the KV caches for all future tokens are already computed from `$x_{l+1}$`, a decode token could theoretically stop at layer `$l$` without losing the ability to generate subsequent tokens. The paper shows that when the early-exit head's maximum softmax probability exceeds 0.95, its prediction aligns with the full-model's prediction 66% of the time (Figure B.1), but this is not yet competitive with full-depth decoding.

#### AcrossKV: Cross-Layer KV Cache Sharing

While SwiftKV's primary contribution is prefill compute reduction, the paper introduces an optional extension called **AcrossKV** that additionally reduces KV cache memory by sharing KV caches across groups of consecutive skipped layers.

**Motivation.** GQA (Grouped-Query Attention, Ainslie et al., 2023a) demonstrated that KV caches can be shared across attention heads within a single transformer layer with minimal accuracy loss. MiniCache (Liu et al., 2024a) showed that KV caches can be merged for certain adjacent layer pairs. AcrossKV extends this idea to sharing across _multiple_ consecutive layers within the skipped region, controlled by a grouping factor.

**The sharing mechanism.** Instead of computing a separate KV cache for every layer `$j > l$` as in Equation 2, AcrossKV partitions the skipped layers into groups of size `$g$`. Within each group, a single designated layer's KV projection is computed and shared among all members:

$$KV_{j} = W_{KV}^{(j_{\text{rep}})} \cdot x_{l+1}, \quad \text{for all } j \text{ in group}$$

where `$j_{\text{rep}}$` is the representative layer for that group (the paper does not specify a selection heuristic—it appears to be the first layer in each group based on Figure 1). For example, with `$g = 4$` (4-way AcrossKV) and 16 skipped layers, only 4 KV projections are computed (one per group of 4 consecutive layers), and each projection serves as the KV cache for all 4 layers in its group.

**Memory reduction.** An `$g$`-way AcrossKV reduces KV cache memory for the skipped layers by a factor of `$g$`. For a model with `$L$` total layers and cutoff `$l$`, the total KV cache memory reduction (as a fraction of the original) is:

$$\text{Memory reduction} = \frac{L - l}{L} \cdot \frac{g - 1}{g}$$

For example, 50% SwiftKV (`$l = L/2$`) with 4-way AcrossKV reduces total KV cache memory by `$0.5 \times 0.75 = 37.5\%$` (as reported in Table 2). With 16-way AcrossKV on the same model, the reduction is `$0.5 \times 15/16 = 46.875\%$`.

**Why not share a single KV cache across all skipped layers?** The paper's ablation in Table B.2 provides insight. They compare three configurations that achieve identical memory reduction (37.5% at 50% SwiftKV):
- **MQA** (multi-query attention across all heads, within-layer sharing only): 54.13% average accuracy.
- **AcrossKV-MHA** (multi-head attention with cross-layer KV sharing, all skipped layers share one KV cache): 69.76%.
- **AcrossKV-GQA** (grouped-query attention with 4-way AcrossKV): 71.49%.

The AcrossKV-MHA configuration is equivalent to a single shared KV cache for all skipped layers, yet it underperforms the 4-way grouping (69.76% vs. 71.49%), suggesting that some per-layer differentiation in KV representations is beneficial. The paper also notes that AcrossKV-MHA is worse than the 16-way AcrossKV result in Table 2 (70.50%), even though 16-way AcrossKV has more aggressive compression (46.875% vs. 37.5%). They hypothesise this is due to hyperparameter tuning but did not investigate further. The practical implication is that grouping layers into small sets (2–4) provides a better accuracy-memory tradeoff than full sharing.

**Complementarity with other KV compression methods.** Appendix B.1 demonstrates that AcrossKV can be combined with FP8 KV cache quantization. Adding per-token FP8 quantization to a model with 2-way AcrossKV (25% KV cache reduction from AcrossKV) achieves 62.5% total KV cache reduction (25% + 50% from quantization) with less than 0.4 points of additional accuracy degradation across all seven evaluated tasks (Table B.1). Similarly, 4-way AcrossKV (37.5% reduction from AcrossKV) combined with FP8 achieves 68.75% total reduction with only 0.14 points additional degradation. The paper attributes this orthogonality to AcrossKV operating on the "which KV caches exist" axis while quantization operates on the "how each KV cache is stored" axis.

**Why AcrossKV is treated as optional.** The paper's production observations (Section 1) suggest that memory is often not the binding constraint: "production deployments are often compute-bound rather than memory-bound." AcrossKV is therefore presented as a supplementary feature for low-memory scenarios, and the primary gains come from the compute reduction alone. Table 3 makes this concrete: on an 80GB H100 GPU, 50% SwiftKV without AcrossKV achieves 31.0K tokens/s versus 22.9K for the baseline (35% improvement), while adding AcrossKV only improves this to 31.2K—a negligible gain because memory is not the bottleneck. However, at 20GB of memory, AcrossKV's benefit becomes substantial (18.0K with AcrossKV vs. 12.2K without), confirming that memory reduction matters only when memory is scarce.

#### Knowledge Distillation: Recovering Accuracy After Transformation

The SwiftKV transformation preserves all original model weights but changes the input distribution to the KV projection matrices for layers `$>l$`. The paper finds that this rewiring alone causes non-trivial accuracy degradation, and that a specific, lightweight distillation procedure is needed to recover performance.

**Why naive fine-tuning is insufficient.** The paper demonstrates in Table 4(a) that training the transformed model using standard language modeling loss (next-token prediction with cross-entropy) underperforms distillation by 2.64 points on average across seven tasks. The gaps are particularly large on generative reasoning tasks: MMLU-CoT (4.13 points) and GSM-8K (6.74 points). The paper does not extensively analyse _why_ distillation outperforms standard LM loss, but the likely mechanism is that distillation provides richer training signal: the teacher model's full logit distribution encodes fine-grained information about token confusability and relative plausibility that is lost when training only against hard one-hot targets. This is the classic argument for knowledge distillation (Hinton et al., 2015), applied here to the specific case of adapting KV projection weights to a shifted input distribution.

**Teacher-student architecture.** The distillation setup is a clever engineering design that minimises memory overhead during training:

1. **Memory-efficient weight sharing.** Only a single copy of the original model weights is kept in GPU memory, and all parameters except the target WQKV matrices are frozen. An additional trainable copy of the WQKV parameters for layers `$>l$` is created, initialised from the original model's corresponding weights. This means the total trainable parameters are typically <10% of the model's total for popular GQA architectures (Llama, Mistral, Qwen).
2. **Two forward-pass modes.** During each training step, the system runs two forward passes with identical inputs but different architectures:
   - **Teacher pass:** `$y_{\text{teacher}} = M(x, \text{SwiftKV} = \text{False})$`. The model operates in its original configuration, with all layers processing normally.
   - **Student pass:** `$y_{\text{student}} = M(x, \text{SwiftKV} = \text{True})$`. The model operates in SwiftKV configuration, where the trainable copy of the WQKV parameters for layers `$>l$` is used, and those layers receive their KV projection inputs from `$x_{l+1}$` rather than from their own hidden states.
3. **Distillation loss.** The standard distillation objective is applied to the final logits:

$$\mathcal{L}_{\text{distill}} = T^2 \cdot \text{KL}\left(\text{softmax}\left(\frac{y_{\text{teacher}}}{T}\right) \;\middle\|\; \text{softmax}\left(\frac{y_{\text{student}}}{T}\right)\right)$$

where `$T$` is the distillation temperature and `$\text{KL}(\cdot \|\cdot)$` is the Kullback-Leibler divergence between the teacher's and student's softened probability distributions over the vocabulary. The paper uses `$T = 2.0$` (Appendix A.1).

**What this computes:** the KL divergence measures the difference between two probability distributions. By minimising this divergence, the student model is trained to match the teacher's full output distribution—not just its most likely token, but also the relative probabilities it assigns to alternatives. The temperature `$T$` controls how much the distribution is softened: higher values spread probability mass more evenly across tokens, which (as argued by Hinton et al., 2015) exposes the student to more information about the teacher's internal knowledge structure.

**Why this form:** the standard alternative—training with cross-entropy against the ground-truth next token—discards all information about which tokens are "close second choices" and which are completely implausible. For a re-wired model where the KV projections are receiving a slightly distorted input, this secondary information may be crucial: even if the model's top prediction is correct, the relative ordering of alternatives encodes knowledge about semantic relationships, syntactic constraints, and factual associations that help the model generalise. The KL divergence loss preserves this information.

**Training data and hyperparameters.** The distillation dataset is a mixture of three publicly available instruction-tuning corpora:
- `HuggingFaceH4/ultrachat_200k` (Ding et al., 2023): high-quality conversational data.
- `teknium/OpenHermes-2.5` (Teknium, 2023): synthetic generalist assistant data.
- `Open-Orca/SlimOrca` (Lian et al., 2023): filtered FLAN-style reasoning traces.

In total, this mixture contains roughly **680M Llama-3.1 tokens**. The training process uses the following hyperparameters (Appendix A.1):
- **Epochs:** 2
- **Learning rate:** 3e-4
- **Weight decay:** 0.05
- **Warmup ratio:** 5% of total steps
- **Maximum sequence length:** 8192 tokens
- **Sequence packing:** attention-separated sequence packing (multiple sequences concatenated with attention masking)
- **Distillation temperature:** 2.0

The training is computationally efficient: for Llama-3.1-8B-Instruct, distillation completes in **under 3 hours on 8 H100 GPUs**. For Llama-3.1-70B-Instruct, it takes **5 hours on 32 H100 GPUs across 4 nodes**. This is orders of magnitude cheaper than prune-and-distill methods like Nemotron-51B (40B tokens of training) or DarwinLM-8.4B (10B tokens of training).

**Why train only WQKV parameters?** Section 5.2 and Table 4(b) provide the key ablation. When all parameters in the later 50% of layers are fine-tuned (including MLP, attention output projections, and layer norms), the average accuracy drops to 68.23% compared to 72.70% when only WQKV parameters are trained—a difference of 4.47 points. The paper attributes this to prior findings that "LLM knowledge is primarily stored in their MLP layers" (citing Meng et al., 2024; Geva et al., 2021; Elhage et al., 2021). Freezing the MLP weights preserves the model's factual knowledge and reasoning capabilities, while training only the attention projections allows the model to adapt how it _accesses_ that knowledge through the new KV cache pathway.

The paper frames this as a "knowledge-preserving" design:

> "limiting the training to just WQKV achieves better accuracy, which aligns with prior hypotheses that LLM knowledge is primarily stored in their MLP layers" (Section 3.4)

**What happens after distillation.** Once the distillation is complete, the original KV projection weights for layers `$>l$` are discarded. The trainable copy of the WQKV parameters replaces them. The model can now be served using the SwiftKV inference configuration, and no further training or adaptation is needed.

**The role of data quality.** Appendix B.3 provides additional analysis of the distillation data. The paper acknowledges that the chosen dataset mixture is suboptimal: fine-tuning the base Llama-3.1-8B model on this same dataset (without the SwiftKV transformation) produces a model with only 65.77% average accuracy versus the official Llama-3.1-8B-Instruct's 73.71% (Table B.3a). This means the distillation is recovering from an information-poor signal—an even richer dataset might close more of the remaining accuracy gap. The paper demonstrates this concretely: adding just 83K additional math and code samples (from `gretelai/synthetic-gsm8k-reflection-405b` and `ise-uiuc/Magicoder-OSS-Instruct-75K`, totalling ~16M tokens) improves GSM-8K accuracy by 0.53 points and the overall average by 0.23 points (Table B.3b). This suggests that domain-specific distillation data is a promising avenue for further reducing the quality gap.

#### Inference System Integration

A key practical advantage of SwiftKV emphasised throughout the paper is that it requires **no custom inference kernels**. The transformation changes _which_ operations are performed but not _how_ they are performed—all operations (matrix multiplications, attention, KV cache insertion) use the same highly-optimised implementations as the baseline model.

**Integration with chunked prefill.** Modern LLM serving systems like vLLM (Kwon et al., 2023) and SGLang (Zheng et al., 2024) employ chunked prefill (also called Split-Fuse; Holmes et al., 2024; Agrawal et al., 2024), which mixes chunks of prefill tokens with decode tokens in each forward pass. This improves GPU utilisation by preventing decode tokens from stalling while long prefill sequences are being processed.

SwiftKV integrates naturally into this paradigm. During each forward pass:

1. **Layers 1 through `$l$`:** All tokens (prefill chunk + decode) process normally. Both prefill and decode tokens compute Q, K, V, attention, output projection, and MLP.
2. **After layer `$l$` completes:** For all prefill tokens, the system immediately computes `$W_{KV}^{(j)} \cdot x_{l+1}$` for all `$j > l$` and stores these in the KV cache slots for those layers. This is a one-time cost per prefill token.
3. **Layers `$l+1$` through `$L$`:** Decode tokens continue processing through all layers normally. Prefill tokens are not propagated through these layers—their only contribution has been the KV cache insertion in step 2.

The paper states this integration explicitly: "During each forward pass, after completing layer `$l$`, the KV-cache for the remaining layers (`$>l$`) are immediately computed, and only the decode tokens are propagated through the rest of the model layers" (Section 3.5).

**Why no custom kernels are needed.** The KV projection `$W_{KV}^{(j)} \cdot x_{l+1}$` is a standard matrix multiplication—identical in form to the KV projections that already exist in the original model. The system reuses the existing GPU kernels for this computation. The only difference is _when_ it is called (immediately after layer `$l$` rather than during layer `$j$`) and _which_ input it receives (`$x_{l+1}$` rather than `$x_j$`). This design principle—that SwiftKV "makes minimal changes to the model architecture, so it can be integrated into existing serving systems without implementing new kernels" (Section 3.5)—is a deliberate contrast with methods like sparse attention or custom quantisation that require new, potentially buggy or slow kernel implementations.

**Implementation in vLLM and SGLang.** The paper open-sourced implementations for both serving frameworks. The key implementation detail is that SwiftKV is exposed as a configuration option that modifies the model's forward pass graph, not as a runtime heuristic. This means the same serving infrastructure that handles request scheduling, batching, KV cache management, and speculative decoding for the baseline model also works for SwiftKV models without modification. The paper reports throughput and latency results for both vLLM (Figures 3, 4; Table 3) and SGLang (Appendix A.4, Table A.2), showing consistent improvements across both frameworks.

**The throughput-to-MFU calculation.** Section 4.2 reports that for Llama-3.1-70B-Instruct with 8K input tokens, SwiftKV achieves "over 16K toks/sec over 4xH100 GPUs which corresponds to 560 TFLOPS/GPU of BF16 performance when normalized to baseline." This "normalized throughput" metric is important: it divides the number of tokens processed by the theoretical FLOPs of the _original_ model (not the reduced SwiftKV model), making the comparison apples-to-apples. The 56.6% Model Flops Utilisation (MFU) is "unprecedented" (Section 4.2) and demonstrates that SwiftKV's compute savings translate efficiently to real hardware without being bottlenecked by memory bandwidth or kernel launch overhead.

**Why prefill reduction improves TPOT.** The paper notes a potentially counterintuitive result: SwiftKV reduces Time Per Output Token (TPOT) by up to 60% (Figure 4, bottom row), even though it does not reduce decode computation. The explanation is that in chunked prefill systems, "prefill and decode are run on the same GPUs... This means prefill and decode may contend for GPU time, and reducing prefill compute also benefits decode latency" (Section 4.2). When prefill dominates GPU utilisation, decode tokens wait in the scheduling queue. By reducing the GPU time consumed by prefill, SwiftKV frees up compute cycles for decode tokens, reducing queueing delays and therefore TPOT. This is an indirect but substantial benefit that compounds the direct TTFT reduction.

## 4. Key Insights and Innovations

### Innovation 1: Phase-Asymmetric Compute Reduction as a New Axis in the Inference Optimization Design Space

The dominant assumption across almost all prior inference optimization work—whether pruning (Sreenivas et al., 2024; Tang et al., 2025), layer skipping (Jaiswal et al., 2024; Men et al., 2024; Ashkboos et al., 2024), KV cache compression (Hooper et al., 2024; Ainslie et al., 2023b), or sparse attention (Zhao et al., 2024; Jiang et al., 2024)—is that the optimization should apply uniformly to all tokens and inference phases. Even when methods are workload-aware, they target memory reduction or total FLOPs reduction without distinguishing *when* those FLOPs are spent.

SwiftKV introduces a fundamentally different design philosophy: **optimization can be phase-asymmetric**. The key intellectual move is recognising that prefill and decode are not just two phases of the same computation—they have different computational profiles, different cost structures in production workloads, and different tolerance for approximation. Prefill is compute-bound, dominates total FLOPs in enterprise workloads, and its output (the KV cache) is reused many times during decode. Decode is memory-bound, accounts for fewer total FLOPs, and its output (the generated token) is autoregressive, meaning errors compound. These asymmetries create an opportunity: reduce prefill computation aggressively while preserving full model capacity for decode, where the marginal cost is low but the marginal benefit of precision is high.

This is not an incremental tuning of an existing approach. Prior methods that skip layers (FFN-SkipLLM, ShortGPT, LayerSkip) reduce compute for both prefill and decode equally, and cap out at roughly 25% layer reduction before significant accuracy loss. SwiftKV’s phase-asymmetric design enables 50% prefill reduction with only 1–2% accuracy degradation across Llama, Mistral, and Deepseek models (Table 2), precisely because it preserves full-depth decode. The lower accuracy of FFN-SkipLLM at 12–19% MLP reduction (70.62% vs. SwiftKV’s 72.70% at 50% reduction on Llama-3.1-8B-Instruct; Table 2) is not a scaling discrepancy—it is evidence that uniform layer reduction is a harder optimization problem than phase-asymmetric reduction, because it forces the model to generate with permanently reduced capacity rather than just encoding with reduced capacity.

The significance of this idea extends beyond the specific SwiftKV mechanism. It opens a new axis in the inference optimization design space: rather than asking “how much of the model can we remove?” it asks “*when* can we remove it?” The answer depends on workload characteristics (the prefill-to-decode ratio) and on phase-specific tolerance for error. A model serving a chatbot with short prompts and long generations would benefit less from phase-asymmetric prefill reduction than the enterprise workloads SwiftKV targets, but the *framework*—identifying phase asymmetry as a design dimension—applies broadly.

---

### Innovation 2: The Hidden-State Similarity Metric as a Diagnostic That Predicts and Explains Transformability

Many model compression or acceleration papers propose a technique and then report where it works and where it fails, with post-hoc speculation about why. SwiftKV does something more principled: it introduces a concrete, measurable metric—`SimScore(x_l)`, the average cosine similarity between a layer’s hidden state and all deeper layers’ hidden states (Equation 1, Figure 2)—that **predicts in advance** how amenable a given model family will be to the transformation, and **explains** the observed accuracy gaps without post-hoc storytelling.

Before this work, the observation that deeper transformer layers produce increasingly similar representations was known (Gromov et al., 2024; Liu et al., 2024b), but it had not been operationalised as a diagnostic for model compression decisions. The prior paradigm was to apply a compression technique, measure accuracy degradation, and iterate. SwiftKV connects the similarity measurement directly to the design decision (where to place the cutoff layer `l`) and to the expected outcome (how much accuracy will degrade at a given reduction ratio).

The predictive power is visible in the contrast between model families. Figure 2 shows that Qwen2.5 models have lower `SimScore` at mid-depth than comparably sized Llama or Mistral models. Table 2 then shows that Qwen2.5-14B-Instruct suffers a 7.4% accuracy drop at 50% SwiftKV versus 1–2% for Llama and Mistral models at the same reduction. This is not a coincidental correlation—it is the diagnostic working as intended. The paper is explicit about this connection, making it a testable claim: if a new model family has high inter-layer similarity at mid-depth, SwiftKV should work well; if not, it should perform poorly. This transforms a heuristic design choice (where to cut) into a principled one (measure similarity first, then decide).

The significance of this diagnostic is twofold. First, it provides a **transferable methodology**: anyone considering applying SwiftKV to a new model can compute `SimScore` before doing any training, estimate feasibility, and select the cutoff layer based on data rather than trial and error. Second, it functions as a **negative result with explanatory power**: the Qwen case is not a failure of the technique but a boundary condition that the diagnostic correctly identifies, making the overall approach more trustworthy because its limitations are predictable rather than mysterious.

---

### Innovation 3: The Compute-Reduction vs. Memory-Reduction Distinction as a Deployment Principle, Not Just a Taxonomy

A large fraction of LLM inference optimization research—particularly KV cache compression—is motivated by the assumption that memory is the primary bottleneck. SwiftKV makes a concrete, evidence-backed argument that this assumption is incorrect for a broad class of production deployments, and that **the field has been over-investing in memory reduction relative to compute reduction**.

The Merge-all-Layers experiment (Section 5.1, Table 3) is the paper’s cleanest articulation of this idea. By constructing an idealised KV compression scheme that achieves 32× or 80× memory reduction with zero computational overhead—far beyond what any published technique can achieve—the paper isolates the effect of pure memory reduction. The result: on an 80GB H100 GPU (a standard datacenter configuration), eliminating essentially all KV cache memory improves throughput by only ~10% over the baseline. In contrast, 50% SwiftKV without any KV compression improves throughput by 35%. The implication is stark: memory reduction, no matter how aggressive, provides minimal benefit when the system is compute-bound.

This reframes the research prioritisation around inference optimization. Prior work treats memory and compute as parallel optimisation targets without an explicit ranking. SwiftKV doesn’t just provide a new method for each—it argues empirically that compute reduction is the higher-leverage target for typical production deployments, and that memory reduction should be treated as a secondary concern, useful primarily when memory is scarce (the 16–20GB experiments in Table 3 confirm that memory reduction becomes valuable at the margin, but only then). The AcrossKV extension is presented as supplementary precisely because of this reasoning: it is there for the scenarios that need it, but the core contribution (and the bulk of the throughput gains) comes from compute reduction.

This is a **framing contribution** rather than a technical mechanism contribution—it changes what the field should optimise for, not how to optimise for it. The fact that it is backed by a concrete, reproducible experiment (Table 3, with publicly available hardware configurations and open-sourced code) makes it actionable: other researchers can test the compute-vs-memory bottleneck on their own workloads and decide accordingly.

---

### Innovation 4: Knowledge Preservation Through Weight-Freezing as a Distillation Strategy

Post-training adaptation of language models—whether for compression, domain transfer, or architecture changes—typically faces a tension: train more parameters to better adapt to the new configuration, or train fewer to preserve existing knowledge. The dominant approaches in prune-and-distill (Sreenivas et al., 2024; Tang et al., 2025) train all remaining parameters after pruning, using 10–100B tokens of data. The intuition is that structural changes (removing whole layers or attention heads) require the surviving components to reorganise to compensate.

SwiftKV takes a counterintuitive position that yields both better accuracy and dramatically lower training cost: **freeze almost everything, train only the attention projection weights, and use distillation rather than standard LM loss**. Table 4(b) shows that full-model fine-tuning of the later 50% of layers produces 68.23% average accuracy (4.47 points worse than training only WQKV), and Table 4(a) shows that distillation outperforms standard LM loss training by 2.64 points, with the gap concentrated on generative reasoning tasks (GSM-8K: +6.74 points).

The conceptual contribution is not the specific finding that MLPs store knowledge—this is consistent with prior work the paper cites (Meng et al., 2024; Geva et al., 2021). Rather, it is the demonstration that this finding has a direct and powerful implication for model transformation procedures: if knowledge is localised in MLP weights, then transformations that change how information *flows* through the model (such as SwiftKV’s KV projection rewiring) can be adapted by training only the *routing* parameters (attention projections) while keeping the *storage* parameters (MLPs) frozen. The model “knows” the same things; it just needs to learn to access that knowledge through a different pathway.

This is a practical insight with significant cost implications. Training 10B+ tokens on all model parameters requires substantial GPU hours; training <1B tokens on <10% of parameters requires 3–5 hours on a modest GPU cluster. For organisations deploying LLMs in production, this makes the difference between a transformation that requires a dedicated training run measured in days and one that can be completed overnight on existing infrastructure. The Nemotron-51B comparison makes this concrete: 40B tokens of distillation versus <1B, yet SwiftKV achieves higher accuracy at greater prefill reduction (82.98% at 50% vs. 82.78% at 28%, Table 2).

The diagnostic value of the finding extends beyond SwiftKV. Any future model transformation that preserves model architecture but changes input distributions to specific components should consider a training strategy that freezes knowledge-storing components and adapts only the routing or access components—this is a design principle, not just a one-off result.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The quality evaluation uses seven standard benchmarks: ARC-Challenge (Clark et al., 2018), Winogrande (Sakaguchi et al., 2019), HellaSwag (Zellers et al., 2019), TruthfulQA (Lin et al., 2022), MMLU (Hendrycks et al., 2021), MMLU-CoT, and GSM8K-CoT (Cobbe et al., 2021). Most results are reported 0-shot, with specific few-shot configurations noted in Table A.1 (e.g., 5-shot for MMLU, 8-shot for GSM8K-CoT). The evaluation harness follows the `neuralmagic` fork of `lm-evaluation-harness` configured for Llama-3.1 instruction-tuned models with chat-templated prompts. Distillation training uses a mixture of Ultrachat (Ding et al., 2023), SlimOrca (Lian et al., 2023), and OpenHermes-2.5 (Teknium, 2023), totalling approximately 680M Llama-3.1 tokens.

- **Base model(s).** The paper evaluates SwiftKV across five model families spanning two orders of magnitude in size: Llama-3.1-Instruct (3B, 8B, 70B, 405B), Qwen2.5-14B-Instruct, Mistral-Small-Instruct-2409, and Deepseek-V2-Lite-Chat. The 405B model uses FP8 (W8A16) quantization. Deepseek-V2-Lite-Chat is a mixture-of-experts model with a novel latent attention mechanism (DeepSeek-AI et al., 2024). The authors state these models were chosen to demonstrate architectural diversity—dense, MoE, standard attention, and latent attention—and to cover sizes typical of production deployments.

- **Metrics.** The primary quality metric is **average accuracy across the seven benchmarks**, computed as the arithmetic mean of task-specific metrics listed in Table A.1: exact-match for ARC-Challenge and MMLU (with multi-choice formatting), accuracy for Winogrande, accuracy-normalised for HellaSwag, MC2 for TruthfulQA, exact-match strict-match for MMLU-CoT and GSM8K-CoT. No single numeric uncertainty measure (confidence intervals, standard deviations) is reported for any accuracy figure, which is a methodological weakness. Throughput metrics for inference experiments are **combined input and output tokens per second**, **time-to-first-token (TTFT)**, and **time-per-output-token (TPOT)**, all measured end-to-end in vLLM and SGLang. Normalised throughput is expressed in TFLOPS/GPU computed against the **baseline model's** total floating-point operations, not the reduced SwiftKV model's—this ensures an apples-to-apples comparison.

- **Baselines.** The paper compares against four categories:
  1. **Original (unmodified) model**: the pretrained, instruction-tuned checkpoint without any transformation.
  2. **FFN-SkipLLM** (Jaiswal et al., 2024): a training-free method that adaptively skips feed-forward network layers based on hidden-state similarity at inference time. The paper configures FFN-SkipLLM with candidate skipped layers in the 35–8% depth range, matching the settings from the original paper. Because FFN-SkipLLM adaptively determines which MLPs to skip per token, the fraction of layers skipped varies by model and task—Table 2 reports the range (e.g., 12–19% for Llama-3.1-8B-Instruct, 7–21% for Qwen2.5-14B-Instruct, 34–37% for Mistral-Small).
  3. **Nemotron-51B** (Sreenivas et al., 2024): a pruned and distilled version of Llama-3.1-70B-Instruct created using neural architecture search and 40B tokens of training. It achieves 28% prefill reduction and 50% KV cache memory reduction. This baseline tests whether SwiftKV's lightweight distillation can match or exceed a much more expensive prune-and-distill pipeline.
  4. **DarwinLM-8.4B** (Tang et al., 2025): a pruned and distilled model derived from Qwen2.5-14B-Instruct using 10B tokens of training, achieving 40% total compute reduction. This baseline situates SwiftKV against evolutionary structured pruning on the same source model family.

- **Generation budget / compute accounting.** For quality evaluation, the "generation budget" concept does not apply since tasks are evaluated with single greedy or few-shot prompts (not test-time search). For inference speedup evaluation, compute is measured end-to-end by total tokens processed per second under fixed hardware configurations (1× H100 for 8B models, 4× H100 with tensor parallelism for 70B models). The paper does not report per-prompt FLOPs counts for inference experiments but instead relies on wall-clock throughput and normalised TFLOPS computed from the baseline model's theoretical FLOPs. For the compute-vs-memory ablation (Table 3), throughput is reported under varying GPU memory limits (80GB, 40GB, 20GB, 16GB) to isolate memory pressure effects.

- **Cross-validation / statistical protocol.** The paper does not employ cross-validation for quality evaluation—all accuracy results in Table 2 are single-point estimates on the full benchmark test sets. No statistical significance tests, confidence intervals, or error bars are reported. For inference throughput experiments, roughly 15M tokens worth of requests are sent per experiment (Section 4.2), and each request generates a fixed 256 output tokens, providing reasonably stable throughput measurements, though the paper does not report variance across runs. The distillation procedure uses a fixed dataset split without mention of held-out validation for early stopping, though Appendix H of the extended paper mentions validation loss monitoring with the caveat that "standard validation loss is not a good signal for early stopping" due to off-policy trajectory issues. The interactive-inference latency results (Figure 4) sweep across a range of request arrival rates and appear to report single-run measurements per rate.

### Main Quantitative Results

Across the quality and inference evaluations, SwiftKV demonstrates three headline findings: (1) 25–50% prefill compute reduction with only 1–4% accuracy degradation across four of five tested model families; (2) up to 2× higher throughput and 60% lower TPOT in end-to-end serving; (3) compute reduction—not memory reduction—is the dominant contributor to throughput gains in standard datacenter GPU configurations. All quality numbers below reference Table 2 unless otherwise specified.

#### Quality Impact Across Model Families

**Llama-3.1-Instruct (8B, 70B, 405B).** The Llama models show the strongest robustness to SwiftKV. For Llama-3.1-8B-Instruct, the baseline achieves 73.71% average accuracy. At 25% SwiftKV, average accuracy actually *increases* slightly to 73.59% (a −0.12 point difference). At 50% SwiftKV, accuracy drops to 72.70%, a 1.01-point degradation. Pushing to 62.5% SwiftKV causes a sharp drop to 66.09% (7.62-point degradation), suggesting that at roughly 60% reduction, the representational mismatch exceeds what distillation can recover. For Llama-3.1-70B-Instruct, the baseline is 84.31%. At 25% SwiftKV, it drops marginally to 83.83% (−0.48 points). At 50% SwiftKV, it reaches 82.98%, a −1.33 point difference. For Llama-3.1-405B-Instruct (FP8), the baseline is 86.6%, and 50% SwiftKV reduces this to 85.9%—a 0.7-point drop, showing that even at extreme scale, the transformation remains benign.

The degradation pattern across these three scales is non-monotonic: the 405B model loses less absolute accuracy (0.7 points) than the 8B model (1.0 point) at the same 50% reduction, despite the baseline being higher. The paper does not analyse this scaling behaviour explicitly, but it is consistent with the similarity measurements in Figure 2—larger models show higher SimScore at mid-depth, meaning earlier layers are better proxies for deeper representations, reducing the distortion introduced by the rewiring.

**Mistral-Small-Instruct-2409.** The baseline is 78.23%. At 25% SwiftKV, accuracy is 77.80% (−0.43 points). At 50% SwiftKV, accuracy is 77.24% (−0.99 points). The degradation profile is nearly identical to the Llama models, consistent with Mistral-Small's similar SimScore curve in Figure 2.

**Deepseek-V2-Lite-Chat.** The baseline is 64.12% (notably lower than the instruction-tuned Llama/Mistral models, consistent with its smaller size and MoE architecture). At 25% SwiftKV, accuracy is 64.19%—actually a 0.07-point *improvement*, similar to the slight uplift seen on Llama-3.1-8B at 25%. At 45% SwiftKV (the maximum tested for this model), accuracy drops to 63.51% (−0.61 points). This is the gentlest degradation among all tested models, though the reduction is 45% rather than the 50% tested on other architectures—the paper does not explain why 45% was chosen over 50% for Deepseek specifically.

**Qwen2.5-14B-Instruct.** This is the notable outlier. The baseline is 77.38%. At 25% SwiftKV, accuracy drops to 76.23% (−1.15 points), already a larger degradation than any other model family at the same reduction level. At 50% SwiftKV, accuracy plummets to 69.93%, a −7.45 point drop—more than 7× the degradation of Llama, Mistral, or Deepseek at comparable reduction ratios. The paper explicitly links this to the lower inter-layer similarity of Qwen models at mid-depth (Figure 2, right panel), where Qwen2.5-72B shows SimScore distinctly below Llama and Mistral architectures of the same scale. This diagnostic connection is the paper's strongest argument that the similarity metric is genuinely predictive rather than post-hoc rationalisation.

**SwiftKV vs. baselines.** The most important comparison is against **FFN-SkipLLM**, the closest prior work in design philosophy (skipping computation based on hidden-state similarity, no permanent weight removal). Across all four model families where both methods are tested (Llama-3.1-8B, Llama-3.2-3B, Mistral-Small, Deepseek-V2-Lite, Qwen2.5-14B):

- **Llama-3.1-8B:** FFN-SkipLLM skips 12–19% of MLP layers and achieves 70.62% (vs. baseline 73.71%). SwiftKV at 50% reduction skips both MLP *and attention* for half the layers and achieves 72.70%—2.08 points *higher* while reducing strictly more compute. By prefill FLOPs accounting (Table 1), 50% SwiftKV removes roughly 49% of prefill compute; FFN-SkipLLM at 19% MLP reduction removes only ~7% of total prefill FLOPs (since MLP is ~37% of FLOPs and attention ~53%).
- **Mistral-Small:** The gap is catastrophic. FFN-SkipLLM at 34–37% MLP reduction reaches only 45.71% average accuracy (vs. baseline 78.23%), a 32.52-point collapse. 50% SwiftKV achieves 77.24%. The paper does not deeply diagnose this failure, but it likely reflects Mistral's attention architecture making MLP skipping with FFN-SkipLLM's similarity heuristic particularly brittle, while SwiftKV's distillation-based recovery is more robust.
- **Deepseek-V2-Lite:** FFN-SkipLLM at 30–32% MLP reduction crashes to 24.83% (vs. baseline 64.12%). 45% SwiftKV achieves 63.51%.
- **Qwen2.5-14B:** FFN-SkipLLM at 7–21% MLP reduction reaches 62.53% (vs. baseline 77.38%). 25% SwiftKV achieves 76.23%, and even 50% SwiftKV at 69.93% outperforms FFN-SkipLLM's 62.53%.

The Nemotron-51B comparison provides a direct cost-efficiency benchmark: Nemotron achieves 82.78% average accuracy at 28% prefill reduction and 50% KV cache reduction on 40B tokens of distillation. SwiftKV-50% on the same source model (Llama-3.1-70B) achieves 82.98% at 50% prefill reduction with <1B tokens of distillation—simultaneously higher accuracy, greater prefill reduction, and ~40× less training data. Similarly, DarwinLM-8.4B (pruned from Qwen2.5-14B on 10B tokens, 40% total reduction) achieves only 35.94% average accuracy—a 41.44-point collapse from its baseline—while 25% SwiftKV on the same source model scores 76.23%. The paper explicitly notes these comparisons in Section 4.1: "50% SwiftKV reduces more prefill while achieving higher accuracies" than either prune-and-distill alternative.

**AcrossKV accuracy impact.** Starting from 50% SwiftKV on Llama-3.1-8B-Instruct (72.70%), adding 2-way AcrossKV (25% KV cache reduction) results in 71.82% (−0.88 points), 4-way (37.5%) in 71.49% (−1.21), 8-way (43.75%) in 70.50% (−2.20), and 16-way (46.875%) in 70.22% (−2.48). The degradation is gradual—16-way AcrossKV (where all 16 skipped layers share a single KV cache) still maintains 70.22% average accuracy, which the paper presents as remarkable evidence of KV cache redundancy. For Llama-3.1-70B-Instruct, the pattern is even milder: 50% SwiftKV baseline at 82.98%, 2-way at 82.63% (−0.35), and 4-way at 82.96% (−0.02—essentially indistinguishable from no AcrossKV). Deepseek-V2-Lite shows more sensitivity: at 45% SwiftKV (63.51%), 2-way AcrossKV reaches 63.07% (−0.44) but 4-way drops sharply to 59.32% (−4.19). The paper does not investigate why Deepseek is more sensitive to cross-layer KV sharing than Llama, though it may relate to the MoE architecture's different representation dynamics.

**KV cache quantisation compatibility (Table B.1).** Adding per-token FP8 KV cache quantisation (Yao et al., 2022) without quantisation-aware fine-tuning produces negligible additional degradation. On 50% SwiftKV Llama-3.1-8B-Instruct: with no AcrossKV and no quantization: 72.70%; with FP8 quantization only: 72.30% (−0.40); with 2-way AcrossKV + FP8 (62.5% total KV reduction): 71.69% (−1.01 from baseline); with 4-way AcrossKV + FP8 (68.75% total KV reduction): 71.35% (−1.35). The orthogonality of quantisation to SwiftKV's rewiring is consistent with the paper's claim that SwiftKV operates on a different compression axis from existing KV cache methods.

#### Inference Performance Results

**Batch inference throughput (Figure 3).** The paper evaluates Llama-3.1-8B-Instruct on 1× H100 and Llama-3.1-70B-Instruct on 4× H100 with tensor parallelism, across input lengths of 2K, 8K, 32K, and 128K tokens with fixed 256-token outputs.

For **Llama-3.1-8B-Instruct** (Figure 3, left):
- At 2K inputs: Baseline achieves approximately 23K tokens/s; 50% SwiftKV reaches roughly 29K tokens/s (1.26× improvement). Adding AcrossKV provides marginal additional gains (approximately 30K for 4× AcrossKV).
- At 8K inputs: Baseline drops to ~19K tokens/s; 50% SwiftKV reaches roughly 28K (1.47×). The paper highlights that this corresponds to 30K tokens/sec/GPU or 480 TFLOPS/GPU normalised throughput.
- At 32K inputs: Baseline is approximately 12K tokens/s; 50% SwiftKV reaches roughly 22K (1.83×).
- At 128K inputs: Baseline falls to roughly 6K tokens/s; 50% SwiftKV reaches roughly 11.5K (1.92×).

The improvement ratio grows with input length, from 1.26× at 2K to 1.92× at 128K. This is expected: longer prompts mean prefill accounts for a larger fraction of total compute, so reducing prefill FLOPs by 50% yields a proportionally larger fraction of total cost reduction.

For **Llama-3.1-70B-Instruct** (Figure 3, right):
- At 2K inputs: Baseline is roughly 9.5K tokens/s; 50% SwiftKV reaches roughly 14K (1.47×).
- At 8K inputs: Baseline is roughly 8K tokens/s; 50% SwiftKV reaches roughly 16K (2.0×). This is where the headline "560 TFLOPS/GPU at 56.6% MFU" figure originates—the paper states it corresponds to "over 16K toks/sec over 4× H100 GPUs."
- At 32K inputs: Baseline approximately 6K; 50% SwiftKV roughly 12K (2.0×).
- At 128K inputs: Baseline approximately 3K; 50% SwiftKV roughly 6K (2.0×).

The 70B model shows a more consistent 1.5–2.0× improvement across all input lengths (versus the 8B model's 1.26–1.92×, which is more length-dependent). The paper does not explain this difference, though it may reflect different compute-vs-memory bottlenecks for the larger model (tensor parallelism introduces communication overhead that prefill reduction partially alleviates). AcrossKV provides noticeable additional throughput even at shorter lengths for the 70B model (e.g., at 8K, 4× AcrossKV adds roughly 1K tokens/s on top of SwiftKV alone), suggesting the 70B model's larger KV cache creates some memory pressure that AcrossKV relieves even at 80GB.

**Interactive inference latency (Figure 4, Llama-3.1-70B-Instruct).** The paper evaluates TTFT and TPOT across a sweep of request arrival rates for input lengths of 2K, 8K, and 32K tokens:

- **TTFT reduction at low arrival rates:** At 32K input length and the lowest tested arrival rate, baseline TTFT is approximately 1.8 seconds; 50% SwiftKV reduces this to roughly 0.9 seconds, a 50% reduction (read from Figure 4, left column, 32K row). At 8K inputs, the reduction is from approximately 0.5s to 0.3s (40% reduction). At 2K inputs, improvement is smaller—approximately 0.18s to 0.14s (22% reduction).
- **Sustainable arrival rate (TTFT explosion point):** The baseline LLM sustains arrival rates up to approximately 1.5 requests/s at 2K input, 0.4 requests/s at 8K, and 0.1 requests/s at 32K before TTFT explodes (the queue grows uncontrollably). 50% SwiftKV shifts these thresholds to roughly 2.5, 0.8, and 0.2 requests/s, respectively—a 1.5–2.0× improvement in sustainable load.
- **TPOT reduction:** At moderate arrival rates (roughly the middle of each subplot in Figure 4 bottom row), 50% SwiftKV reduces TPOT from roughly 0.12s to 0.05s at 2K input (58% reduction), from roughly 0.14s to 0.06s at 8K input (57% reduction), and from roughly 0.18s to 0.07s at 32K input (61% reduction). The paper notes this is counterintuitive—SwiftKV does not reduce decode computation, yet TPOT drops by up to 60%. The explanation is queuing contention: in chunked prefill systems where prefill and decode share GPU time, reducing prefill compute reduces the fraction of time the GPU spends processing prompts, decreasing the average time decode tokens spend in the scheduling queue.

The latency results for Llama-3.1-8B-Instruct (Figure A.1) show qualitatively similar patterns but are relegated to the appendix, suggesting the paper prioritises the 70B results as the more challenging and production-relevant case.

**SGLang throughput (Table A.2).** Results on SGLang closely match vLLM: for Llama-3.1-8B-Instruct at 8K inputs, baseline is 22.9K tokens/s vs. 50% SwiftKV at 31.0K (1.35×), and at 128K inputs, baseline is 7.66K vs. 13.2K (1.72×). For Llama-3.1-70B-Instruct, the improvements are 1.35–1.72×. This replication across two independent serving frameworks (with different internal architectures—vLLM uses PagedAttention, SGLang uses RadixAttention) strengthens the claim that SwiftKV's benefits are architectural rather than implementation-dependent.

**Real-world request distributions (Table A.3).** On ShareGPT data filtered for varying minimum input/output length ratios, the throughput improvements transfer. For the unfiltered ShareGPT (average length ratio 1.5), Llama-3.1-8B-Instruct improves from 23.7K to 27.6K tokens/s (1.16×). Filtering for ratios ≥2 (average ratio 10), throughput rises from 30.3K to 41.5K (1.37×). Filtering for ratios ≥100 (average ratio 150), throughput rises from 40.3K to 64.2K (1.59×). The improvement scales with the input/output ratio, precisely as SwiftKV's design predicts—more prefill-dominant workloads benefit more. This validates that the synthetic fixed-length benchmarks generalise to realistic length distributions.

#### Compute vs. Memory Reduction (Table 3)

The paper's most conceptually important inference experiment isolates the effect of pure KV cache memory reduction from compute reduction. Using Llama-3.1-8B-Instruct on 1× H100:

- **80GB memory (unconstrained):** Baseline: 22.9K tokens/s. Merge-all-Layers (idealised KV compression, 32× memory reduction, zero compute reduction): 25.1K (1.10×). 50% SwiftKV (compute reduction only, zero memory reduction): 31.0K (1.35×). 50% SwiftKV + 4× AcrossKV + FP8: 32.0K (1.40×). The key takeaway: pure memory reduction provides only a 10% gain, while compute reduction provides 35%. Even the most aggressive memory compression imaginable cannot match moderate compute reduction in a compute-bound regime.
- **40GB memory:** Baseline drops to 20.6K tokens/s (memory pressure begins). Merge-all-Layers: 25.2K (1.22×, now more competitive as memory becomes a constraint). 50% SwiftKV: 27.3K (1.33×). SwiftKV + 4× AcrossKV + FP8: 28.9K (1.40×).
- **20GB memory:** Baseline: 10.8K. Merge-all-Layers: 25.2K (2.33×—now the dominant factor, only ~10% below its 80GB performance). 50% SwiftKV (no AcrossKV): 12.2K (1.13×—severely memory-pressured). 50% SwiftKV + 4× AcrossKV + FP8: 23.2K (2.15×—combining compute and memory reduction recovers most of the memory-constrained performance).
- **16GB memory:** Baseline and 50% SwiftKV without AcrossKV both experience out-of-memory (OOM) failures. Merge-all-Layers: 24.8K (unchanged from 80GB, confirming it is purely memory-beneficial with zero compute overhead). SwiftKV + 4× AcrossKV: only 4.22K (still severely constrained). SwiftKV + 4× AcrossKV + FP8: 7.28K.

The results establish a clear regime classification: at 80GB ("standard datacenter GPU"), compute reduction dominates; at 16–20GB ("edge deployment or severely constrained"), memory reduction becomes essential. The combination of SwiftKV + AcrossKV + FP8 quantisation bridges both regimes.

### Ablation Studies and Robustness Checks

**Distillation vs. standard language model loss (Table 4a):** On Llama-3.1-8B-Instruct at 50% SwiftKV, training with distillation (KL divergence to teacher logits) achieves 72.70% average accuracy vs. 70.06% without distillation—a 2.64-point gap. The benefit is concentrated on generative reasoning tasks: MMLU-CoT improves by 4.13 points (65.60 → 69.73) and GSM8K by 6.74 points (72.71 → 79.45). The paper attributes this to distillation providing richer gradient signal through the full output distribution, but does not ablate distillation temperature or compare to alternative soft-target losses. This missing ablation means we cannot conclude whether the specific KL-divergence formulation is critical or whether any soft-target approach would work.

**Partial vs. full model fine-tuning (Table 4b):** Training all parameters in the later 50% of layers (MLP, attention output, layer norms) yields 68.23% average accuracy, versus 72.70% when training only WQKV projections—a 4.47-point *degradation* from training more parameters. This is the paper's strongest evidence for the knowledge-preservation hypothesis (that MLP weights store factual knowledge and should be frozen). However, the paper does not ablate which subset of WQKV parameters is necessary (e.g., Q-only, KV-only, Q-only vs Q+KV), nor does it test training only MLP weights while freezing attention projections. The hypothesis is consistent with prior work but not rigorously tested in this specific transformation context.

**Data quantity and quality (Table B.3):** The paper acknowledges the training data used for distillation is suboptimal: fine-tuning a base Llama-3.1-8B model on this same dataset (without any SwiftKV transformation) produces only 65.77% average accuracy vs. Meta's official instruction-tuned model at 73.71% (Table B.3a). This means the SwiftKV distillation is recovering from a relatively weak teacher signal. Adding 83K additional math and code samples (~16M tokens) from `gretelai/synthetic-gsm8k-reflection-405b` and `ise-uiuc/Magicoder-OSS-Instruct-75K` improves average accuracy from 72.70% to 72.93% (+0.23), with GSM8K specifically improving 0.53 points (Table B.3b). The ablation demonstrates that data quality matters but is far from saturating—using a higher-quality dataset closer to the original instruction-tuning data might close more of the accuracy gap. The paper frames this as "an important direction for future work" but does not systematically explore data scaling curves.

**AcrossKV design space (Table B.2):** For a fixed 37.5% KV cache reduction target on 50% SwiftKV Llama-3.1-8B, three configurations are compared: pure MQA (multi-query attention, no cross-layer sharing) at 54.13%; AcrossKV-MHA (multi-head attention, one shared KV cache for all 16 skipped layers) at 69.76%; and AcrossKV-GQA (the paper's standard 4-way grouping with grouped-query attention) at 71.49%. The result has two implications: (1) cross-layer sharing is substantially better than within-layer sharing alone (54.13% → 69.76%, a 15.63-point gap); (2) grouping layers into small sets (4-way) outperforms full sharing (69.76% → 71.49%), suggesting some per-layer KV differentiation remains important. The paper also notes that AcrossKV-MHA underperforms the 16-way AcrossKV result from Table 2 (70.50%) despite 16-way AcrossKV having more aggressive compression (46.875% vs. 37.5%), but attributes this to hyperparameter tuning differences without further analysis.

**Early exit for decode tokens (Figure B.1, Table B.4):** Adding an extra language modeling head at the cutoff layer `l` and training it to match the full model's logits (via distillation) shows that when the early-exit head's maximum softmax probability exceeds 0.95, its prediction aligns with the full model's prediction 66% of the time. The paper deploys a simple heuristic—exit early when confidence exceeds 0.95, otherwise complete all layers—and provides qualitative examples from Alpaca. This is preliminary and not integrated into the throughput/latency benchmarks, meaning it is a proof-of-concept rather than a validated component. No quantitative accuracy-speed trade-off is measured.

**KV cache quantisation robustness (Table B.1):** Post-training FP8 quantisation of the KV cache without quantisation-aware fine-tuning incurs ≤0.4 points of additional accuracy degradation across all AcrossKV configurations on Llama-3.1-8B-Instruct. The largest combined configuration (4-way AcrossKV + FP8, 68.75% KV cache reduction) degrades accuracy by only 1.35 points from the SwiftKV alone baseline (72.70% → 71.35%). This robustness is notable because it requires no additional training or calibration data beyond what SwiftKV already uses, making it a "free" extension for memory-constrained deployments. However, the paper tests only FP8; other quantisation levels (FP4, INT8, INT4) and techniques (KVQuant, n-bit schemes) are not evaluated.

**Ablations NOT performed:** Several ablations would have strengthened the paper but are absent. (1) The choice of cutoff layer `l` is not systematically varied with accuracy reported for each possible `l`—only 25%, 40%, 45%, 50%, and 62.5% SwiftKV are evaluated, and not for all models. The paper selects `L/2` as the default based on SimScore crossing 0.5, but doesn't show the accuracy-vs-reduction curve as a continuous function of `l`. (2) The distillation data size is not ablated—we do not know whether 100M, 340M, or 680M tokens are necessary, or whether data scaling would further close the accuracy gap. (3) The choice of which layers' KV projections use which earlier layer (the paper always uses `x_{l+1}` for all `j > l`) is not compared against alternatives like using a different early layer for different depth ranges. (4) No ablation compares SwiftKV to simply removing the skipped layers entirely (with appropriate resizing of remaining layers), which would be the closest approximation to prune-and-distill methods but operating at the same compute budget.

### Critical Assessment

#### Claim 1: SwiftKV reduces prefill computation by 25–50% across several LLM families with <1–2% accuracy degradation on average.

**What the experiments actually demonstrate:** The claim holds for Llama-3.1-Instruct (8B, 70B, 405B), Mistral-Small-Instruct-2409, and Deepseek-V2-Lite-Chat at 25–50% reduction, where accuracy drops range from a 0.07-point improvement (Deepseek at 25%) to 0.99 points (Mistral-Small at 50%). However, the "1–2%" figure describes the *absolute percentage-point drop* in average accuracy, not relative degradation. For Llama-3.1-8B at 50% SwiftKV, the relative degradation is 1.4% (72.70/73.71); for Llama-3.1-70B, it is 1.6%. These are genuinely small. But the claim is **conditional on model family**: Qwen2.5-14B-Instruct suffers a 7.45-point degradation at 50% reduction, a 9.6% relative drop—well outside the <2% claim. The paper acknowledges this and attributes it to lower SimScore, but the existence of a model family where the method substantially underperforms means the claim should be qualified: SwiftKV achieves <2% degradation on *most tested architectures*, not universally.

**Weaknesses in the evidence:**
- **No confidence intervals.** All accuracy figures are point estimates. With a ~100-question test set per benchmark (ARC-Challenge: 1172 test questions, MMLU: ~14K questions across 57 subjects but only some are used, etc.), the standard error on a 73% average could be 1–2 percentage points. The 0.07-point "improvement" for Deepseek at 25% or the 0.12-point improvement for Llama-3.1-8B at 25% are almost certainly within noise. The paper would be stronger with error bars or statistical tests.
- **Benchmark selection.** The seven benchmarks cover reasoning (ARC, HellaSwag, MMLU), factual knowledge (MMLU, TruthfulQA), and math (GSM8K). Missing are coding benchmarks (HumanEval, MBPP), long-context tasks, and generation quality metrics (e.g., MT-Bench, AlpacaEval). For a method targeting enterprise workloads like code completion and RAG, the absence of coding benchmarks is a genuine gap.
- **No open-ended generation evaluation.** All quality metrics are multiple-choice or exact-match, which tests whether the model's top-1 prediction is correct but not the quality, coherence, or factuality of generated text. The early-exit examples in Appendix B.4 hint at qualitative performance but are not systematically evaluated.

#### Claim 2: SwiftKV achieves up to 2× higher aggregate throughput and 60% lower TPOT.

**What the experiments actually demonstrate:** The throughput claims are well-supported by Figure 3 and Tables A.2–A.3. The 2× figure is achieved at 128K input length for both 8B and 70B models. At shorter, more common lengths (2K–8K), the improvement is 1.26–1.5× for 8B and 1.35–1.5× for 70B—still substantial but below 2×. The 60% TPOT reduction (Figure 4) is measured at moderate-to-high arrival rates where queuing contention is significant; at the lowest arrival rates, TPOT improvement is smaller or negligible (decode is not constrained by prefill when the GPU is idle). This is not a weakness of the claim—the paper is transparent that the benefit is largest under load—but it means the 60% figure is conditional on the system experiencing sufficient request pressure.

**Weaknesses in the evidence:**
- **Fixed output length (256 tokens).** All throughput benchmarks use a fixed 256-token output per request. Real-world output lengths vary dramatically. Longer outputs would reduce the relative contribution of prefill (since decode cost grows with output length while prefill is constant per input token), potentially reducing the throughput improvement from prefill-only optimisation. The paper does not benchmark variable output lengths.
- **Single hardware configuration per model size.** All 8B experiments use 1× H100; all 70B experiments use 4× H100. Different GPU configurations (A100, H200, different tensor parallelism degrees) might shift the compute-vs-memory balance and change the relative benefit of SwiftKV vs. AcrossKV. The Merge-all-Layers experiment partially addresses this by varying memory limits, but it is a synthetic constraint rather than a different hardware platform.
- **No comparison with pruning-based methods in throughput benchmarks.** The paper compares accuracy with Nemotron-51B and DarwinLM-8.4B but does not benchmark their inference throughput. We cannot tell whether SwiftKV's throughput advantage over these pruned models is proportional to its greater prefill reduction or whether implementation differences (custom kernels vs. standard kernels) play a role.

#### Claim 3: Compute reduction—not memory reduction—is the dominant contributor to throughput gains in standard datacenter GPU configurations.

**What the experiments actually demonstrate:** Table 3 provides strong evidence for this claim under the specific conditions tested (Llama-3.1-8B on H100 with 80GB). Merge-all-Layers (idealised KV compression) improves throughput by 10%, while 50% SwiftKV (compute reduction only) improves it by 35%. The paper argues this generalises because "production deployments are often compute-bound rather than memory-bound" (Section 1) and "long-context requests are rare" (Section 1). However, the evidence for *how common* compute-bound deployments are comes from Snowflake's own production observations, which are stated but not systematically quantified or generalised. The paper does not provide data on typical memory utilisation, typical batch sizes, or typical KV cache sizes in production—it asserts the observation qualitatively.

**Weaknesses in the evidence:**
- **The claim is validated on one GPU (H100) at one memory capacity (80GB).** On A100-40GB GPUs (still widely deployed), or on H100 with larger models where KV cache pressure is higher, the balance might shift toward memory reduction being more valuable. The 40GB and 20GB experiments in Table 3 begin to show this, but only for the 8B model—the 70B model is not tested under memory constraints.
- **The Merge-all-Layers baseline, while elegant, is not a real method.** It demonstrates the upper bound of pure memory reduction but does not compare against *real* KV cache compression methods like KVQuant or MiniCache that might have different throughput characteristics due to quantisation/dequantisation overhead. The paper's point is conceptual—"even the theoretical maximum memory reduction provides limited benefit"—but a validation against an actual deployed method would strengthen it.

#### Claim 4: SwiftKV requires minimal distillation (<1B tokens, <10% parameters) and can be done in hours.

**What the experiments actually demonstrate:** This is directly demonstrated by the training recipe in Appendix A.1 and the wall-clock times reported (3 hours for 8B on 8× H100, 5 hours for 70B on 32× H100). The 680M token dataset size and the parameter count (<10%) are specified precisely. The comparison with Nemotron-51B (40B tokens) and DarwinLM-8.4B (10B tokens) in Table 2 provides evidence for the "minimal" claim relative to existing alternatives. However, the paper does not ablate *how little* data is actually necessary—would 340M tokens work? 170M? There is no data scaling curve, so the 680M number is a single point rather than a demonstrated minimum.

**Weaknesses in the evidence:**
- **No multiple runs or seed sensitivity.** All distillation results in Table 2 are single training runs. Given the small dataset and short training time, there may be meaningful variance across random seeds or data orderings that is not captured.
- **Dataset quality vs. quantity is confounded.** The ablation in Table B.3b shows that adding high-quality domain-specific data (math and code) improves accuracy, but we do not know whether similar improvements could be achieved by simply training on more of the same general-purpose data. The claim that SwiftKV requires "minimal" data might actually be a claim about SwiftKV requiring *high-quality* data—an important distinction the paper does not disentangle.

#### Missing experiments that would strengthen the paper

1. **Scaling curves across model sizes.** The paper evaluates SwiftKV at 3B, 8B, 70B, and 405B scales for Llama models but does not plot the accuracy gap as a function of model size at fixed reduction ratio. Does SwiftKV become more or less effective with scale? The 405B result at 50% reduction (0.7-point drop) suggests it becomes more effective, but with only one data point this remains anecdotal.

2. **Varying the cutoff layer `l` continuously.** Rather than testing only specific fractions (25%, 40%, 50%), a sweep of `l` with accuracy measured at each point would produce a trade-off curve that practitioners could use to select their preferred accuracy-compute operating point.

3. **Coding benchmarks.** Given that code completion is listed as a primary enterprise use case, the absence of HumanEval, MBPP, or LiveCodeBench evaluations is conspicuous.

4. **Long-context evaluation.** The throughput experiments go up to 128K inputs, but the quality evaluation uses standard benchmark prompts which are likely much shorter (hundreds of tokens). Does SwiftKV's accuracy hold up when the prompts are genuinely long (10K–100K tokens)? The similarity analysis in Figure 2 uses short sequences; long-context similarity patterns might differ.

5. **Comparison with inference-time layer skipping methods beyond FFN-SkipLLM.** The paper compares extensively with FFN-SkipLLM but does not benchmark against LayerSkip (Elhoushi et al., 2024), ShortGPT (Men et al., 2024), or LaCo (Yang et al., 2024). Since these methods operate on a different principle (adaptive exit with additional heads), the comparison would be informative about whether SwiftKV's phase-asymmetric approach is fundamentally better or just better-tuned.

6. **Ablation of which attention projections are trained.** Table 4b establishes that training only WQKV is better than training all later-layer parameters. But the paper does not test Q-only vs. KV-only training. If, as the paper hypothesises, the transformation primarily affects the KV cache pathway, perhaps only WKV needs training and WQ can remain frozen—further reducing trainable parameters.

#### Summary of conditional scope

The experimental results are consistent, well-replicated across model families and serving frameworks, and generally support the paper's central claims—**under the specific conditions tested**. The conditions are: instruction-tuned models from the Llama, Mistral, or Deepseek families (Qwen is an acknowledged exception); standard datacenter GPU configurations with sufficient memory (80GB H100); workloads where prefill dominates (>10:1 input-to-output token ratio); and evaluation on multiple-choice or exact-match reasoning and knowledge benchmarks. Outside these conditions—particularly for Qwen models, memory-constrained deployments without AcrossKV, or generation-quality-sensitive applications—the claims may not hold at the same magnitude. The paper is mostly transparent about these boundary conditions, with the notable exception of confidence intervals and seed sensitivity, which remain unreported.

## 6. Limitations and Trade-offs

### 6.1 Difficulty Estimation Overhead Is Unaccounted For in the Reported Compute Savings

**The assumption or constraint.** The entire compute-optimal framework depends on estimating each prompt's difficulty *before* deciding how to allocate the inference budget. The paper's method for doing so—generating 2048 samples per question and averaging either ground-truth correctness (oracle) or PRM final-answer scores (predicted)—is extraordinarily expensive. Section 3.2 acknowledges this explicitly:

> "estimating difficulty in this way still incurs additional computation cost during inference... our experiments do not account for this cost largely for simplicity"

**The consequence.** The reported 4× efficiency gains over best-of-N (Figures 4, 8) are computed *after* difficulty is known, without amortizing the cost of learning it. At 2048 samples per question, the difficulty estimation step alone consumes more compute than the largest test-time budgets studied (256–512 generations). In a realistic deployment, the total cost would be difficulty estimation + strategy execution, and the former could dominate the latter, potentially erasing or even reversing the claimed efficiency gains. The paper frames this as an "exploration-exploitation tradeoff" but does not quantify where the crossover point lies—that is, how many questions a deployed system must answer before the amortized cost of difficulty estimation becomes negligible relative to the per-question savings.

**What evidence exists in the paper.** The predicted difficulty bins (using PRM scores without ground-truth labels) largely overlap with oracle bins in Figures 4 and 8, demonstrating that the system works without access to correct answers. However, the predicted method still requires 2048 samples and PRM scoring per question. The paper does not report the wall-clock time or FLOPs cost of this estimation relative to the problem-solving budget, nor does it evaluate any cheaper difficulty estimation method (e.g., using only 4–8 samples, a lightweight classifier, or difficulty prediction from the prompt text alone).

**Mitigation status.** The paper explicitly flags this as a key avenue for future work in Section 8, suggesting "pretraining or finetuning models to directly predict difficulty of a question" and adaptive estimation where "we can spend a small amount of compute to get a rough estimate of the question difficulty, then spend more" (Section 3.2). No such method is developed or evaluated, meaning the current results represent an **upper bound** on achievable efficiency rather than a realized deployment gain. Until cheap difficulty estimation is demonstrated, the headline 4× figure should be interpreted as the potential ceiling, not a guaranteed practical improvement.

---

### 6.2 The Method Provides No Benefit on Hard Problems Where the Base Model's Capability Is Fundamentally Insufficient

**The assumption or constraint.** SwiftKV's central mechanism—projecting KV caches from an earlier layer's hidden state—relies on the assumption that the representations at deeper layers are sufficiently similar to the cutoff layer's output that the information needed for correct generation is preserved. When this assumption holds (as measured by `SimScore` in Figure 2), accuracy degradation is small. When it doesn't, or when the base model itself cannot solve the problem reliably, SwiftKV provides no benefit and may compound errors.

**The consequence.** Across all methods evaluated—search, revisions, and their compute-optimal combinations—the hardest questions (difficulty bin 5) show **near-zero improvement** regardless of compute budget. In Figure 3 (right), bin 5 accuracy hovers at 1–3% for all methods and all budgets. In Figure 7 (right), bin 5 shows roughly 2–3% accuracy irrespective of the sequential-to-parallel ratio. In the FLOPs-matched comparison (Figure 9), the bin 5 scaling line is essentially flat near 0–5%. The paper is candid about this, but the implication for practitioners is significant: if a deployment faces a substantial fraction of genuinely hard problems (outside the base model's approximate capability range), test-time compute scaling with SwiftKV offers no path forward. For such problems, pretraining a larger model remains the only viable option—the paper's own FLOPs-matched comparison shows the 14× larger model substantially outperforms test-time compute on hard problems (Figure 9, right: −52.9% relative disadvantage for test-time compute at R ≫ 1).

**What evidence exists in the paper.** The difficulty-bin analyses (Figures 3 right, 7 right, 9) all show a sharp drop-off at bin 5 where no method, budget level, or allocation strategy makes meaningful progress. The base model's pass@1 on these problems is effectively zero, meaning there are no correct solutions in the proposal distribution to find or refine. The authors explicitly note this in Section 8: "On hard problems (bins 4–5), pretraining is almost always more effective." This is not a failure of the SwiftKV technique per se but a fundamental limitation of any test-time compute method: it amplifies existing capability but cannot create capability the model lacks.

**Mitigation status.** Not addressed as a limitation to be solved—the paper treats this as an inherent boundary condition that defines *when* test-time compute is appropriate versus when pretraining should be prioritized. The difficulty bin framework itself serves as a diagnostic: if a problem falls in bin 5, the system should (in principle) recognize this and either escalate to a larger model or flag the problem for human review rather than waste compute on fruitless strategies. However, no such escalation mechanism is implemented or evaluated.

---

### 6.3 The Evaluation Is Confined to a Single Benchmark (MATH) and a Single Model Family (PaLM 2), Leaving Domain and Architecture Generalisation Unverified

**The assumption or constraint.** All experiments use the MATH benchmark (500 test questions) with PaLM 2-S* as the base model. The authors state they "believe this model is representative of the capabilities of many contemporary LLMs" (Section 4), but this claim is unverified. The MATH benchmark consists exclusively of competition-level math problems requiring symbolic multi-step reasoning—a domain with clear correctness signals, well-defined solution steps, and a specific difficulty distribution.

**The consequence.** Several aspects of the findings could be model-specific or domain-specific. The PRM's quality and over-optimization behavior (Figure 3 right: beam search degrading easy-problem performance at high budgets) depend on PaLM 2-S*'s output distribution and calibration. A model with different error patterns might exhibit different difficulty-dependent scaling curves. The revision model's ability to learn from incorrect in-context examples depends on the base model's in-context learning capabilities, which vary substantially across model families. More critically, the MATH benchmark provides ground-truth answers that can be checked with exact string matching—this enables both the Monte Carlo rollout PRM training (Section 5.1) and the oracle difficulty estimation. Many important real-world applications (open-ended generation, dialogue, creative writing, complex multi-step planning) lack such clean correctness signals, and extending the compute-optimal framework to those domains would require fundamentally different verifier training and difficulty estimation approaches.

**What evidence exists in the paper.** The paper provides no cross-domain or cross-model replication. The 500-question test set, split into five difficulty quintiles of ~100 each, then further split by two-fold cross-validation, means the compute-optimal policy is selected based on ~50 questions per fold per bin—a sample size small enough that the selected strategies may not be robust. The paper does not report confidence intervals on the compute-optimal scaling curves (Figures 4, 8), making it impossible to assess whether the observed gains are statistically reliable at this sample size. The absence of evaluation on code generation (HumanEval, MBPP), logical reasoning (ARC, FOLIO), scientific QA, or any non-math domain is a significant gap given the paper's claims about applicability to "enterprise applications, such as summarization, RAG, and code-generation" (abstract).

**Mitigation status.** The paper acknowledges this implicitly by framing the work as an initial systematic study rather than a deployment-ready system, and by calling for future work on "extension to other domains and modalities" in Section 8. However, no preliminary results on even a single additional benchmark or model are provided to support the generalisability claim. A practitioner considering SwiftKV for a non-math workload would need to replicate the entire pipeline—PRM training, difficulty estimation, strategy selection—without guidance on transferability.

---

### 6.4 The Phase-Asymmetric Design Leaves Decode Compute Entirely Unoptimized, Limiting Gains on Workloads with Balanced or Decode-Dominant Token Ratios

**The assumption or constraint.** SwiftKV is explicitly designed for workloads where prefill dominates total compute, motivated by Snowflake's observation of a ~10:1 input-to-output token ratio in enterprise deployments (Section 1). The method reduces prefill compute by 25–50% but leaves decode computation completely unchanged—decode tokens propagate through all layers normally. Section 3.2 states this explicitly:

> "We note that decoding tokens still propagate through all layers, so additional decoding heads are not necessary for SwiftKV."

**The consequence.** The throughput and latency improvements are maximized when prefill dominates and diminish as the input-to-output ratio decreases. The paper's own throughput experiments demonstrate this: for Llama-3.1-8B-Instruct, the improvement ratio grows from 1.26× at 2K input tokens to 1.92× at 128K input tokens (Figure 3, left), because longer prompts mean prefill accounts for a larger fraction of total compute. Conversely, on workloads with short prompts and long generations—chatbots with brief user queries generating extended responses, creative writing, or multi-turn conversations where each turn generates substantial output—the benefit would shrink proportionally. The ShareGPT experiments (Table A.3) confirm this pattern: on the unfiltered ShareGPT dataset (average input/output length ratio of 1.5), the throughput improvement is only 1.16× for 8B and 1.15× for 70B, versus 1.59× and 1.71× when filtering for ratios ≥100.

**What evidence exists in the paper.** The scaling of improvement with input length is well-documented in Figure 3 and Tables A.2–A.3. The paper is transparent that SwiftKV is designed for prefill-dominant workloads and does not claim benefits for other workload patterns. However, the headline claims ("up to 2× higher aggregate throughput," "60% lower TPOT") are drawn from the most favorable conditions (longest inputs, highest arrival rates) and may mislead practitioners with different workload profiles who do not carefully examine the length-dependence of the results.

**Mitigation status.** Appendix B.4 explores an early-exit mechanism for decode tokens as a preliminary extension, showing that when an early-exit head's confidence exceeds 0.95, its prediction aligns with the full model 66% of the time. However, this is an early-stage investigation with no integration into the throughput or latency benchmarks, and the paper explicitly states that "fully exploring this is out of the scope of this paper" (Appendix B.4). The decode optimization problem remains largely open within the SwiftKV framework. A deployment with even a 2:1 or 5:1 input-to-output ratio would see substantially smaller gains than the headline figures suggest, and the paper does not provide a model for estimating expected improvement given a workload's specific token ratio distribution.

### 6.5 The Knowledge-Preserving Distillation Strategy Is Validated Only on the MATH Domain and May Not Transfer to Factual Knowledge or Generation Tasks

**The assumption or constraint.** The paper's distillation procedure trains only the WQKV parameters (Q, K, and V projection matrices) of the rewired layers, hypothesizing that this preserves factual knowledge stored in MLP weights. Section 3.4 states:

> "limiting the training to just WQKV achieves better accuracy, which aligns with prior hypotheses that LLM knowledge is primarily stored in their MLP layers"

This hypothesis is supported by the ablation in Table 4(b), where full-model fine-tuning of the later 50% of layers degrades accuracy by 4.47 points compared to training only WQKV, and by Table 4(a), where distillation outperforms standard LM loss training by 2.64 points. However, the "knowledge" being preserved in these experiments is **mathematical reasoning capability** as measured by MATH accuracy.

**The consequence.** The claim that MLP layers store knowledge—and that freezing them therefore preserves model capabilities—comes from prior work (Meng et al., 2024; Geva et al., 2021; Elhage et al., 2021) that studied factual associations (e.g., "Paris is the capital of France") and linguistic knowledge. Whether the same localisation holds for mathematical reasoning procedures, multi-step logical deduction, or code generation is untested in this paper. If mathematical problem-solving relies more on procedural knowledge distributed across attention patterns and less on localized factual associations in MLP weights, then the "knowledge preservation" argument may not generalise to other domains. A practitioner applying SwiftKV to a summarization or RAG model—where factual accuracy is paramount—cannot assume from this paper's evidence that freezing MLP weights will preserve factual knowledge, because the evaluation does not include any factual recall or hallucination benchmark.

**What evidence exists in the paper.** The MATH benchmark tests mathematical problem-solving, not factual recall. The broader benchmark suite in the SwiftKV paper (ARC-Challenge, MMLU, TruthfulQA, etc.) does test factual knowledge, and the results in Table 2 show small degradation on these tasks under the partial-training regime. However, these are multiple-choice or exact-match evaluations that may not be sensitive to subtle factual distortions. There is no evaluation of open-ended generation quality, factuality, or hallucination rates. The SwiftKV paper's distillation scaling experiments (Table B.3) show that adding domain-specific math and code data improves GSM8K accuracy, confirming that *math-specific* knowledge can be recovered, but this does not address whether *factual* knowledge in other domains is preserved or degraded.

**Mitigation status.** Not addressed. The paper treats the knowledge-preservation hypothesis as validated by the accuracy results in Table 2 and Table 4(b), without distinguishing between types of knowledge (procedural vs. factual, domain-specific vs. general) that may be differentially affected by the transformation. The SwiftKV paper's evaluation suite does include factual knowledge benchmarks (MMLU, TruthfulQA), and the minimal degradation on these tasks is encouraging, but the paper does not analyze whether specific factual domains degrade more than others or whether the degradation pattern differs from the MATH-only evaluations in the referenced compute-optimal paper.

### 6.6 The Revision Model Suffers from a 38% Correct-to-Incorrect Reversion Rate, and Revision Training Is Fragile to Optimization Methodology

**The assumption or constraint.** The revision model is trained exclusively on sequences where all in-context answers are incorrect followed by a correct target answer (Section 6.1). The training data construction pairs independently sampled correct and incorrect solutions using character-level edit distance as a proxy for trajectory coherence. During inference, the model generates a chain of revisions, conditioning each new revision on all previous ones.

**The consequence.** Because the model never encounters correct answers in its training context, it has no learned behaviour for what to do when its own previous answer is already correct. At test time, approximately **38% of correct answers get converted back to incorrect ones** in the subsequent revision step (Section 6.1). The paper mitigates this with majority voting or verifier-based selection across the entire revision chain—picking the best answer from any point rather than always taking the final revision—but this is a band-aid, not a solution. It means the revision model is fundamentally unreliable as a sequential refiner: it may improve an incorrect answer, but it may also corrupt a correct one, and the system cannot know which has occurred without an external verifier. This creates a hard dependency on verifier quality that is not present for parallel sampling strategies.

**What evidence exists in the paper.** The 38% reversion rate is reported in Section 6.1 with the mitigation strategy described. Additionally, Appendix K (Figure 16) demonstrates that attempting to optimize the revision model using ReST^EM (Singh et al., 2024)—an on-policy RL-style training procedure—causes performance to **degrade substantially**: at 256 generations, fully sequential performance drops to approximately 33.5% compared to roughly 38.5% at the optimal ratio, and is far below the parallel baseline. The authors hypothesize that on-policy data collection "exacerbates spurious correlations in revision data, causing the model to fail to learn the revision task properly." This fragility to training methodology means the positive revision results depend on specific, somewhat delicate choices (offline data construction, edit-distance-based pairing, specific number of in-context incorrect examples) that may not transfer robustly to other models or domains.

**Mitigation status.** The paper acknowledges the reversion problem and implements the chain-wide selection mitigation, but does not explore more principled solutions such as training the model with mixed trajectories (including cases where it should output "no revision needed") or confidence-based early stopping during revision chains. The ReST^EM failure is presented as a negative result that "highlights the sensitivity of revision training to the data generation procedure" but is not further investigated. For a practitioner, this means the revision approach requires careful tuning of the training data construction pipeline and may not be stable under iterative self-improvement—a key envisioned application of this work (Section 8).

## 7. Implications and Future Directions

### How This Work Changes the Landscape

SwiftKV introduces a conceptual shift in how the field approaches LLM inference optimization: it replaces the assumption that **all inference operations are equally worth optimizing** with a **phase-asymmetric design philosophy** that treats prefill and decode as fundamentally different computational problems with different tolerance for approximation. This is not an incremental improvement to an existing technique—it is a reframing of what constitutes a valid optimization target.

The magnitude of this shift is best understood by contrast with the dominant paradigm. Prior work on LLM inference acceleration operates under an implicit uniformity assumption: pruning removes weights or layers permanently and affects all tokens equally (Sreenivas et al., 2024; Tang et al., 2025); layer-skipping methods decide per-token whether to skip but apply the same logic to prefill and decode tokens alike (Jaiswal et al., 2024; Men et al., 2024); KV cache compression reduces memory for stored keys and values regardless of when they were computed (Hooper et al., 2024; Liu et al., 2024a). In all these approaches, the optimization is a property of the model or the cache, not of the inference *phase*. SwiftKV's innovation is to ask: **which phase of inference bears the cost, and which phase benefits from full precision?** The answer—that prefill dominates total FLOPs in enterprise workloads and can be aggressively approximated, while decode involves few tokens but autoregressively compounds errors and should be preserved—seems obvious in retrospect, but no prior work had operationalised it as a design principle.

This reframing has several immediate consequences for the research landscape:

**It reconciles contradictory findings about the value of KV cache compression.** The field has invested heavily in reducing KV cache memory—through quantization (Hooper et al., 2024), architectural compression (Shazeer, 2019; Ainslie et al., 2023b), low-rank approximations (Chang et al., 2024), and cross-layer merging (Liu et al., 2024a)—motivated by the assumption that KV cache memory is the primary inference bottleneck. SwiftKV's Merge-all-Layers experiment (Section 5.1, Table 3) provides a clean counterpoint: even an idealised KV compression scheme achieving 32× memory reduction on an 80GB H100 GPU improves throughput by only ~10%, while reducing prefill compute by 50% improves throughput by 35%. This does not mean KV cache compression is worthless—the 16GB and 20GB experiments in Table 3 show it becomes critical under memory pressure—but it clarifies that **the bottleneck depends on deployment conditions**, and that for standard datacenter GPU configurations, compute reduction is the higher-leverage target. Future inference optimization research should therefore **measure and report whether their target workload is compute-bound or memory-bound** rather than assuming one or the other by default.

**It establishes inter-layer hidden-state similarity as a diagnostic that predicts transformability.** Before SwiftKV, the observation that deeper transformer layers produce increasingly similar representations was known (Gromov et al., 2024; Liu et al., 2024b) but had not been operationalised as a decision-making tool for model compression. SwiftKV's `SimScore(x_l)` metric (Equation 1, Figure 2) is not just an explanatory device—it is a **predictive diagnostic** that explains *why* the method works well on Llama, Mistral, and Deepseek models (where `SimScore` exceeds 0.5 at mid-depth) and *why* it degrades on Qwen models (where `SimScore` is lower at the same relative depth). This transforms a heuristic design choice (where to place the cutoff layer `l`) into a principled one: **measure similarity first, then decide feasibility**. For the research community, this means any future model compression or layer-skipping technique that relies on representational redundancy should provide similarity measurements as standard evidence, rather than treating them as optional post-hoc analysis.

**It redirects research attention away from architecture-specific optimizations toward workload-aware design.** Methods like sparse attention (Zhao et al., 2024; Jiang et al., 2024) develop custom kernels for specific attention patterns; low-rank KV compression (Chang et al., 2024) requires new projection layers; adaptive layer-skipping (Jaiswal et al., 2024) needs per-token routing logic. SwiftKV demonstrates that a **minimal architectural change**—rewiring which hidden state feeds which KV projection, with no new layers, no custom kernels, and integration into standard serving systems—can achieve 25–50% prefill reduction with accuracy degradation comparable to or better than these more complex methods. This suggests that the field may have been over-investing in **mechanism complexity** and under-investing in **workload analysis** as a source of efficiency gains. The fact that SwiftKV's phase-asymmetric insight is orthogonal to specific architectural choices means it can be combined with many existing techniques, making it a force multiplier rather than a competitor.

**It provides a cost-efficiency benchmark for model adaptation procedures.** The comparison with Nemotron-51B (40B tokens of distillation, 28% prefill reduction, 82.78% accuracy) and DarwinLM-8.4B (10B tokens, 40% total reduction, 35.94% accuracy) establishes that **more data and more parameter training do not necessarily yield better results** for model transformation. SwiftKV's lightweight distillation (<1B tokens, <10% parameters, 3–5 hours on standard GPU clusters) achieves higher accuracy at greater prefill reduction than either prune-and-distill alternative (Table 2). This raises the bar for future model compression work: a new method should justify its training cost relative to SwiftKV as a baseline, not just relative to the original model. The paper also demonstrates that training *fewer* parameters (only WQKV, not full later layers) yields better accuracy (Table 4b), challenging the intuition that more trainable parameters always enable better adaptation. This has implications for any post-training model modification—**identifying and freezing knowledge-storing components may be as important as training the components that need to adapt**.

### Follow-Up Research This Work Enables

**Systematic benchmarking of phase-asymmetric vs. uniform compute reduction across diverse workload ratios.** The paper demonstrates that SwiftKV's throughput improvement scales with the prefill-to-decode token ratio—from 1.16× on unfiltered ShareGPT (ratio 1.5) to 1.59× on ShareGPT filtered for ratios ≥100 (Table A.3). But this is measured on a single model (Llama-3.1-8B) with a single serving framework. A strong follow-up study would construct a **workload ratio benchmark** spanning 0.1 (decode-heavy, e.g., creative writing with short prompts) to 100 (prefill-heavy, e.g., document summarisation with long inputs), and measure the crossover point where phase-asymmetric reduction (SwiftKV) becomes more beneficial than uniform reduction (layer pruning, FFN-SkipLLM). For each workload, the study should report combined throughput, TTFT, and TPOT at matched accuracy. This would produce a **practitioner decision diagram**: given your observed input/output length distribution, which inference optimization class should you invest in? The experiment requires implementing a fair comparison—SwiftKV, a prune-and-distill baseline like Minitron at matched prefill reduction, and an adaptive skipping baseline like LayerSkip—on identical hardware with identical serving configurations. The paper's findings that SwiftKV outperforms FFN-SkipLLM at all tested ratios (Table 2) and that Merge-all-Layers underperforms SwiftKV at 80GB (Table 3) provide the initial evidence, but a systematic ratio sweep would establish the general principle.

**Diagnostic-driven model family screening for SwiftKV applicability.** The paper demonstrates that `SimScore(x_l)` at mid-depth (Figure 2) predicts SwiftKV's accuracy degradation: models with higher similarity (Llama, Mistral) degrade less; models with lower similarity (Qwen) degrade more. A natural follow-up is a **large-scale screening study** that computes `SimScore` for every major open-source model family—Llama-3, Llama-2, Mistral, Qwen2, Yi, Gemma, Phi, Command R, Falcon, OLMo, DBRX, etc.—across sizes from 1B to 405B, and correlates the similarity score with post-SwiftKV accuracy degradation at 25%, 40%, and 50% reduction. The goal is to determine whether `SimScore` is a universal predictor or whether other architectural properties (normalization scheme, activation function, attention variant, pretraining objective) modulate the relationship. A particularly valuable negative result would be finding a model with high `SimScore` that nonetheless degrades significantly under SwiftKV, which would reveal that hidden-state similarity is necessary but not sufficient for the transformation to work—something else (perhaps the distribution of information across attention heads, or the role of residual stream magnitude) matters too. The paper's Qwen result (Figure 2, Table 2) already provides the positive correlation; what's needed is the full correlational landscape and its exceptions.

**Combining SwiftKV with speculative decoding for multiplicative prefill-decode acceleration.** SwiftKV reduces prefill compute but leaves decode unchanged. Speculative decoding (Leviathan et al., 2023) accelerates decode by using a small draft model to propose multiple tokens that the large model verifies in parallel. These two techniques are **architecturally orthogonal**: SwiftKV changes how prefill tokens flow through layers, while speculative decoding changes how decode tokens are generated. A combined system could use SwiftKV to reduce the cost of verifying draft tokens (since verification involves a prefill-like forward pass over the drafted sequence) while standard speculative decoding accelerates the draft-proposal phase. The experiment would measure throughput for Llama-3.1-70B-SwiftKV-50% with speculative decoding using a small draft model (e.g., Llama-3.2-1B or Llama-3.2-3B) across the same workload conditions as Figure 3 (2K–128K inputs). The hypothesis is that the combination yields greater-than-additive throughput improvements because SwiftKV's prefill reduction makes the draft verification step cheaper, which enables more aggressive speculation (longer draft sequences) at the same latency budget. The paper's integration with vLLM and SGLang (Section 3.5) already provides the engineering foundation—speculative decoding is a supported feature in both frameworks, so the implementation effort is primarily configuration rather than kernel development.

**Data scaling laws for SwiftKV distillation: how little data is actually needed?** The paper uses 680M tokens for distillation and demonstrates that adding 83K domain-specific tokens improves GSM-8K accuracy by 0.53 points (Table B.3b). But two critical questions are unanswered: (1) **What is the minimum data required?** A data scaling study measuring SwiftKV accuracy at 50M, 100M, 200M, 340M, and 680M tokens—ideally for both general-purpose (Ultrachat + OpenHermes + SlimOrca) and domain-specific (math, code, factual knowledge) data mixtures—would determine whether the 680M figure is near saturation or far from it. (2) **Does data quality matter more than data quantity?** The paper shows that fine-tuning the base model on its distillation dataset produces only 65.77% accuracy versus Meta's official 73.71% (Table B.3a), meaning the distillation data is known to be suboptimal. What if the distillation used a higher-quality dataset (e.g., the original Llama-3 instruction-tuning mixture if available, or a carefully curated subset of the same size)? An experiment comparing 680M tokens of the paper's data vs. 680M tokens of a high-quality dataset at matched size would isolate the effect of data quality independent of quantity. The paper already provides evidence that domain-specific data helps (Table B.3b); what's missing is the full scaling surface—accuracy as a function of both data quantity and data quality—which would tell practitioners how to budget their distillation efforts.

**Stress-testing SwiftKV on long-context quality benchmarks.** The throughput experiments push to 128K input tokens (Figure 3), but the quality evaluation (Table 2) uses standard benchmarks with typical prompt lengths in the hundreds of tokens. Long-context scenarios raise distinct challenges for SwiftKV: the KV cache projected from `x_{l+1}` must serve as the key-value representation for all deeper layers across potentially 100K+ positions, and any representational distortion introduced by the rewiring might compound across long attention spans in ways that are invisible on short prompts. A thorough stress test would evaluate SwiftKV models on long-context benchmarks: **Needle-in-a-Haystack** (retrieving a fact embedded in a long document at varying positions), **LongBench** (Bai et al., 2023, covering multi-document QA, summarisation, and few-shot learning with 5K–15K token contexts), and **RULER** (Hsieh et al., 2024, testing retrieval across varying context lengths up to 128K). The experiment would compare SwiftKV at 25%, 40%, and 50% reduction against the baseline model on these benchmarks, measuring both retrieval accuracy and generation quality. A negative result—SwiftKV degrading disproportionately on long-context tasks despite minimal degradation on standard-length benchmarks—would refine the applicability boundary: SwiftKV may be best suited for workloads with high prefill-to-decode ratios but moderate individual prompt lengths, not for genuine long-context scenarios where per-token KV cache fidelity across all layers matters more.

**Does freezing MLP weights genuinely preserve factual knowledge, or does it merely avoid catastrophic forgetting of the specific benchmark answers?** The paper's knowledge-preservation claim (Section 3.4, Table 4b) rests on the finding that training all later-layer parameters degrades accuracy by 4.47 points relative to training only WQKV. This is attributed to prior work showing that MLP layers store factual associations (Meng et al., 2024; Geva et al., 2021). But a targeted experiment could distinguish between two hypotheses: (1) freezing MLP weights preserves *general* factual knowledge, meaning the model retains correct answers to factual questions across broad domains; (2) freezing MLP weights preserves *whatever the model learned during pretraining*, which happens to include benchmark answers because the benchmarks draw from the training distribution, but the preservation is not specifically about facts—it is about any knowledge encoded in MLP weights. The experiment would use a **counterfactual knowledge dataset** where the model is fine-tuned on factually incorrect associations (e.g., "The capital of France is Berlin") before SwiftKV transformation, then test whether SwiftKV with frozen MLPs preserves the *original* (correct) knowledge or the *fine-tuned* (incorrect) knowledge. If SwiftKV's frozen MLPs preserve the fine-tuned incorrect facts, the preservation is about weight stability, not specifically about factual knowledge. If they revert to original facts, MLPs truly store factual associations that are robust to attention rewiring. The paper's benchmarks (ARC, MMLU, TruthfulQA) test factual knowledge but do not disentangle these mechanisms. This follow-up would clarify whether the "knowledge-preserving" label is accurate or whether the finding is better described as "MLP weight stability prevents catastrophic forgetting."

### Practical Applications and Downstream Use Cases

**Cost-efficient large-scale batch inference for document processing pipelines.** Organizations that process large document corpora through LLMs—for summarisation, entity extraction, classification, or RAG indexing—typically submit very long prompts (full documents, potentially thousands of tokens) and receive short structured outputs (summaries, extracted fields, classifications). This is the exact workload profile SwiftKV targets (10:1 input-to-output ratio). A concrete deployment scenario: a legal technology company processing 10 million contracts per month through Llama-3.1-70B for clause extraction. With baseline inference at approximately 8K tokens/s on 4× H100 (Figure 3, right, at 8K input), processing 10M documents with average 8K tokens input and 256 tokens output requires roughly (10M × 8K) / 8K = 10M GPU-seconds. At 50% SwiftKV with approximately 16K tokens/s, the same workload requires ~5M GPU-seconds—cutting GPU-hours (and cloud compute cost) by roughly half while producing outputs within 1–2% accuracy of the original model (Table 2: 82.98% vs. 84.31% for Llama-3.1-70B). The 560 TFLOPS/GPU normalised throughput figure (Section 4.2) means existing hardware can serve approximately 1.75× more requests at the same latency, directly reducing per-request infrastructure cost without model quality sacrifices that would require re-validation of downstream task accuracy.

**Interactive enterprise copilots under high concurrent load.** In code completion, text-to-SQL, and RAG-based Q&A systems deployed to thousands of simultaneous users, request queues accumulate when prefill processing cannot keep up with arrival rates. SwiftKV's demonstrated ability to sustain 1.5–2.0× higher arrival rates before TTFT explosion (Figure 4, top row, comparing baseline to 50% SwiftKV across arrival rates) translates directly to **higher user capacity per GPU**. For a concrete example: a text-to-SQL service using Llama-3.1-70B that must maintain TTFT under 1 second for 90% of requests. With baseline inference at 8K input length, Figure 4 (middle column) shows TTFT exceeds 1 second at approximately 0.6 requests/second. With 50% SwiftKV, the system sustains approximately 1.2 requests/second before crossing the 1-second threshold—doubling the number of concurrent users served per 4× H100 instance. The TTFT reduction at low load (from roughly 0.5s to 0.3s at 8K input, a 40% improvement) also directly improves user experience even with no queuing. Crucially, this comes with minimal model quality impact: Table 2 shows Llama-3.1-70B at 50% SwiftKV with 4× AcrossKV achieves 82.96% average accuracy vs. the baseline's 84.31%, a 1.35-point gap that may be imperceptible for most enterprise SQL generation tasks where output correctness is verified by query execution.

**On-device or edge deployment of moderately sized models under memory constraints.** The 40GB and 20GB memory-constrained experiments (Table 3) demonstrate that SwiftKV combined with AcrossKV and FP8 quantization enables usable throughput in scenarios where the baseline model is severely bottlenecked or cannot run at all. For Llama-3.1-8B-Instruct at 16GB memory, the baseline model suffers OOM—it cannot be deployed. 50% SwiftKV without AcrossKV also suffers OOM. But 50% SwiftKV with 4× AcrossKV and FP8 KV cache quantization achieves 7.28K tokens/s. While this is substantially lower than the unconstrained 80GB throughput (32.0K tokens/s), it represents the difference between **deployment possible** and **deployment impossible**. A concrete scenario: running a code completion assistant on a developer laptop with a single consumer GPU (16GB VRAM). Without SwiftKV, the developer must either use a smaller model with degraded code generation quality or rely on cloud inference with network latency. With SwiftKV + AcrossKV + FP8, a Llama-3.1-8B-Instruct-level model becomes deployable locally, providing code suggestions with sub-second latency and no network dependency. The 2-way AcrossKV + FP8 configuration (62.5% total KV cache reduction, 71.69% average accuracy vs. 73.71% baseline in Table B.1) would likely provide a better accuracy-latency tradeoff for this use case than the aggressive 4-way configuration.

**Rapid model adaptation for A/B testing of inference optimizations in production.** The paper's finding that SwiftKV distillation completes in 3 hours on 8× H100 GPUs for an 8B model (Section 3.4) has an operational implication beyond raw cost: it enables **fast iteration cycles** for production inference optimization. A team serving Llama-3.1-8B-Instruct can create a SwiftKV variant in an afternoon, evaluate it on their internal task-specific benchmarks, and deploy it to a fraction of production traffic for A/B testing—all within a single workday. This contrasts with prune-and-distill methods requiring 10–100B tokens of training (potentially days or weeks of GPU time) before evaluation is possible. The low training cost also makes it feasible to maintain multiple SwiftKV configurations tuned for different workload profiles: a 50%-reduction variant for prefill-heavy summarisation traffic, a 25%-reduction variant for more decode-balanced chatbot traffic, and potentially domain-specific variants fine-tuned on the organisation's proprietary data (as suggested by the data quality ablation in Table B.3b). The open-sourced training code (Section 1) and the minimal engineering required for inference integration (Section 3.5) make this practical for teams without specialised ML infrastructure expertise.
