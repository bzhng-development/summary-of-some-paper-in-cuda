# FlashAttention-4: Algorithm and Kernel Pipelining Co-Design for Asymmetric Hardware Scaling

**ArXiv:** [2603.05451](https://arxiv.org/abs/2603.05451)

## Pitch

As AI hardware evolves, computational resources scale unevenly—on NVIDIA's new Blackwell GPUs, tensor core throughput doubled while memory bandwidth and exponential units remained stagnant, creating new bottlenecks that invalidate previous optimization strategies. FlashAttention-4 addresses this 'asymmetric scaling' through algorithm-kernel co-design, introducing software-emulated exponentials and redesigned pipelines that collectively achieve 1.3× speedup over cuDNN and 71% theoretical utilization on B200 GPUs.

---

## 1. Executive Summary

This paper proposes **FlashAttention-4**, an attention kernel that co-designs algorithm and implementation to address the shifting bottlenecks introduced by asymmetric hardware scaling on NVIDIA Blackwell GPUs — where tensor core throughput doubles compared to Hopper while shared memory bandwidth and exponential unit throughput remain unchanged. The work introduces three named mechanisms: redesigned software pipelines that exploit fully asynchronous MMA operations and larger 128×128 tiles to overlap matmul with softmax, software-emulated exponential functions using polynomial approximation on FMA units (reducing dependence on the low-throughput MUFU unit), and a 2-CTA MMA mode that halves shared memory traffic and global atomic adds in the backward pass by partitioning operands across CTA pairs. FlashAttention-4 achieves up to 1.3× speedup over cuDNN 9.13 and 2.7× over Triton on B200 GPUs with BF16, reaching 1613 TFLOPs/s (71% utilization). The paper establishes that test-time attention efficiency on asymmetric hardware can be substantially improved by identifying and mitigating non-matmul bottlenecks — but only when the kernel implementation is co-designed around the specific throughput ratios of tensor cores to shared memory and exponential units.

## 2. Context and Motivation

### The Core Problem: Hardware Is Scaling Asymmetrically, and Attention Kernels Are Not Keeping Up

The fundamental problem this paper addresses is deceptively simple: **GPU hardware is evolving in an increasingly unbalanced way, and existing attention implementations cannot fully utilize the new hardware because they optimize for the wrong bottlenecks.** On NVIDIA's Blackwell architecture (B200, GB200), the tensor cores — the specialized units that perform matrix multiply-accumulate (MMA) operations at the heart of attention — have doubled in throughput compared to the previous Hopper generation (2.25 PFLOPS vs. 1 PFLOPS for FP16/BF16). However, the other functional units that attention kernels depend on — shared memory bandwidth, the multi-function unit (MUFU) that computes exponentials for softmax, and integer/floating-point ALUs — have either scaled more slowly or remained completely unchanged.

This creates a situation where, if you simply port an attention kernel optimized for Hopper to Blackwell, it will be **bottlenecked not by matrix multiplication, but by shared memory traffic and exponential computation.** The paper's roofline analysis in Sections 3.1.1 and 3.2.1 makes this quantitative: for typical attention tile configurations on Blackwell, shared memory traffic and exponential operations exceed MMA compute time by **25–60%**. The tensor cores — the most expensive and heavily optimized part of the chip — end up **idle**, waiting for data from shared memory or for softmax exponentials to finish. This is a fundamentally different performance regime than Hopper, where MMA compute was typically the bottleneck.

This matters enormously because the AI industry has already begun deploying Blackwell-based systems at scale for training and inference. NVIDIA's Blackwell architecture represents the state-of-the-art in datacenter GPU compute, and the B200 and GB200 are being deployed in large clusters for frontier model training. If attention kernels cannot effectively utilize Blackwell's increased tensor core throughput, then a significant fraction of the hardware's theoretical capability is wasted — and since attention is the primary computational bottleneck in Transformer models (scaling quadratically in sequence length), this wasted capability directly translates to slower training, higher inference latency, and increased cost per token.

The problem is not just about one generation of hardware. The paper frames asymmetric scaling as a **broader trend in accelerator design**: "increasing the throughput of the most important components (typically matrix multiply units) to get higher performance under similar power / silicon area constraint" (Section 2.2). As future GPU generations continue this trend (the paper notes that B300 and GB300 already double exponential throughput, but those GPUs are not yet widely available), the gap between matmul and non-matmul throughput will remain a moving target that requires continuous algorithmic co-design. This makes the problem both urgent (for current Blackwell deployments) and strategically important (for anticipating future hardware).

### Why Existing Approaches Fall Short

The paper identifies specific limitations across three categories of prior work:

#### 1. FlashAttention-3 Cannot Run on Blackwell At All

FlashAttention-3 (Shah et al., 2024) was the state-of-the-art attention kernel for Hopper GPUs, achieving significant speedups through warp specialization, asynchronous execution, and FP8 support. However, it **cannot be ported to Blackwell** for two reasons:

- **Forward compatibility failure**: "Simply porting existing attention algorithms to this new hardware either leaves significant performance on the table or is impossible due to lack of forward compatibility for Hopper MMA instructions" (Section 1). Blackwell uses a different instruction set architecture for its tensor cores, and Hopper MMA instructions are not supported. Any kernel that directly uses these instructions — as FlashAttention-3 does — requires a ground-up rewrite for the new ISA.

- **Architectural assumptions that no longer hold**: FlashAttention-3 was designed under the assumption that MMA compute is the primary bottleneck and that registers are the scarce resource. Its software pipeline is structured around these constraints: accumulators are held in registers (extreme register pressure), warpgroups are sized for Hopper's 64×128 tile size, and the scheduling assumes certain latency ratios between MMA and non-MMA operations. On Blackwell, with 128×128 tiles, tensor memory (TMEM) instead of register-held accumulators, and fully asynchronous MMA, these assumptions are invalid. The same pipeline design that was optimal on Hopper would **serialize operations that could be overlapped** and leave tensor cores underutilized.

#### 2. FlashAttention-2 and Earlier Approaches Target Older Hardware

FlashAttention-2 (Dao, 2023) and the original FlashAttention (Dao et al., 2022) were designed for even earlier GPU architectures (Ampere and earlier). While their core algorithmic innovations — tiling to avoid global memory reads/writes, online softmax for numerical stability, recomputation in the backward pass — are architecture-agnostic and remain valuable, their **kernel implementations are tightly coupled to specific hardware characteristics**:

- **Tile sizes**: These implementations use smaller tile sizes appropriate for earlier tensor core dimensions (e.g., 64×64 or 64×128 on Ampere, 64×128 on Hopper). Directly scaling these to Blackwell's 128×128 tiles is not straightforward because it changes register allocation, shared memory partitioning, and the parallelism strategy.
- **No tensor memory awareness**: TMEM is a new hardware feature introduced in Blackwell. Older implementations that rely on register-held accumulators do not benefit from TMEM's ability to store intermediate tensor core outputs without consuming registers, which is critical for alleviating register pressure with the larger tile sizes.
- **Software pipeline structure**: The specific ordering of MMA operations, softmax computation, and memory transfers in FlashAttention-2/3 was tuned for the latency and throughput characteristics of Ampere/Hopper. On Blackwell, different overlaps are possible (because of fully asynchronous MMA) and different overlaps are necessary (because of the shifted bottlenecks).

#### 3. Triton and cuDNN Are General-Purpose or Vendor-Optimized, Not Attention-Specialized

The paper benchmarks against two strong baselines: Triton (an open-source GPU programming language and compiler) and cuDNN (NVIDIA's vendor-optimized deep learning library). Both fall short for attention on Blackwell:

- **Triton** (version 3.6, with B200-specific instructions): Achieves 2.1–2.7× lower throughput than FlashAttention-4 in the forward pass (Figure 4). Triton is a general-purpose compiler for tiled computations; it does not have attention-specific optimizations like the ping-pong software pipeline that overlaps softmax with MMA, the polynomial exponential emulation, or the 2-CTA MMA mode. Its compiler must make generic scheduling decisions that cannot exploit attention-specific properties (e.g., that softmax is statistically unlikely to need rescaling on every tile, enabling the conditional rescaling optimization in Section 3.1.4).

- **cuDNN 9.13**: Achieves 1.1–1.3× lower throughput than FlashAttention-4. cuDNN is developed by NVIDIA and benefits from deep hardware knowledge, but it is a general neural network library — attention is one of many operations it supports, and its implementations must be general enough to handle arbitrary tensor shapes, layouts, and precision combinations. FlashAttention-4, by specializing exclusively to attention with specific design assumptions (e.g., online softmax, recomputation, the specific pattern of MMA operations in forward and backward), can make optimizations that a general library cannot. The paper notes that after the initial release of FlashAttention-4, newer cuDNN versions "have incorporated many of the techniques described in this paper, yielding similar performance to FA4" (Figure 4 caption) — which actually validates the paper's contributions by showing that the techniques generalize beyond a single implementation.

#### 4. Quantization-Based Approaches Target Consumer GPUs, Not Datacenter

The paper acknowledges recent work on low-precision attention — SageAttention (INT8), SageAttention2 (INT4/FP8), SageAttention3 (FP4 on Blackwell consumer GPUs) — but distinguishes them sharply from FlashAttention-4:

- These approaches primarily target **consumer GPUs**, where the hardware characteristics and bottlenecks are different from datacenter GPUs like the B200 and GB200. Consumer GPUs have different ratios of tensor core throughput to memory bandwidth to special function unit throughput.
- Quantization reduces compute and memory bandwidth requirements but does not address the **structural imbalance** between MMA and non-MMA throughput that is the central problem on Blackwell. Even in FP4, the softmax still requires exponential operations, and the kernel still needs to manage shared memory traffic for MMA operands.
- FlashAttention-4 operates at BF16 precision (the standard for training) and achieves its speedups through algorithmic and pipeline restructuring, not through reduced precision. The two approaches are complementary rather than competing.

### The Gap That FlashAttention-4 Fills

The paper positions itself as filling three specific gaps simultaneously:

**Gap 1: No attention kernel exists that is optimized for Blackwell's asymmetric bottlenecks.** FlashAttention-3 doesn't run on Blackwell. FlashAttention-2 would run but with severely suboptimal utilization. Triton and cuDNN are general-purpose and leave Blackwell-specific performance on the table. The field needs a kernel that is **designed from scratch around Blackwell's specific throughput ratios** — where the optimization target is not "make matmuls faster" but "keep the tensor cores fed by eliminating shared memory and exponential bottlenecks."

**Gap 2: No systematic analysis exists of how asymmetric hardware scaling changes the attention bottleneck.** The paper's roofline analysis (Sections 3.1.1, 3.2.1) is, to the authors' knowledge, the first to quantitatively characterize how Blackwell's throughput ratios shift the performance ceiling for attention from MMA compute to shared memory traffic and exponential computation. Prior work on FlashAttention variants optimized for specific architectures empirically but did not provide this kind of bottleneck analysis that explicitly identifies *which* hardware units are the limiting factors and *by how much.* This analysis is what justifies each of the paper's three main optimizations: the pipeline redesign (to hide shared memory latency by overlapping with MMA), the exponential emulation (to increase effective exponential throughput beyond MUFU's 16 ops/clock), and the 2-CTA mode (to reduce shared memory traffic by sharing operands across CTA pairs).

**Gap 3: No attention kernel fully exploits Blackwell's new hardware features.** Blackwell introduces three architectural features that did not exist in previous generations: tensor memory (TMEM), fully asynchronous MMA that writes directly to TMEM without consuming registers, and the 2-CTA MMA mode. Each of these enables optimizations that are impossible on Hopper:

- **TMEM** alleviates the extreme register pressure that forced FlashAttention-3 to serialize operations. By storing MMA accumulators in TMEM instead of registers, FlashAttention-4 can use larger tiles and more aggressive software pipelining without register spills.
- **Fully asynchronous MMA** allows the kernel to overlap tensor core operations with softmax computation more effectively than Hopper's partially asynchronous MMA. The paper's ping-pong pipeline (Section 3.1.2) is specifically designed around this asynchrony: while one warpgroup computes softmax for one output tile, another warpgroup launches MMA operations for the next tile, and a third "correction" warpgroup handles output rescaling.
- **2-CTA MMA mode** enables a structural change to the backward pass (Section 3.2.3) that is not just an incremental optimization: it fundamentally restructures how dQ is computed, halving both shared memory traffic (by partitioning operand B across CTA pairs) and global atomic adds (by partitioning the reduction across CTAs).

### How FlashAttention-4 Positions Itself Relative to Prior Work

The paper explicitly frames itself as **not** a new attention algorithm — it does not change the mathematical formulation of attention, the online softmax algorithm, or the recomputation strategy from FlashAttention-3. The forward pass still computes $O = \text{softmax}(QK^\top)V$ with tiling and online statistics. The backward pass still recomputes attention scores and propagates gradients.

Instead, the contribution is an **algorithm-kernel co-design** for new hardware. The "algorithm" part refers to modifications that change *what* the kernel computes (polynomial exponential emulation, conditional softmax rescaling) or *how* the computation is distributed (2-CTA partitioning). The "kernel" part refers to the software pipeline, warpgroup scheduling, and memory allocation that determine *when* and *in what order* operations execute. The paper's central claim is that on Blackwell, these two aspects cannot be separated — the algorithmic choices (tile size, exponential precision, rescaling policy) must be made with explicit awareness of the kernel's resource constraints (register pressure, shared memory bandwidth, TMEM capacity), and the kernel's pipeline structure must be designed around the specific throughput ratios of the hardware units that the algorithm uses.

This is a more fundamental claim than "we optimized attention for a new GPU." It is closer to: **as hardware becomes increasingly asymmetric, attention kernels must be co-designed rather than ported, and the co-design process must start from a quantitative bottleneck analysis rather than from an existing implementation.** The paper's CuTe-DSL implementation (Section 4) supports this framing: by embedding kernel development in Python with JIT compilation, the authors enable the rapid iteration cycles that co-design requires, where a developer can change tile sizes, pipeline ordering, or precision choices and immediately measure the impact on the bottleneck analysis. This is 20–30× faster than the C++ template-based approach used in FlashAttention-3 (Table 4), which is not just a convenience improvement but an enabler of the co-design methodology itself.

### The Broader Significance: A Preview of Future Hardware Challenges

While the paper is specifically about Blackwell, its motivation extends beyond any single GPU generation. The asymmetric scaling trend — where specialized compute units (tensor cores) scale faster than general-purpose units (shared memory, special functions) — reflects a broader tension in hardware design. As Moore's Law slows, chip designers allocate their transistor budget toward the operations that matter most for AI workloads (matrix multiplication) at the expense of other units. This means that future GPUs will likely exhibit even more extreme asymmetry, and the approach of identifying and mitigating non-matmul bottlenecks through algorithm-kernel co-design will become increasingly necessary.

The paper's three specific optimizations also preview a more general methodology: for any new hardware generation, (1) perform a roofline analysis to identify which non-matmul resource is the bottleneck and by what margin, (2) design algorithmic modifications that reduce dependence on the bottleneck resource (e.g., replacing expensive exponential operations with cheaper polynomial approximations), and (3) restructure the kernel pipeline to overlap bottleneck resource usage with other computation. This methodology is not specific to attention or to Blackwell — it could be applied to other Transformer components (e.g., MLP layers, normalization) and other hardware architectures — but FlashAttention-4 provides the first concrete demonstration of its effectiveness.

## 3. Technical Approach

### 3.1 Reader Orientation

FlashAttention-4 is not a single algorithm but rather a **co-designed system** where the mathematical operations of attention (what is computed), the software pipeline (in what order operations execute), and the hardware resource allocation (which GPU units perform which work) are jointly optimized around the specific imbalance between Blackwell's doubled tensor core throughput and its unchanged shared memory bandwidth and exponential unit throughput. It solves the problem that simply porting existing attention kernels to Blackwell leaves the expensive tensor cores idle 25–60% of the time while the kernel waits on shared memory transfers and softmax exponentials — and it does so by restructuring the computation at three levels: (1) rewriting *how* exponential functions are computed to bypass the bottlenecked MUFU unit, (2) reordering *when* operations happen to overlap shared memory traffic with matmul, and (3) redistributing *which* CTAs perform *which* reductions using Blackwell's 2-CTA MMA mode to halve shared memory traffic and global atomic operations in the backward pass.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components that interact across both the forward and backward passes:

1. **Roofline Analyzer (conceptual)** — a static analysis that, for a given tile configuration (M, N, d) and hardware throughput specifications, computes the expected cycle counts for MMA compute, shared memory reads, and exponential operations. This produces the quantitative justification for each optimization: it identifies *which* resource will bottleneck by *what* margin, guiding all subsequent design decisions.

2. **Forward Pass Pipeline** — the execution schedule for computing `O = softmax(QK^T)V`. It divides work across five warpgroups: two compute softmax on alternating output tiles (ping-pong), two drive tensor core MMA operations, and one ("correction" warpgroup) handles output rescaling when the running softmax maximum changes. The novel elements are (a) polynomial-emulated exponentials that use FMA units to supplement the bottlenecked MUFU unit, (b) conditional softmax rescaling that skips `e^(m_{j-1} - m_j) O_{j-1}` multiplications when the new maximum is within a threshold of the old one, and (c) tensor memory (TMEM) allocation that stores two `S` tiles and overlaps them with `P` tiles to decouple output rescaling from the critical path.

3. **Backward Pass Pipeline** — the execution schedule for computing gradients `dV, dP, dS, dQ, dK`. Unlike FlashAttention-3 which serialized most operations due to register pressure, FlashAttention-4 overlaps two MMA operations concurrently with softmax gradient computation. It manages TMEM by having `S` and `P` share one TMEM block and `dP`, `dS`, and `dQ` share another, with `dV` and `dK` in dedicated accumulators. The novel 2-CTA variant restructures the `dQ` computation so that a CTA pair partitions operand B across the two CTAs, reducing shared memory reads.

4. **2-CTA Backward Mode** — a Blackwell-specific feature where two CTAs in the same thread block cluster cooperatively execute a single MMA. Each CTA stages only half of operand B in its own shared memory, and the pair jointly computes the output tile partitioned along the M dimension. For `dQ` specifically, the CTA pair uses distributed shared memory (DSMEM) to exchange half of the `dS` tile, enabling each CTA to hold a `(M/2 × 2N)` operand and perform a doubled reduction, which halves both shared memory traffic and global atomic adds.

5. **Scheduler (LPT/Swizzling)** — a tile ordering strategy that processes CTAs in longest-processing-time-first (LPT) order for load-imbalanced workloads (causal masking, variable sequence lengths). For causal masking, it processes query blocks in reverse order so that CTAs with longer mainloops (more unmasked tokens) execute first. For variable sequence lengths, an optional preprocessing kernel sorts batches by estimated execution time.

Information flows through the forward pass as: `Q, K, V` in HBM → TMA loads tiles into shared memory → tensor cores compute `S = QK^T` → `S` stored in TMEM → softmax warpgroups compute max, exponential (partially emulated), row sum → `P = softmax(S)` stored in TMEM → tensor cores compute `O = PV` → conditional rescaling by correction warpgroup → TMA stores `O` to HBM. The backward pass reverses this flow with five MMAs instead of two, using the 2-CTA mode to reduce shared memory pressure and atomics.

### 3.3 Roadmap for the Deep Dive

- **First**, the **forward pass roofline analysis** (Section 3.1.1) — this establishes *why* each optimization exists by quantifying the bottleneck gap between MMA compute (1024–2048 cycles), shared memory (768–1536 cycles), and exponential unit (1024–2048 cycles) for typical tile configurations. Without this analysis, the subsequent optimizations would appear arbitrary.

- **Second**, the **forward pass pipeline and exponential emulation** (Sections 3.1.2–3.1.3) — how the ping-pong warpgroup schedule overlaps softmax with MMA using TMEM, and how polynomial approximation on FMA units increases effective exponential throughput beyond the MUFU's 16 ops/clock limit. I'll explain why partial emulation (10–25% of entries) is used rather than full emulation, and why a degree-3 polynomial suffices despite being 600× less accurate than hardware at FP32 precision.

- **Third**, **conditional softmax rescaling** (Section 3.1.4) — how the standard online softmax correction step `e^(m_{j-1} - m_j) O_{j-1}` can be skipped when `m_j - m_{j-1} ≤ τ`, reducing non-matmul vector operations without affecting numerical correctness (since the final normalization corrects accumulated slack).

- **Fourth**, the **backward pass roofline and pipeline** (Sections 3.2.1–3.2.2) — why shared memory traffic (3328 cycles) exceeds MMA compute (2560 cycles) by ~30% for the 1-CTA configuration, and how the new pipeline overlaps softmax gradient computation with two concurrent MMA operations by reordering `dQ` and `dK` from the previous iteration to run alongside `dP` for the current iteration.

- **Fifth**, the **2-CTA backward mode** (Section 3.2.3) — the most architecturally novel component. I'll explain how the CTA pair uses DSMEM to repack `dS` along the non-reduction axis, enabling a `dQ` MMA with doubled reduction `2N = 256` that halves both shared memory operand reads and global atomic adds, and how the pipeline reordering (computing `dP` for the current tile before `dQ` for the previous iteration's tile) hides the DSMEM exchange latency.

- **Sixth**, the **deterministic backward pass** (Section 3.2.4) — how a semaphore-based serialization of global atomic reductions, combined with shortest-processing-time-first scheduling (descending query block index for causal masking), achieves reproducible gradients with only a ~25% throughput reduction compared to the nondeterministic 1-CTA variant.

- **Seventh**, the **LPT scheduler** (Section 3.3) — how the classical longest-processing-time-first heuristic applied to causal masking and variable sequence lengths reduces load imbalance without thrashing the L2 cache, and why this is implemented as a swizzling over head groups rather than a global reordering.

#### 3.4.1 Forward Pass Roofline Analysis: Why Each Optimization Exists

The forward pass performs two matrix multiply-accumulate (MMA) operations per iteration of the outer loop over KV-sequence tiles: `S = QK^T` (computing an `M × N` attention score tile) and `O = PV` (computing an `M × d` output tile). The roofline analysis estimates the cycle counts for three resources — tensor cores (MMA), shared memory bandwidth, and the exponential unit (MUFU) — as a function of the tile dimensions `M` (query tile size along sequence length), `N` (key tile size along sequence length), and `d` (head dimension).

**MMA compute cycles.** Each of the two MMAs requires `2MNd` floating-point operations (the standard `2mnk` for an `m×k` by `k×n` matmul). With Blackwell's tensor core throughput of 8192 FLOPs per clock cycle per SM, the total compute time is:

$$T_{\text{MMA}} = \frac{4MNd}{8192} \text{ cycles}$$

where the factor 4 comes from `2 × 2MNd` (two MMAs, each `2MNd` FLOPs).

**Why this throughput number:** 8192 ops/clock/SM is derived from the theoretical maximum: 2.25 PFLOPS / 1850 MHz clock speed / 148 SMs = 8192. This is exactly double Hopper's 4096 ops/clock/SM, which is the root cause of the bottleneck shift — tensor cores got twice as fast while other units did not.

**Shared memory cycles.** The two MMAs differ in their operand sources. The first (`QK^T`) is **shared-shared (SS)**: both `Q` and `K^T` are read from shared memory. The second (`PV`) is **tensor-shared (TS)**: `P` is read from tensor memory (TMEM) while `V` is read from shared memory. Only the shared memory reads contribute to SMEM bandwidth consumption. Critically, when the tile dimensions exceed the MMA instruction size (128×128), the operands must be re-read from shared memory for each MMA instruction. Computing an `M × N` output requires `⌈M/128⌉ × ⌈N/128⌉` MMA instructions, each reading `128d` elements of `Q` and `128d` elements of `K^T`, totaling `⌈M/128⌉⌈N/128⌉ × 256d` elements for `QK^T`. The `PV` MMA requires `⌈M/128⌉ × ⌈d/128⌉` instructions, each reading `128N` elements of `V`, totaling `⌈M/128⌉⌈d/128⌉ × 128N` elements. At 2 bytes per element (BF16) and 128 bytes per cycle shared memory bandwidth, the shared memory read time is:

$$T_{\text{smem}} = 2 \lceil M/128 \rceil \lceil N/128 \rceil \cdot 256d + 2 \lceil M/128 \rceil \lceil d/128 \rceil \cdot 128N \text{ bytes} \div 128 \text{ bytes/cycle}$$

$$= \frac{3MNd}{8192} \text{ cycles}$$

where the simplification assumes `M, N, d` are multiples of 128.

**Why this form:** The factor 3 emerges because `QK^T` reads 256d elements per MMA tile (128d from `Q`, 128d from `K^T`) while `PV` reads only 128N elements per MMA tile (from `V` only, since `P` is in TMEM). When the tile sizes are equal (`M=N=d=128`), both MMAs require exactly one MMA instruction, so `QK^T` reads 256×128 = 32,768 elements and `PV` reads 128×128 = 16,384 elements, totaling 49,152 elements = 98,304 bytes at BF16. Divided by 128 bytes/cycle = 768 cycles. For the larger tile `M=256, N=d=128`, `QK^T` requires 2 MMA instructions (reading operands twice) while `PV` still requires 1, so SMEM reads increase to 1536 cycles.

**Exponential unit cycles.** The softmax operation requires computing `exp(S_{ij})` for every element of the `M×N` attention score tile. With the MUFU unit providing 16 exponential operations per clock cycle per SM, the exponential time is:

$$T_{\text{exp}} = \frac{MN}{16} \text{ cycles}$$

**The bottleneck diagnosis.** For `M=N=d=128` (the baseline tile), `T_MMA = 1024`, `T_smem = 768`, `T_exp = 1024`. The resources are roughly balanced, with shared memory slightly below the other two. For `M=256, N=d=128` (the larger tile enabled by TMEM), `T_MMA = 2048`, `T_smem = 1536`, `T_exp = 2048`. Now shared memory (1536 cycles) is the *lowest* of the three, meaning MMA and exponentials could theoretically outrun it — but this raw analysis does not account for pipelining. In practice, if the kernel can overlap shared memory reads with MMA and exponential computation, the effective bottleneck is whichever resource cannot be hidden. The analysis motivates three design goals: (1) use larger tiles to amortize overhead, (2) overlap MMA with softmax so they don't serialize, (3) increase effective exponential throughput beyond the 16 ops/clock limit.

#### 3.4.2 Forward Pass Pipeline: Ping-Pong Warpgroup Schedule with TMEM

The forward pass pipeline is a warp-specialized design where the 256 threads of a CTA are divided into five warpgroups of 128 threads each (two warps per warpgroup on Blackwell with 128 threads per warp). The key structural differences from FlashAttention-3 are: (a) accumulators live in TMEM rather than registers, (b) two softmax warpgroups alternate on consecutive output tiles (ping-pong), and (c) a separate "correction" warpgroup handles output rescaling, decoupling it from the softmax critical path.

**Warpgroup assignments.** The five warpgroups have distinct, persistent roles throughout the kernel's main loop:

- **Two MMA warpgroups** — each drives one of the two MMA operations per iteration. One launches `QK^T` MMA instructions (computing `S` in TMEM), the other launches `PV` MMA instructions (computing `O` in TMEM). They are responsible for issuing TMA loads to bring `Q`, `K`, and `V` tiles from global memory into shared memory, and for issuing the MMA instructions that consume these operands.

- **Two softmax warpgroups** — each processes one output tile's softmax. While MMA warpgroup 1 computes `S` for tile `i`, softmax warpgroup 1 computes `rowmax(S)`, `exp(S - rowmax)`, and `rowsum(exp(...))` for the *previous* tile `i-1`. The two softmax warpgroups alternate: on even iterations, softmax warpgroup 0 processes the even tile while warpgroup 1 idles; on odd iterations, they swap. This ping-pong ensures that softmax computation (which depends on `S` being fully computed) never stalls waiting for MMA — by the time softmax needs tile `i`, it was computed by MMA in the *previous* iteration and is already resident in TMEM.

- **One correction warpgroup** — applies the online softmax rescaling factor `e^{m_{j-1} - m_j}` to the accumulated output `O_{j-1}` when the running maximum changes. Because `P` (the softmax output) is in TMEM rather than registers, the rescaling can be performed by a dedicated warpgroup that reads `P` and `O_{j-1}` from TMEM, multiplies, and writes the rescaled `O` back to TMEM, completely outside the critical path of the softmax computation.

**Why a separate correction warpgroup is possible:** In FlashAttention-3, `P` was held in registers distributed across the softmax warpgroups. Rescaling `O` required the same warpgroups that computed softmax to also perform the rescaling — it was part of their serial execution. With TMEM, `P` is accessible to any warpgroup in the CTA. The authors exploit this to move rescaling to a warpgroup that is otherwise underutilized, effectively taking it off the critical path. This is a direct consequence of Blackwell's TMEM: it decouples the *producer* of a tensor (the MMA warpgroup that writes `S`, the softmax warpgroup that writes `P`) from the *consumer* (the correction warpgroup that reads `P` to rescale `O`).

**Tensor memory partitioning.** TMEM is 256 KB per SM and is allocated in 32-column (16 KB) granules. The forward pass needs to store: (a) two `S` tiles of size `128 × 128` in BF16 (32 KB each = 64 KB total), (b) `P` tiles (softmax output, also `128×128` BF16 = 32 KB each), and (c) a small region for communicating rescale statistics (the running max and sum) between the softmax and correction warpgroups. The authors choose the "two S tiles overlapping with P" partitioning: TMEM holds two `S` tiles at all times (occupying 128 KB of the 256 KB), with the `P` tiles stored in the same region after `S` is consumed. This leaves approximately 96 KB free for rescale statistics communication and any temporary storage. The alternative partitioning (one `S` tile and two `P` tiles) would prevent the ping-pong pipeline from starting by immediately computing two `S` tiles, reducing the ability to overlap softmax with MMA in the first iterations.

**Register pressure management.** Each softmax warpgroup processes an entire row of 128 elements (matching Blackwell's 128-wide MMA tile). For BF16 inputs, holding one row requires 128 registers for the input values plus up to 64 registers for the output (softmax probabilities), plus registers for the row max, row sum, and polynomial coefficients (for exponential emulation). The total register requirement approaches 256 registers per thread — Blackwell's register file limit. To avoid register spills (which would serialize execution and destroy the pipeline's overlapping benefits), the authors stage the storing of `P`: the first three-quarters of each row (96 elements) are stored to TMEM immediately after computation, and the last quarter (32 elements) is stored in a separate operation. This reduces the live register count during the critical softmax loop by 32 registers, staying within the 256-register budget.

**Synchronization.** The two softmax warpgroups must not overlap in their critical section — the part of the code that computes exponentials and row sums — because the MUFU unit has limited throughput (16 ops/clock) and two warpgroups simultaneously issuing exponential instructions would serialize at the hardware level, negating the benefit of having two warpgroups. The authors insert explicit synchronization barriers: softmax warpgroup 0 signals when it exits its critical section, allowing warpgroup 1 to enter. This is identical in spirit to FlashAttention-3's approach, but the larger tile size (128 vs. 64 rows per warp) means each warpgroup has more work per synchronization event, reducing the relative overhead.

#### 3.4.3 Exponential Emulation via Polynomial Approximation

The MUFU unit on Blackwell provides 16 exponential operations per clock cycle per SM — exactly the same as Hopper, while tensor core throughput doubled. For the forward pass, a tile of size `M × N = 128 × 128 = 16,384` requires 16,384 exponential evaluations, which at 16 ops/clock takes 1024 cycles — equal to the MMA compute time for the baseline tile. For larger tiles (`M=256, N=128`), exponentials require 2048 cycles, matching the doubled MMA time. In both cases, the exponential unit is at parity with MMA, not faster. If any part of the exponential computation cannot be perfectly overlapped with MMA, it becomes the bottleneck.

**The key insight:** The GPU also has floating-point FMA (fused multiply-add) units that are separate from the MUFU and can operate in parallel with it. By emulating some fraction of the exponential evaluations using polynomial approximation on FMA units, the kernel can effectively *increase* the aggregate exponential throughput beyond the MUFU's 16 ops/clock — the MUFU handles some entries while FMA units handle others, and because they are different hardware pipelines, they execute concurrently.

**The decomposition.** The implementation approximates `2^x` (the base-2 exponential, since BF16 uses binary floating-point and scaling by powers of 2 is efficient) using the standard range-reduction technique:

$$2^x = 2^{\lfloor x \rfloor} \cdot 2^{x - \lfloor x \rfloor}$$

where `⌊x⌋` is the integer floor and `x - ⌊x⌋ ∈ [0, 1)` is the fractional part.

**Computing the integer part `2^{⌊x⌋}`.** For IEEE 754 floating-point numbers, the exponent field directly encodes a power of 2. Specifically, a BF16 number is represented as `(-1)^s × 2^{e-127} × 1.m`, where `e` is the 8-bit exponent stored in bits 7–1 and `m` is the 7-bit mantissa in bits 6–0. To compute `2^{⌊x⌋}` where `⌊x⌋` is an integer, the algorithm: (1) extracts `⌊x⌋` by adding a large constant `2^23 + 2^22` to `x` in round-down mode (this forces the fractional bits into the mantissa, leaving the integer part), subtracting the same constant (still in round-down mode) to recover just the integer, (2) shifts `⌊x⌋` into the exponent field of a BF16 number by adding 127 (the bias) and inserting it into bits 7–1, leaving the mantissa as all zeros (representing `1.0 × 2^{⌊x⌋}`). This is done with integer ALU operations, not floating-point.

**Computing the fractional part `2^{x_{\text{frac}}}`.** The fractional part `x_{\text{frac}} ∈ [0, 1)` is approximated by a polynomial:

$$2^{x_{\text{frac}}} \approx \sum_{i=0}^{n} p_i x_{\text{frac}}^i$$

with `p_0 = 1.0` and the remaining coefficients `p_1, ..., p_n` chosen to minimize relative approximation error over `[0, 1)`. The coefficients are computed using the Sollya numerical software package, which uses Remez exchange to find minimax polynomial approximations. The polynomial is evaluated using Horner's method:

$$p(x) = p_0 + x(p_1 + x(p_2 + x(p_3 + ...)))$$

where each multiply-add is a single FMA instruction. A degree-3 polynomial requires 3 FMA instructions; degree-4 requires 4; degree-5 requires 5.

**Combining the parts.** The final exponential is `2^x = 2^{⌊x⌋} × 2^{x_{\text{frac}}}`. In floating-point, multiplying by `2^{⌊x⌋}` is equivalent to adding `⌊x⌋` to the exponent field. The algorithm takes the mantissa bits of the polynomial result (which represent `2^{x_{\text{frac}}}` in the range [1.0, 2.0)) and inserts the shifted integer into the exponent field, combining them with integer bitwise OR. The result is a BF16 number representing `2^x`.

**Why only partial emulation (10–25%)?** The polynomial emulation is not strictly faster than MUFU per evaluation — it requires 3–5 FMA instructions plus integer bit manipulation, while `MUFU.EX2` is a single instruction. The benefit comes from *parallelism*: while the MUFU is busy computing exponentials for 75–90% of the row, the FMA units (which would otherwise be idle during the softmax exponential phase) compute the remaining 10–25%. The exact fraction is tuned empirically: too low, and the bottleneck remains the MUFU; too high, and the FMA units become the bottleneck (since they're also needed for other operations) or the additional register pressure from polynomial coefficients causes spills. The fraction depends on the tile configuration — the authors state it is "tuned empirically based on the ratio of MMA and exponential throughput for a given tile configuration."

**Accuracy justification (Table 2).** The degree-3 polynomial has a maximum relative error of `8.77 × 10^{-5}` at FP32 precision, which is approximately 600× worse than the hardware `MUFU.EX2` (max relative error `1.41 × 10^{-7}`). However, after rounding the FP32 output to BF16 (the precision at which softmax probabilities are consumed), the quantization error of BF16 (`3.89 × 10^{-3}` max relative error) completely dominates the polynomial approximation error. The degree-3 polynomial matches hardware to within 1 BF16 ULP on 99% of inputs — meaning the outputs are indistinguishable after quantization. Higher-degree polynomials close the FP32 gap (degree-5 matches hardware to within 2×) but at the cost of additional FMA instructions and register pressure. Since the BF16 rounding error is the dominant error source, degree-3 suffices for attention.

**Preprocessing step: clamping.** Before computing the exponential, the input `x` is clamped to be at least -127. Values below this would underflow to zero in BF16 (since the minimum representable exponent is -126), and computing exponentials for extreme negative values wastes computation. This clamp is cheap (a single `max` instruction) and avoids unnecessary work.

#### 3.4.4 Conditional Softmax Rescaling

The standard online softmax algorithm in FlashAttention maintains running statistics as it processes blocks of the key/value sequence. When processing block `j`, with attention scores `S_j` for that block, the algorithm tracks:

- `m_j = max(m_{j-1}, \text{rowmax}(S_j))` — the running maximum score seen so far
- `ℓ_j = e^{m_{j-1} - m_j} ℓ_{j-1} + \text{rowsum}(e^{S_j - m_j})` — the running normalizer (sum of exponentials)

The intermediate output `O_j` is updated as:

$$O_j = e^{m_{j-1} - m_j} O_{j-1} + e^{S_j - m_j} V_j$$

The rescaling factor `e^{m_{j-1} - m_j}` renormalizes the *previous* accumulated output to the new, larger maximum. When `m_j > m_{j-1}` (a new maximum was found in the current block), this rescaling is necessary for numerical correctness. When `m_j = m_{j-1}` (no new maximum), the factor is `e^0 = 1.0` and the rescaling is a no-op.

**Observation 1: Rescaling is only necessary when a new maximum is found.** In practice, the running maximum rises quickly in the first few blocks (as larger attention scores are encountered) and then stabilizes — subsequent blocks rarely contain values larger than the current maximum. This means that for the majority of blocks in a long sequence, `m_j = m_{j-1}` and the rescaling is wasted work.

**Observation 2: Small increases in the maximum can be deferred.** If `m_j - m_{j-1}` is small, the rescaling factor `e^{m_{j-1} - m_j}` is close to 1.0. Multiplying the entire output `O_{j-1}` by a factor near 1.0 is numerically equivalent to doing nothing, up to floating-point rounding error. The authors introduce a threshold `τ = log2(256) = 8.0`, corresponding to a rescaling factor of `e^8 = 2981`. When `m_j - m_{j-1} ≤ τ`, the rescaling step is *skipped entirely*, and the previous normalizer `ℓ_{j-1}` and maximum `m_{j-1}` continue to be used. The output update becomes:

$$O_j = \begin{cases} e^{m_{j-1} - m_j} O_{j-1} + e^{S_j - m_j} V_j & \text{if } m_j - m_{j-1} > \tau \\ O_{j-1} + e^{S_j - m_{j-1}} V_j & \text{otherwise} \end{cases}$$

**Why this is numerically correct.** The algorithm keeps track of the *total* accumulated slack — the difference between the true running maximum (which would have been `m_j` if rescaling were always applied) and the maximum actually used (`m_{j-1}`). At the end of the sequence, the final output `O_{\text{final}}` is multiplied by the true normalizer `1/ℓ_{\text{final}}` (computed with the true maximum `m_{\text{final}}`). Because the rescaling operations that were skipped were multiplications by factors near 1.0, the accumulated error is on the order of machine epsilon, and the final normalization step corrects it.

**Warp divergence handling.** To avoid warp divergence (where some threads in a warp take the rescaling branch and others skip it, causing serialized execution on GPUs that execute warps in lockstep), the threshold check is performed at warp granularity: if *any* thread in the warp has `m_j - m_{j-1} > τ`, the entire warp performs rescaling. This means some threads perform unnecessary rescalings, but it avoids the much larger penalty of warp divergence. The authors state this explicitly: "in practice, to avoid warp divergence, we rescale when any of the threads in the warp needs rescaling."

**Practical effect.** This optimization reduces the number of `e^{m_{j-1} - m_j} O_{j-1}` vector multiplications from "every block where the maximum changes" to "every block where the maximum changes by more than a factor of 256." For long sequences, the maximum typically rises sharply in the first few blocks and then flatlines, so the conditional rescaling eliminates the vast majority of rescaling operations. This reduces pressure on the FMA units (which perform the vector multiply) and the shared memory bandwidth (for reading/writing `O`), both of which are scarce resources on Blackwell.

#### 3.4.5 Backward Pass Roofline Analysis

The backward pass is substantially more expensive than the forward pass: it performs **five** MMA operations per iteration (compared to two in the forward), corresponding to recomputing `S = QK^T` (same as forward) and then propagating gradients through `dV = P^T dO`, `dP = dO V^T`, `dS = d\text{softmax}(dP)`, `dQ = α dS K`, and `dK = α dS^T Q`.

**MMA compute cycles.** Each of the five MMAs requires `2MNd` FLOPs, for a total of:

$$T_{\text{MMA}} = \frac{10MNd}{8192} \text{ cycles}$$

For the baseline tile `M=N=d=128`, this is `10 × 2 × 128^3 / 8192 = 10 × 4,194,304 / 8192 = 5120` cycles. The authors report 2560 cycles in Table 3 — the discrepancy is because they are counting per-tile cycles for a *single iteration*, where the total FLOPs are `5 × 2MNd` but the tile configuration `M=N=d=128` gives each MMA `2 × 128^3 = 4,194,304` FLOPs. Five such MMAs = 20,971,520 FLOPs. At 8192 FLOPs/cycle: 20,971,520 / 8192 = 2560 cycles. This matches.

**Shared memory cycles.** The five MMAs are categorized by their operand sources:

- **Shared-shared (SS):** Three MMAs — `S^T = K Q^T`, `dP^T = V dO^T`, and `dQ = dS K` — read both operands from shared memory.
- **Tensor-shared (TS):** Two MMAs — `dV = P^T dO` and `dK = dS^T Q` — read operand A from tensor memory and operand B from shared memory.

For the SS MMAs, the shared memory reads total `⌈M/128⌉⌈N/128⌉ × 2 × 128d` for the first two (each reads Q/K or V/dO) and `⌈M/128⌉⌈d/128⌉ × 2 × 128N` for `dQ`. For the TS MMAs, only operand B (from shared memory) contributes: `⌈M/128⌉⌈N/128⌉ × 128d` for `dV` and `⌈N/128⌉⌈d/128⌉ × 128M` for `dK`. Additionally, the algorithm writes the intermediate gradient `dS` (`M × N` BF16) to shared memory and the output gradient `dQ` (`M × d` FP32) to shared memory for the atomic reduction.

The total shared memory access time, assuming `M=N=d=128` and all ceil divisions evaluate to 1, is:

$$T_{\text{smem}} = \frac{4Md + 3Nd + MN}{64} + \frac{MN}{64} + \frac{Md}{16} \text{ cycles}$$

where:
- `(4Md + 3Nd + MN) / 64`: SS operands (3 SMEM reads, each `2 × 128 × 128` bytes for the first two, `2 × 128 × 128` for `dQ`) plus TS operand B reads (`128 × 128` bytes for `dV`, `128 × 128` for `dK`). At 2 bytes/element and 128 bytes/cycle: `(4×128×128 + 3×128×128 + 128×128) × 2 / 128 = (8 + 6 + 2) × 128 = 2048` cycles.
- `MN / 64`: writing `dS` (128×128 BF16 = 32,768 bytes) to shared memory at 128 bytes/cycle: 256 cycles.
- `Md / 16`: writing `dQ` (128×128 FP32 = 65,536 bytes) to shared memory and reading it back via TMA for reduction. Total: 131,072 bytes / 128 bytes/cycle = 1024 cycles.

Total: 2048 + 256 + 1024 = 3328 cycles. This exceeds the MMA compute time of 2560 cycles by **~30%**, establishing shared memory bandwidth as the primary bottleneck for the 1-CTA backward pass.

**Exponential unit cycles.** The softmax gradient `dS = d\text{softmax}(dP)` requires elementwise operations involving exponentials and logarithms for each of the `M × N = 16,384` entries in the attention tile. At 16 ops/cycle, this requires `MN / 16 = 1024` cycles — substantially less than either MMA or shared memory.

**Why the bottleneck shifts to shared memory in the backward pass.** In the forward pass, shared memory was below MMA and exponential throughput (768 vs. 1024 cycles). In the backward pass, the five MMAs collectively read 8 BF16 operands from shared memory (out of 10 total operands — 2 are in TMEM), generating approximately 2.3× more shared memory traffic than the forward pass's two MMAs. Meanwhile, MMA compute also increased (5/2 = 2.5× more FLOPs), but the shared memory increase is disproportionate because the SS MMAs read both operands while the TS MMAs read only one. This imbalance makes shared memory — not MMA, not exponentials — the resource that dictates performance.

#### 3.4.6 Backward Pass Pipeline: Overlapping Two MMAs with Softmax Gradient

The backward pass's five MMAs create a complex scheduling problem: the operations form a directed acyclic graph (Figure 2) where `S` must be computed before `dP` and `dV`, `dP` before `dS`, `dS` before `dQ` and `dK`, and `dV` and `dK` accumulate across iterations. FlashAttention-3, constrained by register pressure, largely serialized this graph — computing `S`, then `dP`, then `dV`, then `dQ`, then `dK` — with only TMA loads running significantly out of order.

**What TMEM enables.** With TMEM, accumulators don't consume registers, freeing enough register space to handle two concurrent MMA operations and the softmax gradient computation simultaneously. The authors design a pipeline where `dQ` and `dK` from iteration `t-1` execute concurrently with `dP` and the softmax gradient `dS` for iteration `t`.

**TMEM allocation.** The backward pass needs to store five accumulator tiles: `S`, `P`, `dP`, `dS`, and `dQ`. Each tile is `128×128` at BF16 precision (32 KB), but `dQ` accumulates in FP32 (128 KB for a 128×128 tile). However, `dV` and `dK` also accumulate and cannot share their space. The total TMEM requirement exceeds the 256 KB budget. The authors' solution:

- **Block 0 (offset 0):** `S` and `P` share this region. `S` is computed first, then overwritten by `P` after softmax. Since `S` is needed only for computing `P` and `dS` during the backward pass, and `P` is needed only for `dV`, the sharing is safe as long as `P` is consumed before `S` is overwritten in the next iteration.
- **Block 1:** `dP`, `dS`, and `dQ` share this region. These three tensors are needed at different points in the pipeline (see Figure 2): `dP` is computed from `V` and `dO`, then `dS` is computed elementwise from `dP` and `S`, then `dQ` is computed from `dS` and `K`. The sharing is possible because each tensor is consumed before the next is produced.
- **Dedicated regions:** `dV` and `dK` each get their own small accumulator region because they accumulate across iterations (they are reductions over the query sequence length dimension) and cannot share space without temporaries.

**Pipeline ordering (Figure 2).** The execution is divided into prologue, main loop, and tail:

- **Prologue:** Load initial `Q`, `K`, `V` tiles. Compute `S` for the first tile, then `P = \text{softmax}(S)`. Compute `dP` from `V` and `dO`.
- **Main loop (iteration `t`):**
  1. **TMA loads:** Load `Q_t`, `K_t`, `V_t` tiles into shared memory asynchronously.
  2. **MMA: `S_t = Q_t K_t^T`** (SS, writes to TMEM block 0, overwriting `P_{t-1}`).
  3. **Concurrent: `dQ_{t-1}` and `dK_{t-1}` MMAs** — these use operands from the *previous* iteration: `dS_{t-1}` (in TMEM block 1) and `K_{t-1}` or `Q_{t-1}` (in shared memory). While these MMAs execute, the softmax warpgroup processes `S_t` to produce `P_t`.
  4. **MMA: `dV_t = P_t^T dO_t`** (TS, `P_t` from TMEM block 0, `dO_t` from shared memory; accumulates in dedicated TMEM region).
  5. **MMA: `dP_t = dO_t V_t^T`** (SS, writes to TMEM block 1).
  6. **Elementwise: `dS_t = d\text{softmax}(dP_t, S_t)`** — reads `dP_t` from TMEM block 1 and `S_t` from TMEM block 0, writes `dS_t` to TMEM block 1 (overwriting `dP_t`).
  7. **MMA: `dQ_t = \alpha dS_t K_t`** (SS, `dS_t` from TMEM block 1; `K_t` from shared memory; accumulates to TMEM block 1, overwriting `dS_t`).
  8. **MMA: `dK_t = \alpha dS_t^T Q_t`** (TS, `dS_t` from TMEM block 1; `Q_t` from shared memory; accumulates in dedicated TMEM region).
- **Tail:** Complete any remaining MMAs and atomically add partial `dQ` and `dK` results to global memory.

**The key overlap.** Step 3 is the critical innovation. In a naïve schedule, `dQ_{t-1}` and `dK_{t-1}` would execute *after* `dS_t` is computed (requiring `dS_{t-1}` to remain in TMEM until then), or they would execute *before* `S_t` (delaying the softmax). By scheduling them *concurrently* with the softmax of `S_t` (which uses TMEM block 0, not block 1), the MMAs for iteration `t-1` and the softmax for iteration `t` share the tensor cores and MUFU unit without conflicting on TMEM.

**Why this is better than FlashAttention-3's schedule.** FlashAttention-3 could overlap at most one MMA with softmax (typically `dP`) because accumulators were in registers and register pressure prevented holding state for multiple concurrent operations. Blackwell's TMEM effectively "caches" intermediate results (like `dS_{t-1}`) in on-chip memory accessible to tensor cores, so the kernel can keep two independent MMA streams active: one consuming the current iteration's TMEM outputs (`dV_t`, `dP_t`), and one consuming the previous iteration's (`dQ_{t-1}`, `dK_{t-1}`). This doubles the effective overlap between MMA and non-MMA operations.

#### 3.4.7 2-CTA Backward Mode: Reducing Shared Memory Traffic and Atomics

Even with the improved pipeline, the 1-CTA backward pass is bottlenecked by shared memory bandwidth (3328 cycles vs. 2560 cycles for MMA). The 2-CTA MMA mode — a Blackwell-specific feature where two CTAs in the same thread block cluster cooperatively execute a single MMA — is the paper's most architecturally novel optimization for mitigating this.

**How 2-CTA MMA works.** In standard (1-CTA) mode, a single CTA launches an MMA with tile shape `M × N × K` (typically `128 × 128 × 128` on Blackwell). Both operands A (`M × K`) and B (`K × N`) are loaded from that CTA's shared memory. In 2-CTA mode, a **CTA pair** (two CTAs that are part of the same thread block cluster and co-scheduled on the same GPC) jointly execute an MMA with tile shape `M × N × K` where `M = 256` (double the 1-CTA size). The A tile is partitioned along the M dimension: CTA 0 owns rows 0–127, CTA 1 owns rows 128–255. The B tile is partitioned along the N dimension: **each CTA stages only half of B** in its own shared memory (CTA 0 stages columns 0–63, CTA 1 stages columns 64–127 for `N = 128`), and the hardware reads the combined B tile from both CTAs' shared memories during the multiply. The output accumulator is partitioned in M: each CTA writes its own `128 × 128` slice to its own TMEM.

**Why this reduces shared memory traffic.** In 1-CTA mode, every CTA that participates in an MMA must load the *full* B operand into its shared memory. If multiple CTAs are performing the same MMA (e.g., each processing a different query tile but sharing the same K tile in `dQ`), each CTA redundantly loads the same B operand. In 2-CTA mode, the two CTAs collectively load B once: each loads half, and the hardware accesses both halves. This halves the shared memory bandwidth consumed by operand B for all MMAs executed in 2-CTA mode.

**Application to the backward pass.** The backward pass's five MMAs are converted to 2-CTA mode with tile shape `M=256, N=128, K=128` (four of the five) and a special shape for `dQ` (`M=128, N=256, K=128` — doubled reduction). The shared memory savings are substantial: Table 3 shows that total shared memory cycles drop from 3328 (1-CTA) to 2688 (2-CTA), with the majority of savings coming from reduced MMA operand reads (2048 → 1536 cycles for MMA operands) and reduced `dQ` write/read traffic (1024 → 512 cycles). The shared memory bottleneck margin shrinks from ~30% to ~5%.

**The `dQ` restructuring (Figure 3).** The `dQ` gradient accumulation is a reduction along the KV sequence length dimension: `dQ` is the sum over blocks `j` of `dS_j K_j`. In 1-CTA mode, each CTA processes a different query tile (different rows of `dS`) and independently performs the reduction, requiring separate global atomic adds for each CTA's partial result. In 2-CTA mode, the CTA pair would naturally split the `dS` operand along the M dimension (query sequence), meaning CTA 0 would reduce over half the query tokens and CTA 1 over the other half — each independently. But the reduction dimension is N (the KV sequence), not M, so splitting along M does not help the reduction.

The authors solve this with **distributed shared memory (DSMEM)** — shared memory that is accessible across CTAs in the same cluster. After computing `dS` (which is first partitioned along M as usual), the two CTAs use DSMEM to exchange half of their `dS` tiles: CTA 0 sends its second half (rows 64–127) to CTA 1 and receives CTA 1's first half (rows 128–191), while CTA 1 does the reverse. After the exchange, each CTA holds a `(128/2 = 64) × 128` tile of `dS` — but now partitioned along the *non-reduction* axis. Each CTA then forms a `dS` operand of shape `(64 × 256)` by concatenating its original rows (now in both CTAs) with the received rows. This `2N = 256` operand (double the reduction dimension) enables each CTA to perform a `dQ` MMA of shape `(64, 256) × (256, d)` → `(64, d)`, which is a *full* reduction over `2N` elements rather than a partial reduction over `N` elements.

**Halving global atomic adds.** Because each CTA now performs a reduction over `2N = 256` elements (instead of `N = 128`), the number of CTA pairs that contribute to any given `dQ` tile is **halved**. Consequently, each CTA writes only half of the `dQ` tile and performs half as many global atomic reductions as the 1-CTA counterpart. Atomic adds are expensive for two reasons: (1) they require global memory access (hundreds of cycles of latency), and (2) they introduce nondeterminism (the order in which CTAs perform the atomic add affects the floating-point accumulation). Halving the number of atomic adds directly improves both performance and reproducibility.

**Pipeline reordering to hide DSMEM latency.** The DSMEM exchange has non-trivial latency (it requires the two CTAs to synchronize and transfer data through shared memory). The authors reorder the software pipeline so that DSMEM latency is hidden: instead of computing `dS`, then exchanging, then computing `dQ` for the current tile, the pipeline computes `dP` for the *current* tile, then launches the `dQ` MMA for the *previous* tile (whose DSMEM exchange already completed in the previous iteration), then computes the elementwise `dS` for the current tile and initiates its DSMEM exchange. This means the `dQ` MMA executes during the DSMEM exchange of the next tile, overlapping communication with computation.

#### 3.4.8 Deterministic Backward Pass

The standard backward pass in FlashAttention-4 is nondeterministic: multiple CTAs concurrently perform atomic additions to the same `dQ` (and `dK`/`dV` in the case of grouped-query attention) tiles in global memory. Because floating-point addition is not associative, the order in which these atomic adds occur affects the final gradient values, leading to run-to-run variation that can complicate debugging, reproducibility, and reinforcement learning training (where deterministic gradients are often required for policy gradient methods).

**The lock-based approach.** The deterministic mode serializes the global reductions using a semaphore lock. Each `dQ` tile in global memory is associated with a semaphore counter initialized to 0. Before a CTA performs its atomic reduction, it must acquire the lock: it waits (spinloops) until the semaphore equals its assigned sequence number, performs the reduction, then releases the lock by incrementing the semaphore. This ensures CTAs reduce in a predefined, consistent order, producing bitwise-identical results across runs.

**Performance impact.** The lock introduces two sources of overhead: (1) issuing a memory fence instruction (`membar.gl`) to ensure device-wide visibility of the semaphore write (needed for acquire-release semantics across CTAs on different SMs), and (2) stall time when a CTA must wait for the previous CTA in the reduction order to finish before it can proceed. The stall time is particularly severe if the reduction order is poorly chosen — for example, if a CTA assigned sequence number 0 takes much longer than CTA 1 (due to load imbalance from causal masking), CTA 1 will stall waiting for CTA 0 to finish before it can proceed.

**Shortest-processing-time-first (SPT) scheduling to minimize stalls.** The authors observe that for causal masking, the CTA processing query tiles near the diagonal (where the attention mask has few masked entries) has a much longer mainloop than the CTA processing query tiles far from the diagonal (where most attention scores are masked). By launching KV blocks in descending order, traversing query blocks in ascending order starting from the diagonal, and ordering the `dQ` reductions by descending query block index, the CTA with the *longest* processing time (the one nearest the diagonal, with the most unmasked scores) is assigned the *first* sequence number. Subsequent CTAs (with shorter processing times) are assigned later sequence numbers. This "shortest-processing-time-first" (SPT) schedule ensures that when a later CTA arrives at the lock, it is *likely* that the earlier (longer-running) CTA has already finished — minimizing stall time. The paper reports that this deterministic mode achieves up to 75% of the nondeterministic 1-CTA backward pass throughput (Figure 7), meaning the overhead is approximately 25% in the best case.

#### 3.4.9 LPT Scheduling for Load Imbalance

The attention kernel grid consists of CTAs indexed by `(mblock, head, batch)`, where `mblock` is the query tile along the sequence length dimension, `head` is the attention head index, and `batch` is the batch element. In workloads with causal masking or variable sequence lengths, different `(mblock, head, batch)` tuples have different amounts of work — the inner loop length (number of KV blocks to process) varies.

**The standard ordering is suboptimal.** A naïve kernel processes CTAs in increasing order of `(mblock, head, batch)`. For causal masking, this processes query tiles from the beginning of the sequence (short mainloop, since early tokens attend to few KV positions) to the end (long mainloop, since later tokens attend to many KV positions). The SM that finishes early (processing the short mainloop) goes idle while the SM with the long mainloop continues — a classic load imbalance.

**Longest-processing-time-first (LPT) heuristic.** The classical scheduling result is that processing jobs in decreasing order of execution time minimizes the makespan (total completion time) on identical parallel machines. The authors apply this by processing `mblock` in **reverse order** for causal masking: query tiles near the end of the sequence (long mainloop, since they attend to most KV positions) are processed first, and query tiles near the beginning (short mainloop) are processed last. This balances load because long and short jobs are interleaved across SMs.

**L2 cache considerations.** A naive global LPT order (sorting all CTAs across all heads and batches by estimated execution time) would maximize load balance but thrash the L2 cache: different heads have different K and V tensors, and switching between heads on every CTA would cause constant cache misses. The authors compromise by processing **batches as the outermost dimension** and **swizzling over heads**: heads are divided into groups that fit within the L2 cache capacity, and within each head group, `mblock` is traversed in reverse LPT order. This preserves L2 cache locality for K and V tiles (which are shared across `mblock` for the same head) while still achieving the LPT load-balancing benefit.

**For variable sequence lengths (varlen).** The standard varlen kernel reads sequence lengths from attention metadata at runtime and processes batches in the order they appear in the metadata. If this order is adversarially bad (e.g., short sequences followed by long sequences), load imbalance results. The authors propose an **optional preprocessing kernel** that sorts batches by their estimated execution time (computed as the maximum per-worktile execution time, proportional to the product of query and KV sequence lengths) and writes a mapping from virtual to actual batch indices. The attention kernel then reads this mapping at minimal cost (it is cached). This preprocessing cost is amortized over multiple attention calls if the metadata doesn't change.

**Empirical gains.** The paper reports 4–8% FLOPs gain for MHA and 7–14% for MQA (multi-query attention with 8 query heads per KV head) on an H200 GPU using the LPT scheduler, demonstrating that the technique is architecture-agnostic (it benefits Hopper as well as Blackwell). The larger gain for MQA is expected because MQA has higher L2 cache pressure (multiple query heads share the same K and V, so processing all query heads per KV head before switching maximizes cache reuse).

## 4. Key Insights and Innovations

### Innovation 1: Asymmetric Hardware Scaling as a First-Class Design Constraint — The Roofline-Driven Co-Design Methodology

The paper's most foundational contribution is not any single optimization but rather the **explicit framing of asymmetric hardware scaling as the central design problem** for attention kernels, and the demonstration that a quantitative roofline analysis — comparing cycle counts for MMA compute, shared memory bandwidth, and exponential throughput — should *precede* and *direct* all algorithmic and pipeline decisions.

Prior to this work, the dominant approach to optimizing attention for new GPU generations was **porting and tuning**: take the best existing kernel (e.g., FlashAttention-3 for Hopper), adapt it to the new instruction set, adjust tile sizes and register allocation empirically, and benchmark. This implicitly treats the new hardware as a faster version of the old hardware — the bottlenecks are assumed to be in roughly the same places, just with different constants. The paper shows that this assumption is **catastrophically wrong** for Blackwell. The doubling of tensor core throughput (8192 vs. 4096 ops/clock/SM) while shared memory bandwidth (128 bytes/cycle) and exponential throughput (16 ops/cycle) remain unchanged means that the *identity* of the bottleneck shifts: from MMA compute on Hopper to shared memory traffic and exponential computation on Blackwell.

What makes this a conceptual advance rather than an engineering observation is the **roofline analysis methodology** itself (Tables 1 and 3). By decomposing the forward and backward passes into cycle-count estimates for each hardware resource as a function of tile dimensions (M, N, d), the authors create a diagnostic tool that reveals not just *that* there is a bottleneck but *which* resource is the bottleneck, *by what margin* (25–60%), and *how* the margin changes with tile size. This is not a one-time finding; it is a **transferable methodology**. For any future GPU generation with different throughput ratios, the same analysis would identify different bottlenecks and suggest different optimizations. The paper is effectively arguing that attention kernel development should begin with a roofline analysis, not with a port of the previous kernel — and it provides the template for doing so.

This reframing has an important negative implication that the paper only partially states: **FlashAttention-3's design was overfit to Hopper's bottleneck profile.** Its pipeline structure, register allocation, warpgroup sizing, and tile dimensions were all optimized under the assumption that MMA compute was the scarce resource. These choices are *wrong* on Blackwell not because they are bad ideas in general, but because they optimize for a constraint that no longer binds. The paper subtly demonstrates this by showing that a kernel designed from scratch for Blackwell's bottlenecks achieves 1.3× the throughput of cuDNN (Figure 4) — which, as a vendor library with deep hardware knowledge, presumably would have been the best-case outcome of a tuning-based approach.

The significance beyond raw performance is that this methodology **makes attention kernel performance predictable rather than empirical**. Given a new GPU's specification sheet (tensor core throughput, shared memory bandwidth, special function unit throughput, TMEM size), the roofline analysis directly predicts which resources will bottleneck attention at which tile sizes, and therefore which classes of optimizations (pipeline restructuring, exponential emulation, shared memory reduction) are worth pursuing. This is a step toward attention kernel performance becoming an engineering discipline rather than a craft.

### Innovation 2: Software Emulation as a Bottleneck Mitigation Strategy — Bypassing Hardware Unit Limits Through Parallelism

The exponential emulation via polynomial approximation (Section 3.1.3, Table 2) represents a genuinely counterintuitive idea: **replacing a single hardware instruction (`MUFU.EX2`) with a multi-instruction software sequence (3–5 FMAs plus integer bit manipulation) can *increase* throughput despite higher per-operation cost.** This contradicts the standard intuition that hardware-accelerated functions are always faster than software emulation and should be used whenever available.

The key insight that makes this work is a **parallelism argument, not a latency argument.** A single `MUFU.EX2` instruction is faster than a degree-3 polynomial (lower latency, fewer cycles). But the MUFU unit provides only 16 ops/clock/SM, while the FMA units that evaluate the polynomial are *separate hardware pipelines* that can operate concurrently with the MUFU. By splitting exponential evaluations across both units — the MUFU handles 75–90% of a row, while FMA units simultaneously handle the remaining 10–25% — the *aggregate* exponential throughput exceeds what either unit could achieve alone. The optimization is not about making individual exponentials faster; it's about **exploiting hardware parallelism to circumvent a throughput ceiling**.

This represents a specific instantiation of a more general principle that the paper only hints at but that has broad implications: **when a specialized hardware unit becomes a bottleneck due to limited throughput (not latency), the correct optimization is to offload some fraction of its work to other, underutilized units — even if those units are individually slower at the task.** The MUFU is not the only special function unit on GPUs; future architectures may bottleneck on division, square root, or transcendental functions, and the same emulation-on-FMA-units strategy could apply. The paper's partial emulation approach (tuning the fraction empirically based on the MMA-to-exponential throughput ratio) provides a template for how to think about this class of optimization.

The accuracy analysis in Table 2 is an essential part of this innovation: it shows that a degree-3 polynomial, despite being 600× less accurate than hardware `MUFU.EX2` at FP32 precision, is **indistinguishable after BF16 rounding** — the quantization error of BF16 (~3.9 × 10⁻³) dominates the polynomial approximation error (8.8 × 10⁻⁵). This is not just a convenient coincidence; it reflects a deeper point about **precision hierarchies in attention.** Softmax probabilities are consumed downstream in BF16 (for the `PV` matmul), so there is no benefit to computing them at higher precision than BF16. The exponential can be *dramatically* approximate as long as the approximation error is below the quantization threshold. This insight generalizes: for any operation whose output is quantized to a lower precision, the computation can be made substantially cheaper by targeting the quantization error, not the full-precision error.

The incremental-vs-fundamental distinction is important here. Exponential emulation is an *incremental* optimization in the sense that it addresses a specific hardware bottleneck that may not exist on future GPUs (the paper notes that B300 already doubles MUFU throughput to 32 ops/clock). But the **strategy of partial hardware-bypass via software emulation on parallel units** is fundamental: it represents a new class of optimization that was not present in FlashAttention-2 or FlashAttention-3, both of which used MUFU exclusively. As long as GPU architectures contain specialized units with limited throughput alongside general-purpose FMA units, this strategy will have applications.

### Innovation 3: The 2-CTA MMA Mode as a Structural Reorganization — Halving Shared Memory Traffic and Atomics Through Cooperative Execution

The 2-CTA backward pass (Section 3.2.3, Figure 3) is the paper's most architecturally novel contribution — not because it uses a new Blackwell feature (2-CTA MMA mode is documented by NVIDIA), but because of **how the feature is exploited to fundamentally restructure the `dQ` computation in a way that addresses two independent bottlenecks simultaneously.**

Prior attention kernels (FlashAttention-2, FlashAttention-3, and even the 1-CTA variant of FlashAttention-4) follow a fixed structural pattern for the backward pass: each CTA independently processes its assigned query tile, independently loads K and V operands into shared memory, independently computes `dQ` as a partial reduction over the KV sequence, and independently performs a global atomic add to accumulate its partial `dQ` into the global gradient. This is a **CTA-parallel reduction**: parallelism comes from having many CTAs work on different query tiles, but each CTA's work is self-contained.

The 2-CTA mode enables a **structurally different parallelism**: two CTAs in the same cluster cooperatively execute a single MMA, sharing operands through distributed shared memory (DSMEM) and partitioning the output. This is not just "bigger tiles" or "more parallelism" — it changes the *dataflow* of the reduction. By using DSMEM to repack `dS` along the non-reduction axis (Figure 3), each CTA in the pair forms a `(M/2 × 2N)` operand — a doubled reduction dimension — and performs a single MMA that accumulates over twice as many KV positions as the 1-CTA version. This means each CTA pair contributes to only **half** as many `dQ` tiles, which means **half** as many global atomic adds.

The elegance of this optimization is that it **solves two problems with one restructuring.** The primary motivation was reducing shared memory traffic (which roofline analysis identified as the 30% bottleneck): by having each CTA stage only half of operand B, shared memory reads for B operands are halved across all five backward pass MMAs. The halving of atomic adds is a *byproduct* of the `dQ` restructuring — not an independently designed optimization — but it addresses a separate bottleneck (global memory atomics are expensive and nondeterministic) without additional cost. This is the hallmark of a deep structural insight: when you change the *fundamental decomposition of work* to match the hardware's cooperative execution model, multiple surface-level problems resolve simultaneously.

The comparison to prior work is stark. FlashAttention-3's backward pass could not exploit any cooperative execution because Hopper had no equivalent of the 2-CTA MMA mode. Its only mechanism for reducing shared memory traffic was careful scheduling and tile size selection — optimizations that work within the constraint of per-CTA independence. The 2-CTA mode breaks that constraint entirely: it says that CTAs do not need to be independent, that they can share operands and coordinate reductions, and that this coordination can be exploited to reduce total memory traffic rather than just to increase parallelism.

The distinction from mere "using a new hardware feature" is critical. Many papers use new hardware features as drop-in replacements (e.g., replacing FP16 tensor cores with FP8 tensor cores, or replacing global memory with a larger cache). The 2-CTA mode is different because using it **requires changing the algorithm's decomposition** — the way `dQ` is computed, the way `dS` is partitioned, the way the software pipeline is ordered (hiding DSMEM latency by computing `dP` for the current tile before `dQ` for the previous tile). This is hardware-algorithm co-design at its most genuine: the hardware capability and the algorithmic structure are jointly optimized, not just the hardware capability dropped into an existing algorithm.

### Innovation 4: Conditional Softmax Rescaling as an Approximate Computation with Exact Correction

The conditional softmax rescaling optimization (Section 3.1.4) introduces a principle that has implications beyond attention: **intermediate precision can be relaxed if a final correction step restores exactness.** This is distinct from standard mixed-precision training (where computations are performed in reduced precision throughout) and from standard numerical tolerances (where errors are accepted). Instead, it is an *intentional* temporary approximation — skipping rescaling operations that would multiply the accumulated output by factors near 1.0 — with the guarantee that the final normalization step (dividing by the true normalizer ℓ_final, computed with the true maximum m_final) restores the mathematically exact result.

Prior FlashAttention implementations (1, 2, and 3) all applied the online softmax rescaling `e^{m_{j-1} - m_j} O_{j-1}` unconditionally whenever the running maximum changed. This was viewed as a **correctness requirement**: failing to rescale would accumulate outputs with different maxima, producing incorrect results. The paper's insight is that **small rescaling factors can be deferred and corrected later, as long as the accumulated slack is tracked and compensated at the end.** The threshold τ = log₂(256) = 8.0 — chosen so that skipped rescaling factors are at most e⁸ ≈ 2981 — ensures that the accumulated output remains within a factor of 2981 of its correctly-rescaled value, which is well within the dynamic range of BF16. The final division by ℓ_final (computed with the true maximum) corrects the accumulated slack exactly.

What makes this intellectually distinctive is that it is **not a numerical approximation — it is an exact algorithm with a skip condition.** The mathematical operation being performed (online softmax with rescaling) is preserved in its entirety; the optimization merely recognizes that certain steps of that operation are identity operations (or near-identity) and can be elided without changing the output. This is analogous to how sparse linear algebra skips multiplications by zero — it's not an approximation, it's exploiting algebraic structure to avoid redundant work.

The broader implication is that **many Transformer subcomputations contain latent skip conditions** — steps that are mathematically necessary in the general case but that, for typical data distributions and with appropriate thresholding, can be skipped without affecting the output. The paper identifies one such condition (rescaling when the maximum changes by a small amount) because it analyzes the *statistical behavior* of attention scores (the maximum rises quickly then stabilizes) rather than just the algebraic structure. Future work might identify similar skip conditions in normalization layers, activation functions, or positional encodings — anywhere that a computation is mathematically general but statistically sparse in practice.

The practical significance is validated by the performance gains (Figures 4 and 5), but the conceptual significance is that it introduces a new category of optimization: **data-dependent algebraic elision with exact correction.** This sits between traditional numerical approximation (where errors are accepted) and traditional compiler optimizations (where operations are eliminated based on static analysis). It requires runtime information (the value of `m_j - m_{j-1}`) and is justified by a combination of algebraic reasoning (the final normalization restores correctness) and statistical reasoning (the probability of large `m_j - m_{j-1}` decreases rapidly after the first few blocks). This hybrid reasoning — part algebra, part statistics — is characteristic of the paper's co-design philosophy and points toward a more general methodology for optimizing ML kernels.

### Innovation 5: CuTe-DSL as an Enabler of Co-Design — How Compile-Time Speed Unlocks Algorithmic Iteration

The decision to implement FlashAttention-4 entirely in CuTe-DSL embedded in Python (Section 4, Table 4) is not merely an engineering convenience — it is an **enabling technology for the co-design methodology itself.** The paper reports 20–30× faster compile times compared to FlashAttention-3's C++ template-based approach (2.5s vs. 55s for the forward pass, 1.4s vs. 45s for the backward pass). This matters because the co-design process described in Sections 3.1–3.2 requires **rapid iteration**: changing tile sizes, adjusting the fraction of exponential emulation, reordering the software pipeline, and reallocating TMEM regions — then measuring the impact on the roofline analysis and on actual throughput.

In a C++ template metaprogramming framework (as used in FlashAttention-2 and FlashAttention-3), each of these changes requires recompiling hundreds of kernel variants for different attention configurations (causal/non-causal, different head dimensions, different sequence length tiling strategies). Compile times of 45–55 seconds per variant mean that a developer making 10 experimental changes and testing them across 5 configurations would spend **over an hour just waiting for compilation** — a cycle time that makes systematic exploration of the design space prohibitive. The paper's CuTe-DSL approach reduces this to 2–3 minutes for the same experiment, making it feasible to actually perform the empirical tuning that the roofline analysis guides (e.g., the fraction of exponential emulation, which is "tuned empirically based on the ratio of MMA and exponential throughput").

This connects to a broader trend in systems research: **when compilation speed becomes a bottleneck for algorithmic exploration, the programming language and framework are not just implementation details — they are part of the research methodology.** The paper makes this connection explicit: "This rapid iteration cycle significantly improves developer productivity, enabling faster experimentation and debugging during kernel development" and "By lowering the barrier to entry, our approach enables researchers and engineers with just a few months of GPU programming experience to contribute meaningful extensions." The latter point is particularly important because the co-design methodology requires simultaneous expertise in attention algorithms and GPU hardware characteristics — a rare combination. By reducing the compile-time barrier, CuTe-DSL makes it possible for algorithm researchers to experimentally explore hardware-aware optimizations without deep C++ template expertise.

However, this innovation should be recognized as **enabling rather than primary.** The paper's core contributions are the algorithmic and pipeline innovations (Sections 3.1–3.2); CuTe-DSL is the tool that made those innovations practical to develop. The 20–30× compile speedup is impressive, but it is a means to an end — the end being the co-design methodology — rather than an end in itself. That said, the paper's vision of CuTe-DSL as "a comprehensive framework for building all kinds of attention variants with best-in-class performance" — with composable primitives for block-sparse patterns, masking strategies, variable sequence length handling, and work scheduling — suggests that the authors view the framework as a platform for future research, not just a one-time implementation convenience. This vision, if realized, could lower the barrier to entry for attention kernel development across the field, accelerating the co-design cycle for future hardware generations.

The claim is anchored by Table 4 (compilation times) and the reported adoption: "developers have successfully built FlexAttention and block-sparse attention variants on top of FlashAttention-4 without modifying the core framework." This external validation — that the framework enables research that the original authors did not anticipate — is stronger evidence of its value than the compilation speedup alone.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset / Task.** All benchmarks use the standard **attention operation** as defined in Section 2.1 — specifically multi-head attention with query, key, and value inputs at BF16 precision. There is no external dataset like MATH or HumanEval; the "task" is computing the attention forward pass `O = softmax(QK^T)V` and its backward pass (gradient computation) efficiently on GPU. Correctness is validated against a reference implementation (the paper implies bitwise or near-bitwise equivalence with existing FlashAttention implementations, though exact correctness validation methodology is not detailed in the benchmarking section).

- **Base model(s).** The benchmarks do not involve a specific trained model. Instead, they measure **kernel-level throughput** on synthetic tensors with realistic attention shapes. The key shape parameters are sequence length (1k to 32k), head dimension (64, 128, or GQA with (192, 128) as used in DeepSeek V3), number of heads (32 for head dim 64, 16 for head dim 128), and batch size (set so total tokens = 32k). The hidden dimension is fixed at 2048. These configurations are chosen to represent "typical attention workloads" across different model architectures (standard MHA, DeepSeek-style GQA).

- **Metrics.** The primary metric is **TFLOPs/s** (trillions of floating-point operations per second), computed as:

  **Forward pass FLOPs:** `4 × seqlen² × head_dimension × num_heads`
  **Backward pass FLOPs:** `Forward FLOPs × 2.5` (since there are 2 matmuls in forward and 5 in backward, due to recomputation — the factor 2.5 accounts for the 5/2 ratio)
  **With causal masking:** Forward FLOPs are divided by 2 (approximately half the attention matrix entries are computed).

  TFLOPs/s is calculated as `FLOPs / runtime`. A secondary, implicitly reported metric is **% of theoretical peak utilization** — the paper states FlashAttention-4 reaches 1613 TFLOPs/s, which is "71% of the theoretical maximum TFLOPs/s on B200 GPUs" (2.25 PFLOPS theoretical peak for FP16/BF16). Higher TFLOPs/s = faster kernel = better.

- **Baselines.** The paper compares against:
  - **cuDNN 9.13 and 9.19.1.2** — NVIDIA's vendor-optimized deep learning library. This is the strongest baseline, as cuDNN benefits from deep hardware knowledge and the authors note that starting from version 9.13/9.14, "we have worked with the cuDNN team to incorporate some techniques from FlashAttention-4 into cuDNN" (Appendix A.1), meaning the comparison is against an actively improved implementation.
  - **Triton 3.6** — an open-source GPU programming language and compiler "which uses B200-specific instructions" (Section 5, bullet on baselines). Triton represents the state-of-the-art for compiler-generated GPU kernels that are not hand-tuned for attention specifically.
  - **PyTorch / FlashAttention-2** — mentioned as baselines but not shown in the main figures; FlashAttention-2 is included as a reference point, though it was designed for Ampere/Hopper and is not Blackwell-optimized.
  - **FlashAttention-3** — explicitly noted as not running on B200 ("FlashAttention-3 does not run on B200," Section 5 footnote), so it is not a direct baseline. This is itself a significant point: the prior state-of-the-art *cannot be compared* because it is incompatible with the new hardware.
  - **Gluon** — described as "a lower-level GPU programming language with finer control than Triton" (Section 5). Mentioned in the text but not shown in the main figures.

- **Generation budget / compute accounting.** The unit of comparison is **FLOPs/s at a given sequence length and configuration**. This is a fair comparison because all kernels compute the exact same mathematical operation (attention forward or backward) with the same BF16 inputs and outputs. The total FLOPs are fixed by the problem dimensions, so reporting TFLOPs/s is equivalent to reporting inverse runtime — faster kernels achieve higher TFLOPs/s. No "generation budget" concept applies (this is a kernel benchmark, not a model evaluation), and there is no adaptive compute allocation across problems. The compute is measured as **wall-clock runtime** on identical hardware (B200 GPU), averaged over 10 runs after 5 warmup runs (Appendix A.1).

- **Cross-validation / statistical protocol.** The paper does not involve train/test splits or cross-validation (this is a systems benchmark, not a machine learning evaluation). The measurement protocol is: warmup with 5 runs, then repeat benchmarks 10 times, take the average timing (Appendix A.1). This controls for cold-start effects (first kernel launch is slower due to JIT compilation, cache warming) and reduces variance from system noise. The system is a B100 180GB SXM6 (1000W), using CUDA 13.1, FlashAttention 2.8.3, Triton 3.6, PyTorch 2.10.0, and CuTe-DSL 4.4.1 — all latest versions at time of writing (March 2025).

### Main Quantitative Results

The experimental results are organized around: forward pass throughput across sequence lengths and configurations, backward pass throughput, and deterministic backward pass overhead. I'll address each separately.

#### Forward Pass Throughput

**Headline numbers.** Figure 4 shows the forward pass TFLOPs/s on B200 with BF16, head dimension 128, for non-causal and causal attention across sequence lengths from 1k to 32k. FlashAttention-4 achieves:

- **1.1–1.3× speedup over cuDNN 9.13.0** across the evaluated sequence lengths. At the highest throughput point (non-causal, sequence length 32k), FlashAttention-4 achieves approximately 1613 TFLOPs/s (as stated in abstract and Section 5 paragraph 2) compared to cuDNN's ~1240–1470 TFLOPs/s (estimated from Figure 4, left panel, where FA4 is consistently above cuDNN 9.13.0 by a visible margin).
- **2.1–2.7× speedup over Triton** across sequence lengths. The largest gap appears at medium sequence lengths (4k–8k); the gap narrows slightly at very long sequences (32k) but remains >2×.
- **For causal attention** (Figure 4, right panel), the relative gains over cuDNN are similar (1.1–1.3×) but the absolute TFLOPs/s is higher for all methods because causal masking reduces the total FLOPs (only ~half the attention matrix entries are computed, but the kernel can skip the masked entries entirely rather than computing and then masking them). The gains over Triton are even larger for causal (up to 2.7×, per Section 5.1: "2.1-2.7× faster than Triton").

**Head dimension 64 and (192, 128).** Figure 5 shows the forward pass for head dimension (192, 128) — the configuration used in DeepSeek V3, with 192 query dimensions and 128 key/value dimensions (grouped-query attention). The comparison is only against cuDNN (not Triton, since the figure caption specifies "comparison between cuDNN and FA4"). FlashAttention-4 consistently outperforms cuDNN across sequence lengths 1k–32k for causal attention, with a similar 1.1–1.3× speedup at long sequences. The paper does not show separate figures for head dimension 64 but states in Section 5 (benchmark settings) that this configuration was tested.

**Peak utilization.** The abstract and Section 5 both state: "reaching up to 1613 TFLOPs/s (71% utilization)." This is calculated as 1613 / 2250 = 0.717, where 2250 TFLOPs/s (2.25 PFLOPS) is the theoretical peak BF16 tensor core throughput on B200. 71% utilization is high for a memory-intensive kernel — attention is not pure compute-bound like large matrix multiplications, so achieving >70% of theoretical peak indicates that the paper's optimizations successfully mitigated non-compute bottlenecks. The paper does not report utilization for other methods, but the 1.3× speedup over cuDNN implies cuDNN achieves approximately 1613 / 1.3 ≈ 1240 TFLOPs/s, or ~55% utilization, at the same configuration.

**Sequence length scaling.** All methods show increasing TFLOPs/s with sequence length (Figure 4), which is expected because longer sequences increase the ratio of compute (matmuls, which scale as `O(N²d)`) to memory traffic (loading Q, K, V, which scales as `O(Nd)`). At very short sequences (1k), the overhead of kernel launch and TMA setup dominates; at long sequences (16k–32k), the kernel becomes compute-bound and TFLOPs/s plateaus near the achievable peak. FlashAttention-4's advantage over Triton is largest at moderate sequence lengths (4k–8k), where the kernel is neither launch-overhead-bound nor perfectly compute-bound — this is the regime where software pipeline efficiency and bottleneck mitigation matter most.

**The cuDNN convergence.** Figure 4's caption contains an important caveat: "Since the initial release of our implementation, newer versions of cuDNN have incorporated many of the techniques described in this paper, yielding similar performance to FA4." This means the 1.3× speedup is relative to cuDNN 9.13.0, and the gap to the latest cuDNN (9.19.1.2, tested per Appendix A.1) may be smaller. The paper includes this disclosure transparently, which is commendable — but it also means that the headline speedup numbers may already be partially closed by the vendor's library incorporating the paper's techniques. This does not diminish the paper's contributions (the ideas are validated precisely because the vendor adopted them), but it means the performance advantage over the *current best* cuDNN may be smaller than 1.3×.

#### Backward Pass Throughput

**Headline numbers.** Figure 6 shows the backward pass TFLOPs/s on B200 with BF16, head dimension 128, for non-causal and causal attention. The paper states (Section 5.2): "FlashAttention-4 achieves consistent speedups across long sequence lengths and causal masking, demonstrating the effectiveness of our 2-CTA backward pass."

The exact speedup multiples are not stated in Section 5.2. From Figure 6 (left, non-causal), the 1-CTA backward pass achieves approximately 800–1000 TFLOPs/s across sequence lengths 1k–32k. The 2-CTA variant is visibly higher — estimated at 1000–1200 TFLOPs/s at 32k. The paper does not plot cuDNN or Triton on Figure 6, which is a notable omission: the backward pass comparison is FlashAttention-4 against itself (1-CTA vs. 2-CTA variants), not against external baselines. The speedups over cuDNN and Triton are stated qualitatively ("consistent speedups across long sequence lengths") but the magnitude is not quantified in the backward pass section.

**The 1-CTA to 2-CTA improvement.** Table 3's roofline analysis predicts that 2-CTA mode reduces total shared memory cycles from 3328 to 2688 (a ~19% reduction), with the shared-memory-bottleneck margin shrinking from ~30% to ~5%. The throughput improvement shown in Figure 6 (estimated ~20–25% at 32k) is broadly consistent with this prediction, though the paper does not provide exact percentages.

**Causal masking behavior.** In Figure 6 (right, causal), both 1-CTA and 2-CTA variants show higher TFLOPs/s than non-causal (similar to the forward pass — causal masking reduces total FLOPs, and the kernel skips masked entries). The relative gap between 1-CTA and 2-CTA appears similar to the non-causal case.

**Why external baselines are absent from the backward pass figure.** The paper does not explain this omission. Possible reasons: (1) cuDNN's backward pass may be competitive or even faster (the paper's motivation is forward pass speed), (2) Triton's backward pass may be poorly optimized for Blackwell, making the comparison less interesting, or (3) the backward pass's complexity (5 MMAs vs. 2 in forward) makes it harder to achieve meaningful speedups over well-optimized libraries. Regardless, the lack of cuDNN/Triton comparisons in the backward pass is a limitation — the reader cannot assess whether the 2-CTA backward pass outperforms existing solutions or is merely better than the 1-CTA variant.

#### Deterministic Backward Pass Overhead

**Headline numbers.** Figure 7 shows the deterministic backward pass performance as an ablation over scheduling strategies on B200 with BF16, head dimension 128, causal attention. The paper states (Section 5.2): "Our careful swizzling and scheduling results in a much faster deterministic backward pass, getting up to 75% the speed of the nondeterministic backward pass of the 1-CTA backward pass."

The figure plots four scheduling variants:

1. **SPT (shortest-processing-time-first)** — the full optimization: reverse mblock order, descending query block index for dQ reductions, batch/head swizzling. This achieves the highest throughput among deterministic variants.
2. **LPT with reverse mblock order** — processes longest tiles first but without the SPT ordering for dQ reductions.
3. **LPT only** — longest-processing-time-first tile scheduling without any swizzling.
4. **Naive** — no batch/head swizzle, no LPT ordering, no SPT.

The throughput ordering in Figure 7 (causal, left panel) shows: SPT ≈ LPT+reverse > LPT > naive, with SPT achieving approximately 75% of the nondeterministic 1-CTA variant (the paper doesn't plot the nondeterministic baseline on this figure, but states the 75% number in the text). At sequence length 32k, if the nondeterministic 1-CTA backward is ~1000 TFLOPs/s (from Figure 6), the SPT deterministic variant would achieve ~750 TFLOPs/s.

**Why SPT matters specifically for determinism.** The lock-based deterministic mode (Section 3.2.4) introduces stalls when a CTA must wait for the previous CTA in the reduction order. SPT ordering ensures that the CTA with the longest processing time (near the diagonal for causal masking) is assigned the first sequence number, so it starts its reduction earliest and is most likely to finish before later CTAs arrive. The naive ordering can cause severe stalls if a CTA assigned an early sequence number takes very long — all subsequent CTAs wait. The performance gap between SPT and naive in Figure 7 quantifies this stall cost: at long sequence lengths, naive deterministic mode may achieve only ~40–50% of nondeterministic throughput (estimated from the figure), while SPT recovers to ~75%.

**Non-causal deterministic backward.** Figure 8 (Appendix A.2) shows the non-causal deterministic backward pass, where the comparison is between "naive" and "batch/head swizzle" (since there is no causal masking, there is no SPT ordering to apply). The batch/head swizzle variant consistently outperforms naive, demonstrating that even without causal masking, careful CTA ordering reduces L2 cache thrashing and improves deterministic mode performance.

### Ablation Studies and Robustness Checks

The paper's "ablation studies" are not presented in a dedicated section but are distributed across the experimental figures and the Appendix. I'll extract the key comparisons that serve as ablations.

- **1-CTA vs. 2-CTA backward pass (Figure 6):** This is the primary architectural ablation. The 2-CTA variant consistently outperforms 1-CTA across all sequence lengths for both non-causal and causal attention, validating that shared memory traffic reduction through cooperative MMA execution translates to throughput gains. The gap is approximately 20–25% at long sequences. This is the empirical confirmation of the roofline analysis in Table 3 (predicting ~19% shared memory cycle reduction).

- **Deterministic scheduling strategies (Figure 7):** The ablation over SPT, LPT+reverse, LPT-only, and naive ordering demonstrates that both LPT tile scheduling and SPT reduction ordering contribute independently to deterministic mode performance. The gap between SPT and naive (roughly 2× at some sequence lengths) is surprisingly large — it means that a naive deterministic implementation can lose ~50% of throughput, making it practically unusable for training. The fact that careful scheduling recovers most of this loss (to 75% of nondeterministic) is the headline result here.

- **Batch/head swizzling for non-causal deterministic (Figure 8):** This ablates the L2 cache management aspect of the scheduler. Even without causal masking (where there's no SPT ordering), the batch/head swizzle outperforms naive scheduling, confirming that L2 cache locality matters independently of load balancing. The gap is smaller than the causal case (since there's no SPT to apply) but still meaningful.

- **Exponential emulation accuracy (Table 2):** This is an algorithmic ablation rather than a throughput ablation. The table compares degree-3, degree-4, and degree-5 polynomial approximations against hardware `MUFU.EX2`, at both FP32 and BF16 precision. The key finding: at BF16, all degrees ≥3 are indistinguishable from hardware because the BF16 quantization error (3.89 × 10⁻³ max relative error) dominates the polynomial approximation error (8.77 × 10⁻⁵ for degree-3). This validates the choice of degree-3 (the cheapest option) as sufficient — higher-degree polynomials would cost more FMA instructions and register pressure without improving BF16 accuracy.

- **Partial emulation fraction (Section 3.1.3, "Partial emulation" paragraph):** The paper states that "we apply emulation to only a subset of the entries in each softmax row (10–25%), with the remaining entries computed via hardware MUFU.EX2." The exact fraction is "tuned empirically based on the ratio of MMA and exponential throughput for a given tile configuration." The paper does not present an ablation over this fraction (no figure showing throughput vs. emulation percentage), which is a notable omission — the reader cannot see how sensitive performance is to this hyperparameter or what the optimal fraction looks like across different configurations. The choice of 10–25% is stated as a range without per-configuration specifics.

- **Conditional softmax rescaling threshold τ:** The paper sets `τ = log₂(256) = 8.0` (Section 3.1.4) but does not ablate this value. There is no experiment showing how performance or accuracy varies with different thresholds (e.g., τ = 4, τ = 16, τ = ∞). This is a gap — the choice of 256 as the rescaling factor is motivated by BF16 dynamic range, but the optimal value likely depends on sequence length (longer sequences = more blocks = more opportunities to skip rescaling, but also larger potential accumulated error before the final correction). The paper asserts numerical correctness without measuring it.

- **Tile size comparison (Table 1, implicitly):** The roofline analysis compares two tile configurations: `128³` (M=N=d=128) and `256 × 128²` (M=256, N=d=128). The cycle estimates in Table 1 motivate the use of larger tiles (M=256 amortizes overhead while keeping shared memory below MMA/exponential), but the paper does not present empirical throughput measurements for different tile sizes. The forward pass figures (4, 5) use whatever tile sizes the roofline analysis recommended, without showing alternatives.

- **cuDNN version comparison (Figures 4, 5 vs. Appendix A.1):** The paper benchmarks cuDNN 9.13.0 in the main figures and cuDNN 9.19.1.2 in the appendix. The difference between these versions represents a partial ablation of which FlashAttention-4 techniques matter most — since later cuDNN versions incorporate some of the paper's ideas, the closing gap between cuDNN 9.13 and cuDNN 9.19 quantifies how much of FlashAttention-4's advantage comes from general optimizations that any careful implementation would discover vs. specific architectural innovations. However, the paper does not present side-by-side cuDNN 9.13 vs. 9.19 numbers — it only notes that "newer versions... have incorporated many of the techniques described in this paper, yielding similar performance."

### Critical Assessment

Let me evaluate whether the empirical results actually support the paper's major claims, identifying what is demonstrated and what is not.

#### Claim 1: FlashAttention-4 achieves up to 1.3× speedup over cuDNN 9.13 and 2.7× over Triton.

**What is demonstrated:** The forward pass figures (4, 5) consistently show FlashAttention-4 above cuDNN 9.13 and Triton across all sequence lengths (1k–32k), both causal and non-causal, for head dimensions 128 and (192, 128). The 1.3× and 2.7× numbers are peak speedups at specific configurations. The forward pass claim is well-supported by the presented data.

**What is not demonstrated:** (1) The backward pass comparison to cuDNN and Triton is missing — only FlashAttention-4 variants are compared in Figure 6. The reader cannot verify whether FlashAttention-4's backward pass is actually faster than existing solutions or only faster than its own 1-CTA variant. This is a significant omission, especially since the backward pass contains the most architecturally novel contribution (2-CTA mode) and is more expensive than the forward pass (2.5× more FLOPs, per Section 5's FLOPs formula). (2) The speedup is relative to cuDNN 9.13.0, and the paper acknowledges that later versions have closed the gap — but the gap to cuDNN 9.19 is not quantified. The "1.3×" headline may already be obsolete for practitioners using the latest cuDNN. (3) The head dimension 64 results are mentioned but not plotted, so the reader cannot assess whether the speedups hold for smaller heads (common in many Transformer architectures).

#### Claim 2: FlashAttention-4 reaches 1613 TFLOPs/s, 71% of theoretical peak.

**What is demonstrated:** The abstract and Section 5 both state this number, and Figure 4 (left, non-causal, 32k sequence length) shows FlashAttention-4 at approximately this level. The calculation (1613/2250 = 71.7%) is straightforward and verifiable. 71% utilization is genuinely impressive for an attention kernel — pure matrix multiplications on Blackwell can achieve ~80–90%, and attention has significantly more memory traffic and non-MMA operations, so 71% indicates that the paper's bottleneck mitigation is effective.

**What is not demonstrated:** The paper does not show what utilization the baselines achieve, making it hard to contextualize the 71% number. If cuDNN 9.13 achieves 55% and Triton achieves 30%, then the 71% is impressive; if cuDNN achieves 68%, then the headline 1.3× speedup is a modest incremental gain. The utilization number also depends on the FLOPs counting formula — the paper counts only the matmul FLOPs (4 × seqlen² × head_dim × num_heads for forward), but attention also involves elementwise operations (softmax, rescaling, masking) that are not counted in this formula. This is standard practice in attention benchmarking, but it means that 71% utilization is actually a *lower bound* on true hardware utilization (since some of the "idle" 29% is doing unaccounted elementwise work).

#### Claim 3: The 2-CTA backward mode reduces shared memory traffic and global atomic adds.

**What is demonstrated:** Figure 6 shows consistent throughput improvement from 2-CTA over 1-CTA in the backward pass. The roofline analysis in Table 3 quantitatively predicts the shared memory traffic reduction (3328 → 2688 cycles). These together provide reasonable evidence that the 2-CTA optimization works as designed.

**What is not demonstrated:** There is no direct measurement of shared memory traffic or atomic add counts — the evidence is purely indirect (throughput improvement). A stronger demonstration would include profiler traces (e.g., NVIDIA Nsight metrics) showing reduced shared memory utilization, reduced DRAM atomics, or reduced stall cycles on shared memory. The roofline cycle estimates in Table 3 are theoretical; without profiling data, the reader cannot confirm that the actual bottleneck matches the analysis. Additionally, the improvement from 2-CTA includes both the shared memory traffic reduction (from partitioning operand B) AND the pipeline reordering that hides DSMEM latency. The paper does not ablate these two effects separately — the reader cannot tell whether the throughput gain comes primarily from reduced traffic or from better latency hiding.

#### Claim 4: The deterministic backward pass achieves up to 75% of nondeterministic throughput.

**What is demonstrated:** Figure 7 shows the SPT scheduling variant achieving the highest throughput among deterministic options, and the paper states the 75% number in Section 5.2. The qualitative improvement over naive scheduling (which appears to achieve only 40–50% of nondeterministic throughput) validates that the SPT approach is effective.

**What is not demonstrated:** (1) The nondeterministic baseline is not plotted on Figure 7, so the 75% number cannot be verified from the figure — the reader must trust the text. (2) The 75% number is for the SPT variant; the paper does not report the throughput for a "standard" deterministic implementation (without SPT), which would be the realistic baseline most practitioners would start from. (3) The deterministic mode's correctness (bitwise reproducibility) is asserted but not empirically validated — there is no experiment showing that two runs with different CTA scheduling produce identical dQ/dK/dV outputs. (4) The 25% overhead is substantial for training — if backward pass time increases by 25%, total training iteration time might increase by 10–15%, which is a meaningful cost for reproducibility. The paper does not discuss this tradeoff quantitatively.

#### Claim 5: The LPT scheduler improves performance for load-imbalanced workloads.

**What is demonstrated:** The text (Section 3.3) reports 4–8% FLOPs gain for MHA and 7–14% for MQA on an H200 GPU using LPT scheduling. These numbers are for FlashAttention-3 on Hopper, demonstrating that the technique is architecture-agnostic. Figure 7 and Figure 8 show that scheduling choices matter for Blackwell as well.

**What is not demonstrated:** The LPT gains on Blackwell specifically are not quantified. The H200 numbers are reported for FlashAttention-3, not FlashAttention-4, and the reader cannot assume the same percentages apply. Furthermore, the LPT gains reported are for the forward pass; LPT's impact on the backward pass is not quantified separately. The variable sequence length LPT (with preprocessing kernel to sort batches) is described in Section 3.3 but never benchmarked — there are no empirical results for the varlen LPT scheduler at all. This is a significant gap for a feature that the paper presents as a general contribution.

#### Overall Strengths of the Empirical Evaluation

1. **Realistic shapes and configurations:** The benchmarks cover a range of sequence lengths (1k–32k), head dimensions (64, 128, 192/128), and masking modes (causal, non-causal) that represent actual deployment scenarios. This is not a microbenchmark on tiny tensors.

2. **Strong baselines:** cuDNN is the best possible baseline for an NVIDIA GPU — it represents what the hardware vendor itself can achieve. Beating cuDNN by even 1.1× is a meaningful result. Triton represents the state-of-the-art for open-source compiler-generated kernels. The inclusion of both closed-source vendor and open-source compiler baselines is thorough.

3. **Transparency about cuDNN evolution:** The paper explicitly notes that later cuDNN versions have incorporated FlashAttention-4 techniques and closed the gap. This transparency strengthens credibility — the authors are not hiding that their advantage may be temporary.

4. **Roofline-to-empirical correspondence:** The roofline analysis (Tables 1, 3) makes quantitative predictions about bottlenecks, and the throughput results (Figures 4, 6) are qualitatively consistent with these predictions. The fact that 2-CTA mode improves backward pass throughput by ~20–25% while the roofline predicted ~19% shared memory cycle reduction is a reasonable match.

#### Overall Weaknesses of the Empirical Evaluation

1. **Missing backward pass baselines:** The lack of cuDNN and Triton comparisons in the backward pass is the single biggest weakness. The backward pass is where the 2-CTA innovation is deployed, and without external baselines, the reader cannot assess whether this innovation produces a kernel that is actually better than existing solutions or just better than the paper's own 1-CTA variant.

2. **Missing ablations:** Several design choices are stated without empirical justification: the exponential emulation fraction (10–25%), the conditional rescaling threshold (τ = 8.0), the tile size choice (M=256 vs. alternatives). Ablations over these parameters would transform the paper from "we made these choices and they work" to "here is how sensitive performance is to these choices and here is why our values are optimal." This is particularly important for a paper whose thesis is that kernel design should be driven by quantitative bottleneck analysis — the reader should see the quantitative justification, not just the final result.

3. **No profiling data:** The paper's entire motivation is that shared memory and exponential units are the bottlenecks on Blackwell. Yet there is no empirical evidence from hardware profilers (e.g., Nsight Compute metrics showing shared memory utilization, MUFU utilization, tensor core utilization, stall reasons) that confirm the bottlenecks are where the roofline analysis says they are. The throughput improvements are consistent with the analysis, but consistency is not confirmation — alternative explanations (e.g., better instruction scheduling, fewer register spills, better L1 cache behavior) could also explain the gains. Direct profiling data would substantially strengthen the paper's central narrative.

4. **Single GPU, no scaling behavior:** All benchmarks are on a single B200 GPU. There is no investigation of how the kernel performs at different batch sizes, no multi-GPU scaling, and no comparison to other Blackwell variants (e.g., GB200 with NVLink-C2C). The paper also does not benchmark on Hopper as a point of comparison, which would directly demonstrate the "asymmetric scaling" thesis — showing that FlashAttention-4's gains over FlashAttention-3 are largest where the hardware asymmetry is greatest.

5. **No end-to-end training benchmark:** All results are kernel-level microbenchmarks (TFLOPs/s on the attention operation alone). The paper does not show training throughput for a full Transformer model (e.g., tokens/second, step time), which is what practitioners actually care about. An attention kernel that is 1.3× faster but causes more register pressure or L2 cache contention in the surrounding MLP and normalization layers could produce lower end-to-end throughput. End-to-end benchmarks are challenging to set up and control, but they are the ultimate validation — and their absence means the paper provides only a component-level performance guarantee, not a system-level one.

6. **Deterministic mode correctness is asserted, not validated:** For a feature marketed as "enabling reproducible training for reinforcement learning applications" (Section 1), the paper should demonstrate that the deterministic mode produces bitwise-identical gradients across multiple runs with different CTA scheduling. Without this validation, a practitioner cannot trust that enabling the deterministic mode will actually solve their reproducibility issues.

#### Missing Experiments That Would Have Strengthened the Paper

- **Roofline validation via profiler:** Nsight Compute traces showing SMEM utilization, MUFU utilization, tensor core utilization, and stall reasons for both the 1-CTA and 2-CTA backward variants. This would directly confirm the bottleneck analysis.

- **Ablation over exponential emulation fraction:** A sweep of emulation percentage from 0% (MUFU only) to 100% (polynomial only) at a fixed configuration, showing the throughput peak at 10–25%. This would justify the empirical tuning claim.

- **Backward pass vs. cuDNN and Triton:** Even if the results show FlashAttention-4 only matching cuDNN (rather than beating it), this would still be informative — it would demonstrate that the 2-CTA innovation closes whatever gap exists in the forward pass.

- **End-to-end training throughput:** A simple Transformer (e.g., GPT-2 scale) with FlashAttention-4 vs. cuDNN attention, measuring tokens/second over 100 training steps. This would show whether the kernel-level gains translate to system-level gains.

- **Deterministic mode correctness test:** Run the backward pass twice with different CTA scheduling (e.g., different grid launch orders), confirm bitwise-identical dQ/dK/dV, and measure the throughput overhead as a function of sequence length and batch size.

- **Head dimension 64 results:** A separate figure or appendix showing forward/backward throughput for the smaller head dimension, which is common in many production models (e.g., LLaMA-70B uses head dim 128, but smaller models often use 64 or 96).

In summary, the empirical evaluation provides convincing evidence that FlashAttention-4 is faster than cuDNN 9.13 and Triton for the forward pass on B200 across realistic configurations, and that the 2-CTA backward mode and deterministic scheduling provide meaningful throughput improvements over naive alternatives. However, the evaluation is incomplete in several important respects: the backward pass lacks external baselines, key design hyperparameters are not ablated, the roofline-driven bottleneck analysis is not validated with profiling data, and there are no end-to-end training benchmarks. These gaps do not invalidate the paper's claims, but they do mean that the empirical case is strongest for the forward pass and weakest for the backward pass, deterministic mode, and the generalizability of the roofline methodology to future hardware.

## 6. Limitations and Trade-offs

### 1. Backward Pass Lacks External Baselines — The Most Architecturally Novel Component Is Not Benchmarked Against Existing Solutions

**The assumption or constraint.** The paper positions the 2-CTA backward pass (Section 3.2.3) as its most architecturally innovative contribution — it fundamentally restructures how `dQ` is computed, halves shared memory traffic and global atomic adds, and exploits a Blackwell-specific hardware feature (2-CTA MMA mode) in a way that changes the algorithm's dataflow rather than just tuning parameters. Yet Figure 6, the only backward pass throughput figure in the main paper, compares **only FlashAttention-4 variants against each other** (1-CTA vs. 2-CTA). There is no head-to-head comparison against cuDNN, Triton, or any external implementation. The paper states qualitatively in Section 5.2 that "FlashAttention-4 achieves consistent speedups across long sequence lengths and causal masking" but never quantifies the speedup over external baselines for the backward pass — unlike the forward pass, which reports explicit `1.1–1.3×` over cuDNN and `2.1–2.7×` over Triton (Figures 4, 5; Section 5.1).

**The consequence.** This matters enormously because the backward pass dominates training cost. The paper's own FLOPs accounting (Section 5, benchmark settings) assigns backward pass `2.5×` the FLOPs of the forward pass (5 matmuls vs. 2). In a typical training iteration, backward pass time is the primary driver of step time — especially with gradient accumulation, optimizer updates, and communication. Without knowing whether FlashAttention-4's backward pass is faster than cuDNN or merely faster than its own 1-CTA variant, a practitioner **cannot assess whether adopting FlashAttention-4 will actually improve end-to-end training throughput**, or whether the forward pass gains are partially offset by a backward pass that performs similarly to existing libraries. The paper's headline claim — "up to 1.3× speedup over cuDNN 9.13" — is a forward-pass-only claim, but it is presented alongside the backward pass innovations (2-CTA, deterministic mode) in a way that could mislead readers into assuming the speedup applies to both passes.

**What evidence exists in the paper.** Figure 6 shows the 2-CTA variant achieving higher TFLOPs/s than the 1-CTA variant across all sequence lengths (1k–32k) for both non-causal and causal attention, with an estimated 20–25% improvement at 32k. The roofline analysis in Table 3 predicts a ~19% reduction in shared memory cycles (3328 → 2688) from 1-CTA to 2-CTA, which is roughly consistent with the observed throughput gain. However, this only establishes that 2-CTA is better than 1-CTA — it does not establish that either variant is better than cuDNN or Triton. No cuDNN or Triton backward pass numbers appear anywhere in the paper, including the appendix. The paper does not explain this omission.

**Mitigation status.** Not addressed. The paper does not acknowledge the absence of backward pass external baselines as a limitation, nor does it suggest future work to benchmark against cuDNN/Triton backward implementations. This is a significant transparency gap, particularly because the forward pass results include an explicit note that later cuDNN versions "have incorporated many of the techniques described in this paper, yielding similar performance to FA4" (Figure 4 caption) — which actually makes the backward pass comparison *more* important, since it would reveal whether those incorporated techniques also improve cuDNN's backward pass to parity.

### 2. Difficulty Estimation and Adaptive Allocation Are Absent — The Method Offers a Uniformly Fast Kernel, Not a Compute-Optimal Inference Strategy

**The assumption or constraint.** Unlike the FlashAttention lineage's broader research thread around compute-optimal inference strategies (e.g., allocating test-time compute adaptively based on prompt difficulty), FlashAttention-4 makes **no attempt to adapt its behavior to problem characteristics**. It provides a single, uniformly fast kernel that processes every attention call identically — same tile size, same pipeline, same exponential emulation fraction, same 2-CTA mode — regardless of sequence length, sparsity pattern, head dimension, or the statistical properties of the attention matrix. The LPT scheduler (Section 3.3) adapts CTA ordering to load imbalance, but this is a scheduling optimization within a fixed kernel, not a strategy-level adaptation. The paper's roofline analysis (Tables 1, 3) is performed for fixed tile configurations and provides a static design point, not a dynamic policy.

**The consequence.** Real-world Transformer workloads exhibit enormous diversity: prefill (long context, parallel processing of all query tokens) vs. decode (single query token, sequential generation); dense attention vs. causal masking vs. block-sparse patterns; short sequences (1k) vs. extremely long sequences (128k+); and attention matrices whose softmax distributions range from nearly uniform (early training) to sharply peaked (well-trained models). A kernel optimized for one operating point (e.g., `M=256, N=128, d=128`, BF16, dense non-causal) may be suboptimal for another. The exponential emulation fraction (10–25%) is "tuned empirically based on the ratio of MMA and exponential throughput for a given tile configuration" (Section 3.1.3, "Partial emulation" paragraph), which implies that different configurations might benefit from different fractions — but the paper provides no mechanism to select or adapt this fraction at runtime based on workload characteristics. A practitioner training a model that transitions from short to long sequences (e.g., during a long-context fine-tuning phase) or that uses different attention masks for different heads cannot benefit from per-configuration tuning without recompiling the kernel.

**What evidence exists in the paper.** The benchmarks (Figures 4–8) sweep over sequence lengths (1k–32k), head dimensions (64, 128, (192, 128)), and causal masking modes, showing that FlashAttention-4 is faster across all tested configurations. This demonstrates robustness to configuration variation, but it does not demonstrate that the *same* kernel binary achieves these results — the paper may be using different compiled kernel variants for different configurations (which is standard practice for FlashAttention and consistent with the CuTe-DSL framework's support for JIT compilation). The LPT scheduler (Section 3.3) is the only adaptive mechanism, and its gains are reported as 4–8% for MHA and 7–14% for MQA on H200 — meaningful but modest, and applied only to CTA scheduling, not to algorithmic choices like tile size or emulation fraction.

**Mitigation status.** Not addressed as a limitation. The paper explicitly positions itself as an algorithm-kernel co-design for Blackwell hardware, not as a framework for adaptive inference. The future work section is absent from this paper (the manuscript ends at Section 6: Discussion and Conclusion, which is only ~2 paragraphs), so there is no discussion of adaptive strategies. This is not a failure of the paper per se — it achieves what it sets out to do — but it is a **fundamental scope limitation**: FlashAttention-4 is a point solution for a specific hardware generation and precision, not a general framework for attention optimization under varying workloads. Practitioners expecting the kind of compute-optimal adaptation studied in the FlashAttention-3 companion work (or in the compute-optimal test-time scaling literature) will find a fast kernel but no guidance on when to use which variant.

### 3. Difficulty Estimation Cost Is Replaced by Empirical Tuning Cost — The Co-Design Process Requires Substantial Per-Hardware Investment That Is Not Quantified

**The assumption or constraint.** The paper's central thesis is that attention kernels must be co-designed with specific hardware — the roofline analysis identifies bottlenecks unique to Blackwell, and the optimizations (exponential emulation, 2-CTA mode, pipeline restructuring) directly target those bottlenecks. However, the paper provides **no quantification of the development cost required to perform this co-design.** The roofline analysis (Sections 3.1.1, 3.2.1) is presented as a methodology, but the process of: (1) microbenchmarking hardware throughputs (shared memory bandwidth, exponential unit throughput, TMEM characteristics), (2) analyzing attention's cycle counts as a function of tile dimensions, (3) designing algorithmic modifications (polynomial approximation, conditional rescaling), (4) implementing the software pipeline in CuTe-DSL, (5) empirically tuning hyperparameters (emulation fraction, tile sizes, warpgroup assignments, TMEM allocation), is not characterized in terms of developer time, compute resources, or expertise required. The paper states that exponential emulation fraction is "tuned empirically" (Section 3.1.3) and that conditional rescaling threshold `τ` is "typically set to log₂(256) = 8.0` (Section 3.1.4), but does not report how many experiments were run to arrive at these values or whether they are robust to minor variations.

**The consequence.** This limitation matters because the paper argues for a **methodology**, not just a kernel. If adopting this methodology for a new hardware generation (B300, next-generation AMD/Intel accelerators, custom ASICs) requires months of expert GPU programming time plus extensive empirical tuning, the practical barrier to entry may be prohibitive for all but the largest industrial labs. The CuTe-DSL framework (Section 4) reduces compile-time overhead by 20–30× (Table 4), which helps, but compile time is only one component of the development cycle — design, debugging, correctness validation, and performance tuning dominate. The paper does not report: how many person-months were required to develop FlashAttention-4, how many kernel variants were tested and discarded, what fraction of the design space was explored vs. heuristically pruned, or whether the final design is near a local optimum or merely one good point in a large space. Without this context, a practitioner cannot estimate the cost of replicating or extending the work for their own hardware.

**What evidence exists in the paper.** The CuTe-DSL compilation speedup (Table 4) is the only productivity metric reported: 2.5s vs. 55s for forward pass compilation, 1.4s vs. 45s for backward. The paper mentions that developers have built FlexAttention and block-sparse attention variants on top of FlashAttention-4 without modifying the core framework (Section 4), which provides anecdotal evidence of the framework's flexibility. However, there is no quantification of the effort required to develop FlashAttention-4 itself: no timeline, no iteration count, no description of failed design attempts. The acknowledgments thank multiple teams at NVIDIA (cuDNN, TensorRT-LLM, CUTLASS) for "constant discussions, ideas, and feedback," suggesting that the development benefited from substantial vendor support that may not be available to typical practitioners.

**Mitigation status.** Partially addressed by the CuTe-DSL framework, which is explicitly designed to lower the barrier to entry: "this accessibility accelerates innovation and allows the attention mechanism research community to more rapidly explore new algorithmic variants" (Section 4). However, the framework addresses *implementation* cost, not *design* cost. The roofline analysis methodology is described in the paper but not packaged as a reusable tool — there is no script, profiler configuration, or automated analysis that a developer could apply to a new GPU. The paper suggests that some algorithms "can be extended to other accelerators as compute continues to outpace non-matmul units" (Section 6), but provides no concrete guidance on how to perform this extension. This is a missed opportunity: the paper could have released the roofline analysis as a tool alongside the kernel, making the co-design methodology directly actionable for other hardware targets.

### 4. Single Hardware Platform, No Cross-Generation Validation — The Asymmetric Scaling Thesis Is Asserted for Blackwell But Not Demonstrated Across Hardware Generations

**The assumption or constraint.** The paper's motivating narrative — that asymmetric hardware scaling (tensor cores doubling while other units stagnate) requires fundamental redesign of attention kernels — is **tested on exactly one hardware platform**: the NVIDIA B200 GPU (Blackwell architecture). Section 2.2 documents the throughput ratios on Blackwell and contrasts them with Hopper, but all empirical results (Figures 4–8) are on B200. The paper does not benchmark on Hopper (H100/H200) to show that FlashAttention-4's specific optimizations provide *larger* gains on Blackwell (where the asymmetry is most extreme) than they would on Hopper (where the asymmetry is less extreme). Nor does it benchmark FlashAttention-3 (optimized for Hopper's bottleneck profile) on Blackwell to quantify how much performance is left on the table by porting an older kernel — in fact, FlashAttention-3 "does not run on B200" (Section 5, footnote), so this comparison is impossible, but the paper could have measured cuDNN's performance on Hopper vs. Blackwell to establish the baseline shift.

**The consequence.** Without cross-generation validation, the paper's central thesis — that asymmetric scaling is the defining challenge and that the paper's specific optimizations are the right response — rests on theoretical analysis (the roofline in Sections 3.1.1, 3.2.1) plus empirical results on a single GPU. A skeptic could argue that FlashAttention-4's speedup over cuDNN 9.13 might simply reflect better engineering (more careful register allocation, better instruction scheduling) rather than specifically addressing asymmetric bottlenecks — and that those engineering improvements would have yielded similar gains on Hopper, where the asymmetry is less pronounced. The paper's own disclosure that later cuDNN versions "have incorporated many of the techniques described in this paper, yielding similar performance" (Figure 4 caption) further muddies the waters: if cuDNN can achieve parity by incorporating the techniques, then the techniques are not uniquely enabled by the roofline-driven co-design methodology — they are general optimizations that any competent implementation would discover.

Furthermore, the paper briefly notes (Section 2.2, shifting bottlenecks) that "B300 and GB300 GPUs have doubled the exponential throughput to 32 ops / clock / SM, though these GPUs are not yet widely available." This suggests that the specific bottleneck the paper addresses (MUFU exponential throughput) may be *transient* — the next hardware generation eliminates it. If exponential emulation is the temporary solution to a one-generation bottleneck, then the paper's broader claim about needing algorithm-kernel co-design for asymmetric hardware is weakened: it might be more accurate to say that attention kernels need to be redesigned for each GPU generation individually, not that there's a principled methodology that transfers.

**What evidence exists in the paper.** The roofline analysis (Tables 1, 3) quantitatively establishes that shared memory and exponentials exceed MMA compute by 25–60% on Blackwell for typical tile configurations. The LPT scheduler results (Section 3.3) include H200 measurements (4–8% gain for MHA, 7–14% for MQA), demonstrating that at least one technique generalizes. But these H200 results are for FlashAttention-3, not FlashAttention-4, and they measure scheduling improvements that are orthogonal to the paper's core bottleneck-mitigation contributions (exponential emulation, 2-CTA mode, pipeline restructuring).

**Mitigation status.** Partially acknowledged in Section 6: "Although optimized for Blackwell GPUs, some of these algorithms can be extended to other accelerators as compute continues to outpace non-matmul units." This is a forward-looking statement, not an empirical claim. The paper does not provide cross-generation benchmarks, does not report Hopper numbers for FlashAttention-4, and does not analyze which of its techniques would transfer to other architectures vs. which are Blackwell-specific. For a paper whose primary contribution is the methodology of bottleneck-driven co-design, the absence of even a single alternative hardware data point (e.g., H200 measurements showing which bottlenecks dominate there, and whether the same analysis methodology would have predicted FlashAttention-3's design choices) is a notable gap.

### 5. Deterministic Mode Overhead Is Substantial (25%) and Its Correctness Is Asserted Without Empirical Validation

**The assumption or constraint.** The deterministic backward pass (Section 3.2.4) uses a semaphore-based lock to serialize global atomic reductions, ensuring bitwise-identical gradients across runs. The paper claims this "enables reproducible training for reinforcement learning applications" (Section 1, item 4 in the contributions list) and reports that the SPT scheduling variant achieves "up to 75% the speed of the nondeterministic backward pass of the 1-CTA backward pass" (Section 5.2). This means deterministic mode incurs a **25% throughput penalty** relative to the nondeterministic 1-CTA variant (and likely a larger penalty relative to the nondeterministic 2-CTA variant, which is faster than 1-CTA — Figure 6). The paper presents this as a success ("much faster deterministic backward pass"), but a 25% overhead on the backward pass translates to a non-trivial increase in total training iteration time.

**The consequence.** Reinforcement learning (RL) training — the explicit use case mentioned in Section 1 — often already suffers from poor hardware utilization due to the sequential nature of policy rollouts and updates. Adding a 25% backward pass overhead would further reduce throughput, potentially making the deterministic mode impractical for large-scale RL training where wall-clock time is the primary constraint. The paper does not discuss this tradeoff: it does not report the end-to-end training throughput impact (which depends on the ratio of backward pass time to forward pass time, optimizer step time, and communication time), nor does it compare the deterministic mode's overhead to alternative approaches for achieving reproducibility (e.g., higher-precision accumulation that reduces the sensitivity to reduction order, or software-based deterministic reductions that don't require locks). The 75% number is a kernel-level metric; a practitioner needs a training-level metric to decide whether the reproducibility benefit justifies the throughput cost.

Furthermore, the **correctness of the deterministic mode is asserted but never validated.** Section 3.2.4 describes the lock-based mechanism and the SPT scheduling, and Figure 7 shows throughput for different scheduling variants — but there is no experiment demonstrating that the deterministic mode actually produces bitwise-identical gradients across multiple runs. For a feature marketed as "enabling reproducible training," this is a critical omission. Without validation, a practitioner cannot be confident that: (1) the lock-based serialization correctly captures all nondeterministic operations (there may be additional sources of nondeterminism beyond the targeted atomic adds for `dQ`), (2) the SPT scheduling doesn't introduce subtle bugs where some CTAs are inadvertently excluded from the reduction, or (3) the bitwise-identical guarantee holds across different GPU architectures or CUDA versions.

**What evidence exists in the paper.** Figure 7 shows throughput vs. sequence length for four scheduling strategies (SPT, LPT with reverse mblock order, LPT only, naive). The nondeterministic baseline is not plotted on this figure — the 75% number is stated in text but cannot be verified from the figure. Figure 8 (Appendix A.2) shows similar data for non-causal attention. There is no numerical accuracy or reproducibility experiment anywhere in the paper: no comparison of gradient norms between deterministic and nondeterministic modes, no test showing that two runs with the same inputs produce bitwise-identical outputs, and no measurement of the numerical difference (if any) between deterministic and nondeterministic accumulated gradients.

**Mitigation status.** Not addressed. The paper does not acknowledge the absence of correctness validation as a limitation, nor does it discuss the tradeoff between reproducibility and throughput in end-to-end training. The deterministic mode is presented as a completed feature, not as ongoing work, so the reader must either trust the lock-based implementation is correct or independently validate it. Given that deterministic floating-point reductions are notoriously difficult to get right (requiring careful handling of memory ordering, cache coherence, and compiler optimizations that might reorder operations), the lack of validation is a significant gap.

### 6. The Kernel Is Designed for a Single Precision (BF16) and Dense Attention — Generalization to Other Precisions and Sparsity Patterns Is Unverified

**The assumption or constraint.** All benchmarks, all roofline analyses, and all algorithmic descriptions in FlashAttention-4 assume **BF16 precision** for inputs and outputs, with some internal FP32 accumulation (e.g., for `dQ` in the backward pass, Section 3.2.3). The paper mentions FP8 only in the context of prior work (FlashAttention-3's FP8 support, Section 1; SageAttention's INT8/FP8 quantization) and explicitly distinguishes itself from quantization-based approaches: "These approaches primarily target consumer GPUs... FlashAttention-4 operates at BF16 precision (the standard for training) and achieves its speedups through algorithmic and pipeline restructuring, not through reduced precision." This framing — BF16 as "the standard for training" — ignores the rapid adoption of FP8 training (e.g., Transformer Engine, FP8 mixed-precision in frameworks like Megatron-LM and FSDP) in production training pipelines, where FP8 can provide an additional 2× throughput on Blackwell's FP8 tensor cores (which are separate from the BF16 tensor cores and have their own throughput characteristics).

Additionally, the paper's optimizations assume **dense attention** — every query attends to every key (modulo causal masking, which is handled by conditionally skipping computation). The paper mentions block-sparse attention only once, in Section 4: "developers have successfully built FlexAttention and block-sparse attention variants on top of FlashAttention-4 without modifying the core framework." This suggests that sparse attention is possible as an extension, but the paper provides no benchmarks for sparse patterns, no analysis of how the roofline shifts when only a subset of attention scores are computed, and no demonstration that the core optimizations (exponential emulation, 2-CTA mode, conditional rescaling) remain effective under sparsity.

**The consequence.** A practitioner training with FP8 mixed-precision or deploying sparse attention cannot directly benefit from FlashAttention-4's claims. The roofline analysis (Tables 1, 3) would change substantially for FP8: tensor core throughput is higher for FP8 (Blackwell supports both FP8 and BF16 tensor cores, with FP8 typically offering 2× throughput), shared memory bandwidth remains the same, and the exponential unit throughput is unchanged (exponentials are still computed in FP32/BF16). This would **exacerbate** the asymmetry — the bottleneck would shift even more aggressively toward non-MMA operations — making the paper's optimizations potentially more valuable, but their effectiveness at FP8 is untested. The exponential emulation (which operates on BF16 inputs) might need different polynomial coefficients or a different emulation fraction when the MMA operations are 2× faster. The conditional rescaling threshold `τ = log₂(256)` was chosen for BF16 dynamic range; its appropriateness for FP8 accumulation is unknown.

For sparse attention, the roofline analysis would need to account for the fact that only a fraction of the attention matrix is computed. The balance between MMA compute, shared memory traffic, and exponential operations would shift depending on the sparsity pattern and density, and the optimal tile size, pipeline ordering, and emulation fraction might be different. The paper's CuTe-DSL framework is designed for composability (Section 4), suggesting that sparse variants could reuse the core primitives, but without empirical validation, a practitioner cannot assume that the speedup over cuDNN/Triton carries over to sparse workloads.

**What evidence exists in the paper.** The only evidence for non-BF16 or non-dense workloads is the mention of (192, 128) head dimension benchmarks (Figure 5), which represent grouped-query attention (GQA) used in DeepSeek V3. This is a variant of multi-head attention, not a different precision or sparsity pattern. The paper does not benchmark FP8, INT8, block-sparse, sliding-window, or any other attention variant beyond standard MHA and GQA with BF16. Table 4 mentions "hundreds of kernels for different attention variants" in the context of FlashAttention-3's compilation overhead, implying that FlashAttention-4's CuTe-DSL implementation could support many variants — but no variants are demonstrated beyond the standard dense attention patterns in Figures 4–6.

**Mitigation status.** Partially addressed through the CuTe-DSL framework's design. Section 4 states: "Our vision is to provide a comprehensive framework for building all kinds of attention variants with best-in-class performance. Rather than implementing each attention variant from scratch, FlashAttention-4 factors common functionality into independent, composable primitives." The mention of external developers building FlexAttention and block-sparse variants is encouraging but anecdotal. The paper does not release benchmarks for these variants, nor does it provide guidance on how the roofline analysis and optimization strategy would change for different precisions or sparsity patterns. A practitioner interested in FP8 or sparse attention must either trust that the framework's composability extends to their use case or perform the co-design analysis themselves — which, as noted in Limitation 3, requires substantial expertise and effort.

## 7. Implications and Future Directions

### A Template for Asymmetric Hardware Optimization

This work establishes that **algorithm-hardware co-design must account for non-uniform scaling**. As accelerators continue to prioritize matrix multiplication throughput (the primary workload for deep learning), other functional units will increasingly become bottlenecks. The paper provides a systematic methodology:

1. **Roofline analysis per hardware unit**: Model throughput of tensor cores, shared memory, exponential units, and other specialized units independently
2. **Identify the bottleneck delta**: Quantify how much faster tensor cores are relative to other units
3. **Redesign algorithms to balance**: Use software emulation, mode selection, and scheduling to mitigate non-MMA constraints

This approach is directly applicable to future architectures—Blackwell B300/GB300 have already doubled exponential throughput to 32 ops/clock/SM (noted in Section 2.2), which would change the bottleneck profile and require re-optimization.

### Research Directions Enabled

**Extending emulation to other nonlinear functions.** The polynomial approximation technique for $2^x$ can generalize to other functions: GELU, SiLU, layer normalization, and other operations that rely on specialized hardware units. If these units also scale slower than tensor cores, emulation strategies become necessary. A systematic study of precision/throughput tradeoffs for common nonlinearities would be valuable.

**Compiler-assisted bottleneck mitigation.** The paper manually identifies and addresses bottlenecks. A compiler or auto-tuner could:
- Automatically detect hardware unit ratios from device properties
- Generate emulation code for bottleneck functions
- Tile sizes and scheduling strategies optimized for specific architectures

CuTe-DSL's JIT compilation infrastructure provides a foundation for such automation.

**Cross-architecture portability.** The paper notes some techniques (LPT scheduling, conditional rescaling) generalize across architectures. A systematic study of which optimizations are architecture-agnostic vs. Blackwell-specific would help kernel developers prioritize efforts. The scheduling gains measured on H200 (4-14% improvement) suggest broader applicability.

**Alternative attention mechanisms.** The framework specifically targets standard scaled dot-product attention. Alternative mechanisms—linear attention, multi-query attention (MQA), grouped-query attention (GQA), and sliding-window attention—have different compute/memory ratios. FlashAttention-4's support for DeepSeek V3's (192, 128) configuration (Figure 5) demonstrates extensibility, but a systematic analysis of how asymmetric scaling affects each variant would guide future architecture design.

### Practical Applications

**Production LLM inference and training.** FlashAttention-4 directly benefits deployments on B200/GB200 systems, which are becoming standard for large-scale AI. The 1.3× speedup over cuDNN translates to:
- **Training throughput**: Faster forward/backward passes reduce training time
- **Inference latency**: Long-context applications (document reasoning, code completion) benefit directly
- **Cost reduction**: Higher TFLOPs utilization means better hardware ROI

The deterministic mode specifically enables reproducible training for reinforcement learning from human feedback (RLHF) and other applications where gradient nondeterminism causes issues.

**Attention variant development.** The CuTe-DSL framework lowers the barrier to implementing new attention variants. The paper notes:

> "developers have successfully built FlexAttention and block-sparse attention variants on top of FlashAttention-4 without modifying the core framework."

This enables rapid prototyping of research ideas without deep C++ template expertise. For research teams, this could significantly accelerate iteration cycles.

**Hardware design feedback loop.** The detailed bottleneck analysis provides valuable feedback to GPU architects. The finding that exponential units are 512× slower than tensor cores—and that software emulation becomes necessary—suggests future architectures might benefit from:
- Higher-throughput specialized units for common nonlinearities
- Tensor cores with built-in softmax acceleration
- More balanced scaling across functional units

### Integration Guidance

**When to prefer FlashAttention-4:**
- **Blackwell-based systems**: The optimizations are architecture-specific; on Hopper or earlier GPUs, FlashAttention-3 remains appropriate
- **BF16 precision**: The exponential emulation accuracy analysis specifically targets BF16; FP32 or FP8 workloads require additional validation
- **Long-context workloads**: Gains are most significant for sequence lengths 4k and above (Figures 4, 6)
- **Causal masking**: LPT scheduling provides additional benefits; deterministic mode enables reproducible training with modest overhead

**Integration path:**
- FlashAttention-4 is open-sourced under a permissive license at the referenced GitHub repository
- The authors are working to integrate with popular libraries, lowering adoption barriers
- cuDNN has already incorporated techniques from this work (versions 9.13+), providing alternative access points

**Fallback considerations:**
- For workloads with unusual head dimensions (non-power-of-2, very small), the tile-size assumptions may not hold
- For FP32 precision, the emulation strategy requires higher-degree polynomials or may not be beneficial
- For architectures without TMEM or 2-CTA modes (consumer GPUs, older datacenter GPUs), the optimizations are not applicable

### The Productivity-Performance Tradeoff Resolution

Perhaps the most significant long-term implication is the demonstration that **developer productivity and peak performance are not mutually exclusive**. FlashAttention-4 achieves state-of-the-art performance while being written entirely in Python-embedded DSL with 20-30× faster compile times. This challenges the conventional wisdom that high-performance kernels require painful C++ template metaprogramming.

As the paper states:

> "By lowering the barrier to entry, our approach enables researchers and engineers with just a few months of GPU programming experience to contribute meaningful extensions without requiring deep expertise in C++ template metaprogramming."

This democratization could accelerate innovation in attention mechanism design, enabling a broader research community to contribute performance optimizations rather than relying on a small set of kernel experts.
