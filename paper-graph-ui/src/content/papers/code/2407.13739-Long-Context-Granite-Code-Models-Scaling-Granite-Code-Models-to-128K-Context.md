# Long Context Granite Code Models: Scaling Granite Code Models to 128K Context

**ArXiv:** [2407.13739](https://arxiv.org/abs/2407.13739)

## 🎯 Pitch

Open-source code models can reach 128K-token contexts without sacrificing their core coding ability. By simply continuing pretraining with repository-structured data and a tweaked RoPE frequency schedule, Granite-8B jumps from essentially zero long-context retrieval to 39.2% while losing only ~1% on HumanEval.

---

## 1. Executive Summary

This paper introduces **long-context Granite code models** that extend the effective context window of Granite 3B and 8B code models from 2K/4K to 128K tokens through a lightweight continual pretraining phase—gradually increasing RoPE base frequency with repository-level file packing and per-language length upsampling—followed by instruction tuning on a mix of short and long-context data. The approach yields dramatic improvements on long-context retrieval and completion benchmarks (e.g., +58.0% average retrieval accuracy on RepoQA for the 8B base model at threshold 0.8, lifting it from near-zero to 39.2%) while incurring only a ~1% average degradation on short-context HumanEvalPack synthesis tasks, establishing that context length can be scaled by two orders of magnitude without meaningful compromise to standard code generation capability when the extension is performed on repository-structured data with progressive frequency adjustment.

## 2. Context and Motivation

### The Core Problem: Open-Source Code LLMs Are Stuck at Short Contexts

The fundamental gap this paper addresses is straightforward: **open-source code language models, at the time of this work, could not effectively handle long input contexts**, while proprietary models and real-world software development increasingly demand this capability. The Granite code models—initially released with 2K (3B) and 4K (8B) token context windows—were representative of a broader pattern in the open-source ecosystem. CodeGemma (CodeGemma Team et al., 2024) and Code Llama (Rozière et al., 2023), despite being significant open-source releases, similarly operated within relatively short context limits.

This matters for two distinct reasons:

**1. Repository-level coding tasks require long contexts.** Modern software development happens in repositories, not isolated files. A code completion tool that only sees the current file misses crucial information: function signatures from imported modules, class definitions in sibling files, configuration constants, and documentation scattered throughout the project. Liu et al. (2024; 2023b) established benchmarks specifically designed to test this repository-level understanding, creating a concrete measurement framework that prior short-context models fundamentally could not engage with.

**2. Software development agents need large context windows.** The emergence of AI-powered software development agents—systems that autonomously navigate, edit, and reason about entire codebases—creates demand for models that can hold significant portions of a project in their context simultaneously. As the paper notes, platforms like OpenDevin (OpenDevin Team, 2024) represent this frontier, and their practical utility depends directly on the underlying model's context capacity.

The practical consequence of short context windows is severe: open-source code models were effectively locked out of these emerging application areas, limiting their utility in real-world software engineering workflows and creating a gap between what proprietary systems could offer and what the open-source community could deploy.

### Why Proprietary Models Aren't a Sufficient Answer

The paper implicitly positions itself within a broader ecosystem concern: while GPT-4, Gemini, and Claude all support very long context windows, their proprietary nature imposes constraints that are unacceptable for many use cases. Organizations may need to fine-tune models on proprietary codebases, deploy them in air-gapped environments, audit their behavior, or distribute them as part of products—all of which require open-weight models under permissive licenses. The Granite models are released under Apache 2.0, and the context extension technique is described in sufficient detail to be replicable, making this a contribution to the *practitioner-accessible* frontier of long-context code modeling, not just a demonstration of what's possible.

### Prior Approaches and Where They Fall Short

The paper engages with several strands of prior work, each with identifiable limitations:

**Short-context open code models are the status quo but are inherently limited.** CodeGemma (CodeGemma Team et al., 2024), Code Llama (Rozière et al., 2023), and the original Granite code models (Mishra et al., 2024) all operate in the 2K–16K context range. These models perform well on single-file code completion tasks (HumanEval, MBPP) but degrade sharply or fail entirely when asked to reason about cross-file dependencies or retrieve information from long contexts. The Tables 1–3 in the paper make this degradation starkly visible: the original Granite 8B base model at 4K context length achieves 10.0% average retrieval accuracy on RepoQA (with any non-zero similarity threshold), effectively failing the task, while the 128K version reaches 68.0% under the same conditions. This is not a matter of incremental improvement—it's the difference between usable and unusable.

**RoPE frequency scaling is a known technique but hasn't been combined with repository-aware data engineering for code models.** Xiong et al. (2023) introduced the idea of adjusting Rotary Position Embedding (RoPE) base frequency to extend context length beyond what was seen during original pretraining. Their key insight was that the ability to attend to arbitrary positions is largely acquired during pretraining, and extending context length primarily requires *recalibrating* the position encoding to handle longer distances, not *relearning* attention from scratch. This paper adopts that hypothesis explicitly:

> "Similar to prior works (Fu et al., 2024), we hold the basic hypothesis that the ability to utilize information at arbitrary input locations, is a capability that is mostly already acquired through large-scale pretraining, and that this capability can be readily extended to contexts substantially longer than seen during original pretraining (e.g., 4K to 128K) through lightweight training on appropriate data mixture."

However, prior work applying this technique had not focused specifically on code, and had not addressed the question of *what constitutes an appropriate data mixture* when the target domain involves structured repositories with file-level dependencies. This paper's contribution is in the data engineering, not the RoPE frequency adjustment itself.

**Data engineering for long-context scaling exists but hasn't addressed repository structure.** Fu et al. (2024) and Yu (2023) established that per-language length upsampling—artificially oversampling longer document sequences on a per-language basis—improves long-context training quality by preventing the model from seeing mostly short sequences. The key insight is that long documents naturally come from particular sources or languages, creating a confounding factor: if you don't upsample, the model disproportionately learns from short-document languages. This paper adopts that technique but adds a critical layer: **repository-level file packing with semantic dependency ordering**. Prior approaches concatenated documents arbitrarily or by simple heuristics; the paper's contribution is constructing long training sequences that reflect the actual structure of software repositories, making the context extension *useful* for code rather than just *possible*.

**Long-context instruction tuning data is scarce.** A persistent challenge in adapting models to long contexts is the lack of instruction-tuning data that requires reasoning over long inputs. The paper faces this problem directly: there is no large, permissively licensed dataset of "here's a 64K-token codebase, now answer questions about it" examples. Their solution—bootstrapping from the pretraining corpus by having the original short-context Granite-8B-Code-Instruct model generate responses to synthetic instructions about repository-level file-packed documents—is pragmatic but introduces a dependency on the quality of the short-context model's outputs. This is not a weakness of the approach so much as a reflection of the real constraint the field faces: generating high-quality long-context instruction data is expensive and typically requires already having a long-context model (creating a chicken-and-egg problem).

**Sequence parallelism and Ring Attention enable practical training but aren't contributions of this work.** The paper uses established systems techniques: sequence parallelism (Li et al., 2021) for distributing long sequences across GPUs, Flash Attention 2 for memory-efficient attention up to 64K tokens, and Ring Attention (Liu et al., 2023a) to push beyond that to 128K tokens by distributing the attention computation across devices in a ring topology. These are engineering enablers, not research contributions, but they constrain what's possible: without them, training on 128K-token sequences would be prohibitively expensive or outright infeasible on available hardware.

### How This Paper Positions Itself

The paper positions itself not as proposing fundamentally new methods for context extension (the RoPE frequency adjustment, length upsampling, and progressive training recipe are all drawn from or heavily inspired by prior work), but as demonstrating that **a carefully engineered combination of existing techniques, applied to repository-structured code data, can extend context length by two orders of magnitude with minimal degradation on the original task**.

The emphasis is on practicality and replicability. The total continued pretraining cost is described as "only 0.1% of original pretraining data" (roughly 4B additional tokens), making this a lightweight procedure that other teams could apply to their own code models without requiring the computational resources of a full retraining. The permissively licensed data and Apache 2.0 model release reinforce this positioning: this is intended as infrastructure for the open-source code intelligence ecosystem, not a proprietary capability demonstration.

The paper also positions itself as addressing a specific *gap* in the long-context scaling literature. While Fu et al. (2024) established that long-context scaling is possible for general-purpose LLMs, and Xiong et al. (2023) provided the RoPE frequency adjustment mechanism, neither addressed the domain-specific challenge of making long contexts *useful* for code understanding—which requires that the long sequences reflect the dependency structures of real software repositories, not just arbitrary concatenations. The repository-level file packing algorithm (Section 2.1), with its topological sort of import-graph dependencies and language-stratified organization, is where this paper differentiates itself from a generic application of existing scaling recipes to code data.

Finally, the paper presents its results as establishing a baseline for the field. The Tables 1–4 and Figures 1–3 are dense with comparative numbers, showing not just that the long-context models outperform the short-context originals (which is expected—the short-context models can't even read the input), but quantifying *how much* improvement is achieved and *at what cost* to short-context performance. The ~1% average degradation on HumanEvalPack (Table 5) becomes the key number that makes the case for adoption: practitioners can extend context length without meaningfully sacrificing the capability they already rely on.

## 3. Technical Approach

### 3.1 Reader Orientation

This is primarily a **systems and data engineering paper** describing how to take existing Granite code models (already pretrained on 2K/4K context windows) and extend their effective context length to 128K tokens through a lightweight, two-stage pipeline of continual pretraining followed by instruction tuning. The core idea is that the capability to attend to information at arbitrary positions is largely acquired during original pretraining, and context extension can be achieved by: (1) recalibrating the position encoding to handle longer distances through gradual RoPE base frequency increases, and (2) retraining the model on data organized to reflect real repository structures—file packing with semantic dependency ordering and per-language length upsampling—so the model learns to *use* the extended context for code-relevant tasks. The problem this solves is practical and acute: open-source code models were stuck at short context windows, making them unusable for repository-level tasks, and this paper provides a replicable recipe (4B additional tokens, ~0.1% of original pretraining) to close that gap without sacrificing short-context capability.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has four major components connected in a sequential pipeline:

1. **Base Granite Code Model (3B or 8B parameters)** — a fully pretrained Transformer with Rotary Position Embeddings (RoPE) and 2K or 4K native context length, serving as the starting point. It already possesses code understanding and generation capabilities from large-scale pretraining on code data.

2. **Continual Pretraining Stage** — takes the base model and produces a long-context base model through three intertwined mechanisms: (a) progressive RoPE base frequency adjustment to recalibrate the position encoding for distances up to 128K, (b) repository-level file packing that constructs training sequences reflecting real codebase dependency structures, and (c) per-language length upsampling to ensure the model sees enough long sequences during training. This stage processes ~4B additional tokens and uses sequence parallelism and Ring Attention to handle the computational demands of 128K-token sequences.

3. **Instruction Tuning Stage** — takes the long-context base model and produces a long-context instruct model by finetuning on a mixture of (a) existing short-context instruction datasets (CommitPackFT, MathInstruct, Glaive, etc.) and (b) synthetically generated long-context instruction data created by bootstrapping from the pretraining corpus, where the original short-context Granite-8B-Code-Instruct model generates responses to templated queries about repository-level file-packed documents. Multi-turn loss masking prevents the model from being penalized on user-assistant conversation turns.

4. **Deployment Artifacts** — four models released under Apache 2.0: Granite-3B-Code-Base-128K, Granite-8B-Code-Base-128K, Granite-3B-Code-Instruct-128K, and Granite-8B-Code-Instruct-128K, all supporting effective context windows up to 128K tokens with full attention (no sparse or linear approximations).

Information flows as follows: pretrained base model (2K/4K) → progressive RoPE adjustment + training on repository-packed long sequences → long-context base model (128K) → instruction tuning on mixed short+long data → long-context instruct model (128K). The key design philosophy is that each stage builds incrementally on the previous one, with the continual pretraining stage being surprisingly lightweight (only 500 steps per context-doubling iteration, batch size 32, total 4B tokens).

### 3.3 Roadmap for the Deep Dive

- **First**, the RoPE base frequency adjustment mechanism—how it works, why progressive doubling is used, and the specific theta values chosen at each context window size—since this is the mathematical foundation that makes all the data engineering effective.

- **Second**, repository-level file packing—how files are ordered, what the semantic dependency graph is, why topological sort matters, and how non-connected files are handled—since this is the paper's primary data engineering innovation that distinguishes it from generic long-context scaling recipes.

- **Third**, per-language length upsampling—the downsampling rate, the rationale, and the resulting corpus statistics—since this connects data distribution to training dynamics and explains why the model doesn't just see short sequences despite having long-context capacity.

- **Fourth**, the progressive training protocol—the context-window doubling schedule, the search for optimal RoPE theta and learning rate at each stage, the systems infrastructure (sequence parallelism, Flash Attention 2, Ring Attention), and the total compute budget—since this defines the practical recipe that other teams would need to replicate.

- **Fifth**, the instruction tuning data construction—both the existing short-context datasets and the synthetic long-context generation pipeline (parsing, querying, templating)—since this addresses the chicken-and-egg problem of needing long-context data to train long-context instruct models without already having a long-context model.

- **Sixth**, the training configuration for instruction tuning—batch size, learning rate, noise multiplier, padding-free transformers, and multi-turn loss masking—since these choices affect stability and final performance.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems and data engineering paper** whose core idea is that long-context capability can be added to already-trained code models through lightweight retraining on repository-structured data with recalibrated position encodings, without requiring sparse attention or architectural changes.

#### Rotary Position Embedding (RoPE) and Base Frequency Adjustment

**What RoPE is and why it matters.** Rotary Position Embeddings encode positional information by rotating the query and key vectors in the attention mechanism by an angle proportional to their absolute position in the sequence. For a token at position `$p$` with embedding dimension `$d$` (where dimensions are paired), the rotation applied to dimension pair `$2i, 2i+1$` is:

$$\theta_i = b^{-2i/d}$$

where `$b$` is the base frequency (typically 10,000 in the original RoPE formulation) and `$d$` is the total embedding dimension. At position `$p$`, the rotation angle for dimension pair `$i$` is `$p \cdot \theta_i$`. This means that the relative rotation between positions `$p$` and `$q$` is `$(p - q) \cdot \theta_i$`, which depends only on their distance, not their absolute positions—this is what makes RoPE "relative" despite being applied to absolute position encodings.

**What happens when context length exceeds training length.** When a model trained on sequences of length `$L_{\text{train}}$` (e.g., 2K or 4K tokens) is asked to process sequences of length `$L_{\text{test}} \gg L_{\text{train}}$` (e.g., 128K tokens), the attention mechanism encounters position pairs `$|p - q|$` that are much larger than anything seen during training. With the original base frequency `$b$`, the rotation angles for these large distances would be outside the range the model has learned to interpret. The key insight from Xiong et al. (2023), adopted by this paper, is that **increasing the base frequency `$b$`** reduces the rotation per unit distance, effectively "squeezing" the representable positional range so that the same set of learned frequency patterns covers a longer absolute span.

**Specific RoPE theta values.** The paper progressively doubles the context window from the original 2K/4K up to 128K, searching for the optimal base frequency at each stage. The found values are:

- For 8K context: RoPE theta = 100,000
- For 16K context: RoPE theta = 250,000
- For 32K context: RoPE theta = 500,000
- For 64K context: RoPE theta = 2,000,000
- For 128K context: RoPE theta = 10,000,000

Note that these are the base frequency values `$b$`, not the per-dimension `$\theta_i$` values. The base frequency governs the fundamental wavelength of the position encoding; increasing it from 10,000 (typical default) to 10,000,000 means that positions that were previously separated by one full rotation cycle now require 1,000× the distance to complete the same cycle, effectively stretching the model's positional "ruler" by three orders of magnitude.

**Why progressive doubling rather than jumping directly to 128K.** The paper trains for 500 steps at each intermediate context window size (8K → 16K → 32K → 64K → 128K) rather than immediately training with RoPE theta = 10M on 128K sequences. This progressive approach serves two purposes: (1) it allows the model to gradually adapt its attention patterns to longer distances, reducing the risk of catastrophic forgetting or training instability that could occur from an abrupt 30× jump in effective context length, and (2) it enables hyperparameter search at each stage—the optimal RoPE theta and learning rate are not known in advance and depend on the model's current state, so finding them incrementally is more reliable than guessing for the final configuration.

**Why 500 steps per stage.** The paper states this explicitly as the training duration per context-doubling iteration, with a batch size of 32. This is extremely lightweight: 500 steps × 32 sequences per step = 16,000 sequences per stage, across 5 stages, for roughly 80,000 total training sequences. The total token count is described as "only 0.1% of original pretraining data," confirming that the vast majority of the model's knowledge comes from the original pretraining and that the context extension phase is merely recalibrating positional representations, not teaching the model new code semantics.

#### Repository-Level File Packing

**The problem with naive concatenation.** Standard long-context pretraining datasets often concatenate documents arbitrarily to fill sequence length—for example, taking the next document in the corpus and appending it until the target length is reached. For code, this is suboptimal because two randomly adjacent files from different repositories share no semantic relationship; the attention patterns learned from such sequences would not help the model understand cross-file dependencies, which is the entire point of having long context for code. The model would learn to treat the long context as a sequence of unrelated documents, not as a coherent codebase.

**The semantic dependency graph.** The paper's file packing algorithm begins by analyzing imports within a repository to build a directed acyclic graph (DAG). Each file is a node. A directed edge from file A to file B is created if file A imports or uses APIs defined in file B—that is, A *depends on* B. If file A imports a function from file B, then understanding file A's implementation requires knowing what's in file B. The DAG structure reflects this: edges point from *dependent* to *dependency*.

The paper explicitly mentions breaking cycles in this graph before proceeding. Cycles would occur when two files mutually import from each other (e.g., through circular imports, which some languages permit or which can arise from indirect dependencies). Breaking cycles is necessary to obtain a valid topological ordering, which requires a DAG.

**Topological sorting for file ordering.** Once the graph is a DAG, the algorithm performs a topological sort—an ordering of nodes such that for every directed edge `$u \to v$`, node `$u$` appears before node `$v$` in the ordering. This means that **dependencies appear before the files that depend on them**. When these files are concatenated into a training sequence, the model sees dependency code *before* it sees the code that uses those dependencies. This mimics how a developer would read a codebase (or how an IDE resolves imports)—fundamentally, it creates a training signal where attention from later positions to earlier positions corresponds to genuine code understanding relationships, not arbitrary document boundaries.

**Complete file ordering protocol.** The paper describes a three-part ordering:

1. **Documentation and build files first.** These provide project-wide context (READMEs, configuration, build scripts) that establish the repository's purpose and structure before any implementation code is seen.

2. **Semantically-ordered files next.** The set of files that have import relationships, arranged according to the topological sort of the import DAG. This means the model sees utility code and library code before the application code that uses it, creating a coherent narrative of increasing abstraction.

3. **Non-connected files last.** Files that have no import relationships with other files in the repository (standalone scripts, test fixtures, data files). These are arranged according to their folder structure using a depth-first traversal, which preserves at least some spatial locality (files in the same subdirectory are near each other in the sequence).

**Language stratification.** After ordering files within each repository, the algorithm determines the dominant programming language of the repository based on file extensions and the presence of build files. Repositories are then organized by their dominant language. This ensures that training batches contain code from the same language, preventing the model from needing to context-switch between Python, Java, C++, etc., within a single sequence. It also enables per-language length upsampling (discussed next) by making the language identity of each sequence explicit.

**Why this matters.** The repository-level file packing transforms the long-context training data from "a bunch of code concatenated together" into "a coherent representation of a software project's structure." When the model attends across the full 128K context during training, the attention patterns it learns are genuinely useful for code understanding—looking back at earlier positions retrieves dependency definitions, documentation, and build configurations, just as it would need to do at inference time for repository-level tasks. This is the paper's primary data engineering insight: **long-context training for code is not just about having long sequences; it's about those sequences containing semantically meaningful structure that rewards cross-position attention.**

#### Per-Language Length Upsampling

**The confounding factor problem.** In any natural corpus, long documents and short documents come from different sources. Some languages or repositories tend to produce longer files; others produce shorter ones. If you train directly on the corpus without adjusting, the model sees a distribution heavily skewed toward the lengths and languages that happen to produce short files, potentially learning to expect certain languages only in short contexts. Fu et al. (2024) and Yu (2023) identified this as a key issue in long-context training: the quantity of long sequences available for training depends on the source, not just on the desired capability.

**The downsampling strategy.** The paper downsamples documents shorter than 4096 tokens to a rate of 10%—meaning only 10% of documents under this threshold are retained in the training corpus, while the other 90% are discarded. This is done on a per-language basis: within each programming language, short documents are aggressively filtered while long documents are kept at their natural frequency. The paper states that this 10% rate was found to "ensure a sufficient number of total tokens and documents," suggesting that more aggressive downsampling (e.g., keeping 0% of short documents) would have left too few total training tokens to be effective, while less aggressive downsampling would not have sufficiently shifted the distribution toward long sequences.

**Resulting corpus statistics.** After processing, the training corpus contains 173,336 documents with a mean length of 73,451 tokens. Compare this to the original pretraining data (which trained the 2K/4K models): in that corpus, the vast majority of sequences would have been under the original context window length, with an average length likely under 1K-2K tokens. The length upsampling transforms the effective distribution: the model now sees primarily long sequences (mean ~73K tokens), which is what it needs to learn to use the extended context window effectively.

**Why per-language rather than global.** If upsampling were done globally (downsampling all short documents regardless of language), languages that predominantly produce short documents would be severely underrepresented in the final corpus, potentially causing the model to forget or degrade on those languages. Per-language upsampling ensures that each programming language maintains representation in the training data, even if most of its files are short—the short files that survive the 10% filter are enough to maintain language-specific knowledge while still shifting the overall distribution toward longer sequences.

#### Progressive Training Protocol

**Overall schedule.** The continual pretraining proceeds through five stages, each doubling the context window from the previous stage:

- Stage 1: 2K/4K → 8K tokens (RoPE theta = 100K)
- Stage 2: 8K → 16K tokens (RoPE theta = 250K)
- Stage 3: 16K → 32K tokens (RoPE theta = 500K)
- Stage 4: 32K → 64K tokens (RoPE theta = 2M)
- Stage 5: 64K → 128K tokens (RoPE theta = 10M)

At each stage, the paper trains for 500 steps with a batch size of 32. The total compute cost is therefore: 5 stages × 500 steps × 32 sequences per step = 80,000 sequences processed. At the mean document length of 73,451 tokens, this is approximately 5.9 billion tokens, though the paper quotes the total as "an extra 4B tokens" (the discrepancy may come from variable sequence lengths across stages—earlier stages use shorter sequences because the context window hasn't been fully extended yet).

**Hyperparameter search per stage.** The paper explicitly states it "searches for the optimal RoPE theta and learning rate for each iteration." This implies that the listed theta values (100K, 250K, etc.) are the result of this search, not predetermined. The search likely involves training with several candidate theta values at each stage, evaluating on a validation metric (likely long-context perplexity or retrieval accuracy), and selecting the best performer. The paper does not provide the search range or the exact validation metric used.

**Why RoPE theta increases superlinearly.** The sequence of theta values—100K, 250K, 500K, 2M, 10M—is not a simple doubling. The jump from 500K to 2M is 4×, and from 2M to 10M is 5×. This superlinear scaling likely reflects the fact that as context length grows, the range of positional distances that need to be representable grows, and the RoPE base frequency needs to increase more aggressively to "compress" the representable range into the model's existing learned frequency bands. The paper does not provide theoretical justification for these specific values; they are empirically determined.

**Systems infrastructure.** The training uses several established techniques to handle the computational demands:

- **Sequence parallelism** (Li et al., 2021): Distributes the long sequences across multiple GPUs along the sequence dimension, so each GPU processes only a portion of the sequence length. This is necessary because a single GPU cannot hold an entire 128K-token sequence in memory during training, especially with the 8B parameter model.

- **Flash Attention 2**: A memory-efficient attention implementation that computes attention in blocks rather than materializing the full attention matrix. Used up to 64K context length. Flash Attention avoids the `$O(n^2)$` memory cost of standard attention by tiling the computation, making it feasible to train on sequences where the attention matrix would otherwise require hundreds of gigabytes of memory.

- **Ring Attention** (Liu et al., 2023a): Used to reach 128K tokens. Ring Attention distributes the attention computation across devices arranged in a logical ring, where each device computes attention for its portion of the sequence and passes intermediate results to its neighbor. This scales beyond what Flash Attention 2 alone can handle by parallelizing the attention computation across devices, not just optimizing the per-device computation.

**Data parallelism.** The paper mentions training with "data parallelism" alongside the sequence parallelism and attention optimizations, indicating a hybrid parallelism strategy where different data batches are processed on different sets of GPUs while each batch's long sequences are split across GPUs within its set.

**No sparse or linear attention.** The paper explicitly states the approach does not use "any sparse or linear attention." This is notable because many long-context approaches resort to approximations—sliding window attention, sparse attention patterns, or linear attention mechanisms—that reduce the quadratic complexity of full attention at the cost of restricting which token pairs can attend to each other. By using full attention with Ring Attention for the computational heavy lifting, the Granite models preserve the ability of every token to attend to every other token across the full 128K context, which is particularly important for code understanding where a function call at position 120,000 might need to attend to its definition at position 500.

#### Instruction Tuning Data Construction

**Short-context instruction data.** The instruction tuning phase uses a combination of permissively licensed datasets that were also used in training the original short-context Granite code instruct models (Mishra et al., 2024):

- **CommitPackFT** (Muennighoff et al., 2023): Instruction data derived from git commits, teaching the model to generate code changes in response to commit messages.
- **MathInstruct2** (Yue et al., 2023): Math reasoning instruction data, with GSM8K-RFT and Camel-Math removed due to unknown or non-commercial licenses.
- **MetaMathQA** (Yu et al., 2023): Bootstrap-generated math question-answer pairs.
- **Glaive-Code-Assistant-v3**: A code assistant instruction dataset.
- **Self-OSS-Instruct-SC2**: Self-instruct data filtered for executability.
- **Glaive-Function-Calling-v2**: Function calling instruction data.
- **NL2SQL**: Natural language to SQL instruction data.
- **HelpSteer** (Wang et al., 2023b): Multi-attribute helpfulness dataset.
- **OpenPlatypus** (Lee et al., 2023): Curated open-source instruction dataset.
- **Synthetic datasets**: For API calling (Basu et al., 2024) and multi-turn code interactions with execution feedback.

This mixture covers a broad range of code-related tasks: code generation, editing, explanation, math reasoning, function calling, SQL generation, and interactive coding. The inclusion of this extensive short-context data is deliberate—the paper aims to preserve (or improve) short-context performance while adding long-context capability.

**Long-context instruction data generation pipeline.** Since permissively licensed long-context instruction data is scarce, the paper bootstraps it from the pretraining corpus using a multi-step process:

1. **Start with repository-level file-packed documents** from the pretraining data—the same semantically-ordered, language-stratified sequences used in the continual pretraining stage. These documents are long (up to 128K tokens) and reflect real repository structures.

2. **Parse the document into structural units.** The pipeline extracts classes, methods, and stand-alone functions from each file in the document. This parsing step identifies the boundaries of each code unit, making it possible to query specific implementations.

3. **Generate templated instructions.** For a random subset of the extracted functions and methods (up to 5 per file), the pipeline generates several types of instructions:
   - **Retrieval**: "Find the implementation of function X" — the model must locate and return the correct code from the long context.
   - **Explanation**: "Explain the implementation of function X using available documentation" — the model must synthesize understanding from both code and documentation in the context.
   - **Implementation from context**: Given all the *other* code and documentation in the repository (with the target function excluded), generate the implementation of the target function. This tests the model's ability to infer implementation details from surrounding context—what arguments it should take, what return type it should have, what helper functions it should call.

4. **Generate responses.** The responses come from two sources:
   - **Semantic extraction**: For retrieval tasks, the correct implementation is simply extracted from the parsed document.
   - **Model generation**: For explanation and implementation tasks, the original Granite-8B-Code-Instruct-4K model generates the response. The paper acknowledges this dependency: they are using a *short-context* instruct model to generate *long-context* instruction data, which is possible because the prompts given to the model are templates that reference specific extracted code units, keeping the immediate input short even though the overall document is long.

5. **Multi-turn construction.** The instructions for different functions within the same document are chained into multi-turn conversations. The model sees a sequence of user queries about different parts of the repository, each followed by an assistant response. This multi-turn structure teaches the model to maintain context across multiple interactions about the same codebase, which is representative of how a developer would interact with a code assistant during a real coding session.

6. **Repeat for different functions until desired length.** The process continues generating instruction-response pairs for different functions until the sequence reaches a target length, ensuring that the final training examples exercise the model's ability to handle long contexts with multiple distinct queries.

**Why this bootstrapping approach.** The alternative—using an existing long-context model to generate training data—would have been circular for the paper's goals (they're trying to create a long-context model, which is exactly what they'd need to generate high-quality long-context training data). By using a short-context model with templated prompts that extract specific code units, they break this circularity: the short-context model only needs to reason about the extracted code unit and the immediate template, not the full 128K-token context, so its lack of long-context capability doesn't prevent it from generating useful responses. The long-context *capability* in the training data comes from the structure of the document and the multi-turn chaining, not from the model that generated the responses.

**Multi-turn loss masking.** During instruction tuning, the loss is computed using a multi-turn loss mask. This means the model is only trained to predict tokens in the assistant's responses, not in the user's queries. The paper follows the approach of Wang et al. (2023a) where each sample consists of multiple instruction-response pairs within a single sequence:

- For each user turn (instruction), the loss mask is 0 — the model sees these tokens in its context but is not trained to predict them.
- For each assistant turn (response), the loss mask is 1 — the model is trained to predict these tokens autoregressively.
- An EOS token is appended after each response to prevent runaway generation during inference, where the model might otherwise continue generating endlessly after completing a response.

This masking is particularly important in the multi-turn setting because the user's queries contain information (the task description, the extracted code context) that the model should learn to condition on but not reproduce verbatim as output.

---

#### Instruction Tuning Training Configuration

The training parameters for instruction tuning are:

- **Global batch size**: 128
- **Learning rate**: `$2 \times 10^{-5}$`
- **Noise multiplier for input embeddings**: 5 (this adds Gaussian noise to the input embeddings during training, which can improve robustness and generalization by preventing the model from overfitting to exact input patterns)
- **Padding-free transformers**: Sequences are packed without padding tokens, using the same efficient batching approach as the original short-context instruct models (Mishra et al., 2024). Padding-free training means sequences of different lengths are concatenated and an attention mask prevents cross-sequence attention, maximizing GPU utilization by eliminating wasted computation on padding tokens.

These parameters are identical to those used for the original short-context instruct models, as the paper states it "followed the same training parameters that produced our previous short-context instruct models." This consistency suggests that the instruction tuning process itself doesn't need to be modified for long contexts—the long-context base model already has the positional capability, and the instruction tuning phase is about teaching task-specific behaviors using the same hyperparameters that worked for the short-context version.

## 4. Key Insights and Innovations

### Innovation 1: Long-Context Code Understanding Requires Semantically Structured Training Data, Not Just Long Sequences

The paper's deepest conceptual contribution is the recognition that **context extension for code is fundamentally a data engineering problem, not a modeling problem**. Prior work on long-context scaling—Xiong et al. (2023) with RoPE frequency adjustment, Fu et al. (2024) with length upsampling—treated the challenge primarily as one of positional encoding recalibration: teach the model to attend across longer distances and it will figure out what to attend to. This paper demonstrates that for code specifically, *what* the model attends to matters as much as *how far* it can attend, and that arbitrary concatenation of code files produces sequences where cross-position attention has no systematic relationship to genuine code understanding.

The diagnostic move is subtle but profound: the paper doesn't just ask "can we make the model read 128K tokens?" (the answer would be yes with any reasonable data mixture if RoPE is adjusted correctly) but "can we make the model *use* 128K tokens for code-relevant reasoning?" The repository-level file packing algorithm—building an import DAG, topological sorting, placing documentation first, then dependencies, then dependent code—isn't just a preprocessing heuristic. It's a specific hypothesis about what makes long contexts *useful* for code: that attention from later positions to earlier positions should correspond to genuine dependency relationships (function calls, class inheritance, import resolution), not arbitrary document boundaries. When the model learns to attend backward in the sequence during training, it's learning to resolve imports—exactly the skill tested by RepoQA and LCC at inference time.

This distinguishes the work from generic long-context scaling recipes. Fu et al. (2024) showed that per-language length upsampling helps general-purpose LLMs, but their data remained documents concatenated by simple heuristics. This paper adds the critical layer: **the internal structure of the long sequence must reflect the task structure the model will face.** The dramatic RepoQA results—lifting retrieval accuracy from near-zero to 68.0% average for Granite 8B base (Table 3)—are evidence not just that the model can attend across 128K tokens, but that the attention patterns it learned during training on repository-structured data transfer to retrieval tasks. A model trained on 128K tokens of randomly concatenated code files might achieve similar perplexity on long sequences but would likely perform far worse on RepoQA because it never learned that "attending to earlier positions retrieves dependency definitions."

This is a fundamental reframing, not an incremental improvement. It implies that the long-context scaling community's focus on positional encoding mechanisms and attention efficiency (sparse attention, linear attention, ring attention) may be missing the more important variable: **the semantic coherence of the long sequences used during training.** For code, at least, data engineering dominates architecture in determining whether the extended context is useful.

---

### Innovation 2: Context Extension Can Be Decoupled from Capability Acquisition, Enabling Lightweight Retraining

The paper provides strong empirical evidence for a hypothesis that was previously theoretical: **the ability to utilize information at arbitrary input locations is largely acquired during initial pretraining, and extending context length requires only recalibration of positional representations, not relearning of attention mechanisms or code semantics.** This hypothesis was articulated by Xiong et al. (2023) and Fu et al. (2024), but the paper's results give it quantitative force in a domain where the distinction between "can attend" and "can understand" is sharp.

The evidence comes from the training budget: 4B additional tokens, described as "only 0.1% of original pretraining data." For the Granite 8B model, which was originally trained on roughly 4 trillion tokens (based on typical scaling for models of this size), the context extension phase adds a rounding error of compute. Yet the resulting model goes from effectively zero long-context retrieval capability (10.0% average at threshold > 0 on RepoQA, Table 3) to strong performance (68.0% average).

If the model were genuinely *learning new code understanding capabilities* during the context extension phase—learning that imports from earlier in the sequence correspond to definitions, learning to track variable scopes across file boundaries, learning to reason about cross-file control flow—then 4B tokens would be woefully insufficient. The fact that it *is* sufficient confirms that the model already possessed these capabilities from its original pretraining and only needed its positional encoding recalibrated to apply them across longer distances.

This decoupling has practical significance beyond this paper: it means that for any code model trained with RoPE, context extension can be treated as a lightweight post-processing step rather than a retraining effort. Organizations with existing fine-tuned code models don't need to retrain from scratch to add long-context support; they can apply this recipe (progressive RoPE adjustment + repository-structured data + length upsampling) at a fraction of the original training cost. The paper's Apache 2.0 release of both the models and the recipe makes this directly actionable.

The finding also creates a clear boundary between what context extension can and cannot do. It can recalibrate the model's positional "ruler" to measure longer distances. It cannot teach the model new code reasoning skills that it didn't acquire during pretraining. This explains why the hardest questions on long-context benchmarks still challenge these models—if the base model couldn't reliably resolve cross-file dependencies even at 4K context, extending to 128K won't help because the underlying capability was never learned. The context extension amplifies existing capability; it doesn't create new capability from scratch.

---

### Innovation 3: Synthetic Long-Context Instruction Data Can Be Bootstrapped from Short-Context Models, Breaking the Circular Dependency

The paper's instruction tuning data generation pipeline solves a chicken-and-egg problem that is often a blocker for long-context instruct models: **you need long-context instruction data to train a long-context instruct model, but generating high-quality long-context instruction data typically requires already having a long-context model.** The paper's solution—using a *short-context* instruct model (Granite-8B-Code-Instruct-4K) to generate responses to templated queries about repository-level documents—is conceptually elegant and practically significant.

The key insight is that the long-context *capability* in the training data comes from the structure of the document and the multi-turn chaining, not from the model that generated the individual responses. The short-context model only needs to reason about a specific extracted function or class (a short prompt) and generate a coherent response; the fact that this function is embedded in a 128K-token document is invisible to the response-generation step. But when these responses are assembled into multi-turn conversations about the same repository, the resulting training sequence *is* a long-context interaction—the instruct model must track which functions have been discussed, maintain coherence across turns, and condition its responses on the full context.

This is not the same as having a genuine long-context model generate the data (which might produce more sophisticated cross-references or multi-hop reasoning chains), but it's sufficient to teach the model the basic skills of long-context instruction following: finding relevant information in a long context, responding to queries about different parts of the same codebase, and maintaining conversation coherence. The RepoQA results for instruct models (Table 4)—82.4% average retrieval accuracy for Granite 8B Instruct at threshold 0.0, compared to 7.0% for the short-context instruct baseline—confirm that this bootstrapping approach works.

This is a methodological contribution that generalizes beyond code. The same technique could be applied to long-document QA, legal document analysis, or scientific literature review: use short-context models to generate responses to templated queries about sections of long documents, then assemble the responses into multi-turn long-context training sequences. The quality ceiling is lower than what a native long-context model could produce, but as the paper shows, it's sufficient to bootstrap models that then significantly outperform their short-context originals on long-context tasks.

---

### Innovation 4: Long-Context Extension Can Be Achieved with Minimal Regression on Short-Context Tasks When Instruction Tuning Blends Both Context Lengths

The paper establishes an important empirical finding about the relationship between context extension and capability preservation: **if instruction tuning includes a substantial proportion of short-context data alongside the new long-context data, short-context performance can be maintained or even improved, contradicting the assumption that context extension necessarily involves a tradeoff.**

The evidence is in Table 5 and Figure 3. For base models, long-context extension causes a small but measurable degradation: Granite 8B Base drops from 43.1% to 40.2% on HumanEvalPack synthesis (a ~2.9 percentage point decline), and the overall average across synthesis, fix, and explain tasks drops from 32.5% to 31.2% (~1.3 percentage points). This is consistent with the hypothesis that the continued pretraining phase, while lightweight, slightly shifts the model's distribution away from short-context code generation.

But for instruct models, the pattern reverses: Granite 8B Instruct *improves* from 49.6% to 51.4% on synthesis, and the overall average shows near-parity (43.6% vs. 42.9%). The paper attributes this to "our mixing of short-context SFT data with long-context multi-turn synthetic data." The implication is that the instruction tuning phase, which includes extensive short-context data (CommitPackFT, MathInstruct, Glaive, etc.), not only prevents the degradation observed in base models but can actively recover or surpass the original short-context performance.

This finding has practical significance for model release strategy. It suggests that teams should not release long-context *base* models as the primary artifact (these will show small regressions on standard benchmarks) but should instead release long-context *instruct* models where the instruction tuning phase has re-established short-context capability. The Granite release follows this strategy, and the paper's framing of the ~1% degradation as "a minimal cost" that is "more than offset by the potential of handling long sequences" is most strongly supported for the instruct variants.

The finding also complicates the narrative that context extension is "free" from a capability perspective. The base model degradation is real, if small, and it likely reflects a genuine distribution shift: training on sequences with mean length 73,451 tokens, even for only 0.1% of the original pretraining budget, changes the model's expectations about input length and may slightly erode its ability to reason about very short, single-function code snippets. The instruction tuning phase compensates for this, but only because the training data mixture was deliberately designed to do so—the result is not an automatic property of context extension but a deliberate design choice.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper evaluates on five benchmarks spanning both short-context and long-context code tasks. For long-context evaluation, the primary benchmarks are **Long Code Completion (LCC)** (Guo et al., 2023), **RepoBench-P** (Liu et al., 2023c), **RepoQA** (Liu et al., 2024), and a synthetic **Key Retrieval** benchmark built on Code Contest data (Li et al., 2022). For short-context evaluation, the paper uses **HumanEvalPack** (Muennighoff et al., 2023), which extends the original HumanEval Python problems to five additional languages (JavaScript, Java, Go, C++, Rust) and three task types (synthesis, fix, explain). The specific test splits are: LCC and RepoBench-P are rebalanced from their original distributions (details below); RepoQA uses 10 repositories × 5 languages × 10 needle functions = 500 sub-tasks at 16K context length; Key Retrieval uses synthetic sequences of 512-token steps with key offsets of 512 tokens; HumanEvalPack uses the standard zero-shot evaluation protocol from Muennighoff et al. (2023).

- **Base model(s).** All experiments start from the original Granite Code 3B and 8B models (Mishra et al., 2024), which were pretrained on 2K and 4K context windows respectively using full Rotary Position Embeddings. These serve as the short-context baselines throughout. The long-context variants are produced through the two-stage pipeline described in Section 3 (continual pretraining + instruction tuning), yielding four models: Granite-3B-Code-Base-128K, Granite-8B-Code-Base-128K, Granite-3B-Code-Instruct-128K, and Granite-8B-Code-Instruct-128K. The 3B/8B scale was chosen because these are the sizes available in the Granite family and represent a practical range for open-source deployment—small enough to run on consumer hardware, large enough to demonstrate meaningful code understanding capability.

- **Metrics.** The paper uses several metrics depending on the benchmark:
  - **Exact Match (EM)** for LCC and RepoBench-P: the model's predicted next line must exactly match the ground-truth line of code. This is a strict metric that penalizes semantically equivalent but syntactically different completions.
  - **Retrieval accuracy with similarity thresholds** for RepoQA: the model is given a natural language description of a function and must retrieve the matching function from the context. Accuracy is reported at similarity thresholds from 0.0 to 1.0, where the threshold represents the minimum required similarity between the model's output and the ground-truth function. A threshold of 0.0 counts any non-empty output as correct if it contains a function; a threshold of 1.0 requires exact match. Reporting at multiple thresholds provides a finer-grained view of retrieval quality—the model might find the right function but reproduce it imprecisely.
  - **Pass@1 with greedy decoding** for HumanEvalPack: the fraction of problems for which the model's first generated solution (using greedy sampling, temperature = 0) passes all test cases. This is the standard metric for code synthesis benchmarks.
  - **Key retrieval accuracy** for the synthetic Needle-in-a-Haystack test: whether the model correctly executes the buried Python function and returns the expected output.

- **Baselines.** The primary baselines are the **original short-context Granite models** themselves: Granite-3B-Code-Base-2K, Granite-8B-Code-Base-4K, Granite-3B-Code-Instruct-2K, and Granite-8B-Code-Instruct-4K. These represent the state of the models *before* any context extension, evaluated at the same tasks. The paper does not compare against other long-context code models (e.g., Code Llama with extended context, DeepSeek Coder) in its main tables, making this primarily a within-family comparison that demonstrates the effectiveness of the context extension recipe rather than establishing state-of-the-art on any benchmark.

- **Generation budget / compute accounting.** All evaluations use **greedy decoding** (temperature = 0) to ensure deterministic outputs and eliminate variance from sampling. For long-context benchmarks (LCC, RepoBench-P, RepoQA), the model receives the full context up to the specified length (4K, 8K, 16K, or 32K tokens depending on the evaluation bucket) and generates a single completion. For HumanEvalPack, the model receives the standard short prompt (typically under 1K tokens) and generates a single completion. The paper does not use best-of-N sampling, majority voting, or any test-time compute scaling—all results are pass@1 with greedy decoding. For Key Retrieval, the model processes sequences up to the evaluated length and generates a single output. Compute is not formally measured in FLOPs or GPU-hours for evaluation; the paper focuses on accuracy metrics at fixed context lengths.

- **Cross-validation / statistical protocol.** The paper does not report cross-validation or statistical significance testing. Results are single-run evaluations on fixed test sets. The LCC and RepoBench-P benchmarks are **rebalanced** from their original distributions: the original LCC benchmark is heavily weighted toward contexts around 2K tokens, so following Bai et al. (2024) and Rozière et al. (2023), the paper creates balanced buckets (<4K, 2–4K, 4–8K, 8K+) with 100 samples per bucket when possible. Similarly, RepoBench-P is rebalanced based on the StarCoder tokenizer used for training the Granite models. This rebalancing ensures that reported improvements at long context lengths are not simply an artifact of having more test examples at those lengths—without rebalancing, a model could achieve high overall EM by performing well on the abundant 2K examples while failing at 32K. The paper does not describe a validation set or held-out fold used for hyperparameter selection during the context extension pipeline. The RoPE theta values were found through "search" at each stage, but the search methodology and validation metric are not specified.

### Main Quantitative Results

#### Long Code Completion (LCC)

**Headline result (Table 1):** The long-context Granite base models dramatically outperform their short-context counterparts across all context lengths from 4K to 32K, with the gap *widening* at longer contexts rather than narrowing. For Granite 3B Base, the 128K variant achieves 57.8% EM at 32K context compared to 10.0% for the 2K baseline—an absolute gap of +47.8 percentage points. For Granite 8B Base, the 128K variant achieves 57.4% EM at 32K compared to 15.0% for the 4K baseline (+42.4 percentage points).

**Detailed breakdown:** Reading across the context lengths for Granite 3B:
- At 4K: 24.5% (2K baseline) → 54.6% (128K variant), gap = +30.1
- At 8K: 15.4% → 56.8%, gap = +41.4
- At 16K: 11.4% → 52.2%, gap = +40.8
- At 32K: 10.0% → 57.8%, gap = +47.8

For Granite 8B:
- At 4K: 41.9% (4K baseline) → 56.5% (128K variant), gap = +14.6
- At 8K: 23.7% → 60.1%, gap = +36.4
- At 16K: 19.1% → 51.8%, gap = +32.7
- At 32K: 15.0% → 57.4%, gap = +42.4

**Key pattern:** The short-context baselines degrade monotonically as context length increases—this is expected because these models were not trained on sequences longer than 2K/4K tokens, so their positional encodings become effectively random at longer distances, and attention patterns break down. The 4K performance of the 8B baseline (41.9%) is substantially higher than the 3B baseline (24.5%), reflecting the larger model's stronger code generation capability at its native context length. The long-context variants not only avoid this degradation but maintain roughly stable performance across context lengths (52–60% EM for both models across all lengths), demonstrating that the context extension produces models that genuinely use the additional context rather than ignoring it. The 3B long-context model at 32K (57.8%) actually outperforms the 8B short-context model at 4K (41.9%), suggesting that for this task, long-context capability in a smaller model can compensate for raw parameter count.

#### RepoBench-P

**Headline result (Table 2):** The pattern on RepoBench-P mirrors LCC but with consistently lower absolute scores, reflecting the greater difficulty of cross-file code completion. For Granite 3B Base at 32K: 14.0% (2K baseline) → 45.3% (128K variant), gap = +31.3. For Granite 8B Base at 32K: 7.8% (4K baseline) → 44.5% (128K variant), gap = +36.7.

**Detailed breakdown for Granite 3B:**
- At 4K: 22.0% → 39.8%, gap = +17.8
- At 8K: 17.9% → 46.8%, gap = +28.9
- At 16K: 15.4% → 43.1%, gap = +27.7
- At 32K: 14.0% → 45.3%, gap = +31.3

For Granite 8B:
- At 4K: 27.9% → 42.7%, gap = +14.8
- At 8K: 23.0% → 44.0%, gap = +21.0
- At 16K: 15.7% → 44.8%, gap = +29.1
- At 32K: 7.8% → 44.5%, gap = +36.7

**Key pattern:** The 8B short-context baseline degrades more severely than the 3B baseline as context length grows (dropping from 27.9% at 4K to 7.8% at 32K, a 20.1-point decline vs. the 3B's decline from 22.0% to 14.0%, an 8-point decline). This may reflect the 8B model's stronger tendency to rely on precise positional information that breaks down outside its 4K training window. Both long-context variants stabilize in the 40–47% range across all context lengths, showing the same pattern of length-independent performance as on LCC. The gap between the 3B and 8B long-context models narrows substantially compared to the short-context baselines—at 32K, they achieve 45.3% and 44.5% respectively, effectively tied—suggesting that the context extension recipe provides a floor of cross-file completion capability that is relatively insensitive to model size within this range.

#### RepoQA

**Headline result (Table 3 for base models, Table 4 for instruct models):** This benchmark exposes the most dramatic difference between short-context and long-context models. The short-context baselines **effectively fail the task entirely**—across both model sizes and all five programming languages, accuracy drops to near-zero for any threshold requiring meaningful similarity (threshold > 0). The long-context models achieve substantial retrieval accuracy, with the 8B instruct variant reaching 82.4% average at the most lenient threshold (0.0) and 28.2% at exact match (1.0).

**Base model detailed breakdown (Table 3):** For Granite 8B Base at representative thresholds:
- Threshold 0.0: 10.0% average (short-context) → 68.0% average (long-context), gap = +58.0
- Threshold 0.5: 0.6% → 46.6%, gap = +46.0
- Threshold 0.8: 0.6% → 39.2%, gap = +38.6
- Threshold 1.0: 0.4% → 26.8%, gap = +26.4

The short-context baselines achieve non-zero accuracy only at threshold 0.0 (4.9% for 3B, 10.0% for 8B averaged across languages), which means they occasionally output *some* code that vaguely resembles a function but fails to match the target at any meaningful similarity. For any threshold requiring actual content overlap (0.1 and above), the short-context models drop to 0.0% for most language-threshold combinations.

**Programming language breakdown:** Both long-context base models perform best on Python: the 8B long-context base achieves 85.0% at threshold 0.0 and 45.0% at threshold 1.0 for Python, compared to 57.0% and 23.0% for Java, or 60.0% and 23.0% for C++. The Python advantage likely reflects the dominance of Python in the training data and the model's stronger familiarity with Python code structure and documentation patterns. TypeScript shows the steepest drop-off at exact match for the 8B base (64.0% at threshold 0.0 → 12.0% at threshold 1.0), suggesting that while the model can find the right general area of the context, it struggles to reproduce TypeScript function signatures with exact precision.

**Instruct model results (Table 4):** The instruct variants consistently outperform their base counterparts. For Granite 8B Instruct at threshold 0.0: 82.4% average vs. 68.0% for the base variant—a 14.4-point improvement. At threshold 1.0: 28.2% vs. 26.8% for the base variant. The 3B instruct variant shows an even larger relative gain: 68.0% average at threshold 0.0 vs. 61.6% for the 3B base variant. The instruct models' advantage is most pronounced at intermediate thresholds: for Granite 8B at threshold 0.5, the instruct variant achieves 61.6% vs. 46.6% for the base (+15.0 points), and at threshold 0.8, 47.6% vs. 39.2% (+8.4 points). This suggests that instruction tuning improves the model's ability to produce outputs that are *close* to the target even when not exact, possibly because instruction-following training teaches the model to format and structure its outputs more consistently.

**Figure 1 visualization:** The bar chart in Figure 1 shows retrieval accuracy at threshold 0.5 for all four model variants before and after context extension. The visual contrast is stark: all short-context bars are near-zero (the 8B instruct short-context variant registers barely visible at ~0.6%), while all long-context bars reach substantial heights. The 8B instruct long-context variant achieves the highest at approximately 62%, followed by the 3B instruct at ~38%, the 8B base at ~47%, and the 3B base at ~34%.

#### Key Retrieval (Needle-in-a-Haystack)

**Headline result (Figure 2):** The Key Retrieval heatmap for Granite-8B-Code-Instruct shows two qualitatively different regimes. Before context extension (left panel), the model maintains strong retrieval (green cells) only up to approximately 4K sequence length—exactly its training context window—and then performance collapses to near-zero (red cells) for all longer sequence lengths and all key offset positions. After context extension (right panel), the heatmap is "perfect-all-green" across the full evaluated length, indicating successful retrieval at every sequence length and key offset combination tested.

**Interpretation:** The paper notes that this level of retrieval is "relatively easy for long-context code LLMs," and indeed the green-across-the-board result suggests the benchmark may not be difficult enough to discriminate between different long-context models or configurations. The value of this result is primarily in demonstrating that the context extension works as intended—the model can attend to and execute code at arbitrary positions within a 128K-token Python file, which is a basic prerequisite for more sophisticated long-context code understanding. The fact that the short-context model fails catastrophically beyond 4K is the key contrast: without context extension, even a strong code model becomes useless on this task when the needle is beyond its training length.

#### Short-Context Evaluations (HumanEvalPack)

**Headline result (Table 5):** The long-context extension causes minimal degradation on standard short-context code benchmarks. For base models, the average HumanEvalPack score (averaged across synthesis, fix, and explain tasks across all six languages) drops from 24.9% to 24.2% for 3B (~0.7-point decline) and from 32.5% to 31.2% for 8B (~1.3-point decline). For instruct models, the long-context 3B variant achieves 30.9% vs. 31.0% for the short-context baseline (~0.1-point decline, essentially tied), and the 8B instruct variant achieves 42.9% vs. 43.6% (~0.7-point decline).

**Task-type breakdown:** The degradation is not uniform across task types. For the 8B base model:
- Synthesis: 43.1% → 40.2% (decline of 2.9 points)
- Fix: 29.1% → 25.2% (decline of 3.9 points)
- Explain: 25.4% → 28.2% (improvement of 2.8 points)

The base model shows meaningful declines in synthesis and fix tasks but an unexpected improvement in explanation. The 8B instruct model shows:
- Synthesis: 49.6% → 51.4% (improvement of 1.8 points)
- Fix: 40.9% → 38.3% (decline of 2.6 points)
- Explain: 40.4% → 38.9% (decline of 1.5 points)

The instruct model improves on synthesis despite the context extension, which the paper attributes to the new long-context synthetic instruction data added during tuning. The fix and explain tasks show modest declines.

**Figure 3 interpretation:** The line chart in Figure 3 shows HumanEval-Python pass@1 specifically, comparing short-context and long-context variants. The base model line shows a slight downward trend (the long-context variant underperforms slightly), while the instruct model line shows an upward trend (the long-context variant outperforms). The paper's explanation—that the synthetic long-context instruction data provides additional training signal that benefits short-context tasks—is plausible but not directly tested. An alternative explanation is that the instruction tuning phase simply provides more total training steps, and the improvement would have occurred with any additional instruction data, not specifically long-context data.

### Ablation Studies and Robustness Checks

**Context length bucket analysis on LCC and RepoBench-P (Tables 1–2):** The paper implicitly ablates context length by reporting results at 4K, 8K, 16K, and 32K. The fact that long-context model performance is roughly flat across these lengths (52–60% EM for LCC, 40–47% for RepoBench-P) while short-context baselines degrade sharply demonstrates that the context extension produces genuine length-independent capability, not just a shift of the degradation cliff to a slightly longer length.

**Model scale comparison (3B vs. 8B):** Across all benchmarks, the 8B long-context models consistently outperform the 3B long-context models, but the gap is typically smaller than between the short-context variants. On RepoQA at threshold 0.5, the 8B base achieves 46.6% vs. 33.8% for the 3B base (gap = 12.8 points), while the short-context gap at the same threshold is negligible (both near 0.6%). On HumanEvalPack synthesis, the 8B base at 40.2% outperforms the 3B base at 30.5% (gap = 9.7 points). The 3B long-context model at 32K on LCC (57.8%) even slightly exceeds the 8B long-context model (57.4%), though this may be within noise. The paper does not systematically explore how the benefits of context extension scale with model size beyond these two points.

**Base vs. instruct comparison (Tables 3–4):** The instruct variants consistently outperform their base counterparts on RepoQA, with the gap largest at intermediate thresholds. At threshold 0.5: 8B instruct achieves 61.6% vs. 8B base at 46.6% (gap = +15.0); 3B instruct achieves 38.0% vs. 3B base at 33.8% (gap = +4.2). The larger gap for the 8B model suggests that instruction tuning's benefits compound with model scale—the 8B model may be better able to leverage the additional instruction-following training to produce more precisely formatted outputs.

**Programming language variation on RepoQA (Tables 3–4):** The paper implicitly ablates programming language by reporting per-language scores. Python consistently shows the highest retrieval accuracy across all model variants and thresholds, followed by Rust and TypeScript, with Java and C++ generally trailing. For 8B base at threshold 0.5: Python 65.0%, Rust 54.0%, C++ 35.0%, Java 39.0%, TypeScript 40.0%. This variation likely reflects the distribution of programming languages in the pretraining data—Python is the most represented language in most code training corpora, including the one used for Granite.

**Task type variation on HumanEvalPack (Table 5):** The explain task shows improvement for base models after context extension (25.4% → 28.2% for 8B) while synthesis and fix decline. The paper does not investigate this asymmetry, but it may suggest that the context extension's impact varies by task: tasks requiring holistic code understanding (explanation) may benefit from the model learning to attend across longer document structures, even on short inputs, while tasks requiring precise token-level generation (synthesis, fix) may be more sensitive to distribution shift from the continued pretraining.

**Multi-turn loss masking (implied ablation):** The paper mentions using a multi-turn loss mask during instruction tuning, following Wang et al. (2023a). Without this masking, the model would be trained to predict user-assistant conversation turns, potentially learning to generate user queries rather than assistant responses. The paper does not report results without this masking, so its contribution is not quantified, but the design choice reflects standard practice in instruction tuning.

**No sparse or linear attention:** The paper explicitly states that the models use full attention without sparse or linear approximations. This is implicitly an ablation against approaches like Longformer, BigBird, or Mamba that trade attention fidelity for computational efficiency. The paper does not compare against sparse-attention long-context code models, so the benefit of full attention over sparse attention for code understanding is not directly measured, but the choice reflects a hypothesis that code understanding benefits from unrestricted attention (since any token might depend on any other token through cross-file references).

### Critical Assessment

**Does the paper demonstrate that long-context extension produces effective 128K-token context windows?**

The evidence provides strong support that the models can *utilize* up to 32K tokens of context for code completion (LCC, RepoBench-P) and up to 16K tokens for retrieval (RepoQA), with flat or near-flat performance curves across the evaluated context lengths. However, the claim of "effective context windows of up to 128K tokens" is directly tested only through the Key Retrieval benchmark (Figure 2), which the paper itself describes as "relatively easy for long-context code LLMs." The green-across-the-board heatmap demonstrates that the model's attention mechanism functions at 128K—it can find and execute a specific function at any position—but this is a minimal test of long-context *understanding*. Retrieving a known function signature from a file of syntactically correct Python does not exercise the cross-file dependency reasoning, multi-hop inference, or repository-level comprehension that motivate the need for long contexts in the first place.

The RepoQA benchmark, which tests more realistic code understanding (finding a function from a natural language description within a 16K-token repository context), does not evaluate at 128K—it uses a fixed 16K context length. The LCC and RepoBench-P benchmarks top out at 32K tokens. So while the models are *trained* to handle 128K tokens, the evaluation evidence for *effective* use of contexts beyond 32K is limited to a synthetic retrieval task. The paper does not provide a RepoQA variant at 64K or 128K, nor does it extend LCC/RepoBench-P beyond 32K. This gap between the claimed context window (128K) and the highest non-synthetic evaluation length (32K) is significant—the paper demonstrates that the models don't degrade at lengths they were evaluated on, but doesn't demonstrate that they derive *benefit* from contexts between 32K and 128K on realistic tasks.

**Does the paper demonstrate that repository-level file packing is critical to the results?**

The paper does not include an ablation comparing repository-level file packing against random concatenation or simple file concatenation without topological sorting. All results are for the full recipe (RoPE adjustment + repository packing + length upsampling + instruction tuning). This is the most significant missing experiment in the paper. Without it, the claim that repository-level file packing "was found to be critical for long-context continual pretraining" (Section 2.1) is asserted but not demonstrated. The reader cannot determine how much of the improvement comes from the RoPE frequency adjustment alone (which prior work has shown is sufficient for long-context scaling in general domains) versus the repository-specific data engineering (which is the paper's claimed innovation).

Similarly, the per-language length upsampling is not ablated—there is no comparison against training on the same total token count without upsampling, which would reveal whether the downsampling of short documents was necessary or merely helpful.

These are not minor omissions. The paper's primary claim to novelty over prior work (Fu et al., 2024; Xiong et al., 2023) is the repository-aware data engineering. If similar results could be achieved with RoPE adjustment + arbitrary long code sequences, the paper's contribution would be substantially narrower—a confirmation that existing techniques work for code, rather than a demonstration that code-specific data engineering is required. The absence of these ablations means the paper's central methodological claim is unverified.

**Does the paper demonstrate no significant degradation on short-context tasks?**

The claim of "~1% average degradation" on HumanEvalPack (Table 5) is numerically supported: the 3B base drops from 24.9% to 24.2% (0.7 points), the 8B base from 32.5% to 31.2% (1.3 points), the 3B instruct from 31.0% to 30.9% (0.1 points), and the 8B instruct from 43.6% to 42.9% (0.7 points). The aggregate picture is indeed one of minimal overall degradation.

However, the task-level breakdown reveals meaningful variation that the headline number obscures. The 8B base model drops 3.9 points on the fix task (29.1% → 25.2%), which is a ~13% relative decline. The 8B instruct drops 2.6 points on fix (40.9% → 38.3%). These are not negligible degradations for practitioners who care specifically about code fixing. The paper's averaging across synthesis, fix, and explain tasks produces a compressed picture—a user deploying the long-context model for code fixing specifically would experience a larger degradation than the headline "~1%" suggests.

Additionally, HumanEvalPack is only one benchmark suite. The paper does not evaluate on other short-context code benchmarks (MBPP, DS-1000, CodeContests, etc.), so the finding of minimal degradation is established on a single test distribution. The paper's claim that the degradation is "minimal" should be understood as "minimal on HumanEvalPack specifically," not "minimal across all short-context code tasks."

**Does the paper demonstrate that the instruct model improvements are due to long-context data specifically?**

The paper attributes the instruct models' improved HumanEval-Python performance (Figure 3) and strong RepoQA results (Table 4) to the addition of synthetic long-context instruction data. However, the instruct models also receive extensive short-context instruction data (the same datasets used for the original short-context instruct models). The paper does not run an ablation where the instruct model is trained on short-context data only (without the synthetic long-context data) but using the long-context base model as the starting point. Without this ablation, it's impossible to determine whether the instruct model's strong performance comes from:
- The long-context base model's improved representations (which would transfer even without long-context instruction data),
- The long-context instruction data specifically (teaching the model to use its extended context), or
- Simply the additional training steps from the instruction tuning phase (the short-context data alone might produce similar results on a long-context base).

The paper also does not compare against an oracle upper bound: what would happen if the instruct model were trained on human-generated long-context instruction data rather than synthetic data generated by the short-context Granite-8B-Code-Instruct model? The quality of the synthetic data is an unmeasured variable—if the short-context model produces low-quality or incorrect responses for some of the templated queries, the instruct model would be learning from noisy supervision, potentially limiting its ceiling.

**What about comparisons to other long-context code models?**

The paper provides no comparison to other long-context open-source code models available at the time of writing. Models like DeepSeek Coder (which supports extended context through YaRN), Code Llama with RoPE extension, or StarCoder2 with long-context fine-tuning are not evaluated alongside the Granite models. This makes it impossible to assess whether the approach described here is competitive with, superior to, or inferior to alternative long-context scaling methods for code. The within-family comparison (short-context Granite vs. long-context Granite) demonstrates that the recipe works, but not that it works *better* than alternatives. The paper positions itself as releasing practical models rather than competing for state-of-the-art, but the absence of external baselines limits the reader's ability to calibrate the results.

**Single evaluation per benchmark, no confidence intervals.**

All tables report point estimates without standard deviations, confidence intervals, or statistical significance tests. For the RepoQA benchmark with 500 sub-tasks, the standard error on a proportion can be approximated: for an observed accuracy of 68.0% (Granite 8B base at threshold 0.0, Table 3), the 95% confidence interval is approximately ±4.1 percentage points. This means the differences between the 3B and 8B models, or between base and instruct, may not be statistically significant at the reported precision. The paper's practice of reporting to one decimal place is conventional but potentially overstates the precision of the measurements given the test set sizes.

**The difficulty estimation cost is not addressed, unlike in the prior paper.**

Unlike the "compute-optimal test-time scaling" paper analyzed in Section 3 (which explicitly acknowledged that difficulty estimation required generating 2,048 samples per question and did not account for this cost), this paper does not address the cost of its data preparation pipeline. The repository-level file packing requires parsing imports, building DAGs, performing topological sorts, and organizing by language—computationally non-trivial operations on a corpus of millions of repositories. The synthetic long-context instruction data generation requires running the Granite-8B-Code-Instruct model on templated prompts for every function in every file in every repository. These costs are not quantified, making it difficult for other teams to estimate the total computational budget required to replicate the approach from a pretrained base model.

**The Key Retrieval benchmark may not be discriminating.**

The perfect-green heatmap in Figure 2 raises a concern: if the benchmark is trivially solved by any model with functional attention up to 128K, it provides no signal about the *quality* of long-context understanding. A model that merely has its positional encodings working correctly but doesn't understand cross-file dependencies would also achieve perfect scores on this benchmark. The paper acknowledges this with the phrase "relatively easy for long-context code LLMs," but doesn't provide a more challenging variant that would differentiate models. For future work, a multi-hop retrieval task (find function A, then use its output to find function B, then execute B) or a repository-level reasoning task (fix a bug that spans three files based on a natural language description) would provide stronger evidence of genuine long-context code understanding.

**Summary of the evidence: what is established and what is not.**

What is clearly established:
1. The RoPE frequency adjustment + lightweight continued pretraining recipe produces models that can attend and retrieve across 128K tokens (supported by Key Retrieval).
2. These models dramatically outperform their short-context originals on long-context code completion and retrieval benchmarks at 4K–32K context lengths (supported by LCC, RepoBench-P, and RepoQA).
3. The degradation on HumanEvalPack short-context tasks is modest in aggregate (~1% on average), though some task types show larger declines (supported by Table 5).

What is not established:
1. Whether repository-level file packing is necessary or beneficial compared to random concatenation of code files (no ablation).
2. Whether length upsampling contributes meaningfully beyond what RoPE adjustment alone would achieve (no ablation).
3. Whether the synthetic long-context instruction data improves instruct model performance beyond what additional short-context instruction data would achieve (no ablation).
4. Whether the models effectively use context beyond 32K tokens on realistic code understanding tasks (all non-synthetic long-context evaluations stop at 32K).
5. How the approach compares to alternative long-context scaling methods for code (no external baselines).
6. The statistical reliability of the reported differences given test set sizes (no confidence intervals).

The paper succeeds as a practical release of long-context code models with a described recipe, but as a research contribution, the absence of data engineering ablations leaves its central methodological claim—that repository-level file packing is critical—in the realm of assertion rather than demonstration.

## 6. Limitations and Trade-offs

### Limitation 1: The Central Claim That Repository-Level File Packing Is "Critical" Is Not Experimentally Validated

**The assumption or constraint.** The paper asserts in Section 2.1 that repository-level file packing with semantic dependency ordering "was found to be critical for long-context continual pretraining." This is the paper's primary methodological claim distinguishing it from generic long-context scaling recipes — the idea that constructing training sequences to reflect import DAGs and topological file ordering is what transforms a model that *can* attend across 128K tokens into one that can *use* that attention for code understanding. However, the paper provides no ablation experiment comparing the full recipe (RoPE adjustment + repository packing + length upsampling) against a baseline that uses RoPE adjustment and length upsampling with randomly concatenated code files, or with files concatenated by simple heuristics (e.g., by directory order without import-graph analysis).

**The consequence.** Without this ablation, the reader cannot determine whether repository-level file packing contributes anything beyond what RoPE frequency adjustment and per-language length upsampling already provide. It is possible — and consistent with the evidence presented — that the entire improvement on LCC, RepoBench-P, and RepoQA comes from the RoPE adjustment alone (which prior work, such as Xiong et al., 2023; Fu et al., 2024, has shown is sufficient for extending effective context length in general domains), and that the file packing is an elaborate preprocessing step that does not affect downstream task performance. The paper's primary intellectual contribution — that code-specific data engineering is required for long-context code understanding — is therefore an assertion rather than a demonstrated result.

**What evidence exists in the paper.** None. There is no experiment, table, or figure that isolates the effect of repository-level file packing from the other components of the training pipeline. All results in Tables 1–4 compare the full long-context recipe (all components combined) against the original short-context baselines. The paper does not even include a qualitative argument for why file packing should matter beyond plausibility — no attention map visualizations showing that the model actually learns to attend along import-graph edges, no perplexity comparisons on held-out repositories packed vs. randomly ordered, no retrieval accuracy comparison at an intermediate checkpoint before and after packing is introduced. The phrase "was found to be critical" appears without a supporting citation, experiment, or quantitative justification.

**Mitigation status.** The paper does not attempt to address this limitation. It does not acknowledge the absence of a packing ablation as a gap, nor does it suggest future work to validate the importance of repository structure in training data. A practitioner attempting to replicate the recipe would have no guidance on whether the file packing step is worth implementing versus simply concatenating repository files in filesystem order.

---

### Limitation 2: Evidence for Effective Use of Context Beyond 32K Tokens Is Limited to a Trivially Solved Synthetic Benchmark

**The assumption or constraint.** The paper's title, abstract, and introduction all claim support for "effective context windows of up to 128K tokens." However, the non-synthetic benchmarks that test realistic code understanding tasks — LCC, RepoBench-P, and RepoQA — are evaluated at context lengths up to only 32K (LCC, RepoBench-P) and 16K (RepoQA). The sole evaluation at 128K tokens is the Key Retrieval synthetic benchmark (Figure 2), which the paper itself characterizes in Section 3.3 as "relatively easy for long-context code LLMs." The task — finding and executing a known Python function buried within syntactically correct Python — tests only that the model's positional encodings and attention mechanism function at that length, not that the model derives *benefit* from very long contexts for code understanding tasks that require cross-file reasoning, multi-hop inference, or repository-level comprehension. The paper does not provide, for instance, a RepoQA variant at 64K or 128K, nor does it extend LCC or RepoBench-P beyond 32K.

**The consequence.** The paper's headline claim of "128K effective context" is supported by direct evidence only for a minimal functionality test. A model could pass the Key Retrieval benchmark at 128K while being incapable of using contexts beyond 32K for any task requiring code *understanding* — for example, answering a question that requires synthesizing information from three files spread across positions 5K, 45K, and 110K. The RepoQA and LCC results establish strong evidence for effective use of context up to 16–32K tokens, but the jump from 32K to 128K — an additional 4× in length — is untested on realistic tasks. A practitioner deploying the model for repository-level code understanding at 100K tokens of context would be operating in an unevaluated regime.

**What evidence exists in the paper.** Figure 2 (Key Retrieval) is the only 128K evaluation, and it shows "perfect-all-green" performance — every sequence length and key offset combination succeeds. The LCC and RepoBench-P evaluations (Tables 1–2) extend to 32K and show flat performance curves across 4K, 8K, 16K, and 32K for both models, which is consistent with the hypothesis that performance would remain flat at 64K and 128K, but this is extrapolation, not evidence. RepoQA (Tables 3–4) is evaluated only at a fixed 16K context length. The paper does not report a RepoQA variant at 64K or 128K, which would directly test whether retrieval accuracy degrades or remains stable as context grows by another 4–8×.

**Mitigation status.** The paper acknowledges that Key Retrieval is "relatively easy" but does not treat the gap between 32K and 128K realistic evaluation as a limitation requiring future work. The "perfect-all-green" result is presented as evidence of successful scaling, but the absence of harder 128K evaluations is not discussed as a confidence gap. The paper would be strengthened by extending RepoQA to 64K and 128K, or by introducing a multi-hop retrieval variant of Key Retrieval that tests cross-file dependency resolution at full context length.

---

### Limitation 3: Short-Context Degradation Is Task-Dependent and Potentially Larger Than the Headline "~1% Average"

**The assumption or constraint.** The paper claims in the abstract that long-context models achieve improvements "without any noticeable performance degradation on regular code completion benchmarks (e.g., HumanEval)." This claim is operationalized in Section 3.4 and Table 5 by comparing the average pass@1 across all three HumanEvalPack task types (synthesis, fix, explain) and all six programming languages. The averaging obscures task-level variation that is substantively meaningful. For the Granite 8B base model, the fix task drops from 29.1% to 25.2% — a 3.9 percentage point absolute decline, representing a ~13% relative drop. For the 8B instruct model, the fix task drops from 40.9% to 38.3% (2.6 points, ~6% relative), and the explain task drops from 40.4% to 38.9% (1.5 points, ~4% relative). The synthesis task shows mixed results: a decline for the base model (43.1% to 40.2%, 2.9 points) but an improvement for the instruct model (49.6% to 51.4%, 1.8 points).

**The consequence.** A practitioner who cares primarily about code fixing — a critical capability in real-world development workflows — would experience a degradation substantially larger than the "~1% average" that the paper emphasizes. The 8B base model's fix degradation of 3.9 points is nearly three times the average degradation reported for that model. Furthermore, the evaluation is limited to a single short-context benchmark suite (HumanEvalPack). The paper does not evaluate on MBPP, DS-1000, CodeContests, or other widely-used code benchmarks, so the bounds of the degradation are characterized only on one test distribution. A user switching from the short-context to the long-context Granite model might encounter degradations on their specific tasks that are not captured by the HumanEvalPack suite at all.

**What evidence exists in the paper.** Table 5 provides the task-level breakdown that reveals the variation, though the paper's text emphasizes the average: "only an average ~1% degradation for the pass@1 metric on 3B and 8B models respectively." Figure 3 shows the HumanEval-Python trend specifically, but this is only the Python subset of the synthesis task, not the full task-type and language matrix. The fix and explain tasks receive no visualization or detailed discussion. The paper notes the instruct model improvement on synthesis and attributes it to the synthetic long-context data, but does not discuss why fix and explain decline for the same model, which would be informative about what capabilities the context extension most affects.

**Mitigation status.** The paper does not acknowledge the task-dependent variation as a limitation. The finding that instruct models improve on synthesis is presented as a positive result, and the fix/explain declines are mentioned only in the table, not in the text's discussion. A more complete characterization would include evaluation on additional short-context benchmarks to establish the breadth of the degradation, and would provide per-task analysis of what types of code fixing or explanation problems the long-context model struggles with relative to the original.

---

### Limitation 4: The Synthetic Long-Context Instruction Data Pipeline Depends on a Short-Context Model, Creating an Unmeasured Quality Ceiling

**The assumption or constraint.** Section 2.2 describes the long-context instruction data generation pipeline: for each repository-level file-packed document, the paper generates multi-turn instruction data where responses are "either parsed semantically from the original document or generated using Granite-8b-Code-Instruct-4K" — the original *short-context* instruct model. The short-context model receives templated prompts that extract specific functions or code units, keeping the immediate input short so the model can generate coherent responses despite its 4K context limitation. The paper assumes that these short-context-generated responses are of sufficient quality to serve as training targets for the long-context instruct model, and that the long-context capability in the resulting model comes from the multi-turn chaining and document structure, not from the response quality.

**The consequence.** The quality of the synthetic instruction data is a bottleneck that the paper does not measure. The short-context Granite-8B-Code-Instruct-4K model has its own error rate on code generation and explanation tasks — if it produces incorrect function implementations, flawed explanations, or imprecise documentation references in its responses, the long-context instruct model is being trained on noisy supervision. The resulting instruct model would inherit these errors, potentially learning to generate plausible-sounding but incorrect code explanations, or learning to retrieve the wrong function when the short-context model's generated response mismatched the ground truth. The paper does not compare the synthetic data against human-generated long-context instruction data (which would serve as an oracle upper bound), nor does it report the quality of the synthetic data (e.g., by evaluating the short-context model's responses against ground-truth implementations extracted from the repository). This means the ceiling on instruct model performance imposed by the data generation pipeline is unknown — the model's RepoQA accuracy (82.4% at threshold 0.0 for 8B instruct) may be limited not by the model architecture or training recipe but by the quality of the synthetic responses it was trained to imitate.

**What evidence exists in the paper.** The paper provides no direct evaluation of the synthetic instruction data quality. The RepoQA results for instruct models (Table 4) show improvements over base models (e.g., 8B instruct achieves 82.4% vs. 68.0% base at threshold 0.0, a 14.4-point gain), which is consistent with the synthetic data being useful, but does not establish how much better the instruct model could be if trained on higher-quality (e.g., human-generated) long-context data. The paper does not report an ablation varying the source of instruction responses (synthetic vs. ground-truth extraction vs. human-written), so the contribution of response quality to final instruct model performance is unidentified.

**Mitigation status.** The paper does not acknowledge the quality ceiling imposed by the bootstrapping approach. Section 2.2 describes the pipeline factually without discussing its limitations. The dependency on the short-context model is presented as a pragmatic solution to the scarcity of long-context instruction data, which it is, but the paper should also acknowledge that this pragmatism comes at a cost: the instruct model cannot exceed the quality of its training targets, and those targets were generated by a model that cannot itself read long contexts. Future work might explore iterative bootstrapping (using the first long-context instruct model to regenerate higher-quality training data for a second round of instruction tuning) or using multiple short-context models for response generation with filtering.

---

### Limitation 5: No External Baselines Against Alternative Long-Context Code Models

**The assumption or constraint.** All evaluations in the paper compare the long-context Granite models against their short-context predecessors (Granite-3B/8B-Base-2K/4K and Granite-3B/8B-Instruct-2K/4K). The paper does not compare against any other long-context open-source code models that existed at the time of this work — for instance, Code Llama variants with extended context (Rozière et al., 2023), DeepSeek Coder models with YaRN-based context extension, or StarCoder2 models fine-tuned for long contexts. Section 3 describes the benchmarks and evaluation methodology but never mentions external model comparisons or explains their absence.

**The consequence.** The paper demonstrates that its recipe *works* — that long-context Granite dramatically outperforms short-context Granite on long-context tasks — but does not establish whether it works *well* relative to alternative approaches. A practitioner deciding which long-context code model to adopt has no basis in this paper for choosing Granite over a competitor. It is possible that the Granite models, despite the careful data engineering, underperform other long-context code models on the same benchmarks, or that a simpler recipe (e.g., RoPE adjustment with randomly concatenated code files applied to a different base model) would achieve similar or better results. The within-family comparison is sufficient to demonstrate progress over the Granite baseline, but insufficient to calibrate the absolute quality of the result.

**What evidence exists in the paper.** None. No external model names appear in any results table. The paper references CodeGemma, Code Llama, and other models in the introduction (Section 1) as motivation for why open-source long-context code models are needed, but does not evaluate against them. The paper's positioning as releasing practical models under Apache 2.0 does not preclude comparison — in fact, comparison against existing long-context models would strengthen the case for adoption by showing where Granite is competitive or superior.

**Mitigation status.** The paper does not address this limitation. The absence of external baselines is a significant gap in the experimental design, particularly given that the paper's contribution is positioned as a practical recipe and model release rather than a novel technique. A model release paper should ideally help practitioners understand where the model stands relative to alternatives. The paper could have included Code Llama or DeepSeek Coder comparisons on the same benchmarks (LCC, RepoBench-P, RepoQA) using the same evaluation protocol to provide this calibration.

---

### Limitation 6: The Computational Cost of Data Preparation for the Recipe Is Not Quantified

**The assumption or constraint.** The paper describes in detail the data preparation steps required for the context extension recipe: (1) repository-level file packing, which involves parsing imports, building directed acyclic graphs, breaking cycles, performing topological sorts, determining dominant programming languages, and organizing files accordingly across a corpus of millions of repositories; (2) per-language length upsampling with filtering and downsampling of short documents; (3) synthetic long-context instruction data generation, which involves parsing every repository document into structural units (classes, methods, functions), generating templated queries for random subsets of functions, and running the Granite-8B-Code-Instruct-4K model to generate responses for each query — a process that requires model inference at scale across the entire training corpus. The paper quantifies the training cost (4B additional tokens, "only 0.1% of original pretraining data") but does not estimate the computational cost of the data preparation pipeline that produces those 4B tokens in their repository-structured, length-upsampled, instruction-augmented form.

**The consequence.** A team attempting to replicate the recipe from a different base code model would face an unknown and potentially substantial data engineering cost before any training begins. The import-graph construction and topological sorting must be performed for every repository in the training corpus; the synthetic instruction data requires running inference with the original instruct model for every function in every file across thousands of repositories. These costs could easily exceed the 4B-token training cost itself, particularly the inference cost for synthetic data generation. Without quantification, the paper's framing of the approach as "lightweight" (based solely on the training token count) is incomplete — the total computational budget for replication is the sum of data preparation, synthetic data generation, and training, and only the last of these is measured.

**What evidence exists in the paper.** The paper provides no quantification of data preparation costs. Section 2.1 describes the file packing algorithm but does not report the number of repositories processed, the computational complexity of the DAG construction and topological sort, or the wall-clock time or GPU-hours required. Section 2.2 describes the synthetic data generation pipeline but does not report the number of functions parsed, the number of inference calls made to Granite-8B-Code-Instruct-4K, or the inference compute budget consumed.

**Mitigation status.** The paper does not acknowledge the unmeasured cost of data preparation as a limitation. This is particularly notable because the paper's primary claimed innovations — repository-level file packing and synthetic long-context instruction data — are both data engineering steps that impose costs beyond model training. A full accounting of the replication budget would significantly improve the paper's value as a practical recipe. Future work could profile these costs and explore whether cheaper approximations (e.g., filesystem-order packing without import-graph analysis, or ground-truth extraction without model-generated responses) achieve comparable results at lower data preparation cost.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

This paper shifts the conversation around open-source code models from "can we match proprietary long-context performance?" to "how should we structure training data so that long contexts become genuinely *useful* for code?" The contribution is not a new positional encoding mechanism or attention architecture—the RoPE frequency adjustment is drawn from Xiong et al. (2023), and the progressive training schedule follows Fu et al. (2024). The contribution is a **reframing of long-context code modeling as a data engineering problem**: the bottleneck isn't teaching models to attend across 128K tokens (which prior work already showed is achievable), but constructing training sequences where cross-position attention corresponds to semantically meaningful code relationships—import resolution, function definition lookup, class inheritance chains.

This reframing has two important effects on the field's research priorities:

**First, it redirects attention from architecture to data.** The paper's explicit choice to use full attention with no sparse or linear approximations is a statement: the quadratic cost of attention is an engineering problem (solved here by Flash Attention 2 and Ring Attention), but making attention *useful* is a data problem. If the paper had found that attention architecture or positional encoding design was the limiting factor, the field would be incentivized to develop ever-more-efficient sparse attention mechanisms or novel position representations. Instead, the paper's results—dramatic improvements from lightweight retraining on repository-structured data—suggest that the low-hanging fruit is in data preparation, not model design. This makes research on code-specific data curation pipelines (import-graph-aware packing, documentation-structured ordering, cross-file dependency annotation) more attractive than research on new attention sparsity patterns for code.

**Second, it establishes that context extension can be a lightweight post-training step.** The 4B-token training budget (~0.1% of original pretraining) has immediate practical implications: organizations with fine-tuned code models don't need to retrain from scratch to add long-context support. They can apply the progressive RoPE adjustment + repository-structured data recipe as a post-processing step, preserving their existing fine-tuned capabilities while adding long-context functionality. This decouples the decision to extend context length from the decision to retrain, which changes how model release roadmaps should be planned—teams can release short-context models first and add long-context variants later without starting over.

**Third, it provides a diagnostic framework for why prior long-context code efforts may have underperformed.** The paper doesn't directly compare against other long-context code models, but the repository-packing hypothesis implies a specific diagnosis: models trained on arbitrarily concatenated code files may *achieve* long-context attention but fail to *use* it for code-relevant reasoning because the training signal at long distances was noise (random file boundaries) rather than structure (dependency relationships). This hypothesis is testable—future work can evaluate existing long-context code models on RepoQA and see whether performance correlates with the semantic coherence of their training data—and it gives the field a concrete variable to manipulate rather than a vague "long-context training is hard."

**What the paper does *not* change:** It does not resolve the fundamental tension between context length and short-context capability. The ~1% average degradation on HumanEvalPack is small, but the task-level variation (3.9-point decline on the fix task for 8B base, Table 5) shows that context extension is not entirely free even with careful data mixing. The paper also does not establish that 128K-token contexts are useful for realistic code tasks beyond synthetic retrieval—the gap between the 32K evaluations on LCC/RepoBench-P and the 128K claim remains unbridged. Future work that extends RepoQA or LCC to 64K and 128K contexts will determine whether the flat performance curves observed at 4K–32K continue, or whether a new degradation regime emerges at longer lengths.

### Follow-Up Research This Work Enables

**Ablation study: repository-level file packing vs. random concatenation of code files, controlled for total training tokens and context length.** This is the single most important missing experiment in the paper. Train three long-context variants of the same base model under identical RoPE adjustment schedules and total token budgets, varying only the file ordering within training sequences: (a) repository-level file packing with topological sort (the paper's recipe), (b) repository-level file packing by filesystem order (no import-graph analysis), and (c) random concatenation of files from different repositories. Evaluate all three on RepoQA at 16K, LCC and RepoBench-P at 4K–32K, and Key Retrieval at 128K. The hypothesis from the paper is that (a) should substantially outperform (b) and (c) on RepoQA and cross-file completion tasks, since these require dependency-aware attention patterns that only (a) provides training signal for. A null result—all three performing similarly—would mean the RoPE adjustment alone is sufficient and the repository packing is unnecessary complexity. A strong positive result would validate the paper's central methodological claim and establish import-graph-aware packing as a standard step in long-context code training.

**Extension of RepoQA and LCC benchmarks to 64K and 128K context lengths.** The paper's most significant evaluation gap is that realistic code understanding tasks are tested only up to 32K (LCC, RepoBench-P) and 16K (RepoQA), while the claimed capability is 128K. Construct RepoQA variants at 64K and 128K by including more files from each repository in the context (beyond the 10 needle functions currently used). Evaluate the long-context Granite models on these extended benchmarks and characterize whether retrieval accuracy remains flat (as the Key Retrieval heatmap suggests) or degrades at some intermediate length. A finding that accuracy degrades between 32K and 64K would suggest that the current recipe produces diminishing returns beyond 32K on realistic tasks, while flat performance through 128K would substantially strengthen the paper's headline claim. This experiment also provides a more discriminating test than the trivially solved Key Retrieval benchmark—a multi-hop version where the model must find function A, use its output to identify function B, and then execute B would test genuine cross-file reasoning at full context length.

**Iterative bootstrapping of long-context instruction data.** Section 2.2 describes generating synthetic long-context instruction data using the *short-context* Granite-8B-Code-Instruct-4K model, which creates an unmeasured quality ceiling. A natural extension: after training the first-generation long-context instruct model (Granite-8B-Code-Instruct-128K), use *it* to regenerate responses for the same templated queries on the same repository-level documents. Because the long-context model can attend to the full document rather than just the extracted code unit, it should produce more contextually accurate responses—for example, correctly referencing imports from earlier in the file, using function signatures consistent with their definitions elsewhere in the repository, or identifying edge cases visible only from cross-file context. Train a second-generation instruct model on this regenerated data and compare its RepoQA and HumanEvalPack performance against the first-generation model. Improvements would demonstrate that the bootstrapping pipeline can be iteratively refined, while no improvement would suggest the quality ceiling is determined by the templated query structure rather than the response model's context length. A degradation (e.g., the model learning to reproduce its own errors) would be an important negative result indicating instability in synthetic data bootstrapping.

**Comparison of Granite long-context models against alternative long-context code models on RepoQA, LCC, and RepoBench-P under identical evaluation protocols.** The paper's absence of external baselines makes it impossible to calibrate the absolute quality of the results. Evaluate Code Llama with extended context (RoPE-adjusted variants), DeepSeek Coder with YaRN-based context extension, and StarCoder2 long-context variants on the exact same RepoQA (16K, 500 sub-tasks), LCC (balanced buckets, 4K–32K), and RepoBench-P (rebalanced) benchmarks using greedy decoding. Report per-language and per-threshold breakdowns to enable fine-grained comparison. This establishes whether the repository-level file packing recipe produces models that are competitive with, superior to, or inferior to alternative context-extension methods. A finding that Granite underperforms models trained with simpler data preparation would motivate investigating what else (beyond file packing) drives long-context code performance. A finding that Granite outperforms models with comparable or larger parameter counts would validate the data engineering approach and make the case for adoption.

**Difficulty-stratified evaluation of the context-extension tradeoff on short-context tasks.** The HumanEvalPack results (Table 5) show task-dependent degradation that the headline average obscures. A more informative evaluation would bin HumanEvalPack problems by difficulty (e.g., by the short-context base model's pass@1 rate on each problem, analogous to the difficulty quintile approach in the test-time compute scaling paper) and measure whether degradation is concentrated in easy or hard problems. The hypothesis: context extension may hurt performance on problems requiring precise single-function reasoning (because training on long repository sequences slightly shifts the model's internal representation of "what code looks like") while helping on problems that benefit from broader code understanding (e.g., problems requiring knowledge of standard library functions that might appear in the longer training contexts). A difficulty-stratified analysis would tell practitioners *which* short-context tasks are safe to run on the long-context model and which should use the original short-context variant, enabling a routing strategy rather than a one-size-fits-all deployment.

**Measuring and improving the quality of synthetic long-context instruction data.** The paper's bootstrapping pipeline generates instruction-response pairs using the short-context Granite-8B-Code-Instruct-4K model, but never evaluates the quality of these responses. A concrete follow-up: take a sample of 100–200 generated responses for the "implementation from context" task (where the model must implement a function given all *other* code and documentation in the repository), execute them against ground-truth test cases, and compute pass@1 for the synthetic data itself. This establishes the quality ceiling: if the synthetic data has pass@1 of 40%, the instruct model trained on it cannot plausibly exceed 40% on similar tasks regardless of training recipe. If ceiling is low, experiment with filtering strategies—discard responses that fail type-checking, use execution feedback to regenerate incorrect responses, or ensemble responses from multiple short-context models (Granite + Code Llama + DeepSeek Coder) and select by majority vote. Then train instruct models on filtered vs. unfiltered data and measure the downstream impact on RepoQA and HumanEvalPack. This would quantify how much of the instruct model's performance is attributable to data quality vs. model architecture and training.

### Practical Applications and Downstream Use Cases

**Repository-level code completion in IDEs.** The most direct application is integrating the long-context Granite models into development environments for cross-file code completion. Current short-context code models can complete the current line based on the current file, but break down when the correct completion requires knowing a function signature from an imported module, a class definition from a parent class in another file, or a configuration constant from a project-wide config. The LCC and RepoBench-P results (Tables 1–2) quantify the improvement: on RepoBench-P at 32K context, the long-context Granite 8B base achieves 44.5% exact match vs. 7.8% for the 4K-context original—a 36.7-point improvement representing the difference between useful cross-file completion and effectively random guesses. An IDE plugin that packs the current file plus its import-dependency files (ordered by the same topological sort used in training) into a single context and queries the model for next-line completion would directly leverage this capability. The 3B model's strong performance (45.3% at 32K on RepoBench-P) is particularly relevant for on-device deployment where larger models are impractical.

**Code search and retrieval over large codebases.** The RepoQA results (Tables 3–4) demonstrate that the long-context Granite models can find specific functions given natural language descriptions within a 16K-token repository context. The Granite 8B instruct model achieves 82.4% average retrieval accuracy at the most lenient threshold (0.0) and 61.6% at threshold 0.5, meaning it returns a function with at least 50% similarity to the target in 3 out of 5 cases across five programming languages. A code search tool that indexes a repository by packing files into 16K-token windows (respecting the semantic dependency ordering from the paper's packing algorithm) and queries the instruct model with natural language function descriptions would enable developers to find relevant code without knowing exact function names or file locations. The per-language variation (Python: 89.0% at threshold 0.0 for 8B instruct, C++: 63.0%) provides a realistic expectation of where the tool works best.

**Automated code explanation and documentation generation for legacy codebases.** The instruct models' ability to explain code given long context (tested implicitly through the synthetic instruction data pipeline described in Section 2.2, which includes explanation tasks) enables a practical application: feeding an entire repository into the model's context and asking it to generate documentation for specific functions, classes, or modules. Because the long-context model can see the full dependency graph—imported utilities, parent class definitions, type annotations in other files—its explanations can reference cross-file relationships that a short-context model would miss. The synthetic data generation pipeline described in Section 2.2 already includes this use case: "it then requests and extracts the implementations of a random subset of the extracted functions/methods... and then asks for an explanation of that implementation using available documentation." The 8B instruct model's strong performance on the explain task in HumanEvalPack (38.9% pass@1, down only 1.5 points from the short-context baseline despite having its context window expanded 32×) suggests this capability transfers to at least some short-context explanation tasks.

**Bootstrapping long-context instruction data for other code models.** The paper's synthetic data generation pipeline (Section 2.2) is a methodological contribution that generalizes beyond Granite. Any team with a short-context code instruct model and a repository-level pretraining corpus can replicate the approach: parse repositories into structural units, generate templated queries for function retrieval/explanation/implementation, use the short-context model to generate responses (keeping prompts short by extracting individual functions), and assemble the responses into multi-turn long-context training sequences. This breaks the chicken-and-egg problem of needing long-context data to train long-context instruct models without already having a long-context model to generate it. The paper's results suggest the approach works (the instruct models substantially outperform the base models on RepoQA), but the unmeasured quality ceiling of the synthetic data means teams adopting this recipe should budget for human evaluation of the generated responses and potential filtering or regeneration steps.
