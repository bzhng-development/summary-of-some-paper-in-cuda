# Long Context Compression with Activation Beacon

**ArXiv:** [2401.03462](https://arxiv.org/abs/2401.03462)

## 🎯 Pitch

This paper proposes **Activation Beacon**, a plug-in module for transformer-based LLMs that enables long context compression by distilling raw input into a small set of beacon tokens' activations (keys and values at every layer) through a progressive, fine-grained compression workflow where each chunk is interleaved with beacon tokens and encoded sequentially.

---

## 1. Executive Summary

This paper proposes **Activation Beacon**, a plug-in module for transformer-based LLMs that enables long context compression by distilling raw input into a small set of beacon tokens' activations (keys and values at every layer) through a progressive, fine-grained compression workflow where each chunk is interleaved with beacon tokens and encoded sequentially. Applied to Llama-2-7B and Qwen-2-7B and evaluated on LongBench, Needle-in-a-Haystack, and Multi-Needle-in-a-Haystack tasks, Activation Beacon maintains comparable performance to the uncompressed baseline across compression ratios up to 8×, achieving a 2× acceleration in inference time and an 8× reduction of KV cache memory. By training with chunk-wise randomly sampled compression ratios and compression-based auto-regression, the method generalizes to context lengths far exceeding its 20K training maximum (e.g., 128K), establishing that effective query-independent compression is achievable only when fine-grained progressive distillation replaces the soft-token bottleneck of prior approaches.

## 2. Context and Motivation

### The Core Problem: The Cost of Long Contexts Grows Non-Linearly

The paper addresses a specific and critical efficiency problem in modern LLMs: **as input context length grows, the computational and memory costs of transformer-based models balloon disproportionately, making long-context processing prohibitively expensive for real-world deployment.**

The root cause is the **quadratic complexity of self-attention**. In a standard transformer, every token in the input sequence attends to every preceding token during generation. If the input context has $n$ tokens, the attention computation scales as $O(n^2)$. Beyond the raw computation, LLMs rely on **KV caching** to avoid recomputing attention states for all preceding tokens at each generation step. The KV cache stores per-layer key and value activations for every token in the sequence on GPU memory. As context length increases, both the attention FLOPs and the KV cache memory footprint grow rapidly — the paper visualizes this in Figure 3, where forward FLOPs for full-attention models climb steeply from 4K to 256K context.

This is not a niche concern. The paper identifies several application domains where long-context processing is essential (Section 1):

- **Long-document understanding** (Jiang et al., 2024): analyzing legal contracts, scientific papers, or technical reports that span tens of thousands of tokens.
- **Long-content creation** (Bai et al., 2024): generating coherent documents exceeding 10,000 words, which requires conditioning on extensive prior context.
- **Long-term memorization and reasoning** (Zhang et al., 2024): conversational agents and personal assistants that must retain and reason over interaction histories spanning days or weeks.

In each case, the deployment of models with 128K or larger context windows — which modern architectures like Llama-3 (Dubey et al., 2024), GPT-4 (OpenAI et al., 2024), and Qwen-2 (Yang et al., 2024) now support — incurs costs that scale non-linearly. A 2× increase in context length yields roughly a 4× increase in attention computation and a 2× increase in KV cache memory. For latency-sensitive applications or hardware-constrained deployments (edge devices, consumer GPUs), this renders long-context inference impractical without mitigation.

---

### Why This Problem Matters: The Efficiency-Capability Tension

The paper frames the problem as a tension between **effectiveness** and **efficiency** — a tension that has grown more acute as context windows have expanded. The recipe for extending context windows in modern LLMs is well-established (Section 2): modify rotary position embeddings (RoPE) via extrapolation or interpolation (Chen et al., 2023; Peng et al., 2023; Ding et al., 2024), and train on long-dependency data during both pre-training and post-training phases. This recipe has proven remarkably effective at enabling models to utilize long contexts, but it does nothing to address the resulting computational burden.

The real-world impact is concrete. A model processing a 128K context with full attention might require 8× the FLOPs and 8× the GPU memory of the same model processing a 16K context. For a 7B-parameter model, this can mean the difference between running comfortably on a single consumer GPU (e.g., RTX 4090 with 24GB VRAM) and requiring multiple datacenter-grade GPUs. For the 72B-parameter Qwen-2 model evaluated in the paper (Figure 3C), the full-attention FLOPs at 256K context reaches approximately $1.5 \times 10^5$ TFLOPs — a scale that is beyond practical throughput for most users.

The theoretical significance lies in whether this quadratic scaling is *necessary*. If the information in long contexts can be distilled into more compact representations without losing task-relevant details, then the quadratic complexity is an artifact of the architecture rather than an inherent requirement of the task. This paper makes the case that such compression is achievable, and that the bottleneck is not the volume of information but the method by which it is condensed.

### Prior Approaches: The Landscape Before Activation Beacon

The paper situates itself within three related but distinct research threads, each with identifiable limitations that motivate the proposed approach (Section 2).

#### Sparse Attention: Reduce Computation, but Not Memory

Conventional sparse attention methods (Zaheer et al., 2020; Beltagy et al., 2020) restructure attention patterns so that each token attends to only a subset of preceding tokens — typically a local window plus a small set of global reference points. More recent work (Jiang et al., 2024; Han et al., 2023; Xiao et al., 2023; Zhu et al., 2024) has shown that LLM attention patterns are naturally sparse even when trained densely, and that dynamic sparsity patterns can preserve most of the attention mass with substantially reduced computation.

**Where they fall short:** These methods require holding all KV activations on GPU memory to dynamically determine optimal sparse patterns for each attention head. This makes them effective at reducing computation (FLOPs) but **ineffective at reducing memory** — the KV cache still grows linearly with context length. For memory-constrained deployments, this is a critical limitation. The paper explicitly notes this tradeoff in Section 2:

> "these methods require holding all KV activations on chip to dynamically determine the optimal sparse patterns, making them unsuitable for KV cache reduction."

#### KV Cache Compression: Reduce Memory Along Non-Token Dimensions

This line of work compresses KV activations along dimensions other than the token count: across layers (CLA, Brandon et al., 2024), across attention heads (GQA, Ainslie et al., 2023), across feature channels (MLA, DeepSeek-AI, 2024), or through numerical quantization (KIVI, Liu et al., 2023). These methods are complementary to token-wise compression — in principle, one could apply cross-layer cache sharing and quantization on top of a token-compressed representation.

**Where they fall short:** These methods reduce the memory per token but do not reduce the number of tokens that must be processed. The attention FLOPs still scale quadratically with sequence length because every token still participates in the attention computation. They address the memory bottleneck but leave the computation bottleneck largely intact.

#### Context Compression: The Direct Precursor, with Critical Bottlenecks

This is the most directly relevant prior work: methods that aim to compress the raw input context into shorter, more concise representations. The paper identifies several specific prior approaches and their limitations in detail (Section 2, and elaborated in the experimental comparisons of Sections 4.2–4.4):

**Soft-token-based compression (Gisting, ICAE, AutoCompressor).** Gisting (Mu et al., 2023) compresses user instructions into a small set of "gist" token activations, which are then used as a prefix for generation. However, it compresses the entire input "all-at-once," which limits it to contexts shorter than the model's built-in window size. ICAE (Ge et al., 2024) and AutoCompressor (Chevalier et al., 2023) address this by segmenting long contexts into chunks and compressing each chunk into soft tokens, which then condition the generation of subsequent chunks. The AutoCompressor also introduces a recurrent architecture where the compressed representation of a chunk is fed back as input for the next chunk.

**Where they fall short — the soft-token bottleneck:** The paper identifies that soft tokens "constitute the major bottleneck to encapsulate the complex information within long contexts" (Section 1). A small number of soft tokens (typically 4–16) has limited representational capacity — these vectors must summarize potentially thousands of raw tokens' worth of information. The experimental results in Table 1 bear this out starkly: AutoCompressor achieves only 12.9% on LongBench single-doc QA versus 34.8% for the uncompressed baseline, and ICAE reaches 19.5%. This is not a marginal degradation — it represents a near-total loss of task-relevant information.

**Where they fall short — coarse compression granularity:** Both ICAE and AutoCompressor compress each chunk into a single, uniform set of soft tokens. There is no mechanism for fine-grained, differentiated compression within a chunk. Every part of the chunk receives the same treatment — the model cannot allocate more representational capacity to dense, information-rich segments and less to redundant or boilerplate content.

**Where they fall short — re-encoding overhead:** In both ICAE and AutoCompressor, the soft tokens generated from a chunk must be re-encoded when generating subsequent chunks. This is because their architectures depend on the final-layer outputs of preceding chunks to condition the encoding of the current chunk, creating a sequential dependency that requires recomputation. The paper explicitly notes this introduces "extra overhead" and that Activation Beacon avoids it by virtue of its per-layer conditioning design.

**Where they fall short — fixed compression ratios:** These methods are trained with a fixed number of soft tokens (e.g., exactly 4 tokens per segment). At inference time, the compression ratio is locked to what was used during training. A model trained with 4 soft tokens per chunk cannot be deployed with 2 or 8 tokens without retraining, making it impossible to flexibly trade off between compression rate and downstream accuracy based on the specific task or hardware budget.

**Token-deletion methods (LongLLMLingua, SnapKV).** An alternative branch of context compression deletes tokens deemed unimportant rather than summarizing them (Jiang et al., 2023; Li et al., 2024). These methods estimate the importance of each token — for instance, by analyzing attention patterns — and retain only the top-k most important tokens for conditioning generation.

**Where they fall short — query dependence:** LongLLMLingua and SnapKV are **query-dependent**: they determine which tokens are important based on the specific query that will be asked. This means the compression must be recomputed for every new query, even if the underlying context remains the same. In multi-turn conversational scenarios, where a user asks multiple questions about the same document, this imposes severe latency penalties. The paper's Multi-Needle-in-a-Haystack experiment (Table 2) demonstrates this concretely: at 128K context with three turns, LongLLMLingua requires 27.751 seconds of latency versus Activation Beacon's 2.981 seconds — a 9.3× gap — precisely because LongLLMLingua must re-compress the same context from scratch for each turn.

**Where they fall short — context window limits:** Both methods rely on the backbone LLM's attention mechanism to estimate token importance. When the context exceeds the model's trained window size, attention computations become unreliable, and the importance estimates degrade. This prevents token-deletion methods from processing contexts longer than the LLM's built-in window — a critical limitation when the goal is to handle 128K+ inputs with a model trained for 4K–32K.

**CCM (Compressed Context Memory, Kim et al., 2024).** Specifically designed for online chatting, CCM compresses conversation history. The paper notes it "cannot be used in general long context tasks such as long document understanding," limiting its applicability to the broader long-context processing landscape.

### How Activation Beacon Positions Itself

The paper's positioning is built around overcoming each of the identified limitations through four design principles that collectively constitute the "effective, efficient, and flexible compression" claim (Section 1):

**1. Compression into activations, not soft tokens.** Instead of summarizing chunks into a small number of learnable soft token embeddings (as in ICAE and AutoCompressor), Activation Beacon compresses context into the **keys and values of dedicated beacon tokens at every layer**. These activations are high-dimensional vectors (e.g., 4096-dimensional for a 7B model) that participate directly in self-attention. The representational capacity of per-layer, per-head key-value pairs is orders of magnitude larger than a handful of soft token embeddings, directly addressing the "soft-token bottleneck" that the paper identifies as the primary limitation of prior compression methods.

**2. Progressive, fine-grained compression.** Rather than compressing each chunk into an undifferentiated set of representations, Activation Beacon interleaves beacon tokens with fine-grained units within each chunk. A chunk of 1024 tokens can be partitioned into 256 units of size 4, with one beacon token dispatched after each unit. Each beacon token's attention scope is differentiated — the $j$-th beacon token attends to one more interval than the $(j-1)$-th — enabling fine-grained, localized compression. This directly addresses the "coarse compression granularity" limitation of prior methods.

**3. Query-independent compression with no re-encoding.** Activation Beacon compresses the context once, regardless of what queries will be asked later. The compressed beacon activations are accumulated and reused for all subsequent queries. Moreover, because the encoding of chunk $i$ at layer $l$ depends only on the beacon activations of chunk $i-1$ at layer $l-1$ (the same dependency structure as standard autoregressive transformers), there is no need for re-encoding — the accumulated activations are immediately reusable. This addresses both the re-encoding overhead of soft-token methods and the query-dependent recomputation of token-deletion methods, directly targeting the multi-turn efficiency scenario demonstrated in Table 2.

**4. Flexible compression ratios learned during training.** By randomly sampling the compression ratio $\alpha_i$ per chunk during training from $\{2, 4, 8, 16, 32\}$, the model learns to support a wide range of compression configurations without retraining. At inference, a single ratio is selected and applied uniformly across all chunks. Since all beacon tokens share the same token embedding, varying the number of beacon tokens per chunk simply changes the compression ratio — no architectural modification is needed. This directly addresses the "fixed compression ratio" limitation of prior methods.

**The orthogonal positioning.** The paper is careful to note (Section 2) that context compression is orthogonal to KV cache compression along other dimensions (head reduction, quantization, cross-layer sharing). These techniques can be combined — one could use Activation Beacon for token-wise compression while also applying GQA for head compression and KIVI for quantization — making the approach complementary to the broader KV compression landscape rather than competing with it.

**The training efficiency argument.** The paper also distinguishes itself from recurrent memory methods like RMT (Bulatov et al., 2023) that stop gradient back-propagation at a given chunk boundary for training efficiency. Activation Beacon's per-layer dependency structure (encoding of $X'_i$ at layer $l$ only conditions on $X'_{i-1}$ at layer $l-1$) means gradients can naturally flow through all chunks without creating an excessively deep computation graph. This, combined with the fact that the training loss can be computed from all tokens except those in the first chunk (Equation 11), yields what the paper terms "high sample efficiency that maximizes the use of training data" (Section 3.2).

**The data efficiency argument.** A key practical claim is that Activation Beacon can be trained with relatively modest resources: 1B tokens of plain text for pre-training plus 30K fine-tuning samples, all with maximum context length of 20K (Section 3.2, Section 4.1). This is small compared to the pretraining budgets of the backbone models themselves, and the paper emphasizes that the entire training process "can be quickly accomplished" — a practical consideration for researchers and practitioners who want to apply the method to their own models without massive retraining costs.

## 3. Technical Approach

### 3.1 Reader Orientation

Activation Beacon is a **plug-in module** that attaches to an existing, frozen transformer-based LLM to compress long input contexts into a small set of high-dimensional activation vectors before the model generates a response. It solves the problem that self-attention's quadratic cost and the linear growth of the KV cache make long-context inference prohibitively expensive, and it does so by acting like a **learned, progressive distillation pipeline**: the raw text enters in chunks, each chunk is condensed into a handful of "beacon token" activations in a way that preserves fine-grained information, and these compact activations then stand in for the entire context during generation — cutting both FLOPs and memory by factors of up to 8× while keeping task accuracy nearly unchanged.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components, organized as a processing pipeline that transforms a long input text into a compact representation for downstream generation:

1. **Context Partitioning and Beacon Interleaving** — the raw input is split into fixed-size chunks, each chunk is further divided into fine-grained units, and special beacon tokens (`⟨b⟩`) are inserted at the end of each unit according to a target compression ratio.
2. **Beacon-Enhanced Self-Attention** — the LLM's standard attention mechanism is extended with separate projection matrices for beacon tokens, so that during encoding of each chunk, information from raw tokens flows into beacon tokens' keys and values at every layer.
3. **Progressive Accumulation** — after each chunk is encoded, the raw token activations are discarded but the beacon token activations (their per-layer keys and values) are accumulated into a growing cache that represents all preceding chunks.
4. **Compression-Based Next-Token Prediction** — during training and inference, the LLM conditions its generation on the accumulated beacon activations (the compressed context) plus the local tokens of the current chunk, with no separate decoder or re-encoding step.
5. **Training with Random Compression Ratios** — the beacon-specific parameters (projection matrices and token embedding) are learned via auto-regressive language modeling loss, while the compression ratio is randomly sampled per chunk during training to teach flexibility.

Information flows as follows: a long text enters → it is chunked and interleaved with beacon tokens → the first chunk is encoded by the LLM, during which beacon tokens' keys and values absorb information from surrounding raw tokens via attention → raw token activations are discarded → beacon activations are saved → the second chunk is encoded, conditioning on the saved beacon activations from chunk 1 as well as its own tokens → beacon activations from chunk 2 are appended to the accumulator → after all chunks are processed, the final accumulated beacon activations plus the last chunk's raw tokens condition the model's generation, producing output tokens without ever processing the full raw context at once.

### 3.3 Roadmap for the Deep Dive

This section has four sub-sections, presented in an order that builds from physical tokens through attention mechanics to full training — you should understand *what* a beacon token does before seeing *how* it interacts during attention, and understand attention before seeing how the model is optimized end-to-end.

- **First, the Compression Mechanism (Section 3.1):** How raw text is divided into chunks, how beacon tokens are interleaved with fine-grained units, and the progressive encoding loop that accumulates compressed activations while discarding raw ones. This is the physical procedure — the "what happens when."
- **Second, the Encoding and Compression Attention Mechanics (Section 3.1, continued):** The detailed equations for how beacon tokens participate in self-attention — how separate projection matrices isolate their queries/keys/values from raw tokens, how they interact with accumulated beacon activations from prior chunks, and why this enables fine-grained compression.
- **Third, the Efficiency Analysis (Section 3.1, continued):** How the FLOPs savings arise from the interaction between reduced attention computation and increased beacon token overhead, with the formula that predicts when Activation Beacon becomes more efficient than full attention.
- **Fourth, the Learning Method (Section 3.2):** The compression-based auto-regression objective, the gradient flow property that distinguishes Activation Beacon from recurrent memory methods, and the chunk-wise random compression ratio training strategy.

### 3.4 Detailed, Sentence-Based Technical Breakdown

Activation Beacon is fundamentally a **systems paper with a learning component**: its core contribution is the architecture and training recipe that enables a frozen LLM to compress long contexts into compact, query-independent activations without the soft-token bottleneck or re-encoding overhead of prior work. Every design choice flows from the observation that existing compression methods lose too much information because they force complex contexts through a narrow representational bottleneck (a handful of soft tokens), and that the solution is to distribute the compression load across per-layer, per-head key-value vectors whose dimensionality equals the model's hidden size.

---

#### Compression Mechanism: Chunking, Interleaving, and Progressive Encoding

**The fundamental operation** of Activation Beacon is to replace the raw token sequence with a substantially shorter sequence of beacon tokens whose keys and values encapsulate the same information. The raw context is never processed in its entirety at any point; instead, it is consumed in small, independent chunks that are incrementally compressed and then discarded.

**Step 1 — Partition into chunks (Equation 1).** Given an input context $X = [x_1, \ldots, x_n]$ whose length $n$ may far exceed the backbone LLM's native context window $N$ (e.g., $n = 128$K while $N = 4$K or $32$K), the text is first divided into equal-sized chunks of length $w$:

$$[x_1, \ldots, x_n] \xrightarrow{\text{Partition}} [X_1, \ldots, X_{\lceil n/w \rceil}], \quad X_i = [x_{(i-1)w+1}, \ldots, x_{iw}] = [x^i_1, \ldots, x^i_w].$$

where $w$ is the chunk size — 1024 for Llama-2-7B and 2048 for Qwen-2-7B — and $\lceil n/w \rceil$ is the number of chunks. The last chunk may be shorter than $w$ (this edge case is noted as omitted for simplicity in the paper).

**Step 2 — Determine compression ratio per chunk.** For each chunk $X_i$, a compression ratio $\alpha_i$ is chosen such that $w$ is evenly divisible by $\alpha_i$. This ratio determines how many raw tokens each beacon token will be responsible for summarizing: with $\alpha_i = 8$, each beacon token condenses 8 raw tokens. The number of beacon tokens allocated to chunk $i$ is $k_i = w / \alpha_i$, meaning a chunk of 1024 tokens with $\alpha_i = 8$ receives $k_i = 128$ beacon tokens.

**Step 3 — Split into fine-grained units and interleave beacon tokens (Equation 2).** The chunk $X_i$ is split into $k_i$ contiguous units of size $\alpha_i$, and a beacon token is inserted at the end of every unit:

$$X_i \xrightarrow{\text{Interleave } B_i} X'_i = [x^i_1, \ldots, x^i_{\alpha_i}, \langle b \rangle^i_1, \ldots, x^i_{w-\alpha_i+1}, \ldots, x^i_w, \langle b \rangle^i_{k_i}].$$

where $B_i = [\langle b \rangle^i_1, \ldots, \langle b \rangle^i_{k_i}]$ is the group of beacon tokens for chunk $i$, and all beacon tokens share the same token embedding $e_{\langle b \rangle}$. The interleaving is crucial: each beacon token $\langle b \rangle^i_j$ is positioned immediately after the $j$-th unit of raw tokens, which gives it a differentiated attention scope — $\langle b \rangle^i_j$ can attend to one more unit of context than $\langle b \rangle^i_{j-1}$ (because of causal attention, it sees all tokens up to and including its own position, which covers $j$ units). This is what the paper means by "fine-grained compression": different beacon tokens specialize in different local regions of the chunk, rather than all trying to summarize the entire chunk uniformly.

**Step 4 — Progressive encoding loop (Equation 3).** The chunks are fed into the LLM one at a time. Before encoding chunk $i$, the model has already accumulated the beacon token activations (keys and values at every layer) from all previous chunks $X'_{<i}$. The input to the LLM for chunk $i$ is a concatenation of accumulated beacon activations (which serve as a compressed proxy for $X_{<i}$) and the current chunk's interleaved token sequence $X'_i$:

$$\text{LLM}\left( \underbrace{\langle b \rangle^1_1, \ldots, \langle b \rangle^{i-1}_{k_{i-1}}}_{\text{accumulated beacon activations from } X'_{<i}}, \underbrace{x^i_1, \ldots, x^i_{\alpha_i}, \langle b \rangle^i_1, \ldots, x^i_{w-\alpha_i+1}, \ldots, x^i_w, \langle b \rangle^i_{k_i}}_{\text{current chunk } X'_i} \right).$$

This is the key structural property that distinguishes Activation Beacon from recurrent memory methods like AutoCompressor and ICAE: the encoding of $X'_i$ at layer $l$ depends only on the outputs of $X'_{i-1}$ at layer $l-1$ (the standard per-layer autoregressive structure), not on the final-layer output of $X'_{i-1}$. This means there is no re-encoding bottleneck — the accumulated beacon activations are ready to use immediately without recomputation.

**Step 5 — Discard raw, accumulate beacon.** After $X'_i$ is fully encoded through all layers of the LLM, the activations (keys and values) of all raw tokens $X_i$ are discarded — they are not needed for future chunks. The keys and values of the beacon tokens $B_i$, however, are appended to the accumulator: $K_{ac} \leftarrow [K_{ac}; K_b]$ and $V_{ac} \leftarrow [V_{ac}; V_b]$ (Equation 8). These accumulated beacon activations will serve as the prefix context when encoding $X'_{i+1}$.

**Step 6 — Generate from compressed context.** After all chunks are processed, the model conditions its next-token prediction on the final accumulated beacon activations (representing all chunks) plus the raw tokens of the last chunk $X'_{\lceil n/w \rceil}$. Generation proceeds autoregressively from the hidden state of the last input token — exactly as it would in a standard LLM, except that the preceding "context" is a mixture of compressed beacon activations (for earlier chunks) and raw tokens (for the most recent chunk). There is no separate decoder, no re-encoding of soft tokens, and no architectural change to the generation process.

**Why chunk-wise progressive encoding over "all-at-once"?** If the entire context were compressed at once (as in Gisting), the input length would be capped at the LLM's built-in context window $N$, because the model must process all raw tokens together before compression occurs. Progressive chunk-by-chunk encoding decouples the compression window (the chunk size $w$, which is small — 1024 or 2048) from the total context length (which can be arbitrarily large). The model never sees more than $w + \text{(accumulated beacon tokens)}$ tokens at once, and the accumulated beacon tokens are always fewer than the raw tokens they replace (by a factor of $\alpha$), so the effective sequence length grows sub-linearly with the total context length.

**Why fine-grained interleaving over appending all beacon tokens at the end?** The paper empirically studies this in the ablation (Section 4.6, Table 4) and finds a substantial drop in compression quality: Single-Doc QA accuracy falls from 40.5 to 35.2 when all beacon tokens are placed at the end of the chunk rather than interleaved. The reason, which the paper explains conceptually, is that interleaving gives each beacon token a differentiated attention scope — $\langle b \rangle^i_j$ attends to units 1 through $j$ — so different beacon tokens are responsible for different local contexts. When all beacon tokens are at the end, they all have the identical attention scope (the entire chunk), so they redundantly encode the same information and fail to capture differentiated, fine-grained detail.

#### Encoding and Compression: The Attention Mechanics (Equations 4–8)

The heart of Activation Beacon is the modification to self-attention that enables beacon tokens to distill information from raw tokens while keeping the two token types' representations from interfering with each other. The paper reuses all other LLM modules (MLP, LayerNorm, output projection) unchanged.

**Hidden state extraction (Equation 4).** Let $D$ be the LLM's hidden size (e.g., 4096 for a 7B model), and let $H \in \mathbb{R}^{(w + k_i) \times D}$ be the input hidden states to a self-attention layer for the current chunk $X'_i$ (which contains $w$ raw tokens and $k_i$ beacon tokens). The indices of raw and beacon tokens are separated:

$$I_r = \{j \mid x^i_j \neq \langle b \rangle\}, \quad I_b = \{j \mid x^i_j = \langle b \rangle\}; \quad H_r = H[I_r], \quad H_b = H[I_b].$$

where $I_r$ indexes all positions holding real text tokens, and $I_b$ indexes all positions holding beacon tokens. $H_r$ has shape $(w, D)$ and $H_b$ has shape $(k_i, D)$.

**Separate projections for beacon tokens (Equation 5).** This is the critical architectural addition. While raw tokens use the LLM's original query/key/value projection matrices $W^r_Q, W^r_K, W^r_V$, beacon tokens use newly introduced, separately learned matrices $W^b_Q, W^b_K, W^b_V$:

$$\begin{aligned} Q_r &= W^r_Q H_r, & K_r &= W^r_K H_r, & V_r &= W^r_V H_r, \\ Q_b &= W^b_Q H_b, & K_b &= W^b_K H_b, & V_b &= W^b_V H_b. \end{aligned}$$

where each $W^b_* \in \mathbb{R}^{D \times D}$ is a learnable parameter matrix, one per attention head per layer (following the standard multi-head attention convention). These matrices are the only parameters that Activation Beacon adds to the LLM, aside from the beacon token embedding $e_{\langle b \rangle} \in \mathbb{R}^D$. All $W^r_*$ matrices are frozen — they are part of the backbone LLM and never updated.

**Why separate projection matrices?** If beacon tokens reused the raw token projections, the model would have no way to differentiate between "this is a real token whose meaning I should extract" and "this is a beacon token whose job is to act as a memory buffer." The separate matrices $W^b_*$ allow the beacon tokens' queries, keys, and values to be learned from scratch for the specific purpose of information distillation and retrieval, without interfering with the LLM's carefully trained representations for natural language tokens (which remain frozen and intact). This is what makes Activation Beacon a "plug-in" — it adds capacity without distorting existing capacity.

**Reconstructing the full Q, K, V matrices (Equation 6).** After computing raw and beacon projections separately, they are scattered back into the original token order to form the full query, key, and value matrices $Q, K, V \in \mathbb{R}^{(w + k_i) \times D}$:

$$Q[I_r] = Q_r, \quad Q[I_b] = Q_b; \quad K[I_r] = K_r, \quad K[I_b] = K_b; \quad V[I_r] = V_r, \quad V[I_b] = V_b.$$

This scattering ensures that the subsequent attention computation respects the original token ordering — beacon tokens are positioned after the raw tokens they summarize, which affects their causal attention scope as designed.

**Attention with accumulated beacon activations (Equation 7).** The standard scaled dot-product attention is computed, but the key and value matrices are augmented by prepending the accumulated beacon activations $K_{ac}$ and $V_{ac}$ from all previous chunks:

$$A = \text{softmax}\left( \frac{\text{mask}\left( Q \{K_{ac}; K\}^T \right)}{\sqrt{D}} \right), \quad V = A \{V_{ac}; V\}.$$

where $K_{ac}, V_{ac} \in \mathbb{R}^{m_{i-1} \times D}$ are the concatenated keys and values of all beacon tokens from chunks $1$ through $i-1$, with $m_{i-1} = \sum_{j=1}^{i-1} k_j$ being the total number of accumulated beacon tokens so far. The curly braces with semicolons, $\{\cdot ; \cdot\}$, denote matrix concatenation along the row dimension.

**What this computes, operationally:** Each token in the current chunk $X'_i$ (whether raw or beacon) computes its query $q$, then computes attention scores against all keys in $\{K_{ac}; K\}$ — that is, against (a) every accumulated beacon token from all previous chunks, and (b) every token in the current chunk (causally masked so that token $j$ only attends to tokens $\leq j$). The weighted sum of the corresponding values yields the attention output.

**The role of the causal mask:** The mask enforces that tokens in $X'_i$ cannot attend to future tokens within the same chunk (standard causal attention), but *can* attend to all accumulated beacon tokens from previous chunks without restriction, because those represent past context that should be fully visible. The relative position encoding uses the absolute positions: queries in chunk $i$ are assigned positions $[m_{i-1}, \ldots, m_{i-1} + w + k_i - 1]$ and keys are assigned positions $[0, \ldots, m_{i-1} + w + k_i - 1]$, so that each new token sees all prior accumulated beacon tokens as "earlier" and the current chunk's tokens as ordered by their interleaved positions.

**The information flow during encoding of chunk $X'_i$:** For a raw token $x^i_j$ in the chunk, its query attends to:
- All accumulated beacon tokens from chunks $1$ through $i-1$ (the compressed history) — this gives it access to prior context in compact form.
- All preceding raw tokens in the current chunk — this gives it local context within the chunk.
- All beacon tokens in the current chunk that appear at or before its position — these beacon tokens are themselves being populated with information, so this is a form of within-chunk interaction.

For a beacon token $\langle b \rangle^i_j$ in the chunk, its query attends to:
- The same accumulated beacon tokens from prior chunks (compressed history).
- All raw tokens up to its position — which includes all units $1$ through $j$ of the current chunk. This is the distillation step: the beacon token "reads" the raw tokens it is responsible for summarizing and, through the action of the $W^b_V$ projection and the softmax-weighted value aggregation, encodes their information into its own value vector $V_b[j]$.

**The accumulation step (Equation 8).** After self-attention completes for all layers on $X'_i$, the beacon tokens' keys and values at every layer — which now contain distilled information about the raw tokens they attended to — are appended to the running accumulator:

$$K_{ac} \leftarrow \{K_{ac}; K_b\}, \quad V_{ac} \leftarrow \{V_{ac}; V_b\}.$$

The raw tokens' keys and values $K_r, V_r$ are discarded. What remains in GPU memory after all chunks are processed is only the $m_{\lceil n/w \rceil} = \sum_{i} k_i$ beacon tokens' keys and values across all layers and heads — which is exactly $n / \alpha$ tokens' worth of KV cache, an $\alpha \times$ reduction.

**How does this achieve fine-grained compression?** The progressive interleaving means that $\langle b \rangle^i_1$ summarizes units $1$ (raw tokens $1$ through $\alpha_i$), $\langle b \rangle^i_2$ summarizes units $1$ and $2$ (raw tokens $1$ through $2\alpha_i$), and so on. Because of causal attention, each beacon token's keys and values encode a progressively larger prefix of the chunk. This is not merely a theoretical property — it means that when a later chunk or the generation phase queries these beacon activations, it can attend to specific beacon tokens that cover the relevant region of the prior context. If all beacon tokens were at the end with identical attention scopes, this differentiated prefix structure would be lost, which the paper's ablation confirms degrades performance.

**Relative position encoding detail.** The paper specifies that rotary position embeddings (RoPE) are applied using the absolute token positions in the accumulated sequence: queries in $X'_i$ use positions $[m_{i-1}, \ldots, m_{i-1} + w + k_i - 1]$ and keys use positions $[0, \ldots, m_{i-1} + w + k_i - 1]$. This means that tokens in later chunks see the accumulated beacon tokens as "very far in the past" in terms of position index — but the authors hypothesize (and the strong NIAH results confirm) that the model learns to use the content-based attention patterns (via the learned $W^b_K, W^b_Q$ matrices) rather than relying on position-based proximity to retrieve information from compressed context.

#### Efficiency Analysis: When and Why Activation Beacon Saves Computation

The paper provides a FLOPs model (Equation 9) that explains exactly how Activation Beacon trades off reduced attention computation against increased computation from the inserted beacon tokens.

**The full-attention baseline FLOPs.** For a standard transformer with input sequence length $s$ and KV cache length $s_{\text{pst}}$ (the number of prior tokens' keys and values already cached), the forward FLOPs decomposes as:

$$\text{FLOPs} = F^{\text{Att}}(s, s_{\text{pst}}) + F^{\text{Oth}}(s).$$

$F^{\text{Att}}$ is the FLOPs due to self-attention (computing QKV projections, attention scores, softmax, value aggregation, and output projection), and $F^{\text{Oth}}$ is the FLOPs due to all other modules (MLP up/gate/down projections, layer norm, and final LM head projection). Both increase with $s$ because every additional token requires its own QKV projections, attention computation, and MLP processing.

**The beaconed model FLOPs (Equation 10).** For Activation Beacon, the total FLOPs is the sum over all chunks. For the $i$-th chunk, the LLM processes $w + k_i$ tokens (the $w$ raw tokens plus the $k_i$ interleaved beacon tokens), and the KV cache contains the $m_{i-1}$ accumulated beacon tokens from prior chunks:

$$\text{FLOPs}_{\text{bcn}} = \sum_{i=1}^{\lceil n/w \rceil} \left[ F^{\text{Att}}\left( \frac{(\alpha_i + 1)w}{\alpha_i}, \frac{(i-1)w}{\alpha_i} \right) + F^{\text{Oth}}\left( n + \lceil \frac{n}{\alpha} \rceil \right) \right].$$

where $\alpha$ is the average compression ratio, and we note that $k_i = w / \alpha_i$, so the number of tokens per chunk (raw + beacon) is $w + w/\alpha_i = (\alpha_i + 1)w / \alpha_i$.

**Breaking this down:** For each chunk $i$, the attention computation $F^{\text{Att}}$ operates on:
- **Current tokens** $s = (\alpha_i + 1)w / \alpha_i$: the $w$ raw tokens plus the $w/\alpha_i$ interleaved beacon tokens.
- **Cached tokens** $s_{\text{pst}} = (i-1)w / \alpha_i$: the accumulated beacon tokens from the first $i-1$ chunks (each chunk $j$ contributed $w / \alpha_j$ beacon tokens; the paper simplifies by assuming uniform $\alpha$, giving $(i-1)w/\alpha$ per chunk).

The attention cost for this chunk is therefore quadratic in the *local* sequence length (raw + beacon tokens within the chunk) plus cross-attention between these tokens and the accumulated beacon tokens. Since the local sequence length $(\alpha_i + 1)w / \alpha_i$ is only slightly larger than $w$ (e.g., with $w = 1024$ and $\alpha = 8$, it is $1024 + 128 = 1152$ tokens), the quadratic term is small regardless of total context length. The total context length $n$ appears only in the number of chunks $\lceil n/w \rceil$, making the attention FLOPs grow linearly with $n$, not quadratically.

The $F^{\text{Oth}}$ term, however, processes **all raw tokens and all beacon tokens** across all chunks: $n$ raw tokens plus $\lceil n/\alpha \rceil$ beacon tokens total. This grows linearly with $n$ but with a slight overhead (the additional beacon token processing). The key insight is that $F^{\text{Att}}$ dominates at long sequence lengths (because it is asymptotically quadratic for full attention), so reducing its growth from quadratic to linear yields net savings once context length exceeds a crossover point.

**The crossover point visualized (Figure 3).** The paper plots the FLOPs curves for three models (Llama-2-7B, Qwen-2-7B, Qwen-2-72B) at context lengths from 4K to 256K, comparing full attention against Activation Beacon with $\alpha = 2, 4, 8$. The curves show:
- At 4K context, the FLOPs are similar — the beacon overhead roughly cancels the attention savings.
- As context grows, the full attention FLOPs accelerate upward (quadratic), while beacon FLOPs grow much more slowly. At 256K, Activation Beacon (×8) achieves roughly a 4× reduction in total FLOPs for both 7B models, and a similar proportional reduction for the 72B model (Figure 3C).
- Higher compression ratios yield greater savings but at the cost of potentially lower accuracy — the paper recommends ×8 as the sweet spot.

**The practical implication (latency, Section 4.3, Table 2).** At 128K context, Qwen-2-7B with Activation Beacon (×8) achieves approximately 2× faster end-to-end latency than full attention (2.445 seconds vs. 4.399 seconds for the first turn in the Multi-Needle experiment). This acceleration compounds across multi-turn interactions because the compression is query-independent: once computed, the beacon activations are reused for all subsequent questions about the same context. At three turns, Activation Beacon provides 2.1× speedup over Full-FT (2.981 seconds vs. 6.153 seconds) and 9.3× speedup over LongLLMLingua (27.751 seconds), which must re-compress for each question.

**Memory reduction.** The KV cache size is reduced by a factor of $\alpha$ because only the beacon tokens' keys and values are kept — not the raw tokens'. For $\alpha = 8$, this is an 8× reduction in KV cache memory, which is critical for fitting long-context models into GPU memory budgets.

#### Learning Method: Compression-Based Auto-Regression

Activation Beacon is trained to optimize the quality of generation when conditioned on the compressed context. All of the backbone LLM's parameters $\Theta$ remain frozen; only the beacon-specific parameters $\Theta_b$ are updated.

**The training objective (Equation 11).** The model is trained to predict each raw token in chunks $2$ through $\lceil N/w \rceil$, conditioned on the accumulated beacon activations from all prior chunks plus the preceding raw tokens within the current chunk:

$$\min_{\Theta_b} \sum_{i=2}^{\lceil N/w \rceil} \sum_{j=1}^{w} \Pr\left( x^i_j \mid \langle b \rangle^1_1, \ldots, \langle b \rangle^{i-1}_{k_{i-1}}, x^i_1, \ldots, x^i_{j-1}; \Theta, \Theta_b \right).$$

where $\Theta_b = \{W^b_Q, W^b_K, W^b_V \text{ at each layer}, e_{\langle b \rangle}\}$ — the projection matrices for beacon tokens at each attention head in each layer, plus the single shared beacon token embedding.

**What this loss computes, operationally:** For each raw token $x^i_j$ in chunks $i \geq 2$, the model produces a probability distribution over the vocabulary given (a) all accumulated beacon activations from chunks 1 through $i-1$ (the compressed prefix) and (b) the raw tokens $1$ through $j-1$ within the current chunk $i$ (the local context). The standard cross-entropy loss against the true next token is minimized. Tokens in the first chunk ($i=1$) are excluded from the loss because they have no compressed prefix to condition on.

**Why this leads to "high sample efficiency":** Every raw token except those in the first chunk contributes a training signal. In a training document of length $L$, this yields $L - w$ training examples (all tokens outside the first chunk), compared to training methods that only compute loss at specific summary points or generation targets. The paper explicitly contrasts this with recurrent memory methods that depend on final-layer outputs of preceding chunks, which makes gradient flow through many chunks expensive.

**Beacon tokens are excluded from the loss.** The labels for all beacon token positions are set to -100 (the standard PyTorch convention for ignored cross-entropy targets). This is because beacon tokens are not meant to be generated or predicted — they are purely instrumental carriers of compressed information. The model learns to use them effectively only through the indirect route of improving prediction accuracy on the raw tokens that follow them.

**No stop gradients — why this matters.** The paper emphasizes that Activation Beacon does **not** stop gradient back-propagation at chunk boundaries, unlike recurrent memory methods such as AutoCompressor and RMT. To understand why, consider the computational graph:

- In AutoCompressor, the encoding of chunk $i$ takes as input the **final-layer** output of chunk $i-1$ (the compressed soft tokens). This creates a deep sequential dependency: to compute the gradient for chunk $i-1$, you must backpropagate through chunk $i$, which depends on chunk $i+1$, and so on. The depth of the computation graph grows linearly with the number of chunks, making training on many chunks expensive. To mitigate this, prior work stops gradients after a fixed number of chunks — trading off the ability to learn long-range compression for training feasibility.

- In Activation Beacon, the encoding of chunk $i$ at layer $l$ depends only on the **key-value activations** of chunk $i-1$ at layer $l-1$ — which is the same dependency structure as a standard autoregressive transformer processing a long sequence. There is no cross-layer feedback loop: layer $l$ of chunk $i$ depends on layer $l-1$ of chunk $i-1$, but layer $l-1$ of chunk $i-1$ is already computed and fixed by the time layer $l$ of chunk $i$ runs. The gradient flow is natural — it propagates through the cached keys and values of beacon tokens without creating an unbounded-depth computation graph, because the chain of dependencies is per-layer rather than end-to-end.

**Why this property holds:** The attention computation for token $t$ in chunk $i$ involves $Q_t \cdot K_{\text{past}}^T$, where $K_{\text{past}}$ includes the accumulated beacon keys. These keys were computed from the previous chunk's hidden states at the **same layer**. So the gradient flows from the loss at token $t$ → attention output → values $V_{\text{past}}$ (which are fixed and don't require gradient through their computation) and attention weights → queries $Q_t$ and keys $K_{\text{past}}$. The key insight is that gradients to $K_{\text{past}}$ flow back to the parameters that produced those keys — the $W^b_K$ matrices — but do **not** require re-running the full forward pass of previous chunks, because the keys themselves are cached and the gradient through them is well-defined.

This is stated explicitly in the paper: "Activation Beacon only depends on the previous-layer outputs of preceding chunks (the encoding of $X'_i$ at layer $l$ only conditions on the results of $X'_{i-1}$ at layer $l-1$), which is the same as any auto-regressive LLMs. Thus, the gradients can naturally flow through all chunks to optimize the compression effect over long contexts."

**Chunk-wise random compression ratio training.** During training, the compression ratio $\alpha_i$ for each chunk $i$ is randomly sampled from the set $\{2, 4, 8, 16, 32\}$. The paper emphasizes that this is **chunk-wise**, not instance-wise — within a single training document, different chunks may have different compression ratios. For example, a document with 4 chunks might use $\alpha = [2, 8, 4, 16]$. At inference time, a single compression ratio is chosen uniformly across all chunks.

**Why chunk-wise?** The ablation in Section 4.6 (Table 4) shows that chunk-wise random sampling yields 40.5 Single-Doc accuracy versus 37.7 for instance-wise sampling (where one ratio is sampled for the entire training instance). The paper hypothesizes that chunk-wise variation teaches the model more robust compression because it learns to extract information at multiple granularities within a single forward pass, and must attend appropriately to accumulated beacon tokens that may have been compressed at different ratios in different chunks. Instance-wise sampling, by contrast, only exposes the model to one granularity per training example, producing less flexible representations.

**Why train at multiple ratios rather than a fixed one?** The motivation is deployment flexibility. A model trained at a fixed $\alpha = 8$ can only be used with $\alpha = 8$ — changing the compression ratio would change the number of beacon tokens per chunk, which changes the attention pattern, and the model would have no training signal for the new pattern. By training with $\alpha \in \{2, 4, 8, 16, 32\}$, the model learns to handle the full range, and at inference time the user selects one ratio based on their accuracy-efficiency tradeoff. Because all beacon tokens share the same embedding $e_{\langle b \rangle}$, varying $\alpha$ simply changes how many beacon tokens are inserted per chunk — no architectural weight changes are needed.

**Training data and hyperparameters (Section 4.1).** The training proceeds in two stages:

1. **Pre-training:** 1 billion tokens sampled from RedPajama, with `<eos>` appended to the end of every document, and documents shorter than 2400 or longer than 20,480 tokens filtered out. The maximum context length during pre-training is 20K.

2. **Fine-tuning:** 30K samples from LongAlpaca (long-context QA and summarization), BookSum (chapter-level book summarization), and a synthesized QA dataset (16K QA instances generated by GPT-3.5-turbo from books and papers, where segments of up to 4096 tokens are concatenated and 4 question-answer pairs per segment are generated). All fine-tuning data is formatted as multi-turn conversations and capped at 20K context length. To mitigate forgetting of pre-training knowledge, 5000 pre-training samples are also included.

Hyperparameters: batch size 8, learning rate $5 \times 10^{-5}$ for pre-training and $1 \times 10^{-5}$ for fine-tuning, with linear decay and no warmup. The LLM's original parameters are frozen throughout both stages.

**Implementation details.** The chunk size $w$ is 1024 for Llama-2-7B and 2048 for Qwen-2-7B. FlashAttention-2 is used to accelerate attention computation. All experiments use the HuggingFace framework on a single 8×A800 (80G) machine.

**The implicit design choice: frozen backbone vs. full fine-tuning.** The paper freezes all of the LLM's original parameters and only trains the beacon-specific additions ($W^b_Q, W^b_K, W^b_V$ at each layer, plus $e_{\langle b \rangle}$). This has two consequences:
- **Preservation of short-context capabilities:** Because the LLM's original parameters are untouched, the model's performance on tasks that don't require long contexts is nearly identical to the original (Table 3: Llama-2-7B MMLU drops only from 47.5 to 46.6; Qwen-2-7B BoolQ is unchanged at 87.1 vs. 87.2). Full fine-tuning would risk catastrophic forgetting.
- **Parameter efficiency:** Only a small fraction of the total parameters are trained. For a 7B model with 32 layers, 32 attention heads, and hidden size 4096, the beacon parameters amount to $32 \times 32 \times 3 \times (4096 \times 4096)$ (the projection matrices) plus 4096 (the embedding) — roughly 0.5% of the backbone model's parameters, which makes training fast and accessible.
- **Transferability:** The frozen backbone means the same beacon parameters could, in principle, be trained once and plugged into different instances of the same architecture — though the paper does not explore this cross-model transfer explicitly.

## 4. Key Insights and Innovations

### Innovation 1: The Soft-Token Bottleneck Is the Primary Failure Mode of Prior Context Compression

This paper makes a **diagnostic contribution** that reframes *why* prior context compression methods fail on long contexts. The dominant paradigm before Activation Beacon — exemplified by ICAE (Ge et al., 2024), AutoCompressor (Chevalier et al., 2023), and Gisting (Mu et al., 2023) — was to summarize a chunk of text into a small number of learnable soft tokens (typically 4–16) whose embeddings would then condition subsequent processing. The implicit assumption was that a handful of high-capacity vector representations could adequately encapsulate the semantic content of hundreds or thousands of raw tokens, much as a dense passage retriever compresses a document into a single embedding for similarity search.

Activation Beacon diagnoses this assumption as **the central bottleneck**. The paper's empirical evidence is stark: when AutoCompressor and ICAE are trained with the same data and evaluated on LongBench (Table 1), they achieve 12.9% and 19.5% on single-document QA respectively, compared to 34.8% for the uncompressed baseline and 34.9% for Activation Beacon. This is not a marginal degradation — it represents near-total information loss, where the compressed representations retain almost none of the detail needed for question answering. The paper's conceptual contribution is to identify *why*: a small set of soft token embeddings (even when repeated across layers via the transformer's depth) has representational capacity bounded by the dimensionality of the embedding space — typically the model's hidden size (e.g., 4096 dimensions) — multiplied by the number of soft tokens. For 16 soft tokens in a 4096-dimensional model, this is 65,536 scalar values trying to encode the entirety of a 1024-token chunk's information. The compression ratio in information-theoretic terms is enormous, and critical details are inevitably lost.

The reframing this enables: **the compression bottleneck is not about the *mechanism* of compression (chunking, recurrence, attention patterns) but about the *representational medium* into which compression occurs**. By shifting from soft token embeddings to per-layer, per-head key-value activation vectors, Activation Beacon increases the representational capacity by orders of magnitude. Each beacon token at each layer contributes $D$ dimensions for keys and $D$ for values (2 × 4096 for a 7B model), and there are $H$ attention heads, each with its own key-value subspace. Across all layers and heads, the effective capacity for encoding a chunk's information is the sum of all beacon token key-value dimensions, which scales with the model's total parameter count rather than being capped at a single embedding vector. This is the **fundamental insight** — not a new compression algorithm, but a diagnosis that the field was using the wrong data structure for the task.

This is a **fundamental shift** rather than an incremental refinement. It changes the question from "how can we make soft tokens work better?" to "what representation medium has sufficient capacity for the information density of long contexts, and how do we populate it?" The answer — per-layer key-value activations — is available in every transformer by construction, which is what makes the solution elegant: it exploits existing architectural capacity rather than adding a separate compression module.

---

### Innovation 2: Progressive, Fine-Grained Compression Reconceptualizes "Context" as a Sequence of Differentiated Local Summaries

Before Activation Beacon, chunk-based compression methods treated each chunk as an atomic unit: compress it into a uniform representation, then feed that representation forward. ICAE uses a fixed set of summary tokens positioned at the start of the next chunk's encoding. AutoCompressor feeds the compressed representation as input to the next chunk. In both cases, the compression is **coarse-grained** — every part of the chunk receives the same treatment, and the resulting representation is an undifferentiated summary.

Activation Beacon introduces a **fine-grained compression paradigm** where different beacon tokens within the same chunk have **differentiated attention scopes** and therefore specialize in different local regions. The key conceptual move is the interleaving pattern: by placing one beacon token after every $\alpha$ raw tokens, each beacon token $\langle b \rangle^i_j$ sees a progressively larger prefix of the chunk (units 1 through $j$), giving it a distinct "view" of the context. This is not just a mechanical detail — it fundamentally reframes what "compressing a chunk" means. Instead of producing a single summary vector, the model produces a **sequence of overlapping, progressively broader local summaries**, analogous to how a human reader might annotate a long document with marginal notes at different granularities — some capturing specific sentences, others capturing broader themes that span multiple paragraphs.

The empirical significance is demonstrated in the ablation (Section 4.6, Table 4): removing the fine-grained interleaving (placing all beacon tokens at the end of the chunk with identical attention scopes) drops single-document QA accuracy from 40.5 to 35.2 — a substantial 5.3 percentage point degradation that confirms the differentiated scopes are not merely cosmetic but functionally critical.

This is an **incremental but conceptually important refinement** of the chunking approach. It does not change the overall architecture (chunks are still processed sequentially, beacon tokens are still accumulated), but it changes *how information is distributed across the compressed representation*, enabling a form of content-aware allocation where the model can, through training, learn to route different types of information to different beacon positions. The broader implication is that future compression methods should think about compression granularity as a first-class design dimension — not just how many tokens to compress into, but how to distribute representational responsibility across them.

---

### Innovation 3: Query-Independent Compression as a First-Class Deployment Requirement

The paper makes a **pragmatic reframing** that elevates query independence from an implementation convenience to a central design constraint for long-context compression. Prior work on token-deletion methods (LongLLMLingua, SnapKV) had accepted query dependence as necessary: to compress effectively, you need to know what will be asked, because importance is defined relative to the query. This makes intuitive sense — if you're looking for a specific fact in a document, you'd keep tokens related to that fact and discard others. The field had tacitly assumed this was the price of aggressive compression.

Activation Beacon challenges this assumption by demonstrating that **query-independent compression can match query-dependent methods in accuracy while being dramatically more efficient in multi-turn scenarios**. Table 2 is the key evidence: in the Multi-Needle-in-a-Haystack experiment at 128K context with three conversational turns, Activation Beacon achieves 9.10 accuracy (matching the uncompressed baseline's 9.20) with 2.981 seconds of latency, while SnapKV requires 10.659 seconds (3.6× slower) and LongLLMLingua requires 27.751 seconds (9.3× slower). The accuracy is essentially identical; the efficiency gap is enormous and compounds with each additional turn.

The conceptual contribution is recognizing that **query dependence creates a structural inefficiency that limits deployment viability independently of compression quality**. In real-world multi-turn scenarios — a user asking multiple questions about a long document, a customer support agent referencing a policy manual across multiple user queries, a researcher iteratively querying a scientific paper — re-compressing the entire context for each new question makes the compression overhead dominate the total cost. The paper implicitly argues that compression should be evaluated not just by the accuracy-efficiency tradeoff for a single query, but by the **amortized cost over the full interaction lifecycle**.

This is a **fundamental reframing** of the compression evaluation criterion. Prior work had optimized for the single-query case, treating multi-turn efficiency as an afterthought. Activation Beacon inverts this: it makes query independence a first-class architectural property (because the compression depends only on the context, never on the query), and then shows that this constraint does not force a meaningful accuracy penalty. The implication for future research is that compression methods should report multi-turn latency alongside single-turn accuracy, and that query independence should be prioritized unless there is a clear accuracy advantage to query dependence that cannot be recovered by other means.

---

### Innovation 4: Chunk-Wise Random Compression Ratio Training as a General Strategy for Deployment Flexibility

This is a **training methodology innovation** with implications beyond this specific architecture. Most compression methods are trained with a fixed compression ratio — 4 soft tokens per segment, 50% token retention, etc. Changing the compression ratio at inference time requires either retraining or accepting degraded performance because the model has never seen the new attention patterns that result from a different number of compression tokens.

Activation Beacon introduces **chunk-wise random sampling** of the compression ratio during training: within a single training document, each chunk independently samples $\alpha$ from $\{2, 4, 8, 16, 32\}$. This means the model learns to compress at multiple granularities and, crucially, to condition its generation on accumulated beacon activations that may have been compressed at different ratios in different chunks — a heterogeneous compressed prefix. The result, demonstrated in Figure 5, is a single model that can be deployed at any compression ratio in the trained range without retraining, maintaining top accuracy across ratios.

The conceptual contribution is recognizing that **deployment flexibility is a training problem, not an architecture problem**. Because all beacon tokens share the same embedding and the same projection matrices, varying the compression ratio simply changes how many beacon tokens are inserted per chunk — the architecture is identical regardless of $\alpha$. The only thing that prevents flexibility is that the model hasn't seen certain ratios during training. By exposing the model to the full range during training (and, critically, doing so chunk-wise rather than instance-wise, which the ablation in Table 4 shows is more effective), the flexibility emerges naturally from the optimization process.

This is an **incremental but broadly applicable contribution**. The specific technique (chunk-wise random ratio sampling) is tied to the beacon token architecture, but the underlying principle — expose the model to diverse compression configurations during training so it learns a continuum rather than a point solution — could be applied to any compression method where the compression hyperparameter translates to a change in token counts. For example, a soft-token method could vary the number of summary tokens per segment during training, or a token-deletion method could vary the retention fraction. The paper provides empirical evidence that chunk-wise sampling outperforms instance-wise sampling, suggesting that within-document variation provides a stronger training signal than across-document variation, likely because it forces the model to handle heterogeneous compression rates within a single coherent context.

---

### Innovation 5: The "No Stop Gradients" Property as an Architectural Consequence, Not a Training Trick

Recurrent memory methods for context compression — AutoCompressor, RMT (Bulatov et al., 2023) — must **stop gradient back-propagation** at chunk boundaries to make training computationally feasible. This is because their architectures create a deep sequential dependency: the encoding of chunk $i$ depends on the final-layer output of chunk $i-1$, which depends on chunk $i-2$, and so on. Back-propagating through this chain requires storing intermediate activations for all chunks and flowing gradients through the entire computation graph, which becomes prohibitively expensive as the number of chunks grows. Stopping gradients after a fixed number of chunks is a pragmatic compromise, but it means the model cannot learn long-range compression dependencies beyond the truncation window.

Activation Beacon achieves **natural gradient flow through all chunks without special treatment**, and the paper identifies this as a structural property rather than an optimization trick. The key conceptual move is understanding *why* this property holds: the encoding of $X'_i$ at layer $l$ depends only on the key-value activations of $X'_{i-1}$ at layer $l-1$ (the standard per-layer autoregressive structure), not on any cross-layer feedback from the previous chunk's output. This means the computation graph is no deeper than a standard transformer processing a long sequence — the chain of dependencies is per-layer rather than end-to-end. The paper explicitly contrasts this with prior methods: "Activation Beacon only depends on the previous-layer outputs of preceding chunks... which is the same as any auto-regressive LLMs."

This is a **fundamental architectural insight** with implications for the design of future compression methods. It establishes a design principle: to enable gradient flow through arbitrarily many chunks, structure the compression so that each chunk at layer $l$ depends only on information from the previous chunk at layer $l-1$, never on information that has already passed through higher layers of the previous chunk's processing. This constraint turns what in prior work was a training hack (stop gradients) into a natural property of the architecture, enabling the model to optimize compression quality over the full context length rather than just within a truncated window. The paper doesn't emphasize this as a headline contribution, but it is arguably the architectural insight that makes the rest of the method feasible — without it, training on long documents would be as expensive as in AutoCompressor, and the sample efficiency and rapid training claims (1B pre-training tokens, 30K fine-tuning samples) would not hold.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The primary benchmark is **LongBench** (Bai et al., 2023), a bilingual multi-task benchmark for long-context understanding with 32K maximum context length, covering single-document QA, multi-document QA, summarization, few-shot learning, and code completion. Additionally, **Needle-in-a-Haystack** (NIAH, gkamradt, 2023) tests fine-grained retrieval across context lengths up to 128K+, and **Multi-Needle-in-a-Haystack** (from NeedleBench, Li et al., 2024) evaluates multi-turn retrieval where questions are issued sequentially about the same context. Short-context capabilities are assessed on standard benchmarks: **MMLU** (Hendrycks et al., 2021), **ARC-Challenge** (Bhakthavatsalam et al., 2021), **BoolQ** (Clark et al., 2019), and **GSM8K** (Cobbe et al., 2021).

- **Base model(s).** Activation Beacon is applied to **Llama-2-7B (chat)** and **Qwen-2-7B (instruct)**, with FLOPs analysis also shown for **Qwen-2-72B**. Llama-2-7B is chosen specifically because two critical baselines — AutoCompressor and ICAE — are implemented on Llama-2, enabling direct architectural comparison. Qwen-2-7B is included to demonstrate applicability beyond a single model family and to test behavior at longer context windows (128K native vs. Llama-2's 4K). For the short-context preservation study (Table 3), the exact same backbone models are evaluated with and without Activation Beacon.

- **Metrics.** All accuracy metrics are the standard evaluation protocols for each benchmark: **exact match or task-specific grading** for LongBench; **Needle retrieval accuracy** scored by ChatGPT on a 1–10 scale for NIAH; **retrieval accuracy** (correct needle identification) averaged over 20 runs for Multi-Needle; **accuracy** (multiple-choice or exact match) for MMLU, ARC-C, BoolQ, and GSM8K. Efficiency is measured by **end-to-end latency** in seconds (compression + generation time, Table 2) and **FLOPs** (forward FLOPs estimated analytically via Equations 9–10 and visualized in Figure 3). Memory reduction is reported as the factor of KV cache compression (e.g., 8× reduction when α = 8).

- **Baselines.** The paper compares Activation Beacon against five distinct reference points:
  - **Full**: The original backbone LLM without any compression, limited to its native context window (4K for Llama-2, 32K for Qwen-2) by truncating the middle of longer inputs.
  - **Full-FT**: The backbone LLM fine-tuned on exactly the same training data as Activation Beacon (1B pre-training tokens + 30K fine-tuning samples), operating at its native window size with full attention. This controls for the effect of the training data itself versus the compression mechanism.
  - **AutoCompressor** (Chevalier et al., 2023): A recurrent memory method that compresses each chunk into soft tokens and feeds them as input to the next chunk. Available only for Llama-2.
  - **ICAE** (Ge et al., 2024): An in-context autoencoder that compresses context into a small set of summary tokens. Available only for Llama-2.
  - **LongLLMLingua** (Jiang et al., 2023): A query-dependent token-deletion method that estimates token importance and retains only top-k tokens. Evaluated on both Llama-2 and Qwen-2.
  - **SnapKV** (Li et al., 2024): A query-dependent KV cache compression method that identifies and retains important KV pairs based on attention patterns. Evaluated on both Llama-2 and Qwen-2.
  
  For fair comparison, AutoCompressor and ICAE's official checkpoints are fine-tuned using the same training data as Activation Beacon. LongLLMLingua and SnapKV are used with their released implementations and default settings.

- **Generation budget / compute accounting.** The paper uses **compression ratio (α)** as the primary unit of compute control, where α = 2, 4, 8, 16, or 32 translates to a corresponding reduction in the number of tokens participating in attention. For FLOPs analysis (Figure 3), exact forward FLOPs are computed using the formulas in Appendix B, accounting for both attention FLOPs (which depend on sequence length quadratically) and other module FLOPs (MLP, layer norm, LM head, which depend linearly on the total number of processed tokens, including beacon tokens). For latency measurements (Table 2), end-to-end wall-clock time is measured for the combined compression step (encoding all chunks into beacon activations) plus generation step (autoregressive decoding from the compressed representation), averaged over 20 runs. The paper does *not* include the cost of beacon-specific parameter training in any efficiency metric — all reported savings are inference-only. For LongBench experiments (Table 1), adaptive compression ratios are used for Llama-2 (×2 for 4K–8K, ×4 for 8K–16K, ×8 for 16K–32K contexts) and uniform ×4 for Qwen-2; for NIAH (Figure 4), the same adaptive scheme is applied.

- **Cross-validation / statistical protocol.** No cross-validation or statistical significance testing is reported. The Multi-Needle experiment repeats 20 times with distinct needle positions, providing a measure of variance for that specific task, but all other results (LongBench, NIAH, short-context benchmarks) are reported as single-run accuracies without confidence intervals or standard deviations. The LongBench test set size is not explicitly specified in the paper (the benchmark itself contains 4,750 test instances across all tasks, but per-task sample sizes vary). This means the reported differences — particularly the claims of "comparable performance to the uncompressed baseline" — cannot be assessed for statistical reliability from the information provided.

### Main Quantitative Results

#### Compression Effectiveness on LongBench (Table 1)

**Headline result:** Activation Beacon achieves compression quality that matches or nearly matches the uncompressed fine-tuned baseline (Full-FT), while dramatically outperforming all prior compression methods by double-digit margins on most tasks.

For **Llama-2-7B**, comparing Activation Beacon (32K context, adaptive compression ratio) against the key baselines on the five LongBench task categories:

|------|-----------|---------------|------------|------|-----------|--------|------|
| Single-Doc | 24.7 | 34.8 | 12.9 | 19.5 | 21.5 | 24.2 | **34.9** |
| Multi-Doc | 22.4 | 27.5 | 16.4 | 19.2 | 18.8 | 22.6 | **27.5** |
| Summ. | 24.6 | 23.2 | 16.3 | 19.5 | 21.7 | 16.3 | **25.0** |
| Few-Shot | 63.2 | 61.8 | 23.8 | 24.8 | 49.5 | 60.1 | **61.4** |
| Code | 57.7 | 57.8 | 39.4 | 27.8 | 53.2 | 57.7 | **57.8** |

Two observations are central to the paper's claims:

**First, the soft-token bottleneck is real and severe.** AutoCompressor and ICAE — both soft-token compression methods — achieve only 12.9% and 19.5% on Single-Doc QA, versus 34.8% for the uncompressed baseline and 34.9% for Activation Beacon. This gap of 15–22 percentage points is not a marginal degradation; it represents near-total loss of the context information needed for question answering. Activation Beacon, by compressing into per-layer key-value activations rather than soft tokens, closes this gap essentially completely — its 34.9% is within rounding error of Full-FT's 34.8%. This validates the paper's central diagnostic claim that the representational medium (activations versus soft tokens) is the decisive factor, not the compression ratio or the training data.

**Second, token-deletion methods degrade at high compression ratios.** LongLLMLingua and SnapKV perform substantially better than soft-token methods but still fall short of Activation Beacon, particularly on tasks requiring integration of information across long spans (Multi-Doc: 18.8% and 22.6% vs. 27.5%; Few-Shot: 49.5% and 60.1% vs. 61.4%). The paper attributes this to the fact that token-deletion methods must discard a large fraction of tokens at high compression ratios (e.g., retaining only 12.5% of tokens for a ×8 effective compression), which can break the coherence of the context and remove tokens that are individually low-attention but collectively important for understanding. Activation Beacon, by contrast, *summarizes* rather than *deletes*, so every part of the input contributes to the compressed representation — no information is irrevocably discarded in the raw form.

The pattern replicates: Activation Beacon outperforms SnapKV and dramatically outperforms LongLLMLingua, while remaining within 0.5–2.7 percentage points of the fine-tuned uncompressed baseline. The gain on Code (66.4 vs. 60.3 for full-attention without fine-tuning, 66.1 for Full-FT) suggests the compression training data and process may provide some incidental benefit beyond pure context preservation — possibly because the fine-tuning data includes code-related tasks from LongAlpaca.

**The Llama-2 vs. Full-FT comparison on Single-Doc** deserves specific attention: the Full baseline (truncated 4K context) achieves only 24.7%, while Activation Beacon (which compresses the full 32K into roughly 4K worth of beacon activations) achieves 34.9%. This gap of 10.2 percentage points is *not* about compression quality — it's about the fact that 4K of truncated context is insufficient for the task. Activation Beacon, by compressing 32K into the equivalent of 4K, effectively extends Llama-2's usable context window by an order of magnitude, bringing in information from tokens 4K–32K that the Full baseline simply never sees. The paper explicitly notes this: "it can be viewed as an efficient approach for context extension."

#### Needle-in-a-Haystack: Fine-Grained Retrieval (Figure 4)

**Headline result:** Activation Beacon accurately retrieves the needle across context lengths up to 128K+ — far exceeding its 20K training length — demonstrating that the compression preserves fine-grained, location-specific information and that the learned compression generalizes to unseen context lengths.

Figure 4 presents heatmaps for Llama-2-7B (panel A) and Qwen-2-7B (panel B), where the x-axis is context length (from ~4K to 32K for Llama-2, from ~4K to 128K for Qwen-2) and the y-axis is depth percent (where in the context the needle is placed, from 0% = beginning to 100% = end). Accuracy is scored 1–10 by ChatGPT evaluating whether the model correctly retrieves the needle fact.

For **Llama-2-7B** with Activation Beacon (adaptive compression ratio): scores of 10 (perfect retrieval) dominate the heatmap, with minor degradation (scores of 7–9) in the 25K–33K range when the needle is placed near the very end of the context (depth 80–100%). The overall pattern shows near-perfect retrieval across almost all context lengths and depths, with only a small cluster of moderate scores in the longest-context, end-of-context region.

For **Qwen-2-7B** with Activation Beacon (adaptive compression ratio): the heatmap shows strong retrieval (scores 7–10) across the full 128K range. A band of lower scores (5–7) appears in the 80K–110K region when the needle is at moderate depth (30–60%), and another at the longest lengths (120K–128K) at shallow depths (0–20%). These are not catastrophic failures — the model still retrieves partial information — but they indicate that extreme context lengths push the compression to its limits, particularly when the needle is in the middle of very long contexts.

**The critical implication:** Activation Beacon's compression is **query-independent** — it has no knowledge of what needle will be queried or where it is located — yet it preserves enough information to accurately retrieve a specific fact from anywhere in the context. This directly addresses the concern that compression might work for "gist-level" tasks (summarization, topic QA) but fail for tasks requiring precise, localized information retrieval. The paper explicitly flags this: "this remarkable performance again validates our tailored compression mechanism and learning method can preserve the fine-grained contextual information."

**The generalization claim:** Activation Beacon is trained only on contexts up to 20K (the maximum training length) but generalizes to 128K for Qwen-2. This is not explained mechanistically — the paper simply reports the result as evidence that the compression learned at 20K transfers. It is worth noting that during training, the model sees compression ratios of 2–32 on 20K contexts, so the number of accumulated beacon tokens it learns to condition on (roughly 20K / α averaged over the ratio distribution) is far fewer than the number it encounters at 128K with ×8 compression (128K / 8 = 16K beacon tokens). The effective "sequence length" of the compressed prefix at 128K is thus ~16K tokens, which is within the range of lengths the model sees during training (20K raw tokens), even though the *uncompressed* context is 6.4× longer. This suggests the generalization is a consequence of the chunk-wise processing — the model never sees raw context longer than chunk size (1024–2048 tokens) regardless of total length, and the accumulated beacon sequence grows sub-linearly.

**Headline result:** In multi-turn conversational settings, Activation Beacon achieves near-lossless accuracy (matching the uncompressed baseline within 0.1–0.15 points) while providing 2.1× speedup over Full-FT at 128K context and 9.3× speedup over LongLLMLingua at three turns.

Table 2 reports accuracy and end-to-end latency (seconds) for Multi-Needle-in-a-Haystack, where 3 needles are inserted at different positions in a fixed context, and the model is asked to retrieve one specific needle in each turn of a multi-turn conversation. All compression methods use ×8 compression ratio.

Activation Beacon's accuracy (9.75, 9.40, 9.05 across three turns) is essentially identical to Full-FT (9.75, 9.45, 9.10). At 128K, the latency advantage becomes substantial: Activation Beacon (2.445s) is 1.8× faster than Full-FT (4.399s) at turn 1, and 2.1× faster at turn 3 (2.981s vs. 6.153s). The multi-turn compounding is even more dramatic when compared to query-dependent methods: LongLLMLingua requires 10.455s at turn 1 and 27.751s at turn 3 — a 9.3× gap versus Activation Beacon. SnapKV starts competitively at turn 1 (3.955s) but degrades to 10.659s at turn 3 (3.6× slower than Activation Beacon), because it must re-estimate token importance for each new query.

**Why the latency compounds for query-dependent methods:** In LongLLMLingua, each turn requires reading the full context (or the compressed context from the previous turn), estimating token importance with respect to the new query, and re-compressing. Since the underlying context is 128K tokens, this importance estimation and re-compression step dominates the total cost. In Activation Beacon, the context is compressed once (during the first turn), and the resulting beacon activations are reused for all subsequent turns with zero recomputation. The paper explicitly frames this as the key architectural advantage: "Activation Beacon is query-independent... which eliminates the need to re-compute the compression results for different input questions."

**AutoCompressor and ICAE performance collapse** on this task despite the authors fine-tuning their checkpoints. AutoCompressor achieves only 1.50–1.60 accuracy and ICAE 2.00–2.15, versus 9.75 for the uncompressed baseline. This is a stronger version of the LongBench finding: the soft-token bottleneck is not just about coarse semantic understanding — it catastrophically fails at fine-grained retrieval where a specific fact must be extracted from a long context. The Multi-Needle task is essentially a stress test of compression fidelity, and soft-token methods fail it entirely.

#### Compression Flexibility Across Ratios and Context Lengths (Figure 5)

**Headline result:** Activation Beacon maintains top accuracy across compression ratios from ×2 to ×16 and context lengths from 1K to 32K, while AutoCompressor and ICAE degrade rapidly at higher ratios and SnapKV cannot compress contexts longer than the LLM's window.

Figure 5 presents three bar charts for Needle-in-a-Haystack accuracy at context lengths of 1K, 4K, and 32K (Llama-2-7B backbone), with compression ratio on the x-axis and accuracy on the y-axis. The bars compare Activation Beacon against AutoCompressor, ICAE, LongLLMLingua, and SnapKV.

At **1K context**: all methods perform well. Activation Beacon, SnapKV, and LongLLMLingua all score between ~9 and 10 across ratios ×2 to ×16. AutoCompressor and ICAE show slight degradation at higher ratios (~8 at ×16 vs. ~10 for the best methods) but the differences are small because 1K is short enough that even aggressive compression is manageable.

At **4K context**: a gap emerges. Activation Beacon and SnapKV remain near-perfect (~9.5–10) across all ratios. LongLLMLingua drops to ~7.5 at ×16. ICAE degrades to ~3 at ×16. AutoCompressor falls to ~2 at ×8 and ~1 at ×16. The paper notes that SnapKV performs on par with Activation Beacon at 4K but fails at longer contexts because it cannot compress inputs exceeding the LLM's window size.

At **32K context**: the gap becomes dramatic. Activation Beacon maintains ~9–10 accuracy across all ratios. SnapKV cannot be evaluated because 32K exceeds Llama-2's 4K window and its token-importance estimation depends on full-context attention. LongLLMLingua operates at 32K but degrades to ~5 accuracy at ×16. ICAE and AutoCompressor collapse to near-zero accuracy at all ratios — even at ×2, ICAE achieves only ~1.5 and AutoCompressor ~0.5. The paper notes this is because both methods depend on soft tokens that cannot encapsulate the complexity of 32K contexts, regardless of compression ratio.

**The flexibility message:** Unlike prior compression methods whose performance degrades sharply as compression ratio increases or context length grows, Activation Beacon's accuracy is nearly flat across the tested range. A single trained model can be deployed at ×2, ×4, ×8, or ×16 compression ratios depending on the accuracy-efficiency requirements of the downstream task, without retraining or architectural modification. The paper's recommendation of ×8 as the "sweet spot" is justified by these results: it achieves near-maximum efficiency (8× KV cache reduction, ~4× FLOPs reduction at long contexts) while maintaining accuracy within measurement error of the uncompressed baseline.

**Headline result:** Activation Beacon causes negligible performance degradation on standard short-context benchmarks, confirming that the frozen backbone strategy preserves the LLM's original capabilities.

| Llama-2-7B | Full | 47.5 | 48.5 | 86.2 | 9.2 |

The maximum degradation is 1.0 point on Qwen-2 MMLU (70.1 → 69.1) and 0.9 on Llama-2 MMLU (47.5 → 46.6). **A subtle point not discussed:** The short-context benchmarks are evaluated *without* any compression — the model processes the short input in its standard (non-beacon) mode. This means these results test whether the *presence of beacon-specific parameters* (which were trained on long-context compression tasks) interferes with standard inference, not whether the compression mechanism itself works on short contexts. The near-identical scores confirm that the beacon parameters are effectively "dormant" when not activated by the presence of beacon tokens in the input, which is the desired property for a plug-in module.

#### FLOPs Analysis Across Scales and Context Lengths (Figure 3)

**Headline result:** Activation Beacon delivers increasing FLOPs savings as context length grows, achieving >4× reduction at 256K context for both 7B models, with the savings pattern consistent across model scales (7B to 72B).

Figure 3 shows three line plots — one for Llama-2-7B, one for Qwen-2-7B, and one for Qwen-2-72B — with context length on the x-axis (4K to 256K) and forward FLOPs (in units of 10⁴ or 10⁵) on the y-axis. Each plot compares Full Attention against Activation Beacon at compression ratios ×2, ×4, and ×8.

For **Llama-2-7B** (panel A): At 4K, all methods have similar FLOPs (~0.2 × 10⁴). By 32K, Full Attention reaches ~1.0 × 10⁴ while Activation Beacon (×8) is at ~0.45 × 10⁴ — approximately 2.2× savings. By 256K, Full Attention reaches ~3.8 × 10⁴, and Activation Beacon (×8) is at ~0.85 × 10⁴ — a 4.5× reduction. The ×4 and ×8 curves are close together, indicating diminishing marginal returns from higher compression ratios in terms of FLOPs (though memory continues to scale linearly with α).

For **Qwen-2-7B** (panel B): The pattern is nearly identical to Llama-2-7B, confirming that the FLOPs savings are architecture-independent at a given model scale. Full Attention reaches ~2.7 × 10⁴ at 256K, and Activation Beacon (×8) reaches ~0.65 × 10⁴ — a 4.2× reduction.

For **Qwen-2-72B** (panel C): The absolute FLOPs are an order of magnitude higher (~1.5 × 10⁵ at 256K for Full Attention vs. ~0.4 × 10⁵ for ×8), but the relative savings follow the same pattern — approximately 3.8× reduction at 256K. This confirms that Activation Beacon's efficiency benefits scale with model size, which is expected because the fraction of FLOPs spent in attention versus other modules is similar across model scales for a given architecture family.

**The crossover point:** At 4K context, the ×8 curve is *above* the Full Attention curve for all three models — meaning Activation Beacon is actually *less* efficient than full attention for very short contexts. This is because the overhead of encoding the additional beacon tokens (which go through MLP, layer norm, etc.) outweighs the attention savings when the context is short and attention FLOPs are small. The crossover occurs somewhere between 4K and 8K (the paper doesn't compute the exact point), after which Activation Beacon becomes increasingly advantageous. This implies a practical deployment guideline: for contexts below ~8K, full attention or a lower compression ratio (×2) is more efficient; for longer contexts, ×8 provides optimal efficiency.

**The gap between ×4 and ×8:** At 256K, Llama-2-7B shows FLOPs of ~1.2 × 10⁴ for ×4 compression and ~0.85 × 10⁴ for ×8 — a further 1.4× reduction for doubling the compression ratio. The diminishing return is because the dominant cost at long contexts shifts from attention (which scales with the square of the number of tokens being attended to) to other modules (which scale linearly). The ×8 compression reduces attention tokens by a factor of 8, but the total number of processed tokens (raw + beacon) is only reduced from n + n/4 to n + n/8 — a much smaller proportional change.

### Ablation Studies and Robustness Checks

**Fine-grained compression (interleaving vs. appending beacon tokens at chunk end):** Removing the fine-grained interleaving and instead placing all beacon tokens at the end of the chunk (giving them identical attention scopes) reduces Single-Doc QA accuracy from 40.5 to 35.2 (Table 4, Qwen-2-7B, ×4 compression, 32K context). This 5.3-point drop (~13% relative reduction) confirms that differentiated attention scopes are functionally important — when all beacon tokens share the same view of the chunk, they redundantly encode the same global information and lose fine-grained detail. This is the largest single-factor ablation effect reported.

**Chunk-wise vs. instance-wise random compression ratio:** Replacing chunk-wise random ratio sampling (each chunk independently draws α from {2,4,8,16,32}) with instance-wise sampling (a single α is drawn for the entire training instance) reduces Single-Doc QA accuracy from 40.5 to 37.7 (Table 4). The 2.8-point gap supports the paper's claim that chunk-wise variation provides a stronger training signal. The likely mechanism: chunk-wise sampling forces the model to attend to accumulated beacon activations that were compressed at different ratios, teaching it to handle heterogeneous compression rates within a single forward pass. Instance-wise sampling never exposes the model to this heterogeneity during training.

**Pre-training vs. fine-tuning ablations:** Removing either training stage substantially reduces performance:
- Without pre-training (fine-tuning only): accuracy drops from 40.5 to 34.9 (Table 4). The 5.6-point gap indicates that the 1B-token pre-training phase on RedPajama is essential for learning basic compression capability — the 30K fine-tuning samples alone are insufficient.
- Without fine-tuning (pre-training only): accuracy drops from 40.5 to 35.5 (Table 4). A 5.0-point gap shows that fine-tuning on long-context task data (LongAlpaca, BookSum, synthetic QA) is equally essential for adapting the generic compression learned during pre-training to downstream task-relevant compression behavior.

The combination of both stages substantially outperforms either alone, indicating complementary roles: pre-training teaches the beacon tokens to act as general-purpose information buffers, while fine-tuning teaches them to preserve task-relevant information for QA, summarization, and retrieval.

**Beacon token projection matrices (implicit ablation via design):** The paper does not report an ablation where beacon tokens reuse the raw token projection matrices (W^r_Q, W^r_K, W^r_V) instead of using separate W^b_* matrices. This is a notable omission — it would directly test whether the separation of projection spaces is necessary or whether the frozen LLM's projections are sufficient when applied to beacon tokens. Given that separate projections are a core architectural claim ("a plug-in module"), demonstrating their necessity would strengthen the paper. The absence of this ablation leaves open the possibility that simply inserting beacon tokens with the standard projections (and training only the beacon token embedding) might achieve similar performance, though the paper's design rationale strongly implies otherwise.

**Uniform vs. adaptive compression ratios:** The paper uses adaptive compression ratios for Llama-2 LongBench experiments (×2 for 4–8K, ×4 for 8–16K, ×8 for 16–32K) and uniform ×4 for Qwen-2. No ablation compares these schemes directly. For NIAH, the adaptive scheme is also used, and the heatmaps show strong performance, but it's unclear whether uniform ×8 (for instance) would produce similar results or whether the adaptive scheme is load-bearing for the strong NIAH results. This is especially relevant because the paper recommends ×8 as a general-purpose setting but evaluates most tasks with adaptive ratios.

**Revision to appendix content (verifier for revision model, ReST optimization):** The paper mentions in Appendix K (Figure 16) an experiment with ReST^EM-optimized revision models that is referenced in the Limitations but not described in the main results. Without the appendix content in the provided paper text, this ablation cannot be assessed. The paper's Appendix structure suggests additional ablations (Appendix J on revision model verifier choice, Appendix K on ReST optimization) that are beyond the scope of what is provably in the text.

### Critical Assessment

**Claim 1: Activation Beacon maintains comparable performance to the uncompressed baseline across various compression configurations, achieving a 2× acceleration in inference time and an 8× reduction of KV cache memory.**

This claim is **supported with important qualifications**.

The LongBench results (Table 1) show Activation Beacon scores within 0–1.5 points of the uncompressed fine-tuned baseline (Full-FT) across most task categories: Single-Doc 34.9 vs. 34.8 for Llama-2, 40.5 vs. 41.0 for Qwen-2; Multi-Doc 27.5 vs. 27.5; Code 57.8 vs. 57.8 for Llama-2, 66.4 vs. 66.1 for Qwen-2. The exception is Qwen-2 Few-Shot, where the gap is 68.4 vs. 68.5 (0.1 point) and Llama-2 Few-Shot is 61.4 vs. 61.8 (0.4 point) — both within what would likely be measurement noise if standard deviations were reported.

However, "comparable" is asserted without statistical testing. The LongBench test sets have varying sizes per task, and a 0.5–1.5 point difference on a subset of 200–500 questions may or may not be statistically significant. The paper does not report confidence intervals, standard deviations, or p-values for any comparison. This is a genuine weakness: the central "comparable to uncompressed" claim rests on point estimates alone, and the reader cannot assess whether the observed gaps are within sampling error.

The 2× acceleration claim is supported by the 128K Multi-Needle experiment (Table 2, Qwen-2-7B: 2.445s vs. 4.399s at turn 1, 2.981s vs. 6.153s at turn 3). The 8× KV cache reduction is a direct consequence of the compression ratio (α = 8) and is stated as a design property. Neither claim requires statistical validation — acceleration and memory are deterministic properties of the architecture at a given compression ratio. However, the 2× acceleration figure is specific to α = 8 at 128K context length and is model-dependent (Figure 3 shows varying FLOPs savings at different context lengths and model scales).

What is **not demonstrated**: the claim that performance is "comparable" at compression ratios other than those used in the LongBench experiments. For Llama-2, LongBench uses adaptive ratios (not a fixed ratio); for NIAH, adaptive ratios are used; for Multi-Needle, ×8 is used. Figure 5 shows strong NIAH accuracy at ×2, ×4, ×8, and ×16 for 32K context, which partially supports the "various compression configurations" claim, but this is only one task (NIAH retrieval) and one context length (32K). The paper does not evaluate LongBench at multiple fixed compression ratios, so the interaction between ratio and task type is unknown.

---

**Claim 2: Activation Beacon generalizes to context lengths far exceeding its 20K training maximum (e.g., 128K).**

This claim is **supported by the NIAH and Multi-Needle results, with a plausible mechanism but incomplete characterization**.

The NIAH heatmaps (Figure 4) show Qwen-2-7B accurately retrieving needles at 128K context, and the Multi-Needle results (Table 2) show near-perfect accuracy at 128K. Since the maximum training length is 20K (as stated in Section 4.1), this constitutes a 6.4× extrapolation in context length — a genuine generalization success.

The mechanism for why this works, as discussed earlier, is architectural: the model never processes raw context longer than chunk size (1024–2048 tokens), so the raw input length is irrelevant to the per-chunk encoding. What matters is the number of accumulated beacon tokens, which grows as n/α. At 128K with α = 8, there are 16K beacon tokens — within the 20K raw-token sequence length the model sees during training, so the attention pattern over beacon tokens is in-distribution. This is a clever property, but the paper does not explicitly analyze whether the beacon-to-beacon attention patterns at 128K inference are genuinely similar to those at 20K training — it simply reports the accuracy and asserts generalization.

What is **not tested**: whether the generalization holds for context lengths substantially beyond 128K (e.g., 256K, 512K) where the number of accumulated beacon tokens would exceed the 20K training length even at ×8 compression. If n/α exceeds the trained sequence length, the beacon-to-beacon attention patterns would go out of distribution, and performance might degrade. The paper's training methodology (random chunk-wise ratios, maximum 20K training length) provides no signal for how the model would behave at, say, 256K with ×8 compression (32K beacon tokens). This is a practical limitation for users who might want to deploy Activation Beacon on models with 256K+ context windows.

---

**Claim 3: The soft-token bottleneck (as in AutoCompressor and ICAE) is the primary failure mode of prior compression methods, and Activation Beacon overcomes it by compressing into activations.**

This claim is **strongly supported by the comparative evidence, though the causal attribution is confounded by training data differences**.

The LongBench results (Table 1) show AutoCompressor at 12.9% and ICAE at 19.5% versus Activation Beacon at 34.9% on Single-Doc QA — gaps of 22.0 and 15.4 points respectively. The Multi-Needle results (Table 2) show even more dramatic gaps: AutoCompressor at 1.50–1.60 and ICAE at 2.00–2.15 versus both Activation Beacon and Full-FT at 9.05–9.75. These are not marginal differences — they represent near-total failure of soft-token methods on these tasks.

However, the paper fine-tunes the official AutoCompressor and ICAE checkpoints on its own training data (1B pre-training tokens + 30K fine-tuning samples) for fair comparison. This means the soft-token methods are evaluated after additional training that they were not originally designed for. The poor performance could reflect either (a) the inherent limitation of soft-token compression, as the paper claims, or (b) incompatibility between the training recipe (which was designed for Activation Beacon's architecture) and the AutoCompressor/ICAE architectures. The paper does not evaluate the original (non-fine-tuned) AutoCompressor and ICAE checkpoints on LongBench, nor does it explore whether a different fine-tuning recipe might improve their performance. This is a confounding factor that weakens the causal claim somewhat, though the consistency of the gap across tasks and metrics makes a strong circumstantial case.

A stronger test would be to compare Activation Beacon against a version of itself that uses soft tokens instead of per-layer key-value activations (e.g., compressing each chunk into a learnable embedding vector rather than beacon token activations), keeping the training data and progressive chunk-wise workflow identical. This would isolate the representational medium as the sole variable. The paper does not perform this experiment.

---

**Overall strengths of the experimental design:**

- **Multiple model families** (Llama-2, Qwen-2) and scales (7B, 72B for FLOPs) demonstrate some generality beyond a single architecture.
- **Realistic multi-turn evaluation** (Table 2) that directly addresses the deployment scenario where query-independent compression matters most — this is a thoughtful choice of benchmark that aligns with the paper's practical motivations.
- **Ablation of training stages** (pre-training vs. fine-tuning, Table 4) confirms both are necessary and their contributions are roughly additive.
- **Flexibility testing** (Figure 5) across compression ratios and context lengths demonstrates that the random-ratio training strategy works as intended.

**Overall weaknesses and missing experiments:**

- **No statistical testing or confidence intervals anywhere.** All accuracy numbers are point estimates on test sets whose sizes are not always specified. Differences of 0.5–2.0 points between Activation Beacon and Full-FT are treated as "comparable" without any formal basis. A simple bootstrap confidence interval on the LongBench results would substantially strengthen the paper.
- **Single benchmark for compression quality** (LongBench). While NIAH tests a complementary capability (fine-grained retrieval), the paper's core claim about "maintaining comparable performance to the uncompressed baseline" rests heavily on one benchmark. Additional long-context benchmarks — such as ∞BENCH, L-Eval, or SCROLLS — would increase confidence that the results aren't LongBench-specific.
- **No ablation of separate beacon projection matrices.** The $W^b_Q, W^b_K, W^b_V$ matrices are a core architectural contribution, but the paper never compares against a version where beacon tokens reuse the frozen LLM projections. This leaves the contribution of the separate projections unquantified.
- **The "comparable" claim is evaluated only at the compression ratios used in Table 1** (adaptive for Llama-2, ×4 for Qwen-2). For Llama-2, LongBench performance at fixed ×8 (the recommended ratio) is not reported. The flexibility experiments (Figure 5) use NIAH, not LongBench — so we don't know if LongBench accuracy degrades at ×8.
- **No evaluation of compression quality as a function of training data scale.** The paper uses 1B pre-training tokens and 30K fine-tuning samples. Would 100M tokens suffice? Would 10B tokens yield substantial improvements? A data scaling curve for compression quality would help practitioners estimate training budgets.
- **The Multi-Needle evaluation uses only 20 runs** with distinct needle positions. Given the variability in LLM outputs, 20 runs yields limited statistical power, and the reported accuracy differences of ~0.05–0.15 between Activation Beacon and Full-FT are almost certainly within sampling noise.
- **Short-context evaluation is limited to multiple-choice benchmarks** (MMLU, ARC-C, BoolQ) and one generation benchmark (GSM8K). The paper does not evaluate on short-context versions of the tasks Activation Beacon was designed for — e.g., short-document QA, short-context summarization — which would test whether the beacon parameters interfere with the LLM's reading comprehension capabilities specifically.

## 6. Limitations and Trade-offs

### Limitation 1: Compression Quality Has Only Been Validated on a Single Long-Context Benchmark and Retrieval Task

**The constraint.** The paper's core claim — that Activation Beacon "maintains a comparable performance to the uncompressed baseline across various scenarios" (Section 1) — rests empirically on one long-context understanding benchmark (LongBench) and two variants of needle-in-a-haystack retrieval (single-needle NIAH and Multi-Needle). While these benchmarks cover distinct capabilities (multi-task understanding and fine-grained retrieval), they represent a narrow slice of the long-context processing landscape. The paper does not evaluate on other widely-used long-context benchmarks such as ∞BENCH, L-Eval, SCROLLS, or ZeroSCROLLS, which test additional task types including long-form dialogue, complex multi-hop reasoning, and long-document classification.

**The consequence.** A practitioner cannot determine whether Activation Beacon's near-lossless compression generalizes beyond the specific evaluation domains tested. Tasks that require integrating information across very sparse signal in a long context (e.g., finding and combining three facts scattered across a 100K-token legal document to answer a compound question) may expose information loss that LongBench's relatively structured QA format and NIAH's single-fact retrieval do not. Similarly, tasks requiring the model to track and reason about narrative state over very long horizons (e.g., character relationships across a novel-length text) might suffer from the progressive compression's inherent locality — each beacon token primarily captures local information within its chunk, and cross-chunk dependencies are mediated only through the compressed representations of subsequent chunks attending to prior beacon tokens.

The paper's NIAH results (Figure 4) provide only a partial guarantee about fine-grained information preservation: retrieving a single isolated fact from a haystack of irrelevant text is a necessary condition for compression fidelity, but it is far from sufficient. A compression method could preserve every isolated fact while losing the relational structure that connects facts — and relational reasoning is precisely what many long-context tasks require. The Multi-Needle experiment (Table 2) extends this to three facts, but the needles are independent and retrieval is still single-fact per turn.

**Evidence in the paper.** All main compression-quality results come from LongBench (Table 1), NIAH (Figure 4), and Multi-Needle (Table 2). No other long-context evaluation benchmarks appear. The paper does not acknowledge this as a limitation.

**Mitigation status.** Not addressed. The paper's release of code and models may enable third-party evaluation on additional benchmarks, but the authors do not provide such evaluation themselves and do not discuss the generalizability of their results beyond the tested benchmarks.

---

### Limitation 2: The Difficulty of Compression Is Not Characterized — Some Contexts May Be Inherently Uncompressible at High Ratios

**The constraint.** Activation Beacon is evaluated at fixed compression ratios (×2, ×4, ×8) applied uniformly across all chunks of a given input. The paper demonstrates that ×8 compression yields near-lossless performance on the evaluated benchmarks (Table 1, Figures 4–5), but provides no analysis of *when* compression begins to fail as a function of the input's properties. Not all contexts are equally compressible: a dense mathematical proof with tightly coupled logical dependencies may lose critical structure under aggressive compression, while a verbose narrative with substantial redundancy may tolerate ×16 compression easily. The paper's difficulty estimation is entirely absent — unlike the compute-optimal scaling paper discussed in the prior analysis, which explicitly conditions strategy selection on estimated prompt difficulty, Activation Beacon applies the same compression ratio to all inputs regardless of their information density.

**The consequence.** A practitioner deploying Activation Beacon at ×8 has no way to know whether their specific domain's context characteristics are compatible with this compression ratio. If the domain involves information-dense technical content (legal contracts, scientific specifications, code repositories), ×8 compression may silently discard task-critical details that the LongBench and NIAH evaluations — which use more general-domain text — did not stress. The paper's ablation on compression ratios (Figure 5) shows NIAH accuracy is flat from ×2 to ×16 at 32K context, which might lead a practitioner to overconfidently apply ×16 to their domain without realizing that NIAH's haystack text is intentionally irrelevant fill and therefore highly compressible. The paper offers no diagnostic tool, no per-input confidence score, and no characterization of which types of content degrade first under aggressive compression.

This is a fundamentally different class of limitation from the benchmark scope issue above. Even if Activation Beacon were evaluated on ten more benchmarks, the absence of input-conditional compression quality estimation means deployment remains a blind trust exercise: the model gives no signal when it is compressing beyond its reliable range for a particular input.

**Evidence in the paper.** The compression ratio experiments (Figure 5) treat context length as the primary variable and compression ratio as the secondary variable, but never vary the *nature* of the context. All NIAH evaluation uses the same needle-in-haystack format. The LongBench evaluation (Table 1) aggregates over diverse task types but reports only task-level averages, not per-input or per-domain breakdowns. The paper does not discuss input-dependent compressibility as a concept.

**Mitigation status.** Not addressed. The paper does not acknowledge that compressibility may vary across inputs, does not propose any method for estimating per-input compression quality, and does not suggest adaptive ratio selection based on content properties. Future work on difficulty-aware compression — applying the insights from the compute-optimal scaling paper to the context compression domain — would directly address this gap.

---

### Limitation 3: The Generalization to Context Lengths Beyond 128K Is Untested, and the Training Signal Provides No Grounds to Expect It

**The constraint.** Activation Beacon is trained exclusively on contexts up to 20K tokens (Section 4.1) and evaluated on contexts up to 128K (Figure 4, Table 2). The paper claims the method generalizes to lengths "far exceeding the maximum training length" (Section 1), and this is true for the 128K setting tested. However, the architectural property that enables this generalization — the chunk-wise processing that keeps per-chunk sequence length fixed at w (1024 or 2048) and grows only the accumulated beacon sequence — has an implicit limit that the paper does not examine.

Specifically, the number of accumulated beacon tokens at context length n with compression ratio α is n/α. During training with maximum context 20K and α sampled from {2, 4, 8, 16, 32}, the maximum number of accumulated beacon tokens the model ever sees is 20K/2 = 10K (when α = 2 is sampled for all chunks). At 128K inference with α = 8, the accumulated beacon sequence is 128K/8 = 16K tokens — longer than any training instance. The model is therefore performing attention over a longer beacon sequence than it was trained on. At 256K with α = 8, this becomes 32K beacon tokens — more than 3× the maximum training length — and at 512K, 64K beacon tokens.

**The consequence.** While the 128K results (Figure 4B, Table 2) demonstrate that the model can handle moderate extrapolation in beacon sequence length, there is no evidence that this extrapolation continues to hold at 256K, 512K, or 1M contexts. The attention patterns over beacon tokens — which the model learns during training on sequences of at most 10K beacon tokens — may degrade when faced with much longer beacon sequences, even though the per-chunk encoding remains identical. Position embeddings for the accumulated beacon tokens also go out of distribution: the model learns positional relationships up to roughly position 20K during training (the raw context length), but at 256K inference the beacon tokens at the end of the context have position indices near 256K.

The paper's generalization story relies on the chunk-wise architecture decoupling raw context length from per-step processing cost, but this decoupling does not address the quality of attention over very long accumulated beacon sequences. A practitioner deploying Activation Beacon on a 512K-context model has no empirical basis to expect the near-lossless compression observed at 128K to persist.

**Evidence in the paper.** Figure 4B shows Qwen-2-7B NIAH accuracy at 128K with some degradation (scores of 5–7 in regions) compared to near-perfect scores at shorter lengths. The Multi-Needle experiment (Table 2) shows Activation Beacon at 128K achieving 9.70 accuracy versus 9.75 for full attention at turn 1 — a 0.05 absolute drop that may or may not be noise (no confidence intervals reported). The maximum evaluated length is 128K. No results for 256K or 512K are reported. The paper does not discuss the beacon-sequence-length extrapolation question.

**Mitigation status.** Not addressed. The paper does not acknowledge that beacon sequence length grows with total context length and may go out of distribution, does not evaluate beyond 128K, and does not analyze whether the observed slight degradation at 128K (Figure 4B, lower scores in some regions) might be an early signal of a scaling limit. Training with longer contexts or evaluating at longer lengths would be natural extensions.

---

### Limitation 4: The Separate Beacon Projection Matrices Are a Core Architectural Claim but Their Necessity Is Never Tested

**The constraint.** Activation Beacon introduces separate projection matrices $W^b_Q, W^b_K, W^b_V$ for beacon tokens at every attention head in every layer, in addition to the frozen backbone LLM's projections $W^r_Q, W^r_K, W^r_V$ (Section 3.1, Equations 5–6). The paper presents this as a key design element: beacon tokens use dedicated projections so that their queries, keys, and values "can be learned from scratch for the specific purpose of information distillation and retrieval, without interfering with the LLM's carefully trained representations for natural language tokens" (as characterized in the prior analysis, Section 3.4). However, the paper never ablates this choice. No experiment compares the default configuration (separate beacon projections) against a variant where beacon tokens reuse the frozen LLM projections ($W^b_* = W^r_*$) and only the beacon token embedding $e_{\langle b \rangle}$ is trained.

**The consequence.** It is unknown whether the separate projection matrices are load-bearing for the method's performance or whether they add parameters and complexity without meaningful benefit. If the frozen LLM's projections are sufficient — i.e., if the beacon token embedding alone allows the model to route compression behavior through the existing attention machinery — then the added parameters (one set of $W^b_{Q,K,V}$ per head per layer, totaling roughly 0.5% of the backbone model's parameters) are unnecessary. Conversely, if the separate projections are essential, quantifying their contribution would clarify *why* they matter: do they allow beacon tokens to attend differently than raw tokens? Do they enable a different key-value representation subspace optimized for information retention rather than next-token prediction?

This is not merely an academic concern. The separate projections increase the model's parameter count (albeit modestly) and require training from scratch. If a simpler configuration achieves comparable performance, it would be preferable for both training efficiency and deployment simplicity. If the separate projections are critical, then the paper's core architectural claim — that beacon tokens need their own projection spaces — stands on stronger ground.

**Evidence in the paper.** None. The ablation studies (Section 4.6, Table 4) test the fine-grained interleaving, the chunk-wise random ratio, and the training stages, but do not test beacon projection sharing. The paper does not discuss this as a missing ablation.

**Mitigation status.** Not addressed. No such experiment is proposed or discussed. This is a notable gap because it is one of the few architectural variables that could be tested with minimal implementation effort — it requires only skipping the initialization of separate $W^b_*$ matrices and pointing beacon token projections to the frozen $W^r_*$ matrices — and would directly answer whether the core "plug-in module" design (as opposed to the interleaving and training recipe) is necessary.

---

### Limitation 5: The Training Recipe Assumes Access to a Specific Data Mixture That May Not Transfer to Other Domains or Languages

**The constraint.** Activation Beacon's training uses a two-stage recipe: 1B tokens of English text from RedPajama for pre-training, followed by fine-tuning on 30K samples from LongAlpaca, BookSum, and a GPT-3.5-synthesized QA dataset (Section 4.1, Appendix A). All training data is English-language, sourced from web text, books, and academic papers. The fine-tuning data particularly skews toward summarization and question-answering tasks. The paper demonstrates strong performance on English long-context benchmarks (LongBench English subset, NIAH with English haystack text) but provides no evaluation on non-English long-context tasks or on task types substantially different from those in the fine-tuning mixture (e.g., long-form code generation, multi-turn tool-use over long interaction histories, long mathematical derivations).

**The consequence.** A practitioner wanting to apply Activation Beacon to a non-English LLM or to a domain-specific deployment (e.g., processing long Chinese legal documents, French scientific papers, or multilingual code repositories) must replicate the training recipe with appropriate data in their target language or domain. The paper provides no guidance on how much data is needed, whether the 1B pre-training token budget is sufficient for non-English compression, or whether the synthetic QA generation pipeline (which relies on GPT-3.5-turbo's English capabilities) would work for other languages. The method may work equally well — compression is in principle language-agnostic since it operates on the model's internal representations, not surface text — but this is an assumption, not a verified property.

Additionally, the fine-tuning data's task distribution (QA + summarization) may bias the compression toward preserving information relevant to these task types. A deployment requiring long-context code completion, where the model must track variable definitions and function signatures across thousands of lines of code, may require different information to be preserved. The paper's evaluation on LongBench's Code task (Table 1) shows Activation Beacon achieving 57.8 (Llama-2) and 66.4 (Qwen-2), which is comparable to the uncompressed baselines — but LongBench Code involves relatively short code snippets, not the multi-file, highly structured codebases that characterize real-world long-context code tasks.

**Evidence in the paper.** All evaluation is on English benchmarks. The training data sources are all English-language (RedPajama, LongAlpaca, BookSum, GPT-3.5 synthetic data derived from The Pile's English subsets). The paper does not discuss multilingual or cross-domain generalization. The synthetic data generation pipeline (Appendix A) explicitly uses GPT-3.5-turbo and SemanticTextSplitter, both of which are English-optimized.

**Mitigation status.** Not addressed. The paper does not acknowledge this as a limitation, does not provide multilingual evaluation, and does not discuss domain adaptation requirements. The release of the training code partially mitigates this by enabling others to reproduce the recipe on their own data, but the paper provides no guidance on data requirements, which means practitioners must invest in their own data scaling experiments.

---

### Limitation 6: The FLOPs and Latency Advantages Are Reported Without Accounting for the Cost of Beacon-Specific Computation During Training or Difficulty Estimation

**The constraint.** All efficiency numbers reported in the paper — the 2× acceleration in inference time, the 8× KV cache reduction, the FLOPs curves in Figure 3 — are inference-only metrics. They measure the cost of a forward pass with Activation Beacon compared to a forward pass with full attention, after the beacon parameters have been trained. The training cost itself (1B tokens of pre-training plus fine-tuning on a single 8×A800 machine) is mentioned (Section 4.1) but is not amortized into any efficiency calculation and is not compared against the training cost of competing methods.

This is a minor concern for the efficiency claims *per se* — inference savings are genuinely what matters for deployment — but it becomes material when comparing Activation Beacon against methods that require no training at all, such as LongLLMLingua and SnapKV (which are training-free token-deletion or KV-eviction heuristics). For a practitioner deciding between Activation Beacon and SnapKV, the relevant comparison is not just inference latency (where Activation Beacon wins in multi-turn scenarios, Table 2) but also total cost of ownership, which includes any required training. If SnapKV can be deployed immediately on any model without training, while Activation Beacon requires a multi-stage training process even if the backbone is frozen, the upfront cost may influence adoption decisions for low-budget deployments.

More significantly, the paper's architecture requires one design choice that has a recurring inference-time cost not reflected in the FLOPs curves: the chunk-wise processing introduces a sequential bottleneck. Each chunk must be fully encoded through all layers before the next chunk can begin, because chunk i+1 requires the accumulated beacon activations from chunk i at every layer. This means the encoding of long contexts is serialized across chunks, limiting throughput (contexts processed per second) even as it improves latency for individual queries. For batch processing of many long documents — a common scenario in data processing pipelines — this serialization may offset the FLOPs-per-query savings. The paper's latency measurements (Table 2) are for single-query latency, not throughput under batch processing.

**Evidence in the paper.** The paper acknowledges the training cost implicitly by describing it (Section 4.1) but never quantifies it in FLOPs or GPU-hours, and never compares it against the training cost of AutoCompressor or ICAE. The serialization issue is not discussed. The paper reports "end-to-end latency of compression & generation" (Table 2) but does not report throughput or batch processing performance.

**Mitigation status.** Partially addressed for the training cost: the paper emphasizes that training "can be quickly accomplished" (Section 3.2) and requires only a single 8×A800 machine, implicitly arguing that the training cost is low relative to the inference savings. But no FLOPs or dollar-cost numbers are provided, making this claim qualitative. The serialization issue is not addressed at all — the paper does not discuss throughput vs. latency tradeoffs, batch processing, or whether chunk encoding could be parallelized across chunks with some form of speculative beacon activation.
