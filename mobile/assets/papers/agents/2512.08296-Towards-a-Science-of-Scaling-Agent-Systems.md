# Towards a Science of Scaling Agent Systems

**ArXiv:** [2512.08296](https://arxiv.org/abs/2512.08296)

## 🎯 Pitch

This paper derives quantitative scaling principles for LM-based agent systems, identifying how agent count, coordination topology, model capability, and task properties interact to predict when multi-agent coordination helps or hurts. By running 180 controlled, budget-matched configurations across four agentic benchmarks and five canonical architectures, it introduces measurable coordination metrics (efficiency, overhead, redundancy, error amplification) and a predictive model (R^2=0.524) that gives principled guidance for selecting architectures—showing that “more agents” is beneficial only for specific, decomposable tasks and can severely degrade performance for sequential, tool-heavy problems.

---

## 1. Executive Summary

This paper studies how the performance of language-model-based agent systems changes when they are scaled across coordination architecture, model capability, and task properties, using 260 controlled configurations spanning five canonical agent architectures (Single-Agent, Independent, Centralized, Decentralized, Hybrid), three LLM families (OpenAI, Google, Anthropic), and six agentic benchmarks (BrowseComp-Plus, Finance-Agent, PlanCraft, WorkBench, SWE-bench Verified, Terminal-Bench). The core contribution is a **quantitative scaling principle**—a mixed-effects regression model using empirically measured coordination metrics including efficiency (success per relative turn count), trace-level error amplification (how many times baseline errors propagate through agent interactions—ranging from 4.4× under centralized coordination to 17.2× under independent), message density, and redundancy—that achieves cross-validated R² = 0.373 across all six benchmarks (R² = 0.413 with a task-grounded capability metric), and correctly identifies the best-performing architecture for 87% of held-out configurations. Performance relative to single-agent baselines spans from +80.8% improvement on decomposable financial reasoning under centralized coordination to −70.0% degradation on sequential planning under independent coordination, establishing that multi-agent coordination yields diminishing returns once single-agent baselines exceed approximately 45% accuracy—a capability-saturation effect that persists as the most robust finding across cluster-robust inference (p = 0.004) and multiple-comparison correction (p_Holm = 0.018).

## 2. Context and Motivation

### The Core Problem: We Don't Know When Multi-Agent Systems Actually Help

The fundamental question this paper tackles is deceptively straightforward: **if you can deploy multiple language model agents instead of one, when does it actually improve performance?** This matters because multi-agent systems (MAS) are being rapidly adopted across domains—code generation, web browsing, medical decision-making, financial analysis, and scientific discovery—under an implicit assumption that more agents, collaborating through structured communication, will outperform a single agent working alone. Yet this assumption rests on surprisingly fragile empirical foundations.

The paper identifies a critical gap that separates practice from principle. Despite the proliferation of multi-agent architectures—peer-to-peer debate, hierarchical orchestration, ensemble-style voting, hybrid combinations—there exists **no quantitative framework for predicting when adding agents improves outcomes and when it instead introduces coordination costs that degrade them**. As the authors state in Section 1:

> "concurrent works question whether multi-agent coordination outperforms single-agent systems (SAS), leaving the conditions under which MAS provides genuine benefits remain underexplored."

This is not a minor caveat. It is a foundational uncertainty at the heart of an entire subfield. Without a principled understanding, practitioners rely on heuristics ("more agents must be better," "debate improves reasoning," "centralized coordination reduces errors") that may be correct in some settings and catastrophic in others. The paper's central claim is that these heuristics are not merely imprecise—they are systematically misleading when applied across task types without accounting for difficulty, decomposability, and tool complexity.

### Why This Problem Matters: Beyond Academic Curiosity

The gap is consequential for several practical and theoretical reasons that the paper develops across Sections 1-2:

**Deployment economics are directly affected.** Multi-agent systems consume substantially more tokens than single-agent baselines. The paper reports that coordination overhead ranges from 58% (Independent architecture) to 515% (Hybrid architecture) relative to the single-agent token budget (Table 5). If this additional compute doesn't yield proportional performance gains—and the paper shows it often doesn't—then organizations are burning inference budget on coordination overhead rather than reasoning. For production systems handling millions of queries, the difference between deploying a single strong model versus a multi-agent ensemble with 5× the latency and cost (as Anthropic [44] report: 15× token consumption) represents a massive resource allocation decision made without empirical guidance.

**The capability landscape is shifting under our feet.** As frontier models gain extended context windows, sophisticated tool use, and improved self-reflection capabilities, the value proposition of multi-agent systems becomes increasingly unclear. Section 1 articulates this tension precisely:

> "As base LLMs gain extended context windows, sophisticated tool use, and improved self-reflection, the unique value proposition of multi-agent collaboration becomes unclear. The answer likely depends on task characteristics and architectural choices that remain to be systematically quantified."

A single GPT-5 or Gemini-2.5-Pro might now outperform a team of weaker agents on tasks that previously required collaboration. But a team of strong agents might still outperform any individual. The paper provides the first systematic characterization of **where the crossover point lies** (the 45% single-agent baseline threshold) and **which architectures perform best in which regimes**.

**The distinction between agentic and non-agentic tasks matters.** Section 2 introduces a crucial taxonomy: agentic tasks require (i) sustained multi-step environmental interactions, (ii) iterative information gathering under partial observability, and (iii) adaptive strategy refinement from feedback. Non-agentic tasks—GSM8K, MMLU, HumanEval—evaluate single-shot reasoning. The literature has a known bias: on non-agentic benchmarks, multi-agent systems show monotonic improvement through ensemble effects (e.g., 89% on HumanEval with five agents) because voting corrects independent errors without sequential compounding. But the paper observes that:

> "tasks showing MAS advantages in single-shot settings often exhibit opposite patterns under genuine interaction."

This means the existing multi-agent evaluation literature—conducted predominantly on non-agentic benchmarks—may be providing systematically misleading guidance about when collaboration provides value in real-world deployments, where sustained environmental interaction is the norm.

### Conflicting Prior Evidence and Where Existing Approaches Fall Short

The paper is motivated by a genuine tension in the literature that prior work has not resolved. This tension operates at multiple levels.

#### The "More Agents Is All You Need" vs. "Single Agents Are Enough" Debates

On one side, a body of work suggests that scaling the number of agents produces consistent benefits. Li et al. [41] demonstrate performance improvements with increased team size on reasoning benchmarks. Qian et al. [42] propose scaling laws for multi-agent collaboration, though the paper notes they found "no significant universal pattern." Du et al. [27] show that multi-agent debate improves factuality and reasoning—but with the important caveat (noted by Smit et al. [58]) that debate does not reliably outperform single-agent strategies like self-consistency.

On the other side, a growing body of work challenges the assumption that MAS provides genuine value over simpler alternatives. Huang et al. [3] and Neubig [17] argue that single-agent systems with strong tool use often match or exceed multi-agent configurations. Gao et al. [16] demonstrate that benefits diminish as base models improve, with frontier models often outperforming teams of weaker agents. Cemri et al. [15] catalogue 14 distinct failure modes in multi-agent systems (Cohen's Kappa = 0.88), providing the failure taxonomy (MAST) that this paper builds upon in Section 4.4. Cognition AI [18] takes the strongest position: "Don't build multi-agents."

These conflicting findings are not fundamentally contradictory—they reflect **different methods being applied to different task types under different evaluation protocols**—but the field lacked a framework for reconciling them. This paper's central insight is that the effectiveness of multi-agent coordination is governed by quantifiable trade-offs between architectural properties and task characteristics, and that ignoring this heterogeneity makes the question "do multi-agent systems work?" unanswerable without specifying the task, architecture, and capability regime.

#### Where Prior Approaches Fall Short

The paper identifies specific limitations in prior work along several axes:

**Confounded evaluations prevent causal attribution.** Section 1 argues that "existing MAS evaluations compare architectures using different prompts, tools, or computational budgets, conflating architectural effects with implementation choices and precluding clean causal attribution." If one paper's decentralized system uses better prompts or more tool budget than another's centralized system, performance differences tell us nothing about the architectures themselves. This is not a minor methodological concern—it is a barrier to scientific progress. You cannot derive scaling principles from confounded comparisons.

**Evaluations focus on outcomes, not process.** Beyond final accuracy, the paper notes that prior work largely ignores "process dynamics such as coordination overhead, error propagation, and information flow that determine whether collaboration succeeds or fails." This is analogous to evaluating a drug without measuring the mechanism of action: you might observe that it works (or doesn't), but you cannot predict when it will work or why it might fail in new settings. The paper's empirical coordination metrics—efficiency, trace-level error amplification, message density, redundancy—are designed to fill precisely this gap.

**No systematic exploration of the architecture-task interaction.** While prior work has studied individual architectures (debate [27], hierarchical orchestration [28], ensemble methods) in specific domains, no prior study has systematically varied both architecture type and task domain to characterize their interaction. The paper's design explicitly tests whether "coordination benefits arise from matching communication topology to task structure, not from scaling the number of agents" (Section 2). This framing shifts the research question from "which architecture is best?" to "under what conditions does each architecture excel?"

**Scaling laws are absent or incomplete for agentic systems.** While neural scaling laws for pretraining are well-established (Kaplan et al. [54]), the paper notes that "collaborative scaling exhibits logistic growth patterns emerging at substantially smaller scales" with "no significant universal pattern" (citing Qian et al. [42]). This means the standard toolkit of scaling laws—power-law relationships between compute and performance—doesn't directly transfer to multi-agent systems, which have coordination dynamics that are fundamentally different from parameter scaling. The paper's contribution is not to propose universal scaling laws but to characterize the **conditions under which scaling produces benefits versus costs**.

**No quantitative architecture selection guidance exists.** Section 1 frames this as the practical gap: "practitioners rely on heuristics, hindering both the emergence of a science of agent systems and, critically for real-world deployment, the ability to determine when multi-agent coordination provides genuine value over simpler single-agent alternatives." The paper's regression model (Equation 1) and the derived 45% baseline threshold directly address this gap by providing quantitative rules: if your single-agent baseline exceeds ~45% accuracy, coordination is unlikely to help; if it's below, centralized or decentralized architectures provide the best returns depending on task structure.

### Theoretical Framing: Information Fragmentation and the Coordination Tax

Section 1 provides a theoretical framework that explains why agentic tasks exhibit fundamentally different multi-agent scaling behavior than non-agentic tasks. The core mechanism is **information fragmentation**:

> "Single-agent systems maximize context integration by maintaining a unified memory stream in which all reasoning steps share full access to prior history, enabling effectively constant-time access to global context. In contrast, multi-agent systems impose intrinsic information fragmentation: while parallel agents enable diverse exploration, they incur an unavoidable coordination tax in which the global context must be compressed into inter-agent messages."

This framing draws on Malone and Crowston's [29] concept of coordination costs and connects to the broader organizational behavior literature on team effectiveness (McGrath [30], Lencioni [31]). The insight is that multi-agent systems face a fundamental trade-off that single-agent systems avoid: **diversity of perspective vs. completeness of context**. Parallel agents can explore different solution strategies simultaneously, but each agent operates with only partial information about what others have discovered, and synchronizing that information requires costly communication.

On agentic tasks, this trade-off is particularly sharp because "coordination overhead scales with interaction depth, agents operate on progressively divergent world states, and errors cascade through execution chains rather than being corrected through voting." The paper reports that after 10 interactions, agent world states diverge to only 34% overlap (Section 2), meaning agents are sampling from increasingly different "realities." This explains why voting-based error correction—effective on static benchmarks—fails in agentic settings: there is no single ground-truth output to vote on, only a sequence of interdependent decisions under partial information.

### How This Paper Positions Itself

The paper positions itself not as proposing a new multi-agent architecture, but as providing the **first systematic empirical characterization of the conditions under which coordination provides value**. This is framed as a scientific contribution rather than an engineering contribution:

> "We introduce quantitative scaling principles for agent systems as a predictive model, capturing how performance varies with coordination, model capability, and measurable system and task factors."

Several aspects of this positioning are distinctive:

**Controlled experimentation as scientific method.** The paper explicitly controls for implementation confounds that plague prior comparisons—identical prompts, tools, and computational budgets across all architectures—to isolate architectural effects. This mirrors the controlled experiment methodology of the natural sciences and contrasts with the benchmark-driven approach common in ML, where confounded comparisons are the norm.

**Unified analytical framework rather than architectural advocacy.** The paper's five architectures (SAS, Independent, Decentralized, Centralized, Hybrid) are not presented as competitors to be ranked but as a "structural ablation of coordination mechanisms" (Section 3.1), where Independent isolates parallelization, Decentralized introduces peer communication without hierarchy, Centralized introduces hierarchical verification, and Hybrid combines both. This design enables attribution of effects to specific coordination mechanisms rather than generic "multi-agent" labels.

**Predictive model as scientific output.** Rather than simply reporting which architecture performed best on which benchmark, the paper derives a regression model (Equation 1) that predicts performance from measurable properties. The cross-validated R² = 0.373 (R² = 0.413 with ACI) represents a specific, falsifiable claim about how agent-system performance emerges from task properties, model capability, and coordination structure. The paper acknowledges the limits of this model—it works for relative architecture selection (87% accuracy on held-out configurations) but struggles with absolute cross-domain prediction—which is the appropriate level of epistemic modesty for a first quantitative framework.

**Connection to broader scaling paradigm.** The paper explicitly connects to the scaling laws tradition (Kaplan et al. [54]) while distinguishing agentic scaling from neural scaling: "collaborative scaling exhibits logistic growth patterns" with super-linear turn-count scaling (exponent 1.724, compared to neural scaling exponents of ~0.76). This positioning suggests that agent systems represent a new scaling regime requiring new analytical tools, not a straightforward extension of existing scaling laws.

### Summary of the Gap and the Position

The paper addresses a fundamental gap: the absence of quantitative, empirically grounded principles for predicting when multi-agent coordination improves performance, when it degrades it, and by how much. This gap matters because multi-agent systems are being deployed with significant computational cost based on heuristics ("more agents is all you need") that are contradicted by a body of conflicting evidence. Prior work has evaluated architectures in confounded comparisons, without controlling for implementation differences, and without measuring the coordination dynamics that determine success or failure.

The paper's position is that **architecture-task alignment, not team size, determines collaborative success**, and that this alignment can be characterized through measurable coordination metrics (efficiency, error amplification, message density, redundancy) that explain performance variance across 260 configurations. The 45% single-agent baseline threshold, the tool-coordination trade-off, and the 4.4× vs. 17.2× error amplification difference between centralized and independent architectures are not merely interesting observations—they are the first quantitative principles for designing agent systems, analogous to (but distinct from) the pretraining scaling laws that transformed how we allocate training compute.

## 3. Technical Approach

### 3.1 Reader Orientation

The authors are building a **predictive framework**—not a new agent architecture, but a quantitative model that takes measurable properties of a task, a language model, and a coordination structure as inputs and outputs an expected performance score. The problem it solves is that practitioners currently choose between single-agent and multi-agent systems based on heuristics ("more agents is all you need," "centralized coordination reduces errors") with no principled way to predict when those heuristics hold. The shape of the solution is a regression equation whose coefficients are estimated from 260 controlled experiments, where each experiment varies exactly one dimension (model capability, architecture, benchmark) while holding prompts, tools, and compute budgets identical to isolate the causal effect of coordination structure on performance.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has four major components:

1. **Agent System Configurations (the independent variables)** — Five canonical architectures (Single-Agent, Independent MAS, Centralized MAS, Decentralized MAS, Hybrid MAS) instantiated across nine models from three LLM families. Each architecture specifies a communication topology (who talks to whom), an orchestration policy (how outputs are aggregated), and a computational budget (matched total reasoning tokens across all configurations).

2. **Six Agentic Benchmarks (the task environment)** — BrowseComp-Plus (web browsing), Finance-Agent (financial reasoning), PlanCraft (Minecraft planning), WorkBench (business tool use), SWE-bench Verified (software engineering), and Terminal-Bench (CLI tasks). Each benchmark requires sustained multi-step environmental interaction, partial observability, and adaptive strategy refinement.

3. **Empirical Coordination Metrics (the measured intermediates)** — Six quantities extracted from execution traces: coordination overhead (`$O\%$`), message density (`$c$`), redundancy rate (`$R$`), coordination efficiency (`$E_c$`), trace-level error amplification (`$A_{e}^{\text{trace}}$`), and success rate (`$S$`). These capture *how* coordination succeeds or fails, not just whether it does.

4. **Scaling Principle Regression Model (the predictive output)** — A mixed-effects regression (Equation 1) with 20 parameters that maps model capability, task properties, architecture type, and coordination metrics onto expected task accuracy. The model is fit on 260 configurations and achieves cross-validated `$R^2 = 0.373$`.

Information flows as follows: a model (with Intelligence Index `$I$`) is deployed on a benchmark (with tool count `$T$` and single-agent baseline `$P_{\text{SA}}$`) under a specific architecture → the system runs and produces execution traces → empirical coordination metrics are extracted from those traces → the regression model predicts performance from those metrics plus the original inputs → the predicted performance can be compared across architectures to select the optimal one for a given task.

### 3.3 Roadmap for the Deep Dive

- **First**, the **agent system formalism** (Section 3.1)—the mathematical definitions of single-agent and multi-agent systems, their components, and the four multi-agent architectures. This is the vocabulary needed to understand everything that follows.

- **Second**, the **agentic task definition and benchmark selection** (Section 3.2)—what makes a task "agentic" vs. non-agentic, why this distinction matters for multi-agent evaluation, and the six benchmarks used. This explains *what* is being measured and *why* those choices prevent confounded comparisons.

- **Third**, the **experimental design principles** (Section 4.1)—the controlled evaluation framework, including the five architectures, the Intelligence Index capability metric, the matched-compute budget strategy, and the configuration matrix (`$N = 260$` experiments). This is the "how" of the controlled experiments.

- **Fourth**, the **empirical coordination metrics** (Section 4.4)—the six quantities extracted from execution traces (overhead, message density, redundancy, efficiency, error amplification, turn count). These are the mechanistic lenses through which the paper interprets *why* architectures succeed or fail.

- **Fifth**, the **scaling principle regression model** (Section 4.3)—the full predictive equation (Equation 1), including which terms are included and why, the mechanistic hypotheses behind each interaction, and the cross-validation procedure. This is the quantitative synthesis of everything the experiments measure.

- **Sixth**, the **robustness checks** (Section 4.5)—cluster-robust standard errors, multiple-comparison correction, capability metric sensitivity, and out-of-sample validation. These address threats to statistical validity and establish which findings are most reliable.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily an **empirical measurement paper** whose core idea is that the performance difference between single-agent and multi-agent systems on agentic tasks is governed by quantifiable coordination properties—and that these properties can be predicted from task structure, model capability, and architecture type using a regression model with no dataset-specific parameters.

#### Agent System Formalism: What Constitutes an Agent System

The paper grounds its analysis in a formal definition of agent systems (Section 3.1) that draws on the multi-agent system survey literature [14, 19]. This formalism serves two purposes: it provides precise vocabulary for describing the five architectures, and it enables systematic control of what varies between experiments.

**Definition.** An agent system is a 4-tuple:

$$S = (A, E, C, \Omega)$$

where `$A = \{a_1, \ldots, a_n\}$` is the set of agents (with `$n \geq 1$`), `$E$` is the shared environment, `$C$` is the communication topology defining which agents can send messages to which other agents, and `$\Omega$` is the orchestration policy determining how agent outputs are aggregated and when the system terminates.

**What it represents:** `$S$` is the complete specification of how a set of LLM instances will coordinate to solve a task. The agent set `$A$` determines how many independent reasoning loci exist; the environment `$E$` provides the tool APIs and observation feedback; the communication topology `$C$` constrains information flow; and the orchestration policy `$\Omega$` defines the decision-making procedure that converts multiple agent outputs into a single final answer.

**Why this decomposition:** separating communication topology (`$C$`) from orchestration policy (`$\Omega$`) is critical because they represent distinct coordination dimensions. An Independent architecture and a Centralized architecture both use a star topology, but they differ in orchestration: Independent merely concatenates outputs (aggregation without verification), while Centralized routes through an orchestrator that cross-checks and synthesizes. This decomposition enables the paper's structural ablation (Section 3.1): Independent isolates the effect of parallelization without communication, Decentralized isolates the effect of peer communication without hierarchy, Centralized isolates the effect of hierarchical verification, and Hybrid combines both mechanisms.

**Individual agent definition.** Each agent `$a_i$` is further decomposed:

$$a_i = (\Phi_i, \mathcal{A}_i, M_i, \pi_i)$$

where `$\Phi_i$` is the reasoning policy (the LLM itself), `$\mathcal{A}_i = \{\text{ToolCall}(t, \theta) : t \in \mathcal{T}, \theta \in \Theta_t\}$` is the action space consisting of tool invocations parameterized by available tools `$\mathcal{T}$` and valid parameter configurations `$\Theta_t$`, `$M_i$` is the agent's internal memory, and `$\pi_i : \mathcal{H} \rightarrow \mathcal{A}_i$` is the decision function that maps observation histories to actions.

**What `$\pi_i$` computes:** given the agent's current observation history `$h_{i,t}$` (a sequence of previous action-observation pairs), the LLM `$\Phi_i$` generates a reasoning trace and selects the next tool call `$\alpha_{i, t+1}$`. This is the core agent loop:

$$\begin{aligned}
\alpha_{i,t} &= \pi_i(h_{i,t}) \\
o_{i,t} &= E(\alpha_{i,t}) \\
h_{i, t+1} &= f_i(h_{i,t}, \alpha_{i,t}, o_{i,t})
\end{aligned}$$

where the history update function `$f_i$` appends the new action-observation pair to the agent's history, subject to context window truncation when `$|h_{i, t+1}| > \text{MAX\_TOKENS}$`.

**Why this loop matters:** it formalizes the distinction between agentic and non-agentic evaluation. In non-agentic tasks, the environment `$E$` is essentially the identity function (no feedback beyond the final output), and the loop reduces to a single forward pass. In agentic tasks, `$E$` provides intermediate observations that the agent must incorporate into its next action, creating the sequential interdependence that distinguishes genuine agent behavior from single-shot reasoning. The loop also makes clear why partial observability matters: the agent's history `$h_{i,t}$` contains *observed* information, not the full environment state, so agents operating in parallel develop divergent world models (the 34% overlap after 10 interactions reported in Section 2).

**SAS complexity.** For a Single-Agent System (`$|A| = 1$`), the computational complexity is `$O(k)$` where `$k$` is the number of reasoning iterations. Communication overhead is zero, memory complexity is `$O(k)$`, and parallelization factor is 1. This is the baseline against which all multi-agent systems are compared.

**MAS complexity (Table 2).** For the four multi-agent architectures, the paper provides asymptotic complexity characterizations in terms of LLM calls, sequential depth, communication overhead, parallelization potential, and memory:

- **Independent:** `$O(nk) + O(1)$` LLM calls, sequential depth `$k$`, communication overhead 1 (only the final aggregation message), parallelization factor `$n$`, memory `$O(n \cdot k)$`. The `$+O(1)$` term represents the single aggregation step.

- **Centralized:** `$O(rnk) + O(r)$` LLM calls where `$r$` is the number of orchestrator rounds, sequential depth `$r$`, communication overhead `$r \cdot n$`, parallelization factor `$n$`, memory `$O(r \cdot n \cdot k)$`. The `$+O(r)$` term represents the orchestrator's own reasoning steps.

- **Decentralized:** `$O(dnk) + O(1)$` LLM calls where `$d$` is the number of debate rounds, sequential depth `$d$`, communication overhead `$d \cdot n$`, parallelization factor `$n$`, memory `$O(d \cdot n \cdot k)$`. Each debate round requires all agents to read all other agents' messages (all-to-all communication).

- **Hybrid:** `$O((r + p) \cdot n \cdot k)$` LLM calls where `$p$` is the number of peer communication rounds, sequential depth `$r$`, communication overhead `$r \cdot n + p \cdot m$` where `$m$` is the average number of peer requests per round, parallelization factor `$n$`, memory `$O((r + p) \cdot n \cdot k)$`.

**Why these asymptotic characterizations matter:** they formalize the paper's central theoretical claim—that multi-agent systems face a coordination tax that grows with architectural complexity. The shift from `$O(k)$` (SAS) to `$O(rnk)$` (Centralized) or `$O(dnk)$` (Decentralized) is not a constant factor; it compounds with the number of agents, the depth of coordination, and the per-agent iteration count. Under fixed computational budgets (which the paper enforces), this means per-agent reasoning capacity shrinks as coordination overhead grows—explaining the trade-off observed in Section 4.2 where task domains with low decomposability (PlanCraft) show universal MAS degradation.

**Key architectural distinctions.** The paper defines the five architectures through specific choices of `$C$` and `$\Omega$`:

- **Single-Agent System (SAS):** `$|A| = 1$`, `$C = \emptyset$`, no orchestration needed. One reasoning locus handles all perception, planning, and action sequentially.

- **Independent MAS:** `$C = \{(a_i, a_{\text{agg}}) : \forall i\}$` (agent-to-aggregator only, no peer communication), `$\Omega = \text{synthesis\_only}$`. The synthesis_only policy concatenates sub-agent outputs without cross-validation or majority voting; the aggregator performs no analytical comparison of responses. This isolates pure parallelism without any communication benefit.

- **Centralized MAS:** `$C = \{(a_{\text{orch}}, a_i) : \forall i\}$` (orchestrator-to-agents only), `$\Omega = \text{hierarchical}$`. A single orchestrator decomposes the task, distributes subtasks to sub-agents, collects responses, cross-checks reasoning steps before aggregation, and may override sub-agent decisions. This creates a validation bottleneck that the paper shows reduces trace-level error amplification from 17.2× to 4.4×.

- **Decentralized MAS:** `$C = \{(a_i, a_j) : \forall i, j, i \neq j\}$` (all-to-all topology), `$\Omega = \text{consensus}$`. Agents communicate in sequential debate rounds where each agent reads all others' outputs before producing its next response. Consensus is formed through peer-to-peer discussion without a central authority.

- **Hybrid MAS:** `$C = C_{\text{centralized}} \cup C_{\text{peer}}$` (star + limited peer edges), `$\Omega = \text{hierarchical} + \text{lateral}$`. Combines orchestrator control with directed peer communication, inheriting both the validation bottleneck of centralized and the information-fusion benefits of decentralized, but at the cost of the highest communication overhead (515% in Table 5).

**Error amplification formalism.** The paper defines task-level error amplification:

$$A_e^{\text{task}} = \frac{E_{\text{MAS}}}{E_{\text{SAS}}}$$

where `$E = 1 - P$` is the fraction of tasks not successfully resolved, `$E_{\text{MAS}}$` is the multi-agent error rate, and `$E_{\text{SAS}}$` is the single-agent baseline error rate. `$A_e^{\text{task}} > 1$` indicates coordination introduces net errors; `$A_e^{\text{task}} < 1$` indicates net error suppression.

**What it computes:** the ratio of how often a multi-agent system fails relative to how often a single agent fails on the same tasks. If SAS gets 50% accuracy (`$E_{\text{SAS}} = 0.5$`) and MAS gets 45% (`$E_{\text{MAS}} = 0.55$`), then `$A_e^{\text{task}} = 1.1$`—coordination makes errors 10% more likely.

**Why this decomposition:** it separates total performance into a baseline capability component (captured by SAS accuracy) and a coordination component (captured by the amplification factor). This is essential for the paper's claim that coordination effects depend on baseline performance: when `$E_{\text{SAS}}$` is already low (high single-agent accuracy), there is less room for coordination to help and more risk of it hurting.

The paper additionally defines a complementary trace-level error amplification factor `$A_e^{\text{trace}}$` (Section 4.4) that measures computational work arising from coordination failures, estimated from execution-trace token analysis. These differ: `$A_e^{\text{task}} \approx 1.1$–1.3 while `$A_e^{\text{trace}} \approx 4$–17, reflecting that they capture complementary aspects—task-level measures final output errors, trace-level measures wasted computation.

#### Agentic Task Definition and Benchmark Selection

The paper extends the Agentic Benchmark Checklist (ABC) framework from Zhu et al. [19] to formalize what makes a task "agentic" (Section 3.2). This definition is load-bearing: it determines which benchmarks are included, and it explains why the paper's findings differ from prior multi-agent evaluation literature conducted on non-agentic tasks.

**Formal criterion.** A task `$T$` is agentic when the expected return of the optimal interactive policy `$\pi$` meaningfully exceeds the best possible single-forward-pass function `$g$`:

$$\frac{\max_{\pi} \mathbb{E}[R(\tau)] - \max_g \mathbb{E}[R(g(x))]}{\max_{\pi} \mathbb{E}[R(\tau)]} > \delta$$

where `$\tau = \{(a_t, o_t)\}_{t=0}^{T}$` is an interaction trajectory of action-observation pairs, `$R$` measures task success, `$\delta$` is a task-dependent threshold, and expectations are over task instances `$x$` and stochastic environment dynamics.

**What it computes:** the fractional advantage that an agent that adapts through environment interaction has over the best possible system that produces an answer in a single shot without observing intermediate feedback. When `$\delta$` is large (say, 0.3), the task fundamentally requires agentic interaction for non-trivial performance.

**Why this form:** it operationalizes agency as a measurable quantity rather than a binary label. A task like GSM8K (grade-school math) could hypothetically be made agentic by providing calculator tools, but if current LLMs already solve it near-perfectly in a single forward pass, the numerator is close to zero and the task does not *require* agentic interaction for evaluation purposes. Conversely, SWE-Bench requires multi-step codebase exploration and test feedback—a single forward pass cannot produce a patch that passes hidden tests—so `$\delta$` is large. This definition implicitly acknowledges that "agentic" is relative to model capability.

**Three necessary benchmark properties.** Building on ABC, the paper operationalizes three conditions:

1. **Sequential Interdependence:** later actions depend on earlier observations; a one-shot policy cannot achieve high reward. This excludes benchmarks where each instance could be solved by a single LLM call.

2. **Partial Observability:** critical state information is hidden and must be acquired through active querying or tool use. This excludes tasks with full information at the outset.

3. **Adaptive Strategy Formation:** the policy must update internal beliefs based on new evidence obtained through interaction. This excludes tasks where the optimal strategy is predetermined and static.

**Why this taxonomy matters for multi-agent evaluation.** The paper argues (Section 2) that multi-agent evaluation on non-agentic benchmarks gives systematically misleading results. On static benchmarks like HumanEval, multi-agent systems show monotonic improvement through ensemble effects because task errors are independent across agents—if each agent has an independent 30% chance of error, majority voting over 5 agents drives the error rate down exponentially. But on agentic benchmarks, errors compound sequentially: one agent's wrong tool call leads another agent to explore a dead-end path, and no amount of voting can recover because the agents are operating on incoherent state representations. This is why the paper's findings (Section 4.2) frequently show MAS degradation on agentic tasks where prior non-agentic literature showed improvements.

**Benchmark selection and characteristics.** The paper selects six benchmarks (Table 1) that satisfy the agentic criteria:

- **BrowseComp-Plus** (100 instances): web browsing requiring multi-website information synthesis, comparative analysis, and cross-page fact verification. The environment is the open web, partial observability comes from only seeing one page at a time, and strategy adaptation is required to reformulate queries based on intermediate findings.

- **Finance-Agent** (50 instances): financial analysis tasks including earnings analysis, metric calculations, and market trend interpretation. Each instance includes expert-provided rubrics. The environment provides financial data access tools; partial observability arises because different data sources (SEC filings, news, market data) require different queries.

- **PlanCraft** (100 instances): Minecraft crafting planning where agents must determine optimal action sequences given inventory and recipe constraints. The state space involves multi-step dependencies (crafting planks before doors, doors before rooms), and partial observability requires exploring the recipe space.

- **WorkBench** (100 instances): business task automation across five domains (analytics, calendar, email, project management, CRM). Success requires executing correct sequences of 16 available tools. The environment is deterministic given tool sequences, but partial observability arises because intermediate results from one tool affect which subsequent tools are appropriate.

- **SWE-bench Verified** (20-instance subset, deterministic shuffle seed 42): software engineering tasks requiring GitHub issue resolution with 7 tools (bash, file editing, search, test execution). The environment is a Docker container with a repository snapshot; agents must explore codebases, form hypotheses, generate patches, and verify against test suites.

- **Terminal-Bench** (20 instances, first-N from 86): CLI task execution spanning system administration, security, and ML training with 2 tools (bash execution and answer submission). Docker-based evaluation environments with varying time limits.

**Tool-count range.** Across these six benchmarks, tool counts span `$\{2, 3, 4, 5, 7, 16\}$`, providing the variation needed to estimate the tool-coordination trade-off coefficient (`$\hat{\beta}_{E_c \times T} = -0.096$`, `$p = 0.002$`).

**Benchmark design principles for controlled evaluation.** The paper introduces additional criteria beyond the ABC to enable clean architectural comparisons (Section 3.2):

- **Controlled Tool Interface:** identical tool APIs and observation structures for all architectures. This means the Centralized orchestrator sees the same tool outputs as the Independent aggregator—no architecture gets privileged access to better information.

- **Controlled for Parametric Knowledge:** within each model family, evaluation emphasizes adaptive reasoning over memorized facts. Cross-family comparisons account for inherent knowledge differences through baseline normalization (comparing MAS performance to SAS performance, not raw scores).

- **Action-Observation Loop Length:** each benchmark enforces non-trivial trajectory length `$L > 3$` to ensure sequential reasoning. Tasks solvable in 1-2 steps would blur the agentic/non-agentic distinction.

- **Comparative Normalization:** scores are normalized to the best single-agent baseline, measuring coordination gain or loss rather than absolute capability. This is what enables the paper to compare findings across benchmarks with different raw score ranges.

#### Experimental Design and Configuration Matrix

Section 4.1 specifies the full experimental design that generates the 260-configuration dataset. This is the empirical foundation for the scaling principle.

**Model selection—Intelligence Index.** The paper evaluates nine models from three LLM families, spanning Intelligence Index values from 42 to 71:

- **OpenAI:** GPT-5-nano (Index 59), GPT-5-mini (68), GPT-5 (71)
- **Google:** Gemini-2.0 Flash (47), Gemini-2.5 Flash (58), Gemini-2.5 Pro (65)
- **Anthropic:** Claude Sonnet 3.7 (42), Claude Sonnet 4 (47), Claude Sonnet 4.5 (55)

The Intelligence Index is a composite capability score integrating reasoning, coding, and knowledge benchmarks (detailed in Appendix A). It is produced by Artificial Analysis and combines eight evaluation suites: MMLU-Pro, GPQA Diamond, HLE, AIME 2025, SciCode, LiveCodeBench, IFBench, AA-LCR, Terminal-Bench Hard, and `$\tau^2$`-Bench Telecom. All models are evaluated under consistent zero-shot, instruction-prompted conditions with pass@1 scoring.

For models not yet benchmarked on the official platform, the authors independently reproduced a subset of evaluations using publicly disclosed methodology, prompts, and scoring procedures. These reconstructed values are flagged with asterisks in Table 6.

The paper also introduces an alternative **Agentic Capability Index (ACI)**, defined as each model's mean single-agent performance across all six benchmarks. The correlation between Intelligence Index and ACI is only `$r = 0.45$` (Section 4.5), validating the concern that static benchmark composites diverge from dynamic agentic performance. ACI achieves better cross-validated fit (`$R^2_{\text{CV}} = 0.413$` vs. `$0.373$`) and is recommended as the primary capability metric going forward.

**Architecture selection—structural ablation.** The five architectures are chosen to form a structured ablation over two coordination dimensions:

1. **Orchestrator presence** (hierarchical control vs. flat structure): Independent and Decentralized have no orchestrator; Centralized and Hybrid do.

2. **Peer communication** (direct sub-agent interaction vs. isolated execution): Independent and Centralized have no peer communication; Decentralized and Hybrid do.

This `$2 \times 2$` structure enables attribution of performance differences to specific coordination mechanisms. SAS provides the non-communicating single-agent baseline. If Independent (parallelism + aggregation, no communication) outperforms SAS, the gain is from ensemble effects. If Decentralized (peer debate) outperforms Independent, the additional gain is from information sharing. If Centralized (hierarchical verification) outperforms Decentralized, the additional gain is from validation bottlenecks.

**Configuration matrix.** The full experiment matrix:

- BrowseComp-Plus, Finance-Agent, PlanCraft, Workbench: 9 models × 5 architectures = 45 configurations each
- SWE-bench Verified: 8 models × 5 architectures = 40 configurations (Claude Sonnet 3.7 deprecated)
- Terminal-Bench: 8 models × 5 architectures = 40 configurations
- Total: `$45 \times 4 + 40 \times 2 = 260$` configurations

**Computational budget matching.** A critical design choice: "MAS configurations received equal computational budget through parallel agent processing (smaller per-agent iterations for `$n$`-agent teams), while SAS received proportionally more reasoning rounds to compensate for lack of parallel deliberation." Specifically, all MAS and SAS configurations are matched for total reasoning-token budget (mean `$\mu = 4,800$` tokens per trial, Section 4.4). This means if a Centralized system uses 3 sub-agents × 3 iterations per round × 5 rounds = 45 total agent invocations, the SAS baseline receives proportionally more sequential iterations so the total compute is equivalent.

**Why this matters:** without budget matching, multi-agent systems would naturally have an advantage simply because they consume more compute. A comparison that gave MAS 10× the tokens of SAS would find MAS "better" even if the architecture itself provided no benefit. By matching total tokens, the paper ensures that any observed MAS advantage comes from coordination structure, not from a larger compute budget. This is what makes the degradation findings—MAS performing *worse* despite matched compute—so striking: multi-agent systems are losing to single agents on an equal-footing comparison.

**Specific configuration parameters (Section 3.1, Appendix E):**

- Single agents: maximum 10 iterations
- Independent MAS: 3 agents, synthesis-only coordination (concatenation without cross-validation)
- Centralized MAS: 3 sub-agents + 1 orchestrator, maximum 5 orchestration rounds, 3 iterations per agent per round
- Decentralized MAS: 3 agents, 3 debate rounds, 3 iterations per round
- Hybrid MAS: centralized orchestration with limited peer communication phases

**Agent count scaling experiments (Figure 5).** Beyond the main 260-configuration matrix, the paper explores scaling the number of agents from 1 to 9 for Gemini-2.0 Flash and Gemini-2.5 Pro under Centralized and Decentralized architectures. This is reported separately because it breaks the matched-budget constraint (larger teams inherently consume more tokens even with per-agent budget reduction). The finding: Gemini-2.0 Flash shows optimal performance at 7 agents before degradation; Gemini-2.5 Pro's Decentralized architecture peaks earlier despite its higher single-agent baseline. This provides empirical evidence for the paper's claim that coordination overhead eventually outweighs parallelization benefits for any model, but the threshold varies with capability.

**Heterogeneous agent experiments (Figure 4, Table 12).** A preliminary investigation of 13 configurations on BrowseComp-Plus mixes models of different capability levels within the same LLM family (e.g., GPT-5 orchestrator with GPT-5-nano sub-agents). Key finding: "centralized heterogeneous configurations underperform their strong-model homogeneous counterparts by a mean of 12.6 percentage points, while decentralized configurations show marginal gains (+2.0 pp) largely attributable to the stronger constituent model." This suggests that model mixing does not bypass the capability-saturation threshold identified in Section 4.3.

#### Empirical Coordination Metrics: Measuring How Coordination Succeeds or Fails

Section 4.4 defines six quantitative metrics extracted from execution traces. These are the mechanistic lens through which the paper interprets *why* architectures behave differently, and they serve as predictors in the scaling principle regression (Equation 1).

**Metric 1: Coordination Overhead (`$O\%$`)**

$$O\% = \frac{T_{\text{MAS}} - T_{\text{SAS}}}{T_{\text{SAS}}} \times 100\%$$

where `$T_{\text{MAS}}$` is the total number of reasoning turns for the multi-agent configuration and `$T_{\text{SAS}}$` is the single-agent baseline turn count.

**What it computes:** the percentage increase in total reasoning turns (reasoning-response exchanges) that multi-agent coordination imposes relative to the single-agent baseline. A value of 285% (Centralized) means the system requires 3.85× as many turns as SAS.

**Why this form:** percentage normalization enables comparison across tasks with different absolute turn counts. The metric captures total communication cost, not just inter-agent messages—it includes the extra turns that sub-agents spend re-processing context, resolving ambiguities, and aligning on shared state.

**Empirical values (Table 5):** SAS = 0% (definitionally), Independent = 58%, Decentralized = 263%, Centralized = 285%, Hybrid = 515%. These are measured from trace analysis and treated as architecture-level constants applied uniformly across benchmarks.

**Metric 2: Message Density (`$c$`)**

Defined as inter-agent messages per reasoning turn. For SAS and Independent configurations, `$c = 0$` (no inter-agent communication). For communicating architectures, it captures the intensity of information exchange relative to reasoning activity.

**Empirical values (Table 5):** SAS = 0.00, Independent = 0.00, Decentralized = 0.41, Centralized = 0.39, Hybrid = 0.24. The lower value for Hybrid (0.24) despite its higher total overhead (515%) reflects that Hybrid systems spend more turns on internal processing relative to message exchange.

**Information-theoretic interpretation.** The paper reports that success rate follows an approximately logarithmic relationship with message density: `$S = 0.73 + 0.28 \ln(c)$`, `$R^2 = 0.68$`, `$p < 0.001$`, though this is explicitly flagged as a descriptive trend, not a universal functional form. Performance plateaus near `$c^* = 0.39$` messages/turn (achieved by Decentralized and Centralized), beyond which additional messages yield diminishing returns: Hybrid (515% overhead) shows `$-2.4\%` vs. Centralized (285% overhead), a difference that is not statistically significant (`$t(178) = 0.61$`, `$p = 0.542$`).

**Metric 3: Redundancy Rate (`$R$`)**

$$R = \text{mean cosine similarity of agent output embeddings}$$

ranging from 0.00 (no overlap between agent outputs) to 1.00 (identical outputs). This measures how much work agents duplicate rather than specialize.

**What it computes:** the average pairwise similarity between the final outputs produced by different agents in the same team, measured in embedding space. `$R = 0.41$` means agents produce outputs that are roughly 41% "the same" in semantic content.

**Why cosine similarity:** it captures semantic overlap rather than exact token matching, which would miss paraphrases. Two agents might produce "The answer is 42" and "I computed 42 as the result"—identical in meaning but different in tokens—and cosine similarity would capture this equivalence.

**Empirical values (Table 5):** SAS = 0.00 (only one agent), Independent = `$0.48 \pm 0.09$`, Decentralized = `$0.50 \pm 0.06$`, Centralized = `$0.41 \pm 0.06$`, Hybrid = `$0.46 \pm 0.04$`. The paper reports a negative correlation between redundancy and success (`$r = -0.136$`, `$p = 0.004$`), interpreted as a diversity-efficiency trade-off: teams need enough overlap for consensus but enough diversity for complementary reasoning. Optimal redundancy occurs at `$R \approx 0.41$` (Centralized), "balancing information fusion with reasoning independence."

**Metric 4: Coordination Efficiency (`$E_c$`)**

$$E_c = \frac{S}{T / T_{\text{SAS}}}$$

where `$S$` is the success rate (fraction of tasks correctly resolved) and `$T / T_{\text{SAS}}$` is the relative number of turns compared to the single-agent baseline.

**What it computes:** success per unit of relative turn cost. `$E_c = 0.466$` for SAS means that the single-agent baseline achieves 0.466 fractional success per "turn-unit" (where 1 turn-unit = SAS's absolute turn count). `$E_c = 0.074$` for Hybrid means it achieves only 7.4% success per turn-unit—a 6.3× decrease in computational efficiency.

**Why this form:** it normalizes performance by cost, enabling fair comparison between architectures with different computational footprints. A system might have higher raw accuracy than SAS but still be less efficient if the accuracy gain is proportionally smaller than the cost increase. This is the paper's answer to the "AI agents that matter" critique [23]: multi-agent systems often consume dramatically more compute without proportional performance gains.

**Empirical values (Table 5):** SAS = 0.466, Independent = 0.234, Decentralized = 0.132, Centralized = 0.120, Hybrid = 0.074. The monotonic decrease from SAS through Hybrid reflects the growing coordination tax: more elaborate architectures achieve similar or lower success rates at much higher turn counts, driving efficiency toward zero.

**Metric 5: Trace-Level Error Amplification (`$A_e^{\text{trace}}$`)**

Estimated from execution-trace token analysis, this quantifies how many times baseline errors propagate through agent interactions at the trace level (computational work, not just final outputs). It complements the task-level metric `$A_e^{\text{task}}$` defined in Section 3.

**Empirical values (Table 5):** SAS = 1.0 (baseline), Independent = 17.2, Decentralized = 7.8, Centralized = 4.4, Hybrid = 5.1.

**Interpretation:** in an Independent system, errors at the trace level are amplified 17.2× relative to a single agent working alone. Each agent's mistake spawns computational work that wouldn't exist in a single-agent trajectory—redundant corrections, inconsistent state resolution, and response synthesis from contradictory information. Centralized coordination contains this to 4.4× by enforcing validation bottlenecks where the orchestrator intercepts errors before they propagate through the full system.

**Metric 6: Turn Count Scaling with Agent Count**

The paper fits a power law to the relationship between total reasoning turns `$T$` and the number of agents `$n$`:

$$T = 2.72 \times (n + 0.5)^{1.724}, \quad R^2 = 0.974, \quad p < 0.001$$

with 95% CI on the exponent: `$[1.685, 1.763]$`.

**What it reveals:** the exponent `$1.724 > 1$` indicates super-linear growth—each additional agent increases total turns by more than a constant factor. This contrasts with neural scaling laws where relationships are typically sub-linear (Kaplan et al. report exponent `$b = 0.76$` for dense models). The super-linear growth reflects quadratic message complexity (all-to-all communication potential) tempered by practical bandwidth limits. The implication is stark: "under fixed computational budgets, per-agent reasoning capacity becomes prohibitively thin beyond 3–4 agents, creating a hard resource ceiling where communication cost dominates reasoning capability." Extrapolation to `$n = 10$` predicts approximately 157 turns (95% CI: `$[143, 172]$`), or 21.8× the SAS baseline of 7.2 turns.

**Additional mechanistic measures (Section 4.4).**

Beyond these six core metrics, the paper reports several auxiliary measurements:

- **Error absorption:** `$\text{Absorb} = (E_{\text{SAS}} - E_{\text{MAS}}) / E_{\text{SAS}}$`. Centralized and Hybrid architectures achieve 22.7% average error reduction (95% CI: `$[20.1\%, 25.3\%]$`), peaking at 31.4% for Finance-Agent where structured numerical outputs facilitate verification. Independent MAS shows no error correction (+4.6% amplification) due to the absence of any inter-agent verification mechanism.

- **Token-overlap categories:** each token in agent rationales is labeled as unique (one agent), shared (two or more agents), or contradictory (semantic opposition, BERTScore < 0.3). High-performing runs exhibit increased shared-token entropy (mean ≈1.8 bits for Finance-Agent; `$p < 0.001$` vs. low performers) and reduced contradictory mass (median 2.3% in successes vs. 8.1% in failures). This operationalizes the mechanism: coordination succeeds when agents converge toward mutually consistent sub-proofs rather than self-reinforcing errors.

- **Error taxonomy** building on MAST [15]: four error categories (logical contradiction, numerical drift, context omission, coordination failure) are measured across architectures. Centralized systems reduce logical contradictions by 36.4% (from 12.3–18.7% baseline to 9.1%), context omissions by 66.8% (from 15.8–25.2% to 8.3%), and numerical drift by 24% (from 20.9–24.1% to 18.3%). Hybrid systems amplify numerical drift to 26.4% as rounding errors propagate through multiple coordination layers, and exhibit 12.4% coordination failures from protocol complexity.

- **Information gain `$\Delta I$`:** computed via Bayesian posterior variance reduction comparing pre-coordination and post-coordination task-uncertainty surrogates. In Finance-Agent, `$\Delta I$` correlates strongly with MAS–SAS performance gap (`$r = 0.71$`, `$p < 0.001$`), with successful trials showing `$\Delta I = 0.8$`–2.1 bits vs. failures at 0.2–0.6 bits. In BrowseComp-Plus, the correlation is weak and non-significant (`$r = 0.18$`, `$p = 0.22$`), interpreted as evidence that world ambiguity limits the value of information exchange.

**Token efficiency (success per 1,000 tokens):** SAS achieves 67.7 successes/1K tokens; Centralized drops to 21.5 (3.1× worse); Decentralized to 23.9 (2.8× worse); Hybrid to 13.6 (5.0× worse). These metrics quantify the economic cost of multi-agent coordination independent of whether raw accuracy improves.

#### The Scaling Principle Regression Model

Section 4.3 presents the paper's central quantitative contribution: a regression equation that predicts agent-system performance from model capability, task properties, architecture type, and empirical coordination metrics.

**Model objective.** The model predicts `$P$`, the task success rate (accuracy), as a function of four categories of predictors:

1. **Base model capability:** Intelligence Index `$I$` (or alternatively, the task-grounded Agentic Capability Index)

2. **System configuration:** agent count `$n_a$`

3. **Task properties:** tool count `$T$` (log-transformed) and single-agent baseline performance `$P_{\text{SA}}$`

4. **Empirical coordination metrics:** overhead `$O\%$` (log-transformed), message density `$c$`, redundancy `$R$`, coordination efficiency `$E_c$`, and trace-level error amplification `$A_e^{\text{trace}}$` (log-transformed)

**The complete functional form:**

$$\begin{aligned}
P = &\; \beta_0 \\
&+ \beta_1 (I - \bar{I}) \\
&+ \beta_2 (I - \bar{I})^2 \\
&+ \beta_3 \log(1 + T) \\
&+ \beta_4 \log(1 + n_a) \\
&+ \beta_5 \log(1 + O\%) \\
&+ \beta_6 c \\
&+ \beta_7 R \\
&+ \beta_8 E_c \\
&+ \beta_9 \log(1 + A_e^{\text{trace}}) \\
&+ \beta_{10} P_{\text{SA}} \\
&+ \beta_{11} (I \times E_c) \\
&+ \beta_{12} (A_e^{\text{trace}} \times P_{\text{SA}}) \\
&+ \beta_{13} (O\% \times T) \\
&+ \beta_{14} (R \times n_a) \\
&+ \beta_{15} (c \times I) \\
&+ \beta_{16} (E_c \times T) \\
&+ \beta_{17} (P_{\text{SA}} \times \log(1 + n_a)) \\
&+ \beta_{18} (I \times \log(1 + T)) \\
&+ \beta_{19} (A_e^{\text{trace}} \times T) \\
&+ \varepsilon
\end{aligned}$$

**Variable definitions and transformations:**

- `$I$`: Intelligence Index, mean-centered at `$\bar{I} = 57.5$` to address multicollinearity between `$I$` and `$I^2$` (VIF reduced from 200 to 1.1)
- `$T$`: number of available tools (range: 2–16)
- `$n_a$`: number of agents (range: 1–4 for main configurations, 1–9 for scaling experiments)
- `$O\%$`: coordination overhead percentage (range: 0–515%)
- `$c$`: message density (messages per reasoning turn)
- `$R$`: redundancy (cosine similarity of agent outputs)
- `$E_c$`: coordination efficiency (success per relative turn cost)
- `$A_e^{\text{trace}}$`: trace-level error amplification factor (range: 1.0–17.2)
- `$P_{\text{SA}}$`: single-agent baseline accuracy for the given model on the given benchmark

All predictors are standardized (`$\mu = 0$`, `$\sigma = 1$`) after transformation. Log transformations are applied to right-skewed variables spanning multiple orders of magnitude to improve approximate linearity.

**What this equation computes:** for any combination of (model, task, architecture), plug in the measured values of the predictors and the fitted coefficients from Table 4, and the equation outputs a predicted accuracy `$P$`. This enables "what-if" analysis: for a given task with known `$T$` and `$P_{\text{SA}}$`, and a model with known `$I$`, you can compute the expected accuracy under each architecture by using that architecture's coordination metrics (`$O\%$`, `$c$`, `$R$`, `$E_c$`, `$A_e^{\text{trace}}$`) from Table 5.

**Why this form—design choices and mechanistic hypotheses:**

The model's structure reflects specific mechanistic hypotheses about how coordination affects performance, rather than being a generic flexible regression. Each term is included for a reason:

**Main effects capture direct relationships:**
- `$\beta_1 (I - \bar{I})$`: linear capability effect. The hypothesis is that more capable models perform better, and Table 4 confirms this with `$\hat{\beta}_1 = 0.126$`, `$p = 0.008$`—each unit increase in standardized Intelligence Index corresponds to 0.126 standard deviation increase in predicted accuracy.
- `$\beta_2 (I - \bar{I})^2$`: quadratic capability term to test for accelerating or diminishing returns. The result (`$\hat{\beta}_2 = -0.000$`, `$p = 0.977$`) indicates no evidence of non-linear capability scaling within the tested range (`$I \in [42, 71]$`).
- `$\beta_3 \log(1 + T)$`: tool diversity benefit. More tools provide more capabilities, and the positive coefficient (`$\hat{\beta}_3 = 0.166$`, `$p < 0.001$`) confirms this. The log transform captures diminishing returns—adding a 17th tool to 16 tools matters less than adding a 3rd tool to 2 tools.
- `$\beta_{10} P_{\text{SA}}$`: task difficulty proxy, directly using the single-agent baseline as a measure of how hard the task is for that model.

**Interaction terms test specific hypotheses:**

- **Capability-saturation (`$\beta_{17}$`):** `$P_{\text{SA}} \times \log(1 + n_a)$`. The hypothesis is that multi-agent coordination provides diminishing returns when single-agent performance is already high—there's less room for improvement, and coordination overhead becomes a net cost. Table 4 confirms this with `$\hat{\beta}_{17} = -0.236$`, `$p = 0.004$`. This is the strongest and most robust interaction in the model.

- **Efficiency-tools trade-off (`$\beta_{16}$`):** `$E_c \times T$`. The hypothesis is that coordination inefficiency matters more in tool-rich environments. When `$E_c$` is low (poor coordination efficiency) and `$T$` is high (many tools), the penalty compounds. Table 4 confirms: `$\hat{\beta}_{16} = -0.096$`, `$p = 0.002$`.

- **Overhead-tool scaling (`$\beta_{13}$`):** `$O\% \times T$`. The hypothesis is that coordination overhead costs scale with task complexity. Direction is negative (`$\hat{\beta}_{13} = -0.033$`) but loses significance under cluster-robust inference (`$p = 0.211$`), and is reported as a directional pattern.

- **Error-baseline interaction (`$\beta_{12}$`):** `$A_e^{\text{trace}} \times P_{\text{SA}}$`. The hypothesis is that error amplification matters more when baseline performance is high—when tasks are easy, the cost of introducing errors is proportionally larger. Table 4 shows `$\hat{\beta}_{12} = -0.080$`, `$p = 0.022$`.

- **Redundancy benefit with scale (`$\beta_{14}$`):** `$R \times n_a$`. The hypothesis is that redundant work provides error-correction benefits when more agents participate—if multiple agents independently verify the same sub-problem, errors are more likely to be caught. Table 4 confirms a weak positive effect: `$\hat{\beta}_{14} = 0.024$`, `$p = 0.034$`, but notes this is "minor compared to efficiency losses" (`$|\hat{\beta}_{E_c \times T}| = 0.096$`, 4× larger).

- **Capability-efficiency (`$\beta_{11}$`):** `$I \times E_c$`. Tests whether more capable models benefit more or less from coordination efficiency. Not significant (`$\hat{\beta}_{11} = -0.011$`, `$p = 0.653$`), suggesting capability and coordination efficiency have independent additive effects.

- **Communication-capability (`$\beta_{15}$`):** `$c \times I$`. Tests whether more capable models use communication more or less effectively. Not significant (`$\hat{\beta}_{15} = -0.016$`, `$p = 0.457$`).

- **Capability-tools (`$\beta_{18}$`):** `$I \times \log(1 + T)$`. Tests whether more capable models benefit more from tool-rich environments. Not significant (`$\hat{\beta}_{18} = -0.051$`, `$p = 0.112$`).

- **Error-tool interaction (`$\beta_{19}$`):** `$A_e^{\text{trace}} \times T$`. Tests whether error amplification is worse in tool-rich systems. Not significant (`$\hat{\beta}_{19} = 0.022$`, `$p = 0.332$`).

**Why the model uses log transformations for certain variables:** `$O\%$` (0–515%), `$T$` (2–16), `$n_a$` (1–9), and `$A_e^{\text{trace}}$` (1.0–17.2) span multiple orders of magnitude and are right-skewed. The log transform improves approximate linearity—going from 1 to 2 agents likely matters more than going from 8 to 9—and reduces the influence of extreme values. The `$1 + x$` form handles zero values (e.g., `$O\% = 0$` for SAS) without introducing `$-\infty$`.

**Why the model excludes certain interactions:** the paper "deliberately excludes interactions without clear mechanistic justification (e.g., `$R \times c$`, `$I \times O\%$`) to avoid overfitting." This is a principled approach to model construction: terms are included only when there is a hypothesis about *why* the interaction should exist, not because data-mining found a correlation. All interaction terms retained in the model showed VIF < 5, confirming no severe multicollinearity.

**Fitting and validation procedure.** The model is fit using ordinary least squares on all 260 configurations. Cross-validation uses 5-fold experiment-level holdout—configurations are split at the experiment level (not the instance level) to prevent data leakage between related configurations. The model achieves:

- `$R^2_{\text{train}} = 0.463$`, `$R^2_{\text{CV}} = 0.373$` (±0.170 SD) using Intelligence Index
- `$R^2_{\text{train}} = 0.481$`, `$R^2_{\text{CV}} = 0.413$` (±0.130 SD) using Agentic Capability Index

**Model comparison (Table 3).** The paper provides an ablation showing progressive inclusion of predictor categories:

| Model Specification | `$R^2_{\text{train}}$` | `$R^2_{\text{CV}}$` | AIC |
|---|---|---|---|
| Intelligence + Tools + Agents | 0.405 | 0.360 | −238.8 |
| + Coordination structure | 0.428 | 0.363 | −243.2 |
| + Single-agent baseline | 0.429 | 0.358 | −242.0 |
| + Interaction terms (full model) | 0.463 | 0.373 | −236.3 |

The full model with interaction terms achieves the best cross-validated fit and lowest AIC, confirming that the empirical coordination metrics and their interactions capture meaningful variance beyond what base predictors alone explain.

**Deriving the architecture selection threshold.** From the fitted coefficients, the paper extracts a decision boundary between single-agent and multi-agent deployment:

$$P_{\text{SA}}^* = -\frac{\hat{\beta}_4}{\hat{\beta}_{17}} \approx \frac{0.040}{0.236} = 0.170 \text{ (in standardized units)}$$

which corresponds to raw performance `$\approx 0.45$` after denormalization. Operationally: **if your single-agent baseline exceeds approximately 45% accuracy, multi-agent coordination is unlikely to help and may hurt. If it's below 45%, MAS can provide net benefits.**

**Why this threshold is important:** it replaces heuristic architecture selection with a quantitative criterion derived from data. Cross-validation confirms this rule achieves 87% correct architecture selection on held-out configurations, substantially exceeding random choice (20%) or capability-only models (54%).

**What the model does NOT do—explicit limitations.** The paper acknowledges several boundaries:

- The model predicts relative architecture ranking better than absolute cross-domain performance, as shown by leave-one-dataset-out cross-validation.
- The model `$\beta$` coefficients may not generalize to model capability levels far outside the training range (`$I \in [42, 71]$`), as shown by the over-prediction of SAS performance for held-out models with `$I = 75$` (Section 4.5, Appendix B).
- Dataset-level predictors lose significance under cluster-robust inference because with only `$G = 6$` clusters (benchmarks), standard errors inflate substantially. The paper transparently reports both naive and cluster-robust estimates (Table 14) and frames dataset-level findings as "directional patterns supported by directional consistency rather than confirmed at conventional significance levels."

**Robustness checks (Section 4.5).** Three analyses validate the model's reliability:

1. **Cluster-robust inference:** re-estimating with standard errors clustered at the dataset level (`$G = 6$`, CR1 correction, `$t_5$` critical values). Several predictors lose significance: `$\log(1+T)$` (`$p = 0.172$`), `$I$` (`$p = 0.059$`), `$E_c \times T$` (`$p = 0.205$`), and `$P_{\text{SA}} \times \log(1+n_a)$` (`$p = 0.105$`). However, `$P_{\text{SA}}$` alone survives (`$p = 0.004$`) and `$A_e^{\text{trace}} \times P_{\text{SA}}$` survives (`$p = 0.030$`), making capability saturation the most robust finding.

2. **Multiple-comparison correction:** applying Holm–Bonferroni step-down procedure to control family-wise error rate at `$\alpha = 0.05$` across 19 hypothesis tests. Three predictors survive: `$\log(1+T)$` (`$p_{\text{Holm}} < 0.001$`), `$P_{\text{SA}}$` (`$p_{\text{Holm}} = 0.018$`), and `$E_c \times T$` (`$p_{\text{Holm}} = 0.026$`). Two more (`$I$` and `$P_{\text{SA}} \times \log(1+n_a)$`) are suggestive (`$p_{\text{Holm}} < 0.10$`).

3. **Capability metric sensitivity:** replacing Intelligence Index with ACI maintains qualitatively consistent results (`$R^2_{\text{CV}}$` improves from 0.373 to 0.413) with "zero finding reversals."

The convergence across these checks establishes a hierarchy of confidence: capability-saturation is the most robust result (survives both cluster-robust and multiple-comparison correction), the tool-coordination trade-off is moderately robust (survives Holm-Bonferroni but not cluster-robust), and other directional patterns (e.g., redundancy benefit, capability linearity) are statistically suggestive but require larger-scale replication with more benchmarks to achieve conventional significance under conservative inference.

## 4. Key Insights and Innovations

### Innovation 1: Difficulty-Conditioned Scaling as a Diagnostic Framework—Not a New Architecture, but a New Lens

The most fundamental move this paper makes is not proposing a new coordination mechanism, but rather reframing the question itself. Prior to this work, the multi-agent systems literature operated under an implicit framing: "which architecture is best?" The answer, across dozens of papers, was some variant of "it depends"—on the task, on the model, on the evaluation setup—but the field lacked the vocabulary and the empirical framework to characterize *what* it depends on and *why*. The typical evaluation compared a handful of architectures on one or two benchmarks, reported which one won, and concluded that the winning architecture was generally preferable.

This paper dismantles that framing entirely. In its place, it introduces the concept of **architecture-task alignment as the central object of study**, not a nuisance variable to be controlled away. The key diagnostic move is straightforward but transformative: rather than asking "does multi-agent coordination help?", the paper asks "under what measurable conditions does each coordination mechanism improve or degrade performance?" The difference is between evaluating a drug by asking whether it cures disease versus characterizing the patient populations, dosage regimes, and biomarkers that determine treatment response. The former yields coarse conclusions ("sometimes it works, sometimes it doesn't"); the latter yields predictive principles.

What makes this a genuine conceptual advance rather than an obvious reframing is the **empirical demonstration that the answer is non-monotonic and sometimes counterintuitive**. The paper shows, across 260 controlled configurations, that the *same* architecture—Centralized coordination—delivers +80.8% improvement on financial reasoning but −50.3% degradation on Minecraft planning (Figure 2). The *same* task class—sequential planning—shows universal degradation across *all* multi-agent architectures (PlanCraft: −39% to −70%). The *same* capability increase—moving from GPT-5-nano to GPT-5—produces gains under some architectures and losses under others, depending on whether the baseline has crossed the ~45% capability-saturation threshold.

These are not marginal effects. The performance range spans from +80.8% to −70.0%, a gap of over 150 percentage points, driven entirely by the interaction between architecture choice and task structure. Prior work that reported "multi-agent debate improves reasoning by X%" or "hierarchical orchestration degrades planning by Y%" was implicitly sampling from one region of this landscape. The paper's central insight is that these conflicting findings are not contradictions—they are **samples from different points on a common surface** that the field had not yet mapped.

The significance extends beyond this paper's specific findings. By establishing that architecture-task alignment is the primary driver of coordination effectiveness—not team size, not model capability alone, not any single architectural feature—the paper provides a **conceptual framework for the entire subfield**. Future work evaluating new coordination mechanisms should not merely report whether they outperform baselines on some benchmark; it should characterize where on the difficulty-capability-architecture landscape the benefits appear, and where the costs dominate. The paper's 45% capability-saturation threshold, tool-coordination trade-off, and error amplification hierarchy are first estimates of the shape of this landscape—they will almost certainly be refined by future work—but the framework itself is the enduring contribution.

This is a fundamental shift, not an incremental refinement. It changes the research question from "what works?" to "what works when, and how do we measure the when?"

### Innovation 2: The 45% Capability-Saturation Threshold as an Empirical Law—with Sharp Theoretical Implications

Section 4.3 derives what is arguably the paper's most consequential single finding: when single-agent baselines exceed approximately 45% accuracy, multi-agent coordination yields diminishing returns (coefficient `$\hat{\beta}_{17} = -0.236$`, `$p = 0.004$`), and this threshold correctly predicts optimal architecture choice for 87% of held-out configurations. This is the finding that survives every robustness check the paper applies—cluster-robust standard errors (`$p = 0.004$`), Holm-Bonferroni multiple-comparison correction (`$p_{\text{Holm}} = 0.018$`), and capability metric replacement—making it by far the most statistically reliable result in the paper.

But the *significance* of this finding goes well beyond its statistical robustness. It functions as an **empirical law with clear theoretical implications** that challenge prevailing assumptions in the multi-agent systems literature.

**What the threshold means conceptually.** The 45% figure operationalizes an intuitive idea: coordination can amplify existing capability but cannot create it from nothing. If a single agent already solves the task correctly roughly half the time, adding more agents introduces coordination overhead (messages, context-switching, consensus-formation) that costs more in compute and introduces more potential error modes than the marginal improvement in accuracy justifies. Below 45%, the single agent is struggling—producing incorrect answers or failing to complete tasks—and multi-agent coordination provides genuine benefits through parallel exploration, error correction via verification, and decomposition of complex problems into simpler sub-problems that individual agents can handle.

The precise numeric value (45%) is less important than the **existence of a threshold and its measurability**. This is analogous to how the Chinchilla scaling laws established that optimal pretraining allocates roughly equal scaling to parameters and data—the exact ratio is an empirical finding that may shift with model architecture or data distribution, but the *concept* of an optimal allocation and the methodology for finding it transformed how the field thinks about training compute. Similarly, the 45% threshold may shift with better verifiers, more efficient communication protocols, or different model families. But the *methodology* of measuring single-agent baselines and using them to predict multi-agent benefit is a transferable principle.

**Why this challenges prior assumptions.** The most common heuristic in the multi-agent literature—explicit in paper titles like "More Agents Is All You Need" [41] and implicit in the design of many agent architectures—is that adding agents monotonically improves performance, with coordination overhead as a manageable cost. The capability-saturation threshold directly contradicts this: there is a **hard ceiling** beyond which coordination becomes a net cost, and for many frontier models on many benchmarks, we are already above that ceiling.

This explains a pattern that had been puzzling the field. Gao et al. [16] found that "benefits diminish as base models improve, with frontier models often outperforming teams." Neubig [17] argued "don't sleep on single-agent systems." Cognition AI [18] took the strongest position: "don't build multi-agents." These findings seemed contradictory to the "more agents is all you need" narrative, but the capability-saturation threshold reconciles them: as models improve, an increasing fraction of tasks cross above 45% single-agent accuracy, and multi-agent systems go from providing benefits to imposing costs. The conflicting findings are not about methodology or benchmark selection—they are about *where on the capability curve* the evaluations were conducted.

**The theoretical implication: a boundary on collaborative scaling.** The most profound implication of the threshold is that it establishes a **boundary condition** for multi-agent systems that is fundamentally different from neural scaling laws. Neural scaling laws (Kaplan et al. [54]) describe monotonic improvement with scale—larger models, more data, more compute all produce better performance, albeit with diminishing returns. Collaborative scaling, this paper demonstrates, is **non-monotonic**: more agents help below the capability threshold and hurt above it. This means the scaling behavior of agent systems cannot be described by simple power laws of the form `$\text{performance} \propto (\text{agents})^\alpha$`. It requires a more complex framework that accounts for the interaction between baseline capability and coordination cost.

This is a fundamental distinction, not an incremental refinement. It means the toolkit of scaling laws developed for pretraining cannot be directly applied to multi-agent systems without modification. The paper's regression model (Equation 1) is a first attempt at such a framework, with the `$P_{\text{SA}} \times \log(1 + n_a)$` interaction term explicitly capturing the non-monotonic relationship.

### Innovation 3: Empirical Coordination Metrics as a Diagnostic Instrument

Most multi-agent evaluation papers report a single number: final task accuracy. This paper introduces and systematically measures six **empirical coordination metrics**—coordination overhead (`$O\%$`), message density (`$c$`), redundancy rate (`$R$`), coordination efficiency (`$E_c$`), trace-level error amplification (`$A_e^{\text{trace}}$`), and turn count scaling—that are extracted from execution traces and treated as mechanistic diagnostics rather than final performance measures.

The innovation is not any single metric. Overhead, message density, and redundancy have been discussed conceptually in prior work (e.g., Malone and Crowston's [29] coordination theory, Cemri et al.'s [15] failure taxonomy). What is distinctive is the **systematic, quantitative measurement of these properties across 260 configurations and their integration into a predictive model**. This transforms them from qualitative concepts into operational instruments.

Consider what the metrics reveal that raw accuracy hides:

- **Trace-level error amplification (`$A_e^{\text{trace}}$`)** exposes a dramatic difference in failure modes: Independent architectures amplify errors 17.2× relative to single-agent baselines, while Centralized architectures contain this to 4.4× (Table 5). Both architectures might achieve similar raw accuracy on some benchmarks (e.g., Workbench, where Independent and Centralized differ by only a few percentage points; Figure 2d), but the error amplification metric reveals that they are achieving that accuracy through fundamentally different mechanisms—one through unchecked error propagation, the other through active error suppression. This matters for robustness: a system with 17.2× error amplification is far more vulnerable to distribution shift or edge cases where errors are harder to vote away.

- **Coordination efficiency (`$E_c$`)** reveals the hidden cost of elaborate architectures. Hybrid achieves the highest raw overhead (515%) but only modest accuracy improvements on structured tasks, yielding `$E_c = 0.074$`—meaning each unit of computational cost produces only 16% of the success that the same cost would produce under single-agent deployment. A practitioner comparing only raw accuracy between Hybrid and Decentralized might conclude they're comparable; the efficiency metric reveals that Hybrid costs 3.2× more per unit of success.

- **Redundancy (`$R$`)** reveals an optimal range for agent diversity. The negative correlation between redundancy and success (`$r = -0.136$`, `$p = 0.004$`) and the identification of `$R \approx 0.41$` (Centralized) as optimal operationalize a trade-off that had been discussed qualitatively: teams need enough overlap for consensus but enough diversity for complementary reasoning. Decentralized architectures, with `$R = 0.50$` and strong performance on tool-heavy tasks, approach the upper bound of useful redundancy; beyond this point, agents duplicate work without adding value.

The significance of these metrics extends beyond this paper. They provide a **diagnostic toolkit** for evaluating future multi-agent systems. Rather than asking only "does this new architecture improve accuracy?", researchers can ask: "Does it reduce error amplification? Does it improve coordination efficiency? Does it operate in the optimal redundancy band?" These questions have clearer mechanistic answers than raw accuracy comparisons, and they are more likely to generalize across tasks and model families. The paper's regression model (Equation 1) demonstrates that these metrics explain performance variance (`$R^2 = 0.373$`) beyond what categorical architecture labels alone achieve, confirming their diagnostic value.

This is a methodological innovation rather than a theoretical one—the paper gives the field new instruments for measuring coordination quality, analogous to how the introduction of BLEU and ROUGE gave machine translation and summarization standardized evaluation metrics. The specific numerical values of these metrics (17.2× error amplification, 0.41 optimal redundancy) are first estimates that will be refined, but the **practice of measuring coordination dynamics rather than just outcomes** is the lasting contribution.

### Innovation 4: The Tool-Coordination Trade-Off as a Mechanistic Explanation for a Common Failure Mode

One of the paper's most practically consequential findings is that multi-agent systems degrade disproportionately on tool-heavy tasks. The regression coefficient for the `$E_c \times T$` interaction is `$\hat{\beta} = -0.096$` (`$p = 0.002$`, survives Holm-Bonferroni correction at `$p_{\text{Holm}} = 0.026$`), indicating that coordination efficiency penalties compound as the number of available tools increases.

The paper goes beyond reporting this correlation to provide a **mechanistic explanation** grounded in the token-budget constraint. Under matched total reasoning tokens (mean 4,800 per trial, Section 4.4), multi-agent systems must divide a fixed budget across coordination overhead (inter-agent messages, context-switching, orchestrator synthesis) and domain reasoning (tool selection, parameter configuration, output interpretation). When the task involves 16 tools (e.g., Workbench), the per-agent budget for tool orchestration shrinks substantially compared to a single agent that can devote its entire budget to the 16 tools without coordination overhead. The finding that Decentralized outperforms Centralized on Workbench (mean 0.664 vs. 0.621, Figure 2d) despite higher raw overhead (263% vs. 285%) is consistent with this mechanism: Decentralized's parallel efficiency allows more of the fixed budget to reach tool reasoning, while Centralized's orchestrator bottleneck consumes budget that could otherwise support tool use.

What makes this a distinctive contribution rather than an obvious observation is that it **contradicts the naïve scaling hypothesis**. The intuitive assumption would be that more agents help with more complex tasks—that if a single agent struggles with 16 tools, a team of 3 agents with an orchestrator would handle them better through division of labor. The paper shows this assumption is systematically wrong: tool complexity amplifies the coordination tax rather than being mitigated by it. The architectural advice that follows is counterintuitive but empirically grounded: for tool-heavy tasks, simpler architectures (SAS or Decentralized) outperform more elaborate ones (Centralized or Hybrid) because they preserve more of the fixed token budget for tool reasoning.

This finding has immediate practical implications. Many real-world agent deployments—software engineering (SWE-bench, 7 tools), business automation (Workbench, 16 tools), scientific workflows—involve extensive tool use. The paper provides quantitative evidence that multi-agent coordination on such tasks requires explicit attention to per-agent tool budget, not just overall accuracy. The fact that SWE-bench shows slight degradation across all MAS architectures (Figure 2e, −2% to −15%) despite being a seemingly decomposable engineering task is explained by the combination of high tool count (7) and baseline performance above the 45% threshold—the tool-coordination trade-off and capability-saturation both push toward single-agent deployment.

This is an incremental refinement of the broader architecture-task alignment insight (Innovation 1), but a practically important one: it identifies a specific, measurable task property (tool count) that strongly moderates coordination effectiveness, and provides a mechanistic account of why.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper evaluates on six agentic benchmarks: BrowseComp-Plus (100 instances, web browsing and information synthesis), Finance-Agent (50 instances, financial analysis with expert rubrics), PlanCraft (100 instances, Minecraft crafting planning), WorkBench (100 instances, business task automation with 16 tools), SWE-bench Verified (20-instance subset, deterministic shuffle seed 42, software engineering with 7 tools), and Terminal-Bench (20 instances, first-N from 86, CLI task execution with 2 tools). All benchmarks satisfy the agentic criteria from Section 3.2: they require sustained multi-step environmental interaction, partial observability, and adaptive strategy refinement. The tool-count range across benchmarks is {2, 3, 4, 5, 7, 16}, providing the variation needed to estimate the tool-coordination trade-off coefficient.

- **Base model(s).** Nine models from three LLM families spanning Intelligence Index values from 42 to 71: OpenAI (GPT-5-nano at Index 59, GPT-5-mini at 68, GPT-5 at 71), Google (Gemini-2.0 Flash at 47, Gemini-2.5 Flash at 58, Gemini-2.5 Pro at 65), and Anthropic (Claude Sonnet 3.7 at 42, Claude Sonnet 4 at 47, Claude Sonnet 4.5 at 55). The Intelligence Index is a composite capability score integrating reasoning, coding, and knowledge benchmarks (Appendix A). The paper also introduces the Agentic Capability Index (ACI), each model's mean single-agent performance across all six benchmarks, as a task-grounded alternative—the correlation between Intelligence Index and ACI is only r = 0.45 (Section 4.5), validating the concern that static benchmark composites diverge from dynamic agentic performance. Claude Sonnet 3.7 was deprecated in February 2026 and is unavailable for SWE-bench Verified and Terminal-Bench, yielding 8 models for those two benchmarks and a total of N = 260 configurations (45 × 4 + 40 × 2).

- **Metrics.** The primary outcome is task success rate (accuracy), computed domain-specifically: factual correctness for Finance-Agent (Cohen's κ = 0.91), task completion for WorkBench (κ = 0.89), goal satisfaction for PlanCraft (κ = 0.87), and page synthesis accuracy for BrowseComp-Plus (κ = 0.88). All κ values exceed 0.80, indicating strong inter-rater reliability. SWE-bench Verified and Terminal-Bench use Docker-based evaluation with objective pass/fail criteria tied to test suites and environment metrics. Secondary metrics include coordination overhead O% (percentage increase in reasoning turns over SAS), message density c (inter-agent messages per reasoning turn), redundancy R (cosine similarity of agent output embeddings), coordination efficiency E_c = S / (T / T_SAS) (success normalized by relative turn cost), and trace-level error amplification A_e^trace (estimated from execution-trace token analysis). The task-level error amplification A_e^task = E_MAS / E_SAS (defined in Section 3) captures final-output error dynamics, while A_e^trace captures computational work arising from coordination failures—they capture complementary aspects of error dynamics (A_e^task ≈ 1.1–1.3 vs. A_e^trace ≈ 4–17). All metrics are normalized per reasoning turn and per token to enable cross-architecture comparison.

- **Baselines.** The primary baseline is the Single-Agent System (SAS) operating with matched total reasoning tokens (mean μ = 4,800 per trial, Section 4.4). SAS serves as the reference for all relative performance calculations: percentage annotations in Figure 2 represent (mean_MAS − mean_SAS) / mean_SAS × 100%. Within each benchmark, the best SAS performance across the 9 (or 8) models provides the normalization reference for cross-model comparisons. The four multi-agent architectures (Independent, Centralized, Decentralized, Hybrid) are compared against SAS rather than against each other, since the paper's central question is whether multi-agent coordination provides benefit over single-agent alternatives.

- **Generation budget / compute accounting.** All MAS and SAS configurations are matched for total reasoning-token budget (mean μ = 4,800 tokens per trial, Section 4.4) to isolate coordination effects from raw compute advantages. Specific per-configuration parameters from Section 3.1 and Appendix E: Single agents receive maximum 10 iterations; Independent MAS uses 3 agents with synthesis-only coordination (concatenation without cross-validation); Centralized MAS uses 3 sub-agents + 1 orchestrator across maximum 5 orchestration rounds with 3 iterations per agent per round; Decentralized MAS uses 3 agents across 3 debate rounds with 3 iterations per round; Hybrid combines centralized orchestration with limited peer communication phases. The budget-matching strategy means MAS configurations receive smaller per-agent iterations for n-agent teams while SAS receives proportionally more reasoning rounds to compensate for lack of parallel deliberation. This ensures that any observed MAS advantage comes from coordination structure, not from a larger compute budget. Turn counts in Table 5 reveal the actual computational footprints: SAS requires 7.2 ± 2.1 turns, Independent requires 11.4 ± 3.2, Decentralized requires 26.1 ± 7.5, Centralized requires 27.7 ± 8.1, and Hybrid requires 44.3 ± 12.4.

- **Cross-validation / statistical protocol.** The scaling principle regression (Equation 1, 20 parameters) uses 5-fold cross-validation with experiment-level holdout—configurations are split at the experiment level (not the instance level) to prevent data leakage between related configurations. The model achieves R^2_CV = 0.373 (±0.170 SD) using Intelligence Index and R^2_CV = 0.413 (±0.130 SD) using the task-grounded Agentic Capability Index. Robustness checks in Section 4.5 address three statistical threats: (1) cluster-robust standard errors (clustering on dataset, G = 6, CR1 correction, t_5 critical values) to address pseudoreplication; (2) Holm–Bonferroni step-down procedure for multiple-comparison correction across 19 hypothesis tests; (3) capability metric sensitivity analysis comparing Intelligence Index vs. ACI. Leave-one-dataset-out (LODO) cross-validation is used to assess cross-domain generalization. For architecture selection, within-domain cross-validated evaluation tests whether the model correctly identifies the optimal architecture for held-out configurations. Bootstrap 95% confidence intervals (10,000 resamples) are reported for SWE-bench Verified and Terminal-Bench per-cell resolution rates (Table 16), with typical widths of ±20 percentage points at n = 20 instances.

### Main Quantitative Results

#### Aggregate Multi-Agent Performance Across Benchmarks (Figure 2)

The headline finding from the 260-configuration experiment matrix is that multi-agent performance relative to single-agent baselines spans from +80.8% improvement to −70.0% degradation, with an overall mean MAS improvement of −0.3% (95% CI: [−58.7%, +77.2%]) and high variance (σ = 37.5%). This means that, aggregating across all benchmarks, architectures, and model families, multi-agent systems provide essentially zero net benefit on average—but the average obscures enormous heterogeneity that is the paper's central object of study.

**Finance-Agent (Figure 2b) shows the strongest multi-agent benefits.** Centralized achieves +80.8% relative improvement (mean success 0.631 vs. SAS 0.349), Decentralized achieves +74.5% (0.609), Hybrid reaches +73.1% (0.604), and Independent reaches +57.0% (0.548). All four MAS architectures substantially outperform the single-agent baseline. The mechanism, identified through execution-trace analysis (Section 4.2), is that financial analysis naturally decomposes into parallel information streams—regulatory analysis, SEC filing research, operational impact assessment—that can be executed independently and then synthesized by an orchestrator. Single-agent execution exhibits sequential bottlenecks where a single agent must explore superficially across multiple dimensions; centralized coordination enables depth in each dimension simultaneously.

**PlanCraft (Figure 2c) exhibits universal multi-agent degradation.** All four MAS architectures perform worse than SAS, with Independent showing the largest drop at −70.0% (0.170 vs. SAS 0.568), Centralized at −50.3% (0.282), Decentralized at −41.5% (0.332), and Hybrid at −39.1% (0.346). Execution traces reveal that multi-agent systems decompose inherently sequential tasks—looking up a recipe, moving materials, crafting—into artificial subtasks that generate substantial coordination messages (average for PlanCraft tasks requiring only a few execution steps), consuming token budget on coordination rather than reasoning. The paper provides a concrete trace comparison: a single agent crafting a diorite_wall completes the task in 3 turns (search recipe, move materials, craft), while a centralized system spawns agent roles for "recipe research," "inventory checking," and "crafting execution," where only the last is necessary—the first two duplicate information that any agent can access instantly.

**BrowseComp-Plus (Figure 2a) shows polarized results.** Decentralized achieves a modest +9.2% gain (0.347 vs. SAS 0.318), while Independent catastrophically underperforms at −35.0% (0.207). Centralized is essentially flat at +0.2%. The polarization reflects the benchmark's dynamic web navigation structure: Independent agents explore divergent paths without communication, producing contradictory information that the synthesis-only aggregator cannot reconcile; Decentralized debate enables agents to share findings and converge on consistent interpretations; Centralized's orchestrator bottleneck provides minimal benefit because each agent's web navigation is independently valid and the synthesis challenge is integrating findings rather than verifying correctness.

**WorkBench (Figure 2d) shows marginal effects across architectures.** Decentralized achieves +5.6% (0.664 vs. SAS 0.629), Independent is essentially flat at +0.2% (0.630), Centralized declines by −1.2% (0.621), and Hybrid declines by −11.0% (0.560). The narrow range reflects WorkBench's deterministic structure: tool sequences either succeed or fail based on correct execution, and coordination provides limited benefit when the primary challenge is selecting the right tools in the right order rather than reasoning under uncertainty. The tool-count of 16 makes this benchmark the strongest test of the tool-coordination trade-off.

**SWE-bench Verified (Figure 2e) shows slight degradation across all MAS architectures.** Hybrid declines by −2.1% (0.511 vs. SAS 0.522), Centralized by −3.1% (0.506), Decentralized by −5.4% (0.494), and Independent by −14.9% (0.444). The paper attributes this pattern to the capability-saturation threshold: most models achieve single-agent baselines above 45% on this benchmark, leaving limited room for coordination gains (Section 4.3). The high tool count (7 tools: bash, file editing, directory navigation, search, test execution, and more) further compounds through the tool-coordination trade-off. The Independent architecture's steeper degradation (−14.9%) is consistent with its absence of verification mechanisms in an environment where errors cascade through code edits and test failures.

**Terminal-Bench (Figure 2f) shows mixed results.** Independent achieves a marginal gain of +1.7% (0.350 vs. SAS 0.344), while Centralized degrades substantially by −19.2% (0.278). The low tool count (2 tools: bash execution and answer submission) limits the benefit of orchestration-heavy architectures while making overhead costs less justifiable. The SAS baseline (0.344) is below the 45% capability-saturation threshold, suggesting room for coordination gains, but the low tool count means the coordination efficiency penalty (E_c × T interaction in Equation 1) has limited impact since T = 2.

#### Domain Complexity and Coordination Efficacy (Table 11, Figure 2)

The paper characterizes each benchmark by a domain complexity score D ∈ [0, 1] (Appendix C), capturing the degree of sequential interdependence and empirical difficulty: WorkBench (D = 0.000, minimal sequential constraints), SWE-bench Verified (D = 0.255, decomposable engineering tasks), Finance-Agent (D = 0.407, moderate decomposability), Terminal-Bench (D = 0.414, diverse CLI tasks), PlanCraft (D = 0.419, high sequential dependencies), and BrowseComp-Plus (D = 0.839, dynamic state evolution). The paper identifies a critical threshold at D ≈ 0.40: below this threshold, multi-agent architectures yield net positive returns through effective task decomposition and parallel reasoning; above this threshold, coordination overhead consumes computational resources otherwise allocated to reasoning.

However, domain complexity alone does not fully predict MAS effectiveness. The paper demonstrates this through a specific contrast: Finance-Agent (D = 0.41) achieves +80.8% gains through parallelizable subtask structure, while PlanCraft (D = 0.42) degrades by −70% due to strict sequential dependencies, despite nearly identical complexity scores. This suggests that **sequential interdependence, rather than complexity per se, is the critical moderating variable**—a refinement of the domain complexity concept that the paper develops through the formal agentic task definition in Section 3.2.

The information gain analysis (Section 4.4) provides mechanistic evidence for this interpretation. In Finance-Agent, information gain ΔI correlates strongly with the MAS-SAS performance gap (r = 0.71, p < 0.001), with successful trials showing ΔI = 0.8–2.1 bits vs. failures at 0.2–0.6 bits—agents exchange high-value, verifiable information that improves solutions. In BrowseComp-Plus, the correlation is weak and non-significant (r = 0.18, p = 0.22), indicating that agents' messages provide limited validated information due to inherent world ambiguity, even though agents communicate actively.

#### Architecture-LLM Family Interactions (Figure 3, Section 4.2)

Architecture effectiveness depends systematically on both domain structure and model family, with no single architecture dominating universally. On Finance-Agent, the best-performing architecture varies by vendor: Anthropic's MAS-Centralized achieves +127.5% (0.636 vs. 0.280 SAS, indicating conservative but stable coordination), Google's MAS-Centralized reaches +164.3% (0.740 vs. 0.280 SAS, suggesting stronger attention-mechanism alignment with hierarchical message exchange), and OpenAI's MAS-Centralized achieves +69.9% (0.790 vs. 0.465 SAS). On PlanCraft where all variants degrade, vendor preferences flatten: Anthropic's best variant (Hybrid) degrades by −54.5% (0.310 vs. 0.680 SAS), Google's best degrades by −25.3%, and OpenAI's by −32.3%, "indicating that communication mechanisms cannot overcome fundamental sequential reasoning constraints."

The cost-performance trade-off analysis (Figure 3) reveals family-specific deployment signatures. OpenAI models show consistent gains from Centralized and Hybrid MAS configurations despite higher costs, with Hybrid achieving marginal cost ≈$0.008 per 1% success gain (steep but manageable for structured tasks). Google models display marginal MAS improvements but a clear efficiency plateau, maintaining intermediate costs ≈$0.012 per 1% gain across architectures, suggesting more balanced cost-benefit trade-offs. Anthropic models reveal higher variance and occasional MAS underperformance, with Hybrid reaching ≈$0.024 per 1% gain (3× worse than OpenAI), reflecting sensitivity to coordination overhead. The paper interprets these cross-family discrepancies as reflecting "family-level differences in instruction following, context utilization, inter-turn consistency, or other architectural and training factors that affect how models process coordination messages," explicitly noting that the underlying mechanisms are not isolated.

#### Scaling Principle Regression Results (Table 4, Section 4.3)

The full regression model (Equation 1, 20 parameters) achieves R^2_train = 0.463, R^2_CV = 0.373 (±0.170 SD) using Intelligence Index, and R^2_train = 0.481, R^2_CV = 0.413 (±0.130 SD) using the Agentic Capability Index (Table 13, AIC = −244.8). The progressive model comparison in Table 3 demonstrates that empirical coordination metrics capture meaningful variance beyond base predictors alone: the base model (Intelligence + Tools + Agents) achieves R^2_CV = 0.360, adding coordination structure metrics improves to 0.363, adding the single-agent baseline yields 0.358, and adding all interaction terms reaches 0.373.

**The capability-saturation interaction (P_SA × log(1 + n_a)) is the strongest and most robust effect:** β̂_17 = −0.236, 95% CI: [−0.396, −0.076], p = 0.004 (Table 4). This coefficient means that as the single-agent baseline increases (standardized), the benefit of adding agents decreases—and eventually becomes negative. The paper derives a quantitative decision boundary from this coefficient: P*_SA = −β̂_4 / β̂_17 ≈ 0.040 / 0.236 = 0.170 in standardized units, corresponding to raw performance ≈0.45 after denormalization. This threshold achieves 87% correct architecture selection on held-out configurations, substantially exceeding random choice (20%) or capability-only models (54%). The threshold is further supported with a 94% match rate across all 16 model×benchmark configurations on SWE-bench Verified and Terminal-Bench (p < 0.001 by binomial test, Section 4.5).

**The efficiency-tools trade-off (E_c × T) is the second most robust interaction:** β̂_16 = −0.096, 95% CI: [−0.154, −0.037], p = 0.002 (Table 4). Because all predictors are standardized after transformation, this should not be interpreted by directly multiplying raw values. The paper interprets it qualitatively: tool-rich environments amplify coordination inefficiencies, leading to larger performance penalties for architectures with high coordination overhead. Simple tasks (T ≤ 4) exhibit negligible efficiency effects (|ΔP| < 0.05), consistent with the observation that multi-agent coordination can succeed on decomposable problems with manageable tool counts.

**The linear intelligence effect is significant but modest:** β̂_1 = 0.126, 95% CI: [0.033, 0.218], p = 0.008 (Table 4). After mean-centering to address multicollinearity (VIF reduced from 200 to 1.1), higher-capability models achieve proportionally better performance across all architectures. The quadratic term (I²) is not significant (β̂_2 = −0.000, p = 0.977), indicating linear capability scaling within the tested range (I ∈ [42, 71]) without evidence of emergent super-linear gains.

**The tool diversity main effect is positive:** β̂_3 = 0.166, 95% CI: [0.095, 0.236], p < 0.001 (Table 4). More tools provide more capabilities, and log-transforming captures diminishing returns. This coefficient survives Holm-Bonferroni correction (p_Holm < 0.001, Table 15), confirming its reliability.

**The redundancy-agent interaction is marginally significant:** β̂_14 = 0.024, 95% CI: [0.002, 0.047], p = 0.034 (Table 4). The paper notes this effect is "minor compared to efficiency losses" (|β̂_E_c×T| = 0.096, 4× larger), indicating redundancy cannot compensate for architectural inefficiency. For a 4-agent system with R = 0.50, ΔP_redundancy = 0.024 × 0.50 × 4 = 0.048, equivalent to an ≈5% performance boost in standardized units. This significance near the α = 0.05 threshold "suggests this relationship may be context-dependent, potentially stronger in error-prone domains or weaker when communication is expensive."

**Several interaction terms do not reach statistical significance:** capability-efficiency (I × E_c: p = 0.653), communication-capability (c × I: p = 0.457), capability-tools (I × log(1 + T): p = 0.112), and error-tool interaction (A_e^trace × T: p = 0.332). The paper interprets these null results as evidence that capability and coordination efficiency have independent additive effects, and that error amplification's dramatic architectural differences (17.2× vs. 4.4×) are better explained by other coordination mechanisms (efficiency and overhead) rather than error propagation per se.

**The overhead-tool interaction (O% × T) is a directional pattern that loses significance under conservative inference:** β̂_13 = −0.033, p = 0.211 under cluster-robust inference (Table 14). The paper reports this as a directional pattern supported by consistency across the 4-benchmark subset analysis where it retains significance (β̂ = −0.162, p < 0.001 under naive OLS), but acknowledges that it does not reach conventional significance levels in the full 6-benchmark specification under cluster-robust standard errors.

#### Coordination Efficiency, Error Dynamics, and Information Transfer (Table 5, Section 4.4)

**Turn count exhibits power-law scaling with agent count:** T = 2.72 × (n + 0.5)^1.724, R² = 0.974, 95% CI on exponent: [1.685, 1.763], p < 0.001 (Section 4.4). The super-linear exponent (1.724 > 1) reflects quadratic message complexity tempered by practical bandwidth limits, contrasting with neural scaling laws where exponents are typically sub-linear (~0.76). Extrapolation to n = 10 predicts approximately 157 turns (95% CI: [143, 172]), representing a 21.8× increase over the SAS baseline of 7.2 turns—a hard resource ceiling where per-agent reasoning quality degrades sharply under fixed budgets.

**Trace-level error amplification varies dramatically by architecture (Table 5):** Single-agent (A_e^trace = 1.0, baseline), Centralized (4.4, containing errors through validation bottlenecks), Hybrid (5.1), Decentralized (7.8), and Independent (17.2, unchecked error propagation without inter-agent verification). The paper emphasizes that "neither the main effect of error amplification (β̂ = 0.014, p = 0.658) nor its interaction with tool count (A_e^trace × T: β̂ = 0.022, p = 0.332) reaches statistical significance" in the regression, suggesting that dramatic raw differences in error amplification are "better explained by other coordination mechanisms, particularly efficiency (E_c) and overhead (O%), rather than error propagation per se."

**Error absorption rates reveal architecture-specific correction capabilities (Section 4.4):** Centralized and Hybrid architectures achieve 22.7% average error reduction (95% CI: [20.1%, 25.3%]), peaking at 31.4% for Finance-Agent where structured numerical outputs facilitate verification. Independent MAS shows no error correction (+4.6% amplification) due to absence of any inter-agent verification—errors made by individual agents propagate directly to the aggregated output. The token-overlap analysis operationalizes the mechanism: high-performing runs show increased shared-token entropy (mean ≈1.8 bits for Finance-Agent; p < 0.001 vs. low-performing runs) and substantially reduced contradictory mass (median 2.3% in successes vs. 8.1% in failures), indicating convergence toward mutually consistent sub-proofs.

**The error taxonomy (building on MAST [15]) reveals four failure modes with architecture-specific frequencies (Section 4.4):**

- **Logical Contradiction:** Baseline 12.3–18.7%. Centralized reduces to 9.1% (36.4% reduction); Decentralized achieves 11.5%; Independent unchanged at 16.8%.
- **Numerical Drift:** Baseline 20.9–24.1%. Centralized/Decentralized reduce to 18.3% (24% reduction); Hybrid amplifies to 26.4% as rounding errors propagate through multiple coordination layers; Independent unchanged at 23.2%.
- **Context Omission:** Baseline 15.8–25.2%. Centralized reduces to 8.3% (66.8% reduction) via orchestrator synthesis; Decentralized achieves 11.2%; Independent unchanged at 24.1%.
- **Coordination Failure:** Only appears in MAS. Independent: 0% (no coordination mechanism to fail); Centralized: 1.8%; Decentralized: 3.2%; Hybrid: 12.4% (protocol complexity exceeds robust implementation).

The paper identifies three operational coordination regimes from these patterns: under-coordination (O < 100% overhead), where coordination mechanisms are not yet engaged and accuracy gains are minimal (ΔS ≈ +2–4%); the optimal band (200% < O < 300% overhead), dominated by Centralized and Decentralized with highest success-to-cost ratios (E_c ≈ 0.16) and strong error absorption; and over-coordination (O > 400% overhead), where Hybrid runs show reduced efficiency (E_c ≈ 0.11) and protocol complexity introduces coordination-failure modes.

**Token efficiency reveals sharp cost-benefit trade-offs (Section 4.4):** SAS achieves 67.7 successes per 1,000 tokens; Centralized drops to 21.5 (3.1× worse); Decentralized to 23.9 (2.8× worse); Independent to 42.4 (1.6× worse); and Hybrid to 13.6 (5.0× worse). These metrics quantify the economic cost of multi-agent coordination independent of whether raw accuracy improves.

**Message density exhibits logarithmic saturation (Section 4.4):** Across communicating MAS architectures (excluding c = 0 configurations), success rate follows S = 0.73 + 0.28 ln(c), R² = 0.68, p < 0.001. This should be interpreted as a descriptive trend rather than a universal functional form. Performance plateaus near c* = 0.39 messages/turn (achieved by Decentralized at 0.41 and Centralized at 0.39), beyond which additional messages yield diminishing returns: Hybrid (515% overhead, T = 44.3) shows −2.4% versus Centralized (285% overhead, T = 27.7), a difference that is not statistically significant (t(178) = 0.61, p = 0.542).

**Heterogeneous agent configurations do not bypass the capability-saturation threshold (Figure 4, Table 12):** A preliminary investigation of 13 configurations on BrowseComp-Plus mixes models of different capability levels (e.g., GPT-5 orchestrator with GPT-5-nano sub-agents). Centralized heterogeneous configurations underperform their strong-model homogeneous counterparts by a mean of 12.6 percentage points, while decentralized heterogeneous configurations show marginal gains (+2.0 pp) largely attributable to the stronger constituent model. Anthropic models uniquely benefit from heterogeneous mixing in centralized architecture, where a low-capability orchestrator with high-capability sub-agents (0.42) outperforms homogeneous high-capability (0.32) by 31%, while OpenAI and Gemini show performance degradation under heterogeneous centralized configurations—suggesting model-family-specific interactions with coordination structure that remain to be characterized.

**Agent count scaling experiments reveal model-dependent optimal team sizes (Figure 5):** Gemini-2.0 Flash exhibits a clear optimum at 7 agents before degradation under both Centralized and Decentralized architectures, while Gemini-2.5 Pro's Decentralized architecture peaks earlier despite its higher single-agent baseline. The Centralized architecture demonstrates more stable scaling for Flash but shows diminishing returns for Pro beyond 5 agents—confirming that coordination overhead eventually outweighs parallelization benefits for any model, but the threshold varies with model capability.

#### Architecture Selection Accuracy and Out-of-Sample Validation (Section 4.5, Appendix B)

**The scaling principle achieves 87% correct architecture selection on held-out configurations** (Section 4.3), substantially exceeding random choice (20%) or capability-only models (54%). However, leave-one-dataset-out (LODO) cross-validation highlights the challenge of predicting absolute success rates across structurally diverse task domains: the model captures relative architecture rankings accurately even when absolute cross-domain prediction is limited.

**Out-of-sample validation on held-out models (Appendix B, Tables 7–9):** Three held-out models with Intelligence Index = 75 (GPT-5.2, Gemini-3.0 Pro, Gemini-3.0 Flash), representing extrapolation approximately 5.6% beyond the training range (I ∈ [42, 71]), are evaluated on BrowseComp-Plus. The scaling equation achieves overall MAE = 0.077 across 15 architecture-model combinations. MAS predictions are better calibrated (MAE = 0.061) than SAS predictions (MAE = 0.138), consistent with systematic over-prediction of single-agent performance when extrapolating beyond the training range—a consequence of the linear intelligence effect (β̂_1 = 0.126) being extrapolated without bound. Eleven of 15 finding-model pairs validate (73%), with two partial validations. Three findings generalize universally: the capability ceiling effect, the optimality of Centralized or Decentralized architectures, and Hybrid overhead limiting performance. Two findings show model-family-specific behavior: Independent MAS degradation validates only for GPT-5.2 (−22.2%) but not for Gemini models where Independent matches or outperforms SAS (+11.1% for Pro, +5.9% for Flash), and the BrowseComp-Plus pattern (Decentralized ≥ Centralized) varies across model families. The architecture selection at I = 75 shows a notable limitation: the equation predicts Hybrid as optimal for all three models (P̂_Hybrid = 0.560), yet empirically Centralized and Decentralized achieve superior performance (0.48–0.50). This reflects linear extrapolation of the intelligence effect and failure to capture Hybrid's disproportionate overhead penalty at high capability levels: the equation systematically over-predicts Hybrid performance (mean error +37.0%) while achieving reasonable calibration for Centralized (mean error +3.0%) and Decentralized (signed mean error +8.8%).

### Ablation Studies and Robustness Checks

**Progressive model comparison (Table 3):** The full model with interaction terms achieves R^2_CV = 0.373 and AIC = −236.3, improving over simpler alternatives: Intelligence + Tools + Agents (R^2_CV = 0.360, AIC = −238.8), adding coordination structure metrics (R^2_CV = 0.363, AIC = −243.2), adding single-agent baseline (R^2_CV = 0.358, AIC = −242.0). The full model's superiority demonstrates that empirical coordination metrics and their interactions capture meaningful variance beyond base predictors alone.

**Cluster-robust standard errors (Table 14):** Re-estimating with standard errors clustered at the dataset level (G = 6, CR1 correction, t_5 critical values) reveals substantial inflation for predictors varying primarily at the dataset level. log(1 + T) inflates from p < 0.001 to p = 0.172, E_c × T from p = 0.002 to p = 0.205, and P_SA × log(1 + n_a) from p = 0.004 to p = 0.105. However, single_agent_baseline survives (p = 0.004) and error × baseline survives (p = 0.030), making capability saturation the single most robust finding across both cluster-robust and multiple-comparison correction approaches. The paper transparently frames dataset-level predictors as "directional patterns supported by directional consistency rather than confirmed at conventional significance levels."

**Holm–Bonferroni multiple-comparison correction (Table 15):** Controlling family-wise error rate at α = 0.05 across 19 hypothesis tests (excluding the intercept) using the step-down procedure, three predictors survive: log_tools (p_Holm < 0.001), single_agent_baseline (p_Holm = 0.018), and efficiency_x_tools (p_Holm = 0.026). Two further predictors are suggestive at p_Holm < 0.10: intelligence_centered (p_Holm = 0.056) and baseline_x_agents (p_Holm = 0.084). The Holm–Bonferroni correction was applied to naive OLS p-values (addressing multiplicity), while the cluster-robust analysis (addressing pseudoreplication) was reported separately—"under cluster-robust inference alone, only single_agent_baseline (p = 0.004) survives at α = 0.05, making capability saturation the single most robust finding across both correction approaches."

**Capability metric sensitivity (Table 13):** Replacing the Intelligence Index with the Agentic Capability Index (ACI), defined as each model's mean single-agent performance across all six benchmarks (correlation with Intelligence Index: r = 0.45), improves model fit to R^2_train = 0.481, R^2_CV = 0.413 (±0.130 SD), AIC = −244.8, with "zero reversals in statistical significance across predictors." The paper recommends ACI as the primary capability metric because it directly captures dynamic agentic performance rather than static benchmark composites that correlate only moderately (r = 0.45) with the quantity of interest. The per-dataset single-agent baseline alternative (R^2_train = 0.372, R^2_CV = 0.247) performs substantially worse, confirming that ACI's cross-benchmark averaging provides useful signal.

**SWE-bench Verified and Terminal-Bench bootstrap confidence intervals (Table 16):** At n = 20 instances per configuration, bootstrap 95% CIs (10,000 resamples) yield typical widths of ±20 percentage points per cell. While individual pairwise comparisons are underpowered at this sample size, the paper notes that "aggregate trends across 8 models × 2 benchmarks remain robust"—specifically, the 45% capability-saturation threshold achieves 94% match rate (p < 0.001 by binomial test) across all 16 model×benchmark configurations on these two benchmarks (Section 4.5).

**Cross-domain generalization via LODO cross-validation:** The paper acknowledges that predicting absolute success rates across structurally diverse domains without dataset-specific parameters remains challenging, consistent with the cluster-robust inference results. However, the within-domain cross-validated model correctly identifies the optimal architecture in 87% of held-out cases, indicating that "relative coordination patterns transfer across domains even when absolute performance levels vary."

**Heterogeneous agent configurations do not bypass capability saturation (Table 12, Figure 4):** Centralized heterogeneous configurations underperform homogeneous strong-model counterparts by a mean of 12.6 percentage points on BrowseComp-Plus; decentralized heterogeneous configurations show marginal gains (+2.0 pp) largely attributable to the stronger constituent model. Anthropic models show a unique pattern where heterogeneous centralized configurations with low-capability orchestrator and high-capability sub-agents (0.42) outperform homogeneous high-capability (0.32) by 31%, while OpenAI and Gemini show degradation. The paper interprets this as suggesting that "certain models may be better suited for orchestration versus execution roles," but the sample size (13 configurations on one benchmark) limits generalizability.

**Agent count scaling reveals model-dependent optima (Figure 5):** Gemini-2.0 Flash shows optimal performance at 7 agents before degradation; Gemini-2.5 Pro's Decentralized architecture peaks earlier despite higher single-agent baseline. The Centralized architecture demonstrates more stable scaling for Flash but shows diminishing returns for Pro beyond 5 agents. This confirms that "coordination overhead eventually outweighs parallelization benefits for any model, but the threshold varies with capability."

### Critical Assessment

The paper's central claim is that multi-agent system effectiveness is governed by quantifiable trade-offs between architectural properties and task characteristics, and that these trade-offs can be formalized into a predictive model that achieves cross-validated R^2 = 0.373 (0.413 with ACI) and 87% accuracy in architecture selection for held-out configurations. This claim is supported—but with specific boundary conditions that are important to the paper's framing as a first quantitative framework rather than a final answer.

**Claim 1: A regression model using empirical coordination metrics explains performance variance across 260 configurations (R^2 = 0.373 cross-validated).** The model exists and the cross-validation procedure is appropriate (5-fold, experiment-level holdout). The R^2 value of 0.373 represents meaningful predictive power—substantially better than chance or capability-only baselines—but also substantial unexplained variance (~63%). This is not a weakness for a first empirical framework covering six diverse benchmarks; it would be suspiciously high if it were much larger. The progression in Table 3 from base predictors (R^2 = 0.360) to the full model (0.373) is modest, suggesting the coordination metrics capture real but limited additional signal beyond what intelligence and task properties alone provide. The improvement to R^2 = 0.413 with ACI is more substantial and validates the paper's argument that task-grounded capability metrics are superior to static benchmarks for predicting agentic performance.

The key limitation is that the model's predictive power is asymmetric: it captures relative architecture rankings (87% accuracy for best-architecture selection) better than absolute cross-domain performance, as shown by LODO cross-validation. This means the model is currently more useful as an architecture selection tool within known task regimes than as a universal performance predictor for arbitrary new domains.

**Claim 2: Multi-agent coordination yields diminishing returns once single-agent baselines exceed ~45% accuracy (capability saturation).** This is unequivocally the paper's most robust finding. It survives cluster-robust standard errors (p = 0.004), Holm–Bonferroni multiple-comparison correction (p_Holm = 0.018), and capability metric replacement. The 94% match rate on held-out SWE-bench and Terminal-Bench configurations (Section 4.5) provides additional validation, though these benchmarks are within the training distribution (they were used to fit the model). The threshold of 45% is an empirical estimate from the specific models and tasks evaluated; its precise numerical value should not be over-interpreted as a universal constant. However, the *existence* of a threshold and the methodology for estimating it are the lasting contributions.

The claim properly applies to "coordination yields diminishing returns," not "multi-agent systems become useless." The paper documents cases where MAS provides marginal gains above 45% baselines (e.g., Workbench Decentralized at +5.6% with SAS baseline 0.629; Figure 2d) but the gains are substantially smaller than those observed below the threshold (e.g., Finance-Agent Centralized at +80.8% with SAS baseline 0.349; Figure 2b). The threshold predicts when gains become negative on average, not that every configuration above 45% shows degradation.

**Claim 3: A tool-coordination trade-off exists where tool-heavy tasks suffer disproportionately from multi-agent overhead (β̂ = −0.096, p = 0.002).** This is moderately robust—it survives Holm–Bonferroni correction (p_Holm = 0.026) but loses significance under cluster-robust inference (p = 0.205). The supporting qualitative evidence is strong: the paper provides mechanistic explanations (per-agent token budgets, the contrast between WorkBench's 16 tools and Terminal-Bench's 2 tools) and the directional consistency across architectures is clear. However, the claim rests substantially on the 4-benchmark subset (BrowseComp-Plus, Finance-Agent, PlanCraft, WorkBench) where tool count varies from 3 to 16, while SWE-bench (7 tools) and Terminal-Bench (2 tools) add heterogeneity that reduces the statistical power of this interaction. The paper transparently reports the sensitivity analysis and frames the finding at the appropriate confidence level.

**Claim 4: Architecture-dependent error amplification ranges from 4.4× (Centralized) to 17.2× (Independent).** The raw measurements in Table 5 are dramatic and well-documented through execution-trace analysis. However, the regression results complicate this claim: neither the main effect of error amplification nor its interaction with tool count reaches statistical significance in the full model. This suggests that while error amplification differs dramatically between architectures, those differences are *correlated with*—and statistically subsumed by—other coordination metrics like efficiency and overhead. The claim is factually correct at the descriptive level (the numbers are what they are) but the *causal* interpretation—that error amplification *drives* performance differences—is not supported by the regression. The paper appropriately hedges: "this effect is subsumed by the efficiency metric."

**Experimental design strengths.** The paper's greatest methodological strength is the controlled comparison framework: matching total reasoning tokens across configurations, using identical prompts and tools for all architectures, and systematically varying only coordination structure and model capability. This is what enables causal attribution—without it, performance differences could reflect prompt quality, tool access, or compute budget rather than architecture. The 260-configuration matrix spanning three model families and six benchmarks provides substantially more coverage than typical multi-agent evaluations, and the cross-family consistency (maximum slope difference Δ_max = 0.023, CV < 0.02 across families; Section 4.1) strengthens the claim that coordination scaling follows model-agnostic principles.

**Experimental design limitations.** Several weaknesses merit attention:

**Small test sets on SWE-bench and Terminal-Bench.** The 20-instance subsets mean per-cell bootstrap confidence intervals are ±20 percentage points wide (Table 16). The paper appropriately uses bootstrap CIs and acknowledges the underpowered nature of pairwise comparisons. The 94% match rate for the capability-saturation threshold on these benchmarks provides some reassurance, but the absolute performance estimates on these benchmarks should be treated as approximate.

**Only 6 clusters for cluster-robust inference.** With G = 6 benchmarks, cluster-robust standard errors use t_5 critical values, which are extremely conservative. The paper correctly notes this limitation and transparently reports both naive and cluster-robust estimates. Several predictors that are significant under naive OLS lose significance under cluster-robust inference (Table 14), but this may partly reflect low statistical power from small cluster count rather than absence of true effects. Future work with more benchmarks would enable more precise cluster-robust estimation.

**Limited agent count scaling analysis.** The main 260-configuration matrix fixes n_a = 3 for all multi-agent architectures. The agent count scaling experiments (Figure 5) explore n_a ∈ {1, 3, 5, 7, 9} but only for two Gemini models on one benchmark (BrowseComp-Plus, inferred from context). The super-linear turn-count power law (exponent 1.724) is fit across architecture-aggregated means and the extrapolation to n = 10 is explicitly labeled as such. The paper does not test whether this power law holds for other model families or benchmarks. The finding that Gemini-2.0 Flash peaks at 7 agents while Gemini-2.5 Pro peaks earlier is suggestive of capability-dependent optimal team sizes but is based on limited data.

**Heterogeneous agent experiments are preliminary.** The 13 heterogeneous configurations on BrowseComp-Plus (Table 12, Figure 4) provide interesting model-family-specific patterns (Anthropic benefits from heterogeneity; OpenAI and Gemini do not) but are insufficient to draw general conclusions. The paper correctly frames this as "a preliminary investigation" and identifies systematic study of role specialization as future work.

**The regression model extrapolates poorly.** The out-of-sample validation (Appendix B) on held-out models with I = 75 reveals systematic over-prediction of SAS performance (MAE = 0.138) and Hybrid performance (mean error +37.0%), though MAS predictions are reasonably calibrated (MAE = 0.061). This means the linear intelligence effect (β̂_1 = 0.126) cannot be extrapolated indefinitely—the relationship likely saturates or changes functional form beyond the training range. The paper acknowledges this limitation (Section 5) and the validation results appropriately bound the model's domain of applicability.

**No combination with other test-time compute strategies.** The paper studies coordination structure in isolation, without combining multi-agent architectures with complementary approaches like chain-of-thought prompting variations, self-reflection mechanisms, or verifier-guided search. The possibility that these orthogonal strategies interact with architecture choice is not explored. For example, would the capability-saturation threshold shift if agents used improved reasoning strategies? Would the tool-coordination trade-off weaken if agents used more efficient tool-calling protocols? These questions are beyond the paper's scope but represent natural extensions.

**Missing comparisons.** The paper compares four multi-agent architectures against SAS but does not compare against simpler coordination baselines that might achieve similar benefits at lower cost. For example: SAS with majority voting over multiple independent samples (effectively, Independent without the synthesis-only aggregator), SAS with tool-call parallelism (running multiple tools simultaneously within a single agent loop), or SAS with iterative refinement (revisions without separate agent instances). Some of these are mentioned in related work but not implemented as baselines. The question of whether observed MAS benefits could be achieved by giving a single agent equivalent compute in more effective ways is partially addressed by the matched-budget design (SAS gets proportionally more iterations) but not fully resolved.

**Ecological validity of agent count.** The paper evaluates 3-agent teams (with extensions to 9 agents in Figure 5), but many real-world multi-agent deployments use either 2 agents (simple orchestrator-worker) or much larger collectives (10+ specialized agents for complex workflows). The optimality of 3-agent configurations for many tasks may be an artifact of the specific architectures and budgets tested rather than a general principle.

**What would strengthen the paper.** Several experiments would address these limitations: (1) extending the agent-count scaling analysis to all five architectures across multiple model families and at least two benchmarks with different decomposability profiles; (2) testing heterogeneous configurations systematically across all benchmarks to characterize when capability diversity helps vs. hurts; (3) including SAS + majority voting and SAS + iterative refinement as compute-matched baselines; (4) evaluating on additional benchmarks with intermediate tool counts (e.g., 5–10 tools) to better characterize the tool-coordination trade-off's functional form; (5) testing whether the capability-saturation threshold shifts when per-agent or total compute budgets are increased, since the current finding may be budget-dependent.

**Summary assessment.** The paper's central contribution is the framework itself—the systematic controlled evaluation methodology, the empirical coordination metrics, the regression model with its interaction terms, and the capability-saturation threshold—rather than any single numerical result. This framework demonstrably captures real coordination dynamics: the 87% architecture selection accuracy on held-out configurations would not be achievable if the model were merely overfitting noise. The limitations (small cluster count, limited agent count scaling, model extrapolation bounds) are transparently documented and appropriately constrain the claims. The paper establishes a quantitative foundation where previously only heuristics existed, and the weaknesses primarily reflect the inevitable limitations of a first systematic study rather than fundamental flaws in the approach.

## 6. Limitations and Trade-offs

### The Difficulty Estimation Bottleneck Is Unaccounted for in the Headline Efficiency Claims

The paper's compute-optimal scaling framework—the central architectural contribution—depends on knowing the single-agent baseline `$P_{\text{SA}}$` for a given (model, task) pair before deciding whether to deploy multi-agent coordination. The decision boundary `$P_{\text{SA}}^* \approx 0.45$` (Section 4.3) is the key operational takeaway: if your single-agent accuracy exceeds ~45%, stick with SAS; if it's below, consider MAS. But acquiring `$P_{\text{SA}}$` requires **running the single-agent baseline on the target task**, which consumes exactly the kind of compute the framework is supposed to help allocate efficiently.

The paper acknowledges this circularity implicitly through its capability metric discussion (Section 4.5). The Intelligence Index—a static composite of eight evaluation suites—correlates only `$r = 0.45$` with the Agentic Capability Index (ACI), which is the mean single-agent performance across the six benchmarks. This means the publicly available capability metric cannot reliably substitute for actually measuring `$P_{\text{SA}}$` on the target task. The ACI itself *is* the target measurement: it requires running SAS on all six benchmarks. The paper recommends ACI as the primary capability metric but provides no method for estimating it without running the experiments.

The practical consequence is a **deployment circularity**. A practitioner facing a new task must either (a) guess whether their single-agent baseline exceeds 45%—exactly the heuristic-based approach the paper critiques—or (b) run the single-agent baseline to find out, consuming compute that could have been spent on the task itself. For production systems handling many task types, computing `$P_{\text{SA}}$` for each task class is a one-time cost that can be amortized, but for novel or low-volume tasks, the estimation cost may dominate the coordination savings. The paper's 4× efficiency gains (e.g., Section 4.3: matching 256-generation SAS performance with 64-generation compute-optimal MAS) are computed *after* `$P_{\text{SA}}$` is known, without amortizing the cost of learning it.

The paper does not quantify this amortization cost. Section 4.5 discusses the Intelligence Index vs. ACI discrepancy as a measurement validity concern, not as a deployment cost concern. Appendix A acknowledges that Intelligence Index values for some models are "approximate estimates" with "methodologically consistent but not officially certified" reconstructions, further compounding the practical difficulty of obtaining reliable capability estimates for arbitrary models. The paper explicitly identifies "sparse communication, early-exit mechanisms, or distilled coordinator models" as future efficiency work (Section 5, limitation vi), but does not address the difficulty-estimation-cost problem directly.

### The Regression Model Extrapolates Poorly Beyond Its Training Range, Limiting Deployment to Known Model Capability Regimes

The scaling principle regression (Equation 1) is fit on configurations with Intelligence Index `$I \in [42, 71]$` (Section 4.1). The model uses a linear capability term (`$\hat{\beta}_1 = 0.126$`, `$p = 0.008$`) with no evidence of non-linear scaling within this range (`$\hat{\beta}_2 = -0.000$`, `$p = 0.977$`). This linear fit works reasonably within the training distribution but **cannot be extrapolated to frontier models with substantially higher capability**, as the paper demonstrates through its own out-of-sample validation.

Appendix B evaluates three held-out models with Intelligence Index = 75—only 5.6% beyond the training maximum of 71—and finds systematic failures. The model over-predicts single-agent performance (SAS MAE = 0.138 vs. overall MAE = 0.077 across 15 predictions), over-predicts Hybrid architecture performance by a mean error of +37.0%, and incorrectly selects Hybrid as the optimal architecture for all three held-out models when Centralized and Decentralized empirically outperform it (0.48–0.50 vs. Hybrid predictions of 0.560). The paper is transparent about this: "the equation systematically over-predicts Hybrid performance (mean error +37.0%) while achieving reasonable calibration for Centralized (mean error +3.0%) and Decentralized (signed mean error +8.8%)."

The consequence is that **the scaling principle's quantitative predictions should not be used for models whose Intelligence Index falls outside the 42–71 range**, which as of 2026 includes the most capable frontier models. GPT-5.2, Gemini-3.0 Pro, and Gemini-3.0 Flash (all Index 75) are already beyond this range. The 87% architecture selection accuracy is computed on held-out configurations *within* the training distribution, not on out-of-distribution capability levels. The paper's recommendation to use Agentic Capability Index (ACI) rather than Intelligence Index partially addresses the measurement validity problem but does not solve the extrapolation problem: ACI values for frontier models would still lie beyond the training range unless the benchmarks are re-run to measure them.

The paper explicitly identifies this limitation in Appendix B, noting that "linear extrapolation of the intelligence effect (`$\hat{\beta}_1 = 0.126$`) beyond its training range" is the likely cause of systematic prediction errors. It does not propose a solution, and the limitation is primarily one of scope: the framework is validated for known model tiers within a specific capability band, and extending it to substantially more capable models would require new experiments.

---

### With Only Six Benchmarks (G = 6 Clusters), Several Key Findings Lack Statistical Power Under Conservative Inference

The paper's regression model involves predictors that vary primarily at the dataset level—most critically, `$\log(1 + T)$` (tool count, which takes one value per benchmark) and interactions involving it (`$E_c \times T$`, `$O\% \times T$`). With `$G = 6$` benchmarks, cluster-robust standard errors use `$t_5$` critical values, which are extraordinarily conservative (Section 4.5). The consequence is that several findings that are significant under naive OLS **lose significance when we account for the fact that the effective sample size at the benchmark level is small**.

Table 14 reveals the extent of this problem. `$\log(1 + T)$` inflates from `$p < 0.001$` to `$p = 0.172$` under cluster-robust inference. `$E_c \times T$` inflates from `$p = 0.002$` to `$p = 0.205$`. `$P_{\text{SA}} \times \log(1 + n_a)$` inflates from `$p = 0.004$` to `$p = 0.105$`. Only `$P_{\text{SA}}$` alone (`$\hat{\beta}_{10}$`, `$p = 0.004$` robust) and `$A_e^{\text{trace}} \times P_{\text{SA}}$` (`$\hat{\beta}_{12}$`, `$p = 0.030$` robust) survive this more conservative inference.

This matters because the **tool-coordination trade-off**, one of the paper's three headline scaling patterns (Section 4.3), rests substantially on the `$E_c \times T$` interaction. Under the most conservative inference, this finding is directional (`$\hat{\beta} = -0.096$`) but not statistically confirmed. The qualitative evidence—execution traces showing how multi-agent coordination fragments per-agent tool budgets in WorkBench (16 tools) vs. Terminal-Bench (2 tools), the monotonic degradation pattern in Figure 2d–f—provides supporting mechanistic evidence, but the quantitative estimate of the effect magnitude and its precise functional form are less reliable than the paper's presentation might suggest.

The paper is transparent about this limitation. Section 4.5 explicitly reports both naive and cluster-robust `$p$`-values, frames dataset-level predictors as "directional patterns supported by directional consistency rather than confirmed at conventional significance levels," and the Limitations section (Section 5, item vii) acknowledges that "with a small number of clusters, cluster-robust standard errors are known to be conservative." This is a consequence of studying six diverse benchmarks—the diversity is a strength for ecological validity but a weakness for statistical power at the benchmark level. The mitigation is incomplete: adding more benchmarks would directly address this, but the paper does not include additional benchmarks.

### Agent Count Scaling Analysis Is Sparse, Leaving the Functional Form of Coordination Overhead Poorly Characterized Beyond Small Teams

The paper's central framework uses `$n_a = 3$` agents for all multi-agent architectures in the main 260-configuration matrix (Section 4.1, Appendix E). The power-law relationship `$T = 2.72 \times (n + 0.5)^{1.724}$` (Section 4.4) relating total turns to agent count is fit across architecture-aggregated means with only a handful of data points at each `$n$`, and the extrapolations to `$n = 10$` (~157 turns, 21.8× SAS baseline) are acknowledged as extrapolations. The agent count scaling experiments (Figure 5) explore `$n_a \in \{1, 3, 5, 7, 9\}$` but only for two Gemini models (2.0 Flash and 2.5 Pro) under two architectures (Centralized and Decentralized) on one benchmark (BrowseComp-Plus, inferred from context). This means **the paper's quantitative claims about how performance scales with team size rest on limited evidence**.

The consequence is that the paper cannot characterize whether the capability-saturation threshold shifts with team size, whether the tool-coordination trade-off amplifies or attenuates at larger `$n_a$`, or whether the optimal number of agents varies systematically with task decomposability. The finding that Gemini-2.0 Flash peaks at 7 agents while Gemini-2.5 Pro peaks earlier (Figure 5) is suggestive of a capability-dependent optimal team size, but `$n = 2$` data points cannot establish a functional relationship. The super-linear turn-count scaling is fit across only five architecture-aggregated means (SAS, Independent, Decentralized, Centralized, Hybrid, corresponding to different `$n_a$` values), and the tight `$R^2 = 0.974$` may partially reflect overfitting to a small number of points rather than a robust functional form.

The paper acknowledges this as a limitation in Section 5 (limitation i): "our empirical findings suggest that scaling to larger collectives may face fundamental barriers: the communication overhead we measured grows superlinearly with agent count, and coordination efficiency degrades substantially beyond moderate team sizes. Whether such collectives can exhibit beneficial emergent behaviors, such as spontaneous specialization or hierarchical self-organization, or whether communication bottlenecks dominate remains an open question." This is appropriately framed as future work, and the paper does not overclaim about larger teams. However, a practitioner wanting to deploy 5, 7, or 10 agents on a real task cannot rely on this paper for quantitative predictions about how performance will scale—the evidence simply isn't there.

### All Experiments Use a Single Coordination Paradigm (Natural Language Message Passing), Which May Not Generalize to Alternative Communication Mechanisms

The paper's entire analysis assumes that agent coordination occurs through natural language message passing—agents serialize their reasoning into tokens, send those tokens to other agents (or an orchestrator), and the receiving agents process them through their LLMs. This is the dominant paradigm in current multi-agent systems and the paper appropriately studies it. However, the paper's central mechanistic explanation for coordination costs—the super-linear turn-count scaling, the per-agent token budget fragmentation, the 4.4× vs. 17.2× error amplification differences—is **contingent on this communication modality**. Alternative approaches like latent-space reasoning, shared activation states, structured symbolic protocols, or blackboard architectures with non-linguistic representations might exhibit fundamentally different scaling behavior.

The paper acknowledges this constraint in Section 5 (limitation vi): "the token-centric communication paradigm... imposes fundamental latency and cost floors. Emerging approaches such as latent-space reasoning or direct activation sharing between models could circumvent this bottleneck, potentially altering the scaling dynamics we observe if inter-agent communication shifts from token exchange to more efficient representational transfer." This is not a criticism of the paper's methodology—it studies the dominant paradigm and does so rigorously—but it bounds the **temporal validity** of the findings. If future multi-agent systems move toward more efficient communication mechanisms, the quantitative coefficients (the 45% threshold, the tool-coordination trade-off magnitude, the error amplification hierarchy) may not transfer.

The practical consequence is that practitioners building multi-agent systems with communication optimizations—cached message embeddings, structured JSON protocols, selective information sharing rather than full context transmission—may observe different scaling patterns than those reported here. The paper's finding that Hybrid architecture (515% overhead) underperforms simpler architectures on most tasks is strongly driven by the token cost of its elaborate communication protocol; if that communication could be compressed or made more efficient, Hybrid's relative performance might improve. The paper does not test any communication efficiency optimizations, so the reported overhead values represent upper bounds under naive natural-language protocols.

### The Framework Does Not Address Latency or Wall-Clock Time, Only Total Compute

The paper measures computational cost in total reasoning tokens and total reasoning turns, matched across configurations (mean `$\mu = 4,800$` tokens per trial, Section 4.4). This is the right metric for scientific analysis—it isolates coordination effects from raw compute advantages. But it **ignores latency**, which is often the binding constraint in production deployments. A Single-Agent System with 10 sequential iterations completes in wall-clock time proportional to 10 LLM calls. A Decentralized system with 3 agents across 3 debate rounds requires 9 agent invocations per round, but those 9 invocations can run in parallel within each round, making the wall-clock time proportional to 3 rounds × (1 invocation latency) rather than 27 sequential invocations. Conversely, the 7.2-turn SAS and the 26.1-turn Decentralized system have very different serial depths even if their total token counts are matched.

The paper's efficiency metric `$E_c = S / (T / T_{\text{SAS}})$` (Table 5) normalizes success by relative turn count, which is a throughput metric (success per unit of serial computation), not a latency metric. A system with `$E_c = 0.074$` (Hybrid) might still be preferable for latency-sensitive applications if its parallel structure enables faster time-to-first-token than SAS with `$E_c = 0.466$` but entirely sequential execution. The paper does not measure wall-clock time, does not report parallel speedup factors, and does not discuss the throughput-latency trade-off.

Section 5 (limitation vi) briefly mentions "complementary latency-oriented designs, where parallel agent branches execute speculatively and suboptimal trajectories are pruned post-hoc, may trade increased total compute for reduced wall-clock time," but this is framed as future work rather than analyzed in the paper. The consequence is that a practitioner deciding between SAS and MAS for a latency-sensitive application (interactive assistant, real-time decision-making) cannot use this paper to make an informed decision. The 87% architecture selection accuracy applies to accuracy-maximizing choices under fixed total compute, not to latency-minimizing choices or accuracy-per-unit-latency optimization.

## 7. Implications and Future Directions

- **How this changes the field’s framing (within the paper’s scope).**
  - It argues that “agent scaling” should be studied like an empirical science: not by counting agents, but by quantifying coordination costs and task properties that determine when coordination is net-positive (Abstract; Sections 4.2–4.3).
  - It pushes evaluation toward **agentic benchmarks** and away from static tasks as a proxy for agent performance (Section 3.2).

- **Practical applications / downstream use cases.**
  - **Architecture selection by task type** (supported by Figure 2 and Section 4.3 examples):
    - Prefer **SAS** for **sequential constraint-satisfaction** tasks like PlanCraft, where all MAS variants degrade (`−39%` to `−70%`) (Figure 2; Section 4.2).
    - Prefer **Centralized MAS** for **parallelizable analysis** tasks like Finance-Agent, where centralized gains are largest (`+80.8%`) (Figure 2; Section 4.2).
    - Prefer **Decentralized MAS** for **dynamic browsing/navigation** where peer exploration and fusion helps modestly (`+9.2%`) and centralized is near-neutral (`+0.2%`) (Figure 2; Section 4.2).
  - **Budget-aware design:** Table 5 implies that if token/latency budgets are tight, Hybrid-style coordination can be dominated by overhead.

- **Repro/Integration Guidance (when to prefer what, per the paper).**
  - Use MAS only when the task is **decomposable into parallel subtasks** and the **single-agent baseline is below ~0.45**, because the paper reports a capability/baseline saturation threshold beyond which coordination returns diminish (Abstract; Section 4.3).
  - Avoid MAS for tasks where decomposition is artificial (PlanCraft example in Section 4.2), because coordination messages consume budget without adding useful information.
  - Track measurable metrics like `O%`, `E_c`, and message density `c` from traces (Section 4.1; Table 5) and treat them as design targets, not just post-hoc analytics.

- **Follow-up research directions explicitly suggested by the paper (Limitations Section 5).**
  - Explore whether larger collectives can overcome super-linear overhead via emergent specialization or self-organization, versus being fundamentally bottlenecked by communication (Limitations (i)).
  - Study heterogeneity beyond same-family scale differences, including mixing different model architectures or specialized fine-tunes (Limitations (ii); also Figure 4 analyzes heterogeneous-role effects within families).
  - Develop coordination protocols for tool-intensive tasks (tool scheduling, routing, hierarchical tool delegation), since tool–coordination interactions are a primary failure mode (Limitations (iii); Section 4.3).
  - Extend to more environments (embodied, multimodal, long-horizon feedback) to test generality of the scaling principles (Limitations (v)).
