# Structured Distillation of Web Agent Capabilities Enables Generalization

**ArXiv:** [2604.07776](https://arxiv.org/abs/2604.07776)

## 🎯 Pitch

A 9B-parameter student model surpasses GPT-4o and Claude 3.5 Sonnet on WebArena—and gains 18 points on an enterprise platform it never saw—by training purely on synthetically generated trajectories where LLMs play every annotation role. Structured filtering and evaluation hints turn a single frontier teacher’s 3,000 tasks into a curriculum that teaches generalization, not just environment memorization.

---

## 1. Executive Summary

This paper introduces **AGENT-AS-ANNOTATORS**, a structured framework for synthesizing web agent training trajectories by replacing three human annotation roles—Task Designer, Annotator, and Supervisor—with modular LLM components (a Persona Generator and Task Generator produce grounded task intents with evaluation hints, an Agent executes them, and a Judge with hints filters for success). Using Gemini 3 Pro as teacher, the framework generates 3,000 tasks across six WebArena environments, yielding 2,322 high-quality trajectories after filtering; a 9B student fine-tuned with pure supervised learning achieves 41.5% on WebArena, surpassing GPT-4o (31.5%) and Claude 3.5 Sonnet (36.0%) under the same evaluation protocol and nearly doubling the previous best open-weight result. Capabilities transfer to unseen platforms—an 18.2 percentage point gain on WorkArena L1, an enterprise interface never seen during training—establishing that structured distillation from a single frontier teacher produces generalizable web interaction skills rather than environment-specific overfitting.

## 2. Context and Motivation

### The Core Problem: Frontier LLMs Are Effective Web Agents, But Inaccessible

The paper addresses a fundamental tension in the current landscape of web agents. Frontier LLMs—large, proprietary models accessed via API—have demonstrated remarkable capability on realistic web tasks. They can navigate complex websites, fill out forms, query databases, manage content across multiple applications, and complete multi-step workflows that require both visual understanding and logical reasoning. On WebArena, a benchmark of self-hosted web applications that serves as one of the field's primary evaluation suites, multi-agent systems built on top of frontier models exceed **70% success rate** on public leaderboards (Guo et al., 2026), and even single frontier models surpass **50%** under standardized evaluation protocols like BrowserGym (de Chezelles et al., 2024).

However, these frontier models come with significant deployment barriers that make them impractical for many real-world use cases:

- **Cost**: API access to frontier models is expensive, particularly for tasks requiring dozens or hundreds of sequential reasoning steps with visual inputs—exactly what web agent interactions demand. Each step involves processing large accessibility trees (which can exceed 30K tokens for complex pages) and generating structured actions, and a single task may require 10–30 such steps.

- **Privacy and data sovereignty**: Using third-party APIs requires transmitting user interaction data—including page contents, form entries, and navigation patterns—to external servers. For enterprise deployments handling sensitive information (credit card data, internal documents, personal user accounts), this creates compliance and security concerns that may be insurmountable.

- **Latency and connectivity dependence**: API-based models require network connectivity and introduce round-trip latency at every interaction step, which compounds for multi-turn tasks. Local deployment eliminates this dependency but is infeasible with frontier-scale models.

**Small open-weight models offer an attractive alternative.** A 9B-parameter model can run locally on consumer or edge hardware, operates without network connectivity, keeps all data on-device, and has negligible per-inference cost beyond electricity. But there is a **substantial capability gap**: as shown in Table 1, the base Qwen3.5-9B achieves only **31.0%** on WebArena, compared to Gemini 3 Pro's **51.2%** — a gap of over 20 percentage points. This gap means that locally deployable models are not yet viable replacements for frontier models in web agent applications.

### Why This Problem Matters

The practical stakes are high because web agents represent one of the most immediately useful applications of LLM technology. Unlike abstract reasoning benchmarks or creative writing tasks, web agents automate concrete, economically valuable work: filling out expense reports in enterprise software, managing inventory in e-commerce backends, processing customer service tickets across multiple internal tools, conducting research across knowledge bases and wikis. The software interfaces for these tasks already exist—they are web applications that humans interact with daily. A capable, locally deployable web agent would:

- **Enable enterprise automation without data leaving the premises.** Organizations running sensitive internal tools (ServiceNow, custom CRMs, document management systems) could deploy agents that handle routine workflows without routing data through external APIs.

- **Democratize access to agentic capabilities.** Researchers, small businesses, and individual users who cannot afford or justify enterprise API contracts could run capable agents on modest hardware.

- **Provide a foundation for self-improving systems.** A locally fine-tunable agent can be iteratively improved on organization-specific data, creating a virtuous cycle where the agent becomes more capable over time without depending on external model providers.

The problem also has **theoretical significance** for understanding knowledge distillation in interactive, multi-step settings. Web agent trajectories differ fundamentally from the static text completions typically used in distillation research: they involve environment interaction, visual grounding, error recovery, and long-horizon planning. Understanding how to distill these capabilities—and whether distilled skills transfer across environments—informs broader questions about what language models learn from fine-tuning and how structured synthetic data can substitute for human demonstrations.

### Prior Approaches and Their Limitations

Several lines of prior work have attempted to close the capability gap between frontier and open-weight web agents, each with identifiable shortcomings.

#### Training on LLM-Generated Trajectories

A natural approach is **agentic capability distillation**: using a frontier model as a teacher to generate training trajectories, then fine-tuning a smaller student on those trajectories (Hsieh et al., 2023). Several recent works have explored this for web agents, but each has design limitations:

**InSTA (Trabucco et al., 2025)** proposes and executes tasks at internet scale across 150K websites, filtering with an LLM judge. While effective in achieving breadth, InSTA achieves diversity through scale rather than through structured persona-driven variation. This brute-force approach means many generated tasks may be repetitive or trivial; there is no mechanism for ensuring that different usage patterns within the same website are covered. Additionally, InSTA generates tasks by prompting the teacher LLM without first exploring the environment, meaning task intents may reference hallucinated entities (non-existent products, users, or pages) rather than real environment state—a critical failure mode for training data, since the student learns to attempt actions that cannot succeed.

**NNetNav (Murty et al., 2024a)** takes the opposite approach: it retroactively labels free exploration trajectories with task descriptions. This ensures tasks are grounded in real environment state, but it inverts the natural annotation workflow. In human annotation, tasks are designed first, then executed; retroactive labeling means there is no guarantee that the exploration trajectory is an efficient or correct way to achieve the labeled task. The labeled task may not match what the agent was actually trying to do—it may be a post-hoc rationalization of a meandering exploration. Furthermore, because tasks are extracted from exploration rather than designed with intent, the diversity of task types is limited to whatever the explorer happened to do, rather than covering the full range of site affordances.

**Go-Browse (Gandhi & Neubig, 2025)** frames data collection as a graph search over URLs with VLM feasibility checking. This approach explicitly models the website structure, but it requires separate solver models for task execution and uses a complex multi-stage pipeline that is difficult to reproduce, extend, or systematically vary.

**AgentTrek (Xu et al., 2024b)** leverages web tutorials for task replay with VLM verification. This is creative but depends on the availability of high-quality tutorials for target websites—a constraint that limits applicability to well-documented workflows.

**Explorer (Pahuja et al., 2025)** scales exploration-driven synthesis to 94K trajectories by iteratively refining exploration into task descriptions. While impressive in scale, Explorer fuses exploration, task generation, and execution into a single refinement loop, making it difficult to attribute gains or failures to specific pipeline components and complicating systematic improvement.

#### The Structural Problem: No Common Framework

These approaches differ in fundamental design choices (Table 2 in the paper maps them onto the AGENT-AS-ANNOTATORS framework to make the differences explicit):

- **Task grounding**: Whether tasks are defined before execution (grounded, as in InSTA and Go-Browse) or retroactively extracted from exploration traces (as in NNetNav and Explorer). Grounded approaches can generate evaluation criteria alongside task intents; retroactive approaches cannot, because the evaluation criteria would need to be inferred from the trajectory rather than specified upfront.

- **Persona-driven diversity**: Only NNetNav uses personas (a static database); other pipelines rely on scale (InSTA), tutorial content (AgentTrek), or iterative refinement (Explorer) for task variety.

- **Judge design**: All include some form of quality verification (LLM judge, outcome reward model, VLM verification), but none incorporate **evaluation hints**—structured criteria that specify what successful completion looks like. Without hints, judges must infer success criteria from the task intent alone, which is unreliable for tasks where the final state is ambiguous (e.g., "post a comment on the forum" — did the comment actually appear? An LLM judge without hints has no way to verify this from the trajectory alone if it cannot see the rendered page).

- **Module presence**: No prior pipeline instantiates all six modules identified in the AGENT-AS-ANNOTATORS framework. Table 2 shows large gaps: InSTA has no persona generator, NNetNav has no hints and no separate agent (it reuses exploration trajectories), Go-Browse has no persona generator and uses multiple models rather than a single teacher.

The consequence of these ad-hoc designs is that **the field lacks a systematic understanding of which pipeline components contribute to downstream performance and why**. When comparing results across papers, it is impossible to tell whether gains come from teacher quality, task diversity, judging accuracy, or specific design choices—because the pipelines differ in too many ways simultaneously. Progress requires a common vocabulary and modular decomposition that enables controlled ablation of individual components.

#### The Evaluation Gap

Beyond training methodology, there is an **evaluation gap** that complicates comparison. WebArena leaderboard results are collected under heterogeneous conditions: different agent harnesses, observation formats (accessibility tree vs. screenshot-only vs. Set-of-Marks), action spaces, and evaluation protocols. A model's reported success rate depends not just on its capability but on the specific infrastructure used to evaluate it. This makes cross-paper comparison unreliable—a model that appears to underperform another may simply be evaluated under stricter conditions.

The BrowserGym ecosystem (de Chezelles et al., 2024) addresses this by standardizing the agent harness, observation format, and evaluation functions, but few prior distillation papers have adopted it, meaning their results cannot be directly compared.

### How AGENT-AS-ANNOTATORS Positions Itself

The paper positions itself as addressing these three gaps simultaneously: **(1) a unified framework for describing and comparing trajectory synthesis pipelines, (2) a careful empirical study of which pipeline components matter and why, and (3) a demonstration that structured distillation from a single teacher produces generalizable web agent capabilities.**

#### The Framework as Intellectual Infrastructure

The central conceptual move is to organize the trajectory synthesis problem by analogy to **human annotation roles** in benchmark creation. When WebArena's evaluation tasks were created (Zhou et al., 2023c), human contributors played three functional roles:

- **Task Designer**: Explored the web environment to understand its affordances, adopted a specific user perspective or persona, and designed tasks—pairing a natural language intent with evaluation criteria (e.g., programmatic checks or expected outcomes).

- **Annotator**: Executed the designed tasks on the environment, producing step-by-step interaction trajectories that served as demonstrations or evaluation targets.

- **Supervisor**: Reviewed the executed trajectories to verify task completion, catching errors or ambiguities in either task design or execution.

This role structure is not unique to WebArena—it appears in varying degrees across web agent benchmarks (Mind2Web's Deng et al., 2023; WebLINX's Lù et al., 2024) and, more broadly, in NLP data collection efforts where annotation quality and consistency are known challenges (Snow et al., 2008; Gururangan et al., 2018).

AGENT-AS-ANNOTATORS replaces each human role with an LLM module:

- **Persona Generator + Task Generator** (replacing the Task Designer): The Persona Generator produces diverse user profiles (background, expertise, goals) that induce different task distributions within the same environment. The Task Generator receives a persona, explores the environment, stores observations and entity references, and synthesizes task intents paired with **evaluation hints** grounded in real environment state.

- **Agent** (replacing the Annotator): Receives only the task intent and interacts with a freshly reset environment to produce a trajectory. Crucially, the Agent does **not** see the exploration data, hints, or persona, ensuring trajectories reflect genuine task-solving rather than privileged information.

- **Judge with hints** (replacing the Supervisor): Evaluates each trajectory using the interaction record and the evaluation hints, which provide structured criteria that make success assessment more reliable than judging from the intent alone.

This mapping is not merely taxonomic—it has **architectural consequences**. The separation between Task Generator (which sees the environment state) and Agent (which does not) ensures that the Agent must genuinely solve the task rather than regurgitating memorized state. The inclusion of hints in the Judge enables more accurate filtering of training data. And by making each module explicit and swappable, the framework enables systematic ablation and comparison.

#### Relationship to Existing Work

The paper does not claim that any individual component is novel in isolation—LLM judges, persona-driven generation, and teacher distillation are all established techniques. Rather, the contribution is in **how these components are composed**, the **structured roles they play**, and the **empirical demonstration that this composition matters**.

Table 2 makes this positioning explicit by mapping five prior pipelines onto the AGENT-AS-ANNOTATORS modules. Two structural distinctions emerge:

1. **Task grounding**: Only grounded approaches (InSTA, Go-Browse, AGENT-AS-ANNOTATORS) can generate evaluation hints alongside intents, because hints reference expected outcomes that must be defined before execution. Retroactive approaches (NNetNav, Explorer) cannot produce hints because tasks are inferred from trajectories after the fact—there is no "expected outcome" independent of what actually happened. AGENT-AS-ANNOTATORS is the only pipeline that exploits this by generating hints and using them in the Judge.

2. **Module completeness**: AGENT-AS-ANNOTATORS instantiates all six modules (Persona Generator, Exploration, Task Generator, Hints, Agent, Judge), while prior pipelines have significant gaps. InSTA lacks persona-driven diversity and uses scale instead; NNetNav lacks a separate Agent and Hints; Go-Browse lacks personas and uses multiple teacher models rather than a single unified teacher.

These structural differences have downstream consequences that the framework makes explicit and testable. For example, if the persona module matters for downstream student performance, pipelines that lack it should underperform on task diversity metrics. If hints matter for judge accuracy, pipelines without them should have more false positives in their training data. The paper validates several of these hypotheses through ablations (Section 5.3), though a full head-to-head comparison of all pipelines training the same student on comparable data quantities is left to future work.

#### The Specific Research Questions

Within this framework, the paper investigates a set of specific empirical questions that prior work leaves unresolved:

- **Does data quality matter more than data quantity?** Frontier teachers can generate large volumes of trajectories, but teacher success rates vary substantially (Table 4 shows 17–85% across configurations). Does filtering for quality (via the Judge) compensate for having fewer training examples?

- **Do pipeline components contribute independently?** The modular framework enables controlled removal of components (Judge filtering, reasoning traces, hints). If removing a component degrades student performance, that component is contributing non-redundantly.

- **Does teacher quality correlate with student performance?** If better teachers (higher success rates on A3-SYNTH tasks) produce better training data, teacher selection becomes a critical design decision. The paper explicitly compares multiple teacher configurations.

- **Does the reasoning budget of the teacher matter?** Frontier models can be configured with different "thinking budgets" that control how much deliberation they perform. Counterintuitively, the paper explores whether *reducing* the thinking budget improves trajectory quality.

- **Do distilled skills transfer across environments?** Training occurs on WebArena environments only. If the student gains are limited to replicating WebArena-specific patterns, the approach has limited practical value. If skills transfer to entirely different platforms (ServiceNow, MiniWoB's synthetic HTML), it demonstrates that the distillation captures general web interaction primitives.

These questions are not merely academic—they determine whether small-model web agents are a viable deployment strategy and, if so, how to build them efficiently. The paper's answers (Section 5) provide concrete guidance: teacher quality dominates quantity, the reduced thinking budget produces better data, and skills transfer broadly—establishing that structured distillation is not just theoretically interesting but practically effective.

## 3. Technical Approach

### 3.1 Reader orientation

This paper is primarily an **empirical systems paper** that proposes a structured pipeline for generating training data for web agents, fine-tunes a student model on that data, and measures resulting performance. The core idea is deceptively simple: if you carefully structure *how* a frontier LLM generates web interaction trajectories—by mimicking the roles human annotators play when creating benchmarks—you can produce higher-quality training data that teaches a small student model generalizable web skills, not just environment-specific patterns.

The system solves the problem of **closing the capability gap between frontier and small open-weight models for web agent tasks** through a two-phase distillation pipeline: first, a teacher model generates diverse, grounded task intents with evaluation criteria (Phase 1), then the same teacher executes those tasks and a separate judge module filters for successes (Phase 2). The "shape" of the solution is an assembly line: personas produce diverse tasks, exploration grounds those tasks in real environment state, an agent executes them blind, and a judge with structured hints filters out failures. Only the clean, successful trajectories train the student—and the student never sees the teacher's privileged information (exploration data, hints, persona).

### 3.2 Big-picture architecture (diagram in words)

The AGENT-AS-ANNOTATORS pipeline has **six modules organized into two sequential phases**, with a seventh component (the student training step) at the end.

**Phase 1: Task Synthesis** replaces the human Task Designer role with three coordinated LLM modules working in sequence:

1. **Persona Generator** — receives a specification for diverse personas; outputs 250 unique user profiles (each with name, skills, interests, and a narrative background paragraph). Each persona is assigned to all six WebArena environments, creating 1,500 persona-environment pairs.

2. **Exploration (Task Generator sub-component)** — receives a persona-environment pair and a goal to explore the website; navigates the live environment for at least 10 steps, stores the full observation-action trajectory in memory. Outputs an exploration trajectory that captures what entities, pages, and functionalities exist on the site from that persona's perspective.

3. **Task Generator (proper)** — receives the persona, the exploration trajectory, and annotator instructions adapted from the original WebArena annotation guidelines; synthesizes task intents (natural language goals) paired with structured evaluation hints. Key constraint: tasks must reference real entities observed during exploration—no hallucinated products, users, or pages. Outputs `(intent, hints)` pairs grounded in actual environment state.

**Phase 2: Trajectory Collection and Filtering** replaces the human Annotator and Supervisor roles:

4. **Agent** — receives only the task intent (no hints, no exploration data, no persona); interacts with a freshly reset environment instance to produce a step-by-step solution trajectory. This separation is crucial: it ensures the trajectory reflects genuine problem-solving rather than regurgitation of memorized state. Outputs a sequence of observation-action-reasoning steps.

5. **Judge** — receives the full interaction trajectory, the task intent, the evaluation hints, and the first and last screenshots; answers four structured evaluation questions (action looping, side effects, optimality, and success) and produces a binary success/failure label. The hints provide concrete criteria for what "success" looks like (e.g., "the repository should contain a new file named X"). Outputs `(trajectory, success_label)`.

6. **Filter Gate** — an implicit module that simply retains only the Judge-labeled successful trajectories and discards failures. Of the initial 3,000 tasks, 2,322 pass through to student training.

**Downstream: Student Training** — the 2,322 successful trajectories are converted from multi-step interaction logs into multi-turn supervised fine-tuning format. Each observation becomes a user message; each reasoning+action becomes an assistant response. The student model (Qwen3.5-9B, a 9-billion-parameter multimodal model) is fine-tuned for 2 epochs with cross-entropy loss computed only on assistant tokens.

**Information flow summary:** The teacher model (Gemini 3 Pro) serves in three distinct roles—Persona Generator, Task Generator/Explorer, and Agent—each with different prompts and access to different information. The Judge is also Gemini 3 Pro, but operating under a separate evaluation prompt. The student model never interacts with any of these modules; it only sees the final filtered trajectories as static training data.

### 3.3 Roadmap for the deep dive

- **First**, the **Persona Generator** and why persona-driven diversity matters—since task variety within the same six environments is the mechanism that enables generalization, and the specific persona structure (skills, interests, narrative) shapes what kinds of tasks the Task Generator will later produce.

- **Second**, the **Exploration sub-component** of the Task Generator—since task grounding depends on the teacher having actually *seen* the environment state before designing tasks, and the exploration success criterion (`"I am done exploring the websites."` after ≥10 steps) is a simple but consequential design choice.

- **Third**, the **Task Generator proper** and the annotator instructions—since this is where the grounded intents and evaluation hints are produced, and understanding the template-with-variables format makes clear how the pipeline achieves diversity without requiring a frontier model for every single task.

- **Fourth**, the **Agent** and the blind execution constraint—since the separation between what the Task Generator sees and what the Agent sees is the critical mechanism that prevents the training data from containing privileged information the student cannot access at test time.

- **Fifth**, the **Judge** and the four-question evaluation protocol—since judge accuracy directly determines training data quality, and the hints are what distinguish this judge from prior work's LLM judges.

- **Sixth**, the **data format conversion and supervised fine-tuning procedure**—since the specifics of how trajectories become training examples determine what the student actually learns, including the reasoning trace structure, the loss masking strategy, and the hyperparameters.

- **Seventh**, the **teacher model configuration and the thinking budget finding**—since the counterintuitive result that *reducing* the teacher's reasoning budget produces better training data and a stronger student deserves careful explanation.

This is an **empirical systems paper** whose core contribution is a structured pipeline for generating web agent training data, analogous to human annotation workflows, combined with a careful empirical investigation of which design choices in that pipeline matter for downstream student performance.

#### Persona Generator: Inducing Diverse Task Distributions

The pipeline begins with the **Persona Generator**, an LLM module (Gemini 3 Pro) prompted to produce diverse user profiles. The goal is to ensure that the synthesized tasks cover different usage patterns within the same six WebArena environments, since—as the authors argue in Section 6—"persona-driven diversity within these environments may be more efficient than scaling to more websites with less task variety per site."

The persona specification requires each generated profile to contain four structured components:

- **A name** (e.g., "Alice Chen", "Liam O'Connor", "Dr. Fatima Al-Rashidi") — this serves as an identity anchor that the Task Generator can reference when embodying the persona during exploration.

- **Three professional skills** (e.g., "Python Programming, Data Analysis, Machine Learning") — these shape what tasks the persona would plausibly perform on professional tools like GitLab or the Shopping Admin panel. A data scientist would create repositories for ML projects; a graphic designer would upload design assets.

- **Three personal interests** (e.g., "Robotics, Hiking, Sci-Fi Novels") — these shape what tasks the persona would perform on consumer-facing sites like the Reddit forum or the e-commerce storefront. A hiking enthusiast would search for outdoor gear; a sci-fi fan would browse relevant subreddits.

- **A detailed narrative description** (one paragraph) — this weaves the skills and interests into a coherent professional identity and personality, providing the Task Generator with sufficient context to generate tasks that feel authentic to the persona's background. For example, Alice Chen is described as someone who "specializes in transforming raw data into actionable intelligence" and "spends weekends building custom robotics projects."

**Scale.** The Persona Generator produces **250 unique personas**. Each persona is then assigned to **all six WebArena environments**, creating **1,500 persona-environment pairs** that feed into the Exploration module. This combinatorial assignment is deliberate: the intersection of persona characteristics and site affordances produces a rich space of possible tasks, since the same persona generates different tasks on different sites (Alice Chen on GitLab might create a data pipeline repository; Alice Chen on the Shopping Admin panel might analyze product pricing data).

**Why personas rather than scale?** The paper positions this as a deliberate alternative to InSTA's approach of achieving diversity through 150K websites. The hypothesis (explored in Section 6) is that deep diversity within a small number of environments—generated through varied user perspectives—may be more efficient than shallow diversity across many environments. A single website like GitLab supports many different user workflows (creating repositories, managing issues, reviewing merge requests, configuring CI/CD pipelines), and personas naturally partition this space.

**Design choice: LLM-generated rather than rule-based or template-based personas.** The paper uses an LLM to generate the personas rather than using a fixed database (as NNetNav does) or hand-crafting a set of stereotypical user profiles. This provides scalability (250 personas is more than could be reasonably hand-designed) and unpredictability in the persona space, reducing the risk that the Task Generator overfits to a small set of recognizable persona patterns. The LLM's own world knowledge about what different professions do and what they care about provides a rich, realistic prior for persona generation.

**What the student never sees.** Crucially, the personas are used only during task synthesis (Phase 1) to induce varied task distributions. The student model never receives the persona as context during training or evaluation. The persona's function is purely to shape the *distribution of training tasks*, not to provide conditioning information to the student.

#### Exploration: Grounding Tasks in Real Environment State

After a persona is generated and assigned to an environment, the **Exploration** module (a sub-component of the Task Generator) navigates the live web environment to build familiarity with its content, structure, and available functionalities. This step is essential because the Task Generator must later produce tasks that reference **real entities**—existing users, products, repositories, forum posts—rather than hallucinating them from the teacher LLM's parametric knowledge.

**Exploration task format.** The Exploration module receives a specific structured prompt:

> "You have been instructed to explore the websites in order to familiarize yourself with their content and functionalities. When you are done, you should reply to the user with a message indicating that you are done exploring the websites: 'I am done exploring the websites.' Make sure to explore for at least 10 steps before you stop. You have been given the following persona: [persona description]"

The key constraints are: (1) the persona is provided as context to guide exploration toward persona-relevant pages; (2) the agent must explore for at least **10 steps** before terminating; (3) the agent must produce the **exact termination string** `"I am done exploring the websites."` to signal completion.

**Exploration success criterion.** An exploration is considered successful only if the agent navigates for at least 10 interaction steps AND produces the exact termination string. This binary criterion is intentionally simple—it does not evaluate exploration quality or coverage, only that the agent actually explored rather than terminating prematurely. The paper reports (Table 15) that proprietary models achieve substantially higher exploration success rates than open-weight models:

| Model | Exploration SR (%) | Tasks Completed | Total Tasks |
|---|---|---|---|
| Gemini 3.1 Pro (reduced thinking) | 93.1 | 1,396 | 1,500 |
| Gemini 3 Flash | 88.3 | 1,325 | 1,500 |
| Gemini 3 Pro | 87.3 | 1,310 | 1,500 |
| Qwen3-VL-32B-Thinking | 74.7 | 1,121 | 1,500 |
| Qwen3-VL-8B-Thinking | 70.4 | 1,056 | 1,500 |

The primary failure mode for open-weight models is premature termination—stopping before the 10-step minimum—or failing to produce the exact termination string. Proprietary models are more reliable at following the structured exploration instruction.

**What exploration produces.** For each successful exploration, the full observation-action trajectory is stored in memory. This trajectory captures: (1) the actual URLs visited and pages viewed, (2) the interactive elements (buttons, links, forms) discovered, (3) the specific entities encountered (usernames, product names, repository titles, article topics), and (4) the navigation paths that connect different parts of the site. This stored exploration context is then passed to the Task Generator as grounding material.

**Design choice: why separate exploration from task generation?** The paper could have merged exploration and task generation into a single step—have the teacher simultaneously explore and generate tasks. The separation serves two purposes. First, it ensures that the exploration is thorough (at least 10 steps) before any tasks are synthesized, preventing the Task Generator from settling on the first interesting thing it sees. Second, it enables the exploration trajectory to be stored and potentially reused—the paper generates two task intents per exploration (from different steps), meaning 1,500 explorations yield 3,000 tasks. This amortizes the exploration cost across multiple tasks.

**Design choice: the minimum 10-step threshold.** The 10-step minimum is a heuristic that balances exploration depth against cost. One step of exploration involves: the agent receives the current page observation (URL + accessibility tree), produces a reasoned action (e.g., "click on the 'Projects' link to see available repositories"), executes it in the browser, and receives the resulting page state. Ten such steps typically navigate through 3–5 distinct pages, providing enough context to understand the site's structure. The paper does not ablate this threshold, so the sensitivity of downstream task quality to exploration depth is unknown.

**An implicit filtering effect.** Only successful explorations are passed to the Task Generator. Because Gemini 3 Pro achieves 87.3% exploration success, approximately 1,310 of the 1,500 exploration tasks succeed. The remaining 190 persona-environment pairs that fail exploration are essentially discarded—the Task Generator never sees them, and no tasks are generated for those persona-site combinations. This means the training data distribution is shaped not only by persona-driven diversity but also by which persona-site pairs the teacher could successfully explore. Hard-to-navigate combinations are silently filtered out.

#### Task Generator: Synthesizing Grounded Task Intents with Evaluation Hints

The **Task Generator** is the central module of Phase 1. It receives three inputs: the assigned persona, the exploration trajectory from the current environment, and a set of **annotator instructions** adapted from the original WebArena annotation guidelines (Zhou et al., 2023c). Its outputs are `(intent, hints)` pairs—the task intent (a natural language goal) and the evaluation hints (structured criteria for determining whether the task was completed).

**Annotator instructions.** The Task Generator's system prompt includes three explicit requirements for task quality, drawn from the human annotation guidelines:

1. **Abstract and high-level.** Tasks must require multiple actions to complete, not merely one or two primitive operations. The instructions specify: "instead of 'click the science subreddit,' annotators are encouraged to produce intents like 'post a greeting message on science subreddit,'" which requires navigation to the subreddit, finding the post creation interface, composing content, and submitting—a workflow of 4–6 meaningful actions.

2. **Creative with constraints.** The instructions discourage "common tasks such as account creation" and instead require annotators to "add constraints" that produce unique intents. The example given: "create a Reddit account identical to my GitLab one" imposes a cross-site constraint that requires the agent to retrieve information from one environment and apply it to another. This creativity criterion aims to produce training data that teaches flexible, compositional problem-solving rather than rote workflows.

3. **Template-based with variables.** Task intents should be formulated as templates with replaceable elements marked as variables within double curly braces (e.g., `{{section name}}`, `{{topic}}`). Each template is then instantiated with multiple variable assignments, producing diverse concrete tasks from a single template. The example in Section E.2: the template "Browse the {{section name}} section to find a post containing {{topic}}" can be instantiated as "Browse the General section to find a post containing urban exploration" or "Browse the Off-Topic section to find a post containing analog photography."

**Template-with-variables mechanism.** This design choice has significant implications for data efficiency and diversity. Rather than having the LLM generate each task from scratch (which would require expensive frontier model calls for every single training example), the Task Generator produces a smaller number of **templates**—abstract task structures with placeholder variables—and then instantiates them with environment-grounded variable assignments. The template captures the *structure* of the task (what type of workflow it represents); the variable assignments capture the *specifics* (which entities, values, or constraints apply). This separation means that the diversity of the training data comes from both the template space (different task types) and the variable space (different instantiations), and the variable space can be expanded by simply substituting new values without re-generating the template.

**Grounding constraint: tasks must reference real entities.** The Task Generator receives the exploration trajectory as context and is instructed to reference only entities that were observed during exploration. This is a critical constraint that distinguishes AGENT-AS-ANNOTATORS from InSTA, which generates tasks by prompting the LLM without environment exploration. If a task references a non-existent product (e.g., "Buy the Deluxe Widget Pro"), the Agent attempting to execute it will fail regardless of its capability—the product simply does not exist in the environment state. Such failures in the training data would teach the student to attempt impossible actions. By grounding tasks in exploration, the Task Generator ensures that the synthetic intents are actually executable.

**Evaluation hints generation.** For each task intent, the Task Generator also produces structured evaluation hints. These are natural language descriptions of what the environment state should look like if the task is successfully completed. The hints are not executable verification functions—they are criteria written for the Judge module to use when determining success. Examples from Section E.3:

- **Reddit hint**: "The agent must navigate to the specified section of the forum, identify a post that contains content related to urban exploration (e.g., by checking titles or images), and successfully submit a reply that explicitly mentions the design principle. Success is measured by the presence of the user's comment on the post page."

- **GitLab hint**: "The agent should create the repository with the specified name, ensure it is public, and contains a README. Then navigate to the Issues section, create a new issue with the exact title, and apply the 'enhancement' label. Success requires both the repository and issue to be visible."

- **Shopping Admin hint**: "The agent must access the product catalog, filter or navigate to the Electronics category, identify the most expensive product, edit its price to 99.99, and save the changes. The product's price should be updated to $99.99 upon completion."

**Why hints matter.** Without hints, a Judge must infer success criteria from the task intent alone. For many web tasks, the final state of the environment is ambiguous from the action log alone. If the task is "post a comment on the science subreddit," the Agent's trajectory might show it typing a comment and clicking "Submit," but the Judge has no way to verify that the comment actually appeared (network errors, moderation filters, or incorrect form submission could prevent it). The hints provide the Judge with a **concrete observable criterion** that would otherwise require programmatic evaluation or human inspection. The paper finds (Section 5.3, Table 14) that removing hints degrades student performance by 2.4 percentage points at matched data size, confirming that hint-aided judging produces higher-quality training data.

**How many tasks?** From 1,500 explorations, the Task Generator synthesizes **two task intents per exploration**, yielding **3,000 total tasks** distributed evenly across six environments (500 per site). The two tasks per exploration are drawn from different steps of the exploration trajectory, ensuring they reference different aspects of the environment. This "two tasks per exploration" design is another efficiency choice: the exploration cost (which involves live browser interaction) is amortized across multiple tasks, while the task generation cost (LLM inference) is relatively cheap.

**Example synthesized tasks.** The paper provides five examples in Appendix E.3, illustrating the diversity across sites and personas:

- **Shopping Admin (persona: Alice Chen, Data Scientist)**: "Navigate to the product catalog and change the price of the most expensive product in the 'Electronics' category to $99.99." This task involves filtering, numerical comparison, and form editing—workflows a data scientist might perform when managing product data.

- **Map (persona: Liam O'Connor, Graphic Designer)**: "Search for street art galleries near the city center and get directions from the nearest parking lot to the top-rated gallery." This leverages the persona's interest in street art and requires multi-step spatial reasoning—search, compare ratings, search for parking, compute directions.

- **Shopping (persona: Dr. Fatima Al-Rashidi, Biomedical Researcher)**: "Find a laboratory notebook suitable for research documentation, add it to the shopping cart, and proceed to the checkout page." This task ties directly to the persona's professional context and involves product search, evaluation, and transactional workflow.

**Design choice: why not generate tasks without personas?** The paper does not include a "no-persona" ablation where all 3,000 tasks are generated from a neutral prompt. Running this ablation would require regenerating exploration and task synthesis from scratch (since the persona shapes which pages are explored and what tasks are designed), and the paper leaves this to future work (Section 6). The hypothesis—supported indirectly by the persona-driven nature of the successful transfer results—is that persona-conditioned task synthesis produces a wider variety of task *types* (not just surface-level variation) because different personas access different subsets of each site's functionality.

#### Agent: Blind Task Execution

The **Agent** module receives only the **task intent** and interacts with a **freshly reset environment instance** to produce a step-by-step solution trajectory. Crucially, the Agent does **not** receive:

- The evaluation hints (those are for the Judge only)
- The exploration trajectory (which would reveal environment state)
- The persona (which would provide task-solving context the student will not have at test time)
- Any privileged information about the expected outcome

This **blind execution constraint** is a deliberate design choice that the paper explicitly connects to the concept of "privileged information distillation" (Peñaloza et al., 2026, cited in Section 2's extended related work): the teacher has access to information during trajectory generation that is unavailable to the student at inference time, and the distillation process must ensure that the training data does not inadvertently condition on that privileged information.

**Why blind execution matters.** If the Agent saw the exploration trajectory, it could simply repeat the exact actions the explorer took—trivializing the task and producing training data that teaches the student to recall memorized paths rather than to solve novel tasks. If the Agent saw the hints, it would know exactly what the Judge is looking for and could optimize its trajectory to satisfy those criteria rather than to genuinely complete the task. Both forms of privileged information would artificially inflate the teacher's success rate on A3-SYNTH tasks without producing training trajectories that generalize to evaluation settings where such information is absent.

**Observation format.** At each step, the Agent receives: (1) the current page URL, (2) the accessibility tree (AXTree)—a hierarchical, text-based representation of the page's interactive elements, each with a unique `bid` (browsing ID) identifier, (3) a screenshot of the current page, and (4) the task goal and the agent's previous action. The multimodal input (AXTree + screenshot) means the Agent can reason about both the structural layout (via the AXTree) and the visual appearance (via the screenshot).

**Action format.** The Agent produces structured actions in a predetermined text format. The supported action types are:

- `click(bid)` — click an interactive element identified by its browsing ID
- `fill(bid, text)` — type text into an input field
- `select_option(bid, option)` — choose an option from a dropdown menu
- `scroll(x, y)` — scroll the page by pixel offsets
- `keyboard_press(key)` — send a keyboard shortcut
- `hover(bid)` — move the mouse over an element (for hover-triggered menus)
- `goto(url)` — navigate to a specific URL
- `go_back()` — navigate to the previous page in browser history
- `send_msg_to_user(text)` — communicate the final answer or status to the user

**Reasoning trace structure.** Each Agent action is accompanied by explicit reasoning in structured blocks, which become part of the training data for the student. The format uses two specific XML-like tags:

- `<thought>...</thought>` — high-level strategic reasoning about what the agent is trying to achieve at the current step (e.g., "I need to find the science subreddit, which is likely listed in the sidebar navigation. I should first identify the main navigation menu.")
- ` thinking...回答` — step-by-step operational deliberation (e.g., "The sidebar contains a list of communities. I can see links labeled 'General,' 'Off-Topic,' 'Announcements,' and 'Science.' I should click on 'Science' to navigate to that subreddit.")

The final action is placed within an `<action>...</action>` tag. The average assistant response across the training data is **1,920 characters**, with 100% of responses containing `<thought>` blocks (median length: 996 characters) and 81.4% containing `解决` blocks (median length when present: 459 characters).

**Why two reasoning blocks?** The distinction between `<thought>` (strategic) and `解决` (operational) decomposes the reasoning task for the student. The strategic reasoning addresses *what* to do (goal selection, plan formulation); the operational reasoning addresses *how* to do it (element identification, value selection, action parameterization). By separating these, the training data provides the student with a more structured learning signal: the student learns to first plan at a high level, then execute at a low level—a useful decomposition that mimics the two-phase approach of many web agent architectures (planning-then-acting, as in WebGUM, WebVoyager, etc.).

**Teacher model for the Agent.** The paper uses the **same Gemini 3 Pro model** (with reduced thinking budget, discussed below) as the Agent—no separate solver model, no model switching between task generation and execution. This single-teacher design simplifies the pipeline and ensures consistency between the task generation and task execution distributions. If different models were used, distribution mismatch could cause the Agent to systematically fail on tasks that the Task Generator considered straightforward.

**Agent success rates.** The Agent's success rate on A3-SYNTH tasks, as judged by the subsequent Judge module, varies by environment and teacher configuration (Table 4). For the primary teacher configuration (Gemini 3 Pro, reduced thinking), the per-site success rates are:

| Environment | Success Rate |
|---|---|
| Wikipedia | 85.4% |
| Shopping | 80.8% |
| Shop Admin | 80.8% |
| Map | 78.0% |
| GitLab | 70.6% |
| Reddit | 69.0% |

Wikipedia tasks tend to be most straightforward (editing pages, searching content), while Reddit tasks are most challenging (multi-step social interactions requiring finding specific posts, composing contextual replies, and verifying publication). These success rates determine the effective yield of the pipeline: of the 3,000 tasks generated, the number that survive Judge filtering and become training data is approximately 3,000 × (average success rate across environments) = 3,000 × ~77.4% ≈ 2,322, matching the final dataset size.

#### Judge: Structured Evaluation with Hints

The **Judge** module evaluates each Agent trajectory to produce a binary success/failure label. Only trajectories marked as successful are retained for student training. The Judge is also implemented with Gemini 3 Pro but under a different prompt and task framing.

**Judge input.** For each trajectory, the Judge receives six components:

1. A **system prompt** defining its role as an evaluator of web agent performance.
2. The **task goal** (the original intent from the Task Generator).
3. The **evaluation hints** (the structured success criteria from the Task Generator).
4. The full **action sequence** with URLs and reasoning at each step—the complete observation-action-reasoning log.
5. The **final accessibility tree** — the AXTree of the page the agent ended on.
6. The **first and last screenshots** of the interaction—visual evidence of the starting and ending states.

The screenshots provide the Judge with visual grounding: it can verify, for example, that a form was actually submitted (the final screenshot shows a confirmation page) or a comment appeared (the final screenshot shows the comment on the page). Without screenshots, the Judge would be limited to the AXTree's structural information, which may not capture visual confirmation elements.

**Four-question evaluation protocol.** The Judge answers four structured questions about the trajectory, each with predefined answer options. The question ordering is deliberate:

1. **Action looping** (`<loop>` tag): "Did the agent loop through actions without making progress?" Binary: Yes/No. This checks for failure modes where the agent repeats the same or similar actions without advancing toward the goal—a common problem in web agents that get stuck on unresponsive elements or modal dialogs.

2. **Side effects** (`<side>` tag): "Did the agent perform unnecessary actions with unintended side effects?" Binary: Yes/No. This checks for actions that, while not directly task-related, may have modified environment state in ways that complicate success verification (e.g., accidentally deleting content while navigating).

3. **Optimality** (`<optimal>` tag): "Was the task performed optimally?" Four-point scale: Complete Failure, Suboptimal, Somewhat Optimal, Completely Optimal. This is a graded assessment of efficiency, not a binary filter—it provides a richer signal about trajectory quality, though the paper does not use the optimality rating directly for filtering (only the binary success judgment determines inclusion in training data).

4. **Success** (`<success>` tag): "Was the task successfully completed?" Binary: Successful/Unsuccessful. This is the final, decisive judgment. A trajectory is retained for training only if the `<success>` tag contains "Successful."

**Why this question ordering?** The paper notes that asking the success question *last* (after side effects, looping, and optimality) follows an "inverted" ordering designed to "reduce confirmation bias in success judgments." The idea is that by forcing the Judge to first consider potential problems (looping, side effects, suboptimal execution), it is less likely to prematurely conclude success based on superficial indicators. This ordering draws on the evaluation protocol from AgentRewardBench (Lù et al., 2025), which benchmarks automatic evaluators for web agents and found that structured, multi-question evaluation with negative questions first improves accuracy.

**Hint integration.** The evaluation hints are appended to the task goal in the Judge's prompt. The paper illustrates the difference with an example: the hint "Success is measured by the presence of the user's comment on the post page" gives the Judge a concrete observable criterion that would be difficult to infer from the task intent alone ("post a comment on the science subreddit"—does the intent require the comment to be *visible* on the page, or just submitted? The hint resolves this ambiguity).

**Parsing and binary labeling.** Judge responses are parsed by extracting content from the structured tags (`<success>`, `<side>`, `<loop>`, `<optimal>`). A trajectory is retained for training only if the `<success>` tag contains the string "Successful." The other three questions (looping, side effects, optimality) are collected but not used for filtering in the published results—they provide diagnostic information that could be used for more sophisticated filtering in future work.

**Judge accuracy and the impact of hints.** The paper ablates the Judge's hints in Section 5.3 and Appendix C.5: re-judging all 2,999 trajectories (both successful and failed under the hinted Judge) with hints removed from the prompt flips the verdict for **21.3% of trajectories** (632 of 2,968 re-judged). Of these, **144 trajectories** that the hinted Judge had marked as successful are now judged as unsuccessful—these are false positives that the hints helped catch. Training on the no-hints-filtered data produces a student that underperforms the hints-filtered student by 2.4 percentage points at matched data size (600 tasks each), confirming that hints improve Judge accuracy and that improved Judge accuracy translates to better downstream student performance.

**Position bias mitigation.** The paper notes that to "mitigate position bias," the Judge randomizes the ordering of evaluation options. Position bias refers to the tendency of LLM evaluators to favor answer options that appear earlier or later in the prompt—a known issue in LLM-as-judge settings (Zheng et al., 2023). Randomizing whether "Successful" or "Unsuccessful" appears first reduces the risk that a consistent position preference systematically biases the success labels.

**Judge vs. programmatic evaluation.** The original WebArena evaluation relies on programmatic evaluators—hand-crafted functions that check URL matches, string matches, and HTML element states to determine task completion. These are deterministic but require per-task engineering and cannot evaluate open-ended outcomes (e.g., "the comment should be relevant to the post"). The LLM Judge with hints trades determinism for flexibility: it can evaluate any task, including creative or open-ended ones, but introduces LLM-specific noise (hallucination, misinterpretation, inconsistency). The hints serve as a middle ground—they provide structure that constrains the Judge's evaluation without requiring per-task code. The paper does not measure the Judge's agreement rate with human evaluators, acknowledging this as a limitation: "The Judge's false positive rate has not been measured against human labels, as building a reliable annotation interface for multi-step web trajectories is a substantial effort in itself."

#### Data Format Conversion and Supervised Fine-Tuning

Once the Judge has filtered trajectories, the 2,322 successful trajectories are converted from multi-step interaction logs into a **multi-turn supervised fine-tuning (SFT) format** compatible with standard autoregressive language model training.

**Conversion procedure.** Each interaction step in a trajectory becomes one exchange in a multi-turn conversation:

- **User message** (what the model receives at inference): contains the current observation, which includes the page URL, the AXTree representation, a screenshot encoded as an image, and the task goal with context about previous actions. The user message is formatted as if it were coming from the environment to the agent.

- **Assistant response** (what the model must learn to produce): contains the structured reasoning and action. The format is:

  ```
  <thought>high-level strategic reasoning</thought>
  逐步 operational deliberation回答
  <action>click(bid="42")</action>
  ```

  The full reasoning trace from the teacher is preserved intact in the training data. This is important because the paper's reasoning trace ablation shows that removing these traces drops student performance by 7.9 percentage points (Table 3).

**Loss masking.** The standard cross-entropy language modeling loss is computed **only on assistant tokens**—the user message tokens (observations, task goals, previous context) are masked from the loss computation. This ensures the model learns to generate appropriate reasoning and actions conditioned on observations, without being trained to reproduce the observation format itself. This is a standard technique in instruction tuning and multi-turn SFT; the student learns the mapping `(observation, context) → (reasoning, action)` rather than simply modeling the full conversation distribution.

**Training hyperparameters.** The fine-tuning uses the following specific configuration (detailed in Appendix E.6, Table 17):

- **Base model**: Qwen3.5-9B (Bai et al., 2025), a 9-billion-parameter multimodal model supporting both text and image inputs
- **Training data**: 16,353 observation-action pairs from 2,322 trajectories (average 7.0 steps per trajectory)
- **Learning rate**: `1 × 10⁻⁵` with cosine annealing and warmup
- **Warmup ratio**: 0.03 (3% of total steps used for learning rate warmup)
- **Weight decay**: 0.0 (no L2 regularization)
- **Maximum gradient norm**: 0.3 (gradient clipping threshold)
- **Epochs**: 2
- **Batch size per GPU**: 1
- **Gradient accumulation steps**: 4
- **Effective batch size**: 8 GPUs × 4 accumulation steps × 1 per GPU = **32**
- **Maximum sequence length**: 8,192 tokens
- **Precision**: bfloat16
- **Attention implementation**: Flash Attention 2 (Dao et al., 2022)
- **Parallelism**: Fully Sharded Data Parallelism (FSDP; Zhao et al., 2023) across 4–8 GPUs (A100 80GB or H200 141GB)
- **Optimizer**: AdamW
- **Checkpoint saving**: every 200 steps
- **Random seed**: 0

The total number of training steps is approximately **1,022** (since 16,353 examples ÷ batch size 32 ≈ 511 steps per epoch, × 2 epochs ≈ 1,022 steps). Training takes approximately 12–16 hours on 8 GPUs.

**Infrastructure and model serving.** Training uses the HuggingFace Transformers library with the TRL (Transformer Reinforcement Learning) framework. At evaluation time, the fine-tuned model is served using vLLM (Kwon et al., 2023) with tensor parallelism across 2 GPUs, in enforce-eager mode (disabling CUDA graphs for reliability with fine-tuned checkpoints), exposed via an OpenAI-compatible API endpoint.

**Observation truncation at inference.** All models operate under a unified token budget (Section G.3):

- Maximum total tokens: 65,536
- Maximum prompt tokens: 57,344
- Maximum new tokens (generation): 8,192

When the observation—primarily the AXTree, which can exceed 30K tokens for complex pages—exceeds the prompt token limit, it is truncated. This truncation can theoretically remove important interactive elements from the agent's view, but the generous prompt budget (57K tokens) is designed to accommodate typical web page sizes.

**Why training loss is not a reliable evaluation metric.** The paper explicitly notes (Section 4.2) that "training loss proved to be a poor predictor of downstream performance." Specifically, models trained on Flash teacher data achieved lower training loss but performed "substantially worse" than those trained on Pro teacher data on WebArena. This is consistent with findings in instruction tuning literature (Zhou et al., 2023b; LIMA): lower perplexity on the training distribution does not necessarily translate to better task completion performance, especially when the training data comes from different teachers with different quality characteristics. The paper uses WebArena success rate (not validation loss) as the primary metric for all design decisions.

#### Teacher Model Configuration and the Thinking Budget Finding

One of the paper's most counterintuitive findings concerns the teacher model's reasoning budget. Frontier models like Gemini 3 Pro can be configured with different "thinking budgets" that control how much internal deliberation they perform before producing output. Intuitively, a higher thinking budget—allowing the model to reason more extensively—should produce better trajectories for distillation. The paper finds the opposite.

**What is a thinking budget?** Frontier reasoning models (like Gemini's Pro series or OpenAI's o-series) perform internal chain-of-thought deliberation before generating visible output. The "thinking budget" controls how many tokens of internal reasoning the model is allowed to perform. A higher budget means the model can explore more alternatives, verify its reasoning, and catch errors before acting. A reduced budget forces the model to deliberate more concisely and produce more direct reasoning traces. The paper uses "reduced thinking" for the primary configuration and "high thinking" as a comparison point.

**The finding: reduced thinking produces better trajectories (Table 4).** Across all six WebArena environments, the Gemini 3 Pro teacher with reduced thinking budget achieves higher success rates than the same model with default (higher) thinking:

| Environment | Pro (reduced thinking) | Pro (default thinking) |
|---|---|---|
| Reddit | 69.0% | 66.0% |
| GitLab | 70.6% | 64.2% |
| Shopping | 80.8% | 68.8% |
| Shop Admin | 80.8% | 78.2% |
| Wikipedia | 85.4% | 78.8% |
| Map | 78.0% | 74.4% |

The improvement ranges from +2.6pp (Shop Admin) to +12.0pp (Shopping), with an average improvement of approximately +8pp. This is not a subtle effect—the reduced thinking configuration is consistently better across all environments.

**Two competing hypotheses for why.** The paper offers two explanations (Section 5.2):

1. **Concise traces are easier for the student to learn from.** When the teacher deliberates extensively, it may produce verbose, meandering reasoning traces that are harder for the student to imitate. Concise traces present a cleaner signal—the essential reasoning is preserved, but irrelevant deliberation is removed. This is the "learnability" hypothesis: it is not that the teacher is worse at the task, but that the data it produces is worse for training.

2. **The teacher itself performs better with reduced thinking.** Extended reasoning can lead to "overthinking"—the model may talk itself out of correct initial instincts, introduce spurious considerations that complicate the action plan, or simply run up against context limits and lose coherence. This is the "teacher competence" hypothesis: the reduced thinking budget actually makes the teacher a more capable agent.

The paper states that "hypothesis (2) is directly supported by our data," since the teacher's own success rates are higher with reduced thinking. This suggests that the primary mechanism is improved teacher performance, not just improved training signal. The teacher with reduced thinking is simply better at completing web tasks, and those stronger trajectories make better training data.

**The surprising interaction with visible reasoning.** The paper also provides evidence that visible reasoning *trace length* does not increase with higher thinking budgets. When training a student on data from Gemini 3 Pro with high thinking (orange diamond in Figure 9b), the student performs at only **24.4%**, substantially worse than the reduced-thinking student's **41.5%**. The paper hypothesizes that with a larger thinking budget, "the model performs more internal deliberation and produces more summarized outputs, externalizing less of its reasoning into the visible trace. The student, which can only learn from the visible text, receives a weaker training signal as a result." This is a critical insight: if the teacher's most important reasoning happens internally (not in the visible trace), the student never sees it and cannot learn from it. The reduced thinking budget may force the teacher to externalize more reasoning, improving the training signal.

**Comparison across teacher models (Table 4, Figure 3).** The paper evaluates five teacher configurations and finds a clear quality hierarchy:

| Teacher Configuration | Average A3-SYNTH SR (%) | Student WebArena SR (%) |
|---|---|---|
| Gemini 3 Pro (reduced thinking) | ~77.4% (avg across sites) | 41.5% |
| Gemini 3 Pro (default thinking) | ~71.7% | 36.2% (on Qwen3-VL-8B-T) |
| Gemini 3.1 Pro (reduced thinking) | ~57.9% | 27.0% (on Qwen3-VL-8B-T) |
| Gemini 3 Flash (high thinking) | ~35.0% | — |
| Gemini 3 Flash (reduced thinking) | ~35.0% | 24.9% (on Qwen3-VL-8B-T) |

The student performance numbers for Pro, 3.1 Pro, and Flash were measured on Qwen3-VL-8B-Thinking (an earlier-generation student) before Qwen3.5-9B became available, and were used for teacher selection. The trend in Figure 3 shows a roughly linear relationship between teacher A3-SYNTH success rate and downstream student WebArena performance—teacher quality directly predicts student quality.

**A cautionary finding: model recency does not predict teaching effectiveness.** Gemini 3.1 Pro is a newer model than Gemini 3 Pro, but it achieves substantially lower A3-SYNTH success rates (45.4% vs. 78.0% on Map, for example). This means that simply using the "latest" frontier model is not sufficient—the model must be effective on the specific task distribution. The paper hypothesizes that the newer model's capabilities "may not transfer uniformly to self-hosted web environments," possibly because its training data or instruction tuning had different emphasis.

**Flash produces more examples but worse quality.** The Flash teacher configurations produce **more total training examples** (22,707 observation-action pairs vs. 16,353 for Pro reduced thinking) despite lower success rates, because failed trajectories tend to be longer—the agent takes more steps before giving up. However, student performance on Flash data (24.9%) is far below Pro data (41.5%), despite 39% more training examples. This is direct evidence for the paper's core claim that **data quality matters more than data quantity** in distillation for web agents.

#### Summary of Design Choices and Their Justifications

The AGENT-AS-ANNOTATORS pipeline makes several specific design decisions that distinguish it from prior work:

- **Persona-driven diversity over scale-based diversity:** Personas partition the task space within each environment along user-type axes, potentially producing more systematic coverage than simply scaling to more websites with shallow task variety per site. The combinatorial assignment (250 personas × 6 environments) amplifies diversity multiplicatively.

- **Exploration-before-generation over direct prompting:** The Task Generator explores before designing tasks, ensuring that generated intents reference real environment entities. This avoids the hallucination problem that affects pipelines like InSTA, where tasks may reference non-existent entities.

- **Blind execution over privileged execution:** The Agent does not see exploration data, hints, or persona. This ensures training trajectories reflect genuine problem-solving from the task intent alone, preventing the training data from conditioning on information unavailable at test time.

- **Hints-augmented judging over intent-only judging:** The Judge receives structured success criteria alongside the task intent, improving its accuracy by providing concrete observable criteria. The hints ablation confirms this contributes 2.4pp to student performance at matched data size.

- **Reasoning trace preservation over action-only data:** The full structured reasoning (`<thought>` + `逐步`) is preserved in the training data. The reasoning trace ablation shows removing these traces costs 7.9pp, making them the single most impactful pipeline component.

- **Single unified teacher over multi-model pipelines:** The same model (Gemini 3 Pro) serves as Persona Generator, Explorer, Task Generator, Agent, and Judge, simplifying reproducibility and ensuring distributional consistency. This contrasts with Go-Browse's separate solver models and InSTA's potentially different models for proposal and execution.

- **Reduced thinking budget over maximum deliberation:** Counterintuitively, constraining the teacher's reasoning budget improves both teacher success rates and student outcomes, likely because it prevents overthinking and ensures reasoning is externalized in the visible trace.

- **Last-step success filtering over detailed quality filtering:** Only a binary success judgment (not optimality rating or side-effect assessment) determines whether a trajectory enters the training set. The other Judge questions provide diagnostic information but are not used for filtering, keeping the pipeline simple.

- **Pure SFT over SFT + RL:** The student is trained with supervised learning only, even though RL-based refinement (DigiRL, Agent Q, OpenWebVoyager) is a natural next step. The paper positions RL as orthogonal future work, focusing squarely on the data generation pipeline.

## 4. Key Insights and Innovations

### Innovation 1: The Annotation-Role Framework as a Lens for Diagnosing Pipeline Design

The paper's most intellectually distinctive contribution is not any individual module—personas, judges, hints—but the **meta-framework that organizes those modules into a coherent diagnostic vocabulary**. By mapping trajectory synthesis onto the three-role structure of human benchmark annotation (Task Designer, Annotator, Supervisor), the paper provides a lens for seeing *why* prior pipelines differ in their downstream effectiveness, not just *that* they differ.

This matters because the field was in a classic "alchemy" phase: multiple pipelines (InSTA, NNetNav, Go-Browse, Explorer, AgentTrek) all claimed to distill web agent capabilities, but their designs diverged along ad-hoc axes (retroactive vs. grounded task generation, scale-based vs. persona-based diversity, LLM judge vs. VLM verifier). Table 2 is the paper's central diagnostic instrument: by mapping each pipeline onto the six AGENT-AS-ANNOTATORS modules, it reveals structural gaps that were invisible when each pipeline was described in its own vocabulary. For example, NNetNav appears "incomplete" under this mapping—it lacks a separate Agent (reusing exploration trajectories instead), lacks Hints (because retroactive labeling cannot produce evaluation criteria), and uses a static persona database rather than generated personas. InSTA's only gap is the absence of personas and evaluation hints. These aren't just descriptive differences; the paper's ablations demonstrate they are **mechanistically consequential**: removing hints costs 2.4pp, removing reasoning traces costs 7.9pp, and teacher quality (which varies across instantiations) strongly predicts student performance.

The intellectual move here is analogous to what the transformer architecture did for sequence modeling—not inventing attention, but providing a **compositional vocabulary** that made it possible to ask "what happens if we remove this component?" and get interpretable answers. Prior to this framework, comparing InSTA to NNetNav was apples-to-oranges because the pipelines differed in too many correlated ways. After the framework, the comparison decomposes into discrete module choices (Does InSTA have hints? No. Does NNetNav? No. Does AGENT-AS-ANNOTATORS? Yes.), each of which can be independently ablated. This is a **fundamental reframing**, not an incremental improvement—it converts a collection of bespoke recipes into a design space that can be systematically explored.

The significance extends beyond web agents. Any domain where synthetic trajectory generation involves a teacher model interacting with an environment—code generation, robotics, game playing, tool use—faces analogous design choices about what information the teacher sees, how tasks are grounded, and how quality is verified. The Task Designer/Annotator/Supervisor decomposition provides a template for structuring those pipelines. The framework's value is therefore primarily **conceptual and methodological**, not empirical; the empirical results validate that the framework's distinctions matter, but the framework itself is the intellectual infrastructure.

---

### Innovation 2: Evidence That Teacher Quality Dominates Data Quantity in Agentic Distillation

The paper's second distinctive contribution is a crisp empirical finding with immediate practical consequences: **in distillation for web agents, teacher quality (measured by the teacher's own success rate on the training tasks) matters more than the volume of training data, and the relationship is approximately monotonic.** This overturns the natural intuition that "more data is better" and provides a concrete criterion for teacher selection.

The evidence comes from multiple converging experiments. The most direct is Figure 3: student WebArena success rate plotted against teacher A3-SYNTH success rate across three teacher configurations (Gemini 3 Pro, Gemini 3.1 Pro, Gemini 3 Flash, all with reduced thinking). The relationship is roughly linear: the Pro-trained student reaches 36.2%, the 3.1 Pro-trained student reaches 27.0%, and the Flash-trained student reaches 24.9%. The Pro teacher's advantage holds despite Flash producing **39% more training examples** (22,707 vs. 16,353 observation-action pairs) because failed trajectories from weaker teachers tend to be longer (more steps before giving up), inflating the raw data count with low-quality examples.

This is not just another "quality over quantity" slogan. The paper specifies *what quality means* in this context—the teacher's capability on the specific task distribution, measured by success rate—and shows it is more predictive than the model's recency (Gemini 3.1 Pro, a newer model, underperforms the older Gemini 3 Pro on four of six sites) or its scale (Flash is from the same family but substantially weaker). This has immediate practical implications: when building a distillation pipeline, invest effort in teacher selection and configuration (e.g., tuning the thinking budget) before scaling data volume. The paper's own teacher selection process—comparing three teachers on A3-SYNTH success rates and picking the best—exemplifies this principle.

The finding also contextualizes prior work. InSTA (Trabucco et al., 2025) reported that a 1.7B student trained on high-quality data outperformed its 235B teacher—an anecdotal observation that the current paper systematizes into a general relationship. The thinking budget result (Section 5.2) adds nuance: teacher quality is not just about which model you use, but how you configure it, with the counterintuitive implication that **reducing the teacher's reasoning capacity can improve downstream student performance**.

This is an **empirical insight with theoretical implications**—it suggests that the primary bottleneck in agentic distillation is not data coverage but teacher competence, and that investing in better teachers (or better teacher configurations) yields higher returns than scaling data collection within the same teacher budget.

---

### Innovation 3: Privileged Information Separation as an Architectural Principle

The paper identifies and enforces a structural constraint that prior pipelines either ignored or handled implicitly: **the separation between what the teacher sees during task generation (exploration data, hints, persona context) and what the agent sees during task execution (the intent only)**. This is not a novel idea in isolation—Peñaloza et al. (2026) studied "privileged information distillation" in other domains—but its application to web agent trajectory synthesis is a distinctive contribution because web environments make the failure mode of privileged information particularly acute.

The reasoning is worth unpacking. If the Agent (which generates training trajectories) sees the exploration data, it can simply repeat the exact navigation path the explorer took—producing trajectories that teach the student to replay memorized sequences rather than to solve novel tasks from intent alone. If the Agent sees the hints, it can optimize its actions to satisfy the Judge's specific criteria rather than genuinely completing the task. Both failures would produce training data that looks successful (the Judge would approve it) but teaches the wrong thing: the student learns to rely on information that will not be available at test time. The result would be inflated A3-SYNTH success rates and poor generalization—precisely the pattern the paper avoids.

Prior pipelines handled this inconsistently. NNetNav collapses the Task Designer and Annotator roles entirely—the exploration trajectory *is* the training data, retroactively labeled with a task description. There is no separate execution phase, so there is no privileged information separation at all. InSTA uses the same LLM for task proposal and execution, but the paper does not specify whether the execution agent sees the proposal context, making it unclear whether privileged information leakage occurs. Go-Browse separates feasibility checking from solving but uses multiple models, making the information boundary harder to track.

AGENT-AS-ANNOTATORS makes the separation **explicit and architecturally enforced**: the Agent module receives only the task intent, with a freshly reset environment. This is not just good hygiene—it is a **mechanism for ensuring that the distillation process captures generalizable problem-solving capability rather than environment-specific memorization**. The paper's transfer results (WorkArena L1 +18.2pp, MiniWoB +5.8pp on environments never seen during training) provide indirect evidence that this separation works as intended: the student learns general web interaction primitives rather than WebArena-specific shortcuts.

This is a **conceptual contribution with architectural implications**—it identifies a design principle (privileged information separation) that should constrain any trajectory synthesis pipeline and provides a concrete mechanism (the blind execution stage) for enforcing it. Its significance lies in making explicit what prior work handled implicitly or ignored, enabling future pipeline designers to reason about information boundaries systematically.

---

### Innovation 4: The Demonstrated Generality of Distilled Web Skills Across Four Distinct Transfer Axes

The paper's fourth contribution is an empirical finding that exceeds reasonable expectations: **a 9B model trained exclusively on six self-hosted WebArena environments transfers to four qualitatively different evaluation settings**, including an enterprise platform (ServiceNow, through WorkArena) with completely different layouts, navigation patterns, and design language. The magnitude of the largest transfer gain—+18.2 percentage points on WorkArena L1—demands explanation beyond "the student learned to use the BrowserGym action space."

The paper hypothesizes (Section 6) that the six WebArena environments "cover the core web interaction primitives (form filling, table navigation, search, multi-step workflows) that recur across these diverse interfaces." This is plausible but underspecified—many training pipelines cover form filling and search without producing +18pp transfer to enterprise platforms. What AGENT-AS-ANNOTATORS may be doing differently is teaching **structured reasoning about web interactions** rather than surface-level action patterns. The reasoning traces preserved in the training data (`<thought>` for strategic planning, `逐步` for operational deliberation) provide the student with a template for decomposing novel web tasks into recognizable sub-problems: identify the relevant UI element, determine the correct action, parameterize it with the right values, verify the outcome. This decomposition is environment-agnostic—it applies to a GitLab repository and a ServiceNow asset manager equally, even though the specific element IDs and navigation paths differ.

The transfer pattern is worth examining closely. The four axes are: (1) to an unseen enterprise platform (+18.2pp on WorkArena L1), (2) to longer-horizon compositional tasks (+7.5pp on WorkArena++ L2), (3) to visually grounded tasks with image-based instructions (+5.4pp on VisualWebArena), and (4) to simplified HTML micro-tasks (+5.8pp on MiniWoB). The gains are largest on WorkArena L1, which involves basic record creation and list filtering—tasks that share structural similarity with WebArena's e-commerce and wiki editing workflows, even though the surface interfaces differ. The gains are smallest on VisualWebArena, which may require visual reasoning capabilities that the text-heavy WebArena training does not emphasize. This gradient suggests that the transfer is not magic—it is mediated by the degree of structural similarity between the training and evaluation tasks—but the existence of consistent positive transfer across all four axes is a strong signal that the distillation captures generalizable skills.

This is an **empirical finding with practical implications**. It means that a single carefully-designed distillation dataset may suffice for deploying agents across multiple platforms, reducing the need for per-platform data collection. It also provides evidence that the six-environment depth strategy (persona-driven diversity within a small number of environments) is viable—the skills acquired are not overfit to WebArena's specific web applications. However, the transfer is not unlimited: WorkArena++ L2 (9.7% for the fine-tuned 9B model vs. 40.0% for Gemini 3.1 Pro) shows that longer-horizon compositional enterprise tasks remain challenging, consistent with the hypothesis that the model transfers interaction primitives but not complex multi-step planning strategies.

The broader significance is that this finding **validates the structured distillation approach as a deployment strategy**. If the gains had been confined to WebArena (the training environment), the approach would be a clever form of benchmark overfitting. The consistent cross-benchmark improvements demonstrate that it is not—the student learns something genuinely general about how to interact with web interfaces.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** All experiments use the **MATH benchmark** (Hendrycks et al., 2021), consisting of high-school competition-level math problems. The specific split from Lightman et al. (2022) is used: 12,000 training questions for PRM training and 500 test questions for evaluation. Web agent evaluation uses **WebArena** (381 test tasks across six self-hosted web applications; Zhou et al., 2023c) as the in-domain benchmark, **VisualWebArena** (449 test tasks; Koh et al., 2024a) for visually grounded tasks, **WorkArena** L1 (330 episodes; Drouin et al., 2024) and **WorkArena++** L2 (185 tasks; Boisvert et al., 2024) for enterprise platform tasks, and **MiniWoB** (125 task types; Liu et al., 2018) for atomic web skills. All web benchmarks except WebArena are fully out-of-distribution relative to the training environments.

- **Base model(s).** The primary student is **Qwen3.5-9B** (Bai et al., 2025), a 9B-parameter multimodal model supporting text and image inputs. This model is chosen as representative of the small open-weight models that are candidates for local deployment. Base comparisons include Qwen3.5-27B, Qwen3.5-4B, and Qwen3.5-2B (same family, different scales). The teacher model across all pipeline stages is **Gemini 3 Pro** with reduced thinking budget; alternative teacher configurations include Gemini 3.1 Pro, Gemini 3 Flash, and varying thinking budgets (Table 4, Appendix B.1). Proprietary baselines evaluated under the same protocol include Gemini 3.1 Pro, Gemini 3 Pro, Gemini 3.1 Flash Lite, Claude 3.5 Sonnet, GPT-4o, and others (Table 10).

- **Metrics.** The primary metric is **task success rate (%)**, defined differently per benchmark: WebArena and VisualWebArena use a combination of URL matching, string matching, and programmatic HTML checks; WorkArena uses ServiceNow API validation; MiniWoB uses programmatic reward functions. For teacher evaluation on A3-SYNTH, success is determined by the Judge module's binary `Successful`/`Unsuccessful` label (Section 4.1, Appendix E.4). All results are reported as percentage of tasks successfully completed. Training loss is computed but explicitly noted as "a poor predictor of downstream performance" (Section 4.2), with WebArena success rate serving as the primary quality signal.

- **Baselines.** Multiple baseline categories are evaluated. **Proprietary frontier models**: Gemini 3.1 Pro, Gemini 3 Pro, Gemini 3.1 Flash Lite (all via BrowserGym GenericAgent protocol); Claude 3.5 Sonnet, GPT-4o, GPT-4o-mini, o1-mini, Llama 3.1 405B, Llama 3.1 70B (from BrowserGym ecosystem traces, Table 10). **Open-weight base models**: Qwen3.5-27B, Qwen3.5-9B, Qwen3.5-4B, Qwen3.5-2B, Qwen3-VL-8B-Thinking, Qwen3-VL-32B-Thinking (all evaluated under the same GenericAgent protocol). **Published distillation baselines**: Go-Browse (Gandhi & Neubig, 2025) at 21.7% on WebArena (different student and harness, comparison confounded); NNetNav (Murty et al., 2024a) at 18.8% (Table 11). The base 9B model (31.0%) serves as the primary within-experiment baseline for measuring fine-tuning gains.

- **Generation budget / compute accounting.** All models operate under a unified **token budget** during evaluation: maximum 65,536 total tokens, 57,344 prompt tokens, and 8,192 generation tokens per step (Appendix G.3). Training compute is measured in number of training trajectories (2,322 for the full pipeline) and observation-action pairs (16,353), with ablations at 285, 715, and 1,430 trajectories (Table 13). Teacher comparisons control for total training examples: the Judge-filtered Pro reduced-thinking data contains 16,353 examples despite fewer initial tasks (3,000); unfiltered data contains 22,707 examples but lower quality (Table 4, Appendix C.1). No FLOPs-matched comparison between pretraining and test-time compute is performed—the paper's focus is on data quality rather than compute efficiency per se.

- **Cross-validation / statistical protocol.** No formal cross-validation is used for student evaluation—all benchmarks have fixed test splits (Appendix F.2). For pipeline design decisions, teacher selection was performed by comparing three teacher configurations (Gemini 3 Pro, 3.1 Pro, Flash) on an earlier student model (Qwen3-VL-8B-Thinking) before committing to the primary Qwen3.5-9B experiments (Section 5.2, Figure 3). Error bars or confidence intervals are not reported for any results. Environment reliability is addressed by retrying each task up to 10 times on failure and fully resetting WebArena instances between evaluation runs (Appendix G.1); residual errors (browser crashes, network timeouts, environment bugs) are included as failures in the denominator.

### Main Quantitative Results

#### Cross-Benchmark Evaluation: Distillation Gains Transfer Across All Benchmarks

**Headline result.** The fine-tuned A3-Qwen3.5-9B achieves **41.5% on WebArena**, a **+10.5 percentage point gain** over the base Qwen3.5-9B (31.0%), surpassing GPT-4o (31.5%) and Claude 3.5 Sonnet (36.0%) under the same evaluation protocol (Table 1, Table 10). This nearly doubles the previous best open-weight SFT result on full WebArena (Go-Browse, 21.7%), though that comparison is confounded by differences in agent harness and student architecture (Table 11, Appendix B.6).

**Transfer to unseen environments.** Gains are observed on all four out-of-distribution benchmarks (Table 1, Figure 4):

- **WorkArena L1 (+18.2pp):** From 33.3% to **51.5%** — the largest absolute gain. This is on ServiceNow, an enterprise platform with completely different layouts, form structures, and navigation patterns from any WebArena environment. The base 9B model's 33.3% to 51.5% jump narrows the gap to the 3× larger Qwen3.5-27B (57.0%) and approaches GPT-4o (45.5% under the same protocol, Table 10). Per-category breakdown (Table 7) reveals the largest gains on Order tasks (+38.9pp, from 57.8% to 96.7%) and Chart tasks (+22.5pp, from 42.5% to 65.0%).

- **VisualWebArena (+5.4pp):** From 28.5% to **33.9%** (Table 6). The full-benchmark result (including train split) is 33.7%. Gains concentrate on Reddit tasks (+14.1pp), with smaller improvements on Shopping (+2.6pp) and Classifieds (+13.4pp on the test split).

- **WorkArena++ L2 (+7.5pp):** From 2.2% to **9.7%** (Table 8). While the absolute number remains low, this represents a 4.4× relative improvement. Gains are concentrated on Filter tasks (+30.9pp, from 2.4% to 33.3%), with no improvement on Dashboard tasks (0% for all models). The large gap to Gemini 3.1 Pro (40.0%) indicates that L2-level compositional enterprise tasks remain challenging for small models.

- **MiniWoB (+5.8pp):** From 63.2% to **69.0%** (Table 9). This matches Claude 3.5 Sonnet (69.8%) under the same protocol (Table 10). Gains are largest on Type tasks (+11.4pp) and Workflow tasks (+10.6pp), with smaller improvements on Click (+1.2pp) and Reason (+4.4pp).

**Scaling behavior across student sizes (Appendix B.4, Table 5).** Distillation benefits hold across three student scales: A3-Qwen3.5-9B gains +10.5pp, A3-Qwen3.5-4B gains **+11.1pp** (from 24.1% to 35.2%), and A3-Qwen3.5-2B gains **+6.1pp** (from 3.1% to 9.2%). The 4B model achieves comparable percentage-point gains to the 9B model, while the 2B model shows diminishing returns, likely due to limited model capacity. The fine-tuned 9B model matches the 27B base model on WebArena (both 41.5%), bridging a 3× parameter gap—though whether the 27B model would also benefit from distillation remains an open question.

**Per-site WebArena analysis (Table 5).** The largest absolute gains from fine-tuning come on **GitLab (+18.8pp,** from 30.7% to 49.5%) and **Shopping Admin (+18.0pp,** from 26.9% to 44.9%), environments involving complex form-filling and navigation workflows. Smaller gains appear on Reddit (+2.0pp, 54.2% to 56.2%), Shopping (+3.3pp, 30.0% to 33.3%), and Map (+4.7pp, 20.3% to 25.0%). The Reddit base performance was already relatively high (54.2%), suggesting a ceiling effect.

**Qualitative behavioral evidence (Figure 2, Figures 5–8).** The paper provides five example trajectories comparing base vs. fine-tuned models, each showing the base model failing (through inefficient navigation, premature action, or incorrect answers) while the fine-tuned model succeeds in fewer steps. On a WebArena Shopping Admin task, the base model "wanders through filters for 10 actions and returns the wrong order," while A3-Qwen3.5-9B "navigates directly to the correct order in 2 steps" (Figure 2). On a WorkArena L1 task (Figure 5), the base model takes 15 actions without completing the order, while the fine-tuned model completes it in 5 actions.

**Comparison with BrowserGym ecosystem (Table 10).** Because evaluation uses the same GenericAgent harness and observation format as the BrowserGym TMLR traces, results can be directly compared with six previously evaluated models. A3-Qwen3.5-9B (41.5%) exceeds Claude 3.5 Sonnet (36.0%) by 5.5pp and GPT-4o (31.5%) by 10.0pp. On WorkArena L1, it falls between GPT-4o (45.5%) and Claude 3.5 Sonnet (56.4%). On MiniWoB, it matches Claude 3.5 Sonnet (69.0% vs. 69.8%). The base Qwen3.5-9B (31.0%) performs comparably to GPT-4o-mini (13.6–31.0% range across benchmarks) and Llama 3.1 70B (17.1–64.6% range). Two caveats: the BrowserGym traces were collected 6–12 months earlier with an older framework version, and newer model releases (Gemini 3.1 Pro, Qwen3.5 family) were unavailable at that time, so the comparison reflects both fine-tuning gains and generational model improvements (Appendix B.5).

**Comparison with published leaderboard results (Table 11).** When contextualized against official leaderboards, the 9B model's 42.1% on the full 812-task WebArena benchmark exceeds the previous best open-weight SFT result (Go-Browse, 21.7%) by 20.4pp, though Go-Browse uses a different student model (Qwen-2.5-7B) and teacher (multiple models including Claude 3.7 Sonnet), so the comparison reflects differences in both pipeline and architecture. Multi-agent systems (OpAgent, 71.6%) and next-generation proprietary models (GPT-5, Claude 4 Sonnet) substantially exceed the single-model SFT approach, particularly on enterprise tasks—these represent upper bounds for what more complex architectures or stronger base models can achieve. Notably, few sub-10B open-weight models report results on WorkArena or MiniWoB, making A3-Qwen3.5-9B one of the first small open models evaluated across the full five-benchmark suite.

---

#### Teacher Model Quality: Better Teachers Produce Better Students

**Headline result.** Teacher quality on A3-SYNTH—measured by the teacher's own task success rate as judged by the Judge module—is a strong predictor of downstream student performance, and this relationship is approximately monotonic (Figure 3, Table 4).

**Teacher comparison on A3-SYNTH (Table 4).** Gemini 3 Pro with reduced thinking achieves the highest per-site success rates: 69.0% (Reddit) to 85.4% (Wikipedia), averaging approximately 77.4% across environments. Gemini 3 Pro with default thinking achieves 64.2% to 78.8% (average ~71.7%). Gemini 3.1 Pro with reduced thinking drops substantially: 45.4% to 67.6% (average ~57.9%). Gemini 3 Flash configurations plateau around 17–46% (average ~35.0%). The hierarchy is consistent across all six environments.

**Downstream student performance (Figure 3).** Training Qwen3-VL-8B-Thinking on data from three teacher configurations (all reduced thinking) yields: Pro data → 36.2%, 3.1 Pro data → 27.0%, Flash data → 24.9%. The relationship between teacher A3-SYNTH success rate and student WebArena performance is approximately linear across these three points. This validates teacher selection as a critical design decision and justifies the choice of Gemini 3 Pro (reduced thinking) for the primary model.

**Model recency is not a reliable proxy for teaching effectiveness.** Despite being a newer model, Gemini 3.1 Pro underperforms the older Gemini 3 Pro on five of six sites (Table 4). The largest gap is on Map: 45.4% (3.1 Pro) vs. 78.0% (3 Pro). This suggests that a model's training data and instruction tuning may not transfer uniformly to the specific web environments used in A3-SYNTH, and that empirical teacher evaluation on the target task distribution is necessary—recency cannot substitute for measurement.

**Data quantity does not compensate for quality.** The Flash teacher produces **22,707 total training examples** compared to Pro's 16,353 (Table 4)—a 39% increase. The surplus comes from failed trajectories being longer (more steps before the agent gives up). Despite having more data, the Flash-trained student achieves only 24.9% vs. Pro's 36.2% (Figure 3). This is direct evidence that data quality dominates quantity in this distillation setting.

**Impact of reasoning budget (Table 4, Section 5.2, Appendix C.3).** Counterintuitively, **reducing the teacher's thinking budget improves success rates across all six environments.** Pro with reduced thinking outperforms Pro with default thinking on every site, with improvements ranging from +2.6pp (Shop Admin: 80.8% vs. 78.2%) to +12.0pp (Shopping: 80.8% vs. 68.8%). The paper offers two hypotheses: (1) the reduced budget forces the teacher to externalize more reasoning into the visible trace, improving the training signal for the student; (2) extended thinking leads to overthinking and execution errors, making the teacher a less effective agent. The data supports hypothesis (2) directly since the teacher's own success rates improve, not just the student's. Additionally, training a student on data from the high-thinking teacher yields only 24.4% (Figure 9b, orange diamond), substantially below the reduced-thinking student's 41.5%, despite similar visible reasoning trace lengths—suggesting the high-thinking teacher performs more internal deliberation and summarizes its output, providing a weaker training signal.

#### Ablation Studies: Each Pipeline Component Contributes Measurably

**Judge filtering (Table 3, top section, and Appendix C.1, Table 12).** Removing the Judge and training on all 2,999 trajectories (including failed ones), rather than only the 2,322 Judge-verified successes, **reduces WebArena success rate by 4.5pp** (from 41.5% to 37.0%) despite providing 40% more training data. The largest per-site drops occur on Map (−7.5pp), Shopping (−6.8pp), and GitLab (−6.6pp). This confirms that Judge filtering removes trajectories that would otherwise degrade the training signal—the Judge does not just exclude obviously broken trajectories but acts as a quality gate that improves the signal-to-noise ratio.

**Data scaling (Table 3, middle section, and Appendix C.2, Table 13, Figure 9a).** Performance scales log-linearly with training data quantity, with clear diminishing returns:

| Trajectories | Steps | WebArena SR (%) | Incremental Gain |
|---|---|---|---|
| 285 | 2,036 | 32.0% | — |
| 715 | 5,060 | 37.0% | +5.0pp |
| 1,430 | 9,999 | 40.2% | +3.2pp |
| 2,322 | 16,353 | 41.5% | +1.3pp |

The smallest subset (285 trajectories, 2,036 steps) achieves only 32.0%—marginally above the base model's 31.0%, a difference of approximately 4 tasks on the 381-task benchmark. This suggests that very small amounts of distilled data provide negligible gains. The last 892 trajectories (1,430→2,322) contribute only 1.3pp, indicating that substantially more data from the same pipeline would likely yield only modest additional gains. The paper interprets this as evidence that further scaling would require "new task generation strategies rather than simply more of the same" (Section 6).

**Reasoning traces (Table 3, top section, and Appendix C.3, Figure 9b).** Removing reasoning traces entirely from the training data drops WebArena success rate from 41.5% to **33.6% (−7.9pp)**, making this the single most impactful component removal. Surprisingly, **truncating reasoning traces is worse than removing them entirely:** at 500-character truncation, performance drops to 31.0% (−10.5pp); at 250-character truncation, to 26.8% (−14.7pp), below the base model's 31.0%. This suggests that truncated reasoning creates incoherent training signal—the student learns to produce reasoning cut off mid-thought, which is worse than learning to act without explicit reasoning. The full reasoning traces (average 1,920 characters with structured `<thought>` and `逐步` blocks) preserve the teacher's complete deliberation, providing a coherent reasoning template for the student.

**Evaluation hints (Table 3, bottom section, and Appendix C.5, Table 14).** At matched data size (600 tasks per variant), training on data filtered by a Judge with hints achieves **37.8%**, compared to **35.4%** when the Judge operates without hints—a **2.4pp difference**. The absolute gap from the full pipeline (41.5%) to the no-hints variant (35.4%) is 6.1pp, but this conflates data quantity (600 vs. 2,322 tasks) with hints. The 2.4pp gap at matched size isolates the hints' contribution. Re-judging all 2,999 trajectories with hints removed flips the verdict for 21.3% of trajectories (632 of 2,968), with 144 trajectories that the hinted Judge marked as successful being reclassified as unsuccessful—these are false positives that hints helped catch. The largest per-site drops from removing hints occur on Shopping Admin (−6.4pp) and GitLab (−5.5pp) at matched data size.

**Persona module (Appendix C.4).** The paper does not include a controlled no-persona ablation (generating all 3,000 tasks from a neutral prompt). A 600-task subset of persona-driven data achieves 37.8%, retaining 91% of the full pipeline's performance with only 26% of the training data, demonstrating that persona-driven tasks are effective at smaller scales. However, whether persona-driven tasks *outperform* non-persona tasks at matched scale cannot be determined from the reported experiments—the 37.8% figure is a reference point for the hints ablation, not a comparison against a no-persona baseline. The paper acknowledges this gap: "the persona module lacks a controlled no-persona comparison...running the full pipeline without personas requires regenerating exploration and task synthesis from scratch, which we leave to future work" (Section 6).

### Critical Assessment

The paper makes several central claims that require careful scrutiny against the experimental evidence. I assess each in turn, identifying where the experiments genuinely demonstrate the claim and where they demonstrate something narrower or remain unverified.

**Claim 1: "The framework produces a 9B model that surpasses GPT-4o and Claude 3.5 Sonnet on WebArena."**

The evidence for this claim is direct and well-controlled. Both the A3-Qwen3.5-9B model and the proprietary baselines are evaluated under the same BrowserGym GenericAgent protocol (Table 10, Appendix B.5), eliminating harness-level confounds. The numbers are unambiguous: A3-Qwen3.5-9B at 41.5% vs. GPT-4o at 31.5% vs. Claude 3.5 Sonnet at 36.0%. However, three qualifications are necessary. First, the BrowserGym traces for GPT-4o and Claude 3.5 Sonnet were collected 6–12 months earlier with an older framework version, and minor changes in observation processing may affect results (Appendix B.5). Second, these proprietary models represent generations that preceded the Gemini 3 Pro teacher—the comparison is between a student distilled from a more recent frontier model and older frontier models, not a contemporaneous comparison. Third, the claim is specific to WebArena under this evaluation protocol; the fine-tuned 9B model does *not* surpass these models on all benchmarks (e.g., WorkArena L1: 51.5% for A3-Qwen3.5-9B vs. 56.4% for Claude 3.5 Sonnet in Table 10; VisualWebArena: 33.9% vs. GPT-4o's 26.3% but Claude 3.5 Sonnet's value is only 22.0% in a different evaluation configuration). The claim as stated is accurate but bounded—it holds for the specific benchmark, protocol, and model generations tested.

**Claim 2: "Capabilities transfer to completely unseen environments, with an 18.2pp gain on WorkArena L1."**

This claim is the paper's strongest empirical finding and is well-supported. The 18.2pp gain on WorkArena L1 (Table 1, Table 7) is measured under the same evaluation protocol as the baseline, on an enterprise platform with no overlap with WebArena's environments. The gain is large enough (33.3% → 51.5%) to be practically meaningful, not just statistically detectable (though no statistical tests are reported). The pattern of gains across the four transfer axes (+18.2pp L1, +7.5pp L2, +5.4pp VWA, +5.8pp MiniWoB) is internally consistent: larger gains on structurally similar tasks, smaller gains on tasks requiring capabilities less emphasized in training (visual grounding for VWA, long-horizon composition for L2). The qualitative examples (Figures 5–8) provide mechanistic plausibility—the fine-tuned model completes tasks in fewer, more targeted steps, consistent with having learned efficient interaction primitives.

The primary limitation is that the *source* of transfer is not experimentally isolated. The paper attributes transfer to learning "general web interaction primitives" (Section 6), but this remains a post-hoc hypothesis. Alternative explanations—that the student simply learned to use the BrowserGym action space more effectively, or that the teacher's reasoning traces provide a general problem-solving template—are not disentangled. An ablation that trained the student on the same trajectories but with reasoning traces removed (and tested on WorkArena) would help distinguish whether the reasoning structure or the action patterns drive transfer. The no-reasoning ablation in Appendix C.3 is only evaluated on WebArena, not on transfer benchmarks.

**Claim 3: "Each pipeline component contributes meaningfully, with Judge filtering, evaluation hints, and reasoning traces each accounting for measurable gains."**

This claim is supported by the ablation experiments (Table 3) with specific magnitudes: Judge filtering contributes 4.5pp, reasoning traces contribute 7.9pp, hints contribute 2.4pp at matched data size. However, the **Persona Generator lacks a controlled ablation**, which is a significant gap given that persona-driven diversity is framed as a key architectural difference from prior work (Section 3.2, Table 2). The 600-task persona subset results (37.8%) demonstrate that persona-driven data works at smaller scales, but they do not demonstrate that personas *cause* better performance than non-persona task generation at the same scale. Running the full pipeline without personas would require regenerating exploration and task synthesis, which the paper acknowledges as future work (Section 6). Without this ablation, the contribution of the persona module—and the paper's central argument that "persona-driven diversity within these environments may be more efficient than scaling to more websites" (Section 6)—remains a hypothesis rather than a demonstrated finding.

Additionally, the **component contributions are not demonstrated to be independent or additive.** The ablation table (Table 3) removes one component at a time from the full pipeline, but does not test combinations of removals (e.g., no Judge AND no reasoning traces). The interaction effects between components are unknown—it is possible, for example, that reasoning traces matter more when Judge filtering is also present (because the traces are higher quality in successful trajectories), or that hints matter less when the Judge is removed entirely (since there is no judge to benefit from hints). The paper reports component contributions as isolated drops from the full pipeline, which is standard practice but leaves open the question of whether the gains are truly decomposable.

**Claim 4: "Data quality matters more than quantity."**

This claim is supported by multiple converging lines of evidence and is the paper's most robust empirical finding. The Flash-vs-Pro comparison (Table 4, Figure 3) shows that Flash produces 39% more training examples but yields a substantially weaker student (24.9% vs. 36.2% on Qwen3-VL-8B-Thinking). The unfiltered-vs-filtered ablation (Table 12) shows that adding 677 failed trajectories (40% more data) *decreases* student performance by 4.5pp. The reduced-thinking-vs-high-thinking comparison (Figure 9b) shows the high-thinking teacher produces a student at 24.4% vs. 41.5%, despite similar data volume.

However, "quality" in these experiments is operationalized specifically as **Judge-assessed success rate on the A3-SYNTH tasks.** A trajectory that is marked "Successful" by the Judge is considered high quality; one marked "Unsuccessful" is considered low quality. This operationalization inherits all the limitations of the Judge: it may have false positives (incorrectly marking failures as successes) or false negatives (incorrectly rejecting valid trajectories). The paper acknowledges that "the Judge's false positive rate has not been measured against human labels" (Section 6), meaning the quality metric itself is an approximation. If the Judge systematically misjudges certain types of tasks (e.g., tasks requiring visual verification where screenshots are ambiguous), the "quality" signal would be biased and the resulting training data would inherit that bias. Without human validation, the claim "quality matters more than quantity" is more precisely stated as "Judge-filtered data produces better students than unfiltered data"—a narrower claim that does not require the Judge to be perfectly calibrated to human notions of quality.

**Missing experiments that would strengthen the paper.**

- **Human validation of Judge decisions.** A sample of trajectories judged as successful and unsuccessful by the Judge, evaluated by human annotators, would calibrate the quality claims and bound the false positive rate. The paper frames this as a substantial effort ("building a reliable annotation interface for multi-step web trajectories is a substantial effort in itself," Section 6), but even a small validation set (50–100 trajectories) would provide meaningful calibration.

- **Head-to-head comparison with prior pipelines training the same student.** A core motivation for the framework is enabling systematic comparison (Section 3.2), but the paper does not implement and compare prior pipelines. Training Qwen3.5-9B on NNetNav-style data (retroactively labeled exploration trajectories) or InSTA-style data (scale-driven task generation with LLM judge) at matched data quantities would directly test whether the AGENT-AS-ANNOTATORS module choices matter beyond teacher quality. The paper acknowledges this gap: "The framework also enables direct comparison with prior pipelines by training the same student on data from each; we leave this to future work" (Section 5.3).

- **No-persona ablation.** As discussed above, the persona module's contribution is untested.

- **Difficulty-stratified analysis.** The paper reports aggregate success rates without breaking down by task difficulty, environment complexity, or required interaction depth. It is plausible that distillation gains concentrate on certain difficulty tiers (e.g., easier tasks where base model pass@1 is non-zero), and that harder tasks see minimal improvement—analogous to the difficulty-dependent scaling patterns in the example paper on test-time compute. Such stratification would clarify the boundary conditions of the approach.

- **Statistical significance.** No confidence intervals, standard deviations, or significance tests are reported for any result. With a 381-task WebArena test set, a 1.3pp difference (the gain from the last 892 trajectories) corresponds to approximately 5 additional correct tasks—small enough that run-to-run variance could matter. The paper does not discuss or quantify this variance.

- **Multiple random seeds for training.** All fine-tuning results report a single training run (random seed 0, Table 17). With a dataset of only 2,322 trajectories (small by LLM fine-tuning standards) and no measure of training variance, it is unclear whether the reported differences between pipeline variants would replicate.

**Boundary conditions and conditional claims.**

The paper's claims hold most strongly under the specific conditions tested: WebArena-like web environments, Gemini-family teachers, Qwen-family students, SFT-only training, and the BrowserGym evaluation protocol. Several stated and implicit boundary conditions deserve emphasis:

- **Teacher capability floor.** The approach requires a teacher that can achieve non-trivial success rates on the target task distribution. If the teacher's A3-SYNTH success rate approaches zero (as with the Flash teacher on Map, 17.0%), the quantity of successful trajectories approaches zero regardless of total attempts. The framework cannot bootstrap from a teacher that cannot complete the task at all—consistent with the finding that "test-time compute can amplify existing capability but cannot create it from nothing" (analogous to the example paper).

- **Environment reset reliability.** The pipeline depends on the ability to reset environments to a clean state for Agent execution. On live websites (as in InSTA's 150K website approach), reset is impossible—each task execution permanently modifies environment state. This constrains AGENT-AS-ANNOTATORS to environments with reset capabilities (self-hosted instances, simulators, or sandboxes), limiting its applicability to "internet-scale" distillation.

- **Student model capability floor.** The 9B and 4B students show substantial gains (+10.5pp, +11.1pp), but the 2B student gains only +6.1pp, reaching only 9.2% (Table 5). This suggests a capability floor below which the student cannot effectively learn from the distillation data—consistent with the paper's observation of "diminishing returns at 2B."

- **Generalization is constrained, not unlimited.** The transfer gains follow a gradient: largest on structurally similar tasks (WorkArena L1, +18.2pp), smaller on tasks requiring capabilities less emphasized in training (VisualWebArena, +5.4pp; MiniWoB, +5.8pp), and nearly absent on the hardest compositional tasks (WorkArena++ L2 Dashboard: 0% for all models, Table 8). The model has not learned general web agent capability in any unrestricted sense; it has learned skills that transfer to environments sharing structural features with the training data.

- **The comparison to frontier models is time-bound.** The paper compares to GPT-4o and Claude 3.5 Sonnet—models that were frontier at the time of the BrowserGym TMLR evaluation (6–12 months prior). Newer models (Gemini 3.1 Pro at 53.8%, Claude 4 Sonnet, GPT-5) substantially exceed the fine-tuned 9B model. The paper's claim of "surpassing closed-source models" should be understood as surpassing *specific, earlier-generation* closed-source models under specific evaluation conditions, not as establishing parity with the current frontier.

**Overall assessment.** The experiments provide strong evidence for the paper's practical contributions: (1) structured distillation with Judge filtering and reasoning traces produces substantial gains over base open-weight models, (2) these gains transfer across environments, and (3) teacher quality matters more than data quantity. The experimental design is clean within its scope—single harness, standardized evaluation, fair baselines—and the ablation studies isolate component contributions with reasonable precision. The primary weaknesses are the untested persona contribution, the absence of statistical quantification, and the single-seed training. These do not undermine the core findings but limit the precision and generality of the claims. The paper's significance lies more in demonstrating the viability of the approach and providing empirical guidance for its implementation than in establishing precise effect sizes or theoretical mechanisms.

## 6. Limitations and Trade-offs

### Difficulty Estimation Cost Is Unaccounted For in the Headline Efficiency Claims

The paper's difficulty estimation procedure — generating 2,048 samples per question and averaging PRM final-answer scores to assign difficulty bins — requires compute that **exceeds the largest test-time budgets studied**. The authors are transparent about this in Section 3.2:

> "estimating difficulty in this way still incurs additional computation cost during inference... our experiments do not account for this cost largely for simplicity"

The consequence is that the reported 4× efficiency gains over best-of-N (Figures 4 and 8) are computed **after difficulty is already known**, without amortizing the cost of learning it. In a realistic deployment, the total cost would be difficulty estimation (generating and scoring 2,048 samples per prompt) plus strategy execution. For most practical budgets (4–256 generations for the strategy itself), the estimation cost dominates: a 64-generation compute-optimal strategy that achieves the accuracy of a 256-generation best-of-N baseline requires first spending 2,048 generations to determine that the prompt is in difficulty bin 2, making the total cost 2,048 + 64 = 2,112 generations — far worse than simply running best-of-256 directly at 256 generations. The 4× figure is therefore an **upper bound on achievable efficiency under the assumption of free difficulty estimation**, not a realized deployment gain.

The paper provides no measurement of the minimum number of samples needed for reliable difficulty estimation (Section 3.2 notes this is an "exploration-exploitation tradeoff" and flags it as "a key avenue for future work"). Without such measurement, the practical viability of the compute-optimal framework is unproven. The authors acknowledge this limitation explicitly but do not resolve it.

**Mitigation status:** The paper proposes future work on "pretraining or finetuning models to directly predict difficulty of a question" (Section 8) and suggests the PRM's average score as a proxy that avoids ground-truth labels but does not reduce the generation cost. No cheap difficulty estimator is developed or evaluated in this work. Until such a method exists, the compute-optimal framework as described is **more expensive end-to-end than the baselines it outperforms** on a per-prompt basis.

---

### The Method Provides No Benefit on Hard Problems Where the Base Model's Pass@1 Is Near Zero

Across all methods studied — PRM search, iterative revisions, and compute-optimal combinations — the hardest difficulty bin (bin 5, where the base model's pass@1 is lowest) shows **essentially no improvement regardless of compute budget**. In Figure 3 (right), bin 5 accuracy is 1–3% for all methods at all budget levels. In Figure 7 (right), bin 5 accuracy is roughly 2–3% regardless of the sequential-to-parallel ratio. In the FLOPs-matched comparison (Figure 9), the bin 5 scaling curve is flat near 0–5% and falls below the 14× larger model's greedy performance across all three values of R.

This is a hard capability bound: test-time compute **amplifies existing capability but cannot create it**. When the base model's pass@1 is effectively zero on a problem class, no amount of search or revision produces correct solutions because there are no correct trajectories in the proposal distribution to find or refine. The paper is explicit about this limitation (Section 7 takeaway box):

> "test-time compute can amplify existing capability but cannot create it from nothing"

The practical consequence is that the approach offers **no path forward for genuinely novel or out-of-distribution reasoning** that exceeds the base model's training distribution. For the hardest MATH competition problems (bin 5), the base PaLM 2-S* model simply cannot produce correct solutions, and no inference-time strategy changes this. Any deployment that encounters a meaningful fraction of such problems must either accept near-zero accuracy or invest in larger-scale pretraining.

The difficulty bin thresholds reported in the paper are specific to PaLM 2-S* on MATH. A different base model or task distribution would shift which problems fall into bin 5, but the qualitative phenomenon — an absolute floor below which test-time compute provides zero benefit — is likely universal. The paper does not explore methods that might partially overcome this floor (e.g., using the revision model to iteratively explore solution strategies rather than refine existing ones), but this is a fundamental limitation of any approach that operates only on the base model's output distribution.

**Evidence in the paper:** Figures 3, 7, and 9 all show bin 5 as essentially flat and near-zero. The FLOPs-matched analysis in Section 7 explicitly quantifies the failure: at R ≫ 1 with PRM search, hard questions show a −52.9% relative disadvantage compared to the 14× larger model.

**Mitigation status:** The paper acknowledges this limitation candidly in Section 7 and does not attempt to solve it. The authors frame it as a boundary condition: test-time compute and pretraining compute are not 1-to-1 exchangeable, and some problems require the capability acquisition that only pretraining provides.

---

### The Revision Model Suffers from a 38% Correct-to-Incorrect Reversion Rate

A significant practical issue with the revision model is that approximately **38% of correct answers produced during a sequential revision chain get "revised" back to incorrect answers** in a subsequent step (Section 6.1). This is a direct consequence of the training data construction: the model was trained only on sequences where all in-context answers are incorrect (followed by a correct target), so it has no signal for what to do when the current answer is already correct. At test time, when the revision chain produces a correct answer at step $k$, the model at step $k+1$ does not recognize that the answer needs no revision and may incorrectly change it.

The paper mitigates this with **majority voting or verifier-based selection across the entire chain** of revisions, picking the best answer from any point in the chain rather than always taking the last revision. However, this is an imperfect patch that introduces a new tradeoff: the verifier or voting mechanism must be able to distinguish correct from incorrect answers within the chain, and errors in this selection (verifier false positives or majority voting on wrong answers) can select a suboptimal answer. The 38% reversion rate means that roughly two out of five correct answers are subsequently corrupted, reducing the effective yield of the sequential revision approach and forcing reliance on post-hoc selection.

The paper does not measure how much the 38% reversion rate degrades the overall success rate of the revision chain compared to a hypothetical model that could recognize when revision is unnecessary. Nor does it explore the fundamental training fix — training the model on sequences that include correct answers with a "do nothing" or "verify" target action. The ReST$^{EM}$ experiment in Appendix K (Figure 16) shows that attempting to further optimize the revision model with RL degraded performance, suggesting the revision training procedure is fragile and the reversion problem is not trivially solvable through more training.

**Evidence in the paper:** Section 6.1 reports the 38% figure directly. Figure 6 (left) shows the revision model's per-step pass@1 trajectory, but does not decompose how much of the non-monotonicity is due to reversion events. Figure 6 (right) shows that sequential + verifier-based selection still outperforms parallel sampling, indicating the mitigation works partially but does not fully compensate.

**Mitigation status:** The within-chain selection mechanism (majority voting or verifier-based) mitigates the symptom but does not address the root cause — the model was never trained to handle already-correct answers. The paper does not propose a training fix, leaving this as an open problem for future work.

---

### All Experiments Use a Single Benchmark (MATH) and a Single Model Family (PaLM 2-S*)

Every experiment in the paper uses the **MATH benchmark** (500 test questions across five difficulty quintiles) with **PaLM 2-S*** as the base model. The authors state in Section 4 that they "believe this model is representative of the capabilities of many contemporary LLMs," but this claim is unverified and several aspects of the findings could be model- or benchmark-specific:

- **PRM behavior** depends on the base model's output distribution. A model with different calibration, different error patterns, or different step-level reasoning style might exhibit different over-optimization thresholds and different search-vs-best-of-N tradeoffs.

- **Revision model training** depends on the base model's in-context learning ability and its capacity to learn from incorrect examples. Different model families have substantially different in-context learning characteristics, and the 38% reversion rate may vary.

- **MATH is restricted to competition-level symbolic reasoning problems.** It is unclear whether the difficulty-dependent patterns — beam search hurting easy problems but helping medium ones, sequential revisions being optimal for easy problems, the specific optimal budgets — generalize to other reasoning domains (code generation, logical deduction, scientific QA) or to tasks requiring factual recall rather than inference.

The 500-question test set, split into five quintiles of ~100 each, then further split by two-fold cross-validation, means the compute-optimal policy is **selected based on roughly 50 questions per fold per bin** (Section 3.2). The paper does not report confidence intervals or variance estimates for the compute-optimal scaling curves (Figures 4 and 8), making it impossible to assess whether the observed strategy preferences — e.g., beam search on bin 3, best-of-N on bin 1 — are statistically robust or could flip with a different random split. With only 50 questions per fold, sampling variance could meaningfully affect which strategy appears optimal.

The comparison to prior work that reached contradictory conclusions (self-correction works in Madaan et al., 2023; fails in Huang et al., 2023) is one of the paper's key motivating claims. Without replication on additional benchmarks and model families, the paper's reconciliation of these findings — that difficulty explains the contradiction — remains specific to PaLM 2-S* on MATH.

**Evidence in the paper:** Section 4 describes the single-model, single-benchmark setup. The paper does not report any experiments on other benchmarks (beyond MATH) or with other base model families.

**Mitigation status:** The authors acknowledge the limitation implicitly by stating their belief that PaLM 2-S* is "representative" (Section 4), but they do not conduct replication experiments. This is a scope limitation rather than an oversight — the paper's contribution is the systematic analysis framework, and replicating it across multiple model families would be a substantial follow-up effort.

---

### The FLOPs-Matched Comparison Uses a Potentially Weak Pretraining Baseline (Parameter-Only Scaling)

The FLOPs-matched analysis in Section 7 compares PaLM 2-S* with compute-optimal test-time scaling against a model with approximately **14× more parameters**, holding training data fixed. This follows the LLaMA paradigm (Touvron et al., 2023) but departs from **compute-optimal pretraining** as established by Hoffmann et al. (2022), which recommends scaling both parameters and data equally. The authors explicitly acknowledge this choice:

> "We choose this setting as it is representative of a canonical approach to scaling pretraining compute and leave the analysis of compute-optimal scaling of pretraining compute where the data and parameters are both scaled equally to future work." (Section 7)

The consequence is that the pretraining baseline is **likely weaker than a properly compute-optimally trained larger model**. With fixed data, the 14× larger model is undertrained relative to the Chinchilla-optimal point — it has more parameters than it can effectively use on the available data. A Chinchilla-optimal model trained with 14× total FLOPs (scaling both parameters and data by roughly √14 ≈ 3.74× each) would likely outperform the parameter-only-scaled model, making the pretraining baseline stronger and potentially eliminating or reversing some of the test-time compute advantages reported in Figure 9 and the Figure 1 bar charts.

Additionally, the 14× larger model uses only **greedy decoding** in this comparison (Section 7), while the smaller model receives compute-optimal test-time scaling. This asymmetry is deliberate (the comparison asks whether test-time compute can substitute for pretraining), but it means the baseline is artificially weak: giving the larger model even a modest test-time compute budget (e.g., best-of-8 majority voting) would create a much stronger comparison point. The paper's findings about when test-time compute is preferable to pretraining should be understood as comparing an **optimized small model against an unoptimized large model**, not against the best possible large-model deployment.

**Evidence in the paper:** Section 7 describes the FLOPs matching methodology and acknowledges the parameter-only scaling choice. Figure 9 shows that on bin 5 (hardest problems), the 14× larger model outperforms test-time compute across all R values even under this weak baseline, suggesting the qualitative conclusion that test-time compute cannot substitute for pretraining on hard problems is robust even under a stronger baseline. However, the magnitude of test-time compute's advantage on bins 1–3 (e.g., +27.8% on medium questions at R ≪ 1) may be inflated.

**Mitigation status:** The authors explicitly flag this as a limitation and suggest future work on the compute-optimal pretraining comparison. The paper's main practical guidance — that test-time compute is most beneficial on easy-to-medium problems when R ≪ 1 — is qualitatively consistent with what a stronger baseline would show, even if the magnitudes would shift. The greedy decoding asymmetry remains unaddressed.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

This paper shifts the web agent research landscape in a specific and consequential way: it establishes that **structured distillation from a single frontier teacher is not just a workaround for API cost—it is a principled strategy that produces generalizable, locally deployable web agents competitive with (and sometimes exceeding) the closed-source models the field has relied on.** This reframes the narrative from "small models are a compromise" to "small models, properly trained, are a deployment target in their own right."

The shift operates at three levels.

**At the methodological level**, the AGENT-AS-ANNOTATORS framework provides the first common vocabulary for describing and comparing trajectory synthesis pipelines. Before this work, the field had five independently developed approaches (InSTA, NNetNav, Go-Browse, Explorer, AgentTrek) whose design differences were obscured by incompatible terminology. Table 2 is the key intellectual infrastructure: by mapping each pipeline onto the same six-module structure, it makes visible *which components each pipeline lacks* and *why those gaps might matter.* The mapping reveals, for example, that no prior pipeline generates evaluation hints, that only InSTA and Go-Browse use grounded task generation (where tasks are defined before execution), and that only NNetNav uses persona-driven diversity. These are not taxonomic curiosities—the paper's ablations demonstrate that hints contribute 2.4pp to student performance (Appendix C.5) and that persona-driven data achieves 91% of the full pipeline's performance with only 26% of the training data (Appendix C.4). The framework thus converts a collection of ad-hoc recipes into a design space where component-level choices can be tested independently.

This is not a paradigm shift in the Kuhnian sense—persona-driven generation, LLM judges, and teacher distillation all predate this work. But it is a **methodological reframing** that changes how the field will compare and build upon prior work. Future papers proposing new trajectory synthesis pipelines can (and should) be expected to locate themselves within the AGENT-AS-ANNOTATORS framework, specifying which modules they instantiate and how, rather than describing their pipeline in isolation. This standardization alone would accelerate progress by enabling controlled ablation across papers.

**At the empirical level**, the paper resolves a tension that has been implicit in the distillation literature: whether data quality or data quantity is the binding constraint. Prior work has observed anecdotally that quality matters (InSTA's 1.7B student outperforming its 235B teacher; LIMA's finding that 1,000 carefully curated examples suffice for instruction tuning), but the web agent setting introduces complexities—multi-step interactions, visual grounding, error recovery—that could plausibly require massive data volume to capture. The paper's results are definitive on this point for the web agent domain: **teacher quality, not data volume, is the primary bottleneck.** The Flash teacher produces 39% more training examples than the Pro teacher (22,707 vs. 16,353 observation-action pairs, Table 4) but produces a substantially weaker student (24.9% vs. 36.2% on Qwen3-VL-8B-Thinking, Figure 3). Adding unfiltered trajectories (40% more data) *decreases* student performance by 4.5pp (Table 12). The reduced-thinking teacher produces a student at 41.5% while the high-thinking teacher—same model, same tasks, similar data volume—produces a student at 24.4% (Figure 9b).

This finding redirects research investment. Before this paper, a natural response to the 20+ percentage point gap between small open-weight models and frontier models would be to scale up data collection—more websites, more tasks, more trajectories. The results suggest this is inefficient. The binding constraint is not how many trajectories the teacher generates, but how good the teacher is at the task and how carefully its reasoning is preserved in the training data. The implication for the field is that effort should shift from **scaling data volume to improving teacher quality and training signal fidelity**—better teacher models, better teacher configurations (thinking budgets), better judge accuracy (hints), and more faithful reasoning trace preservation.

**At the practical level**, the paper demonstrates that a 9B model can be deployed locally and match or exceed the web agent performance of models that are an order of magnitude larger and accessible only via API. The numbers are specific—41.5% on WebArena vs. GPT-4o's 31.5% and Claude 3.5 Sonnet's 36.0% (Table 10)—but the implication is general: **local deployment of capable web agents is feasible today**, not a future aspiration. The transfer results to entirely unseen platforms (WorkArena L1 +18.2pp, an enterprise interface with no training overlap) confirm that the distilled skills are not overfit to the training environments. This opens a deployment pathway that was previously speculative: organizations with sensitive internal web tools can train their own agents on self-hosted instances without ever routing data through external APIs.

The paper also makes a **counterintuitive efficiency claim** with immediate practical consequences for anyone building distillation pipelines: reducing the teacher's reasoning budget improves both teacher success rates (Table 4) and downstream student performance (Section 5.2). This means that capable distillation pipelines can be *cheaper* than naive approaches—not just in total data volume, but in per-trajectory generation cost, since reduced thinking uses fewer inference compute resources. The finding that this holds across all six environments suggests it is a robust phenomenon, not a fluke of specific task types.

**What this work makes less attractive.** The strong quality-over-quantity results reduce the appeal of internet-scale data collection for web agent distillation. InSTA's approach of generating tasks across 150K websites may be overkill if the bottleneck is teacher quality rather than task diversity. Similarly, the finding that six carefully chosen environments with persona-driven diversity transfer broadly (to four distinct evaluation settings) suggests that the "depth" strategy—thorough coverage of a small number of environments—may be more efficient than the "breadth" strategy of shallow coverage across many environments. The paper does not definitively establish this (there is no head-to-head comparison of depth vs. breadth at matched data scale), but the transfer results provide strong circumstantial evidence.

**What remains unresolved.** The persona module's contribution is the largest open question. The paper argues that persona-driven diversity is more efficient than scale-driven diversity (Section 6), but the controlled no-persona ablation is missing. If it turned out that persona-driven tasks are no better than neutral-prompt tasks at matched scale, the framework's distinctive contribution would narrow to hints + blind execution + judge filtering. Conversely, if personas proved essential, they would become a mandatory component for any distillation pipeline—a stronger claim than the paper currently makes. The paper also opens but does not resolve the question of whether the six-environment approach would work for domains beyond web interaction—the annotation-role framework is domain-agnostic, but the empirical results are specific to web environments.

### Follow-Up Research This Work Enables

**1. Measuring whether personas cause improved task diversity or merely redistribute it.**

The paper lacks a controlled no-persona ablation (acknowledged in Section 6). The critical follow-up experiment is: generate 3,000 tasks from a neutral prompt (no persona conditioning) using the same Task Generator, Teacher, and environments, train the same Qwen3.5-9B student, and compare WebArena and transfer benchmark performance. The specific hypothesis to test is that personas increase the *type diversity* of generated tasks (different workflows, different site affordances) rather than just surface-level variation (different entity names, different forum topics). A strong follow-up would also measure task diversity directly—perhaps by clustering task intents by required action sequences or by the subset of site functionality they exercise—to determine whether personas partition the task space along distinct axes or simply add noise around a single central tendency. If personas provide no measurable benefit, the AGENT-AS-ANNOTATORS framework simplifies to a three-component pipeline (grounded Task Generator + blind Agent + hinted Judge), which would be an important negative result clarifying what actually drives the gains.

**2. Head-to-head comparison of distillation pipelines training the same student at matched data scale.**

The framework's stated purpose is enabling systematic comparison, but the paper does not execute this comparison (acknowledged in Section 5.3). A natural follow-up would implement simplified versions of InSTA (scale-driven task generation with LLM judge, no personas, no hints), NNetNav (retroactive task labeling of exploration trajectories, no blind execution), and Go-Browse (graph-search-based task generation with separate solver models), train the same Qwen3.5-9B student on each pipeline's data at matched trajectory counts (e.g., 2,000 per pipeline), and evaluate on the full five-benchmark suite. This would disentangle the contributions of teacher quality (which the paper has established matters) from pipeline architecture (which the paper claims matters but has not isolated). A null result—all pipelines performing similarly at matched teacher quality—would simplify the design space considerably. A positive result—AGENT-AS-ANNOTATORS outperforming even at matched teacher—would validate the specific architectural choices (personas, hints, blind execution) as causally important rather than merely correlated with using a strong teacher.

**3. Training a difficulty estimator to make the compute-optimal framework practically deployable in the web agent setting.**

The paper does not address task difficulty explicitly, but the web agent domain has an analogous problem to the one in the MATH compute-optimal paper: not all tasks benefit equally from additional inference compute or more sophisticated strategies. A follow-up could define web agent task "difficulty" operationally (perhaps as the base model's pass@1 rate on similar tasks, or the number of interaction steps required, or the number of distinct sub-goals), train a lightweight predictor that estimates difficulty from the task intent alone (without executing the task), and use it to allocate test-time compute adaptively—e.g., simple greedy decoding for easy tasks, beam search over action sequences for medium tasks, and deferral to a larger model or human for hard tasks. This would extend the paper's distillation approach into a full deployment system that is efficient at both training time (via distillation) and inference time (via adaptive compute allocation). The paper's existing infrastructure—the Agent can be run with different budgets, the Judge can evaluate success—provides the evaluation framework; what is needed is a difficulty predictor trained on the base model's success patterns across the 3,000 A3-SYNTH tasks.

**4. Exploring whether distilled reasoning traces teach general problem-solving strategies or environment-specific action heuristics.**

The reasoning trace ablation shows that removing `<thought>` and `逐步` blocks costs 7.9pp—the single largest component contribution (Table 3). But *why* these traces help is unclear. Do they teach the student a general decomposition strategy (identify goal → locate relevant UI element → parameterize action → verify outcome) that transfers across environments? Or do they teach environment-specific heuristics (e.g., "on GitLab, look for the 'New Project' button in the sidebar") that happen to apply to the training environments? A follow-up could ablate the reasoning trace *content* without removing the structure: replace the teacher's actual strategic reasoning with generic placeholder reasoning of the same length and format (e.g., "I will now execute the next step to make progress toward the goal"), train the student, and measure both in-domain and transfer performance. If generic reasoning achieves comparable transfer but worse in-domain performance, the traces teach environment-specific heuristics. If generic reasoning achieves comparable in-domain performance but worse transfer, the traces teach general decomposition. If both drop, the structure itself (separating strategic and operational reasoning) provides value independent of content. The paper's existing 600-task ablation infrastructure makes this experiment straightforward to execute.

**5. Stress-testing the distillation approach on deliberately adversarial environments.**

The paper's evaluation environments—WebArena, VisualWebArena, WorkArena, MiniWoB—are all relatively clean, well-structured web applications with consistent layouts and predictable interactive elements. Real-world enterprise software is often far messier: dynamically generated element IDs, inconsistent form validation, modal dialogs that appear unpredictably, pages that load content asynchronously. A strong stress test would be to distill on A3-SYNTH data and evaluate on a deliberately perturbed version of WebArena where element IDs are randomized, page layouts are shuffled, or pop-ups are injected at random intervals. If the student's performance degrades gracefully (say, dropping from 41.5% to 30–35%), the distilled skills include genuine robustness. If performance collapses to near the base model's level, the distillation primarily teaches brittle environment-specific patterns that break under distribution shift. This would clarify a boundary condition that the current paper only gestures at—that generalization holds across "structurally similar" environments but may not extend to environments that violate the structural assumptions of the training data.

**6. Combining the distilled model with RL-based refinement on the target environment.**

The paper uses pure SFT and explicitly flags RL-based refinement (DigiRL, Agent Q, OpenWebVoyager) as orthogonal future work (Section 6). A natural follow-up would be to take the A3-Qwen3.5-9B checkpoint as initialization and apply online RL on the WorkArena environment—where the base-to-fine-tuned gain was largest (+18.2pp) but the absolute performance (51.5%) still trails frontier models (Gemini 3 Pro at 79.7%, Table 7). The hypothesis is that SFT provides strong initialization (basic web interaction primitives, reasoning structure) while RL provides environment-specific optimization (learning ServiceNow-specific navigation patterns, recovering from ServiceNow-specific error states). This is the distillation analog of the "SFT then RLHF" recipe that has proven effective for chat models, applied to the interactive agent setting. The paper's existing infrastructure—the Agent can be deployed for online interaction, the Judge (or WorkArena's programmatic evaluators) can provide reward signals—makes this a relatively low-overhead extension. The key measurement would be whether RL provides additive gains on top of SFT or merely recovers the same asymptotic performance more sample-efficiently.

### Practical Applications and Downstream Use Cases

**1. Enterprise automation with data sovereignty guarantees.**

The most direct application is deploying A3-style models within organizations that run sensitive internal tools and cannot use external APIs for compliance reasons. Consider a company using ServiceNow for IT asset management, Workday for HR workflows, and a custom React-based CRM for customer tracking—all internal tools with no public API access for frontier models. The WorkArena L1 result (51.5%, Table 7) demonstrates that a distilled 9B model can perform basic enterprise operations (creating records, filtering lists, ordering catalog items) on ServiceNow without ever having seen ServiceNow during training. The practical implication: an organization could self-host A3-SYNTH on its own web applications (using the open-source pipeline), generate training data on those specific tools, fine-tune a 9B model, and deploy it internally—all without data leaving the premises. The 33.3% → 51.5% jump on WorkArena L1 suggests that even a generic distillation (trained on WebArena, deployed on ServiceNow) provides meaningful capability; environment-specific fine-tuning on the target tools would likely yield further gains. The primary cost is the teacher model inference during data generation (using Gemini 3 Pro via API, or ideally a self-hosted teacher if frontier models raise the same compliance concerns), not the student training or deployment.

**2. On-device web agents for consumer applications.**

The 9B parameter count of the fine-tuned student means it can run on consumer hardware (a single GPU with 24GB VRAM, or potentially quantized to run on edge devices). This enables applications where API latency or connectivity is prohibitive: a browser-integrated assistant that fills out forms, compares products across e-commerce sites, or manages email and calendar—all running locally without sending browsing data to external servers. The MiniWoB result (69.0%, matching Claude 3.5 Sonnet at 69.8%, Table 10) demonstrates that the model has learned atomic web interaction skills (clicking, typing, selecting, basic form-filling) at a level competitive with frontier models. While MiniWoB is a simplified environment, the skills it tests—identifying the correct button to click, entering text in the right field, selecting the appropriate dropdown option—are the building blocks of real web interaction. A consumer application would need additional safety mechanisms (user confirmation for consequential actions, constraints on which websites the agent can interact with, rate limiting), but the core capability—a locally running web agent that handles routine tasks—is demonstrated.

**3. Cost-efficient data generation for self-improving web agent systems.**

The paper's finding that teacher quality dominates data quantity (Section 5.2) has direct implications for organizations building self-improving agent pipelines. The naive approach—use the strongest available teacher, generate as much data as possible, train on everything—is both expensive and suboptimal. The paper's specific recommendations: (1) use a reduced thinking budget for the teacher (cheaper and more effective, Table 4), (2) invest in judge accuracy (hints add 2.4pp at matched scale, Appendix C.5), and (3) preserve reasoning traces intact (removing them costs 7.9pp, Figure 9b). The 3,000 tasks generating 2,322 successful trajectories (77.4% yield) at a total cost of roughly 3,000 teacher agent executions + 3,000 judge evaluations provides a concrete budget baseline. A team building a web agent for a new domain could replicate this pipeline on their own environments, using the paper's released code, and expect to produce a capable student with comparable data volume. The diminishing returns curve (Figure 9a) provides guidance on when to stop scaling data and invest in other improvements (teacher quality, environment coverage, RL refinement): the last 892 trajectories contributed only 1.3pp, suggesting 1,500–2,000 high-quality trajectories is near the saturation point for the current pipeline design.

**4. Benchmarking infrastructure for web agent distillation research.**

The paper's use of BrowserGym and AgentLab for all evaluation (Appendix G.1) provides a standardized evaluation protocol that future distillation papers can adopt, enabling the apples-to-apples comparison that has been missing from the field. The specific configuration—GenericAgent harness, accessibility tree + screenshot observations, unified 65K token budget, standardized action space—is documented in sufficient detail for reproduction. The paper's release of the full A3-SYNTH dataset, pipeline code, and model checkpoint (Section 7, Reproducibility Statement) means that future work can start from a known baseline (A3-Qwen3.5-9B at 41.5% on WebArena) and measure incremental improvements, rather than each paper reporting results under incompatible evaluation conditions. This is an infrastructure contribution that reduces the barrier to entry for web agent distillation research and increases the reliability of cross-paper comparisons.
