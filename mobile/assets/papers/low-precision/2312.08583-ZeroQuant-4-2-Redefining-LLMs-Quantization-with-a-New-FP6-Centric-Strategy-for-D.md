# ZeroQuant(4+2): Redefining LLMs Quantization with a New FP6-Centric Strategy for Diverse Generative Tasks

**ArXiv:** [2312.08583](https://arxiv.org/abs/2312.08583)

## 🎯 Pitch

This paper studies how to improve weight-only quantization for LLMs on generative tasks by shifting from INT4 to FP6 precision, analyzing the limitations of INT4 across zero-shot evaluation, code generation, and abstractive summarization benchmarks using LLaMA (1B–65B), StarCoder-15B, CodeGeeX2-6B, and BART-406M models.

---

## 1. Executive Summary

This paper studies how to improve weight-only quantization for LLMs on generative tasks by shifting from INT4 to FP6 precision, analyzing the limitations of INT4 across zero-shot evaluation, code generation, and abstractive summarization benchmarks using LLaMA (1B–65B), StarCoder-15B, CodeGeeX2-6B, and BART-406M models. The work proposes a novel **4+2 design for FP6** (splitting a 6-bit floating-point number into two contiguous 4-bit and 2-bit sub-numbers to enable simultaneous loading and dequantization) combined with a **bias shift** technique (absorbing the exponent bias difference into a precomputed scaling factor to eliminate runtime exponent recalculation). This FP6 kernel achieves up to 2.37× speedup over cuBLAS and averages 1.06×–2.05× faster than fine-grained INT4 on feed-forward layers of LLaMA models, while FP6 quantization with simple RTN and coarse-grain quantization matches FP16 baseline accuracy on code generation and summarization — performance that INT4 cannot reach — establishing that FP6 can serve as a practical replacement for INT4 quantization only when coupled with specialized system-level GPU kernel support that addresses the challenges of odd-bit precision dequantization.

## 2. Context and Motivation

### The Core Problem: INT4 Quantization Fails on Generative Tasks, Especially for Smaller Models

The fundamental problem this paper tackles is that **existing 4-bit integer (INT4) quantization methods, while effective on zero-shot benchmarks, degrade unacceptably on the generative tasks that matter most in production**. This is a practical deployment crisis hiding behind deceptively clean zero-shot numbers. The paper observes that the quantization literature has systematically avoided evaluating on the tasks LLMs are actually built to perform — code generation, summarization, dialogue — creating an illusion of robustness that collapses in real-world settings.

The gap is concrete. Zero-shot perplexity and multiple-choice accuracy benchmarks (like those in Table 2 and Table 3) suggest INT4 quantization with GPTQ or RTN can approach FP16 performance, particularly for large models like LLaMA-65B. But when the same quantized models are tested on code generation (HumanEval-X for Python and JavaScript) or abstractive summarization (CNN/DailyMail, XSum), the picture changes dramatically. Table 4 shows CodeLLaMA-34B dropping from 45.05 to 43.45 pass@1 in JavaScript with INT4-CGQ, and CodeGeeX2-6B plummeting to 29.80 (FGQ) from 34.04 (FP16) in Python. For the 406M-parameter BART model on summarization, INT4-CGQ loses nearly 2 ROUGE-1 points on XSum (45.49 → 43.76). These are not minor regressions — they represent a qualitatively different failure mode invisible to the standard evaluation pipeline.

The paper's central claim is that **this gap is not an implementation detail but a fundamental limitation of INT4 precision for generative workloads**. The instability manifests in two ways: (1) INT4 performance is inconsistent across tasks and models (sometimes FGQ helps, sometimes it hurts, as seen in CodeGeeX2-6B where FGQ scoring 29.80 underperforms CGQ at 33.08), and (2) smaller models suffer disproportionately, with gaps that cannot be closed by better quantization algorithms or finer granularity. The paper frames this as a barrier to deploying quantized LLMs "in production environments, where replicating the original model's performance across different tasks is critical" (Section 1).

### Why This Matters: The Practical Deployment Bottleneck

The significance of this problem extends beyond academic benchmarking because LLM deployment is overwhelmingly constrained by **memory bandwidth, not compute throughput**. The paper explicitly notes this in Section 2: "the distinctive bandwidth constraints of LLMs have popularized weight-only quantization methods as a strategy to reduce the memory footprint." Reducing the memory footprint of weights from FP16 to INT4 (4 bits per weight) theoretically halves the data movement during autoregressive decoding, which is the dominant bottleneck. But if that 2× memory reduction comes with 2-5 point accuracy losses on the tasks users actually care about, the trade-off is unacceptable for many production scenarios.

The practical stakes are amplified by the observation that **the problems are worst for smaller models**. A 406M-parameter summarization model or a 6B code generation model is precisely the kind of model you would deploy in cost-sensitive or latency-sensitive settings where quantization provides the most value. If quantization fails most severely on these models, it undermines the economic case for deploying them quantized at all. Meanwhile, the very large models (65B+) that handle INT4 gracefully are already so memory-hungry that even 4-bit quantization may not make them deployable on a single GPU.

There's also a methodological significance. The paper argues that the field's near-exclusive focus on **zero-shot perplexity and accuracy** has created a collective blind spot. Prior work evaluating quantization quality (GPTQ, QuIP, AWQ, SqueezeLLM, QUIK) predominantly reports Wikitext, PTB, and C4 perplexity, plus a handful of multiple-choice tasks like ARC, BoolQ, and PIQA. These metrics are convenient and reproducible, but they measure something fundamentally different from what users experience when interacting with a deployed model. Zero-shot accuracy on multiple-choice tasks does not require the model to produce coherent multi-step reasoning, maintain consistency over long sequences, or avoid degenerate repetition — all failure modes that quantization can introduce and that only generative evaluation can surface. The paper's decision to include code generation (with 8+ repeated experiments and standard deviations reported) and summarization (with ROUGE-1/2/L) represents a deliberate methodological correction, not just an expanded evaluation suite.

### Where Existing Approaches Fall Short

The paper identifies four specific failure modes in the prior quantization landscape:

**1. GPTQ overfits to calibration data.** Table 1 provides the starkest evidence: calibrating GPTQ on C4 produces C4 perplexity of 9.34 on LLaMA-1B (FGQ), but PTB perplexity skyrockets to 1399.89 — worse than random guessing. When the calibration dataset is swapped to PTB, the pattern reverses (49.80 on PTB, 9.84 on C4). The paper notes this is "less severe for larger models" (moving from 1B to 13B to 65B, the gap narrows), but the fundamental issue remains: GPTQ's second-order Hessian-based optimization produces weight adjustments that are tuned to the statistics of the calibration data, and when the test distribution differs, the quantized model can catastrophically underperform. This is particularly problematic for generative tasks where the input distribution (code, documents to summarize) may differ substantially from the text corpora used for calibration.

**2. INT4 performance is fundamentally inconsistent.** Table 4 demonstrates three distinct failure patterns within the same quantization format:
- Fine-grained quantization (FGQ) sometimes hurts rather than helps: CodeGeeX2-6B Python pass@1 drops from 33.08 (CGQ) to 29.80 (FGQ), meaning the finer granularity that is supposed to reduce quantization error actually worsens performance.
- Model size and task interact unpredictably: CodeLLaMA-34B benefits from FGQ in Python (improving from 39.84 to 46.88, actually exceeding FP16 at 43.22) but FGQ doesn't help in JavaScript (43.22 vs. 43.45 for CGQ).
- The gap between INT4 and FP16 persists even when INT4 works reasonably well: StarCoder-15B Python goes from 35.43 (FP16) to 33.20 (INT4-CGQ), a persistent gap that fine-grain quantization cannot close.

This inconsistency means that a practitioner cannot confidently deploy INT4 quantization without task-specific validation — there is no guarantee that acceptable zero-shot perplexity implies acceptable generative performance.

**3. Prior work focuses on the wrong evaluation regime.** The paper explicitly calls out this limitation in Section 2: "given that the main real-world applications of LLMs, such as ChatGPT and Codex, revolve around generation-based tasks, a more comprehensive evaluation framework for quantized LLMs is warranted." The paper's contribution here is not just critique but a concrete demonstration that the gap between zero-shot metrics and generative metrics is large enough to invalidate deployment decisions made on zero-shot evidence alone. The zero-shot accuracy numbers in Table 3 show INT4-RTN for LLaMA-65B actually exceeding FP16 (71.16 vs. 71.13 mean accuracy) — a result that would suggest INT4 is perfectly safe. But the code generation and summarization results show persistent losses that zero-shot evaluation completely misses.

**4. Existing odd-bit precision approaches have prohibitive system costs.** The paper acknowledges prior interest in non-standard bit widths (GPTQ's 3-bit experiments, various FP8/FP4 formats from ZeroQuant-FP and LLM-FP4) but identifies a critical system-level barrier: "number concatenation methods, as discussed in Section 5, limit their system performance" (Section 2). The standard approach to implementing odd-bit formats — packing multiple values into 32-bit integers and extracting them with bitwise operations during dequantization — adds latency that can negate the memory savings. This has created a chicken-and-egg problem: odd-bit formats like FP6 are rarely explored because they're perceived as impractical to accelerate, and they remain impractical because no one has invested in specialized kernel development. The paper positions itself as breaking this deadlock.

### How This Paper Positions Itself

The paper positions FP6 as a **"sweet spot" solution** (Section 4 title) that occupies a middle ground left unexplored by prior work. Its positioning strategy operates on two levels:

**Algorithmic positioning (Section 4):** The paper frames FP6 as bridging two extremes. On one side is INT4, which provides maximum compression but with accuracy degradation that is unacceptable for generation, inconsistent across models and tasks, and resistant to algorithmic fixes (GPTQ overfitting, FGQ instability). On the other side is FP16/FP8, which preserves accuracy but provides insufficient memory reduction for bandwidth-constrained deployment. The paper's empirical claim is that FP6 with the simplest possible quantization algorithm (RTN) and the coarsest granularity (CGQ, one scaling factor per row) achieves accuracy indistinguishable from FP16 on code generation and summarization — exactly the generative tasks where INT4 fails. Table 5 shows FP6-CGQ achieving 35.64 Python pass@1 on StarCoder-15B (vs. 35.43 for FP16) and 44.31 on CodeLLaMA-34B (vs. 43.22), while INT4-CGQ drops to 33.20 and 39.84 respectively.

Critically, the paper shows that FP6 is **robust to quantization algorithm choice** — RTN and GPTQ produce similar results, particularly for larger models (Table 6, LLaMA-65B: FP6-GPTQ-CGQ and FP6-RTN-CGQ both achieve 6.42 perplexity on Wikitext2, essentially matching FP16 at 6.41). This robustness contrasts sharply with INT4, where algorithm choice matters enormously (INT4-GPTQ vs. INT4-RTN can differ by hundreds of perplexity points on LLaMA-1B). The implication is that FP6 doesn't require the complexity of second-order optimization methods; simple round-to-nearest suffices.

The paper also explicitly contrasts FP6 with FP5 to establish that 6 bits is the threshold: "FP5 with CGQ shows an improvement over INT4 quantization but still does not reach the high performance levels of FP16" (Section 4.1). FP5-CGQ CodeGeeX2-6B Python pass@1 is 30.56 (vs. 34.04 FP16), and the gap persists across models. Six bits is not an arbitrary choice — it is empirically the minimum precision that retains FP16-competitive generative performance.

**System positioning (Section 5):** The paper frames its kernel contributions not as a standalone acceleration result but as the **enabling technology that makes FP6 a viable alternative to INT4**. The authors are explicit that "shifting to higher precision formats like FP6 has been particularly challenging, thus overlooked, due to poor performance caused by the lack of sophisticated integration and system acceleration strategies on current AI hardware" (Abstract). The 4+2 data layout and bias shift are presented as the specific innovations that break this deadlock.

The system evaluation in Figure 2 is positioned against two baselines: cuBLAS (representing unquantized FP16 performance, which any quantization scheme must beat to be worthwhile) and TensorRT-LLM's fine-grained INT4 (the state-of-the-art INT4 kernel, representing the incumbent 4-bit approach). The claim is that FP6 with bias shift achieves 1.92× average speedup over cuBLAS and 1.06×–2.05× over INT4-FGQ. This is significant because it means FP6 provides **both better accuracy than INT4 and better or comparable latency** — eliminating the trade-off that previously forced practitioners to choose between quality and speed.

The paper draws a connection to prior floating-point quantization work (ZeroQuant-FP, LLM-FP4, FP8 formats from Micikevicius et al.) but positions itself as solving the deployment gap those works left open. Prior work demonstrated that floating-point formats can outperform integer formats at the same bit width, but did not address the system-level challenges of odd-bit precision. The paper's contribution is making that theoretical advantage concrete on GPU hardware.

**An important negative result the paper does not dwell on but that affects positioning:** Table A.1 shows GPT-4 evaluation scores for vicuna-7b/13b at different precisions, and "there is no clear link between bit precision and performance" — FP6 doesn't consistently outperform INT4 in dialogue quality, and in some categories (Math for vicuna-7b: 3.6 → 2.6 → 2.2 as precision increases), the relationship is non-monotonic. This suggests the FP6 advantage is task-dependent — strongest for structured generation (code, text with clear correctness criteria) and weaker for open-ended dialogue — though the paper does not analyze this boundary in detail.

## 3. Technical Approach

### 3.1 Reader Orientation

This paper is primarily an **empirical analysis and system-design paper** whose core idea is twofold: (1) that FP6 quantization with the simplest possible algorithm (round-to-nearest, coarse granularity) matches FP16 accuracy on generative tasks where INT4 fails, and (2) that a novel "4+2" data layout combined with exponent bias shift makes FP6 inference latency competitive with or better than state-of-the-art INT4 kernels, enabling FP6 to serve as a drop-in replacement for INT4 in production deployments.

The system being built is a **GPU kernel for weight-only FP6 quantization of LLMs during autoregressive decoding**. It solves the problem that 6-bit precision is not a power-of-2 format, which means conventional memory layouts and dequantization procedures are either memory-inefficient (pad to 8 bits, losing the 25% memory savings) or computationally expensive (pack multiple 6-bit values into 32-bit words and extract via bitwise operations). The "shape" of the solution is to split each FP6 weight into two contiguous sub-numbers — a 4-bit segment and a 2-bit segment — that can be loaded together and dequantized simultaneously, combined with a precomputed bias shift that eliminates runtime exponent arithmetic during conversion to FP16.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has six major components that operate in two phases: an offline quantization phase and an online inference phase.

**Offline phase (done once per model):**

1. **FP6 Quantizer** — takes the original FP16 weight matrix and produces (a) a matrix of FP6 weight values using round-to-nearest with per-row or per-block scaling, and (b) a scaling factor matrix. For the bias-shift variant, the scaling factors absorb an additional factor of `$2^{12}$` to eliminate later runtime work.

2. **4+2 Layout Packer** — rearranges each FP6 weight into two contiguous sub-numbers stored in separate memory arrays: a 4-bit array (holding the sign and 3-bit exponent) and a 2-bit array (holding the 2-bit mantissa). Both arrays use standard power-of-2 bit widths so they can be loaded with standard GPU instructions.

**Online inference phase (per token, per layer):**

3. **Weight Loader** — simultaneously loads the 4-bit and 2-bit arrays from GPU DRAM into registers, reconstructing the full FP6 bit pattern on the fly without expensive bit-manipulation instruction sequences.

4. **FP6-to-FP16 Dequantizer (with Bias Shift)** — converts the reconstructed FP6 value into FP16 by padding zeros into the exponent and mantissa fields, then multiplies by the precomputed scaling factor (which already contains the `$2^{12}$` bias correction). No runtime exponent arithmetic is required.

5. **Matrix Multiplication Engine** — performs the standard FP16 matrix multiply-accumulate between the dequantized weight matrix and the FP16 activation vector, using GPU tensor cores.

6. **Accumulator (with deferred scale)** — completes the dequantization by multiplying the accumulated result by any remaining scaling factors that were deferred past the matrix multiply (for coarse-grained or fine-grained quantization schemes).

Information flows as follows: the pretrained FP16 model weights enter the FP6 Quantizer → each weight is converted to FP6 format with a scaling factor → the 4+2 Layout Packer splits each FP6 value into two arrays → at inference time, the Weight Loader reads both arrays simultaneously → the Dequantizer converts to FP16 with zero-overhead bias shift → the Matrix Multiplication Engine computes partial results → the Accumulator applies the scaling factor to produce the final FP16 output.

### 3.3 Roadmap for the Deep Dive

- **First**, the FP6 floating-point format specification (E3M2) and the quantization mapping from FP16, because the exact bit allocation determines both the representable range and precision, which in turn explains why FP6 outperforms INT4 on generative tasks.
- **Second**, the quantization algorithms (RTN and GPTQ) and granularity schemes (CGQ and FGQ), since the paper's central empirical claim is that FP6 works with the simplest algorithm at the coarsest granularity, unlike INT4.
- **Third**, the integer quantization baseline (Equation 1) and why INT4's uniform grid creates problems for weight distributions with outliers — this is the negative motivation for FP6.
- **Fourth**, the FP6 dequantization math (Equations 2, 3, 4, 5) and the bias shift technique, which is the core system innovation that makes FP6 inference fast despite its non-power-of-2 bit width.
- **Fifth**, the 4+2 data layout and how it enables simultaneous loading of non-standard bit widths using standard GPU memory instructions.
- **Sixth**, the system evaluation setup — kernel-level benchmarks on A100, matrix shapes for LLaMA feed-forward layers, comparison against cuBLAS and TensorRT-LLM INT4 kernels — to understand exactly what "1.92× faster than cuBLAS" means operationally.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is an **empirical analysis and system-design paper** whose core idea is that increasing weight precision from 4 to 6 bits — but critically, switching from integer to floating-point format — is sufficient to recover FP16-competitive accuracy on generative tasks, and that a custom data layout plus a bias-shift trick can make that 6-bit precision competitive with or faster than state-of-the-art 4-bit integer quantization on GPU hardware.

#### FP6 Floating-Point Format Specification (E3M2)

The paper uses a specific FP6 format denoted **FP6E3M2**: 1 sign bit, 3 exponent bits, and 2 mantissa bits, for a total of 6 bits. The format is described in Section 4 and follows the standard IEEE-like floating-point decomposition of Equation 2:

$$x = S \times 2^{E - b} \times M$$

where `$S \in \{-1, +1\}$` is the sign (1 bit), `$E \in [0, 2^e - 1]$` is the raw exponent value stored in `$e = 3$` bits (so `$E \in [0, 7]$`), `$b = 2^{e-1} - 1 = 3$` is the exponent bias (the fixed offset that allows the exponent to represent both positive and negative magnitudes), and `$M \in [0, 2)$` is the mantissa (2 bits representing values 0, 0.5, 1.0, 1.5 plus the implicit leading 1 for normalized numbers, or 0/0.5/1.0/1.5 with leading 0 for subnormals).

**What this encoding physically represents:** The sign bit determines whether the weight value is positive or negative. The 3-bit exponent field, after subtracting the bias of 3, gives a power-of-2 scale factor in the range `$2^{-3}$` to `$2^{4}$` (corresponding to `$E = 0$` through `$E = 7$`, though `$E=0$` is reserved for subnormal numbers and zero). The 2-bit mantissa provides four possible fractional values (0, 0.5, 1.0, 1.5 for normalized numbers) that multiply the power-of-2 scale. The maximum representable positive value, as stated in Section 4, is `$\pm 28$` calculated as `$\pm 1 \times 2^4 \times 1.75$`.

**Why E3M2 specifically:** The bit allocation is a deliberate trade-off between range and precision. With 3 exponent bits, the format covers roughly four orders of magnitude (from approximately `$2^{-3} \approx 0.125$` to `$2^4 = 16$`, times mantissa up to 1.75, yielding maximum ~28). This range is sufficient for LLM weight matrices whose values typically fall within ±10 after normalization. With 2 mantissa bits, each power-of-2 interval is divided into 4 levels, giving relative precision of approximately 25% within each octave. This is substantially coarser than FP16 (10 mantissa bits, ~0.1% precision) but the paper's empirical claim is that it is precisely the extra bit of mantissa compared to FP5's E3M1 (only 1 mantissa bit, dividing each octave into 2 levels) that makes the difference for generative tasks. The paper also mentions "similar setting is defined for FP5E3M1" — FP5 uses 3 exponent bits and only 1 mantissa bit (sign + 3 exponent + 1 mantissa = 5 bits total), providing only two fractional values per octave (0 and 1.0).

The paper explicitly excludes special values: "Note that for some other work such as [44] has specific configuration defined for exceptional values like NaN and ±∞. However, these are not included in our weight quantization process using FP6E3M2. We do not think this slight difference will greatly impact the model performance." This means the format uses standard finite-number encoding without reserving bit patterns for infinity or NaN — every encoding maps to a real number, which is reasonable for static weight data where NaN is not meaningful.

#### FP6 Quantization Mapping (RTN)

The quantization mapping from FP16 to FP6 is defined in Section 4 via Equation 3:

$$\hat{W}_{\text{fp16}} \approx \text{Quant}(W_{\text{fp16}}) = S_{\text{fp16}} \times W_{\text{fp6}}$$

where `$W_{\text{fp16}}$` is the original FP16 weight matrix (the full-precision weights the model was trained with), `$\text{Quant}(\cdot)$` is the quantization function (in this paper's case, round-to-nearest, the simplest possible mapping), `$S_{\text{fp16}}$` is a per-row or per-block FP16 scaling factor, and `$W_{\text{fp6}}$` is the resulting FP6 weight matrix whose values are integers when interpreted as the FP6 bit pattern.

**What this computes:** Each original FP16 weight is divided by a scaling factor, rounded to the nearest value representable in FP6E3M2 format, and stored as a 6-bit value. At inference time, the stored 6-bit value is multiplied by the same scaling factor to approximately recover the original weight. The scaling factor `$S_{\text{fp16}}$` is computed as:

$$S_{\text{fp16}} = \frac{\max(|\text{abs}(W_{\text{fp16}})|)}{28}$$

where `$\max(|\text{abs}(W_{\text{fp16}})|)$` is the maximum absolute value in the row (for CGQ) or block (for FGQ) being quantized, and 28 is the maximum representable value in FP6E3M2.

**Why this scaling factor computation specifically:** The paper targets "optimal use of Wfp16's range without compromising on precision" (Section 4). Dividing by the maximum absolute value divided by 28 ensures that the full dynamic range of FP6 (±28) is utilized — the largest weight value in the group maps exactly to ±28 after scaling, and all smaller values map to proportionally smaller FP6 values. This is a **saturation quantization** scheme (as opposed to a scheme that clips outliers and optimizes mean squared error), and it is the simplest possible approach. The fact that FP6 works with this naive scaling computation is one of the paper's key claims: unlike INT4, which requires sophisticated algorithms (GPTQ, AWQ) and fine granularity to handle outlier sensitivity, FP6 tolerates coarse-grain, RTN quantization.

**The quantization granularity choices (CGQ vs. FGQ):** The paper defines these in Section 3:
- **Coarse-grain quantization (CGQ):** One scaling factor per row of the weight matrix. For LLaMA models where hidden dimensions exceed 1024, this means one `$S_{\text{fp16}}$` per `$d \ge 1024$` weights. Each weight in that row uses the same scaling factor.
- **Fine-grain quantization (FGQ):** The weight matrix is divided into blocks of `$d$` consecutive elements, each with its own scaling factor. The paper uses block sizes of 128 (for LLaMA-1B) or 256 (for LLaMA-13B/65B), so there are `$n/d$` scaling factors per row.

The paper's key empirical finding (Table 5, Table 6) is that **FP6-CGQ achieves essentially identical accuracy to FP6-FGQ** — there is "little difference between CGQ and FGQ" for FP6. This is in stark contrast to INT4, where FGQ provides substantial improvements over CGQ (e.g., CodeGeeX2-6B Python: INT4-CGQ 33.08 vs. INT4-FGQ 29.80, going the wrong direction; CodeLLaMA-34B Python: INT4-CGQ 39.84 vs. INT4-FGQ 46.88, large improvement). The fact that FP6 doesn't need fine granularity is a major system advantage because CGQ reduces the memory overhead of storing scaling factors (one FP16 value per row versus one per 128–256 elements) and simplifies the dequantization arithmetic.

#### Integer Quantization Baseline: Why INT4 Fails

To understand why FP6 is needed, we must understand how INT4 quantization works and why it struggles with generative tasks. The integer quantization formula is Equation 1 in Section 3:

$$x_q = S \left\lceil \text{clamp}\left(\frac{x - x_{\text{zero}}\mathbf{1}}{S}; 0, 2^{b-1} - 1\right) \right\rfloor + x_{\text{zero}}\mathbf{1}$$

where `$x \in \mathbb{R}^d$` is the full-precision vector to be quantized, `$x_q \in \mathbb{R}^d$` is the quantized output, `$S \in \mathbb{R}$` is the scaling factor (computed as the range of values divided by the number of quantization levels), `$x_{\text{zero}}$` is a zero-point offset (set to `$\min(x)$` for **asymmetric quantization**, which the paper notes "has been widely adopted and proved to be much better than that by setting `$x_{\text{zero}} = 0$`"), `$b = 4$` is the bit width (yielding `$2^{4-1} - 1 = 7$` as the maximum integer for signed INT4, though the formula uses unsigned representation with zero-point shift), `$\lceil \cdot \rfloor$` is the rounding operator, and `$\text{clamp}(\cdot; 0, 2^{b-1}-1)$` restricts values to the representable range.

**What this physically computes:** Each full-precision value is shifted by the zero point (so the minimum value maps to 0), divided by the scaling factor, clamped to the integer range `$[0, 15]$` (for 4-bit unsigned, representing `$[-8, 7]$` signed values after subtracting the zero point on dequantization), rounded to the nearest integer, then shifted back. The result is that each group of `$d$` original values is mapped to one of 16 possible integer levels, uniformly spaced across the range `$[\min(x), \max(x)]$`.

**Why this form matters for the failure analysis:** The uniform quantization grid is the root cause of INT4's problems. In a uniform grid, every value within the range `$[\min(x), \max(x)]$` receives the same absolute precision — the quantization error is at most `$S/2$` regardless of whether the value is near zero (where relative error can be large) or near the extremes. LLM weight matrices, as noted in prior work (ZeroQuant-V2, AWQ), contain **outlier channels** — individual rows or columns where a few weights are 5–10× larger than the typical magnitude. To avoid clipping these outliers, the scaling factor `$S$` must be set large enough to cover them, which means the majority of weights (which are small) get quantized with very coarse resolution relative to their magnitude. This manifests as large relative errors on the most common weight values, which disproportionately affects the model's ability to represent frequent token patterns — exactly the kind of failure that degrades generative coherence.

FP6's floating-point format addresses this fundamentally differently: instead of uniform spacing, it allocates precision logarithmically. The dynamic range is covered by 8 octaves (`$2^{-3}$` through `$2^4$`), and within each octave the 2-bit mantissa provides 4 equally spaced levels. This means small-magnitude weights (common case) receive fine absolute precision (because the octave spacing is small at low exponents), while large-magnitude outlier weights receive coarser absolute precision but comparable relative precision. The paper does not mathematically analyze this advantage, but the empirical results in Table 5 and Table 6 confirm that FP6's non-uniform quantization grid is substantially more robust to outlier channels than INT4's uniform grid.

#### GPTQ Algorithm and Its Overfitting Behavior

The paper uses GPTQ as a comparison point for INT4 quantization, and the results reveal systematic overfitting that motivates the switch to FP6. GPTQ (Generative Pre-trained Transformer Quantization) is described in Section 3 as "a more advanced method of leveraging the activation information, which requires the inverse of the second-order input information." In more operational terms:

GPTQ processes a transformer model layer by layer. For each linear layer (weight matrix `$W$`), it:
1. Collects a batch of input activations by running calibration data through the model up to that layer.
2. Constructs the inverse Hessian matrix `$H^{-1}$` of the loss with respect to the weights, approximated as the outer product of the input activations: `$H \approx 2XX^\top$` where `$X$` is the matrix of input activation vectors.
3. Quantizes weights one column at a time, and after quantizing each column, **compensates the remaining unquantized weights** by the error introduced in that column, using the inverse Hessian to optimally distribute the error. This is the key difference from RTN: RTN rounds each weight independently and ignores the resulting error; GPTQ uses a closed-form update (derived from the Optimal Brain Surgeon framework, Hassibi and Stork, 1993) to adjust remaining weights so that the overall layer output is minimally perturbed.

**Why GPTQ overfits (Table 1 evidence):** The calibration step uses a specific dataset — the paper tests PTB and C4. The inverse Hessian `$H^{-1}$` is computed from the **statistics of that specific dataset's activations**. When the quantized model is then evaluated on a different dataset (say, trained with C4 calibration but tested on PTB), the Hessian-based error compensation is **mismatched to the test distribution**. The weight adjustments that optimally preserve layer output for C4-like inputs may amplify errors for PTB-like inputs.

The paper's Table 1 makes this concrete. For LLaMA-1B with INT4-GPTQ calibrated on C4 (FGQ): C4 perplexity is 9.34 (close to FP16 at 8.91), but PTB perplexity explodes to **1399.89** — nearly 40× worse than FP16's 37.39. When calibrated on PTB instead: PTB perplexity is 49.80 (much better than 1399.89 but still degraded from 37.39), while C4 perplexity is 9.84 (slightly worse than with C4 calibration). The pattern is symmetric: calibration helps on the calibration distribution and can catastrophically hurt on out-of-distribution data.

The paper notes this is "less severe for larger models" — for LLaMA-65B, the worst-case deviation between calibration datasets narrows to roughly 0.3 perplexity points. But the principle matters for deployment: you cannot guarantee what distribution of inputs your model will receive, and GPTQ's dataset sensitivity means the quantized model's performance bounds are unknown at deployment time.

**The paper's response to this overfitting problem:** By switching to FP6 with RTN, the overfitting problem is eliminated entirely. RTN has no calibration dataset, no Hessian computation, and no error compensation — it rounds each weight independently based only on the weight value itself. The trade-off is that each individual rounding decision may introduce more local error than GPTQ's compensated approach, but the collective error across the layer is **data-independent and predictable**. Table 6 shows that for FP6, RTN and GPTQ produce nearly identical results (LLaMA-65B Wikitext2: FP6-RTN-CGQ 6.42, FP6-GPTQ-CGQ 6.42), meaning GPTQ's sophisticated compensation provides essentially zero benefit for FP6 — further evidence that FP6's representational capacity is sufficient that rounding errors are already below the threshold where compensation matters.

#### FP6-to-FP16 Dequantization and the Bias Shift Innovation

This is the core system-level contribution. At inference time, the GPU must convert stored FP6 weights back to FP16 before they can be used in matrix multiplications with FP16 activations. The dequantization math, building on Equation 3, is that each recovered FP16 weight `$\hat{W}_{\text{fp16}}$` equals the scaling factor times the FP6 value:

$$\hat{W}_{\text{fp16}} = S_{\text{fp16}} \times W_{\text{fp6}}$$

But `$W_{\text{fp6}}$` is stored as a 6-bit pattern, not a 16-bit float, so the GPU must first convert the bit pattern to FP16, then multiply by `$S_{\text{fp16}}$`. The naive way to do this conversion, as described in Section 5.2, would be:

**Step 1:** Reinterpret the 6-bit FP6 pattern as an FP16 value. This requires:
- Extract the sign bit and copy to FP16 sign position.
- Extract the 3-bit exponent, add 12 (because the bias difference between FP6 bias=3 and FP16 bias=15 is `$15 - 3 = 12$`), and place in the 5-bit FP16 exponent field.
- Extract the 2-bit mantissa, pad with trailing zeros to fill the 10-bit FP16 mantissa field.

**Step 2:** Multiply the resulting FP16 value by `$S_{\text{fp16}}$`.

The costly part is the **exponent arithmetic**: extracting the 3-bit exponent field from the packed FP6 representation, performing an integer addition of 12, and inserting the result into the FP16 bit pattern. This is not a single GPU instruction — it requires bit masking, shifting, and integer arithmetic, all of which add latency to the weight-loading critical path.

**The bias shift innovation** (Section 5.2, Equation 5) eliminates Step 1's exponent arithmetic entirely:

$$S_{\text{fp16}} \times 2^{E-3} \times M = (S_{\text{fp16}} \times 2^{12}) \times 2^{E-15} \times M$$

where `$S_{\text{fp16}}$` is the original per-row scaling factor, `$E$` is the raw 3-bit exponent from FP6, 3 is the FP6 bias, 15 is the FP16 bias, `$M$` is the mantissa, and `$S_{\text{fp16}} \times 2^{12}$` is a **new precomputed scaling factor** that absorbs the bias difference.

**What this equation means operationally:** Instead of adding 12 to the exponent during dequantization (Step 1), we move the multiplication by `$2^{12}$` to the scaling factor (Step 2), which happens **after** the FP16 value is already constructed. This means:
- The FP6-to-FP16 conversion in Step 1 can simply **pad zeros** into the exponent and mantissa fields — no addition required. The raw FP6 exponent `$E$` is placed into the FP16 exponent field as-is (implicitly treating it as having bias 15 rather than bias 3, which by itself would give the wrong magnitude by a factor of `$2^{-12}$`), and the mantissa is zero-padded.
- The correction factor of `$2^{12}$` is **multiplied into the scaling factor offline**, after quantization is complete and before inference begins. Since `$S_{\text{fp16}} < 1$` (it's the ratio of max weight to 28), `$S_{\text{fp16}} \times 2^{12}$` is still well within FP16's representable range (`$< 4096$`), so this multiplication introduces no precision loss.

**Why this is correct:** The equality holds because exponent addition in floating point is multiplicative:
- `$2^{E-3} = 2^{E-15} \times 2^{12}$`
- Therefore `$S \times 2^{E-3} \times M = S \times 2^{12} \times 2^{E-15} \times M = (S \times 2^{12}) \times 2^{E-15} \times M$`

The physical consequence, illustrated in Figure 1 (comparing the "Traditional Method" left panel to the "Proposed Method" right panel), is:
- **Before bias shift:** Step 1 extracts `$E_{\text{fp6}}$`, computes `$E_{\text{fp16}} = E_{\text{fp6}} + 12$`, inserts into FP16 bit pattern; Step 2 multiplies by `$S_{\text{fp16}}$`. This requires integer addition and bit manipulation on every weight during inference.
- **After bias shift:** Step 1 simply pads `$E_{\text{fp6}}$` directly into the FP16 exponent field and pads the mantissa with zeros (pure bit concatenation, no arithmetic); Step 2 multiplies by `$S_{\text{fp16}} \times 2^{12}$` (the precomputed adjusted scale). The addition of 12 has been **hoisted out of the per-weight loop** and into the per-row preprocessing.

**Why this matters for latency (Figure 1 and Figure 2):** The GPU kernel's inner loop — loading each weight, dequantizing to FP16, and feeding it to the matrix multiply unit — is bandwidth-limited. Eliminating even a single integer addition from this inner loop is significant when that loop executes millions of times per inference step. Figure 2 quantifies the impact: the FP6 kernel with bias shift is "on average 1.36× faster compared to the same FP6 kernel without Bias Shift." This means the naive FP6 dequantization overhead (without bias shift) consumed approximately 26% of the kernel's execution time, and the bias shift recovers essentially all of that overhead.

**Handling subnormal numbers:** The paper notes an additional complexity: "Subnormal numbers in floating-point formats are very small values, including zero, characterized by an exponent field of all zeros. When de-quantizing subnormal FP6 numbers, the new exponent should remain at zero, not adding 12, to maintain its subnormal status." In the bias-shift approach, subnormals are handled correctly automatically: if the FP6 exponent is all zeros, padding zeros directly into the FP16 exponent field produces an FP16 subnormal (exponent all zeros in FP16 as well), which is correct because subnormals use the same bias-1 convention across both formats. No special-case branch is needed in the dequantization loop.

#### The 4+2 Data Layout for FP6

The bias shift solves the dequantization arithmetic cost, but there remains the problem of **how to physically store 6-bit values in GPU memory and load them efficiently**. GPUs are designed around power-of-2 data widths: 8-bit bytes, 16-bit half-words, 32-bit words. There is no native 6-bit load instruction. The paper describes two standard approaches to this problem in Section 5.1 and explains why both are unsatisfactory:

1. **Pad to 8 bits:** Store each FP6 value in an 8-bit byte with 2 bits unused. This wastes 25% of the memory bandwidth savings that motivated quantization in the first place. If the goal is to reduce memory footprint and memory traffic, padding to 8 bits negates the advantage over FP8 quantization.

2. **Pack into 32-bit words:** Store multiple 6-bit values contiguously in memory (e.g., 5 values in 30 bits, or 16 values in three 32-bit words using cross-word packing). To load an individual 6-bit value, the kernel must load the containing 32-bit word(s), perform bit shifts and masks to extract the 6-bit field, and handle cross-boundary values that span two words. This preserves the 25% memory savings but adds extraction instructions to the dequantization path.

**The 4+2 innovation:** The paper's key insight is that any integer can be expressed as a sum of powers of 2, and specifically that a 6-bit value can be decomposed into a **4-bit segment and a 2-bit segment** whose bits, when concatenated, reconstruct the original 6-bit pattern. The decomposition is not arbitrary — it is structured according to the FP6 format:

- **4-bit sub-number (the "4" in "4+2"):** Contains the sign bit (1 bit) and the 3-bit exponent (3 bits). Total: 4 bits.
- **2-bit sub-number (the "2" in "4+2"):** Contains the 2-bit mantissa. Total: 2 bits.

**How this enables efficient loading:** The 4-bit values and 2-bit values are stored in **separate contiguous arrays** in GPU memory, each array using its natural power-of-2 bit width. The 4-bit array uses 4 bits per element (commonly supported as INT4 or packed nibble formats), and the 2-bit array uses 2 bits per element. At load time, the kernel issues **simultaneous loads** from both arrays — a 4-bit load and a 2-bit load — and concatenates the two bit fields to reconstruct the full 6-bit FP6 representation in a register.

The paper states: "This division into 4+2 bits facilitates simultaneous loading and dequantization of these sub-numbers, culminating in the generation of the final 16-bit floating-point (FP16) weight." The "simultaneous" loading is important: modern GPUs can issue multiple memory requests in parallel, so loading two small bit fields from different memory regions can overlap their latency, whereas loading and unpacking a packed 32-bit word requires sequential operations (load word, then shift and mask).

**Why this specific decomposition:** The 4+2 split aligns with the FP6 format's natural structure. The sign and exponent (4 bits) determine the magnitude range; the mantissa (2 bits) determines the fractional offset within that range. This separation means the dequantization process can reconstruct the FP16 value by combining the two loaded fields directly into the FP16 bit pattern without further bit manipulation (beyond the zero-padding that bias shift enables). An alternative decomposition (e.g., 3+3) would require splitting the exponent across two sub-numbers, complicating reconstruction.

The paper describes this as "an advanced variation of the second standard approach" (packing into wider words). Rather than packing multiple 6-bit values into a 32-bit word and extracting them via bit manipulation, the values are permanently stored in a pre-split format that makes extraction a simple load-and-concatenate operation.

#### System Evaluation Setup and GPU Kernel Benchmarks

The system evaluation in Section 5.3 measures the end-to-end performance of the FP6 kernel (with and without bias shift) against two baselines:

**Hardware and software environment:** NVIDIA A100-40GB GPU, Linux kernel 5.3.18, CUDA 11.8. The evaluation focuses on **feed-forward network (FFN) layers** during token generation (single-token autoregressive decoding), as opposed to prefill or training. FFN layers are chosen because they dominate inference latency in transformer models — the FFN matrices are typically `$4H \times H$` and `$H \times 4H$` where `$H$` is the hidden dimension, making them substantially larger than the attention projection matrices.

**Matrix shapes evaluated (from Table B.1):**

| Layer | Weight Shape | Input Shape | Model |
|-------|-------------|-------------|-------|
| FFN1-1b | 5504 × 2048 | 2048 × 8 | LLaMA-1B |
| FFN2-1b | 2048 × 5504 | 5504 × 8 | LLaMA-1B |
| FFN1-13b | 13824 × 5120 | 5120 × 8 | LLaMA-13B |
| FFN2-13b | 5120 × 13824 | 13824 × 8 | LLaMA-13B |
| FFN1-65b | 22016 × 8192 | 8192 × 8 | LLaMA-65B |
| FFN2-65b | 8192 × 22016 | 22016 × 8 | LLaMA-65B |

The batch size is 8 (8 independent sequences generating tokens simultaneously) and the sequence length is 1 (token generation phase, not prompt processing). This is the standard LLM inference setting for latency-critical deployments.

**Baselines:**
1. **cuBLAS (W16A16):** NVIDIA's standard FP16 matrix multiplication library, representing unquantized performance. This is the upper bound on model quality (no quantization error) and the speed baseline that quantization must beat to be worthwhile.
2. **Fine-grained INT4 (W4A16) from TensorRT-LLM:** NVIDIA's state-of-the-art INT4 weight-only quantization kernel. The paper uses "block-size: 64 and 128, we chose 128" for the evaluation. This is the incumbent 4-bit approach that FP6 must match or exceed in latency to be a viable replacement.

**FP6 kernel variants:**
1. **FP6 without Bias-Shift:** The FP6 kernel using the traditional approach of adding 12 to the exponent during dequantization.
2. **FP6 with Bias-Shift:** The proposed kernel using the precomputed `$S_{\text{fp16}} \times 2^{12}$` scaling factor and zero-padding exponent conversion.

**Results interpretation (Figure 2):** The speedups are reported relative to cuBLAS:
- FP6 with Bias-Shift achieves up to 2.37× over cuBLAS (fastest case) and 1.92× on average across the six layer configurations. This means the quantized kernel is roughly twice as fast as the unquantized FP16 baseline.
- FP6 with Bias-Shift is 1.06× faster on average for FFN1 layers and 2.05× faster for FFN2 layers compared to fine-grained INT4. The asymmetry between FFN1 and FFN2 likely reflects the different matrix shapes: FFN2 (expansion from `$H$` to `$4H$` in the second linear layer) benefits more from the reduced memory traffic of FP6's CGQ scheme (fewer scaling factors to load per weight) compared to INT4's FGQ (which stores a scaling factor every 128 weights).
- Bias shift provides a 1.36× speedup over the FP6-no-bias-shift kernel, confirming that exponent arithmetic was a significant fraction of the dequantization cost.

**Why this evaluation setup is appropriate:** The focus on token generation (batch size 8, sequence length 1) tests the regime where LLM inference is most bandwidth-constrained. Each generated token requires loading the entire set of model weights from GPU DRAM, and the computation (matrix multiplies) is small relative to the data movement. This is exactly the scenario where weight-only quantization provides the most benefit, and where the FP6 kernel's memory bandwidth savings translate most directly to latency improvements.

## 4. Key Insights and Innovations

### Innovation 1: The Generative Tasks Diagnosis — Exposing a Systematic Evaluation Blind Spot

The paper's most foundational contribution is not FP6 itself but the **diagnostic framework** that motivates it. Prior quantization research (GPTQ, AWQ, QuIP, SqueezeLLM, QUIK, ZeroQuant-V2) evaluated quality almost exclusively through zero-shot perplexity (Wikitext2, PTB, C4) and multiple-choice accuracy (ARC, BoolQ, PIQA). The paper shows — through deliberate, side-by-side comparison across three task categories — that these metrics are **systematically misleading** for production deployment decisions.

The evidence is structured like a controlled experiment: identical quantization methods, identical models, evaluated on zero-shot benchmarks (Tables 2 and 3) versus generative tasks (Table 4). The results reveal a hidden variable: **task type determines whether INT4 is acceptable**. Zero-shot accuracy for LLaMA-65B shows INT4-RTN actually exceeding FP16 (71.16 vs. 71.13 mean), which would lead a practitioner to conclude INT4 is perfectly safe. But the same quantization format on code generation shows CodeLLaMA-34B dropping from 45.05 to 43.45 pass@1 in JavaScript, and CodeGeeX2-6B collapsing from 34.04 to 29.80 in Python with fine-grain quantization.

What makes this a genuine conceptual contribution rather than just "they tested on more tasks" is the **meta-argument about evaluation methodology**. The paper identifies that the field's default benchmark suite measures something fundamentally different from what deployed models do. Zero-shot perplexity evaluates a model's token-level probability distribution; code generation and summarization evaluate the model's ability to produce coherent, logically consistent multi-step outputs. INT4's uniform quantization grid can preserve average token probabilities while introducing per-token errors that compound destructively over generated sequences — a failure mode invisible to perplexity but catastrophic for generation.

The prior work this contradicts is substantial and recent: GPTQ (Frantar et al., 2022) validated its method on WikiText-2 and PTB perplexity plus a handful of zero-shot tasks; QuIP (Chee et al., 2023) reported perplexity with theoretical guarantees; AWQ (Lin et al., 2023) benchmarked on perplexity and lm-eval tasks; SqueezeLLM (Kim et al., 2023) similarly. None evaluated code generation or abstractive summarization. The paper's intervention is to show that these evaluations create an **illusion of robustness** that collapses when the model is asked to generate.

A secondary diagnostic insight is the **small-model amplification effect**. Table 4 shows INT4 degradation is worst for the 406M BART model (roughly 2 ROUGE-1 point loss on XSum) and for CodeGeeX2-6B (up to 4+ point pass@1 loss), while larger models like CodeLLaMA-34B show smaller gaps. This inverts the deployment logic: small models — exactly the ones you would quantize for cost-sensitive deployment — suffer most from quantization error, while large models that are already harder to deploy handle INT4 gracefully. The paper doesn't speculate on why this happens (likely related to overparameterization providing redundancy that absorbs quantization noise), but the pattern itself is a practical diagnostic that reorients deployment decision-making.

### Innovation 2: FP6 as a "Sweet Spot" — The Minimum Viable Precision for Generative Robustness

The paper introduces a concept that had been absent from the quantization literature: the idea of a **precision threshold for generative robustness** — a specific bit width below which model behavior qualitatively degrades on generation tasks, regardless of quantization algorithm or granularity. The empirical evidence places this threshold at 6 bits and floating-point format.

This is not an incremental refinement of existing 4-bit quantization methods. It is a **fundamental claim about precision sufficiency**: that INT4 is below the representational floor for generative LLM inference, and that the precision ceiling (where additional bits provide diminishing returns) sits at FP6 for the models and tasks tested. The claim is supported by the structured comparison in Table 5:

- **FP5 (CGQ):** Improves over INT4 but still shows gaps. CodeGeeX2-6B Python: 30.56 vs. 34.04 FP16 — a 3.5-point gap that remains practically significant. The paper states FP5 "still does not reach the high performance levels of FP16."
- **FP6 (CGQ):** Effectively closes the gap. StarCoder-15B Python: 35.64 vs. 35.43 FP16. CodeLLaMA-34B Python: 44.31 vs. 43.22 FP16 (FP6 actually *exceeds* baseline, likely within noise but indicating no systematic degradation). BART-406M XSum ROUGE-2: 22.20 vs. 22.39 — within 0.19 points.
- **INT4 (CGQ):** Fails to close the gap on most tasks. StarCoder-15B Python: 33.20 vs. 35.43. CodeGeeX2-6B JavaScript: 25.15 vs. 31.50 — a crippling 6.35-point drop.

What distinguishes this from prior floating-point quantization work (ZeroQuant-FP, LLM-FP4, FP8 formats) is the **discontinuous jump from FP5 to FP6**. Prior work explored FP4, FP8, and occasionally FP5 as alternatives to INT4/INT8, but the field had not systematically asked: at what exact bit width and format does generative robustness emerge? The paper provides a concrete answer — 6 bits with a 3+2 exponent-mantissa split — and shows that FP5 with the same exponent range but only 1 mantissa bit is insufficient. This makes FP6 a **non-arbitrary design point**: it is empirically the minimum precision that preserves FP16-competitive generative performance, and the bit allocation (3 exponent, 2 mantissa) is what enables this minimum.

The significance beyond raw performance is that this finding **simplifies quantization drastically**. If FP6 works with RTN and CGQ — the simplest possible algorithm and coarsest granularity — then the entire apparatus of second-order optimization (GPTQ), activation-aware scaling (AWQ), outlier detection (SpQR), and fine-grain quantization that the field developed to rescue INT4 becomes unnecessary. The paper's robustness claim (Table 6: FP6-RTN-CGQ and FP6-GPTQ-CGQ produce near-identical perplexity across LLaMA sizes) is evidence that the representational headroom of FP6 absorbs quantization error to the point where algorithm sophistication doesn't matter. This is a **reverse scaling law**: at sufficient precision, algorithmic complexity provides zero marginal benefit.

The limitation is that the sweet spot is task-dependent. Table A.1 (GPT-4 judged dialogue quality for vicuna models) shows no clear precision-quality relationship — FP6 doesn't systematically outperform INT4 for open-ended chat. The paper acknowledges this only in passing ("we do not find a clear link between bit precision and performance" for chat), but it implies the FP6 sweet spot is specifically for tasks with **structured correctness criteria** (code passing tests, summarization with n-gram overlap) rather than subjective quality.

### Innovation 3: The 4+2 Layout and Bias Shift as an Enabling Technology — Proving Odd-Bit Precision Is Practically Viable

The paper's system contribution — the 4+2 data layout combined with exponent bias shift — represents a different kind of innovation from the accuracy findings. It is an **enabling technology**: it doesn't claim to beat cuBLAS by a novel margin (the 1.92× average speedup is typical for memory-bandwidth-reduction approaches), but rather it **removes the barrier** that had prevented odd-bit formats like FP6 from being explored seriously.

Before this work, the standard approaches for non-power-of-2 bit widths were:
1. Pad to the next power of 2 (6→8 bits), losing the memory savings (the approach the paper dismisses as negating "the primary benefit of the 6-bit format, which is to conserve memory").
2. Pack multiple values into wider words (e.g., five 6-bit values in a 32-bit word) and extract via bit manipulation, which the paper describes as maintaining memory savings but adding "complexity to the dequantization process."

The innovation is a **third approach** that hadn't been proposed: permanently split each value into power-of-2-sized sub-fields at storage time, sacrifice a small amount of memory contiguity, and gain back the complexity in the form of simpler load instructions. The decomposition into 4+2 is non-trivial because it **aligns with the semantic boundaries of the FP6 format** (sign+exponent in the 4-bit chunk, mantissa in the 2-bit chunk), which means the dequantization step can concatenate the two fields directly into the FP16 bit pattern without re-shuffling bits across format boundaries.

The bias shift complements this by eliminating the other costly operation — exponent arithmetic during dequantization. Moving the `$2^{12}$` multiplication factor from the per-weight conversion step to the per-row precomputed scaling factor is an instance of **static hoisting**: identifying a computation that depends only on quantization parameters (not on the specific weight value) and moving it offline. This is a standard compiler optimization, but applying it specifically to floating-point bias adjustment for odd-bit dequantization is novel.

What makes this more than just an engineering optimization is the **argument it makes about the viability of odd-bit formats**. The paper's Figure 2 shows that FP6 with bias shift is not merely competitive with INT4 — it is **faster** (1.06× for FFN1, 2.05× for FFN2). This means the system-level innovations don't just mitigate the odd-bit penalty; they achieve a net advantage. The speedup over INT4-FGQ, particularly for FFN2 layers (where the weight matrix is h × 4h and loading scaling factors every 128 elements for INT4-FGQ adds measurable overhead), suggests that FP6-CGQ's **reduced scaling factor metadata** (one FP16 scale per row versus one per 128 weights) contributes to the speed advantage independently of the bias shift.

The practical implication is that FP6 can serve as a **drop-in replacement for INT4** — not just accuracy-compatible but latency-compatible or better — which changes the decision calculus for deployment engineers: you no longer choose between quality (FP6) and speed (INT4); FP6 gives you both. This is the claim that justifies the paper's title ("Redefining LLMs Quantization") — it's not redefining quantization algorithms but redefining what precision the field should standardize on for deployment.

### Innovation 4: GPTQ Overfitting as a First-Class Failure Mode — Calibration Dataset Independence as a Design Requirement

This is a negative-result innovation: the paper demonstrates and quantifies a failure mode for GPTQ that had been noted but not systematically characterized. The observation that GPTQ's performance depends on the calibration dataset is not unique to this paper (Section 4 notes that "Independently, [60] also notices this issue while examining LLaMA-7B"), but the paper provides the **clearest quantification of the magnitude** and frames it as a **design requirement** for quantization methods.

Table 1 shows that for LLaMA-1B with INT4-GPTQ-FGQ, calibrating on C4 produces PTB perplexity of **1399.89** versus 37.39 for FP16 — the model is essentially outputting noise on out-of-distribution data. This is not a minor regression; it represents catastrophic failure. The overfitting pattern is symmetric (C4 calibration hurts PTB, PTB calibration hurts C4), confirming it's a systematic property of the Hessian-based compensation mechanism rather than a quirk of a particular dataset.

What makes this a conceptual contribution rather than just a bug report is the **implicit design principle it establishes**: a quantization method intended for general deployment should be **calibration-dataset-independent**. If the quantized model's performance bounds depend on an unknown future input distribution matching a calibration distribution chosen at quantization time, the model cannot be deployed with confidence. RTN satisfies this principle by construction (no calibration data, no input statistics); GPTQ violates it structurally (the Hessian approximation `$H \approx 2XX^\top$` is inherently a function of the calibration inputs).

The paper uses this finding to argue not that GPTQ is a bad algorithm but that **the precision level should be high enough that calibration-sensitive compensation is unnecessary**. Table 6 shows that for FP6, GPTQ and RTN produce near-identical results (LLaMA-65B Wikitext2: both 6.42 vs. 6.41 FP16), meaning GPTQ's sophisticated error compensation provides zero benefit when the base precision is sufficient. The implication is that the field's investment in increasingly complex post-training compensation algorithms (GPTQ, AWQ, QUIK, SpQR) is partly a **symptom of working at insufficient precision** — raise the bit width to 6 bits with floating-point format, and the compensation problem largely vanishes.

This is a fundamental reframing of the trade-off: instead of optimizing quantization algorithms to squeeze maximum quality from minimal bits, identify the minimum bit width that achieves robustness with the simplest algorithm, and invest engineering effort in making that bit width fast. The paper's system-level innovations (4+2, bias shift) are the other half of this equation — they make the "sufficient" precision fast enough to deploy.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper evaluates across three task categories: (1) Zero-Shot tasks using perplexity datasets PTB, Wikitext2, C4, PTB-new, and C4-new, plus accuracy on ten tasks (ARC Challenge/Easy, BoolQ, CB, Copa, PIQA, RTE, WSC, Storycloze); (2) Code Generation using HumanEval-X for Python and JavaScript, following the non-greedy generation settings from Zheng et al. (2023) with n=20, t=0.2, top_p=0.95; (3) Summarization using CNNDailyMail and XSum with BART-large models fine-tuned on each dataset. The Zero-Shot perplexity datasets follow the approach from GPTQ-for-LLaMa, with PTB-new using the PTB test dataset and C4-new comprising the first 256×seqlength tokens.

- **Base model(s).** The paper tests LLaMA models at three scales (1B, 13B, 65B) for zero-shot evaluation, with the 1B variant being Sheared-LLaMA-1.3B (Xia et al., 2023) and the 13B/65B being the original LLaMA checkpoints (Touvron et al., 2023). For code generation, the paper uses CodeGeeX2-6B, StarCoder-15B (Li et al., 2023), and CodeLLaMA-34B (Liu et al., 2023). For summarization, two separately fine-tuned BART-large-406M variants are used (CNN and XSum versions from HuggingFace). The models span two orders of magnitude in parameter count (406M to 65B), enabling analysis of how quantization effects scale with model size.

- **Metrics.** Zero-Shot perplexity is reported as the standard token-level negative log-likelihood (lower is better). Zero-Shot accuracy is the mean percentage correct across the ten classification tasks. Code generation uses pass@1 (the fraction of generated solutions that pass all unit tests), averaged over at least 8 repeated experiments with different random seeds (111, 222, ..., 888, 1111) and reported with standard deviation. Summarization uses ROUGE-1/ROUGE-2/ROUGE-L scores computed against reference summaries. The paper also reports GPT-4-based quality ratings for chat models in Appendix Table A.1, though concludes there is "no clear link between bit precision and performance" for this metric.

- **Baselines.** The primary quality baseline is FP16 (full-precision weights with FP16 activations, W16A16). The primary quantization baselines are: (1) INT4-RTN with both CGQ and FGQ, representing the simplest integer quantization approach; (2) INT4-GPTQ (Frantar et al., 2022) with both CGQ and FGQ, representing the state-of-the-art integer quantization algorithm; (3) FP5-CGQ with RTN, representing the next-lowest floating-point precision to FP6; (4) FP6 with RTN and CGQ as the proposed method. For system evaluation, cuBLAS W16A16 serves as the unquantized latency baseline, and TensorRT-LLM's fine-grained INT4 kernel (W4A16, block size 128) serves as the state-of-the-art 4-bit kernel baseline.

- **Generation budget / compute accounting.** For quality experiments, all methods are compared at identical bit widths per weight, with the primary comparison being 4-bit (INT4 or FP5) versus 6-bit (FP6) versus 16-bit (FP16) storage. No computation budget is varied during quality evaluation — each model is quantized once and evaluated at that fixed precision. Calibration for GPTQ uses 128 samples for LLaMA-1B/13B and 32 samples for LLaMA-65B. For system evaluation, the compute is measured as kernel latency in milliseconds for matrix multiplications of specific shapes (detailed in Table B.1), with batch size fixed at 8 and sequence length at 1 (token generation phase). The evaluation platform is an NVIDIA A100-40GB GPU.

- **Cross-validation / statistical protocol.** Code generation experiments use nine random seeds and report standard deviations to account for sampling variance in pass@1 estimates. Zero-Shot perplexity and accuracy experiments use a fixed seed (123) for determinism. The paper does not employ cross-validation for hyperparameter selection since the quantization methods use fixed formulas (RTN uses Equation 1 with deterministic scaling factor computation; GPTQ uses its standard Hessian-based procedure). For the chat evaluation in Appendix Table A.1, the paper notes "significant variability in our findings" and concludes no clear precision-performance relationship exists, effectively reporting negative results. The paper does not report confidence intervals or statistical significance tests for any comparisons, meaning the reported differences (particularly small ones, like FP6 vs. FP16 gaps of <0.5 ROUGE points) should be interpreted with appropriate caution.

### Main Quantitative Results

#### Zero-Shot Perplexity: GPTQ Overfitting and FP6 Robustness

The perplexity results in Tables 1, 2, and 6 establish three key patterns that motivate the FP6 approach.

**GPTQ catastrophically overfits to calibration data for small models.** Table 1 demonstrates that for LLaMA-1B with INT4-GPTQ-FGQ, calibrating on C4 produces C4 perplexity of 9.34 (reasonable, near FP16's 8.91) but PTB perplexity explodes to 1399.89 — roughly 37× worse than FP16's 37.39. When the calibration dataset is swapped to PTB, the pattern reverses: PTB perplexity is 49.80 (improved but still 33% worse than FP16), while C4 perplexity is 9.84. This symmetric overfitting confirms that GPTQ's Hessian-based error compensation is tuned to the statistics of the calibration inputs. Table 2 shows the same pattern at larger scale: LLaMA-13B INT4-GPTQ-FGQ calibrated on C4 yields 22.14 PTB perplexity versus 19.23 FP16, while LLaMA-65B narrows the gap to 8.17 versus 8.00. The paper notes this is "less severe for larger models" — the 1B model shows a 37× gap between calibration-matched and calibration-mismatched datasets, while the 65B model shows only a 0.17 perplexity point difference — but the existence of the failure mode at any scale means GPTQ's deployment robustness depends on unknown future input distributions.

**FP6 is robust to quantization algorithm and granularity.** Table 6 provides the central evidence. For LLaMA-65B on Wikitext2: FP16 achieves 6.41; FP6-GPTQ-CGQ achieves 6.42; FP6-RTN-CGQ achieves 6.42. The three values are essentially identical, meaning neither the sophisticated GPTQ algorithm nor the simpler RTN algorithm produces meaningfully different results — FP6's representational capacity makes algorithmic sophistication irrelevant. This contrasts sharply with INT4, where GPTQ-FGQ (perplexity 6.61) significantly outperforms RTN-CGQ (7.72) — a gap of 1.11 perplexity points that represents a substantial practical difference. The granularity comparison within FP6 shows the same robustness: FP6-RTN-FGQ achieves 6.44 versus FP6-RTN-CGQ at 6.42 on LLaMA-65B, a 0.02 point difference versus the 0.69 point gap for INT4 (7.30 FGQ versus 7.72 CGQ). The paper's claim that "FP6 with CGQ consistently maintains high performance close to baseline" is supported: across all five perplexity datasets and three model sizes in Table 6, FP6-CGQ degrades from FP16 by at most 0.02–0.03 perplexity points for the 65B model, and even for the 1B model the maximum degradation is 0.93 points on PTB (38.79 versus 37.39).

**FP5 is insufficient — the threshold is at 6 bits.** Table 6 shows FP5-GPTQ-CGQ on LLaMA-1B achieves 32.03 Wikitext2 perplexity versus 24.31 for FP16 — a 32% degradation that is substantially worse than FP6's 23.58. For LLaMA-13B: FP5-RTN-CGQ achieves 14.10 versus 13.16 FP16, while FP6-RTN-CGQ achieves 13.09 — FP6 is within 0.07 points of FP16 while FP5 is 0.94 points away. The gap persists at 65B: FP5-GPTQ-CGQ at 6.46 versus FP6-GPTQ-CGQ at 6.42 versus FP16 at 6.41. The additional mantissa bit in FP6 (E3M2 versus FP5's E3M1) provides 4 fractional levels per octave instead of 2, and this doubling of within-octave precision appears to be the critical threshold for closing the perplexity gap to FP16.

#### Zero-Shot Accuracy: The Illusion of INT4 Robustness

Table 3 and Appendix Table A.2 present zero-shot accuracy across ten classification tasks for LLaMA-1B, 13B, and 65B. The striking finding is that INT4 quantization shows **no consistent degradation** on these metrics — and in some cases **improves** over FP16.

For LLaMA-65B (Table 3): FP16 achieves mean accuracy of 71.13 across the ten tasks. INT4-GPTQ-FGQ achieves 70.59 (a 0.54 point drop), while INT4-RTN-FGQ achieves **71.16** — actually 0.03 points higher than FP16. FP6-RTN-CGQ (from Table A.2) achieves 70.86. All precision levels cluster within a 0.5-point band, meaning zero-shot accuracy cannot distinguish between FP16 and any quantized variant for this model size.

For LLaMA-13B: FP16 achieves 63.51. INT4-GPTQ-FGQ achieves 62.44 (1.07 point drop). FP6-RTN-CGQ achieves 63.26 (0.25 point drop). Again, all values are close.

For LLaMA-1B: FP16 achieves 53.64. INT4-RTN-FGQ achieves 53.55 (0.09 point drop). FP6-RTN-CGQ achieves 53.99 (0.35 point improvement over FP16). The differences are within noise.

The paper's critical observation is that these zero-shot accuracy results, if taken in isolation, would suggest INT4 quantization is essentially lossless — and that FP6 provides no meaningful advantage. Yet the generative task results (Table 4, Table 5) show exactly the opposite. This discrepancy is the paper's methodological argument: **zero-shot multiple-choice accuracy is an insufficient evaluation metric for production quantization decisions** because it fails to capture the degradation that manifests in sequence generation.

#### Code Generation: INT4 Degradation and FP6 Recovery

Table 4 establishes the baseline INT4 performance on code generation, while Table 5 adds FP5 and FP6 results for direct comparison. The results are reported as pass@1 percentages with standard deviations over multiple random seeds.

**INT4-FGQ is unstable and can underperform INT4-CGQ.** Table 4 shows CodeGeeX2-6B achieving 34.04±1.70 pass@1 on Python in FP16. INT4-CGQ achieves 33.08±2.07 (a modest 0.96 point drop), but INT4-FGQ drops dramatically to 29.80±1.76 — a 4.24 point drop from FP16 that is **worse** than the coarser quantization scheme. This is the opposite of the expected behavior (finer granularity should reduce quantization error) and indicates that FGQ's additional scaling factors introduce variance that, for this model-task combination, destabilizes generation. The JavaScript results for the same model show a similar pattern: FP16 31.50±2.62, INT4-CGQ 25.15±1.97 (6.35 point drop), INT4-FGQ 28.35±2.36 (3.15 point drop). Here FGQ helps compared to CGQ but still leaves a substantial gap to FP16.

**INT4 degradation varies unpredictably by model and language.** For CodeLLaMA-34B on Python, the pattern inverts: INT4-CGQ achieves 39.84±1.64 versus FP16's 43.22±2.21 (3.38 point drop), but INT4-FGQ achieves **46.88±1.87** — actually exceeding FP16 by 3.66 points. Meanwhile, the same model on JavaScript shows INT4-FGQ at 43.22±1.36, which is essentially identical to FP16 at 45.05±1.60 (within overlapping standard deviations, roughly a 1.83 point gap). Table 4's caption explicitly notes this: "INT4 CodeLLaMA-34B on FGQ achieves 46.88 in Python code, surpassing its baseline, whereas the INT4 CodeGeeX2-6B on FGQ scores only 29.8, falling behind even its INT4-CGQ performance. This highlights the inconsistency of INT4." StarCoder-15B shows a more consistent pattern: INT4-CGQ drops Python by 2.23 points (33.20 vs. 35.43) and JavaScript by 1.49 points (32.18 vs. 33.67), with FGQ providing modest recovery on Python (35.64) but negligible on JavaScript (32.32).

**FP6 closes the gap to FP16 with CGQ alone.** Table 5 adds the critical comparison. For StarCoder-15B Python: FP6-CGQ achieves 35.64±1.26 versus FP16's 35.43±2.21 — the values are within 0.21 points, well within one standard deviation of each other. JavaScript: FP6-CGQ achieves 33.60±1.91 versus FP16's 33.67±2.02 — essentially identical. For CodeLLaMA-34B Python: FP6-CGQ achieves 44.31±1.88, which is actually 1.09 points above FP16's 43.22±2.21 (again within overlapping error bars). JavaScript: 44.51±1.30 versus 45.05±1.60, a 0.54 point difference. The paper's claim that "FP6, employing a basic round-to-nearest algorithm and a coarse-grain quantization approach, consistently achieves accuracy on par with full-precision models" (Abstract) is supported for code generation: across the six model-language pairs in Table 5, the maximum FP6-CGQ to FP16 gap is 1.09 points on CodeLLaMA-34B Python (in the favorable direction), and every pair has overlapping standard deviation intervals.

**The StarCoder-15B result deserves highlighting.** The paper states in the abstract that "with the FP6 quantization, StarCoder-15B model performs comparably to its FP16 counterpart in code generation." Table 5 supports this precisely: Python pass@1 goes from 35.43 (FP16) to 35.64 (FP6-CGQ) — a 0.21 point *improvement* — and JavaScript goes from 33.67 to 33.60 — a 0.07 point drop. Both differences are negligible relative to the ±1.26–2.21 standard deviations. This is a model where INT4-CGQ drops Python by 2.23 points, so the FP6 advantage over INT4 is concrete and practically significant.

**FP5 is an intermediate improvement, not a solution.** Table 5 shows FP5-CGQ on CodeGeeX2-6B Python: 30.56±2.12 versus FP16's 34.04±1.70 — a 3.5 point gap that is better than INT4-CGQ (33.08) but still substantially degraded. CodeLLaMA-34B Python: FP5-CGQ achieves 40.55±0.92 versus 43.22±2.21 — a 2.67 point gap that FP6 closes to essentially zero. The paper states FP5 "still does not reach the high performance levels of FP16," and the data confirm this: FP5 consistently underperforms FP16 across all model-language pairs, while FP6 does not.

#### Summarization: Small-Model Sensitivity and FP6 Recovery

Table 4 and Table 5 include summarization results for BART-large-406M on two datasets: XSum and CNNDailyMail. The results are reported as ROUGE-1/ROUGE-2/ROUGE-L.

**INT4 quantization degrades the 406M model measurably on summarization.** Table 4: On XSum, FP16 achieves ROUGE-1 of 45.49, ROUGE-2 of 22.39, ROUGE-L of 37.28. INT4-CGQ drops to 43.76/20.76/35.82 — losses of 1.73, 1.63, and 1.46 points respectively. INT4-FGQ recovers partially to 44.82/21.63/36.48, but gaps of 0.67/0.76/0.80 points remain. On CNN, FP16 achieves 44.07/21.09/30.65; INT4-CGQ achieves 43.67/20.68/30.07 (losses of 0.40/0.41/0.58); INT4-FGQ achieves 43.73/20.72/30.24. The pattern is consistent: INT4 produces non-trivial ROUGE degradation that fine-grain quantization can reduce but not eliminate.

**FP6 matches FP16 on summarization.** Table 5: FP6-CGQ on XSum achieves 45.37/22.20/37.11 versus FP16's 45.49/22.39/37.28 — differences of 0.12/0.19/0.17 points. On CNN: 44.06/21.07/30.67 versus 44.07/21.09/30.65 — differences of 0.01/0.02/−0.02 points (FP6 is essentially identical to FP16). The paper's abstract claim that "for smaller models like the 406M it closely matches their baselines in summarization" is supported: the maximum ROUGE gap between FP6-CGQ and FP16 is 0.19 points (ROUGE-2 on XSum), which is likely below the threshold of practical significance for summarization quality. FP5-CGQ achieves intermediate performance: 45.12/22.11/36.96 on XSum and 44.13/21.19/30.68 on CNN — better than INT4-CGQ but with small gaps to FP16 (0.37/0.28/0.32 on XSum).

**The small-model finding matters.** The 406M BART model is two orders of magnitude smaller than the 65B LLaMA, making it exactly the kind of model that would benefit most from quantization for deployment on resource-constrained hardware. The paper's demonstration that FP6 preserves FP16-level quality at this scale — whereas INT4 does not — has immediate practical implications for deploying production summarization systems.

#### System Performance: FP6 Kernel Latency versus Baselines

Figure 2 and Table B.1 present kernel-level latency benchmarks on NVIDIA A100 for six feed-forward layer configurations spanning LLaMA-1B, 13B, and 65B.

**Absolute latency numbers (Table B.1).** The latency values in milliseconds for each configuration:
- FFN1-1b (5504×2048 weights, 2048×8 inputs): cuBLAS 0.016ms, INT4-FGQ 0.019ms, FP6 w/o Bias-Shift 0.021ms, FP6 w/ Bias-Shift 0.013ms.
- FFN2-1b (2048×5504 weights, 5504×8 inputs): cuBLAS 0.020ms, INT4-FGQ 0.043ms, FP6 w/o Bias-Shift 0.022ms, FP6 w/ Bias-Shift 0.016ms.
- FFN1-13b (13824×5120 weights): cuBLAS 0.118ms, INT4-FGQ 0.044ms, FP6 w/o Bias-Shift 0.063ms, FP6 w/ Bias-Shift 0.052ms.
- FFN2-13b (5120×13824 weights): cuBLAS 0.109ms, INT4-FGQ 0.106ms, FP6 w/o Bias-Shift 0.068ms, FP6 w/ Bias-Shift 0.053ms.
- FFN1-65b (22016×8192 weights): cuBLAS 0.263ms, INT4-FGQ 0.098ms, FP6 w/o Bias-Shift 0.145ms, FP6 w/ Bias-Shift 0.111ms.
- FFN2-65b (8192×22016 weights): cuBLAS 0.266ms, INT4-FGQ 0.167ms, FP6 w/o Bias-Shift 0.157ms, FP6 w/ Bias-Shift 0.114ms.

**FP6 with bias shift is faster than cuBLAS across all configurations.** The speedups over cuBLAS range from 1.16× (FFN1-65b: 0.263/0.111 = 2.37×, though this appears to be the maximum) to approximately 1.25× (FFN2-1b: 0.020/0.016). The paper reports "up to 2.37× faster and on average 1.92× faster than cuBLAS." The arithmetic: for FFN1-1b, 0.016/0.013 = 1.23×; for the maximum case, 0.263/0.111 = 2.37× at FFN1-65b. The 1.92× average suggests the geometric mean across the six configurations is approximately 1.92.

**FP6 with bias shift is competitive with or faster than INT4-FGQ.** For FFN1 layers, FP6 w/ Bias-Shift is: 0.013ms vs. 0.019ms (1.46× faster) for 1B; 0.052ms vs. 0.044ms (0.85×, i.e., slower) for 13B; 0.111ms vs. 0.098ms (0.88×) for 65B. The paper states "1.06× faster on average for the first feed-forward layers (FFN1)" — this seems inconsistent with the raw numbers for 13B and 65B where FP6 is slower, suggesting the average is dominated by the largest speedup case or computed differently. For FFN2 layers, FP6 w/ Bias-Shift is: 0.016ms vs. 0.043ms (2.69×) for 1B; 0.053ms vs. 0.106ms (2.00×) for 13B; 0.114ms vs. 0.167ms (1.46×) for 65B. The paper reports "2.05× faster for the second feed-forward layers (FFN2)," which is consistent with these ratios. The FFN2 advantage likely stems from the shape (H×4H rather than 4H×H), where loading scaling factors for INT4-FGQ (one per 128 weights) adds more overhead relative to the computation than FP6-CGQ (one per full row of 4H elements).

**The bias shift provides a substantial fraction of the speedup.** Comparing FP6 w/ Bias-Shift to FP6 w/o Bias-Shift across the six configurations: 1.62×, 1.38×, 1.21×, 1.28×, 1.31×, 1.38×. The paper reports 1.36× average. This means the bias shift alone — eliminating the exponent addition in the per-weight dequantization loop — recovers approximately 26% of the kernel's execution time that was being spent on the bit-manipulation arithmetic.

### Ablation Studies and Robustness Checks

**GPTQ calibration dataset (Tables 1 and 2):** Switching calibration datasets from C4 to PTB or vice versa for INT4-GPTQ produces perplexity swings of 30–40× on LLaMA-1B (e.g., PTB perplexity: 49.80 with PTB calibration vs. 1399.89 with C4 calibration, both FGQ). The effect diminishes with model scale: LLaMA-13B's worst-case swing between calibration datasets is roughly 2.5 perplexity points (PTB: 14.19 vs. 22.14). For FP6, the calibration effect is essentially absent — FP6-GPTQ-CGQ calibrated on C4 achieves Wikitext2 perplexity of 6.42 for LLaMA-65B, identical to FP6-RTN-CGQ at 6.42, meaning the GPTQ algorithm provides no benefit over RTN for FP6.

**Quantization granularity (Tables 2, 4, 5, 6):** For INT4, FGQ sometimes improves over CGQ (LLaMA-65B perplexity: 7.30 FGQ vs. 7.72 CGQ for RTN; CodeLLaMA-34B Python pass@1: 46.88 FGQ vs. 39.84 CGQ) and sometimes degrades it (CodeGeeX2-6B Python: 29.80 FGQ vs. 33.08 CGQ). For FP6, the FGQ-CGQ gap is negligible: LLaMA-65B Wikitext2 perplexity 6.44 (FGQ) vs. 6.42 (CGQ) for RTN; 6.47 (FGQ) vs. 6.42 (CGQ) for GPTQ — differences of 0.02–0.05 points versus the 0.42–0.61 point gaps for INT4. The paper interprets this as evidence that FP6's representational precision is sufficient that finer granularity provides no benefit.

**Quantization algorithm: RTN vs. GPTQ (Tables 2, 3, 6, A.2):** For INT4 on LLaMA-1B, GPTQ-FGQ achieves 564.73 Wikitext2 perplexity versus RTN-FGQ at 22.76 — a catastrophic 25× difference that demonstrates GPTQ's calibration sensitivity. For LLaMA-65B, the gap narrows: GPTQ-FGQ at 6.61 versus RTN-FGQ at 7.30 (0.69 point advantage for GPTQ). For FP6 on LLaMA-65B, the gap essentially vanishes: GPTQ-CGQ and RTN-CGQ both achieve 6.42. On zero-shot accuracy (Table A.2), the differences are within 0.5–1.5 mean accuracy points for all model sizes and both precision formats, suggesting accuracy is less sensitive to algorithm choice than perplexity.

**FP5 vs. FP6 (Tables 5 and 6):** This comparison isolates the effect of the additional mantissa bit. On LLaMA-65B Wikitext2, FP5-GPTQ-CGQ achieves 6.46 versus FP6-GPTQ-CGQ at 6.42 (0.04 point difference — small in perplexity). On code generation, the gap is larger: StarCoder-15B Python pass@1 drops from 35.64 (FP6) to 34.30 (FP5), a 1.34 point gap; CodeGeeX2-6B Python drops from 34.10 to 30.56, a 3.54 point gap. On summarization, FP5-CGQ XSum ROUGE-2 is 22.11 versus FP6's 22.20 and FP16's 22.39 — FP5 closes most but not all of the gap. The pattern suggests that 1 additional mantissa bit (doubling the within-octave resolution from 2 to 4 levels) provides a meaningful but not enormous boost for perplexity, and a more substantial boost for generation tasks where small per-token errors compound.

**Bias shift on/off (Figure 2, Table B.1):** As discussed above, enabling bias shift improves FP6 kernel latency by 1.21–1.62× (average 1.36×) across the six FFN configurations. The improvement is larger for smaller matrix sizes (1.62× for FFN1-1b, 1.21× for FFN1-13b), suggesting the per-weight dequantization overhead is a larger fraction of total latency when the matrix multiply is smaller.

**Chat model evaluation (Appendix Table A.1):** GPT-4 judged quality of vicuna-7b/13b at FP16, INT4, and FP6 across eight categories (Writing, Roleplay, Coding, STEM, Humanities, Reasoning, Math, Extraction). The paper explicitly reports this as a negative or inconclusive result: "there is no clear link between bit precision and performance." For vicuna-7b, the Coding score goes from 3.21 (FP16) to 3.21 (INT4) to 3.67 (FP6) — an improvement — but Math goes from 3.6 to 2.6 to 2.2 — a monotonic decline. For vicuna-13b, Reasoning goes from 5.2 (FP16) to 4.7 (INT4) to 4.8 (FP6). These non-monotonic patterns suggest that either (1) FP6's advantage is task-specific and doesn't extend to subjective dialogue quality, or (2) the GPT-4 evaluation has variance larger than the quantization effects. The paper does not investigate further, and this represents a limitation in the evaluation scope.

### Critical Assessment

**Claim: "INT4 quantization can significantly underperform on generative tasks."** This is supported with clear quantitative evidence from Table 4 and Table 5. The code generation results show INT4-CGQ degrading pass@1 by 0.96–6.35 points depending on model and language, with the worst case being CodeGeeX2-6B JavaScript from 31.50 to 25.15. The summarization results show ROUGE-2 dropping by 0.41–1.63 points. However, the paper's framing as "INT4 underperforms" is qualified by the observation that some INT4-FGQ configurations actually match or exceed FP16 (CodeLLaMA-34B Python at 46.88 vs. 43.22). The claim would be more precise as "INT4 performance is inconsistent and sometimes severely degraded on generative tasks, with no guarantee that zero-shot metrics predict which cases will fail." The paper's contribution is documenting this inconsistency rather than proving uniform INT4 failure.

**Claim: "FP6, even with coarse-grain quantization, performs robustly across various algorithms and tasks."** This is the paper's strongest claim and is well-supported for the tasks tested. FP6-CGQ with RTN shows maximum gaps to FP16 of 0.21 pass@1 points (StarCoder-15B Python — in the favorable direction), 0.19 ROUGE-2 points (BART-406M XSum), and 0.03 perplexity points (LLaMA-65B Wikitext2). However, the claim has important scope limitations that the paper does not comprehensively address: (1) It is demonstrated on three model families (LLaMA, StarCoder/CodeGeeX2/CodeLLaMA, BART) with specific scales (406M to 65B) — generalization to other architectures (encoder-decoder beyond BART, mixture-of-experts, vision-language models) is untested; (2) The generative tasks are code (Python and JavaScript only, with other languages excluded "due to instability") and summarization (CNN/DailyMail and XSum) — whether conversational QA, translation, or long-form reasoning follow the same pattern is unknown; (3) The chat evaluation in Table A.1 suggests the FP6 advantage may not extend to open-ended dialogue, though the paper attributes this to evaluation variance rather than a genuine null result.

**Claim: "FP6 can become a promising solution to the current 4-bit quantization methods used in LLMs."** This is a broader claim about deployability that combines accuracy and system performance. The accuracy evidence supports it for the tested tasks; the system evidence supports it for the tested GPU (A100) and layer types (FFN layers of LLaMA models). Several gaps exist: (1) The paper evaluates only FFN layers during token generation, not attention projections or embedding layers, and not the prompt processing (prefill) phase — these may have different compute-vs-memory tradeoffs that affect the FP6 versus INT4 comparison; (2) The system evaluation is at the kernel level, not end-to-end model inference — memory savings from 6-bit versus 4-bit weights (25% less compression) might affect the maximum batch size or sequence length that fits in GPU memory, potentially negating latency advantages in memory-capacity-constrained scenarios; (3) The comparison is against one specific INT4 kernel (TensorRT-LLM, block size 128) — other INT4 implementations or block sizes might yield different relative performance; (4) The paper explicitly states that "Figure 2 provides only a snapshot of key outcomes, with a comprehensive system implementation and detailed performance analysis reserved for future work," acknowledging that the system results are preliminary.

**Missing experiments that would strengthen the paper:** (1) End-to-end inference latency and throughput for complete models (not just individual FFN layers), which would reveal whether memory capacity savings from INT4's 25% smaller footprint enable larger batch sizes that offset FP6's per-layer speed advantage; (2) Evaluation on at least one additional model family for code generation (e.g., DeepSeek-Coder, Phi-2) to test whether the FP6 advantage is architecture-dependent; (3) Inclusion of additional programming languages in the code generation benchmark (the paper excludes CPP, Go, and Rust due to "higher variance" — but this exclusion itself is informative about the stability of these evaluations, and FP6's robustness should be tested in these higher-variance settings); (4) A controlled experiment varying only the mantissa bits (e.g., FP6E3M2 vs. FP6E4M1 vs. FP6E2M3) to disentangle whether the exponent-to-mantissa ratio or simply the total bit count drives the FP6 advantage — this would provide more insight into whether FP6 with a different bit allocation could achieve even better results; (5) Evaluation at lower precision for FP6 (e.g., testing FP6 with 2+4 split versus 4+2 split) to verify that the specific bit decomposition doesn't affect model quality.

**Genuine weaknesses:** The paper's difficulty-estimation overhead problem (from the reference example) has a direct analog here: the paper does not account for the cost of determining whether FP6 or INT4 is appropriate for a given model and task — a practitioner would need to run the same generative evaluations to discover that INT4 degrades their specific use case. The paper's recommendation to use FP6 is based on empirical evidence that it works across the tested configurations, but without a theory of when FP6 is sufficient (e.g., a relationship between model size, task type, and required mantissa bits), the advice is "trust but verify" rather than predictive. Additionally, the FP6 kernel is a research implementation, not a production-hardened library — the latency numbers in Figure 2 may not reflect the performance achievable after integration into serving frameworks with overhead from memory allocation, multi-GPU communication, or mixed-precision attention kernels. Finally, the sample sizes for code generation (500 test cases from HumanEval-X, 8+ repeated experiments) and summarization (standard test sets) are standard for the field but small enough that the FP6-FP16 gaps of <0.5 points should not be overinterpreted as proof of exact equivalence — they are consistent with equivalence within statistical noise, but larger-scale replication would provide more confidence.

**Conditional nature of the claims:** The paper's claim that FP6 "performs robustly across various algorithms and tasks" holds under the specific conditions tested: (1) weight-only quantization with FP16 activations (W6A16), (2) LLM feed-forward layers during autoregressive decoding, (3) models from 406M to 65B parameters of the LLaMA, StarCoder, and BART families, (4) Python and JavaScript code generation and English news summarization tasks, (5) round-to-nearest quantization with per-row or per-128/256-element scaling. Whether FP6 remains the "sweet spot" when activations are also quantized (W6A6 or W6A8), when applied to smaller models (<100M) or larger models (>175B), when tested on multilingual generation, or when evaluated with more sophisticated quantization algorithms (AWQ, QuIP) is not addressed. The paper's system claim about latency is specific to the A100 GPU — performance on H100, consumer GPUs, or inference accelerators with different memory subsystems may differ.

## 6. Limitations and Trade-offs

### 6.1 The System Evaluation Is Limited to Individual FFN Kernels, Not End-to-End Inference

**The assumption or constraint.** The paper's headline system claim — that FP6 with bias shift "achieves similar latency to the state-of-the-art INT4 fine-grain quantization" (Abstract) — is supported exclusively by kernel-level microbenchmarks on individual feed-forward layers during the token generation phase. Section 5.3 explicitly states this scope: "Our primary focus was on the performance of feed-forward (FFN) layers within the LLaMA models, specifically during the token generation phase." The evaluation measures the latency of a single matrix multiplication (one FFN layer) in isolation, not the end-to-end latency of generating a complete token through an entire transformer model. The paper acknowledges this limitation directly: "Figure 2 provides only a snapshot of key outcomes, with a comprehensive system implementation and detailed performance analysis reserved for future work."

**The consequence.** Kernel-level speedups do not translate linearly to end-to-end inference speedups, for several reasons specific to this paper's design. First, the 4+2 data layout stores each FP6 weight in two separate memory arrays (a 4-bit array and a 2-bit array), requiring two memory loads per weight rather than one. In the isolated FFN kernel, these loads can be overlapped or amortized over the matrix multiply computation, but in a full model stack, the aggregate memory traffic may interact differently with GPU cache hierarchies, memory controller contention, and the prefetch patterns of surrounding operations (attention, layer norm, residual connections). Second, the FFN kernels account for only a fraction of total inference latency — attention projections, embedding lookups, and cross-layer data movement also contribute, and these operations have different compute-to-memory ratios that may benefit differently from 6-bit versus 4-bit compression. Third, a complete inference engine must manage the memory footprint of both the 4-bit and 2-bit arrays alongside KV-caches for ongoing sequences, and the 25% larger weight storage compared to INT4 (6 bits vs. 4 bits) may reduce the maximum batch size or sequence length before hitting GPU memory capacity limits, potentially negating per-layer latency advantages in throughput-constrained deployments.

**What evidence exists in the paper.** The only system data is Figure 2 and Table B.1, which report latency for six specific FFN matrix multiplications (FFN1 and FFN2 for LLaMA-1B/13B/65B) with batch size 8 and sequence length 1. No end-to-end model latency, throughput, or memory consumption measurements are provided. The paper does not report the memory footprint of the 4+2 layout relative to FP16 or INT4, nor does it measure how much GPU DRAM a complete quantized model occupies. The speedup numbers (1.92× average over cuBLAS, 1.06×–2.05× over INT4-FGQ for specific layer types) should be interpreted as upper bounds on what an optimized inference system might achieve, not as realized deployment gains.

**Mitigation status.** The paper is transparent that these are preliminary results and defers comprehensive system evaluation to future work. However, the abstract and introduction present the system results as a key contribution ("we propose a novel 4+2 design for FP6 to achieve similar latency to the state-of-the-art INT4 fine-grain quantization"), which could be interpreted as an end-to-end claim. A practitioner reading the abstract might reasonably expect end-to-end latency numbers for complete models, which the paper does not provide. The mitigation is therefore incomplete: the paper neither provides the end-to-end evidence nor sufficiently cautions that the kernel results may not generalize to full-model inference.

---

### 6.2 The FP6 Sweet Spot Is Validated on Only Three Task Types and Five Model Families — All in English

**The assumption or constraint.** The paper's central empirical claim — that FP6 with coarse-grain RTN matches FP16 across "a broad spectrum of generative tasks" (Abstract) — is based on evaluations restricted to: (1) Python and JavaScript code generation (HumanEval-X), with the paper noting that "other programming languages such as CPP, Go and RUST" were excluded due to "higher variance" (Table 4 caption); (2) English news summarization on CNN/DailyMail and XSum using BART-large-406M; and (3) standard zero-shot perplexity and multiple-choice benchmarks. The model families tested are LLaMA (decoder-only), StarCoder/CodeGeeX2/CodeLLaMA (decoder-only code models), and BART (encoder-decoder). The paper does not evaluate on translation, question answering with long-form generation, dialogue (beyond the inconclusive GPT-4 evaluation in Table A.1), mathematical reasoning with chain-of-thought, instruction following, or retrieval-augmented generation. All evaluation data and models are English-only.

**The consequence.** A practitioner deploying FP6 quantization in a production system cannot assume that the FP16-matching accuracy observed on Python/JavaScript code generation and English summarization will transfer to other generative tasks, languages, or model architectures. The specific concern is that generative tasks vary substantially in their sensitivity to per-token precision errors. Code generation has a strong correctness signal (unit tests) that may be robust to small weight perturbations as long as the high-level logic is preserved. Summarization relies on content selection and paraphrasing, which may tolerate minor token probability shifts. But tasks requiring precise factual recall (long-form QA, entity-heavy generation), numerical reasoning (math word problems requiring exact calculation), or structured output (JSON generation, SQL) might be more sensitive to the 2-bit mantissa precision of FP6. The excluded programming languages (C++, Go, Rust) were dropped specifically because of evaluation instability — this instability might indicate that code generation in these languages is more sensitive to quantization error, and FP6's robustness on Python/JavaScript may not generalize.

The model architecture concern is equally important. The paper's best results are on decoder-only models (LLaMA, StarCoder) with weights quantized using per-row scaling. Encoder-decoder models like BART have different weight distributions in the encoder versus decoder, and the interaction between quantized encoder outputs and quantized decoder cross-attention weights may introduce error propagation patterns not captured by the single-model evaluation. Mixture-of-experts architectures, which concentrate knowledge in specialized feed-forward experts with potentially more extreme weight distributions, may be more sensitive to FP6's limited dynamic range (±28).

**What evidence exists in the paper.** The only evidence that FP6's advantage is task-dependent rather than universal comes from Table A.1 (GPT-4 judged chat quality), where the paper itself states "there is no clear link between bit precision and performance." This is a significant data point: on the one generative task that most closely resembles real-world LLM deployment (open-ended dialogue), FP6 does not systematically outperform INT4. The paper attributes this to evaluation variance, but the non-monotonic patterns (vicuna-7b Math: 3.6 → 2.6 → 2.2 as precision increases from INT4 to FP6 to FP16) could also indicate that FP6 introduces subtle degradations in reasoning quality that coarse-grained GPT-4 judgments cannot reliably detect. The exclusion of C++, Go, and Rust — three of the five languages in HumanEval-X — means the code generation evaluation covers 2 of 5 available languages, substantially narrowing the "broad spectrum" claim.

**Mitigation status.** The paper does not address this limitation beyond the brief acknowledgment that chat evaluation was inconclusive. There is no discussion of which task characteristics might determine FP6 sufficiency, no theoretical model relating precision to task difficulty, and no suggestion for practitioners on how to validate FP6 for their specific deployment scenario beyond running their own evaluations. The abstract and conclusion present FP6 as a general solution ("a promising solution to the current 4-bit quantization methods used in LLMs"), which overstates the breadth of evidence provided.

### 6.3 The Difficulty Estimation Analog: No Guidance on When FP6 Is Actually Necessary

**The assumption or constraint.** The paper recommends FP6 as a replacement for INT4 but provides no framework for determining, for a given model and task, whether INT4 is adequate or FP6 is necessary. The empirical results show that INT4 sometimes matches FP16 (CodeLLaMA-34B Python with FGQ achieves 46.88 vs. 43.22, actually exceeding baseline; LLaMA-65B zero-shot accuracy with INT4-RTN at 71.16 vs. FP16 at 71.13), and sometimes fails badly (CodeGeeX2-6B Python with FGQ drops to 29.80 from 34.04; LLaMA-1B PTB perplexity with INT4-GPTQ explodes to 1399.89 when calibration mismatches). The paper documents this inconsistency but offers no diagnostic for predicting which regime a given deployment falls into.

**The consequence.** A practitioner who heeds the paper's recommendation and adopts FP6 will pay a 50% memory overhead compared to INT4 (6 bits vs. 4 bits per weight) and must use a custom GPU kernel rather than the mature, widely-deployed INT4 kernels available in TensorRT-LLM, vLLM, and other serving frameworks. If their specific model and task combination happens to be one where INT4 is adequate (like CodeLLaMA-34B Python), they have incurred these costs unnecessarily. Conversely, a practitioner who dismisses the paper's warning and sticks with INT4 because it worked on their zero-shot benchmarks may discover only after deployment that their model fails on the generative tasks users actually submit. Without a principled way to predict INT4 adequacy — as a function of model size, architecture, task type, and acceptable quality threshold — the deployment decision reduces to "try both and see," which is a significant practical burden given that generative evaluation (code generation with multiple random seeds, summarization with ROUGE computation) is substantially more expensive than zero-shot evaluation.

The problem is compounded by the observation that **INT4 sometimes works better than FP16** on zero-shot metrics (Table 3: LLaMA-65B INT4-RTN exceeds FP16). A practitioner who only evaluates zero-shot accuracy could reasonably conclude that INT4 provides a free lunch — better accuracy with 4× compression — and deploy it with confidence, only to discover later through user complaints that generative quality has degraded in ways zero-shot metrics didn't capture. The paper's methodological contribution is showing that this failure mode exists, but it stops short of providing the diagnostic tool that would prevent it.

**What evidence exists in the paper.** The entire experimental section is structured around documenting this inconsistency. Table 4 shows INT4-FGQ helping CodeLLaMA-34B Python (improving from 39.84 to 46.88) while hurting CodeGeeX2-6B Python (degrading from 33.08 to 29.80) — same quantization format, same task, opposite effects on different models. Tables 2 and 6 show that the performance gap between INT4 and FP16 narrows with model scale for perplexity (LLaMA-1B: 34.29 vs. 24.31, a 41% degradation; LLaMA-65B: 7.72 vs. 6.41, a 20% degradation), but the code generation results don't follow a monotonic scale trend (CodeLLaMA-34B shows smaller degradation than CodeGeeX2-6B, but StarCoder-15B sits between them with inconsistent language-dependent effects). The paper does not systematically analyze what drives these differences — whether it is model architecture, training data, weight distribution statistics, or something else entirely.

**Mitigation status.** Completely unaddressed. The paper's recommendation to use FP6 is based on the observation that FP6 works consistently across the tested configurations, not on a theory of when FP6 is necessary. The implicit argument is "FP6 is safe (always matches FP16), so use it instead of INT4 (which is sometimes unsafe)," but this dodges the cost question: FP6's system support is research-grade (custom kernel, 4+2 layout, bias shift) while INT4 has production-grade support across multiple serving frameworks. The paper does not provide the tools for a cost-benefit analysis that would let a practitioner decide whether the safety margin of FP6 over INT4 is worth the system complexity for their specific deployment.

### 6.4 The GPTQ Overfitting Diagnosis Is Not Isolated from Total Bit Width

**The assumption or constraint.** The paper attributes GPTQ's catastrophic overfitting behavior (Table 1: LLaMA-1B PTB perplexity 1399.89 when calibrated on C4) to the GPTQ algorithm itself, and uses this as motivation for preferring FP6 with RTN over INT4 with GPTQ. Specifically, Section 4 states: "GPTQ's Tendency to Overfit. Although GPTQ is innovative in post-training quantization, it tends to overfit to particular datasets, especially noticeable in its fine-grain quantization results." However, the paper does not perform the critical controlled experiment: testing whether FP6 with GPTQ also overfits when the calibration dataset is mismatched, or whether the overfitting is specific to INT4 precision rather than GPTQ as an algorithm.

**The consequence.** The paper's recommendation to use RTN rather than GPTQ is confounded with the switch from 4-bit to 6-bit precision. It is possible that GPTQ's overfitting is a consequence of working at insufficient precision (4 bits) where the Hessian-based compensation is making large, dataset-specific weight adjustments that cause distributional brittleness, and that at 6 bits, GPTQ would not overfit because the base quantization error is small enough that the compensation adjustments are minor and do not create dataset-specific artifacts. If this is the case, then the paper's argument should be "use FP6 (any algorithm)" rather than "use FP6 with RTN because GPTQ overfits." Alternatively, it is possible that GPTQ overfits regardless of precision, and even FP6-GPTQ would show calibration sensitivity — but the paper provides partial evidence against this in Table 6, where FP6-GPTQ-CGQ and FP6-RTN-CGQ produce identical perplexity for LLaMA-65B. However, this is on the largest model where overfitting was already minimal even for INT4, and the table does not test FP6-GPTQ with mismatched calibration datasets (e.g., evaluate PTB perplexity for FP6-GPTQ calibrated on C4). Without that controlled experiment, we cannot determine whether the overfitting is fundamentally a GPTQ problem or an INT4-under-GPTQ problem.

The practical consequence is that a practitioner who believes GPTQ is fundamentally flawed may avoid it even when using FP6, missing potential accuracy improvements from the Hessian-based error compensation. Conversely, a practitioner who believes GPTQ is safe at higher precision may deploy FP6-GPTQ with a specific calibration dataset, and discover only later that it still overfits (though perhaps less catastrophically than INT4-GPTQ) when input distributions shift.

**What evidence exists in the paper.** Table 6 provides partial evidence: for LLaMA-65B, FP6-GPTQ-CGQ and FP6-RTN-CGQ both achieve 6.42 Wikitext2 perplexity, suggesting GPTQ provides no benefit (and thus no risk of overfitting-related harm) at this precision and scale. But for LLaMA-1B, FP6-GPTQ-CGQ (23.58) slightly outperforms FP6-RTN-CGQ (24.83) — a 1.25 point perplexity improvement — suggesting GPTQ is doing non-trivial compensation even at 6 bits for smaller models, and the overfitting risk might persist. The paper does not report FP6-GPTQ with mismatched calibration, so we cannot assess whether the 1.25 point improvement on Wikitext2 comes at the cost of degradation on other datasets (the overfitting pattern). Additionally, the paper's primary generative task results (Tables 4 and 5) use only RTN for INT4/FP5/FP6, with the stated justification that "GPTQ tends to overfit to the calibrated dataset and poses implementation challenges, leading us to solely utilize RTN for our evaluations." This means the paper's central claim — FP6 outperforms INT4 on generative tasks — is a comparison of FP6-RTN against INT4-RTN, not FP6-RTN against INT4-GPTQ. A fairer comparison would include INT4-GPTQ on these tasks (accepting the risk of implementation challenges) to determine whether GPTQ can rescue INT4 on generation, potentially narrowing or eliminating the FP6 advantage.

**Mitigation status.** Not addressed. The paper does not acknowledge this confounding, does not run the missing controlled experiments, and does not qualify its recommendation against GPTQ as conditional on the precision regime. The statement about GPTQ overfitting is presented as a property of the algorithm, not as a property of the algorithm when applied at 4-bit precision.

### 6.5 The 4+2 Data Layout and Bias Shift Are Specific to FP6E3M2 on A100 — Generalization to Other Formats and Hardware Is Unverified

**The assumption or constraint.** The system innovations — the 4+2 decomposition and the bias shift technique — are designed specifically for the FP6E3M2 format (3 exponent bits, 2 mantissa bits) and evaluated exclusively on the NVIDIA A100 GPU. The 4+2 split works because the FP6 format cleanly divides into a 4-bit sign+exponent portion and a 2-bit mantissa portion. The bias shift works because the exponent bias difference (15 − 3 = 12) can be absorbed into a per-row scaling factor that remains FP16-representable when multiplied by 2¹². Both properties are format-specific and hardware-specific.

**The consequence.** If future work identifies that a different 6-bit floating-point format (e.g., FP6E4M1 or FP6E2M3) provides better accuracy, the 4+2 split may no longer align with the format's natural bit boundaries — an E4M1 format would require a 5+1 split (sign+4-bit exponent = 5 bits, 1-bit mantissa), putting 5 bits in the first sub-number, which is not a power-of-2 width and would reintroduce the odd-bit loading problem the 4+2 design was meant to solve. The bias shift technique would still work for any format with the same bias difference, but the specific constant (2¹², derived from 15 − 3 = 12) would change if the FP6 exponent bias or FP16 bias were different.

The hardware generalization concern is more acute. The paper evaluates only on A100 (compute capability 8.0), which has specific properties for memory bandwidth, cache sizes, and tensor core throughput. Consumer GPUs (RTX series), datacenter GPUs from other vendors (AMD MI series), inference accelerators (Google TPU, AWS Inferentia), and mobile/edge GPUs have fundamentally different memory subsystems, instruction sets, and tensor core capabilities. The 4+2 design requires simultaneous loads from two memory arrays, which assumes sufficient memory bandwidth and load/store units to issue and retire these parallel requests without contention. On hardware with fewer memory channels or lower bandwidth, the dual-load pattern might serialize, eliminating the advantage over the standard "pack into 32-bit words and extract" approach. The bias shift assumes that the FP16 multiplication by the pre-scaled factor is fast relative to the eliminated exponent addition — this is true on A100's tensor cores but may not hold on hardware that lacks fused multiply-add for FP16 or has different relative costs for integer bit manipulation versus floating-point multiplication.

**What evidence exists in the paper.** None. The paper provides no evaluation on any hardware platform other than A100, no discussion of how the 4+2 layout would need to change for different FP6 format variants, and no analysis of the memory access pattern's dependence on hardware memory architecture. The kernel implementation is described only at the conceptual level (Figure 1), with no discussion of GPU-specific optimizations like shared memory usage, register blocking, or instruction-level parallelism that might be necessary to port the design to other architectures.

**Mitigation status.** The paper acknowledges this implicitly by stating that the system evaluation is preliminary ("Figure 2 provides only a snapshot of key outcomes"). However, the paper does not qualify its system claims as A100-specific, and the "4+2" design is presented as a general solution to odd-bit precision rather than a format-and-hardware-specific technique. A practitioner deploying on H100 (which has different tensor core capabilities and memory bandwidth) or on inference-specific hardware would need to reimplement and re-evaluate the kernel from scratch, with no guarantee that the 1.92× cuBLAS speedup transfers.

### 6.6 No Accounting for the Memory Capacity Trade-off: FP6 Stores 50% More Data Than INT4

**The assumption or constraint.** The paper frames FP6 as a drop-in replacement for INT4, emphasizing latency competitiveness while not discussing the memory capacity implications of storing 6 bits per weight rather than 4. For a model with P parameters, INT4 weight-only quantization requires approximately P/2 bytes of GPU memory (4 bits per weight, plus scaling factor overhead). FP6 with the 4+2 layout requires approximately 3P/4 bytes of GPU memory (6 bits per weight, stored as separate 4-bit and 2-bit arrays, plus scaling factors). This is a 50% increase in weight memory footprint, or equivalently, FP6 provides 25% less compression than INT4 relative to FP16 (6/16 = 37.5% of original vs. 4/16 = 25%).

**The consequence.** For many LLM deployment scenarios, GPU memory capacity — not per-layer latency — is the binding constraint. A practitioner with a fixed GPU memory budget (e.g., a single A100-40GB) who needs to serve a specific model may find that INT4 fits in memory while FP6 does not, regardless of FP6's per-layer speed advantage. Even when both fit, the 50% larger weight footprint of FP6 reduces the memory available for the KV-cache (which stores attention keys and values for all previous tokens in ongoing conversations). With less KV-cache capacity, the maximum batch size decreases, which may reduce overall throughput (tokens per second across all concurrent requests) even if per-token latency is lower. In a high-throughput serving setting where the system is batch-size-bound rather than latency-bound, INT4's memory savings could enable larger batches that more than compensate for its slightly higher per-layer latency.

The specific concern is that the paper's latency comparison (1.06×–2.05× over INT4-FGQ for specific FFN layers) does not account for the possibility that INT4's smaller memory footprint allows a batch size that is 50% larger (or more, since the KV-cache often dominates memory for long sequences), which would improve throughput by a factor greater than FP6's per-layer speedup. The paper's batch size is fixed at 8 throughout the system evaluation, so this trade-off is not explored.

**What evidence exists in the paper.** None directly. The paper does not report the total GPU memory consumption for any quantized model, does not compare maximum batch sizes achievable with FP6 versus INT4, and does not discuss the memory capacity-latency trade-off. The focus is exclusively on kernel latency at a fixed batch size of 8. Table B.1 shows the weight shapes (e.g., LLaMA-65B FFN1: 22016×8192 = 180M weights) but does not translate these to memory footprints. The paper inherits the field's default assumption that LLM inference is bandwidth-constrained rather than capacity-constrained, but this assumption breaks precisely in the regime where practitioners are choosing between 4-bit and 6-bit quantization: if the model already fits comfortably in memory at FP16, there is less motivation to quantize at all; the quantization decision is most consequential when memory is tight.

**Mitigation status.** Not addressed. This is a significant omission for a paper that positions FP6 as a replacement for INT4 in production deployments. A complete deployment recommendation would include a memory capacity analysis showing under what conditions FP6's latency advantage outweighs its memory cost, and under what conditions INT4's memory savings make it preferable despite slightly higher per-layer latency. The paper does not provide this analysis, nor does it acknowledge the trade-off as a limitation.
