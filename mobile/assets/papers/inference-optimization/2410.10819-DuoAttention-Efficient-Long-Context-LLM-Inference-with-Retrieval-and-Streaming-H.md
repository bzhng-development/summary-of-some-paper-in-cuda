## 1. Executive Summary

This paper introduces **DuoAttention**, a framework that reduces the memory and latency of long-context LLM inference by categorizing attention heads into two types—**Retrieval Heads** (a small fraction that require full attention across all tokens to capture contextually relevant information) and **Streaming Heads** (the majority, which focus only on recent tokens and attention sinks and can operate with a constant-length KV cache). Evaluated on Llama-2 and Llama-3 models across Needle-in-a-Haystack, LongBench, MMLU, MBPP, and MT-Bench, DuoAttention uses a lightweight optimization-based procedure with synthetic passkey-retrieval data to identify retrieval heads by directly measuring output deviation under KV cache compression, achieving memory reductions of up to 2.55× for MHA and 1.67× for GQA models, decoding speedups of up to 2.18× and 1.50×, and pre-filling accelerations of up to 1.73× and 1.63×, respectively, with minimal accuracy loss. When combined with 8-bit weight and 4-bit KV cache quantization, DuoAttention enables a Llama-3-8B model to accommodate 3.3 million tokens on a single A100 GPU—a 6.4× capacity increase over full-attention FP16 deployment—establishing that long-context capabilities can be preserved under aggressive KV cache compression only when the fraction of heads identified as retrieval heads is protected from token pruning.

## 2. Context and Motivation

### The Core Problem: KV Cache Memory Is the Bottleneck for Long-Context LLMs

The central issue DuoAttention tackles is the **exponential growth of memory and computational cost** when deploying LLMs on sequences with very long contexts — think hundreds of thousands or even millions of tokens. This is not a niche concern. Modern applications routinely demand such lengths: summarizing a book series like Harry Potter (~1M tokens), processing hour-long videos (a 3-minute video at 24 FPS generates ~1.1M tokens in vision-language models), or maintaining coherent multi-turn dialogues over hundreds of exchanges. Yet the standard Transformer attention mechanism, which computes pairwise interactions between every token and every preceding token, imposes two hard scaling penalties:

1.  **The KV Cache memory bottleneck.** To avoid recomputing keys and values for all prior tokens at each decoding step, LLMs cache the Key and Value states of every token in every attention head. This KV cache grows **linearly with sequence length** and **multiplied by the number of layers and heads**. The paper provides a concrete, sobering number: serving the Llama-3-8B model with FP16 KV cache on a 1-million-token context requires over **137 GB of memory**, which exceeds the 80 GB capacity of a single state-of-the-art A100 GPU. The memory wall is the primary obstacle.

2.  **Decoding and pre-filling latency.** Decoding latency increases linearly with context length because each new token must attend to the entire KV cache. Pre-filling latency is worse — it scales **quadratically** with sequence length, since every token in the prompt attends to every token before it. For extremely long prompts, the time to pre-fill the KV cache before generating a single word can become prohibitive.

The paper argues that this is the fundamental deployment challenge for long-context LLMs: the computational model that gives Transformers their power is also what makes them infeasible at scale without optimization. The problem is not just one of model capability (many models *can* process long contexts if given enough hardware), but of **practical resource constraints** on real-world accelerators.

### Why Existing Solutions Fall Short

The paper identifies four broad classes of prior work aimed at taming the KV cache and attention costs, and systematically explains why each is insufficient for the long-context inference problem *as a whole*.

**Architectural modifications (MQA, GQA) don't reduce compute, only memory.** Multi-Query Attention (MQA) and Grouped-Query Attention (GQA) share KV heads across multiple query heads, shrinking the KV cache size substantially. This is why DuoAttention's relative memory reduction is smaller for GQA (1.67×) than for MHA (2.55×) — GQA already compressed the cache. However, the paper points out that these are **training-time architectural choices**. An already-trained model cannot benefit from them without retraining, and more critically, they **do not reduce the computational cost of the attention operation itself**. The number of scalar attention computations (query-key dot products) is unchanged. For very long sequences, this means memory pressure is eased but latency is not.

**Linear attention methods sacrifice long-context accuracy.** Approaches like Mamba and other state-space models remove the quadratic attention operation entirely, replacing it with recurrent or convolutional primitives that have constant per-step state. While they achieve linear scaling, the paper states they "often underperform in long-context scenarios compared to Transformer models." This is an empirical trade-off: the simplified architecture cannot match the exact retrieval fidelity of full attention on tasks requiring precise look-up of distant information, like needle-in-a-haystack retrieval.

**Approximate attention (token eviction) breaks long-context capabilities.** This is the most directly comparable class of prior work, and the paper's strongest criticism is reserved here. Methods like **H2O**, **StreamingLLM**, **TOVA**, and **FastGen** all attempt to keep the KV cache size bounded by *selectively discarding KV states* for tokens deemed less important.

-   **H2O** evicts tokens based on accumulated attention scores, keeping "heavy hitters."
-   **StreamingLLM** identifies "attention sinks" (the first few tokens that absorb disproportionate attention) and keeps them along with recent tokens.
-   **TOVA** uses a token-eviction policy based on attention to the last token.
-   **FastGen** profiles individual attention heads to determine which tokens each head can discard.

The paper's central empirical claim is that these methods **fundamentally damage the model's long-context retrieval ability**. As shown in Figure 6, on the Needle-in-a-Haystack benchmark, these methods "fail to retrieve correct answers from the various depths of the long sequence, as they discard the KV cache containing the necessary information during generation." The critical, subtle reason is that these methods apply token dropping **uniformly or heuristically**, without recognizing that some attention heads are performing a fundamentally different operation — *retrieval* — that loses essential information when any middle token is discarded. By pruning from all heads indiscriminately, they inevitably discard the specific token states that retrieval heads need to answer queries about the distant past.

Additionally, the paper notes two practical flaws: these eviction-based methods are often **incompatible with FlashAttention** during pre-filling (because attention scores are never materialized, making token selection impossible without expensive re-computation), and they **cannot reduce pre-filling costs** at all — the full quadratic attention computation must still be performed on the original prompt before any tokens can be evicted.

**KV cache quantization is complementary but insufficient alone.** Quantizing KV caches to 4 or 8 bits reduces memory footprint but does not touch the computational cost of the attention operations themselves. The paper explicitly treats quantization as an *orthogonal, complementary* technique rather than a competing one, demonstrating that DuoAttention can be combined with quantization to push capacity even further (to 3.3M tokens on a single GPU). Quantization shrinks the size of each cached element but does not reduce the *number* of elements stored or the number of attention computations performed.

**System-level optimizations don't reduce the fundamental workload.** FlashAttention and its successors (FlashAttention-2, FlashDecoding) exploit GPU memory hierarchy and parallelism to make exact attention faster and more memory-efficient, but they still compute **all** pairwise attention scores. PagedAttention improves memory management by eliminating fragmentation but does not reduce the total KV cache size. RingAttention distributes computation across devices but doesn't reduce the aggregate FLOPs or memory. These are all implementation-level wins, not algorithmic reductions in the amount of computation and storage required.

### How DuoAttention Positions Itself: A Head-Aware, Optimization-Based Framework

DuoAttention's central conceptual move is to reject the premise that KV cache compression should be applied uniformly. Instead, it builds on the observation that attention heads are **functionally specialized**, a finding emerging from mechanistic interpretability work (referencing Wu et al., 2024, which introduced the term "retrieval heads").

The paper positions its approach along two key dimensions that distinguish it from prior work:

**1. Precision of identification: optimization-based over heuristic profiling.** Prior work that *did* distinguish heads (FastGen, RazorAttention) relied on **profiling attention score patterns** to classify heads. For example, if a head's attention distribution is concentrated on recent tokens, it's classified as a local/streaming head; if it shows peaks at distant tokens, it's a retrieval head. The paper argues this is fundamentally limited because it ignores the **end-to-end impact** of compressing that head — attention scores alone do not capture (a) the role of value states (a head might attend broadly but with low-magnitude values, making the attended tokens unimportant), and (b) the variability of attention distributions across different inputs and layers. Section 3.5 quantifies this: attention-profiling-based identification significantly underperforms the proposed optimization approach (Figure 13, panel 1).

Instead, DuoAttention uses a **lightweight optimization procedure with synthetic data** that directly measures the **output deviation** caused by restricting a head to streaming attention. By assigning a continuous gate value $\alpha_{i,j} \in [0,1]$ to each head, optimizing these gates to minimize the L2 distance between the full-attention model's final hidden states and the mixed-attention model's final hidden states (with an L1 sparsity penalty), and then binarizing at a threshold, the method identifies heads whose compression causes measurable harm to the model's output. The paper emphasizes the synthetic data design: unlike natural language modeling, where supervision signals that require long-context reasoning are sparse, a passkey-retrieval dataset forces the model to depend on distant context for every output token, making the distillation loss on passkey tokens a direct signal of head importance for retrieval.

**2. Scope of optimization: both decoding and pre-filling.** Unlike token-eviction methods (which only operate during decoding, after the full KV cache is built during pre-filling), DuoAttention's streaming head design applies during pre-filling as well. Because the streaming heads are defined by a pattern (sink tokens + recent tokens only), pre-filling for streaming heads can be performed with **chunked pre-filling** where each chunk attends only to a constant number of prior tokens (the sinks and the local window). This reduces pre-filling complexity from $O(L^2)$ to $O(LK)$, where $K$ is the chunk size, and reduces peak memory from $O(L)$ to $O(K)$. This is a significant practical advantage not available to prior KV cache compression methods.

**3. Practical deployment simplicity.** The paper stresses that DuoAttention is designed to be "a general, straightforward, and easily integrated approach." The optimization phase is efficient: only a few thousand scalar gate parameters are trained, the LLM's weights remain frozen, and the entire identification process completes in "several hours on an 8 GPU node." At deployment time, the heads are simply partitioned — full attention for retrieval heads, streaming attention for streaming heads — with no per-token decision-making, no dynamic eviction policies, and no specialized custom GPU kernels required beyond existing FlashAttention implementations.

The paper thus frames itself not as a brand-new model architecture or an incremental improvement on token eviction, but as a **framework that correctly identifies the minimal set of attention heads that must be protected from compression to preserve long-context capabilities**, and then compresses everything else aggressively. This is a conceptually different approach from prior work: rather than asking "which tokens can I drop?", it asks "which *heads* can I drop tokens from?" — and uses an optimization procedure grounded in output-level consequences to answer that question.

## 3. Technical Approach

### 3.1 Reader Orientation

DuoAttention is a **deployment-time framework** that modifies how an already-trained LLM computes attention — it does not change model weights or require retraining. It solves the problem of excessive memory and latency during long-context inference by **selectively compressing the KV cache per attention head**: a small fraction of heads (retrieval heads) keep the full KV cache for all tokens, while the majority (streaming heads) store only a constant number of tokens (attention sinks plus recent tokens). The "shape" of the solution is a two-phase process: first, an optimization-based identification phase determines which heads are retrieval heads using synthetic data and a lightweight training procedure; second, at deployment, the model's attention computation is split into two parallel tracks per layer — full attention for retrieval heads, constant-length streaming attention for streaming heads — reducing memory from `$O(L)$` to approximately `$O(rL + (1-r)C)$` where `$r$` is the retrieval head ratio and `$C$` is a small constant.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has four major components, divided across two phases:

**Phase 1: Retrieval Head Identification (offline, one-time per model)**

1.  **Synthetic Dataset Generator**: Creates passkey-retrieval training samples by embedding ten 32-word passkeys at random positions within long documents from the BookSum dataset. The model must recall these passkeys at the end of the context. This ensures every supervision signal depends on long-context retrieval.
2.  **Gate-Controlled Mixed Attention Module**: A modified forward pass where each attention head produces a weighted blend of full attention and streaming attention, controlled by a scalar gate value `$\alpha_{i,j} \in [0,1]$`. Only these gate values are trainable; all model weights are frozen.
3.  **Optimizer and Loss Function**: An AdamW optimizer trains the gate values to minimize a combined loss — an L2 distillation loss between the full-attention model's final hidden states and the mixed-attention model's hidden states (computed only on the passkey tokens), plus an L1 regularization penalty encouraging gate values toward zero. The regularization strength is controlled by hyperparameter `$\lambda = 0.05$`.

Output of Phase 1: a gate value `$\alpha_{i,j}$` for every KV head `$j$` in every layer `$i$`.

**Phase 2: Deployment Inference (runtime)**

4.  **Binarized Attention Executor**: Before inference, the model's Q, K, V projection weight matrices are reordered so that retrieval heads and streaming heads form contiguous blocks. At runtime, each layer maintains **two separate KV caches**: a full-length cache for retrieval heads (growing with sequence length) and a constant-length cache for streaming heads (storing only sink tokens and recent tokens). When a new token arrives, its query, key, and value vectors are split along the head dimension — the retrieval-head portion computes standard causal attention against the full cache, the streaming-head portion computes attention against only sinks and recent tokens, and the outputs are concatenated before the output projection.

Information flows: prompt token `$\rightarrow$` layer's Q/K/V projections `$\rightarrow$` split by head type `$\rightarrow$` two attention computations `$\rightarrow$` concatenation `$\rightarrow$` output projection `$\rightarrow$` next layer. During pre-filling, this is done in chunks to bound peak memory.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems and methods paper** whose core idea is that attention heads in LLMs can be partitioned into retrieval-critical and retrieval-agnostic categories using an output-aware optimization procedure, and that protecting only the former from KV cache compression yields substantial efficiency gains with near-lossless accuracy.

#### 3.4.1 Formal Definition of Retrieval Heads: Output Deviation as the Criterion

The paper opens Section 2.2 by establishing a concrete, quantifiable definition that distinguishes retrieval heads from streaming heads. This definition is the theoretical anchor for the entire method and represents a deliberate departure from prior work.

**The definition (paraphrased):** A "retrieval head" is an attention head that, *when restricted to attending only to attention sinks and recent tokens (i.e., when operated as a streaming head), causes a significant alteration in the model's final output.*

The paper explicitly states:
> "significantly alter model outputs when restricted to recent tokens and attention sinks."

This definition is **output-aware** and **end-to-end**. It does not ask what the attention pattern looks like (e.g., whether the head's attention scores peak at distant tokens), but rather what happens to the model's final hidden states when the KV cache for that head is compressed. The paper justifies this choice by identifying three limitations of prior attention-pattern-based approaches (such as FastGen and RazorAttention, which profile attention score distributions):

1.  **Attention scores ignore value states.** A head might show high attention to a distant token, but if the value vector at that position has near-zero magnitude or encodes irrelevant information, discarding that token has negligible end-to-end impact. Conversely, a head with moderate but broad attention might encode critical information in its value states that would be lost by dropping middle tokens.
2.  **Attention patterns do not capture the end-to-end impact of compression.** The effect of dropping tokens in one head propagates through all subsequent layers. A head might have a locally small attention deviation but be part of a circuit where precision matters downstream.
3.  **Attention distributions vary across layers and input types.** A head classified as "local" on one prompt might become "retrieval" on another. Profiling on a few samples may not capture the head's true functional role.

By defining retrieval heads in terms of output deviation under compression, DuoAttention directly measures the quantity that matters for deployment: *if I compress this head, does the model's answer change?* This is a causal operationalization rather than a correlational one.

The paper also notes a practical definition for GQA models: "in models using GQA, one KV head can be associated with multiple attention heads, and our method accounts for the KV cache compression of an entire group of attention heads." That is, the gate value is assigned per KV head (not per query head), so all query heads sharing a KV head are compressed or retained together. This is both a practical necessity (the KV cache is the shared resource being compressed) and an appropriate granularity because the KV head is the unit of memory savings.

#### 3.4.2 Gate-Controlled Mixed Attention and the Optimization-Based Identification Procedure

The identification procedure is a **lightweight optimization** that trains a small number of scalar parameters to minimize output deviation while encouraging sparsity. The full LLM weights remain frozen. This section explains the forward pass modification, the optimization setup, and the synthetic dataset design.

##### The Gate Mechanism During Training

For each KV head `$j$` in layer `$i$`, a trainable gate value `$\alpha_{i,j}$` is introduced. During the identification phase, the attention output for that head is computed as a **continuous blend** of full attention and streaming attention, weighted by `$\alpha_{i,j}$`:

$$\text{attn}_{i,j} = \alpha_{i,j} \cdot \text{full\_attn} + (1 - \alpha_{i,j}) \cdot \text{streaming\_attn}$$

where:
- `$\alpha_{i,j} \in [0,1]$` is the gate value for the j-th KV head in layer i. It is initialized to 1 (all heads start as retrieval heads).
- `$\text{full\_attn}$` is the standard causal self-attention output: `$\text{softmax}(QK^T \odot M_{\text{causal}})V$`.
- `$\text{streaming\_attn}$` is the attention output when the head is restricted to attending only to attention sinks and recent tokens: `$\text{softmax}(QK^T \odot M_{\text{streaming}})V$`.
- `$M_{\text{causal}}$` is the standard lower-triangular causal mask.
- `$M_{\text{streaming}}$` is a "Λ-like mask" that allows attention to only the initial tokens (sinks) and the most recent tokens, with masked-out positions set to `$-\infty$` before the softmax. The paper references Han et al. (2023) and Xiao et al. (2023b) for this mask shape.

**What this equation computes:** for each head, it produces an attention output that is an interpolation between the full-context version and the streaming version. When `$\alpha = 1$`, the head behaves exactly as full attention (all tokens attended). When `$\alpha = 0$`, the head is purely a streaming head (only sinks and recent tokens). Intermediate values produce a weighted average of the two attention output tensors.

**Why this form:** the continuous relaxation is essential for gradient-based optimization. A hard binary choice (full vs. streaming) is non-differentiable. The gate values provide a differentiable path from the full-attention regime to the streaming regime, allowing the optimizer to assess the marginal impact of compressing each head. This technique is directly inspired by network slimming in CNN filter pruning (Liu et al., 2017), where trainable scaling factors on batch normalization layers are regularized to identify unimportant channels.

##### Optimization Setup: What Is Trained and What Is Frozen

The paper emphasizes the efficiency of the procedure:

- **Total trainable parameters**: only `$N \times H$` scalar values, where `$N$` is the number of layers and `$H$` is the number of KV heads. For a Llama-2-7B model with 32 layers and 32 KV heads (MHA), this is `$32 \times 32 = 1024$` parameters. For a Llama-3-8B model with 32 layers and 8 KV heads (GQA), this is `$32 \times 8 = 256$` parameters. The paper notes this is "only thousands of floating-point numbers."
- **All LLM parameters are frozen**, meaning the model's original capabilities are preserved — this is not fine-tuning that risks catastrophic forgetting.
- **Optimizer**: AdamW, with a learning rate schedule: start at 0.02, warm up from 0.002 in the first 400 steps, and reduce back to 0.002 in the final 400 steps. Total training: 2000 steps. (The learning rate is unusually high because the parameters are simple scalars with no complex interactions.)
- **Batch size**: 1 (because each training sample is a very long sequence — up to 32K tokens).
- **Hardware and time**: "all training experiments in our paper can be conducted on 8×NVIDIA A100 GPU servers" and completes in "several hours."

The use of a batch size of 1 deserves explanation. Each training sample consists of a full-length document (up to the model's maximum context length, e.g., 32K tokens for Llama-2-7B-32K-Instruct) with embedded passkeys. Processing a single such sample already saturates GPU memory on an 80GB A100. Distributed training with DeepSpeed Ulysses sequence parallelism is used to shard the long sequence across multiple GPUs, as noted in Appendix A.1.

##### Training Procedure: What Happens Step by Step

1.  **Initialize**: all gate values `$\alpha_{i,j} = 1$` for all heads in all layers. This means the model initially computes exactly full attention (since `$1 \cdot \text{full\_attn} + 0 \cdot \text{streaming\_attn} = \text{full\_attn}$`). The starting state is zero compression.
2.  **Sample a training data point**: draw a passkey-retrieval sample. A document from the BookSum dataset is taken, and ten 32-word passkeys are embedded at ten random positions. The document length is drawn from 50 intervals ranging from 1000 tokens up to the model's maximum sequence length (4096 for Llama-2-7B-chat, 32000 for Llama-3-8B-Instruct-Gradient-1048K, etc., as detailed in Table 2).
3.  **Forward pass with the full-attention model**: compute the final hidden states `$H_{\text{full}}$` for the entire sequence using standard full attention. This is the "teacher" output.
4.  **Forward pass with the mixed-attention model**: compute the final hidden states `$H_{\text{mixed}}$` for the same sequence using the current gate values, where each head's attention is the weighted blend.
5.  **Compute the loss**: the distillation loss is computed only on the last `$l$` tokens of the sequence (the passkey answer tokens). The regularization loss is computed across all gate values.
6.  **Backward pass and update**: only the gate values `$\alpha_{i,j}$` receive gradient updates. The L1 regularization term pushes gate values toward zero, while the distillation term pushes them toward whatever values minimize output deviation. Heads that are truly unimportant for retrieval can have their gate values driven to near-zero because the streaming attention output is almost identical to the full attention output, so the distillation loss provides little counter-pressure against the L1 penalty. Heads that are critical for retrieval have their gate values remain high because the streaming attention output differs significantly from the full attention output, causing large distillation loss that outweighs the L1 penalty.
7.  **Repeat for 2000 steps.**

At convergence, the gate values form a distribution, visualized in Figure 4 for four different models. The paper notes that MHA models (Llama-2-7B) have a lower ratio of high gate values (retrieval heads) compared to GQA models (Llama-3, Mistral). This is because GQA already shares KV heads, so each KV head carries more responsibility — compressing one KV head in GQA affects multiple query heads, amplifying the output deviation, so fewer heads can be safely compressed.

#### 3.4.3 The Synthetic Passkey-Retrieval Dataset and Why It Is Essential

The paper makes a strong claim that natural language modeling data is insufficient for identifying retrieval heads. The reasoning is subtle and important:

> "relying solely on natural language modeling objectives is insufficient for identifying retrieval heads because the supervision signal in natural text that requires inference over long spans is sparse, and most tokens can be inferred using local context."

In plain language: in a typical long document, most next-token predictions can be made accurately using only the last few sentences. A head that is critical for retrieving information from 10,000 tokens ago would show no output deviation under streaming attention on most tokens, because most tokens simply don't need that information. The distillation loss on natural text would be dominated by local-context tokens, providing almost no signal about which heads are important for long-range retrieval.

**The synthetic dataset construction** (Figure 3):

1.  **Source documents**: The BookSum dataset, which contains long-form narrative texts (full books).
2.  **Passkey generation**: Ten passkeys are randomly generated, each consisting of `$s = 32$` words. These are sequences of random words (e.g., "lima zulu … golf papa") that have no semantic relation to the surrounding text, ensuring the model cannot guess them from context.
3.  **Passkey embedding**: Each of the ten passkeys is inserted at a random position within the long document. The insertion points are sampled from 1000 possible locations within the context. This ensures that the passkeys are scattered throughout the document, not clustered at the beginning or end.
4.  **Query formulation**: At the end of the context, a question asks the model to recall all ten passkeys in order: "Based on the content of the book, what are the passkeys to the vault?" followed by the expected answer format: "First Passkey: [words] … Tenth Passkey: [words]."
5.  **Training samples**: 50 length intervals are used, from 1000 tokens up to the model's maximum sequence length. For each interval, documents are padded or truncated to that length, and passkeys are inserted at random positions. This ensures the model sees a wide range of context lengths and passkey positions during training.
6.  **Distillation loss computation**: The L2 distillation loss is computed **only on the final `$l$` tokens**, which correspond to the passkey words in the answer. This means every single element of the loss is a direct measurement of whether compressing a head damaged the model's ability to retrieve and reproduce a passkey.

**Why synthetic over natural data (design choice justification):**

- **Density of supervision signal**: In natural language, perhaps 1% of tokens require long-range retrieval. In the synthetic dataset, 100% of the tokens used for the loss (the passkey recall answers) require long-range retrieval. This makes the training signal far more efficient — every gradient update is directly informative about retrieval capability.
- **Control over difficulty**: By varying the number of passkeys, their length, and their positions within the context, the difficulty of the retrieval task can be precisely controlled. The paper uses ten 32-word passkeys, which is challenging enough that the model cannot trivially memorize them all from local context but feasible enough that the full-attention model succeeds.
- **Elimination of confounding factors**: In natural text, a head might show output deviation because it's important for some function other than retrieval (e.g., syntactic parsing, local coherence). The synthetic dataset isolates retrieval specifically: the only way to correctly output the passkey words is to have retrieved them from the distant context. This yields a cleaner separation of retrieval-relevant vs. retrieval-irrelevant heads.
- **Generalizability evidence**: Even though the identification procedure uses synthetic passkey data, the resulting head classification transfers to natural long-context tasks (LongBench, Figure 7) and short-context tasks (MMLU, MBPP, Figure 8). This is because the heads that are important for artificial passkey retrieval are also the heads that the model uses for natural long-range information lookup.

**Ablation evidence for synthetic data (Figure 13, panel 1):** The paper compares optimization with synthetic passkey data against optimization with language modeling (computing loss on all tokens of natural text). The passkey-based method "produces significantly better results" — the optimization with language modeling fails to correctly identify which heads are retrieval-critical because the loss signal is dominated by local-context predictions.

#### 3.4.4 The Training Loss Functions in Detail

The training objective combines two terms: a distillation loss that preserves model output quality and a sparsity regularization term that encourages gate values toward zero.

##### Distillation Loss

$$\mathcal{L}_{\text{distill}} = \frac{1}{N} \sum_{i=1}^{N} \sum_{j=T-l+1}^{T} \left( H^{(i)}_{\text{full}}[j] - H^{(i)}_{\text{mixed}}[j] \right)^2$$

where:
- `$N$` is the batch size (1 in practice, but the formula is written for generality).
- `$T$` is the total number of tokens in the input sequence.
- `$l$` is the number of passkey answer tokens at the end of the sequence (the final output tokens that the model must generate to recite the passkeys).
- `$H_{\text{full}}[j]$` is the final hidden state vector at position `$j$` from the full-attention forward pass.
- `$H_{\text{mixed}}[j]$` is the final hidden state vector at the same position from the mixed-attention forward pass (using the current gate values).
- `$(\cdot)^2$` applied element-wise, then summed over the hidden dimension (the L2 norm squared of the difference vector).

**What this equation computes:** for each of the final `$l$` token positions, it computes the squared Euclidean distance between the full-attention model's last-layer hidden state and the mixed-attention model's last-layer hidden state. It then averages over the batch and token positions. The result is a scalar that measures how much the model's internal representation at the output positions differs when some heads are partially compressed.

**Why this form and why last hidden state:** the final hidden state (the output of the last Transformer layer, before the language modeling head) is the information bottleneck that determines the next-token prediction. If the representation at position `$j$` is identical between the full and compressed models, then the predicted token distribution will be identical, and the model's behavior is unchanged. By matching hidden states rather than output token probabilities, the objective is smoother and more informative — it provides a gradient even when the predicted token hasn't changed yet, capturing subtle representational drift before it manifests as a wrong answer. This is a standard knowledge distillation technique (hidden-state matching is often used in model compression).

**Why only the last `$l$` tokens:** the passkey answer tokens are the only positions where long-range retrieval is required. Computing the loss on all `$T$` tokens would dilute the signal — most intermediate token positions in the document are unaffected by head compression because they rely on local context. Focusing the loss on the passkey answer tokens makes the objective a pure measure of retrieval fidelity.

##### Regularization Loss (L1 Sparsity)

$$\mathcal{L}_{\text{reg}} = \sum_{i=1}^{L} \sum_{j=1}^{H} |\alpha_{i,j}|$$

where:
- `$L$` is the number of Transformer layers.
- `$H$` is the number of KV heads per layer.
- `$\alpha_{i,j}$` is the gate value for the `$j$`-th KV head in layer `$i$`.

**What this equation computes:** the sum of absolute values of all gate parameters, also known as L1 norm or Lasso regularization.

**Why this form and why L1 over L2:** L1 regularization promotes sparsity — it pushes parameters exactly to zero rather than just toward small values. This is a well-known property: the L1 penalty has a constant gradient magnitude (`$\pm 1$`) regardless of the parameter value, so small parameters receive the same pressure toward zero as medium parameters. In contrast, L2 regularization (`$\sum \alpha^2$`) has gradient proportional to `$\alpha$`, so it pushes parameters toward small values but rarely to exactly zero. For the binarization step (Section 3.4.5), having gate values that are cleanly separated — some near 1, others near 0 — makes the thresholding decision unambiguous. The L1 penalty is the mechanism that creates this separation.

##### Combined Loss

$$\mathcal{L} = \mathcal{L}_{\text{distill}} + \lambda \mathcal{L}_{\text{reg}}$$

where `$\lambda$` is a hyperparameter controlling the strength of sparsity regularization. The paper sets `$\lambda = 0.05$` in all experiments.

**What this equation computes:** a weighted sum of the two objectives. The optimization balances two competing forces: (a) keep gate values high enough to maintain output fidelity, and (b) push gate values toward zero to maximize compression.

**Why `$\lambda = 0.05$`:** this hyperparameter was presumably chosen empirically. It controls the trade-off between accuracy preservation and sparsity. A larger `$\lambda$` would produce more sparsity (fewer retrieval heads) but potentially damage accuracy; a smaller `$\lambda$` would preserve more heads and thus provide less compression. The paper does not provide an ablation over `$\lambda$`, but the fixed value of 0.05 is used consistently across all models (Llama-2, Llama-3, Mistral) and appears to strike an effective balance.

**The optimization dynamics:** at the start, all `$\alpha_{i,j} = 1$`, so `$\mathcal{L}_{\text{distill}}$` is zero (the mixed model equals the full model) and `$\mathcal{L}_{\text{reg}}$` is at its maximum. As training proceeds, the L1 penalty pushes all gates downward. For heads whose compression causes little output deviation, the distillation loss barely increases as `$\alpha$` drops, so the L1 gradient dominates and drives `$\alpha \to 0$`. For heads whose compression causes significant output deviation, the distillation loss rises sharply as `$\alpha$` drops, creating an opposing gradient that arrests the decline at a higher value. The final gate values (Figure 4) show a distribution with a cluster near 0 (streaming heads), a cluster at intermediate values, and a cluster at high values (retrieval heads). The threshold `$\tau$` for binarization is chosen based on a target sparsity quantile (e.g., 25% retrieval heads for MHA, 50% for GQA).

#### 3.4.5 Binarization, Head Reordering, and Deployment Inference

After the optimization phase produces gate values for every KV head, the deployment phase binarizes the attention policy and executes inference with two separate KV caches per layer.

##### Binarization with a Threshold

The continuous gate values are converted to a hard binary decision using a threshold `$\tau$`, determined by a target sparsity quantile (e.g., "keep the top 25% of heads as retrieval heads"):

$$\text{attn}_{i,j} = \begin{cases} \text{full\_attn} & \text{if } \alpha_{i,j} > \tau \\ \text{streaming\_attn} & \text{otherwise} \end{cases}$$

**What this equation defines:** a deterministic mapping from the trained gate value to the runtime attention mechanism. Heads with gate values above the threshold compute full causal attention against all prior tokens. Heads with gate values below the threshold compute streaming attention against only sink tokens and recent tokens.

**Why a hard binarization over continuous blending:** during training, the continuous blend provides gradients. During deployment, a hard binary choice is required for two practical reasons. First, computing a weighted average of two attention outputs requires computing *both* attention outputs in full, which offers no computational savings — the whole point of DuoAttention is that streaming heads have drastically cheaper attention computations. Second, the KV cache for streaming heads can be aggressively pruned to constant size, which is only possible if the head is purely streaming.

**How `$\tau$` is chosen:** the paper specifies retrieval head *ratios* (not absolute thresholds). For MHA models like Llama-2-7B, the target is 25% retrieval heads; for GQA models like Llama-3-8B and Mistral-7B, the target is 50%. The threshold `$\tau$` is then set to the value that achieves this ratio — e.g., for 32 KV heads per layer, the 8th highest gate value across all layers determines the cutoff. The reason GQA models need a higher ratio is structural: each KV head in GQA serves multiple query heads, so compressing a single GQA KV head has a larger effect than compressing a single MHA KV head. The optimization naturally assigns higher gate values to GQA heads (visible in Figure 4), and the binarization threshold reflects this — keeping 50% of KV heads in GQA achieves comparable accuracy preservation to keeping 25% in MHA.

##### Head Reordering for Efficient Execution

Before deployment, the model's weight matrices are physically reordered. The paper states:

> "we preprocess the model by reordering the output channels of the Query, Key, and Value projection weights according to the attention head assignments."

This is an implementation detail that has a significant practical impact. By default, the attention heads are interleaved in the weight matrices — the output channels for head 0, head 1, …, head H-1 are adjacent. If retrieval and streaming heads are interspersed, each attention computation would need to gather outputs from scattered positions in the KV cache, requiring expensive indexing or scatter-gather operations.

The reordering procedure:
1.  After binarization, classify each head as retrieval or streaming.
2.  Permute the output channels of the Q, K, V projection weight matrices so that all retrieval heads are in a contiguous block and all streaming heads are in another contiguous block within each layer.
3.  Permute the input channels of the output projection weight matrix correspondingly to maintain mathematical equivalence.

The result: at runtime, the Q, K, V vectors for a new token can be cleanly sliced into a "retrieval" portion and a "streaming" portion using simple tensor slicing operations, and the attention outputs can be concatenated back together. The paper notes this avoids "relying on scattering and gathering operations," which are less efficient on GPUs.

##### Decoding with Dual KV Caches

During autoregressive decoding (generating tokens one by one), each layer maintains two KV caches, as illustrated in Figure 5 (left):

**Retrieval head KV cache:**
- **Contents**: Keys and Values for all past tokens (growing linearly with sequence length).
- **Memory complexity**: `$O(r \cdot L)$` where `$r$` is the retrieval head ratio and `$L$` is the sequence length.
- **Attention computation**: standard causal attention — each new token's query attends to all keys in the cache.
- **Update**: after computing K and V for the new token, append them to the cache.

**Streaming head KV cache:**
- **Contents**: Keys and Values for only the attention sink tokens (the first `$S$` tokens of the sequence) and the most recent `$R$` tokens.
- **Memory complexity**: `$O((1-r) \cdot (S+R))$`, which is constant with respect to sequence length.
- **Attention computation**: the new token's query attends only to these `$S+R$` cached tokens. The attention mask is the Λ-like pattern — initial tokens and recent tokens.
- **Update**: after computing K and V for the new token, append to the recent-token portion and evict the oldest recent token to keep the recent window at size `$R$`.

**Per-layer forward pass during decoding**:
1.  Receive the hidden state vector for the new token from the previous layer.
2.  Compute Q, K, V for all heads by multiplying by the (reordered) projection matrices.
3.  Split Q, K, V along the head dimension into retrieval-portion and streaming-portion.
4.  Compute retrieval attention: `$\text{softmax}(Q_{\text{ret}} K_{\text{ret\_cache}}^T) V_{\text{ret\_cache}}$`.
5.  Compute streaming attention: `$\text{softmax}(Q_{\text{str}} K_{\text{str\_cache}}^T) V_{\text{str\_cache}}$`, where the KV cache contains only `$S+R$` tokens.
6.  Concatenate the two attention outputs along the head dimension.
7.  Apply output projection to produce the layer output.

The paper provides concrete deployment configurations: for long-context benchmarks like Needle-in-a-Haystack, they use `$S = 64$` sink tokens and `$R = 256$` recent tokens.

**Why this provides speedup:** for MHA with 25% retrieval heads, 75% of heads have their attention complexity reduced from `$O(L)$` (linear in context length) to `$O(1)$` (constant, because `$S+R = 320$` is small). The total attention FLOPs per token per layer drop from `$H \cdot L$` to approximately `$(H_{\text{ret}} \cdot L + H_{\text{str}} \cdot (S+R))$`. At long context lengths, this approaches a speedup of `$H / H_{\text{ret}} = 1/r$`. For `$r = 0.25$`, the theoretical maximum speedup is `$4\times$`; the achieved speedup of 2.18× (Figure 9) is lower due to fixed overheads (linear layers, communication, etc.) but substantial.

For GQA with 50% retrieval heads, the theoretical maximum is `$2\times$`; the achieved 1.50× is similarly proportioned.

##### Chunked Pre-filling

Pre-filling is the initial phase where the entire prompt is processed to populate the KV cache before generation begins. In standard attention, pre-filling is `$O(L^2)$` in time and `$O(L)$` in memory (for the KV cache being built). DuoAttention reduces both, especially when combined with chunked pre-filling.

**Chunked pre-filling** is a common technique where the prompt is split into fixed-size chunks (e.g., 32K tokens each), and each chunk is processed sequentially. This is already used in systems like vLLM and Sarathi to reduce peak memory, because the intermediate activations of the MLP layers only need to be materialized for one chunk at a time. DuoAttention is fully compatible with this.

**How DuoAttention streaming heads change pre-filling complexity** (Figure 5, right):

- **For retrieval heads**: chunked pre-filling proceeds normally. Each new chunk's tokens attend to all previous tokens in the KV cache (standard causal attention), building up the full KV cache incrementally.
- **For streaming heads**: after each chunk is processed and its K and V states are computed, the KV cache is **immediately pruned** to keep only the sink tokens (the very first tokens in the entire sequence) and the most recent tokens from the current and previous chunks. The streaming head's KV cache never grows beyond `$S+R$` tokens.

This means that when processing chunk `$c$`, the streaming heads in chunk `$c$` only attend to a constant number of tokens (the sinks plus the recent window), rather than attending to all tokens from chunks 1 through `$c-1$`. The paper states:

> "The pre-filling time complexity for streaming heads is optimized from `$O(L^2)$` to `$O(LK)$`, and the memory complexity is reduced from `$O(L)$` to `$O(K)$`."

where `$L$` is the total sequence length and `$K$` is the chunk size. This is because each of the `$L/K$` chunks performs attention of size `$K \times (S+R)$` (approximately `$K \times K$` if `$K$` is comparable to `$S+R$`), giving total complexity `$(L/K) \cdot K^2 = LK$`.

**Concrete example from Figure 10:** for Llama-2-7B pre-filling a 100K-token context with chunk size 10K tokens, DuoAttention reduces latency from ~156 seconds to ~19 seconds (at chunk size 10K) — an 8.2× reduction for pre-filling alone. Memory drops from ~154 GB to ~19 GB. For Llama-3-8B pre-filling 320K tokens, latency drops from ~75 seconds to ~38 seconds at small chunk sizes, and memory drops from ~71 GB to ~26 GB. The improvements are more dramatic at smaller chunk sizes because the streaming heads' `$O(LK)$` complexity benefits proportionally more when `$K$` is small.

**Why no specialized kernels are needed:** the streaming heads' pre-filling uses standard FlashAttention-2, simply with a smaller sequence length (the KV cache size is `$S+R$` rather than the total prefix length). The pruning of the streaming head's KV cache after each chunk is a simple tensor slicing operation. This contrasts with token-eviction methods like H2O and TOVA, which require attention scores to decide which tokens to keep — FlashAttention never materializes attention scores, making those methods incompatible with efficient pre-filling without expensive workarounds. The paper explicitly notes this as an advantage: "the streaming heads' pre-filling in DuoAttention can be achieved with linear time and constant memory complexity, without requiring specialized kernels."

#### 3.4.6 Synthesis: Key Design Choices and Their Justifications

This section connects the technical components to the paper's stated goals and contrasts with alternatives.

**Design choice 1: Optimization-based identification over attention-profiling.**
- **What was chosen**: training gate values to minimize output deviation under compression.
- **Why**: attention profiling (used by FastGen, RazorAttention) only captures the attention score distribution, not the end-to-end impact of compression. It cannot account for value-state importance, downstream propagation of errors, or input-dependent behavior. The optimization directly measures the quantity that matters — does compressing this head change the model's answer? — using a causal intervention (the gate blending).
- **Evidence**: Figure 13, panel 1, shows optimization significantly outperforms attention profiling on passkey retrieval and MMLU.

**Design choice 2: Synthetic passkey data over natural language modeling for the identification loss.**
- **What was chosen**: a dataset where 100% of the loss tokens require long-range retrieval.
- **Why**: natural text is dominated by local-context predictions. The supervision signal for retrieval importance is extremely sparse — perhaps 1% of tokens. The synthetic dataset densifies this signal, making every gradient step informative. Without this, the optimization would primarily learn which heads are important for local syntax, not long-range retrieval.
- **Evidence**: Figure 13, panel 1, shows optimization with language modeling performs substantially worse than with synthetic data.

**Design choice 3: L1 regularization (Lasso) over L2 or other sparsity inducers.**
- **What was chosen**: `$\lambda \sum |\alpha_{i,j}|$`.
- **Why**: L1 produces exact zeros, creating a clean separation between retrieval and streaming heads for thresholding. L2 would produce small-but-nonzero values that make binarization ambiguous.
- **Evidence**: the final gate value distributions in Figure 4 show clusters near 0 and at higher values, confirming the sparsity-inducing effect.

**Design choice 4: Combined sink + recent token pattern during optimization.**
- **What was chosen**: the streaming attention mask in the identification phase includes both attention sinks and recent tokens.
- **Why**: using only sinks or only recent tokens fails to capture the full streaming head behavior. A head might appear retrieval-like under sink-only attention (because it needs recent context) or under recent-only attention (because it relies on the sink), leading to incorrect classification. Using both provides the correct baseline — what does the head's output look like when it has sinks and recent tokens but no middle tokens.
- **Evidence**: Figure 13, panel 2, shows that combining sink and recent tokens produces better identification than either alone.

**Design choice 5: Binarization at deployment rather than continuous blending.**
- **What was chosen**: hard thresholding at a sparsity quantile.
- **Why**: continuous blending requires computing both attention modes, offering no efficiency gains. Binarization enables the streaming heads to use a constant-size KV cache and `$O(1)$` attention per token.
- **Trade-off acknowledged**: the threshold `$\tau$` introduces a hyperparameter (the retrieval head ratio). The paper determines appropriate ratios empirically — 25% for MHA, 50% for GQA — based on the accuracy-efficiency trade-off observed in benchmarks.

**Design choice 6: Head reordering in weight matrices before deployment.**
- **What was chosen**: physical permutation of Q, K, V projection output channels and output projection input channels.
- **Why**: enables clean slicing and concatenation operations instead of scatter-gather during inference. This is a one-time preprocessing cost that pays off in every forward pass.
- **Mathematical equivalence**: the reordering is a permutation, so it does not change the model's output when all heads perform full attention. After binarization, the streaming heads compute different attention, but the head splitting is logically equivalent to what the un-reordered model would do with a scattered index.

**Design choice 7: Compatibility with existing attention kernels and quantization.**
- **What was chosen**: use FlashAttention-2 for both retrieval and streaming heads; support integration with QServe quantization.
- **Why**: the retrieval heads compute standard causal attention (fully compatible with FlashAttention). The streaming heads compute attention with a custom mask, but this is still a standard attention operation — just with a shorter KV cache — and FlashAttention handles it naturally. This means DuoAttention benefits from all the memory-efficiency and speed of FlashAttention without requiring custom CUDA kernels. The quantization compatibility is shown in Figure 12: combining DuoAttention with 8-bit weight and 4-bit KV cache quantization enables 3.3M tokens on a single A100, a 6.4× capacity increase over FP16 full attention.

#### 3.4.7 Summary of the Information Flow

To make the end-to-end process concrete, here is what happens when a long-context query is processed by a DuoAttention-deployed model:

**Phase 1: Identification (done once, offline)**
1.  Freeze the pre-trained LLM.
2.  Attach trainable gate values `$\alpha_{i,j}$` to each KV head.
3.  Generate synthetic passkey-retrieval training samples from BookSum (10 passkeys of 32 words each, 50 length intervals up to max context).
4.  For 2000 steps, process one sample per step: forward pass with full attention (teacher) and forward pass with gate-blended attention (student), compute L2 distillation loss on passkey answer tokens + L1 regularization loss, backpropagate to update only gate values.
5.  Binarize: set threshold `$\tau$` to achieve target retrieval head ratio (25% MHA, 50% GQA). Heads with `$\alpha_{i,j} > \tau$` are retrieval; rest are streaming.
6.  Reorder Q, K, V, and output projection weight matrices to group retrieval and streaming heads contiguously.

**Phase 2: Runtime inference (every query)**
1.  **Chunked pre-filling**: The long prompt is split into chunks of size `$K$` (e.g., 32K tokens).
2.  For each chunk, compute Q, K, V. Split into retrieval and streaming portions.
3.  Retrieval heads: compute causal attention against the growing retrieval KV cache (all prior tokens). Update the cache with the chunk's K and V.
4.  Streaming heads: compute attention against only the `$S$` sink tokens and `$R$` recent tokens (from the current and previous chunk). Update the streaming cache and prune to keep it at constant size `$S+R$`.
5.  Concatenate retrieval and streaming attention outputs, apply output projection, feed to next layer.
6.  **Decoding**: For each generated token, repeat steps 2–5 (the KV caches are now built). Retrieval heads attend to the full sequence; streaming heads attend to sinks + the last `$R$` tokens. The streaming heads' attention cost per token is `$O(S+R)$`, constant; the retrieval heads' cost grows linearly but applies to only a fraction `$r$` of heads.
7.  Output tokens are generated until an end-of-sequence token or max length is reached.

The result: memory usage is dominated by the retrieval head KV cache, which is `$r$` times the size of a full KV cache, plus a constant overhead for streaming heads. Latency per decoding token is reduced by a factor approaching `$1/r$` for the attention component. Pre-filling latency is reduced by converting the streaming heads' portion from `$O(L^2)$` to `$O(LK)$`. All of this is achieved by identifying and protecting the small set of heads that genuinely require full-context attention, and aggressively compressing everything else.

## 4. Key Insights and Innovations

### Innovation 1: Output-Aware Head Classification as an Alternative to Attention-Pattern Profiling

The dominant approach in prior work for identifying which attention heads could be compressed — exemplified by FastGen (Ge et al., 2024) and RazorAttention (Tang et al., 2024a) — was to **profile attention score distributions**. The reasoning was intuitive: if a head's attention scores concentrate on recent tokens, it can be treated as a local head and its distant KV cache entries can be discarded. If scores show peaks at distant positions, the head is doing retrieval and needs full context.

DuoAttention makes a **fundamentally different conceptual move**. Rather than inferring functional importance from attention patterns — a correlational approach — it directly measures the **causal consequence of compression** on the model's output. The paper's definition of retrieval heads — those that "significantly alter model outputs when restricted to recent tokens and attention sinks" — operationalizes importance as a counterfactual: *what would happen to the final hidden states if we forced this head to operate as a streaming head?*

This shift matters for three reasons that attention profiling cannot address. First, **value states carry information independently of attention scores** — a head might attend broadly but encode negligible information in its value vectors, meaning that dropping those tokens has no end-to-end effect despite high attention scores. Second, **downstream propagation is opaque to per-head profiling** — compression errors in one head may be amplified or canceled by subsequent layers, and only an end-to-end measurement captures the net effect. Third, **attention distributions are input-dependent** — a head profiled as "local" on one prompt might become "retrieval" on another, making a static classification based on a few samples unreliable.

The paper quantifies this gap directly in Figure 13 (panel 1). When the same synthetic passkey-retrieval dataset is used to identify retrieval heads via attention profiling versus the optimization-based approach, the optimization method substantially outperforms on both passkey retrieval accuracy and MMLU. This is not an incremental improvement — it demonstrates that attention profiling is fundamentally measuring the wrong quantity. The key insight is that **what a head attends to is not the same as what a head contributes to the output**.

This is a **conceptual advance** rather than merely an engineering improvement. It establishes a new diagnostic criterion — output deviation under targeted compression — that could be applied to other model components beyond attention heads (e.g., MLP layers, entire attention blocks). It also provides a rigorous grounding for the retrieval/streaming dichotomy that prior work (Wu et al., 2024) identified observationally but did not formalize for compression purposes.

---

### Innovation 2: Synthetic Retrieval Stress-Testing as a Replacement for Natural Language Supervision

The paper identifies and solves a subtle failure mode in using natural language data for model compression: **the supervision signal for long-range retrieval is pathologically sparse in natural text**. Most next-token predictions in a document can be made from local context alone. Even in a 32,000-token passage, the fraction of tokens whose prediction genuinely requires information from 10,000+ tokens away is tiny — perhaps 1%. This means that a compression objective that minimizes next-token prediction loss on natural text will primarily optimize for fidelity on local-context predictions, providing negligible signal about which heads handle long-range retrieval.

This is not an obvious problem. Prior compression and distillation work (in both LLMs and vision models) routinely uses natural data, on the implicit assumption that the training distribution matches the deployment distribution and therefore provides appropriate supervision. DuoAttention's key diagnostic move is recognizing that **the supervision signal must be re-weighted to match the capability being preserved**. For KV cache compression, the capability at risk is not general language modeling but specifically the ability to retrieve and use information from the distant past. Natural data provides almost no gradient about this capability, so it is effectively blind to the damage that compression inflicts on retrieval heads.

The solution — a synthetic passkey-retrieval dataset where 100% of the loss tokens depend on long-range retrieval — is deceptively simple but conceptually powerful. It functions as a **stress test** for the model's retrieval circuitry: by forcing every output token to require information from scattered positions in the context, the distillation loss on those output tokens becomes a pure measure of retrieval fidelity. Every gradient step is directly informative about which heads are critical for looking up and reproducing distant information.

Figure 13 (panel 1) provides the empirical validation: optimization with language modeling as the distillation objective performs significantly worse than optimization with synthetic passkey data. This is not because language modeling is inherently worse — it is because language modeling provides almost no signal about the specific capability (long-range retrieval) that compression threatens. The synthetic dataset densifies the signal, turning a needle-in-a-haystack problem for the optimizer into a well-conditioned one.

This is a **transferable research strategy** rather than a domain-specific trick. Any model compression technique that risks damaging a specific, sparse capability (factual recall, mathematical reasoning, code execution) could adopt the same approach: construct synthetic data where the capability is tested on every token, and use output-level distillation on that data to identify which parameters must be preserved. The innovation is recognizing that **the evaluation signal for compression should be capability-specific, not distribution-matched to natural data**.

---

### Innovation 3: The Retrieval Head Ratio as an Emergent Property of Architecture, Not Task

A straightforward application of DuoAttention's identification procedure would produce compression ratios based purely on empirical accuracy-efficiency trade-offs: pick the most aggressive ratio that maintains acceptable benchmark scores. But the paper's data reveals something deeper: **the optimal retrieval head ratio is not a free parameter to be tuned arbitrarily but is largely determined by the model architecture's attention mechanism**.

Specifically, the paper consistently finds that **MHA models (e.g., Llama-2-7B) can operate with ~25% retrieval heads while GQA models (e.g., Llama-3-8B, Mistral-7B) require ~50%**. This ratio is not chosen arbitrarily — it falls out of the optimization procedure naturally, as shown in Figure 4, where the distribution of trained gate values differs qualitatively between MHA and GQA architectures. The paper explains this structurally: in GQA, each KV head serves multiple query heads (typically 4 in Llama-3), so compressing a single KV head affects a larger fraction of the model's total attention capacity. The optimization correctly identifies that each GQA KV head is more "important" on average, assigning higher gate values and resulting in a higher retrieval head ratio after thresholding.

This finding has significant implications beyond DuoAttention itself. It suggests that **the degree to which a model's long-context capability can be compressed is not primarily a property of the task or the data but of how the attention computation is structured**. An MHA model effectively has redundancy in its head configuration — multiple heads can serve overlapping retrieval functions — allowing aggressive compression. A GQA model, by sharing KV heads, has already eliminated some of that redundancy, leaving less room for further compression without damaging retrieval.

This is a **diagnostic insight** that reframes the compression problem. Rather than asking "how much can we compress this model while maintaining accuracy on a specific benchmark?", the better question is "how much redundancy does this architecture's attention mechanism provide for retrieval functions?" The answer to the second question predicts the answer to the first across models, tasks, and benchmarks. The paper does not fully develop this theory — it is an empirical observation rather than a proven law — but the consistency across different model families (Llama-2, Llama-3, Mistral) and the structural explanation (KV head sharing in GQA) makes it a compelling finding that likely generalizes.

This also explains a pattern that might otherwise seem contradictory: while GQA was designed specifically to reduce KV cache memory, DuoAttention achieves a *smaller relative compression ratio* on GQA than on MHA (1.67× vs. 2.55× memory reduction). This is not a weakness — it reflects the fact that GQA has already compressed away the easiest-to-eliminate redundancy, and what remains is proportionally more critical. The absolute memory savings are still substantial because the base KV cache is already smaller in GQA.

---

### Innovation 4: Separating Pre-filling from Decoding in KV Cache Compression

Nearly all prior work on KV cache compression — H2O, StreamingLLM, TOVA, FastGen — operates exclusively during the **decoding phase**. Tokens are evicted from the KV cache after the prompt has been pre-filled, based on attention scores accumulated during generation. This leaves two major inefficiencies unaddressed: (1) the pre-filling phase itself still requires full quadratic attention with peak memory proportional to sequence length, and (2) the compression decisions are made based on attention scores from generated tokens, which means early generated tokens may attend to a degraded KV cache before sufficient statistics are accumulated.

DuoAttention is the first KV cache compression method to **apply compression during pre-filling as well as decoding**, and this is not a minor extension — it is enabled by a fundamental property of the retrieval/streaming head dichotomy that token-eviction methods lack. Because streaming heads are defined by a fixed attention pattern (sinks + recent tokens) rather than by a dynamic eviction policy, their pre-filling computation can be **decoupled from the token-eviction decision entirely**. There is no need to compute attention scores, identify important tokens, or make eviction decisions during pre-filling. The streaming heads simply never attend to middle tokens, from the very first chunk onward.

This property converts the pre-filling complexity for streaming heads from O(L²) to O(LK), where K is the chunk size. The practical consequences are shown in Figure 10: for Llama-2-7B pre-filling a 100K-token context, DuoAttention reduces latency from ~156 seconds (full attention) to ~19 seconds at a 10K chunk size, and memory from ~154 GB to ~19 GB. These are not marginal improvements — they change the feasibility boundary for long-context inference. A 100K-token prompt that previously required multiple high-memory GPUs can now be processed on a single GPU with reasonable latency.

The conceptual distinction is that **token-eviction methods are reactive** — they wait to see which tokens are important during generation, then discard the rest — and therefore cannot reduce pre-filling costs because the importance assessment itself requires full pre-filling. DuoAttention is **proactive** — it determines at the architectural level which heads need full context and which do not, independent of the specific prompt content, enabling compression from the very first token processed. This is a structural advantage, not an incremental optimization.

The compatibility with chunked pre-filling is also notable because it requires no specialized kernels. The streaming heads' pre-filling uses standard FlashAttention-2 on a KV cache of constant size (S+R tokens). This is in contrast to token-eviction methods like H2O and TOVA, which are fundamentally incompatible with FlashAttention during pre-filling because they require materialized attention scores to make eviction decisions. The paper explicitly identifies this as a practical flaw in prior work (Appendix A.3).

This innovation reframes the scope of KV cache compression. It demonstrates that compression is not just a decoding-time memory optimization but a **unified framework that can reduce both pre-filling and decoding costs**, provided the compression policy is pattern-based (streaming heads) rather than dynamic (token eviction).

## 5. Experimental Analysis

### Evaluation Methodology

- **Datasets.** The paper evaluates on both long-context and short-context benchmarks. For long-context: **Needle-in-a-Haystack (NIAH)** (Kamradt, 2024), a synthetic retrieval stress test that measures whether a model can retrieve a specific piece of information ("needle") embedded at various depths within a very long context ("haystack"); and **LongBench** (Bai et al., 2023), a comprehensive bilingual benchmark with 21 tasks spanning question answering, summarization, and retrieval, designed to assess long-context understanding on natural texts. For short-context: **MMLU** (Hendrycks et al., 2021) for knowledge, **MBPP** (Austin et al., 2021) for coding ability, and **MT-Bench** (Zheng et al., 2023) for multi-turn dialogue helpfulness. The paper notes that these short-context benchmarks are included to verify that DuoAttention does not damage the model's general capabilities when compressing the KV cache on sequences where full attention would normally be used.

- **Base models.** The paper uses four model families to demonstrate generality: **Llama-2-7B-chat** (MHA, 32 heads per layer) and its long-context variant **Llama-2-7B-32K-Instruct**; **Llama-3-8B-Instruct** (GQA, 8 KV heads per layer) and its long-context variant **Llama-3-8B-Instruct-Gradient-1048K**; **Llama-3-70B-Instruct** (GQA); and **Mistral-7B-Instruct-v0.2** (GQA). These span both MHA and GQA architectures, with model sizes from 7B to 70B parameters and context windows from 4K to over 1M tokens. The paper argues this range demonstrates that the method is not specific to a single architecture or scale. All models are instruction-tuned, which matters because deployment use cases typically involve chat or instruction-following models, not base models.

- **Metrics.** For **NIAH**, the paper reports exact match accuracy — the fraction of test cases where the model correctly retrieves and outputs the needle text. For **LongBench**, per-task metrics follow the original benchmark's scoring (F1, ROUGE-L, exact match, etc., depending on the task), and the paper reports accuracy as a percentage with the KV cache budget on the x-axis. For **MMLU and MBPP**, accuracy. For **MT-Bench**, the GPT-4 judge score on a scale of 1-10. For **efficiency measurements**, the paper reports two primary metrics: **memory usage in GB** (GPU memory consumed by the KV cache and model weights) and **latency in milliseconds** (per-token decoding time) or **seconds** (total pre-filling time), all measured on a single NVIDIA A100-80G GPU with pre-allocated KV cache to avoid dynamic allocation overhead.

- **Baselines.** The paper compares against four KV cache compression methods: **H2O** (Zhang et al., 2023b), which evicts tokens based on accumulated attention scores; **StreamingLLM** (Xiao et al., 2023b), which retains only attention sink tokens and recent tokens; **TOVA** (Oren et al., 2024), which uses a token-eviction policy based on attention to the last token; and **FastGen** (Ge et al., 2024), which profiles attention heads to determine per-head token retention policies. For efficiency comparisons, the baseline is **full attention** — the unmodified model with complete KV cache for all heads. The paper notes that for long-context evaluations, the original H2O and TOVA implementations are incompatible with FlashAttention during pre-filling (they require materialized attention scores), so the authors modify them by using FlashAttention for exact pre-filling and then applying their eviction policies during simulated decoding on the last 50 tokens of the input (Section A.3). This modification actually *improves* their performance compared to their true designs, making the comparison conservative relative to DuoAttention.

- **Generation budget / compute accounting.** The paper measures KV cache compression in terms of **KV cache budget** — the fraction of the full attention KV cache retained. For example, a 25% KV cache budget means the total number of stored KV entries across all heads is 25% of what full attention would store. DuoAttention achieves its target budget by setting the retrieval head ratio (the fraction of heads that retain full KV caches) and keeping a constant number of sink + recent tokens for streaming heads. For baseline methods, the budget is controlled by the number of tokens retained (H2O, TOVA, StreamingLLM) or the attention recovery ratio (FastGen). For DuoAttention, the paper uses 25% retrieval heads for MHA models and 50% for GQA models in the main experiments, with additional sweeps over different ratios (Figure 11). Deployment configurations for sink/recent tokens are specified per benchmark: for long-context, 64 sink tokens and 256 recent tokens; for short-context, 32 sink / 128 recent (MMLU) or 16 sink / 64 recent (MBPP, MT-Bench).

- **Cross-validation / statistical protocol.** The paper does not use cross-validation. The retrieval head identification is performed once per model using the synthetic dataset (50 length intervals from 1000 tokens up to the model's maximum context length) and the resulting gate values are binarized with a fixed threshold to achieve the target ratio. All test-time evaluations are zero-shot (or one-shot for MMLU). The paper does not report confidence intervals or error bars, which is a limitation discussed in the Critical Assessment. There are no train/validation/test splits for the benchmark evaluations — the standard test sets are used directly.

### Main Quantitative Results

#### Long-Context Benchmarks: Needle-in-a-Haystack (NIAH)

The headline result from Figure 6 is that **DuoAttention is the only method that maintains retrieval accuracy across all context lengths and document depths, while all baseline methods fail**. The figure shows heatmaps for two models (Llama-2-7B-32K-Instruct with 25% KV cache budget and Llama-3-8B-Instruct-Gradient-1048K with 50% KV cache budget) across context lengths up to 32K and 1048K tokens respectively, and document depths from 0% to 100%.

For **Llama-2-7B-32K-Instruct at 25% KV budget**: Full attention serves as the upper bound, showing near-perfect retrieval across all depths and lengths. DuoAttention at 25% shows a heatmap that is visually almost identical to full attention — retrieval accuracy is maintained across the entire 32K context and all document depths. In contrast, H2O at 25%, StreamingLLM at 25%, and TOVA at 25% all show dark regions (failures) throughout the heatmap, indicating that they "fail to retrieve correct answers from the various depths of the long sequence, as they discard the KV cache containing the necessary information during generation." FastGen at 25% (actually >25% average budget, adjusted via recovery ratio) could only be measured up to 24K context before hitting out-of-memory errors due to the quadratic memory cost of its attention profiling phase; even in the measurable range, it shows degraded performance.

For **Llama-3-8B-Instruct-Gradient-1048K at 50% KV budget**: The pattern is identical. Full attention shows strong performance across the full 1048K context range. DuoAttention at 50% maintains retrieval accuracy across all lengths and depths. H2O, StreamingLLM, and TOVA at 50% show pervasive failures. FastGen at 50% (>50% average budget) could only be evaluated up to 32K context due to OOM, and even there shows degraded retrieval.

The paper states: "DuoAttention demonstrates strong performance across all sequence depths, handling lengths up to 1048K tokens effectively." This is a particularly strong result because it shows that **protecting a fraction of heads from compression is sufficient to preserve retrieval**, while uniform compression across all heads — as done by all baseline methods — catastrophically destroys the model's ability to locate specific information in long contexts, regardless of which tokens are retained.

The paper also includes NIAH results for Mistral models (Figures 15 and 16 in Appendix), showing the same qualitative pattern: DuoAttention matches full attention while baselines fail.

#### Long-Context Benchmarks: LongBench

Figure 7 presents a much more detailed picture, showing results on 14 LongBench tasks for both Llama-2-7B-32K-Instruct and Llama-3-8B-Instruct-1048K. The x-axis is the KV cache budget (fraction of full cache retained), and the y-axis is task-specific accuracy. Each task has five curves corresponding to Full (100% budget), H2O, StreamingLLM, TOVA, and DuoAttention. The paper states: "DuoAttention shows a superior trade-off between KV budget and accuracy on most tasks."

For **Llama-2-7B-32K-Instruct** (MHA, 25% budget target for DuoAttention): On tasks like HotpotQA, DuoAttention at 25% achieves approximately 50.44% vs. full attention's 47.98% — actually *exceeding* full attention, likely due to noise or a regularization effect. On GovReport, DuoAttention achieves roughly 27.98% vs. full's 31.23%. On PassageRetrieval-EN, DuoAttention reaches about 47.25% vs. full's 50.92%. On Qasper, 26.59% vs. 33.23%. The key pattern is that DuoAttention consistently outperforms H2O, StreamingLLM, and TOVA at the same budget level. The full table of results for all 21 LongBench tasks is provided in Tables 3 and 4 in the Appendix, where DuoAttention achieves the **highest average score** among all methods at the target budget for both models.

For **Llama-3-8B-Instruct-1048K** (GQA, 50% budget target for DuoAttention): On HotpotQA, DuoAttention at 50% achieves approximately 41.63% vs. full's 40.37%. On MultiFieldQA-en, 51.44% vs. 52.62%. On PassageRetrieval-EN, 87.00% vs. 81.00%. On Qasper, 26.93% vs. 29.21%. The pattern holds: DuoAttention tracks full attention closely and dominates the baselines at the same budget.

The paper also compares with FastGen on a subset of LongBench tasks (Tables 5 and 6). For Llama-3-8B-Instruct-1048K at a >50% budget, FastGen achieves an average score of 32.82 across 16 tasks, while DuoAttention at a strict 50% budget achieves 40.01 — a substantial gap. For Llama-2-7B-32K-Instruct at >25% budget, FastGen averages 19.01 vs. DuoAttention's 32.81. This is a key result because FastGen, like DuoAttention, attempts to distinguish between head types, but uses attention profiling rather than optimization-based identification. The gap demonstrates that the identification method matters significantly for downstream accuracy.

#### Short-Context Benchmarks

Figure 8 shows results on MMLU, MBPP, and MT-Bench for Llama-2-7B and Llama-3-8B across different KV cache budgets. The paper states: "DuoAttention consistently outperforms all baselines under the same KV cache budget across various models."

For **Llama-2-7B** (MHA, Figure 8 left column): At a 50% KV budget, DuoAttention achieves approximately 0.43 on MMLU (full: ~0.44), roughly 0.30 on MBPP (full: ~0.31), and ~6.2 on MT-Bench (full: ~6.3). At 25% budget, DuoAttention maintains ~0.41 on MMLU, ~0.27 on MBPP, and ~5.8 on MT-Bench, while all baselines drop substantially further — H2O and StreamingLLM at 25% fall to ~0.30-0.35 MMLU and near-zero on coding tasks.

For **Llama-3-8B** (GQA, Figure 8 right column): At 50% budget, DuoAttention achieves near-lossless performance on all three benchmarks, matching full attention within measurement noise. At 25% budget, DuoAttention degrades more noticeably but still outperforms H2O, StreamingLLM, and TOVA at the same budget.

Table 1 presents results for **Llama-3-70B-Instruct**, a much larger model, at 50% KV budget. DuoAttention achieves 79.35% on MMLU (full: 79.38%), 47.09% on MBPP (full: 47.85%), and 9.14 on MT-Bench (full: 8.93). H2O at 50% achieves comparable MMLU (79.26%) but drops sharply on MBPP (32.12% vs. 47.09%) — a large gap on coding. StreamingLLM at 50% suffers catastrophic degradation on MBPP (5.57%) and MT-Bench (5.41). The coding benchmark (MBPP) appears to be the most sensitive to KV cache compression, and DuoAttention is the only method that preserves coding ability at aggressive compression rates.

The paper notes: "With a 50% KV cache budget, DuoAttention achieves near-lossless performance on most benchmarks." This is important because it means DuoAttention is not trading short-context capability for long-context efficiency — the model's core knowledge, reasoning, and helpfulness are preserved.

#### Decoding Efficiency

Figure 9 shows per-token decoding latency and memory usage for DuoAttention vs. full attention as context length increases, measured on a single A100 GPU. The paper reports several headline numbers:

- For **Llama-2-7B (MHA, 25% retrieval heads)**: DuoAttention reduces memory from ~75 GB to ~30 GB at 200K context length — a roughly **2.45× memory reduction**. At the same length, decoding latency drops from ~29 ms/token to ~13.5 ms/token — roughly a **2.13× speedup**. The paper notes: "These improvements approach the inverse of the retrieval head ratios as context length increases."

- For **Llama-3-8B (GQA, 50% retrieval heads)**: Memory reduces from ~110 GB to ~68 GB at 1M context length — a **1.65× memory reduction**. Latency drops from ~76 ms to ~52 ms — a **1.50× speedup**.

The paper emphasizes that full attention runs out of memory (OOM) at much shorter context lengths than DuoAttention. For Llama-2-7B, full attention OOMs beyond ~130K tokens on a single A100, while DuoAttention scales to 200K+. For Llama-3-8B, full attention OOMs beyond ~450K tokens, while DuoAttention handles the full 1M token measurement range. The OOM results are "linearly extrapolated from measured data" for the full attention curves.

Figure 11 shows the relationship between retrieval head ratio and efficiency improvements at a fixed context length. The paper states: "Both decoding latency and memory usage decrease linearly as the ratio of retrieval heads is reduced." At the most aggressive ratios measured (implying the fewest retrieval heads), DuoAttention achieves: **2.55× memory reduction for MHA and 1.67× for GQA**, and **2.18× latency reduction for MHA and 1.50× for GQA**. These are the headline efficiency numbers reported in the abstract.

#### Pre-filling Efficiency

Figure 10 shows pre-filling latency and memory usage as a function of the chunk size, comparing DuoAttention to full attention. For Llama-2-7B with a 100K-token context (left panels): At a chunk size of 10K tokens, DuoAttention reduces pre-filling latency from ~156 seconds to ~19 seconds — a roughly **8× reduction** — and memory from ~154 GB to ~19 GB — a roughly **8× reduction**. The paper reports the overall maximum improvements as: **up to 1.73× latency reduction for MHA and 1.63× for GQA**, and **up to 2.38× memory reduction for MHA and 1.53× for GQA**. The larger improvements at smaller chunk sizes are expected: as chunk size decreases, the streaming heads' O(LK) complexity becomes proportionally more advantageous relative to the retrieval heads' O(L²) for smaller K.

For Llama-3-8B with a 320K-token context (right panels): latency drops from ~75 seconds to ~38 seconds at the smallest chunk sizes, and memory drops from ~71 GB to ~26 GB. Full attention hits OOM at smaller chunk sizes for the longer context (the green stars are missing on the right side of the Llama-3-8B memory panel), while DuoAttention continues to operate.

#### Combination with Quantization

Figure 12 shows the number of tokens that can be accommodated on a single A100-80G GPU with the Llama-3-8B model under different configurations. The baseline (full attention, BF16) can handle approximately 0.52 million tokens. Adding DuoAttention alone (50% retrieval heads) increases capacity to roughly 1.84 million tokens — a **3.5× increase**. Combining DuoAttention with 8-bit weight quantization and 4-bit KV cache quantization (QServe) increases capacity to **3.30 million tokens** — a **6.4× increase** over the baseline. The paper states: "Combining quantization techniques with DuoAttention allows us to accommodate up to 3.30 million tokens on a single A100-80G GPU."

This is significant because it demonstrates that DuoAttention is complementary to quantization — the memory reductions from head-based compression and from bit-width reduction compound multiplicatively. The 3.3M token capacity on a single consumer-grade GPU represents a substantial practical advance for long-context deployment.

### Ablation Studies and Robustness Checks

The ablation studies are conducted using the Mistral-7B-Instruct-v0.2 model on two tasks: a passkey retrieval task (8-word passkey embedded in a 30K-word text, linear sweep across 100 insertion depths, exact match accuracy reported) and MMLU.

- **Optimization-based vs. attention-profiling-based retrieval head identification (Figure 13, panel 1):** The optimization-based method with synthetic data substantially outperforms attention profiling on both passkey retrieval and MMLU, across the full range of KV cache budgets. On passkey retrieval at 50% budget, optimization achieves roughly 0.90 accuracy vs. attention profiling's roughly 0.65. On MMLU at 50% budget, optimization achieves roughly 0.585 vs. profiling's roughly 0.560. This confirms that output-aware identification captures retrieval importance better than attention-pattern heuristics.

- **Optimizing with synthetic data vs. language modeling (Figure 13, panel 1):** The synthetic passkey data produces "significantly better results" than language modeling (computing distillation loss on all tokens of natural text). On passkey retrieval, the gap between synthetic data and language modeling is particularly large at lower budgets — at 25% budget, synthetic achieves roughly 0.65 vs. language modeling's roughly 0.35. On MMLU, the gap is smaller but consistent, with synthetic data outperforming at all budgets. This validates the paper's claim that natural language modeling provides insufficient supervision signal for identifying retrieval-critical heads.

- **Necessity of sink + recent attention during optimization (Figure 13, panel 2):** Three configurations are compared during the identification phase: sink tokens only (size 320, no recent tokens), recent tokens only (size 320, no sink tokens), and combined (64 sink + 256 recent). The combined configuration outperforms both single-source configurations. On passkey retrieval at 50% budget, the combined configuration achieves roughly 0.90 vs. roughly 0.62 for sink-only and roughly 0.72 for recent-only. On MMLU, the differences are smaller but combined still leads. The paper convincingly demonstrates that "exclusive reliance on either starting or recent token attention is inadequate for effective retrieval head identification."

- **Deployment phase sink and recent token configuration (Figure 13, panel 3):** Four configurations are tested: sink=4/recent=16, 16/64, 32/128, and 64/256 tokens. The paper finds that "performance plateaus at 16 sink tokens and 64 recent tokens" with "minimal gains beyond these values." This is a useful practical finding: the constant-size KV cache for streaming heads can be quite small (80 tokens total) while still achieving near-optimal performance, keeping the streaming heads' memory and compute overhead minimal.

- **Full LongBench results (Tables 3 and 4):** The appendix tables provide per-task results for all 21 LongBench tasks at the target KV budgets. For Llama-3-8B-Instruct-1048K at 50% budget, DuoAttention achieves the highest average score (40.21) vs. H2O (35.76), StreamingLLM (32.26), and TOVA (35.55). For Llama-2-7B-32K-Instruct at 25% budget, DuoAttention averages 34.49 vs. H2O (26.84), StreamingLLM (27.80), and TOVA (29.78). Across individual tasks, DuoAttention is the top performer on the majority of tasks.

- **Training hyperparameters (Table 2):** The maximum sequence lengths used during training vary by model, from 4096 for Llama-2-7B-chat to 32000 for the long-context variants. This is a practical detail — the synthetic data must fit within each model's native context window during the identification phase.

### Critical Assessment

#### Does the paper demonstrate that only a fraction of heads (retrieval heads) are critical for long-context processing?

**Yes, with strong evidence.** Figure 6 (NIAH) shows that protecting 25% (MHA) or 50% (GQA) of heads with full KV caches while compressing the rest to constant-size streaming caches preserves retrieval accuracy across all context lengths and depths. The contrast with baselines is stark: methods that compress uniformly across all heads fail catastrophically. Figure 1 (right panel) provides a direct causal test: modifying retrieval heads severely damages passkey retrieval, while modifying streaming heads has minimal impact. This is the central mechanistic claim, and the evidence is clear and replicated across multiple model families (Llama-2, Llama-3, Mistral).

However, a limitation is that the retrieval head ratio (25% for MHA, 50% for GQA) is treated as a fixed design choice rather than being systematically explored across a continuous range for each model and benchmark. Figure 13 (panel 3) only sweeps the ratio for one model (Mistral-7B) on two tasks. It would strengthen the paper to show how accuracy degrades as the retrieval head ratio is reduced below the chosen thresholds, helping practitioners understand the sharpness of the trade-off.

#### Does the paper demonstrate that the optimization-based identification method is superior to attention profiling?

**Yes, with direct comparative evidence.** Figure 13 (panel 1) directly compares the two methods on both passkey retrieval and MMLU, and the optimization approach consistently and substantially outperforms. Tables 5 and 6 show that DuoAttention outperforms FastGen (which uses attention profiling) on LongBench tasks. The paper provides a clear conceptual argument for why output-aware identification should be better (value states matter, downstream propagation matters, input-dependence matters), and the empirical results align with this argument.

A missing experiment: the paper does not ablate the threshold binarization approach. What happens if heads with intermediate gate values (e.g., 0.3-0.7) are treated differently — perhaps with a larger sink/recent window rather than full or streaming? The binary classification is a practical simplification, but the continuous gate values in Figure 4 show a distribution, not two clean clusters. Quantifying the accuracy loss from binarization itself (vs. keeping continuous gate values, even if that's not deployable) would clarify whether there is headroom for more nuanced deployment policies.

#### Does the paper demonstrate that DuoAttention achieves the claimed efficiency numbers (2.55× memory reduction for MHA, 2.18× decoding speedup, etc.)?

**Yes, with measured results on real hardware, but the maximum numbers require context.** Figures 9, 10, and 11 present latency and memory measurements on an actual A100 GPU, not simulations or FLOP counts. The maximum reductions (2.55× memory for MHA, 1.67× for GQA; 2.18× speedup for MHA, 1.50× for GQA) are achieved at specific configurations: long context lengths where the retrieval head ratio dominates, and the most aggressive retrieval head ratios measured in the sweep (Figure 11). At shorter context lengths or with more conservative ratios, the improvements are smaller. This is expected — the benefits scale with context length — and the paper is transparent about showing the full scaling curves rather than just the headline maximums.

However, the paper does not report end-to-end generation throughput (tokens/second for a complete sequence), which is what practitioners care about. The per-token decoding latency is measured, but overhead from the non-attention components (linear layers, layer norm, etc.) is not broken out. The 2.18× speedup applies only to the attention computation, not the full model forward pass. The actual end-to-end speedup would be lower, and the paper does not quantify this.

Additionally, the pre-filling speedup numbers (1.73× for MHA, 1.63× for GQA) are reported as maximums across chunk sizes, but Figure 10 shows that the speedup is much larger at very small chunk sizes — the headline numbers appear to be chosen at moderate chunk sizes where the comparison is less extreme but perhaps more representative of deployment practice. The paper does not clearly explain how these specific headline numbers were selected from the chunk size sweep.

#### Does the paper demonstrate that DuoAttention preserves short-context capabilities?

**Yes, with reasonable coverage.** Figure 8 (MMLU, MBPP, MT-Bench on Llama-2-7B and Llama-3-8B) and Table 1 (Llama-3-70B) show that at 50% KV budget, DuoAttention achieves near-lossless performance across knowledge, coding, and dialogue benchmarks. This is important because it shows DuoAttention doesn't require separate short-context and long-context deployment configurations — the same model can handle both.

A gap: the paper does not evaluate on **medium-context** scenarios. All short-context benchmarks use sequences well within the model's native context window (a few thousand tokens at most), and long-context benchmarks push toward the maximum. What happens at intermediate lengths — say, 8K to 32K tokens — where the KV cache is non-trivial but retrieval demands are lower? The methods for streaming heads (sink + recent tokens) might need different sizing at these intermediate lengths, and the retrieval head ratio might be different. The paper doesn't explore this transition region.

#### Does the paper demonstrate that DuoAttention works with quantization and that the benefits compound?

**Yes, with a clear, practical measurement.** Figure 12 shows that DuoAttention alone enables 1.84M tokens on a single A100, and adding 8-bit weight + 4-bit KV quantization pushes this to 3.3M tokens. This is a measured, not extrapolated, result. The compounding is approximately multiplicative, confirming that the two techniques address orthogonal bottlenecks (DuoAttention reduces the number of KV entries; quantization reduces the bits per entry).

A limitation: the paper only tests one quantization method (QServe). The compatibility with other quantization schemes (e.g., KIVI, KVQuant) is assumed but not verified. This is probably fine — DuoAttention modifies which tokens are stored, not how they're encoded — but it means the 3.3M number is specific to the QServe implementation.

#### Missing experiments and genuine weaknesses

- **No error bars or confidence intervals.** All accuracy and efficiency numbers are point estimates without any indication of variance. For benchmarks with small test sets (some LongBench tasks have modest sample sizes), this makes it difficult to assess whether differences between DuoAttention and full attention are statistically significant or within measurement noise.

- **Single hardware configuration.** All efficiency measurements are on a single A100-80G. The paper does not report on other GPU generations (H100, consumer GPUs) or on multi-GPU setups. Memory and latency numbers are hardware-dependent, and the relative improvements might differ on hardware with different memory bandwidth or compute ratios.

- **The identification procedure uses a synthetic dataset that the paper itself must construct.** The method is not "automatic" in the sense of working out-of-the-box on any model without dataset preparation. The paper provides the recipe (10 passkeys of 32 words, BookSum, 50 length intervals), but this is still a manual step that requires generating synthetic data and running a 2000-step optimization. The cost (several hours on 8 GPUs) is modest but not negligible.

- **The retrieval head identification is performed at one specific configuration (sink=128, recent=256 during training) and one dataset type (passkey retrieval).** What if a model's long-context capability is needed for a different type of retrieval — say, multi-hop reasoning rather than literal string lookup? The paper doesn't test whether heads identified as retrieval via passkey data generalize to other retrieval types. The LongBench results provide some evidence of generalization, but a systematic study across retrieval types would strengthen the claim that the identification is robust to the synthetic data design.

- **No comparison to sparse attention methods that are not KV-cache-based**, such as MInference (which accelerates pre-filling via dynamic sparse patterns). The paper acknowledges MInference in Related Work but does not benchmark against it, noting it "does not optimize KV cache storage or latency during decoding." This is a fair scope limitation but means the pre-filling advantage over MInference is unquantified.

- **The threshold for binarization is set post-hoc to achieve a target ratio**, not derived from the optimization loss itself. An ideal method would have the L1 regularization strength set such that the sparsity emerges naturally at the optimal trade-off point, rather than requiring a separate sweep to pick the ratio. The paper does not explore whether the L1 penalty could be tuned to achieve this automatically.

#### Where the claims hold and where they are conditional

- **"Minimal accuracy loss" holds for NIAH, most LongBench tasks, and short benchmarks at the chosen ratios, but not for all LongBench tasks.** Tables 3 and 4 show some tasks where DuoAttention drops noticeably from full attention: for Llama-2-7B, MultiFieldQA-en drops from 33.95% (full) to 25.49% (DuoAttention 25%), and PassageRetrieval-en drops from 50.92% to 47.25%. For Llama-3-8B, LSHT drops from 38.00% to 30.00%. These are not catastrophic drops, but they are real. The paper's framing of "minimal" accuracy loss is valid in aggregate but overlooks task-specific degradation.

- **The efficiency claims (2.55× memory, 2.18× speedup, etc.) hold at long context lengths and aggressive retrieval head ratios.** At shorter contexts or with conservative ratios, the improvements shrink substantially. The abstract's "up to" language is appropriate, but readers should understand these are maximum achievable improvements, not what every deployment will see.

- **The 3.3M token capacity with quantization holds on an A100-80G.** This is an impressive number but is specific to a GPU with 80GB of memory. The same model with the same techniques on a smaller GPU would see proportionally lower capacity. The paper could be clearer that this is a capability demonstration, not a claim that all deployments will reach millions of tokens.

- **The method assumes that the attention sink and recent token sizes chosen during deployment match what the model needs.** The ablation in Figure 13 (panel 3) shows that performance plateaus at 16 sink + 64 recent tokens for one model, but this might be model-specific or task-specific. The paper does not ablate these choices on the long-context benchmarks directly, only on the Mistral passkey task.

## 6. Limitations and Trade-offs

### Difficulty Estimation Cost Is Unaccounted For in the Headline Efficiency Numbers

**The assumption or constraint.** The identification procedure that determines which heads are retrieval heads requires training gate values using a synthetic passkey-retrieval dataset. While the paper emphasizes that this procedure uses "only thousands of floating-point numbers" and completes in "several hours on an 8 GPU node" (Section 2.2), this cost is **not amortized into any of the reported efficiency numbers**. The headline memory reductions (2.55× for MHA, 1.67× for GQA) and latency improvements (2.18× decoding speedup for MHA, 1.50× for GQA) are measured at deployment time only, treating the identification phase as a sunk cost that has already been paid.

**The consequence.** For a practitioner deploying a single model for a single use case, the identification cost is likely acceptable — several hours of GPU time is modest compared to the original model training. However, in several realistic scenarios, this cost becomes material:

- **When deploying multiple model variants or fine-tuned checkpoints**: each variant requires its own identification run. A deployment pipeline with frequent model updates (e.g., weekly fine-tuning) would incur this cost repeatedly.
- **When the task distribution shifts**: the synthetic passkey dataset is designed to stress-test retrieval specifically. If a deployment's long-context demands differ substantially from literal string retrieval (e.g., multi-hop reasoning, summarization, temporal reasoning), the heads identified as "retrieval" by the passkey optimization may not be the right set to protect. Re-running identification on task-specific synthetic data would be necessary but is not explored.
- **When context lengths substantially exceed the training range**: the identification procedure uses training samples drawn from "50 intervals ranging from 1,000 tokens to the model-specific maximum length" (Table 2 lists these maxima: 4096 for Llama-2-7B-chat, 32000 for the long-context variants). A deployment targeting 1M+ token contexts would need identification data at or near that length, which the paper accomplishes for the Gradient-1048K variant (trained to 32K during identification) but may be insufficient for models natively trained to even longer contexts.

**What evidence exists in the paper.** The paper acknowledges this limitation explicitly in Appendix A.1 but does not quantify the cost or analyze its impact: "all training experiments in our paper can be conducted on 8×NVIDIA A100 GPU servers" is a statement of feasibility, not an analysis of whether the cost is prohibitive in any deployment regime. There is no ablation showing whether 2000 steps is the minimum needed, or whether fewer steps or shorter sequences would suffice.

**Mitigation status.** Not addressed. The paper does not explore amortization strategies (e.g., whether the identification generalizes across model versions, whether a distilled classifier could predict retrieval heads from a few forward passes, or whether the identification needs to be rerun at all after minor fine-tuning). Section 8 of the main paper is quite short and does not propose future work on reducing identification cost. This is a genuine gap: the method is presented as a deployment-time optimization, but the deployment pipeline itself requires a non-trivial training phase that is not folded into the cost model.

### Single Benchmark Family for Long-Context Evaluation: All Retrieval-Focused Tasks

**The assumption or constraint.** The paper's long-context evaluations rely on two benchmarks: Needle-in-a-Haystack (NIAH) and LongBench. While LongBench covers 21 tasks spanning question answering, summarization, and retrieval, the **synthetic identification procedure is trained on passkey retrieval data**, and the primary pressure test (NIAH) is also a retrieval task — finding a specific needle in a haystack. Even LongBench contains a substantial fraction of retrieval-oriented tasks (PassageRetrieval, MultiFieldQA, HotpotQA, etc.). The paper implicitly assumes that preserving retrieval fidelity is the primary objective of long-context inference, and that heads critical for retrieval are also critical for other long-context capabilities.

**The consequence.** For downstream applications where long-context processing is not primarily about precise information lookup, the retrieval-head identification procedure may produce a suboptimal compression policy. Consider:

- **Long-form summarization**: the model must integrate information broadly across the context, not retrieve a single fact. Heads that do "global attention" or "aggregation" might be compressed by DuoAttention because they cause little output deviation on passkey recall, yet they could be essential for producing a coherent summary.
- **Multi-hop reasoning or question answering that requires synthesizing multiple distant facts**: the head responsible for binding two pieces of information together — neither of which alone constitutes a "retrieval" — might be misclassified as a streaming head.
- **Code generation over long repositories**: the relevant context might be scattered across many files with complex dependencies; literal retrieval of a single function signature is only one component of the task.

The paper shows strong LongBench results (Figure 7, Tables 3-4), which provides some evidence of generalization beyond pure retrieval. However, LongBench's task distribution is still weighted toward retrieval-adjacent capabilities. There is no evaluation on a benchmark designed to stress-test other long-context capabilities (e.g., book-level summarization, long-document translation, or multi-session dialogue coherence) under DuoAttention compression.

**What evidence exists in the paper.** The strongest evidence that the identification generalizes is the LongBench results themselves, where DuoAttention matches full attention on most tasks at the target budget. However, Tables 3 and 4 also reveal tasks where DuoAttention drops noticeably from full attention: for Llama-2-7B-32K-Instruct at 25% budget, MultiFieldQA-en drops from 33.95% (full) to 25.49% (DuoAttention), and PassageRetrieval-en drops from 50.92% to 47.25%. For Llama-3-8B-Instruct-1048K at 50% budget, LSHT (a legal summarization task in Chinese) drops from 38.00% to 30.00%, and NarrativeQA drops from 26.56% to 24.54%. These are not catastrophic drops, but they suggest that the passkey-optimized head selection is not perfectly aligned with all long-context task formats.

**Mitigation status.** Partially addressed. The paper demonstrates that the synthetic data approach works better than language modeling for identifying retrieval heads (Figure 13, panel 1), which is good. But it does not explore whether task-specific synthetic data (e.g., summarization-oriented synthetic data for summarization deployments) would yield different head classifications and better task-specific accuracy. The paper implicitly assumes that passkey retrieval is a universal proxy for long-context capability, but this assumption is not tested head-to-head against other potential proxy tasks. Future work could explore whether different synthetic data designs produce meaningfully different retrieval head sets for different downstream tasks.

### Hard Problems and Very Long Contexts: The Retrieval Head Ratio May Need to Be Context-Length-Dependent

**The assumption or constraint.** The paper fixes the retrieval head ratio at a single value per model architecture (25% for MHA, 50% for GQA) and uses this ratio across all context lengths and all benchmarks. The underlying assumption is that the **ratio of retrieval-critical to streaming heads is constant regardless of how long the context is**. A head that is a streaming head at 8K tokens is assumed to remain a streaming head at 1M tokens.

**The consequence.** This assumption may break down at extreme context lengths for a subtle reason: as the distance between the query and the relevant information grows, the precision required from the attention mechanism increases. A head that can afford to be "sloppy" (attending broadly) at 4K tokens might need more precise, retrieval-like attention at 1M tokens, because the signal-to-noise ratio degrades as the number of attended tokens increases. The paper's identification procedure trains gate values on sequences up to the model's maximum training length (32K tokens for the long-context variants), meaning the gate values reflect the head's importance at that specific length scale. A model deployed at 1M tokens is operating an order of magnitude beyond where its retrieval heads were identified.

The practical failure mode would be: at moderate context lengths (the evaluation range in most of the paper), DuoAttention performs well because the identified retrieval heads are sufficient to handle the retrieval demands. At extreme context lengths (close to and beyond the model's training context), the constant ratio may be insufficient — heads that were classified as streaming at 32K might become retrieval-critical at 1M — leading to accuracy degradation that the paper does not measure.

**What evidence exists in the paper.** The NIAH results for Llama-3-8B-Instruct-Gradient-1048K (Figure 6, right panel) show DuoAttention maintaining retrieval accuracy out to the full 1048K context length at a 50% retrieval head ratio. This is the strongest counter-evidence to the concern: even though the identification was done at training lengths up to 32K, the resulting head classification transfers to 30× longer contexts. This is genuinely impressive and suggests that the retrieval/streaming distinction is an architectural property of the pre-trained model, not a length-dependent phenomenon. However, the 1048K model is a specific long-context fine-tuned variant — it is unclear whether the same transfer would hold for a base model pushed far beyond its training context via a technique like self-extend or RoPE rescaling.

Additionally, the paper does not sweep the retrieval head ratio as a function of context length. Figure 11 sweeps the ratio at a fixed context length. Figure 9 sweeps context length at a fixed ratio. There is no experiment asking: "at 1M tokens, is 50% retrieval heads still sufficient, or would 60% be needed to match full attention?"

**Mitigation status.** Not addressed. The paper treats the retrieval head ratio as a property of the architecture (MHA vs. GQA) and selects a single value that works across all tested lengths. This is a reasonable pragmatic choice given the strong empirical results, but it leaves open the question of whether more aggressive compression is possible at short-to-medium lengths (where fewer retrieval heads might suffice) or more conservative compression is needed at extreme lengths. This is a tradeoff the paper does not resolve: the fixed ratio is simple and works, but it may leave efficiency on the table for shorter contexts or accuracy risk for longer ones. Future work could explore length-adaptive retrieval head ratios, where the set of heads treated as retrieval expands as the context grows beyond certain thresholds.

### No Measurement of End-to-End Throughput or Latency Sensitivity to the Sequential/Parallel Mix

**The assumption or constraint.** The paper reports two separate latency metrics: per-token decoding latency (Figure 9) and total pre-filling latency (Figure 10). Both are measured under the assumption of a single sequence being processed. However, **DuoAttention introduces a structural asymmetry in the attention computation** that has implications for batch processing and pipeline parallelism that the paper does not measure. Specifically, the retrieval heads compute full attention with O(L) cost per token while the streaming heads compute O(1) attention per token. In a batched inference setting where multiple sequences of different lengths are being decoded simultaneously, this asymmetry could create load imbalance or require padding that erodes efficiency gains.

**The consequence.** For a practitioner deploying DuoAttention in a production serving system, the relevant metric is not per-token latency on a single sequence but **throughput** — tokens generated per second across a batch of requests under a latency service level objective (SLO). The paper's efficiency numbers (2.18× decoding speedup for MHA) apply to the attention computation for a single sequence. In a batched setting, several factors could reduce the realized throughput improvement:

- **Batch padding**: if sequences in a batch have different context lengths, the retrieval heads' attention cost is dominated by the longest sequence in the batch. The streaming heads' constant cost provides less relative benefit when the batch's effective context length is determined by its longest member.
- **KV cache memory pressure under batching**: the memory savings from DuoAttention are per-sequence. If a system is designed to run large batches (where throughput is maximized), the per-sequence memory reduction translates to being able to fit more sequences in GPU memory. But the paper's memory measurements (Figures 9, 10, 11) are for a single sequence. The batched case is not evaluated.
- **Pipeline bubbles**: the paper reorders attention heads into contiguous retrieval and streaming blocks. If the retrieval block's computation takes significantly longer than the streaming block's (at long context lengths), the downstream operations (concatenation, output projection) may need to wait, creating pipeline bubbles that reduce GPU utilization.

The paper acknowledges that DuoAttention "is well-suited for batch operations, which can further enhance LLM efficiency in serving scenarios with large batch sizes" (end of Section 2.3), but this claim is **never evaluated**. No batching experiments are reported.

**What evidence exists in the paper.** None. All efficiency measurements are single-sequence. The paper does not report tokens-per-second throughput, does not measure performance under continuous batching, and does not profile GPU utilization or pipeline stalls. The efficiency numbers are best-case for a single inference stream.

**Mitigation status.** Not addressed. The paper asserts batching compatibility without evidence. This is a significant gap because most production LLM deployments use continuous batching precisely to maximize throughput. The claim that DuoAttention "is well-suited for batch operations" is plausible — the attention patterns are static, not dynamic, so batching should work similarly to full attention — but the magnitude of throughput improvement relative to full attention under realistic serving conditions is unknown. Future work should measure tokens-per-second under continuous batching with a production-grade serving framework (e.g., vLLM) at various batch sizes and sequence length distributions.

### Retrieval Head Identification Is Static and Does Not Adapt to Input Content

**The assumption or constraint.** DuoAttention's identification procedure produces a **single, static classification** of each attention head as either retrieval or streaming. This classification is baked into the model's weight matrices via the reordering step (Section 2.3) and applied uniformly to **all inputs**, regardless of what the input actually requires. The implicit assumption is that a head's functional role — whether it performs retrieval or streaming attention — is invariant across prompts.

**The consequence.** This assumption is likely true in aggregate but may fail on specific inputs in ways that damage accuracy on those inputs. Consider a prompt where the answer is located in the very first sentence — all the "work" is done by the streaming heads' sink tokens, and the retrieval heads' full context is unnecessary. Conversely, consider a prompt requiring retrieval of a detail from the exact middle of a document that a particular streaming head would have attended to in the full-attention model. In the full-attention baseline, that head could have contributed to retrieving the answer; in DuoAttention, it cannot, because it has been statically classified as streaming and its KV cache was pruned.

The paper provides no mechanism for **input-adaptive** head classification — for instance, using a lightweight controller that examines the prompt and decides which heads to treat as retrieval on a per-request basis. The head classification is determined solely by the offline optimization on synthetic passkey data.

**What evidence exists in the paper.** The LongBench per-task results (Tables 3 and 4) show task-level variation in how well DuoAttention tracks full attention. On some tasks (e.g., HotpotQA), DuoAttention matches or exceeds full attention. On others (e.g., LSHT, MultiFieldQA-en), there is a noticeable gap. This could be interpreted as evidence that the static head classification is better suited to some task formats than others — tasks where the retrieval heads naturally align with the task's information-seeking patterns perform well; tasks where the "retrieval" is distributed across heads that the optimization classified as streaming perform less well. However, the paper does not analyze the per-task variance through this lens, so this remains a hypothesis rather than a demonstrated failure mode.

The NIAH results (Figure 6) are the strongest counter-evidence: if the static classification were brittle to input content, we would expect to see failures at specific document depths or context lengths where the needle happens to fall in a "blind spot" for the static head assignment. The heatmap is uniformly strong, suggesting that the classification generalizes well across needle positions. However, NIAH is a single retrieval task; the variation across more diverse LongBench tasks suggests the static classification may be a source of task-dependent accuracy loss.

**Mitigation status.** Not addressed. The paper does not discuss input-adaptive head classification, nor does it analyze whether the per-task accuracy gaps in LongBench correlate with the mismatch between static head assignments and task-specific retrieval patterns. The binary, static classification is a deliberate design choice for simplicity and efficiency (avoiding per-token decision overhead), and the paper's strong aggregate results justify this choice. But it represents a fundamental tradeoff: **simplicity and predictability vs. input-specific optimality**. An input-adaptive version of DuoAttention could potentially achieve better accuracy at the same compression ratio by promoting certain streaming heads to retrieval on inputs that specifically require their participation, but this would require an online classification mechanism that the paper does not develop or evaluate.
