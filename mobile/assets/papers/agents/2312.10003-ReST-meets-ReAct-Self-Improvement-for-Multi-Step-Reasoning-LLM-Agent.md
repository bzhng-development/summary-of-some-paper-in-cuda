# ReST meets ReAct: Self-Improvement for Multi-Step Reasoning LLM Agent

**ArXiv:** [2312.10003](https://arxiv.org/abs/2312.10003)

## 🎯 Pitch

This paper introduces **ReST meets ReAct**, a method that applies Reinforced Self-Training (ReST)–style iterative self-improvement to a process-based ReAct LLM agent for multi-step web-search question answering, using the PaLM 2 model family and composing synthetic trajectories with AI feedback as a ranking reward model rather than human labels.

---

## 1. Executive Summary

This paper introduces **ReST meets ReAct**, a method that applies Reinforced Self-Training (ReST)–style iterative self-improvement to a process-based ReAct LLM agent for multi-step web-search question answering, using the PaLM 2 model family and composing synthetic trajectories with AI feedback as a ranking reward model rather than human labels. Starting from a prompted PaLM 2-L teacher, the agent generates long-form attributed answers through a structured pipeline of interleaved search, summarization, answer generation, and self-critique steps, then iteratively improves via a grow-improve loop—each iteration fine-tunes a model on re-ranked trajectories sampled from the previous iteration’s best policy. After two iterations of this self-improvement and self-distillation procedure, a fine-tuned PaLM 2-XS model (two orders of magnitude smaller than the teacher) reaches 65.9% accuracy on the Bamboogle auto-eval benchmark, matching or approaching the prompted large model’s 70.3%, and 63.0% on the held-out BamTwoogle test set—comparable to the teacher’s 68.0%—establishing that multi-step reasoning agent performance can be preserved under extreme compression only when iterative process-based synthetic data generation is combined with AI-feedback re-ranking rather than outcome-based correctness filtering.

## 2. Context and Motivation

### The Core Problem: We Can't Directly Train Multi-Step Reasoning Agents End-to-End

The fundamental challenge this paper addresses is deceptively simple: **how do you fix a multi-step LLM agent when it makes mistakes?** For outcome-based systems — a chatbot that produces a single response, a classifier that outputs a label — the answer is straightforward: collect more labeled data where the correct output is known, and fine-tune on it. The system produces one output; the output is either right or wrong; you train on right-wrong signals.

But this breaks down entirely for process-based systems, which this paper defines as LLM agents that execute a sequence of reasoning steps and tool interactions to achieve a goal. The Search Agent studied here, for example, interleaves web search queries, snippet summarization, answer drafting, and self-critique — a trajectory of 5+ distinct LLM calls, each conditioning on the outputs of previous steps. When such an agent produces a wrong final answer, the failure could originate from any step in the chain: a poorly formulated search query, a missed relevant snippet, an incomplete summary, a logical leap in the answer draft, or a flaw in the self-critique that should have caught the error.

The critical impossibility the paper identifies (Section 1, paragraph 1) is that **interaction with external knowledge is non-differentiable**. You can't backpropagate through a Google search API call. You can't compute a gradient for "the third search query should have included the word 'cargo' instead of 'trunk'" and propagate that signal backward to update the LLM's decision-making policy. In the authors' words:

> "we cannot directly train them end-to-end to fix such failures, as interaction with external knowledge is non-differentiable."

This is not just an implementation inconvenience. It's a structural barrier that separates process-based agents from the dominant paradigm of end-to-end gradient-based optimization that has driven so much progress in machine learning. If you can't differentiate through the environment, you need an entirely different training signal — and that signal is expensive to obtain.

### Why This Problem Matters: The Shift from Outcome-Based to Process-Based Systems

The paper situates this challenge within a broader shift in how LLMs are being deployed. The authors observe an "explosive growth" (Section 1) in techniques, frameworks, and libraries for defining process-based workflows with LLMs — they cite Chain-of-Thought prompting (Gao et al., 2023), Self-Refine (Madaan et al., 2023), DSP (Khattab et al., 2023a), DSPy (Khattab et al., 2023b), LangChain (Chase, 2022), and LlamaIndex (Liu, 2022). The ReAct framework (Yao et al., 2022) in particular has become a popular recipe for LLM agents that interleave reasoning traces with tool-use actions.

This shift matters because **many real-world problems require compositionality that outcome-based systems cannot provide**. The Bamboogle dataset (Press et al., 2023) that the paper uses for evaluation consists of 2-hop questions deliberately constructed to be unanswerable by a direct Google search — for example, "What is the maximum airspeed of the third fastest bird?" requires first identifying which bird is third fastest, then looking up that bird's airspeed. No single search query can retrieve both facts; the system must decompose the question, execute sequential searches, and compose the results. This compositional reasoning capability is precisely what multi-step agents are designed to provide.

But the shift from outcome-based to process-based systems introduces a **training data bottleneck** that outcome-based systems don't face. The authors identify two dimensions of this bottleneck (Section 1, paragraph 3):

**First, the quantity problem.** Process-based systems require significantly more labeled data than outcome-based systems because the supervision signal must cover intermediate steps, not just final outputs. The paper cites Uesato et al. (2022) and Lightman et al. (2023) as evidence that process supervision demands larger datasets. If you're labeling final answers, you get one labeled example per question. If you're labeling reasoning steps, you get one labeled example per step per question — a multiplicative increase.

**Second, the difficulty problem.** It is "generally harder for humans to determine an optimal multi-step trajectory" (Section 1, paragraph 3) than to judge the correctness of a single output. A human can look at a final answer and say "that's wrong" or "that's right." But determining whether a particular intermediate search query was optimal — whether a different query would have retrieved better information, whether the agent should have done one more search or stopped earlier, whether the snippet summarization captured the right level of detail — requires expertise, careful analysis, and often domain knowledge. This makes high-quality human labeling for process-based systems not just abundant but expensive.

The paper's motivation crystallizes here: if process-based agents are essential for compositional reasoning, and if labeling process-level data is expensive and difficult, then **we need methods for improving agent performance that don't depend on human-labeled process supervision**. This is the gap that ReST meets ReAct aims to fill.

### Where Existing Approaches Fall Short

The paper identifies several classes of prior work and explains why each fails to fully address the problem of improving multi-step reasoning agents without human labels.

**Outcome-based self-improvement methods address the wrong problem.** The paper explicitly contrasts its approach with STAR (Zelikman et al., 2022), ReST (Gulcehre et al., 2023), ReST$^{EM}$ (Singh et al., 2023), and RAFT (Dong et al., 2023) — all methods for self-improvement from AI feedback that operate on outcome-based systems. These methods assume a correctness signal: they filter generated outputs by whether the final answer matches a known ground truth (STAR, ReST$^{EM}$) or rank them using a reward model trained on human preference data (ReST, RAFT). The paper's setup explicitly violates both assumptions: the questions are open-ended with long-form paragraph answers where exact match is meaningless (an answer about hummingbird airspeed expressed as "320 kph" versus "about 320 kilometers per hour" versus "320 km/h" — are these correct or incorrect?), and there is no reward model trained on human preferences available for the Search Agent's intermediate steps. The authors state:

> "Unlike STAR and ReST$^{EM}$, we don't use the correctness of the answer as a signal. And, unlike ReST and RAFT, we don't have the proper reward model trained on human preferences." (Section 7)

This is not a minor adaptation — it's a fundamentally different training regime. Outcome-based self-improvement methods lean on a binary correctness signal that process-based open-ended QA systems cannot provide.

**Manually prompted agents are brittle and don't improve.** The most common practice for building LLM agents, the paper notes, is to "set up language agents with manually designed few-shot prompts" (Section 7, citing Press et al., 2023; Yao et al., 2022; Shinn et al., 2023). This approach works — the paper's own prompted PaLM 2-L achieves 70.3% on Bamboogle — but it has a hard ceiling: you can tune the prompt, but you can't fundamentally change the model's behavior without fine-tuning. The model's knowledge of how to formulate effective search queries, what makes a good summary, and how to detect grounding failures is frozen at whatever level the pre-trained model possesses. Moreover, the paper emphasizes (Section 3.6) that the initial prompted model must be "capable of performing the Search Agent task at a certain level" — if the pre-trained model's baseline performance is too low, there are no good trajectories to bootstrap self-improvement from.

**Human-labeled fine-tuning doesn't scale to process data.** WebGPT (Nakano et al., 2021) is the closest prior work to the paper's Search Agent setup — it tackles long-form question answering with web search and uses imitation learning plus RL from a "large number of human demonstrations." But as the paper notes (Section 7), this approach requires extensive human involvement: human raters must evaluate not just final answers but also the quality of search queries, the relevance of selected links, and the faithfulness of generated text to retrieved sources. The authors position their work as aiming to "minimize human involvement" — their only labeled demonstrations are the few-shot exemplars in the prompts (which are manually written once and then reused across all iterations). No additional human labels are used for training or filtering.

**FireAct (Chen et al., 2023) fine-tunes agents but still uses human labels.** The paper identifies FireAct as the closest prior work in terms of fine-tuning setup, with the crucial difference that "we don't use human labels for training or data filtering" (Section 7). FireAct demonstrates that fine-tuning an LLM agent on multi-step trajectories improves performance, but those trajectories are selected using human-labeled correctness judgments. The paper's contribution is doing the same thing — iterative fine-tuning on agent trajectories — but with AI feedback replacing human judgment at every step.

**The self-critique paradox.** The paper engages with a specific tension in the literature around self-critique / self-correction in LLMs. Huang et al. (2023) famously found that "large language models cannot self-correct reasoning yet" — that prompting an LLM to check its own work and revise errors actually hurts performance on reasoning tasks. This is a deeply concerning finding for the Search Agent architecture, which includes two explicit self-check steps (relevance and grounding). The paper doesn't resolve this tension theoretically, but Section 6 notes that their empirical findings "contrast the recent observations" — in their process-based multi-step setup, self-critique provides a "small but measurable positive boost." This discrepancy itself motivates the need for systematic study of when and why self-critique works in agentic contexts.

### How This Paper Positions Itself

The paper positions itself at the intersection of two research threads that haven't been combined before: **ReAct-style process-based agent architectures** (for decomposing complex questions into tool-use trajectories) and **ReST-style iterative self-training** (for improving models without human labels). The title "ReST meets ReAct" is literal: bring the self-improvement machinery from Reinforced Self-Training into the multi-step, non-differentiable world of ReAct agents.

The key adaptation that makes this possible is replacing ReST's typical reward model (trained on human preference data, used for threshold-based filtering) with a **zero-shot LLM ranking model** that evaluates intermediate actions. The paper describes this in Section 3.5:

> "our approach differs from ReST, which uses threshold-based filtering with a reward model (RM) trained on human preference data. What we do is closer to RAFT (Dong et al., 2023), where the reward model ranks sampled responses to select high-scoring subsets for model fine-tuning."

This is a pragmatic, practically-motivated choice: training a proper reward model would require human preference labels that the paper explicitly wants to avoid. Instead, an instruction-tuned PaLM 2-L is prompted to compare multiple candidate actions (search queries, summaries, answers) and select the best one. The ranking matters more than absolute scores — the system doesn't need to know *how good* an action is, only which of several candidates is *best*.

The paper also positions itself relative to the **self-distillation** literature. A crucial aspect of their framework is that the synthetic data generated by the large teacher model during self-improvement can be used to fine-tune smaller models — not just the same-sized model. This is why Figure 1 shows results for PaLM 2-XS and PaLM 2-S, not just PaLM 2-L. The authors frame this as a practical benefit: if the expensive iterative self-improvement loop only needs to be run once (on the large model), and the resulting high-quality synthetic data can then distill performance into smaller, cheaper models, the approach becomes much more cost-effective for deployment.

A subtle but important positioning choice: the paper selects the "code as the prompt" paradigm (Section 3.1), formatting all agent prompts as Python code with dataclasses, type annotations, and todo-style comments. This is justified by three observations: (1) code is structured and easier to parse for downstream tool integration, (2) code combines structure ("keywords and syntax") with natural language ("comments and descriptive naming"), and (3) LLMs are trained on code and can both read and write it. But this choice has a consequence the paper is explicit about: "only the PaLM 2-L can perform it consistently well" out of the pre-trained models they tried (Section 3.1). This makes the teacher model a hard constraint — smaller pre-trained models can't reliably follow the code-as-prompt format, which is why the distillation pipeline (fine-tuning smaller models on trajectories generated by the large model) is necessary rather than optional.

Finally, the paper positions its evaluation methodology as a contribution in itself. The Bamboogle dataset (125 questions) is small, and the paper introduces BamTwoogle (100 questions) as a held-out test set specifically to guard against overfitting from using Bamboogle as a validation set during development. More importantly, the paper develops and validates an **auto-eval protocol** (Section 4.2) that uses PaLM 2-L to judge whether the agent's long-form answer implies the reference answer, reporting a Pearson correlation of 0.98 with human evaluations. This matters because the agent's answers are paragraphs with citations, not single tokens or short phrases. Without reliable auto-eval, measuring performance across 10 runs per model (to account for stochastic trajectories) would be prohibitively expensive. The paper frames auto-eval as solving both the scale problem ("doing one human eval is much easier than doing five") and the variance problem ("we can't easily reduce the variance by increasing the number of repetitions per question with human evals").

## 3. Technical Approach

### 3.1 Reader Orientation

This paper builds a system that **iteratively improves a multi-step web-search question-answering agent without ever using human-labeled correctness judgments** — it learns purely from self-generated trajectories that are filtered and ranked by a zero-shot LLM critic. The core idea is that you can treat an agent's entire reasoning chain (search queries, snippet summaries, answer drafts, self-checks) as training data for fine-tuning, even when you don't know what the "correct" chain should have been, as long as you have a way to distinguish better trajectories from worse ones using AI feedback.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components organized around a **ReST-style outer-inner loop**:

1. **Search Agent State Machine** — a ReAct-style agent with five distinct reasoning steps (search decision, tool output summarization, answer generation, relevance self-check, grounding self-check) that calls a search API as its tool. It receives a question and produces a long-form attributed answer.

2. **Prompted Teacher Model (PaLM 2-L)** — the pre-trained large language model that executes the Search Agent flow guided by few-shot exemplars formatted as Python code. It serves as the initial policy from which all synthetic data originates.

3. **Trajectory Generator ("Grow" Phase)** — samples the current best policy (starting with the prompted teacher, then advancing to the fine-tuned model from the previous iteration) on 2000 fixed seed questions to produce completed agent trajectories. Each trajectory is a sequence of five step-types with their inputs, outputs, and internal reasoning.

4. **AI Ranking Reward Model** — an instruction-tuned PaLM 2-L prompted zero-shot to compare multiple candidate actions for a single reasoning step and rank them from best to worst. It replaces both the correctness-based filtering of STAR/ReST$^{EM}$ and the human-preference-trained reward model of ReST/RAFT, enabling fully automated quality selection without any human labels.

5. **Fine-Tuning Pipeline ("Improve" Phase)** — decomposes collected trajectories into individual reasoning steps, optionally re-ranks the best candidate using the ranking model, constructs a fine-tuning mixture from these steps, and fully fine-tunes models of three sizes (XS, S, L) on this mixture. The fine-tuned large model then becomes the new policy for the next "grow" iteration.

Information flows in a cycle: **questions → prompted L model → trajectory collection → AI ranking of candidate actions → fine-tuning mixture construction → fine-tuned models (L, S, XS) → next iteration's L model generates better trajectories → repeat**. The fine-tuned XS and S models represent distillation — they never generate training data, only consume it.

### 3.3 Roadmap for the Deep Dive

- **First**, the Search Agent state machine — its five reasoning steps, the code-as-prompt paradigm, and the per-step sampling-and-selection procedure — because this defines the structure of every trajectory and what exactly is being trained on.
- **Second**, the input data construction — the four-source dataset of 2000 seed questions and why these specific sources were chosen — because seed questions determine the distribution the agent learns to handle.
- **Third**, the trajectory collection protocol for the "grow" phase — how 2000 questions become completed trajectories, temperature settings, number of samples per step, and the perplexity-based default selection — because this is the raw material for everything downstream.
- **Fourth**, the AI ranking reward model — the zero-shot prompt, the candidate comparison format, and when ranking is applied (off-policy during mixture construction vs. on-policy during trajectory generation) — because ranking is the mechanism that replaces human labels.
- **Fifth**, the fine-tuning mixture construction — how trajectories are split into step-level examples, how re-ranking modifies the default selection, and the resulting dataset sizes — because this is the bridge between trajectory collection and model training.
- **Sixth**, the iterative self-improvement loop — the full grow-improve cycle across two iterations, how the teacher model is updated between iterations, and the self-distillation pathway to smaller models — because this is the core algorithm the paper contributes.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems and training methodology paper** whose core idea is that a process-based LLM agent can bootstrap its own improvement through iterative self-training with AI feedback on intermediate actions, without any human-labeled correctness signals, and that the resulting synthetic data simultaneously enables model compression through distillation.

---

#### The Search Agent State Machine

The Search Agent is defined as a finite state machine with five distinct reasoning steps (Section 2, Figure 2). Each step corresponds to one LLM call, and the calls are chained sequentially — the output of each step becomes part of the context for all subsequent steps. The five steps are:

**Step 1: Decision Step.** The agent receives the original question and its full history of past actions. It must decide whether it needs additional information from web search to answer the question or whether it already has enough information to terminate the search loop. If it decides to search, it must also formulate the search query — the `Search(query=...)` action — and provide its reasoning in a `thoughts` field. The decision is structured as an `ActionWrapper` dataclass with fields `thoughts: str` and `action: Action`, where `Action` can be either `Search(query=...)` or `Terminate()`. The number of remaining allowed searches is tracked in a `REMAINING_SEARCHES` field (capped at 10 per trajectory, as specified in Section 3.2), and past actions are accumulated in a `PAST_ACTIONS` list that preserves the full history of what the agent has done and learned.

**Step 2: Search Result Filtering and Summarization.** After the search API returns results (configured to return top-3 snippets per query via an internal Google Q&A API, Section 3.2), the agent receives the current search results and must select which result items are relevant to the original question, summarize the selected information in a grounded fashion, and record its reasoning. The output is a `LinkSelection` object containing `selected_link_ids`, a `grounded_summarization` string that explicitly cites which link IDs support each claim, and a `thoughts` field. This step is crucial because it determines what information enters the agent's working memory — poorly selected or summarized information at this stage will propagate errors into the final answer.

**Step 3: Answer Generation.** When the agent has terminated the search loop, it receives all past actions (including all selected links and grounded summarizations) and must produce a draft answer. The output is an `Answer` object with `thoughts` and `answer` fields. The answer is explicitly required to be attributed — claims must reference the `[link_id=N]` format to connect statements back to their source snippets. This is a deliberate design choice inherited from WebGPT (Nakano et al., 2021); the authors emphasize "explicitly attributable final answers" (Section 1, paragraph 2).

**Step 4: Relevance Self-Check.** The agent receives the original question, its entire action history, and the draft answer. It must determine whether the answer addresses the original question. If it passes, the action is `Check_Answer(passed=True)`. If it fails, the action is `Revise_Answer(revised_answer=...)` — the agent must produce a corrected answer that better addresses the question. This is the first of two self-critique steps.

**Step 5: Grounding Self-Check.** The agent receives the same context as Step 4 (original question, past actions, current answer) and must verify that all claims in the answer are supported by the information actually present in the retrieved snippets. As with Step 4, the output is either `Check_Answer(passed=True)` or `Revise_Answer(revised_answer=...)`. The grounding check specifically examines whether the answer's content matches what the search snippets actually say — it's checking for hallucination or fabrication, not just relevance. The final answer after both self-checks is what the system reports.

**The code-as-prompt paradigm (Section 3.1).** All five steps use few-shot prompts formatted as Python code with dataclasses, type annotations, and comments. The prompts define Python classes like `Action`, `Search(Action)`, `Terminate(Action)`, `ActionWrapper`, and `ResultItem` as if implementing a real agent library. Each prompt then provides multiple input-output exemplars as if continuing the Python code. For example, Listing 1 (the Decision Step prompt) begins with `"""Implement an agent capable of answering complex queries by potentially search multiple times."""` followed by imports, class definitions, and numbered examples like `# Example 1:` where the input variables (`ORIGINAL_QUESTION`, `PAST_ACTIONS`, `REMAINING_SEARCHES`) are assigned literal values and the output (`ACTION_SELECTED = ActionWrapper(...)`) follows. The model is expected to continue the Python code by producing the correct `ACTION_SELECTED` assignment.

The authors justify this unusual choice with three observations: first, "there is often a need to parse the LLM's output for integration with other systems and tools, which is much easier to do if the model's input and output are well-structured"; second, "code uniquely combines a structured aspect (keywords and syntax) with a natural language aspect (comments and descriptive naming)"; third, "LLMs are capable of both reading and writing code" (Section 3.1). The consequence — which the paper is explicit about — is that this format is challenging: "only the PaLM 2-L can perform it consistently well" among the pre-trained models they tested. This is the structural reason why distillation from L to S and XS is necessary rather than optional.

**Per-step sampling and selection (Section 3.2).** At each of the five steps, the model does not produce a single deterministic output. Instead, it generates **multiple samples** — 4 samples for PaLM 2-L and PaLM 2-S, and 16 samples for PaLM 2-XS — and then **selects the one with the lowest perplexity** to continue the trajectory forward. Perplexity here is the model's own token-level loss on the generated continuation; lower perplexity means the model considers the output more probable given its own distribution. This selection mechanism is the on-policy default: when the agent is actually executing (generating a trajectory from scratch), it uses perplexity-based selection because that's available without any external model call. The temperature for all sampling is set to `T = 0.5` (Section 3.2), determined through hyperparameter sweeps using Bamboogle auto-eval as described in Section 4.2.

**Search tool constraints.** The web search tool is the "internal Google Q&A API that returns top-k snippets," configured to return "top-3 snippets per query" (Section 3.2). The total number of searches per trajectory is limited to at most 10 via the `REMAINING_SEARCHES` counter in the prompts. The trajectory state — all actions taken so far — is preserved in the `PAST_ACTIONS` field, which grows with each step and provides the agent with full access to its search history, selected links, and grounded summarizations.

#### Input Data Construction

The paper constructs a set of 2000 diverse seed questions by randomly sampling from four existing datasets (Section 3.3):

- **500 questions from HotpotQA** (Yang et al., 2018): a multi-hop reasoning QA dataset requiring information from multiple documents to answer. This provides compositional questions that inherently require multi-step reasoning.
- **500 questions from Eli5** (Fan et al., 2019): a long-form question-answering dataset built from the Reddit forum "Explain Like I'm Five" (r/explainlikeimfive). These questions are open-ended "why" and "how" questions requiring paragraph-length explanatory answers.
- **500 questions from Eli5-askH** (Blagojevic, 2022): similar to Eli5 but sourced from the r/askhistorians subreddit, providing questions about historical topics.
- **500 questions from Eli5-askS** (Blagojevic, 2022): sourced from the r/askscience subreddit, providing questions about scientific topics.

The authors explicitly state that they "don't use any other information from these datasets, like labels" (Section 3.3). They do not filter trajectories by matching the correct answer from HotpotQA (the only source with ground-truth labels), they do not use these datasets' validation splits for hyperparameter tuning or performance assessment, and the 2000 questions serve purely as **seed prompts** to elicit agent behavior. The diversity — factual multi-hop questions (HotpotQA) plus explanatory open-ended questions across general knowledge, history, and science (the three Eli5 variants) — is intended to produce agent trajectories covering a range of reasoning patterns and difficulty types.

The fixed set of 2000 questions is reused across iterations — all "grow" phases sample trajectories from the same questions. This is a deliberate design choice that differs from standard ReST (which could expand the question set) and creates a controlled setting where improvements can be attributed to better policy execution rather than to seeing new questions.

#### Trajectory Collection Protocol ("Grow" Phase)

The "grow" phase takes a policy (initially the prompted PaLM 2-L, then the fine-tuned PaLM 2-L from the previous iteration) and produces completed agent trajectories for each of the 2000 seed questions. The protocol is:

1. For each question, initialize an empty `PAST_ACTIONS` list and set `REMAINING_SEARCHES = 10`.
2. Execute Step 1 (Decision Step): sample 4 candidate outputs from the model at `T = 0.5`, select the one with lowest perplexity. If the action is `Search(query=...)`, proceed to Step 2. If `Terminate()`, jump to Step 3.
3. Execute Step 2 (Summarization): call the search API with the query from Step 1, receive top-3 snippets, format them as `CURRENT_SEARCH_RESULTS`, sample 4 candidate summarizations, select lowest perplexity, append to `PAST_ACTIONS`. Go back to Step 1.
4. Repeat Steps 1-2 until either `Terminate()` is selected or `REMAINING_SEARCHES` reaches 0 (meaning 10 searches have been performed).
5. Execute Step 3 (Answer Generation): sample 4 candidate answers from all accumulated `PAST_ACTIONS`, select lowest perplexity.
6. Execute Step 4 (Relevance Self-Check): sample 4 candidate checks/revisions, select lowest perplexity. If a revision is produced, it replaces the answer for Step 5.
7. Execute Step 5 (Grounding Self-Check): sample 4 candidate checks/revisions from the updated answer, select lowest perplexity. The final revised answer (or the original if both checks passed) is the trajectory's output.

The result is one completed trajectory per question: a sequence of alternating Search and LinkSelection actions (the search loop) followed by an Answer, then up to two Check/Revise actions (the self-critique). Each trajectory preserves the full structure — the model's `thoughts` at every step, the queries it chose, the link IDs it selected, the grounded summarizations it wrote, and the answer it produced.

**Pilot data vs. main data.** The paper distinguishes between two scales of trajectory collection (Section 5.2, Table 3). The **pilot experiment** generates 500 trajectories using only HotpotQA and Eli5 questions (no Eli5-askH or Eli5-askS), with default perplexity-based selection and no RM re-ranking, followed by manual human filtering (approximately 30% of examples removed for being "bad" — unhelpful queries, empty thoughts, summaries missing important information, etc.). This yields 500 trajectories that convert into 4518 training examples (unfiltered) or 3015 training examples (human-filtered). The **main experiments** generate 2000 trajectories (iteration 1, "1st gen") using all four data sources, again with perplexity-based selection. For iteration 2 ("2nd gen"), the policy is the fine-tuned PaLM 2-L from iteration 1, and 8000 trajectories are generated by sampling each of the 2000 questions 4 times (the paper notes this as "analogous to a 'grow' stage in ReST", Section 5.2). The repetition — 4 trajectories per question rather than 1 — is motivated by the ablation in Table 3 showing a +2.2% gain when going from 1x to 2x trajectories per question.

#### The AI Ranking Reward Model

The paper replaces human-labeled reward models with a **zero-shot LLM ranking model** (Section 3.5). The ranking model is an instruction-tuned PaLM 2-L prompted to compare multiple candidate outputs for a single reasoning step and rank them from best to worst. The full prompt is shown in Listing 8.

**Prompt structure.** The prompt begins with a `Rater Instructions` section that defines the filtering goal:

> "The goal of this rating is to filter out bad actions, so that they'll be excluded from the fine-tuning dataset. Overall, we want to the agent to produce relevant and grounded answers with minimal steps. Anything that deviates from this goal is considered bad. If any element (thoughts, comments etc.) is empty, then it's automatically bad."

This is followed by the model's input context (the `Model Can See` section — original question, past actions, etc.) and then 4 candidate outputs labeled `Model Output #1` through `Model Output #4`. The rater must output exactly 3 lines:

```
Explanation: why you think model output #X is the best
Answer: #X
Ranking: #X > #Y > ...
```

**Key design differences from ReST/RAFT.** The paper explicitly contrasts this approach with two alternatives (Section 3.5, Section 7):

- **Unlike ReST** (Gulcehre et al., 2023), there is no threshold-based filtering with a reward model trained on human preference data. The ranking model provides relative comparisons ("which of these is best?") rather than absolute scores ("is this output above threshold?"). The paper notes this is "closer to RAFT (Dong et al., 2023), where the reward model ranks sampled responses to select high-scoring subsets for model fine-tuning, and the RM rankings matter much more than absolute scores."
- **Unlike STAR/ReST$^{EM}$**, there is no correctness signal used. The ranking model evaluates the quality of an action (its relevance, grounding, minimality) without knowing whether it ultimately contributes to a correct final answer. This is essential because the search agent answers open-ended questions where "correctness" is ill-defined.

**Where ranking is applied: off-policy vs. on-policy.** The paper makes a crucial distinction (Section 3.5):

> "we mainly do the LLM-based selection off-policy, i.e., by updating the current action used for fine-tuning. The on-policy trajectory rollouts use perplexity."

During the "grow" phase — when the agent is actually executing and producing trajectories — it uses perplexity-based selection because this is available without an additional costly LLM call for every step. During the "improve" phase — when collected trajectories are being converted into a fine-tuning mixture — the ranking model can be applied retrospectively: for each step in the collected trajectories, the system has 4 (or 16) candidate outputs that were generated, and instead of using the one with lowest perplexity, it uses the one ranked highest by the AI ranking model. This is "off-policy" because it changes which action goes into the training data without re-executing the trajectory — the original trajectory was generated with perplexity-based selection, but the fine-tuning data uses ranking-based selection.

This design choice has an important consequence: the agent's behavior during deployment (which uses perplexity) doesn't directly experience the ranking model's preferences. The ranking model's influence is purely through the training data distribution — the fine-tuned model learns to produce outputs that the ranking model would have selected, even though at deployment time the selection is still done by perplexity.

**Why a separate instruction-tuned model?** The ranking prompt (Listing 8) is notable for being the only prompt in the paper that is zero-shot (no exemplars) and does not use the "code as the prompt" approach. The paper states it's "intended to be used with an instruction-tuned model" — presumably because following free-form ranking instructions with explanations is a task that instruction-tuned models handle better than base models responding in a code-continuation format.

---

#### Fine-Tuning Mixture Construction ("Improve" Phase)

Converting collected trajectories into a fine-tuning dataset involves a specific decomposition and optional re-ranking procedure (Section 3.4):

**Trajectory decomposition.** Each completed trajectory is a sequence of 5+ LLM calls (search loop steps plus answer generation plus self-checks). The paper "splits each completed Search Agent trajectory into the reasoning steps" (Section 3.4). Each step becomes an independent training example: the input is the full context up to that point (original question, past actions, current search results if applicable, etc.), and the target output is the action the agent produced (search query, link selection with summarization, answer, or check/revise). This means a single trajectory of, say, 4 search steps + 1 answer + 2 self-checks produces 7 training examples, each training the model on one specific reasoning step type.

The decomposition is crucial because it enables the model to learn from steps that are part of trajectories that ultimately produce wrong answers. As the paper emphasizes (Section 6):

> "in this setup, the model can learn something useful even from the states that eventually lead to the wrong final answer."

A trajectory where the agent makes a good search query but later messes up the answer still contains a high-quality Search action that can improve the model's query formulation ability. This is a key advantage of process-based training over outcome-based training — the signal is finer-grained and doesn't require the entire trajectory to be correct.

**Off-policy re-ranking with RM.** During mixture construction, for each step that originally had 4 (or 16) candidate outputs, the system can call the AI ranking model to re-evaluate which candidate is best. The ranking model receives all candidates and selects the top-ranked one to include in the fine-tuning mixture, replacing the original perplexity-based selection. This is what the paper means by "apply re-ranking with RM during the conversion" (Section 3.6, Step 2).

**Dataset sizes.** Table 3 provides concrete numbers for the PaLM 2-XS experiments:
- Pilot, human-filtered: 500 trajectories → 3,015 training examples
- Pilot, unfiltered: 500 trajectories → 4,518 training examples
- 1st generation: 2,000 trajectories → 17,970 training examples
- 2nd generation (1 trajectory per question): 2,000 trajectories → 18,007 training examples
- 2nd generation (2 trajectories per question): 4,000 trajectories → 36,238 training examples
- 2nd generation (4 trajectories per question): 8,000 trajectories → 72,424 training examples

The conversion ratio is approximately 9 training examples per trajectory (17,970 ÷ 2,000 for 1st gen; 18,007 ÷ 2,000 for 2nd gen 1x), consistent with an average of roughly 4-5 search loop steps plus answer plus 2 self-checks equaling 7-8 examples per trajectory, with some variation due to variable search loop length.

**Full fine-tuning.** The paper uses "full fine-tuning for all the experiments" (Section 3.4) — meaning all model parameters are updated during training, as opposed to parameter-efficient methods like LoRA. The checkpoint selection is done per model size using Bamboogle auto-eval: step 9K for PaLM 2-XS, step 5K for PaLM 2-S, and step 3.5K for PaLM 2-L (Section 4.2). Larger models converge faster (fewer steps needed), which is consistent with standard scaling behavior. Training hyperparameters beyond the checkpoint selections are not explicitly provided in the main paper text; the focus is on the data generation and selection methodology rather than the optimization details.

#### The Iterative Self-Improvement Loop

The full algorithm integrates all components into a cyclical process (Section 3.6):

**Initialization.** Start with the prompted (not fine-tuned) PaLM 2-L model executing the Search Agent flow using the manually constructed few-shot prompts. This initial policy achieves 70.3% on Bamboogle auto-eval (Table 1, "Pre-trained" L column) — establishing the "certain level" of capability required to bootstrap self-improvement.

**Iteration 1 (Grow).** Use the prompted PaLM 2-L to generate 2000 trajectories (one per seed question) via the on-policy perplexity-based sampling protocol. This is the "1st gen" data.

**Iteration 1 (Improve).** Decompose the 2000 trajectories into step-level examples. Apply RM re-ranking to select the best candidate for each step (off-policy). Construct a fine-tuning mixture of 17,970 examples. Fine-tune PaLM 2-L, PaLM 2-S, and PaLM 2-XS models on this mixture. The fine-tuned L model achieves 74.0% on Bamboogle (Table 1, "Self-improvement, 1st gen" L column), a +3.7 percentage point gain over the prompted baseline. The fine-tuned S and XS models achieve 61.9% and 54.4% respectively — these are distillation results, since the smaller models never generated trajectories themselves.

**Iteration 2 (Grow).** Now use the fine-tuned PaLM 2-L from iteration 1 as the policy (not the original prompted model). Generate 8000 trajectories — each of the 2000 seed questions sampled 4 times — to produce the "2nd gen" data. The paper frames this repetition as "analogous to a 'grow' stage in ReST" (Section 5.2); the 4x repetition is motivated by the ablation in Table 3 showing diminishing returns beyond 2x (63.4% for 1x, 65.6% for 2x, 65.9% for 4x on XS).

**Iteration 2 (Improve).** Decompose the 8000 trajectories into step-level examples with RM re-ranking. Construct a fine-tuning mixture of 72,424 examples (for the 4x variant). Fine-tune PaLM 2-L, PaLM 2-S, and PaLM 2-XS models on this mixture. The fine-tuned L achieves 76.1% (Table 1), a further +2.1 percentage point gain over iteration 1. The fine-tuned XS achieves 65.9%, a dramatic +11.5 point gain over iteration 1 XS (54.4%) and within 4.4 points of the original prompted L (70.3%).

**Why not a third iteration?** The paper doesn't run iteration 3, but Section 6 flags the question of a saturation point as an open problem: "How many additional iterations of self-improvement can we undertake past the 2nd one that still results in non-trivial gains?" The diminishing returns from iteration 1 to iteration 2 (+3.7 for L in iteration 1, +2.1 for L in iteration 2) suggest the curve may be flattening, but whether this is due to the agent approaching the ceiling of what's achievable with this tool setup, the ranking model's limited discrimination ability, or the fixed question set being exhausted, is not determined.

**Self-distillation pathway.** A crucial feature of this loop is that the smaller models (S and XS) never participate in trajectory generation — they are purely consumers of the synthetic data produced by the large model. This makes their training a form of **knowledge distillation**: the large model's multi-step reasoning behavior, improved through self-training, is compressed into smaller architectures that couldn't have learned the task from scratch (since the code-as-prompt format requires a large model to execute). The paper emphasizes this in the abstract and conclusion: the fine-tuned XS achieves "comparable performance... with two orders of magnitude fewer parameters" than the prompted teacher.

**Fixed question set design choice.** The paper keeps the 2000 seed questions fixed across both iterations — the "grow" stage of ReST is modified to reuse the same questions rather than expanding the question pool. This is a deliberate simplification that makes the experimental design cleaner (performance improvements can't be attributed to seeing harder or different questions) but limits the diversity of training data. The paper doesn't discuss whether expanding the question set in later iterations would yield additional gains or whether the fixed set eventually leads to overfitting on the question distribution.

---

#### Design Choices and Their Rationales

**Code-as-prompt paradigm over natural language prompts.** The decision to format prompts as Python code (Section 3.1) is motivated by three practical considerations: (1) structured outputs are easier to parse for downstream tool integration, (2) code combines syntactic structure with natural language expressiveness, and (3) LLMs are capable of code generation. The trade-off — that only PaLM 2-L can reliably follow this format — is explicit and accepted.

**Perplexity-based on-policy selection over learned value function.** During trajectory generation, the agent selects among 4 candidate outputs at each step using minimum perplexity. This is computationally cheap (perplexity is a byproduct of generation) and doesn't require an external model call. The alternative — using the ranking model at every step during trajectory generation — would multiply the number of LLM calls by 4-16x, which is prohibitive for generating thousands of trajectories.

**Zero-shot LLM ranking over trained reward model.** The paper chooses an instruction-tuned LLM prompted zero-shot rather than training a reward model on human preference data. The stated reason is to "minimize human involvement" — the only human-labeled demonstrations are the few-shot exemplars in the five prompts. The trade-off is that the ranking model's preferences are not calibrated or validated against human judgments; the paper relies on downstream task improvement (Bamboogle accuracy) as the implicit validation that the ranking model's selections are beneficial.

**Off-policy re-ranking for data quality.** By applying the ranking model during mixture construction rather than during trajectory generation, the paper achieves data quality improvement without changing the agent's deployment behavior. The fine-tuned model learns from higher-quality examples than what the on-policy sampling would have produced, but at inference time the agent still uses simple perplexity-based selection. This is an asymmetric design: training benefits from expensive AI feedback, but inference remains lightweight.

**Full fine-tuning over parameter-efficient methods.** The paper uses full fine-tuning for all experiments, which is feasible because the models are small enough (PaLM 2-XS, S, L) and the data volume is modest (tens of thousands of examples). For much larger models, parameter-efficient methods would likely be necessary.

**Fixed 2000 questions over expanding question pool.** Unlike standard ReST which could expand the dataset, the fixed question set provides controlled iteration-to-iteration comparisons — any performance improvement must come from better policy execution, not from seeing more diverse questions. The potential cost is that the policy may overfit to the question distribution, though the BamTwoogle test set (held out and never used for training or hyperparameter selection) serves as a guard against this.

## 4. Key Insights and Innovations

### Innovation 1: Process-Based Self-Improvement Without Any Correctness Signal — A Fundamental Break from Outcome-Based Self-Training

The paper's most distinctive intellectual contribution is demonstrating that a multi-step reasoning agent can bootstrap its own improvement **without ever knowing whether its final answers are right or wrong**. This represents a categorical departure from the entire family of self-training methods that the field had developed up to this point.

**What the field did before.** Every major self-improvement paradigm for LLMs — STAR (Zelikman et al., 2022), ReST$^{EM}$ (Singh et al., 2023), ReST (Gulcehre et al., 2023), RAFT (Dong et al., 2023) — depended on some form of outcome-quality signal to filter or rank training data. STAR and ReST$^{EM}$ use binary correctness: generated solutions that produce the right final answer are kept; wrong answers are discarded. ReST and RAFT use reward models trained on human preference data, which provide a scalar quality score for complete outputs. In all four paradigms, the fundamental logic is the same: generate outputs, evaluate their quality using a signal external to the policy, and train only on the good ones. The quality signal applies to the **outcome** — the final answer, the complete response, the end product.

This logic breaks when you try to apply it to open-ended long-form question answering. The paper's Search Agent produces paragraph-length attributed answers to questions like "What's the white powdery residual often found on a humidifier?" The answer is explanatory prose with citations — and there is no single correct target string against which to judge correctness. An answer that says "the white dust is usually caused by mineral content in the water" and an answer that says "white dust consists of dried mineral deposits, typically calcium and magnesium from hard water" are both correct, and neither can be matched to a ground-truth label with an exact-match metric.

**What makes this innovation fundamental rather than incremental.** The paper doesn't just adapt ReST to a new domain — it reconceptualizes what the quality signal operates on. Instead of filtering trajectories by whether the final answer is "correct" (impossible for open-ended QA), the system applies AI feedback at the **step level**: each individual action (search query, snippet summary, answer draft, self-check) is ranked relative to alternative actions that could have been taken at that step, without reference to whether the trajectory ultimately yielded a good final answer. The paper makes this explicit:

> "in this setup, the model can learn something useful even from the states that eventually lead to the wrong final answer." (Section 6)

This is a conceptual shift from **outcome supervision** (which actions led to good outcomes?) to **process preference** (which actions are better than others, given the context?). The ranking model (Section 3.5, Listing 8) evaluates actions based on criteria like relevance, grounding, and minimality — not on whether they contribute to a factually correct conclusion. A well-formulated search query is a well-formulated search query regardless of whether the final answer gets the bird's airspeed right. A properly grounded summary is properly grounded regardless of whether the summary itself contains all the information needed.

**Why this matters beyond raw performance.** This innovation addresses a structural limitation that has kept self-improvement methods confined to tasks with clean correctness signals (math, coding, multiple-choice QA). If process-based self-improvement can work without outcome labels, it extends the reach of self-training to the vast space of real-world tasks where "correctness" is ambiguous, multi-dimensional, or defined only by human judgment — open-ended QA, summarization, analysis, recommendation, dialogue. The paper doesn't just present a method; it reframes what "supervision" means in a self-training loop. The supervisor doesn't need to know the right answer — it only needs to know which process looks better.

**Evidence anchoring.** The empirical proof that this works is in Table 1: after two iterations of process-based self-improvement with AI feedback, PaLM 2-L improves from 70.3% (prompted baseline) to 76.1% on Bamboogle auto-eval — a +5.8 percentage point absolute gain — without any human-labeled training data and without any outcome correctness filtering. The ablation in Table 3 further supports the point: going from iteration 1 data (17,970 step-level examples) to iteration 2 data with the same number of questions but better-quality actions (18,007 examples) yields a +9 percentage point gain on XS (54.4% → 63.4%), demonstrating that process-level quality improvement — not just more data — drives the gains.

---

### Innovation 2: The Grow-Improve Loop Decouples Exploration Quality from Deployment Cost Through Asymmetric Selection Strategies

The paper introduces a design pattern that is easy to miss on first reading but represents a genuine architectural insight: **use cheap selection during trajectory generation (so you can afford to explore) and expensive selection during training data construction (so the model learns from the best examples), without letting the expensive selection leak into the deployment path**.

**What the field did before.** In standard ReST and related methods, the quality signal used to filter training data is the same signal that would be used at deployment time — because it's typically correctness (which you either have or don't) or a learned reward model trained to predict human preferences. The deployment agent and the training data filter use the same mechanism. There's no asymmetry between how trajectories are generated and how they're evaluated for training.

**What the paper does differently.** The Search Agent uses two completely different selection mechanisms at different points in the loop (Section 3.5):

- **During trajectory generation (on-policy, "grow" phase):** The agent selects among 4 candidate outputs at each step using **minimum perplexity** — the model's own token-level loss. This requires zero additional computation beyond what's already needed for generation. It's a "free" selection signal.

- **During training data construction (off-policy, "improve" phase):** The same candidate outputs are re-evaluated by the **AI ranking model** — a separate instruction-tuned PaLM 2-L prompted zero-shot to compare actions and select the best one. This is an expensive LLM call (the ranking model is the same size as the teacher, and it's called once per step per trajectory). But because it's applied offline during dataset construction, not during live agent execution, the cost is amortized over the entire training run rather than paid per inference query.

The consequence is a separation of concerns: **the agent at deployment time remains lightweight** (using only perplexity, which is computationally trivial), but **the training data it learns from has been curated by a much more expensive critic**. The expensive critic never appears in the inference path.

**Why this is not obvious.** The natural impulse — and the approach taken by most prior work — would be to either (a) use the expensive critic during trajectory generation too (so the on-policy experience matches the training data distribution), or (b) train a distilled version of the critic that's cheap enough to use at both training and inference time. The paper rejects both options: (a) would make trajectory generation prohibitively expensive (4-16 additional PaLM 2-L calls per step, per question, times 2000 questions, times 4 repetitions), and (b) would require additional infrastructure (distilling a reward model) that the paper explicitly avoids because it wants zero human labels.

Instead, the paper embraces the asymmetry. The agent explores with a cheap, imperfect selection strategy (perplexity), and the training data is retrospectively curated with an expensive, higher-quality selection strategy (AI ranking). The fine-tuned model learns to produce outputs that look like what the ranking model would have selected — even though at deployment time, the agent still uses perplexity. The paper provides evidence that this works: the fine-tuned L model improves from 70.3% to 74.0% in one iteration (Table 1), demonstrating that learning from RM-curated data transfers to deployment behavior even though the deployment selection mechanism (perplexity) never changed.

**Why this matters beyond this paper.** This asymmetric design pattern — cheap exploration, expensive retrospective curation — is broadly applicable to any agent system where deployment latency or cost constraints prevent using the best available quality signal at inference time. It suggests that the training environment and the deployment environment don't need to use the same selection strategy; you can train with a "richer" supervisor than you deploy with. This is a form of **off-policy learning** that the paper implements implicitly through the grow-improve loop structure.

**Evidence anchoring.** The ablation in Table 3 supports the benefit of this asymmetry indirectly: going from 1st gen to 2nd gen data (which uses a better policy for generation — the fine-tuned L rather than the prompted L — but the same asymmetric selection pattern) yields a 9-point accuracy gain on XS (54.4% → 63.4%) while keeping the number of training examples roughly constant (~18K). The quality improvement comes from better generation (the 2nd gen policy produces better candidates for the ranking model to choose among) combined with consistent retrospective curation.

### Innovation 3: Self-Distillation as an Emergent Property of the Self-Improvement Loop — Compression Without a Separate Distillation Phase

The paper discovers — without setting out to study it as a primary contribution — that the synthetic data generated during self-improvement simultaneously serves as a highly effective distillation medium for much smaller models. This is not a separate technique; it's an **emergent property** of the iterative process-based training loop that the paper identifies and validates empirically.

**What the field did before.** Standard knowledge distillation for LLMs typically follows a two-phase protocol: (1) train or prompt a large teacher model to produce high-quality outputs, (2) use those outputs as targets to train a smaller student model. The teacher is fixed — it doesn't improve during the distillation process. The student learns from whatever quality the fixed teacher can produce. If the teacher makes systematic errors, the student learns those errors.

**What the paper shows.** In the ReST meets ReAct loop, the teacher **itself improves across iterations** (prompted L → 1st gen fine-tuned L → 2nd gen fine-tuned L), and the smaller models are fine-tuned on the data from each iteration. This creates a compound effect: the teacher gets better at the task, producing higher-quality trajectories, which become better training data for the student models, which then achieve higher accuracy. The distillation is not a separate step — it's folded into the same grow-improve loop. Table 1 makes this visible:

- PaLM 2-XS trained on iteration 1 data: 54.4%
- PaLM 2-XS trained on iteration 2 data: 65.9%
- PaLM 2-L (prompted teacher baseline): 70.3%

The XS model trained on iteration 2 data closes the gap to the prompted teacher to just 4.4 percentage points, despite being two orders of magnitude smaller. On the held-out BamTwoogle test set (Table 2), the 2nd gen XS achieves 63.0% versus the prompted L's 68.0% — a 5-point gap preserved under extreme compression.

**Why this is non-trivial.** Distillation typically incurs a compression tax — the student model performs worse than the teacher, and the gap widens as the size ratio increases. What's surprising here is not that distillation works, but that **the distillation quality improves as the teacher self-improves, without any changes to the distillation protocol itself**. The same fine-tuning procedure applied to iteration 1 vs. iteration 2 data yields dramatically different student performance (54.4% → 65.9% on XS), purely because the data quality improved. This suggests that in process-based agent domains, the bottleneck for small-model performance is not the student's capacity to learn the task, but the quality of the training demonstrations. Better demonstrations from a self-improving teacher directly translate to better student performance, without requiring the student to participate in the improvement loop.

**What makes this a genuine finding rather than obvious.** It would have been reasonable to expect that PaLM 2-XS simply lacks the capacity to execute the Search Agent task — after all, the paper explicitly states that "only the PaLM 2-L can perform it consistently well" as a pre-trained model (Section 3.1). The fact that fine-tuning on high-quality synthetic data from the self-improved teacher enables the XS model to approach the prompted L's performance indicates that the pre-trained XS's failure was not a capacity limitation but a **format and behavior limitation** — it couldn't follow the code-as-prompt format from few-shot exemplars, but it could learn the behavior pattern from sufficient fine-tuning data. This is an insight about the nature of the capability gap between model sizes in agent settings: the gap may be more about zero-shot instruction following than about underlying reasoning capacity.

**Evidence anchoring.** The full progression is in Table 1, but the critical comparison is XS 2nd gen (65.9%) versus prompted L (70.3%) on Bamboogle, and XS 2nd gen (63.0%) versus prompted L (68.0%) on BamTwoogle (Table 2). The paper also reports in Table 3 that data quality matters more than data quantity for small-model performance — going from 1st gen to 2nd gen (1x) with the same number of training examples (~18K) yields a 9-point gain on XS (54.4% → 63.4%), while quadrupling the data within 2nd gen (1x → 4x) yields only a 2.5-point gain (63.4% → 65.9%).

### Innovation 4: Self-Critique Works in Process-Based Agent Contexts — Reconciling Contradictory Findings from the Literature

The paper provides empirical evidence that resolves an apparent contradiction in the literature about whether LLMs can self-correct their own reasoning. This is not a theoretical resolution but an **empirical diagnostic finding**: self-critique helps in process-based multi-step agent setups even though it has been shown to hurt in outcome-based single-pass reasoning setups.

**What the field knew before.** Huang et al. (2023) published the influential finding that "large language models cannot self-correct reasoning yet" — prompting an LLM to check its own work and revise errors actually degraded performance on reasoning benchmarks compared to simply taking the first answer. This finding was widely cited and created a pessimistic narrative around self-critique as a viable inference-time strategy. If an LLM can't reliably identify its own errors, asking it to revise its outputs is more likely to introduce new errors than to fix existing ones.

**What the paper finds.** The Search Agent includes two explicit self-critique steps (relevance check and grounding check) as part of its state machine architecture (Figure 2, Steps 4-5). Using their auto-eval infrastructure, the paper measures the impact of these steps by comparing performance with and without them (evaluating the answer after Step 3 vs. after Step 5). The result, shown in Figure 4 and detailed in Table 4 (Appendix), is that self-critique provides a "small but measurable positive boost" of approximately 0.5–1.0 percentage points for most models. The paper explicitly contrasts this with prior work:

> "This contrasts the recent observations (Huang et al., 2023) that adding self-critique hurts the performance in an outcome-based CoT setup." (Section 6)

**Why the discrepancy matters — and what it tells us.** The paper doesn't fully explain *why* self-critique works here but not in Huang et al.'s setting, but the structural differences between the two setups suggest a hypothesis: in the Search Agent, self-critique is **scoped to specific, well-defined checks** (relevance and grounding) with clear criteria, and the model has access to explicit evidence (the original question, the retrieved snippets). In Huang et al.'s outcome-based CoT setup, the model is asked to check its own reasoning chain without external grounding — it has to detect logical errors in its own thinking using only its own internal knowledge. The Search Agent's checks are closer to **factual verification against retrieved text** than to **introspective logical error detection**, and the former may be an easier task that LLMs can perform more reliably.

Additionally, the paper notes (Section 6) that the positive effect of self-critique "depends on the model size (larger for larger models)" — the gap between pre- and post-self-critique performance is more pronounced for PaLM 2-L than for PaLM 2-XS (Table 4: L loses ~0.8 points without self-critique in the pre-trained setting and ~1.1 points in the 2nd gen setting, while XS loses only ~0.3 points in both settings). This suggests that the self-critique capability itself scales with model size, consistent with the broader finding that certain capabilities emerge only at larger scales.

**Why this is a conceptual contribution rather than just a performance detail.** The finding reframes the question from "can LLMs self-correct?" (a binary, model-centric framing) to "under what conditions, with what scaffolding, and on what types of checks does self-critique provide value?" (a conditional, system-design framing). The paper doesn't claim that LLMs have a general self-correction capability — it shows that within a specific process-based architecture with explicit verification criteria and external evidence, self-critique provides a small but reliable benefit. This suggests that the Huang et al. finding is not a fundamental limitation of LLMs but a limitation of a particular self-critique setup (unstructured, evidence-free, introspective). The implication for agent design is that self-critique should be structured around verifiable claims against external evidence, not open-ended "check your reasoning" prompts.

Additionally, the paper notes (Section 6) that the self-critique benefit "does not seem to be affected by the self-improvement process" — the gap between pre- and post-self-critique performance remains roughly constant across iterations (prompted L, 1st gen L, 2nd gen L all show similar ~0.6-1.1 point self-critique gains in Table 4). This is an interesting null result: self-improvement makes the agent better at the core task (search, summarization, answering) but does not amplify the self-critique capability beyond its initial level. The self-critique skill may be learned primarily during pre-training and is less amenable to the kind of process-based fine-tuning that improves the other steps.

**Evidence anchoring.** Figure 4 visually shows the small but consistent gap between the "with self-critique" and "without self-critique" bars across model sizes and training iterations. Table 4 provides the exact numbers — for 2nd gen L, accuracy is 76.1% with self-critique and 75.0% without, a +1.1 point gain. For 2nd gen XS, it's 65.9% vs. 65.6%, a +0.3 point gain. The gains are small but directionally consistent and, as the paper notes, measurable thanks to the reduced variance from running 10 repetitions per evaluation (enabled by auto-eval).

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The primary evaluation vehicle is Bamboogle (Press et al., 2023), a semi-adversarial dataset of 125 two-hop questions manually verified to be unanswerable by direct Google search but answerable via composing information from Wikipedia. The paper also introduces BamTwoogle, a handcrafted held-out test set of 100 questions constructed by the authors to serve as a more challenging complement, requiring 2–4 steps to answer and explicitly verified to not appear on the first page of Google search results. Neither dataset is used for training or prompt tuning — Bamboogle serves as a de-facto validation set for hyperparameter selection (temperature, checkpoint step, whether to proceed with another iteration), while BamTwoogle is reserved exclusively for final performance measurement (Section 4.3).

- **Base model(s).** All experiments use the PaLM 2 model family (Anil et al., 2023) in three sizes: PaLM 2-XS, PaLM 2-S, and PaLM 2-L. The pre-trained PaLM 2-L is the only model capable of reliably executing the Search Agent from few-shot prompts in the code-as-prompt format (Section 3.1) — this motivates its role as the teacher model that generates all synthetic training data. PaLM 2-S and PaLM 2-XS serve as distillation targets, fine-tuned on data generated entirely by the large model.

- **Metrics.** The primary metric is **accuracy on Bamboogle** and **BamTwoogle**, measured via either human evaluation or LLM-based auto-eval. For auto-eval, an instruction-tuned PaLM 2-L (separate from the base model used for agent execution) is prompted with the original question, the agent's long-form answer, and the reference answer, and must judge whether the answer implies the reference answer (Listing 7). The paper establishes alignment between auto-eval and human judgment by comparing both on a diverse set of agents, reporting a Pearson correlation of 0.98 (p = 6.6 × 10⁻⁸) and Spearman correlation of 0.83 (p = 0.0015) (Section 4.2). To account for stochastic trajectories (temperature T = 0.5 during sampling), the paper reports **mean accuracy with standard deviation over 10 runs** for all auto-eval results — each run produces one trajectory per Bamboogle question, and the mean across 10 such runs is the reported accuracy.

- **Baselines.** The paper uses three baselines (Table 1): (1) **Pre-trained (prompted) PaLM 2-L** — the model executing the Search Agent using only the manually constructed few-shot prompts, with no fine-tuning on any trajectories, achieving 70.3% on Bamboogle auto-eval; (2) **Pilot, human-filtered** — models fine-tuned on 500 trajectories manually reviewed to remove ~30% of "bad" examples (unhelpful queries, empty thoughts, missing summaries), yielding 3,015 training examples; (3) **Pilot, unfiltered** — the same 500 trajectories without human filtering, yielding 4,518 training examples (Table 3). The prompted PaLM 2-L serves as the "teacher" baseline, while the pilot data baselines establish a floor for what fine-tuning alone achieves without iterative self-improvement.

- **Generation budget / compute accounting.** The paper does not use a FLOPs-based compute budget in the style of test-time scaling papers. Instead, the relevant resource accounting tracks **number of trajectories generated** for training data (500 for pilot, 2,000 for iteration 1, 8,000 for iteration 2) and **number of samples per reasoning step** during trajectory generation (4 for L and S models, 16 for XS). The cost of the ranking model — a separate PaLM 2-L call per step per trajectory during off-policy re-ranking — is not explicitly quantified but is acknowledged as off-policy (Section 3.5), meaning it is paid once during training data construction, not at inference time. For evaluation, each reported auto-eval number represents 10 runs × 125 questions = 1,250 complete agent trajectories, each with 5+ LLM calls plus search API calls.

- **Cross-validation / statistical protocol.** The paper does not use k-fold cross-validation on the evaluation datasets — instead, it maintains a strict separation between training data (2,000 questions from HotpotQA, Eli5, Eli5-askH, and Eli5-askS), validation data (Bamboogle, used for hyperparameter selection and iteration decisions), and test data (BamTwoogle, used only for final evaluation). The paper explicitly states: "we never use Bamboogle as a training set, as we neither tune our prompts on Bamboogle nor use questions from it to generate fine-tuning trajectories" (Section 4.2). This three-way split — seed questions for trajectory generation, Bamboogle for development, BamTwoogle for testing — serves the same function as cross-validation in preventing overfitting while being tailored to the agent-evaluation setting where generating trajectories from evaluation questions would contaminate the test set.

### Main Quantitative Results

#### Self-Improvement Scaling: Accuracy Gains Across Iterations

The core quantitative result is the progression of Bamboogle auto-eval accuracy across training iterations for all three model sizes, presented in Table 1 and Figure 1. The headline numbers are:

**Prompted teacher baseline (PaLM 2-L):** 70.3% ± 3.5% (Table 1, "Pre-trained" row, L column). This is the starting point — a pre-trained (not fine-tuned) model executing the Search Agent purely through few-shot code-as-prompt exemplars.

**Iteration 1 ("1st gen"):** After one grow-improve cycle using 2,000 trajectories generated by the prompted L model, fine-tuned on 17,970 step-level training examples (Table 3, "1st gen" column):
- Fine-tuned L: 74.0% ± 3.3% (+3.7 points over prompted L)
- Fine-tuned S: 61.9% ± 1.9%
- Fine-tuned XS: 54.4% ± 3.6%

The L model improves meaningfully from its own data — this is self-improvement in the strict sense: the same-sized model generating data that improves itself. The S and XS numbers represent distillation from the prompted L teacher (not the fine-tuned L), since iteration 1 trajectories were generated by the prompted model.

**Iteration 2 ("2nd gen"):** After a second grow-improve cycle, now using 8,000 trajectories (4 repetitions of each of the 2,000 seed questions) generated by the **fine-tuned L from iteration 1**, fine-tuned on 72,424 step-level training examples (Table 3, "2nd gen (4x)" column):
- Fine-tuned L: 76.1% ± 1.3% (+2.1 points over iteration 1 L, +5.8 points over prompted L)
- Fine-tuned S: 69.7% ± 1.3% (+7.8 points over iteration 1 S)
- Fine-tuned XS: 65.9% ± 2.6% (+11.5 points over iteration 1 XS)

Three quantitative patterns stand out:

**Pattern 1: Diminishing returns on the teacher.** The prompted → iteration 1 gain on L is +3.7 points; iteration 1 → iteration 2 gain is +2.1 points. The marginal benefit of additional self-improvement iterations is shrinking, consistent with the agent approaching a performance ceiling determined by the task, model capacity, and verifier quality.

**Pattern 2: Acceleration on smaller models.** The iteration 1 → iteration 2 jump is much larger for S (+7.8 points) and XS (+11.5 points) than for L (+2.1 points). This is because the iteration 2 data comes from a **better teacher** (the fine-tuned L rather than the prompted L) — the smaller models benefit disproportionately from higher-quality demonstrations, since they couldn't have generated such trajectories themselves. This is the distilled version of the self-improvement gain.

**Pattern 3: Variance reduction with better data.** The standard deviation decreases across iterations for all model sizes: L goes from ±3.5 (prompted) to ±3.3 (1st gen) to ±1.3 (2nd gen); XS goes from ±3.6 (1st gen) to ±2.6 (2nd gen). Higher-quality training data produces more consistent agent behavior across stochastic runs.

#### Human Evaluation on Held-Out Test Set

Table 2 provides the crucial out-of-sample validation using human evaluation on BamTwoogle (100 questions, never used during development):

| Model | Bamboogle (human eval) | BamTwoogle (human eval) |
|---|---|---|
| Pre-trained L | 68.8% | 68.0% |
| 2nd gen XS | 67.2% | 63.0% |
| 2nd gen S | 68.0% | 63.0% |
| 2nd gen L | 74.4% | 74.0% |

The 2nd gen L outperforms the prompted L on both datasets (74.4% vs. 68.8% on Bamboogle; 74.0% vs. 68.0% on BamTwoogle), confirming that the self-improvement gains measured by auto-eval on Bamboogle transfer to a held-out dataset evaluated by humans. The 2nd gen XS (63.0%) and 2nd gen S (63.0%) both approach the prompted L's 68.0% on BamTwoogle, with a gap of only 5.0 points — substantial compression from two orders of magnitude fewer parameters. Note that the S and XS models tie at 63.0% on BamTwoogle despite S being larger and performing notably better on Bamboogle (68.0% vs. 67.2%) — the paper does not comment on this reversal, but it highlights the importance of the held-out test set in revealing that the Bamboogle gains for S vs. XS may partially reflect overfitting to the development set.

#### Data Quality vs. Data Quantity: The Table 3 Ablation

Table 3 provides a controlled comparison that isolates the impact of training data quality (which generation produced it) from training data quantity (how many examples), using the PaLM 2-XS model as the testbed:

| Training Data | Total Trajectories | Training Examples | Bamboogle Accuracy |
|---|---|---|---|
| Pilot, human filtered | 500 | 3,015 | 44.7% ± 3.1 |
| Pilot, unfiltered | 500 | 4,518 | 47.2% ± 3.1 |
| 1st gen | 2,000 | 17,970 | 54.4% ± 3.6 |
| 2nd gen (1x) | 2,000 × 1 | 18,007 | 63.4% ± 1.7 |
| 2nd gen (2x) | 2,000 × 2 | 36,238 | 65.6% ± 1.8 |
| 2nd gen (4x) | 2,000 × 4 | 72,424 | 65.9% ± 2.6 |

**Finding 1: Quality dominates quantity.** Going from 1st gen to 2nd gen (1x) — keeping the number of training examples nearly constant (~18K) but using data generated by the fine-tuned L instead of the prompted L — yields a **+9.0 point gain** (54.4% → 63.4%). This is the cleanest demonstration that the teacher model's capability improvement (from self-improvement iteration 1) translates directly into better training data for the student, independent of data volume.

**Finding 2: Quantity has diminishing returns once quality is high.** Within the 2nd gen data, increasing from 1x (18,007 examples) to 2x (36,238 examples) to 4x (72,424 examples) yields gains of +2.2 points (63.4% → 65.6%) and then +0.3 points (65.6% → 65.9%). The marginal benefit of additional trajectories from the same teacher is small — the first trajectory per question captures most of the value, and additional repetitions add little. This is consistent with a saturation effect: once the model has seen one high-quality trajectory per question, seeing another trajectory for the same question from the same policy provides minimal new information.

**Finding 3: Human filtering hurts.** Surprisingly, fine-tuning on human-filtered pilot data (44.7%) performs worse than fine-tuning on unfiltered pilot data (47.2%) — a **−2.5 point penalty** from human curation. The paper hypothesizes two mechanisms (Section 5.3): (1) the reduced size of the filtered mixture (3,015 vs. 4,518 examples) makes it harder for the model to learn the proper prompt format, and (2) filtering removes only the immediate "bad" example, not the whole trajectory — the "bad" step often still appears in the `PAST_ACTIONS` field of other examples, so the model is still exposed to it. This is a significant negative result: it suggests that **naïve human filtering of process data can be counterproductive** because trajectory-level quality is entangled across steps, and removing individual steps breaks the coherence that the model needs for learning.

#### Self-Critique Analysis: Small but Consistent Positive Effect

Figure 4 and Table 4 (Appendix) report the impact of the two self-critique steps (relevance check and grounding check) on final answer accuracy, measured by comparing auto-eval scores on the "Answer Generation" step output versus the "Final Answer" (after both self-checks):

**Pre-trained L:** Loses −0.8 points without self-critique (69.5% vs. 70.3%). The prompted model benefits slightly from asking itself to verify relevance and grounding before delivering the final answer.

**Across self-improvement iterations for L:** The self-critique benefit remains in the range of −0.6 to −1.1 points: pilot L loses −0.6 (70.9% → 71.5%), 1st gen L loses −0.9 (73.1% → 74.0%), 2nd gen L loses −1.1 (75.0% → 76.1%). The gain is small and doesn't grow with self-improvement — the paper notes that the self-critique capability "does not seem to be affected by the self-improvement process" (Section 6).

**Effect varies with model size:** For 2nd gen models, the self-critique benefit is +1.1 points for L, +0.5 points for S (69.2% → 69.7%), and +0.3 points for XS (65.6% → 65.9%). Larger models benefit more from self-critique, consistent with the broader finding that certain meta-cognitive capabilities scale with model size.

**Interpretation:** The self-critique steps provide a reliable but small improvement — approximately 0.5–1.0% absolute accuracy — that is consistent across model sizes and training iterations but does not compound with self-improvement. This contrasts with Huang et al. (2023)'s finding that self-correction hurts performance in outcome-based CoT setups, and the paper attributes the difference to the structured, evidence-based nature of the Search Agent's self-checks (verifying claims against retrieved snippets) versus open-ended introspective correction.

### Ablation Studies and Robustness Checks

**Human filtering of process data:** Human curation of pilot trajectories — removing ~30% of examples judged "bad" (unhelpful queries, empty thoughts, missing information) — **reduces** XS performance by 2.5 points relative to unfiltered data (44.7% vs. 47.2%, Table 3). This negative result is attributed to reduced dataset size impairing format learning and the fact that removed "bad" steps still appear in the `PAST_ACTIONS` field of other examples, exposing the model to them anyway (Section 5.3).

**Number of trajectories per question:** Within the 2nd gen data, increasing from 1 to 2 trajectories per seed question yields a +2.2 point gain on XS (63.4% → 65.6%, Table 3), but further increasing to 4 trajectories per question yields only +0.3 additional points (65.6% → 65.9%). The paper concludes that "it helps to use two trajectories per question instead of 1... but more than that doesn't improve performance significantly" (Section 5.3). The 2x configuration (36,238 training examples) captures most of the available benefit at roughly half the data generation cost of the 4x configuration (72,424 examples).

**Presence of self-critique steps:** Removing the relevance and grounding self-checks (evaluating on the Answer Generation step rather than the Final Answer) reduces accuracy by 0.3–1.1 points depending on model size and training iteration (Table 4, Figure 4). The effect is always positive but small — self-critique helps, but it is not a major driver of the overall self-improvement gains, which are dominated by better search and summarization behavior from the fine-tuned models.

**Question diversity in pilot data:** The pilot data uses only 500 questions from HotpotQA and Eli5 (excluding Eli5-askH and Eli5-askS), compared to the 2,000 questions from all four sources in the main experiments. The 1st gen data (2,000 questions, all four sources) achieves 54.4% on XS vs. 47.2% for pilot unfiltered (Table 3) — a +7.2 point gain. However, this comparison confounds question diversity (500 vs. 2,000 questions), trajectory quality (pilot uses prompted L; 1st gen uses prompted L but benefits from RM re-ranking, though the paper states 1st gen uses "default best actions" without explicit confirmation of RM re-ranking), and dataset scale (4,518 vs. 17,970 examples), so the individual contribution of each factor cannot be isolated.

**RM re-ranking impact (implicit ablation):** The paper does not report a direct ablation comparing fine-tuning with perplexity-selected actions versus RM-ranked actions. This is a notable gap — while the RM ranking mechanism is central to the paper's claim of replacing human labels with AI feedback, there is no experiment that isolates its contribution. The improvement from iteration 1 to iteration 2 data could be due to the better generation policy (fine-tuned L vs. prompted L), the RM re-ranking applied during mixture construction, or both — and the paper does not disentangle these.

**Trajectory repetition across iterations (implicit design choice):** The same 2,000 seed questions are used for both iteration 1 and iteration 2 trajectory generation, with iteration 2 using 4 repetitions per question. The paper does not test whether introducing new seed questions in iteration 2 would yield additional gains beyond repetition of the same questions, which would help distinguish between "the policy is improving at these specific questions" and "the policy is genuinely improving at the task."

### Critical Assessment

#### Claim: Self-improvement improves agent performance without human-labeled training data

**Verdict: Supported, with important scope qualifications.**

The progression from prompted L (70.3%) → iteration 1 fine-tuned L (74.0%) → iteration 2 fine-tuned L (76.1%) on Bamboogle (Table 1) demonstrates that iterative training on self-generated trajectories with AI-feedback re-ranking improves performance without any human-labeled correctness judgments on the training data. The only human involvement is the initial prompt construction (few-shot exemplars for each of the five reasoning steps) and the BamTwoogle test set evaluation (100 questions, human-judged, Table 2).

However, this claim comes with two important scope limitations. **First**, the evaluation is confined to Bamboogle and BamTwoogle — two small datasets (125 and 100 questions) of compositional web-search questions. Whether the improvement generalizes to other types of agent tasks, other tools, or other question distributions is not tested. The paper acknowledges this limitation explicitly: "Futures work could explore if the same self-improvement algorithm applies to multiple tool settings" (Section 6).

**Second**, the paper demonstrates self-improvement for only two iterations, with diminishing returns (iteration 1: +3.7; iteration 2: +2.1). Whether a third iteration would yield further gains, or whether the curve asymptotes, is an open question the paper leaves unanswered (Section 6). This matters for the practical significance of the method: if the gains saturate after two iterations, the long-term value of the approach is limited to a one-time bootstrapping procedure rather than a continuous improvement engine.

#### Claim: Self-distillation achieves comparable performance to the prompted teacher with two orders of magnitude fewer parameters

**Verdict: Supported for the specific setting, but "comparable" requires careful interpretation.**

The 2nd gen PaLM 2-XS achieves 65.9% on Bamboogle auto-eval versus the prompted PaLM 2-L's 70.3% (Table 1) — a gap of 4.4 percentage points, or 6.3% relative degradation. On BamTwoogle human eval, the gap is 63.0% vs. 68.0% (Table 2) — 5.0 points. Whether this qualifies as "comparable performance" depends on the use case. The XS model captures roughly 93–94% of the prompted L's accuracy while being approximately two orders of magnitude smaller (the paper doesn't specify exact parameter counts, but PaLM 2-XS and PaLM 2-L differ substantially based on the model family's naming convention).

An important caveat: the comparison is between **fine-tuned XS** (trained on 72,424 high-quality examples generated by the self-improved teacher) and **prompted L** (no fine-tuning, relying purely on few-shot exemplars). This is not a controlled comparison of model capacity — it's a comparison between two different deployment strategies (fine-tune a small model vs. prompt a large model). A more informative baseline would be **prompted PaLM 2-XS**, but the paper states that pre-trained PaLM 2-XS cannot reliably execute the Search Agent at all due to the code-as-prompt format ("only the PaLM 2-L can perform it consistently well," Section 3.1). This means the distillation result, while impressive, is partially a demonstration that the code-as-prompt format imposes a capability threshold that fine-tuning can bridge — not necessarily that the XS model has learned the full reasoning capability of the L model.

The paper also does not compare against a **fine-tuned PaLM 2-L using the same 2nd gen data but without the iterative process** — that is, what if you just generated 8,000 trajectories from the prompted L (skipping the iteration 1 fine-tuning step) and fine-tuned the L model on those? This would isolate the contribution of iterative improvement (better teacher via iteration 1) from the contribution of simply having more data from a fixed teacher. Without this baseline, the specific value of the iterative loop versus a one-shot data generation approach is unquantified.

#### Claim: AI feedback (zero-shot LLM ranking) can replace human-labeled reward models for process-based training

**Verdict: Incompletely supported — the ablation is missing.**

The paper's central methodological claim is that a zero-shot prompted LLM can serve as the quality filter in a self-training loop, replacing both correctness-based filtering (STAR/ReST$^{EM}$) and human-preference-trained reward models (ReST/RAFT). However, there is **no direct experiment comparing RM-ranked training data against an alternative selection strategy** — such as random selection, perplexity-based selection, or human-ranked selection. The ranking model's contribution is confounded with the improved generation policy in iteration 2 data, making it impossible to determine whether the ranking model is actually providing better selections than simple perplexity.

The paper states that "we mainly do the LLM-based selection off-policy, i.e., by updating the current action used for fine-tuning" (Section 3.5) and that on-policy rollouts use perplexity. But it does not report: (1) what fraction of steps get a different action selected by the RM versus perplexity; (2) whether fine-tuning on the perplexity-selected actions (without RM re-ranking) would achieve similar performance; or (3) how often the RM's top-ranked action disagrees with human judgment. Without these analyses, the reader cannot assess whether the AI feedback mechanism is genuinely providing a useful quality signal or is simply a correlate of model confidence that adds little beyond perplexity.

This is the most significant gap in the experimental validation. If the RM ranking doesn't actually change which actions are selected for training (because the lowest-perplexity output is usually also the RM's top choice), then the paper's central claim about replacing human labels with AI feedback is tautological — the improvement would come entirely from the iterative generation of better trajectories by a better policy, not from the RM's discrimination ability.

#### What the experiments do and do not demonstrate

**What they demonstrate clearly:** That fine-tuning on process-based trajectories from a better policy (iteration 2 data from fine-tuned L vs. iteration 1 data from prompted L) substantially improves small-model performance — the +9.0 point gain on XS with constant dataset size (Table 3) is clean, well-controlled evidence. That iterative self-training with the same model size can improve performance — the prompted L (70.3%) → iteration 1 L (74.0%) → iteration 2 L (76.1%) progression (Table 1) demonstrates this, though the absolute gains shrink each iteration. That self-critique provides a small positive benefit in this architecture — Figure 4 and Table 4 show this consistently across all model sizes and iterations. That distillation can preserve most of the teacher's performance — the XS model reaches within 4–5 points of the prompted L (Tables 1 and 2).

**What they do not demonstrate:** That the AI ranking model specifically (as opposed to any quality signal correlated with model confidence) is necessary for the gains — no ablation compares RM ranking against alternative selection methods. That self-improvement would continue beyond two iterations — the saturation point is unknown. That the method generalizes beyond the Search Agent / Bamboogle / BamTwoogle setting — no other tasks, tools, or datasets are evaluated. That the difficulty estimation cost (generating 4 candidate outputs per step and re-ranking them with a PaLM 2-L model per training example) is practical at scale — the paper doesn't quantify the total FLOPs cost of the self-improvement pipeline relative to simply prompting a larger model or collecting human labels.

#### Missing experiments that would have strengthened the paper

- **RM ranking ablation:** Compare PaLM 2-XS fine-tuned on randomly selected actions versus perplexity-selected actions versus RM-ranked actions, all from the same trajectory pool, at the same dataset size.
- **One-shot vs. iterative comparison:** Fine-tune PaLM 2-L on 10,000 trajectories (2,000 questions × 5 repetitions) generated by the prompted L, and compare against iteration 2 L (which used iteration 1 L as the generator). This would isolate the value of the iterative teacher improvement from the value of simply generating more data from the fixed prompted teacher.
- **Diverse question pool experiment:** Use different seed questions in iteration 2 versus iteration 1, to determine whether the policy improvement is genuine or reflects overfitting to the fixed question distribution.
- **Scaling the number of iterations to saturation:** Run iterations until performance plateaus, to characterize the self-improvement scaling curve and determine the practical ceiling.
- **Human evaluation of the RM's selections:** Have humans rate how often the RM's top-ranked action is genuinely better than the perplexity-selected action, to validate that the AI feedback signal is meaningful rather than just a proxy for model confidence.

## 6. Limitations and Trade-offs

### 6.1 The AI Ranking Model's Contribution Is Unvalidated — No Ablation Exists to Isolate Its Effect from Perplexity-Based Selection

**The assumption or constraint.** The paper's central methodological claim is that a zero-shot prompted LLM can replace human-labeled reward models and correctness-based filtering for process-level data curation. The AI ranking model is positioned as the mechanism that makes self-improvement possible without human supervision — it "ranks sampled responses to select high-scoring subsets for model fine-tuning" (Section 3.5), and the paper explicitly states it is applied "off-policy, i.e., by updating the current action used for fine-tuning" while "the on-policy trajectory rollouts use perplexity" (Section 3.5). The entire "improve" phase of the ReST loop depends on this re-ranking step to curate higher-quality training examples than what perplexity alone would select.

**The consequence.** The reader cannot determine whether the AI ranking model provides any value beyond what simple perplexity-based selection would achieve. Three alternative hypotheses are equally consistent with the reported results:

- **Hypothesis A (the intended mechanism):** The RM selects genuinely better actions than perplexity, and this curation is a necessary component of the performance gains.
- **Hypothesis B (perplexity sufficiency):** The RM's top-ranked action is usually the same as the lowest-perplexity action — in which case the RM contributes nothing, and the gains come entirely from the iterative improvement of the generation policy (better trajectories from the fine-tuned L teacher).
- **Hypothesis C (any signal helps):** Any selection signal correlated with model confidence (perplexity, RM ranking, or even random selection from the top-2 candidates) would produce similar results, and the specific choice of a zero-shot LLM ranker is incidental.

Without an ablation comparing training on RM-ranked actions versus perplexity-selected actions versus randomly selected actions from the same candidate pool, the paper's core methodological contribution — that AI feedback can replace human labels for process-based training — remains an **untested assertion** rather than an empirically validated finding.

**What evidence exists in the paper.** No experiment in the paper compares different action selection strategies for fine-tuning data construction. Table 3 shows that 2nd gen data outperforms 1st gen data, but this comparison confounds two changes: (a) the generation policy improved (fine-tuned L vs. prompted L), producing better candidates for the RM to choose from; and (b) the RM re-ranking was applied to both datasets during mixture construction. Neither Table 1 nor Table 3 isolates the contribution of (b) from (a). The paper never reports what fraction of steps the RM selects a different action than perplexity would have chosen, nor whether fine-tuning on the perplexity-selected actions alone would achieve similar accuracy numbers.

The paper's ablation on data quantity (Table 3, 2nd gen 1x vs. 2x vs. 4x) shows that more trajectories help but with diminishing returns, but this tells us nothing about whether the RM ranking specifically is responsible for the quality of those training examples. Section 3.5 describes the ranking model's prompt (Listing 8) and states it is "closer to RAFT" but does not validate that the rankings it produces are better than the default perplexity selections.

**Mitigation status.** Not addressed. The paper does not acknowledge this as a missing experiment, does not suggest running such an ablation, and does not qualify the claims about AI feedback with appropriate caveats. Section 6 lists future directions around multiple tool settings and saturation points but does not mention validating the RM ranking mechanism itself. This is the single largest gap between what the paper claims ("purely from stepwise AI feedback without using human-labeled training data") and what it has demonstrated — the "AI feedback" component is unvalidated as a causal contributor to the results.

### 6.2 The Method's Practical Cost Structure Is Not Quantified — Making Deployment Feasibility Unknown

**The assumption or constraint.** The paper makes an implicit assumption that the computational cost of the self-improvement pipeline — trajectory generation, RM re-ranking, and iterative fine-tuning — is acceptable relative to the performance gains it provides. The paper uses the term "grow" and "improve" phases (Section 3.6) modeled on ReST, but provides no FLOPs accounting, no wall-clock time measurements, and no comparison of total compute expenditure against simpler alternatives (e.g., generating more trajectories from the prompted teacher in a single pass, or using a larger prompted model with no fine-tuning at all). The paper's only resource metric is "number of trajectories generated" and "number of training examples" (Table 3), which captures data volume but not computational cost.

**The consequence.** A practitioner reading this paper cannot answer fundamental deployment questions: Is it cheaper to run two iterations of self-improvement on PaLM 2-L and then distill to XS, or to simply deploy the prompted PaLM 2-L directly? What is the total inference cost of generating 8,000 trajectories (iteration 2) with 4 samples per step and then re-ranking every action with a separate PaLM 2-L call? How does this compare against collecting a modest amount of human-labeled data to train a reward model once and reuse it? The headline result — XS achieves ~94% of L's accuracy — is missing its denominator: at what total compute cost was this achieved?

The hidden costs are substantial but unquantified:

- **Trajectory generation overhead.** Each of the 8,000 trajectories (iteration 2, 4x) requires 5+ LLM calls (decision, summarization, answer, relevance check, grounding check), with 4 samples per call for L and S models. This means roughly 40+ PaLM 2-L generations per question (8,000 trajectories × ~5 steps × 4 samples = ~160,000 total LLM calls, not counting the RM).
- **RM re-ranking overhead.** During off-policy mixture construction, each of the 72,424 training examples (2nd gen 4x, Table 3) potentially requires a separate PaLM 2-L call to rank 4 candidate actions. This could add another ~70,000+ PaLM 2-L inferences.
- **Iterative training.** Three model sizes (XS, S, L) are fine-tuned to 9K, 5K, and 3.5K steps respectively (Section 4.2), at each of two iterations, using full fine-tuning (Section 3.4).
- **Difficulty estimation for hyperparameters.** The paper uses Bamboogle auto-eval "to answer various questions that one would typically use a validation set for" (Section 4.2), including temperature selection and checkpoint selection. Each such decision requires running 10 repetitions × 125 questions = 1,250 complete agent trajectories for evaluation, plus a separate PaLM 2-L call per question for the auto-eval judgment itself.

None of these costs appear in any table or analysis.

**What evidence exists in the paper.** The paper provides fragmentary cost indicators: 4 samples per step for L and S, 16 for XS (Section 3.2); the ranking model is an instruction-tuned PaLM 2-L (Section 3.5); fine-tuning checkpoints are at 9K, 5K, and 3.5K steps (Section 4.2). But there is no integrated cost analysis, no comparison of total compute against baselines, and no discussion of whether the approach is economically practical. The paper notes that the RM is applied off-policy "so that the inference path remains lightweight" (Section 3.5, implicitly), but this only addresses deployment cost — it does nothing to quantify the training cost that makes that lightweight deployment possible.

**Mitigation status.** Not addressed. The paper does not list cost analysis as a limitation or future work. Section 6 mentions "computational and time constraints" as limitations but refers to them as constraints on the authors' experimental scope, not as a structural limitation of the method that would affect practitioners. The lack of cost transparency is a significant barrier to adoption — a practitioner evaluating whether to implement this pipeline has no basis for estimating the required compute budget.

---

### 6.3 Generalization Is Demonstrated Only on a Single Task Type with a Single Model Family and a Single Tool — No Evidence of Transfer to Other Agent Settings

**The assumption or constraint.** All experiments in the paper use the same agent architecture (Search Agent with web search as the only tool), the same model family (PaLM 2, in three sizes), the same prompt paradigm (Python code-as-prompt), and two small evaluation datasets (Bamboogle, 125 questions; BamTwoogle, 100 questions) that share the same underlying structure — compositional questions requiring web search to retrieve and compose facts from multiple sources. The paper acknowledges this limitation directly in Section 6:

> "this work... has numerous limitations due to computational and time constraints: manually constructed prompts, small evals, a limited set of models, and only a single tool, to name just a few."

**The consequence.** A practitioner cannot infer from the reported results whether the self-improvement methodology would transfer to their setting if it differs in any of the following dimensions:

- **Different tool families.** The Search Agent uses only web search. Would the method work for agents that use calculators, code interpreters, database queries, or APIs with structured inputs and outputs? The RM ranking prompt (Listing 8) is generic ("we want the agent to produce relevant and grounded answers with minimal steps"), but whether this ranking criterion would effectively discriminate good actions for, say, a code-writing agent or a SQL-querying agent is unknown.
- **Different model families.** The code-as-prompt paradigm restricts the initial teacher to PaLM 2-L — "only the PaLM 2-L can perform it consistently well" (Section 3.1) among the pre-trained models tested. Would the self-improvement loop work starting from a different large model (GPT-4, Claude, Llama) that may have different strengths, weaknesses, and output distributions? Would the RM (also PaLM 2-L) be as effective at ranking actions from a different model family?
- **Different task types beyond compositional QA.** The evaluation datasets (Bamboogle, BamTwoogle) consist of fact-seeking questions with verifiable answers amenable to auto-eval against reference strings. Would the method work for open-ended analysis tasks, creative generation, multi-turn dialogue, or tasks where "correctness" cannot be reduced to whether the answer implies a reference string? The auto-eval protocol itself relies on reference answers existing (Listing 7), which constrains the task space to questions with known answers.
- **Different prompt formats.** The code-as-prompt approach is an unusual design choice. Would the method work with natural language prompts, function-calling APIs, or structured JSON formats? The authors chose this format for parsing reliability (Section 3.1), but this choice creates a distribution-specific requirement that may not generalize.

The two evaluation datasets are also small (125 + 100 = 225 total questions) and were both constructed by the same research group with similar design principles (two-hop requires search to compose; manually verified unanswerable by single Google query). It is possible that the self-improvement gains are specific to this narrow question distribution and would not replicate on, for example, questions requiring 3+ hops, temporal reasoning, or numerical computation.

**What evidence exists in the paper.** The paper provides exactly the evidence necessary to support its claims, but no more: results on two closely related datasets (Bamboogle, BamTwoogle) with one model family (PaLM 2) on one agent architecture (Search Agent with web search). There is no cross-task evaluation, no cross-model evaluation (e.g., using a different model as the base policy for trajectory generation), and no tool-diversity experiment. The human eval on BamTwoogle (Table 2) serves as a held-out test, but the test distribution is deliberately similar to the development distribution (Bamboogle) — both are compositional, web-search-requiring, fact-seeking questions.

Table 2 does reveal an interesting pattern that amplifies generalization concerns: the XS and S models both score 63.0% on BamTwoogle human eval despite S scoring higher on Bamboogle (68.0% vs. 67.2%). This reversal suggests that the Bamboogle-optimized hyperparameters (Section 4.2: checkpoint selection, temperature) may not transfer optimally to even a closely related dataset, let alone a fundamentally different task.

**Mitigation status.** Partial — acknowledgment only. The paper explicitly lists these scope limitations in Section 6 and suggests future work on "multiple tool settings" and "if the ability to handle unseen tools could be improved." But these are presented as aspirational future directions, not as caveats that qualify the current claims. The paper's title and abstract frame the contribution as a general method for "Multi-Step Reasoning LLM Agent" self-improvement, but the evidence covers only one specific multi-step reasoning agent on one specific task family. A more accurate framing would be "Self-Improvement for a Web-Search QA Agent on Compositional Fact-Seeking Questions" — but this more limited scope is not reflected in the paper's positioning.

### 6.4 The Code-as-Prompt Paradigm Creates a Hard Capability Floor That Excludes Smaller Models from the Improvement Loop — Distillation Becomes Mandatory Rather Than Optional

**The assumption or constraint.** The paper's Search Agent uses Python code-formatted prompts (Listings 1-6) with dataclasses, type annotations, and structured code-continuation expectations. The authors justify this choice with three observations about code's structure, natural language integration, and LLM code literacy (Section 3.1). However, they then state the critical constraint:

> "only the PaLM 2-L... can perform it consistently well. Hence, this is the model that we use to produce reasoning trajectories from few-shot prompts." (Section 3.1)

**The consequence.** This design choice creates a **hard asymmetry** between models that can generate training data and models that can only consume it. Pre-trained PaLM 2-S and PaLM 2-XS cannot execute the Search Agent from few-shot prompts in this format — they cannot participate in the "grow" phase of self-improvement, cannot generate their own trajectories, and cannot contribute to the iterative exploration of the action space. They are permanently locked into the role of distillation targets, learning purely from trajectories generated by the large model.

This has three consequences that affect the paper's claims:

- **Distillation is not an "emergent property" — it's a forced consequence of the prompt format.** The paper frames self-distillation as a beneficial feature of the approach ("the synthetic data produced as part of this iterative process could be used for distilling the agent into one or two orders of magnitude smaller models," Section 1). But the smaller models *cannot generate data themselves* because of the prompt format, not because of an inherent reasoning capacity gap. If a natural-language prompt format or a simpler structured format had been used, the smaller models might have been capable of generating trajectories (of lower quality than L, but still useful), and they could have participated in the self-improvement loop directly — potentially yielding even larger gains through on-policy fine-tuning.

- **The performance ceiling for small models is capped by the teacher's quality.** Since XS and S learn only from L-generated data, their maximum achievable performance cannot exceed what the best available L policy can demonstrate in its trajectories. If the prompted L has systematic blind spots (certain question types it consistently answers poorly, certain search strategies it never discovers), those blind spots are inherited by the distilled models. The small models cannot explore the action space themselves and potentially discover strategies the large model missed.

- **The "two orders of magnitude" compression claim conflates format with reasoning capability.** The paper states the fine-tuned XS achieves comparable performance to the prompted L "with two orders of magnitude fewer parameters" (Abstract, Section 8). But we don't know whether an XS model fine-tuned on trajectories from an XS-sized model using a more accessible prompt format would perform similarly — because we never see pre-trained XS executing the task in the code-as-prompt format. The capability gap being bridged by distillation may be partially a **format-following gap** rather than a **reasoning gap**, and the parameter count comparison is therefore inflated. An XS model that could execute the task from simple natural language prompts might achieve, say, 40% accuracy from the prompted baseline, making the distillation gain from 40% to 65.9% less dramatic than the implicit comparison to 0% (can't execute at all).

**What evidence exists in the paper.** The paper is transparent about the format limitation (Section 3.1) but does not explore its consequences. Table 1 shows that pre-trained PaLM 2-S and PaLM 2-XS have no Bamboogle scores — the "Pre-trained" row only has an entry for L (70.3%) with "N/A" for S and XS. This confirms they cannot execute the agent from few-shot prompts in the code-as-prompt format. But the paper does not report whether these models can execute a simpler version of the agent (e.g., natural language prompts), which would establish a baseline for how much of the improvement comes from format accessibility versus reasoning capability transfer.

The ablation on "More data vs better data" (Section 5.3, Table 3) shows that data quality (going from 1st gen to 2nd gen) matters more than data quantity for XS. But this analysis is entirely from the perspective of the small model as a data consumer — it doesn't address what would happen if the small model could also be a data generator in its own self-improvement loop.

**Mitigation status.** Not addressed as a limitation. The paper treats the code-as-prompt format as a justified design choice (Section 3.1) and the inability of smaller models to execute it as a fact about pre-training, not as a limitation of the methodology. Section 6 does not mention the prompt format as a constraint on the generality of the findings or as a factor that makes distillation less "emergent" and more "forced" than it appears.

### 6.5 Self-Improvement Saturates Rapidly — Gains Shrink to ~2 Points Per Iteration with Only Two Iterations Tested, and the Ceiling Is Unknown

**The assumption or constraint.** The paper demonstrates self-improvement for exactly two iterations, observing that the prompted PaLM 2-L improves from 70.3% (pre-trained) to 74.0% (iteration 1, +3.7 points) to 76.1% (iteration 2, +2.1 points) on Bamboogle auto-eval (Table 1). The paper does not run a third iteration, leaving the asymptotic behavior of the method uncharacterized. Section 6 explicitly raises this as an open question:

> "Another open question is a saturation point. How many additional iterations of self-improvement can we undertake past the 2nd one that still results in non-trivial gains? What does the saturation look like for smaller models? Will they all eventually converge to the same performance, or will the smaller models always be capped by the performance of the initial prompted large model?"

**The consequence.** The paper's framing of self-improvement as an iterative bootstrapping process ("ReST-like method that iteratively trains on previous trajectories," Section 1) implies that repeated cycles of grow → improve → grow → improve should yield continuous improvement. But the evidence from only two iterations already shows the canonical pattern of diminishing returns: the second iteration's gain (+2.1 points) is only 57% of the first iteration's gain (+3.7 points). If this trend continued linearly, a third iteration would yield roughly +1.2 points (76.1% → 77.3%), a fourth would yield +0.7 points (77.3% → 78.0%), and so on toward an asymptote — but whether the asymptote is at 78%, 80%, or 85% is entirely unknown.

This has direct practical implications:

- **If the asymptote is near 78%**, then the entire self-improvement pipeline (two iterations of trajectory generation, RM re-ranking, and fine-tuning three model sizes) yields a net +7.8 point gain over the prompted baseline, with no path to further improvement. A practitioner would need to weigh whether an 8-point accuracy gain justifies the computational cost and infrastructure complexity of the iterative loop.

- **If the asymptote is higher (e.g., 85%)**, then the paper's results represent only the beginning of a longer improvement curve, and the method is more valuable than the reported numbers suggest — but this would require a fundamentally different pattern than the one observed (diminishing returns between iterations would need to reverse or plateau at a higher level).

- **If the saturation is caused by the fixed question set**, then introducing new seed questions could restart the improvement curve — but the paper doesn't test this, so the saturation could also be caused by the agent hitting a fundamental capability ceiling (the base model's knowledge limits, the search tool's coverage, or the prompt format's expressiveness).

The paper's self-distillation results further complicate the saturation picture. The XS model improves dramatically from iteration 1 to iteration 2 (54.4% → 65.9%, +11.5 points), but this is driven by the teacher model improving between the two iterations (prompted L → fine-tuned L), not by the XS model participating in self-improvement. A third iteration would improve the teacher further (if at all), and the XS model would benefit from that improved data — but if the teacher saturates, the distillation path saturates with it. The paper asks whether smaller models "will always be capped by the performance of the initial prompted large model" (Section 6) — the answer from the current data is: they are capped by the performance of the *current* large model, and if that model saturates, so do they.

**What evidence exists in the paper.** Only two iterations of the self-improvement loop are run (Section 5.2). The diminishing returns pattern is visible in Table 1: +3.7 for L in iteration 1, +2.1 in iteration 2; +7.4 for S in iteration 1 (61.9% up from no prompted baseline), +7.8 in iteration 2; +9.7 for XS in iteration 1 (54.4% up from no prompted baseline), +11.5 in iteration 2. The L numbers are the cleanest measure of self-improvement per se (same-sized model improving from its own data), and they show clear deceleration. The paper does not report confidence intervals that would help determine whether the iteration 2 gain is statistically distinguishable from zero, though the standard deviations (±3.5 for prompted, ±3.3 for 1st gen, ±1.3 for 2nd gen) suggest it may be marginal given the sample size.

The paper's discussion of the saturation question (Section 6) acknowledges the uncertainty but does not attempt to bound it — there is no extrapolation, no analysis of what factors might limit further improvement (e.g., is the ranking model's discrimination ability the bottleneck? Is the search tool's coverage maxed out? Is the agent approaching an irreducible error rate from ambiguous questions?), and no proposal for how to diagnose which factor is the limiting one.

**Mitigation status.** Acknowledged but not measured. The paper raises the saturation question as future work (Section 6) but does not estimate where the asymptote might be or analyze which component of the system is likely to be the bottleneck. The open questions posed are exactly the right ones, but the paper's inability to answer them — even with bounding analyses or diagnostic experiments — means the reader leaves without knowing whether the method's yield curve is ~80% done (the asymptote is near 76%) or ~50% done (the asymptote is much higher, and more iterations would eventually reach it).

### 6.6 The Reference-Answer Requirement for Auto-Eval Restricts the Method to Questions with Known, Verifiable Answers — Incompatible with Truly Open-Ended Generation Tasks

**The assumption or constraint.** The paper's evaluation infrastructure — both auto-eval and human evaluation — depends on the existence of reference answers against which the agent's output can be judged. The auto-eval prompt (Listing 7) instructs the evaluator LLM to "Check whether the ANSWER implies the REF_ANSWER to the question" and provides examples explicitly comparing the agent's generated answer against a ground-truth reference string. Human evaluation, while not shown in full, is described as "either manually judge correctness or run auto-eval" (Section 4.1), implying a similar reference-answer-based protocol. The Bamboogle dataset comes with ground-truth answers; BamTwoogle was constructed with expected answers (Section 4.3 specifies that "expected answers should not be ambiguous").

**The consequence.** This evaluation design creates a fundamental tension with one of the paper's motivating claims. The paper argues that self-improvement without human labels is particularly valuable for "open-ended questions that don't have a single well-defined correct answer" (Eli5 family, Section 3.3) — yet the evaluation methodology cannot assess performance on such questions except by reducing them to reference-answer verification. The auto-eval prompt's logic — "does the answer imply the reference answer?" — assumes there is a reference answer to imply. For genuinely open-ended questions (e.g., "Explain why the sky is blue"), there may be many valid answers of varying depth, emphasis, and framing, none of which exactly matches a single reference. The auto-eval protocol has no mechanism for distinguishing between "this answer is wrong" and "this answer is correct but differently phrased or differently detailed than the reference."

The paper uses Eli5, Eli5-askH, and Eli5-askS questions as seed data for trajectory generation (Section 3.3), but evaluates only on Bamboogle and BamTwoogle — datasets of fact-seeking compositional questions with unambiguous answers. This means the training data includes open-ended explanatory questions, but the evaluation does not measure whether the agent's open-ended answering capability improves through self-training. The self-improvement gains demonstrated (Tables 1, 2) are gains on closed-form fact-seeking QA — not on the open-ended generation tasks that motivate the paper's emphasis on process-based training without correctness signals.

This limitation has a specific downstream consequence: **the method's value proposition changes significantly depending on task type**. For fact-seeking QA with verifiable answers, simpler outcome-based self-training methods (like STAR or ReST$^{EM}$) might work if you have access to reference answers, making the paper's process-based approach an interesting alternative primarily when reference answers are unavailable. But the paper's evaluation always uses reference answers at evaluation time — it never demonstrates that the method works when neither training *nor* evaluation has answer labels. The auto-eval itself is a form of reference-based supervision that would be unavailable in a truly open-ended deployment setting.

**What evidence exists in the paper.** The auto-eval prompt (Listing 7) and its validation against human judgments (Section 4.2, Pearson r = 0.98) demonstrate that the auto-eval accurately reproduces human reference-based judgments. But this validation is entirely within the reference-answer paradigm — it shows that the LLM judge agrees with human judges on whether an answer implies the reference, not that the reference-based judgment itself is a valid measure of answer quality for open-ended questions. The human evaluation protocols for Bamboogle and BamTwoogle (Section 4.3, Table 2) are not described in detail, but the fact that BamTwoogle explicitly specifies that "expected answers should not be ambiguous" (Section 4.3) confirms that even the most challenging evaluation dataset was designed with unique correct answers in mind.

The paper's choice of seed datasets reveals the gap: 500 questions from HotpotQA (multi-hop QA with reference answers) plus 1,500 questions from three Eli5 variants (long-form QA, typically with reference answers from Reddit). The agent is trained on trajectories from all 2,000 questions, but its performance is only measured on the 225 questions that have clean, unambiguous reference answers (Bamboogle and BamTwoogle). Whether the agent's Eli5-style explanatory answering quality improves through self-training is never assessed.

**Mitigation status.** Not acknowledged. The paper does not discuss the tension between its open-ended training data and its closed-form evaluation, nor does it propose evaluation methodologies that could assess performance on questions without unique correct answers. Section 6 mentions "open-ended questions" as part of the motivation ("the model can learn to handle open-ended questions that don't have a single well-defined correct answer in the first place"), but the evaluation section (Section 4) never addresses how such handling would be measured. The auto-eval infrastructure, which the paper presents as a contribution, is validated only for reference-based correctness judgments.
