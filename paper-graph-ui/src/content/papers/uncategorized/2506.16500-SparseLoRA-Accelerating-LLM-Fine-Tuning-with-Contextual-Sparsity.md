# SparseLoRA: Accelerating LLM Fine-Tuning with Contextual Sparsity

**ArXiv:** [2506.16500](https://arxiv.org/abs/2506.16500)

## 🎯 Pitch

This paper introduces **SparseLoRA**, a method that accelerates LLM fine-tuning by applying contextual sparsity—dynamically selecting a sparse subset of weights for loss and gradient computation based on the input sequence.

---

## 1. Executive Summary

This paper introduces **SparseLoRA**, a method that accelerates LLM fine-tuning by applying contextual sparsity—dynamically selecting a sparse subset of weights for loss and gradient computation based on the input sequence. Evaluated on LLaMA2-7B/13B and LLaMA3-8B across commonsense reasoning, arithmetic reasoning, code generation, and instruction following benchmarks, SparseLoRA uses a lightweight, training-free SVD sparsity estimator to identify important channels on the fly, combined with sensitivity-aware non-uniform sparsity across layers, context-output token splitting (applying sparsity only to context tokens while keeping output tokens dense), and progressive dense-to-sparse training (running dense fine-tuning for early steps before switching to sparse computation). The method reduces computational cost by up to 2.2× and achieves a measured wall-clock speedup of up to 1.6× while maintaining accuracy comparable to standard LoRA, establishing that contextual sparsity can effectively transfer from inference to the fine-tuning regime only when the sparsity patterns are adapted to layer-specific sensitivity, token-type sensitivity, and training-step sensitivity rather than applied uniformly.

## 2. Context and Motivation

### The Core Problem: Fine-Tuning Computation Has Been Neglected

The paper addresses a specific, concrete gap in the LLM fine-tuning landscape: **parameter-efficient fine-tuning (PEFT) methods successfully reduce memory usage but do nothing to reduce computational cost — and in some cases, they actively increase it.** This is not a hypothetical concern but a measurable reality. As Figure 1 shows, DoRA — a state-of-the-art PEFT method that reparameterizes weight matrices for more effective optimization — runs approximately **20% slower than standard LoRA** while delivering similar accuracy. QLoRA, which combines quantization with low-rank adapters to enable single-GPU fine-tuning of large models, runs about **10% slower than LoRA** (see Figure 1 bar chart, showing 716 ms forward pass for LoRA vs. 834 ms for QLoRA, and 623 ms backward vs. 809 ms for QLoRA). These methods trade runtime for memory savings, solving one bottleneck while leaving another untouched.

The practical consequence is significant: a memory-efficient fine-tuning method that takes 20–30% longer per step directly impacts researcher iteration speed, cloud compute costs, and the feasibility of running multiple fine-tuning experiments under budget constraints. For practitioners fine-tuning models on consumer-grade GPUs or paying for cloud instances by the hour, this compute overhead is not just an academic inconvenience — it translates directly to dollars and deadlines.

This gap has been systematically overlooked because the PEFT community's primary focus has been memory reduction, driven by the fact that full fine-tuning of modern LLMs (e.g., LLaMA2-7B requiring ~56 GB of VRAM for full-weight training) is impossible on a single consumer GPU. Methods like LoRA (Hu et al., 2022), QLoRA (Dettmers et al., 2023), DoRA (Liu et al., 2024b), and GaLore (Zhao et al., 2024) address this by reducing trainable parameters, quantizing weights, projecting gradients, or decomposing updates — all targeting the memory footprint of optimizer states, gradients, and activations. But as the paper's Figure 2 reveals, these memory-focused techniques operate in a regime where **linear layers dominate the runtime profile**: across sequence lengths from 128 to 2048 tokens, the combination of QKVO projections, FFN layers, and attention accounts for approximately 75–85% of total runtime in LLaMA3-8B fine-tuning. Reducing the number of trainable parameters (which is what LoRA does) does not reduce the cost of forward or backward passes through these dominant linear layers — the base model weights must still be multiplied by the full input tensor at every step.

The theoretical significance of this gap is that it represents a **missing dimension in the resource-efficiency landscape**. The community has developed sophisticated tools for trading off parameter count against memory, but has no analogous toolkit for trading off computation against accuracy during fine-tuning. This leaves an entire axis of optimization unexplored, creating a situation where a practitioner can choose between "memory-efficient but slow" methods and "fast but memory-hungry" full fine-tuning, with no option that is both memory-efficient and compute-efficient simultaneously.

### Why This Problem Matters: The Practical Economics of Fine-Tuning

The paper's Figure 2 provides the quantitative motivation. When fine-tuning LLaMA3-8B with LoRA, the runtime breakdown across different sequence lengths shows that:

- At sequence length 128: FFN layers consume ~63% of runtime, attention projections (QKVO) consume ~14%, with the remaining time split across LoRA branches (~2%), layer norm (~10%), RoPE (~8%), and other operations (~3%).
- At sequence length 512: FFN still dominates at ~62%, attention at ~15%, and LoRA branches remain at ~3%.
- At sequence length 2048: FFN drops to ~55% (as attention becomes relatively more expensive due to quadratic scaling), attention rises to ~15%, but LoRA branches remain minimal at ~6%.

The key insight from this breakdown: **the main branch of the model — the frozen, pretrained weights — dominates the computation budget, while the LoRA updates themselves (the low-rank matrices that represent the actual trainable parameters) consume only 2–6% of runtime.** This means that the PEFT community's focus on reducing trainable parameters, while successful for memory, is attacking a target that is essentially irrelevant for compute efficiency. To make fine-tuning faster, one must reduce the cost of forward and backward passes through the **frozen** pretrained weights — which is exactly where SparseLoRA applies its sparsity.

The real-world impact extends beyond individual researchers. Organizations running fine-tuning at scale — fine-tuning on multiple datasets, performing hyperparameter sweeps, or maintaining regularly updated fine-tuned models for production — face compounding compute costs. A 1.6× wall-clock speedup (as SparseLoRA achieves on LLaMA3-8B with arithmetic reasoning) means a hyperparameter sweep that would take 10 hours now takes ~6.25 hours, or conversely, allows ~1.6× more experiments in the same time budget. For cloud computing environments where GPU costs can exceed $2–4/hour for high-end instances, these savings are economically meaningful.

The memory-compute disconnect also matters for accessibility. Consumer GPUs (like the NVIDIA RTX 4090 with 24 GB VRAM) can fit quantized models for fine-tuning, but the resulting training speed can be so slow that experimentation becomes impractical. A method that reduces compute while maintaining the memory savings of quantization (as SparseLoRA demonstrates in combination with QLoRA in Table 6) directly addresses this pain point.

### Where Prior Approaches Fall Short

The paper identifies four distinct categories of prior work, each falling short of solving the compute-efficiency problem:

**Memory-Efficient Fine-Tuning (PEFT) — Reduced Memory, Not Compute**

The dominant PEFT approaches — LoRA, QLoRA, DoRA, and their variants — all operate by reducing the number of parameters that need gradient computation and optimizer state storage. They achieve this through low-rank decomposition (LoRA: $\Delta W = BA$ where $B \in \mathbb{R}^{d_{\text{out}} \times r}$ and $A \in \mathbb{R}^{r \times d_{\text{in}}}$ with $r \ll \min(d_{\text{in}}, d_{\text{out}})$), quantization (QLoRA: 4-bit NormalFloat quantization of the base model plus LoRA adapters), or weight decomposition (DoRA: decomposing pretrained weights into magnitude and direction components, then applying LoRA only to the directional component).

The critical limitation: none of these techniques reduce the FLOPs required for the forward or backward pass through the frozen pretrained weights. They all require computing $y = Wx + BAx$ — the full matrix-vector product $Wx$ still executes at full precision and full dimensionality. DoRA actually increases computation because its weight decomposition adds extra operations (magnitude normalization and directional reparameterization). The paper quantifies this directly: DoRA uses 132% of LoRA's FLOPs and runs at 0.7× LoRA's speed (Table 1), making it **slower than vanilla LoRA** despite its improved optimization properties.

GaLore (Zhao et al., 2024) takes a different approach — it projects gradients into a low-rank subspace using periodic online SVD updates, reducing optimizer state memory. However, as the paper's Table 13 reveals, this comes at a severe compute penalty: GaLore runs **1.58× slower than LoRA** with an amortized cost (including periodic SVD updates) of **13.72×**. The online SVD, while enabling gradient compression, is itself computationally expensive and fundamentally at odds with the goal of accelerating training.

**Contextual Sparsity for Inference — Wrong Granularity, Wrong Phase**

A substantial body of work has demonstrated that LLMs exhibit **contextual sparsity during inference** — significant portions of hidden states dynamically contain near-zero values depending on the input (Liu et al., 2023b; Song et al., 2023; Alizadeh et al., 2024; Lee et al., 2024; Akhauri et al., 2024). Methods like Deja Vu (Liu et al., 2023b) train small predictor networks to identify which attention heads and FFN neurons will be activated for a given input, then skip computation for the predicted-inactive components. These methods achieve 2× or greater inference speedups on single-token autoregressive generation.

However, the paper identifies three specific reasons these inference-time methods do not transfer to fine-tuning:

1. **Single-token vs. multi-token batch processing**: Inference methods operate on one token at a time during autoregressive generation. Fine-tuning processes entire sequences (potentially thousands of tokens) in parallel within a batch. The sparsity patterns that emerge for individual tokens may not compose cleanly when considering collective activation across a full sequence. A neuron that is inactive for 90% of individual tokens might still be active for the remaining 10%, and in batch processing across multiple sequences, the union of active neurons across all tokens can approach the full set.

2. **Head-level pruning granularity is too coarse**: Prior inference methods often prune entire attention heads (e.g., Deja Vu identifies and removes "uniform" heads that show flat attention patterns). The paper's Figure 9 demonstrates why this fails in fine-tuning: attention head patterns vary substantially across tokens within a sequence. A head that appears uniform for one token (and would be pruned by inference-time methods) may be a critical "heavy hitter" for another token in the same sequence. In LLaMA2-7B with 32 attention heads and 11,384 FFN channels, removing entire heads (as shown in Table 10: head-level QK pruning achieves 79.6% accuracy vs. 80.7% for channel-level) leaves far too little granularity for the diverse token-level processing demands of fine-tuning.

3. **Learned predictors may not generalize**: Methods like Deja Vu train dataset-specific predictor networks to map inputs to sparsity masks. These predictors are trained on inference workloads and may not generalize to the different data distributions encountered during fine-tuning, where the model sees training examples from specific downstream tasks rather than diverse general-domain text. The paper addresses this by proposing a training-free estimator (SVD-based) that does not require dataset-specific training.

**Computation-Efficient Training — Wrong Sparsity Type or Limited Scope**

Prior work on sparse training for LLMs has explored several directions, each with specific shortcomings:

- **Unstructured sparsity** (Thangarasa et al., 2023; Mozaffari et al., 2024): These methods prune individual weights (e.g., keeping only 50% of entries in a weight matrix, scattered arbitrarily). While they achieve theoretical FLOPs reduction, unstructured sparsity is notoriously difficult to accelerate on consumer GPUs because it does not map well to the GPU's SIMD execution model. Modern GPUs (like the NVIDIA A6000 used in this paper) are optimized for dense matrix operations — skipping individual scalar multiplies scattered throughout a tensor provides negligible actual speedup due to memory access patterns. The paper explicitly notes that these methods have "theoretical gains [that] are challenging to realize on consumer-grade GPUs" (Section 2).

- **Long-context focused methods** (Chen et al., 2024): LongLoRA uses shifted sparse attention to reduce the quadratic cost of attention computation when extending context windows. However, this targets only the attention mechanism and only when sequence lengths are very long. In the standard fine-tuning regimes the paper studies (sequence lengths 128–2048), Figure 2 shows that FFN layers, not attention, dominate runtime. Sparse attention alone leaves the majority of computation untouched.

- **Partial acceleration** (Ma et al., 2024; Chen et al., 2025): Recent work has attempted structural sparsity for training acceleration but either accelerates only the backward pass (leaving forward pass costs fully in place) or is not memory-efficient, forcing a choice between speed and memory savings. The paper's approach is specifically designed as **end-to-end acceleration**: sparsity is applied in both forward and backward passes (the sparsity mask is computed once per forward pass and reused during backward computation), and memory efficiency is preserved by keeping the LoRA branches dense and small.

**Gradient-Based and Dynamic Sparsity — Wrong Mechanism**

Methods that use gradient information to dynamically select sparse subnetworks during training (Zhou et al., 2021; Li et al., 2022) face a fundamental chicken-and-egg problem: to determine which weights are important for the current batch, you need the gradients through those weights, but computing those gradients requires executing the dense forward pass first. This circularity means gradient-based selection typically requires periodic dense passes to collect gradient signals, limiting the achievable sparsity ratio and complicating implementation.

### How SparseLoRA Positions Itself

The paper positions SparseLoRA at the intersection of two previously separate research threads — contextual sparsity (for inference) and parameter-efficient fine-tuning (for memory) — combining them to address the **compute-efficiency gap** that neither thread alone could solve. The key conceptual move is recognizing that the same principle that makes contextual sparsity work for inference (most input-dependent computation is redundant) should apply to fine-tuning, but only if the sparsity mechanism is **redesigned** to account for the distinct characteristics of the fine-tuning workload.

This redesign operates across four dimensions, each motivated by a specific failure mode of prior approaches:

1. **From single-token to batch-aware sparsity**: Instead of selecting neurons per-token (which would require recomputing sparsity masks for every token position, adding unacceptable overhead), SparseLoRA computes a single sparsity mask per linear layer per forward pass by aggregating activation signals across all tokens in the batch. This is the batch-level extension of token-level inference sparsity, enabled by the SVD estimator that can process the full input tensor $X \in \mathbb{R}^{(B \times L) \times D}$ efficiently.

2. **From head-level to channel-level granularity**: Rather than pruning entire attention heads (32 granularity units in LLaMA2-7B), SparseLoRA prunes individual channels within Q, K, V, and O projections (thousands of granularity units), enabling fine-grained selection that preserves critical token-level attention patterns. The QK Norm criterion (Equation in Section 3.1.2) specifically targets channels with minimal contribution to attention scores, avoiding the information loss that head-level pruning causes during fine-tuning.

3. **From learned predictors to training-free estimation**: Instead of training a predictor network (which requires dataset-specific training and may not generalize across fine-tuning tasks), SparseLoRA uses an offline SVD decomposition of the pretrained weights — computed once before fine-tuning begins — to project inputs into a low-rank space where the oracle sparsity metric can be approximated without any training. The SVD components ($U[:, :k]$, $S[:k]$, $V[:k, :]$) are loaded alongside the model weights and reused across all datasets and tasks, with the rank $k$ (typically 8) controlling the accuracy-efficiency tradeoff. Table 7 confirms this adds only 0.05% FLOPs and 0.8% runtime overhead while matching oracle accuracy within 0.3 percentage points (81.1% vs. 81.4% on Math10K).

4. **From uniform to sensitivity-aware allocation**: Rather than applying the same sparsity ratio to every layer (which prior sparse training methods often do), SparseLoRA conducts a layer-wise sensitivity analysis (Figure 7) and allocates sparsity non-uniformly: shallower layers remain mostly dense (they're more sensitive to perturbation), while deeper layers can tolerate aggressive sparsification (up to 90–97% for FFN layers, as shown in Table 12). This mirrors a finding from inference-time sparsity research (Gromov et al., 2024) but adapted to the fine-tuning context where layer importance can shift based on the downstream task.

The paper also explicitly distinguishes SparseLoRA from memory-efficient methods by emphasizing **complementarity rather than competition**. SparseLoRA is built on top of LoRA (sparsifying only the frozen main branch while leaving the LoRA adapters dense), meaning it inherits LoRA's memory savings of only storing optimizer states for the low-rank matrices. It can be combined with QLoRA (Table 6: SparseQLoRA achieves 1.2–1.3× speedup over QLoRA alone while maintaining its memory savings from 4-bit quantization), with gradient checkpointing, or with any other memory-reduction technique, since sparsity is applied orthogonally to the computation graph rather than competing for the same resources.

This positioning is captured succinctly in the paper's Section 1 statement:

> "To the best of our knowledge, this is the first work to leverage contextual sparsity for accelerating LLM fine-tuning."

This is a precise claim: it does not assert being the first to use sparsity in LLM training (which would be false, given the prior work on sparse pre-training and sparse attention), but rather the first to successfully adapt the specific mechanism of **contextual, input-dependent sparsity** — previously a purely inference-time technique — to the **fine-tuning** setting with the necessary modifications to handle multi-token batches, maintain end-to-end acceleration, and preserve accuracy across diverse downstream tasks.

## 3. Technical Approach

### 3.1 Reader Orientation

This paper presents a **system that accelerates LoRA-based LLM fine-tuning by bypassing computation on frozen pretrained weights that are not needed for a given input batch**. The core problem SparseLoRA solves is that PEFT methods like LoRA successfully reduce memory usage but leave the dominant computational cost — the forward and backward passes through the frozen base model — completely untouched. The solution involves dynamically selecting, at each training step and for each layer, a subset of weight channels to actually compute, while skipping the rest, with the selection driven by an extremely cheap estimator that looks at the input activations projected through a low-rank decomposition of the pretrained weights.

### 3.2 Big-Picture Architecture (Diagram in Words)

SparseLoRA has five major components, from offline preprocessing to online training:

1. **Offline SVD Decomposition** — performed once before any fine-tuning begins: each linear layer's pretrained weight matrix is decomposed via truncated SVD. The resulting low-rank factors (`$W_A$`, `$W_B$`) are stored alongside the model and loaded at the start of fine-tuning. These factors serve as the "estimator" that will predict sparsity masks at runtime.

2. **SVD Sparsity Estimator (Runtime)** — for each linear layer at each forward pass, the input activations are projected through the stored SVD factors to produce a low-rank approximation of the layer's output. A selection metric (L2 norm for FFN/VO projections, QK norm for QK projections) is computed from these approximate outputs, and the top-k channels are retained based on a pre-configured sparsity ratio for that layer. This produces a binary mask per layer, per batch.

3. **Sparse Computation Engine** — given the sparsity mask for a layer, only the columns of the weight matrix corresponding to retained channels are loaded and multiplied against the corresponding rows of the input. The output is a partial result that omits contributions from pruned channels. For the backward pass, the same mask is reused, so gradients flow only through the active weights.

4. **Context-Output Token Splitter** — the input sequence is divided into context tokens (the prompt) and output tokens (the target). SparseLoRA applies the sparsity mask only to context tokens; output tokens are always processed densely through the full weight matrix. The final loss is computed by gathering sparse results for context positions and dense results for output positions, then concatenating.

5. **Progressive Scheduling Controller** — for the first `$k$`% of training steps (configurable, up to 10%), all computation runs densely (standard LoRA). After this warmup period, the controller switches to sparse computation for the remaining steps, using the SVD estimator and pre-configured per-layer sparsity ratios determined by an offline sensitivity analysis.

Information flows as follows: a batch enters → the SVD estimator processes each layer's input activations → a binary sparsity mask is produced → the main branch weight multiplication executes sparsely using the mask (while LoRA branches run densely) → context tokens receive sparse treatment, output tokens receive dense treatment → the forward pass output is assembled → the loss is computed on output tokens → the backward pass reuses the same sparsity masks → optimizer updates only the LoRA parameters (since the base model is frozen).

### 3.3 Roadmap for the Deep Dive

- **First**, the oracle sparsity criteria (Sections 3.1.1 and 3.1.2) — the L2 Norm metric for FFNs and VO projections, and the QK Norm metric for QK projections. These define what "ideal" channel selection would look like if computation were free, establishing the ground truth that the SVD estimator must approximate.
- **Second**, the SVD sparsity estimator itself (Section 3.2, Algorithm 1) — how it approximates the oracle at negligible cost, why SVD rather than learned predictors, and how the rank parameter controls the accuracy-efficiency tradeoff.
- **Third**, the layer sensitivity analysis and non-uniform sparsity allocation (Section 3.3, "Layer Sensitivity") — how per-layer sparsity ratios are determined offline and why deeper layers can tolerate far more pruning than shallow ones.
- **Fourth**, the context-output token splitting strategy (Section 3.3, "Token Sensitivity") — why output tokens are disproportionately sensitive to sparsity, how the structural distinction between context and output enables a simple rule, and the empirical evidence supporting this design.
- **Fifth**, the progressive sparse fine-tuning schedule (Section 3.3, "Step Sensitivity") — why early training steps need dense computation, the warmup ratio configuration, and how this interacts with the other sensitivity dimensions.
- **Sixth**, the complete integration of all these mechanisms into the end-to-end SparseLoRA fine-tuning procedure, including how masks are computed once per forward pass and reused in the backward pass, and why this enables measured wall-clock speedups (not just theoretical FLOPs reduction).

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems and methods paper** whose core idea is that contextual sparsity — previously used only for accelerating single-token LLM inference — can be adapted to multi-token batch fine-tuning by redesigning the sparsity selection mechanism (training-free SVD estimator instead of learned predictors), the pruning granularity (channel-level instead of head-level), and the allocation strategy (non-uniform across layers, tokens, and steps based on systematic sensitivity analysis).

#### Oracle Sparsity Criteria: Defining the Ideal Selection Mechanism

The foundation of SparseLoRA is the observation that, during fine-tuning, not all weight channels contribute equally to the forward pass output for a given input batch. If one could identify — with perfect accuracy and zero overhead — which channels matter most for a specific input, computation on the remaining channels could be skipped entirely. The paper defines two **oracle criteria** that represent this ideal: metrics that, if computed from the *actual* full-precision activations, would select the optimal subset of channels. These oracles are computationally infeasible to compute in practice (since they require the dense forward pass that sparsity is meant to avoid), but they serve as the **target that the SVD estimator must approximate** and as the **evaluation benchmark** against which the estimator's quality is measured.

##### L2 Norm Criterion for FFNs and VO Projections

For feed-forward network (FFN) layers and value-output (VO) attention projections, the paper selects channels based on the L2 norm of their output activations, motivated by the extreme sparsity observable in certain intermediate activations.

**Where the sparsity comes from:** In the FFN of LLaMA-style models, the computation proceeds as:

$$\text{FFN}(x) = W_{\text{down}} \cdot \left( \text{SiLU}(x W_{\text{gate}}) \odot (x W_{\text{up}}) \right)$$

where `$W_{\text{gate}}$`, `$W_{\text{up}}$`, and `$W_{\text{down}}$` are the three weight matrices of the gated FFN block, `$\text{SiLU}$` is the Sigmoid Linear Unit activation function, and `$\odot$` denotes element-wise multiplication. The key insight from prior work (Alizadeh et al., 2024; Lee et al., 2024; Song et al., 2023) and confirmed in this paper's Figure 4 is that **the SiLU activation naturally induces sparsity**: SiLU outputs near-zero values for negative inputs, meaning that a significant fraction of the intermediate hidden dimensions become essentially zero after the activation. The paper's Figure 4 visualizes this: the input activations to `$W_{\text{down}}$` (the down projection) follow a Laplace-like distribution with most values concentrated near zero, implying that only a small subset of channels carry substantial signal.

**The oracle selection procedure for FFNs:**

1. Compute the full intermediate activations: `$h = \text{SiLU}(x W_{\text{gate}}) \odot (x W_{\text{up}})$`. This requires executing `$W_{\text{gate}}$` and `$W_{\text{up}}$` densely, which is the expensive operation sparsity aims to avoid — hence this is an oracle, not a practical method.

2. Compute the output of the down projection: `$o = h W_{\text{down}}$`, but consider it column-wise: each column `$j$` of `$W_{\text{down}}$` produces one scalar contribution per token per batch element, given by `$h_j \cdot W_{\text{down}}[:, j]$`. The aggregate importance of channel `$j$` across all tokens is the L2 norm of these contributions:

   $$\text{importance}_j = \| h[:, j] \cdot W_{\text{down}}[:, j] \|_2$$

   where `$h[:, j]$` is the `$j$`-th column of the intermediate activations (values for channel `$j$` across all tokens in the batch), and `$W_{\text{down}}[:, j]$` is the `$j$`-th column of the down-projection weight matrix.

   More directly, the paper frames this as the L2 norm of the output activation contributed by each channel. For a batch of activations `$X$` (shape `$(B \times L) \times D_{\text{in}}$`), each channel `$i$` in the input dimension produces an output contribution that can be measured by its L2 norm across the batch and sequence dimensions.

3. Retain the top `$n$` channels with the highest L2 norm, where `$n$` is determined by the layer's configured sparsity ratio (e.g., for 90% sparsity, keep the top 10% of channels).

**Channel sharing between gate, up, and down projections:** The paper introduces a critical structural optimization. As illustrated in Figure 5, the three FFN weight matrices (`$W_{\text{gate}}$`, `$W_{\text{up}}$`, `$W_{\text{down}}$`) share the same intermediate dimension (the "hidden" or "intermediate" dimension of the FFN, typically 11,008 for LLaMA2-7B). The channels selected for the down projection — identified by their indices in this intermediate dimension — can be applied to the gate and up projections as well. That is, if channel `$j$` is selected for `$W_{\text{down}}$` (meaning column `$j$` of `$W_{\text{down}}$` is retained), then row `$j$` of `$W_{\text{gate}}$` and row `$j$` of `$W_{\text{up}}$` are also retained, and computation for all other channels in the gate and up projections is skipped. This eliminates the need to independently assess sparsity for gate and up projections — the mask derived from the down projection's output activations propagates backward to the preceding linear layers.

**For VO attention projections:** The same L2 norm criterion applies to the output projection (`$W_O$`) of attention layers. The input activations to `$W_O$` (which are the concatenated outputs of all attention heads) exhibit similar sparsity patterns to FFN down projections, as shown in Figure 4 (the "Attn Input" distributions for `$W_O$` follow a Laplace-like shape). The L2 norm of each channel's contribution is computed from the output of `$W_O$` and channels are selected accordingly. As with FFNs, the channel indices selected for `$W_O$` are also applied to `$W_V$` (the value projection) in the preceding step — they share the same head dimension — so sparsity on VO projections is coordinated rather than independent.

**Why L2 norm rather than alternatives:** The paper explicitly compares L2 norm against Wanda (Sun et al., 2024), a weight-magnitude-based pruning criterion, and random selection (Table 10) in the oracle setting. On Math10K with 90% uniform sparsity, FFN sparsity using L2 norm achieves 81.4% accuracy, Wanda achieves 81.3% (nearly identical), and random achieves 78.6%. The paper notes that L2 norm is preferred for its simplicity: it requires only the activation values (which must be computed anyway for the forward pass) without accessing weight magnitudes or gradient information. The justification in Section 3.1.1 states that "activations generally contain more influential outliers than weights" (Xiao et al., 2023), making activation-based criteria more directly informative about which channels drive the layer's output.

##### QK Norm Criterion for Query and Key Projections

The L2 norm criterion that works well for FFNs and VO projections fails for query and key (`$W_Q$`, `$W_K$`) projections. The paper's Figure 4 shows why: the input activations to Q and K projections do not exhibit the Laplace-like sparsity pattern seen in FFN down projections and attention output projections. Instead, the activation distributions for Q and K are more uniform, meaning that simply taking the L2 norm of their output activations would not concentrate importance in a small subset of channels — the pruning would be essentially random.

The paper considers and rejects head-level pruning for QK projections. Prior inference-time methods (Liu et al., 2023b; Akhauri et al., 2024) identify entire attention heads with uniform attention scores and prune them entirely. This coarse granularity is acceptable for single-token autoregressive generation, where removing a head that distributes attention uniformly across all previous tokens causes minimal harm. However, the paper's Appendix A.1 (Figure 9) demonstrates that this fails in fine-tuning: attention head patterns vary substantially across different tokens within the same sequence. A head that appears uniform for one query token (and would be pruned by inference-time heuristics) may serve as a critical "heavy hitter" head for another token. Moreover, with only 32 attention heads in LLaMA2-7B, the granularity is too coarse — pruning even one head removes 1/32 ≈ 3.1% of attention capacity, which is a blunt instrument compared to the thousands of FFN channels where individual channel removal affects only ~0.009% of capacity.

The paper's solution is a channel-level QK pruning criterion based on attention scores rather than activation magnitudes. The computation, defined in Section 3.1.2, is as follows:

Given the query and key projection outputs `$Q, K \in \mathbb{R}^{(B \times L) \times D}$` where `$B$` is batch size, `$L$` is sequence length, and `$D$` is the hidden dimension (e.g., 4096 for LLaMA2-7B), first compute the L2 norm of each across the flattened batch and sequence dimensions to get per-channel magnitude vectors:

$$q = \|Q\|_2 \in \mathbb{R}^D$$

$$k = \|K\|_2 \in \mathbb{R}^D$$

where `$q_j = \sqrt{\sum_{b,l} Q_{b,l,j}^2}$` is the aggregate magnitude of the `$j$`-th query channel across all tokens in the batch, and similarly for `$k_j$`.

These two vectors are combined via element-wise (Hadamard) product to produce the importance score per channel:

$$s = q \odot k \in \mathbb{R}^D$$

where `$s_j = q_j \cdot k_j$` is the product of the query and key magnitudes for channel `$j$`.

**What this computes:** The element-wise product `$s_j = q_j \cdot k_j$` measures the joint contribution of channel `$j$` to the attention mechanism. In the attention computation, the pre-softmax attention scores are `$Q K^T$`, and each entry `$(i, j)$` of this matrix involves the inner product of the `$i$`-th query vector with the `$j$`-th key vector. The per-channel contribution to these inner products is `$Q_{:, c} \cdot K_{:, c}$` — the product of the query and key values at channel `$c$` for each pair of positions. By aggregating across all positions via the L2 norm, `$q_c$` measures how strongly channel `$c$` participates in queries, `$k_c$` measures how strongly it participates in keys, and their product `$s_c$` approximates how much channel `$c$` contributes to the overall attention score matrix. Channels with small `$s_c$` contribute minimally to attention and can be pruned.

The top `$n$` channels (those with the largest `$s_c$` values) are retained, where `$n$` is determined by the configured sparsity ratio for QK projections.

**Why this form:** The product `$q \odot k$` captures the multiplicative nature of attention — a channel can be important even if only queries use it strongly, or only keys use it strongly, or (most importantly) both use it strongly. An additive criterion like `$q + k$` would incorrectly treat a channel with strong query presence but zero key presence as moderately important, when in fact it contributes nothing to the attention dot products (since `$Q_c \cdot 0 = 0$`). The product correctly zeroes out channels that are absent from either queries or keys. The paper validates this empirically in Table 10: under 90% uniform sparsity with token splitting at 5% step offset, attention norm (channel-wise) achieves 80.7% accuracy on Math10K, while L2 norm on QK activations achieves only 79.8%, and random achieves 79.1%.

**The oracle status of QK Norm:** Computing `$q$` and `$k$` requires executing `$W_Q$` and `$W_K$` densely to obtain the full `$Q$` and `$K$` matrices. Like the L2 norm oracle for FFNs, this is the dense computation that sparsity aims to avoid. The SVD estimator must approximate these per-channel importance scores without performing the dense QK projection.

#### The SVD Sparsity Estimator: Approximating the Oracle Without Dense Computation

The oracle criteria demonstrate that dynamic, input-dependent channel selection can identify sparse subsets that preserve model quality. However, computing the oracle patterns requires partial dense computation — specifically, the gate and up projections for FFN intermediate activations (to get the L2 norm), and the full QK projections for attention-based importance scores. This partial dense computation would negate any speedup from sparsifying the remaining layers, creating a circular dependency: to know which channels to skip, you must first compute the very operations you want to skip.

The paper's central technical contribution is the **SVD sparsity estimator**: a lightweight, training-free mechanism that approximates the oracle sparsity masks using only the input activations and a pre-computed low-rank decomposition of the pretrained weights, adding negligible computation overhead (0.05% FLOPs, 0.8% runtime).

##### Core Idea: Low-Rank Approximation of Oracle Metrics

The intuition, expressed in Section 3.2, is:

> "instead of training a predictor to map inputs to sparsity masks, we project inputs onto a low-rank SVD decomposition of the original weights and compute the oracle metric from these projected activations"

In other words: **approximate the layer's output using a cheap low-rank projection, then apply the same importance metric to this approximate output as you would to the true output.** If the low-rank projection captures the dominant directions of variation in the weight matrix, the approximate activations will preserve the relative ordering of channel importance, even if their absolute values are inaccurate.

The SVD of a weight matrix `$W \in \mathbb{R}^{D_{\text{in}} \times D_{\text{out}}}$` decomposes it as:

$$W = U \Sigma V^T$$

where `$U \in \mathbb{R}^{D_{\text{in}} \times D_{\text{in}}}$` contains the left singular vectors, `$\Sigma \in \mathbb{R}^{D_{\text{in}} \times D_{\text{out}}}$` is a rectangular diagonal matrix of singular values `$\sigma_1 \geq \sigma_2 \geq \dots \geq \sigma_{\min(D_{\text{in}}, D_{\text{out}})} \geq 0$`, and `$V \in \mathbb{R}^{D_{\text{out}} \times D_{\text{out}}}$` contains the right singular vectors.

A rank-`$k$` truncated SVD retains only the top-`$k$` singular values and their corresponding vectors:

$$W^{(k)} = U_{:, :k} \Sigma_{:k, :k} V_{:k, :}^T$$

This `$W^{(k)}$` is the optimal rank-`$k$` approximation of `$W$` in the Frobenius norm (by the Eckart-Young-Mirsky theorem). The forward pass using this low-rank approximation would be:

$$y_{\text{approx}} = x W^{(k)} = x (U_{:, :k} \Sigma_{:k, :k}) V_{:k, :}^T$$

By splitting the diagonal singular value matrix symmetrically, the paper defines two low-rank factors:

$$W_A = U_{:, :k} \Sigma_{:k, :k}^{1/2} \in \mathbb{R}^{D_{\text{in}} \times k}$$

$$W_B = \Sigma_{:k, :k}^{1/2} V_{:k, :}^T \in \mathbb{R}^{k \times D_{\text{out}}}$$

such that `$W^{(k)} = W_A W_B$`. The approximate output can then be computed as a chained low-rank projection:

$$y_{\text{approx}} = (x W_A) W_B$$

where `$x W_A$` reduces the input from `$D_{\text{in}}$` dimensions to `$k$` dimensions (cheap), and the subsequent multiplication by `$W_B$` expands from `$k$` to `$D_{\text{out}}$` dimensions (also cheap when `$k \ll \min(D_{\text{in}}, D_{\text{out}})$`).

**Concretely, the procedure at runtime** (Algorithm 1):

1. For a given linear layer with input activations `$x$` of shape `$(B \times S, D_{\text{in}})$`:
   - Compute the low-rank projected activations: `$h = x W_A$`, producing a tensor of shape `$(B \times S, k)$`. This costs `$O(B \cdot S \cdot D_{\text{in}} \cdot k)$` FLOPs, which for small `$k$` (e.g., 8) is negligible compared to the full matrix multiplication `$x W$` that costs `$O(B \cdot S \cdot D_{\text{in}} \cdot D_{\text{out}})$` (e.g., `$2 \times B \cdot S \cdot 4096 \cdot 11008 \approx 90$` million FLOPs per batch element for a single FFN layer).
   - Compute the approximate output: `$\hat{y} = h W_B$`, producing a tensor of shape `$(B \times S, D_{\text{out}})$`. This costs `$O(B \cdot S \cdot k \cdot D_{\text{out}})$` FLOPs.

2. Apply the oracle metric to `$\hat{y}$` rather than to the true output `$y$`:
   - For FFN and VO layers: compute the L2 norm of each channel's contribution from `$\hat{y}$`, select the top channels.
   - For QK layers: compute `$q$` and `$k$` from the approximate Q and K projections (obtained via the SVD estimator applied to `$W_Q$` and `$W_K$`), compute `$s = q \odot k$`, select the top channels.

3. The resulting binary mask indicates which channels to compute densely. Only these channels are processed through the full-precision weight matrix.

##### Offline Preprocessing and Runtime Cost

The SVD decomposition is performed **once offline** before fine-tuning begins, separately for each linear layer in the model. The resulting low-rank factors `$W_A$` and `$W_B$` for each layer are saved to disk and loaded alongside the model weights at the start of fine-tuning.

The paper states (Section 3.2 and Table 7) that the SVD estimator uses **rank `$k = 8$`**. This is a critical hyperparameter choice:
- Too low a rank (e.g., `$k = 2$` or `$4$`): the low-rank approximation captures too little of the weight matrix's variance, and the estimated importance scores become inaccurate — channels that are actually important may be incorrectly pruned, degrading model quality.
- Too high a rank (e.g., `$k = 32$` or `$64$`): the approximation quality improves, but the computational overhead of the SVD estimator grows — `$O(B \cdot S \cdot D_{\text{in}} \cdot k + B \cdot S \cdot k \cdot D_{\text{out}})$` becomes non-negligible when `$k$` approaches the original dimensions.
- At `$k = 8$`, the paper reports that the overhead is **0.05% of total FLOPs** and **0.8% of end-to-end runtime**, while achieving accuracy within 0.3 percentage points of the oracle (81.1% vs. 81.4% on Math10K, Table 7). The SVD factors add 30 MB of memory overhead.

The paper explicitly notes why this overhead is acceptable in fine-tuning but would be problematic in inference:

> "while low-rank module overheads can be significant in inference-time sparsity methods due to memory-bound execution... our approach introduces minimal overhead (less than 1% of runtime) since the lightweight SVD projections are negligible compared to the matrix multiplications in the compute-bound LLM fine-tuning"

During **inference**, operations are memory-bandwidth-bound: the GPU spends most of its time waiting for weights to be loaded from memory, so even small additional computations (like a rank-8 projection) can significantly impact latency because they compete for memory bandwidth. During **fine-tuning**, operations are compute-bound: the large matrix multiplications (`$x W$` where `$x$` has batch dimension) saturate the GPU's compute units, and the small SVD projections can execute concurrently with memory transfers without competing for the primary bottleneck. This makes the rank-8 estimator effectively free in the fine-tuning regime.

##### Training-Free vs. Learned Predictors

The paper explicitly contrasts the SVD estimator with the learned predictor approach used in inference-time methods like Deja Vu (Liu et al., 2023b). Learned predictors require:
1. Collecting training data: run the model on representative inputs, record which neurons activate (or which would be selected by the oracle), and use these as supervised targets.
2. Training a small neural network (typically a 2–3 layer MLP) to predict the sparsity mask from the layer's input activations.
3. Potentially repeating this process for each new dataset or task, since sparsity patterns may shift with the data distribution.

The SVD estimator eliminates all three requirements. The SVD decomposition depends only on the pretrained weights (which are fixed throughout fine-tuning), not on any training data. The same SVD factors serve for all downstream tasks, all datasets, and all fine-tuning runs. This is what the paper means by "training-free": no gradient updates, no data collection, no hyperparameter tuning beyond choosing the rank `$k$`.

The paper validates this in Table 7: the SVD estimator achieves accuracy within 0.3% of the oracle, confirming that a rank-8 approximation of the weight matrix is sufficient to preserve the relative ordering of channel importance. The residual error (oracle 81.4% vs. SVD 81.1%) is attributed to cases where the low-rank approximation distorts the importance ordering for channels with very similar oracle scores — but since these are precisely the channels where the choice matters least (their contributions are nearly equal), the impact on final accuracy is minimal.

##### Why SVD Specifically?

The paper does not extensively justify SVD over other low-rank factorizations (e.g., QR decomposition, random projections), but several properties make SVD the natural choice:
- **Optimality**: The truncated SVD provides the best rank-`$k$` approximation in Frobenius norm, meaning no other rank-`$k$` matrix approximates `$W$` more accurately. This directly translates to the best possible preservation of output activation patterns for a given rank budget.
- **Determinism**: SVD of a fixed matrix is deterministic and can be computed once offline with high numerical precision (using `torch.linalg.svd` with `full_matrices=False`). There is no randomness, no convergence issues, and no need for multiple runs.
- **Decomposability**: Splitting `$\Sigma^{1/2}$` symmetrically between `$U$` and `$V$` ensures that the two low-rank projections are balanced in scale, avoiding numerical instability where one factor has extremely large values and the other extremely small.

#### Layer Sensitivity Analysis and Non-Uniform Sparsity Allocation

The paper observes that "the inherent contextual sparsity across layers in LLMs often varies significantly" and that "the importance of individual layers and their contributions to fine-tuning can differ substantially" (Section 3.3). Applying a uniform sparsity ratio (e.g., 50% for all layers) would be suboptimal because it would over-prune sensitive shallow layers and under-prune redundant deep layers.

##### The Layer Sensitivity Analysis Procedure

To determine per-layer sparsity configurations, the paper conducts an empirical sensitivity study using the commonsense reasoning benchmark (CSR170K) as a proxy task. The procedure works as follows:

1. Start with a model that has been **densely fine-tuned** (standard LoRA, no sparsity) on CSR170K. This provides the baseline accuracy that sparse configurations must approach.

2. For each layer `$\ell$` independently:
   - Apply a candidate sparsity ratio `$s \in \{10\%, 30\%, 50\%, 70\%, 90\%\}$` **only to layer `$\ell$`**, keeping all other layers fully dense.
   - Re-evaluate accuracy on the CSR170K test set.
   - Record the accuracy drop `$\Delta_\ell(s) = \text{accuracy}_{\text{dense}} - \text{accuracy}_{\ell \text{ at sparsity } s}$`.

3. This produces, for each layer, a **sensitivity curve**: accuracy as a function of sparsity ratio for that layer in isolation.

Figure 7 shows the results for LLaMA2-7B across all 32 layers. The key pattern:

- **Shallow layers (layers 0–10)** are highly sensitive to sparsity. At 90% sparsity, accuracy drops from roughly 0.84 to approximately 0.77 for the earliest layers. At 50% sparsity, the drop is still visible at roughly 0.01–0.03 absolute accuracy points.
- **Deeper layers (layers 15–30)** are remarkably resilient. For layers beyond index 20, even 90% sparsity causes minimal accuracy degradation — the curve at 90% sparsity sits very close to the 10% sparsity curve, and both are near the dense baseline of ~0.84.
- **Intermediate layers (10–15)** show a transitional pattern: moderate sensitivity at high sparsity ratios, but resilient at lower ratios.

This pattern aligns with findings from Gromov et al. (2024), who observed that deeper layers in LLMs contain more redundant information and can be aggressively pruned or even removed with minimal impact on downstream performance. The paper hypothesizes that deeper layers in pretrained transformers encode more abstract, compositional features that are distributed across many channels, making individual channels less critical. Shallower layers, by contrast, encode more concrete, local features where individual channels may carry specific syntactic or lexical information that cannot be easily recovered from other channels.

##### Translating Sensitivity Curves to Sparsity Configurations

The sensitivity analysis does not directly prescribe a sparsity configuration — it provides a per-layer sensitivity profile that the practitioner uses to **allocate the sparsity budget non-uniformly**. The concrete configurations used in the paper's experiments are shown in Table 12:

**For LLaMA2-7B on CSR170K (1.3× speedup):**
- **FFN layers**: Layers 13–29 are sparsified at 90%. Layers 0–12 and layer 30–31 remain dense (0% sparsity).
- **QKVO projections**: Layers 17–29 are sparsified at 50%, with layers 20 and 24 specifically excluded (kept dense). All other layers remain dense.
- **Progressive step offset**: 5% of training steps run densely before switching to sparse.

**For LLaMA3-8B on Math10K (1.6× speedup, the paper's most aggressive configuration):**
- **FFN layers**: Layers 3–30 are sparsified at 99% — essentially, only 1% of FFN channels are retained in these layers. Layers 0–2 and 31 remain dense.
- **QKVO projections**: Layers 14–19 and 21–23 and 25–29 are sparsified at 75% (retaining 25% of channels). Specific layers are excluded (kept dense): 0–13, 20, 24, 30–31.
- **Progressive step offset**: 0% — training runs sparsely from the very beginning.

The pattern is consistent: deeper layers get higher sparsity, shallower layers remain dense, and within the attention projections, certain layers are explicitly excluded from sparsity (layers 20 and 24 for LLaMA2-7B, layers 20 and 24 for LLaMA3-8B). The paper does not explain the specific choice of excluded layers, but these are likely identified by the sensitivity analysis as anomalously sensitive attention layers that buck the general trend of deep-layer resilience.

Table 9 provides an ablation confirming the value of non-uniform allocation. On LLaMA3-8B with Math10K:
- At **60% FLOPs** (i.e., 40% FLOPs reduction): uniform sparsity achieves 80.3% accuracy at 1.1× speedup; non-uniform achieves 81.1% accuracy at 1.4× speedup. The non-uniform configuration is both faster and more accurate.
- At **46% FLOPs** (54% reduction): uniform achieves 80.2% accuracy at 1.5× speedup; non-uniform achieves 81.1% at 1.6× speedup.
- At **37% FLOPs** (63% reduction): uniform achieves 79.5% accuracy at 1.6× speedup; non-uniform achieves 80.5% at 1.8× speedup.

The non-uniform configuration consistently outperforms uniform sparsity at the same FLOPs budget, and the gap widens at higher sparsity ratios. This is because uniform sparsity forces the same ratio onto sensitive shallow layers and resilient deep layers, wasting the sparsity budget on layers where it hurts while leaving performance on the table for layers that could tolerate more.

#### Context-Output Token Splitting: Why Output Tokens Need Dense Computation

The paper identifies a second dimension of sensitivity: not all tokens in a sequence are equally affected by sparsity. In supervised fine-tuning, each training example consists of a **context** (the input prompt, which is provided to the model) and an **output** (the target response, which the model must learn to generate). The loss is computed only on the output tokens — the model's predictions on context tokens are ignored during backpropagation, since the model is not being trained to reproduce the prompt.

This structural distinction has a direct consequence for sparsity: **output tokens are much more sensitive to pruning than context tokens.** The paper demonstrates this empirically in Table 8:

On Math10K (where output tokens constitute a substantial fraction of the total sequence — math reasoning problems have long solutions):
- **All tokens sparsified**: accuracy drops catastrophically to 47.1% (from a dense baseline that would be approximately 80%).
- **Random subset kept dense** (matching the number of output tokens, but chosen randomly rather than specifically targeting outputs): accuracy recovers only to 70.9%.
- **Output tokens kept dense, context tokens sparsified**: accuracy recovers to 81.1% — essentially matching or slightly exceeding the dense baseline.

On CSR170K (where output tokens are a smaller fraction of the sequence — e.g., multiple-choice answers are short):
- The degradation from sparsifying all tokens is much smaller (86.7% → 86.7% vs. 86.9% with output-aware splitting), confirming that the sensitivity is proportional to the fraction of output tokens.

**Why output tokens are more sensitive:** The paper's explanation is rooted in optimization dynamics. During the backward pass, gradients flow from the loss computation (at output token positions) back through the network. If the forward pass activations at output token positions are approximated (via sparse computation), the gradients computed from them will be similarly approximate, leading to noisier or biased gradient signals for the LoRA parameter updates. Context tokens, by contrast, do not directly contribute to the loss — their activations matter only insofar as they influence the hidden states that the output tokens attend to. Approximating context token computations introduces some distortion in the attention patterns and hidden state propagation, but this distortion is second-order compared to the first-order error of approximating the very activations from which the loss is derived.

The implementation (Figure 8) is straightforward:
1. During the forward pass, the input sequence is split into context positions and output positions based on the known token boundaries in the training data.
2. The sparse computation (using the SVD-derived mask) is applied to all tokens, producing sparse outputs.
3. The dense computation is applied **only to output tokens**, producing dense outputs for those positions.
4. The final hidden states are assembled by taking sparse results for context positions and dense results for output positions, then concatenating along the sequence dimension.
5. The language modeling head and loss computation proceed as normal on the assembled hidden states.

The computational cost of this splitting is modest: output tokens typically constitute 10–30% of the total sequence length (e.g., for CSR170K with short answers, ~5–10%; for Math10K with step-by-step solutions, ~30–50%). The overhead is running dense computation on this fraction of tokens, which reduces the effective sparsity ratio but preserves gradient signal quality where it matters most.

#### Step Sensitivity and Progressive Sparse Fine-Tuning

The paper identifies a third sensitivity dimension: **early fine-tuning steps are more sensitive to sparsity than later steps**. This observation is consistent with broader findings in sparse training literature (Lu et al., 2023; Thangarasa et al., 2023; Bambhaniya et al., 2024) suggesting that maintaining dense computation during the initial optimization phase allows the model to establish a good parameter trajectory before transitioning to sparse computation.

The mechanism: In the early steps of fine-tuning, the LoRA parameters (`$A$` and `$B$` matrices) are typically initialized to produce near-zero updates (e.g., `$A$` initialized with random Gaussian, `$B$` initialized to zero, so `$BA \approx 0$` and the model initially behaves identically to the pretrained base model). The first several hundred steps represent the most dramatic parameter movement, as the LoRA matrices rapidly adapt to the downstream task. During this phase, gradient signal quality is critical — errors introduced by sparse approximation of the forward pass can cause the LoRA parameters to converge to a suboptimal basin, from which later recovery is difficult.

By contrast, later in fine-tuning (after the initial rapid adaptation), the parameter trajectory enters a refinement phase where gradient signals are smaller and the optimization landscape is flatter. Sparse approximation errors are less consequential at this stage because they represent a smaller fraction of the already-diminished gradient magnitude.

The implementation is controlled by a **step offset hyperparameter**, expressed as a percentage of total training steps:

- For the first `$p$`% of training steps, all computation runs densely (standard LoRA, no sparsity masks applied).
- After `$p$`% of steps have elapsed, the controller switches to sparse computation for all remaining steps.

The paper uses `$p = 5\%$` for most configurations (Table 12: CSR170K, GLUE, CodeFeedback, WizardLM) and `$p = 10\%$` for LLaMA2-13B on CSR170K. For the most aggressive configuration (LLaMA3-8B on Math10K at 1.6× speedup), `$p = 0\%$` — training is sparse from the very first step. The paper does not provide a dedicated ablation study on the step offset parameter (it appears only in the configuration table), but the choice of `$p = 0\%$` for the highest-speedup configuration suggests that dense warmup is a conservative choice that can be reduced or eliminated when aggressive speedup is prioritized over maximal accuracy preservation.

**Interaction with other sensitivity dimensions:** The progressive schedule compounds with the other sensitivity mechanisms. During the dense warmup phase, all layers, all tokens (context and output), and all channels are processed densely. When the switch to sparsity occurs, the non-uniform layer configurations and context-output splitting take effect simultaneously. This means the model transitions from a fully dense optimization regime to a regime where shallow layers are dense (because they were configured as dense), deeper layers are sparse on context tokens but potentially dense on output tokens, and the LoRA adapters remain dense throughout. The progressive schedule smooths this transition by establishing initial LoRA parameter values under ideal (dense) conditions before introducing approximation.

#### End-to-End Integration: How All Mechanisms Compose During a Training Step

Putting together all components, a single training step in SparseLoRA proceeds as follows:

**1. Forward pass, layer by layer:**

For each linear layer (FFN gate/up/down, Q/K/V/O projections):
   a. The input activations `$x$` (shape `$(B \times L) \times D_{\text{in}}$`) are projected through the SVD estimator:
      - `$h = x W_A$` (shape `$(B \times L) \times k$`, where `$k = 8$`)
      - `$\hat{y}_{\text{SVD}} = h W_B$` (shape `$(B \times L) \times D_{\text{out}}$`)
   b. The oracle metric is computed on `$\hat{y}_{\text{SVD}}$`:
      - For FFN/VO: per-channel L2 norm; retain top `$n$` channels where `$n = D_{\text{out}} \times (1 - \text{sparsity\_ratio})$`.
      - For QK: per-channel product of query and key norms; retain top `$n$` channels.
   c. A binary mask `$m \in \{0, 1\}^{D_{\text{out}}}$` is constructed: `$m_j = 1$` if channel `$j$` is retained, `$0$` otherwise.
   d. The main branch computes sparsely: `$y_{\text{sparse}} = x[:, \text{active}] \cdot W[\text{active}, :]$` where `active` indexes the columns of `$x$` and rows of `$W$` corresponding to retained channels. The inactive channels contribute zero.
   e. The LoRA branch computes densely: `$y_{\text{LoRA}} = x A B$` (where `$A \in \mathbb{R}^{D_{\text{in}} \times r}$`, `$B \in \mathbb{R}^{r \times D_{\text{out}}}$`, `$r = 32$`).
   f. The layer output is `$y = y_{\text{sparse}} + y_{\text{LoRA}}$`.

**2. Context-output splitting:**

For the final output of the last transformer layer (before the language modeling head):
   - Context token positions: keep the sparse result `$y_{\text{sparse}} + y_{\text{LoRA}}$` as computed.
   - Output token positions: re-run the layers densely for these tokens only, producing `$y_{\text{dense}} + y_{\text{LoRA}}$`. Replace the sparse results with these dense results. (In practice, this re-computation may be fused: during the initial forward pass, the system knows which positions are output tokens and skips sparsity for those.)

**3. Loss computation:**

The language modeling head produces logits from the assembled hidden states. Cross-entropy loss is computed only on output token positions.

**4. Backward pass:**

Gradients flow backward through the computation graph:
   - For LoRA parameters (`$A$`, `$B$`): gradients are computed normally, since the LoRA branch was always dense. These are the only parameters that receive updates.
   - For the frozen main branch weights: gradients flow only through the active channels (those where `$m_j = 1$`). Gradients for inactive channels are zero (since those channels contributed zero to the forward pass output, their gradient contributions are also zero by the chain rule).
   - The SVD estimator (`$W_A$`, `$W_B$`) does not receive gradients — it is used only for mask generation, and the mask is treated as a discrete, non-differentiable selection. The straight-through estimator is not needed because the SVD factors are never updated during fine-tuning.
   - For output token positions: the dense re-computation during the forward pass means that the backward pass through those positions uses the dense gradient path, preserving full gradient fidelity where the loss is computed.

**5. Optimizer step:**

The optimizer (AdamW) updates only the LoRA parameters `$A$` and `$B$`. The main branch weights, SVD factors, and sparsity masks remain unchanged.

**Key design property: mask reuse in backward pass.** The paper notes that the sparsity mask is computed once per layer per forward pass and reused during the backward pass. This is crucial for efficiency: if the mask had to be recomputed for the backward pass (e.g., because the gradient of the loss with respect to the layer output requires different channels than the forward pass), the SVD estimator would need to run twice, doubling its (admittedly small) overhead. By reusing the forward-pass mask, the backward pass simply performs the transpose operation (`$g W^T$`) on only the active channels, maintaining the same sparsity pattern. This is valid because the frozen weights are not updated — the importance of each channel for the backward pass is proportional to its importance for the forward pass, since the gradient flows through the same weight values.

**Why this achieves actual wall-clock speedup, not just theoretical FLOPs reduction:** The sparsity is **structural** (channel-level), not unstructured. When the system retains, say, 10% of FFN channels, it literally performs a matrix multiplication with a weight matrix of shape `$(D_{\text{in}} \times 0.1 \cdot D_{\text{out}})$` instead of `$(D_{\text{in}} \times D_{\text{out}})$`. On a GPU, this translates to proportionally fewer multiply-accumulate operations, proportionally less memory bandwidth consumed for weight loading, and (crucially) the operation can be implemented as a dense GEMM call on the sliced weight tensor — there is no overhead from scatter/gather operations, no sparse matrix format decoding, and no irregular memory access patterns. The GPU's tensor cores process the sliced dense matrix at full throughput, and the speedup comes purely from the reduced dimension. This is why SparseLoRA achieves a measured 1.6× wall-clock speedup on Math10K with LLaMA3-8B, not just a theoretical FLOPs reduction, and why the paper emphasizes "structured contextual sparsity" as distinct from unstructured approaches whose "theoretical gains are challenging to realize on consumer-grade GPUs."

#### Compatibility and Generality

**Combination with QLoRA (Table 6):** "SparseQLoRA" applies the SparseLoRA sparsity mechanism on top of a QLoRA base: the frozen pretrained weights are stored in 4-bit NormalFloat format and dequantized on the fly before the sparse matrix multiplication. The LoRA adapters operate in full precision (BF16/FP16) as in standard QLoRA. The SVD estimator operates on the dequantized weights, computing the SVD offline from the full-precision checkpoint before quantization. Results show that SparseQLoRA achieves 1.2× speedup over QLoRA on CSR170K (65% FLOPs) and 1.3× speedup on Math10K (60% FLOPs), while maintaining the memory savings of 4-bit quantization. This demonstrates that sparsity and quantization are complementary — sparsity reduces the number of operations, quantization reduces the memory footprint of the weights, and they can be combined without interference.

**Application to different PEFT methods:** The paper notes that SparseLoRA "can, in principle, be applied to any other PEFT method" beyond LoRA. The core mechanism — sparsifying the main branch while keeping the adapter branches dense — is agnostic to the specific adapter architecture. Whether the adapter is LoRA (low-rank matrices), DoRA (weight-decomposed LoRA), IA3 (learned rescaling vectors), or prefix tuning (learned prefix embeddings), the main branch computation `$y = Wx$` remains the dominant cost and can be sparsified identically. The paper does not empirically validate this claim beyond LoRA and QLoRA, leaving the combination with DoRA's weight decomposition (which adds its own computational overhead) as an open question.

**Application to different projection sets (Table 15):** The paper verifies that SparseLoRA works when LoRA is applied to different subsets of projections:
- **QKVO only** (standard LoRA configuration): LoRA 79.9% vs. SparseLoRA 80.0% on Math10K.
- **QKVUD** (Q, K, V, up, down projections): LoRA 80.3% vs. SparseLoRA 80.9%.
- **QKVOGUD** (all projections including output and gate): LoRA 80.5% vs. SparseLoRA 80.7%.

The accuracy gap is consistently small or slightly favors SparseLoRA, confirming that the sparsity mechanism does not depend on a specific choice of which projections receive LoRA adapters. This is expected because sparsity is applied to the frozen main branch, which exists regardless of which projections have LoRA adapters attached.

**Iso-FLOP comparison (Figure 10, Appendix A.7):** When constrained to the same total FLOPs budget (e.g., 20% of one epoch's FLOPs), SparseLoRA achieves higher accuracy than dense LoRA at every budget level on both Math10K and CSR170K. The gap widens at lower FLOP budgets: at 5% FLOPs on Math10K, SparseLoRA achieves roughly 76% vs. LoRA's ~74%. At 20% on CSR170K, SparseLoRA achieves roughly 85.5% vs. LoRA's ~84.5%. This confirms that the efficiency gains are not simply from running fewer FLOPs — SparseLoRA extracts **more accuracy per FLOP** than dense LoRA, likely because the sparsity acts as an implicit regularizer that prevents overfitting to the small fine-tuning dataset, a phenomenon the paper does not explore in depth but which is consistent with broader findings in sparse training literature.

## 4. Key Insights and Innovations

### Innovation 1: Contextual Sparsity as a Compute-Efficiency Axis for Fine-Tuning, Not Just Inference

The paper's most fundamental intellectual contribution is recognizing that **contextual sparsity — previously treated as an inference-only technique — can be repurposed as a compute-efficiency mechanism for fine-tuning, provided the sparsity selection and allocation strategy is redesigned for the multi-token batch workload.** This is not an incremental extension but a conceptual reframing of what contextual sparsity is *for*.

Before this work, contextual sparsity was firmly situated in the inference literature (Deja Vu, Liu et al., 2023b; ShadowLLM, Akhauri et al., 2024; CATS, Lee et al., 2024). The dominant assumption was that sparsity helps at test time because autoregressive generation is memory-bandwidth-bound — skipping weight reads translates directly to latency reduction — and because single-token processing makes sparsity pattern prediction tractable with small learned models. Fine-tuning, by contrast, was seen as a fundamentally different regime: compute-bound (large matrix multiplications saturate GPU throughput), multi-token (batched sequences mean the union of active neurons across all positions approaches the full set), and gradient-sensitive (approximation errors in the forward pass propagate to noisy gradient signals that destabilize optimization). The implicit consensus was that what works for inference cannot work for training.

This paper demolishes that assumption, but not by naively porting inference methods to fine-tuning. Instead, it demonstrates that the assumption was correct *under the specific design choices of inference-time sparsity methods* — but that a fundamentally different sparsity architecture, designed from scratch for fine-tuning's constraints, can succeed. The key intellectual move is diagnostic: the paper identifies *why* inference methods fail (head-level granularity too coarse for multi-token diversity, learned predictors too dataset-specific and training-intensive, the union-of-active-neurons problem across batch elements), and then proposes a system where each failure mode is addressed by a structural change (channel-level granularity, training-free SVD estimation, batch-aware aggregation of importance scores across all tokens).

The significance of this reframing extends beyond the specific method. It establishes that **compute efficiency during adaptation is a tractable target**, not an inherent tradeoff where memory efficiency must come at the cost of runtime. This opens a new axis in the PEFT design space: until now, the field implicitly accepted that LoRA's computational cost was the baseline and that improvements could only come from reducing trainable parameters further (which, as Figure 1 shows, can actually *increase* runtime due to decomposition overhead). SparseLoRA demonstrates that the frozen main branch — the 95%+ of computation that PEFT methods leave untouched — is the right target for optimization, and that input-dependent sparsity is a viable mechanism for pruning that computation without sacrificing accuracy.

The evidence for the conceptual leap, rather than the implementation, comes from the breadth of the evaluation: commonsense reasoning (Table 1), arithmetic reasoning (Table 2), code generation (Table 5), instruction following (Table 4), and sequence classification (Table 3) across three model scales (7B, 8B, 13B) and two model families (LLaMA2, LLaMA3). The consistency of the speedup-accuracy tradeoff across these diverse settings confirms that the underlying phenomenon — contextual redundancy in frozen weights during fine-tuning — is robust, not a quirk of a specific dataset or model.

### Innovation 2: The SVD Estimator as a Training-Free Oracle Approximation — Eliminating the Predictor Bottleneck

The second distinctive contribution is the **replacement of learned sparsity predictors with an offline SVD-based estimator**, a design choice that is simple to describe but whose implications are far-reaching: it eliminates the need for dataset-specific training, removes a source of generalization error, and reduces the sparsity selection overhead to near-zero.

In the inference-time sparsity literature, the dominant paradigm — established by Deja Vu (Liu et al., 2023b) and followed by ShadowLLM (Akhauri et al., 2024) and others — is to train a small neural network (typically a 2–3 layer MLP) to map input activations to a binary sparsity mask. This predictor is trained on a representative dataset by running the full model, recording oracle sparsity patterns (e.g., which neurons would have fired under a threshold), and using these as supervised targets. This approach has two structural weaknesses that become acute in the fine-tuning setting:

1. **Dataset dependence**: The predictor learns sparsity patterns specific to the training data distribution. When the fine-tuning dataset differs from the predictor's training data (as it almost always will — fine-tuning datasets are task-specific while predictor training is typically done on general corpora), the predicted masks may select suboptimal channels, degrading accuracy. The paper does not belabor this point, but it is implicit in the choice to avoid learned predictors entirely.

2. **Training overhead**: Training a predictor for every layer in a large model (e.g., 32 layers × multiple linear projections per layer in LLaMA2-7B) requires substantial computation and hyperparameter tuning. This overhead must be amortized over many fine-tuning runs to be worthwhile, which limits applicability for researchers running diverse, one-off experiments.

The SVD estimator sidesteps both problems by exploiting a property that is unique to the fine-tuning setting: **the pretrained weights are frozen and known in advance.** During inference, this property also holds, but the memory-bandwidth-bound nature of inference makes even small low-rank projections expensive (as the paper notes, "low-rank module overheads can be significant in inference-time sparsity methods"). During fine-tuning's compute-bound regime, a rank-8 SVD projection adds negligible cost — and because it depends only on the weights (which are fixed), it generalizes across all datasets and tasks without any training.

This is a conceptual advance in **sparsity mechanism design**, not just an engineering convenience. It reframes the sparsity selection problem from "predict which neurons will be active" (a learning problem requiring data) to "approximate the output well enough to rank channel importance" (a linear algebra problem solvable offline). The SVD of a weight matrix directly captures the directions of maximal variance in the linear transformation — the singular vectors corresponding to large singular values represent the input-output mappings that dominate the layer's computation. By projecting through these dominant directions, the estimator preserves the *relative* importance ordering of channels (which is what matters for top-k selection) while discarding the *absolute* accuracy of the output values (which doesn't matter for mask generation).

The evidence for this innovation's distinctiveness comes from Table 7: the SVD estimator matches oracle accuracy within 0.3 percentage points on Math10K (81.1% vs. 81.4%) while adding only 0.05% FLOPs and 0.8% runtime overhead, with a 30 MB memory footprint. The tiny gap between SVD and oracle confirms that a rank-8 approximation of the weight matrix is sufficient to capture channel importance ordering — a finding that is not obvious a priori and that the paper establishes empirically. The comparison to learned predictors is implicit but clear: a training-free method that achieves near-oracle accuracy eliminates an entire category of complexity (predictor architecture design, training data collection, hyperparameter tuning, generalization concerns) from the sparsity pipeline.

### Innovation 3: Multi-Dimensional Sensitivity Analysis as a Systematic Framework for Sparsity Allocation

The paper's third distinctive contribution is less a single technique than a **diagnostic methodology**: the systematic decomposition of sensitivity across layers, tokens, and training steps, with each dimension revealing a different failure mode of naive sparsity and motivating a specific, targeted intervention. This transforms sparsity allocation from a heuristic (e.g., "apply 50% sparsity everywhere") into a structured optimization problem with empirically grounded allocation rules.

What makes this an intellectual contribution rather than just careful engineering is that each sensitivity dimension reveals a **non-obvious property of the fine-tuning dynamics** that would be missed by aggregate measurements:

**Layer sensitivity (Figure 7)** reveals that deeper layers are dramatically more resilient to sparsity than shallow layers — a finding that echoes inference-time observations (Gromov et al., 2024) but is independently validated in the fine-tuning context where gradient flow through pruned layers could theoretically amplify errors. The non-uniform allocation derived from this analysis (Table 12) shows that extreme sparsity ratios (90–99% for FFN layers) are viable when concentrated in the deeper half of the model, while shallow layers must remain dense. Table 9 provides the ablation: at the same FLOPs budget of 46%, non-uniform allocation achieves 81.1% accuracy at 1.6× speedup vs. 80.2% at 1.5× for uniform — the non-uniform version is both faster and more accurate because it concentrates the sparsity budget where it does the least harm.

**Token sensitivity (Table 8)** reveals the failure mode of applying sparsity uniformly across all tokens: on Math10K, where output tokens constitute a large fraction of the sequence, sparsifying all tokens causes accuracy to collapse from ~81% to 47.1%. The paper's insight is that this is not a general sensitivity to sparsity but a **specific sensitivity of output tokens** — the positions where the loss is computed and from which gradients originate. Keeping output tokens dense while sparsifying context tokens recovers full accuracy (81.1%). This finding has a theoretical implication: the gradient signal quality depends disproportionately on the fidelity of the forward pass at loss-computation positions, and approximation errors at context positions matter primarily through their second-order effects on attention patterns and hidden state propagation. The structural distinction between context and output tokens (which always exists in supervised fine-tuning, unlike in autoregressive inference where every token is both context and output for subsequent steps) enables a simple rule that would not apply in pretraining or inference contexts.

**Step sensitivity** (configured but not ablated in detail) captures the finding that early optimization steps are more sensitive to gradient noise than later steps — a phenomenon known in sparse training literature (Lu et al., 2023; Thangarasa et al., 2023) but adapted here to the PEFT setting where only adapter parameters are updated. The progressive schedule (dense warmup for the first 5–10% of steps, then switch to sparse) is a lightweight intervention that costs little in overall speedup (since the dense portion is small) but prevents the LoRA parameters from converging to a suboptimal basin during their most dramatic initial movement.

The intellectual contribution is the **framework itself**: the recognition that sparsity sensitivity is not a monolithic property of "the model" or "the dataset" but a multi-dimensional phenomenon that must be analyzed along each axis independently to identify which dimensions dominate and which interventions are needed. This framework is portable — future sparsity methods for fine-tuning (or for other training phases) can apply the same layer-token-step decomposition to identify their own sensitivity patterns, even if the specific configurations differ. The paper does not claim that its specific settings (e.g., 90% FFN sparsity for layers 13–29 of LLaMA2-7B) are universal; rather, it provides the methodology for deriving such settings for any model and task.

### Innovation 4: Structured Channel-Level Sparsity as the Enabling Granularity for Practical Speedup

A less flashy but operationally crucial contribution is the **identification and validation of channel-level structured sparsity as the correct granularity for achieving both accuracy preservation and wall-clock speedup on GPU hardware.** This insight bridges the gap between theoretical FLOPs reduction (which unstructured sparsity can achieve on paper) and measured runtime improvement (which unstructured sparsity consistently fails to deliver on consumer GPUs).

The paper's Table 10 explicitly compares pruning granularities: for QK projections, channel-level pruning using the attention norm criterion achieves 80.7% accuracy at 90% sparsity, while head-level pruning achieves only 79.6%. The 1.1 percentage point gap may seem modest, but at 90% sparsity, the channel-level approach preserves 10× more pruning granularity (hundreds of channels per head vs. 32 heads total), allowing the selection criterion to retain the most important computation while discarding the rest. For FFN layers, the granularity difference is even starker: 11,008 channels in LLaMA2-7B vs. no head-level analog. The paper's Appendix A.1 (Figure 9) provides the mechanistic explanation: attention head behavior varies across tokens within a sequence, making head-level pruning a blunt instrument that inevitably removes heads that are critical for some tokens.

The significance of this choice extends beyond accuracy. Channel-level sparsity is **natively supported by GPU tensor cores** through standard dense GEMM operations on sliced tensors. When SparseLoRA retains 10% of FFN channels, it literally calls a dense matrix multiplication on a weight matrix of shape `(D_in × 0.1 · D_out)`, which executes at full tensor core throughput. Unstructured sparsity (pruning individual scalar weights scattered throughout the matrix) requires either sparse matrix formats (CSR, COO) with irregular memory access patterns that underperform on GPUs, or masking operations that compute the full product and then zero out results — providing no speedup at all. The paper explicitly calls this out in Section 2: prior sparse training work (Thangarasa et al., 2023; Mozaffari et al., 2024) has "theoretical gains [that] are challenging to realize on consumer-grade GPUs."

The intellectual contribution is establishing that **the tension between sparsity granularity (finer is better for accuracy) and hardware efficiency (coarser is better for speedup) can be resolved at the channel level for transformer architectures.** Channel-level sparsity is the "sweet spot": fine enough to preserve model quality (as Table 10 shows, it outperforms head-level pruning) but coarse enough that the resulting sliced matrices are still large, contiguous, and amenable to dense GEMM. This finding is not specific to SparseLoRA — it is a design principle that applies to any structured sparsity method for transformer training or inference — but the paper provides the first systematic validation of this granularity choice in the fine-tuning context with measured wall-clock speedups, not just theoretical FLOPs counts.

The evidence is the speedup numbers themselves: 1.6× on Math10K with LLaMA3-8B (Table 2), 1.5× on instruction following (Table 4), 1.3× on commonsense reasoning across multiple model sizes (Table 1). These are measured wall-clock improvements on an NVIDIA A6000 GPU, not simulated or projected. They validate that channel-level structured sparsity translates theoretical compute reduction into practical runtime savings — a claim that unstructured sparsity methods in prior training work could not make.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper evaluates on five downstream task groups spanning diverse fine-tuning scenarios. **Commonsense reasoning (CSR170K)** combines eight datasets: BoolQ, PIQA, SIQA, HellaSwag, WinoGrande, ARC-Easy, ARC-Challenge, and OpenbookQA, with models fine-tuned on the combined training sets following Hu et al. (2023). **Arithmetic reasoning (Math10K)** combines GSM8K, MAWPS, and SVAMP, excluding AQuA because "none of the methods in Hu et al. (2023) achieve better-than-random performance." **GLUE benchmark** evaluates sequence classification on nine tasks (COLA, STS-B, MRPC, RTE, SST2, QNLI, WNLI, MNLI, QQP) following Wang et al. (2018). **Instruction following** uses WizardLM (Xu et al., 2024) for training and MT-Bench (Zheng et al., 2023) for evaluation across eight categories (Coding, Extraction, Humanities, Math, Reasoning, Roleplay, STEM, Writing), with GPT-4 scoring response quality. **Code generation** trains on CodeFeedback (Chen et al., 2021) and tests on HumanEval and HumanEval+ (Zheng et al., 2024b; Liu et al., 2023a), measuring pass@1. Training hyperparameters are detailed in Table 11, varying by dataset: CSR170K uses sequence length 512, batch size 8, 1 epoch, learning rate 3e-4; Math10K matches CSR170K but uses 3 epochs; GLUE tasks use sequence length 128 with batch size 8, learning rate 5e-5; CodeFeedback uses sequence length 1024, batch size 6, learning rate 2e-5; WizardLM uses sequence length 2048, batch size 2, learning rate 2e-5. All experiments use cosine learning rate scheduling with 0.04 warmup ratio.

- **Base model(s).** The paper experiments with LLaMA2-7B, LLaMA2-13B, LLaMA3-8B, and LLaMA3.1-8B (Instruct). LLaMA2 models represent the prior generation of open-weight LLMs with SiLU activation in FFN layers (which naturally induces activation sparsity — a property SparseLoRA exploits), while LLaMA3 models represent more recent architectures with different activation patterns, testing the method's generality across model families. The range of scales (7B to 13B) tests whether the sparsity patterns and sensitivity profiles are consistent as model depth and width increase. The instruct-tuned LLaMA3.1-8B is specifically used for instruction following and code generation benchmarks where chat-format interactions matter. The base model without fine-tuning is evaluated as a reference point in each results table (e.g., LLaMA2-7B achieves 2.6% average on Math10K without fine-tuning in Table 2).

- **Metrics.** The primary metrics are **accuracy** (for commonsense reasoning, arithmetic reasoning, and GLUE tasks — computed as the fraction of test examples where the selected answer matches the ground truth), **MT-Bench score** (for instruction following — a 1–10 quality rating assigned by GPT-4 evaluating model responses across eight task categories, averaged per category and overall), and **pass@1** (for code generation — the fraction of programming problems for which the model's first generated solution passes all unit tests). Efficiency is measured through **#FLOPs** (computational cost as a percentage of the dense LoRA baseline), **Speedup** (measured wall-clock runtime improvement factor on an NVIDIA A6000 GPU, not theoretical), and **runtime** (forward and backward pass latency in milliseconds, shown in Figure 1). For CSR170K and Math10K, the paper runs each experiment five times, discards the highest and lowest performing runs, and reports the average of the remaining three to reduce variance from random initialization.

- **Baselines.** The paper compares against four baselines: **(1) LoRA** (Hu et al., 2022) — standard low-rank adaptation applied to QKVO projections with rank 32, scaling factor α=64, no dropout, serving as the primary accuracy and speed reference (100% FLOPs, 1.0× speedup); **(2) QLoRA** (Dettmers et al., 2023) — combines 4-bit NormalFloat quantization of the base model with LoRA adapters, included to demonstrate that SparseLoRA's sparsity is complementary to quantization-based memory savings; **(3) DoRA** (Liu et al., 2024b) — weight-decomposed low-rank adaptation that reparameterizes pretrained weights into magnitude and direction components, included specifically because it exemplifies PEFT methods that increase computation (132% FLOPs, 0.7–0.8× speedup vs. LoRA) despite reducing trainable parameters; **(4) GaLore** (Zhao et al., 2024) — gradient low-rank projection that reduces optimizer state memory via periodic online SVD, included in Appendix Table 13 to contrast memory-efficiency approaches that incur severe compute penalties (1.58× LoRA runtime, 13.72× amortized with SVD updates). For code generation and instruction following, only LoRA is compared directly (Tables 4 and 5). The base model without fine-tuning is reported as a zero-shot reference in each table.

- **Generation budget / compute accounting.** The paper uses two complementary measures of computational cost. **FLOPs** (floating-point operations) are measured as a percentage of the dense LoRA baseline — SparseLoRA's FLOPs percentage reflects the fraction of multiply-accumulate operations executed relative to standard LoRA on the same data. **Wall-clock speedup** is measured directly on an NVIDIA A6000 GPU, capturing the end-to-end training time reduction including all overhead (SVD estimator, mask construction, sparse computation, and any dense warmup steps). The distinction matters because theoretical FLOPs reduction does not always translate to runtime improvement on GPUs (as the paper notes for unstructured sparsity). SparseLoRA consistently achieves wall-clock speedup factors that are somewhat smaller than the FLOPs reduction factor (e.g., 46% FLOPs → 1.6× speedup, not 2.17×), reflecting overheads from the SVD estimator, mask generation, and dense computation on output tokens and early training steps. The progressive step offset is accounted for in the overall speedup: a 5% dense warmup on a 1.3× sparse speedup reduces the effective speedup over the full training run to slightly less than 1.3× (the paper reports the net speedup including warmup overhead).

- **Cross-validation / statistical protocol.** For CSR170K and Math10K, each experiment is run five times with different random seeds, the highest and lowest runs are discarded, and the average of the remaining three is reported. This trimmed-mean approach is a simple robustness check against outlier runs but does not constitute formal cross-validation (there is no held-out validation split within the training data — the combined training sets are used in full). For GLUE, instruction following, and code generation, the paper does not specify the number of runs or statistical protocol, implying single-run results. The layer sensitivity analysis (Figure 7) uses a subset of the CSR170K task as a proxy for determining per-layer sparsity configurations, which are then applied to other benchmarks — this is a form of transfer of hyperparameters across tasks, and the paper implicitly validates this transfer by showing strong results on Math10K, GLUE, CodeFeedback, and WizardLM using configurations derived from CSR170K sensitivity curves. There is no explicit held-out validation set for tuning the sparsity configurations (e.g., sparsity ratios per layer, progressive step offset percentage) — these appear to be set through direct experimentation on the test benchmarks, which could introduce overfitting to the specific test sets used. The paper does not report confidence intervals, standard deviations, or statistical significance tests for any results.

### Main Quantitative Results

#### Commonsense Reasoning (CSR170K)

Table 1 presents the core results across LLaMA2-7B, LLaMA2-13B, and LLaMA3-8B on the eight-task CSR170K benchmark. The headline finding: **SparseLoRA achieves 1.3× wall-clock speedup while reducing FLOPs to 61–65% of LoRA, with average accuracy within 0.5 percentage points of the dense baseline across all three model scales.**

On **LLaMA2-7B**, SparseLoRA uses 65% of LoRA's FLOPs and achieves 1.3× speedup while delivering 81.8% average accuracy vs. LoRA's 82.3% (a 0.5 point gap). Compared to QLoRA (82.5% at 100% FLOPs and 0.9× speedup — meaning QLoRA is *slower* than LoRA despite equivalent FLOPs due to dequantization overhead), SparseLoRA is both faster and more memory-efficient when combined with quantization (as shown later in Table 6). Compared to DoRA (81.7% at 132% FLOPs and 0.7× speedup), SparseLoRA is 1.86× faster at equivalent accuracy. The per-task breakdown shows SparseLoRA closely tracks LoRA: on BoolQ (69.7 vs. 70.7), PIQA (84.3 vs. 84.8), SIQA (80.8 vs. 81.4), HellaSwag (88.4 vs. 90.0), WinoGrande (86.0 vs. 85.8), ARC-Easy (86.7 vs. 87.6), ARC-Challenge (73.4 vs. 74.3), and OBQA (84.0 vs. 84.7). The largest gaps are on HellaSwag (1.6 points) and ARC-Easy (0.9 points), while SparseLoRA slightly *outperforms* LoRA on WinoGrande (86.0 vs. 85.8). The base LLaMA2-7B without fine-tuning achieves only 31.4% average, confirming that fine-tuning provides a large absolute improvement that SparseLoRA largely preserves.

On **LLaMA2-13B**, SparseLoRA uses 61% FLOPs and achieves 1.3× speedup, with average accuracy of **85.0% — actually outperforming LoRA's 84.7%** by 0.3 points. This is a rare case where the sparse fine-tuned model exceeds the dense baseline, possibly due to an implicit regularization effect from sparsity that prevents overfitting to the fine-tuning data (the base LLaMA2-13B at 35.0% has substantial room for improvement, and CSR170K's 170K training examples may be small enough that regularization matters). The per-task breakdown shows SparseLoRA leading LoRA on BoolQ (74.1 vs. 72.0, +2.1), PIQA (87.1 vs. 86.7, +0.4), SIQA (82.4 vs. 82.2, +0.2), and HellaSwag (92.3 vs. 91.0, +1.3), while trailing slightly on ARC-Challenge (78.7 vs. 80.5, -1.8) and OBQA (86.9 vs. 85.6, +1.3). The 1.8-point gap on ARC-Challenge is the only task where SparseLoRA meaningfully underperforms at the 13B scale.

On **LLaMA3-8B**, SparseLoRA uses 65% FLOPs at 1.3× speedup with 86.9% average accuracy vs. LoRA's 87.1% (0.2 point gap). QLoRA achieves 87.1% at 0.9× speedup (10% slower than LoRA), and DoRA achieves 87.1% at 0.8× speedup (20% slower). SparseLoRA is thus 1.44× faster than QLoRA and 1.63× faster than DoRA while matching their accuracy. The per-task breakdown shows tight tracking: SparseLoRA is within 0.6 points of LoRA on all tasks except OBQA (82.9 vs. 83.4) and slightly *outperforms* on BoolQ (75.0 vs. 74.6) and PIQA (89.6 vs. 89.4). The base LLaMA3-8B achieves 62.5% without fine-tuning, significantly higher than LLaMA2-7B's 31.4%, reflecting LLaMA3's stronger pretraining.

The key pattern across all three model scales is that **SparseLoRA's accuracy degradation relative to LoRA is smaller on larger models** — LLaMA2-7B loses 0.5 points, LLaMA3-8B loses 0.2 points, and LLaMA2-13B actually gains 0.3 points. This suggests that larger models have more redundancy in their pretrained representations, making them more tolerant of aggressive sparsity during adaptation. The paper does not explicitly discuss this trend, but it is visible in the data and consistent with the layer sensitivity finding (Figure 7) that deeper layers (which are proportionally more numerous in larger models) are more amenable to sparsification.

#### Arithmetic Reasoning (Math10K)

Table 2 presents results on the more challenging Math10K benchmark, where output tokens constitute a larger fraction of the sequence (step-by-step math solutions) and the task requires precise multi-step reasoning. The headline: **SparseLoRA achieves up to 1.6× speedup with 46% FLOPs on LLaMA3-8B while matching dense accuracy (81.1% for both SparseLoRA and LoRA/DoRA).**

On **LLaMA2-7B**, SparseLoRA uses 73% FLOPs at 1.2× speedup, achieving 53.7% average vs. LoRA's 54.6% (0.9 point gap). QLoRA achieves 55.0% at 0.9× speedup (again slower than LoRA), and DoRA achieves 54.5% at 0.7× speedup. The per-task breakdown shows SparseLoRA closely tracking on GSM8K (37.6 vs. 38.6) and MAWPS (77.9 vs. 77.5 — actually slightly higher), with the main gap on SVAMP (46.4 vs. 47.5). The base LLaMA2-7B achieves only 2.6% on Math10K, making the absolute improvement from fine-tuning large (~51 points) and SparseLoRA's preservation of nearly all of it impressive.

On **LLaMA2-13B**, SparseLoRA uses 70% FLOPs at 1.3× speedup, achieving 62.7% vs. LoRA's 63.5% (0.8 point gap). On GSM8K, SparseLoRA achieves 49.5% vs. 50.2%; on SVAMP, 57.1% vs. 59.1%; on MAWPS, 81.5% vs. 81.0% — actually slightly *outperforming* LoRA on this sub-task.

On **LLaMA3-8B**, the paper achieves its most aggressive speedup: **46% FLOPs and 1.6× speedup** (the largest runtime improvement across all experiments). SparseLoRA achieves 81.1% average accuracy, matching both LoRA (81.0%) and DoRA (81.0%), while being 1.6× faster than LoRA and 2.0× faster than DoRA (which uses 132% FLOPs at 0.8× speedup). QLoRA achieves 80.6% at 0.9× speedup. On GSM8K, SparseLoRA achieves 72.0% vs. LoRA's 71.8% and DoRA's 72.5%; on SVAMP, 80.2% vs. 80.3% for LoRA; on MAWPS, 90.9% vs. 90.9% for LoRA. SparseLoRA matches or exceeds the dense baselines on every sub-task while cutting computation by more than half.

The sparsity configuration for this 1.6× result (Table 12) is notably aggressive: FFN layers 3–30 are sparsified at **99%** (retaining only 1% of channels), QKVO layers 14–19, 21–23, and 25–29 at 75% sparsity, with **0% progressive step offset** — training is sparse from the very first step, with no dense warmup. The fact that accuracy is fully preserved under these extreme conditions suggests that on Math10K, the frozen LLaMA3-8B weights contain massive redundancy, and the LoRA adapters can compensate for the approximation errors introduced by sparsity. This is the most compelling single result for SparseLoRA's practical value: a measured 1.6× speedup with zero accuracy loss on a challenging multi-step reasoning benchmark.

#### Sequence Classification (GLUE)

Table 3 presents results on nine GLUE tasks using LLaMA3-8B. SparseLoRA achieves **1.3× speedup at 61% FLOPs**, with average GLUE score of 87.7 vs. LoRA's 87.3 — **actually outperforming** the dense baseline by 0.4 points. The per-task breakdown shows SparseLoRA matching or exceeding LoRA on every single task: COLA (66.3 vs. 65.8), STS-B (89.3 vs. 88.8), MRPC (88.6 vs. 87.7), RTE (82.9 vs. 82.8), SST2 (96.6 vs. 96.4), QNLI (96.6 vs. 95.7, a notable +0.9 gain), WNLI (55.9 vs. 45.5, a large +10.4 gain), MNLI (91.8 vs. 91.8, tie), and QQP (89.8 vs. 89.8, tie). The large WNLI improvement is likely an artifact of WNLI's tiny test set (making the score noisy) combined with regularization from sparsity, rather than a genuine capability gain. Excluding WNLI, SparseLoRA's advantage is modest (~0.3 points) but consistent, suggesting that sparsity during fine-tuning serves as a mild regularizer that slightly improves generalization for these natural language understanding tasks.

This experiment is notable because GLUE represents a different fine-tuning paradigm from the generative tasks: it requires sequence-level classification (a single label per input) rather than token-level generation. SparseLoRA's strong performance here confirms that the method does not depend on any property specific to autoregressive language modeling — the sparsity mechanism operates purely at the level of linear layer computation, which is identical whether the final output is used for classification or generation.

#### Instruction Following (MT-Bench)

Table 4 evaluates SparseLoRA on the challenging instruction-following benchmark using LLaMA3.1-8B fine-tuned on WizardLM. SparseLoRA achieves **1.5× speedup at 53% FLOPs**, with an average MT-Bench score of 6.06 vs. LoRA's 6.03 — a marginal 0.03-point improvement. The base LLaMA3.1-8B (without fine-tuning) scores 4.08, so fine-tuning provides a large absolute gain (~1.95 points) that SparseLoRA fully preserves.

The per-category breakdown shows SparseLoRA matching or exceeding LoRA across all eight evaluation categories: Coding (5.30 vs. 5.10, +0.20), Extraction (5.45 vs. 5.50, -0.05), Humanities (8.10 vs. 8.00, +0.10), Math (2.20 vs. 2.25, -0.05), Reasoning (5.35 vs. 5.30, +0.05), Roleplay (7.35 vs. 7.35, tie), STEM (7.70 vs. 7.78, -0.08), and Writing (7.05 vs. 7.00, +0.05). All deviations are within ±0.20, which is well within the noise of GPT-4-based evaluation (inter-rater reliability for LLM judges is typically ±0.3–0.5 points). The Math category scores are notably low for both methods (2.20–2.25 out of 10), suggesting that the WizardLM fine-tuning data does not substantially improve math instruction-following — but within this low-performance regime, sparsity does not degrade the already-weak signal. The Coding category shows the largest SparseLoRA advantage (+0.20), but this is likely statistical noise rather than a genuine benefit.

This result is significant because instruction following is a more demanding fine-tuning scenario than the classification and reasoning benchmarks: WizardLM involves diverse, open-ended instructions with long responses (sequence length 2048, batch size 2), and MT-Bench evaluation requires holistic quality assessment across multiple dimensions. The fact that SparseLoRA achieves 1.5× speedup with no measurable quality degradation in this setting strengthens the case for its generality.

#### Code Generation (HumanEval)

Table 5 evaluates code generation performance on HumanEval and HumanEval+ using LLaMA2-7B and LLaMA3.1-8B fine-tuned on CodeFeedback. On **LLaMA2-7B**, SparseLoRA uses 73% FLOPs at 1.2× speedup, achieving pass@1 of 12.8% on HumanEval vs. LoRA's 13.0% (0.2 point gap), and 11.0% on HumanEval+ vs. LoRA's 10.2% (+0.8 point gain). On **LLaMA3.1-8B**, SparseLoRA achieves **1.3× speedup at 66% FLOPs**, with pass@1 of 43.9% vs. LoRA's 43.1% on HumanEval (+0.8 points) and 37.0% vs. 36.2% on HumanEval+ (+0.8 points). In both cases, SparseLoRA slightly *outperforms* the dense baseline on both benchmarks — a surprising result that may reflect sparsity acting as a regularizer, preventing the model from overfitting to superficial patterns in the CodeFeedback training data that do not generalize to the distinct programming problems in HumanEval.

The base models without fine-tuning score much lower: LLaMA2-7B at 3.6%/3.0% (HumanEval/HumanEval+), LLaMA3.1-8B at 30.9%/27.9%. The fine-tuning improvement is large for LLaMA3.1-8B (~13 points on HumanEval) and moderate for LLaMA2-7B (~9 points), and SparseLoRA preserves all of this improvement while providing measurable speedup.

The CodeFeedback → HumanEval transfer represents a different generalization challenge than CSR170K or Math10K where train and test come from similar distributions. CodeFeedback consists of diverse programming instructions and solutions, while HumanEval tests on specific function-writing problems not seen during fine-tuning. SparseLoRA maintaining (and slightly exceeding) LoRA's generalization performance suggests that the sparsity is not causing the LoRA adapters to overfit to training-data-specific features at the expense of general coding capability.

#### Compatibility with Memory-Efficient Methods (SparseQLoRA)

Table 6 demonstrates that SparseLoRA can be **combined with QLoRA's 4-bit quantization**, achieving both memory savings and runtime acceleration. On LLaMA3-8B with CSR170K, SparseQLoRA uses 65% FLOPs at 1.2× speedup with 86.9% accuracy vs. QLoRA's 87.1% at 1.0× speedup. On Math10K, SparseQLoRA uses 60% FLOPs at 1.3× speedup with 80.8% accuracy vs. QLoRA's 80.6% at 1.0× speedup. The speedup factors (1.2×, 1.3×) are slightly lower than SparseLoRA with full-precision base weights (1.3×, 1.6×) because the dequantization step adds overhead that partially offsets the sparse computation savings. However, the combination is still profitable: for practitioners using QLoRA to fit models on memory-constrained GPUs, adding SparseLoRA provides a "free" 20–30% speedup with negligible accuracy loss, making the already memory-efficient fine-tuning also compute-efficient.

#### GaLore vs. SparseLoRA (Appendix A.4)

Table 13 in the appendix provides a direct comparison with GaLore (Zhao et al., 2024) on LLaMA3-8B. On CSR170K, GaLore achieves 84.1% accuracy at 1.58× LoRA runtime (with 13.72× amortized cost including periodic online SVD updates), while SparseLoRA achieves 87.0% accuracy at 0.78× LoRA runtime. On Math10K, GaLore achieves 78.7% at 1.58× runtime vs. SparseLoRA's 80.0% at 0.82× runtime. SparseLoRA is approximately **2× faster than GaLore** on both benchmarks while achieving 2–3 points higher accuracy. The amortized cost of GaLore (13.72× when including periodic SVD recomputation) is extreme — the online SVD that enables gradient compression dominates the training time, making GaLore impractical for any setting where training speed matters. This comparison highlights SparseLoRA's architectural advantage: by keeping the SVD offline and training-free, the estimator cost is negligible, whereas GaLore's online SVD (necessary for adapting the low-rank gradient subspace during training) consumes the majority of the runtime budget.

#### Iso-FLOP Comparison (Appendix A.7)

Figure 10 compares SparseLoRA and LoRA under equal FLOPs budgets, sweeping from 5% to 100% of one full epoch's compute on LLaMA3-8B with Math10K and CSR170K. On Math10K, SparseLoRA consistently achieves higher accuracy than LoRA at every budget: at 5% FLOPs, SparseLoRA reaches ~76% vs. LoRA's ~74%; at 20% FLOPs, SparseLoRA reaches ~79% vs. LoRA's ~78%; at 100% FLOPs, SparseLoRA reaches ~80.0% vs. LoRA's ~80.0% (converging at full budget). On CSR170K, the pattern is similar: at 5% FLOPs, SparseLoRA reaches ~82% vs. LoRA's ~81%; at 20%, ~85.5% vs. ~84.5%; at 100%, ~87.1% vs. ~87.1%. The gap is largest at intermediate budgets (~20–40% FLOPs), where SparseLoRA extracts roughly 0.5–1.5 additional accuracy points from the same compute. This is consistent with the interpretation that sparsity acts as an implicit regularizer: with limited data or limited optimization steps, the reduced effective capacity of the sparse forward pass prevents overfitting, allowing SparseLoRA to generalize better than dense LoRA at low compute budgets. At full compute (100% FLOPs), both methods converge to similar accuracy, suggesting that the regularization benefit diminishes when optimization is run to completion.

### Ablation Studies and Robustness Checks

- **SVD estimator quality vs. oracle (Table 7):** On Math10K with LLaMA3-8B, the SVD estimator (rank 8) achieves 81.1% accuracy using only 0.05% additional FLOPs, 0.8% runtime overhead, and 30 MB memory, compared to the oracle criterion's 81.4% — a gap of just 0.3 percentage points. This confirms that a rank-8 low-rank approximation of the pretrained weights preserves channel importance ordering sufficiently well for near-oracle sparsity mask selection. The 0.8% runtime overhead is notably small, validating the paper's claim that the SVD projections are negligible in the compute-bound fine-tuning regime (in contrast to inference, where such overheads would be significant due to memory-bandwidth binding). The 30 MB memory footprint is also minimal — roughly 0.2% of LLaMA3-8B's ~15 GB weight size.

- **Output token splitting effectiveness (Table 8):** Three configurations are compared on LLaMA3-8B: sparsifying all tokens uniformly, randomly selecting a subset of tokens to keep dense (matching the number of output tokens), and the proposed context-output splitting (keeping output tokens dense, sparsifying context). On CSR170K (where output tokens are a small fraction), all configurations perform similarly (86.6–86.9% accuracy) because output tokens constitute too few positions for errors on them to significantly impact the overall loss. On Math10K (where output tokens are a larger fraction), the differences are stark: all-tokens-sparse drops to 47.1%, random-dense recovers only to 70.9%, while output-token-dense achieves 81.1%. The random-dense baseline is important because it controls for the possibility that any additional dense computation (regardless of which tokens) provides the benefit — the 10.2-point gap between random-dense (70.9%) and output-dense (81.1%) confirms that the structural distinction between context and output positions is the causal factor, not merely the increased computation budget.

- **Uniform vs. non-uniform layer sparsity (Table 9):** Across multiple FLOPs budgets on LLaMA3-8B with Math10K, the non-uniform (sensitivity-aware) allocation consistently outperforms uniform sparsity at the same compute level. At 60% FLOPs: uniform achieves 80.3% at 1.1× speedup, non-uniform achieves 81.1% at 1.4× speedup — the non-uniform configuration is both faster (due to concentrating sparsity on layers where it can be applied more aggressively without accuracy loss) and more accurate. At 46% FLOPs (the most aggressive setting): uniform achieves 80.2% at 1.5× speedup, non-uniform achieves 81.1% at 1.6× speedup — the 0.9-point accuracy gap and 0.1× speedup advantage both favor non-uniform. At 37% FLOPs (beyond the paper's main reported configurations): uniform achieves 79.5% at 1.6× speedup, non-uniform achieves 80.5% at 1.8× speedup, with the accuracy gap widening to 1.0 point. This ablation validates the layer sensitivity analysis in Figure 7: the performance difference between uniform and non-uniform allocation grows with sparsity ratio, confirming that the sensitivity differences across layers become more consequential under more aggressive budgets.

- **Pruning criterion comparison (Table 10):** For QK projections under 90% uniform sparsity with token splitting and 5% step offset, the paper compares four criteria on Math10K. The proposed **attention norm (channel-wise)** achieves 80.7%, outperforming head-level attention norm (79.6%), channel-wise L2 norm (79.8%), and random pruning (79.1%). The 1.1-point gap between channel-level attention norm and head-level attention norm validates the granularity argument: pruning individual channels rather than entire heads preserves attention patterns more accurately. For VO projections, L2 norm achieves 81.4% vs. random at 79.6% — the 1.8-point gap confirms that L2 norm captures genuine importance rather than being equivalent to random selection. For FFN projections, L2 norm (81.4%) slightly edges out Wanda (81.3%) and substantially outperforms random (78.6%) — the 2.8-point gap between structured selection and random confirms the oracle metric's validity. The near-tie between L2 norm (activation-based) and Wanda (weight-based) for FFN suggests that activation and weight magnitudes are correlated in these layers, making either criterion viable, but L2 norm is preferred for simplicity and computational efficiency (no need to access or normalize weight magnitudes).

- **Compatibility with different LoRA projection sets (Table 15):** SparseLoRA is tested with LoRA applied to three different sets of projections: QKVO only (the standard configuration), QKVUD (adding up and down projections), and QKVOGUD (all projections including output and gate). On LLaMA3-8B with Math10K, SparseLoRA consistently matches or slightly exceeds LoRA: QKVO (80.0% vs. 79.9%), QKVUD (80.9% vs. 80.3%), QKVOGUD (80.7% vs. 80.5%). The ∆ column shows SparseLoRA gaining +0.1, +0.6, and +0.2 points respectively. This confirms that the sparsity mechanism is independent of which layers receive LoRA adapters — sparsifying the main branch is beneficial regardless of adapter placement, and the accuracy is robust to the specific configuration.

- **Learning rate robustness (Table 14):** A sweep of learning rates from 3e-5 to 9.5e-4 on LLaMA3-8B shows that the optimal learning rate is similar for LoRA and SparseLoRA, and the performance gap between best configurations is small. On Math10K, the best LoRA achieves 80.2% (at 5e-4) while the best SparseLoRA achieves 80.0% (at 3e-4) — a 0.2-point gap at slightly different optimal learning rates. On CSR170K, the best LoRA achieves 87.7% (at 9.5e-5) vs. best SparseLoRA at 87.4% (also at 9.5e-5) — a 0.3-point gap. This ablation rules out the concern that SparseLoRA's results might benefit from a different optimal learning rate than the LoRA baseline; the learning rate sensitivity is comparable between methods.

- **GaLore comparison (Table 13):** While not a SparseLoRA ablation per se, this comparison with a competing memory-efficient method demonstrates SparseLoRA's compute-efficiency advantage. GaLore's 1.58× runtime (13.72× amortized) vs. SparseLoRA's 0.78× runtime on CSR170K represents a 2× wall-clock advantage for SparseLoRA with 2.9 points higher accuracy (87.0% vs. 84.1%). On Math10K, SparseLoRA is 1.93× faster with 1.3 points higher accuracy (80.0% vs. 78.7%). This confirms that SparseLoRA occupies a distinct point in the design space: it accelerates training, whereas GaLore slows it down in exchange for memory savings.

- **Attention head patterns during fine-tuning vs. inference (Figure 9, Appendix A.1):** The appendix provides the mechanistic evidence for why head-level pruning fails in fine-tuning. Three attention heads (7, 9, 21) are visualized for the last 9 tokens of a sequence. Head 7 shows varying attention patterns across tokens: it acts as a uniform "token mixing" head for some tokens but a focused "heavy hitter" for others. Head 9 similarly varies between uniform and focused patterns depending on token position. Head 21 maintains a more consistent pattern. During inference (single-token generation, equivalent to the last row of the attention map), these heads could be classified and pruned based on their behavior on that single token. During fine-tuning (processing all tokens in parallel), the same head serves different roles for different tokens, making classification-based pruning unreliable. This qualitative evidence supports the quantitative finding in Table 10 (channel-level 80.7% vs. head-level 79.6%).

### Critical Assessment

#### Claim 1: SparseLoRA "reduces computational cost by up to 2.2× and a measured speedup of up to 1.6×"

**This claim is supported with precisely quantified conditions.** The 2.2× FLOPs reduction corresponds to the 46% FLOPs figure in Table 2 (LLaMA3-8B on Math10K), which implies a 1/0.46 ≈ 2.17× reduction — the paper rounds to 2.2×. The 1.6× wall-clock speedup corresponds to the same configuration. The distinction between FLOPs reduction and wall-clock speedup is appropriately maintained throughout the paper: at the most aggressive configuration (37% FLOPs in Table 9), the "speedup" is 1.8×, not the theoretical 2.7×, indicating overheads are honestly reported.

**However, the FLOPs accounting deserves scrutiny.** The paper reports FLOPs as a percentage of the dense LoRA baseline, but does not specify whether the SVD estimator's FLOPs (0.05% per Table 7), the dense output-token computation, and the progressive warmup steps are amortized into these percentages. If the 46% figure represents only the sparse forward/backward FLOPs during the sparse phase, the true amortized FLOPs would be higher. Given that the warmup is only 0–10% of steps and the SVD estimator adds 0.05%, the amortized overhead is likely small (adding perhaps 1–3 percentage points to the FLOPs percentage), but the paper does not explicitly amortize these costs.

**The speedup numbers are measured on a single GPU model (NVIDIA A6000).** GPU characteristics (tensor core throughput, memory bandwidth, cache hierarchy) vary substantially across hardware generations. The A6000 (Ampere architecture, 48 GB VRAM) is a mid-range professional GPU; speedup factors on consumer GPUs (RTX 4090, Ada Lovelace), datacenter GPUs (A100, H100), or older hardware could differ. Specifically, the compute-bound vs. memory-bandwidth-bound balance shifts with GPU capability — on a more compute-capable GPU, the relative overhead of the SVD estimator might be even smaller, potentially increasing the speedup; on a more memory-bandwidth-constrained GPU, the sparsity might yield less benefit because weight loading (rather than computation) is the bottleneck. The paper does not discuss this hardware dependence.

#### Claim 2: SparseLoRA "maintains accuracy across various downstream tasks"

**This claim is strongly supported with an important caveat about variance and statistical rigor.** Across all benchmark tables, SparseLoRA's accuracy is within 0.5 percentage points of LoRA for most configurations, with several cases where SparseLoRA slightly exceeds the dense baseline (LLaMA2-13B on CSR170K: +0.3; LLaMA3-8B on Math10K: +0.1; GLUE average: +0.4; HumanEval: +0.8). The per-task breakdowns in Tables 1–5 show no systematic pattern of degradation — SparseLoRA sometimes slightly underperforms, sometimes slightly outperforms, with deviations typically within 1 point. For the instruction following and code generation tasks (Tables 4–5), the deviations are even smaller or favor SparseLoRA.

**However, the paper's statistical protocol is minimal.** For CSR170K and Math10K, five runs with trimmed mean reduce the impact of outlier seeds, but confidence intervals are not reported. For GLUE, instruction following, and code generation, it is unclear whether multiple runs were performed at all. The sample sizes for some benchmarks are small: HumanEval has only 164 problems, so a pass@1 difference of 0.8 points (Table 5, LLaMA3.1-8B: 43.9% vs. 43.1%) corresponds to roughly 1 problem — well within sampling noise. The WNLI task in GLUE has an extremely small test set, making the large +10.4 point improvement (55.9% vs. 45.5%) almost certainly noise rather than a genuine effect. The MT-Bench evaluation uses GPT-4 as a judge, which has known inter-rater reliability of ±0.3–0.5 points; the 0.03-point SparseLoRA advantage (6.06 vs. 6.03) is far below this noise floor.

The paper makes no attempt to establish statistical significance (e.g., bootstrap confidence intervals, paired difference tests), meaning the small accuracy fluctuations between SparseLoRA and LoRA cannot be distinguished from random variation. This is acceptable for the paper's core claim ("SparseLoRA maintains accuracy" — meaning it doesn't catastrophically degrade), but weakens any suggestion that SparseLoRA actually *improves* accuracy in some cases. The regularization hypothesis (sparsity preventing overfitting) is plausible and consistent with the iso-FLOP results (Figure 10) and the occasional SparseLoRA > LoRA findings, but is not experimentally isolated or directly tested.

#### Claim 3: The SVD estimator is "lightweight, training-free" and achieves near-oracle accuracy

**This claim is well-supported with direct oracle comparison (Table 7).** The 0.3 percentage point gap (81.1% vs. 81.4%) on Math10K is genuinely small, and the 0.05% FLOPs / 0.8% runtime / 30 MB overhead figures are precise and credible. The rank-8 SVD choice is justified by these results but the paper does not ablate the rank parameter — there is no sweep showing accuracy vs. FLOPs overhead as k varies from, say, 2 to 32. A rank-4 SVD might achieve nearly the same accuracy with even less overhead (0.025% FLOPs?), while a rank-16 SVD might recover the remaining 0.3-point oracle gap at slightly higher cost. Without this ablation, the reader cannot assess whether rank 8 is near-optimal or whether it was chosen ad hoc.

**The "training-free" claim is accurate for the estimator itself but omits the layer sensitivity analysis.** The per-layer sparsity configurations (Table 12) are determined by an offline sensitivity sweep on CSR170K (Figure 7), which requires running multiple sparse fine-tuning experiments at different sparsity ratios. This sensitivity analysis is effectively a hyperparameter optimization that must be performed once per model architecture. While the SVD factors are training-free and reusable across all datasets, the sparsity ratios are dataset- and task-dependent to some degree — the configurations differ between CSR170K, Math10K, GLUE, CodeFeedback, and WizardLM (Table 12). The paper does not test whether a single set of sparsity ratios works well across all tasks, or whether task-specific tuning is required. If practitioners need to repeat the sensitivity analysis for each new fine-tuning task, the "training-free" characterization applies only to the estimator, not to the complete SparseLoRA pipeline.

#### What Would Strengthen the Paper

Several experiments would substantially increase confidence in the claims:

1. **A rank ablation for the SVD estimator**: accuracy and overhead at k ∈ {2, 4, 8, 16, 32} to characterize the accuracy-efficiency Pareto frontier and justify the rank-8 choice.

2. **Cross-task transfer of sparsity configurations**: apply the CSR170K-derived configurations to Math10K without any task-specific tuning, and vice versa, to measure how much the sensitivity profile shifts across tasks. This would determine whether the sensitivity analysis needs to be repeated per domain.

3. **Ablation of the progressive step offset parameter**: accuracy vs. speedup at step offsets of 0%, 2%, 5%, 10%, 20% to characterize the warmup sensitivity. The paper currently uses 0–10% without explaining how these specific values were chosen or measuring their impact.

4. **Evaluation on at least one non-LLaMA model family**: Mistral, Falcon, or Gemma would test whether the SiLU-induced FFN sparsity pattern (which SparseLoRA exploits) generalizes to models with different activation functions (e.g., GELU in Gemma). The paper acknowledges that newer architectures use non-SiLU activations (Section 2) but does not evaluate on any such model.

5. **Confidence intervals or standard deviations**: for at least the main accuracy results in Tables 1–2, to distinguish genuine differences from sampling noise, particularly for the configurations where SparseLoRA allegedly outperforms LoRA.

6. **Hardware diversity**: speedup measurements on at least one additional GPU (e.g., consumer RTX 3090/4090, datacenter A100) to characterize the hardware dependence of the speedup factor.

7. **Direct test of the regularization hypothesis**: compare the generalization gap (train vs. test accuracy) between LoRA and SparseLoRA at different dataset sizes. If sparsity is acting as a regularizer, SparseLoRA should show a smaller generalization gap, particularly on small fine-tuning datasets where overfitting risk is higher.

#### Unsupported or Weakly Supported Sub-claims

**"SparseLoRA can, in principle, be applied to any other PEFT method" (Section 4.2):** The paper validates this only for QLoRA (Table 6) and different LoRA projection sets (Table 15). Application to DoRA — which has its own weight decomposition overhead — is not tested, nor are non-LoRA-based PEFT methods like IA3, prompt tuning, or adapter layers. This claim is aspirational rather than empirically established.

**"The SVD sparsity estimator leads to better generalization across datasets" compared to learned predictors (Section 1):** This claim appears in the introduction but is never experimentally tested — the paper does not implement or compare against a learned predictor baseline. The Deja Vu-style learned predictor is discussed as a conceptual alternative but not implemented, trained, or evaluated. The SVD estimator's generalization advantage over learned predictors is therefore a theoretical claim, not an empirical finding.

**The 2.2× FLOPs reduction "headline number"**: This figure represents the most aggressive configuration (46% FLOPs → 2.17× reduction, rounded to 2.2×) but is only achieved on one benchmark (Math10K with LLaMA3-8B). Across other configurations, the FLOPs reduction ranges from 1.37× (73% FLOPs on LLaMA2-7B Math10K) to 1.89× (53% FLOPs on LLaMA3.1-8B WizardLM). The "up to 2.2×" framing is technically accurate but the modal reduction is closer to 1.5–1.7×. The wall-clock speedup range (1.2× to 1.6×) is narrower than the FLOPs reduction range, reflecting the growing overhead costs at higher sparsity ratios.

## 6. Limitations and Trade-offs

### The SVD Sparsity Estimator Depends on SiLU-Induced Activation Sparsity — Behavior with Other Activation Functions Is Unknown

**The assumption or constraint.** SparseLoRA's effectiveness for FFN layers relies on the natural activation sparsity produced by the SiLU (Sigmoid Linear Unit) activation function in LLaMA-family models. Figure 4 explicitly demonstrates this: the input activations to the FFN down projection follow a Laplace-like distribution with most values concentrated near zero, which is what allows the L2 norm criterion to cleanly separate important from unimportant channels. The paper acknowledges in Section 2 that "newer architectures often employ non-ReLU activations... that create different sparsity patterns, necessitating alternative methods to reintroduce and exploit sparsity." The implication is that models using GELU (Gemma, some BERT variants), SwiGLU variants with different gating, or standard ReLU may not exhibit the same concentration of activation mass in a small subset of channels.

**The consequence.** For models without SiLU or with different sparsity-inducing activation functions, the L2 norm criterion for FFN channel selection may degrade substantially — the activation distributions may be more uniform, making the distinction between "important" and "unimportant" channels much noisier. This would force either lower sparsity ratios (reducing speedup) or acceptance of larger accuracy degradation. The QK norm criterion for attention projections does not depend on activation sparsity, so attention sparsity may remain viable, but FFN layers dominate the runtime (Figure 2: ~55–63% of total), meaning that losing the ability to aggressively sparsify FFNs would eliminate most of the speedup. The paper evaluates only LLaMA2 and LLaMA3, both of which use SiLU-based gated FFNs (SwiGLU in LLaMA2/3 uses SiLU gating), leaving the behavior on other architectures entirely uncharacterized.

**What evidence exists in the paper.** None. Every experiment uses LLaMA-family models with SiLU activations. The paper does not evaluate on Gemma (GELU), Mistral (SiLU, but different architecture), Falcon (GELU), or any non-SiLU model. Figure 4 shows the Laplace-like distribution for LLaMA2-7B specifically, but does not provide analogous visualizations for other activation functions to support any claim of generality. Section 2's discussion of "alternative methods to reintroduce and exploit sparsity" for non-SiLU models is a pointer to prior work (Song et al., 2023; Zhang et al., 2024c) on continued pretraining to induce sparsity, but SparseLoRA does not incorporate any such technique.

**Mitigation status.** Not addressed. The paper's scope is explicitly limited to LLaMA models, and the authors do not claim that SparseLoRA transfers to other architectures without modification. However, the paper also does not discuss this as a limitation — the dependence on activation sparsity is presented as a design motivation rather than a constraint on applicability. Practitioners using non-LLaMA models would need to characterize their activation sparsity patterns from scratch and may need to fall back on weight-based criteria (e.g., Wanda, which achieves 81.3% vs. L2 norm's 81.4% in Table 10 for the oracle FFN setting) if activation-based selection proves insufficient.

### Per-Layer Sparsity Configurations Require Task-Specific Sensitivity Analysis — The "Training-Free" Claim Applies Only to the Estimator

**The assumption or constraint.** The paper's "training-free" characterization (Section 1, Section 3.2) applies specifically to the SVD estimator: the low-rank factors are computed offline from pretrained weights and reused across all fine-tuning runs without gradient updates. However, the complete SparseLoRA pipeline includes a **layer sensitivity analysis** (Figure 7, Section 3.3) to determine per-layer sparsity ratios. This analysis requires running multiple sparse fine-tuning experiments at different sparsity levels and measuring accuracy degradation, which is itself a form of meta-training. Table 12 reveals that the optimal sparsity configurations differ substantially across tasks: LLaMA3-8B uses 99% FFN sparsity on layers 3–30 for Math10K (with QKVO sparsity at 75% on selected layers) but only 97% FFN sparsity on layers 17–30 for CSR170K, with QKVO sparsity at 20% on different layer subsets. The configuration for CodeFeedback includes FFN sparsity on layers 3–30 at 99% but QKVO sparsity at only 25–40%. These differences imply task-dependent sensitivity profiles that cannot be predicted from model weights alone.

**The consequence.** A practitioner adopting SparseLoRA for a new fine-tuning task must either: (a) use the sensitivity profile from the paper (derived from CSR170K for LLaMA2-7B and reused for other tasks with modifications) and hope it transfers, (b) conduct their own sensitivity analysis on their specific task, which requires running dozens of sparse fine-tuning experiments to generate curves like Figure 7, or (c) conservatively use lower sparsity ratios to ensure accuracy preservation, sacrificing speedup. Option (a) is what the paper implicitly does — CSR170K-derived sensitivity information guides the configurations for Math10K, GLUE, CodeFeedback, and WizardLM — but the paper provides no evidence that a single sensitivity profile works well across all tasks. Option (b) negates much of the practical speedup advantage, since the sensitivity analysis itself consumes significant compute. Option (c) means the headline speedup numbers (1.6× on Math10K) may not be achievable without task-specific tuning.

**What evidence exists in the paper.** The evidence is indirect but clear: Table 12 shows different sparsity configurations for different tasks on the same model. For LLaMA3-8B, Math10K uses 99% FFN sparsity on layers 3–30 with 0% step offset, while CSR170K uses 97% on layers 17–30 with 5% step offset — the differences in which layers are sparsified and at what ratio are substantial. The paper does not provide an ablation showing what happens if the Math10K configuration is used on CSR170K or vice versa. The layer sensitivity analysis itself (Figure 7) is only performed on CSR170K for LLaMA2-7B; sensitivity profiles for LLaMA3-8B and for other tasks are not shown, making it unclear how the configurations in Table 12 were derived. The progressive step offset parameter (0% to 10%) also varies across configurations without an ablation study characterizing its impact.

**Mitigation status.** Not addressed directly. The paper presents the sensitivity analysis as a one-time cost per model architecture ("we conduct a systematic layer sensitivity analysis using a subset of the Commonsense Reasoning task... as a proxy"), implying that the resulting sensitivity profile transfers across tasks. But the configuration table (Table 12) undermines this claim by showing significant variation across tasks for the same model. The paper does not discuss this tension or provide guidance on how practitioners should set sparsity ratios for new tasks without conducting their own sensitivity sweep.

### The FLOPs Reduction and Speedup Numbers Do Not Amortize the One-Time Costs

**The assumption or constraint.** The headline speedup figures (1.2× to 1.6×) and FLOPs reduction percentages (46% to 73% of LoRA FLOPs) measure the cost of a single fine-tuning run *after* all one-time setup has been completed. This setup includes: (1) computing the SVD decomposition of every linear layer's weight matrix offline, (2) conducting the layer sensitivity analysis to determine per-layer sparsity ratios (Figure 7), (3) potentially tuning the progressive step offset percentage, and (4) for the SVD estimator, loading the rank-8 factors (30 MB) alongside the model weights. For a practitioner running a single fine-tuning experiment, these one-time costs may be small relative to the training time saved. For a practitioner running a hyperparameter sweep across 20 learning rates and 5 rank configurations (100 fine-tuning runs), the one-time costs are trivially amortized. But for the practitioner running a single fine-tuning experiment and comparing SparseLoRA to standard LoRA, the total end-to-end time including setup must be considered. The paper does not report the time required for offline SVD computation (which scales with model size and involves `torch.linalg.svd` on matrices of shape 4096 × 11008 for LLaMA2-7B FFN layers) or for the sensitivity analysis (which involves multiple sparse fine-tuning runs).

**The consequence.** For one-off fine-tuning tasks — which are common in research settings where a practitioner fine-tunes a model on a specific dataset once and evaluates — the setup overhead could consume a non-trivial fraction of the training time savings. If the SVD computation takes, say, 30 minutes for a 7B model and the layer sensitivity analysis takes several hours of GPU time, and the fine-tuning itself takes 4 hours with LoRA vs. 2.5 hours with SparseLoRA (1.6× speedup), the total time including setup might be 4 hours (LoRA) vs. 2.5 + 0.5 + X hours (SparseLoRA), where X is the sensitivity analysis cost. If X is comparable to the training time itself, SparseLoRA may not provide a net time savings for single-run scenarios. The paper implicitly assumes that the fixed costs are amortized over many fine-tuning runs (which is reasonable for the authors' use case of evaluating across many benchmarks and model scales) but does not discuss this assumption or characterize the magnitude of the fixed costs.

**What evidence exists in the paper.** The only setup cost quantified is the runtime overhead of the SVD estimator during training (0.8%, Table 7) and its memory overhead (30 MB). The offline SVD computation time, the layer sensitivity analysis time, and any hyperparameter tuning time for sparsity configurations are not reported. The paper does not provide an end-to-end time accounting that includes all setup costs. The SVD estimator's simplicity (rank 8, computed once per layer) suggests the offline computation is fast — `torch.linalg.svd` on a 4096 × 11008 matrix with `full_matrices=False` is computationally manageable — but without measured numbers, practitioners cannot estimate the breakeven point for their use case.

**Mitigation status.** Not addressed. The paper frames all costs in terms of per-training-step or per-fine-tuning-run metrics, consistent with standard practice in the efficient training literature. However, given that SparseLoRA introduces a new category of one-time preprocessing (offline SVD, sensitivity analysis) that standard LoRA does not require, reporting these costs — even as a rough order of magnitude — would substantially aid practitioners in adoption decisions. The paper does not flag this as a limitation or suggest future work on reducing setup costs.

### Generalization Beyond the MATH/Commonsense/Code/Instruction Domains Is Untested

**The assumption or constraint.** The paper evaluates SparseLoRA on five task families: commonsense reasoning (CSR170K), arithmetic reasoning (Math10K), natural language understanding (GLUE), instruction following (MT-Bench), and code generation (HumanEval). All of these are text-based tasks where the model either selects from discrete options (multiple choice), generates short answers evaluated by exact match or unit tests, or produces text evaluated by an LLM judge (MT-Bench). The paper does not evaluate on tasks requiring factual knowledge recall (e.g., closed-book QA like TriviaQA or Natural Questions), long-form generation (e.g., summarization, story generation), structured prediction (e.g., named entity recognition, relation extraction), or multilingual tasks. The paper also does not evaluate on multi-modal fine-tuning, retrieval-augmented generation, or tasks where the fine-tuning data distribution differs dramatically from the pretraining distribution (e.g., fine-tuning on a highly specialized domain like medical or legal text).

**The consequence.** Two distinct failure modes are plausible in untested domains. First, **knowledge-intensive tasks**: SparseLoRA sparsifies the frozen pretrained weights (and, for FFN layers, the channels where factual knowledge is stored — prior work suggests FFN layers in transformer LMs act as key-value memories for factual associations). If SparseLoRA prunes channels that encode critical factual knowledge needed for the downstream task, the LoRA adapters (which have limited capacity at rank 32) may not be able to compensate. The paper's tasks (commonsense reasoning, math, code) primarily require reasoning over information provided in the context, rather than recalling facts stored in the pretrained weights, which may explain SparseLoRA's success. Second, **distribution-shifted domains**: the layer sensitivity profile derived from CSR170K (Figure 7) may not reflect sensitivity patterns for a domain that activates different sets of pretrained knowledge. The paper's own configuration table (Table 12) shows that optimal sparsity ratios vary across tasks, reinforcing the concern that extreme domain shifts could require entirely different sensitivity profiles.

**What evidence exists in the paper.** The evaluation is broad within its chosen domains (five task families, three model scales, two model generations) but explicitly limited to these families. No experiment tests SparseLoRA on knowledge-intensive QA, long-form generation, or domain-specific fine-tuning. The base-model zero-shot accuracies in Tables 1–5 provide some insight: for Math10K, the base LLaMA2-7B achieves only 2.6% accuracy, meaning fine-tuning teaches the model to reason in ways it almost never does in pretraining — yet SparseLoRA succeeds. This suggests that SparseLoRA does not simply preserve existing capabilities but allows new capabilities to be learned through the LoRA adapters even on heavily sparsified main branches. However, for tasks where the pretrained knowledge *itself* (rather than the reasoning pattern) is the primary determinant of success, the sparsification of knowledge-bearing FFN channels could be more damaging.

**Mitigation status.** Not addressed as a limitation. The paper claims that SparseLoRA "maintains accuracy across a wide range of benchmarks" (Section 5) but does not discuss the scope of these benchmarks relative to the full space of fine-tuning applications. The consistent success across five diverse task families is genuinely encouraging, but practitioners in specialized domains should verify SparseLoRA's effectiveness on their specific task before adopting, since the paper provides no evidence about domain-transfer properties.

### The Method Is Validated on a Single Consumer-Grade GPU — Speedup Transferability to Other Hardware Is Uncharacterized

**The assumption or constraint.** All speedup measurements in the paper are reported on an NVIDIA A6000 GPU (Ampere architecture, 48 GB VRAM, 309.7 GB/s memory bandwidth, 38.7 TFLOPS FP16 with sparsity). The A6000 is a professional visualization GPU that sits between consumer cards (RTX 3090/4090) and datacenter cards (A100/H100) in terms of compute throughput and memory bandwidth. SparseLoRA's speedup comes from reducing the FLOPs of dense matrix multiplications — a compute-bound operation — but the degree to which FLOPs reduction translates to wall-clock speedup depends on the memory-bandwidth-to-compute ratio of the specific GPU. On a GPU with higher compute throughput relative to memory bandwidth (e.g., H100 at 989 TFLOPS FP16), the compute savings may yield larger speedups because computation is even more of a bottleneck. On a GPU with lower compute throughput (e.g., older generation cards), the speedup may be smaller because weight loading (memory bandwidth) dominates. Additionally, the paper's implementation of sparse computation (slicing weight matrices and calling dense GEMM on the slices) may have GPU-specific performance characteristics depending on tensor core utilization, cache behavior, and the efficiency of the deep learning framework's handling of dynamically sliced tensors.

**The consequence.** The headline "up to 1.6× speedup" cannot be assumed to transfer directly to other hardware. On a datacenter A100 (80 GB, 2.0 TB/s memory bandwidth, 312 TFLOPS FP16), the speedup might be larger (e.g., 1.8× or 2.0×) because the A100's higher compute-to-bandwidth ratio makes it even more compute-bound, amplifying the benefit of FLOPs reduction. On a consumer RTX 3090 (24 GB, 936 GB/s memory bandwidth, 35.6 TFLOPS FP16), which has a similar compute-to-bandwidth ratio to the A6000, the speedup might be similar. On a budget card like the RTX 3060 (12 GB, 360 GB/s memory bandwidth, 12.7 TFLOPS FP16), the speedup might be smaller because the smaller batch sizes required to fit in 12 GB may make the workload less compute-bound. For practitioners using cloud GPU instances (where GPU type may vary by availability zone) or shared clusters with heterogeneous hardware, the speedup factor may not be consistent across runs. This is not a flaw in the method but a practical consideration for deployment planning.

**What evidence exists in the paper.** Only A6000 measurements are reported. The paper does not provide FLOPs-count-paired speedup measurements on any other GPU. The FLOPs percentages (46% to 73% of LoRA) provide a hardware-independent measure of computational savings, and the paper appropriately reports both FLOPs and speedup, allowing practitioners to estimate speedup on their own hardware based on the FLOPs reduction. However, the paper does not characterize the relationship between FLOPs reduction and speedup (e.g., why 46% FLOPs yields 1.6× speedup rather than 2.17×, what the overhead components are, and how they scale with GPU capability). The Table 9 comparison of uniform vs. non-uniform sparsity shows that the same FLOPs budget (60%) yields different speedups (1.1× vs. 1.4×) depending on the sparsity allocation — which further complicates hardware-independent speedup estimation, since speedup depends not just on total FLOPs but on which layers are sparsified and how the computation is distributed.

**Mitigation status.** Not addressed. The paper does not discuss hardware dependence, does not provide speedup measurements on other GPUs, and does not provide a FLOPs-to-speedup breakdown that would help practitioners estimate expected speedups on their hardware. The reporting of both FLOPs and speedup is a partial mitigation (practitioners can use FLOPs as a hardware-independent metric for comparison), but the gap between theoretical FLOPs reduction and measured speedup (sometimes substantial, as seen in the 37% FLOPs → 1.8× speedup configuration in Table 9) makes this translation non-trivial.

### The Context-Output Token Splitting Assumes a Clean Structural Distinction — Pretraining and Prompt Tuning Scenarios Are Excluded

**The assumption or constraint.** SparseLoRA's token-level sparsity strategy (Section 3.3, "Token Sensitivity") relies on the supervised fine-tuning paradigm where training examples have a clear, known split between context tokens (the input prompt) and output tokens (the target response). The system sparsifies context tokens while keeping output tokens dense because output tokens are where the loss is computed and gradient signal quality matters most. This structural distinction exists in instruction fine-tuning, sequence classification (where "output" is the [CLS] token or equivalent), and any supervised learning setup. It does **not** exist in unsupervised pretraining (where every token is both context and output for subsequent tokens), in prompt tuning where the "output" is implicitly the next-token prediction over the entire sequence, or in reinforcement learning from human feedback (RLHF) where the loss may be computed at arbitrary positions based on a reward model. The paper evaluates only supervised fine-tuning tasks, consistent with its stated scope (Section 1: "Fine-tuning LLMs is both computationally and memory-intensive"), but the limitation of the token-splitting strategy to supervised settings is never discussed.

**The consequence.** SparseLoRA cannot be directly applied to continued pretraining, unsupervised domain adaptation, or any scenario where the context-output split is ambiguous or where loss is computed across all tokens. In these settings, the token-splitting strategy would either need to be disabled (sparsifying all tokens, which Table 8 shows causes catastrophic accuracy degradation on output-heavy tasks) or replaced with a different sensitivity mechanism. The paper's observation that output tokens are disproportionately sensitive to sparsity is an empirical finding about supervised fine-tuning dynamics, not a universal property of transformer training. In pretraining, where the loss is computed at every position, all tokens are "output tokens" for some future prediction, making them all sensitive — and the union of active channels across all positions would likely approach the full set, eliminating the sparsity opportunity.

**What evidence exists in the paper.** Table 8 provides direct evidence of the limitation: the "All tokens" configuration (sparsifying everything uniformly) achieves only 47.1% on Math10K (vs. 81.1% with output splitting), confirming that uniform sparsity across all tokens is not viable for tasks with substantial output token fractions. This result is shown only for the supervised fine-tuning setting; the paper does not evaluate any unsupervised or pretraining scenario. The method description (Section 3.3, Figure 8) explicitly ties the splitting strategy to the context-output distinction in supervised fine-tuning data, but does not discuss what would happen in its absence.

**Mitigation status.** Not addressed as a limitation. The paper's title and introduction frame the work as targeting "LLM fine-tuning," which in current usage primarily refers to supervised fine-tuning (instruction tuning, task-specific adaptation). However, the distinction between fine-tuning and continued pretraining is increasingly blurred — many practitioners perform continued pretraining on domain-specific corpora before supervised fine-tuning, or use unsupervised objectives for domain adaptation. SparseLoRA's inapplicability to these scenarios is a genuine scope constraint that the paper does not acknowledge. The authors do not suggest future work on extending the token sensitivity strategy to unsupervised settings (e.g., by estimating token importance via gradient norms or loss magnitudes rather than structural position).
