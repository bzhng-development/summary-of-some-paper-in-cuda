# MEGABYTE: Predicting Million-byte Sequences with Multiscale Transformers

**ArXiv:** [2305.07185](https://arxiv.org/abs/2305.07185)

## 🎯 Pitch

Standard transformers buckle on sequences over a few thousand tokens, but MEGABYTE removes tokenization entirely and models raw bytes in million-length sequences by pairing a large global model with a tiny local model. The result is a 1.5B-parameter architecture that trains cheaper, generates 40% faster than a 350M transformer, and matches state-of-the-art subword perplexity—all while handling text, images, and audio with the same byte-level approach.

---

## 1. Executive Summary

This paper introduces **MEGABYTE**, a multiscale decoder architecture that enables end-to-end differentiable modeling of sequences exceeding one million bytes by segmenting sequences into fixed-size patches and using a large global transformer to model patch-level dependencies while a smaller local transformer autoregressively predicts individual bytes within each patch. The architecture is evaluated across diverse modalities—language modeling (PG-19, Books, Stories, arXiv, Code), high-resolution image modeling on ImageNet at resolutions up to 640×640 pixels (1.2M+ token sequences), and raw 16-bit audio modeling—with all comparisons controlled for identical compute and data budgets. MEGABYTE achieves sub-quadratic self-attention complexity, enables much larger feedforward layers for equivalent FLOPs (a patch size $P$ allows $P\times$ larger feedforward networks at the same cost since they operate per-patch rather than per-byte), and reduces serial decoding operations during generation—yielding a 40% generation speedup over a standard 350M-parameter Transformer while using a 1.5B-parameter model that achieves lower perplexity. The architecture allows byte-level language models to perform competitively with subword models (achieving 36.4 word-level test perplexity on PG-19 versus 28.9–33.6 for state-of-the-art subword models) and matches the state-of-the-art density estimation on ImageNet 64×64 (3.40 bpb versus Perceiver AR's 3.40 bpb while using half the GPU hours), establishing that tokenization-free autoregressive sequence modeling at scale is viable across text, image, and audio domains when model capacity is allocated hierarchically across timescales.

## 2. Context and Motivation

### The Core Problem: Autoregressive Transformers Scale Poorly to Long Sequences

The central challenge this paper addresses is deceptively simple: **standard autoregressive transformer decoders are prohibitively expensive for modeling sequences longer than a few thousand tokens**. Despite the spectacular success of transformer-based language models on short-text tasks (Brown et al., 2020; Zhang et al., 2022a), they fail catastrophically as sequence length grows. This is not a minor scalability issue — it fundamentally restricts *which* types of data can be modeled end-to-end. The paper argues that sequences of millions of bytes are ubiquitous in the real world: high-resolution images, podcasts, code repositories, and full-length books all routinely exceed megabytes in size. Yet the state-of-the-art practice at the time of publication constrains models to context windows of only a few thousand tokens.

This gap is particularly acute because it forces practitioners into a series of unsatisfactory workarounds. Tokenization — the process of compressing multiple bytes into a single discrete token — is the most common such workaround. Subword tokenizers like BPE (Sennrich et al., 2015) and SentencePiece (Kudo & Richardson, 2018) can losslessly compress text by roughly 4×, reducing sequence length enough for short-to-medium documents. But the paper highlights that tokenization introduces its own set of problems: it complicates preprocessing pipelines, creates domain-transfer issues (a tokenizer trained on English text works poorly on code or other languages), and can interact unpredictably with prompting and truncated sampling — for example, whether a prompt should end in whitespace depends on details of the particular subword algorithm used (Section 1). For non-text modalities like images and audio, the situation is worse: lossless tokenization is mathematically impossible because of the high-frequency information density in these signals. Instead, practitioners resort to lossy compression via clustering (e.g., HuBERT; Hsu et al., 2021) or discrete autoencoders (e.g., VQ-VAE; Ramesh et al., 2021), which necessarily discard information and likely limit generative model quality. A truly general-purpose sequence model, the paper argues, should operate directly on raw bytes — but doing so requires handling sequences orders of magnitude longer than current transformers can manage.

### Why Byte-Level Long-Sequence Modeling Matters

The paper's motivation rests on several concrete benefits that would follow from practical byte-level modeling at scale:

**Eliminating tokenization as a design bottleneck.** Tokenization is a preprocessing step that sits *outside* the end-to-end learning paradigm. It requires language-specific heuristics (Radford et al., 2019), limits out-of-domain generalization (Sharami et al., 2023), and effectively hides structural regularities from the model — a byte-level model could, in principle, learn the same compression patterns that BPE discovers, but adapt them continuously during training rather than freezing them in a fixed vocabulary. Removing tokenization would make models truly end-to-end, simplifying deployment across languages and modalities.

**Unified multimodal modeling.** If a single architecture can handle byte sequences of arbitrary length, the same model could ingest text, images, audio, and any other data representable as bytes — without modality-specific preprocessing pipelines. This is a necessary condition for future foundation models that learn from heterogeneous data without human-designed modality boundaries.

**Capturing long-range dependencies.** Real-world data — books with plot structures spanning chapters, images with global coherence at high resolution, audio with multi-second temporal structure — contain dependencies that exceed even the largest practical context windows of contemporary models. A model that can attend to an entire book or a full-resolution image in a single forward pass could learn these structures in ways that chunked or truncated approaches inherently cannot.

**Breaking the wall-clock bottleneck on generation.** Transformer decoders generate tokens one at a time, with each step requiring a full pass through every layer of the network. For long outputs, this serial dependency dominates latency regardless of how much parallelism is available in hardware. Any architectural change that reduces the number of serial operations per output byte directly improves generation speed for real applications.

### Two Cost Sources: Self-Attention AND Feedforward Layers

Most prior work on long-sequence transformers focuses overwhelmingly on mitigating the $\mathcal{O}(T^2)$ cost of self-attention. The paper points out a key oversight that motivates its design: **in large transformer decoders, the feedforward layers are actually the dominant cost, not self-attention**. Section 3 explicitly notes that in a GPT3-style architecture, quadratic self-attention accounts for only 1.4% of total FLOPs — the remaining 98%+ is spent in position-wise feedforward networks.

This observation is critical because it changes the optimization target. Reducing attention cost alone (via sparse attention, linear attention, or recurrence) addresses a minor fraction of total compute. A genuinely efficient architecture must also reduce the per-position cost of feedforward layers. The paper's insight is that these two problems can be tackled jointly through **patchification**: if the model operates on patches of bytes rather than individual bytes for most of its computation, both the attention sequence length *and* the number of feedforward applications are reduced proportionally. For a patch size $P$, the global model sees a sequence of length $T/P$ rather than $T$, and its feedforward layers — which might otherwise be applied at every one of $T$ positions — are applied only at each of $T/P$ patches. This enables the model to be $P$ times larger in parameter count for the same computational budget (Section 2.4).

The paper draws an analogy to Vision Transformers (Dosovitskiy et al., 2020), which patchify images for encoder architectures. But the challenge is fundamentally different for decoder-only models: in an encoder, you can simply embed all patches independently without worrying about information leakage, because there is no autoregressive constraint. In a decoder, the model predicts one byte at a time, and must not see future bytes. Naively predicting an entire patch at once would require modeling a distribution over $256^P$ possibilities — tractable only for trivial $P$. This is the core design challenge MEGABYTE solves: how to get the efficiency benefits of patchification while preserving autoregressive byte-level prediction.

### Where Existing Approaches Fall Short

The paper identifies several families of prior work and explains their specific limitations, positioning MEGABYTE as filling a gap none of them adequately address.

**Efficient encoder models cannot be straightforwardly adapted.** Patchifying operations have been successfully applied in encoder architectures — ViT (Dosovitskiy et al., 2020) for images, CANINE (Clark et al., 2022) for text using downsampling — and Perceiver (Jaegle et al., 2021) uses cross-attention into a shorter latent sequence to compress inputs. However, these techniques cannot be naively applied to decoder-only models. If you patchify a sequence and predict patches autoregressively, you must model the joint distribution over all bytes in the next patch simultaneously — a $256^P$-way classification problem that is computationally intractable for any useful patch size. If instead you factor the predictions as conditionally independent (predicting each byte in the patch independently given the patch context), you lose the ability to model dependencies *within* the patch, which means the model cannot express distributions like "50% cat and 50% dog" without putting probability mass on invalid strings like "cag" or "dot" (Section 2.4). MEGABYTE resolves this by using an autoregressive local model within each patch, so intra-patch dependencies are properly modeled.

**Efficient decoder approaches focus on attention, missing the feedforward bottleneck.** The paper surveys three categories of prior efficient decoder work (Section 9):

1. **Chunking with recurrence or cross-attention**: Transformer-XL (Dai et al., 2019) and Block-Recurrent Transformers (Hutchins et al., 2022) segment sequences into blocks and propagate information across blocks using recurrence. Perceiver AR (Hawthorne et al., 2022) — the strongest general-purpose autoregressive model the paper identifies — uses cross-attention from a shorter latent sequence into a longer context. These methods effectively extend context, but they still apply large feedforward layers at every position within each block, so the feedforward cost remains proportional to sequence length.

2. **Linear attention and state-space models**: Linear Transformers (Katharopoulos et al., 2020), Performers (Choromanski et al., 2020), and state-space models like S4 (Gu et al., 2021) and MEGA (Ma et al., 2022) reduce attention to linear or near-linear complexity through kernel approximations or structured recurrences. However, the paper notes that "we are not aware of competitive results on large scale language modeling tasks" for these approaches (Section 3.1), and they still compute per-position feedforward layers at every timestep.

3. **Sparse attention**: Reformer (Kitaev et al., 2020), Longformer (Beltagy et al., 2020), Sparse Transformers (Child et al., 2019), and Routing Transformers (Roy et al., 2020) achieve sub-quadratic attention through various sparsity patterns (local windows, strided attention, learned routing). These have demonstrated strong results — Sparse Transformers achieve $\mathcal{O}(T^{3/2})$ complexity — but again leave the feedforward cost untouched.

The paper's key architectural insight is that **all** of these approaches miss the dominant cost source. Even if attention were made free, a large transformer with a $d$-dimensional feedforward layer applied at each of $T$ positions would still require approximately $2mT$ FLOPs (where $m$ is the number of non-embedding parameters, following Kaplan et al., 2020). MEGABYTE attacks both costs simultaneously: attention complexity drops because the global model operates on a sequence of length $T/P$, and feedforward cost drops because those layers are applied per-patch rather than per-byte.

**Perceiver AR is the strongest prior baseline, but has fundamental limitations.** The paper pays particular attention to Perceiver AR (Hawthorne et al., 2022), which it describes as "the best performing general purpose autoregressive model we are aware of" (Section 4.2) and which "achieves state-of-the-art results across several modalities." Perceiver AR extends a standard transformer with a single cross-attention layer that attends over a much longer context, compressing it into a shorter latent sequence on which self-attention operates. The paper reproduces Perceiver AR's results to validate its implementation — achieving 3.53 bpb on downsized ImageNet 64×64 versus the reported 3.54 — demonstrating the comparison is fair.

However, Perceiver AR has several structural drawbacks that MEGABYTE aims to overcome. First, the cross-attention mechanism creates a bottleneck: the latent sequence must compress all information from the long context, and the model must learn what information to preserve. Second, Perceiver AR still applies large feedforward layers on every token of the shorter sequence, so while it improves attention scaling, the feedforward scaling remains proportional to the latent sequence length. Third, the cross-attention mechanism does not reduce the serial operations required during generation in the same way that MEGABYTE's hierarchical architecture does. Fourth, Perceiver AR requires careful tuning of the number of latents and cannot easily handle the million-token sequences that MEGABYTE processes in a single forward pass — in the paper's experiments at higher resolutions (Table 5), Perceiver AR cannot model full sequences and must split images into segments.

**Tokenization compounds the sequence length problem but introduces its own costs.** The paper acknowledges that tokenization is the de facto standard approach to shortening sequence lengths, but it argues this is a fundamentally limiting path. For text, subword tokenizers work well enough that the field has largely converged on them, but they still impose costs: they require language-specific design choices (Radford et al., 2019), they degrade on out-of-domain text (Sharami et al., 2023), and they introduce subtle artifacts — the paper notes that "whether or not a prompt should end in whitespace depends on details of the underlying subword algorithm used" (Section 9). For non-text modalities, the costs are starker: lossy compression via clustering or discrete autoencoders discards information that might be useful for generation. A byte-level model sidesteps all of these issues, but only if it can efficiently handle the resulting long sequences.

The paper also briefly notes Edman et al. (2022), which "downsamples characters using subword information" for machine translation and shows promising results, but characterizes this as a hybrid approach that still relies on subword information rather than operating on pure bytes.

### How This Paper Positions Itself

The paper frames its contribution not as a single technique but as a **architectural paradigm shift**: rather than trying to make the transformer efficient at per-token processing (via sparse attention, linear attention, or recurrence), restructure the model so that most computation happens at a coarser timescale (patches) while a lightweight model handles the fine timescale (bytes within patches). This is explicitly a **multiscale** approach — analogous to how a human reader processes text in chunks (phrases, sentences) rather than letter-by-letter for most comprehension, while still being able to attend to individual characters when needed.

The positioning is ambitious: the paper aims to show that this architectural change enables byte-level models to be **competitive with subword models on language modeling** — something no prior byte-level work had achieved at meaningful scale — while simultaneously matching or exceeding state-of-the-art results on image and audio density estimation, all within a single unified architecture. The consistent use of compute-and-data-controlled experiments across all comparisons is a deliberate methodological choice: by fixing the training budget and varying only the architecture, the paper isolates the effect of the architectural design from the confounding effects of training at different scales.

The paper also positions itself as bridging a gap between efficient encoder and decoder research. It explicitly notes that patchification has been used in encoders (ViT, CANINE) but "such methods cannot be naively applied to decoder-only models without leaking information to future bytes in the same patch" (Section 9). MEGABYTE solves this by offsetting the inputs to the global and local models, so the global model sees only past patches while the local model autoregressively predicts within the current patch — a clean generalization of the patchification idea to the autoregressive setting.

## 3. Technical Approach

### 3.1 Reader Orientation

MEGABYTE is a two-level hierarchical decoder architecture that models long byte sequences by splitting them into fixed-size patches — a large global transformer processes the sequence of patches to capture long-range structure, while a small local transformer autoregressively predicts individual bytes within each patch, conditioned on the global model's output for that patch. The system solves the problem of making byte-level autoregressive modeling computationally tractable for million-byte sequences by shifting the bulk of the model's capacity (feedforward layers, self-attention) to the coarse patch timescale, reducing both the quadratic attention cost and the dominant per-position feedforward cost simultaneously, while the lightweight local model handles the fine-grained byte-level prediction within each patch.

### 3.2 Big-Picture Architecture (Diagram in Words)

The MEGABYTE architecture has five major components arranged in a processing pipeline:

1. **Byte Embedding Layer** — maps each raw byte (a value from 0–255, vocabulary size $V = 256$) to a dense vector of dimension $D_G$ (the global model's hidden dimension), and adds learnable positional encodings.

2. **Patch Embedder** — chunks the sequence of byte embeddings into fixed-size patches of length $P$, producing $K = T/P$ patch representations. Crucially, the patch sequence is padded and shifted to prevent information leakage: the global model's input for position $k$ contains the embeddings for bytes $(k-1) \cdot P$ through $k \cdot P$, meaning the global model at step $k$ sees the *previous* patch, not the current one it is helping to predict.

3. **Global Transformer** — a large decoder-only transformer (dimension $P \cdot D_G$) that operates on the sequence of $K$ patch representations. It performs causal self-attention over patches (each patch can attend to all previous patches but not future ones) and applies large feedforward layers per-patch rather than per-byte. Its output is a sequence of $K$ contextualized patch representations, each of which contains information from all previous patches.

4. **Local Transformer** — a small decoder-only transformer (dimension $D_L$, typically much smaller than $D_G$) that runs independently on each patch. For patch $k$, it receives as input a length-$P$ sequence where each position $p$ is the sum of: (a) a linear projection of the global model's output for that patch at that byte position, and (b) an embedding of the *previous* byte in the sequence (byte $k \cdot P + p - 1$). It then autoregressively predicts the bytes within the patch, one at a time, using causal self-attention within the patch.

5. **Output Projection** — maps the local transformer's output at each byte position through a linear layer shared with the byte embedding matrix (weight tying) to produce a distribution over the 256 possible byte values.

**Information flow:** The raw byte sequence enters → each byte is embedded and position-encoded → bytes are chunked into patches with the appropriate padding/shifting → the global transformer processes the full sequence of patch representations, producing one contextualized representation per patch → for each patch, the global output is reshaped and projected down to the local model's dimension, then summed with local byte embeddings of the previous byte in the sequence → the local transformer runs autoregressively within each patch (all patches can be processed in parallel during training) → the local output at each byte position is softmaxed to produce the next-byte prediction distribution.

- **Third**, the training procedure, hyperparameters, and the compute-controlled experimental methodology, because the paper's claims about efficiency and performance all depend on fair comparisons under identical compute budgets.
- **Fourth**, the architecture variations and extensions (convolutional patch encoder, cross-patch attention, strided inference), explaining what each modification does and why it helps.
- **Fifth**, the generation mechanism and why MEGABYTE achieves faster decoding despite having more parameters, because generation speed is a key practical advantage.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is a **new architecture paper** whose core idea is that modeling long byte sequences can be made computationally tractable by decomposing the problem into two timescales — a coarse patch-level model that handles long-range dependencies and absorbs most of the compute budget, and a fine byte-level model that autoregressively predicts within each patch using a much smaller network — with careful padding and shifting to preserve the autoregressive property.

---

#### Mathematical Specification of the Core Architecture

The MEGABYTE forward pass is defined by six equations (Equations 1–6 in the paper, summarized in Figure 2) that together specify how a raw byte sequence is transformed into next-byte prediction probabilities. We step through each in sequence, since each builds on the previous one.

---

**Equation 1: Byte embedding with positional encoding**

$$h_{\text{embed}, t} = E_{\text{global-embed}}(x_t) + E_{\text{pos}}(t) \quad t \in [0, T)$$

where $x_t \in \{0, 1, \ldots, 255\}$ is the byte at position $t$ in the sequence of length $T$, $E_{\text{global-embed}} \in \mathbb{R}^{V \times D_G}$ is a learned embedding table with vocabulary size $V = 256$ and embedding dimension $D_G$ (the global model's hidden dimension), $E_{\text{pos}} \in \mathbb{R}^{T \times D_G}$ is a learned positional embedding table, and $h_{\text{embed}, t} \in \mathbb{R}^{D_G}$ is the resulting vector representation of byte $t$.

**What it computes:** each raw byte index is looked up in the embedding table to get a $D_G$-dimensional dense vector, and a position-specific learned vector is added to encode where in the sequence this byte occurs. The output is a sequence of $T$ vectors, each of dimension $D_G$.

**Why this form:** using learned byte embeddings rather than raw byte values allows the model to learn meaningful representations of individual bytes (which may function as characters, parts of multi-byte UTF-8 sequences, or raw pixel values depending on the modality). The addition of positional embeddings is standard in transformers since self-attention is permutation-invariant without them. Unlike sinusoidal positional encodings, learned position embeddings give the model flexibility to learn position representations suited to byte-level data.

---

**Equation 2: Patch chunking with causal padding**

$$h_{\text{global-in}}^k = \begin{cases} E_{\text{global-pad}}, & \text{if } k = 0, \\ h_{\text{embed}, ((k-1)\cdot P) : (k\cdot P)}, & k \in [1, K) \end{cases}$$

where $P$ is the patch size (a hyperparameter, typically 8 for text and 12–192 for images), $K = T / P$ is the number of patches (integer division, assuming $T$ is divisible by $P$), $E_{\text{global-pad}} \in \mathbb{R}^{P \times D_G}$ is a learned trainable padding embedding shaped as a full patch of $P$ vectors (each of dimension $D_G$), $h_{\text{embed}, a:b}$ denotes the concatenation of embedding vectors from position $a$ (inclusive) to $b$ (exclusive) producing a tensor of shape $P \times D_G$, and $h_{\text{global-in}} \in \mathbb{R}^{K \times (P \cdot D_G)}$ is the resulting sequence of $K$ patch representations fed to the global model.

**What it computes:** the byte embedding sequence is reshaped from a flat $T \times D_G$ tensor into $K$ patches, each containing the embeddings for $P$ consecutive bytes flattened into a single vector of dimension $P \cdot D_G$. The first patch position ($k = 0$) receives the learned padding patch rather than any actual bytes. For positions $k = 1, 2, \ldots, K-1$, the patch contains bytes $(k-1)P$ through $kP$. The last $P$ bytes of the original sequence (bytes $T-P$ through $T-1$) are not included in the global model's input because their corresponding patch would be at position $k = K$, which exceeds $K-1$.

**Why this form — the critical causal shift:** the alignment between what the global model sees at position $k$ and what the local model predicts is crucial and non-obvious. The global model at position $k$ receives a patch representing bytes $(k-1)P$ through $kP$, but then outputs a contextualized representation that will be used to help predict bytes $kP$ through $(k+1)P$. In other words, the patch the global model processes is *one patch behind* the patch being predicted. The padding patch at $k=0$ provides a dummy input for the first position so the global model can output a representation used to predict the first actual patch (bytes $0$ through $P$). The last actual patch (bytes $T-P$ through $T$) is predicted using the global model's output at position $K-1$, which processes bytes $T-2P$ through $T-P$. This offset is what prevents the global model from having access to bytes in the patch it is helping to predict — it sees only *past* patches, enforcing the autoregressive property. Without this shift, the global model would leak information from within the current patch to the local model's predictions.

An equivalent way to think about this: the global model's input is the original byte sequence padded at the beginning with $P$ dummy bytes and with the last $P$ bytes truncated. The patches are then formed from this shifted sequence without further adjustment.

---

**Equation 3: Global transformer over patches**

$$h_{\text{global-out}, 0:K} = \text{transformer}_{\text{global}}(h_{\text{global-in}, 0:K})$$

where $\text{transformer}_{\text{global}}$ is a decoder-only transformer with causal self-attention masking, $h_{\text{global-in}} \in \mathbb{R}^{K \times (P \cdot D_G)}$ is the input patch sequence, and $h_{\text{global-out}} \in \mathbb{R}^{K \times (P \cdot D_G)}$ is the output sequence of the same shape.

**What it computes:** a standard autoregressive transformer processes the sequence of $K$ patch representations. At each transformer layer, self-attention allows patch $k$ to attend to patches $0$ through $k$ (causal masking prevents attending to $k+1$ and beyond), followed by position-wise feedforward networks applied independently to each patch position. The output at position $k$ is a contextualized representation of the $k$-th patch that incorporates information from all previous patches.

**Why this form:** the architectural choice of using a standard decoder-only transformer (rather than an encoder-decoder or a specialized architecture) is deliberate — it means MEGABYTE inherits the well-studied scaling properties of transformers, and any future improvements to transformer architectures (better activation functions, normalization schemes, etc.) can be directly incorporated. The dimension $P \cdot D_G$ is $P$ times larger than the byte-level embedding dimension because a patch representation must encode information about $P$ bytes simultaneously. This means the global model's hidden dimension grows linearly with patch size, which is computationally feasible because the sequence length simultaneously shrinks by a factor of $P$.

---

**Equation 4: Combining global context with local byte embeddings**

$$h_{\text{local-in}}^{k,p} = w_{\text{GL}} \cdot h_{\text{global-out}}^{k, (p \cdot D_G):((p+1) \cdot D_G)} + \begin{cases} E_{\text{local-pad}}, & \text{if } p = 0 \\ E_{\text{local-embed}}(x_{k \cdot P + p - 1}), & p \in [1, P) \end{cases}$$

where $h_{\text{global-out}}^{k} \in \mathbb{R}^{P \cdot D_G}$ is the global model's output for patch $k$, $h_{\text{global-out}}^{k, a:b}$ extracts a slice of dimension $D_G$ from that output (bytes $a$ through $b$ of the flattened patch representation, where each "byte" occupies $D_G$ dimensions), $w_{\text{GL}} \in \mathbb{R}^{D_G \times D_L}$ is a learned linear projection matrix from the global dimension to the local model dimension $D_L$, $E_{\text{local-pad}} \in \mathbb{R}^{D_L}$ is a learned trainable padding embedding for the first position in each patch, $E_{\text{local-embed}} \in \mathbb{R}^{V \times D_L}$ is a second, separate byte embedding table for the local model (with the same vocabulary $V = 256$ but potentially different dimension $D_L$), $x_{k \cdot P + p - 1}$ is the actual byte value at position $k \cdot P + p - 1$ in the original sequence (the byte immediately before the one being predicted), and $h_{\text{local-in}} \in \mathbb{R}^{K \times P \times D_L}$ is the resulting input tensor for the local model.

**What it computes:** for each patch $k$ and each byte position $p$ within that patch, a local input vector is formed by summing two terms. The first term extracts the portion of the global model's output corresponding to byte position $p$ (dimensions $p \cdot D_G$ through $(p+1) \cdot D_G$ of the $P \cdot D_G$-dimensional patch representation) and projects it down to dimension $D_L$ via the learned matrix $w_{GL}$. The second term embeds the *previous* byte in the overall sequence using the local embedding table. For the first position in each patch ($p = 0$), there is no previous byte within the same patch, so the learned padding embedding $E_{\text{local-pad}}$ is used instead.

**Why this form — two separate embedding tables:** the paper uses separate embedding tables for the global and local models ($E_{\text{global-embed}}$ and $E_{\text{local-embed}}$) because they serve different purposes. The global embedding produces representations that are chunked into patches and processed by a large transformer at patch granularity — it needs to capture information useful for long-range dependencies between patches. The local embedding produces representations used within a small transformer for fine-grained byte prediction — it needs to capture local sequential patterns within a word or subword. These might benefit from different dimensionalities and different learned representations. The projection matrix $w_{GL}$ serves as an interface, translating from the global model's "language" (dimension $D_G$) to the local model's "language" (dimension $D_L$).

The shift in the local model mirrors the shift in the global model: at position $p$ within a patch, the local model receives the embedding of byte at absolute position $kP + p - 1$, which is the byte *before* the one being predicted. Position $p=0$ of patch $k$ receives the embedding of byte $kP - 1$ (the last byte of the previous patch, or the padding embedding for $p=0$ of patch $k=0$). This is exactly the standard autoregressive setup: to predict byte $t$, you see byte $t-1$ (and all previous bytes via the global context).

---

**Equation 5: Local transformer within each patch**

$$h_{\text{local-out}}^{k, 0:P} = \text{transformer}_{\text{local}}(h_{\text{local-in}}^{k, 0:P})$$

where $\text{transformer}_{\text{local}}$ is a smaller decoder-only transformer of dimension $D_L$, $h_{\text{local-in}}^{k} \in \mathbb{R}^{P \times D_L}$ is the input sequence for patch $k$ (length $P$, dimension $D_L$), and $h_{\text{local-out}}^{k} \in \mathbb{R}^{P \times D_L}$ is the output sequence.

**What it computes:** for each patch $k$ independently, a small autoregressive transformer processes the length-$P$ sequence of local input vectors. Causal masking ensures that position $p$ can attend to positions $0$ through $p$ within the same patch. The output at position $p$ is a contextualized representation that combines: (1) the global model's summary of all previous patches (via the term $w_{GL} \cdot h_{\text{global-out}}$), (2) the embedding of the immediately preceding byte, and (3) local self-attention over the current patch's prefix.

**Why this form — parallelism during training:** during training, all $K$ copies of the local model run independently and in parallel on their respective patches. Since each patch's local computation does not depend on other patches' local computations (the inter-patch dependency flows through the global model only), all $K$ local forward passes can be batched into a single tensor operation: reshape the $K \times P \times D_L$ tensor to $(K \cdot P) \times D_L$, but with attention masks that restrict attention to within each patch. This means the local model, despite being run $K$ times, adds only $O(T \cdot D_L^2)$ computation rather than $O(K \cdot P^2 \cdot D_L^2)$. This is equivalent to the standard transformer's per-token computation but with the crucial difference that the local model has a much smaller dimension $D_L$ (typically 1024) compared to what a single-level transformer would require (typically 2048–4096 for a comparable-parameter model), and its feedforward layers are correspondingly smaller.

---

**Equation 6: Next-byte probability distribution**

$$p(x_t | x_{0:t}) = \text{softmax}(E_{\text{local-embed}} \cdot h_{\text{local-out}}^{k, p})_{x_t}$$

where $t = k \cdot P + p$ is the absolute byte position decomposed into patch index $k$ and intra-patch position $p$, $h_{\text{local-out}}^{k, p} \in \mathbb{R}^{D_L}$ is the local model's output vector for that position, the multiplication by $E_{\text{local-embed}} \in \mathbb{R}^{V \times D_L}$ (with the embedding matrix interpreted as a linear transformation) produces a vector of logits of dimension $V = 256$, and the softmax converts these to a probability distribution over the 256 possible byte values.

**What it computes:** the standard way to produce output probabilities from a transformer decoder — the output hidden state is projected to vocabulary-size logits using the same embedding matrix that was used for input (weight tying), and softmax normalizes these to a valid probability distribution. The model is trained with standard cross-entropy loss against the true next byte.

**Why this form — weight tying:** sharing the embedding matrix between input and output (weight tying) reduces the parameter count by $V \cdot D_L$ (which is small since $V=256$) and enforces that byte representations used for conditioning (when a byte is used as input) are consistent with those used for prediction (when a byte is the target). This is standard practice in language modeling.

**Why this form — only 256 output classes:** because the model operates on raw bytes, the output vocabulary is naturally 256 classes (one per possible byte value), regardless of the data modality. This is in stark contrast to subword models where vocabularies are typically 32k–50k tokens, or audio models that need special techniques to handle 16-bit samples. The small output vocabulary is computationally cheap — the final projection and softmax over 256 classes is negligible compared to the transformer layers — and it eliminates the need for any modality-specific output handling.

#### Why a Local Model Is Necessary (the Inadequacy of Simpler Alternatives)

Section 2.4 presents a critical design justification that explains why MEGABYTE cannot simply use the global model alone with conditionally independent byte predictions.

**The naive alternative considered:** if the global model outputs a $P \cdot D_G$-dimensional vector for each patch, one might consider directly predicting all $P$ bytes in the next patch from this single vector. This would mean modeling the joint distribution $p(x_{t+1}, \ldots, x_{t+P} | x_{\leq t})$ as a single $256^P$-way classification problem. For $P=8$, this is a $256^8 = 2^{64}$-way classification, which is computationally intractable — the final softmax layer alone would require $2^{64} \cdot P \cdot D_G$ parameters, exceeding the number of atoms in the observable universe.

**Another naive alternative considered:** one could factor the joint distribution into a product of conditionally independent distributions: $p(x_{t+1} | x_{\leq t}) \cdot p(x_{t+2} | x_{\leq t}) \cdot \ldots \cdot p(x_{t+P} | x_{\leq t})$, where each byte in the patch is predicted independently given only the global context (the previous patches). This is computationally tractable — it's just $P$ independent 256-way classifications — but it severely limits the model's expressive power. The paper gives a concrete example: suppose the true distribution within a patch is "50% probability the patch spells 'cat' and 50% probability it spells 'dog'." A conditionally independent model cannot represent this distribution, because it would have to assign independent probabilities to each byte position. The only way to represent a mixture of 'cat' and 'dog' is to assign some probability to each possible combination of first, second, and third letters — including strings like 'cag', 'cot', 'dat', etc. — which would place probability mass on invalid or unintended strings. The autoregressive local model solves this by conditioning each byte on previous bytes within the same patch, allowing it to represent the conditional distribution $p(x_{t+p} | x_{t}, \ldots, x_{t+p-1}, x_{\leq t})$, which can perfectly represent distributions concentrated on valid strings.

**The MEGABYTE solution:** the local model provides exactly this autoregressive intra-patch conditioning using a small transformer. The global model provides a summary of all previous patches (the long-range context), and the local model uses that summary plus the autoregressive history within the current patch to produce rich, correlated distributions over byte sequences within the patch.

#### Why Larger Feedforward Layers Are Enabled

Section 2.4 and Section 3.1 provide the analysis that explains one of MEGABYTE's most important efficiency properties.

**The standard transformer cost breakdown:** following the FLOP approximation from Kaplan et al. (2020), a forward pass of a transformer with $m$ non-embedding parameters on a sequence of length $T$ uses approximately $2mT$ FLOPs. This cost is linear in both the model size and the sequence length, and it is dominated by the position-wise feedforward networks (which account for $>98\%$ of FLOPs in large models, per Section 3.1).

**Why position-wise means per-token:** in a standard transformer, every layer's feedforward network is applied independently at each of the $T$ sequence positions. If the feedforward network at a given layer has a weight matrix of size $d \times 4d$ (the standard expansion ratio of 4), the cost at that layer is approximately $8T d^2$ FLOPs (for the two linear projections: $d \to 4d$ and $4d \to d$). Crucially, a larger model (larger $d$) pays this cost at every single token position.

**MEGABYTE's per-patch feedforward layers:** the global model applies its feedforward layers at each of the $K = T/P$ patch positions rather than at each of the $T$ byte positions. This means the global model's feedforward cost is proportional to $T/P$, not $T$. Since the global model contains the bulk of the parameters (in the experiments, the global model is typically 3–5× larger than the local model), this is a substantial reduction.

**The parameter amplification effect:** for a fixed compute budget, the paper argues that MEGABYTE can use feedforward layers that are $P$ times larger than a standard transformer's, because the standard transformer applies its feedforward layer $P$ times for every one application in MEGABYTE's global model. If the global model uses $m_g$ parameters and the local model uses $m_l$ parameters (with $m_g \gg m_l$), the total FLOPs are approximately $2T (m_g/P + m_l)$, compared to $2T m$ for a standard transformer. When $m_g \approx m$ (same total parameters) and $m_l$ is small, MEGABYTE uses roughly $2T m / P$ FLOPs — a factor of $P$ reduction. Equivalently, for the same FLOP budget, MEGABYTE can use a global model with roughly $P \times$ more parameters than a standard transformer could have.

**Concrete numbers from the experiments:** Table 2 shows a MEGABYTE with 758M global parameters and 262M local parameters (total ~1B) compared to a 320M transformer — MEGABYTE has roughly 3× more parameters but uses the same compute because its large feedforward layers are applied 8× less frequently ($P=8$).

#### Compute-Controlled Experimental Methodology

Section 4.1 describes the experimental design principle that underlies all comparisons in the paper — a design choice critical to interpreting the results.

**The problem with naive comparisons:** the paper acknowledges that model performance improves with both more parameters and more training data (Kaplan et al., 2020; Hoffmann et al., 2022). If one architecture uses more FLOPs per training step or trains on more data, it may outperform another architecture simply because it received more compute, not because the architecture is better. Standard practice of comparing models at equal parameter count or equal training steps can therefore be misleading.

**The compute-controlled approach:** all comparisons in the paper fix both the total compute budget (wall-clock training time on identical hardware) and the total data budget (number of training bytes seen). To achieve this, the authors "adjust model hyperparameters (mainly, number of layers) within each architecture so that the forward pass time taken per byte is matched, and then train all models for the same number of bytes" (Section 4.1). This means a more efficient architecture can use more layers or wider dimensions for the same per-byte cost, and the comparison measures whether those extra parameters translate to better performance.

**Why adjust layers primarily:** the number of transformer layers directly controls the total FLOPs per forward pass, since each layer contributes roughly equally to the cost. By reducing the number of layers in an inefficient architecture and increasing them in an efficient one, the per-token cost is equalized. Other hyperparameters (hidden dimension, number of heads) are adjusted secondarily.

**Advantage over parameter-matched comparisons:** the paper claims this methodology "focus[es] our comparisons solely on the model architecture rather than training resources" — a stronger claim than parameter-matched or FLOP-matched comparisons, because it accounts for implementation-specific overhead and GPU utilization differences.

**Potential limitation acknowledged:** the approach depends on the specific hardware and software implementation; a different GPU generation or a more optimized implementation of one architecture could shift the compute-matched configuration. This is unavoidable in any empirical comparison, and the paper mitigates it by using the same codebase (Metaseq) for all models.

#### Training Procedure, Hyperparameters, and Implementation Details

Appendix A.1 provides the training configuration used across experiments. These details matter for reproducibility and for understanding the experimental scale.

**Optimizer and scheduling:** all models use the Adam optimizer (Kingma & Ba, 2015) with $\beta_1 = 0.9$, $\beta_2 = 0.98$. The learning rate schedule is a polynomial decay from the initial learning rate to 0, with 500 warmup updates. The initial learning rate varies by experiment (typically $2 \times 10^{-4}$ to $3 \times 10^{-4}$, as detailed in Table 12). Gradient clipping with a maximum norm of 1.0 is applied.

**Regularization:** dropout of 0.1 is applied throughout the network, but specifically "we do not apply any dropout to embeddings." Weight decay of 0.1 is used.

**Weight initialization:** the paper describes using "a variant based on Megatron-LM codebase, which involves using a normal distribution with a mean of zero and a standard deviation of 0.006. We truncate this normal distribution within two standard deviations and observed substantial gain in both training stability and performance." This is a non-standard initialization (typical transformer implementations use Xavier/Glorot initialization or a normal distribution with standard deviation $\sqrt{2/(5d)}$), and the authors explicitly note it improved training.

**Normalization and activation:** all models use pre-normalization (LayerNorm applied before attention and feedforward sublayers, rather than after) and ReLU activation functions (rather than GELU or SwiGLU, which are common in more recent models — this reflects the ~2022–2023 vintage of the work).

**Precision and distributed training:** mixed precision training is used (Micikevicius et al., 2017) to improve training efficiency. Fully sharded model and optimizer states are implemented via FairScale (Baines et al., 2021) to improve memory efficiency. The codebase is Metaseq (Zhang et al., 2022b), built on PyTorch (Paszke et al., 2019).

**Perceiver AR reproduction:** as a validation step, the authors reproduced Perceiver AR's ImageNet 64×64 experiment. "By carefully matching hyperparameters, we achieved a bits per byte (bpb) score of 3.53, compared to the reported 3.54 in the original paper." This gives confidence that the Perceiver AR baseline is well-implemented and that performance differences in other experiments reflect architectural differences rather than implementation quality.

#### Architecture Variations and Extensions

Section 2.3 describes three modifications to the base MEGABYTE architecture that address specific limitations.

**Convolutional Patch Encoder (Section 2.3.1):**

**Problem addressed:** the basic patch embedder chunks byte embeddings directly without any cross-byte processing before chunking. This means a byte's representation depends on its absolute position within a patch — the same byte sequence (e.g., the letters 'c', 'a', 't') might be embedded differently depending on whether it starts at position 0, 1, or 2 within a patch. The model would need to learn representations for each offset, which is data-inefficient.

**Mechanism:** before chunking into patches, the embedded byte sequence passes through a stack of causal convolutional layers with filter sizes 3, 5, and 7. Causal convolutions ensure each position can only see previous positions (maintaining the autoregressive property). After convolution, the resulting contextualized embeddings are chunked into patches as before. The convolutions provide translation invariance — the same byte sequence at different patch offsets will produce similar representations because the convolutional filters are applied identically across the sequence.

**Why causal convolutions:** using standard (non-causal) convolutions would allow a position to incorporate information from future bytes, breaking the autoregressive property. Causal convolutions (padding only on the left) prevent this.

**Implementation note:** the paper reports that this modification provides slight improvements on the Librilight-L audio dataset (3.477 → 3.475 bpb) and ImageNet256 (3.158 → 3.155 bpb), but no improvement on arXiv text (0.6871 unchanged) — see Table 7. The benefit appears modality-dependent.

**Cross-Patch Attention (Section 2.3.2):**

**Problem addressed:** the local model's attention is restricted to within a single patch (length $P$). For a patch size of 8 on text, this means the local model can only attend to at most 7 previous bytes, which may be insufficient for modeling dependencies that span patch boundaries (e.g., a word that straddles two patches). The global model provides long-range information, but it does so at a coarse granularity — it summarizes entire patches into single vectors, which may lose fine-grained byte-level information.

**Mechanism:** in each self-attention layer of the local model, the keys and values from the last $r$ positions of the *previous* patch are concatenated with the current patch's keys and values. This means each position in the current patch can attend to (1) all previous positions within the same patch, and (2) the last $r$ positions of the immediately preceding patch. The paper uses rotary position embeddings (Su et al., 2021) to encode relative positions between elements across patch boundaries.

**Relationship to Transformer-XL:** the paper notes this is "reminiscent of TransformerXL (Dai et al., 2019) but differs by being fully differentiable." In Transformer-XL, representations from previous segments are cached and treated as fixed (no gradient flows through them) during training of the current segment, which breaks the differentiable end-to-end property. In MEGABYTE, the previous patch's representations are produced by the local model running on that patch, and since all patches are processed in parallel during training, gradients can flow from the current patch back through the local model's computation on the previous patch.

**Performance impact:** Table 7 shows that removing cross-patch attention has minimal impact on arXiv text (0.6871 with vs. 0.6781 without, *improving* slightly when removed) and audio (3.477 vs. 3.481), and a small negative impact on ImageNet256 (3.158 vs. 3.259). The architecture is robust to this modification, suggesting the global model already provides sufficient cross-patch information for these tasks at these patch sizes.

**Strided Inference (Section 2.3.3):**

**Problem addressed:** empirically, the paper observes that the per-token loss within each patch increases toward the end of the patch (Figure 5). This makes intuitive sense: early positions in the patch benefit from a global model representation that is relatively "fresh" (computed from the most recent patch), while later positions in the patch rely more heavily on the local model's own autoregressive predictions, with the global context becoming "stale" — it was computed from the patch before the current one and hasn't been updated with information from bytes within the current patch.

**Mechanism:** run the full MEGABYTE model twice on the same sequence, with the inputs offset by $P/2$ positions. In the first pass, patches are formed as usual: patch 0 covers bytes $-P$ through $0$ (with padding), patch 1 covers bytes $0$ through $P$, etc. In the second pass, the entire sequence is shifted by $P/2$ positions before patching: patch 0 covers bytes $-P/2$ through $P/2$, patch 1 covers bytes $P/2$ through $3P/2$, etc. The final predictions are formed by taking the first $P/2$ byte predictions from each patch in both passes and interleaving them. This ensures every predicted byte comes from the first half of some patch, where the global context is freshest.

**Cost:** this doubles the inference cost (two forward passes instead of one), so it represents a compute-for-quality tradeoff analogous to sliding window evaluation (Press et al., 2020).

**Performance impact:** Table 8 shows that strided inference reduces bpb from 0.9079 (basic inference) to 0.8926 on PG-19, and is additive with sliding window (0.8751 bpb when both are applied). The independent contributions suggest these techniques address different aspects of the within-patch loss increase.

**Compatibility with sliding window:** standard sliding window evaluation (averaging predictions from multiple overlapping context windows) is also applicable to MEGABYTE and provides roughly similar gains. The two techniques can be combined for a $4\times$ inference cost multiplier (2× from strided, 2× from sliding window).

#### Generation Mechanism and Speed Advantage

Section 3.2 analyzes why MEGABYTE generates sequences faster than a standard transformer despite having more parameters.

**The serial bottleneck in standard transformer generation:** during autoregressive generation, a transformer must process one token at a time sequentially. For each new token, every layer of the network must be computed, using the previous token's output as input. This means the number of serial operations to generate a sequence of length $T$ is $T \times L$, where $L$ is the number of layers — each token requires computing $L$ layers, and tokens are generated one after another. Since individual layer computations on a single token typically do not saturate GPU parallelism, the serial depth (not total FLOPs) determines generation latency.

**MEGABYTE's reduced serial depth:** for a MEGABYTE model with $L_{\text{global}}$ global layers and $L_{\text{local}}$ local layers, generating a patch of $P$ bytes requires:

- 1 forward pass of the global model to produce the patch representation: cost approximately $O(L_{\text{global}})$ serial operations (parallelizable across tokens within the patch representation computation but the global model sees only one new patch).
- $P$ forward passes of the local model to generate $P$ bytes autoregressively within the patch: cost $O(P \cdot L_{\text{local}})$ serial operations.

Total serial operations per patch: $O(L_{\text{global}} + P \cdot L_{\text{local}})$. Total serial operations for the full sequence of $T$ bytes: $O(\frac{T}{P} \cdot L_{\text{global}} + T \cdot L_{\text{local}})$.

**Standard transformer serial depth for comparison:** a transformer with $L_{\text{global}} + L_{\text{local}}$ total layers would require $(L_{\text{global}} + L_{\text{local}})$ serial operations per byte, for a total of $T \cdot (L_{\text{global}} + L_{\text{local}})$.

**The speedup factor:** when $L_{\text{global}} \gg L_{\text{local}}$ (the global model is much deeper than the local model), the global model component dominates the per-byte cost in the standard transformer ($T \cdot L_{\text{global}}$), but in MEGABYTE it is amortized over $P$ bytes ($\frac{T}{P} \cdot L_{\text{global}}$). The speedup approaches a factor of $P$ for the global model's layers.

**Concrete measured speedup:** Table 6 reports that a MEGABYTE model with a 1.3B-parameter global model and a 218M-parameter local model (total ~1.5B parameters) generates a sequence of 8192 bytes 40% faster than a standard 350M-parameter transformer, while also achieving lower perplexity (0.991 vs. 1.064 bpb). This is despite MEGABYTE having over 4× more total parameters. The speedup comes from the fact that the 1.3B global parameters are only activated once per $P=8$ bytes, while the 350M transformer's parameters are activated on every byte.

**Why this matters practically:** generation speed is often the binding constraint for deployed language models. A model that is both more accurate and faster to generate from is a rare and valuable combination — typically, larger models are slower, and faster models are less accurate. MEGABYTE breaks this tradeoff by concentrating parameters where they are most useful (modeling long-range dependencies between patches) and amortizing their cost across multiple generated bytes.

#### Why Standard Efficient Transformer Techniques Don't Suffice

Section 3.1 presents a unified FLOP analysis comparing MEGABYTE against standard transformers and linear transformers across a range of model sizes and sequence lengths, explaining why the architecture change is necessary even if attention were made linear.

**Attention cost analysis:** for a sequence length $T$ and patch size $P$, the global model's self-attention operates on a sequence of length $T/P$, giving complexity $O(T^2 / P^2)$. The local model runs on $T/P$ sequences of length $P$, giving complexity $O((T/P) \cdot P^2) = O(TP)$. Total attention complexity: $O(T^2/P^2 + TP)$. Setting $P = T^{1/3}$ (the optimal choice to balance the two terms) gives $O(T^{4/3})$, which is better than the transformer's $O(T^2)$ and comparable to sparse transformers' $O(T^{3/2})$ (Child et al., 2019; Roy et al., 2020).

**The feedforward cost dominance:** however, the paper argues that "attention is not the main cost in large transformers." In a GPT3-style architecture, self-attention accounts for only 1.4% of FLOPs. The dominant cost is the position-wise feedforward network, which costs approximately $2mT$ FLOPs for a model with $m$ non-embedding parameters and sequence length $T$. This cost is linear in both sequence length and model size, and nothing about sparse or linear attention addresses it.

**MEGABYTE's feedforward cost:** the global model applies its feedforward layer only at $T/P$ positions, giving a cost proportional to $2m_g T / P$ (where $m_g$ is the global model's non-embedding parameters). The local model's feedforward cost is $2m_l T$ (applied at every one of $T$ positions, but $m_l$ is small). Total: $2T (m_g/P + m_l)$. When $m_g \gg m_l$, this is approximately $2T m_g / P$ — a factor of $P$ smaller than a standard transformer with the same $m = m_g + m_l$.

**Combined FLOP analysis (Figure 3):** the paper computes total FLOPs for standard transformers, linear transformers, and MEGABYTE across model sizes from 660M to 173B parameters and sequence lengths up to 1M tokens, using the FLOP estimates from Kaplan et al. (2020). MEGABYTE with $P=8$ consistently uses fewer FLOPs than either baseline across the entire range. For the largest configuration (173B parameters, 1M token sequence), the standard transformer requires approximately $2 \times 10^{12}$ FLOPs per token, linear transformers require about $6 \times 10^{11}$, and MEGABYTE requires about $3 \times 10^{11}$ — roughly 6× less than the standard transformer and 2× less than the linear transformer.

**The critical takeaway:** even if attention cost were reduced to zero (as linear attention attempts), the feedforward cost would still dominate at large model sizes. MEGABYTE is the only architecture among those analyzed that attacks both costs simultaneously.

## 4. Key Insights and Innovations

### Innovation 1: Reframing the Long-Sequence Bottleneck from Attention-Centric to Feedforward-Centric

The paper's most intellectually distinctive move is not a new mechanism but a **diagnostic reframing**: it argues that the dominant computational bottleneck in large autoregressive transformers is not self-attention — which the field had spent years trying to optimize — but rather the position-wise feedforward layers that consume >98% of FLOPs in models like GPT-3. This is a genuinely disruptive claim because it implies that the entire research program of efficient attention (sparse transformers, linear attention, state-space models, recurrence-based approximations) was solving the wrong problem, or at least a secondary one.

Prior to MEGABYTE, the standard narrative in long-sequence transformer research was overwhelmingly attention-focused. The abstract of nearly every efficient transformer paper — Sparse Transformers (Child et al., 2019), Reformer (Kitaev et al., 2020), Linear Transformers (Katharopoulos et al., 2020), Performer (Choromanski et al., 2020), Routing Transformers (Roy et al., 2020), Longformer (Beltagy et al., 2020) — led with the quadratic complexity of self-attention as the problem to be solved. Compressing, sparsifying, or linearizing attention was the dominant paradigm. The paper does not dispute that attention scales quadratically, but it points out a fact hiding in plain sight: in large models, attention is a small fraction of total compute, so making it faster provides diminishing returns. The real target should be the feedforward layers applied at every position.

What makes this reframing powerful is that it **redefines the optimization objective**. If feedforward cost dominates, the goal is not just to reduce the number of attention operations but to reduce the number of *positions at which any computation is performed*. This points toward hierarchical or multiscale architectures — not as an alternative to efficient attention, but as the *only* way to address the true bottleneck. MEGABYTE's patchification is the natural consequence of this diagnosis: by grouping bytes into patches, both attention length and feedforward applications are reduced simultaneously.

The paper supports this claim with concrete numbers rather than hand-waving. Figure 3 shows the FLOP comparison across model sizes and sequence lengths, demonstrating that MEGABYTE with $P=8$ uses fewer FLOPs than both standard transformers and linear transformers — the gap growing with model size precisely because the feedforward cost grows with the hidden dimension. Section 3.1's analysis that "self-attention computation accounts for only 1.4% of FLOPS" in GPT-3 is a crisp empirical anchor. The 40% generation speedup in Table 6 despite 4× more parameters is a second anchor that validates the theoretical analysis in practice.

This reframing is **fundamental rather than incremental** — it changes what problem researchers should be working on. It is analogous to the shift in computer architecture from optimizing instruction count to optimizing memory access patterns when the memory wall became the dominant constraint. Just as that shift redirected hardware design for a generation, this reframing suggests that long-sequence model research should prioritize architectures that reduce per-position computation over architectures that merely make attention cheaper.

---

### Innovation 2: Hierarchical Autoregressive Decomposition as a Viable Alternative to Tokenization

The paper proposes a concrete, fully differentiable alternative to tokenization — the dominant approach for shortening sequence lengths — and demonstrates it at a scale that makes the alternative credible. This is not merely an incremental improvement over prior byte-level models; it is the first demonstration that a byte-level autoregressive model can be **competitive with subword models on standard language modeling benchmarks** (Table 3: 36.4 word-level perplexity versus 28.9–33.6 for state-of-the-art subword models on PG-19).

Tokenization has been so universally adopted in large language models that it is often treated as a necessary evil rather than a design choice to be questioned. The paper's motivation section catalogs tokenization's pathologies — language-specific heuristics (Radford et al., 2019), domain transfer failures (Sharami et al., 2023), unpredictable interactions with prompting, and the fundamental impossibility of lossless tokenization for images and audio — but prior to MEGABYTE, no byte-level model had demonstrated performance within striking distance of subword models at meaningful scale. The only prior byte-level experiments cited (Hutchins et al., 2022, using Block-Recurrent and Memorizing Transformers) achieved test perplexities of 46.5–49.5 on PG-19, compared to MEGABYTE's 36.4. This ~10-point perplexity gap is enormous, and closing it is what makes the tokenization-free vision plausible rather than merely aspirational.

The conceptual innovation is the **hierarchical decomposition of the autoregressive prediction problem itself**. Prior byte-level models attempted to apply the same transformer architecture at the byte level that subword models use at the token level — different embedding granularity, same architectural paradigm. MEGABYTE recognizes that bytes and tokens have fundamentally different information density: predicting the next byte is often trivially easy (e.g., completing a word given the first few characters), while predicting the next high-level semantic unit requires deep reasoning. Assigning the same model capacity to both types of predictions is wasteful. The two-level architecture — large global model for hard, infrequent decisions (patch-level semantics), small local model for easy, frequent decisions (byte-level completion) — allocates capacity in proportion to the difficulty of the prediction task, not uniformly across all positions.

This is significant beyond raw performance because it **decouples the sequence length problem from the representation problem**. Tokenization compresses sequences by merging adjacent bytes into fixed vocabulary items, which conflates compression with representation learning — the tokenizer's merge rules determine what the model can and cannot express. MEGABYTE's patches are fixed-size chunks with no learned merging; the global model learns to represent whatever information is useful for the local model's predictions, but the local model retains full control over byte-by-byte generation. This means the architecture can, in principle, learn any compression scheme that is useful for the data, and adapt it continuously during training, without being locked into a static vocabulary. The paper doesn't fully realize this vision — the patches are fixed-size and non-overlapping — but it opens the door to architectures where the model dynamically determines how to group bytes for efficient processing.

The empirical evidence that this decomposition works across modalities (text, images, audio) with the same architecture and no modality-specific modifications (Table 2, Table 5, Table 7) is a secondary but important finding: it suggests the hierarchical decomposition is a general principle for sequence modeling, not a text-specific trick.

---

### Innovation 3: Breaking the Serial Bottleneck in Autoregressive Generation Through Hierarchical Parameter Allocation

The paper identifies and exploits a property of autoregressive generation that had not been systematically leveraged in prior architectures: **the serial depth of generation is determined by the depth of the model used at the finest timescale, not by total parameter count**. By placing the bulk of the parameters in a global model that operates at a coarser timescale (once per patch rather than once per byte), MEGABYTE achieves lower latency than a smaller model while using more parameters and achieving better accuracy.

This reverses the standard accuracy-latency tradeoff. Normally, larger models are slower — more layers mean more serial operations per token. MEGABYTE's 1.5B-parameter model generates 40% faster than a 350M-parameter transformer (Table 6) because the expensive global model (1.3B parameters) is invoked only once per $P=8$ bytes, while the 350M transformer runs all its layers on every byte. The serial depth is reduced from $T \cdot (L_{\text{global}} + L_{\text{local}})$ to $\frac{T}{P} \cdot L_{\text{global}} + T \cdot L_{\text{local}}$, and when $L_{\text{global}} \gg L_{\text{local}}$, the first term dominates and is reduced by a factor approaching $P$.

What makes this an innovation rather than an obvious consequence of the architecture is the **explicit analysis of the serial-versus-parallel tradeoff in decoder design** (Section 3.2). The paper treats generation latency as a first-class design objective, not an afterthought, and shows that the hierarchical structure provides a "free lunch" — more parameters with less latency — because parameters allocated to the global model are amortized across multiple output bytes. This analysis generalizes beyond MEGABYTE: any decoder architecture that can shift expensive computation to a coarser timescale will see similar benefits. It suggests a design principle: **allocate parameters where they are most useful for prediction quality, but place them at the coarsest timescale where they remain effective, to minimize serial operations during generation**.

Prior work on fast generation (e.g., non-autoregressive models, speculative decoding, parallel decoding) typically trades quality for speed or uses auxiliary models to guess multiple tokens simultaneously. MEGABYTE achieves speedup without quality loss and without auxiliary models — it is a single, end-to-end model whose architecture is naturally suited to fast generation. The paper doesn't extensively compare generation speed to prior fast-decoding methods, which is a limitation, but the principle it establishes — hierarchical parameter allocation for latency reduction — is more general than any particular speedup number.

### Innovation 4: The Compute-Controlled Experimental Protocol as a Methodological Contribution

While the paper's primary contributions are architectural, its experimental methodology represents a significant methodological advance for architecture research. The **compute-and-data-controlled comparison protocol** (Section 4.1) — adjusting model hyperparameters so that all architectures use identical wall-clock training time on identical data, rather than matching parameter count or training steps — addresses a pervasive confound in neural architecture evaluation that the paper identifies explicitly: "models show consistent improvements when increasing both data and compute (Kaplan et al., 2020; Hoffmann et al., 2022), meaning that one model can outperform another because of an increased training budget instead of an improved architecture."

The standard practice in architecture papers is to compare models at equal parameter count, which implicitly gives more efficient architectures less compute (they train faster per step, so equal steps means less total FLOPs) — systematically disadvantaging the architectures one is trying to evaluate. The paper's approach instead equalizes total compute, allowing an efficient architecture to use more parameters or more layers for the same training budget, and asking whether those extra parameters translate to better performance. This is a fairer comparison because it measures what practitioners actually care about: given a fixed budget of GPU hours, which architecture produces the best model?

The paper validates this methodology by reproducing Perceiver AR's published results (3.53 vs. 3.54 bpb on ImageNet 64×64) in the same codebase, establishing that the baselines are well-implemented and that observed differences reflect architecture rather than implementation quality. The consistent application of this protocol across all experiments — text (Table 2), images at three resolutions (Table 5), audio (Table 7), and the scaling experiment (Table 3) — makes the cumulative evidence unusually trustworthy by the standards of architecture papers, where cherry-picked baselines and unfair compute allocations are common.

This innovation is **methodological rather than algorithmic**, but it is important because it sets a standard that, if adopted more broadly, would substantially raise the quality of empirical evidence in architecture research. The paper doesn't belabor this point, but its careful execution of the protocol throughout the experiments implicitly advocates for it.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper evaluates on five text datasets encompassing diverse long-form modalities: **PG-19** (10.1GB, mean document 411,404 bytes — English books pre-1919 from Project Gutenberg; Rae et al., 2019b), **Stories** (21.3GB, mean 35,265 bytes — CommonCrawl subset emulating Winograd schemas; Trinh & Le, 2018), **Books** (79.7GB, mean 509,526 bytes — English-language books; Gao et al., 2020), **arXiv** (91.5GB, mean 58,518 bytes — technical publications in LaTeX), and **Code** (353.7GB, mean 7,461 bytes — open-source code under Apache/BSD/MIT licenses). For image modeling, the paper uses **ImageNet** (Oord et al., 2016) at three resolutions (64×64, 256×256, 640×640), with the 640×640 variant requiring modeling of sequences exceeding 1.2M tokens. For audio, the paper uses a proprietary **2TB dataset** (roughly 18,000 hours) of 16kHz, 16-bit audio. All text experiments use the same training hyperparameters across datasets without per-dataset tuning — "We use the same set of parameters on all datasets" — which tests architectural robustness rather than optimally tuned per-dataset performance.

- **Base model(s).** All experiments use transformer decoder architectures built within the **Metaseq** codebase (Zhang et al., 2022b). The paper defines six standard model size configurations (S1–S6) ranging from 125M to 6.7B parameters (Table 11), with layer counts, hidden dimensions, and attention heads specified. These base configurations are then adapted for each experiment by adjusting primarily the number of layers to equalize per-byte forward pass time across architectures. The paper does not start from pretrained checkpoints — all models are trained from scratch for each experiment under the compute-controlled protocol. The choice to use a consistent codebase (Metaseq) rather than assembling models from disparate implementations is deliberate: "all models share a similar data loader, preprocessing step, and trainer to avoid any artifacts in our compute-controlled experiments."

- **Metrics.** The primary metric across all experiments is **bits per byte (bpb)** — the negative log-likelihood per byte measured in bits (equivalent to average log-loss divided by $\ln 2$). For language modeling comparisons with prior subword-based work (Table 3), bpb is converted to word-level perplexity by exponentiating: perplexity $= 2^{\text{bpb} \times \text{bytes-per-word}}$, where bytes-per-word is dataset-specific. For image density estimation, bpb is the standard metric in the autoregressive image modeling literature (Oord et al., 2016). For generation speed, the metric is **wall-clock time** to generate 8192 bytes on identical hardware.

- **Baselines.** The paper compares MEGABYTE against three primary baselines:
  - **Standard decoder-only Transformer**: a vanilla autoregressive transformer with causal self-attention, using the same Metaseq implementation as MEGABYTE's global and local models. This tests whether the hierarchical decomposition provides benefits beyond a flat architecture.
  - **Perceiver AR** (Hawthorne et al., 2022): the best-performing general-purpose autoregressive long-context model at the time, which uses cross-attention from a shorter latent sequence into a longer context. The paper reproduces Perceiver AR's published ImageNet 64×64 result (3.53 vs. 3.54 bpb) to validate the implementation.
  - **Byte-level baselines** from prior work for the PG-19 scaling comparison (Table 3): Block-Recurrent Transformer and Memorizing Transformer results from Hutchins et al. (2022), and subword-based models including Transformer-XL (Rae et al., 2019a), Compressive Transformer (Rae et al., 2019a), and Perceiver AR with SentencePiece tokenization.

- **Generation budget / compute accounting.** The paper introduces a **compute-controlled experimental protocol** (Section 4.1) as its central methodological contribution: "We conduct experiments using a fixed compute and data budget across all models to focus our comparisons solely on the model architecture rather than training resources." Concretely, the authors adjust model hyperparameters (primarily the number of layers) within each architecture so that the wall-clock time per byte of forward pass is matched across all models being compared, then train all models on the same number of bytes (identical data budget). This means a more efficient architecture can use more layers or wider dimensions for the same training time. Total compute is measured in GPU hours on identical hardware. The approach differs from parameter-matched or FLOP-matched comparisons — it accounts for implementation-specific overhead and GPU utilization rather than counting theoretical operations. All experiments in a given table use identical compute and data — "All models within a column are trained using the same compute and data" (Table 7 caption). For generation speed comparisons (Table 6), compute is measured as wall-clock generation time for a fixed-length sequence.

- **Cross-validation / statistical protocol.** The paper does not use cross-validation or report confidence intervals. All results are single-run test set evaluations. For the PG-19 scaling experiment (Table 3), the "Validation" and "Test" columns report performance on the standard PG-19 validation and test splits. For ImageNet, the standard 64×64 validation split is used. For the higher-resolution ImageNet experiments (Table 5) and audio experiments (Table 7), the paper does not specify whether results are on validation or test sets. The absence of error bars or multiple training runs means that small performance differences (e.g., 0.6871 vs. 0.6781 bpb in Table 7 for arXiv with and without cross-patch attention) cannot be assessed for statistical significance.

### Main Quantitative Results

#### Language Modeling Across Diverse Text Modalities (Table 2)

The headline finding is that **MEGABYTE consistently outperforms both the standard transformer and Perceiver AR across all five text datasets under identical compute and data budgets**. On the compute-matched condition (80B training bytes, models scaled to equal wall-clock time):

| Dataset | Transformer (320M) | Perceiver AR (248M) | MEGABYTE (758M/262M) |
|---------|-------------------|---------------------|----------------------|
| PG-19 | 1.057 | 1.104 | **1.000** |
| Stories | 1.064 | 1.070 | **0.978** |
| Books | 1.097 | 1.104 | **1.007** |
| arXiv | 0.816 | 0.791 | **0.678** |
| Code | 0.575 | 0.546 | **0.411** |

MEGABYTE achieves the lowest bpb on every dataset. The gains are particularly pronounced on arXiv (0.678 vs. 0.816 for transformer, a 16.9% relative reduction in bpb) and Code (0.411 vs. 0.575, a 28.5% reduction). On PG-19, the gain over the transformer is more modest (1.000 vs. 1.057, a 5.4% reduction), but MEGABYTE is using a substantially larger model (758M global + 262M local = ~1B total) for the same compute — the transformer is constrained to 320M parameters to match the per-byte cost. This means MEGABYTE's architectural efficiency enables it to effectively use ~3× more parameters within the same compute budget.

Notably, Perceiver AR — the strongest prior general-purpose long-context model — slightly underperforms the standard transformer on PG-19 and Books (1.104 vs. 1.057, and 1.104 vs. 1.097), while showing marginal improvements on arXiv (0.791 vs. 0.816) and Code (0.546 vs. 0.575). This suggests that Perceiver AR's cross-attention mechanism does not consistently translate to better language modeling compared to a dense transformer at the same compute budget, whereas MEGABYTE's hierarchical decomposition does.

The specific configurations used: Transformer at 320M with context length 1024, Perceiver AR at 248M with context length 8192 and 1024 latents, MEGABYTE with 758M global model (D=2048, 14 layers) and 262M local model (D=1024, 18 layers), context length 8192 bytes, patch size P=8 (Table 12). The transformer and MEGABYTE both process raw bytes; Perceiver AR operates on bytes with a compressive latent bottleneck.

#### Scaling Experiment on PG-19 (Table 3)

When scaled to 400B training bytes with the same compute-controlled protocol, **MEGABYTE dramatically outperforms other byte-level models** and achieves performance competitive with state-of-the-art subword models:

| Model | Tokenizer | Vocab Size | Test Perplexity |
|-------|-----------|------------|-----------------|
| Transformer-XL (Rae et al., 2019a) | SentencePiece | 32k | 36.3 |
| CompressiveTransformer (Rae et al., 2019a) | SentencePiece | 32k | 33.6 |
| Perceiver AR (Hawthorne et al., 2022) | SentencePiece | 32k | 28.9 |
| BlockRecurrent (Hutchins et al., 2022) | SentencePiece | 32k | 26.5 |
| Transformer byte-level (ours) | Bytes | 256 | 69.4 |
| Perceiver AR byte-level (ours) | Bytes | 256 | 88.8 |
| **MEGABYTE** | **Bytes** | **256** | **36.4** |

MEGABYTE's test perplexity of 36.4 is within ~26% of the best subword model (BlockRecurrent at 26.5) and within ~10% of the second-best subword model (Perceiver AR at 28.9). The gap between MEGABYTE (36.4) and the next-best byte-level model — the byte-level transformer at 69.4 — is enormous: MEGABYTE reduces perplexity by 47.5% relative. The byte-level Perceiver AR actually performs *worse* than the byte-level transformer (88.8 vs. 69.4), suggesting that Perceiver AR's latent bottleneck is particularly harmful for byte-level modeling, likely because individual bytes carry little semantic information and the bottleneck discards crucial fine-grained detail.

The paper explicitly notes: "The only prior byte-level experiments we are aware of are at a smaller scale in Hutchins et al. (2022), who report results equivalent to test perplexities of 46.5 with a version of the Block-Recurrent transformer, and 49.5 with Memorizing Transformers (Wu et al., 2022), compared to 36.4 with our model." These prior byte-level results are from models that also modify the transformer architecture for long sequences, but neither achieves MEGABYTE's performance, and both are at a smaller training scale — underscoring that MEGABYTE's approach is genuinely more effective, not merely benefiting from more compute.

The paper acknowledges that the subword comparisons "may be confounded by differing amounts of compute and tuning used" since these are results from different papers with different training budgets. However, the comparison establishes that byte-level models are no longer categorically inferior — the performance gap has closed to the point where tokenization-free modeling is a viable alternative rather than a compromise.

#### Image Modeling — Compute-Controlled Comparison at Three Resolutions (Table 5)

The paper tests MEGABYTE's ability to model increasingly long sequences by evaluating on ImageNet at 64×64 (12,288 bytes), 256×256 (196,608 bytes), and 640×640 (1,228,800 bytes) resolutions, all under identical compute and data budgets per resolution:

| Context | Image64 (12K bytes) | Image256 (197K bytes) | Image640 (1.2M bytes) |
|---------|---------------------|-----------------------|------------------------|
| Transformer | 3.62 (ctx 1024) | 3.801 (ctx 1024) | 2.847 (ctx 1024) |
| Perceiver AR | 3.55 (ctx 12000) | 3.373 (ctx 8192, 768 latents) | 2.345 (ctx 4096, 1024 latents) |
| MEGABYTE | **3.52** (full 12K) | **3.158** (full 197K) | **2.282** (full 1.2M) |

MEGABYTE outperforms both baselines at all three resolutions, with the advantage growing as sequence length increases. At Image64, the margin is small (3.52 vs. 3.55 for Perceiver AR, a 0.8% reduction). At Image256, the gap widens substantially (3.158 vs. 3.373, a 6.4% reduction). At Image640, MEGABYTE achieves 2.282 bpb versus Perceiver AR's 2.345 (2.7% reduction) and the transformer's 2.847 (19.8% reduction). The transformer, constrained to context 1024 at all resolutions because it cannot handle longer sequences at reasonable model sizes, performs progressively worse relative to the architectures with longer context.

A critical methodological detail: **only MEGABYTE processes the full image sequence in a single forward pass** at all resolutions. The transformer and Perceiver AR must "split images into segments of size 1024 and 12000 respectively" for the longer sequences (Section 6.3), meaning they do not have access to the full image context. The paper explicitly states: "We found neither the standard Transformer nor PerceiverAR could model such long sequences at a reasonable model size, so instead we split images into segments." This means the comparison at Image256 and Image640 is between an architecture that can see the entire image (MEGABYTE) and architectures that see only segments — making MEGABYTE's advantage partly about longer effective context rather than purely about model quality per FLOP. The paper does not explore whether giving the transformer or Perceiver AR longer segments (at the cost of a smaller model to maintain the compute budget) would close the gap.

For Image64, MEGABYTE uses patch size 12 with a 1.3B global and 1.3B local model (both D=2048, L=24). For Image256 and Image640, MEGABYTE uses patch size 192 with a 125M global and 125M local model (D=768, L=12 for Image256; 125M global and 83M local for Image640). The paper also introduces **patch scan** — a 2D-aware ordering where patches of $p \times p \times 3$ bytes are formed from the image grid and then raster-scanned both within and between patches — and reports this is "more effective than raster scan for modeling image sequencing" (Appendix D.2), improving both MEGABYTE (3.158 vs. 3.428 bpb with raster scan on Image256) and Perceiver AR (3.373 vs. 3.552) substantially.

#### Image Modeling — State-of-the-Art Comparison on ImageNet 64×64 (Table 4)

To position MEGABYTE against the best published results regardless of compute budget, the paper trains a large MEGABYTE (2.7B global, 350M local) for 1.4T tokens on ImageNet 64×64:

| Model | bpb |
|-------|-----|
| Routing Transformer (Roy et al., 2020) | 3.43 |
| Combiner (Ren et al., 2021) | 3.42 |
| Perceiver AR (Hawthorne et al., 2022) | 3.40 |
| **MEGABYTE** | **3.40** |

MEGABYTE matches the state-of-the-art 3.40 bpb while using "less than half the GPU hours we would have needed to reproduce the best PerceiverAR model described by Hawthorne et al. (2022)" — estimated based on the Perceiver AR configuration. This establishes that MEGABYTE is not only more efficient at matched compute (Tables 2, 5) but can also reach the frontier of what's achievable when scaled up, at substantially lower cost. The absolute bpb of 3.40 represents a density estimation quality where the model assigns high likelihood to genuine ImageNet images — lower bpb means the model is less "surprised" by real images and would presumably generate more realistic samples.

#### Audio Modeling (Section 7)

On the 2TB audio dataset with sequence length 524,288 bytes (patch size 32), MEGABYTE achieves **3.477 bpb**, outperforming both Perceiver AR (**3.543 bpb**) and the standard transformer (**3.567 bpb**) under compute-matched conditions. The paper emphasizes a simplification enabled by byte-level modeling: "we simplify the audio modeling process by directly reading the bytes (256 possible values) from the audio file and conducting an autoregressive language model on top of that." This avoids the specialized techniques required by prior audio models — µ-law companding (van den Oord et al., 2016), discretized mixture of logistics (Salimans et al., 2017), or dual softmax (Kalchbrenner et al., 2018) — which were necessary to handle 16-bit samples (65,536 possible values) with manageable softmax layers. MEGABYTE's byte-level approach naturally produces a 256-way classification per byte, making audio modeling as straightforward as text modeling from an architectural perspective.

The absolute gap between models is modest (3.477 vs. 3.543 vs. 3.567), but the paper emphasizes the architectural simplicity rather than dramatic accuracy improvements. The specific configuration: MEGABYTE with 350M global model (D=1024, L=24) and 125M local model (D=768, L=12), batch size 256, learning rate $2 \times 10^{-4}$, context 524,288 bytes with patch size 32.

#### Generation Speed (Table 6)

On PG-19, a MEGABYTE model with 1.3B global parameters and 218M local parameters (total ~1.5B, context 8192, P=8) is compared to a 350M-parameter transformer (context 1024), both trained with equal compute:

| Model | Total Parameters | bpb | Generation Time for 8192 bytes |
|-------|-----------------|-----|-------------------------------|
| Transformer | 350M | 1.064 | 132s |
| MEGABYTE | 1.5B (1.3B + 218M) | 0.991 | **93s** |

MEGABYTE generates sequences **40% faster** (93s vs. 132s) while achieving substantially lower perplexity (0.991 vs. 1.064 bpb), despite having over 4× more total parameters. The paper attributes this to "the bulk of the parameters being in the Global model, which only needs to be computed once for every 8 tokens, whereas all the parameters in the baseline model are used on every token."

This result directly validates the theoretical analysis in Section 3.2: the serial depth of generation is $L_{\text{global}}/P + L_{\text{local}}$ per byte for MEGABYTE versus $L_{\text{total}}$ for a standard transformer. With $L_{\text{global}} = 24$, $L_{\text{local}} = 15$, $P = 8$, MEGABYTE's serial operations per byte are $24/8 + 15 = 18$, versus $24$ for the transformer (assuming comparable layer count). The actual speedup (40%) is slightly less than the theoretical maximum (roughly $24/18 \approx 1.33\times$, which would be 25% faster), likely because the global model's per-patch computation is more expensive per-layer than the local model's per-byte computation, and GPU parallelism effects complicate the simple serial-depth model.

#### Effective Context Utilization (Figure 4)

Figure 4 shows the average log probability assigned to tokens at different positions within the 8192-byte context window for MEGABYTE and a compute-matched vanilla transformer (PG-19 test set). The transformer's likelihood curve is relatively flat — later tokens in the context window do not have consistently higher likelihood, indicating the model struggles to effectively use tokens beyond a certain distance. MEGABYTE's likelihood curve **rises throughout its context window**: "likelihoods rise throughout its context window, demonstrating that it can use tokens from 8k bytes previously to improve its predictions." This is direct evidence that MEGABYTE's hierarchical architecture enables effective use of longer context, whereas the standard transformer's fixed context window provides diminishing returns beyond the first few thousand tokens — consistent with prior findings that long-context models "often struggle to benefit from the full context" (Sun et al., 2021, cited in Section 8.3).

### Ablation Studies and Robustness Checks

Table 7 presents systematic ablation of MEGABYTE components across three modalities (arXiv text, Librilight-L audio, ImageNet256):

**Removing the local model (w/o local model):** This configuration removes the local transformer and has the global model predict patch bytes directly — effectively a decoder-only ViT-like architecture. Performance degrades catastrophically on all modalities: arXiv worsens from 0.6871 to 1.263 bpb (84% increase), audio from 3.477 to 5.955 (71% increase), ImageNet256 from 3.158 to 4.768 (51% increase). This validates the paper's argument in Section 2.4 that directly predicting patch contents without an autoregressive local model is fundamentally limited — the global model cannot represent complex within-patch distributions. The "w/o local model" configuration uses a much larger global model (2.3B-2.7B parameters) to compensate for the removed local model while maintaining compute budget, demonstrating that the limitation is representational rather than merely a capacity issue.

**Removing the global model (w/o global model):** This configuration removes the global transformer and has the local model predict bytes with only its own limited context (a single patch of length P). Performance degrades substantially: arXiv worsens from 0.6871 to 1.373 bpb (100% increase), audio from 3.477 to 3.659 (5.2% increase), ImageNet256 from 3.158 to 3.181 (0.7% increase). The degradation is much larger for text (where long-range linguistic dependencies matter) than for audio or images (where local patterns dominate). This confirms that the global model is essential for capturing long-range structure in text but less critical for modalities where local context suffices — a non-obvious finding that demonstrates the architecture adapts to the dependency structure of each modality.

**Removing cross-patch attention (w/o cross-patch attention):** The base MEGABYTE's cross-patch attention — where the local model can attend to the last $r$ positions of the previous patch — has minimal or slightly negative impact. On arXiv, removing it *improves* bpb from 0.6871 to 0.6781. On audio, performance slightly degrades from 3.477 to 3.481. On ImageNet256, performance degrades from 3.158 to 3.259 (3.2% increase). The negative result on arXiv suggests that the global model already provides sufficient cross-patch information for text at patch size 8, and the cross-patch attention may introduce noise or overfitting. On ImageNet256 with a much larger patch size (192), the loss of cross-patch attention hurts more because the patch boundaries are farther apart in pixel space, making the global model's coarse patch representations less adequate for fine-grained boundary information.

**Adding a convolutional patch encoder (w/ CNN encoder):** Adding causal convolutional layers before patch chunking (filter sizes 3, 5, 7) provides negligible or very small improvements: arXiv unchanged at 0.6871, audio improves from 3.477 to 3.475 (0.06% reduction), ImageNet256 improves from 3.158 to 3.155 (0.09% reduction). The paper states this "suggests that the MEGABYTE architecture can benefit from integrating alternative encoding mechanisms" but the benefits are so small (within likely statistical noise) that the practical value of the CNN encoder is questionable. The near-zero impact on text is particularly notable — it suggests that the translation invariance problem the CNN encoder was designed to solve (different offsets of the same byte sequence within a patch) is either not a real problem for the tasks tested, or the model learns to handle it effectively without architectural intervention.

**Patch size variation (Table 9):** On Image256, the paper tests patch sizes of 48, 192, and 768 (corresponding to 4×4×3, 8×8×3, and 16×16×3 pixel blocks respectively), adjusting model sizes to maintain identical compute:

| Patch Size | Global Size | Local Size | bpb |
|-----------|-------------|------------|-----|
| 48 | 125M (D=768, L=11) | 114M (D=768, L=11) | 3.178 |
| 192 | 125M (D=768, L=12) | 125M (D=768, L=12) | **3.158** |
| 768 | 125M (D=768, L=12) | 83M (D=768, L=8) | 3.186 |

Performance is relatively flat across a 16× range of patch sizes (3.158–3.186), with patch size 192 providing the optimum. The paper claims "a wide range of values where MEGABYTE performs similarly" and "similar robustness against the choice of this hyperparameter across all modalities," which is valuable from a practical standpoint — practitioners don't need to heavily tune patch size. However, the underlying reason for this robustness is not explored. The paper notes that "the optimal patch size itself can be different across modalities" (8 for text, 32 for audio, 192 for images), suggesting that the optimal patch size relates to the natural correlation length of each modality — characters within words (text, ~4-8 bytes), audio samples within a phoneme (~100s-1000s of bytes at 16kHz), and pixels within texture patches (images, hundreds of bytes).

**Global-to-local model size ratio (Table 10):** On PG-19, the paper varies the ratio of global to local model capacity while maintaining total compute:

| Global Size | Local Size | bpb |
|-------------|------------|-----|
| 350M (D=1024, L=24) | 290M (D=1024, L=20) | 1.014 |
| 760M (D=1536, L=24) | 262M (D=1024, L=18) | 1.002 |
| 1.3B (D=2048, L=24) | 218M (D=1024, L=15) | **0.991** |

Increasing the global model's capacity relative to the local model consistently improves performance. The paper states: "a given compute budget is spent optimally when the Global model has more parameters than the Local model. This trend was consistent across all modalities and various patch sizes." This is intuitive — the global model makes fewer, harder decisions (patch-level semantics) and can use more capacity, while the local model makes many easy decisions (byte completion within a word or phrase) and needs less. The optimal ratio itself (ranging from roughly 1.2:1 to 6:1) likely depends on the task's long-range dependency structure.

**Strided inference and sliding windows (Table 8):** On PG-19 with the best MEGABYTE model:

| Method | Inference Cost Multiplier | bpb |
|--------|--------------------------|-----|
| Basic Inference | 1× | 0.9079 |
| w/ Sliding Window | 2× | 0.8918 |
| w/ Strided Inference | 2× | 0.8926 |
| w/ Sliding & Strided | 4× | **0.8751** |

Strided inference and sliding window provide roughly equal and additive gains (each ~0.015 bpb improvement at 2× cost), with combined gains of 0.0328 bpb at 4× cost. The additivity suggests these techniques address different aspects of the within-patch loss degradation: sliding window allows the model to see more global context, while strided inference ensures each predicted byte comes from the first half of a patch where the global context is freshest.

**Longer context lengths (Table 14):** On PG-19 with the scaling configuration (1.3B global, 350M local, P=8), increasing context from 8192 to 16384 bytes does not improve bpb (0.8751 vs. 0.8787, slight degradation). The paper attributes this to model size: "With longer sequence, we didn't observe further improvement, consistent with findings in Hawthorne et al. (2022). We think we will benefit more from longer sequence when we further scale up the model size and data." This is an important negative result that bounds the practical benefit of MEGABYTE's long-context capability: having the architectural capacity for long context (up to 1M+ tokens) does not automatically translate to better predictions if the model lacks the parametric capacity to learn useful long-range patterns from the available training data.

**Perceiver AR reproduction validation (Section 4.3):** The paper reports: "By carefully matching hyperparameters, we achieved a bits per byte (bpb) score of 3.53, compared to the reported 3.54 in the original paper" on downsized ImageNet 64×64. This 0.01 bpb difference validates the Perceiver AR implementation and gives confidence that subsequent comparisons reflect architectural differences rather than implementation quality.

### Critical Assessment

**Does the evidence support the claim that MEGABYTE enables "end-to-end differentiable modeling of sequences of over one million bytes"?**

The claim is directly supported. On ImageNet 640×640, MEGABYTE processes sequences of 1,228,800 bytes in a single forward pass (Table 5: context length listed as "Full, 1,228,800"). This is an existence proof: the architecture can handle million-byte sequences. However, the claim that this constitutes "modeling" rather than merely "processing" deserves scrutiny. The bpb of 2.282 on Image640, while better than baselines, is not compared to any external standard — we don't know whether this represents good density estimation or merely non-catastrophic behavior. The effective context utilization analysis (Figure 4) shows MEGABYTE benefits from 8K bytes of context, but this is far short of 1M — the paper does not provide equivalent analysis for whether the model actually uses context from hundreds of thousands of bytes away in the Image640 experiments. The architecture *can* process sequences that long, but whether it *benefits* from the full length is unproven at the largest scales.

**Does the evidence support the claim that MEGABYTE allows byte-level models to "perform competitively with subword models on long context language modeling"?**

This claim is supported with qualifications. On PG-19, MEGABYTE's test perplexity of 36.4 is within ~10–26% of the best subword models (28.9–33.6; Table 3). Whether this gap is "competitive" depends on one's standard: it is far closer than any prior byte-level model (previous best: 46.5 from Hutchins et al., 2022), but there remains a meaningful gap. The paper is transparent that the subword comparisons come from different papers with different training budgets, acknowledging this confound. However, it does not run its own subword baseline with the same compute budget — a natural experiment that would have directly answered whether the remaining gap is due to byte-level vs. subword representation or to training budget differences. Such an experiment is missing and would have substantially strengthened this claim.

Additionally, "long context language modeling" is only tested on PG-19 (mean document 411K bytes). The Books dataset has even longer documents (mean 509K bytes), but Table 2 only reports aggregate bpb without length-stratified perplexity. The paper does not show whether MEGABYTE's advantage over the transformer grows with document length, which would be direct evidence of better long-context utilization.

**Does the evidence support the claim of achieving "state-of-the-art density estimation on ImageNet"?**

This claim is narrowly but cleanly supported. On ImageNet 64×64, MEGABYTE achieves 3.40 bpb, matching Perceiver AR's 3.40 bpb (the prior state-of-the-art) while using half the GPU hours (Table 4). This is a genuine achievement: it matches the frontier at substantially lower cost. However, the claim of "state-of-the-art" applies only to ImageNet 64×64 among autoregressive models — the paper doesn't compare to diffusion models, GANs, or other generative paradigms. This is appropriate given the paper's focus on autoregressive sequence modeling, but readers should not confuse "state-of-the-art density estimation on ImageNet" with "state-of-the-art image generation on ImageNet."

For the higher resolutions (256×256 and 640×640), there is no comparison to published state-of-the-art — Table 5 only compares against the paper's own baselines under compute-controlled conditions. So the state-of-the-art claim applies only to the 64×64 resolution.

**Does the evidence support the claim that MEGABYTE "model[s] audio from raw files"?**

Supported, but the audio results are the least developed in the paper. The audio section (Section 7) is brief, uses a proprietary dataset (2TB, "roughly 18,000 hours"), and provides only aggregate bpb comparisons without qualitative analysis of generated audio, without comparison to published audio models (WaveNet, SampleRNN, etc.), and without demonstrating that the bpb results translate to perceptually good generation. The paper claims the approach "greatly streamlines the modeling process, making it easier and more efficient" — which is true in the sense that no µ-law companding or dual softmax is needed — but the actual modeling results are not benchmarked against standard audio generation metrics (MOS scores, Fréchet Audio Distance, etc.). This makes the audio section a proof of concept rather than a rigorous demonstration.

**The compute-controlled methodology: strength and limitations.**

The compute-controlled protocol is the paper's strongest methodological contribution, but it has limitations the paper does not fully address. By adjusting layer counts to equalize wall-clock time, the paper implicitly assumes that training time is the binding constraint and that all architectures have similar training dynamics (convergence speed, sensitivity to learning rate, etc.) when layer counts differ. A model with fewer layers might need fewer training steps to converge — the paper's protocol of training all models for the same number of bytes could disadvantage architectures that converge faster. Conversely, deeper models might benefit more from longer training, and equalizing per-step time does not account for potential differences in data efficiency.

The specific implementation also embeds assumptions about GPU efficiency. The paper uses FairScale's fully sharded data parallelism, and the wall-clock time depends on how well each architecture utilizes the sharding. A model with more parameters but fewer layers (e.g., MEGABYTE with wide shallow layers) might have different communication patterns than a standard transformer with more layers but fewer parameters — the compute-matching protocol would capture this, but it means results are implementation-specific and might not transfer to different parallelism strategies or hardware.

**Missing experiments that would strengthen the paper:**

1. **Subword baseline with matched compute**: Training a SentencePiece-based transformer with the same compute budget as the MEGABYTE scaling experiment would directly measure how much of the byte-vs-subword gap is architectural vs. representational.

2. **Length-stratified perplexity**: Breaking down perplexity by sequence length would show whether MEGABYTE's advantage comes from better short-sequence modeling (due to larger effective model size) or genuinely better long-range context utilization. Figure 4 shows rising likelihoods within the context window, but this doesn't separate "more parameters helping everywhere" from "hierarchical architecture specifically helping long-range dependencies."

3. **MEGABYTE with subword tokens**: Running the hierarchical architecture on subword tokens would test whether the gains are due to the hierarchical decomposition (which would transfer to tokens) or specifically to the byte-level representation (which would not). This ablation would disentangle the two innovations.

4. **Comparison to sparse attention methods beyond Perceiver AR**: The paper argues that feedforward cost dominates, but doesn't compare against sparse attention methods (Routing Transformer, Sparse Transformer) that also reduce feedforward cost by limiting the number of positions at which computation occurs. These methods could plausibly achieve similar FLOP reductions without the hierarchical decomposition.

5. **Generation quality evaluation for images and audio**: The paper reports only bpb (density estimation quality), not sample quality. For generative models, these can diverge — a model can achieve low bpb but produce unrealistic samples. Qualitative examples or FID/IS scores for images would strengthen the claim that MEGABYTE is useful for generation, not just density estimation.

6. **Confidence intervals or multiple runs**: Small differences in bpb (e.g., 0.6871 vs. 0.6781) are treated as meaningful without any measure of variance. Given the single-run evaluation protocol, these could easily be noise.

**Conditional nature of the findings:**

The paper's strongest claims hold for the specific regime it tests: models in the 100M–3B parameter range, trained on 80B–400B bytes, evaluated on density estimation (bpb). The paper explicitly notes that "the scale of experiments here is far below those of state-of-the-art language models (Brown et al., 2020), and future work should explore scaling MEGABYTE to much larger models and datasets" (Section 10). This is not a weakness of the paper — it's scoped appropriately — but the reader should understand that the demonstrated advantages (4× larger models for same compute, 40% generation speedup) are measured at moderate scale and may not extrapolate to the 100B+ parameter regime where attention cost becomes proportionally larger or where different parallelism strategies dominate.

The claim that MEGABYTE "may allow byte-level models to replace tokenization" is explicitly couched as a possibility, not an accomplished fact: "may allow byte-level models to replace tokenization" (Section 10). The evidence makes this plausible — 36.4 test perplexity vs. 28.9–33.6 for subword models, competitive ImageNet density estimation, simplified audio modeling — but the gap on text is real, and closing it completely at scale remains future work.

## 6. Limitations and Trade-offs

### 6.1 The Compute-Controlled Protocol Depends on Implementation-Specific Efficiency and May Not Transfer Across Hardware or Software Stacks

**The assumption or constraint:** All comparisons in the paper rely on equalizing *wall-clock training time per byte* across architectures by adjusting model hyperparameters (primarily layer counts). The paper states: "We adjust model hyperparameters (mainly, number of layers) within each architecture so that the forward pass time taken per byte is matched, and then train all models for the same number of bytes" (Section 4.1). This protocol assumes that the relative efficiency of architectures measured in one software/hardware configuration (Metaseq on what is presumably NVIDIA hardware with FairScale sharding) generalizes to other configurations.

**The consequence:** The specific numerical advantages reported — MEGABYTE using a 758M global model versus a 320M transformer for identical compute (Table 2), the 40% generation speedup (Table 6), the factor-of-P amplification of feedforward layer size — are all calibrated to the Metaseq implementation and the specific GPU hardware available in 2023. A different parallelism strategy (tensor parallelism, pipeline parallelism), a different GPU generation with different memory bandwidth and FLOP ratios, or a different attention implementation (FlashAttention, which did not exist at the time of Metaseq's development) could shift the optimal layer count for each architecture and change the compute-matched configuration. For instance, FlashAttention substantially reduces the memory and compute cost of self-attention, which could make the standard transformer's attention less of a bottleneck and reduce MEGABYTE's relative advantage. Conversely, hardware with higher FLOP-to-memory-bandwidth ratios might benefit MEGABYTE's per-patch feedforward layers more than the transformer's per-token layers, amplifying the advantage.

**What evidence exists in the paper:** The paper provides no sensitivity analysis to hardware or implementation changes. All comparisons are based on a single software stack (Metaseq with FairScale). The Perceiver AR reproduction (3.53 vs. 3.54 reported bpb) validates the implementation quality of that baseline, but does not test whether the relative efficiency ordering would hold in a different framework. The FLOP analysis in Figure 3 and Section 3.1 is theoretical (based on the Kaplan et al., 2020 approximations) and does not account for implementation-specific constants, memory access patterns, or communication overhead. Tables 2, 5, and 7 all use the same compute-matching methodology without reporting what the underlying per-byte wall-clock times actually were or how sensitive the matching was to hyperparameter choices.

**Mitigation status:** Not addressed. The paper does not discuss the dependence of its results on the implementation or hardware, and does not suggest that the compute-matching methodology is specific to its experimental setup. The FLOP analysis in Section 3.1 provides a theoretical case that MEGABYTE's advantages are architectural rather than implementation-specific, but theory and practice diverge in distributed training — the theoretical FLOP advantage could be consumed by communication overhead, memory constraints, or suboptimal kernel fusion that the Metaseq implementation handles differently for different architectures. A practitioner considering MEGABYTE for a different framework (JAX, Megatron-LM) or hardware (TPUs, newer GPU generations) would need to recalibrate the compute-matching for their setup, with no guidance from the paper on how to do so.

### 6.2 The Architecture Does Not Demonstrate Effective Utilization of Million-Byte Context — Only That It Can Process Sequences of That Length Without Collapsing

**The assumption or constraint:** The paper's title and abstract claim "predicting million-byte sequences" and "end-to-end differentiable modeling of sequences of over one million bytes." The Image640 experiments (Table 5) process sequences of 1,228,800 bytes in a single forward pass — meeting the literal claim of *processing* sequences of that length. However, the paper's evidence for *utilizing* context at that scale is indirect and limited to much shorter sequences.

**The consequence:** A practitioner deploying MEGABYTE for genuinely long-range tasks (e.g., modeling full books of millions of bytes, high-resolution image generation that requires global coherence across the entire canvas) has no evidence that the model actually learns dependencies spanning hundreds of thousands of bytes. The paper's only direct evidence of effective context utilization is Figure 4, which shows rising likelihoods within an 8192-byte context window on PG-19 — a sequence length 150× shorter than the million-byte regime claimed in the title. The Image640 experiments (Table 5) report only aggregate bpb scores, not length-stratified likelihoods or any analysis of whether the model uses context from, say, the top-left corner of the image to inform predictions at the bottom-right corner. It is entirely possible that MEGABYTE's advantage on Image640 comes from better local modeling (since it can process the full image without segmentation) rather than from genuine million-byte-range dependency learning. The model could, in principle, attend only to the immediately preceding patches and ignore 99% of the context, and the aggregate bpb would not reveal this.

Additionally, the PG-19 scaling experiment (Table 14) shows that increasing context from 8192 to 16384 bytes does *not* improve perplexity (0.8751 vs. 0.8787 — slight degradation). The paper attributes this to insufficient model capacity: "We think we will benefit more from longer sequence when we further scale up the model size and data." This is a plausible explanation, but it means the paper provides no evidence that MEGABYTE actually learns to use very long context — only that it processes long sequences without the perplexity collapsing to infinity (which might happen if the model lost track of position or suffered from numerical instability). The million-byte claim is about architectural capability, not demonstrated learning of million-byte dependencies.

**What evidence exists in the paper:** The effective context utilization analysis (Figure 4) covers only 8192 bytes. The only million-byte experiments are on Image640 (Table 5), which report only aggregate bpb. No attention pattern analysis, gradient flow analysis, or long-range dependency probing is provided for any experiment. Table 14 directly shows no benefit from doubling context length on PG-19 at the tested model scale.

**Mitigation status:** The paper acknowledges the scaling limitation for longer context implicitly — "With longer sequence, we didn't observe further improvement, consistent with findings in Hawthorne et al. (2022). We think we will benefit more from longer sequence when we further scale up the model size and data" (Appendix D.3). However, this acknowledgment appears only in the appendix, not in the main text, and it addresses only the PG-19 scaling experiment, not the Image640 results that are the basis for the million-byte claim. The paper does not provide any analysis of whether the Image640 model actually learns dependencies at the million-byte scale or merely benefits from not segmenting the image. Future work "exploring scaling MEGABYTE to much larger models and datasets" is suggested (Section 10), but not specifically to validate long-range dependency learning.

### 6.3 The Architecture Introduces a Fundamental Tradeoff Between Patch Size, Context Granularity, and Model Capacity That Is Unexplored and Likely Task-Dependent

**The assumption or constraint:** MEGABYTE's efficiency comes from the patch size $P$ — larger $P$ means the global model runs on shorter sequences (cheaper attention) and its feedforward layers are applied less frequently (cheaper per-byte FFN cost), enabling a larger model for the same compute. However, larger $P$ also means the global model provides coarser-grained information to the local model: a single $P \cdot D_G$-dimensional patch representation must summarize $P$ bytes of context for the local model to use in byte-level prediction. This creates an information bottleneck: as $P$ grows, the global model's representation must be more compressive, potentially discarding fine-grained cross-patch information that the local model needs.

**The consequence:** The optimal patch size likely depends on the natural correlation scale of the data — for text, characters within a word (~4-8 bytes); for audio, samples within a phoneme (~100s of bytes); for images, pixels within a texture patch (~100s of bytes). The paper shows robustness to patch size on Image256 (Table 9: 3.158-3.186 bpb across a 16× range), but this robustness is measured on aggregate bpb and may hide task-specific failure modes. For tasks requiring fine-grained cross-patch reasoning — say, detecting that a specific character sequence spans a patch boundary, or tracking a single-pixel feature across a high-resolution image — a larger patch size would force the global model to represent byte-level information in a compressed patch vector, which may be impossible without information loss. Conversely, for tasks requiring very long-range dependencies with little need for fine-grained cross-patch information, a small patch size wastes capacity on making the global model process more positions than necessary.

A practitioner choosing $P$ for a new task or modality has limited guidance. The paper reports optimal patch sizes for its tested modalities (8 for text, 32 for audio, 192 for Image256 — derived from the $768/3$ patch size in the table captions and main text), but these are post-hoc optima found by grid search, not principled predictions from data properties. The paper does not provide heuristics — e.g., "set $P$ to the average length of a semantically meaningful unit in your data" or "measure the autocorrelation length and set $P$ accordingly." The robustness on Image256 (Table 9) is reassuring but may not generalize: text at patch size 8 vs. 16 vs. 4 is never tested in a controlled ablation, and the consequences of a suboptimal $P$ for a new modality are unknown.

**What evidence exists in the paper:** Table 9 shows patch size robustness on Image256 (48, 192, 768). Table 12 lists the chosen patch sizes per experiment (8 for text, 12 for Image64, 192 for Image256/640, 32 for audio) but does not show ablations for text or audio. The paper states "We found similar robustness against the choice of this hyperparameter across all modalities, although the optimal patch size itself can be different across modalities" (Section 8.5), but the evidence for text and audio robustness is not presented.

**Mitigation status:** Partially addressed through the empirical robustness demonstration on Image256, but the underlying tradeoff (coarser patches = more efficiency but less granular information) is never formalized or analyzed theoretically. The paper does not provide a heuristic or principle for choosing $P$ on new tasks, nor does it analyze the information-theoretic bottleneck that $P$ creates. A practitioner must either replicate the paper's grid search (expensive) or hope that the reported optimal $P$ values transfer to their domain. Future work on dynamically adaptive patch sizes — where the model learns to group bytes into variable-length patches based on content — would directly address this limitation, but the paper does not suggest this direction.

### 6.4 The Paper Evaluates Only Density Estimation (bpb), Not Generation Quality, Limiting Evidence That MEGABYTE Is Useful for Generative Applications

**The assumption or constraint:** All quantitative results in the paper use bits-per-byte (bpb) as the sole evaluation metric. bpb measures how well the model predicts held-out data — density estimation quality. The paper claims MEGABYTE enables "tokenization-free autoregressive sequence modeling at scale" and discusses generation speed (Section 3.2, Table 6), but provides no evaluation of generated sample quality for any modality.

**The consequence:** Density estimation and generation quality are correlated but distinct properties. A model can achieve low perplexity while producing samples that are repetitive, lack diversity, or suffer from exposure bias (the train-test mismatch between teacher-forced training and autoregressive generation). This is particularly relevant for MEGABYTE because its hierarchical architecture introduces a specific potential failure mode: the global model runs once per patch and provides a fixed context vector to the local model for all $P$ byte predictions within that patch. During generation, errors in the global model's patch representation affect all $P$ bytes in the patch — a single mistake could produce a cascade of errors within the patch that the local model cannot recover from, since it has no mechanism to request an updated global context mid-patch. This exposure bias (teacher forcing during training uses ground-truth previous patches; generation uses model-predicted previous patches) may be more severe for MEGABYTE than for standard transformers because errors propagate at two timescales.

For image generation, a model with low bpb might still produce images with unnatural textures, global incoherence, or mode collapse — problems that would be visible in FID or Inception Score metrics but invisible in bpb. For audio, low bpb says nothing about whether generated audio sounds natural, is free of artifacts, or maintains temporal consistency beyond what bpb captures. The paper's audio section (Section 7) is particularly affected: without any qualitative examples or perceptual metrics, it is unclear whether MEGABYTE's simplified byte-level audio modeling (avoiding µ-law companding, etc.) actually produces listenable audio.

**What evidence exists in the paper:** None. The paper provides zero generated samples (text, image, or audio), zero qualitative analysis of model outputs, and zero evaluation using generation-quality metrics (FID, IS, MOS, human evaluation). The only generation-related result is the speed measurement in Table 6, which measures how quickly the model produces bytes, not whether those bytes form coherent outputs.

**Mitigation status:** Not addressed at all. The paper frames itself as a density estimation and architecture contribution, not a generative modeling paper, which is a defensible scope. However, the claims about "modeling audio from raw files" (Section 7) and the emphasis on generation speed (Section 3.2, Table 6) strongly imply generative applications. The abstract's statement that results "establish the viability of tokenization-free autoregressive sequence modeling at scale" would be substantially weakened if the model produced poor samples despite good bpb. This is a significant evidence gap that limits the paper's practical impact for practitioners interested in generation (as opposed to, say, using bpb as a compression metric or a pretraining objective for downstream fine-tuning).

### 6.5 The Architecture Has Not Been Demonstrated at the Scale of Contemporary Large Language Models (100B+ Parameters), and Scaling Behavior Is Extrapolated Rather Than Measured

**The assumption or constraint:** The largest MEGABYTE model trained in the paper has a 2.7B-parameter global model and a 350M-parameter local model (Image64, Table 4) — total ~3B parameters. Most experiments use models in the 100M–1.5B parameter range (Tables 2, 5, 12). The paper's efficiency analysis (Figure 3) extrapolates to 173B parameters, but no model of that scale is trained or evaluated. The paper acknowledges this explicitly: "the scale of experiments here is far below those of state-of-the-art language models (Brown et al., 2020), and future work should explore scaling MEGABYTE to much larger models and datasets" (Section 10).

**The consequence:** Several of MEGABYTE's claimed advantages may not extrapolate to the 100B+ parameter regime where contemporary LLMs operate:

- **Feedforward vs. attention cost ratio:** The paper's central argument — that feedforward layers dominate and attention is negligible — relies on the GPT-3 architecture where attention is 1.4% of FLOPs. This ratio depends on the sequence length relative to the hidden dimension. At very large model sizes, hidden dimensions grow (4096 to 8192 to 16384+), making attention more expensive in absolute terms, potentially shifting the bottleneck back toward attention even if feedforward remains dominant. Additionally, inference-time deployment of very large models often uses memory bandwidth-bound hardware configurations where the exact FLOP breakdown matters less than memory access patterns.

- **Global vs. local model capacity allocation:** The paper finds that a larger global model improves performance (Table 10), but the optimal ratio of global to local capacity at 100B+ scale is unknown. If the global model needs to be, say, 90% of total parameters to be effective at very long contexts, then the local model's capacity is squeezed, potentially harming within-patch byte-level prediction quality. Conversely, if the local model needs more capacity at scale, the efficiency advantage shrinks.

- **Training stability:** The paper mentions using a specific weight initialization (truncated normal with std 0.006) that provided "substantial gain in both training stability and performance" (Appendix A.1). This suggests MEGABYTE is sensitive to initialization, and it is unknown whether the same recipe works at 100B+ scale or whether new stability issues emerge from the two-level architecture.

- **Distributed training dynamics:** MEGABYTE's two-model architecture creates a different communication pattern than a flat transformer — the global model's output for patch $k$ must be communicated to the local model processing patch $k$, which may sit on a different device in a model-parallel setup. The paper uses FairScale's fully sharded data parallelism, which treats the entire model as a single unit. At 100B+ scale, sophisticated 3D parallelism (data, tensor, pipeline) is typically required, and MEGABYTE's two-level structure may interact poorly with pipeline parallelism (where different stages of the network sit on different devices and the global-to-local boundary could create pipeline bubbles).

**What evidence exists in the paper:** The FLOP analysis in Figure 3 extrapolates to 173B parameters, but this is purely theoretical (using the Kaplan et al., 2020 approximations) and does not account for training stability, communication, or memory constraints. The scaling experiment on text (Table 3) uses models at the ~1B scale trained for 400B bytes — far below the trillions of tokens used for state-of-the-art LLMs. No experiment demonstrates that MEGABYTE's advantages hold or grow with scale.

**Mitigation status:** The paper is transparent about this limitation in Section 10, explicitly calling for future work on scaling. The FLOP analysis in Section 3.1 and Figure 3 provides theoretical reason to believe the advantages will persist at scale, but theory and practice often diverge at extreme scales (as the history of large model training demonstrates — predicted scaling laws frequently break at new scale regimes due to unforeseen bottlenecks). A practitioner considering MEGABYTE for a large-scale deployment would need to conduct their own scaling experiments, with no guidance from the paper on what to expect.

### 6.6 Byte-Level Text Modeling Incurs a Computational Overhead That Is Incompletely Characterized and May Be Prohibitive for Some Deployment Scenarios

**The assumption or constraint:** MEGABYTE operates on raw bytes, which means the sequence length for text is approximately 4× longer than for subword-tokenized text (since a typical subword token is ~4 bytes). The paper argues that MEGABYTE's architectural efficiency compensates for this length increase — the global model processes $T/P$ patches rather than $T$ bytes, and $P=8$ provides a roughly 2× length reduction relative to raw bytes, meaning the global model's sequence length is still about 2× longer than a subword model's sequence. The paper does not provide a direct FLOP-matched or latency-matched comparison between a MEGABYTE byte-level model and an equivalently performant subword model.

**The consequence:** A practitioner choosing between deploying a MEGABYTE byte-level model and a standard subword model must weigh the benefits of tokenization-free modeling against a potentially large computational overhead that the paper incompletely characterizes.

The overhead arises from several sources:
- **Local model cost:** The local model runs $P$ times per global model step and contributes $2T m_l$ FLOPs (where $m_l$ is the local model's parameters). For the PG-19 scaling configuration (Table 3: 758M global, 262M local), this is not negligible — the local model has 262M parameters applied at every byte position, which is comparable to a medium-sized standard transformer. In contrast, a subword model does not have this additional per-token cost.
- **Sequence length for the global model:** With patch size $P=8$ and a subword compression ratio of ~4×, the global model's sequence length $(T/4)/8 = T/32$ for subword-equivalent text coverage, versus $T/4$ for a subword model — actually *shorter* by 8×. However, the global model's dimension is $P \cdot D_G$, which is $P$ times larger than the byte-level dimension. For $P=8$ and $D_G$ comparable to a subword model's hidden dimension, the global model's per-layer compute is roughly $P^2$ larger in the feedforward layers (since FFN cost scales as $d_{\text{model}} \cdot d_{\text{ff}} \approx d_{\text{model}} \cdot 4 d_{\text{model}}$). So while the sequence is shorter, the per-position cost is much higher. The net effect on total FLOPs depends on the specific $P$, $D_G$, and the relative sequence lengths, and the paper does not provide this comparison for equivalent-quality models.
- **Memory for patch representations:** The patch embedder produces vectors of dimension $P \cdot D_G$ for the global model. For $P=8$ and $D_G=2048$, each patch representation is 16,384-dimensional — substantially larger than a typical subword model's token embedding. This increases activation memory for the global model's layers, potentially limiting batch size or maximum sequence length.

The paper reports that MEGABYTE achieves 36.4 test perplexity on PG-19 versus 28.9-33.6 for subword models (Table 3) — a remaining 1.08-1.26× perplexity multiplier. It is unknown how much additional compute (or model scale) would be needed to close this gap completely, and whether the tokenization-free benefits justify that compute premium.

**What evidence exists in the paper:** The paper provides compute-matched comparisons against *byte-level* baselines (Tables 2, 3, 5) but never a compute-matched comparison against a *subword* model. The subword results in Table 3 are from other papers with different training budgets. The paper acknowledges this confound but does not remedy it. The FLOP analysis in Section 3.1 and Figure 3 compares against byte-level transformers and linear transformers, not against subword models. The generation speed comparison (Table 6) compares a byte-level MEGABYTE against a byte-level transformer — a subword model would generate tokens ~4× slower in terms of *tokens per second* but might produce equivalent text faster in terms of *characters per second*, depending on the relative overheads.

**Mitigation status:** Not addressed. The paper frames tokenization elimination as a major motivation (Section 1, Section 9) but does not provide the head-to-head comparison that would allow a practitioner to assess the cost of achieving tokenization-free modeling. A reader is left to extrapolate from the subword results in Table 3 (which the paper acknowledges are confounded by training budget) and the MEGABYTE-vs-transformer byte-level comparisons, without a clear picture of the byte-level premium. This is the most significant missing experiment for the paper's central narrative about tokenization elimination.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

This paper introduces a **diagnostic reframing** rather than a single new technique: it identifies that the dominant computational bottleneck in large autoregressive transformers is not self-attention (which the field had spent years optimizing) but rather the position-wise feedforward layers that consume >98% of FLOPs in models like GPT-3. This reframing matters because it changes *which problem researchers should be working on*. Prior to MEGABYTE, the long-sequence transformer literature was overwhelmingly attention-centric — Sparse Transformers, Reformer, Linear Transformers, Performer, Routing Transformers, Longformer, and dozens of other methods all led with the quadratic cost of self-attention as the problem to be solved. MEGABYTE demonstrates that even if attention were made free, the feedforward cost would still dominate at large model sizes, and that attacking *both* costs simultaneously through hierarchical decomposition is a qualitatively different — and more effective — approach.

This shift is analogous to the memory wall in computer architecture: when memory latency became the binding constraint, optimizing instruction throughput provided diminishing returns. Similarly, MEGABYTE's analysis (Figure 3, Section 3.1) implies that the entire efficient-attention research program, while not worthless, addresses a secondary bottleneck. The paper does not merely claim this — it provides the FLOP decomposition to support it (Section 3.1: "self-attention computation accounts for only 1.4% of FLOPS" in GPT-3) and validates it empirically through the generation speed result (Table 6: a 1.5B-parameter MEGABYTE generates 40% faster than a 350M-parameter transformer, demonstrating that reducing per-position computation — not just per-position attention — is what improves latency).

**Reconciling prior contradictions.** The paper resolves a tension in the efficient-transformers literature between methods that work in theory and those that work in practice. Linear attention mechanisms (Katharopoulos et al., 2020; Choromanski et al., 2020) provably reduce attention complexity but "we are not aware of competitive results on large scale language modeling tasks" (Section 3.1). The paper's feedforward-centric diagnosis explains this: linear attention addresses 1.4% of the problem. Perceiver AR (Hawthorne et al., 2022) — the strongest prior general-purpose autoregressive long-context model — does compress the sequence (via cross-attention into a latent bottleneck), but it still applies large feedforward layers at every latent position and cannot model the million-token sequences that MEGABYTE handles in a single forward pass (Table 5). MEGABYTE's hierarchical decomposition explains *why* these prior methods underperform: they leave the feedforward bottleneck largely intact.

The paper also reconciles the separate traditions of encoder patchification (ViT, CANINE) and efficient decoder design. Patchification had been successfully applied in encoder architectures but "cannot be naively applied to decoder-only models without leaking information to future bytes in the same patch" (Section 9). MEGABYTE shows how to generalize the idea to decoders through the combination of causal offset (the global model sees one patch behind the patch being predicted) and autoregressive within-patch modeling (the local model). This bridges a gap that had prevented encoder efficiency techniques from transferring to the decoder setting where most large language models operate.

**Research directions that become more attractive.** The paper makes **hierarchical, multiscale architectures** the central research direction for long-sequence modeling — not as one option among many, but as the natural consequence of the feedforward bottleneck diagnosis. Any architecture that can shift expensive computation from the fine timescale (individual bytes or tokens) to a coarser timescale (patches, chunks, or latent segments) will see proportional efficiency gains. This encompasses not just MEGABYTE's specific two-level design but more general hierarchical decompositions with learned rather than fixed patch boundaries, with more than two levels of hierarchy, or with adaptive allocation of capacity across timescales. The paper's Table 7 (ablation showing both global and local models are critical) and Table 10 (larger global-to-local ratio improves performance) provide empirical grounding for this direction.

The paper also makes **verifier or critic models for patch-level decisions** more attractive, though it does not use this language. The global model functions as a context provider for the local model — it makes coarse decisions (what kind of content should appear in this patch?) that the local model refines into byte-level predictions. This is structurally analogous to a critic providing a value function for an actor, and the paper's architecture could be extended to allow the global model to condition on feedback from the local model (e.g., the local model's uncertainty within a patch could signal the global model to provide more detailed context for the next patch). The paper does not explore this, but the architecture naturally supports it.

**Research directions that become less attractive.** Pure attention-efficiency approaches — sparse attention, linear attention, kernel approximations — become harder to justify as the *primary* solution to long-sequence modeling, given the paper's evidence that they address a small fraction of total compute. These methods may still be useful as components within hierarchical architectures (the global model could use sparse attention internally to further reduce its cost), but as standalone solutions they cannot match the efficiency gains of reducing per-position feedforward computation. The paper does not argue these methods are useless — it uses dense attention itself — but it shifts their status from "the solution to long sequences" to "a secondary optimization within a hierarchical framework."

Tokenization research aimed at better compression (better BPE variants, learned tokenizers, modality-specific compression) becomes somewhat less urgent if byte-level models can achieve competitive performance, though the paper does not close the gap completely. The PG-19 scaling result (36.4 byte-level test perplexity vs. 28.9 for the best subword model; Table 3) leaves room for tokenization to remain relevant, but the trajectory suggests that architectural improvements to byte-level models may eventually eliminate the need for tokenization as a preprocessing step.

### Follow-Up Research This Work Enables

**1. Dynamic, learned patch boundaries instead of fixed-size chunking.** The paper uses fixed-size patches ($P=8$ for text, $P=192$ for images) and demonstrates robustness to this choice (Table 9), but the fundamental limitation is that patch boundaries are arbitrary — a word or semantic unit can be split across two patches, forcing the local model to stitch information across the boundary using only its limited cross-patch attention (which, per Table 7, has minimal or negative impact on text). A natural extension is to make patch boundaries **learned and content-dependent**: the model could predict, at each position, whether to emit a "patch boundary" token, allowing it to segment the sequence into variable-length patches that align with semantic units (words, phrases, or visual motifs). This is architecturally feasible within MEGABYTE's framework — the global model would process a variable number of variable-length patches — and would test whether the fixed-patch robustness in Table 9 is because patch boundaries genuinely don't matter or because the model learns to be invariant to them. A strong experiment would compare fixed-patch MEGABYTE against a dynamic-patch variant on a task requiring cross-patch reasoning (e.g., code completion where variable names span patch boundaries, or morphological inflection where character-level edits cross boundaries), measuring whether dynamic patches improve bpb specifically at patch-adjacent byte positions.

**2. Scaling MEGABYTE to 70B+ parameters on trillion-token datasets, with direct subword-controlled comparison.** The paper's scaling experiment (Table 3) uses models at the ~1B-parameter scale on 400B bytes and acknowledges this is "far below those of state-of-the-art language models" (Section 10). The most important follow-up is a **direct, compute-controlled comparison** between a MEGABYTE byte-level model and a SentencePiece subword transformer at matched FLOPs, matched data, and matched total parameters in the 70B+ regime, trained on 1T+ tokens. This would answer the question the paper leaves open: does the byte-level gap close completely at scale, or is there a fundamental representational disadvantage to bytes that no amount of architectural efficiency can overcome? Concretely, one would train a MEGABYTE with a 65B global model (D=8192, L=80) and a 5B local model (D=2048, L=24), patch size optimized on a validation set, against a 70B standard transformer with a 32k SentencePiece vocabulary, both on the same 1T-token corpus with identical optimizer settings, and report test perplexity on PG-19, Books, and C4. The paper's Table 10 (larger global-to-local ratio improves performance) and Table 3 (36.4 vs. 28.9 gap at 1B scale) provide the motivation and baseline. A negative result — the gap persists or widens — would establish that tokenization provides a representational advantage beyond sequence length compression, likely because subword boundaries provide useful inductive bias. A positive result — the gap closes — would make tokenization elimination a credible path for next-generation LLMs.

**3. Conditional computation within the local model based on prediction difficulty.** The paper observes that "most byte predictions are relatively easy (for example, completing a word given the first few characters)" (Section 1) and that per-token loss increases toward the end of each patch (Figure 5). These observations suggest that the local model's capacity is wasted on easy predictions and insufficient for hard ones. A follow-up could implement **conditional computation** within the local model: early-exit classifiers at each local transformer layer that allow the model to stop computing when the prediction is confident, and additional local layers or a wider dimension that is dynamically activated for difficult byte positions (e.g., the first byte of a new word, or the end of a patch where global context is stale). This would be evaluated by measuring the average number of local layers used per byte position versus the fixed-depth baseline, and whether the saved FLOPs can be reallocated to the global model or to additional training data within the same compute budget. The paper's strided inference result (Table 8: 0.9079 → 0.8926 bpb at 2× cost) provides evidence that the within-patch loss degradation is real and addressable; conditional computation would attack it more efficiently than double-inference.

**4. Cross-modal pretraining with a single byte-level MEGABYTE on text, images, and audio jointly.** The paper demonstrates MEGABYTE on text (Table 2), images (Table 5), and audio (Section 7) but trains separate models for each modality. A significant test of the "tokenization-free autoregressive sequence modeling" vision would be to train a **single MEGABYTE model** on a mixture of text documents, image files (as raw PNG or JPEG byte streams), and audio files (as raw WAV byte streams), with modality indicated by a special prefix byte sequence. This would test whether the hierarchical architecture can learn shared representations across modalities without any modality-specific preprocessing. The key question is whether the global model learns to represent cross-modal concepts (e.g., "a description of a dog in text" and "pixels of a dog in an image" sharing similar patch-level representations) or whether the modalities remain segregated. The experiment would require careful patch size selection — since optimal $P$ differs across modalities (8 for text, 192 for images, 32 for audio; Tables 2 and 5, Section 7) — and might benefit from modality-adaptive patch sizes. A positive result (cross-modal transfer improves perplexity on each individual modality compared to single-modality training) would be strong evidence that byte-level modeling enables unified multimodal learning without the information loss of modality-specific tokenizers. A negative result (modalities interfere or the model fails to learn) would establish boundaries on the unified-byte-modeling vision and suggest that some modality-specific inductive bias is necessary.

**5. Understanding and mitigating exposure bias in hierarchical autoregressive models.** MEGABYTE's two-level autoregressive structure introduces a specific exposure bias problem not present in flat transformers. During training, the local model receives global context computed from *ground-truth* previous patches (teacher forcing). During generation, the local model receives global context computed from *model-generated* previous patches. Errors in the global model's patch representation affect all $P$ bytes in the patch, because the local model has no mechanism to request updated global context mid-patch. A follow-up could measure the severity of this exposure bias by comparing MEGABYTE's perplexity under teacher forcing versus under **scheduled sampling** (where the global model is trained on a mixture of ground-truth and model-generated previous patches) or by measuring the **perplexity gap** between teacher-forced evaluation and autoregressive generation at various sequence lengths. This would determine whether the bpb results reported in the paper overstate MEGABYTE's generative performance. If the gap is large, architectural mitigations could include: allowing the local model to emit a "request global context update" signal mid-patch, having the global model process overlapping patches, or training the global model with dropout on its input patch representations to simulate generation-time uncertainty.

**6. Direct comparison against sparse feedforward methods (mixture-of-experts, dynamic width) that also reduce per-position computation.** The paper argues that MEGABYTE's key advantage is reducing per-position feedforward cost by shifting computation to the patch level. But there exist alternative methods for reducing per-position feedforward cost that do not require hierarchical decomposition — most notably **mixture-of-experts (MoE)** layers, where only a subset of feedforward parameters are activated per token, and **dynamic width networks** that adjust layer width based on input complexity. A critical stress-test of the feedforward-centric diagnosis would be a compute-controlled comparison between MEGABYTE and a standard transformer with MoE feedforward layers (e.g., Switch Transformer architecture), where the MoE model uses a comparable total parameter count but only activates a fraction per token. If the MoE transformer matches or exceeds MEGABYTE's performance at equivalent FLOPs, it would suggest that the feedforward bottleneck can be addressed without hierarchical decomposition — undermining MEGABYTE's central motivation. If MEGABYTE outperforms MoE at matched compute, it would strengthen the case that hierarchical decomposition provides benefits beyond simple per-position FLOP reduction (e.g., the coarse structure helps with long-range dependency learning). This experiment would use the same text datasets (PG-19, arXiv) with models at the 1B-parameter scale, matching total training FLOPs and comparing bpb. The paper's FLOP analysis (Section 3.1, Figure 3) provides the theoretical framing, but no MoE comparison exists in the current work.

### Practical Applications and Downstream Use Cases

**1. Cost-efficient pretraining of byte-level language models for multilingual or code-heavy deployments.** An organization training a language model for a deployment where the input distribution includes many languages, code, and formatted text (e.g., a documentation assistant, a code completion service, or a multilingual chatbot) currently must either train separate tokenizers per language (fragile, complex preprocessing) or use a single multilingual tokenizer that allocates vocabulary unevenly across languages (degrading performance on low-resource languages). MEGABYTE's byte-level modeling eliminates this problem entirely — the "vocabulary" is always 256 bytes regardless of language, and the model learns language-appropriate subword patterns internally through the local model. The paper's text results (Table 2: MEGABYTE outperforms byte-level baselines on all five text datasets including code and multilingual arXiv) and scaling experiment (Table 3: 36.4 test perplexity, competitive with subword models) suggest this is feasible today at moderate scale. The 40% generation speedup (Table 6) makes deployment latency competitive. An organization could pretrain a MEGABYTE model on a multilingual corpus at, say, 7B total parameters (6B global, 1B local) for the cost of a comparable-quality 2-3B subword model, benefiting from simplified preprocessing and uniform performance across languages, with generation latency comparable to or better than the subword alternative.

**2. High-resolution image density estimation for compression, anomaly detection, or out-of-distribution detection.** MEGABYTE's ability to process million-byte image sequences in a single forward pass (Table 5: 2.282 bpb on ImageNet 640×640, outperforming Perceiver AR's 2.345) makes it directly applicable to tasks requiring whole-image likelihood estimation at resolutions where prior autoregressive models required segmenting the image (losing global context). Use cases include: **lossless or near-lossless image compression** using the model's byte-level probability estimates as an entropy coder (lower bpb → better compression); **anomaly detection** in medical imaging or manufacturing, where images with unusually high bpb under a model trained on normal examples are flagged; and **out-of-distribution detection** for deployed vision systems, where inputs from a shifted distribution receive lower likelihood. The practical advantage over prior methods is that MEGABYTE can process the full high-resolution image without tiling artifacts — for a 640×640 medical image, a standard transformer with context 1024 would need to process the image in ~1200 segments, losing cross-segment context for detecting anomalies that span segments. MEGABYTE processes all 1.2M bytes jointly (Table 5). The paper's demonstration that MEGABYTE matches state-of-the-art density estimation at half the training cost on ImageNet 64×64 (Table 4: 3.40 bpb) provides confidence that the approach scales to production-useful quality.

**3. Efficient on-device audio processing with simplified modeling pipelines.** The paper's audio experiments (Section 7) demonstrate that MEGABYTE can model raw 16-bit audio as byte sequences without the specialized preprocessing that prior neural audio models require — no μ-law companding (van den Oord et al., 2016), no discretized mixture of logistics (Salimans et al., 2017), no dual softmax (Kalchbrenner et al., 2018). This simplification has practical value for **on-device audio applications** (voice assistants, hearing aids, real-time audio enhancement) where model complexity and preprocessing code footprint are constrained. The paper achieves 3.477 bpb on a 2TB audio dataset with a MEGABYTE model (350M global, 125M local; Table 7) processing 524,288 bytes per sequence with patch size 32. For a 16kHz, 16-bit audio stream, this corresponds to 32k bytes per second, meaning the model's context window covers ~16 seconds of audio — sufficient for many real-time processing tasks. The byte-level approach means the same model architecture can process audio from different sample rates or bit depths without architecture changes (just retraining), unlike models with fixed input preprocessing pipelines. A production deployment could use a smaller MEGABYTE (e.g., 50M parameters total, processing 1-second audio chunks) on-device with the simplified byte-level pipeline, reducing engineering complexity and maintenance burden compared to models with modality-specific frontends.

**4. Unified multimodal pretraining data pipelines for foundation model training.** Large-scale multimodal model training (e.g., training a single model on text, images, and audio) currently requires separate preprocessing pipelines: text tokenizers, image patchifiers or VQ-VAE encoders, audio compression and discretization — each with modality-specific hyperparameters, each losing information, and each requiring engineering effort to maintain. MEGABYTE offers a path to **unified preprocessing**: read any file as bytes, embed each byte, and train. This is not yet demonstrated in the paper (models are trained separately per modality), but the consistent architecture across text (Tables 2, 3), images (Tables 4, 5), and audio (Section 7) — with the same codebase, same optimizer, same byte-level input representation — makes unified training an incremental engineering step rather than a research problem. The practical benefit is reduced pipeline complexity: one codebase, one preprocessing step (`open(file, 'rb').read()`), one model architecture, one set of hyperparameters. For an organization training multimodal models at scale, this could substantially reduce the engineering overhead of maintaining modality-specific pipelines and the risk of pipeline mismatches causing subtle bugs. The paper's demonstration that the architecture is "robust to other modifications" (Table 7, Section 8.5) suggests that a single patch size and model configuration could work across modalities with acceptable performance, though modality-optimal patch sizes differ (8 for text, 192 for images, 32 for audio), so some modality-specific tuning would still be needed for best results.
