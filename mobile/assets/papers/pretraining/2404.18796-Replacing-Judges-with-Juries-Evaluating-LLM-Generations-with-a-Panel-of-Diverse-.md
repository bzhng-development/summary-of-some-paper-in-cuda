# Replacing Judges with Juries: Evaluating LLM Generations with a Panel of Diverse Models

**ArXiv:** [2404.18796](https://arxiv.org/abs/2404.18796)

## 🎯 Pitch

This paper proposes evaluating LLM generations using a **Panel of LLm evaluators (PoLL)** — a diverse set of smaller models from different families whose judgments are pooled, rather than relying on a single large judge like GPT-4.

---

## 1. Executive Summary

This paper proposes evaluating LLM generations using a **Panel of LLm evaluators (PoLL)** — a diverse set of smaller models from different families whose judgments are pooled, rather than relying on a single large judge like GPT-4. Across three settings (single-hop QA, multi-hop QA, and Chatbot Arena) spanning six datasets, a PoLL composed of Command R, Claude-3 Haiku, and GPT-3.5 achieves stronger correlation with human judgments than GPT-4 alone while reducing intra-model bias (the tendency of evaluators to favor outputs from their own model family) and costing over seven times less. The work establishes that a heterogeneous panel of smaller models can outperform a single large evaluator across multiple settings, with the benefits holding consistently even as individual judges exhibit high variance under prompt changes.

## 2. Context and Motivation

### The Core Problem: Our Evaluation Methods Have Not Kept Pace With Model Capabilities

The fundamental challenge this paper addresses is a mismatch between how good LLMs have become at generating free-form text and how poorly we can evaluate that text. As the authors state in their opening line:

> "As Large Language Models (LLMs) have become more advanced, they have outpaced our abilities to accurately evaluate their quality."

This is not merely an academic inconvenience — it is a bottleneck that affects the entire field's ability to make progress. If you cannot reliably measure whether model A is better than model B, you cannot make informed decisions about which architecture to use, which training recipe to adopt, or which model to deploy in production. The evaluation gap means that much of the field's claimed progress rests on shaky methodological foundations.

The paper identifies two distinct challenges within the broader evaluation problem:

**Challenge 1: Finding meaningful probing data.** It is difficult to construct datasets that actually test the capabilities we care about, rather than testing something adjacent that happens to be easier to measure. Multiple-choice benchmarks like MMLU (Hendrycks et al., 2020) became popular precisely because they sidestep the problem of evaluating free-form text — you just check whether the model picked option C. But as the authors note, multiple-choice questions are "in many ways probing a different property than that of a free-form generative task, which is oftentimes closer to the downstream use-case." In other words, being good at multiple-choice tests does not necessarily mean being good at the open-ended generation tasks that users actually want LLMs to perform.

**Challenge 2: Evaluating the correctness of free-form generation.** Even when you have a good question, determining whether the model's answer is correct turns out to be surprisingly hard. This is the challenge the paper focuses on.

### Why Traditional Metrics Fail

The paper illustrates the inadequacy of traditional automatic metrics through concrete examples drawn from question answering (QA), a domain where "correctness" seems like it should be straightforward to assess.

**Heuristic string-matching metrics** such as Exact Match (EM), BLEU (Papineni et al., 2002), and ROUGE (Lin, 2004) are the traditional workhorses of NLP evaluation. In QA, the standard approach is to compare the model's generated answer against a set of reference answers using normalized string matching. The paper identifies two systematic failure modes:

Let's consider each. A **false positive failure** occurs when EM declares a match but the answer is actually wrong — for example, when the model's output contains the reference answer string by coincidence through "superfluous token overlap" rather than because it arrived at the correct answer through genuine reasoning. An answer like "The capital of France is not Paris, it is Lyon" would technically contain the reference string "Paris" and might pass a naive containment-based EM check, even though the model has fundamentally failed to answer the question correctly.

A **false negative failure** — which the authors identify as the more common problem — occurs when EM declares a mismatch but the answer is actually correct. The paper provides several examples that will resonate with anyone who has worked on QA evaluation:

> "QA metrics... invariably lead to... false negatives due to an incomplete set of gold reference answers (e.g. date format differences, inclusion of middle initial in person's name, etc.)."

The paper also notes a specific, almost humorous example from their own model evaluations:

> "We found that EM unjustly penalized Command models for a tendency to write in Canadian or British English as QA dataset annotations typically format dates in American MM-DD-YYYY format."

This is a perfect illustration of the problem: a model that answers "15 October 2023" is objectively correct when the reference says "10/15/2023," but a naive string match will mark it wrong. The model is being penalized not for being incorrect, but for using a different but equally valid date format. Multiply this by the thousands of similar surface-form variations (abbreviations, name formats, alternative phrasings, synonyms) that can occur in free-form text, and you have an evaluation methodology that systematically underestimates model performance.

The deeper issue here is that **correctness in free-form generation is fundamentally a semantic judgment, not a syntactic one**. Two text strings can convey identical meaning while sharing few or no words in common. Conversely, two strings can share many words while conveying opposite meanings. String-matching metrics can only operate on the surface form, making them fundamentally incapable of capturing what we actually care about.

### The Rise of LLM-as-Judge and Its Specific Failures

In response to the inadequacy of string-matching metrics, the field has increasingly turned to a seemingly natural solution: **use LLMs themselves to evaluate other LLMs**. The intuition is compelling — if LLMs can understand semantic meaning well enough to generate coherent text, surely they can understand it well enough to judge whether one answer means the same thing as another. Prior work has indeed shown that model-based scoring methods often correlate better with human judgments than heuristic metrics (Bohnet et al., 2022; Zheng et al., 2024), and that strong evaluator models generalize well across different tasks (Huang et al., 2024).

This approach has become extremely popular. The paper describes three common variants:

- **Single-point scoring**: The judge rates the quality of a single model output without any point of comparison, relying on its internal model of what constitutes a good answer.
- **Reference-based scoring**: The judge is given both the model's answer and a gold reference answer, and asked to determine if they match semantically (this is the primary setting in the paper's QA experiments).
- **Pair-wise scoring**: The judge compares two outputs and expresses a preference, often on a multi-point scale (this is the setting used in Chatbot Arena).

Within this LLM-as-judge paradigm, the dominant practice has been to use the single largest, most capable model available — typically GPT-4 — as the evaluator. This choice seems natural: if you want reliable judgments, use the smartest model you can find. As the paper notes, this has become the default:

> "it is most common to use the largest, most universally capable models as evaluators, which is both slow and costly, limiting applicability and access."

However, the paper identifies three specific problems with the single-large-judge approach, each of which motivates a different aspect of their proposed solution.

#### Problem 1: Intra-Model Bias

The most insidious problem is that **evaluator models prefer their own outputs**. This is not a subtle effect — it is a systematic bias that can fundamentally distort model rankings. The paper cites Panickssery et al. (2024), who demonstrated that "LLM evaluators recognize and favor their own generations." When GPT-4 is the judge, GPT-4-family outputs get an unfair advantage. When Claude is the judge, Claude-family outputs get the boost.

This makes intuitive sense when you think about how LLMs work. A model trained to produce text in a certain style, with certain patterns of reasoning and certain vocabulary preferences, will naturally find outputs from similar models more "natural" or "correct-looking." The evaluator is not making an objective assessment of correctness — it is making an assessment colored by its own training distribution, which happens to overlap more with models from the same family.

The practical consequence is severe: if you use a single-model judge, **your model rankings may reflect the judge's familial affiliations rather than genuine quality differences**. A model that is objectively worse could rank higher simply because it happens to share lineage with the evaluator. This undermines the entire purpose of evaluation.

#### Problem 2: High Variance Under Prompt Changes

The paper discovers, through their own experiments, that GPT-4's performance as a judge is surprisingly unstable. When they systematically varied the prompt given to GPT-4 for the same evaluation task (judging answer correctness on Natural Questions), they observed substantial swings in agreement with human judgments. As shown in Table 3 (discussed in detail in Section 4.3), Cohen's κ with human judgments varied from 0.518 (zero-shot) to 0.725 (with explicit "don't overthink" instructions) depending purely on how the task was described to the model.

This is troubling because it means that **reported evaluation results may depend as much on prompt engineering as on actual model quality**. Two research groups evaluating the same models on the same data with the same GPT-4 judge could reach different conclusions simply because they worded their judge prompt slightly differently. This makes evaluation results fragile and difficult to reproduce.

More subtly, the paper observes that GPT-4 — despite being the "most powerful" judge model tested — actually performed worse than less capable models on what is essentially a semantic matching task. They hypothesize:

> "GPT-4 is over-reasoning and injecting too much background knowledge into determining the correctness of an answer rather than simply aligning the gold reference with the generation."

This is a fascinating observation: the very capability that makes GPT-4 powerful (its ability to reason deeply about text) may actually make it a worse judge for certain tasks, because it cannot resist going beyond the simple matching task it was asked to perform. A "dumber" model that just does what it is told — check if the reference answer's meaning appears in the generated answer — may actually be more reliable.

#### Problem 3: Cost and Access

The final problem is more pragmatic but equally important for the research community. Using GPT-4 as a judge is expensive. The paper reports that at the time of writing, GPT-4 Turbo costs $10 per million input tokens and $30 per million output tokens. For large-scale evaluations involving thousands or tens of thousands of examples, these costs add up quickly. This creates a barrier to entry: well-resourced labs can afford comprehensive LLM-based evaluation, while smaller labs, independent researchers, and practitioners in resource-constrained settings cannot.

Additionally, cost is not just about money — it is about environmental impact and computational resource consumption. Running the largest models for evaluation purposes consumes significant energy, and if smaller models can do the job equally well or better, there is a sustainability argument for using them.

### How This Paper Positions Itself

The paper frames its contribution not as a completely new evaluation paradigm, but as a **correction to the default practice within the existing LLM-as-judge paradigm**. The key insight is that the field has made an implicit assumption — that the best evaluator is the single most capable model — and this assumption is wrong in ways that matter.

The authors draw an explicit analogy to a well-established practice in human evaluation: **pooling multiple annotators to reduce individual bias and variance**. As they note:

> "Similar pooling techniques are used to reduce variance in human annotations by normalizing out both natural variation in human judgements caused by their own subjective biases as well as human error."

When humans evaluate something subjective — relevance of a search result, quality of a translation, correctness of an answer — we never rely on a single judge. We use multiple annotators and aggregate their judgments, because we know that every individual annotator brings their own biases, blind spots, and inconsistencies. The aggregated judgment is more reliable than any individual judgment. The paper's proposal is simply to apply the same logic to LLM evaluators.

The innovation is not in the idea of aggregation per se (prior work by Li et al., 2023 had explored using multiple judges, though only with large models on pair-wise evaluations), but in the specific composition of the panel. By deliberately drawing judges from **disparate model families** — Command R (Cohere), Claude-3 Haiku (Anthropic), and GPT-3.5 (OpenAI) — the panel is designed to have **non-overlapping biases**. A bias that affects one judge (say, GPT-3.5's preference for GPT-family outputs) is unlikely to be shared by the other two judges from different families, so it gets washed out in aggregation.

This is a fundamentally different philosophy from the single-large-judge approach. Rather than trying to find one perfect, unbiased evaluator (which may not exist), the panel approach accepts that every evaluator is biased and instead uses diversity as a mechanism for **canceling out** those biases. This is the same logic that underlies ensemble methods in machine learning more broadly: individual models may be weak or biased, but a diverse ensemble can be stronger than any single model, including models that are individually more capable than any ensemble member.

The paper's positioning is therefore: **we are not replacing LLM-as-judge — we are fixing how it is done**. The default approach (single large judge) has specific, identifiable failure modes (intra-model bias, prompt sensitivity, cost), and a heterogeneous panel directly addresses each of these failures through a different mechanism: diversity cancels bias, pooling reduces variance, and smaller models reduce cost.

## 3. Technical Approach

### 3.1 Reader Orientation

The paper proposes a system for **evaluating LLM-generated text by replacing a single evaluator model (the "judge") with a diverse panel of smaller evaluator models whose individual judgments are pooled together**. The core insight is that every individual LLM evaluator carries its own biases — particularly a preference for outputs from its own model family — and that these biases can be **canceled out through aggregation across evaluators from disparate model families**, producing a final score that correlates better with human judgment than any single evaluator, including much larger and more expensive ones like GPT-4.

### 3.2 Big-Picture Architecture (Diagram in Words)

The PoLL system has four major components:

1. **Individual Evaluator Models (the Panel Members)** — Three LLMs drawn from different model families (Command R, Claude-3 Haiku, GPT-3.5), each of which independently scores a given model output according to the same task-specific judging protocol.
2. **Judging Protocol** — The prompt template and scoring format that defines the evaluation task (reference-based binary scoring for QA, pair-wise comparison for Chatbot Arena).
3. **Voting Function** — A rule for combining the individual scores from each panel member into a single final score. For binary judgments (QA), this is max voting (any judge saying "correct" yields a "correct" final answer); for scalar judgments (Chatbot Arena), this is average pooling.
4. **Calibration Reference** — Human annotations used as ground truth for measuring how well each judge (or panel) correlates with human judgment, measured via Cohen's κ for binary tasks and Pearson/Kendall-Tau correlation for rankings.

Information flows as follows: a model-generated answer enters the system → each of the three panel members independently scores it using the same prompt template → the individual scores (binary "True"/"False" or scalar 1–5) are aggregated by the voting function → the pooled score is the final evaluation. This pooled score is then compared against human judgments to measure correlation, and against GPT-4's judgments to measure improvement.

### 3.3 Roadmap for the Deep Dive

- **First**, the formal definition of PoLL scoring — what the voting function computes and why the specific form matters for bias cancellation.
- **Second**, the panel composition — which models are chosen, from which families, and the deliberate design principle of family-heterogeneity that underlies the selection.
- **Third**, the three distinct judging protocols — how the evaluation task differs across single-hop QA, multi-hop QA, and Chatbot Arena, and how PoLL adapts to each through prompt templates and voting functions.
- **Fourth**, the prompt engineering for judges — the few-shot example construction, the instruction design, and the GPT-4 prompt optimization experiments that reveal sensitivity to wording.
- **Fifth**, the human annotation pipeline — how ground-truth judgments were collected, the annotator demographics, the single vs. triple annotation design, and why this matters for measuring judge quality.
- **Sixth**, the bias measurement methodology — how intra-model bias is operationalized and quantified, by comparing each judge's deviation from human judgments as a function of which model's outputs are being evaluated.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily an **empirical methods paper** whose core idea is that a heterogeneous panel of smaller evaluator models, when aggregated through simple voting, can outperform a single large evaluator on correlation with human judgments while reducing intra-model bias and cost. The technical approach consists of a specific panel instantiation, a set of judging protocols adapted to different evaluation settings, and a measurement framework for quantifying judge quality.

#### The PoLL Scoring Function: Aggregating Heterogeneous Judgments

The central computational operation in PoLL is the aggregation of individual judge scores into a panel-level score. The paper defines this through a voting function that operates on a set of independent evaluations.

For a given model output $a$ and a panel $P$ composed of individual judges $j_1, j_2, ..., j_k$, each drawn from a different model family, the PoLL score is:

$$\text{PoLL}(a) = f(\{j(a) : j \in P\})$$

where $j(a)$ is the score produced by judge $j$ on output $a$, and $f$ is the voting function — either max pooling or average pooling depending on the judgment type.

**What it computes:** The function takes a set of $k$ independent judgments from $k$ different evaluator models, all applied to the same generated answer, and collapses them into a single scalar or binary decision. For binary judgments (where each $j(a) \in \{\text{True}, \text{False}\}$), max voting returns True if any judge considers the answer correct. For scalar judgments (where each $j(a)$ is a rating on a 1–5 scale), average pooling computes the arithmetic mean of all judge scores.

**Why this form:** The voting function is deliberately simple. The paper's hypothesis is that the benefit of PoLL comes not from sophisticated aggregation but from the **diversity of the panel itself** — the fact that different judges have different, non-overlapping biases. A complex learned aggregation function could potentially learn to upweight judges that happen to match human judgments on a particular dataset, but this would risk overfitting to that dataset's idiosyncrasies and would obscure the paper's central claim: that diversity alone is sufficient. Max voting for binary tasks is conservative (it only requires one judge to recognize a correct answer, which is appropriate when false negatives are the primary concern in QA evaluation). Average pooling for scalar tasks treats all judges as equally informative, which is the simplest assumption consistent with the claim that the panel's collective judgment is better than any individual's.

The paper explicitly states:

> "In this work we consider both max and average pool voting, though other functions could also work well."

This signals that the specific voting function is not the claimed contribution — it is the panel composition.

---

#### Panel Composition: The Principle of Family Heterogeneity

The panel is composed of three models drawn from three different model families, each developed by a different organization:

1. **Command R (CMD-R, 35B parameters)** from Cohere — an open-weight model.
2. **Claude-3 Haiku** from Anthropic — the smallest model in the Claude-3 family (which also includes the larger Sonnet and Opus).
3. **GPT-3.5** from OpenAI — a widely-used model from the GPT family.

The selection is not arbitrary. Each judge comes from a **disparate model family** — meaning the models were developed independently by different organizations with different training data, different architectural choices, different fine-tuning procedures, and different output distributions. This is the critical design principle. The authors state:

> "We construct a PoLL from three models being drawn from three disparate model families."

The rationale is that **intra-model bias is family-specific**. GPT-3.5 prefers GPT-family outputs because it was trained on data that reflects GPT-like generation patterns. Command R prefers Command-R-family outputs for analogous reasons. Haiku prefers Claude-family outputs. When you aggregate across families, these biases point in different directions and tend to cancel out. No single family's preference dominates the final score.

The paper also evaluates models from a fourth family — Mistral (Mistral Large and Mistral Medium) — but does not include them in the panel. Instead, Mistral models serve as an "unaffiliated" test case: models whose outputs are evaluated by the panel but which are not themselves members of any judge family. This allows the paper to test whether bias effects are truly about family membership: if Mistral outputs show no systematic advantage or disadvantage from any particular judge, that supports the claim that bias is family-specific rather than, say, a general preference for certain answer styles.

The panel size (three) is a practical choice. The paper does not claim that three is optimal; the authors explicitly leave "the task of 'panel selection', or identifying the best models to include in PoLL in terms of quality and cost, to future work." The choice of three is likely motivated by a balance between diversity (you want at least a few different families), cost (each additional judge adds inference cost), and the voting dynamics (three judges create a clear majority in binary tasks without ties).

#### Judging Protocol 1: Reference-Based Binary Scoring for QA

In the question answering experiments (both single-hop and multi-hop), each judge is given three pieces of information and asked to produce a binary judgment:

- **The Question** — the original question asked of the model being evaluated.
- **The Provided Answer** — the generated answer from the model being evaluated.
- **The Reference Answer** — the gold-standard correct answer, typically a short string.

The judge must determine whether the Provided Answer is semantically equivalent to the Reference Answer — that is, whether the correct answer information appears somewhere in the generated text. The judge outputs exactly "True" or "False."

The instruction line in the prompt reads:

> "You will be given a Question and a Provided Answer. Judge whether the Provided Answer is correct by comparing it to the Reference Answer. Differently formatted dates, people with missing middle names, and alternative spellings should all be considered the same. If the Provided Answer is correct say exactly "True", otherwise say "False"."

This instruction is carefully designed to address known failure modes of string-matching metrics. It explicitly tells the model to consider surface-form variations (dates, names, spellings) as equivalent, which directly targets the problem identified in the introduction where EM penalizes Canadian date formatting. The instruction essentially asks the judge to perform **semantic containment** — does the meaning of the short reference answer appear within the longer generated answer?

**Few-shot example construction.** The prompts include multiple few-shot examples (8–16, depending on the dataset) showing the judge what constitutes a correct and incorrect answer. The construction of these examples is systematic and dataset-specific. For the KILT datasets, the authors describe a deliberate selection procedure:

> "We therefore create new judgement prompts the following procedure for each of the KILT datasets, randomly sampling a set of labelled fewshot examples from our pool human-labelled examples according to the following constraints: at least 1 annotated positive example from each model family's generations, at least 1 annotated negative example from each model family's generations, at least 1 example where the human disagrees with keyword-based exact match score."

This construction process serves three purposes. First, including both positive and negative examples from each model family ensures that the judge sees the range of answer styles it will encounter — it learns that a verbose Command-R-style answer can be correct, and that a terse GPT-3.5-style answer can be incorrect, and vice versa. Second, including examples where human judgment disagrees with EM teaches the judge that surface-form matching is not the criterion — the judge must look deeper. Third, drawing examples from the pool of human-labeled data ensures that the few-shot examples reflect the same distribution as the test cases.

The number of few-shot examples is determined empirically:

> "We sweep over n shots in {8, 10, 16}, picking the prompt that has strongest agreement on average across all judges for a small held-out portion of human labels."

This means the prompt construction itself involves a small held-out validation step, which is methodologically sound — it avoids contaminating the test set with prompt optimization decisions.

**Dataset-specific prompts.** The paper creates separate prompt templates for each KILT dataset (Natural Questions, TriviaQA, HotpotQA) because the answer styles and question types differ across datasets. The exact prompts are provided in Appendix Tables 11, 12, and 13. Each follows the same structural template — instruction line, followed by numbered question-answer-reference triples with the "Correct: True/False" label, followed by the target question with the label blank for the judge to fill in — but uses different few-shot examples tailored to each dataset's distribution.

#### Judging Protocol 2: Reference-Based Scoring for Multi-Hop QA

The multi-hop QA protocol (Bamboogle and multi-hop HotPotQA) uses reference-based scoring similar to the single-hop case, but with a prompt template that reflects the more complex, multi-step nature of the questions. The prompt in Table 10 follows the same structural pattern but uses examples drawn from the multi-hop setting, where answers tend to be longer and require synthesizing information from multiple retrieval steps.

The multi-hop experiments also involve a more complex answer generation pipeline: models operate as REACT agents (Yao et al., 2022) with a Thought-Action-Observation loop, iteratively calling search tools and reasoning over retrieved documents before producing a final answer. This means the Provided Answers being judged are the outputs of multi-step tool-use processes rather than single-pass generations, which may affect answer verbosity, structure, and error patterns. The paper uses the same reference-based binary scoring protocol regardless, testing whether the PoLL approach generalizes across generation methodologies.

---

#### Judging Protocol 3: Pair-Wise Scoring for Chatbot Arena Hard

In the Chatbot Arena Hard setting, the evaluation task is fundamentally different. Instead of judging whether a single answer matches a reference, the judge compares two model outputs and selects which is better, using a head-to-head comparison framework developed by Li et al. (2024a).

The authors explicitly state that they follow the original implementation exactly:

> "We do not modify the judge prompts in any way from the original implementation."

In this setting, the judge is given a user prompt and two anonymized model responses, and must produce a score on a 1–5 scale indicating which response is better (or if they are approximately equal). The paper treats the crowd-sourced human annotations from Chatbot Arena as ground truth for calculating correlation between evaluator models and human judgments.

The PoLL adaptation for this setting uses **average pooling** rather than max voting because the judgments are scalar (1–5) rather than binary. The paper notes:

> "For Chatbot Arena we instead use average pooling because judgements are scores ranging from 1-5 and a three judge panel often does not produce a clear majority decision."

This is a practical detail: with three judges and a five-point scale, the probability that any two judges produce exactly the same score is low enough that majority voting would frequently fail to produce a decision. Average pooling avoids this issue by treating the panel's collective judgment as a continuous value.

The paper also notes experimentation with a hybrid approach:

> "We also experimented with max voting with average voting fallback which yielded similar results with an identical overall ranking."

This robustness check suggests that the specific aggregation function is not driving the results — the panel composition is.

#### Prompt Engineering and the GPT-4 Sensitivity Analysis

One of the paper's key empirical findings is that GPT-4's performance as a judge is highly sensitive to prompt wording. This is not merely an observation — it is a methodological investigation that reveals something important about the fragility of single-judge evaluation.

The authors systematically varied the prompt given to GPT-4 on the Natural Questions dataset and measured the resulting Cohen's κ with human judgments. The variants tested were:

1. **Zero-shot** (κ = 0.518): The natural language instruction is supplied as a system message with no labeled examples. This is the simplest possible setup and produces the worst agreement.

2. **Few-shot Standard** (κ = 0.627): The prompt used for all other model judges, with 10 in-context examples and the standard instruction line. This is the baseline for comparison.

3. **No Instruction Line** (κ = 0.594): The instruction line is removed entirely from the few-shot prompt, on the hypothesis that it might be confusing the model. Performance drops, indicating the instruction is helpful.

4. **Move Instruction Line** (κ = 0.637): The instruction is moved from the user message to a separate system message. This produces a marginal improvement, suggesting that GPT-4 may process system-level instructions differently from in-message instructions.

5. **Chat-Formatted Shots** (κ = 0.561): Each few-shot example is formatted as a separate conversational turn between user and assistant. This substantially reduces performance, possibly because it disrupts the pattern that GPT-4 has learned to expect in few-shot prompts.

6. **"Don't Overthink" Variant** (κ = 0.725): The instruction line is replaced with explicit guidance not to over-reason:

> "You are judging whether a model has generated a correct answer to a question. Study the examples the user gives you as they will be very informative for how to do the task. The Reference Answers you get will be short. An model's answer will be longer, and can be considered correct if it contains the semantic content of short reference answer somewhere within it. Don't worry about factuality with respect to the real world, just judge the example based on what you see. No need to overthink this task, it really comes down to just soft matching."

This produces the best performance, jumping from 0.627 to 0.725 — a substantial improvement purely from prompt engineering.

The pattern across these variants reveals something important about GPT-4 as a judge. The largest improvements come from **constraining the model's reasoning** — telling it not to overthink, not to worry about real-world factuality, and to treat the task as simple soft matching. This supports the authors' hypothesis that GPT-4's default behavior (deep reasoning, bringing in external knowledge) is counterproductive for a task that requires narrow semantic comparison. The model is too capable for its own good — it cannot resist going beyond what the task actually requires.

Critically, the paper notes that this optimized prompt did not generalize well to other models:

> "the 'don't overthink' prompt had a negligible positive effect on Haiku, minor negative effect to Command R and a severe negative impact on GPT-3.5."

This asymmetry is revealing. The prompt that helps GPT-4 actually hurts GPT-3.5. This means that **the optimal prompt is model-specific**, which creates a practical problem: if you use a single judge, you need to tune the prompt for that specific judge, and your tuning may not transfer if you switch judges. The PoLL approach sidesteps this problem because the aggregation across models reduces sensitivity to any individual model's prompt-engineering quirks.

#### Human Annotation Pipeline: Establishing Ground Truth

To measure how well any judge (single model or panel) performs, the paper needs ground-truth human judgments. The annotation methodology is described in Appendix A.3.

**Annotator qualifications.** The paper uses Cohere's internal annotation workforce, describing them as:

> "professional annotators with diverse demographic and professional backgrounds including novelists, copywriters, copy editors, and journalists."

This is notable because these are not crowdworkers from a platform like Mechanical Turk — they are experienced language professionals who are likely to produce higher-quality, more consistent judgments than a general crowd. This matters for the reliability of the human-judgment baseline against which the LLM judges are measured.

**Annotation task.** Annotators are shown a single anonymized model-generated answer along with the original question and reference answer. They are asked to judge whether the reference answer is semantically contained within the generated answer. The paper notes:

> "By asking for answer correctness alone, we hope to minimize any potential annotator bias or preference towards a particular model's style."

This is an important design choice. By anonymizing model outputs and asking only about semantic correctness rather than quality or preference, the annotation design tries to isolate the objective correctness dimension from subjective style preferences. If annotators saw model names or were asked about "quality," they might rate verbose, well-written answers higher even if they were less factually accurate. The narrow "is the reference answer contained?" framing reduces this confound.

**Single vs. triple annotation.** The paper uses different annotation schemes for different datasets:

| Dataset | Annotated Examples | Annotations per Example |
|---|---|---|
| Natural Questions | 688 | Triple |
| TriviaQA | 316 | Single |
| HotPotQA (single-hop) | 784 | Triple |
| HotPotQA (multi-hop) | 595 | Single |
| Bamboogle | 750 | Single |

For triple-annotated datasets, the final ground-truth label is determined by majority vote among the three annotators. This is methodologically important: on the datasets where the paper's main claims are most heavily tested (Natural Questions and single-hop HotPotQA), the ground truth itself is a form of panel judgment, reducing the impact of individual annotator error. The paper could have strengthened its claims (or been more transparent about limitations) by reporting inter-annotator agreement on the triple-annotated datasets, since the reliability of the ground truth directly bounds the maximum possible κ that any automatic judge can achieve.

#### Measuring Judge Quality: Cohen's κ and Correlation Metrics

The paper uses different metrics for different evaluation settings, chosen to match the nature of the judgments.

**Cohen's κ for binary QA judgments.** For the reference-based QA setting where judgments are binary (correct/incorrect), the paper uses Cohen's κ to measure agreement between each judge (or PoLL) and human annotators. Cohen's κ is defined as:

$$\kappa = \frac{p_o - p_e}{1 - p_e}$$

where $p_o$ is the observed proportion of agreement between the judge and the human annotator (simply the fraction of examples where they agree), and $p_e$ is the expected proportion of agreement by chance (the fraction of agreement that would be expected if both the judge and human were guessing randomly at the base rates of "correct" and "incorrect" in the data).

**What it computes:** κ takes the raw agreement rate $p_o$ and adjusts it downward by how much agreement could happen by chance given the marginal distributions of the two raters. If a judge simply says "correct" 90% of the time and the dataset is 90% correct answers, raw agreement would be high but κ would be near zero because this agreement could be achieved by a coin flip biased to 90% heads. The denominator $1 - p_e$ normalizes so that perfect agreement yields κ = 1 and chance-level agreement yields κ ≈ 0.

**Why this form:** κ is standard in inter-rater reliability studies because it accounts for base-rate effects that simple accuracy does not. In QA evaluation, where correct answers may be more common than incorrect ones (or vice versa, depending on model quality), raw accuracy would overstate agreement for a judge that simply guesses the majority class. κ penalizes such strategies appropriately.

The paper interprets κ values using standard heuristics: κ > 0.8 is strong agreement, κ > 0.6 is moderate agreement.

**Pearson and Kendall-Tau for Chatbot Arena rankings.** In the Chatbot Arena setting, where the output is a ranked list of models rather than binary per-example judgments, the paper uses rank correlation metrics. Pearson correlation measures the linear relationship between the judge's model scores and the ground-truth ELO scores. Kendall-Tau measures the ordinal agreement between the judge's ranking and the ground-truth ranking — specifically, it counts the fraction of model pairs that are ordered consistently between the two rankings, adjusted for ties.

The paper reports both because they capture different aspects of agreement: Pearson is sensitive to the magnitude of score differences (how far apart models are), while Kendall-Tau is purely ordinal (which model is better, ignoring by how much). If both metrics are high, the judge is getting both the ordering and the spacing right.

---

#### Intra-Model Bias Measurement Methodology

The paper operationalizes intra-model bias through a specific measurement approach. For each judge model and each evaluated model, the paper computes the **delta in absolute accuracy** — the difference between the judge's accuracy assessment and the human annotators' accuracy assessment for that model.

Concretely, for a given judge $J$ and a given evaluated model $M$, the paper computes:

$$\Delta(J, M) = \text{Accuracy}_J(M) - \text{Accuracy}_{\text{human}}(M)$$

where $\text{Accuracy}_J(M)$ is the fraction of model $M$'s answers that judge $J$ marks as correct, and $\text{Accuracy}_{\text{human}}(M)$ is the fraction that human annotators mark as correct. A positive $\Delta$ means the judge overestimates the model's accuracy (it is too lenient); a negative $\Delta$ means the judge underestimates it (it is too harsh).

**What this measures:** If intra-model bias exists, we would expect $\Delta$ to be systematically higher when $J$ and $M$ come from the same model family — that is, judges should overestimate the accuracy of models from their own family relative to human judgment. The paper visualizes this by plotting $\Delta$ values for each (judge, evaluated-model) pair and looking for a pattern where the highest positive $\Delta$ in each judge's column occurs on the diagonal (when the judge evaluates its own family's outputs).

**How PoLL reduces bias:** The PoLL score aggregates across judges from different families. When GPT-3.5 overestimates GPT-4's accuracy (positive $\Delta$) but Command R and Haiku do not share this bias, the pooled score brings the estimate back toward the human baseline. The paper quantifies this through the standard deviation of $\Delta$ scores: PoLL has a standard deviation of 2.2 across evaluated models, compared to 6.1 for GPT-3.5 (the highest-variance individual judge). A lower standard deviation means the panel's assessments are more consistent across different evaluated models — it is not systematically favoring or disfavoring any particular model family.

This measurement approach has an important limitation: it can only measure relative bias (compared to human judgments), not absolute bias. If all human annotators share some systematic bias (e.g., a preference for concise answers), the measurement would not capture it, and the paper does not discuss this possibility.

#### Cost and Latency Framework

The paper makes explicit cost comparisons between PoLL and GPT-4 as a single judge. The cost analysis uses the API pricing at the time of writing:

**PoLL costs:** The panel of three models costs $1.25 per million input tokens plus $4.25 per million output tokens. The paper does not break down the per-model contribution to these costs, but the total is the sum across all three panel members.

**GPT-4 Turbo costs:** $10 per million input tokens plus $30 per million output tokens.

**Cost ratio:** Depending on the input-to-output token ratio in a given task, running the entire three-model PoLL is seven to eight times less expensive than running a single GPT-4 judge. The paper reports this as:

> "Depending on the ratio of input-to-output tokens in a given task, running the entire three model PoLL is seven to eight times less expensive than running a single GPT-4 judge."

This cost advantage is important context for the paper's claims. Even if PoLL were only equal to GPT-4 in judgment quality (rather than better, as the paper claims), the 7–8× cost reduction would make it a compelling alternative for large-scale evaluation. The fact that PoLL is both better and cheaper makes the case particularly strong.

**Latency considerations.** The paper acknowledges that it did not run explicit latency evaluations but notes:

> "In general though, running a collection of smaller models in parallel (as in PoLL) is faster than a single big model."

This claim is plausible — smaller models have lower per-token latency, and the three panel members can run in parallel, so the wall-clock time is bounded by the slowest panel member rather than the sum of all three. However, the paper does not provide quantitative evidence, and the actual latency advantage would depend heavily on serving infrastructure, model hosting decisions, and batch sizes. A practitioner evaluating whether to adopt PoLL for latency-sensitive applications would need to benchmark this in their specific deployment context.

## 4. Key Insights and Innovations

### Innovation 1: Panel Heterogeneity as a Mechanism for Bias Cancellation, Not Just Variance Reduction

The standard argument for ensembling is statistical: average multiple noisy estimators and the uncorrelated errors cancel, reducing variance. The paper’s core intellectual move is sharper than this. It identifies **model family membership as a specific, diagnosable source of systematic error** in LLM evaluation — intra-model bias — and designs a panel whose composition directly targets that error source rather than generic noise.

Before this work, the field’s response to the discovery that LLM evaluators prefer their own outputs (Panickssery et al., 2024) could have been: “find an unbiased judge.” The paper argues that this is likely impossible — any model carries the imprint of its training distribution — and instead adopts a **bias-cancellation-by-design** philosophy. By deliberately selecting judges from three disparate model families (Cohere, Anthropic, OpenAI), the panel ensures that the systematic upward bias each judge applies to its own family’s outputs points in a different direction. When GPT-3.5 inflates GPT-4’s score, Command R and Haiku — lacking that specific family affiliation — do not share the inflation. Aggregation washes it out.

This is not a generic ensemble claim. It is a claim about **what kind of diversity matters** for this specific failure mode. The paper operationalizes this through the delta-from-human analysis (Figures 3 and 4). Each individual judge shows its highest positive delta (overestimation relative to humans) when scoring outputs from its own model family. PoLL, by pooling across families, produces a standard deviation of deltas (2.2) that is substantially lower than any individual judge (GPT-3.5 reaches 6.1). The panel is not just averaging out random noise — it is systematically neutralizing a known, directional bias that single-judge evaluation cannot escape. This reframes evaluation methodology from “pick the smartest rater” to “assemble raters whose blind spots are known to be non-overlapping.”

### Innovation 2: The Diagnostic Finding That Evaluator Capability and Evaluator Quality Are Not Monotonic

A natural assumption — and the one underlying the field’s default use of GPT-4 as judge — is that larger, more capable models make strictly better evaluators. The paper presents a clear counterexample that complicates this assumption in a theoretically interesting way. On Natural Questions with a standard few-shot prompt, GPT-4 achieves κ = 0.627 with human judgments, while the smaller Command R (κ = 0.734) and Haiku (κ = 0.749) substantially outperform it (Table 1). GPT-4 is the weakest judge tested on this task in the standard configuration.

What elevates this from a curiosity to a genuine insight is the **mechanism** the paper identifies through prompt ablation (Table 3). When GPT-4 is explicitly instructed not to overthink — “No need to overthink this task, it really comes down to just soft matching” — its κ jumps from 0.627 to 0.725. The same prompt has negligible or negative effects on other models. The interpretation (Section 4.3) is that GPT-4’s strength — deep reasoning, integration of world knowledge — becomes a liability on a task requiring narrow semantic comparison. It “over-reasons,” bringing in extraneous factual considerations rather than simply checking whether the reference answer’s meaning appears in the generated text.

This is a **capability-task mismatch** diagnostic. It implies that evaluator selection cannot be reduced to a single capability dimension. The traits that make a model strong on MMLU or complex reasoning benchmarks are not the same traits needed for reliable reference-based judgment. A “worse” model that faithfully executes the narrow matching task may outperform a “better” model that cannot resist editorializing. The finding also exposes a fragility in single-judge pipelines: the optimal prompt is model-specific (“don’t overthink” helps GPT-4 but severely harms GPT-3.5), meaning prompt tuning does not transfer across judges. PoLL naturally mitigates this because aggregation across models with different prompt sensitivities reduces dependence on any single model’s prompt-engineering state.

### Innovation 3: Reframing LLM Evaluation as a Problem That Inherits the Logic of Human Inter-Rater Reliability

Pooling multiple human annotators to reduce individual bias and error is foundational in evaluation methodology, from TREC to machine translation to summarization. The paper’s insight is not that this logic exists — it is that **the same logic applies to LLM evaluators with even greater force**, and that the dominant LLM-as-judge paradigm has systematically ignored it.

The default practice of using a single large judge implicitly treats LLM evaluators as oracles — neutral instruments that apply universal correctness criteria. The paper demonstrates that they are better understood as **raters with systematic biases sharing the same structural properties as human raters**: each has individual idiosyncrasies, family-specific preferences, and sensitivity to task framing. The difference is that LLM biases are, in one sense, worse (family affiliation is a stronger and more predictable confound than most human demographic variables) and, in another sense, more tractable (we can deliberately compose panels across families in a way we cannot compose panels of humans with non-overlapping cognitive biases).

The paper tests this reframing across three qualitatively different evaluation settings — binary reference-based scoring, binary scoring with multi-step tool-use generation, and scalar pair-wise comparison — and finds that PoLL matches or exceeds GPT-4 in every case (Tables 1, 2, 5, 6). This cross-setting consistency separates the finding from a domain-specific trick. The principle holds regardless of whether the judgment is binary or scalar, whether the generation is single-pass or agent-based, or whether the domain is factual QA or open-ended chat.

By anchoring the approach in the inter-rater reliability tradition (explicitly citing Voorhees, 1998 on variance in relevance judgments), the paper frames PoLL not as a cost-saving hack but as a **methodologically principled correction** to an oversight in how the field adopted LLM evaluators. The oversight was treating model-based evaluation as categorically different from human evaluation, when in fact the same structural problem — individual raters carry individual biases — applies to both.

## 5. Experimental Analysis

### Evaluation Methodology

- **Datasets.** The paper uses six datasets spanning three evaluation settings: single-hop QA (Natural Questions, TriviaQA, HotpotQA from KILT; Petroni et al., 2021), multi-hop QA (Bamboogle from Press et al., 2023; multi-hop HotpotQA from Shinn et al., 2024), and Chatbot Arena Hard (500 prompts from Li et al., 2024a). For KILT, the test sets are the standard splits: 688 annotated NQ examples, 316 TriviaQA examples, and 784 single-hop HotpotQA examples. Bamboogle contains 125 adversarially constructed multi-hop questions; the multi-hop HotpotQA subset size is not explicitly stated but follows Shinn et al. (2024). Chatbot Arena Hard uses exactly 500 prompts mined by Li et al. (2024a).

- **Evaluated models (the "test models" being judged).** The outputs being evaluated come from multiple model families: **Command R** (CMD-R, 35B) and **Command R+** (CMD-R+, 103B) from Cohere; **GPT-3.5** and **GPT-4** from OpenAI; **Claude-3 Haiku**, **Sonnet**, and **Opus** from Anthropic; and **Mistral Large** and **Mistral Medium** from Mistral. In single-hop QA, all models generate answers using retrieved evidence from the KILT Wikipedia dump (top-10 snippets via GTE-large dense retrieval; Wang et al., 2023). In multi-hop QA, models operate as REACT agents (Yao et al., 2022) with tool-use access (internet search for Bamboogle, dense embedding search with Cohere EmbedV3 + Rerank 3 for HotpotQA). In Chatbot Arena Hard, the authors generated new outputs for models not already in the original Li et al. (2024a) repository.

- **Metrics.** For binary QA judgments, the primary metric is **Cohen's κ** between each judge (or PoLL) and human annotators, measuring agreement above chance. For Chatbot Arena, the metrics are **Pearson correlation** and **Kendall-Tau** between the judge's model rankings and the crowd-sourced ELO leaderboard from Chatbot Arena. For bias measurement, the metric is **delta from human accuracy** (Δ = judge_accuracy − human_accuracy per evaluated model), with the standard deviation of these deltas quantifying consistency.

- **Baselines.** The paper compares against four individual judge baselines: **GPT-4** (the default single-large-judge approach; Zheng et al., 2024), **GPT-3.5**, **Command R**, and **Claude-3 Haiku**. Additionally, the paper includes **Exact Match (EM)** — specifically the "containment" variant from Liu et al. (2024) that checks if the normalized reference answer string appears within the generated output — as a non-LLM heuristic baseline in the QA experiments. The EM baseline is not used in Chatbot Arena since pair-wise scalar judgments have no string-matching analog.

- **Generation budget / compute accounting.** The paper does not measure test-time compute in FLOPs or tokens. Instead, cost is measured in **API pricing** (dollars per million input/output tokens) and compared directly: PoLL (three smaller models) costs $1.25/M input + $4.25/M output; GPT-4 Turbo costs $10/M input + $30/M output. The paper reports PoLL as "over seven times less expensive" based on these figures, without specifying exact token counts per experiment. Latency is discussed qualitatively but not benchmarked.

- **Cross-validation / statistical protocol.** No cross-validation is used. Prompt construction for KILT datasets involves sweeping over $n \in \{8, 10, 16\}$ few-shot examples and selecting the prompt with strongest average agreement across judges on "a small held-out portion of human labels" (Section A.1.1), but this is prompt selection rather than formal cross-validation. For Chatbot Arena, the paper uses existing crowd-sourced ELO scores as ground truth without further statistical testing. For the triple-annotated QA datasets (NQ, single-hop HotpotQA), ground truth is majority vote among three annotators; for singly-annotated datasets (TriviaQA, multi-hop HotpotQA, Bamboogle), ground truth is a single annotator's judgment.

### Main Quantitative Results

#### Single-Hop QA: PoLL Consistently Achieves Highest Agreement with Humans

Table 1 reports Cohen's κ between each judge and human annotators on three KILT datasets: Natural Questions (NQ), TriviaQA (TQA), and HotpotQA (HPQA). The headline finding is that **PoLL achieves the highest κ on two of three datasets** and ties for highest on the third.

On NQ, PoLL achieves κ = 0.763, outperforming every individual judge: Haiku (0.749), Command R (0.734), GPT-3.5 (0.726), EM (0.651), and GPT-4 (0.627). The gap between PoLL and GPT-4 — the current default single judge — is 0.136 κ points, which is substantial on a scale where 0.6 is "moderate" and 0.8 is "strong" agreement. GPT-4 is the weakest LLM judge on this dataset, trailing even the string-matching EM baseline.

On TQA, PoLL achieves κ = 0.906, again the highest, with Command R at 0.902, Haiku at 0.894, GPT-3.5 at 0.859, GPT-4 at 0.841, and EM at 0.827. The margins are tighter here — PoLL beats Command R by only 0.004 κ — but the pattern of PoLL at or near the top holds.

On HPQA, PoLL achieves κ = 0.867, ranking second behind Haiku (0.873) and ahead of GPT-3.5 (0.833), GPT-4 (0.830), Command R (0.815), and EM (0.662). This is the one dataset where PoLL does not claim the top spot, though the difference from Haiku (0.006 κ) is negligible.

A pattern emerges across all three datasets: **GPT-4 is consistently among the weaker judges**, ranking last among LLM judges on NQ, last on TQA, and fourth (effectively tied for third) on HPQA. This directly challenges the default practice of using GPT-4 as the sole evaluator.

The EM baseline shows an interesting profile: it performs reasonably on TQA (κ = 0.827, better than GPT-4's 0.841? No — actually worse than all LLM judges on TQA), but is substantially weaker on NQ (0.651) and HPQA (0.662), consistent with the paper's claim that string matching fails when answer formats vary. The fact that EM outperforms GPT-4 on NQ (0.651 vs. 0.627) is a striking illustration of how poorly GPT-4 performs on this task without the optimized prompt.

#### Multi-Hop QA: PoLL Generalizes Across Datasets and Agent-Based Generation

Tables 5 and 6 extend the analysis to multi-hop QA, where models generate answers through multi-step REACT agent processes rather than single-pass generation. The pattern of PoLL dominance largely persists.

On Bamboogle (Table 5), the total κ across all evaluated models is: PoLL 0.896, Haiku 0.898 (essentially tied), Command R 0.885, GPT-3.5 0.846, GPT-4 0.846, EM 0.762. PoLL and Haiku are statistically indistinguishable at the top. Critically, the per-model breakdown reveals substantial variation: for evaluating Haiku's own outputs, Haiku-the-judge achieves κ = 0.802 while PoLL achieves 0.803 (near-identical). For Mistral-LG outputs, Command-R-the-judge achieves 0.936, Haiku-the-judge achieves 0.936, but GPT-3.5-the-judge achieves only 0.760 — a massive gap. PoLL achieves 0.872 on Mistral-LG, meaning it is pulled down by GPT-3.5's poor performance on this model but still outperforms GPT-3.5 alone. This per-model variation is exactly the kind of judge-evaluated-model interaction that motivates a panel approach.

On multi-hop HotPotQA (Table 6), PoLL achieves total κ = 0.871, second to Command R (0.886) but ahead of Haiku (0.849), GPT-3.5 (0.827), GPT-4 (0.827), and EM (0.773). The gap between PoLL and GPT-4 is 0.044 κ points — smaller than on single-hop QA but still meaningful. GPT-4 and GPT-3.5 are again among the weaker judges, though the ordering is less extreme than on NQ.

An important cross-setting observation: **Haiku is the strongest individual judge on four of the five QA datasets** (NQ, TQA, HPQA single-hop, Bamboogle), with Command R taking the lead on multi-hop HotPotQA. There is no single consistently-best individual judge. PoLL, by aggregating across judges, achieves either the best or statistically equivalent-to-best performance on every dataset. This supports the paper's claim that "there is not a single 'best' judge across all settings, while PoLL performs well consistently" (Section 5).

#### Chatbot Arena Hard: PoLL Rankings Correlate Better with Human Preferences

Table 2 reports correlation between judge-produced model rankings and the Chatbot Arena crowd-sourced ELO leaderboard (treated as ground truth). For Pearson correlation: PoLL achieves 0.917, Haiku and GPT-3.5 tie at 0.883, GPT-4 and Command R tie at 0.817. For Kendall-Tau: PoLL achieves 0.778, GPT-3.5 achieves 0.730, Haiku achieves 0.722, Command R achieves 0.676, GPT-4 achieves 0.667.

PoLL leads on both metrics. The Kendall-Tau gap between PoLL (0.778) and GPT-4 (0.667) is 0.111 — a meaningful ordinal improvement. On Pearson, the gap is 0.100 (0.917 vs. 0.817).

Figure 2 visualizes these rankings as a rank-comparison plot. The "gold" ranking (Chatbot Arena ELO) appears on the diagonal. The key visual evidence for intra-model bias: **GPT-4-the-judge ranks GPT-4-0314 (a different GPT-4 variant) at position 2, whereas its actual crowd-sourced position is 4.** GPT-4 overestimates its own family member by two rank positions. PoLL's ranking is visually closer to the diagonal, particularly at the top of the list where practical decisions about which model to deploy are most consequential.

The raw PoLL scores for Arena Hard are reported in Table 7: GPT-4-turbo scores 68.7, Sonnet 57.6, Command R+ 57.1, Haiku 55.9, GPT-4-0314 50.0, Mistral Medium 49.0, Command R 48.0, Mistral Large 43.7, GPT-3.5 41.2. These scores are derived from average pooling across the three panel members. The 95% confidence intervals are reported, with widths ranging from approximately ±2.0 to ±3.2 depending on the model, though the paper does not describe how these intervals are computed.

#### Intra-Model Bias: Quantified and Reduced by PoLL

Figures 3 and 4 visualize the delta-from-human-accuracy analysis (Δ = judge_accuracy − human_accuracy) for each (judge, evaluated-model) pair on multi-hop HotPotQA and Bamboogle respectively. The dotted zero line represents perfect agreement with human judgments.

The consistent pattern across both figures: **each individual judge shows its highest positive Δ when evaluating outputs from its own model family.** In Figure 3 (multi-hop HotPotQA), GPT-3.5-the-judge overestimates GPT-3.5-the-evaluated-model's accuracy by the largest positive margin (approximately 6–8 percentage points above human judgment). Command-R-the-judge overestimates Command-R's accuracy. Haiku-the-judge overestimates Haiku's accuracy. This is the visual signature of intra-model bias.

The paper quantifies the spread of these deltas through standard deviation: **PoLL has a standard deviation of 2.2 across evaluated models, compared to 6.1 for GPT-3.5** (the highest-variance individual judge). EM, notably, has the largest spread in Figure 4 (Bamboogle), with deltas reaching approximately −15 to +15 percentage points depending on the model, illustrating how string matching can be simultaneously too lenient on some models and too harsh on others.

Figure 4 (Bamboogle) shows an even starker pattern on the diagonal: the highest positive delta for each individual judge (GPT-3.5, Command R, Haiku) occurs when that judge evaluates its own model family's outputs. The PoLL bar in each evaluated-model group generally sits closer to the zero line than the worst-deviating individual judge.

In Figure 2 (Chatbot Arena rankings), the bias manifests differently: rather than a numeric overestimate, it appears as a rank displacement. GPT-4-the-judge promotes GPT-4-0314 from its true rank (4) to rank 2, a two-position inflation that would materially affect model selection decisions. PoLL's ranking shows no comparable family-inflation pattern — the panel does not systematically promote any model family.

### Ablation Studies and Robustness Checks

**Prompt sensitivity of GPT-4:** Table 3 reports κ on NQ for six GPT-4 prompt variants. The key finding is that GPT-4's κ varies from 0.518 (zero-shot) to 0.725 (optimized "don't overthink" prompt), a range of 0.207. The optimized prompt brings GPT-4 up to the level of GPT-3.5 with the standard prompt (0.726; Table 1) but still below Command R (0.734), Haiku (0.749), and PoLL (0.763). Table 4 shows the "don't overthink" prompt's effect on other models: Haiku improves marginally (0.749 → 0.757), Command R degrades (0.734 → 0.687), GPT-3.5 degrades severely (0.729 → 0.509), and PoLL degrades (0.763 → 0.699). The cross-model asymmetry confirms that the optimal prompt is model-specific and that prompt optimization for one judge does not transfer.

**Voting function robustness for Chatbot Arena:** The paper reports that max voting with average voting fallback "yielded similar results with an identical overall ranking" to pure average pooling (Section 3.1), suggesting that the specific aggregation function is not driving the Chatbot Arena results.

**Few-shot example count:** The prompt construction procedure sweeps over $n \in \{8, 10, 16\}$ few-shot examples, selecting the best-performing prompt on a held-out subset. The paper does not report how sensitive κ is to the number of shots, nor whether different judges have different optimal shot counts, which limits the robustness analysis. The final prompts use 10 examples for NQ (Table 11), 16 for HotpotQA (Table 12), and 8 for TriviaQA (Table 13), suggesting that dataset-specific tuning matters.

**Single vs. triple annotation:** The paper does not report inter-annotator agreement on the triple-annotated datasets (NQ, single-hop HotpotQA). This is a notable omission because the maximum achievable κ for any judge is bounded by human inter-annotator agreement. If human agreement is, say, κ = 0.85, then PoLL's κ = 0.763 on NQ represents recovery of approximately 90% of the achievable signal — a very different interpretation than comparing against a theoretical maximum of 1.0. The absence of this baseline makes it harder to assess how much room for improvement remains.

**Evaluated model coverage:** The paper includes Mistral models as an "unaffiliated" test case (no Mistral model serves as a judge). The per-model κ breakdowns in Tables 5 and 6 show that Mistral-LG's κ varies substantially across judges (e.g., 0.760 for GPT-3.5 vs. 0.936 for Command R on Bamboogle). PoLL achieves 0.872 on Mistral-LG, meaning it is pulled down from the best individual judge (0.936) but up from the worst (0.760), demonstrating the bias-cancellation mechanism on a family with no panel representation.

**Cost comparison:** The paper reports PoLL as "over seven times less expensive" than GPT-4 based on API pricing at time of writing. However, this comparison does not account for the fact that PoLL requires three inference calls per judgment vs. one for GPT-4, which could affect latency in non-parallelized settings. The paper acknowledges this indirectly by noting that parallel execution makes PoLL "faster than a single big model" in general, but provides no quantitative latency data.

### Critical Assessment

#### Does PoLL actually outperform a single large judge?

The experimental evidence partially supports this claim, but with important qualifications that the paper's framing sometimes obscures.

On single-hop QA (Table 1), PoLL achieves the highest κ on all three datasets (technically tied for second on HPQA, 0.867 vs. Haiku's 0.873). However, the margin over the best individual judge is modest: +0.014 on NQ over Haiku, +0.004 on TQA over Command R, and actually −0.006 on HPQA vs. Haiku. On two of three datasets, PoLL's advantage over the best individual model is within what might reasonably be attributed to sampling noise (the paper reports no confidence intervals on κ values). The stronger and more consistent finding is that **PoLL outperforms GPT-4**, the current default, by margins of 0.136, 0.065, and 0.037 κ on NQ, TQA, and HPQA respectively. The claim that PoLL "outperforms a single large judge" holds unambiguously when the single large judge is GPT-4. It holds more tenuously when the comparison is against the best individual judge for each dataset.

On multi-hop QA (Tables 5 and 6), PoLL is essentially tied with Haiku on Bamboogle (0.896 vs. 0.898) and trails Command R on HotpotQA (0.871 vs. 0.886). The panel is never the clear loser, but it is also not always the clear winner. The consistent pattern is that **PoLL is always in the top tier** — it achieves either the best or statistically indistinguishable-from-best performance on every dataset — which supports the claim that it performs "well consistently" even when it is not strictly dominant.

On Chatbot Arena (Table 2), PoLL's advantage is clearer: Pearson 0.917 vs. the next-best 0.883, Kendall-Tau 0.778 vs. 0.730. These are the largest relative gaps in any setting. However, the sample size is only 9 evaluated models producing one ranking per judge, which makes the rank correlation metrics inherently higher-variance than the per-example κ values on QA. A single rank swap in a 9-item list can meaningfully shift both Pearson and Kendall-Tau.

#### Does PoLL reduce intra-model bias?

The evidence in Figures 3 and 4 supports this claim clearly. The standard-deviation-of-deltas metric (2.2 for PoLL vs. 4–6 for individual judges) quantifies what is visually apparent: individual judges show systematic family-preferences, and PoLL smooths them out. The Chatbot Arena ranking (Figure 2) provides a qualitatively different form of evidence: GPT-4's inflation of GPT-4-0314 from rank 4 to rank 2 is a concrete, interpretable instance of the bias the paper is targeting.

A limitation not discussed in the paper: the bias measurement relies entirely on deviation from human judgments as the benchmark. If human annotators themselves exhibit systematic biases (e.g., a preference for concise answers, which could disadvantage verbose models like Command R), then a judge that matches those biases would appear unbiased by this metric. The paper cannot distinguish between "PoLL reduces intra-model bias" and "PoLL happens to produce scores closer to human judgments for other reasons," though the per-judge delta patterns (highest positive delta on own-family outputs) make the bias interpretation more plausible than alternatives.

#### Is PoLL actually more cost-effective?

The cost comparison is straightforward (7–8× cheaper based on API pricing) but incomplete. First, the paper does not factor in the **difficulty estimation cost** of prompt engineering: the "don't overthink" prompt variant required experimentation to discover, and that cost is not amortized. Second, the cost comparison assumes all three panel members are needed, but the paper provides no evidence that three models from three families is optimal rather than, say, two models or four. If two models of different families achieved equivalent κ, the cost advantage would be even larger; if four were needed for some tasks, it would be smaller. Third, the dollar cost per API call does not directly translate to total cost of ownership for a research lab that may self-host some models and pay API fees for others.

#### What the experiments do not show

The paper does not test whether the specific PoLL composition (Command R + Haiku + GPT-3.5) generalizes beyond the three model families involved. Would a panel of GPT-3.5 + Llama-3 + Gemini work equally well? The principle of family heterogeneity predicts yes, but this is untested. The paper also does not evaluate PoLL on evaluation tasks fundamentally different from the three settings tested — for example, scoring mathematical correctness (where models often struggle; Zheng et al., 2024, which the paper itself cites), evaluating summarization quality on a multi-dimensional scale, or detecting subtle factual errors in long-form generation. The cross-setting consistency within the tested domains is encouraging, but the paper's "limited settings" limitation (acknowledged in Section 5) is genuine.

The sample sizes warrant attention. For Chatbot Arena, 9 models and 500 prompts produce a single ranked list per judge; the rank correlations are computed from 9 data points. For the KILT datasets, NQ has 688 triple-annotated examples, but TriviaQA has only 316 single-annotated examples — meaning the ground-truth κ calculations on TriviaQA are based on agreement with a single human annotator. The paper does not report the impact of single vs. triple annotation on the reliability of the human-judgment baseline.

Finally, the paper does not provide a **sensitivity analysis of panel composition**: what happens to PoLL's κ if you remove the best-performing member (Haiku) or the worst-performing member (GPT-3.5, in some settings)? Would a two-model panel of Command R + Haiku match or exceed the three-model panel? This ablation would strengthen the claim that diversity specifically (three families) rather than simply "more models" drives the benefit. The omission is particularly notable because on several datasets, the best individual judge is within sampling noise of PoLL's performance, suggesting that PoLL's gain comes primarily from not picking the wrong single judge rather than from aggregation per se.

## 6. Limitations and Trade-offs

### 6.1 The Cost of Difficulty Estimation Is Excluded from the Core Efficiency Claim

The paper reports that PoLL is "over seven times less expensive" than using GPT-4 as a single judge (Section 4.5), and that PoLL "performs well consistently" across settings (Section 5). However, these claims assume that the panel composition and prompt configuration are already established — the cost of discovering *which* models to include in the panel, *how many* to include, and *how to prompt each one* is not amortized into any reported figure.

**The underlying assumption** is that a fixed panel of three specific models (Command R, Haiku, GPT-3.5) with dataset-specific few-shot prompts (8–16 examples each) will generalize across evaluation tasks without requiring per-task or per-dataset reconfiguration. The paper acknowledges this implicitly by leaving "the task of 'panel selection,' or identifying the best models to include in PoLL in terms of quality and cost, to future work" (Section 5), but does not characterize how sensitive PoLL's performance is to panel composition or how expensive panel selection would be for a new domain.

**The consequence** is that the 7–8× cost advantage is a *marginal* cost comparison (cost per evaluation, given an already-configured panel), not a *total cost of ownership* comparison. A practitioner adopting PoLL for a new evaluation task would need to: (1) select panel members from candidate model families, (2) construct and optimize few-shot prompts for each member, (3) potentially tune the voting function, and (4) validate the panel against human judgments. The prompt optimization alone required sweeping over 8, 10, and 16 few-shot examples per KILT dataset and selecting based on a held-out subset (Section A.1.1) — a non-trivial computational and human-oversight cost. If prompt engineering is as consequential as the paper's own GPT-4 ablation demonstrates (κ varying from 0.518 to 0.725 on NQ purely from prompt changes; Table 3), then the cost of tuning prompts for three panel members could be substantial. The paper's experiments benefited from access to an internal human annotation workforce for this tuning; a lab without such resources would face additional costs or accept lower-quality prompts.

**Evidence in the paper:** The prompt sensitivity analysis (Section 4.3, Table 3) demonstrates that GPT-4's κ varies by 0.207 points across prompt variants, and Table 4 shows that the prompt optimized for GPT-4 severely degrades GPT-3.5 (0.729 → 0.509 κ). This cross-model asymmetry means that practitioners cannot optimize a prompt once and apply it across panel members — each model may need its own prompt optimization. The paper does not report how many prompt variants were tested per model, what the total token cost of prompt optimization was, or how many human annotation hours were required for the held-out validation subsets.

**Mitigation status:** The paper does not address this limitation directly. It treats the specific PoLL composition as given and evaluates its performance, without providing guidance on how a new user would construct an equivalent panel for a different task or domain. The suggestion of future work on panel selection is mentioned but not developed.

### 6.2 The Panel's Performance Advantage Over the Best Single Judge Is Modest and Not Uniform

The paper's central claim is that PoLL "outperforms a single large judge" (Section 1). While this holds strongly against GPT-4 specifically, the evidence that PoLL outperforms the *best* single judge in any given setting is thinner, and on some datasets PoLL is measurably worse than the best individual model.

**The constraint** is that PoLL's aggregation mechanism is fixed and simple (max voting for binary, average pooling for scalar). It does not learn to weight judges by their per-dataset or per-model reliability. This means PoLL is always an average of its members — and if the best member would have been the right choice for a given dataset, PoLL underperforms that member. The evidence bears this out directly:

- On single-hop HotPotQA (Table 1), PoLL achieves κ = 0.867, while Haiku alone achieves 0.873 — PoLL is 0.006 κ points *below* the best individual judge.
- On multi-hop Bamboogle (Table 5), PoLL achieves 0.896 while Haiku achieves 0.898 — essentially tied, but PoLL does not outperform.
- On multi-hop HotPotQA (Table 6), PoLL achieves 0.871 while Command R achieves 0.886 — PoLL trails by 0.015 κ.

On only two of five QA datasets (NQ and TQA) does PoLL strictly outperform every individual judge, and on NQ the margin over Haiku is 0.014 κ — a difference that may not be statistically significant (no confidence intervals are reported for the κ values). On Chatbot Arena (Table 2), PoLL's advantage is clearer (Pearson 0.917 vs. 0.883, Kendall-Tau 0.778 vs. 0.730), but this is computed from only 9 evaluated models producing a single ranking per judge.

**The consequence** is that a practitioner who already knows which individual judge performs best on their specific evaluation task (e.g., through a small pilot study) might achieve equal or better performance by using that single judge rather than PoLL, at lower cost and latency. The paper's value proposition shifts from "PoLL is always better" to "PoLL protects you from accidentally picking a weak judge (like GPT-4 with a bad prompt) without sacrificing much when a strong individual judge exists." This is a genuine benefit — the paper shows that GPT-4 underperforms on several datasets and that prompt optimization is model-specific — but it is a different and weaker claim than "PoLL outperforms a single large judge."

**Evidence in the paper:** Tables 1, 5, and 6 provide the per-judge breakdowns. The paper's own wording in Section 5 — "there is not a single 'best' judge across all settings, while PoLL performs well consistently" — is an accurate characterization of what the data supports: PoLL is a robust choice that avoids worst-case outcomes, not a strictly dominant one.

**Mitigation status:** The paper does not discuss when a practitioner should prefer a single judge over PoLL, nor does it provide a decision rule based on available resources, domain characteristics, or the cost of identifying the best individual judge through pilot experiments. The robustness value of PoLL is emphasized, but the scenarios where PoLL is worse than an identifiable individual judge are not addressed.

### 6.3 The Panel Is Tested Only on Semantic Equivalence and Pairwise Preference Judgments

All experiments in the paper fall into two judgment types: **binary semantic containment** (does the reference answer's meaning appear in the generated text?) and **pairwise preference** (which of two responses is better?). The paper explicitly acknowledges this scope limitation but does not test the boundaries beyond it:

> "In this work we investigated only three evaluator settings and a limited number of judges and panel compositions. While we showed that PoLL is an effective alternative to a single large model in these settings, further work is needed to see how broadly applicable the method is, for example, in math or reasoning evaluations, where language models often struggle." (Section 5)

**The consequence** of this scope limitation is significant because the failure modes of LLM judges in mathematical or reasoning evaluation are likely **qualitatively different** from the failure modes in semantic equivalence judgment. In the QA setting, the judge's task is essentially a soft string-matching problem: determine if the semantic content of a short reference answer appears in a longer generated answer. GPT-4's primary failure mode, per the paper's analysis, is "over-reasoning" — bringing in extraneous world knowledge rather than performing the narrow comparison task (Section 4.3). In mathematical reasoning evaluation, the opposite problem may apply: the judge needs to verify multi-step logical derivations, where under-reasoning (failing to trace the logic) would be the primary failure mode. The paper's finding that smaller, "dumber" models outperform GPT-4 on semantic matching (because they faithfully execute the narrow task) may **reverse** for math evaluation, where deeper reasoning capability is genuinely required to assess correctness. Similarly, for tasks like summarization quality assessment or long-form factuality checking, the judgment criteria are multi-dimensional and subjective in ways that binary semantic containment is not. The biases that PoLL cancels (intra-model style preferences) may be less relevant than other biases (e.g., preference for certain summary lengths or factuality heuristics) that a heterogeneous panel does not automatically address.

**Evidence in the paper:** None — this is a gap the paper identifies but does not probe. The paper includes no experiments on mathematical correctness, reasoning verification, summarization quality, or any judgment type requiring multi-step logical evaluation. The Chatbot Arena setting is the most open-ended domain tested, but even there the judgment is a holistic pairwise preference rather than a correctness verification.

**Mitigation status:** The paper explicitly calls this out as a limitation and suggests future work. No mitigation is attempted within the paper.

### 6.4 The Bias Measurement Relies on Human Judgments as an Unbiased Baseline

The paper's evidence for intra-model bias reduction (Section 4.4, Figures 3 and 4) depends entirely on treating human annotator judgments as the ground-truth reference point. The bias metric Δ = judge_accuracy − human_accuracy assumes that human judgments are unbiased, or at least that any human biases are orthogonal to model family membership.

**The assumption** is stated indirectly in Appendix A.3: "By asking for answer correctness alone, we hope to minimize any potential annotator bias or preference towards a particular model's style." But the paper does not measure whether this hope was realized. Human annotators — even professional novelists, copywriters, and journalists — may have systematic preferences that correlate with model family outputs in ways that are not about "style" in a surface-form sense but about deeper properties like verbosity, confidence calibration, or reasoning transparency. If human annotators share a bias (e.g., preferring concise answers), then a model family that systematically produces verbose answers (Command R, per the paper's note about its tendency toward longer generations; Table 11 prompt examples) would appear to be "underestimated" by human judges relative to its true correctness. A subsequent LLM judge that shares the same verbosity preference as the human annotators would then appear "unbiased" by the paper's metric, even though both the human and the LLM judge exhibit the same bias.

**The consequence** is that the paper cannot distinguish between two interpretations of reduced PoLL variance: (a) PoLL genuinely cancels intra-model family bias, or (b) PoLL's aggregated scores happen to align more closely with human judgments that themselves carry biases (such as a preference for certain answer formats or conciseness levels). The per-judge delta patterns (Figures 3, 4) showing the highest positive deltas on own-family outputs make interpretation (a) more plausible — it is unlikely that human annotators just happen to rate GPT-family outputs lower in exactly the pattern that makes GPT-3.5's inflated ratings look like bias. However, the paper does not provide the one piece of evidence that would settle this: **inter-annotator agreement on the triple-annotated datasets**. If human agreement is, say, κ = 0.85, then the upper bound on any judge's agreement with the pooled human label is 0.85, and PoLL's κ = 0.763 on NQ represents recovery of ~90% of the achievable signal. If human agreement is lower — say, κ = 0.70 — then the picture changes substantially.

**Evidence in the paper:** The paper reports the number of triple-annotated examples (Table 8: 688 for NQ, 784 for single-hop HPQA) but does not report inter-annotator agreement statistics. This omission makes it impossible to assess the reliability of the human baseline against which all judge quality is measured.

**Mitigation status:** Not addressed. The paper does not discuss potential human annotator biases, does not report inter-annotator agreement, and does not consider whether some of the "intra-model bias" signal could reflect genuine quality differences that multiple human annotators would also detect. The use of triple annotation with majority voting is a partial mitigation for random annotator error, but it does not address systematic annotator biases shared across the annotator pool.

### 6.5 Single Annotation for Key Datasets Weakens the Ground-Truth Baseline

Three of the five QA datasets used to evaluate PoLL — TriviaQA (316 examples), multi-hop HotPotQA (595 examples), and Bamboogle (750 examples) — are singly annotated (Table 8). In the paper's own terminology, these datasets rely on a "single judge" (one human annotator) to establish ground truth.

**The consequence** is that the κ values reported on these datasets measure agreement between the LLM judge and a single human rater, not agreement with a consensus human judgment. A single human rater carries individual biases, attention lapses, and interpretation variations that majority voting across three raters would smooth out. The paper cannot know, for the singly-annotated datasets, whether a disagreement between PoLL and the human label represents an error by PoLL or an error by the single human annotator. Both possibilities produce the same κ penalty. If the single human annotator on TriviaQA had an idiosyncratic interpretation of what constitutes a correct answer on 5% of examples, PoLL's κ = 0.906 would actually underestimate its agreement with "true" correctness, and the comparison against other judges would be noisier than on triple-annotated datasets.

**Evidence in the paper:** Table 8 reports the annotation scheme per dataset. The paper does not discuss how single annotation affects the reliability of the ground truth, nor does it compare κ values between singly-annotated and triple-annotated datasets to check for systematic differences (e.g., whether κ values are consistently higher or lower on one annotation scheme).

**Mitigation status:** The paper does not address this limitation. It treats all κ values as directly comparable regardless of whether they are computed against a single annotator or a majority-voted pool of three annotators. A standard mitigation would be to report κ values only on triple-annotated datasets for the central claims, with singly-annotated datasets as supplementary, or to acknowledge that κ on singly-annotated data has a lower ceiling and wider confidence intervals.

### 6.6 No Quantitative Latency Analysis Despite Practical Relevance

The paper claims that "running a collection of smaller models in parallel (as in PoLL) is faster than a single big model" (Section 4.5) but provides no latency measurements. This claim is plausible — smaller models have lower per-token decode latency, and the three panel members can execute concurrently — but it elides several practical complications that affect whether PoLL is actually faster in a deployment setting.

**The unexamined factors include:**

1. **Parallelization overhead:** Running three models in parallel requires either three separate inference servers or a batching infrastructure that can handle heterogeneous model requests simultaneously. If a practitioner's infrastructure supports only sequential API calls (e.g., a single-GPU setup), the latency of PoLL is the sum of three inference calls, not the maximum. For the QA setting where judgments are binary and input prompts are long (10–16 few-shot examples plus the question and answer), the time to process the shared prompt prefix across three sequential calls could be substantial.

2. **Model hosting asymmetry:** The paper's panel uses two models available via API (GPT-3.5, Haiku) and one open-weight model (Command R) that could be self-hosted. Self-hosting Command R introduces its own latency profile (dependent on hardware, batch size, quantization) that may not match API latencies. The paper provides no data on per-model latency for the specific prompt lengths and output lengths used in the experiments.

3. **Prompt length effects:** The judge prompts for KILT datasets contain 8–16 few-shot examples, making them quite long (Tables 11–13 show thousands of tokens of context). Prefill latency (processing the input prompt before generating the first token) scales with prompt length and can dominate total latency for short-output tasks like binary classification. GPT-4's prefill latency may be higher than Haiku's or Command R's, but the paper provides no measurements.

**Evidence in the paper:** The paper explicitly states: "We did not run explicit latency evaluations" (Section 4.5). The latency claim is based on general reasoning about model size, not on measured data.

**Mitigation status:** The paper acknowledges the absence of latency data and notes that "many factors such as model choice, serving platform, and more can impact speed." This is transparent, but for a paper whose practical contribution includes claims about deployment efficiency, the absence of latency data is a significant gap. A practitioner deciding whether to replace a single GPT-4 call with three parallel smaller-model calls in a latency-sensitive application (e.g., real-time evaluation during model inference) needs quantitative latency data that the paper does not provide.
