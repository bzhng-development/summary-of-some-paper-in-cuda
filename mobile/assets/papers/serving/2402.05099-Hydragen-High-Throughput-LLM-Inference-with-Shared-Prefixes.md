# Hydragen: High-Throughput LLM Inference with Shared Prefixes

**ArXiv:** [2402.05099](https://arxiv.org/abs/2402.05099)

## 🎯 Pitch

Simply sharing KV cache memory across sequences with a common prompt doesn't speed up attention—it still forces the GPU to repeat the same memory-bound matrix-vector products for every sequence. Hydragen replaces those redundant reads with a single batched matrix-matrix product for the shared prefix, boosting CodeLlama-13b decoding throughput by up to 32× and making it nearly indifferent to growing prefix length.

---

## 1. Executive Summary

This paper introduces **Hydragen**, a hardware-aware exact implementation of attention that is specialized for batches of sequences sharing common prefixes — such as a chatbot system prompt or few-shot examples — and operates by decomposing attention into separate computations over the shared prefix and unique suffixes, then batching attention queries inter-sequence when attending over the prefix (replacing many memory-bound matrix-vector products with fewer hardware-friendly matrix-matrix products that leverage tensor cores). Evaluated on CodeLlama-13b end-to-end throughput benchmarks, Hydragen improves decoding throughput by up to 32× over the vLLM baseline, with the speedup growing as batch size and shared prefix length increase — for instance, when batch size is fixed at 1024, increasing the shared prefix from 1K to 16K tokens decreases Hydragen throughput by less than 15% while vLLM throughput drops by over 90%. The method also generalizes to tree-based prompt sharing patterns — demonstrated on competitive programming problems from the APPS dataset where two-level hierarchical sharing reduces evaluation time by an additional 55% over single-level sharing — establishing that the benefits of shared-prefix optimization can be compounded across multiple levels of overlap when sequences are organized hierarchically.

## 2. Context and Motivation

### The Core Problem: Shared Prefixes Expose Redundant Computation, Not Just Redundant Memory

LLM inference in production settings frequently involves batches of sequences that share a common prefix. A chatbot serving millions of users might prepend the same system prompt ("You are ChatGPT, a large language model trained by OpenAI…") to every user query. A code-generation system might use identical few-shot examples across thousands of candidate solutions. In these scenarios, the initial tokens of every sequence are identical, which means the attention keys and values computed for those prefix tokens are identical across the entire batch.

Prior work on shared-prefix optimization (most notably vLLM's PagedAttention; Kwon et al., 2023) recognized that naively storing a separate KV cache for every sequence wastes GPU memory by storing the same prefix keys and values repeatedly. Their solution was elegant: a virtual paging system that stores the prefix KV cache once and shares references to it across sequences. This is a **memory optimization** — it reduces the memory footprint of the KV cache, allowing larger batches to fit within GPU memory constraints.

However, this memory-centric view misses an equally important bottleneck: **the attention computation itself performs redundant work even when memory is not redundantly allocated**. The paper's critical observation is that FlashAttention and PagedAttention both compute attention by performing independent matrix-vector products for each sequence in the batch during decoding. Since each sequence has only a single attention query at each decoding step (the most recent token), the attention computation comprises $B$ independent matrix-vector products (one per sequence in the batch), each of which must read the prefix's keys and values from GPU memory. Whether those keys and values are stored once (vLLM) or redundantly (naive FlashAttention), they are **read from memory $B$ times** — once for each sequence's matrix-vector product.

This is a **memory-bandwidth bottleneck**, not a memory-capacity bottleneck. The arithmetic intensity of a matrix-vector product is inherently low: each element of the key/value matrix is read from memory but participates in only a single multiply-accumulate operation with the single query vector. As GPU computational capability has improved at a significantly faster rate than memory bandwidth across successive hardware generations (Figure 1, bottom right), this memory-bound operation has become an increasingly severe drag on throughput. Modern GPUs dedicate an increasingly large fraction of their total floating-point operations (FLOPs) to tensor cores — specialized hardware units that are designed exclusively for matrix-matrix multiplications, not matrix-vector products. When attention is computed as independent matrix-vector products, tensor cores sit idle, and the GPU operates far below its theoretical peak throughput.

### The Gap: No Existing Method Addresses Redundant Attention Reads

The paper identifies a specific gap in the literature: while previous work optimized the **storage** of shared prefix KV caches, no existing method optimizes the **computation** of attention over those shared prefixes to eliminate redundant memory reads. This gap exists across several categories of prior work:

**KV Cache Management Systems.** vLLM's PagedAttention (Kwon et al., 2023) avoids redundant storage and achieves a higher GPU cache hit rate when reading the prefix, which reduces the cost of redundant reads somewhat, but it does not fundamentally change the fact that attention is computed as independent matrix-vector products. The prefix keys and values are still read from memory once per sequence. Concurrent work, SGLang (Zheng et al., 2023), introduced RadixAttention, which dynamically identifies overlapping subsequences across incoming requests to avoid recomputing keys and values, but like vLLM, it focuses on the prefill cost of computing those keys and values rather than the decoding-time cost of attending over them repeatedly.

**FlashAttention (Dao et al., 2022; Dao, 2023).** FlashAttention is a hardware-aware exact attention implementation that reduces memory requirements from $O(N^2)$ to $O(N)$ and improves execution time by avoiding redundant data movement between GPU memory hierarchies. However, it is designed for the general case where each sequence has distinct keys and values. When applied to a batch of sequences with shared prefixes, FlashAttention treats each sequence independently and therefore redundantly reads the prefix KV cache for every sequence, missing the opportunity to amortize those reads across the batch.

**Architectural Approaches.** Multi-Query Attention (MQA; Shazeer, 2019) and Grouped-Query Attention (GQA; Ainslie et al., 2023) modify the transformer architecture to reduce the number of key-value attention heads, thereby shrinking the KV cache size. While these techniques reduce the total volume of data that must be read from memory, they do not change the fundamental issue: attention over a shared prefix still involves independent matrix-vector products that redundantly access the same memory. A smaller KV cache can accommodate larger batch sizes, but each sequence still performs its own memory-bound reads of the prefix.

**Hardware-Aware Algorithms.** The broader trend toward hardware-aware algorithm design (e.g., FlashFFTConv; Fu et al., 2023) has demonstrated that restructuring computations to leverage tensor cores and optimize I/O patterns can yield order-of-magnitude improvements. However, prior to Hydragen, no hardware-aware attention implementation had been designed to exploit the specific structure of shared prefixes to convert memory-bound operations into compute-bound operations.

### Why This Matters Now: Scaling Trends Make the Bottleneck Worse

The paper argues that this gap is becoming increasingly consequential for several reasons tied to deployment trends and hardware evolution:

**1. Batch sizes are growing as LLMs serve more users and explore more candidates.** In production chatbot deployments, hundreds of users may be serviced simultaneously, each with the same system prompt. In competitive programming systems like AlphaCode (Li et al., 2022), millions of candidate programs may be sampled per problem, each sharing the problem description and few-shot examples. Tree-of-Thoughts (Yao et al., 2023) and similar search-based reasoning methods sample many candidate reasoning paths from shared contexts. The batch size (number of sequences processed in parallel) directly amplifies the cost of redundant prefix reads — with batch sizes in the hundreds or thousands, reading the prefix KV cache once per sequence becomes the dominant inference cost.

**2. Context lengths are increasing faster than memory bandwidth.** As models support longer contexts (16K, 32K, 200K tokens), the shared prefix can contain large system prompts, long documents, or many few-shot examples. A longer prefix means a larger KV cache that must be read for every matrix-vector product. The paper's experiments demonstrate this acutely: with vLLM, increasing the prefix from 1K to 16K tokens at a fixed batch size of 1024 causes throughput to drop by over 90%, while the non-attention components of the model remain unaffected. The prefix length directly multiplies the cost of each redundant read.

**3. The hardware compute-to-bandwidth ratio is growing across GPU generations.** As shown in Figure 1 (bottom right), the fraction of total GPU FLOPs available through tensor cores (which can only perform matrix-matrix products) has increased dramatically from around 2016 to 2022. The NVIDIA A100 dedicates over 10× more FLOPs to tensor cores than to general-purpose arithmetic. When attention computes matrix-vector products, it uses only the general-purpose units, leaving the majority of the GPU's computational capacity unused. Hydragen's key insight is that shared prefixes create an opportunity to batch queries together and convert these matrix-vector products into matrix-matrix products, unlocking tensor core utilization.

### Where Prior Approaches Fall Short: A Concrete Example

Consider a batch of 1024 sequences, each sharing a 2048-token prefix (a realistic chatbot scenario with a substantial system prompt). During each decoding step:

- **FlashAttention** stores the prefix KV cache 1024 times, exhausting GPU memory, and reads each copy independently — 1024 matrix-vector products, each reading 2048 key-value vectors.
- **vLLM (PagedAttention)** stores the prefix KV cache once in shared memory, avoiding redundant storage. However, it still computes 1024 independent matrix-vector products, each reading the same 2048 key-value vectors from memory. The shared storage means the reads can sometimes hit GPU caches, but fundamentally the attention operation is still $B$ separate memory-bound operations.
- **Hydragen** decomposes attention, isolates the prefix computation, and replaces those 1024 matrix-vector products with a single matrix-matrix product: a $(1024 \times d)$ query matrix multiplied by a $(2048 \times d)$ key matrix. The prefix KV cache is read from memory once, all queries are processed simultaneously on tensor cores, and the result is distributed back to each sequence.

The arithmetic intensity of the Hydragen approach is far higher because each prefix key-value element participates in 1024 multiply-accumulates (one per sequence in the batch) rather than just one. This transforms prefix attention from a memory-bound operation into a compute-bound operation that leverages the GPU's most powerful hardware units.

### How This Paper Positions Itself

Hydragen is not proposed as an end-to-end inference system (the paper explicitly states it is "not intended to be an end-to-end inference solution" in Section 5), but rather as **a targeted optimization for the attention operation** that can be integrated into existing inference frameworks. Its contributions are:

1. **Attention decomposition** (Section 3.1): A mathematically exact method for splitting full-sequence attention into separate computations over the shared prefix and unique suffixes, enabling the prefix computation to be isolated for special treatment.

2. **Inter-sequence batching** (Section 3.2): A technique for merging attention queries across sequences when they attend over identical keys and values, replacing many matrix-vector products with fewer matrix-matrix products.

3. **Generalization to hierarchical sharing** (Section 3.3): An extension beyond simple prefix-suffix decomposition to tree-structured sharing patterns (where sequences may share at multiple levels, e.g., a global few-shot prompt plus per-problem descriptions), enabling nested application of the same batching principle.

The paper positions Hydragen relative to existing work along several axes:

- **Versus vLLM:** Hydragen addresses the complementary problem of redundant reads (not redundant storage). The two approaches are orthogonal and could be combined — PagedAttention for memory management and Hydragen for attention computation.

- **Versus FlashAttention:** Hydragen uses FlashAttention as a building block (for suffix attention and as the fast attention primitive for prefix attention), but adds the decomposition and batching logic on top. Hydragen does not require custom CUDA kernels; it is implemented entirely in PyTorch plus calls to existing fast attention libraries, making it portable to other hardware platforms.

- **Versus architectural changes (MQA/GQA):** Hydragen is a systems-level optimization that works with standard multi-head attention. When combined with GQA models, Hydragen benefits additionally because the reduced KV cache size allows even larger batch sizes, further amplifying the speedup from inter-sequence batching.

- **Versus concurrent work (RadixAttention):** Both methods exploit sharing patterns, but RadixAttention focuses on prefill-time reuse (avoiding recomputation of keys/values for overlapping prefixes), while Hydragen focuses on decoding-time attention (avoiding redundant reads of already-computed keys/values). The two could be combined: RadixAttention identifies and computes shared prefixes; Hydragen then efficiently attends over them during decoding.

The paper's framing emphasizes that shared prefixes are not just a memory management opportunity — they fundamentally change the compute structure of attention in a way that can be exploited through batching. This reframing from a memory problem to a compute problem is the conceptual contribution that motivates the technical approach.

## 3. Technical Approach

### 3.1 Reader Orientation

Hydragen is a GPU kernel and algorithmic strategy — not a standalone inference server, but an exact, drop-in implementation of the scaled dot-product attention operation — that re-organizes *how* attention is computed when a batch of sequences shares a common prefix, so that the prefix's keys and values are read from memory only once and the per-sequence queries are processed together as a single batched matrix-matrix multiplication instead of as many independent matrix-vector products. It solves the problem that during LLM decoding with shared prefixes, the attention operation is memory-bound and wastes GPU tensor cores because each sequence in the batch redundantly reads the same prefix data from memory to perform its own tiny, low-arithmetic-intensity computation; the shape of the solution is a **decompose-then-batch** strategy: split full attention into separate prefix and suffix sub-computations, batch all sequences' queries together for the prefix sub-computation (where keys and values are identical across sequences), and then combine the results exactly using stored log-sum-exp values.

### 3.2 Big-Picture Architecture (Diagram in Words)

The Hydragen system consists of four major components, applied at every transformer layer during decoding:

1. **Attention Decomposer** — Takes the full keys `$K$` and values `$V$` for each sequence, splits them at the boundary between the shared prefix and the unique suffix, and routes each partition to a separate attention sub-computation. It also computes and stores the log-sum-exp (LSE) of the attention scores for each sub-computation, which will be needed later to recombine the results.

2. **Inter-Sequence Query Batcher** — For the prefix sub-computation only (where all sequences share identical keys and values), it reshapes the batch of per-sequence query vectors (each of shape `$[1, d]$`) into a single large query matrix (shape `$[B \times 1, d]$`, or more generally `$[B \times n_q, d]$`) by concatenating queries across the batch dimension. This batched query matrix is then treated as the queries for a single sequence attending over the prefix.

3. **Attention Primitives (FlashAttention for Prefix, FlashAttention/Triton Kernel for Suffix)** — Two separate calls to fast attention kernels. The prefix attention sees a batched query matrix and a single set of prefix keys and values; this is now a compute-bound matrix-matrix product that runs efficiently on tensor cores. The suffix attention sees per-sequence queries and per-sequence suffix keys/values; these remain independent matrix-vector products, computed normally.

4. **Softmax Recombiner** — Takes the two attention outputs (prefix output `$O_{\text{prefix}}$` and suffix output `$O_{\text{suffix}}$`, along with their respective LSEs), weights each output by its exponentiated LSE (its partial softmax denominator), sums them, and normalizes by the sum of the exponentiated LSEs. This recovers the exact result of full-sequence attention without ever having computed full-sequence attention explicitly.

The flow for one decoding step is:

1. The input query vectors `$Q$` (shape `$[B, 1, d]$`) arrive, one per sequence in the batch.
2. The Attention Decomposer identifies the prefix keys `$K_{\text{pref}}$` (shared, shape `$[L_{\text{pref}}, d]$`) and values `$V_{\text{pref}}$`, and the suffix keys `$K_{\text{suff}}$` (per-sequence, shape `$[B, L_{\text{suff}, i}, d]$`) and values `$V_{\text{suff}}$`.
3. The Inter-Sequence Query Batcher reshapes `$Q$` into `$Q_{\text{batched}}$` of shape `$[1, B, d]$` (merging batch into sequence dimension for a single logical sequence).
4. The fast attention primitive computes `$O_{\text{pref}}, \text{LSE}_{\text{pref}} = \text{Attention}(Q_{\text{batched}}, K_{\text{pref}}, V_{\text{pref}})$` using FlashAttention, producing output of shape `$[1, B, d]$` and LSE of shape `$[1, B, 1]$`.
5. The same or a different attention primitive computes `$O_{\text{suff}}, \text{LSE}_{\text{suff}} = \text{Attention}(Q, K_{\text{suff}}, V_{\text{suff}})$` for each sequence independently, producing outputs of per-sequence shapes.
6. The Softmax Recombiner unbatches `$O_{\text{pref}}$` back to `$[B, 1, d]$`, computes the weighted sum `$O_{\text{pref}} \cdot \exp(\text{LSE}_{\text{pref}}) + O_{\text{suff}} \cdot \exp(\text{LSE}_{\text{suff}})$`, divides by `$\exp(\text{LSE}_{\text{pref}}) + \exp(\text{LSE}_{\text{suff}})$`, and produces the final attention output `$O$` of shape `$[B, 1, d]$`.

For hierarchical sharing (Section 3.3), this pattern is applied recursively: the batch is organized as a tree where each node's token sequence is shared by all descendants, and attention is decomposed at every node, with inter-sequence batching applied at every level of the tree.

### 3.3 Roadmap for the Deep Dive

- **First**, the attention decomposition formula (Equation 5) and its mathematical justification — this is the foundational algebraic trick that makes everything else possible, so understanding why it is exact and how it uses log-sum-exp to recombine partitioned softmax results is essential.
- **Second**, the inter-sequence batching mechanism — how the decomposition enables queries across sequences to be merged into a single attention operation, what the computational cost implications are, and why this transforms the prefix attention from memory-bound to compute-bound.
- **Third**, the generalization to hierarchical sharing — how the decomposition-plus-batching pattern extends from a flat prefix-suffix split to tree-structured overlaps, and what changes in the implementation.
- **Fourth**, the throughput estimation framework — how to predict when Hydragen will provide meaningful speedups based on batch size, prefix length, suffix length, attention architecture, and hardware characteristics.
- **Fifth**, the implementation details — the specific libraries, kernels, and design choices made in the proof-of-concept, including the handling of CUDA graphs and the simplicity of the codebase.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems paper** whose core idea is that when sequences share a prefix, the attention computation can be restructured to amortize memory reads across the batch and replace memory-bound matrix-vector operations with compute-bound matrix-matrix operations, enabling efficient use of tensor cores without any loss of numerical precision.

#### The Attention Decomposition Formula

The central mathematical insight of Hydragen is that scaled dot-product attention over a concatenated key-value sequence can be exactly decomposed into separate attention computations over the sub-sequences, then recombined using their respective softmax denominators. This decomposition is what allows the shared prefix portion to be isolated for batched processing.

**The general attention operation.** Standard scaled dot-product attention (Equation 1) operates on queries `$Q \in \mathbb{R}^{N_q \times d}$`, keys `$K \in \mathbb{R}^{N_{kv} \times d}$`, and values `$V \in \mathbb{R}^{N_{kv} \times d}$` to produce output `$O \in \mathbb{R}^{N_q \times d}$`:

$$O = \text{SDP}(Q, K, V) = \text{softmax}\left(\frac{Q K^T}{\sqrt{d}}\right) V$$

where `$N_q$` is the number of query tokens, `$N_{kv}$` is the number of key/value tokens, and `$d$` is the per-head dimension. During decoding, `$N_q = 1$` (one query per sequence, the current token) while `$N_{kv} \gg 1$` (all previous tokens in the sequence, stored in the KV cache), making the multiplications with `$K^T$` and `$V$` matrix-vector products.

**Partitioning the keys and values.** The key insight begins with observing that if we split the keys and values into two contiguous sub-sequences — the shared prefix and the unique suffix — we can write:

$$K = K_1 \parallel K_2$$
$$V = V_1 \parallel V_2$$

where `$\parallel$` denotes concatenation along the sequence (row) dimension. The challenge is that the softmax operation involves a sum over all exponentiated attention scores across the *entire* sequence, so we cannot naively compute `$\text{SDP}(Q, K_1, V_1)$` and `$\text{SDP}(Q, K_2, V_2)$` separately and add them together — each sub-computation would normalize by its own partial sum, not the full-sequence sum.

**The log-sum-exp (LSE) trick.** The solution is to store, alongside each sub-computation's output, the log of the softmax denominator — formally called the log-sum-exp of the attention scores:

$$\text{LSE}(Q, K) = \log\left(\text{sum}\left(\exp\left(\frac{Q K^T}{\sqrt{d}}\right), \text{dim} = 1\right)\right)$$

where `$\text{LSE}(Q, K) \in \mathbb{R}^{N_q}$` is a vector containing, for each query position, the natural logarithm of the sum of exponentiated dot products between that query and all key vectors. This value is the log of the denominator that softmax divides by.

In plain language: for each query, we compute all its attention scores (dot products with keys, scaled by `$1/\sqrt{d}$`), exponentiate them, sum them into a single number per query, and take the natural log. The result is a per-query scalar that captures the normalization factor.

**The recombination formula.** Given the two partial attention outputs and their LSEs, the full attention result is recovered as:

$$\text{SDP}(Q, K, V) = \frac{\text{SDP}(Q, K_1, V_1) \cdot e^{\text{LSE}(Q, K_1)} + \text{SDP}(Q, K_2, V_2) \cdot e^{\text{LSE}(Q, K_2)}}{e^{\text{LSE}(Q, K_1)} + e^{\text{LSE}(Q, K_2)}}$$

**What it computes:** The right-hand side performs three steps. First, it multiplies each partial attention output by its associated softmax denominator — `$\text{SDP}(Q, K_1, V_1) \cdot \exp(\text{LSE}(Q, K_1))$` recovers the raw numerator of the weighted value sum from sub-sequence 1 (before division by the full softmax denominator). Second, it sums these numerators from both sub-sequences. Third, it divides by the sum of the two denominators, which is exactly the full-sequence softmax denominator (since `$\exp(\text{LSE}(Q, K_1)) + \exp(\text{LSE}(Q, K_2)) = \sum_1 \exp(s_{1i}) + \sum_2 \exp(s_{2j}) = \sum_{\text{all}} \exp(s_k)$`). The output is numerically identical to `$\text{SDP}(Q, K_1 \parallel K_2, V_1 \parallel V_2)$`.

**Why this form:** The key property that makes this decomposition valid is that the softmax operation's denominator is additive across disjoint sub-sequences in the exponentiated domain: the sum of exponentiated scores over the full sequence equals the sum of the exponentiated scores over sub-sequence 1 plus the sum over sub-sequence 2. The LSE values store these logs of the partial sums, and exponentiating them recovers the original sums. The decomposition would *not* work with an arithmetic mean (where denominators are simply the count of elements) because adding partial means requires knowing the count from each partition. It works specifically because softmax normalizes by a sum of exponentials, which cleanly factorizes across disjoint partitions. This is the same mathematical property that enables FlashAttention's tiled/blocked softmax computation (Dao et al., 2022), and Hydragen inherits that technique but applies it across the batch dimension rather than within a single sequence's tiles.

**The proof (Appendix A).** The paper provides a step-by-step algebraic verification. Starting from the definition of SDP with the softmax expanded, substituting the LSE-based expression for each partial result, the cross-multiplication by the partial denominators cancels with the partial softmax's divisions, the numerators sum to the full-sequence numerator, and the combined denominator is exactly the full-sequence LSE exponentiated. The derivation is straightforward and confirms that no approximation is introduced — this is an exact algebraic equivalence.

**What happens computationally in Hydragen.** During each decoding step:

1. The system calls a fast attention primitive (FlashAttention) to compute `$\text{SDP}(Q, K_{\text{pref}}, V_{\text{pref}})$` for the shared prefix, with the additional request to return the LSE of the attention scores. FlashAttention already computes this intermediate value during its tiled softmax and can return it at negligible extra cost.
2. The system separately calls another attention primitive on the per-sequence suffixes, obtaining `$\text{SDP}(Q, K_{\text{suff}}, V_{\text{suff}})$` and `$\text{LSE}(Q, K_{\text{suff}})$`.
3. A small element-wise kernel (written in Triton for non-hierarchical inputs, or as PyTorch operations) applies the recombination formula: weigh each output by its exponentiated LSE, sum, and normalize.

The critical practical detail is that no custom CUDA is required — the recombination is a simple element-wise operation on tensors whose sizes are proportional to the batch size and head dimension, not the sequence length.

#### Inter-Sequence Batching of Prefix Attention

Attention decomposition alone does not improve performance — in fact, it adds overhead (the LSE storage and the recombination step). The performance gains come from what the decomposition **enables**: recognizing that, for the prefix sub-computation, the keys and values are identical across all sequences in the batch, which means the queries can be merged into a single, larger attention computation.

**Why independent attention over shared keys is wasteful.** In standard batched attention (FlashAttention or vLLM), each sequence has its own query vector `$q_i \in \mathbb{R}^{1 \times d}$` and the computation proceeds as `$B$` independent operations:

$$\text{For each } i \in \{1, \ldots, B\}: \quad o_i = \text{softmax}\left(\frac{q_i K_{\text{pref}}^T}{\sqrt{d}}\right) V_{\text{pref}}$$

Each operation reads the entire `$K_{\text{pref}}$` and `$V_{\text{pref}}$` matrices from GPU memory (or from caches, in vLLM's case) but uses each element in only a single multiply-accumulate with the single query vector `$q_i$`. The arithmetic intensity — the ratio of floating-point operations to bytes transferred — is extremely low because the dominant cost is reading `$K_{\text{pref}}$` and `$V_{\text{pref}}$` from memory, and each byte read contributes to only `$O(1)$` arithmetic operations per query.

**Batching queries across sequences.** The key observation is that attention queries are independent of each other — the output for query `$q_i$` depends on `$q_i$`, `$K$`, and `$V$` alone, not on any other query `$q_j$`. Therefore, if multiple sets of queries are attending over **identical** keys and values, they can be combined into a single attention operation with a larger number of queries. Formally, instead of computing:

$$o_i = \text{SDP}(q_i, K_{\text{pref}}, V_{\text{pref}}) \quad \text{for } i = 1, \ldots, B$$

Hydragen computes:

$$O_{\text{batched}} = \text{SDP}\left( \begin{bmatrix} q_1 \\ q_2 \\ \vdots \\ q_B \end{bmatrix}, K_{\text{pref}}, V_{\text{pref}} \right)$$

where the batched query matrix has shape `$[B, d]$` (for single-query-per-sequence decoding) or `$[B \times n_q, d]$` (for multi-query scenarios). The output `$O_{\text{batched}}$` has shape `$[B, d]$`, and the `$i$`-th row is exactly `$o_i$` — the same result as if computed independently.

**What this does to arithmetic intensity.** In the batched version, each element of `$K_{\text{pref}}$` is read from memory once but now participates in `$B$` multiply-accumulate operations (one with each of the `$B$` query vectors). The arithmetic intensity scales linearly with the batch size: the same number of bytes are transferred, but `$B$` times more arithmetic operations are performed. This transforms the operation from memory-bound (bottlenecked waiting for data from GPU memory) to compute-bound (bottlenecked waiting for arithmetic units to finish), as long as `$B$` is sufficiently large.

**Why this enables tensor core utilization.** Tensor cores — the specialized matrix-multiplication units on modern NVIDIA GPUs — are designed to compute operations of the form `$D = A \times B + C$` where `$A$` and `$B$` are matrices. A matrix-vector product is technically a special case of matrix-matrix multiplication (where one matrix has a singleton inner dimension equal to 1), but tensor cores are optimized for large inner dimensions and cannot be efficiently utilized when one operand is a vector. The batched query matrix restores the matrix-matrix shape: `$Q_{\text{batched}} \cdot K_{\text{pref}}^T$` is a proper `$[B, L_{\text{pref}}]$` matrix multiplication that maps cleanly onto tensor cores, enabling the prefix attention to run at tensor-core throughput rather than general-purpose arithmetic throughput.

**The concrete memory access pattern.** In the unbatched case, `$K_{\text{pref}}$` (size `$L_{\text{pref}} \times d$`) is read from GPU global memory (or L2 cache) `$B$` separate times — once per sequence. Each read transfers `$L_{\text{pref}} \cdot d$` elements. In Hydragen's batched case, `$K_{\text{pref}}$` is read exactly once, and the queries (size `$B \times d$`) are read once. The total memory traffic is reduced by a factor approaching `$B$` for the prefix portion of attention. This is why the speedup grows with batch size: larger `$B$` means more redundant reads are eliminated.

**Why suffixes cannot be batched.** The suffix keys and values are different for every sequence — each sequence has generated different completion tokens. Therefore, there is no key-value overlap to exploit, and suffix attention must proceed as independent matrix-vector products. The decomposition is essential precisely because it separates the portion of the computation that *can* be batched (the prefix) from the portion that *cannot* (the suffixes). Without decomposition, the presence of distinct suffixes would prevent batching the entire attention operation.

**Implementation in code (Appendix B pseudocode).** The paper provides PyTorch-style pseudocode that shows the key operations:

1. The queries `$q$` arrive with shape `$[B, 1, \text{nheads}, d]$`.
2. They are reshaped to `$[1, B \times 1, \text{nheads}, d]$` — the batch dimension is merged into the sequence dimension of a single logical sequence.
3. The fast attention primitive is called with this batched query and the prefix keys/values, which have been unsqueezed to add a batch dimension of 1: `$K_{\text{pref}}$` goes from `$[L_{\text{pref}}, \text{nheads}, d]$` to `$[1, L_{\text{pref}}, \text{nheads}, d]$`.
4. The prefix output (shape `$[1, B, \text{nheads}, d]$`) and LSE (shape `$[1, B, \text{nheads}]$`) are reshaped back to `$[B, 1, \text{nheads}, d]$` and `$[B, 1, \text{nheads}]$`.
5. Suffix attention is called normally with the original unbatched queries and per-sequence suffix keys/values.
6. The `combine_lse` function applies the softmax recombination using the exponentiated LSEs as weights.

The pseudocode is notably concise — the core logic is about 30 lines of Python with no custom CUDA kernels — which the authors emphasize as a practical advantage for portability across hardware platforms (TPUs, other accelerators) that also have hardware specialized for matrix multiplications.

#### Hierarchical Sharing Generalization

The prefix-suffix decomposition described so far assumes a flat structure: all sequences in the batch share exactly the same starting sub-sequence, followed by entirely distinct suffixes. However, many practical scenarios involve richer sharing patterns where sequences form a **tree** of overlaps.

**The competitive programming example (Figure 2).** Consider evaluating a set of competitive programming problems where, for each problem, many candidate solutions are sampled. The few-shot prompt (a couple of solved example problems) is shared across *all* candidate solutions for *all* problems. Each problem's description is shared across all candidate solutions for *that problem* but not across other problems. The candidate solutions themselves are distinct across all sequences. This creates a two-level tree:

- **Level 0 (root):** The few-shot prompt — shared by all sequences in the batch.
- **Level 1:** Per-problem descriptions — each shared by all sequences in that problem's group.
- **Level 2 (leaves):** Unique candidate solutions — no sharing.

Traditional prefix-suffix decomposition would only identify the few-shot prompt as shared, treating the problem description as part of each sequence's unique suffix. This misses a second layer of sharing opportunity.

**Generalizing decomposition to trees.** To apply Hydragen to a tree, the decomposition is performed recursively at every internal node of the tree. At each node:

1. The token sequence associated with that node is the "local prefix" — it is shared by all descendant sequences.
2. The keys and values from that node are separated out, just as in the flat case.
3. All queries from descendant sequences are batched together into a single attention operation over this local prefix.
4. The output and LSE from each node-level attention are combined with the results from other nodes along the path from root to leaf, using the same LSE-based recombination formula.

The recombination proceeds hierarchically: for a sequence at a leaf, its full attention output is the combination of (attention over the root node) + (attention over its level-1 node) + (attention over its unique suffix), all recombined using the LSE values from each sub-computation.

**What changes in the implementation.** The key difference from the flat case is that the query batching at each node must respect the tree structure: only queries from sequences that are descendants of a given node should be batched together for that node's attention. In the competitive programming example:

- At the root (few-shot prompt): all queries from all sequences are batched together — batch size equals the total number of candidate solutions across all problems.
- At each level-1 node (per-problem description): only queries from candidate solutions for that specific problem are batched together — batch size equals the number of samples per problem.
- At the leaves (candidate solutions): no batching occurs — each sequence attends independently over its own generated tokens.

**Performance benefits beyond the flat case.** Hierarchical sharing provides two advantages:

1. **Additional batching of reads.** The problem description (level 1) is now treated as a shared prefix for all of that problem's candidate solutions, so its keys and values are read from memory once per problem group rather than once per candidate solution. This provides a second tier of memory-traffic reduction beyond what the root-level sharing alone achieves.

2. **Memory savings from non-redundant storage.** Without hierarchical sharing, the problem description's KV cache is stored separately for every candidate solution (if using a naive approach) or at least accessed independently. With two-level Hydragen, the problem description is stored once and shared across its candidate solutions, reducing total KV cache memory footprint and allowing larger batch sizes.

**Empirical demonstration (Section 4.4, Figure 6).** The APPS competitive programming benchmark with 120 problems, two few-shot examples, and 128 candidate solutions per problem demonstrates the compound benefit. Single-level Hydragen (sharing only the few-shot prompt) provides one level of speedup. Two-level Hydragen (sharing both few-shot prompt and per-problem descriptions) further reduces evaluation time by 18% even at the same batch size (from improved attention efficiency), and by 55% overall when the memory savings are also used to increase the batch size (from 4 to 32 problems processed simultaneously in one batch). This experiment confirms that hierarchical sharing is not merely a theoretical generalization but concretely improves throughput in realistic multi-problem evaluation settings.

#### Estimating Throughput Improvements

Hydragen does not uniformly accelerate all LLM inference workloads. Whether it provides meaningful end-to-end throughput improvements depends on the characteristics of the specific deployment setting. The paper provides a framework for reasoning about when Hydragen will be effective.

**The condition for Hydragen to matter: attention must be a significant fraction of total decoding time.** During LLM decoding, the forward pass consists of alternating attention and MLP blocks (plus normalization and residual connections). The MLP blocks are compute-bound matrix-matrix multiplications that benefit from batching and can use tensor cores. The attention blocks, in the absence of Hydragen, are memory-bound matrix-vector products that do not use tensor cores. If attention is a small fraction of total decoding time (e.g., with small batch sizes or short sequence lengths where the MLP dominates), then accelerating attention — even dramatically — will not translate into proportional end-to-end speedup. The paper uses a "No Attention" baseline (where all attention computations are removed from the transformer, leaving only the linear projections and MLPs) as an upper bound on achievable throughput to help quantify how close different methods come to saturating the non-attention components.

**Factors that increase attention's fraction of total time** — and therefore increase Hydragen's potential impact:

- **Large batch sizes.** As batch size grows, the MLP's matrix multiplications become larger (more tokens to process in parallel), so their arithmetic intensity improves. But attention remains `$B$` separate matrix-vector products whose intensity does not improve with batch size. The cost of attention therefore grows as a fraction of total time with batch size. This is visible in Figure 3(a): at batch size 32, all methods achieve throughput within 50% of the No Attention ceiling; at batch size 1024, vLLM throughput drops to far below the ceiling while Hydragen stays within 50%.

- **Long shared prefixes.** The cost of reading the prefix KV cache scales linearly with prefix length. For vLLM, this cost is multiplied by the batch size (each sequence reads the prefix). For Hydragen, the prefix is read once regardless of batch size. Therefore, longer prefixes amplify Hydragen's relative advantage. Figure 3(b) demonstrates this acutely: at batch size 1024, increasing the prefix from 1K to 16K tokens causes vLLM throughput to drop by over 90%, while Hydragen throughput drops by less than 15%.

- **Models with standard multi-head attention (MHA).** MHA stores one set of keys and values per attention head. Multi-Query Attention (MQA; Shazeer, 2019) and Grouped-Query Attention (GQA; Ainslie et al., 2023) reduce the number of key-value heads, shrinking the KV cache size. A smaller KV cache means less data to read from memory, so the cost of the memory-bound matrix-vector products is lower to begin with, and Hydragen's relative speedup is smaller. However, the smaller KV cache also allows larger batch sizes to fit in GPU memory, which can increase Hydragen's absolute speedup (more sequences benefit from shared reads).

- **GPUs with a high compute-to-bandwidth ratio.** Modern GPUs (H100, L40S) have even higher ratios of tensor-core FLOPs to memory bandwidth than the A100 used in most experiments. On these GPUs, memory-bound operations are even more bottlenecked relative to compute-bound operations, so converting memory-bound to compute-bound operations yields larger speedups. The paper's microbenchmarks on an L40S (Appendix C.2, Figure 7) show even larger speedups than on the A100, confirming this trend.

**The suffix length penalty.** Hydragen makes no optimization to suffix attention — it is computed as standard memory-bound matrix-vector products. As decoding proceeds and completions grow longer, the suffixes grow, and the fraction of total attention time spent on suffixes (unaccelerated) increases while the fraction spent on the prefix (accelerated) stays constant. This means Hydragen's throughput advantage is highest for the earliest generated tokens and gradually diminishes as more tokens are generated. The microbenchmarks in Figure 4 show this explicitly: at a fixed batch size and prefix length, the speedup over FlashAttention decreases as suffix length grows from 0 to 500 tokens. This has practical implications for deployment: for applications that generate long completions, the average speedup over the entire generation will be lower than the speedup for the first few tokens. However, if the prefix is very long relative to typical completion lengths (as in the long document QA experiment with a ~20K-token prefix and short question-answering completions), the prefix dominates and Hydragen maintains near-ceiling throughput throughout.

**The prefill is excluded from benchmarks.** The paper's end-to-end throughput measurements (Section 4.1) are "decode-only" — they exclude the time required for the prefill stage where the prompt's keys and values are initially computed. This is justified because (a) in many serving scenarios, the prefill is a one-time cost amortized over many decoding steps and many sequences, and (b) the prefill stage is already compute-bound (matrix-matrix multiplications due to many query tokens processed in parallel) and benefits less from Hydragen's batching optimization. For very long prefixes, prefill time can be substantial, and the paper acknowledges this by reporting that vLLM appears to redundantly detokenize the prompt for every sequence in the batch during prefill (which can take minutes for large batch sizes and long sequences), a cost that Hydragen avoids by sharing the prefix representation.

#### Implementation Details

The paper emphasizes that Hydragen's implementation is intentionally simple — requiring no custom CUDA code — to maximize portability and ease of integration. The entire implementation is in PyTorch (for non-hierarchical inputs, with a Triton kernel for the LSE combination step) plus calls to two existing fast attention libraries.

**Fast attention primitives used:**

1. **FlashAttention (via the `flash-attn` package, version 2.3.6).** Used for prefix attention because it returns the LSE values needed for softmax recombination and is optimized for large matrix-matrix products. The prefix attention operates with `$N_q = B$` (batched queries) and `$N_{kv} = L_{\text{pref}}$` (shared prefix), which is a compute-bound regime where FlashAttention's tiling and parallelism strategies are effective.

2. **Triton kernel from `xformers`.** Used for suffix attention for two reasons: first, it allows changing sequence lengths in the suffix KV cache across decoding steps (as completions grow); second, it adheres to the constraints required to use CUDA graphs, which reduce CPU kernel launch overhead — important because decoding steps with small batch sizes and short suffixes can be very fast (tens of microseconds), where CPU overhead would otherwise dominate.

**The `combine_lse` function (Appendix B).** The recombination step applies Equation 5 numerically stably. Directly exponentiating LSE values can cause overflow if LSEs are large. The implementation uses the standard log-sum-exp trick for numerical stability:

1. Compute `$m = \max(\text{LSE}_1, \text{LSE}_2)$` — the maximum of the two LSEs.
2. Compute adjustment factors `$\text{adj}_i = \exp(\text{LSE}_i - m)$` — these are now in the range `$(0, 1]$` and will not overflow.
3. The new denominator is `$\text{adj}_1 + \text{adj}_2$`.
4. The aggregated output is `$(\text{out}_1 \cdot \text{adj}_1 + \text{out}_2 \cdot \text{adj}_2) / (\text{adj}_1 + \text{adj}_2)$`.

This is mathematically equivalent to Equation 5 (the factor `$e^{-m}$` cancels in both numerator and denominator) but avoids numerical overflow. For hierarchical sharing, this recombination is applied repeatedly along the path from root to leaf.

**CUDA graph compatibility.** CUDA graphs allow the entire sequence of GPU kernel launches for a model forward pass to be recorded once and replayed without CPU involvement, dramatically reducing launch overhead. However, CUDA graphs require that tensor shapes and memory allocations are fixed across replays. The Triton kernel for suffix attention is chosen specifically because it supports this constraint even as suffix lengths change (e.g., by operating on padded tensors with a mask). The prefix attention's batch size and prefix length are fixed across decoding steps, so it is trivially CUDA-graph compatible.

**Model support.** The implementation targets the Llama family of models (Llama, Llama 2, CodeLlama; Touvron et al., 2023a,b; Rozière et al., 2023), which use standard multi-head attention with rotary position embeddings. The authors note that porting to other architectures would be straightforward because Hydragen operates at the attention-operation level and does not depend on architectural details beyond the standard `(Q, K, V)` interface.

**Limitation: manual specification of sharing structure.** The proof-of-concept implementation requires the user to explicitly specify where sharing occurs — i.e., which portion of each sequence is the shared prefix, and (for hierarchical sharing) the tree structure of overlaps. This is not a fundamental limitation but a scoping decision: the paper positions Hydragen as an attention optimization that can be integrated into inference serving systems (like vLLM or SGLang's RadixAttention) that dynamically identify sharing patterns from incoming requests. The authors flag this integration as important future work (Section 5).

**No custom CUDA kernels.** This design choice is deliberate and notable. PagedAttention (vLLM) and many other high-performance attention implementations require custom CUDA kernels to manage the paged memory layout and perform reads and writes with virtual-to-physical address translation. Hydragen avoids this complexity entirely by decomposing attention into standard FlashAttention calls plus simple element-wise recombination. This makes the codebase portable: any platform with a fast matrix-multiplication primitive and an attention implementation that returns LSE (or can be modified to do so) can run Hydragen. The authors specifically mention TPUs as a target platform, since TPUs also have dedicated matrix-multiplication units (systolic arrays) and would benefit from the same batched attention strategy.

**Memory considerations.** Hydragen does not directly address KV cache memory management — it is complementary to systems like PagedAttention that do. In the experiments, Hydragen uses its own simple memory management: the prefix KV cache is stored once and shared, while per-sequence suffix caches are stored independently. The hierarchical sharing extension naturally reduces memory consumption by sharing at multiple levels (e.g., per-problem descriptions in competitive programming), but this is a consequence of the sharing pattern being exploited, not a separate memory-management subsystem. For production deployment, Hydragen would likely be combined with PagedAttention or a similar paging system for fine-grained memory management of the suffix KV caches.

## 4. Key Insights and Innovations

### Innovation 1: Reframing Shared Prefixes from a Memory-Capacity Problem to a Memory-Bandwidth Problem

The dominant intellectual framing for shared-prefix optimization prior to this work was **memory-capacity reduction**: shared prefixes create redundant storage of the KV cache, so the solution is to store the prefix once and share references. vLLM's PagedAttention (Kwon et al., 2023) fully solved this framing with an elegant virtual paging system that eliminates duplicate storage and enables fine-grained memory management. If shared prefixes were *only* a memory-capacity problem, vLLM would represent a near-complete solution — you store the prefix once, you fit larger batches, and you're done.

Hydragen's fundamental conceptual move is to argue that memory capacity is the *wrong bottleneck to focus on* for decoding throughput. Even when the prefix KV cache is stored once (as vLLM does), the attention computation **reads it from memory B times** — once for each sequence's independent matrix-vector product — because FlashAttention and PagedAttention both compute attention per-sequence rather than across sequences. This shifts the diagnosis from "we're wasting GPU memory" to "we're wasting GPU memory **bandwidth**," which is a more severe and hardware-trend-driven bottleneck.

Why this reframing is intellectually significant: memory capacity and memory bandwidth are qualitatively different constraints with different scaling properties. Memory capacity can be addressed by adding more GPUs or offloading to CPU/disk (as in FlexGen, Sheng et al., 2023, and DeepSpeed-Inference, Aminabadi et al., 2022). Memory bandwidth, however, is a hard per-GPU limit that degrades with batch size and sequence length, and — critically — the ratio of compute to bandwidth has been growing rapidly across GPU generations as tensor cores claim an increasing fraction of total FLOPs (Figure 1, bottom right). By reframing the problem, Hydragen identifies that the shared-prefix setting contains a structural property — identical keys and values across sequences — that can convert bandwidth-bound operations into compute-bound operations, something that optimizing for storage alone does not exploit.

The reframing also explains a non-obvious empirical observation: vLLM throughput degrades dramatically with prefix length (Figure 3b, >90% drop from 1K to 16K tokens at batch size 1024) even though vLLM already avoids redundant storage. If the bottleneck were capacity, longer prefixes would only limit maximum batch size, not per-step throughput for a given batch. The throughput degradation confirms that the bandwidth cost of repeatedly reading the prefix — even from a shared memory location — is the real bottleneck. Hydragen's reframing correctly predicts this behavior and provides the remedy.

This is a **fundamental shift**, not an incremental refinement, because it changes what practitioners should optimize for (bandwidth, not capacity), what hardware trends to track (compute-to-bandwidth ratio, not total memory), and what algorithmic properties matter (arithmetic intensity of the attention operation, not just memory footprint).

---

### Innovation 2: Cross-Sequence Query Batching as a Hardware-Aware Primitive for Attention

Prior to Hydragen, the standard decomposition of LLM inference optimization separated concerns along model-parallelism and data-parallelism axes: you could batch *sequences* together to increase MLP utilization (data parallelism within a forward pass), or you could shard *model parameters* across devices (tensor parallelism). But attention queries during decoding were always treated as independent per-sequence because each sequence's KV cache is distinct. The field's assumption — implicit in FlashAttention, PagedAttention, and every standard inference framework — was that attention over the full sequence must be computed per-sequence because each sequence has different keys and values.

Hydragen introduces a third axis that cuts across this assumption: **cross-sequence batching of attention queries when the key-value context overlaps**. The key observation is that queries are independent of each other in the attention operation — `o_i = softmax(q_iK^T / sqrt(d))V` depends only on `q_i`, `K`, and `V` — so if `K` and `V` are identical across sequences, the queries can be merged into one batched operation. This is a genuinely new primitive: inter-sequence batching for attention, analogous to how inter-token batching in the prefill stage (many queries from one sequence) already produces efficient matrix-matrix products.

What makes this intellectually distinctive is that it identifies an **algebraic property of attention** (query independence) combined with a **structural property of the data** (shared prefixes) to enable a **hardware-level transformation** (matrix-vector to matrix-matrix). It is not obvious that this combination is exploitable because the presence of unique suffixes in each sequence would seem to prevent any batching — you cannot batch full-sequence attention when suffixes differ. The decomposition (Innovation 3, covered below in the paper's structure) is what enables the batching, but the conceptual insight is that batching *across* sequences is possible at all. This was not explored in prior work because the dominant mental model treated each sequence as an irreducible unit of attention computation.

The significance extends beyond raw throughput numbers. Cross-sequence batching changes how we should think about the economics of shared-context inference: the marginal cost of adding another sequence to a batch (in terms of prefix attention time) is near-zero because the prefix KV cache read is amortized. This has algorithmic implications — it makes it practically costless to increase the number of candidate samples in self-consistency or majority-voting schemes (Wang et al., 2023), and it encourages using longer shared prefixes (more few-shot examples, more system instructions, longer retrieved documents) because the throughput penalty for prefix length is nearly eliminated (Figure 3b, <15% drop from 1K to 16K tokens for Hydragen). The throughput ceiling demonstrated by the "No Attention" baseline in Figure 3b — Hydragen remaining within 70% of that ceiling across all prefix lengths — shows that prefix attention has been nearly removed as a bottleneck, which is a qualitative change in what deployment strategies are viable.

This is a **fundamental primitive**, not an incremental optimization, because it identifies a new dimension of parallelism that was previously invisible. Like FlashAttention's insight that attention can be computed in tiles to reduce I/O, Hydragen's cross-sequence batching reveals a structural opportunity in shared-prefix workloads that transforms the compute characteristics of the operation.

---

### Innovation 3: Exact Decomposition as the Enabling Mechanism for Partial-Context Batching

A natural question when learning about Hydragen is: why not simply compute attention separately over the prefix and suffix and add the results? The answer — that softmax normalization is global across the full sequence, making naive addition incorrect — is mathematically straightforward, but its *consequence* for shared-prefix optimization is subtle: without an exact decomposition, you cannot isolate the prefix for special batching treatment without introducing approximation error. The field's prior solutions either (a) computed full-sequence attention per-sequence (FlashAttention, PagedAttention), accepting the bandwidth cost, or (b) used architectural changes like sliding-window attention or sparse attention that restrict the attention pattern, trading fidelity for speed.

Hydragen's decomposition — splitting attention into prefix and suffix sub-computations, storing log-sum-exp values, and recombining exactly via Equation 5 — is not presented as a mathematical novelty (it inherits from FlashAttention's tiled softmax; Dao et al., 2022). Its intellectual contribution is **recognizing that this decomposition is the precise enabling mechanism for partial-context cross-sequence batching**, and that it can be applied at the batch level rather than within a single sequence. Prior work used the LSE recombination trick to handle memory constraints within a single attention computation (tiling across the sequence dimension). Hydragen re-purposes it to separate the shared and unique portions of the context, creating an interface where the shared portion can be processed with an entirely different computational strategy (batched matrix-matrix) than the unique portion (independent matrix-vector).

What makes this distinctive is that it reveals a form of **composability in attention**: the full attention output is algebraically expressible as a weighted combination of sub-attention outputs, where the weights are the exponentiated softmax denominators. This is not obvious from the standard attention formulation (Equation 1), which presents attention as a monolithic operation. By exposing this composability, Hydragen creates a framework where different parts of the context can be processed by different optimized kernels, on different hardware units, or even on different devices — the decomposition is exact, so there is no quality tradeoff.

The empirical significance is visible in the microbenchmark speedups (Figure 4): at batch size 4096 and prefix length 8192, Hydragen attention achieves over 16× speedup over FlashAttention at short suffix lengths. This is not a small constant-factor optimization — it is an order-of-magnitude improvement that comes entirely from restructuring the computation, not from reducing the amount of work or approximating the result. The speedup grows with batch size and prefix length precisely because these parameters increase the amount of redundant work in the baseline while Hydragen's batched approach keeps the prefix cost nearly constant.

This is best characterized as a **clever application of an existing technique to a novel setting**, with the novelty lying in recognizing that the setting (shared prefixes) and the technique (LSE-based attention decomposition) are a perfect match. It is not a fundamental mathematical advance — the decomposition was known from FlashAttention — but the insight to apply it across the batch dimension rather than the sequence dimension is non-trivial and unlocks a qualitatively different performance regime.

---

### Innovation 4: Hierarchical Sharing as a Compositional Generalization Strategy

The flat prefix-suffix decomposition covers an important special case — all sequences share the same initial tokens — but many real-world inference workloads have richer sharing structures. Competitive programming systems sample many candidate solutions per problem across many problems; tree-of-thought reasoning explores branching paths from a shared root; multi-turn chatbot conversations share system prompts and conversation history up to the branch point. Prior work on shared-prefix optimization (vLLM, RadixAttention) either handled only the flat case or required dynamic detection of sharing patterns at the granularity of individual requests.

Hydragen's contribution is recognizing that the decomposition-plus-batching strategy is **compositional**: it can be applied recursively at every node in a tree of shared token sequences. At each node, the local token sequence is treated as a "prefix" for all descendant sequences, attention is decomposed at that boundary, and descendant queries are batched together. The LSE-based recombination formula then composes cleanly along the path from root to leaf — the final attention output for a leaf sequence is the weighted combination of (attention over the root) + (attention over the level-1 node) + ... + (attention over the unique suffix), where each sub-computation's output is weighted by its exponentiated LSE and the combination is exact.

What makes this intellectually distinctive is that it identifies **sharing structure as a recursive, not flat, property** of batched inference workloads, and shows that the same algebraic mechanism (attention decomposition) scales cleanly to arbitrary tree depths. This is not an incremental extension — it changes how practitioners should organize their inference workloads. Instead of thinking about "what is the shared prefix," the framework encourages thinking about "what is the sharing tree" — identifying multiple levels of overlap and structuring batches to maximize the number of levels where batching applies.

The empirical demonstration (Section 4.4, Figure 6) shows this is not merely a theoretical curiosity. On the APPS competitive programming benchmark with 120 problems and 128 samples per problem, two-level Hydragen (sharing both the global few-shot prompt and the per-problem description) reduces total inference time by 55% compared to single-level Hydragen (sharing only the few-shot prompt). The breakdown is informative: 18% comes from improved attention efficiency at the same batch size (eliminating redundant reads of the problem description within each problem group), and the remaining 45% comes from memory savings (not redundantly storing the problem description) enabling a larger batch size. This demonstrates that hierarchical sharing compounds both the bandwidth and capacity benefits.

The conceptual significance extends beyond this specific benchmark. Hierarchical compositionality means Hydragen's benefits scale with the *depth* of sharing in the workload, not just the *breadth* (batch size). As LLM inference patterns grow more complex — with multi-agent debates, complex search procedures, and nested reasoning structures — the depth of sharing trees will increase, and Hydragen's recursive decomposition provides a principled way to extract efficiency from that complexity. This is a **fundamental insight** about the structure of shared-prefix inference: sharing is not binary (shared vs. not-shared) but graded (shared at multiple levels), and optimizing for graded sharing requires a compositional mechanism, not a flat one.

---

### Innovation 5: Demonstrating That Test-Time Compute Scaling Need Not Be Memory-Bandwidth-Bound

This innovation is not a technical mechanism but an empirical finding with implications for how the field thinks about scaling test-time compute. Prior to Hydragen, the dominant narrative around batched LLM inference was that throughput is fundamentally constrained by the memory bandwidth of reading the growing KV cache, and that architectural changes (Multi-Query Attention, Grouped-Query Attention) are the primary path to relief because they shrink the cache. This narrative implied that scaling batch sizes or context lengths would always hit a bandwidth wall, and that the only sustainable solutions were at the model architecture level.

Hydragen's empirical results — particularly the end-to-end throughput measurements with the "No Attention" ceiling — directly challenge this narrative for the important special case of shared prefixes. Figure 3b shows that with Hydragen, CodeLlama-13b throughput at batch size 1024 remains within 70% of the No Attention ceiling across all prefix lengths from 1K to 16K tokens. The No Attention ceiling represents the throughput achievable if attention were entirely free — i.e., if only the MLP and linear projection computations remained. Staying within 70% of this ceiling means that **prefix attention has been effectively removed as a bottleneck**. The remaining gap to the ceiling is primarily due to suffix attention, not prefix attention.

What makes this finding significant beyond the specific benchmark is that it demonstrates a **systems-level decoupling** between prefix length and decoding throughput. In the vLLM baseline, prefix length and throughput are tightly coupled (90% drop from 1K to 16K). Hydragen breaks this coupling almost entirely (<15% drop). This has algorithmic implications: it makes it practical to provide LLMs with extremely long shared contexts — thousands of tokens of system instructions, dozens of few-shot examples, entire retrieved documents — without paying a proportional throughput penalty. The long document QA experiment (Section 4.3, Figure 5) demonstrates this concretely: with a 19,947-token shared prefix, Hydragen processes 256 questions in less time than FlashAttention processes 64, and stays within 60% of the No Attention optimum.

This finding is **conceptually significant** because it reframes what constitutes a "practical" inference configuration. Before Hydragen, using a 16K-token system prompt with a thousand concurrent users would have been considered infeasible due to bandwidth constraints. After Hydragen, it is not only feasible but nearly as fast as using a 1K-token prompt. This changes the cost-benefit calculus for prompt engineering, retrieval-augmented generation, and few-shot learning — techniques that expand the shared prefix are now nearly free in terms of decoding throughput, shifting the primary constraint to prefill time and total memory capacity (areas where complementary optimizations like PagedAttention and RadixAttention already operate).

This is best characterized as an **empirical demonstration that reframes design constraints**, not a theoretical advance. The theoretical basis is straightforward (batching reduces memory reads), but the magnitude of the effect — near-elimination of the prefix bottleneck rather than incremental improvement — is what changes the landscape. The finding that Hydragen enables prefix length scaling with minimal throughput penalty is the key takeaway that should influence how practitioners provision and configure LLM inference systems.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The end-to-end throughput benchmarks (Section 4.1) use synthetic prompts of specified token lengths (1K to 16K tokens) to control prefix and generation lengths precisely, without reference to a specific NLP dataset. The long document QA benchmark (Section 4.3) constructs a document by embedding synthetic facts into an excerpt of Tolstoy's *War and Peace* (19947 total tokens), with a held-out set of 261 procedurally generated question-answer pairs (256 for evaluation plus 5 for few-shot examples). The hierarchical sharing benchmark (Section 4.4) uses 120 problems from the introductory difficulty split of the APPS dataset (Hendrycks et al., 2021), filtered to exclude problems with starter code; two few-shot examples (2400 tokens total) come from the APPS training split, while all evaluation examples come from the APPS test split.

- **Base model(s).** Experiments use three models from the CodeLlama family (Rozière et al., 2023) — CodeLlama-7b, CodeLlama-13b, and CodeLlama-34b — which employ standard multi-head attention (MHA) with 32 query heads and 32 key-value heads, making the KV cache relatively large and the attention cost significant. The long document QA benchmark uses Yi-6B-200k (01-ai, 2023), chosen because it supports a 200K-token context window to accommodate the ~20K-token document while being small enough (6B parameters, 4 key-value attention heads) to fit a large KV cache in GPU memory for baseline runs. The hierarchical sharing benchmark uses CodeLlama-7b. These models span a range of scales and attention architectures (MHA vs. GQA-like reduced heads in Yi-6B-200k), testing Hydragen's generality across different attention configurations.

- **Metrics.** The primary metric is **decoding throughput in tokens per second (TPS)**, measured as the total number of new tokens generated divided by the total wall-clock time during the decoding phase only (excluding prefill time, tokenization, and detokenization). For the APPS benchmark, the metric is **total evaluation time** in seconds to run inference on all 120 problems, including all overheads except tokenization and detokenization. The paper also reports **speedup** as the ratio of Hydragen's throughput (or time) to a baseline's throughput (or time) at the same configuration. All throughput measurements are averaged over multiple timing iterations after warmup iterations (10 warmup + 10 timing for FlashAttention and No Attention baselines; 10 warmup + 10 timing for Hydragen with batch size < 256, reduced to 3+3 for larger batches; 3+3 or 1+1 for vLLM depending on runtime).

- **Baselines.** Four baselines are compared in the end-to-end benchmarks:
  1. **FlashAttention** (Dao et al., 2022; Dao, 2023): A naive batched inference baseline that computes full-sequence attention for each sequence independently using a fast Triton kernel (the same kernel Hydragen uses for suffix attention) without any shared-prefix optimization, redundantly storing the prefix KV cache for every sequence. This baseline runs out of GPU memory quickly due to KV cache redundancy.
  2. **vLLM** (Kwon et al., 2023, version 0.2.7): Uses PagedAttention to avoid redundant prefix KV cache storage and to manage KV cache memory via virtual paging. It achieves a higher GPU cache hit rate when reading the shared prefix but still computes attention per-sequence.
  3. **vLLM without Detokenization**: vLLM with incremental detokenization disabled (accomplished by commenting out a single line in the vLLM codebase), which the authors observed to improve throughput by eliminating what appears to be redundant re-detokenization of the prompt for every sequence in the batch at the start of inference.
  4. **No Attention**: A functionally incorrect but informative throughput ceiling where all self-attention computations (but not the query, key, value, and output linear projections) are removed from the transformer. This establishes the maximum possible throughput achievable if attention were instantaneous, isolating the cost of non-attention model components.

  The attention microbenchmarks (Section 4.2) compare Hydragen against FlashAttention only, measuring isolated attention operation time rather than end-to-end model throughput.

- **Generation budget / compute accounting.** The paper does not use a "generation budget" in the sense of sampling a fixed number of candidate solutions. Instead, it measures throughput under controlled configurations: **batch size** (number of sequences processed in parallel), **shared prefix length** (number of tokens in the common prefix), **suffix length** (number of generated tokens per sequence), and **number of generated tokens** (how many decoding steps are performed). In the end-to-end benchmarks (Section 4.1), prefix length is fixed while batch size is swept (Figure 3a), and batch size is fixed while prefix length is swept (Figure 3b). In microbenchmarks (Section 4.2), batch size, prefix length, and suffix length are all swept independently to characterize attention performance. GPU memory constraints are a limiting factor — configurations marked with "X" in the detailed tables (Appendix C.1) indicate that the baseline runs out of GPU memory. All end-to-end benchmarks are run on 8× A100-40GB GPUs with tensor parallelism to maximize available KV cache memory; microbenchmarks run on a single A100-40GB (with additional results on H100 and L40S in Appendix C.2).

- **Cross-validation / statistical protocol.** There is no cross-validation or statistical significance testing; this is a systems benchmarking paper, not a machine learning evaluation. The primary concern is measurement noise from GPU execution time variability. To mitigate this, the paper uses warmup iterations (discarded) before timing iterations (averaged), and reports mean throughput across timing iterations. For vLLM baselines at very large batch sizes where a single iteration can take minutes, only 1 warmup and 1 timing iteration are used. The authors note that shorter-running Hydragen benchmarks (small batch sizes, short sequences) can occasionally produce outlier times due to variations in prefill time, which is subtracted out for the decode-only measurement.

### Main Quantitative Results

#### End-to-End Throughput: Batch Size Scaling (Figure 3a, Table 3)

With CodeLlama-13b generating 128 tokens per sequence from a 2048-token shared prefix:

- At batch size 32, Hydragen achieves approximately 2.0K TPS, vLLM (no detokenization) achieves approximately 1.8K TPS, and the No Attention ceiling is approximately 2.3K TPS. All methods are within 30% of each other because attention is not yet the dominant bottleneck — the MLP and linear projections dominate decoding time.

- As batch size increases, vLLM throughput grows slowly and plateaus: at batch size 128, vLLM (no detokenization) reaches approximately 5.5K TPS versus Hydragen's 5.8K TPS (a 5% gap); at batch size 256, the gap widens to 9.6K (Hydragen) versus 8.0K (vLLM no detokenization), a 20% advantage. At batch size 512, Hydragen achieves 13.4K TPS versus vLLM no detokenization at 4.7K TPS — a 2.85× speedup. At batch size 1024, Hydragen reaches 15.6K TPS versus vLLM no detokenization at 4.9K TPS — a 3.2× speedup. The vLLM (standard) baseline is consistently slightly slower than vLLM no detokenization (e.g., 4.2K vs 4.9K at batch 1024).

- FlashAttention can only reach batch size 256 before running out of GPU memory (due to redundant prefix KV cache storage), achieving 5.7K TPS at that batch size (versus Hydragen's 9.6K TPS).

- The "No Attention" ceiling grows steadily with batch size (from 2.3K at batch 32 to 18.5K at batch 1024), representing the throughput if attention were free. Hydragen's throughput stays within approximately 50% of this ceiling at all batch sizes (15.6K achieved versus 18.5K ceiling at batch 1024, i.e., 84% of ceiling), while vLLM no detokenization drops to 4.9K / 18.5K = 26% of ceiling. This demonstrates that Hydragen has largely eliminated prefix attention as a bottleneck; the remaining gap is due to suffix attention and non-attention components.

The same pattern holds for CodeLlama-7b (Table 1) with even larger speedups: at batch 1024 and prefix length 2048 with 128 generated tokens, Hydragen achieves 25.1K TPS versus vLLM no detokenization at 2.8K TPS — a **9× speedup**. For CodeLlama-34b (Table 5), the relative speedup is smaller but still significant: at batch 1024 with 128 generated tokens, Hydragen achieves 9.2K TPS versus vLLM no detokenization at 2.8K TPS — a 3.3× speedup. The diminishing relative speedup with larger models reflects that the MLP blocks consume a larger fraction of total FLOPs, so attention (even unoptimized) is a smaller fraction of total time.

#### End-to-End Throughput: Prefix Length Scaling (Figure 3b, Table 3)

With CodeLlama-13b, batch size fixed at 1024, generating 128 tokens per sequence:

- At prefix length 1024, vLLM no detokenization achieves approximately 4.9K TPS versus Hydragen's 15.6K TPS — a 3.2× speedup.

- At prefix length 2048: vLLM no detokenization drops to approximately 2.8K TPS while Hydragen stays at 15.5K TPS — a **5.5× speedup**.

- At prefix length 4096: vLLM no detokenization drops further to approximately 1.6K TPS versus Hydragen's 15.3K TPS — a **9.6× speedup**.

- At prefix length 8192: vLLM no detokenization falls to approximately 0.8K TPS versus Hydragen's 14.8K TPS — an **18.5× speedup**.

- At prefix length 16256: vLLM no detokenization reaches approximately 0.4K TPS versus Hydragen's 14.0K TPS — a **32× speedup**. This is the headline speedup number from the abstract.

The absolute throughput numbers reveal the key dynamic: **vLLM throughput drops by over 90%** (from ~4.9K to ~0.4K TPS) as prefix length grows 16×, while **Hydragen throughput drops by less than 15%** (from 15.6K to 14.0K TPS). The Hydragen throughput remains within 70% of the No Attention ceiling (approximately 18.5K TPS at batch 1024, independent of prefix length) across all prefix lengths. At 16K prefix length, Hydragen achieves 14.0K versus the 18.5K ceiling (76% of ceiling), while vLLM achieves 0.4K (2% of ceiling).

For CodeLlama-7b (Tables 1–2), the speedup is even larger due to the smaller model's attention being a larger fraction of total FLOPs: at batch 1024, prefix length 16256, and 128 generated tokens, Hydragen achieves 22.4K TPS versus vLLM no detokenization at 0.4K TPS — a **56× speedup**. With 256 generated tokens (Table 2), the speedup is similarly large: 21.0K vs 0.4K, a 52.5× speedup.

#### End-to-End Throughput: Varying Numbers of Generated Tokens (Tables 1–6)

Comparing tables for the same model size but different generation lengths (128 vs. 256 tokens) reveals consistent patterns:

For CodeLlama-13b (Tables 3 vs. 4), Hydragen throughput at batch 1024 and prefix 2048 drops from 15.6K TPS (128 tokens) to 15.5K TPS (256 tokens) — essentially unchanged. vLLM no detokenization drops from 2.8K to 2.8K — also unchanged. The No Attention ceiling drops from 18.5K to 16.1K — a 13% reduction reflecting the increased FLOPs from the MLP processing more tokens. Hydragen's throughput relative to the ceiling actually *improves* slightly: 84% (128 tokens) to 96% (256 tokens), suggesting that with longer generations, attention (which Hydragen accelerates) constitutes a smaller fraction of non-ceiling overhead.

For CodeLlama-7b (Tables 1 vs. 2), the Hydragen advantage is larger: at batch 1024, prefix 2048, Hydragen achieves 25.1K (128 tokens) vs. 23.2K (256 tokens), while vLLM no detokenization achieves 2.8K vs. 2.8K. The speedup is 9.0× (128 tokens) and 8.3× (256 tokens), slightly decreasing because longer generations increase suffix attention cost (unaccelerated) as a fraction of total prefix+suffix attention.

#### Attention Microbenchmarks (Figure 4, Appendix C.2 Figure 7)

On a single A100-40GB GPU with 8 query heads, 1 key-value head, and head dimension 128 (matching CodeLlama-34b when distributed across 8 GPUs):

- At batch size 512, prefix length 1024, and suffix length 0 (i.e., only attention over the prefix), Hydragen achieves approximately a **13–16× speedup** over FlashAttention. As suffix length grows to 500 tokens, the speedup decays to approximately 6–8×.

- At batch size 1024 and prefix length 2048: speedup ranges from approximately 14× (suffix length 0) to 7× (suffix length 500).

- At batch size 2048 and prefix length 4096: similar pattern, starting near 15× and decaying to 7×.

- At batch size 4096 and prefix length 8192: the largest configuration, with speedup near **16×** at suffix length 0, decaying to 8× at suffix length 500. This is the attention-level speedup cited in the abstract ("The attention operation in isolation can be accelerated by over 16×").

The decay with suffix length is consistent across configurations: prefix attention is accelerated by batching (the speedup factor is roughly proportional to batch size for the prefix portion), but suffix attention is not accelerated. As suffix length grows from 0 to 500, the fraction of total attention time spent on suffixes increases, and the overall speedup decreases. Extrapolating: if suffix length were to grow much larger than prefix length, the speedup would asymptotically approach 1× (no benefit), since suffix attention would dominate. This is why Hydragen is most beneficial when prefixes are long relative to suffixes.

On an L40S GPU (Appendix C.2, Figure 7 right), with an even higher compute-to-bandwidth ratio than the A100, speedups are larger: at batch 4096, prefix 8192, and short suffix lengths, the speedup exceeds 30×. On an H100 (Figure 7 left), speedups are similar to the A100, which the authors attribute to the flash-attn package not being fully optimized for the Hopper architecture, resulting in lower device utilization on the H100.

#### Long Document Question Answering (Figure 5, Section 4.3)

With Yi-6B-200k on 4× A100-40GB GPUs, a 19,947-token shared prefix (document + 5 few-shot examples), and varying numbers of questions answered simultaneously:

- At 64 questions, Hydragen processing time is approximately 1.5× the No Attention baseline, while FlashAttention is approximately 2.5× the No Attention baseline.

- At 128 questions, Hydragen time is approximately 1.5× No Attention, FlashAttention is approximately 4× No Attention.

- At 256 questions, Hydragen time is approximately 1.5× No Attention, while FlashAttention would require approximately 6× No Attention time (but runs out of memory at 128 questions, so this is extrapolated from the trend). Explicitly: "Hydragen can process 256 questions in less time than it takes the FlashAttention baseline to process 64 questions."

- FlashAttention runs out of GPU memory above 64 questions (marked with "X" in Figure 5) due to redundant storage of the prefix KV cache — the prefix alone is ~20K tokens × 4 GPUs worth of memory, and storing it independently for each sequence exhausts capacity.

The key finding is that Hydragen's processing time remains within 60% of the No Attention optimum across all batch sizes tested, while FlashAttention's processing time diverges rapidly. This demonstrates that with very long shared contexts, the attention bottleneck is severe for standard approaches, and Hydragen nearly eliminates it.

#### Hierarchical Sharing in Competitive Programming (Figure 6, Section 4.4)

Evaluating CodeLlama-7b on 120 APPS introductory problems with a two-shot prompt (2400 tokens) and 128 candidate solutions per problem:

- **Single-Level Hydragen** (sharing only the few-shot prompt, problem descriptions redundantly stored and not shared): With a batch size of 4 (4 problems processed simultaneously, each with 128 candidate solutions = 512 total sequences), total evaluation time is approximately 2800 seconds.

- **Two-Level Hydragen, same batch size** (sharing both the few-shot prompt and the per-problem descriptions, but still batch size 4): Total evaluation time drops to approximately 2300 seconds — an **18% reduction**. This reduction comes purely from improved attention efficiency (eliminating redundant reads of the per-problem description within each problem group), since the batch size and total work are identical.

- **Two-Level Hydragen, increased batch size** (sharing both levels, batch size increased to 32 problems simultaneously): Total evaluation time drops to approximately 1250 seconds — a **45% additional reduction** from the memory-saved batch size increase, and a **55% overall reduction** compared to single-level Hydragen (2800 → 1250 seconds).

The memory savings from not redundantly storing the per-problem description (which must be stored 128 times per problem in single-level Hydragen) enable the batch size to increase from 4 to 32 problems, which in turn increases GPU utilization and throughput. This demonstrates the compound benefit of hierarchical sharing: bandwidth reduction (18% from eliminating redundant reads) plus capacity reduction (45% from enabling larger batches) compound to 55% total.

### Ablation Studies and Robustness Checks

**Impact of model scale on relative speedup (Tables 1–6):** Across CodeLlama-7b, 13b, and 34b, the absolute Hydragen throughput decreases with model size (larger models have more FLOPs per token), but the speedup over vLLM also decreases. At batch 1024 and prefix 2048 with 128 generated tokens: CodeLlama-7b shows **9.0× speedup** (25.1K vs 2.8K TPS), CodeLlama-13b shows **5.5× speedup** (15.5K vs 2.8K TPS), and CodeLlama-34b shows **3.3× speedup** (9.2K vs 2.8K TPS). This is expected because larger models spend a greater fraction of total FLOPs on the MLP (which scales with model dimension squared) relative to attention (which scales linearly with sequence length), so accelerating attention provides diminishing end-to-end returns. The trend confirms that Hydragen's impact is largest when attention is a dominant fraction of total decode time — which occurs with smaller models, larger batch sizes, and longer prefixes.

**Impact of generated token count on Hydragen advantage (Tables 1–6, 128 vs 256 tokens):** Doubling the number of generated tokens per sequence from 128 to 256 slightly reduces Hydragen's relative throughput advantage because longer suffixes increase the fraction of attention time spent on unaccelerated suffix attention. For CodeLlama-13b at batch 1024 and prefix 2048, the speedup drops from 5.5× (128 tokens) to 5.5× (256 tokens) — the drop is minimal because suffix attention even at 256 tokens is small relative to prefix attention at 2048 tokens. The pattern is consistent across all model sizes, though the magnitude of the drop is small, indicating that suffix length has not grown large enough relative to prefix length to significantly erode the benefit in these configurations.

**Impact of GPU compute-to-bandwidth ratio (Appendix C.2, Figure 7):** Running the same microbenchmarks on A100, H100, and L40S GPUs reveals that the speedup grows with the GPU's ratio of tensor core FLOPs to memory bandwidth. The L40S, which has the highest compute-to-bandwidth ratio of the three, shows the largest speedups (30+× at batch 4096, prefix 8192, and short suffixes). The H100, despite having a higher theoretical compute-to-bandwidth ratio than the A100, shows similar speedups to the A100, which the authors attribute to the flash-attn package not being optimized for the Hopper architecture, limiting device utilization. This suggests that (a) Hydragen's benefits will continue to grow with future GPU generations that further increase the compute-to-bandwidth ratio, and (b) optimizing the underlying attention primitives for newer architectures is an important complementary effort.

**vLLM incremental detokenization overhead (Figure 3a and 3b, "vLLM" vs. "vLLM No Tokenization"):** Across nearly all configurations, disabling incremental detokenization in vLLM improves throughput by 10–20%. The authors observed that vLLM appears to redundantly detokenize the shared prompt for every sequence in the batch at the beginning of inference, an operation that can take minutes for large batch sizes and long sequence lengths. This is a systems-level artifact of how vLLM handles prompt processing, not a fundamental algorithmic property, but it significantly impacts measured throughput in shared-prefix settings. The "vLLM No Tokenization" baseline is the more competitive baseline because it isolates the attention performance from this orthogonal systems overhead.

**Suffix attention kernel choice (Section 3.5, Appendix B pseudocode):** Hydragen uses FlashAttention (via the flash-attn package v2.3.6) for prefix attention because it returns the LSE needed for softmax recombination and is optimized for large matrix-matrix products. For suffix attention, it uses a Triton kernel from xformers specifically because it supports changing sequence lengths across decoding steps (as suffixes grow) while remaining compatible with CUDA graphs, which reduce CPU kernel launch overhead. The choice of two different attention backends for prefix and suffix is a practical engineering decision, not a fundamental requirement — any fast attention implementation that returns LSE could be used for either component. The paper does not ablate this choice (e.g., using FlashAttention for suffixes with padding), likely because the Triton kernel's CUDA graph compatibility is essential for measuring meaningful throughput at very fast decoding speeds.

**Memory savings from non-redundant prefix storage (implied by FlashAttention out-of-memory results):** In all experiments with large batch sizes and long prefixes, FlashAttention runs out of GPU memory while Hydragen and vLLM do not (marked with "X" in the detailed tables). For CodeLlama-13b at batch size 128 with 128 generated tokens, FlashAttention can only run up to prefix length 1024 (Table 3), while Hydragen and vLLM can run all prefix lengths. At batch size 256, FlashAttention can only run at prefix length 1024. At batch size 512, FlashAttention cannot run any configuration. This demonstrates that Hydragen (like vLLM) benefits from memory savings by sharing the prefix KV cache, enabling batch sizes and prefix lengths that would be impossible with naive per-sequence storage. This is an indirect ablation — the paper does not separately measure the throughput impact of memory savings versus attention acceleration — but the hierarchical sharing experiment (Figure 6) partially decomposes this by showing that two-level Hydragen at the same batch size (pure attention benefit) provides 18% improvement, while the memory-saved batch size increase provides an additional 45%.

**Hierarchical sharing depth (Figure 6, single-level vs. two-level):** This serves as an ablation of the generalization from flat prefix-suffix to tree-structured sharing. At the same batch size (4 problems), two-level Hydragen reduces evaluation time by 18% compared to single-level Hydragen for the APPS benchmark. This quantifies the marginal benefit of exploiting a second level of sharing, isolating the pure attention acceleration (since memory savings are excluded when batch size is held constant). The result confirms that hierarchical decomposition provides non-trivial attention efficiency gains beyond what single-level sharing achieves, because it eliminates redundant reads at the second sharing level (per-problem descriptions within each problem's candidate solution group).

**"No Attention" throughput ceiling robustness (all figures and tables):** The No Attention baseline consistently serves as a stable upper bound. Its throughput grows with batch size (more sequences amortize the linear projection and MLP costs) and is independent of prefix length (since no attention is performed on the prefix). Hydragen approaches within 50–84% of this ceiling for CodeLlama-13b, within 60–96% for CodeLlama-7b and CodeLlama-34b (exact percentage varies with configuration), demonstrating that Hydragen has largely eliminated attention — specifically prefix attention — as a throughput bottleneck. The remaining gap is attributable to suffix attention (unaccelerated) and the overhead of the LSE recombination, which is negligible relative to the attention cost. This "near-ceiling" performance is the strongest evidence that Hydragen has solved the prefix attention bottleneck, not just incrementally improved it.

### Critical Assessment

**Does Hydragen really achieve "up to 32×" end-to-end speedup?** Yes, but only under specific conditions. The 32× speedup over vLLM (with detokenization) is achieved at batch size 1024 with prefix length 16256 on CodeLlama-13b (Figure 3b). This is the most extreme configuration tested — maximum batch size, longest prefix — and is exactly where Hydragen's advantages are largest. At more moderate configurations (e.g., batch 128, prefix 2048), the speedup is much smaller (approximately 1.1×, Table 3). The paper is transparent about this conditionality: speedup "grows with batch size and shared prefix length." A practitioner with a smaller deployment (batch 32, short system prompt) would see minimal benefit. This is not a weakness of the method but a property of the workload: Hydragen removes the *scaling cost* of prefixes, so if prefixes are small, there is little cost to remove.

**Does Hydragen truly "enable the use of very long shared contexts"?** The claim in the abstract — "increasing the prefix length from 1K to 16K tokens decreases Hydragen throughput by less than 15%" — is strongly supported by Figure 3b and Tables 3–6. The absolute throughput numbers are consistent across multiple model sizes and generation lengths. However, the caveat is that this measures *decoding* throughput only. The prefill stage (processing the initial prefix) is excluded from all measurements, and for a 16K-token prefix, the prefill could be substantial. The paper acknowledges this exclusion and justifies it by noting that prefill is a one-time cost amortized over many decoding steps and many sequences. For interactive applications where a 16K-token prompt is processed once and then used for many user queries, this is reasonable. For one-shot applications where the prompt is used once for a small number of completions, the excluded prefill cost could dominate, and the end-to-end (prefill + decode) speedup would be much smaller.

**Is the speedup over vLLM a fair comparison?** The paper uses vLLM version 0.2.7, which was the current release at the time. vLLM optimizes memory management but not the attention computation itself, so Hydragen's advantage is genuine — it addresses a complementary bottleneck. However, two aspects of the comparison warrant scrutiny:

1. **The "vLLM no detokenization" baseline is not standard vLLM.** Disabling incremental detokenization (by commenting out a line of vLLM's code) improves throughput by 10–20%, making it a stronger baseline. The paper reports both, but the 32× claim is over standard vLLM (with detokenization), while the tables show vLLM no detokenization as the more competitive variant. The speedup over vLLM no detokenization at the 32× configuration (batch 1024, prefix 16256) is closer to 35× (14.0K vs 0.4K TPS), so the headline figure is actually conservative.

2. **vLLM's prefix processing overhead.** The authors note that vLLM "appears to redundantly detokenize the prompt for every sequence in the batch at the beginning of inference," which can take minutes for large batches. This is a real systems-level artifact of how vLLM currently handles shared prefixes, and Hydragen avoids it by sharing the prefix representation. Some might argue this is an unfair comparison because future versions of vLLM could fix this orthogonal overhead. However, the "vLLM no detokenization" baseline largely controls for this, and Hydragen still achieves dramatic speedups over that baseline at large batch sizes and long prefixes.

**Does the work demonstrate that inter-sequence batching is the key mechanism, or could other factors explain the speedup?** The microbenchmarks (Figure 4) isolate the attention operation and show 16×+ speedups over FlashAttention, confirming that the attention computation itself is accelerated, not some other part of the pipeline. The decomposition of the hierarchical sharing results (Figure 6) — 18% from attention efficiency alone (same batch size, same memory footprint) — confirms that inter-sequence batching provides a standalone benefit. The fact that Hydragen's throughput stays near the No Attention ceiling (which removes all attention) further supports that prefix attention has been nearly eliminated as a bottleneck, which is consistent with the batching mechanism (reading the prefix once for all sequences) but not with mechanisms that only reduce storage redundancy.

**What is not tested?** Several important dimensions are absent:

1. **No non-Llama model architectures.** All experiments use CodeLlama or Yi models, which share the Llama architecture. Hydragen's approach should generalize to any standard transformer with dot-product attention, but this is not demonstrated for encoder-decoder models (T5), mixture-of-experts models (Mixtral), or models with different attention patterns (e.g., models with cross-attention between encoder and decoder).

2. **No GQA or MQA models as primary test models.** The CodeLlama models use standard multi-head attention (32 query heads, 32 key-value heads). Yi-6B-200k uses 4 key-value heads (similar to GQA with a large group size), and Hydragen achieves strong results on it (Figure 5, staying within 60% of No Attention), but no systematic comparison across GQA group sizes is performed. The paper argues (Section 3.4) that GQA/MQA models would show smaller relative speedups per attention operation but could achieve larger absolute speedups because the smaller KV cache allows larger batch sizes. This interaction is not experimentally explored.

3. **No integration with PagedAttention for suffix memory management.** Hydragen's implementation stores suffix KV caches without paging, limiting maximum batch size for long suffixes. The paper envisions combining Hydragen's attention computation with vLLM's memory management but does not implement this combination.

4. **No real chatbot trace or production workload.** The experiments use synthetic prompts of specified lengths. A production chatbot deployment would have variable prefix lengths (different system prompts for different use cases), variable suffix lengths (different conversation histories), and dynamic batching (sequences complete at different times). Hydragen's requirement that the sharing structure be specified in advance is a barrier to such dynamic settings, and the paper does not demonstrate integration with a continuous batching scheduler like vLLM's.

5. **No multi-turn conversation benchmarks.** The hierarchical sharing experiment (APPS) demonstrates static tree-structured sharing, but multi-turn conversations with branching dialogue paths (where the shared prefix is the conversation history up to the branch point) are not tested. This would be a more dynamic form of tree-structured sharing where the tree grows incrementally as users diverge in their conversations.

6. **Prefill time not measured or reported.** The decode-only measurement is standard in LLM inference benchmarking, but for long shared prefixes, the prefill can be significant, and Hydragen does not accelerate it. The paper's claim that Hydragen enables very long shared contexts would be strengthened by reporting total (prefill + decode) time for representative scenarios.

**Is the method truly "exact," and does exactness matter?** The mathematical proof (Appendix A) confirms that the decomposition is algebraically exact — no approximation is introduced. This matters for two reasons: (1) it eliminates any accuracy-throughput tradeoff, which is important for deployment where model quality must be preserved, and (2) it means Hydragen is a drop-in replacement for attention that produces identical outputs, simplifying integration into existing inference pipelines. The exactness is a consequence of using the LSE recombination trick, which is well-understood from FlashAttention's tiled softmax. The contribution is not the trick itself but recognizing that it enables cross-sequence batching for shared prefixes.

**Does the paper overclaim or misrepresent the baselines?** The 32× speedup in the abstract is explicitly qualified as "against competitive baselines" and the specific comparison (vLLM) is named in the text. The paper does not claim that Hydragen is 32× faster than all possible implementations — it compares against the state-of-the-art at the time. The speedup is measured at the most favorable configuration (largest batch, longest prefix), which is appropriate for demonstrating the scaling trend. The more representative speedup at moderate configurations is clearly visible in the detailed tables. The paper is transparent about when Hydragen does not help (small batch, short prefix, GQA models) in Section 3.4 and in the varying results across model sizes.

**Bottom-line assessment:** The experiments genuinely support the central claims — Hydragen provides dramatic throughput improvements for shared-prefix attention at large batch sizes and long prefixes, with the benefits growing with both parameters; the decomposition-plus-batching mechanism is validated by microbenchmarks and by Hydragen's proximity to the No Attention ceiling; and hierarchical sharing provides compound benefits beyond flat prefix-suffix decomposition. The primary limitations are scope (Llama-family MHA models, synthetic benchmarks, no dynamic batching integration) and the exclusion of prefill time from measurements, which makes the results most directly applicable to sustained serving scenarios rather than one-shot inference. The paper is forthright about these limitations and positions Hydragen as a component to be integrated into larger inference systems, not as a complete solution.

## 6. Limitations and Trade-offs

### Manual Specification of Sharing Structure Prevents Dynamic Deployment

**The assumption or constraint.** Hydragen's proof-of-concept implementation requires that the user explicitly specify where sharing occurs across input sequences — which portion is the shared prefix, and for hierarchical sharing, the tree structure of overlaps. The paper acknowledges this directly in Section 5:

> "Our proof-of-concept implementation of Hydragen requires that the user specifies where sharing occurs across the input sequences."

**The consequence.** This makes Hydragen, as currently implemented, unsuitable for the most common production LLM serving scenario: a continuous stream of incoming requests where sequences dynamically enter and leave the batch, have variable prefix lengths (different system prompts for different applications), and complete at unpredictable times. In such a setting, the sharing structure must be identified automatically and updated as the batch composition changes. A deployment using vLLM or SGLang's RadixAttention can dynamically detect overlapping prefixes across incoming requests and share KV cache pages without user intervention. Hydragen currently cannot — the user must pre-organize sequences into sharing groups and specify the prefix boundaries before inference begins. This limits the method's applicability to *offline batch evaluation* (as in the APPS benchmark) or to serving scenarios where the batch is static and the sharing structure is known in advance (e.g., sampling many completions from a single prompt), which is a subset of real-world LLM inference workloads.

**What evidence exists in the paper.** No experiment evaluates Hydragen with dynamic batching or continuously arriving requests. All benchmarks use static, pre-organized batches where the sharing structure is known and fixed before inference begins. The end-to-end throughput experiments (Section 4.1) sample many completions from a single fixed prompt; the long document QA experiment (Section 4.3) processes a fixed set of questions against a single document; the APPS hierarchical sharing experiment (Section 4.4) evaluates a fixed set of problems with known sharing structure. The paper does not compare against vLLM's continuous batching scheduler or demonstrate Hydragen integrated with one. The throughput numbers are therefore best understood as applying to *batch processing* workloads, not *interactive serving* workloads where request arrival times are stochastic.

**Mitigation status.** The paper explicitly frames this as future work, not a solved problem. Section 5 states:

> "We are excited about future work that incorporates Hydragen into systems that continuously receive requests and schedule sequences for generation, such that overlapping sequences can be dynamically identified and exploited."

The paper positions Hydragen as a component to be integrated into inference frameworks (like vLLM or SGLang) that already handle dynamic scheduling and prefix detection. The current implementation is a demonstration of the attention optimization itself, not a complete serving system. A production integration would likely use the existing RadixAttention or PagedAttention mechanisms to dynamically identify shared prefixes, then call Hydragen's attention decomposition and batching for the attention computation over those identified prefixes. This is not a fundamental algorithmic limitation — the decomposition and batching work for any sharing pattern — but it is a substantial engineering gap that prevents immediate deployment in interactive serving settings.

### Prefill Cost Is Excluded From All Throughput Measurements

**The assumption or constraint.** All end-to-end throughput benchmarks in the paper are "decode-only" — they explicitly exclude the time required for the prefill stage where the shared prefix's keys and values are initially computed and stored in the KV cache. Section 4.1 and Appendix D.1 describe the measurement methodology:

> "Our end-to-end benchmarks only measure decoding throughput and exclude the time required to compute the prefill."

The paper justifies this by noting that prefill is a one-time cost amortized over many decoding steps and many sequences sharing the same prefix.

**The consequence.** For workloads where the shared prefix is processed once and then used for many decoding steps across many sequences — such as a chatbot with a fixed system prompt serving thousands of users throughout the day — excluding prefill time is reasonable because the amortized per-token cost of prefill is negligible. However, for many of the scenarios the paper uses as motivation, the prefill cost can be substantial and may even dominate end-to-end latency:

- **Sustained serving with long prefixes:** A 16K-token system prompt requires a 16K-token prefill forward pass. While this is indeed amortized over many queries, the *latency* of that initial prefill (which can be seconds for a 16K-token prompt) may be unacceptable for interactive applications where the first response must be fast. The throughput numbers (tokens per second during decoding) look excellent, but the user still waits for the prefill to complete before any decoding begins.

- **One-shot batch evaluation:** In the competitive programming benchmark (Section 4.4), a 2400-token few-shot prompt is prefill-processed once and then used for 128 candidate solutions per problem. The total prefill time is amortized over 128 × 120 = 15,360 decoding streams, so the per-stream amortized cost is small. However, for applications with fewer completions per prefix (e.g., sampling only 4–8 candidates), the unmeasured prefill cost represents a larger fraction of total time.

- **Long document QA (Section 4.3):** A 19,947-token prefix requires a substantial prefill. The paper notes in Figure 5's caption "Time to process prefix is excluded." For a one-time document QA task where the model answers questions immediately after prefill, the excluded prefill time could be comparable to or larger than the measured decoding time, making the reported "Hydragen processes 256 questions in less time than FlashAttention processes 64" somewhat misleading — this is true for decoding time only, not end-to-end wall-clock time.

**What evidence exists in the paper.** The paper does not report any prefill time measurements. There is no comparison of total (prefill + decode) wall-clock time for any benchmark. The authors note (Appendix D.1) that vLLM appears to redundantly detokenize the prompt for every sequence during prefill, which can take "minutes for large batch sizes and sequence lengths" — a cost that is excluded from the decode-only throughput numbers but would be part of any realistic end-to-end measurement. The paper acknowledges prefill as an orthogonal concern and does not claim Hydragen accelerates it.

**Mitigation status.** The paper does not address this limitation. Hydragen targets the decoding phase specifically, and the prefill phase is inherently compute-bound (many query tokens processed in parallel, yielding efficient matrix-matrix multiplications) and would not benefit from Hydragen's inter-sequence batching because the prefix keys and values are being *computed* for the first time, not *read* from a pre-existing KV cache. The prefill cost is therefore a fundamental overhead that Hydragen cannot reduce. A complete deployment would need to combine Hydragen (for decoding throughput) with techniques that reduce prefill cost — such as RadixAttention's caching of prefill computations for reused prefixes, or prompt compression techniques that shrink the prefix before prefill. The paper does not discuss these combinations or report how they would affect end-to-end performance.

### Single Model Family and Synthetic Workloads Leave Generality Unverified

**The assumption or constraint.** All experiments use models from the Llama family (CodeLlama-7b/13b/34b and Yi-6B-200k) employing standard multi-head attention or GQA-like reductions, evaluated on synthetic prompts of controlled lengths rather than real production workloads. The paper states in Section 4.1:

> "We run our benchmarks on CodeLlama-13b"

and in Section 4.3:

> "We construct a document by embedding synthetic facts into an excerpt of War and Peace"

The long document QA benchmark uses procedurally generated facts and questions ("The dog named {name} has fur that is {color}" / "What color is the fur of the dog named {name}?"), not a standard NLP benchmark.

**The consequence.** Several aspects of the findings could be model-architecture-specific or workload-specific:

1. **Attention architecture sensitivity:** The CodeLlama models use standard multi-head attention with 32 key-value heads. Models using Grouped-Query Attention (GQA) with fewer key-value heads (common in Llama 2 70B, Llama 3, Mistral) have smaller KV caches per head, reducing the absolute cost of the memory-bound attention that Hydragen accelerates. The paper argues (Section 3.4) that Hydragen's relative speedup would be smaller for GQA models but the absolute throughput could still be higher because smaller KV caches enable larger batch sizes. This interaction — smaller per-operation benefit but larger maximum batch — is not empirically characterized. The only non-MHA model tested is Yi-6B-200k (4 key-value heads, akin to GQA with large group size), which shows strong Hydragen performance (Figure 5), but no systematic sweep across GQA configurations is performed.

2. **Model scale extrapolation:** The largest model tested is CodeLlama-34b (approximately 34 billion parameters). For models at the 70B+ scale, the MLP blocks consume an even larger fraction of total FLOPs relative to attention, further reducing the end-to-end impact of attention acceleration. The trend is visible in the paper's own data: the speedup over vLLM at batch 1024 and prefix 2048 decreases from 9.0× (CodeLlama-7b) to 5.5× (CodeLlama-13b) to 3.3× (CodeLlama-34b). Extrapolating this trend to 70B or 405B models, the speedup might become modest, though it would still be meaningful at very large batch sizes and long prefixes where attention dominates. No experiment confirms or refutes this extrapolation.

3. **Workload realism:** The throughput benchmarks use synthetic prompts of fixed token lengths (1K, 2K, 4K, 8K, 16K tokens) with no natural language content. The long document QA benchmark, while using real text (War and Peace), embeds synthetic facts and uses procedurally generated questions. Real production workloads — actual chatbot conversations, real code generation tasks, retrieval-augmented generation with variable retrieved document lengths — may have different prefix-to-suffix ratios, different attention patterns, or different computational bottlenecks that affect Hydragen's relative benefit. The paper provides no evidence that the throughput results transfer to real deployment traces.

4. **No encoder-decoder or cross-attention models:** Hydragen's approach assumes standard causal self-attention in decoder-only transformers. It is not obvious whether the decomposition and inter-sequence batching would apply to encoder-decoder architectures (T5, BART) with cross-attention between encoder outputs and decoder queries, or to mixture-of-experts models where different tokens may be routed to different experts.

**What evidence exists in the paper.** The consistent pattern across three model sizes (Tables 1–6 in Appendix C.1) provides some confidence that the trends generalize within the Llama architecture. The Yi-6B-200k results (Figure 5) show Hydragen working well with a GQA-like model, and the microbenchmarks (Figure 4, Figure 7) use an abstracted attention configuration (8 query heads, 1 key-value head, head dimension 128) that is architecture-agnostic and shows the attention-level speedup directly. However, no experiment tests a non-Llama model family, a model larger than 34B, or a real production workload trace.

**Mitigation status.** The paper does not claim generality beyond the tested models and workloads; it presents results on representative configurations and explicitly notes in Section 3.4 that benefits depend on "the details of the inference setting being considered." The authors frame their work as a demonstration of the technique rather than a comprehensive evaluation across all model architectures. The open-source code release enables others to test on additional models and workloads, but the paper itself provides no further evidence.

### Hydragen Provides No Benefit for Suffix Attention, and Performance Degrades as Suffixes Grow

**The assumption or constraint.** Hydragen's decomposition and inter-sequence batching apply exclusively to the *shared prefix* portion of attention. Suffix attention — where each sequence has distinct keys and values from its own generated completion tokens — is computed using standard per-sequence matrix-vector products with no batching or acceleration. The paper states this explicitly in Section 3.2:

> "Note that we are unable to apply inter-sequence batching when computing attention over suffixes, since the keys and values in each sequence's suffix are not identical."

**The consequence.** This creates a fundamental tradeoff that limits Hydragen's benefit in several important regimes:

1. **Long completions erode the speedup.** As decoding proceeds, the suffixes (completion tokens generated so far) grow linearly with the number of generation steps, while the prefix length remains fixed. The fraction of total attention time spent on suffixes increases, and since suffix attention is unaccelerated, the overall speedup over FlashAttention decreases. The microbenchmarks in Figure 4 quantify this decay: at batch size 4096 and prefix length 8192, the speedup drops from ~16× at suffix length 0 to ~8× at suffix length 500. If completions are very long (thousands of tokens), the suffix attention cost could eventually dominate, reducing Hydragen's benefit to near-zero for the later tokens. This means Hydragen's throughput advantage is highest for the *first* tokens generated and gradually diminishes throughout each sequence's generation — a non-uniform speedup profile that complicates throughput estimation.

2. **Short-prefix, long-suffix workloads benefit least.** Applications with short shared prefixes and long completions — such as few-shot prompts with lengthy generated essays, or system prompts of a few sentences followed by long code generation — will see minimal benefit from Hydragen because the prefix constitutes a small fraction of total attention work. The paper's largest speedups occur when the prefix is thousands of tokens and completions are hundreds; reversing this ratio (hundred-token prefix, thousand-token completions) would produce much smaller gains.

3. **Suffix memory management is not addressed.** Hydragen stores suffix KV caches without paging or sophisticated memory management (unlike vLLM's PagedAttention). As suffixes grow, the per-sequence KV cache memory footprint grows, potentially limiting the maximum batch size that can be maintained throughout generation. This is not a Hydragen-specific problem — it affects all batched inference — but Hydragen does not provide any mitigation for it. A combined system using PagedAttention for suffix memory management and Hydragen for prefix attention computation would address both, but such a combination is not demonstrated.

**What evidence exists in the paper.** The microbenchmarks (Figure 4) are the primary evidence, explicitly sweeping suffix length from 0 to 500 tokens while holding batch size and prefix length constant. The speedup curves show a consistent downward trend as suffix length increases across all batch-size/prefix-length configurations. The end-to-end experiments (Tables 1–6) show a small but consistent reduction in Hydragen throughput when generating 256 tokens vs. 128 tokens (e.g., CodeLlama-13b at batch 1024, prefix 2048 drops from 15.6K to 15.5K TPS), confirming that longer suffixes reduce throughput. The effect is small in these experiments because the prefixes (1K–16K tokens) remain large relative to the suffixes (128–256 tokens). The long document QA experiment (Figure 5) has a massive prefix (~20K tokens) and very short completions (question-answering, likely single-digit tokens), so suffix cost is negligible — this is the ideal case.

**Mitigation status.** The paper acknowledges the suffix limitation in Section 3.4:

> "Hydragen makes no optimizations to attention over suffixes, long suffixes can decrease generation throughput."

It presents the microbenchmark results showing the decay with suffix length, so the tradeoff is well-characterized for the tested configurations. However, the paper does not propose any technique to accelerate suffix attention (which may be impossible for unique per-sequence suffixes without hardware support for batched matrix-vector products) or to reduce the rate at which suffixes grow (e.g., through early stopping, speculative decoding, or suffix token merging). The practical recommendation is implicit: Hydragen is most beneficial when the shared prefix is long relative to the completions. For deployments with the opposite characteristic, the paper provides no solution.

### No Integration with a Continuous Batching Scheduler or Production Serving Stack

**The assumption or constraint.** Hydragen is evaluated as a standalone attention implementation in a custom benchmarking harness, not integrated into a production inference serving system with continuous batching, request scheduling, or KV cache memory management. The paper states in Section 5:

> "We emphasize that Hydragen is an optimization that can be applied as part of a larger inference framework, and is not intended to be an end-to-end inference solution."

**The consequence.** Several practical aspects of production deployment are unexplored, and the reported throughput numbers may not translate directly to a real serving environment:

1. **Continuous batching dynamics:** In a production serving system, sequences complete at different times (some generate short responses, some long), and new sequences continuously enter the batch. The batch composition — and therefore the sharing structure — changes over time. Hydragen's current implementation lacks the scheduling logic to maintain batching groups as sequences arrive and depart, to decide when to switch from batching queries together to computing attention independently, or to handle the case where some sequences in the batch have outgrown their suffix and new sequences with fresh suffixes enter. The throughput benefits measured in static batches may be reduced in a dynamic setting due to imperfect batching opportunities, scheduler overhead, or load imbalance.

2. **KV cache memory management for suffixes:** Hydragen's implementation does not include a paging system for suffix KV caches. As suffixes grow, memory consumption increases, and without paging (like vLLM's PagedAttention), the maximum batch size that fits in GPU memory is lower than what a production system could achieve. The reported throughput numbers for large batch sizes (1024, 2048) may not be achievable in a system that also needs to manage suffix memory efficiently.

3. **No latency measurements.** The paper reports throughput (tokens per second) but never reports latency (time to first token, time per output token). For interactive applications, latency matters as much as throughput. Hydragen's batching of queries across sequences could potentially increase per-step latency (more computation per step due to larger matrix multiplications, even if more tokens are processed overall) — a tradeoff that is not measured. The CUDA graph usage (Section 3.5) is designed to minimize launch overhead for latency-sensitive settings, but no latency numbers are provided.

4. **No integration with prefix detection mechanisms.** Systems like SGLang's RadixAttention dynamically identify the longest matching prefix for incoming requests to avoid recomputation. Hydragen could benefit from such a mechanism to automatically determine prefix boundaries, but no integration is demonstrated. The user currently specifies the sharing structure manually, which is impractical for a production system with variable request patterns.

**What evidence exists in the paper.** No experiments involve continuous batching, variable arrival rates, or integration with a serving scheduler. All benchmarks use pre-organized static batches. The vLLM baseline (Section 4.1) includes vLLM's continuous batching scheduler as part of its inference pipeline, while Hydragen's benchmarks use a simpler, custom harness — so the comparison is not entirely fair on this dimension (vLLM pays some scheduler overhead that Hydragen's harness avoids). The paper does not compare against vLLM's throughput in a setting where continuous batching is the primary optimization (e.g., serving variable-length requests with stochastic arrival) because Hydragen would need to be integrated into a comparable serving stack to make this comparison meaningful.

**Mitigation status.** The paper acknowledges this as a scoping decision, not a fundamental limitation, and explicitly identifies the integration as important future work (Section 5). The simplicity of Hydragen's implementation (no custom CUDA, pure PyTorch plus fast attention primitives) is presented as an advantage for integration — it should be easier to incorporate into existing serving frameworks than approaches requiring custom GPU kernels. However, the engineering effort to build a production-quality serving system around Hydragen (with continuous batching, dynamic prefix detection, suffix paging, and latency-aware scheduling) is substantial and not addressed in this paper. The open-source code release provides a starting point, but the gap between a research attention kernel and a production serving stack is large.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

Hydragen introduces a **reframing of the shared-prefix inference problem** that shifts the field's focus from memory capacity to memory bandwidth. Prior to this work, the dominant approach to shared prefixes — exemplified by vLLM's PagedAttention (Kwon et al., 2023) — treated the problem as one of eliminating redundant storage: store the prefix KV cache once and share references to it across sequences. This framing led to elegant virtual paging systems that reduce GPU memory consumption and enable larger batch sizes, but it left the attention computation itself untouched — each sequence still performed independent, memory-bound matrix-vector products that redundantly read the prefix from memory.

Hydragen's reframing is that **shared prefixes expose redundant memory reads, not just redundant memory allocation**, and that these reads constitute a bandwidth bottleneck that grows with batch size and prefix length faster than memory capacity constraints. The conceptual shift is from "we need to store the prefix once" to "we need to read the prefix once" — a distinctly harder problem because it requires restructuring the computation itself, not just the memory layout. This reframing is not a paradigm shift (the underlying mathematical tools — attention decomposition via LSE, inter-sequence batching — existed before this work), but it is a significant reinterpretation of where the bottleneck lies and what kind of solution is needed.

**The magnitude of the change is substantial within its scope.** For the specific but important workload pattern of batched inference with shared prefixes, Hydragen demonstrates that prefix attention can be nearly eliminated as a throughput bottleneck. The empirical evidence is striking: at batch size 1024 and prefix length 16K tokens, Hydragen's CodeLlama-13b throughput remains within 76% of the No Attention ceiling (Figure 3b), while vLLM's throughput drops to 2% of that ceiling. This is not an incremental 20–30% improvement — it is an order-of-magnitude change in what prefix lengths are practically usable at scale. The finding that increasing prefix length from 1K to 16K tokens decreases Hydragen throughput by less than 15% (versus >90% for vLLM) fundamentally alters the cost-benefit calculus for prompt engineering: long system prompts, many few-shot examples, and large retrieved documents become nearly free in terms of decoding throughput.

The reframing also reconciles a subtle tension in the literature. Prior work on KV cache optimization (MQA, GQA, PagedAttention) implicitly suggested that the path to higher throughput was to *shrink the KV cache* — fewer key-value heads, paged memory to fit more sequences. Hydragen demonstrates that an orthogonal path — *eliminating redundant reads of the existing cache* — can provide comparable or larger benefits without changing the model architecture. These approaches are complementary (Hydragen works with MHA, and GQA enables even larger batches for Hydragen to accelerate), but Hydragen's existence means that model architects need not trade off attention quality (fewer key-value heads) for throughput if the deployment pattern involves shared prefixes.

**Research directions that become more attractive:**

- **Prefix-rich inference algorithms.** Since Hydragen makes long shared prefixes nearly free, algorithms that consume substantial shared context — many few-shot examples, detailed system instructions, extensive chain-of-thought templates, retrieval-augmented generation with long retrieved documents — become economically viable at scale. This should encourage more aggressive use of in-context learning and prompt engineering rather than fine-tuning, since the inference cost of long prompts is no longer prohibitive.

- **Hardware-aware attention design for structured sparsity patterns.** Hydragen exploits one specific structure (shared prefixes) to convert memory-bound to compute-bound operations. Other structured sparsity patterns in attention — such as sliding windows, block-sparse patterns, or hierarchical attention — might admit similar decomposition-plus-batching strategies. The paper's success with a simple, exact decomposition suggests that more sophisticated attention patterns could benefit from hardware-aware restructuring without approximation.

- **Cross-sequence batching as a general primitive.** The core idea of batching attention queries across sequences whenever key-value contexts overlap could be applied beyond prefix sharing. For example, in multi-turn conversations, sequences that share a conversation history up to a branch point could have their shared-history attention batched. In retrieval-augmented generation, sequences that retrieve the same document could share that document's attention computation. This generalizes Hydragen from a prefix-specific optimization to a more general framework for exploiting any key-value overlap across sequences.

**Research directions that become less attractive:**

- **Pure memory-capacity optimizations for shared prefixes.** vLLM's PagedAttention largely solved the memory-capacity side of shared prefixes. Hydragen shows that capacity was never the primary throughput bottleneck — bandwidth was. Further work on more sophisticated prefix storage schemes (beyond what PagedAttention already provides) is unlikely to yield significant throughput improvements because the bottleneck has shifted. The remaining capacity challenge is suffix management during long generations, which Hydragen does not address.

- **Architectural changes solely for KV cache size reduction.** MQA and GQA were motivated in part by the desire to reduce the KV cache memory footprint and bandwidth cost. Hydragen demonstrates that for shared-prefix workloads, the bandwidth cost can be addressed at the systems level without shrinking the KV cache. While GQA remains valuable for enabling larger batch sizes (by freeing GPU memory), the argument that reducing key-value heads is *necessary* for throughput is weakened for shared-prefix serving. Models with full multi-head attention may be more viable in deployment than previously thought, as long as the serving infrastructure exploits prefix sharing.

### Follow-Up Research This Work Enables

**Integration of Hydragen with continuous batching schedulers on production workloads.** The paper evaluates Hydragen on static, pre-organized batches where the sharing structure is known in advance. The most important immediate follow-up is to integrate Hydragen into a production inference serving system (such as vLLM or SGLang) with continuous batching, dynamic prefix detection (like RadixAttention), and suffix KV cache paging. A strong follow-up would: (a) implement Hydragen attention as a drop-in replacement for the attention operation in vLLM's serving stack, (b) use RadixAttention or a similar mechanism to dynamically identify shared prefixes from incoming request streams, (c) benchmark on real production traces (e.g., chatbot logs with variable system prompts, LMSYS-Chat-1M, or synthetic traces with Pareto-distributed prompt reuse), and (d) measure both throughput and latency (time-to-first-token, token-to-token latency) under realistic request arrival patterns with variable prefix lengths and completion lengths. The key question is whether the 32× speedups observed in static offline batches translate to dynamic serving, and if not, how much of the benefit is retained and what new bottlenecks emerge (scheduler overhead, prefix detection latency, load imbalance when some sequences complete and leave the batch while others continue). This is the single most impactful follow-up because it bridges the gap from a research attention kernel to a deployable system.

**Hydragen with Grouped-Query Attention: characterizing the interaction between KV cache shrinkage and batched attention.** The paper notes (Section 3.4) that GQA models have smaller KV caches, which reduces the absolute benefit of Hydragen per attention operation but allows larger batch sizes — the net effect on end-to-end throughput is unclear. A systematic study would: (a) take a single base model architecture and create variants with different GQA group sizes (e.g., 1, 4, 8, 32 key-value heads), (b) benchmark Hydragen vs. FlashAttention and vLLM on each variant across a sweep of batch sizes and prefix lengths, (c) measure both attention-level speedup and end-to-end throughput, and (d) determine whether there exists an optimal GQA group size that maximizes combined throughput when Hydragen is deployed. The hypothesis from the paper's data is that smaller group sizes reduce per-operation benefit but enable larger batch sizes, potentially yielding a "sweet spot" where the batch-size increase compensates. This experiment would provide concrete guidance for model architects choosing attention configurations for shared-prefix serving deployments.

**Hierarchical Hydragen for tree-of-thought and search-based reasoning.** The APPS competitive programming experiment (Section 4.4) demonstrates two-level hierarchical sharing for a specific static pattern (global few-shot prompt + per-problem descriptions). Many recent LLM algorithms — Tree-of-Thoughts (Yao et al., 2023), Graph-of-Thoughts (Besta et al., 2023), Monte Carlo Tree Search with LLMs, and self-consistency over branching reasoning paths — involve tree-structured prompt sharing where many candidate reasoning paths diverge from shared intermediate states. A strong follow-up would: (a) implement Hydragen with dynamic tree construction, where the sharing tree is not known in advance but grows as the search algorithm expands nodes, (b) apply it to a Tree-of-Thoughts benchmark (e.g., Game of 24, creative writing, or mini-crosswords) with hundreds to thousands of candidate paths, (c) measure the total inference time reduction compared to a naive per-sequence attention baseline, and (d) characterize how the benefit scales with tree depth, branching factor, and the fraction of tokens that are shared versus unique at each level. This would demonstrate whether Hydragen's hierarchical generalization can accelerate the kinds of structured exploration that are increasingly central to LLM reasoning research, and whether the batch-size amplification from hierarchical sharing (as seen in Figure 6's 55% reduction) scales to deeper trees with more nodes.

**Prefill-time optimization for Hydragen: quantifying and reducing the excluded cost.** The paper explicitly excludes prefill time from all throughput measurements, acknowledging that for very long shared prefixes, prefill can be substantial. A direct follow-up would: (a) benchmark total end-to-end latency (prefill + decode) for Hydragen versus baselines across a sweep of prefix lengths (1K to 32K tokens) and batch sizes, (b) quantify what fraction of total time is spent in prefill versus decode as a function of prefix length and number of completions per prefix, (c) determine the break-even point — how many decoding steps or sequences must share a prefix for the decode-time savings to outweigh the prefill cost, and (d) explore combining Hydragen with prefill-time optimizations such as prefix caching (RadixAttention's approach of reusing prefill computations when the same prefix appears across batches) or prompt compression (reducing prefix length before prefill). This experiment would provide the complete cost picture that the current decode-only measurements obscure, and would identify the deployment regimes (sustained serving vs. one-shot batch evaluation vs. interactive low-latency) where Hydragen's benefits are most and least compelling.

**Stress-testing Hydragen on non-Llama architectures and very large models.** The paper evaluates only Llama-family decoder-only models up to 34B parameters. A stress-test follow-up would: (a) port Hydragen to a non-Llama architecture — Mixture-of-Experts (e.g., Mixtral 8×7B), encoder-decoder (e.g., FLAN-T5), or models with non-standard attention patterns (e.g., models with cross-attention, sliding-window attention like Mistral, or hybrid sparse-dense attention), (b) benchmark on these architectures to determine whether Hydragen's decomposition and batching generalize or whether architecture-specific modifications are needed (e.g., for cross-attention where the shared "prefix" might be the encoder outputs), (c) scale to a very large dense model (70B–405B parameters) to test the paper's implicit extrapolation that Hydragen's relative speedup diminishes with model size as MLP FLOPs dominate, and (d) for MoE models specifically, investigate whether the expert routing introduces per-token variability in computational cost that interacts with Hydragen's batching. The key questions are: does Hydragen work unchanged, does it require architectural awareness (e.g., knowing which tokens are routed to which experts), and at what model scale does the end-to-end benefit become negligible even at large batch sizes and long prefixes? This stress-test would establish the boundaries of Hydragen's applicability and identify architectural features that either amplify or suppress its benefits.

**Adaptive prefix-suffix boundary selection for mixed workloads.** Hydragen currently assumes a fixed boundary between the shared prefix and unique suffixes, specified by the user. In real deployments, the optimal boundary may not be obvious — sequences may share varying amounts of initial context, and the decision of where to stop sharing (and start computing per-sequence) affects both memory usage (shared tokens are stored once) and compute efficiency (shared tokens benefit from batching). A follow-up could: (a) develop an algorithm that dynamically determines, for a given set of sequences with overlapping prefixes, the optimal cut point that maximizes throughput given a memory constraint and expected completion lengths, (b) implement this as an online decision in a continuous batching scheduler that can choose to share more or fewer tokens based on the current batch composition and memory pressure, and (c) evaluate on mixed workloads where different groups of sequences share different amounts of initial context (e.g., a chatbot serving multiple applications with different system prompts). This would move Hydragen from a fixed-configuration optimization to an adaptive one that can handle heterogeneous sharing patterns without manual specification.

### Practical Applications and Downstream Use Cases

**Large-scale code generation with many candidate samples per problem.** The APPS competitive programming experiment (Section 4.4, Figure 6) directly demonstrates this use case: evaluating 120 problems with 128 candidate solutions each using a two-shot prompt. With two-level Hydragen, total inference time is reduced by 55% compared to single-level sharing. This maps directly to production code generation systems like AlphaCode (Li et al., 2022), which sample up to a million candidate programs per problem. For a deployment evaluating thousands of problems daily with hundreds to thousands of samples each, the 55% time reduction translates to halving GPU-hours consumed or doubling throughput on fixed hardware. The hierarchical sharing pattern (global few-shot examples + per-problem descriptions) is generic across any multi-problem benchmark or production system that uses few-shot prompting. The practical implementation requires only organizing the batch so that sequences sharing intermediate context are grouped together — the tree structure is natural for this workload.

**Chatbot serving with long system prompts at scale.** Consider a deployment where a single LLM serves hundreds of concurrent users, each conversation prepended with a detailed system prompt (e.g., "You are a medical assistant with the following guidelines…" spanning several thousand tokens). Figure 3b demonstrates that with a 16K-token system prompt and batch size 1024, Hydragen achieves 14,000 tokens/second on CodeLlama-13b — within 76% of the theoretical ceiling where attention is free — while vLLM achieves only 300–400 tokens/second. For a service handling millions of queries per day, the throughput difference (32×) directly determines how many GPUs are needed to meet demand. The practical benefit is not just cost savings but also the ability to provide much richer system prompts: detailed safety guidelines, extensive knowledge base context, long conversation histories — all of which were previously prohibitively expensive in terms of decoding throughput because the prefix length multiplied by batch size dominated the attention cost. With Hydragen, the prefix length is nearly decoupled from throughput, enabling prompt engineers to add context without worrying about the throughput penalty.

**Retrieval-augmented generation (RAG) with long retrieved documents.** The long document QA experiment (Section 4.3, Figure 5) with a 19,947-token shared document and up to 256 questions demonstrates that Hydragen can process large batches of queries over a shared long context while staying within 60% of the No Attention optimum. For a RAG system that retrieves a long document (e.g., a legal contract, a scientific paper, a technical manual) and answers many user questions about it — a common pattern in enterprise search, legal tech, and academic research tools — Hydragen enables the document to be prefill-processed once and then queried at high throughput. The paper's result that "Hydragen can process 256 questions in less time than it takes the FlashAttention baseline to process 64 questions" means that for a given latency budget, Hydragen can serve 4× more concurrent users querying the same document. This directly impacts the cost-per-query and the maximum concurrent users for document-grounded QA services.

**Offline batch inference for dataset annotation and synthetic data generation.** Many LLM applications involve running inference over a static dataset with a shared prompt — generating training data, annotating examples, extracting structured information from documents, or scoring candidate outputs. In these settings, the entire dataset is known in advance, the sharing structure can be specified exactly, and Hydragen's static batching assumption is not a limitation. The end-to-end throughput results (Tables 1–6) show that for a moderate configuration (CodeLlama-13b, batch 128, prefix 2048, 128 generated tokens), Hydragen achieves 5.8K tokens/second versus vLLM's 4.7K — a 23% throughput improvement. For larger batch sizes and longer prefixes, the improvement grows to multiple times. For organizations running nightly batch inference jobs over millions of examples, a 23%–300% throughput improvement directly reduces GPU rental costs or enables processing larger datasets on fixed hardware. The practical integration is straightforward because the sharing structure is known from the dataset format — there is no dynamic scheduling complexity.
