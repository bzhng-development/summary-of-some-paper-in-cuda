# Faster Causal Attention Over Large Sequences Through Sparse Flash Attention

**ArXiv:** [2306.01160](https://arxiv.org/abs/2306.01160)

## 🎯 Pitch

This paper introduces **Sparse Causal Flash Attention (SCFA)**, a GPU kernel extending FlashAttention to handle dynamic, irregular sparsity patterns in the causal attention matrix — specifically, query/key dropping (where entire key or query heads are discarded per example) and hash-based sparsity (where attention is restricted to keys and queries sharing the same hash bucket).

---

## 1. Executive Summary

This paper introduces **Sparse Causal Flash Attention (SCFA)**, a GPU kernel extending FlashAttention to handle dynamic, irregular sparsity patterns in the causal attention matrix — specifically, query/key dropping (where entire key or query heads are discarded per example) and hash-based sparsity (where attention is restricted to keys and queries sharing the same hash bucket). Evaluated on autoregressive language modeling benchmarks including OpenWebText2 with a 122M-parameter transformer, SCFA delivers training speedups of 2.0× and 3.3× for sequences of 8k and 16k tokens respectively without sacrificing perplexity, establishing that dynamic sparse attention can outperform dense FlashAttention in wall-clock time only when the sparsity pattern is sufficiently coarse-grained to amortize the linear-cost pre-processing overhead against the quadratic savings in attention computation.

## 2. Context and Motivation

### The Core Problem: Dynamic Sparsity Patterns Are Theoretically Promising but Practically Useless

The fundamental tension this paper addresses is one that anyone who has implemented a sparse transformer quickly discovers: **you can design clever algorithms that reduce the asymptotic complexity of self-attention, but your GPU will punish you for it.** The self-attention mechanism in transformers scales quadratically with sequence length $O(T^2)$ — this is the bottleneck that everyone wants to solve — yet the most successful deployed models (GPT-family, PaLM, LLaMA) overwhelmingly use dense, vanilla attention. Why? Because the FlashAttention kernel (Dao et al., 2022) made dense attention so fast on actual hardware that mathematically cheaper sparse methods end up being *slower in wall-clock time*, not faster.

This paper identifies a specific technical gap that explains this paradox. FlashAttention achieves its speed by carefully tiling the attention computation — processing the attention matrix in blocks to minimize data transfer between GPU high-bandwidth memory (HBM) and on-chip SRAM. Critically, FlashAttention's causal masking logic assumes a **perfectly regular, lower-triangular structure**. When you want to apply a causal mask, FlashAttention checks block indices: if the query block index $i$ is strictly greater than the key block index $j$, compute the full tile; if $i = j$, apply a standard lower-triangular mask within the tile; if $i < j$, skip the tile entirely. This is efficient but brittle — it only works when the causal mask is a clean triangle.

The paper identifies two concrete scenarios where this assumption breaks:

1. **Query/key dropping**: If you independently decide to keep or discard individual key and query heads (as proposed by methods like token pruning in Goyal et al., 2020, or head pruning in Michel et al., 2019), and then compact the tensors by removing dropped elements, the remaining attention matrix is no longer a clean triangle. The indices are still monotonically increasing (you preserve time order), but there are "holes" where keys or queries were removed, creating an irregular staircase pattern (Figure 1, center, and Figure 2, center bottom). FlashAttention cannot handle this — it would either compute unnecessary tiles or, worse, fail to compute required ones.

2. **Hash-based sparsity**: If you assign hash codes to keys and queries (as in the Reformer; Kitaev et al., 2020), sort them by hash bucket, and restrict attention to within-bucket interactions, you get a block-diagonal-plus-off-diagonal structure with irregular causal masking within each block (Figure 1, right, and Figure 2, right bottom). The attention matrix now has a complex pattern of "compute these tiles, skip those tiles" that FlashAttention's simple index-comparison logic cannot express.

The core gap is therefore: **there exists no IO-aware, tiled attention kernel that can handle dynamic, irregular sparsity patterns while maintaining the memory efficiency of FlashAttention.** Without such a kernel, researchers proposing dynamic sparse attention schemes face a cruel choice: (a) implement their method with existing library calls, which forces materialization of a mask and typically falls back to a slower code path — resulting in runtimes *worse* than dense FlashAttention even at high sparsity levels — or (b) simplify their sparsity pattern to be static and regular (like block-sparse or local window patterns) so that existing kernels can handle it, sacrificing the adaptivity that made the approach promising in the first place.

### Why This Matters: The Sequence Length Scaling Wall

The importance of this problem is driven by a clear trend in deployed transformer applications: sequence lengths are growing rapidly. Long-document understanding, code generation with full repository context, multi-turn dialogue with long history, video understanding as token sequences, and biological sequence modeling (DNA, proteins) all push sequence lengths into the tens or hundreds of thousands of tokens. The paper's Figure 9 illustrates why this is an existential problem: for a 12-layer transformer, the attention operations dominate total runtime as sequence length grows, while the feed-forward components scale only linearly.

This creates an economic and environmental pressure. Training and serving models on 16k, 32k, or 128k token sequences is expensive — the quadratic attention cost means that doubling the sequence length roughly quadruples the attention FLOPs. The paper cites the broader concern captured by Bender et al. (2021) and Weidinger et al. (2021) about the energy and societal costs of large language models. Making attention efficient isn't just an academic exercise; it directly affects who can afford to train and deploy these models, and what applications are economically viable.

However, the paper also makes clear that the problem isn't just about raw FLOP reduction — it's about **translating algorithmic sparsity into actual wall-clock speedups on GPU hardware**. This is the key framing: many papers claim to reduce the asymptotic complexity of attention, but if the constant factors (from irregular memory access, mask materialization, or kernel launch overhead) are large enough, the "faster" algorithm loses to optimized dense attention for all practical sequence lengths. The paper aims to close this translation gap.

### Where Prior Approaches Fall Short

The paper surveys the efficient transformer landscape (Section 2 and Appendix A) and identifies three categories of prior work, each with characteristic limitations:

**1. Linearized and kernel-based attention (Katharopoulos et al., 2020; Choromanski et al., 2020; Wang et al., 2020; Peng et al., 2021; Qin et al., 2022).** These methods replace or approximate the softmax attention with operations that permit linear-complexity computation via the associativity of matrix products (computing $Q(K^\top V)$ rather than $(QK^\top)V$). While these achieve genuine asymptotic complexity reductions, the paper notes a critical weakness (Appendix A.1): they "have been shown to underperform on certain downstream tasks" (citing Tay et al., 2021b). The issue is expressivity — the softmax attention's ability to produce sharply peaked distributions that focus on specific tokens is traded away for computational efficiency. For language modeling, where precise attention to specific context tokens matters, this degradation is often unacceptable. The paper explicitly contrasts its approach: "Compared to those methods, we are not trying to replace or find an estimator of the softmax attention, we instead provide an efficient way to leverage different forms of sparsity of the softmax attention matrix." This is a key distinction — SCFA preserves the exact softmax computation where it matters, rather than approximating it everywhere.

**2. Static sparse attention patterns (Child et al., 2019; Zaheer et al., 2020; Beltagy et al., 2020).** These methods impose a fixed, hand-designed sparsity structure — local windows, strided patterns, global tokens, or combinations thereof — that is independent of the input content. Information from distant tokens is assumed to propagate through the fixed structure over multiple layers. While these patterns can be implemented efficiently (FlashAttention itself supports block-sparse patterns), the paper's critique is implicit: fixed patterns cannot adapt to the varying importance of different tokens across different inputs, heads, or positions. Two sequences of identical length may require attention to entirely different subsets of tokens, and a static pattern either over-computes (attending to irrelevant tokens) or under-computes (missing important ones).

**3. Dynamic sparse attention with implementation pathologies.** This is the category the paper most directly engages with. Two exemplars are highlighted:

- **The Reformer (Kitaev et al., 2020)**: Uses locality-sensitive hashing (LSH) to assign queries and keys to buckets, then restricts attention to within-bucket interactions. The idea is elegant: only compute dot products for key-query pairs likely to have high similarity. However, the actual GPU implementation required significant compromises. To efficiently batch computation on GPUs, the Reformer splits queries into **fixed-size chunks** and allows attention only within the same chunk and one neighboring chunk. This means the implementation does not actually compute all within-bucket interactions — the "coverage" (fraction of hash collisions actually attended to) drops significantly as sequence length increases (Figure 4b). The paper quantifies this: at longer sequences, the Reformer misses a substantial fraction of the key-query pairs it *should* attend to according to the hash buckets. This is not a theoretical limitation of the algorithm, but an implementation limitation forced by the lack of a flexible kernel.

- **Naive implementations of dynamic sparsity using existing PyTorch operations**: The paper demonstrates this concretely in Figure 7a. If you try to implement query/key dropping by compacting tensors (removing dropped elements) and then calling `torch.nn.functional.scaled_dot_product_attention` with a custom causal mask, two things go wrong. First, the mask is no longer lower-triangular, so PyTorch cannot use the FlashAttention backend (it falls back to a slower generic implementation). Second, even if you accept the fallback, the mask must still be materialized and applied, adding overhead. The result: as the paper shows, "a naive implementation using existing PyTorch functionalities only starts to provide a speedup when dropping more than 70% of the keys and queries." Below 70% sparsity, the overhead of the non-Flash path exceeds the savings from computing fewer attention dot products. This is a devastating finding — it means that, with existing tools, you must discard more than two-thirds of your attention computation before you break even with dense FlashAttention.

**4. Pruning literature disconnect.** The paper also contextualizes its work against the substantial literature on pruning transformer heads and tokens (Michel et al., 2019; Voita et al., 2019; Goyal et al., 2020; Wang et al., 2021). Many of these methods make fine-grained pruning decisions — dropping individual heads or tokens based on importance scores — but the paper points out (Appendix A.2) that they are primarily evaluated for *inference speedup on downstream tasks*, not for training efficiency. Moreover, many modify the training process to facilitate later pruning, which can make training *slower*, not faster. The paper positions its contribution as orthogonal: it provides the kernel infrastructure that could make these fine-grained dynamic pruning methods practical *during training*, where the speedup is most needed.

### How This Paper Positions Itself

The paper's positioning has three key facets:

**First, it is a systems contribution that enables algorithmic research.** The authors are explicit that they are not proposing a new sparsity pattern or a new attention mechanism. The novel hash and QK-dropping schemes they present are "prototypes" — deliberately simple instantiations meant to demonstrate the kernel's capabilities, not to claim state-of-the-art sparsification methods. The real contribution is the SCFA kernel itself, which they hope will "inspire the community to research dynamic attention patterns in a way that is less constrained by a tight computational budget" (Section 5). This is a classic systems-for-ML contribution: remove a hardware-imposed constraint so that algorithm designers can innovate freely.

**Second, it targets the exact computation, not approximations.** Unlike linearized attention or kernel methods, SCFA computes the *exact* softmax attention on the selected subset of key-query pairs. The paper argues this is important because it preserves the expressivity and sharp focus of softmax attention, which matters for language modeling quality. The sparsity comes from *deciding not to compute* certain dot products — not from approximating the ones you do compute. This is particularly visible in the hash-based attention comparison with the Reformer (Figure 4b): SCFA achieves 100% coverage of hash collisions (every key-query pair that should be computed gets computed), while the Reformer's chunked implementation misses an increasing fraction as sequences grow longer.

**Third, it demonstrates that sparsity must be sufficiently coarse-grained to be GPU-efficient.** This is the paper's most practically important insight, though it's stated implicitly through the experimental results rather than as an explicit design principle. The QK-sparse results (Figure 7) show that the Pre-processing overhead (sorting, compacting, padding tensors) grows linearly with sequence length. For short sequences, this linear cost can outweigh the quadratic savings from sparsifying attention, resulting in no speedup or even a slowdown. The break-even point depends on the sparsity level and sequence length, but the trend is clear: as sequences get longer, the quadratic savings dominate, and even modest sparsity (20-30%) yields significant speedups. This insight connects directly to the broader literature on sparse computation on GPUs, where fine-grained sparsity (individual element-level) often fails to translate to speedups because the hardware is optimized for dense, regular computation. SCFA makes sparsity work by operating at the granularity of *tiles* (blocks of queries and keys), where the overhead of deciding which tiles to compute is amortized over many dot products within each tile.

**Fourth, it re-opens the hash-based attention research direction.** The Reformer was an influential paper, but its practical adoption was limited partly because of the implementation compromises it required. By providing a kernel that can handle hash-based sparsity exactly and efficiently, SCFA removes the implementation barrier that forced those compromises. The paper's hash-based language model (H-LM) is a direct demonstration: using the same locality-sensitive hashing scheme as the Reformer, but benefiting from exact collision coverage and a faster kernel, it achieves better perplexity on enwik8 (2.29 vs. 3.32 bits per character) and comparable perplexity on sequential MNIST (1.67 vs. 1.76) while being faster (Table 5, Figure 4a).

In summary, the paper positions SCFA as filling a specific, well-defined gap in the ML systems stack: the lack of an IO-aware, tiled attention kernel that can exploit dynamic, irregular sparsity patterns while preserving exact softmax computation. The motivation is both practical (enabling faster training for long sequences) and methodological (unblocking research on dynamic sparse attention that was previously constrained by implementation limitations).

## 3. Technical Approach

### 3.1 Reader Orientation

This paper develops **Sparse Causal Flash Attention (SCFA)**, a GPU kernel written in Triton that extends the FlashAttention algorithm to compute exact softmax attention efficiently when the causal attention mask is irregular and dynamic — specifically, when you have dropped selected keys and queries or reordered them by hash buckets. The kernel solves the practical problem that existing FlashAttention implementations can only handle perfectly triangular causal masks, which blocks researchers from implementing dynamic sparse attention schemes that actually run faster than dense attention; SCFA introduces index-tracking arrays that accompany the query and key tensors, enabling the kernel to determine which tiles to compute and which to skip based on arbitrary monotonic index structures rather than assuming a fixed triangular pattern.

### 3.2 Big-Picture Architecture (Diagram in Words)

The SCFA system consists of four components that transform the standard attention pipeline:

1. **Pre-processing module** (CPU/GPU boundary) — takes the standard query, key, and value tensors plus a sparsity specification (either hash bucket assignments or keep/drop decisions per head) and produces reordered, possibly compacted tensors plus index and hash tracking arrays. This runs once per attention layer invocation and costs $O(T \log T)$ for sorting (hash-based) or $O(T)$ for compaction (QK-dropping).

2. **SCFA Triton kernel** (GPU on-chip) — the core innovation. Given query, key, and value blocks plus index arrays (`qidx`, `kidx`) and optional hash arrays (`qhash`, `khash`), it iterates over key blocks, uses the tracking arrays to find the first and last relevant tiles, computes dot products only for those tiles, applies local causal and hash masking, and accumulates softmax statistics using the FlashAttention online algorithm. The algorithm is described in pseudocode in Algorithm 1 (QK-sparse) and Algorithm 2 (Hash-sparse) and handles the edge case of queries with no matching keys (Section 3.1, Appendix B.1, Algorithm 3).

3. **Post-processing module** — scatters the compact output back into the original sequence shape (for QK-sparse) or reverse-sorts the output to restore the original token ordering (for Hash-sparse).

4. **The sparsity decision mechanism** (external to SCFA) — produces either per-head hash bucket assignments (via LSH) or per-head keep/drop binary decisions. The paper treats this as a pluggable component and provides simple prototypes (random uniform hashing, random dropping with fixed probability) to validate the kernel, while making clear that more sophisticated sparsity controllers could be substituted.

Information flows as follows: the sparsity controller produces a decision per query/key/head → the Pre-processing module reorders/compacts Q, K, V and builds index/hash tracking arrays → the SCFA kernel computes attention only on relevant tiles using the tracking arrays to navigate the irregular structure → the post-processing module reconstructs the output in the original sequence order.

### 3.3 Roadmap for the Deep Dive

- **First**, the core FlashAttention tiling mechanism, because SCFA is a direct modification of it and understanding the baseline is essential for understanding what changes.
- **Second**, the QK-sparse kernel (Section 3.1), since it is the simpler extension — removing whole queries and keys creates a smaller but still monotonic index structure, and the core modification is replacing the "skip tiles where query block index < key block index" rule with a comparison of actual position indices.
- **Third**, the Hash-sparse kernel (Section 3.2), which builds on the same principle but adds a second level of sparsity (bucket matching) and requires finding both starting and ending tiles rather than just an ending tile.
- **Fourth**, the softmax statistics accumulation under irregular masking, including the NaN-avoidance mechanism (Algorithm 3) that handles the edge case of queries with no matching keys — a detail that is essential for correctness but easy to overlook.
- **Fifth**, the pre-processing pipelines for both methods, because the kernel speedup depends critically on amortizing the cost of sorting and compacting tensors, and understanding this overhead explains the experimental tradeoff curves.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems paper** whose core idea is that dynamic sparse attention can be made GPU-efficient by extending FlashAttention's tiled computation to handle irregular causal structures through index-tracking arrays, and that the resulting kernel enables sparsity patterns (hash-based, QK-dropping) that were previously either approximated or slower than dense computation.

#### The FlashAttention Baseline: Tiling, Online Softmax, and the Triangular Causal Assumption

To understand SCFA, we must first understand what FlashAttention does and why it cannot handle irregular sparsity. The standard self-attention operation for a single head takes a query tensor $Q \in \mathbb{R}^{T_Q \times d}$, a key tensor $K \in \mathbb{R}^{T_{KV} \times d}$, and a value tensor $V \in \mathbb{R}^{T_{KV} \times d}$, and computes:

$$O = \text{softmax}\left( \frac{Q K^\top}{\sqrt{d}} \odot M_{\text{causal}} \right) V$$

where $Q K^\top \in \mathbb{R}^{T_Q \times T_{KV}}$ is the attention score matrix, $d$ is the per-head dimension, $M_{\text{causal}}$ is the causal mask (0 for allowed positions, $-\infty$ for forbidden future positions), and softmax is applied row-wise.

**What it computes:** For each query position, compute dot-product similarity with all keys up to and including that position, normalize with softmax to obtain attention weights, and produce a weighted sum of value vectors. The output $O$ has shape $T_Q \times d$.

**Why this form:** This is the original transformer self-attention from Vaswani et al. (2017) with causal masking added for autoregressive training, where the model can only attend to past positions. The $\sqrt{d}$ scaling prevents dot products from growing too large in high dimensions, which would push the softmax into saturation.

**The naive implementation problem.** A naive PyTorch implementation would: (1) compute the full $T_Q \times T_{KV}$ attention score matrix in GPU high-bandwidth memory (HBM), (2) apply the causal mask, (3) compute row-wise softmax, (4) multiply by $V$, and (5) repeat all these steps in the backward pass, materializing the attention matrix again. The memory cost is $O(T_Q \times T_{KV})$, which for long sequences dominates the GPU memory and forces extremely small batch sizes or sequence truncation.

**FlashAttention's key insight: tiling with online softmax.** Dao et al. (2022) observed that the softmax operation can be computed incrementally using a running statistics algorithm. For a given query vector, softmax over a set of scores can be accumulated as follows: maintain a running maximum $m$ and a running sum $\ell$; when a new chunk of scores arrives, update $m$ to be the maximum of the old $m$ and the new scores' maximum; rescale the old running sum by $e^{m_{\text{old}} - m_{\text{new}}}$; compute the new chunk's softmax contributions relative to $m_{\text{new}}$; add them to the rescaled sum. The paper formalizes this in Appendix B.1, drawing directly from the FlashAttention derivation.

This enables tiling: the attention computation is split into blocks of queries (size $B_m$) and blocks of keys (size $B_n$). The kernel loads one query block into on-chip SRAM, then iterates over key blocks, loading each key block into SRAM, computing the dot-product tile $T_{i,j} = Q_i K_j^\top \in \mathbb{R}^{B_m \times B_n}$, updating softmax statistics online, computing the partial output contribution, and writing the result back to HBM only after all key blocks are processed for that query block. This keeps the attention matrix in fast SRAM (never materialized in HBM), reducing memory transfers from $O(T_Q \times T_{KV})$ to $O(T_Q \times T_{KV} \times d / \text{block\_size})$ — a substantial reduction when the block size is large relative to $d$.

**The causal masking shortcut in FlashAttention.** FlashAttention's causal masking exploits a key property: because the mask is perfectly lower-triangular, the decision of whether to compute a full tile $T_{i,j}$ depends only on the block indices $i$ and $j$. Specifically:
- If query block index $i >$ key block index $j$: compute the full tile (all queries in this block come after all keys in this block, so all dot products are valid).
- If $i = j$: compute the tile but apply a lower-triangular mask within the tile (some query-key pairs are future-masked).
- If $i < j$: skip the tile entirely (all queries precede all keys, everything is future-masked).

This logic is embedded directly in the kernel's loop structure: for a given query block $i$, the kernel only iterates over key blocks $j \leq i$, and the condition `i == j` triggers a local causal mask. This is what makes FlashAttention fast for causal attention — it skips roughly half the tiles without even examining their contents.

**Why this breaks for irregular sparsity.** FlashAttention's block-index comparison relies on a one-to-one correspondence between block indices and temporal position. When you drop keys and queries, this correspondence is broken: a query block $i$ in the compacted tensor may contain queries originally from positions scattered throughout the sequence, and a key block $j$ may contain keys from similarly scattered positions. A tile where $i < j$ might still contain some valid query-key pairs (queries that come after some keys in the tile), and a tile where $i > j$ might contain mostly invalid pairs. FlashAttention has no mechanism to express "compute this tile but only for specific query-key pairs that satisfy a complex condition" — it can only compute entire tiles or local triangular masks.

#### The QK-Sparse Kernel: Extending FlashAttention with Index-Tracking Arrays

The QK-sparse method (Section 3.1) addresses the case where, independently for each head, some keys and queries are dropped entirely from the attention computation. Dropping is per-head and per-position: for a given head, a query at position $t$ might be kept (its head participates in attention) or dropped (it produces a zero output, and no key attends to it). After dropping, the remaining queries and keys are packed into compact tensors $Q^c$, $K^c$, $V^c$ with shapes determined by the maximum number of kept elements across all heads in the batch.

**Pre-processing: building compact representations.** The pre-processing pipeline (Listing 4 in Appendix B.2) operates as follows. Given a keep/drop tensor `q_keep` of shape $B \times T_Q \times H$ (containing 1.0 for kept elements, 0.0 for dropped), the algorithm:

1. For each head independently, identifies which query positions are kept. This is done by sorting `q_keep` along the sequence dimension with `stable=True, descending=True` to bring all kept elements (1.0) to the front while preserving their original temporal order. The `descending=True` is essential — it means all 1.0 entries come before all 0.0 entries, giving a simple "first $k$ elements are kept" structure.

2. Computes the maximum number of kept queries across all heads in the batch, `buffer_size = indices_per_head.max().int()`. This determines the size of the compact tensor — all heads are padded to this maximum size.

3. Gathers the kept queries into a compact tensor `Q_c` of shape $B \times \text{buffer\_size} \times H \times D$ using the sorted indices.

4. Creates an index tensor `q_idx` of shape $B \times \text{buffer\_size} \times H$ that stores, for each position in the compact tensor, the original sequence position from which that query came. This is then padded: for heads with fewer kept elements than `buffer_size`, the extra positions are filled with a sentinel value (-1 for queries, `1e9` for keys).

5. Repeats steps 1-4 for keys and values, using the same `k_keep` tensor for both.

**The critical property: monotonic index structure.** Because the sorting is stable and descending, the index arrays `q_idx` and `k_idx` are monotonically increasing within each head. A query originally at position 3 will appear after a query originally at position 1 in the compact tensor. This monotonicity is what enables the causal logic: if the largest query index in query block $Q^c_i$ is less than the smallest key index in key block $K^c_j$, then no query in $Q^c_i$ can attend to any key in $K^c_j$ (all keys are in the "future" relative to all queries), and the entire tile can be skipped.

**The key kernel modification: finding `j_stop` from index arrays.** Algorithm 1 (Appendix B.1) shows the forward pass for one query block. The crucial addition is a preliminary scan over key blocks to find the last block that needs to be computed. The kernel is given the query block $Q_i$ and its corresponding index block `qidx_i`. It then iterates over key index blocks `kidx_0, kidx_1, ..., kidx_n` and checks the condition:

$$\max(\text{qidx}_i) < \min(\text{kidx}_j)$$

where `qidx_i` is the block of original position indices for the queries in $Q_i$, and `kidx_j` is the block of original position indices for the keys in $K_j$.

**What this condition means:** It asks "is the most temporally advanced query in this query block still earlier in the sequence than the earliest key in this key block?" If yes, then every query-key pair in the tile $Q_i K_j^\top$ is a future-looking pair, and the tile can be entirely skipped. The first key block $j$ for which this condition holds is `j_stop` — tiles $T_{i,0}, ..., T_{i, j_{\text{stop}}-1}$ need to be computed; tiles $T_{i, j_{\text{stop}}}$ onward can be skipped.

This generalizes FlashAttention's causal logic. In the dense triangular case, $j_{\text{stop}} = i+1$ (we need to compute tiles up to and including the diagonal block), and the index-based condition reduces precisely to this because `max(qidx_i) < min(kidx_{i+1})` always holds when indices are the identity mapping $0, 1, 2, ..., T-1$. But when queries and keys have been dropped, the index mapping is no longer the identity, and $j_{\text{stop}}$ can be anywhere — later than $i+1$ if many keys were dropped (keys from distant positions are packed into earlier blocks), or earlier than $i+1$ if many queries were dropped (query blocks contain positions from further ahead in the sequence).

**Three-level causal masking within computed tiles.** For tiles that are computed ($j < j_{\text{stop}}$), the kernel applies a local causal mask by comparing the per-element indices:

$$M_{\text{local}}[p, q] = \begin{cases} 0 & \text{if } \text{qidx}_i[p] \geq \text{kidx}_j[q] \\ -\infty & \text{if } \text{qidx}_i[p] < \text{kidx}_j[q] \end{cases}$$

This is a standard lower-triangular mask but computed using the original sequence positions rather than the compact positions. The kernel then adds this mask to the dot-product scores $Q_i K_j^\top$ before the softmax, same as FlashAttention does for the diagonal block in the dense case.

**Handling stranded queries.** A crucial edge case arises when the compact tensor includes padding. For heads with fewer kept elements than `buffer_size`, the padded queries have `q_idx` values of -1 (the sentinel). These queries have no valid keys — the pad index is less than all real key indices, but there are no real queries at position -1, and these padded positions should produce zero output vectors. The standard FlashAttention implementation would produce NaN values for a query that has no valid keys (softmax over an empty set, or equivalently softmax over a vector where all entries are $-\infty$). The paper modifies the softmax statistics accumulation (Algorithm 3, described in detail below) to handle this by treating running maximum values of $-\infty$ as 0 in the scaling computations and replacing $\infty$ in the reciprocal of the sum with 1.0, which causes these queries to produce zero vectors.

**The backward pass** follows the same principle but in reverse. For a given query block $Q_i$, the backward pass needs to iterate over the same key blocks that were used in the forward pass. The kernel uses the same `j_stop` determination to restrict the backward computation to only the relevant tiles.

**Overhead analysis.** The pre-processing cost is dominated by the stable sort along the sequence dimension, which costs $O(T \log T)$ per head, and the gather/scatter operations, which cost $O(T \times D)$ memory bandwidth. This is linear in sequence length, unlike the quadratic attention cost. For short sequences, this linear overhead can dominate the quadratic savings, creating a break-even sparsity threshold. For long sequences, the tradeoff flips: the paper shows (Figure 7b) that at 32k tokens, even 20% sparsity (keeping 80% of queries and keys) provides a visible speedup over FlashAttention, because the $O(T^2)$ savings from a 20% reduction in $T$ (which gives a 36% reduction in attention FLOPs, since $(0.8T)^2 = 0.64 T^2$) outweigh the $O(T)$ sorting cost.

#### The Hash-Sparse Kernel: Block-Diagonal Sparsity with Irregular Causal Masking

The Hash-sparse method (Section 3.2) addresses the case where attention is restricted to keys and queries that share the same hash bucket. The motivation comes from the observation that in softmax attention, the keys with the largest dot products dominate the output — if you can quickly identify which keys are likely to have large dot products with each query, you can dramatically reduce computation with minimal accuracy loss. Locality-sensitive hashing (LSH) does this by assigning nearby vectors (in angular distance) to the same hash bucket with high probability.

**Pre-processing: sorting by hash bucket.** The pre-processing pipeline (Listing 3 in Appendix B.2) takes hash assignments `q_hash` and `k_hash` (integer bucket indices, shaped $B \times T \times H$) and:

1. Stably sorts the queries, keys, and values along the sequence dimension according to their hash bucket indices. "Stable" means that within each bucket, the original temporal order is preserved. This is essential: without stability, the causal structure within a bucket would be scrambled, and the index-based masking would not correctly enforce causality.

2. Records the sorting indices: `q_idx` and `k_idx` store, for each position in the sorted tensor, the original sequence position. These are the monotonic index arrays used by the kernel.

3. Records the hash values of the sorted elements: `q_hash_sorted` and `k_hash_sorted` are the bucket indices for each position in the sorted tensors.

**The resulting tensor structure.** After sorting, all queries with hash bucket $h$ appear contiguously, followed by all queries with bucket $h+1$, and so on. The same holds for keys. Because the same hash function is used for both, queries in bucket $h$ will have their matching keys also somewhere in the contiguous block for bucket $h$ (though these blocks are at different positions in the query and key tensors, because the numbers of queries and keys per bucket differ). This creates a block-diagonal structure in the attention matrix: the dot products that matter are concentrated in block-shaped sub-regions where both query and key have the same hash.

**The kernel modification: finding both `j_start` and `j_stop`.** Algorithm 2 (Appendix B.1) shows that the Hash-sparse kernel must determine both where to start and where to stop processing key blocks for a given query block. The kernel has access to `qhash_i` (hash values for queries in the current block), `khash_j` (hash values for keys in block $j$), `qidx_i`, and `kidx_j`.

**First pass: hash-based range.** The kernel scans over all key hash blocks and determines `start` and `endhash`:

- `start` is incremented for every key block $j$ where `max(khash_j) < min(qhash_i)` — that is, where all keys in the block have hash values strictly smaller than the smallest hash value among the queries. These blocks cannot contain any key-query pairs with matching hashes, so they are skipped from the left.
- `endhash` is the first key block where `min(khash_j) > max(qhash_i)` — where all keys have hash values strictly larger than the largest query hash value. Blocks beyond this point cannot have matching hashes.

This gives a coarse range `[start, endhash)` of key blocks that could potentially contain matching hashes. Within this range, some blocks may still have no matching hashes (e.g., a key block with hash values [2, 2, 2] while the query block has hash values [1, 1, 3, 3] — there is no overlap, but the block is inside the broad range). This is fine — these blocks will be computed but will have all dot products masked out, which is correct but slightly wasteful.

**Second pass: index-based refinement.** The kernel then scans within `[start, endhash)` to refine the end point based on the original position indices:

- `end` is updated to the last block $j$ where `min(kidx_j) <= max(qidx_i)` — that is, where there is at least one key that is not strictly in the future relative to all queries in the block.

The final processing range is `[start, end)`. This ensures we never compute tiles that are entirely beyond the causal horizon (all keys are future keys for all queries in the block).

**Dual per-tile masking.** Within each computed tile $T_{i,j}$, the kernel applies two masks simultaneously:

$$M_{\text{combined}}[p, q] = \begin{cases} 0 & \text{if } (\text{qidx}_i[p] \geq \text{kidx}_j[q]) \text{ AND } (\text{qhash}_i[p] = \text{kidx}_j[q]) \\ -\infty & \text{otherwise} \end{cases}$$

The first condition enforces causality (query must come at or after the key in the original sequence). The second condition enforces hash matching (query and key must be in the same bucket). Both must hold for the dot product to be included in the softmax. This is a more restrictive mask than the QK-sparse case, but the mechanism is the same: the mask is applied to the dot-product scores before softmax, and elements with $-\infty$ mask are effectively zero-weighted.

This masking enables the "serendipity" mentioned in the paper: within a computed tile, attention is restricted to same-hash pairs, but the tile is computed because the hash ranges overlap — we don't pre-filter at a finer granularity than the tile. This avoids expensive per-element hash comparison in the tile selection logic (which would require iterating over all keys individually) while still enforcing exact hash matching at the computation level.

**Base case: this generalizes QK-sparse.** If all hash values are set to 0 (a single universal bucket), the hash masking is always satisfied, and the `start`/`endhash` range becomes `[0, T]` — the entire key sequence. The hash-sparse kernel then reduces to the QK-sparse kernel with no elements dropped, which in turn reduces to standard causal FlashAttention. This nesting demonstrates that the hash-sparse kernel is a strict generalization.

**Forward pass pseudocode walkthrough (Algorithm 2).** For each query block at position `start_m`:
1. Load $B_m$ query vectors, their original indices `qidx`, and their hash values `qhash` into SRAM.
2. Scan all key blocks to find `start` (first block with hash overlap) and `endhash` (last block with hash overlap).
3. Within `[start, endhash)`, scan again to find `end` (last block where temporal overlap is possible, using indices).
4. For key blocks `j = start` to `end - 1`: load key block, value block, indices, and hashes; compute tile $Q_i K_j^\top$; apply combined causal+hash mask; update online softmax statistics; accumulate output contribution.
5. Write the result for this query block back to HBM.

The backward pass finds the range of query blocks that could have contributed to each key-value block and performs the reverse computation, following the standard FlashAttention backward algorithm but restricted to the dynamically determined tile ranges.

**Coverage guarantee.** Unlike the Reformer's chunked implementation, SCFA's Hash-sparse kernel processes all key blocks whose hash range overlaps with the query block's hash range. This means every key-query pair with matching hash buckets and valid causality is guaranteed to be computed. The paper quantifies this in Figure 4b: SCFA maintains 100% coverage at all sequence lengths, while the Reformer's coverage drops from approximately 85% at 10k tokens to around 62% at 60k tokens. This coverage gap explains the perplexity difference observed in Table 5.

#### Online Softmax Statistics with Irregular Masking and NaN Handling

The softmax accumulation algorithm used by SCFA is a direct adaptation of FlashAttention's online softmax, but must handle queries that have no valid keys (all dot products masked to $-\infty$). The standard algorithm is presented in Section 3.2 of Dao et al. (2022); SCFA modifies the final normalization step to avoid NaN propagation.

**Standard online softmax recap.** For a single query, we want to compute:

$$\text{softmax}(s) = \frac{e^{s - \max(s)}}{\sum_j e^{s_j - \max(s)}}$$

where $s \in \mathbb{R}^{T_{KV}}$ is the vector of attention scores (dot products plus causal mask). The online algorithm maintains three running vectors across key blocks: $m \in \mathbb{R}^{B_m}$ (current maximum score per query), $\ell \in \mathbb{R}^{B_m}$ (current sum of exponentials per query), and $o \in \mathbb{R}^{B_m \times d}$ (current output accumulation per query). When a new key block arrives with scores $s_{\text{new}} \in \mathbb{R}^{B_m \times B_n}$:

$$m_{\text{new}} = \max(m_{\text{old}}, \text{rowmax}(s_{\text{new}}))$$
$$\ell_{\text{new}} = e^{m_{\text{old}} - m_{\text{new}}} \odot \ell_{\text{old}} + \text{rowsum}(e^{s_{\text{new}} - m_{\text{new}}})$$
$$o_{\text{new}} = \text{diag}\left(\frac{\ell_{\text{old}}}{\ell_{\text{new}}}\right) o_{\text{old}} + \text{diag}\left(\frac{1}{\ell_{\text{new}}}\right) \left(e^{s_{\text{new}} - m_{\text{new}}}\right) V_{\text{new}}$$

where $\odot$ is element-wise multiplication and all operations on $m$ and $\ell$ are per-query (broadcast appropriately). The key insight is that $\ell$ and $o$ can be updated incrementally without ever storing the full $e^{s}$ matrix.

**Why standard accumulation fails for stranded queries.** A stranded query is one where every key has been masked out — $s_{\text{new}}$ contains all $-\infty$ entries in every row corresponding to that query. In this case, $\text{rowmax}(s_{\text{new}}) = -\infty$ for those queries. If $m_{\text{old}}$ was initialized to $-\infty$, then $m_{\text{new}} = \max(-\infty, -\infty) = -\infty$. The computation $e^{m_{\text{old}} - m_{\text{new}}} = e^{-\infty + \infty}$ is undefined and produces NaN. Similarly, $\text{rowsum}(e^{s_{\text{new}} - m_{\text{new}}})$ involves $e^{-\infty + \infty}$ which is NaN. Even if $m_{\text{new}}$ is computed correctly, the final normalization involves $\frac{1}{\ell_{\text{new}}}$ where $\ell_{\text{new}} = 0$ for the stranded query, producing $\infty$.

**SCFA's NaN-avoidance mechanism (Algorithm 3 in Appendix B.1).** The fix has three parts:

1. **Replace $-\infty$ maxima with 0 during scaling.** After computing $m_{\text{new}} = \max(m_{\text{old}}, \text{rowmax}(s_{\text{new}}))$, the kernel computes $\hat{m}_{\text{new}}$ where any $-\infty$ entries are replaced with 0:

```
m_new_hat = WHERE(m_new == -inf, 0, m_new)
```

The exponential $p = e^{s_{\text{new}} - \hat{m}_{\text{new}}}$ then uses $\hat{m}_{\text{new}}$ instead of $m_{\text{new}}$. For stranded queries where $s_{\text{new}}$ and $\hat{m}_{\text{new}}$ are both 0, this gives $p = e^{0 - 0} = 1$ for all key positions in the block — which is numerically well-defined but results in uniform weights. This is corrected in the next step.

2. **Handle zero sum during normalization.** The old sum is rescaled: $\ell_{\text{new}} = e^{m_{\text{old}} - \hat{m}_{\text{new}}} \odot \ell_{\text{old}} + \text{rowsum}(p)$. For stranded queries, $\ell_{\text{old}} = 0$ (no previous keys either), so $\ell_{\text{new}} = 0 + B_n = B_n$ (assuming the block has $B_n$ keys, all receiving weight 1.0 from step 1). The kernel then computes $z = 1 / \ell_{\text{new}}$, but any $\ell_{\text{new}} = 0$ entries are replaced with 1.0:

```
z = WHERE(z == inf, 1, z)
```

This ensures that division by zero is avoided. The per-element weight multiplication $p \leftarrow p \times z$ then gives $p = 1 \times 1 = 1$ for all keys in the block, and the output correction $o \leftarrow o \times (\ell \times z)$ similarly multiplies the old output (which was zero) by a finite factor.

3. **Implicitly, stranded queries accumulate zero output.** Over the entire sequence, a stranded query accumulates contributions proportional to $1/B_n$ from each key block, but these are later offset by the correction factor in step 2. The net result: the query's accumulated $\ell$ value grows with each block, but the output $o$ remains exactly zero because all dot products are $-\infty$-masked and the exponential $e^{-\infty} = 0$ — the edge case handling only affects the *normalization constants*, not the actual weighted sum. The final output for a stranded query is a zero vector, which is the desired behavior (a query that can attend to nothing produces no output).

This fix is not mathematically deep but is essential for correctness. Without it, any batch containing a head where some queries have fewer kept keys than the buffer size (or all keys mapped to different hash buckets) would produce NaN values that would propagate through the network, causing training to diverge.

**Block size and performance considerations.** The paper uses block sizes $B_m$ and $B_n$ of 128 (standard for Triton implementations). The choice of block size affects the tradeoff between SRAM usage and tile efficiency. Larger blocks use more SRAM but process more dot products per tile, reducing the number of iterations and the overhead of the per-tile logic (hash checking, index scanning). For the Hash-sparse method, if the sequence length is small relative to the block size, most tiles will contain multiple hash buckets, reducing effective sparsity — the kernel computes many dot products that end up masked out. This explains why the Hash-sparse method shows significant speedup only for longer sequences (Figure 3): at short sequences, the tile-level granularity is too coarse to capture the hash-based sparsity effectively.

#### Pre-Processing Pipelines: Cost, Amortization, and Design Rationale

The speed of SCFA in practice depends on the net effect of two competing costs: the $O(T \log T)$ or $O(T)$ pre-processing overhead versus the quadratic savings in attention computation. The paper provides detailed Python listings of exactly what operations constitute this overhead, enabling analysis of when SCFA is beneficial.

**QK-sparse pre-processing (Listing 4, Appendix B.2).** The `compact` function performs these operations for a tensor $X$ of shape $B \times T \times H \times D$:

1. **Counting kept elements:** `indices_per_head = keep_tensor.sum(dim=-2)` sums the keep/drop mask (floats 0.0/1.0) along the sequence dimension, giving a $B \times H$ tensor of how many keys/queries are kept per head. This is $O(T \times H \times B)$ work but is a simple sum, well-optimized on GPU.

2. **Buffer sizing:** `buffer_size = indices_per_head.max().int()` finds the maximum across all heads and batch elements. This determines the size of the compact tensor — all heads are padded to this uniform size, which is necessary for batched GPU processing (ragged tensors would require dynamic shapes that are inefficient on GPU).

3. **Stable sort to group kept elements:** `sorted = keep_tensor.sort(dim=-2, descending=True, stable=True)` is the most expensive step. The sort is $O(T \log T)$ per head, and for a transformer with $H$ heads, this is $O(H \times T \log T)$ overall — still linear in $T$ up to the log factor, which is negligible compared to the $O(T^2)$ attention cost for large $T$.

4. **Gathering kept elements:** `compact_x = x.gather(dim=-3, index=index.unsqueeze(-1).expand(-1, -1, -1, D))` gathers from the original tensor the elements at the sorted indices, writing them to the compact tensor. This is $O(T \times D)$ memory bandwidth — each element is read and written once.

5. **Index array padding:** The `pad_index` function (Listing 4) fills unused positions in the index array with sentinel values (-1 for queries, `1e9` for keys). The sentinels are chosen so that padded queries (index -1) are correctly identified as having no matching keys (since all real key indices are $\geq 0 > -1$), and padded keys (index `1e9`) are correctly ignored (since all real queries have indices $\leq T-1 \ll 10^9$).

**Hash-sparse pre-processing (Listing 3, Appendix B.2).** The pre-processing for hash-based sparsity involves:

1. **Stable sort by hash bucket:** Both query and key hash tensors are stably sorted along the sequence dimension. This costs $O(T \log T)$ per head, same as the QK case but with the additional overhead of sorting two tensors (queries and keys) and broadcasting the sort indices to values.

2. **Extending sort indices:** `q_idx_extended = q_idx.unsqueeze(-1).expand_as(q)` broadcasts the index tensor to match the query tensor dimensions, costing $O(T \times D)$ memory.

3. **Gather by index:** `q = torch.gather(q, dim=-2, index=q_idx_extended)` reorders the queries to match the sorted hash order. This is $O(T \times D)$ memory bandwidth.

4. **No compaction:** Unlike QK-sparse, the Hash-sparse method does not reduce the sequence length — it only permutes it. The tensors remain size $T \times D$, and the sparsity comes from skipping tiles, not from computing on a smaller matrix. This means the attention computation itself is still $O(T^2)$ in the worst case (if all items hash to the same bucket), but the constant factor is reduced by the fraction of tiles that can be skipped.

**Why the overhead is acceptable for long sequences: an analytical argument.** The attention computation (in FLOPs) is approximately $2 \times T_Q \times T_{KV} \times d$ for the dot products plus $3 \times T_Q \times T_{KV}$ for the softmax (exponential, sum, normalization). For $T_Q = T_{KV} = T$, this is roughly $2 T^2 d$ FLOPs. The pre-processing is approximately $c_1 T \log T + c_2 T d$ operations, where $c_1$ and $c_2$ are hardware-dependent constants. For large $T$, $T^2$ dominates $T \log T$ and $T d$ regardless of the constant factors — there exists some $T_0$ beyond which any reduction in the $T^2$ term, even a modest one, outweighs the pre-processing cost.

The paper's experiments (Figure 7b) confirm this empirically. At $T = 4096$, 20% QK-dropping barely breaks even (the curve cross the FlashAttention baseline). At $T = 32768$, 20% QK-dropping provides a clear speedup (the SCFA curve is well below the baseline). The break-even moves to lower sparsity levels as $T$ grows because the $T^2$ savings grow faster than the $T \log T$ overhead.

**Transposition overhead.** Both methods also require transposing the Q, K, V tensors from the standard PyTorch shape $(B, T, H, D)$ to the kernel-friendly shape $(B, H, T, D)$ and back. The paper accounts for this in its timing measurements (the baseline FlashAttention implementation in Listing 1 also performs these transpositions), making the comparison fair. The transposition is $O(T \times H \times D)$ memory bandwidth, which is linear in $T$ and small relative to the attention cost for long sequences.

#### The Sparsity Decision Mechanism: What SCFA Expects and What the Prototypes Provide

SCFA is sparsity-pattern-agnostic: it expects two arrays specifying which key-query interactions to compute, and it processes whatever pattern those arrays define. The paper provides two simple prototype sparsity controllers to validate the kernel, while explicitly stating that better controllers are possible.

**Prototype 1: Uniform random hashing (for Hash-sparse).** The hash-based language model (H-LM) uses the same LSH procedure as the Reformer. Specifically, the paper states (Section 4.2):

> "we adopt the same hashing procedure as Kitaev et al. (2020). Namely, we use a shared query-key space, and we disallow queries to attend to themselves. We also adopt the LSH scheme from Andoni et al. (2015). This allows us to pick the number of unique hash codes."

In practice, this means that for each head, the keys and queries are first normalized (to make the LSH effective for angular distance), then random hyperplane projections are applied to generate hash codes. The number of buckets $n_b$ is a hyperparameter — the paper sweeps values $n_b \in \{2, 4, 8, 16, 32, 64\}$ in the runtime benchmarks and uses $n_b = 16$ for language modeling experiments. Importantly, queries and keys share the same hash function (shared query-key space), which means $Q = K$ (or rather, the keys are normalized versions of the queries). This reduces the attention to self-attention within each bucket.

The restriction that "queries cannot attend to themselves" is implemented by using `>` instead of `>=` in the causal mask comparison. This prevents a token from incorporating its own information through the attention mechanism, forcing it to rely on context.

**Prototype 2: Uniform random dropping (for QK-sparse).** The dropping language model (D-LM) simply drops each key/query head independently with probability $s$:

> "We show that naively dropping heads for each key and query at random can already yield competitive results while significantly improving the runtime."

The paper experiments with sparsity ratios $s \in \{0.3, 0.5, 0.7\}$ (probability of dropping), meaning the fraction kept is $(1-s)$. The dropping decision is per-head and per-position — two different sequences in a batch can have completely different dropping patterns, and within a single sequence, some heads might have most queries kept while others have few. This is the "very dynamic" behavior the paper highlights (Figure 8 caption: "two sequences are allowed to have completely different dropping patterns").

**Why these simple prototypes are sufficient for validation.** The paper's goal is not to achieve state-of-the-art sparsification but to demonstrate that the kernel provides speedup for realistic dynamic patterns. The critical findings (Figures 6, 8) are that even random dropping at 30% matches FlashAttention in perplexity while training 1.9× faster at sequence length 8192, and that hash-based sparsity with 16 buckets matches FlashAttention perplexity while training 2.0–3.3× faster. These results validate the core claim: with SCFA, dynamic sparsity can be practically faster than dense computation, removing the implementation barrier that previously made such methods uncompetitive.

Better sparsity controllers — learned importance scores, attention-based pruning, reinforcement learning for dropping decisions — would likely improve the perplexity-vs-speed tradeoff beyond what the random prototypes achieve. The paper explicitly invites this follow-up research in the Conclusion: "We hope that our contribution will inspire the community to research dynamic attention patterns in a way that is less constrained by a tight computational budget."

#### The Edge Case: Empty Attention Windows and Gradient Correctness

A subtle correctness issue arises when a query has zero valid keys within its hash bucket or after QK-dropping. In standard attention, a query always has at least itself as a key (in self-attention), so the softmax sum is never zero. In SCFA, a query might be the only element in its hash bucket, and if self-attention is disallowed (`>` masking), it has zero valid keys. Similarly, in QK-sparse, a kept query might have all its neighboring keys dropped.

**Forward pass behavior.** The kernel must produce a well-defined output (zero vector) for such queries. The NaN-avoidance mechanism in Algorithm 3 ensures this by converting what would be an undefined $\frac{0}{0}$ normalization into a zero output. The paper states: "We solve this issue by modifying how softmax statistics are accumulated during the forward and backward passes and ensure stranded queries default to 0 vectors" (Section 3.1).

**Backward pass implications.** For a zero-output query, the gradient with respect to the query should be zero (since changing the query vector would not affect the output if there are no keys to attend to), and the gradient with respect to the (non-existent) keys should also be zero. The modified backward pass handles this by recognizing that the softmax denominator is zero for these queries and setting gradients appropriately. This is a necessary correctness property — without it, training would produce non-zero gradients for queries that contribute nothing to the output, leading to parameter drift or instability.

The paper does not provide the backward pass pseudocode explicitly, but states (Appendix B.1): "The backward pass relies exactly on the same trick, we first iterate over query indices to find the starting block of queries." For the QK-sparse case, this means the backward pass scans query blocks to find which ones could have contributed to each key-value block, using the same `j_stop` logic in reverse. For the Hash-sparse case, the backward pass uses the `start`/`end` ranges symmetrically. The softmax gradient computation is adapted to handle the $\ell = 0$ case in the same manner as the forward pass (Algorithm 3), preventing division by zero.

#### Integration with the Transformer Training Pipeline

The paper integrates SCFA into a standard autoregressive transformer training loop. The attention module is swapped (FlashAttention for baselines, SCFA variants for experiments), but all other components remain identical. This is an important experimental design choice: it isolates the effect of the attention mechanism, ensuring that speedups and perplexity differences can be attributed to the kernel change rather than to architectural differences.

**Shared query-key space.** The paper follows the Reformer's design choice of setting keys equal to normalized queries ("we set the keys equal to normalized queries for all of our models," Section 4.1). This is necessary for locality-sensitive hashing, which relies on the query and key vectors being in the same space for the hashing to be meaningful. In a standard transformer, $Q$ and $K$ are produced by separate linear projections from the input, so they need not be equal. The paper modifies the model architecture to make $K = \text{normalize}(Q)$, which means the keys are a normalized version of the queries rather than an independently learned projection. This reduces the model's expressivity slightly (one fewer learned projection matrix) but is required for the hashing to work. The paper notes that the baseline (F-LM) models also use this shared $Q=K$ design, making the comparison fair — the speedup is not achieved by giving the baseline a less expressive architecture.

**Language modeling hyperparameters.** The models are 12-layer transformers with hidden size 768, 12 heads of dimension 64 each, resulting in approximately 122M parameters. Training uses the AdamW optimizer with weight decay 0.1, learning rate 0.001, cosine schedule with 2% warmup, batch sizes of 96 (for $T=8192$) and 30 (for $T=16384$) achieved through gradient accumulation and data parallelism over 2-3 A100 GPUs. Training runs for 15k iterations (or 50k in the extended experiments of Figure 16). The tokenizer is GPT-2's, and the dataset is OpenWebText2.

**What the speedup numbers actually measure.** The paper reports "iterations per minute on 1 GPU" as the speed metric. This is computed by measuring total training time (including pre-processing, attention, feed-forward, optimizer steps, and communication) and normalizing by the number of GPUs. The reported 2.0× speedup for H-LM at $T=8192$ means that the entire training loop — not just the attention component — runs twice as fast. This is a stronger result than reporting attention-only speedup, because it accounts for Amdahl's law: even if attention is perfectly accelerated, the overall training speedup is limited by the non-attention components (feed-forward networks, layer norm, optimizer). The fact that the overall training loop achieves 2.0–3.3× speedup implies that attention dominates the runtime at these sequence lengths, consistent with Figure 9.

**Curious observation: H-LM speeds up during training.** Appendix C (Figure 14a) notes that hash-based models accelerate during early training. The paper interprets this as evidence that the hash buckets become more balanced as training progresses — initially, the LSH projections are random, and some buckets may receive more elements than others, reducing effective sparsity. As the model learns meaningful representations, the keys and queries distribute more uniformly across buckets, increasing the fraction of tiles that can be skipped. This is a nice example of learned sparsity emerging naturally from the training process, rather than being imposed as a fixed schedule.

## 4. Key Insights and Innovations

### Innovation 1: The Kernel Is the Enabler — Not the Sparsity Pattern Itself

The paper's most distinctive contribution is not a new sparsity scheme for attention but rather the **removal of a hardware-imposed constraint that was silently blocking an entire research direction**. This is a systems-for-ML innovation in its purest form: the authors identify a specific, well-defined gap in the GPU kernel landscape — the absence of an IO-aware, tiled attention kernel that can handle dynamic, irregular causal masking — and fill it with SCFA. The intellectual move is diagnostic: rather than asking "what new attention pattern can we invent?", they ask "why have promising dynamic patterns (Reformer's LSH, token/head pruning) failed to deliver practical speedups?" The answer — FlashAttention's hardcoded assumption of a perfectly triangular causal mask — is subtle enough that many researchers working with sparse attention had likely experienced the frustration without pinpointing its root cause.

This framing sets SCFA apart from the efficient transformer literature surveyed in Section 2 and Appendix A. Prior work falls largely into two camps. One camp proposes new sparsity patterns (Child et al., 2019; Zaheer et al., 2020; Beltagy et al., 2020; Kitaev et al., 2020) — algorithmic innovations that reduce theoretical complexity but struggle with implementation. The other camp develops new attention mechanisms that are inherently linear (Katharopoulos et al., 2020; Choromanski et al., 2020; Peng et al., 2021) — mathematical innovations that change what is computed, trading expressivity for speed. SCFA belongs to neither camp. It changes neither the sparsity pattern (the prototypes use existing ideas — LSH from the Reformer, random dropping) nor the attention mechanism (it computes exact softmax, not an approximation). Instead, it changes the **computational substrate** — the kernel that maps the abstract pattern onto GPU hardware — and in doing so, makes a whole class of previously impractical patterns suddenly viable.

The significance of this contribution is evidenced by the paper's most striking negative result: Figure 7a, where a naive PyTorch implementation of QK-dropping (compacting tensors plus `scaled_dot_product_attention` with a custom mask) requires *more than 70% sparsity* before it even breaks even with dense FlashAttention. Below that threshold, the irregular mask forces a fallback to a slower code path, and the overhead of mask materialization and non-IO-aware computation erases all savings from computing fewer dot products. This result isn't just a systems curiosity — it explains why years of research on dynamic token and head pruning had produced papers with theoretical speedups but few deployed models. The implication for practitioners is clear: **if you design a dynamic sparsity method without a kernel that can efficiently execute it, you are almost certainly making your model slower, not faster**. SCFA flips that dynamic: with it, even 20% random dropping (keeping 80% of computation) provides a net speedup at long sequence lengths (Figure 7b).

The paper's open-source implementation in Triton (Tillet et al., 2019) is integral to this contribution. By using a high-level language that compiles to CUDA, the authors make their kernel accessible to researchers who lack the expertise to write raw CUDA. The explicit `dynamic_sparse_attention` interface (Listing 2 in Appendix B.2) — accepting query and key tensors plus index/hash arrays and a `sparsity_mode` flag — abstracts away the kernel complexity, allowing future work to plug in arbitrary sparsity controllers without touching the CUDA-level code. This is a deliberate act of infrastructure-building, not just a proof-of-concept.

### Innovation 2: Index-Tracking Arrays as a Generalization of FlashAttention's Causal Logic

The second insight is conceptual: SCFA demonstrates that FlashAttention's block-index-based causal masking (skip tile if query block index < key block index) can be **generalized to arbitrary monotonic index structures** by replacing block index comparison with per-tile maximum/minimum checks on arrays of original position indices. This is not a deep mathematical contribution — the comparison `max(qidx_i) < min(kidx_j)` is structurally the same operation as `i < j` — but it is a powerful systems insight because it expands the space of computable attention patterns without sacrificing the memory efficiency that makes FlashAttention fast.

To appreciate what this generalization unlocks, consider the prior state. FlashAttention's causal logic was baked into its control flow: the loop over key blocks was implicitly bounded by `j <= i`. This meant that the kernel could only process patterns where the "computation front" was a straight diagonal line in the attention matrix — the standard causal triangle. Any pattern requiring non-contiguous key accesses (gaps, blocks, or reordering) could not be expressed within this loop structure. Practitioners who needed such patterns had three poor options: (1) write a custom CUDA kernel from scratch (prohibitively difficult for most ML researchers), (2) fall back to a generic PyTorch implementation that materialized the mask (slow, as Figure 7a shows), or (3) approximate their desired pattern with something FlashAttention could handle (as the Reformer did with its fixed-size chunks, sacrificing coverage — Figure 4b).

SCFA's index-tracking approach breaks this logjam by separating the **computation pattern** (which tiles to process) from the **data layout** (how queries and keys are ordered in memory). The kernel doesn't assume that block index equals temporal position; it reads the actual position indices from the auxiliary arrays and decides tile-by-tile, using the same kind of comparison FlashAttention uses block-by-block. This is a clean conceptual move: it takes the efficiency of FlashAttention's tiled skipping (amortizing the decision cost over a whole tile of $B_m \times B_n$ dot products) and applies it to arbitrary monotonic permutations and compactions of the sequence.

The power of this generalization is demonstrated by its nesting property (implicit in the paper's architecture): if you set all hash values to 0 and don't drop any keys or queries, the Hash-sparse kernel reduces exactly to the QK-sparse kernel, which reduces exactly to standard causal FlashAttention. This isn't a trivial observation — it means SCFA is a **strict superset** of FlashAttention's causal capabilities, with zero overhead when no sparsity is applied (the `j_stop` scan over index blocks would find `j_stop = i+1` and the per-tile masks would be identical). The backward compatibility is important because it means practitioners can adopt SCFA as a drop-in replacement for FlashAttention, with the option to activate sparsity when beneficial, without worrying about correctness in the dense case.

The hash-sparse kernel extends this further by adding a second layer of tile filtering: hash-based range finding (`start`, `endhash`) followed by index-based refinement (`end`). The two-stage process (Algorithms 2 in Appendix B.1) is a specific instance of a more general principle: **arbitrary tile-skipping predicates can be implemented by pre-scanning the key block metadata**, as long as the predicate can be evaluated on the metadata without loading the full key/value tensors from HBM. This opens the door to future kernels that filter tiles based on learned importance scores, attention-based gating, or structural priors — anything that can be expressed as a per-key-block attribute check.

### Innovation 3: Dynamic Sparsity Is Practically Viable Only with Sufficient Coarse-Graining

The paper's experiments yield a finding that, while not framed as a formal theorem, constitutes a significant practical insight: **dynamic sparse attention only translates algorithmic FLOP reduction into wall-clock speedup when the sparsity pattern is coarse-grained enough to amortize the pre-processing overhead against the quadratic attention savings**. This is an empirical discovery about the GPU hardware-computation interface, not about attention mechanisms per se, and it has implications for how future sparse attention methods should be designed.

The evidence for this insight comes from the detailed runtime decompositions in Figures 3, 7, 10, and 11, which show forward and backward pass times separately across sparsity levels and sequence lengths. The key pattern is the **break-even curve**: at short sequence lengths (roughly below 4k tokens), even substantial sparsity (50-70% QK-dropping) fails to beat FlashAttention because the linear pre-processing cost (sorting, gathering, padding) dominates. As sequence length grows, the break-even sparsity threshold drops — at 32k tokens, even 20% sparsity provides a speedup (Figure 7b). This is exactly the behavior one would expect if the pre-processing is $O(T)$ and the attention is $O(T^2)$: there exists a critical $T$ beyond which any reduction in the quadratic term, however small as a percentage, outweighs the linear overhead.

But the insight goes deeper than this asymptotic argument. The paper shows that **how** sparsity is structured matters for its GPU efficiency. The QK-sparse method reduces the effective sequence length (compacting $T$ to $(1-s)T$), which means the attention computation itself runs on smaller tensors — a direct reduction in both FLOPs and memory bandwidth. The Hash-sparse method keeps the sequence length at $T$ but skips tiles — a reduction in FLOPs but not in the tensor dimensions. The two methods thus have different scaling properties, and the paper's data shows that QK-sparse achieves break-even at lower sparsity levels than Hash-sparse for a given sequence length (compare the 20% curve in Figure 11a with the $n_b = 2$ curve in Figure 10a — QK-sparse with 20% dropping (80% kept) is faster than FlashAttention at ~20k tokens, while Hash-sparse with 2 buckets (which should give roughly 50% sparsity if hashes are balanced) breaks even at a similar point). This suggests that **reducing tensor dimensions is more GPU-efficient than skipping tiles within full-size tensors**, likely because the reduced memory footprint improves cache utilization and reduces the number of blocks processed.

The coarse-graining insight also explains the limitations of the Reformer's implementation. The Reformer used fixed-size chunks and allowed attention only within the current and neighboring chunk — a coarse but rigid sparsification. SCFA's Hash-sparse kernel, by contrast, uses tile-level granularity (blocks of $B_n = 128$ keys) to decide which regions to compute. This is coarser than per-element hash checking (which would require loading individual key vectors to check their hashes) but finer than the Reformer's chunk approach (which forces all elements in a chunk to be computed even if many don't share the query's hash). The tile granularity hits a sweet spot: it's coarse enough that the per-tile decision cost is amortized over 128 key-query dot products, but fine enough that hash-based sparsity actually reduces the number of computed tiles when buckets are small.

For future algorithm designers, this insight provides a design constraint: **proposed sparsity patterns should be block-structured at a granularity of at least tens of elements per block** to be efficiently executable by SCFA-like kernels. Finer-grained sparsity (individual key-query pair dropping) may reduce FLOPs but will likely fail to translate to speedup because the decision overhead per element erases the savings. This is not articulated as a hard rule in the paper, but it follows directly from the experimental scaling behavior.

### Innovation 4: Verifier Over-Optimization at the Hardware Level — Why Naive Masked Attention Slows You Down

While the paper's primary contribution is constructive (building SCFA), it also provides a valuable **diagnostic result** that reframes how the community understands the gap between algorithmic complexity and actual runtime for attention. The Figure 7a experiment — showing that a PyTorch-native implementation of dynamic sparsity using `scaled_dot_product_attention` with a custom causal mask requires >70% sparsity to outperform dense FlashAttention — is a miniature negative-result paper in itself. It demonstrates that the standard fallback for irregular masks in PyTorch is catastrophically slow relative to IO-aware implementations, and it provides quantitative evidence for a phenomenon many practitioners have suspected: **dynamic sparsity, implemented naively, is worse than useless — it's actively harmful to throughput**.

This finding has a direct parallel to the concept of "verifier over-optimization" seen in the RLHF and test-time compute literature, but applied at the hardware level. In both cases, optimizing too aggressively against an imperfect proxy (the verifier's score; the GPU's mask-application path) leads to worse outcomes than not optimizing at all. For attention masks, the proxy is the generic masked-softmax implementation that PyTorch uses when the mask is not perfectly triangular. This implementation does not benefit from FlashAttention's tiling and IO-awareness, meaning it materializes intermediate tensors in HBM that FlashAttention keeps in SRAM, and it likely computes dot products for masked-out positions before zeroing them — wasteful both in FLOPs and memory bandwidth.

The diagnostic value of Figure 7a is that it quantifies the **hidden tax** on dynamic sparsity. Someone reading a paper that proposes a clever token-dropping scheme might see "we drop 30% of tokens, reducing attention FLOPs by ~50%" and assume a ~2× speedup. The Figure 7a result shows that, with standard tools, dropping 30% of tokens actually *increases* runtime by roughly 50–100% at sequence lengths above 1k tokens. This is not a failure of the sparsity idea — it's a failure of the implementation substrate. By quantifying this gap, the paper makes a compelling case that the kernel infrastructure is the bottleneck, not the algorithms, and that SCFA (or something like it) is a necessary precondition for dynamic sparse attention to be practical.

This negative result also explains the curious trajectory of the Reformer: despite being an influential paper, its LSH attention was not widely adopted in deployed models, and many follow-up works abandoned hashing entirely in favor of static sparse patterns or linearized attention. The Figure 4a and Figure 7a results suggest that this was not because LSH is a bad idea, but because the Reformer's chunk-based GPU implementation (necessary due to the lack of a flexible kernel) was both approximate (missing hash collisions) and not as fast as it could be. SCFA's Hash-sparse kernel demonstrates that LSH attention, when implemented with an appropriate kernel, can simultaneously achieve 100% coverage (Figure 4b) and outperform FlashAttention at practical sequence lengths (Figures 3, 6). This rehabilitates a research direction that was prematurely abandoned due to systems limitations rather than algorithmic deficiencies.

The broader implication is that **the field's evaluation of sparse attention methods has been systematically biased by implementation quality**. A method paired with a well-optimized kernel (like FlashAttention for dense patterns) will appear far more competitive than an equally clever method forced to use a generic implementation path. This means that negative results on dynamic sparsity — papers showing that certain pruning or hashing schemes "don't work" in practice — should be re-examined with the understanding that the failure may be in the kernel, not the algorithm. SCFA provides the tool to conduct this re-examination properly.

## 5. Experimental Analysis

### Evaluation Methodology

**Datasets.** The paper evaluates hash-based sparsity on three datasets: MNIST (LeCun et al., 1998) for autoregressive image generation (predicting pixels as a sequence), enwik8 (Hutter, 2012) for character-level language modeling, and OpenWebText2 (Gao et al., 2020) for word-level language modeling. QK-dropping sparsity is evaluated only on OpenWebText2. No custom data splits are created; standard dataset boundaries are used.

**Base model.** All language modeling experiments on OpenWebText2 use a 12-layer autoregressive transformer with hidden size 768, 12 attention heads of dimension 64 each, resulting in approximately 122M parameters (Section 4.1). The model is deliberately kept modest in scale — the goal is not state-of-the-art perplexity but rather demonstrating that SCFA enables speedup without accuracy degradation at a representative model scale. For comparisons with the Reformer (Kitaev et al., 2020) on MNIST and enwik8, smaller variants are used: 8 transformer blocks with hidden dimension 256 for MNIST, and 12 blocks with 768 hidden dimensions and 8 heads for enwik8.

**Metrics.** Three classes of metrics are reported:
- **Wall-clock speed**: measured as iterations per minute on 1 GPU, normalized by the number of GPUs used in data-parallel training (Section 4.1). This captures end-to-end training throughput including pre-processing, attention, feed-forward, and communication. For kernel-only benchmarks, forward and backward pass times in milliseconds are measured in isolation.
- **Model quality**: validation perplexity for language models, bits per character (bpc) for enwik8, and perplexity for pixel prediction on MNIST.
- **Coverage** (for hash-based methods): the fraction of key-query pairs with matching hash buckets that are actually computed in the attention operation. This measures how much of the theoretically desirable computation is captured by the implementation.

**Baselines.** The paper compares against:
- **FlashAttention (F-LM)**: the standard `torch.nn.functional.scaled_dot_product_attention` with `is_causal=True`, which uses the FlashAttention kernel from Dao et al. (2022) for dense causal attention. This is the primary baseline — all speedup claims are relative to this.
- **Naive PyTorch implementation** of sparse attention: for QK-sparse, this means compacting tensors (removing dropped elements) and then calling `scaled_dot_product_attention` with a custom causal mask. For Hash-sparse, this means reordering tensors by bucket and computing the full attention matrix with a mask applied. Both fall back to a non-FlashAttention code path.
- **Reformer attention** (Kitaev et al., 2020): for hash-based experiments only. The Reformer's LSH attention with fixed-size chunks, compared against SCFA's Hash-sparse kernel on both speed (Figure 4a) and coverage (Figure 4b).

**Compute accounting.** For kernel-only benchmarks (Figures 3, 4, 7, 10, 11, 12), the unit of measurement is milliseconds for the forward pass, backward pass, or combined forward+backward, at a given sequence length and sparsity configuration. Pre-processing (sorting, compacting, transposing) is explicitly included in the timing, as shown in the Python listings in Appendix B.2. For some analyses, separate timing with pre-processing assumed free is also provided (Figure 12) to isolate the kernel contribution. For end-to-end training experiments (Figures 6, 8), the metric is iterations per minute per GPU, which captures total training loop time. All timing experiments use NVIDIA A100 GPUs with bfloat16 precision.

**Model configuration for fair comparison.** A critical design choice: all models, including the FlashAttention baseline, use a shared query-key space where keys are set equal to normalized queries (Section 4.1). This is required for the LSH hashing to be meaningful (queries and keys must be in the same space), and the paper applies this constraint uniformly to ensure the baseline is not disadvantaged by having a more expressive architecture. The hash-based language model (H-LM) uses the same LSH procedure as the Reformer: random hyperplane projections to generate hash codes, with queries disallowed from attending to themselves (Section 4.2). The dropping language model (D-LM) uses independent random dropping per head per position at fixed probability $s$.

### Main Quantitative Results

#### Hash-Sparse Attention: Kernel Benchmarks (Figures 3, 4, 10)

The kernel-level benchmarking establishes the raw performance characteristics of SCFA's Hash-sparse implementation before integration into a full training pipeline.

**Headline result (Figure 3).** At sequence length 32,768, the Hash-sparse kernel with $n_b = 64$ buckets completes forward+backward in approximately 350 ms, compared to roughly 1,200 ms for FlashAttention over the full sequence — a speedup of approximately 3.4×. The naive hash-sparse implementation (reordering tensors, computing full masked attention) shows runtime independent of the number of buckets and significantly worse than FlashAttention at all tested sequence lengths, taking approximately 1,400 ms at 32k regardless of $n_b$. This confirms the central diagnostic: without a kernel that skips tiles based on hash metadata, hash-based sparsity provides no speed benefit and is actually slower than dense computation.

The scaling behavior with number of buckets $n_b$ is monotonic but sublinear in benefit. Examining Figure 3:
- At $n_b = 2$, the Hash-sparse kernel is slightly *slower* than FlashAttention at all sequence lengths below ~20k tokens. The cross-over occurs around 24k tokens.
- At $n_b = 4$, the break-even is around 12k tokens. At 32k tokens, speedup over FlashAttention is approximately 1.5×.
- At $n_b = 16$, break-even occurs around 6k tokens. At 32k tokens, speedup is approximately 2.3×.
- At $n_b = 64$, break-even occurs around 3k tokens. At 32k tokens, speedup is approximately 3.4×.

The diminishing returns from increasing $n_b$ are visible: doubling from 2 to 4 buckets provides a large jump, but doubling from 32 to 64 provides a smaller incremental gain. This is expected because the average bucket size shrinks as $T / n_b$, and the per-tile overhead of hash checking becomes a larger fraction of the work when buckets are small. The inset in Figure 3 zooms in on short sequences (0–4000 tokens), showing that even at $n_b = 64$, the Hash-sparse kernel underperforms FlashAttention below ~3k tokens due to the pre-processing overhead dominating.

**Forward vs. backward asymmetry (Figure 10).** The paper provides separate forward and backward timing breakdowns. At 32k tokens with $n_b = 64$, the forward pass takes approximately 80 ms (vs. ~270 ms for FlashAttention, a 3.4× speedup), while the backward pass takes approximately 270 ms (vs. ~530 ms, a 2.0× speedup). The backward pass benefits less from sparsity because it requires recomputing attention scores from the saved softmax statistics, and the gradient computation involves additional operations that don't benefit from tile skipping to the same degree.

**Coverage comparison with Reformer (Figure 4b).** The Reformer's chunk-based LSH attention shows coverage declining with sequence length: approximately 85% at 10k tokens, dropping to roughly 62% at 60k tokens. SCFA's Hash-sparse kernel maintains 100% coverage at all sequence lengths — every key-query pair that shares a hash bucket and satisfies causality is computed. This is the direct consequence of the kernel's ability to process all tiles where hash ranges overlap, rather than being forced into fixed-size chunks. On the speed axis (Figure 4a), SCFA's Hash-sparse is faster than the Reformer across all sequence lengths for $n_b = 16$, with the gap widening at longer sequences (the Reformer curve grows roughly linearly with sequence length, while SCFA's grows more slowly due to effective sparsity).

#### Hash-Sparse Attention: Language Modeling on OpenWebText2 (Figures 6, 15, 16)

The end-to-end training experiments test whether kernel-level speedups translate into actual training throughput improvements without accuracy degradation.

**Headline result (Figure 6).** Comparing H-LM (Hash-sparse with $n_b = 16$) against F-LM (FlashAttention baseline) on OpenWebText2:

| Sequence length | F-LM speed (iter/min/GPU) | H-LM speed (iter/min/GPU) | Speedup | Perplexity match? |
|---|---|---|---|---|
| 8,192 | ~5.0 | ~10.0 | 2.0× | Yes (within noise) |
| 16,384 | ~1.6 | ~5.3 | 3.3× | Yes (slightly better) |

The speedup numbers come from the bar chart in Figure 6c, where the F-LM bar reaches approximately 5 iter/min at 8k and 1.6 iter/min at 16k, while H-LM reaches approximately 10 and 5.3 respectively.

**Perplexity vs. iterations (Figure 6a).** The validation perplexity curves for H-LM and F-LM are nearly overlapping at both sequence lengths. At 8k tokens, H-LM reaches approximately perplexity 30 at 15k iterations compared to F-LM's approximately 30.5 — a slight advantage. At 16k tokens, H-LM reaches approximately 35 at 15k iterations compared to F-LM's approximately 37, a clearer advantage. The paper does not provide error bars or multiple seeds for these curves (though Figure 16 shows 2-seed averaging for the 50k-iteration experiments), so it is unclear whether these differences are statistically significant. However, the key claim — that H-LM "does not sacrifice perplexity" — is supported: the curves are qualitatively close.

**Perplexity vs. wall-clock time (Figure 6b).** The x-axis shift between the F-LM and H-LM curves is dramatic. F-LM at 8k takes approximately 90 hours to reach perplexity 30, while H-LM reaches the same perplexity in approximately 50 hours — a 1.8× reduction in time-to-quality. At 16k, F-LM takes approximately 150 hours to reach perplexity 35, while H-LM reaches it in approximately 55 hours — a 2.7× reduction. This is the paper's most practically meaningful result: for a fixed training budget, H-LM achieves substantially better perplexity, or equivalently, achieves the same perplexity substantially faster.

**Effect of number of buckets (Figure 15).** For $T = 8192$, the training speed is:
- F-LM: ~5.0 iter/min/GPU
- H-LM with $n_b = 8$: ~9.0 iter/min/GPU (1.8×)
- H-LM with $n_b = 16$: ~10.0 iter/min/GPU (2.0×)
- H-LM with $n_b = 32$: ~10.5 iter/min/GPU (2.1×)

The diminishing returns with increasing $n_b$ observed in kernel benchmarks (Figure 3) persist in end-to-end training. Doubling from 8 to 16 buckets gives a 1.11× incremental speedup; doubling from 16 to 32 gives 1.05×. For $T = 16384$, the pattern is similar: $n_b = 8$ gives 2.6×, $n_b = 16$ gives 3.3×, $n_b = 32$ gives 3.6×.

**Longer training runs (Figure 16).** To verify that the speedup is not an artifact of early training dynamics, the paper trains H-LM and F-LM for 50k iterations at $T = 8192$ with $n_b \in \{8, 16\}$. The results, averaged over two seeds:
- H-LM with $n_b = 8$: approximately 1.4× faster than F-LM (down from 1.8× at 15k iterations — this discrepancy is not explained in the paper, but likely reflects the speedup stabilizing as hash bucket distributions converge)
- H-LM with $n_b = 16$: approximately 1.8× faster than F-LM (down from 2.0× at 15k iterations)
- Perplexity at 50k iterations: F-LM reaches ~18.5, H-LM ($n_b = 8$) reaches ~18.5, H-LM ($n_b = 16$) reaches ~18.3 — both H-LM variants match or slightly outperform the baseline.

The reduction in speedup from 15k to 50k iterations (2.0× → 1.8× for $n_b = 16$) is consistent with the observation in Appendix C that H-LM models speed up during early training (Figure 14a) — the speedup is larger early on and then stabilizes.

**Self-speedup during training (Figure 14a).** The paper shows a plot of iterations vs. wall-clock time (normalized per GPU) comparing F-LM and H-LM at 8k tokens with $n_b \in \{8, 16, 32\}$. The H-LM curves show a slight positive curvature (iterations accumulate faster as training progresses), while the F-LM curve is nearly linear. At $n_b = 32$, the H-LM reaches 15k iterations in approximately 25 hours, compared to F-LM's approximately 50 hours. The speedup is attributed to hash bucket distributions becoming more balanced as the model learns meaningful representations, increasing the effective sparsity.

#### QK-Dropping Attention: Kernel Benchmarks (Figures 7, 11)

**Headline result (Figure 7b).** The QK-sparse kernel provides speedup over FlashAttention for a wide range of sparsity levels and sequence lengths, with the break-even point depending on both factors.

At sequence length 32,768:
- 20% dropping (80% kept): approximately 620 ms vs. 1,200 ms (1.9× speedup)
- 30% dropping (70% kept): approximately 520 ms (2.3×)
- 40% dropping (60% kept): approximately 430 ms (2.8×)
- 50% dropping (50% kept): approximately 350 ms (3.4×)
- 70% dropping (30% kept): approximately 220 ms (5.5×)
- 80% dropping (20% kept): approximately 150 ms (8.0×)

The break-even sequence length (where the QK-sparse curve crosses the FlashAttention curve) depends on sparsity:
- 20% dropping: break-even at approximately 5k tokens
- 30% dropping: break-even at approximately 3k tokens
- 40% dropping: break-even at approximately 2.5k tokens
- 50% dropping: break-even at approximately 2k tokens
- 70% dropping: break-even at approximately 1.5k tokens
- 80% dropping: break-even at approximately 1k tokens

Below 1k tokens, the QK-sparse kernel is always slower than FlashAttention, regardless of sparsity — the pre-processing cost of compacting and reordering tensors dominates for short sequences.

**Comparison with naive implementation (Figure 7a).** This is the paper's most important negative result. The naive PyTorch implementation (compacting tensors, then `scaled_dot_product_attention` with custom mask) shows:
- At 50% dropping: *slower* than FlashAttention at all sequence lengths up to 4k (the maximum tested in Figure 7a), approximately 1.5× slower at 4k tokens.
- At 70% dropping: roughly equal to FlashAttention at 4k tokens, slower at shorter lengths.
- At 80% dropping: approximately 1.5× faster than FlashAttention at 4k tokens.

The naive implementation only provides a speedup when dropping more than 70% of keys and queries. This quantifies the hidden tax that SCFA eliminates: the generic masked attention path is so inefficient that it erases all savings from reduced FLOPs until the sparsity is extreme.

**Forward vs. backward breakdown (Figure 11).** Similar to the hash-sparse case, the forward pass benefits more from sparsity than the backward pass. At 32k tokens with 50% dropping, the forward pass takes approximately 120 ms (vs. ~270 ms for FlashAttention, a 2.3× speedup) while the backward pass takes approximately 230 ms (vs. ~530 ms, a 2.3× speedup). The ratios are more symmetric than in the hash case, likely because QK-sparse reduces the tensor dimensions directly, which benefits forward and backward symmetrically.

**Ablation with free pre-processing (Figure 12a).** When pre-processing cost is excluded, the break-even for the QK-sparse kernel shifts to shorter sequences: even at 1k tokens, 20% dropping provides a slight speedup. The offset between the "with preprocessing" and "without preprocessing" curves is approximately 15–20 ms at short sequences, representing the linear cost of sorting and compacting.

**Headline result (Figure 8).** Comparing D-LM (QK-dropping with various sparsity ratios) against F-LM (FlashAttention) on OpenWebText2 at $T = 8192$:

| Model | Sparsity ($s$) | Speed (iter/min/GPU) | Speedup vs. F-LM | Final perplexity (~15k iter) |
|---|---|---|---|---|
| F-LM | 0% | ~5.0 | 1.0× | ~30.5 |
| D-LM | 30% | ~9.5 | 1.9× | ~31 (slightly worse) |
| D-LM | 50% | ~13.0 | 2.6× | ~33 |
| D-LM | 70% | ~17.5 | 3.5× | ~37 |

The speedups are substantial, but perplexity degrades monotonically with sparsity. The 30% dropping model is the sweet spot: it nearly matches F-LM perplexity (31 vs. 30.5) while training 1.9× faster.

**Perplexity vs. iterations (Figure 8a).** The D-LM curves show clear separation by sparsity level. The 30% dropping curve tracks F-LM closely through training, finishing within approximately 0.5 perplexity points. The 50% dropping curve diverges mildly (finishing approximately 2.5 points worse). The 70% dropping curve diverges significantly (finishing approximately 6.5 points worse). This is expected: random dropping of 70% of heads means the model is essentially training with heavily restricted attention, which limits its capacity to learn long-range dependencies.

**Perplexity vs. wall-clock time (Figure 8b).** The time-to-quality tradeoff is more nuanced:
- To reach perplexity 35: F-LM takes approximately 35 hours, D-LM ($s = 30\%$) takes approximately 18 hours, D-LM ($s = 50\%$) takes approximately 14 hours, D-LM ($s = 70\%$) takes approximately 10 hours.
- However, D-LM ($s = 70\%$) plateaus at a higher perplexity (~37), so it never reaches the quality of the lower-sparsity models regardless of time.
- D-LM ($s = 50\%$) reaches perplexity 33 in approximately 30 hours, while F-LM reaches 33 in approximately 25 hours — so despite the 2.6× per-iteration speedup, the quality gap means D-LM is not actually faster to a target perplexity below 33.
- D-LM ($s = 30\%$) reaches perplexity 31 in approximately 25 hours, while F-LM takes approximately 40 hours — a genuine 1.6× speedup in time-to-quality.

**Curriculum dropping experiment (Figure 13).** The paper explores a simple curriculum: start training with 80% dropping and linearly decay the dropping probability to 20% over the course of training (model labeled "D-LM s = 80% → 20%"). The hypothesis is that early training benefits from high sparsity (learning coarse features), while later training benefits from denser attention (learning fine-grained dependencies). Results:
- Speed: approximately 7.5 iter/min/GPU (1.5× vs. F-LM) — slower than fixed 50% dropping (2.6×) because the sparsity decreases over time.
- Perplexity: approximately 30 at 15k iterations — matching F-LM and slightly better than fixed 30% dropping.
- Time-to-perplexity-31: approximately 30 hours — faster than F-LM (40 hours) but slower than fixed 30% dropping (25 hours), because the model slows down as training progresses (Figure 14b shows the curriculum model's speed decreasing during training, unlike fixed-sparsity models which maintain constant speed).

This is a promising direction but not clearly superior to the simpler fixed 30% dropping — the perplexity improvement is marginal, and the total time-to-quality is worse. The paper includes this result as a proof-of-concept rather than a recommendation.

### Ablation Studies and Robustness Checks

**Number of hash buckets ($n_b$) for H-LM**: The training speedup scales sublinearly with $n_b$. At $T = 8192$, $n_b = 8$ gives 1.8× speedup, $n_b = 16$ gives 2.0×, and $n_b = 32$ gives 2.1× (Figure 15). The diminishing returns are consistent with the kernel benchmarks (Figure 3), where the per-tile overhead of hash checking increases as buckets shrink. The paper uses $n_b = 16$ as the default for H-LM experiments, representing a practical balance between speedup and hash quality (too many buckets means each bucket contains very few tokens, limiting the model's ability to capture long-range dependencies that span multiple hash codes).

**Fixed vs. curriculum dropping for D-LM**: Fixed 30% random dropping matches F-LM perplexity while training 1.9× faster. Fixed 50% dropping degrades perplexity by approximately 2.5 points but trains 2.6× faster. A curriculum that decays sparsity from 80% to 20% achieves perplexity comparable to fixed 30% dropping but is slower (1.5× speedup) because sparsity decreases during training (Figure 13). The curriculum approach shows that dynamic sparsity schedules are possible with SCFA — the kernel handles changing sparsity patterns per iteration without modification — but the specific linear decay schedule tested does not improve upon a well-tuned fixed rate.

**Sequence length scaling**: The speedup of both Hash-sparse and QK-sparse methods improves with sequence length. For H-LM ($n_b = 16$), the speedup increases from 2.0× at 8k to 3.3× at 16k tokens (Figure 6c). For QK-sparse at 50% dropping, the speedup over FlashAttention increases approximately linearly with log sequence length: from ~1.1× at 4k to ~3.4× at 32k (Figure 7b). This is the expected behavior when an $O(T \log T)$ or $O(T)$ overhead is amortized against $O(T^2)$ savings.

**Training duration**: The 50k-iteration experiments (Figure 16) confirm that H-LM speedups persist through longer training. The speedup for $n_b = 16$ stabilizes at approximately 1.8× (down from 2.0× at 15k iterations), and perplexity continues to match or slightly exceed F-LM. This addresses the concern that early-training speedups might not be representative of full training runs.

**Pre-processing cost isolation**: Figure 12 shows kernel timing when pre-processing is excluded. For QK-sparse, the break-even sequence length drops significantly — even at 1k tokens, low sparsity levels provide speedup without the sorting/gathering overhead. For Hash-sparse, the offset is smaller because the hash-sparse method does not reduce tensor dimensions; the tile-skipping benefit is inherently coarser. This ablation clarifies how much of the short-sequence slowdown is due to pre-processing vs. kernel inefficiency.

**Naive implementation comparison**: Figure 7a serves as both a baseline comparison and an ablation demonstrating the necessity of SCFA. The naive PyTorch approach — which is what most researchers would implement if they wanted to test a dynamic sparsity idea — is catastrophically slower than FlashAttention unless sparsity exceeds 70%. This result is robust across sequence lengths and sparsity levels, and it constitutes the paper's empirical justification for building SCFA in the first place.

**Training speed stability**: For fixed-sparsity D-LM models, speed remains constant throughout training (Figure 14b). For H-LM models, speed increases during early training (Figure 14a) as hash bucket distributions become more balanced, then stabilizes. The curriculum D-LM model slows down during training as sparsity decreases (Figure 14b). These dynamics confirm that SCFA's speed is data-dependent — sparsity patterns that distribute elements evenly across buckets or keep fractions yield better speedups — but the effects are predictable and stable after an initial transient.

**Shared Q=K space**: All models use a shared query-key space where keys equal normalized queries (Section 4.1). This is a confounding factor: the baseline F-LM could potentially perform better (lower perplexity) with independent Q and K projections. However, since the research question is about the speed-perplexity tradeoff of attention sparsity, the paper rightly applies this constraint to all models, making the comparison internally valid. The absolute perplexity numbers should not be compared to models with standard Q/K projections.

### Critical Assessment

#### Claim 1 (from Executive Summary): SCFA "delivers training speedups of 2.0× and 3.3× for sequences of respectively 8k and 16k tokens without sacrificing perplexity."

**What the experiments demonstrate**: This claim is supported for the Hash-sparse method (H-LM) with $n_b = 16$ buckets on OpenWebText2 at a single model scale (122M parameters). The speedup numbers are directly measured from end-to-end training (Figure 6c): 2.0× at 8k, 3.3× at 16k. The "without sacrificing perplexity" is supported by Figure 6a, where H-LM and F-LM validation perplexity curves nearly overlap, with H-LM slightly ahead at both sequence lengths (perplexity ~30 vs. ~30.5 at 8k, ~35 vs. ~37 at 16k after 15k iterations).

**What the experiments do not demonstrate**: 
- **Model scale robustness**: All experiments use a single model size (122M parameters). It is unknown whether the speedup scales with model size — larger models have different ratios of attention to feed-forward computation, which would affect Amdahl's Law limits on overall training speedup. A larger model with more feed-forward parameters relative to attention might see smaller overall speedups even if attention is perfectly accelerated.
- **Longer training convergence**: The 15k-iteration experiments (Figures 6, 8) show perplexity still decreasing at termination. The 50k-iteration extension (Figure 16) confirms the trend holds, but the speedup decreases from 2.0× to 1.8×. It is unclear whether this decrease would continue asymptotically — the paper does not train long enough to establish a stable asymptotic speedup.
- **Dataset diversity**: OpenWebText2 is a single web-text corpus. It is unknown whether the hash bucket distribution remains balanced on other corpora (code, scientific text, multilingual) — if hashing produces highly imbalanced buckets on certain data distributions, the speedup could be substantially less. The MNIST and enwik8 results (Table 5) provide some cross-domain evidence, but these use different architectures and are not directly comparable to the language modeling speedup claims.
- **Statistical significance**: The paper reports single training runs for most experiments (Figure 16 is averaged over two seeds, but Figures 6 and 8 appear to be single runs). Narrow perplexity gaps (e.g., H-LM vs. F-LM at 8k, ~30 vs. ~30.5 at 15k iterations) could be within the noise of different random initializations. The claim of "no perplexity sacrifice" would be stronger with multiple seeds and confidence intervals.

#### Claim 2: "Even with relatively low degrees of sparsity, our method improves visibly upon FlashAttention as the sequence length increases."

**What the experiments demonstrate**: For QK-dropping, this is strongly supported by Figure 7b. At 32k tokens, 20% dropping (80% kept) provides approximately 1.9× speedup. At 20k tokens, the same sparsity level provides approximately 1.3×. The break-even is around 5k tokens. The paper shows that the speedup threshold decreases as sequence length grows, exactly as predicted by the $O(T^2)$ attention cost vs. $O(T \log T)$ overhead argument.

For Hash-sparse, this claim is less strongly supported at "relatively low degrees of sparsity." Two hash buckets ($n_b = 2$) provides approximately 50% sparsity in expectation (if hashes are balanced), and Figure 3 shows this configuration breaks even with FlashAttention only around 20k tokens — not "visible improvement" at moderate sequence lengths. The claim is more comfortably true for moderate $n_b$ values (8–16) at sequences above 8k tokens.

**Missing evidence**: The paper does not systematically vary sparsity level for Hash-sparse in the language modeling experiments — only $n_b \in \{8, 16, 32\}$ is tested at 8k and 16k tokens (Figure 15). Testing $n_b = 4$ or $n_b = 64$ would help establish the practical range where hash sparsity provides net benefit without degrading perplexity. At $n_b = 64$, the average bucket size at 8k tokens is only 125 tokens — whether this provides sufficient context for language modeling is an open question.

#### Claim 3: The Hash-sparse kernel is faster than the Reformer and maintains 100% collision coverage.

**What the experiments demonstrate**: Figure 4a shows SCFA Hash-sparse is faster than the Reformer across all sequence lengths tested (up to ~65k tokens) at matched bucket sizes. Figure 4b shows 100% coverage for SCFA versus declining coverage (85% → 62%) for the Reformer as sequence length grows from 10k to 60k tokens. Table 5 shows better perplexity on MNIST and enwik8 with matched bucket sizes. These results are internally consistent and well-supported within the tested range.

**What is missing**: The Reformer comparison uses random inputs for the coverage and speed benchmarks, not actual training runs. The MNIST and enwik8 comparisons use training runs but at much smaller scale than the OpenWebText2 experiments. There is no head-to-head H-LM vs. Reformer training run on OpenWebText2 at the 122M parameter / 8k–16k token scale that would most directly validate the practical superiority claim. The coverage argument (Figure 4b) is compelling but indirect — we must infer that coverage loss causes the perplexity gap in Table 5, without a direct causal experiment varying coverage while holding other factors constant.

#### Genuine Weaknesses and Missing Experiments

**Single model scale and architecture**: All OpenWebText2 experiments use a 12-layer, 768-hidden, 12-head, ~122M-parameter transformer. This is a single point in a large design space. Larger models (more layers, wider hidden dimension, more heads) would have different attention-to-feed-forward ratios, potentially different hash behavior, and potentially different sparsity tolerance. The paper's speedup claims cannot be safely extrapolated to the billion-parameter scale without additional experiments.

**Single GPU architecture**: All timing is on NVIDIA A100 GPUs. The speedup depends on the memory hierarchy (HBM bandwidth, SRAM size, compute throughput) which varies across GPU generations and vendors. SCFA's tile size choices (128) and the balance of pre-processing to attention cost could shift on different hardware (e.g., H100 with larger SRAM, or consumer GPUs with different bandwidth ratios).

**No perplexity-vs-speed Pareto frontier**: The paper presents individual speedup points (H-LM at $n_b = 16$, D-LM at various sparsities) but does not systematically sweep the speed-perplexity tradeoff. A Pareto frontier plot showing multiple $n_b$ values, multiple QK sparsity ratios, and the FlashAttention baseline all on the same axes would be more informative than the separate Figures 6 and 8. It would directly answer: "what is the best perplexity I can achieve at 2× training speedup, and what method achieves it?"

**Hash quality not analyzed**: The paper uses the Reformer's LSH procedure unchanged but does not analyze the quality of the hash buckets during training — how balanced are they? What fraction of the true top-k attention scores fall within the same bucket? A diagnostic experiment measuring "attention recall" (what fraction of the top-k attention weights from dense attention are captured within the hash buckets) would help explain why H-LM matches F-LM perplexity — is it because the hash buckets genuinely capture the important key-query pairs, or because the model adapts its representations to make the hashing work?

**No combination of methods**: The paper studies Hash-sparse and QK-sparse independently but never combines them. A natural extension — use hashing to identify candidate key-query pairs, then drop low-importance ones within each bucket — could achieve higher sparsity with less perplexity degradation. The paper's architecture supports this combination (the interface in Listing 2 could accept both hash and keep/drop arrays simultaneously), but no combined experiments are reported.

**QK-dropping perplexity degradation not analyzed**: The paper reports that 30% dropping matches F-LM perplexity while 50% and 70% degrade it, but provides no analysis of *why* perplexity degrades. Is it because certain heads are more important than others and random dropping occasionally removes them? Is it because some sequence positions (e.g., rare tokens, long-range dependencies) require attention more than others? An importance-weighted dropping scheme (dropping low-norm or low-attention-entropy heads) would be an obvious improvement, and its absence makes the D-LM results feel preliminary.

**Training cost of sparsity decision**: For QK-dropping, the keep/drop decisions are random and cost essentially zero to generate. For Hash-sparse, the paper states it uses the Reformer's LSH procedure but does not include the cost of computing hash codes in the pre-processing timing. The LSH requires additional linear projections (random hyperplanes) and sign computations, which add FLOPs not present in the baseline. If these hash computations are included in the pre-processing overhead measured in Figures 3 and 10, they are accounted for; if not, the speedup is overstated. The paper's Appendix B.2 code listings show that `q_hash` and `k_hash` are inputs to the `dynamic_sparse_attention` function, implying hash computation happens outside the timed region. This is a significant accounting ambiguity.

## 6. Limitations and Trade-offs

### Single Model Scale and Architecture: Speedup Claims Are Untested Beyond 122M Parameters

**The assumption or constraint.** All end-to-end training experiments on OpenWebText2 use a single model configuration: 12 layers, hidden size 768, 12 attention heads, approximately 122M parameters (Section 4.1). The paper makes no claim that these speedups generalize to other model scales, but the absence of multi-scale experiments means the headline numbers (2.0× at 8k, 3.3× at 16k) are point estimates at one point in a large design space. The authors acknowledge the modest scale indirectly: "The goal not being to outperform the state-of-the-art perplexity, we train for 15k iterations" (Section 4.1).

**The consequence.** The overall training speedup depends on the fraction of total runtime consumed by attention, which varies with model architecture. A wider model (larger hidden size relative to sequence length) spends proportionally more time in feed-forward networks, which are unaffected by SCFA. Amdahl's Law imposes a ceiling: if attention accounts for 75% of runtime at 122M parameters and 16k tokens (Figure 9), then even infinite acceleration of attention can at most yield a 4× overall speedup; the 3.3× achieved at 16k already approaches this ceiling. At larger model scales where feed-forward dominates more (e.g., models with hidden size 2048 or 4096 at similar sequence lengths), the achievable overall speedup would be proportionally smaller. Conversely, at longer sequences where attention dominates more heavily, speedups might exceed 3.3×. The paper provides no framework for predicting speedup at arbitrary (model size, sequence length) combinations.

**What evidence exists in the paper.** Figure 9 (Appendix C) decomposes transformer runtime into attention and feed-forward components as a function of sequence length for the 122M model. At 16k tokens, attention accounts for approximately 75% of total runtime — this single data point bounds the maximum possible speedup but does not show how the ratio changes with model width, depth, or number of heads. The kernel-level benchmarks (Figures 3, 7) are independent of model scale (they measure attention operation time only), but the translation from attention-level speedup to end-to-end speedup is model-dependent and untested beyond the single configuration.

**Mitigation status.** Not addressed. The paper does not discuss model-scale dependence, does not experiment with different architectures, and does not provide a model for extrapolating speedups. A practitioner deploying SCFA at billion-parameter scale would need to measure the attention-to-feed-forward ratio of their specific model to estimate expected gains.

---

### Difficulty Estimation Cost Is Not Accounted for in Headline Speedups

**The assumption or constraint.** Both sparse attention methods require pre-processing that transforms the query, key, and value tensors before the attention kernel runs: stable sorting by hash bucket for Hash-sparse, and stable sorting plus compaction for QK-sparse (Section 3.1, 3.2; Appendices B.2 Listings 3 and 4). The paper explicitly includes these operations in kernel-level timing benchmarks (Figures 3, 7), but the cost of *computing* the sparsity decisions themselves — the hash codes for Hash-sparse, the keep/drop decisions for QK-sparse — is treated as external to the timed region. The `dynamic_sparse_attention` interface (Listing 2, Appendix B.2) accepts `q_idx` and `k_idx` arrays as inputs, meaning the caller is responsible for producing them. For the random dropping baseline in the QK-sparse experiments, this cost is negligible (sampling random masks). For the Hash-sparse experiments, however, computing LSH codes requires additional linear projections (random hyperplanes), dot products, and sign computations that scale with the sequence length, head dimension, and number of hash functions. The paper states it uses the hashing procedure from Kitaev et al. (2020) and Andoni et al. (2015) (Section 4.2) but does not specify how many hash functions are used, nor does it measure or report the FLOPs or wall-clock time for hash code computation.

**The consequence.** The reported speedups for H-LM (2.0× at 8k, 3.3× at 16k) may overstate the true end-to-end gain if hash code computation constitutes a non-trivial fraction of attention-layer cost. The LSH procedure involves: (1) normalizing query vectors, (2) multiplying by a random projection matrix, (3) taking signs, (4) converting binary codes to integer bucket indices. Step (2) in particular is a matrix multiplication of dimension $T \times d \times n_{\text{hashes}}$, where $n_{\text{hashes}}$ determines the number of buckets as $2^{n_{\text{hashes}}}$. For $n_b = 16$ buckets, $n_{\text{hashes}} = 4$; for $n_b = 64$, $n_{\text{hashes}} = 6$. This is a non-trivial computation (roughly $T \times d \times n_{\text{hashes}}$ multiply-adds per head) that is not captured in the reported timings. If hash computation takes even 5% of the attention time, the net speedup drops; at 15%, the advantage over FlashAttention could narrow substantially.

**What evidence exists in the paper.** The paper provides no measurement of hash computation cost. The pre-processing code in Listing 3 (Appendix B.2) shows the sorting and transposition steps but begins with `q_hash` and `k_hash` already as input tensors. The language modeling experiments (Section 4.2) state that "obtaining the buckets can be cheap and in no way prevents us from improving the attention runtime (see Fig. 6)," but Figure 6 shows end-to-end training speed where hash computation is presumably included in the per-iteration time. However, the statement is qualitative — no breakdown of hash cost vs. attention cost vs. other operations is provided. A practitioner cannot determine from the paper whether the LSH overhead is 1%, 5%, or 20% of the total attention-layer cost.

**Mitigation status.** The paper acknowledges this implicitly by providing the interface abstraction and stating that hash computation is "cheap," but provides no quantitative evidence. The end-to-end training speedups in Figure 6 are the best available evidence that the hash overhead is tolerable in practice, since the training loop includes hash computation. However, for a researcher trying to estimate whether H-LM would speed up a different model or dataset, the lack of cost decomposition makes prediction impossible.

---

### Single Hardware Platform: All Timings on NVIDIA A100 GPUs

**The assumption or constraint.** Every runtime measurement in the paper — kernel benchmarks (Figures 3, 4, 7, 10, 11, 12), end-to-end training (Figures 6, 8), and the Reformer comparison (Figure 4) — is collected on NVIDIA A100 GPUs using bfloat16 precision (Section 4.1, Appendix B.3). The paper makes no claims about other hardware and does not discuss hardware sensitivity.

**The consequence.** SCFA's performance depends critically on the GPU memory hierarchy: the tile size choices ($B_m = B_n = 128$, stated in Appendix B.1), the balance between SRAM capacity and HBM bandwidth, and the cost of the stable sort in pre-processing all vary across GPU generations and vendors. On an H100 (larger SRAM, higher bandwidth), larger tile sizes might be optimal, potentially improving speedup by reducing the fraction of time spent on per-tile index scanning overhead. On consumer GPUs with less SRAM and lower memory bandwidth, the pre-processing cost (which involves significant memory movement for sorting and gathering) would be proportionally more expensive relative to compute, potentially shifting the break-even points to longer sequences or higher sparsity. On non-NVIDIA hardware (AMD, Apple Silicon, custom accelerators), the Triton compiler may produce different code quality or be entirely unsupported, and the specific optimizations in SCFA (cooperative groups, shared memory usage patterns) may not have direct analogues. A practitioner targeting inference on edge devices or training on non-A100 clusters cannot safely extrapolate the reported speedups.

**What evidence exists in the paper.** None beyond the hardware specification. The paper does not include any multi-GPU ablation, does not vary tile sizes or block dimensions to show sensitivity, and does not discuss hardware portability. The Triton implementation is portable in principle (Triton compiles to multiple backends), but performance portability is not guaranteed and is not tested.

**Mitigation status.** Not addressed. The paper does not acknowledge hardware dependence as a limitation. The use of Triton rather than raw CUDA provides some degree of portability, but the paper does not claim or test performance on any non-A100 target. This is a standard limitation of GPU kernel papers and does not invalidate the A100 results, but it constrains the actionable scope of the speedup claims.

---

### QK-Dropping Perplexity Degradation Is Not Analyzed, and the Dropping Strategy Is Trivially Suboptimal

**The assumption or constraint.** The QK-dropping experiments (Section 4.3, Figures 8, 13) use **independent random dropping** of each query and key head with fixed probability $s$. The paper explicitly states this was chosen for simplicity, not optimality: "We show that naively dropping heads for each key and query at random can already yield competitive results while significantly improving the runtime. While better dropping schemes could be devised, they are outside of the scope of this work" (Section 4.3). The paper provides no analysis of why random dropping degrades perplexity (e.g., which heads, positions, or sequence regions are most affected), no comparison with an importance-weighted dropping baseline, and no investigation of whether the perplexity gap grows or shrinks with training duration.

**The consequence.** A practitioner using SCFA for QK-dropping would need to either accept the perplexity-vs-speed tradeoff of random dropping (which is worse than necessary) or develop a custom dropping strategy without guidance from the paper on what approaches are promising. The paper demonstrates that at 30% dropping, perplexity nearly matches the baseline, while at 50% and 70% dropping, perplexity degrades by approximately 2.5 and 6.5 points respectively (Figure 8a, ~15k iterations). However, the paper provides no insight into *why* perplexity degrades: is it because certain attention heads are uniformly more important and occasionally get dropped? Is it because long-range dependencies require attention from specific positions that happen to be dropped? Is it because rare tokens rely more heavily on attention context? An importance-based dropping scheme — for instance, retaining heads with higher attention entropy (suggesting they distribute weight across many positions and are harder to replace with local context) or higher output norm (suggesting they contribute more to the layer output) — would likely preserve perplexity at higher sparsity levels than random dropping. The paper's curriculum experiment (80% → 20% dropping, Figure 13) is a step in this direction but is more about scheduling than about per-token importance; it does not fundamentally address *which* queries and keys to drop.

**What evidence exists in the paper.** The paper demonstrates the speed-perplexity tradeoff (Figure 8) but provides no diagnostic experiments. There is no analysis of: (a) whether perplexity degradation is uniform across sequence positions or concentrated at long-range dependencies; (b) whether certain heads are dropped more frequently than others (they should be uniform in expectation, but per-batch variance matters); (c) whether the degradation changes over training (Figure 8a shows the gap emerging early and persisting); (d) how the degradation compares to simply reducing the number of attention heads (which would be a static version of head dropping). The absence of any structured alternative to random dropping makes the QK-sparse results feel like a proof-of-concept for the kernel rather than a validated method.

**Mitigation status.** The paper explicitly defers better dropping strategies to future work (Section 4.3). This is a reasonable scope limitation for a systems paper, but it means the QK-sparse results should be interpreted as a lower bound on what is achievable — a practitioner implementing a smarter dropping scheme would likely see better perplexity at the same speedup, or the same perplexity at higher speedup. The paper provides the kernel infrastructure (SCFA) to support arbitrary dropping schemes but does not develop or evaluate them.

---

### No Evaluation of Inference Latency or Autoregressive Decoding

**The assumption or constraint.** All experiments in the paper measure **training throughput** (iterations per minute, Section 4.1) or **kernel-level forward+backward time** (milliseconds per operation, Figures 3, 7). The paper does not evaluate the method in an inference setting, where autoregressive decoding generates one token at a time with a growing key-value cache. The Hash-sparse method requires re-sorting queries and keys by bucket after each new token is generated, and the QK-sparse method requires re-compacting the key-value cache as tokens are added. These operations have costs and latency characteristics that differ fundamentally from the training setting.

**The consequence.** A practitioner deploying an H-LM or D-LM model for text generation (the primary use case for autoregressive language models) cannot estimate inference latency from the paper's results. In autoregressive decoding, the key-value cache stores all previously generated tokens; for Hash-sparse, each new query must be hashed and matched against the appropriate key buckets, potentially requiring incremental re-sorting or bucket assignment that was batched and amortized in training. If the per-token pre-processing overhead is high, the method could provide training speedup but inference *slowdown* — faster training but slower generation would be a problematic tradeoff for applications where inference cost dominates (e.g., deployed chatbots, API services). Even if inference is faster in throughput (tokens per second with large batch), the latency for a single sequence could be worse due to the serial nature of pre-processing in the autoregressive loop.

**What evidence exists in the paper.** None. The paper does not mention inference, autoregressive decoding, or key-value caching. All kernel benchmarks use randomly initialized tensors of fixed size. All training experiments use teacher forcing (standard for language model training) where the full sequence is processed in parallel. This is a significant gap because the practical motivation for efficient attention includes both training cost and serving cost, and the two have different computational patterns.

**Mitigation status.** Not addressed. The paper's framing focuses on training efficiency (Section 1: "we increase the training speed of a transformer language model"; Section 4.1: training hyperparameters; Section 4.2–4.3: training throughput results). A reviewer or practitioner interested in inference would need to implement inference-specific adaptations of SCFA and benchmark them independently. The paper does not claim applicability to inference, but the omission is notable given that autoregressive generation is the primary downstream use case for language models.

---

### Dynamic Sparsity Patterns Are Not Combined or Compared Against Static Alternatives

**The assumption or constraint.** The paper studies Hash-sparse and QK-sparse as independent mechanisms and never combines them (e.g., hashing to identify candidate key-query pairs, then dropping low-importance ones within each bucket; or dropping entire heads and then hashing the remainder). It also does not compare against static sparsity patterns that FlashAttention already supports efficiently — specifically, block-sparse patterns (e.g., local windows combined with global tokens, as in BigBird or Longformer) that can be implemented within FlashAttention's existing `block_sparse` interface. The paper's comparison is exclusively against dense FlashAttention and the Reformer's approximate LSH implementation.

**The consequence.** A practitioner choosing a sparse attention method needs to decide among multiple options: static patterns (simple, fast, but potentially less expressive per layer), dynamic patterns (adaptive but with pre-processing overhead), or combinations. The paper demonstrates that dynamic sparsity *can* beat dense attention, but it does not demonstrate that it beats well-designed static sparsity at the same computational budget. For instance, a block-sparse pattern that restricts attention to a local window of 2,048 tokens plus a few global tokens might achieve similar or better perplexity than random hashing into 16 buckets at the same FLOP reduction, and would have lower pre-processing overhead (no sorting needed). The absence of this comparison means the paper's speedup claims are relative to a dense baseline, not to the best available sparse alternative — which is what a practitioner would actually compare against when deciding whether to adopt SCFA.

**What evidence exists in the paper.** The paper discusses static sparse patterns in the related work (Section 2, Appendix A.1) and acknowledges they exist, but the only head-to-head comparisons are against dense FlashAttention and the Reformer. There is no experiment where, for example, H-LM at $n_b = 16$ is compared against a local-window attention of equivalent FLOP budget, or where QK-dropping is compared against statically reducing the number of heads. The paper also states explicitly that PRM tree-search was not combined with revisions (Section 3.2: "we did not experiment with PRM tree-search techniques in combination with revisions"); while this quote refers to a different paper's limitation, the structural gap is analogous — two promising directions studied independently, with the combination unexplored.

**Mitigation status.** Not addressed. The paper's explicit scope is demonstrating that SCFA enables dynamic sparsity to be practically efficient, not that dynamic sparsity is better than static sparsity. However, the absence of static baselines weakens the practical recommendation: a systems practitioner reading this paper would want to know "should I adopt SCFA with hashing, or should I just use FlashAttention's existing block-sparse mode with a local window?" The paper provides no evidence to answer this question. The architecture (Listing 2, Appendix B.2) supports combining hash and QK-dropping signals simultaneously — the `dynamic_sparse_attention` interface could accept both hash and keep/drop arrays — but this capability is not tested.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

This paper is best understood not as proposing a new attention mechanism but as **removing a hardware-imposed constraint that was silently blocking an entire research direction**. The landscape shift is methodological rather than algorithmic: SCFA demonstrates that the gap between theoretical FLOP reduction and actual wall-clock speedup for dynamic sparse attention — a gap that had made this class of methods practically unusable — is not fundamental. It is an artifact of the implementation substrate, specifically FlashAttention's hardcoded assumption of a perfectly triangular causal mask. By filling this kernel-level gap, SCFA changes the evaluation criteria for future sparse attention research: a method should no longer be judged by whether it can be made to work with existing library calls (Figure 7a shows that approach is hopeless below ~70% sparsity), but by whether it produces sparsity patterns that are sufficiently coarse-grained and block-structured to exploit SCFA-like tiled skipping.

The paper's most conceptually important finding is the **Figure 7a diagnostic**: a naive PyTorch implementation of QK-dropping with custom causal masking is *slower than dense FlashAttention* until sparsity exceeds ~70%. This single result reframes years of prior work on dynamic pruning, token dropping, and hash-based attention. Papers that reported theoretical FLOP reductions from these methods but evaluated only on asymptotic complexity or on small-scale custom implementations were effectively measuring the wrong thing — the constant factors imposed by the GPU's preference for regular, tiled computation dominate until sparsity is extreme. SCFA resolves this contradiction by providing an implementation path where the constant factors are comparable to FlashAttention's, meaning the asymptotic benefits actually materialize. This reconciliation is analogous to the paper's own narrative about the Reformer: LSH attention was a good idea that was abandoned partly because its GPU implementation forced compromises (fixed-size chunks, declining coverage) that made it appear worse than it needed to be. SCFA shows that LSH attention, when given an appropriate kernel, can simultaneously achieve exact collision coverage and outperform dense FlashAttention (Figures 4a, 4b, Table 5). The paper thus re-opens a research direction that was prematurely closed.

The paper also shifts the burden of proof for future efficient attention work. Prior to SCFA, a researcher proposing a new dynamic sparsity pattern could reasonably argue that their method's $O(T \log T)$ or $O(T)$ complexity was the key contribution, and that implementation efficiency was a secondary concern to be addressed later. After SCFA, that argument is harder to sustain — the paper provides both the diagnostic (Figure 7a: naive implementations are useless) and the remedy (index-tracking arrays + tiled skipping). A new dynamic sparsity method should now be accompanied by evidence that it can be implemented with similar tile-level efficiency, or at minimum, an analysis of why its sparsity pattern is fundamentally incompatible with SCFA-like tiling. This raises the methodological bar for the subfield.

On the practical deployment side, the paper establishes that **dynamic sparse attention during training is not just a research curiosity but a genuine speedup lever** at sequence lengths that are increasingly common in production (8k–16k tokens). The 2.0× and 3.3× end-to-end training speedups (Figure 6c) are measured on real language modeling workloads with a representative model architecture, not on synthetic benchmarks. This matters because the efficient transformer literature has produced many methods with impressive asymptotic claims but few that demonstrably accelerate actual training loops at realistic scales. SCFA's integration into a standard training pipeline (NanoGPT-based, Section 4.1, Appendix B.3) and the measurement of wall-clock iteration time rather than attention-module time alone make these speedup claims unusually credible for the subfield.

A subtler shift is in how the paper frames the tradeoff between **sparsity granularity and GPU efficiency**. The implicit design principle — that sparsity decisions must be made at the granularity of tiles ($B_m \times B_n = 128 \times 128$ dot products) to amortize the per-decision overhead — provides a concrete constraint for future algorithm designers. Fine-grained per-element sparsity patterns, even if they achieve higher theoretical FLOP reduction, will likely fail to translate to speedup on current GPU architectures because the decision cost per element cannot be amortized. SCFA's success with block-level skipping (hash ranges, compacted index blocks) provides positive evidence for this principle; the failure of naive per-element masking (Figure 7a) provides negative evidence. This is not proven as a theorem, but it is strongly suggested by the scaling behavior across Figures 3, 7, 10, and 11.

Finally, the paper's open-source implementation in Triton lowers the barrier to entry for kernel development. By providing the `dynamic_sparse_attention` interface (Listing 2, Appendix B.2) that abstracts the kernel complexity behind a simple API accepting index/hash arrays, the paper enables researchers without CUDA expertise to prototype new sparsity controllers. This is an infrastructure contribution that could accelerate research velocity in the same way that FlashAttention's availability in PyTorch 2.0 accelerated adoption of efficient attention more broadly.

### Follow-Up Research This Work Enables

**Learned sparsity controllers evaluated end-to-end with SCFA.** The paper deliberately uses the simplest possible sparsity controllers — random uniform hashing and random independent dropping — to validate the kernel. This leaves open the question of how much better the speed-perplexity tradeoff can be with learned sparsity. A natural follow-up would train a lightweight gating network that predicts, for each attention head and sequence position, whether to keep or drop that query/key, using a loss that combines language modeling perplexity with a sparsity regularization term (e.g., penalizing the fraction of kept elements). The gating network could be a small MLP taking the query/key representation as input and producing a scalar keep probability, trained jointly with the main model using straight-through gradient estimation. The key question: at a fixed training speedup (say, 2×), how much lower can perplexity go compared to random 30% dropping? SCFA makes this experiment tractable because the kernel can handle per-batch, per-head, per-position dropping decisions — the gating network outputs would directly feed the `q_keep` and `k_keep` tensors in Listing 2. A strong result would show that learned dropping achieves the same perplexity as dense FlashAttention at 50% sparsity (vs. 30% for random dropping), effectively doubling the speedup at equal quality.

**Attention recall analysis for hash-based sparsity.** The paper demonstrates that H-LM matches F-LM perplexity (Figure 6a) but provides no analysis of *why* — specifically, what fraction of the top-$k$ attention weights from dense attention are captured within the hash buckets? A diagnostic experiment would instrument a trained F-LM model, run a forward pass on a validation set, record the top-10% attention weights per query (by magnitude), then compute what fraction of those key-query pairs would have been computed by H-LM at various $n_b$ values. This "attention recall" metric would reveal whether hash-based sparsity works because LSH genuinely captures high-similarity key-query pairs (the intended mechanism), or because the model learns to distribute its attention across buckets during training (an adaptation effect), or because language modeling is surprisingly robust to dropping random long-range attention edges (a null effect). A finding that recall is high (>80%) at $n_b = 16$ would validate the LSH mechanism; a finding that recall is low (<40%) would suggest the model is compensating through increased local attention or through the feed-forward layers. This experiment would directly inform the design of better hashing schemes — if recall is high, the focus should be on cheaper hashing; if recall is low, the focus should be on better hash functions or alternative sparsity patterns.

**Combined Hash+QK sparsity with SCFA.** The paper studies Hash-sparse and QK-sparse as independent mechanisms, and the architecture (Listing 2, Appendix B.2) supports both simultaneously — the kernel already accepts hash arrays and a `sparsity_mode` flag. A natural extension is a two-stage sparsification: first, use LSH to assign queries and keys to buckets; second, within each bucket, apply learned or heuristic dropping to further reduce computation. For example, with $n_b = 8$ buckets (expected 1/8 of keys per bucket) and 50% QK-dropping within each bucket, the effective fraction of key-query pairs computed would be $(1/8) \times (1/2)^2 = 1/32$ of the full attention matrix (accounting for both query and key dropping), giving a theoretical 32× FLOP reduction. The SCFA kernel would process this as: hash-based tile range finding (`start`/`endhash`) followed by compacted index-based refinement (`end` from QK-sparse logic), with dual masking within computed tiles. The key experiment: at $T = 16384$, can a combined H+D-LM achieve 4–5× training speedup while matching F-LM perplexity? SCFA's hash-sparse kernel already handles the case where not all queries in a bucket are kept (via the QK-sparse index logic), so the combination requires only a sparsity controller that outputs both hash assignments and keep/drop decisions — no kernel modification needed.

**Inference-specific adaptation of SCFA for autoregressive decoding.** The paper evaluates only training throughput, leaving open the question of whether SCFA provides speedup during autoregressive generation. During inference, the key-value cache stores all previously generated tokens, and each new token generation adds one query and one key-value pair. For Hash-sparse, this means: (1) the new query must be hashed, (2) the new key-value pair must be inserted into the correct bucket position in the cache, and (3) attention must be computed only against keys in matching buckets. The naive approach (re-sorting the full cache after each token) would be prohibitively expensive. A more sophisticated approach would maintain a bucket-indexed data structure (e.g., per-bucket contiguous segments with insertion pointers) that supports $O(1)$ append and $O(1)$ lookup of bucket boundaries. The SCFA kernel could then be called with `T_Q = 1` (single query) and `T_KV` being the variable-length per-bucket cache segments. The key question: at what sequence length does the per-token hashing and bucket-maintenance overhead become small relative to the savings from sparse attention during decoding? A strong result would show that H-LM provides, say, 1.5× faster token generation at 8k context length compared to dense FlashAttention with KV cache, enabling longer-context interactive applications.

**Stress-testing SCFA on non-language modalities and model scales.** The paper's experiments are confined to autoregressive language modeling on text at a single model scale (122M parameters). Follow-up work should stress-test SCFA in two directions: (1) different modalities where attention patterns may have different sparsity structure, and (2) larger model scales where the attention-to-feed-forward ratio changes. For modalities, protein language models (e.g., ESM-2) and DNA sequence models (e.g., Enformer) operate on long sequences (thousands to millions of tokens) where attention is the clear bottleneck, but the optimal sparsity pattern may differ from text — proteins have strong local structure (secondary structure elements are contiguous in sequence) and specific long-range contacts (tertiary structure), suggesting that a combination of local window attention and hash-based long-range attention might be particularly effective. For model scale, a replication of the H-LM experiment at 1B parameters (e.g., 24 layers, hidden 2048, 16 heads) would test whether the 72–77% attention fraction (Figure 9) holds at larger scale — if attention accounts for less of the total runtime, the overall speedup from SCFA will be proportionally smaller, and the maximum useful sparsity will shift. The key question: does the optimal $n_b$ for hash-based sparsity depend on model scale, or is it determined primarily by sequence length?

**Verifier over-optimization at the hardware level: a systematic study of sparsity-to-speedup translation.** The paper's Figure 7a is a single data point in a larger phenomenon: the translation from algorithmic sparsity to actual GPU speedup is highly non-linear and depends on the interaction between sparsity pattern structure and hardware execution characteristics. A systematic follow-up study could measure the "speedup efficiency" (actual speedup / theoretical FLOP reduction) for different sparsity patterns — random per-element, random per-tile, hash-based, local window, strided — across sequence lengths and GPU architectures (A100, H100, consumer GPUs). The goal would be to produce design guidelines for sparse attention: "on GPU X, sparsity pattern Y achieves >80% speedup efficiency when granularity is at least Z elements per block and the pattern is structured as W." SCFA provides the kernel infrastructure to implement and benchmark these patterns on equal footing, enabling a controlled experiment that the field currently lacks. A negative result — for instance, showing that per-element random sparsity achieves <10% speedup efficiency even with an optimal kernel — would be as valuable as a positive one, because it would definitively establish that certain classes of sparsity are impractical on current hardware regardless of kernel quality.

### Practical Applications and Downstream Use Cases

**Long-document language model training at reduced cost.** The most direct application of this work is accelerating the training of autoregressive language models on long sequences. For a team training a GPT-style model on 16k-token documents, replacing FlashAttention with H-LM ($n_b = 16$) would reduce training time by approximately 3.3× (Figure 6c), or equivalently reduce GPU-hours by ~70% for the same number of training tokens. At current cloud GPU pricing (~$1–2 per A100-hour), a 10,000-GPU-hour training run becomes ~3,000 GPU-hours, saving $7,000–14,000. The hash-based method is particularly attractive because it requires no modification to the training objective or architecture beyond setting $K = \text{normalize}(Q)$ (which the paper's baseline also uses), making it a drop-in replacement for standard causal FlashAttention. The speedup is largest precisely where attention dominates (long sequences), which is the regime where training is most expensive. The paper's 50k-iteration experiments (Figure 16) confirm that the speedup persists through longer training, suggesting the benefit is not limited to early-stage pretraining.

**On-device or edge fine-tuning with limited compute budgets.** For applications where a pretrained language model must be fine-tuned on long-context data using constrained hardware (e.g., a single consumer GPU, an edge server, or a research lab with limited resources), the QK-dropping method provides a tunable speed-perplexity tradeoff. At 30% random dropping, D-LM trains 1.9× faster while nearly matching dense FlashAttention perplexity (Figure 8); at 50% dropping, it trains 2.6× faster with approximately 2.5 perplexity points degradation. Practitioners can select the sparsity level based on their compute budget and quality requirements. Because the dropping is random per-batch and per-head, the same model can be fine-tuned at different sparsity levels for different tasks without retraining the sparsity controller. The SCFA kernel handles the dynamic compaction without modification, and the pre-processing overhead is amortized for sequences above ~4k tokens (Figure 7b). For a lab that can only afford a single A100, this means a 16k-token fine-tuning run that would take 3 days can be completed in approximately 1–1.5 days at modest quality cost.

**Hash-based attention for retrieval-augmented and memory-augmented architectures.** The Hash-sparse kernel's ability to restrict attention to within-bucket interactions without approximation (100% collision coverage, Figure 4b) makes it suitable for architectures where attention is intentionally sparse by design, not just as a speed optimization. For example, in retrieval-augmented generation (RAG), retrieved passages could be assigned hash codes, and each generation step would attend only to passages with matching codes — effectively implementing a learnable, differentiable retrieval within the attention mechanism. Because SCFA computes exact softmax on the selected subset, there is no information leakage from non-matching passages, and gradients correctly flow only through the attended-to retrieved content. Similarly, memory-augmented transformers that maintain a large external key-value store could use hashing to select a subset of memory slots for attention at each step, with SCFA ensuring that the selection is exact (all matching slots are attended to, no non-matching slots leak information) and efficient (only the relevant tiles are computed). The 100% coverage guarantee distinguishes SCFA from the Reformer's approximate implementation, which would silently miss some matching elements.

**Data preprocessing and feature extraction pipelines on long biological sequences.** Beyond language modeling, the attention mechanism is increasingly used for biological sequence analysis — protein folding prediction, variant effect prediction, and regulatory genomics all involve applying transformers to sequences of thousands to millions of tokens. In these settings, the attention patterns often have known structure (e.g., in proteins, attention should focus on spatially proximate residues in the folded structure, not just sequentially nearby ones). A practitioner could use SCFA's Hash-sparse kernel with domain-specific hash functions (e.g., based on predicted contact maps, evolutionary coupling scores, or structural templates) to restrict attention to biologically plausible interactions, reducing computation while preserving or even improving prediction quality by acting as an inductive bias. The 3.3× speedup at 16k tokens (Figure 6c) suggests that a protein language model operating on 16k amino acid sequences would see similar training acceleration — for a dataset like UniRef with millions of sequences, this translates to weeks of GPU time saved.
