# Cheaply Evaluating Inference Efficiency Metrics for Autoregressive Transformer APIs

**ArXiv:** [2305.02440](https://arxiv.org/abs/2305.02440)

## 🎯 Pitch

OpenAI’s ChatGPT looks blazingly fast—but the paper reveals that its raw latency advantage disappears after correcting for API-level optimizations. By estimating an “idealized runtime” on uniform hardware, they show that some smaller models actually deliver more capability per FLOP than their larger rivals, completely reshuffling the cost–performance leaderboard.

---

## 1. Executive Summary

This paper proposes and evaluates a methodology for comparing inference efficiency across black-box autoregressive Transformer APIs. Using ten state-of-the-art LLMs—ranging from 6B to 530B parameters—on four HELM benchmark tasks (IMDB, MMLU, BoolQ, RAFT), the paper introduces the **idealized runtime**, a metric that estimates what inference latency *would* be if all models ran on uniform hardware and software (e.g., NVIDIA A100 GPUs with Megatron) without performance contention, contrasting it with raw runtime that includes provider-specific optimizations and variable queuing delays. The key empirical insight is that idealized runtime reshuffles the efficiency-capability Pareto frontier: OpenAI/davinci appears on the frontier when using raw runtime across all four benchmarks, but consistently falls off it under idealized runtime, establishing that the superior inference performance of certain APIs is often a byproduct of optimizations within the API rather than inherent efficiency in the model itself. The methodology enables efficient estimation by exploiting the finding that autoregressive inference runtime is the sum of a piecewise linear function of prompt size and a linear function of output tokens, requiring only a small set of profiled "configuration" queries rather than exhaustive per-benchmark measurement.

## 2. Context and Motivation

### The Core Problem: We Have No Common Yardstick for Inference Efficiency

The fundamental challenge this paper addresses is deceptively simple: **given two language models accessed through different black-box APIs, how do you compare their inference efficiency fairly?** This question matters enormously because LLMs are deployed at staggering scale—the paper opens by noting that models have grown by *almost four orders of magnitude* in recent years, powering everything from ChatGPT to GitHub Copilot to Bing. Yet the infrastructure behind these deployments remains opaque. When you send a query to OpenAI's API, you observe a raw latency number. When you send a different query to AI21's API, you observe another latency number. Are those numbers comparable? Can you conclude that one model is "more efficient" than the other based on them?

The paper argues—and demonstrates empirically—that the answer is **no**, and that this lack of comparability has serious consequences for model developers, researchers, and the broader ecosystem.

### Why This Gap Matters: Three Stakeholder Perspectives

The importance of inference efficiency comparisons cuts across multiple constituencies (Section 1, with specific examples drawn from the paper's framing):

**For end users and application developers**, raw runtime *is* what they experience. But raw runtime alone tells a misleading story about model efficiency because it bundles together two things that should be analyzed separately: the inherent computational cost of the model architecture, and the quality of the serving infrastructure. The paper's analytical decomposition—factoring total observed latency into prompt encoding time, per-token generation time, and a noise/overhead term (Equation 3, Section 3.3)—allows practitioners to understand *why* a model feels fast or slow, and whether switching providers would improve their application's latency in a predictable way. Without this decomposition, a developer who switches from one API to another has no way to anticipate whether the new model's architecture will bottleneck their use case differently (e.g., long-prompt vs. long-generation scenarios).

**For model creators and researchers**, the gap is even starker. When designing a new model architecture or scaling an existing one, the inference cost of that architectural decision will be borne for the entire deployed lifetime of the model—which, for widely-used models, can dwarf training costs. The paper explicitly notes that "model inference costs might outweigh training costs for certain applications (e.g., ChatGPT)" (Section 1). If a researcher trains two model variants and evaluates them through differently-optimized APIs, the raw runtime numbers may suggest the wrong variant is more efficient. The paper's concrete finding with OpenAI/davinci—that its Pareto-frontier status under raw runtime disappears under idealized runtime (Section 5.4, Figure 9)—is a case study in exactly this trap: a model can *appear* architecturally efficient when the efficiency actually comes from engineering investments that other providers haven't (yet) made.

**For the scientific community and benchmarking efforts**, the problem threatens the validity of capability-efficiency tradeoff analyses. The paper positions itself against major benchmarking efforts like BIG-Bench (Srivastava et al., 2022) and HELM (Liang et al., 2022), which compare model capabilities extensively but either use model size as the efficiency proxy or report raw runtime without accounting for the confounding factors the paper identifies. Model size (number of parameters) is particularly problematic as an efficiency metric—the paper points out that "two models with the same size can have vastly different inference runtimes" due to architectural differences like attention head configuration, hidden dimension, layer count, and sparsity patterns (Fedus et al., 2021; Jeon & Kim, 2018; Henderson et al., 2020; Scao et al., 2022). A 175B-parameter dense model and a 175B-parameter mixture-of-experts model have radically different inference FLOPs per token, yet a naive parameter-count comparison treats them as equivalently "efficient."

### Where Prior Approaches Fall Short

The paper identifies three categories of prior approaches, each with specific failures that motivate the proposed methodology:

**1. Model size (parameter count) as efficiency proxy.** This is the dominant approach in the scaling laws literature (Kaplan et al., 2020) and in most model announcement papers (Chowdhery et al., 2022; Rae et al., 2021). The paper identifies two distinct problems. First, parameter count is *uninterpretable* for practical deployment decisions: "Can model X meet a latency SLO of 100 milliseconds?" or "How much will it cost to use model X in this concrete application?" cannot be answered from parameter count alone (Section 6). Second, parameter count ignores architectural choices that dramatically affect runtime for the same parameter budget—the paper cites Scao et al. (2022)'s finding that two models with identical parameter counts can have substantially different inference runtimes due to differences in how those parameters are organized (e.g., wider-but-shallower vs. narrower-but-deeper configurations produce different computational patterns that interact differently with hardware). The idealized runtime metric directly addresses this by measuring *actual computational work* (in FLOPs) as realized on specific hardware, which captures these architectural effects.

**2. Floating-point operations (FLOPs) count.** Several works use per-forward-pass FLOP count as a proxy for inference cost. While FLOPs are architecture-aware (unlike parameter count), the paper identifies crucial limitations (Section 6). First, **FLOPs don't translate linearly to runtime**: "two operators with the same number of FLOPs could be executed with different efficiencies if one of the operators involves more memory accesses, preventing execution at peak device throughput." This is a direct consequence of the roofline model (Williams et al., 2009) which shows that operator runtime is determined by the *minimum* of peak compute throughput and peak memory bandwidth—two operators with identical FLOP counts but different arithmetic intensity (FLOPs per byte of memory access) can have very different runtimes. The paper's idealized runtime metric naturally captures these effects by measuring on actual hardware rather than counting operations in the abstract. Second, **FLOPs are hard to interpret for end users** in the same way parameter count is—they don't directly answer latency or cost questions. Third, for autoregressive inference specifically, the relationship between prompt size and inference FLOPs is non-trivial (involving both a prompt encoding phase and a per-token generation phase with different compute characteristics), making naive total-FLOP comparisons potentially misleading if prompt/output length distributions aren't matched.

**3. Raw API runtime.** This is what practitioners actually measure, and the paper acknowledges it "accurately represents the behavior API consumers observe" (Section 6). However, raw runtime suffers from two fatal flaws for the purpose of comparing *model efficiency* as opposed to *API quality*. The first is **provider-specific optimizations orthogonal to the model**. An API provider might use custom inference kernels (e.g., FlashAttention; Dao et al., 2022), model parallelism strategies that reduce latency, query caching, or proprietary hardware (TPUs, custom ASICs). The paper's striking finding that OpenAI/davinci appears on the raw-runtime Pareto frontier for all four benchmarks but falls off under idealized runtime (Section 5.4, Figure 9) is the clearest evidence that these optimizations can create the illusion of model efficiency where none exists.

The second flaw is **performance contention and variability**. The paper demonstrates empirically that:
- Heavy load can increase raw API runtime by **up to 2×** for certain providers (Section 3.5, Figure 6—showing Anthropic/v4-s3 runtime scaling with parallel query count).
- Some models experience dramatically higher per-trial variance than others: the paper reports that AI21/J1-Grande v1 has an average coefficient of variation of approximately **0.55** compared to roughly **0.2** for other AI21 models, and "outlier points can have as much as 3× higher latency" even for models with generally lower variance (Section 3.5, Figure 5). This means that comparing two models based on a small number of API queries can produce misleading conclusions purely due to random queuing effects.

The paper's **denoised runtime** metric addresses this second flaw by factoring out the noise via minimum-over-trials regression, providing an intermediate metric between raw and idealized runtime (Section 4.1). The inequality the paper establishes—$t_{\text{raw}} \geq t_{\text{denoised}} \geq t_{\text{idealized}}$ (assuming idealized software/hardware is at least as fast as the API's stack)—provides a formal decomposition isolating different sources of observed latency differences.

### The Specific Technical Challenge of Autoregressive Inference

Beyond the general problem of comparing API-served models, the paper confronts a more specific technical challenge: **autoregressive inference has a fundamentally different structure than standard ML inference**, and this structure creates both the difficulty of exhaustive measurement and the opportunity for efficient estimation.

For a standard image classifier (e.g., ResNet-50), inference is a single forward pass: input goes in, prediction comes out, runtime is roughly constant per input. For autoregressive LLMs, inference is a two-phase process (Section 2.2):
- **Prompt encoding**: the entire input prompt (p tokens) is processed in parallel, similar to training. The computational cost per token is relatively low because attention is computed in parallel across all prompt tokens.
- **Token generation**: each output token must be generated sequentially, with each new token requiring its own forward pass through the entire model. Critically, the computation of attention scores for each new token involves comparing it against *all previous tokens* (prompt + already-generated output), meaning the per-token compute cost grows *with sequence length* even in the generation phase—though the paper shows this growth is negligible when $i \ll 6h$, which holds for typical LLMs (e.g., for OpenAI/davinci, max context length is 2048 while $h = 12288$, so the correction term $i/6h$ is at most ~0.028; Appendix A.2).

This two-phase structure means that **naively measuring inference cost per benchmark is expensive**: every query with different prompt/output length would need to be profiled exhaustively. The paper's key analytical contribution—both deriving and empirically validating that end-to-end runtime is $t(p, o) = \text{prompt\_encoding\_time}(p) + (o-1) \cdot g$ (Equation 3, Section 3.3)—enables an estimation procedure that requires profiling only a small set of $(p, o)$ configurations and then using linear regression to predict runtime for arbitrary queries (Section 3.4). The piecewise linear nature of $\text{prompt\_encoding\_time}(p)$—linear at large $p$ but curving at small $p$ due to throughput effects—is given theoretical justification through the arithmetic intensity argument (Section 3.2) and validated empirically with $R^2 > 0.999$ for all models on dedicated hardware.

### How This Paper Positions Itself

The paper situates itself at the intersection of three research threads:

**Benchmarking and capability evaluation.** The paper explicitly builds on HELM (Liang et al., 2022), using its scenarios (IMDB, MMLU, BoolQ, RAFT) as the capability dimension of its tradeoff analyses. It positions itself as complementing capability-focused benchmarking with a principled efficiency dimension, arguing that "scale alone does not predict model capabilities" and that "rigorous empirical evaluation of LLMs is also needed" alongside scaling laws (Section 5.4).

**Inference cost measurement.** The paper acknowledges prior work on training cost measurement—energy consumption (Cao et al., 2020; Henderson et al., 2020; Strubell et al., 2019; Patterson et al., 2021), carbon emissions (Bender et al., 2021), and the general principle that training costs need systematic reporting—but notes that "information on inference-time costs of LLMs is more scant." The reasons identified include the competitive sensitivity of runtime performance and the technical difficulty of measurement across heterogeneous serving stacks. The paper positions its idealized runtime methodology as overcoming these barriers through a combination of architectural knowledge (model hyperparameters are often public even when weights are not) and efficient profiling.

**Hardware-software co-design evaluation.** The paper demonstrates a secondary use case for its methodology: comparing different hardware and software stacks *for the same model* (Section 5.3, Figure 8). By estimating idealized runtime on A100 GPUs vs. V100 GPUs, the paper can answer questions like "Is it cheaper to run this workload on older, cheaper hardware or newer, faster hardware?"—finding, for example, that V100s are "both slower and more expensive" for most models because the reduced memory capacity (32GB vs. 80GB) often requires using more GPUs in parallel. This capability positions the methodology as useful not just for cross-model comparison but also for deployment planning and infrastructure decisions.

### Summary of the Gap and Position

In essence, the paper identifies a methodological void: **there exists no standardized, interpretable, and practically measurable metric for comparing inference efficiency across LLMs served through black-box APIs.** This void has real consequences—it causes model developers to make architectural decisions without understanding inference cost implications, it prevents fair capability-efficiency comparisons, and it obscures whether API latency improvements come from model quality or infrastructure investments. The paper fills this void by (1) deriving a parametric form for autoregressive inference runtime that enables efficient estimation, (2) defining a hierarchy of metrics (raw → denoised → idealized) that isolate different sources of latency variation, and (3) demonstrating through concrete tradeoff analyses that the choice of metric changes which models appear on the Pareto frontier—a finding with direct implications for how the field evaluates and compares large language models.

## 3. Technical Approach

### 3.1 Reader Orientation

This paper does not build a new ML system but rather a **measurement methodology**—a procedure and a set of metrics for estimating what inference latency *would* be if every large language model were served on identical hardware under identical conditions, even when the actual models are only accessible through opaque, proprietary, and differently-optimized black-box APIs. The core problem it solves is the **lack of a standardized, fair yardstick for comparing inference efficiency across models from different providers**, where raw API runtimes conflate inherent model computational cost with provider-specific engineering optimizations and variable server load. The shape of the solution is a three-tier metric hierarchy (raw → denoised → idealized runtime) grounded in a parametric understanding of how autoregressive Transformer inference decomposes into a prompt-processing phase and a token-generation phase, enabling the full idealized runtime for any query to be estimated from a small number of profiling measurements rather than exhaustive per-benchmark timing.

### 3.2 Big-Picture Architecture (Diagram in Words)

The methodology has five logical components, though they are interleaved in the paper's exposition:

1. **Analytical Runtime Model**: A closed-form parametric expression, derived from the Transformer architecture's FLOP counts, showing that end-to-end autoregressive inference runtime for a query with prompt size `$p$` tokens and `$o$` generated output tokens decomposes as the sum of a piecewise linear function of `$p$` (the prompt encoding phase) and a linear function of `$o$` (the token generation phase). This model is what makes efficient estimation possible, since it reduces the infinite-dimensional space of `$(p, o)$` pairs to a small number of parameters.

2. **Profiling Engine**: A standalone implementation of the target model architecture on the chosen hardware/software stack (e.g., Megatron on NVIDIA A100 GPUs), instantiated with the correct hyperparameters (hidden size, number of layers, number of attention heads) but *without trained weights*, since runtime depends only on tensor shapes and compute patterns, not parameter values. This engine is used to measure runtime for a small set of "configuration" queries covering a grid of prompt sizes and output token counts.

3. **Linear Regression Estimator**: For a given prompt size `$p$`, runtimes from the profiling engine are measured at multiple values of `$o$` and fit to a line, yielding a y-intercept (the prompt encoding time for that `$p$`) and a slope (the per-output-token generation time `$g$`, which is independent of `$p$`). Repeating across prompt sizes builds a lookup table for `$\text{prompt\_encoding\_time}(p)$`, with interpolation for unseen `$p$` values.

4. **Metric Hierarchy**: Three distinct runtime metrics are defined, each stripping away a different source of non-comparability:
   - **Raw runtime** `$t_{\text{raw}}$`: what the API actually returns, including provider-specific optimizations and queuing noise.
   - **Denoised runtime** `$t_{\text{denoised}}$`: raw runtime with performance variation factored out, estimated by applying the same regression procedure to API calls, but using the *minimum* runtime across multiple trials at each `$(p, o)$` configuration. This gives the runtime with zero noise (`$\eta = 0$`).
   - **Idealized runtime** `$t_{\text{idealized}}$`: what the runtime *would be* on a uniform, specified hardware and software stack, estimated by profiling the model architecture on that stack. This removes provider-specific optimizations entirely.

5. **Cost-Aware Extensions**: The idealized runtime is augmented with scaling factors—the number of accelerators needed to serve the model and the per-unit-time cost or power draw of those accelerators—to produce **idealized dollar cost** and **idealized energy cost**. These are derived metrics, not independently estimated, but they transform a latency metric into a resource-consumption metric more relevant for deployment planning.

Information flow: model hyperparameters (hidden size `$h$`, number of layers `$l$`, number of attention heads `$n$`) → profiling engine (run on target hardware/software with a grid of `$(p, o)$` queries) → linear regression (yielding `$\text{prompt\_encoding\_time}(p)$` and `$g$` for each model) → idealized runtime prediction for arbitrary queries → (optionally) multiplication by accelerator count and cost/power factors to yield dollar or energy cost.

### 3.3 Roadmap for the Deep Dive

- **First**, the analytical runtime derivation (Section 3.1 of the paper) that reduces the FLOP counts of prompt encoding and token generation to a simple linear-plus-piecewise-linear form. This is the intellectual foundation—everything else depends on the parametric form being correct.
- **Second**, the empirical validation (Section 3.2) showing that the linear relationship holds with `$R^2 > 0.999$` on dedicated hardware and explaining *why* `$\text{prompt\_encoding\_time}(p)$` is piecewise linear rather than globally linear (arithmetic intensity transitions).
- **Third**, the estimation procedure itself (Sections 3.4 and 4.1)—exactly what profiling configuration is run, how regression is performed, and how interpolation handles unseen prompt sizes. This is the practical "how-to" that makes the methodology replicable.
- **Fourth**, the denoised runtime estimation (Section 4.1) and its relationship to raw runtime—the use of minimum-over-trials regression to factor out API noise, and the formal inequality `$t_{\text{raw}} \geq t_{\text{denoised}} \geq t_{\text{idealized}}$`.
- **Fifth**, the cost-aware metric extensions (Section 4.2) that multiply idealized runtime by accelerator count and per-unit cost or power to yield dollar and energy costs, and the design choice of why these are derived from idealized runtime specifically.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **measurement methodology paper** whose core technical contribution is the derivation and empirical validation of a parametric form for autoregressive Transformer inference runtime, which enables efficient estimation of fair comparison metrics without exhaustive profiling.

---

#### Deriving the Parametric Runtime Model from Transformer FLOP Counts

The paper begins from the observation that autoregressive inference for Transformer language models is structurally different from standard ML inference. In a standard classifier, one forward pass produces one prediction. For autoregressive LLMs, generating `$o$` output tokens requires `$o$` forward passes (the first token is generated during prompt encoding, and each subsequent token requires its own forward pass, making `$o-1$` additional forward passes beyond the prompt phase). The paper decomposes total runtime into two additive components:

$$t(\text{prompt size } p, \text{ number of output tokens } o) = \text{prompt\_encoding\_time}(p) + \text{output\_generation\_time}(o)$$

where `$p$` is the number of tokens in the input prompt and `$o$` is the total number of output tokens generated (including the first token produced during prompt encoding).

**What it computes:** the end-to-end wall-clock time for an autoregressive inference query as the sum of time spent processing the prompt (which depends only on `$p$`) and time spent generating output tokens (which depends only on `$o$`). The decomposition encodes the assumption that these two phases are additive and independent—the prompt encoding time does not depend on how many tokens will be generated, and the per-output-token generation time does not depend on the prompt size (beyond the KV cache accumulated during prompt encoding, whose size affects attention computation cost but whose contribution the paper shows is negligible in practice).

**Why this form:** this additive decomposition mirrors the actual two-phase execution of autoregressive inference. The alternative would be to model runtime as a single monolithic function of `$(p, o)$`, which would require a much larger profiling grid and would obscure the fundamentally different computational characteristics of the two phases (prompt encoding is compute-bound with high parallelism; token generation is memory-bandwidth-bound with sequential dependence).

---

##### Prompt Encoding FLOP Count

The paper derives the FLOP count for prompt encoding from the standard Transformer forward pass computation described in Section 2.1 and Appendix A.1. For a prompt with `$p$` tokens, microbatch size `$b$` (typically 1 for online inference), hidden size `$h$`, and `$l$` Transformer layers, the total FLOP count through all Transformer layers is:

$$24 b p h^2 l \left(1 + \frac{p}{6h}\right)$$

where `$b$` is the microbatch size (number of sequences processed simultaneously, typically 1 for online inference), `$p$` is the number of prompt tokens, `$h$` is the hidden dimensionality of the model, and `$l$` is the number of Transformer layers.

The term `$24 b p h^2 l$` comes from summing the FLOP contributions of: (1) the key, query, value transformations (a `$(bp, h) \times (h, 3h)$` matrix multiply costing `$2 \cdot bp \cdot h \cdot 3h = 6bph^2$` FLOPs), (2) the attention score computation (`$b n$` batched multiplies of size `$(p, h/n) \times (h/n, p)$` costing `$2 \cdot b n \cdot p \cdot (h/n) \cdot p = 2b p^2 h$` FLOPs—this is where the `$p/6h$` correction term comes from, since `$2b p^2 h = 24bph^2 \cdot (p/12h)$`), (3) the attention-over-value computation (another `$2b p^2 h$` FLOPs for `$b n$` multiplies of size `$(p, p) \times (p, h/n)$`), (4) the post-attention projection (a `$(bp, h) \times (h, h)$` multiply costing `$2bph^2$` FLOPs), and (5) the two MLP matrix multiplies (`$(bp, h) \times (h, 4h)$` at `$8bph^2$` and `$(bp, 4h) \times (4h, h)$` at `$8bph^2$`). Summing yields `$24bph^2 + 4bp^2h = 24bph^2(1 + p/6h)$`.

**What it computes:** the total number of floating-point operations executed by all Transformer layers during the prompt encoding phase, which processes all `$p$` prompt tokens in parallel (in a single forward pass, as during training). This is the computational "work" that must be performed before the first output token can be generated.

**Why this form:** when `$p \ll 6h$`—which the paper states is true for most LLMs (e.g., for OpenAI/davinci, maximum context length is 2048 while `$h = 12288$`, so `$p/6h \leq 0.028$`)—the correction term is negligible, and the FLOP count simplifies to `$24 b p h^2 l$`, which is **linear in `$p$`**. This linearity in `$p$` is the first key insight: prompt encoding FLOPs scale linearly with prompt length. The paper introduces the notation `$\theta_{\text{pe}} \cdot p$` for this linear function, where `$\theta_{\text{pe}} = 24bh^2l$` captures all model-architecture-specific constants.

---

##### Output Token Generation FLOP Count

The FLOP count for generating the `$(i+1)$`-th token (after `$i$` tokens have already been generated, including the prompt) is derived in Appendix A.2:

$$24 b h^2 l + 4 b i h l = 24 b h^2 l \left(1 + \frac{i}{6h}\right)$$

where `$i$` is the number of tokens generated so far (prompt tokens plus previously generated output tokens). The `$24 b h^2 l$` term comes from the key/query/value transformations for the single new token, the post-attention projection, and the two MLP layers—all of which operate on a single token vector of size `$(b, h)$` rather than `$(b, i, h)$`. The `$4 b i h l$` term comes from the attention computations that must compare the new token against all `$i$` previous tokens: `$b n$` batched multiplies of size `$(1, h/n) \times (h/n, i)$` for score computation (`$2 b n \cdot 1 \cdot (h/n) \cdot i = 2b i h$`) and `$(1, i) \times (i, h/n)$` for value aggregation (another `$2b i h$` FLOPs), summing to `$4b i h$` per layer, times `$l$` layers yields `$4b i h l$`.

**What it computes:** the FLOPs required to generate one additional output token, given the KV cache containing all previous tokens. Unlike prompt encoding, which processes all tokens in parallel, token generation processes one token at a time, but must attend over the growing sequence of previous tokens.

**Why this form:** the key observation is the same `$i \ll 6h$` condition. When this holds—which, again, it does for typical LLMs—the term `$i/6h$` is negligible, and the per-token generation FLOP count becomes approximately **constant**, independent of how many tokens have been generated so far. The paper denotes this constant as `$\theta_{\text{og}} = 24bh^2l$`. This constant per-token cost is the second key insight: once the prompt is encoded, each subsequent output token costs roughly the same amount of computation, regardless of sequence position.

---

##### From FLOPs to Runtime

The paper converts FLOP counts to wall-clock runtime by dividing by the achievable throughput (FLOPs per second) of the hardware for each computational phase:

$$\text{prompt\_encoding\_time}(p) = \frac{\theta_{\text{pe}} \cdot p}{\text{throughput}_{\text{pe}}(p)}$$

$$\text{output\_generation\_time}(o) = \sum_{\text{token } i} \frac{\theta_{\text{og}}}{\text{throughput}_{\text{og}}(i)}$$

**What it computes:** the actual wall-clock time by dividing FLOP counts by hardware throughput. For prompt encoding, throughput is written as a function of `$p$` because the arithmetic intensity of the computation changes with prompt size (larger matrix multiplies achieve higher utilization of GPU compute units). For output token generation, throughput is written as potentially depending on which token is being generated (since larger `$i$` means larger attention matrices).

**The crucial empirical simplification:** the paper observes that `$\text{throughput}_{\text{og}}$` is empirically **constant across all tokens** (independent of `$i$`), which means the summation simplifies to a linear function of `$o$`:

$$\text{output\_generation\_time}(o) = (o - 1) \cdot g$$

where `$g = \theta_{\text{og}} / \text{throughput}_{\text{og}}$` is the constant per-output-token generation time. The `$o-1$` accounts for the fact that the first output token is generated during the prompt encoding phase (so `$o$` total output tokens require `$o-1$` additional forward passes).

**Why this simplification holds:** the `$i \ll 6h$` condition means the attention computation over the growing KV cache remains a small fraction of total FLOPs per token, and the throughput of the dominant operations (the matrix multiplies operating on single-token vectors) is independent of sequence position because the shapes of those operations do not change with `$i$`—only the attention operations change shape, and those are negligible in total cost.

---

##### Putting It Together: The Final Parametric Form

Combining the FLOP-to-runtime conversions yields the paper's central parametric expression (Equation 3, Section 3.3):

$$t(\text{prompt size } p, \text{ number of output tokens } o) = \text{prompt\_encoding\_time}(p) + (o - 1) \cdot g$$

where `$\text{prompt\_encoding\_time}(p)$` is a piecewise linear function of `$p$`, `$g$` is the constant per-output-token generation time (in seconds per token), and `$o$` is the number of output tokens generated.

**What it computes:** the total inference runtime for any query as the sum of two terms: a prompt-processing cost that depends only on prompt length, and a generation cost that is linear in the number of output tokens with slope `$g$`. Crucially, `$g$` does *not* depend on `$p$`—the per-token generation cost is the same whether the prompt is 10 tokens or 10,000 tokens (because the dominant FLOPs come from the fixed-size matrix multiplies, not the attention over the KV cache).

**Why this piecewise-linear-plus-linear form rather than globally linear:** the arithmetic intensity argument explains the piecewise nature. At very small prompt sizes (e.g., `$p = 1$`), the matrix multiplications in the Transformer are too small to saturate the GPU's compute units—the computation is **memory-bandwidth-bound** (the GPU spends more time waiting for data to arrive from memory than actually computing). As `$p$` grows, the matrix dimensions grow, and the computation transitions into the **compute-bound** regime where the GPU's floating-point units are fully utilized. The prompt encoding throughput `$\text{throughput}_{\text{pe}}(p)$` increases through this transition and then plateaus once compute-bound. Since runtime is FLOPs divided by throughput, and FLOPs grow linearly with `$p$`, runtime is initially **super-linear** in `$p$` (when throughput is increasing) and eventually **linear** in `$p$` (when throughput has plateaued). This produces the piecewise linear shape observed in Figure 4. The paper notes this explicitly: "the prompt-encoding throughput (`$\text{throughput}_{\text{pe}}$`) initially increases as `$p$` increases (arithmetic intensity of the computation increases with `$p$`) but eventually plateaus. Consequently, we observe that `$\text{prompt\_encoding\_time}$` is piecewise linear."

#### Empirical Validation of the Parametric Form

The paper validates the derived parametric form through two sets of experiments: one on dedicated hardware (using Megatron) and one through black-box APIs.

**Dedicated hardware validation (Figures 3 and 4).** The authors implement the model architectures in Table 1 using Megatron (NVIDIA's optimized Transformer implementation) on NVIDIA A100 GPUs, using the minimum number of GPUs necessary to fit each model in memory (with tensor model parallelism within a server when one GPU is insufficient, and pipeline model parallelism for the largest model, Microsoft+NV/TNLG v2). They profile end-to-end runtimes for a grid of `$(p, o)$` values and observe:

- **Figure 3**: For each fixed prompt size `$p$`, runtime versus number of output tokens `$o$` shows an "extremely strong linear relationship" with "coefficients of determination (`$R^2$`) for the resulting time estimates... very close to `$1.0$` (`$> 0.999$`) for all models." This confirms that `$g$` is indeed constant—`$\text{output\_generation\_time}(o)$` is linear in `$o$`.
  
- **Figure 4**: Runtime versus prompt size `$p$` shows a "roughly linear relationship, especially at large prompt sizes," but curvature is visible at small `$p$` (e.g., the first few hundred tokens), confirming the piecewise linear nature with a bandwidth-bound-to-compute-bound transition.

**Why this empirical validation matters:** the parametric form was derived from a theoretical FLOP analysis that made the simplifying assumption `$p \ll 6h$`. The `$R^2 > 0.999$` result confirms that this assumption does not introduce meaningful error for practical model sizes and context lengths. The validation also confirms that throughput is indeed constant during token generation, which was an empirical claim not proven analytically.

**Black-box API validation (Table 2).** The authors run a similar experiment by sending synthetic queries with controlled prompt sizes and output token counts to black-box APIs (OpenAI, AI21, Cohere, Anthropic). They fit the same linear regression and report `$R^2$` values in Table 2, which range from 0.917 (AI21/J1-Grande v1, which has high variance) to 0.997 (Cohere/XL v20220609). The lower `$R^2$` for some models is attributed to performance variance—the API noise term `$\eta \geq 0$` that adds random positive latency to the underlying denoised runtime. The high `$R^2$` values despite this noise confirm that the parametric form is correct even when measured through noisy API calls.

**The extended parametric form for black-box APIs (Section 3.5):**

$$t(\text{prompt size } p, \text{ number of output tokens } o) = \text{prompt\_encoding\_time}(p) + (o - 1) \cdot g + \text{overhead}$$

where `$\text{overhead}$` captures "the fixed costs of using an API to serve model predictions instead of using accelerators locally (e.g., round-trip latency of communicating with a remote API server) and performance variability (e.g., queuing delay or performance interference across requests)."

**What it computes:** the same linear-plus-piecewise-linear decomposition, but with an additional constant term representing API-specific overheads that do not scale with prompt size or output count—things like network latency, authentication, request queuing, and load balancing.

**Why this additive overhead form:** the overhead is modeled as additive and constant (independent of `$p$` and `$o$`) because network round-trip time, authentication overhead, and baseline server latency do not depend on the size of the language model computation. Performance variability from load, however, *could* scale with query size, but the paper treats it as approximately constant additive noise for simplicity. This is a modeling choice—the denoised runtime estimation procedure (using minimum-over-trials) is designed to mitigate the impact of this noise without needing to model its precise statistical structure.

---

#### The Estimation Procedure

The parametric form enables a two-step profiling-and-regression procedure that estimates `$\text{prompt\_encoding\_time}(p)$` and `$g$` for any model and target system using measurements from a small set of configuration queries (Section 3.4).

**Step 1: Profile prompt encoding times at discrete prompt sizes.** The user selects a set of prompt sizes to profile, e.g., `$P = \{1, 256, 512, 1024, 1536\}$` for a model with `$\text{max\_context\_length} = 2048$`. For each `$p \in P$`:
- Run the autoregressive inference engine with `$p$` prompt tokens and varying numbers of output tokens `$o$` (e.g., `$o \in \{1, 2, 4, 8, 16, 32, 48, 64\}$`).
- Fit a linear regression model `$\text{runtime} = \text{intercept} + \text{slope} \cdot o$` to the measured runtimes.
- The y-intercept of this regression is `$\text{prompt\_encoding\_time}(p)$`—the estimated runtime when `$o = 1$` (only the first token is generated, which happens during prompt encoding, so the generation cost is zero). The slope is `$g$`, and should theoretically be the same for all `$p$`—this provides a consistency check.

**Step 2: Estimate the per-output-token generation time `$g$`.** The paper describes two approaches, which should yield equivalent results:
- Take the slopes from the per-`$p$` regressions and verify they are approximately equal, then average them.
- Compute `$\text{total\_runtime}(p, o) - \text{prompt\_encoding\_time}(p)$` for all profiled `$(p, o)$` pairs, then fit a single linear regression with `$y = \text{runtime difference}$` and `$x = o$`. The slope of this regression is `$g$`, the runtime cost per additional output token.

**Step 3 (online): Predict runtime for arbitrary queries.** For a new query with prompt size `$p^*$` and output token count `$o^*$`:
- If `$p^*$` is exactly in the profiled set `$P$`, use the measured `$\text{prompt\_encoding\_time}(p^*)$`.
- If `$p^*$` is between two profiled values `$p_a$` and `$p_b$`, interpolate linearly: since `$\text{prompt\_encoding\_time}$` is piecewise linear, linear interpolation within each linear piece is exact.
- Compute `$t(p^*, o^*) = \text{prompt\_encoding\_time}(p^*) + (o^* - 1) \cdot g$`.

**Why this two-step procedure rather than direct per-query profiling:** the space of possible `$(p, o)$` pairs is large, but the parametric form reduces the degrees of freedom to `$|P| + 1$` parameters (the prompt encoding times at `$|P|$` prompt sizes, plus one `$g$`). Profiling a `$|P| \times |O|$` grid (e.g., `$5 \times 8 = 40$` measurements) suffices to estimate runtimes for *any* `$(p, o)$` within the profiled range, whereas exhaustive profiling of every distinct query in a benchmark might require thousands of measurements. The paper quantifies this efficiency gain: "profil[ing] on the order of hours (`< 2$` hours for most models)... once, compared to hours per benchmark (depending on number of queries in the benchmark) for exhaustive profiling" (Section 5.3).

---

#### Idealized Runtime: Definition and Estimation

The idealized runtime `$t_{\text{idealized}}^{(m, s, h)}$` is defined as the runtime of model `$m$` on a **specified, uniform software stack `$s$` and hardware type `$h$`** (Section 4.1). The paper's default configuration is Megatron (`$s = \text{Megatron}$`) on NVIDIA A100 80GB GPUs (`$h = \text{A100}$`):

$$t_{\text{idealized}}^{(m, s, h)}(\text{prompt size } p, \text{ number of output tokens } o) = \text{prompt\_encoding\_time}_{\text{idealized}}^{(m, s, h)}(p) + (o - 1) \cdot g_{\text{idealized}}^{(m, s, h)}$$

**What it computes:** the hypothetical wall-clock time if model `$m$` were served on the specified software and hardware, with no performance contention and no provider-specific optimizations. It is "idealized" in the sense that it assumes dedicated, contention-free access to the hardware.

**Estimation procedure:** the same two-step regression procedure described above, but using the profiling engine running the model architecture on the target software `$s$` and hardware `$h$`, rather than measuring through a black-box API. The paper implements this using Megatron's Transformer and autoregressive inference functionality, with tensor model parallelism within a multi-GPU server when the model does not fit on a single GPU (the paper notes that "tensor model parallelism is optimal within a multi-GPU server since expensive all-to-all communication is limited to fast high-bandwidth NVLink"), and pipeline model parallelism for the largest model (Microsoft+NV/TNLG v2) when tensor parallelism alone would cause poor scaling.

**Hardware configuration details (Table 1):** each model is profiled on the minimum number of GPUs needed to fit its parameters in memory. For example, OpenAI/davinci (175B parameters, `$h = 12288$`, `$l = 96$`) requires 8×80GB-A100 GPUs, while AI21/J1-Large v1 (6.7B parameters, `$h = 4096$`, `$l = 32$`) fits on a single 80GB-A100 GPU. This choice of the *minimum* number of GPUs is a design decision: it represents the most cost-efficient serving configuration.

**Why this uniform-hardware approach rather than just raw API runtime:** by fixing `$s$` and `$h$`, the idealized runtime removes two major sources of non-comparability. First, it eliminates provider-specific software optimizations—if OpenAI has invested in custom CUDA kernels or advanced batching strategies that Megatron does not have, those advantages are stripped away, revealing the inherent computational cost of the model architecture. Second, it eliminates hardware differences—if one provider uses newer, faster GPUs or TPUs, the idealized runtime puts all models on the identical hardware type. The result is a metric that answers the question: "all else being equal, which model architecture is more efficient?"

**The "at least as fast" assumption:** the paper states that the idealized software `$s^*$` and hardware `$h^*$` should be "at least as fast as those used to back the original API." This ensures the inequality `$t_{\text{denoised}} \geq t_{\text{idealized}}$` holds—if the idealized stack were slower, the idealized runtime could be *higher* than the API's denoised runtime, which would violate the intended interpretation (that idealized runtime represents a lower bound achievable with known technology). In practice, the paper uses A100 GPUs because they are "the fastest widely available GPU right now" (as of late 2022), and Megatron because it is a highly optimized open-source implementation.

---

#### Denoised Runtime: Definition and Estimation

The denoised runtime `$t_{\text{denoised}}$` is an intermediate metric between raw and idealized runtime (Section 4.1). It uses the same hardware and software as the actual API (whatever that may be), but factors out the random performance variation `$\eta$`:

$$t_{\text{denoised}}^{m \text{ on API } a}(\text{prompt size } p, \text{ number of output tokens } o) = \text{prompt\_encoding\_time}_{\text{denoised}}^{m \text{ on API } a}(p) + (o - 1) \cdot g_{\text{denoised}}^{m \text{ on API } a}$$

**What it computes:** the runtime of model `$m$` served through API `$a$`, but with the random noise component `$\eta \geq 0$` removed—essentially, the runtime the API would achieve under zero load with no queuing delays or performance interference.

**Estimation procedure:** the same two-step regression, but instead of running a local profiling engine, the user sends synthetic queries with controlled prompt sizes and output token counts to the black-box API. The critical difference is that **multiple trials are run for each `$(p, o)$` configuration**, and the **minimum runtime** across trials is used in the regression rather than the mean or any individual trial. This is because the noise `$\eta \geq 0$` is always non-negative (it can only add latency, never subtract it), so the minimum across trials is the observation with the least noise—ideally `$\eta \approx 0$` if enough trials are run.

**Why the minimum rather than the mean:** using the mean would bake in the average queuing delay and load-dependent slowdown, which is exactly what the denoised metric aims to remove. The minimum provides an estimate of the "true" underlying runtime of the API's serving stack without contention. This is a standard technique in systems benchmarking for measuring uncontended performance.

**The inequality chain (Section 4.1):**

$$t_{\text{raw}}^{m \text{ on API } a}(p, o) \geq t_{\text{denoised}}^{m \text{ on API } a}(p, o) \geq t_{\text{idealized}}^{(m, s^*, h^*)}(p, o)$$

where `$s^*$` and `$h^*$` are assumed to be at least as fast as the API's software and hardware. This inequality decomposes the total observed latency into three additive (in expectation) components: raw = denoised + noise, denoised = idealized + (API optimizations delta if any, or zero if the idealized stack is faster). When denoised is *significantly larger* than idealized, it indicates the API provider is using slower hardware or software than the idealized stack. When denoised is *smaller*, it indicates the provider has optimizations beyond the idealized stack (the inequality is violated in that case, as the paper observes for OpenAI and AI21 models, where idealized runtime on Megatron+A100 is sometimes *higher* than denoised runtime—meaning those APIs use faster software or hardware than Megatron on A100 GPUs).

---

#### Cost-Aware Extensions: Idealized Dollar Cost and Idealized Energy Cost

The idealized runtime measures latency, but latency alone does not capture the full resource cost of serving a model. A larger model might achieve the same latency as a smaller model by using more accelerators in parallel (via model parallelism), but this consumes more hardware and energy. The paper defines two derived metrics that multiply idealized runtime by the number of accelerators and a per-accelerator scaling factor (Section 4.2):

**Idealized dollar cost:**

$$t_{\text{idealized}}^{(m, s, h)} (\text{secs}) \times n_{\text{accelerator } h} \times c_{\text{accelerator } h} (\$/\text{sec})$$

where `$n_{\text{accelerator } h}$` is the number of accelerators of type `$h$` used simultaneously to serve a single request (1 if the model fits on one GPU, >1 if model parallelism is required), and `$c_{\text{accelerator } h}$` is the per-unit-time rental cost of one such accelerator (e.g., the per-hour cost of an NVIDIA A100 GPU on AWS).

**What it computes:** the hypothetical cloud rental cost (in dollars or cents) to serve a single inference query on the specified hardware, assuming dedicated, contention-free access. This answers the question: "if I rent A100 GPUs on AWS and serve this model myself using Megatron, how much would each query cost?"

**Idealized energy cost:**

$$t_{\text{idealized}}^{(m, s, h)} (\text{secs}) \times n_{\text{accelerator } h} \times p_{\text{accelerator } h} (\text{W})$$

where `$p_{\text{accelerator } h}$` is the power draw (in watts) of one accelerator of type `$h$` under inference load. The result is energy consumption in watt-seconds (joules).

**What it computes:** the hypothetical energy consumed to serve a single inference query, which can be compared to the energy cost of training to assess the break-even point for amortizing training energy (e.g., "how many inference queries before the total inference energy exceeds the training energy?").

**Why these metrics are derived from idealized runtime specifically:** the paper notes that these cost-aware extensions "cannot similarly modify the denoised runtime since we do not know the type of hardware and the number of chips used by the model provider." The idealized runtime, by contrast, uses known hardware and a known accelerator count (chosen as the minimum needed to serve the model), making the multiplication factors well-defined. The dollar and energy costs are thus "idealized" in a double sense: they use idealized runtime (uniform software/hardware, no contention) and they assume known, publicly available pricing and power characteristics for the idealized hardware.

**The design choice of using minimum GPUs:** Table 1 specifies, for each model, the minimum number and type of GPUs needed. For example, OpenAI/davinci uses 8×80GB-A100 GPUs, while EleutherAI/GPT-J uses 1×80GB-A100. Using the minimum number represents the most cost-efficient configuration—adding more GPUs could reduce latency (through additional parallelism) but would increase the per-query cost. The idealized dollar cost is thus a *lower bound* on achievable cost given the hardware type, not a prediction of what any particular provider actually spends (they might use more GPUs for lower latency, or different hardware entirely).

---

#### Hardware Comparison Methodology

The parametric estimation procedure enables efficient comparison of different hardware and software stacks for the same model without re-running entire benchmarks (Section 5.3). The procedure:
1. Profile the model architecture on hardware configuration A (e.g., Megatron on A100 GPUs) using the `$|P| \times |O|$` grid, yielding `$\text{prompt\_encoding\_time}_A(p)$` and `$g_A$`.
2. Profile the model architecture on hardware configuration B (e.g., Megatron on V100 GPUs) using the same grid, yielding `$\text{prompt\_encoding\_time}_B(p)$` and `$g_B$`.
3. For any benchmark query with known `$(p, o)$`, the speedup of A over B is simply `$t_B(p, o) / t_A(p, o)$`.

**Why this avoids exhaustive per-benchmark profiling:** once the parametric parameters are estimated for a hardware configuration, they apply to *all* queries in *all* benchmarks, because the parametric form `$t(p, o)$` is universal for autoregressive Transformer inference. The profiling investment is amortized across arbitrary downstream analyses. The paper contrasts this with the alternative of timing every query in every benchmark on both hardware configurations, which would scale with the number of queries.

---

#### Summary of Design Choices and Their Justifications

- **Parametric form derived from FLOP counts rather than purely empirical curve-fitting:** provides theoretical grounding and explains *why* the form is linear in `$o$` and piecewise linear in `$p$`, which builds confidence that the form will generalize to new models and hardware.
- **Two-phase additive decomposition (`$t = \text{PE}(p) + (o-1)g$`):** mirrors the actual execution structure of autoregressive inference and enables the efficient grid-based profiling procedure.
- **Megatron on A100 as the default idealized stack:** A100 GPUs were the fastest widely available GPUs at the time; Megatron is a well-optimized, publicly described Transformer implementation. Both are accessible to researchers who want to replicate or extend the methodology.
- **Minimum GPUs per model:** represents the most cost-efficient serving configuration on the given hardware; avoids biasing comparisons by assuming providers use unnecessarily many accelerators.
- **Minimum-over-trials for denoised runtime:** standard technique for measuring uncontended performance in the presence of one-sided positive noise, justified by the `$\eta \geq 0$` property of queuing delays.
- **Linear interpolation for unseen prompt sizes:** justified by the piecewise linearity of `$\text{prompt\_encoding\_time}(p)$`; within each linear piece, linear interpolation is exact, and the paper's chosen profiling points (multiples of 256 or 512 tokens) are spaced to capture the piecewise structure.
- **Cost metrics derived from idealized runtime only:** reflects the lack of information about API providers' actual hardware configurations; the idealized cost provides a standardized lower-bound estimate that is comparable across models.

## 4. Key Insights and Innovations

### Innovation 1: A Formal Hierarchy Decomposing API Latency Into Non-Comparable Components

The paper's most fundamental intellectual move is not proposing a new metric per se, but constructing a **formal inequality chain** that isolates three distinct sources of latency variation between black-box APIs: performance noise, software/hardware optimizations, and inherent model computational cost:

$$t_{\text{raw}} \geq t_{\text{denoised}} \geq t_{\text{idealized}}$$

What makes this decomposition conceptually novel—rather than just a practical convenience—is that it identifies latency not as a single number to be minimized, but as a **composite of factors with different owners and different policy implications**. Prior benchmarking efforts (BIG-Bench, HELM, model announcement papers) implicitly treated raw runtime as a direct proxy for model efficiency. The paper shows this is wrong not just empirically but structurally: the raw runtime gap between two models can arise from any combination of (a) the API provider having better caching/infrastructure, (b) one provider having worse load management, or (c) one model architecture being genuinely more efficient. Without a decomposition, there is no way to attribute improvements.

This is a fundamental reframing, not an incremental refinement. The field's prior approaches to efficiency comparison—parameter count, FLOP count, raw API runtime—all collapse these distinct factors into a single scalar. The paper's hierarchy instead treats them as **orthogonal axes that should be analyzed independently**, analogous to how the program analysis community distinguishes between algorithmic complexity and implementation efficiency. The inequality itself is definitional (noise is non-negative by construction; idealized hardware/software is chosen to be at least as fast as the API's), but the *diagnostic power* it provides is new: when the denoised runtime is significantly larger than the idealized runtime, the API's hardware/software is slower than the idealized stack (e.g., using older GPUs or less optimized kernels); when the denoised runtime is *smaller* than the idealized runtime—as the paper observes for OpenAI models 64.2% of the time and AI21 models 15.7% of the time (Section 5.2, Figure 7b)—the API has optimizations beyond the idealized reference implementation. This last case is particularly important because it means `t_idealized` is not a lower bound in practice for the most heavily-engineered APIs—it serves instead as a **baseline for what's achievable with publicly-known techniques**, against which private optimizations can be measured.

The denoised runtime itself is a quieter but equally important innovation in this hierarchy. By using the **minimum across trials** rather than the mean, the regression procedure exploits the one-sided nature of queuing noise (`\eta \geq 0` always adds latency, never subtracts it) to estimate uncontended performance without needing to know the API's server architecture, load patterns, or scheduling policy. This is a simple technique but its justification—the parametric form makes the noise term identifiable as purely additive—depends on the paper's central runtime parameterization. Prior work on benchmarking web APIs typically either ignored noise or averaged it away; the paper's approach of explicitly modeling it as a positive random variable and removing it via minimum-over-trials estimation provides a statistical foundation for fair comparison that was absent from earlier ad-hoc API benchmarking.

### Innovation 2: The Autoregressive Inference Runtime Parameterization as a Profiling Multiplier

Section 3 of the prior-sections analysis has covered the derivation and mechanics of `t(p, o) = prompt_encoding_time(p) + (o-1) * g`. The innovation worth surfacing here is the **implications of this parameterization for how the field should think about inference cost measurement**, not the parameterization itself.

The key conceptual shift is from treating inference runtime as a **per-benchmark measurement problem** to treating it as a **model-level property that can be estimated once and reused**. Specifically: the parametric form shows that a model's inference behavior on a given hardware/software stack is fully characterized by `|P| + 1` parameters (prompt encoding times at `|P|` prompt sizes, plus one per-token generation time `g`), regardless of how many distinct queries the model will ever serve. This means that benchmarking 10 models on 4 benchmarks with hundreds of queries each requires profiling `10 * (|P| * |O|)` configuration queries—a few hundred—rather than `10 * 4 * (number of benchmark queries)` individual measurements. The paper's claim of "profil[ing] on the order of hours (< 2 hours for most models) once, compared to hours per benchmark for exhaustive profiling" (Section 5.3) is the practical consequence, but the intellectual contribution is the recognition that **inference runtime is separable from task content** in a way that prior benchmarking approaches did not exploit.

This separability distinguishes autoregressive Transformer inference from the inference of both traditional ML models and other generative architectures. For a ResNet-50, inference runtime is constant—there is no concept of a query having variable "length" that affects computational cost. For autoregressive Transformers, inference time varies dramatically with both prompt length and output length, making per-benchmark measurement expensive. The paper shows that this variability, counter to intuition, is actually **highly structured and low-dimensional**: once you know how a model performs at a handful of prompt sizes and output lengths, you can predict its runtime for any combination within the profiled range. This transforms inference cost estimation from a per-task chore into a **model-level specification** that could, in principle, be published alongside model architecture details.

A subtler insight embedded in the parameterization is the **distinction between prompt encoding and token generation as different computational regimes**. Prior work on Transformer inference efficiency (e.g., Narayanan et al., 2021) analyzed FLOP counts but did not use the analysis to build a practical measurement methodology. The paper shows that these two phases have fundamentally different scaling properties (piecewise linear in `p` vs. linear in `o`) and different sensitivities to hardware characteristics (prompt encoding throughput varies with `p` due to arithmetic intensity transitions; token generation throughput is constant). This matters for practical deployment decisions: an application with long prompts but short outputs will be bottlenecked by prompt encoding performance, while a chatbot generating long responses will be bottlenecked by per-token generation time. The parameterization makes these distinctions visible and quantifiable, whereas a single "average runtime per query" number would conflate them.

### Innovation 3: The Constructive Use of Provider Opacity—Measuring Models Without Weights

The paper makes a methodological contribution that is easy to overlook: it demonstrates that **meaningful inference efficiency comparisons can be made even when model weights are completely inaccessible**, using only publicly available architectural hyperparameters (hidden size, number of layers, number of attention heads). This is not an obvious claim. One might reasonably assume that without access to trained weights, you cannot measure inference cost because you cannot actually run the model. The paper shows that for runtime measurement, **weights are irrelevant**—the computational graph and tensor shapes are fully determined by the architecture, and runtime on a given hardware/software stack depends only on those shapes, not on the specific floating-point values stored in the matrices.

This insight has implications beyond the specific methodology described. It means that **model creators can, in principle, report idealized runtime alongside model architecture** without exposing weights, enabling independent verification and comparison. It means that **researchers studying capability-efficiency tradeoffs can include models they do not host or have special access to**, as long as architectural details are public. The paper applies this to ten models including commercial black-box APIs (OpenAI/davinci, AI21/J1-Jumbo v1), privately-held models where research access was granted (Anthropic/v4-s3, Microsoft+NV/TNLG v2), and open-source models run through a third-party API (Yandex/YaLM, BigScience/BLOOM via Together). The methodology's ability to span this range of access models—from fully open to fully proprietary—is a direct consequence of the weights-are-irrelevant property.

This constructively subverts a common defense against efficiency transparency. Providers often claim that revealing inference performance characteristics would expose proprietary optimizations or competitive advantages. The paper shows that **providers need not expose anything about their actual serving infrastructure** for fair model-level comparisons to be made—only the model architecture, which many providers already publish (all models in Table 1 have publicly available `h`, `l`, and `n` values). The idealized runtime explicitly strips away all provider-specific optimizations, so reporting it reveals nothing about how the provider actually serves the model, only about the inherent computational cost of the architecture. This creates a path toward transparency that does not require providers to compromise their infrastructure secrets—a pragmatic resolution to a genuine tension in the ecosystem.

### Innovation 4: The Empirical Refutation of Raw Runtime as a Valid Cross-Provider Efficiency Metric

The most consequential finding in the paper is not methodological but empirical: **the model that wins on raw runtime is not the model that wins on architectural efficiency**, and the misattribution is systematic rather than random. The specific finding—"the `OpenAI/davinci` model appears in the Pareto frontier for each benchmark when using raw runtimes but not the idealized metrics" (Section 5.4, Figure 9)—functions as an existence proof that the concern motivating the paper is not hypothetical. It is *not* the case that raw runtime roughly correlates with idealized runtime and provider optimizations add small, random perturbations. Instead, the optimizations are large enough and systematic enough to **change which models appear on the efficiency frontier entirely**.

Figure 9 presents this argument across four diverse benchmarks (sentiment analysis, question answering, classification) and six efficiency metrics (model size, FLOPs, raw runtime, denoised runtime, idealized runtime, idealized cost). The visual pattern is striking: in the raw runtime row, `OpenAI/davinci` and `AI21/J1-Jumbo v1` frequently appear as Pareto-optimal squares. In the idealized runtime row, the Pareto frontier shifts—`BigScience/BLOOM`, `Yandex/YaLM`, and `Microsoft+NV/TNLG v2` gain prominence relative to the commercial API models. This reshuffling is the paper's core empirical contribution: it demonstrates that **the choice of efficiency metric determines which models are considered "best" in a capability-efficiency tradeoff**, and that raw runtime—the metric practitioners naturally reach for—is systematically misleading for the purpose of comparing model architectures.

The significance of this finding goes beyond the specific models studied. It implies that every capability-efficiency tradeoff analysis conducted using raw API runtimes (or, worse, model size) is vulnerable to the same confounding. If a paper claims "Model A achieves higher accuracy than Model B at lower inference cost" based on raw API timings, the claim is ambiguous: the cost advantage might come from the serving infrastructure, not the model. This is not merely an academic concern. It affects:
- **Model selection decisions:** an organization choosing between API providers based on published benchmarks might select a provider whose apparent efficiency advantage is due to better infrastructure, only to find that advantage disappears when the provider's infrastructure changes or when the organization eventually moves to self-hosting.
- **Architecture research:** if researchers evaluating new architectures compare against baselines through differently-optimized APIs, they may incorrectly conclude that an architectural innovation improves efficiency when the improvement is actually from the serving stack.
- **Scaling law validation:** efforts to fit curves relating model size/capability to inference cost will produce different coefficients depending on whether raw or idealized runtime is used, potentially affecting conclusions about whether scaling continues to be cost-effective.

The finding that AI21/J1-Grande v1 (17B parameters) sometimes achieves *worse* raw runtime than AI21/J1-Jumbo v1 (178B parameters, ~10× larger) due to higher performance variance (coefficient of variation ~0.55 vs. ~0.2; Section 3.5, Figure 5) provides a particularly stark illustration. No one would argue the smaller model is *inherently* slower—the reversal is purely an artifact of server-side conditions—yet a naive benchmark would report exactly that conclusion.

### Innovation 5: Separating Model Architecture Design from Deployment Engineering as Distinct Optimization Axes

The paper's unified framework implicitly introduces a conceptual distinction that the field had not previously articulated with this clarity: **model architecture efficiency and deployment engineering efficiency are different optimization problems with different stakeholders, timelines, and evaluation criteria**, and they should be measured separately because improvements in one can mask deficiencies in the other.

The idealized runtime isolates model architecture efficiency. It answers: given the tensor shapes and compute patterns this model requires, how fast *could* it run on standardized hardware with a reference implementation? This is what model architects control—choices about hidden size, layer count, attention head configuration, sparsity, mixture-of-experts routing, etc. Improvements to idealized runtime come from changes to the model architecture itself and persist regardless of how the model is deployed.

The denoised-to-idealized gap captures deployment engineering efficiency. It answers: how much faster is this API's serving stack compared to the reference implementation? This is what infrastructure engineers control—choices about custom CUDA kernels, model parallelism strategies, query batching, KV-cache management, speculative decoding, quantization, etc. Improvements here are independent of model architecture and can benefit *any* model served through that infrastructure.

The raw-to-denoised gap captures operational quality. It answers: how much latency does load and contention add? This is what SRE teams and capacity planners control—provisioning, autoscaling, load balancing, request prioritization.

This tripartite decomposition makes visible a perverse dynamic that the paper's results expose but do not explicitly name: **a model with a mediocre architecture but exceptional deployment engineering can appear more efficient than a model with a better architecture but average engineering**. The OpenAI/davinci Pareto-frontier result is exactly this pattern—the model looks great on raw runtime because OpenAI's infrastructure is highly optimized, but under idealized conditions where every model gets the same software/hardware, the architectural efficiency is unexceptional. This is not a criticism of OpenAI (investing in infrastructure is entirely legitimate) but a demonstration that **conflating these dimensions leads to incorrect conclusions about the models themselves**.

The practical implication is a kind of **efficiency attribution discipline**: any claim that "Model X is more efficient than Model Y" should be accompanied by an analysis of *why*—is it because of the architecture, the deployment engineering, or the operational conditions? The idealized runtime methodology provides a concrete, replicable procedure for isolating the architectural contribution, enabling the community to move from "which API is fastest?" (a question about infrastructure) to "which model design is most efficient?" (a question about architecture)—two questions that prior benchmarking frameworks did not clearly separate.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The experiments use four diverse tasks drawn from the HELM benchmark (Liang et al., 2022): IMDB (a sentiment analysis task), MMLU (college chemistry subset; Hendrycks et al., 2020), BoolQ (a question answering task; Clark et al., 2019), and RAFT (terms of service; a classification task; Alex et al., 2021). The paper evaluates each of the ten models on all four tasks, reporting the accuracy averaged over all instances in each scenario. The choice of these four specific tasks is not extensively justified beyond representing diverse NLP scenarios—sentiment analysis, factual QA, yes/no QA, and classification—providing a cross-section of capabilities rather than a single-axis comparison. The paper evaluates in the "few-shot evaluation setting, similar to other benchmarks for LLMs like BIG-Bench and HELM" (Section 5.1), but does not specify the exact number of few-shot examples used per task (this information would be found in the HELM benchmark specification).

- **Base model(s).** Ten state-of-the-art autoregressive Transformer LLMs are evaluated, spanning roughly two orders of magnitude in parameter count: EleutherAI/GPT-J (6B), AI21/J1-Large v1 (6.7B), AI21/J1-Grande v1 (17B), Cohere/XL v20220609 (52B), Anthropic/v4-s3 (52B), Yandex/YaLM (100B), OpenAI/davinci (175B), BigScience/BLOOM (176B), AI21/J1-Jumbo v1 (178B), and Microsoft+NV/TNLG v2 (530B). Key architectural hyperparameters (hidden size `h`, number of layers `l`, number of attention heads `n`) are listed in Table 1. The models span different access models: some were public via commercial APIs (OpenAI, AI21, Cohere), some were private but the model owner provided research access (Anthropic, Microsoft+NV), and some were open-source and run through the Together Open Models API (GPT-J, YaLM, BLOOM). The paper explicitly excludes "models with publicly unavailable model architecture details (including OpenAI's ChatGPT and GPT-4)" (Section 5.1), since the idealized runtime estimation requires known values of `h`, `l`, and `n`.

- **Metrics.** The primary efficiency metrics on the x-axes of the tradeoff graphs (Figure 9) are:
  1. **Model size** (billions of parameters)
  2. **Number of floating-point operations (FLOPs)** for the forward pass
  3. **Raw runtime** (seconds) as returned by the black-box API
  4. **Denoised runtime** (seconds) estimated via minimum-over-trials regression from API calls
  5. **Idealized runtime** (seconds) estimated via profiling on Megatron + NVIDIA A100 GPUs
  6. **Idealized cost** (cents) computed as `t_idealized × n_accelerator × c_accelerator`
  
  The capability metric on the y-axis is **accuracy** on the target task, averaged over all instances in a scenario (Section 5.4). For the cross-benchmark ranking analysis (Figure 10), the paper defines two objective functions combining accuracy and idealized runtime: `f1 = accuracy / idealized_runtime` and `f2 = accuracy / log(idealized_runtime)`, the latter de-emphasizing the importance of inference efficiency relative to accuracy.

- **Baselines.** The paper does not compare against a prior inference efficiency metric in the traditional sense—there is no accepted standard for this purpose. Instead, the paper's contribution *is* the metrics themselves (idealized and denoised runtime), and the evaluation consists of demonstrating that these proposed metrics produce different efficiency-capability tradeoff conclusions than the commonly-used proxies:
  1. **Model size** (parameter count): the dominant proxy in scaling laws work (Kaplan et al., 2020) and model announcement papers.
  2. **FLOPs count** (per-query floating-point operations): used as an architecture-aware alternative to parameter count.
  3. **Raw API runtime**: what practitioners actually measure and what prior API benchmarking implicitly relied on.
  
  The paper does not claim any of these are invalid—only that they answer *different questions* than architectural efficiency, and that using them for cross-model architectural comparison produces misleading conclusions. The "baseline" is therefore the existing practice that the proposed methodology aims to improve upon.

- **Generation budget / compute accounting.** There is no explicit compute budget comparison across models in the sense of matching FLOPs or generation counts. The methodology is purely a *measurement* framework—it estimates what runtime *would be* for each model on standardized hardware—rather than a strategy for allocating inference compute. The "budget" in the profiling procedure is the number of `(p, o)` configuration queries used to fit the parametric model: for each model and target system, a grid of prompt sizes `P = {1, 256, 512, 1024, 1536}` (for models with max context length 2048) and output token counts (e.g., `o ∈ {1, 2, 4, 8, 16, 32, 48, 64}` as shown in Figure 3) is profiled, requiring on the order of `|P| × |O| ≈ 5 × 8 = 40` measurements per model-hardware pairing. For hardware comparison (Figure 8), the same grid is profiled on both A100 and V100 GPUs for each model, requiring on the order of hours (< 2 hours for most models) of profiling once, rather than hours per benchmark for exhaustive per-query timing (Section 5.3).

- **Cross-validation / statistical protocol.** The paper does not employ cross-validation in the model-selection sense, since there is no training or hyperparameter optimization occurring. The key statistical procedures are:
  1. **Linear regression for parametric fitting**: for each model and prompt size, runtimes are measured at multiple `o` values and fit via linear regression. The paper reports `R^2 > 0.999` for all models on dedicated hardware (Section 3.2) and `R^2` ranging from 0.917 to 0.997 for black-box APIs (Table 2), confirming the linearity assumption.
  2. **Minimum-over-trials for denoised runtime**: multiple trials are run for each `(p, o)` configuration when profiling through black-box APIs, and the minimum runtime across trials is used in the regression to estimate uncontended performance. The paper quantifies the per-trial variance: AI21/J1-Grande v1 has an average coefficient of variation of approximately 0.55 compared to ~0.2 for other AI21 models, and outlier points can show up to 3× higher latency even for models with lower spread (Section 3.5).
  3. **Pareto frontier identification**: for each efficiency-capability scatter plot (Figure 9), data points on the Pareto frontier (models not dominated by any other model in both accuracy and the efficiency metric) are shown as squares with a dotted connecting line, while dominated models are shown as circles. This is a standard visualization technique, not a statistical test, and the paper does not report confidence intervals on frontier membership.

### Main Quantitative Results

The experimental results section investigates three primary questions stated in Section 5: (1) Is the proposed estimation procedure accurate? (2) Is it efficient compared to exhaustive profiling? (3) Can it reveal interesting insights about efficiency-capability tradeoffs? The results are organized around these questions, with the tradeoff analysis (question 3) receiving the bulk of the attention.

#### Accuracy of the Runtime Estimation Procedure

**Headline result: The parametric form `t(p, o) = prompt_encoding_time(p) + (o-1) · g` fits measured runtimes with `R^2 > 0.999` on dedicated hardware and `R^2 ≥ 0.917` through black-box APIs, confirming that autoregressive Transformer inference runtime decomposes cleanly into a piecewise-linear prompt encoding component and a linear token generation component.**

**Dedicated hardware validation (Figures 3, 4).** Using Megatron on NVIDIA A100 GPUs, the paper profiles four representative models (Anthropic/v4-s3, AI21/J1-Jumbo v1, OpenAI/davinci, Microsoft+NV/TNLG v2) across a range of prompt sizes (1, 512, 1024, 1536 tokens) and output token counts (1 through 64 tokens). Figure 3 shows that for each fixed prompt size, runtime versus number of output tokens exhibits an extremely strong linear relationship—the paper reports `R^2` values "very close to 1.0 (> 0.999) for all models" (Section 3.2). This confirms both that `g` is constant (per-token generation throughput `throughput_og` is independent of the token being generated) and that the additive decomposition holds. The slopes vary across models—ranging from roughly 0.02 seconds per output token for the faster models at small prompt sizes to roughly 0.08–0.10 seconds per output token for the slower models at large prompt sizes (extracted visually from Figure 3)—reflecting differences in hidden size, layer count, and the effectiveness of tensor model parallelism.

Figure 4 validates the piecewise linearity of `prompt_encoding_time(p)`. The paper observes that runtime and prompt size show a "roughly linear relationship, especially at large prompt sizes" but notes that "this linear relationship breaks down at smaller prompt sizes." For example, for OpenAI/davinci (Figure 4c), the curve shows slight upward curvature from `p = 1` to `p = 512` before becoming essentially linear from `p = 512` to `p = 1920`. This is consistent with the arithmetic intensity explanation: at small `p`, the matrix multiplications are too small to saturate the GPU's compute units (the computation is memory-bandwidth-bound), and as `p` grows, throughput increases until the computation becomes compute-bound and throughput plateaus, producing the transition from super-linear to linear runtime scaling.

**Black-box API validation (Table 2, Figure 5).** Applying the same regression methodology to black-box API calls, the paper reports `R^2` values: OpenAI/davinci (0.985), AI21/J1-Large v1 (0.990), AI21/J1-Grande v1 (0.917), AI21/J1-Jumbo v1 (0.995), Cohere/XL v20220609 (0.997), and Anthropic/v4-s3 (0.924). The lower `R^2` for AI21/J1-Grande v1 and Anthropic/v4-s3 is attributed to higher performance variance. Figure 5 visualizes this variance: per-trial runtimes for 10 trials at each `(p=512, o)` configuration show that AI21/J1-Grande v1 has substantially larger spread (runtimes ranging from approximately 0.5 to 3.5 seconds at `o = 64`) compared to AI21/J1-Large v1 (tightly clustered around 0.5 seconds at `o = 64`) or AI21/J1-Jumbo v1 (clustered around 1.0–1.5 seconds at `o = 64`). The paper quantifies this as "an average coefficient of variation of about 0.55 compared to much smaller coefficients of variation (~0.2) for the other AI21 models."

**The inequality chain validation (Figure 7).** Figure 7a compares denoised runtime to raw runtime across all profiled queries. The paper reports that "96.6% of points" fall below the `y = x` line, meaning raw runtime is greater than denoised runtime in the vast majority of cases. This is expected from the construction (denoised runtime removes positive noise), and the 3.4% of points above the line may reflect cases where the minimum-over-trials estimate is noisy or where the underlying runtime has drift. Figure 7b compares idealized runtime (Megatron + A100) to denoised runtime. Here the pattern is model-provider-dependent: "For AI21 Labs models, idealized runtimes are greater than denoised runtimes 15.7% of the time. For OpenAI models, idealized runtimes are greater than denoised runtimes 64.2% of the time. For all other models, idealized runtimes are always lower than the denoised runtimes" (Section 5.2). This is the paper's key diagnostic finding: OpenAI's and (to a lesser extent) AI21's APIs achieve runtimes *faster* than the reference Megatron+A100 implementation, indicating provider-specific optimizations beyond what the open-source stack provides, while other providers' APIs are slower than the idealized reference, suggesting they use slower hardware or software than the idealized baseline.

**Estimated parameters (Table 3).** The paper reports the learned `prompt_encoding_time(p)` at `p = 512/1024/1536` and per-output-token generation time `g` for both `t_idealized` (Megatron, A100) and `t_denoised` for several models. For OpenAI/davinci, the idealized prompt encoding time at `p = 512` is 0.178 seconds while the denoised version is only 0.045 seconds—approximately 4× faster—and the idealized per-token generation time is 0.081 seconds vs. 0.030 seconds denoised (roughly 2.7× faster). This means OpenAI's API achieves roughly 2.5–4× speedup over Megatron on A100 GPUs on the same model architecture, confirming substantial software/hardware optimizations beyond the reference implementation. For AI21/J1-Jumbo v1, the pattern is more mixed: denoised per-token generation time (0.042 seconds) is faster than idealized (0.064 seconds), but denoised prompt encoding times are sometimes *slower* (0.268 vs. 0.164 seconds at `p = 512`), suggesting AI21's optimizations are more effective for the token generation phase than for prompt encoding.

#### Efficiency of the Profiling Methodology

**Headline result: The parametric estimation procedure requires profiling on the order of hours (< 2 hours for most models) once per model-hardware pairing, compared to hours per benchmark for exhaustive per-query timing, enabling efficient comparison of alternative hardware and software stacks.**

**Hardware comparison (Figure 8).** The paper demonstrates the methodology's efficiency by comparing idealized metrics estimated on NVIDIA A100 GPUs versus the older NVIDIA V100 GPUs for all ten models across all four benchmarks. Each subplot in Figure 8 shows two bar charts side-by-side: idealized runtime (top) and idealized cost (bottom), with A100 estimates on the left and V100 estimates on the right. The comparison reveals that "V100 GPUs are both slower and more expensive" (Section 5.3) for most models. This counterintuitive result—older hardware being *more expensive* despite lower per-hour rental costs—arises because "we often have to use double the GPUs to fit the model parameters in GPU memory, since V100 GPUs only have 32GB of device memory compared to 80GB on the A100 GPUs." For example, models that fit on a single A100 GPU (e.g., AI21/J1-Large v1 at 6.7B parameters) might require 2× V100 GPUs, doubling the accelerator count `n_accelerator` and therefore the idealized cost despite the lower per-GPU price.

The key methodological point is that this hardware comparison across all ten models and all four benchmarks required only "profil[ing] on the order of hours (< 2 hours for most models, depending on the number of `(p, o)` values profiled) once, compared to hours per benchmark (depending on number of queries in the benchmark) for exhaustive profiling" (Section 5.3). Once the parametric parameters `prompt_encoding_time(p)` and `g` are estimated for a given model on a given hardware/software stack, they can be applied to predict runtime for any query in any benchmark without additional measurement.

**Software stack comparison capability.** The paper notes that the same methodology can be applied to evaluate different software stacks: "We can perform similar analysis for different software stacks as well (e.g., Nvidia Triton or Megatron with FlashAttention (Dao et al., 2022) enabled)" (Section 5.3). While no such analysis is presented in the paper, the claim is that the profiling overhead is the same—`|P| × |O|` measurements—regardless of the benchmark the results will be applied to. This positions the methodology as a general-purpose tool for hardware-software co-design evaluation, not merely for cross-model comparison.

#### Efficiency-Capability Tradeoff Analysis

**Headline result: The choice of efficiency metric changes which models appear on the Pareto frontier. OpenAI/davinci appears on the raw runtime frontier for all four benchmarks but consistently falls off under idealized runtime and idealized cost, revealing that its apparent efficiency advantage is largely attributable to API optimizations rather than inherent model architecture efficiency.**

This is the paper's central empirical finding and is presented in Figure 9, which shows six rows of scatter plots (one per efficiency metric) × four columns (one per benchmark). Each subplot places accuracy on the y-axis and the efficiency metric on the x-axis. Models on the Pareto frontier (not dominated by any other model in that metric) are shown as squares connected by a dotted line; all other models are circles.

**The raw runtime row reveals the optimization illusion.** Looking across the four benchmarks in the raw runtime row (third row of Figure 9):

- **IMDB (Figure 9a, third row):** OpenAI/davinci sits squarely on the Pareto frontier alongside BigScience/BLOOM and EleutherAI/GPT-J, achieving approximately 0.86 accuracy at roughly 0.2 seconds—significantly faster than similarly-accurate models like Yandex/YaLM (~0.75 accuracy at ~1.0 seconds) or AI21/J1-Jumbo v1 (~0.87 accuracy at ~0.7 seconds).
- **MMLU college chemistry (Figure 9b, third row):** OpenAI/davinci dominates: it achieves ~0.28 accuracy at ~0.15 seconds, the highest accuracy and among the lowest runtimes, making it the sole Pareto-optimal model.
- **RAFT terms of service (Figure 9c, third row):** OpenAI/davinci (~0.82 accuracy at ~0.2 seconds) is on the frontier with BigScience/BLOOM (~0.75 accuracy at ~0.15 seconds).
- **BoolQ (Figure 9d, third row):** OpenAI/davinci (~0.78 accuracy at ~0.3 seconds) is again Pareto-optimal, alongside Anthropic/v4-s3 (~0.78 accuracy at ~0.15 seconds—faster but not meaningfully more accurate).

Across all four benchmarks, OpenAI/davinci appears as a Pareto-optimal model when evaluated by raw runtime. A practitioner or researcher using raw API latency as their efficiency metric would conclude that this model offers an excellent capability-efficiency tradeoff.

**The idealized runtime row reshuffles the frontier.** Looking at the same benchmarks in the idealized runtime row (fifth row of Figure 9):

- **IMDB:** OpenAI/davinci (~0.86 accuracy at ~0.35 seconds) is now dominated by BigScience/BLOOM (~0.94 accuracy at ~0.12 seconds—more accurate *and* faster) and Yandex/YaLM (~0.75 accuracy at ~0.05 seconds—slightly less accurate but dramatically faster). OpenAI/davinci is not on the frontier.
- **MMLU college chemistry:** OpenAI/davinci (~0.28 accuracy at ~0.35 seconds) is no longer Pareto-optimal. Instead, BigScience/BLOOM (~0.24 accuracy at ~0.12 seconds) and AI21/J1-Jumbo v1 (~0.26 accuracy at ~0.30 seconds) define the frontier, with Microsoft+NV/TNLG v2 (~0.25 accuracy at ~0.25 seconds) also competitive.
- **RAFT:** OpenAI/davinci (~0.82 accuracy at ~0.35 seconds) is dominated by BigScience/BLOOM (~0.75 accuracy at ~0.12 seconds—faster and only slightly less accurate) and Yandex/YaLM (~0.70 accuracy at ~0.05 seconds). Again, OpenAI/davinci drops off the frontier.
- **BoolQ:** OpenAI/davinci (~0.78 accuracy at ~0.35 seconds) falls off the frontier; Anthropic/v4-s3 (~0.78 accuracy at ~0.12 seconds) and BigScience/BLOOM (~0.65 accuracy at ~0.10 seconds) are Pareto-optimal.

The pattern is consistent: **under idealized runtime, OpenAI/davinci is never on the Pareto frontier for any of the four benchmarks**, despite being on the raw runtime frontier for all four. The efficiency that appeared to belong to the model architecture actually belongs to OpenAI's serving infrastructure.

**The idealized cost row (bottom row) shows additional reshuffling.** Because idealized cost multiplies idealized runtime by the number of accelerators (Table 1: OpenAI/davinci requires 8× A100 GPUs while BigScience/BLOOM also requires 8× A100 GPUs), the frontier shifts further:

- **IMDB:** BigScience/BLOOM (~0.94 accuracy at ~0.4 cents) dominates; Yandex/YaLM (~0.75 accuracy at ~0.1 cents, requiring only 4 GPUs) appears on the frontier.
- **MMLU:** The frontier is Microsoft+NV/TNLG v2 (~0.25 accuracy at ~0.35 cents), AI21/J1-Jumbo v1 (~0.26 accuracy at ~0.65 cents), and BigScience/BLOOM (~0.24 accuracy at ~0.25 cents). The large models with high GPU counts are penalized relative to smaller models.
- **RAFT:** Yandex/YaLM (~0.70 accuracy at ~0.1 cents) and BigScience/BLOOM (~0.75 accuracy at ~0.4 cents) are on the frontier.
- **BoolQ:** Anthropic/v4-s3 (~0.78 accuracy at ~0.25 cents) and BigScience/BLOOM (~0.65 accuracy at ~0.4 cents) define the frontier.

**Quantitative impact of metric choice on frontier composition.** The paper does not provide a table or summary statistic counting how many models are on each frontier under each metric—a missed opportunity. However, the visual evidence in Figure 9 is clear: BigScience/BLOOM, Yandex/YaLM, and Anthropic/v4-s3 gain prominence under idealized metrics, while OpenAI/davinci loses its Pareto-optimal status entirely. The paper explicitly states: "This suggests that the OpenAI API implementation is more optimized than others: this could be due to a number of factors, such as query caching or better resilience to high load" (Section 5.4).

**The FLOPs and model size rows provide intermediate comparisons.** The second row (FLOPs) shows that FLOP count as an efficiency metric produces different frontiers than either raw or idealized runtime. For example, on IMDB, Yandex/YaLM appears highly efficient by FLOP count (fewer FLOPs than similarly-accurate models) and also by idealized runtime, but BigScience/BLOOM is more efficient by idealized runtime than by FLOPs alone—the paper attributes this to BLOOM's "more thorough search through model architectures for minimum runtime with a given number of floating-point operations in the forward pass" (Section 5.4, citing Scao et al., 2022). This is a concrete demonstration of why FLOPs ≠ runtime: architectural choices that produce the same FLOP count can have different hardware utilization efficiency, captured by idealized runtime but missed by FLOP counting.

**Cross-benchmark ranking analysis (Figure 10).** Figure 10 shows each model's rank when ordered by an objective function combining accuracy and idealized runtime across the four benchmarks. Under `f1 = accuracy / idealized_runtime` (Figure 10a), Yandex/YaLM consistently ranks 1st across three benchmarks (RAFT, BoolQ, IMDB) and 3rd on MMLU, reflecting its strong combination of moderate accuracy and very low idealized runtime. BigScience/BLOOM ranks 2nd or 3rd across all benchmarks. OpenAI/davinci ranks 4th–7th, never in the top 3.

Under `f2 = accuracy / log(idealized_runtime)` (Figure 10b), which de-emphasizes runtime differences by applying a log transformation, the rankings change notably: OpenAI/davinci rises to rank 1st on MMLU and 2nd–3rd on other benchmarks, while Microsoft+NV/TNLG v2—which had poor rankings under `f1` due to high runtime—improves significantly. This sensitivity analysis demonstrates that the relative ordering of models depends on how strongly the objective function weights efficiency versus accuracy. The paper's point is not that one objective function is correct, but that **"none of the models we evaluated dominated across scenarios and objective functions"** (Section 5.4), and the choice of metric and objective together determine which models appear best.

**The AI21 variance anomaly (Figure 5, discussed in Section 5.4).** A specific finding highlighted in the tradeoff analysis is that "AI21/J1-Grande v1 often achieves worse raw runtime than AI21/J1-Jumbo v1 despite having 10× fewer parameters, since the Grande model experiences higher performance variance (Figure 5). The idealized metrics factor out run-to-run variance, making it easier to see the true efficiency-capability tradeoffs" (Section 5.4). In the raw runtime plots (Figure 9, third row), AI21/J1-Grande v1 appears scattered at relatively high and variable raw runtimes despite its small size (17B parameters). In the idealized runtime plots (fifth row), AI21/J1-Grande v1 appears much closer to where its parameter count would suggest—fast, though not Pareto-optimal. This is a particularly stark illustration of how raw runtime can be dominated by operational factors (API server load for that particular model endpoint) rather than architectural efficiency.

### Ablation Studies and Robustness Checks

The paper is not structured around traditional ML ablations (since it proposes a measurement methodology rather than a model or training procedure). However, several analyses serve the function of validating the methodology's robustness to different conditions:

**Hardware comparison (A100 vs. V100, Figure 8):** This serves as a robustness check that the idealized runtime estimation procedure is hardware-agnostic and produces consistent results when applied to different hardware targets. The finding that V100 GPUs are "both slower and more expensive" for most models—despite lower per-hour rental costs—validates that the methodology correctly accounts for the increased accelerator count needed when GPU memory is smaller (32GB vs. 80GB). The consistency of the runtime ranking across hardware types (models that are faster on A100 are generally faster on V100, though the magnitude of difference varies) indicates that idealized runtime captures inherent computational properties of the architecture rather than artifacts of a specific hardware choice.

**Multiple objective functions for ranking (Figure 10):** The comparison of `f1 = accuracy / idealized_runtime` versus `f2 = accuracy / log(idealized_runtime)` serves as a sensitivity analysis showing that the model ranking is not robust to the choice of how strongly to weight efficiency relative to accuracy. Under `f1`, Yandex/YaLM dominates (rank 1 on 3 of 4 benchmarks); under `f2`, the rankings flatten and OpenAI/davinci and Microsoft+NV/TNLG v2 improve. This is not a negative result—the paper explicitly states that "studying the implications of different objective functions in detail is interesting future work" (Section 5.4)—but it does temper the claim that idealized runtime provides a unique "correct" ranking. It provides a *different* ranking from raw runtime, but which specific model is "best" still depends on how the user weights latency versus accuracy.

**Multiple trials for denoised runtime estimation (Figure 5, Table 2):** The use of minimum-over-trials regression for denoised runtime, rather than mean-over-trials, is an implicit ablation on the noise reduction strategy. The paper shows that some models (AI21/J1-Grande v1) have very high per-trial variance (~0.55 coefficient of variation), meaning that using the mean could produce estimates that are substantially inflated by outlier trials that happened to experience high load. The minimum-over-trials approach is validated by the observation that 96.6% of raw runtime points are above the denoised estimates (Figure 7a), consistent with the model that noise is one-sided (`η ≥ 0`). The paper does not, however, compare minimum-over-trials to alternative noise reduction strategies (e.g., median, trimmed mean, or discarding the top-k slowest trials), so the optimality of the minimum approach is assumed rather than demonstrated.

**Comparison across diverse NLP tasks (Figure 9, four benchmarks):** The use of four tasks spanning sentiment analysis, QA, classification, and yes/no QA serves as a robustness check that the metric-dependent frontier shifts are not task-specific. The finding that OpenAI/davinci is on the raw runtime frontier for all four tasks but off the idealized runtime frontier for all four tasks demonstrates that the optimization illusion is consistent across task types. However, all four tasks are relatively similar in structure (short-form text input, single-label output), and the paper does not evaluate on tasks with very different inference characteristics (e.g., long-form generation, where output token counts would be much larger and the per-token generation time `g` would dominate total runtime; or multi-turn dialogue, where the prompt grows with each turn).

**Model size range (6B to 530B, Table 1, Figure 9):** The ten models span roughly two orders of magnitude in parameter count. The finding that Mid-size models (BigScience/BLOOM at 176B, Yandex/YaLM at 100B) appear on the idealized runtime frontier while the largest model (Microsoft+NV/TNLG v2 at 530B) generally does not is consistent with the expectation that idealized runtime captures diminishing returns to scale. However, the paper does not control for model family or training data differences—BigScience/BLOOM and Yandex/YaLM may have lower accuracy than Microsoft+NV/TNLG v2 on some tasks (e.g., MMLU in Figure 9b, where Microsoft+NV/TNLG v2 achieves ~0.25 accuracy vs. Yandex/YaLM's ~0.22 and BLOOM's ~0.24), making the frontier determination sensitive to the exact accuracy-efficiency tradeoff preference.

### Critical Assessment

The paper's central empirical claim is that **raw API runtime produces different efficiency-capability Pareto frontiers than idealized runtime, and that the former systematically overstates the architectural efficiency of models served through heavily-optimized APIs (specifically OpenAI/davinci).** The experiments in Figure 9 provide strong support for the *existence* of this discrepancy—the frontier reshuffling is visually unambiguous across all four benchmarks. However, the paper makes several narrower claims that warrant specific scrutiny, and several experimental gaps limit the strength of conclusions that can be drawn.

**Claim 1: "OpenAI/davinci consistently appears on the raw runtime Pareto frontier but not the idealized runtime frontier."** This is the paper's headline empirical result, and it is clearly supported by Figure 9. The visual evidence is unambiguous: across IMDB, MMLU, BoolQ, and RAFT, OpenAI/davinci is a Pareto-optimal square in the raw runtime row and a dominated circle in the idealized runtime row. However, the claim's *interpretation*—"the superior inference runtime performance of certain APIs is often a byproduct of optimizations within the API rather than the underlying model"—rests on the assumption that Megatron on A100 GPUs is a fair baseline for "what the model architecture costs." This assumption has several vulnerabilities:

- **Megatron may not be the most optimized open-source implementation of Transformer inference.** The paper acknowledges that FlashAttention (Dao et al., 2022) is a known optimization not included in the default Megatron stack, and that enabling it could close some of the gap between idealized and denoised runtimes for OpenAI. The paper does not report idealized runtime with FlashAttention enabled, so the extent to which the idealized-to-denoised gap reflects hardware differences (OpenAI might use TPUs or H100 GPUs) versus software differences (OpenAI might use custom kernels not represented in any open-source stack) is not disentangled.

- **The "minimum GPUs to fit the model" design choice means idealized runtime and idealized cost are lower bounds, not realistic estimates.** If OpenAI actually uses more than 8 GPUs to serve davinci (for lower latency or higher throughput), the idealized cost estimate understates the true serving cost. The paper's idealized cost for davinci on A100 GPUs is an estimate of what *could* be achieved with the minimum hardware, not what OpenAI actually spends.

- **The benchmarking was performed in September/October 2022.** API performance characteristics can change rapidly as providers upgrade infrastructure, change load-balancing policies, or adjust rate limits. The specific numbers in Figure 9 are a snapshot and may not reflect current API performance.

**Claim 2: "The denoised runtime factors out performance noise and provides a lower bound for raw runtime."** The evidence in Figure 7a (96.6% of raw runtime points above denoised) supports the claim that the minimum-over-trials regression produces a reasonable lower bound. However, the 3.4% of points where raw runtime is *below* denoised runtime is not explained—possible causes include measurement error, drift in API performance over the course of the profiling period, or the minimum-over-trials approach being unreliable when the number of trials is insufficient to capture the true minimum. The paper runs 10 trials per configuration (Figure 5 shows 10 points per `(p, o)`), which may not be enough for models with high variance (e.g., AI21/J1-Grande v1 with coefficient of variation 0.55). A more thorough validation would show how the denoised estimate changes with increasing numbers of trials, or compare against an alternative noise model (e.g., estimating the lower bound from the bottom-k percentiles rather than the minimum).

**Claim 3: "The methodology enables efficient comparison of alternative hardware and software stacks."** The A100 vs. V100 comparison (Figure 8) demonstrates the methodology's capability, but the paper does not quantify the *accuracy* of the hardware comparison. When the methodology predicts that V100 is 2× slower than A100 for a particular model and query, is that prediction verified by actually running the full model on V100 GPUs? The profiling procedure uses model architectures without trained weights (since runtime depends only on tensor shapes), so the estimated V100 runtimes are predictions from measurements on V100 GPUs—but the paper does not report doing a held-out validation where the parametric predictions are compared to per-query measurements on the target hardware.

**Missing experiments that would strengthen the paper:**

1. **Direct measurement of the idealized-to-denoised gap components:** The paper identifies the gap between idealized and denoised runtime as representing hardware/software differences, but does not systematically vary software (e.g., Megatron vs. Megatron+FlashAttention vs. FasterTransformer) to attribute how much of the gap is software versus hardware. This would distinguish between "OpenAI has faster GPUs" and "OpenAI has better kernels."
   
2. **Evaluation on generation-heavy tasks:** All four benchmarks (IMDB, MMLU, BoolQ, RAFT) involve relatively short outputs—classification labels, yes/no answers, or short multiple-choice responses. The per-token generation time `g` is therefore a small fraction of total runtime for these tasks; prompt encoding time dominates. The paper's parametric form would be most valuable for tasks where output length varies substantially (e.g., summarization, code generation, open-ended QA), where the linear relationship between runtime and `o` would be the primary driver of total cost. Evaluating on such tasks would demonstrate the methodology's utility in the regime where it provides the most value over naive FLOP counting.

3. **Sensitivity to the number of profiling points:** The paper uses `|P| = 5` prompt sizes and `|O| ≈ 8` output token counts. A natural ablation would be to show how the accuracy of runtime predictions for held-out queries degrades as fewer profiling points are used, establishing the minimum profiling budget needed for reliable estimation.

4. **Reproducibility across time:** The API measurements were taken in September/October 2022. Repeating the same measurements at a later date would reveal whether the observed differences between providers are stable or transient, and whether the idealized-to-denoised gap for a given provider narrows as they upgrade infrastructure.

5. **Confidence intervals on Pareto frontier membership:** The paper identifies frontier models visually but provides no statistical test for whether one model "significantly" dominates another. With only 10 models, small measurement errors in accuracy or runtime could change frontier membership. Reporting bootstrap confidence intervals on the accuracy and runtime estimates, or at minimum error bars on the scatter points in Figure 9, would make the frontier determinations more rigorous.

6. **Comparison against a "simulated idealized runtime" using actual model weights:** The paper constructs idealized runtime from model architecture alone, without trained weights. A validation experiment could take an open-source model (e.g., GPT-J or BLOOM, for which both architecture and weights are available), measure actual inference runtime with weights loaded, and compare to the idealized runtime estimated from architecture alone through the profiling procedure. This would directly test the claim that "runtime is independent of the model's parameters given a prompt size and number of output tokens" (Section 3.2).

**Conditional nature of the claims:**

The paper's central empirical claim—that the choice of efficiency metric changes the Pareto frontier—holds without qualification for the four benchmarks and ten models studied. However, the *practical* significance of this finding is conditional on:
- **How different the models' architectures are.** If all models had similar FLOP-per-token profiles, idealized and raw runtime might correlate well despite provider optimizations. The paper's models span a wide range of hidden sizes (4096 to 20480) and layer counts (28 to 105), creating substantial architectural heterogeneity that makes the metric choice matter. For a comparison within a single model family (e.g., OpenAI's davinci vs. curie vs. babbage), the provider optimizations might be identical and raw runtime might correlate well with idealized runtime.
- **Whether the API provider's optimizations are persistent.** If OpenAI's infrastructure advantage over Megatron on A100 GPUs is primarily due to using TPUs or custom ASICs, that advantage is durable and arguably should be considered part of the "model offering." If it's due to software optimizations that will eventually be upstreamed to open-source frameworks, the idealized-to-denoised gap will close over time. The paper's methodology cannot distinguish these cases.
- **The user's actual objective.** For an end user choosing between APIs, raw runtime *is* the relevant metric—they care about the latency they experience, not the architectural efficiency. The paper's idealized runtime is most useful for model creators making architectural decisions and for researchers analyzing inherent efficiency-capability tradeoffs. The paper is clear about this distinction, but the practical takeaway depends on the stakeholder.

**The AI21 variance finding is compelling but under-analyzed.** The observation that AI21/J1-Grande v1 has much higher runtime variance than other AI21 models (coefficient of variation ~0.55 vs. ~0.2; Figure 5) is one of the paper's most striking results, but it is presented as an incidental finding rather than systematically investigated. Possible causes—differential load on different model endpoints, different serving configurations for models of different sizes, or different request routing policies—are not explored. Understanding *why* variance differs across models from the same provider would strengthen the case that raw runtime is unreliable for cross-model comparison and would provide actionable guidance for API providers seeking to reduce variance.

**In summary**, the experiments convincingly demonstrate that the choice of efficiency metric matters and that raw runtime can mislead about model architectural efficiency. The parametric estimation procedure is empirically validated (`R^2 > 0.999` on dedicated hardware) and the efficiency gain from amortized profiling is clearly articulated. However, several important validations are missing (direct verification that architecture-only profiling matches actual inference with weights, sensitivity to profiling budget, evaluation on generation-heavy tasks), and the paper's interpretation of the idealized-to-denoised gap as "API optimizations" would benefit from finer-grained attribution (hardware vs. software). The paper's main contribution is therefore primarily **methodological**—providing a framework and demonstrating its feasibility—with the specific empirical findings (OpenAI/davinci's frontier reshuffling) serving as validating case studies rather than the primary contribution.

## 6. Limitations and Trade-offs

### The Idealized Runtime Requires Model Architecture Details That Are Increasingly Withheld

**The assumption or constraint.** The methodology's core requirement is knowledge of the model's hidden size `h`, number of layers `l`, and number of attention heads `n`—the hyperparameters that determine the tensor shapes governing runtime on the idealized hardware. The paper is explicit about this boundary: "We do not evaluate models with publicly unavailable model architecture details (including OpenAI's ChatGPT and GPT-4)" (Section 5.1). The profiling engine instantiates model architectures without trained weights, exploiting the fact that runtime depends only on shapes, but this requires knowing what those shapes are.

**The consequence.** The most commercially significant models at the time of publication—and an increasing fraction of models since—do not disclose architecture details. GPT-4's architecture was not disclosed in the GPT-4 Technical Report (OpenAI, 2023). Claude's architecture is not public. Gemini's architecture is not public. The methodology therefore cannot be applied to the very models that dominate production deployment and for which the efficiency-capability tradeoff is most practically consequential. This creates an ironic asymmetry: the paper's motivating use case is comparing black-box API models, but the methodology works only for the subset of black-box models whose creators have chosen to reveal architectural specifications. As frontier models become more closed, the methodology's applicable scope shrinks.

A secondary consequence is strategic: a model provider who wants to avoid idealized runtime comparisons can simply decline to publish `h`, `l`, and `n`. The paper provides no estimation procedure for inferring these parameters from API behavior alone (e.g., by exploiting known scaling relationships between parameter count, layer count, and hidden size, or by measuring runtime scaling patterns to reverse-engineer model dimensions). The methodology thus depends on a norm of architectural transparency that the industry is moving away from rather than toward.

**What evidence exists in the paper.** The limitation is self-imposed by the paper's design: Table 1 lists `h`, `l`, and `n` for all ten evaluated models, and Section 5.1 explicitly excludes ChatGPT and GPT-4. The paper does not measure how many production LLMs have publicly available architecture details, nor does it discuss whether the ten models evaluated are representative of the broader landscape of deployed models in terms of architecture disclosure rates.

**Mitigation status.** Not addressed. The paper treats the exclusion of architecture-withheld models as a scope limitation rather than a weakness to be solved. No method for inferring architecture from API behavior is proposed, nor is there discussion of whether partial architecture information (e.g., parameter count alone, which is often disclosed) could enable approximate idealized runtime estimation through some form of architectural interpolation or scaling-law-based imputation. Future work on "estimating idealized runtime from black-box observations without architectural disclosure" would substantially expand the methodology's practical reach.

---

### The Difficulty Estimation Analog: No Account for Variable Query Complexity

**The assumption or constraint.** The idealized runtime for a query depends only on its prompt size `p` and output token count `o`, not on the semantic content of the query. This is an explicit design choice grounded in the parametric form `t(p, o) = prompt_encoding_time(p) + (o-1) · g`, where the per-token generation time `g` is constant regardless of what tokens are being generated. This holds because the Transformer's computational graph is static—the same matrix multiplications execute regardless of token identities—and the paper empirically validates it with `R^2 > 0.999` (Section 3.2).

**The consequence.** While the *model's* computation is indeed query-independent in FLOP count, the *overall system* serving the model may not be. Several realistic deployment scenarios introduce query-dependent runtime variation that the idealized metric does not capture and that could systematically bias cross-model comparisons:

- **Variable tokenization efficiency.** Different models use different tokenizers, meaning the same natural-language query can produce different prompt sizes `p` across models. The paper treats `p` as given, but in practice, a user comparing two APIs sends the same text and receives different token counts. A model with a more efficient tokenizer (fewer tokens per word) will have a lower effective `p` for the same query, translating to lower idealized runtime—but this advantage is an inherent property of the tokenizer design, not captured by comparing models at the same `p`. The paper does not discuss whether tokenizer differences across the ten evaluated models could systematically advantage some models in real usage.

- **Speculative decoding and early exiting.** Some inference systems dynamically vary computation per token—for example, speculative decoding (Leviathan et al., 2023) generates multiple tokens per forward pass when predictions are confident, and early-exit mechanisms skip later Transformer layers for "easy" tokens. These optimizations make per-token generation time `g` query-dependent in a way that violates the constant-`g` assumption. If one API provider deploys speculative decoding and another does not, the idealized runtime (which assumes standard autoregressive decoding) will not reflect this—but unlike the provider-specific optimizations the paper *wants* to strip away, speculative decoding and early exiting may be architectural choices that should arguably be attributed to the model deployment strategy rather than treated as "unfair" optimizations. The methodology cannot distinguish between "this API is faster because of better CUDA kernels" (which idealized runtime correctly removes) and "this API is faster because it uses a different decoding algorithm" (which may be a legitimate efficiency property of the serving approach).

- **Variable token difficulty for generation.** While the FLOP count per forward pass is constant, some tokens are objectively harder to generate than others (lower entropy, requiring more complex reasoning). This does not affect *runtime* on dedicated hardware (since the compute graph is identical), but it could affect API runtime if providers implement adaptive compute based on token difficulty—for example, using larger beam widths for low-confidence tokens. None of the ten evaluated APIs are known to do this, but the methodology provides no way to detect or account for such behavior.

**What evidence exists in the paper.** The `R^2 > 0.999` validation (Figures 3, 4) is conducted on synthetic prompts with uniform content (not semantically varying queries), so it validates the parametric form for *synthetic* queries but not for semantically diverse real-world queries where tokenizer differences or adaptive serving strategies might matter. The paper does not measure `p` variation across the four HELM benchmarks for different tokenizers, nor does it discuss whether any of the evaluated APIs use non-standard decoding strategies.

**Mitigation status.** Not addressed. The paper treats `p` as an input to be measured per query, which in principle accounts for tokenizer differences if `p` is computed using each model's own tokenizer. However, the paper does not discuss whether the profiling procedure uses model-specific tokenization or a uniform tokenizer, and the idealized runtime estimates in Table 3 and Figure 9 are presented without any normalization for tokenizer differences. A user naively comparing idealized runtimes at the same `p` across models with different tokenizers would be comparing the cost of processing different amounts of semantic content, potentially misattributing tokenizer efficiency to model architecture efficiency.

---

### Profiling Cost Is Amortized Across Benchmarks But Not Accounted in Headline Comparisons

**The assumption or constraint.** The paper claims the parametric estimation procedure is efficient because it requires "profil[ing] on the order of hours (< 2 hours for most models) once, compared to hours per benchmark (depending on number of queries in the benchmark) for exhaustive profiling" (Section 5.3). The "once" refers to the fact that the estimated parameters `prompt_encoding_time(p)` and `g` can be reused across any number of benchmarks and queries without additional measurement.

**The consequence.** While this amortization argument is logically correct, the paper never accounts for the profiling cost in any of its quantitative comparisons. The idealized runtime numbers reported in Figure 9 and Table 3 are the *predictions* from the fitted parametric model—they do not include the measurement overhead required to obtain those predictions. For a user who wants to compare two models on a single benchmark with 100 queries, the parametric approach requires profiling a grid of `|P| × |O| ≈ 40` configuration queries (costing "on the order of hours") plus ~100 inexpensive predictions, while exhaustive profiling requires timing ~100 actual benchmark queries. For N benchmarks, the parametric approach wins. For one benchmark, the tradeoff is less clear and depends on the relative cost of profiling configuration queries versus benchmark queries.

More importantly, the profiling cost depends on the fidelity of the piecewise-linear approximation. The paper uses `|P| = 5` prompt sizes for models with `max_context_length = 2048`. For models with larger context windows (many newer models support 32K, 128K, or even 1M tokens), the number of profiling points needed to capture the piecewise linear structure across the full range would grow, and the "hours" estimate may no longer hold. The paper does not discuss how profiling cost scales with context length or model size.

Additionally, the profiling must be repeated for each hardware configuration and each software stack. The paper's A100 vs. V100 comparison (Figure 8) required profiling all ten models on *both* hardware types, doubling the measurement cost. If a researcher wants to compare five hardware configurations and three software stacks, the profiling cost multiplies accordingly. The paper's efficiency claim—"once, rather than per-benchmark"—is thus relative to the number of benchmarks, not the number of hardware/software configurations.

**What evidence exists in the paper.** The paper provides the qualitative estimate of "< 2 hours for most models" (Section 5.3) but does not report the actual wall-clock time spent profiling, the total number of configuration queries used, or the GPU-hours consumed. No experiment varies the number of profiling points or benchmarks to empirically measure the break-even point where the parametric approach becomes cheaper than exhaustive profiling. The paper does not discuss how profiling cost scales with context length or model size.

**Mitigation status.** Not addressed. The paper treats profiling cost as a sunk cost that is not part of the efficiency comparison, which is reasonable for the paper's purpose (demonstrating the methodology's feasibility and comparing models) but would need to be considered in a deployment context. A practitioner deciding whether to adopt this methodology for their own model comparison needs to know: how many profiling queries are needed? How does this scale with the number of models, hardware targets, and benchmarks? The paper provides qualitative guidance (hours, not days) but no quantitative cost model for the profiling step itself.

---

### The Single-Hardware, Single-Software Idealized Stack Does Not Capture Real-World Deployment Diversity

**The assumption or constraint.** The idealized runtime is defined with respect to a specific, uniform software stack `s` and hardware type `h`. The paper's default choice is Megatron (`s = Megatron`) on NVIDIA A100 80GB GPUs (`h = A100`), justified because "A100 GPUs are the fastest widely available GPU right now" (Section 3.2) and Megatron is a well-optimized, publicly described Transformer implementation. The methodology requires fixing a single reference configuration so that all models are compared on equal footing.

**The consequence.** The choice of reference stack is not neutral—it can systematically advantage or disadvantage different model architectures, and the paper's specific choice may not represent the deployment environments most relevant to practitioners. Several concrete issues arise:

- **GPU architecture sensitivity.** Different GPU architectures have different ratios of compute to memory bandwidth, different tensor core capabilities, and different memory capacities. A model architecture that is efficient on A100 GPUs (high compute, high bandwidth, 80GB memory) might be inefficient on a different hardware target—for example, an inference-optimized accelerator with lower memory bandwidth, or a consumer GPU with less memory requiring more aggressive model parallelism. The paper's V100 comparison (Figure 8) is a step toward addressing this, but it only evaluates one alternative (an older NVIDIA GPU), not the space of possible deployment hardware (TPUs, Inferentia, consumer GPUs, edge devices).

- **The "minimum GPUs" design choice creates a specific cost model.** The paper uses "the minimum number of GPUs necessary" to fit each model (Table 1), which represents the most cost-efficient configuration *for latency* but not necessarily for throughput. In high-throughput batch serving, using more GPUs with tensor parallelism can reduce latency per query while increasing throughput-per-dollar, which would change which models appear on the cost-efficiency frontier. The paper's idealized cost metric assumes single-query latency optimization, but many production deployments optimize for throughput or for latency under a throughput constraint.

- **FP16 vs. FP8 vs. INT8 quantization.** The paper profiles models at the precision implied by Megatron's default configuration (likely FP16 or BF16, though this is not explicitly stated). Different models may benefit differently from quantization—a model trained with quantization-aware training might achieve much lower idealized runtime if profiled at INT8, while a model that degrades under quantization cannot exploit this optimization. The paper's uniform precision assumption prevents these model-specific quantization advantages from being reflected in idealized runtime.

- **The Megatron choice as a moving target.** Megatron is actively developed and optimized. The paper's measurements from late 2022 may not reflect Megatron's performance in 2024 with FlashAttention integration, improved kernel fusion, or better parallelism strategies. The idealized runtime for a given model is therefore not a fixed property but a function of the reference software stack's maturity, which evolves over time independently of the model architecture. Two researchers computing idealized runtime for the same model at different times could obtain different numbers purely due to Megatron improvements, undermining the metric's stability as a "model property."

**What evidence exists in the paper.** The paper acknowledges the possibility of alternative software/hardware choices: "Other accelerators like the TPU (Jouppi et al., 2017) or the NVIDIA H100 GPU could also be used" and "We can perform similar analysis for different software stacks as well (e.g., Nvidia Triton or Megatron with FlashAttention enabled)" (Section 5.3). However, the paper does not perform these comparisons (with the exception of the V100 analysis in Figure 8), so the sensitivity of the idealized runtime ranking to the choice of reference stack is not quantified. The paper does not discuss how the "minimum GPUs" assumption interacts with throughput-oriented deployment scenarios, nor does it specify the precision used in profiling.

**Mitigation status.** Partially addressed through the extensibility of the methodology. The paper positions the reference stack as a *choice* that can be adapted to the user's needs—"the main metric we propose is the idealized runtime, which is the runtime of an inference query if run on a specified software and hardware stack" (Section 1, emphasis on "specified"). In principle, a practitioner could profile models on their own target hardware and software, producing an idealized runtime relevant to *their* deployment. The paper's single-stack evaluation (Megatron + A100) serves as a reference point and proof of concept rather than a claim that this specific stack is universally appropriate. However, the paper's headline tradeoff analyses (Figure 9) and the conclusion that "OpenAI/davinci...consistently not in [the Pareto frontier]" are all based on this single reference stack, and the paper does not discuss whether these conclusions would hold under alternative hardware/software choices. A practitioner reading the paper might reasonably conclude that OpenAI/davinci is architecturally inefficient *in general*, when the paper's evidence only supports the narrower claim that it is inefficient relative to other models *when served on Megatron+A100 with minimum GPUs*.

### The Denoised Runtime Lower Bound Is Fragile Under Transient API Conditions

**The assumption or constraint.** The denoised runtime is estimated by taking the **minimum runtime across multiple trials** at each `(p, o)` configuration, under the assumption that performance noise `η ≥ 0` is always additive and that sufficiently many trials will eventually observe the uncontended runtime (`η ≈ 0`). The paper runs 10 trials per configuration (Figure 5) and reports that 96.6% of raw runtime points are above the denoised estimates (Section 5.2, Figure 7a).

**The consequence.** The minimum-over-trials approach is a reasonable heuristic but provides no statistical guarantee that the true uncontended runtime has been observed. Several failure modes are possible, and the paper provides no diagnostic for detecting them:

- **Insufficient trials for high-variance models.** For models with high coefficient of variation (AI21/J1-Grande v1 at ~0.55), the probability of observing a near-minimum runtime in only 10 trials may be low. The true uncontended runtime could be substantially lower than the minimum observed in 10 trials, meaning the denoised estimate is still inflated by residual noise. The paper does not report how the denoised estimate changes with the number of trials—e.g., does the minimum decrease significantly when going from 5 to 10 to 50 trials? Without this analysis, the reader cannot assess whether 10 trials is adequate for the variance levels observed.

- **Time-of-day and day-of-week effects.** API load varies systematically with time (business hours, weekdays vs. weekends, product launch events). If all trials for a given model are run within a short time window (which the paper's methodology implies but does not state), the denoised estimate may reflect the minimum latency *during that window's load conditions* rather than the minimum latency the API can achieve under optimal conditions. A model profiled during a low-load period will appear to have lower denoised runtime than the same model profiled during a high-load period, even though the underlying serving stack is identical. The paper does not discuss whether profiling was spread across different times or concentrated in a single session.

- **Persistent but slow-varying performance degradation.** Some API performance issues are not captured by a per-trial noise model. For example, a gradual memory leak in the serving infrastructure might cause latency to increase over the course of hours, with even the minimum across trials being elevated relative to the true capability of a freshly-restarted server. The minimum-over-trials approach only removes transient noise (queuing delays, request scheduling jitter), not persistent degradation.

- **The 3.4% of points where raw runtime is below denoised (Figure 7a).** The paper does not explain these violations of the expected inequality `t_raw ≥ t_denoised`. Possible causes include measurement error (clock synchronization issues, the API returning a response before the client believes the request was sent), API performance improving over the measurement period (making later trials faster than earlier ones, so the minimum is from a different performance regime), or the model's API endpoint being migrated to faster hardware mid-experiment. These violations suggest that the denoised estimation procedure is not perfectly reliable, but the paper provides no investigation of their causes or frequency.

**What evidence exists in the paper.** Figure 5 shows 10 trials per `(p, o)` configuration for AI21 models, providing a visual sense of variance. Figure 6 shows that increasing parallel load from 1 to ~25 requests increases runtime by up to 2× for Anthropic/v4-s3, demonstrating that load is a meaningful source of variation. Figure 7a shows the 96.6% vs. 3.4% split. The paper does not report the number of trials for non-AI21 models, the time span over which trials were collected, or diagnostics for the minimum-over-trials estimate's stability.

**Mitigation status.** Partially addressed through the idealized runtime, which does not depend on API measurements at all and thus sidesteps the noise estimation problem entirely. The denoised runtime is an intermediate diagnostic metric rather than the primary contribution; the paper's main proposed metric is idealized runtime, which is estimated on dedicated, contention-free hardware. However, the denoised runtime serves an important role in the paper's argument—it decomposes the raw-to-idealized gap and provides evidence that some APIs have optimizations beyond the idealized stack (when denoised < idealized). If the denoised estimates are unreliable due to insufficient trial counts or systematic time-of-day effects, the claim that "OpenAI models have idealized runtimes greater than denoised runtimes 64.2% of the time" (Section 5.2) could be an artifact of measurement methodology rather than a true signal of API optimizations. The paper does not cross-validate the denoised estimates by, for example, splitting trials into two sets and checking whether the minimum is stable, or by repeating the profiling at different times and comparing denoised estimates.

---

### No Evaluation on Generation-Heavy or Latency-Critical Production Workloads

**The assumption or constraint.** All four benchmarks used to evaluate efficiency-capability tradeoffs—IMDB (sentiment analysis), MMLU college chemistry (multiple-choice QA), BoolQ (yes/no QA), and RAFT terms of service (classification)—involve tasks with **short, fixed-format outputs**. The model is expected to produce a label, a single word, or a short phrase. The number of output tokens `o` is therefore very small (typically 1–5 tokens), meaning that the per-token generation time `g` contributes negligibly to total runtime. The idealied runtime for these tasks is dominated entirely by prompt encoding time `prompt_encoding_time(p)`.

**The consequence.** The parametric form's most distinctive feature—the decomposition into prompt encoding and token generation phases, and the linear scaling of runtime with `o`—is almost entirely irrelevant for the benchmarks used to make the paper's headline claims. The paper demonstrates that `g` is constant and that `t(p, o)` is linear in `o` (Figures 3, 4), but the downstream tradeoff analysis (Figure 9) effectively reduces to comparing `prompt_encoding_time(p)` across models, since `o` is too small for `g` to matter. This means:

- **The methodology's value proposition is not stress-tested on the workloads where it would provide the most benefit.** In production LLM applications—chatbots, summarization, code generation, creative writing—output lengths can range from tens to thousands of tokens. For such workloads, the per-token generation time `g` dominates total runtime, and differences in `g` across models (which the paper shows can vary by 2–4×; Table 3) become the primary determinant of user-perceived latency. The paper's efficiency-capability tradeoff conclusions (OpenAI/davinci off the idealized frontier, BigScience/BLOOM and Yandex/YaLM on it) are based on prompt-encoding-dominated tasks; on generation-heavy tasks, the ranking might shift substantially if models that are slow at prompt encoding are fast at token generation, or vice versa.

- **The "accuracy vs. runtime" tradeoff is fundamentally different for generation-heavy tasks.** For classification and short-answer tasks, accuracy is typically independent of `o` (the model either produces the right label or it doesn't; producing more tokens doesn't help). For generation tasks, there is often a quality-latency tradeoff: chain-of-thought prompting produces longer outputs with higher accuracy, beam search with larger beam width increases both quality and latency, and techniques like best-of-N sampling trade compute for accuracy. The paper's analysis does not capture these tradeoffs because it treats `o` as an input to the runtime formula rather than as a variable that can be optimized. A compute-optimal allocation framework (as in the other example paper) would need to jointly consider `(p, o)` and accuracy, but the idealized runtime methodology only provides the cost model, not the capability model.

- **The parametric form may break down for very long outputs.** The paper's derivation assumes `i ≪ 6h` (that the sequence length is much smaller than 6× the hidden size), which makes the attention FLOP contribution negligible. For OpenAI/davinci, `h = 12288`, so `6h = 73728`, and the maximum context length is 2048—the assumption holds easily. But for models with smaller hidden sizes or longer context windows, or for workloads generating thousands of output tokens, the `i/6h` correction term becomes non-negligible, and the constant-`g` assumption degrades. The paper does not evaluate models or workloads where this matters.

**What evidence exists in the paper.** The four benchmarks are described in Section 5.4 but their output token distributions are not reported. Based on the task descriptions (IMDB: sentiment label; MMLU: multiple-choice answer; BoolQ: yes/no; RAFT: classification label), `o` is almost certainly in the range 1–5 for all queries. Figure 3 validates the linear-in-`o` relationship up to `o = 64` tokens, which covers the benchmark output range but does not test the parameterization at the scale of typical generation workloads (hundreds to thousands of tokens). The paper does not discuss whether any of the evaluated APIs implement quality-latency tradeoffs (e.g., beam search) that would make accuracy depend on `o`.

**Mitigation status.** Not addressed. The paper does not claim that the four benchmarks are representative of all LLM workloads, nor does it discuss the prompt-encoding-dominated nature of these tasks. The choice of benchmarks appears driven by the HELM evaluation framework rather than by a deliberate analysis of which workloads would best exercise the methodology. A reader interested in applying idealized runtime to generation-heavy applications would need to extrapolate from the paper's prompt-encoding-dominated results with no guidance on whether the parametric form remains accurate at large `o`, whether model rankings are stable across prompt-encoding-heavy and generation-heavy workloads, or how to incorporate quality-latency tradeoffs into the analysis.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

This paper introduces a **measurement methodology, not a model or training technique**, so its impact on the field operates differently from a typical ML contribution. Rather than advancing the state of the art on a benchmark, it provides the intellectual scaffolding for asking a question the field had previously answered only through ad-hoc proxies: **how do you compare the inference efficiency of language models on a level playing field when the models themselves are increasingly inaccessible?**

The core conceptual shift is from treating inference efficiency as a **latent property of models that cannot be directly observed** (and must therefore be approximated by parameter count, FLOPs, or raw API latency) to treating it as a **measurable, decomposable quantity that can be estimated from architecture alone, even without access to weights or the serving infrastructure.** This is a reframing, not a paradigm shift—the paper does not overturn existing scaling laws or capability benchmarks—but it is a reframing with practical consequences that ripple through how the field evaluates, compares, and reports on large language models.

Consider the status quo ante. A model announcement paper reports parameter count as the efficiency dimension, with perhaps a footnote about inference latency on the authors' infrastructure. A practitioner deciding between two APIs runs a handful of queries, observes raw latencies, and picks the faster one—implicitly attributing the speed difference to model quality. A benchmarking effort like HELM or BIG-Bench reports capabilities with model size on the x-axis, knowing that model size is an imperfect proxy but lacking a standardized alternative. In all three scenarios, inference efficiency is being reasoned about, but through metrics that the paper demonstrates can be misleading: the Pareto frontier shifts when moving from model size to idealized runtime (Figure 9), raw runtime can be dominated by noise rather than model properties (AI21/J1-Grande v1's 0.55 coefficient of variation), and FLOPs do not translate linearly to wall-clock time due to hardware utilization effects (the BLOOM vs. YaLM reversal in Figure 9).

The paper's contribution is to replace this landscape of proxies with a **principled hierarchy**: raw → denoised → idealized runtime, each stripping away a different source of non-comparability. This hierarchy does not declare any single metric "correct"—raw runtime is genuinely what users experience, and the paper acknowledges this—but it gives researchers and practitioners a vocabulary for distinguishing between "this model is faster because of its architecture" and "this model is faster because its API provider has better infrastructure." The inequality chain `t_raw ≥ t_denoised ≥ t_idealized` (Section 4.1, Figure 7) makes these distinctions formally quantifiable rather than matters of speculation.

**Why this matters beyond the specific ten models studied.** The paper's most durable contribution is not the finding that OpenAI/davinci falls off the idealized Pareto frontier (which may change as reference software improves or as API providers upgrade hardware) but the **framework for making such determinations reproducibly.** A researcher in 2025 evaluating a new model architecture can apply the same methodology—profile the architecture on their reference stack, compare to denoised API measurements—and draw conclusions about whether the efficiency gains are architectural or infrastructural. A model provider can report idealized runtime alongside architecture details without revealing anything about their actual serving stack, enabling independent verification. A benchmark can include idealized runtime as a standardized efficiency axis alongside capability metrics, making cross-model comparisons more informative than parameter count alone.

The paper also implicitly resolves a tension in how the field talks about model efficiency. Prior work oscillated between two unsatisfactory extremes: either efficiency was reduced to parameter count (Kaplan et al., 2020; model announcement papers) with full acknowledgment that this ignores architecture-dependent runtime variation, or raw API latency was treated as the ground truth (practitioner benchmarks) with full acknowledgment that it conflates model and infrastructure. The idealized runtime provides a **third option that is both architecture-aware and infrastructure-independent**, giving the field a common yardstick that neither extreme provided. This matters for scientific discourse: if two papers report contradictory conclusions about whether "larger models are more efficient," the idealized runtime framework provides a way to diagnose whether the disagreement stems from different model architectures, different serving infrastructures, or different operational conditions (load, time of measurement).

**Directions that become more attractive.** The paper's methodology makes **inference efficiency a first-class object of study** in a way that was previously difficult. This shifts research incentives in several ways:
- **Architecture co-design for inference efficiency** becomes easier to evaluate. A researcher proposing a new attention mechanism or sparsity pattern can measure idealized runtime on standardized hardware and quantify the latency impact, rather than relying on FLOP counts that may not translate to wall-clock improvements. The availability of a reproducible measurement methodology lowers the barrier to entry for hardware-aware architecture research.
- **Lifecycle cost analysis** for LLM deployment becomes more rigorous. The idealized dollar cost metric (`t_idealized × n_accelerator × c_accelerator`; Section 4.2) provides a standardized way to estimate per-query cost that is independent of provider pricing strategies, enabling apples-to-apples comparisons of total cost of ownership across deployment options.
- **Transparency norms** around model reporting could shift. The paper demonstrates that architectural hyperparameters (`h`, `l`, `n`) are sufficient for meaningful efficiency comparison, even without weight access. This creates a path for model providers to be transparent about inference efficiency—by publishing architecture details and perhaps idealized runtime estimates—without compromising competitive advantages in serving infrastructure. If idealized runtime were adopted as a standard reported metric (alongside parameter count and benchmark scores), consumers of model cards would have a much clearer picture of deployment costs.

**Directions that become less central.** The paper's analysis suggests that **raw API latency benchmarking, in isolation, is insufficient for scientific conclusions about model efficiency.** This does not mean raw latency is irrelevant—for end users choosing an API, it is the most relevant metric—but it means that papers claiming "Model A is more efficient than Model B" based solely on API timings are making a claim that conflates multiple factors the paper shows can be disentangled. Similarly, **parameter count as a sole efficiency proxy** is further undermined by the paper's demonstration that models with similar parameter counts (e.g., BLOOM at 176B vs. davinci at 175B) can have meaningfully different idealized runtimes (Figure 9, idealized runtime row), and that smaller models can be slower than larger ones when API variance is high (AI21/J1-Grande v1 vs. J1-Jumbo v1 in raw runtime).

### Follow-Up Research This Work Enables

**Cheap difficulty estimation for the profiling procedure—can we predict idealized runtime from partial architecture information?** The methodology's central requirement is knowledge of `h`, `l`, and `n`—the hyperparameters that determine tensor shapes. But Section 5.1 explicitly excludes "models with publicly unavailable model architecture details (including OpenAI's ChatGPT and GPT-4)." A natural extension asks: given only *partial* architecture information (e.g., parameter count alone, which is often disclosed even when layer dimensions are not), can idealized runtime be estimated to within useful accuracy? This is an imputation problem: from the ten models in Table 1, one could fit a regression from `(h, l, n)` to `prompt_encoding_time(p)` and `g`, then test how well parameter count alone (or parameter count plus inference-observable properties like the ratio of prompt encoding time to per-token generation time) predicts idealized runtime for held-out models. If successful, this would dramatically expand the methodology's scope to the frontier models where efficiency comparisons are most needed. If unsuccessful—if idealized runtime cannot be reliably predicted from size alone—that finding would itself be important: it would mean that architectural transparency (`h`, `l`, `n`) is irreplaceable for efficiency comparison, strengthening the case for disclosure norms.

**What is the idealized-to-denoised gap composed of? A controlled software ablation study.** The paper observes that OpenAI's denoised runtime is frequently *lower* than idealized runtime on Megatron+A100 (64.2% of queries; Section 5.2, Figure 7b), interpreting this as evidence of API optimizations beyond the reference stack. But the gap conflates hardware differences (OpenAI might use TPUs, H100 GPUs, or custom ASICs) with software differences (OpenAI might use custom CUDA kernels, FlashAttention, or advanced batching). A controlled experiment would take a single model architecture (e.g., an open-source model like BLOOM or GPT-J where weights are available) and measure idealized runtime on A100 GPUs with: (a) vanilla Megatron, (b) Megatron + FlashAttention, (c) NVIDIA TensorRT-LLM, (d) vLLM, and (e) a fully custom serving stack if available. This would decompose the OpenAI gap into "how much is achievable with off-the-shelf open-source software?" vs. "how much requires custom engineering or different hardware?" The paper mentions FlashAttention as an example optimization (Section 5.3) but never quantifies its impact; this experiment would close that gap and provide a calibration point for what "idealized runtime with best open-source practices" looks like.

**How does the idealized runtime ranking change when output token count `o` is large? Stress-testing on generation-heavy benchmarks.** The paper's four benchmarks (IMDB, MMLU, BoolQ, RAFT) all involve short outputs—classification labels or short answers where `o` is small and prompt encoding time dominates. The parametric form's most distinctive feature, the linear scaling of runtime with `o`, is therefore largely irrelevant to the headline tradeoff results. A critical stress test would replicate Figure 9 on generation-heavy tasks: summarization (CNN/DailyMail, XSum), code generation (HumanEval with multiple samples per problem), or open-ended QA where responses are paragraphs rather than words. On these tasks, the per-token generation time `g` (which varies by 2–4× across models in Table 3) becomes the dominant cost. Would the idealized runtime frontier be different from the prompt-encoding-dominated frontier? A model that excels at prompt encoding (large batch-friendly matrix multiplies) but is slow at token generation (attention over large KV caches) might appear efficient on IMDB but inefficient on summarization. This experiment would establish whether a single idealized runtime ranking suffices for all workloads, or whether workload-specific efficiency characterization is necessary—a question the paper's current benchmark selection cannot answer.

**Can we estimate idealized runtime from black-box API observations alone, without architecture knowledge?** The paper's methodology requires knowing `h`, `l`, `n` to instantiate the profiling engine. But an API consumer without this information might still observe how runtime scales with `p` and `o`—the slopes and intercepts of the parametric form are *observable through the API* even if the model architecture is hidden. Specifically, by sending synthetic queries to the API and fitting the same linear regression (as done for denoised runtime estimation), one could extract `prompt_encoding_time(p)` and `g` *for that API's serving stack.* These empirically-derived parameters would be the denoised runtime parameters, but they might correlate with what idealized runtime would be if the architecture were known. A research direction: collect `(prompt_encoding_time(p), g)` estimates from multiple APIs for multiple models, obtain the true architectures where possible (for open models), and test whether the API-observed parameters can predict the idealized runtime parameters through a learned mapping. This is effectively a "reverse engineering" approach to efficiency comparison—can we infer architectural efficiency from observable scaling behavior without knowing the architecture? A negative result (API-observed parameters do not predict idealized parameters well, because provider optimizations obscure the signal) would validate the paper's claim that architectural transparency is necessary. A positive result would provide a practical workaround for the increasing opacity of frontier models.

**Establish inference efficiency scaling laws: how does idealized runtime scale with parameter count, hidden size, and layer count?** The paper evaluates ten models spanning 6B to 530B parameters, but presents the results as individual data points on scatter plots (Figure 9) rather than fitting scaling relationships. Given the parametric form `t(p,o) = f_p(p; h,l,n) + (o-1) · f_g(h,l,n)`, where `f_p` and `f_g` are functions of the architecture hyperparameters, one could fit predictive models for `prompt_encoding_time` and `g` as functions of `(h,l,n)` across the ten evaluated models and test whether these predictions hold for new architectures. This is the inference-time analog of the training scaling laws literature (Kaplan et al., 2020; Hoffmann et al., 2022): rather than predicting training loss from model size and data, predict inference latency from hidden size, layer count, and head count. Such laws would let model designers estimate inference cost *before training*, during the architecture design phase, and would make explicit the latency implications of architectural choices (e.g., "doubling `h` increases prompt encoding time by factor X, but increasing `l` by the same parameter budget increases it by factor Y"). The paper's ten models provide a starting point for such a fit, though more data points (particularly at intermediate sizes) would be needed for reliable extrapolation.

**Adversarial evaluation of the minimum-over-trials denoising approach.** The paper uses minimum-over-trials regression to estimate denoised runtime, running 10 trials per configuration and reporting that 96.6% of raw runtime points are above the denoised estimate (Figure 7a). But how many trials are *enough*? For models with high coefficient of variation (AI21/J1-Grande v1 at ~0.55), the probability of observing the true uncontended minimum in only 10 trials may be low. A systematic evaluation would: (a) for a model with known high variance, collect a large number of trials (e.g., 100–1000) to establish a ground-truth minimum; (b) subsample at different trial counts (5, 10, 20, 50) and measure how the estimated denoised runtime converges to the ground truth; (c) evaluate alternative estimators (e.g., 5th percentile, 10th percentile, or fitting an extreme value distribution to the lower tail) to see if they provide more reliable estimates with fewer trials. This would convert the minimum-over-trials heuristic from a plausible approach into a statistically characterized procedure with known confidence bounds, making the denoised runtime a more rigorous metric.

### Practical Applications and Downstream Use Cases

**Model selection for self-hosting deployments.** An organization planning to deploy an LLM on their own infrastructure (e.g., an enterprise with on-premise GPUs or a startup renting cloud instances) faces a model selection problem: which open-source or licensed model provides the best capability per unit of serving cost? Raw API benchmarks are irrelevant here—the organization will run the model themselves, so API-specific optimizations and load patterns do not apply. The idealized runtime (estimated on the organization's target hardware) directly answers their question. Using the methodology, they would: (1) profile candidate models on their hardware (e.g., 4×A100 GPUs) to obtain `prompt_encoding_time(p)` and `g`; (2) for their expected workload distribution (distribution of `p` and `o`), compute expected per-query idealized runtime and idealized cost; (3) plot accuracy vs. idealized cost for each candidate model and select the Pareto-optimal option. The paper's Figure 9 (idealized cost row) is a template for this analysis, and the paper's finding that BigScience/BLOOM and Yandex/YaLM appear on the idealized cost frontier while larger models like Microsoft+NV/TNLG v2 do not (due to requiring 24 GPUs vs. 4–8) provides a concrete example of how this analysis can surface non-obvious choices—a model with 3× the parameters may have 10× the serving cost, and the capability gain may not justify it.

**Inference cost budgeting for LLM-powered products.** Product teams building LLM-powered features (chatbots, copilots, content generation tools) need to estimate per-query inference cost at scale to model unit economics. API pricing (dollars per 1K tokens) provides one estimate, but if the team is considering multiple providers or a hybrid self-hosted/API architecture, the idealized cost metric provides a provider-independent baseline for what serving *should* cost on standardized hardware. The methodology enables answering: "If we served this model ourselves on A100 GPUs, what would our per-query cost be?" Comparing this to API pricing reveals the provider's margin and can inform negotiation or build-vs-buy decisions. For example, the paper observes that idealized costs are "up to an order of magnitude lower than the charged actual costs" (Section 5.4), which gives product teams a quantitative basis for understanding the premium they pay for managed API access versus self-hosting. For a product serving 1M queries per day, a 10× cost difference between self-hosting and API pricing represents a substantial line item in infrastructure budgets.

**Hardware procurement and upgrade planning.** The paper's A100 vs. V100 comparison (Figure 8) demonstrates a counterintuitive finding: older, cheaper GPUs can be *more expensive per query* when they require more GPUs in parallel to fit the model in memory (V100's 32GB vs. A100's 80GB). This analysis is directly actionable for organizations planning hardware purchases. By profiling their target models on candidate GPU types (A100, H100, L40S, consumer GPUs like RTX 4090), they can compute idealized cost per query for each hardware option and identify the most cost-effective configuration, accounting for both per-GPU rental price and the minimum GPU count needed to serve each model. The methodology makes this analysis efficient: profiling each GPU type requires hours, not days, and the results apply to all workloads the model will serve. As new hardware becomes available (H100 with FP8 support, inference-specialized accelerators), the same profiling procedure can be repeated to evaluate whether upgrading is cost-effective.

**Standardized efficiency reporting in model cards and benchmarks.** The paper's methodology provides a concrete, replicable procedure for reporting inference efficiency that is independent of any specific API provider's infrastructure. A benchmark like HELM could adopt idealized runtime (on a specified reference stack, e.g., "Megatron on A100-80GB") as a standard efficiency metric reported alongside accuracy for every evaluated model. Model creators could report idealized runtime in model cards alongside parameter count, training compute, and benchmark scores, giving downstream users a standardized basis for estimating deployment cost. The key requirement—publishing `h`, `l`, `n`—is already met by many model releases (all ten in Table 1 have public architecture details). Adopting idealized runtime as a community standard would shift the norm from "report parameter count as the efficiency metric" to "report the architectural hyperparameters necessary to compute efficiency," which the paper shows is substantially more informative (Figure 9: parameter count row vs. idealized runtime row show different model rankings).
