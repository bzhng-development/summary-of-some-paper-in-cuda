## 3. Technical Approach

### 3.1 Reader Orientation
This paper builds a **meta‑strategy for allocating a fixed budget of inference‑time computation over a set of candidate methods** so that a language model (PaLM 2‑S*) answers a given math problem as accurately as possible. The problem it solves is that different test‑time techniques (parallel sampling, sequential revisions, beam search) are optimal on different kinds of questions, and the key to efficiency is to **automatically estimate each prompt’s difficulty and then select the right mix of technique, hyper‑parameters, and compute distribution** for that prompt.

### 3.2 Big‑Picture Architecture (Diagram in Words)
The system consists of five major components that interact in a pipeline:

1. **Prompt difficulty estimator** – produces a discrete difficulty level (bin 1 through 5) for the given question, based on the base model’s own success rate or a verifier’s average score.
2. **Compute‑optimal allocation policy (pre‑computed)** – a lookup table that maps (difficulty bin, total generation budget) to a specific combination of strategy hyper‑parameters (e.g., use beam search with width 4, or use 4 sequential revisions per each of 8 parallel chains).
3. **Base LLM (PaLM 2‑S\*, code name Codey)** – generates candidate solutions; serves as the “proposal distribution” from which all answers originate.
4. **Verifier (PRM)** – a fine‑tuned model that scores every intermediate step of a solution; used both for difficulty estimation and for guiding search/selection.
5. **Revision model** – a fine‑tuned variant of the base LLM that can sequentially improve its own answers by conditioning on previous attempts.

Information flows as follows: a prompt enters → the difficulty estimator bins it into one of five quantiles → the allocation policy selects hyper‑parameters (search method, beam width, revision chain length, number of parallel chains) → the base LLM or revision model generates candidate solutions under those settings → the verifier (PRM or revision‑specific ORM) scores the candidates → an aggregation procedure picks the final answer.

### 3.3 Roadmap for the Deep Dive
The remainder of this section builds a detailed understanding of each component in logical order:

- **First**, the formal definition of the compute‑optimal allocation objective (Equation 1), which frames the problem as a per‑prompt optimization and explains why difficulty is the key sufficient statistic.
- **Second**, the procedure for estimating prompt difficulty, since it is the linchpin that enables adaptive allocation and is used across both the search and revision pipelines.
- **Third**, the process reward model (PRM) — how it is trained, how its per‑step scores are aggregated, and how it serves as a verifier for best‑of‑N weighted selection and search.
- **Fourth**, the three search algorithms (best‑of‑N weighted, beam search, lookahead search), their mechanics, their cost model, and why the choice among them depends on difficulty.
- **Fifth**, the revision model — how training data is constructed, how the model performs iterative refinement, and how sequential and parallel sampling are combined.
- **Sixth**, the FLOPs‑matched comparison framework that defines the exchange rate between scaling pretraining and scaling test‑time compute, enabling the final trade‑off analysis.

### 3.4 Detailed, Sentence‑Based Technical Breakdown
This is primarily an **empirical analysis paper** whose core contribution is a prompt‑adaptive meta‑policy for test‑time compute allocation. The technical approach builds on two independently controlled axes — modifying the proposal distribution via revisions and optimizing selection via a process reward model — and then introduces a difficulty‑conditioned coordinator that selects among these techniques on a per‑prompt basis.

#### Compute‑Optimal Strategy and Difficulty Estimation

The allocation problem is formalized as an optimization over strategy hyper‑parameters. Let `$q$` be a prompt, `$y^*(q)$` its ground‑truth correct answer, `$N$` the test‑time compute budget (measured in number of generated complete solutions), and `$\theta$` a vector of all hyper‑parameters that determine how the budget is spent (e.g., which search algorithm, beam width, sequential‑to‑parallel ratio). Define `$\text{Target}(\theta, N, q)$` as the distribution over output tokens induced by the model under strategy `$\theta$` with budget `$N$` on prompt `$q$`. The compute‑optimal strategy `$\theta^*_{q, y^*(q)}(N)$` is then:

$$\theta^*_{q, y^*(q)}(N) = \arg\max_\theta \left( \mathbb{E}_{y \sim \text{Target}(\theta, N, q)} \left[ \mathbb{1}_{y = y^*(q)} \right] \right)$$

In plain language: for a given question and compute budget, we want the inference‑time hyper‑parameters that maximize the probability of producing the exact correct answer. Crucially, `$\theta^*$` depends on the specific prompt `$q$` — a strategy that works best on an easy problem may be sub‑optimal on a hard one, and vice versa.

Because solving this maximization for every possible prompt is intractable, the paper approximates the optimal strategy by conditioning on a single sufficient statistic: **estimated difficulty of the question from the base model’s perspective**. The authors partition the test questions into five difficulty quintiles and, for each bin and budget level, pre‑compute (via cross‑validation) which strategy `$\theta$` maximises accuracy. At test time, the system first estimates the difficulty bin for the given prompt, then looks up the corresponding pre‑computed strategy.

**Defining difficulty without ground‑truth labels.** The difficulty of a question is defined relative to the base LLM, not by the dataset’s human‑assigned difficulty levels. The **oracle difficulty** is obtained by sampling 2048 complete solutions from the base model, computing the pass@1 rate (the fraction correct), and binning the 500 test questions into five quantiles (bin 1 easiest, bin 5 hardest). This requires ground‑truth correctness labels, which are unknown at deployment. Therefore the paper also introduces **predicted (model‑based) difficulty**: instead of checking correctness, it averages the PRM’s final‑answer score (a predicted probability of correctness) over the same 2048 samples and bins the questions by those average scores into five quantiles. This removes the need for ground‑truth labels but still requires the cost of generating 2048 samples; the paper acknowledges this as a deployment‑time exploration cost and a subject for future work.

**Cross‑validation for strategy selection.** To avoid overfitting the compute‑optimal policy to the test set, the paper uses two‑fold cross‑validation within each difficulty bin on the 500‑question test set. For a given budget, the best‑performing strategy is chosen on one fold and evaluated on the other, and the results are averaged. Thus the “compute‑optimal” curves shown in the paper are out‑of‑sample with respect to the strategy choice.

#### Process Reward Model (PRM) Training and Usage

The PRM is a fine‑tuned PaLM 2‑S* model that scores every intermediate step of a solution with a value between 0 and 1, representing the estimated probability that a correct final answer can be reached from that point. It serves as the verifier for all search methods.

**Training procedure: Monte Carlo rollout supervision.** The paper uses the approach of Wang et al. (2023) to avoid expensive human labels (and because the publicly available PRM800k dataset caused distribution shift with PaLM 2 outputs). For each question in the training set:
1. Sample 16 full solutions from the few‑shot prompted base model.
2. For each step in each solution, sample 16 Monte Carlo rollouts from that step forward (using the same base model) and record whether each rollout reaches the correct final answer.
3. The fraction of rollouts that succeed becomes the **soft label** for that step — it is the empirical reward‑to‑go value from the base model’s sampling policy.
4. Fine‑tune the base model as a binary classifier on these soft labels, using binary cross‑entropy loss:

$$\mathcal{L} = -\left(y \log(\hat{y}) + (1 - y) \log(1 - \hat{y})\right)$$

where `$y$` is the rollout‑derived soft target and `$\hat{y}$` is the model’s predicted value. Training hyper‑parameters: AdamW optimizer, learning rate `$3 \times 10^{-5}$`, batch size 128, dropout 0.05, Adam betas (0.9, 0.95), early stopping on a held‑out validation set (10% of the PRM800k training split).

Samples that fail to produce a parsable final answer are filtered out, as they hurt PRM quality in early experiments.

**Step‑wise aggregation.** Once the PRM has scored every step of a complete solution, the system must produce a single solution‑level score. The paper compares taking the minimum across steps (“min”), the product of step probabilities (“prod”), and using only the PRM’s prediction at the **last step** (“last”). Empirically, “last” performed best (Figure 13). The authors hypothesize that because the PRM was trained with soft Monte Carlo returns rather than binary labels, the “last” step naturally captures the expected final correctness. This effectively turns the PRM into an outcome reward model at aggregation time, but the PRM still outperforms a separately trained ORM (Appendix F), indicating that the per‑step training acts as beneficial representation learning.

**Inter‑answer aggregation: best‑of‑N weighted.** When selecting among N complete candidate solutions, the paper does not simply pick the one with the highest score. Instead it applies **best‑of‑N weighted selection** (following Li et al., 2023): for each distinct final answer, the PRM scores of all solutions that produced that answer are summed, and the final answer with the largest total sum is selected. This incorporates a consensus effect — if many diverse solutions converge on the same answer, that answer gets a higher aggregate score, making the selection more robust.

#### Search Algorithms Against the PRM

Three search methods are studied (illustrated in Figure 2). All operate on the few‑shot prompted base LLM and use the PRM for scoring; the final chosen answer is always determined by best‑of‑N weighted aggregation over the N generated candidates.

**Best‑of‑N weighted.** Generate N complete solutions independently from the base model, score each with the PRM (last‑step aggregation), and apply best‑of‑N weighted selection. The generation budget equals N.

**Beam search.** This step‑by‑step search prunes unpromising partial solutions at each step:
1. Sample N candidate first steps.
2. Score each step with the PRM’s step‑level prediction.
3. Keep only the top `$N/M$` highest‑scoring steps, where `$M$` is the **beam width** — the number of expansions from each kept prefix.
4. From each surviving prefix, sample M next‑step continuations, restoring the total number of candidate prefixes to N.
5. Repeat steps 2–4 until the solution terminates or a maximum of 40 expansion rounds is reached.
6. Apply best‑of‑N weighted selection to the N completed solutions.

The generation budget is N (the number of beams). Two main configurations are swept: beam width `$M = \sqrt{N}$` (growing with budget) and a fixed beam width `$M = 4$`.

**Lookahead search.** This method improves the per‑step scoring of beam search by simulating `$k$` additional steps forward before evaluating a prefix. For each candidate prefix, the system rolls out `$k$` steps at temperature 0 (to minimize variance) and uses the PRM’s prediction at the end of the lookahead rollout as the score for that prefix, rather than the raw PRM score at the current step. This can be seen as a special case of Monte Carlo Tree Search where the exploration components are removed (the PRM is already learned and frozen). The cost model accounts for the extra computation: a lookahead search with `$k$` steps costs `$N \times (k+1)$` generations, since each of the N beams uses k extra sampling steps. The paper sweeps `$k = 1$` with `$M = \sqrt{N}$`, and `$k = 3$` with `$M = \sqrt{N}$` and `$M = 4$`. All methods are compared fairly by plotting accuracy against total generation cost (including the lookahead overhead).

**Why the choice depends on difficulty.** The paper’s subsequent experiments show that beam search strongly outperforms best‑of‑N on medium‑difficulty problems (bins 3–4) but **degrades** on easy problems at high budgets, a sign of over‑optimizing the PRM (the verifier signal is exploited). Best‑of‑N, being a weaker optimizer, is safer on easy problems. This motivates the compute‑optimal policy: use best‑of‑N on easy problems (bins 1–2) and beam search on harder ones (bins 3–4), while the hardest problems (bin 5) get little benefit from any method.

#### Revision Model: Modifying the Proposal Distribution

The revision model is a fine‑tuned variant of PaLM 2‑S* that generates an initial answer and then **iteratively refines it** by conditioning on its own previous (incorrect) attempts. This directly improves the proposal distribution, making higher‑quality candidates available before any verifier‑based selection.

**Training data generation.** Because prompting off‑the‑shelf models to self‑correct is ineffective (Huang et al., 2023), the model must be explicitly trained. The procedure builds on Qu et al. (2024) but introduces a post‑hoc data construction approach that avoids expensive on‑policy multi‑turn rollouts:
1. For each training question, sample 64 responses in parallel from the base model at elevated temperature.
2. Filter out answers that fail to produce a parsable final result.
3. For each correct answer, construct a multi‑turn trajectory by pairing it with a sequence of 0 to 4 incorrect answers as context (the number is uniformly sampled from {0,1,2,3,4}).
4. The **last incorrect answer in the context** is chosen to be the one with the smallest **character‑level edit distance** to the correct answer. This ensures the incorrect answer is structurally similar to the correct one, teaching the model to make targeted edits rather than ignoring context and starting afresh. The remaining incorrect answers are sampled randomly from the pool.
5. Fine‑tune the base model with SFT on these trajectories, training only on the tokens of the correct answer.

Training hyper‑parameters: AdamW optimizer, learning rate `$1 \times 10^{-5}$`, batch size 128, dropout 0.0, Adam betas (0.9, 0.95). Because the validation data becomes off‑policy after fine‑tuning, checkpoints slightly after the point where validation loss increases are selected (the revision skill improves even as loss on original trajectories rises).

**Inference with revisions.** At test time, the revision model generates a chain of up to several dozen revisions. Although trained with at most 4 previous answers in context, longer chains are supported by truncating context to the most recent 4 answers. The model’s pass@1 at each step gradually improves (Figure 6, left), showing that it learned to generalise beyond its training horizon.

A critical problem is **correct‑to‑incorrect reversion**: because the training data contained only incorrect‑to‑correct transitions, the model may encounter a correct answer in its context and mistakenly “revise” it into an incorrect answer. The paper reports that about 38% of correct answers get reverted. To mitigate this, the system does not simply take the last revision; instead it uses majority voting or a verifier to select the best answer across the entire chain.

**Trading off sequential and parallel compute.** The revision model can be used in two extreme modes:
- **Fully parallel:** generate N independent initial answers (each in its own chain) and select the best one with a verifier.
- **Fully sequential:** generate a single chain of N revisions and select the best answer within that chain.

More generally, the system can hybridize: generate `$S$` parallel chains, each of length `$L$`, such that `$S \times L = N$`. The hierarchical selection works as follows:
- Within each chain, a verifier (a revision‑specific ORM, fine‑tuned on revision model outputs to avoid distribution shift) selects the best answer using best‑of‑N weighted aggregation.
- Then, across the S best answers (one from each chain), another round of best‑of‑N weighted aggregation picks the final answer.

Majority voting is used as an alternative selection mechanism, especially when sample counts within a chain are too small for a verifier; then all answers across all chains are pooled and the majority answer is taken.

**Verifier for revisions.** The PRM trained on base model outputs performs worse on revision model outputs due to distribution shift, so a separate ORM is fine‑tuned. This ORM is given the same context as the revision model (previous revision attempts), which slightly improves its accuracy.

#### FLOPs‑Matched Comparison: Pretraining vs. Test‑Time Compute

To answer when test‑time compute can substitute for scaling up model parameters, the paper defines an exchange rate based on total FLOPs. The standard approximations are used:

- Pretraining FLOPs: `$X = 6 N D_{\text{pretrain}}$`
- Inference FLOPs (for greedy decoding): `$Y = 2 N D_{\text{inference}}$`

where `$N$` is the number of model parameters, `$D_{\text{pretrain}}$` the number of pretraining tokens, and `$D_{\text{inference}}$` the total number of tokens generated during inference for the considered set of prompts.

If we scale up model parameters by a factor of `$M$` (while keeping pretraining data fixed, as in the LLaMA paradigm), both pretraining and inference FLOPs multiply by `$M$`, giving a total of `$M(X+Y)$`. To match this total budget using the smaller model with extra test‑time compute, the smaller model’s inference compute must be scaled by a factor:

$$\text{Inference multiplier} = M + 3 \cdot \frac{D_{\text{pretrain}}}{D_{\text{inference}}} \cdot (M - 1)$$

Restated in prose: the amount of extra inference compute the smaller model can use equals the parameter scaling factor `$M$` plus an additional term that accounts for the fact that the saved pretraining FLOPs can be re‑invested. This term is proportional to `$M-1$` and the ratio of pretraining tokens to inference tokens. Crucially, the extra inference budget depends on `$R = D_{\text{inference}} / D_{\text{pretrain}}$`: when `$R \ll 1$` (very few inference tokens relative to pretraining), the smaller model gets a large inference budget; when `$R \gg 1$` (many inference tokens), the budget is tight because the larger model’s per‑token inference cost dominates. The paper evaluates three representative values: `$R = 0.16$` (`$R \ll 1$`), `$R = 0.79$` (`$R \approx 1$`), and `$R = 22$` (`$R \gg 1$`), and compares compute‑optimal test‑time scaling of PaLM 2‑S* against a model with `$\sim 14\times$` more parameters (using greedy decoding without extra test‑time compute). This framework allows a direct, FLOP‑normalized investigation of the trade‑off between investing compute in training larger models versus keeping the model small and spending the compute at inference time.
