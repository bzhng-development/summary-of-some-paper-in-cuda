# Coffee-Gym: An Environment for Evaluating and Improving Natural Language Feedback on Erroneous Code

**ArXiv:** [2409.19715](https://arxiv.org/abs/2409.19715)

## 🎯 Pitch

This paper introduces **COFFEE-GYM**, a comprehensive reinforcement learning environment for training open-source models that generate natural language feedback to guide code editing.

---

## 1. Executive Summary

This paper introduces **COFFEE-GYM**, a comprehensive reinforcement learning environment for training open-source models that generate natural language feedback to guide code editing. COFFEE-GYM combines two core components: **COFFEE**, a dataset of human-written code edit traces with annotated pairwise feedback across diverse difficulty levels, and **COFFEEEVAL**, a unit-test-driven reward function that measures feedback helpfulness by assessing whether the edited code passes test cases (executing the revised code against hidden inputs and checking outputs). The feedback model trained with PPO and COFFEEEVAL achieves 73.8% Pass@1 on HumanEvalFix when paired with DeepSeekCoder-7B as the editor, closing the gap with closed-source models—matching GPT-4-Turbo's feedback performance (74.4%) while outperforming GPT-3.5-Turbo feedback (72.5%). The approach demonstrates that reinforcement learning with execution-grounded rewards produces more helpful feedback than supervised fine-tuning alone, establishing that open-source feedback models can rival closed-source alternatives only when reward signals faithfully reflect the downstream impact of feedback on code correctness.

## 2. Context and Motivation

### The Core Problem: Open-Source Models Produce Low-Quality Code Editing Feedback

The fundamental gap this paper addresses is that **open-source code LLMs cannot generate effective natural language feedback for code editing**, despite their competence at code generation itself. This creates a hard dependency on expensive, closed-source models like GPT-4 whenever a system needs to provide descriptive guidance for fixing buggy code. The paper quantifies this gap directly: when DeepSeekCoder-7B generates its own feedback (Self-Feedback), the resulting code editing Pass@1 on HumanEvalFix is 67.7% — only marginally above the no-feedback baseline of 60.4% (Table 3). In contrast, the same model with feedback from GPT-4-Turbo reaches 74.4%. The 6.7 percentage-point gap between what open-source models can produce and what closed-source models can produce is the specific deficit the paper sets out to close.

This problem matters for three concrete reasons the paper identifies (Section 1):

- **API cost and rate limits**: Using GPT-4 for feedback generation incurs per-query costs and throughput constraints that become prohibitive at scale. Training an open-source alternative amortizes the cost across many queries.
- **Security and confidentiality**: Submitting code to external API endpoints exposes potentially proprietary or sensitive source code. The authors cite Greshake et al. (2023) and Siddiq and Santos (2023) to highlight risks of indirect prompt injection and code leakage in LLM-integrated applications.
- **Intervention in self-improvement pipelines**: Autonomous code editing loops (where a model writes code, tests it, and refines it) require continuous feedback generation. An open-source feedback model makes such pipelines practical without external API calls.

### Why Simple Fine-Tuning Fails: The Misalignment Problem

The most intuitive approach — supervised fine-tuning (SFT) on a dataset of (problem, buggy code, feedback, correct code) — produces models that **generate plausible feedback but fail to improve editing outcomes**. The paper demonstrates this empirically in the bottom of Figure 1: an SFT model trained on the Code-Feedback dataset (Zheng et al., 2024) using the same backbone (DeepSeekCoder-7B) achieves only 62.1% Pass@1 on HumanEvalFix, compared to 73.8% for the RL-trained model. Both use the exact same editor model (DeepSeekCoder-7B); the difference is purely in the helpfulness of the feedback.

This failure mode is not unique to code. The authors cite Liu et al. (2022) to establish that supervised fine-tuning in text generation tasks does not optimize for the downstream impact of generated text — the model learns to imitate the surface form of feedback without internalizing which feedback properties actually cause the editor to produce correct code. A concrete example appears in the paper's qualitative analysis (Appendix C.3, Figure 13): the SFT model produces feedback that appears reasonable but includes unnecessary information that "may confuse the editor," while the PPO-trained model provides "focused and helpful feedback on the incorrect part without unnecessary information."

### Two Gaps in the RL-for-Feedback Pipeline

The paper frames its contribution through the lens of reinforcement learning, identifying what the RLHF paradigm (Ouyang et al., 2022) requires and what is missing for feedback generation specifically. The authors identify three challenges (Section 2.3):

#### Gap 1: No Dataset with the Required Properties

Training a feedback model with RL requires data that existing code-editing datasets do not provide:

- **Coverage of diverse errors at varying difficulty**: Model-generated error datasets (like those produced by prompting GPT models to insert bugs) tend to produce errors that cluster in embedding space. The paper demonstrates this quantitatively in Figure 5(b): CodeBERT embeddings of incorrect solutions from ChatGPT and GPT-4 show higher pairwise cosine similarity than human-written incorrect solutions, meaning machine-generated errors are less diverse. A model trained only on such data will have limited exposure to the error types humans actually make, especially on problems that GPT models themselves cannot solve (Figure 5c shows GPT-4-Turbo achieves only 16.6% Pass@1 on the hardest problems in COFFEE, compared to 48.0% human solve rate).

- **Pairwise feedback data**: Both PPO (which trains an explicit reward model) and DPO (which optimizes directly from preferences) require preference pairs — a chosen (helpful) feedback and a rejected (unhelpful) feedback for the same (problem, buggy code) input. Standard feedback datasets contain only correct feedback annotations (e.g., Code-Feedback by Zheng et al., 2024). The paper needs both correct and incorrect feedback annotations paired with the same input to construct meaningful training signals.

- **Test cases for execution-grounded rewards**: The paper's core design insight is that feedback quality should be measured by whether the editor produces correct code after receiving the feedback, not by surface-level properties of the feedback text. This requires hidden test cases — input-output pairs — for each problem to independently verify code correctness. Existing code editing benchmarks like HumanEvalFix include test cases for evaluation, but they do not provide them at the scale needed for reward computation during training.

#### Gap 2: No Validated Reward Function That Respects Feedback-Edit Alignment

The standard approach to evaluating text quality with LLMs is to use a powerful model (typically GPT-4) as a judge, producing Likert-scale scores based on a rubric. This approach is called G-Eval (Liu et al., 2023c) in the paper. However, the paper identifies two problems with this approach for feedback evaluation:

- **LLM judges do not correlate with editing outcomes**: Table 2 shows that GPT-4-Turbo with G-Eval achieves only a 0.135 Pearson correlation with ground-truth feedback helpfulness labels, and a mean squared error of 0.415. This is barely better than random. The reason is that LLM judges evaluate the feedback text itself — its grammar, specificity, apparent relevance — without measuring whether it actually causes the editor to fix the bug. A feedback string can read beautifully and still mislead the editor.

- **API cost makes online RL infeasible**: PPO requires computing rewards for every generated feedback during training (potentially thousands per training run). Calling GPT-4 for each reward would be both slow and expensive, making the training loop impractical even if the reward quality were high.

A more direct approach — using the code editor model itself to evaluate feedback by checking if the edited code is correct — also fails. The paper demonstrates in Table 2 that **code LLMs are biased toward producing correct code regardless of feedback quality**. When given incorrect feedback, GPT-4-Turbo still produces correct edits 51.8% of the time (the False Positive rate). This means the editor's output cannot be used directly as a reward signal: a high pass rate after editing may indicate a strong editor rather than helpful feedback.

### The Gap the Paper Addresses in the Literature

The paper positions itself at the intersection of several active research threads, each with acknowledged limitations:

**Code editing benchmarks** (Muennighoff et al., 2023; Tian et al., 2024; Guo et al., 2024b) evaluate whether models can fix bugs but do not provide training infrastructure for feedback generation. The paper notes that DebugBench and CodeEditorBench have critical evaluation flaws — ground-truth solutions fail their own unit tests — making them unreliable for the rigorous evaluation needed in RL.

**LLM-based feedback methods** like Self-Refine (Madaan et al., 2023) and Reflexion (Shinn et al., 2023) demonstrate that closed-source LLMs can generate effective feedback through iterative prompting, but they provide no mechanism for training open-source alternatives. They treat feedback generation as an emergent capability of large models rather than a learnable skill.

**Execution feedback** (Chen et al., 2023; Gou et al., 2023) — providing error messages and stack traces rather than natural language — improves editing but is less effective than natural language guidance. Table 3 shows that Execution Feedback improves DeepSeekCoder-7B from 60.4% to 68.3% on HumanEvalFix (+7.9), while the paper's feedback achieves 73.8% (+13.4). The gap between execution feedback and NL feedback (+5.5 percentage points) represents the value of descriptive, reasoning-level guidance that goes beyond what error messages convey.

**RL for code generation** (Le et al., 2022; Liu et al., 2023a; Shen et al., 2023) uses unit test results as rewards to improve code generation models. The paper draws inspiration from this line of work but identifies a crucial difference: using execution results to reward code generation is straightforward because the code is executed directly; using execution results to reward *feedback* requires an intermediate editor model, and standard code LLMs do not faithfully translate feedback quality into editing outcomes. The paper's contribution is solving this indirection problem.

**Concurrent work** by Ni et al. (2024) explores building feedback models but, as the paper notes, "they do not provide the dataset used nor the model checkpoint," making their work unreproducible and impossible to build upon. COFFEE-GYM releases both dataset and model checkpoint.

### Why the Problem Cannot Be Solved with Existing Resources

The paper's architecture reveals why off-the-shelf solutions are insufficient through a diagnostic experiment (Table 2, comparing Editing baselines). When standard code LLMs (GPT-4-Turbo, GPT-3.5-Turbo, DeepSeekCoder-7B) are used as editors to evaluate feedback:

- GPT-4-Turbo achieves 53.0% True Positive rate (passes on correct feedback) but also 51.8% False Positive rate (passes on incorrect feedback), resulting in only 50.6% precision. This means the model is essentially guessing — correct and incorrect feedback produce indistinguishable editing outcomes.
- DeepSeekCoder-7B shows 36.0% True Positive vs. 28.8% False Positive (55.6% precision), which is slightly more discriminative but still far from reliable.
- The Pearson correlation between these edit-based scores and true feedback helpfulness never exceeds 0.101 for the base models.

This failure is not obvious a priori: one might expect that a good code editor would only produce correct code when given helpful guidance. The paper's finding that strong code LLMs "correct" code even with misleading feedback challenges this assumption and motivates the need for a purpose-built editor that is trained to be faithful to feedback quality.

### How This Paper Positions Itself

The paper does not propose a new RL algorithm or a new model architecture. Instead, it constructs the **missing infrastructure** that makes standard RL approaches (PPO, DPO, rejection sampling) applicable to feedback generation for the first time. The contribution is an environment — a dataset, a reward function, and a reference implementation — that converts feedback model training from an unexplored research problem into a well-defined RL task.

The paper's framing (Section 1, abstract) explicitly draws the parallel to RLHF but notes that RLHF for feedback has been blocked by data availability and reward reliability. COFFEE-GYM removes these blockers. This positions the work as enabling rather than competing: future improvements in RL algorithms, reward modeling, or code editing architectures can be deployed within COFFEE-GYM and evaluated against the baselines established in Section 5.

The paper also carefully distinguishes itself from its own preprint (Moon et al., 2023), noting in the abstract footnote that while both works share the COFFEE dataset, the current submission introduces "significant advancements in methodology, analysis, and results" — specifically the COFFEEEVAL reward function design, the editor faithfulness training, the systematic RL algorithm comparison, and the human evaluation studies.

## 3. Technical Approach

This is primarily an **infrastructure and systems paper** whose core idea is that reinforcement learning can train open-source models to generate helpful code-editing feedback, but only if two conditions are met: (1) the training data includes diverse human-written code edit traces with pairwise correct/incorrect feedback across difficulty levels, and (2) the reward function measures feedback helpfulness through execution outcomes of the edited code rather than surface-level text evaluation or naive editor pass rates.

### 3.1 Reader Orientation

The paper builds a **training environment** — not a single model — that takes a base code LLM (like DeepSeekCoder-7B) and produces a fine-tuned feedback model capable of generating natural language guidance that actually helps an editor model fix buggy code. The environment solves the problem that supervised fine-tuning produces feedback models that *sound* reasonable but fail to improve editing outcomes, while closed-source models (GPT-4) generate genuinely helpful feedback but are expensive and expose code to external APIs. The solution's shape is a reinforcement learning loop: a feedback model generates candidate feedback, a purpose-built editor model applies that feedback to buggy code, the edited code is executed against hidden test cases, and the pass/fail outcome is used as a reward signal to update the feedback model via PPO.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components, deployed in two phases (training infrastructure construction, then RL training):

1. **COFFEE Dataset** — human-written code submission histories from a competitive programming platform, augmented with GPT-3.5-Turbo-annotated pairwise feedback (correct and incorrect) and synthetic test cases. This provides the raw material for training both the editor model and the feedback model.

2. **Faithful Code Editor** (ϕ) — a DeepSeekCoder-7B model fine-tuned on COFFEE to produce edits that correlate with feedback quality. Unlike off-the-shelf code LLMs, this editor is trained on both (feedback, correct code) pairs and (misleading feedback, incorrect code) pairs so that its pass/fail behavior reflects the helpfulness of the input feedback rather than its own editing capability.

3. **COFFEEEVAL Reward Function** — a unit-test-driven scoring mechanism that takes feedback `$\hat{c}$`, feeds it to the faithful editor `$\phi$` along with the problem description `$q$` and buggy code `$\tilde{y}$`, executes the edited code `$y' = \phi(q, \tilde{y}, \hat{c})$` against hidden test cases `$T$`, and returns the fraction of passed tests as the reward. This is the core alignment mechanism.

4. **SFT-Initialized Feedback Model** (θ) — a DeepSeekCoder-7B model first fine-tuned on COFFEE's correct feedback annotations to learn the basic mapping from (problem, buggy code) to NL feedback. This serves as the starting policy for RL.

5. **RL Training Loop** — using PPO (or DPO, or rejection sampling), the feedback model generates candidate feedback, COFFEEEVAL computes rewards, and the policy is updated to maximize expected reward. The loop runs online for PPO (continuously updating the reference model) or offline for DPO (constructing preference pairs from ranked samples).

Information flows through the system during RL training as follows: a (problem, buggy code) pair is sampled from COFFEE → the feedback model generates feedback → the faithful editor produces edited code conditioned on that feedback → the edited code is executed against test cases → the pass ratio becomes the reward → the RL algorithm updates the feedback model's parameters.

### 3.3 Roadmap for the Deep Dive

- **First**, the COFFEE dataset construction pipeline — how human edit traces are collected, filtered, and augmented with feedback annotations and synthetic test cases. This is the foundation everything else depends on.
- **Second**, the faithful code editor training procedure — why standard code LLMs cannot serve as the editor in a reward function, the precise two-phase training recipe, and the keyword token mechanism that prevents confusion during learning.
- **Third**, the COFFEEEVAL reward function — its mathematical definition, the execution protocol, and the critical design choice to measure edited code correctness rather than feedback text quality.
- **Fourth**, the SFT initialization of the feedback model — the supervised fine-tuning step that precedes RL and why it is necessary.
- **Fifth**, the RL training algorithms deployed within the environment: PPO with COFFEEEVAL as the reward model, DPO with preference pair construction strategies, and rejection sampling as a baseline, including the specific preference pair construction methods and their tradeoffs.

### 3.4 Detailed, Sentence-Based Technical Breakdown

#### 3.4.1 COFFEE Dataset Construction: Human Edit Traces, Pairwise Feedback, and Synthetic Test Cases

The COFFEE dataset provides the raw training material for both the editor model and the feedback model. Its construction follows a four-stage pipeline (Section 3.1, Figure 3): (1) collecting human-authored code submission histories from an online competitive programming platform, (2) forming (problem, wrong code, correct code) triplets from submission sequences, (3) annotating pairwise NL feedback describing the differences between code pairs, and (4) augmenting each instance with synthetic test cases for execution-based evaluation.

**Stage 1: Collecting Human Edit Traces.** The authors scrape submission histories from an online competitive programming platform (specifically, "an online competitive programming platform" that appears to be https://www.acmicpc.net/ based on the footnote in Section 3.1.1). For each problem `$q$` on the platform, human programmers repeatedly submit solutions until one passes all hidden test cases. The platform records every submission — both incorrect and correct — along with the submitting user's identity.

The key data structure extracted is a **submission history**: for a given user solving problem `$q$`, the platform records a sequence of submissions `$\{\tilde{y}_1, \tilde{y}_2, ..., y^*_n\}$` where `$\{\tilde{y}_k\}_{k=1}^{n-1}$` are incorrect solutions and `$y^*_n$` is the first correct solution. Each `$\tilde{y}_k$` and `$y^*_n$` is the full source code submitted at that attempt.

The authors impose two collection constraints to ensure data quality and diversity. First, they collect an **equal number of problems from each of five difficulty levels** defined by the platform (ranging from beginner to expert). This prevents the dataset from being skewed toward easy problems that current LLMs already solve. The difficulty labels are platform-specific tiers (the paper mentions Bronze, Silver, Gold in Figure 5c, suggesting a tiered ranking system common in competitive programming platforms). Second, they collect submission histories from **100 different users** per problem (where available), ensuring that the dataset captures diverse coding styles and error patterns rather than the idiosyncratic mistakes of a few programmers.

The authors explicitly filter out two categories of problematic data. First, they remove "submissions from different users whose correct solutions are identical," noting in Appendix A.1.1 that "these solutions are usually copied from the web without undergoing editing processes" — meaning they would introduce (buggy code, correct code) pairs where no actual editing occurred, which would not provide meaningful training signal for a feedback model. Second, for feedback annotation, they filter out submission histories where "the LLM fails to find any errors" (i.e., where the model annotating feedback cannot identify differences between the code versions), though the paper does not specify the exact filtering rate.

**Stage 2: Forming Edit Triplets.** From each submission history `$\{\tilde{y}_1, \tilde{y}_2, ..., y^*_n\}$`, the authors construct two types of pairs for different purposes:

For **correct feedback annotation**, they pair each incorrect submission with the final correct submission: `$(q, \tilde{y}_k, y^*_n)$` for `$k = 1, ..., n-1$`. These triplets represent "edit this wrong code into the correct code" and will be annotated with feedback describing what changes are needed.

For **incorrect feedback annotation**, they pair consecutive incorrect submissions: `$(q, \tilde{y}_k, \tilde{y}_{k+1})$` for `$k = 1, ..., n-2$`. These represent transitions between two wrong solutions — the programmer thought they were fixing the bug but produced another incorrect version. The feedback annotating these pairs will describe changes that *did not* fix the problem, providing the negative examples needed for pairwise preference data.

The distinction between these two types is crucial: correct feedback describes changes from wrong to right (helpful guidance), while incorrect feedback describes changes from wrong to a different wrong (misleading guidance). Having both types for the same initial wrong code `$\tilde{y}_k$` enables constructing preference pairs `$c^+ \succ c^- | q, \tilde{y}_k$` where `$c^+$` guides toward the correct solution and `$c^-$` guides toward another incorrect solution.

**Stage 3: Annotating Pairwise Feedback with GPT-3.5-Turbo.** The authors use GPT-3.5-Turbo (not GPT-4) to annotate NL feedback for both correct and incorrect pairs. This is a deliberate cost-saving choice — the dataset requires annotating thousands of pairs, and GPT-3.5-Turbo is substantially cheaper than GPT-4. The quality is validated through human evaluation: on a sample of 100 instances from the COFFEE test set, human raters on Amazon Mechanical Turk scored the annotated feedback at an average of 3.88 on a 5-point Likert scale (with standard deviation 0.91), indicating "generally acceptable" quality (Appendix A.1.2, Table 4). The full distribution shows 42.0% rated 4 ("mostly correct") and 27.0% rated 5 ("completely correct"), with only 7.6% rated 1 or 2.

The annotation prompts (provided in full in Appendices D.1 and D.2) differ between correct and incorrect feedback:

- **Correct feedback prompt (Appendix D.1):** The model receives the problem description, the incorrect code `$\tilde{y}_k$`, and the correct code `$y^*_n$`, and is instructed to "Generate an explanation, analyzation, and plan to generate code" that describes the differences. The prompt includes four example instances with their explanations to establish the expected format. The key instruction is to produce feedback that explains how to get from the wrong code to the correct code — it is a **differential explanation**, not a general code review.

- **Incorrect feedback prompt (Appendix D.2):** The model receives the problem description, the earlier incorrect code `$\tilde{y}_k$`, and the later incorrect code `$\tilde{y}_{k+1}$`, and is instructed to "Generate feedback that guides the refinement from Code before editing to Code after editing" with the constraint "Assume that the code after editing is 100% correct." This constraint is notable — it instructs the model to produce feedback as if `$\tilde{y}_{k+1}$` were correct, even though it is not. This creates feedback that is internally consistent and plausible but ultimately misleading, which is exactly the property needed for the negative examples in pairwise preference data.

- **Sampling parameters:** Both prompts use top-p sampling with `$p = 0.95$`, temperature `$T = 0.7$`, and a maximum of 500 generation tokens (Appendix A.1.1).

**Stage 4: Augmenting Synthetic Test Cases.** The competitive programming platform does not make its test cases publicly available — the platform evaluates submissions server-side against hidden inputs and only reports pass/fail. To enable execution-grounded reward computation, the authors synthesize test cases using GPT-3.5-Turbo.

For each problem in COFFEE, the prompt (Appendix D.3) provides the problem's input format specification and the correct solution code, and asks GPT-3.5-Turbo to "provide at least 30 challenging test input values to evaluate its functionality." The generated inputs are then executed against the correct solution `$y^*_n$` to obtain expected outputs. Any test case whose execution fails (e.g., the generated input causes a runtime error in the correct code) is filtered out.

This process yields an average of **35.5 test cases per problem** (Section 3.1.3, Figure 4 statistics). Each test case `$t_i \in T$` consists of an input `$x_i$` and the expected output `$z_i = y^*(x_i)$`, where `$y^*$` is the ground-truth correct code.

The authors validate these synthetic test cases by checking whether any incorrect solutions in the evaluation set pass all of them. They sample 200 incorrect code instances from the COFFEE evaluation set and compute the pass ratio (fraction of test cases passed) for each. The results (Table 5, Appendix A.1.4) show a **maximum pass ratio of 0.985** and a **mean pass ratio of 0.342** — no incorrect solution passes all test cases, and on average, incorrect solutions fail the majority of test cases. The distribution has a median of 0.162 and a 75th percentile of 0.693, indicating that most incorrect solutions pass fewer than 70% of test cases. The authors further verify on COFFEE-TEST (the held-out evaluation set) that "no wrong solutions pass all the test cases" (Appendix A.1.4).

This validation addresses a critical threat to validity: if incorrect code could pass all synthetic tests, COFFEEEVAL would assign a reward of 1.0 to unhelpful feedback that guides the editor toward that incorrect code, breaking the alignment signal.

**Dataset statistics.** The final COFFEE dataset (Figure 4 statistics panel) contains:
- **44,782 instances** total (though the paper does not specify the train/validation/test split sizes explicitly, Section 5.1.1 mentions COFFEE-TEST has 180 held-out instances with no overlapping problems).
- Average **4.19 submissions per user** per problem (length of edit trace).
- Problems come from **742 total problem sets** across five difficulty levels.
- Average solution length: **674.1 characters**; average wrong code length: **674.1 characters** (essentially the same, suggesting edits tend to be localized rather than complete rewrites); average feedback length: **269.0 characters**; average problem description length: **649.4 characters**.

**Diversity and difficulty analysis.** The authors conduct three analyses to characterize COFFEE's distributional properties (Section 3.1.1, Figure 5):

- **Edit trace length by difficulty (Figure 5a):** The average number of submissions per user increases steadily with problem difficulty level. This validates that harder problems genuinely require more editing attempts, meaning COFFEE captures the full difficulty spectrum from trivial fixes to multi-step debugging.

- **Code embedding similarity (Figure 5b):** Using CodeBERT (Feng et al., 2020) to embed incorrect solutions, the authors compare the distribution of pairwise cosine similarities between human-written incorrect solutions versus machine-generated incorrect solutions (from ChatGPT and GPT-4). The histogram shows that machine-generated codes cluster at higher similarity values — they are more homogeneous. Human-written codes show a broader distribution with a lower mean similarity, confirming that collecting human edit traces captures more diverse error patterns than synthetic error injection.

- **GPT-4 vs. human solve rates (Figure 5c):** Across the five difficulty levels, GPT-4-Turbo's Pass@1 drops from 63.1% on Bronze to 16.6% on Gold, while human solve rates drop from 57.1% to 40.7%. Notably, human solve rates exceed GPT-4 on the hardest tier (40.7% vs. 16.6%), confirming that COFFEE includes problems where current LLMs fail but humans succeed — exactly the regime where feedback model training needs human-authored data rather than model-generated synthetic data.

**Train-test overlap analysis (Appendix A.1.6, Figure 10).** To ensure COFFEE does not leak solutions into benchmarks used for evaluation, the authors measure line-level overlap between COFFEE training instances and HumanEval test problems. Following the methodology of Odena et al. (2021), they compute the fraction of duplicated lines and the absolute number of duplicated lines per instance. The results show that "most solutions in COFFEE do not contain lines that appear in the benchmark dataset" — the distribution of overlap fractions is heavily concentrated near zero, with the vast majority of instances having no duplicated lines at all. This validates that improvements on HumanEvalFix are not due to memorization.

#### 3.4.2 Faithful Code Editor Training: Aligning Editing Behavior with Feedback Quality

The COFFEEEVAL reward function (Section 3.2, Equation 1) requires an editor model `$\phi$` that faithfully translates feedback quality into editing outcomes: helpful feedback should produce correct edits, unhelpful feedback should produce incorrect edits. The paper demonstrates empirically (Section 4.2, Table 2) that standard code LLMs fail this requirement — they tend to produce correct code even when given misleading feedback, making their output unusable as a reward signal.

The solution is to train a **purpose-built editor** on both positive and negative examples from COFFEE, using a two-phase training procedure (Appendix A.2.2). The backbone model is DeepSeekCoder-7B (specifically the instruct variant, based on the HuggingFace model reference in Appendix A.2.1 footnote).

**Training data construction.** The editor is trained on two disjoint subsets of COFFEE:

- `$D_{\text{correct}}$`: instances where the feedback describes changes from wrong to correct code, i.e., `$(q, \tilde{y}, c^*, y^*)$` where `$c^*$` is the correct feedback (from Stage 3 of dataset construction, describing differences between `$\tilde{y}$` and `$y^*$`) and `$y^*$` is the ground-truth correct solution.

- `$D_{\text{wrong}}$`: instances where the feedback describes changes from wrong to a different wrong code, i.e., `$(q, \tilde{y}, \tilde{c}, \tilde{y}_{\text{next}})$` where `$\tilde{c}$` is the incorrect feedback (describing differences between `$\tilde{y}_k$` and `$\tilde{y}_{k+1}$`, two consecutive incorrect submissions) and `$\tilde{y}_{\text{next}}$` is the subsequent incorrect submission.

**Phase I: Keyword-conditioned training.** In the first phase, the editor is trained to generate the target code with an explicit correctness indicator prepended. For correct edits, the target sequence is `[Correct] y^*`; for incorrect edits, the target sequence is `[Wrong] \tilde{y}_{\text{next}}`. The training objective is:

$$L(\phi) = -\sum_{(q, \tilde{y}, c^*, y^*) \in D_{\text{correct}}} \log p_\phi(\texttt{[Correct]}, y^* \mid q, \tilde{y}, c^*) - \sum_{(q, \tilde{y}, \tilde{c}, \tilde{y}_{\text{next}}) \in D_{\text{wrong}}} \log p_\phi(\texttt{[Wrong]}, \tilde{y}_{\text{next}} \mid q, \tilde{y}, \tilde{c})$$

where `$p_\phi$` is the editor model's token-level probability distribution and the log-probability is summed over all tokens in the keyword plus code sequence.

**What it computes:** the standard autoregressive negative log-likelihood for two types of training instances. For each correct-edit instance, the model is trained to first emit the token `[Correct]` and then generate the correct solution `$y^*$` conditioned on the problem `$q$`, the buggy code `$\tilde{y}$`, and the correct feedback `$c^*$`. For each incorrect-edit instance, the model is trained to first emit `[Wrong]` and then generate the subsequent incorrect submission `$\tilde{y}_{\text{next}}$` conditioned on the same `$q$` and `$\tilde{y}$` but with misleading feedback `$\tilde{c}$`. The loss sums over all tokens in both sequences.

**Why this form:** the keyword tokens serve as an explicit signal to the model about whether the target code represents a correct or incorrect edit. This prevents a training ambiguity: without keywords, the model sees `$y^*$` as the target for some instances and `$\tilde{y}_{\text{next}}$` for others, with no in-context cue distinguishing them. The model might learn to simply ignore the feedback and produce a plausible-looking code edit, which is exactly the behavior of standard code LLMs that COFFEEEVAL needs to avoid. By conditioning generation on the keyword, the model learns to associate helpful feedback with `[Correct]` outputs and misleading feedback with `[Wrong]` outputs. The paper follows the approach of Wang et al. (2023a), who used similar keyword tokens for self-consistent chain-of-thought distillation.

**Phase II: Keyword-free training.** After Phase I converges, the model is further fine-tuned on the same dataset but **without the keyword tokens**. The training objective becomes:

$$L(\phi) = -\sum_{(q, \tilde{y}, c^*, y^*) \in D_{\text{correct}}} \log p_\phi(y^* \mid q, \tilde{y}, c^*) - \sum_{(q, \tilde{y}, \tilde{c}, \tilde{y}_{\text{next}}) \in D_{\text{wrong}}} \log p_\phi(\tilde{y}_{\text{next}} \mid q, \tilde{y}, \tilde{c})$$

**What it computes:** the same autoregressive negative log-likelihood as Phase I, but with the keyword tokens removed from the target sequence. During inference, the editor will not be prompted with a keyword — it simply receives `$(q, \tilde{y}, \hat{c})$` and must generate an edit `$y'$`. Phase II teaches the model to directly map from (problem, buggy code, feedback) to the appropriate code without the keyword crutch.

**Why this form:** Phase I teaches the model to distinguish correct from incorrect edits using an explicit signal; Phase II internalizes that distinction so it can operate without the signal at inference time. This is a standard curriculum learning pattern: use auxiliary information during early training to establish the right representations, then remove it so the model learns to make the distinction implicitly. The alternative — training without keywords from the start — would risk the model converging to the "ignore feedback, produce a reasonable code edit" behavior that makes standard code LLMs unusable as editors.

**Implementation details.** The editor is trained using QLoRA (Dettmers et al., 2023) with 4-bit quantization of the base DeepSeekCoder-7B model. The LoRA configuration uses a rank (dimension of low-rank matrices) of 64 and an alpha of 16. Training uses a learning rate of `$5 \times 10^{-5}$`, a batch size of 4, and runs for 2 epochs on 8 NVIDIA GeForce RTX 3090 GPUs (Appendix A.2.1). Both Phase I and Phase II use the same hyperparameter settings. The prompt format for the editor (Appendix D.3.1) structures the input as:

```
Description: {problem_description}
- output format: {output_format}
- input format: {input_format}
Incorrect code:
```python
{wrong_code}
```
Feedback: {feedback}
Correct code:
```

The editor is trained to generate only the code after "Correct code:" — the prompt, description, buggy code, and feedback are part of the conditioning context, and the loss is computed only on the target code tokens (plus the keyword token in Phase I).

**Validation of faithfulness.** The paper validates the editor's faithfulness in Section 4.2 (Table 2). The key metric is **discrimination**: when given correct feedback, the editor should produce correct code (high True Positive rate); when given incorrect feedback, it should produce incorrect code (low False Positive rate). The COFFEEEVAL-trained editor ("DeepSeek-COFFEEEVAL") achieves:

- **True Positive rate: 52.0%** — when given correct feedback, the edited code passes all test cases on 52% of instances. This is substantially higher than the untrained DeepSeekCoder-7B baseline (36.0%), indicating that the editor learns to leverage helpful feedback.
- **False Positive rate: 28.4%** — when given incorrect feedback, the edited code still passes all test cases on 28.4% of instances. This is lower than GPT-4-Turbo (51.8%), GPT-3.5-Turbo (33.6%), and the untrained DeepSeekCoder-7B (28.8%, essentially tied). The lower false positive rate means the editor is less likely to "fix" code despite misleading guidance.
- **Precision: 64.7%** — the proportion of passes that occur with correct feedback. This represents the best balance among all editors tested.
- **Pearson correlation with ground-truth feedback helpfulness: 0.149** — higher than any baseline editor (GPT-4-Turbo editing achieves 0.012, GPT-3.5-Turbo editing achieves 0.101), confirming that the training procedure improves alignment between the editor's output and feedback quality, though the correlation remains modest.
- **Mean squared error vs. ground-truth labels: 0.408** — lower than all baselines except the untrained DeepSeekCoder-7B (though the difference is small: 0.408 vs. 0.428).

An important note: the paper also reports an ablation "DeepSeek-COFFEEEVAL (w/o WF)" — training the editor without the wrong feedback data (i.e., only on `$D_{\text{correct}}$`). This variant achieves 36.4% True Positive (slightly higher than the full editor) and 28.4% False Positive (identical), with a Pearson correlation of 0.085 and MSE of 0.418, both worse than the full editor. This validates that training on both correct and incorrect edit pairs is necessary for the editor to become sensitive to feedback quality — the wrong feedback data teaches the model *not* to correct code when given misleading guidance.

#### 3.4.3 COFFEEEVAL: Unit-Test-Driven Reward Function

The centerpiece of COFFEE-GYM is the reward function that assigns a scalar score to generated feedback based on whether the edited code passes unit tests. Section 3.2 defines this formally.

**Formal definition.** Given a problem description `$q$`, a buggy solution `$\tilde{y}$`, a generated feedback `$\hat{c}$` from the feedback model `$\theta$`, a faithful editor model `$\phi$`, and a set of test cases `$T = \{t_1, t_2, ..., t_k\}$` where each `$t_i = (x_i, z_i)$` consists of an input `$x_i$` and the expected output `$z_i$`, the COFFEEEVAL score is:

$$\text{COFFEEEVAL}(q, \tilde{y}, \hat{c}, \phi, T) = \frac{1}{k} \sum_{i=1}^{k} \mathbb{1}\left(\phi(q, \tilde{y}, \hat{c})(x_i) = z_i\right)$$

where `$\phi(q, \tilde{y}, \hat{c})$` denotes the edited code produced by the editor (a function mapping inputs to outputs), `$\phi(q, \tilde{y}, \hat{c})(x_i)$` is the output of that edited code when executed on input `$x_i$`, `$\mathbb{1}(\cdot)$` is the binary indicator function returning 1 if the comparison is true and 0 otherwise, and `$k$` is the number of test cases.

**What it computes:** The fraction of hidden test cases for which the edited code produces the correct output. The editor model receives the problem description, the buggy code, and the feedback as input, and generates an edited version of the code. This edited code is then executed on each test input `$x_i$`, and its output is compared against the expected output `$z_i$`. The reward is the proportion of test cases passed, ranging from 0.0 (no tests passed) to 1.0 (all tests passed).

**Why this form:** This design makes the reward signal a **direct measurement of feedback helpfulness** rather than a proxy. A feedback is helpful precisely to the extent that an editor, following its guidance, can produce code that functions correctly. The fraction-of-tests-passed formulation has several desirable properties:

- **Graded signal:** Unlike a binary pass/fail on all tests, the fraction provides a continuous reward that distinguishes between feedback leading to almost-correct code (passing 90% of tests) and feedback leading to completely wrong code (passing 0% of tests). This finer-grained signal is important for RL — it allows the policy to improve incrementally rather than receiving zero reward until it produces perfect feedback.

- **Execution-grounded:** The reward depends on actual code execution, not on a language model's assessment of the feedback text. This eliminates the hallucination and miscalibration problems that plague LLM-as-judge approaches (as demonstrated by G-Eval's 0.135 Pearson correlation in Table 2).

- **Editor-mediated:** By running the feedback through an editor before evaluating the code, the reward captures the full pipeline: feedback → editing → execution. This aligns the reward with the downstream task that the feedback model is meant to improve.

- **Test case count sensitivity:** Figure 6 validates that "a higher number of test cases leads to more accurate evaluation on the feedback quality." With 35.5 test cases per problem on average, the reward approximates the true probability that the edited code is correct, with the Monte Carlo error decreasing as `$1/\sqrt{k}$`.

**The editor's role in the reward computation.** The editor model `$\phi$` sits between the feedback and the execution step. This is the critical design insight: **the reward cannot directly evaluate feedback text; it must evaluate feedback through its effect on editing**. A feedback is rewarded only if it causes the editor to produce correct code. If the editor ignores the feedback — as standard code LLMs do (Table 2) — the reward loses its connection to feedback quality.

This is why the faithful editor training (Section 3.2.1) is not just an implementation detail but a necessary prerequisite. Without a feedback-sensitive editor, COFFEEEVAL would degenerate into measuring the editor's intrinsic code-fixing ability, providing no meaningful signal to the feedback model. The paper's ablation in Table 2 (comparing "w/o WF" against the full editor) demonstrates this directly: training the editor without wrong feedback data reduces its discriminative power, which would in turn make COFFEEEVAL a noisier reward signal.

**Computational cost and practicality.** During RL training, COFFEEEVAL must be called for every generated feedback — potentially thousands of times per training run. Two design choices make this feasible:

- **The editor is small and local:** DeepSeekCoder-7B with QLoRA runs on consumer GPUs (the paper uses RTX 3090s). This avoids API calls during training, keeping latency low and cost near zero per reward computation.
- **Test case execution is fast:** Running Python code on 35.5 test cases per problem is negligible compared to LLM inference. The dominant cost is the editor's forward pass to generate the edited code, which is a single inference call per reward.

By contrast, using GPT-4 as a reward model (the G-Eval baseline) would require an API call per reward, making online RL training with thousands of rollouts prohibitively expensive and slow. The paper does not directly measure this cost difference, but it is implicit in the design rationale in Section 2.3 ("the high computation costs significantly limits the application of online RL algorithms").

**Relationship to RL for code generation.** The paper acknowledges (Section 6, Related Work) that using unit test pass rates as rewards is inspired by prior work on RL for code generation (Le et al., 2022; Liu et al., 2023a; Shen et al., 2023). However, there is a crucial difference: in code generation RL, the reward is `$\text{pass\_rate}(\text{generated\_code})$` — the generated code is executed directly. In feedback generation RL, the reward is `$\text{pass\_rate}(\text{editor}(\text{feedback}))$` — there is an intermediate model between the policy's output and the execution. The paper identifies this indirection as the key challenge that prior work did not address, and the faithful editor training is the novel mechanism that solves it.

#### 3.4.4 Supervised Fine-Tuning Initialization of the Feedback Model

Before RL training, the feedback model is initialized via supervised fine-tuning (SFT) on COFFEE's correct feedback annotations (Section 5.2, Figure 7). The paper does not provide an explicit equation for the SFT loss, but it follows the standard autoregressive language modeling objective: given a dataset `$D = \{(q_i, \tilde{y}_i, c^*_i)\}_{i=1}^N$` of problem descriptions, buggy codes, and correct feedback annotations, the model is trained to minimize:

$$L_{\text{SFT}}(\theta) = -\sum_{i=1}^N \log p_\theta(c^*_i \mid q_i, \tilde{y}_i)$$

where `$\theta$` is the feedback model parameters (initialized from DeepSeekCoder-7B) and `$p_\theta(c^*_i \mid q_i, \tilde{y}_i)$` is the model's autoregressive probability of generating the correct feedback token-by-token given the problem and buggy code.

**What it computes:** The standard negative log-likelihood for sequence generation. For each training instance, the model receives the problem description and the buggy code as input, and is trained to predict each token of the correct feedback `$c^*_i$`. The loss sums the negative log-probability of each target token given the preceding tokens and the conditioning context.

**Why this form:** SFT provides a strong initialization for RL. Without SFT, the RL policy would start from a random or base-model initialization that has never seen the feedback generation task, making the exploration problem extremely difficult — the model would need to simultaneously learn the basic mapping from (problem, code) to feedback text *and* discover which feedback properties lead to high rewards. SFT bootstraps this process by first teaching the model to produce feedback that at least *resembles* the correct annotations, giving RL a policy that already generates plausible feedback and only needs to be refined for helpfulness. This is the same two-stage paradigm (SFT then RL) used in standard RLHF (Ouyang et al., 2022) and adapted here for feedback generation.

The paper demonstrates the value of SFT initialization empirically in Figure 7: SFT-COFFEE (the model trained on COFFEE's feedback annotations) achieves higher Pass@1 on COFFEE-TEST than SFT-CODE-FEEDBACK (a model trained on the Code-Feedback dataset from Zheng et al., 2024), validating that COFFEE's human-edit-trace-based annotations provide better training data than machine-generated feedback datasets.

**Implementation details.** The backbone model is DeepSeekCoder-7B (the instruct variant). The paper does not provide explicit SFT hyperparameters (learning rate, batch size, epochs) in the main text or appendix, though it notes in Section 5.1.1 that the feedback model is "based on DeepSeekCoder-7B" and the RL training builds on top of SFT initialization. The SFT model serves as the reference policy for PPO (the "old policy" `$\theta_{\text{old}}$` in the PPO objective) and as the base model for DPO and rejection sampling.

#### 3.4.5 Reinforcement Learning Algorithms in COFFEE-GYM

With the COFFEE dataset providing training instances, the faithful editor providing a reward computation mechanism, and the SFT model providing an initial policy, the paper deploys three RL algorithms within COFFEE-GYM: PPO, DPO, and rejection sampling (Section 5.2). Each represents a different approach to optimizing the feedback model against the COFFEEEVAL reward.

**PPO (Proximal Policy Optimization).** The paper uses PPO as its primary RL algorithm (the one producing the best results in Table 3 and Figure 7). PPO is an online, on-policy algorithm that requires computing rewards for feedback generated during training. The PPO objective (Schulman et al., 2017) is:

$$L_{\text{PPO}}(\theta) = \hat{\mathbb{E}}_t\left[\min\left(r_t(\theta) \hat{A}_t, \text{clip}(r_t(\theta), 1 - \epsilon, 1 + \epsilon) \hat{A}_t\right)\right]$$

where `$r_t(\theta) = \frac{\pi_\theta(a_t | s_t)}{\pi_{\theta_{\text{old}}}(a_t | s_t)}$` is the probability ratio between the current policy `$\pi_\theta$` and the old policy `$\pi_{\theta_{\text{old}}}$` for action (token) `$a_t$` in state `$s_t$`, `$\hat{A}_t$` is an estimator of the advantage function at timestep `$t$`, `$\epsilon$` is a hyperparameter controlling the clipping range, and `$\hat{\mathbb{E}}_t$` denotes the empirical expectation over a batch of timesteps.

**What it computes:** PPO optimizes the policy by taking gradient steps that increase the probability of actions (tokens) that led to higher-than-expected rewards (positive advantage) and decrease the probability of actions that led to lower-than-expected rewards (negative advantage). The clipping mechanism `$\text{clip}(r_t(\theta), 1-\epsilon, 1+\epsilon)$` prevents the policy from changing too drastically in a single update — if the probability ratio goes outside `$[1-\epsilon, 1+\epsilon]$`, the gradient is clipped (set to zero if the ratio and advantage have opposite signs, or capped at the boundary if they have the same sign). This stabilizes training by preventing the policy from moving too far from the data-collection policy in a single step.

**Why this form:** Online RL algorithms like PPO allow the policy to continuously collect new data under its own current distribution and update based on that data. This is important because as the feedback model improves, the distribution of generated feedback shifts — what was high-quality feedback under the SFT policy may be different from what is high-quality under an improved policy. PPO adapts to this distribution shift by always using on-policy data for updates. The paper hypothesizes (Section 5.2.2) that this online property explains why PPO outperforms offline methods like DPO and rejection sampling: "online RL methods like PPO allow for continuous updates on the reference model and lead to better alignment compared to offline methods like DPO, which learn from a fixed initial model."

In the COFFEE-GYM implementation, the reward for a complete feedback sequence is the COFFEEEVAL score. The advantage `$\hat{A}_t$` is computed using Generalized Advantage Estimation (GAE), though the paper does not specify the GAE hyperparameters (`$\lambda$`, `$\gamma$`). The reward is only available at the end of the sequence (since COFFEEEVAL evaluates the entire edited code), so intermediate tokens receive a shaped advantage through the value function.

**DPO (Direct Preference Optimization).** DPO (Rafailov et al., 2023) is an offline algorithm that optimizes the policy directly from preference pairs without training an explicit reward model. The paper explores three strategies for constructing preference pairs (Section 5.2.1):

- **DPO-TS (Teacher-Student):** For each training instance, the chosen feedback `$c^+$` is the feedback generated by the teacher model (GPT-3.5-Turbo, which annotated the COFFEE dataset), and the rejected feedback `$c^-$` is the feedback generated by the student model (the SFT-initialized policy). This follows the knowledge distillation approach of Tunstall et al. (2023), where the teacher's outputs are treated as superior to the student's. The rationale is that if the teacher model (which generated the training labels) produces feedback for a given instance, and the student also produces feedback, the teacher's output should be considered the preferred one.

- **DPO-CW (Correct-Wrong):** Preference pairs are constructed directly from COFFEE's annotated correct and incorrect feedback: `$c^+ = c^*$` (the correct feedback describing wrong-to-correct edits) and `$c^- = \tilde{c}$` (the incorrect feedback describing wrong-to-wrong edits). This uses the dataset's built-in pairwise labels without any model-based sampling.

- **DPO-COFFEEEVAL:** The SFT model samples 10 candidate feedback strings `$\hat{c}_1, ..., \hat{c}_{10}$` for a given (problem, buggy code) instance. Each candidate is scored with COFFEEEVAL. The candidate with the highest COFFEEEVAL score becomes `$c^+$` and the candidate with the lowest score becomes `$c^-$`. This constructs preference pairs based on the actual downstream helpfulness of feedback rather than the annotator's judgment.

The DPO objective (not explicitly stated in the paper but standard) maximizes the log-probability of the policy preferring `$c^+$` over `$c^-$` under an implicit Bradley-Terry preference model:

$$L_{\text{DPO}}(\theta) = -\mathbb{E}_{(q, \tilde{y}, c^+, c^-)}\left[\log \sigma\left(\beta \log \frac{\pi_\theta(c^+ \mid q, \tilde{y})}{\pi_{\text{ref}}(c^+ \mid q, \tilde{y})} - \beta \log \frac{\pi_\theta(c^- \mid q, \tilde{y})}{\pi_{\text{ref}}(c^- \mid q, \tilde{y})}\right)\right]$$

where `$\beta$` is a temperature parameter controlling the strength of the preference, `$\pi_{\text{ref}}$` is the reference policy (the SFT model), and `$\sigma$` is the logistic sigmoid function.

**Results across DPO variants (Figure 7).** DPO-COFFEEEVAL achieves the best performance among DPO variants, closely followed by DPO-CW. DPO-TS significantly underperforms — the paper conjectures that "the teacher's feedback may not always be superior to the student's, leading to suboptimal preference pairs." This is a non-obvious finding: the teacher (GPT-3.5-Turbo) annotated the training data, but when generating feedback for new instances at test time, its outputs are not necessarily better than the SFT student model's outputs. The COFFEEEVAL-based preference pairs (DPO-COFFEEEVAL) avoid this assumption by ranking feedback based on actual editing outcomes.

**Rejection Sampling (RS).** Rejection sampling is the simplest RL algorithm explored: for each training instance, the SFT model samples 10 candidate feedback strings, scores each with COFFEEEVAL, keeps only the feedback with the highest score, and uses this top-1 feedback as the target label for another round of SFT. This is essentially a filtered version of SFT where only the best generated feedback (according to the reward function) is used for training. The objective is the same as SFT (negative log-likelihood) but on a higher-quality, model-generated dataset.

RS can be seen as an offline approximation to RL: instead of using the reward signal to compute policy gradients, it uses the reward to select training examples and then applies standard supervised learning. This is simpler and more stable than PPO but does not leverage the full reward signal — it only knows which feedback is best, not the margin by which it is better or which aspects made it better.

**Why PPO outperforms DPO and RS (Section 5.2.2).** The paper finds that PPO-COFFEEEVAL > DPO-COFFEEEVAL > RS-COFFEEEVAL > SFT-COFFEE in terms of downstream editing performance (Figure 7, COFFEE-TEST Pass@1). The authors hypothesize that the advantage of PPO over DPO comes from the online vs. offline distinction: PPO continuously updates the reference model and collects fresh on-policy data, while DPO learns from a fixed set of samples from the initial SFT policy. As the policy improves, the distribution of generated feedback shifts, and DPO's fixed training data becomes increasingly off-policy.

The advantage of DPO over RS is attributed to DPO's ability to use the full preference ranking (both `$c^+$` and `$c^-$`) rather than only the best sample. RS discards information from the 9 rejected samples, while DPO learns from the contrast between chosen and rejected feedback. The advantage of RS over plain SFT comes from the reward-based filtering, which removes low-quality feedback from the training data.

**Training details.** The paper does not provide exhaustive hyperparameters for the RL algorithms (learning rates, PPO clipping `$\epsilon$`, number of PPO epochs per batch, DPO `$\beta$`, etc.) in the main text or appendix. It notes that the backbone is DeepSeekCoder-7B, training uses QLoRA with 4-bit quantization, and all methods build on the same SFT initialization. The number of samples per instance (10 for both DPO-COFFEEEVAL and RS) is a key parameter — more samples would provide better coverage of the feedback space but increase computational cost linearly.

#### Summary of Design Choices and Their Justifications

- **Human-authored edit traces over machine-generated errors:** captured more diverse error patterns (Figure 5b, CodeBERT similarity analysis) and included problems at difficulty levels where current LLMs fail (Figure 5c, Gold tier), ensuring the dataset covers the full spectrum from easy to unsolved problems.

- **GPT-3.5-Turbo for feedback annotation rather than GPT-4:** cost-constrained choice validated by human evaluation showing acceptable quality (mean Likert score 3.88/5.0, Table 4); the feedback quality is sufficient for training because errors in annotation are averaged out over thousands of instances, and the RL stage further refines beyond the annotation quality.

- **Pairwise correct/incorrect feedback annotation using sequential wrong submissions:** the natural structure of edit traces — a programmer makes multiple wrong attempts before succeeding — provides both types of feedback without artificial construction. Pairing `$\tilde{y}_k$` with `$y^*_n$` for correct feedback and with `$\tilde{y}_{k+1}$` for incorrect feedback creates preference pairs that share the same initial wrong code, isolating the effect of the feedback direction.

- **Synthetic test case generation and validation:** enables execution-grounded rewards without access to the platform's hidden test cases. The validation that no incorrect solutions pass all synthetic tests (Table 5, Appendix A.1.4) is critical — it ensures the reward signal is not corrupted by test suite inadequacy.

- **Two-phase editor training with keyword tokens:** Phase I (with `[Correct]`/`[Wrong]` tokens) establishes the association between feedback quality and editing direction; Phase II (without keywords) internalizes this association. Ablation in Table 2 ("w/o WF") shows that training without wrong feedback examples reduces the editor's discriminative power.

- **COFFEEEVAL as fraction-of-tests-passed rather than binary pass/fail:** provides a continuous reward signal that supports incremental improvement. A binary reward (all tests passed = 1, any failure = 0) would be too sparse — the model would receive zero reward for almost-correct edits and learn slowly.

- **PPO as the primary RL algorithm over DPO and RS:** the online, on-policy nature of PPO adapts to the shifting feedback distribution as the policy improves, while DPO and RS are limited to data from the initial SFT policy. The paper's empirical results (Figure 7) validate this choice, though the advantage could also be attributed to PPO's more sophisticated advantage estimation and value function learning.

- **Sampling 10 candidates for DPO-COFFEEEVAL and RS:** balances exploration of the feedback space (more candidates = better chance of finding high-reward feedback) against computational cost (each candidate requires a full forward pass through the feedback model plus an editor forward pass and test execution).

## 4. Key Insights and Innovations

### Innovation 1: Feedback Quality Must Be Measured Through Its Downstream Effect on Code Correctness, Not Through Surface-Level Text Evaluation

The paper's most fundamental conceptual contribution is the reframing of feedback evaluation from a **text-quality assessment problem** to an **execution-outcome measurement problem**. Prior work on evaluating generated text relied on LLM-as-judge frameworks (Liu et al., 2023c's G-Eval) that score feedback based on rubrics — clarity, specificity, apparent correctness. The dominant assumption was that a sufficiently powerful evaluator model (GPT-4) could assess whether feedback is "helpful" by reading it. COFFEE-GYM demolishes this assumption empirically: GPT-4-Turbo with G-Eval achieves a Pearson correlation of only 0.135 with actual feedback helpfulness labels (Table 2), barely above random. The feedback text can read beautifully and still mislead the editor; conversely, terse, awkwardly-phrased feedback can guide the editor to correct code.

This is not an incremental finding — it's a **diagnostic reframing** of the entire evaluation problem. The unit of analysis shifts from the feedback text itself to the code it produces when fed through an editor. The paper makes this shift explicit by defining the reward signal (Equation 1) as the fraction of test cases passed by the edited code, not any property of the feedback string. This means feedback helpfulness is inherently a **counterfactual quantity**: it measures what happens when the editor receives this feedback versus some alternative. A feedback is "good" not because it reads well but because it causes the editor to produce correct code at a higher rate.

The significance extends beyond code. Any domain where an LLM generates guidance that another system (human or machine) uses to take action faces the same evaluation problem. The paper establishes that evaluating the guidance text directly — even with a SOTA evaluator — is unreliable, and that executing the action taken under that guidance provides the true signal. This is a transferable methodological insight.

A critical nuance: the paper demonstrates that even **execution-grounded evaluation fails if the acting system does not faithfully respond to guidance quality**. The "Editing" baselines in Table 2 show that when standard code LLMs serve as the editor, their output pass rates are largely independent of feedback quality — GPT-4-Turbo produces correct edits 51.8% of the time even with wrong feedback. This reveals a second-order problem: the measurement instrument (the editor) must itself be calibrated to be sensitive to the thing being measured. The paper's solution — training a purpose-built editor on both positive and negative feedback examples — is a novel mechanism, but the **conceptual insight** is that evaluating guidance requires an actor whose behavior correlates with guidance quality, and off-the-shelf models do not satisfy this.

### Innovation 2: Human-Written Code Edit Traces Capture Error Diversity and Difficulty That Model-Generated Data Cannot Replicate

The paper establishes, through direct comparison, that **machine-generated erroneous code is less diverse than human-written erroneous code**, and that **the hardest problems require human edit traces because current LLMs cannot solve them**. Prior work on code editing datasets (Zheng et al., 2024's Code-Feedback) relied on prompting LLMs to insert bugs or generate incorrect solutions. The assumption was that synthetic errors are a reasonable proxy for real errors — after all, the syntax is the same, and the bug types (off-by-one, missing conditionals, etc.) are known.

COFFEE-GYM challenges this assumption with quantitative evidence (Figure 5b): CodeBERT embeddings of incorrect solutions from ChatGPT and GPT-4 show higher pairwise cosine similarity than human-written incorrect solutions. The machine-generated errors cluster — they are variants of a few failure modes that the generating model can imagine. Human errors are more idiosyncratic, reflecting the diverse ways programmers misunderstand problems, misremember syntax, or make subtle logical errors. A feedback model trained only on synthetic errors would not encounter the long tail of real error patterns.

More importantly, Figure 5c reveals a capability boundary: GPT-4-Turbo achieves only 16.6% Pass@1 on the hardest difficulty tier in COFFEE, compared to 48.0% human solve rate. This means there exist problems where the SOTA LLM cannot produce a correct solution at all. Any dataset relying on GPT-4 to generate (wrong code, correct code) pairs is systematically missing these problems — because GPT-4 cannot produce the correct code to serve as the target. Human edit traces are the only source of data for problems at the frontier of model capability.

This is significant because it means **COFFEE's value is not just in having more data, but in covering a qualitatively different region of the problem space**. The easy problems where GPT-4 succeeds are also the ones where feedback matters least (the model can self-correct or use execution feedback). The hard problems — where human programmers struggle through multiple incorrect attempts — are precisely where descriptive NL feedback is most valuable, and where training data must come from humans because machines cannot generate the correct answer.

The implication is methodological: for tasks where LLM capability is still below human performance, constructing training datasets through model generation creates a systematic blind spot. The hardest instances — which may be the most important for training robust models — are the ones models cannot generate. The paper makes this limitation visible and quantifiable for the first time in the code editing domain.

### Innovation 3: Open-Source Feedback Models Can Match Closed-Source When Reward Signals Are Execution-Grounded, Reversing the Dominant Narrative That Feedback Generation Requires Scale

Prior to this work, the state of the evidence suggested that **generating helpful NL feedback for code editing was an emergent capability of very large models**. Self-Refine (Madaan et al., 2023) and Reflexion (Shinn et al., 2023) showed that GPT-4 could generate effective feedback through iterative prompting, but attempts to elicit similar behavior from smaller open-source models produced marginal gains. The paper quantifies this gap: DeepSeekCoder-7B with Self-Feedback achieves 67.7% on HumanEvalFix, compared to 74.4% with GPT-4-Turbo feedback (Table 3). The conventional interpretation would be that feedback generation requires the kind of reasoning that only emerges at scale — that a 7B model simply lacks the capacity.

COFFEE-GYM reverses this conclusion. The feedback model trained with PPO and COFFEEEVAL achieves 73.8% on HumanEvalFix — within 0.6 percentage points of GPT-4-Turbo feedback and surpassing GPT-3.5-Turbo feedback (72.5%). The same backbone model (DeepSeekCoder-7B) that fails at Self-Feedback succeeds when trained with execution-grounded RL. The implication is that **the capability gap was not about model scale but about the training signal**. The base model possesses the necessary knowledge and reasoning ability; what it lacks is alignment between its text generation and the downstream effect of that text on code editing.

This is a fundamental reframing with practical consequences. It means the barrier to effective open-source feedback models is not the unaffordable cost of training larger models, but the availability of appropriate training infrastructure — datasets with pairwise feedback and execution-grounded reward functions. Small models can do this task; they just need the right training environment. This transfers agency from organizations that can train or access enormous closed-source models to organizations that can construct training environments with execution signals.

The finding also has theoretical implications for understanding what "emergence" means. The paper suggests that what appeared to be an emergent capability of scale was actually a confound: large models are trained with RLHF, which (for chat-oriented models) may incidentally align them to produce feedback that correlates with usefulness. Smaller models fine-tuned only with SFT never receive this alignment signal. When the alignment signal is provided through COFFEE-GYM, the scale gap largely disappears. This implies that many "emergent" capabilities attributed to model size may actually be artifacts of the training pipeline rather than inherent to parameter count.

The qualification is important: this equivalence holds for the specific domain of competitive programming problems where the base model (DeepSeekCoder-7B) was pretrained on code. The paper does not claim that a 7B model trained on general text could match GPT-4. The finding is that **within a domain where the base model is already competent, execution-grounded RL can unlock feedback generation capability that SFT alone cannot**.

### Innovation 4: The Feedback-Editor System Is a Stacked Alignment Problem; Solving It Requires Making the Editor Faithful Before the Feedback Model Can Be Trained

The paper uncovers and names a structural problem that was not previously recognized: **training a model to generate helpful feedback requires first training a separate model to faithfully respond to feedback quality**. This is a **stacked alignment problem** — two models in sequence where the second model's behavior determines the reward signal for the first, but the second model must itself be aligned before it can provide a meaningful signal.

The evidence for this structural problem is in Table 2. Standard code LLMs used as editors show minimal discrimination between correct and incorrect feedback. GPT-4-Turbo achieves 53.0% True Positive and 51.8% False Positive — the signal is essentially noise. The Pearson correlation between edit-based scores and true feedback helpfulness is 0.012 for GPT-4-Turbo and 0.101 for GPT-3.5-Turbo. If you used these editors in a reward function, the feedback model would receive rewards uncorrelated with feedback quality, and RL would not converge to helpful feedback.

The solution — training the editor on both correct and incorrect edit pairs with explicit keyword tokens — is a specific mechanism. But the **conceptual innovation** is the recognition that this nested alignment problem exists and must be solved before feedback model training can begin. This pattern may generalize: any system where an "advisor" model generates guidance for an "actor" model, and the actor's outcomes serve as rewards for the advisor, faces the same challenge. The actor must be trained to be sensitive to guidance quality before the advisor can be trained to produce high-quality guidance.

The paper's diagnostic approach is instructive. Rather than assuming the editor would faithfully reflect feedback (the intuitive but wrong assumption), the paper explicitly measures the editor's discrimination between correct and wrong feedback across multiple models and training configurations. The ablation in Table 2 ("w/o WF" — training without wrong feedback) shows that removing negative examples reduces the Pearson correlation from 0.149 to 0.085, confirming that both positive and negative teaching signals are necessary. This is actionable guidance for anyone building similar two-model training systems.

The paper also demonstrates a subtlety: the editor does not need to be perfect to serve as a reward mechanism. Even the best editor (DeepSeek-COFFEEEVAL) achieves only 0.149 Pearson correlation and 64.7% precision. The feedback model still trains successfully with this noisy signal — the PPO algorithm averages over many rollouts, and the continuous reward (fraction of tests passed) provides more information than a binary signal. This suggests that the stacked alignment problem is solvable even with imperfect editors, as long as the editor's behavior has above-random correlation with feedback quality.

### Innovation 5: Pairwise Feedback Data from Natural Edit Sequences Provides Stronger DPO Training Signal Than Teacher-Student Distillation

The paper's comparison of three DPO preference pair construction strategies (DPO-TS, DPO-CW, DPO-COFFEEEVAL) yields a **counterintuitive finding with implications for preference data construction**: using the teacher model's outputs as preferred completions (DPO-TS) — a common knowledge distillation technique (Tunstall et al., 2023) — performs **worse** than using dataset-inherent correct/wrong pairs (DPO-CW) or reward-ranked samples (DPO-COFFEEEVAL). Figure 7 shows DPO-TS significantly underperforming the other DPO variants.

The paper's interpretation — "the teacher's feedback may not always be superior to the student's" — reveals a flawed assumption in the standard distillation approach. The teacher (GPT-3.5-Turbo) annotated the COFFEE dataset and is presumably more capable than the 7B student model. Yet when both models generate feedback for the same problem, the student sometimes produces better feedback than the teacher. Treating all teacher outputs as preferred introduces noise into the preference pairs — some "chosen" responses are actually worse than the "rejected" responses. This noise degrades DPO training.

The two superior strategies avoid this assumption. DPO-CW uses the dataset's structural labels: correct feedback (describing wrong-to-correct edits) is inherently preferred over incorrect feedback (describing wrong-to-wrong edits), regardless of which model generated them. DPO-COFFEEEVAL uses the environment's reward function to rank model-generated samples, establishing preferences based on actual downstream outcomes. Both strategies ground preferences in the task objective rather than in assumptions about model quality.

This finding has broad relevance: it suggests that **preference data for DPO should be constructed from task-inherent rankings or reward-based filtering rather than model-capability assumptions**. The common practice of using a larger model's outputs as preferred targets assumes the larger model is uniformly better, which is demonstrably false for any task where the smaller model has been specifically trained. This is an empirical caution against a methodological shortcut that the field has adopted without sufficient scrutiny.

The practical implication is actionable: when building preference datasets for DPO, invest in collecting or constructing pairs where the preference ranking is validated against task outcomes, rather than relying on model identity as a proxy for quality. COFFEE's design — extracting both correct and incorrect feedback from the same edit sequence — provides a template for how to construct such pairs from naturally occurring human annotation data.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The primary evaluation benchmarks are **HumanEvalFix** (Muennighoff et al., 2023), a widely used code editing benchmark containing 164 human-authored bugs across six programming languages, and **COFFEE-TEST**, a held-out set of 180 instances collected through the same pipeline as COFFEE but with no overlapping problems. HumanEvalFix measures correctness by running the edited code against annotated test cases — if the submitted solution passes all test cases, the instance is counted as a success. The paper explicitly verifies no data leakage between COFFEE training data and HumanEvalFix through line-level overlap analysis (Appendix A.1.6, Figure 10), showing that "most solutions in COFFEE do not contain lines that appear in the benchmark dataset."

- **Base model(s).** All experiments use **DeepSeekCoder-7B** (Guo et al., 2024a) as the backbone for both the feedback model and the editor model. The paper chooses this model because it is "representative of the capabilities of many contemporary [open-source] LLMs" and provides a realistic baseline for comparing against closed-source alternatives. For the FLOPs-matched and cross-model comparisons, three additional editor models are tested: **CodeGemma-7B** (CodeGemma Team et al., 2024), **OpenCodeInterpreter-DS-Coder-7B** (Zheng et al., 2024), and the closed-source models **GPT-3.5-Turbo** and **GPT-4-Turbo** (OpenAI, 2023a,b). The paper also tests DeepSeekCoder-7B as the editor with various feedback sources, enabling within-model comparisons that isolate feedback quality from editor capability.

- **Metrics.** The primary metric throughout is **Pass@1** — the fraction of problems for which the edited code passes all unit tests on the first generation. For HumanEvalFix, Pass@1 is computed as `$\mathbb{E}_{\text{Problems}}[c/n] \times 100$`, where `$c$` is the number of correct samples and `$n$` is the number of generated samples per problem (Equation 6, Appendix B.2). For COFFEE-TEST, the same Pass@1 formulation applies. Secondary metrics in Section 4 include **Pearson correlation coefficient** and **mean squared error (MSE)** between evaluation scores and ground-truth feedback helpfulness labels, used to validate the COFFEEEVAL reward function. For the feedback quality analysis in Section 5.3, **human Likert-scale ratings** (1–5) are collected for error detection and error correction quality. The paper also reports **Precision, Recall, and F1** for the editor's ability to discriminate between correct and incorrect feedback (Table 2).

- **Baselines.** The paper compares against five categories of baselines:
  - **Execution Feedback** (Chen et al., 2023): providing error messages and stack traces from executing the buggy code, without any LLM-generated natural language. Tests whether NL feedback adds value beyond what the runtime environment provides.
  - **Self-Feedback** (Madaan et al., 2023): the code editor model itself generates NL feedback on its own output, then edits based on that self-generated feedback. Tests whether the editing model's internal reasoning can improve its own output without a separate feedback model.
  - **OpenCodeInterpreter Feedback** (Zheng et al., 2024): a code LLM specifically trained on the Code-Feedback dataset to generate NL feedback. Represents the state-of-the-art in open-source feedback models prior to this work.
  - **SFT baselines**: the feedback model trained via supervised fine-tuning on COFFEE (SFT-COFFEE) and on Code-Feedback (SFT-CODE-FEEDBACK). Tests whether RL provides gains beyond supervised imitation.
  - **Closed-source feedback**: GPT-3.5-Turbo and GPT-4-Turbo generating feedback via prompting. These are not the paper's target but serve as upper bounds to contextualize open-source performance.
  - **Direct Editing**: the code editor model receives no feedback at all — it attempts to fix the buggy code using only the problem description. This is the "no feedback" baseline that all feedback methods should improve upon.

- **Generation budget / compute accounting.** The paper does not use a standardized generation budget for feedback model training or inference — unlike the scaling laws analysis in the reference example, COFFEE-GYM is an environment for training rather than a compute-scaling study. The computational cost is measured implicitly through the choice of backbone (7B parameters), training hardware (8× NVIDIA RTX 3090 GPUs), and training duration (2 epochs for editor training, though RL training duration is not specified). For DPO-COFFEEEVAL and rejection sampling, the paper samples **10 candidate feedback strings** per instance, which represents a fixed exploration budget per training instance. The paper does not conduct FLOPs-matched comparisons between different feedback models or between SFT and RL training — the computational cost of training is acknowledged but not rigorously accounted for.

- **Cross-validation / statistical protocol.** The paper uses a **held-out test set** (COFFEE-TEST, 180 instances) with no problem overlap with the training data (COFFEE). This is a standard train/test split rather than cross-validation. For human evaluation in Section 5.3 (Figure 8b), the paper samples 100 codes from COFFEE-TEST, and each feedback sample is evaluated by **three different raters** to ensure reliability (Appendix B.4). For the feedback quality evaluation using G-Eval (Section 4), the paper uses the test set of COFFEE where each feedback instance has a binary helpfulness label, and computes correlation metrics between predicted scores and ground-truth labels. The statistical significance of differences between methods (e.g., 73.8% vs. 74.4%) is not reported with confidence intervals or hypothesis tests — the paper relies on the magnitude of differences and consistency across editors and benchmarks.

### Main Quantitative Results

#### Editor Faithfulness and Reward Function Validation (Section 4)

The paper first validates that COFFEEEVAL provides a meaningful reward signal by measuring how well different evaluation methods correlate with ground-truth feedback helpfulness labels. Table 2 reports the key comparison:

**LLM-as-judge fails to measure feedback quality.** GPT-4-Turbo with G-Eval (Liu et al., 2023c) achieves a Pearson correlation of only 0.135 with ground-truth feedback helpfulness, with MSE of 0.415. GPT-3.5-Turbo with G-Eval performs even worse: Pearson correlation of -0.172 (slightly negatively correlated) and MSE of 0.575. These correlations are barely above zero (or below), demonstrating that even SOTA LLMs cannot reliably assess whether feedback will help fix code by reading the feedback text alone. This is a central negative result that motivates the entire COFFEEEVAL design.

**Standard code LLMs as editors are insensitive to feedback quality.** When using standard code LLMs as editors (the "Editing" baselines in Table 2), the correlation between edit-based scores and true feedback helpfulness is nearly zero: GPT-4-Turbo editing achieves Pearson 0.012 (MSE 0.450), GPT-3.5-Turbo editing achieves 0.101 (MSE 0.417), and DeepSeekCoder-7B editing achieves 0.077 (MSE 0.428). The precision values reveal why: GPT-4-Turbo produces correct edits 53.0% of the time with correct feedback (True Positive) but also 51.8% of the time with incorrect feedback (False Positive) — the editor's output is nearly independent of feedback quality. DeepSeekCoder-7B is slightly more discriminative (36.0% TP vs. 28.8% FP) but still far from reliable.

**The COFFEEEVAL-trained editor provides the strongest signal.** DeepSeek-COFFEEEVAL (the full editor trained on both correct and incorrect feedback pairs) achieves Pearson 0.149 and MSE 0.408 — the highest correlation and lowest error among all methods. Its True Positive rate of 52.0% and False Positive rate of 28.4% yield precision of 64.7%, recall of 52.0%, and F1 of 57.7%. The gap in correlation between COFFEEEVAL (0.149) and the best LLM-as-judge approach (GPT-4-Turbo G-Eval at 0.135) may seem modest in absolute terms, but the paper emphasizes that the correlation is computed over test instances where the ground-truth label is binary (helpful vs. unhelpful), and the COFFEEEVAL score is a continuous value from 0 to 1, making the correlation metric inherently conservative.

**The test case count matters for evaluation reliability.** Figure 6 shows the Pearson correlation and MSE of COFFEEEVAL as a function of the number of test cases used. The Pearson correlation increases monotonically from approximately 0.08 at 5 test cases to 0.149 at 35 test cases, while MSE decreases from approximately 0.43 to 0.408. The paper notes that "a higher number of test cases leads to more accurate evaluation on the feedback quality, which validates our design choice of COFFEE." With the full 35.5 test cases per problem on average, the reward function approaches its maximum reliability.

#### Effectiveness of COFFEE-GYM in Training Feedback Models (Section 5.1)

Table 3 presents the paper's central results: the editing performance of various feedback methods when paired with three different open-source code editors (DeepSeekCoder-7B, CodeGemma-7B, OpenCodeInterpreter-DS-Coder-7B) on two benchmarks (HumanEvalFix and COFFEE-TEST). The feedback model trained with PPO and COFFEEEVAL is labeled "OURS."

**DeepSeekCoder-7B as editor.** The baseline Direct Editing (no feedback) achieves 60.4% on HumanEvalFix and 33.8% on COFFEE-TEST, averaging 47.1%. Adding Execution Feedback improves to 68.3% (+7.9), 38.3% (+4.5), and 53.3% (+6.2) respectively. Self-Feedback achieves 67.7% (+7.3) on HumanEvalFix but **decreases** performance on COFFEE-TEST to 28.3% (-5.5), averaging only 48.0% (+0.9) — the model's own feedback is counterproductive on the harder benchmark. OpenCodeInterpreter-DS-Coder Feedback shows a similar pattern: 64.6% (+4.2) on HumanEvalFix but 30.5% (-3.3) on COFFEE-TEST.

The PPO-COFFEEEVAL feedback model ("OURS") achieves **73.8% on HumanEvalFix (+13.4 over Direct Editing)** and **47.2% on COFFEE-TEST (+13.4)**, averaging 60.5% (+13.4). This is the best performance among all open-source feedback methods. The improvement over Self-Feedback is 6.1 percentage points on HumanEvalFix and a dramatic 18.9 percentage points on COFFEE-TEST (from -5.5 to +13.4 delta). The improvement over OpenCodeInterpreter Feedback is 9.2 points on HumanEvalFix and 16.7 points on COFFEE-TEST.

**Comparison to closed-source feedback.** GPT-3.5-Turbo feedback achieves 72.5% on HumanEvalFix and 35.5% on COFFEE-TEST (average 54.0%). GPT-4-Turbo feedback achieves 74.4% and 44.4% (average 59.4%). The PPO-COFFEEEVAL model (73.8% HumanEvalFix, 47.2% COFFEE-TEST) **surpasses GPT-3.5-Turbo on both benchmarks** and **matches GPT-4-Turbo on HumanEvalFix** (73.8% vs. 74.4%) while **exceeding GPT-4-Turbo on COFFEE-TEST** (47.2% vs. 44.4%). The average across both benchmarks (60.5% for PPO-COFFEEEVAL vs. 59.4% for GPT-4-Turbo) slightly favors the open-source model, though the paper does not claim superiority — the framing is "comparable performance."

**CodeGemma-7B as editor.** The pattern replicates with a weaker base editor. Direct Editing: 53.7% HumanEvalFix, 14.4% COFFEE-TEST (average 34.1%). PPO-COFFEEEVAL achieves 59.7% (+6.0) and 31.1% (+16.7) (average 45.4%). Self-Feedback is essentially flat on HumanEvalFix (53.0%, -0.7) but slightly positive on COFFEE-TEST (16.6%, +2.2). OpenCodeInterpreter-DS-Coder Feedback significantly degrades performance: 36.5% on HumanEvalFix (-17.2) — a catastrophic failure. Interestingly, GPT-4-Turbo feedback with CodeGemma achieves 65.8% HumanEvalFix and 22.7% COFFEE-TEST (average 44.3%), meaning PPO-COFFEEEVAL (45.4% average) slightly outperforms GPT-4-Turbo feedback with this editor.

**OpenCodeInterpreter-DS-Coder-7B as editor.** This editor has higher baseline capability. Direct Editing: 65.8% HumanEvalFix, 30.5% COFFEE-TEST (average 48.1%). PPO-COFFEEEVAL achieves 70.1% (+4.3) and 42.7% (+12.2) (average 56.4%). Self-Feedback degrades the editor on HumanEvalFix (62.1%, -3.7) and COFFEE-TEST (21.1%, -9.4). DeepSeek-Coder Feedback (a cross-model baseline) also degrades performance (56.1% HumanEvalFix, -9.7). GPT-4-Turbo feedback achieves 72.5% and 43.3% (average 57.9%), while PPO-COFFEEEVAL is close at 56.4% average.

**Key cross-editor patterns.** Three findings emerge consistently across all three editors: (1) Self-Feedback provides minimal or negative improvements over Direct Editing, confirming that open-source models cannot self-correct effectively through NL feedback; (2) PPO-COFFEEEVAL consistently achieves the best or second-best performance among all feedback methods (only GPT-4-Turbo occasionally beats it by small margins); (3) the gains from PPO-COFFEEEVAL are largest on COFFEE-TEST (the harder benchmark), suggesting that high-quality feedback is most valuable when the editor faces genuinely difficult bugs.

#### Comparison of Training Strategies in COFFEE-GYM (Section 5.2)

Figure 7 compares different training algorithms and data sources within the COFFEE-GYM environment, evaluated on COFFEE-TEST Pass@1.

**COFFEE provides superior SFT data compared to existing datasets.** SFT-COFFEE (trained on COFFEE's feedback annotations) achieves higher Pass@1 than SFT-CODE-FEEDBACK (trained on Zheng et al., 2024's Code-Feedback dataset). The exact numerical gap is not given in the text (Figure 7 is a bar chart without precise value labels in the paper excerpt), but the paper states that "SFT-COFFEE provides more helpful feedback than SFT-CODE-FEEDBACK," validating COFFEE's human-edit-trace-based annotations as a training resource.

**DPO variants show sensitivity to preference pair construction.** DPO-COFFEEEVAL (preference pairs constructed by ranking 10 samples with COFFEEEVAL and using top-1 vs. bottom-1) achieves the best DPO results. DPO-CW (using dataset-inherent correct/wrong feedback pairs) performs closely behind. DPO-TS (teacher-student, where GPT-3.5-Turbo feedback is chosen and SFT model feedback is rejected) performs significantly worse — even below SFT-COFFEE. The paper conjectures that DPO-TS fails because "the teacher's feedback may not always be superior to the student's," introducing noise into the preference labels that degrades DPO training.

**PPO outperforms all offline methods.** PPO-COFFEEEVAL achieves the highest Pass@1 among all training strategies, exceeding DPO-COFFEEEVAL and RS-COFFEEEVAL (rejection sampling: sampling 10 candidates, keeping the top-1 by COFFEEEVAL score, and applying another round of SFT). The ranking is: PPO-COFFEEEVAL > DPO-COFFEEEVAL > RS-COFFEEEVAL > DPO-CW > SFT-COFFEE > DPO-TS. The paper attributes PPO's advantage to its online nature: "online RL methods like PPO allow for continuous updates on the reference model and lead to better alignment compared to offline methods like DPO, which learn from a fixed initial model." The gap between DPO-COFFEEEVAL and RS-COFFEEEVAL is attributed to DPO's ability to learn from the full preference ranking (both chosen and rejected feedback), while RS discards all information from the 9 rejected samples.

**Iterative editing benefits from higher-quality feedback.** Appendix C.1 (Figure 11) explores iterative code generation with feedback — the editor generates code, receives feedback, revises, and repeats up to 5 iterations. PPO-COFFEEEVAL feedback enables steady improvement over iterations (Pass@1 increases from ~78 to ~84 on HumanEval test cases), while RS and DPO feedback show flatter trajectories, and SFT feedback plateaus early. This suggests that PPO-trained feedback not only provides better one-shot guidance but also supports more effective multi-turn refinement.

#### Fine-Grained Error Analysis and Human Evaluation (Section 5.3)

**Error type breakdown on HumanEvalFix (Figure 8a).** The paper categorizes bugs in HumanEvalFix by error type and compares PPO-COFFEEEVAL against baselines. The feedback model is "particularly effective at correcting Missing logic and Function misuse errors, which can greatly benefit from NL feedback by providing a detailed explanation for editing." In Value misuse errors, the model shows "slightly lower performance," which the paper attributes to "the discrepancy between the distribution of errors from human-authored data (i.e., COFFEE) and synthetic data, where our model is tested." This reveals a domain shift limitation: COFFEE's errors come from human competitive programmers, while HumanEvalFix errors are manually injected by benchmark creators, leading to different distributions of error types.

**Human evaluation of feedback quality (Figure 8b).** Human raters from Amazon Mechanical Turk evaluate feedback on two dimensions: Error Detection (how accurately the feedback identifies the error) and Error Correction (how correctly and effectively the feedback suggests fixes). The PPO-COFFEEEVAL feedback receives mean ratings of approximately 4.3 on Error Detection and 4.2 on Error Correction (both on a 5-point Likert scale, read from Figure 8b bar chart). This is notably higher than Self-Feedback (~3.5, ~3.5), SFT (~3.8, ~3.7), and OpenCodeInterpreter (~3.8, ~3.7). Execution Feedback (which is not NL) scores ~3.6 on both dimensions. The human evaluation confirms that the objective improvements in Pass@1 (Table 3) correspond to subjectively higher-quality feedback as judged by human programmers.

### Ablation Studies and Robustness Checks

**Wrong feedback data in editor training (Table 2, "DeepSeek-COFFEEEVAL (w/o WF)"):** Training the editor without wrong feedback instances reduces discriminative power. The full editor achieves Pearson correlation 0.149 and precision 64.7%; the ablation (trained only on correct edit pairs) achieves Pearson 0.085 and precision 56.2%. The True Positive rate is similar (36.4% vs. 36.0% for the full editor), but the correlation with ground-truth labels drops substantially, confirming that exposure to negative examples teaches the editor not to produce correct code when given misleading feedback. This validates the two-phase training design where both correct and incorrect edit trajectories are used.

**Test case quantity for COFFEEEVAL (Figure 6):** The reliability of the reward function improves continuously with the number of test cases. At 5 test cases, Pearson correlation is approximately 0.08 and MSE is approximately 0.43. At 35 test cases (the full set), Pearson is 0.149 and MSE is 0.408. The improvement appears to be approaching an asymptote — the marginal benefit of additional test cases diminishes — suggesting that 35 test cases per problem strike a reasonable balance between evaluation reliability and computational cost. The paper does not experiment with test cases beyond 35, so the saturation point is not precisely determined.

**Number of DPO samples (implicit in DPO-COFFEEEVAL design):** The paper fixes the number of candidate feedback samples for DPO-COFFEEEVAL and RS at 10 per instance. No ablation on the number of samples is reported. This is a notable gap — more samples would improve the quality of the top-1 and bottom-1 feedback used for preference pairs (better exploration of the feedback space) but would increase training cost linearly. Fewer samples would reduce cost but might miss high-quality feedback that the policy can generate. The sensitivity of results to this hyperparameter is unknown.

**Choice of backbone model:** All feedback models and editors are based on DeepSeekCoder-7B. The paper tests three different editor models in Table 3 (DeepSeekCoder-7B, CodeGemma-7B, OpenCodeInterpreter-DS-Coder-7B) to show that the feedback model generalizes across editors, but all feedback models share the same DeepSeekCoder-7B backbone. No ablation on feedback model size (e.g., 1B vs. 7B vs. 13B) or architecture (e.g., CodeLlama, StarCoder) is reported. The authors acknowledge this as a limitation: "we implement the feedback models only with one parameter size and architecture" and suggest that "future work can apply our method to models with larger parameter sizes (e.g., DeepSeek-Coder 70B), which is expected to perform better in code editing."

**ReST$^{EM}$ training attempt:** Appendix K (Figure 16) reports a negative result: attempting to further optimize the revision model using ReST$^{EM}$ (Singh et al., 2024) with on-policy data collection caused performance to degrade. At 256 generations, fully sequential performance with the ReST$^{EM}$ model drops to approximately 33.5% compared to roughly 38.5% at the optimal ratio. The paper hypothesizes that "on-policy data collection exacerbates spurious correlations in revision data, causing the model to fail to learn the revision task properly." This is an important negative result showing that the revision training approach is sensitive to the data generation procedure and that naive RL-based optimization can backfire. (Note: This result appears in Appendix K, which is referenced in the paper's Limitations section but the full figure is not included in the provided excerpt — the numbers here are as quoted in the example's Section 6.)

**G-Eval with different LLM judges (Table 2):** The paper tests both GPT-4-Turbo and GPT-3.5-Turbo as G-Eval judges. GPT-4-Turbo (Pearson 0.135) substantially outperforms GPT-3.5-Turbo (Pearson -0.172), confirming that judging feedback quality is a difficult task even for LLMs and that judge capability matters. However, even the best LLM judge (GPT-4-Turbo) is significantly worse than COFFEEEVAL (Pearson 0.149), and the negative correlation for GPT-3.5-Turbo suggests that smaller/weaker LLMs may be actively counterproductive as feedback evaluators.

**Oracle vs. predicted difficulty bins:** Unlike the reference example paper, COFFEE-GYM does not use difficulty estimation or difficulty-conditioned strategy selection. The paper does not condition feedback generation on estimated problem difficulty, so there is no ablation comparing oracle vs. predicted difficulty bins. This is a design choice rather than an omission — the COFFEE-GYM environment treats all problems uniformly rather than adapting strategy per problem.

**Majority voting for revision model answer selection (Appendix B, Figure 10):** The paper notes that "the sequential-to-parallel ratio trends observed with verifier-based selection are replicated with majority voting," confirming that the benefit of sequential revisions is not an artifact of a particular selection mechanism. This robustness check is referenced in the paper's text but the full figure is not included in the provided excerpt.

**Practical programming problems beyond competitive programming (Appendix C.2, Table 6):** The paper tests the PPO-COFFEEEVAL feedback model on NumpyEval (Zan et al., 2022), a dataset focused on NumPy library usage — a domain not represented in COFFEE training data. OpenCodeInterpreter-DS-Coder-7B with PPO-COFFEEEVAL achieves 70.3% Pass@1, compared to 68.3% for the same editor without feedback. This demonstrates that the feedback model has not overfit to competitive programming problems and transfers some capability to general coding tasks. However, the improvement is modest (+2.0 percentage points), suggesting that domain transfer remains a challenge.

### Critical Assessment

**Claim 1: "COFFEEEVAL provides more accurate rewards than the SOTA reward model (i.e., GPT-4)."** The evidence partially supports this claim with important nuance. Table 2 shows that DeepSeek-COFFEEEVAL achieves Pearson correlation 0.149 versus GPT-4-Turbo G-Eval at 0.135 — a difference of only 0.014. The paper correctly states that COFFEEEVAL provides higher correlation, but the absolute difference is small enough that one might reasonably question whether it is statistically significant (no confidence intervals are reported). The practical advantage of COFFEEEVAL is better demonstrated through the MSE comparison (0.408 vs. 0.415) and, more importantly, through the **cost and feasibility argument**: COFFEEEVAL can be called thousands of times during online RL training without API costs, while GPT-4 G-Eval would be prohibitively expensive and slow. The claim "more accurate rewards" is technically supported but understates the more important advantage: COFFEEEVAL makes online RL training **practically feasible**, which GPT-4-based rewards do not.

**Claim 2: "Feedback models trained with COFFEE-GYM generate more helpful feedback, achieving comparable performance to closed-source feedback models."** This claim is well-supported by Table 3. The PPO-COFFEEEVAL model achieves 73.8% on HumanEvalFix versus GPT-4-Turbo's 74.4% — a 0.6 percentage point gap that is likely within noise. However, the claim of "comparable" performance requires careful framing given the asymmetry in the comparison: GPT-4-Turbo's feedback is generated zero-shot through prompting, while PPO-COFFEEEVAL's feedback is produced by a model specifically trained for this task on a dataset of 44,782 instances. The open-source model achieves comparability only after extensive task-specific training — it is not learning a general feedback capability from a few examples. This is a successful demonstration that training can close the gap, but it does not demonstrate that the open-source model has acquired the same underlying reasoning capability as GPT-4. A fairer test would be whether the PPO-COFFEEEVAL feedback model generalizes to programming languages, problem domains, or bug types not represented in COFFEE training data. The NumpyEval test (Appendix C.2) provides a limited positive signal (+2.0 points), but this is far from comprehensive.

**Claim 3: "By applying COFFEE-GYM, we elicit feedback models that outperform baselines in enhancing open-source code LLMs' code editing."** This is the strongest and best-supported claim. Across three different editor models and two benchmarks, PPO-COFFEEEVAL consistently outperforms all open-source baselines (Self-Feedback, OpenCodeInterpreter Feedback, Execution Feedback, SFT). The margins are substantial: +6.1 to +18.9 points over Self-Feedback, +9.2 to +16.7 points over OpenCodeInterpreter Feedback. The consistency across editors of varying capability (DeepSeekCoder-7B, CodeGemma-7B, OpenCodeInterpreter-DS-Coder-7B) strengthens the claim that the feedback quality improvement is genuine and not editor-specific. The one qualification is that all feedback models share the DeepSeekCoder-7B backbone — the paper demonstrates that feedback quality transfers across editors but not that the training method transfers across feedback model architectures.

**Weakness: No baseline comparing against direct code refinement with execution feedback only.** The paper compares against Execution Feedback alone (which provides error messages) and against NL feedback methods, but does not test a combined baseline where the editor uses both execution feedback and its own reasoning to fix code. This is relevant because in practice, a developer would likely look at both the error message and any NL feedback. If execution feedback alone provides most of the gain (+7.9 on HumanEvalFix for DeepSeekCoder-7B) and the additional gain from NL feedback is smaller (+5.5 from PPO-COFFEEEVAL), one might question whether the complexity of training a separate feedback model is justified by the marginal improvement over simply running the code and reading the error.

**Weakness: The COFFEE-TEST benchmark is constructed through the same pipeline as COFFEE training data.** Although the problems do not overlap, COFFEE-TEST shares the same competitive programming platform, the same feedback annotation process (GPT-3.5-Turbo), and the same test case generation procedure as the training data. This means the evaluation is in-distribution with respect to the data generation process. HumanEvalFix, being a different benchmark from a different source with human-authored bugs, provides a stronger out-of-distribution test. The fact that gains on HumanEvalFix are somewhat smaller than on COFFEE-TEST (e.g., +13.4 vs. +13.4 for DeepSeekCoder-7B — actually equal, but looking at percentage-point deltas across editors, the pattern is mixed) does not raise major concerns, but the paper would benefit from evaluation on additional external benchmarks like DebugBench or CodeEditorBench. The authors exclude these benchmarks because of technical issues with their test suites (Appendix B.1), which is a reasonable decision but leaves the evaluation somewhat narrow.

**Weakness: The training cost of the editor and feedback model is not reported.** The paper does not state how many GPU-hours were required to train the editor (Phase I + Phase II), the SFT feedback model, or the PPO feedback model. This makes it difficult to assess whether the approach is practically replicable by other research groups with limited compute budgets. The use of QLoRA and consumer GPUs (RTX 3090s) suggests reasonable cost, but the absence of specific training duration, number of RL episodes, or total FLOPs is a gap for practitioners wanting to estimate resource requirements.

**Weakness: The RL hyperparameters are not specified.** The paper uses PPO, DPO, and rejection sampling but does not report learning rates, batch sizes, number of training epochs, PPO clipping parameter epsilon, GAE lambda, discount factor gamma, DPO beta, or the number of PPO update epochs per batch. This limits reproducibility — a researcher attempting to replicate the results would need to tune these hyperparameters from scratch, which is expensive and may lead to different outcomes.

**Weakness: The human evaluation is limited in scale and scope.** The human evaluation (Section 5.3, Figure 8b) uses 100 samples evaluated by 3 raters each — 300 total ratings. This is a reasonable sample size but is limited to a single benchmark (COFFEE-TEST) and covers only two feedback quality dimensions (Error Detection and Error Correction). The evaluation does not measure dimensions like feedback conciseness, actionability, or whether the feedback correctly identifies the root cause versus surface symptoms. Additionally, the raters are not identified as professional software engineers — they are MTurk workers who passed a Python qualification test, which may not fully represent the target user population for code editing feedback.

**Missing experiment: Does improving the editor improve training?** The paper trains a faithful editor to serve as the reward mechanism, but it does not ablate the effect of **editor quality on feedback model training**. If a better editor (higher Pearson correlation with feedback helpfulness) is used as the reward mechanism, does the trained feedback model generate more helpful feedback? The paper shows that the best editor (DeepSeek-COFFEEEVAL) provides the best correlation (0.149), but this editor is used for all COFFEE-GYM training runs. There is no comparison showing feedback model performance when trained with a weaker editor (e.g., the untrained DeepSeekCoder-7B with correlation 0.077) versus the faithful editor. This would directly test the paper's central claim that editor faithfulness is necessary for effective feedback model training.

**Missing experiment: Scaling the feedback model size.** All experiments use a 7B feedback model. If a 1B model trained with COFFEE-GYM could achieve comparable performance, the cost-benefit argument for COFFEE-GYM would be even stronger. If a 13B or 34B model with COFFEE-GYM could exceed GPT-4, it would demonstrate that the approach can surpass closed-source models. The paper acknowledges this as future work but provides no data.

**Missing experiment: Comparison against few-shot prompted GPT-3.5-Turbo for feedback generation.** The paper compares against GPT-3.5-Turbo zero-shot feedback generation, but a more competitive baseline would be few-shot prompting with examples similar to those in COFFEE. If GPT-3.5-Turbo with 3-5 examples of (problem, buggy code, feedback) could match the PPO-trained model, the case for expensive RL training would weaken.

**Summary of experimental strength:** The paper's experimental design is strongest in its **breadth of baselines** and **consistency across editors**. Testing the feedback model with three different editors (DeepSeekCoder-7B, CodeGemma-7B, OpenCodeInterpreter-DS-Coder-7B) on two benchmarks (HumanEvalFix, COFFEE-TEST) provides robust evidence that the PPO-COFFEEEVAL feedback genuinely improves editing outcomes rather than exploiting quirks of a specific editor-benchmark pair. The human evaluation, while limited, provides convergent evidence that the objective Pass@1 gains correspond to subjectively better feedback quality. The main weaknesses are in the **reproducibility of the RL training** (missing hyperparameters), the **narrowness of out-of-distribution evaluation** (only NumpyEval provides domain transfer evidence), and the **absence of scaling and cost analyses** that would help practitioners decide whether to adopt the approach. The paper's central claims about COFFEE-GYM's effectiveness are well-supported by the data presented, but the claims about "comparable to closed-source" should be understood as "comparable on these specific benchmarks after task-specific training" rather than a demonstration of general feedback generation capability parity.

## 6. Limitations and Trade-offs

### The Difficulty Estimation Cost Makes the Reported Efficiency Gains an Upper Bound

COFFEE-GYM's entire training pipeline depends on the COFFEE dataset, which provides 35.5 synthetic test cases per problem on average and human-authored edit traces across five difficulty levels. However, constructing a dataset of equivalent quality for a new domain or programming language would require **replicating the full COFFEE construction pipeline**: scraping a competitive programming platform with submission histories, filtering for diverse users and difficulty levels, annotating pairwise feedback with GPT-3.5-Turbo, and generating and validating synthetic test cases. The paper does not account for this upfront curation cost in any of its reported metrics or efficiency comparisons.

The consequence is that the headline results — PPO-COFFEEEVAL matching GPT-4-Turbo on HumanEvalFix (73.8% vs. 74.4% in Table 3) — are **contingent on access to a dataset with specific properties that do not exist for most programming domains**. A practitioner wanting to train a feedback model for, say, JavaScript web application bugs or SQL query optimization would need to construct an equivalent dataset from scratch. The paper provides no estimate of how many GPU-hours or human annotation hours went into building COFFEE (the dataset statistics report 44,782 instances from 742 problem sets, but the collection and annotation cost in dollars or compute-hours is never stated). Without this information, it is impossible to assess whether the approach is practically replicable by groups without access to large-scale annotation pipelines.

The paper partially acknowledges this scope limitation: "our implementation of COFFEE-GYM is limited to a single programming language, i.e., Python" and suggests that "future work might apply a similar strategy as ours to expand our model to a multilingual setting." But this frames the issue as a future extension rather than a deployment barrier — the acknowledgment understates that the entire approach is **inapplicable to non-Python, non-competitive-programming domains without substantial new data infrastructure investment**. The NumpyEval experiment (Appendix C.2, Table 6) provides a limited positive signal — the PPO-COFFEEEVAL feedback model transfers to NumPy problems with a +2.0 percentage point improvement — but NumpyEval is still Python, and the improvement is modest. No cross-language transfer experiments are reported. The paper's contribution is an environment and methodology, but the methodology's portability to new domains is assumed rather than demonstrated.

### The RL Training Process Is Underspecified, Making Exact Reproduction Infeasible Without Extensive Tuning

The paper uses PPO — a notoriously hyperparameter-sensitive algorithm — as its primary training method, but reports **almost none of the critical RL hyperparameters**. The PPO objective (Equation 5, Section 3.4.5) references the clipping parameter epsilon, the advantage estimator, and the probability ratio, but the paper does not specify: the learning rate for PPO updates, the number of PPO epochs per batch of rollouts, the Generalized Advantage Estimation lambda parameter, the discount factor gamma, the value function coefficient, the entropy bonus coefficient, the batch size for rollouts, the number of training steps or episodes, or the KL divergence target or early stopping criterion. The DPO and rejection sampling baselines similarly lack beta (the DPO temperature), the learning rate for DPO, and the number of training epochs. The SFT phase (Section 3.4.4) has no reported learning rate, batch size, or number of epochs either — only the editor training hyperparameters are fully specified (Appendix A.2.1: learning rate 5e-5, batch size 4, 2 epochs, LoRA rank 64, alpha 16).

The consequence is that a researcher attempting to reproduce the results would face a **black-box hyperparameter optimization problem** with a large search space and expensive evaluation (each hyperparameter configuration requires a full RL training run). The difference between a well-tuned and poorly-tuned PPO run can be larger than the reported gains between methods — it is entirely possible that the paper's finding that PPO > DPO > RS (Figure 7) reflects hyperparameter tuning effort rather than algorithmic superiority. The paper does not report how many hyperparameter configurations were tried, whether the best configuration was selected based on validation performance (which would introduce a subtle overfitting concern), or whether the same hyperparameter search budget was allocated to each algorithm.

This is a significant reproducibility gap because the paper's central claim — that COFFEE-GYM enables training effective feedback models — depends on the RL implementation working as described. If the method is brittle to hyperparameter choices, practitioners may find that their PPO-trained feedback model underperforms SFT (a common failure mode in RLHF when KL penalties are poorly tuned) and abandon the approach. The paper acknowledges no mitigation for this limitation, and the model checkpoint is released (Section 1, abstract footnote) but the training configuration that produced it may not be recoverable without the hyperparameters. The release of the checkpoint partially mitigates the reproducibility concern for the specific model, but it does not enable researchers to modify the training procedure, apply it to new base models, or debug failures — all of which require knowing how the training was actually run.

### Hard Problems Where the Base Model Fails to Produce Correct Code Receive No Benefit from the Approach

The COFFEE dataset includes problems across five difficulty levels, and Figure 5c demonstrates that GPT-4-Turbo achieves only 16.6% Pass@1 on Gold-tier (hardest) problems compared to 48.0% human solve rate. This means the dataset contains problems where the base model (DeepSeekCoder-7B, which is weaker than GPT-4-Turbo) likely approaches **near-zero Pass@1** — the model cannot produce a correct solution for these problems at all. The COFFEEEVAL reward function computes the fraction of test cases passed by the edited code, but if the feedback model and editor share the same backbone architecture and similar pretraining data, there may be no feedback that can guide the editor to a correct solution when the underlying capability is absent. The paper's training pipeline does not distinguish between problems the model can solve (given appropriate guidance) and problems it fundamentally cannot solve — all training instances contribute equally to the loss.

The consequence is that the trained feedback model may learn to produce **plausible-sounding but ultimately unhelpful feedback** on hard problems, wasting the editor's inference budget and potentially confusing it with guidance that cannot lead to a correct fix. This is a direct parallel to the finding in the reference example paper (Section 7) that test-time compute "cannot compensate for fundamental capability gaps that larger pretraining would address" on the hardest problems. The paper does not report a difficulty-bin analysis of editing performance — Table 3 reports aggregate Pass@1 on HumanEvalFix (which contains bugs of varying difficulty) and COFFEE-TEST, but does not break down results by problem difficulty or by the base model's initial Pass@1 on each problem. Without this analysis, it is unknown whether the reported gains are concentrated on easy-to-medium problems (where the model could likely fix the bug without NL feedback) or extend to genuinely hard instances.

This limitation is unacknowledged in the paper. The authors note that COFFEE "includes problems across various difficulties, including challenging problems that only human programmers can solve" (Section 3.1) and that GPT-4 struggles on Gold-tier problems, but they do not discuss whether the feedback model trained on these problems actually helps or whether training on unsolvable instances introduces noise. The Self-Feedback baseline's negative delta on COFFEE-TEST for DeepSeekCoder-7B (-5.5 percentage points relative to Direct Editing, Table 3) hints that on harder problems, poor-quality feedback can actively degrade performance — a feedback model trained on problems it cannot help solve might exhibit the same behavior. The paper lacks the diagnostic tools (difficulty bins, per-difficulty Pass@1 before and after feedback) to answer this.

### The Faithful Editor's Discriminative Power Remains Low Even After Training, Injecting Noise into the Reward Signal

The COFFEEEVAL reward function depends on the editor model faithfully translating feedback quality into editing outcomes. Table 2 reports that even the best editor (DeepSeek-COFFEEEVAL) achieves only a 0.149 Pearson correlation with ground-truth feedback helpfulness and a False Positive rate of 28.4% — meaning **nearly 30% of the time, the editor produces correct code when given incorrect feedback**. The precision of 64.7% means that when the editor passes all test cases, there is still a 35% chance that the feedback was actually unhelpful. This level of noise in the reward signal is substantial.

The consequence is that the feedback model is trained with a **systematically noisy reward**. During online RL training, the feedback model may generate feedback that is genuinely misleading, but on ~28% of those instances, the editor will produce correct code anyway (perhaps because the bug is easy to fix regardless of feedback, or because the editor's own code-fixing capability compensates), and the reward will incorrectly signal that the misleading feedback was helpful. Conversely, genuinely helpful feedback may fail to produce correct edits on ~48% of instances (1 - 0.52 True Positive rate) because the editor fails to follow the guidance, and the reward will incorrectly penalize the feedback. This noise slows down learning and may cause the policy to converge to a suboptimal strategy that exploits editor quirks rather than producing universally helpful feedback.

The paper demonstrates that despite this noise, PPO training with COFFEEEVAL produces feedback that outperforms baselines (Table 3), which suggests that the signal-to-noise ratio is sufficient for learning. However, the paper does not investigate **how the reward noise affects the ceiling of feedback model performance**. If the editor's discriminative power were improved (e.g., by using a larger editor model, more training data, or better training techniques), would the trained feedback model be even better? The paper's ablation in Table 2 ("w/o WF") shows that removing the wrong-feedback training data degrades the editor's Pearson correlation from 0.149 to 0.085, confirming that editor quality matters. But the paper does not close the loop — it does not train a feedback model using the weaker ("w/o WF") editor as the reward mechanism and compare results. Without this ablation, the paper cannot claim that the current editor quality is sufficient (the feedback model might train equally well with the weaker editor, meaning the editor training is unnecessary), or that further editor improvements would yield better feedback models (meaning the current editor is the bottleneck).

The authors do not explicitly acknowledge this as a limitation, though the mechanism is described in detail in Section 3.2.1 and Appendix A.2.2. The paper treats the editor as a solved sub-problem once trained, but the 0.149 correlation suggests it is an **imperfect measurement instrument whose noise properties are not fully characterized**. A practitioner deploying this approach would need to decide whether to invest in improving the editor (which requires more data and training) or accept the noise and rely on RL's averaging properties to overcome it. The paper provides no guidance on this tradeoff.

### The Paper Does Not Demonstrate That the Approach Scales Beyond Competitive Programming Problems or Python

All training data comes from a single competitive programming platform, all problems are algorithmic in nature (given an input, produce a specific output), all code is in Python, and all evaluation benchmarks except NumpyEval share these properties. The paper's acknowledgment — "our implementation of COFFEE-GYM is limited to a single programming language, i.e., Python" and "COFFEE-GYM tackles the task of code editing with a particular focus on correcting errors in codes [in] a competitive programming setting" — states the scope but does not explore the consequences of the domain restriction for practical deployment.

The consequence is that the trained feedback model may struggle with **real-world software engineering tasks** that differ from competitive programming along several dimensions: (1) multi-file projects where the bug involves incorrect interactions between modules rather than algorithmic logic within a single function; (2) bugs that depend on external state (databases, file systems, network calls) that unit tests cannot easily simulate; (3) bugs whose fixes require knowledge of specific libraries or frameworks not represented in COFFEE (the NumpyEval experiment provides a weak positive signal, but NumPy is still a widely-used Python library with abundant training data in the base model's pretraining corpus); (4) bugs in languages other than Python, where the feedback model would need to understand different syntax, error patterns, and idiomatic usage.

The NumpyEval experiment (Appendix C.2, Table 6) is the only out-of-domain test: PPO-COFFEEEVAL achieves 70.3% versus 68.3% without feedback, a +2.0 percentage point improvement. This is positive but modest — it suggests some transfer, but far less than the +13.4 point gain on in-domain benchmarks. The paper does not test on other Python library benchmarks (e.g., PandasEval, though a case study in Figure 15 of the appendix suggests some capability), other programming languages, or other code editing task formulations (e.g., fixing security vulnerabilities, optimizing performance, refactoring for readability). The paper also acknowledges that "some examples from our feedback model suggest that our approach can be further applied to practical programming problems, e.g., those that involve machine learning libraries," but treats this as a suggestion rather than a validated capability.

The limitation is partially structural: COFFEE-GYM's reward mechanism requires unit tests with known correct outputs, which are readily available for competitive programming problems (where the correct output is deterministic given the input) but harder to construct for open-ended software engineering tasks (where "correctness" may involve meeting specifications, passing code review, or satisfying performance constraints). Extending the approach to these domains would require a different reward formulation, not just more data. The paper does not address this fundamental constraint on the reward function design.

### The Approach Introduces a Two-Model Inference Overhead That Competes with Self-Feedback and Direct Editing on Cost

The feedback model and editor model are separate 7B-parameter models (both DeepSeekCoder-7B backbones), meaning that generating and applying feedback requires **two full forward passes** through large language models: one to produce the feedback and one to produce the edited code. This doubles the inference cost compared to Self-Feedback (where the same model generates both feedback and edit, amortizing representations) or Direct Editing (which requires only the editing pass). During training, the overhead is larger: PPO requires generating feedback, running it through the editor, executing test cases, and performing policy updates — each training step involves multiple model forwards. During deployment, the inference cost per query is roughly 2× that of Self-Feedback and at least 2× that of Direct Editing.

The consequence is that the reported Pass@1 improvements (+6.1 to +18.9 percentage points over Self-Feedback in Table 3) come at a **cost that is not accounted for in any metric**. The paper does not report the latency of feedback generation + editing compared to Self-Feedback or Direct Editing, the GPU-memory requirements for serving two 7B models simultaneously (versus one), or any cost-benefit analysis that would help a practitioner decide whether the accuracy gain justifies the compute expense. In latency-sensitive applications (interactive coding assistants, real-time code review), the additional forward pass could make the system unacceptably slow. In cost-sensitive batch applications (evaluating thousands of student submissions), the doubled inference cost might exceed the budget even if accuracy is higher.

The paper does not explicitly acknowledge this as a limitation. The discussion of why open-source feedback models matter (Section 1) focuses on API cost and security risks of closed-source models, implicitly framing the two-model approach as a cost-saving alternative to GPT-4 API calls. But this framing only holds if the comparison is against the closed-source API cost — it does not address the **relative cost within the open-source ecosystem**, where Self-Feedback or Direct Editing with a single model might provide better cost-adjusted performance. A practitioner with access to a single 7B model and a limited inference budget might rationally prefer Self-Feedback (67.7% on HumanEvalFix) over PPO-COFFEEEVAL (73.8%) if the 2× inference cost is not justified by the 6.1 percentage point gain, or if the available hardware cannot host two models simultaneously. The paper provides no data to inform this decision.

The separate-model design is not an accident — the paper demonstrates that Self-Feedback is ineffective (Table 3, -0.7 to -5.5 delta on COFFEE-TEST) and that the feedback and editing tasks benefit from specialized training. But the cost of specialization is the architectural complexity and inference overhead introduced. The paper's release of model checkpoints partially mitigates the practical burden (practitioners do not need to retrain), but the inference cost remains and is not discussed.
