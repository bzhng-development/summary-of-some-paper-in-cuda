# Balancing Pipeline Parallelism with Vocabulary Parallelism

**ArXiv:** [2411.05288](https://arxiv.org/abs/2411.05288)

## 🎯 Pitch

Pipeline parallelism breaks down when vocabulary sizes grow large because the embedding and output layers can demand 5× more computation and memory than a standard transformer layer, starving all but the first and last devices. This method partitions those vocabulary layers across all pipeline devices and fuses the pieces into existing schedules like 1F1B, yielding up to 51% throughput gains and perfectly balanced memory when paired with V-Half.

---

## 1. Executive Summary

This paper addresses a frequently overlooked imbalance in pipeline parallelism (PP) for transformer training, where vocabulary-related layers—the input embedding and output projection layers—create disproportionate computation and memory demands that worsen pipeline bubbles and memory bottlenecks. The authors introduce **Vocabulary Parallelism**, a method that partitions vocabulary layers evenly across all pipeline devices and groups the partitioned computation into pipeline passes that integrate with existing schedules like 1F1B and V-Half via a generalizable building-block framework. To reduce the activation memory overhead from communication barriers introduced by partitioning softmax, they propose two algorithms that progressively reduce the number of all-reduce synchronization points from three to one by leveraging online-softmax-style reordering—trading a small amount of extra computation for fewer cross-device dependencies. Evaluated on GPT-like models ranging from ~4B to ~30B parameters with vocabulary sizes from 32k to 256k on up to 32 A100 GPUs, Vocabulary Parallelism achieves a 5% to 51% throughput improvement over naïve approaches while significantly reducing peak memory, and when combined with the memory-balanced V-Half schedule, yields perfect balance in both computation and memory—establishing that pipeline parallelism can scale to large vocabularies without the imbalanced stages that plague standard layer-distribution methods, though the approach applies only when the vocabulary layers can be partitioned and the resulting communication barriers can be overlapped with transformer-layer computation.

## 2. Context and Motivation

### The Core Problem: Vocabulary Layers Break the Assumption of Uniform Pipeline Stages

Pipeline parallelism (PP) is built on a deceptively simple premise: split the layers of a neural network evenly across devices, and each device does roughly the same amount of work per microbatch. This assumption—that all layers impose comparable computational and memory costs—holds reasonably well for transformer layers, which dominate the model's depth and have uniform structure (self-attention followed by feed-forward, each with predictable FLOPs and parameter counts). But it breaks down completely at the **vocabulary layers**: the input embedding lookup and, more critically, the output projection layer that maps hidden states back to a distribution over the entire vocabulary.

The output layer's forward pass alone costs $6bshV$ FLOPs (where $b$ is microbatch size, $s$ is sequence length, $h$ is hidden dimension, and $V$ is vocabulary size), compared to $bsh(72h + 12s)$ for a full transformer layer (Table 4, Appendix A). For modern models with large vocabularies, this ratio can be dramatic. The paper quantifies this concretely with Gemma2 9B (vocabulary size 256k): **the output layer's compute and parameter memory are both approximately 5× those of a single transformer layer** (Figure 2). This means the last pipeline stage—which by convention hosts the output layer on top of its share of transformer layers—does substantially more work and stores substantially more parameters than any other stage.

The consequences cascade through the entire pipeline. On the computation side, the overloaded last stage becomes a bottleneck: other stages finish their work and sit idle waiting for it to complete, creating **pipeline bubbles**—gaps where devices are underutilized. Figure 1 illustrates this with a stark visual: a repeating pattern where a blue "extra output layer" block on Device 4 forces all other devices to wait, turning what should be a smooth pipeline into a stuttering one. On the memory side, the first stage (which hosts the input embedding layer) and especially the last stage (with the output projection) must store larger parameter tensors than intermediate stages, pushing memory utilization asymmetrically. For most PP schedules, including the widely-used 1F1B (Harlap et al., 2018), the memory bottleneck is already the limiting factor for model scale—and this imbalance makes it worse by concentrating pressure on specific devices.

### Why This Problem Is Growing Urgent

The imbalance is not a minor inefficiency that can be hand-waved away. Three trends in language model development are amplifying it:

**1. Vocabulary sizes are increasing.** The paper explicitly cites Tao et al. (2024), which established scaling laws showing that larger models deserve larger vocabularies. Modern open-source models reflect this: Gemma2 uses 256k tokens, Llama 3 uses 128k, and the trend line points upward. As $V$ grows, the output layer's compute ($6bshV$) and parameter memory ($2hV$) scale linearly with it, while transformer layers remain largely unaffected—the imbalance ratio gets worse with each generation of models.

**2. Pipeline parallelism is increasingly attractive for large-scale training.** Among the model parallelism techniques, PP has distinct advantages: its communication cost is low (only activations at stage boundaries, compared to the frequent all-reduce in tensor parallelism or the parameter gathering in ZeRO), and its arithmetic intensity is high (each device operates on full matrix multiplications rather than sharded operations). As models cross the hundred-billion parameter threshold, these properties make PP a natural choice—but the vocabulary imbalance undermines its efficiency at exactly the scales where PP's advantages should be most pronounced.

**3. Memory, not compute, is the binding constraint.** The paper repeatedly emphasizes this point: for most PP schedules, activation memory—the storage of intermediate tensors from forward passes that must be retained for backward passes—is the critical bottleneck limiting model scale (Section 1). Techniques like activation recomputation (Chen et al., 2016; Korthikanti et al., 2023) and memory offloading (Kim et al., 2023) have been developed specifically to address this. But when the first or last stage must additionally store outsized vocabulary parameters, the memory ceiling drops further—and it drops asymmetrically, so the peak memory across all devices (which determines whether training is possible at all) is set by the worst-offending stage.

The problem is not merely academic. In the paper's experiments, the naïve baseline (equal transformer layers per stage with vocabulary layers on endpoints) becomes outright infeasible in multiple configurations: training a ~30B model with 32 GPUs and a 256k vocabulary on the V-Half schedule hits **out-of-memory** (Figure 13 caption, Section 6.4). The imbalance literally prevents training from running.

### Prior Approaches and Where They Fall Short

The paper identifies several existing strategies for handling this imbalance, each with a fundamental limitation:

#### Layer Redistribution (DeepSpeed, Skywork-MoE)

The most straightforward fix is to give fewer transformer layers to the stages that host vocabulary layers, and more to the intermediate stages. DeepSpeed's automatic partitioning (Smith et al., 2022) uses a greedy algorithm to balance FLOPs across stages, and similar manual redistribution was employed in training Skywork-MoE (Wei et al., 2024). The idea is simple: since the first stage has an extra input layer (low compute, moderate memory) and the last has an extra output layer (high compute, high memory), offset those costs by adjusting their transformer layer allocations.

The paper demonstrates why this fails with a concrete example in Figure 3: for a 7B model with vocabulary size 128k, the output layer has 2.4× the compute and 2.6× the parameter memory of a transformer layer. Even after redistributing transformer layers (moving one from each intermediate stage to stages 1 and 4 in a 4-stage pipeline), the compute and memory remain measurably imbalanced—the bars in Figure 3's right-hand plots are not flat. The root cause is that **redistribution can only adjust in discrete layer increments**. If each stage starts with only 2 transformer layers (a realistic scenario as pipeline depth scales), taking one layer from each intermediate stage leaves them with 1, while the endpoints get 3. The output layer's 2.4× equivalent compute means the last stage still has roughly $3 + 2.4 = 5.4$ units of work versus the intermediate stages' 1 unit—a 5:1 imbalance.

More subtly, the paper identifies that **compute and memory cannot be simultaneously balanced by layer redistribution**. Transformer layers and vocabulary layers have different compute-to-memory ratios (Table 4). Moving transformer layers adjusts both compute and memory by linked amounts, while the vocabulary-layer imbalance affects compute and memory disproportionately. In practice, redistribution optimizes for compute balance (since pipeline bubbles are the most visible symptom), leaving parameter memory imbalance largely unaddressed. The first stage's input embedding layer is particularly problematic here: it requires minimal compute ($3bsh$ FLOPs) but substantial parameter memory ($2hV$, same as the output layer). Redistribution gives the first stage fewer transformer layers to offset the compute of the input layer, but this does nothing to address the input layer's memory footprint—the first stage still stores $2hV$ more parameters than an intermediate stage.

Finally, the paper notes that redistribution's effectiveness is **configuration-dependent**: "the effectiveness and planning of redistribution heavily depend on both the model settings and pipeline parallel settings" (Section 2). When the number of transformer layers per stage is large (e.g., a small model on few GPUs), the discrete granularity of layer moves is less problematic. When the vocabulary size is modest, the imbalance is naturally small. But as pipeline depth increases (more GPUs) and vocabulary sizes grow, redistribution's limitations become severe—it cannot guarantee balance in the scenarios where balance matters most.

#### Architectural Modifications (Llama 3's Approach)

The paper mentions that Llama 3 (Dubey et al., 2024) reduces one transformer layer from each of the first and last stages during pretraining from scratch. This is an architectural fix: by designing the model with the pipeline imbalance in mind, you can compensate structurally. The paper explicitly excludes this from scope because "it requires changes to architecture of models" and "has limitations if the training starts from a checkpoint where the number of transformer layers of model is fixed"—meaning it cannot be applied to existing pretrained models being fine-tuned or continued-trained, which is a common use case.

#### Interlaced Pipeline (nnScaler's Approach)

The most directly comparable prior method is the **interlaced pipeline** proposed by nnScaler (Lin et al., 2024), an automatic parallelism framework. The idea is to use **tensor parallelism (TP) for vocabulary layers** while keeping transformer layers in a standard pipeline: the output layer's weight matrix is split column-wise across devices (the TP approach for large linear layers), and an all-reduce is performed after the forward pass to synchronize the partial outputs. Since TP distributes both computation and parameters evenly, this should—in principle—balance the vocabulary layers perfectly.

The paper's ablation (Appendix B) reveals two fatal flaws with this approach:

**1. Activation memory increases by 1.5×.** Using the building-block framework from Qi et al. (2024), the paper shows in Figure 15 that the interlaced schedule's building block lengthens the **lifespan** (the interval between a forward pass and its corresponding backward pass) from $3p$ to approximately $4.5p$, where $p$ is the number of pipeline devices. Since peak activation memory is proportional to lifespan divided by interval, this translates directly to a 1.5× increase in activation memory. For 1F1B schedules that are already memory-constrained, this is catastrophic—the paper reports out-of-memory errors when training a 21B model with sequence length 4096 on 32 GPUs using the interlaced approach (Figure 11 caption, Section 6.3).

**2. Synchronous all-reduce creates ~11% pipeline bubble overhead.** TP-style communication requires all devices to synchronize before proceeding—the all-reduce in the output layer's forward pass and the reduce-scatter in its backward pass are blocking operations. Unlike the overlap-able communication in the paper's Vocabulary Parallelism (where all-reduce runs in a separate CUDA stream alongside transformer computation), the interlaced pipeline's communication is on the critical path. The paper quantifies this with an ablation (Appendix B.2): removing the synchronous all-reduce communications from the interlaced pipeline improved end-to-end iteration time by 10.95% when training a 21.5B model on 32 GPUs. This means approximately 11% of training time was spent idle waiting for vocabulary-layer synchronization—a direct throughput penalty.

The combination of higher memory pressure and lower throughput makes the interlaced pipeline **practically untenable for multi-node training**, which is precisely the regime where pipeline parallelism is most valuable (since tensor parallelism is typically confined to intra-node due to its communication volume).

#### The Broader Landscape: Why Existing PP Optimizations Don't Help

The paper positions its work relative to a broader class of PP improvements that are **orthogonal** to the vocabulary imbalance problem. Activation memory balancing techniques like BPipe (Kim et al., 2023), which transfers activations between devices, and V-Half (Qi et al., 2024), which uses V-shaped device placement to equalize activation memory across stages, address a *different* imbalance: the fact that 1F1B schedules inherently store more activations on earlier pipeline stages. These methods can balance activation memory perfectly, but they do nothing about parameter memory or compute imbalance from vocabulary layers. Similarly, zero-bubble pipeline parallelism (Qi et al., 2023) eliminates pipeline bubbles caused by the forward-backward timing mismatch, but only if the underlying workload is balanced—if one stage has extra vocabulary computation, bubbles re-emerge.

The paper's key insight is that these existing optimizations and the vocabulary imbalance are **independent problems requiring independent solutions**. V-Half can make activation memory perfectly balanced across stages, but the last stage will still store $2hV$ more parameter memory than its neighbors, and the first-to-last-stage memory gap can reach 45GB in the paper's experiments (Section 6.4, Figure 14 caption). Conversely, fixing the vocabulary imbalance with redistribution addresses compute bubbles but leaves activation memory asymmetry untouched. The paper's ambition—partially realized by combining Vocabulary Parallelism with V-Half—is to solve both simultaneously for a truly balanced pipeline.

### How This Paper Positions Itself

The paper frames Vocabulary Parallelism not as an alternative to existing PP schedules, but as a **composable technique** that can be integrated with minimal disruption. This is explicit in the design principles stated in Section 3:

> "To be native to pipeline parallelism, the computation of vocabulary layers should be represented as passes similar to forward/backward passes of transformer layers."
> "Integrating vocabulary passes into pipeline schedules should not drastically affect the memory and efficiency of the original pipeline schedule."

This is a deliberate design stance. Rather than proposing a new pipeline schedule (which would fragment the ecosystem and require re-engineering existing implementations), the paper treats vocabulary layers as additional "passes" (like forward and backward) that slot into the building blocks of existing schedules. The only modification needed is to insert a fixed number of extra intervals between the forward and backward passes of the last transformer layer—a change that can be implemented by altering the building block definition while leaving the rest of the schedule machinery intact.

The paper's contribution is therefore **not a new schedule, but a new partitioning strategy for vocabulary layers** paired with a **generalizable integration methodology** that works across multiple schedules (1F1B and V-Half are demonstrated; the framework extends to any schedule constructed from repeating building blocks). The claim, validated by the experiments, is that this approach achieves what redistribution and interlacing cannot: perfect or near-perfect balance in both computation and parameter memory, with only a small constant activation memory overhead (at most 2 microbatches' worth), and without the 1.5× activation memory penalty of synchronous approaches.

The positioning is also carefully scoped. The paper acknowledges that it addresses only the vocabulary-layer imbalance in text-based LLMs, and explicitly suggests that multimodal embedding layers "suffer from the same problem and can be further explored" (Section 7). It does not claim to solve all pipeline imbalances—just the one that existing PP literature has largely overlooked and that grows more severe with vocabulary scaling trends.

## 3. Technical Approach

### 3.1 Reader Orientation

This paper develops a systematic method for partitioning the vocabulary layers (input embeddings and output projection) of a transformer across all pipeline-parallel devices, then scheduling the resulting split computation as additional "passes" that slot cleanly into standard pipeline schedules like 1F1B and V-Half. The core problem is that vocabulary layers create massive compute and memory imbalance—the first and last pipeline stages do significantly more work and store far more parameters than intermediate stages—and the solution "shape" is to shard these layers across the vocabulary dimension so every device handles an equal share, while carefully reordering the computation to minimise the number of cross-device synchronisation barriers that would otherwise balloon activation memory.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has five major components:

1. **Vocabulary Partitioning** — the input and output layers' weight matrices are split column-wise across all pipeline devices, so each device owns a slice of the embedding table and output projection, eliminating the parameter memory concentration at endpoints.

2. **Computation Reordering (Forward and Backward Optimizations)** — the output layer's softmax computation is algebraically rewritten (using online-softmax-style transformations) to reduce three cross-device communication barriers (two all-reduces and one reduce) down to two, then down to one, by reordering operations so that the remaining all-reduce covers only lightweight elementwise work, while the heavy matrix multiplications happen independently before the barrier.

3. **Pipeline Pass Abstraction** — the partitioned vocabulary computation is grouped into named passes (`S` for the forward softmax operations, `T` for the backward weight gradient operations) that behave like forward/backward passes of transformer layers, fitting into the existing interval-based building-block framework of pipeline schedules.

4. **Schedule Integration via Building Blocks** — rather than designing a new schedule from scratch, the vocabulary passes are inserted by widening the "lifespan" (the gap between the last transformer layer's forward and backward) by 1–2 intervals, creating space to schedule `S` and `T` passes while preserving the overall repeating pattern. The peak activation memory increase is bounded at 1–2 microbatches—a small constant—regardless of pipeline depth.

5. **Communication Overlap via Streams** — the all-reduce and reduce operations are placed in separate CUDA streams so that their execution overlaps with transformer-layer computation in the main stream, hiding communication latency behind useful work.

Information flows as follows: each microbatch's hidden states exit the last transformer layer → the partitioned forward softmax computation (`S`) runs locally on each device, producing partial results → an all-reduce synchronises the necessary global scalars → the backward computation (`T`) produces partial input gradients → a reduce scatters the full input gradient back to all devices → the remaining backward pass of the transformer layer proceeds. Meanwhile, the input embedding layer's forward and backward are piggybacked onto the warmup and cooldown phases of the pipeline, holding input embeddings for at most two microbatches at any moment.

### 3.3 Roadmap for the Deep Dive

- **First**, the design principles and core partitioning strategy (Section 3 of the paper): why partition across the vocabulary dimension, and what constraints must any vocabulary-parallel scheme satisfy to be "native" to pipeline parallelism.
- **Second**, the naïve partitioning approach with three communication barriers, necessary to understand what the optimizations improve upon: the computation graph of the softmax and its backward pass, where the three all-reduce/reduce operations sit, and why they create problems for pipeline scheduling and activation memory.
- **Third**, the forward-phase optimization (Algorithm 1) that reduces three barriers to two, using an online-softmax identity that defers the global maximum and sum to after the local softmax: the algebraic derivation, the exact operations moved, and why this helps.
- **Fourth**, the backward-phase optimization (Algorithm 2) that reduces barriers to one, by computing the input gradients' matrix multiplications before the communication barrier and deferring only lightweight rescaling to the synchronized step: the deeper rearrangement, the extra computation it introduces, and the activation memory savings it enables.
- **Fifth**, the pipeline scheduling integration methodology using the building-block framework from Qi et al. (2024): how lifespans, intervals, and repeating patterns determine peak activation memory, and how inserting vocabulary passes widens the lifespan by a bounded constant.
- **Sixth**, the specific schedule constructions for 1F1B and V-Half, including the input layer's piggybacked scheduling in warmup/stable/cooldown phases.
- **Seventh**, the implementation details that make it work in practice: CUDA stream management, NCCL communication choices, vocabulary padding for memory alignment, and how these interact.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems optimization paper** whose core idea is that vocabulary-layer imbalance in pipeline parallelism can be eliminated entirely—not merely mitigated—by partitioning the vocabulary layers across all pipeline devices, grouping the split computation into pipeline passes, and integrating those passes into existing schedules using a building-block framework that bounds the activation memory overhead to a small constant.

#### Design Principles (Section 3 of the Paper)

The paper opens its technical contribution with three explicit design principles that constrain every subsequent decision:

> 1. "We partition the vocabulary layers across the vocabulary dimension, and distribute it evenly to all pipeline devices."
> 2. "To be native to pipeline parallelism, the computation of vocabulary layers should be represented as passes similar to forward/backward passes of transformer layers."
> 3. "Integrating vocabulary passes into pipeline schedules should not drastically affect the memory and efficiency of the original pipeline schedule."

**Principle 1—Partition across the vocabulary dimension, not the batch or hidden dimension.** The vocabulary dimension (size $V$) is the natural choice because it is large (32k–256k in modern models), independent of the batch and sequence dimensions, and orthogonal to other parallelism strategies like tensor parallelism (which typically partitions attention heads or hidden dimensions) and data parallelism (which partitions the batch). Partitioning column-wise means each device $i$ owns a slice $W_i \in \mathbb{R}^{V/p \times h}$ of the embedding matrix, receiving only the hidden states that project onto its vocabulary slice. This distributes both compute ($6bshV/p$ FLOPs instead of $6bshV$) and parameter memory ($2hV/p$ instead of $2hV$) evenly—assuming $V$ is divisible by $p$ (a constraint the paper handles via padding).

**Principle 2—Vocabulary computation as pipeline passes.** The pipeline model of computation revolves around "passes": forward pass (F), backward pass (B), and in zero-bubble schedules, weight gradient pass (W). Each pass is a contiguous block of computation on a single microbatch. By framing vocabulary computation in these terms—named `S` (softmax forward operations) and `T` (weight gradient backward operations)—the vocabulary work becomes a first-class citizen in the scheduling framework. The key constraint is that `S` passes have dependencies on transformer forward passes, and `T` passes have dependencies on `S` passes, just as backward passes depend on forward passes. Representing vocabulary computation this way means existing schedule machinery (building blocks, interval counting, lifespan analysis) applies without modification.

**Principle 3—Bounded memory overhead.** This is the most operationally critical principle. Pipeline schedules are already memory-constrained; any vocabulary-parallelism scheme that substantially increases activation memory is self-defeating. The paper's target is a "small constant overhead"—at most 2 microbatches' worth of activation memory, regardless of pipeline depth $p$ or vocabulary size $V$. This constraint directly motivates the communication-barrier reduction algorithms: each barrier widens the lifespan (the gap between a forward and its corresponding backward) by one interval, and peak activation memory is proportional to lifespan divided by interval.

#### The Naïve Partitioning Approach (Section 4.1)

Before presenting the optimizations, the paper walks through the straightforward partitioning to establish the baseline and surface the communication problem.

**Output layer computation unpartitioned.** For a single microbatch with hidden states $X \in \mathbb{R}^{bs \times h}$ and embedding weights $W \in \mathbb{R}^{V \times h}$, the standard forward pass computes:

$$Y = XW^T$$

where $Y \in \mathbb{R}^{bs \times V}$ is the logits matrix—one row per token, one column per vocabulary entry. The (safe) softmax then computes, for each token $i$:

$$m_i = \max_k Y_{ik}$$
$$sum_i = \sum_k e^{Y_{ik} - m_i}$$
$$\text{softmax}(Y_{ij}) = \frac{e^{Y_{ij} - m_i}}{sum_i}$$

where $m_i$ is the maximum logit for token $i$ (subtracted for numerical stability), and $sum_i$ is the sum of exponentiated logits.

In the backward pass (assuming cross-entropy loss with ground-truth labels $g_i$), the gradients are:

$$\nabla X = (\text{softmax}(Y) - G) W$$
$$\nabla W = (\text{softmax}(Y) - G)^T X$$

where $G \in \mathbb{R}^{bs \times V}$ is a sparse matrix with $G_{i, g_i} = 1$ and zeros elsewhere.

**Partitioned version with three communication barriers.** After splitting $W$ column-wise across $p$ devices, each device $d$ holds $W_d \in \mathbb{R}^{V/p \times h}$ and computes $Y_d = X W_d^T \in \mathbb{R}^{bs \times V/p}$, which is the logits for its vocabulary slice only. The softmax, however, requires **global** statistics—the maximum $m_i$ and sum $sum_i$ across all $V$ logits, not just the $V/p$ on device $d$. This forces synchronisation:

1. **All-reduce for maximum (AR Max):** Each device computes its local maximum $m_i^{(d)} = \max_{k \in \text{slice}_d} (Y_d)_{ik}$. An all-reduce with `MAX` operation computes the global $m_i = \max_d m_i^{(d)}$, broadcasting it to all devices.

2. **All-reduce for sum (AR Sum):** Each device computes its local sum $sum_i^{(d)} = \sum_{k \in \text{slice}_d} e^{(Y_d)_{ik} - m_i}$ (using the now-known global $m_i$ for numerical stability). An all-reduce with `SUM` operation computes the global $sum_i = \sum_d sum_i^{(d)}$, broadcasting it to all devices.

3. **Reduce for input gradients (R):** In the backward pass, each device computes $\nabla X^{(d)} = (\text{softmax}(Y_d) - G_d) W_d$, but this gives only the contribution from its vocabulary slice. A reduce (summation across devices, with the result on one device) or all-reduce (result on all devices) is needed to combine partial input gradients into the full $\nabla X$.

These three operations—two all-reduces in the forward path (after $F1$ and $F2$ in Figure 4's notation) and one reduce in the backward path—create **cross-device dependencies**: no device can proceed past an all-reduce until all devices reach it. In pipeline scheduling terms, each barrier forces a synchronisation point where all pipeline stages must align, complicating the insertion of vocabulary passes into the otherwise-independent per-device schedule.

**Why three barriers are problematic for pipelines.** Figure 6 shows the dependency structure for a single microbatch: each device executes $F1$ (initial matrix multiply and local max/sum), then all-reduce for max, then $F2$ (local softmax using global max), then all-reduce for sum, then $B$ (backward matrix multiplies and local input gradients), then reduce for input gradients. The consequence for pipeline scheduling (detailed later in Section 5.2) is that each communication barrier **widens the lifespan**—the interval between a forward and its corresponding backward—by one microbatch slot. Three barriers mean the lifespan grows by at most 3 intervals, which translates directly to proportionally higher peak activation memory. The paper's optimization goal is therefore to reduce the number of barriers, ideally to one.

#### Forward Phase Optimization: Three Barriers to Two (Section 4.3, Algorithm 1)

The first optimization leverages an algebraic identity from **online softmax** (Milakov & Gimelshein, 2018; Dao et al., 2022) to combine the two forward-phase all-reduces into one, reducing the total barrier count from 3 to 2.

**The key identity.** Online softmax observes that given local statistics and the global statistics, you can correct the local softmax to the global softmax without recomputing from scratch. Specifically, if device $d$ computes softmax using only its local maximum $m_i^{(d)}$ and local sum $sum_i^{(d)}$:

$$m_i'^{(d)} = \max_{k \in \text{slice}_d} (Y_d)_{ik}$$
$$sum_i'^{(d)} = \sum_{k \in \text{slice}_d} e^{(Y_d)_{ik} - m_i'^{(d)}}$$
$$\text{softmax}'( (Y_d)_{ij} ) = \frac{e^{(Y_d)_{ij} - m_i'^{(d)}}}{sum_i'^{(d)}}$$

Then given the global maximum $m_i$ and global sum $sum_i$, the global softmax is obtained by a rescaling:

$$\text{softmax}(Y_{ij}) = \text{softmax}'( (Y_d)_{ij} ) \times \frac{sum_i'^{(d)} \times e^{m_i'^{(d)} - m_i}}{sum_i}$$

**What this identity enables.** Instead of computing the all-reduce for $m_i$, then computing local sums using the global max, then all-reducing sums—a sequential chain of two barriers—the local softmax $\text{softmax}'$ can be computed **before any communication**. Then a single communication phase (`C1` in Algorithm 1) all-reduces both the local maximum $m_i'^{(d)}$ and the modified local sum $sum_i'^{(d)} \times e^{m_i'^{(d)} - m_i}$ simultaneously. After this single barrier, the global softmax is obtained via the rescaling factor.

**Algorithm 1 walkthrough (Figure 7, middle panel).** The execution order for a single microbatch becomes:

1. **`C0` (broadcast):** Receive hidden states $X$ from the last transformer layer (this is standard pipeline boundary communication, not a new barrier—the data must arrive before computation starts).

2. **`S` (local computation block):** Compute $Y_d = X W_d^T$, then the local softmax $\text{softmax}'(Y_d)$ using only local statistics. No communication needed. All operations are matrix multiplications or elementwise, making this a compute-dense block.

3. **`C1` (single all-reduce barrier):** All-reduce the pairs $(m_i'^{(d)}, sum_i'^{(d)} \times e^{m_i'^{(d)} - m_i})$. After the all-reduce, every device knows $m_i = \max_d m_i'^{(d)}$ and $sum_i = \sum_d sum_i'^{(d)} \times e^{m_i'^{(d)} - m_i}$. The elementwise rescaling to obtain global softmax is lightweight (only tensors of size $bs$, not $bs \times V/p$) and can execute within the same stream as the all-reduce, overlapping with any transformer computation happening in the main stream.

4. **`T` (backward computation):** Compute $\nabla X^{(d)} = (\text{softmax}(Y_d) - G_d) W_d$ and $\nabla W_d = (\text{softmax}(Y_d) - G_d)^T X$. These are matrix multiplications and independent of other devices.

5. **`C2` (reduce barrier):** Reduce the partial input gradients: $\nabla X = \text{Reduce}(\nabla X^{(d)})$, summing across devices and distributing the result.

**What changed from naïve.** The two forward-phase all-reduces (AR Max and AR Sum) are merged into one combined all-reduce. The cost is slightly more computation in `C1` (the elementwise operations to combine max and sum before the all-reduce, and the rescaling after), but these operations involve tiny tensors ($[bs]$) compared to the $[bs, V/p]$ logits tensors, so the overhead is negligible.

**Why this matters for pipeline scheduling.** The barrier count drops from 3 to 2, which means the lifespan of a microbatch widens by at most 2 intervals instead of 3. Peak activation memory is proportional to lifespan, so this is a direct memory reduction. The impact becomes concrete in Figure 9 (top): with Algorithm 1, the 1F1B building block inserts 2 intervals between the last transformer forward and backward, versus 3 for the naïve approach.

#### Backward Phase Optimization: Two Barriers to One (Section 4.4, Algorithm 2)

The second optimization goes further, observing that **all three communication barriers can be deferred to a single synchronization point** after most of the backward computation, reducing the barrier count to one.

**The deeper rearrangement.** Equation (6) in the paper provides the key insight. The input gradient can be written as:

$$\nabla X = \text{softmax}'(Y) W \times \frac{sum_i' \times e^{m_i' - m_i}}{sum_i} - GW$$

where $\text{softmax}'(Y) W$ and $GW$ are both matrix multiplications that can be computed **before any communication**. Let $A = \text{softmax}'(Y) W$ and $B = GW$. Both are computed locally on each device, using only data the device already has: $A$ uses the local softmax and local weight slice, $B$ uses the ground-truth labels (known to all devices) and local weight slice.

After computing $A$ and $B$, the device can participate in a **single combined communication phase** that:

1. All-reduces $m_i'^{(d)}$ (same as before).
2. All-reduces $sum_i'^{(d)} \times e^{m_i'^{(d)} - m_i}$ (same as before).
3. Reduces $A \times \frac{sum_i' \times e^{m_i' - m_i}}{sum_i} - B$ (the input gradient contribution).

The critical observation is that steps 1 and 2 provide the global $m_i$ and $sum_i$, which then allow rescaling $A$ to the correct input gradient. Since the rescaling is elementwise and cheap (only $[bs, h]$ tensors), the entire input gradient computation inside the barrier is lightweight.

**Algorithm 2 walkthrough (Figure 7, bottom panel).** The execution order becomes:

1. **`C0` (broadcast):** Receive $X$.

2. **`S` (local computation block):** Identical to Algorithm 1's `S`: compute $Y_d$, local softmax, and additionally precompute $A = \text{softmax}'(Y_d) W_d$ and $B = G_d W_d$. These are the dominant FLOPs of the backward pass—two matrix multiplications—and they execute independently on each device before any communication.

3. **`C1` (single combined barrier):** All-reduce the pair $(m_i'^{(d)}, sum_i'^{(d)} \times e^{m_i'^{(d)} - m_i})$ to obtain global $m_i$ and $sum_i$, and simultaneously reduce $\nabla X^{(d)} = A \times \frac{sum_i' \times e^{m_i' - m_i}}{sum_i} - B$ to obtain the full input gradient $\nabla X$. All communication happens in this single synchronization point.

4. **`T` (weight gradient):** Compute $\nabla W_d = (\text{softmax}(Y_d) - G_d)^T X$. Critically, this step can be **arbitrarily delayed**—"similar to the idea in zero-bubble strategy (Qi et al., 2023)"—because no downstream computation depends on the weight gradients until the optimizer step at the end of the batch. The paper exploits this by scheduling `T` flexibly after `C1`, wherever it fits in the pipeline without creating new dependencies.

**What changed from Algorithm 1.** The separate reduce for input gradients (`C2` in Algorithm 1) is absorbed into the combined barrier `C1`. The barrier count drops from 2 to 1. The tradeoff is additional computation in `S` (precomputing $A$ and $B$, which doubles the matrix multiplications in the local block) and slightly heavier `C1` (now includes the input gradient reduce alongside the max/sum all-reduces). However, as the paper notes in Section 6.5, this extra computation is modest—Table 3 shows Algorithm 2 achieves 75–89% of linear scaling for the output layer, versus 80–93% for Algorithm 1 (both measured relative to ideal $p \times$ speedup). The 5–10% throughput difference is the price paid for halving the barrier count.

**Why one barrier is the theoretical minimum.** The output layer fundamentally requires at least one global reduction: the softmax normalisation needs the maximum and sum across all vocabulary partitions, and the input gradient needs to sum partial gradients. These are irreducible cross-device dependencies—you cannot avoid them entirely without changing the mathematical definition of the softmax. One barrier represents the tightest possible integration, where all necessary global information is exchanged in a single synchronised step.

**Comparison with the naïve approach (Figure 7).** The three-panel figure in the paper shows the evolution clearly:
- **Naïve:** Sequential `F1` → AR Max → `F2` → AR Sum → `B` → Reduce → end. Three barriers interleaved with computation.
- **Algorithm 1:** `S` → combined AR → `T` → Reduce. Two barriers.
- **Algorithm 2:** `S` (with precomputed $A$, $B$) → combined AR+Reduce → `T`. One barrier.

The scheduling dependencies for a single microbatch in each algorithm are further illustrated in Figure 8. In Algorithm 1 (top), device 4's `T` completes before the backward pass can start on device 3, and the separate `C2` adds an extra synchronisation. In Algorithm 2 (bottom), `T` is flexibly placed after the backward pass on some devices (device 4 does `T` after `B`, while device 1 does `T` before `B`), demonstrating that the removal of the second barrier decouples the weight gradient computation from the critical path.

#### Pipeline Scheduling Integration: The Building-Block Methodology (Section 5)

The paper does not design a new pipeline schedule from scratch. Instead, it adapts the building-block framework from Qi et al. (2024) to incorporate vocabulary passes with minimal changes.

**The building-block framework in brief.** In this framework, every pipeline schedule can be defined by a **building block**—the pattern of passes (forward `F`, backward `B`, weight gradient `W`, and now vocabulary passes `S` and `T`) that each microbatch follows on each device. The full schedule is constructed by **repeating the building block uniformly** for each microbatch, with appropriate warmup (filling the pipeline) and cooldown (draining the pipeline) phases at the boundaries. This uniform repetition makes the schedule easy to reason about: the peak activation memory is determined by the **lifespan** (the time between a forward and its corresponding backward) divided by the **interval** (the workload of a single microbatch on each device). The lifespan is measured in intervals, so if a building block has a forward at time $t$ and its backward at time $t + L$, the device must store the forward's activations for $L$ intervals, and the peak occurs when the maximum number of in-flight forwards overlap.

**How vocabulary passes modify the building block.** The key observation is that the vocabulary `S` and `T` passes need to be inserted between the forward and backward of the **last transformer layer**—the one immediately preceding the output projection. The paper's approach is direct: widen the lifespan of that last transformer layer by inserting 1 or 2 extra intervals (for Algorithm 2 or Algorithm 1 respectively), creating space to schedule `S` and `T` on each device.

Concretely, for the 1F1B schedule (Figure 9, top panel for Algorithm 1; bottom panel for Algorithm 2):
- The standard 1F1B building block has a **lifespan** of $p$ intervals (where $p$ is the number of pipeline stages), meaning each device holds at most $p$ in-flight activations.
- With Algorithm 1, the building block inserts **2 intervals** between `F` and `B` for the last transformer layer, occupied by `S` and `T` passes. The lifespan becomes $p + 2$ intervals, and peak activation memory rises to $p + 2$ microbatches' worth.
- With Algorithm 2, only **1 interval** is inserted (the combined `C1` and `T` follow `S` in a single slot), giving lifespan $p + 1$ and peak memory $p + 1$ microbatches.

Crucially, this overhead is **constant**: it does not scale with vocabulary size $V$, pipeline depth $p$, or number of microbatches. Adding 2 microbatches of activation memory on a pipeline that already stores $p$ microbatches is a small fractional increase (e.g., for $p=8$, it's $10/8 = 1.25\times$; for $p=32$, it's $34/32 \approx 1.06\times$). This satisfies the third design principle—the memory overhead is bounded and becomes negligible at scale.

**The full scheduling dependencies (Figure 8).** For a single microbatch, the constraints are:
- `S` must execute after the forward pass of the last transformer layer completes (since `S` takes $X$ as input).
- `T` must execute after `S` completes (since `T` needs the global softmax from `C1`).
- For Algorithm 1 only: the backward pass of the last transformer layer must wait for `T` to complete (because the reduce for $\nabla X$ in `C2` provides the input gradient needed to start the transformer backward).
- For Algorithm 2: `T` can be arbitrarily delayed (weight gradients are not consumed until the optimizer step), so the transformer backward can start as soon as `C1` provides $\nabla X$. This is why Figure 8 (bottom) shows `T` placed flexibly—sometimes before the backward, sometimes after, depending on where it fits.

**The complete 1F1B schedules (Figure 10).** The paper presents the full schedules for 8 microbatches on 4 pipeline devices. Reading the diagrams:
- Each numbered box is a microbatch. `F` is forward, `B` is backward, and the colored blocks are vocabulary passes (input layer in green/orange, output layer passes in blue/purple).
- In Algorithm 1's schedule (Figure 10a), each device follows a `F → S → T → B` pattern on the last microbatch, with `S` and `T` inserted between forward and backward. The extra `C2` barrier means `T` must complete before `B` starts, creating visible gaps.
- In Algorithm 2's schedule (Figure 10b), the pattern is more flexible: some devices do `T` after `B` (e.g., device 4 on microbatch 1), some do `T` before `B` (e.g., device 2 on microbatch 3), exploiting the decoupling of weight gradient computation from the backward critical path.

**Input layer scheduling.** The input embedding layer is simpler because it has no cross-device dependencies in the forward/backward computations themselves—only an all-reduce to gather the embedded outputs and a broadcast to scatter the input gradients. The paper schedules these as follows (Section C in the appendix, and the green/orange blocks in Figure 10):

- **Warmup phase:** Input forward is performed one microbatch **before** the first transformer forward, creating one interval of slack for the all-reduce to complete before the transformer layer needs the embedded tokens.
- **Stable phase:** Input forward is "piggybacked" with the output layer passes, scheduled at least one repeating interval before the corresponding transformer forward. Similarly, input backward is piggybacked at least one interval after the transformer backward, providing slack for the broadcast.
- **Cooldown phase:** Input backward is performed one microbatch after the last transformer backward.

This piggybacking ensures that each device holds the input layer's output embeddings for **at most two microbatches** at any instant, minimizing the memory pressure from what would otherwise be large intermediate tensors ($bs \times h$).

**V-Half integration (Appendix D, Figure 16).** The V-Half schedule (Qi et al., 2024) uses a V-shaped device placement where the first and last pipeline stages are on the same physical device, halving peak activation memory. The paper's integration follows the same building-block methodology: the V-Half building block (which already includes `W` weight gradient passes) is modified to insert `S` and `T` passes between the last transformer forward and backward, with 2 or 1 extra intervals depending on the algorithm. Figure 16 shows the modified building block with `F → S → T → B` inserts. The result, validated experimentally in Section 6.4, is a schedule balanced in both activation memory (thanks to V-Half) and parameter memory/computation (thanks to Vocabulary Parallelism)—a "fully balanced pipeline parallelism."

#### Implementation Details That Make It Work (Section 6.1)

Beyond the algorithms and scheduling, several low-level implementation choices are critical to realizing the theoretical benefits in practice.

**Profiling-based schedule generation.** Standard pipeline schedules assume the backward pass takes exactly twice the time of the forward pass (a rule of thumb for transformer layers). The paper notes that this assumption can introduce "unnecessary bubbles," so they **profile the actual run time** of each pass type and adjust the schedule accordingly. If the profiling shows the $B:F$ ratio deviates from 2:1 beyond a threshold, the schedule is recomputed. In practice, the paper reports that "the difference is negligible in most transformer networks," so this profiling is "viewed as optional"—but it represents a pragmatic engineering choice to avoid hardcoding assumptions.

**CUDA stream management for communication-computation overlap.** The all-reduce and reduce operations in Algorithms 1 and 2 are placed in **separate CUDA streams** from the main computation stream. This allows the GPU to overlap communication kernels with computation kernels: while the all-reduce for $m_i$ and $sum_i$ proceeds on one stream, the transformer layer's forward or backward can execute on another stream (Figure 5 illustrates the overlap concept). The paper maps CUDA streams to separate GPU work queues by setting `CUDA_DEVICE_MAX_CONNECTIONS` appropriately.

A subtlety arises with tensor parallelism. TP relies on single work queues for efficient communication-computation overlap; using multiple streams can degrade TP performance. To mitigate this, the paper sets **all model-parallel communication groups to use high-priority streams**, ensuring TP's communication gets scheduled ahead of vocabulary-layer communication when they contend for bandwidth.

**NCCL communication choices.** Both the `AllReduce` and `Reduce` operations in Algorithms 1 and 2 are implemented as **NCCL AllReduce**. Using `AllReduce` for what is logically a reduce (summation across devices) avoids **imbalanced communication volume** across devices—a standard `Reduce` would concentrate all data on a root device, creating a bottleneck, while `AllReduce` scatters the result uniformly.

**Vocabulary padding for memory alignment.** The vocabulary size $V$ is padded to be a multiple of $2p$ (where $p$ is the number of pipeline devices). This is a memory alignment optimization: GPU kernels for matrix multiplication operate most efficiently when dimensions are multiples of small powers of two. The paper reports a concrete impact: "an approximate 8% increase in performance if our method is applied to 24 devices with padded size 256032 (a multiple of 48), compared to the original value 256008."

**Untied embedding weights (harder setting).** Some models tie the input and output embedding weights (a single $W$ serves both embedding lookup and output projection), which would simplify Vocabulary Parallelism by reducing the number of weight tensors to manage. The paper deliberately uses the **untied** setting "since it is adapted by some open source models like Llama 3 (Dubey et al., 2024)"—this is the harder case because it requires managing separate weight tensors and gradient synchronisations for input and output layers, making the results a conservative estimate of the method's benefits.

**FP16/BF16 considerations.** While not explicitly discussed in the main text, the paper's implementation targets mixed-precision training, which is standard in Megatron-LM. The vocabulary layers' matrix multiplications operate in half-precision (with master weights in FP32), and the all-reduce communications operate on half-precision tensors to minimize bandwidth.

---

#### Connection to Prior Work: Why This Isn't Just Tensor Parallelism

A reader familiar with tensor parallelism might ask: isn't partitioning the output layer's weight matrix column-wise exactly what TP does? The distinction is crucial and explains why Vocabulary Parallelism avoids TP's pitfalls.

**Tensor parallelism (Megatron-LM style):** In TP, a linear layer $Y = XW^T$ is partitioned column-wise across devices. Each device computes $Y_i = X W_i^T$. To proceed with subsequent operations, the partial outputs $Y_i$ must be gathered (via all-reduce or all-gather) so that each device sees the full $Y$. This synchronisation happens **inside the layer**, on the critical path, and involves the full $bs \times V$ tensor. For the output layer, this is an enormous communication volume (e.g., $bs \times 256k$ elements), and it must complete before the softmax can begin. In the backward pass, an equivalent all-reduce is needed for the input gradients. This synchronous, high-volume communication is why TP is typically confined to intra-node (NVLink) and why the interlaced pipeline (which applies TP to vocabulary layers) incurs an ~11% throughput penalty.

**Vocabulary Parallelism:** The vocabulary layers are partitioned (same column-wise split), but the softmax computation is reordered so that **only the global statistics ($m_i$ and $sum_i$, each of size $bs$) are communicated**, not the full $bs \times V/p$ logits tensors. The key enabler is the online-softmax identity (Algorithm 1) and its backward extension (Algorithm 2): by precomputing the local softmax and the matrix multiplications that consume it, the communication is reduced to lightweight elementwise operations on tiny tensors. The communication volume drops from $O(bsV)$ (full logits) to $O(bs)$ (global max and sum), a reduction factor of $V/p$ (which is thousands to tens of thousands). Moreover, this reduced communication is overlapped with transformer computation via separate streams, hiding its latency.

This is not merely a different schedule—it is a **mathematically correct reordering** of the softmax computation that changes what needs to be communicated. The paper's Algorithms 1 and 2 are the mechanism by which what looks like TP is transformed into something with pipeline-appropriate communication properties.

---

#### Summary of Design Choices and Their Justifications

- **Partition across vocabulary dimension** rather than batch or hidden dimensions: exploits the large $V$, ensures even distribution, orthogonal to other parallelism axes.
- **Online-softmax forward optimization (Algorithm 1):** defers global statistics to after local softmax, merging two all-reduces into one, reducing barriers from 3 to 2.
- **Backward precomputation optimization (Algorithm 2):** precomputes $\text{softmax}'(Y)W$ and $GW$ before the barrier, absorbing the input gradient reduce into the single combined barrier, reducing barriers from 2 to 1.
- **One barrier as the practical optimum:** irreducible global dependencies exist, but all are combined into a single synchronised step.
- **Building-block integration (not custom schedule):** inserts vocabulary passes by widening the last transformer layer's lifespan by 1–2 intervals, bounding activation memory overhead to a constant small multiple.
- **Separate CUDA streams for communication overlap:** hides all-reduce latency behind transformer computation, achieving near-zero communication cost on throughput.
- **NCCL AllReduce for all reductions:** avoids imbalanced communication volume and simplifies the implementation.
- **Vocabulary padding to multiple of $2p$:** memory alignment optimization yielding ~8% throughput improvement on 24 GPUs.
- **Untied embedding weights:** tests the harder case, making results conservative for the tied-weight scenario.
- **Input layer piggybacking:** leverages warmup/cooldown slack to overlap input layer communication, bounding input embedding storage to at most 2 microbatches.

## 4. Key Insights and Innovations

### Innovation 1: Vocabulary Imbalance as a Diagnosable, Independent Bottleneck in Pipeline Parallelism

The paper's most foundational contribution is not a technique but a **diagnostic reframing**: it identifies vocabulary-layer imbalance as a distinct failure mode of pipeline parallelism that is orthogonal to the activation-memory and bubble problems that prior PP research has focused on.

Before this work, the PP literature treated workload imbalance as a general problem to be addressed through layer redistribution (DeepSpeed's greedy balancing, Smith et al., 2022; manual redistribution in Skywork-MoE, Wei et al., 2024) or through more sophisticated scheduling (zero-bubble, Qi et al., 2023; V-Half, Qi et al., 2024). The implicit assumption was that imbalance is a layer-counting problem—stages have different numbers of layers, so move layers around until the counts roughly match. The vocabulary layers were just "a few extra layers" on the endpoints, to be compensated for by adjusting transformer layer allocations.

The paper demonstrates that this framing is fundamentally inadequate. Vocabulary layers are not merely "extra layers" with the same properties as transformer layers; they have a **qualitatively different compute-to-memory ratio and scaling behavior**. Table 4 (Appendix A) makes this quantitative: a transformer layer's compute is $bsh(72h + 12s)$ with parameter memory $24h^2$, while the output layer's compute is $6bshV$ with parameter memory $2hV$. The ratio of compute to parameter memory is fundamentally different—transformer layers are compute-bound relative to their parameter count ($O(h)$ compute per parameter for large $h$), while output layers are parameter-memory-heavy when $V$ is large ($O(bs)$ compute per parameter). This means that **any strategy that treats vocabulary layers as interchangeable with transformer layers—like redistribution—can balance either compute or memory, but not both simultaneously** (Section 2, Figure 3).

The diagnostic power of this reframing is substantial. It explains *why* redistribution fails in specific, predictable ways: when $V$ is large, the last stage's parameter memory is dominated by the output layer ($2hV$), and moving transformer layers (which each add $24h^2$ to parameter memory) cannot compensate unless the number of transformer layers per stage is very large—which is precisely the regime where redistribution is least needed. It explains *why* the problem grows more severe with vocabulary scaling (Tao et al., 2024) independent of model size: $V$ appears linearly in the output layer's costs but not in any transformer layer term. And it explains *why* the input layer, despite its minimal compute ($3bsh$ FLOPs), is still a memory problem: its parameter memory ($2hV$) equals the output layer's, making the first stage a memory outlier even when compute is balanced.

This is a **fundamental conceptual advance**, not an incremental refinement. It shifts the vocabulary imbalance from an implementation annoyance to a first-class systems problem with its own scaling laws, its own failure modes, and its own solution requirements. The paper's Figure 2—showing how vocabulary size multiplies the relative cost of vocabulary layers—is a diagnostic tool that should become standard in PP capacity planning, analogous to how the Chinchilla scaling laws (Hoffmann et al., 2022) shifted pretraining planning from model size to the joint model-data optimization.

The evidence for this reframing's validity is the systematic failure of the layer-redistribution baseline across the paper's experiments (Figures 11, 12, 13, 14): as vocabulary size grows from 32k to 256k, redistribution's throughput drops by 8–33% while Vocabulary Parallelism maintains nearly constant MFU, and redistribution's peak memory remains highly imbalanced (up to 45GB difference across devices in the V-Half experiments, Section 6.4) while Vocabulary Parallelism achieves near-perfect balance. The redistribution baseline is not just "slightly worse"—it is **qualitatively different in its scaling behavior**, confirming that the vocabulary imbalance is a distinct phenomenon that redistribution's layer-counting heuristic cannot address.

---

### Innovation 2: Communication Barriers as the Knob That Controls Activation Memory in Partitioned Softmax

The second conceptual contribution is the insight that **the number of communication barriers in a partitioned softmax directly controls the activation memory overhead** when integrating vocabulary layers into pipeline schedules, and that this number can be systematically reduced through algebraic reordering of the softmax computation.

Prior to this work, the standard approach to partitioning a large linear layer across devices was tensor parallelism (Shoeybi et al., 2019): split the weight matrix, compute partial outputs, and all-reduce to obtain the full result. This treats the communication as an implementation detail—something to be optimized (through fast interconnects, overlapping, or quantization) but not something that can be reduced in *number*. The interlaced pipeline (Lin et al., 2024) applies exactly this TP-style approach to vocabulary layers, and the paper's analysis (Appendix B.1, Figure 15) shows the consequence: the synchronous all-reduce for the full logits tensor widens the pipeline's building-block lifespan from $3p$ to $4.5p$ intervals, producing a 1.5× increase in peak activation memory—a catastrophic overhead for already-memory-constrained schedules.

The paper's key move is to recognize that **softmax is not an arbitrary nonlinearity**—it has algebraic structure that permits the global statistics (max and sum) to be computed *after* a local softmax, not before. The online-softmax identity (Equation 5) is the mechanism, but the conceptual insight is deeper: by reordering the computation so that the **communication covers only lightweight elementwise operations** (on $O(bs)$ tensors) rather than heavy matrix multiplications (on $O(bs \times V/p)$ tensors), the communication barriers can be combined and reduced in number without sacrificing correctness. Algorithm 1 reduces three barriers to two; Algorithm 2 reduces two barriers to one—each reduction directly translates to one fewer interval of lifespan widening and hence one fewer microbatch of peak activation memory (Figure 9, Section 5.2).

This connection between barrier count, lifespan, and activation memory is not merely a performance observation—it is a **theoretical framework for reasoning about the memory cost of partitioned operations in pipeline schedules**. The paper articulates this through the building-block analysis from Qi et al. (2024): peak activation memory is proportional to lifespan divided by interval, each communication barrier adds one interval to the lifespan, and therefore the barrier count *is* the memory overhead. This gives a precise, quantitative language for comparing approaches: the naïve partitioning has 3 barriers → +3 intervals of memory; Algorithm 1 has 2 barriers → +2 intervals; Algorithm 2 has 1 barrier → +1 interval; the interlaced pipeline's synchronous TP effectively creates a barrier that blocks the entire building block → +1.5p intervals (a 1.5× multiplier, not a constant addition). This framework explains *why* the interlaced pipeline's memory overhead is qualitatively worse (multiplicative in $p$) than Vocabulary Parallelism's (additive constant), and *why* Algorithm 2's single-barrier design is optimal—one barrier is the irreducible minimum given that softmax requires global statistics.

This is a **fundamentally new design principle** for partitioned nonlinearities in pipeline-parallel training: the number of communication barriers, not the volume of communication per barrier, is the dominant factor in activation memory cost when the barriers sit on the critical path between forward and backward passes. This principle generalizes beyond softmax to any operation that requires global reductions—layer normalization across devices, contrastive losses with global statistics, or cross-device attention—and provides a concrete optimization target (reduce barriers to the minimum) with a measurable payoff (one microbatch of activation memory per eliminated barrier).

The experimental validation is in the memory comparisons (Figures 12, 14) and throughput scaling (Figure 11): Algorithm 2 consistently achieves slightly lower peak memory than Algorithm 1 (because of the one fewer barrier), and both dramatically outperform the interlaced pipeline, which goes out-of-memory on the 32-GPU, seq-len-4096 configuration. Table 3 quantifies the computation tradeoff: Algorithm 2 achieves 75–93% of linear scaling for the partitioned output layer (versus 80–93% for Algorithm 1), a 5–10% throughput cost for a 1-microbatch memory saving—a favorable tradeoff in memory-constrained regimes.

### Innovation 3: Vocabulary Parallelism as a Composable Pass, Not a Separate Schedule

The third conceptual contribution is methodological: the paper demonstrates that **vocabulary-layer computation can be modularized into pipeline "passes" that integrate with existing schedules through a generic building-block interface**, rather than requiring custom schedule designs or ad-hoc scheduling logic.

Prior approaches to handling vocabulary layers in PP fall into two camps. The first camp modifies the *model partitioning* (redistribution: move transformer layers) without changing the scheduling—the vocabulary layers remain monolithic blocks on the first and last stages, and the schedule treats them as part of those stages' forward/backward passes. The second camp modifies the *parallelism strategy* (interlaced pipeline: switch to TP for vocabulary layers) which forces a different communication pattern that must be scheduled around—essentially creating a hybrid schedule specific to vocabulary layers.

The paper's approach is different: it treats vocabulary computation as additional **pass types** (`S` and `T`) that obey the same scheduling abstraction as `F` (forward), `B` (backward), and `W` (weight gradient) passes. The only modification needed to a schedule is to insert a fixed number of extra intervals between the forward and backward of the last transformer layer, then slot `S` and `T` into the resulting space. The uniform repetition of the building block handles everything else—dependencies, device-to-device synchronization, warmup/cooldown phasing—without special cases.

This composability is a **conceptual shift** from "vocabulary layers are a special problem requiring a special schedule" to "vocabulary layers are just another pass type with specific dependencies." The paper demonstrates this generality by applying the exact same methodology to two fundamentally different schedules: 1F1B (asymmetric activation memory, single pipeline chunk per device) and V-Half (balanced activation memory, virtual pipeline chunks, V-shaped device placement). The building-block modifications are structurally identical in both cases (Figures 9 and 16)—insert 1–2 intervals, place `S` and `T`—despite the schedules' different internal logic. This is strong evidence that the approach generalizes to any schedule constructed from repeating building blocks, which covers virtually all modern PP schedules including the zero-bubble family.

The significance of this composability extends beyond the immediate results. It means Vocabulary Parallelism can be **adopted incrementally**: a training system already using 1F1B or V-Half can add vocabulary partitioning by modifying the building-block definition, without re-engineering the scheduler, the communication library, or the model definition (beyond the vocabulary layer implementation). It means future schedule innovations (e.g., new memory-balanced or bubble-reducing schedules) can incorporate Vocabulary Parallelism by following the same recipe, without the paper's authors needing to derive a custom integration for each one. And it means the vocabulary-layer implementation (Algorithms 1 and 2) and the schedule integration (building-block modification) are **decoupled concerns**—improvements to one do not require changes to the other.

This is an **architectural innovation** rather than a purely algorithmic one. It doesn't change *what* computation happens, but it changes *how* that computation is organized relative to the rest of the system. The payoff is engineering robustness: the method "just works" across model sizes (4B to 30B), vocabulary sizes (32k to 256k), pipeline depths (8 to 32 GPUs), and schedule types (1F1B and V-Half), without configuration-specific tuning beyond profiling pass runtimes for precise interval sizing. The consistent MFU across all these configurations (Figures 11 and 13—Vocabulary Parallelism lines are nearly flat while baselines slope downward) is the empirical signature of this composability: the system's behavior is predictable and uniform because the vocabulary passes are properly modularized.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper does not evaluate on a downstream task or benchmark; it measures training system performance directly. All experiments pretrain GPT-like models from scratch on a customized C4 dataset (hosted at https://huggingface.co/datasets/mtyeung/vocab_parallel_sample_dataset), which is downloaded automatically by the experiment scripts (Appendix G.3.4). The data exists solely to drive the training loop—no validation perplexity, downstream accuracy, or convergence metrics are reported in the main experiments (convergence correctness is verified separately in Appendix E).

- **Base model(s).** The experiments use GPT-like transformer architectures of varying sizes to test Vocabulary Parallelism across scales. Three model families are constructed for the 1F1B experiments (~4B, ~10B, ~21B parameters) and three for the V-Half experiments (~7B, ~16B, ~30B parameters), with detailed configurations in Tables 1 and 2 respectively. The models are not pretrained checkpoints but rather architecture specifications instantiated for training benchmarks. The specific hyperparameters (layers, attention heads, hidden size) are chosen to be representative of contemporary LLM scales while fitting within GPU memory constraints.

- **Metrics.** The paper uses two primary metrics: **Model FLOPs Utilization (MFU)** and **Peak Memory (GB)**. MFU is computed by dividing the theoretical peak FLOPs of the hardware by the actual FLOPs achieved during training, following the derivation of Narayanan et al. (2021) for counting model FLOPs. Peak Memory is the maximum allocated memory across all devices—not the average or the memory on a specific device—since training is gated by whichever device runs out of memory first. Both metrics are measured after several warm-up iterations to stabilize CUDA kernel launch overheads and memory allocator behavior.

- **Baselines.** Five approaches are compared on the 1F1B schedule (Section 6.2):

  - **Baseline** (naïve Megatron-LM): Equal transformer layers per pipeline stage, with the input layer on the first device and the output layer on the last device—the standard out-of-the-box partitioning that creates the maximal vocabulary imbalance.

  - **Redis** (layer redistribution): Transformer layers are redistributed across stages to balance compute as evenly as possible, following the FLOPs estimation method from Narayanan et al. (2021) that minimizes the workload of the longest stage. This is the approach used by DeepSpeed (Smith et al., 2022) and Skywork-MoE (Wei et al., 2024).

  - **Interlaced**: The synchronous interlaced pipeline from nnScaler (Lin et al., 2024), where vocabulary layers use tensor-parallel-style partitioning with blocking all-reduce communication. This is the most directly comparable prior method that also partitions vocabulary layers.

  - **Vocab-1**: Vocabulary Parallelism with forward-phase optimization only (Algorithm 1, 2 communication barriers).

  - **Vocab-2**: Vocabulary Parallelism with both forward and backward phase optimizations (Algorithm 2, 1 communication barrier).

  For the V-Half experiments (Section 6.4), only Baseline (naïve V-Half) and Vocab-1 are compared, since memory-balanced integration with V-Half is the primary demonstration target.

- **Generation budget / compute accounting.** The paper measures training system throughput in terms of MFU, not model accuracy on a task. The key fairness consideration is that all methods train the same model architecture with the same global batch size (128 microbatches of size 1) and the same sequence length, meaning they perform identical total FLOPs of useful computation per iteration. Differences in MFU arise entirely from how efficiently those FLOPs are executed—pipeline bubbles, communication overhead, and kernel inefficiency. The "compute budget" is therefore implicit: the paper compares wall-clock iteration time at fixed model scale, not accuracy-vs-compute tradeoffs.

- **Cross-validation / statistical protocol.** There is no cross-validation or statistical significance testing. The experiments are deterministic system benchmarks: given fixed hardware and software configuration, the same iteration time and peak memory are reproducible. The paper records running time after several warm-up iterations to avoid cold-start effects, but does not report multiple runs with variance. The primary threat to reproducibility is hardware heterogeneity (interconnect bandwidth, GPU model, CUDA version), not statistical noise. The artifact appendix (Appendix G) provides a Docker-based reproduction package that targets specific results from Table 5 on an 8-GPU A100 server.

### Main Quantitative Results

#### Comparison of Methods on 1F1B (Section 6.3)

The headline result for the 1F1B schedule is that Vocabulary Parallelism (both Vocab-1 and Vocab-2) achieves **nearly constant MFU as vocabulary size scales from 32k to 256k**, while the Baseline and Redis approaches suffer substantial throughput degradation, and the Interlaced approach fails on memory at large scales.

**Throughput (Figure 11).** Across all six hardware configurations (8/16/32 GPUs × sequence lengths 2048/4096), the Baseline's MFU drops monotonically and substantially as vocabulary size increases. For the 32-GPU, sequence-length-2048 configuration, Baseline MFU falls from 42.81% at 32k vocabulary to 20.86% at 256k—a 51% relative decline (Table 5). Redis partially mitigates this decline but cannot eliminate it: on the same configuration, Redis drops from 43.48% at 32k to 29.16% at 256k, a 33% relative decline. The paper attributes Redis's residual degradation to the fact that "the output layer alone already has a higher computation cost than that in the other pipeline devices" (Section 6.3)—redistribution can only adjust in discrete transformer-layer increments, and when the output layer's compute exceeds a single transformer layer's, no integer reallocation can perfectly balance.

In contrast, Vocab-1 and Vocab-2 maintain MFU within a narrow band across all vocabulary sizes. On the 32-GPU, sequence-length-2048 configuration, Vocab-1 ranges from 45.85% to 46.11% and Vocab-2 from 45.54% to 46.16% as vocabulary grows from 32k to 256k—a variation of less than 1.3%. The absolute throughput advantage over Baseline at 256k vocabulary is dramatic: Vocab-1 achieves 46.11% MFU versus Baseline's 20.86%, a **2.2× throughput improvement**, while over Redis (29.16%) the improvement is **58%**. The paper's abstract claim of "5% to 51% improvement in throughput" spans the range from small-vocabulary scenarios (where the imbalance is minimal and Vocabulary Parallelism's overhead is the dominant factor—the lower bound) to large-vocabulary scenarios (where Baseline's imbalance is severe—the upper bound).

The Interlaced pipeline achieves competitive MFU at smaller scales (within ~0.5 percentage points of Vocab methods on 8 GPUs) but underperforms on multi-node setups. For the 21B model on 32 GPUs with sequence length 2048, Interlaced achieves 42.40–43.25% MFU versus Vocab-1/2 at 45.54–46.16%—a gap of 6.7–8.2% that the paper attributes to the synchronous all-reduce overhead quantified in Appendix B.2 (~11% iteration time penalty). More critically, Interlaced **goes out-of-memory** on the 32-GPU, sequence-length-4096 configuration (Figure 11, bottom-right panel, dashed line ends; Table 5 shows "--"), while Vocab methods continue to operate. This is the 1.5× activation memory penalty documented in Appendix B.1 manifesting as a hard feasibility boundary.

**Peak Memory (Figure 12, Table 5).** The memory results tell a complementary story. Baseline and Redis have identical peak memory because redistribution moves transformer layers but does not change the fact that the first and last stages store the full vocabulary parameters. As vocabulary size increases, peak memory grows substantially: on 32 GPUs with sequence length 2048, Baseline/Redis peak memory rises from 33.45 GB (32k vocab) to 52.16 GB (128k vocab) to 73.05 GB (256k vocab, seq-len-4096, Table 5). The vocabulary parameters ($2hV$ each for input and output layers) are concentrated on two devices, and this concentration dominates peak memory at large $V$.

Vocabulary Parallelism distributes these parameters evenly, reducing peak memory substantially at large vocabulary sizes. On 32 GPUs with sequence length 4096 and 256k vocabulary, Vocab-1 achieves 58.58 GB peak memory versus Baseline's OOM (out-of-memory) at 73.05 GB—a **reduction of at least 20%** (the Baseline number is for 128k, not 256k, since 256k OOM's). At the 128k point where both are measurable, Vocab-1 uses 57.88 GB versus Baseline's 62.29 GB, a 7% reduction. The absolute memory savings grow with vocabulary size because the vocabulary parameters scale as $2hV$ and are fully concentrated on two devices in Baseline, while Vocabulary Parallelism distributes them by a factor of $p$ (32 in this case).

Vocab-2 consistently achieves slightly lower peak memory than Vocab-1 (e.g., 56.09 GB vs. 57.41 GB on 32 GPUs, seq-len-4096, 32k vocab; 33.84 GB vs. 34.51 GB on 32 GPUs, seq-len-2048, 256k vocab). This ~1 GB difference is the activation memory savings from reducing communication barriers from 2 to 1—specifically, one fewer microbatch of activations stored during the extended lifespan. The paper's activation memory analysis (Section 5.2) predicted exactly this: Algorithm 2's peak activation memory is $p+1$ microbatches versus Algorithm 1's $p+2$ (Figure 9), and with $p=32$, one microbatch of activations for these model sizes corresponds to roughly 1–2 GB.

Interlaced shows the highest peak memory across all configurations where it runs. On 16 GPUs with sequence length 4096, Interlaced uses 49.16–51.28 GB versus Vocab-1's 39.46–41.53 GB—a **24–30% overhead**. This is the 1.5× activation memory multiplier from the synchronous TP communication (Appendix B.1) added on top of the already-balanced parameter memory (since Interlaced, like Vocabulary Parallelism, distributes vocabulary parameters). The paper emphasizes that this activation memory penalty "may make the critical memory bottleneck even worse" (Section 2), and the OOM on 32 GPUs with sequence length 4096 confirms that this is not a theoretical concern—it renders the method infeasible at scale.

**Key takeaway from the 1F1B comparison.** Vocab-1 and Vocab-2 are the only methods that simultaneously maintain throughput and reduce peak memory at large vocabulary sizes. Redis maintains throughput partially but cannot reduce memory; Interlaced reduces memory but destroys throughput (and eventually becomes infeasible). Vocabulary Parallelism's combination of both properties—enabled by the communication-barrier optimizations—is what distinguishes it from prior approaches.

#### Vocabulary Parallelism with Memory-Balanced Schedules: V-Half Results (Section 6.4)

The paper's second major set of experiments demonstrates that Vocabulary Parallelism composes with activation-memory-balanced schedules to achieve fully balanced pipelines. The V-Half schedule (Qi et al., 2024) independently balances activation memory through V-shaped device placement, but inherits the vocabulary-layer parameter memory imbalance from whichever partitioning strategy is used. By applying Vocab-1 on top of V-Half, the paper aims for balance in **both** activation memory (from V-Half) and parameter memory / compute (from Vocabulary Parallelism).

**Throughput (Figure 13, Table 6).** The results mirror the 1F1B experiments but with larger relative gains because V-Half's baseline is weaker (it does not redistribute transformer layers at all). On 32 GPUs with sequence length 4096, Baseline V-Half drops from 56.06% MFU at 32k vocabulary to 37.85% at 128k vocabulary—a 32% decline—and goes **out-of-memory at 256k** (the Baseline line in Figure 13 ends). Vocab-1 V-Half maintains 59.82–60.72% MFU across all vocabulary sizes, including 256k where Baseline cannot run. The improvement at 128k vocabulary is 60.72% versus 37.85%, a **60% relative throughput gain**. The paper also reports a 143% improvement on the 16-GPU, sequence-length-2048 configuration at 256k vocabulary (52.89% for Vocab-1 vs. 19.99% for Baseline, Table 6), which represents the extreme end where Baseline's imbalance is worst relative to Vocab-1's overhead.

The MFU of Vocab-1 V-Half is consistently higher than Vocab-1 on 1F1B at comparable model scales (e.g., ~52–60% vs. ~45–51% on similar configurations). This is expected: V-Half inherently reduces pipeline bubbles compared to 1F1B, and Vocabulary Parallelism rides on top of that efficiency without interfering. The paper does not provide a detailed bubble analysis for the combined schedule, but the throughput numbers are consistent with V-Half's claimed advantages being preserved.

**Peak Memory (Figure 14, Table 6).** This is the paper's most visually striking result. The shaded regions in Figure 14 represent the **range** of peak memory across all pipeline devices—minimum to maximum. For Baseline V-Half, the range is enormous: on 32 GPUs with sequence length 2048 and 128k vocabulary, the minimum device uses ~34 GB while the maximum uses ~53 GB, a **19 GB spread** (Table 6: baseline peak memory 53.22 GB vs. the lower bound visible in Figure 14's shaded region). On 24 GPUs with sequence length 4096 and 256k vocabulary, the spread reaches approximately **45 GB** (Figure 14 caption: "up to 45GB difference"). This imbalance is almost entirely driven by vocabulary parameters concentrated on the first and last stages—the activation memory is balanced by V-Half, so the remaining spread is parameter memory.

Vocab-1 V-Half collapses this range to near-zero. On 32 GPUs with sequence length 2048 and 256k vocabulary, Vocab-1's peak memory is 32.18 GB with a device-to-device variation of <1.5 GB (the shaded region is barely visible in Figure 14). On 24 GPUs with sequence length 4096 and 256k vocabulary, Vocab-1 uses 34.12 GB with a similarly tight spread. The paper notes that "the first pipeline device still holds slightly more parameters due to positional and token type embedding, the extra memory required is a small constant. In our experiments, this is less than 2.5GB" (Section 6.4). This residual imbalance is architectural and independent of vocabulary size—positional and token type embeddings have fixed dimensions regardless of $V$.

The combination of balanced throughput and balanced memory achieves what the paper claims as "perfect balance in both memory and computation" (Abstract, Section 6.4). Specifically:

- **Computation balance**: Vocab-1 V-Half's MFU is independent of vocabulary size (flat lines in Figure 13), meaning no stage is a compute bottleneck as $V$ grows.
- **Parameter memory balance**: The peak memory spread collapses from ~45 GB (Baseline) to <2.5 GB (Vocab-1), meaning no stage is a memory outlier due to vocabulary parameters.
- **Activation memory balance**: Inherited from V-Half's V-shaped scheduling, which the paper does not independently verify but relies on Qi et al. (2024)'s claims.

#### Scaling Analysis of Vocabulary Layers (Section 6.5)

To understand the inherent overhead of partitioning vocabulary layers, the paper measures the **scaling factor**—the ratio of actual per-device throughput to the ideal linear scaling ($p \times$ the original unpartitioned throughput). Table 3 reports these factors for the output layer (Vocab-1 and Vocab-2 separately) and the input layer, broken out by pipeline depth and sequence length.

**Output layer.** For Vocab-1 (Algorithm 1), the scaling factor is 91.29%, 84.22%, and 80.59% on 8, 16, and 32 GPUs respectively at sequence length 2048. It improves at sequence length 4096: 93.21%, 88.02%, 85.24%. Vocab-2 (Algorithm 2) is consistently lower: 86.72%, 79.84%, 75.93% at sequence length 2048 and 88.36%, 83.42%, 79.66% at sequence length 4096.

Two trends are evident. **First**, scaling efficiency degrades as pipeline depth increases. The paper attributes this to two factors: (a) "partitioning the vocabulary layers will reduce the model FLOPs utilization (MFU) of GPU kernels as the operations are smaller and hence less parallelized"—when $V$ is divided by a larger $p$, each device's matrix multiplication operates on dimensions $[bs, V/p]$, which becomes less GPU-efficient as $V/p$ shrinks; and (b) the communication overhead, though overlapped, still consumes some GPU resources and becomes proportionally larger relative to the shrunken local computation. **Second**, Vocab-2's additional precomputation ($A = \text{softmax}'(Y)W$ and $B = GW$ in the local block) imposes a 5–10% throughput penalty relative to Vocab-1, consistent across scales. This is the price of the single-barrier design—extra FLOPs in exchange for one fewer activation memory microbatch.

**Input layer.** The input layer scaling is substantially worse than the output layer: 39.99%, 28.85%, 15.18% on 8, 16, 32 GPUs at sequence length 2048, and 27.69%, 15.52%, 8.35% at sequence length 4096. The paper explains this as a fundamental limitation: "partitioning the vocabulary layers... brings extra computation, especially for the input layer where all devices have to construct the output tensor, whose size is independent of the size of the vocabulary partition" (Section 6.5). In other words, after the input embedding lookup on each device (which produces a $bs \times h$ tensor from the device's $V/p$ slice of the embedding table), an all-gather or equivalent operation must reconstruct the full embedded output for the transformer layers to consume. This reconstruction cost—dominated by the output tensor size $bsh$, which does not shrink with $p$—amortizes poorly. The paper notes, however, that "both input and output still only take a small portion of the computation of the entire model after being partitioned" (Section 6.5), so the poor input-layer scaling does not dominate end-to-end throughput.

#### Convergence Correctness (Appendix E)

While not the primary evaluation, the paper verifies that Vocabulary Parallelism produces **numerically correct training** by comparing loss curves against the original Megatron-LM implementation. Two configurations are tested: pure pipeline parallelism (PP=8) and hybrid tensor + pipeline parallelism (TP=2, PP=4), both with 256k vocabulary on the ~4B model. Figure 17 shows the loss curves tracking each other closely through 1000 training steps, with "some small numerical differences" (Appendix E)—expected due to different ordering of floating-point operations in the partitioned softmax versus the unpartitioned version. The paper does not quantify the numerical difference (e.g., maximum absolute loss deviation), but the qualitative convergence matching establishes the implementation's correctness as a training system.

This is an important validation because the online-softmax reordering in Algorithms 1 and 2 changes the order of floating-point operations (summations over different subsets of the vocabulary happen in different orders), which can theoretically affect training dynamics if the numerical differences compound. The convergence curves demonstrate that in practice, the differences are negligible for training purposes.

### Ablation Studies and Robustness Checks

The paper is a systems optimization paper, so its "ablation studies" take the form of comparing algorithm variants (Vocab-1 vs. Vocab-2), testing across a wide range of configurations, and isolating the impact of specific implementation choices.

- **Algorithm 1 versus Algorithm 2 (communication barrier count):** Across all 1F1B configurations (Table 5), Vocab-2 achieves slightly lower peak memory than Vocab-1 (by approximately 1–2 GB depending on model scale) at the cost of slightly lower throughput (by 0.3–0.8 percentage points MFU). For example, on 8 GPUs with sequence length 4096 and 256k vocabulary, Vocab-2 achieves 50.40% MFU and 25.73 GB peak memory versus Vocab-1's 50.66% MFU and 27.34 GB—a 0.26 percentage point throughput penalty for a 1.61 GB memory saving. The throughput-memory tradeoff is quantified consistently across all configurations, with the memory saving growing more significant at larger pipeline depths (where one extra microbatch of activations is larger). The paper does not declare one algorithm preferable; the experiments establish that both are viable depending on whether memory or throughput is the binding constraint.

- **Vocabulary size scaling:** The paper sweeps four vocabulary sizes (32k, 64k, 128k, 256k) across all configurations. The consistent finding is that Baseline and Redis MFU drop as $V$ increases (Figure 11: downward-sloping lines), while Vocab-1 and Vocab-2 MFU are essentially flat (horizontal lines). This is not a surface-level property—it directly validates the central claim that Vocabulary Parallelism eliminates vocabulary-size-dependent imbalance. The flatness is quantitatively tight: on 16 GPUs with sequence length 2048, Vocab-1 ranges from 49.02% to 50.66% MFU across the four vocabulary sizes, a maximum deviation of 1.64 percentage points (3.3% relative). Baseline ranges from 45.66% to 24.21%, a 47% relative decline.

- **Pipeline depth scaling (8, 16, 32 GPUs):** The experiments span 8 to 32 GPUs on 1F1B and 16 to 32 GPUs on V-Half. Vocabulary Parallelism's throughput advantage over Baseline grows with pipeline depth on 1F1B: at 8 GPUs with sequence length 2048 and 256k vocabulary, Vocab-1 achieves 50.12% vs. Baseline's 25.23% (1.99×); at 32 GPUs, it's 46.11% vs. 20.86% (2.21×). This is consistent with the expected behavior: deeper pipelines have fewer transformer layers per stage (e.g., 64 layers ÷ 32 stages = 2 layers per stage), making the vocabulary layer's relative contribution larger and the imbalance proportionally more severe.

- **Sequence length scaling (2048 vs. 4096):** At longer sequence lengths, transformer layer compute grows (the $bsh(72h + 12s)$ term in Table 4), while vocabulary layer compute remains dominated by $6bshV$ (which also grows with $s$, but proportionally). Overall MFU tends to be higher at sequence length 4096 because larger matrix multiplications achieve better GPU utilization. Vocabulary Parallelism's advantage is slightly smaller at longer sequences because the vocabulary layers' relative contribution to total compute shrinks (transformer layers benefit more from increased $s$ due to the $O(s^2)$ attention term). For example, on 32 GPUs with 256k vocabulary, the Vocab-1-to-Baseline MFU ratio is 2.21× at sequence length 2048 and 2.16× at sequence length 4096.

- **V-Half combined with Vocabulary Parallelism:** The V-Half experiments (Figures 13, 14) serve as an ablation of combinability with memory-balanced schedules. The key result is that Vocabulary Parallelism does not interfere with V-Half's activation memory balancing: the combined approach achieves both balanced memory (Figure 14's tight spread) and balanced compute (Figure 13's flat lines). The paper does not run Vocab-2 on V-Half, which would have shown whether the additional memory savings carry over—a minor omission.

- **Vocabulary padding for memory alignment (Section 6.1):** The paper reports that padding the vocabulary size from 256008 to 256032 (a multiple of 48, where $2p = 2 \times 24 = 48$) yields "an approximate 8% increase in performance" on 24 GPUs. This is a substantial effect from a minor implementation detail, highlighting the sensitivity of GPU kernel efficiency to dimensional alignment. The paper does not conduct a systematic sweep of padding amounts or target alignment multiples, so the 8% figure is a point observation rather than a comprehensive study.

- **Untied versus tied embedding weights (Section 6.1):** The paper uses the **harder** setting of untied weights (Llama 3-style) throughout all experiments, making throughput and memory numbers conservative relative to tied-weight models. Tying input and output embedding weights would reduce total vocabulary parameters by a factor of 2 (from $4hV$ to $2hV$) and eliminate the need for separate gradient synchronizations, improving both memory and throughput. The paper does not run a tied-weight ablation to quantify the benefit.

- **Interlaced pipeline communication overhead ablation (Appendix B.2):** The paper directly measures the cost of synchronous all-reduce in the interlaced pipeline by removing those communications and measuring the speedup. On a 21.5B model with 32 GPUs, removing the synchronous all-reduces improved end-to-end iteration time by **10.95%**. This cleanly isolates the TP-style communication as the dominant inefficiency in the interlaced pipeline and validates the paper's motivation for developing a communication-overlapped alternative (Vocabulary Parallelism). The ablation is performed on one configuration, but the consistency of the interlaced pipeline's underperformance across all multi-node experiments corroborates the finding.

- **Numerical correctness with tensor parallelism (Appendix E):** In addition to pure PP, the paper verifies that Vocabulary Parallelism works correctly in a hybrid TP+PP setting (TP=2, PP=4). The convergence curves in Figure 17 (right) show the loss tracking the original Megatron-LM implementation, confirming that vocabulary partitioning does not interact incorrectly with tensor-parallel transformer layers. This is notable because both TP and Vocabulary Parallelism partition weight matrices—TP partitions attention heads and hidden dimensions, Vocabulary Parallelism partitions the vocabulary dimension—and they operate on the same tensors at the boundary between the last transformer layer and the output layer. The convergence match suggests that the numerical interactions (different partitioning schemes, different communication patterns) do not compound to affect training.

### Critical Assessment

The paper's central claims are: (1) vocabulary layers cause severe compute and memory imbalance in pipeline parallelism that grows with vocabulary size; (2) Vocabulary Parallelism eliminates this imbalance by partitioning vocabulary layers across all devices; (3) the communication-barrier optimizations (Algorithms 1 and 2) bound activation memory overhead to a small constant; (4) Vocabulary Parallelism composes with existing schedules (1F1B, V-Half) to achieve balanced pipelines; and (5) the result is 5–51% throughput improvement and substantially reduced peak memory. The experiments provide strong support for these claims, but with boundary conditions that deserve explicit scrutiny.

**Claim (1)—vocabulary layers cause imbalance that grows with vocabulary size**—is the most thoroughly validated claim. Figure 11 shows Baseline MFU dropping from 42.81% to 20.86% on 32 GPUs as vocabulary grows from 32k to 256k—a clean demonstration that the imbalance is vocabulary-size-dependent, not a fixed overhead. Figure 12 shows peak memory growing from 33.45 GB to 52.16 GB (on 32 GPUs, sequence length 2048) over the same range, with the 256k point going OOM at sequence length 4096. Table 4 provides the FLOPs analysis that explains *why*. The evidence is consistent across all six 1F1B configurations and all four V-Half configurations, leaving no doubt that vocabulary imbalance is a scaling problem, not a model-specific quirk.

**Claim (2)—Vocabulary Parallelism eliminates the imbalance**—is supported by the flat MFU curves in Figures 11 and 13 and the collapsed memory ranges in Figures 12 and 14. However, the evidence is entirely within the context of the tested model architectures (GPT-like, dense, untied embeddings) and vocabulary sizes (32k–256k). The paper does not test on:

- **Extremely large vocabularies** (e.g., 512k or 1M tokens, which some multimodal models or multilingual models use). At these scales, the per-device vocabulary slice $V/p$ would still be large enough to maintain GPU kernel efficiency (a positive), but the communication volume for the all-reduce would grow (since the max and sum tensors are $O(bs)$, independent of $V$—so this is actually a non-issue for Vocabulary Parallelism's communication design, which communicates only $O(bs)$ scalars regardless of $V$). The point is not that larger vocabularies would break the method, but that the paper hasn't demonstrated this.

- **MoE (mixture-of-experts) models**, where the vocabulary imbalance might interact with expert-routing imbalances in non-obvious ways. The paper mentions Skywork-MoE (Wei et al., 2024) as a model that used layer redistribution for vocabulary imbalance, suggesting the problem exists in MoE settings too, but doesn't test Vocabulary Parallelism in that context.

- **Encoder-decoder architectures** (T5-style), where there are two vocabulary layers (encoder input, decoder input, decoder output) with potentially different imbalance patterns.

**Claim (3)—activation memory overhead bounded to a small constant**—is validated indirectly through the peak memory measurements. The difference in peak memory between Vocab-1 and Vocab-2 (1–2 GB, consistent with $p+2$ vs. $p+1$ microbatches) matches the building-block analysis. The Interlaced pipeline's 1.5× activation memory overhead (Appendix B.1, Figure 15) and its OOM behavior at scale provide a contrasting data point that validates the "small constant" characterization. However, the paper does not report **standalone activation memory measurements**—the peak memory numbers include parameter memory, optimizer states, and activations combined, so the contribution of the extra 1–2 microbatches is inferred rather than directly measured. A clean ablation comparing activation memory specifically (perhaps by disabling activation recomputation or measuring memory before/after scheduling vocabulary passes) would have made this point more directly.

Additionally, the "small constant" claim holds in **absolute terms** (1–2 microbatches) but is **relatively larger at small pipeline depths**. On 8 GPUs, the 1F1B building block normally stores $p=8$ microbatches of activations; adding 2 brings it to 10, a 25% increase. On 32 GPUs, the increase is from 32 to 34, a 6.25% increase. The paper emphasizes the diminishing relative overhead at scale, but the absolute overhead is constant—it doesn't become "negligible" in all senses, just proportionally smaller. For deployments where pipeline depth is small (e.g., 4–8 GPUs), the activation memory overhead is a more significant fraction, and Vocab-2's single-barrier design (only 1 extra microbatch) becomes more attractive.

**Claim (4)—composability with existing schedules**—is demonstrated for two schedules (1F1B and V-Half). The building-block integration methodology is described generically enough that it should apply to any schedule constructed from repeating blocks, but the paper does not demonstrate integration with:

- **Zero-bubble schedules** (Qi et al., 2023), which split the backward pass into activation gradient and weight gradient passes. Vocab-1's `S` and `T` passes would need to be positioned relative to these sub-passes, and it's not obvious from the paper whether the single-barrier design of Algorithm 2 would interact cleanly with a schedule that already has finely-grained backward splitting.

- **Interleaved 1F1B** (Narayanan et al., 2021), where each device hosts multiple pipeline stages (virtual pipeline parallelism). The paper mentions that the V-Half experiments use "virtual pipeline chunks" (Table 2 caption), implying interleaving, but doesn't detail how Vocabulary Parallelism interacts with virtual stage scheduling.

The claim of general composability is plausible but stronger than what the experiments directly demonstrate.

**Claim (5)—5% to 51% throughput improvement**—requires careful interpretation. The 5% lower bound corresponds to small-vocabulary, large-pipeline-depth configurations where the imbalance is naturally small and Vocabulary Parallelism's overhead (partitioned kernel inefficiency, extra communication) partially offsets the benefit. The 51% upper bound is the extreme case (32 GPUs, 256k vocabulary, short sequence length) where Baseline's imbalance is worst. This is a fair characterization, but the reader should understand that the 51% figure is the **maximum observed improvement**, not the typical improvement across realistic deployments. In more moderate configurations (e.g., 64k vocabulary, 16 GPUs, sequence length 4096), the improvement is in the 20–25% range (Table 5: 50.97% vs. 41.21%, a 23.7% improvement). The abstract's "5% to 51%" range is technically accurate but spans from a near-wash to a dramatic gain, and the specific improvement in any given deployment depends on the ratio of vocabulary layer cost to transformer layer cost.

**Missing experiments and analyses that would strengthen the paper:**

- **Comparison with Megatron-LM's sequence parallelism.** For very long sequences, Megatron-LM's sequence parallelism (Korthikanti et al., 2023) distributes the sequence dimension across devices, which changes the $s$ factor in the FLOPs analysis (Table 4: output layer compute is $6bshV$, where $s$ is per-device sequence length under sequence parallelism). This could mitigate the output layer imbalance differently than Vocabulary Parallelism, and the paper does not discuss the interaction.

- **Detailed bubble analysis for the combined V-Half + Vocabulary Parallelism schedule.** The paper reports end-to-end MFU but doesn't break down where time is spent (bubbles vs. communication vs. kernel execution) for the combined schedule, making it difficult to assess whether any residual imbalance remains or whether the perfect balance claimed is realized in practice.

- **Ablation on tied vs. untied embeddings.** This would quantify the upper bound of what Vocabulary Parallelism could achieve if the model architecture permitted weight tying, which is common in earlier models (GPT-2, OPT) and reduces vocabulary parameter memory by 50%. The paper's choice of untied weights as "the harder setting" is conservative, but an explicit comparison would help practitioners estimate benefits for tied-weight models.

- **Memory breakdown by type (parameters, gradients, optimizer states, activations).** The paper reports total peak memory and attributes the reduction to parameter memory balancing, but a detailed breakdown would make the causal chain explicit and help capacity planners estimate memory savings for their specific configurations.

- **Experiments with activation recomputation enabled.** Many production training runs use activation recomputation (checkpointing) to trade compute for memory. This changes the activation memory profile and could alter the relative importance of the 1–2 extra microbatch overhead. The paper doesn't mention whether recomputation is used, and if not, how the overhead would change under recomputation regimes.

- **Scaling to larger GPU counts.** The experiments cap at 32 GPUs. At larger scale (e.g., 128 or 256 GPUs), the per-device vocabulary slice $V/p$ shrinks further, and the constant activation memory overhead becomes proportionally even smaller. The paper's trends suggest Vocabulary Parallelism would scale well, but the absence of larger-scale data leaves this as an extrapolation.

- **End-to-end training throughput over full training runs, not just iteration time.** The paper measures per-iteration throughput after warmup. For long-running training jobs, factors like communication contention, memory fragmentation, and garbage collection can affect sustained throughput. The convergence verification (Appendix E) runs 1000 steps, but throughput is not reported for that duration.

**Conditional limits of the claims:**

The paper's approach works when: (1) the vocabulary layers can be partitioned column-wise (true for standard embedding and output projection layers, but not for more complex output heads like sequence-to-sequence models with separate decoder embeddings); (2) the pipeline schedule has enough slack in its lifespan to absorb the extra intervals without creating new bubbles (1F1B and V-Half have this slack; the paper doesn't analyze for schedules where the lifespan is already fully packed); (3) the GPU hardware supports effective communication-computation overlap through separate CUDA streams (true for modern NVIDIA GPUs with sufficient streaming multiprocessor capacity; the paper's A100 setup meets this).

The approach does **not** help when: (1) the vocabulary size is very small (e.g., character-level tokenization with $V < 1000$), where the imbalance is negligible and Vocabulary Parallelism's overhead would dominate; (2) the model uses a non-standard output head that cannot be partitioned along the vocabulary dimension; (3) the pipeline depth is very shallow (e.g., 2 GPUs), where the per-device vocabulary slice $V/p$ is still large and the activation memory overhead (1 microbatch out of $p=2$) is proportionally significant.

Overall, the experimental design is **strong for a systems paper**—it tests across a wide range of model scales, vocabulary sizes, sequence lengths, pipeline depths, and two qualitatively different schedules. The measurements are reproducible (with the artifact appendix providing Docker-based reproduction), the comparisons against Redis and Interlaced are fair and well-motivated, and the ablation of synchronous communication overhead in Appendix B.2 provides a clean causal test of why the Interlaced pipeline underperforms. The primary limitation is the absence of larger-scale experiments (beyond 32 GPUs) and the reliance on end-to-end aggregate metrics (MFU, peak memory) without deeper profiling breakdowns (bubble time, communication time, kernel efficiency per pass type). For a paper whose contribution is demonstrating balanced pipelines with bounded overhead, the evidence is sufficient to establish the method's viability and advantages over existing approaches, while leaving open the question of how the benefits scale to massive training runs on hundreds of GPUs.


## 6. Limitations and Trade-offs

### Difficulty Estimation Cost Is Unaccounted for in the Headline Efficiency Numbers

The most significant practical limitation of this work is that the cost of integrating vocabulary passes into pipeline schedules is measured only in terms of the building-block framework's activation memory overhead (1–2 extra microbatches), without accounting for the profiling step that the paper itself describes as necessary for good performance.

Section 6.1 states:

> "Scheduling under the assumption that backward takes twice time as forward might introduce unnecessary bubbles, especially when these values differ significantly. As a result, we profile the run time of the passes and schedule the S and T passes accordingly."

While the paper downplays this as "optional" since "the difference is negligible in most transformer networks," the profiling step imposes a deployment cost that matters in two ways. First, **any change to model architecture, vocabulary size, sequence length, or GPU hardware requires re-profiling** to determine the correct pass durations and interval spacing for the building-block schedule. The paper does not quantify how long this profiling takes, whether it needs to be repeated if training hyperparameters change, or how sensitive schedule quality is to profiling accuracy. Second, the profiling cost is **not amortized** into the throughput or memory numbers in Figures 11–14—those numbers represent steady-state iteration time after the schedule has been generated, not the full end-to-end cost including schedule construction.

This matters for practitioners who cannot assume the 2:1 backward-to-forward ratio holds. While the paper's experiments find the ratio is consistent enough that profiling doesn't change the schedule, this is an empirical property of the specific transformer architectures tested (GPT-like, standard attention, 2048/4096 sequence lengths). Architectures with different forward-backward ratios—sparse attention, long-context variants with distinct attention implementations, or models using activation recomputation selectively on certain layers—could require profiling that is not optional, adding an unmeasured overhead to the deployment workflow.

The paper partially addresses this by noting that profiling is "viewed as optional" and that the schedule generation is a one-time cost, but the absence of any quantification makes it difficult to assess whether this is genuinely negligible or a hidden tax. No mitigation beyond the "optional" characterization is proposed.

---

### Input Layer Scaling Efficiency Degrades Severely at Pipeline Depth

Vocabulary Parallelism partitions *both* the input embedding layer and the output projection layer across all pipeline devices, but the paper's own scaling analysis (Section 6.5, Table 3) reveals a stark asymmetry: the output layer retains reasonable scaling efficiency while the input layer's efficiency collapses as pipeline depth increases.

Specifically, at sequence length 2048, the input layer achieves only **39.99%**, **28.85%**, and **15.18%** of linear scaling on 8, 16, and 32 GPUs respectively. At sequence length 4096—where larger matrix multiplications should improve GPU utilization—the numbers are even worse: **27.69%**, **15.52%**, **8.35%**. On 32 GPUs with sequence length 4096, the input layer runs at less than one-tenth of its theoretical partitioned speed.

The paper's explanation (Section 6.5) identifies the root cause: "all devices have to construct the output tensor, whose size is independent of the size of the vocabulary partition." In practical terms, after each device performs its local embedding lookup (which produces a $bs \times h$ tensor from its $V/p$-sized vocabulary slice), the system must gather these partial embeddings into the full embedded output that the first transformer layer expects. This gathering—whether implemented as an all-gather, an all-reduce, or a broadcast—operates on a tensor whose size is $bsh$, which is **independent of $p$**. As $p$ grows, the local embedding lookup becomes cheaper (fewer vocabulary entries per device), but the gathering communication remains fixed—and eventually dominates the cost.

The paper argues that this is acceptable because "both input and output still only take a small portion of the computation of the entire model after being partitioned." This is true in an absolute sense—the input layer's forward pass costs only $3bsh$ FLOPs, which is dwarfed by transformer layers—but it has implications for scaling behavior. As pipeline depth increases, the input layer's inefficiency grows without bound (scaling factor $\to 0$ as $p \to \infty$), while the output layer stabilizes around 75–85%. For very deep pipelines (e.g., 64 or 128 GPUs), the input layer could become a **latency bottleneck** even if its total FLOPs are small, because its communication phase cannot be overlapped with other work as effectively as the output layer's.

The paper does not propose a mitigation for this. The input layer scheduling (Appendix C) piggybacks the forward and backward onto warmup and cooldown phases to bound memory, but does not improve the computation scaling itself. This is a genuine tradeoff: Vocabulary Parallelism balances parameter memory perfectly (the input embedding table is evenly distributed), but pays for it with poor input-layer compute scaling that worsens with pipeline depth.

---

### Single Hardware Platform and Interconnect Evaluation

All experiments in the paper are conducted on a single hardware configuration: up to 32 NVIDIA A100 SXM 80GB GPUs distributed across 4 nodes, interconnected by a RoCE RDMA network (Section 6.2). While this is a realistic and well-specified setup, the paper's core optimization—overlapping all-reduce communication with transformer computation via separate CUDA streams—depends on hardware capabilities that are not universal.

The communication-computation overlap that makes Vocabulary Parallelism's throughput competitive with (and often superior to) the Interlaced pipeline relies on two properties: (1) the GPU must have sufficient streaming multiprocessor capacity and memory bandwidth to execute communication kernels concurrently with computation kernels without significant contention; and (2) the interconnect must provide enough bandwidth that the all-reduce of $O(bs)$ scalars (the global max and sum tensors) completes within the duration of the transformer layer computation it overlaps with. On A100 GPUs with RoCE RDMA, the paper demonstrates that this overlap is effective—the Vocabulary Parallelism methods match or exceed the Interlaced pipeline's throughput across all tested configurations (Figure 11).

However, the paper does not evaluate on:

- **Older GPU architectures** (V100, T4) where concurrent stream execution may be less efficient or where the ratio of computation speed to communication bandwidth is different—potentially making the overlapped all-reduce more of a bottleneck.
- **Slower interconnects** (e.g., 10GbE without RDMA, or cloud environments with variable network performance). The Interlaced pipeline's synchronous all-reduce is already shown to cost ~11% of iteration time (Appendix B.2); if the overlapped all-reduce in Vocabulary Parallelism cannot be fully hidden behind computation on slower networks, its advantage over the Interlaced approach could shrink.
- **Higher GPU counts** (128+ GPUs) where the all-reduce latency grows with the number of participants and the communication pattern becomes more complex (hierarchical all-reduce across nodes). The paper's scaling analysis (Table 3) shows output-layer efficiency dropping from ~91% to ~80% as pipeline depth goes from 8 to 32 GPUs, suggesting communication is already a contributing factor at 32 GPUs. Whether this trend continues or plateaus at larger scale is unknown.

The paper does not acknowledge this as a limitation—the experiments are presented as representative without caveats about hardware sensitivity. A practitioner deploying on non-A100 hardware, in cloud environments with provisioned rather than dedicated interconnects, or at larger scale should treat the reported throughput numbers as **best-case estimates** for the tested hardware rather than guarantees of performance portability. No mitigation or future work addressing hardware generality is proposed.

---

### The Constant Activation Memory Overhead Is Proportionally Larger at Small Pipeline Depths

The paper characterizes the activation memory overhead of Vocabulary Parallelism as "a small constant overhead" (Abstract, Section 5.2)—specifically, 2 extra microbatches for Algorithm 1 and 1 extra microbatch for Algorithm 2, regardless of pipeline depth $p$. This framing emphasizes that the overhead becomes proportionally negligible at large $p$ (e.g., $34/32 \approx 1.06\times$ at 32 GPUs). However, the flip side is that **at small pipeline depths, the overhead is proportionally significant**, and these are precisely the settings where memory is most constrained per device.

On 8 GPUs with the 1F1B schedule, the standard building block stores $p = 8$ microbatches of activations. Algorithm 1 (Vocab-1) adds 2 intervals, bringing the total to 10—a **25% increase in peak activation memory** from the vocabulary passes alone. Algorithm 2 reduces this to 9 microbatches, a 12.5% increase. These are not "small constant" overheads in relative terms; they represent a meaningful fraction of the total activation memory budget. And 8 GPUs is a common setup—many research labs and smaller teams train moderate-scale models on single nodes with 8 GPUs, where pipeline parallelism is a natural choice but memory pressure is high because there is no data-parallel dimension to offload optimizer states.

The paper's experiments do show that Vocabulary Parallelism still achieves lower **total** peak memory than Baseline even at 8 GPUs (Figure 12, Table 5), because the parameter memory savings from distributing vocabulary layers outweigh the activation memory increase. But this tradeoff is configuration-dependent: if the vocabulary size is moderate (32k–64k) and the model's hidden dimension is large (making transformer-layer activations dominate memory), the activation memory overhead could exceed the parameter memory savings. The paper does not provide a breakdown that would let practitioners predict when this crossover occurs.

Additionally, the paper evaluates only on configurations with a microbatch size of 1. With larger microbatches (common in practice to improve GPU utilization), the activation memory per microbatch grows, making the 1–2 extra microbatches more costly in absolute GB. The paper's building-block analysis (Section 5.2) is expressed in microbatch-count units, which is independent of per-microbatch size, but the practical memory impact scales linearly with per-microbatch activation size.

The paper does not address this limitation explicitly—the "small constant" framing emphasizes the favorable scaling at large $p$ without discussing the less favorable regime at small $p$. No mitigation is proposed beyond the availability of Algorithm 2 (which halves the overhead from 2 to 1 microbatch). A practitioner deploying at 4–8 GPUs should evaluate whether the parameter memory savings justify the activation memory increase for their specific model configuration, rather than assuming the overhead is universally small.

---

### No Demonstration with Activation Recomputation or Selective Checkpointing

The paper's experiments use **no activation recomputation** (also called gradient checkpointing)—a standard technique in large-model training where intermediate activations are discarded during the forward pass and recomputed during the backward pass, trading computation for memory. The absence of recomputation matters for two reasons.

First, it changes the relative importance of the activation memory overhead. When activations are stored in full (as in the paper's experiments), the 1–2 extra microbatch overhead from vocabulary passes is a small fraction of total activation memory. But when activation recomputation is enabled, the *stored* activation memory is much smaller (only the layer boundaries are checkpointed, not all intermediate tensors), so the vocabulary passes' overhead becomes a **larger fraction** of the remaining stored activations. The paper's building-block analysis (lifespan ÷ interval) still applies—the overhead is still 1–2 microbatches' worth of *whatever activations are stored*—but the practical interpretation changes when the per-microbatch stored activation size shrinks dramatically under recomputation.

Second, activation recomputation changes the compute profile. Recomputed forward passes consume additional FLOPs, altering the ratio of forward-to-backward time that the pipeline schedule assumes. The paper's profiling-based schedule generation (Section 6.1) would handle this automatically by measuring the actual pass durations, but the paper does not demonstrate that the profiling-and-scheduling pipeline works correctly when recomputation is enabled, nor does it report throughput or memory numbers under recomputation regimes.

The paper also does not discuss **selective activation recomputation** (Korthikanti et al., 2023), where only certain layers (e.g., attention) are recomputed while others (e.g., feed-forward) are not. Since the vocabulary passes' memory overhead is measured in microbatches of the last transformer layer's activations, if that layer's activations are recomputed rather than stored, the overhead in absolute memory terms could be substantially different from the paper's measurements.

This limitation reduces the direct applicability of the paper's memory numbers to production training setups, which almost universally use some form of activation recomputation for large models. The paper does not acknowledge this gap or propose experiments to address it. A practitioner using activation recomputation should treat the reported peak memory savings as **directionally correct but not quantitatively transferable**—the balance improvements will still hold (vocabulary parameters are distributed regardless of recomputation), but the absolute memory numbers and the activation memory overhead fraction will differ.

---

### Composability Claim Extends Only to Two Specific Schedules

The paper presents Vocabulary Parallelism's integration with pipeline schedules as general and modular, via the building-block framework: "By uniformly repeating a building block, we can construct a pipeline schedule... This approach greatly simplifies dependency management for each microbatch and facilitates memory consumption analysis" (Section 5.2). The claim—implicitly—is that any schedule constructed from repeating building blocks can incorporate vocabulary passes by inserting 1–2 intervals into the last transformer layer's lifespan and slotting in `S` and `T` passes.

However, the paper demonstrates this for only **two specific schedules**: 1F1B (Harlap et al., 2018) and V-Half (Qi et al., 2024). While these are arguably the most widely used pipeline schedules, the landscape of PP scheduling is broader:

- **Zero-bubble pipeline parallelism** (Qi et al., 2023) splits the backward pass into two sub-passes: `B` (activation gradient computation) and `W` (weight gradient computation), using the gap between them to fill bubbles. The vocabulary `S` and `T` passes would need to be positioned relative to `B` and `W`, and it's not obvious whether the single-barrier design of Algorithm 2 (which decouples `T` from the backward critical path) would interact cleanly with a schedule that already has decoupled `B` and `W`. The paper explicitly references zero-bubble in Section 4.4 when noting that `T` "can be arbitrarily delayed" similar to zero-bubble's weight gradient handling—suggesting compatibility—but does not construct or evaluate the schedule.

- **Interleaved 1F1B** (Narayanan et al., 2021) assigns multiple virtual pipeline stages to each physical device. The paper mentions using virtual pipeline chunks in the V-Half experiments (Table 2 caption), but does not detail how the building-block modification interacts with virtual stage scheduling—whether the 1–2 extra intervals apply per virtual stage or per physical device, and how this affects the interleaving pattern.

- **Dynamic or adaptive schedules** (e.g., those that vary the number of microbatches in-flight based on memory pressure) may not have a fixed repeating building block at all, making the paper's integration methodology inapplicable without extension.

The paper's building-block methodology is elegant and the demonstrations on 1F1B and V-Half are thorough, but the generalizability claim is stronger than the evidence. The authors do not explicitly flag this as a limitation—the methodology is presented as universally applicable to schedules with repeating building blocks—but a practitioner using a schedule other than 1F1B or V-Half should expect to do their own integration work, potentially involving non-trivial dependency analysis if the schedule's internal structure differs significantly from the two demonstrated cases. The paper suggests no methodology for validating correctness of integration with novel schedules beyond the building-block construction, and no future work on extending the framework to broader schedule families.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

This paper makes a **diagnostic reframing with immediate practical consequences**, not a paradigm shift. It does not propose a new parallelism strategy, a new model architecture, or a new theoretical framework for distributed training. Instead, it identifies a specific, growing, and systematically overlooked bottleneck in pipeline parallelism—vocabulary-layer imbalance—and provides a self-contained, composable fix that slots into existing infrastructure with minimal disruption. The conceptual shift is from treating vocabulary layers as "just a few extra layers on the endpoints" to recognizing them as **qualitatively different from transformer layers** in their compute-to-memory ratio, their scaling behavior with vocabulary size, and their interaction with pipeline schedules. Table 4's FLOPs analysis, Figure 2's illustration of the 5× multiplier for Gemma2 9B, and the systematic failure of layer redistribution across all tested configurations (Figures 11–14) make this reframing hard to dispute.

The methodological change this triggers is that **vocabulary partitioning becomes a first-class design consideration in pipeline-parallel training**, on par with activation checkpointing and schedule selection. Before this work, a practitioner setting up a PP training run would choose a schedule (1F1B, V-Half, zero-bubble), decide on activation recomputation, and then—if imbalance was noticed—apply layer redistribution as a heuristic post-processing step, accepting that compute and memory could not be simultaneously balanced. After this work, the practitioner has a third orthogonal knob: partition vocabulary layers across all pipeline devices using either Algorithm 1 (throughput-prioritized) or Algorithm 2 (memory-prioritized), integrate the resulting passes into the schedule via a building-block modification, and achieve near-perfect balance in both dimensions. This is not a fundamental breakthrough, but it is a **high-leverage engineering contribution** that eliminates a bottleneck that was previously tolerated as inevitable.

The paper also **reconciles contradictory design intuitions** in the systems community. The interlaced pipeline (Lin et al., 2024) demonstrated that vocabulary layers *could* be partitioned for balance, but at the cost of a 1.5× activation memory penalty and ~11% synchronous communication overhead (Appendix B). The layer-redistribution approach (DeepSpeed, Smith et al., 2022; Skywork-MoE, Wei et al., 2024) demonstrated that imbalance *could* be mitigated without changing the parallelism strategy, but only partially and without addressing parameter memory. The field was left with an implicit tradeoff: balance compute imperfectly via redistribution, or balance both compute and memory via TP at the cost of activation memory and throughput. Vocabulary Parallelism resolves this tradeoff by showing that **the communication cost of vocabulary partitioning can be reduced, overlapped, and integrated without the catastrophic memory penalty**—the key enablers being the online-softmax reordering (Algorithms 1 and 2) and the building-block integration methodology (Section 5). The resolution is not a compromise between the two prior approaches; it is a third path that achieves the benefits of both while avoiding their respective failures.

The research directions this work makes more attractive are those that assume **balanced pipelines are achievable without architectural modification**. For instance, work on automated parallelism planning (nnScaler, Alpa, Unity) can now treat vocabulary-partitioned PP as a viable configuration option rather than a special case requiring TP fallback. Work on scaling laws for vocabulary size (Tao et al., 2024), which showed that larger models benefit from larger vocabularies, can now proceed without the implicit assumption that larger vocabularies will create pipeline imbalance—Vocabulary Parallelism decouples vocabulary size from pipeline efficiency. Conversely, research directions that focus on ad-hoc layer redistribution heuristics or on model architecture modifications to compensate for vocabulary imbalance (e.g., Llama 3's layer removal) become less urgent—the problem has a cleaner, more general solution at the systems level.

Finally, the paper establishes **vocabulary-layer scaling analysis as a standard diagnostic** for pipeline-parallel capacity planning. Figure 2's visualization of how vocabulary size multiplies compute and memory costs relative to transformer layers should become as routine as FLOPs estimates or memory breakdowns when configuring a training run. The paper's Table 4, which cleanly separates the FLOPs and parameter memory contributions of transformer, input, and output layers, provides a template that practitioners can instantiate for their own model architectures to predict whether vocabulary imbalance will be a bottleneck before training begins—and whether Vocabulary Parallelism is warranted.

### Follow-Up Research This Work Enables

**Integration with zero-bubble pipeline schedules.** The paper explicitly notes (Section 4.4) that the backward weight gradient pass `T` in Algorithm 2 "can be arbitrarily delayed, similar to the idea in zero-bubble strategy (Qi et al., 2023)," hinting at compatibility. Zero-bubble schedules split the backward pass into activation gradient (`B`) and weight gradient (`W`) sub-passes, using the gap between them to fill pipeline bubbles. A natural extension is to construct a combined schedule where the output layer's `S` and `T` passes are positioned relative to `B` and `W`, with `T` potentially filling the zero-bubble gap on the last pipeline stage. The specific question is: does the single-barrier design of Algorithm 2 allow `T` to be scheduled into the bubble-filling slot without creating new cross-device dependencies, and does this combination achieve both zero bubble *and* vocabulary balance? A strong follow-up would implement the building-block modification for the zero-bubble schedule, measure end-to-end MFU and peak memory on the same model configurations as this paper (Tables 1 and 2), and compare against zero-bubble with layer redistribution (the current best practice for zero-bubble under vocabulary imbalance).

**Vocabulary Parallelism for encoder-decoder architectures.** The paper evaluates exclusively on GPT-like decoder-only models, where there are two unbalanced vocabulary layers: the input embedding (first stage) and the output projection (last stage). Encoder-decoder models (T5, BART) add complexity: there is an encoder input embedding on the first encoder stage, a decoder input embedding on the first decoder stage, and a decoder output projection on the last decoder stage. The decoder output projection is identical to what the paper already handles, but the encoder input embedding may sit on a different pipeline stage and have different activation memory characteristics (encoder activations are typically smaller for seq2seq tasks with short encoder inputs). Additionally, some encoder-decoder models share embeddings between the encoder input and decoder input, creating parameter-memory sharing that Vocabulary Parallelism could exploit (tying becomes trivial when both embedding tables are partitioned identically across devices). A concrete experiment: take a T5-11B configuration, train with pipeline parallelism on a seq2seq task, implement Vocabulary Parallelism for all three vocabulary-layer positions, and measure whether the combined imbalance (encoder input + decoder input + decoder output) is fully resolved and whether embedding sharing provides additional memory benefits beyond what the decoder-only experiments suggest.

**Sensitivity of communication-computation overlap to interconnect bandwidth and GPU architecture.** The paper's throughput results depend on the ability to hide all-reduce latency behind transformer-layer computation via separate CUDA streams. This overlap was demonstrated on A100 GPUs with RoCE RDMA (Section 6.2), but the paper does not evaluate on slower interconnects or older GPU architectures where concurrent stream execution is less efficient. A critical negative result would be: at what interconnect bandwidth does Vocabulary Parallelism's throughput advantage over the Interlaced pipeline (or over Redis) vanish? The ablation in Appendix B.2 quantifies the Interlaced pipeline's synchronous all-reduce overhead at ~11% on the paper's hardware. By artificially throttling interconnect bandwidth (e.g., using `tc` traffic control or running on a cluster with 10GbE without RDMA), a follow-up could measure the crossover point where Vocabulary Parallelism's overlapped all-reduce no longer fits within the transformer computation window, causing it to become an exposed latency on the critical path. The experiment would profile per-pass timings with and without throttling, report the breakdown of time spent in communication vs. computation for the `C1` barrier in Algorithm 2, and establish a hardware requirement curve (minimum interconnect bandwidth per GPU for effective overlap at a given model scale and sequence length).

**Scaling to very large vocabulary sizes (512k–1M+) and multimodal embedding tables.** The paper sweeps vocabulary sizes up to 256k, which covers current large-scale LLMs (Gemma2, Llama 3). Two scaling questions are open. First, for multilingual models or byte-level tokenizers with 512k–1M vocabulary entries, does the per-device vocabulary slice $V/p$ become small enough that GPU kernel efficiency degrades measurably? The paper's scaling analysis (Table 3) shows output-layer efficiency dropping from ~91% to ~80% as $p$ goes from 8 to 32 at $V=256k$; extrapolating, at $V=1M$ and $p=64$, each device's slice would be $1M/64 \approx 15.6k$, which is smaller than the 256k/8 = 32k slice that achieves 91% efficiency in Table 3. The efficiency decline may be modest (the matrix multiplication dimensions are $[bs, V/p]$, and $bs$ dominates for long sequences), but this needs measurement. Second, multimodal models (vision-language, speech-text) often have separate embedding tables for different modalities—an image patch embedding, a text token embedding, an audio codebook embedding—potentially creating multiple vocabulary-layer-style imbalances on different pipeline stages. Does Vocabulary Parallelism extend cleanly to multiple heterogeneous embedding tables that may be placed on different stages? A follow-up could implement Vocabulary Parallelism for a multimodal model (e.g., LLaVA-style) and measure whether the separate embedding tables can be partitioned independently across the same pipeline devices without creating scheduling conflicts in the building-block framework.

**Vocabulary Parallelism under activation recomputation regimes.** The paper's experiments use no activation recomputation (Section 6 limitation), but production training runs almost universally use some form of checkpointing. The building-block analysis (Section 5.2) predicts that peak activation memory increases by 1–2 microbatches regardless of whether those microbatches' activations are stored in full or checkpointed, but the absolute memory impact depends on what fraction of activations are stored. Under full activation recomputation where only layer inputs are saved, the per-microbatch stored activation size is much smaller, so the 1–2 extra microbatches may be a larger *relative* overhead even if the absolute memory cost is smaller. A concrete experiment: run the same 1F1B configurations as Table 5 with full activation recomputation enabled, measure peak memory and MFU for Baseline, Vocab-1, and Vocab-2, and compute the activation memory overhead fraction (total peak memory minus parameter memory minus optimizer states, compared with and without vocabulary passes). The hypothesis is that the parameter memory savings from Vocabulary Parallelism become even more significant under recomputation (because activation memory shrinks, making parameter memory a larger fraction of total memory), while the activation memory overhead becomes proportionally larger but still small in absolute terms. This would provide practitioners with the data needed to decide whether Vocab-2 (1 barrier, throughput penalty) is preferable to Vocab-1 (2 barriers, lower throughput penalty) under their specific recomputation strategy.

**Automated difficulty-adaptive vocabulary pass scheduling.** The paper uses profiling to determine pass durations and construct the building-block schedule, but this profiling is a one-time cost that assumes fixed per-pass timing. In practice, the ratio of vocabulary-layer computation to transformer-layer computation varies with sequence length, which can change during training (e.g., packing variable-length sequences, or training with progressively longer contexts). An adaptive scheduler could monitor per-pass timings during the first few iterations and adjust the interval spacing in the building block without requiring a separate profiling phase. This is a direct extension of the paper's profiling-based approach (Section 6.1) and connects to the broader literature on adaptive pipeline scheduling (e.g., dynamic rebalancing in GPipe, or workload-aware scheduling in Alpa). The specific question is: can the building-block interval be adjusted online without stalling the pipeline, and does this online adaptation recover throughput when sequence length changes mid-training (e.g., when switching from 2048 to 4096 at a curriculum learning boundary)? A strong follow-up would implement an adaptive interval-sizing mechanism in the paper's open-source codebase, test it on a training run with multiple sequence-length phases, and measure whether the throughput achieved matches the profiled optimal at each phase.

### Practical Applications and Downstream Use Cases

**Training large-vocabulary LLMs on single-node multi-GPU setups (8 GPUs).** The paper's 8-GPU experiments (Table 5) directly inform a common scenario: a research lab with a single 8×A100 node training a ~4B parameter model with a large vocabulary (128k or 256k). Without Vocabulary Parallelism, this setup suffers a 33–51% throughput penalty and up to 25.64 GB peak memory (seq-len-2048, 256k vocab) from vocabulary imbalance. With Vocab-1, throughput improves to 50.12% MFU (a 2× gain over Baseline's 25.23%) and peak memory drops to 18.59 GB—staying within the 80 GB A100 budget with comfortable headroom for larger microbatches, longer sequences, or activation recomputation. The practical decision is straightforward: if the vocabulary size exceeds ~64k on an 8-GPU pipeline, enabling Vocabulary Parallelism via the paper's open-source implementation (integrated into Megatron-LM) recovers substantial throughput and memory with minimal code changes.

**Production training of models with tied embeddings (e.g., GPT-2, OPT, some multilingual models).** The paper deliberately uses untied embeddings throughout as "the harder setting" (Section 6.1), but notes that tying input and output embedding weights makes Vocabulary Parallelism implementation easier: the shared weight tensor is already partitioned evenly across devices, gradient synchronization is simplified (no separate all-reduce for input vs. output gradients), and total vocabulary parameter memory is halved (from $4hV$ to $2hV$). For a practitioner training or fine-tuning a tied-embedding model with pipeline parallelism, Vocabulary Parallelism's benefits are even larger than the paper's reported numbers. The peak memory savings relative to Baseline would approximately double in the vocabulary-parameter component (since only half the vocabulary parameters exist to distribute), and the implementation is simpler (no need to handle separate input and output weight tensors in the pipeline passes). The paper's open-source code supports tied embeddings, and the artifact appendix (Appendix G) provides a Docker-based reproduction package that a practitioner can use to benchmark on their specific tied-embedding model.

**Cost-efficient fine-tuning of large models where pretrained checkpoints have small vocabularies, but the fine-tuning domain requires vocabulary expansion.** A common workflow is to take a pretrained checkpoint (e.g., Llama 3 with 128k vocabulary), expand the vocabulary for a domain-specific tokenizer (adding 50k–100k new tokens for code, medicine, or multilingual text), and fine-tune with pipeline parallelism. The vocabulary expansion creates a new imbalance: the original 128k tokens were balanced (or the imbalance was tolerated during pretraining), but the expanded vocabulary makes the output layer proportionally larger than during pretraining, potentially creating pipeline bubbles that weren't present in the original training configuration. Vocabulary Parallelism directly addresses this: the expanded vocabulary layers are partitioned evenly regardless of their absolute size, so the fine-tuning throughput and memory profile match the pretraining profile (modulo the increased vocabulary FLOPs). Without Vocabulary Parallelism, the practitioner would need to either accept the new imbalance or manually redistribute transformer layers (which may not be possible if the checkpoint's layer count is fixed and the fine-tuning setup uses a different GPU count than pretraining). This makes Vocabulary Parallelism particularly valuable for the increasingly common "continued pretraining with domain-specific vocabulary expansion" workflow.

**Enabling memory-balanced V-Half scheduling for very large models.** The V-Half schedule (Qi et al., 2024) balances activation memory but inherits vocabulary-layer parameter memory imbalance. The paper's Section 6.4 demonstrates that without Vocabulary Parallelism, training a ~30B model with 256k vocabulary on 32 GPUs and V-Half scheduling **goes out-of-memory** (Figure 13 caption). With Vocab-1, the same configuration runs successfully at 59.82% MFU with a peak memory spread of <2.5 GB across devices. For practitioners targeting the largest models that fit in GPU memory (the Pareto frontier of scale), the combination of V-Half + Vocabulary Parallelism is what pushes the feasibility boundary: it simultaneously eliminates both the activation memory imbalance (via V-Half) and the parameter memory imbalance (via Vocabulary Parallelism), achieving what the paper calls "perfect balance in both memory and computation." Anyone using V-Half for memory efficiency should adopt Vocabulary Parallelism as a standard component if their model's vocabulary size exceeds ~64k—the paper's data shows that the two techniques are orthogonal and compose without interference.

### When to Prefer This Method

The paper itself frames Vocabulary Parallelism against two named alternatives—layer redistribution (Redis) and the interlaced pipeline (Interlaced, from nnScaler)—and the experimental comparisons in Figures 11–14 make the tradeoffs explicit enough to derive a practical decision rule. The following guidance is grounded in the paper's measurements, not in generic principle.

- **Prefer Vocabulary Parallelism (Vocab-1 or Vocab-2) over layer redistribution when the vocabulary size exceeds ~64k and the number of pipeline stages is ≥8.** The paper's data shows that Redis (layer redistribution) cannot maintain balanced throughput as vocabulary size grows: on 8 GPUs, Redis drops from 46.01% MFU at 32k vocab to 38.91% at 256k (Figure 11, Table 5), a 15% relative decline. Redis also cannot reduce peak memory, which grows identically to Baseline as vocabulary parameters remain concentrated on endpoints. Vocabulary Parallelism maintains flat MFU and substantially reduces peak memory at all tested vocabulary sizes, with the advantage growing larger as vocabulary size increases. At small vocabulary sizes (≤32k), Redis and Vocabulary Parallelism are close in throughput, and the implementation complexity of Vocabulary Parallelism may not be justified—the paper's 32k-vocab results show Redis at 46.01% vs. Vocab-1 at 50.42% on 8 GPUs, a modest gain.

- **Prefer Algorithm 2 (Vocab-2) over Algorithm 1 (Vocab-1) when activation memory is the binding constraint, especially at shallow pipeline depths (≤8 GPUs) where the 1-microbatch savings is a larger fraction of total activation memory.** At 8 GPUs, Algorithm 2's single-barrier design reduces peak memory by ~1.6 GB compared to Algorithm 1 (e.g., 27.34 GB → 25.73 GB at seq-len-4096, 256k vocab; Table 5), while sacrificing 0.26–0.5 percentage points of MFU. At deeper pipelines (32 GPUs), the memory savings are similar (~0.7 GB, Table 5) but the throughput penalty remains, making Algorithm 1 preferable if memory is not critically tight. The absolute memory savings are driven by one fewer microbatch of activations, making the choice dependent on per-microbatch activation size (larger for longer sequences and wider hidden dimensions) and whether the system is at the OOM boundary. The paper provides both implementations; practitioners can benchmark both on their specific configuration and choose based on whether the memory savings push them under the OOM threshold.

- **Strongly prefer Vocabulary Parallelism over the interlaced pipeline in any multi-node setting.** The paper's Appendix B.2 quantifies that the interlaced pipeline's synchronous all-reduce for vocabulary layers introduces ~11% idle time on 32 GPUs (from the ablation removing those communications). Combined with the 1.5× activation memory penalty (Appendix B.1, Figure 15), the interlaced pipeline objectively underperforms Vocabulary Parallelism on both throughput and memory at every multi-node configuration tested (Figures 11, 12). At 8 GPUs (single-node), the interlaced pipeline achieves competitive MFU (within 0.5 percentage points of Vocab methods, Figure 11), but its peak memory is still 2–3 GB higher (Figure 12). The interlaced pipeline has no configuration where it outperforms Vocabulary Parallelism in both metrics. The paper's experiments clearly demonstrate that Vocabulary Parallelism dominates the interlaced pipeline on NVLink-connected multi-GPU and multi-node RoCE RDMA setups, leaving no scenario where the interlaced approach is preferable.

- **When tied embeddings are available, Vocabulary Parallelism's memory and implementation advantages are amplified.** The paper tests only untied embeddings as the harder case, but notes that tied embeddings simplify gradient synchronization and halve vocabulary parameter memory. For tied-embedding models, the parameter memory savings relative to Baseline are approximately double the paper's reported numbers, and the implementation avoids managing separate input and output weight tensors. If the model architecture permits weight tying (common in GPT-2, OPT, some encoder-decoder models), Vocabulary Parallelism should be preferred almost unconditionally over Redis and Interlaced for vocabulary sizes above 64k—the already-clear advantages become even larger.

The paper does **not** provide evidence to recommend Vocabulary Parallelism over layer redistribution in regimes where vocabulary size is very small (<32k) and pipeline depth is shallow (<4 GPUs)—in those configurations, the vocabulary imbalance is naturally small and Vocabulary Parallelism's communication and kernel-efficiency overheads may dominate. The paper also does not compare against sequence parallelism approaches (Megatron-LM's sequence parallelism, ring attention) that may reduce the $s$ factor in the output layer's FLOPs ($6bshV$) by distributing the sequence dimension, potentially mitigating vocabulary imbalance for long-sequence settings without vocabulary partitioning. These are gaps in the paper's evaluation, not flaws in the method, but they mean the decision rule above is conditional on the tested regimes.
