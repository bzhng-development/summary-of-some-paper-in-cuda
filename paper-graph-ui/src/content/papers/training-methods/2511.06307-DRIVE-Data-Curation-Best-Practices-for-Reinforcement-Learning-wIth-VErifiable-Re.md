# DRIVE: Data Curation Best Practices for Reinforcement Learning wIth VErifiable Reward in Competitive Code Generation

**ArXiv:** [2511.06307](https://arxiv.org/abs/2511.06307)

## 🎯 Pitch

Training models to solve competitive programming problems with standard RL causes performance collapse, but preceding it with an entropy-expansion phase on thousands of easy-to-medium problems unexpectedly eliminates repetition and unlocks massive gains from a subsequent hard-focus curriculum. This two-stage recipe allows a 32B model to match or beat much larger systems, shifting the bottleneck in RL for code from algorithm design to how—and when—you curate the training data.

---

## 1. Executive Summary

This paper studies how to construct RLVR datasets and design training curricula for competitive-programming code generation, implementing a two-stage pipeline on Qwen2.5-32B that combines supervised fine-tuning distilled from strong open-source models with reinforcement learning using executable, testcase-driven rewards. The core contribution is a **two-stage RL framework** that first applies entropy expansion — training on a large, uniformly distributed set of ~9k competitive-programming problems with moderate rollout budgets (8 rollouts per prompt) and short generation windows (24k tokens) to diversify outputs and reduce repetition — followed by a **hard-focus curriculum** (termed Pre-GRPO) that trains on a small, challenging subset of problems with large rollout budgets (64–80 rollouts per prompt) while continuously retaining the lowest-pass-rate instances across progressive phases. The resulting model achieves state-of-the-art performance among 32B-parameter models, with relative improvements over the SFT baseline of 13.0% on LeetCode Weekly and 58.3% on Codeforces, and matches or exceeds much larger systems such as DeepSeek V3.1 and Seed1.6-0715 on LiveCode benchmarks, establishing that difficulty-aware data curation and curriculum design are as critical as algorithmic innovations for RLVR success — but only when the entropy expansion stage precedes hard-focus training, as ablations reveal that skipping Stage 1 degrades out-of-distribution generalization (a 4.8% drop on LeetCode Weekly) and that standard RL without difficulty filtering can cause training collapse (up to a 48.8% drop on LeetCode Weekly).

## 2. Context and Motivation

### The Core Problem: RLVR for Code Is Underexplored, and Data Curation Is Neglected

The paper addresses a specific, understudied gap: **how should we construct training data and design curricula for reinforcement learning with verifiable rewards (RLVR) in competitive-programming code generation?** While the broader RLVR literature has exploded in recent months — driven by reasoning-first models like OpenAI o1 (Jaech et al., 2024) and DeepSeek R1 (Guo et al., 2025) — the vast majority of this work has focused on mathematical reasoning benchmarks, particularly AIME (Yu et al., 2025; Li et al., 2025b; Lou et al., 2025; Yue et al., 2025). Competitive programming, despite sharing superficial similarities with math (both require multi-step logical reasoning), imposes fundamentally different demands that researchers have largely neglected.

The distinction matters because competitive-programming problems require models to produce **executable code** — not just a final answer — that must satisfy multiple hidden constraints. As the paper states in Section 1:

> "solutions must not only be logically correct but also executable, efficient, and capable of handling edge cases within strict computational constraints."

This means the reward signal in RLVR for code is simultaneously richer (executable tests provide unambiguous binary feedback) and more challenging (a solution can be logically on the right track but fail due to a subtle implementation bug, an off-by-one error, or a timeout on hidden edge cases). The training dynamics that work for math — where the output is typically a short final answer amenable to string matching — may not transfer straightforwardly to code generation where outputs are hundreds or thousands of tokens long and verification requires actual execution.

### Why This Problem Matters: Practical and Scientific Significance

**Practical deployment.** Competitive-programming benchmarks are becoming the standard measure of reasoning capability in LLMs, alongside math. The paper evaluates on LeetCode and Codeforces weekly contests specifically to avoid data leakage (Section 4.1), making these evaluations genuinely predictive of real-world coding ability. Improving RLVR for code has direct downstream implications: better competitive-programming models are better software engineering assistants, better at algorithmic problem-solving in general, and more capable at handling the kinds of structured reasoning tasks that appear in professional programming contexts.

**Scientific gap in the RLVR literature.** The paper identifies a striking imbalance in prior work (Section 2). Research on RLVR has been dominated by algorithm design — new variants of GRPO, PPO, and other policy optimization methods (Shao et al., 2024; Hu et al., 2025; Zheng et al., 2025; Li et al., 2025c). Where data curation *has* been studied in RL, it has almost entirely been in the context of RLHF (reinforcement learning from human feedback) for alignment, not RLVR for reasoning (Gao et al., 2025; Li et al., 2025a; Shen et al., 2025). The paper states this gap explicitly:

> "RL data construction for RLVR, especially for competitive-programming code generation, remains largely unexplored. To our knowledge, this is the first study to systematically investigate this problem in RLVR."

This is significant because RLVR differs from RLHF in a critical way: the reward signal in RLVR is **objective and verifiable** (test cases pass or fail) rather than subjective and model-estimated (a reward model's predicted human preference). This makes the data curation problem qualitatively different — you can use the reward signal itself to filter and select training prompts, which is exactly what the paper's Pre-GRPO method does — but it also means that overfitting to the reward is possible in ways that aren't relevant to RLHF.

**Scaling implications.** The paper positions itself within a broader conversation about whether RL scaling laws exist and how they interact with model size. Most RLVR scaling studies have been limited to dense 7B–32B models (Section 2), leaving open the question of whether the same strategies transfer to much larger architectures. The paper's inclusion of scaling experiments on an "internal large-scale MoE model" (Section 4.6) is specifically motivated by this gap, aiming to validate that the proposed data curation principles are not merely artifacts of the 32B scale.

### Where Prior Approaches Fall Short

The paper identifies several specific limitations in existing work that motivate its two-stage design.

**1. SFT models suffer from low entropy, repetition, and mode collapse entering RL.** The paper's analysis of its own SFT baseline (distilled from DeepSeekR1-0528 on 470K prompts) reveals three critical pathologies that standard RLVR training inherits and amplifies (Section 3.2). First, the model exhibits **low entropy**: it converges to a narrow set of solution patterns and fails to explore alternative approaches. Figure 3 directly visualizes this by comparing entropy distributions between 24k-context and 32k-context training, showing that the SFT model's output distribution is sharply peaked. Second, it generates **repetitive patterns** — the case study in Appendix B documents extensive template repetition, redundant edge-by-edge evaluation loops, and cyclical "try → fail → express confusion → retry" reasoning that leads to truncated outputs. Third, **harder problems that require longer responses are disproportionately penalized** during SFT due to long-sequence dependency challenges: the model never learns to sustain coherent reasoning over the extended contexts that difficult competitive-programming problems demand. Table 1 quantifies this asymmetry: on the relatively easier LeetCode Weekly problems, the SFT model's pass@10 (96.88%) matches DeepSeek V3.1 (96.88%) and Seed1.6-0715 (96.88%), but on the harder Codeforces problems, it falls substantially behind (24.24% vs. 33.33% and 39.39%). The model has learned to solve easy problems but plateaus on hard ones — a pattern that standard RLVR, applied uniformly, inherits rather than fixes.

**2. Prior RLVR research neglects data difficulty and treats all prompts uniformly.** This is the paper's central critique of existing RLVR work. As noted in Section 2:

> "Most existing approaches either apply uniform training strategies across all problem difficulties or rely on simplistic difficulty categorization, potentially limiting the model's ability to tackle the most challenging problems that define competitive programming excellence."

The consequences of this uniform treatment are visible in the paper's own ablation experiments (Table 4 and Figure 4). When the authors apply standard GRPO training directly to the SFT model using all 175 LiveCodeBench V6 problems without difficulty filtering ("RL with all LiveCodeV6 dataset"), performance **collapses** — dropping from the SFT baseline's 0.578 to 0.296 on LeetCode Weekly OJ, a 48.8% decrease. This is not a small regression; it is catastrophic degradation. The likely mechanism is that easy problems, which the model already solves correctly, dilute the RL training signal because they provide no meaningful gradient (the model is already rewarded for solving them). The RL objective, faced with a mix of trivial and impossible problems, overfits to the few examples where improvement is marginally possible while destabilizing overall performance. The paper's finding that "difficulty-aware training is crucial" and that "mixing easy problems into RL fails to obtain best performance and can even cause training/performance to collapse" (Section 4.4) is not an incremental observation — it is a fundamental insight that challenges the default assumption in much of the RLVR literature that more diverse training data is always better.

**3. Standard RL training creates a "capability ceiling" on hard problems.** Figure 5 provides the key diagnostic: when the authors cluster problems by their initial rollout accuracy (using 8 rollouts as the evaluation metric) and track training accuracy over time, they find that problems with medium initial accuracy improve rapidly, but problems with low initial accuracy **barely improve at all** — their training curves are essentially flat. The paper explains:

> "This pattern indicates that standard RL training struggles with difficult cases, potentially creating a capability ceiling that limits the model's performance on complex problem-solving tasks."

This is a specific, empirically grounded version of a more general concern: RLVR with limited rollouts per prompt may not provide enough positive signal on hard problems. If a problem has a pass@1 of, say, 2%, then with only 8 rollouts per prompt, the model will generate a correct solution in only ~15% of training batches (assuming independent sampling). The remaining 85% of the time, it receives only negative feedback — "all 8 attempts failed" — which provides no gradient toward the correct solution, only gradient away from the incorrect ones. This is a sparse-reward problem that is particularly acute in competitive programming, where the space of incorrect solutions is astronomically larger than the space of correct ones.

**4. Limited understanding of how rollout budget interacts with problem difficulty.** Prior work has generally treated rollout count as a hyperparameter to be tuned for overall performance, not as a strategic resource to be allocated differentially based on problem difficulty. The paper's single-case and few-case training experiments (Appendix A, Figures 6–8) provide direct evidence that this matters: increasing the rollout count from 8 to 64 significantly accelerates learning on hard cases, and certain problems that appear "frozen" at 12.5% accuracy under standard 8-rollout training remain learnable when given sufficient sampling budget. However, naively applying large rollout budgets across all problems would be computationally prohibitive — the paper's solution is to concentrate the large-budget training on the hardest subset of problems, which is the core of the Pre-GRPO strategy.

**5. The gap between SFT and competitive performance on hard problems is structural, not just quantitative.** This is perhaps the most subtle point the paper makes, and it's worth unpacking carefully. Table 1 shows that the SFT model's pass@10 on LeetCode Weekly (96.88%) is essentially saturated — the model can almost always find a correct solution given 10 attempts. But its Avg@1 on the same benchmark is only 57.81%, meaning that its first attempt is correct less than 60% of the time. On Codeforces, the gap is even starker: pass@10 of 24.24% vs. Avg@1 of 11.52%. This means the model *can* solve hard problems given enough attempts, but its proposal distribution is poorly calibrated — it cannot reliably generate a correct solution on the first try. Standard SFT, even with difficulty-aware duplication (the "Twice Hard Learning" strategy in Table 3), does not close this gap because it teaches the model what correct solutions look like but does not train it to systematically explore solution space or recover from initial failures. RLVR *should* help here because the executable reward signal provides direct feedback on which exploration paths are fruitful — but only if the RL training is designed to encourage exploration (entropy expansion) and to concentrate learning on the problems where the gap between pass@1 and pass@k is largest (hard-focus curriculum). Prior RLVR approaches that apply uniform training miss both aspects.

### How This Paper Positions Itself

The paper positions itself at the intersection of two under-explored directions in RLVR research: **data curation** (how to select and structure RL training prompts) and **curriculum design** (how to sequence training to progressively tackle harder problems). Its distinctive claim is that these aspects are *as important as algorithmic innovations* for achieving strong performance:

> "Our analysis reveals three critical insights: (1) standard RL training struggles with hard problems, creating a capability ceiling that limits model performance; (2) large rollout budgets (64+ samples) are essential for mastering challenging cases; and (3) progressive curriculum learning that continuously retains the hardest problems outperforms uniform difficulty distribution."

The paper is explicit that it is not proposing a new RL algorithm. It uses standard GRPO (Group Relative Policy Optimization) throughout. Rather, it is proposing a **training strategy** — a set of data curation and scheduling decisions — that makes standard RL algorithms work dramatically better for competitive programming than they do under conventional uniform training. This is a deliberate contrast with the algorithmic focus of contemporaneous work like DAPO (Yu et al., 2025), VAPO (Yue et al., 2025), and ProRL (Liu et al., 2025), all of which modify the RL objective to improve performance on math benchmarks. The paper implicitly argues that for competitive programming — and perhaps for reasoning tasks more broadly — the bottleneck is not the RL algorithm but rather *what data the algorithm sees and in what order*.

The paper also positions itself as providing **practical, validated best practices** rather than a single novel technique. The title emphasizes "Best Practices" — the goal is to distill actionable insights that practitioners can adopt, not to claim priority over a specific method. This is evident in the paper's structure: extensive ablations (Tables 3 and 4, Appendix A) systematically rule out alternative explanations, scaling experiments on a separate MoE architecture (Section 4.6) validate transferability, and the case study in Appendix B provides qualitative evidence for the entropy expansion hypothesis. The paper wants to convince the reader that the two-stage approach works *and* that its components are individually necessary, which is a higher evidentiary bar than simply reporting a single strong result.

Finally, the paper positions itself relative to the training-inference tradeoff literature implicitly rather than explicitly. By demonstrating that large rollout budgets (64–80 rollouts per prompt in Stage 2) are crucial for learning hard problems, the paper implies that compute spent on wider sampling during RL training is not wasted — it is essential for pushing the model's capability frontier. This has implications for how organizations allocate RL training compute: rather than maximizing the number of distinct training prompts, it may be more effective to deeply sample a smaller set of challenging problems. The paper's finding that "training with a larger share of challenging samples consistently improves results across all benchmarks" (Section 4.5, Table 4) directly supports this view and challenges the "more data is better" heuristic that dominates much of the LLM training literature.

## 3. Technical Approach

### 3.1 Reader Orientation

This paper presents a **training pipeline** — a sequenced set of data curation choices, training stages, and curriculum schedules — that transforms a base language model (Qwen2.5-32B-Instruct) into a competitive-programming specialist through supervised fine-tuning followed by two-stage reinforcement learning with verifiable rewards. The core problem the pipeline solves is that standard SFT leaves models with low output diversity, repetitive generation patterns, and a "capability ceiling" on hard problems that standard RLVR inherits and amplifies; the solution is to first expand the model's exploration entropy through broad, moderate-budget RL training, then concentrate a large rollout budget on a carefully filtered set of the hardest problems using a progressive curriculum that continuously retains the lowest-pass-rate instances.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has four major sequential components, each feeding into the next:

1. **SFT Data Construction and Training** — Collects open-source competitive-programming prompts, generates high-quality responses via distillation from DeepSeekR1-0528, filters to 470K hard examples using arena learning, duplicates the hardest problems, and fine-tunes Qwen2.5-32B-Instruct for 3 epochs. This produces the **SFT Model**, which can solve easy problems but plateaus on hard ones.

2. **Stage 1 RL: Entropy Expansion** — Takes the SFT model and trains it via GRPO on ~9K uniformly distributed competitive-programming problems with 8 rollouts per prompt and a 24K-token generation window for 32 steps. This produces a model with diversified output patterns, reduced repetition, and improved general competitive-programming capability, but still limited on the hardest problems.

3. **Stage 2 RL: Hard-Focus Curriculum (Pre-GRPO)** — Takes the Stage 1 model and trains it on a small, dynamically filtered subset of the hardest problems from LiveCodeBench V6 (175 total, with only 72/50/25 retained across three progressive phases) using large rollout budgets (64–80 rollouts per prompt) and a 32K-token generation window. The key mechanism is **Pre-GRPO**: after each phase, problems with the lowest pass rates are carried forward while easier ones are dropped, so the model increasingly concentrates its learning on the examples it still cannot solve.

4. **Evaluation Framework** — Validates the final model on LiveCode08-11, LiveCodeV5, LiveCodeV6, LeetCode Weekly contests (32 problems), and Codeforces Weekly contests (33 problems), with the latter two released after the training data cutoff to prevent contamination.

Information flows linearly: raw prompts → SFT data curation → SFT training → SFT model → Stage 1 entropy expansion → Stage 1 model → Stage 2 hard-focus curriculum → final RL model → evaluation.

### 3.3 Roadmap for the Deep Dive

- **First, the SFT data construction pipeline**, because it establishes the baseline model that RL inherits — and whose pathologies (low entropy, repetition, hard-problem weakness) directly motivate the RL design.
- **Second, the entropy expansion stage**, because its mechanisms (uniform problem distribution, moderate rollout budget, short generation window) are designed to fix specific SFT failures, and understanding those failures first makes the design choices intelligible.
- **Third, the hard-focus curriculum (Pre-GRPO)**, because it depends on the Stage 1 model as its starting point and because its difficulty-filtering mechanism builds conceptually on the SFT data curation philosophy (concentrating resources on hard examples).
- **Fourth, the GRPO algorithm itself**, because both RL stages use the same underlying optimizer but with different data, rollout budgets, and sequence lengths — understanding the algorithm once allows us to see how the two stages differ operationally.
- **Fifth, the evaluation protocol and contamination controls**, because the paper's validity claims rest on careful benchmark selection and the absence of data leakage.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems and training methodology paper** whose core idea is that RLVR for competitive programming works best when training data is difficulty-curated and training is sequenced: broad entropy expansion first, then concentrated hard-problem optimization with large rollout budgets.

---

#### Supervised Fine-Tuning Data Construction and Training

The SFT phase establishes the starting point for all subsequent RL training. Its design reflects the paper's overarching philosophy — concentrate computational resources on hard examples — and its specific choices directly shape the failure modes that the RL stages must later address.

**Base model and data sources.** The pipeline begins with **Qwen2.5-32B-Instruct** (Hui et al., 2024), a 32-billion-parameter dense transformer. The authors initially collect **1.27 million open-source competitive-programming prompts** and generate corresponding responses through **distillation from DeepSeekR1-0528**, a strong open-source reasoning model. Distillation here means: for each prompt, DeepSeekR1-0528 generates a response (presumably with chain-of-thought reasoning), and that response becomes the supervised target for training Qwen2.5-32B. This is standard knowledge distillation — the student model learns to imitate the teacher's output distribution on the same inputs — but the choice of teacher matters: DeepSeekR1-0528 is itself an RLVR-trained reasoning model, so the distilled SFT data implicitly encodes exploration patterns and solution strategies that emerged from RL training on a larger model.

**Arena learning for hard-sample filtering.** Rather than training on all 1.27M examples — which would include many easy problems the model already handles — the authors apply a **5-round arena learning strategy** (Luo et al., 2024) to reduce the dataset to **470K high-quality prompts**. The procedure works as follows:

1. Split the 1.27M prompts into five equal folds (each ~254K prompts).
2. Train an initial model on the first fold.
3. Use that model to generate predictions on the second fold.
4. Retain only the samples the model **fails on** ("hard samples") from the second fold.
5. Train the next model iteration on the retained hard samples from fold 2 (plus possibly fold 1 data — the paper doesn't specify whether previous folds are accumulated or replaced, but the core mechanism is filtering by failure).
6. Repeat for all five folds, each time training on the hard samples identified by the previous model iteration.

The result is a condensed dataset of 470K prompts — a reduction of over 60% from the original 1.27M — that is enriched for problems the model finds challenging. Table 3 confirms that this filtering alone nearly maintains performance despite the massive data reduction: the Arena Learning Strategy achieves comparable results to the Basic SFT Strategy (trained on all 1.27M) across most benchmarks, with only slight underperformance attributed to "an insufficient training token budget."

**Twice Hard Learning.** Building on the arena-filtered 470K dataset, the authors introduce a further refinement: **Twice Hard Learning**. After identifying the hard samples via arena learning, they **duplicate each hard problem once** in the training data, effectively doubling the model's exposure to challenging examples while keeping the overall training token budget comparable to the original full-dataset training. The paper explicitly compares this to Difficulty-Aware Rejection Tuning (DART) for mathematical problem-solving (Tong et al., 2024), but notes a key difference:

> "we do not directly adopt their RFT method, as it requires extensive model sampling which is computationally expensive for our use case. Our simpler duplication strategy achieves similar benefits of emphasizing difficult problems while maintaining computational efficiency."

This is a pragmatic design choice: DART's rejection tuning requires the model to generate multiple candidate solutions per problem, evaluate them, and only train on successful ones — a computationally expensive loop. Simple duplication achieves the same effect of increasing the model's exposure to hard problems without the generation overhead. The paper also adds **general-purpose coding data and reasoning-intensive problems** beyond competitive programming, noting that this "significantly improves performance on competitive programming tasks, likely due to enhanced reasoning and code comprehension abilities."

**Training hyperparameters and configuration.** The SFT training is configured as follows:

- **Base model:** Qwen2.5-32B-Instruct
- **Training data:** 470K prompts (after arena filtering), with hard problems duplicated once
- **Epochs:** 3
- **Learning rate:** `$1 \times 10^{-5}$`
- **GPU count:** 256
- **Global batch size:** 512 sequences
- **Context window:** 32K tokens (this is the generation window during SFT and evaluation)

The resulting **SFT Model** achieves the baseline performance shown in Table 1: pass@10 of 96.88% on LeetCode Weekly and 24.24% on Codeforces OJ, with avg@1 of 57.81% and 11.52% respectively. These numbers encode the core pathology the RL stages must address: the model *can* find correct solutions given enough attempts (pass@10 is high on LeetCode), but its *first attempt* is much less reliable (avg@1 is substantially lower), and on harder problems (Codeforces), even pass@10 is weak.

**Why this design?** The SFT pipeline embodies three design principles that carry through to the RL stages. First, **difficulty matters**: concentrating training on hard examples (via arena filtering and duplication) is more effective than uniform exposure to all problems, even at the same total token budget. Second, **token budget allocation is a zero-sum game**: the Twice Hard strategy doesn't increase total training tokens; it redistributes them toward harder examples, and this reallocation improves performance (Table 3). Third, **distillation provides a strong initialization but not a complete solution**: the SFT model inherits reasoning patterns from DeepSeekR1-0528 but develops its own pathologies — low entropy, repetition, and a hard-problem ceiling — that distillation alone cannot fix.

#### Analysis of the SFT Model: Three Pathologies That Motivate the RL Design

Before describing the RL stages, the paper performs diagnostic analysis on the SFT model to identify *why* standard RLVR would fail if applied directly. This analysis (Section 3.2) identifies three interrelated problems:

**Pathology 1: Low entropy and limited exploration.** The model's output distribution is sharply peaked — it converges to a narrow set of solution patterns for each problem type. Figure 3 visualizes this by comparing entropy distributions between what the paper calls "24k-style training" and "32k-style training." (The paper doesn't precisely define these terms here, but based on context: "32k-style" refers to SFT with a 32K-token generation window, which is the default SFT configuration; "24k-style" refers to RL training with a shorter 24K-token window, which is what Stage 1 uses. The comparison shows that the 32K SFT model has lower entropy than the 24K RL-trained model.) Low entropy means the model repeatedly generates similar solutions, failing to explore alternative algorithms or implementation strategies. For competitive programming, this is particularly damaging because different problems require different algorithmic approaches (dynamic programming vs. greedy vs. graph traversal vs. number theory), and a model stuck in a narrow solution mode will fail on problems outside that mode.

**Pathology 2: Repetitive generation patterns leading to truncation.** The model produces redundant code structures and falls into reasoning loops that consume the generation budget without reaching a correct solution. Appendix B provides an extensive case study documenting this behavior. The key patterns include:

- **Computational template repetition:** the same permutation-validation algorithm is applied systematically across dozens of different permutations, each following identical logical steps with different parameters.
- **Granular analysis loops:** each permutation analysis involves repetitive edge-by-edge evaluation following the pattern "determine desired state → check current state → calculate cost difference → accumulate total."
- **Hypothesis-testing cycles:** "try permutation X → calculate cost → compare to expected → express confusion → try next permutation," creating systematic but inefficient exploration strategies.
- **Debugging iteration patterns:** systematic testing of permutation variations using identical verification procedures, creating computational redundancy despite thorough coverage.
- **Meta-cognitive loops:** high-level reasoning cycles of "acknowledging complexity → attempting enumeration → encountering discrepancies → expressing uncertainty → restarting with variations."

These patterns consume the 32K-token generation window without producing correct solutions, leading to **truncated outputs** — the model runs out of context before completing its reasoning. This is a direct consequence of the SFT training objective: the model learns to imitate correct solutions but never receives feedback on *when to stop exploring* or *how to recognize that a particular approach is futile*. It has no internal signal for "this line of reasoning is going nowhere, try something different."

**Pathology 3: Hard problems requiring long responses are disproportionately penalized.** The paper observes empirically that "harder problems tend to require longer responses, which are harder to learn and generalize during SFT due to long-sequence dependency challenges." Table 1 quantifies the consequence: on the relatively easier LeetCode Weekly problems, the SFT model's pass@10 (96.88%) equals or exceeds much larger models, but on the harder Codeforces problems, its pass@10 (24.24%) is substantially behind DeepSeek V3.1 (33.33%) and Seed1.6-0715 (39.39%). The model has not learned to sustain coherent, multi-step reasoning over the long sequences that difficult problems demand, likely because the SFT objective provides weaker supervision for later steps in long solutions — the model receives the same loss weight on every token, but the signal for early reasoning steps is stronger (they are more similar across problems) while the signal for later, problem-specific steps is weaker and more diffuse.

**Why these pathologies matter for RL design.** These three problems are not independent. Low entropy (Pathology 1) means the model generates a narrow range of candidate solutions during RL training, limiting the diversity of reward signals the RL algorithm receives. Repetitive patterns (Pathology 2) mean that even the limited exploration the model does attempt is inefficient, consuming the generation budget on redundant computation rather than genuine exploration. And the hard-problem penalty (Pathology 3) means that the RL algorithm, which depends on occasionally generating correct solutions to receive positive reward, will almost never see positive examples on the hardest problems — the model's initial pass@1 is near zero on those problems, so with small rollout budgets the RL process receives only negative feedback and cannot learn. These three observations directly motivate the two-stage design: Stage 1 addresses Pathologies 1 and 2 (entropy and repetition), while Stage 2 addresses Pathology 3 (hard-problem learning) by concentrating large rollout budgets on the most difficult cases.

#### Stage 1: Entropy Expansion RL

The first RL stage is designed to **increase output diversity, reduce repetitive generation patterns, and improve general competitive-programming capability** before tackling the hardest problems. It operates on the SFT model using standard GRPO but with specific data and hyperparameter choices that encourage exploration.

**Training data.** Stage 1 uses a dataset of approximately **9,000 competitive-programming problems** sourced from open-source repositories. Unlike the SFT data, which was filtered for difficulty, this dataset is **uniformly distributed** — it includes easy, medium, and hard problems in roughly equal proportions. The rationale is that entropy expansion requires the model to encounter a broad range of problem types and difficulty levels to diversify its output distribution. If the data were filtered to only hard problems, the model would have no opportunity to explore and master the medium-difficulty patterns that serve as building blocks for harder solutions. If it were only easy problems, the model would not be pushed to generate the longer, more complex solution structures that Stage 2 requires as a starting point. The uniform distribution provides both scaffolding (easier problems reinforce basic patterns) and challenge (harder problems force the model to stretch beyond its SFT comfort zone).

**Training configuration.** The key hyperparameters for Stage 1 are:

- **RL algorithm:** GRPO (Group Relative Policy Optimization) — the same algorithm used in Stage 2, described in detail in the GRPO subsection below.
- **Training steps:** 32 steps (a "step" here is one GRPO update, meaning the model's parameters are updated 32 times).
- **Rollouts per prompt:** 8 (for each prompt in a training batch, the model generates 8 complete solutions, and the GRPO algorithm computes advantage relative to the group).
- **Total sequence length:** 24K tokens (including both the prompt tokens and the generated response tokens). This is shorter than the SFT model's 32K evaluation window, and the choice is deliberate.
- **Generation budget per step:** `$\text{batch size} \times \text{rollouts per prompt} \times \text{max sequence length}$`. The paper does not specify the Stage 1 batch size explicitly, but the global batch size of 512 from SFT and the Stage 2 configuration (batch size 128 for the MoE experiments) provide context. Given that Stage 1 uses ~9K prompts and 32 steps, a batch size of approximately 256–512 prompts per step is implied (9K prompts ÷ 32 steps ≈ 281 prompts per step if each prompt is seen once; with 8 rollouts, that's ~2,250 generations per step).

**The 24K sequence length constraint.** Why 24K tokens when the SFT model was trained and evaluated at 32K? The paper's Figure 3 provides the answer: comparing entropy between "24k-style" and "32k-style" training shows that the shorter generation window produces higher output entropy. The mechanism is not fully explained, but a plausible interpretation is: when the model has a full 32K tokens to work with, it can afford to generate longer, more detailed reasoning chains — which naturally exhibit lower entropy because longer chains contain more predictable, templated structure (each step follows logically from the previous one). When constrained to 24K tokens, the model is forced to be more concise, which reduces the opportunity for repetitive filler and encourages more diverse, compressed reasoning strategies. Additionally, the shorter window directly mitigates the truncation problem: solutions that would have been truncated at 32K because of repetitive loops are more likely to complete within 24K simply because the model has less room to loop.

**What Stage 1 accomplishes.** The paper identifies three specific benefits, validated by the ablation in Table 4:

1. **Entropy enhancement:** Training on a broad, uniformly distributed problem set with moderate rollout budgets expands the model's output diversity. The model learns to generate a wider range of algorithmic approaches and implementation patterns because it is reinforced for correct solutions across many different problem types, each requiring different strategies.

2. **Pattern reduction:** The increased entropy directly reduces the repetitive generation patterns documented in Appendix B. The model receives positive reward for *correct* solutions regardless of their structure, and negative reward for *incorrect* solutions (including those that loop or repeat). Over 32 update steps, this reinforcement signal teaches the model to stop generating redundant computation and to recognize when a reasoning path is unproductive.

3. **Overall performance improvement:** Table 2 shows that the RL Stage 1 model improves over the SFT baseline on most benchmarks, with gains of +2.3 percentage points on LiveCode08-11 (0.602 → 0.625), +3.3 on LiveCodeV5 (0.594 → 0.627), +8.5 on LiveCodeV6 (0.549 → 0.634), and +2.5 on LeetCode Weekly (0.578 → 0.603). The notable exception is Codeforces, where Stage 1 slightly *decreases* performance (0.115 → 0.112), suggesting that entropy expansion alone does not help — and may slightly hurt — on the hardest problems. This is expected: Stage 1 trades some precision for diversity, and on problems where the model needs maximum precision, that tradeoff is unfavorable. Stage 2 is designed to recover and exceed the precision on hard problems.

**Design choice: why 8 rollouts and not more?** The paper's scaling analysis (Section 4.5, Figure 6) shows that higher rollout counts accelerate learning on hard cases, but Stage 1 is not primarily about hard cases — it's about diversifying the model's behavior across the entire problem distribution. With 8 rollouts per prompt, each prompt produces enough samples for GRPO to compute a meaningful group-relative advantage (it can distinguish better solutions from worse ones within the group of 8), but not so many that the computational cost becomes prohibitive across 9K prompts. The paper's later finding that 64+ rollouts are needed for hard problems (Stage 2) does not contradict the choice of 8 rollouts here — it shows that different stages have different optimal rollout budgets, which is precisely the paper's point about strategic resource allocation.

**Table 4 ablation: removing Stage 1.** The ablation "RL without First Stage Only Second Stage" (row 3 of Table 4) directly applies the hard-focus curriculum (Stage 2) to the SFT model without the entropy expansion stage. The results are revealing: while this configuration improves on the in-distribution LiveCodeV6 dataset (+25.9% relative improvement, from 0.549 to 0.691), it **degrades performance on out-of-distribution benchmarks** — LeetCode Weekly OJ drops from 0.578 to 0.550, a 4.8% decrease. This is the key evidence for Stage 1's necessity: without entropy expansion, the model can overfit to the specific hard problems in the Stage 2 curriculum (LiveCodeV6) but loses generalization to unseen problems (LeetCode Weekly, which was released after training). Stage 1 prevents this by ensuring the model maintains broad capability while Stage 2 pushes its frontier.

#### Stage 2: Hard-Focus Curriculum (Pre-GRPO)

The second RL stage is where the paper's core contribution — difficulty-aware data curation for RLVR — is most concretely realized. The goal is to push the model's capability frontier on the hardest problems by concentrating a large rollout budget on a small, dynamically filtered set of challenging examples.

**Training data: LiveCodeBench V6 with Pre-GRPO filtering.** Stage 2 starts with the full **LiveCodeBench V6 dataset**, which contains **175 high-quality competitive-programming problems with comprehensive test cases**. However, rather than training on all 175 problems uniformly, the paper applies a filtering procedure called **Pre-GRPO**. The name is analogous to Shen et al.'s (2025) Pre-PPO for RLHF, but adapted for GRPO: before each training phase, problems are evaluated (presumably by generating rollouts from the current model) and only those with the **lowest pass rates** are retained for the next phase.

The specific curriculum schedule is:

- **Phase 1:** Train on the **72 hardest cases** (the 72 problems with lowest pass rates out of the 175 in LiveCodeV6) for **32K steps** (the paper says "32k steps" but given the extremely small dataset — only 72 prompts — this likely means 32K *total* steps or iterations; the three phases together total 32K steps, with Phase 1 taking the majority). The rollout budget is **80 rollouts per prompt** (from Section 3.2: "We sample 80 rollouts per prompt in this stage"), and the generation window is **32K tokens**.
- **Phase 2:** Retain the **50 hardest cases** from Phase 1 (the 50 problems that still have the lowest pass rates after Phase 1 training) and train for the remaining steps with a reduced rollout budget of **64 rollouts per prompt**. The paper says Phase 2 uses a "32-step budget," but this likely means 32 rollouts per prompt (the wording is ambiguous — "a 32-step budget" in the original text might refer to rollout count rather than training steps; given the pattern of Phase 1 = 80 rollouts, Phase 2 = reduced, Phase 3 = further reduced, I'll interpret "32-step" as 32 rollouts, though the paper is inconsistent here — the later scaling experiments in Section 4.6 use 64 rollouts for Stage 2, suggesting the intended number is 64).
- **Phase 3:** Retain the **25 hardest cases** from Phase 2 and train for the final portion with **32 rollouts per prompt**.

The progressive reduction in dataset size (72 → 50 → 25 problems) and rollout budget (80 → 64 → 32) creates an increasingly focused training signal: the model spends its final training steps exclusively on the 25 problems it still cannot reliably solve, with substantial sampling to ensure it occasionally generates correct solutions and receives positive reward.

**The Pre-GRPO mechanism in detail.** The core innovation is the continuous retention of the hardest problems. After each phase, the model is evaluated on all problems in the current set (by generating multiple rollouts and computing pass rates), and only those below a threshold — or simply the bottom N by pass rate — are carried forward. This creates a **dynamic curriculum**: problems graduate out of the training set when the model masters them (their pass rate rises above the threshold), and the model increasingly concentrates on the problems where it still struggles. The paper describes this as:

> "Pre-GRPO carries forward a subset of low–pass-rate cases from each phase to the next."

This is fundamentally different from standard curriculum learning, where the difficulty threshold is predetermined (e.g., train on easy problems first, then medium, then hard) and static. In Pre-GRPO, the difficulty threshold is **model-relative** — a problem is "hard" only if the current model cannot solve it — and it updates as the model improves. This means the curriculum automatically adapts to the model's learning trajectory: if the model rapidly masters certain problems, they are dropped quickly; if it struggles unexpectedly with others, they remain in the training set.

**Why large rollout budgets (64–80) are essential.** The paper's few-case and single-case training analysis (Appendix A, Figures 6–8) provides the empirical justification. When training on a single hard case with 8 rollouts per prompt, the model either learns very slowly (Case 1: from 12% to 36.7% accuracy after 60 steps) or not at all (Case 4: frozen at 12.5%). This is the sparse-reward problem: with only 8 rollouts and a pass@1 of ~12%, the model generates at least one correct solution in only ~64% of batches (assuming independent sampling: `$1 - (1 - 0.12)^8 \approx 0.64$`). In the other 36% of batches, all 8 rollouts fail, and the model receives no positive signal — only gradients pushing it away from the incorrect solutions. This is not just inefficient; it can be actively harmful because the model may learn to avoid solution patterns that are *close* to correct (but contain a subtle bug) without ever seeing what the correct pattern actually is.

With 64 rollouts at the same pass@1 of 12%, the probability of at least one correct solution rises to `$1 - (1 - 0.12)^{64} \approx 0.9997$` — essentially certain. The model will almost always have at least one positive example in each batch, providing a gradient *toward* the correct solution space, not just away from the incorrect one. Figure 6 directly confirms this: higher rollout counts accelerate learning on hard cases. The paper's Stage 2 rollout budget of 64–80 is chosen to make this probability high enough that hard problems actually provide a learnable signal. The computation is expensive — 80 rollouts per prompt across 72 prompts, each up to 32K tokens — but the paper argues this concentrated investment is more effective than spreading the same total compute across more prompts with fewer rollouts each.

**The 32K generation window in Stage 2.** Unlike Stage 1's 24K window, Stage 2 uses a 32K-token generation window, matching the SFT evaluation length. The rationale is that hard problems genuinely require longer reasoning chains — they involve multi-step algorithm design, edge-case analysis, and implementation details that cannot be compressed into 24K tokens without losing correctness. The entropy expansion in Stage 1, by reducing repetitive patterns, ensures that the 32K window is used efficiently (less looping, more productive reasoning), so the model can actually benefit from the extra tokens rather than filling them with redundancy.

**Relationship to the "RL with all LiveCodeV6 dataset" ablation.** Table 4's most dramatic result is the catastrophic failure of training directly on all 175 LiveCodeV6 problems without Pre-GRPO filtering ("RL with all LiveCodeV6 dataset"): performance on LeetCode Weekly drops from 0.578 (SFT) to 0.296, a 48.8% decrease. This ablation demonstrates that the Pre-GRPO filtering is not just helpful but *necessary* — training on a mix of easy and hard problems destroys performance. The mechanism is likely that easy problems dominate the gradient signal: since the model already solves them correctly, they produce near-zero advantage (all rollouts succeed, so there's no within-group variation for GRPO to exploit), but they still consume the generation budget and contribute noise to the parameter updates. The hard problems, which should provide the learning signal, are underrepresented in the effective gradient because their advantage estimates are buried in the noise from easy-problem updates. Pre-GRPO eliminates this by removing easy problems entirely, ensuring that every training step is spent on problems where the model's current policy has room to improve.

**Design choice: why three phases and not continuous filtering?** The paper uses discrete phases (72 → 50 → 25) rather than updating the difficulty filter after every training step. This is likely a pragmatic choice driven by computational cost: evaluating pass rates on all 175 problems requires generating multiple rollouts per problem, which is expensive. Doing this after every phase (every ~10K steps) is feasible; doing it every step would consume more compute than the training itself. The three-phase schedule provides enough adaptation to track the model's learning while keeping the evaluation overhead manageable.

#### The GRPO Algorithm: How Both RL Stages Optimize

Both RL stages use **Group Relative Policy Optimization (GRPO)**, the same algorithm popularized by DeepSeek R1 (Guo et al., 2025) and DAPO (Yu et al., 2025). The paper does not modify the algorithm; it uses GRPO as a fixed optimizer and varies the data, rollout budget, and sequence length. Understanding GRPO is essential to understanding what the two stages are actually *doing* at the optimization level.

**What GRPO optimizes.** GRPO is a policy gradient method designed for RL with verifiable rewards. The core idea is to generate multiple complete solutions (rollouts) for each prompt, compute a reward for each solution, and then update the model to increase the probability of solutions that received higher-than-average reward (for that prompt) while decreasing the probability of solutions that received lower-than-average reward. The "group-relative" part means that the advantage (how much better or worse a solution is) is computed *within* the group of rollouts for a single prompt, not across prompts or relative to a learned value function.

**The reward signal.** The reward for each generated solution is binary and execution-based: the generated code is compiled and run against the problem's hidden test cases. If all test cases pass, the reward is 1 (success). If any test case fails, the reward is 0 (failure). There is no partial credit — the model does not receive reward for "almost correct" solutions or for passing some test cases but not others. This binary reward is a deliberate choice: it is objective (no reward model to train or hack), verifiable (execution provides ground truth), and aligned with the evaluation metric (pass@1 is what the benchmarks measure). However, it inherits the sparsity problem discussed above: on hard problems, most rollouts receive zero reward, making the gradient signal weak.

**The GRPO advantage computation.** For a given prompt with `$K$` rollouts (where `$K = 8$` in Stage 1 and `$K = 64$` or `$80$` in Stage 2), let the rewards be `$r_1, r_2, \dots, r_K \in \{0, 1\}$`. GRPO computes the advantage for rollout `$i$` as:

$$A_i = \frac{r_i - \bar{r}}{\sigma(r)}$$

where `$\bar{r} = \frac{1}{K}\sum_{j=1}^K r_j$` is the mean reward across the group, and `$\sigma(r)$` is the standard deviation of rewards across the group (or a constant normalization factor — the paper doesn't specify the exact normalization, but standard GRPO uses standard deviation for stability).

**What this computes:** the advantage is a standardized score indicating how much better (positive advantage) or worse (negative advantage) rollout `$i$` is compared to the average rollout for that prompt. If a rollout succeeded (reward = 1) while most others failed (mean reward is low), it receives a large positive advantage — the model is strongly reinforced toward this solution pattern. If a rollout succeeded but most others also succeeded (mean reward is high), it receives a small positive advantage — the model is weakly reinforced, since success is already common. If a rollout failed while most others succeeded (mean reward is high), it receives a large negative advantage — the model is strongly pushed away from this pattern. If a rollout failed and most others also failed (mean reward is low), it receives a small negative advantage — the model is weakly pushed away, since failure is already the norm and the specific reason for failure is hard to distinguish from the general difficulty of the problem.

**The GRPO policy gradient update.** The model's parameters `$\theta$` are updated to maximize:

$$\mathcal{J}(\theta) = \mathbb{E}_{q \sim \mathcal{D}, \{o_i\}_{i=1}^K \sim \pi_{\theta_{\text{old}}}(q)} \left[ \frac{1}{K} \sum_{i=1}^K \min\left( \frac{\pi_\theta(o_i|q)}{\pi_{\theta_{\text{old}}}(o_i|q)} A_i, \operatorname{clip}\left( \frac{\pi_\theta(o_i|q)}{\pi_{\theta_{\text{old}}}(o_i|q)}, 1-\epsilon, 1+\epsilon \right) A_i \right) \right]$$

where:

- `$\mathcal{D}$` is the training prompt distribution (the ~9K prompts in Stage 1, the filtered hard subset in Stage 2).
- `$\pi_\theta(o_i|q)$` is the probability the current model assigns to the generated output sequence `$o_i$` given prompt `$q$`.
- `$\pi_{\theta_{\text{old}}}(o_i|q)$` is the probability the *old* model (before the current update) assigned to `$o_i$` — this is the importance sampling ratio that corrects for the fact that the rollouts were generated by an older policy.
- `$A_i$` is the group-relative advantage computed as above.
- `$\epsilon$` is a clipping parameter (typically around 0.2) that prevents the policy from changing too dramatically in a single update.
- The `$\min$` operation implements PPO-style clipping: if the advantage is positive, the ratio `$\pi_\theta / \pi_{\theta_{\text{old}}}$` is clipped at `$1 + \epsilon$` to prevent the model from becoming overconfident; if the advantage is negative, the ratio is clipped at `$1 - \epsilon$` to prevent the model from completely abandoning a solution pattern that may have been close to correct.

**What this computes:** the objective increases when the model assigns higher probability to rollouts with positive advantage (successful solutions, especially surprising ones) and lower probability to rollouts with negative advantage (failed solutions, especially ones that failed when others succeeded). The clipping prevents destructive updates — the model cannot change its probability by more than a factor of `$1 \pm \epsilon$` for any given output sequence, which stabilizes training and prevents the policy from collapsing to a single mode.

**Why GRPO rather than standard PPO?** GRPO eliminates the need for a learned value function (the "critic" in actor-critic methods). Instead of estimating the expected future reward of a state using a separate neural network, GRPO uses the empirical mean reward across the group of rollouts as a baseline. This is computationally simpler (no critic network to train and maintain), avoids the instability that can arise from imperfect value estimates, and is particularly well-suited to settings where the reward is binary and the rollouts are independent — the group mean is an unbiased estimate of the expected reward for that prompt under the current policy. The cost is that GRPO requires multiple rollouts per prompt (at least 2, and practically 8 or more to get meaningful advantage estimates), which increases the generation budget. This is the tradeoff the paper exploits: by varying the rollout count between Stage 1 (8 rollouts, broad coverage) and Stage 2 (64–80 rollouts, deep sampling of hard problems), it allocates the generation budget where it provides the most learning signal.

**How the two stages differ under GRPO.** The algorithmic mechanics are identical — same clipping, same advantage computation, same policy gradient — but the effective behavior differs because of the data and rollout budget. Stage 1, with 8 rollouts per prompt across 9K diverse problems, provides a broad but shallow learning signal: the model gets moderate-quality advantage estimates (8 rollouts is enough to distinguish good from bad solutions but far from the precision of 64 rollouts) on a wide range of problem types, which pushes it toward general-purpose improvement and diversity. Stage 2, with 64–80 rollouts on only 25–72 hard problems, provides a narrow but deep learning signal: the model gets high-quality advantage estimates (the probability of seeing at least one success is near 1) on the specific problems it struggles with most, which pushes it to master those problems specifically. The paper's ablation showing that both stages are necessary (Table 4) confirms that neither broad coverage alone nor deep sampling alone achieves the best results — the combination, in sequence, is what works.

#### Evaluation Protocol and Contamination Controls

The paper's evaluation framework is designed to test both in-distribution and out-of-distribution generalization while ensuring that performance gains are not driven by data leakage. The choice of benchmarks and the distinction between "contaminated" and "uncontaminated" sets is central to the paper's credibility.

**Benchmark suite.** Five benchmarks are used:

1. **LiveCodeBench 08-11:** 166 problems. The paper states this is "uncontaminated throughout the SFT and RL stages" — none of these problems appeared in any training data.
2. **LiveCodeBench V5:** 167 problems. Also uncontaminated.
3. **LiveCodeBench V6:** 175 problems. This benchmark was "exposed during the second RL stage" — meaning the Stage 2 training data is drawn from this set, so performance on LiveCodeV6 is partially in-distribution and should be interpreted with caution. The paper is transparent about this contamination, noting it explicitly in Section 4.1.
4. **LeetCode Weekly OJ (32 problems):** Problems from LeetCode weekly contests released *after* the training data collection cutoff. Since LeetCode releases new problems each week, selecting contests that postdate the training data ensures these are genuinely unseen during both SFT and RL. This is the primary out-of-distribution generalization test.
5. **Codeforces OJ (33 problems):** Similarly, problems from Codeforces contests released after the training data cutoff. These are generally harder than LeetCode problems and provide the most stringent test of the model's competitive-programming capability.

**Metrics.** The paper reports two metrics per benchmark:

- **Pass@1:** The fraction of problems for which the model's first generated solution passes all test cases. This is the strictest metric — it measures the model's ability to produce a correct solution on the first attempt without any retries.
- **Avg@1:** Appears to be synonymous with Pass@1 in most tables (Table 1 uses both "Pass@10" and "Avg@1" in the same columns, suggesting "Avg@1" is the average pass rate at one attempt, i.e., Pass@1).
- **Pass@10:** The fraction of problems for which at least one of the first 10 generated solutions passes all test cases. This is reported only for the LeetCode and Codeforces evaluations in Table 1, not for the LiveCode benchmarks.

**Contamination control.** The paper's primary defense against data leakage is temporal: the LeetCode and Codeforces weekly contests used for evaluation are "released after our training data collection cutoff" (Section 4.1). This means that regardless of what data was in the open-source training corpora used for SFT and RL, these specific problems did not exist at training time and cannot have been memorized. The LiveCode08-11 and LiveCodeV5 benchmarks serve as additional uncontaminated evaluations, though the paper doesn't specify the temporal relationship between these benchmarks and the training data.

**Why LiveCodeV6 evaluation is still reported despite contamination.** The paper includes LiveCodeV6 results (Table 2) even though it was used in Stage 2 training. This is standard practice in RLVR research — reporting both training-set and held-out performance provides a complete picture of learning dynamics. The contaminated results show what the model achieves on problems it was explicitly trained to improve on (a measure of optimization success), while the uncontaminated results show what transfers to novel problems (a measure of generalization). The gap between LiveCodeV6 (0.703) and the uncontaminated benchmarks (0.653 on LeetCode, 0.182 on Codeforces) reveals the expected pattern: the model performs better on problems it was trained on, but the improvement transfers substantially to unseen problems, especially on LeetCode Weekly (13.0% relative improvement over SFT).

**The SFT model's unusual pass@10 vs. Avg@1 pattern.** Table 1 reports the SFT model's pass@10 on LeetCode Weekly as 96.88% — meaning that given 10 attempts, the model finds a correct solution on all but one of the 32 problems. Yet its Avg@1 is only 57.81%. This gap of 39 percentage points between pass@10 and pass@1 quantifies the model's unreliability: it *can* solve nearly all the problems, but it usually doesn't on the first try. This is a hallmark of a model with a reasonable proposal distribution (correct solutions are in the support) but poor calibration (correct solutions are not the most likely). RL training should narrow this gap by making successful solution patterns more probable and unsuccessful patterns less probable — and indeed, the final RL model's pass@1 on LeetCode Weekly (0.653) substantially closes the gap, though a 31-point gap to the SFT's pass@10 (96.88%) remains, indicating that even after RL the model still benefits from multiple attempts on some problems.

## 4. Key Insights and Innovations

### Innovation 1: Data Curation and Curriculum Design Are First-Class Design Dimensions in RLVR, Not Just Algorithmic Tweaks

The paper's most fundamental conceptual move is reframing what matters for RLVR success. Since DeepSeek R1 (Guo et al., 2025) demonstrated that GRPO with verifiable rewards could induce reasoning capabilities, the dominant research response has been algorithmic: DAPO (Yu et al., 2025) enhanced GRPO's performance through better optimization tricks, VAPO (Yue et al., 2025) proposed an improved PPO variant, ProRL (Liu et al., 2025) explored GRPO optimization hacks, and GSPO (Zheng et al., 2025) addressed MoE-specific stability issues. The implicit assumption across this line of work is that the bottleneck is the optimization procedure — that better algorithms will unlock better reasoning, and that data is an input to be maximized in volume and diversity.

This paper challenges that assumption directly, not through argument but through diagnostic evidence. The ablation in Table 4 is the pivotal demonstration: applying the same GRPO algorithm to different data configurations produces not just different levels of improvement but qualitatively different outcomes — from catastrophic collapse (a 48.8% drop on LeetCode Weekly when training on all 175 LiveCodeV6 problems without filtering) to substantial gains (a 58.3% relative improvement on Codeforces with the full two-stage pipeline). The algorithm is held constant; the data curation choices alone produce a swing of over 100 percentage points in relative performance. This is not an incremental finding — it is evidence that **data curation is not merely an input to the algorithm but a design space of equal or greater importance**, and that getting it wrong can destroy performance in ways that no amount of algorithmic sophistication can recover.

What makes this genuinely novel rather than obvious is the specificity of the failure mode. The common intuition in machine learning is that more diverse training data is better — that including a wider range of examples prevents overfitting and improves generalization. The paper's central counterexample to this intuition is the "RL with all LiveCodeV6 dataset" condition: training on *more* problems (all 175, including easy ones) produces *worse* results than training on *fewer* problems (the dynamically filtered hard subset of 25–72). The mechanism — that easy problems dilute the gradient signal because they provide no meaningful within-group advantage variance while still consuming the generation budget — is non-obvious and, to the authors' knowledge, previously undocumented in the RLVR literature. It suggests that RLVR training has qualitatively different data requirements than supervised learning: in SFT, seeing more examples is generally helpful because each example provides a direct supervised signal; in RLVR, seeing examples the model already solves provides nearly zero learning signal while occupying slots that could be used for more informative examples. This is a **fundamental reframing** of how to think about RLVR data, not an incremental refinement.

The paper's elevation of data curation to a first-class design dimension is reinforced by the SFT data construction analysis (Table 3). The Twice Hard Learning strategy — which doubles the exposure of hard examples while keeping the total token budget constant — outperforms both the Basic SFT Strategy (trained on all 1.27M examples) and the Arena Learning Strategy (trained on 470K filtered examples without duplication). This demonstrates that token budget allocation, not just total budget size, determines SFT quality — and that the same principle (concentrate resources on hard examples) applies across both SFT and RL stages, albeit through different mechanisms (duplication in SFT, difficulty filtering in RL). The paper doesn't just claim that data curation matters; it provides a coherent **design philosophy** — identify hard examples, allocate disproportionate resources to them, and dynamically update the definition of "hard" as the model improves — that spans the entire training pipeline.

### Innovation 2: The "Capability Ceiling" as a Diagnostic Concept for Why Standard RL Fails on Hard Problems

The paper introduces a specific, empirically grounded diagnostic concept: the **capability ceiling**. The idea is that standard RLVR training — applied uniformly across all problem difficulties with moderate rollout budgets — creates an upper bound on model performance that is determined not by the model's ultimate potential but by the interaction between its initial pass rate on hard problems and the limited exploration budget per training step. The model plateaus not because it cannot learn to solve hard problems, but because the training procedure never provides it with enough positive examples to learn from.

The diagnostic evidence for this concept is Figure 5 in Section 4.5. When problems are clustered by their initial rollout accuracy (using 8 rollouts as the evaluation metric, matching the standard GRPO configuration) and training dynamics are tracked, the pattern is stark: medium-accuracy problems improve rapidly, high-accuracy problems improve modestly (they are already near ceiling), and low-accuracy problems barely move at all — their training curves are essentially flat lines. This is not a question of insufficient training steps; the curves remain flat over the entire training duration. The problem is structural: with only 8 rollouts and an initial pass@1 of, say, 5%, the probability that a training batch contains at least one correct solution is only `$1 - (1-0.05)^8 \approx 0.34$`. In two-thirds of batches, the model receives only negative feedback — gradients pushing it away from incorrect solutions but no gradients pulling it toward the correct solution space. The model learns what *not* to do but never sees what it *should* do, and over time its probability mass diffuses away from the correct region without being anchored there.

What makes this concept innovative is that it reframes the hard-problem learning challenge from an **architecture or algorithm problem** (the model isn't smart enough; the optimizer isn't good enough) to a **sampling budget problem** (the model isn't given enough chances to stumble onto the correct solution). The implication is that the bottleneck is not the model's capacity or the RL algorithm's efficiency but the exploration budget per training step — and that this budget must be scaled with problem difficulty, not held constant. The few-case and single-case experiments in Appendix A (Figures 6–8) validate this reframing directly: increasing the rollout count from 8 to 64 dramatically accelerates learning on hard cases, and some problems that appear "frozen" at 8 rollouts become learnable with 64. Figure 6 shows this most clearly — higher rollout counts produce steeper learning curves for single hard cases.

This concept has implications beyond the paper's specific implementation. It suggests that the standard practice in RLVR research — reporting results with a fixed rollout budget (typically 8 or 16) across all problems — systematically underestimates what the model can achieve, and that the apparent "diminishing returns" of RL training on hard benchmarks like AIME may partly reflect insufficient rollout budgets rather than fundamental limits. The capability ceiling is not a property of the model but a property of the training procedure, and it can be raised by allocating more sampling compute to hard problems. This is a **diagnostic contribution**: the paper gives the field a concept and a measurement methodology (clustering by initial accuracy, tracking per-cluster improvement) for identifying when and why RL training is leaving performance on the table.

### Innovation 3: Entropy Expansion as a Prerequisite for Hard-Problem Specialization, Not an Independent Objective

The two-stage structure — broad entropy expansion followed by targeted hard-problem training — might appear to be a straightforward combination of two independently useful techniques. The paper's critical insight, validated by the ablation in Table 4, is that they are not independent: the entropy expansion stage is a **prerequisite** for the hard-focus stage to work without destroying generalization, not merely a complementary addition.

The evidence is the ablation condition "RL without First Stage Only Second Stage" (Table 4, row 3). This configuration applies the hard-focus curriculum directly to the SFT model, skipping entropy expansion entirely. The result is a **divergent pattern**: the model improves substantially on LiveCodeV6 (the in-distribution training data, +25.9% relative improvement from 0.549 to 0.691) but **degrades** on out-of-distribution benchmarks like LeetCode Weekly OJ (-4.8%, from 0.578 to 0.550). This is a clean demonstration of overfitting — the model learns to solve the specific hard problems it was trained on but loses the broader competitive-programming capability that the SFT model possessed.

Why does this happen? The mechanism the paper implies (though doesn't fully articulate) is that the SFT model's low entropy and repetitive generation patterns (Pathologies 1 and 2 from Section 3.2) make it vulnerable to destructive specialization. When trained exclusively on hard problems with large rollout budgets, the model can improve on those problems by narrowing its output distribution further — committing more strongly to the solution patterns that work on the training set. But without the diversification provided by Stage 1, this narrowing comes at the expense of the general solution strategies that work across diverse problem types. The model becomes a specialist on LiveCodeV6-style problems at the cost of its generalist capabilities.

Stage 1 prevents this by forcing the model to maintain a broad output distribution. Training on 9K uniformly distributed problems with moderate rollout budgets teaches the model that many different solution patterns can be correct — dynamic programming for some problems, greedy algorithms for others, graph traversals for still others — and reinforces the meta-skill of adapting strategy to problem type. When the model then enters Stage 2's hard-focus training, it specializes within a foundation of maintained diversity rather than from a starting point of already-narrow behavior. The result is improvement on hard problems that transfers to novel problems, as evidenced by the full two-stage model's gains on LeetCode Weekly (+13.0%) and Codeforces (+58.3%) — benchmarks that were temporally separated from all training data.

This insight reframes the role of entropy in RLVR training. Prior work has generally treated output diversity as an independently desirable property — models should be creative, should avoid mode collapse — but the paper shows that entropy is **functionally necessary** for curriculum-based specialization to generalize. Without it, hard-problem training doesn't just fail to transfer; it actively reduces generalization. This transforms entropy expansion from a nice-to-have into an essential architectural component of any difficulty-based RLVR curriculum, with a specific causal role: preserving the breadth of solution strategies that specialization would otherwise erode.

### Innovation 4: The Pre-GRPO Dynamic Filtering Mechanism — Difficulty Is Model-Relative, Not Absolute

The paper's Pre-GRPO filtering procedure introduces a subtle but important conceptual shift: **difficulty is defined relative to the current model's capabilities, not by an external, static classification**. This departs from the dominant approach in prior RLVR work, where problems are categorized as easy, medium, or hard based on fixed heuristics (problem source, human ratings, or a one-time model evaluation) and then treated as static bins throughout training (Seed et al., 2025; Yu et al., 2025; Li et al., 2025b).

The problem with static difficulty categorization is that it cannot adapt to what the model actually learns. A problem classified as "hard" at the start of training might become easy for the model after a few thousand steps — but if the curriculum keeps treating it as hard and allocating disproportionate resources to it, those resources are wasted on an already-solved problem. Conversely, a problem classified as "medium" might prove unexpectedly stubborn for a particular model, yet the static curriculum never gives it the focused attention it needs. Static difficulty is a property of the problem; model-relative difficulty is a property of the (problem, model) pair — and only the latter is relevant for deciding where to allocate training compute.

Pre-GRPO operationalizes model-relative difficulty through a simple mechanism: after each training phase, the model is evaluated on all problems in the current set, and only those with the lowest pass rates are carried forward. This means a problem graduates out of the training set when — and only when — the model actually masters it. No problem is permanently labeled hard; no problem is prematurely dropped because of an initial misclassification. The curriculum adapts to the model's actual learning trajectory.

What makes this innovative is not the mechanism itself — curriculum learning with dynamic difficulty adjustment has been explored in other contexts — but its application to RLVR for reasoning and the evidence that it is **necessary for stable training**, not just helpful. The ablation condition "RL with all LiveCodeV6 dataset" (Table 4) demonstrates this necessity dramatically: training on all 175 problems without dynamic filtering causes catastrophic collapse (-48.8% on LeetCode Weekly). This is not a small efficiency gain from better curriculum design; it is the difference between a functioning training run and a completely broken one. Dynamic difficulty filtering is not an optimization — it is a stability requirement for RLVR on mixed-difficulty problem sets.

The three-phase progressive schedule (72 → 50 → 25 problems, with correspondingly reduced rollout budgets of 80 → 64 → 32) reveals an additional insight: the optimal allocation of sampling compute shifts as the model improves. Early in Stage 2, when many problems are genuinely hard for the model, a large rollout budget across a moderately sized hard-problem set is appropriate — the model needs the exploration capacity to find correct solutions on problems it's still struggling with. As training progresses and the model masters some problems (which are then dropped), the remaining problems are the truly stubborn ones, and the model benefits from increasingly focused attention — fewer problems, but each receiving a still-substantial rollout budget to ensure occasional successes. The paper doesn't fully optimize this schedule (it's hand-designed, not learned), but the empirical success of the three-phase structure suggests that matching the rollout budget to the remaining problem count — keeping the per-problem sampling high as the problem set shrinks — is a key design principle.

This insight reframes how to think about curriculum learning for RLVR: the goal is not to train on hard problems, but to train *exclusively* on problems the model cannot yet solve, and to continuously update the definition of "cannot yet solve" as the model improves. This is a more demanding standard than typical curriculum learning, and it requires the kind of dynamic evaluation and filtering that Pre-GRPO provides. The paper's contribution is demonstrating that this standard is not just aspirational but **operationally necessary** for RLVR on competitive programming, and providing a practical implementation that achieves it.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper constructs a multi-benchmark evaluation suite. The primary in-distribution validation sets are **LiveCodeBench 08-11** (166 problems, uncontaminated throughout SFT and RL), **LiveCodeBench V5** (167 problems, uncontaminated), and **LiveCodeBench V6** (175 problems, partially contaminated since Stage 2 training data is drawn from it). The primary out-of-distribution generalization benchmarks are **LeetCode Weekly OJ** (32 problems) and **Codeforces OJ** (33 problems), both sourced from weekly contests released *after* the training data collection cutoff to prevent data leakage (Section 4.1).

- **Base model(s).** The primary experiments use **Qwen2.5-32B-Instruct** (Hui et al., 2024), a 32-billion-parameter dense transformer. The paper also reports scaling experiments on an **internal large-scale Mixture-of-Experts (MoE) model** (Section 4.6) to validate transferability to much larger architectures. Qwen2.5-32B is chosen as representative of the 32B-scale reasoning model class, and the paper compares against similarly-sized open-source models (QwQ-32B, OpenReasoning-Nemotron-32B) as well as substantially larger systems (DeepSeek V3.1, Seed1.6-0715, Qwen3-235B).

- **Metrics.** The primary metric across all benchmarks is **Pass@1** (referred to interchangeably as **Avg@1**), defined as the fraction of problems for which the model's first generated solution passes all hidden test cases. Table 1 additionally reports **Pass@10** for the LeetCode and Codeforces evaluations, defined as the fraction of problems for which at least one of the first 10 generated solutions is correct. All correctness is determined by executing the generated code against the problem's test suite — this is an objective, binary pass/fail signal with no partial credit.

- **Baselines.** The paper compares against the following models, all evaluated under their standard configurations (Table 2): **DeepSeek V3.1** (64k context, Taşyürek et al., 2025), **Seed1.6-0715** (64k context, Seed et al., 2025), **Qwen3-235B-2507** (64k context, Yang et al., 2025), **QwQ-32B** (32k context), and **OpenReasoning-Nemotron-32B** (32k context). The **SFT model** (the model produced by the full SFT pipeline before any RL training) serves as the primary within-family baseline for measuring RL improvements. For ablation purposes (Table 4), additional baselines include: RL applied directly to the SFT model on all 175 LiveCodeV6 problems without filtering, RL on all 9K Stage 1 problems without Stage 2, and Stage 2 applied directly to the SFT model skipping Stage 1.

- **Generation budget / compute accounting.** The paper measures RL training compute through two key parameters: **rollouts per prompt** (8 in Stage 1, 64–80 in Stage 2) and **total sequence length** (24K tokens in Stage 1, 32K tokens in Stage 2). Generation budget per training step is the product of batch size, rollouts per prompt, and maximum sequence length. For evaluation, the standard Pass@1 metric uses a budget of 1 generation per problem; Pass@10 uses 10 generations. The paper does not report total FLOPs or wall-clock training time, making precise compute comparisons across methods difficult.

- **Cross-validation / statistical protocol.** The paper does not employ formal cross-validation. Instead, it relies on temporal separation of evaluation benchmarks: LeetCode and Codeforces weekly contests are drawn from competitions held after the training data collection cutoff (Section 4.1), ensuring these problems could not have appeared in any training data regardless of the data curation process. LiveCode08-11 and LiveCodeV5 are stated to be uncontaminated throughout SFT and RL, though no temporal verification mechanism is specified. LiveCodeV6 is explicitly acknowledged as partially contaminated (used in Stage 2 training). No confidence intervals, standard errors, or statistical significance tests are reported for any result.

### Main Quantitative Results

#### SFT Baseline Performance and the Pass@1 vs. Pass@10 Gap

The SFT model establishes the starting point for all RL experiments (Table 1). On LeetCode Weekly OJ (32 problems), the SFT model achieves **Pass@10 of 96.88%** and **Avg@1 of 57.81%**. On Codeforces OJ (33 problems), it achieves **Pass@10 of 24.24%** and **Avg@1 of 11.52%**. For comparison, DeepSeek V3.1 achieves Pass@10 of 96.88% and Avg@1 of 68.75% on LeetCode, and 33.33% Pass@10 and 16.06% Avg@1 on Codeforces. Seed1.6-0715 achieves 96.88% Pass@10 and 74.38% Avg@1 on LeetCode, and 39.39% Pass@10 and 18.79% Avg@1 on Codeforces.

The key diagnostic from these numbers is the **39-percentage-point gap between Pass@10 and Pass@1 on LeetCode Weekly** for the SFT model (96.88% vs. 57.81%). This means the model can find correct solutions for nearly every LeetCode problem given 10 attempts, but its first attempt is correct less than 60% of the time. On the harder Codeforces problems, the Pass@10 to Pass@1 gap is narrower (24.24% vs. 11.52%, a 12.7-point gap), but the absolute performance is much lower. The SFT model's pass@10 on Codeforces (24.24%) substantially trails DeepSeek V3.1 (33.33%) and Seed1.6-0715 (39.39%), indicating that distillation alone fails to transfer strong performance to the hardest problems.

#### SFT Ablation: Data Curation Strategies (Table 3)

Table 3 compares three SFT data construction approaches evaluated on all five benchmarks:

- **Basic SFT Strategy** (all 1.27M prompts): achieves 0.582 on LiveCode08-11, 0.603 on LiveCodeV5, 0.545 on LiveCodeV6, 0.558 on LeetCode Weekly, and 0.112 on Codeforces.
- **Arena Learning Strategy** (470K hard-filtered prompts, no duplication): achieves 0.600, 0.598, 0.542, 0.553, and 0.111 respectively. Despite using >60% less data, performance is comparable — slightly better on LiveCode08-11 (+0.018), slightly worse on LiveCodeV5 (-0.005) and LiveCodeV6 (-0.003), and essentially tied on LeetCode Weekly (-0.005) and Codeforces (-0.001).
- **Twice Hard Learning Strategy** (470K hard-filtered prompts with hard problems duplicated once): achieves 0.602, 0.594, 0.549, 0.578, and 0.115 — outperforming both alternatives on all benchmarks except LiveCodeV5, where Arena Learning is 0.004 points higher.

The key finding: allocating additional training token budget to hard examples (via duplication) improves performance across all out-of-distribution benchmarks, with the largest gain on LeetCode Weekly (+2.0 percentage points over Basic SFT, from 0.558 to 0.578, and +2.5 points over Arena Learning, from 0.553 to 0.578). The Twice Hard strategy is the SFT configuration used for all subsequent experiments.

#### Overall RL Performance: Two-Stage Pipeline vs. Baselines (Table 2)

Table 2 presents the headline results comparing the SFT model, the RL Stage 1 model, and the final RL model against external baselines:

**SFT model Pass@1:** LiveCode08-11: 0.602; LiveCodeV5: 0.594; LiveCodeV6: 0.549; LeetCode Weekly: 0.578; Codeforces OJ: 0.115.

**RL Stage 1 model Pass@1:** 0.625 (+0.023), 0.627 (+0.033), 0.634 (+0.085), 0.603 (+0.025), 0.112 (-0.003). Stage 1 improves all benchmarks except Codeforces, where it slightly regresses.

**Final RL model Pass@1:** 0.699, 0.697, 0.703, 0.653, 0.182. The relative improvements over the SFT baseline are +16.1% on LiveCode08-11, +17.3% on LiveCodeV5, +28.1% on LiveCodeV6, +13.0% on LeetCode Weekly, and **+58.3% on Codeforces OJ** — the largest relative gain.

**Comparison to external baselines (all at Pass@1):** The final RL model (32B parameters, 32k context) achieves **0.699 on LiveCode08-11** vs. DeepSeek V3.1's 0.692, Seed1.6-0715's 0.803, and Qwen3-235B's 0.681. On **LiveCodeV5**, it scores **0.697** vs. 0.713, 0.824, and 0.713 respectively. On **LiveCodeV6**, it achieves **0.703** vs. 0.693, 0.770, and 0.646. On **LeetCode Weekly**, it scores **0.653** vs. 0.688, 0.743, and 0.688. On **Codeforces OJ**, it achieves **0.182** vs. 0.161, 0.188, and 0.200.

The 32B model thus matches or exceeds the 64k-context, much larger DeepSeek V3.1 on three of five benchmarks (LiveCode08-11: 0.699 vs. 0.692; LiveCodeV6: 0.703 vs. 0.693; Codeforces: 0.182 vs. 0.161), trails Seed1.6-0715 on all benchmarks, and is competitive with Qwen3-235B on LiveCode benchmarks but behind on LeetCode Weekly (0.653 vs. 0.688) and Codeforces (0.182 vs. 0.200). Against 32B-class models, the improvement is decisive: +0.076 over OpenReasoning-Nemotron-32B on LiveCode08-11, +0.079 on LiveCodeV6, +0.044 on LeetCode Weekly, and +0.050 on Codeforces OJ.

#### RL Ablation: Two-Stage Design vs. Single-Stage Variants (Table 4 and Figure 4)

Table 4 reports Pass@1 for four RL configurations, isolating the contribution of each stage:

**Configuration 1: "RL with all LiveCodeV6 dataset"** — GRPO applied directly to the SFT model on all 175 LiveCodeV6 problems (no Stage 1, no difficulty filtering). Results: LiveCode08-11: 0.506; LiveCodeV5: 0.512; LiveCodeV6: 0.522; LeetCode Weekly: 0.296; Codeforces: 0.105. Compared to the SFT baseline (0.602, 0.594, 0.549, 0.578, 0.115), this represents **regressions on every benchmark**: -0.096, -0.082, -0.027, -0.282, and -0.010. The 48.8% drop on LeetCode Weekly (0.578 → 0.296) is catastrophic.

**Configuration 2: "RL with all 9k data"** — GRPO on the full 9K uniformly distributed problem set at 32k context (no Stage 2). Results: 0.676, 0.688, 0.675, 0.592, 0.102. Compared to SFT, this improves LiveCode benchmarks (+0.074, +0.094, +0.126) and LeetCode Weekly (+0.014) but **degrades Codeforces** (-0.013). This configuration outperforms the SFT model on most benchmarks but substantially underperforms the full two-stage method on LeetCode Weekly (0.592 vs. 0.653) and Codeforces (0.102 vs. 0.182).

**Configuration 3: "RL without First Stage Only Second Stage"** — hard-focus curriculum applied directly to the SFT model, skipping entropy expansion entirely. Results: 0.636, 0.626, 0.691, 0.550, 0.142. On LiveCodeV6 (contaminated training data), this achieves 0.691 — close to the full method's 0.703 (+25.9% over SFT's 0.549). However, on **LeetCode Weekly**, it drops to 0.550 — a **4.8% degradation from the SFT baseline's 0.578**. On Codeforces, it achieves 0.142 — better than SFT (0.115) but substantially worse than the full method (0.182).

**Configuration 4: "Our Method"** — full two-stage pipeline. Results: 0.699, 0.697, 0.703, 0.653, 0.182 — the best result across all five benchmarks.

**Configuration 5: "Our Method with More Harder Samples in Stage 2"** — the full pipeline augmented with an additional 109 hard cases from an internal dataset. Results: 0.712, 0.707, 0.743, 0.678, 0.188 — further improvements across all benchmarks, with LiveCodeV6 reaching 0.743 (+35.3% over SFT's 0.549) and LeetCode Weekly reaching 0.678 (+17.3% over SFT's 0.578).

Figure 4 tracks training dynamics for selected configurations, plotting Pass@1 on LiveCodeV6 (part a) and LiveCode08-11 (part b) over training steps. The full two-stage method shows steady improvement on both metrics throughout training. The "Second Stage Only" configuration improves on LiveCodeV6 but **diverges negatively** on LiveCode08-11 (the uncontaminated set) compared to the full method, visually confirming the generalization gap. The "RL with all LiveCodeV6" configuration shows **degrading performance** on both metrics during training — the curves trend downward, consistent with the catastrophic collapse observed in Table 4.

#### Training Dynamics: Difficulty-Clustered Accuracy Evolution (Figure 5)

Figure 5 clusters LiveCodeV6 problems by their **initial rollout accuracy** at the start of standard RL training (using rollout = 8 as the evaluation metric) and tracks training accuracy over time for each cluster. The clusters are: problems with low initial accuracy, medium initial accuracy, and high initial accuracy.

The **medium-accuracy cluster** shows the most rapid improvement, with training accuracy rising steeply over the training steps. The **high-accuracy cluster** shows modest gains — these problems are already largely solved, so improvement is limited. The **low-accuracy cluster** shows **stagnant, essentially flat training curves** — accuracy barely increases over the entire training duration. This is the "capability ceiling" diagnostic: standard RL training with 8 rollouts fails to improve performance on problems where the model's initial pass rate is low, because insufficient rollouts mean the model rarely sees correct solutions and thus receives almost exclusively negative feedback with no positive gradient toward the correct solution space.

#### Few-Case and Single-Case Training Analysis (Appendix A, Figures 6–8)

Figure 7 tracks the per-case accuracy evolution when training on only four randomly selected LiveCodeV6 problems using GRPO with rollout = 8. The trajectories diverge sharply: Cases 2 and 3 improve rapidly from ~15–22% to ~80% accuracy within 60 steps. Case 1 improves slowly from 12% to 36.7%. Case 4 remains **frozen at approximately 12.5%** throughout training — essentially no learning occurs.

Figure 8 compares single-case training (training on Case 1 alone) to the four-case training setting. When Case 1 is trained in isolation, its learning trajectory becomes **noticeably slower** than when trained alongside Cases 2–4. The paper interprets this as evidence of positive transfer — co-training on diverse problems facilitates learning even on stubborn cases — though the effect size is not quantified.

Figure 6 isolates the effect of rollout count on single-case training performance. Higher rollout counts produce **steeper learning curves** on the hard case. The paper does not provide exact numbers for the final accuracy at different rollout counts, but the visual trend is clear: rollout = 64 yields faster improvement than rollout = 32, which yields faster improvement than rollout = 8. The paper also reports two qualitative observations from this experiment: (1) training on a single hard case has "negligible impact on the performance of other cases, including easy ones," and (2) "learning a hard case can improve generalization to other hard cases," suggesting some positive transfer within the hard-problem category specifically.

#### Scaling Trends on Large-Scale MoE Model (Table 5, Section 4.6)

Table 5 reports results from applying the two-stage pipeline to an internal large-scale MoE model, trained with a larger context window (64k) and larger rollout budgets (16 in Stage 1, 64 in Stage 2):

**SFT model (64k):** LiveCode08-11: 0.681; LiveCodeV5: 0.692; LiveCodeV6: 0.656; LeetCode Weekly: 0.627; Codeforces: 0.155.

**RL Stage 1 (32k train, 64k test):** 0.690, 0.740, 0.665, 0.611, 0.123. Relative to SFT: +1.32%, +6.94%, +1.37%, **-2.55%**, **-20.65%**. Stage 1 improves LiveCode benchmarks but substantially degrades the out-of-distribution competitive programming benchmarks.

**RL Stage 2 (64k, 50 steps total):** 0.708, 0.744, 0.737, 0.722, 0.194. Relative to SFT: +3.96%, +7.51%, +12.35%, +15.17%, +25.16%. Stage 2 recovers and substantially exceeds the SFT baseline on all benchmarks, with the largest absolute gain on LeetCode Weekly (+0.095) and the largest relative gain on Codeforces (+25.16%).

The MoE scaling results mirror the Qwen2.5-32B pattern: Stage 1 produces mixed results (improvements on some benchmarks, regressions on competitive programming), and Stage 2 provides substantial gains across all metrics. The paper notes that "these experiments were constrained by computational resources, and training was not continued to full convergence," suggesting that the reported numbers may underestimate the approach's potential at scale. The Stage 2 training used only 50 total steps across three phases (20 + 20 + 10), significantly fewer than the 32K steps reported for the Qwen2.5-32B experiments.

### Ablation Studies and Robustness Checks

**SFT data quantity vs. data curation (Table 3):** The Arena Learning Strategy, which reduces training data from 1.27M to 470K prompts (a >60% reduction) by filtering for hard examples, maintains comparable performance to training on the full dataset (0.600 vs. 0.582 on LiveCode08-11; 0.598 vs. 0.603 on LiveCodeV5; 0.553 vs. 0.558 on LeetCode Weekly). This demonstrates that data curation — not data volume — is the binding constraint, and that easy examples provide minimal marginal benefit in SFT once a sufficient quantity of hard examples is present. However, the Arena Learning Strategy slightly underperforms the Basic SFT Strategy (0.553 vs. 0.558 on LeetCode Weekly, -0.005), which the paper attributes to "an insufficient training token budget" — the 470K filtered dataset has fewer total tokens than the full 1.27M set, and this deficit is only compensated by the Twice Hard duplication strategy, which restores the token budget by oversampling hard examples.

**Hard example duplication in SFT (Table 3):** The Twice Hard Learning Strategy (+duplication of hard examples) improves over the Arena Learning Strategy on all benchmarks: +0.002 on LiveCode08-11, -0.004 on LiveCodeV5 (slight regression, the one exception), +0.007 on LiveCodeV6, +0.025 on LeetCode Weekly, and +0.004 on Codeforces. The largest gain is on LeetCode Weekly (+0.025, from 0.553 to 0.578), confirming that allocating additional token budget to hard examples specifically improves out-of-distribution generalization to competitive programming tasks.

**Removing Stage 1 (entropy expansion) from the pipeline (Table 4, row 3):** Applying the hard-focus curriculum directly to the SFT model produces a divergent outcome: improvement on in-distribution LiveCodeV6 (+0.142 over SFT, from 0.549 to 0.691) but **degradation on out-of-distribution LeetCode Weekly** (-0.028, from 0.578 to 0.550). This is a critical robustness check: it demonstrates that the Stage 2 curriculum alone is sufficient to improve performance on problems the model is directly trained on, but that this improvement overfits and damages generalization unless preceded by the entropy expansion stage. The finding also validates that the full method's gains on LiveCode benchmarks are not solely attributable to Stage 2 — they represent a synergistic combination where Stage 1 provides generalization robustness that Stage 2's specialization would otherwise erode.

**Removing Stage 2 (hard-focus curriculum) from the pipeline (Table 4, row 2):** Training only with Stage 1 RL on all 9K prompts (32k context, no difficulty filtering) improves LiveCode benchmarks (+0.074 to +0.126 over SFT) and LeetCode Weekly (+0.014) but **degrades Codeforces** (-0.013, from 0.115 to 0.102). This confirms that Stage 1 alone provides broad improvements but cannot push the hard-problem frontier — the Codeforces regression suggests that entropy expansion without targeted hard-problem training may actually dilute the model's capability on the most difficult problems, likely because the model spreads its probability mass more evenly (higher entropy) without the concentrated reinforcement needed to master challenging algorithmic patterns.

**Difficulty filtering in RL is necessary, not optional (Table 4, row 1):** Training on the full, unfiltered LiveCodeV6 dataset (all 175 problems, mixed difficulty) causes catastrophic performance degradation — a 48.8% drop on LeetCode Weekly (0.578 → 0.296). This is the most dramatic ablation result in the paper and serves as the primary evidence that difficulty-aware data curation is not just helpful but **required for stable RL training** in this setting. The degradation is not limited to out-of-distribution benchmarks: even LiveCodeV6 itself decreases slightly (0.549 → 0.522, a 4.9% drop), indicating that the unfiltered training actually *unlearns* the SFT model's capabilities rather than simply failing to improve them.

**Increasing hard samples in Stage 2 (Table 4, row 5):** Augmenting the Stage 2 curriculum with 109 additional hard cases from an internal dataset consistently improves results: +0.013 on LiveCode08-11, +0.010 on LiveCodeV5, +0.040 on LiveCodeV6, +0.025 on LeetCode Weekly, and +0.006 on Codeforces. The monotonic improvement across all benchmarks suggests that the model's capability frontier continues to expand as more challenging problems are incorporated, and that the Pre-GRPO mechanism scales effectively — more hard problems in the curriculum produce more learning, without the performance collapse observed when easy problems are included (Configuration 1). This is a non-obvious finding: it could have been the case that a certain number of hard problems saturates the model's learning capacity and additional hard problems provide diminishing returns, but the paper's results show continued improvement.

**Single-case training with varying rollout budgets (Figure 6):** Higher rollout counts accelerate learning on hard cases when training in isolation. The paper does not quantify final accuracy differences but states that "higher rollout counts accelerate learning." An additional observation from the single-case experiments: training on one hard case has negligible effect on performance on other cases (including easy ones), but "learning a hard case can improve generalization to other hard cases" — this provides weak evidence for positive transfer within difficulty tiers, though the sample size (4 cases total) is too small for strong conclusions.

**MoE scaling validation (Table 5):** The two-stage pattern replicates at larger scale: Stage 1 produces mixed results (improvements on some LiveCode benchmarks, regressions on LeetCode and Codeforces), Stage 2 recovers and substantially exceeds the SFT baseline across all benchmarks. The relative improvement pattern is consistent with the 32B results — largest gains on the hardest benchmarks (Codeforces: +25.16% on MoE, +58.3% on 32B) and more modest gains on the easier LiveCode benchmarks (+3.96% to +12.35% on MoE, +16.1% to +28.1% on 32B). The MoE experiments used only 50 total Stage 2 steps and were not trained to convergence, making the demonstrated gains a lower bound.

### Critical Assessment

#### What the Experiments Actually Demonstrate

**Claim from the executive summary: "The two-stage RL framework achieves state-of-the-art performance among 32B models."** The experiments in Table 2 support this claim for the specific benchmarks tested. The final RL model achieves Pass@1 of 0.653 on LeetCode Weekly and 0.182 on Codeforces, substantially outperforming OpenReasoning-Nemotron-32B (0.609 and 0.132) and QwQ-32B (0.472 and 0.124). The margin is large enough (0.044–0.050 on LeetCode, 0.050–0.058 on Codeforces) that it is unlikely to be noise, though the absence of confidence intervals or statistical tests prevents formal confirmation. However, the claim is limited to the specific evaluation sets used: the LeetCode and Codeforces tests consist of only 32 and 33 problems respectively, making them small and potentially high-variance evaluation sets. A single lucky or unlucky problem can shift Pass@1 by ~3 percentage points on a 32-problem set. The paper would be strengthened by evaluation on larger held-out sets (e.g., 100+ problems) to reduce variance.

**Claim: "The model is comparable to much larger systems such as DeepSeek V3.1 and Seed1.6-0715."** This claim requires careful qualification. The 32B model matches or slightly exceeds DeepSeek V3.1 on LiveCode08-11 (0.699 vs. 0.692) and LiveCodeV6 (0.703 vs. 0.693), but DeepSeek V3.1's precise parameter count, architecture, and training methodology are not described in this paper — the comparison is to a previously published result from a different team with possibly different evaluation conditions. On Codeforces, the 32B model (0.182) outperforms DeepSeek V3.1 (0.161) but trails Seed1.6-0715 (0.188) and Qwen3-235B (0.200). The model clearly does not match Seed1.6-0715, which outperforms it on all five benchmarks, often by substantial margins (e.g., LiveCode08-11: 0.803 vs. 0.699, a gap of 0.104). The claim of "comparability" is most defensible for the DeepSeek V3.1 comparison and weakest for Seed1.6-0715.

**Claim: "RL training delivers 13.0% relative improvement on LeetCode Weekly and 58.3% on Codeforces over the SFT baseline."** Table 2 directly supports these numbers: LeetCode Weekly improves from 0.578 to 0.653 (+13.0%), Codeforces from 0.115 to 0.182 (+58.3%). The relative improvement on Codeforces is numerically impressive but should be interpreted in the context of low absolute performance: a gain from 11.5% to 18.2% means the model still fails on >80% of Codeforces problems on the first attempt. The relative percentage inflates the perceived magnitude of improvement when the baseline is low; an absolute gain of 6.7 percentage points on Codeforces is meaningful but not transformative.

**Claim: "Removing Stage 1 causes a 4.8% degradation on LeetCode Weekly."** Table 4, row 3 supports this: the "Second Stage Only" configuration scores 0.550 on LeetCode Weekly vs. the SFT baseline's 0.578. However, the degradation is measured relative to the SFT model, not relative to the full two-stage method. The full method achieves 0.653 on LeetCode Weekly, so skipping Stage 1 causes a loss of 0.103 (0.653 - 0.550), or roughly a 15.8% reduction from the best achievable performance. The paper's framing of a "4.8% degradation" references the drop below the SFT baseline, which is the more conservative framing but potentially understates the practical importance of Stage 1 — it is not just preventing regression but enabling the full gain.

**Claim: "Standard RL without difficulty filtering causes training collapse with up to a 48.8% drop on LeetCode Weekly."** Table 4, row 1 supports this: the "RL with all LiveCodeV6 dataset" configuration scores 0.296 on LeetCode Weekly vs. 0.578 for the SFT baseline. The drop of 0.282 absolute (48.8% relative) is indeed catastrophic and is the strongest evidence in the paper for the necessity of difficulty filtering. However, the experiment uses a specific configuration — all 175 LiveCodeV6 problems, GRPO, 24k context — and it is unclear whether the collapse would generalize to other RL algorithms, dataset sizes, or context lengths. The paper does not test whether, for example, simply increasing the rollout budget would prevent the collapse, or whether a different advantage normalization scheme (beyond standard GRPO) would stabilize training. The experiment demonstrates that *this specific configuration* fails, not that *any unfiltered RL training* fails.

---

#### Genuine Weaknesses and Missing Experiments

**Small out-of-distribution evaluation sets.** The LeetCode Weekly OJ (32 problems) and Codeforces OJ (33 problems) are the paper's primary generalization benchmarks, but each contains fewer problems than even a single difficulty bin in prior RLVR scaling studies. On a 32-problem set, the difference between 0.653 and 0.688 (the 32B model vs. DeepSeek V3.1 on LeetCode Weekly) is approximately one problem — a difference that could arise from sampling noise rather than genuine capability differences. No confidence intervals or bootstrap estimates are reported, making it impossible to assess whether the performance gaps are statistically reliable. A standard practice would be to report 95% confidence intervals or to use a larger test set (100+ problems) drawn from the same temporal window.

**No comparison to RL algorithm variants.** The paper uses GRPO throughout and argues that data curation matters more than algorithmic innovation, but it never tests this claim by comparing its data-curated GRPO against, for example, a data-curated version of DAPO (Yu et al., 2025) or VAPO (Yue et al., 2025). The claim that "data curation and curriculum design are as critical as algorithmic innovations" (Section 5) is supported only by showing that data curation matters *holding the algorithm fixed* — it does not demonstrate that data curation matters *as much as* algorithmic changes, which would require a factorial experiment varying both factors independently. A minimal version of this experiment would apply the two-stage data pipeline with an alternative RL algorithm (e.g., standard PPO with a learned value function) to determine whether the gains are algorithm-specific.

**Contaminated data used in Stage 2 evaluation.** LiveCodeV6 serves as both the training data source for Stage 2 and a reported evaluation benchmark. The paper is transparent about this (Section 4.1: "LiveCodeV6 was exposed during the second RL stage"), but the transparency does not eliminate the contamination. The LiveCodeV6 results (0.703 for the final model, +28.1% over SFT) should be interpreted as a measure of training-set optimization, not generalization. The paper's strongest generalization claims rest on the uncontaminated benchmarks (LiveCode08-11, LiveCodeV5, LeetCode, Codeforces), which do show meaningful improvements, but the contaminated LiveCodeV6 numbers are presented alongside the clean evaluations in Table 2 without differentiation, which could mislead casual readers.

**No ablation on the 24k vs. 32k context length choice.** The paper claims that Stage 1's 24k-token generation window increases entropy compared to 32k training (Figure 3), but this is never tested as an independent variable. Is the benefit of Stage 1 attributable to the sequence length constraint, the uniform problem distribution, or both? An ablation comparing Stage 1 at 24k vs. Stage 1 at 32k (all else equal) would isolate this effect. Without it, the entropy expansion hypothesis — that shorter context windows force more diverse, compressed reasoning — remains suggestive but unproven. The 24k choice could be incidental to the actual mechanism (uniform problem distribution, moderate rollout budget) rather than causal.

**The MoE scaling experiments are preliminary.** The scaling results in Section 4.6 are described as "constrained by computational resources, and training was not continued to full convergence." The Stage 2 training used only 50 total steps (20 + 20 + 10), compared to 32K steps for the Qwen2.5-32B experiments (though the "32K steps" figure in the 32B setting is ambiguous — it likely refers to total iterations across all three phases, not 32K steps per phase). The MoE results demonstrate that the two-stage pattern replicates at larger scale, but the absolute numbers cannot be compared to the 32B results because the training was terminated early. A proper scaling comparison would require training both model sizes to convergence under matched compute budgets.

**No analysis of the computational cost of Pre-GRPO evaluation.** Pre-GRPO requires evaluating pass rates on all remaining candidate problems after each phase to determine which are still "hard." This evaluation step involves generating multiple rollouts per problem and executing them against test suites — a substantial computational overhead that is not accounted for in any budget analysis. The paper does not report how much compute is spent on Pre-GRPO evaluation relative to the actual RL training. If the evaluation overhead is comparable to or larger than the training budget itself, the practical efficiency of the approach is overstated.

**The pass@10 results in Table 1 are not replicated for the RL model.** Table 1 reports Pass@10 for the SFT model (96.88% on LeetCode, 24.24% on Codeforces) but does not report Pass@10 for the final RL model, making it impossible to assess whether RL training narrows the pass@1-to-pass@10 gap (an explicit objective stated in Section 3.2). The RL model's pass@10 is never reported anywhere in the paper, leaving a key diagnostic metric unmeasured. If the RL model's pass@10 on LeetCode Weekly is, say, 100% while pass@1 is 65.3%, that would indicate the gap narrowed but did not close; if pass@10 remains at 96.88%, that would indicate the RL training actually reduced diversity (fewer problems are solvable with 10 attempts even though first-attempt accuracy improved). Neither hypothesis can be evaluated with the reported data.

---

#### Experiments That Would Have Strengthened the Paper

1. **A rollout budget sweep in both stages.** The paper argues that Stage 1 requires moderate rollout budgets (8) while Stage 2 requires large budgets (64–80), but this is never systematically tested. A grid experiment crossing Stage 1 rollout count (4, 8, 16, 32) with Stage 2 rollout count (16, 32, 64, 128) would reveal whether the optimal allocation is the one chosen, or whether other combinations work equally well. This is important because the paper's core thesis is about strategic resource allocation — but it never empirically validates that its specific allocation (8 in Stage 1, 64–80 in Stage 2) is better than alternatives at the same total compute budget.

2. **An RLHF-style "data scaling" experiment in Stage 2.** The paper shows that increasing hard samples in Stage 2 (from 25–72 to 25–72+109) improves performance, but it doesn't characterize the shape of this scaling curve. Does performance continue to improve linearly with additional hard problems, or do returns diminish? At what point does adding more hard problems stop helping? This would provide practical guidance for practitioners deciding how many hard problems to include.

3. **A direct comparison to an alternative difficulty-filtering method.** Pre-GRPO's dynamic, model-relative filtering is presented as superior to static difficulty categorization, but the paper never compares it against a static baseline — for example, training on the 72 hardest problems as determined by a one-time initial evaluation and never updating the filter. This comparison would isolate the value of dynamic filtering specifically, as opposed to simply training on hard problems.

4. **Pass@10 evaluation for the RL model.** As noted above, the absence of pass@10 for the final model leaves a key question unanswered: does RL training improve the model's pass@k scaling behavior, or does it only improve pass@1? This is directly relevant to the paper's stated goal of addressing the SFT model's pass@1-to-pass@10 gap.

5. **Transfer experiments on non-competitive-programming code tasks.** The paper evaluates exclusively on competitive programming benchmarks. Demonstrating that the two-stage approach also improves performance on standard code generation tasks (HumanEval, MBPP, SWE-bench) would distinguish between "this is a competitive-programming-specific training recipe" and "this is a general method for RLVR on code."

6. **Variance estimates.** The paper reports point estimates for all metrics without any measure of uncertainty. Given the small evaluation sets (32–175 problems per benchmark), reporting bootstrap confidence intervals or at minimum standard deviations across multiple evaluation runs would allow readers to distinguish genuine improvements from sampling noise. On the 32-problem LeetCode set, the standard error of a Pass@1 estimate is approximately `$\sqrt{p(1-p)/32}$`, which for p ≈ 0.65 is roughly 0.084 — meaning the 95% confidence interval spans approximately ±17 percentage points. At this level of uncertainty, many of the pairwise comparisons in the paper may not be statistically distinguishable.

## 6. Limitations and Trade-offs

### The Hardest 20–25% of Problems Remain Effectively Unsolved

**The assumption or constraint.** The entire RL pipeline — both entropy expansion and hard-focus curriculum — assumes that the model can eventually produce correct solutions to training problems given enough rollouts. But this assumption breaks down on problems where the base model's initial pass rate is near zero. The paper's own diagnostic in Figure 5 reveals that problems with "low initial accuracy" show **stagnant, flat training curves** over the entire training duration — the model receives exclusively negative feedback (reward = 0 for all 8 rollouts in most batches) and cannot learn. The paper acknowledges this indirectly in Appendix A: even with single-case training and 60+ steps, Case 4 remained "frozen at approximately 12.5%," and Case 1 plateaued at 36.7% despite focused training.

**The consequence.** The two-stage framework has no mechanism for solving problems that the model cannot *already* occasionally solve. The hard-focus curriculum identifies low-pass-rate problems and concentrates resources on them, but if the model's pass@1 on a problem is 0% — meaning it has never generated a correct solution in any training batch — then no amount of focused training can help because there is no positive gradient signal. The reward is binary (pass or fail all test cases), so the model receives only gradients pushing it away from incorrect solutions with no gradient pulling it toward a correct region. This creates a fundamental **capability floor**: the approach amplifies existing capability (making the model more reliable on problems it can sometimes solve) but cannot create it from scratch (making the model solve problems entirely beyond its current reach).

**What evidence exists in the paper.** The per-difficulty-cluster training dynamics in Figure 5 directly show this limitation: the low-accuracy cluster's training curve is flat. In Table 2, the final RL model achieves 0.182 on Codeforces OJ — a 58.3% relative improvement over the SFT baseline (0.115), but still failing on ~82% of problems on the first attempt. This is an absolute gain of only 6.7 percentage points on the hardest evaluation benchmark. The scaling experiments in Table 5 show the same pattern at larger scale: after Stage 2, the MoE model reaches 0.194 on Codeforces (up from 0.155), still failing on >80% of problems. The paper never reports accuracy breakdowns by difficulty within the evaluation benchmarks, so it is impossible to determine whether the RL improvements are concentrated on the easier half of the Codeforces set (where the SFT model already had some traction) while the hardest problems remain unsolved.

**Mitigation status.** The paper does not address this limitation. The large-rollout strategy in Stage 2 (64–80 rollouts per prompt) helps when the model's per-attempt success rate is low but non-zero — it increases the probability that at least one rollout succeeds, providing a positive gradient. But when that rate is truly zero, even 80 rollouts produce zero successes. The paper does not explore techniques for bootstrapping on problems with zero initial success rate, such as providing partial credit (reward for passing a subset of test cases rather than all), using a learned reward model, or incorporating warm-start solutions from a stronger model during early RL training. The failure mode is structurally built into the combination of binary executable rewards and GRPO: the model can only learn from problems it can sometimes solve, and it cannot learn from problems it never solves.

---

### The Pre-GRPO Difficulty Evaluation Cost Is Potentially Massive and Unaccounted

**The assumption or constraint.** Pre-GRPO requires evaluating pass rates on all candidate problems after each training phase to determine which are still "hard" and should be retained. The paper describes the mechanism in Section 3.2: "Pre-GRPO carries forward a subset of low–pass-rate cases from each phase to the next." This evaluation step involves generating **multiple rollouts per problem** and executing them against hidden test suites to compute pass rates. The paper never specifies how many rollouts are used for this evaluation, nor does it amortize this computation into the reported training budgets.

**The consequence.** Depending on how thorough the Pre-GRPO evaluation is, it could consume more compute than the RL training itself. Consider the numbers: Stage 2 Phase 1 trains on 72 problems. If Pre-GRPO evaluation uses 64 rollouts per problem (matching the training rollout budget) to get a reliable pass-rate estimate, and evaluates all 175 LiveCodeV6 problems (since the model must identify the 72 worst performers from the full set), that is 175 × 64 = 11,200 additional generations per phase boundary. Across three phases with two phase boundaries (Phase 1 → Phase 2, Phase 2 → Phase 3), that is ~22,400 generations of evaluation overhead, each up to 32K tokens. If the evaluation uses fewer rollouts (which would be noisier and risk misclassifying problems), the cost is lower but the filtering quality degrades. In either case, this cost is **not included in any headline number** — the reported training budgets (9K prompts × 8 rollouts in Stage 1, 72–25 prompts × 64–80 rollouts in Stage 2) exclude the Pre-GRPO evaluation overhead entirely.

The paper also never clarifies whether Pre-GRPO evaluation uses the same compute infrastructure as training (256 GPUs) or is amortized across machines. If evaluation blocks the training pipeline (the model cannot continue training until pass rates are computed), it introduces latency that reduces wall-clock training throughput even if total FLOPs are comparable.

**What evidence exists in the paper.** The paper does not report Pre-GRPO evaluation cost anywhere. Section 4.1 describes the Stage 2 training configuration (batch size, rollout count, sequence length, number of steps) but never mentions the evaluation budget. Section 3.2 states the curriculum schedule (72 → 50 → 25 problems, 80 → 64 → 32 rollout budgets) without indicating how pass rates are measured to determine which problems to retain. This is a missing number in a paper that otherwise provides fairly detailed hyperparameter accounting.

**Mitigation status.** The paper does not acknowledge this limitation. It presents the two-stage pipeline as a complete recipe without discussing the overhead of the difficulty-filtering mechanism that makes Stage 2 possible. A practitioner attempting to replicate the method would need to make ad-hoc decisions about how many rollouts to use for Pre-GRPO evaluation, how to parallelize it with training, and whether to include it in their compute budget. The paper's claim that the method is "practical" (Section 1) and provides "best practices" (title) is weakened by the absence of any analysis of this overhead. A straightforward fix — using the training rollouts themselves as the evaluation signal (i.e., the pass rate computed from the rollouts generated during the last training step of each phase) — would eliminate the overhead entirely but is never discussed.

---

### The LeetCode and Codeforces Test Sets Are Dangerously Small for Reliable Performance Claims

**The assumption or constraint.** The paper's strongest generalization claims rest on evaluation sets of **32 problems (LeetCode Weekly)** and **33 problems (Codeforces OJ)** — numbers that are reported in Table 1. These are the only out-of-distribution, temporally-separated benchmarks that are uncontaminated by both SFT and RL training. (LiveCode08-11 and LiveCodeV5 are also uncontaminated but are larger: 166 and 167 problems respectively.)

**The consequence.** On a 32-problem set, a single problem represents ~3.1 percentage points of Pass@1. The difference between the final RL model (0.653 on LeetCode Weekly) and DeepSeek V3.1 (0.688) is 0.035 — essentially one problem. The difference between the RL model (0.653) and Seed1.6-0715 (0.743) is 0.090 — approximately three problems. With no reported confidence intervals, the reader cannot distinguish genuine capability differences from sampling variance inherent to small test sets. If the standard error of the Pass@1 estimate on 32 problems is approximately ~0.084 (95% CI spans ±17 percentage points for a proportion near 0.65), then **none of the pairwise comparisons on LeetCode Weekly between the RL model and other systems are statistically distinguishable**. The model could be genuinely better, genuinely worse, or genuinely equal to DeepSeek V3.1 — the data cannot tell us which.

On Codeforces, the absolute scores are lower (0.115–0.200 range) but the test set is only marginally larger (33 problems), so the standard error is similar. The reported 58.3% relative improvement on Codeforces (from 0.115 to 0.182) represents an absolute gain of 6.7 percentage points, or approximately 2.2 additional problems solved correctly out of 33. This is a meaningful improvement directionally, but without variance estimates it is impossible to say whether it would replicate on a different sample of Codeforces contests.

The LiveCode benchmarks (08-11: 166 problems, V5: 167 problems) provide more reliable estimates for those specific evaluation distributions, but the paper's strongest claims about competitive programming in the wild — LeetCode and Codeforces weekly contests, explicitly chosen to avoid contamination — rest on the smallest evaluation sets.

**What evidence exists in the paper.** The evaluation set sizes are reported in Table 1 and Section 4.1. No confidence intervals, standard deviations, bootstrap estimates, or p-values are reported anywhere in the paper. The aggregated tables (2, 3, 4) report point estimates to three decimal places without any indication of uncertainty. The training dynamics curves in Figure 4 show continuous trends but are plotted without error bands.

**Mitigation status.** The paper does not address this limitation. The choice of temporally-separated weekly contests is methodologically sound for contamination control, but it intrinsically produces small test sets because each weekly contest contains only a few problems. A larger evaluation could be constructed by aggregating multiple weekly contests over a longer time window (e.g., 10 weeks of contests yielding ~300+ problems) and releasing them as a single benchmark, but the paper does not do this. The LiveCode benchmarks partially compensate by providing larger sample sizes (166–175 problems), but they are not explicitly temporally separated from the training data in the same way — only LiveCode08-11 and V5 are stated to be uncontaminated, and the mechanism ensuring this (temporal cutoff vs. dataset curation) is not described.

---

### The Contribution of Context-Length Constraints to Stage 1's Benefits Is Unclear — Confounding Entropy Expansion with Sequence Compression

**The assumption or constraint.** Stage 1 uses a **24K-token generation window** while the SFT model was trained and evaluated at **32K tokens**. The paper attributes Stage 1's benefits to "entropy expansion" — the claim that training on a broad, uniformly distributed problem set with moderate rollout budgets increases output diversity. However, the shorter context window is confounded with the data distribution change: Stage 1 differs from SFT in both what data the model sees (9K uniformly distributed problems vs. 470K hard-filtered problems) and how many tokens it can generate per solution (24K vs. 32K). The paper provides Figure 3 to show that 24k-style training produces higher entropy than 32k-style training, but this figure compares two different training runs (SFT at 32K vs. RL Stage 1 at 24K), not a controlled ablation varying only the context length while holding the data distribution constant.

**The consequence.** If the entropy benefit comes primarily from the shorter context window rather than the uniform data distribution, then the paper's conceptual framing — that Stage 1 is about "entropy expansion through broad problem exposure" — is misleading. The actual mechanism would be **sequence-length regularization**: constraining the model to produce solutions within 24K tokens forces it to be more concise, which indirectly reduces repetitive patterns and increases diversity per token because there is less room for filler. This is a fundamentally different mechanism from the stated one, and it has different practical implications. For example, if the 24K constraint is the active ingredient, then the benefit should disappear when the model is later evaluated at 32K (the extra 8K tokens might be filled with the same repetitive patterns that Stage 1 suppressed). The paper never evaluates the Stage 1 model at 24K vs. 32K separately, so we cannot tell.

The same concern applies to the claim that Stage 2's 32K window is necessary for hard problems because they "require longer reasoning chains." If Stage 1's benefit came from the 24K constraint, then moving to 32K in Stage 2 might partially undo that benefit — the model would regain the capacity to generate repetitive filler. The paper never tests whether Stage 2 at 24K (all else equal) would perform better or worse than Stage 2 at 32K.

**What evidence exists in the paper.** Figure 3 directly compares entropy between 24k-style and 32k-style training, but as noted, this comparison does not isolate the context-length variable. The ablation in Table 4, row 3 ("RL without First Stage Only Second Stage") removes Stage 1 entirely but keeps Stage 2 at 32K — it tests the effect of removing the uniform-data-plus-24K-constraint bundle as a whole, not the individual components. No experiment varies the context length within Stage 1 (e.g., Stage 1 at 32K with uniform data) or within Stage 2 (e.g., Stage 2 at 24K with hard-focus curriculum).

**Mitigation status.** The paper does not acknowledge this confound or attempt to resolve it. The 24K → 32K transition between stages is presented as a natural design choice (Stage 1 uses short context to reduce truncation, Stage 2 uses long context to accommodate hard problems) without any ablation verifying that the context-length choice is causal for the observed benefits. A minimal experiment — running Stage 1 at 32K instead of 24K, holding the data distribution constant, and comparing the resulting entropy and downstream Stage 2 performance — would clarify whether entropy expansion or sequence compression is the active mechanism. The absence of this experiment makes the paper's explanation for *why* Stage 1 works less reliable than its demonstration *that* Stage 1 works.

---

### The Approach Has Only Been Validated on a Single Model Family and a Single Task Domain

**The assumption or constraint.** All primary experiments use **Qwen2.5-32B-Instruct** as the base model, and all experiments — SFT, RL Stage 1, RL Stage 2 — target **competitive programming** (LiveCode, LeetCode, Codeforces). The scaling validation in Section 4.6 uses an "internal large-scale MoE model" that is from the same organization (Tencent's Hunyuan team) and whose architecture, training data, and pre-training methodology are not described. The paper claims in Section 1 that its findings represent "best practices" and "practical training techniques" without qualification to specific model families or code-generation subdomains.

**The consequence.** Several aspects of the approach may not transfer to other settings:

- **Base model dependence.** Qwen2.5-32B-Instruct is an instruction-tuned model with specific pre-training data and alignment properties. The paper's SFT model inherits reasoning patterns distilled from DeepSeekR1-0528. The three pathologies that motivate the two-stage RL design — low entropy, repetitive generation, hard-problem ceiling (Section 3.2) — may be specific to this base model or to distillation-based SFT. A model with a different pre-training distribution (e.g., one trained primarily on code rather than general text) might not exhibit these pathologies in the same form, and the entropy expansion stage might be unnecessary or even harmful.

- **Task domain dependence.** Competitive programming has specific properties that enable the paper's approach: binary executable rewards (test cases pass or fail), clean correctness signals, and a clear difficulty hierarchy. The paper never tests whether the two-stage framework transfers to math reasoning (where rewards are also binary/verifiable but outputs are typically shorter), general code generation (where correctness may be ambiguous or unverifiable), or other reasoning domains (scientific QA, logical deduction). The "best practices" framing implies generality that the experiments do not support.

- **Verifier dependence.** The paper uses executable test cases as the reward signal — an oracle verifier with zero error. In domains where such ground-truth verification is unavailable (most real-world coding tasks don't come with comprehensive hidden test suites), the entire approach would need to be adapted to use learned reward models, which introduce their own over-optimization risks. The paper does not discuss this transition.

**What evidence exists in the paper.** The paper evaluates exclusively on competitive programming benchmarks (Section 4.1). The external baselines (DeepSeek V3.1, Seed1.6-0715, Qwen3-235B, QwQ-32B, OpenReasoning-Nemotron-32B) are compared only on these same benchmarks (Table 2). The scaling experiments in Section 4.6 are on the same task domain using a single additional model. The paper states its contributions are for "competitive-programming code generation" (abstract), but the title ("Data Curation Best Practices for Reinforcement Learning with Verifiable Reward") and the abstract ("Our study distills concise best practices for data curation, entropy expansion, and curriculum design in RLVR for competitive-programming code generation") are ambiguous about whether the best practices are claimed to be domain-specific or general.

**Mitigation status.** The paper provides limited mitigation through the MoE scaling experiment (Section 4.6), which demonstrates that the two-stage pattern replicates on a different model architecture and scale. This provides some evidence that the findings are not purely artifacts of Qwen2.5-32B's specific properties. However, the MoE model is from the same organization and its training details are not disclosed, so we cannot assess whether it shares the same pre-training data, distillation procedure, or alignment methodology as Qwen2.5-32B. The paper suggests in the conclusion that "future work could explore adaptive curriculum strategies and more efficient sampling techniques," but does not call for multi-model or multi-domain validation as a specific next step. A practitioner using a different base model (e.g., Llama-3, Gemma, Mistral) or a different task domain should treat the paper's specific hyperparameter choices (8 rollouts in Stage 1, 64–80 in Stage 2, three-phase curriculum with 72/50/25 problem splits) as untested in their setting.

---

### The Hard-Focus Curriculum Ablation Claims Are Limited by Weak Baseline Configurations

**The assumption or constraint.** The paper's central ablation — Table 4 — demonstrates that the two-stage pipeline outperforms three alternatives: (1) RL on all LiveCodeV6 problems without filtering, (2) RL on all 9K problems without Stage 2, and (3) Stage 2 only without Stage 1. The conclusion that "both stages synergize effectively" and "difficulty-aware training is crucial" rests on these comparisons. However, the baseline configurations are designed to demonstrate failure modes, not to represent the strongest possible alternatives to the two-stage design.

**The consequence.** The ablation tells us that the proposed method beats clearly broken alternatives, but it does not tell us whether alternative difficulty-filtering or curriculum strategies would work equally well or better. Specifically:

- **The "RL with all LiveCodeV6" condition (row 1)** uses a single-stage GRPO with 24K context and 8 rollouts (the Stage 1 configuration) applied to the SFT model on unfiltered LiveCodeV6 data. This collapses catastrophically (-48.8% on LeetCode Weekly). But **why** does it collapse? The paper attributes it to mixing easy and hard problems, but alternatively it could be because the configuration uses only 8 rollouts — far too few to learn on hard problems — combined with a data distribution shift from the SFT training data. If this same experiment were run with 64 rollouts (matching Stage 2's budget), would it still collapse? The paper never tests this.

- **The "RL without First Stage" condition (row 3)** applies Stage 2 directly to the SFT model, showing that it overfits to LiveCodeV6 while degrading on LeetCode Weekly. But what if Stage 2 were applied to the SFT model with a different configuration — for example, including a small amount of entropy-expanding data from Stage 1 mixed into the Stage 2 curriculum, or using a longer Stage 2 with a more gradual difficulty ramp? The paper's conclusion that Stage 1 is "necessary" is based on a single configuration of Stage 2 applied directly to SFT, not a systematic exploration of alternatives to Stage 1's role.

- **No comparison to a simpler baseline:** what if the SFT model were trained with the full 32K-stage-1-pool data simply as additional supervised fine-tuning (not RL) before Stage 2? What if Stage 2 used a static difficulty filter (72 hardest problems determined once, never updated) instead of Pre-GRPO's dynamic filtering? These baselines would help isolate the contribution of RL-vs-SFT in Stage 1 and dynamic-vs-static filtering in Stage 2, respectively, but neither is tested.

**What evidence exists in the paper.** Table 4 reports the three ablation conditions and the full method. No additional baselines are tested beyond the five configurations in that table (plus the "more harder samples" variant, which adds data to the full method rather than changing its structure). The paper does not include an ablation varying the rollout budget in the unfiltered RL condition (row 1) or testing a static difficulty filter alternative to Pre-GRPO.

**Mitigation status.** The paper does not acknowledge that the ablation baselines are weak. The conclusion that "difficulty-aware training is crucial" is supported by showing that *not* being difficulty-aware causes catastrophic failure. But the paper leaves open the possibility that other difficulty-aware strategies — with different filtering mechanisms, different stage boundaries, or different allocation of rollout budget across stages — could achieve comparable or better results. A reader seeking to adopt the paper's approach cannot determine whether the specific Pre-GRPO mechanism (three-phase dynamic filtering with 72/50/25 splits) is necessary, or whether any reasonable difficulty-filtering strategy combined with large rollout budgets on hard problems would work. The paper demonstrates that its specific recipe works, not that its specific recipe is optimal or uniquely effective among the space of difficulty-aware curricula.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

This paper changes how the RLVR community should think about training data, not by proposing a new algorithm but by demonstrating that **data curation choices can swing performance by over 100 percentage points** while holding the algorithm fixed. The pivotal evidence is Table 4: applying the same GRPO optimizer to different data configurations produces outcomes ranging from catastrophic collapse (a 48.8% drop on LeetCode Weekly when training on unfiltered LiveCodeV6) to state-of-the-art 32B-model performance (a 58.3% gain on Codeforces with the full two-stage pipeline). This is not an incremental refinement — it is evidence that data curation is a **first-class design dimension of equal or greater importance than algorithm design**, and that the community's heavy emphasis on algorithmic innovation (DAPO, VAPO, ProRL, GSPO) has been optimizing a dimension that may be secondary to getting the data right.

The magnitude of this shift should not be overstated: the paper does not claim that algorithms don't matter, nor does it propose a new data-centric paradigm that replaces algorithmic research. What it does is provide **concrete, replicated evidence** that certain data configuration choices — specifically, difficulty filtering during RL training — are not optional optimizations but **stability requirements**. The fact that training on mixed-difficulty problems causes catastrophic collapse rather than merely reduced efficiency is a finding that challenges the default assumption in much of the RLVR literature that more diverse training data is uniformly beneficial. This assumption is implicit in standard practice: most RLVR papers train on the largest available problem set without difficulty stratification. The paper's ablation showing that this practice can actively destroy performance — not just leave gains on the table — should change how researchers construct their RL training sets, at minimum by forcing them to verify that mixed-difficulty training is stable for their specific domain before adopting it.

The paper also **reconciles a latent tension** in the RLVR literature between the math-focused and code-focused research threads. Math RLVR (dominant in the o1/R1 lineage) benefits from short, easily verifiable outputs where the exploration problem is less acute because correct answers are typically compact. Code RLVR faces a structurally harder exploration challenge: solutions are hundreds or thousands of tokens long, and the space of incorrect implementations is astronomically larger than the space of correct ones. The paper's diagnostic of the "capability ceiling" (Figure 5) — where problems with low initial accuracy fail to improve under standard RL — explains why methods that work for math (uniform training, moderate rollout budgets) may not transfer to code without modification. The implied reconciliation is that **code RLVR requires difficulty-aware data curation and scaled rollout budgets** in ways that math RLVR may not, because the exploration challenge is fundamentally different in magnitude. This is not a claim the paper makes explicitly, but it is the natural interpretation of its findings: the techniques that dominate math RLVR research are solving a problem that is qualitatively easier on the exploration axis, and code RLVR reveals failure modes that are latent but less visible in math benchmarks.

Several research directions become more attractive as a result of this work:

- **Difficulty-adaptive RLVR training protocols** — where the rollout budget, data mixture, and even the RL algorithm are dynamically adjusted based on model-relative problem difficulty — are now supported by direct evidence that static configurations fail. The paper's Pre-GRPO mechanism is a first cut at this idea, but more sophisticated adaptive strategies (continuous difficulty estimates, online budget allocation) are a natural extension.
- **Understanding the gradient dynamics of mixed-difficulty RL training** becomes a priority. The paper demonstrates *that* mixing easy and hard problems causes collapse, but the mechanism (easy problems diluting the gradient signal? variance in advantage estimates swamping the learning on hard problems?) is only hypothesized, not established. A rigorous gradient analysis — tracking per-problem gradient norms, advantage variance, and update magnitudes across difficulty tiers — would transform this empirical finding into a theoretical understanding.
- **Verifier design for exploration-challenged domains** becomes more urgent. The paper relies on executable test suites as an oracle verifier, but the capability ceiling is fundamentally a verifier problem: on hard problems, the oracle verifier provides zero positive signal because the model never generates a correct solution. Techniques that provide partial credit or learned dense rewards for code — such as rewarding passing a subset of test cases, or using compiler/interpreter feedback as an intermediate signal — could lower the exploration barrier and make hard problems learnable even with limited initial success rates.

Directions that become **less attractive** include naive data scaling (training on ever-larger problem sets without difficulty filtering) and algorithmic tweaks to GRPO that don't address the underlying exploration bottleneck. The paper implies that marginal improvements to the RL optimizer are unlikely to help if the training data is misconfigured to begin with — a 5% improvement in sample efficiency from a better algorithm is irrelevant if the data configuration causes a 48.8% performance collapse.

### Follow-Up Research This Work Enables

**A controlled experiment isolating the 24K vs. 32K context-length confound in Stage 1.** The paper attributes Stage 1's entropy expansion benefit to the broad, uniformly distributed problem set, but the shorter 24K-token generation window (vs. SFT's 32K) is perfectly confounded with the data distribution change. To test whether entropy expansion comes from data diversity or sequence-length regularization, a minimal follow-up would train three Stage 1 variants: (a) the original configuration (9K uniform problems, 24K context), (b) 9K uniform problems at 32K context, and (c) the SFT's 470K hard-filtered problems at 24K context. Measuring output entropy (replicating Figure 3), repetition frequency (replicating the Appendix B case study methodology), and downstream Stage 2 performance on LeetCode Weekly for all three variants would isolate the causal factor. If variant (b) achieves similar entropy expansion and downstream gains, the 24K constraint is incidental; if variant (c) achieves entropy expansion but variant (b) does not, the sequence length is the active ingredient, which would fundamentally change how practitioners should configure Stage 1.

**A rollout-budget sweep crossing both training stages to identify the compute-optimal allocation.** The paper claims that strategic resource allocation — moderate rollout budgets in Stage 1, large budgets in Stage 2 — is key to its success, but this allocation is never empirically validated against alternatives at the same total compute budget. A grid experiment would cross Stage 1 rollout counts (4, 8, 16, 32) with Stage 2 rollout counts (16, 32, 64, 128), keeping total generation budget approximately constant across conditions (by adjusting the number of training steps or the number of prompts in each stage). The evaluation would measure final Pass@1 on LeetCode Weekly and Codeforces OJ, as well as training stability metrics (advantage variance, policy entropy, pass-rate trajectories). If the paper's chosen allocation (8 / 64–80) is near-optimal, the grid would show a clear peak; if a wide range of allocations work equally well, the strategic-resource-allocation framing is less important than the paper claims, and the key insight is simply that some difficulty-filtered Stage 2 is necessary, not that the specific rollout ratios matter.

**A static-vs.-dynamic difficulty filter comparison within Stage 2.** The Pre-GRPO mechanism uses dynamic, model-relative difficulty filtering — problems are dropped from the curriculum only when the current model masters them, as measured by pass rates after each phase. This is presented as an advance over static difficulty categorization, but no direct comparison is made. A follow-up would compare the full Pre-GRPO curriculum (dynamic filtering, 72 → 50 → 25 problems) against a static baseline where the 72 hardest problems are identified once at the start of Stage 2 (using the Stage 1 model's initial pass rates) and trained on throughout without updating the filter. Both conditions would use identical rollout budgets, training steps, and evaluation protocols. If the static baseline performs comparably, dynamic filtering is unnecessary complexity; if dynamic filtering is essential (because the model masters some initially-hard problems and needs to refocus on the remaining stubborn ones), this would validate Pre-GRPO specifically rather than difficulty-filtered training generally.

**A gradient-analysis study tracing why mixed-difficulty RL collapses.** The paper shows that training on all 175 LiveCodeV6 problems (mixed difficulty) causes catastrophic collapse (Table 4, row 1), but the mechanism is only hypothesized. A diagnostic experiment would instrument the training run: for each GRPO update, log per-problem advantage statistics (mean, variance, fraction of rollouts with positive advantage), gradient norms stratified by problem difficulty, and the cosine similarity between the update directions from easy-problem batches vs. hard-problem batches. The hypothesis is that easy-problem updates dominate the gradient (because they have near-zero advantage variance, producing noisy but high-magnitude updates that wash out the sparse signal from hard problems) and that hard-problem updates are directionally misaligned with easy-problem updates (optimizing for both simultaneously pulls the model in conflicting directions). If confirmed, this would explain the collapse mechanistically and suggest specific mitigations (gradient filtering, difficulty-weighted loss scaling, or separate optimization steps per difficulty tier) that are more targeted than the paper's current solution of removing easy problems entirely.

**A partial-credit reward experiment targeting the capability floor on zero-success-rate problems.** The paper's fundamental limitation is that hard problems with near-zero initial pass rates receive no positive gradient signal — the model cannot learn what it never generates. A natural follow-up would replace the binary reward (all test cases pass → reward = 1, else 0) with a **stepwise or test-case-level partial credit signal**. For example, reward could be the fraction of hidden test cases passed, or could incorporate intermediate execution feedback (does the code compile? does it run without runtime errors? does it produce output in the expected format?). Training the same two-stage pipeline with partial-credit rewards on problems where the SFT model's initial pass@1 is truly zero would test whether the capability floor can be lowered. The paper's Case 4 (frozen at 12.5% in single-case training, Appendix A) and the flat low-accuracy training curves in Figure 5 are the specific phenomena this experiment would target. If partial-credit rewards enable learning on previously unlearnable problems, the binary-reward constraint is the bottleneck; if they don't, the capability floor is due to model capacity or architecture rather than the reward structure.

**A cross-model-family replication to test whether the two-stage recipe transfers or is Qwen2.5-specific.** The paper's primary experiments use Qwen2.5-32B-Instruct exclusively. The three pathologies that motivate the two-stage design — low entropy, repetitive patterns, hard-problem ceiling (Section 3.2) — may be specific to this model or to the distillation-based SFT procedure that produced it. A replication applying the same pipeline (identical SFT data construction, identical Stage 1 and Stage 2 configurations, evaluation on the same LeetCode/Codeforces weekly contests) to Llama-3-70B or Gemma-2-27B would test transferability. If the three pathologies are absent in a different base model — if, for example, a code-pretrained model already has high entropy and low repetition — then Stage 1 might be unnecessary or even harmful (adding entropy to an already-diverse model could reduce precision without providing benefit). The replication would measure not just final performance but the same diagnostic metrics the paper uses to motivate its design: Figure 3 (entropy comparison), Appendix B-style repetition analysis, and per-difficulty-cluster training dynamics (Figure 5). This would distinguish "these best practices are general for RLVR on code" from "these best practices fix specific failure modes of Qwen2.5-32B + distillation-based SFT."

### Practical Applications and Downstream Use Cases

**Cost-efficient competitive-programming model training for organizations with limited compute budgets.** The paper's finding that difficulty-filtered RL training on only 25–72 hard problems can produce models that outperform 5–10× larger systems on competitive programming benchmarks (Table 2: the 32B model matches or exceeds DeepSeek V3.1 and Qwen3-235B on LiveCode benchmarks) implies that organizations can achieve competitive performance without training enormous models. The key practical insight is the **concentration of RL compute on hard problems**: rather than spreading a fixed training budget across 9K+ problems uniformly, Stage 2's focused training on the hardest 25–72 problems with large rollout budgets (64–80 rollouts per prompt) is what drives frontier performance. A team with a limited GPU budget could allocate the majority of their RL training FLOPs to deep sampling of a small, curated hard-problem set rather than broad but shallow training across many problems. The paper's scaling results on the MoE model (Table 5) suggest this principle transfers to larger architectures, making it applicable across compute scales. The 58.3% relative improvement on Codeforces from RL training (0.115 → 0.182) over the already-strong SFT baseline gives a concrete estimate of the expected gain from adopting this focused-training approach.

**Automated benchmark-specific model specialization for coding competition platforms.** The Pre-GRPO mechanism's dynamic difficulty filtering — retaining only problems the model cannot yet solve, dropping them when mastered — is well-suited to **continuous deployment scenarios** where the goal is to maximize performance on a regularly-updated problem distribution. A platform like Codeforces or LeetCode releases new problems weekly; a model trained with Pre-GRPO could automatically maintain a curriculum of the hardest recent problems, concentrating training on the frontier of its capability. As the model masters older problems (their pass rates rise, and they are dropped from the curriculum), new contest problems are added to the candidate pool, and the dynamic filter identifies which are hardest for the current model. This creates a **self-maintaining training pipeline** that doesn't require manual difficulty annotation or static problem classification. The paper's demonstration that adding more hard problems to Stage 2 consistently improves results (Table 4, row 5: +0.013 to +0.040 across benchmarks) suggests the mechanism scales with problem-set size, though the computational cost of Pre-GRPO evaluation (generating rollouts to compute pass rates for filtering) would need to be managed in a production system — perhaps by using a lightweight proxy model for difficulty estimation rather than the full training model.

**Quality-filtered data generation for supervised distillation pipelines.** The paper's SFT ablation (Table 3) demonstrates that arena learning — filtering a 1.27M-prompt dataset to 470K by retaining only problems the model fails on — maintains performance while reducing data volume by over 60%, and that duplicating hard examples ("Twice Hard Learning") further improves results. This principle — **train SFT models on hard examples disproportionately** — is directly applicable to organizations generating synthetic training data for code models. When distilling from a strong teacher model (as the paper does with DeepSeekR1-0528), the resulting dataset naturally contains many examples where the student would have succeeded anyway. Filtering these out before SFT training reduces computational cost without sacrificing downstream performance, and can even improve it by focusing the model's capacity on the examples that provide genuine learning signal. The concrete recipe from the paper: generate responses for a large prompt set, train an initial model, use it to identify failure cases, retain only those, and optionally duplicate them to restore the training token budget. No part of this pipeline requires RL, making it applicable even to teams without RL infrastructure. The 60% data reduction from arena learning (1.27M → 470K) translates to a roughly equivalent reduction in SFT training compute.

### When to Prefer This Method

The paper does not explicitly frame its method as a choice against named alternatives — it presents the two-stage RL pipeline as a training recipe rather than as one option in a decision matrix — so a "Prefer A when / Prefer B when" framework would be extrinsic to the paper's own analysis. The paper's ablations do, however, reveal clear conditions under which the approach succeeds or fails, which can guide a practitioner's decision.

The two-stage pipeline is appropriate when:
- The SFT baseline exhibits the specific pathologies documented in Section 3.2 — low output entropy (visualized in Figure 3), repetitive generation patterns (documented in Appendix B), and a large pass@1-to-pass@10 gap (evident in Table 1) — indicating that standard RL would inherit and amplify these failures rather than fixing them.
- The problem domain provides **executable, binary verifiable rewards** (test cases for code, formal verifiers for proofs, execution-based evaluation for commands) that can serve as an oracle reward signal. The entire approach — Pre-GRPO filtering, large-rollout GRPO, difficulty estimation via pass rates — depends on the ability to automatically and accurately score generated outputs.
- Training compute is sufficient to support large rollout budgets (64–80 rollouts per prompt) on the hardest problem subset. Stage 2's effectiveness depends on generating enough samples per hard problem that positive examples appear in most training batches. If the rollout budget must be kept small (e.g., <16 rollouts per prompt due to hardware constraints), the capability-ceiling problem (Figure 5) will likely prevent learning on the hardest problems, and the two-stage pipeline may not outperform simpler single-stage RL.
- The problem distribution includes a substantial fraction of "hard but learnable" problems — cases where the base model's initial pass@1 is low but non-zero (maybe 2–15%), so that large rollouts can occasionally discover correct solutions. If most problems have pass@1 identically zero, Stage 2 provides no learning signal regardless of rollout budget; if most problems have pass@1 already high (>50%), the hard-focus curriculum offers limited benefit over uniform training.

The approach should be avoided or modified when:
- The reward signal is noisy, learned, or non-binary — for example, using a reward model rather than execution-based verification. The paper provides no evidence about whether difficulty filtering and large-rollout GRPO remain stable when the reward signal has model-dependent error, and the over-optimization risks in that setting are different from the sparse-reward problem the paper addresses.
- The training compute budget is severely limited and cannot support large rollouts on even a small hard-problem set. In that regime, the paper's alternative configurations — for example, Stage 1 only with 9K prompts and 8 rollouts (Table 4, row 2), which improves LiveCode benchmarks by +0.074 to +0.126 over SFT — may provide better return on limited compute than an under-resourced Stage 2 that never generates enough positive examples to learn from hard problems.
- The SFT model already exhibits high entropy and low repetition — for example, if the base model was pre-trained primarily on code rather than general text, or if the SFT data included extensive diversity-promoting augmentation. In that case, Stage 1's entropy expansion may be unnecessary or could even reduce precision without providing countervailing benefits. The paper's "Second Stage Only" ablation (Table 4, row 3), which overfits to the training set but still improves LiveCodeV6 by +25.9%, suggests that Stage 2 can work without Stage 1 when generalization to novel problem distributions is not the primary concern — though the 4.8% LeetCode Weekly degradation in that condition underscores the generalization risk.
