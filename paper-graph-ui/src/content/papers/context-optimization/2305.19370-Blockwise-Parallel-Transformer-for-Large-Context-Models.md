## 1. Executive Summary

This paper introduces the **Blockwise Parallel Transformer (BPT)**, a memory-efficient architecture that computes both self-attention and the feedforward network in a fused blockwise manner — iterating over query blocks in an outer loop while processing key-value blocks in an inner loop to avoid materializing full intermediate tensors — to dramatically reduce the activation memory footprint of large Transformer models. Evaluated on GPT-style language models ranging from 1B to 70B parameters trained on OpenWebText and on reinforcement learning tasks from the ExoRL benchmark, BPT enables training sequences up to 32× longer than vanilla attention-based Transformers and up to 4× longer than prior memory-efficient methods such as FlashAttention and Memory Efficient Attention (achieving 131K-token contexts on a single A100 for a 3B model, versus 16K for FlashAttention). The approach reduces per-layer activation memory from 8bsh in memory-efficient attention methods to 2bsh by eliminating the need to store the feedforward network's large intermediate activations on the full sequence, establishing that the feedforward sub-layer — not the attention mechanism — becomes the dominant memory bottleneck once exact blockwise attention is employed.

## 2. Context and Motivation

### The Core Problem: Feedforward Networks Are the Overlooked Memory Bottleneck

The paper addresses a specific, technically precise gap: Transformer models cannot handle long sequences at training time because of memory constraints, and **the true bottleneck has been systematically misidentified**. Prior work across the field treated the self-attention mechanism's $O(s^2)$ memory footprint as the primary obstacle to scaling context length. This was a reasonable assumption — storing the full attention matrix `softmax(QK^T)` for a sequence of length $s$ with $a$ attention heads requires $O(bs^2 a)$ bytes, which dominates total activation memory when $s$ is moderate to large. The research community responded with a wave of techniques aimed at reducing attention's memory cost: sparse approximations, low-rank factorizations, kernel-based linearization, and eventually exact blockwise computation via online softmax.

However, the paper makes a critical observation: once you solve the attention memory problem through blockwise/online computation, the memory bottleneck **shifts entirely**. The feedforward network (FFN) — specifically the large intermediate activations produced by the first linear transformation — becomes the dominant consumer of activation memory. As stated in Section 2:

> "the large feedforward layers have been overlooked"

Why does this matter? In a standard Transformer layer, the FFN applies two linear transformations with a nonlinearity between them (Equation 2):

$$\text{FFN}(x) = \max(0, xW_1 + b_1)W_2 + b_2$$

The intermediate hidden dimension is typically 4× the model dimension (in GPT-style architectures), so for a hidden dimension $d_{model}$, the intermediate activation vector has dimension $4 \cdot d_{model}$. When computed on the full sequence, this requires storing $b \cdot s \cdot 4 \cdot d_{model}$ elements of activations at each layer. Even with gradient checkpointing, which trades computation for memory by not saving intermediates for the backward pass, the maximum FFN activation size is **$8 b s h$ bytes** (Section 3.1) — and this remains the dominant term.

The paper quantifies this precisely: for FlashAttention or Memory Efficient Attention, the attention sub-layer contributes $2 b s h$ bytes of activation memory, while the FFN contributes $8 b s h$ bytes. The FFN is responsible for **4× more activation memory** than the already-optimized attention mechanism. This means that further gains in context length require addressing the FFN, not the attention mechanism.

### Why Long Contexts Matter (and Why Memory Limits Are the Blocking Issue)

The paper's motivation is grounded in specific application requirements that exceed current context-length capabilities. Several are referenced in Section 1:

- **Large language models for code understanding** (Chen et al., 2021): source files, entire codebases, and debugging traces routinely span tens of thousands of tokens. The ability to condition on an entire repository or long execution trace requires context lengths far beyond the 2K-8K tokens that were standard in GPT-3-scale models.
- **High-resolution images and visual-language models**: When images are tokenized (e.g., as patches), high-resolution inputs produce very long sequences. Flamingo (Alayrac et al., 2022) and similar models must process interleaved visual and text sequences that can easily exceed 10K+ tokens.
- **Long-form content**: Podcasts, books, research papers, and legal documents span tens to hundreds of thousands of tokens. Models that can reason over an entire book or multiple documents simultaneously need context lengths in the 64K-128K+ range.
- **Reinforcement learning with many trajectories**: The paper's own RL experiments (Section 5.3) exemplify the need. The Agentic Transformer (Liu and Abbeel, 2023) conditions on multiple trajectories of (state, action, reward, next-state) tuples to learn policies. With each trajectory spanning 1000 timesteps × 4 tokens per timestep, conditioning on 32 or 64 trajectories produces sequences of 128K-256K tokens — impossible to train with standard or even memory-efficient Transformers without BPT.

The issue is not purely one of model capability — it's a **hardware constraint**. Training Transformers on long sequences requires fitting activations, parameters, and optimizer states in GPU/TPU high-bandwidth memory (HBM). For a 13B parameter model in float32, the parameters alone consume ~52GB. With Adam optimizer states (momentum + variance) adding 2×, we're at ~156GB before accounting for any activations. A single 80GB A100 cannot hold the parameters, let alone activations. This necessitates model parallelism (sharding parameters across devices), but activation memory scales with batch size and sequence length *independently of the sharding strategy* — each device still stores the activations for its shard of the computation. So activation memory becomes the binding constraint that limits context length even in distributed settings.

The paper's perspective is that **memory, not compute, is the bottleneck for long-context training**. Compute can be parallelized across devices with near-linear scaling. Memory — specifically activation memory that must be stored for the backward pass — cannot be distributed in the same way (without pipeline parallelism, which introduces its own efficiency challenges). Therefore, reducing activation memory per device directly translates to the ability to train on longer sequences.

### Prior Approaches and Why They Fall Short

The paper positions itself within a mature research landscape of Transformer efficiency work, summarized in Section 6 and distilled here as they relate to the specific gap:

**Attention-focused memory reductions (the first wave).** The dominant line of prior work attacked the $O(s^2)$ memory cost of self-attention:

- **Sparse and low-rank approximations** (Child et al., 2019; Beltagy et al., 2020; Choromanski et al., 2020; Wang et al., 2020): These reduce memory by restricting attention to local windows, predefined sparse patterns, or low-rank factorizations. The fundamental limitation: they **approximate** attention rather than computing it exactly. Approximation quality degrades unpredictably on tasks requiring global context, and the sparsity patterns must be hand-designed per application.

- **Exact blockwise attention via online softmax** (Milakov and Gimelshein, 2018; Rabe and Staats, 2021; Dao et al., 2022): This is the approach the paper builds on. By computing attention in blocks — splitting the query sequence into $B_q$ blocks and iterating over $B_{kv}$ blocks of keys and values — the full attention matrix is never materialized. Instead, each query block's attention is computed incrementally, and blockwise results are combined by tracking normalization constants (the softmax denominator and maximum subtraction). This yields $O(s)$ memory complexity for attention with **exact** (non-approximate) results.

FlashAttention (Dao et al., 2022) and Memory Efficient Attention (Rabe and Staats, 2021) represent the state-of-the-art in this category. The paper explicitly acknowledges them as the starting point and builds directly on their approach. Their key contribution — computing exact attention in blocks to avoid materializing the full $QK^T$ matrix — is the foundation that makes BPT possible.

**Where these methods fall short:** Even after reducing attention memory to $O(s)$, the **feedforward network remains untouched**. As the paper's memory analysis in Section 3.1 shows, a FlashAttention Transformer layer still requires $8 b s h$ bytes of activation memory — all of it from the FFN's intermediate activations. This means that for any sequence length $s$ where the FFN dominates, further improvements to the attention mechanism provide zero benefit. The paper characterizes this as hitting a new ceiling:

> "the large feedforward layers have been overlooked... this issue becomes the key memory challenge once employing memory-efficient attention mechanisms"

This ceiling is what prevents FlashAttention from scaling beyond approximately 16K-65K tokens on large models (Table 2), even though the attention mechanism itself could theoretically handle much longer sequences.

**Other approaches the paper distinguishes itself from:**

- **Replacing attention entirely** (Gu et al., 2021; Poli et al., 2023; Orvieto et al., 2023): State-space models, convolutional alternatives, and gated linear recurrences aim to avoid the quadratic complexity of attention altogether. The paper does not position itself against these — BPT computes exact attention, making it a drop-in replacement for any Transformer, rather than an architectural departure that requires retraining and may not match attention's modeling capabilities.

- **Feedforward sparsity** (Shazeer et al., 2017; Lepikhin et al., 2020; Fedus et al., 2022): Mixture-of-Experts (MoE) layers reduce FFN memory by only activating a subset of experts per token. This is **complementary** to BPT: BPT reduces the per-layer activation memory regardless of the FFN architecture, while MoE reduces the parameter count. The paper does not claim to compete with MoE — reducing activation memory is a different axis.

- **Sequence parallelism** (Korthikanti et al., 2022): Distributing sequence chunks across devices reduces per-device activation memory but requires communication between devices for attention computation. BPT operates **per-device** and is orthogonal to sequence parallelism — they can be combined, as the paper notes in Section 6.

- **Gradient checkpointing** (Chen et al., 2016): This trades compute for memory by not storing intermediate activations and recomputing them during the backward pass. BPT uses gradient checkpointing as a **component** (the `remat_ffn` module in Algorithm 1), but checkpointing alone does not fundamentally change the *maximum* activation footprint — it only controls which activations are stored. The $8 b s h$ FFN bottleneck is the activation size at a specific point in the forward/backward computation graph, which checkpointing can relocate but not eliminate at the peak.

### How BPT Positions Itself

The paper's key insight is deceptively simple: once attention is computed blockwise (iterating over query and key-value blocks), the FFN computation can be **fused into the same blockwise loop structure**. Instead of:

1. Compute full attention output for the entire sequence (blockwise, but producing the complete output tensor)
2. Apply FFN to the complete attention output
3. Store huge FFN intermediate activations

BPT does:

1. For each query block:
   a. Iterate over all key-value blocks to compute blockwise attention for this query block
   b. Apply FFN *immediately* to this query block's attention output
   c. Add residual connection
   d. The FFN intermediates for that block can be discarded (or checkpointed) before moving to the next query block

This fusing reduces the per-layer activation memory from $8 b s h$ to $2 b s h$ (Section 3.1), a 4× reduction. The outer loop over query blocks processes the sequence in $B_q$ chunks of size $c$, and at any time only activations for the current chunk ($2 b c h$ bytes) plus the accumulated output tensor ($2 b s h$ bytes) need to be in memory.

The paper explicitly positions this as **building on, not competing with, blockwise attention methods**:

> "We observe that the blockwise computation is not limited to self-attention but can also be applied to the feedforward network" (Section 3)

The approach is architecturally identical to a standard Transformer — no changes to the attention mechanism, FFN structure, or layer connectivity. It is purely a **compute reordering** that trades some sequentialization (the outer query-block loop introduces a dependency) for dramatically lower memory. This makes BPT compatible with existing Transformer training pipelines, optimization techniques, and pretrained model checkpoints (though the paper does not explore converting pretrained models).

A subtle but important design choice: the paper's blockwise fusion goes beyond simply computing the FFN in blocks. By nesting the FFN computation *inside* the query-block loop, the system avoids ever storing attention outputs for the full sequence at once. In FlashAttention, the blockwise attention computation produces the full output tensor, which then feeds into the FFN — so while attention memory is reduced *during* the attention computation, the output of attention (size $b s h$) must be stored for the FFN's forward and backward passes. BPT eliminates this intermediate storage entirely by consuming the attention output block-by-block.

## 3. Technical Approach

### 3.1 Reader Orientation

The system being built is a **memory-efficient computation strategy for Transformer models** — specifically a way to reorganize how a standard Transformer layer computes its outputs so that intermediate results (activations) consume dramatically less GPU or TPU memory during training. The problem it solves is that the feedforward network in a Transformer layer produces very large intermediate tensors whose dimensions scale with both model size and sequence length, and these tensors must be stored in high-bandwidth memory (HBM) for the backward pass. Once prior work solved the attention mechanism's memory bottleneck through blockwise computation, the feedforward network became the dominant memory consumer — and BPT addresses this by **fusing the feedforward computation into the same blockwise loop that already computes attention, so the FFN never operates on the full sequence at once**.

The shape of the solution is a nested pair of loops: an outer loop iterates over chunks of the input sequence (query blocks), and for each query block, an inner loop iterates over all key-value blocks to compute the attention for that query block. Immediately after computing attention for one query block, the feedforward network is applied to just that block's output, and the FFN's large intermediate activations can be discarded before moving to the next query block. This reordering is mathematically equivalent to the standard Transformer computation — it produces identical outputs — but reduces the peak activation memory per layer from $8 b s h$ to $2 b s h$ bytes.

### 3.2 Big-Picture Architecture (Diagram in Words)

The system has three major components, all operating within a single Transformer layer:

1. **Blockwise Self-Attention Engine** — computes exact (non-approximate) multi-head attention incrementally over blocks of the input sequence. It splits the query, key, and value sequences into chunks, processes them in a double loop, and maintains running normalization statistics (online softmax) to combine partial results. This component is architecturally identical to the attention mechanism in FlashAttention and Memory Efficient Attention — the paper explicitly builds on their blockwise formulation.

2. **Fused Feedforward Network** — applied per query block immediately after that block's attention is computed. It performs the standard two-layer FFN transformation ($xW_1 + b_1 \rightarrow \text{ReLU} \rightarrow xW_2 + b_2$) but only on a small chunk of the sequence at a time, followed by a residual connection. This is the novel component that distinguishes BPT from prior work.

3. **Nested Loop Controller** — the outer loop iterates over $B_q$ query blocks, and for each query block, the inner loop iterates over $B_{kv}$ key-value blocks. This controller also manages gradient checkpointing (rematerialization) of the FFN and the accumulation of outputs into the final tensor.

Information flows through the system as follows:

- **Step 1:** The input sequence $x \in \mathbb{R}^{b \times s \times h}$ is projected into query $Q$, key $K$, and value $V$ via learned linear projections (as in a standard Transformer layer).
- **Step 2:** The query sequence is split into $B_q$ blocks (each of size $c$ along the sequence dimension), and the key/value sequences are split into $B_{kv}$ blocks (also of size $c$).
- **Step 3 (outer loop):** For each query block $Q_i$ (where $i$ ranges from 1 to $B_q$):
  - **Step 3a (inner loop):** For each key-value block pair $(K_j, V_j)$ (where $j$ ranges from 1 to $B_{kv}$):
    - Compute the attention score matrix for this pair of blocks: $Q_i K_j^T$, scaled by $1/\sqrt{d}$ and with positional bias added.
    - Track the running maximum score and running sum of exponentiated scores (softmax denominator) to enable numerically stable softmax computation without materializing the full row.
    - Compute the weighted value $(\text{softmax} \cdot V_j)$ and accumulate it into a running numerator, appropriately rescaled when a new maximum is encountered.
  - **Step 3b:** After the inner loop completes, the accumulated numerator is divided by the accumulated denominator to produce the exact attention output for query block $i$.
  - **Step 3c:** The feedforward network (with gradient checkpointing applied) processes this attention output, producing the FFN output for block $i$.
  - **Step 3d:** A residual connection adds the original query block $Q_i$ (before projection) to both the attention output and the FFN output: $\text{Output}_i = \text{FFN}(\text{Attention}(Q_i) + Q_i^{\text{input}}) + \text{Attention}(Q_i) + Q_i^{\text{input}}$.
- **Step 4:** All block outputs $\text{Output}_i$ are concatenated along the sequence dimension to form the final output of the Transformer layer.

The system is architecturally identical to a standard Transformer — the same linear projections, the same attention computation, the same FFN weights, the same residual connections. The only difference is the **order** in which computations are performed and the **granularity** at which intermediate tensors are materialized and discarded.

#### Online Softmax and Blockwise Attention (The Foundation BPT Builds On)

The starting point for BPT is the observation from Milakov and Gimelshein (2018) that the softmax function can be computed incrementally over blocks without materializing the full input vector. This "online softmax" or "tiling" technique is what enables exact blockwise attention with $O(s)$ memory.

**Standard softmax requires two passes over the data.** For a vector $v = [v_1, v_2, \ldots, v_n]$, the standard numerically stable softmax computation is:

$$\text{softmax}(v_i) = \frac{\exp(v_i - m)}{\sum_{j=1}^n \exp(v_j - m)}$$

where $m = \max(v_1, \ldots, v_n)$ is the maximum value in the vector, subtracted for numerical stability (preventing exponentiation of large positive numbers).

**What it computes:** Each element $v_i$ is transformed into a positive value that sums to 1 across all $i$. The max-subtraction trick ensures the largest argument to $\exp$ is 0, avoiding overflow.

**Why this form is problematic for blockwise computation:** Both the maximum $m$ and the denominator sum require a complete pass over all $n$ elements. If the vector is split into blocks, computing the softmax for one block requires knowing the global maximum and global sum, which depend on other blocks.

**The key insight of online softmax:** You can process blocks sequentially and maintain three running statistics — the current maximum value $m$, the current sum of exponentiated values $\ell$, and the current weighted sum of values $a$ — and update all three correctly when a new maximum is discovered in a later block.

Specifically, for attention computation, the softmax is applied row-wise to the matrix $QK^T/\sqrt{d}$. For a single query vector $q$ (one row of $Q$), the attention output is:

$$\text{Attention}(q, K, V) = \frac{\sum_{j} \exp(q \cdot k_j / \sqrt{d}) \cdot v_j}{\sum_{j} \exp(q \cdot k_j / \sqrt{d})}$$

**What it computes:** A weighted average of all value vectors $v_j$, where each weight is proportional to $\exp(q \cdot k_j / \sqrt{d})$ — the exponentiated scaled dot-product between the query and that key. Vectors with higher dot-product scores contribute more to the output.

**Why blockwise computation works:** If we process the key-value pairs in blocks, for each block $j$ we compute the block-specific quantities: the maximum dot-product score in that block $m_j$, the sum of exponentiated scores in that block $\ell_j$, and the weighted sum of values in that block $a_j$. We can then merge block $j$ into the running statistics using:

$$m_{\text{new}} = \max(m_{\text{old}}, m_j)$$

$$\ell_{\text{new}} = \ell_{\text{old}} \cdot \exp(m_{\text{old}} - m_{\text{new}}) + \ell_j \cdot \exp(m_j - m_{\text{new}})$$

$$a_{\text{new}} = a_{\text{old}} \cdot \exp(m_{\text{old}} - m_{\text{new}}) + a_j \cdot \exp(m_j - m_{\text{new}})$$

**What these update rules do:** When a new maximum $m_{\text{new}}$ is discovered (larger than the previous running maximum $m_{\text{old}}$), all previously accumulated statistics must be "down-weighted" by multiplying by $\exp(m_{\text{old}} - m_{\text{new}})$, which is less than 1. This is the same correction that would have been applied if the global maximum were known from the start — it's just applied retroactively. After processing all blocks, the final attention output for query $q$ is $a_{\text{final}} / \ell_{\text{final}}$.

**Why this enables $O(s)$ memory:** At no point is the full $s \times s$ attention matrix stored. Only the running statistics ($m$, $\ell$, $a$) for each query need to be maintained, and these are of size proportional to the number of queries times the head dimension — $O(s \cdot d_{\text{head}})$ rather than $O(s^2)$.

The paper's Algorithm 1 (and the JAX implementation in Figure 3) implements exactly this pattern. In the inner loop (`scan_kv_block`), for each key-value block, the dot products `attn_weights = jnp.einsum('bqhd,bkhd->bqhk', query_chunk, key_chunk)` are computed, the running maximum is updated (`max_score = jnp.maximum(prev_max_score, max_score)`), the previously accumulated numerator and denominator are corrected (`numerator = numerator * correction + exp_values`, where `correction = jnp.exp(prev_max_score - max_score)`), and the loop continues.

#### Fusing the Feedforward Network Into the Query-Block Loop (The Core Innovation)

The paper's central technical contribution is the observation that the blockwise computation pattern is not restricted to self-attention — it can be extended to the feedforward network by nesting the FFN computation **inside the outer query-block loop**.

**What the standard Transformer does:** After computing attention for all queries (producing an output tensor of shape $[b, s, d_{\text{model}}]$), the entire attention output is fed through the FFN. The FFN computes:

$$\text{FFN}(x) = \max(0, xW_1 + b_1)W_2 + b_2$$

where $W_1 \in \mathbb{R}^{d_{\text{model}} \times d_{\text{ff}}}$ and $W_2 \in \mathbb{R}^{d_{\text{ff}} \times d_{\text{model}}}$ are learned weight matrices, and $d_{\text{ff}}$ is typically $4 \cdot d_{\text{model}}$. The intermediate activation (after the first linear layer and ReLU) has shape $[b, s, d_{\text{ff}}]$, requiring $b \cdot s \cdot d_{\text{ff}}$ floating-point numbers to be stored.

**Why this is a problem:** With gradient checkpointing, the FFN's maximum activation size is $8 b s h$ bytes (where $h = d_{\text{model}}$). For a 13B model ($h = 5140$) with batch size 1 and sequence length 65536, this is $8 \cdot 1 \cdot 65536 \cdot 5140 \approx 2.69$ GB — per layer. With 40 layers and activation recomputation, the peak memory is on the order of tens of gigabytes, overwhelming available HBM.

**What BPT does differently:** For each query block $i$, after the inner loop over key-value blocks completes and produces the attention output for that query block, the FFN is applied **immediately** to just that block:

$$\text{Output}_i = \text{FFN}\big(\text{Attention}(Q_i, K, V) + Q_i^{\text{input}}\big) + \text{Attention}(Q_i, K, V) + Q_i^{\text{input}}$$

**What this equation computes:** For the $i$-th chunk of the input sequence, it first computes the exact multi-head attention (using the blockwise procedure over all key-value chunks), adds the residual connection from the original input to that chunk, passes the result through the fully connected feedforward network, and adds a second residual connection from the attention output. The structure is identical to a standard Transformer's "attention + residual + FFN + residual" pattern — it's just restricted to a single query block.

**Why the FFN can be applied per-block:** The feedforward network is **position-wise** — it applies the identical transformation to each position in the sequence independently. There are no interactions between positions in the FFN (unlike self-attention, which mixes information across positions). This means the FFN output for position $t$ depends only on the input at position $t$, not on inputs at other positions. Therefore, there is no mathematical requirement to have the full sequence's attention outputs available before computing the FFN — any subset of positions can be processed independently.

**The memory benefit:** By computing the FFN on a block of size $c$ (where $c = s / B_q$) rather than the full sequence of size $s$, the intermediate FFN activation size drops from $b \cdot s \cdot d_{\text{ff}}$ to $b \cdot c \cdot d_{\text{ff}}$ — a factor of $s/c = B_q$ reduction. With gradient checkpointing applied to the FFN (the `remat_ffn` in the implementation), the peak activation for the FFN is $8 b c h$ bytes per block rather than $8 b s h$ bytes for the full sequence.

**The interaction with attention memory:** In the outer loop, the system must store:
- The current query block's attention output: $2 b c h$ bytes (with gradient checkpointing, the forward activations before the FFN are recomputed during backward, but the query block's output from the inner loop must be preserved for the FFN backward pass)
- The accumulated final output tensor: $2 b s h$ bytes (this is the concatenation of all query blocks' outputs — it grows as the outer loop progresses, since the layer's output must be complete before the next layer can begin)

The larger of these two terms is $2 b s h$ bytes, which becomes the total activation memory per BPT layer.

**The gradient checkpointing (`remat_ffn`) details:** The FFN is applied with gradient checkpointing, meaning its intermediate activations (the large $d_{\text{ff}}$-dimensional vectors after the first linear layer and ReLU) are not stored during the forward pass. During the backward pass, the FFN forward computation is re-executed for the current block to regenerate these intermediates. This trades a modest amount of extra computation (recomputing the FFN forward pass once per block) for eliminating the storage of $\sim 8 b c h$ bytes of activations. The implementation uses JAX's `jax.checkpoint` (or equivalently `jax.remat`) to wrap the FFN call.

**The nested loop structure in Algorithm 1:**

```
Initialize:
  Project input x into Q, K, V
  Split Q into B_q blocks
  Split K, V into B_kv blocks

for outer = 1 to B_q:
  Choose the outer-th query block Q_i
  for inner = 1 to B_kv:
    Choose the inner-th key block K_j and value block V_j
    Compute attention(Q_i, K_j, V_j), record normalization statistics
  Combine blocks by scaling to get attention output for Q_i
  Compute FFN(attention_output + Q_i) + attention_output + Q_i
```

**What the outer loop does:** For each chunk of queries (sized $c$), it computes the full attention over all key-value chunks, producing a chunk of attention outputs. This chunk is immediately consumed by the FFN and residual connection to produce the final output for that chunk.

**What the inner loop does:** For a fixed query chunk, it iterates over all key-value chunks, accumulating the running softmax statistics (numerator, denominator, max score) as described in the online softmax section. After the inner loop, the accumulated numerator divided by the accumulated denominator yields the exact attention output for every position in the query chunk.

**A subtle correctness guarantee:** The key-value blocks are the **same** for every query block iteration in the outer loop. This means the full set of key-value pairs is processed $B_q$ times — once per query block. While this increases the total computation (each key-value block is re-read from memory and re-processed $B_q$ times, once for each query block), it ensures that each query block receives exactly the same attention output it would in a standard Transformer where the full attention matrix is computed at once. There is no approximation — the blockwise computation with online softmax rescaling produces mathematically identical results to the full-materialization approach.

**The positional bias handling:** In the JAX implementation (Figure 3), a chunk-based positional bias is computed via `_chunk_bias_fn(query_chunk_idx, key_chunk_idx)`. This avoids materializing the full positional bias matrix by computing only the bias values for the specific pair of chunks currently being processed. The bias is added to the attention weights before the softmax, preserving the standard relative or absolute positional encoding scheme.

#### Detailed Memory Cost Analysis: Why BPT Reduces Activation Memory 4×

Section 3.1 provides a line-by-line accounting of the activation memory required during the forward pass for three architectures: the vanilla Transformer, FlashAttention/Memory Efficient Attention, and BPT. All analyses assume gradient checkpointing is used (so activations are not stored for the backward pass unless explicitly checkpointed).

**Vanilla Transformer attention memory:**

- Input $x$ to the attention layer: $2 b s h$ bytes (stored for backward)
- Query and Key activations for $QK^T$ matmul: $4 b s h$ bytes (stored for backward)
- Input to softmax ($QK^T$ matrix): $2 b s^2 a$ bytes, where $a$ is the number of attention heads
- Softmax attention matrix: $2 b s^2 a$ bytes (stored for backward for the score × V operation)
- Value activations for score × V matmul: $2 b s h$ bytes
- Output projection input and dropout mask: $2 b s h + b s h$ bytes

The dominant term is $O(s^2)$, making the attention mechanism the primary bottleneck. For $s = 8192$ with $b=1$, $h=2048$, $a=16$, the $2 b s^2 a$ term alone is $2 \cdot 1 \cdot 8192^2 \cdot 16 \approx 2.15$ GB — just for the softmax matrix at one layer.

**Vanilla Transformer FFN memory:**

- Input to first linear layer: $2 b s h$ bytes
- Input to activation function (after first linear): $8 b s h$ bytes (the intermediate $d_{\text{ff}}$ dimension is $4h$, so $2 \cdot b \cdot s \cdot 4h = 8 b s h$)
- Input to second linear layer: $8 b s h$ bytes
- Dropout mask: $b s h$ bytes

The dominant term is $8 b s h$ bytes. With gradient checkpointing, the maximum FFN activation size is $8 b s h$ bytes — this is the peak memory during the FFN computation.

**FlashAttention / Memory Efficient Attention memory:**

The attention mechanism is computed blockwise, so the $O(s^2)$ terms are eliminated. The attention sub-layer's memory is dominated by the query output activations (the attention outputs for the full sequence, stored to feed into the FFN), which require $2 b s h$ bytes.

However, the FFN is **unchanged** from the vanilla Transformer. The FFN still requires $8 b s h$ bytes of activation memory.

Crucially, the total per-layer activation memory is the **maximum** of the attention peak and the FFN peak (or their sum if they don't overlap in the computation graph). Since the FFN peak ($8 b s h$) exceeds the attention peak ($2 b s h$), the FFN is the bottleneck:

> "each Flash Attention layer's memory cost is 8bsh" (Section 3.1)

**BPT memory:**

**Attention sub-layer:** Identical to FlashAttention — the inner loop over key-value blocks avoids materializing the full attention matrix, and only the query block's activations need to be stored during the inner loop. With gradient checkpointing, the maximum attention activation is $2 b s h$ bytes (the query output activations for the full sequence, which must be accumulated across outer loop iterations).

**FFN sub-layer:** Because the FFN is applied per query block of size $c$, the intermediate activation size is $8 b c h$ bytes (the FFN intermediate dimension is $4h$, and with gradient checkpointing this is the peak for one block). Additionally, storing the output of the outer loop (the concatenated block outputs) requires $2 b s h$ bytes. Since $c \ll s$, the $8 b c h$ term is negligible compared to $2 b s h$, and the per-layer activation memory is:

> "each BPT layer's memory cost of activation is 2bsh" (Section 3.1)

**The 4× reduction:** FlashAttention requires $8 b s h$ bytes per layer; BPT requires $2 b s h$ bytes per layer. The ratio is $8/2 = 4$, meaning BPT uses **4× less activation memory** per layer than the prior state-of-the-art memory-efficient Transformers. This directly enables training on sequences that are 2–4× longer (since total memory includes parameters, optimizer states, and other overhead, not just activations — the actual context length scaling depends on the proportion of total memory consumed by activations).

**A breakdown of why the FFN dominates in FlashAttention:**

In a Transformer layer with FlashAttention, the computation flow is:
1. Compute Q, K, V projections from input $x$: activations stored ($2 b s h$ bytes for each)
2. Compute blockwise attention: avoids materializing $QK^T$, only stores per-block intermediates and final attention output
3. Store full attention output: $2 b s h$ bytes (this tensor has shape $[b, s, h]$, same as the input)
4. Feed attention output through FFN: the first linear layer produces intermediate activations of shape $[b, s, 4h]$, requiring $8 b s h$ bytes to store (twice the bytes because of the gradient checkpointing policy — storing the input to the ReLU activation)

Step 4 is the peak. Even though the attention is memory-efficient, the FFN must still process the entire sequence at once because it receives the complete attention output. BPT eliminates step 3's full-sequence storage by feeding each query block directly into the FFN, so the FFN never sees a tensor larger than $[b, c, h]$ at a time.

#### Why Blockwise Parallelization Is Practical Despite Sequentialization

Section 3.2 addresses a natural concern: if blockwise computation introduces sequential dependencies between blocks (the outer loop must process query blocks one at a time), doesn't this hurt throughput by underutilizing parallel hardware?

The paper's answer is nuanced and depends on the model size and sequence length:

**Large models or extremely long sequences may already saturate device compute on a single block.** In modern GPUs and TPUs, arithmetic density — the ratio of compute operations to memory accesses — determines whether a computation is compute-bound or memory-bound. For a sufficiently large block (determined by the chunk size $c$, batch size $b$, and hidden dimension $h$), the matrix multiplications within one block's attention and FFN computation may fully utilize the device's compute units. In this regime, trying to process the full sequence in parallel (as a standard Transformer does) would exceed the device's compute capacity, causing the computation to be memory-bandwidth-bound rather than compute-bound. Blockwise computation effectively trades parallelism for reduced memory pressure, but when the parallelism was already exceeding what the hardware could exploit, this trade is essentially free.

> "In cases where the model is large or the context length is extremely long, a block may reach its maximum arithmetic density, making it impractical to execute the original full-length sequence in parallel." (Section 3.2)

**SRAM vs. HBM speed differences make blockwise computation attractive regardless.** Modern accelerators have a hierarchy of memory: a small, fast on-chip memory (SRAM, typically ~20-40 MB on A100 GPUs) and a large, slow off-chip memory (HBM, typically 40-80 GB). Accessing SRAM is an order of magnitude faster than accessing HBM. Blockwise computation keeps the working set of each block in SRAM, reducing costly HBM reads and writes. This is the same insight that motivated FlashAttention's IO-aware design (Dao et al., 2022), and BPT extends it to the FFN.

> "By utilizing blockwise parallelization, we can tap into the increased speed of SRAM, thereby reducing communication costs and increasing throughput." (Section 3.2)

**The outer loop's sequential dependency is between query blocks, not within them.** The inner loop over key-value blocks can be executed with full parallelism within each iteration (the key-value blocks are independent for a fixed query block). And within the outer loop, different Transformer layers can be pipelined — while layer $L$ is processing query block $i$, layer $L+1$ can already begin processing query block $i-1$ if the computation graph allows. This means the effective sequentialization overhead is much less than a naive $B_q \times$ slowdown.

**Empirical throughput results support this argument.** Table 4 shows that at sequence lengths where both BPT and FlashAttention can run (2K, 8K, 16K), BPT achieves slightly higher throughput: 1.04× at 2K, 1.15× at 4K, 1.17× at 8K, 1.2× at 16K. This speedup is attributed to reduced HBM accesses from the fused FFN computation. At 32K, where FlashAttention can still run but BPT achieves 1.1× throughput over it, and at 64K, where only BPT can run at all, BPT maintains 600 tokens per second per device.

**The fundamental tradeoff:** BPT trades some degree of parallelism (sequentializing the outer query-block loop) for dramatically lower memory usage. For deployments where memory is the binding constraint — which is the case for long-context training of large models — this tradeoff is clearly favorable, as evidenced by BPT training on sequences 2-4× longer than alternatives.

#### Implementation Details: The JAX Code Structure

Section 3.3 and Figure 3 provide the key implementation functions in JAX. The code reveals several important implementation-level design decisions.

**The `blockwise_ffn` function:**

The FFN is wrapped with `jax.checkpoint` (aliased as `remat_ffn`) and then applied in a blockwise manner using `nn.scan`. The `rearrange` operation splits the input of shape `[b, s, d]` into shape `[b, B_q, c, d]` (reshaping along the sequence dimension into chunks of size `c`). The `scan_ffn` function processes one chunk at a time, and `nn.scan` iterates over the chunks along the sequence axis. Importantly, `nn.scan` with `variable_broadcast="params"` ensures that the same FFN parameters are used for every chunk — the FFN weights are shared across positions, which is correct because the FFN is position-wise. The `split_rngs={"params": False, "dropout": True}` setting means that the same parameter random seed is used (no parameter noise) but different dropout masks are applied to each chunk.

**Why `nn.scan` rather than a Python loop:** JAX's `scan` primitive compiles the loop body once and executes it efficiently, with the ability to carry state across iterations. It also enables the XLA compiler to optimize across loop iterations and fuse operations. For a position-wise operation like the FFN, scanning over chunks produces identical results to processing the full sequence at once.

**The `blockwise_attn` function:**

This implements the online softmax attention over query and key-value chunks. The query is first scaled by $1/\sqrt{d}$ and then split into chunks along the sequence dimension. The key and value sequences are similarly chunked.

The outer scan (`lax.scan` at the bottom of `blockwise_attn`) iterates over query chunks (and their indices). For each query chunk, the inner scan (`lax.scan` inside `scan_kv_block` within `scan_attention`) iterates over key-value chunks.

**The `scan_kv_block` inner function details:**

For a specific (query_chunk, key_chunk, value_chunk, key_chunk_idx) tuple, the function:
1. Computes attention weights via `jnp.einsum('bqhd,bkhd->bqhk', query_chunk, key_chunk)`. This is a batched matrix multiplication producing scores of shape `[batch, query_chunk_size, num_heads, key_chunk_size]`.
2. Computes chunk-wise positional bias via `_chunk_bias_fn(query_chunk_idx, key_chunk_idx)` and adds it to the attention weights.
3. Determines the running maximum score: `max_score = jnp.maximum(prev_max_score, max_score)`, where `prev_max_score` was carried from previous key-value blocks.
4. Applies a `stop_gradient` to the maximum — this is a numerical stability detail: the maximum is used for scaling but should not contribute to gradients (it is a non-differentiable operation).
5. Computes exponentiated weights with the current maximum correction: `exp_weights = jnp.exp(attn_weights - max_score)`.
6. Computes the weighted value sum for this block: `exp_values = jnp.einsum('bqhv,bvhf->bqhf', exp_weights, value_chunk)`.
7. Computes the correction factor for previously accumulated statistics: `correction = jnp.exp(prev_max_score - max_score)`. If `max_score > prev_max_score`, this is less than 1, down-weighting the old numerator and denominator. If `max_score == prev_max_score`, this is 1, leaving them unchanged.
8. Applies the correction and accumulates: `numerator = numerator * correction + exp_values` and `denominator = denominator * correction + exp_weights.sum(axis=-1, keepdims=True)`.

**Initialization of the running state:**

The initial carry for the inner scan is:
- `numerator`: zeros of shape `[batch, query_chunk_size, num_heads, dim_per_head]`
- `denominator`: zeros of the same shape
- `prev_max_score`: $-\infty$ for each position, ensuring the first block's maximum is always larger

**After the inner scan completes:** The accumulated numerator is divided by the accumulated denominator: `outputs = (numerator / denominator).astype(dtype)`. This yields the exact multi-head attention output for the query chunk. The output then flows through the FFN per the overall BPT layer structure.

**Gradient checkpointing policies:**

The paper tunes checkpointing policies for the attention computation. The three policies explored are:
- `nothing_saveable`: no intermediate tensors are saved; everything is recomputed during backward
- `dots_saveable`: the dot-product results are saved (reducing recomputation cost at the expense of some memory)
- `dots_with_no_batch_dims_saveable`: dot-product results with batch dimensions collapsed are saved

The `blockwise_attn` function uses `jax.checkpoint` with the configured policy and `prevent_cse` flag (preventing common subexpression elimination that could inadvertently materialize full tensors). The FFN uses `nothing_saveable` (maximum memory saving, accepting the recomputation cost).

**Block size tuning:**

The paper performs a grid search over query block sizes and key-value block sizes from the set `[16, 64, 128, 512, 1024, 2048, 4096]`, selecting the configuration that achieves the lowest memory usage for each model size and hardware configuration. This is important because the optimal block size depends on the SRAM capacity, the hidden dimension, and the tradeoff between reduced memory (smaller blocks) and increased loop overhead (more iterations).

#### Summary of Design Choices and Their Justifications

- **Fusing FFN into the query-block loop (rather than computing FFN blockwise separately):** If the FFN were computed blockwise but *after* attention completed for the full sequence, the full attention output tensor ($2 b s h$ bytes) would still need to be stored to feed into the blockwise FFN loop. Fusing eliminates this intermediate storage because each query block goes directly from attention to FFN without the full tensor ever existing.

- **Applying gradient checkpointing to the FFN (`remat_ffn`):** The FFN's intermediate activations (the $4h$-dimensional hidden vectors) are the single largest contributor to activation memory in standard and memory-efficient Transformers. Checkpointing these — recomputing them during backward rather than storing them during forward — eliminates $8 b s h$ bytes of storage per layer.

- **Using JAX's `nn.scan` and `lax.scan` rather than manual Python loops:** Scan operations are compiled to efficient XLA primitives, enable automatic fusion with surrounding operations, and correctly handle the rematerialization and gradient flow through the loop iterations. Manual Python loops would prevent compilation of the loop body.

- **Two-level nested loops ($B_q$ outer, $B_{kv}$ inner) rather than a single level:** The outer loop over query blocks is necessary because the FFN must be applied per-query-block to achieve the memory reduction. The inner loop over key-value blocks is the standard online softmax iteration from prior work. The double loop is the minimal structure that achieves both attention and FFN blockwise processing.

- **Chunk-based positional bias computation:** Materializing the full $s \times s$ positional bias matrix would defeat the purpose of blockwise computation. Computing it per chunk pair and adding it to the attention logits before softmax preserves the exact positional encoding behavior without the memory cost.

- **Re-reading key-value blocks $B_q$ times:** This is the computational cost of the memory reduction. Each key-value block is loaded from HBM and processed once per query block. For typical block sizes and model dimensions, the increased computation is acceptable because the bottleneck is memory capacity, not compute throughput — and the alternative is being unable to train at all due to out-of-memory errors.

## 4. Key Insights and Innovations

### Innovation 1: Identifying the Feedforward Network as the True Memory Bottleneck in Memory-Efficient Transformers

The paper's most consequential intellectual move is a diagnostic one: it identifies that the research community has been solving the wrong problem. Prior to BPT, the narrative around Transformer memory efficiency was entirely attention-centric. The field had converged on a shared assumption: self-attention's $O(s^2)$ memory footprint is the bottleneck, and solving it unlocks long-context training. This assumption was so deeply embedded that the terms "memory-efficient Transformer" and "memory-efficient attention" became nearly synonymous — papers proposing blockwise, sparse, or low-rank attention mechanisms routinely described themselves as solving the Transformer memory problem, not merely the attention sub-problem.

BPT exposes this as a category error. The insight is not that feedforward networks consume memory (that was always known), but rather that **once attention memory is reduced to $O(s)$, the feedforward network becomes the dominant consumer — and prior work had no mechanism to address it**. The paper's memory accounting in Section 3.1 makes this quantitative: FlashAttention reduces attention's contribution to $2bsh$ bytes per layer, but the FFN still demands $8bsh$ bytes. The FFN is responsible for 4× more activation memory than the already-optimized attention. This means that for any model where sequence length pushes FFN activations above the HBM capacity, further improvements to attention are entirely wasted — they cannot increase maximum context length because the FFN ceiling remains.

This is a **fundamental reframing**, not an incremental improvement. It shifts the optimization target from "how do we compute attention with less memory?" to "how do we restructure the entire layer computation graph so that the FFN's memory peak is reduced?" This reframing has implications beyond BPT itself: it suggests that future work on Transformer memory efficiency should benchmark against the FFN bottleneck, not just the attention bottleneck, and that reported context-length improvements from attention-only methods may be misleading if they don't account for the FFN's dominance at scale.

The evidence for this claim is the systematic memory analysis in Section 3.1 and the fact that FlashAttention/Memory Efficient Attention hit a context-length ceiling (e.g., 16K for a 3B model on one A100, Table 2) even though their attention mechanism could theoretically handle much longer sequences. BPT breaks through this ceiling not by improving attention further but by addressing the FFN — the problem FlashAttention didn't solve.

### Innovation 2: Fusing Feedforward and Attention Computation Into a Single Blockwise Pass

The second innovation is a **structural insight about the Transformer computation graph**: if self-attention is computed blockwise (iterating over query blocks in an outer loop and key-value blocks in an inner loop), then the feedforward network can be fused into that same loop structure, applied to each query block immediately after its attention is resolved, *before* moving to the next query block. Prior to BPT, the standard approach — even in memory-efficient Transformers — treated attention and feedforward as sequential stages: compute attention for the full sequence (perhaps blockwise, but producing the complete output tensor), then feed that tensor through the FFN. The attention output tensor ($bsh$ elements) was an unavoidable intermediate that had to be stored between these stages.

BPT's insight is that this intermediate storage is unnecessary because the FFN is **position-wise** — it applies identically to each sequence position independently. There is no cross-position mixing in the FFN (unlike attention), so there is no computational dependency that requires all positions' attention outputs to be available before FFN processing can begin. By applying the FFN per query block, the attention output for that block is consumed immediately, and its storage can be released before the next block's attention is computed. The full attention output tensor never exists in memory at any single point in time.

What makes this conceptually distinctive is that it treats the Transformer layer not as a pipeline of operations but as a **spatially decomposable computation** where each chunk of the output can be computed independently. This is not obvious from the standard Transformer formulation, which presents the layer as "attention over the whole sequence, then FFN over the whole sequence." BPT reveals that this sequential description is an implementation choice, not a mathematical requirement — the layer's computation can be reordered into a "compute one chunk completely, then move to the next" pattern without changing the output.

The significance of this fusion extends beyond the memory savings. It demonstrates that **optimizing Transformer memory requires thinking about the interaction between sub-layers, not just optimizing each sub-layer in isolation**. FlashAttention optimized the attention sub-layer. BPT optimizes the *interface* between attention and FFN — eliminating the intermediate tensor that connected them. This is a different class of optimization, more akin to operation fusion in compiler design than to algorithmic improvement of individual operations.

The evidence is the memory analysis showing the reduction from $8bsh$ to $2bsh$ per layer (Section 3.1), and the context-length scaling results (Table 2) showing BPT achieving 2-4× longer sequences than FlashAttention across model sizes from 1B to 70B parameters.

### Innovation 3: Establishing That Activation Memory, Not Compute, Is the Binding Constraint for Long-Context Training

BPT makes an implicit but powerful argument about the nature of the scaling bottleneck. The paper does not claim to reduce FLOPs — in fact, BPT increases total computation because each key-value block must be re-read and re-processed $B_q$ times (once per query block). Yet BPT enables training on dramatically longer sequences. This reveals that **memory capacity, not computational throughput, is the binding constraint** when training Transformers on long contexts.

This framing challenges a common intuition in deep learning systems design, where compute is often treated as the primary scarce resource and memory as a secondary concern. For long-context training, the hierarchy is inverted: devices have abundant compute (and it's parallelizable across more devices), but HBM capacity is fixed per device and cannot be easily expanded. Activation memory scales with sequence length, and when it exceeds HBM capacity, training becomes impossible regardless of how much compute is available. BPT works not by being computationally more efficient (it's slightly more compute-intensive due to re-reading key-value blocks) but by **trading compute for memory** — recomputing or serializing operations to reduce the peak memory footprint.

This tradeoff is crystallized in the throughput results (Table 4). At sequence lengths where both FlashAttention and BPT can run (2K-16K), BPT achieves marginally higher throughput (1.04-1.2×) because the reduced HBM accesses from fusing the FFN more than compensate for the extra key-value block reads. At 32K, FlashAttention runs but BPT achieves 1.1× throughput. At 64K, **only BPT runs at all** — FlashAttention runs out of memory. The throughput at 64K (600 tokens/device/second) is lower than at shorter lengths, but the critical point is that there is a throughput to measure at all. BPT converts an impossible training run into a feasible one by reducing memory, not by reducing compute.

This insight has practical implications for how researchers and engineers should think about scaling. If memory is the binding constraint, then optimizations that reduce memory at the cost of additional compute (gradient checkpointing, activation recomputation, blockwise serialization) are not just acceptable — they're the **only viable scaling strategy** for long contexts. The paper implicitly argues that the field's focus on FLOPs efficiency and throughput benchmarks may be misdirected for long-context work; maximum sequence length at a given memory budget is the more relevant metric.

### Innovation 4: Demonstrating That Long-Context Training Directly Improves Reinforcement Learning Performance

While the RL experiments (Section 5.3, Table 5) are an application rather than a core contribution to the architecture, they establish an important empirical finding: **scaling context length through memory-efficient training directly translates to improved task performance** in a domain where long contexts are necessary for optimal results.

The original Agentic Transformer (AT; Liu and Abbeel, 2023) conditioned on 4 trajectories of (state, action, reward, next-state) tuples to learn policies from the ExoRL dataset. With each trajectory spanning 1000 timesteps × 4 tokens, this produced sequences of 16K tokens — manageable with standard Transformers. However, the dataset contains 8000 trajectories collected by 8 different unsupervised RL algorithms, and conditioning on more trajectories provides the model with richer contextual information about diverse behaviors and their outcomes. Scaling to 32 or 64 trajectories (128K-256K tokens) was infeasible with vanilla or FlashAttention Transformers due to memory constraints.

BPT removes this constraint, enabling AT to condition on 32 trajectories during training and 16 during testing. The results are striking: AT + BPT achieves an average return of 111.13 across six ExoRL tasks, compared to 83.02 for AT with 4 trajectories — a 34% relative improvement. On individual tasks, the gains are substantial: Cheetah Run improves from 125.68 to 178.75 (+42%), Walker Stand from 68.55 to 95.45 (+39%), Jaco Reach from 52.98 to 87.56 (+65%).

What makes this intellectually significant is that it **validates the premise of the entire paper**. BPT's memory reduction is not just an engineering curiosity — it enables a qualitatively different kind of model (one that conditions on an order of magnitude more contextual information) that was previously impossible to train, and this model demonstrably outperforms its shorter-context counterpart. The RL results close the loop from "we can train on longer sequences" to "training on longer sequences matters for downstream performance."

The finding also suggests a general principle that may extend beyond RL: in any domain where additional context provides useful signal (multi-document reasoning, long-form generation, codebase understanding), memory-efficient training that enables longer contexts should yield performance improvements — provided the base architecture can effectively utilize the additional context. This is an empirical hypothesis that the paper demonstrates for one domain but does not test broadly, making it a productive direction for follow-up work.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** The paper uses two datasets: **OpenWebText** (Gokaslan and Cohen, 2019) for language modeling experiments, a filtered collection of over 6 billion tokens from more than 40 million web pages covering diverse topics; and **ExoRL** (Yarats et al., 2022) for reinforcement learning experiments, consisting of 8 million timesteps (8000 episodes) of exploratory data collected by eight different unsupervised RL algorithms on continuous control tasks, with each episode spanning 1000 steps. The OpenWebText split follows the methodology of nanoGPT (Andrej, 2023). The ExoRL benchmark includes six tasks: Walker Stand, Walker Run, Walker Walk, Cheetah Run, Jaco Reach, and Cartpole Swingup.

- **Base model(s).** The language modeling experiments use the **GPT architecture** at six scales: 1B (1.3B parameters, 24 layers, $d_{model}=2048$, 16 heads), 3B (2.7B parameters, 32 layers, $d_{model}=2560$, 32 heads), 7B (6.7B parameters, 32 layers, $d_{model}=4096$, 32 heads), 13B (13.0B parameters, 40 layers, $d_{model}=5140$, 40 heads), 30B (30.0B parameters, 48 layers, $d_{model}=7168$, 56 heads), and 70B (70.0B parameters, 80 layers, $d_{model}=8192$, 64 heads). The RL experiments use a smaller Transformer with 3 layers, 1 attention head, and embedding dimension 128, following the Agentic Transformer (Liu and Abbeel, 2023) configuration. All experiments use full precision (float32), not mixed precision, which the authors explicitly note because mixed precision would further reduce memory and potentially amplify or diminish the relative advantage of BPT.

- **Metrics.** Three primary metrics are used: **(1) Maximum context length** — the longest sequence length that can be trained without exceeding device memory, measured in tokens and determined by incrementally increasing sequence length until an out-of-memory (OOM) error occurs; **(2) Memory usage** — peak GPU/TPU memory consumption in gigabytes, profiled using `jax.profile` and averaged over 100 repetitions; **(3) Throughput** — tokens processed per device per second during training. For RL experiments, the metric is **cumulative return** on each ExoRL task, following the evaluation protocol from Yarats et al. (2022), with the total average return computed across all six tasks. For the language modeling throughput experiments, validation loss is also reported to confirm that BPT does not change model quality (training convergence is not affected by the computation reordering).

- **Baselines.** Three baselines are compared: **(1) Vanilla Transformer** (Vaswani et al., 2017) — standard attention that materializes the full $QK^T$ matrix and computes the FFN on the full sequence; **(2) MemoryEfficient** — which encompasses both FlashAttention (Dao et al., 2022) for GPU experiments and Memory Efficient Attention (Rabe and Staats, 2021) for TPU experiments, since they share the same blockwise attention approach but are optimized for different hardware; **(3) AT + ME** — the Agentic Transformer using MemoryEfficient attention, evaluated on ExoRL tasks. All baselines use the same gradient checkpointing policies as BPT where applicable. The RL baselines also include Behavior Cloning (BC-10%), Decision Transformer (DT; Chen et al., 2021), and the original Agentic Transformer (AT; Liu and Abbeel, 2023) with 4 trajectories, with numbers taken from the ExoRL and AT papers.

- **Generation budget / compute accounting.** The paper measures memory and throughput at training time, not inference time. The unit of "compute" is not directly budgeted — rather, the experiments measure **what sequence length is achievable given a fixed memory budget** (the HBM capacity of the hardware). For fair comparison, all methods use the same model architecture, same batch size, same gradient checkpointing policies (tuned per-method via grid search), and same hardware. The block size for both BPT and the baselines is tuned via grid search over `{16, 64, 128, 512, 1024, 2048, 4096}` to find the lowest-memory configuration for each method. Throughput comparisons are made at the same context length, same batch size in tokens (1 million tokens per batch via gradient accumulation), and same hardware configuration, with the best-performing gradient checkpointing policy selected for each method.

- **Cross-validation / statistical protocol.** No cross-validation is used. Memory and throughput measurements are deterministic given the model configuration and block sizes. Memory profiling is repeated 100 times and averaged to account for measurement noise. For RL experiments, the paper reports cumulative returns following the standard ExoRL evaluation protocol but does not report error bars, confidence intervals, or multiple seeds. This is a notable limitation — single-run RL results can be highly variable, and without multiple seeds, the reported improvements (e.g., AT + BPT achieving 111.13 vs. AT's 83.02 total average return) should be interpreted cautiously.

### Main Quantitative Results

#### Maximum Context Length Scaling (Memory Capacity Results)

The headline result is that BPT enables training sequences **2–4× longer than MemoryEfficient attention** and **up to 32× longer than vanilla attention** across model scales and hardware configurations. Table 2 provides the complete results, organized by hardware setting.

**Single A100 GPU (80GB), models up to 3B parameters:**

For the 350M and 1B models, all three methods fit within 80GB, but the maximum achievable sequence lengths differ dramatically:
- Vanilla: 16,384 tokens
- MemoryEfficient: 65,536 tokens (4× over Vanilla)
- BPT: 131,072 tokens (2× over MemoryEfficient, 8× over Vanilla)

For the 3B model:
- Vanilla: 8,192 tokens
- MemoryEfficient: 16,384 tokens (2× over Vanilla)
- BPT: 65,536 tokens (4× over MemoryEfficient, 8× over Vanilla)

The progression reveals that MemoryEfficient's advantage over Vanilla shrinks as model size increases (from 4× at 1B to 2× at 3B), while BPT's advantage over MemoryEfficient grows (from 2× at 1B to 4× at 3B). This pattern is consistent with the paper's claim that the FFN becomes the dominant bottleneck as model size increases: larger models have larger $d_{model}$ and $d_{ff}$, making the FFN's $8bsh$ term proportionally larger relative to the fixed HBM capacity.

**8× A100 GPUs (model parallelism, 80GB each), models 3B to 30B:**

With model parallelism distributing parameters across 8 GPUs, the activation memory per device becomes the binding constraint. Results:
- **3B:** BPT reaches 131,072 tokens vs. MemoryEfficient's 65,536 and Vanilla's 16,384
- **7B:** BPT reaches 131,072 tokens vs. MemoryEfficient's 65,536 and Vanilla's 16,384
- **13B:** BPT reaches 65,536 tokens vs. MemoryEfficient's 32,768 and Vanilla's 8,192
- **30B:** BPT reaches 65,536 tokens vs. MemoryEfficient's 16,384 and Vanilla's 8,192

At 30B, BPT enables 4× longer sequences than MemoryEfficient and 8× longer than Vanilla. The absolute maximum sequence length of 65,536 tokens for a 30B model on 8 GPUs is the most practically significant result — it represents training a GPT-3-scale model on full-length book chapters or long documents, which was impossible with prior methods.

**64 TPUv4 devices, models 13B to 70B:**

On TPUs, the maximum sequence lengths are lower because TPUv4 HBM capacity is smaller than A100 (32GB vs. 80GB), but the relative advantage of BPT persists:
- **13B:** BPT reaches 32,768 tokens vs. MemoryEfficient's 16,384 and Vanilla's 4,096
- **30B:** BPT reaches 16,384 tokens vs. MemoryEfficient's 4,096 and Vanilla's 2,048
- **70B:** BPT reaches 8,192 tokens vs. MemoryEfficient's 2,048 and Vanilla's 1,024

At 70B, BPT enables 4× longer sequences than MemoryEfficient and 8× longer than Vanilla. The 1,024-token limit for Vanilla at 70B is effectively unusable for most long-context applications; BPT's 8,192 tokens, while modest, at least reaches the context lengths that were standard for smaller models.

The results for 70B models are presented in Figure 1 alongside the 1B to 30B results for visual comparison, showing BPT's consistent advantage across the full range of model scales.

#### Memory Usage Analysis

Table 3 provides detailed memory consumption comparisons at specific (model, hardware, sequence length) configurations, confirming that BPT's memory advantage comes from reducing activation memory, not from any change to parameter or optimizer storage.

**3B model on a single A100:**

| 8,192 | 64 GB | 44 GB | 43 GB |
| 16,384 | OOM | 47 GB | 45 GB |

At 8,192 tokens, BPT uses only 43 GB vs. MemoryEfficient's 44 GB — a marginal 1 GB saving, because at short context lengths the FFN activation memory ($8bsh$) is not yet the dominant term. The gap widens as sequence length increases: at 65,536 tokens, BPT saves 5 GB (70 vs. 75 GB). The most dramatic result is at 131,072 tokens, where BPT fits within 79 GB (just under the 80 GB limit) while MemoryEfficient cannot run at all.

The pattern is identical: BPT saves 2-7 GB compared to MemoryEfficient, with the savings increasing at longer sequence lengths. The 7 GB saving at 65,536 tokens (68 vs. 75 GB) is the difference between fitting and not fitting for a 80 GB device with other overhead.

The memory usage results directly support the paper's central claim that BPT reduces per-layer activation memory from $8bsh$ to $2bsh$. The measured memory savings correspond to the expected reduction in FFN activation storage: at 65,536 tokens with a 13B model on 8 GPUs (so per-GPU batch size is effectively 1/8 of the model parallelism shard), the FFN intermediate activations scale with $b \cdot s \cdot 4h$, and avoiding storing these on the full sequence saves tens of gigabytes.

#### Throughput and Training Speed

Table 4 presents throughput comparisons for the GPT-1B model on OpenWebText using 8 GPUs, measured in tokens per device per second.

**At context lengths where all methods can run (2K-16K):**

BPT achieves comparable or slightly higher throughput than MemoryEfficient while dramatically reducing memory usage:
- 2,048 tokens: BPT achieves 3,985 tokens/sec vs. MemoryEfficient's 4,371 (0.91× — slightly slower) and Vanilla's 3,827 (1.04×)
- 4,096 tokens: BPT achieves 2,687 vs. MemoryEfficient's 2,567 (1.05×) and Vanilla's 2,340 (1.15×)
- 8,192 tokens: BPT achieves 2,875 vs. MemoryEfficient's 2,781 (1.03×) and Vanilla's 2,455 (1.17×)
- 16,384 tokens: BPT achieves 2,045 vs. MemoryEfficient's 1,889 (1.08×) and Vanilla's 1,701 (1.20×)

The speedup over Vanilla increases with context length (from 1.04× at 2K to 1.20× at 16K), consistent with the growing cost of materializing the full attention matrix in Vanilla. The marginal throughput advantage over MemoryEfficient (1.03-1.08×) suggests that the fused FFN computation reduces HBM accesses enough to offset the extra key-value block re-reads inherent in BPT's double-loop structure.

At 2,048 tokens, BPT is actually slightly slower than MemoryEfficient (3,985 vs. 4,371 tokens/sec). This is the only configuration where BPT underperforms, and it likely occurs because at very short context lengths, the overhead of the double-loop structure (scan setup, block indexing, carry state management) dominates the memory access savings. As context length grows, the memory savings become more significant relative to the loop overhead.

**At context lengths where only BPT can run:**

- 32,768 tokens: BPT achieves 857 tokens/sec vs. MemoryEfficient's 810 tokens/sec (1.06×). MemoryEfficient can still run at this length, but BPT is faster.
- 65,536 tokens: BPT achieves 600 tokens/sec. MemoryEfficient and Vanilla are both OOM — there is no comparison to make.

The 600 tokens/sec at 65K context length demonstrates that BPT's training speed, while reduced from shorter contexts (as expected — longer sequences require more computation per batch), is still practical. A 1B model training at 600 tokens/device/second on 8 GPUs processes ~4,800 tokens/second total, meaning a 1M token batch takes ~3.5 minutes per step. This is slower than training at 2K context but represents a qualitatively different training regime (conditioning on full documents rather than paragraphs).

**Validation loss consistency:**

Table 4 also reports validation loss per context length, and crucially, the validation loss is **identical** across all three methods at the same context length:
- At 2,048: Vanilla 2.46, MemoryEfficient 2.46, BPT 2.46
- At 4,096: all three at 2.44
- At 8,192: all three at 2.43
- At 16,384: all three at 2.41

This confirms that BPT's computation reordering produces mathematically identical outputs to the standard Transformer — there is no approximation, no information loss, and no impact on model quality. The validation loss decreases with context length (2.46 → 2.41) because longer contexts provide more information per training example, which is expected for language modeling and is independent of the attention mechanism.

Table 5 presents the cumulative returns on the ExoRL benchmark, comparing behavior cloning, decision transformer, the original Agentic Transformer (AT) with 4 trajectories, and AT augmented with MemoryEfficient or BPT to condition on 32 trajectories during training.

**AT + BPT with 32 trajectories vs. AT with 4 trajectories:**

BPT enables conditioning on 32 trajectories (128K tokens: 32 × 1000 × 4), which is impossible with Vanilla or MemoryEfficient attention due to OOM. The performance improvement is substantial and consistent across all six tasks:

| Task | AT (4 trajs) | AT + BPT (32 trajs) | Improvement |
|---|---|---|---|
| Walker Stand | 68.55 | 95.45 | +39.2% |
| Walker Run | 88.56 | 105.88 | +19.6% |
| Walker Walk | 64.56 | 78.56 | +21.7% |
| Cheetah Run | 125.68 | 178.75 | +42.2% |
| Jaco Reach | 52.98 | 87.56 | +65.3% |
| Cartpole Swingup | 97.81 | 120.56 | +23.3% |
| **Total Average** | **83.02** | **111.13** | **+33.9%** |

The largest relative improvements are on Jaco Reach (+65.3%) and Cheetah Run (+42.2%), both of which involve complex continuous control with sparse rewards where conditioning on diverse trajectories likely helps the model identify successful strategies. The smallest improvement is on Walker Run (+19.6%), which is a relatively simpler locomotion task.

**AT with MemoryEfficient at 32 trajectories:** Both Vanilla and MemoryEfficient attention run OOM when attempting to train with 32 trajectories on a 350M parameter model, as noted in the table (all entries are "oom"). This is the key enabling contribution: without BPT, the experiment is impossible; with BPT, it achieves state-of-the-art results. The 350M model size used for RL is much smaller than the language models tested in the memory scaling experiments, which suggests that even modestly sized Transformers hit the FFN memory bottleneck when sequence lengths reach hundreds of thousands of tokens.

**AT + BPT vs. prior methods:** AT + BPT's total average return of 111.13 substantially exceeds BC-10% (36.11), DT (45.51), and the original AT with 4 trajectories (83.02). It also exceeds AT conditioned on 32 trajectories using MemoryEfficient, but only because the latter cannot run — the comparison is between a feasible method (BPT) and infeasible baselines. This is a case where memory efficiency is not just a performance improvement but an **enabling capability** — without BPT, the experiment cannot be conducted at all.

**Test-time configuration:** During testing, the number of trajectories is limited to 16 (rather than 32) to reduce autoregressive sampling time. The paper notes that "performing autoregressive sampling over a large number of trajectories (e.g., 64 × 1000 × 4 total number of tokens) can be computationally slow." This is a practical concession: BPT reduces training memory, but inference still requires generating tokens autoregressively, and the wall-clock time for sampling 64 trajectories would be prohibitive. The fact that performance improves even when testing with fewer trajectories than training (16 vs. 32) suggests that the model learns transferable patterns from the additional training context.

### Ablation Studies and Robustness Checks

**Block size tuning:** The paper performs a grid search over query and key-value block sizes from `{16, 64, 128, 512, 1024, 2048, 4096}` for all methods, reporting "the lowest memory achieved" for each. No ablation table is provided showing how memory usage varies with block size, but the methodology description implies that block size significantly impacts memory because: (a) smaller blocks reduce the $bch$ term (where $c$ is the block size) but increase loop overhead and the number of iterations; (b) larger blocks increase the per-block activation memory but reduce the number of outer-loop iterations and associated overhead. The optimal block size is hardware-dependent (balancing SRAM capacity against loop efficiency), and the paper's grid search ensures fair comparison.

**Gradient checkpointing policy:** The paper grid-searches among three checkpointing policies for attention: `nothing_saveable`, `dots_saveable`, and `dots_with_no_batch_dims_saveable`. The FFN always uses `nothing_saveable` (maximum memory saving). The best-performing policy is selected for each method, which is important because the memory-throughput tradeoff differs between Vanilla (where saving dot products dramatically reduces recomputation), MemoryEfficient (where blockwise computation changes what's worth saving), and BPT (where the fused FFN changes the memory profile again). The paper does not report which policy was selected for which configuration, but the fact that each method gets its own tuned policy ensures the comparison is fair in terms of achievable memory-throughput Pareto frontier.

**Full precision vs. mixed precision:** All experiments use full precision (float32) rather than mixed precision (float16/bfloat16). This is an important design choice for the ablation: mixed precision would reduce memory by approximately 2× for activations (since float16 uses 2 bytes vs. float32's 4 bytes) and would change the relative importance of FFN vs. attention memory. The paper does not run mixed-precision experiments, which means the reported 4× reduction from $8bsh$ to $2bsh$ applies to the full-precision setting. In mixed precision, the absolute memory savings would be smaller, but the relative reduction would be identical since all methods would benefit equally from the precision reduction.

**Single-sequence evaluation (no data parallelism):** The paper explicitly states that "no data parallelism is considered in our evaluations since our approach is independent of data parallelism. As a result, the batch sizes used in our analysis are much lower than the ones used for the end-to-end training." This means the reported maximum sequence lengths are **with batch size 1** along the data-parallel dimension (model parallelism may still be used to shard parameters). In practice, training with data parallelism would multiply the activation memory by the per-device batch size, potentially reducing the maximum sequence length. The paper's reported maxima should therefore be understood as upper bounds — the achievable sequence length in a full training run with typical batch sizes (e.g., 8-64) would be lower unless activation memory is further reduced through techniques like activation offloading or more aggressive gradient checkpointing.

**Validation loss as a correctness check (Table 4):** The identical validation loss across all three methods at every context length serves as an implicit ablation confirming that BPT's computation reordering does not introduce numerical differences. This is critical because the online softmax with blockwise rescaling involves multiple floating-point operations (exponentiation, max, division) that could theoretically accumulate numerical errors differently from the full-materialization approach. The identical validation loss confirms that any numerical differences are below the threshold that affects training dynamics or model quality.

**Number of trajectories in RL (Table 5):** The RL results implicitly ablate the number of conditioning trajectories. The original AT used 4 trajectories; BPT enables 32. The jump from 83.02 to 111.13 total average return demonstrates that additional trajectories provide useful signal. However, the paper does not include intermediate values (e.g., 8 or 16 trajectories) to show whether performance scales smoothly with context length or saturates. This is a missing ablation that would strengthen the claim that longer contexts are responsible for the improvement rather than some other property of BPT.

**Model scales (Table 2):** The paper evaluates BPT across six model sizes (1B to 70B), which serves as a de facto ablation over model scale. The consistent 2-4× improvement over MemoryEfficient across all scales suggests the FFN bottleneck is universal, not specific to a particular model size. However, the ratio of improvement does vary: at 1B on a single GPU, BPT achieves 2× over MemoryEfficient; at 3B, 4×; at 30B and 70B, 4×. The paper does not analyze why the ratio varies, but it likely relates to the proportion of total memory consumed by FFN activations vs. other fixed costs (parameters, optimizer states, attention activations).

### Critical Assessment

#### Claim 1: BPT enables training sequences 32× longer than vanilla Transformers and 4× longer than memory-efficient methods.

**What the experiments demonstrate:** Table 2 provides unambiguous evidence for the relative improvements. Across model sizes and hardware configurations, BPT consistently achieves 2-4× longer sequences than MemoryEfficient and 4-32× longer than Vanilla. The 32× figure comes from specific configurations (e.g., 1B model on single GPU: Vanilla max 16K, BPT max 131K; 131K/16K ≈ 8×, not 32× — the 32× appears to come from different configurations, possibly the 13B on 8 GPUs where Vanilla reaches 8K vs. BPT's 131K for 7B, giving ~16×). The paper's abstract claims 32× and 4×; Table 2 supports these as best-case ratios across experiments, not as uniform improvements.

**What the experiments do not demonstrate:** The maximum sequence lengths are measured with batch size 1 (no data parallelism, possibly with model parallelism). In a realistic training setup with data parallelism (batch size > 1 per device), the available memory per sequence would be proportionally lower, and the maximum sequence length would decrease. The reported 131K-token context on a single GPU for a 1B model may not be achievable with a typical batch size of 8 or 16. The paper's memory analysis focuses on activations per sequence, but total memory includes parameters, optimizer states, and activations multiplied by batch size. The relative advantage of BPT (4× over MemoryEfficient) should still hold because both methods' activation memory scales linearly with batch size, but the absolute sequence lengths would be lower. The absence of data-parallel experiments means the practical value of the reported maxima is unclear.

Additionally, the experiments measure *training* sequence length only. The paper does not report whether inference (which does not require storing activations for backward) benefits similarly from BPT. For autoregressive generation where tokens are produced one at a time, the FFN memory bottleneck is less severe because only the current token's activations need to be stored (not the full sequence). The paper's contribution is specifically about training-time memory, which is important because training on long contexts is prerequisite to deploying models that can handle them.

#### Claim 2: The feedforward network, not attention, is the dominant memory bottleneck in memory-efficient Transformers.

**What the experiments demonstrate strongly:** The memory analysis in Table 3 shows that MemoryEfficient attention reaches OOM at sequence lengths where BPT still fits, and the gap is exactly what would be predicted from the $8bsh$ vs. $2bsh$ per-layer activation memory analysis. At 65,536 tokens with a 3B model, MemoryEfficient uses 75 GB while BPT uses 70 GB; at 131,072 tokens, only BPT fits (79 GB). The 5-10 GB savings correspond directly to the avoided storage of FFN intermediate activations on the full sequence. The fact that MemoryEfficient — which already has $O(s)$ attention memory — cannot reach the same context lengths as BPT is direct evidence that something other than attention is the bottleneck, and the only other major memory consumer is the FFN.

**Nuance the paper acknowledges:** The memory analysis (Section 3.1) explicitly accounts for gradient checkpointing and shows that with optimal checkpointing, the FFN's $8bsh$ term is the maximum activation size. This relies on the assumption that gradient checkpointing eliminates other large tensors (the $bs^2a$ terms from Vanilla attention). The paper verifies this assumption by using the same checkpointing policies across all methods and confirming that MemoryEfficient's maximum activation is indeed $8bsh$.

**What is not demonstrated:** The paper does not provide a breakdown of actual per-layer memory usage from profiling (e.g., showing that attention activations consume X GB and FFN activations consume Y GB at a given sequence length). The $8bsh$ vs. $2bsh$ analysis is a theoretical accounting that is consistent with the total memory measurements; a per-component memory profile would provide direct confirmation. Without this, the claim that the FFN specifically (as opposed to some other implementation detail) is the bottleneck rests on the analytical model, which is convincing but not experimentally verified at the component level.

#### Claim 3: BPT achieves competitive or better throughput compared to memory-efficient methods while using less memory.

**What the experiments demonstrate with qualification:** Table 4 shows that at context lengths 4K-65K, BPT achieves 1.03-1.20× the throughput of MemoryEfficient while using substantially less memory. At 2K, BPT is slightly slower (0.91×). The throughput advantage is modest but consistent at longer sequences, suggesting that the fused FFN computation's memory access savings offset the overhead of the double-loop structure. At 65K, where MemoryEfficient cannot run at all, BPT's throughput of 600 tokens/sec is a valid standalone measurement.

**What weakens this claim:** The throughput measurements are for a single model size (1B) and a single hardware configuration (8 GPUs). It is unclear whether the throughput advantage persists at larger model scales, different hardware, or different parallelism strategies. Larger models have proportionally more parameters and optimizer states, which may change the compute-vs-memory tradeoff. Additionally, the throughput advantage over MemoryEfficient is small (3-8% at most lengths), and at 2K it reverses. The practical significance of a 1.03-1.08× throughput improvement is marginal — the primary value of BPT is the memory reduction, not the throughput. The paper appropriately does not emphasize throughput as a primary contribution.

#### Claim 4: BPT enables conditioning on 32 trajectories in RL, improving performance by 34% over the original Agentic Transformer.

**What the experiments demonstrate:** Table 5 shows AT + BPT with 32 trajectories achieving 111.13 total average return vs. 83.02 for AT with 4 trajectories. The improvement is on all six tasks, and BPT makes the experiment possible (both alternatives OOM). This claim is well-supported at face value.

**Weaknesses in the experimental design:**

- **Single run, no error bars:** The paper does not report standard deviations, confidence intervals, or multiple random seeds for the RL experiments. RL training is notoriously high-variance; a single-run improvement of 34% could be partially attributable to random seed effects. The ExoRL benchmark paper (Yarats et al., 2022) reports results over multiple seeds; the absence here weakens the claim.

- **Conflating context length with architecture:** The 34% improvement is attributed to conditioning on 32 trajectories instead of 4, but BPT also changes the computation graph (double-loop structure, gradient checkpointing policies). It is extremely unlikely that the computation reordering itself improves task performance (since BPT produces identical outputs to a standard Transformer), but the paper does not rule out that some other implementation detail differs between the AT and AT+BPT runs (e.g., different random seeds, different hyperparameter tuning, different checkpointing affecting optimization dynamics). Ideally, the paper would train AT with 4 trajectories using BPT to confirm identical performance to AT with 4 trajectories using Vanilla attention, isolating the context length as the sole variable.

- **No intermediate context lengths:** The paper jumps from 4 to 32 trajectories. Showing performance at 8, 16, and 32 trajectories would establish whether longer contexts monotonically improve performance, whether there are diminishing returns, and whether the full 32 trajectories are necessary. The missing data makes it impossible to know whether 32 trajectories are significantly better than 16 or 24, or whether most of the gain comes from the first jump beyond 4.

- **Test-time mismatch:** The model is trained on 32 trajectories but tested on 16 (for speed). The paper does not explain whether this mismatch was also present in the original AT (which trained on 4 and tested on 4, per the AT paper), and does not ablate whether training on 32 but testing on 16 is better than training and testing on 16. This confound makes it unclear whether the improvement comes from the additional training context or from some beneficial effect of the train-test trajectory count mismatch.

#### Missing Experiments That Would Strengthen the Paper

- **Mixed-precision results:** All experiments use float32, but most large-scale Transformer training uses bfloat16 or float16. Showing that BPT's 4× memory reduction persists (or changes) in mixed precision would be practically important. In mixed precision, the FFN's $8bsh$ bytes becomes $4bsh$ (since bfloat16 uses 2 bytes), potentially changing the relative importance of FFN vs. attention memory.

- **Data-parallel scaling:** The experiments use batch size 1 per device. Showing maximum sequence length with typical batch sizes (e.g., 8, 16, 32) would provide practitioners with realistic expectations for training throughput and memory usage.

- **Per-component memory profiling:** A breakdown showing exactly how much memory is used by attention activations, FFN activations, parameters, and optimizer states for each method at a given sequence length would directly confirm the analytical model in Section 3.1.

- **Convergence speed and model quality:** The paper reports validation loss in Table 4, confirming identical outputs, but does not show training curves or downstream task evaluations to confirm that BPT-trained models achieve the same final quality as Vanilla-trained models. While identical per-step validation loss suggests identical training dynamics, confirming this over a full training run would be valuable.

- **Larger RL model or more trajectories:** The RL experiments use a tiny Transformer (3 layers, 128-dim embeddings, ~350M parameters). Showing that BPT enables training a larger RL model (matching the scale of the language models) on even more trajectories (64 or 128) would strengthen the claim that BPT unlocks qualitatively different capabilities.

- **Comparison to sequence parallelism:** The paper mentions that BPT is orthogonal to sequence parallelism (Korthikanti et al., 2022) but does not compare against it or combine with it. Sequence parallelism also reduces per-device activation memory by distributing sequence chunks across devices. A comparison showing BPT's memory reduction vs. sequence parallelism's, and whether they compose multiplicatively, would clarify BPT's position in the design space.

## 6. Limitations and Trade-offs

### 6.1 All Experiments Are Limited to a Single Model Family, Single Domain, and Single-Implementation Framework

**The assumption or constraint:** Every result in the paper — memory scaling, throughput, context length ceilings, and RL performance — is obtained using GPT-style decoder-only Transformers implemented in JAX. The six model scales (1B to 70B) all use the same architectural template: post-layer-norm, ReLU feedforward activations, standard multi-head attention. The paper does not test encoder-decoder architectures (T5, BART), models with different FFN structures (GELU, SwiGLU, GLU variants), or models using alternative attention mechanisms beyond standard scaled dot-product attention. Furthermore, all experiments use the JAX framework with its specific `scan`, `checkpoint`, and XLA compilation behavior; the paper does not implement or evaluate BPT in PyTorch, TensorFlow, or custom CUDA kernels. As the authors acknowledge in Section 7:

> "While our implementation prioritizes simplicity with high-level Jax operations, optimizing low-level operations is crucial for achieving optimal performance. In future work, we suggest considering porting our method to CUDA and OpenAI Triton to achieve minimal memory cost and maximum speedup."

**The consequence:** The headline `4×` memory reduction over FlashAttention depends on the FFN-to-attention activation memory ratio of `8bsh / 2bsh = 4×`. This ratio is specific to the GPT architecture with `d_ff = 4 · d_model` and ReLU activation. Architectures using SwiGLU or other gated FFN variants have three weight matrices instead of two (gate, up, down projections), potentially doubling the intermediate activation footprint. In such architectures, the FFN bottleneck would be *even more severe*, and BPT's savings proportionally larger — or conversely, if an architecture already implements memory optimizations for the FFN (e.g., activation recomputation at a finer granularity than the whole layer), BPT's advantage might shrink. Without testing across FFN variants, the paper cannot claim the `4×` factor generalizes.

The model-family constraint also matters for adoption: a team using PyTorch and HuggingFace Transformers cannot directly use BPT without reimplementing the nested-scan logic (which relies on JAX's `lax.scan` and `nn.scan` primitives for efficient compilation of the loop body). The paper's JAX implementation (Figure 3) is 62 lines and depends on specific JAX features (eigenstring notation, `jax.checkpoint` with `prevent_cse`, `nn.scan` with `variable_broadcast`). Porting this to PyTorch while maintaining the same memory reduction would require careful handling of autograd's gradient tape and would likely need custom CUDA kernels to match the memory access pattern — a non-trivial engineering effort the paper does not estimate.

The domain constraint limits evidence for the paper's motivating claims. The introduction argues that long contexts are needed for "high-resolution images, podcasts, code, or books," but the only application evaluated beyond language modeling is reinforcement learning on continuous control (ExoRL). Vision Transformers, which process image patches as tokens and have different memory profiles (larger hidden dimensions, smaller sequence lengths typically), are not tested. Machine translation, code generation, and long-document QA — all prominent long-context applications — are absent.

**What evidence exists in the paper:** The paper presents results exclusively on GPT models and ExoRL (Sections 4–5). Table 1 lists the six GPT configurations. The RL experiments use a custom 3-layer architecture with embedding dimension 128. No encoder-decoder, vision transformer, or non-JAX results appear anywhere. The implementation section (3.3) and Figure 3 are JAX-specific.

**Mitigation status:** The limitation is partially acknowledged in the Limitation and Future Work section ("porting our method to CUDA and OpenAI Triton"), but this addresses only the implementation framework aspect, not the architecture or domain coverage. The paper does not discuss how BPT's memory reduction would change for GELU FFNs, SwiGLU FFNs, cross-attention, or encoder-decoder models. No non-JAX implementation or benchmark is provided. The limitation is open and significant for practitioners evaluating whether to adopt BPT.

### 6.2 Blockwise Sequentialization Introduces a Latency-Throughput Tradeoff That Is Not Characterized

**The assumption or constraint:** BPT replaces the standard Transformer computation order — compute attention for the entire sequence, then apply FFN to the entire sequence — with a double-loop structure where the outer loop iterates sequentially over $B_q$ query blocks. Each query block's attention and FFN must complete before the next query block can begin. While this reduces peak activation memory, it **serializes computation that was previously parallelizable** across the sequence dimension. The paper addresses this concern qualitatively in Section 3.2:

> "In cases where the model is large or the context length is extremely long, a block may reach its maximum arithmetic density, making it impractical to execute the original full-length sequence in parallel."

The argument is that for large models or long sequences, the hardware is already saturated processing a single block, so the lost parallelism is not actually lost — the hardware couldn't exploit additional parallelism anyway. This argument depends on the block size, model size, batch size, and hardware characteristics, none of which are systematically varied in the analysis.

**The consequence:** For smaller models or shorter sequences, the sequentialization overhead may substantially reduce throughput, and the paper's throughput measurements (Table 4) partially confirm this: at 2,048 tokens, BPT's throughput (3,985 tokens/sec) is 9% *lower* than MemoryEfficient's (4,371 tokens/sec), even though BPT uses less memory. This reversal at the shortest context length suggests that when the FFN's memory footprint is not the binding constraint (because the sequence is short enough to fit comfortably), the overhead of the double-loop structure dominates any memory-access savings. A practitioner training a relatively small model (e.g., 350M parameters) on moderately long sequences (e.g., 8K-16K tokens) might find that FlashAttention provides better throughput with adequate memory headroom, making BPT's memory savings unnecessary.

More critically, the paper measures only training throughput (tokens processed per second) — it does not measure **latency** (wall-clock time for a single forward-backward pass). In a distributed training setup, latency matters for pipeline parallelism efficiency, gradient synchronization frequency, and fault tolerance. BPT's outer loop over query blocks adds a sequential dimension: all $B_q$ iterations must complete before the layer output is ready to feed into the next layer. If $B_q = 32$ (e.g., splitting a 65K sequence into 2K-token blocks), the layer's forward pass involves 32 sequential iterations, each with an inner loop over key-value blocks. The total wall-clock time for one layer is at least $B_q$ times the time to process one query block (plus key-value loop overhead), whereas a standard Transformer processes all positions in parallel for both attention and FFN. For inference, where autoregressive generation already serializes token-by-token, BPT's additional serialization would compound latency — but the paper does not evaluate inference at all.

**What evidence exists in the paper:** Table 4 provides the only throughput comparison, at context lengths from 2K to 65K, for the 1B model on 8 GPUs. At 2K, BPT is slower than MemoryEfficient (0.91×). At 4K and above, BPT is marginally faster (1.03-1.08×). At 32K, BPT achieves 1.06× throughput; at 65K, only BPT runs. No latency measurements, no throughput measurements at larger model scales (3B, 7B, 13B, 30B, 70B), and no scaling analysis of how the sequentialization overhead changes with $B_q$ (the number of query blocks) are provided.

**Mitigation status:** Section 3.2 provides a qualitative argument that blockwise computation can be efficient when blocks reach maximum arithmetic density, but no quantitative analysis supports this. The paper does not discuss the block-size-throughput tradeoff, does not provide a model for predicting when BPT's throughput exceeds FlashAttention's (e.g., as a function of sequence length, model dimension, and SRAM size), and does not address inference latency at all. The limitation is largely unaddressed — a practitioner cannot determine from the paper whether BPT will be faster or slower than FlashAttention for their specific model size, sequence length, and hardware configuration without running their own benchmarks.

### 6.3 The Memory Analysis Excludes Data Parallelism, Overstating the Absolute Sequence Lengths Achievable in Realistic Training

**The assumption or constraint:** All memory and maximum-sequence-length experiments (Tables 2–3, Figure 1) use a **batch size of 1** in the data-parallel dimension. The paper is explicit about this in Section 4:

> "We note that no data parallelism is considered in our evaluations since our approach is independent of data parallelism. As a result, the batch sizes used in our analysis are much lower than the ones used for the end-to-end training."

The reasoning is that data parallelism multiplies all activation memory by the per-device batch size, so BPT's relative advantage over other methods (the 4× reduction) is unchanged. This is mathematically correct: if BPT uses 4× less activation memory per sample, it uses 4× less per sample regardless of batch size. But it ignores a crucial practical consequence: the absolute maximum sequence length that can be trained *decreases* as batch size increases, because total activation memory scales as `batch_size × sequence_length × hidden_dimension`.

**The consequence:** The headline numbers in the abstract — "training sequences 32 times longer than vanilla Transformers and up to 4 times longer than previous memory-efficient methods" — are best-case values measured at batch size 1. In a realistic training setup, practitioners typically use batch sizes of at least 8–64 samples per device for training stability and throughput. At batch size 8, the activation memory is 8× larger, and the maximum sequence length must drop by approximately 8× to fit in the same HBM budget. A configuration that achieves 131K-token context at batch size 1 would only support roughly 16K tokens at batch size 8 — which is close to what FlashAttention already supports at batch size 1. The relative advantage of BPT (2-4× over FlashAttention) persists, but the absolute sequence lengths that BPT enables in a realistic training run are much less dramatic than the abstract suggests.

Concretely: the paper reports that BPT trains a 70B model on 8,192 tokens using 64 TPUv4 devices (Table 2). This is with batch size 1 per device. A typical large-scale training run for a 70B model might use batch size 16 or 32 (with gradient accumulation to maintain a large effective batch size). At batch size 16, the maximum sequence length would be approximately 8,192 / 16 ≈ 512 tokens — which is shorter than the 2,048 tokens that GPT-3 used. This does not mean BPT is useless at batch size 16; it means BPT's practical value for large-model training depends heavily on whether training can succeed with very small per-device batch sizes (compensated by gradient accumulation across many steps).

The paper also does not discuss how BPT interacts with **gradient accumulation**. If a target effective batch size of 512 samples is achieved by using a per-device batch size of 1 and accumulating gradients over 512 steps, the training throughput is very different (and likely much lower) than using a per-device batch size of 16 and accumulating over 32 steps. The latency of each step (time to process one micro-batch) determines how long the 512-step accumulation takes. Since BPT's latency characteristics are not measured (see Limitation 6.2), a practitioner cannot estimate the wall-clock time for a full training run at batch size 1 with heavy gradient accumulation.

**What evidence exists in the paper:** Table 2 and Figure 1 report results at batch size 1 (explicitly noted in Section 4). Table 3's memory measurements are at batch size 1. The RL experiments use batch size 64 (Table 6), but the sequence length there is fixed by the RL task (32 trajectories × 1000 steps × 4 tokens = 128K); the paper does not explore how RL batch size affects maximum trainable sequence length. No experiments vary batch size to show how maximum sequence length degrades.

**Mitigation status:** The paper acknowledges the batch size limitation explicitly and argues that "our approach is independent of data parallelism." This is technically accurate for the relative comparison but does not address the practical concern about absolute achievable context lengths. The authors do not propose or evaluate strategies for training with larger batch sizes (e.g., combining BPT with activation offloading, sequence parallelism, or more aggressive gradient checkpointing). The limitation is acknowledged but not explored, leaving practitioners uncertain about the practical ceiling on sequence length in their own training setups.

### 6.4 Difficulty Estimation and Strategy Selection Are Not Part of the Framework; No Guidance Is Provided on Tuning Block Sizes or Checkpointing Policies

**The assumption or constraint:** BPT requires selecting several hyperparameters: the query block size (chunk size $c$, which determines $B_q = s/c$), the key-value block size (which determines $B_{kv}$), and the gradient checkpointing policy (one of `nothing_saveable`, `dots_saveable`, `dots_with_no_batch_dims_saveable` for attention, and `nothing_saveable` for FFN). The paper tunes these via grid search:

> "We conducted a grid search for the optimal query block size and key-value block size, considering values from the set [16, 64, 128, 512, 1024, 2048, 4096]. For each method, we reported the lowest memory achieved." (Appendix A.1)

This means the reported memory reductions are **best-case values after exhaustive hyperparameter search** — they are not what a practitioner would achieve by using default or rule-of-thumb settings.

**The consequence:** The grid search over 7 block sizes × 7 block sizes = 49 configurations, plus 3 checkpointing policies, evaluates 147 configurations per method per model size per hardware setting. This is feasible for a research paper but impractical for a practitioner deploying BPT on a new model architecture, new dataset, or new hardware. The paper provides no heuristics, rules of thumb, or analytical model for selecting block sizes. A practitioner who picks a suboptimal block size might get substantially worse memory reduction — potentially erasing most of BPT's advantage and causing out-of-memory at sequence lengths that the paper claims are achievable.

The sensitivity of memory usage to block size is not quantified. At one extreme, a block size that is too small (e.g., 16 tokens) produces many outer-loop iterations ($B_q = s/16$), increasing loop overhead and potentially reducing throughput without proportionally reducing memory (because the fixed costs — storing the output tensor, the query projection, etc. — do not scale with block size). At the other extreme, a block size that is too large (e.g., 4096 tokens for a query block on a model with large $h$) may exceed the SRAM capacity, causing the block's intermediate tensors to spill to HBM and potentially negating the memory savings. The paper acknowledges that the choice matters (by doing a grid search) but does not analyze *how much* it matters — no ablation showing memory vs. block size, no recommendation for how to choose $c$ given $d_{model}$, HBM size, and SRAM size.

Similarly, the checkpointing policy has a significant impact: `nothing_saveable` saves the most memory but requires full recomputation of the attention dot products during backward; `dots_saveable` saves the dot products (increasing memory but reducing recomputation); `dots_with_no_batch_dims_saveable` is an intermediate point. The optimal choice depends on whether the system is memory-bound or compute-bound, which in turn depends on the model size, sequence length, and hardware. The paper provides no guidance on this tradeoff beyond reporting that it selected the best configuration.

**What evidence exists in the paper:** The paper reports that a grid search was performed (Appendix A.1, A.2) but does not present the results: no table showing how memory varies with block size, no figure plotting the memory-throughput Pareto frontier across block sizes, no analysis of which checkpointing policy was chosen for which configuration, and no sensitivity analysis showing whether the optimal block size is sharp (a narrow range works well) or broad (many block sizes achieve similar memory).

**Mitigation status:** Not addressed. The authors do not discuss this as a limitation, propose heuristics for block size selection, or analyze the sensitivity of results to these hyperparameters. For a paper whose primary contribution is practical memory reduction, the absence of deployment guidance is a significant gap. A practitioner reading the paper knows that BPT *can* achieve 4× memory reduction with the right hyperparameters, but does not know how difficult it is to find those hyperparameters or how much performance degrades with suboptimal choices.

### 6.5 The Reinforcement Learning Results Combine Context-Length Scaling with an Uncontrolled Train-Test Mismatch, Confounding the Causal Claim

**The assumption or constraint:** The RL experiments (Section 5.3, Table 5) attribute the performance improvement of AT + BPT (111.13 total average return) over the original AT (83.02) to the increased number of conditioning trajectories (32 vs. 4). However, the experiments also introduce a **train-test mismatch**: the model is trained on 32 trajectories but evaluated on only 16 trajectories during testing. As stated in Appendix A.3:

> "During testing, increasing the number of trajectories has been shown to improve performance. However, performing autoregressive sampling over a large number of trajectories (e.g., 64 × 1000 × 4 total number of tokens) can be computationally slow. To reduce the sampling time, we limited the rollout to 16 trajectories."

The original AT trained on 4 trajectories and was tested on 4 trajectories — no such mismatch existed. The AT + BPT setup changes **both** the training context length (4 → 32) **and** the relationship between training and testing context lengths (matched → mismatched). This means the observed 33.9% improvement cannot be causally attributed solely to longer training contexts; part of the gain could arise from the mismatch itself (e.g., the model learning to generalize from many trajectories to fewer at test time, which might have different properties than training and testing on the same number).

**The consequence:** The central claim of the RL section — that BPT enables improved RL performance by allowing conditioning on more trajectories — is confounded. It is possible that training on 32 trajectories and testing on 16 trajectories would outperform training on 16 and testing on 16, not because 32 is better than 16 per se, but because the mismatch acts as a form of regularization or forces the model to learn a more robust policy that does not depend on the exact number of input trajectories. Alternatively, training on 32 and testing on 16 could perform *worse* than training and testing on 16, if the distribution shift between train and test causes the model to rely on trajectory-count-specific cues that are absent at test time. The paper provides no evidence to distinguish these possibilities.

Furthermore, the paper does not establish a dose-response curve: does performance improve monotonically with the number of training trajectories? Showing results at 4, 8, 16, 24, and 32 trajectories (all tested on the same number, say 16, to isolate the training effect) would demonstrate that the additional context is the causal driver. The jump from 4 to 32 trajectories conflates the effect of additional trajectories with any non-linearities or threshold effects.

The train-test mismatch also raises questions about what the RL results actually demonstrate. If the goal is to show that BPT enables training on longer contexts, the cleanest experiment would be: (a) show that AT + BPT with 4 trajectories matches AT with 4 trajectories (confirming BPT does not change model quality), then (b) show that increasing to 32 trajectories while keeping test conditions matched improves performance. The paper does neither. The absence of the "BPT with 4 trajectories" control makes it impossible to rule out that some implementation difference between the original AT and AT + BPT — different JAX compilation, different checkpointing, different random seeds — contributes to the performance difference.

**What evidence exists in the paper:** Table 5 reports one data point per method. The original AT numbers are taken from the AT paper, not re-run in the same codebase. AT + ME (MemoryEfficient) and AT + BPT are run by the authors, but AT + ME runs OOM at 32 trajectories. No test on matched train-test conditions is provided. The train-test mismatch is disclosed in Appendix A.3 but not discussed as a limitation.

**Mitigation status:** The train-test mismatch is acknowledged as a practical concession to sampling speed but is not analyzed or controlled for. The paper does not report results for AT + BPT with matched train-test counts, does not ablate the number of training trajectories, and does not discuss the confound. The limitation is acknowledged only procedurally (in the appendix), not substantively, and weakens the causal claim that longer contexts are responsible for the RL performance improvement.

### 6.6 There Is No Evaluation of Training Convergence, Downstream Task Quality, or Numerical Stability at Scale; Correctness Is Verified Only at the Per-Step Level

**The assumption or constraint:** The paper treats BPT as producing "identical outputs" to a standard Transformer because the blockwise computation of attention (via online softmax) and the per-block FFN are mathematically equivalent to the full-sequence computation. The evidence for this equivalence is Table 4's validation loss, which is identical across Vanilla, MemoryEfficient, and BPT at each context length (e.g., all three report 2.46 at 2,048 tokens, 2.44 at 4,096). This confirms that, for a single forward-backward step on the validation set, BPT computes numerically identical results to the reference implementation.

However, the paper does **not** evaluate whether this per-step equivalence holds over a full training run, at the largest model scales tested for memory (13B-70B), or at the longest sequence lengths (65K-131K tokens). Training divergence, subtle numerical differences that compound over thousands of gradient steps, and precision-related instabilities at extreme sequence lengths are all unexamined.

**The consequence:** Numerical equivalence per step does not guarantee equivalence over training. BPT introduces many more floating-point operations than a standard Transformer: the online softmax rescaling involves repeated exponentiation, max operations, and division for each block pair, and these operations are applied in a different order than the full-materialization approach. While mathematically equivalent in exact arithmetic, floating-point arithmetic is non-associative — the order of summations and the sequence in which rescaling corrections are applied can produce slightly different results. Over thousands of training steps, these small differences could compound, potentially leading to divergence or different final model quality.

The validation loss in Table 4 is measured at a **single checkpoint** during training, not at convergence. It is possible that BPT and Vanilla produce identical per-step losses early in training but diverge later — especially at the extreme sequence lengths where BPT enables training that Vanilla cannot perform at all (so no comparison is possible). The paper cannot compare 65K-token BPT training to 65K-token Vanilla training because the latter is impossible (OOM). This means the claim of equivalence is only tested in the regime where both methods can run — short to moderate context lengths — and is unverified in the regime that BPT uniquely enables.

A related concern: BPT's nested-loop structure reorders computation in ways that could interact poorly with mixed-precision training (which the paper does not use, but which is standard practice). In particular, the rescaling corrections in the online softmax involve multiplying accumulated values by `exp(prev_max_score - max_score)`, where the exponentiated difference can be extremely small (if a new maximum is much larger than the previous one) or close to 1 (if the new maximum is similar). In float16 or bfloat16, these corrections could underflow or lose precision, causing incorrect attention outputs. The paper's full-precision setting avoids this, but means the numerical stability results do not transfer to the mixed-precision regime most practitioners use for large-scale training.

Finally, the paper provides no downstream evaluation of BPT-trained models. The only quality metric is validation loss (Table 4), which measures next-token prediction perplexity but does not assess whether the model learns useful representations, can perform reasoning tasks, or generalizes to downstream applications. For the RL experiments (Table 5), cumulative return is a downstream metric, but as discussed in Limitation 6.5, the comparison is confounded. A language model trained with BPT on 65K-token contexts might achieve the same validation loss as a standard model trained on 16K-token contexts but perform differently on long-document question answering, summarization, or code completion — tasks that directly leverage the extended context. The paper provides no such evaluation.

**What evidence exists in the paper:** Table 4 provides validation loss at four context lengths (2K, 4K, 8K, 16K) for the 1B model, showing identical values across methods. No training curves, no convergence analysis, no loss values at 32K or 65K (where Vanilla cannot run, so cross-checking is impossible), and no downstream task evaluations. The largest model tested for throughput/loss is 1B parameters; the memory scaling results extend to 70B but without any quality metrics. The paper does not report gradient norm statistics, loss spikes, or any other training stability indicators that might reveal numerical differences.

**Mitigation status:** The paper treats the identical validation loss in Table 4 as sufficient evidence of correctness and does not discuss numerical stability, training divergence, or the limitations of per-step equivalence. The Limitation and Future Work section mentions "Optimal performance" (porting to CUDA/Triton for speed) but not numerical robustness. The absence of training convergence results, mixed-precision evaluation, and downstream task benchmarks represents a significant gap between the paper's systems-level claims and the evidence needed to adopt BPT for training production models. A practitioner considering BPT for a large-scale training run needs to know whether the model will train stably and achieve the same final quality — and the paper provides no evidence on this question.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

BPT fundamentally reframes the Transformer memory bottleneck conversation from an attention-centric narrative to a **feedforward-centric one**. This is not an incremental refinement — it is a diagnostic correction that changes what problem the field should be trying to solve. Prior to BPT, the literature treated "memory-efficient Transformer" and "memory-efficient attention" as roughly synonymous. The research community invested heavily in sparse attention patterns, low-rank approximations, kernel-based linearization, and eventually exact blockwise attention via online softmax — all targeting the $O(s^2)$ attention memory footprint. BPT demonstrates that this investment solved only half the problem: once attention memory is reduced to $O(s)$, the feedforward network becomes the dominant memory consumer (contributing $8bsh$ bytes per layer vs. attention's $2bsh$), and further attention optimizations yield zero additional context-length gains because they leave the FFN bottleneck completely untouched.

The consequence of this reframing is that **the optimization target shifts from "how to compute attention with less memory" to "how to restructure the entire layer computation so that the FFN's memory peak is reduced."** This is a different class of problem. Attention optimizations focused on algorithmic improvements to a specific operation (the softmax over $QK^T$). Addressing the FFN bottleneck requires thinking about the **interface between sub-layers** — eliminating the intermediate tensor that connects attention outputs to FFN inputs — rather than optimizing either sub-layer in isolation. BPT's fusion of FFN into the attention blockwise loop is the first demonstration that this interface can be collapsed, and the 4× memory reduction it achieves establishes a new baseline for what "memory-efficient Transformer" means: the metric is no longer just attention memory, but total per-layer activation memory including the FFN.

The paper also **reconciles a latent contradiction** in the memory-efficient Transformer literature. FlashAttention and Memory Efficient Attention claimed to solve the Transformer memory problem by reducing attention to $O(s)$ complexity. Yet practitioners found that maximum context lengths still hit ceilings well below what $O(s)$ attention alone would predict — for example, a 13B model with FlashAttention on 8 A100s maxes out at 32K tokens (Table 2). BPT explains this gap: the ceiling is set not by attention's $O(s)$ scaling but by the FFN's $8bsh$ activation footprint, which FlashAttention never addressed. The contradiction between "$O(s)$ attention should allow arbitrarily long sequences" and "empirically, sequences are still limited" is resolved by identifying the FFN as the residual bottleneck.

Methodologically, BPT changes the **benchmarking landscape** for Transformer efficiency. Prior work compared methods primarily on attention memory or attention throughput. BPT implies that future efficiency papers must report **total per-layer activation memory with the FFN included**, and that maximum trainable sequence length — not attention-specific metrics — is the gold-standard evaluation. A new attention mechanism that reduces attention memory from $2bsh$ to $1bsh$ would be practically useless if the FFN still demands $8bsh$, because the total activation memory drops only from $10bsh$ to $9bsh$ (a 10% improvement), not 50%. BPT makes this arithmetic inescapable.

The work also demonstrates that **compute and memory are not symmetric resources in long-context training**. BPT increases total FLOPs (each key-value block is re-read and re-processed $B_q$ times) yet enables dramatically longer sequences because memory — not compute — is the binding constraint. This inverts the typical deep learning optimization priority, where FLOPs efficiency is treated as primary. For long-context work, optimizations that are FLOPs-neutral or FLOPs-increasing but memory-reducing (gradient checkpointing, blockwise serialization, activation recomputation) are not just acceptable — they're the only viable scaling strategy when HBM capacity is the hard ceiling.

### Follow-Up Research This Work Enables

**Porting BPT to CUDA and Triton with fused kernels that eliminate loop overhead.** The paper's JAX implementation achieves the memory reduction but relies on high-level `scan` primitives that add loop overhead, particularly at short context lengths where BPT underperforms FlashAttention (0.91× throughput at 2K tokens, Table 4). A low-level implementation with hand-fused CUDA or Triton kernels could merge the outer query-block loop, the inner key-value loop, the online softmax rescaling, and the FFN computation into a single GPU kernel that keeps all intermediates in SRAM. The key experiment: measure throughput and memory at context lengths from 2K to 131K for a 7B model, comparing the JAX implementation against a custom CUDA implementation, and determine whether the throughput inversion at short contexts (where BPT is slower) can be eliminated. FlashAttention's success was driven partly by its custom CUDA kernels achieving higher throughput than naive implementations despite doing the same computation — BPT needs an analogous IO-aware fused kernel to realize its full potential on GPUs. The paper's authors explicitly flag this: "porting our method to CUDA and OpenAI Triton to achieve minimal memory cost and maximum speedup" (Section 7).

**Combining BPT with sequence parallelism to determine whether the memory reductions compose multiplicatively or sub-additively.** Sequence parallelism (Korthikanti et al., 2022) distributes sequence chunks across devices, reducing per-device activation memory by roughly the parallelism degree, but requires communication for the attention computation. BPT operates per-device and is "orthogonal" to sequence parallelism (Section 6). The critical open question: if BPT reduces per-device activation memory by 4× and sequence parallelism across 8 devices reduces it by another ~8×, does the combined system achieve ~32× memory reduction (multiplicative) or does some fixed overhead (e.g., communicating key-value blocks between devices for attention) limit the composability? The experiment would measure maximum sequence length for a 13B model on 8 GPUs under four conditions: (a) FlashAttention without sequence parallelism, (b) FlashAttention with sequence parallelism, (c) BPT without sequence parallelism, (d) BPT with sequence parallelism. If the reductions compose multiplicatively, BPT + sequence parallelism could push trainable context lengths beyond 500K tokens on current hardware.

**Evaluating BPT on SwiGLU and other gated FFN variants to determine whether the memory reduction factor changes.** Modern large language models (LLaMA, PaLM, Chinchilla) use gated FFN variants like SwiGLU, which have three weight matrices (gate, up, down projections) instead of two, and typically use an intermediate dimension of $8/3 \cdot d_{model}$ rather than $4 \cdot d_{model}$. The activation memory footprint of the SwiGLU FFN is different: the gate and up projections both produce intermediate activations, potentially doubling the intermediate storage compared to a standard ReLU FFN. BPT's 4× memory reduction ($8bsh \rightarrow 2bsh$) was derived for the standard two-matrix ReLU FFN. For SwiGLU, the FFN activation memory might be larger (making BPT's savings proportionally greater) or differently structured (the gate activation and the up activation might need to be stored separately). The experiment would implement BPT for a LLaMA-style architecture, measure per-layer activation memory with and without BPT at a fixed sequence length, and compute the new reduction factor. If SwiGLU's intermediate activations are $> 8bsh$, BPT's relative advantage increases, strengthening the case for adoption in modern architectures.

**Establishing a dose-response curve for context length vs. RL performance in the ExoRL benchmark.** The paper's RL experiment (Table 5) convincingly shows that 32 trajectories outperform 4, but the jump from 4 to 32 conflates the effect size. A rigorous follow-up would train Agentic Transformer with BPT at 4, 8, 16, 24, and 32 trajectories, always testing on 16 trajectories (to eliminate the train-test mismatch confound), and report cumulative return with multiple random seeds and confidence intervals for each configuration. The key question: does performance scale monotonically with context length, or are there diminishing returns (e.g., 24 trajectories performs similarly to 32), or even inverse-U effects (too many diverse trajectories confuse the model)? The dose-response curve would establish the "Chinchilla-optimal" context length for RL conditioning — the point beyond which additional trajectories provide negligible benefit — and validate whether the scaling behavior is log-linear (as is common in language modeling) or follows a different functional form. This experiment would also include a BPT-at-4-trajectories control to confirm equivalence with the original AT, isolating context length as the sole causal variable.

**Mixed-precision evaluation and numerical stability analysis at extreme sequence lengths.** The paper uses full precision (float32) for all experiments, but large-scale Transformer training universally uses bfloat16 or float16 to reduce memory and increase throughput. BPT's online softmax involves repeated rescaling by $\exp(m_{\text{old}} - m_{\text{new}})$ where the exponentiated difference can be extremely small when a new maximum is much larger than the previous running maximum. In bfloat16 (which has a minimum positive normal of ~$1.17 \times 10^{-38}$), these corrections could underflow, causing the accumulated numerator or denominator to zero out and producing incorrect attention outputs. The experiment would train a 1B model with BPT in bfloat16 at context lengths of 16K, 32K, and 65K, measuring validation loss and gradient norm statistics over a full training run (not just one step), and comparing against a float32 BPT baseline. The finding would determine whether BPT requires full precision for numerical stability (which would halve its practical memory advantage relative to mixed-precision baselines) or whether the rescaling corrections are well-behaved in low precision (making BPT fully compatible with standard training recipes). The paper's own Limitation section does not mention this, but it is a critical blocker for production adoption.

**Full-training convergence and downstream evaluation of BPT-trained models on long-context tasks.** The paper validates correctness only through per-step validation loss (Table 4), showing identical values across methods at a single checkpoint during training. This does not guarantee that a full training run with BPT converges to the same final model quality or that models trained on the longer sequences BPT enables actually benefit on downstream tasks. The experiment would train two 1B models from scratch on OpenWebText — one with FlashAttention at 16K context (the maximum achievable), one with BPT at 65K context — both to convergence (matching the same number of tokens). Then evaluate both on long-document benchmarks: PG-19 (book-level language modeling), SCROLLS (long-document QA and summarization), and a synthetic needle-in-a-haystack retrieval task where the answer depends on tokens at positions 50K-60K. The key prediction: the BPT model trained on 65K contexts should dramatically outperform the 16K model on tasks requiring access to information beyond 16K tokens, even if validation perplexity is similar. If this prediction fails — if the 65K model does not leverage the additional context — it would suggest that simply training on longer sequences is insufficient without architectural changes to the attention mechanism's ability to attend over very long ranges.

### Practical Applications and Downstream Use Cases

**Training large language models on entire codebases for repository-scale code understanding.** Modern coding assistants need to reason over entire repositories — thousands of lines spanning dozens of files, plus dependency graphs, documentation, and test suites. This material routinely exceeds 100K tokens when tokenized. Prior to BPT, training a 13B-parameter code model on 100K-token contexts was impossible with FlashAttention even on 8 A100s (Table 2: FlashAttention maxes at 32K for 13B, while BPT reaches 65K). With BPT's 2-4× context-length extension, a 13B model can train on 65K tokens on 8 GPUs, and with sequence parallelism combined (per the composability hypothesis above), 100K+ tokens becomes feasible. The practical benefit is a model that can condition on an entire codebase at training time, learning patterns that span files — how function definitions in one file are used in another, how APIs evolve across versions, how test coverage relates to implementation — rather than being limited to single-file contexts. The 1.17-1.20× throughput advantage over Vanilla attention at 8K-16K tokens (Table 4) means this capability does not come at a training speed penalty for moderate context lengths.

**Offline reinforcement learning from very large experience datasets in robotics and game AI.** The ExoRL results (Table 5) demonstrate that conditioning on 32 trajectories (128K tokens) improves policy performance by 34% over conditioning on 4 trajectories. This finding generalizes to any offline RL setting where the dataset contains thousands of diverse trajectories collected by different policies or exploration strategies. Robotics datasets (e.g., RoboNet, Bridge Data) and game replay datasets (e.g., Atari, StarCraft) routinely contain millions of timesteps. BPT enables training a single Transformer policy that conditions on hundreds of trajectories simultaneously — essentially giving the model a broad view of "what worked and what didn't" across many episodes before making decisions. This matters because offline RL algorithms typically struggle with dataset diversity: policies can exploit spurious correlations in small subsets of the data. Conditioning on many trajectories at once provides a natural regularization by forcing the model to find patterns that generalize across diverse experiences. The practical setup: a 350M-parameter Agentic Transformer trained with BPT on 128 trajectories (512K tokens) using 8 A100s, where FlashAttention would OOM at 32 trajectories.

**Long-document processing for legal, scientific, and educational applications.** Legal contracts, scientific papers, textbooks, and regulatory filings routinely exceed 50K-100K tokens. Training a model to summarize, answer questions about, or extract structured information from such documents requires the model to have seen full documents — not truncated excerpts — during training. BPT's ability to train a 7B model on 131K tokens using 8 A100s (Table 2) makes this practical on academic-scale compute. A legal-tech company could fine-tune a pretrained 7B model on a dataset of 100K regulatory filings with BPT, enabling the model to learn cross-references between sections, consistency requirements between different clauses, and document-level reasoning patterns that are invisible when training on 8K-token chunks. The 4× memory reduction means this can be done on 8 GPUs rather than requiring 32 GPUs with FlashAttention, reducing the infrastructure cost by roughly 4× for the same training job.

**Training vision-language models on high-resolution images without aggressive downsampling.** Current vision-language models (Flamingo, PALI) process images by splitting them into patches, with high-resolution images producing very long patch sequences. A 1024×1024 image split into 16×16 patches produces 4096 visual tokens; multiple such images (e.g., for video understanding or multi-image reasoning) quickly exhaust the context window. BPT's memory reduction shifts the tradeoff: instead of downsampling images to 256×256 to fit within a 16K-token budget, a model can process images at 512×512 or 1024×1024, preserving fine-grained visual details that matter for tasks like document OCR, medical image analysis, or satellite imagery interpretation. The specific benefit: for a ViT-style vision encoder with $d_{model}=1024$ and batch size 1, FlashAttention's 16K-token budget limits total visual tokens to ~16K across all images; BPT at 65K tokens allows ~4× more visual information per training example, directly translating to higher-resolution inputs or more images per example.

### When to Prefer This Method

The paper positions BPT as a direct memory-efficiency upgrade over FlashAttention and Memory Efficient Attention — it computes identical outputs with up to 4× less activation memory. The tradeoffs that determine when to prefer BPT are:

- **When activation memory, not compute throughput, is the binding constraint on context length.** BPT increases total FLOPs (key-value blocks are re-read $B_q$ times) but reduces peak activation memory from $8bsh$ to $2bsh$ per layer. If you are hitting OOM errors at your target context length with FlashAttention — as was the case for all configurations in Table 2 where MemoryEfficient shows "oom" — BPT is the direct solution. The throughput cost is modest: BPT is 0.91-1.20× the speed of FlashAttention depending on context length (Table 4), and at the longest trainable sequences (where FlashAttention OOMs), BPT is the only option, making the comparison moot.

- **When you are training large models (13B+) and need context lengths beyond ~32K tokens on current hardware.** The paper's scaling results show that FlashAttention's advantage over Vanilla attention shrinks as model size increases (1B: 4× longer than Vanilla; 3B: 2× longer), while BPT's advantage over FlashAttention grows (1B: 2× longer; 30B: 4× longer). This suggests that for models above 13B parameters, the FFN bottleneck is so severe that FlashAttention provides relatively modest context-length gains, and BPT delivers proportionally more value.

- **When training batch size can be kept small (1–2 per device) with gradient accumulation.** BPT's memory reduction is per-sample; it does not change the fact that total activation memory scales linearly with batch size. If your training setup requires a per-device batch size of 8 or more (for training stability or throughput reasons), the absolute maximum context length BPT enables will be proportionally lower, potentially bringing it back into FlashAttention's feasible range. The paper's batch-size-1 experiments (Table 2) represent the upper bound on achievable context length.

- **Prefer FlashAttention (or Memory Efficient Attention) when training at moderate context lengths (≤16K) with small models (≤3B) where throughput is prioritized over maximum context length.** At 2,048 tokens, BPT is 9% slower than FlashAttention (Table 4). At 4,096–16,384 tokens, BPT is 3–8% faster, but the margin is small enough that implementation maturity matters: FlashAttention has battle-tested CUDA kernels with widespread adoption, while BPT's implementation is research-grade JAX code. For a practitioner who does not need the context-length extension (because 16K tokens suffices), the engineering simplicity and ecosystem support of FlashAttention may outweigh BPT's marginal throughput advantage.

- **Prefer BPT over sparse-attention or approximation-based methods (Longformer, BigBird, Reformer) when exact attention is required.** BPT computes exact (non-approximate) attention, producing identical outputs to a standard Transformer. If your application requires the full attention matrix (no sparse masking, no low-rank approximation, no hashing), and you need the memory savings, BPT is the only method that provides both exactness and reduced memory, since prior exact methods (FlashAttention, Memory Efficient Attention) leave the FFN bottleneck unaddressed.
