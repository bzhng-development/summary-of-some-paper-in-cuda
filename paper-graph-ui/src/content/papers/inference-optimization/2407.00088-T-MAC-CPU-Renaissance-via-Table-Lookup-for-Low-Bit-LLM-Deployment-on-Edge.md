# T-MAC: CPU Renaissance via Table Lookup for Low-Bit LLM Deployment on Edge

**ArXiv:** [2407.00088](https://arxiv.org/abs/2407.00088)

## 🎯 Pitch

On CPUs, lower-bit LLM weights can actually run *slower* than higher-bit ones due to dequantization overhead—until T-MAC. It replaces multiplication with bit-wise table lookups, slashing energy by 70% and hitting 71 tokens/s on M2 Ultra for a 1.58-bit model, all without dequantization.

---

## 1. Executive Summary

T-MAC introduces a **lookup table (LUT)-based method** for efficient low-bit LLM inference on CPUs, transforming the dominant data-type-centric multiplication into bit-wise table lookup to directly support mixed-precision matrix multiplication (mpGEMM) without dequantization. Evaluated on low-bit Llama and BitNet models across diverse edge devices—from Apple M2 Ultra to Raspberry Pi 5—T-MAC delivers up to 4× end-to-end throughput increase and 70% energy reduction compared to llama.cpp, achieving 30 tokens/s on a single core and 71 tokens/s with eight cores on M2-Ultra for BitNet-b1.58-3B, and 11 tokens/s on Raspberry Pi 5. The approach scales linearly with weight bit-width through **bit-serial decomposition** of the weight matrix into one-bit matrices combined with **table quantization and mirror consolidation** to compress LUT storage, establishing that CPU-based LLM deployment can match or exceed GPU performance on the same edge device—but only when the LUT resides in on-chip registers through axis reordering and tiling that maximize table reuse while minimizing temporary result competition for limited on-chip memory.

## 2. Context and Motivation

### The Core Problem: Low-Bit LLMs Need Mixed-Precision Compute That Hardware Cannot Provide

The fundamental problem T-MAC addresses is deceptively simple: **when you deploy a weight-quantized LLM on an edge device, the CPU cannot natively multiply low-bit weights by high-bit activations.** This mismatch between what low-bit models need and what hardware supports creates a performance bottleneck that becomes worse at lower bit-widths—precisely the opposite of what quantization promises.

To understand why this matters, consider the two operands in an LLM inference computation. During the decode stage—which dominates token generation—the model performs matrix-vector multiplications (mpGEMV) between an activation vector and a weight matrix. Weight quantization reduces the weight matrix to 4, 3, 2, or even 1 bit per parameter, slashing memory footprint from 16-bit floating point (FP16) down to a fraction of that. However, activations remain at higher precision (typically FP16 or INT8) because their distribution contains outliers that resist aggressive quantization. The result is an **asymmetric mixed-precision operation**—for example, W4A16 (4-bit weights × 16-bit activations) or W1A8 (1-bit weights × 8-bit activations).

Modern CPUs do not natively support any of these mixed-precision combinations. Their SIMD instruction sets (NEON on ARM, AVX2 on x86) operate on symmetric operand pairs: both inputs must be the same width, typically INT8, FP16, or INT32. There is no instruction for "multiply this 4-bit weight by this 16-bit activation."

The workaround used by all current systems—including llama.cpp, Intel Neural Compressor, and TensorRT-LLM—is **dequantization**: convert the low-bit weight *back* to a higher precision at runtime, then perform a standard high-precision multiplication. This is the indirect path shown in Figure 1(a): the weight is unpacked from its compact bit-packed representation into an INT8 or FP16 value, aligned with the activation precision, and then fed into a conventional GEMM/GEMV.

This workaround introduces two critical problems that the paper explicitly motivates around:

**Problem 1: Dequantization overhead negates bit-width scaling.** The entire point of quantizing to lower bit-widths is to reduce memory footprint *and* computational cost. Intuitively, a 2-bit model should be roughly 2× faster than a 4-bit model—half the data to load, half the operations. But because dequantization is a fixed per-weight conversion cost independent of the number of bits, it does not scale down. As Section 2.3 explains:

> "the efficacy of such methods is contingent upon the assumption that dequantization does not become a bottleneck and can be overlapped with memory loading. Since this indirect approach ultimately reverts to high-precision computation, it fails to fully capitalize on the benefits of low-bit weights, such as reduced memory usage and potentially faster computation."

The empirical evidence for this failure is Figure 6. When llama.cpp runs from 4-bit to 3-bit to 2-bit weights, the latency does not decrease—in fact, it sometimes increases. At 3-bit, llama.cpp experiences a "15% slowdown at 3-bit compared to 4-bit due to decoding overhead" (Section 5.2). The 3-bit case is particularly pathological because 8 (the number of bits in a byte) is indivisible by 3, so packing and unpacking 3-bit values from byte-aligned memory requires awkward SHIFT-and-AND sequences that are more expensive than the simpler 4-bit case. The net result: **scaling down bit-width with dequantization-based approaches provides no performance benefit**, and can actively hurt performance.

This is the key motivation behind T-MAC's design goal stated in Section 3: "a mpGEMM kernel design, which is independent of hardware data types and the bit width of the quantization algorithms, to achieve scalable speedup with bit scaling down." The paper is explicitly targeting the failure of dequantization to deliver on the promise of quantization.

**Problem 2: Bit-width diversity requires case-by-case kernel design.** The paper identifies a second, less obvious problem: the sheer diversity of bit-widths and precisions needed across different deployment scenarios. As Section 2.3 argues:

> "No single bit-width or precision setting can universally satisfy the diverse demands of all possible use cases. Consequently, this necessitates computational approaches capable of supporting a spectrum of low-bit widths, ensuring adaptability to the wide-ranging needs of edge computing tasks."

In the current dequantization paradigm, each bit-width combination demands its own custom kernel. The data layout for W3 weights (which might pack 2 bits in one array and 1 bit in another, with specific interleaving patterns for memory alignment) is fundamentally different from W2 or W4 layouts. The unpacking logic must understand this layout. The tiling strategy must account for different memory transaction patterns. The result: "the data layouts, as well as the interleaving or swizzling methods for W3 and W2 are totally different. The kernels need to be redesigned to match the layout" (Section 3). This is an engineering burden that multiplies with each new quantization format—and the field is moving rapidly, with BitDistiller exploring 2-bit post-training quantization, BitNet proposing 1-bit training from scratch, and novel formats like 1.58-bit emerging.

T-MAC's promise is to reduce all of these diverse bit-widths to a **unified bit-serial decomposition**, where any n-bit weight becomes n one-bit matrices, each processed identically. The weight layout becomes a simple 1-bit format regardless of the original bit-width.

### Why This Problem Matters: LLM-on-Edge Is Memory-Bound, Not Compute-Bound—Yet Current Solutions Fight the Wrong Battle

To understand why dequantization overhead matters so much, we need to understand the bottleneck in edge LLM inference. Section 2.1 provides the critical analysis:

**The decode stage is memory-bound.** After the initial prompt processing (prefill) which is compute-intensive, generating each subsequent token requires loading the entire model from memory. This is a matrix-vector multiplication (GEMV) where the weight matrix—billions of parameters—must stream from DRAM. On a typical edge device, the arithmetic intensity (FLOPs per byte loaded) is very low. The CPU cores sit idle waiting for data.

In this regime, the primary objective is to **reduce the total bytes transferred**. Lower-bit quantization directly addresses this: a 2-bit model transfers 1/8 the weight data of an FP16 model. However, dequantization *increases* the bytes processed: the low-bit weight is unpacked into a wider format, consuming additional CPU instructions and potentially additional memory bandwidth for intermediate values. The overhead is particularly damaging because it lengthens the time each byte spends in the CPU pipeline, reducing effective bandwidth utilization.

**Power and energy are existential constraints.** Section 2.1 emphasizes that edge devices—smartphones, robotics, IoT—are battery-operated. "These devices are designed for prolonged operation on finite energy reserves, making energy efficiency an essential consideration." The dequantization instructions (shifts, masks, type conversions) consume power without contributing to the actual arithmetic result. T-MAC's table lookup approach eliminates multiplication *and* dequantization, replacing both with lookup instructions that are significantly more energy-efficient on CPU hardware. The paper quantifies this: 60–70% energy reduction versus llama.cpp (Section 5.4, Figure 9).

**Edge deployment is single-batch by nature.** Unlike cloud serving where batched inference amortizes memory loads across many queries, edge devices process one user interaction at a time—batch size of one. This means the memory bottleneck cannot be hidden behind parallelism. Every GEMV is latency-critical. The pressure to maximize single-threaded throughput is extreme, which is why the paper evaluates single-threaded performance extensively (Figure 6a).

**The alternative—GPUs and NPUs—presents its own problems.** The paper acknowledges that GPUs are the dominant LLM inference platform, but counters with a practical reality: not all edge devices have GPUs, and those that do often have integrated GPUs sharing unified memory with the CPU, eliminating the bandwidth advantage. Furthermore, Section 5.7 demonstrates that T-MAC on CPU can outperform GPU on the same device for low-bit models, while consuming 66% less power. The paper's positioning is not "CPU is better than GPU" but rather "with LUT-based computation, the pervasive CPU becomes a viable deployment target that was previously dismissed."

### Where Prior Approaches Fall Short

The paper identifies three categories of prior work, each with specific limitations that motivate T-MAC:

#### Dequantization-Based Inference Systems (llama.cpp, Intel Neural Compressor, TensorRT-LLM)

These are the production systems deployed today. Section 2.3 describes their common approach: "converting low-precision weights back to a higher precision to align with activation precision... an indirect approach." Their fundamental limitation is that **the cost does not scale with bit-width reduction**. The evidence in Figure 6 is damning: llama.cpp GEMV kernels show essentially flat or even negative scaling from 4-bit to 2-bit across all matrix shapes. A smaller model in memory does not translate to faster inference because the unpacking cost dominates.

A secondary limitation is the **engineering complexity of supporting diverse bit-widths**. Each new quantization format (W2, W3, W4, etc.) requires custom layout design and custom kernel implementation. This is a maintenance burden and a barrier to adopting new quantization research.

#### LUT-Based Methods on GPU (LUT-GEMM, Park et al. 2023)

The paper explicitly acknowledges prior work on LUT-based computation for quantized LLMs on GPUs (Section 2.4). However, it provides concrete evidence that these GPU implementations are **worse than dequantization** in practice:

> "the average latency of LUT-GEMM kernels is 2.34×, 1.87×, and 1.75× longer than dequantization-based kernels in BitBLAS for W_INT4_A_FP16, W_INT2_A_FP16, and W_INT1_A_FP16 mpGEMVs, respectively."

Why do LUT methods fail on GPU? The paper attributes this to "the constraints of the GPU's fixed architecture, which offers either inadequate storage capacity for the lookup tables or insufficiently rapid table access" (Section 2.4). GPUs have shared memory and L1 cache, but these are far slower than CPU registers for random access. The table lookup pattern—randomly indexing into a precomputed table based on weight bit-patterns—is inherently a low-latency random-access operation. CPU registers, accessed via TBL (ARM) or PSHUF (x86) instructions, provide single-cycle latency. GPU shared memory has 20–30 cycle latency. The GPU's strength—massive parallel throughput—is mismatched to the LUT pattern, which is latency-sensitive.

This is a crucial insight that positions T-MAC's contribution: **the paper is not the first to propose LUT-based mpGEMM, but it is the first to demonstrate that CPUs—with their register file architecture—are actually better suited to LUT methods than GPUs**. The paper's title "CPU Renaissance" is not hyperbolic; it is a specific claim that the LUT paradigm shifts the architectural advantage from GPU to CPU for this workload.

#### LUT Methods for Other Quantized Models (DeepGEMM, MADDNESS, LUT-NN)

Section 2.4 cites prior LUT work for quantized CNNs (DeepGEMM) and for vector-quantized models (MADDNESS, LUT-NN). These works established the viability of table lookup for neural network inference, but they targeted **symmetric quantization**—both weights and activations quantized to low precision. In the LLM domain, the asymmetry (low-bit weights, high-bit activations) changes the table characteristics: the table is precomputed from the activation vector with all possible weight bit-patterns, and its size depends on the group size $g$ (the number of weight bits aggregated into one index). The paper identifies that making this table fit in on-chip registers, and accessing it without spilling, is the key challenge unique to LLM inference on CPUs.

### How T-MAC Positions Itself

The paper positions T-MAC through four key design claims that directly address the identified gaps:

**1. Bit-serial decomposition provides unification and scalability.** Rather than designing a separate kernel for W4, W3, W2, and W1, T-MAC decomposes any n-bit weight matrix into n one-bit matrices through Equation 1:

$$A \times W = A \times \left(\sum_{i=0}^{n-1} 2^i W_i\right) = \sum_{i=0}^{n-1} 2^i A \times W_i$$

Each $W_i$ is a simple 1-bit matrix. The computation reduces to n identical LUT-based 1-bit mpGEMM operations, whose results are shifted and accumulated. This means **supporting a new bit-width requires zero new kernel code**—only changing the number of iterations of bit-serial aggregation. The cost scales linearly with bit-width, which is the scaling property that dequantization fails to provide (compare llama.cpp's flat curve to T-MAC's linear increase in Figure 6).

**2. LUT eliminates multiplication and dequantization simultaneously.** Traditional LUT methods for quantized models (DeepGEMM) precompute *all possible multiplication results* between quantized weights and activations and store them in a table. T-MAC's innovation is to apply this to the bit-serial decomposition: for each 1-bit matrix $W_i$, group every $g$ bits of weight into an index that selects among $2^g$ precomputed values. The precomputed values are sums of the corresponding activation elements, with signs determined by the bit pattern (0 → -activation, 1 → +activation, using the $s_0 = -1, s_1 = 1$ linear transformation described in Section 4). This replaces both the dequantization (the bits directly index the table) and the multiplication (the table contains precomputed dot products).

**3. The CPU register file is the ideal LUT storage tier.** The paper's key architectural insight is that modern CPU SIMD registers can hold an entire LUT for $g = 4$, and the TBL/PSHUF instructions can perform 16 or 32 parallel lookups in a single cycle. This is fundamentally different from GPU LUT implementations that must use shared memory. The paper's design is built entirely around enabling this in-register LUT: the LUT-centric data layout (Section 3.2) ensures each LUT stays resident in registers while being reused across all weight indices in a tile, and the LUT compression techniques (Section 3.3) ensure the table is small enough to fit without register spilling.

**4. CPUs are pervasively available—and now performant enough.** The evaluation across four devices from Raspberry Pi 5 to M2-Ultra (Table 2) is deliberate. The paper wants to establish that T-MAC works not just on high-end CPUs with large caches, but on the Cortex-A76 in a $60 single-board computer. The 11 tokens/s result on Raspberry Pi 5 for BitNet-b1.58-3B (Figure 8) is a concrete demonstration that CPU-based LLM deployment is now practical where it was previously infeasible. The comparisons against GPU and NPU (Section 5.7) further position T-MAC as not just a CPU optimization, but a legitimate alternative to dedicated AI accelerators for edge deployment.

### The Gap That Prior Work Missed: On-Chip Memory as the LUT Bottleneck

A subtle but critical motivation that emerges from the technical sections is that **the LUT approach has a memory amplification problem**. For a group size $g = 4$, a [1, 4] activation vector produces a table of size [1, 16]—a 4× expansion. If multiple tables are needed in parallel to maintain throughput, the on-chip memory pressure becomes severe. The paper identifies that "the LUT method enlarges the on-chip memory usage compared to traditional mpGEMM" (Section 3.1). The challenge is not merely fitting one table, but fitting enough tables to overlap computation and hide latency while also storing intermediate accumulation results.

This problem is what motivates the paper's two-pronged optimization strategy: **(a) maximize table reuse** through the LUT-centric data layout (axis reordering so the temporal axis $K$ is processed first, tiling with large $M_{tm}$ to reuse each table across many weight rows), and **(b) reduce table size** through mirror consolidation (halving the table by exploiting sign symmetry) and table quantization (reducing width from FP16 to INT8). Without these optimizations, a naive LUT implementation would constantly spill tables to cache or memory, losing the register-speed advantage that makes LUT viable in the first place.

Prior LUT work on GPUs did not face exactly this challenge because GPU shared memory is larger than CPU registers, but it faced the complementary problem of higher access latency. T-MAC's contribution is therefore not the LUT idea itself, but the **system-algorithm co-design that makes in-register LUT practical** for the specific shapes and memory constraints of LLM inference on CPUs.

## 3. Technical Approach

### 3.1 Reader Orientation

T-MAC is a **mixed-precision matrix multiplication kernel library** for CPUs that replaces the standard multiply-and-accumulate computation in LLM inference with **lookup table (LUT)-based operations**, systematically eliminating both dequantization overhead and multiplication instructions. The system solves the problem that current CPU hardware cannot natively multiply low-bit weights (1–4 bits) by high-bit activations (8–16 bits), and that the standard workaround—dequantizing weights back to higher precision before multiplication—introduces overhead that negates the speedup promised by lower bit-widths. The shape of the solution is a **bit-serial decomposition** that turns any mixed-precision operation into a series of identical 1-bit operations, each implemented as table lookups where precomputed activation-bit-pattern products are indexed by the actual weight bits, with the results shifted and accumulated.

### 3.2 Big-Picture Architecture (Diagram in Words)

The T-MAC system has two stages connected by a bit-serial decomposition:

1. **Offline Weight Preprocessing**: An n-bit weight matrix `$W$` of shape `$[M, K]$` is decomposed into `$n$` separate 1-bit matrices `$W_0, W_1, \ldots, W_{n-1}$`, each of the same shape. These 1-bit matrices are then grouped into `$g$`-bit chunks (typically `$g = 4$`) that serve as indices into lookup tables. The preprocessing also permutes the weight layout so that tiles are stored sequentially in memory for efficient DRAM access, and interleaves packed bytes to eliminate runtime reordering during unpacking.

2. **Online Inference Engine**: For each incoming activation matrix `$A$` of shape `$[N, K]$`, the engine traverses every `$[1, g]$` vector of activations, precomputes its dot product with all `$2^g$` possible `$g$`-bit patterns, and stores these results in a lookup table (LUT). It then iterates through the `$n$` 1-bit weight matrices in sequence. For each, it uses the `$g$`-bit weight chunks as indices to look up partial results from the LUT, accumulates these partial results across the `$K$` dimension, applies the appropriate bit-position scaling factor `$2^i$`, and sums across all `$n$` bit-planes to produce the final output matrix `$R$` of shape `$[N, M]$`.

Information flows as follows: the offline stage produces permuted, interleaved 1-bit weight indices and stores them in DRAM → at runtime, an activation matrix enters the system → the LUT precomputation stage builds tables from the activation values → the bit-serial loop dispatches each 1-bit weight matrix against these tables → the lookup results are accumulated within each bit-plane → bit-plane results are shifted, scaled, bias-corrected, and summed → the final output emerges.

### 3.3 Roadmap for the Deep Dive

- **First, the bit-serial decomposition** (Equation 1 and its linear transformation variant), because it is the conceptual foundation that transforms the diverse mixed-precision problem into a unified 1-bit framework.
- **Second, the core LUT algorithm** (Algorithm 1), explaining how 1-bit mpGEMM becomes table lookup, what the groups and indices mean concretely, and how the precompute-lookup-accumulate pipeline operates.
- **Third, the LUT-centric data layout** (axis reordering, tiling, weight permutation, weight interleaving), because the viability of the algorithm depends entirely on keeping LUTs in registers through careful data reuse.
- **Fourth, the two LUT storage reduction techniques** (mirror consolidation and table quantization), which compress the table to fit on-chip and reduce lookup bandwidth.
- **Fifth, the implementation details** (code generation, hardware intrinsics, fast aggregation, register swizzling), since the theoretical algorithm must be realized efficiently on real CPU instruction sets.

### 3.4 Detailed, Sentence-Based Technical Breakdown

This is primarily a **systems paper** whose core idea is that the multiplication of an activation matrix by a low-bit weight matrix can be restructured as a series of table lookups indexed by the weight bits, and that CPUs—with their register file architecture and single-cycle TBL/PSHUF instructions—are actually better suited to this paradigm than GPUs. The paper's contribution is not the LUT concept itself (which appears in prior GPU work), but the **system-algorithm co-design** that makes in-register LUT practical for LLM inference shapes on edge CPUs.

#### The Bit-Serial Decomposition: Turning Mixed Precision into Repeated 1-Bit Operations

The theoretical foundation of T-MAC is a linear algebraic equivalence that decomposes a mixed-precision matrix multiplication into a sum of 1-bit matrix multiplications. The paper states this transformation in Equation 1:

$$A \times W = A \times \left(\sum_{i=0}^{n-1} 2^i W_i\right) = \sum_{i=0}^{n-1} 2^i A \times W_i$$

where `$A$` is the activation matrix of shape `$[N, K]$`, `$W$` is the weight matrix of shape `$[M, K]$` (or `$[K, M]$` depending on layout convention; the paper treats `$W$` as `$M \times K$` with rows being output dimensions), `$n$` is the bit-width of the weights (e.g., `$n = 4$` for 4-bit quantization), `$W_i$` is the `$i$`-th bit matrix extracted from `$W$` where each element is either 0 or 1, and `$2^i$` is the positional weight of that bit in the binary representation.

**What it computes:** This equation says that multiplying `$A$` by an n-bit weight matrix `$W$` is equivalent to: (1) decomposing `$W$` into `$n$` separate matrices, each containing only the bits at one position; (2) multiplying `$A$` by each of these 1-bit matrices independently; (3) scaling each result by `$2^i$` corresponding to its bit position; and (4) summing all the scaled partial results.

**Why this form:** The power of this decomposition is that it reduces the diversity problem to uniformity. A W4A16 operation, a W3A16 operation, and a W1A8 operation all reduce to the same primitive: multiply `$A$` by a 1-bit matrix `$W_i$`, repeated `$n$` times. The only difference is how many bit-planes exist (`$n$`). This eliminates the case-by-case kernel design that plagues dequantization approaches—a new bit-width requires only changing the iteration count of the bit-serial loop, not redesigning data layouts or unpacking logic for that specific bit-width. The cost scales linearly with `$n$`, which is the scaling property that dequantization-based approaches spectacularly fail to provide (as shown in Figure 6 where llama.cpp latency is flat or increasing as bit-width decreases).

**The bit-extraction process:** The preprocessing stage (Algorithm 1, lines 24–28) performs this decomposition offline. For each bit position `$i$` from 0 to `$n - 1$` and each element `$W[m, k]$`, the relevant bit is extracted and packed into groups of `$g$` bits to form indices. Specifically, the operation `(W[m, k] >> i) << (k % g)` extracts the `$i$`-th bit of the weight value, shifts it to the appropriate position within a `$g$`-bit group (determined by the column index modulo `$g$`), and accumulates it into `$W_i[m, k/g]$`. The result is that `$W_i$` is a matrix of `$g$`-bit integers, each representing `$g$` consecutive bits from the same bit-position `$i$` in the original weight matrix. These `$g$`-bit integers serve as indices into lookup tables during online inference.

**The 1.58-bit case:** For ternary weights (as in BitNet-b1.58, where weights take values -1, 0, or +1), the paper interprets them as 2-bit values and decomposes them into two 1-bit matrices. This is a specific instantiation of the general framework: the ternary value is treated as a 2-bit binary number (plus a sign/magnitude encoding), and the bit-serial decomposition handles it identically to any other bit-width.

#### The Linear Transformation: Converting Bits to Signed Values

The raw bit-serial decomposition uses values 0 and 1 for each weight bit. However, the paper introduces a linear transformation `$f$` that maps these binary values to a more computationally convenient signed representation, typically `$f(0) = -1$` and `$f(1) = +1$`. This is described in Section 4 (Implementation) under "Bit-serial linear transformation."

The transformation is defined as:

$$f(v_i) = \alpha'_i v_i + \beta'_i, \quad v_i = \alpha_i f(v_i) + \beta_i$$

where `$v_i \in \{0, 1\}$` is the original bit value, `$f(v_i) \in \{-1, +1\}$` is the transformed signed value, `$\alpha'_i$` and `$\beta'_i$` are the forward transformation parameters, and `$\alpha_i = 1/\alpha'_i$` and `$\beta_i = -\beta'_i / \alpha'_i$` are the inverse transformation parameters.

With this transformation, the bit-serial decomposition becomes:

$$W = \sum_{i=0}^{b-1} \alpha_i 2^i W'_i + B$$

where `$W'_i = f(W_i)$` is the matrix of transformed signed values (each element is -1 or +1), `$\alpha_i 2^i$` is the combined scaling factor, and `$B = J \cdot \sum_{i=0}^{b-1} \beta_i 2^i$` is a bias matrix where `$J$` is a matrix of all ones, correcting for the shift introduced by the linear transformation.

**What it computes:** The bias term `$B$` ensures that substituting the signed representation (+1/-1) for the binary representation (1/0) produces mathematically identical results. The bias correction `$A \cdot B^T$` is computed once and added to the accumulated sum.

**Why `$s_0 = -1, s_1 = +1$`:** The paper states that these values were chosen "to circumvent float-multiply instructions" and "to minimize the difference between the largest and smallest entries of the lookup table." With `$s_0 = -1, s_1 = +1$`, the LUT entries are sums of activation elements with signs determined by the bit pattern. For example, the pattern `[1, 0, 1, 1]` (mapped to `[+1, -1, +1, +1]`) produces the table entry `+A1 - A2 + A3 + A4`. All entries are formed by addition and subtraction of the same set of activation values, requiring no multiplication. The range of table values is well-balanced (symmetric around zero), which reduces quantization error when table quantization is applied (Section 3.3). Other choices from the set {-1, 0, 1} would either introduce zeros (wasting table entries) or create asymmetries that complicate quantization.

#### The Core LUT Algorithm: From Bits to Table Lookups

Algorithm 1 (excerpted and annotated below) captures the entire online computation. The key insight is that for a group of `$g$` 1-bit weights, there are only `$2^g$` possible bit patterns, each of which selects a specific signed sum of the corresponding `$g$` activation elements. Precomputing all `$2^g$` possible sums into a table transforms the matrix multiplication into a series of table lookups.

**Step 1: LUT Precomputation (lines 14–22 of Algorithm 1)**

For each element position `$n$` (batch index) and each group position `$k/g$` (column group index), the algorithm initializes `$2^g$` table entries. For each entry index `$i$` from 0 to `$2^g - 1$` and each bit position `$j$` from 0 to `$g - 1$` within the group:

- If the `$j$`-th bit of `$i$` is set (`i & (1 << j)`), the activation element `$A[n, k + j]$` is added to `LUT[n, k/g, i]`.
- Otherwise, `$A[n, k + j]$` is subtracted from `LUT[n, k/g, i]`.

Concretely, when `$g = 4$`, for an activation vector `[A1, A2, A3, A4]`, the LUT contains 16 entries ranging from `-A1-A2-A3-A4` (index 0b0000) to `+A1+A2+A3+A4` (index 0b1111). The entry for index 0b0101 would be `-A1+A2-A3+A4`.

**What this computes:** Each table is a `$[1, 2^g]$` vector containing the dot products of a `$[1, g]$` activation slice with every possible `$g$`-bit pattern, using the signed representation where 1 → +1 and 0 → -1.

**Step 2: Table Lookup and Partial Accumulation (lines 6–8)**

For each bit-plane `$i$` from 1 to `$b$` (where `$b = n$` is the number of bit-planes), and for each output position `$n$` (batch index), `$m$` (output feature), and input group position `$k$`:

$$R_i[n, m] = \sum_{k=1}^{K/g} \text{Look-up}(LUT, W_i, n, m, k)$$

The lookup operation: `W_i[m, k]` is a `$g$`-bit integer (the packed weight index), and `LUT[n, k, ...]` is the precomputed table for that `$(n, k)$` position. The lookup returns the precomputed partial dot product corresponding to that bit pattern. The sum accumulates these partial products across all `$K/g$` groups along the reduction dimension `$K$`.

**What this computes:** For a single bit-plane, this produces a matrix `$R_i$` of shape `$[N, M]$` where each element is the dot product of one row of `$A$` with the corresponding column of the 1-bit matrix `$W_i$`, computed entirely through table lookups and additions—**zero multiplications**.

**Step 3: Bit-Serial Aggregation (lines 10–13)**

The bias matrix `$B$` (of the same shape as `$W$`, with all elements equal to the bias value `$\beta$`) is multiplied by the activations to produce `$R_\beta = A \cdot B^T$`, which corrects for the shift from binary to signed representation.

The final result is:

$$R = \sum_{i=1}^{b} \alpha_i R_i + R_\beta$$

where `$\alpha_i = 2^i$` for standard binary decomposition (with the linear transformation, `$\alpha_i$` absorbs the inverse scaling as described above).

**What this computes:** The bit-plane results `$R_i$` are scaled by their positional weights `$\alpha_i$` and summed, with the bias correction added, to produce the exact result of the mixed-precision matrix multiplication `$A \times W$`.

**Why this is efficient:** The algorithm replaces `$N \times M \times K$` multiplications (in standard GEMM) with `$N \times (K/g) \times 2^g$` additions for LUT precomputation, plus `$b \times N \times M \times (K/g)$` table lookups and additions. The multiplications vanish entirely because: (a) the LUT precomputation uses only addition and subtraction (the activation values are simply summed with appropriate signs), and (b) the main loop performs only table lookups and accumulations. The scaling factors `$\alpha_i$` are powers of 2, so the final scaling can be implemented as bit-shifts rather than true multiplications.

---

#### LUT-Centric Data Layout: Keeping Tables in Registers

The LUT algorithm as described above has a critical performance vulnerability: the table lookups are **random access**—the weight indices can point to any entry in the LUT, and consecutive indices have no predictable pattern. If the LUT resides in cache or (worse) in DRAM, each lookup incurs tens to hundreds of cycles of latency, destroying performance. The paper's central design challenge is therefore: **keep every LUT in on-chip registers throughout its active use, and maximize reuse of each LUT before it is evicted.**

This is difficult because LUTs are large relative to the available register file. For `$g = 4$` and FP16 activations, one LUT is `$1 \times 16$` FP16 values = 32 bytes = one 256-bit AVX register (or two 128-bit NEON registers). But a single LUT only processes `$g = 4$` elements along the `$K$` dimension—the system needs many LUTs active simultaneously to maintain throughput. The paper's LUT-centric data layout is a coordinated set of four techniques that together ensure LUTs stay in registers without spilling.

##### Axis Reordering: Temporal-First Access Pattern

Traditional GEMM implementations loop over spatial axes first (`$N$` and `$M$`) and then the reduction axis `$K$`. This is natural because it lets the output tile `$C[N_{tn}, M_{tm}]$` accumulate in registers while the reduction dimension streams from memory.

T-MAC **reverses this order**: it processes the reduction axis `$K$` first, then the spatial axes `$N$` and `$M$`. The reason is directly tied to LUT construction:

- The LUT is built along the `$K$` dimension: for each group of `$g$` consecutive activation elements, a `$2^g$`-entry table is constructed.
- If `$K$` is the outer loop, only a **single `$[1, 2^g]$` LUT** needs to exist at any time—it is built for the current `$k$` group, used to process all `$M$` weight rows against that group, then discarded.
- If instead `$M$` were the outer loop (traditional order), the system would need to maintain LUTs for many `$k$` groups simultaneously across the entire `$K$` dimension, requiring memory proportional to `$(K/g) \times 2^g$`—far exceeding register capacity.

The axis reordering is thus the foundational decision that makes in-register LUT possible: it reduces LUT lifetime from "the entire GEMM duration" to "the processing of one `$k$` group."

##### Tiling: Maximizing LUT Reuse Through `$M_{tm}$`

With `$K$` as the outer axis, each LUT is built for one group of `$g$` activation elements. How many weight rows can use this LUT before it must be rebuilt for the next `$k$` group? This is determined by the tiling along the `$M$` dimension.

The paper introduces tiling parameters `$N_{tn}, M_{tm}, K_{tk}$` analogous to standard GEMM tiling, but with different priorities:

- **`$M_{tm}$` (tile size along output feature dimension)**: This is the critical parameter for T-MAC. Each LUT is reused across all `$M_{tm}$` weight rows in the current tile. A larger `$M_{tm}$` means more weight indices processed per LUT construction, amortizing the precomputation cost. The paper sets `$M_{tm} = 32$` for the example in Figure 3, meaning each LUT serves 32 weight rows before the `$k$` loop advances. This is a deliberate deviation from llama.cpp, which uses `$M_{tm} = 1$` (processing one output feature at a time) because its dequantization approach benefits from different access patterns.

- **`$N_{tn}$` (tile size along batch dimension)**: For GEMV (batch size 1), this is trivially 1. For the GEMM case (prefill with sequence length > 1), it controls how many activation rows share LUTs.

- **`$K_{tk}$` (tile size along reduction dimension)**: This controls how many groups (each of size `$g$`) are processed before the `$M$` loop advances. In the example in Figure 3, `$K_{tk} = 4$`, meaning 4 groups (each of 4 consecutive weights, so 16 weight elements total) are processed per tile.

**Why this matters for on-chip memory:** The tiling configuration determines the register pressure. In the example of Figure 3 (left), T-MAC uses 144 8-bit registers versus 104 for llama.cpp. The `$M_{tm} = 32$` choice means 32 partial results of shape `$[1, 32]$` must be accumulated in registers alongside the LUT. If `$M_{tm}$` were larger, register spilling would occur; if smaller, the LUT reuse benefit would be lost.

##### Weight Permutation: Sequentializing Tile Access for DRAM Bandwidth

Tiling introduces a new problem: weight matrices are stored in row-major or column-major order, but tiles are contiguous blocks that span the matrix in non-contiguous chunks. Accessing tiles directly from the original memory layout results in strided access patterns that underutilize DRAM bandwidth.

T-MAC solves this through **offline weight permutation**. After the tiling schedule (the order in which tiles will be processed) is determined, the weight matrix is physically reorganized in memory:

- All elements within each tile are flattened into a sequential byte array.
- The flattened tiles are concatenated in the exact order they will be accessed during inference.
- This rearrangement is done once offline and stored; at inference time, weight loading is purely sequential reads, achieving full DRAM bandwidth utilization.

Since LLM weights are read-only during inference and typically loaded once, this one-time cost is amortized over many inference operations. The paper explicitly notes: "the weight matrix will not be modified during LLM inference, so this permutation can be done in offline. This offline permutation does not introduce cost in inference."

##### Weight Interleaving: Eliminating Little-Endian Reordering Overhead

A subtler problem arises from the interaction of bit-packing and CPU byte ordering. Modern CPUs are little-endian: bytes within a multi-byte integer are stored in reverse order. When packed weight bytes are loaded as integers and then unpacked using SHIFT and AND instructions, the byte order must be reversed to produce the correct unpacked sequence. Without mitigation, this requires additional shuffle instructions per unpack operation.

T-MAC eliminates this overhead through **weight interleaving**, which is also an offline transformation. Figure 4 illustrates the technique: rather than storing weights in their natural packed order, the packed bytes are rearranged such that when loaded as integers and unpacked without reordering, the resulting values emerge in the correct sequential order. The interleaving pattern depends on the little-endian byte layout, so the transformation is hardware-specific but computed entirely offline. The result: "unpacking the interleaved weights can directly produce the required weights sequentially."

#### Reducing LUT Storage: Mirror Consolidation and Table Quantization

Even with axis reordering and tiling, the LUT remains large relative to the register file. For `$g = 4$` and FP16, a single LUT consumes one AVX2 register. With `$M_{tm} = 32$`, accumulating partial results requires 32 × 4 bytes = 128 bytes = 4 AVX2 registers (for FP32 accumulation) or more if intermediate precision is maintained. The paper introduces two complementary techniques to compress the LUT and thus fit more concurrent state in registers.

##### Mirror Consolidation: Exploiting Sign Symmetry

When using `$s_0 = -1, s_1 = +1$` for the linear transformation, the LUT entries exhibit exact sign symmetry: for every bit pattern, its bitwise complement (all bits flipped) produces the negated sum. For instance, pattern `0000` produces `-A1-A2-A3-A4`, and pattern `1111` produces `+A1+A2+A3+A4`. Pattern `0101` produces `-A1+A2-A3+A4`, and pattern `1010` produces `+A1-A2+A3-A4`.

Mirror consolidation exploits this by storing only half the table—typically entries 0 through `$2^{g-1} - 1$`. When a weight index `$i$` is in the upper half (`$i \ge 2^{g-1}$`), the system looks up the complementary entry `$i - 2^{g-1}$` (or equivalently, `$i$` bitwise complemented) and negates the result. This **halves the table length**: a 16-entry table becomes 8 entries, cutting register pressure in half for the LUT storage.

The paper describes this as "lossless, preserving the model's inference accuracy entirely" and notes it also "proves to be highly efficient, accelerating the precomputation of the lookup table, reducing the required storage, and speeding up table accesses." The precomputation benefit comes from computing only half the entries; the access speedup comes from fewer bytes to load (relevant when tables briefly reside in cache).

##### Table Quantization: Reducing Value Width

The LUT entries are initially computed in the activation's native precision—typically FP16. Table quantization reduces this to INT8 by quantizing each table independently with a per-table scaling factor. This reduces the table width by half: a 16-entry FP16 LUT (32 bytes) becomes a 16-entry INT8 LUT (16 bytes) plus one scaling factor.

The paper emphasizes several design choices that distinguish this from conventional activation quantization (which is notoriously difficult for LLMs):

- **Fine granularity**: Each LUT table (covering `$g = 4$` activation elements for 16 entries) gets its own quantization scale, rather than a single scale for the entire activation tensor. This is "quantizing 8 values for k=4" (though the description is slightly ambiguous; the key point is that the quantization granularity is per-LUT, not per-layer).
- **Dynamic quantization**: The scale is computed at runtime from the actual table values, not pre-calibrated from a calibration dataset. This eliminates offline calibration error.
- **The impact is "imperceptible"**: Section 5.6 demonstrates that table quantization introduces negligible error both at the kernel level (Table 3: NMSE of 3.35e-03 for T-MAC vs. 3.33e-03 for llama.cpp on a 4096×4096×1 GEMV) and at the model level (Table 4: identical perplexity and accuracy on WikiText-2, LAMBADA, and WinoGrande compared to llama.cpp).

Combined, mirror consolidation and table quantization reduce the LUT storage to **one-quarter of its original size**: half the entries (mirror) and half the width per entry (quantization). For `$g = 4$`, the compressed LUT is 8 INT8 values = 8 bytes, fitting in a single 64-bit register or a quarter of a NEON register.

---

#### Hardware Implementation: Bridging the Algorithm to Real CPUs

The paper implements T-MAC using TVM (Tensor Virtual Machine) for code generation, targeting ARM NEON and Intel AVX2 instruction sets. Section 4 describes the concrete mapping of the LUT algorithm to hardware instructions.

##### Code Generation and Integration

T-MAC uses TVM with LLVM backend for code generation, enabling automatic application of standard optimizations: loop unrolling, vectorization, and constant folding. Hardware-specific intrinsics are embedded via TVM's Tensorize mechanism, and AutoTVM automatically tunes tiling parameters (`$N_{tn}, M_{tm}, K_{tk}$`), unroll factors, and vectorization strategies for each target hardware.

For integration into existing frameworks, T-MAC provides a consistent C++/Python API using DLPack tensor structures for interoperability with PyTorch and NumPy. A key practical detail: when integrating into llama.cpp, the paper discovered that llama.cpp's threadpool and TVM's runtime threadpool conflict (threads from both pools compete for CPU resources). The solution was to generate raw C++ code from TVM rather than library files, then post-process the code to remove TVM runtime dependencies. The generated function executes a single threadblock; the application's threadpool (llama.cpp's) distributes these threadblocks across threads. This approach achieves "better performance and compatibility."

The paper evaluates T-MAC integrated into llama.cpp for end-to-end measurements (Section 5.3), replacing llama.cpp's mixed-precision GEMV/GEMM kernels with T-MAC's LUT-based kernels while retaining llama.cpp's attention, KV-cache management, and other components.

##### Hardware Intrinsics: TBL and PSHUF for Parallel Table Lookup

The core primitive is the 8-bit table lookup instruction:

- **ARM NEON**: `vqtbl1q_u8` — looks up 16 bytes from a 16-byte table using 16 indices, producing 16 output bytes in a single instruction.
- **Intel AVX2**: `_mm256_shuffle_epi8` (PSHUFB) — looks up bytes from a 32-byte table, but with a crucial constraint: the lookup operates within 128-bit lanes. The lower 16 bytes of the table are indexed by indices 0–15 in the lower lane, and the upper 16 bytes by indices 16–31 in the upper lane (with the high bit of each index byte controlling zeroing). The paper compensates by duplicating the table into both 128-bit lanes, so a full 256-bit register holds two copies of the 16-byte LUT.

For `$g = 4$`, the complete LUT (after mirror consolidation and quantization) has 8 entries, each 1 byte = 8 bytes total. This fits comfortably in a single 128-bit NEON register. For AVX2, the 8-byte table is duplicated to fill both 128-bit lanes, enabling 32 independent lookups per instruction (16 indices per lane).

When the activation precision is FP16 and table quantization is not applied (or when the model's quantization scales require FP16 precision), the LUT contains 16-bit values. Since NEON and AVX2 do not directly support 16-bit table lookups, the paper splits each FP16 value into two 8-bit halves (lower and upper bytes), performs two separate 8-bit lookups, and recombines the results.

##### Fast 8-Bit Aggregation: Trading Accuracy for Throughput

After table lookup, the partial results must be accumulated. The paper offers two accumulation strategies:

**Standard accumulation:** The INT8 (or INT16) lookup results are converted to a wider type (INT16 or INT32) to avoid overflow during summation, then accumulated. This preserves full accuracy but uses instructions with lower throughput (INT16 operations typically have half the throughput of INT8 on modern CPUs).

**Fast 8-bit aggregation:** The lookup results are accumulated directly in INT8 using averaging instructions—`vrhaddq_u8` on ARM NEON and `_mm256_avg_epu8` on AVX2. These instructions compute the average of two 8-bit values with rounding, avoiding overflow by halving the sum. To compensate for the averaging, a probabilistic bias is subtracted from the final accumulated value.

The paper treats this as an optional optimization ("we offer it as an optional optimization"). Table 4 quantifies the tradeoff: fast aggregation improves throughput from 7.34 to 8.97 tokens/s for Llama-2-7B-4bit (a 1.2× additional gain over standard T-MAC), but increases perplexity on WikiText-2 from 5.96 to 6.38 and reduces WinoGrande accuracy from 70.8% to 67.8%. The paper acknowledges this accuracy degradation and anticipates it "can be mitigated with straightforward optimizations of the CPU micro-architecture" (e.g., adding native 8-bit accumulation with saturation support).

##### Register Swizzling for Efficient LUT Precomputation

Building the LUT—computing `$2^g$` signed sums of the activation elements—presents a data layout challenge. Each table entry sums `$g$` activation elements with signs determined by the bit pattern. For `$g = 4$`, the pattern `0b0101` sums `-A[0] + A[1] - A[2] + A[3]`. When vectorized across multiple groups (to compute multiple LUTs simultaneously), the access pattern into the activation array is non-contiguous: the elements for one group are at strides of `$g$` (e.g., positions 0, 4, 8, 12 for the first of four groups being computed in parallel).

ARM NEON provides the `LD4` instruction to efficiently load four interleaved data streams, directly supporting this pattern. Intel AVX2 lacks an equivalent instruction. The paper's workaround is to use `vgatherdps` (which gathers elements from arbitrary memory locations into a register) for loading, but this creates a problem for storing results: "extracting specific bytes from a SIMD register and writing to memory is highly inefficient for AVX2."

The solution is **register swizzling**: a sequence of blend, permute, and shuffle operations that rearranges the computed LUT entries in-register so they become contiguous before being written to memory:

1. `vpblendvb`: blends 8-bit values from different registers (each holding non-contiguous entries across different LUTs) into one register, grouping entries that belong to the same LUT.
2. `vpermd`: permutes 32-bit dwords across 256-bit lanes to bring related entries together.
3. `vpshufb`: final byte-level shuffle within 128-bit lanes to achieve the exact contiguous order.

After swizzling, the LUT is stored as a linear array in memory, ready for efficient sequential access during the lookup phase.

##### Determining On-Chip Resources: `$g$` and Number of Concurrent LUTs

The group size `$g$` is a critical parameter that trades off table size against index efficiency:

- **`$g = 4$`** is the default choice: the `$2^4 = 16$` entry table exactly fills one NEON register (128 bits for 16 × 8-bit entries) or half an AVX2 register (duplicated to fill both 128-bit lanes). The TBL and PSHUF instructions are designed for exactly this register width.
- **`$g = 5$`** would require `$2^5 = 32$` entries, needing two registers and the slower `TBL2` instruction (ARM) or requiring AVX-512 with `vpermb` (not available on all CPUs). The paper does not use this.

The number of concurrent LUTs is tuned per hardware platform "to make sure on-chip memory can be fully utilized and LUTs won't be swapped out for the tile." More LUTs enable more partial results to be accumulated before writing back to memory, but exceeding register capacity causes spilling to cache, which defeats the purpose of in-register LUTs. The tuning is performed by AutoTVM across the parameter space of `$N_{tn}, M_{tm}, K_{tk}$`, with the register budget as an implicit constraint.

---

#### Summary: Why the Co-Design Matters

The paper's technical approach is best understood as a **layered solution to a constraint satisfaction problem**:

- **Constraint 1**: LUTs must reside in registers to achieve single-cycle random access. (Motivates axis reordering so LUT lifetime is one `$k$` group.)
- **Constraint 2**: Register capacity is small—typically 16–32 architectural SIMD registers plus a similar number of scalar registers. (Motivates mirror consolidation and table quantization to compress LUTs to 8 bytes each; motivates careful tiling to balance LUT count versus partial result storage.)
- **Constraint 3**: DRAM bandwidth is limited on edge devices, and weight loading must be sequential for full utilization. (Motivates offline weight permutation.)
- **Constraint 4**: The algorithm must be bit-width agnostic to support the diversity of quantization formats. (Motivates bit-serial decomposition, which reduces everything to repeated 1-bit operations.)

Each optimization addresses one constraint while respecting the others. The result is a system where the theoretical reduction in operations (LUT replacing multiplication) is actually realizable in practice because the memory system has been reorganized to feed the LUT engine without stalls. The paper's title "CPU Renaissance" reflects the finding that this LUT-centric design shifts the architectural advantage: what was a hindrance for traditional GEMM (limited register file, emphasis on sequential access) becomes an asset for LUT-based computation (single-cycle register access, mature SIMD lookup instructions).

## 4. Key Insights and Innovations

### Innovation 1: Reframing Mixed-Precision GEMM as a Register-Centric LUT Problem Rather Than a Compute-Centric Dequantization Problem

The dominant mental model for mixed-precision LLM inference on edge devices has been: "hardware only supports symmetric operand types, so convert low-bit weights up to match activation precision, then compute." This is the dequantization-first mindset embodied by llama.cpp, Intel Neural Compressor, and TensorRT-LLM. It treats the bit-width mismatch as a type-conversion tax to be paid before the real work begins, and it implicitly assumes that the conversion cost can be hidden behind memory bandwidth or parallel execution.

T-MAC fundamentally inverts this framing. Rather than viewing the problem as "how do we efficiently convert weights to make them compatible with hardware multiplication," it asks: **"can we eliminate multiplication entirely and restructure the computation so that hardware's actual strength—single-cycle random access into small register-resident tables—becomes the primary operation?"**

This is not merely an implementation switch. It is a conceptual reframing that changes which hardware resource is the bottleneck and which architectural feature is the optimization target. Dequantization-based approaches optimize for the multiply-accumulate pipeline: they unpack weights, align data types, and feed into SIMD dot-product instructions whose throughput is well-understood. T-MAC optimizes for the **register file**: the size of LUTs, the number of concurrent LUTs, the reuse distance of each table, and the latency of the TBL/PSHUF instruction. These are entirely different design constraints, and they lead to entirely different design decisions—axis reordering to minimize LUT lifetime, tiling along `$M$` to maximize table reuse, and table compression to reduce register pressure.

The significance of this reframing is that it identifies CPUs as **architecturally advantaged** for LUT-based computation compared to GPUs, which is the precise opposite of the conventional wisdom. GPUs have massive compute throughput but high-latency shared memory (20–30 cycles). CPUs have modest compute but single-cycle register access via TBL/PSHUF. For the LUT pattern—where a small table is randomly indexed many times—register latency dominates, and CPUs win. The paper makes this explicit by showing that prior GPU LUT implementations (LUT-GEMM, Park et al. 2023) are 1.75–2.34× *slower* than dequantization on GPU, whereas T-MAC's CPU implementation is up to 6.6× *faster* than dequantization on CPU. The hardware that was "wrong" for dequantization becomes "right" for LUT.

This is a **fundamental shift**, not an incremental refinement. It reopens the question of what hardware is best suited for low-bit inference—a question the field had largely settled in favor of GPUs and NPUs—and provides a concrete counterexample where the pervasive, general-purpose CPU outperforms dedicated accelerators. The evidence is in Figure 11 and Table 7: T-MAC on CPU matches or beats llama.cpp on GPU for low-bit GEMV kernels, and achieves 1.4–3× higher throughput than GPU/NPU for end-to-end 2-bit Llama-2-7B inference across three different edge platforms.

---

### Innovation 2: Bit-Serial Decomposition as a Unifying Framework That Eliminates Bit-Width-Specific Kernel Engineering

Prior to T-MAC, supporting a new weight bit-width meant designing a new kernel. The data layout for 3-bit weights—where 8 is indivisible by 3, requiring awkward split-packing of 2 bits and 1 bit into separate arrays with specific interleaving—was fundamentally different from 4-bit or 2-bit. The unpacking logic, the memory access pattern, and the tiling strategy all had to be redesigned. Each new quantization research advance (GPTQ for 4-bit, BitDistiller for 2-bit, OneBit for 1-bit) carried an implicit engineering tax: someone had to write and optimize the kernel for that specific bit-width on each target hardware platform.

T-MAC's bit-serial decomposition eliminates this tax by reducing **every** bit-width to the same primitive: a 1-bit matrix multiplication via table lookup. The decomposition `$A \times W = \sum 2^i A \times W_i$` means that supporting W4, W3, W2, or W1 requires zero new kernel code—only changing the number of iterations of the bit-serial accumulation loop. The weight layout reduces to a simple packed 1-bit format regardless of the original precision. The 3-bit case, which was particularly pathological for dequantization (indivisible by 8, causing a 15% slowdown in llama.cpp relative to 4-bit as shown in Figure 6), becomes as straightforward as any other bit-width in T-MAC.

This is a **conceptual unification** that matters beyond implementation convenience. It means the performance of T-MAC is **predictably linear in bit-width**: halving the bit-width (e.g., 4-bit to 2-bit) roughly halves the number of bit-planes to process, and therefore roughly halves the computation time. Figure 6 demonstrates this linear scaling empirically, with T-MAC latency decreasing approximately proportionally from 4-bit to 2-bit to 1-bit across all matrix shapes and devices. In contrast, llama.cpp's dequantization-based kernels show flat or even negative scaling—the decoding overhead dominates regardless of bit-width.

This unification also makes T-MAC **future-proof** against the rapid diversification of quantization formats. When BitNet proposes 1.58-bit ternary weights, T-MAC handles them as 2-bit values without modification. If future work explores 5-bit or 6-bit quantization (balancing accuracy and compression), T-MAC's kernel requires no changes. The bit-serial framework absorbs this diversity at the algorithmic level rather than the engineering level, which is a qualitatively different approach from the case-by-case kernel design that has been the norm.

I characterize this as a **fundamental contribution** rather than incremental because it changes the abstraction boundary: the kernel developer no longer thinks in terms of "how do I unpack and compute with this specific bit-width" but rather "how do I efficiently execute the 1-bit LUT primitive and accumulate across bit-planes." The downstream benefit—scalable performance that tracks bit-width reduction—is what makes quantization actually deliver on its promise of faster inference with smaller models.

---

### Innovation 3: Identifying On-Chip Memory Pressure as the LUT Bottleneck and Solving It Through Algorithm-Hardware Co-Design

The LUT approach to matrix multiplication was known before T-MAC. DeepGEMM applied it to symmetrically quantized CNNs. LUT-GEMM applied it to weight-quantized LLMs on GPUs. MADDNESS and LUT-NN applied it to vector-quantized models. But none of these prior works achieved practical speedups over dequantization for LLM inference—LUT-GEMM was 1.75–2.34× *slower* than BitBLAS on GPU.

T-MAC's diagnostic contribution is identifying **why** prior LUT methods failed and **what specific architectural condition** must be satisfied for LUT to win. The answer is not "LUT is a good idea" in the abstract; it is that **the LUT must reside in the fastest on-chip memory throughout its active use, and the CPU register file—accessed via TBL/PSHUF—is the only memory tier fast enough.** GPU shared memory, at 20–30 cycles latency, is too slow. CPU cache, at 4–40 cycles, is borderline. CPU registers, at 1 cycle, are sufficient.

This diagnosis reframes the LUT problem from a compute-reduction technique (replacing multiplications with lookups) to a **memory-hierarchy optimization problem** (ensuring the lookup table fits in the narrowest, fastest memory tier). The paper's key insight is that for LLM inference shapes—particularly GEMV with batch size 1, where the memory bottleneck is extreme—the register file's limited capacity is the binding constraint, and every design decision must be evaluated against its impact on register pressure.

The innovation is not the individual techniques (mirror consolidation, table quantization, axis reordering, tiling) in isolation—many of these have precedents in other contexts—but rather their **coordinated application to a specific constraint**: the finite register budget of modern CPU SIMD units. Mirror consolidation halves the LUT entries, table quantization halves the LUT width, axis reordering reduces LUT lifetime to one `$k$`-group, and tiling with large `$M_{tm}$` maximizes reuse of each LUT before eviction. Together, these reduce the storage per LUT to **one-quarter of its original size** and ensure that the active LUT set fits within the 16–32 architectural SIMD registers available on target CPUs.

The significance is that it provides a **design methodology** for LUT-based computation that generalizes beyond the specific implementation. Future LUT systems—whether on CPUs with wider vectors (AVX-512, SVE), on NPUs with scratchpad memories, or on custom accelerators—can apply the same analysis: (1) measure the latency of the lookup tier, (2) determine the maximum LUT size that fits, and (3) apply compression and reuse optimizations to stay within that budget.

This is a **diagnostic innovation**—it teaches the field *what to measure and what to optimize* for LUT-based inference, rather than just providing a point solution. The optimization breakdown in Figure 10 supports this: each technique (table quantization, tiling, permutation, interleaving) provides a measurable, additive speedup, and their combination transforms a baseline implementation that is *slower* than llama.cpp into one that is up to 6.6× faster.

---

### Innovation 4: Establishing That CPU-Based Low-Bit LLM Inference Can Match or Exceed GPU/NPU Performance on Edge Devices

The field's trajectory for edge LLM deployment has been toward specialized hardware: Apple's Neural Engine, Qualcomm's Hexagon NPU, NVIDIA's Jetson GPU series. The assumption—reasonable given the compute intensity of transformer inference—has been that general-purpose CPUs are at best a fallback for devices without accelerators, and at worst unsuitable for interactive LLM applications.

T-MAC provides **concrete counterevidence** that challenges this assumption, but more importantly, it provides a **mechanistic explanation** for *why* the counterevidence exists. The explanation is not "CPUs got faster" or "LLMs got smaller." It is that the LUT paradigm shifts the bottleneck from compute throughput (where GPUs/NPUs dominate) to **memory latency for random access into small tables** (where CPU registers dominate). On edge devices with unified memory architectures—where CPU, GPU, and NPU share the same DRAM—the memory bandwidth is the same for all processors. What differs is how efficiently each processor can use that bandwidth. T-MAC's LUT approach, by eliminating dequantization overhead and reducing total operations, saturates the memory bandwidth more effectively, achieving higher throughput from the same physical DRAM.

The evidence is specific and striking:

- **Versus GPU**: On Jetson AGX Orin, T-MAC on CPU achieves 78% of GPU throughput for Llama-2-7B-2bit while consuming only 34% of the power, yielding 2.3× better energy efficiency (Table 5). For individual GEMV kernels, T-MAC on CPU outperforms GPU at W1A16 across all shapes (Figure 11).
- **Versus NPU**: On Surface Laptop 7, T-MAC on 4 out of 12 CPU cores achieves 3× the throughput of the Hexagon NPU for Llama-2-7B-2bit. On OnePlus 12, T-MAC achieves 1.5× NPU throughput for 2-bit and 9.7× GPU throughput for 2-bit (Table 7).
- **Versus nothing (Raspberry Pi)**: T-MAC delivers 11 tokens/s on a $60 single-board computer that has no GPU or NPU to speak of, making interactive LLM inference feasible on a device class previously considered incapable of it.

This is a **reframing contribution** rather than a purely technical one. It changes the deployment calculus for practitioners: the question shifts from "which accelerator do I need?" to "can I use the CPU I already have, and at what bit-width does it become competitive?" The answer, per T-MAC's data, is that at 2-bit and below, the CPU is not just viable but often superior in energy efficiency, and at 4-bit it is competitive on many platforms. The paper's title "CPU Renaissance" is a claim that LUT-based computation revives the CPU as a legitimate inference platform in an era where it was being written off in favor of specialized silicon.

This innovation is **significant but conditional**: it applies to edge devices with unified memory and to low-bit models (≤4-bit). It does not claim CPU superiority for all workloads or all hardware configurations. But within its demonstrated scope, it opens a practical deployment path that eliminates dependency on specialized accelerators, reduces system cost and complexity, and leverages the most pervasive computing platform available.

## 5. Experimental Analysis

### Evaluation Methodology

- **Dataset.** T-MAC is a kernel-level system; it does not train or fine-tune models, so there is no training dataset. For kernel benchmarks, matrix shapes are drawn from real Llama-2-7B and Llama-2-13B model configurations: the six shapes tested are `4096×4096×1`, `11008×4096×1`, `4096×11008×1`, `5120×5120×1`, `13824×5120×1`, and `5120×13824×1` (covering the FFN up/down projections and attention projections in both model sizes). For end-to-end model inference, the paper uses pre-quantized models: 4-bit Llama-2-7B from GPTQ, 3-bit and 2-bit Llama-2-7B from BitDistiller, 1-bit Llama-2-7B from OneBit, and 1.58-bit BitNet-3B trained from scratch. Model quality evaluation uses WikiText-2 (perplexity), LAMBADA (perplexity), and WinoGrande (accuracy).

- **Base model(s).** The evaluated models span two families: Llama-2 (7B and 13B parameter scales) across 1/2/3/4-bit weight quantization, plus BitNet-b1.58-3B. These represent both post-training quantized models (GPTQ, BitDistiller, OneBit) and quantization-aware trained models (BitNet). The choice covers the spectrum of current low-bit LLM deployment scenarios—from mainstream 4-bit to experimental 1-bit—and includes both the Llama architecture (for compatibility with llama.cpp baselines) and the more recent BitNet architecture (for demonstrating generality). The 13B shapes are used in kernel benchmarks only; end-to-end measurements focus on 7B and 3B models.

- **Metrics.** Kernel performance is measured as **latency in milliseconds (ms)** per GEMV or GEMM call, computed as the average over 100 runs after a 10-iteration warmup. On M2-Ultra specifically, warmup requires at least 1 second to reach maximum clock frequency (Apple Silicon's performance core boosting behavior). End-to-end inference is measured as **token generation throughput in tokens per second**, obtained by generating 64 tokens repeatedly for 20 iterations. Energy consumption is measured in **Joules per token** on M2-Ultra using `powermetrics` at 500 ms sampling intervals, integrating power over continuous token generation for a minimum of 120 seconds. Model quality uses standard **perplexity** (lower is better) on WikiText-2 and LAMBADA, and **accuracy** (higher is better) on WinoGrande.

- **Baselines.** The primary baseline is **llama.cpp** (version b2794, released May 2024), chosen because it represents "the state-of-the-art implementation for LLM deployment on edge devices" with "highly optimized kernel implementations tailored to each hardware platform." For mpGEMV (matrix-vector multiply, the decode stage), the paper compares against llama.cpp's own optimized mixed-precision kernels. For mpGEMM (matrix-matrix multiply, the prefill stage with batch size > 1), llama.cpp delegates to BLAS libraries (Accelerate on M2-Ultra, OpenBLAS on other platforms), because llama.cpp's custom mixed-precision kernels are optimized only for GEMV shapes and BLAS provides better GEMM performance. Therefore, T-MAC's GEMM comparison is against **llama.cpp (BLAS)**, not llama.cpp's native GEMV kernels.

- **Generation budget / compute accounting.** The paper measures compute in two contexts. For kernel-level benchmarks, the "budget" is implicitly the matrix shape (dimensions and bit-width), with latency measured directly for each shape. The key fairness consideration is that both T-MAC and llama.cpp process the identical mathematical operation—e.g., a W4A16 GEMV of shape `[4096, 4096, 1]`—and the latency comparison reflects which implementation completes it faster. For end-to-end inference, both T-MAC and llama.cpp run the same model weights at the same bit-width, generating the same tokens under identical conditions (same attention implementation, same KV-cache management, same threading configuration within llama.cpp). The only difference is which kernel executes the linear layers. The paper integrates T-MAC kernels as drop-in replacements within llama.cpp's inference loop, ensuring a controlled comparison.

- **Cross-validation / statistical protocol.** The paper does not employ cross-validation in the machine learning sense (there is no training or hyperparameter selection on held-out data). For kernel benchmarks, variance is addressed through repeated runs: 100 iterations after warmup, with the average reported. For model quality evaluation, the perplexity and accuracy metrics are computed on standard test sets (WikiText-2, LAMBADA, WinoGrande) using llama.cpp's built-in evaluation tools. For energy measurements, the 120-second continuous generation window smooths out transient power fluctuations. The paper does not report confidence intervals or standard deviations for any latency or throughput measurements, which is a limitation.

### Main Quantitative Results

#### mpGEMV Kernel Performance: T-MAC Achieves Linear Bit-Width Scaling While llama.cpp Stalls

The kernel-level mpGEMV results in Figure 6 are the paper's most important empirical contribution—they isolate T-MAC's advantage at the computational primitive level, before end-to-end system effects (attention, KV-cache, threading) enter the picture.

**Figure 6(a): Single-Threaded mpGEMV.** Across all four devices and all six matrix shapes, T-MAC's latency decreases approximately linearly as bit-width drops from 4 to 1, while llama.cpp's latency is flat or increases. At 4-bit, T-MAC achieves maximum speedups of 3.1× (the paper states this for 4-bit across devices, though the per-device breakdown is in the figure). At 2-bit, the speedup grows substantially. At 1-bit, T-MAC reaches maximum speedups of **11.2×** on M2-Ultra, **5.8×** on the unspecified best device for this number, **4.7×** on another, and **3.1×** on the slowest. The critical pattern: llama.cpp's 3-bit performance is **15% slower** than its 4-bit performance due to decoding overhead (8 is indivisible by 3, requiring complex SHIFT+AND unpacking), while T-MAC's 3-bit is faster than its 4-bit, as the bit-serial decomposition means 3 bit-planes cost less than 4. The dashed lines for llama.cpp 1-bit are extrapolated from its 2-bit performance since llama.cpp does not provide a native 1-bit kernel—the paper argues performance would be similar since decoding overhead already dominates at 2-bit.

**Figure 6(b): Multi-Threaded mpGEMV.** When memory bandwidth becomes the bottleneck (multiple cores sharing DRAM), the absolute speedups are smaller but still significant. At 2-bit, T-MAC achieves **4.0×** speedup on M2-Ultra, **4.0×** on Raspberry Pi 5, **5.3×** on Jetson AGX Orin, and **2.5×** on Surface Book 3. The lower speedups on Surface Book 3 reflect its lower memory bandwidth (58.2 GB/s vs. 819.2 GB/s on M2-Ultra, per Table 2), which limits how much T-MAC's reduced operation count can translate to throughput when the system is bandwidth-saturated. The paper notes that "T-MAC's performance is primarily constrained by memory bandwidth, but T-MAC can still achieve significant speedup due to efficient memory access"—the key being that T-MAC spends less time per byte loaded, so it reaches bandwidth saturation at a higher absolute throughput.

**The shape-dependent variation is informative.** On the larger shapes (11008×4096, which corresponds to FFN up-projection in Llama-2-7B), both T-MAC and llama.cpp show higher absolute latency, but T-MAC's relative advantage is maintained or grows. This is because larger K dimensions mean more LUT reuse per table construction: each `[1, g]` activation group produces one LUT that processes `M` weight rows, and larger M means more reuse, amortizing the precomputation cost more effectively.

#### mpGEMM Kernel Performance: T-MAC's Advantage Extends to Prefill but Is Platform-Dependent

Figure 7 shows multi-threaded mpGEMM (sequence length 256) results. The prefill stage with batch processing is compute-bound rather than memory-bound, favoring parallel throughput over latency sensitivity. The results reveal a nuanced picture:

- On Raspberry Pi 5, Jetson AGX Orin, and Surface Book 3, T-MAC achieves substantial speedups at 2-bit: **4.0×**, **5.3×**, and **5.3×** respectively. These are comparable to the GEMV speedups, indicating that T-MAC's LUT approach scales well to higher arithmetic intensity.
- On M2-Ultra, T-MAC's advantage is narrower, with a maximum of **2.0×** at 1-bit. The paper explains this: "Apple Silicon CPUs are equipped with a powerful AMX co-processor to handle GEMM operations." The AMX (Apple Matrix coprocessor) provides dedicated matrix multiplication hardware that llama.cpp can leverage through Accelerate, making the dequantization-based baseline much stronger on M2-Ultra for GEMM than for GEMV. This is an important qualification: T-MAC's advantage is largest where the baseline's hardware acceleration is weakest—on ARM Cortex cores and x86 without AMX-class coprocessors.

The 3-bit advantage is "significant" across all platforms (Section 5.2). As with GEMV, the 3-bit case is particularly pathological for dequantization due to the 8/3 indivisibility problem. T-MAC's bit-serial decomposition treats 3-bit identically to any other bit-width, making its 3-bit performance a straightforward midpoint between 4-bit and 2-bit. This is a concrete demonstration of the unification benefit: the pathological case for the old paradigm is just another point on the scaling curve for T-MAC.

#### End-to-End Inference Throughput: 2–4× Speedup on Real Model Inference

Figure 8 integrates T-MAC kernels into llama.cpp and measures actual token generation throughput for three models: Llama-2-7B-4bit (M1), Llama-2-7B-2bit (M2), and BitNet-b1.58-3B (M3).

**Single-threaded results (Figure 8a):** On Raspberry Pi 5—the most resource-constrained device—T-MAC achieves **2.8×** speedup for Llama-2-7B-4bit (from ~5 to ~14 tokens/s, estimated from the bar chart), **6.7×** for Llama-2-7B-2bit, and **5.8×** for BitNet-3B. On M2-Ultra, the speedups are more modest but still notable: Llama-2-7B-4bit improves from ~9 to ~12 tokens/s (~1.3×), Llama-2-7B-2bit from ~8 to ~18 (~2.3×), and BitNet-3B from ~10 to ~30 (~3×). Surface Book 3 and Jetson AGX Orin show intermediate gains, with the 2-bit and BitNet models benefiting more than the 4-bit model.

**Multi-threaded results (Figure 8b):** The absolute throughput numbers are impressive—T-MAC reaches **71 tokens/s** on M2-Ultra for BitNet-3B (8 cores) and **11 tokens/s** on Raspberry Pi 5 (4 cores). However, the relative speedups are smaller than single-threaded: **1.1×**, **2.3×**, and **1.7×** for the three models on M2-Ultra. The paper attributes this to "memory constraints and operators other than mpGEMV/mpGEMM"—when the linear layers are accelerated by T-MAC, the remaining components (attention, KV-cache management, activation functions, layer norm) become the bottleneck. This is the classic Amdahl's Law effect: T-MAC accelerates the matrix multiplications, but the fraction of total runtime that matrix multiplications occupy shrinks as they get faster.

**The BitNet-3B result on Raspberry Pi is particularly significant** for demonstrating practical deployment feasibility: 11 tokens/s is within the range of comfortable reading speed (roughly 5–15 tokens/s depending on the user), meaning interactive chat with a 3B-parameter model on a $60 device is now achievable. The paper explicitly flags this: "indicating promising real-world edge deployment."

#### Power and Energy Consumption: 60–70% Total Energy Reduction

Figure 9 and the associated text in Section 5.4 present power and energy measurements on M2-Ultra for multi-threaded inference. These measurements capture the full system power draw, not just the CPU package, using `powermetrics` at 500 ms intervals over >120 seconds of continuous generation.

- **Llama-2-7B-4bit**: Power drops from ~42W to ~37.7W (10.3% reduction). Energy drops from ~1.15 J/token to ~0.91 J/token (**20.6% reduction**).
- **Llama-2-7B-2bit**: Power drops from ~42W to ~37.7W (10.3% reduction). Energy drops from ~1.2 J/token to ~0.47 J/token (**61.2% reduction**).
- **BitNet-3B**: Power drops from ~36W to ~29.9W (17.3% reduction). Energy drops from ~0.84 J/token to ~0.41 J/token (**51.3% reduction**).

The energy reduction is substantially larger than the power reduction because T-MAC also reduces latency—the system draws slightly less power for significantly less time. The power reduction itself is notable: LUT-based computation uses lookup instructions (TBL/PSHUF) and addition instructions, which consume less dynamic power than the multiply-accumulate and dequantization instruction sequences used by llama.cpp. The paper does not isolate whether the power savings come from reduced instruction count, reduced instruction-level energy per operation, or reduced memory traffic—all three likely contribute.

The 2-bit and BitNet models show much larger energy reductions than the 4-bit model because T-MAC's bit-serial decomposition scales down computation with bit-width (fewer bit-planes → fewer instructions → less time and energy), while llama.cpp's dequantization overhead remains approximately constant regardless of bit-width.

#### Comparison with GPU and NPU: CPU Matches or Exceeds Accelerators for Low-Bit Inference

Section 5.7 presents a series of comparisons that challenge the assumption that GPUs and NPUs are necessary for edge LLM inference.

**Kernel-level GPU comparison (Figure 11):** On Jetson AGX Orin, comparing T-MAC on CPU versus llama.cpp on GPU for individual mpGEMV kernels from Llama-2-7B shapes:
- W1A16: T-MAC (CPU) significantly outperforms GPU across all three shapes tested.
- W2A16 and W3A16: T-MAC achieves comparable performance to GPU.
- At higher bits and larger shapes, GPU pulls ahead due to its massive parallel compute capacity. The shape `11008×4096×1` at 4-bit shows GPU with a clear latency advantage.

This kernel-level result isolates where the architectural advantage shifts: at very low bit-widths, the LUT approach on CPU registers beats GPU shared-memory-based dequantization; at higher bit-widths, GPU compute throughput dominates.

**End-to-end GPU comparison (Table 5):** For Llama-2-7B-2bit on Jetson AGX Orin:
- llama.cpp (CPU): 7.08 tokens/s, 15.0W, 2.12 J/token
- llama.cpp (GPU): 20.03 tokens/s, 30.8W, 1.54 J/token
- T-MAC (CPU): **15.62 tokens/s**, **10.4W**, **0.66 J/token**

T-MAC achieves 78% of GPU throughput at 34% of GPU power, yielding **2.3× better energy efficiency**. The paper notes that the GPU still wins on raw throughput for this model, but the energy advantage and the fact that T-MAC reaches the same order of magnitude of throughput (15.6 vs. 20.0 tokens/s) make CPU deployment competitive on this platform.

**Multi-platform comparison (Table 7):** Across three additional devices—Surface Laptop 7 (Snapdragon X Elite), OnePlus 12 (Snapdragon 8 Gen 3), and Jetson Orin NX (ARM Cortex-A78AE + Ampere GPU)—T-MAC on CPU outperforms GPU and NPU baselines for 2-bit models:
- Surface Laptop 7, Llama-2-7B-2bit: T-MAC achieves **31.83 tokens/s** versus 10.40 tokens/s on NPU (3× speedup), using only 4 of 12 CPU cores.
- OnePlus 12, Llama-2-7B-2bit: T-MAC achieves **16.62 tokens/s** versus 1.72 on GPU (9.7×) and 11.30* on NPU (1.5×, the NPU 2-bit figure is marked with "*" indicating deduction from 4-bit performance, since NPUs lack native 2-bit support).
- Jetson Orin NX, Llama-2-7B-2bit: T-MAC achieves **11.41 tokens/s** versus 7.94 on GPU (1.4×).

Even at 4-bit, T-MAC maintains advantages on some platforms: 2.1× over NPU on Surface Laptop 7, and 6.4× over GPU on OnePlus 12. The OnePlus 12 GPU result (1.60 tokens/s for 4-bit) is strikingly low, likely reflecting the Adreno GPU's limited suitability for LLM inference workloads compared to the Cortex-X4 CPU cores.

The paper is careful to note that these comparisons use "the minimum number of CPU cores that can fully leverage the memory bandwidth and nearly achieve optimal performance" (4 on Surface Laptop 7, ~4 on OnePlus 12, 6 on Jetson Orin NX). Using more cores would not improve throughput (memory-bandwidth-bound) but would increase power consumption.

### Ablation Studies and Robustness Checks

**Optimization breakdown on M2-Ultra (Figure 10):** T-MAC's performance is decomposed across six configurations applied step-by-step to multi-threaded GEMV kernels. The baseline, TM-base, uses hardware intrinsics for table lookup but implements no memory access optimizations. Its performance is up to 17% **slower** than llama.cpp, confirming that naive LUT is insufficient without the co-designed data layout. Each subsequent optimization adds measurable improvement:

- **+Table Quantization (TQ):** Performance becomes competitive with llama.cpp, roughly matching it. This demonstrates that the reduced table width enables more efficient register usage and reduces memory traffic.
- **+Tiling:** A maximum 1.45× speedup over the previous step. This is the largest single gain, confirming the paper's central thesis that LUT reuse through tiling is the critical enabler.
- **+Permutation:** An additional 1.39× speedup. This confirms that DRAM bandwidth utilization matters even after the LUT is register-resident, because the weight indices must still be streamed from memory.
- **+Tuning (AutoTVM):** The figure shows this provides minimal additional gain on M2-Ultra because "the default tiling configurations already align well with M2-Ultra registers and caches." However, the paper notes that tuning "should assist in finding a better configuration" for other devices with different cache hierarchies.
- **+Interleaving (→ T-MAC):** A 1.42× speedup by eliminating unpacking overhead. This is one of the larger contributions, underscoring that even small per-element instruction overheads accumulate across millions of weight indices.
- **+Fast Aggregation (TM+FA, optional):** Up to 1.29× additional speedup over T-MAC, but with accuracy degradation (see below).

The cumulative effect transforms TM-base from a net loss relative to llama.cpp into T-MAC's up to 6.6× gain. The speedup factors are multiplicative in sequence: ~1.45 × 1.39 × 1.42 ≈ 2.86× over TM+TQ, excluding the initial catch-up from table quantization.

**Table quantization error (Table 3, Table 4):** This is the critical ablation for correctness. At the kernel level (Table 3), the Normalized Mean Squared Error (NMSE) between T-MAC and the unquantized W_FP16_A_FP16 ground truth is nearly identical to llama.cpp's NMSE—e.g., for shape 4096×4096×1, NMSE is 3.33e-03 for llama.cpp versus 3.35e-03 for T-MAC. For 11008×4096×1, it's 3.44e-03 versus 3.46e-03. The difference is in the fourth significant digit and represents the quantization error from the low-bit weight representation itself, not from T-MAC's table quantization—the table quantization introduces no measurable additional error.

At the model level (Table 4), Llama-2-7B-4bit shows **identical** perplexity and accuracy between llama.cpp and T-MAC on all three benchmarks:
- WikiText-2 PPL: 5.96 for both
- LAMBADA PPL: 12.95 for both
- WinoGrande Acc: 70.8% for both

The un-quantized FP16 baseline achieves 5.80 / 12.65 / 71.0, so the dominant quality degradation comes from weight quantization itself, not from T-MAC's computation method. This is a strong result: T-MAC is mathematically equivalent to the dequantization approach to within the precision limits of INT8 table quantization, and those limits are below the noise floor of model quality measurement.

**Fast aggregation error (Table 3, Table 4):** When fast aggregation is enabled, NMSE increases to 8.09e-03 (2.5× T-MAC's standard NMSE) at the kernel level. At the model level, perplexity degrades noticeably: WikiText-2 PPL increases from 5.96 to 6.38 (+0.42), LAMBADA PPL increases from 12.95 to 13.99 (+1.04), and WinoGrande accuracy drops from 70.8% to 67.8% (-3.0 percentage points). The paper treats fast aggregation as "an option for users in scenarios that prioritize real-time performance and are less sensitive to accuracy," which is a reasonable engineering tradeoff but highlights a limitation: the 8-bit averaging instructions on current CPUs introduce non-negligible error that would need microarchitectural changes (native saturating 8-bit accumulation) to eliminate.

**Oracle vs. predicted difficulty bins (not applicable):** T-MAC does not employ difficulty estimation or adaptive strategy selection, so this common LLM inference ablation does not apply.

**Revision history in verifier context (not applicable):** T-MAC is a kernel library, not an inference strategy. There are no revisions or verifiers in the system.

**Single-threaded vs. multi-threaded scaling (Figure 6a vs. 6b):** The paper implicitly ablates the effect of parallelism by reporting both single-threaded and multi-threaded results. The key observation is that T-MAC's relative advantage is larger in single-threaded mode because dequantization overhead is more damaging when there is no parallelism to hide it. In multi-threaded mode, both T-MAC and llama.cpp become memory-bandwidth-bound, compressing the relative speedups. This is an important robustness check: T-MAC's advantage is not solely an artifact of single-thread execution; it persists in realistic multi-core deployments.

**Device diversity as implicit ablation (Table 2):** The paper tests across four devices spanning three orders of magnitude in memory bandwidth (17.1 GB/s on Raspberry Pi 5 to 819.2 GB/s on M2-Ultra), three CPU architectures (Apple Silicon, ARM Cortex-A76/78, Intel Core), and three operating systems (macOS, Linux, Windows). T-MAC's consistent advantage across this diversity suggests the LUT-centric design is not tightly coupled to any specific microarchitecture—though the absolute speedup magnitudes vary (larger on bandwidth-constrained devices, smaller on devices with powerful matrix coprocessors like AMX).

### Critical Assessment

**Claim 1: T-MAC achieves up to 4× end-to-end throughput increase.** This claim is supported by Figure 8, but with important qualifications. The 4× figure appears to come from the single-threaded Raspberry Pi 5 results for specific models (e.g., Llama-2-7B-2bit shows ~6.7×; other configurations may average to ~4×). However, the paper's abstract states "up to 4× increase in throughput" and the multi-threaded results in Figure 8b show more modest gains (1.1× to 2.3× on M2-Ultra). The "up to" qualifier is doing significant work: the realized throughput gain depends heavily on the device, the model bit-width, and the threading configuration. A practitioner deploying on a multi-core system with high memory bandwidth should expect gains closer to 1.5–2.5× for 4-bit models and 2–3× for 2-bit models, not the headline 4×. The paper would be strengthened by a summary table showing the throughput gain for each device-model-threading combination, rather than requiring the reader to estimate from bar charts.

**Claim 2: T-MAC reduces energy consumption by 70%.** The energy results in Figure 9 and Section 5.4 support this with nuance. The 70% figure specifically refers to the combination of reduced power and reduced time. The actual energy reductions are 20.6% for 4-bit, 61.2% for 2-bit, and 51.3% for BitNet-3B. The 70% in the abstract ("and 70% reduction in energy consumption compared to llama.cpp") rounds up the 61.2% figure and should be interpreted as "up to ~60–70%" for low-bit models, not as a universal claim. Importantly, the energy measurements are taken only on M2-Ultra, which has a unique power profile (Apple Silicon's efficiency cores, unified memory). Energy results on x86 or other ARM platforms may differ substantially. This is a genuine weakness: energy efficiency is a major selling point for edge deployment, and single-platform measurements are insufficient to establish generality.

**Claim 3: T-MAC scales linearly with weight bit-width.** Figure 6 provides compelling evidence. T-MAC's latency decreases approximately proportionally as bit-width drops from 4 to 3 to 2 to 1 across all shapes and devices. This contrasts sharply with llama.cpp's flat or negative scaling. The linear scaling is a direct consequence of the bit-serial decomposition (fewer bit-planes = proportionally less work) and the absence of fixed per-weight overhead (no dequantization). This claim is robustly supported. One minor limitation: the paper does not test bit-widths above 4, so the claim technically applies to the range 1–4 bits. Extrapolation to higher bit-widths (where the LUT approach would do more bit-planes, potentially losing its advantage over native INT8 multiplication) is not validated.

**Claim 4: CPU-based inference with T-MAC matches or exceeds GPU/NPU performance on the same device.** This claim is supported with significant platform-dependent qualifications. The kernel-level comparison in Figure 11 shows CPU defeating GPU only at W1A16; at W2A16 and W3A16 it is comparable; at higher bits, GPU wins. The end-to-end comparison in Table 5 shows T-MAC achieving 78% of GPU throughput—"matches" is generous; "approaches and exceeds in energy efficiency" is more precise. Table 7 shows CPU outperforming GPU and NPU on specific platforms, particularly for 2-bit models, but the comparisons have important caveats:

- The GPU baselines use llama.cpp's CUDA or OpenCL backends, which may not be as optimized as vendor-specific GPU inference libraries. A TensorRT-LLM baseline on Jetson would be stronger.
- The NPU baselines on Qualcomm platforms are "sourced from official data released by Qualcomm via Qualcomm AI Hub," which may not represent the best possible NPU performance for llama.cpp-style inference (Qualcomm's numbers may use different runtimes or optimizations).
- The NPU 2-bit numbers are asterisked as "deduced from 4-bit" because current NPUs do not natively support 2-bit inference. This is simultaneously a strength of T-MAC (it supports bit-widths that NPUs cannot) and a weakness of the comparison (we don't know how NPU would perform if it did support 2-bit natively).
- The GPU and NPU comparisons use different numbers of CPU cores than T-MAC, making it unclear whether the comparison is normalized for total silicon area or power budget. T-MAC uses "the minimum number of CPU cores that can fully leverage the memory bandwidth"—this is a reasonable engineering choice, but it means T-MAC leaves other CPU cores idle while GPU/NPU comparisons may use the full accelerator.

The paper would be strengthened by a FLOPs-matched or bandwidth-matched comparison that normalizes for the total hardware resources consumed, and by including vendor-optimized GPU baselines (TensorRT-LLM on Jetson, CoreML/MLX on Apple Silicon) rather than only llama.cpp's GPU backend.

**Claim 5: T-MAC provides a unified solution for any mixed bit-width.** The design principle is clearly articulated, but the experimental validation is limited to the bit-widths for which quantized models exist (1, 2, 3, 4 bits). The paper does not test W5, W6, W7, W8, or any non-power-of-two combination. The unification claim is algorithmic (the bit-serial decomposition works for any n), not empirical. Extrapolating from the 1–4 bit results, it is plausible that the linear scaling continues, but at higher bit-widths the dequantization baseline may become more competitive (native INT8 dot-product instructions are highly optimized), and the crossover point where T-MAC loses its advantage is not characterized.

**Missing experiments that would strengthen the paper:**

1. **Roofline analysis.** The paper argues that T-MAC saturates memory bandwidth more effectively than llama.cpp, but never presents a roofline plot showing achieved bandwidth utilization vs. arithmetic intensity for each kernel and device. This would make the bottleneck analysis quantitative rather than qualitative.

2. **Performance on x86 server CPUs.** All tested CPUs are edge/mobile-class. It is unclear how T-MAC performs on high-core-count server x86 processors (Xeon, EPYC) with AVX-512, where the larger vector width (512-bit) could hold larger LUTs (g=5 would fit in one register) and where memory bandwidth is higher. This would test the scalability claim to a different point in the hardware design space.

3. **Comparison against non-llama.cpp baselines.** While llama.cpp is the state-of-the-art for edge CPU deployment, other frameworks exist: ONNX Runtime with CPU execution providers, OpenVINO, MLC-LLM. A multi-framework comparison would establish whether T-MAC's advantage is over llama.cpp specifically or over the dequantization paradigm generally.

4. **Ablation of group size g.** The paper fixes g=4 based on register width, but never shows results for g=3 or g=5 (on AVX-512) to validate that the choice is optimal. This is a minor missed opportunity.

5. **Latency variance.** The paper reports mean latency over 100 runs but provides no standard deviations or percentiles. For real-time interactive applications, tail latency (p95, p99) matters as much as mean. T-MAC's random table access pattern might have different tail behavior than llama.cpp's sequential dequantization.

6. **Effect of weight permutation cost.** The paper states offline weight permutation has no inference cost, and this is true for a model loaded once and used many times. But for scenarios where models are frequently switched (multi-tenant edge serving), the permutation cost might be incurred repeatedly. Quantifying this cost would help practitioners assess suitability for their deployment patterns.

Overall, the experiments provide strong evidence for T-MAC's core claims about kernel acceleration, energy efficiency, and linear bit-width scaling. The end-to-end results convincingly demonstrate practical deployment feasibility on edge devices. The comparisons against GPU and NPU, while qualified, establish that CPU-based inference is now a legitimate alternative for low-bit models—a significant result that the experiments support, even if the magnitude of the advantage varies across platforms and bit-widths. The main limitations are the single-framework baseline, the lack of tail latency characterization, the single-platform energy measurements, and the absence of server-class CPU evaluation, all of which narrow the generality of the conclusions without undermining the core technical contribution.

## 6. Limitations and Trade-offs

### Single-Kernel Baseline: No Comparison Against Vendor-Optimized GPU/NPU Inference Stacks

**The assumption or constraint.** The paper compares T-MAC exclusively against llama.cpp—both its CPU kernels and its GPU/CUDA backend—and Qualcomm's official AI Hub numbers for NPU performance. However, llama.cpp's GPU backend is a cross-platform OpenCL/CUDA implementation that is not performance-competitive with vendor-optimized inference stacks. The authors do not test against TensorRT-LLM (NVIDIA's own optimized LLM inference framework for Jetson), MLC-LLM, CoreML/MLX (Apple's frameworks with ANE support), or Qualcomm's Snapdragon Neural Processing Engine SDK. The paper's claim in Section 5.7—"CPU-based LLM deployments on edge devices…without relying on GPUs"—is tested only against the weakest available GPU baseline for each platform.

The paper acknowledges this implicitly when it states that llama.cpp's GPU evaluation uses "the CUDA backend for the NVIDIA GPU and OpenCL backend for the Qualcomm GPU" (Section 5.7), but does not discuss the performance gap between llama.cpp's portable GPU backends and vendor-tuned alternatives.

**The consequence.** The headline finding that T-MAC on CPU "matches or exceeds GPU/NPU performance" may not hold against properly optimized accelerator inference stacks. On Jetson AGX Orin, llama.cpp GPU achieves 20.03 tokens/s for Llama-2-7B-2bit (Table 5); a TensorRT-LLM deployment with INT4 quantization, kernel auto-tuning, and fused attention might achieve significantly higher throughput. If the GPU baseline could achieve, say, 35 tokens/s instead of 20, T-MAC's 15.62 tokens/s would represent 45% of GPU throughput rather than 78%—a meaningfully different deployment calculus.

Similarly, the OnePlus 12 GPU result of 1.60 tokens/s for 4-bit (Table 7) is anomalously low and likely reflects the immaturity of llama.cpp's OpenCL backend on Adreno GPUs rather than the GPU's actual capability. A Qualcomm-optimized inference pipeline using the Snapdragon Neural Processing SDK might narrow or reverse the 6.4× advantage T-MAC shows.

The Qualcomm AI Hub NPU numbers are also noted as "official data released by Qualcomm," but these numbers may reflect peak theoretical throughput rather than end-to-end inference in a llama.cpp-style runtime. The mismatch in software stacks (llama.cpp for CPU vs. Qualcomm's own runtime for NPU) means the comparison is not purely hardware vs. hardware.

**What evidence exists in the paper.** The paper provides the specific framework and backend used for each GPU/NPU comparison in Section 5.7 and Table 7, which allows a careful reader to identify the baseline limitation, but does not discuss the implications or attempt any vendor-optimized baseline comparison.

**Mitigation status.** Not addressed. The paper does not mention TensorRT-LLM, CoreML, MLX, or the Snapdragon Neural Processing SDK as potential baselines, nor does it justify why llama.cpp's GPU backend is the appropriate comparison point. The claim that CPUs can replace GPUs for low-bit LLM inference requires testing against the best available GPU inference stack for each platform; until that comparison exists, the claim should be interpreted as "T-MAC on CPU matches or exceeds llama.cpp on GPU"—a weaker but still meaningful result.

### Energy Measurements Are Restricted to a Single Apple Silicon Platform

**The assumption or constraint.** The paper's energy efficiency results—10–17% power reduction, 20–61% energy reduction—are measured exclusively on the Apple M2-Ultra using `powermetrics`. This is stated in Section 5.4: "we conducted experiments using multi-threaded implementations on the M2 Ultra device." No energy measurements are provided for the x86 Surface Book 3, the ARM-based Jetson AGX Orin, or the ARM-based Raspberry Pi 5, despite these being the other three evaluation platforms.

Apple Silicon's power architecture is unique among the tested devices. The M2-Ultra uses a hybrid core configuration (performance + efficiency cores), unified memory with high bandwidth (819.2 GB/s), and a tightly integrated PMU (performance monitoring unit) accessible through `powermetrics`. The relationship between instruction mix and power draw on Apple Silicon—particularly the power cost of NEON TBL instructions versus Intel AVX2 PSHUF instructions or ARM Cortex NEON instructions—may differ substantially from other microarchitectures.

**The consequence.** A practitioner deploying T-MAC on a battery-constrained x86 laptop or an ARM-based robotics platform cannot reliably estimate energy savings from the M2-Ultra numbers. If the TBL/PSHUF lookup instructions are relatively more power-hungry on Intel's implementation than on Apple's, the 10–17% power reduction might shrink or vanish. Conversely, if x86 dequantization (SHIFT, AND, type conversion) is particularly inefficient on Intel's pipeline, the power savings might be larger.

The energy numbers also embed the M2-Ultra's specific idle power characteristics, memory controller efficiency, and clock-gating behavior. A Raspberry Pi 5, with completely different power management (no hybrid cores, different process node, different DRAM technology), could show a different relationship between T-MAC's instruction mix and total system power. Since T-MAC's most compelling deployment scenario is low-power edge devices (Section 5.3 emphasizes the 11 tokens/s on Raspberry Pi), the absence of power measurements on exactly those devices is a significant gap.

The paper reports the 61.2% energy reduction on Llama-2-7B-2bit as a key result (abstract and Section 5.4), but this number applies only to the device with the highest memory bandwidth and most sophisticated power management in the test suite—the device least representative of typical edge deployment constraints.

**What evidence exists in the paper.** Section 5.4 reports power and energy for exactly three models on exactly one device (M2-Ultra). The measurement methodology (500 ms sampling, 120-second continuous generation, `powermetrics`) is well-described. The paper does not claim that these results generalize to other platforms, but it also does not flag the single-platform limitation in the abstract or conclusions.

**Mitigation status.** None. The paper does not provide energy measurements for any other platform, does not discuss why other platforms were excluded, and does not speculate on whether the results would generalize. The abstract's statement of "70% reduction in energy consumption" appears without qualification about platform specificity, which could mislead practitioners targeting non-Apple edge hardware.

### Difficulty Estimation Cost for Model-Specific Tuning Is Not Characterized

**The assumption or constraint.** T-MAC's kernel performance depends on tuned hyperparameters—tiling sizes (Ntn, Mtm, Ktk), number of concurrent LUTs, group size g, and instruction scheduling choices—that are optimized per hardware platform using AutoTVM. The paper states in Section 4: "AutoTVM is used to automatically fine-tune the generated code for different hardware targets" and in Section 5.5 notes that tuning "should assist in finding a better configuration" for different devices.

However, the paper never reports the computational cost of this auto-tuning process. For each new hardware target, for each matrix shape, for each bit-width, AutoTVM must explore a search space of tiling configurations, compile candidate kernels, and benchmark them—a process that typically requires hours to days of dedicated CPU time. Furthermore, T-MAC's offline weight permutation (Section 3.2) must be recomputed whenever the tiling schedule changes, meaning that model weights must be re-permuted for each hardware target. The paper states that "this offline permutation does not introduce cost in inference" (Section 3.2), which is true, but it does introduce a per-device, per-model preprocessing cost that scales with model size.

**The consequence.** The headline speedup numbers (4× throughput, 6.6× kernel speedup) represent the performance *after* tuning and weight permutation are complete. For a practitioner deploying a new model on a new device, the total time-to-deployment includes: (1) the AutoTVM tuning time (exploring hundreds or thousands of tiling configurations), (2) the weight permutation time (reading the original model, decomposing into bit-planes, reordering tiles, interleaving bytes), and (3) the actual inference time. If AutoTVM tuning requires 4–8 hours per model shape per device, and a Llama-2-7B model has 6 distinct matrix shapes, the tuning cost could be 24–48 hours of dedicated CPU time before the first inference runs. For a one-time deployment, this is amortized over the model's lifetime; for a research or prototyping workflow where models change frequently, it could be prohibitive.

The weight permutation also creates a **model portability problem**. A permuted weight file is specific to one tiling schedule, which is specific to one hardware target's register file size, cache hierarchy, and SIMD width. A weight file prepared for M2-Ultra (with its specific tiling parameters) cannot be directly deployed on Raspberry Pi 5 without re-permutation. This is a departure from llama.cpp's approach, where the same GGUF weight file can run on any CPU without modification—the runtime handles layout adaptation. T-MAC trades this portability for performance, which is a reasonable engineering choice, but one that the paper does not discuss.

**What evidence exists in the paper.** The paper mentions AutoTVM in Section 4 and shows "Tuning" as a step in the optimization breakdown (Figure 10), where it provides minimal additional gain on M2-Ultra because "the default tiling configurations already align well with M2-Ultra registers and caches." This suggests that on some hardware, the default configurations may be good enough without extensive tuning, but the generality of this claim across the four tested platforms (with very different cache hierarchies) is not established. The paper provides no data on tuning time, tuning search space size, or weight permutation time.

**Mitigation status.** Not addressed. There is no discussion of tuning cost, no measurement of weight permutation time, and no mention of the portability tradeoff. The paper does not propose a method for sharing tiling configurations across similar hardware or for reducing the tuning burden. A practitioner reading the paper would not know what preprocessing investment is required to reproduce the reported speedups.

### No Tail Latency Characterization: Mean-Centric Evaluation Hides Jitter That Matters for Interactive Applications

**The assumption or constraint.** All latency and throughput measurements in Section 5 report **means** over repeated runs: "100 runs to calculate an average" for kernel benchmarks (Section 5.1), "generate 64 tokens for 20 iterations to evaluate token generation throughput" for end-to-end inference (Section 5.1). No standard deviations, percentiles (p95, p99), or latency distribution plots are provided anywhere in the paper.

This is particularly relevant because T-MAC's LUT-based approach introduces a new source of potential latency variance: the table lookup pattern is **random access into register-resident tables**. While register access itself is single-cycle, the *precomputation* of LUTs involves non-contiguous memory access (gathering activation elements at stride g), and the register swizzling operations on AVX2 (Section 4, "Register swizzling for efficient LUT precomputation") introduce data-dependent permutation sequences. Additionally, the weight index stream—while loaded sequentially from DRAM after permutation—contains random values that index into the table, creating a data-dependent access pattern within the CPU pipeline. If certain index patterns trigger speculative execution mispredictions or pipeline stalls, tail latency could be affected even if mean latency is not.

llama.cpp's dequantization approach, by contrast, involves entirely sequential access: load a packed weight byte, unpack it with deterministic SHIFT+AND instructions, multiply by the activation. There is no data-dependent control flow or memory access pattern. This is not to say llama.cpp has lower variance—its cache behavior may introduce its own jitter—but the variance characteristics of the two approaches are likely different, and the paper provides no data to characterize either.

**The consequence.** For interactive LLM applications (chat, voice assistants, real-time translation), **tail latency matters as much as mean throughput**. A system that achieves 30 tokens/s on average but drops to 5 tokens/s on 5% of tokens (due to LUT precomputation stalls or cache misses) provides a noticeably worse user experience than a system achieving 20 tokens/s with tight latency bounds. The user perceives jank and inconsistent typing speed rather than average throughput. Edge deployment scenarios (Section 2.1) emphasize "real-time task response" as a key benefit, making tail latency directly relevant to the paper's motivation.

The lack of variance data also makes it impossible to assess whether the reported speedups are statistically reliable. With a test set of 500 questions (in the context of LLM benchmarking, though T-MAC doesn't use this split directly) and 100 kernel runs per shape, the standard error of the mean latency should be quite small for the kernel benchmarks. But for end-to-end token generation, with only 20 iterations of 64 tokens each, the sample size is small enough that variance could meaningfully affect the reported throughput numbers. The paper does not assess whether the observed differences between T-MAC and llama.cpp are statistically significant.

**What evidence exists in the paper.** The methodology section states the measurement approach (10 warmup iterations, 100 runs, average reported) but provides no variance metrics. The paper does not discuss tail latency, jitter, or real-time performance guarantees. The "Performance Benchmark" figures (Figures 6, 7) show only mean latency as bar charts with no error bars.

**Mitigation status.** None. The paper treats latency as a single-point estimate throughout. There is no acknowledgment that variance might differ between T-MAC and the baseline, no discussion of real-time constraints for edge deployment, and no suggestion for how to bound tail latency in a LUT-based system.

### The Bit-Serial Framework's Upper-Bit-Width Crossover Point Is Not Characterized

**The assumption or constraint.** T-MAC's bit-serial decomposition reduces an n-bit weight matrix multiplication to n separate 1-bit LUT operations. The cost scales approximately linearly with n, which the paper demonstrates for n ∈ {1, 2, 3, 4} in Figure 6. However, the paper does not evaluate T-MAC at bit-widths above 4, nor does it characterize the crossover point where T-MAC's LUT approach becomes slower than a dequantization-based approach.

This matters because the dequantization baseline has a fundamentally different cost structure. For dequantization, the fixed overhead of unpacking and type conversion dominates at low bit-widths (explaining the flat llama.cpp curve in Figure 6). As bit-width increases toward 8, the dequantization overhead becomes a smaller fraction of total work (the actual INT8 dot-product computation grows with bit-width), while T-MAC's bit-serial loop length grows linearly. There must exist some n where the lines cross and dequantization becomes faster—but the paper provides no data to locate this crossover.

Furthermore, for 8-bit weights (INT8), native hardware support exists: CPUs have INT8 dot-product instructions (VMMADD on x86, SDOT/UDOT on ARM) that are highly optimized. T-MAC's LUT approach for W8A16 would require 8 bit-planes of table lookups and accumulations, competing against a single hardware-accelerated INT8 dot product. It is unlikely that T-MAC would win at 8-bit, but the paper provides no evidence to confirm this or to identify the exact bit-width where the advantage disappears.

**The consequence.** A practitioner evaluating T-MAC for a model quantized to 5, 6, or 8 bits (all realistic possibilities with modern post-training quantization) has no guidance on whether to expect speedup or slowdown. The paper's claim of "unified and scalable solution for any mixed bit-width" (Section 3, abstract) is algorithmically true—T-MAC can execute any bit-width—but the performance claim does not extend beyond 4 bits because it is untested.

The absence of a crossover characterization also makes it harder to understand the mechanism of T-MAC's advantage. If T-MAC wins at 4-bit but loses at 6-bit, the advantage is specific to the regime where dequantization overhead is large relative to compute. If T-MAC wins up to 8-bit, the advantage is more fundamental and reflects the intrinsic efficiency of LUT over multiplication. The former interpretation (supported by the flat llama.cpp curve in Figure 6) suggests T-MAC is primarily a workaround for hardware's lack of native mixed-precision support, not a universally faster computation method.

**What evidence exists in the paper.** The paper evaluates bit-widths 1, 2, 3, and 4 exclusively. The abstract and Section 3 describe the bit-serial decomposition as general for any n. Figure 6 shows linear scaling from 4 to 1 bits for T-MAC and flat scaling for llama.cpp. No results exist for bit-widths above 4.

**Mitigation status.** Not addressed. The paper does not discuss the existence of a crossover point, does not hypothesize where it might lie, and does not suggest that users should fall back to dequantization-based inference for higher bit-widths. The "unified solution" framing implies applicability to all bit-widths, but the performance evidence only covers the low-bit regime.

### Offline Preprocessing Creates a Tight Coupling Between Compiled Kernels and Specific Weight Matrices

**The assumption or constraint.** T-MAC's weight preprocessing pipeline (Section 3.2) performs three offline transformations that are specific to the combination of model architecture, weight matrix shapes, and hardware tiling schedule: (1) bit-serial decomposition into n one-bit matrices, (2) weight permutation (reordering tiles to be sequential in memory according to the access schedule), and (3) weight interleaving (rearranging bytes to eliminate little-endian unpacking overhead). These transformations produce a binary weight representation that is tightly coupled to the specific compiled kernel that will consume it.

The paper states that this is done offline and "does not introduce cost in inference" (Section 3.2), which is true for a deployment where the model is loaded once and used many times. However, this creates a more fundamental constraint that the paper does not discuss: **the preprocessed weights are not portable across hardware or kernel versions.** If AutoTVM selects different tiling parameters for Raspberry Pi 5 versus M2-Ultra (as it should, given their vastly different cache hierarchies and SIMD widths), the weight file for one platform is incompatible with the kernel for the other. Even on the same hardware, if a kernel is re-tuned (e.g., to exploit a newly discovered optimization), the weight permutation must be recomputed.

This is a departure from the portability model of frameworks like llama.cpp, where the same GGUF weight file runs on any CPU target without modification. In llama.cpp, the weight layout is standardized (e.g., Q4_0, Q2_K), and the kernel adapts to the layout at runtime. T-MAC inverts this: the kernel's tiling schedule is fixed at compile time, and the weights are physically rearranged to match.

**The consequence.** The preprocessing cost—time and storage—is incurred per (model, hardware, kernel version) tuple. For a deployment serving multiple models on heterogeneous hardware, this multiplies storage requirements and pre-deployment processing time. For a development workflow where kernels are iteratively optimized, every kernel change triggers a full model re-permutation.

The weight file size also changes after preprocessing. While bit-serial decomposition does not increase the total number of bits (an n-bit weight becomes n one-bit weights, which is the same total information), the permutation step may introduce padding to align tiles with memory transaction boundaries, slightly increasing file size. The paper provides no measurements of post-preprocessing weight file sizes.

Additionally, the preprocessing pipeline must be executed on a machine with sufficient memory to hold both the original and transformed weight matrices simultaneously (the bit-serial decomposition produces n separate matrices, temporarily quadrupling memory for a 4-bit model during preprocessing). For large models on memory-constrained edge devices, this could require preprocessing on a separate, more capable machine.

**What evidence exists in the paper.** The paper describes the three offline transformations in Section 3.2 and states that they incur no inference cost. No measurements of preprocessing time, memory usage, or output file size are provided. The paper does not discuss weight portability or the coupling between kernel tiling and weight layout.

**Mitigation status.** Not addressed. The paper does not acknowledge the portability tradeoff, does not measure preprocessing costs, and does not propose techniques to reduce the coupling (e.g., a standardized tiling that works reasonably well across a family of similar hardware). The statement that offline permutation "does not introduce cost in inference" is accurate but incomplete—it omits the deployment-time cost of performing the permutation and the portability cost of maintaining hardware-specific weight files.

## 7. Implications and Future Directions

### How This Work Changes the Landscape

T-MAC does not propose a new quantization algorithm or a new model architecture. It proposes a **fundamental shift in the computational paradigm** for low-bit LLM inference: from data-type-centric multiplication to bit-wise table lookup. This is not an incremental optimization over dequantization—it is a reframing of what the primitive operation should be. The implications ripple through how we think about hardware suitability, inference system design, and the deployment economics of edge AI.

**The CPU becomes a legitimate inference platform for low-bit models.** Before T-MAC, the prevailing assumption was that CPUs are a fallback for edge LLM deployment—usable when no GPU or NPU is available, but always suboptimal. The evidence in Section 5.7 challenges this directly: T-MAC on CPU achieves 78% of GPU throughput on Jetson AGX Orin while consuming 34% of the power (Table 5), and outperforms NPUs on Surface Laptop 7 and OnePlus 12 for 2-bit models (Table 7). The mechanism is not "CPUs got faster" but rather that the LUT paradigm shifts the bottleneck from compute throughput—where GPUs and NPUs dominate—to **register-level random access latency**, where CPUs have a structural advantage through single-cycle TBL/PSHUF instructions. The title "CPU Renaissance" is a specific claim that has now been empirically substantiated: for low-bit models on edge devices with unified memory, the pervasive CPU can match or exceed dedicated accelerators. This changes the hardware procurement calculus for edge AI deployments, making the CPU a first-class inference target rather than a compromise.

**Quantization's performance promise can actually be realized.** A frustrating paradox has plagued low-bit LLM deployment: reducing weight precision from 4-bit to 2-bit reduces the model's memory footprint, but the dequantization overhead prevents any corresponding inference speedup. Figure 6 makes this failure visible—llama.cpp's latency is flat or increasing as bit-width drops. T-MAC resolves this paradox by eliminating dequantization entirely. Its bit-serial decomposition means that halving the bit-width roughly halves the number of bit-planes to process, and Figure 6 demonstrates that this linear scaling is actually achieved in practice. The implication for the quantization research community is significant: quantization algorithms that push to lower bit-widths (OneBit at 1-bit, BitNet at 1.58-bit, BitDistiller at 2-bit) are no longer fighting against a dequantization tax that erases their benefit. The computational incentive now aligns with the memory reduction incentive, making extreme low-bit quantization (2-bit and below) a genuinely attractive deployment target rather than a research curiosity with limited practical speedup.

**The LUT approach reconciles contradictory architectural priorities.** The paper resolves an implicit tension in edge AI hardware design. GPUs and NPUs are optimized for high-throughput compute on regular data access patterns—matrix multiplication tiles, convolution windows, attention blocks. But the decode stage of LLM inference—which dominates token generation—is memory-bound GEMV with batch size 1, where arithmetic intensity is low and data access patterns are already bottlenecked by DRAM bandwidth. T-MAC demonstrates that for this specific workload profile, **the right computational primitive is not a high-throughput multiplier but a low-latency lookup table**. This reopens the question of what an optimal edge AI accelerator should look like. The paper explicitly points toward this in its conclusion: "T-MAC also opens up the broad opportunity for novel LLM hardware accelerator design based on LUT, as LUT is much more efficient in hardware implementation than multiplications." A custom accelerator built around a register file and TBL-like lookup units, rather than multiply-accumulate arrays, could achieve even better energy efficiency than T-MAC on general-purpose CPUs—and T-MAC provides the algorithmic template for how such an accelerator would operate.

**The diversity of quantization formats becomes tractable.** The paper's bit-serial decomposition addresses a fragmentation problem that was growing worse as quantization research diversified. GPTQ (4-bit), AWQ (4-bit), BitDistiller (2–3-bit), OneBit (1-bit), BitNet (1.58-bit ternary), and emerging formats each required bespoke kernel implementations in the dequantization paradigm. T-MAC reduces all of them to the same 1-bit LUT primitive, with the bit-width controlled by a loop iteration count. This unification is not merely an engineering convenience—it means that quantization researchers can propose new formats without waiting for kernel engineers to implement and optimize support for each one. The deployment path from a novel quantization scheme to an efficient inference kernel shrinks from months of hand-tuned assembly to reusing the same tested LUT engine. This lowers the barrier to entry for quantization innovation and accelerates the research-to-deployment pipeline.

**Energy becomes a first-class metric for inference system design.** The paper's energy measurements (Figure 9) demonstrate that T-MAC's LUT approach reduces total energy consumption by 61% for 2-bit Llama-2-7B and 51% for BitNet-3B on M2-Ultra. These are not marginal improvements—they change the feasibility of battery-operated LLM inference. For a smartphone or robotics platform with a fixed energy budget, a 2× reduction in Joules per token means either doubling the usable interaction time or halving the battery capacity required. The mechanism—replacing power-hungry multiply-accumulate and dequantization instructions with lower-power lookup instructions—is likely to generalize across microarchitectures, though the paper only measures M2-Ultra. This positions energy efficiency, not just throughput, as the headline metric for future inference system comparisons, which aligns with the edge deployment motivation (Section 2.1) but has been underemphasized in prior work that focused primarily on latency.

### Follow-Up Research This Work Enables

**Characterizing the T-MAC crossover point against dequantization at higher bit-widths.** The paper evaluates T-MAC at 1–4 bits but never identifies the bit-width where the LUT approach loses its advantage over dequantization. This is a critical gap because the bit-serial loop length grows linearly with bit-width, while dequantization overhead becomes proportionally smaller as the actual INT8 compute dominates. A follow-up study should benchmark T-MAC against llama.cpp and vendor-optimized INT8 GEMM libraries (oneDNN, QNNPACK) at W4A16, W5A16, W6A16, W7A16, and W8A16 across the same four devices plus a server x86 platform (Xeon with AVX-512). The key measurement is the **crossover bit-width**: the highest precision at which T-MAC still provides a speedup, and how that crossover varies with matrix shape (GEMV vs. GEMM) and memory bandwidth. This would establish the practical range of the "unified solution" claim and give practitioners clear guidance on when to use T-MAC versus when to fall back to hardware-accelerated INT8 dot products. A negative result—T-MAC already loses at 5-bit—would not diminish the 1–4 bit contribution but would bound its generality.

**T-MAC as a template for LUT-based custom accelerator design.** The paper's conclusion explicitly invites this: "T-MAC also opens up the broad opportunity for novel LLM hardware accelerator design based on LUT." A first-order follow-up would design and simulate a minimal LUT accelerator—essentially, a wide register file feeding an array of TBL-like lookup units, with dedicated accumulation hardware and a DMA engine optimized for streaming permuted weight indices from DRAM. The design space includes: the register file width (determining maximum group size g), the number of parallel lookup units, the accumulation precision (INT8 vs. INT16 vs. FP16, with the fast aggregation tradeoff from Table 4 as a starting point), and the memory hierarchy for weight streaming. The evaluation should compare against an iso-area systolic array (the standard ML accelerator building block) for GEMV workloads at 1–4 bit precision, measuring throughput per mm² and energy per operation. T-MAC's optimization breakdown (Figure 10) provides the algorithmic decomposition; the hardware question is whether a specialized LUT engine can outperform a general-purpose CPU by enough to justify the silicon area, and whether the LUT approach is fundamentally more energy-efficient than multiplication in hardware (as the paper claims) or whether CPU register files are simply a uniquely good match.

**Combining T-MAC's LUT kernels with speculative decoding for end-to-end acceleration.** The paper's end-to-end results (Figure 8) show that after T-MAC accelerates the linear layers, Amdahl's Law kicks in: other components (attention, KV-cache management, activation functions) become the bottleneck, and the multi-threaded speedup over llama.cpp shrinks to 1.1–2.3× on M2-Ultra. Speculative decoding—where a small draft model generates candidate tokens that the large model verifies in parallel—shifts work from memory-bound serial GEMV to compute-bound parallel GEMM, potentially amplifying T-MAC's advantage because T-MAC also accelerates GEMM (Figure 7). A follow-up should integrate T-MAC with a speculative decoding framework (e.g., Medusa or standard draft-model speculation) and measure end-to-end throughput for Llama-2-7B-2bit across the four edge devices. The hypothesis is that the combination provides multiplicative gains: T-MAC reduces the cost per forward pass, and speculative decoding amortizes that cost over multiple tokens, resulting in throughput improvements beyond what either technique achieves alone. The experiment should report both throughput and the draft-model acceptance rate, which affects how much of T-MAC's GEMM acceleration is actually realized.

**Extending T-MAC to activation-quantized LLMs (W#A# where A < 16).** T-MAC's design assumes high-precision activations (A16 or A8) and low-bit weights (W1–W4). This matches the current practice where activation quantization is difficult due to outliers (Section 1). However, research on activation quantization is progressing—SmoothQuant and LLM.int8() address outlier channels, and some systems now deploy W4A8 or W4A4. If activations are quantized to 4 or 8 bits, the LUT precomputation changes: instead of summing FP16 activation values with signs, the LUT entries become sums of quantized activation values, and the table quantization step (Section 3.3) may interact differently with already-quantized values. A follow-up should adapt T-MAC's LUT precomputation to accept INT8 activations directly, measure whether the table quantization error compounds with activation quantization error (using the kernel-level NMSE and model-level perplexity methodology from Section 5.6), and benchmark against dequantization baselines at W4A8 and W2A8 on the same four edge devices. If T-MAC maintains accuracy and speedup for quantized activations, its applicability broadens to the full spectrum of mixed-precision configurations.

**Stress-testing T-MAC on non-LLM sparse or structured workloads.** T-MAC is designed for dense GEMV/GEMV—the compute pattern of transformer linear layers. But the LUT approach may generalize to other workloads with low-bit parameters and repeated dot products: recommendation models (embedding tables with low-bit entries), sparse expert mixtures (MoE layers with low-bit expert weights), or graph neural networks (low-bit feature aggregation). A stress-test follow-up would benchmark T-MAC's LUT kernel against dequantization on matrix shapes from these domains, specifically testing: (a) extremely rectangular matrices (M << K or K << M, as in embedding lookups), (b) batched GEMV with moderate batch sizes (2–8, as in tree-search or beam-search decoding), and (c) sparse weight matrices where many entries are zero (as in pruned models). The key question is whether T-MAC's tiling strategy (optimized for Llama-2 shapes and batch size 1) degrades gracefully or requires re-tuning for these different operational regimes. A negative result on sparse or batched workloads would delineate T-MAC's domain of applicability, while a positive result would extend its impact beyond the LLM inference niche.

**Automated difficulty estimation for T-MAC's tiling parameter selection.** The paper uses AutoTVM for offline tuning of tiling parameters (Section 4), but never characterizes the tuning cost or the transferability of tuned configurations across similar hardware. A practitioner-facing follow-up would: (1) measure AutoTVM's tuning time for Llama-2-7B shapes on each of the four devices, reporting the search space size and the number of trials required to converge; (2) test whether a configuration tuned on one device transfers to another with similar cache hierarchy (e.g., M2-Ultra to M2-Pro, or Raspberry Pi 5 to other Cortex-A76 devices), measuring the performance gap versus a device-specific tune; (3) develop a lightweight cost model that predicts near-optimal tiling parameters from hardware specifications (register count, cache sizes, SIMD width) without exhaustive search. This would address the portability concern (the paper's preprocessed weights are hardware-specific) and reduce the deployment friction for practitioners who cannot afford per-device AutoTVM runs. A strong result—configurations transferring with <5% performance loss across same-architecture devices—would make T-MAC practical for heterogeneous edge fleets.

### Practical Applications and Downstream Use Cases

**On-device conversational agents on low-cost hardware.** T-MAC enables interactive LLM inference on devices previously considered incapable of it. The 11 tokens/s result for BitNet-b1.58-3B on Raspberry Pi 5 (Figure 8) means a $60 single-board computer can now run a 3B-parameter model at reading speed. This opens the door to offline voice assistants, educational tools, and accessibility devices that operate entirely on-device—no cloud dependency, no subscription, no privacy concerns. The energy consumption (though not directly measured on Raspberry Pi, the 51% reduction on M2-Ultra for BitNet in Figure 9 suggests similar benefits) means battery-powered operation is feasible. A concrete deployment: a portable language learning device that runs BitNet-3B for conversational practice, with a battery life of several hours on commodity LiPo cells, costing under $100 in parts.

**Privacy-preserving smartphone assistants with extended battery life.** Current on-device LLM deployments (Apple Intelligence, Google's Gemini Nano, Samsung's Galaxy AI) run on specialized NPUs and are restricted to high-end devices. T-MAC's results on OnePlus 12 (Table 7: 16.62 tokens/s for 2-bit Llama-2-7B on CPU, 1.5× the NPU's estimated 2-bit performance) suggest that CPU-based inference can match or exceed NPU throughput on flagship smartphones while consuming less power (the M2-Ultra data shows 10–17% power reduction for T-MAC vs. llama.cpp). A practical deployment would use T-MAC on the CPU cores for a 2-bit Llama-2-7B, leaving the NPU free for other tasks (camera processing, voice recognition) and extending battery life by reducing total SoC power draw. The privacy benefit is inherent: all inference stays on-device, with no data leaving the phone, addressing the "user data protection" motivation in Section 1.

**Battery-constrained robotics with real-time language understanding.** Service robots, drones, and autonomous vehicles operate under strict energy budgets and often lack discrete GPUs. T-MAC's energy reduction (61% for 2-bit Llama-2-7B on M2-Ultra, Figure 9) directly extends operational time. A robot using a Jetson AGX Orin-class compute module could run continuous LLM inference for natural language command understanding at 15.62 tokens/s for 2-bit Llama-2-7B (Table 5) while consuming 10.4W for the CPU portion—leaving the GPU available for vision and navigation tasks. The 2.3× energy efficiency improvement over GPU-based inference (0.66 vs. 1.54 J/token, Table 5) translates to more than double the interaction time on a fixed battery capacity, which is a decisive advantage for field-deployed systems that cannot recharge frequently.

**Cost-efficient batch inference for synthetic data generation.** Organizations generating synthetic training data with LLMs (for fine-tuning smaller models, data augmentation, or self-improvement loops) often run large batches through cloud GPU instances. T-MAC on high-core-count server CPUs (not evaluated in the paper but a natural extension) could provide a cheaper alternative. If T-MAC achieves comparable throughput-per-dollar on CPU instances versus GPU instances for low-bit models, the economic calculus shifts toward CPU-based batch inference, which benefits from greater instance availability, lower spot pricing, and simpler scaling. The paper's GEMM results (Figure 7) showing 4–5.3× speedups on ARM and x86 platforms for batch size 256 prefill suggest this is plausible, though the paper does not evaluate server-class hardware or provide a cost analysis. A deployment would use T-MAC on AWS Graviton or Azure Ampere instances for overnight batch jobs generating millions of training examples from a 2-bit teacher model, with the cost savings quantified against equivalent GPU instance hours.
